================================================================
GRAPHQL INPUT TYPES — IN DEPTH
================================================================

1. WHAT ARE INPUT TYPES?
------------------------
Input types are special Object-like types used exclusively as ARGUMENT values.
They allow passing complex, structured data into queries and mutations.

```graphql
input CreateProductInput {
  name: String!
  price: Float!
  description: String
  categoryId: ID!
  tags: [String!]
}

type Mutation {
  createProduct(input: CreateProductInput!): Product!
}
```

Input types are fundamentally different from Object types:
  - Object types = OUTPUT (what the server returns)
  - Input types  = INPUT  (what the client sends)

2. WHY INPUT TYPES EXIST
--------------------------
  a) TYPE SAFETY: Arguments can be strongly typed and validated
  b) REUSABILITY: Same input type can be used in multiple mutations
  c) CIRCULAR REFS: Input types prevent circular input references
     (Object types could have fields pointing back to themselves as inputs)
  d) SEPARATION OF CONCERNS: Read model (Object) ≠ Write model (Input)
  e) EVOLUTION: You can change the input without affecting the output type

3. INPUT TYPE SYNTAX
---------------------
```graphql
input TypeName {
  fieldName: FieldType
  fieldWithDefault: String = "default value"
  requiredField: String!
  optionalField: String
  nestedInput: AnotherInputType
  listField: [String!]
}
```

Rules for Input type fields:
  ✓ Scalar types (Int, Float, String, Boolean, ID)
  ✓ Custom scalar types (DateTime, UUID, etc.)
  ✓ Enum types
  ✓ Other Input types (nesting is allowed)
  ✓ Lists of the above: [String!], [TagInput!]
  ✗ Object types (User, Product, etc.) — NOT ALLOWED
  ✗ Interface types — NOT ALLOWED
  ✗ Union types — NOT ALLOWED
  ✗ Circular Input references — NOT ALLOWED (spec disallows)

4. COMMON PATTERNS
------------------

  4.1 CREATE vs UPDATE Input Types
  ---------------------------------
  Create: All required fields are non-null
  Update: All fields are optional (partial update / PATCH semantics)

  ```graphql
  input CreateUserInput {
    name: String!
    email: String!
    password: String!
    roleId: ID
    address: AddressInput
  }

  input UpdateUserInput {
    name: String        # null = don't change
    email: String       # null = don't change
    address: AddressInput
  }

  type Mutation {
    createUser(input: CreateUserInput!): User!
    updateUser(id: ID!, input: UpdateUserInput!): User!
  }
  ```

  4.2 Filter Input Types
  -----------------------
  ```graphql
  input ProductFilter {
    nameContains: String
    minPrice: Float
    maxPrice: Float
    categoryIds: [ID!]
    inStock: Boolean
    tags: [String!]
    createdAfter: DateTime
    createdBefore: DateTime
  }

  input ProductOrderBy {
    field: ProductSortField!
    direction: SortDirection = DESC
  }

  enum ProductSortField {
    NAME
    PRICE
    CREATED_AT
    POPULARITY
  }

  type Query {
    products(
      filter: ProductFilter
      orderBy: ProductOrderBy
      first: Int = 20
      after: String
    ): ProductConnection!
  }
  ```

  4.3 Nested Input Types
  ----------------------
  ```graphql
  input AddressInput {
    street: String!
    city: String!
    state: String
    country: String!
    postalCode: String!
    coordinates: CoordinatesInput
  }

  input CoordinatesInput {
    latitude: Float!
    longitude: Float!
  }

  input CreateBusinessInput {
    name: String!
    email: String!
    phone: String
    headquarters: AddressInput!
    branches: [AddressInput!]
    settings: BusinessSettingsInput
  }

  input BusinessSettingsInput {
    currency: String = "USD"
    timezone: String = "UTC"
    locale: String = "en-US"
    notifications: NotificationSettingsInput
  }
  ```

  4.4 Pagination Input
  --------------------
  ```graphql
  input PaginationInput {
    first: Int
    after: String
    last: Int
    before: String
  }

  # Or simpler offset-based:
  input PageInput {
    page: Int! = 1
    pageSize: Int! = 20
  }
  ```

5. DEFAULT VALUES
------------------
Input fields can have default values using `=`:

```graphql
input SearchInput {
  query: String!
  first: Int = 10       # Default 10 results
  after: String         # No default (null by default)
  sortBy: SortField = RELEVANCE
  includeInactive: Boolean = false
}
```

Default values:
  - Must be a valid value for the field's type
  - Applied when the client omits the field
  - NOT applied when the client explicitly sends null for a nullable field

  Null vs Omitted (important distinction):
  - Omitted field → default value applies
  - `field: null` explicitly → null value (ignores default)
  - This matters for update operations: omit = don't change, null = clear field

6. INPUT VALIDATION
--------------------
Validation happens at two levels:

  Level 1: GraphQL type validation (automatic)
  - Non-null fields must be provided
  - Enum values must be valid
  - Types must match (can't send string where Int is expected)

  Level 2: Business validation (custom, in resolvers)
  ```java
  @MutationMapping
  public User createUser(@Argument CreateUserInput input) {
    // Business validation
    if (userRepository.existsByEmail(input.getEmail())) {
      throw new GraphQLException("Email already registered");
    }
    if (input.getPassword().length() < 8) {
      throw new GraphQLException("Password must be at least 8 characters");
    }
    // Proceed with creation
    return userService.create(input);
  }
  ```

  Using Bean Validation (Spring):
  ```java
  public record CreateUserInput(
    @NotBlank String name,
    @Email String email,
    @Size(min = 8) String password
  ) {}

  // In resolver:
  @MutationMapping
  @Validated
  public User createUser(@Argument @Valid CreateUserInput input) { ... }
  ```

7. INPUT TYPE IN JAVA (SPRING FOR GRAPHQL)
-------------------------------------------
Spring for GraphQL maps input types to Java records or POJOs:

```java
// As Java record (preferred — immutable)
public record CreateProductInput(
  String name,
  Float price,
  String description,
  String categoryId,
  List<String> tags
) {}

// As Java class (for more complex cases)
public class UpdateProductInput {
  private String name;
  private Float price;
  private String description;
  // getters, setters, etc.
}

// In controller:
@MutationMapping
public Product createProduct(@Argument CreateProductInput input) {
  return productService.create(input);
}
```

Field name mapping (SDL camelCase → Java camelCase — automatic):
  SDL: `categoryId` → Java: `categoryId` ✓ (same)
  SDL: `createdAfter` → Java: `createdAfter` ✓

8. THE ONE-OF INPUT PATTERN (EXPERIMENTAL)
-------------------------------------------
@oneOf directive allows exactly ONE field to be non-null (like a discriminated union for inputs):

```graphql
input UserLookupInput @oneOf {
  id: ID
  email: String
  username: String
}

type Query {
  findUser(by: UserLookupInput!): User
}
```

Client must provide exactly one field:
  ✓ { id: "123" }
  ✓ { email: "alice@example.com" }
  ✗ { id: "123", email: "alice@example.com" }   → validation error
  ✗ {}                                           → validation error

Status: @oneOf is in the GraphQL spec as an RFC. Support varies by library.
Spring for GraphQL: check current version for @oneOf support.

9. INPUT TYPES AND IDEMPOTENCY
--------------------------------
For safe mutation design, include idempotency keys in inputs:

```graphql
input PlaceOrderInput {
  items: [OrderItemInput!]!
  shippingAddressId: ID!
  paymentMethodId: ID!
  idempotencyKey: String!   # Client-generated UUID, server deduplicates
}
```

This prevents double-billing if the client retries due to network failures.

10. VERSIONING INPUT TYPES
---------------------------
Input types can evolve without breaking changes:
  ✓ Add optional fields (with defaults or nullable)
  ✓ Mark fields as @deprecated
  ✗ Remove required fields (breaking)
  ✗ Add required fields to existing inputs (breaking)
  ✗ Change field types (breaking)

Strategy for breaking changes:
  - Add a NEW input type (CreateUserInputV2) with the new contract
  - Gradually migrate mutations to use the new input type
  - Deprecate the old mutation and eventually remove it

11. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: Why can't Object types be used as input field types?
A: Object types can have fields with arguments (e.g., `posts(filter: ...)`)
   which don't make sense in input context. More importantly, Object types
   are cyclic (User has posts, Post has author [User]), and allowing Object
   types in inputs would create circular input types, making validation
   undecidable. The spec explicitly restricts input fields to scalars, enums,
   and other input types.

Q: What is the difference between an Input type and an Object type?
A: Object types are output types (returned to the client). Input types are
   input types (sent by the client). Object fields can have arguments; Input
   fields cannot. Object types can implement interfaces; Input types cannot.
   Object types can be part of Unions; Input types cannot.

Q: How do you handle partial updates (PATCH semantics) in GraphQL?
A: Define an Update input type where all fields are nullable (optional).
   A null value means "don't change this field". Document this clearly.
   Some teams use a more explicit pattern with wrapper types or the @oneOf
   pattern. Consider: null = clear the field vs null = no-op are different
   semantics, so document your convention.

Q: What happens if a client sends a required input field (!) as null explicitly?
A: GraphQL validation rejects it immediately before reaching the resolver.
   Non-null input fields (`name: String!`) cannot be null. The client gets
   a validation error: "Expected non-null value for field 'name'."

Q: What is the @oneOf directive on input types?
A: It restricts input objects to have exactly one non-null field set (like a
   discriminated union). Useful for "find by X or Y or Z" patterns where
   exactly one identifier is required. It's in the spec as an RFC but support
   varies by server library.

Q: How do you validate input types beyond type checking?
A: GraphQL runtime validates types, non-null, and enum values automatically.
   For business rules (email uniqueness, password strength, etc.), validate
   in the resolver. In Spring, use Bean Validation (@Valid, @NotBlank, @Email)
   on input record fields combined with @Validated on the controller.
