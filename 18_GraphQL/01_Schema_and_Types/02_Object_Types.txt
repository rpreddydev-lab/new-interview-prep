================================================================
GRAPHQL OBJECT TYPES — IN DEPTH
================================================================

1. WHAT ARE OBJECT TYPES?
--------------------------
Object types are the primary building blocks of a GraphQL schema. They
represent entities in your domain — Users, Products, Orders, etc.

An Object type is a named set of fields. Each field has:
  - A name (must start with a letter or underscore, no spaces)
  - A return type (scalar, enum, another object type, etc.)
  - Optional arguments
  - Optional description
  - Optional directives

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  age: Int
  createdAt: DateTime!
}
```

2. FIELD ARGUMENTS
-------------------
Fields can accept arguments — they work like function parameters.

```graphql
type User {
  # Simple argument
  posts(status: PostStatus): [Post!]!

  # Multiple arguments with defaults
  orders(
    status: OrderStatus
    from: DateTime
    to: DateTime
    first: Int = 10
    after: String
  ): OrderConnection!

  # Computed field with argument
  avatar(
    size: Int = 200
    format: ImageFormat = WEBP
  ): String!
}
```

Arguments differ from variables:
  - Arguments are part of the field definition in the SCHEMA
  - Variables are passed by the client per-request
  - They meet at the query: `{ user { posts(status: PUBLISHED) { title } } }`

3. RELATIONSHIPS BETWEEN TYPES
--------------------------------
Object types can reference each other, forming a graph:

```graphql
type User {
  id: ID!
  name: String!
  posts: [Post!]!         # One-to-many: User has many Posts
  address: Address        # One-to-one: User has optional Address
}

type Post {
  id: ID!
  title: String!
  author: User!           # Many-to-one: Post belongs to User
  comments: [Comment!]!
  tags: [Tag!]!
}

type Comment {
  id: ID!
  body: String!
  author: User!
  post: Post!
}

type Address {
  street: String!
  city: String!
  country: String!
}
```

Circular references are allowed and common:
  User → Post → Comment → User (commenting on posts)

4. ROOT OBJECT TYPES
---------------------
Three special object types serve as entry points:

```graphql
type Query {
  # Every query field is a root resolver
  user(id: ID!): User
  users(filter: UserFilter, first: Int, after: String): UserConnection!
  me: User          # Current authenticated user
  product(id: ID!): Product
  search(text: String!): [SearchResult!]!
}

type Mutation {
  # Every mutation field is a write operation
  createUser(input: CreateUserInput!): UserPayload!
  updateUser(id: ID!, input: UpdateUserInput!): UserPayload!
  deleteUser(id: ID!): DeletePayload!
  login(email: String!, password: String!): AuthPayload!
}

type Subscription {
  # Real-time event streams
  userCreated: User!
  orderStatusChanged(orderId: ID!): Order!
  messageAdded(channelId: ID!): Message!
}
```

5. IMPLEMENTING INTERFACES
---------------------------
Object types can implement one or more interfaces:

```graphql
interface Node {
  id: ID!
}

interface Timestamped {
  createdAt: DateTime!
  updatedAt: DateTime
}

type Product implements Node & Timestamped {
  id: ID!
  createdAt: DateTime!
  updatedAt: DateTime
  # Product-specific:
  name: String!
  price: Float!
  sku: String!
}
```

Rules:
  - The implementing type MUST include all interface fields
  - The implementing type MAY add additional fields
  - A type can implement multiple interfaces (separated by &)
  - The return type of an interface field CAN be a subtype of the interface's
    declared type (covariant return — added in GraphQL spec 2021)

6. FIELD ALIASING (CLIENT SIDE)
---------------------------------
Clients can rename fields in the response using aliases. This is a query
feature, not a schema feature.

```graphql
query {
  primary: user(id: "1") {
    name
  }
  secondary: user(id: "2") {
    name
  }
}
```

Returns:
```json
{
  "data": {
    "primary": { "name": "Alice" },
    "secondary": { "name": "Bob" }
  }
}
```

7. COMPUTED FIELDS
------------------
Object type fields don't have to map directly to database columns.
They can be computed by resolvers:

```graphql
type User {
  id: ID!
  firstName: String!
  lastName: String!
  fullName: String!          # Computed: firstName + " " + lastName
  postCount: Int!            # Computed: COUNT from posts table
  isOnline: Boolean!         # Computed: check presence cache
  profileUrl: String!        # Computed: construct URL from id
}
```

In Spring for GraphQL:
```java
@SchemaMapping(typeName = "User", field = "fullName")
public String fullName(User user) {
  return user.getFirstName() + " " + user.getLastName();
}

@SchemaMapping(typeName = "User", field = "postCount")
public CompletableFuture<Integer> postCount(User user, DataLoader<Long, Integer> postCountLoader) {
  return postCountLoader.load(user.getId());
}
```

8. MUTATION PAYLOAD PATTERN
-----------------------------
Best practice: mutations return a payload type rather than the entity directly.

```graphql
type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
}

type CreateUserPayload {
  user: User                     # null if operation failed
  userErrors: [UserError!]!      # empty if success
  clientMutationId: String       # echo back for client tracking
}

type UserError {
  field: [String!]
  message: String!
  code: UserErrorCode!
}

enum UserErrorCode {
  EMAIL_TAKEN
  INVALID_EMAIL
  WEAK_PASSWORD
  UNAUTHORIZED
}
```

Benefits:
  - Supports partial failure with structured errors
  - Easy to add fields later without breaking clients
  - Shopify/GitHub style — widely recognized pattern
  - `clientMutationId` for request tracking (idempotency)

9. CONNECTION/PAGINATION PATTERN
----------------------------------
Following the Relay spec for cursor-based pagination:

```graphql
type UserConnection {
  edges: [UserEdge!]!
  pageInfo: PageInfo!
  totalCount: Int!
}

type UserEdge {
  cursor: String!
  node: User!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

type Query {
  users(
    first: Int
    after: String
    last: Int
    before: String
    filter: UserFilter
    orderBy: UserOrderBy
  ): UserConnection!
}
```

Client usage:
```graphql
query GetUsers($after: String) {
  users(first: 20, after: $after) {
    edges {
      cursor
      node {
        id
        name
        email
      }
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}
```

10. OBJECT TYPE BEST PRACTICES
--------------------------------
  ✓ Keep types focused on a single domain concept
  ✓ Use the Node interface + global IDs for cacheable entities
  ✓ Use Connection types for all paginated lists
  ✓ Use Payload types for all mutations
  ✓ Add descriptions to all types and fields
  ✓ Mark fields non-null (!) unless null is a meaningful value
  ✓ Use camelCase for field names (GraphQL convention)
  ✓ Avoid deeply nested mutations — prefer flat operations with IDs
  ✗ Don't expose internal DB structure directly
  ✗ Don't return raw error strings in data fields — use error types
  ✗ Don't use abbreviations in field names (use `description` not `desc`)

11. FEDERATION AND ENTITY TYPES
---------------------------------
In Apollo Federation, object types that are shared across subgraphs are
"entities" — identified by a `@key` directive:

```graphql
# In the Users subgraph
type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}

# In the Orders subgraph
type User @key(fields: "id") {
  id: ID!
  orders: [Order!]!
}
```

The gateway merges these into a single `User` type. The `@key` directive
specifies the primary key field(s) used to identify the entity.

12. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: Can two fields on the same Object type have the same name?
A: No. Field names within a type must be unique. However, field names in
   different types can be the same.

Q: Can an Object type implement zero interfaces?
A: Yes. Interfaces are optional. Many object types implement no interfaces.
   When using Relay-style global IDs, it's best practice to implement
   the `Node` interface for all entities.

Q: What is the difference between a root Query type field and a regular object field?
A: Root Query fields are resolved with access to the root value (usually null)
   as their parent. Regular object fields receive the parent resolver's result
   as their parent. Root fields are entry points; nested fields traverse the graph.

Q: Why use a Payload type for mutations instead of returning the entity directly?
A: Payload types allow mutations to return both the mutated entity AND
   structured errors in the same response. They also make it easy to add
   metadata later (like `clientMutationId` or debug info) without breaking
   existing clients. Direct entity returns make error handling harder — you'd
   have to rely on the top-level `errors` array for business logic errors.

Q: What is the Relay Connection specification and why follow it?
A: A standard for cursor-based pagination using Connection, Edge, and PageInfo
   types. Benefits: stable pagination that handles insertions/deletions
   correctly (unlike offset), compatibility with Relay's client-side caching,
   and interoperability between teams. `edges.cursor` is opaque to clients.

Q: How are bidirectional relationships handled in GraphQL?
A: Both directions are modeled as fields. `User.posts` and `Post.author`
   both exist in the schema. Each has its own resolver. The graph is
   navigable in both directions without the client needing to know the DB
   schema. Resolvers fetch the appropriate data for each direction.
