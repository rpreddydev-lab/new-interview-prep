================================================================
GRAPHQL TYPES — COMPLETE OVERVIEW
================================================================

1. THE TYPE SYSTEM
------------------
GraphQL's type system is the core of its contract model. Every piece of data
that flows through a GraphQL API is described by a type.

Categories of types:
  ┌─────────────────────────────────────────────────────┐
  │  Named Types (have a name in the schema)            │
  │  ├── Scalar  (leaf values: Int, String, Boolean...) │
  │  ├── Object  (fields: type User { id: ID! name: String! }) │
  │  ├── Interface (abstract: interface Node { id: ID! }) │
  │  ├── Union   (one-of: union Search = User | Post)   │
  │  ├── Enum    (set: enum Status { ACTIVE INACTIVE })  │
  │  └── Input   (write-only: input CreateUserInput {...}) │
  │                                                     │
  │  Wrapping Types (modifiers)                         │
  │  ├── Non-Null  (String!)                            │
  │  └── List      ([String])                           │
  └─────────────────────────────────────────────────────┘

2. SCALARS
----------
Scalars are leaf types — they represent a single value and have no sub-fields.

Built-in scalars:
  Int       → Signed 32-bit integer (-2,147,483,648 to 2,147,483,647)
  Float     → 64-bit IEEE floating point
  String    → UTF-8 string
  Boolean   → true / false
  ID        → Opaque unique identifier (serialized as String)

Custom scalars:
  ```graphql
  scalar Date       # e.g., "2026-04-08"
  scalar DateTime   # e.g., "2026-04-08T10:00:00Z"
  scalar JSON       # Arbitrary JSON blob
  scalar UUID       # e.g., "123e4567-e89b-12d3-a456-426614174000"
  scalar Upload     # File upload (multipart)
  scalar BigDecimal # Arbitrary precision number
  scalar URL        # Validated URL string
  scalar EmailAddress
  scalar PhoneNumber
  ```

3. OBJECT TYPES
----------------
The most fundamental output type. Composed of fields, each with a type.

  ```graphql
  type User {
    id: ID!
    name: String!
    email: String!
    age: Int
    roles: [Role!]!
    profile: Profile
    createdAt: DateTime!
  }
  ```

  Fields can have arguments:
  ```graphql
  type User {
    posts(status: PostStatus, first: Int = 10): [Post!]!
    avatar(size: AvatarSize = MEDIUM): String
  }
  ```

4. INTERFACE TYPES
-------------------
Abstract type that defines a set of fields. Implementing types must include
all interface fields PLUS their own.

  ```graphql
  interface Node {
    id: ID!
  }

  interface Auditable {
    createdAt: DateTime!
    updatedAt: DateTime
    createdBy: User
  }

  type Product implements Node & Auditable {
    id: ID!          # from Node
    createdAt: DateTime!  # from Auditable
    updatedAt: DateTime   # from Auditable
    createdBy: User       # from Auditable
    # Product-specific fields:
    name: String!
    price: Float!
  }
  ```

  When to use Interface:
  - Types share a structural contract (like a common `id` field — Node pattern)
  - You want polymorphic queries: `query { node(id: "1") { id ... on User { name } } }`

5. UNION TYPES
---------------
Like an interface but with NO required shared fields.

  ```graphql
  union SearchResult = User | Product | Article | Category

  type Query {
    search(text: String!): [SearchResult!]!
  }
  ```

  Accessing union data requires inline fragments:
  ```graphql
  query {
    search(text: "apple") {
      __typename
      ... on User    { name email }
      ... on Product { name price }
      ... on Article { title summary }
    }
  }
  ```

  Key differences:
  ┌──────────────────┬─────────────────────────────────────────────┐
  │                  │ Interface              │ Union              │
  ├──────────────────┼────────────────────────┼────────────────────┤
  │ Shared fields    │ Yes (required)         │ No (none)          │
  │ Can query common │ Yes, directly          │ Only via __typename │
  │ Use case         │ Structural similarity  │ Diverse types      │
  └──────────────────┴────────────────────────┴────────────────────┘

6. ENUM TYPES
--------------
Restricted set of values. Useful for status fields, categories, roles.

  ```graphql
  enum OrderStatus {
    PENDING
    PROCESSING
    SHIPPED
    DELIVERED
    CANCELLED
    REFUNDED
  }

  enum SortDirection {
    ASC
    DESC
  }
  ```

  Enums with descriptions:
  ```graphql
  enum Priority {
    "Lowest urgency"
    LOW
    "Standard urgency"
    MEDIUM
    "Must be addressed immediately"
    HIGH
    "Drop everything"
    CRITICAL
  }
  ```

  Enums in schema vs values in code:
  - The SDL enum values (PENDING, SHIPPED) are what the API exposes
  - Internally, the server may map these to different values (0, 1, 2)
  - Custom enum value mappings are configured in the resolver layer

7. INPUT TYPES
---------------
Object types for write operations. CANNOT be used as output types.

  ```graphql
  input CreateUserInput {
    name: String!
    email: String!
    password: String!
    roleIds: [ID!]
    address: AddressInput
  }

  input AddressInput {
    street: String!
    city: String!
    country: String!
    postalCode: String
  }

  input UpdateUserInput {
    name: String     # All fields optional for updates
    email: String
    address: AddressInput
  }
  ```

  Rules for Input types:
  - Fields can only be: scalars, enums, other input types
  - Cannot contain Object types, Interfaces, or Unions
  - Can be nested (AddressInput inside CreateUserInput)
  - Support default values: `input Foo { limit: Int = 10 }`

8. TYPE MODIFIERS (NON-NULL AND LIST)
--------------------------------------
These are wrapping types that modify Named types.

  Modifier    | SDL Syntax   | Meaning
  ──────────────────────────────────────────────────────────────
  Nullable    | String       | Value OR null
  Non-Null    | String!      | Value, NEVER null (error if null)
  List        | [String]     | Nullable list of nullable strings
  List NonNull| [String!]!   | Non-null list of non-null strings

  Reading complex types:
  `[Post!]!`
  → Non-null list (!  on the outside)
  → of non-null Post objects (! on the inside)
  → An empty list [] is valid, but null is not
  → No null items in the list

  `[Post]`
  → Nullable list
  → of nullable Post objects
  → null is valid, [] is valid, [null, null] is valid

  Common design decisions:
  - `id: ID!`     → IDs are always present
  - `name: String!` → Required string
  - `middleName: String` → Optional field
  - `tags: [String!]!` → List is always present (may be empty), no null tags
  - `phone: String` → Optional, null means "not provided"

9. THE NODE INTERFACE PATTERN
------------------------------
Industry standard pattern (from Relay spec) for globally unique IDs:

  ```graphql
  interface Node {
    id: ID!   # Globally unique across ALL types
  }

  type User implements Node {
    id: ID!   # Encodes type + DB ID: base64("User:42") = "VXNlcjo0Mg=="
    name: String!
  }

  type Query {
    node(id: ID!): Node  # Look up ANY entity by global ID
  }
  ```

  The server decodes the ID, determines the type, and routes to the right
  repository. This enables Apollo Client's powerful normalized caching.

10. BUILT-IN TYPES
-------------------
Every GraphQL schema includes these built-in types automatically:

  __Schema       → schema metadata
  __Type         → type metadata
  __Field        → field metadata
  __InputValue   → input field/argument metadata
  __EnumValue    → enum value metadata
  __Directive    → directive metadata

  __typename     → special field available on every Object/Interface/Union

  Built-in scalars: Boolean, Int, Float, String, ID
  Built-in directives: @skip, @include, @deprecated, @specifiedBy

11. CUSTOM SCALARS IN DEPTH
-----------------------------
Custom scalars require three functions:

  1. serialize(value)         → converts internal value → JSON output
  2. parseValue(value)        → converts JSON input → internal value
  3. parseLiteral(ast)        → converts AST literal → internal value

  Java example (Spring for GraphQL with graphql-java-extended-scalars):
  ```java
  // Add to pom.xml: com.graphql-java:graphql-java-extended-scalars
  // In schema: scalar Date

  @Configuration
  public class GraphQLConfig {
    @Bean
    public RuntimeWiringConfigurer runtimeWiringConfigurer() {
      return builder -> builder.scalar(ExtendedScalars.Date);
    }
  }
  ```

  Common custom scalar libraries for Java:
  - graphql-java-extended-scalars: Date, DateTime, JSON, BigDecimal, URL...

12. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What are the 6 named type categories in GraphQL?
A: Scalar, Object, Interface, Union, Enum, and Input. Plus two wrapping types:
   Non-Null and List.

Q: What is the difference between Object type and Input type?
A: Object types are used as output (return types). Input types are used as
   input (argument types). Input types can only have scalar, enum, or other
   input type fields — not Object, Interface, or Union fields. This avoids
   circular references and separates read and write models.

Q: When would you use a Union vs an Interface?
A: Use Interface when types share common fields you want to query without
   type-specific fragments. Use Union when types are structurally unrelated
   but can appear in the same position (e.g., a search result that returns
   different entities). A Union cannot have common fields queried directly;
   an Interface can.

Q: What does `[Post!]!` mean vs `[Post]`?
A: `[Post!]!` means: the list itself will never be null (but can be empty),
   AND each element in the list will never be null. `[Post]` means: the list
   itself may be null, and any element may be null. Best practice is usually
   `[Post!]!` to avoid defensive null checks.

Q: Why is ID a special scalar in GraphQL?
A: The ID scalar signals that a field is a unique identifier. It's serialized
   as a string (even if the underlying value is a number) and is treated as
   opaque by clients. This allows servers to use any ID format (integer, UUID,
   compound key) without the client needing to know the format.

Q: How do custom scalars work?
A: Custom scalars require three coercion functions: serialize (output),
   parseValue (for variable values), and parseLiteral (for inline values in
   the query). Libraries like graphql-java-extended-scalars provide common
   custom scalars (Date, DateTime, BigDecimal, etc.) ready to use.
