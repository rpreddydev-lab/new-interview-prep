GRAPHQL SCALAR TYPES — IN DEPTH
================================================================

1. WHAT ARE SCALARS?
--------------------
Scalars are the "leaf" types of the GraphQL type system. They represent
concrete, atomic data values. A field of scalar type has no sub-fields —
the value is the end of the query traversal.

Every GraphQL schema has 5 built-in scalars, and you can define custom ones.

2. BUILT-IN SCALARS
--------------------

  2.1 Int
  -------
  - Signed 32-bit integer
  - Range: -2,147,483,648 to 2,147,483,647
  - JSON representation: JSON number without decimal (e.g., 42)
  - Use for: counts, ages, small IDs, quantities

  ```graphql
  type Product {
    stockCount: Int!
    viewCount: Int!
  }
  ```

  2.2 Float
  ---------
  - Double-precision (64-bit) IEEE 754 floating-point
  - JSON representation: JSON number (e.g., 3.14, -0.001, 1.5e10)
  - Use for: prices, coordinates, percentages, measurements
  - WARNING: Floats have precision issues. For financial data use BigDecimal
    (custom scalar) instead!

  ```graphql
  type Product {
    price: Float!
    weight: Float
    latitude: Float
    longitude: Float
  }
  ```

  2.3 String
  ----------
  - UTF-8 character sequence of any length
  - JSON representation: JSON string
  - Use for: names, descriptions, text content, dates-as-strings, JSON

  ```graphql
  type User {
    name: String!
    bio: String
    profileJson: String   # Avoid this — use JSON scalar instead
  }
  ```

  2.4 Boolean
  -----------
  - true or false
  - JSON representation: JSON boolean (not "true"/"false" strings)
  - Use for: flags, permissions, existence checks

  ```graphql
  type User {
    isActive: Boolean!
    isVerified: Boolean!
    hasSubscription: Boolean
  }
  ```

  2.5 ID
  ------
  - Unique identifier. Opaque to the client.
  - Serialized as String, but can hold integer or UUID values server-side
  - Clients must treat it as an opaque string, never parsing it
  - Use for: all primary keys in your API
  - Special: Apollo Client uses `__typename` + `id` for cache keys

  ```graphql
  type User {
    id: ID!       # Could be "42", "user-42", or a UUID
    name: String!
  }
  ```

  Why ID and not String or Int?
  - Semantic: it signals "this is an identifier"
  - Allows schema evolution (change from int IDs to UUIDs without client changes)
  - Tools (Apollo Client) treat ID specially for caching

3. CUSTOM SCALARS — DEEP DIVE
-------------------------------
Custom scalars let you encode domain-specific values beyond the 5 built-ins.

  3.1 Declaring a Custom Scalar
  ------------------------------
  ```graphql
  scalar DateTime
  scalar Date
  scalar Time
  scalar JSON
  scalar UUID
  scalar BigDecimal
  scalar URL
  scalar EmailAddress
  scalar Upload
  scalar PhoneNumber
  scalar HexColor
  scalar IBAN
  ```

  3.2 How Custom Scalars Work (Runtime)
  --------------------------------------
  A custom scalar needs 3 coercion functions:

  serialize(internalValue) → externalValue
    - Called when sending the value to the client
    - E.g., Java Instant → ISO-8601 String "2026-04-08T10:00:00Z"

  parseValue(externalValue) → internalValue
    - Called when receiving a variable value (JSON input)
    - E.g., "2026-04-08" → Java LocalDate

  parseLiteral(astNode) → internalValue
    - Called when the value appears inline in the query
    - E.g., `filter: { date: "2026-04-08" }` in query text → Java LocalDate

  3.3 Custom Scalars in Java (Spring for GraphQL)
  ------------------------------------------------
  Using graphql-java-extended-scalars library:

  ```xml
  <!-- pom.xml -->
  <dependency>
    <groupId>com.graphql-java</groupId>
    <artifactId>graphql-java-extended-scalars</artifactId>
    <version>21.0</version>
  </dependency>
  ```

  ```java
  // Configuration
  @Configuration
  public class GraphQLScalarConfig {
    @Bean
    public RuntimeWiringConfigurer runtimeWiringConfigurer() {
      return wiringBuilder -> wiringBuilder
        .scalar(ExtendedScalars.DateTime)
        .scalar(ExtendedScalars.Date)
        .scalar(ExtendedScalars.Json)
        .scalar(ExtendedScalars.NonNegativeInt)
        .scalar(ExtendedScalars.BigDecimal)
        .scalar(ExtendedScalars.Url)
        .scalar(ExtendedScalars.UUID);
    }
  }
  ```

  In schema:
  ```graphql
  scalar DateTime
  scalar Date
  scalar JSON
  scalar BigDecimal
  scalar UUID

  type Order {
    id: UUID!
    placedAt: DateTime!
    deliveryDate: Date
    total: BigDecimal!
    metadata: JSON
  }
  ```

  3.4 Writing a Custom Scalar in Java
  -------------------------------------
  ```java
  // Custom EmailAddress scalar
  public class EmailScalar {
    public static final GraphQLScalarType EMAIL_ADDRESS = GraphQLScalarType.newScalar()
      .name("EmailAddress")
      .description("A valid email address")
      .coercing(new Coercing<String, String>() {

        @Override
        public String serialize(Object dataFetcherResult) throws CoercingSerializeException {
          if (dataFetcherResult instanceof String email) {
            if (isValidEmail(email)) return email;
            throw new CoercingSerializeException("Invalid email: " + email);
          }
          throw new CoercingSerializeException("Expected String");
        }

        @Override
        public String parseValue(Object input) throws CoercingParseValueException {
          if (input instanceof String email) {
            if (isValidEmail(email)) return email;
            throw new CoercingParseValueException("Invalid email: " + email);
          }
          throw new CoercingParseValueException("Expected String");
        }

        @Override
        public String parseLiteral(Object ast) throws CoercingParseLiteralException {
          if (ast instanceof StringValue sv) {
            String email = sv.getValue();
            if (isValidEmail(email)) return email;
            throw new CoercingParseLiteralException("Invalid email: " + email);
          }
          throw new CoercingParseLiteralException("Expected StringValue");
        }

        private boolean isValidEmail(String email) {
          return email.contains("@") && email.contains(".");
        }
      })
      .build();
  }
  ```

  3.5 The Upload Scalar
  ----------------------
  Used for file uploads. Not a standard GraphQL feature — uses the
  "GraphQL multipart request spec":
  https://github.com/jaydenseric/graphql-multipart-request-spec

  ```graphql
  scalar Upload

  type Mutation {
    uploadAvatar(file: Upload!): User!
    uploadDocuments(files: [Upload!]!): [Document!]!
  }
  ```

  Spring for GraphQL supports this natively:
  ```java
  @MutationMapping
  public User uploadAvatar(@Argument MultipartFile file, @ContextValue User currentUser) {
    // process file...
  }
  ```

4. SCALAR COERCION IN PRACTICE
--------------------------------
Coercion converts between the JSON representation and the server's native type.

  Scalar     | JSON Input       | Java Type       | Example
  ─────────────────────────────────────────────────────────────────
  Int        | Number (integer) | Integer         | 42
  Float      | Number           | Double          | 3.14
  String     | String           | String          | "Alice"
  Boolean    | Boolean          | Boolean         | true
  ID         | String or Number | String          | "user-1" or "42"
  DateTime   | String (ISO)     | OffsetDateTime  | "2026-04-08T10:00:00Z"
  Date       | String (ISO)     | LocalDate       | "2026-04-08"
  UUID       | String (UUID)    | UUID            | "123e4567-..."
  BigDecimal | String or Number | BigDecimal      | "99.99" or 99.99

5. BEST PRACTICES FOR SCALARS
-------------------------------
  ✓ Use BigDecimal (custom scalar) for financial/monetary values — Float has
    precision errors (0.1 + 0.2 ≠ 0.3 in floating point)
  ✓ Use DateTime custom scalar instead of String for dates — provides
    validation and consistent format
  ✓ Use ID for all primary keys and foreign keys — semantic clarity
  ✓ Use UUID custom scalar to document that your IDs are UUIDs
  ✓ Avoid returning raw JSON as String — define proper types instead;
    use JSON scalar only for truly dynamic/unknown structures
  ✗ Don't use Int for IDs that might exceed 2^31-1 (use ID or String)
  ✗ Don't use Float for prices in e-commerce (rounding errors)

6. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the difference between String and ID in GraphQL?
A: Both are serialized as strings in JSON, but ID has semantic meaning: it
   identifies a unique entity. Tools like Apollo Client use ID for cache
   normalization. ID is opaque to clients — they should never parse or
   construct IDs. Use String for text data, ID for identifiers.

Q: When should you use a custom scalar?
A: When the built-in scalars don't capture your domain semantics. Common cases:
   - DateTime/Date (ISO format with validation)
   - BigDecimal/Money (precision-safe numbers)
   - UUID (validated format)
   - JSON (arbitrary JSON objects)
   - Upload (file uploads)
   Custom scalars enforce validation at parse time.

Q: Can a GraphQL query have sub-fields on a scalar field?
A: No. Scalars are leaf types — they have no sub-fields. If you try to select
   sub-fields on a String or Int field, you get a validation error.

Q: What happens if a Float is used for currency in GraphQL?
A: Float is a 64-bit IEEE 754 number, which has precision issues (e.g., 0.1
   + 0.2 = 0.30000000000000004). For monetary values, use a custom BigDecimal
   scalar that uses arbitrary precision arithmetic. Alternatively, represent
   money as Int (cents) and convert in the UI.

Q: What are the three coercion functions needed for a custom scalar?
A: serialize (converts server value to JSON for the response), parseValue
   (converts JSON variable input to server type), and parseLiteral (converts
   inline AST literal in the query to server type). All three are required
   for a correctly functioning custom scalar.
