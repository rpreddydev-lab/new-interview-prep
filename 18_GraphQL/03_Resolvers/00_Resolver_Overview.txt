GRAPHQL RESOLVERS — COMPLETE OVERVIEW
================================================================

1. WHAT IS A RESOLVER?
-----------------------
A resolver is a function responsible for returning the value of a single
field in a GraphQL schema. The resolver is the bridge between the GraphQL
type system and your actual data sources (databases, microservices, caches).

One resolver per field (conceptually). If no resolver is provided, the
default resolver is used (returns property of same name on parent object).

2. THE RESOLVER FUNCTION SIGNATURE
------------------------------------
```javascript
// JavaScript/Node.js canonical signature:
fieldName(parent, args, context, info) {
  // parent  = result of parent resolver (or rootValue for root fields)
  // args    = arguments passed to this field in the query
  // context = shared per-request object (auth, DB, DataLoader)
  // info    = field metadata (name, type, path, schema, AST)
  return value;  // or Promise<value>
}
```

Java equivalent (Spring for GraphQL annotations):
```java
@QueryMapping          // Root Query field resolver
public User user(@Argument String id) { ... }

@SchemaMapping         // Nested field resolver
public List<Post> posts(User user) { ... }  // parent = User

@MutationMapping       // Root Mutation field resolver
public UserPayload createUser(@Argument CreateUserInput input) { ... }
```

3. THE FOUR RESOLVER PARAMETERS
---------------------------------

  3.1 parent (root / source)
  ---------------------------
  The value returned by the PARENT resolver. For root-level fields (on Query,
  Mutation, Subscription), this is the root value (usually null or a service).

  ```
  Query.user(parent=null, args={id:"1"})
    → returns User{id:1, name:"Alice"}

  User.posts(parent=User{id:1, name:"Alice"}, args={first:10})
    → returns [Post{...}, Post{...}]

  Post.author(parent=Post{id:"p1", authorId:"1"}, args={})
    → returns User{id:1, name:"Alice"}  (by looking up authorId)
  ```

  3.2 args
  ---------
  The arguments provided in the query for this specific field invocation.
  Always an object (empty object if no arguments).

  Schema: `user(id: ID!): User`
  Query: `{ user(id: "1") { name } }`
  args = `{ id: "1" }`

  3.3 context
  -----------
  A shared object passed to ALL resolvers in a single request. Built once
  per request by the framework and injected. Contains:
  - Authenticated user/session
  - DataLoader instances
  - Database connections / repositories
  - Logger with request correlation ID
  - Feature flags

  IMPORTANT: Context is PER-REQUEST — never share state across requests!

  3.4 info
  --------
  Contains metadata about the current execution:
  - `info.fieldName`: the field name
  - `info.returnType`: the field's return type
  - `info.path`: the path from root to this field
  - `info.schema`: access to the full schema
  - `info.fieldNodes`: AST nodes for this field (used for look-ahead)
  - `info.fragments`: named fragments in the document

  Advanced use: inspect child selections to optimize DB queries:
  ```javascript
  function user(parent, args, context, info) {
    const selections = info.fieldNodes[0].selectionSet.selections;
    const fieldNames = selections.map(s => s.name.value);
    // Only SELECT the needed columns from DB
    return db.user.findById(args.id, { select: fieldNames });
  }
  ```

4. DEFAULT RESOLVERS
---------------------
When you don't define a resolver for a field, GraphQL uses the default:

```javascript
// Default resolver behavior:
(parent) => parent[fieldName]
```

If the `user` resolver returns `{ id: "1", name: "Alice", email: "alice@ex.com" }`,
the `name` field resolver (default) returns `parent["name"]` = `"Alice"`.

In Java (Spring for GraphQL): default resolvers access Java bean properties
using reflection (getters, public fields, records).

```java
// The following field resolver is NOT needed — default handles it:
@SchemaMapping(typeName = "User", field = "name")
public String name(User user) {
  return user.getName();  // Default resolver already does this!
}
```

5. ROOT RESOLVERS VS FIELD RESOLVERS
--------------------------------------
Root resolvers (on Query/Mutation/Subscription):
  - parent = null (or root value)
  - Fetch data from scratch (DB query, API call)
  - Entry points into the data graph

Field resolvers (on object type fields):
  - parent = the parent object returned by the parent resolver
  - Often use the parent's ID to fetch related data
  - May use DataLoader for batching

```java
// Root resolver (Query.users)
@QueryMapping
public List<User> users(@Argument UserFilter filter) {
  return userRepository.findAll(filter);
}

// Field resolver (User.posts) — triggered for EACH user
@SchemaMapping(typeName = "User", field = "posts")
public CompletableFuture<List<Post>> posts(User user, DataLoader<Long, List<Post>> postsLoader) {
  return postsLoader.load(user.getId());  // DataLoader batches these calls!
}
```

6. ASYNC RESOLVERS
------------------
Resolvers can return Promises (JS) or CompletableFutures/Mono/Flux (Java).
This enables concurrent I/O.

```java
// Spring for GraphQL: CompletableFuture enables async execution
@SchemaMapping(typeName = "User", field = "posts")
public CompletableFuture<List<Post>> posts(User user) {
  return CompletableFuture.supplyAsync(() ->
    postRepository.findByUserId(user.getId()),
    executor
  );
}

// Reactor Mono (for reactive stacks)
@SchemaMapping(typeName = "User", field = "posts")
public Mono<List<Post>> posts(User user) {
  return postRepository.findByUserIdReactive(user.getId());
}
```

7. RESOLVER EXECUTION MODEL
-----------------------------
```
          Query execution (parallel where possible):
          ──────────────────────────────────────────
          Query.user(id:"1")  ← called once
          └── User.name       ← called once (parallel with email)
          └── User.email      ← called once (parallel with name)
          └── User.posts      ← called once
              └── Post.title  ← called N times (once per post)
              └── Post.author ← called N times (N+1 problem if no DataLoader!)
```

8. RESOLVER BEST PRACTICES
----------------------------
  ✓ Keep resolvers thin — delegate to services/repositories
  ✓ Use DataLoader for any 1-to-many or many-to-1 relationships
  ✓ Use context for per-request resources (avoid module-level state)
  ✓ Return null for nullable fields that have no data (don't throw)
  ✓ Throw meaningful errors (not generic "Internal error")
  ✓ Log errors with correlation IDs from context
  ✓ Use async/CompletableFuture for I/O-bound resolvers
  ✗ Don't query the DB in a field resolver without DataLoader
  ✗ Don't put business logic in resolvers (put it in services)
  ✗ Don't share state across requests

9. RESOLVER TYPES IN SPRING FOR GRAPHQL
-----------------------------------------
```java
// Query root resolver
@QueryMapping
public User user(@Argument String id) { ... }

// Mutation root resolver
@MutationMapping
public UserPayload createUser(@Argument CreateUserInput input) { ... }

// Subscription root resolver
@SubscriptionMapping
public Flux<Order> orderStatusChanged(@Argument String orderId) { ... }

// Nested field resolver
@SchemaMapping(typeName = "User", field = "posts")
public List<Post> posts(User user) { ... }

// Shorthand when method name matches field name
@SchemaMapping(typeName = "User")
public List<Post> posts(User user) { ... }

// Batch resolver using DataLoader
@SchemaMapping(typeName = "Post", field = "author")
public CompletableFuture<User> author(Post post, DataLoader<Long, User> authorLoader) {
  return authorLoader.load(post.getAuthorId());
}
```

10. RESOLVER RETURN TYPES
--------------------------
```java
// Synchronous
public User user(@Argument String id) { ... }

// Asynchronous (recommended for I/O)
public CompletableFuture<User> user(@Argument String id) { ... }

// Reactive (Project Reactor)
public Mono<User> user(@Argument String id) { ... }
public Flux<User> users() { ... }   // For lists

// List
public List<User> users() { ... }

// Optional (null → GraphQL null, not error)
public Optional<User> user(@Argument String id) { ... }

// Iterable
public Iterable<User> users() { ... }
```

11. RESOLVER LOOKUP ORDER (Spring for GraphQL)
------------------------------------------------
When resolving a field on type T, Spring for GraphQL looks for:
1. A @SchemaMapping or @QueryMapping method where the bean class and method
   match the type/field name
2. DataFetcher registered via RuntimeWiringConfigurer
3. Default property-based resolution (reflection on the parent object)

12. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is a resolver in GraphQL?
A: A resolver is a function that fetches the value for a single field in the
   schema. Each field can have a resolver; if absent, the default resolver
   returns the property of the same name from the parent object. Resolvers
   are the connection between the GraphQL type system and real data sources.

Q: What is the resolver signature and what does each parameter mean?
A: (parent, args, context, info):
   - parent: the result of the parent resolver (null for root fields)
   - args: the arguments provided for this field in the query
   - context: shared per-request object (auth, DB, DataLoader instances)
   - info: field metadata (name, type, schema, path, AST)

Q: What is a default resolver and when is it used?
A: When no custom resolver is defined for a field, the runtime uses the default
   resolver: `(parent) => parent[fieldName]`. It accesses the property of the
   parent object. This means if your User object already has a `name` property,
   you don't need a custom resolver for `User.name`.

Q: What are root resolvers vs field resolvers?
A: Root resolvers are on the Query/Mutation/Subscription types — they have no
   parent (or parent is null) and are entry points into the data graph.
   Field resolvers are on regular object types; they receive the parent
   object as their first argument and typically use it to fetch related data.

Q: Should resolvers contain business logic?
A: No. Resolvers should be thin adapters: validate authorization, delegate to
   a service, and return the result. Business logic belongs in services/use
   cases that are independent of GraphQL. This makes the code testable,
   reusable (same service for REST and GraphQL), and maintainable.
