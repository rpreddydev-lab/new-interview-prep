================================================================
GRAPHQL RESOLVER CHAIN — IN DEPTH
================================================================

1. WHAT IS THE RESOLVER CHAIN?
--------------------------------
The resolver chain is the sequence of resolver function calls that happens
during GraphQL execution. When the server processes a query, it walks the
AST depth-first, calling a resolver for each field. The output of each
resolver becomes the `parent` input for the next level's resolvers.

2. VISUALIZATION OF THE RESOLVER CHAIN
-----------------------------------------
Query:
```graphql
{
  user(id: "1") {
    name
    email
    posts {
      title
      author {
        name
      }
    }
  }
}
```

Resolver chain:
```
STEP 1: Query.user(parent=null, args={id:"1"})
        Returns: User { id: "1", name: "Alice", email: "alice@ex.com" }

STEP 2a: User.name(parent=User{Alice}, args={})    ← parallel with 2b
          Returns: "Alice"

STEP 2b: User.email(parent=User{Alice}, args={})   ← parallel with 2a
          Returns: "alice@ex.com"

STEP 2c: User.posts(parent=User{Alice}, args={})
          Returns: [Post{id:"p1", title:"Hi"}, Post{id:"p2", title:"Hello"}]

STEP 3a (for p1): Post.title(parent=Post{p1}, args={})    ← parallel with 3b
                   Returns: "Hi"
STEP 3a (for p2): Post.title(parent=Post{p2}, args={})
                   Returns: "Hello"

STEP 3b (for p1): Post.author(parent=Post{p1,authorId:"1"}, args={})
                   DB Query: SELECT * FROM users WHERE id = "1"
                   Returns: User { id: "1", name: "Alice" }

STEP 3b (for p2): Post.author(parent=Post{p2,authorId:"1"}, args={})
                   DB Query: SELECT * FROM users WHERE id = "1"   ← SAME QUERY AGAIN!
                   Returns: User { id: "1", name: "Alice" }

STEP 4a (for p1): User.name(parent=User{Alice})   ← default resolver
STEP 4a (for p2): User.name(parent=User{Alice})   ← default resolver
```

This shows the N+1 problem: N posts → N author queries.

3. CHAIN TERMINATION
---------------------
The chain terminates when:
  - A scalar value is returned (leaf type — String, Int, Boolean, etc.)
  - A null is returned (propagates up as null in the response)
  - An error is thrown (error bubbles up; nullable fields become null)

4. NULL PROPAGATION IN THE CHAIN
----------------------------------
When a resolver returns null for a non-null field, GraphQL:
  1. Marks the field as null
  2. Adds a field error to the errors array
  3. Propagates null up to the nearest nullable parent

Example:
```graphql
type Query { order: Order! }
type Order { id: ID!, user: User!, total: Float! }
type User { id: ID!, name: String! }
```

If `User.name` resolver throws an error:
1. `name` becomes null (but `name` is `String!` — non-null!)
2. Error propagates up to `user` (User is the parent)
3. `user` becomes null (but `user` is `User!` — non-null!)
4. Error propagates up to `order`
5. `order` becomes null (but `order: Order!` in Query — non-null!)
6. `data` becomes null → `{ "data": null, "errors": [...] }`

LESSON: Design nullable fields carefully. Making fields non-null is a
commitment that failures cascade to the root if not absorbed by a nullable parent.

5. RESOLVER CHAIN WITH INTERFACES
-----------------------------------
When a field returns an interface type, the chain includes a type resolution step:

```
Query.node(id: "entity-1")
  → resolver returns a Java object (e.g., Product instance)
  → __resolveType is called: "What GraphQL type is this Java object?"
  → Returns "Product"
  → Product.name resolver called (type-specific field)
```

6. HOW PARENT DATA FLOWS DOWN
--------------------------------
The parent object flows down the resolver chain as-is. Resolver return types
determine what data is available at each level.

```java
// Level 1: Query.user — fetches from DB
@QueryMapping
public UserEntity user(@Argument String id) {
  return userRepository.findById(id).orElseThrow();
  // Returns UserEntity { id, firstName, lastName, email, posts... }
}

// Level 2: User.fullName — computed from parent
@SchemaMapping(typeName = "User", field = "fullName")
public String fullName(UserEntity user) {
  // parent = UserEntity returned by Query.user
  return user.getFirstName() + " " + user.getLastName();
}

// Level 2: User.posts — fetches related data from parent's ID
@SchemaMapping(typeName = "User", field = "posts")
public List<PostEntity> posts(UserEntity user) {
  // parent = UserEntity; uses parent.id to fetch posts
  return postRepository.findByUserId(user.getId());
}

// Level 3: Post.title — default resolver (no code needed)
// Spring reads postEntity.getTitle() automatically

// Level 3: Post.author — fetch from parent's authorId
@SchemaMapping(typeName = "Post", field = "author")
public UserEntity author(PostEntity post) {
  // parent = PostEntity; uses parent.authorId to fetch author
  return userRepository.findById(post.getAuthorId()).orElseThrow();
}
```

7. RESOLVER CHAIN IN MUTATIONS
--------------------------------
Mutations execute the root field serially, but the return value's field
resolvers behave exactly like query field resolvers:

```
Mutation.createOrder(args={...})
  → OrderEntity saved to DB
  → Returns OrderEntity

OrderEntity.id         (default resolver)
OrderEntity.status     (default resolver)
OrderEntity.user       (field resolver: UserEntity by userId)
OrderEntity.items      (field resolver: List<OrderItemEntity> by orderId)
  → OrderItemEntity.product (field resolver: ProductEntity by productId)
  → ...
```

8. DEFERRED RESOLVER CHAIN (@defer)
-------------------------------------
With `@defer`, part of the resolver chain is executed asynchronously after
the initial response:

```graphql
query {
  user(id: "1") {
    name          # Resolved and sent immediately
    email         # Resolved and sent immediately
    ... @defer {
      recentActivity { ... }  # Resolved and sent later as a patch
    }
  }
}
```

The client receives two responses:
1. `{ data: { user: { name: "Alice", email: "..." } } }`
2. `{ incremental: [{ data: { recentActivity: [...] }, path: ["user"] }] }`

9. TRACING THE RESOLVER CHAIN
-------------------------------
Apollo Tracing extension adds timing data to the response:

```json
{
  "data": { ... },
  "extensions": {
    "tracing": {
      "version": 1,
      "startTime": "2026-04-08T10:00:00Z",
      "duration": 150000000,
      "execution": {
        "resolvers": [
          { "path": ["user"], "field": "user", "duration": 50000000 },
          { "path": ["user", "name"], "field": "name", "duration": 100000 },
          { "path": ["user", "posts"], "field": "posts", "duration": 80000000 },
          { "path": ["user", "posts", 0, "title"], "field": "title", "duration": 50000 }
        ]
      }
    }
  }
}
```

Spring Boot Apollo Tracing:
```java
@Bean
public Instrumentation apolloTracingInstrumentation() {
  return new TracingInstrumentation();
}
```

10. RESOLVER CHAIN OPTIMIZATION TECHNIQUES
-------------------------------------------
  a) DataLoader (batch N queries into 1)
     → Applied at field resolver level
     → Collect all IDs in a tick, then batch query

  b) Look-ahead (inspect child selections in info)
     → In a root resolver, check what nested fields were requested
     → JOIN the needed tables upfront in a single query

  c) SQL selection optimization
     → Only SELECT needed columns based on requested fields
     → Inspect info.fieldNodes to determine needed fields

  d) Connection pooling
     → Use a DB connection pool (HikariCP in Spring Boot by default)
     → Resolvers use the pool, not individual connections

  e) Caching at resolver level
     → DataLoader provides per-request deduplication
     → Redis/Caffeine for cross-request caching of stable data

  Look-ahead example (Spring for GraphQL):
  ```java
  @QueryMapping
  public User user(@Argument String id, DataFetchingEnvironment env) {
    // Check if client requested 'posts' field
    boolean needsPosts = env.getSelectionSet().contains("posts");

    if (needsPosts) {
      // Fetch user + posts in one JOIN query
      return userRepository.findByIdWithPosts(id);
    } else {
      return userRepository.findById(id).orElseThrow();
    }
  }
  ```

11. RESOLVER CHAIN DEBUGGING
------------------------------
Common techniques to debug resolver chains:
  1. Add logging at each resolver entry/exit
  2. Use Apollo Tracing to see timing per resolver
  3. Use DataLoader debug mode to see batched calls
  4. Add `@skip` directives to isolate problematic resolvers
  5. Use GraphiQL/Apollo Sandbox to run queries with tracing

```java
@SchemaMapping(typeName = "User", field = "posts")
public List<PostEntity> posts(UserEntity user) {
  log.debug("Fetching posts for user: {}", user.getId());
  long start = System.currentTimeMillis();
  List<PostEntity> posts = postRepository.findByUserId(user.getId());
  log.debug("Fetched {} posts in {}ms", posts.size(), System.currentTimeMillis() - start);
  return posts;
}
```

12. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: How does data flow through the resolver chain?
A: Each resolver returns a value that becomes the `parent` argument for the
   next level's resolvers. Root resolvers (Query/Mutation) start with null
   as parent and fetch data from scratch. Each subsequent level uses the
   parent object to fetch related data, passing it to child resolvers.

Q: What determines the execution order in a resolver chain?
A: Depth-first traversal with parallel sibling execution. Within a level,
   siblings (fields of the same object) can execute in parallel. A parent
   resolver must complete before its children's resolvers are called.
   Exception: top-level mutation fields execute serially.

Q: What happens in the resolver chain when null is returned for a non-null field?
A: The runtime marks the field as null and adds a field error. Since the
   field is non-null, the error propagates up to the nearest nullable parent.
   If all ancestors are non-null, `data` becomes null. This is called null
   propagation and is why schema design with non-null requires careful thought.

Q: What is look-ahead in GraphQL and why is it useful?
A: Look-ahead means inspecting the child field selections (from the `info`
   parameter's `selectionSet`) inside a parent resolver to determine what
   data will be needed downstream. This allows the parent resolver to JOIN
   related tables upfront in a single query, avoiding the N+1 problem at
   the DB level without needing DataLoader.

Q: How would you trace performance issues in the resolver chain?
A: (1) Enable Apollo Tracing to see per-resolver execution time. (2) Add
   logging at resolver entry/exit. (3) Use DataLoader debug stats to see
   batch sizes. (4) Look for resolvers with high execution time or high
   call count (N+1 indicators). (5) Use database query logging to count
   queries per request.
