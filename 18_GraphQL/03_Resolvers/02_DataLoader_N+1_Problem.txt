DATALOADER AND THE N+1 PROBLEM — IN DEPTH
================================================================

1. THE N+1 PROBLEM
-------------------
The N+1 problem is the most critical performance issue in GraphQL. It occurs
when fetching a list of N items where each item triggers an additional query
to fetch a related entity — resulting in N+1 total queries.

Classic example:
```graphql
query {
  posts(first: 100) {
    title
    author {   # ← DANGER: one DB query per post!
      name
    }
  }
}
```

Without optimization:
1. `Query.posts` → SELECT * FROM posts LIMIT 100   (1 query)
2. `Post.author` for post 1 → SELECT * FROM users WHERE id = 1  (1 query)
3. `Post.author` for post 2 → SELECT * FROM users WHERE id = 2  (1 query)
4. `Post.author` for post 3 → SELECT * FROM users WHERE id = 1  (1 query — same user!)
...
101. `Post.author` for post 100 → ...  (1 query)

TOTAL: 101 queries for 100 posts → O(N) queries → N+1 problem.
With many users duplicated, it's even worse.

2. WHAT IS DATALOADER?
-----------------------
DataLoader is a utility (originally by Facebook) that solves the N+1 problem
through two mechanisms:

  BATCHING:   Groups multiple individual loads into a single batch call
  CACHING:    Within a single request, the same key is loaded only once

DataLoader collects all `load(key)` calls that happen in the CURRENT event
loop tick, then batches them into a single `batchLoadFn(keys)` call.

Original JavaScript library: https://github.com/graphql/dataloader
Java implementation: org.dataloader:java-dataloader (used by graphql-java)

3. HOW DATALOADER WORKS (MECHANISM)
-------------------------------------
```
Tick 1 (resolver calls):
  Post 1 resolver: loader.load("user-1")   ← queued
  Post 2 resolver: loader.load("user-2")   ← queued
  Post 3 resolver: loader.load("user-1")   ← queued (same key — deduplicated)
  Post 4 resolver: loader.load("user-3")   ← queued
  ...
  Post 100 resolver: loader.load("user-5") ← queued

Tick 2 (batch function fires):
  batchLoadFn(["user-1", "user-2", "user-3", ..., "user-5"])
  → SELECT * FROM users WHERE id IN ('user-1', 'user-2', ..., 'user-5')
  → 1 QUERY for all unique user IDs

  Results distributed back to each waiting promise:
  Post 1 ← User{id: user-1, name: "Alice"}
  Post 2 ← User{id: user-2, name: "Bob"}
  Post 3 ← User{id: user-1, name: "Alice"}  ← from cache
  Post 4 ← User{id: user-3, name: "Charlie"}
  ...
```

Result: 1 query for posts + 1 query for all unique user IDs = 2 queries total!

4. DATALOADER IN SPRING FOR GRAPHQL
--------------------------------------
Spring for GraphQL has built-in DataLoader support via @BatchMapping and
the DataLoaderRegistry.

  4.1 Using @BatchMapping (Spring's preferred way)
  -------------------------------------------------
  ```java
  // Schema:
  // type Post { author: User! }

  @Controller
  public class PostController {

    private final UserRepository userRepository;

    // @BatchMapping = Spring's high-level DataLoader abstraction
    // Instead of loading one post's author, loads ALL posts' authors at once
    @BatchMapping(typeName = "Post", field = "author")
    public Map<Post, User> author(List<Post> posts) {
      // posts = all Post objects needing their author in this request tick
      Set<Long> authorIds = posts.stream()
        .map(Post::getAuthorId)
        .collect(Collectors.toSet());

      Map<Long, User> userMap = userRepository.findAllById(authorIds)
        .stream()
        .collect(Collectors.toMap(User::getId, Function.identity()));

      // Return a Map from Post → User (Spring handles distribution)
      return posts.stream()
        .collect(Collectors.toMap(
          Function.identity(),
          post -> userMap.get(post.getAuthorId())
        ));
    }
  }
  ```

  4.2 Using DataLoader Manually
  ------------------------------
  ```java
  // Register DataLoader
  @Configuration
  public class DataLoaderConfig {
    @Bean
    public DataLoaderRegistrar userDataLoaderRegistrar(UserRepository userRepository) {
      return registry -> {
        BatchLoaderWithContext<Long, User> batchLoader = (keys, env) -> {
          List<User> users = userRepository.findAllById(keys);
          Map<Long, User> userMap = users.stream()
            .collect(Collectors.toMap(User::getId, Function.identity()));
          // Return in same order as input keys
          return CompletableFuture.completedFuture(
            keys.stream().map(userMap::get).collect(Collectors.toList())
          );
        };
        registry.register("userLoader", DataLoaderFactory.newDataLoader(batchLoader));
      };
    }
  }

  // Use in resolver
  @SchemaMapping(typeName = "Post", field = "author")
  public CompletableFuture<User> author(Post post, DataLoader<Long, User> userLoader) {
    return userLoader.load(post.getAuthorId());
  }
  ```

  4.3 DataLoader for Many-to-Many (List Results)
  ------------------------------------------------
  ```java
  // Batch load: User → List<Post> (one user has many posts)
  @BatchMapping(typeName = "User", field = "posts")
  public Map<User, List<Post>> posts(List<User> users) {
    List<Long> userIds = users.stream().map(User::getId).collect(Collectors.toList());

    // Single query: SELECT * FROM posts WHERE user_id IN (...)
    List<Post> allPosts = postRepository.findByUserIdIn(userIds);

    // Group posts by userId
    Map<Long, List<Post>> postsByUserId = allPosts.stream()
      .collect(Collectors.groupingBy(Post::getUserId));

    // Map each User to their posts
    return users.stream()
      .collect(Collectors.toMap(
        Function.identity(),
        user -> postsByUserId.getOrDefault(user.getId(), List.of())
      ));
  }
  ```

5. DATALOADER CACHING
----------------------
DataLoader maintains a per-request cache (memoization):

  - Same key loaded twice → second call returns cached value immediately
  - Cache is cleared per-request (fresh cache for each GraphQL operation)
  - Do NOT share DataLoader instances across requests!

  Example:
  ```
  loader.load("user-1")   → queued
  loader.load("user-1")   → returns same Promise (from cache, no extra batch entry)
  loader.load("user-1")   → returns same Promise (from cache)
  ```

  In one request with 100 posts all by user-1:
  → Only 1 user loaded (despite 100 resolver calls)!

6. DATALOADER BATCH SIZE
--------------------------
For very large requests, you can limit batch size to avoid overwhelming the DB:

```java
DataLoaderOptions options = DataLoaderOptions.newOptions()
  .setMaxBatchSize(100)     // Batch at most 100 keys at a time
  .setCachingEnabled(true);

DataLoader<Long, User> userLoader = DataLoaderFactory.newDataLoader(batchFn, options);
```

7. DATALOADER EXECUTION SCHEDULING
-------------------------------------
DataLoader dispatches when:
  a) The current execution tick ends (automatic in graphql-java with
     ScheduledDataLoaderRegistry)
  b) `dataLoader.dispatch()` is called manually

In Spring for GraphQL, dispatching is handled automatically.

8. DETECTING N+1 IN PRODUCTION
---------------------------------
Signs you have an N+1 problem:
  - Query time increases linearly with result count
  - DB slow query log shows many identical queries
  - APM tool (New Relic, DataDog) shows spike in DB calls per GraphQL request

Debugging:
```java
// Enable DataLoader statistics
@Bean
public DataLoaderRegistrar userDataLoaderRegistrar(UserRepository repo) {
  return registry -> {
    DataLoaderOptions options = DataLoaderOptions.newOptions()
      .setStatisticsCollector(SimpleStatisticsCollector::new);

    // ... register loader
  };
}

// Log DataLoader stats at end of request
DataLoaderRegistry registry = ...;
registry.getDataLoaders().forEach(dl -> {
  log.info("DataLoader stats: {}", dl.getStatistics());
});
```

9. ALTERNATIVES AND COMPLEMENTS TO DATALOADER
-----------------------------------------------
  a) Look-ahead JOIN (most efficient for simple cases)
     → Inspect child selections in root resolver
     → JOIN the needed tables upfront
     → No DataLoader needed, single query
     → But: complicates resolver code

  b) DataLoader (recommended for complex graphs)
     → Clean separation of concerns
     → Works at any nesting level
     → Automatic batching and caching

  c) Persistent Query Optimization
     → Analyze most common query shapes
     → Create optimized SQL views or stored procedures for them
     → Cache at application level

  d) Limit query depth
     → Prevent deeply nested queries that cause cascading N+1
     → Max depth of 5 is common

  e) Field-level resolver skip
     → Only define resolvers for fields that aren't already on the parent object
     → Avoid unnecessary resolver calls

10. BEYOND N+1: M×N PROBLEM
-----------------------------
The M×N problem is even worse: a list of M items, each with N related items,
each with their own related items...

```graphql
{
  users(first: 10) {           # 10 users
    posts(first: 5) {          # 5 posts per user = 50 posts
      comments(first: 3) {     # 3 comments per post = 150 comments
        author { name }        # 150 author lookups → N+1!
      }
    }
  }
}
```

Without DataLoader: 1 + 10 + 50 + 150 = 211 queries
With DataLoader:    1 + 1 + 1 + 1 = 4 queries (batch at each level)
With depth limiting: Reject query if too deep!

11. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the N+1 problem in GraphQL?
A: When resolving a list of N items, a naive field resolver for a nested
   relationship fires one DB query per item, resulting in N+1 queries (1
   for the list + N for each item's related data). With 100 posts, this
   means 101 DB queries instead of 2.

Q: How does DataLoader solve the N+1 problem?
A: DataLoader batches multiple individual load(key) calls that happen in
   the same execution tick into a single batch function call. Instead of
   100 individual user lookups, all 100 user IDs are collected and
   fetched with a single `SELECT WHERE id IN (...)`. It also caches within
   the request so the same key is never loaded twice.

Q: What is the difference between batching and caching in DataLoader?
A: Batching collects multiple keys from the current tick and fetches them
   together in one round trip. Caching stores results per request — if the
   same key is requested multiple times within one request, the value is
   returned from cache immediately without re-batching.

Q: Should DataLoader instances be shared across requests?
A: No! DataLoader instances must be created fresh per request. They maintain
   a per-request cache. Sharing across requests would serve stale data,
   create memory leaks, and potentially expose data from other users' requests.

Q: What is @BatchMapping in Spring for GraphQL?
A: @BatchMapping is Spring's high-level annotation for batch loading. Instead
   of loading one entity's field at a time (N+1 risk), it receives ALL parent
   objects needing that field in one call. You return a Map<Parent, Value>
   and Spring distributes results back to each resolver. Internally, it uses
   DataLoader.

Q: Is DataLoader only useful for DB queries?
A: No. DataLoader can batch any asynchronous operation: REST API calls,
   gRPC calls, Redis lookups, external service calls. Anywhere you'd otherwise
   make N individual network calls, DataLoader can batch them.

Q: How would you detect an N+1 problem in production?
A: (1) Enable DB query logging and count queries per request — N+1 shows
   as many identical queries with incrementing IDs. (2) Use APM (DataDog,
   New Relic) to see DB query count per GraphQL operation. (3) Use DataLoader
   statistics to see batch sizes — small batch sizes (1) indicate N+1.
   (4) Look for response time that scales linearly with result set size.
