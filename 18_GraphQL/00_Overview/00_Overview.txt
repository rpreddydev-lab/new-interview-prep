GRAPHQL — COMPLETE OVERVIEW
================================================================

1. WHAT IS GRAPHQL?
-------------------
GraphQL is a query language for APIs and a server-side runtime for executing
those queries. It was developed internally by Facebook in 2012 and open-sourced
in 2015. Unlike REST, where the server defines what data is returned, GraphQL
lets the CLIENT specify exactly what data it needs.

Key insight: GraphQL is a SPECIFICATION, not a library or framework. Multiple
implementations exist in nearly every language (graphql-java, graphql-js,
graphql-dotnet, Strawberry for Python, etc.).

2. CORE PHILOSOPHY
------------------
  - "Ask for what you need, get exactly that"
  - Single endpoint (typically /graphql)
  - Hierarchical: queries mirror the shape of the data they return
  - Strongly typed: every API is defined by a type system (the Schema)
  - Introspective: clients can query the schema itself

3. THREE OPERATION TYPES
------------------------
  a) Query      — Read data (like GET in REST)
  b) Mutation   — Write/modify data (like POST/PUT/DELETE in REST)
  c) Subscription — Real-time stream of data (WebSocket-based push)

4. THE GRAPHQL EXECUTION LIFECYCLE
------------------------------------
  Step 1: CLIENT sends HTTP POST to /graphql with a JSON body:
    {
      "query": "{ user(id: 1) { name email } }",
      "variables": {},
      "operationName": null
    }

  Step 2: SERVER parses the query string into an AST (Abstract Syntax Tree)

  Step 3: SERVER validates the AST against the Schema

  Step 4: SERVER executes the query — resolver functions are called for each field

  Step 5: SERVER serializes the result and returns:
    {
      "data": { "user": { "name": "Alice", "email": "alice@example.com" } },
      "errors": []
    }

5. KEY CHARACTERISTICS
-----------------------
  • Single Endpoint:      All operations go through POST /graphql
  • Declarative:          Clients declare data requirements up front
  • Strongly Typed:       Schema is the contract between client and server
  • Self-Documenting:     Schema doubles as documentation via Introspection
  • Version-Free:         Add fields without breaking existing clients
  • Transport Agnostic:   Usually HTTP, but also WebSockets, gRPC, etc.

6. GRAPHQL RESPONSE STRUCTURE
------------------------------
Every GraphQL response has the same shape:
  {
    "data": { ... },        // Successful field data (null if fatal error)
    "errors": [ ... ],      // Array of error objects (optional)
    "extensions": { ... }   // Optional metadata (tracing, pagination cursors)
  }

  Error object shape:
  {
    "message": "User not found",
    "locations": [{ "line": 2, "column": 3 }],
    "path": ["user"],
    "extensions": { "code": "NOT_FOUND", "timestamp": "2026-04-08T10:00:00Z" }
  }

7. THE GRAPHQL SCHEMA
---------------------
The Schema is the single source of truth. Written in SDL (Schema Definition
Language), it defines:
  - Types (Object, Scalar, Enum, Interface, Union, Input)
  - Queries, Mutations, and Subscriptions available
  - Relationships between types
  - Documentation strings

  Example:
  ```
  type Query {
    user(id: ID!): User
    users: [User!]!
  }

  type User {
    id: ID!
    name: String!
    email: String!
    posts: [Post!]!
  }
  ```

8. GRAPHQL ECOSYSTEM
---------------------
  Clients:
    - Apollo Client (JS/React)
    - URQL
    - Relay (Facebook)
    - Spring GraphQL (Java)

  Servers:
    - Apollo Server (Node.js)
    - graphql-java + Spring for GraphQL
    - Hasura (auto-generates GraphQL from DB)
    - Hot Chocolate (.NET)
    - Strawberry (Python)

  Tools:
    - GraphiQL     — In-browser IDE for writing queries
    - Apollo Studio — Schema registry, query monitoring
    - DataLoader   — Batching utility to solve N+1 problem
    - Nexus / TypeGraphQL — Code-first schema generation

9. GRAPHQL VS REST — QUICK CONTRAST
--------------------------------------
  Feature             REST                GraphQL
  ─────────────────────────────────────────────────────────
  Endpoints           Many (one per resource)   One
  Data fetching       Over/Under fetch possible  Precise
  Schema/Contract     OpenAPI/Swagger (optional) Always (SDL)
  Versioning          /v1, /v2                   Evolve schema
  Real-time           Webhooks/polling            Subscriptions
  Caching             HTTP cache (GET)            Need custom approach
  Tooling             Mature                      Growing rapidly

10. INTERVIEW TALKING POINTS
-----------------------------
  • "GraphQL is a query language AND a runtime. The specification is
    separate from the implementation."
  • "The schema is the contract — if it compiles and validates, both client
    and server agree on the API shape."
  • "GraphQL doesn't replace REST for everything. File uploads, caching,
    and simple CRUD may still be better served by REST."
  • "The main advantages are flexibility for clients, reduced round trips
    (get related data in one request), and better developer experience
    through strong typing and introspection."
  • "The N+1 problem is the biggest performance challenge in GraphQL, solved
    with DataLoader (batching + caching)."
