GRAPHQL vs REST — IN-DEPTH COMPARISON
================================================================

1. ARCHITECTURAL DIFFERENCE
----------------------------
REST (Representational State Transfer):
  - Resource-based: each URL maps to a resource
  - Multiple endpoints: GET /users, GET /users/1, GET /users/1/posts
  - Server decides what data is returned per endpoint
  - HTTP verbs carry semantic meaning (GET=read, POST=create, etc.)

GraphQL:
  - Graph-based: data is a graph of interconnected nodes
  - Single endpoint: POST /graphql
  - Client decides what data is returned via query
  - Only POST (and sometimes GET) used; verbs lose semantic role

2. OVER-FETCHING AND UNDER-FETCHING
-------------------------------------
OVER-FETCHING (REST problem):
  GET /users/1 returns:
    { "id": 1, "name": "Alice", "email": "alice@ex.com",
      "address": {...}, "preferences": {...}, "createdAt": "..." }

  But client only needed: name, email → wasted bandwidth & processing.

UNDER-FETCHING (REST problem):
  Client needs user + their posts + comments on those posts.
  REST requires:
    GET /users/1          → user data
    GET /users/1/posts    → post IDs
    GET /posts/10         → post details (N calls for N posts)
    GET /posts/10/comments → comment IDs ... (even more calls)

GraphQL solution:
  One request gets exactly what's needed:
  ```graphql
  query {
    user(id: 1) {
      name
      email
      posts {
        title
        comments {
          body
          author { name }
        }
      }
    }
  }
  ```

3. ENDPOINT DESIGN
------------------
REST:
  GET    /products         → list products
  GET    /products/42      → get product
  POST   /products         → create product
  PUT    /products/42      → update product
  DELETE /products/42      → delete product

GraphQL (all on POST /graphql):
  Query:    { products { id name price } }
  Query:    { product(id: 42) { id name } }
  Mutation: mutation { createProduct(input: {...}) { id } }
  Mutation: mutation { updateProduct(id: 42, input: {...}) { id } }
  Mutation: mutation { deleteProduct(id: 42) { success } }

4. VERSIONING
--------------
REST versioning:
  - /api/v1/users   (old clients hit v1)
  - /api/v2/users   (new clients hit v2)
  - Parallel maintenance burden
  - Deprecation cycles are painful

GraphQL versioning strategy:
  - No versioning! Schema evolves.
  - Add new fields without breaking old clients
    (old clients simply don't request new fields)
  - Deprecate fields with @deprecated directive:
    ```graphql
    type User {
      username: String @deprecated(reason: "Use 'name' instead")
      name: String!
    }
    ```
  - Only REMOVE a field when zero clients use it (track via query analytics)
  - This is called "versionless API evolution"

5. TYPE SAFETY
--------------
REST:
  - Optionally typed via OpenAPI/Swagger
  - Many teams skip it → undocumented, no validation
  - Type contracts drift from implementation

GraphQL:
  - Schema is MANDATORY and enforced by the runtime
  - Every field has a declared type
  - Non-null types enforced: String! means never null
  - Invalid queries rejected at parse/validation time, before execution

6. DOCUMENTATION
-----------------
REST: Must maintain separate documentation (Swagger UI, Postman collections)

GraphQL:
  - Schema IS the documentation
  - Add description strings directly in SDL:
    ```graphql
    """
    Represents a product in the catalog.
    """
    type Product {
      "Unique identifier"
      id: ID!
      "Display name of the product"
      name: String!
    }
    ```
  - Introspection allows tools to auto-generate docs (GraphiQL, Apollo Sandbox)

7. CACHING
----------
REST caching (strong):
  - HTTP GET requests are cacheable by default
  - CDN, browser cache, Varnish all work out-of-the-box
  - Cache key = URL + headers
  - ETags, Cache-Control headers

GraphQL caching (harder):
  - All requests are POST → no HTTP-level GET caching
  - Must implement application-level caching
  - Options:
    a) Persisted Queries — assign a hash to a query, cache by hash
    b) DataLoader       — in-memory per-request cache (deduplication)
    c) Apollo Client    — normalized in-memory client-side cache
    d) CDN with APQ     — Automatic Persisted Queries allow GET requests for cached queries
    e) Field-level cache — cache resolver results with TTL (e.g., Redis)

8. ERROR HANDLING
-----------------
REST:
  - HTTP status codes carry meaning: 200, 201, 400, 401, 403, 404, 500
  - Body may have error detail

GraphQL:
  - HTTP status is almost always 200 (even on errors!)
  - Errors are in the "errors" array in the response body
  - Partial success is possible: some fields resolve, others error
  - Custom error codes in "extensions":
    ```json
    {
      "data": { "user": null },
      "errors": [{
        "message": "User not found",
        "extensions": { "code": "USER_NOT_FOUND", "statusCode": 404 }
      }]
    }
    ```
  INTERVIEW TIP: "In REST a 404 immediately tells the client something is
  missing. In GraphQL you must check the 'errors' array even when HTTP returns
  200. This is often surprising to developers new to GraphQL."

9. REAL-TIME DATA
-----------------
REST real-time options:
  - Polling (client repeatedly GETs data)
  - Long-polling (hold connection open)
  - Server-Sent Events (SSE)
  - Webhooks (server calls client)

GraphQL Subscriptions:
  - First-class real-time via WebSocket (usually graphql-ws or subscriptions-transport-ws)
  - Client subscribes to an event; server pushes updates
  ```graphql
  subscription {
    orderStatusChanged(orderId: "123") {
      status
      updatedAt
    }
  }
  ```

10. FILE UPLOADS
----------------
REST: PUT/POST with multipart/form-data — natural and well-supported
GraphQL: Not natively supported! Must use:
  - GraphQL multipart spec (jaydenseric/graphql-multipart-request-spec)
  - Or use a separate REST endpoint for uploads
  - Spring for GraphQL supports file uploads via the multipart spec

11. WHEN TO CHOOSE GRAPHQL OVER REST
--------------------------------------
Choose GraphQL when:
  ✓ Multiple clients (mobile, web, TV) need different data shapes
  ✓ Complex, interconnected data (social graph, product catalog)
  ✓ Rapid iteration — client teams shouldn't wait on backend changes
  ✓ You want strong typing and schema-first development
  ✓ Reducing round trips is critical (mobile on slow networks)

Choose REST when:
  ✓ Simple CRUD operations with uniform data needs
  ✓ Public API that must work with HTTP caching (CDN-heavy)
  ✓ File upload/download is a primary use case
  ✓ Team is unfamiliar with GraphQL and timeline is tight
  ✓ API is consumed by many third-party developers who expect REST

12. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the N+1 problem in GraphQL?
A: When resolving a list of N items, each item's sub-field triggers a separate
   DB query, resulting in N+1 total queries. Solved with DataLoader (batching).

Q: Why does GraphQL always return HTTP 200?
A: The spec separates transport errors (HTTP codes) from application errors
   (in the "errors" array). A request can partially succeed—some fields
   resolved correctly while others errored—which doesn't map cleanly to a
   single HTTP status. The convention is 200 unless the request itself was
   malformed (400) or the server crashed (500).

Q: Can GraphQL be used with GET?
A: Yes. Simple queries can be sent as GET with the query in a URL parameter:
   GET /graphql?query={user(id:1){name}}
   This allows HTTP caching for those queries. Mutations must always be POST.

Q: How is versioning handled in GraphQL?
A: GraphQL APIs are designed to be versionless. New fields are added without
   breaking existing queries. Old fields are deprecated with @deprecated and
   eventually removed only when usage drops to zero. Analytics on query usage
   (via Apollo Studio or similar) help make these decisions.

Q: How does GraphQL handle authentication vs REST?
A: Both use the same mechanisms (Bearer tokens, cookies, OAuth). The difference
   is that GraphQL authorization is typically field-level or resolver-level,
   using a context object populated with the authenticated user. REST typically
   secures endpoints; GraphQL secures individual fields.
