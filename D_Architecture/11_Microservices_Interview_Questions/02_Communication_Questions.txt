TOP 15 COMMUNICATION QUESTIONS — covering REST, gRPC, Kafka, service mesh.

Q1. What is the difference between synchronous and asynchronous communication?
================================================================================

ANSWER:
Synchronous: Caller sends request and BLOCKS waiting for response.
  Examples: REST HTTP call, gRPC unary call.
  Use when: caller needs result immediately to continue processing.
  Tradeoff: temporal coupling — if provider is slow/down, caller is blocked.

Asynchronous: Caller sends message and continues. Response (if any) comes later.
  Examples: Kafka message, RabbitMQ queue, SQS.
  Use when: operation can be processed later, decoupling is important.
  Tradeoff: eventual consistency, harder to debug, message ordering complexity.

DECIDING FRAMEWORK:
  "Does the caller NEED the result to continue?" → Synchronous
  "Can the caller continue without the result?" → Asynchronous

  Hybrid: Publish event (async) but expose a polling endpoint for result.
  Pattern: "Fire and poll" — order service publishes to Kafka, client polls
  GET /orders/{id} until status changes.

Q2. REST vs gRPC — when do you choose each?
================================================================================

ANSWER:
REST (HTTP/1.1, JSON):
  + Human-readable, easy to debug (curl, browser, Postman)
  + Universal support, firewall-friendly
  + Great for public APIs, third-party integrations
  - Verbose (JSON parsing overhead)
  - No strong typing (schema drift over time)
  - Limited to request-response

gRPC (HTTP/2, Protocol Buffers):
  + 5-10x faster than REST (binary serialization, multiplexing, compression)
  + Strong typing via .proto schema (compile-time contract validation)
  + Streaming support (server-side, client-side, bidirectional)
  + Code generation in 10+ languages
  - Not human-readable (binary)
  - Limited browser support (grpc-web needed)
  - Tooling less mature for debugging

RULE:
  Internal service-to-service → gRPC (performance, type safety)
  Public API / third-party integration → REST
  Real-time streaming (sensor data, live updates) → gRPC streaming

Q3. How does Kafka differ from RabbitMQ?
================================================================================

ANSWER:
                  │ Kafka                      │ RabbitMQ
──────────────────┼────────────────────────────┼───────────────────────────
Architecture      │ Log-based (append-only)    │ Queue-based (push/pull)
──────────────────┼────────────────────────────┼───────────────────────────
Message storage   │ Retained (configurable)    │ Deleted after consume
──────────────────┼────────────────────────────┼───────────────────────────
Replay            │ Yes (offset-based replay)  │ No (once consumed, gone)
──────────────────┼────────────────────────────┼───────────────────────────
Throughput        │ Millions/sec (sequential)  │ Thousands/sec
──────────────────┼────────────────────────────┼───────────────────────────
Consumer model    │ Consumer group / pull      │ Push or pull
──────────────────┼────────────────────────────┼───────────────────────────
Ordering          │ Per partition              │ Per queue
──────────────────┼────────────────────────────┼───────────────────────────
Use case          │ Event streaming, audit log │ Task queues, RPC
──────────────────┼────────────────────────────┼───────────────────────────
Message routing   │ Topic + partition key      │ Exchange + routing key

CHOOSE KAFKA when: high throughput, event replay needed, event sourcing,
audit trail, Kafka Streams processing.
CHOOSE RabbitMQ when: task queues, complex routing (fanout, topic, headers),
lower volume, transactional messages.

Q4. What is the outbox pattern and why is it needed?
================================================================================

ANSWER:
Problem: Service needs to update DB AND publish Kafka event atomically.
If DB commit succeeds but Kafka publish fails → data inconsistency.
Two-phase commit is too expensive.

Outbox Pattern Solution:
  1. Write business entity + outbox event record in SAME database transaction
  2. Separate process (CDC / polling) reads outbox table and publishes to Kafka
  3. After publish, mark outbox record as processed

  // Step 1: Atomic DB write
  @Transactional
  public void createOrder(CreateOrderRequest request) {
    Order order = orderRepository.save(new Order(request));
    outboxRepository.save(OutboxEvent.of("OrderCreated", order.getId(), order));
  }

  // Step 2: CDC reads outbox → publishes to Kafka
  // Debezium monitors outbox table, publishes on INSERT

This guarantees: if the event exists in Kafka, the DB change definitely happened.
At-least-once delivery. Consumer must be idempotent.

Q5. How does a service mesh work?
================================================================================

ANSWER:
A service mesh is an infrastructure layer that manages service-to-service
communication transparently via sidecar proxies.

Architecture:
  Data Plane: Envoy/Linkerd2-proxy sidecar injected into every pod.
  Control Plane: Istiod (Istio) configures all proxies centrally.

Each pod's traffic flows: App → Envoy Sidecar → Network → Envoy Sidecar → App

Capabilities handled by mesh (NOT by application code):
  - mTLS (mutual TLS between all services automatically)
  - Load balancing with circuit breaking and outlier detection
  - Retry logic with jitter
  - Timeout enforcement
  - Traffic splitting (canary deployments without code changes)
  - Distributed tracing (Envoy emits spans automatically)
  - Observability (metrics for every service-to-service call)

WHEN to use service mesh:
  Many services (20+), polyglot stack, security/compliance requirements
  (mTLS mandatory), need sophisticated traffic management.

WHEN NOT to use:
  Small number of services — overhead isn't worth it.
  Single language — library-based solutions (Resilience4j) simpler.

Q6. How do you handle API versioning in microservices?
================================================================================

ANSWER — Three strategies:

1. URI versioning: /api/v1/orders, /api/v2/orders
   (+) Simple, explicit, cache-friendly
   (-) Pollutes URL, REST purists dislike it

2. Header versioning: Accept: application/vnd.company.v2+json
   (+) Clean URLs
   (-) Harder to test in browser, not cacheable by default

3. Query parameter: /api/orders?version=2
   (+) Easy to test
   (-) Cacheable only if included in cache key

BEST PRACTICE:
  Prefer URI versioning for simplicity.
  Use semantic versioning for services internally.
  Deploy v1 and v2 simultaneously during migration.
  Deprecate (warn in response header), then sunset old versions.
  Consumer-Driven Contract tests (Pact) catch breaking changes.

ADDITIVE CHANGES (non-breaking, no version bump needed):
  - Adding new optional fields to response
  - Adding new optional request fields
  - Adding new endpoints

BREAKING CHANGES (require version bump):
  - Removing/renaming fields
  - Changing field types
  - Changing status codes
  - Removing endpoints

Q7. What is the difference between an event, a command, and a query?
================================================================================

ANSWER:
Command: "DO this thing." Directed at a specific service.
  Name: imperative (CreateOrder, ProcessPayment)
  Has one handler. Expects a response (ack or result).
  Example: PlaceOrderCommand → Order Service

Event: "THIS THING HAPPENED." Fact about the past.
  Name: past tense (OrderPlaced, PaymentProcessed)
  Has zero or many handlers. Fire and forget.
  Example: OrderPlacedEvent → [Inventory Service, Notification Service, Billing Service]

Query: "GIVE ME DATA." No side effects. Read-only.
  Name: question form (GetOrderById, ListUserOrders)
  Returns data. Idempotent.
  Example: GetOrderByIdQuery → Order Service

CQRS separates Commands + Queries into different models (write side / read side).
Event-driven architecture uses Events to decouple services.

Q8. How do you handle service communication when a downstream service is unavailable?
================================================================================

ANSWER — Resilience patterns:

1. Retry with Exponential Backoff + Jitter
   Transient failures (network blip) often resolve with retry.
   Jitter prevents thundering herd (all services retrying simultaneously).

2. Circuit Breaker (Resilience4j)
   CLOSED → normal. OPEN → fail fast, return fallback. HALF-OPEN → probe.
   Prevents cascading failures when a service is down.

3. Fallback
   Return cached value, default response, or degraded functionality.
   Example: product recommendations down → return empty list, not error.

4. Bulkhead
   Limit concurrent calls to a slow service.
   Prevent one slow service from consuming all threads.

5. Timeout
   Never wait indefinitely. Set connection timeout + read timeout.
   Fail fast rather than holding resources.

6. Dead Letter Queue (async)
   Failed messages go to DLQ for retry/manual intervention.

IN PRACTICE:
  @CircuitBreaker(name = "inventory", fallbackMethod = "fallbackInventory")
  @Retry(name = "inventory")
  @TimeLimiter(name = "inventory")
  public Mono<InventoryStatus> checkInventory(Long productId) { ... }

Q9. What is the difference between choreography and orchestration in Saga?
================================================================================

ANSWER:
Saga = sequence of local transactions + compensations for distributed transactions.

CHOREOGRAPHY:
  Each service publishes events. Other services react.
  No central coordinator.
  
  Order Service publishes OrderCreated →
    Payment Service listens → processes payment → publishes PaymentProcessed →
      Inventory Service listens → reserves stock → publishes StockReserved →
        Order Service listens → updates status to CONFIRMED

  (+) Fully decoupled, no SPOF
  (-) Hard to track saga state, cycle risk, debugging is painful

ORCHESTRATION:
  Central Saga Orchestrator (state machine) drives the saga.
  Orchestrator sends commands to services, receives responses.
  
  OrderSaga → send PaymentCommand → receive PaymentResult →
    if success: send ReserveStockCommand → receive StockResult →
      if success: send ConfirmOrderCommand

  (+) Clear flow, easy to visualize, easier to add steps
  (-) Orchestrator is a coupling point
  (-) Orchestrator can become God object

RECOMMENDATION:
  Simple flows (2-3 steps) → Choreography.
  Complex flows (5+ steps, conditional branching) → Orchestration.

Q10. What is request tracing and how do you implement it?
================================================================================

ANSWER:
Distributed tracing tracks a request as it flows through multiple services.
Each request gets a unique Trace ID. Each service hop creates a Span.

Implementation:
  1. Assign Trace ID at entry point (API Gateway or first service)
  2. Propagate via HTTP headers:
     - W3C traceparent: 00-traceId-spanId-flags
     - B3 headers: X-B3-TraceId, X-B3-SpanId
  3. Each service creates child spans for its operations
  4. All spans exported to tracing backend (Jaeger, Zipkin, Tempo)

Spring Boot + OpenTelemetry:
  spring.application.name=order-service
  management.tracing.sampling.probability=1.0

  # Auto-configures trace/span injection into MDC for logging
  # logging.pattern.level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"

Correlation with logs:
  traceId + spanId injected into every log line via MDC.
  In Grafana: correlate traces (Tempo) with logs (Loki) via traceId link.

Q11. How do you prevent a slow service from cascading failures?
================================================================================

ANSWER:
Cascading failure: Service A calls slow Service B → A's threads fill up →
A can't serve its own requests → Service C calling A also fails → entire system down.

Prevention:

1. Timeouts — always set. Never wait indefinitely.
   WebClient: .responseTimeout(Duration.ofSeconds(3))

2. Circuit Breaker — stop calling failed service.
   Resilience4j CircuitBreaker opens after failure threshold.
   Fail fast + fallback instead of waiting.

3. Bulkhead — isolate thread pools per dependency.
   Even if Service B is slow, only B's thread pool fills up.
   Other services' thread pools unaffected.
   @Bulkhead(name = "inventory", type = THREADPOOL)

4. Rate limiting inbound — prevent overload from clients above.
   Protects the service from being the slow one.

5. Asynchronous communication — decouple at Kafka level.
   Service B down? Messages queue in Kafka, Service B processes when recovered.
   Service A never blocked by Service B.

================================================================================

ANSWER:

────────────────────┼─────────────────────────────┼──────────────────────────

────────────────────┼─────────────────────────────┼──────────────────────────

────────────────────┼─────────────────────────────┼──────────────────────────

────────────────────┼─────────────────────────────┼──────────────────────────

Concern             │ API management              │ Traffic distribution

Typical architecture:
  Internet → Load Balancer (distribute across gateway instances) →
  API Gateway (auth, rate limit, route) → Microservices

Q13. How do you implement distributed rate limiting?
================================================================================

ANSWER:
Per-instance rate limiting (in-memory) fails in multi-instance deployments.
If each of 5 gateway instances allows 100 req/s → effectively 500 req/s.

Distributed rate limiting: use Redis as shared counter.

  // Spring Cloud Gateway + Redis rate limiter
  spring:
    cloud:
      gateway:
        routes:
          - id: order-service
            uri: lb://order-service
            predicates:
              - Path=/api/orders/**
            filters:
              - name: RequestRateLimiter
                args:
                  redis-rate-limiter.replenishRate: 10   # tokens/sec
                  redis-rate-limiter.burstCapacity: 20   # max burst
                  key-resolver: "#{@userKeyResolver}"    # per user

  // Key resolver — rate limit per user
  @Bean
  KeyResolver userKeyResolver() {
    return exchange -> Mono.justOrEmpty(
      exchange.getRequest().getHeaders().getFirst("X-User-Id")
    );
  }

Rate limiting algorithms:
  Token Bucket — tokens replenish at fixed rate. Allow bursts up to bucket size.
  Leaky Bucket — smooth output rate, queue requests.
  Fixed Window — count resets every interval. Boundary problem.
  Sliding Window — more accurate, counts requests in rolling window.

Q14. How do you test service communication?
================================================================================

ANSWER:
Testing strategy for communication:

1. Unit: Mock HTTP clients with Mockito. Test service logic.

2. Contract (Pact): Consumer writes contract tests. Provider verifies.
   Tests API interface compatibility without running both services.

3. Integration (WireMock): Test your HTTP client code against realistic stubs.
   WireMock stubs provider responses. Tests retry logic, error handling,
   timeout handling, circuit breaker behavior.

4. Component Test: Run service + its TestContainers (DB, Kafka) + WireMock
   for all HTTP dependencies. Test complete service in near-isolation.

5. E2E: Full environment. Only critical paths.

WireMock for fault injection:
  // Test how service handles provider slowness
  wireMock.stubFor(get("/inventory/items/100")
    .willReturn(aResponse()
      .withFixedDelay(6000)  // 6 second delay → should trigger timeout
      .withStatus(200)));

Q15. What is idempotency and why is it important in microservices?
================================================================================

ANSWER:
Idempotency: Calling an operation multiple times with same input has same
result as calling it once. No additional side effects on repeated calls.

WHY critical in microservices:
  - Network calls can fail after server processed request but before response
  - Message queues guarantee at-least-once delivery (duplicates possible)
  - Retries are essential for reliability but create duplicates

Implementation patterns:
  1. Natural idempotency: read-only operations (GET), absolute state (PUT)
  2. Idempotency key: client sends unique ID, server deduplicates
     Header: Idempotency-Key: <UUID>
     Server stores (key, response), returns stored response on duplicate.

  // Idempotency key table
  CREATE TABLE idempotency_keys (
    key VARCHAR(255) PRIMARY KEY,
    response_body TEXT,
    status_code INT,
    created_at TIMESTAMP DEFAULT NOW()
  );

  // Filter intercepts duplicate requests and replays response
  // See 08_Microservices_Patterns/07_Idempotency_Pattern.txt

  3. Conditional DB inserts: INSERT ... ON CONFLICT DO NOTHING
  4. Message deduplication: inbox table with message_id UNIQUE constraint

WHICH OPERATIONS NEED idempotency keys:
  POST /orders — creates new resource
  POST /payments — charges card
  POST /reservations — reserves inventory
  Not needed for: GET, PUT (naturally idempotent)
