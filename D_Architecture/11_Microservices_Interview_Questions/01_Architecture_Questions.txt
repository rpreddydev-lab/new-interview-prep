================================================================================

TOP 15 ARCHITECTURE QUESTIONS — with answers, depth, and talking points.

================================================================================
Q1. What are microservices and how are they different from a monolith?
================================================================================

ANSWER:
Microservices is an architectural style where an application is built as a
collection of small, independently deployable services. Each service:
  - Owns a single business capability (bounded context)
  - Has its own database (database-per-service)
  - Communicates over lightweight protocols (HTTP/gRPC/messaging)
  - Can be independently deployed and scaled

Monolith: All functionality in a single deployable unit. Changes require
redeploying the entire application. A bug in one module can crash everything.

Key differences:
  Monolith                         │ Microservices
  ─────────────────────────────────┼──────────────────────────────────
  Single deployable unit           │ Many independent services
  Single database                  │ DB per service
  Shared memory communication      │ Network calls (latency, failures)
  Easy to test and debug           │ Complex testing and observability
  Technology locked (one stack)    │ Polyglot (each service picks its stack)
  Scale whole application          │ Scale specific services
  Simple transactions (ACID)       │ Distributed transactions (Saga)

FOLLOW-UP: "So why not always use microservices?"
  The distributed systems tax: network latency, partial failures, distributed
  transactions, observability complexity, operational overhead (100 services
  to deploy, monitor, secure). Microservices pay off at scale; premature
  decomposition slows small teams.

Q2. How do you decompose a monolith into microservices?
================================================================================

ANSWER — Four decomposition strategies:

1. Decompose by Business Capability (preferred)
   Each service = a core business capability
   E-commerce: Order Service, Payment Service, Inventory Service, User Service
   
2. Decompose by Subdomain (Domain-Driven Design)
   Identify Bounded Contexts — areas with clear domain boundaries
   The language used in one context is different from another
   (e.g., "customer" in Sales vs "client" in Billing)

3. Decompose by Volatility
   Services that change frequently → independent deployments
   Stable core → can stay together longer

4. Strangler Fig Pattern
   Don't rewrite — gradually route traffic from the monolith to new services
   Wrap monolith with API Gateway, extract services one by one

PITFALLS:
  - Too many services too soon (nanoservices)
  - Service boundaries based on data model, not business capability
  - Shared database — negates independence
  - Distributed monolith — tight coupling over the network

Q3. What is Domain-Driven Design and how does it apply to microservices?
================================================================================

ANSWER:
DDD is a software design approach focused on modeling software to match the
business domain.

Key concepts:
  Bounded Context: A boundary within which a domain model applies consistently.
    Example: "Order" means different things in Sales vs Fulfillment vs Billing.
    Each context has its own model.

  Ubiquitous Language: Shared vocabulary between developers and domain experts
    within a bounded context. Code uses the same terms as business.

  Aggregate: Cluster of objects treated as a single unit for data changes.
    Has a root entity (Aggregate Root). External access only through root.
    Example: Order aggregate = Order + OrderItems + ShippingAddress.

  Domain Events: Something meaningful that happened in the domain.
    Example: OrderPlaced, PaymentProcessed, ItemShipped.

  Anti-Corruption Layer (ACL): Translates between different bounded contexts.
    Prevents one model from corrupting another.

Microservice mapping:
  1 Bounded Context ≈ 1 Microservice (starting point)
  Domain Events → Kafka messages between services
  Aggregates → unit of consistency within a service

Q4. What is the Twelve-Factor App?
================================================================================

ANSWER — 12 principles for building cloud-native services:

  I.   Codebase — one repo per service, multiple deployments
  II.  Dependencies — declared and isolated (pom.xml, no system deps)
  III. Config — store in environment (not code). 12FA rule violated: if
       you can't open-source the code due to config in code
  IV.  Backing services — treat DB/Kafka/Redis as attached resources
  V.   Build/Release/Run — strictly separate stages
  VI.  Processes — stateless, share-nothing
  VII. Port binding — export services via port (self-contained)
  VIII.Concurrency — scale out via process model
  IX.  Disposability — fast startup, graceful shutdown (SIGTERM handling)
  X.   Dev/prod parity — keep environments as similar as possible
  XI.  Logs — treat as event streams (stdout), don't manage log files
  XII. Admin processes — run management tasks as one-off processes

Most critical for microservices interviews: III (config), VI (stateless),
IX (fast startup/graceful shutdown), XI (structured logging to stdout).

Q5. How do microservices handle distributed transactions?
================================================================================

ANSWER:
Traditional ACID transactions don't span services (can't lock rows across
different databases). Two main patterns:

1. SAGA Pattern — sequence of local transactions with compensations.
   Two implementations:
   a. Choreography: Services publish events, others react.
      + Decoupled, no orchestrator
      - Hard to visualize, hard to debug, cycle risk
   b. Orchestration: Central orchestrator (saga manager) tells services what to do.
      + Clear flow, easier to visualize
      - Orchestrator is a coupling point

2. Two-Phase Commit (2PC) — NOT recommended for microservices.
   Phase 1: Coordinator asks all services to prepare (lock resources).
   Phase 2: Coordinator commits if all prepared, otherwise rollback.
   Problems: blocking protocol, coordinator SPOF, kills availability.

RECOMMENDATION: Use Sagas. Accept eventual consistency. Make business
operations idempotent. Use Outbox Pattern to ensure events are published
atomically with database changes.

Q6. What is the CAP Theorem and how does it affect microservices design?
================================================================================

ANSWER:
CAP Theorem: A distributed system can guarantee at most 2 of 3 properties:
  C — Consistency: Every read gets the most recent write
  A — Availability: Every request gets a response (not error)
  P — Partition Tolerance: System operates despite network partitions

Network partitions WILL happen in distributed systems.
Therefore real choice is: CP (consistency over availability) vs AP (availability
over consistency).

Microservices typically choose AP:
  - Services should remain available even when other services are unreachable
  - Accept eventual consistency (Saga, event-driven updates)
  - Use compensating transactions instead of rollback

Example: Order service creates order (local write) even if Inventory service
is temporarily unavailable. Inventory check happens asynchronously. If
insufficient inventory → compensate (cancel order, notify user).

PACELC adds latency dimension: even without partition, trade consistency for
lower latency. Most microservices choose EL (eventual consistency, low latency).

Q7. What is eventual consistency and how do you handle it?
================================================================================

ANSWER:
Eventual consistency means: all replicas/services will eventually converge
to the same state, but not immediately.

Example: User updates profile → Profile Service updates DB → event published
to Kafka → Order History Service updates its read model. During propagation
delay (milliseconds to seconds), Order History might show stale data.

Handling strategies:
  1. Accept and document it — most reads tolerate slight staleness
  2. Read-your-writes consistency — after write, read from same service/region
  3. Versioning — include version/timestamp in responses
  4. Causal consistency — track causal dependencies (vector clocks)
  5. Synchronous communication where strong consistency required
     (but this couples services — use sparingly)

UI handling: Show "order placed, processing..." instead of immediate confirmation.
Optimistic UI updates that rollback on failure.

Q8. How does service-to-service communication work in microservices?
================================================================================

→ See 01_Communication_Questions.txt for full depth on this topic.

Summary:
  Synchronous (direct): REST (HTTP/JSON) or gRPC (HTTP/2, Protocol Buffers)
  Use for: real-time queries, reads, when caller needs immediate response

  Asynchronous (messaging): Kafka, RabbitMQ, SQS
  Use for: commands, state changes, when coupling should be minimal,
  when operation can be eventual

  Service Mesh (Istio/Linkerd): handles cross-cutting concerns (mTLS, retries,
  circuit breaking) at infrastructure level via sidecar proxies

Q9. What is an API Gateway and what does it do?
================================================================================

ANSWER:
API Gateway is the single entry point for all external requests.

Responsibilities:
  - Request routing to appropriate microservice
  - Authentication/Authorization (JWT validation)
  - Rate limiting (protect services from abuse)
  - SSL termination
  - Request/response transformation
  - Load balancing
  - Caching
  - Request aggregation (BFF pattern)

Popular implementations:
  Spring Cloud Gateway — Spring-native, reactive (Netty)
  Kong — plugin-based, performance-focused
  AWS API Gateway — managed
  Nginx/Envoy — proxy-based

Anti-pattern: putting business logic in API Gateway.
API Gateway should be dumb routing + cross-cutting concerns only.

Q10. What is service discovery and how does it work?
================================================================================

ANSWER:
Service discovery enables services to find each other dynamically.
In dynamic environments (K8s, cloud), service IPs change constantly.

Client-side discovery:
  Client queries Service Registry (Eureka/Consul) directly.
  Client performs load balancing. Example: Spring Cloud Netflix Eureka.
  (+) Client has control over load balancing strategy
  (-) Client must implement discovery logic

Server-side discovery:
  Client sends request to Load Balancer/API Gateway.
  LB queries registry and routes request.
  Example: Kubernetes kube-proxy + Service, AWS ALB.
  (+) Client is simple
  (-) LB is another network hop, potential bottleneck

Kubernetes DNS-based:
  K8s assigns each Service a DNS name: order-service.default.svc.cluster.local
  kube-dns resolves to stable ClusterIP (virtual IP with iptables routing).
  Pod IPs are ephemeral but Service IP is stable.

Q11. How do you ensure data consistency across microservices?
================================================================================

ANSWER:
Short answer: You don't guarantee strong consistency — you ensure eventual
consistency with compensation mechanisms.

Patterns:
  1. Outbox Pattern: Write to DB + outbox table atomically (single transaction).
     CDC (Debezium) reads outbox table and publishes events to Kafka.
     Guarantees at-least-once delivery. Consumer uses idempotency keys.

  2. Saga Pattern: Chain of local transactions. Compensate on failure.
     Choreography (events) or Orchestration (saga orchestrator).

  3. CQRS: Separate read/write models. Write model (commands) is authoritative.
     Read models (query projections) are eventually consistent copies.

  4. Event Sourcing: Store all state as events. Rebuild state by replaying.
     Never lose history. Time travel: query past state.

KEY INTERVIEW POINT: "I cannot have distributed ACID transactions without
2PC which kills availability. I design for eventual consistency with
compensation and idempotency."

Q12. What is the strangler fig pattern?
================================================================================

ANSWER:
The Strangler Fig Pattern (named after a parasitic plant) is a migration
strategy for incrementally replacing a monolith with microservices.

Steps:
  1. Put API Gateway in front of the monolith
  2. Identify one bounded context to extract first
  3. Build the new microservice in parallel
  4. Route a subset of traffic to new service (e.g., read traffic first)
  5. Gradually shift all traffic to new service
  6. "Strangle" (remove) the monolith code for that capability
  7. Repeat for next capability

Key considerations:
  - Data migration: run dual writes, sync data, then cut over reads
  - Anti-Corruption Layer: between monolith and new service
  - Feature flags: safe rollback if new service has issues

"We never big-bang rewrite. We strangle the monolith incrementally."

Q13. What is the database-per-service pattern and what are the challenges?
================================================================================

ANSWER:
Each service owns its own database (schema). No service can directly access
another service's database. Data sharing only via APIs/events.

Benefits:
  ✓ Service independence — change DB schema without coordinating with other teams
  ✓ Technology choice — polyglot persistence
  ✓ Fault isolation — DB failure doesn't cascade
  ✓ Scale independently

Challenges:
  1. Cross-service queries — can't JOIN across service databases.
     Solutions: CQRS read models, data denormalization, API composition
  2. Distributed transactions — Saga pattern needed
  3. Referential integrity — no foreign keys across services.
     Solution: eventual consistency, accept orphaned references
  4. Data duplication — some data replicated to avoid cross-service calls

Q14. How do microservices handle security?
================================================================================

→ See 03_Resilience_and_Security_Questions.txt for full depth.

Summary:
  External auth: OAuth2 + JWT. API Gateway validates token.
  Service-to-service: mTLS (mutual certificate auth) + JWT propagation.
  Service mesh: Istio PeerAuthentication enforces mTLS automatically.
  Secrets: HashiCorp Vault or K8s Secrets (encrypted at rest + restricted RBAC).
  Defense in depth: auth at multiple layers (gateway + service level).

Q15. When would you NOT use microservices?
================================================================================

ANSWER:
Microservices are NOT always the right choice.

DON'T use microservices when:
  - Small team (< 5 engineers) — overhead kills productivity
  - Early-stage startup — requirements change rapidly, service boundaries wrong
  - Simple domain — few bounded contexts, low complexity
  - Tight budget — operational costs (K8s, multiple DBs, monitoring) are high
  - Team lacks distributed systems expertise — operational risk
  - System doesn't need independent scaling — all components scale together

Start with modular monolith:
  - Clear module boundaries (future service boundaries)
  - Separate packages per domain
  - Interfaces between modules
  - Single DB with schema separation

Extract services when:
  - Independent scaling needed for specific components
  - Teams need to deploy independently
  - Technology diversity required
  - Specific component has different reliability requirements

"I'd start with a modular monolith and extract services when specific scaling
or team autonomy needs justify the distributed systems overhead."
