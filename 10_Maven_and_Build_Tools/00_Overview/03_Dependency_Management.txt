WHAT IS DEPENDENCY MANAGEMENT?
───────────────────────────────
In the Java ecosystem, virtually every project depends on third-party libraries
(Spring, Hibernate, Jackson, Lombok, etc.). Dependency management is the process
of:
  • Declaring what libraries your project needs
  • Specifying which versions to use
  • Resolving transitive dependencies automatically
  • Handling version conflicts
  • Making dependencies available on the correct classpath

Without a build tool, developers download JARs manually, manage versions in
spreadsheets, and deal with "JAR hell" — the nightmare of conflicting library
versions. Maven and Gradle solve all this.

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY COORDINATES (GAV)
─────────────────────────────────────────────────────────────────────────────────

  Every Maven artifact is uniquely identified by three coordinates:

  <groupId>     — Organisation or project namespace (e.g., org.springframework)
  <artifactId>  — Library name (e.g., spring-core)
  <version>     — Version string (e.g., 6.1.2)

  Combined as: groupId:artifactId:version  →  org.springframework:spring-core:6.1.2

  Optional additional coordinates:
  <type>        — Artifact type (jar, war, pom, etc.) — default: jar
  <classifier>  — Additional qualifier (e.g., sources, javadoc, tests)
  <scope>       — When this dependency is available (see below)

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY SCOPES
─────────────────────────────────────────────────────────────────────────────────

  Scope         Compile  Test  Runtime  Transitive  Use case
  ──────────────────────────────────────────────────────────────────────────────
  compile       ✔       ✔    ✔        ✔           Default. Available everywhere.
  provided      ✔       ✔    ✗        ✗           Provided by container (e.g.,
                                                    servlet-api in a WAR project —
                                                    Tomcat provides it at runtime)
  runtime       ✗       ✔    ✔        ✔           Not needed to compile, needed
                                                    at runtime (e.g., JDBC driver)
  test          ✗       ✔    ✗        ✗           Only for tests (JUnit, Mockito)
  system        ✔       ✔    ✗        ✗           Local JAR, not from repo
                                                    (avoid — not portable)
  import        N/A          N/A                   Used in <dependencyManagement>
                                                    to import a BOM (pom type only)

  Examples:
  <dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided</scope>   <!-- Tomcat provides this; don't bundle it -->
  </dependency>

  <dependency>
    <groupId>mysql</groupId>
    <artifactId>mysql-connector-java</artifactId>
    <version>8.0.33</version>
    <scope>runtime</scope>   <!-- JDBC driver: not needed to compile, needed to run -->
  </dependency>

  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.0</version>
    <scope>test</scope>       <!-- Only for tests -->
  </dependency>

─────────────────────────────────────────────────────────────────────────────────
REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

  1. Local Repository (~/.m2/repository)
     ─────────────────────────────────────
     • Cached on each developer's machine
     • Maven checks here first before going to remote repos
     • Populated by "mvn install" and by downloading artifacts
     • Can become large — safe to delete and let Maven re-download

  2. Remote / Central Repository (https://repo.maven.apache.org/maven2)
     ────────────────────────────────────────────────────────────────────
     • The global public repository hosted by Apache Software Foundation
     • Contains millions of open-source artifacts
     • Free to use, read-only for the public
     • Accessed over HTTPS

  3. Corporate/Private Repository (Nexus, Artifactory)
     ─────────────────────────────────────────────────
     • Self-hosted artifact storage for proprietary libraries
     • Acts as a proxy/mirror for Maven Central (caches downloads)
     • Stores internally developed artifacts
     • Enables access control and vulnerability scanning

  Resolution Order:
  Local cache → defined repositories in pom.xml → central (default)

  Declaring a custom repository in pom.xml:
  <repositories>
    <repository>
      <id>company-nexus</id>
      <url>https://nexus.company.com/repository/maven-public/</url>
    </repository>
  </repositories>

─────────────────────────────────────────────────────────────────────────────────
TRANSITIVE DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  When you declare:
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <version>3.2.0</version>
  </dependency>

  Maven downloads spring-boot-starter-web AND all of its dependencies:
  spring-boot-starter-web
  ├── spring-boot-starter (core Spring Boot)
  │   ├── spring-boot
  │   ├── spring-core
  │   └── ...
  ├── spring-webmvc
  ├── jackson-databind
  ├── tomcat-embed-core
  └── ...

  This is called the transitive dependency graph. Maven resolves it automatically
  by reading each artifact's POM and following their dependencies recursively.

  Problem: Two different paths in the tree can pull in the same library at
  different versions → DEPENDENCY CONFLICT

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY CONFLICT RESOLUTION
─────────────────────────────────────────────────────────────────────────────────

  Maven uses "nearest definition wins":
  ─────────────────────────────────────
  • The version declared closest to the project root in the dependency tree wins
  • If two paths are equal depth, the first declaration in pom.xml wins

  Example:
  Your project → library-A → commons-lang3:3.10
  Your project → library-B → commons-lang3:3.12

  Both are depth 2. library-A is declared first → 3.10 is used.
  But you probably want 3.12! Fix by explicitly declaring:

  <dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>3.12.0</version>  <!-- Direct declaration always wins -->
  </dependency>

  Gradle uses "highest version wins" by default (usually safer behavior).

─────────────────────────────────────────────────────────────────────────────────
EXCLUDING TRANSITIVE DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  Sometimes a transitive dependency causes conflicts or should not be included:

  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-logging</artifactId>
    <exclusions>
      <exclusion>
        <groupId>org.apache.logging.log4j</groupId>
        <artifactId>log4j-to-slf4j</artifactId>   <!-- Remove this transitive dep -->
      </exclusion>
    </exclusions>
  </dependency>

  Common use case: Excluding Logback when using Log4j2, or excluding a vulnerable
  transitive dependency while waiting for the parent library to upgrade.

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT vs RELEASE VERSIONS
─────────────────────────────────────────────────────────────────────────────────

  SNAPSHOT (e.g., 1.0.0-SNAPSHOT):
  • A development/work-in-progress version
  • Maven may download a newer SNAPSHOT on every build (timestamps)
  • Should NEVER be used in production dependencies
  • Can be published to a snapshot repository (separate from release repo)
  • Useful for developing multiple interdependent modules simultaneously

  RELEASE (e.g., 1.0.0 or 1.0.0.RELEASE):
  • An immutable, stable version
  • Once deployed, can never be overwritten (enforced by repos)
  • What you should depend on in production code

  mvn versions:display-dependency-updates  → Find available newer versions

─────────────────────────────────────────────────────────────────────────────────
BILL OF MATERIALS (BOM)
─────────────────────────────────────────────────────────────────────────────────

  A BOM is a special POM that defines a set of dependency versions that are
  known to work together. Instead of specifying every version yourself, you
  import a BOM and get curated, compatible versions.

  Example — importing Spring Boot BOM:
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.2.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  Now you can declare Spring dependencies WITHOUT versions:
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>  <!-- no version needed! -->
  </dependency>

  Popular BOMs:
  • spring-boot-dependencies         — all Spring Boot managed versions
  • spring-cloud-dependencies        — Spring Cloud versions
  • io.quarkus:quarkus-bom            — Quarkus ecosystem
  • com.azure:azure-sdk-bom           — Azure SDK
  • software.amazon.awssdk:bom        — AWS SDK v2

─────────────────────────────────────────────────────────────────────────────────
USEFUL DEPENDENCY COMMANDS
─────────────────────────────────────────────────────────────────────────────────

  mvn dependency:tree
      Show the full transitive dependency tree

  mvn dependency:tree -Dverbose
      Show the full tree including omitted/conflicted versions

  mvn dependency:tree -Dincludes=org.apache.logging.log4j
      Filter tree to show only a specific groupId

  mvn dependency:analyze
      Identify: (1) used but undeclared deps, (2) declared but unused deps

  mvn dependency:resolve
      List all resolved dependencies and their versions

  mvn dependency:copy-dependencies -DoutputDirectory=libs
      Copy all dependency JARs to a directory

  mvn versions:display-dependency-updates
      Show which dependencies have newer versions available

  mvn versions:use-latest-releases
      Automatically update POM to latest release versions

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What are the Maven dependency scopes?
A: compile (default, available everywhere), provided (compile-time only, provided
   by runtime container), runtime (not needed to compile, needed at runtime),
   test (only in test classpath), system (explicit local JAR path — avoid),
   import (only in dependencyManagement, for BOMs).

Q: How does Maven resolve dependency version conflicts?
A: Maven uses "nearest wins" — the version of a library closest to the root of
   the dependency tree is selected. If two paths are equal, the first declaration
   wins. You can force a specific version by explicitly declaring it in the POM.

Q: What is a transitive dependency?
A: A dependency of a dependency. If your project depends on library A, and A
   depends on library B, then B is a transitive dependency of your project.
   Maven resolves and downloads the entire graph automatically.

Q: What is a BOM?
A: A Bill of Materials is a POM file (with <packaging>pom</packaging>) that
   manages a curated set of compatible dependency versions. Importing a BOM via
   <scope>import</scope> in <dependencyManagement> lets you use dependencies
   from that ecosystem without specifying versions.

Q: What is the difference between SNAPSHOT and RELEASE versions?
A: SNAPSHOT versions end in "-SNAPSHOT" and are mutable — the same version can
   point to different artifacts as development progresses. RELEASE versions are
   immutable — once published, they cannot change. Production code should only
   depend on RELEASE versions.

Q: How do you exclude a transitive dependency?
A: Use the <exclusions> element inside the <dependency> block to exclude specific
   transitive artifacts by groupId and artifactId.
