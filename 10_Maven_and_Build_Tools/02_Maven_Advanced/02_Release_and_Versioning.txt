================================================================================
  MAVEN RELEASE PROCESS AND VERSIONING
================================================================================

SEMANTIC VERSIONING (SemVer)
─────────────────────────────
Maven projects typically follow Semantic Versioning: MAJOR.MINOR.PATCH

  MAJOR: Breaking changes (API incompatible changes)
  MINOR: New features (backward-compatible)
  PATCH: Bug fixes (backward-compatible)

  Examples:
  1.0.0         → Initial stable release
  1.1.0         → New feature, backward-compatible
  1.1.1         → Bug fix release
  2.0.0         → Breaking change (API rewrite, major framework upgrade)
  1.0.0-SNAPSHOT → Development version of 1.0.0 (before release)
  1.0.0-RC1     → Release Candidate 1
  1.0.0-alpha   → Alpha pre-release
  1.0.0-beta.2  → Beta pre-release

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT vs RELEASE VERSIONS
─────────────────────────────────────────────────────────────────────────────────

  SNAPSHOT (e.g., 1.2.0-SNAPSHOT):
  ─────────────────────────────────
  • Indicates work-in-progress
  • Maven can download a NEWER snapshot even if one is cached (mutable)
  • Stored in snapshot repositories
  • Should NOT be used as a dependency in release artifacts
  • Timestamped on deployment: 1.2.0-20240108.143022-1 (internal, unique)
  • The "-SNAPSHOT" suffix is special — Maven treats it differently from a release

  RELEASE (e.g., 1.2.0):
  ────────────────────────
  • Immutable — once deployed, cannot be changed
  • What your CI/CD deploys to production
  • Must NOT depend on SNAPSHOT versions (enforced by maven-enforcer-plugin)

─────────────────────────────────────────────────────────────────────────────────
THE MAVEN RELEASE PLUGIN
─────────────────────────────────────────────────────────────────────────────────

  The maven-release-plugin automates the release process:
  1. Verifies no uncommitted changes
  2. Runs tests
  3. Removes -SNAPSHOT suffix from version
  4. Commits the release POM to SCM
  5. Tags the commit in SCM (e.g., my-app-1.2.0)
  6. Builds and deploys the release artifact to the remote repository
  7. Increments version to the next SNAPSHOT (e.g., 1.3.0-SNAPSHOT)
  8. Commits the new SNAPSHOT version to SCM

  Configuration:
  ──────────────
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-release-plugin</artifactId>
    <version>3.0.1</version>
    <configuration>
      <tagNameFormat>v@{project.version}</tagNameFormat>   <!-- v1.2.0 -->
      <autoVersionSubmodules>true</autoVersionSubmodules>  <!-- Multi-module: same version -->
      <releaseProfiles>production</releaseProfiles>        <!-- Activate profile on release -->
      <goals>deploy</goals>                                <!-- Goal to run for the release -->
      <preparationGoals>clean verify</preparationGoals>    <!-- Before release: verify passes -->
    </configuration>
  </plugin>

  Also requires SCM info:
  <scm>
    <connection>scm:git:https://github.com/example/my-app.git</connection>
    <developerConnection>scm:git:https://github.com/example/my-app.git</developerConnection>
    <url>https://github.com/example/my-app</url>
  </scm>

  Two-step release process:
  ──────────────────────────
  # Step 1: Prepare — update version, tag, commit
  mvn release:prepare

  # Step 2: Perform — checkout tagged version, build, deploy
  mvn release:perform

  # Rollback if something goes wrong during prepare:
  mvn release:rollback

  # Clean up leftover release files:
  mvn release:clean

  Non-interactive (for CI/CD):
  mvn release:prepare -B -DskipTests -Dtag=v1.2.0 \
    -DreleaseVersion=1.2.0 -DdevelopmentVersion=1.3.0-SNAPSHOT
  mvn release:perform -B

─────────────────────────────────────────────────────────────────────────────────
VERSIONS MAVEN PLUGIN — MANAGING VERSIONS
─────────────────────────────────────────────────────────────────────────────────

  A more flexible alternative for version management:

  # Show what dependency updates are available:
  mvn versions:display-dependency-updates

  # Show what plugin updates are available:
  mvn versions:display-plugin-updates

  # Update all dependencies to latest release:
  mvn versions:use-latest-releases

  # Update all dependencies to latest (including minor/major):
  mvn versions:use-latest-versions

  # Update to latest within the same major version:
  mvn versions:use-latest-releases -DallowMajorUpdates=false

  # Set project version (all modules):
  mvn versions:set -DnewVersion=2.0.0

  # Commit changes (remove backup pom.xml.versionsBackup files):
  mvn versions:commit

  # Revert if not satisfied:
  mvn versions:revert

CI-FRIENDLY VERSIONING (Maven 3.5+)
─────────────────────────────────────────────────────────────────────────────────

  Problem: Traditional versioning requires editing pom.xml for every release,
  creating merge conflicts in multi-module projects.

  Solution: Use ${revision} (and optionally ${sha1} and ${changelist}) as version:

  Root pom.xml:
  <version>${revision}</version>
  <properties>
    <revision>1.0.0-SNAPSHOT</revision>
  </properties>

  Each child pom.xml:
  <parent>
    <version>${revision}</version>
  </parent>
  <version>${revision}</version>

  CI/CD usage:
  # Build a snapshot:
  ./mvnw clean verify                                      → 1.0.0-SNAPSHOT

  # Build a release version (pass from CI):
  ./mvnw clean deploy -Drevision=1.2.0                    → 1.2.0

  # Build with Git SHA:
  ./mvnw clean deploy -Drevision=1.2.0-${GIT_COMMIT:0:7}  → 1.2.0-a3f5c2b

  IMPORTANT: You MUST use the flatten-maven-plugin to resolve ${revision}
  before deploying, otherwise consumers of your artifact won't see the
  actual version — they'll see "${revision}" literally.

  <plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>flatten-maven-plugin</artifactId>
    <version>1.5.0</version>
    <configuration>
      <updatePomFile>true</updatePomFile>
      <flattenMode>resolveCiFriendliesOnly</flattenMode>
    </configuration>
    <executions>
      <execution>
        <id>flatten</id>
        <phase>process-resources</phase>
        <goals><goal>flatten</goal></goals>
      </execution>
      <execution>
        <id>flatten.clean</id>
        <phase>clean</phase>
        <goals><goal>clean</goal></goals>
      </execution>
    </executions>
  </plugin>

─────────────────────────────────────────────────────────────────────────────────
CHANGELISTS — COMBINING BASE + QUALIFIER
─────────────────────────────────────────────────────────────────────────────────

  Using ${revision} + ${changelist}:

  <version>${revision}${changelist}</version>
  <properties>
    <revision>1.0.0</revision>
    <changelist>-SNAPSHOT</changelist>
  </properties>

  # Release build (overrides changelist to empty):
  mvn deploy -Dchangelist=

  # This produces: 1.0.0 (no SNAPSHOT suffix)
  # Default build produces: 1.0.0-SNAPSHOT

RELEASE WORKFLOW IN MODERN CI/CD (without release plugin)
─────────────────────────────────────────────────────────────────────────────────

  Many teams use a simpler CI/CD-driven approach instead of maven-release-plugin:

  1. Feature development: version = 1.2.0-SNAPSHOT
  2. CI builds snapshots on every commit to main
  3. When ready to release, CI/CD:
     a. Sets version: mvn versions:set -DnewVersion=1.2.0
     b. Commits pom.xml with version 1.2.0
     c. Tags git commit: git tag v1.2.0
     d. Builds and deploys: mvn clean deploy
     e. Sets next SNAPSHOT: mvn versions:set -DnewVersion=1.3.0-SNAPSHOT
     f. Commits next SNAPSHOT version
  4. Push tags and commits

  OR with CI-friendly versioning:
  # Compute version from git tag in CI:
  VERSION=$(git describe --tags --match "v*" | sed 's/^v//')
  ./mvnw clean deploy -Drevision=$VERSION -Dchangelist=

─────────────────────────────────────────────────────────────────────────────────
ENFORCING RELEASE QUALITY
─────────────────────────────────────────────────────────────────────────────────

  Always use the enforcer plugin to prevent releasing with SNAPSHOT deps:

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <executions>
      <execution>
        <id>no-snapshot-deps</id>
        <phase>verify</phase>
        <goals><goal>enforce</goal></goals>
        <configuration>
          <rules>
            <requireReleaseDeps>
              <onlyWhenRelease>true</onlyWhenRelease>  <!-- Only check in release builds -->
              <message>Release builds cannot have SNAPSHOT dependencies!</message>
            </requireReleaseDeps>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What does the maven-release-plugin do?
A: It automates the full release workflow: verifies no uncommitted changes,
   removes the -SNAPSHOT suffix, runs tests, tags the commit in SCM, deploys
   the release artifact to the remote repository, then bumps the version to the
   next SNAPSHOT and commits. Two commands: release:prepare and release:perform.

Q: What is the difference between release:prepare and release:perform?
A: release:prepare: Validates the project, removes -SNAPSHOT, commits, tags the
   VCS, and bumps to next SNAPSHOT. It creates release.properties with the state.
   release:perform: Checks out the tagged version and runs the actual build + deploy.

Q: What is CI-friendly versioning?
A: Using ${revision} as the version in pom.xml and passing the actual version
   value via -Drevision=1.2.0 at build time. This avoids editing pom.xml for
   each release and works well with CI/CD pipelines that compute versions from
   git tags. Requires flatten-maven-plugin for correct POM publishing.

Q: Why can't a release artifact depend on a SNAPSHOT?
A: SNAPSHOT versions are mutable — the same SNAPSHOT version can point to
   different artifacts over time. This makes release builds non-reproducible.
   If a release depends on 1.0.0-SNAPSHOT of library X, nobody can reproduce
   that exact build in the future. Use the maven-enforcer-plugin to enforce this.

Q: How do you update all dependency versions in a pom.xml at once?
A: Use the versions-maven-plugin:
   mvn versions:display-dependency-updates  → shows what's available
   mvn versions:use-latest-releases         → updates pom.xml
   mvn versions:commit                      → removes backup files
