================================================================================
  NEXUS REPOSITORY MANAGER AND ARTIFACTORY
================================================================================

WHAT ARE THEY?
──────────────
Nexus Repository Manager (Sonatype) and Artifactory (JFrog) are enterprise-grade
artifact repository managers. They act as a hub for all binary artifacts in your
organization.

Primary functions:
  1. HOST: Store and serve your own internally-built artifacts
  2. PROXY: Cache artifacts from Maven Central and other public repos
  3. GROUP: Aggregate multiple repositories into one URL

─────────────────────────────────────────────────────────────────────────────────
NEXUS vs ARTIFACTORY
─────────────────────────────────────────────────────────────────────────────────

  Feature               Nexus OSS (Free)        Artifactory OSS (Free)
  ──────────────────── ──────────────────────── ──────────────────────────────
  Maven support         ✔ Full                   ✔ Full
  npm, PyPI, Docker     ✔ (some in Pro)          ✔ (more in Pro/SaaS)
  Helm charts           Pro only                 Free (limited)
  UI                    Good                     Better, more polished
  REST API              ✔                        ✔ (richer)
  Build integration     Good                     Excellent (Artifactory plugin)
  Cloud (SaaS)          Sonatype Nexus IQ        JFrog Platform Cloud
  License               Apache 2.0 (OSS)         LGPL (OSS)
  Enterprise features   Nexus Pro/IQ             Artifactory Pro/Enterprise
  CVE scanning          Nexus IQ (separate tool) Xray (integrated)

  In practice:
  • Nexus is most common in traditional enterprise Java shops
  • Artifactory is preferred in DevOps-heavy, polyglot, or cloud-native orgs
  • Both are functionally equivalent for basic Maven use cases

─────────────────────────────────────────────────────────────────────────────────
NEXUS REPOSITORY TYPES
─────────────────────────────────────────────────────────────────────────────────

  1. HOSTED Repository
  ─────────────────────
  Stores artifacts you create and publish. Two subtypes:
  • Release repository: For stable release versions (1.0.0, 2.3.1)
    - Redeploy policy: "Disable redeploy" (immutable)
  • Snapshot repository: For SNAPSHOT versions (1.0.0-SNAPSHOT)
    - Redeploy policy: "Allow redeploy" (mutable)

  2. PROXY Repository
  ────────────────────
  Caches artifacts from a remote repository:
  • maven-central proxy → caches from https://repo.maven.apache.org/maven2/
  • spring-milestones proxy → caches from https://repo.spring.io/milestone/
  • First request goes to remote; subsequent requests served from Nexus cache

  3. GROUP Repository
  ─────────────────────
  Aggregates multiple hosted and proxy repos into one URL:
  • maven-public group = maven-releases + maven-snapshots + maven-central-proxy
  • Developers use ONE URL: https://nexus.company.com/repository/maven-public/

  Typical Nexus setup:
  ─────────────────────────────────────────────────────────────────────────────
  maven-public (GROUP)
  ├── company-releases (HOSTED)      ← Your release artifacts
  ├── company-snapshots (HOSTED)     ← Your snapshot artifacts
  ├── maven-central (PROXY)          ← Cached Maven Central
  ├── spring-milestones (PROXY)      ← Cached Spring Milestones
  └── confluent (PROXY)              ← Cached Confluent Kafka packages

─────────────────────────────────────────────────────────────────────────────────
CONFIGURING MAVEN TO USE NEXUS
─────────────────────────────────────────────────────────────────────────────────

  ~/.m2/settings.xml:
  ────────────────────
  <settings>
    <!-- Route all traffic through Nexus -->
    <mirrors>
      <mirror>
        <id>nexus</id>
        <url>https://nexus.company.com/repository/maven-public/</url>
        <mirrorOf>*</mirrorOf>
      </mirror>
    </mirrors>

    <!-- Credentials for deploying to Nexus -->
    <servers>
      <server>
        <id>company-releases</id>
        <username>deploy</username>
        <password>{encrypted-password}</password>
      </server>
      <server>
        <id>company-snapshots</id>
        <username>deploy</username>
        <password>{encrypted-password}</password>
      </server>
    </servers>
  </settings>

  pom.xml — distributionManagement:
  ────────────────────────────────────
  <distributionManagement>
    <repository>
      <id>company-releases</id>      <!-- Must match server <id> in settings.xml -->
      <url>https://nexus.company.com/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
      <id>company-snapshots</id>     <!-- Must match server <id> in settings.xml -->
      <url>https://nexus.company.com/repository/maven-snapshots/</url>
    </snapshotRepository>
  </distributionManagement>

  Deploy command:
  ./mvnw clean deploy                   # Deploys SNAPSHOT or RELEASE based on version

─────────────────────────────────────────────────────────────────────────────────
DEPLOYING AN ARTIFACT MANUALLY
─────────────────────────────────────────────────────────────────────────────────

  # Deploy a JAR file that doesn't have a Maven POM (e.g., Oracle JDBC driver):
  mvn deploy:deploy-file \
    -DgroupId=com.oracle \
    -DartifactId=ojdbc8 \
    -Dversion=19.3.0 \
    -Dpackaging=jar \
    -Dfile=ojdbc8.jar \
    -DrepositoryId=company-releases \
    -Durl=https://nexus.company.com/repository/maven-releases/

  # Install to local repo without deploying:
  mvn install:install-file \
    -DgroupId=com.oracle \
    -DartifactId=ojdbc8 \
    -Dversion=19.3.0 \
    -Dpackaging=jar \
    -Dfile=ojdbc8.jar

─────────────────────────────────────────────────────────────────────────────────
ARTIFACT CLEANUP POLICIES
─────────────────────────────────────────────────────────────────────────────────

  Nexus supports cleanup policies to manage disk space:

  1. Snapshot cleanup: Delete SNAPSHOT versions older than N days
     • Common: remove snapshots older than 30 days
     • Keep the last N versions of each artifact

  2. Release cleanup: Be careful — releases should generally be kept forever
     • Some orgs keep 90 days or last 10 versions

  3. Proxy cleanup: Remove unused cached artifacts
     • Items not accessed in 90 days

  Configure in: Nexus UI → Repository → Cleanup Policies → Assign to Repos

─────────────────────────────────────────────────────────────────────────────────
SECURITY AND ACCESS CONTROL
─────────────────────────────────────────────────────────────────────────────────

  Nexus security model:
  • Privileges: Fine-grained (read, update, delete per repo)
  • Roles: Groups of privileges (deploy-role, readonly-role)
  • Users: Assigned to roles (developer, ci-user, admin)

  Common roles:
  ─────────────────────────────────────────────────────────────────────────────
  Role             Privileges
  ──────────────── ──────────────────────────────────────────────────────────
  developer        Read all repos, deploy to company-snapshots only
  ci-deploy-user   Read all repos, deploy to both release and snapshot repos
  admin            Full access
  readonly         Read all repos (for external partners)

  Best practices:
  ✔ CI/CD uses a dedicated service account with deploy rights
  ✔ Developers have read-only to release repos, write to snapshots
  ✔ Production systems have read-only access
  ✔ Use LDAP/SSO integration for large teams (Nexus Pro)
  ✔ Enable "Disable anonymous access" in production

─────────────────────────────────────────────────────────────────────────────────
NEXUS IQ / SONATYPE LIFECYCLE — CVE SCANNING
─────────────────────────────────────────────────────────────────────────────────

  Nexus IQ (now "Sonatype Lifecycle") scans artifacts for known CVEs and
  policy violations. Integrates with:
  • Maven build: sonatype-clm-maven-plugin
  • Nexus Repository: automatic scanning on upload
  • IDE: SonarLint-like plugins
  • CI/CD: scan before deploy, fail on critical CVEs

  Maven plugin:
  <plugin>
    <groupId>com.sonatype.clm</groupId>
    <artifactId>clm-maven-plugin</artifactId>
    <version>2.34.0-01</version>
    <configuration>
      <serverUrl>https://iq.company.com/</serverUrl>
      <applicationId>my-app</applicationId>
    </configuration>
  </plugin>

  mvn clm:evaluate   # Run CVE analysis
  mvn clm:index      # Index artifacts

ARTIFACTORY SPECIFICS
─────────────────────────────────────────────────────────────────────────────────

  Key differences from Nexus:
  • Build info: Artifactory captures complete build metadata (Git commit, env vars,
    all artifacts produced, all deps used) — full traceability
  • Virtual repositories (Artifactory) ≈ Group repositories (Nexus)
  • Local repositories (Artifactory) ≈ Hosted repositories (Nexus)
  • Remote repositories (Artifactory) ≈ Proxy repositories (Nexus)

  Artifactory REST API (very powerful):
  # Search for an artifact:
  curl https://artifactory.company.com/artifactory/api/search/quick?name=my-app.jar

  # Download artifact:
  curl -u user:pass https://artifactory.company.com/artifactory/libs-release/com/example/my-app/1.0.0/my-app-1.0.0.jar

  Artifactory Maven configuration:
  <distributionManagement>
    <repository>
      <id>central</id>
      <name>Artifactory Releases</name>
      <url>https://artifactory.company.com/artifactory/libs-release</url>
    </repository>
    <snapshotRepository>
      <id>snapshots</id>
      <name>Artifactory Snapshots</name>
      <url>https://artifactory.company.com/artifactory/libs-snapshot</url>
    </snapshotRepository>
  </distributionManagement>

PUBLISHING TO MAVEN CENTRAL (OSS SONATYPE)
─────────────────────────────────────────────────────────────────────────────────

  For open-source projects that want to publish to Maven Central:

  1. Register at https://central.sonatype.com/ (or https://issues.sonatype.org/ for legacy)
  2. Add required metadata to pom.xml:
     - <name>, <description>, <url>, <licenses>, <developers>, <scm>
  3. Sign artifacts with GPG: maven-gpg-plugin
  4. Deploy to staging OSSRH repository
  5. Close and release the staging repository

  Maven Central publishing plugin (Central Publisher Portal — new approach):
  <plugin>
    <groupId>org.sonatype.central</groupId>
    <artifactId>central-publishing-maven-plugin</artifactId>
    <version>0.4.0</version>
    <extensions>true</extensions>
    <configuration>
      <publishingServerId>central</publishingServerId>
      <tokenAuth>true</tokenAuth>
    </configuration>
  </plugin>

  GPG signing plugin:
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-gpg-plugin</artifactId>
    <version>3.1.0</version>
    <executions>
      <execution>
        <id>sign-artifacts</id>
        <phase>verify</phase>
        <goals><goal>sign</goal></goals>
      </execution>
    </executions>
  </plugin>

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is Nexus and why would you use it?
A: Nexus Repository Manager is an artifact repository server. You'd use it to:
   (1) store and serve your own internally-built artifacts, (2) proxy and cache
   public repositories like Maven Central (saves bandwidth, enables air-gapped builds),
   (3) provide a single repository URL for all developers, and (4) enforce security
   policies and CVE scanning on all dependencies.

Q: What is the difference between hosted, proxy, and group repositories in Nexus?
A: Hosted repos store your own artifacts. Proxy repos cache artifacts from external
   repos (Maven Central, Spring Milestones). Group repos aggregate multiple repos
   under one URL, so developers only need one configuration.

Q: How does Maven authenticate to Nexus when deploying?
A: Via <server> entries in ~/.m2/settings.xml. The <server><id> must exactly match
   the <repository><id> (or <snapshotRepository><id>) in the pom.xml's
   <distributionManagement>. Maven looks up credentials from settings.xml by ID.

Q: What is a proxy repository and why is it useful?
A: A proxy repository passes requests to a remote repository and caches the
   responses. Benefits: (1) faster downloads (local network vs internet),
   (2) works even if remote is down (cached artifacts available),
   (3) enables air-gapped environments, (4) all downloads are logged and scanned.

Q: What is the difference between Nexus and Maven Central?
A: Maven Central is the global public repository for open-source Java artifacts.
   Nexus is a private, self-hosted repository server. Typically, Nexus proxies
   Maven Central (caches it), plus hosts your private/proprietary artifacts.
