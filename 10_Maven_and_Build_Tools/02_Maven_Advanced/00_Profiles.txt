  MAVEN PROFILES
================================================================================

WHAT ARE MAVEN PROFILES?
─────────────────────────
Maven Profiles allow you to customize build configuration for different
environments or scenarios. A profile can override or augment almost any POM
element: properties, dependencies, plugins, repositories, and more.

Use profiles for:
  • Environment-specific configs (dev, staging, prod)
  • OS-specific builds (Windows vs Linux JNI libraries)
  • CI/CD-specific behavior
  • Optional feature flags
  • Integration vs unit test separation

─────────────────────────────────────────────────────────────────────────────────
WHERE PROFILES ARE DEFINED
─────────────────────────────────────────────────────────────────────────────────

  1. pom.xml               → Project-specific, committed to source control
  2. ~/.m2/settings.xml    → User-specific, personal credentials/configs
  3. ${M2_HOME}/conf/settings.xml  → Global Maven installation (all users)
  4. profiles.xml (deprecated)     → No longer supported in Maven 3

  Profiles in pom.xml are the most common. Settings.xml profiles are useful for
  environment-level things like repository credentials or proxy settings.

─────────────────────────────────────────────────────────────────────────────────
BASIC PROFILE STRUCTURE
─────────────────────────────────────────────────────────────────────────────────

  <profiles>
    <profile>
      <id>production</id>            <!-- Unique identifier for this profile -->

      <!-- ACTIVATION: when should this profile be active? -->
      <activation>
        <!-- ... (see activation section below) ... -->
      </activation>

      <!-- OVERRIDE/AUGMENT any POM section: -->
      <properties>
        <spring.profiles.active>prod</spring.profiles.active>
        <log.level>WARN</log.level>
      </properties>

      <dependencies>
        <dependency>
          <groupId>com.oracle</groupId>
          <artifactId>ojdbc8</artifactId>
          <version>19.3.0</version>
          <scope>runtime</scope>
        </dependency>
      </dependencies>

      <build>
        <plugins>
          <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-shade-plugin</artifactId>
            <!-- ... -->
          </plugin>
        </plugins>
      </build>

    </profile>
  </profiles>

─────────────────────────────────────────────────────────────────────────────────
PROFILE ACTIVATION MECHANISMS
─────────────────────────────────────────────────────────────────────────────────

  1. COMMAND-LINE ACTIVATION (most common and explicit)
  ──────────────────────────────────────────────────────
  mvn clean package -Pproduction          # Activate by profile ID
  mvn clean package -Pproduction,metrics  # Activate multiple profiles
  mvn clean package -P!development        # Deactivate a profile

  2. PROPERTY-BASED ACTIVATION
  ─────────────────────────────
  <activation>
    <property>
      <name>env</name>
      <value>prod</value>          <!-- Active when -Denv=prod -->
    </property>
  </activation>

  mvn clean package -Denv=prod           # Activates this profile

  Alternatively, activate when a property is present (any value):
  <property>
    <name>performanceTests</name>        <!-- Active when -DperformanceTests -->
  </property>

  3. OS-BASED ACTIVATION
  ─────────────────────────
  <activation>
    <os>
      <name>Windows 10</name>
      <family>Windows</family>           <!-- windows, unix, mac -->
      <arch>x86_64</arch>
      <version>10.0</version>
    </os>
  </activation>

  Useful for: native library dependencies that differ by OS.

  4. FILE-BASED ACTIVATION
  ──────────────────────────
  <activation>
    <file>
      <exists>${basedir}/src/main/resources/prod.properties</exists>
      <!-- OR: missing (active when file is MISSING) -->
      <missing>${basedir}/local-dev.flag</missing>
    </file>
  </activation>

  5. JDK-BASED ACTIVATION
  ─────────────────────────
  <activation>
    <jdk>21</jdk>            <!-- Exact JDK 21 -->
    <!-- or range: -->
    <jdk>[17,)</jdk>          <!-- JDK 17 or higher -->
    <jdk>[11,17)</jdk>        <!-- JDK 11 up to (not including) 17 -->
  </activation>

  6. DEFAULT ACTIVATION
  ──────────────────────
  <activation>
    <activeByDefault>true</activeByDefault>   <!-- Always active unless another profile deactivates -->
  </activation>

  NOTE: If ANY other profile in the POM is explicitly activated (via -P or other
  conditions), activeByDefault profiles are automatically DEACTIVATED.
  Use this sparingly to avoid confusion.

─────────────────────────────────────────────────────────────────────────────────
PRACTICAL PROFILE EXAMPLES
─────────────────────────────────────────────────────────────────────────────────

  Example 1: Different Spring profiles per environment
  ──────────────────────────────────────────────────────
  <profiles>
    <profile>
      <id>dev</id>
      <activation><activeByDefault>true</activeByDefault></activation>
      <properties>
        <spring.profiles.active>dev</spring.profiles.active>
        <maven.test.skip>false</maven.test.skip>
      </properties>
    </profile>

    <profile>
      <id>staging</id>
      <properties>
        <spring.profiles.active>staging</spring.profiles.active>
      </properties>
    </profile>

    <profile>
      <id>prod</id>
      <properties>
        <spring.profiles.active>prod</spring.profiles.active>
      </properties>
      <build>
        <plugins>
          <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-enforcer-plugin</artifactId>
            <executions>
              <execution>
                <id>enforce-no-snapshots</id>
                <goals><goal>enforce</goal></goals>
                <configuration>
                  <rules>
                    <requireReleaseDeps/>
                  </rules>
                </configuration>
              </execution>
            </executions>
          </plugin>
        </plugins>
      </build>
    </profile>
  </profiles>

  Usage:
  mvn clean package          → dev profile (default)
  mvn clean package -Pstaging
  mvn clean package -Pprod

  Example 2: Integration tests profile
  ──────────────────────────────────────
  <profiles>
    <profile>
      <id>integration-tests</id>
      <build>
        <plugins>
          <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-failsafe-plugin</artifactId>
            <executions>
              <execution>
                <goals>
                  <goal>integration-test</goal>
                  <goal>verify</goal>
                </goals>
              </execution>
            </executions>
          </plugin>
        </plugins>
      </build>
    </profile>
  </profiles>

  mvn clean verify -Pintegration-tests

  Example 3: OS-specific native libraries
  ─────────────────────────────────────────
  <profiles>
    <profile>
      <id>linux-natives</id>
      <activation><os><family>unix</family></os></activation>
      <dependencies>
        <dependency>
          <groupId>io.netty</groupId>
          <artifactId>netty-transport-native-epoll</artifactId>
          <classifier>linux-x86_64</classifier>
        </dependency>
      </dependencies>
    </profile>

    <profile>
      <id>mac-natives</id>
      <activation><os><family>mac</family></os></activation>
      <dependencies>
        <dependency>
          <groupId>io.netty</groupId>
          <artifactId>netty-transport-native-kqueue</artifactId>
          <classifier>osx-x86_64</classifier>
        </dependency>
      </dependencies>
    </profile>
  </profiles>

─────────────────────────────────────────────────────────────────────────────────
LISTING AND DEBUGGING PROFILES
─────────────────────────────────────────────────────────────────────────────────

  # List all profiles and whether they are active:
  mvn help:active-profiles

  # Show active profiles for a specific activation:
  mvn help:active-profiles -Pproduction

  # Show the effective POM with a profile active:
  mvn help:effective-pom -Pproduction

  # Debug profile issues with verbose output:
  mvn clean package -X -Pproduction 2>&1 | grep -i profile

─────────────────────────────────────────────────────────────────────────────────
PROFILE BEST PRACTICES
─────────────────────────────────────────────────────────────────────────────────

  ✔ Use -P for explicit activation in CI/CD — never rely on activeByDefault in CI
  ✔ Keep profile names short and meaningful: dev, staging, prod, integration
  ✔ Don't put secrets in pom.xml profiles — use settings.xml or CI secrets
  ✔ Prefer Spring's own profile mechanism (spring.profiles.active) over Maven
    profiles for runtime config; Maven profiles are for BUILD-TIME config
  ✔ Use Maven profiles for: different dependencies per env, skip/include plugins,
    OS-specific builds, CI-specific behavior
  ✔ Avoid: profiles that fundamentally change what the build produces (different
    code paths per profile make reproducibility hard to verify)

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is a Maven profile and when would you use one?
A: A Maven profile is a set of configuration overrides that can be activated under
   certain conditions. Use them for environment-specific builds (dev/staging/prod),
   OS-specific native dependencies, optional plugin execution (integration tests),
   and CI/CD-specific settings. Profiles keep the default POM clean while allowing
   conditional customization.

Q: How do you activate a Maven profile?
A: Several ways:
   - Command-line: -Pprofile-id (most common)
   - System property: via <activation><property> in the profile
   - OS: via <activation><os>
   - File existence: via <activation><file>
   - JDK version: via <activation><jdk>
   - Default: via <activation><activeByDefault>true</activeByDefault>

Q: What is the pitfall of activeByDefault profiles?
A: If ANY other profile is explicitly activated (by -P, property, OS, or file),
   ALL activeByDefault profiles are automatically deactivated. This causes
   surprising behavior where your "default" profile silently stops applying.
   In CI/CD, always activate profiles explicitly with -P.

Q: Where can Maven profiles be defined?
A: In the project pom.xml, in the user's ~/.m2/settings.xml, and in the Maven
   installation's conf/settings.xml. POM profiles are project-scoped; settings.xml
   profiles are user/machine-scoped (good for credentials, proxies).

Q: What is the difference between Maven profiles and Spring profiles?
A: Maven profiles control BUILD-TIME behavior (which dependencies to include,
   which plugins to run, etc.). Spring profiles control RUNTIME behavior
   (which beans to create, which properties to load). They can be combined:
   a Maven profile can set spring.profiles.active as a property that Spring reads.
