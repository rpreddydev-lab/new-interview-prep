  GRADLE vs MAVEN — COMPREHENSIVE COMPARISON REFERENCE CARD

PHILOSOPHY
───────────
  Maven:   Convention over configuration. Opinionated standard lifecycle.
           Declarative XML — describes WHAT, not HOW.
  Gradle:  Programmatic build logic. Highly flexible. Convention + configuration.
           Imperative Groovy/Kotlin DSL — describes HOW with imperative code.

─────────────────────────────────────────────────────────────────────────────────
BUILD SCRIPT FORMAT
─────────────────────────────────────────────────────────────────────────────────

  Maven (pom.xml):
  ─────────────────
  <project>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <version>3.2.0</version>
      </dependency>
    </dependencies>
  </project>

  Gradle (build.gradle.kts):
  ───────────────────────────
  plugins {
      id("org.springframework.boot") version "3.2.0"
  }
  group = "com.example"; version = "1.0.0"
  dependencies {
      implementation("org.springframework.boot:spring-boot-starter-web")
  }

PERFORMANCE
─────────────────────────────────────────────────────────────────────────────────

  Feature                          Maven    Gradle
  ──────────────────────────────── ──────── ────────────────────────────────────
  Incremental compilation          ✅       ✅
  Incremental task execution       ❌       ✅ (task UP-TO-DATE)
  Parallel module build            ✅ -T    ✅ --parallel
  Build cache (local)              ❌       ✅ org.gradle.caching=true
  Build cache (remote)             ❌       ✅ (Develocity / custom)
  Configuration cache              ❌       ✅ (stores task graph)
  Daemon (warm JVM)                ❌ (poor) ✅ (robust, default on)
  File system watching             ❌       ✅ --watch-fs

  Real-world performance:
  • Gradle is typically 2x–10x faster than Maven for large incremental builds.
  • Maven is competitive on clean builds; Gradle wins on incremental builds
    due to build cache and task UP-TO-DATE tracking.

─────────────────────────────────────────────────────────────────────────────────
LIFECYCLE / BUILD MODEL
─────────────────────────────────────────────────────────────────────────────────

  Maven:
  • Fixed lifecycle: validate → compile → test → package → verify → install → deploy
  • Plugins bind goals to specific phases
  • Cannot easily add phases; must fit into existing lifecycle
  • Same set of phases regardless of project type (with some variation by packaging)

  Gradle:
  • No fixed lifecycle — tasks and their dependency graph define the build
  • Built-in lifecycle tasks: build, check, assemble (composites)
  • You can add any task anywhere in the graph
  • Task execution order determined by dependsOn/mustRunAfter/finalizedBy

DEPENDENCY MANAGEMENT
─────────────────────────────────────────────────────────────────────────────────

  Feature                  Maven                     Gradle
  ──────────────────────── ───────────────────────── ───────────────────────────
  Conflict resolution      Nearest-wins (closest     Highest-wins (highest
                           to root in dep tree)      version anywhere in graph)
  Scopes                   compile/test/provided/    implementation/api/
                           runtime/system/import     compileOnly/runtimeOnly/
                                                     testImplementation/etc.
  BOM import               import scope in depMgmt   platform() / enforcedPlatform()
  Version catalog          N/A (use BOM)             libs.versions.toml (built-in)
  Dependency locking       ❌ (third-party plugins)  ✅ (built-in)
  Dep verification (hash)  ❌                        ✅ verification-metadata.xml
  Bill of Materials        <dependencyManagement>    java-platform plugin
  Dependency constraints   ❌                        ✅ constraints {} block
  Exclude transitive dep   <exclusions>              exclude(group=, module=)
  Transitive scope matrix  Scope propagation table   Depends on api vs implementation

  Maven scope vs Gradle configuration mapping:
  ──────────────────────────────────────────────
  Maven compile   → Gradle api (if library) or implementation (if app)
  Maven provided  → Gradle compileOnly
  Maven runtime   → Gradle runtimeOnly
  Maven test      → Gradle testImplementation
  Maven import    → Gradle platform()

─────────────────────────────────────────────────────────────────────────────────
PLUGIN SYSTEM
─────────────────────────────────────────────────────────────────────────────────

  Maven:
  • Plugins discovered from Maven Central / plugin repositories
  • Declared in <build><plugins> or <pluginManagement>
  • Configured in <configuration> blocks
  • Plugin versions must be declared explicitly (best practice)
  • Strongly tied to lifecycle phases via goal bindings

  Gradle:
  • Plugins from Gradle Plugin Portal (plugins.gradle.org) or Maven repos
  • Declared in plugins {} block
  • Convention plugins via buildSrc or included builds
  • Can write plugins in Groovy, Kotlin, or Java
  • Plugins add tasks, configurations, extensions to the project

  Key difference: Gradle plugins can add new configurations, extend the DSL,
  and define custom task types. Maven plugins only bind goals to phases.

WHEN TO CHOOSE WHICH
─────────────────────────────────────────────────────────────────────────────────

  Choose MAVEN when:
  • Enterprise Java shops with established Maven conventions
  • Strong Spring Boot projects (spring-boot-starter-parent is Maven-native)
  • Need to publish to Maven Central (better tooling support)
  • Team prefers declarative, XML-based configs with no surprises
  • Build logic is standard and fits the lifecycle model

  Choose GRADLE when:
  • Performance is critical (Android REQUIRES Gradle)
  • Complex build logic (code generation, custom steps, DSL extensions)
  • Kotlin/Android development (Kotlin DSL is first-class)
  • Need incremental builds and build cache across teams
  • Polyglot projects (Java + Kotlin + C++ in one build)
  • Modern toolchain with version catalogs and convention plugins

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the biggest performance difference between Maven and Gradle?
A: Gradle has several performance advantages: (1) UP-TO-DATE checking skips tasks
   whose inputs/outputs haven't changed, (2) build cache stores task outputs and
   reuses them even after clean or on other machines, (3) configuration cache avoids
   re-evaluating the build script on every run, (4) the Gradle Daemon keeps the JVM
   warm. Maven has incremental compilation but no equivalent to Gradle's build cache.

Q: How does dependency conflict resolution differ between Maven and Gradle?
A: Maven uses "nearest-wins" — the dependency closest to the root of the dependency
   tree wins. Gradle uses "highest-wins" — the highest version requested anywhere
   in the graph wins. Gradle's approach generally makes more sense (you want the
   newest compatible version), but you can override with resolutionStrategy.force()
   or strictly() if needed.

Q: Can Gradle use Maven repositories and POMs?
A: Yes. Gradle fully understands Maven POMs, including BOM imports (via platform()),
   and resolves dependencies from Maven repositories (mavenCentral(), local Maven
   repos). The two tools are interoperable from a repository perspective — Gradle
   can consume anything Maven publishes and vice versa.

Q: What is the Gradle Build Scan?
A: Running ./gradlew build --scan generates a web link to a hosted report showing
   the full build timeline, task execution details, test results, dependency trees,
   and performance insights. It's free for public projects. The enterprise version
   (Develocity) allows storing scans on-premise and enabling remote build caches.
