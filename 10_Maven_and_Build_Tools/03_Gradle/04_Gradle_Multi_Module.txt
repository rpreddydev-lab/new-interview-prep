================================================================================
  GRADLE MULTI-MODULE PROJECTS
================================================================================

OVERVIEW
─────────
Multi-module (multi-project) builds let you split one codebase into multiple
subprojects with shared dependencies, coordinated builds, and cross-project
references. This mirrors Maven's multi-module reactor.

Typical structure:
  my-app/
  ├── settings.gradle.kts          ← declares all subprojects
  ├── build.gradle.kts             ← root (optional shared config)
  ├── gradle/
  │   ├── libs.versions.toml       ← version catalog (shared)
  │   └── wrapper/
  ├── api/
  │   └── build.gradle.kts
  ├── service/
  │   └── build.gradle.kts        ← depends on :api
  ├── persistence/
  │   └── build.gradle.kts        ← depends on :api
  └── web/
      └── build.gradle.kts        ← depends on :service, :persistence

─────────────────────────────────────────────────────────────────────────────────
SETTINGS FILE — settings.gradle.kts
─────────────────────────────────────────────────────────────────────────────────

  rootProject.name = "my-app"

  // Include subprojects by their directory name
  include(":api", ":service", ":persistence", ":web")

  // Nested subprojects
  include(":modules:payment", ":modules:notification")

  // Subproject in a non-default directory
  include(":legacy")
  project(":legacy").projectDir = file("legacy-code/legacy-module")

  // Version catalog
  dependencyResolutionManagement {
      repositories {
          mavenCentral()
      }
      versionCatalogs {
          create("libs") {
              from(files("gradle/libs.versions.toml"))
          }
      }
  }

─────────────────────────────────────────────────────────────────────────────────
ROOT BUILD SCRIPT — build.gradle.kts
─────────────────────────────────────────────────────────────────────────────────

  // Option 1: Only configure subprojects from root (no plugins applied to root)
  subprojects {
      apply(plugin = "java")

      repositories {
          mavenCentral()
      }

      dependencies {
          // Common test dependencies for all subprojects
          "testImplementation"("org.junit.jupiter:junit-jupiter")
          "testRuntimeOnly"("org.junit.platform:junit-platform-launcher")
      }

      tasks.withType<Test> {
          useJUnitPlatform()
      }

      java {
          toolchain {
              languageVersion.set(JavaLanguageVersion.of(21))
          }
      }
  }

  // allprojects — applies to root + all subprojects
  allprojects {
      group = "com.example"
      version = "1.0.0-SNAPSHOT"
  }

  // Targeting specific subprojects
  project(":web") {
      apply(plugin = "org.springframework.boot")
  }

─────────────────────────────────────────────────────────────────────────────────
SUBPROJECT BUILD SCRIPT
─────────────────────────────────────────────────────────────────────────────────

  // :service/build.gradle.kts
  plugins {
      `java-library`
  }

  dependencies {
      // Project dependency
      api(project(":api"))

      // External dependencies from version catalog
      implementation(libs.spring.context)
      implementation(libs.slf4j.api)

      testImplementation(libs.junit.jupiter)
  }

  // :web/build.gradle.kts
  plugins {
      id("org.springframework.boot")
      id("io.spring.dependency-management")
  }

  dependencies {
      implementation(project(":service"))
      implementation(project(":persistence"))
      implementation("org.springframework.boot:spring-boot-starter-web")
  }

─────────────────────────────────────────────────────────────────────────────────
PROJECT DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  // implementation — dependency's classes available at compile + runtime
  implementation(project(":api"))

  // api — exposes :api transitively to consumers of :service
  api(project(":api"))

  // testImplementation — for test code only
  testImplementation(project(":test-fixtures"))

  // Test fixtures support (Gradle 5.6+)
  // In :api/build.gradle.kts:
  plugins { `java-test-fixtures` }
  // Exposes src/testFixtures/java
  testFixtures(project(":api"))  // consume test fixtures in other projects

─────────────────────────────────────────────────────────────────────────────────
RUNNING TASKS IN MULTI-MODULE BUILDS
─────────────────────────────────────────────────────────────────────────────────

  ./gradlew build                    # Build all subprojects (in dependency order)
  ./gradlew :service:build           # Build only :service and its deps
  ./gradlew :web:test                # Run tests only in :web
  ./gradlew -p service build         # Equivalent using -p (project dir)
  ./gradlew build --parallel         # Build independent subprojects in parallel
  ./gradlew :web:dependencies        # Dependency tree for :web only

  Execution order is determined by the dependency graph, not declaration order.
  If :web depends on :service, Gradle builds :service first automatically.

─────────────────────────────────────────────────────────────────────────────────
CONVENTION PLUGINS (THE MODERN PATTERN)
─────────────────────────────────────────────────────────────────────────────────

  Problem: Duplicating plugin application and configuration across many
           subproject build.gradle.kts files.

  Solution: Convention plugins — reusable configuration packaged as a plugin,
  applied to subprojects. Lives in buildSrc/ or a dedicated build-conventions module.

  buildSrc/ directory structure:
  ─────────────────────────────
  buildSrc/
  ├── build.gradle.kts
  └── src/main/kotlin/
      ├── java-common-conventions.gradle.kts
      ├── java-library-conventions.gradle.kts
      └── spring-boot-conventions.gradle.kts

  buildSrc/build.gradle.kts:
  ──────────────────────────
  plugins {
      `kotlin-dsl`
  }
  repositories { gradlePluginPortal() }

  buildSrc/src/main/kotlin/java-common-conventions.gradle.kts:
  ─────────────────────────────────────────────────────────────
  plugins {
      java
      checkstyle
      jacoco
  }

  java {
      toolchain { languageVersion.set(JavaLanguageVersion.of(21)) }
  }

  repositories { mavenCentral() }

  dependencies {
      testImplementation("org.junit.jupiter:junit-jupiter:5.10.1")
      testRuntimeOnly("org.junit.platform:junit-platform-launcher")
  }

  tasks.test { useJUnitPlatform() }
  tasks.check { dependsOn(tasks.jacocoTestCoverageVerification) }

  buildSrc/src/main/kotlin/java-library-conventions.gradle.kts:
  ──────────────────────────────────────────────────────────────
  plugins {
      id("java-common-conventions")
      `java-library`
      `maven-publish`
  }

  // Use in subproject:
  // plugins { id("java-library-conventions") }
  // No more boilerplate in each subproject!

─────────────────────────────────────────────────────────────────────────────────
COMPOSITE BUILDS
─────────────────────────────────────────────────────────────────────────────────

  Composite builds let you include another Gradle build as a dependency,
  substituting a project dependency for a published artifact.
  Useful for working on a library and its consumer simultaneously.

  settings.gradle.kts:
  ────────────────────
  includeBuild("../my-library") {
      dependencySubstitution {
          substitute(module("com.example:my-library"))
              .using(project(":"))
      }
  }

  Now any dependency on com.example:my-library resolves to the local build
  of ../my-library instead of the published artifact.
  Changes in ../my-library are immediately reflected in this build.

─────────────────────────────────────────────────────────────────────────────────
MAVEN vs GRADLE MULTI-MODULE COMPARISON
─────────────────────────────────────────────────────────────────────────────────

  Feature                     Maven                   Gradle
  ─────────────────────────── ─────────────────────── ──────────────────────────
  Module declaration          pom.xml <modules>        settings.gradle include()
  Shared config               Parent POM               subprojects {} / convention plugins
  Execution order             Reactor sort by deps     Task dependency graph
  Parallel build              -T flag                  --parallel flag
  Cross-project reference     <dependency> on artifact project(":module")
  Version management          Parent POM / BOM         Version catalog / platform
  Selective build             -pl :module -am          :module:build
  Working with local source   Maven local repo         Composite builds

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the role of settings.gradle.kts in a multi-module Gradle build?
A: It is the entry point for the Gradle build. It declares the root project name
   and all subprojects using include(). Gradle reads this file first during
   Initialization to know which projects exist. It can also configure the dependency
   resolution management (repositories, version catalogs) shared by all subprojects.

Q: What is the difference between subprojects{} and allprojects{} in Gradle?
A: allprojects{} applies configuration to the root project AND all subprojects.
   subprojects{} applies only to subprojects, not the root. In practice, avoid
   using these and prefer convention plugins (buildSrc) — cross-project configuration
   via allprojects/subprojects is considered an anti-pattern in modern Gradle as it
   couples everything tightly.

Q: What is buildSrc in Gradle and what is it used for?
A: buildSrc is a special Gradle project whose output is automatically added to the
   build script classpath of all other subprojects. It's used to define convention
   plugins — reusable build logic (plugins, utility functions) shared across
   subprojects. When you define java-conventions.gradle.kts in buildSrc, any
   subproject can apply it with plugins { id("java-conventions") } without
   publishing it to a repository.

Q: What is a Gradle composite build?
A: Composite builds (includeBuild in settings.gradle.kts) allow you to substitute
   a published artifact with a local project. This lets you develop multiple
   related projects together — changes to the included build are immediately picked
   up by the consumer build, without needing to publish to a local repository.
