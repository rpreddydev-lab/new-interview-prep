================================================================================
  MAVEN LIFECYCLE PHASES — DEEP DIVE
================================================================================

(See also: 00_Overview/02_Build_Lifecycle.txt for the overview)

This file focuses on the practical mechanics, phase-goal bindings, and real-world
usage patterns that interviewers love to probe.

─────────────────────────────────────────────────────────────────────────────────
HOW PHASES AND GOALS INTERACT
─────────────────────────────────────────────────────────────────────────────────

  The lifecycle is a sequence of named phases.
  Plugins provide goals.
  Goals are bound to phases.
  Running a phase runs all PRIOR phases, then executes the goals bound to each.

  Analogy:
  Phase  = a stage in an assembly line (e.g., "paint")
  Goal   = the actual robot performing the work (e.g., "spray-paint:apply")
  Plugin = the manufacturer of the robots (e.g., "PaintingCo")

─────────────────────────────────────────────────────────────────────────────────
DEFAULT LIFECYCLE — PHASE-TO-GOAL BINDINGS BY PACKAGING
─────────────────────────────────────────────────────────────────────────────────

  PACKAGING: jar (most common)
  ─────────────────────────────
  Phase                   Plugin:Goal
  ─────────────────────── ────────────────────────────────────────────────────
  process-resources       maven-resources-plugin:resources
  compile                 maven-compiler-plugin:compile
  process-test-resources  maven-resources-plugin:testResources
  test-compile            maven-compiler-plugin:testCompile
  test                    maven-surefire-plugin:test
  package                 maven-jar-plugin:jar
  install                 maven-install-plugin:install
  deploy                  maven-deploy-plugin:deploy

  PACKAGING: war
  ──────────────
  All of the above, EXCEPT:
  package → maven-war-plugin:war   (instead of maven-jar-plugin:jar)

  PACKAGING: pom (parent/aggregator)
  ────────────────────────────────────
  install → maven-install-plugin:install
  deploy  → maven-deploy-plugin:deploy
  (No compile, test, or package phases — nothing to compile)

─────────────────────────────────────────────────────────────────────────────────
HOW TO ADD GOALS TO A PHASE
─────────────────────────────────────────────────────────────────────────────────

  You bind additional goals to phases via <executions> in plugin config.

  Pattern:
  <plugin>
    <groupId>PLUGIN_GROUP</groupId>
    <artifactId>PLUGIN_ARTIFACT</artifactId>
    <version>PLUGIN_VERSION</version>
    <executions>
      <execution>
        <id>UNIQUE_ID</id>             <!-- arbitrary identifier -->
        <phase>LIFECYCLE_PHASE</phase>  <!-- when to run -->
        <goals>
          <goal>GOAL_NAME</goal>        <!-- what to run -->
        </goals>
        <configuration>
          <!-- goal-specific config -->
        </configuration>
      </execution>
    </executions>
  </plugin>

  Example — Generate Avro classes during generate-sources:
  <plugin>
    <groupId>org.apache.avro</groupId>
    <artifactId>avro-maven-plugin</artifactId>
    <version>1.11.3</version>
    <executions>
      <execution>
        <id>generate-avro</id>
        <phase>generate-sources</phase>
        <goals><goal>schema</goal></goals>
        <configuration>
          <sourceDirectory>${project.basedir}/src/main/avro/</sourceDirectory>
          <outputDirectory>${project.build.directory}/generated-sources/avro/</outputDirectory>
        </configuration>
      </execution>
    </executions>
  </plugin>

─────────────────────────────────────────────────────────────────────────────────
MAVEN SUREFIRE PLUGIN — UNIT TEST EXECUTION
─────────────────────────────────────────────────────────────────────────────────

  Surefire runs during the "test" phase. By default it runs:
  • Classes matching: **/*Test.java, **/Test*.java, **/*Tests.java, **/*TestCase.java

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>3.1.2</version>
    <configuration>
      <!-- Run tests in parallel -->
      <parallel>methods</parallel>
      <threadCount>4</threadCount>

      <!-- Specific test inclusion/exclusion -->
      <includes>
        <include>**/*Test.java</include>
      </includes>
      <excludes>
        <exclude>**/*IntegrationTest.java</exclude>
      </excludes>

      <!-- Skip tests -->
      <skipTests>false</skipTests>

      <!-- JVM args for tests -->
      <argLine>-Xmx1024m -XX:+UseG1GC</argLine>

      <!-- System properties available to tests -->
      <systemPropertyVariables>
        <spring.profiles.active>test</spring.profiles.active>
      </systemPropertyVariables>
    </configuration>
  </plugin>

─────────────────────────────────────────────────────────────────────────────────
MAVEN FAILSAFE PLUGIN — INTEGRATION TEST EXECUTION
─────────────────────────────────────────────────────────────────────────────────

  Failsafe runs integration tests during pre-integration-test / integration-test
  / post-integration-test / verify phases. Key difference from Surefire:
  • Surefire: test phase — build FAILS immediately if a test fails
  • Failsafe: verify phase — build reports failures AFTER post-integration-test
    (so teardown still runs even if tests fail)

  Default matching: **/*IT.java, **/IT*.java, **/*ITCase.java

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <version>3.1.2</version>
    <executions>
      <execution>
        <goals>
          <goal>integration-test</goal>  <!-- runs ITs during integration-test phase -->
          <goal>verify</goal>             <!-- reports failures during verify phase -->
        </goals>
      </execution>
    </executions>
  </plugin>

  Common pattern with Testcontainers or Embedded Server:
  pre-integration-test  → start Docker containers / embedded server
  integration-test      → run @SpringBootTest integration tests
  post-integration-test → stop containers
  verify                → check results, fail if tests failed

─────────────────────────────────────────────────────────────────────────────────
JACOCO — CODE COVERAGE INTEGRATION
─────────────────────────────────────────────────────────────────────────────────

  JaCoCo works by attaching a Java agent that instruments bytecode at runtime.

  <plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>
    <executions>
      <!-- Step 1: prepare agent BEFORE tests run -->
      <execution>
        <id>prepare-agent</id>
        <goals><goal>prepare-agent</goal></goals>
        <!-- Binds to "initialize" phase by default -->
      </execution>
      <!-- Step 2: generate report AFTER tests run -->
      <execution>
        <id>report</id>
        <phase>verify</phase>
        <goals><goal>report</goal></goals>
      </execution>
      <!-- Step 3: enforce coverage threshold -->
      <execution>
        <id>check</id>
        <phase>verify</phase>
        <goals><goal>check</goal></goals>
        <configuration>
          <rules>
            <rule>
              <limits>
                <limit>
                  <counter>LINE</counter>
                  <value>COVEREDRATIO</value>
                  <minimum>0.80</minimum>  <!-- 80% line coverage required -->
                </limit>
              </limits>
            </rule>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

─────────────────────────────────────────────────────────────────────────────────
MAVEN COMPILER PLUGIN — IMPORTANT SETTINGS
─────────────────────────────────────────────────────────────────────────────────

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.11.0</version>
    <configuration>
      <source>21</source>
      <target>21</target>
      <!-- OR use release for sealed/records stricter mode: -->
      <release>21</release>  <!-- preferred over source/target for JDK 9+ -->

      <encoding>UTF-8</encoding>
      <showWarnings>true</showWarnings>
      <showDeprecation>true</showDeprecation>

      <!-- Annotation processors (e.g., Lombok, MapStruct) -->
      <annotationProcessorPaths>
        <path>
          <groupId>org.projectlombok</groupId>
          <artifactId>lombok</artifactId>
          <version>1.18.30</version>
        </path>
        <path>
          <groupId>org.mapstruct</groupId>
          <artifactId>mapstruct-processor</artifactId>
          <version>1.5.5.Final</version>
        </path>
      </annotationProcessorPaths>
    </configuration>
  </plugin>

  Note: <release> vs <source>/<target>:
  • <source>/<target> allows code to use newer APIs even on older JDKs (dangerous)
  • <release> enforces both language level AND API availability for that JDK version
  • Always prefer <release> for JDK 9+

SPRING BOOT MAVEN PLUGIN
─────────────────────────────────────────────────────────────────────────────────

  The Spring Boot Maven Plugin creates an executable "fat JAR" (or WAR) with all
  dependencies embedded.

  <plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
      <!-- Exclude annotation-only dependencies from fat JAR -->
      <excludes>
        <exclude>
          <groupId>org.projectlombok</groupId>
          <artifactId>lombok</artifactId>
        </exclude>
      </excludes>
      <!-- JVM args when using mvn spring-boot:run -->
      <jvmArguments>-Xmx512m -Dspring.profiles.active=dev</jvmArguments>
    </configuration>
  </plugin>

  Key goals:
  • spring-boot:run       — run the app without packaging
  • spring-boot:repackage — repackage the JAR/WAR to be executable (bound to package)
  • spring-boot:build-image — build OCI image using Cloud Native Buildpacks

─────────────────────────────────────────────────────────────────────────────────
RUNNING GOALS OUT OF LIFECYCLE ORDER
─────────────────────────────────────────────────────────────────────────────────

  You can invoke any goal directly, bypassing the lifecycle:

  mvn compiler:compile         # Just compile, skip validate/initialize
  mvn surefire:test            # Just run tests (assumes already compiled)
  mvn dependency:tree          # Utility goal, no lifecycle needed
  mvn versions:display-dependency-updates
  mvn jacoco:report            # Generate coverage report (assumes data exists)
  mvn spring-boot:run          # Run the app directly

  This is useful for debugging or running specific utility goals without a full build.

─────────────────────────────────────────────────────────────────────────────────
PHASE SKIPPING AND CONDITIONAL EXECUTION
─────────────────────────────────────────────────────────────────────────────────

  # Skip test EXECUTION (tests are still compiled):
  mvn package -DskipTests

  # Skip test COMPILATION AND execution:
  mvn package -Dmaven.test.skip=true

  # Skip Checkstyle plugin:
  mvn package -Dcheckstyle.skip=true

  # Skip JaCoCo:
  mvn package -Djacoco.skip=true

  # Skip the entire verify phase checks:
  mvn package -Dmaven.test.failure.ignore=true   # Continue even if tests fail

  # Run only a specific test class:
  mvn test -Dtest=UserServiceTest

  # Run a specific test method:
  mvn test -Dtest=UserServiceTest#testCreateUser

  # Run with a regex pattern:
  mvn test -Dtest="UserService*,OrderService*"

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between Surefire and Failsafe plugins?
A: Both run tests, but:
   • Surefire runs unit tests during the "test" phase. Build fails immediately.
   • Failsafe runs integration tests during "integration-test" and reports results
     during "verify". This ensures post-integration-test cleanup (e.g., stopping
     containers) runs even if tests fail. Failsafe tests typically match **/*IT.java.

Q: How do you configure Maven to run tests in parallel?
A: In the Surefire plugin configuration, set <parallel>methods</parallel> and
   <threadCount>4</threadCount> (or <forkCount>2</forkCount> for forked JVMs).
   Be careful with shared state and database connections when parallelizing.

Q: What is the difference between <release> and <source>/<target> in the compiler plugin?
A: <release>21</release> is a single setting that restricts both the Java language
   version AND the available APIs to exactly that JDK version. Using <source>21 and
   <target>21> separately doesn't prevent accidental use of APIs not available in the
   target JDK. Always prefer <release> for Java 9+.

Q: How do you run a single test class with Maven?
A: mvn test -Dtest=UserServiceTest
   Or a specific method: mvn test -Dtest=UserServiceTest#testCreateUser

Q: How do you add JaCoCo code coverage to a Maven project?
A: Add the jacoco-maven-plugin with two executions:
   1. prepare-agent (bound to initialize) — attaches the JaCoCo agent
   2. report (bound to verify) — generates the HTML/XML coverage report
   Run "mvn verify" to get the coverage report in target/site/jacoco/.
