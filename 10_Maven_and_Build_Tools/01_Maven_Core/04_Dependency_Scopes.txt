WHAT IS A DEPENDENCY SCOPE?
────────────────────────────
A dependency scope controls:
  1. Which classpaths the dependency appears on (compile / test / runtime)
  2. Whether the dependency is included in the packaged artifact (JAR/WAR)
  3. Whether the dependency is transitively passed on to consumers of your artifact

There are 6 scopes in Maven: compile, provided, runtime, test, system, import

─────────────────────────────────────────────────────────────────────────────────
SCOPE COMPARISON TABLE
─────────────────────────────────────────────────────────────────────────────────

  Scope     Compile  Test  Runtime  Packaged  Transitive  Description
  ───────── ──────── ───── ──────── ───────── ─────────── ─────────────────────
  compile   ✔       ✔    ✔        ✔         ✔           Default. Everywhere.
  provided  ✔       ✔    ✗        ✗         ✗           Container provides it
  runtime   ✗       ✔    ✔        ✔         ✔           Not needed to compile
  test      ✗       ✔    ✗        ✗         ✗           Only in tests
  system    ✔       ✔    ✗        ✗         ✗           Explicit local JAR path
  import    N/A     N/A  N/A      N/A       N/A         BOM import only

  "Packaged" = included in the final JAR/WAR artifact

─────────────────────────────────────────────────────────────────────────────────
1. COMPILE SCOPE (default)
─────────────────────────────────────────────────────────────────────────────────

  • Available on compile, test, AND runtime classpaths
  • Included in the packaged artifact
  • Transitively passed to consumers of your library
  • Use for: your core dependencies that code directly imports and uses

  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.16.0</version>
    <!-- scope defaults to compile if omitted -->
  </dependency>

  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>

  When to use: Any library you import with "import" statements in your code.

─────────────────────────────────────────────────────────────────────────────────
2. PROVIDED SCOPE
─────────────────────────────────────────────────────────────────────────────────

  • Available on compile and test classpaths
  • NOT included in the packaged artifact (runtime container provides it)
  • NOT transitively passed to consumers
  • Use for: APIs provided by the runtime environment (servlet container, app server)

  <dependency>
    <groupId>javax.servlet</groupId>
    <artifactId>javax.servlet-api</artifactId>
    <version>4.0.1</version>
    <scope>provided</scope>
  </dependency>

  Real-world examples:
  • javax.servlet-api / jakarta.servlet-api → provided by Tomcat/Jetty
  • javax.ejb-api → provided by JBoss/WildFly
  • lombok → annotation processor, not needed at runtime
  • Java EE / Jakarta EE APIs in EAR deployments

  WHY: If you bundle the servlet-api JAR inside your WAR, you'd have two copies
  (one from your WAR, one from Tomcat) — this causes ClassCastException and
  other mysterious failures.

  Spring Boot special case: Lombok uses provided scope because the compiler
  processes @Data etc. during compilation; no Lombok code remains at runtime.

─────────────────────────────────────────────────────────────────────────────────
3. RUNTIME SCOPE
─────────────────────────────────────────────────────────────────────────────────

  • NOT available on compile classpath
  • Available on test and runtime classpaths
  • Included in the packaged artifact
  • Transitively passed to consumers

  <dependency>
    <groupId>mysql</groupId>
    <artifactId>mysql-connector-java</artifactId>
    <version>8.0.33</version>
    <scope>runtime</scope>
  </dependency>

  Real-world examples:
  • JDBC drivers (mysql, postgresql, ojdbc) — you code against java.sql.*, not the driver
  • Logging implementations (logback-classic) — you code against SLF4J API
  • SLF4J bindings (slf4j-simple)
  • Database connection pool implementations when using the interface only

  WHY: Using runtime scope enforces proper separation between API and implementation.
  Your code compiles against the INTERFACE (java.sql.Driver, org.slf4j.Logger)
  and the implementation is swapped in at runtime.

  <dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.4.14</version>
    <scope>runtime</scope>
  </dependency>

─────────────────────────────────────────────────────────────────────────────────
4. TEST SCOPE
─────────────────────────────────────────────────────────────────────────────────

  • ONLY available in test compilation and test execution
  • NOT included in the packaged artifact
  • NOT transitively passed to consumers
  • Use for: test frameworks, mocking libraries, test utilities

  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.1</version>
    <scope>test</scope>
  </dependency>

  <dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <version>5.8.0</version>
    <scope>test</scope>
  </dependency>

  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
  </dependency>

  <dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>1.19.3</version>
    <scope>test</scope>
  </dependency>

  WHY: Ensures test code and test libraries don't leak into production artifacts.
  Keeps JARs small and clean.

─────────────────────────────────────────────────────────────────────────────────
5. SYSTEM SCOPE (AVOID)
─────────────────────────────────────────────────────────────────────────────────

  • Behaves like "provided" but requires explicit <systemPath>
  • References a JAR on the local filesystem (not from any repository)
  • NOT transitively passed to consumers
  • DEPRECATED and REMOVED from Maven 3.8.1+ for external repo usage

  <dependency>
    <groupId>com.oracle</groupId>
    <artifactId>ojdbc8</artifactId>
    <version>19.3.0</version>
    <scope>system</scope>
    <systemPath>${project.basedir}/libs/ojdbc8.jar</systemPath>
  </dependency>

  WHY TO AVOID:
  • Not portable — breaks on other developer machines
  • Not reproducible — CI/CD may fail if path doesn't exist
  • Bypasses dependency management

  ALTERNATIVE: Install the JAR to your local repo or upload to Nexus:
  mvn install:install-file -Dfile=ojdbc8.jar -DgroupId=com.oracle \
    -DartifactId=ojdbc8 -Dversion=19.3.0 -Dpackaging=jar

─────────────────────────────────────────────────────────────────────────────────
6. IMPORT SCOPE
─────────────────────────────────────────────────────────────────────────────────

  • ONLY valid inside <dependencyManagement>
  • ONLY valid for artifacts with <type>pom</type>
  • Imports all <dependencyManagement> entries from the target POM (BOM)
  • Equivalent to merging another POM's dependency management into yours

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.2.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
      <dependency>
        <groupId>io.awspring.cloud</groupId>
        <artifactId>spring-cloud-aws-dependencies</artifactId>
        <version>3.1.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  You can import MULTIPLE BOMs. If the same artifact is in multiple BOMs,
  the FIRST import wins (order matters!).

─────────────────────────────────────────────────────────────────────────────────
TRANSITIVE SCOPE RESOLUTION
─────────────────────────────────────────────────────────────────────────────────

  When Library A depends on Library B with scope X, and your project depends on
  Library A with scope Y, Library B's effective scope in your project is:

  Table: Effective scope of B in your project
  ─────────────────────────────────────────────────────────────────────────────
       A's scope of B →    compile   provided  runtime   test
  ─────────────────────────────────────────────────────────────────────────────
  Your scope of A ↓
  compile                  compile   (-)       runtime   (-)
  provided                 provided  (-)       provided  (-)
  runtime                  runtime   (-)       runtime   (-)
  test                     test      (-)       test      (-)

  (-) means the dependency is NOT included in your project.

  Key takeaways:
  • "provided" and "test" transitive deps are NEVER included
  • "compile" transitive of "compile" = "compile" in your project
  • "runtime" transitive of "compile" = "runtime" in your project

─────────────────────────────────────────────────────────────────────────────────
PRACTICAL DECISION GUIDE
─────────────────────────────────────────────────────────────────────────────────

  "Does my code directly use types from this library with import statements?"
  └── Yes → compile (default)
  └── No, only needed at runtime (driver, impl) → runtime

  "Is it provided by the application server or container at runtime?"
  └── Yes → provided

  "Is it only needed in test code?"
  └── Yes → test

  "Is this a local JAR file not in any repository?"
  └── Yes → system (but please install it to a local/private repo instead!)

  "Is this a BOM I want to import into dependency management?"
  └── Yes → import (with type=pom, in dependencyManagement only)

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What are all Maven dependency scopes?
A: compile (default), provided, runtime, test, system (deprecated), import.

Q: What is the difference between compile and provided scope?
A: Both are available during compilation. But provided is NOT included in the
   final artifact (JAR/WAR) because the runtime environment (servlet container,
   app server) is expected to provide it. Example: servlet-api is "provided"
   because Tomcat ships with it — bundling it would cause conflicts.

Q: What is the difference between compile and runtime scope?
A: compile is on the compile classpath AND runtime classpath. runtime is only
   on the runtime classpath (and test). Use runtime for implementations where
   you code against an interface (JDBC drivers, SLF4J implementations) to enforce
   the separation and prevent accidental direct use of implementation classes.

Q: Why would you use runtime scope for a JDBC driver?
A: Because your code should only use java.sql.* interfaces, not MySQL-specific
   classes. Using runtime scope ensures the driver is present to run your code,
   but prevents accidentally importing mysql.jdbc.Driver directly in your code.
   This makes it easy to swap database drivers without changing code.

Q: Does a test-scoped dependency transitively propagate?
A: No. test scope is never transitive. Your library's test dependencies (JUnit,
   Mockito) will never be added to projects that depend on your library.

Q: What scope should Lombok be?
A: provided. Lombok is an annotation processor — all @Data/@Builder/@Slf4j etc.
   are processed at compile time and replaced with generated code. No Lombok
   classes are needed at runtime, so it should not be bundled in the final JAR.
