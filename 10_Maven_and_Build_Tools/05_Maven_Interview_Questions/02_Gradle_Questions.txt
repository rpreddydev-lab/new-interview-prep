  GRADLE INTERVIEW QUESTIONS & ANSWERS

─────────────────────────────────────────────────────────────────────────────────
GRADLE FUNDAMENTALS
─────────────────────────────────────────────────────────────────────────────────

Q1: What are the three phases of a Gradle build?
A:  1. Initialization — reads settings.gradle(.kts) to determine which projects
       are part of the build. Creates Project objects for each.
    2. Configuration — evaluates all build.gradle(.kts) files (configures all tasks).
       Builds the task execution graph. Every task object is configured here,
       even if it won't run. This is why tasks.register() (lazy) is preferred
       over tasks.create() (eager).
    3. Execution — runs only the tasks requested (and their dependencies) in
       dependency order. Other tasks are skipped.

Q2: What is the Gradle Daemon and why is it important?
A:  The Gradle Daemon is a long-lived JVM process that stays running between
    builds. It avoids the JVM startup overhead (~1-3 seconds) on every build
    invocation and allows the JIT compiler to warm up (faster execution over time).
    It also caches dependency resolution metadata and file system state.
    Enabled by default since Gradle 3.x.
    Commands: ./gradlew --status (list daemons), ./gradlew --stop (stop all),
    gradle.properties: org.gradle.daemon=true (explicit enable)
    Timeouts after 3 hours of inactivity. CI environments use --no-daemon.

Q3: What is the Gradle Wrapper and why use it?
A:  gradlew (gradlew.bat on Windows) is a script that downloads and uses the
    specific Gradle version declared in gradle/wrapper/gradle-wrapper.properties.
    Benefits: (1) team members don't need Gradle installed, (2) guarantees everyone
    uses the exact same Gradle version, (3) CI environments are consistent.
    Always commit the wrapper scripts and gradle-wrapper.properties to source control.

Q4: What is the difference between tasks.register() and tasks.create() in Gradle?
A:  tasks.register() — lazy: the task is only configured when Gradle determines it
    will actually run. This is the Configuration Avoidance API (Gradle 4.9+).
    tasks.create() — eager: the task is configured immediately during the
    configuration phase for every build invocation, even if the task won't run.
    In large projects, eager creation of all tasks wastes significant time.
    Use tasks.register() for all new tasks. Use tasks.named("existingTask") { }
    to lazily configure tasks registered by plugins.

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCIES & CONFIGURATIONS
─────────────────────────────────────────────────────────────────────────────────

Q5: What is the difference between "implementation" and "api" in Gradle?
A:  Both put the dependency on compile + runtime classpaths.
    api — exposes the dependency transitively to consumers (they see it on their
    compile classpath). Use when your library's public API uses types from the dep.
    implementation — hides the dep from consumers at compile time (they only get
    it at runtime through your artifact). Use for internal implementation details.
    "api" requires the java-library plugin. Default choice: implementation.
    Using "api" unnecessarily forces recompilation of all consumers when the dep changes.

Q6: How does Gradle resolve version conflicts by default?
A:  Gradle uses "highest-wins" — it selects the highest version requested anywhere
    in the dependency graph. This is generally preferable to Maven's "nearest-wins"
    because you typically want the newest compatible version. Override with:
    resolutionStrategy.force("group:artifact:version") — forces exact version
    dependency version { strictly("x.y.z") } — strict version on one dep
    resolutionStrategy.failOnVersionConflict() — fail instead of resolving

Q7: What is a Gradle platform() and how does it differ from enforcedPlatform()?
A:  platform() imports a Maven BOM (or Gradle platform project), providing version
    recommendations that can be overridden by the consumer.
    enforcedPlatform() imports the BOM and FORCES all versions — overrides are
    not allowed, and versions can be downgraded.
    Use platform() by default. Use enforcedPlatform() only when you need strict
    consistency and the tradeoffs (potential downgrades) are acceptable.

Q8: What is a Gradle Version Catalog?
A:  A libs.versions.toml file in the gradle/ directory that centralizes all
    dependency versions, coordinates, bundles (groups of deps), and plugin
    declarations. Provides type-safe accessor syntax in build scripts
    (e.g., libs.spring.boot.starter.web instead of literal strings). Works
    across all subprojects, enabling consistent version management without
    a BOM. Generated IDE accessors provide autocomplete.

─────────────────────────────────────────────────────────────────────────────────
TASKS
─────────────────────────────────────────────────────────────────────────────────

Q9: What does "UP-TO-DATE" mean in Gradle task output?
A:  Gradle skipped the task because its declared inputs and outputs haven't changed
    since the last run. This is incremental build — Gradle compares task input hashes
    with the previous run's hashes stored in ~/.gradle/caches/. Related states:
    FROM-CACHE — outputs restored from the build cache (local or remote),
    SKIPPED — onlyIf condition evaluated to false,
    NO-SOURCE — no source files (e.g., empty source directory),
    EXECUTED — task actually ran.

Q10: What is the difference between dependsOn, mustRunAfter, and finalizedBy?
A:  dependsOn("x") — the current task won't run unless x has run first. Adds x to
    the task graph if not already present (creates a true dependency).
    mustRunAfter("x") — if both tasks are in the task graph, this runs after x.
    Does NOT add x to the graph — it's only an ordering constraint.
    finalizedBy(x) — x always runs after the current task, even on task failure.
    Classic use: tasks.test { finalizedBy(tasks.jacocoTestReport) }

Q11: How do you make a custom Gradle task cacheable?
A:  Annotate it with @CacheableTask. Declare all inputs with @Input, @InputFile,
    @InputDirectory (with appropriate @PathSensitive annotation for remote cache
    portability — use RELATIVE or NAME_ONLY, not ABSOLUTE). Declare outputs with
    @OutputFile or @OutputDirectory. The task must be deterministic — same inputs
    must always produce the same outputs. Also configure:
    tasks.withType<AbstractArchiveTask>().configureEach {
        isPreserveFileTimestamps = false; isReproducibleFileOrder = true
    }

─────────────────────────────────────────────────────────────────────────────────
BUILD CACHE & PERFORMANCE
─────────────────────────────────────────────────────────────────────────────────

Q12: What is the Gradle build cache and how does it work?
A:  The build cache stores task outputs keyed by a hash of all task inputs
    (input files, property values, Gradle version, JDK version, plugin versions).
    On a cache hit, Gradle restores the outputs from cache instead of running
    the task. The local cache stores entries in ~/.gradle/caches/build-cache/.
    Remote cache (e.g., Develocity) shares entries across machines — CI builds
    write to cache, developer machines read from it. Enable:
    org.gradle.caching=true in gradle.properties.

Q13: What is the Gradle configuration cache?
A:  The configuration cache stores the serialized task execution graph (result of
    the configuration phase) to disk. Subsequent builds with unchanged build scripts
    skip the configuration phase entirely — no build script evaluation, just execute
    tasks. Reduces build startup time by 5-30+ seconds for large projects.
    Enable: org.gradle.configuration-cache=true. Build scripts must be configuration-
    cache-compatible (no file reads, no System.getenv calls in configuration phase).

Q14: What is the difference between the Gradle build cache and UP-TO-DATE checking?
A:  UP-TO-DATE: "On THIS machine, have the inputs changed since the last run?"
    (incremental, local, survives between runs of the same task)
    Build cache: "Has ANYONE computed this exact task output before?" (cross-machine,
    survives clean, works across branches). UP-TO-DATE doesn't help after git clean
    or on a new CI runner. Build cache still gets hits in those scenarios.

─────────────────────────────────────────────────────────────────────────────────
MULTI-PROJECT BUILDS
─────────────────────────────────────────────────────────────────────────────────

Q15: What is the purpose of buildSrc in Gradle?
A:  buildSrc is a special directory whose contents are compiled and added to the
    build script classpath of all subprojects. Used to define convention plugins —
    reusable build logic (plugins, utility functions, shared configurations) that
    can be applied across subprojects with plugins { id("java-conventions") }.
    Avoids duplicating build configuration in every subproject. Alternative:
    included builds (for sharing logic across separate repositories).

Q16: What is the difference between subprojects{} and allprojects{} in Gradle?
A:  allprojects{} applies configuration to the root project AND all subprojects.
    subprojects{} applies only to subprojects, not the root.
    Both are considered an anti-pattern in modern Gradle (cross-project configuration
    couples everything tightly and breaks configuration avoidance). The preferred
    approach is convention plugins in buildSrc where each subproject explicitly
    opts in with plugins { id("my-conventions") }.

Q17: What is a Gradle composite build?
A:  Defined with includeBuild() in settings.gradle.kts, composite builds allow
    you to substitute a published artifact with a local build:
    substitute(module("com.example:my-lib")).using(project(":"))
    This lets you develop a library and its consumer simultaneously without
    publishing to a local repository. Changes to the included build are immediately
    picked up by the consumer build.

─────────────────────────────────────────────────────────────────────────────────
GROOVY vs KOTLIN DSL
─────────────────────────────────────────────────────────────────────────────────

Q18: Should new Gradle projects use Groovy or Kotlin DSL?
A:  Kotlin DSL (build.gradle.kts) is recommended for new projects. Benefits:
    static typing (full IDE autocompletion, type checking, refactoring support),
    compile-time errors in build scripts, first-class Kotlin tooling in IntelliJ.
    Groovy DSL (build.gradle) is still valid — more concise, faster to write,
    huge existing ecosystem. Both use the same Gradle API. Migration is typically
    straightforward: rename files, change quote style, add parentheses to method calls.
