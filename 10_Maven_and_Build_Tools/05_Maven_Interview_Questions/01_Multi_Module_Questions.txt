================================================================================
  MAVEN MULTI-MODULE INTERVIEW QUESTIONS & ANSWERS
================================================================================

─────────────────────────────────────────────────────────────────────────────────
STRUCTURE & CONCEPTS
─────────────────────────────────────────────────────────────────────────────────

Q1: What is a Maven multi-module project?
A:  A project structure where a parent POM (aggregator) declares multiple
    <modules>, each being a separate Maven project (submodule) with its own
    pom.xml. Maven builds them together in the correct order determined by their
    inter-dependencies. This allows sharing configuration via parent inheritance
    and enables building the entire project with a single mvn command.

Q2: What is the difference between an aggregator POM and a parent POM?
A:  Aggregator POM (packaging=pom, has <modules>): tells Maven which subprojects
    to include in the build. When you run mvn build from the aggregator, it builds
    all listed modules.
    Parent POM (referenced via <parent> in child POMs): provides inherited
    configuration — <dependencyManagement>, <pluginManagement>, <properties>.
    A POM can be both aggregator AND parent simultaneously (common pattern).
    They can also be separate — a child can have a parent that isn't the aggregator.

Q3: What is the Maven Reactor?
A:  The Reactor is Maven's mechanism for building multi-module projects. It:
    1. Collects all modules declared in <modules>
    2. Reads each module's pom.xml to understand inter-module dependencies
    3. Sorts them into a build order using topological sort (ensuring modules
       that depend on others are built after their dependencies)
    4. Executes the build in that order
    "Reactor build order" is shown at the start of mvn output.

Q4: What configuration is inherited by child modules from the parent POM?
A:  Inherited:
    • <groupId> and <version> (can be omitted in child if same as parent)
    • <properties>
    • <dependencyManagement> — version/scope declarations (not the deps themselves)
    • <pluginManagement> — plugin configurations (not the plugins themselves)
    • <build> settings (source/test directories, resource filtering)
    • <repositories> and <pluginRepositories>
    • <distributionManagement>
    NOT inherited (must redeclare in each child):
    • <dependencies> — actual dependencies
    • <plugins> in <build>
    • <modules>

─────────────────────────────────────────────────────────────────────────────────
COMMANDS & REACTOR
─────────────────────────────────────────────────────────────────────────────────

Q5: How do you build only a specific module and its dependencies?
A:  Use -pl (project list) with -am (also make — build dependencies):
    mvn install -pl :service-impl -am
    This builds service-impl and all modules that service-impl depends on.
    Without -am, only service-impl is built, which may fail if its dependencies
    are not already installed.

Q6: What does "-am" and "-amd" do in Maven?
A:  -am (--also-make): when building a subset with -pl, also build modules that
    the selected modules depend on (upstream dependencies). Ensures the selected
    module can compile.
    -amd (--also-make-dependents): also build modules that depend on the selected
    modules (downstream dependents). Useful when you change a shared library and
    want to verify nothing downstream breaks.
    Example: mvn test -pl :api -amd → test api and all modules that use api.

Q7: What is "-T" flag and how does it affect the build?
A:  -T enables parallel module builds in the Reactor.
    -T 4          → use 4 threads
    -T 1C         → 1 thread per CPU core (recommended: -T 1C)
    -T 2C         → 2 threads per CPU core
    Maven only parallelizes modules that have no dependency relationship.
    Modules that depend on each other are still built sequentially.
    Caution: some plugins are not thread-safe; test before enabling in CI.

Q8: What is "-rf" (resume from) used for?
A:  -rf :module — resume a failed multi-module build from a specific module.
    If a build of 20 modules fails at module 10, fix the issue and run:
    mvn install -rf :failed-module
    This skips modules 1-9 (already built) and starts from module 10.

─────────────────────────────────────────────────────────────────────────────────
VERSION MANAGEMENT
─────────────────────────────────────────────────────────────────────────────────

Q9: How do you manage versions across multiple modules?
A:  Three approaches:
    1. Parent POM with explicit version: All modules declare the same parent
       version. Change versions with versions plugin: mvn versions:set -DnewVersion=2.0
    2. CI-friendly ${revision}: Define version once in parent as
       <revision>1.0.0-SNAPSHOT</revision>, all modules use ${revision} in their
       <version> tag. Pass version via: mvn -Drevision=1.2.0 install
    3. BOM import: Separate platform/BOM module manages all internal artifact versions.

Q10: What is the versions-maven-plugin and how do you use it?
A:  A plugin for updating versions across a multi-module project:
    mvn versions:set -DnewVersion=2.0.0     # Update all modules to 2.0.0
    mvn versions:commit                       # Remove backup pom.xml.versionsBackup
    mvn versions:revert                       # Revert using backup files
    mvn versions:display-dependency-updates   # Show available dependency upgrades
    mvn versions:display-plugin-updates       # Show available plugin upgrades
    mvn versions:use-latest-releases         # Auto-update to latest releases
    Always run mvn versions:commit after set to clean up .versionsBackup files.

Q11: What is CI-friendly versioning in Maven?
A:  A pattern (introduced in Maven 3.5+) where all module versions use a property
    placeholder ${revision} instead of hardcoded version strings:
    <version>${revision}</version>
    The actual version is passed via command line: mvn -Drevision=1.0.${BUILD_NUMBER} package
    Requires the flatten-maven-plugin to replace ${revision} in installed/deployed
    POMs with the actual resolved version (otherwise consumers see a literal
    ${revision} in the deployed artifact's POM — broken dependency resolution).

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY MANAGEMENT IN MULTI-MODULE
─────────────────────────────────────────────────────────────────────────────────

Q12: How do you share dependency versions across all modules without forcing
     every module to include all dependencies?
A:  Use <dependencyManagement> in the parent POM. It declares versions and scopes
    but does NOT add dependencies to the classpath. Each child module then declares
    only the dependencies it actually uses (without version — inherited from parent's
    dependencyManagement). This provides version consistency without forcing unused
    dependencies on all modules.

Q13: What is the difference between using a parent POM and importing a BOM?
A:  Parent POM (inheritance): A module can have ONLY ONE parent. Inherits all
    configuration from the parent — dependencies, plugins, properties, everything.
    Tight coupling to the parent's structure.
    BOM import (scope=import): Can import MULTIPLE BOMs. Only imports version
    management — no plugin or other configuration is inherited. More flexible
    for mixing with spring-boot-starter-parent or when you can't control the
    parent hierarchy.

Q14: How do you reference one module from another within the same multi-module build?
A:  Declare a project dependency in the consuming module's pom.xml:
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>shared-utils</artifactId>
      <version>${project.version}</version>
    </dependency>
    Or better, manage the version in parent's dependencyManagement and omit
    the version tag. Maven's Reactor ensures the dependency module is built first.

─────────────────────────────────────────────────────────────────────────────────
SPRING BOOT PARENT IN MULTI-MODULE
─────────────────────────────────────────────────────────────────────────────────

Q15: How do you use spring-boot-starter-parent in a multi-module project?
A:  Two patterns:
    Pattern 1 (parent chain): Root POM inherits from spring-boot-starter-parent,
    all child modules inherit from root. Simple but uses up the single-parent slot.

    Pattern 2 (BOM import): Root POM does NOT inherit from Spring Boot; instead
    imports spring-boot-dependencies as a BOM:
    <dependencyManagement>
      <dependencies>
        <dependency>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-dependencies</artifactId>
          <version>3.2.0</version>
          <type>pom</type>
          <scope>import</scope>
        </dependency>
      </dependencies>
    </dependencyManagement>
    Pattern 2 is preferred when root must inherit from a corporate parent POM.

Q16: In a multi-module project, which module should the spring-boot-maven-plugin
     be applied to?
A:  Only to the module that produces the executable JAR/WAR (the "web" or "app"
    module). Library modules (api, service, persistence) should NOT have
    spring-boot-maven-plugin because it would repackage their JARs as executable
    Spring Boot JARs, making them unusable as library dependencies (the repackaged
    JAR cannot be used on the classpath of another project).
