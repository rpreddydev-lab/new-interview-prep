WHAT ARE TRANSITIVE DEPENDENCIES?
───────────────────────────────────
When you depend on library A, and library A depends on library B, your project
gets library B automatically — it is a transitive dependency.

Example:
  Your project → spring-boot-starter-web
                 → spring-webmvc
                    → spring-context
                       → spring-core
                 → spring-boot-starter-tomcat
                    → tomcat-embed-core
                 → jackson-databind
                    → jackson-core
                    → jackson-annotations

You declared 1 dependency; you got ~50 transitively.
This is powerful but requires careful management.

DEPENDENCY GRAPH
─────────────────────────────────────────────────────────────────────────────────

  A dependency graph is a directed acyclic graph (DAG) where:
  • Each node is a Maven artifact (groupId:artifactId:version)
  • Each edge represents "X depends on Y"
  • The root node is your project

  Visualizing the dependency tree:
  ─────────────────────────────────
  # Maven
  mvn dependency:tree
  mvn dependency:tree -Dincludes=org.springframework                 # filter
  mvn dependency:tree -Dverbose                                       # show all versions
  mvn dependency:tree -Dscope=runtime                                 # specific scope
  mvn dependency:tree -DoutputFile=deps.txt                           # save to file
  mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-core

  # Gradle
  ./gradlew dependencies
  ./gradlew dependencies --configuration runtimeClasspath             # specific config
  ./gradlew :module:dependencies --configuration compileClasspath
  ./gradlew dependencyInsight --dependency jackson-databind \
      --configuration runtimeClasspath                                # why was this version chosen?

  Maven tree output format:
  ──────────────────────────
  [INFO] com.example:my-app:jar:1.0.0
  [INFO] +- org.springframework.boot:spring-boot-starter-web:jar:3.2.0:compile
  [INFO] |  +- org.springframework:spring-webmvc:jar:6.1.0:compile
  [INFO] |  \- (org.springframework:spring-core:jar:6.1.0:compile - omitted for duplicate)
  [INFO] \- com.fasterxml.jackson.core:jackson-databind:jar:2.16.0:compile

  "omitted for duplicate"  — same GAV already included; not included twice
  "omitted for conflict"   — different version; the winner is shown elsewhere

SCOPE / CONFIGURATION PROPAGATION
─────────────────────────────────────────────────────────────────────────────────

  Maven Transitive Scope Rules:
  ──────────────────────────────
  Parent scope \ Transitive scope → result:
         compile  provided  runtime  test
  compile  compile  -         runtime  -
  provided provided -         provided -
  runtime  runtime  -         runtime  -
  test     test     -         test     -

  Meaning:
  • If A (compile) → B (compile): you get B as compile ✅
  • If A (compile) → B (provided): B is NOT transitive ❌ (provided deps stop here)
  • If A (compile) → B (runtime):  you get B as runtime ✅
  • If A (test)    → B (compile):  you get B as test ✅

  Gradle Transitive Rules:
  • api → propagated transitively to consumers
  • implementation → NOT propagated (stops here)
  • compileOnly → never propagated
  • runtimeOnly → runtime only, not propagated to consumers' compile

IDENTIFYING UNUSED AND UNDECLARED DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  # Maven — analyze dependencies
  mvn dependency:analyze

  Output: Used but undeclared (you rely on transitive — risky!)
          Declared but unused (can remove — reduces classpath)

  Example warning:
  [WARNING] Used undeclared dependencies found:
  [WARNING]    org.slf4j:slf4j-api:jar:2.0.9:compile
  → You're using SLF4J but only have it transitively via logback.
    If logback is removed/upgraded, it might break. Declare it explicitly.

  [WARNING] Unused declared dependencies found:
  [WARNING]    org.apache.httpcomponents:httpclient:jar:4.5.14:compile
  → You declared this but your code doesn't import from it directly.
    Possibly a transitive is needed; possibly you can remove it.

  Gradle equivalent:
  ./gradlew dependencies --configuration compileClasspath > deps.txt

─────────────────────────────────────────────────────────────────────────────────
OPTIONAL DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  Maven optional dependencies are NOT transitive — they're pulled only if
  the consumer explicitly declares them.

  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.16.0</version>
    <optional>true</optional>
  </dependency>

  Use case: A library that can optionally serialize to JSON (requires Jackson)
  but doesn't force all consumers to have Jackson.

  In Gradle, there's no direct optional concept; use compileOnly or the
  Capabilities API for optional features.

─────────────────────────────────────────────────────────────────────────────────
CLASSPATH EXPLOSION PROBLEM
─────────────────────────────────────────────────────────────────────────────────

  Problem: Unchecked transitive dependencies can pull in hundreds of JARs,
           leading to:
  • Classpath conflicts (incompatible versions of the same class)
  • Fat JAR / WAR size explosion
  • Security vulnerabilities from unused transitive deps
  • Slower startup and compile times

  Solutions:
  1. Use dependency scopes/configurations correctly (runtime only where possible)
  2. Exclude unwanted transitives explicitly
  3. Use BOMs / platforms for version alignment
  4. Run mvn dependency:analyze / ./gradlew dependencies regularly
  5. Enable vulnerability scanning (OWASP, Snyk)
  6. Keep direct dependencies minimal (prefer umbrella starters)

ENFORCING NO UNEXPECTED TRANSITIVES (Maven Enforcer)
─────────────────────────────────────────────────────────────────────────────────

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <version>3.4.1</version>
    <executions>
      <execution>
        <id>enforce</id>
        <goals><goal>enforce</goal></goals>
        <configuration>
          <rules>
            <!-- Fail if any dep version converges to something unexpected -->
            <dependencyConvergence/>
            <!-- Fail if using a banned dep -->
            <bannedDependencies>
              <excludes>
                <exclude>commons-logging:commons-logging</exclude>
                <exclude>log4j:log4j</exclude>
              </excludes>
            </bannedDependencies>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is a transitive dependency?
A: A transitive dependency is an indirect dependency — if your project depends on
   library A, and library A depends on library B, then B is a transitive dependency
   of your project. Both Maven and Gradle resolve transitives automatically. You can
   view the full graph with mvn dependency:tree or ./gradlew dependencies.

Q: What does "Used undeclared dependency" mean in Maven dependency:analyze?
A: It means your code compiles because of a transitive dependency — you import
   classes from a library that you didn't explicitly declare, but which came in
   transitively through another dependency. This is fragile: if the providing
   dependency is removed or updated to not include that transitive, your build breaks.
   You should declare the dependency explicitly.

Q: How do you view the full transitive dependency tree in Maven?
A: mvn dependency:tree — shows the full resolution graph. Add -Dverbose to see
   all versions including omitted ones. Add -Dincludes=groupId:artifactId to
   filter for a specific artifact. Use mvn dependency:analyze to find used-undeclared
   and unused-declared dependencies.

Q: What is the risk of relying on transitive dependencies directly?
A: Transitive dependencies are not guaranteed to be stable — the direct dependency
   may change its own dependencies in a new version, removing or replacing the
   transitive you relied on. This causes compilation or runtime failures when you
   upgrade the direct dependency. Best practice: always declare every dependency
   your code directly uses, even if it's already available transitively.
