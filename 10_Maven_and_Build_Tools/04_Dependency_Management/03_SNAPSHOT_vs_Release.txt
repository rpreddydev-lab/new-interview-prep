================================================================================
  SNAPSHOT vs RELEASE DEPENDENCIES
================================================================================

CORE CONCEPTS
──────────────
  RELEASE version:  1.0.0, 2.3.1, 3.0.0-RC1
    • Immutable — once deployed, the artifact at that GAV never changes
    • Downloaded once and cached forever in local repo
    • Used for stable, production-grade code

  SNAPSHOT version:  1.0.0-SNAPSHOT, 2.3.1-SNAPSHOT
    • Mutable — represents "work in progress" / "next unreleased version"
    • Can be redeployed as many times as needed (artifact changes)
    • Repository managers periodically check for updated SNAPSHOTs
    • NOT suitable for production deployments

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT MECHANICS IN MAVEN
─────────────────────────────────────────────────────────────────────────────────

  When you deploy a SNAPSHOT:
  ────────────────────────────
  mvn deploy

  Maven actually uploads the artifact with a TIMESTAMP version:
    mylib-1.0.0-20240115.143022-1.jar  (timestamp + build number)

  The remote repo also updates:
    maven-metadata.xml  — points the latest timestamp version for mylib-1.0.0-SNAPSHOT

  When someone depends on mylib:1.0.0-SNAPSHOT and runs mvn, Maven:
  1. Reads maven-metadata.xml from the remote repo
  2. Finds the latest timestamp version
  3. Downloads mylib-1.0.0-20240115.143022-1.jar
  4. Stores it in local repo as mylib-1.0.0-SNAPSHOT (no timestamp in local cache)

  Update policy:
  ────────────────
  By default Maven checks for SNAPSHOT updates once per day.
  Override:
  • -U flag:  mvn -U install  → force check for updates right now
  • Repository update policy configuration:

  <repository>
    <id>my-repo</id>
    <snapshots>
      <updatePolicy>always</updatePolicy>   <!-- always | daily | interval:60 | never -->
      <checksumPolicy>warn</checksumPolicy>  <!-- fail | warn | ignore -->
    </snapshots>
  </repository>

  Local repo structure:
  ──────────────────────
  ~/.m2/repository/com/example/mylib/1.0.0-SNAPSHOT/
  ├── mylib-1.0.0-SNAPSHOT.jar
  ├── mylib-1.0.0-SNAPSHOT.pom
  └── maven-metadata-local.xml

─────────────────────────────────────────────────────────────────────────────────
RELEASE MECHANICS IN MAVEN
─────────────────────────────────────────────────────────────────────────────────

  Releases are immutable. Once 1.0.0 is deployed:
  • maven-metadata.xml is updated with versioning history
  • The artifact itself cannot be redeployed (repo manager enforces this)
  • Cached in local ~/.m2 forever (never rechecked)

  Release checks:
  ────────────────
  <repository>
    <id>my-repo</id>
    <releases>
      <updatePolicy>never</updatePolicy>     <!-- Never re-download a release -->
      <checksumPolicy>fail</checksumPolicy>  <!-- Fail if checksum mismatch -->
    </releases>
  </repository>

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT vs RELEASE REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

  Best practice: separate SNAPSHOT and RELEASE repositories.
  SNAPSHOTs change; releases are immutable. Mixing them in one repo
  is possible but makes cleanup/access control harder.

  Nexus / Artifactory:
  • maven-snapshots   — hosted repo, SNAPSHOT only
  • maven-releases    — hosted repo, RELEASE only, redeploy disabled
  • maven-public      — group repo combining both + Maven Central proxy

  Maven settings for separate repos:
  ─────────────────────────────────────
  <distributionManagement>
    <repository>
      <id>releases</id>
      <url>https://nexus.example.com/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
      <id>snapshots</id>
      <url>https://nexus.example.com/repository/maven-snapshots/</url>
    </snapshotRepository>
  </distributionManagement>

  Maven automatically deploys SNAPSHOT builds to snapshotRepository
  and RELEASE builds to repository based on the POM version string.

─────────────────────────────────────────────────────────────────────────────────
PREVENTING SNAPSHOTS IN RELEASES
─────────────────────────────────────────────────────────────────────────────────

  A release artifact must NOT depend on a SNAPSHOT (that would make the
  release non-reproducible and potentially broken).

  Enforce with Maven Enforcer:
  ─────────────────────────────
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <executions>
      <execution>
        <id>enforce-no-snapshots</id>
        <goals><goal>enforce</goal></goals>
        <configuration>
          <rules>
            <requireReleaseDeps>
              <message>Release builds must not depend on SNAPSHOTs!</message>
              <failWhenParentIsSnapshot>false</failWhenParentIsSnapshot>
            </requireReleaseDeps>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

  The maven-release-plugin also checks this automatically during release:prepare.

─────────────────────────────────────────────────────────────────────────────────
GRADLE SNAPSHOT HANDLING
─────────────────────────────────────────────────────────────────────────────────

  Declaring a SNAPSHOT dependency:
  ──────────────────────────────────
  dependencies {
      implementation("com.example:mylib:1.0.0-SNAPSHOT")
  }

  Gradle treats SNAPSHOT versions as "changing modules" and checks for updates
  every 24 hours by default.

  Force update check immediately:
  ────────────────────────────────
  ./gradlew build --refresh-dependencies

  Configure update frequency:
  ────────────────────────────
  configurations.all {
      resolutionStrategy {
          cacheChangingModulesFor(4, TimeUnit.HOURS)   // custom interval
          cacheChangingModulesFor(0, TimeUnit.SECONDS) // always check (like -U)
      }
  }

  Fail on SNAPSHOT deps in production:
  ──────────────────────────────────────
  configurations.all {
      resolutionStrategy {
          failOnChangingVersions()   // Gradle 7+ — fails if SNAPSHOT detected
      }
  }

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT IN CI/CD — BEST PRACTICES
─────────────────────────────────────────────────────────────────────────────────

  ✅ DO:
  • Use SNAPSHOT during active development of a library
  • Use SNAPSHOT for integration between teams building concurrently
  • Resolve SNAPSHOTs with -U in CI to always get the latest
  • Convert to RELEASE before cutting a production release

  ❌ DON'T:
  • Use SNAPSHOT versions in production deployments
  • Depend on a SNAPSHOT in a released artifact
  • Use SNAPSHOT in Docker image tags referenced by production environments
  • Use SNAPSHOT across team boundaries without coordination (it can change under you)

  Pipeline pattern for library teams:
  ─────────────────────────────────────
  feature branch: 1.0.0-SNAPSHOT → deploy to snapshot repo on every merge to main
  release branch: 1.0.0          → deploy to releases repo when ready to ship
  consumers of library:
    development: use 1.0.0-SNAPSHOT with -U
    production release: switch to 1.0.0 (RELEASE)

─────────────────────────────────────────────────────────────────────────────────
COMPARING SNAPSHOT vs RELEASE
─────────────────────────────────────────────────────────────────────────────────

  Property              SNAPSHOT                    RELEASE
  ──────────────────── ─────────────────────────── ──────────────────────────
  Mutability           Mutable — can redeploy       Immutable — cannot redeploy
  Caching              Re-checked periodically      Cached forever
  Reproducibility      NOT reproducible             Reproducible
  Production use       ❌ Never                     ✅ Required
  Versioning           1.0.0-SNAPSHOT               1.0.0, 1.0.1, 2.0.0
  Maven repoManager    snapshot repository          releases repository
  maven-metadata.xml   Has timestamp entries        Has version history
  Force re-download    mvn -U / --refresh-deps      Not possible (by design)
  Suitable for CI      ✅ (between builds)          ✅ (final artifacts)

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between a SNAPSHOT and a RELEASE dependency?
A: A RELEASE version (e.g., 1.0.0) is immutable — once published, the artifact
   at that GAV never changes. A SNAPSHOT (e.g., 1.0.0-SNAPSHOT) is mutable and
   represents work-in-progress. It can be redeployed repeatedly. Maven/Gradle
   periodically re-check SNAPSHOT dependencies for updates. SNAPSHATs should never
   be used in production or as dependencies of released artifacts.

Q: How does Maven store SNAPSHOT artifacts in a remote repository?
A: Each SNAPSHOT deployment gets a unique timestamp-based filename:
   mylib-1.0.0-20240115.143022-1.jar. The repository's maven-metadata.xml records
   all available timestamped versions and which is the latest. When Maven resolves
   1.0.0-SNAPSHOT, it reads maven-metadata.xml to find and download the latest
   timestamped artifact.

Q: How do you force Maven to re-download the latest SNAPSHOT?
A: Use the -U flag: mvn -U clean install. Without -U, Maven uses a cached SNAPSHOT
   and only re-checks based on the repository update policy (default: daily).

Q: Why should SNAPSHOT dependencies never appear in a released artifact?
A: A SNAPSHOT can change at any time, making the release non-reproducible.
   If someone builds the released artifact later (or in a different environment),
   they may get a different SNAPSHOT version, potentially breaking the build or
   runtime behavior. The maven-release-plugin enforces this by checking that no
   SNAPSHOT dependencies exist during release:prepare.
