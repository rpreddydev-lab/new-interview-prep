================================================================================
REDIS HIGH AVAILABILITY — OVERVIEW
================================================================================

1. WHY HIGH AVAILABILITY?
───────────────────────────
  A single Redis instance is a single point of failure (SPOF).
  If it crashes: cache miss, session loss, queue stall.

  Redis HA approaches:
    1. Replication         → copy data to one or more replicas
    2. Redis Sentinel      → automatic failover for standalone Redis
    3. Redis Cluster       → sharding + HA at scale

  Goal of HA:
    - Minimize downtime (recovery time objective: RTO)
    - Minimize data loss (recovery point objective: RPO)
    - Automatic failover without manual intervention


2. HA TOPOLOGY OPTIONS
────────────────────────
  Topology                 │ Sharding │ Automatic Failover │ Use Case
  ─────────────────────────┼──────────┼────────────────────┼────────────────────
  Standalone               │ No       │ No                 │ Dev/test
  Primary + Replica        │ No       │ No (manual)        │ Read scaling
  Sentinel (1 primary)     │ No       │ Yes                │ HA single dataset
  Cluster (N shards)       │ Yes      │ Yes (per shard)    │ Scale + HA


3. REPLICATION
───────────────
  Redis replication is asynchronous by default.
  Primary → writes → immediately returns to client
  Primary → sends write commands → replica applies asynchronously

  Replication lag exists. WAIT command can enforce sync:
    WAIT numreplicas timeout  → wait until N replicas ack, or timeout ms
    WAIT 1 1000               → wait for 1 replica within 1 second

  Replica reads:
    By default: replicas serve reads (replica-read-only yes)
    Stale reads possible due to async replication lag
    Use slave-serve-stale-data yes/no to control behavior during sync


4. SENTINEL — AUTOMATIC FAILOVER (STANDALONE)
───────────────────────────────────────────────
  Redis Sentinel is a distributed system of monitoring processes.
  Each Sentinel monitors the primary and replicas.
  On primary failure: Sentinels vote, elect leader, promote a replica.

  Sentinel quorum:
    Minimum Sentinels agreeing on failure = quorum (typically 2 of 3).
    Minimum Sentinels for election = majority of all Sentinels.

  Typical deployment:
    3 Sentinel processes + 1 Primary + 1-2 Replicas

  Client connects to Sentinel first:
    sentinel.getMasterAddrByName("mymaster") → returns current primary address
    Client library handles automatic reconnect on failover.

  Key Sentinel config:
    sentinel monitor mymaster 127.0.0.1 6379 2   # quorum=2
    sentinel down-after-milliseconds mymaster 5000
    sentinel failover-timeout mymaster 60000
    sentinel parallel-syncs mymaster 1


5. REDIS CLUSTER — SHARDING + HA
──────────────────────────────────
  Redis Cluster horizontally shards data across N primary nodes.
  Each primary can have replicas.
  Total hash slots: 16,384 (0 – 16383).
  Each key maps to a slot: CRC16(key) % 16384
  Each primary owns a range of slots.

  Minimum cluster size: 3 primaries (1 replica each = 6 nodes recommended).

  Automatic failover:
    If a primary is unreachable: its replicas vote to promote one.
    Cluster continues serving keys from healthy shards.
    Keys on failed shard (until failover completes) return CLUSTERDOWN.

  Hash tags:
    Force keys to same slot: {user:42}:session, {user:42}:profile
    Both keys → hash of "user:42" → same slot.


6. FAILOVER TIMELINE
──────────────────────
  Sentinel failover:
    1. Primary unresponsive for down-after-milliseconds (e.g., 5000ms)
    2. Sentinel marks primary as SDOWN (subjective down)
    3. Quorum of Sentinels agree → ODOWN (objective down)
    4. Sentinel election for failover leader
    5. Leader promotes best replica (highest replication offset)
    6. Other replicas repoint to new primary
    7. Old primary (if recovered) becomes a replica

  Total failover time: typically 10–30 seconds.
  Data loss window: commands during this time may be lost.

  Cluster failover:
    Similar but per-shard, handled by cluster nodes themselves.
    No external Sentinel process needed.


7. QUICK COMPARISON TABLE
───────────────────────────
  Feature               │ Sentinel              │ Cluster
  ──────────────────────┼───────────────────────┼────────────────────────────
  Sharding              │ No (single dataset)   │ Yes (16384 hash slots)
  Max dataset size      │ Single node RAM       │ Sum of all primary RAM
  Automatic failover    │ Yes                   │ Yes (per shard)
  Client complexity     │ Low (Sentinel aware)  │ Higher (cluster-aware)
  Multi-key commands    │ Unrestricted          │ Same slot only
  Replication           │ Yes                   │ Yes (per shard)
  Write scaling         │ No                    │ Yes (N primaries)
  Read scaling          │ Yes (read replicas)   │ Yes (read from replicas)
  Min recommended nodes │ 3 Sentinel + 1P + 1R  │ 6 (3P + 3R)
