gRPC COMMUNICATION IN MICROSERVICES
================================================================================

WHAT IS gRPC?
-------------
gRPC (Google Remote Procedure Call) is a high-performance, open-source RPC
framework developed by Google. Released as open source in 2015.

Core idea: Make calling a remote service feel like calling a local function.
           Hide all network serialization/deserialization from the developer.

Key technologies:
  - HTTP/2 as transport layer
  - Protocol Buffers (Protobuf) as interface definition language + serialization
  - Code generation from .proto files into client/server stubs

GRPC vs REST QUICK COMPARISON
─────────────────────────────
Feature         │ REST                    │ gRPC
────────────────┼─────────────────────────┼─────────────────────────
Protocol        │ HTTP/1.1                │ HTTP/2
Payload format  │ JSON (text, ~verbose)   │ Protobuf (binary, ~compact)
Performance     │ Baseline                │ 5-10x faster
Type safety     │ None (JSON is loose)    │ Strong (proto schema)
Streaming       │ Limited (SSE, WS)       │ Native 4 streaming modes
Contracts       │ Optional (OpenAPI)      │ Mandatory (.proto files)
Browser support │ Native                  │ Needs grpc-web proxy
Human readable  │ Yes (curl, Postman)     │ No (binary), use grpcurl
Code generation │ Optional                │ Required (protoc compiler)
Use case        │ External APIs           │ Internal high-perf services

PROTOCOL BUFFERS (PROTOBUF)
============================

Protobuf is both:
  1. An Interface Definition Language (IDL) — defines the API contract
  2. A serialization format — more efficient than JSON

Why Protobuf beats JSON:
  - Binary encoding → smaller payloads (typically 3-5x smaller)
  - Faster parsing (no string parsing, no schema validation at runtime)
  - Strongly typed → compile-time errors, not runtime errors
  - Forward/backward compatible with field numbers

PROTOBUF EXAMPLE (.proto file):

  syntax = "proto3";

  package order;

  option java_multiple_files = true;
  option java_package = "com.example.order.grpc";

  // Service definition
  service OrderService {
    rpc GetOrder (GetOrderRequest) returns (Order);
    rpc CreateOrder (CreateOrderRequest) returns (Order);
    rpc ListOrders (ListOrdersRequest) returns (stream Order);  // server streaming
    rpc ProcessOrders (stream Order) returns (OrderSummary);    // client streaming
  }

  // Messages
  message GetOrderRequest {
    int64 order_id = 1;  // field number — used in binary encoding
  }

  message CreateOrderRequest {
    int64 user_id = 1;
    repeated OrderItem items = 2;
    string shipping_address = 3;
  }

  message Order {
    int64 id = 1;
    int64 user_id = 2;
    OrderStatus status = 3;
    repeated OrderItem items = 4;
    google.protobuf.Timestamp created_at = 5;
    double total_amount = 6;
  }

  message OrderItem {
    int64 product_id = 1;
    int32 quantity = 2;
    double price = 3;
  }

  enum OrderStatus {
    ORDER_STATUS_UNSPECIFIED = 0;  // proto3: first enum value must be 0
    ORDER_STATUS_PENDING = 1;
    ORDER_STATUS_CONFIRMED = 2;
    ORDER_STATUS_SHIPPED = 3;
    ORDER_STATUS_DELIVERED = 4;
  }

FIELD NUMBERS:
  - Each field has a unique number (1, 2, 3...)
  - Used in binary encoding instead of field names (saves space)
  - NEVER change field numbers (backward compatibility breaks)
  - NEVER reuse field numbers from deleted fields
  - Can add new fields (backward compatible)
  - Can delete fields (forward compatible — receivers just ignore unknown fields)

GRPC STREAMING MODES
=====================

gRPC supports 4 communication modes (unlike REST which only supports request/response):

1. UNARY RPC (simple request/response)
   Client sends one request → server sends one response
   Most common mode. Equivalent to REST.

   rpc GetOrder (GetOrderRequest) returns (Order);

   Flow: Client ──[req]──→ Server ──[resp]──→ Client

2. SERVER STREAMING RPC
   Client sends one request → server streams multiple responses
   Use case: Live stock prices, progress updates, large data sets

   rpc ListOrders (ListOrdersRequest) returns (stream Order);

   Flow: Client ──[req]──→ Server ──[resp1]──→ Client
                                  ──[resp2]──→
                                  ──[resp3]──→
                                  ──[END]────→

3. CLIENT STREAMING RPC
   Client streams multiple requests → server sends one response
   Use case: File upload in chunks, bulk data import

   rpc UploadOrderItems (stream OrderItem) returns (UploadSummary);

   Flow: Client ──[item1]──→ Server
               ──[item2]──→
               ──[item3]──→
               ──[END]────→ Server ──[summary]──→ Client

4. BIDIRECTIONAL STREAMING RPC
   Both client and server send streams simultaneously
   Use case: Real-time chat, collaborative tools, trading platforms

   rpc Chat (stream ChatMessage) returns (stream ChatMessage);

   Flow: Client ──[msg]──→ Server
               ←──[msg]──
               ──[msg]──→
               ←──[msg]──

HTTP/2 ADVANTAGES
==================

HTTP/2 gives gRPC significant performance advantages over REST/HTTP/1.1:

1. MULTIPLEXING
   Multiple requests/responses over a single TCP connection simultaneously.
   HTTP/1.1: Each request needs its own connection (or connection pools)
   HTTP/2:   All requests share one connection → less overhead

2. HEADER COMPRESSION (HPACK)
   HTTP headers are compressed.
   REST: Headers like Authorization, Content-Type sent in full every request
   gRPC: Headers compressed → smaller payload

3. BINARY FRAMING
   Data sent as binary frames (more efficient than text)

4. SERVER PUSH
   Server can proactively send data to client before client requests

GRPC IN SPRING BOOT
====================

Dependencies (pom.xml):
  <dependency>
    <groupId>net.devh</groupId>
    <artifactId>grpc-server-spring-boot-starter</artifactId>
    <version>3.1.0.RELEASE</version>
  </dependency>

  <build>
    <extensions>
      <extension>
        <groupId>kr.motd.maven</groupId>
        <artifactId>os-maven-plugin</artifactId>
      </extension>
    </extensions>
    <plugins>
      <plugin>
        <groupId>org.xolstice.maven.plugins</groupId>
        <artifactId>protobuf-maven-plugin</artifactId>
        <!-- generates Java stubs from .proto files -->
      </plugin>
    </plugins>
  </build>

Server implementation:
  @GrpcService
  public class OrderGrpcService extends OrderServiceGrpc.OrderServiceImplBase {

    @Override
    public void getOrder(GetOrderRequest request, StreamObserver<Order> observer) {
      try {
        OrderEntity order = orderRepository.findById(request.getOrderId())
          .orElseThrow(() -> new StatusRuntimeException(Status.NOT_FOUND));

        Order response = Order.newBuilder()
          .setId(order.getId())
          .setUserId(order.getUserId())
          .setStatus(OrderStatus.valueOf(order.getStatus()))
          .setTotalAmount(order.getTotalAmount())
          .build();

        observer.onNext(response);
        observer.onCompleted();
      } catch (Exception e) {
        observer.onError(Status.INTERNAL
          .withDescription(e.getMessage())
          .asRuntimeException());
      }
    }

    @Override
    public void listOrders(ListOrdersRequest request, StreamObserver<Order> observer) {
      // Server streaming — send multiple orders
      orderRepository.findByUserId(request.getUserId())
        .forEach(order -> {
          observer.onNext(buildOrderProto(order));
        });
      observer.onCompleted();
    }
  }

Client implementation:
  @GrpcClient("order-service")  // references application.yml
  private OrderServiceGrpc.OrderServiceBlockingStub orderStub;

  // Blocking (sync) call
  Order order = orderStub.getOrder(
    GetOrderRequest.newBuilder().setOrderId(123L).build()
  );

  // Async call
  OrderServiceGrpc.OrderServiceFutureStub asyncStub = ...;
  ListenableFuture<Order> future = asyncStub.getOrder(request);

application.yml (client):
  grpc:
    client:
      order-service:
        address: static://order-service:9090
        negotiation-type: plaintext  # or TLS for production

GRPC ERROR HANDLING
====================

gRPC uses Status codes (different from HTTP status codes):

Status Code     │ HTTP Equivalent │ Meaning
────────────────┼─────────────────┼──────────────────────────────
OK              │ 200             │ Success
INVALID_ARGUMENT│ 400             │ Invalid request parameters
NOT_FOUND       │ 404             │ Resource not found
ALREADY_EXISTS  │ 409             │ Duplicate/conflict
PERMISSION_DENIED│403             │ Not authorized
UNAUTHENTICATED │ 401             │ Not authenticated
RESOURCE_EXHAUSTED│ 429           │ Rate limit exceeded
INTERNAL        │ 500             │ Server error
UNAVAILABLE     │ 503             │ Service down
DEADLINE_EXCEEDED│ 504            │ Timeout

Throwing errors:
  throw Status.NOT_FOUND
    .withDescription("Order " + id + " not found")
    .asRuntimeException();

Interceptors for global error handling:
  @Component
  public class ExceptionInterceptor implements ServerInterceptor {
    @Override
    public <Req, Resp> ServerCall.Listener<Req> interceptCall(...) {
      // wrap with try/catch, translate exceptions to gRPC Status
    }
  }

GRPC SECURITY
==============
1. TLS/mTLS for transport encryption
   grpc:
     server:
       security:
         certificate-chain: classpath:server.crt
         private-key: classpath:server.key

2. Interceptors for JWT authentication:
   @GrpcGlobalServerInterceptor
   public class AuthInterceptor implements ServerInterceptor {
     @Override
     public <Req, Resp> ServerCall.Listener<Req> interceptCall(...) {
       String token = metadata.get(AUTHORIZATION_KEY);
       validateJwt(token); // throw UNAUTHENTICATED if invalid
       return next.startCall(call, headers);
     }
   }

WHEN TO USE gRPC vs REST
=========================

Use gRPC when:
  ✓ Internal service-to-service communication
  ✓ High-performance / high-throughput required (10000s req/sec)
  ✓ Bi-directional or server-side streaming needed
  ✓ Strongly typed contracts are desired
  ✓ Polyglot environment (proto generates code for 10+ languages)
  ✓ Low latency is critical (e.g., trading, gaming backends)

Use REST when:
  ✓ Public external API (browsers, third parties)
  ✓ Simple CRUD with occasional traffic
  ✓ Human-readable, easily debuggable API needed
  ✓ Integration with legacy systems
  ✓ API consumption by mobile/web apps directly

INTERVIEW QUESTIONS
====================

Q: What is gRPC and why is it faster than REST?
A: gRPC is an RPC framework using HTTP/2 and Protobuf. Faster because:
   Protobuf is binary (smaller payload, faster serialization), HTTP/2 provides
   multiplexing and header compression, and streaming is natively supported.

Q: What are the 4 types of gRPC communication?
A: 1) Unary (request/response like REST), 2) Server streaming (client sends one
   request, server streams many responses), 3) Client streaming (client streams
   multiple requests, server sends one response), 4) Bidirectional streaming.

Q: How does Protobuf ensure backward compatibility?
A: Each field has a unique field number used in binary encoding. Adding new
   fields is backward compatible (old receivers ignore unknown fields). Never
   change field numbers or reuse deleted field numbers.

Q: What's the disadvantage of gRPC compared to REST?
A: Not browser-native (needs grpc-web proxy), binary format is not human-
   readable (harder to debug without tools), requires code generation toolchain,
   and has a steeper learning curve.

Q: What gRPC status code is equivalent to HTTP 404?
A: Status.NOT_FOUND — thrown as Status.NOT_FOUND.asRuntimeException()
