================================================================================
API VERSIONING IN MICROSERVICES
================================================================================

WHY API VERSIONING MATTERS
---------------------------
In a microservices system:
  - Multiple teams independently deploy their services
  - External consumers (mobile apps, third-party integrators) use your APIs
  - API changes must not break existing consumers
  - Consumers may update at different rates (old mobile app versions)

Without a versioning strategy: a single API change breaks all consumers.

KEY PRINCIPLE: Backward compatibility + Clear deprecation policy

────────────────────────────────────────────────────────────────────────────────

TYPES OF API CHANGES
=====================

BACKWARD-COMPATIBLE CHANGES (Non-breaking — safe in existing version):
  ✓ Adding a new optional field to a response
  ✓ Adding a new optional request parameter
  ✓ Adding a new endpoint
  ✓ Adding a new enum value (carefully — consumers must handle unknown values)

BREAKING CHANGES (Require a new version):
  ✗ Removing a field from a response
  ✗ Renaming a field
  ✗ Changing the type of a field (String → Integer)
  ✗ Adding a required request field
  ✗ Changing an HTTP verb (GET → POST)
  ✗ Changing a URL path
  ✗ Changing error response format

────────────────────────────────────────────────────────────────────────────────

VERSIONING STRATEGIES
======================

STRATEGY 1: URI VERSIONING (Most Common)
-----------------------------------------
Version number embedded in the URL path.

  /api/v1/users        → Original API
  /api/v2/users        → New version with breaking changes

Spring Boot implementation:
  @RestController
  @RequestMapping("/api/v1/users")
  public class UserControllerV1 { ... }

  @RestController
  @RequestMapping("/api/v2/users")
  public class UserControllerV2 { ... }

  Or using a shared controller with version-specific service:
  @GetMapping("/api/{version}/users/{id}")
  public ResponseEntity<?> getUser(@PathVariable String version,
                                    @PathVariable Long id) {
    if ("v1".equals(version)) return ResponseEntity.ok(userServiceV1.getUser(id));
    if ("v2".equals(version)) return ResponseEntity.ok(userServiceV2.getUser(id));
    return ResponseEntity.badRequest().build();
  }

Pros:
  ✓ Most visible — version clear in URL
  ✓ Easy to test with curl/Postman
  ✓ Simple to route at gateway level

Cons:
  ✗ "Dirty" URLs — purists argue version is metadata, not resource
  ✗ Can lead to many version URLs over time

STRATEGY 2: HEADER VERSIONING
------------------------------
Version passed in a custom HTTP header or Accept header.

  GET /api/users/123
  Header: API-Version: 2
  or
  Accept: application/vnd.myapp.v2+json

Spring Boot implementation:
  @GetMapping(value = "/users/{id}", headers = "API-Version=1")
  public ResponseEntity<UserV1DTO> getUserV1(@PathVariable Long id) { ... }

  @GetMapping(value = "/users/{id}", headers = "API-Version=2")
  public ResponseEntity<UserV2DTO> getUserV2(@PathVariable Long id) { ... }

Pros:
  ✓ Clean URLs
  ✓ Separation of version from resource identifier

Cons:
  ✗ Not visible in URL (harder to test in browser)
  ✗ Caching can be tricky (cache must vary on header)
  ✗ Less common → less tooling support

STRATEGY 3: QUERY PARAMETER VERSIONING
----------------------------------------
  GET /api/users/123?version=2
  GET /api/users/123?api-version=2.0

Spring Boot:
  @GetMapping("/users/{id}")
  public ResponseEntity<?> getUser(@PathVariable Long id,
                                    @RequestParam(defaultValue = "1") int version) {
    return switch (version) {
      case 1 -> ResponseEntity.ok(userServiceV1.getUser(id));
      case 2 -> ResponseEntity.ok(userServiceV2.getUser(id));
      default -> ResponseEntity.badRequest().build();
    };
  }

Pros: ✓ Simple; visible in URL; easy to test
Cons: ✗ Version mixed into query string with other params

STRATEGY 4: MEDIA TYPE / CONTENT NEGOTIATION
---------------------------------------------
  GET /api/users/123
  Accept: application/vnd.company.user-v2+json

Pros: ✓ RESTful purist approach; follows HTTP spec
Cons: ✗ Complex to implement; poor tooling support

RECOMMENDATION: URI versioning for most microservices teams.
  Simple, visible, easy to test, easy to route at gateway level.

────────────────────────────────────────────────────────────────────────────────

API VERSIONING IN API GATEWAY
================================
Route traffic to correct version at the gateway level:

  Spring Cloud Gateway route config:
  ```yaml
  spring:
    cloud:
      gateway:
        routes:
          - id: user-service-v1
            uri: lb://user-service
            predicates:
              - Path=/api/v1/users/**
          - id: user-service-v2
            uri: lb://user-service-v2
            predicates:
              - Path=/api/v2/users/**
  ```

This allows v1 and v2 to run as SEPARATE service deployments if needed.

DEPRECATION POLICY
===================

A proper API deprecation lifecycle:

1. Release v2 alongside v1
2. Announce v1 deprecation with sunset date (e.g., 6 months notice)
3. Add Deprecation header to v1 responses:
   Deprecation: Sun, 30 Jun 2024 00:00:00 GMT
   Sunset: Mon, 31 Dec 2024 00:00:00 GMT
   Link: </api/v2/users>; rel="successor-version"

4. Monitor v1 usage metrics — identify who's still using it
5. Notify consumers via email/changelog
6. After sunset date: return 410 Gone

In Spring Boot:
  @GetMapping("/api/v1/users/{id}")
  @Deprecated
  public ResponseEntity<UserV1DTO> getUserV1(..., HttpServletResponse response) {
    response.addHeader("Deprecation", "true");
    response.addHeader("Sunset", "Mon, 31 Dec 2024 00:00:00 GMT");
    response.addHeader("Link", "</api/v2/users/" + id + ">; rel=\"successor-version\"");
    return ResponseEntity.ok(userService.getUserV1(id));
  }

PROTOBUF BACKWARD COMPATIBILITY (gRPC Versioning)
===================================================

Protobuf is inherently designed for backward compatibility:

  Rules to maintain backward compatibility:
    1. Never change a field number
    2. Never reuse a field number of a deleted field
    3. Adding new fields: always safe (old clients ignore unknown fields)
    4. Removing fields: safe for wire format (use "reserved" keyword)
    5. Never change field types

  proto3 "reserved" keyword:
    message User {
      int64 id = 1;
      string email = 2;
      // old_name was field 3 — deleted, marked reserved
      reserved 3;
      reserved "old_name";
      string full_name = 4;  // new field — safe to add
    }

  Versioning gRPC services:
    package order.v1;
    service OrderService { ... }

    package order.v2;
    service OrderService { ... }

CONSUMER-DRIVEN CONTRACT TESTING
==================================
(Pact framework — prevents breaking API changes)

1. Consumer defines a Pact (contract): "I expect this endpoint with this response structure"
2. Pact published to Pact Broker
3. Provider must pass consumer's contract tests before deploying
4. If provider change breaks the contract → CI pipeline fails

This prevents breaking changes from reaching production.

Consumer test example:
  @Pact(consumer = "notification-service")
  public RequestResponsePact getOrderPact(PactDslWithProvider builder) {
    return builder
      .given("Order 123 exists")
      .uponReceiving("get order by id")
        .path("/api/v1/orders/123")
        .method("GET")
      .willRespondWith()
        .status(200)
        .body(new PactDslJsonBody()
          .numberType("id", 123)
          .stringType("status", "CONFIRMED")
        )
      .toPact();
  }

EVENT VERSIONING (Async APIs)
==============================
When using Kafka or message brokers, events also need versioning:

1. Include version in event payload:
   {
     "eventType": "OrderPlaced",
     "eventVersion": "2",
     "payload": { ... }
   }

2. Or use separate topics per version:
   "order-events-v1"
   "order-events-v2"

3. Avro + Schema Registry (Confluent):
   - Schemas registered in Schema Registry
   - Consumers can evolve independently using schema evolution rules
   - Backward/forward/full compatibility modes

────────────────────────────────────────────────────────────────────────────────

BEST PRACTICES SUMMARY
=======================
  1. Use URI versioning for REST APIs (/api/v1/, /api/v2/)
  2. Default to v1 if no version specified (graceful)
  3. Never remove/rename existing fields — only add
  4. Maintain at minimum 2 versions simultaneously during transitions
  5. Use Deprecation and Sunset headers to communicate timeline
  6. Monitor version usage metrics before sunsetting
  7. Use Consumer-Driven Contract Tests (Pact) to catch breaking changes
  8. For gRPC: never change field numbers; use "reserved" for deleted fields
  9. For events: include version in event payload or use Schema Registry

INTERVIEW QUESTIONS
====================

Q: How do you handle API versioning in microservices?
A: URI versioning (/api/v1/, /api/v2/) is most common. Key rules: never remove
   or rename fields in an existing version. Breaking changes go in a new version.
   Old version stays alive with a deprecation notice and sunset date.

Q: What's the difference between backward-compatible and breaking changes?
A: Adding new optional fields is backward-compatible (existing consumers work).
   Removing/renaming fields, changing types, or adding required fields are
   breaking changes that require a new API version.

Q: How do you prevent breaking changes in a CI/CD pipeline?
A: Consumer-Driven Contract Testing with Pact. Consumers define contracts;
   the provider must pass all consumer contracts before deployment.
   Any breaking change fails the pipeline.

Q: How do you version events in an event-driven system?
A: Include version in the event payload ("eventVersion": "2") or use separate
   topics per version. For Avro, use Confluent Schema Registry which enforces
   schema compatibility rules.

Q: How would you sunset an API version?
A: Add Deprecation and Sunset response headers, communicate timeline to
   consumers, monitor usage metrics to identify remaining users, notify them,
   then return 410 Gone after the sunset date. Maintain ≥ 6 months notice.
