================================================================================
SERVICE MESH: ISTIO & LINKERD
================================================================================

WHAT IS A SERVICE MESH?
------------------------
A service mesh is an infrastructure layer that handles service-to-service
communication in a microservices architecture. It offloads cross-cutting concerns
(observability, security, traffic management, resilience) from the application
code into the infrastructure.

THE PROBLEM IT SOLVES:
  In a microservices system with 50 services, every service needs:
    - mTLS for encryption between services
    - Retries and circuit breaking
    - Load balancing
    - Distributed tracing
    - Metrics collection
    - Rate limiting

  Without a service mesh:
    - Each service team implements these in application code
    - Different languages → different libraries → inconsistent behavior
    - Difficult to upgrade (must update 50 services)

  With a service mesh:
    - Infrastructure handles all of this automatically
    - Services are oblivious to it (zero application code changes)
    - Consistent behavior across all services regardless of language

SIDECAR PROXY PATTERN
======================

Service mesh uses the Sidecar pattern:
  - Every service pod gets an additional proxy container (sidecar)
  - ALL incoming and outgoing traffic for the service goes through the sidecar
  - Sidecar proxies form the "data plane"
  - Central control plane configures all sidecars

  ┌──────────────────────────────────────┐
  │  Kubernetes Pod                      │
  │  ┌──────────────┐  ┌──────────────┐ │
  │  │ App Container│←→│Sidecar Proxy │ │
  │  │ (Your code)  │  │ (Envoy/Linkerd-proxy) │
  │  └──────────────┘  └──────────────┘ │
  └──────────────────────────────────────┘
                             ↕ (all traffic flows through)
  ┌──────────────────────────────────────┐
  │  Another Pod                         │
  │  ┌──────────────┐  ┌──────────────┐ │
  │  │ App Container│←→│Sidecar Proxy │ │
  │  └──────────────┘  └──────────────┘ │
  └──────────────────────────────────────┘

The app doesn't know traffic is going through the sidecar.
The sidecar intercepts at the OS networking layer (iptables rules).

────────────────────────────────────────────────────────────────────────────────

SERVICE MESH ARCHITECTURE
===========================

DATA PLANE:
  - Collection of sidecar proxies
  - Handles actual traffic (routing, load balancing, TLS termination)
  - Istio uses Envoy proxy; Linkerd uses linkerd-proxy (Rust-based)

CONTROL PLANE:
  - Configures the data plane (what to do with traffic)
  - Issues mTLS certificates
  - Collects telemetry
  - Provides UI/API for configuration

  Istio control plane components:
    - Istiod: Combined control plane (merged Pilot, Citadel, Galley in Istio 1.5+)
      - Pilot: Service discovery, routing rules
      - Citadel: Certificate management (mTLS)
      - Galley: Configuration validation

ISTIO — THE COMPREHENSIVE SERVICE MESH
========================================

OVERVIEW:
  - Developed by Google, IBM, Lyft (2017)
  - Uses Envoy proxy as sidecar
  - Feature-rich but complex to operate
  - Ideal for large enterprises with complex requirements

KEY FEATURES:

1. TRAFFIC MANAGEMENT
   a) Load Balancing:
      - Round-robin (default)
      - Least connection
      - Random
      - Consistent hash (for session affinity)

   b) Traffic Splitting (Canary Deployments):
      VirtualService (Istio CRD):
      ```yaml
      apiVersion: networking.istio.io/v1alpha3
      kind: VirtualService
      metadata:
        name: order-service
      spec:
        hosts:
        - order-service
        http:
        - route:
          - destination:
              host: order-service
              subset: v1
            weight: 90
          - destination:
              host: order-service
              subset: v2
            weight: 10  # 10% of traffic goes to v2
      ```

   c) Circuit Breaker:
      DestinationRule:
      ```yaml
      apiVersion: networking.istio.io/v1alpha3
      kind: DestinationRule
      metadata:
        name: order-service
      spec:
        host: order-service
        trafficPolicy:
          outlierDetection:
            consecutive5xxErrors: 5
            interval: 30s
            baseEjectionTime: 30s
      ```

   d) Retry Policy:
      ```yaml
      retries:
        attempts: 3
        perTryTimeout: 2s
        retryOn: gateway-error,connect-failure,retriable-4xx
      ```

   e) Fault Injection (Testing):
      ```yaml
      fault:
        delay:
          percentage:
            value: 10
          fixedDelay: 5s  # Inject 5s delay to 10% of requests
      ```

2. OBSERVABILITY
   - Automatic distributed tracing (Jaeger/Zipkin) — zero code changes
   - Automatic metrics (Prometheus) for every service-to-service call
   - Access logs for all traffic
   - Kiali: Service mesh topology visualization UI

3. SECURITY
   - Automatic mTLS between all services (zero code changes)
   - Service identity based on SPIFFE/SPIRE standard
   - Authorization policies (who can call what)

   mTLS modes:
   - PERMISSIVE: Accepts both TLS and plaintext (migration period)
   - STRICT: Only mTLS allowed (fully secured)

   PeerAuthentication (enable mTLS):
   ```yaml
   apiVersion: security.istio.io/v1beta1
   kind: PeerAuthentication
   metadata:
     name: default
     namespace: production
   spec:
     mtls:
       mode: STRICT
   ```

   AuthorizationPolicy (service-to-service ACLs):
   ```yaml
   apiVersion: security.istio.io/v1beta1
   kind: AuthorizationPolicy
   metadata:
     name: allow-order-to-inventory
   spec:
     selector:
       matchLabels:
         app: inventory-service
     rules:
     - from:
       - source:
           principals: ["cluster.local/ns/default/sa/order-service"]
       to:
       - operation:
           methods: ["GET", "POST"]
   ```

LINKERD — THE LIGHTWEIGHT SERVICE MESH
========================================

OVERVIEW:
  - Created by Buoyant (2016), donated to CNCF
  - Uses linkerd-proxy (Rust-based, ultra-light)
  - Simpler than Istio, easier to operate
  - Fewer features but lower operational overhead
  - Ideal for teams wanting simplicity

LINKERD vs ISTIO:

Feature              │ Linkerd              │ Istio
─────────────────────┼──────────────────────┼───────────────────────
Proxy                │ linkerd-proxy (Rust) │ Envoy (C++)
Weight (memory/CPU)  │ Very lightweight     │ Heavier
Complexity           │ Simple               │ Complex (many CRDs)
Features             │ Core (mTLS, obs, LB) │ Full-featured
Traffic mgmt         │ Basic                │ Advanced (header routing, etc.)
Installation         │ linkerd CLI          │ Helm/Operator
WASM support         │ No                   │ Yes (Envoy filters)
Best for             │ Simplicity priority  │ Fine-grained control

LINKERD INSTALLATION:
  # Install CLI
  curl --proto '=https' --tlsv1.2 -sSfL https://run.linkerd.io/install | sh

  # Install to Kubernetes cluster
  linkerd install --crds | kubectl apply -f -
  linkerd install | kubectl apply -f -

  # Check
  linkerd check

  # Inject sidecar to a deployment
  kubectl get deploy my-service -o yaml | linkerd inject - | kubectl apply -f -
  # Or: annotate namespace for automatic injection
  kubectl annotate namespace default linkerd.io/inject=enabled

SERVICE MESH CAPABILITIES SUMMARY
===================================

Capability               │ Without Mesh              │ With Mesh
─────────────────────────┼───────────────────────────┼──────────────────────────
mTLS between services    │ App code, per service      │ Automatic, universal
Circuit Breaker          │ Resilience4j, per service  │ Configured in mesh CRDs
Retries                  │ App code                   │ Mesh-level, per route
Distributed tracing      │ SDK per service             │ Automatic via headers
Metrics (latency/RPS)    │ Manual instrumentation     │ Automatic for all traffic
Traffic splitting        │ Manual (K8s weight ingress)│ VirtualService weight rules
Fault injection          │ N/A (need chaos tools)     │ Built-in
Service topology view    │ External tool              │ Kiali (Istio), Viz (Linkerd)
Load balancing           │ K8s kube-proxy (L4)        │ L7 (application-aware)

WHEN TO USE A SERVICE MESH
============================

USE when:
  ✓ Large number of services (50+) where cross-cutting concerns must be consistent
  ✓ Security mandate: zero-trust networking, mTLS required
  ✓ Need for fine-grained traffic control (canary deploys, A/B testing)
  ✓ Polyglot environment (can't rely on language-specific libraries)
  ✓ Observability is critical and team doesn't want to instrument each service

AVOID when:
  ✗ Small number of services (< 10) — too much overhead
  ✗ Team doesn't have K8s expertise to operate the mesh
  ✗ Low traffic volume — overhead not justified
  ✗ Simple application where Resilience4j + Spring Sleuth suffices

INTERVIEW QUESTIONS
====================

Q: What is a service mesh?
A: An infrastructure layer that handles cross-cutting concerns for service-to-
   service communication: mTLS encryption, observability, retries, circuit
   breaking, and traffic management — all without changing application code.

Q: What is the Sidecar pattern in service mesh?
A: A proxy container is deployed alongside each service container in the same
   Pod. All traffic flows through the sidecar proxy, which implements the mesh
   capabilities transparently to the app.

Q: What's the difference between Istio and Linkerd?
A: Istio is feature-rich (advanced traffic management, WASM filters) but complex,
   using Envoy proxy. Linkerd is lightweight with a Rust-based proxy, simpler to
   operate, with fewer but sufficient features. Choose Linkerd for simplicity,
   Istio for fine-grained control.

Q: How does Istio implement traffic splitting for canary deployments?
A: Via VirtualService and DestinationRule CRDs. VirtualService defines weighted
   routes (e.g., 90% to v1, 10% to v2). DestinationRule defines the subsets
   (v1, v2) that correspond to different pod label selectors.

Q: How does a service mesh provide mTLS without changing application code?
A: The sidecar proxy handles TLS termination and initiation at the OS network
   level. The app container communicates as if it's plain HTTP/gRPC. The sidecar
   intercepts all traffic via iptables rules, wraps it in mTLS, and handles
   certificate management via the control plane.
