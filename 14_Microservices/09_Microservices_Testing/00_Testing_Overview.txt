MICROSERVICES TESTING OVERVIEW
================================================================================

TESTING CHALLENGES IN MICROSERVICES
-------------------------------------
In a monolith: run the app locally, test everything.
In microservices: 50 services, each owned by different teams.
  - Cannot run all 50 services locally
  - Services evolve independently — how to detect breaking changes?
  - Integration tests are slow and flaky
  - End-to-end tests are expensive to maintain

The Testing Pyramid for Microservices:

            ┌─────────────────────┐
            │   E2E / UI Tests    │ ← Few (5-10), slow, expensive
            │  (full environment) │   Critical user journeys only
            ├─────────────────────┤
            │ Integration Tests   │ ← Some (20-30%), test real infra
            │ (TestContainers)    │   DB, Kafka, Redis
            ├─────────────────────┤
            │  Contract Tests     │ ← Medium, test API agreements
            │  (Pact / Spring)    │   Prevents breaking changes
            ├─────────────────────┤
            │    Unit Tests       │ ← Many (70%), fast, isolated
            │   (JUnit, Mockito)  │   Business logic focus
            └─────────────────────┘

TEST TYPES AND THEIR PURPOSE
==============================

Test Type          │ Tests What           │ Speed  │ Isolation │ Infrastructure
───────────────────┼──────────────────────┼────────┼───────────┼───────────────
Unit               │ Single class/method  │ ms     │ Full mock │ None (pure JVM)
─── ───────────────┼──────────────────────┼────────┼───────────┼───────────────
Slice (Spring)     │ Spring layer (web,   │ Fast   │ Partial   │ Embedded
                   │  data, security)     │        │           │ (H2, mock MVC)
───────────────────┼──────────────────────┼────────┼───────────┼───────────────
Contract           │ API contracts        │ Fast   │ Stub/Mock │ None (stubs)
(Producer side)    │ (does my service     │        │           │
(Consumer side)    │  fulfill contracts?) │        │           │
───────────────────┼──────────────────────┼────────┼───────────┼───────────────
Integration        │ Service + real infra │ Slow   │ None      │ Docker
(TestContainers)   │ DB, Kafka, Redis     │        │           │ containers
───────────────────┼──────────────────────┼────────┼───────────┼───────────────
Component          │ Whole service in     │ Slow   │ Stubbed   │ TestContainers
                   │ isolation            │        │ dependencies│ for own infra
───────────────────┼──────────────────────┼────────┼───────────┼───────────────
E2E                │ Full user journeys   │ Very   │ None      │ Full env
                   │ across services      │ Slow   │           │

INTERVIEW QUESTIONS
====================

Q: How does the testing pyramid differ for microservices vs monolith?
A: The pyramid structure is similar (many unit, some integration, few E2E) but
   contract tests become critical in microservices — they detect breaking API
   changes before deployment. E2E tests are more expensive (need multiple services)
   and more flaky. TestContainers enables realistic integration tests without
   full environment. Consumer-Driven Contract tests can partially replace E2E.

Q: What are the main challenges of testing microservices?
A: Cannot run all dependencies locally. Services evolve independently causing
   integration failures in production. E2E tests are slow and fragile. Contract
   tests (Pact) help detect breaking changes early. TestContainers enables
   realistic integration tests with actual databases/brokers.
