MICROSERVICES SECURITY OVERVIEW
================================================================================

SECURITY SURFACE IN MICROSERVICES
-----------------------------------
In a monolith, security is centralized — one entry point, one trust boundary.
In microservices, attack surface expands:
  - Multiple service endpoints
  - Inter-service communication channels
  - Distributed secret management
  - Multiple databases and storage
  - Third-party integrations per service

Security must be applied at multiple layers simultaneously.

────────────────────────────────────────────────────────────────────────────────

THE LAYERED SECURITY MODEL
============================

Layer 1: PERIMETER (External boundary)
  - API Gateway authentication (JWT/OAuth2)
  - Rate limiting and DDoS protection
  - WAF (Web Application Firewall)
  - TLS termination

Layer 2: SERVICE-TO-SERVICE (East-West traffic)
  - mTLS (Mutual TLS) — service identity verification
  - Service mesh authorization policies
  - JWT propagation between services

Layer 3: DATA (At-rest and in-transit)
  - Encryption at rest (database, object storage)
  - TLS in transit (all internal service calls)
  - Secrets management (Vault, AWS Secrets Manager)

Layer 4: AUTHORIZATION (Within services)
  - RBAC (Role-Based Access Control)
  - ABAC (Attribute-Based Access Control)
  - Scope-based authorization (OAuth2 scopes)

Layer 5: AUDIT (Detect and respond)
  - Centralized logging with security events
  - Distributed tracing for request chain
  - SIEM integration

────────────────────────────────────────────────────────────────────────────────

SECURITY PATTERNS OVERVIEW
============================

Pattern                  │ Purpose
─────────────────────────┼────────────────────────────────────────────────────
JWT + OAuth2             │ Stateless authentication and authorization
mTLS                     │ Mutual service authentication (east-west traffic)
API Gateway Security     │ Centralized external auth, rate limiting
RBAC / ABAC              │ Fine-grained authorization within services
Secrets Management       │ Store and rotate credentials securely
Zero Trust               │ Never trust, always verify — even internal traffic
Defense in Depth         │ Multiple security layers, no single point of failure
────────────────────────────────────────────────────────────────────────────────

ZERO TRUST ARCHITECTURE
=========================

Traditional: "Trust but verify" — internal network is trusted
Zero Trust:  "Never trust, always verify" — every request verified regardless of origin

Principles:
  1. Verify every request (authentication) regardless of network location
  2. Use least privilege access (minimum permissions needed)
  3. Assume breach (design as if attacker is already inside)
  4. Micro-segment the network (service-level policies)

Implementation:
  - mTLS between ALL services (even internal)
  - JWT tokens validated at every service hop
  - Service mesh authorization policies (Istio AuthorizationPolicy)
  - Short-lived credentials with automatic rotation

────────────────────────────────────────────────────────────────────────────────

KEY SECURITY CONCEPTS
======================

Authentication (AuthN): Verify WHO you are (identity)
  → JWT, OAuth2, mTLS certificates, API keys

Authorization (AuthZ): Verify WHAT you're allowed to do (permissions)
  → Scopes, roles, RBAC, ABAC, policy-based access

Encryption in Transit: All communication over TLS 1.2+
  → HTTPS for external, mTLS for internal

Encryption at Rest: DB encryption, object storage encryption
  → PostgreSQL TDE, AWS RDS encryption, S3 server-side encryption

Secrets Management: Never hardcode credentials
  → HashiCorp Vault, AWS Secrets Manager, Kubernetes Secrets (encrypted etcd)

INTERVIEW QUESTIONS
====================

Q: How does security differ in microservices vs monoliths?
A: In a monolith, security is centralized at one entry point. In microservices,
   security must be applied at every layer: perimeter (API gateway), east-west
   service-to-service (mTLS), within services (RBAC/ABAC), and at data layer
   (encryption at rest and in transit). The attack surface is much larger.

Q: What is Zero Trust architecture?
A: Never trust any request by default — verify identity and authorization for
   every request, regardless of network origin (even internal). Uses mTLS for
   service identity, JWT for user identity, short-lived credentials, and
   least-privilege access policies.

Q: What is the difference between authentication and authorization?
A: Authentication (AuthN) verifies WHO you are — JWT validation, mTLS certificate.
   Authorization (AuthZ) verifies WHAT you can do — checking if the authenticated
   identity has the required role/scope/permission for the requested operation.
