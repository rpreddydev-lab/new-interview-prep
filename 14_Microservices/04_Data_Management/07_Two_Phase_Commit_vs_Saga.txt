TWO-PHASE COMMIT (2PC) vs SAGA
================================================================================

TWO-PHASE COMMIT (2PC)
-----------------------
2PC is a distributed transaction protocol that ensures all participants either
COMMIT or ROLLBACK together. Uses a central COORDINATOR.

PHASE 1 — PREPARE:
  Coordinator sends "Prepare" to all participants
  Each participant:
    - Executes the transaction up to commit point (write redo log, acquire locks)
    - Responds "Yes" (can commit) or "No" (cannot commit)

PHASE 2 — COMMIT or ROLLBACK:
  If ALL participants voted "Yes":
    Coordinator sends "Commit" → all participants commit
  If ANY participant voted "No":
    Coordinator sends "Rollback" → all participants rollback

Timeline:
  Coordinator → [Prepare] → Participant A (locks row, votes Yes)
  Coordinator → [Prepare] → Participant B (locks row, votes Yes)
  Coordinator → [Commit]  → Participant A (commits, releases lock)
  Coordinator → [Commit]  → Participant B (commits, releases lock)

PROBLEMS WITH 2PC IN MICROSERVICES:
  1. Blocking protocol: resources locked throughout the protocol
     → Long lock hold times → reduced throughput
  2. Coordinator failure: if coordinator crashes after Prepare but before Commit
     → Participants stuck holding locks indefinitely (blocking failure)
  3. Tight coupling: all services must participate in coordinator's protocol
  4. Single point of failure: coordinator failure = system halt
  5. Network partitions: participants can't know if to commit or abort
  6. Not suitable for long-running transactions (minutes, hours)

────────────────────────────────────────────────────────────────────────────────

3-PHASE COMMIT (3PC) — BRIEF MENTION
======================================
Adds a "Pre-commit" phase to reduce blocking.
Still has problems in asynchronous networks.
Rarely used in practice — complexity outweighs benefits.

SAGA vs 2PC COMPARISON
========================

Dimension           │ 2PC                          │ Saga
────────────────────┼──────────────────────────────┼──────────────────────────
Consistency         │ Strong (ACID)                │ Eventual consistency
Coupling            │ Tight (coordinator required) │ Loose (events/messages)
Scalability         │ Poor (locks, blocking)       │ Good (async, no locks)
Availability        │ Lower (coordinator SPOF)     │ Higher
Duration            │ Short only (seconds)         │ Any duration (minutes/hours)
Language/DB         │ Must support XA protocol     │ Any DB/language
Failure handling    │ Automatic (rollback)         │ Explicit compensations
Complexity          │ Infrastructure complexity    │ Business logic complexity
Suitable for        │ Single-service, same DB      │ Cross-service transactions

────────────────────────────────────────────────────────────────────────────────

TCC — TRY-CONFIRM-CANCEL
==========================
A pattern that sits between 2PC and Saga:
  - TRY: Reserve/tentatively allocate resources (don't fully commit)
  - CONFIRM: Confirm the reservation (finalize the transaction)
  - CANCEL: Cancel the reservation (release the hold)

Example: Hotel booking
  TRY:     Reserve room (mark as tentatively held)
  CONFIRM: Complete booking (charge credit card, room is booked)
  CANCEL:  Release reservation (room available again)

TCC vs 2PC:
  - No central coordinator required
  - Services implement their own try/confirm/cancel logic
  - More flexible — can be retried at business level

TCC vs Saga:
  - TCC provides better atomicity (resources held until confirm)
  - Saga uses compensating transactions (undo what was done)
  - TCC: RESERVE then CONFIRM; Saga: DO then UNDO IF NEEDED

────────────────────────────────────────────────────────────────────────────────

WHEN TO USE WHAT
==================

Use 2PC when:
  ✓ Single service, multiple data sources (e.g., multiple DBs in one service)
  ✓ Strict ACID guarantees needed
  ✓ Short transactions only
  ✓ All participants support XA (Java EE JTA, database XA protocol)

Use Saga when:
  ✓ Cross-service transactions in microservices
  ✓ Long-running transactions
  ✓ High availability required
  ✓ Polyglot services (different DBs, languages)

Use TCC when:
  ✓ Need stronger atomicity than Saga
  ✓ Resources can be "reserved" before commit
  ✓ Avoiding compensation transactions (prefer prevent-then-confirm over do-then-undo)

XA TRANSACTIONS IN SPRING (JTA)
==================================

Spring Boot supports XA (distributed ACID) within a single service using JTA:

  # pom.xml
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jta-atomikos</artifactId>
  </dependency>

  # Use case: Single service that must write to two databases atomically
  @Transactional  # JTA transaction coordinator
  public void transferBetweenDatabases() {
    primaryDataSource.write(data1);
    secondaryDataSource.write(data2);
    // Either both commit or both rollback
  }

Note: This is within ONE service — not across service boundaries.
For cross-service transactions, use Saga.

INTERVIEW QUESTIONS
====================

Q: Why is 2PC not suitable for microservices?
A: 2PC requires a central coordinator and resource locks throughout the protocol.
   In microservices: coordinator is a single point of failure, locks reduce
   throughput, services must support XA, long-running distributed transactions
   hold locks for too long, and network partitions can leave participants blocked.

Q: How does Saga differ from 2PC?
A: Saga uses local transactions with compensating transactions for rollback.
   No central coordinator, no distributed locks. Provides eventual consistency
   rather than strong consistency. Better availability, scalability, and
   suitability for long-running workflows.

Q: What is the TCC pattern?
A: Try-Confirm-Cancel. Services expose three operations: Try (reserve resources
   tentatively), Confirm (finalize), Cancel (release reservation). Provides
   stronger atomicity than Saga by preventing over-commitment, without the
   blocking of 2PC.

Q: When would you still use 2PC in a microservices environment?
A: Within a single service that needs to write to multiple data stores atomically
   (e.g., PostgreSQL + Kafka within one service boundary using JTA/Atomikos).
   Never for cross-service coordination.
