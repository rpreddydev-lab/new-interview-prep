================================================================================
EVENTUAL CONSISTENCY
================================================================================

DEFINITION
-----------
Eventual consistency guarantees that, given no new updates, all replicas/nodes
will eventually converge to the same value. There is NO guarantee of WHEN this
convergence happens — it could be milliseconds or seconds.

In microservices, services that communicate asynchronously via events are
eventually consistent: after one service updates its data and publishes an event,
other services will eventually update their data models — but not instantly.

────────────────────────────────────────────────────────────────────────────────

EVENTUAL CONSISTENCY vs STRONG CONSISTENCY
============================================

Strong Consistency:
  - After a write, all reads return the updated value immediately
  - Guaranteed by locking, 2PC, synchronous replication
  - Costs: higher latency, reduced availability (locks, coordination overhead)
  - Example: Bank transfer — balance updated instantly, visible everywhere

Eventual Consistency:
  - After a write, reads may temporarily return stale data
  - Data converges over time (typically milliseconds to seconds)
  - Benefits: higher availability, lower latency, partition tolerance
  - Example: Social media like count — may show 999 while actual is 1000

────────────────────────────────────────────────────────────────────────────────

WHERE EVENTUAL CONSISTENCY APPEARS IN MICROSERVICES
======================================================

1. SAGA PATTERN
   During a saga, the system is in an intermediate state:
   - Order created (Order Service)
   - Inventory not yet reserved (InventoryService event not yet processed)
   → System temporarily inconsistent until saga completes

2. CQRS READ MODELS
   Write model updated → event published → read model updated asynchronously
   → Brief window where read model shows stale data

3. EVENT-DRIVEN BETWEEN SERVICES
   UserService updates user email → emits UserUpdatedEvent
   → OrderService read model updates customer email... eventually
   → Brief period: OrderService shows old email

4. REPLICATED DATA
   Service A has a copy of User data for quick access
   → User changes their name in UserService
   → Service A's copy is stale until it receives the update event

────────────────────────────────────────────────────────────────────────────────

HANDLING STALE READS — PATTERNS
==================================

1. RETURN DATA IN COMMAND RESPONSE
   Don't immediately query after a write — use the write response:
   
   ✗ BAD:
   POST /orders → 201 Created {orderId: 123}
   GET /orders/123 → 404 (read model not yet updated!)

   ✓ GOOD:
   POST /orders → 201 Created {orderId: 123, status: "PENDING", total: 150.00}
   → Use this data; don't query immediately

2. DUAL READ STRATEGY
   - First try read model (fast, may be stale)
   - For freshness-critical reads, query the write model
   - For search/list/analytics, read model is fine

   @GetMapping("/{id}")
   public OrderDTO getOrder(@PathVariable Long id) {
     // Use write model for individual ID lookups (strong consistency)
     return orderRepository.findById(id)
       .map(OrderDTO::from)
       .orElseThrow(() -> new NotFoundException("Order not found"));
   }

   @GetMapping  // List/search uses eventual read model
   public Page<OrderReadModel> listOrders(Pageable pageable) {
     return orderSearchRepository.findAll(pageable);
   }

3. OPTIMISTIC UI
   Update UI immediately based on the expected state
   If server-sent event confirms, great
   If failure event arrives, rollback UI
   Example: Chat app shows message immediately ("sending...") before server confirms

4. POLLING
   After write, poll until read model reflects the update
   Maximum N attempts with delay before showing "processing..."

5. WEBSOCKET / SSE NOTIFICATIONS
   Server pushes update to client when read model is ready
   Client doesn't need to poll

CONFLICT RESOLUTION — CONCURRENT UPDATES
==========================================

When two services update the same logical data:

Last Write Wins (LWW):
  Highest timestamp wins.
  Simple, but can lose data if clocks are skewed.

Vector Clocks:
  Track causality — each event has a version vector.
  Detects concurrent conflicting updates.
  Used by Riak, DynamoDB.

CRDTs (Conflict-free Replicated Data Types):
  Data structures designed to merge automatically without conflicts.
  Examples:
    - Grow-only counter (G-Counter): increment only, merge by max
    - 2P-Set: add + remove operations that commute
  Used in: distributed counters, shopping carts, collaborative text

Domain-specific resolution:
  - For inventory: max(reservations) — conservative
  - For prices: latest update wins
  - For user profile: latest-timestamp-wins

────────────────────────────────────────────────────────────────────────────────

WHAT REQUIRES STRONG CONSISTENCY vs CAN ACCEPT EVENTUAL
=========================================================

Strong Consistency Required:
  ✓ Payment processing (can't double-charge)
  ✓ Inventory reservation (can't oversell)
  ✓ Authentication/authorization (security critical)
  ✓ Financial account balances

Eventual Consistency Acceptable:
  ✓ Product catalog updates (price change visible in 5 seconds is OK)
  ✓ User profile updates (old name shows for 1 second is OK)
  ✓ Social metrics (like counts, view counts)
  ✓ Search indexes
  ✓ Recommendation updates
  ✓ Analytics dashboards

INTERVIEW QUESTIONS
====================

Q: What is eventual consistency and when is it acceptable?
A: Data will converge to a consistent state eventually, but reads may return
   stale data temporarily. Acceptable for: product catalogs, user profiles,
   recommendations, analytics. NOT acceptable for: payment, inventory reservation,
   authentication.

Q: How do you handle the read-after-write problem with eventual consistency?
A: Return the necessary data in the write response so clients don't need to
   immediately query. For freshness-critical reads, query the write (command)
   model. For search/list queries, the eventually-consistent read model is fine.

Q: What are CRDTs?
A: Conflict-free Replicated Data Types — data structures that can be merged
   automatically without conflicts. Grow-only counters, two-phase sets. Used
   for distributed counters, shopping carts, collaborative features where
   concurrent updates from multiple nodes must converge deterministically.
