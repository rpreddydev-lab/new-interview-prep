MICROSERVICES PATTERNS OVERVIEW
================================================================================

WHAT ARE MICROSERVICES PATTERNS?
----------------------------------
Patterns are proven solutions to recurring problems in microservices architecture.
They encode collective wisdom from teams that have faced and solved these problems.

Patterns in this section address:
  - Migrating from monolith (Strangler Fig)
  - Infrastructure concerns alongside services (Sidecar, Ambassador)
  - Client-specific APIs (Backend for Frontend)
  - Data consistency across services (Outbox, Inbox)
  - Safe cross-service calls (Anti-Corruption Layer)
  - Exactly-once semantics (Idempotency)

CHOOSING THE RIGHT PATTERN
============================

"I need to migrate from monolith without big bang rewrite"
  → Strangler Fig Pattern

"All my services need retry logic, circuit breakers, telemetry"
  → Sidecar / Service Mesh (Istio/Linkerd)

"I need different APIs for my mobile app vs web app"
  → Backend for Frontend (BFF)

"I publish events from DB writes but need atomicity"
  → Outbox Pattern

"My Kafka consumer processes the same event twice on restart"
  → Inbox / Idempotency Pattern

"My service calls a legacy system with a different domain model"
  → Anti-Corruption Layer

INTERVIEW QUESTIONS
====================

Q: Name 5 important microservices patterns and when to use each.
A: 1. Strangler Fig — when migrating from a monolith incrementally without a
   full rewrite. 2. Outbox — when you need atomic save + event publish (no dual
   write). 3. Sidecar — when you want to add cross-cutting concerns (TLS, retry,
   tracing) without modifying application code. 4. BFF — when mobile and web
   have different API needs, avoid over-fetching. 5. Anti-Corruption Layer —
   when integrating with a legacy system that has a different domain model.
