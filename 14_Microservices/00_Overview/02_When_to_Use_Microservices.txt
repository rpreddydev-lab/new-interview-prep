================================================================================
WHEN TO USE MICROSERVICES
================================================================================

OVERVIEW
--------
Microservices are NOT a silver bullet. Choosing them incorrectly leads to
unnecessary complexity. This guide covers the signals that indicate microservices
are the right choice, and when to stay with a monolith.

THE GOLDEN RULE
---------------
"Don't start with microservices. Start with a monolith, understand the domain,
then extract services when you hit real pain points."
                                             — Martin Fowler, Sam Newman

────────────────────────────────────────────────────────────────────────────────

SIGNALS THAT MICROSERVICES ARE NEEDED
======================================

1. INDEPENDENT SCALING REQUIREMENTS
   Problem: One component uses 10x more resources than others.
   Example: In an e-commerce app, the ProductSearch service needs 50x more
            compute than the UserProfile service.
   Microservices Solution: Scale ProductSearch independently without scaling
   everything else.

2. INDEPENDENT DEPLOYMENT FREQUENCY
   Problem: Deployments are bottlenecked because many teams work on one codebase.
   Example: Payment team needs to deploy 5 times/day; Reporting team deploys
            once a month. With a monolith, every Payment deploy triggers a full
            regression test for Reporting too.
   Microservices Solution: PaymentService deploys independently.

3. TEAM SIZE AND AUTONOMY (CONWAY'S LAW)
   Problem: Large teams stepping on each other's changes.
   Rule: If you need more than ~8-10 people on a single service, it's too big.
   Microservices Solution: Small, autonomous teams ("two-pizza teams" at Amazon).
   Guideline: Number of microservices ≈ Number of autonomous teams.

4. TECHNOLOGY HETEROGENEITY
   Problem: Different parts of the system need different technologies.
   Example:
     - ML recommendations → Python (scikit-learn, TensorFlow)
     - Real-time chat → Node.js (event-driven, WebSockets)
     - Financial calculations → Java (type safety, precision)
     - Data pipeline → Go (performance)
   Microservices Solution: Each service uses best-fit technology.

5. FAULT ISOLATION REQUIREMENTS
   Problem: A bug in the Reporting module crashes the entire app including
            the critical Checkout flow.
   Microservices Solution: ReportingService failure doesn't affect
   CheckoutService. Circuit breakers protect dependencies.

6. DOMAIN COMPLEXITY WITH CLEAR BOUNDED CONTEXTS
   Problem: The codebase has clear boundaries (Orders, Payments, Inventory)
            but they're muddled together in a monolith.
   Microservices Solution: DDD Bounded Contexts become service boundaries.
   Prerequisite: Domain must be well-understood first!

7. HIGH SECURITY/COMPLIANCE ISOLATION NEEDS
   Problem: Payment processing (PCI-DSS) must be strictly isolated from
            other systems.
   Microservices Solution: PaymentService runs in a separate, hardened
   environment with strict access controls.

────────────────────────────────────────────────────────────────────────────────

WHEN NOT TO USE MICROSERVICES
==============================

1. SMALL TEAM (< 5-6 ENGINEERS)
   - Microservices overhead (CI/CD, service registry, observability) consumes
     too much of a small team's capacity
   - Small teams can't effectively own multiple services
   - A modular monolith is better

2. EARLY-STAGE PRODUCT / UNCLEAR DOMAIN
   - If you don't understand the domain well, you'll draw the wrong service
     boundaries and spend months refactoring
   - "Premature decomposition" is costly
   - Rule: Build the monolith first, extract when boundaries are proven

3. NO DEVOPS MATURITY
   - Microservices require: CI/CD pipelines, container orchestration (K8s),
     distributed tracing, centralized logging, health checks
   - Without these, microservices become unmanageable
   - You need: Docker, Kubernetes, Helm, Prometheus, Jaeger, ELK Stack
   - Cost: significant infrastructure investment

4. SIMPLE / CRUD-HEAVY APPLICATION
   - If the app is mostly read/write operations on data with simple logic,
     a monolith with a good ORM and database is more appropriate

5. STRONG CONSISTENCY REQUIREMENTS
   - If your domain requires ACID transactions spanning multiple entities
     constantly (e.g., double-entry bookkeeping across many accounts), a
     single-database monolith handles this naturally
   - Microservices require Saga pattern for distributed transactions — complex

6. STARTUP / MVP
   - Need to move fast, iterate quickly, pivot easily
   - Microservices slow down initial development
   - Facebook, Twitter, LinkedIn, Airbnb all started as monoliths

────────────────────────────────────────────────────────────────────────────────

THE MICROSERVICES PREMIUM
==========================

Martin Fowler coined "Microservices Premium":
  - Microservices add significant overhead (infra, tooling, distributed systems)
  - You only get value when productivity gains from independence > premium cost
  - Small/simple systems: Monolith always wins
  - Large/complex systems: Microservices premium is worth it

                   Productivity
                       │
          Monolith───╗ │
                     ║ │
                     ║ │                    ╔══ Microservices
                     ╚═╪════════════════════╝
                       │           Complexity/Scale

Below the crossover: Monolith wins
Above the crossover: Microservices wins

DECISION FRAMEWORK
===================

Use this checklist before choosing microservices:

  □ Is the team large enough (8+ per bounded context)?
  □ Do different components genuinely need different scaling?
  □ Are there multiple teams that need to deploy independently?
  □ Do you have solid CI/CD pipelines?
  □ Is container orchestration (K8s) or serverless available?
  □ Is distributed tracing and centralized logging set up?
  □ Is the domain well-understood with clear boundaries?
  □ Is there operational maturity to run distributed systems?

If you checked < 4: Start with a modular monolith.
If you checked 4-6: Selective extraction (Strangler Fig) is appropriate.
If you checked all: Full microservices is justified.

REAL-WORLD CASE STUDIES
========================

AMAZON:
  - Started as a monolith in 1995
  - Moved to microservices ~2001-2004
  - Today: Hundreds of services for a single product page
  - Key driver: Teams stepping on each other, slow deployments

NETFLIX:
  - Moved from monolith to microservices 2008-2012
  - Trigger: AWS outage took down all of Netflix (single point of failure)
  - Today: 700+ microservices
  - Key driver: Fault isolation and global scale

UBER:
  - Started with a single Python monolith
  - Moved to microservices ~2014 for different geo regions
  - Later faced "monorepo microservices" challenges
  - Key driver: Geographic scaling and team growth

SHOPIFY:
  - Chose a "modular monolith" approach
  - Used pods (self-contained modules with own databases)
  - Avoided full microservices complexity while gaining modularity
  - Key driver: Balance between speed and structure

AIRBNB:
  - Went microservices, later experienced "service sprawl"
  - 2000+ services became hard to manage
  - Consolidated back to fewer, more powerful services
  - Lesson: Don't over-decompose

────────────────────────────────────────────────────────────────────────────────

COMMON MISTAKES TO AVOID
=========================

1. DISTRIBUTED MONOLITH
   "We use microservices but they all share a database and call each other
   synchronously in long chains." → Worst of both worlds.
   Fix: Each service owns its data, use async events where possible.

2. NANOSERVICES
   "Each function is a service" → 10,000 tiny services with enormous overhead.
   Fix: Right-size services around bounded contexts/business capabilities.

3. PREMATURE EXTRACTION
   "We don't understand the domain but extracted 50 services."
   Fix: Understand domain first. Wrong service boundaries = massive refactoring.

4. IGNORING OPERATIONAL OVERHEAD
   "We have microservices but no CI/CD, no K8s, no monitoring."
   Fix: Invest in DevOps infrastructure before/with microservices.

5. CHATTY SERVICES
   "Order service calls Inventory service calls Pricing service calls
   Discount service for every request" → Network latency adds up.
   Fix: Consider denormalization, caching, or merging chatty services.

INTERVIEW QUESTIONS
====================

Q: When would you recommend microservices vs a monolith?
A: I'd recommend microservices when there are multiple large teams that need
   to deploy independently, different components have different scaling needs,
   and the team has the operational maturity (CI/CD, K8s, observability).
   For early-stage or small teams, a modular monolith is almost always better.

Q: What are the hidden costs of microservices?
A: Distributed systems complexity, network latency and failures, distributed
   tracing overhead, polyglot data consistency, operational tooling (K8s,
   Helm, Prometheus), and the cognitive overhead of service boundaries.

Q: What's the "Microservices Premium"?
A: The additional complexity and operational overhead that microservices impose.
   It's only worth paying when the scale/team size makes the productivity
   gains from independence larger than this overhead.

Q: Have you seen microservices fail? What caused it?
A: Common failure modes are: distributed monolith (shared database, tight
   coupling), premature extraction before domain is understood, over-
   decomposition leading to service sprawl, and missing observability
   infrastructure making debugging nearly impossible.
