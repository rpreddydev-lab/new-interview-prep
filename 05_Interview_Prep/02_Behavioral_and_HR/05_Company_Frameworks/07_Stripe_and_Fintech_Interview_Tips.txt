TECHNICAL — JAVA / PAYMENTS / DISTRIBUTED SYSTEMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PAYMENTS-SPECIFIC JAVA CONCEPTS (must know deeply):

  IDEMPOTENCY:
    → Idempotency key: client-generated UUID sent with every request
    → Server stores (key, response) in DB; returns cached response on retry
    → Must be persisted BEFORE processing, not after
    → Implementation: unique constraint on idempotency_key column
    → Stripe's entire API is idempotent — know this cold

  EXACTLY-ONCE SEMANTICS:
    → In Kafka: transactions + idempotent producers + transactional consumers
    → In REST: idempotency key + conditional update (optimistic lock)

  DISTRIBUTED TRANSACTIONS:
    → Stripe avoids distributed transactions using the Outbox pattern
    → Event is written to outbox table in same DB transaction as state change
    → Separate relay process reads outbox and publishes to Kafka

  FINANCIAL PRECISION:
    → NEVER use float or double for money — use BigDecimal or integer cents
    → Currency-aware arithmetic, rounding mode (HALF_UP for most financial)
    → Store amounts as minor units (cents, paise) in integer columns

  STRIPE-RELEVANT TECHNICAL QUESTIONS:
    Q: How would you implement an idempotent payment API in Spring Boot?
    Q: What happens if a network timeout occurs after you charge a card
       but before you return the response? How do you handle it?
    Q: How would you design a webhook delivery system with guaranteed
       at-least-once delivery?
    Q: Explain optimistic vs pessimistic locking. When would you use each
       in a payment processing context?
    Q: How would you implement a rate limiter for Stripe's public API?
       (Token bucket vs sliding window — when to use each?)
    Q: How do you prevent double-charges in a distributed payment system?

TIPS FOR STRIPE AND FINTECH INTERVIEWS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. IDEMPOTENCY is the single most important topic. Understand it deeply
     (request deduplication, key lifecycle, race conditions, expiry).

  2. CORRECTNESS over speed. At Stripe, a bug in a financial calculation
     is catastrophic. Show you think about edge cases obsessively.

  3. API DESIGN MATTERS. Stripe is famous for its API quality.
     If asked to design an API, think about:
     - Consistent naming conventions
     - Pagination strategy (cursor-based > offset for large sets)
     - Error response format (code, message, param)
     - Versioning strategy

  4. READ STRIPE'S ENGINEERING BLOG (stripe.com/blog/engineering):
     → Articles on: payments infrastructure, IDempotency, Sorbet (type checker),
       their Java to Ruby to Go migration stories

  5. WRITTEN CULTURE: Mention design docs, ADRs, RFCs in your stories.
     "I wrote a detailed RFC comparing three approaches..." is gold.

  6. KNOW BigDecimal in Java:
     BigDecimal amount = new BigDecimal("9.99");  // ← String constructor!
     BigDecimal result = amount.multiply(new BigDecimal("1.1"))
                               .setScale(2, RoundingMode.HALF_UP);
     // NEVER: double amount = 9.99; (binary floating point error)
