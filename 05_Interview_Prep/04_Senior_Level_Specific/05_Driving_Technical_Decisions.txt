================================================================================
DRIVING TECHNICAL DECISIONS — INTERVIEW PREPARATION
================================================================================
Purpose: Demonstrate decision-making capability — how you analyze options,
         involve stakeholders, make the call, and live with the outcome.
         This is one of the hardest senior signals to fake.
================================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
THE DECISION-MAKING FRAMEWORK INTERVIEWERS WANT TO SEE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Strong senior engineers don't just implement — they make calls.
Here is the framework that signals maturity:

  STEP 1: DEFINE THE PROBLEM CLEARLY
    → Separate symptoms from root cause
    → "The system was slow" vs "p99 latency spiked to 4s under load
       due to N+1 queries in the product listing endpoint"

  STEP 2: IDENTIFY OPTIONS (at least 3)
    → Never present just one solution — shows you didn't explore
    → Example: "We could (a) optimize the query, (b) add a cache layer,
       or (c) denormalize the data model"

  STEP 3: EVALUATE TRADE-OFFS
    → Cost, complexity, time, risk, reversibility
    → "Option (b) is fastest to implement but adds operational overhead.
       Option (c) is most performant long-term but introduces data sync risk."

  STEP 4: MAKE THE DECISION (AND OWN IT)
    → State clearly what you chose and why
    → "We chose (b) first as a tactical fix with (c) planned for Q3"

  STEP 5: VALIDATE AND ADJUST
    → How did you measure the outcome?
    → "After caching, p99 dropped to 180ms. We added dashboards to
       track cache hit rate and set alerts if it dropped below 80%."

REAL DECISION SCENARIOS TO PREPARE (WITH SAMPLE ANSWERS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO 1: Choosing a messaging system
  Options:   Kafka, RabbitMQ, AWS SQS/SNS, ActiveMQ
  Decision:  "We chose Kafka because we needed replay capability,
              ordered message delivery per partition, and the volume
              (50K events/sec) ruled out SQS cost-effectively."

SCENARIO 2: Monolith vs microservices at project start
  Options:   Start as monolith, start as microservices, modular monolith
  Decision:  "We started as a modular monolith — clean package boundaries
              but single deployment. After 18 months and 4 teams working
              on it, we split out the payment and notification domains.
              Starting as microservices with a 3-person team would have
              been premature."

SCENARIO 3: SQL vs NoSQL for a new feature
  Options:   PostgreSQL, MongoDB, DynamoDB, Cassandra
  Decision:  "Chose PostgreSQL because we needed ACID guarantees for
              financial transactions and the query patterns were relational.
              We added MongoDB only for the unstructured audit log where
              schema flexibility was required."

SCENARIO 4: REST vs gRPC vs GraphQL
  Options:   REST, gRPC, GraphQL, WebSocket
  Decision:  "Chose gRPC for internal service-to-service calls (typed
              contracts, multiplexing, performance). REST for external APIs
              (broad client compatibility). Rejected GraphQL because our
              data access patterns were predictable and didn't justify
              the complexity."

SCENARIO 5: Synchronous vs asynchronous processing
  Options:   Synchronous REST call, async with Kafka, async with SQS
  Decision:  "For the order confirmation email, we chose async Kafka.
              The user doesn't need to wait for the email to be sent.
              This decoupled the email service and let us retry failed
              sends without affecting the purchase flow."

HANDLING "WHAT DECISION DO YOU REGRET?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This question is specifically asked to assess self-awareness and growth.
The wrong answer: "I don't have any regrets."
The weak answer:  A trivial mistake with no reflection.
The right answer:  A real, meaningful decision where you learned something.

TEMPLATE:
  "The decision I most regret was [specific choice] because [reason].
   At the time, I believed [rationale]. What I didn't anticipate was
   [consequence]. When [outcome occurred], I took ownership by [action].
   In hindsight, I would have [alternative]. Since then, I've applied
   [lesson] in [later project] and [result was better]."

EXAMPLE:
  "The decision I most regret was not adding idempotency keys to our
   payment retry logic in the first version. I de-prioritized it because
   we had a small user base. Six months later, a network timeout caused
   double charges for ~200 customers. We had to manually reconcile and
   refund. Since then, idempotency is non-negotiable in any payment flow
   I design — I treat it as a Day 1 requirement."

TECH DEBT DECISIONS — SHOWING JUDGMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

One of the clearest senior signals: knowing when to incur tech debt
vs. when to pay it down. Prepare a story for each:

  WHEN TO INCUR:
    "We had a hard deadline for a partner launch. I made the decision
     to hard-code the feature flag configuration in a config file
     rather than build a proper feature flag service. I documented
     it as intentional tech debt with a linked ticket and 60-day SLA
     to address it. We shipped on time."

  WHEN TO PAY DOWN:
    "Our synchronous payment flow was causing cascading timeouts.
     Despite pressure to keep shipping features, I made the case to
     the engineering manager that this was an incident waiting to happen.
     I quantified the risk: 12 incidents in 3 months, $50K estimated
     customer impact. Got 3 sprint commitment to refactor."
