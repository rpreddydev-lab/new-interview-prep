================================================================================
ARCHITECTURE OWNERSHIP — INTERVIEW PREPARATION
================================================================================
Purpose: Demonstrate you have owned system architecture end-to-end,
         not just implemented what was handed to you. This is the single
         clearest differentiator between Senior and Mid-level engineers.
================================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WHAT INTERVIEWERS MEAN BY "ARCHITECTURE OWNERSHIP"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - You made design choices, not just implemented them
  - You understood the trade-offs and defended them under questioning
  - You evolved the architecture over time based on production learnings
  - You knew when to pay down tech debt vs. ship fast
  - You designed for failure: retry, circuit breaker, fallbacks, idempotency

KEY SIGNAL: If every architecture decision you describe starts with
            "My tech lead said..." or "The architect decided...",
            you are signaling mid-level, not senior.

HOW TO TALK ABOUT SYSTEMS YOU BUILT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ALWAYS be able to answer for any system you claim you "built":

  1. WHY was this system designed this way?
     "We chose a microservices split because the team was growing to 3 squads
      and we needed independent deployment pipelines."

  2. WHAT alternatives did you consider?
     "We evaluated GraphQL vs REST. Chose REST because our consumers were
      existing mobile clients already built around REST conventions."

  3. WHAT failed in production?
     "We had a thundering herd problem on cache miss. Fixed it with a
      probabilistic early expiration strategy (cache jitter)."

  4. HOW did it scale?
     "Started at 5K req/sec. After optimizing the DB queries with
      connection pooling (HikariCP) and adding a Redis cache layer,
      we reached 50K req/sec with p99 latency under 80ms."

  5. WHAT would you do differently?
     "I would have introduced the Outbox pattern earlier. Dual-write
      bugs cost us two P1 incidents before we refactored."

ARCHITECTURE PATTERNS YOU SHOULD OWN AS STORIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  MONOLITH → MICROSERVICES MIGRATION
    → Strangler fig pattern, bounded context identification
    → Managing data consistency during split (dual-read phase)
    → API versioning strategy during migration

  EVENT-DRIVEN ARCHITECTURE
    → Kafka topics, consumer groups, partition strategy
    → Idempotency and exactly-once guarantees
    → Dead Letter Queue (DLQ) and retry policies

  CACHING STRATEGY
    → Write-through vs write-behind vs cache-aside
    → TTL tuning, cache invalidation, stampede protection
    → L1 (in-process Caffeine) + L2 (distributed Redis) layering

  DATABASE SCALING
    → Vertical → read replicas → sharding decision tree
    → Indexing strategy: query-driven index design
    → Connection pool tuning (HikariCP: minimumIdle, maximumPoolSize)

  API GATEWAY / SERVICE MESH
    → Why you added an API Gateway (rate limiting, auth, routing)
    → Sidecar pattern with Envoy or Istio for observability

  OBSERVABILITY STACK
    → Distributed tracing: correlation IDs, OpenTelemetry spans
    → Alerting on SLO breach rather than raw metrics
    → Runbooks: what you automated from on-call incidents

DEEP-DIVE FRAMEWORK — THE "ARCHITECTURE TOUR"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When asked "walk me through a system you designed," use this structure:

  1. CONTEXT (30 sec)
     Scale: MAU, req/sec, data volume, team size
     "We had 2M active users, 20K req/sec peak, 5-person team"

  2. REQUIREMENTS (30 sec)
     Functional: what it does
     Non-functional: latency SLA, availability target (99.9% or 99.99%), RPO/RTO

  3. ARCHITECTURE DIAGRAM (describe verbally)
     "Client → API Gateway → [Auth Service] → [Core Service]
      → PostgreSQL (primary) + Redis cache
      → Kafka event bus → [Notification Service]"

  4. KEY DECISIONS (60 sec each, pick 2-3)
     "The most interesting decision was..."
     Cover: trade-offs, alternatives considered, why you chose this

  5. FAILURE MODES AND MITIGATIONS
     "The DB being a single point of failure was our biggest risk.
      We added a read replica and automated failover within 30 seconds."

  6. LEARNINGS + EVOLUTION
     "After 6 months in production, we discovered... and we changed..."

NUMBERS YOU MUST KNOW ABOUT YOUR OWN SYSTEMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ❌ WEAK: "We had a lot of users and it was very fast"
  ✅ STRONG: "We served 15K req/sec at p99 latency of 95ms,
              on a 6-node Kubernetes cluster with autoscaling
              triggered at 70% CPU, backed by a 500GB PostgreSQL
              with 4 read replicas"

  Prepare these numbers for your top 2-3 projects:
    [ ] Peak requests per second
    [ ] p50 / p95 / p99 latency
    [ ] Data volume (records, GB/TB)
    [ ] Availability (uptime %)
    [ ] Number of services / microservices you owned
    [ ] Team size you worked with / led technically
    [ ] Number of engineers you mentored
    [ ] Business impact (revenue protected, cost saved, time saved)
