================================================================================
STUCK RECOVERY STRATEGIES - WHAT TO DO WHEN YOUR BRAIN GOES BLANK
================================================================================
Last Updated: April 2026
Purpose: A complete playbook for getting unstuck in coding interviews.
         Getting stuck is normal. Staying stuck silently is the problem.
================================================================================

--------------------------------------------------------------------------------
1. THE REALITY OF GETTING STUCK
--------------------------------------------------------------------------------

FACT: Even the best engineers get stuck on interview problems.
FACT: Many people who work at Google/Meta/Amazon got stuck during their interviews.
FACT: Getting stuck is NOT the failure mode. How you handle it is.

What separates top performers from others when stuck:
  - They stay calm (anxiety spiraling uses cognitive resources needed for solving)
  - They have a systematic recovery process
  - They communicate openly rather than freezing silently
  - They use hints gracefully and productively

The interviewer is not hoping you fail. They want you to succeed.
When you get stuck, they feel mild tension too. Asking for a hint
gives BOTH of you a way forward.

DEFINITION: You are "stuck" when you have made no meaningful progress
  toward a solution for more than 2-3 minutes.

--------------------------------------------------------------------------------
2. THE STUCK RECOVERY LADDER
--------------------------------------------------------------------------------

Work through these steps IN ORDER when stuck. Each step gets more explicit
about asking for help.

RUNG 1: RESET AND RE-READ (30-60 seconds)
  - Stop what you're doing.
  - Re-read the problem from the beginning.
  - Look at the examples again with fresh eyes.
  - Often, a misread is the cause of being stuck.

RUNG 2: SIMPLIFY THE PROBLEM (1-2 minutes)
  - "What if n=1? n=2? n=3?"
  - "What if all values are positive?"
  - "What if the array is sorted?"
  - Solve the simplified version. Then generalize.

RUNG 3: THINK OUT LOUD WITH EXAMPLES (1-2 minutes)
  Say out loud:
  "Let me try a concrete example... input is [2, 5, 1, 8, 3]...
   if I want the longest subarray where... okay so manually the answer is...
   how did I arrive at that? The pattern I see is..."
  Sometimes verbalizing unlocks the answer.

RUNG 4: PATTERN SCAN (1-2 minutes)
  Rapidly scan through all the major patterns:
  "Could this be Two Pointers? ... maybe not, not sorted.
   Could this be Sliding Window? ... could be, there's a constraint.
   Could this be a HashMap? ... the problem involves lookups.
   Could this be DP? ... the choices feel overlapping.
   
   Actually, the sliding window fits because..."

RUNG 5: STATE WHAT YOU KNOW (1 minute)
  Say out loud:
  "Let me state what I know and what I need:
   - I have [known structure].
   - I need to find/compute [output].
   - I know that [what's been established].
   - The gap is that I don't know how to [specific gap]."
  
  Sometimes articulating the gap precisely reveals the solution.

RUNG 6: TRY BRUTE FORCE (3-5 minutes)
  "I'm not seeing the optimal approach, so let me code a brute force
   solution first. That will give us a working solution and might help
   me see the optimization pattern."
  
  Code it. Test it. Then say:
  "This is O(n²). The inefficiency is [identify it]. I think we can fix
   that by [direction]..."

RUNG 7: ASK FOR A HINT (directly)
  "I've been working through several approaches and I'm not finding a
   clear path forward from here. Could you give me a nudge in the
   right direction?"
  
  OR (more specific):
  "I'm between two approaches - [approach A] and [approach B].
   I'm not sure which direction is better. Do you have any guidance?"

RUNG 8: EXPLICITLY ASK FOR THE KEY INSIGHT
  If the hint didn't help:
  "I appreciate the hint, but I'm still not seeing how to apply it.
   Could you walk me through the key insight for this problem?"
  
  Note: This is not ideal, but it's BETTER than complete silence.
  Even if they walk you through it, you can still demonstrate understanding,
  clean coding, and good testing in the remaining time.

--------------------------------------------------------------------------------
3. SPECIFIC TECHNIQUES FOR COMMON STUCK SCENARIOS
--------------------------------------------------------------------------------

STUCK SCENARIO 1: "I know I need some data structure but can't figure out which"
  
  Recovery: Run through each major data structure and ask:
  "What does [data structure] give me?"
  
  - HashMap: O(1) lookup by key; good for "have I seen X before?"
  - MinHeap/MaxHeap: O(log n) access to smallest/largest; good for "K-th..."
  - Stack: LIFO; good for "matching brackets", "next greater element"
  - Queue/Deque: FIFO; good for BFS, sliding window maximum
  - Set: O(1) membership check; good for "no duplicates" or "seen before"
  - Array: O(1) indexed access; good for frequency counts, DP tables
  
  "The problem requires [what]. That sounds like [data structure] because..."

STUCK SCENARIO 2: "I have a brute force but can't optimize it"
  
  Recovery: Identify what's being REPEATED in the brute force.
  
  "In my O(n²) solution, for each element I'm [doing X].
   That means I'm computing [something] n times when I could compute it once.
   
   If I precompute [something] and store it... OR
   If I use a rolling calculation to avoid recomputing... OR
   If I use a data structure that maintains [something] incrementally..."

STUCK SCENARIO 3: "I know the algorithm but can't figure out the exact code"
  
  Recovery: Code in pseudocode or English first.
  
  "Let me write this in pseudocode first to make sure the logic is right,
   then I'll convert to actual code."
  
  ```
  // For each element from left to right:
  //   If current element > max so far:
  //     Update max
  //   If current element completes a valid pair:
  //     Add pair to result
  // Return result
  ```
  
  Then fill in the actual syntax.

STUCK SCENARIO 4: "The recursive logic isn't working right"
  
  Recovery: Trace the call tree explicitly.
  
  "Let me trace the recursive calls for input n=4:
   fib(4) → fib(3) + fib(2)
   fib(3) → fib(2) + fib(1)
   ...
   Do I see the repeated work? Yes, fib(2) is called twice.
   That tells me I need memoization."

STUCK SCENARIO 5: "My DP doesn't work and I can't find the bug"
  
  Recovery: Print out your DP table manually.
  
  "Let me draw out the DP table for a small input:
   input: 'abcbda', target: 'bda'
   
       ''  b  d  a
   ''  0   0  0  0
   a   0   0  0  1
   b   0   1  1  1
   c   0   1  1  1
   ...
   
   Ah, I see the issue - my transition is wrong at this cell because..."

STUCK SCENARIO 6: "I can't figure out the graph/tree traversal"
  
  Recovery: Draw the graph.
  
  "Let me draw the graph for this input first..."
  
  [Draw on paper/whiteboard]
  
  "Now manually trace what BFS would do:
   Queue: [0]
   Visit 0, add neighbors [1, 2]: Queue [1, 2]
   Visit 1, add neighbors [3]: Queue [2, 3]
   ...
   
   Now I can see the pattern and code it."

STUCK SCENARIO 7: "The two-pointer approach isn't converging correctly"
  
  Recovery: Clarify the loop invariant.
  
  "Let me define exactly what my invariant should be:
   - left pointer: [what it represents]
   - right pointer: [what it represents]
   - At each step: [what condition must hold]
   - Move left when: [condition]
   - Move right when: [other condition]
   
   Okay, with that invariant clear, let me re-code this..."

--------------------------------------------------------------------------------
4. WHEN TO ASK FOR A HINT VS. KEEP TRYING
--------------------------------------------------------------------------------

KEEP TRYING if:
  - You've been stuck for less than 3 minutes
  - You have a direction but are stuck on implementation details
  - You're mid-trace and hit a snag (keep tracing)
  - You haven't tried all the techniques above

ASK FOR A HINT if:
  - You've been stuck for 3-5 minutes with no progress
  - You've exhausted your pattern scanning
  - You have no idea even where to start
  - You've been going down a wrong path and need a redirect

HOW TO ASK GRACEFULLY:
  BAD: "I give up. What's the answer?"
  BAD: (silence, staring at the screen)
  
  GOOD: "I've explored [approach 1] and [approach 2], but I'm not finding
  a clear path. Could you give me a nudge or confirm if I'm thinking
  about this in the right direction?"
  
  GOOD: "I believe the key insight I'm missing is how to [specific gap].
  Could you help me think through that part?"

AFTER GETTING A HINT:
  - Pause 5-10 seconds to absorb it
  - Don't immediately say "Oh! I know!" and rush to code
  - Explain your understanding: "Okay, so if I [restate the hint],
    that means I can [implication]. Let me try coding that..."
  - Ask if you've understood correctly: "Is that what you were pointing toward?"

5. MENTAL TECHNIQUES FOR PANIC RECOVERY
--------------------------------------------------------------------------------

THE PAUSE-AND-BREATHE:
  When you feel panic starting, explicitly STOP.
  Say: "Let me take a moment to organize my thoughts..."
  Take 2-3 slow breaths. (This takes 10-15 seconds and is completely normal)
  Return to the problem with a reset state.

THE GROUND TECHNIQUE:
  If panic is strong, ground yourself:
  - Look at your hands
  - Feel the keyboard
  - Say to yourself: "I have solved hard problems before. I will work
    through this methodically."

THE CURIOSITY REFRAME:
  Change the internal narrative:
  FROM: "I MUST solve this or I'll fail"
  TO: "This is a genuinely interesting puzzle. Let me explore it."
  
  Curiosity reduces anxiety. Anxiety consumes the working memory you need.

THE "WHAT DO I KNOW?" ANCHOR:
  When completely lost, start from certainty:
  "What DO I know?"
  - "I know the input is an array of integers."
  - "I know I need to find a subarray."
  - "I know the answer for the example is 5."
  - "I know I can compute this in O(n²) with nested loops."
  
  Build from what's solid. Uncertainty recedes.

--------------------------------------------------------------------------------
6. RECOVERING FROM A WRONG APPROACH
--------------------------------------------------------------------------------

SCENARIO: You've coded a full solution and it's wrong. You or the interviewer
  has found a bug that reveals a fundamental flaw in your approach.

WRONG RESPONSE:
  - "Oh no, the whole thing is wrong..." (defeatist)
  - "Let me just try to patch it..." (bandaid on fundamental issue)
  - Silence + frantic rewriting

RIGHT RESPONSE:
  Step 1: Acknowledge clearly: "I see - my approach doesn't account for
          [the issue]. The fundamental problem with my current solution is..."
  
  Step 2: Diagnose: "This fails because I assumed [wrong assumption].
          In reality, [correct understanding]."
  
  Step 3: Decide: "I think the cleanest fix is to [new approach] because
          that would avoid this issue entirely. Should I rewrite with that
          approach, or would you like me to patch the current one?"
  
  Step 4: Code the new approach - this time FASTER because you understand
          the problem better after your first attempt.

INSIGHT: A second attempt after discovering your first approach was wrong
  can actually be MORE IMPRESSIVE than getting it right the first time,
  if you handle the pivot gracefully and show learning/adaptation.

--------------------------------------------------------------------------------
7. STUCK-RECOVERY SUMMARY CARD
--------------------------------------------------------------------------------

WHEN STUCK, IN ORDER:
  1. RE-READ the problem (30 sec)
  2. SIMPLIFY to n=1, n=2, n=3
  3. WORK AN EXAMPLE manually + verbalize
  4. SCAN PATTERNS: Two Ptr? Sliding Window? HashMap? DP? BFS/DFS? Heap?
  5. STATE what you know and don't know out loud
  6. CODE BRUTE FORCE and optimize from there
  7. ASK FOR A HINT explicitly

NEVER:
  - Go silent for more than 2 minutes
  - Pretend to be coding when you're actually stuck
  - Give up entirely and say "I don't know"

ALWAYS:
  - Tell the interviewer what you're thinking/doing
  - Frame being stuck as "exploring"
  - Use hints gracefully and immediately
  - Return to the problem fresh after a brief pause

TIME CAPS:
  - Each rung of the ladder: max 2 minutes before escalating
  - If on rung 3+ with no progress after 5 min total: ask for hint
  - Never spend >5 min on one stuck point without action
