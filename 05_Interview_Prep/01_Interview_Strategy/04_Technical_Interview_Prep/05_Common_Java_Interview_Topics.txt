--------------------------------------------------------------------------------
1. JVM INTERNALS
--------------------------------------------------------------------------------

JVM ARCHITECTURE:
  - ClassLoader Subsystem: loads .class files into memory
    Load → Link (verify + prepare + resolve) → Initialize
    Bootstrap ClassLoader → Extension ClassLoader → Application ClassLoader

  - Runtime Data Areas:
    Method Area (Metaspace in Java 8+): class metadata, static variables
    Heap:            object instances and arrays; GC-managed
    Stack:           per-thread; holds stack frames (local vars, operand stack, frame data)
    PC Register:     per-thread; current instruction pointer
    Native Method Stack: for native (C/C++) method calls

  - Execution Engine:
    Interpreter: executes bytecode line by line
    JIT Compiler: compiles hot methods to native machine code (HotSpot)
    Garbage Collector: reclaims unreachable objects

BYTECODE vs. SOURCE:
  .java → (javac) → .class (bytecode) → (JVM) → machine code
  Bytecode is platform-independent; JVM is platform-specific

JUST-IN-TIME (JIT) COMPILATION:
  - HotSpot identifies "hot" methods (frequently executed)
  - Compiles them to native code for speed
  - Tiered compilation: C1 (fast compile, less optimized) → C2 (slow, aggressive optimization)
  - OSR (On-Stack Replacement): replace running interpreted code with compiled code

CLASS LOADING:
  - Classes are loaded lazily (on first use)
  - loadClass() → findClass() → defineClass()
  - ClassCastException when same class loaded by different classloaders

2. GARBAGE COLLECTION
--------------------------------------------------------------------------------

HEAP STRUCTURE (HotSpot):
  Young Generation:
    Eden Space: new allocations
    Survivor 0, Survivor 1: objects that survived at least one GC
  Old Generation (Tenured): long-lived objects
  Metaspace (Java 8+): class metadata (not in heap)

GC PROCESS:
  Minor GC: collects Young Generation; fast (< 100ms typically)
  Major / Full GC: collects Old Generation; slower (hundreds of ms to seconds)
  STW (Stop-The-World): all application threads paused during certain GC phases

GARBAGE COLLECTORS:
  Serial GC:       Single-threaded; for small apps or single-CPU
  Parallel GC:     Multi-threaded; throughput-focused; good for batch jobs
  CMS (Concurrent Mark Sweep): Low-pause; concurrent mark + sweep; deprecated in Java 9
  G1 GC (Java 9+ default): Region-based; predictable pause times; good for large heaps
  ZGC (Java 15+ production): Sub-millisecond pauses; scales to terabytes of heap
  Shenandoah:      Similar to ZGC; low pause; OpenJDK project

G1 GC TUNING FLAGS:
  -XX:+UseG1GC
  -Xms<size>      : Initial heap size
  -Xmx<size>      : Max heap size (keep Xms == Xmx to avoid resizing pauses)
  -XX:MaxGCPauseMillis=200 : Target max GC pause (soft goal)
  -XX:G1HeapRegionSize     : G1 region size (1-32 MB; powers of 2)
  -verbose:gc              : Enable GC logging

MEMORY LEAKS IN JAVA:
  - Static collections holding references: class-level Map never cleared
  - Listener/callback not removed: event bus or Observable not unregistered
  - ThreadLocal not removed: thread pool threads hold stale ThreadLocal values
  - Interned Strings: String.intern() adds to string pool (Metaspace)
  - Caches without eviction: unlimited Guava Cache / HashMap

TOOLS FOR GC ANALYSIS:
  - jstat, jmap, jconsole, jvisualvm, Java Flight Recorder (JFR)
  - Heap dump: jmap -dump:live,format=b,file=heap.hprof <pid>
  - Analyze heap dump: Eclipse MAT, VisualVM

3. CONCURRENCY AND MULTITHREADING
--------------------------------------------------------------------------------

JAVA MEMORY MODEL (JMM):
  - Defines when changes made by one thread are visible to other threads
  - Actions: read, write, lock, unlock, thread start, thread join
  - Happens-Before relationship: if A happens-before B, then A's effects are visible to B
    Examples of HB:
      - A write to a volatile variable happens-before every subsequent read of it
      - Thread.start() happens-before any action in the started thread
      - Object monitor unlock happens-before a subsequent lock
      - All actions before Thread.join() happen-before join() returns

VOLATILE:
  - Guarantees visibility: reads/writes go directly to main memory (not CPU cache)
  - Does NOT guarantee atomicity: i++ is not atomic even if i is volatile
  - Use when: boolean flag for thread stopping; singleton DCL (Double-Checked Locking)

SYNCHRONIZED:
  - Intrinsic (monitor) lock on an object; only one thread can hold it at a time
  - synchronized method: locks on 'this' (or class object for static method)
  - synchronized(obj) {} block: more granular locking
  - Provides: mutual exclusion + visibility (happens-before on unlock/lock)

JAVA.UTIL.CONCURRENT:

  ReentrantLock:
    - Explicit lock; same semantics as synchronized but more control
    - tryLock() — non-blocking attempt; fairness policy; interruptible locking
    - Must manually unlock() in finally block

  ReadWriteLock / ReentrantReadWriteLock:
    - Multiple readers OR one writer; not both
    - Good for: read-heavy data structures

  StampedLock (Java 8):
    - Optimistic read mode: no lock; validate stamp after read; retry if stale
    - Best performance for read-heavy loads with rare writes

  AtomicInteger, AtomicLong, AtomicReference (java.util.concurrent.atomic):
    - Lock-free, CAS (Compare-And-Swap) based operations
    - incrementAndGet(), compareAndSet(expected, update) — atomic

  CountDownLatch:
    - One-time gate: await() blocks until count reaches zero
    - Use: wait for N tasks to complete

  CyclicBarrier:
    - Reusable gate: all N threads wait at barrier, then all proceed
    - Use: iterative algorithms (parallel phases)

  Semaphore:
    - Controls access to N permits
    - Use: limit concurrent DB connections, rate limiting

  BlockingQueue:
    - Producer-consumer pattern; put() blocks if full; take() blocks if empty
    - Implementations: LinkedBlockingQueue, ArrayBlockingQueue, PriorityBlockingQueue

  ConcurrentHashMap:
    - Thread-safe HashMap; segment locking (Java 7) → CAS + lock striping (Java 8+)
    - computeIfAbsent(), merge() are atomic operations
    - Much better performance than Hashtable or synchronized Map

  CopyOnWriteArrayList:
    - All mutative operations (add, remove) copy the underlying array
    - Reads are lock-free; writes are slow
    - Use when: reads are far more frequent than writes; small lists

THREAD POOL (ExecutorService):
  - Thread creation is expensive; pool and reuse threads
  - Executors.newFixedThreadPool(n) — n threads; bounded
  - Executors.newCachedThreadPool() — unbounded (can cause OOM)
  - Executors.newScheduledThreadPool(n) — for scheduled/periodic tasks
  - ThreadPoolExecutor: configure corePoolSize, maxPoolSize, keepAlive, queue, handler
  - ForkJoinPool: work-stealing for recursive divide-and-conquer

COMPLETABLEFUTURE (Java 8):
  - Async computation; chain with thenApply(), thenCompose(), thenAccept()
  - Combine: allOf(), anyOf()
  - Exception handling: exceptionally(), handle()
  - Supply/run: supplyAsync(() -> ..., executor), runAsync(() -> ...)

DEADLOCK:
  - Conditions: mutual exclusion + hold and wait + no preemption + circular wait
  - Prevention: always acquire locks in the same order; use timeout (tryLock)
  - Detection: thread dump analysis (jstack); look for "BLOCKED" state with cycle

COMMON INTERVIEW CONCURRENCY QUESTIONS:
  Q: Implement a thread-safe Singleton
     → Double-Checked Locking with volatile OR enum singleton (simplest + safe)

  Q: What's the difference between wait() and sleep()?
     → wait() releases the monitor lock; sleep() does not; wait() must be called inside synchronized

  Q: What is a race condition?
     → When program behavior depends on relative timing of concurrent operations

  Q: How do you avoid race conditions?
     → Synchronization, atomic operations, immutable objects, thread confinement

4. JAVA COLLECTIONS DEEP DIVE
--------------------------------------------------------------------------------

HIERARCHY:
  Collection
    List: ArrayList, LinkedList, Vector, Stack
    Set: HashSet, LinkedHashSet, TreeSet
    Queue: LinkedList, PriorityQueue, ArrayDeque
    Deque: ArrayDeque, LinkedList
  Map (not Collection)
    HashMap, LinkedHashMap, TreeMap, Hashtable, ConcurrentHashMap

ARRAYLIST vs. LINKEDLIST:
  ArrayList:   O(1) get by index; O(n) insert/delete in middle; backed by array
  LinkedList:  O(n) get by index; O(1) insert/delete at known node; doubly linked

HASHMAP INTERNALS (Java 8+):
  - Array of buckets; key hashed to bucket index via hash(key) % capacity
  - Each bucket: linked list (up to 8 elements) → treeified to Red-Black Tree (> 8)
  - Load factor: default 0.75; rehash when size > capacity * loadFactor
  - Initial capacity: 16; doubles on rehash; prefer setting capacity if size known
  - hashCode() and equals() MUST be consistent

TREEMAP vs. HASHMAP:
  HashMap:   O(1) average put/get; unordered; allows null key
  TreeMap:   O(log n) put/get; sorted by natural order or Comparator; no null key

PRIORITYQUEUE:
  - Min-heap by default; provide Comparator for max-heap
  - O(log n) offer/poll; O(1) peek
  - Backed by array; not thread-safe

ARRAYS vs. COLLECTIONS SORT:
  Arrays.sort():      Dual-Pivot Quicksort for primitives; MergeSort for objects
  Collections.sort(): TimSort (hybrid MergeSort + InsertionSort); stable; O(n log n)

5. JAVA 8+ FEATURES (INTERVIEW FAVORITES)
--------------------------------------------------------------------------------

LAMBDA EXPRESSIONS:
  - Anonymous function: (params) -> expression or (params) -> { body }
  - Requires a @FunctionalInterface (single abstract method)
  - Example: list.sort((a, b) -> a.compareTo(b));

STREAMS API:
  - Lazy evaluation; operations are intermediate (lazy) or terminal (eager)
  - Intermediate: filter, map, flatMap, sorted, distinct, limit, skip, peek
  - Terminal: forEach, collect, reduce, count, findFirst, anyMatch, toList
  - Parallel streams: stream.parallel() — uses ForkJoinPool.commonPool()
  - Collectors: Collectors.toList(), groupingBy(), joining(), counting()

  Common pattern:
    List<String> result = list.stream()
        .filter(s -> s.length() > 3)
        .map(String::toUpperCase)
        .sorted()
        .collect(Collectors.toList());

OPTIONAL:
  - Container that may or may not hold a value; avoid NullPointerException
  - Optional.of(value), Optional.ofNullable(value), Optional.empty()
  - isPresent(), get(), orElse(default), orElseGet(supplier), ifPresent(consumer)
  - map(), flatMap(), filter() — compose operations without null checks

FUNCTIONAL INTERFACES:
  Function<T, R>:    T → R    (map)
  Predicate<T>:      T → boolean (filter)
  Consumer<T>:       T → void (forEach)
  Supplier<T>:       () → T  (lazy evaluation)
  BiFunction<T,U,R>: T,U → R
  UnaryOperator<T>:  T → T
  BinaryOperator<T>: T,T → T

DEFAULT AND STATIC METHODS IN INTERFACES:
  - Interfaces can have default (implemented) methods
  - Allows backward-compatible interface evolution
  - If a class implements two interfaces with same default method, MUST override

RECORD TYPES (Java 16+):
  - Immutable data carrier; auto-generates constructor, getters, equals, hashCode, toString
  - record Point(int x, int y) {}
  - Cannot extend; can implement interfaces

SEALED CLASSES (Java 17+):
  - Restricts which classes can extend or implement a class/interface
  - sealed class Shape permits Circle, Square {}

PATTERN MATCHING INSTANCEOF (Java 16+):
  - if (obj instanceof String s) { s.length(); } — eliminates explicit cast

RECORDS + SEALED CLASSES: used in domain modeling; shows Java 17+ knowledge

SWITCH EXPRESSIONS (Java 14+):
  int result = switch (day) {
      case MONDAY, FRIDAY -> 6;
      case TUESDAY -> 7;
      default -> 8;
  };

TEXT BLOCKS (Java 15+):
  String json = """
      {
          "name": "Alice"
      }
      """;

VAR (Java 10+):
  var list = new ArrayList<String>(); // type inferred as ArrayList<String>
  Only for local variables; does NOT make Java dynamically typed

6. SPRING FRAMEWORK
--------------------------------------------------------------------------------

SPRING CORE:
  - IoC Container: manages object creation and lifecycle (ApplicationContext)
  - Dependency Injection: constructor injection (preferred) vs. setter vs. field (@Autowired)
  - Bean lifecycle: instantiate → populate properties → BeanPostProcessor → init → use → destroy
  - Bean scopes: singleton (default), prototype, request, session, application

ANNOTATIONS:
  @Component, @Service, @Repository, @Controller, @RestController
  @Bean, @Configuration — Java-based bean configuration
  @Autowired — inject dependency (prefer constructor injection)
  @Qualifier — disambiguate when multiple beans of same type
  @Primary — default bean when multiple candidates
  @Value("${property}") — inject from properties file
  @Profile("dev") — bean active only for given profile

SPRING BOOT:
  - Auto-configuration: @EnableAutoConfiguration reads spring.factories
  - Starter dependencies: spring-boot-starter-web, -data-jpa, -security, -test
  - application.properties / application.yml: configuration externalization
  - Actuator: /health, /metrics, /env, /beans endpoints for monitoring

SPRING MVC:
  - DispatcherServlet → HandlerMapping → Controller → ViewResolver
  - @RequestMapping, @GetMapping, @PostMapping, @PathVariable, @RequestParam, @RequestBody
  - @ResponseBody / @RestController: serialize response to JSON (Jackson)
  - @ControllerAdvice + @ExceptionHandler: global exception handling

SPRING DATA JPA:
  - JpaRepository<Entity, ID>: gives you findById, findAll, save, delete, count
  - Custom queries: @Query("SELECT u FROM User u WHERE u.email = :email")
  - JPQL vs. native SQL: JPQL is ORM-independent; native SQL for complex queries
  - Lazy vs. eager loading: @OneToMany(fetch = FetchType.LAZY) — default for collections
  - N+1 problem: accessing lazy collection in a loop fires N additional queries
    Fix: JOIN FETCH in JPQL or @EntityGraph

SPRING SECURITY:
  - Authentication: who are you? (UsernamePasswordAuthenticationFilter, JWT)
  - Authorization: what can you do? (hasRole(), hasAuthority())
  - SecurityFilterChain: chain of filters; each can abort or pass to next
  - Password encoding: BCryptPasswordEncoder (never store plain text)
  - JWT: stateless; encode claims in signed token; validate on each request

SPRING TRANSACTION:
  @Transactional: wraps method in a DB transaction
  Propagation: REQUIRED (join existing or create new), REQUIRES_NEW (always new)
  Isolation: READ_COMMITTED, SERIALIZABLE, REPEATABLE_READ, READ_UNCOMMITTED
  Self-invocation problem: @Transactional doesn't apply to methods called
    within the same class (Spring proxy is bypassed) → extract to another bean

7. JAVA DESIGN PATTERNS (INTERVIEW-RELEVANT)
--------------------------------------------------------------------------------

CREATIONAL:
  Singleton: One instance; use enum or lazy initialization with DCL + volatile
  Builder: Fluent construction of complex objects; avoids telescoping constructors
  Factory Method: Subclass decides which class to instantiate
  Abstract Factory: Family of related objects without specifying concrete classes

STRUCTURAL:
  Adapter: Converts interface of a class into another interface clients expect
  Decorator: Adds behavior to objects dynamically (InputStream → BufferedInputStream)
  Proxy: Controls access to an object (Spring AOP is proxy-based)
  Composite: Tree structure; treat leaf and composite uniformly

BEHAVIORAL:
  Strategy: Family of algorithms; swap at runtime (Comparator is a Strategy)
  Observer: Subscribers notified when subject state changes (Event listeners)
  Command: Encapsulate request as an object; supports undo
  Template Method: Define algorithm skeleton in base class; subclasses fill in steps
  Iterator: Traverse a collection without exposing its representation

8. COMMON JAVA INTERVIEW QUESTIONS (WITH ANSWERS)
--------------------------------------------------------------------------------

Q: What is the difference between == and equals()?
   == compares references (memory addresses); equals() compares content.
   For String: "abc" == "abc" is true for string literals (interned) but
   new String("abc") == new String("abc") is false.

Q: What is the difference between String, StringBuilder, StringBuffer?
   String: immutable; new object on every modification
   StringBuilder: mutable; not thread-safe; use in single-threaded contexts
   StringBuffer: mutable; thread-safe (synchronized methods); slower

Q: What is the difference between final, finally, finalize?
   final: variable (constant), method (no override), class (no extend)
   finally: block in try-catch that always executes
   finalize(): deprecated method called by GC before collecting object

Q: What are checked vs. unchecked exceptions?
   Checked: subclass of Exception (not RuntimeException); must declare or handle
   Unchecked: subclass of RuntimeException; optional to declare or handle
   Error: not meant to be caught; JVM-level (OutOfMemoryError, StackOverflowError)

Q: What is the contract between hashCode() and equals()?
   If a.equals(b) is true, then a.hashCode() == b.hashCode() MUST be true.
   The reverse is not required (hash collisions are allowed).

Q: How does ConcurrentHashMap differ from HashTable?
   Both thread-safe, but ConcurrentHashMap uses lock striping (Java 8: CAS);
   HashTable uses a single global lock. ConcurrentHashMap is much faster under contention.
   Also, ConcurrentHashMap doesn't allow null keys/values; HashTable also doesn't.

Q: What is a functional interface? Give an example.
   An interface with exactly one abstract method (SAM type).
   @FunctionalInterface annotation documents this (not required).
   Examples: Runnable, Callable, Comparator, Predicate, Function, Consumer.

Q: What is the difference between Callable and Runnable?
   Runnable: run() returns void, cannot throw checked exceptions
   Callable: call() returns a value (V), can throw checked exceptions
   Use Callable with ExecutorService.submit() to get a Future<V>
