================================================================
FULL-STACK ARCHITECTURE — REACT + SPRING BOOT (AND VARIANTS)
================================================================

This file covers how a full-stack application is structured when
React is the frontend and Spring Boot (or Node.js / Python) is the
backend. Knowing architecture at this level is expected in senior
and architect-level interviews.

================================================================
1. MONOLITH vs MICROSERVICES FROM A FRONTEND PERSPECTIVE
================================================================

A) SINGLE BACKEND (Monolith / BFF)
   React → One API base URL → One Spring Boot app
   - Simple, fewer moving parts
   - Easier CORS, auth, and session management
   - BFF (Backend For Frontend) pattern: a dedicated backend that is
     shaped specifically for what the frontend needs

B) MICROSERVICES (Multiple backends)
   React → API Gateway → Service A, Service B, Service C
   - API Gateway (AWS API Gateway, Kong, Spring Cloud Gateway, NGINX)
     handles routing, auth, rate limiting
   - React always talks to ONE URL (the gateway)
   - Services behind the gateway are invisible to the browser
   - Auth is validated at the gateway level (JWT verification)

   Architecture:
     React App
         │
         ▼
     API Gateway (https://api.example.com)
         │
         ├──► /users  → User Service (Spring Boot)
         ├──► /orders → Order Service (Spring Boot)
         ├──► /products → Product Service (Go)
         └──► /chat   → Chat Service (Node.js, WebSocket)

================================================================
2. BACKEND FOR FRONTEND (BFF) PATTERN — DEEP DIVE
================================================================

Problem: A REST API designed for multiple clients (mobile, web, 3rd party)
often returns too much or too little data for any single client.

Solution: Create a BFF — a dedicated backend that aggregates, transforms,
and optimizes data specifically for the React frontend.

  Mobile App → Mobile BFF → Microservices
  React Web  → Web BFF    → Microservices

Benefits:
  - Frontend gets exactly the shape it needs (no over/under-fetching)
  - Auth, session, token refresh logic is centralized in the BFF
  - The BFF can aggregate multiple service calls into one frontend call
  - The BFF hides internal service topology from the browser

Example:
  React calls GET /dashboard
  Web BFF calls:
    - GET /users/{id}        (User Service)
    - GET /orders?userId={id} (Order Service)
    - GET /notifications/{id} (Notification Service)
  BFF merges responses into one JSON
  React renders without three round-trips

3. CORS — WHY IT EXISTS AND HOW IT WORKS
================================================================

CORS = Cross-Origin Resource Sharing.
A browser security feature that prevents JavaScript from making requests
to a different origin than the page was loaded from.

Origin = Protocol + Host + Port
  http://localhost:3000  ≠  http://localhost:8080  (different port)
  https://app.example.com ≠ https://api.example.com (different subdomain)

PREFLIGHT REQUEST (OPTIONS):
  For non-simple requests (POST with JSON, Authorization header, etc.)
  the browser sends an OPTIONS request first:
    OPTIONS /api/users HTTP/1.1
    Origin: http://localhost:3000
    Access-Control-Request-Method: POST
    Access-Control-Request-Headers: Content-Type, Authorization

  Server must respond:
    Access-Control-Allow-Origin: http://localhost:3000
    Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
    Access-Control-Allow-Headers: Content-Type, Authorization
    Access-Control-Max-Age: 3600   ← cache preflight for 1 hour

  If server doesn't respond correctly → browser blocks the request.

SPRING BOOT CORS CONFIG:
  Option 1: Annotation on controller
    @CrossOrigin(origins = "http://localhost:3000")
    @RestController
    public class UserController { ... }

  Option 2: Global config (preferred)
    @Configuration
    public class WebConfig implements WebMvcConfigurer {
        @Override
        public void addCorsMappings(CorsRegistry registry) {
            registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:3000",
                                "https://app.example.com")
                .allowedMethods("GET","POST","PUT","DELETE","OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)   // needed for cookies
                .maxAge(3600);
        }
    }

  Option 3: Spring Security CORS (when using Spring Security)
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.cors(cors -> cors.configurationSource(corsConfigurationSource()))
            ...
        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of("http://localhost:3000"));
        config.setAllowedMethods(List.of("GET","POST","PUT","DELETE"));
        config.setAllowedHeaders(List.of("*"));
        config.setAllowCredentials(true);
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }

4. API VERSIONING STRATEGIES
================================================================

Versioning ensures backward compatibility when the API evolves.

A) URL Versioning (most common)
   /api/v1/users
   /api/v2/users

B) Header Versioning
   GET /api/users
   API-Version: 2

C) Query Param Versioning
   GET /api/users?version=2

D) Content Negotiation (Accept header)
   Accept: application/vnd.example.v2+json

Recommendation: URL versioning is the most discoverable and easy to test.

5. DEPLOYMENT ARCHITECTURE
================================================================

A) SEPARATE DEPLOYMENTS (Most common in production)
   React → CDN (AWS CloudFront, Vercel, Netlify)
   API   → Cloud servers / containers (AWS ECS, GKE, Azure AKS)

   React build artifacts (index.html, JS bundles, CSS) are static files.
   They are served from a CDN globally.
   API is deployed on compute instances or containers.

   React talks to the API via API base URL configured in .env.production.

B) SAME-ORIGIN DEPLOYMENT (Avoids CORS entirely)
   Spring Boot serves both the API AND the React static build.
   React build output is placed in src/main/resources/static/.
   Both served from http://example.com → no CORS needed.

   Drawback: Couples deployment of frontend and backend.

C) DOCKER COMPOSE (Local development)
   services:
     frontend:
       build: ./frontend
       ports:
         - "3000:3000"
     backend:
       build: ./backend
       ports:
         - "8080:8080"
     db:
       image: postgres:15

D) NGINX REVERSE PROXY (Production-like local)
   NGINX serves the React build on port 80.
   NGINX proxies /api/* requests to the backend on port 8080.
   This eliminates CORS because both are on the same origin.

   nginx.conf:
     server {
       listen 80;
       location / {
         root /usr/share/nginx/html;
         try_files $uri /index.html;  # SPA support
       }
       location /api/ {
         proxy_pass http://backend:8080/api/;
       }
     }

6. ENVIRONMENT CONFIGURATION ARCHITECTURE
================================================================

.env                  ← shared defaults
.env.development      ← local dev overrides
.env.staging          ← staging environment
.env.production       ← production environment

Vite variables start with VITE_:
  VITE_API_BASE_URL=http://localhost:8080/api
  VITE_WS_URL=ws://localhost:8080/ws

CRA variables start with REACT_APP_:
  REACT_APP_API_BASE_URL=http://localhost:8080/api

Usage in code:
  const API_BASE_URL = import.meta.env.VITE_API_BASE_URL;  // Vite
  const API_BASE_URL = process.env.REACT_APP_API_BASE_URL;  // CRA

NEVER put secrets (API keys, passwords) in .env files for the frontend.
These are bundled into the JS output and visible to anyone.

  ▼

  │  GET /api/products
  │  Authorization: Bearer eyJhbGc...
  ▼

  │  @GetMapping("/api/products")
  │  public ResponseEntity<List<Product>> getProducts()
  ▼

  │  @Service
  │  business logic, validation
  ▼

  │  JpaRepository<Product, Long>
  ▼
Database (PostgreSQL)
  │
  ▼ (response path)
  │
JSON Response → Axios → React Query cache → Component re-renders

9. INTERVIEW QUESTIONS ON ARCHITECTURE
================================================================

Q: What is the BFF pattern and why would you use it?
A: Backend For Frontend — a dedicated backend that shapes data
   specifically for a frontend. Useful when you have multiple clients
   (web/mobile) with different data needs, or when aggregating many
   microservice calls into single responses.

Q: How does CORS work and who is responsible for fixing it?
A: CORS is a browser security mechanism. The BACKEND must send the correct
   Access-Control-Allow-* headers. The frontend developer needs to
   understand it to diagnose issues, but cannot fix it from the client side.

Q: How do you deploy a React app with a Spring Boot backend?
A: Preferred: React built to static files on a CDN, backend deployed
   separately, API URL configured via .env. Alternative: NGINX reverse
   proxy to unify origins. Dev: Docker Compose + CORS configured.

Q: What is the difference between monolith, BFF, and microservices
   from a React perspective?
A: Monolith: one API URL, simple. BFF: one dedicated backend per frontend
   client, aggregates services, frontend-optimized. Microservices with
   gateway: React sees one gateway URL, services hidden behind it.

Q: How do you handle API versioning in a React app?
A: The API base URL can include the version (e.g., /api/v1).
   When upgrading, update the base URL or create version-specific
   service functions. Use feature flags to gradually migrate.
