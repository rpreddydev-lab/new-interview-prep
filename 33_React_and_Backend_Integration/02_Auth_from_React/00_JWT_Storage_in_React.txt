================================================================
JWT STORAGE IN REACT — SECURITY & PATTERNS
================================================================

JWT (JSON Web Token) is the most common token format for
stateless authentication in React + REST API applications.

================================================================
1. WHAT IS A JWT?
================================================================

A JWT consists of three base64url-encoded parts separated by dots:

  eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9  ← Header
  .eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6IkFETUlOIn0   ← Payload
  .SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← Signature

HEADER: { "alg": "HS256", "typ": "JWT" }
PAYLOAD: { "sub": "user123", "role": "ADMIN", "exp": 1700000000, "iat": 1699996400 }
SIGNATURE: HMAC-SHA256(base64(header) + "." + base64(payload), secret)

KEY CONCEPTS:
  - JWTs are signed, not encrypted. Anyone can read the payload.
    NEVER put passwords or sensitive PII in JWT payload.
  - Signature verifies the token wasn't tampered with.
  - exp (expiry) claim: token invalid after this Unix timestamp.
  - iss (issuer): who issued the token.
  - sub (subject): who the token represents.
  - aud (audience): who the token is intended for.

ACCESS TOKEN: Short-lived (5-15 min), used for API authentication.
REFRESH TOKEN: Long-lived (days/weeks), used only to get new access tokens.

================================================================
2. WHERE TO STORE TOKENS — THE DEBATE
================================================================

THREE MAIN OPTIONS:

  A) localStorage
  B) sessionStorage
  C) In-memory (JavaScript variable)
  D) httpOnly Cookie (server-set)

─────────────────────────────────────────────────────────
OPTION A: localStorage
─────────────────────────────────────────────────────────
  localStorage.setItem('accessToken', token);
  const token = localStorage.getItem('accessToken');
  localStorage.removeItem('accessToken');

  PROS:
  ✅ Persists across browser tabs and sessions
  ✅ Easy to implement
  ✅ Survives page refresh

  CONS:
  ❌ Vulnerable to XSS (Cross-Site Scripting)
     If an attacker injects JS into your page, they can read localStorage.
     This is the #1 security concern.
  ❌ Not recommended by security professionals for tokens

─────────────────────────────────────────────────────────
OPTION B: sessionStorage
─────────────────────────────────────────────────────────
  sessionStorage.setItem('accessToken', token);

  PROS:
  ✅ Cleared when the tab is closed
  ✅ Not shared across tabs (reduces attack surface)

  CONS:
  ❌ Still vulnerable to XSS (same as localStorage)
  ❌ User is logged out on tab close (poor UX for many apps)

─────────────────────────────────────────────────────────
OPTION C: IN-MEMORY (Recommended for access tokens)
─────────────────────────────────────────────────────────
  // tokenStore.js
  let accessToken = null;

  export const getAccessToken = () => accessToken;
  export const setAccessToken = (token) => { accessToken = token; };
  export const clearAccessToken = () => { accessToken = null; };

  OR in a Zustand store:
  const useAuthStore = create((set) => ({
    accessToken: null,
    setAccessToken: (token) => set({ accessToken: token }),
    clearAuth: () => set({ accessToken: null }),
  }));

  PROS:
  ✅ Invisible to XSS (not accessible via document.cookie or localStorage)
  ✅ Cleared automatically when page closes

  CONS:
  ❌ Lost on page refresh → need a way to restore it
     Solution: Use a refresh token in httpOnly cookie + silent refresh
  ❌ Not shared across tabs

─────────────────────────────────────────────────────────
OPTION D: httpOnly Cookie (Most Secure — Recommended)
─────────────────────────────────────────────────────────
  The server sets the token in a cookie:
    Set-Cookie: refreshToken=<value>; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

  httpOnly flag: Cookie is NOT accessible by JavaScript at all.
  Secure flag: Cookie only sent over HTTPS.
  SameSite=Strict: Cookie not sent on cross-site requests (CSRF protection).

  The browser sends it automatically on matching requests.

  PROS:
  ✅ Cannot be read by JavaScript → immune to XSS token theft
  ✅ Automatic expiry via cookie Max-Age

  CONS:
  ❌ Vulnerable to CSRF if not properly configured
     Mitigated with SameSite=Strict/Lax + CSRF tokens
  ❌ withCredentials: true required in Axios for cross-origin requests
  ❌ Backend must set cookie domain/path correctly

================================================================
3. RECOMMENDED STRATEGY (BEST PRACTICE 2024)
================================================================

ACCESS TOKEN:  Store in memory (JavaScript variable / Zustand)
               → Short-lived (5-15 min), no XSS risk
               → Sent in Authorization header

REFRESH TOKEN: Store in httpOnly cookie
               → Long-lived (30 days)
               → Never accessible by JS
               → Only sent to /auth/refresh endpoint

ON PAGE LOAD:  Call /auth/refresh using the cookie
               → If cookie is valid, get a new access token
               → Store new access token in memory
               → This is called "silent refresh" at startup

================================================================
4. IMPLEMENTATION — MEMORY + COOKIE STRATEGY
================================================================

BACKEND SETS REFRESH TOKEN:
  Spring Boot:
    ResponseCookie cookie = ResponseCookie.from("refreshToken", refreshToken)
        .httpOnly(true)
        .secure(true)
        .sameSite("Strict")
        .path("/api/auth/refresh")
        .maxAge(Duration.ofDays(30))
        .build();
    response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());

REACT — TOKEN STORE:
  // src/store/tokenStore.js
  let _accessToken = null;
  export const getAccessToken = () => _accessToken;
  export const setAccessToken = (token) => { _accessToken = token; };
  export const clearAccessToken = () => { _accessToken = null; };

REACT — AUTH SERVICE:
  // src/services/authService.js
  import axios from 'axios';
  import { setAccessToken, clearAccessToken } from '../store/tokenStore';

  const AUTH_URL = import.meta.env.VITE_API_BASE_URL + '/auth';

  export const login = async (email, password) => {
    const response = await axios.post(`${AUTH_URL}/login`,
      { email, password },
      { withCredentials: true }  // sends/receives cookies
    );
    setAccessToken(response.data.accessToken);
    return response.data;
  };

  export const logout = async () => {
    await axios.post(`${AUTH_URL}/logout`, {}, { withCredentials: true });
    clearAccessToken();
  };

  export const silentRefresh = async () => {
    const response = await axios.post(`${AUTH_URL}/refresh`, {}, {
      withCredentials: true,  // sends the httpOnly refresh token cookie
    });
    setAccessToken(response.data.accessToken);
    return response.data.accessToken;
  };

REACT — STARTUP SILENT REFRESH:
  // App.jsx or AuthProvider
  useEffect(() => {
    silentRefresh()
      .then(() => setAuthenticated(true))
      .catch(() => setAuthenticated(false))
      .finally(() => setLoading(false));
  }, []);

5. READING JWT PAYLOAD IN REACT
================================================================

  const decodeToken = (token) => {
    try {
      const payload = token.split('.')[1];
      return JSON.parse(atob(payload));
    } catch {
      return null;
    }
  };

  const token = getAccessToken();
  const payload = decodeToken(token);
  // { sub: 'user123', role: 'ADMIN', exp: 1700000000 }

  const isTokenExpired = (token) => {
    const payload = decodeToken(token);
    if (!payload?.exp) return true;
    return Date.now() >= payload.exp * 1000; // exp is in seconds
  };

  // Extract roles/permissions
  const getUserRoles = () => {
    const payload = decodeToken(getAccessToken());
    return payload?.roles ?? [];
  };

  Note: Use jwt-decode library for robust decoding:
    npm install jwt-decode
    import { jwtDecode } from 'jwt-decode';
    const decoded = jwtDecode(token); // { sub, exp, roles, ... }

6. ZUSTAND AUTH STORE
================================================================

  // src/store/authStore.js
  import { create } from 'zustand';
  import { jwtDecode } from 'jwt-decode';

  const useAuthStore = create((set, get) => ({
    accessToken: null,
    user: null,
    isAuthenticated: false,

    setAccessToken: (token) => {
      let user = null;
      try {
        user = jwtDecode(token);
      } catch {}
      set({ accessToken: token, user, isAuthenticated: !!token });
    },

    clearAuth: () => {
      set({ accessToken: null, user: null, isAuthenticated: false });
    },

    hasRole: (role) => {
      const { user } = get();
      return user?.roles?.includes(role) ?? false;
    },
  }));

  export default useAuthStore;

  // Usage in Axios request interceptor:
  import useAuthStore from '../store/authStore';

  apiClient.interceptors.request.use((config) => {
    const token = useAuthStore.getState().accessToken;
    if (token) config.headers.Authorization = `Bearer ${token}`;
    return config;
  });

7. INTERVIEW QUESTIONS
================================================================

Q: Where should you store JWT access tokens in a React app?
A: In memory (a JavaScript variable or Zustand store) — not in
   localStorage or sessionStorage. In-memory storage is XSS-safe
   because it's inaccessible to injected scripts. The downside is
   the token is lost on refresh, solved by using a refresh token
   in an httpOnly cookie and calling /auth/refresh on startup.

Q: What is the difference between an access token and a refresh token?
A: Access tokens are short-lived (5-15 min) and used to authenticate
   API requests (sent in Authorization header). Refresh tokens are
   long-lived (days/weeks) and used only to obtain new access tokens
   (sent to /auth/refresh). The refresh token should be stored in
   an httpOnly cookie for security.

Q: Why is localStorage considered insecure for JWT storage?
A: localStorage is accessible by any JavaScript on the page.
   An XSS vulnerability (e.g., from a compromised npm package or
   user-generated content) allows malicious scripts to read and
   exfiltrate the token. httpOnly cookies cannot be read by JS at all.

Q: What is a silent refresh and how does it work?
A: Silent refresh is the technique of automatically obtaining a new
   access token in the background using the refresh token, without
   the user needing to log in again. On page load, a call to
   /auth/refresh is made (with credentials to send the cookie),
   and the new access token is stored in memory. It also happens
   when the access token expires (401 interceptor).

Q: What is the httpOnly flag on a cookie and why is it important?
A: The httpOnly flag prevents JavaScript from accessing the cookie via
   document.cookie. This makes it immune to XSS attacks that attempt
   to steal tokens. The cookie is sent automatically by the browser
   on matching requests, but is invisible to JavaScript code.
