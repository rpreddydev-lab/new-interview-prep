================================================================
AWS DATABASES — ELASTICACHE: REDIS AND MEMCACHED
Complete Interview Preparation Guide
================================================================

1. ELASTICACHE OVERVIEW
================================================================

  ElastiCache is AWS's managed in-memory data store service.
  Supports two engines:
    - Redis:     Feature-rich, persistence, pub/sub, sorted sets, data structures
    - Memcached: Simple key-value cache, pure horizontal scaling, no persistence

  Why use ElastiCache?
    - Reduce database load (cache frequently read data)
    - Sub-millisecond latency (vs single-digit ms for DynamoDB, ms for RDS)
    - Handle read spikes without database scaling
    - Session management, leaderboards, pub/sub, rate limiting

================================================================
2. REDIS vs MEMCACHED
================================================================

  ┌──────────────────────────┬──────────────────────────┬──────────────────────────┐
  │ Feature                  │ Redis                    │ Memcached                │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────┤
  │ Data Structures          │ Strings, Hash, List, Set,│ Strings only             │
  │                          │ Sorted Set, HyperLogLog, │                          │
  │                          │ Bitmaps, Streams         │                          │
  │ Persistence              │ RDB (snapshots) + AOF    │ None (in-memory only)    │
  │ Replication              │ Yes (primary + replicas) │ No                       │
  │ Multi-AZ/Failover        │ Yes (auto failover)      │ No                       │
  │ Pub/Sub                  │ Yes                      │ No                       │
  │ Transactions             │ Yes (MULTI/EXEC)         │ No                       │
  │ Lua Scripting            │ Yes                      │ No                       │
  │ Sorted Sets              │ Yes (leaderboards)       │ No                       │
  │ Backup/Restore           │ Yes                      │ No                       │
  │ Encryption at rest       │ Yes                      │ No                       │
  │ Scaling                  │ Read replicas + sharding │ Horizontal only          │
  │ Thread model             │ Single-threaded          │ Multi-threaded           │
  │ Use case                 │ Feature-rich caching,    │ Simple, high-throughput  │
  │                          │ sessions, queues, gaming │ cache, pure performance  │
  └──────────────────────────┴──────────────────────────┴──────────────────────────┘

  CHOOSE REDIS when:
    - Need persistence (survive restart)
    - Need replication/HA/failover
    - Using advanced data structures (sorted sets, lists)
    - Session storage (must persist across restarts)
    - Pub/Sub messaging
    - Leaderboards, rate limiting

  CHOOSE MEMCACHED when:
    - Purely horizontal scaling is needed
    - Simple key-value caching
    - Highest possible throughput, multi-threaded
    - Data loss on restart is acceptable

3. ELASTICACHE REDIS ARCHITECTURE
================================================================

  CLUSTER MODE DISABLED (Replication Group):
    - Single shard (single primary + up to 5 read replicas)
    - Data NOT sharded — full dataset on every node
    - Manual promotion to promote replica to primary on failure
    - Multi-AZ: replicas in different AZs

    [Primary Node] — writes + reads
         ↓ async replication
    [Replica 1] [Replica 2] — reads only

  CLUSTER MODE ENABLED (Redis Cluster):
    - Data sharded across multiple shards (1–500 shards)
    - Each shard has 1 primary + 0-5 replicas
    - Horizontal scaling: add/remove shards
    - Keys distributed via hash slots (0–16383 slots)
    - Supported commands: limited to commands that work within a single shard
    - Multi-AZ: replicas in different AZs per shard

  AUTO FAILOVER:
    - Multi-AZ must be enabled
    - AWS detects primary failure
    - Promotes best replica to primary (least replication lag)
    - DNS automatically updated
    - RTO: ~60 seconds

4. CACHING PATTERNS
================================================================

  1. CACHE-ASIDE (Lazy Loading):
     - Application checks cache first
     - Cache miss: fetch from DB, write to cache, return data
     - Cache hit: return from cache directly
     - PROS: Only requested data is cached; cache failure doesn't break app
     - CONS: First request always hits DB (cache miss penalty); stale data possible

     Code pattern (Redis with Jedis/Lettuce):
     String value = redis.get(key);
     if (value == null) {
         value = db.query("SELECT ...");
         redis.setex(key, 300, value);  // Cache for 5 minutes
     }
     return value;

  2. WRITE-THROUGH:
     - Write to cache AND DB simultaneously on every write
     - PROS: Cache always has fresh data; no stale reads
     - CONS: Extra write latency; writes to cache even for data rarely read

  3. WRITE-BEHIND (Write-Back):
     - Write to cache only; asynchronously write to DB later
     - PROS: Lower write latency
     - CONS: Risk of data loss if cache fails before async write

  4. REFRESH-AHEAD:
     - Proactively refresh cache before TTL expires for frequently accessed keys
     - PROS: Avoids cache miss latency spikes
     - CONS: Complex to implement; may refresh unused data

5. ELASTICACHE SECURITY
================================================================

  NETWORK:
    - Place ElastiCache in PRIVATE subnets (not public)
    - Security Groups: Allow only application servers to connect
    - In-transit encryption (TLS): Must enable at creation

  AUTHENTICATION (Redis only):
    - AUTH Token (password): Set at cluster creation
    - Redis RBAC (Role-Based Access Control) via user groups
    - Memcached: No built-in authentication

  ENCRYPTION:
    - At rest: AES-256 (stored data, backups, replicas)
    - In transit: TLS
    - Both must be enabled at creation — cannot enable on existing cluster

================================================================
6. ELASTICACHE SCALING
================================================================

  REDIS SCALING:
    Vertical (Scale Up/Down):
      - Change instance type
      - Requires minimal downtime (reads served from replica while primary scales)
    
    Horizontal Read Scaling:
      - Add more read replicas (up to 5 per shard)
    
    Horizontal Write Scaling (Cluster Mode Enabled only):
      - Add more shards
      - Online resharding available (no downtime)

  MEMCACHED SCALING:
    - Add/remove nodes (horizontal scaling only)
    - Data is distributed across nodes but NOT replicated
    - Removing a node = data on that node is lost (cold cache)

7. COMMON USE CASES AND PATTERNS
================================================================

  SESSION MANAGEMENT:
    - Store user session data in Redis instead of DB or sticky sessions
    - TTL = session timeout duration
    - Works with multiple application instances (stateless apps)
    - redis.setex("session:" + sessionId, 3600, serializedSession);

  DATABASE QUERY CACHING:
    - Cache results of expensive/frequent DB queries
    - Key: hash of SQL query or logical key (e.g., "users:active:page1")
    - TTL based on data freshness requirements

  LEADERBOARD (Sorted Sets):
    - Redis Sorted Sets: elements stored with score, automatically sorted
    - ZADD leaderboard 1000 "player1"
    - ZADD leaderboard 2500 "player2"
    - ZRANGE leaderboard 0 9 WITHSCORES REV  // Top 10 players

  RATE LIMITING:
    - INCR request_count:{userId}:{minute}
    - EXPIRE request_count:{userId}:{minute} 60
    - If count > limit: reject request

  REAL-TIME ANALYTICS:
    - HyperLogLog for approximate unique counts (e.g., unique visitors)
    - Bitmaps for tracking boolean attributes at scale (e.g., daily active users)

  PUB/SUB MESSAGING:
    - Redis channels for real-time notifications
    - Lightweight alternative to SQS/SNS for simple in-process messaging

8. INTERVIEW QUESTIONS
================================================================

Q: When would you use ElastiCache with RDS?
A: ElastiCache reduces database load by storing frequently read data in memory.
   Common scenario: an application reads the same data repeatedly (product catalog,
   user profiles, configuration). Each DB read takes milliseconds and consumes
   database connections. Caching these in Redis/Memcached means subsequent reads
   take microseconds and don't hit the DB. Benefits: lower DB CPU/connection count,
   faster response times, protection from read spikes. Tradeoff: cache invalidation
   complexity — you must handle stale data.

Q: What is the difference between Redis and Memcached?
A: Redis is feature-rich: supports advanced data structures (sorted sets, lists, hashes),
   persistence (RDB + AOF), replication with auto-failover, pub/sub, transactions,
   encryption. Memcached is simpler: strings only, no persistence, no replication,
   but multi-threaded and horizontally scalable. Use Redis for most production use cases
   (especially if you need HA or complex data structures). Use Memcached if you need
   simple, high-throughput caching with multi-threaded performance and can accept data loss.

Q: What is cache invalidation and what strategies exist?
A: Cache invalidation is ensuring cached data stays current when the underlying data changes.
   Strategies: 1) TTL-based expiration (let cache expire naturally — tolerate some staleness),
   2) Write-through (update cache and DB together on every write), 3) Cache-aside invalidation
   (delete the cache key when DB data changes, let next read repopulate), 4) Event-driven
   (DynamoDB Streams → Lambda → delete cache key on DB change). TTL-based is simplest but
   may serve stale data. Cache-aside deletion ensures consistency but causes cache miss on
   next read.

Q: What is Redis Cluster Mode and when should you use it?
A: Cluster Mode Enabled shards data across multiple nodes (up to 500 shards) using hash
   slots. Enables horizontal scaling for both reads AND writes when a single shard can't
   handle the write throughput. Use when: dataset doesn't fit in one node, need more write
   throughput than a single primary can provide. Limitation: can't use commands that span
   multiple keys across different slots (MGET, MSET, and some pipeline operations must use
   hash tags to colocate keys).
