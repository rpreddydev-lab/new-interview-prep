AWS NETWORKING — ROUTE 53 DNS
Complete Interview Preparation Guide
================================================================

1. ROUTE 53 OVERVIEW
================================================================

  Amazon Route 53 is a highly available, scalable DNS (Domain Name System) service.
  
  Three main functions:
    1. DOMAIN REGISTRATION: Register domain names (e.g., myapp.com)
    2. DNS HOSTING: Host DNS records for your domains (Hosted Zones)
    3. HEALTH CHECKING: Monitor endpoint health and route traffic accordingly

  100% SLA for basic DNS routing.
  
  Name "Route 53": DNS uses port 53.

================================================================
2. HOSTED ZONES
================================================================

  A Hosted Zone is a container for DNS records for a domain.
  
  PUBLIC HOSTED ZONE:
    - Contains DNS records for public internet-facing domains
    - e.g., myapp.com A record → 52.x.x.x (EC2 Elastic IP)
    - Any DNS resolver on the internet can query it
    - Cost: $0.50/month per hosted zone

  PRIVATE HOSTED ZONE:
    - Contains DNS records visible ONLY within associated VPCs
    - e.g., db.internal → 10.0.5.10 (RDS private IP)
    - Enables internal DNS names for private resources
    - Must associate with VPC(s) where it should be visible

  CREATE HOSTED ZONE:
  aws route53 create-hosted-zone \
    --name myapp.com \
    --caller-reference $(date +%s)

================================================================
3. DNS RECORD TYPES
================================================================

  A Record:
    - Maps hostname to IPv4 address
    - example.com → 52.1.2.3
  
  AAAA Record:
    - Maps hostname to IPv6 address
  
  CNAME Record:
    - Maps hostname to another hostname
    - api.myapp.com → lb-12345.us-east-1.elb.amazonaws.com
    - Cannot create CNAME for root domain (myapp.com) — use ALIAS instead
  
  ALIAS Record (AWS-specific):
    - Maps hostname to AWS resource (ALB, CloudFront, S3, etc.)
    - Works for ROOT DOMAIN (myapp.com) — unlike CNAME
    - No additional charge for queries
    - AWS automatically resolves to underlying IPs
    - Set: myapp.com → ALB DNS name
  
  NS Record:
    - Name Server records — which DNS servers are authoritative for the domain
    - Automatically created when you create a hosted zone
  
  SOA Record:
    - Start of Authority — metadata about the DNS zone
    - Auto-created
  
  MX Record:
    - Mail exchange servers
  
  TXT Record:
    - Arbitrary text — used for domain verification, SPF records

  ALIAS vs CNAME:
  ┌──────────────────┬──────────────────────────┬────────────────────────────┐
  │ Feature          │ CNAME                    │ ALIAS                      │
  ├──────────────────┼──────────────────────────┼────────────────────────────┤
  │ Root domain      │ NOT supported            │ Supported                  │
  │ Target           │ Any hostname             │ AWS resources only         │
  │ Cost             │ Charged per query        │ Free for AWS resources     │
  │ TTL              │ Configurable             │ Managed by AWS             │
  └──────────────────┴──────────────────────────┴────────────────────────────┘

4. ROUTING POLICIES
================================================================

  SIMPLE ROUTING:
    - Single resource, one IP (or a few)
    - No health checks
    - If multiple values in record: returns all IPs, client picks randomly
    - Use for: basic single-server setup, dev environments

  WEIGHTED ROUTING:
    - Route traffic by percentage across multiple resources
    - 70% to v1, 30% to v2 (gradual traffic shifting for deployments)
    - Set weight 0 to stop traffic to an endpoint without deleting record
    - Set all weights equal for load balancing

  LATENCY-BASED ROUTING:
    - Route to the region with LOWEST LATENCY for the user
    - You create records for same hostname in multiple regions
    - Route 53 measures latency from user to each region and picks lowest
    - Use for: global apps needing performance optimization

  FAILOVER ROUTING:
    - PRIMARY record (health checked)
    - SECONDARY record (failover target — another region, static page, etc.)
    - If primary health check fails → Route 53 returns secondary record
    - Use for: disaster recovery / active-passive configuration

  GEOLOCATION ROUTING:
    - Route based on USER'S GEOGRAPHIC LOCATION (country, continent)
    - EU users → EU instances; US users → US instances
    - Use for: legal compliance (GDPR data residency), localization, content restrictions
    - Must create a "default" record for users who don't match any location

  GEOPROXIMITY ROUTING (with Traffic Flow):
    - Route based on distance from resource and user with adjustable bias
    - Increase bias → more traffic to that resource (expands effective region)
    - Requires Route 53 Traffic Flow (visual editor)
    - More fine-grained than Geolocation

  MULTI-VALUE ROUTING:
    - Return multiple IPs (up to 8) with health checking per record
    - Unhealthy records are filtered out
    - Not a load balancer — client chooses randomly — but provides basic HA
    - Difference from Simple: Simple returns all records even if unhealthy

  WEIGHTED ROUTING — CLI EXAMPLE:
  # Create two records, same name, weighted routing
  aws route53 change-resource-record-sets \
    --hosted-zone-id ZONE_ID \
    --change-batch '{
      "Changes": [
        {
          "Action": "CREATE",
          "ResourceRecordSet": {
            "Name": "api.myapp.com",
            "Type": "A",
            "SetIdentifier": "v1",
            "Weight": 70,
            "TTL": 60,
            "ResourceRecords": [{ "Value": "52.1.1.1" }]
          }
        },
        {
          "Action": "CREATE",
          "ResourceRecordSet": {
            "Name": "api.myapp.com",
            "Type": "A",
            "SetIdentifier": "v2",
            "Weight": 30,
            "TTL": 60,
            "ResourceRecords": [{ "Value": "52.2.2.2" }]
          }
        }
      ]
    }'

5. HEALTH CHECKS
================================================================

  Route 53 can monitor endpoint health and route traffic only to healthy resources.
  
  TYPES:
    Endpoint check:      HTTP/HTTPS/TCP check to a URL or IP
    Calculated check:    Combine multiple health checks (AND/OR logic)
    CloudWatch alarm:    Trigger failover based on any CloudWatch alarm

  ENDPOINT CHECK:
    - Checks every 10 or 30 seconds
    - Considers healthy: endpoint responds with 2xx/3xx status in 4 seconds
    - 18% of Route 53 health checkers worldwide must see it healthy
    - Checks private resources via CloudWatch metric (health checkers are global, not in VPC)

  FAILOVER EXAMPLE:
    Primary: api.myapp.com → ALB in us-east-1 (with health check)
    Secondary: api.myapp.com → ALB in eu-west-1 (failover)
    
    If primary health check fails → Route 53 returns secondary record automatically.

6. ROUTE 53 RESOLVER
================================================================

  DNS RESOLUTION IN VPC:
    By default, VPC instances use Route 53 Resolver (169.254.169.253) for DNS.
    Resolves both public and private hosted zone records.

  ROUTE 53 RESOLVER ENDPOINTS:
    Inbound Endpoint:
      - On-premises → AWS: Resolve AWS private hosted zone records
      - On-premises DNS server forwards DNS queries for *.internal.myapp.com
        to the inbound endpoint in your VPC

    Outbound Endpoint:
      - AWS → On-premises: Resolve on-premises DNS names from AWS
      - VPC instances can resolve on-premises hostnames like db.corp.internal
      - Forwarding rules define which domains forward to on-premises DNS

  Use case: Hybrid cloud setup where:
    - AWS workloads need to resolve on-premises hostnames
    - On-premises servers need to resolve AWS private DNS names

7. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between CNAME and ALIAS records in Route 53?
A: Both redirect one hostname to another, but ALIAS records are AWS-specific and
   work for ROOT DOMAINS (e.g., myapp.com) while CNAME does NOT work at the zone
   apex. ALIAS records are free (no per-query cost). ALIAS targets must be AWS
   resources (ALB, CloudFront, S3, another Route 53 record). When you point myapp.com
   (without www) to an ALB, you must use an ALIAS record. For subdomains (api.myapp.com),
   either works.

Q: Which Route 53 routing policy would you use for a blue-green deployment?
A: Weighted Routing. Create two records with the same name: one pointing to the
   "blue" environment (weight=100) and one to the "green" environment (weight=0).
   To shift traffic gradually: change to weight=90/10, then 70/30, then 0/100.
   This allows incremental traffic shifting while monitoring metrics. If issues arise,
   shift weight back to blue immediately without downtime.

Q: What is the difference between Geolocation and Latency-based routing?
A: Geolocation routes based on WHERE the user is geographically (country/continent) —
   deterministic, used for compliance (GDPR — EU data stays in EU), language
   localization, or content restrictions. Latency-based routing routes to the AWS
   region with the LOWEST MEASURED LATENCY for that user — performance-based, not
   location-based. A US East Coast user might have lower latency to us-east-1, but
   a US West Coast user to us-west-2. Use Geolocation for compliance/localization;
   use Latency for best performance.

Q: How does Route 53 health check work with private resources?
A: Route 53 health checkers are publicly distributed and cannot reach private
   VPC resources directly. For private resources: 1) create a CloudWatch Metric
   and Alarm that monitors the resource (e.g., ALB target health), 2) create a
   Route 53 health check based on that CloudWatch Alarm state. When the alarm
   fires (resource unhealthy), Route 53 treats the health check as failed and
   triggers failover.
