AWS COMPUTE — EC2 INSTANCE TYPES AND PRICING MODELS
Complete Interview Preparation Guide

1. EC2 PRICING MODELS OVERVIEW
================================================================

  ┌──────────────────────────────────────────────────────────────────────┐
  │ MODEL             │ COMMITMENT │ SAVINGS vs On-Demand │ INTERRUPTIBLE │
  ├──────────────────────────────────────────────────────────────────────┤
  │ On-Demand         │ None       │ 0% (baseline)        │ No            │
  │ Reserved (1yr)    │ 1 year     │ Up to 40%            │ No            │
  │ Reserved (3yr)    │ 3 years    │ Up to 72%            │ No            │
  │ Savings Plans     │ 1 or 3 yrs │ Up to 72%            │ No            │
  │ Spot              │ None       │ Up to 90%            │ YES (2-min warn)│

  │ Dedicated Instance│ None       │ Premium for isolation│ No            │

================================================================
2. ON-DEMAND INSTANCES
================================================================

  - Pay per second (Linux/Ubuntu) or per hour (Windows, other)
  - No commitment, no upfront payment
  - Highest cost
  - Immediate availability
  
  Use cases:
  - Short-term, unpredictable workloads
  - Applications being developed or tested for the first time
  - Spiky workloads that cannot be predicted
  - Workloads that CANNOT be interrupted

================================================================
3. RESERVED INSTANCES (RIs)
================================================================

  Types:
    Standard RIs: Highest discount; cannot change instance family/OS
    Convertible RIs: Lower discount; CAN change instance family, OS, tenancy
    Scheduled RIs: Reserved for specific time windows (now deprecated; use Savings Plans)

  ATTRIBUTES (must all match to get discount):
    - Instance type (e.g., m5.xlarge)
    - Region
    - Tenancy (shared or dedicated)
    - OS (Linux or Windows)

  PAYMENT OPTIONS:
    All Upfront     → Best discount
    Partial Upfront → Medium discount
    No Upfront      → Smallest discount (still saves vs On-Demand)

  RI MARKETPLACE:
    - Buy/sell unused RIs
    - If you no longer need an RI before it expires, sell on the marketplace

  SCOPE:
    - Regional RI: Applies to any AZ in the region (flexible)
    - Zonal RI: Applies to a specific AZ (reserving capacity)

================================================================
4. SAVINGS PLANS
================================================================

  More flexible than RIs — commitment is a $/hour spend level,
  not a specific instance type.

  COMPUTE SAVINGS PLANS:
    - Most flexible: applies to any EC2 instance type, size, AZ, region, OS, tenancy
    - Also applies to Fargate and Lambda
    - Discount: up to 66% vs On-Demand
    - Commit: $10/hour spend for 1 or 3 years

  EC2 INSTANCE SAVINGS PLANS:
    - Applies to a specific instance family in a region (e.g., M5 in us-east-1)
    - ANY size, AZ, OS within that family/region
    - Discount: up to 72% vs On-Demand

  SAGEMAKER SAVINGS PLANS:
    - For ML SageMaker instances

  Why Savings Plans vs RIs?
    Savings Plans are preferred for most new workloads because they're:
    - More flexible (no need to specify exact instance type)
    - Simpler to manage
    - Cover EC2 + Fargate + Lambda with Compute Savings Plans

================================================================
5. SPOT INSTANCES
================================================================

  - Bid on spare EC2 capacity
  - Up to 90% savings vs On-Demand
  - AWS can reclaim (interrupt) with a 2-minute warning
  - Perfect for fault-tolerant, stateless workloads

  HOW SPOT PRICING WORKS:
    - Spot price fluctuates based on supply/demand
    - Set a maximum price (optional) or use current spot price
    - If spot price exceeds max, instance terminates or stops
    - Check Spot Instance Advisor for interruption frequency by instance type

  INTERRUPTION BEHAVIOR:
    - AWS gives 2-minute warning via instance metadata:
      http://169.254.169.254/latest/meta-data/spot/termination-time
    - Instance can be: Terminated, Stopped, or Hibernated (your choice)
    - Handle gracefully: save state, drain from load balancer, etc.

  SPOT FLEET:
    - Collection of Spot Instances (and optionally On-Demand)
    - Define multiple instance types, sizes, AZs to maximize availability
    - Auto-replaces interrupted instances with other available capacity

  SPOT BLOCKS (now deprecated):
    - Reserved Spot for 1-6 hours without interruption

  USE CASES:
    ✓ Batch processing jobs
    ✓ CI/CD pipelines
    ✓ Machine learning training
    ✓ Stateless web servers (with Auto Scaling, handles interruptions gracefully)
    ✓ Data analysis / ETL jobs
    ✗ NOT for: databases, critical apps that cannot tolerate interruptions

================================================================
6. DEDICATED HOSTS vs DEDICATED INSTANCES
================================================================

  DEDICATED INSTANCES:
    - Run on hardware dedicated to ONE AWS account
    - No other customers on the same host
    - But you don't control which specific host
    - Use case: Compliance requirements for dedicated hardware
    - Billing: Per-instance premium

  DEDICATED HOSTS:
    - Physical server FULLY dedicated to your use
    - You choose which instances run on which host
    - Full visibility into CPU sockets and cores
    - BYOL (Bring Your Own License) for per-socket/per-core licensing
    - Use cases: Software licenses tied to specific hardware (Oracle, Windows Server,
                 SQL Server), compliance requiring specific host identification
    - Most expensive option

7. INSTANCE TYPE SELECTION GUIDE
================================================================

  WORKLOAD                    → RECOMMENDED INSTANCE TYPE
  ─────────────────────────────────────────────────────
  Dev / Test                  → t3.micro, t3.small
  General web app             → t3.medium or m5.large
  High-traffic web / API      → m5.xlarge or m5.2xlarge
  CPU-intensive (encoding)    → c5.xlarge, c6i.2xlarge
  Memory-intensive (JVM, SAP) → r5.xlarge, r5.2xlarge
  In-memory DB (Redis)        → r6i.large
  ML Training                 → p3.2xlarge, p4d.24xlarge, trn1
  ML Inference (cost)         → inf1, inf2
  High IOPS DB                → i3.large, i4i.large
  Hadoop / data lake          → d3.2xlarge
  ARM/Graviton                → t4g, m6g, c6g (20-40% cheaper)

8. EC2 COST OPTIMIZATION STRATEGIES
================================================================

  1. RIGHT-SIZING: Use AWS Compute Optimizer recommendations
  2. PURCHASE MODELS: Mix Savings Plans (base load) + On-Demand (peak) + Spot (batch)
  3. GRAVITON: Move to arm64 Graviton instances (up to 40% savings)
  4. AUTO SCALING: Scale down when not needed; terminate idle dev instances
  5. SCHEDULES: Stop dev/test instances nights and weekends (70% savings)
  6. SPOT FOR BATCH: Use Spot instances for batch and fault-tolerant workloads
  7. RESERVED CAPACITY: Savings Plans for predictable baseline load
  8. TAGGING: Tag all instances to track costs by team/project

  TYPICAL ARCHITECTURE (cost-optimized):
    - 30-40% of fleet: Savings Plans (baseline)
    - 30-40% of fleet: On-Demand (predictable overflow)
    - 20-40% of fleet: Spot (batch, stateless, interruptible)

9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Reserved Instances and Savings Plans?
A: Both offer long-term commitment discounts (1 or 3 years), but Savings Plans
   are more flexible. Reserved Instances require you to commit to a specific
   instance type, region, and OS. Savings Plans commit to a $/hour spend level —
   Compute Savings Plans are the most flexible (any EC2 type, Fargate, Lambda).
   EC2 Instance Savings Plans commit to an instance family in a region but allow
   any size, AZ, and OS. Savings Plans are now generally preferred over RIs for
   their flexibility.

Q: When should you use Spot instances?
A: Spot instances when your workload is: fault-tolerant (can handle sudden interruption),
   stateless (no persistent state that would be lost), or able to checkpoint state.
   Perfect for: batch processing, CI/CD pipelines, ML training, data analytics.
   NOT suitable for: production databases, real-time user-facing applications with
   no fallback, or any job that cannot afford the 2-minute interruption warning.

Q: What is the difference between a Dedicated Instance and a Dedicated Host?
A: Dedicated Instances run on hardware dedicated to one account but AWS controls
   which physical host. Dedicated Hosts give you full visibility and control over
   a specific physical server, including socket/core information. Dedicated Hosts
   are required for BYOL (Bring Your Own License) software like Oracle or SQL Server
   licensed per-socket/per-core. Both ensure no shared tenancy with other customers.

Q: How do you choose between t3, m5, c5, and r5 instance types?
A: T3 is burstable (good for variable CPU dev/test workloads). M5 is balanced
   general-purpose. C5 is compute-optimized (more vCPUs per RAM dollar — for
   CPU-bound tasks like video encoding, scientific computing). R5 is
   memory-optimized (more RAM per vCPU — for large in-memory databases, caching,
   big JVM applications). When unsure, start with M5 and use AWS Compute Optimizer
   to analyze actual usage and recommend right-sizing.

Q: You have a 24x7 Java application server with predictable load. What is the most
   cost-effective EC2 pricing strategy?
A: Use a Compute Savings Plan or EC2 Instance Savings Plan with 1-year or 3-year
   commitment for the baseline (predictable) capacity — saves up to 72% vs
   On-Demand. For occasional burst capacity above the baseline, use On-Demand.
   If possible, evaluate Graviton (ARM) instance types (t4g, m6g) for additional
   20-40% cost savings if the Java app is compatible with ARM architecture.
