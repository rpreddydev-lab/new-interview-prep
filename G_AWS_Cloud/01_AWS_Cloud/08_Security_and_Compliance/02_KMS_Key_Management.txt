AWS SECURITY — KMS KEY MANAGEMENT SERVICE
Complete Interview Preparation Guide
================================================================

1. KMS OVERVIEW
================================================================

  AWS Key Management Service (KMS) is a managed service for creating 
  and controlling encryption keys.
  
  Core concept: ENVELOPE ENCRYPTION
  
  ┌─────────────────────────────────────────────────────────────┐
  │                  ENVELOPE ENCRYPTION                        │
  │                                                             │
  │  1. KMS creates a DATA KEY (plain + encrypted copy)         │
  │  2. Use plain data key to encrypt your data locally         │
  │  3. Store ENCRYPTED data key alongside your ciphertext      │
  │  4. Discard plain data key from memory                      │
  │  5. To decrypt: call KMS to decrypt the encrypted data key, │
  │     use resulting plain data key to decrypt your data       │
  │                                                             │
  │  CMK never leaves KMS — data key does the actual encryption │
  └─────────────────────────────────────────────────────────────┘
  
  Why envelope encryption?
    - CMK can only encrypt 4 KB directly
    - Encrypt large data without sending it to KMS network
    - Data key is cached; reduces KMS API calls and cost

2. KEY TYPES
================================================================

  ┌─────────────────────┬───────────────────────────────────────────────────────┐
  │ Key Type            │ Description                                           │
  ├─────────────────────┼───────────────────────────────────────────────────────┤
  │ AWS Owned Keys      │ Free, fully managed by AWS, no visibility/control     │
  │                     │ e.g., default SSE-S3, default DynamoDB encryption     │
  │ AWS Managed Keys    │ Created by AWS services in your account (aws/service) │
  │                     │ Free, key policy managed by service, auto-rotated     │
  │                     │ e.g., aws/s3, aws/rds, aws/ebs                        │
  │ Customer Managed    │ You create and control, $1/month per key              │
  │ Keys (CMKs)         │ Custom key policy, manual or auto rotation, auditable │
  │ Imported Key        │ Bring your own key material, $1/month                 │
  │ Material            │ You responsible for key material backup               │
  └─────────────────────┴───────────────────────────────────────────────────────┘

3. KEY POLICIES
================================================================

  Every KMS key has a RESOURCE-BASED POLICY called a key policy.
  
  Without a key policy allowing IAM to manage the key, even 
  IAM policies cannot grant KMS access!
  
  Default key policy (allows root account full access):
  {
    "Sid": "Enable IAM User Permissions",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
    "Action": "kms:*",
    "Resource": "*"
  }
  
  Add a specific user/role to a key:
  {
    "Sid": "Allow Lambda Function",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:role/my-lambda-role" },
    "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
    "Resource": "*"
  }
  
  KEY GRANTS:
    - Temporary programmatic access to a CMK
    - Used for cross-service encryption (EMR, Redshift Spectrum)
    - More granular than key policies, can be scoped by encryption context

4. KEY OPERATIONS (CLI)
================================================================

  CREATE CMK:
  aws kms create-key \
    --description "App encryption key" \
    --key-usage ENCRYPT_DECRYPT \
    --key-spec SYMMETRIC_DEFAULT

  CREATE ALIAS (human-readable name):
  aws kms create-alias \
    --alias-name alias/my-app-key \
    --target-key-id 12345678-1234-5678-abcd-1234567890ab

  ENCRYPT (up to 4 KB):
  aws kms encrypt \
    --key-id alias/my-app-key \
    --plaintext fileb://secret.txt \
    --query CiphertextBlob \
    --output text | base64 --decode > encrypted.bin

  DECRYPT:
  aws kms decrypt \
    --ciphertext-blob fileb://encrypted.bin \
    --query Plaintext \
    --output text | base64 --decode

  GENERATE DATA KEY:
  aws kms generate-data-key \
    --key-id alias/my-app-key \
    --key-spec AES_256
  # Returns: Plaintext (use to encrypt) + CiphertextBlob (store with data)

  ENABLE AUTO KEY ROTATION (annual, CMKs only):
  aws kms enable-key-rotation --key-id alias/my-app-key

================================================================
5. KEY ROTATION
================================================================

  AWS MANAGED KEYS: Rotated automatically every year by AWS
  
  CUSTOMER MANAGED KEYS (Symmetric):
    - Enable auto rotation: rotates every year
    - Old key material kept forever to decrypt old ciphertext
    - Key ID/alias don't change — transparent to applications
    - Manual rotation: create new key, update alias, schedule deletion of old key
    
  ASYMMETRIC KEYS: No automatic rotation (manual only)

  Key DELETION:
    - Schedule deletion 7–30 days in advance (default 30)
    - Cannot delete immediately — waiting period for safety
    - KEY CANNOT BE RECOVERED AFTER DELETION
    - Disable key first if you just want to stop use without deletion

================================================================
6. ENCRYPTION CONTEXT
================================================================

  Optional key-value pairs you can include in encrypt/decrypt calls.
  
  Purpose:
    - Binds ciphertext to specific context (prevents data misuse)
    - Must provide same context to decrypt
    - Context appears in CloudTrail logs for auditing
  
  Example: Encrypt an order, bound to that orderId:
  aws kms encrypt \
    --key-id alias/my-app-key \
    --plaintext fileb://card.txt \
    --encryption-context orderId=123,env=prod
  
  To decrypt, must provide the same context:
  aws kms decrypt \
    --ciphertext-blob fileb://encrypted.bin \
    --encryption-context orderId=123,env=prod

================================================================
7. MULTI-REGION KEYS
================================================================

  KMS Multi-Region Keys allow encrypting in one region and 
  decrypting in another.
  
  Use cases:
    - Active-active global databases (Aurora Global)
    - Cross-region disaster recovery
    - Client-side encryption for DynamoDB global tables
  
  Key IDs have same key ID across regions (mrk-... prefix)
  Key material is replicated; NOT the same as single-region key copies

================================================================
8. CLOUDTRAIL INTEGRATION
================================================================

  Every KMS API call is logged in CloudTrail:
    - Who called Decrypt/Encrypt
    - Which key was used
    - From which IP address and user agent
    - Encryption context used
    - Whether the request was allowed or denied

9. JAVA SDK v2 — KMS OPERATIONS
================================================================

  import software.amazon.awssdk.services.kms.KmsClient;
  import software.amazon.awssdk.services.kms.model.*;
  import software.amazon.awssdk.core.SdkBytes;
  
  private static final KmsClient kmsClient = KmsClient.create();
  
  // DIRECT ENCRYPT (up to 4 KB)
  public SdkBytes encrypt(String keyId, String plaintext) {
      EncryptResponse response = kmsClient.encrypt(
          EncryptRequest.builder()
              .keyId(keyId)
              .plaintext(SdkBytes.fromUtf8String(plaintext))
              .encryptionContext(Map.of("app", "my-service", "env", "prod"))
              .build()
      );
      return response.ciphertextBlob();
  }
  
  // DIRECT DECRYPT
  public String decrypt(SdkBytes ciphertext) {
      DecryptResponse response = kmsClient.decrypt(
          DecryptRequest.builder()
              .ciphertextBlob(ciphertext)
              .encryptionContext(Map.of("app", "my-service", "env", "prod"))
              .build()
      );
      return response.plaintext().asUtf8String();
  }
  
  // GENERATE DATA KEY (envelope encryption pattern)
  public EncryptedData encryptLargeData(String keyId, byte[] data) {
      GenerateDataKeyResponse dataKey = kmsClient.generateDataKey(
          GenerateDataKeyRequest.builder()
              .keyId(keyId)
              .keySpec(DataKeySpec.AES_256)
              .build()
      );
  
      // Use plaintext data key to encrypt data (AES/GCM locally)
      byte[] encryptedData = aesEncrypt(data, dataKey.plaintext().asByteArray());
      
      // Store alongside the encrypted data key
      // NEVER store plaintext data key
      return new EncryptedData(encryptedData, dataKey.ciphertextBlob().asByteArray());
  }
  
  // LIST KEY ALIASES
  public void listAliases() {
      ListAliasesResponse response = kmsClient.listAliases(
          ListAliasesRequest.builder().build()
      );
      response.aliases().forEach(alias ->
          System.out.println(alias.aliasName() + " -> " + alias.targetKeyId())
      );
  }

10. INTERVIEW QUESTIONS
================================================================

Q: Explain envelope encryption and why it is used.
A: Envelope encryption is a two-layer encryption approach. You use a CMK in KMS to 
   encrypt a Data Key. The Data Key (in plaintext) encrypts your actual data locally. 
   Then you store the encrypted data key alongside the encrypted data and throw away the 
   plaintext data key. 
   
   Why: (1) KMS CMKs can only directly encrypt up to 4 KB — not practical for large files.
   (2) The actual encryption happens locally on your machine/Lambda — no network latency 
   for large data, and data never leaves your compute. (3) The CMK never leaves KMS 
   HSMs, maintaining the root of trust. (4) You can reuse a cached data key to encrypt 
   many messages, reducing KMS API call costs.

Q: What is the difference between AWS Managed Keys and Customer Managed Keys?
A: AWS Managed Keys (aws/s3, aws/rds) are created by AWS services in your account, 
   rotated automatically, and you can see them in KMS but cannot change the key policy 
   or use them directly in your code — they're for automatic service encryption. No cost.
   
   Customer Managed Keys (CMKs) are created by you, giving you full control: 
   custom key policies (who can use/manage), grants, enable/disable, schedule deletion, 
   manual rotation, cross-account access, encryption context, and CloudTrail auditing 
   per key. Cost $1/month per key. Use CMKs when you need: audit trail, cross-account 
   sharing, custom access control, or BYOK (bring your own key material).

Q: If a developer accidentally deletes a KMS CMK, how do you prevent data loss?
A: KMS has a mandatory waiting period of 7-30 days before actual deletion. During this 
   time, cancel the deletion via the console or CLI. Best practices: (1) Enable CloudTrail 
   to alert on kms:ScheduleKeyDeletion API calls. (2) Use SCPs to deny ScheduleKeyDeletion 
   for production keys. (3) Create a CloudWatch alarm on the CloudTrail metric filter for 
   key deletion events. (4) Require MFA for key deletion in the key policy. (5) Disable 
   the key first (immediately stops encryption operations) rather than deleting.
