AWS OVERVIEW — GLOBAL INFRASTRUCTURE: REGIONS AND AZs
Complete Interview Preparation Guide
================================================================

1. AWS GLOBAL INFRASTRUCTURE (2025)
================================================================

  - 33 Geographic Regions
  - 105 Availability Zones
  - 400+ Edge Locations (CloudFront)
  - 13 AWS Local Zones (metro-area compute)
  - 29 AWS Wavelength Zones (5G network edge)

================================================================
2. REGIONS
================================================================

Definition:
  A Region is a physical location in the world where AWS clusters data centers.
  Each region is completely independent and isolated from other regions.

Key Characteristics:
  - Each region has at least 2 (usually 3) Availability Zones
  - Data does NOT automatically replicate across regions
  - You choose which region to deploy resources in
  - Latency to end users depends on region proximity
  - Some services are global (IAM, Route 53, CloudFront)
  - Most services are regional (EC2, S3, RDS, Lambda)

Important Regions:
  us-east-1      N. Virginia   — first AWS region; cheapest; most services launch here
  us-east-2      Ohio
  us-west-1      N. California
  us-west-2      Oregon
  eu-west-1      Ireland
  eu-central-1   Frankfurt
  ap-southeast-1 Singapore
  ap-northeast-1 Tokyo
  ap-south-1     Mumbai
  sa-east-1      São Paulo

How to choose a region:
  1. Compliance/Data sovereignty — data must stay in country (GDPR, data residency laws)
  2. Latency — deploy close to users
  3. Service availability — not all services in all regions
  4. Pricing — varies by region (us-east-1 typically cheapest)

================================================================
3. AVAILABILITY ZONES (AZs)
================================================================

Definition:
  An AZ is one or more discrete data centers with redundant power, networking,
  and connectivity in a Region. AZs are separated by meaningful physical distance
  (many km apart) but connected with low-latency fiber (< 2ms).

Key Characteristics:
  - Each AZ is isolated — failure in one doesn't affect others
  - Single point of failure: deploying in only 1 AZ
  - Multi-AZ deployments provide high availability
  - AZs are named: us-east-1a, us-east-1b, us-east-1c
  - Actual locations are obfuscated (us-east-1a for account A ≠ account B)

Multi-AZ Pattern:
  ┌──────────────────── us-east-1 ─────────────────────┐
  │                                                      │
  │  ┌──────────────┐   ┌──────────────┐                │
  │  │  us-east-1a  │   │  us-east-1b  │  ...           │
  │  │  EC2 + RDS   │   │  EC2 + RDS   │                │
  │  │  (primary)   │   │  (standby)   │                │
  │  └──────────────┘   └──────────────┘                │
  │                                                      │
  └──────────────────────────────────────────────────────┘

  If us-east-1a fails → ELB routes traffic to us-east-1b automatically
  RDS Multi-AZ promotes standby replica in us-east-1b

4. EDGE LOCATIONS AND CLOUDFRONT
================================================================

  Edge Locations (400+):
    - CloudFront CDN caching nodes
    - Much more numerous than regions (cities worldwide)
    - Cache static content closer to users (lower latency)
    - Also used by: Route 53 (DNS resolution), Shield (DDoS protection)

  Regional Edge Caches:
    - Larger cache between edge locations and origin servers
    - Content not in edge locations → checked here before origin

  AWS Local Zones:
    - Extension of a region placed in specific metro areas
    - Ultra-low latency for users in cities without a full region
    - Example: Los Angeles Local Zone extends us-west-2

  AWS Wavelength Zones:
    - Deployed at 5G carrier networks
    - Single-digit millisecond latency for mobile applications
    - Compute at the mobile network edge

================================================================
5. HIGH AVAILABILITY VS. FAULT TOLERANCE VS. DISASTER RECOVERY
================================================================

  High Availability (HA):
    - System remains operational despite component failures
    - Achieved with Multi-AZ deployments
    - Target: 99.9% - 99.99% uptime
    - Example: RDS Multi-AZ, EC2 Auto Scaling across AZs

  Fault Tolerance:
    - System continues operating EVEN during failures (no downtime)
    - Higher cost than HA
    - Example: Active-active multi-AZ with stateless apps

  Disaster Recovery (DR):
    - Recovery after a major failure (region-level)
    - RTO (Recovery Time Objective) — acceptable downtime
    - RPO (Recovery Point Objective) — acceptable data loss
    
    DR Strategies (cheapest → most expensive):
      Backup & Restore    → high RTO/RPO, low cost
      Pilot Light         → minimal core infra in DR region
      Warm Standby        → scaled-down live stack in DR region
      Multi-Site Active   → full live stack in multiple regions

================================================================
6. RESILIENCE BEST PRACTICES
================================================================

  1. Deploy across ≥2 AZs (High Availability minimum)
  2. Use Auto Scaling Groups with multi-AZ subnets
  3. Use RDS Multi-AZ for databases
  4. Use ELB to distribute traffic across AZs
  5. Decouple services with SQS/SNS
  6. Store state in managed services (S3, DynamoDB, RDS) not local EC2 storage
  7. Define and regularly test DR procedures
  8. Use Route 53 health checks + failover routing for multi-region

================================================================
7. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between an AWS Region and an Availability Zone?
A: A Region is a geographic area (e.g., us-east-1 = N. Virginia) containing
   multiple isolated Availability Zones. An AZ is one or more physically separate
   data centers within a region with independent power and networking. Regions are
   independent of each other (data doesn't cross regions automatically). AZs within
   a region are isolated for fault tolerance but connected with low-latency fiber.

Q: How would you design a highly available architecture on AWS?
A: Deploy EC2 instances in an Auto Scaling Group across at least 2 AZs.
   Put an Application Load Balancer in front, spanning all AZs. Use RDS
   Multi-AZ for database. Store session state in ElastiCache (not EC2).
   Use S3 for static assets. Enable Route 53 health checks for DNS failover.
   This ensures that an AZ failure causes automatic failover with no manual
   intervention.

Q: What is the difference between HA and Fault Tolerance?
A: HA (High Availability) means the system has minimal downtime and quickly
   recovers from failures — there may be brief interruptions. Fault Tolerance
   means the system continues to function WITHOUT ANY interruption even during
   failures. Fault tolerance requires redundant active components (active-active),
   which is more expensive. Multi-AZ RDS (standby failover) = HA. Stateless
   EC2 behind ELB (all AZs active simultaneously) approaches fault tolerance.

Q: What is the difference between RTO and RPO in disaster recovery?
A: RTO (Recovery Time Objective) — maximum acceptable time the system can be
   down after a disaster. RPO (Recovery Point Objective) — maximum acceptable
   amount of data loss measured in time (e.g., RPO = 1 hour means you might
   lose up to 1 hour of data). Shorter RTO/RPO requires more expensive solutions.
   Backup & Restore = high RTO; Multi-site active = near-zero RTO.
