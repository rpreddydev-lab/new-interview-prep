================================================================
AWS STORAGE — S3 VERSIONING AND REPLICATION
Complete Interview Preparation Guide
================================================================

1. S3 VERSIONING
================================================================

  Versioning keeps MULTIPLE VERSIONS of an object in the same bucket.
  Protects against accidental deletions and overwrites.

  STATE TRANSITIONS:
    Unversioned → Versioned (cannot go back to Unversioned)
    Versioned → Versioning Suspended (new objects get "null" version ID)
    When versioning is Suspended, existing versions are preserved.

  Enable versioning:
  aws s3api put-bucket-versioning \
    --bucket my-bucket \
    --versioning-configuration Status=Enabled

  How versioning works:
  - Every PUT creates a new version with unique version ID
  - GET without version ID returns the LATEST version
  - GET with version ID returns that specific version
  - DELETE without version ID creates a "delete marker" (latest version = delete marker,
    object appears deleted but older versions remain)
  - DELETE with version ID permanently deletes THAT specific version
  - To restore a "deleted" object: delete the delete marker

  Delete marker behavior:
  - Is itself a version object (has a version ID)
  - Is returned as "current version" when you list the object
  - S3 returns 404 when the current version is a delete marker
  - Delete the delete marker → previous version becomes current again

  Retrieve a specific version:
  aws s3api get-object \
    --bucket my-bucket \
    --key document.pdf \
    --version-id "3sL4kqtJlcpXrsDtxxx" \
    document_v1.pdf

  List all versions:
  aws s3api list-object-versions \
    --bucket my-bucket \
    --prefix document.pdf

2. MFA DELETE
================================================================

  MFA Delete adds an extra layer of security for versioned buckets.
  When enabled, MFA is REQUIRED to:
    1. Permanently delete an object version
    2. Change bucket versioning status (enable/disable/suspend)

  Requirements:
    - Must enable versioning first
    - Root account credentials required to configure
    - MFA device (virtual or hardware) required

  Enable MFA Delete (only via CLI with root credentials):
  aws s3api put-bucket-versioning \
    --bucket my-bucket \
    --versioning-configuration '{
      "MFADelete":"Enabled",
      "Status":"Enabled"
    }' \
    --mfa "arn:aws:iam::123456789012:mfa/root-account-mfa-device 123456"

  Use case: Highly sensitive data that must be protected from accidental
  or malicious deletion by compromised admin credentials.

3. S3 REPLICATION
================================================================

  Replication automatically and asynchronously copies objects from
  a SOURCE bucket to a DESTINATION bucket.

  PREREQUISITES (both CRR and SRR):
    ✓ Versioning MUST be enabled on BOTH source and destination buckets
    ✓ IAM role that S3 can assume to read from source and write to destination
    ✓ Bucket policy on destination must allow source account's role (for cross-account)
    ✓ Objects must not be encrypted with SSE-C (SSE-S3 and SSE-KMS replication supported)

  TYPES:
    CRR — Cross-Region Replication: source and destination in DIFFERENT regions
    SRR — Same-Region Replication:  source and destination in SAME region

  CRR USE CASES:
    - Compliance (data must be stored in another region/country)
    - Lower latency for global users (replicate to nearest region)
    - Cross-account replication (prod → audit account)
    - Disaster recovery — active data in backup region

  SRR USE CASES:
    - Log aggregation (multiple source buckets → single log bucket)
    - Test environments that mirror production data
    - Live replication between production accounts in same region
    - Maintain a copy in the same region for a different team/account

================================================================
4. SETTING UP REPLICATION
================================================================

  Step 1: Create IAM role for replication
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Service": "s3.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }]
  }

  Permissions policy for the role:
  {
    "Statement": [
      {
        "Effect": "Allow",
        "Action": ["s3:GetObject","s3:GetObjectVersionAcl","s3:GetObjectVersionTagging",
                   "s3:ListBucket","s3:GetReplicationConfiguration"],
        "Resource": ["arn:aws:s3:::source-bucket","arn:aws:s3:::source-bucket/*"]
      },
      {
        "Effect": "Allow",
        "Action": ["s3:ReplicateObject","s3:ReplicateDelete","s3:ReplicateTags",
                   "s3:GetObjectVersionTagging","s3:ObjectOwnerOverrideToBucketOwner"],
        "Resource": "arn:aws:s3:::destination-bucket/*"
      }
    ]
  }

  Step 2: Configure replication rule
  aws s3api put-bucket-replication \
    --bucket source-bucket \
    --replication-configuration '{
      "Role": "arn:aws:iam::123456789012:role/s3-replication-role",
      "Rules": [{
        "ID": "ReplicateLogs",
        "Status": "Enabled",
        "Filter": { "Prefix": "logs/" },
        "Destination": {
          "Bucket": "arn:aws:s3:::destination-bucket",
          "StorageClass": "STANDARD_IA"
        }
      }]
    }'

================================================================
5. REPLICATION CONFIGURATION OPTIONS
================================================================

  FILTER: Replicate a subset of objects
    By Prefix: Only objects starting with "logs/"
    By Tag:    Only objects with tag { "Environment": "prod" }
    By Both:   Prefix AND tag (using And filter)
    No Filter: Replicate all objects (set Filter: {})

  STORAGE CLASS AT DESTINATION:
    - Can specify a different (cheaper) storage class for replica
    - Default: same as source object's storage class

  REPLICA OWNERSHIP:
    - By default: replica owned by SOURCE account (for same-account)
    - For cross-account: Use "AccessControlTranslation" to change owner
      to destination account (so destination account can read it)

  DELETE MARKER REPLICATION:
    - By default: DELETE MARKERS are NOT replicated
    - Must explicitly enable if you want deletes to propagate:
      "DeleteMarkerReplication": { "Status": "Enabled" }

  REPLICATION TIME CONTROL (RTC):
    - SLA: 99.99% of objects replicated within 15 MINUTES
    - CloudWatch metrics for replication lag
    - Additional cost: ~$0.015/GB replicated
    - Use case: Compliance requiring tight RPO, audit requirements

================================================================
6. WHAT IS NOT REPLICATED
================================================================

  ✗ Objects that existed BEFORE replication was enabled
    (replication is not retroactive — must use S3 Batch Replication)
  ✗ Objects in Glacier Flexible or Deep Archive storage class
  ✗ Objects encrypted with SSE-C (customer-provided keys)
  ✗ Objects where the bucket owner doesn't have permission
  ✗ S3 Lifecycle actions (transitions, expirations)
  ✗ Objects in destination region that were replicated there from elsewhere
    (no chaining — A→B→C doesn't work automatically without separate config)
  ✗ Delete markers (by default — must explicitly enable)

================================================================
7. BATCH REPLICATION
================================================================

  For objects that existed BEFORE replication was configured.
  Also used to re-replicate objects that failed to replicate.

  aws s3control create-job \
    --account-id 123456789012 \
    --manifest-generator ... \
    --operation '{ "S3ReplicateObject": {} }' \
    --priority 10 \
    --role-arn arn:aws:iam::123456789012:role/S3BatchRole

  S3 Batch Replication creates a job that finds all objects matching your
  criteria and queues replication for each.

================================================================
8. VERSIONING + REPLICATION: INTERACTION RULES
================================================================

  ┌──────────────────────────────────────────────────────────────────┐
  │ Action at Source          │ What's Replicated                    │
  ├──────────────────────────────────────────────────────────────────┤
  │ PUT new object            │ Object + version ID replicated       │
  │ PUT new version           │ New version replicated               │
  │ DELETE (delete marker)    │ NOT replicated by default            │
  │ DELETE specific version   │ NOT replicated (permanent delete)    │
  └──────────────────────────────────────────────────────────────────┘

================================================================
9. VERSIONING LIFECYCLE POLICIES
================================================================

  Manage storage costs for versioned buckets:

  {
    "Rules": [{
      "ID": "CleanupOldVersions",
      "Status": "Enabled",
      "NoncurrentVersionTransitions": [{
        "NoncurrentDays": 30,
        "StorageClass": "STANDARD_IA"
      }],
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 90
      },
      "ExpiredObjectDeleteMarker": true   // Auto-delete delete markers with no versions
    }]
  }

  Explanation:
    - NoncurrentVersionTransitions: After a version is superseded, move it to IA after 30 days
    - NoncurrentVersionExpiration: Permanently delete non-current versions after 90 days
    - ExpiredObjectDeleteMarker: Automatically remove delete markers that have no remaining versions

10. INTERVIEW QUESTIONS
================================================================

Q: What happens when you delete a versioned object in S3?
A: A "delete marker" is created as the new "current" version. The object appears
   deleted (S3 returns 404) but all previous versions are still stored. The delete
   marker has its own version ID. To "undelete" the object, delete the delete marker —
   the previous version becomes current again. To permanently delete the object,
   you must delete ALL versions including all delete markers using their specific version IDs.

Q: What is the difference between CRR and SRR?
A: CRR (Cross-Region Replication) copies objects to a bucket in a DIFFERENT region —
   used for compliance (data sovereignty), disaster recovery, or low-latency access
   for global users. SRR (Same-Region Replication) copies to a bucket in the SAME
   region — used for log aggregation, maintaining a live copy for a separate team,
   or replicating to a different account in the same region. Both require versioning
   enabled on both buckets.

Q: Are objects replicated before a replication rule was created?
A: No. Standard replication is NOT retroactive — only new objects created after
   the rule is established are replicated. To replicate existing objects, use
   S3 Batch Replication, which creates a batch operations job that processes
   existing objects and queues them for replication.

Q: Does deleting an object in the source bucket delete it in the replica?
A: By default, NO. Delete markers are NOT replicated in S3 CRR/SRR. This is a
   deliberate safety measure to protect against accidental deletes propagating
   to your replica. If you want deletes to propagate, you must explicitly enable
   Delete Marker Replication in your replication configuration.

Q: How do you control costs for a versioned S3 bucket?
A: Use lifecycle rules targeting non-current versions:
   1. NoncurrentVersionTransitions: Move old versions to cheaper storage classes
      (Standard-IA or Glacier) after N days
   2. NoncurrentVersionExpiration: Permanently delete non-current versions after N days
   3. Keep only the last N versions using NumberOfNewerNoncurrentVersions parameter
   4. Use ExpiredObjectDeleteMarker to auto-clean stale delete markers
   Without these rules, a versioned bucket can accumulate unlimited old versions and
   storage costs grow indefinitely.
