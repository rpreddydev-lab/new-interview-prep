================================================================
AWS STORAGE — S3 SECURITY AND BUCKET POLICIES
Complete Interview Preparation Guide
================================================================

1. S3 SECURITY OVERVIEW
================================================================

S3 access control is multi-layered:
  1. Block Public Access (account/bucket level guardrail)
  2. Bucket Policies (resource-based — who can access)
  3. ACLs (legacy, largely replaced by bucket policies)
  4. IAM Policies (identity-based — what the user can do)
  5. Presigned URLs (temporary access)
  6. Encryption (data protection at rest and in transit)

================================================================
2. BLOCK PUBLIC ACCESS
================================================================

  The strongest safeguard against unintended public exposure.
  Available at BUCKET and ACCOUNT levels.

  SETTINGS (4 independent toggles):
    BlockPublicAcls:        Reject bucket/object ACLs that grant public access
    IgnorePublicAcls:       Ignore existing public ACLs (don't evaluate them)
    BlockPublicPolicy:      Reject bucket policies that grant public access
    RestrictPublicBuckets:  Restrict access to only AWS services and authorized users
                            when the policy already grants public access

  Best practice: Enable ALL 4 at the account level by default
  aws s3control put-public-access-block \
    --account-id 123456789012 \
    --public-access-block-configuration \
    "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

  If you need to host a public website, disable specifically for that bucket
  while keeping the account-level block on for all other buckets.

================================================================
3. BUCKET POLICIES
================================================================

  Bucket policies are resource-based IAM policies attached to S3 buckets.
  They define WHO can access the bucket and WHAT they can do.

  POLICY STRUCTURE (same as IAM):
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "AllowPublicRead",
        "Effect": "Allow",
        "Principal": "*",                    // Everyone
        "Action": "s3:GetObject",
        "Resource": "arn:aws:s3:::my-bucket/*"
      }
    ]
  }

  COMMON BUCKET POLICY PATTERNS:

  1. Enforce HTTPS Only:
  {
    "Statement": [{
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }]
  }

  2. Restrict access to specific VPC:
  {
    "Statement": [{
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringNotEquals": { "aws:SourceVpc": "vpc-12345678" }
      }
    }]
  }

  3. Allow cross-account access:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::ACCOUNT_B:root" },
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ]
    }]
  }

  4. Allow only specific IAM role:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::123456789012:role/AppRole" },
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }]
  }

  5. Allow CloudFront OAC (Origin Access Control) only:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/DISTRIBUTION_ID"
        }
      }
    }]
  }

4. S3 ACCESS CONTROL LISTS (ACLs)
================================================================

  Legacy mechanism for controlling access at bucket and object level.
  
  Types:
    - Private (default): owner has full control
    - Public-read: anyone can read
    - Authenticated-read: any authenticated AWS user can read
    - Bucket-owner-full-control: bucket owner gets full control on new objects
  
  Recommendation: Disable ACLs and use bucket policies instead.
  In 2022, AWS made ACLs disabled (Object Ownership: Bucket owner enforced) the
  recommended default for new buckets.

5. S3 ENCRYPTION
================================================================

ENCRYPTION AT REST:
  SSE-S3 (Server-Side Encryption with S3 Keys):
    - AWS manages the keys entirely
    - AES-256 encryption
    - Free
    - Header: x-amz-server-side-encryption: AES256
    - Default for new buckets since Jan 2023
  
  SSE-KMS (Server-Side Encryption with KMS Keys):
    - Uses KMS Customer Managed Key (CMK)
    - You control key policies (who can use the key)
    - Audit key usage in CloudTrail
    - Additional cost: KMS API calls ($0.03/10,000 calls)
    - Header: x-amz-server-side-encryption: aws:kms
    - Best for: regulatory compliance, access audit requirements
  
  SSE-C (Server-Side Encryption with Customer-Provided Keys):
    - You provide the encryption key with EVERY API call
    - AWS uses it and DISCARDS it immediately (doesn't store)
    - Only via HTTPS
    - Rare use case: if you must control the key outside AWS
  
  CSE (Client-Side Encryption):
    - Encrypt data BEFORE sending to S3
    - AWS has no access to plaintext or keys
    - Use for: data that should never be seen by AWS
    - Manage keys yourself (AWS Encryption SDK helps)

ENCRYPTION IN TRANSIT:
  - Always use HTTPS (TLS) for S3 API calls
  - Enforce with bucket policy: Deny when aws:SecureTransport = false

ENFORCE ENCRYPTION AT UPLOAD:
  # Bucket policy to require SSE-KMS on all uploads
  {
    "Statement": [{
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"
        }
      }
    }]
  }

6. S3 ACCESS CONTROL FLOW
================================================================

  Request → AWS evaluates in this order:

  1. Is Block Public Access enabled? → YES + request is "public" → DENY
  2. Is there an explicit DENY in bucket policy? → DENY
  3. Is there an explicit ALLOW in IAM policy (for AWS principal)? → Check bucket policy too
  4. Same account: IAM OR bucket policy ALLOW → ALLOW
  5. Cross-account: BOTH IAM (source account) AND bucket policy MUST allow → ALLOW
  6. Default: DENY

7. S3 VPC ENDPOINT (GATEWAY ENDPOINT)
================================================================

  Access S3 from EC2 in a VPC WITHOUT going through the internet.
  
  S3 Gateway Endpoint:
    - Free
    - Route table entry: S3 traffic routes within AWS network
    - Bucket policy can restrict to only VPC endpoint traffic
    - No NAT gateway needed for EC2 in private subnets to access S3
  
  Add VPC endpoint to route table:
  aws ec2 create-vpc-endpoint \
    --vpc-id vpc-12345678 \
    --service-name com.amazonaws.us-east-1.s3 \
    --route-table-ids rtb-12345678
  
  Bucket policy to restrict to VPC only:
  {
    "Statement": [{
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpce": "vpce-12345678"  // Your S3 endpoint ID
        }
      }
    }]
  }

8. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between an S3 bucket policy and an IAM policy for S3 access?
A: IAM policy is identity-based — attached to users/roles to define what they can do
   across AWS services including S3. Bucket policy is resource-based — attached to the
   S3 bucket to define who can access IT. Key difference: bucket policies can specify
   "Principal" (who) and work across accounts without requiring role assumption.
   For same-account access, either works. For cross-account access without role
   assumption, bucket policies are required (or both IAM + bucket policy must allow).

Q: What are the 4 Block Public Access settings and why are they important?
A: BlockPublicAcls prevents new public ACLs; IgnorePublicAcls ignores existing
   public ACLs; BlockPublicPolicy rejects new public bucket policies;
   RestrictPublicBuckets restricts buckets with public policies to AWS services only.
   They're important because accidental S3 public exposure is one of the most common
   cloud security incidents. These act as guardrails that prevent accidental data
   leaks even if someone mistakenly sets a public policy or ACL.

Q: What is SSE-S3 vs SSE-KMS for S3 encryption? When would you use each?
A: SSE-S3 uses AWS-managed keys — transparent, free, no additional setup. SSE-KMS
   uses Customer Managed KMS keys — you control who can use the key via KMS key
   policy, and every encrypt/decrypt is logged in CloudTrail. Use SSE-S3 for most
   general workloads (free, automatic). Use SSE-KMS when you need: audit of who
   accessed what data (compliance/HIPAA/PCI), ability to revoke access by disabling
   the key, or cross-account access with specific key policies.

Q: How do you ensure all S3 uploads are encrypted?
A: Two approaches: 1) Enable default bucket encryption (SSE-S3 or SSE-KMS) — AWS
   automatically encrypts all new objects. 2) Add a bucket policy that DENIES
   s3:PutObject when x-amz-server-side-encryption header is not set to "AES256" or
   "aws:kms". The default encryption handles most cases; the bucket policy is an
   additional enforcement for compliance requirements.

Q: What is the purpose of an S3 VPC Gateway Endpoint?
A: An S3 VPC Gateway Endpoint allows EC2 instances in private subnets to access
   S3 without traversing the internet (no NAT Gateway required). Traffic stays
   within the AWS network, reducing cost and improving security. The endpoint adds
   an entry to your VPC route tables that directs S3-destined traffic to the endpoint.
   You can also restrict bucket access to only traffic from specific VPC endpoints
   using bucket policy conditions.
