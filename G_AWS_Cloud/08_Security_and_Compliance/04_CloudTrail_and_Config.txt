================================================================
AWS SECURITY — CLOUDTRAIL & AWS CONFIG
Complete Interview Preparation Guide
================================================================

1. CLOUDTRAIL OVERVIEW
================================================================

  AWS CloudTrail records API calls made in your AWS account.
  "Who did what to which resource and when?"
  
  Enabled by default: Last 90 days of management events in Event History.
  To retain longer / add S3: create a TRAIL.

================================================================
2. CLOUDTRAIL EVENT TYPES
================================================================

  ┌───────────────────┬──────────────────────────────────────────────┐
  │ Event Type        │ Description                                  │
  ├───────────────────┼──────────────────────────────────────────────┤
  │ Management Events │ Operations on AWS resources                  │
  │                   │ e.g., CreateBucket, RunInstances, PutPolicy  │
  │                   │ Default: Read + Write both logged            │
  │ Data Events       │ Operations ON resource data                  │
  │                   │ e.g., S3 GetObject/PutObject, Lambda Invoke  │
  │                   │ NOT enabled by default (high volume/cost)    │
  │ Insight Events    │ Unusual API call volume detection            │
  │                   │ e.g., spike in EC2 TerminateInstances calls  │
  └───────────────────┴──────────────────────────────────────────────┘

================================================================
3. CLOUDTRAIL TRAIL
================================================================

  CREATE TRAIL:
  aws cloudtrail create-trail \
    --name org-trail \
    --s3-bucket-name my-cloudtrail-logs \
    --is-multi-region-trail \
    --include-global-service-events \
    --enable-log-file-validation
  
  START LOGGING:
  aws cloudtrail start-logging --name org-trail
  
  KEY OPTIONS:
    --is-multi-region-trail:          Captures events from ALL regions (recommended)
    --include-global-service-events:  IAM, STS, CloudFront events (global services)
    --enable-log-file-validation:     SHA-256 digest files to detect log tampering
    --is-organization-trail:          Captures events from all accounts in AWS Org
  
  WHERE LOGS GO:
    - S3 Bucket (JSON files, prefix: AWSLogs/accountId/CloudTrail/region/yyyy/mm/dd/)
    - CloudWatch Logs (for real-time alerting via metric filters)
    - CloudTrail Lake (for ad-hoc SQL querying, no need to export to S3)

5. CLOUDTRAIL ALERTS WITH CLOUDWATCH
================================================================

  Setup: CloudTrail → CloudWatch Logs → Metric Filter → Alarm → SNS
  
  Common alerts to create:
  
  1. Root account login:
     Pattern: { $.userIdentity.type = "Root" }
  
  2. IAM policy changes:
     Pattern: { ($.eventName = DeleteGroupPolicy) || ($.eventName = PutGroupPolicy) ||
                ($.eventName = PutRolePolicy) || ($.eventName = PutUserPolicy) }
  
  3. Console login failures:
     Pattern: { ($.eventName = ConsoleLogin) && ($.errorMessage = "Failed authentication") }
  
  4. S3 bucket deletion:
     Pattern: { ($.eventSource = s3.amazonaws.com) && ($.eventName = DeleteBucket) }
  
  CLI example:
  aws logs put-metric-filter \
    --log-group-name CloudTrailLogs \
    --filter-name root-login \
    --filter-pattern '{ $.userIdentity.type = "Root" }' \
    --metric-transformations '[{
      "metricName": "RootLogin",
      "metricNamespace": "SecurityAlerts",
      "metricValue": "1"
    }]'

6. AWS CONFIG OVERVIEW
================================================================

  AWS Config continuously records the CONFIGURATION STATE of 
  your AWS resources over time.
  "What is the current state of my infrastructure, and how has it changed?"
  
  Answers questions like:
    - Was this security group open to 0.0.0.0/0 yesterday?
    - When was this S3 bucket made public?
    - Does every EC2 instance have an IAM profile?
    - Are all RDS instances encrypted?

================================================================
7. AWS CONFIG — KEY CONCEPTS
================================================================

  CONFIGURATION ITEM (CI):
    - Snapshot of a resource at a point in time
    - Includes: configuration, relationships, tags, event that triggered the change
  
  CONFIGURATION RECORDER:
    - Records configuration changes for resources in the region
    - Stores CIs in S3 (configuration history bucket)
  
  CONFIG RULES:
    - Checks whether resources comply with desired configurations
    - Triggered by: configuration change or on a schedule
    - Result: COMPLIANT or NON_COMPLIANT
    
    Managed Rules (AWS provided, 150+ rules):
      - s3-bucket-public-read-prohibited
      - encrypted-volumes (EBS)
      - rds-instance-public-access-check
      - iam-root-access-key-check
      - restricted-ssh (SG not allowing SSH from 0.0.0.0/0)
    
    Custom Rules: Lambda function called by Config
  
  REMEDIATION ACTIONS:
    - Manual: flag non-compliant and alert
    - Automatic: associate an SSM Automation document to fix automatically
    - Example: Auto-tag EC2 instances, revoke SSH access from 0.0.0.0/0
  
  CONFORMANCE PACKS:
    - Bundle of rules and remediation actions
    - Deploy as a CloudFormation template
    - AWS provides pre-built packs: CIS AWS Foundations, PCI-DSS, HIPAA, etc.

8. AWS CONFIG — CLI
================================================================

  ENABLE RECORDER:
  aws configservice put-configuration-recorder \
    --configuration-recorder name=default,roleARN=arn:aws:iam::123456789012:role/config-role \
    --recording-group allSupported=true,includeGlobalResourceTypes=true
  
  SET DELIVERY CHANNEL (where to store):
  aws configservice put-delivery-channel \
    --delivery-channel '{
      "name": "default",
      "s3BucketName": "my-config-bucket",
      "snsTopicARN": "arn:aws:sns:us-east-1:123456789012:config-alerts"
    }'
  
  START RECORDER:
  aws configservice start-configuration-recorder --configuration-recorder-name default
  
  PUT MANAGED RULE:
  aws configservice put-config-rule \
    --config-rule '{
      "ConfigRuleName": "s3-bucket-public-read-prohibited",
      "Source": {
        "Owner": "AWS",
        "SourceIdentifier": "S3_BUCKET_PUBLIC_READ_PROHIBITED"
      }
    }'
  
  LIST COMPLIANCE:
  aws configservice describe-compliance-by-config-rule \
    --config-rule-names s3-bucket-public-read-prohibited
  
  GET COMPLIANCE DETAILS FOR RESOURCE:
  aws configservice get-compliance-details-by-resource \
    --resource-type AWS::S3::Bucket \
    --resource-id my-sensitive-bucket

9. CLOUDTRAIL vs AWS CONFIG
================================================================

  ┌──────────────────────┬───────────────────────────┬────────────────────────────────┐
  │ Dimension            │ CloudTrail                │ AWS Config                     │
  ├──────────────────────┼───────────────────────────┼────────────────────────────────┤
  │ Question answered    │ Who did what and when?    │ What is the state of resources?│
  │ Focus                │ API actions (events)      │ Resource configuration state   │
  │ Data retention       │ 90 days (Event History)   │ History in S3 indefinitely     │
  │                      │ or custom (trail to S3)   │                                │
  │ Compliance checks    │ No                        │ Yes (Config Rules)             │
  │ Alerting             │ Via CloudWatch metric      │ Via SNS on rule violation      │
  │                      │ filters                   │                                │
  │ Auto-remediation     │ No                        │ Yes (SSM Automation)           │
  │ Use case             │ Security forensics,        │ Configuration compliance,      │
  │                      │ audit trail, detect       │ inventory, drift detection,    │
  │                      │ unauthorized actions      │ change history                 │
  └──────────────────────┴───────────────────────────┴────────────────────────────────┘

10. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between CloudTrail and AWS Config?
A: CloudTrail records API call activity — who called which AWS API, when, and from where.
   It answers "who deleted that S3 bucket?" or "who changed that IAM policy?"
   AWS Config records the configuration state of resources over time and checks compliance.
   It answers "is this S3 bucket currently public?" or "which EC2 instances don't have 
   encrypted EBS volumes?" Both are complementary: use CloudTrail for audit/forensics 
   and security event detection; use Config for compliance validation, inventory, and 
   configuration change history.

Q: How would you detect and alert when someone logs in as the AWS root user?
A: CloudTrail + CloudWatch:
   1. Create a CloudTrail trail with logging to CloudWatch Logs.
   2. Create a CloudWatch metric filter on the log group with pattern:
      { $.userIdentity.type = "Root" && $.eventType != "AwsServiceEvent" }
   3. Create a CloudWatch Alarm triggered when metric >= 1.
   4. Alarm notifies an SNS topic which emails the security team.
   This is a CIS AWS Foundations Benchmark recommended control. Can also use AWS Security 
   Hub which automates this check.

Q: How would you automatically fix non-compliant S3 buckets that are publicly accessible?
A: AWS Config auto-remediation:
   1. Create a Config Rule: s3-bucket-public-read-prohibited (or s3-bucket-server-side-
      encryption-enabled for encryption compliance)
   2. Associate a Remediation Action using SSM Automation document 
      AWS-DisableS3BucketPublicReadWrite (AWS-provided document)
   3. Set remediation as AUTOMATIC — when Config marks a bucket NON_COMPLIANT, it 
      automatically invokes the SSM document which enables Block Public Access
   4. CloudTrail records the remediation action for audit
   For critical environments, use manual remediation + SNS alert first, or test 
   auto-remediation in dev before prod to avoid unexpected side effects.
