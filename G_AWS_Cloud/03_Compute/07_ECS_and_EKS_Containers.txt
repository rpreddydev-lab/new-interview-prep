1. CONTAINERS ON AWS OVERVIEW
================================================================

AWS provides multiple container management services:

  Amazon ECS (Elastic Container Service):
    - AWS-native container orchestration
    - Fully managed control plane
    - Simpler; no Kubernetes knowledge needed
    - Deep AWS integration (IAM, ALB, CloudWatch, Secrets Manager)

  Amazon EKS (Elastic Kubernetes Service):
    - Managed Kubernetes on AWS
    - Same K8s API as on-premises / other clouds
    - Use when: already using K8s, need portability, large engineering teams
    - More complex but more powerful and portable

  Amazon ECR (Elastic Container Registry):
    - Managed Docker/OCI image registry
    - Stores container images used by ECS and EKS
    - Private by default; supports vulnerability scanning
    - Integrated with IAM for access control

2. AMAZON ECS — DEEP DIVE
================================================================

KEY COMPONENTS:

  TASK DEFINITION:
    - Blueprint describing the container (like a docker-compose.yml)
    - Defines: Docker image, CPU/memory, ports, environment variables,
               logging, IAM task role, volumes, network mode
    - Versioned (each update creates a new revision)

  TASK:
    - A running instance of a task definition
    - Can run one or more containers defined in the task definition
    - Running a task = "one-off job" (like a cron job)

  SERVICE:
    - Long-running tasks (like a web server)
    - Maintains desired number of tasks
    - Integrates with ALB for load balancing
    - Handles task failures (restarts automatically)
    - Supports rolling deployments and blue/green deployments

  CLUSTER:
    - Logical grouping of tasks and services
    - Can use EC2 launch type (you manage EC2 instances)
    - Or Fargate launch type (serverless — AWS manages)

NETWORK MODES:
  ┌────────────────────────────────────────────────────────────────┐
  │ MODE      │ DESCRIPTION                                        │
  ├────────────────────────────────────────────────────────────────┤
  │ awsvpc    │ Each task gets its OWN ENI and private IP          │
  │           │ Best: security groups per task, ALB integration    │
  │           │ REQUIRED for Fargate                               │
  ├────────────────────────────────────────────────────────────────┤
  │ bridge    │ Default Docker networking on EC2                   │
  │           │ Uses docker0 virtual bridge                        │
  │           │ Dynamic host port mapping                          │
  ├────────────────────────────────────────────────────────────────┤
  │ host      │ Container uses EC2 host's network directly         │
  │           │ Best performance; but port conflicts possible      │
  ├────────────────────────────────────────────────────────────────┤
  │ none      │ No networking (isolated containers)                │
  └────────────────────────────────────────────────────────────────┘

IAM ROLES IN ECS:
  Task Execution Role: Used by ECS agent to pull images from ECR, get secrets,
                       write logs to CloudWatch. AWS-managed policy: 
                       AmazonECSTaskExecutionRolePolicy
  
  Task Role: IAM role assumed by containers in the task to call AWS services
             (DynamoDB, S3, SQS). This is what your application uses.

3. ECS DEPLOYMENT STRATEGIES
================================================================

  Rolling Update (default):
    - Gradually replace old tasks with new tasks
    - Define minimumHealthyPercent and maximumPercent
    - Example: min=50%, max=200% → doubles tasks, waits for health checks,
                                    then removes old tasks
    - Zero downtime for ALB-integrated services

  Blue/Green (with CodeDeploy):
    - Create entirely new "green" task set
    - ALB shifts traffic from "blue" (old) to "green" (new)
    - Option: test green before shifting traffic
    - Option: shift traffic linearly (10% per minute) or all-at-once
    - Easy rollback: shift traffic back to blue

4. AMAZON EKS — DEEP DIVE
================================================================

KEY COMPONENTS:

  Control Plane (AWS managed):
    - API server, etcd, scheduler, controller manager
    - AWS handles: multi-AZ, patching, upgrades (with your approval)
    - You pay: ~$0.10/hour per cluster

  Worker Nodes:
    - EC2 instances running kubelet + container runtime
    - Managed Node Groups: AWS provisions and updates EC2 instances
    - Self-managed: You manage EC2 instances
    - Fargate Profile: Serverless pods (no EC2 management)

  EKS ADD-ONS:
    - CoreDNS (cluster DNS)
    - kube-proxy (network rules)
    - Amazon VPC CNI (pod networking using VPC IPs)
    - AWS Load Balancer Controller (ALB Ingress Controller)

AWS VPC CNI:
  - Each pod gets a real VPC IP address (from the VPC subnet)
  - Pods can directly communicate with other AWS services
  - Security groups apply to pods (Security Groups for Pods feature)

ALB INGRESS CONTROLLER:
  - Kubernetes Ingress → creates an ALB
  - Path-based routing to different Kubernetes services
  - Supports: HTTP/HTTPS, SSL termination, WAF integration

IRSA (IAM Roles for Service Accounts):
  - Gives Kubernetes pods fine-grained AWS IAM permissions
  - Each Service Account maps to an IAM role
  - Replaces EC2 node-level IAM roles (too broad)
  
  How it works:
  1. Create IAM OIDC provider for the EKS cluster
  2. Create IAM role with trust policy for the service account
  3. Annotate Kubernetes service account with role ARN
  4. Pods using that service account automatically get credentials

  kubectl annotate serviceaccount -n my-namespace my-sa \
    eks.amazonaws.com/role-arn=arn:aws:iam::123456789012:role/MyRole

5. ECR — ELASTIC CONTAINER REGISTRY
================================================================

  # Authenticate Docker to ECR
  aws ecr get-login-password --region us-east-1 | \
    docker login --username AWS \
    --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
  
  # Create repository
  aws ecr create-repository --repository-name my-java-app
  
  # Build and push image
  docker build -t my-java-app .
  docker tag my-java-app:latest \
    123456789012.dkr.ecr.us-east-1.amazonaws.com/my-java-app:latest
  docker push \
    123456789012.dkr.ecr.us-east-1.amazonaws.com/my-java-app:latest

  FEATURES:
    - Private and public registries
    - Image scanning (basic: CVE scan on push; enhanced: Amazon Inspector)
    - Image lifecycle policies (auto-delete old images)
    - Replication across regions/accounts
    - Cross-account access via ECR resource-based policies

================================================================

  ├──────────────────────────────────────────────────────────────┤
  │ Learning Curve    │ Low                   │ High             │
  │ AWS Integration   │ Native/deep           │ Good (via addons)│
  │ Portability       │ AWS-specific          │ Highly portable  │
  │ Community         │ AWS ecosystem         │ K8s community    │
  │ Control Plane Cost│ Free                  │ ~$0.10/hr        │
  │ Networking        │ awsvpc (ENI per task) │ VPC CNI (ENI per pod)│

  │ Use case          │ AWS-native apps       │ Multi-cloud, K8s │

7. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between a Task Definition and a Task in ECS?
A: A Task Definition is the blueprint — it specifies the Docker image, CPU/memory,
   ports, IAM roles, environment variables, and logging configuration. It's versioned.
   A Task is a running instance of a task definition. Running a task once (like a
   cron job) creates one task. An ECS Service runs and maintains N tasks continuously,
   replacing failed tasks and integrating with load balancers.

Q: What is the difference between Task Role and Task Execution Role in ECS?
A: The Task Execution Role is used by the ECS infrastructure agent to: pull the
   container image from ECR, retrieve secrets from Secrets Manager/Parameter Store,
   and write logs to CloudWatch. It's an AWS operational concern. The Task Role is
   used by the APPLICATION running inside the container to call AWS services
   (DynamoDB, S3, SQS). These are two separate IAM roles for separation of concerns.

Q: What is IRSA in EKS and why is it important?
A: IRSA (IAM Roles for Service Accounts) lets individual Kubernetes pods assume
   specific IAM roles rather than inheriting the broad IAM role of the EC2 node.
   Without IRSA, all pods on an EC2 node share the same IAM permissions — a
   vulnerability. With IRSA, you annotate a Kubernetes Service Account with an
   IAM role ARN, and only pods using that service account get those permissions.
   This provides least-privilege IAM access per microservice in EKS.

Q: When would you choose ECS over EKS?
A: Choose ECS when: you're building AWS-native workloads and don't need K8s portability,
   you want simpler operations with less Kubernetes expertise required, you want deep
   AWS integration without installing addons, and you don't have existing K8s investment.
   Choose EKS when: you already use Kubernetes on-premises or other clouds, you need
   K8s portability, you have a large team with Kubernetes expertise, or you need
   specific K8s ecosystem tools (Helm, Istio, Argo CD, etc.).

Q: How does ECS service discovery work?
A: ECS integrates with AWS Cloud Map for service discovery. When using awsvpc
   network mode, tasks register in Cloud Map with their private IPs. Other services
   discover them by DNS name (e.g., payment-service.local). ALB can also be used
   for external service discovery. For internal microservice communication, use an
   internal ALB or Cloud Map service discovery with DNS resolution.
