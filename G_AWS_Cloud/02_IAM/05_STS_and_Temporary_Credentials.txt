================================================================
AWS IAM — STS AND TEMPORARY CREDENTIALS
Complete Interview Preparation Guide
================================================================

1. WHAT IS AWS STS?
================================================================

AWS Security Token Service (STS) is a web service that enables you to
request temporary, limited-privilege credentials for IAM users or federated users.

Key characteristics:
  - Issues short-lived credentials (15 minutes to 12 hours, or up to 36 hours
    for AssumeRoleWithWebIdentity)
  - No need to create long-term IAM users for every use case
  - Temporary credentials automatically expire
  - STS is a global service with regional endpoints available

Temporary Credential Components:
  - Access Key ID (starts with ASIA, not AKIA)
  - Secret Access Key
  - Session Token (must be used together with access key)
  - Expiration time

================================================================
2. STS API OPERATIONS
================================================================

AssumeRole
  Most common. IAM users or roles assume another role for cross-account
  or privilege escalation (within limits of permissions boundaries).
  
  aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/CrossAccountRole \
    --role-session-name MySession \
    --duration-seconds 3600
  
  Returns:
  {
    "Credentials": {
      "AccessKeyId": "ASIAIOSFODNN7EXAMPLE",
      "SecretAccessKey": "wJalrXUtnFEMI/K7MDENGbPxRfiCYEXAMPLEKEY",
      "SessionToken": "AQoEXAMPLEH4aoAH0gNCAPyJxz4BlCFFxWNE1OPTgk...",
      "Expiration": "2024-01-15T23:28:33Z"
    }
  }
  
  Duration: 15 min to 12 hours (role max session duration controls max)

---

AssumeRoleWithWebIdentity
  For users authenticated via a web identity provider (Amazon, Google,
  Facebook) or any OIDC-compatible IdP. Used by mobile apps.
  
  aws sts assume-role-with-web-identity \
    --role-arn arn:aws:iam::123456789012:role/MobileAppRole \
    --role-session-name mobile-session \
    --web-identity-token <jwt-from-oidc-provider>
  
  Note: For modern workloads, use Amazon Cognito instead of calling
  AssumeRoleWithWebIdentity directly.
  
  Duration: 15 min to 1 hour

---

AssumeRoleWithSAML
  For users authenticated via SAML 2.0 identity providers (Active Directory,
  Okta, Azure AD, PingIdentity).
  
  Flow:
  User → IdP (SAML assertion) → POST to AWS SSO endpoint → STS → Credentials
  
  Duration: 15 min to 1 hour

---

GetFederationToken
  For proxying credentials to federated users (custom identity broker).
  The calling user's permissions are intersected with the requested policy.
  
  Duration: 15 min to 36 hours
  Note: Cannot be used with IAM roles; requires long-term IAM user credentials

---

GetSessionToken
  For IAM users who need to call AWS with MFA. Gets temporary credentials
  with MFA verification for API/CLI access.
  
  aws sts get-session-token \
    --serial-number arn:aws:iam::123456789012:mfa/alice \
    --token-code 123456 \
    --duration-seconds 3600
  
  Duration: 15 min to 36 hours
  Use case: Enable MFA for programmatic access

3. USING TEMPORARY CREDENTIALS IN CODE (Java SDK)
================================================================

// Using AssumeRole with AWS SDK v2 for Java
import software.amazon.awssdk.services.sts.StsClient;
import software.amazon.awssdk.services.sts.model.AssumeRoleRequest;
import software.amazon.awssdk.services.sts.model.AssumeRoleResponse;
import software.amazon.awssdk.auth.credentials.AwsSessionCredentials;
import software.amazon.awssdk.auth.credentials.StaticCredentialsProvider;
import software.amazon.awssdk.services.s3.S3Client;

public class CrossAccountAccess {
    public S3Client getS3ClientForRole(String roleArn) {
        // Step 1: Assume the role
        StsClient stsClient = StsClient.create();
        
        AssumeRoleRequest assumeRoleRequest = AssumeRoleRequest.builder()
            .roleArn(roleArn)
            .roleSessionName("my-cross-account-session")
            .durationSeconds(3600)
            .build();
        
        AssumeRoleResponse response = stsClient.assumeRole(assumeRoleRequest);
        
        // Step 2: Extract temporary credentials
        AwsSessionCredentials tempCreds = AwsSessionCredentials.create(
            response.credentials().accessKeyId(),
            response.credentials().secretAccessKey(),
            response.credentials().sessionToken()
        );
        
        // Step 3: Create S3 client with those credentials
        return S3Client.builder()
            .credentialsProvider(StaticCredentialsProvider.create(tempCreds))
            .build();
    }
}

// Easier: Use StsAssumeRoleCredentialsProvider (auto-refreshes)
import software.amazon.awssdk.auth.credentials.StsAssumeRoleCredentialsProvider;

StsAssumeRoleCredentialsProvider provider = StsAssumeRoleCredentialsProvider.builder()
    .stsClient(StsClient.create())
    .refreshRequest(AssumeRoleRequest.builder()
        .roleArn("arn:aws:iam::123456789012:role/MyRole")
        .roleSessionName("auto-refresh-session")
        .build())
    .build();

S3Client s3 = S3Client.builder()
    .credentialsProvider(provider)
    .build();
// Credentials automatically refreshed before expiration!

4. CROSS-ACCOUNT ACCESS PATTERN
================================================================

SCENARIO: App in Account A needs to access S3 in Account B

SETUP STEPS:

Step 1 — In Account B (resource account), create a role:
  Trust Policy:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::ACCOUNT_A:root" },
      "Action": "sts:AssumeRole"
    }]
  }
  
  Permission Policy:
  { "Statement": [{ "Effect": "Allow", "Action": "s3:*", "Resource": "*" }] }

Step 2 — In Account A, create a policy allowing AssumeRole:
  {
    "Statement": [{
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::ACCOUNT_B:role/S3AccessRole"
    }]
  }
  Attach this to the Lambda/EC2 role in Account A.

Step 3 — Code in Account A calls STS to get temp credentials for Account B's role:
  → Uses those credentials to access S3 in Account B

ARCHITECTURE:
  Account A (app)         Account B (data)
  +---------------+       +------------------+
  | Lambda        |  STS  | Role: S3Access    |
  | (IAM Role) ───────────► (Trust: AccountA) |
  |               | assume|                  |
  |               |◄──────┤ Temp Credentials  |
  |               |       +------------------+
  | Use credentials        | S3 Bucket        |
  +───────────────────────► (data bucket)    |
                           +------------------+

5. EXTERNAL ID FOR CROSS-ACCOUNT ROLES
================================================================

Problem: The "Confused Deputy" attack — Account B role could be tricked
by a malicious Account C if Account B is a 3rd-party SaaS provider.

Solution: External ID
  - Account B (SaaS) gives Account A a unique External ID
  - Account A's trust policy requires that External ID
  - Only the real Account A would know the correct External ID
  
  Trust Policy with ExternalId:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::SAAS_ACCOUNT:root" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "unique-external-id-xyz" }
      }
    }]
  }

6. SESSION POLICIES
================================================================

When calling AssumeRole, you can pass an inline session policy to
FURTHER RESTRICT (not expand) the permissions of the assumed role.

  aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/AdminRole \
    --role-session-name restricted-session \
    --policy '{"Statement":[{"Effect":"Allow","Action":["s3:GetObject"],"Resource":"*"}]}'
  
  Result: Even though AdminRole has full access, this session can only do s3:GetObject
  
  Use case: Temporary restricted access for a specific task

7. INTERVIEW QUESTIONS
================================================================

Q: What is AWS STS and why is it important?
A: STS (Security Token Service) issues temporary security credentials with
   a limited lifetime (minutes to hours). This is important because temporary
   credentials reduce security risk — they expire automatically, so even if
   compromised, the window of exposure is limited. STS powers IAM role assumption,
   cross-account access, federated identity, and MFA-required programmatic access.

Q: What is the difference between AssumeRole and GetSessionToken?
A: AssumeRole is used to switch to a different IAM role (within same account or
   cross-account), gaining that role's permissions. Used by services, cross-account
   access, and federated identity. GetSessionToken is used by an existing IAM user
   to get temporary credentials that include MFA verification — the user keeps their
   own identity but gets time-limited credentials that prove MFA was used. You can't
   assume a role with GetSessionToken.

Q: What is the "Confused Deputy" problem in IAM?
A: It's a security vulnerability where a 3rd-party service (SaaS) creates cross-account
   roles for customers, but a malicious customer tricks the service into using another
   customer's role. Solution: External ID. The resource owner adds a unique ExternalId
   condition to their trust policy — only the legitimate requester who was given the
   ExternalId can assume the role, preventing the confused deputy attack.

Q: How long can temporary credentials last?
A: AssumeRole: 15 minutes to 12 hours (configurable on the role's MaxSessionDuration,
   up to 12 hours). Role chaining (assume role from an already assumed role): max 1 hour.
   GetFederationToken: 15 minutes to 36 hours. GetSessionToken: 15 minutes to 36 hours.
   AssumeRoleWithWebIdentity: 15 minutes to 1 hour.

Q: How do you automatically refresh temporary credentials in Java SDK?
A: Use StsAssumeRoleCredentialsProvider. It wraps the AssumeRole call and
   automatically refreshes credentials before they expire (typically 5 minutes
   before expiration). The S3/DynamoDB client using this provider always has
   valid credentials without any manual refresh logic.
