1. X-RAY OVERVIEW
================================================================

  AWS X-Ray provides distributed tracing for applications — 
  visualize requests flowing through microservices, identify 
  bottlenecks, and analyze errors.
  
  ┌────────────────────────────────────────────────────────────────┐
  │  Request Flow Visualization (Service Map)                      │
  │                                                                │
  │  Client → API Gateway → Lambda → DynamoDB                      │
  │            [12ms]       [45ms]   [8ms]                         │
  │                         ↓                                      │
  │                       SQS → Lambda → RDS                       │
  │                      [5ms]   [120ms]  [25ms]                   │
  └────────────────────────────────────────────────────────────────┘

2. X-RAY CONCEPTS
================================================================

  TRACE:
    - End-to-end journey of a request
    - Composed of one or more SEGMENTS
    - Has a unique Trace ID: X-Amzn-Trace-Id header
  
  SEGMENT:
    - Data about work done by a single service/resource
    - Contains: host, request, response, duration, error/fault
    - Example: one segment per Lambda invocation, EC2 service
  
  SUBSEGMENT:
    - Granular breakdown within a segment
    - Example: a DynamoDB call, HTTP call to external API, SQL query
    - Provides timing, metadata for that specific operation
  
  SERVICE MAP:
    - Visual graph of all services and their connections
    - Shows response time percentiles, error/fault rates
    - Color-coded: green (OK), yellow (errors), red (faults)
  
  ANNOTATIONS:
    - Key-value pairs indexed for filtering traces
    - Used in Filter Expressions to search traces
    - Example: userId, orderId, region
  
  METADATA:
    - Key-value pairs NOT indexed — for debugging detail only
    - Arbitrary data, not searchable in filter expressions
    - Example: full request payload, intermediate state
  
  ERRORS vs FAULTS vs THROTTLES:
    - Error: 4xx response (client error)
    - Fault: 5xx response (server error) — shown in red on service map
    - Throttle: 429 response (too many requests)

3. X-RAY SAMPLING
================================================================

  X-Ray does NOT record every request (would be too expensive).
  Uses SAMPLING to record a representative subset.
  
  Default sampling rule:
    - Record FIRST request per second per host (reservoir)
    - Then 5% of additional requests (rate)
  
  Custom sampling rules (via X-Ray console or API):
    - Match criteria: service name, HTTP method, URL path
    - Set custom reservoir and rate
    - Example: 100% sample /health check paths = 0 (skip)
    - Example: 10% sample for high-volume /api/v1/products

4. X-RAY WITH LAMBDA
================================================================

  Enable: Set TracingConfig.Mode = "Active" on Lambda function
  
  aws lambda update-function-configuration \
    --function-name my-function \
    --tracing-config Mode=Active
  
  Lambda automatically creates:
    - Segment for the Lambda function itself
    - Subsegments for AWS SDK calls (DynamoDB, S3, SQS)
  
  Active vs PassThrough:
    - Active: Lambda samples and records traces
    - PassThrough: Lambda records if trace header exists (upstream decides)

5. JAVA SDK X-RAY INSTRUMENTATION
================================================================

  Add X-Ray SDK dependency:
  <!-- pom.xml -->
  <dependency>
      <groupId>com.amazonaws</groupId>
      <artifactId>aws-xray-recorder-sdk-core</artifactId>
      <version>2.14.0</version>
  </dependency>
  <dependency>
      <groupId>com.amazonaws</groupId>
      <artifactId>aws-xray-recorder-sdk-aws-sdk-v2</artifactId>
      <version>2.14.0</version>
  </dependency>
  
  // INSTRUMENT AWS SDK v2 CLIENT
  import com.amazonaws.xray.interceptors.TracingInterceptor;
  
  DynamoDbClient dynamoDb = DynamoDbClient.builder()
      .overrideConfiguration(ClientOverrideConfiguration.builder()
          .addExecutionInterceptor(new TracingInterceptor())
          .build())
      .build();
  
  // CREATE CUSTOM SUBSEGMENT
  import com.amazonaws.xray.AWSXRay;
  
  public void processOrder(Order order) {
      AWSXRay.beginSubsegment("ProcessOrder");
      try {
          // Add annotations (indexed, searchable)
          AWSXRay.getCurrentSubsegment()
              .putAnnotation("orderId", order.getId())
              .putAnnotation("customerId", order.getCustomerId());
          
          // Add metadata (NOT indexed)
          AWSXRay.getCurrentSubsegment()
              .putMetadata("orderDetails", order);
          
          // Your business logic here
          validateOrder(order);
          persistOrder(order);
          
      } catch (Exception e) {
          AWSXRay.getCurrentSubsegment().addException(e);
          throw e;
      } finally {
          AWSXRay.endSubsegment();
      }
  }

6. X-RAY WITH SPRING BOOT
================================================================

  <!-- pom.xml -->
  <dependency>
      <groupId>com.amazonaws</groupId>
      <artifactId>aws-xray-recorder-sdk-spring</artifactId>
      <version>2.14.0</version>
  </dependency>
  
  // Enable X-Ray filter for all HTTP requests
  @Bean
  public Filter tracingFilter() {
      return new AWSXRayServletFilter("my-service");
  }
  
  // Enable AOP-based tracing
  @Configuration
  @EnableAspectJAutoProxy
  public class XRayConfig {
      @Bean
      public XRayAspect xRayAspect() {
          return new XRayAspect();
      }
  }
  
  // Instrument a method as a subsegment
  @XRayEnabled
  @Service
  public class OrderService {
      public Order processOrder(String orderId) {
          // Automatically creates a subsegment named "OrderService"
      }
  }

7. X-RAY FILTER EXPRESSIONS
================================================================

  Use in X-Ray console to search traces:
  
  # Find slow traces (> 5 seconds)
  duration > 5
  
  # Find errors
  error = true
  
  # Find traces with specific annotation
  annotation.orderId = "order-123"
  
  # Find traces from specific service
  service("my-lambda-function")
  
  # Combine conditions
  service("order-service") AND fault = true AND duration > 2
  
  # Find traces calling DynamoDB
  edge(id(name: "order-service"), id(name: "DynamoDB"))

8. X-RAY GROUPS
================================================================

  Groups are named filter expressions saved for ongoing monitoring.
  
  Create a group for "slow orders" to monitor on a dedicated dashboard:
  aws xray create-group \
    --group-name "SlowOrders" \
    --filter-expression "annotation.service = \"order-api\" AND duration > 3"
  
  Insights can be enabled per group to automatically detect anomalies.

10. INTERVIEW QUESTIONS
================================================================

Q: What is distributed tracing and why is X-Ray important in microservices?
A: Distributed tracing follows a single request as it flows through multiple services.
   In a monolith, a stack trace shows the full call chain. In microservices, a request 
   might touch: API Gateway → Lambda A → SQS → Lambda B → RDS → ElastiCache. A 500 
   error could originate anywhere.
   
   X-Ray assigns a Trace ID at the entry point and propagates it as an HTTP header. 
   Each service creates a Segment (and Subsegments for downstream calls). The X-Ray 
   service map shows the complete request graph with timing at each hop. You can 
   instantly see: "The Lambda took 200ms, of which 180ms was the RDS query, so the 
   bottleneck is the database." Without tracing, you'd correlate timestamps across 
   multiple CloudWatch log groups manually.

Q: What is the difference between annotations and metadata in X-Ray?
A: Annotations are indexed key-value pairs that can be used in filter expressions to 
   search and filter traces in the X-Ray console or API. Use them for important 
   business identifiers: userId, orderId, tenantId, requestType. They are stored 
   in the trace and are searchable.
   
   Metadata are key-value pairs that are NOT indexed and NOT searchable. They are 
   for debugging detail: full request payloads, intermediate state, configuration 
   values at the time of the call. They don't affect performance of trace retrieval.
   
   Rule of thumb: annotate what you'll SEARCH by; use metadata for what you'll 
   READ when looking at a specific trace.

Q: How do you trace a request that goes through API Gateway → Lambda → DynamoDB?
A: Three steps:
   1. API Gateway: Enable X-Ray tracing on the stage (creates the root segment).
   2. Lambda: Set TracingConfig.Mode=Active (inherits the trace ID from API Gateway, 
      creates a segment for the Lambda invocation).
   3. DynamoDB SDK calls: Use X-Ray SDK's TracingInterceptor with the DynamoDB SDK v2 
      client builder. This automatically creates subsegments for each DynamoDB operation.
   
   The trace ID propagates as the X-Amzn-Trace-Id HTTP header. The service map will 
   show: Client → API Gateway → Lambda → DynamoDB with timing for each hop. You can 
   then see: if DynamoDB subsegment shows 200ms for a GetItem, you know your table 
   design may need a cache (DAX) or index optimization.
