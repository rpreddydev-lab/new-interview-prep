2. AWS SDK FOR JAVA v2 — ARCHITECTURE
================================================================

  AWS SDK v2 is a complete rewrite of v1 with:
    - Non-blocking async clients (built on Netty)
    - Modular: import only what you need (not a fat JAR)
    - Immutable request/response objects
    - Builder pattern throughout
    - Better configurability (HTTP client, retry, timeout)
    - AWS CRT-based HTTP client option
  
  Maven dependency structure:
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>bom</artifactId>
        <version>2.25.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>
  
  <dependencies>
    <dependency>
      <groupId>software.amazon.awssdk</groupId>
      <artifactId>s3</artifactId>    <!-- only S3, not the whole SDK -->
    </dependency>
    <dependency>
      <groupId>software.amazon.awssdk</groupId>
      <artifactId>dynamodb-enhanced</artifactId>
    </dependency>
  </dependencies>

3. CLIENT INITIALIZATION PATTERNS
================================================================

  SYNCHRONOUS CLIENT (standard):
  S3Client s3 = S3Client.builder()
      .region(Region.US_EAST_1)
      .credentialsProvider(DefaultCredentialsProviderChain.create())
      .build();
  
  ASYNCHRONOUS CLIENT (non-blocking):
  S3AsyncClient s3Async = S3AsyncClient.builder()
      .region(Region.US_EAST_1)
      .build();
  
  CompletableFuture<ListBucketsResponse> future = s3Async.listBuckets();
  future.thenAccept(response ->
      response.buckets().forEach(b -> System.out.println(b.name()))
  );
  
  LAMBDA PATTERN (static initialization — warm reuse):
  public class Handler implements RequestHandler<...> {
      // Initialize OUTSIDE handleRequest — shared across warm invocations
      private static final DynamoDbClient dynamoDb = DynamoDbClient.create();
      private static final S3Client s3 = S3Client.create();
      
      public Object handleRequest(Object event, Context ctx) {
          // Use the already-initialized clients
      }
  }
  
  WHY STATIC: Lambda reuses the execution environment for warm invocations.
  Static clients avoid re-initialization overhead (TLS handshake, credential 
  loading) on every invocation.

4. CREDENTIALS PROVIDER CHAIN
================================================================

  DefaultCredentialsProvider checks in order:
  
  1. Environment variables:    AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
  2. Java system properties:   aws.accessKeyId, aws.secretAccessKey
  3. AWS credentials file:     ~/.aws/credentials [default]
  4. AWS config file:          ~/.aws/config [default]
  5. ECS task role:            Via ECS container credentials endpoint
  6. EC2 instance profile:     Via IMDSv2 (Instance Metadata Service)
  7. Lambda execution role:    Via environment variables set by Lambda service
  
  NEVER hardcode credentials in code!
  
  Assume Role:
  StsClient sts = StsClient.create();
  StsAssumeRoleCredentialsProvider roleProvider =
      StsAssumeRoleCredentialsProvider.builder()
          .stsClient(sts)
          .refreshRequest(AssumeRoleRequest.builder()
              .roleArn("arn:aws:iam::123456789012:role/cross-account-role")
              .roleSessionName("my-session")
              .build())
          .build();
  
  DynamoDbClient dynamoDb = DynamoDbClient.builder()
      .credentialsProvider(roleProvider)
      .build();

5. HTTP CLIENT CONFIGURATION
================================================================

  Default HTTP client: Apache HTTP (sync) / Netty (async)
  
  Custom HTTP settings:
  S3Client s3 = S3Client.builder()
      .httpClientBuilder(ApacheHttpClient.builder()
          .maxConnections(200)
          .connectionTimeout(Duration.ofSeconds(5))
          .socketTimeout(Duration.ofSeconds(30))
          .connectionAcquisitionTimeout(Duration.ofSeconds(10)))
      .build();
  
  Connection pools are critical for Lambda performance!
  Shared client = shared connection pool across warm invocations.

================================================================
6. RETRY CONFIGURATION
================================================================

  SDK v2 retries on throttling and transient errors by default.
  
  S3Client s3 = S3Client.builder()
      .overrideConfiguration(ClientOverrideConfiguration.builder()
          .retryPolicy(RetryPolicy.builder()
              .numRetries(5)
              .retryCondition(RetryCondition.defaultRetryCondition())
              .backoffStrategy(EqualJitterBackoffStrategy.builder()
                  .baseDelay(Duration.ofMillis(100))
                  .maxBackoffTime(Duration.ofSeconds(10))
                  .build())
              .build())
          .apiCallTimeout(Duration.ofSeconds(30))
          .apiCallAttemptTimeout(Duration.ofSeconds(10))
          .build())
      .build();

7. WAITERS AND PAGINATORS
================================================================

  WAITERS (poll until state reached):
  S3Waiter waiter = s3.waiter();
  waiter.waitUntilBucketExists(
      HeadBucketRequest.builder().bucket("my-bucket").build()
  );
  
  PAGINATORS (auto-handle pagination):
  // Without paginator (manual)
  String nextToken = null;
  do {
      ListObjectsV2Response resp = s3.listObjectsV2(
          ListObjectsV2Request.builder().bucket("my-bucket").continuationToken(nextToken).build()
      );
      resp.contents().forEach(o -> System.out.println(o.key()));
      nextToken = resp.nextContinuationToken();
  } while (nextToken != null);
  
  // With paginator (auto-handles pagination)
  ListObjectsV2Publisher paginator = s3Async.listObjectsV2Paginator(
      ListObjectsV2Request.builder().bucket("my-bucket").build()
  );
  paginator.contents().subscribe(obj -> System.out.println(obj.key())).join();
  
  // Sync paginator
  s3.listObjectsV2Paginator(
      ListObjectsV2Request.builder().bucket("my-bucket").build()
  ).forEach(page ->
      page.contents().forEach(obj -> System.out.println(obj.key()))
  );

8. INTERVIEW QUESTIONS
================================================================

Q: Why should you initialize AWS SDK clients as static fields in Lambda?
A: Lambda reuses the same execution environment (JVM process) for multiple warm 
   invocations. Client initialization involves: loading credentials, establishing 
   TLS connections, creating HTTP connection pools, and service discovery. If you 
   initialize inside handleRequest(), this overhead happens on EVERY invocation.
   
   As static final fields, initialization happens ONCE during cold start (class 
   loading). All subsequent warm invocations reuse the initialized client with its 
   existing HTTP connection pool.
   
   Example: DynamoDB SDK client creation takes ~200-500ms. If your Lambda runs 
   10,000 times/day with 80% warm rate, moving to static saves (8,000 × 350ms) = 
   47 minutes of execution time per day, reducing both latency and cost.

Q: What is the difference between AWS SDK v1 and v2 for Java?
A: Key differences:
   1. Async: v2 has native async clients (S3AsyncClient) using CompletableFuture/Netty; 
      v1's async was bolted on as a wrapper
   2. Immutability: v2 request/response objects are immutable; v1 used mutable beans
   3. Modularity: v2 you import only specific services (s3, dynamodb); v1 was a monolith
   4. HTTP client: v2 is pluggable (Apache, Netty, URL Connection, CRT); v1 used Apache
   5. SDK metrics: v2 has built-in SDK metrics publishable to CloudWatch
   6. Enhanced clients: DynamoDbEnhancedClient with @DynamoDbBean annotations
   7. Builder pattern: consistent Fluent builders everywhere in v2 vs v1's many constructors
   8. Default credentials: v2 uses DefaultCredentialsProvider; cleaner chain

Q: How does the credentials provider chain work, and what is the recommended approach 
   for different environments?
A: DefaultCredentialsProvider.create() tries providers in order:
   1. Env vars → 2. Java props → 3. AWS profile → 4. ECS task role → 5. EC2 instance profile
   
   Recommended by environment:
   - Local dev: ~/.aws/credentials or AWS SSO (aws configure sso)
   - EC2: IAM Instance Profile (never put credentials in code/env on EC2)
   - Lambda: Lambda Execution Role (automatically available as env vars)
   - ECS/Fargate: ECS Task Role (per-task permissions, not per-host)
   - Cross-account: AssumeRole via StsAssumeRoleCredentialsProvider
   
   The key principle: use IAM roles for AWS compute services; credentials files for 
   local development. Never store long-lived access keys in EC2/Lambda/ECS 
   environments.
