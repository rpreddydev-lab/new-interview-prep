VIRTUAL DOM - INTERVIEW PREPARATION

1. WHAT IS THE DOM?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The DOM (Document Object Model) is a tree-structured representation of an
HTML document that the browser creates. JavaScript can manipulate it via APIs
like document.getElementById(), appendChild(), etc.

The Problem with Direct DOM Manipulation:
  - DOM operations are EXPENSIVE (reflow, repaint, layout recalculation)
  - Even small changes can trigger full layout recomputation
  - Repeatedly querying and updating the real DOM for every UI change causes
    performance bottlenecks (especially with complex, dynamic UIs)

Example of the cost:
  // Bad: Each line triggers a reflow/repaint
  element.style.width = '100px';
  element.style.height = '100px';
  element.style.background = 'red';

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. WHAT IS THE VIRTUAL DOM?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Virtual DOM (VDOM) is a lightweight, in-memory JavaScript representation
(plain object tree) of the real DOM tree.

It is NOT a browser API — it's a React concept/implementation detail.

A Virtual DOM node looks roughly like:
  {
    type: 'div',
    props: {
      className: 'container',
      children: [
        {
          type: 'h1',
          props: { children: 'Hello World' }
        },
        {
          type: 'p',
          props: { children: 'Some text' }
        }
      ]
    }
  }

When you write JSX:
  <div className="container">
    <h1>Hello World</h1>
    <p>Some text</p>
  </div>

Babel transforms it to:
  React.createElement('div', { className: 'container' },
    React.createElement('h1', null, 'Hello World'),
    React.createElement('p', null, 'Some text')
  )

This returns a plain JS object — the virtual DOM node.

3. HOW VIRTUAL DOM WORKS (THE DIFFING PROCESS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Step-by-step process:

  1. INITIAL RENDER:
     - React creates a virtual DOM tree from your components
     - React "commits" this to the real DOM (browser renders it)
     - React keeps a copy of the virtual DOM in memory

  2. STATE/PROP CHANGE:
     - Component function is called again (re-render)
     - A NEW virtual DOM tree is produced

  3. DIFFING (Reconciliation):
     - React compares the OLD virtual DOM with the NEW virtual DOM
     - React's diffing algorithm finds the MINIMAL set of changes needed
     - This is called "reconciliation"

  4. PATCHING:
     - React updates ONLY the changed parts of the real DOM
     - Batch updates wherever possible
     - Browser only re-paints the changed elements

  Diagram:
  ┌─────────────────────────────────────────────────────┐
  │                   State Change                       │
  └───────────────────┬─────────────────────────────────┘
                      │
                      ▼
  ┌─────────────────────────────────────────────────────┐
  │         New Virtual DOM Tree Created                 │
  └───────────────────┬─────────────────────────────────┘
                      │
                      ▼
  ┌─────────────────────────────────────────────────────┐
  │   Diff: Old VDOM  ←→  New VDOM (find changes)       │
  └───────────────────┬─────────────────────────────────┘
                      │
                      ▼
  ┌─────────────────────────────────────────────────────┐
  │    Patch Real DOM (only changed nodes updated)       │
  └─────────────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. REACT'S DIFFING ALGORITHM (HEURISTIC O(n))
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The naive diffing of two trees is O(n³) which is too slow. React uses a
heuristic O(n) algorithm based on two assumptions:

  ASSUMPTION 1 - Different types produce different trees:
    - If the root element type changes (<div> → <span>), React destroys
      the old tree entirely and builds a new one from scratch.
    - Component type changes also trigger full unmount/remount.

  ASSUMPTION 2 - Keys help identify which items changed in lists:
    - Without keys, React diffs by index (can cause bugs with reordering)
    - With stable keys, React can correctly match old and new items

  Example of assumption 1:
    Old: <Counter />   →   New: <Button />
    React unmounts Counter, mounts Button (full replacement)

  Example with same type:
    Old: <div className="a" />   →   New: <div className="b" />
    React keeps the DOM node and only updates className attribute

5. KEYS IN RECONCILIATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Keys are special props that help React identify list items across renders.

  WITHOUT KEYS (index-based diffing):
    // If items are reordered, React compares by position:
    Old: [A(0), B(1), C(2)]
    New: [C(0), A(1), B(2)]
    // React thinks ALL 3 items changed (wrong!) → unnecessary re-renders

  WITH KEYS (id-based diffing):
    <li key="A">A</li>
    <li key="B">B</li>
    <li key="C">C</li>
    // React knows A, B, C are the same items just reordered → only moves DOM nodes

  BAD key usage — using array index as key:
    items.map((item, i) => <li key={i}>{item}</li>)
    // When items are added/removed from the front, all keys shift
    // Causes incorrect reconciliation, lost state, input focus bugs

  GOOD key usage — use stable, unique ID:
    items.map(item => <li key={item.id}>{item.name}</li>)

6. VIRTUAL DOM vs REAL DOM vs SHADOW DOM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  | Feature       | Real DOM          | Virtual DOM         | Shadow DOM        |
  |---------------|-------------------|---------------------|-------------------|
  | What is it?   | Browser's DOM     | JS object copy      | Browser-native    |
  | Who uses it   | Browser           | React, Vue          | Web Components    |
  | Purpose       | Render HTML       | Optimize diffing    | Style encapsul.   |
  | Performance   | Slow to update    | Fast (batch update) | Independent CSS   |
  | Part of React?| No (browser)      | Yes                 | No                |

  Shadow DOM: A browser-native feature for Web Components that encapsulates
  styles and markup. NOT the same as React's Virtual DOM.

7. IS VIRTUAL DOM ALWAYS FASTER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MYTH: Virtual DOM is always faster than direct DOM manipulation.
TRUTH: For carefully optimized vanilla JS, direct DOM manipulation CAN be faster.

Virtual DOM is faster than NAIVE (unoptimized) DOM manipulation because:
  - It batches multiple changes into a single DOM update
  - It avoids redundant DOM reads/writes
  - It reduces reflow/repaint cycles

BUT: Libraries like Svelte (no virtual DOM, compiles to direct DOM updates) can
be faster than React for certain use cases.

React's value is in DEVELOPER EXPERIENCE + GOOD ENOUGH PERFORMANCE, not
theoretical maximum performance.

8. RECONCILIATION IN REACT 18 (CONCURRENT MODE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In React 18, the render phase can be:
  - Interrupted (by more urgent updates)
  - Paused (to let browser handle user input)
  - Resumed or Discarded

This is possible because the Virtual DOM diffing (render phase) is pure
(no DOM mutations). React can throw away a half-completed render and restart.

  useTransition / startTransition: marks updates as "non-urgent"
  → React can interrupt these to process urgent updates (like typing)
  → Only possible because VDOM diffing doesn't commit to the real DOM yet

9. COMMON INTERVIEW QUESTIONS ON VIRTUAL DOM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the Virtual DOM and why does React use it?
A: The Virtual DOM is an in-memory JavaScript representation of the real DOM.
   React uses it to minimize expensive real DOM operations by batching and
   computing the minimal set of changes via diffing before touching the real DOM.

Q: What is the difference between Virtual DOM and Real DOM?
A: Real DOM is the browser's actual tree structure (slow to manipulate). Virtual
   DOM is a fast JS object copy. React diffs the virtual trees and applies only
   necessary changes to the real DOM.

Q: Explain the reconciliation process.
A: When state/props change, React re-renders the component tree into a new VDOM.
   It diffs the new VDOM against the old one using heuristics (O(n) algorithm):
   different element types → replace tree; same type → update attributes;
   lists → use keys for matching. Then it commits only the real changes to the DOM.

Q: Why shouldn't you use array indices as keys?
A: Using index as key causes incorrect reconciliation when items are
   reordered/inserted/deleted, because keys shift. This can cause wrong
   components to be reused, state loss, and input focus bugs.

Q: Is the Virtual DOM a browser feature?
A: No. It's a React (and Vue) implementation detail — purely a JavaScript concept.
   It has nothing to do with the browser's Shadow DOM.

Q: What is the Shadow DOM?
A: Shadow DOM is a browser-native Web API for encapsulating styles and markup
   inside Web Components. It's separate from React's Virtual DOM concept.

Q: How does React's diffing algorithm work?
A: React uses a heuristic O(n) diffing algorithm with two key assumptions:
   1. Elements of different types produce different trees (triggers full remount)
   2. Keys help identify items in lists across renders
   Without keys, React diffs by position; with keys, it matches by identity.

Q: How does Concurrent Mode affect the Virtual DOM?
A: In Concurrent Mode, React can interrupt the render phase (VDOM diffing) to
   handle more urgent updates. Since VDOM diffing doesn't touch the real DOM,
   it's safe to discard a partial render and restart.
