1. RENDERING LISTS IN REACT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React renders arrays of JSX elements natively. Array.map() is the standard
way to render a list of items.

  const fruits = ['Apple', 'Banana', 'Cherry'];

  function FruitList() {
    return (
      <ul>
        {fruits.map((fruit, index) => (
          <li key={index}>{fruit}</li>
        ))}
      </ul>
    );
  }

  // Better: using stable ID as key
  const products = [
    { id: 1, name: 'Laptop', price: 999 },
    { id: 2, name: 'Phone', price: 599 },
    { id: 3, name: 'Tablet', price: 399 },
  ];

  function ProductList() {
    return (
      <ul>
        {products.map(product => (
          <ProductItem key={product.id} product={product} />
        ))}
      </ul>
    );
  }

  function ProductItem({ product }) {
    return (
      <li>
        <span>{product.name}</span>
        <strong>${product.price}</strong>
      </li>
    );
  }

2. WHAT ARE KEYS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Keys are special string attributes that help React identify which items in a
list have changed, been added, or been removed during reconciliation.

  // Without key → React warning: "Each child in a list should have a unique key"
  {items.map(item => <li>{item.name}</li>)}

  // With key → React can correctly diff the list
  {items.map(item => <li key={item.id}>{item.name}</li>)}

Rules:
  - Keys must be UNIQUE among siblings (not globally unique)
  - Keys must be STABLE (same item → same key across renders)
  - Keys must be CONSISTENT (if an item reorders, its key follows it)
  - Keys are NOT passed as props (child cannot access key via props.key)

3. WHY KEYS MATTER — THE RECONCILIATION PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WITHOUT KEYS (index-based diffing):
  Old list:  [<A key=0>, <B key=1>, <C key=2>]
  New list:  [<X key=0>, <A key=1>, <B key=2>, <C key=3>]
  // X inserted at beginning. React sees:
  //   pos 0: was A, now X → UPDATE
  //   pos 1: was B, now A → UPDATE
  //   pos 2: was C, now B → UPDATE
  //   pos 3: new → INSERT C
  // Result: 3 updates + 1 insert (inefficient + WRONG state behavior)

WITH KEYS (id-based diffing):
  Old list:  [<A key="a">, <B key="b">, <C key="c">]
  New list:  [<X key="x">, <A key="a">, <B key="b">, <C key="c">]
  // React sees:
  //   key "x": new → INSERT X at position 0
  //   key "a", "b", "c": MOVE to new positions
  // Result: 1 insert + 3 moves (correct and efficient)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. THE INDEX-AS-KEY PROBLEM (Common Bug)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Using array index as key causes bugs when items can be REORDERED, INSERTED,
or DELETED from anywhere other than the end.

  // Problematic scenario with index key:
  const [items, setItems] = useState([
    { id: 1, name: 'Alice' },
    { id: 2, name: 'Bob' },
  ]);

  // Each item has an uncontrolled input inside
  function ItemList() {
    return (
      <ul>
        {items.map((item, index) => (
          <li key={index}>
            {item.name}: <input defaultValue={item.name} />
          </li>
        ))}
      </ul>
    );
  }

  // If user types in Alice's input, then Alice is deleted:
  // Old: [Alice(key=0), Bob(key=1)]
  // New: [Bob(key=0)]
  // React sees key=0 still exists → REUSES Alice's input DOM element
  //   → Bob's row shows Alice's typed value (WRONG!)

  // FIX: Use item.id as key
  <li key={item.id}>

When IS index key acceptable?
  - The list is static (will never reorder/add/remove items)
  - Items have no state (pure display, no inputs)
  - You have no stable ID and reordering is impossible

5. GENERATING KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BEST: Use ID from data source (database ID, UUID):
  {items.map(item => <li key={item.id}>{item.name}</li>)}

If no ID exists, generate one when creating the item (NOT during render):
  import { v4 as uuidv4 } from 'uuid';

  // When adding to list (generate once):
  const newItem = { id: uuidv4(), name: 'New Item' };

  // BAD: generating key during render (new key every render → remount every time)
  {items.map(item => <li key={uuidv4()}>{item.name}</li>)} // WRONG!

String concatenation for composite keys:
  {sections.map(section =>
    section.items.map(item =>
      <Item key={`${section.id}-${item.id}`} item={item} />
    )
  )}

6. USING KEY TO FORCE REMOUNT (Reset Trick)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Changing a component's key forces React to unmount + remount it (fresh state):

  // Reset a form when userId changes without managing controlled inputs:
  function UserForm({ userId }) {
    return <Form key={userId} userId={userId} />;
  }
  // When userId changes, the key changes → Form completely remounts with fresh state

  // Reset an animation or counter:
  <Counter key={resetKey} />
  // Call setResetKey(k => k + 1) to reset Counter to initial state

7. OTHER ARRAY METHODS FOR RENDERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // filter + map: render subset
  {products
    .filter(p => p.inStock)
    .map(p => <ProductCard key={p.id} product={p} />)
  }

  // flatMap: flatten nested arrays
  {categories.flatMap(cat =>
    cat.items.map(item => <Item key={item.id} item={item} />)
  )}

  // reduce: group items
  const grouped = items.reduce((acc, item) => {
    (acc[item.category] = acc[item.category] || []).push(item);
    return acc;
  }, {});
  {Object.entries(grouped).map(([category, items]) => (
    <section key={category}>
      <h2>{category}</h2>
      {items.map(item => <Item key={item.id} item={item} />)}
    </section>
  ))}

8. COMMON INTERVIEW QUESTIONS ON LISTS AND KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why do we need keys in React lists?
A: Keys help React's reconciliation algorithm identify which items changed,
   were added, or removed when a list updates. Without keys, React diffs by
   position (index), causing incorrect reuse of DOM nodes and component state.

Q: Can you use the array index as a key?
A: It's acceptable ONLY when the list is static and items never reorder/insert/delete.
   Using index as key when items can change order leads to incorrect DOM reuse,
   state bugs (wrong input values), and performance issues.

Q: What properties should a good key have?
A: Unique among siblings, stable across renders, and consistent (same item always
   gets the same key). Typically a database ID or UUID generated when the item
   is created.

Q: Can a child component read its own key?
A: No. Key is a special prop consumed by React internally. It's not passed to the
   component. If you need the ID inside the component, pass it as a separate prop:
   <Item key={item.id} id={item.id} />

Q: How can you use the key prop to reset component state?
A: By changing the key, you force React to unmount the old component and mount
   a fresh one (with initial state). Common use: resetting a form when the user/
   entity changes: <Form key={userId} />.

Q: What is the warning "Each child in a list should have a unique key prop"?
A: React warns when list items don't have keys. It means React is using index-
   based diffing, which is error-prone. Fix: add a stable unique key to each item.
