CONTEXT AND GLOBAL STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is prop drilling and how do you avoid it?
A: Prop drilling is passing data through multiple component layers that don't
   need the data themselves — just to reach a deeply nested component.
   Solutions:
   (1) Context API — inject at any depth without manual passing
   (2) Component composition — pass components as props instead of data
   (3) Zustand/Redux — access state anywhere via hooks without prop passing

Q2: When should you use Context API vs Redux?
A: Context is ideal for low-frequency global values: auth, theme, locale.
   Redux (or Zustand) is better when: state updates are frequent, you need
   selectors to prevent unnecessary re-renders, you want DevTools/time-travel
   debugging, or you need middleware (logging, optimistic updates, async).

Q3: Why does Context API cause performance issues with frequent updates?
A: Every time the Provider's value changes, ALL consumers re-render — even
   components that only use a part of the value that didn't change. Context
   has no concept of selectors. For frequent updates, Zustand's subscription
   model is better: components only re-render when their specific slice changes.

Q4: How do you prevent unnecessary re-renders with Context?
A: (1) Split contexts by update frequency. (2) Memoize the provider value
   with useMemo so a new object isn't created on every render. (3) Use
   separate state and dispatch contexts — dispatch from useReducer is always
   stable, so components that only dispatch never re-render due to state changes.

Q5: What is the difference between useSelector and useContext?
A: useSelector (Redux) accepts a selector function — the component only
   re-renders when the selected value changes (uses strict equality).
   useContext re-renders whenever ANY part of the context value changes.
   For fine-grained subscriptions, useSelector is significantly more efficient.

REDUX TOOLKIT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q6: What is Redux and what are its three core principles?
A: Redux is a predictable state container.
   Three principles:
   (1) Single source of truth — one global store.
   (2) State is read-only — only dispatched actions can change state.
   (3) Changes via pure functions — reducers are pure: (state, action) => newState.

Q7: How does Redux Toolkit differ from plain Redux?
A: RTK reduces boilerplate: createSlice auto-generates action creators and
   action type strings. configureStore sets up redux-thunk and DevTools.
   createAsyncThunk provides standardized async action handling. Immer is
   integrated — you can write "mutating" code that produces immutable updates.

Q8: What are the three actions generated by createAsyncThunk?
A: prefix/pending (dispatched before the async function runs),
   prefix/fulfilled (dispatched with the return value on success),
   prefix/rejected (dispatched with the error on failure).
   Handle these in the slice's extraReducers with builder.addCase().

Q9: What is the immer library and why does RTK use it?
A: Immer allows writing state "mutations" that actually produce new immutable
   state via structural sharing. RTK uses it in createSlice, so you can
   write state.count += 1 instead of return { ...state, count: state.count + 1 }.

ZUSTAND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q10: How does Zustand differ from Redux?
A: Zustand requires no Provider, has minimal boilerplate (no action types,
   no dispatch — just call functions), and is ~1KB. Actions are defined
   alongside state in the store. Redux has better DevTools, time-travel
   debugging, and is more structured (better for large teams with clear
   conventions).

Q11: How do you prevent re-renders with Zustand?
A: Use granular selectors — select only the state you need:
   const count = useStore(state => state.count);
   For multiple values, use useShallow:
   const { a, b } = useStore(useShallow(state => ({ a: state.a, b: state.b })));

TANSTACK QUERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q12: What problem does TanStack Query solve?
A: Server state management — caching, background refetching, deduplication,
   loading/error states. Without it, you'd manually manage all this with
   useEffect + useState + loading flags. React Query provides a declarative
   API that handles all of it automatically.

Q13: What is staleTime and how does it affect refetching?
A: staleTime is the duration data is considered "fresh". During this period,
   React Query will NOT refetch even on window focus or component mount.
   After staleTime expires, data is "stale" and will be refetched in the
   background on next access. Default is 0 (immediately stale).

Q14: How do optimistic updates work in React Query?
A: In onMutate: cancel in-flight queries, save snapshot, update cache.
   In onError: restore snapshot.
   In onSettled: invalidate to refetch real data.
   This lets the UI feel instant while the server confirms the change.

Q15: What is the difference between invalidateQueries and refetch?
A: invalidateQueries marks queries as stale and refetches any that are
   currently observed. refetch imperatively triggers a fetch for a specific
   query regardless of stale status. Use invalidateQueries after mutations.

Q16: You have a dashboard with: authenticated user, theme, shopping cart, 
     user list from API. How would you manage each?
A:
   - Auth user: Context API (read-only during session, low frequency)
   - Theme: Context API (changes only when user toggles)
   - Shopping cart: Zustand with persist middleware (frequent updates, needs persistence)
   - User list from API: TanStack Query (server state — caching, refetch)

Q17: Your app has a list of 1000 items with a search bar. Every keystroke 
     causes the whole list to re-render slowly. How do you fix it?
A: Several approaches:
   (1) useTransition / useDeferredValue — defer the list update so typing stays
       responsive while list re-renders in background.
   (2) Virtualize the list with react-window if rendering all items is slow.
   (3) Memoize the filtered list with useMemo.
   (4) Wrap the list component with React.memo and pass a stable data prop.
   (5) Debounce the search query for API-based searches.
