1. WHAT IS CODE SPLITTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

By default, bundlers (Webpack, Vite) compile all code into one large JS bundle.
Code splitting breaks this bundle into smaller chunks loaded on demand.

  Benefits:
  - Smaller initial download → faster First Contentful Paint (FCP)
  - Only download code for the current page
  - Better caching: unchanged chunks are reused between deployments

  Without code splitting:
    main.js: 2MB (Home + About + Dashboard + Admin + Charts + ...)
    User on /home downloads all 2MB including Admin page they'll never see

  With code splitting:
    main.js: 200KB (core React + Layout + Home)
    dashboard.[hash].js: 500KB (loaded only when user visits /dashboard)
    admin.[hash].js: 300KB (loaded only when admin visits /admin)

2. DYNAMIC IMPORT — THE MECHANISM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Static import (always bundled together):
  import HeavyChart from './HeavyChart';

  // Dynamic import (creates a separate chunk):
  const HeavyChart = React.lazy(() => import('./HeavyChart'));

  Dynamic import returns a Promise. Bundlers (Vite/Webpack) detect it at build
  time and emit a separate file for the module.

  // Also works for non-component dynamic imports:
  async function loadParser() {
    const { marked } = await import('marked');  // lazy-load markdown library
    return marked(content);
  }

4. COMPONENT-LEVEL SPLITTING (BEYOND ROUTES)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Code split any large component, not just routes:

  // Conditionally rendered heavy component
  const Modal = lazy(() => import('./Modal'));

  function App() {
    const [isOpen, setIsOpen] = useState(false);

    return (
      <div>
        <button onClick={() => setIsOpen(true)}>Open Modal</button>
        {isOpen && (
          <Suspense fallback={<div>Loading...</div>}>
            <Modal onClose={() => setIsOpen(false)} />
          </Suspense>
        )}
      </div>
    );
    // Modal chunk is only downloaded when user clicks the button
  }

  // Good candidates for component-level splitting:
  // - Rich text editors (ProseMirror, TipTap, Quill)
  // - Chart libraries (Recharts, Chart.js)
  // - Map components (Leaflet, Google Maps)
  // - PDF viewers
  // - Heavy data grids (AG Grid)
  // - Modals, dialogs, drawers (conditionally rendered)

5. BUNDLE ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Before optimizing, analyze what's large:

  # Vite:
  npm install --save-dev rollup-plugin-visualizer
  # in vite.config.ts: plugins: [visualizer({ open: true })]
  npm run build → opens interactive bundle treemap

  # Webpack:
  npm install --save-dev webpack-bundle-analyzer

  What to look for:
  - Large third-party libraries in main chunk (moment.js, lodash — tree-shakeable?)
  - Duplicate dependencies
  - Pages bundled together that could be split
  - Server-only code accidentally included in client bundle

6. COMMON INTERVIEW QUESTIONS

Q: What is code splitting and how do you implement it in React?
A: Code splitting breaks the JS bundle into smaller chunks loaded on demand.
   In React, you use React.lazy(() => import('./Component')) with Suspense.
   The bundler (Vite/Webpack) automatically creates a separate chunk for each
   dynamic import.

Q: What is tree shaking?
A: Tree shaking is dead code elimination — the bundler removes exported
   functions/variables that are never imported. It only works with ES module
   syntax (import/export). Named imports (import { fn } from 'lib') enable
   tree shaking; default imports sometimes don't.

Q: What is the difference between code splitting and lazy loading?
A: Code splitting is the build-time process of breaking code into chunks.
   Lazy loading is the runtime behavior of loading those chunks on demand.
   React.lazy() implements both: it splits at build time and loads lazily
   when the component first renders.

Q: When should you NOT code split?
A: Don't split very small components (network overhead > saved render time).
   Don't split components that are always needed on first render (landing page).
   Don't split if the loading flash (Suspense fallback) would hurt UX more than
   the download time it saves.
