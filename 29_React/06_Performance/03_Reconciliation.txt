RECONCILIATION - INTERVIEW PREPARATION

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. WHAT IS RECONCILIATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Reconciliation is React's process of comparing the previous Virtual DOM tree
with the new one after a state/prop change, and computing the minimal set of
DOM mutations needed to bring the DOM in sync.

  Steps:
  1. State/prop changes → component function re-runs
  2. New Virtual DOM tree is built (React elements)
  3. React DIFFS new tree against previous tree (reconciliation)
  4. React calculates minimal set of changes (patches)
  5. Commit phase: patches applied to real DOM

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. DIFFING ALGORITHM — TWO HEURISTICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A naïve tree diff is O(n³). React's algorithm is O(n) by using two assumptions:

  HEURISTIC 1: Different element TYPES produce different trees.
    If <div> changes to <span>, React unmounts the entire div subtree
    and mounts a fresh span subtree. No attempt to match children.

    Before:
      <div>
        <Counter />
      </div>

    After:
      <span>   ← type changed from div → span
        <Counter />
      </span>
    Result: Counter is UNMOUNTED and REMOUNTED (state lost!)

  HEURISTIC 2: Developer provides keys on list items to assist matching.
    Without keys: React matches by INDEX position
    With keys:    React matches by KEY value regardless of position

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. KEYS — RECONCILIATION IN LISTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Without keys (using index):
    Before: [A, B, C]  →  After: [X, A, B, C] (prepend)
    React matches by index:
      Index 0: A → X (update DOM: A → X)
      Index 1: B → A (update DOM: B → A)
      Index 2: C → B (update DOM: C → B)
      Index 3: ―― → C (create new node)
    = 3 DOM updates + 1 create (expensive, and state for A/B/C is lost)

  With stable keys:
    Before: [A(key=a), B(key=b), C(key=c)]
    After:  [X(key=x), A(key=a), B(key=b), C(key=c)]
    React matches by key:
      key=x: NEW → create X
      key=a: same → move A to new position
      key=b: same → move B
      key=c: same → move C
    = 1 create + 3 moves (cheap, state preserved!)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. BAILOUTS — WHEN REACT SKIPS RECONCILIATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  React skips reconciling a subtree when it can prove the output won't change:

  1. React.memo: Props shallow-equal → skip render (no new VDOM produced)
  2. useState/useReducer bailout: If new state === old state (Object.is),
     React bails out before re-rendering:
       setState(currentValue);   // no re-render triggered

  3. useMemo: Returns memoized value, computation is not re-run, no new value
  4. Same element type AND same key → React UPDATES (not unmount/remount)

5. RECONCILIATION vs RENDERING vs COMMIT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Render phase (pure, interruptible in Concurrent Mode):
    - React calls component functions to get new elements
    - Builds new Virtual DOM tree
    - Diffs it against current tree (reconciliation)
    - Computes a list of "effects" (DOM mutations, ref updates, lifecycle calls)

  Commit phase (synchronous, non-interruptible):
    - React applies DOM mutations
    - Calls useLayoutEffect cleanup + setup
    - Browser paints
    - React calls useEffect cleanup + setup

6. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is React reconciliation?
A: Reconciliation is React's algorithm for determining what changed between
   two Virtual DOM trees and computing the minimal DOM mutations needed.
   It uses two heuristics: same-type elements are updated (not replaced),
   and keys help match list items across renders.

Q: Why does changing an element type (div → span) cause a full unmount?
A: React assumes different types produce entirely different subtrees. Rather
   than trying to reconcile two different components, it's more efficient to
   unmount and remount. This means component state is lost when the parent
   element type changes.

Q: How does React's diff algorithm achieve O(n) complexity?
A: By using two heuristics: (1) Different element types → unmount everything.
   (2) Same type + same key → update in place. Without these assumptions,
   the optimal tree diff would be O(n³). These heuristics make it O(n) but
   require developers to use keys on lists.

Q: What happens to component state when a key changes?
A: When a component's key changes, React treats it as a different component.
   It unmounts the old and mounts a new one — state is reset. This is the
   "key-as-reset" technique: deliberately change a key to force remount.
