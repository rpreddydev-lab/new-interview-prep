================================================================================
LOCAL vs GLOBAL STATE - INTERVIEW PREPARATION
================================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. TYPES OF STATE IN REACT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React state can be categorized by SCOPE and PURPOSE:

  1. LOCAL STATE         — owned by one component
  2. LIFTED STATE        — shared between siblings via common ancestor
  3. GLOBAL STATE        — accessible anywhere in the app
  4. SERVER/REMOTE STATE — data from API (async, cacheable)
  5. URL STATE           — stored in URL (path, query params)
  6. FORM STATE          — controlled inputs, validation errors

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. LOCAL STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

State that only one component needs. Managed with useState or useReducer.

  Examples:
  - Is a modal open? (only the Modal component cares)
  - Current tab selected in a tab panel
  - Input value in a search box
  - Toggle state of a dropdown menu

  function Counter() {
    const [count, setCount] = useState(0); // local — nothing else needs this
    return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
  }

  RULES for local state:
  - Keep state as close to where it's used as possible
  - Don't lift state until you actually need to share it (YAGNI principle)
  - Prefer local state over global for performance (global = all consumers re-render)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. LIFTING STATE UP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When two sibling components need the same piece of state, lift it to their
lowest common ancestor and pass it down via props.

  // BEFORE: siblings can't communicate
  function TemperatureInput({ scale }) {
    const [value, setValue] = useState('');
    return <input value={value} onChange={e => setValue(e.target.value)} />;
  }

  // AFTER: state lifted to parent
  function Calculator() {
    const [celsius, setCelsius] = useState('');
    const fahrenheit = celsius ? celsius * 9/5 + 32 : '';

    return (
      <div>
        <TemperatureInput label="Celsius" value={celsius} onChange={setCelsius} />
        <TemperatureInput label="Fahrenheit" value={fahrenheit}
          onChange={f => setCelsius((f - 32) * 5/9)} />
      </div>
    );
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. GLOBAL STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

State that multiple unrelated components need. Options:

  a) React Context API   — built-in, best for low-frequency updates
  b) Redux / RTK         — predictable, great for complex state logic
  c) Zustand             — minimal boilerplate, great DX
  d) Jotai / Recoil      — atom-based, fine-grained reactivity

  Common global state examples:
  - Authenticated user object
  - Theme (light/dark)
  - Shopping cart contents
  - Language/locale preference
  - Notification queue

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. SERVER / REMOTE STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Async state fetched from an API. Has unique requirements:
  - Loading/error/success states
  - Caching to avoid redundant requests
  - Background refetching (stale-while-revalidate)
  - Optimistic updates

  Tools designed for this:
  - TanStack Query (React Query)
  - SWR
  - RTK Query (part of Redux Toolkit)

  Bad pattern: putting server state into Redux/Zustand:
    // Don't do this:
    dispatch(setUsers(await fetchUsers())); // manual fetching + caching yourself

  Good pattern: let React Query handle it:
    const { data: users, isLoading } = useQuery({ queryKey: ['users'], queryFn: fetchUsers });

6. URL STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

State stored in the URL (query params, route params). Benefits:
  - Shareable links
  - Browser back/forward navigation
  - Bookmarkable state

  Use React Router's useSearchParams for query params:
    const [searchParams, setSearchParams] = useSearchParams();
    const page = searchParams.get('page') ?? '1';

7. DECISION FRAMEWORK: WHICH STATE TOOL TO USE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Does only one component need it?
    → useState / useReducer (LOCAL)

  Do a few nearby components need it?
    → Lift state up (PROP DRILLING is fine for 2-3 levels)

  Do many unrelated components need it? (low update frequency)
    → Context API

  Do many components need it? (frequent updates / complex logic)
    → Zustand or Redux Toolkit

  Is it async data from an API?
    → TanStack Query / SWR

  Does it need to persist across browser sessions?
    → localStorage / sessionStorage + sync with useState

  Does it need to be in the URL?
    → useSearchParams / URL params

8. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is state colocation and why does it matter?
A: State colocation means keeping state as close as possible to where it's
   used. It improves performance (fewer components re-render), maintainability
   (easier to find where state lives), and avoids premature abstraction.

Q: When should you lift state up?
A: When two sibling components need the same piece of state, lift it to
   their closest common ancestor. Don't lift state unnecessarily — it
   increases prop-drilling and causes more re-renders.

Q: What is the difference between UI state and server state?
A: UI state (open/closed modals, selected tabs, form inputs) lives on the
   client and is controlled by the app. Server state is async data from an
   API that needs caching, background refetching, and synchronization.
   Use different tools for each (local state for UI, React Query for server state).

Q: Can you over-use global state?
A: Yes. Over-globalizing state causes performance issues (all consumers
   re-render on every update), makes components harder to test in isolation,
   and creates hidden dependencies between components.
