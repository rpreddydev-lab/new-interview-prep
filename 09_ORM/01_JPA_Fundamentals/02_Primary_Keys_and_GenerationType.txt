JPA Primary Keys and GenerationType
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. @ID — THE PRIMARY KEY ANNOTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Id marks the field/property that is the entity's primary key.

Supported types for @Id:
  Primitive: byte, short, int, long (use wrappers to allow null check)
  Wrappers:  Byte, Short, Integer, Long  ← preferred
  Strings:   String
  Dates:     java.util.Date, java.sql.Date (legacy)
  UUID:      java.util.UUID (JPA 3.1+ natively)
  BigInteger, BigDecimal

Best practice: Use Long as the ID type for auto-generated keys.

@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}

2. GENERATION STRATEGIES — @GENERATEDVALUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@GeneratedValue(strategy = GenerationType.???)

Strategy       | Description                          | DB Support
───────────────|──────────────────────────────────────|───────────────────
AUTO           | JPA picks best strategy for the DB   | All
IDENTITY       | DB auto-increment column             | MySQL, PostgreSQL, SQL Server, H2
SEQUENCE       | DB sequence object                   | PostgreSQL, Oracle, H2
TABLE          | JPA manages a table of counters      | All (portable but slow)
UUID (JPA 3.1) | UUID primary key generation          | All

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. GENERATIONTYPE.IDENTITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

How it works:
  - Uses the DB's AUTO_INCREMENT (MySQL) or SERIAL/BIGSERIAL (PostgreSQL)
  - DB generates the ID during INSERT
  - Hibernate must execute the INSERT immediately to get the ID back
  - This DISABLES Hibernate's batch insert optimization!
    (Because each INSERT must return the generated key)

Pros:
  - Simple, works out of the box on MySQL, PostgreSQL
  - No extra DB objects needed

Cons:
  - Cannot batch inserts efficiently
  - ID only known after INSERT completes

DDL Generated:
  MySQL:      id BIGINT NOT NULL AUTO_INCREMENT
  PostgreSQL: id BIGSERIAL NOT NULL  (or BIGINT with GENERATED ALWAYS AS IDENTITY)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. GENERATIONTYPE.SEQUENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
@SequenceGenerator(
    name = "user_seq",
    sequenceName = "user_id_seq",
    allocationSize = 50   // fetch 50 values at once (batching!)
)
private Long id;

How it works:
  - Hibernate calls nextval('user_id_seq') BEFORE the INSERT
  - ID is known before INSERT → enables batch inserts
  - allocationSize: Hibernate fetches N IDs at once and distributes them
    (reduces DB round-trips)

Pros:
  - Best performance with batch inserts (allocationSize > 1)
  - Portable across Oracle, PostgreSQL, H2
  - ID is known before persisting (can be added to sets)

Cons:
  - Not supported by MySQL < 8 (use IDENTITY for MySQL)
  - Requires creating a DB sequence object

DDL Generated:
  CREATE SEQUENCE user_id_seq START 1 INCREMENT 50;

allocationSize Pitfall:
  If allocationSize = 50 and DB sequence increments by 1,
  you'll get ID conflicts (IDs 1..50 in app, but DB next is 2, 3...).
  The DB sequence INCREMENT BY must match allocationSize!
  Or use: @SequenceGenerator(allocationSize = 1) for simple cases.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. GENERATIONTYPE.AUTO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;

How it works:
  - JPA provider picks the strategy based on the database
  - Hibernate 5+: defaults to SEQUENCE with a shared sequence "hibernate_sequence"
  - Hibernate 4:  SEQUENCE for Oracle/PostgreSQL, TABLE for MySQL

Problem with AUTO in Hibernate 5+:
  - All entities share one sequence "hibernate_sequence"
  - This sequence has allocationSize=1 by default (slow)
  - Not recommended for production; be explicit

Recommendation: Avoid AUTO. Use IDENTITY for MySQL, SEQUENCE for PostgreSQL.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. GENERATIONTYPE.TABLE (Avoid in production)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Id
@GeneratedValue(strategy = GenerationType.TABLE, generator = "id_gen")
@TableGenerator(
    name = "id_gen",
    table = "id_generator",
    pkColumnName = "gen_name",
    valueColumnName = "gen_val",
    pkColumnValue = "user_id",
    allocationSize = 1
)
private Long id;

How it works:
  - JPA creates a "id_generator" table to track counter values
  - Reads + increments the counter row per INSERT (row-level lock!)

Pros:
  - Fully portable across all databases
Cons:
  - Very slow (extra SELECT + UPDATE before every INSERT)
  - Contention on the counter row under high load
  - Never use in production with meaningful load

7. UUID PRIMARY KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option 1: JPA 3.1 UUID Generation (Spring Boot 3+)
  @Id
  @GeneratedValue(strategy = GenerationType.UUID)
  private UUID id;

Option 2: Application-assigned UUID (most portable)
  @Id
  @Column(columnDefinition = "uuid", updatable = false)
  private UUID id = UUID.randomUUID();  // assigned in app before persist

Option 3: String UUID
  @Id
  @Column(length = 36, updatable = false)
  private String id = UUID.randomUUID().toString();

UUID Pros:
  ✓ Globally unique → safe for distributed systems / microservices
  ✓ ID known before INSERT → no round-trip needed
  ✓ Harder to enumerate/guess (security)
  ✓ Works well with event sourcing / distributed ID assignment

UUID Cons:
  ✗ 16 bytes vs 8 bytes for Long → larger indexes
  ✗ Random UUID (v4) causes B-tree index fragmentation
  ✗ Poor sequential ordering → use UUID v7 or ULID for ordered inserts

UUID v7 / ULID (time-ordered):
  - Time-ordered → monotonically increasing → B-tree friendly
  - ULID library: https://github.com/f4b6a3/ulid-creator
  private String id = UlidCreator.getUlid().toString();

8. COMPOSITE PRIMARY KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option 1: @EmbeddedId

@Embeddable
public class OrderItemId implements Serializable {
    private Long orderId;
    private Long productId;
    // equals, hashCode
}

@Entity
public class OrderItem {
    @EmbeddedId
    private OrderItemId id;
    private int quantity;
}

Option 2: @IdClass

public class OrderItemId implements Serializable {
    private Long orderId;
    private Long productId;
    // equals, hashCode
}

@Entity
@IdClass(OrderItemId.class)
public class OrderItem {
    @Id private Long orderId;
    @Id private Long productId;
    private int quantity;
}

When to use composite keys:
  - Junction table with extra columns
  - Legacy databases with composite PKs
  - Join tables in @ManyToMany

9. CHOOSING THE RIGHT STRATEGY — QUICK GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Database      | Recommended Strategy
──────────────|────────────────────────────────────────────
MySQL / MariaDB| IDENTITY (AUTO_INCREMENT)
PostgreSQL    | SEQUENCE with allocationSize = 50
Oracle        | SEQUENCE with allocationSize = 50
H2 (testing)  | IDENTITY or SEQUENCE (both work)
Distributed   | UUID (v4 or v7)
Any (portable)| TABLE (only if you must, it's slow)

10. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between IDENTITY and SEQUENCE strategies?
A: IDENTITY uses DB auto-increment; ID is set after INSERT completes.
   SEQUENCE fetches next value from a DB sequence BEFORE INSERT; this
   enables Hibernate to batch multiple INSERTs efficiently.

Q: Why does IDENTITY strategy disable batch inserts?
A: Hibernate needs the generated ID immediately after each INSERT to
   populate the entity. This forces one INSERT at a time, preventing
   batch accumulation.

Q: What is allocationSize in @SequenceGenerator?
A: It tells Hibernate to pre-allocate N IDs from the sequence at once.
   Hibernate keeps an in-memory range and uses it for multiple INSERTs
   before going back to the DB. Reduces DB round-trips dramatically.
   The DB sequence's INCREMENT BY must equal allocationSize.

Q: Why avoid GenerationType.AUTO?
A: In Hibernate 5+, AUTO maps to SEQUENCE with a shared single sequence
   "hibernate_sequence" used by ALL entities, which is a bottleneck and
   not intuitive. Be explicit about strategy per entity.

Q: When would you use UUID as a primary key?
A: In distributed systems where multiple services/nodes generate IDs
   independently, or when you need to generate the ID client-side before
   sending to the server, or for security (non-guessable resource IDs).
