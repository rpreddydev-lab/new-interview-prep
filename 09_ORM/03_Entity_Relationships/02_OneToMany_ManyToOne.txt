@OneToMany and @ManyToOne — The Core Relationship

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OneToMany / @ManyToOne is the most common relationship in JPA.

Examples:
  User (1) → Orders (N)       — one user has many orders
  Department (1) → Employees (N)
  Category (1) → Products (N)

Rule: The FK is ALWAYS in the MANY side's table.
  users table: id, email
  orders table: id, total, user_id   ← FK here

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. BIDIRECTIONAL @ONETOMANY / @MANYTOONE (RECOMMENDED)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String email;

    @OneToMany(
        mappedBy = "user",           // "user" field in Order entity
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY       // explicit LAZY (default)
    )
    private List<Order> orders = new ArrayList<>();

    // Always maintain both sides of bidirectional relationship:
    public void addOrder(Order order) {
        orders.add(order);
        order.setUser(this);    // set FK side
    }

    public void removeOrder(Order order) {
        orders.remove(order);
        order.setUser(null);    // clear FK side
    }
}

@Entity
@Table(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private BigDecimal total;
    private String status;

    @ManyToOne(fetch = FetchType.LAZY)    // ALWAYS use LAZY for @ManyToOne!
    @JoinColumn(name = "user_id", nullable = false)   // FK column
    private User user;   // OWNING SIDE
}

Usage:
  User user = new User();
  user.setEmail("alice@example.com");

  Order order = new Order();
  order.setTotal(new BigDecimal("99.99"));

  user.addOrder(order);  // sets both sides
  userRepository.save(user);  // cascades to Order

3. UNIDIRECTIONAL @ONETOMANY (AVOID — creates extra join table)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Without mappedBy, Hibernate creates a JOIN TABLE:

@Entity
public class User {
    @OneToMany(fetch = FetchType.LAZY)  // No mappedBy!
    private List<Order> orders;         // BAD: creates user_orders join table
}

To fix unidirectional without join table, use @JoinColumn:

@Entity
public class User {
    @OneToMany(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")   // tells Hibernate to use FK in orders table
    private List<Order> orders;
}
// Note: This is still less efficient than bidirectional.
// Updates to the collection cause extra UPDATE statements.

Best practice: Always use BIDIRECTIONAL with mappedBy.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. UNIDIRECTIONAL @MANYTOONE (FINE — no join table)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
public class Order {
    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;  // FK: orders.user_id → users.id
}
// No reference on User side — unidirectional from Order to User
// This is perfectly fine for simple use cases

5. COLLECTION TYPE CHOICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Type              | JPA/Hibernate | Notes
──────────────────|───────────────|──────────────────────────────────
List<T>           | YES           | Ordered by insertion; allows duplicates
Set<T>            | YES           | No duplicates; requires equals/hashCode
Map<K,V>          | YES           | Key-value; K = String or @MapKey field
Collection<T>     | YES           | Generic, seldom used directly
SortedSet<T>      | Hibernate     | DB-sorted set
SortedMap<K,V>    | Hibernate     | DB-sorted map

// Using Set (deduplication):
@OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
private Set<Order> orders = new HashSet<>();
// Requires proper equals/hashCode on Order!

// Using Map:
@OneToMany(mappedBy = "user")
@MapKey(name = "status")   // key = order.status
private Map<String, Order> orderByStatus = new HashMap<>();

6. ORDERING THE COLLECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OrderBy (ORDER BY in SQL):
  @OneToMany(mappedBy = "user")
  @OrderBy("createdAt DESC, id ASC")   // HQL field names, not column names
  private List<Order> orders;

@SortNatural / @SortComparator (In-memory sort):
  @OneToMany(mappedBy = "user")
  @SortNatural   // sorts in JVM memory after load (Comparable)
  private SortedSet<Order> orders;

@OrderColumn (maintain persistent list order):
  @OneToMany(mappedBy = "user")
  @OrderColumn(name = "order_position")  // adds a position column to orders table
  private List<Order> orders;

7. N+1 PROBLEM WITH @ONETOMANY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem:
  List<User> users = userRepo.findAll();  // 1 SELECT
  for (User u : users) {
      int orderCount = u.getOrders().size();  // N SELECTs (one per user!)
  }
  Total: N+1 queries for N users!

Fixes:

Fix 1: JOIN FETCH (eager load in single SQL)
  @Query("SELECT DISTINCT u FROM User u LEFT JOIN FETCH u.orders")
  List<User> findAllWithOrders();
  // One SQL with LEFT JOIN, deduplication via DISTINCT

Fix 2: @EntityGraph
  @EntityGraph(attributePaths = {"orders"})
  List<User> findAll();

Fix 3: @BatchSize (batch-load missing associations)
  @OneToMany(mappedBy = "user")
  @BatchSize(size = 20)   // load orders for up to 20 users in one query
  private List<Order> orders;
  // First query: SELECT users. Second: SELECT orders WHERE user_id IN (1,2,...,20)

Fix 4: DTO projection (skip loading entities entirely)
  @Query("SELECT new com.example.UserOrderDto(u.id, u.email, COUNT(o)) " +
         "FROM User u LEFT JOIN u.orders o GROUP BY u.id, u.email")
  List<UserOrderDto> findUserOrderCounts();

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: In a @OneToMany bidirectional relationship, which side is the owner?
A: The @ManyToOne side is the owner (it has the FK column).
   The @OneToMany side is the inverse and uses mappedBy.
   JPA determines the FK value from the @ManyToOne side.

Q: What happens if you don't set the FK side in a bidirectional relationship?
A: The FK remains null in the DB. If you only add to the @OneToMany collection
   without setting the @ManyToOne field, Hibernate won't persist the FK.
   Always use helper methods that set both sides.

Q: Why should @ManyToOne always be LAZY?
A: The default is EAGER, meaning every time you load an Order, Hibernate also
   loads the User. With a list of 100 orders, this is 100 extra SELECTs if
   each user isn't in the 1LC. Always use FetchType.LAZY and fetch explicitly
   with JOIN FETCH when needed.

Q: What is the difference between List and Set in @OneToMany?
A: List allows duplicates and preserves insertion order.
   Set prevents duplicates and requires correct equals/hashCode on the entity.
   With JOIN FETCH, List can return duplicates (one row per joined record);
   use SELECT DISTINCT or a Set to deduplicate.

Q: What is orphanRemoval and when do you use it?
A: When orphanRemoval=true, removing an entity from the collection
   automatically deletes it from the DB. Use it when the child's lifecycle
   is owned by the parent (e.g., OrderItems belong to Order — removing
   an item from the order should delete it from the DB).
