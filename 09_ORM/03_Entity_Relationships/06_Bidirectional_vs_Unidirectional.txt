================================================================
Bidirectional vs Unidirectional Relationships
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. DEFINITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Unidirectional: Only ONE entity has a reference to the other.
  Order → User (Order has a User field; User has no Orders field)
  Navigation only works one way.

Bidirectional: BOTH entities have references to each other.
  Order → User AND User → Orders
  You can navigate from either side.

Note: Bidirectional/Unidirectional is a JAVA concept only.
The DB schema is the same — FK still goes in the same column.
The difference is purely how many Java fields reference each other.

2. UNIDIRECTIONAL EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OneToMany Unidirectional (AVOID — creates hidden join table):
  @Entity
  public class User {
      @OneToMany   // No mappedBy!
      private List<Order> orders;
      // Hibernate creates: user_orders(user_id, order_id) join table
  }

  To avoid the join table, add @JoinColumn:
  @OneToMany
  @JoinColumn(name = "user_id")   // FK in orders table, but no back-reference
  private List<Order> orders;
  // Still less efficient than bidirectional — extra UPDATEs on modification

@ManyToOne Unidirectional (FINE — simple and efficient):
  @Entity
  public class Order {
      @ManyToOne(fetch = FetchType.LAZY)
      @JoinColumn(name = "user_id")
      private User user;   // FK in orders.user_id
  }
  // No reference on User side — clean and simple

@OneToOne Unidirectional (FINE for simple read path):
  @Entity
  public class User {
      @OneToOne(cascade = CascadeType.ALL, fetch = FetchType.LAZY)
      @JoinColumn(name = "profile_id", unique = true)
      private UserProfile profile;
  }
  // UserProfile has no back-reference to User

3. BIDIRECTIONAL EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OneToMany + @ManyToOne Bidirectional (RECOMMENDED for parent-child):
  @Entity
  public class User {
      @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
      private List<Order> orders = new ArrayList<>();

      public void addOrder(Order order) {
          orders.add(order);
          order.setUser(this);   // MUST set both sides
      }
  }

  @Entity
  public class Order {
      @ManyToOne(fetch = FetchType.LAZY)
      @JoinColumn(name = "user_id")
      private User user;   // owning side (FK determined here)
  }

@ManyToMany Bidirectional:
  @Entity
  public class Student {
      @ManyToMany
      @JoinTable(name = "student_courses", ...)
      private Set<Course> courses = new HashSet<>();   // owner

      public void addCourse(Course c) {
          courses.add(c);
          c.getStudents().add(this);   // sync inverse side
      }
  }

  @Entity
  public class Course {
      @ManyToMany(mappedBy = "courses")
      private Set<Student> students = new HashSet<>();   // inverse
  }

4. COMPARISON TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Aspect                  | Unidirectional          | Bidirectional
────────────────────────|─────────────────────────|──────────────────────────────
Navigation              | One way only            | Both ways
DB schema               | Same (FK in same column)| Same
Ownership / FK control  | Always the field owner  | Owning side (mappedBy defines inverse)
Code complexity         | Simpler                 | More code (helper methods)
Consistency risk        | N/A (one side)          | Must sync both sides manually
@OneToMany without FK   | Creates join table!     | Uses mappedBy (no join table)
Performance             | Fine for @ManyToOne     | Fine for all types
JSON serialization      | No circular refs        | Can cause infinite loops (use @JsonManagedReference / DTOs)

5. MAINTAINING BOTH SIDES (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JPA determines the FK value from the OWNING side (@ManyToOne side).
If you only set the inverse side (@OneToMany), the FK is NOT set!

// WRONG — FK stays NULL
user.getOrders().add(order);  // sets collection but NOT the FK
orderRepo.save(order);        // order.user_id = null!

// CORRECT — use helper method that sets both sides
user.addOrder(order);   // sets order.setUser(user) AND adds to list
userRepo.save(user);    // cascades and FK is correct

// Always keep helper methods on the PARENT (@OneToMany side):
public void addOrder(Order order) {
    this.orders.add(order);
    order.setUser(this);
}
public void removeOrder(Order order) {
    this.orders.remove(order);
    order.setUser(null);
}

6. JSON CIRCULAR REFERENCE PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Bidirectional relationships cause infinite loops in Jackson:
  User → orders → Order → user → User → ...  ← StackOverflowError

Solutions:

Option 1: Use DTOs (best practice — decouple domain from API)
  return new UserDto(user.getId(), user.getEmail());  // no entity serialization

Option 2: @JsonManagedReference / @JsonBackReference (Jackson)
  @JsonManagedReference          // User.orders — serialized
  @OneToMany(mappedBy = "user")
  private List<Order> orders;

  @JsonBackReference             // Order.user — NOT serialized (prevents loop)
  @ManyToOne
  private User user;

Option 3: @JsonIgnore on inverse side
  @JsonIgnore
  @ManyToMany(mappedBy = "courses")
  private Set<Student> students;

Option 4: @JsonIdentityInfo (serialize as ID on second occurrence)
  @JsonIdentityInfo(generator = ObjectIdGenerators.PropertyGenerator.class, property = "id")
  public class User { ... }

7. WHEN TO USE EACH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use Unidirectional when:
- Simple read path (child looks up parent, parent doesn't need to know about children)
- @ManyToOne is all you need (most common for reference data)
- Clean separation of concerns (Order knows its User, but User is agnostic of Orders)
- You want to avoid the complexity of helper methods

Use Bidirectional when:
- Parent owns the child lifecycle (cascade, orphanRemoval)
- You need to navigate from both sides in domain logic
- You frequently access children from the parent
- You're implementing aggregate root pattern

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between unidirectional and bidirectional in JPA?
A: Unidirectional means only one entity has a reference field to the other.
   Bidirectional means both entities reference each other. The DB schema is
   the same either way — the FK column doesn't change. The difference is
   purely in Java object model navigation.

Q: What is the mappedBy attribute used for?
A: mappedBy tells JPA that this side is the INVERSE of the relationship.
   The field named in mappedBy (on the other entity) is the OWNING side
   that controls the FK. mappedBy prevents JPA from creating a duplicate
   FK column or join table on the inverse side.

Q: Why must you always set both sides of a bidirectional relationship?
A: JPA reads the FK value from the OWNING side (the @ManyToOne or @JoinColumn
   side). If you only add to the inverse @OneToMany collection without setting
   the @ManyToOne field, the FK column remains null or stale. Always use helper
   methods that set both sides atomically.

Q: What happens if you forget mappedBy on a @OneToMany?
A: JPA/Hibernate creates a join table (e.g., user_orders) with two FK
   columns. This is usually unintended and wastes a table. Add mappedBy
   or @JoinColumn to prevent it.

Q: How do you avoid infinite recursion with bidirectional entities in REST APIs?
A: Best practice is to use DTOs that only expose flat data.
   Alternatively, use @JsonManagedReference / @JsonBackReference to mark
   one side as non-serializable. Never return JPA entities directly from
   REST controllers in production code.
