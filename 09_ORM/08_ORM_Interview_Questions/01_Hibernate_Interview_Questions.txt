Hibernate Interview Questions — 45 Essential Q&A

ARCHITECTURE AND CORE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is Hibernate and how does it relate to JPA?
A: Hibernate is an ORM framework that implements the JPA specification plus
   provides additional features beyond the spec (2LC, HQL extras, @Filter,
   @Immutable, Envers, spatial types, etc.). When you use Hibernate, you can
   use both JPA-standard APIs (EntityManager) and Hibernate-native APIs (Session).

Q2: What is the difference between Session and EntityManager?
A: EntityManager is the JPA standard interface; Session is Hibernate's native API.
   Session extends EntityManager in Hibernate 6+. They are functionally equivalent
   for standard operations. Session provides extra features: @NaturalId lookups,
   StatelessSession, Filter.enable(), lock() with extra modes.

Q3: What is SessionFactory vs EntityManagerFactory?
A: SessionFactory is Hibernate's native factory; EntityManagerFactory is the JPA
   equivalent. In Hibernate 6, SessionFactory extends EntityManagerFactory.
   Both are application-scoped, thread-safe, and expensive to create.
   Spring manages these as singletons.

Q4: What is HQL?
A: Hibernate Query Language — Hibernate's predecessor to JPQL. HQL and JPQL are
   nearly identical (HQL influenced JPQL). HQL supports additional features like
   natural join and insert-select. JPQL is the standard; HQL is the Hibernate superset.

Q5: What is a Hibernate dialect?
A: A Dialect class that translates Hibernate's generic SQL generation to
   database-specific SQL syntax (PostgreSQLDialect, MySQLDialect, OracleDialect).
   Set via spring.jpa.database-platform or auto-detected in Spring Boot 3.

FIRST-LEVEL CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q6: What is the first-level cache?
A: The persistence context / EntityManager's internal identity map.
   Scoped to a single Session/transaction. Guarantees identity: two calls to
   find(User.class, 1L) within the same session return the SAME Java object.
   Automatically cleared on session close.

Q7: How can stale data from the first-level cache cause bugs?
A: If you perform a bulk UPDATE/DELETE via @Modifying or native SQL, the 1LC
   is NOT automatically updated. Subsequent reads within the same transaction
   return the cached stale version. Fix: @Modifying(clearAutomatically=true)
   or call em.clear() after bulk operations.

Q8: Can you bypass the first-level cache?
A: Yes. StatelessSession has NO 1LC, NO dirty checking. Used for bulk read/write
   operations. Also: em.refresh(entity) re-reads from DB into 1LC.

SECOND-LEVEL CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q9: What is the second-level cache?
A: An application-scoped shared cache (across sessions/threads). Unlike 1LC,
   it survives session boundaries. Requires a CacheProvider (EhCache, Caffeine,
   Infinispan). Not enabled by default — requires @Cacheable on entities and
   hibernate.cache.use_second_level_cache=true.

Q10: What entities should go in the second-level cache?
A: Entities that are: read often, rarely written, not user-specific.
   Examples: lookup/reference data (Country, Category, Status enum tables).
   Bad candidates: entities with frequent updates (Order, Payment).

Q11: What is the query cache?
A: Caches the result SET of JPQL/HQL queries (list of PKs). Requires 2LC.
   Must be enabled with hibernate.cache.use_query_cache=true and @QueryHints
   with CacheModeType.NORMAL on the query. Rarely worth the complexity unless
   the same parameterized query is called repeatedly.

Q12: What happens when a cached entity is updated?
A: Hibernate invalidates the entity's 2LC region on UPDATE/DELETE.
   The next read repopulates the cache from DB. Queries whose result sets
   depend on the updated table also have their query cache regions invalidated.

HIBERNATE SPECIFIC ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q13: What is @NaturalId?
A: Hibernate annotation marking a unique business key (e.g., email, SKU).
   Allows lookup by natural key via session.byNaturalId(). Results are cached
   in 2LC. More semantic than find(id) when business key is the common query.

Q14: What is @Immutable?
A: Hibernate annotation on an entity (or collection) that makes it read-only.
   Hibernate skips dirty checking entirely for @Immutable entities.
   No UPDATE statements will ever be generated. Any modification attempt is silently ignored.
   Perfect for reference data, historical records, audit logs.

Q15: What is @DynamicUpdate?
A: Hibernate annotation that generates UPDATE SQL with only the changed columns
   instead of all columns. Reduces UPDATE statement size and reduces lock
   contention (more useful in wide-table schemas). Trade-off: SQL is generated
   per-operation instead of cached at startup.

Q16: What is @BatchSize?
A: @BatchSize(size=N) on a collection or entity tells Hibernate to use IN clause
   batching instead of individual per-entity queries. Solves N+1 by batching:
   SELECT * FROM orders WHERE id IN (1,2,3,...,N). Reduces N queries to N/batch queries.

Q17: What is @Filter?
A: Hibernate @Filter/@FilterDef allows adding dynamic WHERE conditions to
   entities/collections activated per-session. Used for soft delete, tenant
   filtering, date-range filtering. Must be enabled per session:
   session.enableFilter("activeFilter").setParameter("status", "ACTIVE").

Q18: What is @Formula?
A: Hibernate annotation that maps a field to a SQL expression (subquery or
   formula) instead of a column. Computed on SELECT: @Formula("(SELECT COUNT(*)
   FROM orders o WHERE o.user_id = id)"). Read-only, not flushed to DB.

Q19: What is @SQLRestriction (Hibernate 6)?
A: Applies a static WHERE condition to ALL queries on an entity or collection.
   Previously named @Where in older Hibernate. Use for soft delete filtering:
   @SQLRestriction("deleted_at IS NULL") — automatically appended to every query.

Q20: What is @SQLDelete and @SQLInsert?
A: Hibernate hooks to customize the DML SQL generated for an entity.
   @SQLDelete("UPDATE users SET deleted_at=NOW() WHERE id=?") converts
   DELETE to soft-delete UPDATE. Can override INSERT/UPDATE/DELETE.

PROXIES AND LAZY LOADING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q21: How does Hibernate implement lazy loading?
A: For @ManyToOne/@OneToOne: returns a Javassist/ByteBuddy proxy that extends
   the entity class. On first property access (not getId()), Hibernate fires
   a SELECT.
   For collections: returns an uninitialized PersistentBag/PersistentList/PersistentSet.
   On first access (not via getId), Hibernate fires collection SELECT.

Q22: Why does getId() on a lazy proxy NOT trigger a SELECT?
A: The ID is already known (it's how the proxy was created). Hibernate
   stores the ID in the proxy shell and can return it without initializing.
   Only accessing non-ID fields triggers the SELECT.

Q23: Can a Hibernate entity class be final?
A: No (for lazy loading to work). Hibernate must subclass the entity to create
   a proxy. Final classes and methods break this. @Embedded objects can be final.

Q24: What is Hibernate.initialize()?
A: A utility method that forces initialization of a proxy or collection
   while the session is still open. Use sparingly inside @Transactional scope.
   Better alternatives are JOIN FETCH or @EntityGraph.

STATELESS SESSION AND BATCH OPERATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q25: What is StatelessSession?
A: Hibernate StatelessSession bypasses 1LC, dirty checking, and cascading.
   Provides: insert(), update(), delete(), get(). SQL is fired immediately.
   No proxies, no caching — low-overhead for high-volume batch processing.
   Trade-off: no automatic relationship management.

Q26: How do you optimize batch inserts in Hibernate?
A: 1. Set hibernate.jdbc.batch_size=50 (or higher).
   2. Set hibernate.order_inserts=true and hibernate.order_updates=true.
   3. Use SEQUENCE or UUID for @GeneratedValue (not IDENTITY — kills batching).
   4. Call em.flush() + em.clear() every batch_size iterations to prevent 1LC bloat.

DIRTY CHECKING AND FLUSH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q27: How does Hibernate dirty checking work?
A: When an entity is loaded into 1LC, Hibernate stores a hydrated snapshot
   (the original column values as an Object[]). On flush, it compares the
   snapshot to current values field-by-field. Changed fields → UPDATE.
   Cost: O(N entities × M fields) per flush.

Q28: What is FlushMode and when would you change it?
A: AUTO (default): flush before queries that might be affected by pending changes.
   COMMIT: flush only on transaction commit (dangerous — query results may be stale).
   MANUAL: never auto-flush (must call flush() explicitly).
   Change to COMMIT in read-heavy operations where you know no queries need
   to see pending changes.

HIBERNATE ENVERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q29: What is Hibernate Envers?
A: An auditing module that tracks entity change history. Add @Audited to an entity
   and Hibernate creates a mirror _AUD table with revision data. AuditReader API
   lets you query historical states: what did this entity look like at revision N?

Q30: What does an Envers audit table look like?
A: user_aud table: all user columns + REV (revision number) + REVTYPE (0=INSERT,
   1=UPDATE, 2=DELETE). revinfo table: REV, REVTSTMP (timestamp).
   Each write operation to the audited entity inserts a row in _aud.

LOCKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q31: What is optimistic locking in Hibernate?
A: Uses a @Version field. Hibernate adds AND version=? to UPDATE WHERE clause.
   If another transaction updated the row, the count returns 0 and Hibernate
   throws StaleObjectStateException (wrapped as OptimisticLockException by JPA).

Q32: What is pessimistic locking in Hibernate?
A: Issues SELECT FOR UPDATE (PESSIMISTIC_WRITE) or SELECT FOR SHARE (PESSIMISTIC_READ).
   Blocks concurrent access at the DB level. Session.lock() or em.find() with
   LockModeType applies it. Use for financial/inventory operations with high
   contention where retry overhead is unacceptable.

INHERITANCE MAPPING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q33: Which inheritance strategy does Hibernate use by default?
A: SINGLE_TABLE is the default. All subclass rows in one table with
   @DiscriminatorColumn to differentiate types. Subtype-specific columns
   are nullable for rows of other types.

Q34: What is the performance profile of JOINED inheritance?
A: Each entity load requires a JOIN between parent and child table.
   More normalized (no nullable subtype columns) but slower for bulk reads.
   Good when subtype tables are wide and subtypes are queried independently.

Q35: Can you query a parent class and get mixed subtype instances?
A: Yes — Hibernate uses polymorphic queries. SELECT e FROM Employee e returns
   both FullTimeEmployee and PartTimeEmployee instances. Only works with
   SINGLE_TABLE (discriminator) and JOINED (JOIN on type). TABLE_PER_CLASS
   uses UNION and is least efficient for polymorphic queries.

SCHEMA AND TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q36: How does Hibernate handle JSON columns?
A: Hibernate 6+: @JdbcTypeCode(SqlTypes.JSON) on a field. Hibernate serializes/
   deserializes using Jackson. Postgres jsonb, MySQL JSON supported.
   JPQL can filter: WHERE json_extract(e.metadata, '$.status') = 'ACTIVE'.

Q37: What is a UserType in Hibernate?
A: Custom Hibernate type implementing UserType<T> for mapping complex Java types
   to DB columns when AttributeConverter isn't enough (e.g., multi-column mapping,
   custom null handling). Registered via @TypeDef or @Type annotation.

SCENARIO QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q38: Your service loads 50,000 records and runs out of heap. What do you do?
A: (1) Use pagination (Pageable) instead of findAll(); (2) Use ScrollableResults
   with StatelessSession; (3) Use DTO projections (load only needed columns);
   (4) Use @BatchSize + iteration; (5) Consider database cursor streaming.

Q39: You enabled 2LC but DB and cache are inconsistent. Why?
A: Likely: a bulk UPDATE or native SQL bypassed Hibernate — Hibernate doesn't
   know to invalidate 2LC on non-Hibernate DML. Fix: call session.getSessionFactory()
   .getCache().evictEntityData(User.class) manually, or avoid 2LC for frequently
   written entities.

Q40: equals() and hashCode() — why do they matter in Hibernate?
A: Hibernate uses equals/hashCode when storing entities in collections (Set, Map).
   Generated @EqualsAndHashCode on @Id field is problematic because ID is null
   until persist(). Best practice: implement equals/hashCode on a unique natural
   key (email, code). Never use generated ID alone in mutable hashCode.

Q41: What is the "attach detached entity" anti-pattern?
A: Calling em.merge() with a detached entity that has EAGER associations causes
   Hibernate to select all associated entities. Alternatively merge() on a stale
   detached entity overwrites DB changes made after detachment (last-write-wins).
   Fix: always reload from DB before merge, or use specific field updates.

Q42: How does Hibernate know an entity is "new" vs "existing" on save()?
A: Spring Data JPA: if entity implements Persistable, uses isNew(). Otherwise:
   if @Id field is null (or 0 for primitives) → persist (INSERT).
   If @Id is non-null → merge (SELECT + UPDATE). This is why UUID.randomUUID()
   assigned before save() triggers a SELECT (Hibernate thinks it's existing).
   Fix: implement Persistable or use @GeneratedValue.

Q43: What is MultipleBagFetchException?
A: Hibernate can't fetch two LAZY bags (List without @OrderColumn) with JOIN FETCH
   in the same query — it can't build correct results from the Cartesian product.
   Fix: (1) Change to Set; (2) Use separate queries; (3) Use @BatchSize;
   (4) Use multiple @EntityGraphs with separate queries.

Q44: What is the difference between @Fetch(FetchMode.SUBSELECT) and @BatchSize?
A: @BatchSize(size=N): loads N collections at a time with IN clause. Multiple
   trips to DB (one per N).
   SUBSELECT: loads ALL collections in ONE extra query using a subquery matching
   the original entity query. Better when all collections need loading; worse
   for memory.

Q45: How do you enable SQL logging in Spring Boot?
A: application.properties:
   spring.jpa.show-sql=true
   spring.jpa.properties.hibernate.format_sql=true
   logging.level.org.hibernate.SQL=DEBUG
   logging.level.org.hibernate.orm.jdbc.bind=TRACE  (for bind parameters)

   For production: use datasource-proxy to log SQLs + parameter values +
   slow query detection without impacting Hibernate's query plan cache.
