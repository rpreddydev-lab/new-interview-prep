1. WHAT IS THE QUERY CACHE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Query Cache stores the RESULTS of HQL/JPQL queries:
  - Key: query string + bind parameters + flush mode
  - Value: list of entity IDs (NOT entity objects)

On a cache hit, Hibernate returns the cached entity IDs,
then loads each entity from the 2LC (or DB if not in 2LC).

This means:
  Query Cache = useful ONLY when the entities are also in the 2LC.
  If entities are NOT in 2LC → cache hit on query cache still
  triggers N individual DB queries for each entity ID.

Requirements:
  1. Second-level cache provider configured (EhCache, Caffeine, etc.)
  2. use_second_level_cache=true
  3. use_query_cache=true

application.properties:
  spring.jpa.properties.hibernate.cache.use_second_level_cache=true
  spring.jpa.properties.hibernate.cache.use_query_cache=true
  spring.jpa.properties.hibernate.cache.region.factory_class=\
      org.hibernate.cache.jcache.internal.JCacheRegionFactory

3. ENABLING QUERY CACHING PER QUERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Via EntityManager / Session:
  List<Country> countries = em.createQuery(
      "SELECT c FROM Country c ORDER BY c.name", Country.class)
      .setHint("org.hibernate.cacheable", true)
      .setHint("org.hibernate.cacheRegion", "country.list")
      .getResultList();

Via Spring Data JPA repository:
  @QueryHints({
      @QueryHint(name = "org.hibernate.cacheable", value = "true"),
      @QueryHint(name = "org.hibernate.cacheRegion", value = "country.list")
  })
  @Query("SELECT c FROM Country c ORDER BY c.name")
  List<Country> findAllOrdered();

Via @NamedQuery:
  @NamedQuery(
      name = "Country.findAll",
      query = "SELECT c FROM Country c ORDER BY c.name",
      hints = {
          @QueryHint(name = "org.hibernate.cacheable", value = "true"),
          @QueryHint(name = "org.hibernate.cacheRegion", value = "country.all")
      }
  )

4. QUERY CACHE REGIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each query cache entry is stored in a "region" (like a named bucket).
  Default region: org.hibernate.cache.internal.StandardQueryCache
  Custom region: set via "org.hibernate.cacheRegion" hint

Custom regions allow different TTLs and sizes per query type.

Hibernate also maintains a "update timestamps cache" region
(org.hibernate.cache.spi.UpdateTimestampsCache) that tracks when
tables were last modified. If a table is modified, all query cache
entries for that table are invalidated.

5. WHEN IS THE QUERY CACHE INVALIDATED?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Automatic invalidation occurs when:
  - Any entity from the query's result is updated or deleted
  - Any entity of the queried type is inserted (table timestamp updated)
  - Even ONE write to the queried entity type invalidates ALL query
    cache entries for that entity!

This is the main weakness of the query cache:
  - High write frequency → constant cache misses
  - Effective ONLY for read-heavy, rarely updated data

6. QUERY CACHE vs APPLICATION CACHE (Redis/Spring Cache)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Feature                  | Hibernate Query Cache | Spring @Cacheable (Redis)
─────────────────────────|───────────────────────|─────────────────────────────
Where cached?            | Within Hibernate       | Application layer
Scope                    | JVM (or distributed)  | Configurable (Redis, etc.)
Invalidation             | Auto (table timestamp) | Manual / TTL-based
Works across instances?  | Only with dist. cache  | Yes (Redis, Hazelcast)
Caches JPA relations?    | Yes (entity IDs)       | No (must cache DTO)
Easy to understand?      | Complex (2-level)      | Simple (@Cacheable)

For microservices / multi-instance:
  Prefer Spring @Cacheable + Redis over Hibernate query cache.
  More predictable, simpler invalidation.

Q: What does the Hibernate Query Cache cache?
A: Not entity objects, but the list of entity IDs returned by a query.
   On a subsequent identical query, it returns the IDs from cache,
   then loads each entity from the 2LC. If entities are not in the 2LC,
   it still queries the DB per entity (N round-trips).

Q: When is the Query Cache beneficial?
A: When (1) the query cache is enabled, (2) the entities are also in the
   2LC, (3) the same exact query with same parameters runs frequently,
   and (4) the queried data changes infrequently. Classic example: list
   of countries, currencies, or configuration entries.

Q: What causes a query cache miss even when the data hasn't changed?
A: Any write (INSERT/UPDATE/DELETE) to the queried entity type updates
   the "timestamps cache" and invalidates ALL query cache entries for
   that entity type, even if the specific rows queried weren't modified.

Q: Should you use Hibernate Query Cache in a multi-instance deployment?
A: Only if using a distributed 2LC provider (Redis, Infinispan, Hazelcast).
   With in-process caches (EhCache single node), each instance has its
   own separate cache — inconsistency risk. Spring @Cacheable + Redis is
   often a simpler and more flexible choice.
