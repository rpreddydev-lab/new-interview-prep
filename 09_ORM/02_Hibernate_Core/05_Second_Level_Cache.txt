1. WHAT IS THE SECOND-LEVEL CACHE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Second-Level Cache (2LC) is an optional, application-scoped cache
shared across all Sessions (transactions) for the same SessionFactory.

Characteristics:
  - Shared across all transactions / Sessions
  - Survives beyond a single transaction
  - Must be explicitly configured and enabled
  - Not all entities should be cached (see guidelines below)
  - Stores entity state as "disassembled" data (dehydrated cache entries),
    not live entity objects

When a Session closes:
  1LC is cleared → entities detached
  BUT if 2LC is enabled, the entity data remains in 2LC
  Next Session looking for same entity checks 2LC before going to DB

Cache lookup flow:
  em.find(User.class, 1L)
    → check 1LC (current session)
      → check 2LC (all sessions)
        → query DB

2. CACHE PROVIDERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Provider       | Description              | Use Case
───────────────|──────────────────────────|────────────────────────
EhCache        | In-process, heap/off-heap| Single JVM, simple setup
Caffeine       | In-process, high perf    | Single JVM, fast LRU
Infinispan     | Distributed (JBoss)      | Clustered, replicated
Hazelcast      | Distributed              | Clustered, partitioned
Redis          | External, distributed    | Multi-instance, shared

Most common for Spring Boot:
  → Caffeine (simple, fast, single instance)
  → Ehcache 3 (more features, configurable TTL/size)
  → Redis (for distributed / multi-node deployments)

3. SETUP — EHCACHE 3 (JCACHE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

pom.xml:
  <dependency>
      <groupId>org.hibernate.orm</groupId>
      <artifactId>hibernate-jcache</artifactId>
  </dependency>
  <dependency>
      <groupId>org.ehcache</groupId>
      <artifactId>ehcache</artifactId>
      <classifier>jakarta</classifier>  <!-- for Hibernate 6 / Spring Boot 3 -->
  </dependency>

application.properties:
  spring.jpa.properties.hibernate.cache.use_second_level_cache=true
  spring.jpa.properties.hibernate.cache.use_query_cache=true
  spring.jpa.properties.hibernate.cache.region.factory_class=\
      org.hibernate.cache.jcache.internal.JCacheRegionFactory
  spring.jpa.properties.hibernate.javax.cache.provider=\
      org.ehcache.jsr107.EhcacheCachingProvider
  spring.jpa.properties.hibernate.javax.cache.uri=classpath:ehcache.xml

ehcache.xml (src/main/resources):
  <config xmlns:xsi="..." xmlns="http://www.ehcache.org/v3"
          xsi:noNamespaceSchemaLocation="http://www.ehcache.org/schema/ehcache-core.xsd">
      <cache alias="com.example.User">
          <expiry><ttl unit="minutes">10</ttl></expiry>
          <heap>1000</heap>
      </cache>
      <cache alias="com.example.Product">
          <expiry><ttl unit="hours">1</ttl></expiry>
          <heap>5000</heap>
          <offheap unit="MB">100</offheap>
      </cache>
  </config>

4. MARKING ENTITIES AS CACHEABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Two ways to mark an entity for 2LC:

Option 1: JPA Standard @Cacheable
  @Entity
  @Cacheable(true)
  public class Country { ... }

Option 2: Hibernate @Cache (more control over concurrency strategy)
  @Entity
  @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
  public class Product { ... }

  @Entity
  @Cache(usage = CacheConcurrencyStrategy.NONSTRICT_READ_WRITE,
         region = "products")
  public class Product { ... }

5. CACHE CONCURRENCY STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Strategy              | Description                  | When to Use
──────────────────────|──────────────────────────────|───────────────────────
READ_ONLY             | No updates allowed. Fastest. | Truly immutable data
                      | Exception if modified        | (country codes, enums)
NONSTRICT_READ_WRITE  | Invalidates on write. No lock| Rarely updated data
                      | Short stale window possible  | (product catalog)
READ_WRITE            | Soft locking on update.      | Frequently updated,
                      | Consistent, safe             | read-mostly
TRANSACTIONAL         | Full XA transaction support  | Critical data (EhCache,
                      | Fully ACID consistent        | JTA environment only)

Guideline:
  - Most entities: READ_WRITE is safest balance
  - Config/reference data: READ_ONLY
  - Cluster with distributed cache: TRANSACTIONAL

6. CACHING COLLECTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Collections are NOT cached automatically even if the owning entity is.
You must annotate the collection separately:

@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Product {
    @Id @GeneratedValue private Long id;

    @OneToMany(mappedBy = "product", cascade = CascadeType.ALL)
    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)  // ← cache the collection
    private List<Review> reviews = new ArrayList<>();
}

Without @Cache on the collection:
  Loading product → 2LC hit ✓
  Accessing product.getReviews() → DB query ✗ (not cached)

7. QUERY CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Query Cache caches the IDs of entities returned by a query.
On subsequent runs with same parameters, it returns IDs from cache,
then loads each entity from the 2LC (or DB if not cached there).

IMPORTANT: Query cache is ONLY useful when:
  - The queried entities are also cached in 2LC
  - The query is executed frequently with same parameters
  - The result set changes rarely

Enable:
  spring.jpa.properties.hibernate.cache.use_query_cache=true

Apply to a query:
  em.createQuery("SELECT c FROM Country c", Country.class)
    .setHint("org.hibernate.cacheable", true)
    .setHint("org.hibernate.cacheRegion", "country.query")
    .getResultList();

Spring Data JPA:
  @QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
  @Query("SELECT c FROM Country c ORDER BY c.name")
  List<Country> findAllCached();

8. WHAT ENTITIES TO CACHE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GOOD candidates for 2LC:
  ✓ Reference / lookup data (countries, currencies, categories)
  ✓ Configuration data (feature flags, settings)
  ✓ Rarely updated data (product catalog, user roles)
  ✓ Read-many, write-seldom entities

BAD candidates for 2LC:
  ✗ Frequently updated entities (orders, account balances)
  ✗ User-specific personalized data (session data)
  ✗ Large data sets (full user table)
  ✗ Entities that MUST be consistent in real-time (financial transactions)

9. CACHE EVICTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Hibernate evicts automatically on:
  - UPDATE / DELETE via Hibernate (entity state changes)
  - READ_WRITE strategy: soft lock during update

Manual eviction:
  SessionFactory sf = emf.unwrap(SessionFactory.class);
  Cache cache = sf.getCache();

  cache.evictEntityData(User.class, 42L);       // evict one entity
  cache.evictEntityData(User.class);            // evict all Users
  cache.evictCollectionData(User.class, "orders", 42L); // evict collection
  cache.evictQueryRegions();                    // evict all query cache
  sf.getCache().evictAllRegions();              // nuclear option: evict all

10. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the second-level cache in Hibernate?
A: An optional, application-scoped cache shared across all Sessions.
   Unlike the 1LC (per-transaction), the 2LC survives transaction boundaries.
   Configured with a cache provider (EhCache, Caffeine, Redis). Entities
   must be explicitly marked with @Cache or @Cacheable to use it.

Q: What is the difference between 1LC and 2LC?
A: 1LC: per-Session, always on, not configurable, lives for one transaction.
   2LC: per-SessionFactory, optional, configurable, shared across all
   sessions, survives transaction boundaries, needs provider (EhCache, etc.)

Q: When would you NOT use the 2LC?
A: For frequently updated data (stale cache risk), financial/critical data
   needing real-time consistency, large datasets, or user-specific data.

Q: What are the cache concurrency strategies?
A: READ_ONLY (immutable data), NONSTRICT_READ_WRITE (rarely updated, small
   stale window OK), READ_WRITE (soft locking, safest), TRANSACTIONAL
   (full XA, only with JTA-compatible cache providers).

Q: What is the Query Cache and when is it useful?
A: The Query Cache stores query results (as entity IDs). It's ONLY useful
   when both the query cache AND the entity 2LC are enabled, the query
   runs frequently with the same parameters, and the result set changes
   rarely. Misused, it adds overhead without benefit.
