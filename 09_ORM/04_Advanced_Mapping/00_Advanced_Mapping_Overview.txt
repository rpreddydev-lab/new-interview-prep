1. WHAT IS ADVANCED MAPPING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Beyond basic entity→table mapping, JPA/Hibernate supports:
- Mapping class hierarchies to tables (Inheritance Strategies)
- Embedding value objects inside entities (@Embeddable)
- Composite primary keys (@EmbeddedId, @IdClass)
- Fine-grained column/table customization
- Mapping enums and custom types
- Multitenancy (shared database, separate schema, separate DB)

Mastering these topics is expected at senior-level interviews.

3. @EMBEDDABLE (Quick Summary)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Embeddable: A class whose columns are embedded into the owner entity's table.
  No separate table. Used for value types (Address, Money, Period).

@Embedded: The field in the entity that holds the @Embeddable.
  Use @AttributeOverride to rename columns when embedding multiple instances.

See: 02_Embeddable_and_Embedded.txt

Three strategies:
- Discriminator Column: all tenants share same schema + table; tenant_id column filters
- Separate Schema: each tenant has own schema, same DB
- Separate Database: each tenant has own DB

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: When would you use @MappedSuperclass vs inheritance strategies?
A: @MappedSuperclass is NOT an entity — it has no table, can't be queried
   directly, just shares mapping metadata. Use it for common fields like
   id/createdAt/updatedAt. Inheritance strategies (SINGLE_TABLE, JOINED,
   TABLE_PER_CLASS) model IS-A relationships where the subclasses ARE
   entities and can be queried polymorphically.

Q: What is the difference between @Embeddable and a normal Entity?
A: An @Embeddable class has no identity (@Id) and cannot exist independently.
   Its columns are embedded in the owner's table. An @Entity has its own
   table and identity and can be queried independently. Use @Embeddable
   for value types (Address, Money) that semantically belong to the owner.

Q: Which inheritance strategy is most efficient?
A: SINGLE_TABLE — all subtypes in one table, no JOIN needed. Best for
   read-heavy workloads with a moderate number of subtype-specific nullable
   columns. JOINED is cleanest (normalized), but requires JOINs.
   TABLE_PER_CLASS is rarely recommended due to UNION queries.
