Inheritance Mapping Strategies in JPA/Hibernate

1. THE PROBLEM — Mapping Java Inheritance to Relational Tables
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Java supports inheritance: Animal ← Dog, Cat
Relational DBs do not have a native inheritance concept.
JPA provides 3 mapping strategies + 1 non-strategy option.

Hierarchy example used throughout:
  @Entity
  public abstract class Payment {    // parent
      Long id;
      BigDecimal amount;
      LocalDate paymentDate;
  }

  @Entity
  public class CreditCardPayment extends Payment {  // subtype
      String cardNumber;
  }

  @Entity
  public class BankTransferPayment extends Payment {  // subtype
      String iban;
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. STRATEGY 1: SINGLE_TABLE (Default)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All classes share ONE table. A discriminator column identifies the type.

@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type", discriminatorType = DiscriminatorType.STRING)
public abstract class Payment {
    @Id @GeneratedValue private Long id;
    private BigDecimal amount;
    private LocalDate paymentDate;
}

@Entity
@DiscriminatorValue("CREDIT_CARD")
public class CreditCardPayment extends Payment {
    private String cardNumber;
}

@Entity
@DiscriminatorValue("BANK_TRANSFER")
public class BankTransferPayment extends Payment {
    private String iban;
}

Generated table:
  payments(id, amount, payment_date, payment_type, card_number, iban)
  ← card_number is NULL for bank transfers; iban is NULL for credit cards

Pros:
  + No JOINs — fastest reads (single SELECT)
  + Simple queries for the parent type

Cons:
  - Many nullable columns (NOT NULL constraints impossible on subtype fields)
  - Table grows wide and sparse as subtypes grow
  - All subtypes in one table makes it hard to enforce subtype-specific constraints

Default discriminator type: STRING. Can also be CHAR or INTEGER.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. STRATEGY 2: JOINED (Most Normalized)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Parent has its own table. Each subtype has its own table with FK to parent.
A JOIN is required to load a full subtype.

@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class Payment {
    @Id @GeneratedValue private Long id;
    private BigDecimal amount;
}

@Entity
@Table(name = "credit_card_payments")  // FK: id → payments.id
public class CreditCardPayment extends Payment {
    private String cardNumber;
}

@Entity
@Table(name = "bank_transfer_payments")  // FK: id → payments.id
public class BankTransferPayment extends Payment {
    private String iban;
}

Generated tables:
  payments(id, amount, payment_date)
  credit_card_payments(id, card_number)   ← id is FK to payments.id
  bank_transfer_payments(id, iban)

SQL for loadSubtype:
  SELECT p.*, c.card_number FROM payments p
  INNER JOIN credit_card_payments c ON p.id = c.id
  WHERE p.id = ?

Pros:
  + Normalized schema; no nullable columns
  + Easy to add NOT NULL constraints on subtype-specific columns
  + Table size proportional to actual data

Cons:
  - JOINs required on every load (performance overhead for many subtypes)
  - Polymorphic queries: LEFT JOIN all subtype tables

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. STRATEGY 3: TABLE_PER_CLASS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each concrete class has its own table with ALL columns (parent + own).
No shared parent table; no discriminator column; no FK to parent.

@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Payment {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)  // IDENTITY doesn't work!
    private Long id;
    private BigDecimal amount;
}

@Entity
@Table(name = "credit_card_payments")
public class CreditCardPayment extends Payment {
    private String cardNumber;
}

Generated tables:
  credit_card_payments(id, amount, payment_date, card_number)  ← all fields
  bank_transfer_payments(id, amount, payment_date, iban)       ← all fields

Polymorphic query (SELECT p FROM Payment p):
  UNION ALL of all subtype tables

Pros:
  + No JOINs for single-type queries
  + Each table is self-contained

Cons:
  - UNION queries for polymorphic access (slow with many subtypes)
  - Duplicate columns (amount, payment_date in every table)
  - IDENTITY generation strategy doesn't work — must use SEQUENCE or TABLE
  - Not ideal for polymorphic associations

5. NON-STRATEGY: @MAPPEDSUPERCLASS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@MappedSuperclass is NOT an inheritance strategy — it's NOT an entity.
No table is created for it. It only shares mapping metadata (fields).
Cannot be queried: "FROM BaseEntity" would fail.

@MappedSuperclass
public abstract class BaseEntity {
    @Id @GeneratedValue private Long id;

    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}

@Entity
public class User extends BaseEntity {
    private String email;
    // Table: users(id, created_at, updated_at, email)
}

Use @MappedSuperclass for:
- Common audit fields (id, createdAt, updatedAt, version)
- Shared validation annotations
- Common equals/hashCode implementation

6. STRATEGY COMPARISON TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Feature             | SINGLE_TABLE  | JOINED         | TABLE_PER_CLASS
────────────────────|───────────────|────────────────|──────────────────
Tables created      | 1             | 1 per class    | 1 per concrete class
Discriminator col   | YES (needed)  | Optional       | NO
Nullable columns    | YES (many)    | NO             | NO
Polymorphic queries | Fast (no JOIN)| JOIN           | UNION ALL
Single subtype load | Fast          | JOIN required  | Fast
NOT NULL constraints| Not on subtypes| YES on each   | YES on each
IDENTITY key gen    | YES           | YES            | NO (SEQUENCE only)
Normalization       | Poor          | Best           | Medium
Recommendation      | Default pick  | Best for complex| Rarely used

7. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the default inheritance strategy in JPA?
A: SINGLE_TABLE. If you annotate a class @Entity and extend it with
   another @Entity without @Inheritance, JPA uses SINGLE_TABLE by default.

Q: When would you choose JOINED over SINGLE_TABLE?
A: When subtype-specific columns have NOT NULL constraints, or when the
   hierarchy has many subtypes with distinct attributes that would make
   the single table very wide and sparse. JOINED is more normalized but
   requires JOINs on every load.

Q: What is the problem with TABLE_PER_CLASS and IDENTITY generation?
A: IDENTITY lets the DB auto-increment per table. With TABLE_PER_CLASS,
   all tables generate IDs independently, so two tables could have the
   same ID value, breaking polymorphic queries. Use SEQUENCE or TABLE
   strategy with a shared sequence to ensure globally unique IDs.

Q: What is @MappedSuperclass and how is it different from inheritance strategies?
A: @MappedSuperclass is NOT an entity. It has no table and cannot be queried.
   It only provides field/annotation inheritance to concrete subclass entities.
   Use it for shared audit/metadata fields. Inheritance strategies (SINGLE_TABLE,
   JOINED, TABLE_PER_CLASS) are for actual IS-A entity hierarchies where the
   parent class IS also an entity.

Q: Can you have polymorphic associations with all three strategies?
A: Yes, but with different performance. SINGLE_TABLE is fastest (no JOIN,
   just filter by discriminator). JOINED uses LEFT JOINs to all subtype tables.
   TABLE_PER_CLASS uses UNION ALL which is slowest for many subtypes.
