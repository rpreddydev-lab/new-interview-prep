================================================================
ORM — Pros, Cons, and Trade-offs
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. ADVANTAGES OF ORM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Productivity and Reduced Boilerplate
   - No manual ResultSet mapping (no "rs.getString("email")" loops)
   - CRUD operations in one line: repo.save(user)
   - Spring Data derived queries eliminate even query writing

2. Database Portability
   - JPQL is database-agnostic; change DB driver and it still works
   - Critical for apps that need to support MySQL, PostgreSQL, Oracle

3. Object Graph Navigation
   - Navigate relationships naturally: user.getOrders().get(0).getItems()
   - No manual JOINs for simple association traversal

4. Built-in Caching
   - First-level cache: within a transaction, same entity = same object
   - Second-level cache: across transactions (EhCache, Redis, Infinispan)
   - Query cache: cache query results for repeated identical queries

5. Dirty Checking
   - No need to write UPDATE; ORM detects changed fields automatically
   - Only modified columns can be updated (with @DynamicUpdate)

6. Optimistic & Pessimistic Locking
   - @Version annotation gives you conflict detection for free
   - LockModeType.PESSIMISTIC_WRITE → SELECT ... FOR UPDATE

7. Schema Generation (dev only)
   - DDL auto can create/update tables from entities during development
   - Flyway/Liquibase integration for production migrations

8. Auditing
   - @CreatedDate, @LastModifiedDate, @CreatedBy built into Spring Data JPA

9. Inheritance Mapping
   - ORM handles complex inheritance hierarchies → SINGLE_TABLE,
     JOINED, TABLE_PER_CLASS strategies automatically

10. Type Safety
    - Criteria API and JPQL give compile-time checks over string SQL

2. DISADVANTAGES OF ORM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. N+1 Query Problem (Most Common Interview Topic!)
   Problem: Loading a list of 100 orders triggers 100 extra queries
            to fetch the associated user for each order.
   Cause:   Lazy loading by default on @ManyToOne and @OneToMany
   Fix:     JOIN FETCH in JPQL, @EntityGraph, batch fetching

   // Problem:
   List<Order> orders = orderRepo.findAll();  // 1 query
   for (Order o : orders) {
       o.getUser().getName();  // N additional queries!
   }

   // Fix:
   @Query("SELECT o FROM Order o JOIN FETCH o.user")
   List<Order> findAllWithUser();

2. Hidden/Uncontrolled SQL
   - Hard to predict exactly what SQL is generated
   - Can generate inefficient queries (Cartesian products, extra columns)
   - Requires enabling show-sql=true to see actual queries

3. Performance for Bulk Operations
   - Hibernate loads each entity to update/delete it (objects in memory)
   - "DELETE FROM orders WHERE status='CANCELED'" is one SQL statement
   - With Hibernate: it loads every Order, then issues N DELETE statements
   - Fix: use @Query with bulk DML, or native SQL

4. Memory Overhead
   - Loading full entity objects when you only need 2 columns wastes memory
   - Fix: projections, DTOs, SELECT new MyDto(...) in JPQL

5. LazyInitializationException
   - Accessing lazy collection after EntityManager is closed
   - Common in REST controllers that access lazy fields outside transaction
   - Fix: @Transactional, EAGER, DTO pattern, @EntityGraph

6. Learning Curve
   - Persistence context lifecycle, flush modes, cascade types,
     fetch strategies, optimistic locking — not trivial for beginners

7. Complex Queries are Awkward
   - Multi-table aggregations, window functions, CTEs are hard in JPQL
   - Criteria API is verbose and hard to read
   - Native queries lose DB portability

8. Startup Time
   - Hibernate scans all entity classes, builds schema metadata at startup
   - Large applications can have noticeable startup time

9. Concurrency Issues
   - EntityManager is NOT thread-safe; must be scoped to request/transaction
   - Second-level cache can cause stale data issues

10. Object Identity Confusion
    - Detached entities from previous requests may confuse developers
    - Merging detached entities can overwrite newer data

3. REAL-WORLD TRADE-OFF DECISION GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Scenario                              | Recommended Approach
──────────────────────────────────────|──────────────────────────────
Standard REST CRUD API                | Spring Data JPA (ORM)
Domain-driven, complex object graphs  | JPA + Hibernate
Bulk import/export of millions rows   | JDBC / Spring JDBC
Complex reporting / analytics         | Native SQL or JdbcTemplate
Microservice, simple reads            | Spring Data JDBC (no ORM)
Real-time, ultra-low latency          | JOOQ or raw JDBC
Multi-DB support needed               | JPA (DB-agnostic JPQL)
Audit trail required                  | Hibernate Envers
Need full SQL control (complex joins) | @Query nativeQuery=true / JOOQ

4. ALTERNATIVES TO JPA/HIBERNATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JOOQ (Java Object Oriented Querying):
  - Type-safe SQL DSL (not ORM, not raw string SQL)
  - Generates Java classes from DB schema
  - Full SQL power with compile-time safety
  - Best for teams that want SQL control + type safety

MyBatis:
  - SQL Mapper: you write SQL, MyBatis maps results
  - XML or annotation-based SQL definitions
  - Middle ground between JDBC and ORM
  - Popular in legacy enterprise / Asian tech companies

Spring Data JDBC:
  - Simpler than JPA: no lazy loading, no dirty checking, no caching
  - Direct SQL model, aggregate-aware, no persistence context
  - Better for DDD (Domain-Driven Design) aggregates
  - Much easier to reason about (no hidden state)

R2DBC (Reactive):
  - Non-blocking reactive SQL for Spring WebFlux apps
  - No ORM magic; works with Spring Data R2DBC repositories

5. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the main problems you've faced with ORM in production?
A: (1) N+1 queries — solved with JOIN FETCH / EntityGraph.
   (2) LazyInitializationException — solved with @Transactional or DTOs.
   (3) Bulk update performance — solved with native queries.
   (4) Unexpected SQL — identified with show-sql logging.

Q: Would you use ORM for a high-traffic read-heavy microservice?
A: Depends. For a service that just reads data for API responses,
   I'd consider DTOs with Spring Data projections or even Spring Data JDBC
   to avoid ORM overhead. For write-heavy domain logic, full JPA is great.

Q: What is JOOQ and why might you prefer it over Hibernate?
A: JOOQ generates type-safe Java code from your DB schema. You write
   SQL-like code in Java with full type safety. Unlike Hibernate, you see
   exactly what SQL runs, no magic. Better for teams that want to leverage
   advanced SQL features while keeping refactoring safety.

Q: Is Hibernate always the right choice?
A: No. For simple microservices, Spring Data JDBC is lighter and easier
   to reason about. For bulk operations, native SQL is faster. For complex
   reporting, JOOQ or native SQL is better. Choose the tool that fits the
   use case, not the tool you always use.
