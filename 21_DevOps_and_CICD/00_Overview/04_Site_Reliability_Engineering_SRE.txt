1. WHAT IS SRE?
================================================================================

SRE (Site Reliability Engineering):
  A discipline that applies software engineering principles to infrastructure
  and operations problems. Originated at Google in 2003, when Ben Treynor
  Sloss formed the first SRE team.

The Core Insight:
  "SRE is what happens when you ask a software engineer to design an
   operations function." — Ben Treynor Sloss, VP Engineering, Google

Traditional Ops Problem:
  - Ops teams rewarded for stability → resist change (change causes outages)
  - Dev teams rewarded for features → push changes frequently (change causes outages)
  - Structural conflict: both teams contribute to the problem they blame each other for

SRE Solution:
  - Use engineering to solve operational problems (automation, software)
  - Define reliability targets (SLOs) as the basis for decision-making
  - Error budgets: quantify how much risk is acceptable
  - If budget remains: deploy new features; if exhausted: focus on reliability

SRE Core Responsibilities:
  1. Availability and latency management
  2. Performance and efficiency
  3. Change management (safe deployments)
  4. Monitoring and alerting
  5. Capacity planning
  6. Emergency response
  7. Culture and tooling

SRE vs Ops:
  Traditional Ops                 | SRE
  --------------------------------|--------------------------------
  Manual operations               | Automate everything possible
  Reactive (fix when broken)      | Proactive (prevent breakage)
  Resist change (stability focus) | Enable change with error budgets
  Siloed from development         | Partners with development teams
  Output: uptime (binary)         | Output: reliability (quantified)
  No formal engineering track     | Software engineers doing ops

2. SRE vs DEVOPS
================================================================================

Relationship:
  DevOps is a broader cultural and organizational philosophy.
  SRE is an opinionated, concrete implementation of DevOps principles.
  
  "Class SRE implements interface DevOps" — common SRE saying

Comparison:

Dimension           | DevOps                          | SRE
--------------------|----------------------------------|-----------------------------------
Scope               | Entire SDLC philosophy          | Operations + reliability focus
Origin              | Community movement (~2009)       | Google (~2003)
Prescriptiveness    | Principles, not prescriptive    | Specific practices and roles
Focus               | Breaking Dev/Ops silos          | Engineering approach to operations
Key Metric          | DORA metrics                    | Error budgets, SLOs
Staffing Model      | Varies                          | Ops capacity cap: 50% engineering work
Toil Management     | Reduce toil (general)           | Explicit 50% toil cap
Error Budgets       | Rarely formalized               | Core decision-making tool
Incident Response   | Varies                          | Formal incident command, postmortems
Team Model          | Cross-functional                | Central SRE team or embedded model

Overlap:
  - Both emphasize automation
  - Both value blameless postmortems
  - Both break down Dev/Ops silos
  - Both use monitoring and metrics
  - Both promote "you build it, you run it"

3. SLIs, SLOs, SLAs, AND ERROR BUDGETS
================================================================================

This is one of the most important and commonly tested SRE topics.

-------------------------------------------------------
SLI — SERVICE LEVEL INDICATOR
-------------------------------------------------------
Definition: A quantitative measure of some aspect of the service being provided.
            The actual measurement.

Format: (Good events / Total events) × 100%
         OR (Time serving good requests / Total time) × 100%

Common SLIs:
  Availability SLI:   (Successful requests / Total requests) × 100%
  Latency SLI:        (Requests < 200ms / Total requests) × 100%
  Error Rate SLI:     (Non-5xx requests / Total requests) × 100%
  Throughput SLI:     Requests per second

Example:
  "In the last 30 days, 99.95% of requests to our API returned a 2xx response
   within 500ms." → This is an SLI measurement.

Important: SLIs should measure what the USER experiences, not just
           infrastructure metrics (CPU, memory).

Bad SLI: "CPU utilization < 80%"
Good SLI: "99% of homepage loads complete in < 2 seconds"

-------------------------------------------------------
SLO — SERVICE LEVEL OBJECTIVE
-------------------------------------------------------
Definition: A target value or range of values for an SLI. An internal goal.

Format: SLI [comparison] target [over measurement window]

Examples:
  "99.9% of requests will complete successfully over a 30-day rolling window"
  "99th percentile latency will be < 300ms over a 28-day rolling window"
  "Error rate will be < 0.1% over a 7-day rolling window"

Choosing SLOs:
  1. Start with customer expectations (what do users need?)
  2. Look at current performance (what can we reliably deliver?)
  3. Don't set SLOs too high (100% availability is a lie and impossible)
  4. Make SLOs measurable and observable
  5. Review and adjust SLOs based on data

The SLO Tightrope:
  Too tight (99.999%): Engineers spend all time firefighting, no features
  Too loose (90%): Users are unhappy, churn, poor reputation

SLO vs SLA:
  SLO is INTERNAL target.
  SLA is EXTERNAL commitment (usually with financial penalties).
  
  Rule: Set your SLO TIGHTER than your SLA.
  If SLA = 99.9%, set internal SLO = 99.95%
  This gives buffer before violating contractual obligations.

-------------------------------------------------------
SLA — SERVICE LEVEL AGREEMENT
-------------------------------------------------------
Definition: A contractual agreement with customers about the level of service.
            Violations typically incur financial penalties (service credits).

Examples:
  AWS EC2 SLA: 99.99% monthly uptime. Violation → service credits up to 30%
  Google Cloud Compute: 99.99%. Violation → 10-50% service credits
  Azure Virtual Machines: 99.99% for multi-instance in availability sets

SLA Hierarchy:
  SLA (external contract) > SLO (internal target) > SLI (actual measurement)
  
  If SLI drops below SLO → engineering alarm bells
  If SLO is breached → SLA is at risk
  If SLA is breached → business consequences (credits, churn, legal)

-------------------------------------------------------
ERROR BUDGETS
-------------------------------------------------------
Definition: The maximum allowed amount of unreliability, derived from the SLO.

Calculation:
  SLO = 99.9% → Error Budget = 100% - 99.9% = 0.1%
  
  Over 30 days (30 × 24 × 60 = 43,200 minutes):
  Error Budget = 0.1% × 43,200 = 43.2 minutes of downtime allowed per month

Error Budget Table:
  SLO       | Monthly Downtime Budget
  ----------|-----------------------
  90%       | 72 hours
  99%       | 7.2 hours
  99.9%     | 43.2 minutes
  99.99%    | 4.32 minutes
  99.999%   | 25.9 seconds

How Error Budgets Are Used:
  1. Budget remaining → Dev and SRE teams can take risks (deploy features)
  2. Budget nearly exhausted → Slow down deployments, prioritize reliability
  3. Budget exhausted → Freeze feature deployments, focus on stability
  
  "The error budget provides a common incentive for Dev and Ops to find the
   right balance between innovation and reliability." — Google SRE Book

Error Budget Policy:
  Documented agreement between Dev and SRE:
  - If budget > 50% remaining: Normal operations
  - If budget < 50% remaining: Reliability features prioritized
  - If budget exhausted: Feature freeze until budget replenishes
  - Exception for critical security patches

Error Budget Benefits:
  - Removes subjective arguments ("is this safe to deploy?")
  - Aligns Dev and SRE on shared goals
  - Quantifies risk tolerance objectively
  - Creates incentive for reliability investment

4. THE FOUR GOLDEN SIGNALS
================================================================================

Defined in the Google SRE Book as the key metrics to monitor for any service:

1. LATENCY
   Definition: Time it takes to service a request
   
   Important distinction:
   - Successful latency vs FAILED request latency (track separately!)
   - A timeout that returns an error has 100ms latency — this skews the good
     latency metric downward if not separated
   
   Measurements:
   - Average latency (less useful — hides outliers)
   - Percentile latency (more useful — P50, P95, P99, P999)
   - P99 = 99% of requests are faster than this value
   
   Example SLI: "P99 latency of POST /api/checkout < 500ms"

2. TRAFFIC
   Definition: Demand on the system (requests per second)
   
   For web services: HTTP requests per second
   For storage: Transactions per second, bytes read/written
   For streaming: Messages per second
   
   Why it matters:
   - Helps correlate other signals (error rate spike + traffic spike = incident)
   - Used for capacity planning
   - Alert on unexpected traffic drops (could be outage on client side)

3. ERRORS
   Definition: Rate of requests that fail
   
   Categories:
   - Explicit errors: HTTP 500, 4xx (some 4xx are user error, not system error)
   - Implicit errors: Wrong content, slow responses (HTTP 200 but data is wrong)
   - Policy violations: Violating SLO (even if technically successful)
   
   Example SLI: "Error rate < 0.1% (non-5xx / total requests)"
   
   Note: Watch out for "silent failures" — requests that return 200 but with
   wrong data. These require content validation in your monitoring.

4. SATURATION
   Definition: How "full" the service is — how close to capacity
   
   Often the leading indicator of performance degradation.
   
   Metrics:
   - CPU utilization (alert at 70-80%, not 100% — it's too late at 100%)
   - Memory utilization
   - Disk I/O saturation
   - Queue depth (Kafka lag, SQS depth)
   - Connection pool utilization
   - Thread pool utilization
   
   Example: When connection pool is 90% utilized, latency starts to increase.
   Alert at 80% before it becomes a problem.

Beyond the Four Golden Signals — RED Method (for microservices):
  R — Rate: Requests per second
  E — Errors: Error rate
  D — Duration: Latency distribution
  (Subset of the Four Golden Signals)

USE Method (for infrastructure/hardware):
  U — Utilization: % of time resource is busy
  S — Saturation: Extra work queued (can't be serviced)
  E — Errors: Error count

5. TOIL AND THE 50% RULE
================================================================================

Toil Definition (Google SRE):
  Work that is:
  - Manual: Done by hand, not automated
  - Repetitive: Doing the same thing over and over
  - Automatable: Could be done by a machine with enough effort
  - Tactical: Interrupt-driven reactive work
  - No enduring value: Doesn't improve things permanently
  - Scales with service growth: More traffic → more manual work linearly

Examples of Toil:
  - Manually restarting services when they fail
  - Approving routine deployments one by one
  - Manually scaling infrastructure before peak traffic
  - Password resets, account provisioning
  - Weekly capacity reports compiled manually
  - Manually triaging and routing alerts

Non-Toil (Engineering Work):
  - Automating the above tasks
  - Writing and improving monitoring systems
  - Building self-healing systems
  - Improving deployment pipelines
  - Capacity planning systems that auto-scale

The 50% Rule:
  Google mandates that SREs spend no more than 50% of their time on toil.
  At least 50% must be engineering/project work.
  
  Enforcement:
  - SREs report toil percentage in weekly/quarterly reviews
  - If toil > 50%, the SRE team escalates to management
  - Teams are given engineering time to automate the toil
  - SREs can "hand back" excess operational work to dev teams

Why the Rule Exists:
  - Prevents SRE from becoming a renamed Ops team
  - Ensures SREs spend time improving systems, not just operating them
  - Attracts and retains engineers (engineers don't want to do only manual work)
  - Builds a culture of automation

Measuring Toil:
  - Time tracking per activity
  - # of alerts that required manual intervention per week
  - # of manual deployments vs automated
  - # of tickets requiring manual remediation

6. INCIDENT MANAGEMENT AND POSTMORTEMS
================================================================================

Incident Severity Levels (common model):
  P0/SEV0: Complete outage, total service unavailability, revenue impact
  P1/SEV1: Major degradation, large portion of users affected
  P2/SEV2: Partial degradation, some users affected
  P3/SEV3: Minor issues, monitoring/alerting, no user impact
  P4/SEV4: Informational, documentation issues

Incident Response Process:

  1. DETECTION
     - Automated alerting (PagerDuty, OpsGenie trigger from Prometheus)
     - User reports (support tickets, social media)
     - Internal discovery
     
  2. ACKNOWLEDGMENT
     - On-call engineer acknowledges the alert
     - SLA on acknowledgment: typically < 5 minutes
     
  3. TRIAGE
     - Determine severity
     - Notify stakeholders (status page, Slack channel)
     - Assemble incident team if P0/P1
     
  4. INVESTIGATION
     - Identify affected components
     - Review recent changes (recent deploys? config changes?)
     - Correlate metrics/logs/traces
     
  5. MITIGATION (Not Root Cause!)
     - Goal: Restore service FIRST, investigate later
     - Rollback the last deployment
     - Disable the problematic feature flag
     - Scale up infrastructure
     - Failover to backup region
     
  6. RESOLUTION
     - Confirm service is restored
     - Remove temporary mitigations (if possible)
     - Notify stakeholders
     
  7. POSTMORTEM
     - Within 48-72 hours of incident
     - Blameless, factual analysis
     - Action items assigned

Incident Command System (ICS):
  Borrowed from emergency services:
  - Incident Commander (IC): Owns the incident, coordinates response
  - Communications Lead: Manages stakeholder updates, status page
  - Operations Lead: Leads technical investigation
  - Scribe: Documents timeline in real-time (very important!)

Key Principles During an Incident:
  - Never blame, stay factual
  - Communicate frequently (every 30 min update to stakeholders)
  - Prioritize mitigation over root cause analysis during the incident
  - Keep the incident channel on-topic (separate #incident-discussion)
  - Declare incidents early (better to declare and stand down than miss one)

Postmortem Format (Google):
  1. Summary (one paragraph)
  2. Impact (users affected, revenue impact, duration)
  3. Root Causes (what actually caused it)
  4. Resolution (how it was resolved)
  5. Timeline (chronological facts — who, what, when)
  6. What Went Well
  7. What Went Wrong
  8. Where We Got Lucky
  9. Action Items (with DRIs and due dates)

Postmortem Quality:
  Good postmortem:
  - Identifies systemic causes, not human error
  - Has concrete, assigned action items
  - Addresses monitoring gaps (why didn't we detect sooner?)
  - Published broadly for organizational learning

  Bad postmortem:
  - "Engineer X clicked the wrong button"
  - Action: "Be more careful next time"
  - No systemic improvements

7. RELIABILITY PRACTICES
================================================================================

A. CAPACITY PLANNING
   - Forecast demand growth based on business metrics
   - Ensure sufficient resources before they're needed
   - Load testing to find breaking points
   - Target: have sufficient capacity for 1.5-2x current peak traffic
   - Tools: AWS Cost Explorer, Kubernetes VPA, KEDA

B. LOAD SHEDDING
   - When overloaded, gracefully reject lower-priority requests
   - Better to reject some requests than fail all requests
   - Implementation: Rate limiting, circuit breakers, backpressure
   - Example: During traffic spike, return HTTP 429 for non-critical endpoints
     while keeping checkout endpoint running

C. GRACEFUL DEGRADATION
   - When a dependency fails, serve a degraded but functional experience
   - Example: If recommendation service is down, show popular items instead
   - Implementation: Fallbacks, cached responses, circuit breakers

D. CIRCUIT BREAKER PATTERN
   - Prevent cascading failures in distributed systems
   - States: Closed (normal) → Open (rejecting) → Half-Open (testing recovery)
   - Closed: Requests pass through normally
   - Open (triggered after X failures): Requests fail fast without calling service
   - Half-Open: Allow test request to check if service recovered
   - Libraries: Resilience4j (Java), Polly (.NET), hystrix (Netflix)

E. BULKHEAD PATTERN
   - Isolate failures to prevent them from cascading
   - Named after ship compartments — flood one, others stay intact
   - Implementation: Separate thread pools per service call
   - Example: Slow database calls use a dedicated pool, don't exhaust main pool

F. RETRY WITH EXPONENTIAL BACKOFF AND JITTER
   - Transient failures: retry with increasing delays
   - Exponential backoff: 1s, 2s, 4s, 8s delays
   - Jitter: Add randomness to prevent "thundering herd" (all clients retry at same time)
   - Max retries: 3-5 attempts, then fail

G. RUNBOOKS AND OPERATIONAL DOCUMENTATION
   - Documented procedures for common operational tasks
   - Stored in version control alongside code
   - Include: what the alert means, how to investigate, how to fix
   - Alert → Runbook link directly in alert notification

H. GAME DAYS
   - Scheduled exercises simulating failure scenarios
   - Team practices incident response in controlled environment
   - Tests runbooks, escalation procedures, monitoring effectiveness
   - Builds muscle memory for real incidents

8. CHAOS ENGINEERING
================================================================================

Definition:
  "The discipline of experimenting on a system to build confidence in the
   system's capability to withstand turbulent conditions in production."
   — Principles of Chaos Engineering

Origin: Netflix (2011) — "Chaos Monkey" randomly terminated EC2 instances in
production to force engineers to build resilient systems.

The Chaos Engineering Process:
  1. Define "steady state" — normal system behavior (baseline metrics)
  2. Hypothesize: "If we kill service X, the system will remain in steady state"
  3. Run experiment in production or staging
  4. Observe: Did the system remain in steady state?
  5. Fix weaknesses discovered
  6. Repeat with increasingly complex scenarios

Netflix Simian Army (historical):
  - Chaos Monkey: Randomly kills EC2 instances
  - Chaos Gorilla: Takes down entire AWS Availability Zone
  - Latency Monkey: Introduces artificial network latency
  - Conformity Monkey: Shuts down non-conforming instances
  - Doctor Monkey: Health checks and terminates unhealthy instances

Chaos Engineering Tools:
  - Chaos Monkey / Chaos Engineering Platform: Netflix
  - Gremlin: Commercial SaaS chaos engineering platform
  - LitmusChaos: Kubernetes-native chaos engineering (CNCF)
  - Chaos Mesh: Kubernetes chaos engineering (CNCF)
  - AWS Fault Injection Simulator (FIS): AWS managed chaos engineering

Chaos Experiment Examples:
  - Kill a pod/container in Kubernetes
  - Introduce 500ms of latency to database calls
  - Fill disk to 90% capacity
  - Exhaust CPU on a node
  - Drop 20% of network packets
  - Kill a microservice that another depends on
  - Revoke IAM credentials

Key Principle:
  "Chaos engineering is NOT about breaking things randomly. It's about
   conducting controlled experiments to gain confidence in your system."

When to Start Chaos Engineering:
  Prerequisites:
  1. Solid monitoring and alerting (you need to measure steady state)
  2. On-call rotation in place
  3. Runbooks for common failures
  4. Leadership buy-in (especially for production experiments)

9. SRE TEAM MODELS
================================================================================

Three Models (from Google SRE Book):

1. KITCHEN SINK (central SRE team supports all services)
   - One SRE team responsible for all services
   - Best for: small organizations, early-stage adoption
   - Risk: Doesn't scale as company grows

2. INFRASTRUCTURE SRE (central team owns shared infra)
   - SRE team owns platform infrastructure (K8s cluster, CI/CD, monitoring)
   - Product teams own their service reliability
   - Best for: Platform engineering model

3. EMBEDDED SRE (SREs placed in product teams)
   - SREs embedded in development teams
   - Deep product knowledge
   - Risk: Loss of consistency, SRE practices diverge across teams
   - Safeguard: SRE "community of practice" / chapter for shared standards

On-Call Practices:
  - On-call rotation: Typically 1 week, rotating among SREs
  - On-call load: < 2 incidents per shift on average
  - Escalation path: L1 on-call → L2 expert → Management
  - Compensation: Additional pay or time off for on-call burden
  - Psychological safety: Never penalize for escalating

SRE SLA for Reliability:
  - Google's rule: SRE team takes on service only if it meets reliability bar
  - Service must have adequate test coverage
  - Development team must commit to fixing reliability issues SRE identifies
  - SRE can "hand back" services that consistently violate reliability standards

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is SRE and how does it differ from traditional operations?
A: SRE is a discipline that applies software engineering to infrastructure and
   operations problems. Ben Treynor Sloss at Google coined it: "SRE is what
   happens when you ask a software engineer to design an operations function."
   
   Traditional Ops reacts to problems manually, resists change for stability,
   and is separated from development. SRE applies engineering: automates toil,
   uses error budgets to quantify risk tolerance, and partners with development
   teams. SRE's goal isn't just stability — it's the RIGHT level of reliability,
   measured against SLOs.

Q2: Explain SLI, SLO, SLA, and error budgets with an example.
A: 
   SLI (Indicator): The measurement. Example: "98.5% of API requests returned
   2xx in the last 30 days."
   
   SLO (Objective): The target. Example: "99.9% of requests should return 2xx."
   
   SLA (Agreement): External contract. Example: "We guarantee 99.5% uptime;
   violations trigger service credits."
   
   Error Budget: The tolerance. SLO = 99.9% → Error Budget = 0.1% = 43.2
   minutes/month. If we've used 30 minutes this month, we have 13 minutes left
   to "spend" on risky deployments.
   
   Practical use: With 30 minutes of budget remaining, we can deploy a
   moderate-risk feature. With 2 minutes remaining, we pause non-critical
   deployments and focus on reliability.

Q3: What are the Four Golden Signals?
A: Latency (how long requests take), Traffic (how many requests per second),
   Errors (rate of failed requests), and Saturation (how full the system is —
   CPU, memory, queue depth). If you can only measure four things, measure
   these. Together they give a complete picture of service health. Latency and
   errors tell you about correctness; traffic tells you about demand; saturation
   is the leading indicator of degradation.

Q4: What is the SRE 50% toil rule?
A: Google mandates that no SRE spends more than 50% of their time on toil —
   manual, repetitive, automatable work. The remaining 50%+ must be
   engineering: improving systems, reducing toil, building automation.
   If toil exceeds 50%, the team escalates to management and gets engineering
   time to automate. This prevents SRE from becoming a renamed ops team
   and ensures continuous improvement.

Q5: Walk me through how you would respond to a production P0 incident.
A: 
   1. Detection: PagerDuty fires. I acknowledge within 5 minutes.
   2. Triage: Check monitoring dashboard — error rate spiked to 50%,
      latency P99 at 10 seconds. Check recent deploys — deployment 20 min ago.
   3. Notify: Post in #incidents channel, assign Incident Commander,
      update status page.
   4. Mitigate first: Rollback the deployment. Observe metrics recovering.
   5. Communicate: Update stakeholders every 30 minutes.
   6. Resolve: Confirm metrics return to normal. Close incident.
   7. Postmortem: Within 48 hours — timeline, root cause, action items.
      Why didn't staging catch this? Why did the alert take 5 min to fire?

Q6: What is Chaos Engineering and why would you implement it?
A: Chaos Engineering is the practice of deliberately injecting failures into
   a system to test its resilience. Netflix pioneered this with Chaos Monkey,
   which randomly kills production servers.
   
   The rationale: Systems will fail in production regardless. You'd rather
   discover failure modes in a controlled experiment than during a real incident.
   Chaos engineering validates that your redundancy, fallbacks, and monitoring
   actually work.
   
   Prerequisites: Solid monitoring (to measure steady state), runbooks, and
   leadership buy-in. Start in staging, graduate to production with small
   blast radius experiments.

Q7: How do error budgets align Dev and SRE teams?
A: Error budgets create a shared quantitative language for reliability vs
   velocity discussions. Without error budgets, the conversation is subjective:
   "Can we deploy?" "I don't know, is it safe?" "I think so."
   
   With error budgets: "We have 20 minutes of budget remaining this month.
   This deployment has an estimated 10% chance of causing a 5-minute outage
   (0.5 minute expected cost). We can deploy, but should monitor closely."
   
   When the budget is exhausted, the policy (not the SRE team) dictates
   freezing feature deployments. This removes the "SRE is blocking us"
   frustration — the policy is agreed upon in advance.
