1. WHAT IS SDLC?
================================================================================

SDLC (Software Development Life Cycle):
  A structured process for planning, creating, testing, and deploying software
  systems. It defines the stages a software product goes through from inception
  to retirement.

Purpose:
  - Provide a systematic approach to software development
  - Ensure quality and correctness of software
  - Reduce project risk
  - Align software delivery with business needs
  - Provide clarity for teams on roles and responsibilities

Core Stages (regardless of methodology):
  1. Planning & Requirements
  2. System Design
  3. Implementation (Coding)
  4. Testing & QA
  5. Deployment
  6. Maintenance & Operations

2. TRADITIONAL SDLC MODELS
================================================================================

A. WATERFALL (Sequential)
   -----------------------
   Structure:
     Requirements → Design → Implementation → Testing → Deployment → Maintenance
   
   Each phase is completed before the next begins. No going back.

   Characteristics:
     - Heavy upfront documentation
     - Long release cycles (6-18 months)
     - Testing happens late (after all code is written)
     - Changes are expensive (especially late in the cycle)
     - Customers don't see the product until final delivery

   Problems:
     - Requirements change during development
     - Bugs found late are 10-100x more expensive to fix
     - Developers and operations are completely separate teams
     - "Throw it over the wall" from Dev to Ops at the end

   When Waterfall Fails:
     Classic example: A project takes 2 years. Halfway through, a competitor
     releases a similar product. The team can't pivot without restarting.

B. V-MODEL (Verification and Validation)
   ----------------------------------------
   Extension of Waterfall where each development phase has a corresponding
   test phase:

     Requirements Spec ←→ Acceptance Testing
     High-Level Design ←→ System Testing
     Low-Level Design  ←→ Integration Testing
     Coding            ←→ Unit Testing

   Benefits over Waterfall:
     - Test planning begins early
     - Each phase has clear exit criteria

   Limitation: Still sequential, still slow.

C. SPIRAL MODEL
   -------------
   Combines iterative development with systematic aspects of Waterfall.
   Each spiral cycle includes: Planning → Risk Analysis → Engineering → Evaluation

   Best for: High-risk, large-scale projects (defense, aerospace)
   Limitation: Complex to manage, expensive

D. ITERATIVE / INCREMENTAL
   -------------------------
   Software is built in small increments, each adding new functionality.
   Each iteration goes through full SDLC phases.
   Precursor to Agile.

E. AGILE (Iterative + Adaptive)
   ------------------------------
   Short iterations (sprints), continuous customer feedback, adaptive planning.
   Already covered in detail in 02_DevOps_vs_Agile.txt.

3. HOW DEVOPS TRANSFORMS THE SDLC
================================================================================

Traditional SDLC Problems DevOps Solves:

PROBLEM 1: Long Release Cycles
  Traditional: Quarterly or annual releases
  DevOps Solution: CI/CD enables daily or hourly deployments

PROBLEM 2: Manual, Error-Prone Deployments
  Traditional: Runbooks, manual steps, human error
  DevOps Solution: Automated deployment pipelines (Jenkins, GitHub Actions)

PROBLEM 3: Late Testing
  Traditional: QA phase starts after all code is written
  DevOps Solution: Test automation runs on every commit (shift left)

PROBLEM 4: Siloed Teams
  Traditional: Dev passes code to QA → QA passes to Ops → Ops deploys
  DevOps Solution: Cross-functional teams own code from commit to production

PROBLEM 5: Lack of Feedback
  Traditional: Customer feedback after months of development
  DevOps Solution: Production monitoring, A/B testing, feature flags for
  real-time feedback from actual users

PROBLEM 6: Inconsistent Environments
  Traditional: "Works on my machine" — different configs between Dev/QA/Prod
  DevOps Solution: Containers (Docker), IaC (Terraform) ensure parity

PROBLEM 7: No Visibility into Production
  Traditional: Ops manages production, Dev never sees it
  DevOps Solution: Shared monitoring dashboards, shared on-call rotation

DevOps SDLC vs Traditional SDLC:

Phase              | Traditional                    | DevOps
-------------------|--------------------------------|----------------------------------
Requirements       | Big upfront requirements doc   | User stories, rolling backlog
Design             | Complete design before coding  | Evolutionary design, ADRs
Development        | Months of isolated coding      | Daily commits, trunk-based dev
Testing            | Manual QA phase at the end     | Automated tests on every commit
Integration        | "Integration hell" at the end  | Continuous integration
Deployment         | Manual, quarterly              | Automated, daily or continuous
Monitoring         | Ops team only                  | Shared dashboards, alerts to dev
Feedback           | After release (post-launch)    | Real-time from production metrics
Incident Response  | Ops handles, Dev not involved  | Shared on-call, blameless retro
Improvement        | Ad-hoc                         | Sprints, retrospectives, postmortems

4. MODERN DEVOPS SDLC PHASES
================================================================================

The DevOps SDLC is a continuous loop (the "infinity loop"):

PHASE 1: PLAN
  Activities:
    - Define features, user stories, acceptance criteria
    - Backlog prioritization
    - Sprint planning (if using Scrum)
    - Architecture Decision Records (ADRs)
    - Capacity planning
  
  Tools: Jira, GitHub Issues, Azure Boards, Confluence, Miro

  Best Practices:
    - Write Acceptance Criteria in BDD (Given/When/Then) format
    - Keep stories small (can be completed in 1-3 days)
    - Involve Ops in planning (operational requirements, SLOs)
    - Define non-functional requirements: performance, scalability, security

PHASE 2: CODE
  Activities:
    - Feature development
    - Code review (PRs)
    - Pair programming
    - Documentation (README, API docs)
  
  Tools: Git, GitHub/GitLab/Bitbucket, VS Code, IntelliJ, pre-commit hooks
  
  Best Practices:
    - Trunk-based development or short-lived feature branches
    - Pre-commit hooks for linting and formatting
    - Sign commits (GPG signatures for auditability)
    - Conventional commits for changelog generation
    - Write tests alongside code (TDD)

PHASE 3: BUILD
  Activities:
    - Compile source code
    - Dependency resolution
    - Static code analysis
    - Create artifacts (JARs, WARs, Docker images, npm packages)
  
  Tools: Maven, Gradle, npm, pip, Docker, Make, Bazel
  
  Best Practices:
    - Deterministic, reproducible builds
    - Pin dependency versions (lock files: package-lock.json, Pipfile.lock)
    - Fail fast: if compilation fails, stop pipeline immediately
    - Build once, deploy many times (don't build per-environment)
    - Artifact versioning: semantic versioning or git SHA tags

PHASE 4: TEST
  Activities:
    - Unit testing
    - Integration testing
    - End-to-end testing
    - Performance testing
    - Security scanning (SAST, dependency check)
  
  Tools: JUnit, Pytest, Selenium, Cypress, JMeter, SonarQube, Snyk, OWASP
  
  Best Practices:
    - Follow the Test Pyramid (more unit, fewer E2E)
    - Fail pipeline on any test failure
    - Measure code coverage (target: 80%+)
    - Run tests in parallel to reduce time
    - Keep tests fast: unit tests < 1 min, full suite < 30 min

PHASE 5: RELEASE / PACKAGE
  Activities:
    - Tag artifacts with version
    - Push to artifact registry
    - Generate changelog
    - Create release notes
    - Security scanning of artifacts
  
  Tools: JFrog Artifactory, Nexus, Docker Hub, ECR, GitHub Releases
  
  Best Practices:
    - Immutable artifacts: once published, never overwrite
    - Semantic versioning: MAJOR.MINOR.PATCH
    - Scan images for vulnerabilities before publishing (Trivy, Snyk)
    - Signed artifacts for supply chain security (Sigstore/Cosign)

PHASE 6: DEPLOY
  Activities:
    - Deploy to staging environment (automated)
    - Run smoke tests
    - Deploy to production (automated or with approval gate)
    - Verify deployment health
  
  Tools: ArgoCD, Helm, Jenkins, GitHub Actions, Spinnaker, Flux
  
  Best Practices:
    - Progressive deployment (Canary or Blue-Green)
    - Automated rollback on health check failure
    - Deploy during low-traffic periods for high-risk changes
    - Feature flags to separate deployment from feature release
    - Immutable deployments (replace, don't modify)

PHASE 7: OPERATE
  Activities:
    - Scale infrastructure based on demand
    - Manage configurations
    - Certificate rotation
    - Backup and disaster recovery
    - Cost optimization
  
  Tools: Kubernetes HPA, Terraform, Ansible, AWS Auto Scaling, Vault
  
  Best Practices:
    - Infrastructure as Code (no manual changes)
    - Auto-scaling policies based on metrics
    - Chaos engineering (deliberately test failure scenarios)
    - GitOps: Git as source of truth for infrastructure state

PHASE 8: MONITOR
  Activities:
    - Collect metrics, logs, and traces
    - Alert on anomalies
    - Create dashboards
    - Incident management
    - Capacity planning from trends
  
  Tools: Prometheus, Grafana, Datadog, ELK Stack, PagerDuty, Jaeger
  
  Best Practices:
    - The Four Golden Signals: Latency, Traffic, Errors, Saturation
    - Define SLOs before deploying
    - Alert on SLO breach, not arbitrary thresholds
    - Distributed tracing for microservices debugging
    - Log correlation IDs for request tracking

5. TESTING IN THE SDLC — THE TEST PYRAMID
================================================================================

The Test Pyramid (Martin Fowler):

            /\
           /  \
          / E2E\  ← Few, slow, expensive (UI, browser tests)
         /------\
        /  Integ \  ← Medium amount, test component interactions
       /----------\
      /  Unit Tests\  ← Many, fast, cheap, high coverage
     /--------------\

Unit Tests (Base — ~70%):
  - Test individual functions/classes in isolation
  - Mocked dependencies
  - Fast (milliseconds per test)
  - Developers write them
  - Tools: JUnit, Pytest, Jasmine, Jest, NUnit

Integration Tests (Middle — ~20%):
  - Test interaction between components
  - Real database, real service calls (or test doubles)
  - Slower than unit tests (seconds per test)
  - Tools: Spring Test, TestContainers, Pytest with real DB

End-to-End (E2E) Tests (Top — ~10%):
  - Test complete user journeys through the application
  - Real browser, real infrastructure
  - Slowest and most brittle
  - Tools: Selenium, Cypress, Playwright, Appium (mobile)

Additional Test Types:
  - Contract Tests: Verify API contracts between services (Pact framework)
  - Performance Tests: Load testing, stress testing (JMeter, Gatling, k6)
  - Security Tests: SAST, DAST, dependency scanning
  - Chaos Tests: Resilience testing under failure conditions
  - Smoke Tests: Quick sanity checks after deployment ("is it alive?")
  - Regression Tests: Ensure existing functionality still works

Testing Anti-Pattern — The Testing Ice Cream Cone:
  Too many E2E tests, too few unit tests.
  - Slow pipeline (E2E tests take hours)
  - Brittle tests (break on UI changes)
  - Poor coverage insight
  - Late feedback (failures discovered after all code is merged)

6. SECURITY IN THE SDLC (DEVOPS SHIFT LEFT)
================================================================================

Shift Left Security (DevSecOps):
  Move security checks as early as possible in the SDLC.

Cost of Fixing Vulnerabilities:
  Design phase:    1x cost
  Development:     6x cost
  QA Testing:      15x cost
  Production:      100x cost
  (IBM Systems Sciences Institute research)

Security at Each SDLC Phase:

PLAN:
  - Threat modeling (STRIDE: Spoofing, Tampering, Repudiation,
    Info Disclosure, Denial of Service, Elevation of Privilege)
  - Security requirements defined upfront
  - Privacy by design

CODE:
  - IDE security plugins (SonarLint, Snyk IDE)
  - Pre-commit hooks: secret detection (git-secrets, detect-secrets)
  - Peer code review with security checklist

BUILD:
  - SAST (Static Application Security Testing): SonarQube, Checkmarx, Semgrep
  - Secret scanning: GitGuardian, TruffleHog
  - Dependency vulnerability scanning: Snyk, OWASP Dependency Check

TEST:
  - DAST (Dynamic Application Security Testing): OWASP ZAP, Burp Suite
  - API security testing
  - Fuzz testing

RELEASE:
  - Container image scanning: Trivy, Clair, Anchore, Snyk Container
  - Software Bill of Materials (SBOM): Syft, CycloneDX

DEPLOY:
  - Secrets management: HashiCorp Vault, AWS Secrets Manager
  - Policy as Code: OPA (Open Policy Agent), Kyverno

OPERATE:
  - Runtime security: Falco, Sysdig
  - RBAC and least privilege
  - Network policies

MONITOR:
  - SIEM (Security Information and Event Management): Splunk, QRadar
  - Anomaly detection
  - Audit log monitoring

7. ENVIRONMENTS IN THE SDLC
================================================================================

Typical Environment Chain:
  Development → CI → Staging (UAT) → Pre-Production → Production

LOCAL DEVELOPMENT:
  - Developer's machine
  - Uses local databases, mocked external services
  - Docker Compose for local environment parity
  - Must mirror production as closely as possible

CI ENVIRONMENT:
  - Ephemeral — spun up for each pipeline run
  - Isolated from other runs
  - Runs all automated tests
  - Should be as close to production as possible

STAGING / QA ENVIRONMENT:
  - Permanent environment for QA and UAT
  - Matches production configuration
  - May use production-like data (anonymized)
  - Acceptance testing and exploratory testing happen here

PRE-PRODUCTION / CANARY:
  - Production-identical environment
  - Performance testing, final smoke tests
  - Sometimes receives a small % of production traffic (canary)

PRODUCTION:
  - The real thing
  - Users interact here
  - Monitoring and alerting most critical here

Environment Parity Best Practices:
  - Use containers so the same image runs in all environments
  - Use IaC to create environments reproducibly
  - Separate configuration from code (12-Factor App principle)
  - Use feature flags instead of separate code branches per environment

The 12-Factor App (Configuration):
  Factor III: "Store config in the environment"
  - Database URLs, API keys, feature flags: environment variables or secrets
  - Never hardcode environment-specific values in code
  - Same artifact deployed to all environments; config differs

8. SDLC GOVERNANCE AND COMPLIANCE
================================================================================

Change Management:
  - Formal Change Advisory Boards (CABs) vs. automated approval
  - ITIL (IT Infrastructure Library): Framework for IT service management
  - Change Categories:
    - Standard (pre-approved, low-risk): Automated
    - Normal (goes through change process): CI/CD with approval gate
    - Emergency: Fast-track process for critical fixes

Compliance Frameworks:
  - SOC 2: Security, availability, processing integrity, confidentiality, privacy
  - PCI-DSS: Payment Card Industry Data Security Standard
  - HIPAA: Health Insurance Portability and Accountability Act
  - ISO 27001: Information security management
  - GDPR: General Data Protection Regulation

DevOps and Compliance:
  - "Compliance as Code": Policy checks in the pipeline
  - Audit logs automatically captured via Git commits, pipeline runs
  - Immutable artifact registry provides evidence of what was deployed
  - Separation of duties: Different people approve vs deploy
  - Automated security scanning provides audit trail

Architecture Decision Records (ADRs):
  - Document significant architectural decisions
  - Format: Context, Decision, Status, Consequences
  - Stored in the repository (docs/adr/)
  - Provides audit trail of why technical choices were made

9. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the SDLC and how does DevOps change it?
A: The SDLC is the process of planning, building, testing, deploying, and
   maintaining software. Traditional SDLC models like Waterfall use sequential
   phases with handoffs between teams — Dev writes code, passes to QA, which
   passes to Ops for deployment. This creates bottlenecks, delays, and
   "integration hell."
   
   DevOps transforms the SDLC by automating the handoffs, enabling continuous
   integration and deployment, shifting testing and security left (earlier in
   the process), and creating shared ownership across Dev and Ops. The result
   is a faster, more reliable delivery loop where code can go from commit to
   production in hours rather than months.

Q2: What is "shift left" and why is it important?
A: Shift left means moving quality and security checks to earlier stages in the
   SDLC. "Left" refers to the left side of a timeline diagram. Instead of
   testing after all code is written (right side), you write unit tests while
   coding and run them on every commit (left side). Instead of security
   scanning before release, you scan code in CI on every PR.
   
   It's important because defects are exponentially cheaper to fix earlier.
   A bug found in unit testing costs 1x to fix. Found in QA: 15x. Found in
   production: 100x. Shift left reduces both cost and time to delivery.

Q3: Describe the Test Pyramid and why it matters.
A: The Test Pyramid has three layers: Unit tests (base — many, fast, cheap),
   Integration tests (middle — fewer, test component interactions), and E2E
   tests (top — few, slow, expensive). You should have the most unit tests and
   the fewest E2E tests.
   
   It matters because many teams fall into the "testing ice cream cone"
   anti-pattern: too many E2E tests that run slowly and break frequently.
   Following the pyramid keeps the CI pipeline fast (unit tests run in seconds),
   provides accurate test coverage information, and ensures failures are caught
   close to their source.

Q4: How do you ensure environment parity in a DevOps pipeline?
A: Three main approaches:
   1. Containers (Docker): The same Docker image runs in dev, staging, and
      production. The environment is defined in the Dockerfile.
   2. Infrastructure as Code (Terraform): The same Terraform modules are used
      to provision all environments, ensuring identical configurations.
   3. Configuration separation (12-Factor App): Config (DB URLs, API keys)
      comes from environment variables, not the application code. So the same
      artifact is deployed everywhere with environment-specific config.

Q5: What is Configuration Drift and how do you prevent it?
A: Configuration drift occurs when servers that were once identical diverge
   over time due to manual changes, ad-hoc fixes, or software updates. A server
   that was manually patched differs from another that wasn't, making the
   environment unpredictable.
   
   Prevention:
   - Immutable infrastructure: Replace servers instead of modifying them
   - Configuration Management tools: Ansible runs regularly to enforce desired
     state and detect/correct drift
   - No manual SSH access to production (all changes via code)
   - Regular compliance scans (AWS Config, Azure Policy)

10. QUICK REFERENCE CHEAT SHEET
================================================================================

SDLC Models (oldest to newest):
  Waterfall → V-Model → Spiral → Iterative → Agile → DevOps

DevOps SDLC Phases:
  Plan → Code → Build → Test → Release → Deploy → Operate → Monitor

Test Pyramid (bottom to top):
  Unit Tests (70%) → Integration Tests (20%) → E2E Tests (10%)

Shift Left principle:
  Move testing, security, and quality checks earlier in the pipeline
  Cost: 1x (design) → 6x (dev) → 15x (QA) → 100x (production)

Environment chain:
  Local → CI → Staging → Pre-Prod → Production

12-Factor App (Config):
  Store config in environment, not code. Same artifact, different config.

Compliance keywords:
  SOC 2, PCI-DSS, HIPAA, GDPR
  "Compliance as Code" — policy checks in the pipeline

Key DevOps SDLC improvements:
  - Build once, deploy many (immutable artifacts)
  - Continuous testing (every commit triggers tests)
  - Automated deployments (no manual runbooks)
  - Feature flags (deploy code without releasing features)
  - Production monitoring feeding back to development
