1. ANSIBLE OVERVIEW AND ARCHITECTURE
================================================================================

What is Ansible?
  Open-source IT automation tool for:
  - Configuration management (install packages, configure files)
  - Application deployment (deploy code, restart services)
  - Infrastructure provisioning (create cloud resources)
  - Orchestration (rolling deployments, ordered operations)
  
  Created by: Michael DeHaan (2012), acquired by Red Hat (2015), part of IBM.

Key Characteristics:
  Agentless:
    No agent installed on managed nodes.
    Uses SSH (Linux/macOS) or WinRM (Windows).
    Control node connects to managed nodes on demand.
  
  Declarative (mostly):
    Describe desired state ("nginx should be installed").
    Modules handle idempotency ("if installed, do nothing").
  
  YAML-based:
    Playbooks, roles, variables — all YAML.
    Human-readable, no special syntax to learn.
  
  Push-based:
    Control node PUSHES configuration to managed nodes.
    (vs. Puppet/Chef which are pull-based: agents pull from server)

Architecture:
  
  ┌────────────────────────────────────────────────┐
  │            Control Node (your machine/CI)       │
  │                                                  │
  │  ┌──────────┐  ┌──────────┐  ┌──────────────┐  │
  │  │ Playbooks│  │ Inventory│  │ Ansible.cfg  │  │
  │  └──────────┘  └──────────┘  └──────────────┘  │
  │                    │                            │
  └────────────────────┼────────────────────────────┘
                       │ SSH / WinRM
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │ Web 1    │ │ Web 2    │ │ DB 1     │
    │ (Ubuntu) │ │ (Ubuntu) │ │ (Ubuntu) │
    └──────────┘ └──────────┘ └──────────┘
                Managed Nodes
                (no agent needed)

Ansible vs Terraform:
  Terraform: Provision cloud INFRASTRUCTURE (EC2, VPC, RDS)
  Ansible:   Configure SERVERS (install packages, configure apps)
  
  Often used together:
  Terraform creates servers → Ansible configures them.

2. INVENTORY
================================================================================

What is Inventory?
  Defines the managed nodes (hosts) and organizes them into groups.
  Static (files) or Dynamic (scripts/plugins that query cloud APIs).

Static Inventory (INI format):
  
  # inventory/hosts.ini
  
  # Standalone host:
  web1.example.com
  web2.example.com ansible_host=10.0.0.5    # Override connection hostname
  
  # Groups:
  [webservers]
  web1.example.com
  web2.example.com
  web3.example.com
  
  [databases]
  db1.example.com
  db2.example.com
  
  # Group of groups:
  [production:children]
  webservers
  databases
  
  # Group variables:
  [webservers:vars]
  ansible_user=ubuntu
  nginx_port=80
  
  [production:vars]
  environment=production

Static Inventory (YAML format, preferred):
  
  # inventory/hosts.yaml
  all:
    children:
      production:
        children:
          webservers:
            hosts:
              web1.example.com:
                ansible_host: 10.0.0.11
                nginx_port: 80
              web2.example.com:
                ansible_host: 10.0.0.12
          databases:
            hosts:
              db1.example.com:
                ansible_host: 10.0.0.21
                pg_version: 15
        vars:
          environment: production
          ansible_user: ubuntu
          ansible_ssh_private_key_file: ~/.ssh/prod_key

Dynamic Inventory:
  For cloud environments where hosts change.
  Plugin queries AWS/GCP/Azure API to build inventory dynamically.
  
  # inventory/aws_ec2.yaml (AWS plugin):
  plugin: amazon.aws.aws_ec2
  regions:
    - us-east-1
  filters:
    tag:Environment: production
  keyed_groups:
    - key: tags.Role
      prefix: role_
  compose:
    ansible_host: public_ip_address
  
  # Run:
  ansible-inventory -i aws_ec2.yaml --list
  ansible-playbook -i aws_ec2.yaml playbook.yml

Host Variables (host_vars/group_vars directories):
  
  # group_vars/webservers.yaml:
  nginx_version: "1.24"
  max_connections: 1000
  ssl_cert: "/etc/ssl/certs/web.crt"
  
  # host_vars/web1.example.com.yaml:
  ansible_host: 10.0.0.11
  primary: true

3. PLAYBOOKS
================================================================================

Playbook Structure:
  
  ---
  # site.yaml — main playbook
  
  - name: Configure web servers
    hosts: webservers          # Target hosts or group
    become: true               # Use privilege escalation (sudo)
    become_user: root
    gather_facts: true         # Collect system facts (default: true)
    serial: 1                  # Only 1 host at a time (rolling update)
    
    vars:
      nginx_port: 80
    
    pre_tasks:
    - name: Update apt cache
      apt:
        update_cache: yes
        cache_valid_time: 3600
    
    roles:
    - role: nginx
    - role: app
      vars:
        app_port: 8080
    
    tasks:
    - name: Ensure nginx is started
      service:
        name: nginx
        state: started
        enabled: true
    
    post_tasks:
    - name: Verify nginx is responding
      uri:
        url: "http://localhost:{{ nginx_port }}"
        return_content: yes
      register: webpage
    - name: Fail if nginx not responding
      fail:
        msg: "nginx not serving traffic"
      when: webpage.status != 200
    
    handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted

Running Playbooks:
  ansible-playbook site.yaml                               # Run on all hosts
  ansible-playbook site.yaml -i inventory/hosts.yaml       # Custom inventory
  ansible-playbook site.yaml --limit webservers            # Specific group
  ansible-playbook site.yaml --limit web1.example.com      # Specific host
  ansible-playbook site.yaml --tags "deploy,restart"       # Only tagged tasks
  ansible-playbook site.yaml --skip-tags "install"         # Skip tagged tasks
  ansible-playbook site.yaml --check                       # Dry run
  ansible-playbook site.yaml --diff                        # Show file changes
  ansible-playbook site.yaml --check --diff                # Both
  ansible-playbook site.yaml -e "version=2.0"             # Extra variables
  ansible-playbook site.yaml -v / -vv / -vvv              # Verbose output

4. TASKS AND MODULES
================================================================================

Task Structure:
  
  - name: Human-readable task description   # Required (best practice)
    module_name:                             # Module to use
      parameter1: value1
      parameter2: value2
    register: variable_name                  # Save output to variable
    when: condition                          # Conditional execution
    loop: "{{ list }}"                       # Loop over items
    notify: handler_name                     # Trigger handler on change
    tags: [install, packages]               # Tag for selective execution
    become: true                             # Override play-level become
    ignore_errors: true                     # Continue even if task fails

Common Core Modules:
  
  # Package management:
  - name: Install nginx
    apt:                        # or: yum, dnf, package (universal)
      name: nginx
      state: present            # present, absent, latest
      update_cache: yes
  
  - name: Install multiple packages
    apt:
      name:
      - nginx
      - python3
      - python3-pip
      state: present
  
  # File operations:
  - name: Create directory
    file:
      path: /etc/myapp
      state: directory           # directory, file, absent, link, touch
      mode: "0755"
      owner: www-data
      group: www-data
  
  - name: Copy file
    copy:
      src: files/nginx.conf      # Local path (relative to playbook)
      dest: /etc/nginx/nginx.conf
      owner: root
      group: root
      mode: "0644"
      backup: yes
    notify: restart nginx
  
  - name: Template file
    template:
      src: nginx.conf.j2          # Jinja2 template
      dest: /etc/nginx/nginx.conf
      mode: "0644"
    notify: restart nginx
  
  - name: Ensure line in file
    lineinfile:
      path: /etc/sysctl.conf
      line: "net.ipv4.ip_forward = 1"
      state: present
  
  # Service management:
  - name: Enable and start nginx
    service:
      name: nginx
      state: started             # started, stopped, restarted, reloaded
      enabled: yes               # Start on boot
  
  # User/group management:
  - name: Create user
    user:
      name: appuser
      shell: /bin/bash
      groups: sudo
      append: yes
      create_home: yes
  
  # Shell commands (use sparingly — not idempotent):
  - name: Run migration
    command: /app/manage.py migrate
    args:
      chdir: /app
    changed_when: false         # Mark as not changed (doesn't affect idempotency)
  
  - name: Run shell command
    shell: "echo 'hello' | grep hello"
    register: result
    failed_when: result.rc != 0
  
  # Git:
  - name: Clone repository
    git:
      repo: https://github.com/example/myapp.git
      dest: /opt/myapp
      version: main
  
  # System facts:
  - name: Print OS family
    debug:
      msg: "OS is {{ ansible_os_family }}"   # facts from gather_facts
  
  # Pause / wait:
  - name: Wait for port 8080
    wait_for:
      port: 8080
      host: localhost
      delay: 5
      timeout: 60
  
  # HTTP requests:
  - name: Download file
    get_url:
      url: https://releases.example.com/app-1.0.tar.gz
      dest: /tmp/app-1.0.tar.gz
      checksum: sha256:abc123...

Register and Debug:
  
  - name: Get current date
    command: date
    register: current_date
  
  - name: Print date
    debug:
      msg: "Date is: {{ current_date.stdout }}"
  
  - name: Check service status
    command: systemctl is-active nginx
    register: nginx_status
    failed_when: false    # Don't fail if nginx is not active
  
  - name: Start nginx if not running
    service:
      name: nginx
      state: started
    when: nginx_status.rc != 0

5. VARIABLES
================================================================================

Variable Precedence (highest to lowest):
  1. Extra vars (-e on command line) ← HIGHEST
  2. task vars (within task)
  3. block vars
  4. role vars (vars/main.yaml in role)
  5. play vars (vars: in play)
  6. host_vars/hostname.yaml
  7. group_vars/groupname.yaml
  8. inventory vars
  9. role defaults (defaults/main.yaml in role) ← LOWEST

Variable Usage:
  
  # String:
  app_name: "my-application"
  
  # Number:
  app_port: 8080
  
  # Boolean:
  enable_ssl: true
  
  # List:
  packages:
    - nginx
    - python3
    - vim
  
  # Dict/Map:
  app_config:
    host: localhost
    port: 5432
    name: mydb
  
  # In tasks:
  - debug:
      msg: "App: {{ app_name }}, port: {{ app_port }}"
  
  # Access dict:
  - debug:
      msg: "DB host: {{ app_config.host }}"
      # OR:
      msg: "DB host: {{ app_config['host'] }}"
  
  # Default filter (if undefined):
  - debug:
      msg: "{{ some_var | default('fallback') }}"

Facts (Auto-collected Variables):
  Ansible collects system facts via setup module.
  
  ansible_os_family           # RedHat, Debian, Windows, Darwin...
  ansible_distribution        # Ubuntu, CentOS, Amazon...
  ansible_distribution_version  # 22.04, 8.5...
  ansible_hostname
  ansible_default_ipv4.address
  ansible_architecture        # x86_64, aarch64...
  ansible_processor_cores
  ansible_memtotal_mb
  
  # Conditional on OS:
  - name: Install nginx on Ubuntu
    apt:
      name: nginx
      state: present
    when: ansible_os_family == "Debian"
  
  - name: Install nginx on CentOS
    yum:
      name: nginx
      state: present
    when: ansible_os_family == "RedHat"

6. ROLES
================================================================================

What are Roles?
  A structured way to organize related tasks, variables, templates, and files.
  Reusable, shareable, composable.
  
  Standard directory structure:
  
  roles/
  └── nginx/
      ├── tasks/
      │   └── main.yaml        # Main tasks file
      ├── handlers/
      │   └── main.yaml        # Handlers
      ├── templates/
      │   └── nginx.conf.j2    # Jinja2 templates
      ├── files/
      │   └── ssl.crt          # Static files
      ├── vars/
      │   └── main.yaml        # Role-specific vars (high priority)
      ├── defaults/
      │   └── main.yaml        # Default values (lowest priority)
      ├── meta/
      │   └── main.yaml        # Role metadata, dependencies
      └── README.md

Role Example — nginx role:
  
  # roles/nginx/defaults/main.yaml:
  nginx_port: 80
  nginx_user: www-data
  nginx_worker_processes: auto
  
  # roles/nginx/tasks/main.yaml:
  ---
  - name: Install nginx
    package:
      name: nginx
      state: present
  
  - name: Create nginx config directory
    file:
      path: /etc/nginx/conf.d
      state: directory
      mode: "0755"
  
  - name: Configure nginx
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: restart nginx
  
  - name: Start and enable nginx
    service:
      name: nginx
      state: started
      enabled: yes
  
  # roles/nginx/handlers/main.yaml:
  ---
  - name: restart nginx
    service:
      name: nginx
      state: restarted
  
  - name: reload nginx
    service:
      name: nginx
      state: reloaded

Using Roles in Playbook:
  
  - name: Configure web servers
    hosts: webservers
    become: true
    roles:
    - role: common           # Apply to all servers
    - role: nginx            # Web server role
      vars:
        nginx_port: 443      # Override defaults
    - role: ssl-certs
      when: enable_ssl | default(true)

Role Dependencies (meta/main.yaml):
  
  dependencies:
  - role: common
  - role: firewall
    vars:
      allowed_ports: [80, 443]

Ansible Galaxy (Community Roles):
  Ansible Galaxy is the hub for community roles (like Docker Hub for images).
  
  # Install a role:
  ansible-galaxy role install geerlingguy.nginx
  ansible-galaxy install -r requirements.yaml
  
  # requirements.yaml:
  roles:
  - name: geerlingguy.docker
    version: 6.1.0
  - name: geerlingguy.nodejs
    version: 6.2.0
  
  collections:
  - name: community.docker
    version: 3.4.0
  - name: amazon.aws
    version: 6.3.0

7. TEMPLATES (JINJA2)
================================================================================

Jinja2 Templates:
  Text files with {{ variable }} substitution and control flow.
  Used with template: module.
  
  # templates/nginx.conf.j2:
  
  user {{ nginx_user }};
  worker_processes {{ nginx_worker_processes }};
  
  events {
      worker_connections 1024;
  }
  
  http {
      server {
          listen {{ nginx_port }};
          server_name {{ inventory_hostname }};
          
          {% if enable_ssl %}
          ssl_certificate     {{ ssl_cert_path }};
          ssl_certificate_key {{ ssl_key_path }};
          {% endif %}
          
          location / {
              {% for backend in app_backends %}
              proxy_pass http://{{ backend }}:{{ app_port }};
              {% endfor %}
          }
      }
  }

Common Jinja2 Filters:
  {{ var | upper }}           Convert to uppercase
  {{ var | lower }}           Convert to lowercase
  {{ var | default('x') }}    Default if undefined
  {{ var | int }}             Convert to integer
  {{ var | string }}          Convert to string
  {{ list | join(', ') }}     Join list elements
  {{ var | replace('a','b')}} Replace string
  {{ var | length }}          Length
  {{ var | regex_replace(regex, replacement) }}
  {{ var | to_yaml }}         Format as YAML
  {{ var | to_json }}         Format as JSON
  {{ var | b64encode }}       Base64 encode
  {{ var | b64decode }}       Base64 decode

8. HANDLERS
================================================================================

Handlers run ONLY when notified, ONCE at the END of a play.
  
  # In task:
  - name: Update nginx config
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: restart nginx    # Triggers handler IF this task changed
  
  # Handler:
  handlers:
  - name: restart nginx
    service:
      name: nginx
      state: restarted
  
  # Multiple notifications of same handler = ONE handler execution
  # Handler runs at end of play, not immediately

Force Handler Run:
  - meta: flush_handlers    # Run pending handlers NOW (before end of play)

Listen / Multi-handler:
  - name: restart web stack
    service:
      name: nginx
      state: restarted
    listen: "web stack changed"   # Multiple tasks can notify same topic
  
  - name: restart app
    service:
      name: myapp
      state: restarted
    listen: "web stack changed"
  
  # Task notifies the topic:
  - name: Update app config
    template:
      src: app.conf.j2
      dest: /etc/myapp/app.conf
    notify: "web stack changed"   # Both handlers run

9. ANSIBLE VAULT (SECRETS)
================================================================================

Ansible Vault encrypts sensitive data (passwords, API keys, private keys).
  
  # Encrypt a file:
  ansible-vault encrypt vars/secrets.yaml
  
  # Create a new encrypted file:
  ansible-vault create vars/secrets.yaml
  
  # Edit encrypted file:
  ansible-vault edit vars/secrets.yaml
  
  # View encrypted file:
  ansible-vault view vars/secrets.yaml
  
  # Decrypt file:
  ansible-vault decrypt vars/secrets.yaml
  
  # Re-key (change vault password):
  ansible-vault rekey vars/secrets.yaml
  
  # Encrypt a string (for inline use):
  ansible-vault encrypt_string 'super-secret-password' --name 'db_password'
  
  # Output:
  # db_password: !vault |
  #   $ANSIBLE_VAULT;1.1;AES256
  #   66386439...

Using Vault in Playbooks:
  
  # Run playbook with vault password:
  ansible-playbook site.yaml --ask-vault-pass     # Prompt for password
  ansible-playbook site.yaml --vault-password-file ~/.vault_pass  # File
  
  # In CI/CD, use environment variable:
  echo "$VAULT_PASSWORD" > /tmp/vault_pass
  ansible-playbook site.yaml --vault-password-file /tmp/vault_pass
  rm -f /tmp/vault_pass

Encrypted vars/secrets.yaml:
  
  # Before encryption (YAML content):
  db_password: "super-secret-db-password"
  api_key: "abc123-secret-api-key"
  ssl_private_key: |
    -----BEGIN PRIVATE KEY-----
    ...
  
  # After ansible-vault encrypt:
  $ANSIBLE_VAULT;1.1;AES256
  66386439653736353537353538343763...

10. COMMON PATTERNS
================================================================================

Rolling Updates (serial):
  
  - name: Rolling update web servers
    hosts: webservers
    serial: 1             # Update 1 server at a time
    # OR:
    serial: "25%"         # 25% at a time (1 of 4 servers)
    # OR:
    serial: [1, 2, 5]     # First 1, then 2, then 5 at a time
    
    tasks:
    - name: Remove from load balancer
      # ...
    - name: Deploy new code
      # ...
    - name: Run smoke test
      # ...
    - name: Add back to load balancer
      # ...

Conditional Tasks:
  
  - name: Install docker on Ubuntu
    apt:
      name: docker.io
      state: present
    when: ansible_os_family == "Debian"
  
  - name: Start service only if feature enabled
    service:
      name: myfeature
      state: started
    when: enable_myfeature | bool
  
  # Combine conditions:
  when:
    - ansible_os_family == "RedHat"
    - ansible_distribution_major_version | int >= 8

Loops:
  
  # Simple loop:
  - name: Create users
    user:
      name: "{{ item }}"
      state: present
    loop:
      - alice
      - bob
      - charlie
  
  # Loop over list of dicts:
  - name: Create users with options
    user:
      name: "{{ item.name }}"
      groups: "{{ item.groups }}"
    loop:
      - { name: alice, groups: [developers, sudo] }
      - { name: bob, groups: [developers] }
  
  # Loop with index:
  - debug:
      msg: "{{ index }}: {{ item }}"
    loop: [a, b, c]
    loop_control:
      index_var: index

Block Groups:
  Group tasks, apply when/rescue/always to all:
  
  - block:
      - name: Install app
        apt:
          name: myapp
          state: present
      - name: Start app
        service:
          name: myapp
          state: started
    rescue:
      - name: Log failure
        debug:
          msg: "App installation failed"
    always:
      - name: Send notification
        # ...
    when: install_app | bool

Tags:
  
  - name: Install packages
    apt:
      name: nginx
      state: present
    tags: [install, packages]
  
  - name: Configure nginx
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    tags: [configure]
  
  - name: Restart service
    service:
      name: nginx
      state: restarted
    tags: [restart, configure]
  
  # Run only specific tags:
  ansible-playbook site.yaml --tags install
  ansible-playbook site.yaml --skip-tags restart

11. ANSIBLE IN CI/CD
================================================================================

Typical CI/CD Usage:
  
  # GitHub Actions step:
  - name: Run Ansible playbook
    uses: dawidd6/action-ansible-playbook@v2
    with:
      playbook: playbooks/deploy.yaml
      inventory: inventories/production/hosts.yaml
      options: |
        --extra-vars "version=${{ github.sha }}"
        --limit webservers
        --tags deploy
  
  # Or with direct ansible-playbook:
  - name: Deploy with Ansible
    env:
      ANSIBLE_HOST_KEY_CHECKING: "False"
      VAULT_PASSWORD: ${{ secrets.VAULT_PASSWORD }}
    run: |
      echo "$VAULT_PASSWORD" > /tmp/vault-pass
      ansible-playbook \
        -i inventories/production/hosts.yaml \
        playbooks/deploy.yaml \
        --vault-password-file /tmp/vault-pass \
        --extra-vars "version=${{ github.sha }}" \
        --limit webservers
      rm -f /tmp/vault-pass

Configuration:
  
  # ansible.cfg:
  [defaults]
  inventory     = inventories/
  remote_user   = ubuntu
  private_key_file = ~/.ssh/id_rsa
  host_key_checking = False
  stdout_callback = yaml
  callbacks_enabled = profile_tasks
  
  [privilege_escalation]
  become        = True
  become_method = sudo
  become_user   = root

12. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Ansible and how does it differ from Terraform?
A: Ansible is a configuration management and automation tool. It's agentless
   (uses SSH), YAML-based, and excels at configuring existing systems.
   
   Key differences from Terraform:
   
   Purpose:
   Terraform: Provision infrastructure (create EC2, VPC, RDS, K8s clusters)
   Ansible: Configure servers (install nginx, deploy app, manage users)
   
   State:
   Terraform: Stateful (tracks state in .tfstate file)
   Ansible: Stateless (checks current state each run, no state file)
   
   Approach:
   Terraform: Declarative (describe final state)
   Ansible: Hybrid (modules are declarative, but tasks are procedural)
   
   Idempotency:
   Terraform: Natively idempotent (plan = diff)
   Ansible: Mostly idempotent (depends on module; shell/command are not)
   
   Use case today:
   With Docker/K8s, Ansible's role in server config has shrunk.
   Modern flow: Terraform provisions cloud resources + K8s cluster.
   Docker images replace Ansible for app config (baked in at build time).
   Ansible still useful for: OS hardening, non-containerized apps, migrations.

Q2: What is an Ansible role and why would you use one?
A: A role is a structured way to organize Ansible tasks, variables, templates,
   and files into a reusable package.
   
   Role directory structure:
   roles/nginx/
     tasks/main.yaml       Main tasks
     handlers/main.yaml    Service restart handlers
     templates/*.j2        Jinja2 config templates
     files/                Static files to copy
     defaults/main.yaml    Default variables (lowest priority)
     vars/main.yaml        Role variables (high priority)
     meta/main.yaml        Dependencies on other roles
   
   Why use roles:
   1. Reusability: nginx role used in web-dev, web-staging, web-prod playbooks
   2. Abstraction: Playbook says "apply nginx role" not 20 tasks
   3. Modularity: Test and maintain roles independently
   4. Sharing: Publish to Ansible Galaxy for community use
   5. Convention: Standardized structure = everyone knows where to look
   
   vs. raw tasks in playbook: Tasks in a playbook become long, unmanageable.
   Roles separate concerns — same as microservices vs. monolith.
   
   Industry pattern: Use community Galaxy roles for common services
   (geerlingguy.docker, geerlingguy.nginx) rather than writing from scratch.

Q3: How do handlers work in Ansible and when would you use one?
A: Handlers are tasks that run at the END of a play, ONLY when notified,
   and ONLY ONCE regardless of how many tasks notify them.
   
   Example without handlers (wrong):
   - name: Update config
     template: src=nginx.j2 dest=/etc/nginx/nginx.conf
   - name: Restart nginx immediately
     service: name=nginx state=restarted  ← ALWAYS restarts, even if no change
   
   With handlers (correct):
   Task:
   - name: Update config
     template: src=nginx.j2 dest=/etc/nginx/nginx.conf
     notify: restart nginx    ← notify ONLY if task changed the file
   
   Handler:
   - name: restart nginx
     service: name=nginx state=restarted
   
   Benefits:
   1. Idempotency: Only restarts if config actually changed
   2. De-duplication: 5 tasks notify "restart nginx" → ONE restart at end
      (not 5 restarts mid-play causing unnecessary downtime)
   3. Ordering: Handler runs after all tasks complete (not mid-play)
   
   Use cases: restart services (nginx, postgresql, sshd), reload configs,
   clear caches, trigger alerts after state changes.

Q4: How do you manage secrets in Ansible?
A: Ansible Vault is the built-in solution for encrypting sensitive data.
   
   What Vault does: Encrypts files using AES256 with a password.
   The encrypted content is safe to commit to Git.
   
   Usage patterns:
   
   1. Encrypt an entire file (group_vars/all/vault.yaml):
      ansible-vault encrypt vault.yaml
      Contents look like: $ANSIBLE_VAULT;1.1;AES256\n66386...
   
   2. Encrypt individual strings (inline in vars):
      ansible-vault encrypt_string 'my-password' --name 'db_password'
      Result in vars file: db_password: !vault | $ANSIBLE_VAULT;...
   
   3. Reference in tasks:
      - name: Set DB password
        command: "mysql -e \"ALTER USER root IDENTIFIED BY '{{ db_password }}';\""
   
   4. Provide vault password at runtime:
      ansible-playbook site.yaml --ask-vault-pass         # Interactive
      ansible-playbook site.yaml --vault-password-file ~/.vault_pass  # File
      In CI: echo "$VAULT_PASS" > /tmp/vp && ansible-playbook ... --vault-password-file /tmp/vp
   
   Best practices:
   - Keep vault.yaml separate from regular vars (easier to manage)
   - One vault password per environment (dev vault ≠ prod vault)
   - Rotate vault password periodically
   - Consider using Vault (HashiCorp) for enterprise-grade secret management
     with Ansible integration via the community.hashi_vault collection

Q5: What is the difference between vars and defaults in an Ansible role?
A: Both define variables for a role, but at different precedence levels:
   
   defaults/main.yaml (LOWEST priority):
   - Intended to be overridden by users of the role
   - "Sensible defaults" that work out of the box
   - Users can override via group_vars, host_vars, or playbook vars
   
   Example: nginx_port: 80 (most people use 80; override to 443 if needed)
   
   vars/main.yaml (HIGH priority):
   - "Internal" role variables
   - Hard to override (only extra_vars can beat them)
   - Used for role-internal constants or computed values
   - Users are NOT expected to override these
   
   Example: Internal paths, computed values that should be consistent
   
   Precedence order (simplified):
   extra_vars (-e) > vars/main.yaml > host_vars > group_vars > defaults/main.yaml
   
   Practical rule:
   - Everything you WANT users to customize → defaults/main.yaml
   - Implementation details users should NOT change → vars/main.yaml
   - Most things should be in defaults (more flexible roles)
