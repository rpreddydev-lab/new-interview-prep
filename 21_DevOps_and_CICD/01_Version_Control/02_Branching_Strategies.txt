1. WHY BRANCHING STRATEGIES MATTER
================================================================================

A branching strategy defines:
  - How developers create and name branches
  - When and how branches are merged
  - Which branches are "protected" and what approvals they need
  - How releases are managed
  - How hotfixes are handled

Without a strategy:
  - Merge conflicts become a daily nightmare
  - "Integration hell" — large batches of code that don't integrate
  - Unclear what's in production vs staging vs development
  - Risk of deploying unreviewed or untested code
  - Difficulty rolling back specific features

With a strategy:
  - Everyone follows the same rules
  - Code reviews happen systematically
  - CI/CD pipelines know what to do with each branch
  - Releases are predictable and auditable

Branching strategy is tightly coupled to:
  - Team size (1 person vs 500 engineers)
  - Release cadence (daily vs quarterly)
  - Number of supported versions (1 vs many)
  - Deployment model (SaaS vs on-premise)

2. BRANCH TYPES
================================================================================

MAIN / MASTER (Protected, Always Deployable):
  - Represents production-ready code
  - NEVER commit directly to this branch
  - Only merged to via PRs with required approvals
  - Always in a deployable state (passing tests)
  - Renamed from "master" to "main" in recent years (default on GitHub)

DEVELOP / INTEGRATION (Protected, Integration Target):
  - Used in Git Flow as the integration branch
  - Feature branches merge here first
  - Should always have passing tests
  - More lenient than main but still protected

FEATURE BRANCHES (Short-lived, Per Feature):
  - Created from main or develop
  - Naming: feature/JIRA-123-user-authentication
  - Lives only until feature is merged
  - Ideally merged within 1-3 days (avoid long-lived branches)
  - One developer (or pair) per feature branch

RELEASE BRANCHES (For Release Preparation):
  - Cut from develop when ready for release
  - Only bug fixes, no new features
  - Naming: release/v2.1.0
  - Merged to both main AND develop after release

HOTFIX BRANCHES (Emergency Production Fixes):
  - Cut from main/master (not develop)
  - For critical production bugs that can't wait for normal release
  - Naming: hotfix/critical-payment-bug
  - Merged to both main AND develop after fix

SUPPORT BRANCHES:
  - For maintaining older versions in parallel
  - Example: support/v1.x while main is v2.x
  - Used when multiple versions are in production simultaneously

4. FEATURE BRANCH WORKFLOW
================================================================================

Structure:
  main (protected)
    └── feature/add-login
    └── feature/payment-integration
    └── bugfix/fix-typo

Process:
  1. Create feature branch from main
  2. Develop on feature branch
  3. Open Pull Request → code review
  4. CI pipeline runs on PR
  5. Approved PR merged to main
  6. Deploy main to production

Diagram:
  main:    A ─────────────────── M1 ── M2
                                /       \
  feature-1: B ── C ── D ──────         \
                                         \
  feature-2:     E ── F ── G ─────────────

Pros:
  + Simple to understand
  + Good isolation of work
  + Code review before merge
  + CI/CD on each PR

Cons:
  - Long-lived branches → integration problems
  - No explicit release management
  - Feature branches can diverge significantly from main

Best Practices:
  - Keep branches short-lived (< 1-3 days)
  - Rebase onto main regularly to stay current
  - Small PRs — easier to review and less conflict risk
  - Branch naming convention: feature/<ticket>-<description>

5. GIT FLOW
================================================================================

Created by: Vincent Driessen (2010)
Best for: Projects with scheduled releases, version-based software, libraries

Branches:
  - main: Production code only, tagged with version numbers
  - develop: Integration branch for features
  - feature/*: New features (branch from develop, merge back to develop)
  - release/*: Release preparation (branch from develop, merge to main+develop)
  - hotfix/*: Emergency fixes (branch from main, merge to main+develop)

Full Git Flow Process:

  FEATURE DEVELOPMENT:
    git checkout develop
    git checkout -b feature/JIRA-123-new-login
    # ... code, commit ...
    git checkout develop
    git merge --no-ff feature/JIRA-123-new-login
    git branch -d feature/JIRA-123-new-login

  RELEASE PREPARATION:
    git checkout develop
    git checkout -b release/v2.1.0
    # Bug fixes, version bumps only (no new features)
    git checkout main
    git merge --no-ff release/v2.1.0
    git tag -a v2.1.0 -m "Release v2.1.0"
    git checkout develop
    git merge --no-ff release/v2.1.0
    git branch -d release/v2.1.0

  HOTFIX:
    git checkout main
    git checkout -b hotfix/payment-critical-bug
    # Fix bug
    git checkout main
    git merge --no-ff hotfix/payment-critical-bug
    git tag -a v2.0.1 -m "Hotfix v2.0.1"
    git checkout develop
    git merge --no-ff hotfix/payment-critical-bug
    git branch -d hotfix/payment-critical-bug

Diagram:
  main:        M1 ──────────────────────────── M2 ─── M3 (hotfix)
                \                             /         \
  develop:       D1 ─── D2 ─── D3 ─────── D4 ─────── D5
                         /  \              /  \
  feature:        F1───F2    \           F3───F4
                              \
  release:                     R1────R2 (bug fixes only)

Pros:
  + Clear, well-defined process
  + Good for teams with multiple concurrent features
  + Supports multiple versions in parallel
  + Release branch allows final QA without blocking development

Cons:
  - Very complex (5 branch types)
  - Two "long-lived" branches (main + develop) cause merge overhead
  - Not ideal for continuous deployment
  - Merging to both main AND develop is error-prone
  - Overkill for most web applications

When to Use Git Flow:
  - Mobile apps, SDKs, libraries (versioned releases)
  - Enterprise software with formal release windows
  - Projects maintaining multiple versions simultaneously
  - Teams with formal QA cycles before release

6. GITHUB FLOW
================================================================================

Created by: GitHub (2011)
Best for: SaaS, web apps with continuous deployment, simple workflows

Branches:
  - main: Always deployable, reflects production
  - feature/* or anything: Feature branches created from main

Process:
  1. Create branch from main
  2. Add commits
  3. Open Pull Request (this triggers discussion and CI)
  4. Review, discuss, and approve
  5. Deploy the PR branch to staging (optional)
  6. Merge to main → auto-deploys to production

Diagram:
  main: A ──── B ────────── C ──── D
               \           /       \
  feature:      X ── Y ── Z         \
                                     \
  hotfix:                             H ── (merged back to main)

Pros:
  + Simple (only one long-lived branch: main)
  + Continuous deployment friendly
  + Short-lived branches
  + Clear: main = production

Cons:
  - No dedicated develop/staging branch
  - Less structured release management
  - Not ideal for versioned software

When to Use GitHub Flow:
  - Web services deploying multiple times per day
  - SaaS products with no versioned releases
  - Small to medium teams

7. GITLAB FLOW
================================================================================

Created by: GitLab (2014)
Best for: Teams that deploy to multiple environments or maintain releases

GitLab Flow adds environment branches to GitHub Flow:

Environment Branch Variant:
  main (development code)
    └── staging (deployed to staging)
          └── production (deployed to production)

  Flow: PR to main → CI passes → merge to staging manually → verify → merge to production

Release Branch Variant:
  main (ongoing development)
    └── release-1.0
    └── release-1.1
    └── release-2.0

Upstream First Principle:
  Fixes MUST be merged to main FIRST, then cherry-picked to release/env branches.
  This prevents regression where a fix is in production but not in the next release.

Diagram (Environment Branches):
  main:       A ── B ── C ── D ── E
              |         |         |
  staging:    A ─────── C ──────── E
                        |
  production:           C

Pros:
  + Good balance between simplicity and structure
  + Works well with GitLab's CI/CD environments
  + Upstream-first prevents missed fixes
  + Better than GitHub Flow for complex deployment targets

Cons:
  - More complexity than GitHub Flow
  - Cherry-picking can be error-prone

When to Use GitLab Flow:
  - Teams using GitLab with multiple deployment environments
  - Projects needing both feature branches AND environment tracking
  - Teams needing release branches without full Git Flow complexity

8. TRUNK-BASED DEVELOPMENT (TBD)
================================================================================

Core Principle: All developers commit directly to "trunk" (main/master) at
least once per day. Feature branches are short-lived (< 1-2 days) or
non-existent.

Types of TBD:

  1. PURE TRUNK-BASED (High-trust, small teams):
     - Everyone commits directly to main
     - No feature branches
     - Feature flags hide incomplete work
     - Requires strong test culture
     
  2. SHORT-LIVED FEATURE BRANCHES (Most common version):
     - Branch from main
     - Commit must merge within 1-2 days
     - Small, focused changes
     - At least daily rebase onto main

Diagram (Pure TBD):
  trunk (main): A ── B ── C ── D ── E ── F ── G ── H
                (every engineer commits here directly)

Diagram (Short-lived branches):
  main:    A ───────────── B ─────────── C
                          /               \
  alice:        a1 ── a2 ─                \
                                b1 ── b2 ──
  bob:

Feature Flags (critical for TBD):
  - Incomplete features committed but hidden behind feature flags
  - Flag disabled in production → feature not visible
  - Code review happens on small increments
  - Team can deploy at any time regardless of feature completeness
  
  Example:
  if (featureFlags.isEnabled("new-checkout")) {
    return newCheckoutFlow();
  } else {
    return legacyCheckoutFlow();
  }

Branch by Abstraction (alternative to long feature branches):
  1. Create abstraction layer over the existing code
  2. Gradually implement new code behind the abstraction
  3. Once complete, switch to new implementation
  4. Remove old implementation and abstraction layer
  
  All changes happen in small commits to trunk — no long-lived branch needed.

Pros of TBD:
  + Maximum CI/CD velocity (no merge queue, no integration hell)
  + No long-lived branches → no merge conflicts
  + Forces small, incremental changes
  + Supports continuous deployment naturally
  + What FAANG companies use (Google, Facebook/Meta, Netflix)

Cons of TBD:
  - Requires mature test culture and CI infrastructure
  - Feature flags add complexity
  - Harder to audit "what was in release X"
  - Requires high developer discipline
  - Not suitable for teams with low test coverage

DORA Research Finding:
  "Trunk-based development is a key predictor of continuous delivery capability
   and high performance." — DORA State of DevOps Report
  
  Elite performers use trunk-based development with short-lived branches.

9. RELEASE BRANCHING
================================================================================

When You Need Multiple Supported Versions:
  - Enterprise software: v1.x and v2.x both in production for different customers
  - Mobile SDK: Old apps use SDK 1.x, new apps use SDK 2.x
  - Operating systems: Ubuntu 20.04 LTS and Ubuntu 22.04 LTS

Release Branch Model:
  main (v3.0 development)
  release/v2.1 (fixes only, backported from main)
  release/v1.5 (critical security fixes only)

Backporting:
  A fix applied to main that also needs to be applied to older release branches.
  
  Process:
  1. Fix is merged to main (upstream first)
  2. Cherry-pick the fix commit to release/v2.1
  3. Cherry-pick to release/v1.5 if critical enough

Release Cadence and Semantic Versioning:
  MAJOR.MINOR.PATCH (e.g., 2.3.1)
  
  MAJOR: Breaking changes (API incompatible)
  MINOR: New features, backward compatible
  PATCH: Bug fixes, backward compatible
  
  Examples:
    v2.3.1 → v2.3.2  (patch: bug fix)
    v2.3.2 → v2.4.0  (minor: new feature)
    v2.4.0 → v3.0.0  (major: breaking change)
  
  Pre-release: v3.0.0-alpha.1, v3.0.0-beta.2, v3.0.0-rc.1

10. COMPARING STRATEGIES
================================================================================

Summary Table:

Strategy         | Branches  | Release  | CI/CD  | Team Size | Complexity
-----------------|-----------|----------|--------|-----------|----------
Feature Branch   | Many      | Manual   | Good   | Any       | Low
Git Flow         | Many      | Formal   | OK     | Medium+   | High
GitHub Flow      | Few       | Always   | Excel  | Any       | Low
GitLab Flow      | Medium    | Env-based| Good   | Medium    | Medium
Trunk-Based Dev  | Few/None  | Cont.    | Excel  | Any       | Medium

Release Model Comparison:
  Git Flow:     Explicit release branches, versioned releases
  GitHub Flow:  main is always production, no explicit releases
  GitLab Flow:  Environment branches represent deployment targets
  TBD:          Feature flags manage what's visible, continuous release

Decision Framework:
  Q: Do you deploy multiple times per day?
    YES → GitHub Flow or Trunk-Based Development
    NO  → Continue...
  
  Q: Do you support multiple production versions?
    YES → Git Flow with release branches
    NO  → Continue...
  
  Q: Do you have formal QA/release cycles?
    YES → Git Flow
    NO  → GitHub Flow or TBD
  
  Q: Are you a mobile/SDK/library developer?
    YES → Git Flow
    NO  → GitHub Flow or TBD

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What branching strategy would you recommend and why?
A: It depends on the team's release cadence and deployment model. For most
   modern SaaS web applications deploying frequently, I'd recommend either
   GitHub Flow (simple, main is always deployable, PR-based) or Trunk-Based
   Development with feature flags (maximum CI/CD velocity, no merge conflicts).
   
   For versioned software (SDKs, mobile apps, enterprise software) where you
   maintain multiple versions simultaneously, Git Flow makes more sense despite
   its complexity.
   
   I'd avoid Git Flow for web applications — it's over-engineered and slows
   down continuous delivery.

Q2: What is the problem with long-lived feature branches?
A: Long-lived branches (open for days or weeks) create several problems:
   1. Merge conflicts: The branch diverges significantly from main, making
      merging extremely painful ("integration hell")
   2. Delayed integration: Bugs in the feature are discovered late
   3. Large PRs: Hard to review thoroughly (reviewers just approve to unblock)
   4. Delayed feedback: CI feedback is late
   5. Feature isolation: The feature doesn't get tested alongside other features
   
   The solution: Keep branches short (1-3 days max), use feature flags for
   incomplete work, and merge partial implementations continuously.

Q3: What is trunk-based development and why do companies like Google use it?
A: Trunk-based development means all developers commit to a single main branch
   (the "trunk") at least daily, with feature branches lasting at most 1-2 days.
   
   Google uses it because it maximizes flow: no merge queue, no integration
   branches, no long-lived branches causing conflicts. DORA research shows TBD
   is a predictor of high-performing engineering teams.
   
   It requires: feature flags for incomplete work, strong test culture
   (automated tests on every commit), and high developer discipline.

Q4: How do you handle hotfixes in your branching strategy?
A: In GitHub Flow: Create a hotfix branch from main, push the fix, get emergency
   approval (maybe fewer reviewers for urgency), merge to main, deploy.
   
   In Git Flow: Create hotfix branch from main, fix, merge to BOTH main (with
   version tag) and develop (so the fix isn't lost in next release).
   
   Key principle: A hotfix should be minimal and surgical — only fix the critical
   issue, nothing else. Also backport to any affected release branches.

Q5: What is the difference between merge and squash merge for PRs?
A: 
   Regular merge (--no-ff): Creates a merge commit. All individual commits from
   the feature branch appear in main's history. Useful when commit history is
   meaningful (each commit is a logical unit).
   
   Squash merge: All commits from the feature branch are squashed into a single
   commit before merging. Cleaner main history (one commit = one feature).
   Useful when feature branch commits are messy ("WIP", "fix typo", "fix again").
   
   Rebase merge: Replays feature commits onto main (no merge commit, linear
   history, but preserves individual commits).
   
   I prefer squash merge for most teams — cleaner main branch history, easier
   to revert entire features with one commit revert.

12. QUICK REFERENCE CHEAT SHEET
================================================================================

Branching Strategies:
  Feature Branch: Simple. Branch per feature, PR to main.
  Git Flow: 5 branch types. Best for versioned software with release cycles.
  GitHub Flow: main + short feature branches. Best for SaaS/CD.
  GitLab Flow: Adds environment branches. Good middle ground.
  Trunk-Based Dev: All to main daily. Best for high-frequency deployment.

DORA Finding: Trunk-based development → high-performing teams

Branch Types:
  main: Always deployable, reflects production
  develop: Integration branch (Git Flow only)
  feature/*: New features, short-lived
  release/*: Release preparation (Git Flow)
  hotfix/*: Emergency production fixes

Git Flow Rule: Merge hotfix to BOTH main AND develop
TBD Rule: Feature branches < 1-2 days. Feature flags for incomplete work.

Semantic Versioning: MAJOR.MINOR.PATCH
  MAJOR: Breaking changes
  MINOR: New features, backward compatible
  PATCH: Bug fixes

Branch naming:
  feature/JIRA-123-add-user-auth
  fix/JIRA-456-login-timeout
  hotfix/critical-payment-bug
  release/v2.1.0

Merge types:
  Regular merge: Merge commit, full history
  Squash merge: One commit per PR, clean history
  Rebase merge: Linear history, no merge commit
