1. WHAT IS A PULL REQUEST?
================================================================================

Definition:
  A Pull Request (PR) — also called Merge Request (MR) in GitLab — is a
  mechanism to propose changes from one branch (or fork) to another.
  It initiates a formal code review process before merging.

Alternative Names:
  - GitHub, Bitbucket: "Pull Request" (PR)
  - GitLab: "Merge Request" (MR)
  - Azure DevOps: "Pull Request" (PR)
  - The concept is the same regardless of platform name

Purpose of a Pull Request:
  1. CODE REVIEW: Other engineers review changes before they merge
  2. DISCUSSION: Threaded comments for questions and suggestions
  3. CI/CD GATE: Automated tests, linters, security scans must pass
  4. DOCUMENTATION: PR description explains the "what" and "why"
  5. AUDIT TRAIL: Permanent record of what changed, who approved it, why
  6. KNOWLEDGE SHARING: Others learn from seeing code changes
  7. POLICY ENFORCEMENT: Required approvals, signed commits, etc.

PR vs Direct Push:
  Direct push to main (bad):
    - No code review
    - No automated testing gate
    - No record of approval
    - Compliance/audit failure in many organizations

  PR workflow (good):
    - Forces code review
    - Automated CI must pass before merge
    - Permanent record of reviewer approvals
    - Discussion preserved
    - Can be configured with required checks

2. THE CODE REVIEW PROCESS
================================================================================

Full PR Lifecycle:

  1. DEVELOPER CREATES BRANCH
     git checkout main && git pull
     git checkout -b feature/JIRA-123-user-profile-page
     
  2. DEVELOPMENT
     Developer writes code, commits frequently:
     git commit -m "feat(profile): add user profile data model"
     git commit -m "feat(profile): implement profile API endpoint"
     git commit -m "test(profile): add unit tests for profile service"
     
  3. PUSH AND OPEN PR
     git push -u origin feature/JIRA-123-user-profile-page
     # On GitHub: Compare & Pull Request button
     # Fills in PR template if one exists (.github/PULL_REQUEST_TEMPLATE.md)
     
  4. AUTOMATED CHECKS RUN IMMEDIATELY
     - CI pipeline: build, unit tests, integration tests
     - Linting and code style checks (ESLint, Checkstyle, Pylint)
     - Code coverage check
     - SAST (security scan)
     - Dependency vulnerability scan
     - PR size check (warn if > 400 changed lines)
     
  5. REVIEWER ASSIGNED
     - Author assigns reviewers manually
     - Or CODEOWNERS file auto-assigns based on changed files
     - Or round-robin assignment via tools (reviewers.yml, GitHub teams)
     
  6. CODE REVIEW (typically 1-2 business days)
     Reviewer reads the diff, comments, approves or requests changes
     
  7. AUTHOR ADDRESSES FEEDBACK
     Makes changes based on comments
     git commit -m "refactor: address code review feedback"
     git push (updates the PR automatically)
     
  8. RE-REVIEW (if needed)
     Reviewer checks that feedback was addressed
     
  9. APPROVAL
     Required number of approvals reached (typically 1-2)
     
  10. MERGE
      PR merged (squash, merge commit, or rebase)
      Branch deleted automatically (if configured)
      CI runs on main after merge

CODEOWNERS File:
  Automatically assigns reviewers based on which files are changed.
  
  Location: .github/CODEOWNERS (GitHub) or CODEOWNERS (root or /docs)
  
  Example:
  # Global owners
  *                          @global-reviewer
  
  # Frontend changes need frontend team
  /src/frontend/             @frontend-team
  
  # Payment code needs security + payments team
  /src/payment/              @payments-team @security-team
  
  # Infra changes need DevOps approval
  /infrastructure/           @devops-team
  /Dockerfile                @devops-team
  /.github/workflows/        @devops-team

3. WRITING A GOOD PR
================================================================================

PR Size (The #1 Factor):
  - Keep PRs small: target < 400 lines changed
  - Large PRs (> 1000 lines) are rarely reviewed thoroughly
  - "A 10-line PR gets 10 detailed comments. A 1000-line PR gets LGTM."

PR Title Format:
  Use Conventional Commits format:
  feat(auth): add OAuth2 Google login
  fix(payment): correct rounding in cart totals
  refactor(user): extract email validation logic
  
  Good titles:
  ✓ "feat(api): add pagination to /users endpoint"
  ✓ "fix(db): prevent N+1 query in order loading"
  
  Bad titles:
  ✗ "Changes"
  ✗ "WIP"
  ✗ "Fixing stuff"

PR Description Template:

  ## What does this PR do?
  Brief description of the change and its motivation.
  
  ## Why?
  Context: link to ticket, explain business reason.
  JIRA: https://company.atlassian.net/browse/JIRA-123
  
  ## How to Test
  Step-by-step instructions for reviewers to verify the change:
  1. Pull this branch
  2. Run `npm start`
  3. Navigate to /profile
  4. Verify user profile loads correctly
  
  ## Screenshots (if UI change)
  Before: [screenshot]
  After: [screenshot]
  
  ## Checklist
  - [ ] Unit tests written/updated
  - [ ] Integration tests pass
  - [ ] Documentation updated
  - [ ] No new secrets in code
  - [ ] Performance impact considered
  
  ## Breaking Changes
  None / [describe breaking changes and migration path]

GitHub PR Template (.github/PULL_REQUEST_TEMPLATE.md):
  Check in this file and GitHub auto-populates new PRs with it.

Draft PRs:
  Create a PR in "Draft" state to:
  - Get early feedback on approach before finishing
  - Share work-in-progress with teammates
  - Keep CI running while working
  - Notify team about work in progress
  
  GitHub: Open PR → "Create draft pull request"
  GitLab: WIP: prefix in title → Draft: prefix (newer)

4. REVIEWING CODE EFFECTIVELY
================================================================================

What to Look For in Code Review:

  A. CORRECTNESS
     - Does the code do what it's supposed to do?
     - Are edge cases handled? (null values, empty lists, boundary conditions)
     - Are errors handled gracefully?
     - Thread safety (for concurrent code)
     
  B. DESIGN
     - Does the code follow SOLID principles?
     - Is there unnecessary complexity?
     - Is it following the existing patterns in the codebase?
     - Are abstractions correct? Too many or too few?
     - Single responsibility principle violated?
     
  C. TESTS
     - Are there tests for the new/changed behavior?
     - Do tests cover happy path AND edge cases?
     - Are tests clear and readable?
     - Are there brittle tests (testing implementation, not behavior)?
     
  D. SECURITY
     - Any new attack surface?
     - SQL injection, XSS, CSRF vulnerabilities?
     - Authentication and authorization correct?
     - Secrets hardcoded? (should never be)
     - Input validation?
     
  E. PERFORMANCE
     - N+1 queries? (common in ORM code)
     - Expensive operations in loops?
     - Memory leaks?
     - Missing indexes for new DB queries?
     
  F. READABILITY
     - Variable and function names clear?
     - Comments explain "why", not "what"?
     - Complex logic documented?
     
  G. DOCUMENTATION
     - API docs updated?
     - README updated if necessary?
     - CHANGELOG updated?

Comment Types (Tone and Clarity):

  BLOCKING (must be addressed):
    "This will fail if user is null. We need to add a null check here:
     if (user == null) return ResponseEntity.notFound().build();"

  NON-BLOCKING (suggestion):
    "nit: Consider extracting this into a helper method for clarity. But LGTM
     either way — up to you!"

  QUESTION (genuine curiosity):
    "I'm not familiar with this pattern — can you explain why we use
     X instead of Y here? Want to learn!"

  PRAISE (important for culture):
    "Great abstraction here! Really clean solution."

Google Engineering Code Review Principles:
  - As a reviewer, approve the PR if it improves the codebase overall,
    even if it's not perfect
  - Don't let perfect be the enemy of good
  - Leave "nit:" prefix for stylistic suggestions (not blocking)
  - Respond to PRs within 1 business day

Code Review Etiquette:
  For Authors:
    - Respond to all comments (even if just "Done" or "ACK")
    - Explain your reasoning when disagreeing
    - Don't take feedback personally — it's about the code, not you
    - Keep PRs small to make reviewer's job easier
    
  For Reviewers:
    - Be respectful and kind
    - Explain WHY you're requesting a change
    - Distinguish blocking vs non-blocking feedback
    - Timely reviews (within 1 business day)
    - Acknowledge good work

5. BRANCH PROTECTION RULES
================================================================================

What Are Branch Protection Rules?
  Settings on protected branches (main, develop) that enforce policies before
  merging. Configured in GitHub (Settings → Branches → Add Rule) or GitLab.

Common Branch Protection Settings:

  1. REQUIRE PULL REQUEST REVIEWS
     - Minimum number of approvals (typically 1-2)
     - Dismiss stale reviews on new commits (re-review after changes)
     - Require review from Code Owners

  2. REQUIRE STATUS CHECKS TO PASS
     - Specify which CI checks must pass before merging
     - Example: "build", "unit-tests", "security-scan"
     - "Require branches to be up to date before merging"

  3. REQUIRE CONVERSATION RESOLUTION
     - All review comments must be resolved before merge

  4. REQUIRE SIGNED COMMITS
     - All commits must have GPG signature
     - Ensures commit author authenticity

  5. REQUIRE LINEAR HISTORY
     - Prevents merge commits — only squash or rebase merging allowed

  6. INCLUDE ADMINISTRATORS
     - Even admins must follow protection rules (no "emergency" bypasses)

  7. RESTRICT PUSH ACCESS
     - Only specific users/teams can push/merge to protected branches

Example GitHub Branch Protection Config (via terraform-github):
  resource "github_branch_protection" "main" {
    repository_id = github_repository.app.node_id
    pattern       = "main"
    
    required_pull_request_reviews {
      required_approving_review_count = 2
      dismiss_stale_reviews           = true
      require_code_owner_reviews      = true
    }
    
    required_status_checks {
      strict   = true   # Require branch to be up to date
      contexts = ["ci/build", "ci/unit-tests", "security/scan"]
    }
    
    enforce_admins = true
    
    required_linear_history = true
  }

6. AUTOMATED CHECKS IN PRs
================================================================================

Status Checks Integration:
  CI systems can report status back to the PR:
  - ✅ Green check = passed
  - ❌ Red X = failed (merge blocked)
  - 🟡 Yellow circle = in progress

Types of Automated Checks:

  BUILD AND TEST:
    - Compilation (Java: Maven/Gradle, JS: webpack, Python: no-op)
    - Unit tests (must pass, 0 failures)
    - Integration tests
    - Code coverage gate (fail if < 80% coverage)
  
  CODE QUALITY:
    - Linting (ESLint, Pylint, Checkstyle, SpotBugs)
    - Code formatting (Prettier, Black, Google Java Format)
    - Complexity checks (cyclomatic complexity limit)
    - SonarQube quality gate (bugs, vulnerabilities, code smells)
  
  SECURITY:
    - SAST (SonarQube, Semgrep, CodeQL, Checkmarx)
    - Secret scanning (GitHub, GitGuardian, TruffleHog)
    - Dependency vulnerability scan (Snyk, Dependabot, OWASP Dependency Check)
  
  INFRASTRUCTURE:
    - Terraform plan (show what will change in infra)
    - terraform validate (syntax check)
    - tflint (Terraform-specific linting)
    - Infracost (cost estimation for IaC changes)
  
  OTHER:
    - PR size check (warn if > 400 lines)
    - License compliance (FOSSA, SPDX)
    - API breaking change detection (openapi-diff)
    - Performance regression detection (benchmarks)

GitHub Actions PR Check Example:
  # .github/workflows/pr-checks.yml
  on:
    pull_request:
      branches: [main]
  
  jobs:
    test:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - name: Run Tests
          run: |
            npm install
            npm test
        - name: Check Coverage
          run: npm run coverage -- --threshold=80
    
    lint:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - run: npm run lint
    
    security:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: snyk/actions/node@master
          env:
            SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}

7. CODE REVIEW BEST PRACTICES
================================================================================

PR Size Best Practices:
  - Target: < 400 lines of diff
  - Maximum before mandatory split: 1000 lines
  - Why: Reviewers' attention diminishes rapidly with PR size
  
  Splitting Large PRs:
    Method 1: Stacked PRs (PR2 depends on PR1)
      PR1: Add data model and migration
      PR2: Add API endpoints (depends on PR1)
      PR3: Add UI (depends on PR2)
    
    Method 2: Feature flags enable partial merges
      Merge incomplete feature behind disabled flag
    
    Method 3: Refactor + feature separately
      PR1: Refactor existing code (no behavior change)
      PR2: Add new feature (smaller, cleaner code)

Response Time SLAs:
  - First review response: Within 1 business day
  - Subsequent reviews: Within 4 hours (if actively iterating)
  - Teams should define SLAs and track review wait time
  
  Warning sign: PRs sitting in review for > 2 days

Review Culture:
  - Reviews are collaborative, not adversarial
  - "We" not "you": "We should handle this error" not "you forgot to handle this"
  - Acknowledge learning: "I learned something from this PR!"
  - Spread knowledge: If only one person can review something, that's a risk
  - Rotate reviewers to spread knowledge

Pair Programming as Code Review:
  - Code reviewed while written (no separate review step)
  - Faster than async review
  - Strong knowledge sharing
  - Often used in TBD setups

Asynchronous Code Review Tools:
  - GitHub PR comments / GitLab MR comments
  - Suggested changes (reviewer can propose exact code changes)
  - Request changes / Approve / Comment statuses
  - Review summary at the end

The "Approval Checkbox" Anti-Pattern:
  - Reviewers rubber-stamp PRs without reading
  - Caused by: Large PRs, time pressure, no psychological safety
  - Solution: Smaller PRs, explicit review culture, quality gates

8. COMMON ANTI-PATTERNS
================================================================================

A. "LGTM" WITHOUT READING
   Problem: Reviewer approves without actually reviewing
   Solution: Pair review requirements, PR size limits, quality culture

B. TOO MANY REQUIRED REVIEWERS
   Problem: 5 required approvals → PR stuck for days
   Solution: 1-2 required approvals. More optional, fewer required.

C. REVIEW IN ISOLATION (NO COLLABORATION)
   Problem: Author and reviewer exchange many async messages over days
   Solution: Use PR comments efficiently; jump on a call for complex discussions

D. REVIEWER AS GATEKEEPER (NOT COLLABORATOR)
   Problem: Reviewer says "no" without explaining why or offering alternatives
   Solution: Code review training, clear norms on constructive feedback

E. STALE BRANCHES
   Problem: PR opened but author is slow to respond to feedback
   Solution: Time limits on PR response, bot reminders, team norms

F. GIANT PRs
   Problem: 3000-line PR, reviewer gives up
   Solution: PR size limits, automated warnings, culture of small PRs

G. NO PR TEMPLATE
   Problem: PRs lack context, reviewers don't know what/why/how to test
   Solution: PR template in .github/PULL_REQUEST_TEMPLATE.md

H. BROKEN BUILDS IGNORED
   Problem: CI is red but team merges anyway ("it's a flaky test")
   Solution: Never merge failing builds. Fix flaky tests or delete them.

9. PR MERGE STRATEGIES
================================================================================

GitHub/GitLab offer three merge options:

1. MERGE COMMIT (--no-ff):
   - Creates a merge commit joining the branches
   - Full commit history from feature branch preserved
   - main history shows branching and merging
   
   History: A ── B ── E ── M
                 \       /
                  C ── D
   
   Best for: Teams that want full commit history, complex features
   Result: Noisy history with many merge commits

2. SQUASH AND MERGE:
   - All feature branch commits squashed into one commit on main
   - Cleaner main branch history (1 commit per PR)
   - Individual commit history from feature branch is lost (visible in PR)
   
   History: A ── B ── E ── "feat: all feature work" (S)
   
   Best for: Feature branches with many "WIP" / "fix typo" commits
   Benefit: Clean main history, easy to revert entire feature

3. REBASE AND MERGE:
   - Commits from feature branch replayed onto main (no merge commit)
   - Linear history
   - Individual commits preserved but rewritten (new SHAs)
   
   History: A ── B ── E ── C' ── D'  (C' and D' are rebased versions)
   
   Best for: Teams wanting linear history without squashing
   Risk: SHA changes can confuse if commits were referenced elsewhere

Configuration in GitHub:
  Repo Settings → Allow merge commits / Allow squash merging / Allow rebase merging
  Uncheck options you don't want to enforce a strategy.

Popular Choice: Squash merge
  - Clean main history (1 commit = 1 feature = 1 revert if needed)
  - Less noisy than merge commits
  - Details visible in the PR (not in git log)

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is a Pull Request and why is it important in DevOps?
A: A Pull Request is a request to merge code from one branch into another,
   serving as a formal gate before changes reach the main branch. It's important
   in DevOps because it combines code review, automated testing, and compliance
   checks in one workflow.
   
   In DevOps, it's the primary control point where:
   - Code quality is enforced (human review + automated checks)
   - Security vulnerabilities are caught before production
   - Knowledge is shared across the team
   - An audit trail is created (who approved, what changed, when)
   
   Without PRs, code changes directly to main often bypass all these controls.

Q2: How do you keep the code review process fast without sacrificing quality?
A: Several practices:
   1. Small PRs (< 400 lines): Faster to review, better feedback quality
   2. Clear PR description: Reviewer understands context immediately
   3. Automated checks: CI handles the mechanical quality checks, reviewer
      focuses on logic and design
   4. Clear review SLAs: Team agrees on 1-business-day response time
   5. Draft PRs: Get early architecture feedback before full implementation
   6. CODEOWNERS: Right reviewer assigned automatically
   7. Stale PR notifications: Bot reminds when PRs are waiting
   
   Ironically, faster code review comes from spending more upfront time on
   writing a clear PR description and keeping changes small.

Q3: What should you look for when reviewing code?
A: In priority order:
   1. Correctness: Does it do what it's supposed to? Edge cases handled?
   2. Tests: Are there tests that would catch regressions?
   3. Security: SQL injection, unvalidated input, hardcoded secrets?
   4. Design: SOLID principles, appropriate abstractions, follows patterns?
   5. Performance: N+1 queries, expensive operations in loops?
   6. Readability: Clear names, comments explain "why"?
   
   I also check if the PR description explains the "why" and if there are
   instructions for testing the change.

Q4: Explain branch protection rules and why they matter.
A: Branch protection rules are repository settings that enforce policies on
   protected branches (typically main/master) before allowing merges.
   
   Key rules:
   - Require pull request reviews (N approvals needed)
   - Require status checks (CI must pass)
   - Require conversation resolution (all comments resolved)
   - Include administrators (no bypasses)
   
   They matter because they automate policy enforcement. Without them,
   a developer (or even an admin) can push directly to main, bypassing code
   review and CI. In regulated industries, they're often required for compliance
   (SOC 2, PCI-DSS require separation of duties).

Q5: What is a CODEOWNERS file?
A: A CODEOWNERS file maps file paths to users or teams who must review changes
   to those files. When a PR touches matching files, those owners are
   automatically requested for review.
   
   For example: /src/payment/ @security-team @payments-team
   Any PR modifying payment code requires approval from both teams.
   
   Benefits: Ensures domain experts review their areas, prevents accidental
   changes to sensitive code, enforces organizational knowledge distribution.
   
   Security implication: Can ensure security team reviews security-sensitive
   code, satisfying compliance requirements.

Q6: Squash merge vs regular merge commit — which do you prefer and why?
A: I generally prefer squash merge for feature PRs because it keeps the main
   branch history clean and readable. Each PR becomes one commit with a
   meaningful message (the PR title). This makes `git log --oneline` on main
   actually useful — you can see each feature at a glance.
   
   If you need to revert a feature, you revert one commit.
   
   However, if individual commits in a feature branch are meaningful (each is a
   self-contained change that tells a story), rebase merge preserves them without
   the noise of a merge commit.
   
   For hotfixes or important standalone commits, regular merge with no-ff
   preserves the merge commit as a marker in history.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

PR Lifecycle:
  Create branch → Develop → Push → Open PR → CI runs → Review → Approve → Merge

PR Title Format: <type>(<scope>): <description>
Example: feat(auth): add OAuth2 login

Good PR:
  - Small (< 400 lines)
  - Clear description (what, why, how to test)
  - All CI checks pass
  - Linked to ticket/issue

Code Review Focus Areas:
  Correctness → Tests → Security → Design → Performance → Readability

Branch Protection Rules:
  - Required approvals (1-2)
  - Required status checks (CI)
  - Include administrators
  - Dismiss stale reviews on new commits

CODEOWNERS:
  /src/payment/ @security-team @payments-team
  (auto-assign reviewers based on changed files)

Merge Strategies:
  Squash: Clean history, 1 commit per PR (most common)
  Merge commit: Full history, shows branches
  Rebase: Linear, no merge commit, individual commits preserved

Anti-patterns:
  ✗ "LGTM" without reading
  ✗ Giant PRs (> 1000 lines)
  ✗ No PR template
  ✗ Merging failing CI
  ✗ Too many required reviewers (slows delivery)
