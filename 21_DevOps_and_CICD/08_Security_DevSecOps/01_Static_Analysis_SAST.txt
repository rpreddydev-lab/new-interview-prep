1. SAST OVERVIEW
================================================================================

Static Application Security Testing analyzes source code WITHOUT running it.
  "White box" testing — has full access to code.
  
  Findings:
  ✅ SQL injection, command injection, XSS
  ✅ Insecure cryptographic usage (MD5, SHA1)
  ✅ Hardcoded credentials and secrets
  ✅ Insecure deserialization
  ✅ Path traversal, SSRF patterns
  ✅ Insecure random number generation
  ✅ Missing authorization checks (some tools)
  
  Limitations:
  ❌ Cannot find runtime configuration issues
  ❌ Business logic vulnerabilities
  ❌ Authentication bypass (needs running app)
  ❌ High false positive rate (needs tuning)

When to Run:
  Pre-commit (fast, changed files only)
  PR check (full analysis, block merge on critical)
  CI pipeline (comprehensive scan, track over time)

Key Concepts:
  False positive:  Tool reports vulnerability that doesn't exist.
                   Too many → developers ignore alerts (alert fatigue).
  False negative:  Tool misses a real vulnerability.
                   More dangerous — false sense of security.
  
  Tuning: Every SAST tool needs rules tailored to your tech stack.
          Suppress known false positives. Focus on actionable findings.

2. SEMGREP
================================================================================

What is Semgrep?
  Open-source SAST tool.
  Pattern-based analysis: Write rules that look like the code you want to find.
  Extremely fast (designed for CI).
  Large community ruleset (semgrep-rules).

Why Semgrep is Popular:
  - Rules in YAML, patterns look like code → easy to write custom rules
  - Free community tier with thousands of rules
  - First-class CI integration (GitHub Actions, GitLab CI, Jenkins)
  - Multi-language support (30+ languages)
  - Low false positive rate compared to traditional SAST tools

Installation:
  pip install semgrep
  # or
  brew install semgrep

Basic Usage:
  # Scan current directory with default rules:
  semgrep --config=auto .
  
  # Use OWASP Top 10 ruleset:
  semgrep --config="p/owasp-top-ten" .
  
  # Scan specific directory with Python security rules:
  semgrep --config="p/python" src/
  
  # Exit with non-zero on findings:
  semgrep --config="p/security-audit" --error .
  
  # Output as JSON (for CI integration):
  semgrep --config=auto --json --output=semgrep-results.json .

Custom Rule Example:
  # Find hardcoded AWS access keys:
  rules:
  - id: hardcoded-aws-access-key
    pattern: |
      $X = "AKIA..."
    message: "Possible AWS access key hardcoded: $X"
    languages: [python, javascript, java]
    severity: ERROR
  
  # Find use of dangerous eval():
  rules:
  - id: dangerous-eval
    pattern: eval($USER_INPUT)
    message: "Do not use eval() with user input — code injection risk"
    languages: [python, javascript]
    severity: ERROR
    fix: "# Use ast.literal_eval() or json.loads() instead"
  
  # Find SQL injection (string formatting in query):
  rules:
  - id: sql-injection-string-format
    patterns:
    - pattern: cursor.execute($QUERY % ...)
    - pattern-not: cursor.execute($QUERY, ...)  # Parameterized is OK
    message: "SQL injection risk: use parameterized queries"
    languages: [python]
    severity: ERROR
  
  # Run custom rule:
  semgrep --config=my-rules.yaml src/

Semgrep in GitHub Actions:
  name: SAST - Semgrep
  
  on:
    push:
      branches: [main]
    pull_request:
  
  jobs:
    semgrep:
      runs-on: ubuntu-latest
      container:
        image: semgrep/semgrep
      steps:
      - uses: actions/checkout@v4
      
      - name: Run Semgrep SAST
        run: |
          semgrep \
            --config=auto \
            --config="p/owasp-top-ten" \
            --config="p/python" \
            --json \
            --output=semgrep-results.json \
            --severity=ERROR \
            --error \
            .
        env:
          SEMGREP_APP_TOKEN: ${{ secrets.SEMGREP_APP_TOKEN }}
      
      - name: Upload results to GitHub Security
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: semgrep-results.json
      
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: semgrep-results
          path: semgrep-results.json

3. SONARQUBE
================================================================================

What is SonarQube?
  Comprehensive code quality AND security analysis platform.
  Analyzes code for bugs, vulnerabilities, code smells, and coverage.
  Self-hosted (Community Edition free) or SonarCloud (SaaS).

Key Features:
  - SAST: Vulnerability and bug detection
  - Code quality: Complexity, duplication, coverage
  - Quality Gates: Block merge/deploy if quality/security thresholds not met
  - Security Hotspots: Requires human review (not automatically flagged as issue)
  - Track technical debt over time

SonarQube Quality Gate:
  Defines pass/fail conditions for code.
  Example quality gate:
  - Coverage on new code > 80%
  - No new critical vulnerabilities
  - No new blocker bugs
  - Duplication on new code < 3%

Integration with CI (GitHub Actions):
  jobs:
    sonarqube:
      runs-on: ubuntu-latest
      steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # Full history for better analysis
      
      - name: Run SonarQube Scan
        uses: SonarSource/sonarqube-scan-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
        with:
          args: >
            -Dsonar.projectKey=my-project
            -Dsonar.sources=src
            -Dsonar.tests=tests
            -Dsonar.python.coverage.reportPaths=coverage.xml
  
  # sonar-project.properties (in repo root):
  sonar.projectKey=payment-service
  sonar.projectName=Payment Service
  sonar.sources=src/
  sonar.tests=tests/
  sonar.python.version=3.11
  sonar.exclusions=**/migrations/**,**/node_modules/**

SonarQube Docker Deployment:
  # docker-compose.yml:
  version: "3"
  services:
    sonarqube:
      image: sonarqube:community
      ports:
        - "9000:9000"
      volumes:
        - sonarqube_data:/opt/sonarqube/data
        - sonarqube_logs:/opt/sonarqube/logs
        - sonarqube_extensions:/opt/sonarqube/extensions
      environment:
        SONAR_JDBC_URL: jdbc:postgresql://db:5432/sonar
        SONAR_JDBC_USERNAME: sonar
        SONAR_JDBC_PASSWORD: sonar
    db:
      image: postgres:15
      environment:
        POSTGRES_USER: sonar
        POSTGRES_PASSWORD: sonar
        POSTGRES_DB: sonar
  
  volumes:
    sonarqube_data:
    sonarqube_logs:
    sonarqube_extensions:

4. CODEQL (GITHUB ADVANCED SECURITY)
================================================================================

What is CodeQL?
  Semantic code analysis by GitHub (acquired from Semmle).
  Treats code as data → SQL-like queries to find vulnerabilities.
  Deep dataflow analysis: can trace user input to dangerous function calls.
  
  "Is user input from request.args ever passed to subprocess.call()?"
  CodeQL can track this data flow across files and functions.

CodeQL in GitHub Actions:
  name: CodeQL Security Analysis
  
  on:
    push:
      branches: [main]
    pull_request:
    schedule:
    - cron: '30 1 * * 1'   # Weekly full scan
  
  jobs:
    analyze:
      runs-on: ubuntu-latest
      permissions:
        actions: read
        contents: read
        security-events: write   # Required for uploading SARIF
      
      strategy:
        matrix:
          language: ['python', 'javascript']
          # Other supported: java, csharp, go, cpp, ruby, swift
      
      steps:
      - name: Checkout code
        uses: actions/checkout@v4
      
      - name: Initialize CodeQL
        uses: github/codeql-action/init@v3
        with:
          languages: ${{ matrix.language }}
          queries: security-and-quality  # Use security + quality queries
      
      - name: Autobuild
        uses: github/codeql-action/autobuild@v3
        # For compiled languages: builds automatically
        # For Python/JS: no build needed
      
      - name: Perform CodeQL Analysis
        uses: github/codeql-action/analyze@v3
        with:
          category: "/language:${{ matrix.language }}"
  
  # Results appear in GitHub Security → Code scanning alerts
  # Blocks PRs if configured in branch protection rules

5. SAST IN CI/CD PIPELINES
================================================================================

Recommended Pipeline Design:
  
  Fast PR check (< 2 minutes):
  - Semgrep on changed files only
  - Secret scanning on changed files
  - Block on CRITICAL findings
  
  Thorough CI scan (runs on merge to main, < 15 minutes):
  - Semgrep full scan
  - SonarQube with quality gate
  - Upload SARIF to GitHub Security tab
  
  Weekly scheduled scan:
  - CodeQL deep analysis
  - Review new findings from technical debt perspective

Handling False Positives:
  1. Add inline suppression comments:
     # nosec B608    (Bandit suppression)
     # semgrep:ignore  (Semgrep suppression)
     // NOSONAR     (SonarQube suppression)
  
  2. Add to project-level ignore file (.semgrepignore):
     # .semgrepignore:
     tests/fixtures/
     migrations/
     *_test.go
  
  3. Use SonarQube "Won't Fix" or "False Positive" marking.
  
  Rule: Never suppress without a comment explaining WHY.
  "# nosec B608: This query is built only from internal constants, no user input."

SARIF (Static Analysis Results Interchange Format):
  Standard format for security tool output.
  GitHub, GitLab, Azure DevOps all support SARIF uploads.
  Enables viewing findings directly in PR comments and Security tab.

6. DAST OVERVIEW
================================================================================

Dynamic Application Security Testing tests a RUNNING application.
  "Black box" testing — treats the app as an external attacker would.
  Sends HTTP requests, observes responses, identifies vulnerabilities.

Findings:
  ✅ Cross-Site Scripting (XSS) — by injecting scripts and seeing if they execute
  ✅ SQL injection — by injecting SQL and observing errors/data leakage
  ✅ Authentication/session issues — by manipulating tokens/cookies
  ✅ Security header misconfigurations (missing X-Frame-Options, CSP, etc.)
  ✅ Directory traversal — by modifying file paths in requests
  ✅ Server information disclosure — by reading error messages and headers
  
  Limitations:
  ❌ Cannot find issues only visible in code (logic bugs, weak crypto in code)
  ❌ Requires a running application (needs deploy to staging)
  ❌ May miss complex authenticated flows (needs authentication setup)
  ❌ Can be slow (crawls and tests entire application surface)

DAST Scope:
  Active DAST:  Sends attack payloads (may break the app, generate fake data)
                Run against STAGING only — never production.
  Passive DAST: Observes traffic, doesn't send attacks
                Safe to use against production (integrated with proxy/WAF).

7. OWASP ZAP
================================================================================

What is OWASP ZAP (Zed Attack Proxy)?
  Open-source web vulnerability scanner.
  Most popular free DAST tool.
  Can be used manually (GUI) or automated (CLI, API, GitHub Actions).

ZAP Scan Modes:
  Baseline Scan:   Fast, passive scan + spider. Good for CI.
  Full Scan:       Active scan — sends attack payloads. Use in staging.
  API Scan:        Optimized for REST/GraphQL APIs (uses OpenAPI spec).

ZAP Baseline Scan (Docker, fastest):
  # Passive + spider scan (safe for any environment):
  docker run --rm -v $(pwd):/zap/wrk/:rw \
    ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
    -t https://staging.myapp.com \
    -r zap-report.html \
    -x zap-report.xml \
    -I                              # Don't fail on warnings
    --exit-code 1                   # Exit 1 on alerts found

ZAP Full Scan (active, staging only):
  # Full active scan with authentication:
  docker run --rm -v $(pwd):/zap/wrk/:rw \
    ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
    -t https://staging.myapp.com \
    -r zap-full-report.html \
    -x zap-full-report.xml \
    -c zap-rules.conf            # Rule configuration (suppress false positives)

ZAP API Scan (OpenAPI/Swagger):
  # Scan REST API using OpenAPI spec:
  docker run --rm -v $(pwd):/zap/wrk/:rw \
    ghcr.io/zaproxy/zaproxy:stable zap-api-scan.py \
    -t https://staging.myapp.com/openapi.json \
    -f openapi \
    -r zap-api-report.html

ZAP Rule Configuration (.conf file):
  # zap-rules.conf — suppress noisy rules for your environment:
  10015     IGNORE     (Incomplete or No Cache-control Header Set)
  10096     IGNORE     (Timestamp Disclosure)

8. AUTOMATED DAST IN CI/CD
================================================================================

DAST Pipeline Stage:
  
  ┌─────────────────────────────────────────────────────────────────────┐
  │  CI/CD Pipeline with DAST:                                          │
  │                                                                      │
  │  Build → Unit Tests → Deploy to Staging → [DAST Scan] → Approve    │
  │                                                    │                 │
  │                                              ┌─────▼──────────┐    │
  │                                              │ ZAP Baseline   │    │
  │                                              │ ZAP API Scan   │    │
  │                                              │ Upload SARIF   │    │
  │                                              └────────────────┘    │
  └─────────────────────────────────────────────────────────────────────┘

GitHub Actions DAST with ZAP:
  name: DAST - OWASP ZAP
  
  on:
    push:
      branches: [main]
  
  jobs:
    dast:
      runs-on: ubuntu-latest
      needs: deploy-staging     # Depends on staging deployment
      
      steps:
      - name: Checkout
        uses: actions/checkout@v4
      
      # ZAP Baseline Scan:
      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.10.0
        with:
          target: 'https://staging.myapp.com'
          rules_file_name: '.zap/rules.tsv'
          cmd_options: '-I'    # Don't fail on warnings
          allow_issue_writing: true  # Create GitHub issues for findings
      
      # ZAP API Scan:
      - name: ZAP API Scan
        uses: zaproxy/action-api-scan@v0.6.0
        with:
          target: 'https://staging.myapp.com/openapi.json'
          format: openapi
          rules_file_name: '.zap/api-rules.tsv'
      
      # Upload SARIF to GitHub Security:
      - name: Upload ZAP SARIF Report
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: zap.sarif

DAST with Authentication:
  # ZAP context file for authenticated scanning:
  # Create auth script in .zap/auth.js or use form-based auth config
  
  - name: ZAP Authenticated Scan
    uses: zaproxy/action-full-scan@v0.9.0
    with:
      target: 'https://staging.myapp.com'
      zap_auth_header_value: 'Bearer ${{ secrets.STAGING_API_TOKEN }}'
      # ZAP will include Authorization header in all requests

9. SAST VS DAST COMPARISON
================================================================================

  ┌─────────────────────┬─────────────────────────────┬───────────────────────────┐
  │ Dimension           │ SAST                         │ DAST                      │
  ├─────────────────────┼─────────────────────────────┼───────────────────────────┤
  │ Timing              │ During development/PR/CI     │ After deployment (staging) │
  │ Target              │ Source code                  │ Running application        │
  │ Visibility          │ White box (sees code)        │ Black box (HTTP requests)  │
  │ Languages           │ Language-specific            │ Language-agnostic          │
  │ False positive rate │ Higher (needs tuning)        │ Lower (confirmed behavior) │
  │ Coverage            │ All code paths               │ Only reachable endpoints   │
  │ Speed               │ Fast (IDE/PR in seconds)     │ Slow (crawl + attack)      │
  │ What it finds       │ Code-level vulnerabilities   │ Runtime behavior           │
  │ Auth required       │ No                           │ Yes (for authenticated)    │
  │ Breaks staging?     │ No                           │ Active scan may create data│
  └─────────────────────┴─────────────────────────────┴───────────────────────────┘

Combined Approach:
  Use BOTH for comprehensive coverage:
  - SAST: Catches code-level issues early (cheap to fix)
  - DAST: Validates nothing was missed in running behavior
  - Neither replaces the other or manual penetration testing

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between SAST and DAST and when would you use each?
A: SAST and DAST are complementary approaches with different strengths:
   
   SAST (Static Analysis):
   - Analyzes source code without executing the application
   - Runs early: in IDE, at pre-commit, in PR checks
   - Good for: injection patterns, insecure crypto, hardcoded secrets, path traversal
   - Limitation: High false positive rate; can't find runtime behavior issues
   - Tools: Semgrep, SonarQube, CodeQL
   
   DAST (Dynamic Analysis):
   - Tests a running application by sending HTTP requests
   - Runs after deployment to a staging environment
   - Good for: XSS, authentication issues, header misconfigurations, directory traversal
   - Limitation: Requires a running app; can be slow; may miss code-level issues
   - Tools: OWASP ZAP, Burp Suite
   
   Use both in a pipeline:
   PR/CI → SAST (fast, code-level) → build passes
   CI/CD → Deploy to staging → DAST scan → approve for production
   
   Real example: SAST might detect "cursor.execute(user_input)" pattern (SQL injection).
   DAST confirms by sending "'; DROP TABLE users;--" and observing the response.
   SAST finds it earlier and cheaper. DAST validates it's actually exploitable.

Q2: How do you handle SAST false positives at scale?
A: False positives are the biggest adoption barrier for SAST tools.
   Strategy:
   
   1. Start with high-confidence rules only:
      Don't enable every rule on day one.
      Use curated rulesets (Semgrep "p/owasp-top-ten" has low FP rate).
      Gradually add more rules as you tune existing ones.
   
   2. Suppress known false positives with explanations:
      # nosec B608: query is constructed only from internal constants
      This creates a self-documenting audit trail (why was this suppressed?).
      Require PR review to add suppressions.
   
   3. Track FP rate per rule:
      If a rule has >50% false positive rate → disable or tune it.
      SonarQube "Won't Fix" counts contribute to FP tracking.
   
   4. Use inline annotations for third-party code paths:
      semgrep .semgrepignore to exclude test fixtures, generated code, migrations.
   
   5. Configure severity thresholds:
      Block CI only on HIGH/CRITICAL
      Report MEDIUM/LOW in PR comments (informational, not blocking)
      This reduces developer friction dramatically.
   
   6. Review suppressions in quarterly audits:
      Has the code changed? Is the suppression still valid?

Q3: Walk me through setting up OWASP ZAP in a CI pipeline.
A: Steps to integrate ZAP into a GitHub Actions CI pipeline:
   
   1. Ensure staging environment is deployed before DAST runs:
      Use workflow dependencies (needs: [deploy-staging]).
   
   2. Choose scan type:
      Baseline scan: Fast passive scan, safe, good for all environments.
      API scan: For REST APIs with OpenAPI spec, targeted.
      Full scan: Active attacks, staging only, more findings.
   
   3. Configure suppression rules:
      Create .zap/rules.tsv to suppress known acceptable alerts.
      Example: "Timestamp disclosure" is often acceptable, suppress it.
   
   4. Use ZAP GitHub Actions:
      zaproxy/action-baseline@v0.10.0 — wraps ZAP in a Docker container.
      Handles docker pull, scan execution, result parsing.
   
   5. Handle results:
      Upload SARIF to GitHub Security tab (via github/codeql-action/upload-sarif).
      Create GitHub issues for findings (action-baseline supports this natively).
      Set exit code: fail build on high-severity active findings.
   
   6. Authenticated scanning (if needed):
      Pass API token via header: zap_auth_header_value
      For form-based auth: write a ZAP authentication script.
   
   Key consideration: Active DAST scans create data in your staging environment.
   Use a dedicated staging environment with test data that can be reset.
   ZAP may trigger rate limiting or WAF rules — allowlist your ZAP runner IP.

Q4: How would you implement a "security quality gate" for deployments?
A: A security quality gate prevents insecure code from reaching production:
   
   Gates by environment:
   
   Dev → PR merge (GitHub branch protection):
   - Required: SAST passes (no new critical findings)
   - Required: SCA scan passes (no critical unfixed CVEs in new dependencies)
   - Required: No secrets detected in code
   - Optional: SonarQube quality gate passes (configurable thresholds)
   
   Main → Staging deploy:
   - Container image scan: trivy exits 0 (no HIGH/CRITICAL vulnerabilities)
   - IaC scan: checkov passes critical checks
   - Policy compliance: OPA/Conftest rules pass
   
   Staging → Production:
   - DAST baseline scan passed
   - No open critical security findings in last 30 days
   - All required reviews approved (including security team for high-risk changes)
   
   Implementation in GitHub Actions:
   - Branch protection rules: require specific status checks to pass
   - Required reviewers: CODEOWNERS file routes security-sensitive paths to security team
   - Environments with protection rules: production environment requires approval + passing security checks
   
   Baseline management:
   On legacy codebases: Don't fail on all existing issues.
   Use "new code only" policies in SonarQube.
   Semgrep: ignore results on unchanged code, only new findings block.

Q5: What is CodeQL and how is it different from tools like Semgrep or Bandit?
A: CodeQL is a semantic code analysis platform developed by GitHub (from Semmle).
   
   Key differentiator: Dataflow analysis.
   
   CodeQL converts source code into a relational database.
   It then runs QL (CodeQL Query Language) queries that can:
   - Track the flow of data from source (user input) to sink (dangerous function)
   - Across multiple files, functions, and modules
   
   Example:
   Semgrep finds: cursor.execute("SELECT..." + user_input)  (pattern match)
   CodeQL finds: user data from request.args["name"] flows into cursor.execute()
                 even if it goes through 3 helper functions and 2 files first.
   
   This makes CodeQL significantly more powerful for complex vulnerabilities.
   
   Comparison:
   
   Bandit (Python-specific):
   - Rules-based, fast, single file analysis
   - Good for: Quick Python security scan, simple patterns
   - Limitation: Doesn't track data flow across functions
   
   Semgrep:
   - Pattern-based, multi-language, fast, easy custom rules
   - Good for: Fast CI scans, custom patterns for your codebase
   - Limitation: Limited cross-function data flow analysis
   
   CodeQL:
   - Deep semantic + dataflow analysis, multi-language
   - Good for: Finding complex vulnerabilities across code paths
   - Limitation: Slower (needs to compile code model), GitHub-dependent for easy use
   
   In practice:
   Use Semgrep for fast PR checks (seconds).
   Use CodeQL for deeper weekly scans.
   These are complementary, not alternatives.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

SAST TOOLS:
  Semgrep      Pattern-based, fast, multi-language, custom rules
  SonarQube    Quality + security, quality gates, technical debt tracking
  CodeQL       Deep dataflow analysis, GitHub-integrated
  Bandit       Python-specific, simple, good for baseline

DAST TOOLS:
  OWASP ZAP    Open source, baseline/full/API scan modes
  Burp Suite   Professional manual + automated DAST
  Nikto        Fast web server scanner

SEMGREP COMMANDS:
  semgrep --config=auto .                  Auto-select rules
  semgrep --config="p/owasp-top-ten" .     OWASP ruleset
  semgrep --config=my-rules.yaml src/      Custom rules
  semgrep --json --output=results.json .   JSON output for CI

ZAP DOCKER COMMANDS:
  zap-baseline.py -t <url>     Passive scan (fast, safe)
  zap-full-scan.py -t <url>    Active scan (staging only!)
  zap-api-scan.py -t <spec>    API scan (OpenAPI/Swagger)

FALSE POSITIVE HANDLING:
  # nosec B608      Bandit suppression
  # semgrep:ignore  Semgrep suppression
  // NOSONAR        SonarQube suppression
  Always add comment explaining why suppression is valid

SECURITY QUALITY GATE STAGES:
  PR gate:       SAST critical, no new CVEs, no secrets
  CI gate:       Container scan, IaC scan, policy compliance
  Pre-prod gate: DAST baseline, no open criticals
  Prod gate:     Approval + all gates green
