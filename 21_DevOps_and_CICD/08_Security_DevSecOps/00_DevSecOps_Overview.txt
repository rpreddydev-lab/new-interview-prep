1. WHAT IS DEVSECOPS?
================================================================================

DevSecOps integrates security practices into DevOps workflows.
"Security as Code" — security automated, shift-left, everyone's responsibility.

Traditional view: Security team reviews software BEFORE release.
DevSecOps view: Security checks run AUTOMATICALLY at every stage of the pipeline.

Core Principle: Fail fast, fail early.
  Catch a SQL injection bug in a developer's PR: costs 1 hour to fix.
  Catch it in staging: costs 1 day.
  Catch it in production: costs thousands/millions + reputational damage.

DevSecOps Mantra:
  "Security is not a gate. It's a guardrail."
  Guardrails guide without stopping. Gates block and create bottlenecks.

2. SHIFTING SECURITY LEFT
================================================================================

The "Security Left" Concept:
  
  Traditional:
  Dev → Dev → Dev → Test → Staging → Security Review → Production
                                              ↑
                                        Security is HERE
  
  Shift Left:
  Dev → Dev → Dev → Test → Staging → Production
   ↑     ↑    ↑     ↑       ↑
  IDE  Pre-commit  PR    CI/CD   Pre-release
  
  Security checks run at every stage, not just at the end.

Benefits of Shift Left:
  Cheaper: Finding a bug in IDE vs production is 30-100x cheaper to fix.
  Faster: Automated checks in CI = no waiting for security team review.
  Better: Developers learn security by seeing immediate feedback.
  Safer: Continuous security vs point-in-time review.

How to Shift Left:
  1. IDE plugins: SonarLint, Snyk VS Code extension — flag issues as you type.
  2. Pre-commit hooks: Block commits with secrets, run SAST on changed files.
  3. PR checks: SAST, SCA (dependency scanning) on every pull request.
  4. CI pipeline: DAST, container scanning, IaC scanning on every build.
  5. CD pipeline: Policy enforcement before deployment.
  6. Runtime: Falco (anomaly detection in K8s), WAF, RASP.

4. SECURITY IN THE SDLC
================================================================================

Phase 1: PLANNING / REQUIREMENTS
  Threat modeling:
  - What are the assets we're protecting? (user data, payment info, credentials)
  - Who are the threats? (external attackers, malicious insiders, accidental)
  - What are the attack vectors? (injection, auth bypass, supply chain)
  - STRIDE model: Spoofing, Tampering, Repudiation, Info Disclosure, DoS, Elevation
  
  Security requirements:
  - Define what "secure" means for this feature
  - Define compliance requirements (GDPR, PCI-DSS, SOC 2, HIPAA)

Phase 2: DEVELOPMENT (IDE + Pre-commit)
  Tools:
  - SonarLint (IDE plugin) — real-time code analysis
  - Snyk IDE plugin — dependency vulnerability scanning
  - .pre-commit-config.yaml — run SAST, secret detection on commit
  
  Developer practices:
  - Never store secrets in code (use env vars, Vault, AWS Secrets Manager)
  - Input validation on all external inputs
  - Parameterized queries (prevent SQL injection)
  - OWASP Top 10 awareness training

Phase 3: CODE REVIEW (PR)
  Automated checks on PR:
  - SAST: Semgrep, SonarQube (static code analysis)
  - SCA: Snyk, Dependabot, OWASP Dependency Check (dependency vulnerabilities)
  - Secret scanning: GitHub Secret Scanning, TruffleHog
  - IaC scanning: tfsec, checkov (if IaC files changed)
  
  Human review:
  - Security-sensitive PRs require security team review
  - Mandatory review for: auth changes, crypto, payment processing

Phase 4: CI/CD PIPELINE (Build + Test)
  Automated security gate in CI:
  - SAST: Full codebase scan (not just changed files)
  - Container image scanning: Trivy, Snyk Container, Clair
  - DAST: Automated web vulnerability scan against staging environment
  - License scanning: Check for GPL licenses in proprietary code
  - Compliance validation: OPA/Sentinel policy checks

Phase 5: STAGING / PRE-PRODUCTION
  - Penetration testing (regular, not just at release)
  - DAST against production-like environment
  - Security review for new features with high-risk profiles
  - Compliance checks (GDPR data flows, PCI requirements)

Phase 6: PRODUCTION
  - Runtime security: Falco (K8s anomaly detection), WAF (web application firewall)
  - SIEM: Security information and event management (Splunk, Elastic SIEM)
  - Vulnerability management: Continuously scan running containers
  - Incident response plan ready

5. SAST, DAST, SCA — OVERVIEW
================================================================================

SAST — Static Application Security Testing:
  Analyzes SOURCE CODE without running the application.
  "White box" testing — can see inside the code.
  
  Finds: Injection flaws, insecure crypto, hardcoded secrets, insecure deserialization.
  Cannot find: Runtime vulnerabilities (logic flaws, authentication bypass).
  
  Tools: Semgrep, SonarQube, Checkmarx, Veracode, CodeQL

DAST — Dynamic Application Security Testing:
  Tests a RUNNING application by sending requests and observing responses.
  "Black box" testing — treats app as external attacker would.
  
  Finds: XSS, SQL injection (via responses), broken auth, misconfigurations.
  Cannot find: Source code issues, logic issues not visible via HTTP.
  
  Tools: OWASP ZAP, Burp Suite, Nikto, Nessus

SCA — Software Composition Analysis:
  Analyzes DEPENDENCIES (third-party libraries) for known vulnerabilities.
  Checks against CVE databases (NVD, OSS Index, GitHub Advisory).
  
  Finds: Known CVEs in dependencies, license compliance issues.
  Cannot find: Custom code vulnerabilities, business logic issues.
  
  Tools: Snyk, Dependabot (GitHub), OWASP Dependency Check, WhiteSource/Mend

  ┌──────────────────┬────────────────────────┬────────────────────┐
  │ Type             │ Tests                   │ Best Stage         │
  ├──────────────────┼────────────────────────┼────────────────────┤
  │ SAST             │ Source code analysis    │ PR + CI pipeline   │
  │ DAST             │ Running application     │ Staging/pre-prod   │
  │ SCA              │ Dependencies            │ PR + CI pipeline   │
  │ Container Scan   │ Container images        │ CI (post-build)    │
  │ IaC Scan         │ Terraform/K8s YAML      │ PR + CI pipeline   │
  └──────────────────┴────────────────────────┴────────────────────┘

7. SECURITY POLICIES AS CODE
================================================================================

Why Policies as Code?
  Manual security reviews don't scale.
  Automated policy enforcement = consistent, auditable, fast.

OPA (Open Policy Agent) — see 06_IaC section for detail.
  Write Rego policies that enforce security rules.
  Integrate with CI/CD (Conftest), K8s (Gatekeeper), Terraform (Sentinel).

Kyverno (Kubernetes-native):
  Alternative to OPA Gatekeeper for K8s admission control.
  Policies written as Kubernetes YAML (not Rego).
  
  Example: Require all Deployments to have resource limits:
  apiVersion: kyverno.io/v1
  kind: ClusterPolicy
  metadata:
    name: require-resource-limits
  spec:
    validationFailureAction: enforce
    rules:
    - name: require-limits
      match:
        any:
        - resources:
            kinds:
            - Deployment
      validate:
        message: "CPU and memory limits are required."
        pattern:
          spec:
            template:
              spec:
                containers:
                - resources:
                    limits:
                      cpu: "?*"
                      memory: "?*"
  
  Example: Disallow privileged containers:
  apiVersion: kyverno.io/v1
  kind: ClusterPolicy
  metadata:
    name: disallow-privileged
  spec:
    validationFailureAction: enforce
    rules:
    - name: disallow-privileged
      match:
        any:
        - resources:
            kinds: [Pod]
      validate:
        message: "Privileged mode is not allowed."
        pattern:
          spec:
            containers:
            - =(securityContext):
                =(privileged): "false"

RBAC as Code:
  Kubernetes RBAC managed via GitOps (ArgoCD/FluxCD).
  All role bindings in Git → auditable, reviewable.
  Any RBAC change requires PR review.

8. COMPLIANCE AND GOVERNANCE IN CI/CD
================================================================================

Compliance Frameworks:
  PCI-DSS:  Payment Card Industry — for payment processing
  HIPAA:    Healthcare data
  SOC 2:    Service Organization Controls — trust service criteria
  GDPR:     EU data privacy
  ISO 27001: Information security management
  CIS Benchmarks: Center for Internet Security hardening standards

Automating Compliance:
  
  CIS Benchmark scanning:
  - kube-bench: Checks K8s clusters against CIS K8s benchmark
    kubectl apply -f https://raw.githubusercontent.com/aquasecurity/kube-bench/main/job.yaml
  
  - AWS Inspector / Security Hub: Automated CIS AWS benchmark checks
  
  Compliance as Code (example: ensure all S3 buckets are encrypted):
  # Conftest/OPA policy:
  deny[msg] {
      resource := input.resource.aws_s3_bucket[name]
      not resource.config.server_side_encryption_configuration
      msg := sprintf("S3 bucket '%v' must have server-side encryption enabled", [name])
  }
  
  Drift detection:
  - AWS Config Rules: Continuously check if resources conform to rules
    Example rule: "ALL S3 buckets must have encryption enabled"
    Alert when a bucket is created without encryption.

Audit Trails:
  Every deployment should produce an audit trail:
  - Who triggered the deployment (Git commit author)
  - What was deployed (Docker image SHA, Git commit SHA)
  - When it was deployed (timestamp)
  - What environment (production, staging)
  
  This is automatically captured by GitOps (ArgoCD/FluxCD) with Git history.

9. BUILDING A DEVSECOPS CULTURE
================================================================================

Common Challenges:
  "Security slows us down" → Automate security (automated = fast).
  "Security is the security team's job" → Everyone owns security.
  "We'll add security later" → Security debt is expensive; shift left.
  "Our codebase is too complex to scan" → Start with high-risk areas.

Getting Buy-In:
  Start with wins: Find real vulnerabilities in existing code with SAST.
     Show: "This SQL injection would have let attackers read all user data."
  Make it easy: Security tools in IDE (instant feedback vs waiting for CI).
  Celebrate secure code: Recognize developers who catch security issues.

Champions Model:
  Embed a "security champion" in each team.
  - Developer with security interest/training
  - Not a full-time security role
  - Liaison between security team and dev team
  - Reviews security-sensitive PRs
  - Keeps team up to date on new vulnerabilities

Training:
  OWASP Top 10 awareness for all developers.
  Secure coding workshops.
  Bug bounty programs (external researchers find bugs, report responsibly).
  Regular phishing simulations for security awareness.

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is DevSecOps and why has it become important?
A: DevSecOps integrates security practices into the DevOps software development
   and delivery lifecycle. The "Sec" is placed in the middle to emphasize that
   security is not a separate stage — it's continuous.
   
   Why it's become important:
   
   1. Speed of delivery: Modern teams release multiple times per day.
      Traditional "security review before release" creates a bottleneck.
      DevSecOps automates security checks so they run at CI/CD speed.
   
   2. Supply chain attacks increased: Attackers now target developer tools,
      build pipelines, and open source dependencies.
      (SolarWinds, Log4Shell, XZ Utils attacks)
      SCA tools continuously monitor dependencies.
   
   3. Cloud-native complexity: Kubernetes, Terraform, microservices — more
      attack surface, more configuration, more places for mistakes.
      IaC scanning, K8s policy enforcement now essential.
   
   4. Regulatory compliance: GDPR, PCI-DSS, HIPAA require ongoing security
      controls, not just point-in-time reviews.
   
   5. Cost of late discovery: Security bugs found in production cost 30-100x
      more to fix than those caught during development.
   
   DevSecOps key practices:
   - Automated SAST, SCA, container scanning in every PR/build
   - Secrets management (Vault, never in code)
   - Policy as code (OPA, Kyverno, Sentinel)
   - Runtime security monitoring (Falco)

Q2: How would you implement security scanning in a CI/CD pipeline?
A: A layered security pipeline with checks at each stage:
   
   Pull Request (fast, developer feedback):
   - Secret scanning: TruffleHog or detect-secrets on changed files
     Blocks merge if secrets found
   - SAST: Semgrep rules on changed files (fast, incremental)
     Report as PR comments (don't block on warnings, block on criticals)
   - SCA: Snyk or Dependabot on package manifest changes
     Block if critical CVE in new dependency
   
   CI Build (every commit to main):
   - Full SAST scan (SonarQube or Semgrep)
   - Container image build → Trivy scan:
     trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest
     Block build if HIGH/CRITICAL unfixed CVEs
   - IaC scan: checkov on all Terraform files
     Block if critical IaC misconfigurations
   
   Pre-Production:
   - DAST: OWASP ZAP scan against staging environment
     Fails build if active exploitable issues found
   - Compliance check: OPA/Conftest policies for your framework
   
   Production (continuous):
   - Runtime: Falco for anomaly detection
   - AWS Inspector / Snyk for continuous container re-scanning
   
   Key decisions:
   - What severity BLOCKS vs REPORTS: Start with only CRITICAL blocking.
     Expand to HIGH once your baseline is clean.
   - Don't scan legacy code without a plan: Suppress findings for known issues,
     add to backlog, fix systematically.

Q3: What is the OWASP Top 10 and which items are most commonly exploited?
A: OWASP Top 10 is the standard reference for web application security risks:
   
   A01: Broken Access Control (most common/dangerous today)
        Users accessing resources they shouldn't. Missing authorization checks.
        Example: Changing user_id in API request to access another user's data.
        Prevention: RBAC, object-level authorization checks, deny by default.
   
   A02: Cryptographic Failures
        Using weak encryption, storing passwords in plaintext, SSL misconfiguration.
        Prevention: bcrypt for passwords, AES-256, TLS 1.2+, never roll your own crypto.
   
   A03: Injection (SQL, OS command, LDAP)
        Classic attack — unsanitized input executed as code.
        Prevention: Parameterized queries, input validation, ORMs.
   
   A04: Insecure Design
        Missing security controls at the design level.
        Prevention: Threat modeling, security requirements in design phase.
   
   A05: Security Misconfiguration
        Default credentials, open S3 buckets, unnecessary services running.
        Prevention: IaC with security scanning (tfsec, checkov), hardened base images.
   
   A06: Vulnerable and Outdated Components (SCA targets this)
        Using libraries with known CVEs (Log4Shell is a perfect example).
        Prevention: Automated SCA scanning, dependency update automation.
   
   A07: Authentication/ID Failures
        Broken login, weak password policies, exposed session tokens.
        Prevention: Multi-factor auth, strong session management, OTel logging.
   
   A08: Software and Data Integrity Failures (new in 2021 — supply chain)
        Untrusted CI/CD pipelines, unverified packages, auto-update attacks.
        Prevention: Sign commits, verify package checksums, SBOM.
   
   A09: Security Logging and Monitoring Failures
        Inability to detect breaches, insufficient log detail for forensics.
        Prevention: Comprehensive audit logging, SIEM, alert on suspicious activity.
   
   A10: Server-Side Request Forgery (SSRF)
        App fetches remote resource without validating user-supplied URL.
        Attacker redirects to internal services (AWS metadata: 169.254.169.254).
        Prevention: Allowlist external URLs, block requests to internal ranges.
   
   Most commonly exploited in practice: A01 (access control), A03 (injection),
   A05 (misconfiguration), A06 (vulnerable dependencies).

Q4: How do you handle secrets securely in a DevOps pipeline?
A: Secrets management is a layered problem. Key principles:
   
   1. Never store secrets in source code:
      - Use environment variables, not hardcoded values
      - Pre-commit hooks with detect-secrets or gitleaks block commits
      - GitHub Secret Scanning (built-in, free) alerts on leaked secrets
   
   2. Use a secrets manager:
      HashiCorp Vault: Enterprise-grade, dynamic secrets, lease-based
      AWS Secrets Manager: Native AWS, automatic rotation, IAM access control
      Azure Key Vault, GCP Secret Manager: Cloud-native equivalents
   
   3. In Kubernetes:
      Don't use K8s Secrets directly (base64 is NOT encryption).
      Use External Secrets Operator: Pulls secrets from Vault/AWS SM at runtime.
      Or: Sealed Secrets (encrypt with public key, only cluster can decrypt).
      Or: SOPS (encrypt secret files in Git, decrypt at deploy time).
   
   4. In CI/CD pipelines:
      Use CI-native secrets (GitHub Actions secrets, GitLab CI/CD variables).
      Secrets injected as environment variables at runtime.
      NEVER print secrets in logs: mask them (GitHub Actions masks automatically).
   
   5. Least privilege:
      CI pipeline should only have secrets it actually needs.
      Use OIDC instead of long-lived keys: pipeline gets short-lived token via OIDC
      (no keys stored anywhere — GitHub Actions → AWS OIDC).
   
   If a secret is leaked:
   - ROTATE IMMEDIATELY (before worrying about audit trail)
   - Revoke the old credential
   - Remove from Git history: git-filter-repo (don't use git filter-branch)
   - Audit: Did anyone use the leaked credential? (CloudTrail, audit logs)

Q5: What is Falco and how does it enhance Kubernetes security?
A: Falco is an open-source runtime security tool from Sysdig (now CNCF).
   It monitors system calls and K8s audit events, detecting anomalous behavior.
   
   How it works:
   - Runs as a DaemonSet on every K8s node
   - Uses eBPF (or kernel module) to capture syscalls
   - Evaluates syscalls against rules
   - Alerts/responds when rules match
   
   What Falco detects:
   - Container running in privileged mode (unexpected)
   - Shell spawned inside a container (kubectl exec into running pod)
   - File system writes in unexpected locations
   - Unexpected outbound network connections
   - Process trying to read /etc/shadow or /etc/kubernetes/admin.conf
   - Pod trying to read AWS metadata endpoint (instance profile stealing)
   
   Example Falco rules:
   - rule: Terminal shell in container
     desc: Container has shell (exec into pod detected)
     condition: spawned_process and container and shell_procs
     output: "Shell spawned in container (user=%user.name, container=%container.name, cmd=%proc.cmdline)"
     priority: WARNING
   
   - rule: Write below binary dir
     desc: File write to /bin /sbin /usr/bin (potential backdoor)
     condition: open_write and container and (fd.name startswith /bin or fd.name startswith /usr/bin)
     output: "Write below binary dir (file=%fd.name container=%container.name)"
     priority: ERROR
   
   Falco response options:
   - Alert to Slack/PagerDuty
   - Generate K8s audit events
   - Terminate the offending container (via Falco Sidekick)
   
   Key value: Even if an attacker bypasses all preventive controls, Falco detects
   the attack at runtime — like an intrusion detection system (IDS) for containers.
