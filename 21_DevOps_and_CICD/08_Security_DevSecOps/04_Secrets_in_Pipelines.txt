1. WHY SECRETS IN PIPELINES ARE HARD
================================================================================

The Secret Sprawl Problem:
  Secrets multiply as a system grows:
  - Local developer .env files
  - CI/CD environment variables (GitHub Actions, GitLab CI, Jenkins)
  - Kubernetes Secrets (base64-encoded, not encrypted)
  - Docker build args (can leak into image layers)
  - Terraform state files (contain DB passwords, API keys)
  - Cloud provider credentials (long-lived access keys)
  - Third-party service tokens (Slack webhooks, PagerDuty, Datadog)

How Secrets Leak:
  1. Committed to Git directly (most common)
  2. Printed in CI/CD logs (echo $SECRET or error messages)
  3. Stored in Docker image layers:
     # WRONG — password in layer even if deleted later:
     RUN export DB_PASS=mysecret && ./install.sh && unset DB_PASS
  4. In Terraform state files (stored plaintext in S3 by default)
  5. In environment variables visible to all processes (ps aux)
  6. In K8s pod specs (env.value instead of env.valueFrom.secretKeyRef)

Detection → Response → Prevention Workflow:
  Detect:   Secret scanning in PRs and on git history
  Respond:  Rotate immediately, audit access logs, assess exposure
  Prevent:  Pre-commit hooks, CI enforcement, education

2. SECRET DETECTION TOOLS (DEEP DIVE)
================================================================================

TruffleHog v3:
  Most effective for finding real secrets (not just patterns).
  Uses entropy analysis AND pattern matching.
  --only-verified flag: only reports secrets that actually authenticate.
  
  # Scan repo history:
  trufflehog git https://github.com/myorg/myrepo --only-verified
  
  # Scan local repo:
  trufflehog git file://. --only-verified
  
  # Scan a single commit:
  trufflehog git file://. --since-commit HEAD~1 --only-verified
  
  # Scan a Docker image:
  trufflehog docker --image myrepo/myapp:latest --only-verified
  
  # GitHub Actions integration:
  - name: TruffleHog scan
    uses: trufflesecurity/trufflehog@main
    with:
      path: ./
      base: ${{ github.event.repository.default_branch }}
      head: HEAD
      extra_args: --only-verified

Gitleaks:
  Fast, configurable, regex + entropy based.
  Widely used in CI/CD pipelines.
  
  # Scan staged changes (pre-commit):
  gitleaks protect --staged
  
  # Scan repo history (full):
  gitleaks detect --source . --report-path gitleaks-report.json
  
  # Custom config (.gitleaks.toml):
  [extend]
  useDefault = true           # use built-in rules as base
  
  [[rules]]
  id = "myapp-api-key"
  description = "MyApp internal API key"
  regex = '''myapp_[a-zA-Z0-9]{32}'''
  entropy = 3.5
  
  [allowlist]
  description = "Known safe values"
  regexes = ['''EXAMPLE_API_KEY''', '''test_key_placeholder''']
  paths = ["test/fixtures/"]

detect-secrets (Yelp):
  Baseline-based approach.
  Creates a baseline of known/approved secrets to avoid false positives.
  
  # Create baseline (first time):
  detect-secrets scan > .secrets.baseline
  
  # Check new content against baseline:
  detect-secrets scan --baseline .secrets.baseline
  
  # Audit: mark false positives as approved:
  detect-secrets audit .secrets.baseline
  
  # pre-commit hook config (.pre-commit-config.yaml):
  repos:
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
    - id: detect-secrets
      args: ['--baseline', '.secrets.baseline']

3. GITHUB ACTIONS SECRETS & OIDC
================================================================================

GitHub Actions — Secrets Management:
  Levels:
  - Repository secrets: Available to all workflows in the repo
  - Environment secrets: Available only when deploying to a named environment
  - Organization secrets: Shared across multiple repos
  
  Environments (critical for deployment gating):
  # .github/workflows/deploy.yml:
  jobs:
    deploy-production:
      environment: production     # ← requires approval from reviewers
      runs-on: ubuntu-latest
      steps:
      - name: Deploy
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}  # environment-scoped secret
        run: ./deploy.sh

OIDC — The Right Way to Authenticate to AWS/GCP/Azure:
  No long-lived credentials stored as GitHub secrets.
  GitHub generates a short-lived JWT for each workflow run.
  Cloud provider validates it and grants temporary credentials.
  
  # GitHub Actions → AWS (OIDC):
  permissions:
    id-token: write     # required for OIDC
    contents: read
  
  jobs:
    deploy:
      runs-on: ubuntu-latest
      steps:
      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/GitHubActionsRole
          aws-region: us-east-1
      
      - name: Use AWS (no secrets needed)
        run: aws s3 ls s3://my-bucket
  
  # IAM Trust Policy (allows GitHub → AWS):
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::123456789:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:myorg/myrepo:environment:production"
        }
      }
    }]
  }
  # ↑ The sub condition scopes to a specific environment — critical for security

4. GITLAB CI & JENKINS SECRETS
================================================================================

GitLab CI Variables:
  Types:
  - Variable: Regular environment variable (value masked in logs)
  - File: Writes value to a temp file, injects file path as variable
        Useful for: SSH keys, service account JSON files, certificates
  
  # Using a file-type variable (e.g., GCP service account):
  deploy:
    script:
    - gcloud auth activate-service-account --key-file=$GCP_SA_KEY  # GCP_SA_KEY = file path

  Protected variables: Only available in protected branches/tags.
  Masked variables: Value never shown in job logs (requires format restrictions).

GitLab CI → Vault integration:
  # .gitlab-ci.yml:
  deploy:
    image: hashicorp/vault:latest
    script:
    - vault login -method=jwt jwt=$CI_JOB_JWT vault_addr=$VAULT_ADDR
    - export DB_PASS=$(vault kv get -field=password secret/myapp/db)
    - ./deploy.sh

Jenkins Credentials Plugin:
  Stores secrets in Jenkins credentials store (encrypted at rest).
  Types: Username+Password, Secret text, SSH key, Certificate, File
  
  # Jenkinsfile:
  pipeline {
    agent any
    stages {
      stage('Deploy') {
        steps {
          withCredentials([
            string(credentialsId: 'my-api-key', variable: 'API_KEY'),
            usernamePassword(
              credentialsId: 'prod-db',
              usernameVariable: 'DB_USER',
              passwordVariable: 'DB_PASS'
            )
          ]) {
            sh './deploy.sh'
          }
          // API_KEY and DB_PASS are unset after the withCredentials block
        }
      }
    }
  }

5. HASHICORP VAULT (ADVANCED)
================================================================================

Vault Authentication Methods:
  
  AppRole (for CI/CD pipelines):
    Machine-to-machine auth without human interaction.
    RoleID is not secret (like a username).
    SecretID is secret (like a password, has TTL and usage limits).
    
    # Create AppRole:
    vault auth enable approle
    vault write auth/approle/role/myapp-ci \
      token_policies="myapp-policy" \
      token_ttl=1h \
      secret_id_num_uses=1 \       # SecretID single-use (prevents replay)
      secret_id_ttl=30m
    
    # Get RoleID (static, embed in pipeline config):
    vault read auth/approle/role/myapp-ci/role-id
    
    # Get SecretID (generate fresh each pipeline run):
    vault write -f auth/approle/role/myapp-ci/secret-id
    
    # Authenticate:
    vault write auth/approle/login role_id=$ROLE_ID secret_id=$SECRET_ID
  
  Kubernetes Auth Method:
    Pods authenticate using their ServiceAccount JWT.
    Vault verifies the JWT with the K8s API server.
    
    # Enable K8s auth:
    vault auth enable kubernetes
    vault write auth/kubernetes/config \
      kubernetes_host=https://kubernetes.default.svc \
      kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
    
    # Create role binding K8s ServiceAccount → Vault policy:
    vault write auth/kubernetes/role/myapp \
      bound_service_account_names=myapp-sa \
      bound_service_account_namespaces=production \
      policies=myapp-policy \
      ttl=1h

Vault Policies (HCL):
  # myapp-policy.hcl:
  path "secret/data/myapp/*" {
    capabilities = ["read"]
  }
  
  path "database/creds/myapp-role" {
    capabilities = ["read"]
  }
  
  # DENY access to admin paths:
  path "sys/*" {
    capabilities = ["deny"]
  }
  
  # Apply policy:
  vault policy write myapp-policy myapp-policy.hcl

6. AWS SECRETS MANAGER (ADVANCED)
================================================================================

Automatic Secret Rotation:
  AWS Secrets Manager can rotate secrets automatically using Lambda.
  Supports built-in rotation for RDS, Redshift, DocumentDB.
  
  # Create secret with rotation:
  aws secretsmanager create-secret \
    --name prod/myapp/db-password \
    --secret-string '{"username":"dbuser","password":"initial-password"}'
  
  # Enable automatic rotation (built-in RDS Lambda):
  aws secretsmanager rotate-secret \
    --secret-id prod/myapp/db-password \
    --rotation-lambda-arn arn:aws:lambda:us-east-1:123456789:function:SecretsManagerRDSRotation \
    --rotation-rules AutomaticallyAfterDays=30
  
  # The rotation Lambda follows a 4-step process:
  # createSecret → setSecret → testSecret → finishSecret

Retrieving Secrets in Applications:
  # Python (boto3):
  import boto3, json
  
  client = boto3.client('secretsmanager', region_name='us-east-1')
  response = client.get_secret_value(SecretId='prod/myapp/db-password')
  secret = json.loads(response['SecretString'])
  db_password = secret['password']
  
  # Best practice: cache with TTL, don't call on every request:
  from functools import lru_cache
  from datetime import datetime, timedelta
  
  _secret_cache = {}
  def get_secret(secret_id, ttl_minutes=5):
      cached = _secret_cache.get(secret_id)
      if cached and datetime.now() < cached['expiry']:
          return cached['value']
      value = fetch_from_aws(secret_id)
      _secret_cache[secret_id] = {
          'value': value,
          'expiry': datetime.now() + timedelta(minutes=ttl_minutes)
      }
      return value

7. SOPS + AGE ENCRYPTION FOR GITOPS
================================================================================

What is SOPS?
  SOPS = Secrets OPerationS (Mozilla).
  Encrypts specific values inside structured files (YAML, JSON, ENV, INI).
  Keys remain readable; only values are encrypted.
  Integrates with AWS KMS, GCP KMS, Azure Key Vault, PGP, and Age.
  Perfect for storing secrets in Git (GitOps approach).

Age (Modern Encryption):
  Simple, fast, modern alternative to PGP.
  No key management complexity of GPG.
  
  # Install age:
  brew install age
  
  # Generate key pair:
  age-keygen -o ~/.age/key.txt
  # Public key: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p
  
  # .sops.yaml configuration:
  creation_rules:
  - path_regex: k8s/.*\.yaml$
    age: >-
      age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p,
      age1p4uzhezkktq32... # CI/CD pipeline key
  
  - path_regex: terraform/.*\.tfvars$
    kms:
    - arn: arn:aws:kms:us-east-1:123456789:key/abc123

SOPS Workflow:
  # Encrypt a file:
  sops --encrypt secrets.yaml > secrets.enc.yaml
  # Or in-place:
  sops --encrypt --in-place secrets.yaml
  
  # Decrypt to use:
  sops --decrypt secrets.enc.yaml
  
  # Edit encrypted file (SOPS decrypts, opens editor, re-encrypts on save):
  sops secrets.enc.yaml
  
  # What the encrypted file looks like:
  # Before:
  apiVersion: v1
  kind: Secret
  data:
    password: mysecretpassword
  
  # After sops --encrypt:
  apiVersion: v1
  kind: Secret
  data:
      password: ENC[AES256_GCM,data:abc123==,iv:xyz==,tag:zzz==,type:str]
  sops:
      age:
      - recipient: age1ql3...
        enc: |
            -----BEGIN AGE ENCRYPTED FILE-----
            ...

SOPS + FluxCD:
  FluxCD has native SOPS support.
  
  # flux-system/kustomization.yaml:
  apiVersion: kustomize.toolkit.fluxcd.io/v1
  kind: Kustomization
  metadata:
    name: production
    namespace: flux-system
  spec:
    decryption:
      provider: sops
      secretRef:
        name: sops-age   # K8s secret containing age private key

8. SEALED SECRETS (BITNAMI)
================================================================================

What are Sealed Secrets?
  Kubernetes-native secret management for GitOps.
  
  Architecture:
  - SealedSecret controller runs in K8s cluster
  - kubeseal CLI encrypts secrets using cluster's public key
  - Encrypted SealedSecret objects are safe to commit to Git
  - Controller decrypts and creates regular K8s Secrets
  
  ┌─────────────────────────────────────────────────────┐
  │  Developer                                          │
  │  kubectl create secret --dry-run -o yaml |         │
  │  kubeseal > sealed-secret.yaml                     │
  │        │                                           │
  │        v                                           │
  │  sealed-secret.yaml committed to Git               │
  │        │                                           │
  │        v                                           │
  │  ArgoCD/Flux applies sealed-secret.yaml to cluster │
  │        │                                           │
  │        v                                           │
  │  Sealed Secrets Controller decrypts → K8s Secret  │
  └─────────────────────────────────────────────────────┘

kubeseal Usage:
  # Install Sealed Secrets controller:
  helm install sealed-secrets sealed-secrets/sealed-secrets \
    -n kube-system --set fullnameOverride=sealed-secrets-controller
  
  # Seal a secret:
  kubectl create secret generic myapp-db \
    --from-literal=password=mysecretpassword \
    --dry-run=client -o yaml | \
    kubeseal --format yaml > sealed-myapp-db.yaml
  
  # The SealedSecret YAML (safe to commit to Git):
  apiVersion: bitnami.com/v1alpha1
  kind: SealedSecret
  metadata:
    name: myapp-db
    namespace: production
  spec:
    encryptedData:
      password: AgBy3i4OJSWK+PiTySYZZA9rO43c...
    template:
      type: Opaque
  
  # Backup master key (IMPORTANT! keep safe):
  kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key \
    -o yaml > sealed-secrets-master-key.yaml
  # Store this backup in a secure vault — losing it = losing all secrets!

9. SECRET ROTATION WITHOUT DOWNTIME
================================================================================

Blue/Green Secret Rotation:
  Run two versions of the secret simultaneously.
  Applications can use either version.
  Rotate gradually without downtime.
  
  Step-by-step:
  1. Current state: app uses db_password_v1
  2. Create db_password_v2 (new password set in DB)
  3. Update DB to accept BOTH v1 and v2 (DB supports multiple passwords for same user)
  4. Deploy app with new config → uses db_password_v2
  5. Wait for all instances to roll over
  6. Revoke db_password_v1 in DB
  7. Delete v1 from secrets manager

Database Credential Rotation (Vault Dynamic Secrets):
  Best rotation strategy — never manually rotate.
  Vault generates unique credentials per app instance with TTL.
  After TTL expires, credentials are automatically revoked.
  
  # Vault database engine:
  vault secrets enable database
  
  vault write database/config/myapp-postgres \
    plugin_name=postgresql-database-plugin \
    connection_url="postgresql://{{username}}:{{password}}@postgres:5432/myapp" \
    allowed_roles="myapp-role" \
    username="vault-admin" \
    password="admin-password"
  
  vault write database/roles/myapp-role \
    db_name=myapp-postgres \
    creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN ENCRYPTED PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT,INSERT,UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
    default_ttl=1h \
    max_ttl=24h
  
  # Application gets unique creds:
  vault read database/creds/myapp-role
  # Key              Value
  # username         v-app-abc123
  # password         A1a-xxxxxxxx
  # lease_duration   1h
  # (Auto-revoked after 1h. App must renew or re-request.)

  # Vault audit logs → SIEM:
  # Use Filebeat or Fluent Bit to ship logs to Elasticsearch/Splunk

AWS CloudTrail for Secrets Manager:
  All AWS Secrets Manager API calls logged in CloudTrail.
  Key events to alert on:
  - GetSecretValue (by unexpected principals)
  - DeleteSecret (any deletion)
  - PutSecretValue (unexpected updates)
  
  # CloudWatch alarm for GetSecretValue by non-app principal:
  aws cloudwatch put-metric-alarm \
    --alarm-name UnauthorizedSecretAccess \
    --metric-name UnauthorizedAttempts \
    --namespace AWS/SecretsManager \
    --comparison-operator GreaterThanThreshold \
    --threshold 0 \
    --evaluation-periods 1

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: How do you prevent secrets from being committed to Git?
A: Multi-layer defense:
   
   Pre-commit (developer machine):
   - Install pre-commit framework: https://pre-commit.com
   - Configure gitleaks or detect-secrets as pre-commit hook
   - Hook runs before every `git commit`, blocks if secrets found
   
   Pull Request (CI/CD):
   - TruffleHog or Gitleaks scans diff on every PR
   - Fail the PR check if secrets detected
   - Scan is mandatory — can't be bypassed by developers
   
   Git history scanning (weekly):
   - Full repo history scan with TruffleHog --only-verified
   - Catches secrets that slipped through or were added before hooks existed
   
   Branch protection:
   - Require all status checks to pass before merge
   - This enforces the CI secret scan as a gate
   
   Culture and education:
   - Onboarding: "Never commit secrets, use env variables and secrets managers"
   - Incident response playbook: "If you think you leaked a secret, rotate it NOW"

Q2: Compare SOPS vs Sealed Secrets for GitOps secret management.
A: Both allow storing encrypted secrets in Git — but different approaches.
   
   Sealed Secrets:
   - Kubernetes-native: creates actual K8s Secret resources
   - Encryption tied to specific K8s cluster (cluster's keypair)
   - Can't decrypt outside the cluster
   - Simpler developer workflow: just use kubeseal CLI
   - Risk: if cluster is destroyed and master key is lost, all secrets are lost
   - Best for: single K8s cluster, team prefers simple tooling
   
   SOPS:
   - Cloud-native: works with KMS, doesn't depend on K8s
   - Can use same key across multiple environments
   - Secrets can be decrypted locally for debugging (with correct key access)
   - Works for non-K8s secrets too (Terraform tfvars, app configs)
   - More complex: requires SOPS + age/KMS setup
   - Best for: multi-cluster, multi-environment, GitOps with FluxCD

Q3: A junior engineer accidentally committed an AWS Access Key to GitHub. Walk me through your response.
A: Immediate triage:
   1. Confirm exposure: Is the repo public or private? Public = immediate critical risk.
   2. ROTATE NOW — revoke the old key immediately. Before doing anything else.
      aws iam delete-access-key --access-key-id AKIAIOSFODNN7EXAMPLE
   3. Assess blast radius:
      - Check AWS CloudTrail: what API calls were made with that key after the commit?
      - Check GitHub audit log: when was the commit pushed? How long was it public?
      - Look at what the key had permissions to do (IAM policy attached)
   4. Issue new key if needed (prefer IAM roles/OIDC — no long-lived keys)
   5. Remove from Git history:
      git filter-repo --invert-paths --path path/to/file-with-secret
      git push origin --force --all
      (Or use BFG Repo-Cleaner for large repos)
   6. Notify: If data was accessed, follow your incident response and breach notification process.
   7. Post-mortem: Why did pre-commit hooks not catch this? Fix the gap.

SECRET MANAGEMENT TOOLS BY USE CASE:
  Pre-commit scanning:   gitleaks, detect-secrets, trufflehog
  CI/CD scanning:        trufflehog (--only-verified), gitleaks detect
  Runtime secrets:       Vault, AWS Secrets Manager, External Secrets Operator
  GitOps K8s secrets:    Sealed Secrets (kubeseal) or SOPS + FluxCD
  GitOps non-K8s:        SOPS + Age/KMS

VAULT AUTH METHODS:
  approle:     For CI/CD pipelines (RoleID + SecretID)
  kubernetes:  For pods (ServiceAccount JWT)
  jwt/oidc:    For GitHub Actions (OIDC)
  userpass:    For developers (interactive)

GITLEAKS COMMANDS:
  gitleaks protect --staged          Pre-commit check
  gitleaks detect --source .         Scan repo history
  gitleaks detect -r report.json     With JSON report

SECRET ROTATION STRATEGY:
  1. Generate new secret (v2)
  2. Update service to accept both v1 and v2
  3. Deploy apps with v2
  4. Revoke v1
  Best with: Vault dynamic secrets (no manual rotation needed)
