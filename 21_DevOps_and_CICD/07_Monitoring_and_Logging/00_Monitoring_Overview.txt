1. WHY MONITORING MATTERS
================================================================================

Without monitoring:
  - You learn about outages from customers (too late)
  - No visibility into resource utilization (waste or under-provisioning)
  - Debugging takes hours or days (no data to correlate)
  - No capacity planning data (scaling decisions are guesses)
  - Compliance/audit requirements unmet

With monitoring:
  - Proactive detection before user impact
  - Data-driven scaling and capacity planning
  - Fast incident resolution (MTTR reduction)
  - SLA evidence for customers
  - Performance trend analysis

MTTR and MTTD:
  MTTD  Mean Time To Detect    — How long until you know something is broken
  MTTR  Mean Time To Recover   — How long to resolve after detection
  MTTF  Mean Time To Failure   — How long between failures
  MTBF  Mean Time Between Failures = MTTF + MTTR

2. THE THREE PILLARS OF OBSERVABILITY
================================================================================

Observability (from control theory): 
  A system is observable if you can understand its internal state
  from its external outputs.
  
  ┌─────────────────────────────────────────────────────────────┐
  │                   OBSERVABILITY                              │
  │                                                              │
  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐  │
  │  │   METRICS    │  │    LOGS      │  │     TRACES       │  │
  │  │              │  │              │  │                  │  │
  │  │ Aggregated   │  │ Timestamped  │  │ Request path     │  │
  │  │ numbers over │  │ events with  │  │ across services  │  │
  │  │ time         │  │ context      │  │                  │  │
  │  │              │  │              │  │                  │  │
  │  │ "What"       │  │ "Why"        │  │ "Where"          │  │
  │  └──────────────┘  └──────────────┘  └──────────────────┘  │
  │        │                  │                   │             │
  │   Prometheus          ELK / Loki         Jaeger / Tempo    │
  │   Grafana             Splunk             OpenTelemetry     │
  └─────────────────────────────────────────────────────────────┘

Monitoring vs Observability:
  Monitoring: Pre-defined dashboards and alerts on KNOWN failure modes.
              "Alert when CPU > 90%"
  
  Observability: Ability to ask NEW questions about the system state.
                 "Why is this specific user's request slow?"
  
  Monitoring tells you WHEN something is wrong.
  Observability tells you WHY.

3. METRICS VS LOGS VS TRACES
================================================================================

Metrics:
  Numerical measurements over time. Aggregated, sampled.
  
  Types:
  Counter    Monotonically increasing value (total requests, total errors)
  Gauge      Value that goes up and down (current connections, memory usage)
  Histogram  Distribution of values in buckets (request latency distribution)
  Summary    Like histogram, calculates quantiles client-side
  
  Examples:
  http_requests_total{method="GET", status="200"}  = 14523  (counter)
  process_resident_memory_bytes                     = 892928 (gauge)
  http_request_duration_seconds_bucket{le="0.5"}   = 4523   (histogram bucket)
  
  Best for: Alerting, dashboards, capacity planning, SLO tracking.
  Storage: Efficient — one number per metric per time interval.

Logs:
  Timestamped records of events. Human-readable (or JSON).
  
  Structured log (JSON — preferred):
  {
    "timestamp": "2024-01-15T10:23:45Z",
    "level": "ERROR",
    "service": "payment-service",
    "trace_id": "abc123",
    "user_id": "user_456",
    "message": "Payment failed",
    "error": "connection timeout",
    "retry_count": 3
  }
  
  Unstructured (harder to parse):
  2024-01-15 10:23:45 ERROR payment-service: Payment failed for user 456
  
  Best for: Debugging, root cause analysis, audit trails.
  Storage: Expensive at high volume (compress + rotate).

Traces:
  Track a single request across multiple services.
  Each request has a Trace ID. Each service hop is a Span.
  
  Anatomy:
  Trace ID: abc123
  
  ├── Span: API Gateway (50ms)
  │   └── Span: auth-service.validateToken (10ms)
  ├── Span: payment-service.processPayment (200ms)
  │   ├── Span: database.query (150ms)  ← slow!
  │   └── Span: notification-service.send (30ms)
  └── Total: 260ms
  
  Best for: Distributed system debugging, latency root cause, service dependency mapping.

4. MONITORING TYPES
================================================================================

Infrastructure Monitoring:
  CPU, memory, disk, network — at host/container/pod level.
  Tools: Prometheus + Node Exporter, Datadog, CloudWatch.

Application Performance Monitoring (APM):
  Code-level performance: slow functions, DB queries, external calls.
  Distributed tracing, error rates, response time percentiles.
  Tools: Datadog APM, New Relic, Dynatrace, Jaeger (open source).

Synthetic Monitoring:
  Probes that simulate user actions from external locations.
  "Can a user in Tokyo reach our login page in under 2s?"
  Tools: Pingdom, Datadog Synthetics, AWS CloudWatch Synthetics.

Real User Monitoring (RUM):
  Collect performance data from ACTUAL user browsers.
  Page load times, JS errors, clicks, navigation paths.
  Tools: Datadog RUM, New Relic Browser, Sentry.

Business Monitoring:
  Track business KPIs alongside technical metrics.
  Orders per minute, checkout success rate, revenue per hour.
  Often built on top of application metrics.

5. GOLDEN SIGNALS (SRE)
================================================================================

Google SRE's four golden signals (from the SRE book):
  
  1. LATENCY
     Time to service a request.
     IMPORTANT: Track FAILED request latency separately from successful.
     A 5xx that returns in 1ms can hide real latency issues.
     
     Metrics: p50, p95, p99, p999 response time
     Example: 99th percentile response time for checkout endpoint

  2. TRAFFIC
     Demand on your system.
     Requests per second, active connections, transactions per minute.
     
     Metrics: http_requests_total (rate over time window)
     Example: 1200 requests/sec at peak

  3. ERRORS
     Rate of requests that fail.
     Include: HTTP 5xx, HTTP 4xx (for user errors), timeouts, partial failures.
     
     Metrics: error rate = errors / total requests
     Example: 0.1% error rate

  4. SATURATION
     How "full" a service is. Resource utilization.
     CPU, memory, disk I/O, network bandwidth, queue depth.
     Often predictive — saturation increases before failures occur.
     
     Metrics: CPU utilization %, queue depth, connection pool usage
     Example: DB connection pool at 85% = near saturation

USE Method (Brendan Gregg — for resources):
  Utilization, Saturation, Errors — for each resource (CPU, memory, disk, network).

RED Method (Tom Wilkie — for services):
  Rate, Errors, Duration — for each service/endpoint.

6. SLI, SLO, AND SLA
================================================================================

SLI — Service Level Indicator:
  A quantitative measure of service behavior.
  The METRIC that represents quality.
  
  Examples:
  - % of HTTP requests returning 2xx in last 5 minutes
  - % of requests completing in under 200ms
  - % of successful login attempts
  - % of messages processed within 30 seconds

SLO — Service Level Objective:
  A TARGET value for an SLI.
  The GOAL your team commits to internally.
  
  Examples:
  - 99.9% of requests return 200 in last 30 days (availability SLO)
  - 95% of requests complete in < 200ms (latency SLO)
  - 99.5% of messages processed in < 30s
  
  Error Budget:
  If SLO is 99.9% availability → 0.1% error budget
  In 30 days (720 hours) → 43.2 minutes of downtime allowed
  
  When error budget is exhausted:
  - STOP new feature development
  - Focus on reliability improvements
  
  When error budget has headroom:
  - Use it for faster releases, experiments, taking risks

SLA — Service Level Agreement:
  A CONTRACTUAL COMMITMENT to customers.
  Usually LESS strict than your SLO (you need a buffer).
  Breaking an SLA has financial consequences (service credits, penalties).
  
  Example: SLO = 99.95%, SLA = 99.9% (the gap is your safety buffer)

Relationship:
  SLI (measurement) → SLO (internal goal) → SLA (customer contract)

7. ALERTING BEST PRACTICES
================================================================================

Alert on SLO breach (not thresholds):
  Bad:  "Alert when CPU > 80%" → noisy, not customer-impacting
  Good: "Alert when error rate exceeds SLO budget consumption rate"
        "Alert when p99 latency > 500ms for 5 consecutive minutes"

Alert on Symptoms, Not Causes:
  Symptom: Users can't checkout (payment service down)
  Cause:   Database CPU at 100%
  
  Alert on the SYMPTOM (user-facing impact).
  Alert on the CAUSE only if it consistently precedes the symptom.

Page vs Ticket:
  Page (wake someone up at 3am):  Customer impact is happening NOW.
  Ticket (work during business hours): Trend that may cause issue in days.

Alert Fatigue:
  Too many alerts → engineers ignore them → real outage missed.
  Every alert should be ACTIONABLE.
  If you can't describe what action to take → delete the alert.
  
  Alert properties:
  1. Actionable — someone can do something about it
  2. Relevant — customer-impacting or leading indicator
  3. Calibrated — threshold chosen based on data, not guesses
  4. Documented — runbook linked in alert

Runbooks:
  Document for EACH alert:
  - What is alerting
  - What impact users are experiencing
  - Steps to diagnose
  - Steps to mitigate
  - Steps to resolve
  - Escalation path

Dead Man's Switch:
  Alert that fires when something STOPS happening (monitoring breaks).
  "Alert if I haven't received a heartbeat from the monitoring agent in 5 minutes"

================================================================================

Open Source Stack:
  
  Collection:      Prometheus (metrics), Fluentbit/Fluentd (logs), Jaeger (traces)

9. OBSERVABILITY IN KUBERNETES
================================================================================

K8s provides built-in visibility:
  kubectl top nodes / kubectl top pods    Resource utilization
  kubectl describe pod <name>            Events + conditions
  kubectl logs <pod> [-c <container>]    Pod logs
  kubectl get events --sort-by='.lastTimestamp'  Cluster events
  kubectl rollout status deployment/<name>  Rollout progress

kube-prometheus-stack:
  Most common production monitoring setup.
  Installed via Helm, includes:
  - Prometheus (metrics collection + alerting rules)
  - Grafana (dashboards — pre-built for K8s)
  - Alertmanager (routes alerts to Slack, PagerDuty, etc.)
  - Node Exporter (per-node OS metrics)
  - kube-state-metrics (K8s object state as metrics)
  
  helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
  helm install kube-prom-stack prometheus-community/kube-prometheus-stack \
    --namespace monitoring --create-namespace

Key Kubernetes Metrics to Monitor:
  Cluster-level:
  - Node CPU/memory utilization
  - Pod count vs. requested
  - API server latency
  
  Workload-level:
  - Deployment replica desired vs. ready
  - Pod restart count (CrashLoopBackOff)
  - HPA current vs. desired replicas
  
  Application-level:
  - Request rate, error rate, latency (exposed via /metrics)

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What are the three pillars of observability?
A: The three pillars are Metrics, Logs, and Traces — each serves a different purpose.
   
   Metrics: Numerical measurements aggregated over time.
   Counters (total requests), gauges (current memory), histograms (latency distribution).
   Best for: Alerting, dashboards, SLO tracking. Efficient storage.
   Tools: Prometheus, CloudWatch, Datadog.
   
   Logs: Timestamped records of events with context.
   Structured (JSON) logs are searchable and parseable.
   Best for: Root cause analysis, debugging specific incidents.
   Tools: ELK stack, Loki, Splunk.
   
   Traces: Track a single request across multiple microservices.
   Each request has a trace_id; each service hop is a span.
   Shows WHERE time is spent across distributed systems.
   Best for: Latency debugging in microservices, dependency mapping.
   Tools: Jaeger, Zipkin, Tempo, Datadog APM.
   
   How they complement each other:
   Alert on metric → look at logs for that time window → trace the slow request.
   
   Modern tools (Grafana, Datadog) link all three: metric spike → correlate logs → find trace.

Q2: What are the Google Golden Signals?
A: The four golden signals from Google's SRE book:
   
   1. Latency: Time to service a request. Track error latency separately.
      Use percentiles (p99) not averages — averages hide tail latency.
   
   2. Traffic: Demand on the system. Requests per second, transactions per minute.
      Understand your normal pattern to detect anomalies.
   
   3. Errors: Rate of failed requests. 5xx, timeouts, business logic errors.
      Even a 0.1% error rate = 1 in 1000 customers affected.
   
   4. Saturation: How "full" the system is. CPU, memory, queue depth.
      Often predictive — saturation rises before failures.
   
   Why these four matter: They cover all meaningful dimensions of service health.
   A service that is fast, handles traffic, has no errors, and isn't saturated = healthy.
   
   Practical application:
   - Alert on all four golden signals
   - Dashboard them for each critical service
   - Tie them to SLOs (error rate < 0.1%, p99 latency < 500ms)

Q3: What is the difference between SLI, SLO, and SLA?
A: They form a hierarchy of service quality definitions:
   
   SLI (Service Level Indicator): The MEASUREMENT.
   A specific metric that represents user-experienced quality.
   "% of requests returning 2xx in the last 5 minutes"
   
   SLO (Service Level Objective): The internal GOAL.
   A target value for an SLI that your team commits to.
   "99.9% of requests return 2xx over a 30-day rolling window"
   
   SLA (Service Level Agreement): The external CONTRACT.
   A commitment to customers, typically less strict than SLO.
   "We commit to 99.5% availability" (with financial penalties if breached)
   
   Why gap between SLO and SLA?
   SLO 99.9% → SLA 99.5% → the 0.4% gap is your safety buffer.
   Your SLO breach doesn't immediately breach the SLA.
   
   Error Budget:
   99.9% SLO = 0.1% error budget = 43.2 minutes downtime per month allowed.
   When budget is spent → stop features, focus on reliability.
   When budget is healthy → ship faster, take risks.
   
   Why this matters in interviews: SLO/error budget aligns developer incentives
   with reliability. Developers get "budget to spend" on risky releases.
   When spent, they're motivated to fix reliability (not just add features).

Q4: What is alert fatigue and how do you prevent it?
A: Alert fatigue occurs when too many alerts cause engineers to ignore or dismiss
   alerts without investigation, eventually missing real incidents.
   
   Causes:
   - Alerts on symptoms that aren't customer-impacting (CPU 80% threshold)
   - Too low thresholds (alert on CPU > 50% — fires constantly)
   - No runbook (engineer doesn't know what to do → dismisses alert)
   - Flapping alerts (resolves/fires repeatedly on boundary)
   - Duplicate alerts (same issue fires multiple alerts)
   
   Prevention:
   
   1. Alert on symptoms, not causes:
      "Payment service error rate > 1% for 5 minutes" = actionable
      "Database CPU > 80%" = noisy, not always customer-impacting
   
   2. Alert on SLO burn rate, not raw thresholds:
      If your SLO is 99.9% availability, alert when you're consuming
      error budget faster than sustainable (e.g., 5x normal burn rate)
   
   3. Every alert must have an action:
      If you can't describe "what do I do when this fires?" → don't alert, use a ticket
   
   4. Add pending period / evaluation window:
      Don't alert on instantaneous spikes (network hiccup)
      Alert when condition is true for 5+ minutes
   
   5. Use severity levels:
      Critical (page on-call): User-impacting, need action now
      Warning (Slack notification): Trending toward issue, investigate today
      Info (ticket): Track, may need attention this week
   
   6. Regular alert reviews:
      Monthly review: Which alerts fired last month? Were they actionable?
      Delete or tune alerts that weren't.

Q5: How would you set up monitoring for a new microservice?
A: I approach this in layers — from infrastructure up to user experience.
   
   1. Infrastructure metrics (automatic with K8s monitoring):
      CPU, memory, network from kube-prometheus-stack / Node Exporter.
      No code changes needed.
   
   2. Application metrics (instrument the code):
      Expose a /metrics endpoint using Prometheus client library.
      Track: request count (counter), request duration (histogram), active connections (gauge).
      
      # Python example:
      from prometheus_client import Counter, Histogram
      REQUEST_COUNT = Counter('http_requests_total', 'Total requests', ['method', 'status'])
      REQUEST_DURATION = Histogram('http_request_duration_seconds', 'Request duration')
      
      # Add ServiceMonitor for Prometheus to scrape:
      apiVersion: monitoring.coreos.com/v1
      kind: ServiceMonitor
      metadata:
        name: my-service
      spec:
        selector:
          matchLabels:
            app: my-service
        endpoints:
        - port: metrics
   
   3. Logs (structured from day 1):
      Emit JSON logs with trace_id, user_id, request_id, level, message.
      Promtail/Fluentbit collects from stdout → Loki/Elasticsearch.
   
   4. Traces:
      Add OpenTelemetry SDK for distributed tracing.
      Auto-instrumentation for HTTP clients, DB calls.
   
   5. Dashboards:
      Golden signals dashboard: rate, errors, duration (RED method)
      Link to logs and traces from dashboard panels.
   
   6. Alerts:
      Alert on error rate > SLO threshold.
      Alert on p99 latency > SLA.
      Alert on pod CrashLoopBackOff.
   
   7. Runbooks:
      Document what each alert means and how to respond.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

THREE PILLARS:
  Metrics    Numbers over time (Prometheus, CloudWatch)
  Logs       Timestamped events (ELK, Loki, Splunk)
  Traces     Request path across services (Jaeger, Tempo, Zipkin)

GOLDEN SIGNALS:
  Latency      Request duration (p99, not average)
  Traffic      Requests per second
  Errors       Error rate (5xx, timeouts)
  Saturation   Resource "fullness" (CPU%, queue depth)

SLI/SLO/SLA:
  SLI    What you measure ("% successful requests")
  SLO    Internal target (99.9% availability)
  SLA    Customer contract (99.5% availability, with penalties)
  Error Budget = 100% - SLO = budget for downtime/risk

METRIC TYPES:
  Counter      Always increases (total requests)
  Gauge        Goes up and down (current connections)
  Histogram    Distribution in buckets (latency per bucket)

ALERTING RULES:
  ✅ Alert on customer-facing symptoms
  ✅ Every alert has a runbook
  ✅ Add pending/evaluation window (avoid flapping)
  ❌ Don't alert on causes without user impact
  ❌ Don't alert on thresholds without customer context
