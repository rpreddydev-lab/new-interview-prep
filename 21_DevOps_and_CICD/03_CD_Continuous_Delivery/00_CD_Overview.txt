1. WHAT IS CONTINUOUS DELIVERY?
================================================================================

Definition:
  Continuous Delivery (CD) is the practice of ensuring that software is always
  in a deployable state. Every change that passes automated tests can be
  released to production at any time — the actual release is a business
  decision, not a technical one.

Jez Humble & David Farley (Book: Continuous Delivery, 2010):
  "Our highest priority is to satisfy the customer through early and continuous
  delivery of valuable software."
  
  CD Goal: "Keep your software in a state where it can be released to production
  at any time, at a cost of pressing a button."

Key Distinction:
  CONTINUOUS DELIVERY:   Can deploy at any time. Deployment is MANUAL decision.
  CONTINUOUS DEPLOYMENT: Every passing change is automatically deployed.

CD extends CI:
  CI: Build + Test code on every commit
  CD: CI + Deploy to production-like environments, validate, enable human deployment

The CD Promise:
  Without CD:
  - Release is a big, scary, infrequent event
  - Weeks of manual testing, coordination, ceremonies
  - High risk = big bang changes
  - Release teams work nights and weekends
  - Low deployment frequency
  
  With CD:
  - Release is a boring, routine, frequent event
  - "If it's painful, do it more often and bring the pain forward"
  - Low risk = small incremental changes
  - Deployment can be done by any developer
  - High deployment frequency (DORA metric)

The Deployment Pipeline:
  The foundation of CD. A deployment pipeline is an automated manifestation of
  your process for getting software from version control to users.
  
  Stages: Commit Stage → Acceptance Stage → Capacity Testing → Production
  
  Commit Stage (CI):
    Compile → Unit Tests → Analysis → Package Artifact
    Fast: < 10 minutes
  
  Acceptance Stage (staging):
    Deploy to staging → Functional Tests → Performance Tests
    Slower: 30 minutes - 2 hours
  
  UAT / Pre-Prod:
    Deploy → Manual/Exploratory Testing → Approval
  
  Production:
    Deploy using chosen strategy → Smoke Tests → Monitor

2. CONTINUOUS DELIVERY VS CONTINUOUS DEPLOYMENT
================================================================================

CONTINUOUS INTEGRATION (CI):
  Scope: Code commit → Tests pass
  Automation: Full
  Frequency: Multiple times per day per developer
  Human gate: None

CONTINUOUS DELIVERY (CD - lower D):
  Scope: CI + Deploy to staging → Validate → Production-READY
  Automation: Automated up to production gate
  Frequency: Every passing build can be deployed
  Human gate: YES — someone presses the "deploy to production" button

CONTINUOUS DEPLOYMENT (CD - upper D):
  Scope: CI → Automated production deployment
  Automation: FULLY automated including production
  Frequency: Every passing commit goes to production
  Human gate: NONE

Visual Diagram:
  
  CI:            [Commit] → [Build] → [Test] → ✓ or ✗
  
  Delivery:      [Commit] → [Build] → [Test] → [Staging] → [UAT] → [Manual gate] → [Production]
  
  Deployment:    [Commit] → [Build] → [Test] → [Staging] → [Smoke] → [PRODUCTION] ← Fully Auto

When to Choose Each:

  Continuous Delivery (with manual gate):
  - Regulated industries (finance, healthcare, pharmaceutical) requiring sign-off
  - Public-facing features requiring product/marketing coordination
  - High-stakes systems where human validation is required
  - Teams building confidence in automation
  
  Continuous Deployment (fully automated):
  - High test confidence (extensive automated test suites)
  - Feature flags to control user exposure
  - Mature monitoring and quick rollback capability
  - SaaS products, e-commerce, consumer apps
  - Companies like Netflix, Amazon, Facebook, GitHub

Reality:
  Most companies practice Continuous Delivery (with manual approval for
  production) rather than full Continuous Deployment. The key capability of CD
  is that the software COULD be deployed at any time — the decision is purely
  business.

3. THE CD PIPELINE
================================================================================

A complete CD pipeline from code to production:

  STAGE 1: COMMIT STAGE (CI — covered in CI section)
  ─────────────────────────────────────────────────
  Trigger: Code push
  Duration: < 10 minutes
  Steps:
    - Checkout code
    - Build and compile
    - Unit tests
    - Static analysis
    - Package artifact (Docker image, JAR)
    - Publish artifact to registry
  Output: Deployable artifact (tagged with git SHA)
  Success: Tests pass, artifact published

  STAGE 2: ACCEPTANCE TESTS (STAGING ENVIRONMENT)
  ────────────────────────────────────────────────
  Trigger: Commit stage success
  Duration: 15-60 minutes
  Steps:
    - Deploy artifact to staging environment
    - Run functional/integration smoke tests
    - Run API contract tests
    - Run performance tests (baseline)
    - Security scan (DAST on running application)
    - Validate configuration
  Output: Staging validation passed or failed
  Success: Application works correctly in production-like environment

  STAGE 3: MANUAL ACCEPTANCE / UAT
  ─────────────────────────────────
  Trigger: Acceptance tests pass
  Duration: Variable (hours to days for compliance)
  Steps:
    - Notify stakeholders
    - Product/QA manual validation
    - Exploratory testing
    - Business sign-off
  Output: Approval to proceed to production
  Success: Human approver clicks "Deploy to Production"

  STAGE 4: PRODUCTION DEPLOYMENT
  ────────────────────────────────
  Trigger: Manual approval (CD) or automatic (Continuous Deployment)
  Duration: Minutes
  Steps:
    - Deploy using chosen strategy (Blue-Green, Canary, Rolling)
    - Run smoke tests / synthetic tests
    - Monitor error rates, latency, alerts
    - Auto-rollback trigger if metrics degrade
  Output: Application running in production
  Success: Smoke tests pass, no error spike, healthy monitoring

  STAGE 5: POST-DEPLOYMENT VALIDATION
  ─────────────────────────────────────
  Duration: 15-30 minutes post-deploy
  Steps:
    - Monitor dashboards
    - Check error rate trends
    - Validate business metrics (conversion, sign-ups)
    - Confirm no regression alerts
  Output: Deployment confirmed successful or rollback triggered

Artifact Traceability:
  Every artifact must be traceable:
  - Which commit produced this artifact? (git SHA as tag)
  - Which build pipeline run? (build URL in artifact metadata)
  - Which tests validated it? (test results linked to build)
  - Where is it currently deployed? (deployment tracking)
  
  This is achieved through consistent tagging:
  image: myapp:a3f8d92b
  - a3f8d92b is the git short SHA
  - Run `git show a3f8d92b` to see exactly what code is in production

4. DEPLOYMENT STRATEGIES OVERVIEW
================================================================================

(Deep dives in 02_Deployment_Strategies.txt and 05_Blue_Green_vs_Canary.txt)

The main question: How do you update running software without downtime?

RECREATE (simplest):
  Stop old version → Deploy new version → Start
  
  Zero downtime? NO (brief outage during swap)
  Rollback?       Redeploy old version (slow)
  Use for:        Development, batch jobs, testing environments
  
  v1 running → STOP → v2 starting → v2 running
                 (DOWNTIME)

ROLLING UPDATE:
  Replace instances one-by-one. Both old and new versions run temporarily.
  
  Zero downtime? YES (if done carefully)
  Rollback?       Continue rolling, but in reverse
  Use for:        Stateless services, default Kubernetes strategy
  
  [v1][v1][v1] → [v2][v1][v1] → [v2][v2][v1] → [v2][v2][v2]

BLUE-GREEN DEPLOYMENT:
  Two identical environments. Traffic switches atomically.
  
  Zero downtime? YES
  Rollback?       Switch DNS/load balancer back to Blue (instant)
  Use for:        Applications needing instant rollback, database migrations
  
  [Blue v1] ← traffic    →    [Blue v1] [Green v2] ← traffic

CANARY DEPLOYMENT:
  Gradually shift traffic to new version.
  
  Zero downtime? YES
  Rollback?       Shift traffic back to 100% old version
  Use for:        Risk reduction, detecting issues with subset of users
  
  Traffic: 100% v1 → 5% v2, 95% v1 → 25% v2, 75% v1 → 100% v2

A/B TESTING:
  Different versions for different user segments (not the same as canary).
  Purpose: Measure which version performs better.
  Example: 50% see checkout flow A, 50% see checkout flow B
  Decision: Business metric (conversion rate) determines winner.

FEATURE FLAGS:
  Deploy code to 100% of servers, but control who sees the feature via config.
  
  if (featureEnabled("new-checkout", user)) {
    return newCheckoutService.handle(request);
  } else {
    return oldCheckoutService.handle(request);
  }

5. RELEASE MANAGEMENT
================================================================================

Release vs Deployment:
  DEPLOYMENT: Technical act of getting code to an environment
  RELEASE: Making a feature available to users
  
  With feature flags, these are decoupled:
  - Deploy code at any time (always safe)
  - Release feature to users when business decides
  
  Example: Deploy dark launch code to production, but feature flag is OFF.
  Release = turn the flag ON (instant, reversible, no deployment needed)

Semantic Versioning:
  MAJOR.MINOR.PATCH (e.g., 2.3.1)
  
  MAJOR: Breaking changes (API changed, incompatible)
  MINOR: New features, backward-compatible
  PATCH: Bug fixes, backward-compatible
  
  Pre-release: 2.3.1-SNAPSHOT, 2.3.1-rc1, 2.3.1-beta
  
  When to bump:
  - New bug fix: 2.3.1 → 2.3.2
  - New feature: 2.3.1 → 2.4.0
  - Breaking API: 2.3.1 → 3.0.0

Automated Versioning:
  Tools that auto-generate version from commit history:
  
  semantic-release (Node.js):
    Analyzes Conventional Commits (feat:, fix:, BREAKING CHANGE:)
    Automatically bumps version and creates GitHub release
  
  release-please (Google):
    GitHub Action that creates release PRs
    Merging the PR creates the release
  
  git-flow with versioning:
    Release branch named release/2.3.0 sets the version

Change Log / Release Notes:
  Document every release with:
  - New features (feat: commits)
  - Bug fixes (fix: commits)
  - Breaking changes
  - Security updates
  
  Auto-generated from Conventional Commits:
    CHANGELOG.md generated by standard-changelog, release-please, etc.

Release Coordination:
  RELEASE NOTES: What changed, for user-facing communication
  RUNBOOK: How to deploy (pre/post steps, database migrations, config changes)
  ROLLBACK PLAN: How to revert if something goes wrong
  COMMUNICATION PLAN: Who needs to know (support, stakeholders, users)

6. CD PRINCIPLES AND PREREQUISITES
================================================================================

For CD to work, you need:

1. VERSION CONTROL FOR EVERYTHING
   - Code: Source files
   - Configuration: app configs, infrastructure code
   - Database: Schema migrations (Liquibase, Flyway)
   - Scripts: Deployment scripts, runbooks
   
   "If it's not in version control, it doesn't exist."

2. COMPREHENSIVE AUTOMATED TEST SUITE
   - High confidence that passing tests = working software
   - If tests don't cover your critical paths, CD is scary
   - Test Pyramid: Lots of unit, some integration, few E2E
   
   Rule: Never deploy if tests don't pass.

3. DEPLOYMENT PIPELINE
   - Automated process from commit to production
   - Consistent: Same process every time
   - Fast enough for feedback: < 30 minutes ideally

4. SHORT-LIVED BRANCHES / TRUNK-BASED DEVELOPMENT
   - Long-lived branches accumulate integration risk
   - CD requires frequent merging to trunk (main)
   - Feature flags for WIP features in trunk

5. FEATURE FLAGS
   - Allow incomplete features to be in trunk
   - Separate deployment from release
   - Enable instant rollback without deployment

6. MONITORING AND OBSERVABILITY
   - Must know if deployment was successful
   - Metrics, logs, traces must be in place before CD
   - Automated rollback requires automated alerting

7. FAST AND RELIABLE BUILD
   - CI pipeline must be fast (< 15 minutes)
   - If pipeline takes 2 hours, CD cadence is limited to few times per day
   - Flaky tests kill CD (destroy trust in pipeline)

8. DATABASE MIGRATION STRATEGY
   - Schema changes must be backward-compatible with old code
   - Expand-Contract pattern for zero-downtime schema changes
   - Tools: Flyway, Liquibase

Database Migrations in CD:
  Problem: Old code + new schema = broken. New schema + old code = broken.
  Solution: Expand-Contract (also called parallel change):
  
  PHASE 1 - EXPAND: Add new column (nullable), run both old and new code
  PHASE 2 - MIGRATE: Populate new column, run new code only
  PHASE 3 - CONTRACT: Remove old column (after all old code removed)
  
  Example: Rename column 'name' to 'full_name':
  1. Add 'full_name' column (nullable)
  2. Update new code to write to both 'name' AND 'full_name'
  3. Backfill: UPDATE users SET full_name = name WHERE full_name IS NULL
  4. Update new code to read from 'full_name' (stop reading 'name')
  5. Drop 'name' column (in a later deploy)

7. ENVIRONMENT MANAGEMENT
================================================================================

Environment Chain:
  
  LOCAL → CI → DEV → STAGING → PRE-PROD → PRODUCTION
  
  LOCAL:
    Developer's machine. Fastest feedback.
    Using Docker Compose or mock services.
    Not always identical to production.
  
  CI (Build Environment):
    Ephemeral containers/runners.
    Run on every commit.
    Unit + integration tests.
  
  DEV (Development/Integration):
    Shared environment for developers.
    Latest merged code deployed automatically.
    Not for demos or stability testing.
  
  STAGING:
    Most production-like environment.
    Feature validation, performance testing.
    CD gate: Must pass staging before production.
    Isolated from production data.
  
  PRE-PROD (UAT/QA):
    For user acceptance testing, compliance verification.
    May use production data snapshots (anonymized).
    Final human approval gate.
  
  PRODUCTION:
    Real users, real data.
    Multiple deployment strategies available.

Environment Parity:
  "dev-prod parity" — keep dev/staging as similar to production as possible.
  
  Sources of parity drift:
  - Different database versions
  - Different library versions
  - Different OS
  - Different configurations
  - Different data volumes
  
  Solutions:
  - Docker containers: Same OS, same base image everywhere
  - Infrastructure as Code: Same Terraform for all environments
  - Data: Synthetic data generation or anonymized production snapshots
  - Configuration: Environment-specific config via environment variables

Ephemeral Environments:
  Short-lived environments created for a specific purpose.
  
  PR Environments (Review Apps):
    Created when PR is opened.
    Destroyed when PR is merged/closed.
    URL: https://pr-123.preview.example.com
    Enables: Live review of feature branches
    Tools: GitLab Review Apps, GitHub Environments, Kubernetes + DNS
  
  Benefits:
  - Isolated testing per feature
  - Product/design review on running app
  - No shared staging environment conflicts

8. RELEASE TRAINS AND CADENCE
================================================================================

Release Train:
  A scheduled, periodic release where multiple features board a "train" that
  leaves at a fixed time regardless of which features are ready.
  
  Like a real train: If your feature isn't ready when the train leaves,
  it waits for the next train.
  
  Benefits:
  - Predictable release cadence
  - Multiple teams can plan around train schedule
  - Features don't delay train (just miss it)
  
  Used by: Firefox (4-week trains), Chrome (6-week trains), SAFe enterprise

Release Cadence Options:
  
  ON-DEMAND: Deploy when needed (with CD)
    Best for: Teams with high confidence, mature CD, small changes
  
  CONTINUOUS: Every passing commit (Continuous Deployment)
    Best for: SaaS, e-commerce, startups
  
  DAILY/WEEKLY: Scheduled deploy of latest stable build
    Common in many enterprises
  
  SPRINT-BASED: Deploy at end of each sprint
    Common with Agile teams, predictable for stakeholders
  
  FIXED TRAIN: Monthly/quarterly (enterprise, regulated)
    SAFe: Program Increment (PI) = 10-week cycle, multiple sprints

9. CD METRICS
================================================================================

DORA Four Key Metrics (Google DevOps Research):
  
  1. DEPLOYMENT FREQUENCY
     How often code is deployed to production.
     Elite: Multiple times per day
     High: Once per week to once per month
     Medium: Monthly
     Low: Less than once per 6 months
     
     Measure by: Count production deployments per time period
  
  2. LEAD TIME FOR CHANGES
     Time from code commit to code in production.
     Elite: Less than 1 hour
     High: Between 1 day and 1 week
     Medium: Between 1 week and 1 month
     Low: Between 1 and 6 months
     
     Measure by: Timestamp of commit vs timestamp of deployment to production
  
  3. CHANGE FAILURE RATE
     Percentage of deployments that cause a production incident.
     Elite: 0-15%
     High: 16-30%
     Medium/Low: 31-45%
     
     Measure by: Incidents / Deployments × 100%
  
  4. MEAN TIME TO RECOVERY (MTTR)
     Time to restore service after a production incident.
     Elite: Less than 1 hour
     High: Less than 1 day
     Medium: Between 1 day and 1 week
     Low: More than 1 week
     
     Measure by: Average time from incident detection to resolution

Deployment Pipeline Metrics:
  - Pipeline success rate (> 95% target)
  - Pipeline execution time (per stage)
  - Queue wait time (waiting for runner)
  - Rollback rate (how often rollbacks happen)
  - Time from merge to staging deployment
  - Time from staging to production deployment

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between Continuous Delivery and Continuous Deployment?
A: Continuous Delivery means every change that passes automated tests is in a
   deployable state, but humans decide WHEN to deploy to production (manual
   approval gate).
   
   Continuous Deployment goes further — every passing change is automatically
   deployed to production with NO manual gate.
   
   Example: Netflix practices Continuous Deployment — they deploy thousands of
   times per day automatically. A regulated bank might practice Continuous
   Delivery — code is always deployable, but a change manager approves before
   production release.
   
   The underlying goal is the same: make deployment a non-event that can happen
   at any time. The difference is just whether that final step is automated.

Q2: What are the prerequisites for Continuous Delivery?
A: CD requires several foundations:
   1. Comprehensive automated tests — If you can't trust your tests, you can't
      trust automated deployments
   2. Fast, reliable CI pipeline — Must provide timely feedback
   3. Production-like staging environment — Testing must be realistic
   4. Feature flags — Decouple deployment from release, manage risk
   5. Database migration strategy — Expand-contract for zero-downtime schema changes
   6. Monitoring and alerting — Need to know immediately if deploy caused issues
   7. Automated rollback capability — Must be able to recover quickly
   8. Short-lived branches/TBD — Long-lived branches accumulate integration risk
   
   Often, the limiting factor is test coverage and confidence, not tooling.

Q3: How do you handle database migrations in a CD pipeline?
A: Database migrations are the hardest part of CD because databases have state
   and you can't just swap them out like a stateless service.
   
   Strategy: Expand-Contract (also called parallel change):
   Never make a breaking schema change. Instead:
   1. EXPAND: Add new column/table (backward-compatible with old code)
   2. Deploy new code that writes to both old and new structures
   3. MIGRATE: Run data migration
   4. Deploy code that only reads new structure
   5. CONTRACT: Remove old column/table (in a later deployment)
   
   Tools: Flyway or Liquibase manage migration scripts, run automatically
   during deployment. Each script has a version; Flyway tracks which have run.
   
   In CD, migrations run as part of the deployment pipeline before the
   application starts. Rolling migrations (running during a rolling deployment)
   require the "expand" version to already be deployed.

Q4: What are the DORA Four Key Metrics and why do they matter?
A: DORA (DevOps Research and Assessment) identified four metrics that predict
   organizational performance:
   
   1. Deployment Frequency: How often you deploy to production
   2. Lead Time for Changes: Commit to production time
   3. Change Failure Rate: % of deployments causing incidents
   4. MTTR: Mean time to recover from incidents
   
   Why they matter: Elite performers (like Amazon, Google, Netflix) deploy
   thousands of times per day with low failure rates and recover in minutes.
   Research shows high performers have 46× more frequent deployments AND
   7× lower change failure rates than low performers — speed and stability are
   NOT a tradeoff.
   
   Practical use: These metrics give you an objective, research-backed view of
   your delivery capability. They reveal bottlenecks (high lead time often means
   long-lived branches; high failure rate often means insufficient testing).

11. QUICK REFERENCE CHEAT SHEET
================================================================================

CD Definition: Always in a deployable state. Deploy is a business decision.
CD != Continuous Deployment: Delivery = manual gate; Deployment = fully auto

The CD Pipeline:
  Commit → Artifact → Staging → (Optional UAT) → [Gate] → Production

Deployment Strategies Summary:
  Recreate:       Stop all, deploy new. Has downtime.
  Rolling:        Replace instances gradually. No downtime.
  Blue-Green:     Switch traffic between two environments. Instant rollback.
  Canary:         Gradually shift traffic. Catch issues early.
  Feature Flags:  Deploy code, control feature activation separately.

CD Prerequisites:
  Tests → Pipeline → Staging parity → Feature flags → DB migration strategy →
  Monitoring → Rollback capability

DORA Metrics (Elite = more frequent, lower failure):
  Deployment Frequency:    Multiple/day (elite) vs < 6×/year (low)
  Lead Time for Changes:   < 1 hour (elite) vs > 6 months (low)
  Change Failure Rate:     0-15% (elite) vs 31-45% (low)
  MTTR:                    < 1 hour (elite) vs > 1 week (low)

Database Migrations: Expand-Contract pattern (never break backward compat)
  Tools: Flyway, Liquibase

Versioning:
  SemVer: MAJOR.MINOR.PATCH
  Releases: git SHA tag for traceability, semver for human-readable versions

Environment Chain:
  Local → CI → Dev → Staging → Pre-Prod → Production

Key Principle: "If it hurts, do it more often, and bring the pain forward."
