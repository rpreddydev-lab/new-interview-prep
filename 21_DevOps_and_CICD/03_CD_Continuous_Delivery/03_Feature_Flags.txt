1. WHAT ARE FEATURE FLAGS?
================================================================================

Definition:
  Feature flags (also called feature toggles, feature switches, or feature bits)
  are a software development technique that allows turning features on or off
  at runtime WITHOUT deploying new code.
  
  A feature flag is fundamentally an if-statement controlled by configuration:
  
  if (featureEnabled("new-checkout-flow")) {
      return newCheckoutService.process(cart);
  } else {
      return legacyCheckoutService.process(cart);
  }

Why Feature Flags Matter:
  
  WITHOUT FEATURE FLAGS:
  - Deploy when feature is complete (large, risky deployments)
  - Long-lived feature branches (merge conflicts, integration risk)
  - Release = Deployment (tied together, can't separate)
  - Rollback = Redeploy (slow, scary)
  - Testing in production = affect all users
  
  WITH FEATURE FLAGS:
  - Deploy incomplete features (hidden behind flag)
  - Trunk-based development (small, frequent merges)
  - Release ≠ Deployment (completely decoupled)
  - Rollback = Toggle flag (instant, no deployment)
  - Testing in production = enable flag for test users only

The Core Concept — Decouple Deploy from Release:
  
  DEPLOY:  Technical act of getting code to production servers
           (Done by engineers, any time)
  
  RELEASE: Making a feature available to users
           (Done by product team, when business is ready)
  
  Example timeline:
  Day 1:  Engineers deploy new homepage redesign (flag OFF)
  Day 5:  More code shipped, feature complete (flag OFF)
  Day 8:  Marketing campaign ready, documentation written
  Day 8:  Product team turns flag ON → Feature "released"
  Day 9:  Users complain about a bug → Turn flag OFF → Instant "rollback"
  Day 12: Bug fixed, flag turned ON again

Relationship to CI/CD:
  Feature flags are a prerequisite for Trunk-Based Development and
  Continuous Deployment:
  
  - Engineer merges work-in-progress code daily (behind flag)
  - No merge conflicts from long-lived branches
  - Deployment can happen anytime (incomplete code is hidden)
  - Release is a business decision, not a technical event

2. TYPES OF FEATURE FLAGS
================================================================================

Martin Fowler & Pete Hodgson (martinfowler.com/articles/feature-toggles.html)
identify four main types:

1. RELEASE TOGGLES (a.k.a. Feature Flags in the common sense)
   ──────────────────────────────────────────────────────────
   Purpose: Enable incomplete features in trunk, hide until ready for release
   Lifespan: SHORT — days to weeks (removed after full rollout)
   Dynamism: Can change without deployment, but rarely changed
   Decision: Product team decides when to enable
   
   Example:
   if (flags.isEnabled("new-onboarding-flow", user)) {
       return newOnboardingController.handle(request);
   } else {
       return legacyOnboardingController.handle(request);
   }
   
   Use case: A team is building a new feature over 3 weeks. They commit
   to main daily (trunk-based dev), but the flag keeps it hidden from users.
   When ready, product team enables it. After full rollout, the flag is
   removed and old code path deleted.

2. EXPERIMENT TOGGLES (a.k.a. A/B Flags)
   ────────────────────────────────────────
   Purpose: A/B testing, multivariate testing, measuring feature impact
   Lifespan: SHORT TO MEDIUM — days to weeks until experiment concludes
   Dynamism: Stable during experiment, but configured per user segment
   Decision: Data science/product analytics team decides
   
   Example:
   variant = flags.getVariant("checkout-button-color", userId)
   # Returns: "control" | "treatment_green" | "treatment_red"
   analytics.track("page_view", {variant: variant, userId: userId})
   
   if variant == "treatment_green":
       render_green_button()
   else:
       render_blue_button()   # control
   
   Use case: Test whether a new recommendation algorithm improves click-through
   rate. Route 50% of users to old algorithm, 50% to new. Measure after
   1 week with statistical significance. Ship winner.

3. OPS TOGGLES (Operations Toggles)
   ──────────────────────────────────
   Purpose: Control system behavior for operational/performance reasons
   Lifespan: LONG — months to years (circuit breakers, kill switches)
   Dynamism: Changed during incidents or operational events
   Decision: Operations/SRE team changes in real-time
   
   Example:
   if (flags.isEnabled("enable-recommendations-engine")) {
       recommendations = recommendationService.getFor(user);
   } else {
       recommendations = fallback.getDefaultRecommendations();
   }
   // During high traffic event: disable expensive recommendations to save DB
   
   Use case: During Black Friday, disable non-critical features (search 
   autocomplete, recommendations) to reduce load on the database. After
   the peak, re-enable them.
   
   Also called: Kill switches, circuit breakers, graceful degradation toggles.

4. PERMISSION TOGGLES (Access Control)
   ──────────────────────────────────────
   Purpose: Control which users have access to features
   Lifespan: LONG — permanent or semi-permanent access control
   Dynamism: Changed when user permissions change
   Decision: Product/business decisions about access tiers
   
   Example:
   if (flags.hasPermission("advanced-analytics", user)) {
       return advancedAnalyticsDashboard();
   } else {
       return standardDashboard();
   }
   
   Use case: Premium tier users have access to advanced analytics.
   Beta program: specific users get early access to new features.
   Internal users: employees see a debug panel that external users don't.

Summary Table:
  
  TYPE         PURPOSE                LIFESPAN    WHO CONTROLS     DYNAMISM
  ───────────────────────────────────────────────────────────────────────────
  Release      Deploy without release Short       Product team      Low
  Experiment   A/B testing            Short-Med   Data/Analytics    Medium
  Ops          Kill switch            Long        SRE/Ops           High
  Permission   Access control         Long        Product/Bizdev    Low-Medium

3. FEATURE FLAG ARCHITECTURE
================================================================================

The Components:
  
  1. FLAG DEFINITION: What flags exist and their rules
  2. FLAG STORAGE: Where flag configs are stored (DB, config service)
  3. FLAG EVALUATION: The SDK/library in your code that evaluates flags
  4. FLAG MANAGEMENT UI: Dashboard to manage flags without code changes
  5. ANALYTICS: Tracking which variant users saw (for experiments)
  
  Developer uses SDK:
  featureFlags.isEnabled("flag-name", user)
         ↓
  SDK calls flag service (or local cache)
         ↓
  Returns true/false based on:
  - Is flag enabled globally?
  - Does user match targeting rules?
  - What's the rollout percentage?
  - Which variant does this user get?

Flag Targeting:
  Flags can be targeted to specific users or segments:
  
  ALL USERS: Simple on/off for everyone
  
  SPECIFIC USERS: List of user IDs
  - {"flag": "beta-ui", "enabled": ["user-123", "user-456"]}
  
  PERCENTAGE ROLLOUT: X% of all users
  - {"flag": "new-search", "percentage": 10}
  - Must be DETERMINISTIC: Same user ALWAYS gets same assignment
  - Implementation: hash(userId + flagName) % 100 < percentage
  
  USER ATTRIBUTES: Target by attribute value
  - {"flag": "eu-privacy-banner", "rules": [{"country": "DE", "enabled": true}]}
  - Examples: country, plan type, company, user age, device type
  
  USER SEGMENTS: Pre-defined groups
  - Beta testers, premium users, internal users, employees

Deterministic User Assignment (Consistent Hashing):
  
  Critical requirement: A user must always see the SAME variant of an experiment.
  If they see variant A in one request and variant B the next, results are invalid.
  
  # Python example of deterministic assignment
  import hashlib
  
  def get_variant(flag_name: str, user_id: str, percentage: int) -> bool:
      """Returns True if user is in the enabled bucket."""
      hash_input = f"{flag_name}-{user_id}"
      hash_value = int(hashlib.md5(hash_input.encode()).hexdigest(), 16)
      bucket = hash_value % 100
      return bucket < percentage
  
  # Same user always gets same result for same flag
  assert get_variant("new-feature", "user-123", 10) == get_variant("new-feature", "user-123", 10)

Flag Data Model:
  
  {
    "flagKey": "new-checkout-flow",
    "enabled": true,
    "description": "New streamlined checkout experience",
    "createdBy": "alice@example.com",
    "createdAt": "2024-01-15T09:00:00Z",
    "variants": ["on", "off"],
    "defaultVariant": "off",
    "rules": [
      {
        "id": "beta-testers",
        "clauses": [{"attribute": "email", "operator": "endsWith", "values": ["@example.com"]}],
        "variant": "on",
        "description": "Enable for internal employees"
      },
      {
        "id": "percentage-rollout",
        "clauses": [],
        "rollout": {"on": 10, "off": 90},
        "description": "10% of all users"
      }
    ]
  }

4. IMPLEMENTATION PATTERNS
================================================================================

PATTERN 1: BASIC BOOLEAN FLAG
  
  # Simple on/off, all or nothing
  if feature_flags.enabled("new-header"):
      return render_new_header()
  return render_old_header()

PATTERN 2: PERCENTAGE ROLLOUT
  
  # Deterministic percentage-based rollout
  if feature_flags.rollout("redesign", user.id, percentage=25):
      return new_design_component()
  return old_design_component()

PATTERN 3: STRATEGY PATTERN (Cleanest for Large Features)
  
  # Avoid scattered if-statements — use strategy/factory pattern
  
  class CheckoutService(ABC):
      @abstractmethod
      def process(self, cart: Cart) -> Order:
          pass
  
  class LegacyCheckoutService(CheckoutService):
      def process(self, cart: Cart) -> Order:
          # Old implementation
          ...
  
  class NewCheckoutService(CheckoutService):
      def process(self, cart: Cart) -> Order:
          # New implementation
          ...
  
  class CheckoutServiceFactory:
      def __init__(self, feature_flags: FeatureFlags):
          self.flags = feature_flags
      
      def get_service(self, user: User) -> CheckoutService:
          if self.flags.enabled("new-checkout", user.id):
              return NewCheckoutService()
          return LegacyCheckoutService()
  
  # Usage
  service = checkout_factory.get_service(current_user)
  order = service.process(cart)

PATTERN 4: BRANCH BY ABSTRACTION (Larger Architecture Changes)
  
  Goal: Progressively replace a large subsystem.
  
  Step 1: Create abstraction layer over current system
  Step 2: Implement new system behind abstraction
  Step 3: Use feature flag to route to new implementation
  Step 4: Remove old implementation and abstraction
  
  # Before (tightly coupled)
  result = LegacySearchEngine().search(query)
  
  # After (Branch by Abstraction)
  class SearchEngine(Protocol):
      def search(self, query: str) -> SearchResults: ...
  
  class LegacySearchEngine(SearchEngine): ...
  class ElasticSearchEngine(SearchEngine): ...
  
  def get_search_engine(flags, user) -> SearchEngine:
      if flags.enabled("elastic-search", user.id):
          return ElasticSearchEngine()
      return LegacySearchEngine()

PATTERN 5: DARK LAUNCH (Read from Both, Serve Old)
  
  # Validate new service behavior against production traffic
  # without affecting users
  
  legacy_result = legacy_service.search(query)
  
  if feature_flags.enabled("new-search-shadow", user.id):
      try:
          new_result = new_service.search(query)
          # Log comparison for analysis, don't serve to user
          if legacy_result != new_result:
              logger.warning("Search divergence detected", 
                           query=query, legacy=legacy_result, new=new_result)
      except Exception as e:
          metrics.increment("shadow_search_error")
  
  return legacy_result  # Always return legacy result during dark launch

CONFIGURATION IN CODE vs CONFIGURATION FILE vs REMOTE SERVICE:

  IN-CODE (simple, not recommended for production):
    FLAG_ENABLED = True
    if FLAG_ENABLED: ...
    Problem: Requires code deploy to change flag. Defeats the purpose.
  
  CONFIG FILE (slightly better):
    # flags.yaml
    new_checkout: enabled
    # Can update config file without code change
    Problem: Requires server restart or config reload.
  
  ENVIRONMENT VARIABLES (12-factor apps):
    NEW_CHECKOUT_ENABLED=true
    if os.getenv("NEW_CHECKOUT_ENABLED", "false") == "true": ...
    Problem: Requires restart. Can't do percentage rollouts.
  
  REMOTE FLAG SERVICE (recommended for production):
    LaunchDarkly, Unleash, AWS AppConfig, Flagsmith
    - Central management UI
    - Real-time updates without deployment or restart
    - Percentage rollouts, user targeting
    - Audit log of flag changes
    - SDK caches flags locally (no per-request latency)

================================================================================

LAUNCHDARKLY:
  Industry leader. Enterprise-grade. SaaS only.
  
  Features:
  - All flag types (release, experiment, ops, permission)
  - Multivariate flags (not just on/off, any value)
  - AI-powered automatic rollout analysis
  - Data Export: Send flag evaluations to analytics systems
  - Integrations: Jira, GitHub, DataDog, Slack
  - SDK support: Java, Node.js, Python, Go, React, mobile, and more
  - Audit log, approval workflows, flag templates
  
  Pricing: Expensive ($75+/seat/month). Best for large enterprises.
  
  SDK Example (Python):
  import ldclient
  from ldclient.config import Config
  
  ldclient.set_config(Config("YOUR_SDK_KEY"))
  client = ldclient.get()
  
  user = {"key": "user-123", "email": "user@example.com", "country": "US"}
  
  if client.variation("new-checkout", user, False):
      return new_checkout_handler(request)
  return legacy_checkout_handler(request)

UNLEASH (Open Source):
  Open-source feature management. Self-hosted or cloud.
  
  Features:
  - Enterprise-grade OSS (Unleash OSS is free, Unleash Enterprise is paid)
  - Strategy types: gradual rollout, user ID, IP address, hostname, custom
  - Client SDKs: multiple languages
  - Self-hosted = full control, no vendor lock-in

        POSTGRES_DB: unleash

  const { initialize } = require('unleash-client');
  
  const unleash = initialize({
    url: 'http://localhost:4242/api/',

  });
  
  if (unleash.isEnabled('new-checkout', { userId: '123' })) {
    res.send(newCheckout());
  } else {
    res.send(legacyCheckout());
  }

FLAGSMITH (Open Source):
  Similar to Unleash but newer. Good free tier. Can be self-hosted.
  
  Features:
  - Feature flags + Remote Configuration (set values, not just on/off)
  - A/B testing built-in
  - REST API
  - SDKs: Python, Node.js, Java, Go, React, iOS, Android

AWS APPCONFIG:
  Native AWS feature flag service (part of AWS Systems Manager).
  
  Features:
  - Integrated with AWS services (Lambda, ECS, EC2)
  - Deployment strategies (linear, exponential rollout)
  - Automatic rollback on CloudWatch alarm
  - Config validation with JSON schema
  - Free tier available
  
  Example:

  client = boto3.client('appconfigdata', region_name='us-east-1')

      return new_checkout_handler(request)

SPLIT.IO:

GROWTHBOOK (Open Source):

6. FEATURE FLAG LIFECYCLE
================================================================================

The lifecycle of a Release Toggle:

  PHASE 1: CREATION
  ─────────────────
  - Engineer creates flag in management system
  - Flag configured as OFF for all users
  - Code written with flag check
  - Deployed to production (flag is OFF → old behavior for everyone)
  
  PHASE 2: INTERNAL TESTING
  ─────────────────────────
  - Flag enabled for internal users (employees, testers)
  - Targeting rule: "Email ends with @company.com"
  - Bug fixes deployed, feature iterated
  - Still OFF for all external users
  
  PHASE 3: BETA / LIMITED ROLLOUT
  ─────────────────────────────────
  - Flag enabled for beta tester group
  - Or: 1-5% of all users (percentage rollout)
  - Monitor error rates, performance, user feedback
  - Automated canary analysis (if integrated with monitoring)
  
  PHASE 4: GRADUAL ROLLOUT
  ─────────────────────────
  - Increase percentage: 5% → 25% → 50% → 75% → 100%
  - Each step: Monitor metrics, validate no regressions
  
  PHASE 5: FULL RELEASE
  ─────────────────────
  - Flag enabled for 100% of users
  - Feature is now "generally available"
  - Flag is still in code (for instant rollback if needed)
  
  PHASE 6: FLAG REMOVAL (CLEANUP — MOST OFTEN SKIPPED, CAUSING TECH DEBT)
  ─────────────────────────────────────────────────────────────────────────
  - After feature is stable for 2-4 weeks at 100% rollout
  - Remove flag check from code
  - Remove old code path (legacy implementation)
  - Delete flag from management system
  - RESULT: Codebase is cleaner

Flag Ownership and Governance:
  
  Each flag should have:
  - Owner: Who is responsible for this flag?
  - Expiry date: When should this flag be removed?
  - JIRA/ticket: Track flag cleanup as a task
  
  Process:
  - Engineers set flag expiry on creation
  - Automated alerts when flags approach expiry
  - Sprint planning includes flag cleanup tasks
  - PR created automatically to remove expired flags (some tools support this)

7. FEATURE FLAGS IN TESTING
================================================================================

Testing With Flags — The Challenge:
  Feature flags increase the number of code paths.
  With 10 flags, you technically have 2^10 = 1024 possible combinations.
  Testing all combinations is impossible.

Testing Strategies:

  1. TEST EACH FEATURE IN ISOLATION:
     - Test flag=OFF: Old behavior still works
     - Test flag=ON: New behavior works as expected
     - Don't test every combination of flags
  
  2. USE FLAG DEFAULTS IN TESTS:
     - Most tests should run with flags at their DEFAULT state
     - Unit tests: Mock feature flag service; control flag state explicitly
     - Integration tests: Use a test configuration with known flag states
  
  3. TEST ENVIRONMENT FLAG STATES:
     - Dev: All flags ON (developers see new features by default)
     - Staging: Mirror production flag state
     - Production: Gradually rolling out
  
  4. OVERRIDE FLAGS IN TESTS:
     # Python test example
     def test_new_checkout():
         with feature_flags.override("new-checkout", True):
             result = checkout_service.process(cart)
             assert result.message == "New checkout complete"
     
     def test_legacy_checkout():
         with feature_flags.override("new-checkout", False):
             result = checkout_service.process(cart)
             assert result.message == "Legacy checkout complete"

Beware of Combinatorial Explosion:
  
  Problem: 5 interacting flags = 32 code paths.
  Solution: Keep flags independent (no if A and B logic).
  
  BAD (flags interact):
  if (flags.enabled("new-ui") and flags.enabled("new-api")):
      # Special combined behavior
  
  GOOD (flags are independent):
  if (flags.enabled("new-ui")):
      render_new_ui()  # Independent of API
  if (flags.enabled("new-api")):
      use_new_api()    # Independent of UI

Contract Tests for Flagged APIs:
  If your API behavior changes based on a flag, ensure both variants are
  tested in contract tests so consumers are not surprised.

8. FEATURE FLAG ANTI-PATTERNS AND TECHNICAL DEBT
================================================================================

THE MOST COMMON PROBLEM: FLAG DEBT (Zombie Flags)
  
  Flags that should have been removed months ago but weren't.
  Code becomes:
  
  if (flags.enabled("checkout-v2-2021")):          # From 2021?!
      if (flags.enabled("checkout-v2-redesign")):  # Which is the current one?
          if (flags.enabled("checkout-v3-beta")):  # Still in beta since 2022?
              return newNewNewCheckout()
          return newNewCheckout()
      return newCheckout()
  return legacyCheckout()  # Is this even reachable?

ANTI-PATTERN 1: Long-Lived Release Flags
  Symptom: Release flags that are always ON but never removed
  Impact: Code complexity, dead code in codebase
  Fix: Enforce maximum lifetime for release flags; create cleanup tickets

ANTI-PATTERN 2: Config with Business Logic in Flags
  Symptom: Flags that control pricing, tax rules, business logic
  Impact: Hard to audit, hard to test, security risk
  Fix: Feature flags for feature access; separate config for business rules

ANTI-PATTERN 3: Flags with Side Effects
  Symptom: Flag evaluation triggers events or has side effects
  Impact: Unpredictable behavior, testing nightmare
  Fix: Flags should ONLY return a value. No side effects in evaluation.

ANTI-PATTERN 4: Too Many Interacting Flags
  Symptom: Multiple flags with if A and B conditions
  Impact: 2^n code paths, untestable
  Fix: Keep flags independent. One feature = one flag.

ANTI-PATTERN 5: No Flag Ownership
  Symptom: Flag created, nobody knows what it does or who owns it
  Impact: Fear to remove it (what if it's needed?), flag debt accumulates
  Fix: Require owner, description, and expiry date on every flag

ANTI-PATTERN 6: Hardcoded Flags
  Symptom: FLAG_ENABLED = True in code
  Impact: Requires deployment to change. Defeats the purpose.
  Fix: Always use a proper flag service.

ANTI-PATTERN 7: Flags for Non-Features
  Symptom: Using flags for configuration, constants, credentials
  Impact: Flag service becomes a config store (wrong tool)
  Fix: Use proper config management (AWS Parameter Store, Vault) for config

Managing Flag Debt — Recommendations:
  1. Set maximum lifespan when creating flags (14 days for release flags)
  2. Automated reminder when flag is past expiry date
  3. Track all flags in Jira/backlog
  4. "Flag cleanup" as a regular sprint activity
  5. Code review: Flag-removal PRs should be praised, not just adding flags

9. ADVANCED PATTERNS
================================================================================

GRADUAL ROLLOUT WITH AUTOMATIC ANALYSIS:
  LaunchDarkly Experimentation, Unleash with Prometheus integration.
  Automatically compares error rates between flag=ON and flag=OFF cohorts.
  Pauses rollout if metrics degrade. Alerts engineering team.

PROGRESSIVE DELIVERY:
  Combines feature flags + canary deployments.
  
  Tools: Flagger, Argo Rollouts
  - Deploy new version to 10% of pods (canary)
  - Enable feature flag for those 10%
  - Monitor metrics
  - Expand canary OR rollback based on automated analysis

FEATURE FLAG AS CIRCUIT BREAKER:
  
  # Ops toggle acting as circuit breaker
  class RecommendationService:
      def get_recommendations(self, user_id: str) -> List[Item]:
          if not self.flags.enabled("recommendations-engine"):
              # Graceful degradation: return empty or cached list
              return self.cache.get_popular_items()
          
          try:
              return self.ml_model.predict(user_id)
          except Exception as e:
              self.metrics.increment("recommendation_error")
              # Auto-disable flag on repeated failures
              if self.metrics.get("recommendation_error") > 100:
                  self.flags.disable("recommendations-engine")
              return self.cache.get_popular_items()

ENTITLEMENT FLAGS (SaaS Feature Gating):
  Control access to features based on subscription tier.
  
  class FeatureGate:
      FEATURES = {
          "advanced-analytics": ["pro", "enterprise"],
          "api-access": ["enterprise"],
          "custom-branding": ["pro", "enterprise"],
          "sso": ["enterprise"],
      }
      
      def has_access(self, feature: str, user: User) -> bool:
          if feature not in self.FEATURES:
              return True  # Default: allow
          return user.plan in self.FEATURES[feature]

MULTIVARIATE FLAGS:
  Not just on/off. Return different values:
  
  button_color = flags.get_value("checkout-button-color", user.id, default="blue")
  # Returns: "blue" | "green" | "red" (string value)
  
  api_version = flags.get_value("api-version", user.id, default="v1")
  # Returns: "v1" | "v2" | "v3"
  
  page_limit = flags.get_number("results-per-page", user.id, default=20)
  # Returns: 10 | 20 | 50

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What are feature flags and why are they important in CD/CI pipelines?
A: Feature flags (feature toggles) are software mechanisms that allow you to
   turn features on or off at runtime without deploying new code.
   
   In CI/CD pipelines, they are important because they:
   1. Enable trunk-based development — engineers commit incomplete features
      to main, hidden behind a flag, eliminating long-lived branches
   2. Decouple deployment from release — code can be deployed at any time,
      but the feature is released only when the business is ready
   3. Enable gradual rollouts — expose to 1%, 10%, 100% of users progressively
   4. Provide instant rollback — toggle the flag off (no deployment needed)
   5. Enable dark launches — deploy and test on production traffic safely
   6. Support A/B testing — route different user segments to different variants
   
   Without feature flags, Continuous Deployment is extremely risky. They are
   a prerequisite for high-velocity delivery.

Q2: What are the different types of feature flags?
A: Four main types (from Martin Fowler's taxonomy):
   
   1. Release Toggles: Hide incomplete features during development. Short-lived
      (days to weeks). Removed after full rollout.
   
   2. Experiment Toggles: A/B testing. Route different users to different code
      paths to measure which performs better. Also short-lived.
   
   3. Ops Toggles (Kill Switches): Control system behavior for operational
      reasons. Long-lived. Changed during incidents to disable expensive features.
      Example: "disable-recommendations" toggle to reduce database load.
   
   4. Permission Toggles: Control access based on user attributes. Long-lived.
      Example: Premium users have access to advanced analytics.
   
   The key distinction is that they have very different lifecycles and owners:
   Release flags are owned by engineers and removed after rollout.
   Ops flags are owned by SRE and may live indefinitely.

Q3: How do you prevent feature flag technical debt?
A: Feature flag debt (zombie flags) accumulates when flags are never removed.
   Prevention:
   
   1. Set expiry dates: Every flag has a maximum lifetime (e.g., 14 days for
      release flags). Automated alerts when flag is past expiry.
   
   2. Ownership: Every flag has an owner and a linked Jira ticket.
   
   3. Regular cleanup: Flag removal is treated as normal sprint work.
   
   4. Code review culture: Celebrate flag removal PRs.
   
   5. Flag naming convention: Include date in name: "new-checkout-2024-01"
      makes old flags obvious.
   
   6. Tool support: LaunchDarkly, Unleash, and others have built-in
      "stale flag" detection that shows flags that haven't been evaluated
      in N days.
   
   The deeper principle: Flags are temporary by nature. The goal is always
   to remove them. A codebase with 100 permanent flags is a maintenance burden.

Q4: How do feature flags interact with automated testing?
A: Feature flags add complexity to testing because each flag creates additional
   code paths. Best practices:
   
   1. Test each state explicitly: Unit tests explicitly test flag=ON and
      flag=OFF scenarios for every flagged feature.
   
   2. Use test doubles: In unit tests, mock the flag service to control state.
   
   3. Keep flags independent: Avoid if (flagA and flagB) conditions.
      This prevents combinatorial explosion of test cases.
   
   4. Environment-specific defaults: Dev environment has all flags ON
      (developers see new features). Staging mirrors production flag state.
   
   5. Integration test config: Maintain a known flag state config for
      integration tests to ensure reproducible results.
   
   The biggest risk is that inadequate testing of flagged code leads to
   production bugs when flags are turned on. Treat flag=ON as a separate
   code path that requires full testing.

Q5: What is the difference between a feature flag and a configuration setting?
A: They solve different problems:
   
   FEATURE FLAG: Controls which CODE PATH runs. Is about BEHAVIOR.
   - "Should we use the new checkout flow?" → Yes/No
   - Managed in a flag service (LaunchDarkly, Unleash)
   - Often per-user, percentage-based
   - Typically short-lived (removed after rollout)
   - Changes don't require deployment
   
   CONFIGURATION: Controls how code runs with PARAMETERS. Is about SETTINGS.
   - "What is the database connection URL?" → Parameter value
   - Managed in config stores (AWS Parameter Store, Vault, environment variables)
   - Usually global (same value for all users)
   - Often long-lived and permanent
   - May require restart to take effect
   
   In practice, the line blurs (some flag systems support config values).
   The key distinction: if it's a business/product decision about which
   experience users have → feature flag. If it's an infrastructure or
   operational parameter → configuration.

  Create → Internal test → Beta → Gradual rollout → 100% → REMOVE FLAG

  Flagsmith: OSS + Cloud, remote config

  ✗ Never removing flags (flag debt/zombie flags)

  ✓ Set expiry dates on all release flags
  ✓ One flag = one feature (keep independent)
  ✓ Test both flag states (ON and OFF)
  ✓ Own flag cleanup as sprint work
  ✓ Use proper flag service (not env vars or hardcoded)

  Trunk-Based Development: Flags allow merging WIP daily
  Continuous Deployment: Flags enable safe automated deploys
