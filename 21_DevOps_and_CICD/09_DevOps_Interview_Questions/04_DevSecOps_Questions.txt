SECTION A: SHIFT-LEFT SECURITY
================================================================================

Q1: What does "shift-left security" mean and how do you implement it?

A: Shift-left = move security checks earlier in the SDLC (to the left on a
   timeline: design → code → build → test → deploy → operate).
   
   Why it matters:
   - Cost to fix a vulnerability at design: $1
   - Cost at code review: $10
   - Cost at testing: $100
   - Cost in production: $1,000+
   
   Implementation at each stage:
   
   Design phase:
   - Threat modeling (STRIDE: Spoofing, Tampering, Repudiation, Info Disclosure,
     Denial of Service, Elevation of Privilege)
   - Security requirements in user stories
   - Architecture review: identify trust boundaries
   
   Code phase (developer machine):
   - IDE plugins: Snyk for VS Code, SonarLint, CodeQL
   - Pre-commit hooks: gitleaks (secret detection), bandit (Python SAST)
   - Developer security training: OWASP Top 10, secure coding patterns
   
   Code review:
   - Checklist: "Does this PR handle authentication? Input validation? Logging?"
   - Security champion reviews PRs for sensitive modules
   
   CI pipeline:
   - SAST: Semgrep, CodeQL (runs on every PR)
   - Dependency scanning: Snyk, OWASP Dependency-Check
   - Secret scanning: TruffleHog, gitleaks
   - Container scanning: Trivy (on every image build)
   - IaC scanning: tfsec, checkov (on every Terraform PR)
   
   Pre-production:
   - DAST: OWASP ZAP baseline scan on staging deployment
   - Penetration testing: quarterly or before major releases
   
   Production:
   - Runtime security: Falco (K8s syscall monitoring)
   - SIEM: ship security-relevant logs to Elastic/Splunk
   - Continuous compliance: AWS Config rules, Kyverno policies

Q2: What is the OWASP Top 10? Pick 3 and explain how to prevent them.

A: OWASP Top 10 (2021):
   A01: Broken Access Control
   A02: Cryptographic Failures
   A03: Injection
   A04: Insecure Design
   A05: Security Misconfiguration
   A06: Vulnerable and Outdated Components
   A07: Identification and Authentication Failures
   A08: Software and Data Integrity Failures
   A09: Security Logging and Monitoring Failures
   A10: Server-Side Request Forgery (SSRF)
   
   A01 — Broken Access Control:
   What it is: Users can access resources/functions they shouldn't.
   Examples: Access /api/users/456 when logged in as user 123 (IDOR);
             Regular user accessing /admin; Horizontal privilege escalation.
   
   Prevention:
   - Enforce access control at server side (never client side)
   - Default deny: no access unless explicitly granted
   - Use UUIDs for resource IDs (harder to enumerate than sequential integers)
   - Test every API endpoint for authorization (automated BOLA testing)
   - Log all access control failures and alert on spikes
   
   # Python example — verify ownership before returning:
   def get_order(order_id, current_user):
       order = db.query(Order).filter_by(id=order_id).first()
       if order.user_id != current_user.id:
           raise PermissionDenied("Not your order")
       return order
   
   A03 — Injection (SQL, LDAP, OS command):
   What it is: Untrusted data sent to an interpreter as part of a command or query.
   
   Prevention:
   - Parameterized queries (NEVER string concatenation in SQL):
   
   # VULNERABLE:
   query = f"SELECT * FROM users WHERE username = '{username}'"
   
   # SAFE (parameterized):
   cursor.execute("SELECT * FROM users WHERE username = %s", (username,))
   
   - ORMs (SQLAlchemy, Hibernate) — parameterized by default
   - Input validation: whitelist allowed characters, reject unexpected input
   - Least privilege DB account: app user can't DROP tables
   
   A06 — Vulnerable and Outdated Components:
   What it is: Using libraries/frameworks with known CVEs.
   
   Prevention:
   - Dependency scanning in CI: Snyk, OWASP Dependency-Check
   - Dependabot: automated PRs for dependency updates
   - Keep base images updated (use Dependabot for Dockerfile FROM)
   - SBOM: know exactly what's in your software
   - Have a process to respond to critical CVEs within 48-72 hours

SECTION B: VULNERABILITY MANAGEMENT
================================================================================

Q3: A critical CVE is published affecting a library your application uses.
    Walk me through your response process.

A: Triage first (30 minutes):
   1. Read the CVE description: What is the attack vector?
      - Network exploitable vs local only?
      - Authentication required?
      - Does our usage pattern match the vulnerable code path?
   2. CVSS score: Critical (9.0+) or High (7.0+)?
   3. Check if a fix exists: has the library released a patched version?
   
   Assess impact (1-2 hours):
   4. Which of our services use this library?
      # Find in all requirements.txt / package.json / pom.xml:
      grep -r "library-name" . --include="requirements*.txt"
      # Or use Snyk/Grype with SBOM for quick cross-service query
   5. Is the vulnerable code path exercised?
      - Review how we use the library
      - If we use feature X and the CVE is in feature Y → lower priority
   
   Remediate (timeline depends on severity):
   Critical, network-exploitable, no auth: patch within 24-48 hours
   High: patch within 1-2 sprints (1-2 weeks)
   Medium: patch in next 1-2 months
   
   Remediation steps:
   6. Update library version to patched release
   7. Run existing tests to verify no breakage
   8. Create a PR — CI will scan and confirm CVE is resolved
   9. Deploy (expedited approval for critical)
   
   If no patch available:
   - Can we disable the vulnerable feature?
   - Workaround in WAF (block requests exploiting the CVE)?
   - Accept risk with documented reasoning and owner
   
   Communication:
   - Internal: security team + engineering manager + relevant service owners
   - External: if data was exposed, follow breach notification procedures
   
   Documentation:
   - Track CVE in security issue tracker
   - Note: discovered → triaged → patched → deployed dates
   - Used for audit trail and MTTR measurement

Q4: What is an SBOM and why is it important for vulnerability management?

A: SBOM = Software Bill of Materials
   A formal, machine-readable inventory of all components in a software product.
   
   Contents:
   - Component name, version, type (library, framework, OS package)
   - Package URL (PURL) — unique identifier
   - License (GPL, MIT, Apache 2.0) — for license compliance
   - Hash (SHA-256) — integrity verification
   - Relationships (which component depends on which)
   
   Why it matters:
   
   1. Rapid CVE response:
      When a new CVE is published, scan your SBOM to instantly know
      which services are affected — without scanning every image.
   
   2. License compliance:
      Identify GPL components that might require you to open-source your code.
      Important for commercial products.
   
   3. Regulatory requirements:
      US Executive Order 14028 (May 2021) requires SBOMs for software
      sold to the US federal government.
      HIPAA, PCI-DSS increasingly expect SBOMs for audit.
   
   4. Supply chain transparency:
      Customers can audit what's in your software.
   
   Generating SBOMs:
   # Syft (most popular):
   syft myapp:latest -o cyclonedx-json > sbom.json
   syft myapp:latest -o spdx-json > sbom.spdx.json
   
   # Trivy:
   trivy image --format cyclonedx myapp:latest > sbom.json
   
   Using SBOM for vulnerability scanning:
   # Faster than re-scanning image (use cached SBOM):
   grype sbom:./sbom.json
   
   # Attach SBOM as signed attestation to image (Cosign):
   cosign attest --predicate sbom.json --type cyclonedx myapp@$DIGEST

SECTION C: SECRETS MANAGEMENT AT SCALE
================================================================================

Q5: How do you manage secrets for 50+ microservices across multiple environments?

A: This is a systems design problem — no single tool, need a strategy.
   
   Core principle: Different secrets, different storage:
   
   Short-lived cloud credentials:
   Use OIDC — no stored secrets at all.
   GitHub Actions → AWS OIDC → Assume role → Temporary credentials (15 min)
   No rotation needed. No secret to leak.
   
   Application secrets (DB passwords, API keys):
   Central secrets manager + K8s External Secrets Operator (ESO).
   
   Architecture:
   AWS Secrets Manager / HashiCorp Vault
          │
          │ (pulls on schedule / on-demand)
          │
   External Secrets Operator (in K8s cluster)
          │
          │ (creates/updates)
          │
   Kubernetes Secrets ← Application reads from here
   
   Operational patterns for scale:
   
   Namespacing: /app/service-name/env/secret-name
   {service} = myapp, auth-service, payment-service
   {env} = dev, staging, production
   
   # AWS SM: prod/payment-service/db-credentials
   # Vault:  secret/data/production/payment-service/db
   
   Rotation strategy:
   - Use secrets with TTLs (Vault dynamic secrets) — auto-expire after 1h
   - Set up rotation automation (AWS SM Lambda rotation for RDS)
   - Never static secrets if avoidable
   
   CI/CD secrets:
   - OIDC for cloud provider auth (no stored keys)
   - GitHub Actions environments for per-environment secrets with approval gates
   - No production secrets in dev/staging CI jobs
   
   Audit:
   - All secret access logged (CloudTrail, Vault audit log)
   - Alert on: access by unexpected principal, access outside business hours
   - Quarterly: review who has access to what, revoke stale access

SECTION D: CONTAINER & KUBERNETES SECURITY
================================================================================

Q6: How do you harden a Kubernetes cluster from a security perspective?

A: Defense in depth — multiple layers:
   
   1. Control Plane Security:
   - Use managed K8s (EKS, GKE, AKS) — provider handles etcd encryption,
     API server TLS, control plane updates
   - Enable etcd encryption at rest (for Secrets)
   - Restrict API server access (private endpoint + authorized CIDR blocks)
   - Audit logging: log all API server requests to CloudWatch/Elasticsearch
   
   2. Authentication & Authorization:
   - Disable anonymous auth on API server
   - RBAC: least privilege for every ServiceAccount
   - No cluster-admin for application service accounts
   - Use OIDC for human users (tie to corporate IdP, not static kubeconfig certs)
   - Regularly audit: kubectl get rolebindings,clusterrolebindings -A
   
   3. Network Security:
   - Default deny all NetworkPolicy in every namespace
   - Allow only required traffic explicitly
   - Use Cilium for L7 policy (control by HTTP method/path, not just port)
   
   4. Pod Security:
   - Pod Security Standards: Restricted for production, Baseline for system
   - securityContext: non-root, readOnly filesystem, drop ALL capabilities
   - seccompProfile: RuntimeDefault on all pods
   
   5. Image Security:
   - Kyverno admission controller:
     * Allow only from trusted registries
     * Require signed images (Cosign)
     * Block :latest tag
   - Trivy scans in CI: block critical CVEs
   - ECR enhanced scanning + EventBridge alerts
   
   6. Runtime Security:
   - Falco: detect shell in container, package install, suspicious network
   - Falco Sidekick → PagerDuty/Slack for runtime alerts
   
   7. Secret Management:
   - Don't use base64-encoded K8s Secrets for sensitive data
   - Use External Secrets Operator → AWS SM / Vault
   - Consider Sealed Secrets or SOPS for GitOps secret management
   
   8. Regular hygiene:
   - kube-bench: CIS benchmark automated check
   - Trivy misconfig scan: trivy k8s --report summary cluster
   - Rotate certificates (check with: kubeadm certs check-expiration)

SECTION E: SUPPLY CHAIN SECURITY
================================================================================

Q7: What is a software supply chain attack and how do you defend against it?

A: Supply chain attack: compromise the tools or dependencies used to BUILD
   software, rather than attacking the software directly.
   
   Famous examples:
   - SolarWinds (2020): Build pipeline compromised, malicious code in signed binaries
   - Log4Shell (2021): Vulnerability in widely-used Log4j library (supply chain risk)
   - XZ Utils (2024): Backdoor inserted into open-source compression library
   - Codecov (2021): CI tool compromised, exfiltrated environment variables
   
   Defense layers:
   
   1. Know what you're using (SBOM):
      Generate SBOM for every build. Know all dependencies.
      When new CVE published → instantly know if affected.
   
   2. Pin dependency versions:
      requirements.txt: library==2.4.1  (not library>=2.4.0)
      Dockerfile: FROM debian@sha256:abc123 (digest pin, not tag)
      package-lock.json / Pipfile.lock / go.sum: lock transitive deps
   
   3. Verify integrity (hash checking):
      pip install uses hashes: pip install --require-hashes -r requirements.txt
      npm uses package-lock integrity field (SHA-512)
   
   4. Private artifact mirrors:
      Proxy PyPI, npm, Maven through Artifactory/Nexus.
      No direct internet downloads in build pipeline.
      Reduces dependency confusion attacks.
   
   5. Image signing (Cosign):
      Sign every image built in CI. Verify before deploying.
      Admission controller rejects unsigned images.
   
   6. SLSA framework:
      Level 2+: provenance attestation (cryptographically proves build origin)
      Level 3: isolated build environment (no network during build, reproducible)
   
   7. Build system security:
      Minimal CI/CD permissions (OIDC, not stored credentials)
      CI runners in isolated networks
      Audit all CI/CD changes (changes to .github/workflows require approval)

SECTION F: COMPLIANCE & ZERO TRUST
================================================================================

Q8: How do you implement compliance as code for SOC 2 or PCI-DSS?

A: Manual compliance audits are slow and point-in-time. Automate with code.
   
   Core idea: Express compliance requirements as code policies.
   Every resource change is checked against policies. Non-compliant = blocked.
   
   Tools:
   - AWS Config Rules: continuously evaluate AWS resource configurations
   - OPA/Conftest: policy as code for any JSON/YAML (Terraform, K8s, Docker)
   - Kyverno: K8s-native policy enforcement
   - Chef InSpec / OpenSCAP: OS-level compliance scanning
   
   SOC 2 — Common controls automated:
   
   CC6.1 (Logical access controls):
   - Kyverno: require RBAC, no cluster-admin for workloads
   - AWS Config: detect IAM policies with overly broad permissions
   
   CC6.3 (Access removal):
   - IAM Access Analyzer: identify unused permissions
   - Vault TTL-based tokens: access automatically expires
   
   CC7.2 (Monitoring for threats):
   - Falco: runtime threat detection → alert
   - AWS GuardDuty: threat detection for AWS API calls
   
   CC8.1 (Change management):
   - All changes via Git PRs (audit trail)
   - Required approvals before merge
   - Deployment audit log (who deployed what when)
   
   Evidence collection:
   - AWS Config: continuous compliance snapshots
   - Export to S3, review with auditors quarterly
   - Automation shows "we are always compliant" not "we were compliant 90 days ago"

SECTION G: SECURITY INCIDENT RESPONSE
================================================================================

Q9: You detect a container running a shell that shouldn't be there (Falco alert).
    What do you do?

A: This is a potential active attack or malicious insider.
   
   Immediate (first 5 minutes):
   1. Don't panic — assess before acting (some actions can destroy evidence)
   2. Capture forensics BEFORE killing the pod:
      # Capture running processes:
      kubectl exec suspicious-pod -- ps aux > forensics/processes.txt
      # Capture network connections:
      kubectl exec suspicious-pod -- netstat -antp > forensics/netstat.txt
      # Capture environment (check for exfiltrated secrets):
      kubectl exec suspicious-pod -- env > forensics/environment.txt
      # Capture recent command history (if shell has history):
      kubectl exec suspicious-pod -- cat /root/.bash_history
   
   3. Isolate the pod (block further damage):
      # Apply restrictive NetworkPolicy to isolate this pod:
      kubectl apply -f - <<EOF
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      metadata:
        name: isolate-suspicious-pod
        namespace: production
      spec:
        podSelector:
          matchLabels:
            app: suspicious-app
        policyTypes: [Egress, Ingress]
        # No egress/ingress rules = deny all
      EOF
   
   4. Assess blast radius:
      - What secrets/environment variables did the pod have access to?
      - What other services could the pod reach (before isolation)?
      - Was data exfiltrated? (Check outbound network logs in the time window)
   
   5. Rotate any credentials the pod had access to
   
   6. Kill the pod after forensic capture:
      kubectl delete pod suspicious-pod --force
   
   Post-incident:
   - How did the attacker get a shell? (Exploited vulnerability? Misconfigured RBAC?)
   - Is this an isolated incident or a broader compromise?
   - Deploy fix (patch CVE, fix RBAC, add NetworkPolicy)
   - Post-mortem + security retrospective

Q10: How does zero-trust security apply to a DevOps environment?

A: Zero Trust: "Never trust, always verify." No implicit trust based on network location.
   
   Traditional security: inside the network = trusted. Outside = untrusted.
   Problem: once attacker is inside the network, they can move laterally freely.
   
   Zero Trust principles applied to DevOps:
   
   No implicit trust based on network position:
   - K8s pods can't communicate freely just because they're in the same cluster
   - Enforce NetworkPolicy: default deny, explicit allow per service
   - Service mesh (Istio/Linkerd): mTLS between ALL services
     Every service proves its identity to every other service
   
   Least privilege access:
   - K8s RBAC: minimal permissions per ServiceAccount
   - AWS IAM: minimal permissions per service (no AdministratorAccess)
   - Secrets: only the services that need them can read them (Vault policies)
   
   Assume breach:
   - Falco: monitor runtime behavior (assume something will get in, detect it)
   - Micro-segmentation: even if one service is compromised, it can't reach others
   - Short-lived credentials: even if token is stolen, it expires in 1 hour
   
   Verify continuously:
   - mTLS: services re-authenticate on every request
   - OIDC tokens: re-issued frequently (not stored static credentials)
   - Regular access reviews: remove stale permissions
   
   Implementation in K8s (Istio service mesh):
   # Enforce mTLS everywhere in namespace:
   apiVersion: security.istio.io/v1beta1
   kind: PeerAuthentication
   metadata:
     name: default
     namespace: production
   spec:
     mtls:
       mode: STRICT   # Reject any non-mTLS traffic
   
   # Authorization policy: only frontend can call backend:
   apiVersion: security.istio.io/v1beta1
   kind: AuthorizationPolicy
   metadata:
     name: backend-policy
     namespace: production
   spec:
     selector:
       matchLabels:
         app: backend
     rules:
     - from:
       - source:
           principals: ["cluster.local/ns/production/sa/frontend-sa"]
       to:
       - operation:
           methods: ["GET", "POST"]
           paths: ["/api/*"]

OWASP TOP 10 (2021):
  A01  Broken Access Control        (BOLA, IDOR, missing authz checks)
  A02  Cryptographic Failures       (weak TLS, plaintext passwords)
  A03  Injection                    (SQL, LDAP, OS command)
  A05  Security Misconfiguration    (default creds, open S3, missing headers)
  A06  Vulnerable Components        (outdated dependencies — CVEs)

DEVSECOPS PIPELINE TOOLS:
  Pre-commit:   gitleaks, detect-secrets, bandit
  SAST:         Semgrep, CodeQL, SonarQube
  Dep Scan:     Snyk, Trivy, OWASP Dep-Check
  DAST:         OWASP ZAP, Burp Suite Enterprise
  Container:    Trivy, Grype, Cosign (signing)
  IaC:          tfsec, checkov, Conftest (OPA)
  Runtime:      Falco + Falco Sidekick

SECRET MANAGEMENT HIERARCHY:
  1st choice: No secrets (OIDC)
  2nd choice: Vault dynamic secrets (auto-expire)
  3rd choice: AWS/GCP/Azure Secrets Manager
  4th choice: K8s External Secrets (from above)
  Avoid:      K8s base64 Secrets for sensitive data
  Never:      Committed to Git, in Docker image, in app code

SUPPLY CHAIN SECURITY:
  SBOM:     Know what's in your software (Syft, Trivy)
  Sign:     Cosign keyless signing (OIDC-based)
  Verify:   Kyverno + Cosign at deploy time
  SLSA:     Provenance attestation (Level 2+ = signed, Level 3 = isolated build)
  Scan:     Scan registry continuously (ECR Inspector, Trivy cron)
