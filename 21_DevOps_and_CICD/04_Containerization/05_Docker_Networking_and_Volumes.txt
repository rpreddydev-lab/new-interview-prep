1. DOCKER NETWORKING OVERVIEW
================================================================================

Container Networking Model (CNM):
  Docker's networking architecture is based on three concepts:
  
  SANDBOX: Isolated network namespace for a container.
           Has its own interfaces, routes, DNS.
  
  ENDPOINT: Virtual network interface connecting a sandbox to a network.
            Uses veth (virtual Ethernet) pairs.
  
  NETWORK: Group of endpoints that can communicate with each other.
           Implemented using Linux bridges, iptables, overlay.

Network Types Overview:
  
  ┌─────────────┬──────────────────────────────────────────────────────────┐
  │ Driver      │ Description                                              │
  ├─────────────┼──────────────────────────────────────────────────────────┤
  │ bridge      │ Default. Isolated Linux bridge network on single host   │
  │ host        │ Container shares host network namespace (no isolation)  │
  │ none        │ No network connectivity                                 │
  │ overlay     │ Multi-host (Docker Swarm / Kubernetes)                  │
  │ macvlan     │ Container gets own MAC address (appears as physical)    │
  │ ipvlan      │ Container shares host MAC (L2 or L3 modes)             │
  └─────────────┴──────────────────────────────────────────────────────────┘

How Linux Networking Enables Docker Networking:
  
  NAMESPACES: Each container gets isolated network namespace (net namespace)
              Isolated: interfaces, routes, iptables rules, sockets
  
  VETH PAIRS: Virtual Ethernet cable with two ends
              One end in container namespace, other end on host bridge
  
  LINUX BRIDGE: Software switch (docker0 by default)
                Containers connect to bridge via veth pairs
                Bridge routes traffic between containers and to host
  
  IPTABLES: Docker manages iptables rules for:
            - NAT (MASQUERADE for outbound traffic)
            - Port forwarding (DNAT for -p published ports)
            - Container isolation
  
  Host Network (bridge docker0):
  
  ┌─────────────────────────────────────────────────────┐
  │ Host                                                │
  │  ┌────────────────────────────────────────────┐    │
  │  │ docker0 bridge (172.17.0.1)               │    │
  │  │   ┌────────┐        ┌────────┐            │    │
  │  │   │ veth0a │        │ veth1a │            │    │
  │  └───┴────────┴────────┴────────┴────────────┘    │
  │         │                    │                     │
  │    ┌────┴────┐          ┌────┴────┐               │
  │    │Container│          │Container│               │
  │    │ eth0    │          │ eth0    │               │
  │    │172.17.0.2│         │172.17.0.3│              │
  │    └─────────┘          └─────────┘               │
  └─────────────────────────────────────────────────────┘

2. BRIDGE NETWORKS (DEFAULT AND USER-DEFINED)
================================================================================

Default Bridge Network (docker0):
  Created automatically by Docker.
  All containers on default bridge can communicate via IP address.
  No DNS — containers cannot find each other by name.
  Considered LEGACY for production use.
  
  # Container on default bridge gets IP from 172.17.0.0/16
  docker run -d --name app1 nginx
  docker run -d --name app2 nginx
  
  # app1 cannot reach app2 by name "app2" — only by IP
  docker exec app1 ping 172.17.0.3    # Works (by IP)
  docker exec app1 ping app2          # FAILS (no DNS)

User-Defined Bridge Networks (RECOMMENDED):
  
  Create a dedicated network:
  docker network create my-network
  docker network create --driver bridge --subnet 10.10.0.0/16 my-network
  
  Run containers on custom network:
  docker run -d --name db --network my-network postgres:15
  docker run -d --name app --network my-network -e DB_HOST=db myapp
  
  Benefits over default bridge:
  ✓ AUTOMATIC DNS: Containers can reach each other by container name
  ✓ ISOLATION: Containers on different networks can't communicate
  ✓ CONNECT/DISCONNECT at runtime without restarting
  ✓ Better network configuration (subnet, gateway)

Network Commands:
  docker network create my-network
  docker network create \
    --driver bridge \
    --subnet 172.20.0.0/16 \
    --gateway 172.20.0.1 \
    --label env=prod \
    my-network
  
  docker network ls                    # List networks
  docker network inspect my-network   # View details, connected containers
  docker network rm my-network        # Remove network
  docker network prune                 # Remove unused networks
  
  docker network connect my-network container     # Add running container to network
  docker network disconnect my-network container  # Remove from network

Multi-Network Containers:
  A container can be on multiple networks simultaneously.
  Common pattern: frontend + backend separation.
  
  docker network create frontend
  docker network create backend
  
  docker run --network frontend --name web nginx   # Only on frontend
  docker run --network backend --name db postgres  # Only on backend
  docker run --network frontend --name api myapp   # Start on frontend
  docker network connect backend api               # Also connect to backend
  # api can reach both web (frontend) and db (backend)
  # web CANNOT reach db (not on same network)

3. HOST NETWORK
================================================================================

How Host Networking Works:
  Container skips network namespace isolation.
  Binds directly to host's network stack.
  Container sees all host interfaces.
  Ports are directly on host — no port mapping needed.
  
  docker run --network host nginx
  # nginx's port 80 is directly on host's port 80
  # No need for -p 80:80

When to Use Host Networking:
  ✓ High-performance networking (minimal overhead)
  ✓ Monitoring agents that need to see all host network traffic
  ✓ Services that need to bind to specific host IPs
  ✓ Network testing and debugging
  
  ✗ NOT for general application services (no isolation)
  ✗ Port conflicts with host services

Practical Example:
  # Prometheus Node Exporter needs access to host network:
  docker run -d \
    --network host \
    --pid host \
    prom/node-exporter
  # Exposes metrics at host:9100 without port mapping

Host vs Bridge Performance:
  Host networking eliminates NAT overhead and has lower latency.
  Typically 10-20% faster for high-throughput networking workloads.

================================================================================
4. NONE NETWORK
================================================================================

How None Networking Works:
  Container has its own network namespace but NO interfaces configured
  (except loopback: lo).
  
  No external connectivity. Cannot reach internet or other containers.
  
  docker run --network none myapp

When to Use None Networking:
  ✓ Security-sensitive batch processing (no network access needed)
  ✓ CPU/memory-bound workloads that shouldn't have network access
  ✓ Security hardening (defense in depth)
  ✓ Testing how app handles no network connectivity

5. OVERLAY NETWORK (DOCKER SWARM)
================================================================================

What is Overlay Networking:
  Multi-host virtual network that spans multiple Docker hosts.
  Containers on different hosts can communicate as if on same LAN.
  Uses VXLAN (Virtual Extensible LAN) encapsulation over UDP port 4789.
  Requires Docker Swarm mode to create overlay networks.

Architecture:
  Host A                    Host B
  ┌─────────────────┐      ┌─────────────────┐
  │ Container1      │      │ Container2       │
  │ eth0: 10.0.1.2  │      │ eth0: 10.0.1.3   │
  │      │          │      │      │           │
  │  VXLAN tunnel ──┼──────┼── VXLAN tunnel   │
  │  eth0: 192.168. │      │  eth0: 192.168.  │
  └─────────────────┘      └─────────────────┘
  
  Packet from Container1 to Container2:
  1. Inner IP packet: src=10.0.1.2, dst=10.0.1.3
  2. Wrapped in VXLAN header with VNID
  3. Outer UDP packet: src=192.168.1.10, dst=192.168.1.20 (host IPs)
  4. Transmitted across physical network
  5. Target host unwraps and delivers to container

Creating Overlay Networks (Swarm):
  # Initialize Swarm
  docker swarm init
  
  # Create overlay network
  docker network create \
    --driver overlay \
    --subnet 10.0.9.0/24 \
    --opt encrypted \           # Encrypt overlay traffic
    my-overlay-net
  
  # Deploy service on overlay network
  docker service create \
    --name myapp \
    --network my-overlay-net \
    --replicas 3 \
    myapp:v1

6. MACVLAN NETWORK
================================================================================

What is Macvlan:
  Each container gets its own MAC address.
  Container appears as physical device on the network.
  IP assigned from physical network's subnet.
  
  Use cases:
  - Legacy applications that need to be "on the physical network"
  - Applications needing specific MAC addresses
  - Network appliances, monitoring

Macvlan Setup:
  # Create macvlan network
  docker network create \
    --driver macvlan \
    --subnet 192.168.1.0/24 \
    --gateway 192.168.1.1 \
    --opt parent=eth0 \         # Physical interface to attach to
    my-macvlan
  
  # Run container with specific IP
  docker run --network my-macvlan \
    --ip 192.168.1.100 \
    nginx

Note: Containers on macvlan can communicate with physical hosts on the network
but NOT with the Docker host itself (by default, due to macvlan promiscuous
mode limitations). Use macvlan in bridge mode for host communication.

7. DNS AND SERVICE DISCOVERY IN DOCKER
================================================================================

Embedded DNS Server:
  Docker runs an embedded DNS server at 127.0.0.11.
  Containers on user-defined networks use this for name resolution.
  
  Resolution order:
  1. Container name
  2. Network alias
  3. Service name (Docker Swarm)
  4. External DNS (from host's /etc/resolv.conf)

Container Name Resolution:
  docker network create mynet
  docker run --name database --network mynet postgres
  docker run --name webapp --network mynet myapp
  
  # webapp can reach database at:
  # database         (container name)
  # database.mynet   (FQDN within network)

Network Aliases:
  docker run --name db-primary \
    --network mynet \
    --network-alias db \         # Additional DNS alias
    postgres
  
  docker run --name db-replica \
    --network mynet \
    --network-alias db \         # Both resolve to "db"
    postgres
  # If multiple containers have same alias, Docker load-balances

Custom DNS in Containers:
  docker run --dns 8.8.8.8 --dns 8.8.4.4 myapp
  docker run --dns-search example.com myapp

8. PORT PUBLISHING AND EXPOSURE
================================================================================

Port Publishing vs Expose:
  
  EXPOSE in Dockerfile:
    Documentation only. Doesn't publish ports.
    Tells users "this container listens on this port."
  
  -p / --publish:
    Actually publishes a port. Creates iptables DNAT rule.
    Maps container port to host port.
  
  -P / --publish-all:
    Publishes all EXPOSE'd ports to random ephemeral ports.

Port Mapping Syntax:
  
  -p 8080:80              # host:container — all IPs, TCP (default)
  -p 127.0.0.1:8080:80   # Bind only to localhost (more secure)
  -p 8080:80/tcp          # Explicit TCP
  -p 5353:5353/udp        # UDP port
  -p 8080-8090:80-90      # Port range
  
  # Ephemeral port (random host port):
  -p 80                   # Host assigns random port from ephemeral range

View Port Mappings:
  docker port my-container          # All port mappings
  docker port my-container 80       # Mapping for container port 80
  docker ps --format "table {{.Names}}\t{{.Ports}}"

Inspecting Port Configuration:
  docker inspect my-container \
    --format '{{json .NetworkSettings.Ports}}'

9. NETWORK TROUBLESHOOTING
================================================================================

Common Troubleshooting Steps:
  
  1. VERIFY NETWORK EXISTS AND CONTAINERS ARE CONNECTED:
     docker network inspect my-network
     # Shows connected containers and their IPs
  
  2. CHECK CONTAINER IP:
     docker inspect container --format '{{.NetworkSettings.Networks.my-network.IPAddress}}'
     # Or:
     docker exec container ip addr show eth0
  
  3. TEST CONNECTIVITY:
     docker exec container ping other-container
     docker exec container curl http://other-container:8080/health
  
  4. DNS RESOLUTION:
     docker exec container nslookup other-container
     docker exec container cat /etc/resolv.conf   # Check DNS server
  
  5. NETWORK PATH:
     docker exec container traceroute 8.8.8.8
     docker exec container netstat -tulnp         # Listening ports
  
  6. IPTABLES RULES:
     sudo iptables -L -n -t nat                   # NAT rules
     sudo iptables -L DOCKER -n                   # Docker rules

Useful Debugging Container:
  # busybox or alpine with network tools
  docker run --rm --network my-network -it nicolaka/netshoot
  # Includes: curl, wget, nslookup, dig, ping, traceroute, nmap, tcpdump, etc.

Common Issues:
  
  CONTAINER CAN'T REACH INTERNET:
  - Check host's internet connectivity
  - Check Docker daemon's DNS config
  - Check iptables MASQUERADE rule: sudo iptables -t nat -L POSTROUTING
  
  CONTAINERS CAN'T REACH EACH OTHER BY NAME:
  - Are they on the same USER-DEFINED network? (default bridge has no DNS)
  - Create user-defined network and reconnect containers
  
  PORT NOT ACCESSIBLE FROM HOST:
  - Is -p flag used? EXPOSE alone doesn't publish
  - Check which IP the port is bound to:
    netstat -tlnp | grep 8080
    # If bound to 127.0.0.1 only, not accessible from outside

10. DOCKER VOLUMES OVERVIEW
================================================================================

Storage Options:
  
  Docker containers have a layered filesystem:
  ┌────────────────────────────────────────┐
  │ Container Layer (writable, ephemeral)  │
  ├────────────────────────────────────────┤
  │ Image Layer N (read-only)              │
  ├────────────────────────────────────────┤
  │ Image Layer 2 (read-only)              │
  ├────────────────────────────────────────┤
  │ Image Layer 1 (read-only)              │
  └────────────────────────────────────────┘
  
  Container writable layer:
  - Exists only as long as container exists
  - Stored in /var/lib/docker/overlay2 (OverlayFS)
  - Not suitable for persistent data
  
  For persistence, use external storage:
  ┌─────────────────────────────────────────────────────────────────┐
  │ Type          │ Location              │ Persistence │ Portability│
  ├───────────────┼───────────────────────┼─────────────┼────────────┤
  │ Named Volume  │ Docker-managed        │ Yes         │ Good       │
  │ Bind Mount    │ Host filesystem       │ Depends     │ Limited    │
  │ tmpfs Mount   │ Host RAM (memory)     │ No          │ N/A        │
  └───────────────┴───────────────────────┴─────────────┴────────────┘

11. NAMED VOLUMES
================================================================================

Overview:
  Named volumes are managed by Docker. Stored at:
  /var/lib/docker/volumes/<volume-name>/_data
  
  Benefits:
  ✓ Easy to backup and restore
  ✓ Can be shared between containers
  ✓ Exist independently of containers
  ✓ Volume drivers support NFS, EBS, etc.
  ✓ No absolute host path needed (portable compose files)

Creating and Using Named Volumes:
  
  # Create named volume
  docker volume create mydata
  
  # Use named volume
  docker run -v mydata:/var/lib/postgresql/data postgres:15
  docker run --mount type=volume,source=mydata,target=/var/lib/postgresql/data postgres
  
  # Both containers share the same volume:
  docker run --name writer -v shared:/data alpine sh -c "echo hello > /data/test.txt"
  docker run --name reader -v shared:/data alpine cat /data/test.txt
  # reader sees: hello

Volume Commands:
  docker volume ls                                    # List volumes
  docker volume create myvolume                      # Create
  docker volume inspect myvolume                     # Inspect (find path)
  docker volume rm myvolume                          # Delete (fails if in use)
  docker volume rm $(docker volume ls -q)            # Delete all
  docker volume prune                                 # Delete unused volumes

Volume Backup and Restore:
  
  # Backup: Create temp container, mount volume + host dir, tar it
  docker run --rm \
    -v myvolume:/data \
    -v $(pwd):/backup \
    alpine:3.18 \
    tar czf /backup/myvolume-backup.tar.gz -C /data .
  
  # Restore:
  docker run --rm \
    -v myvolume:/data \
    -v $(pwd):/backup \
    alpine:3.18 \
    tar xzf /backup/myvolume-backup.tar.gz -C /data

Volume Inspect (find actual path):
  docker volume inspect myvolume
  # Output includes "Mountpoint": "/var/lib/docker/volumes/myvolume/_data"
  # You can browse: ls /var/lib/docker/volumes/myvolume/_data

12. BIND MOUNTS
================================================================================

Overview:
  Map a host filesystem path directly into the container.
  Any change in container immediately appears on host (and vice versa).
  
  Syntax:
  docker run -v /absolute/host/path:/container/path
  docker run --mount type=bind,source=/host/path,target=/container/path

Use Cases:
  
  DEVELOPMENT: Mount source code for live reload without rebuilding
  docker run -v $(pwd):/app -p 3000:3000 node:18-alpine npm run dev
  
  CONFIG FILES: Mount configuration files from host
  docker run -v /etc/myapp/config.yaml:/app/config.yaml:ro myapp
  
  LOG COLLECTION: Mount log directories
  docker run -v /var/log/app:/app/logs myapp
  
  DATA IMPORT/EXPORT: Pass files to/from container
  docker run -v $(pwd)/data:/data myapp python process.py

Important Notes:
  
  - Path must exist on host (Docker doesn't create it for you like with volumes)
  - Bind mounts bypass Docker's ownership/permission model
    If host path is owned by root, container process needs root to write it
  
  # Set correct permissions:
  docker run -v $(pwd)/data:/app/data --user $(id -u):$(id -g) myapp
  
  Read-only bind mount:
  docker run -v /host/config:/container/config:ro myapp

Bind Mounts vs Named Volumes:
  
  Feature              Named Volume              Bind Mount
  ──────────────────────────────────────────────────────────
  Managed by Docker    Yes                       No
  Host path needed     No                        Yes
  Works on all hosts   Yes (Docker manages)      No (requires same host path)
  Performance          Good (volume driver)      Good (direct host FS)
  Docker manages perms Yes                       No (host perms)
  Portable             Yes                       No (absolute path)
  Best for             Prod data, databases      Dev code mounting, configs

13. TMPFS MOUNTS
================================================================================

Overview:
  Stored in host RAM (not on disk).
  Fast. Disappears when container stops.
  Never written to host filesystem or container filesystem.

Use Cases:
  ✓ Sensitive data (tokens, credentials) that shouldn't persist
  ✓ Cache files that don't need persistence
  ✓ High-performance temporary files
  ✓ Testing (guarantee fresh state every run)

Usage:
  # Using --tmpfs
  docker run --tmpfs /tmp myapp
  docker run --tmpfs /tmp:rw,noexec,nosuid,size=65536k myapp
  
  # Using --mount (more options):
  docker run \
    --mount type=tmpfs,destination=/tmp,tmpfs-mode=1770,tmpfs-size=65536k \
    myapp
  
  # Multiple tmpfs:
  docker run --tmpfs /tmp --tmpfs /var/run myapp

In Docker Compose:
  services:
    app:
      tmpfs:
        - /tmp
        - /var/run:rw,noexec,nosuid

Security Note:
  Useful for containers that have read-only root filesystems:
  docker run --read-only --tmpfs /tmp --tmpfs /run myapp
  # Main filesystem: immutable
  # /tmp and /run: writable but in RAM, not on disk

14. VOLUME DRIVERS AND PLUGINS
================================================================================

Default Local Driver:
  Default volume driver: local
  Stores at /var/lib/docker/volumes/ on Docker host
  
  Local driver options (bind, tmpfs, NFS):
  docker volume create \
    --driver local \
    --opt type=nfs \
    --opt o=addr=10.0.0.1,rw,nfsvers=4 \
    --opt device=:/exports/data \
    nfs-volume

Third-Party Volume Drivers:
  
  REX-RAY (EMC, for cloud storage):
  docker plugin install rexray/ebs         # AWS EBS plugin
  docker volume create --driver rexray/ebs my-ebs-volume
  
  AZURE STORAGE:
  docker plugin install azure-storage-driver
  
  Kubernetes CSI (equivalent in K8s):
  - AWS EBS CSI Driver
  - Google Persistent Disk CSI Driver
  - Azure Disk CSI Driver
  - NFS CSI Driver

Volume Plugins for Cloud:
  In Kubernetes, PersistentVolumes + StorageClasses replace volume plugins.
  CSI (Container Storage Interface) is the standard.

15. DATA PERSISTENCE PATTERNS
================================================================================

Pattern 1: Database Data Volume
  
  # Always use a named volume for database data
  version: "3.9"
  services:
    postgres:
      image: postgres:15
      volumes:
        - postgres_data:/var/lib/postgresql/data   # Persists across restarts
      environment:
        POSTGRES_DB: myapp
        POSTGRES_USER: user
        POSTGRES_PASSWORD: password
  
  volumes:
    postgres_data:       # Docker-managed named volume

Pattern 2: Development Code Mount
  
  services:
    app:
      build: .
      volumes:
        - .:/app                      # Mount source code (live reload)
        - /app/node_modules           # Anonymous volume: don't overwrite
      ports:
        - "3000:3000"
      command: npm run dev            # Watches for file changes
  
  # The /app/node_modules trick:
  # Without it, host's node_modules (possibly empty) would override container's
  # The anonymous volume at /app/node_modules takes precedence over the bind mount

Pattern 3: Config Injection
  
  # Mount config file(s) as read-only
  services:
    nginx:
      image: nginx:alpine
      volumes:
        - ./nginx.conf:/etc/nginx/nginx.conf:ro   # Read-only config
        - ./ssl:/etc/nginx/ssl:ro                 # Read-only certs

Pattern 4: Log Collection
  
  services:
    app:
      volumes:
        - app_logs:/var/log/app
    
    filebeat:
      image: elastic/filebeat:8.10.0
      volumes:
        - app_logs:/var/log/app:ro      # Read-only access to app logs
        - ./filebeat.yml:/usr/share/filebeat/filebeat.yml:ro
  
  volumes:
    app_logs:

Pattern 5: Shared Scratch Space
  
  # Multiple containers writing to same scratch volume
  services:
    producer:
      volumes:
        - scratch:/workspace
    
    consumer:
      volumes:
        - scratch:/workspace
  
  volumes:
    scratch:
      driver: local
      driver_opts:
        type: tmpfs     # In-memory scratch space
        device: tmpfs

Data Portability and Backup:
  
  Best practice for stateful containers:
  1. Use named volumes for all important data
  2. Schedule regular backups using backup containers
  3. For K8s: Use PersistentVolumes with a StorageClass that supports snapshots
  4. Test restoration periodically
  
  # Automated backup with cron container:
  docker run \
    --rm \
    -v postgres_data:/data:ro \
    -v /backup:/backup \
    -e BACKUP_DATE=$(date +%Y%m%d_%H%M) \
    alpine:3.18 \
    tar czf /backup/pg-backup-$BACKUP_DATE.tar.gz -C /data .

16. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: Explain the different Docker network types and when you'd use each.
A: Docker has several network drivers:
   
   BRIDGE (default): Creates an isolated network on a single Docker host.
   User-defined bridge networks are the standard choice for multi-container
   apps on a single host. They provide automatic DNS (containers find each
   other by name), configurable subnets, and network isolation.
   
   HOST: Container uses the host's network namespace directly — no isolation.
   Use for performance-sensitive apps (no NAT overhead) or when the container
   needs direct access to host network interfaces (like monitoring agents).
   
   NONE: No network connectivity at all. Only loopback. Use for security-
   sensitive batch jobs that need complete network isolation.
   
   OVERLAY: Multi-host network for Docker Swarm. Containers on different
   physical hosts communicate as if on the same network using VXLAN tunneling.
   
   MACVLAN: Each container gets a real MAC address and appears as a physical
   device on the network. Used for legacy apps that need to be "on the
   physical network" or need specific MAC addresses.
   
   In modern production setups, most use bridge networks for single-host
   or overlay for Swarm. Kubernetes has its own CNI-based networking.

Q2: What is the difference between a named volume and a bind mount?
A: Both mount storage into containers, but they differ significantly:
   
   NAMED VOLUME:
   - Docker creates and manages the storage (at /var/lib/docker/volumes/)
   - Referenced by name, not path: -v mydata:/container/path
   - Portable: works on any Docker host (Docker creates the directory)
   - Docker manages permissions
   - Best for: Production data, databases, shared data between containers
   
   BIND MOUNT:
   - Maps a specific host filesystem path: -v /host/absolute/path:/container/path
   - Host path must exist
   - Not portable: hardcodes a host path
   - Host file permissions apply
   - Best for: Development (mount source code), config injection, log collection
   
   For production databases, ALWAYS use named volumes. For development
   source code mounting, bind mounts are the right choice.

Q3: Why can't two containers on the default bridge network communicate by name?
A: The default bridge network (docker0) doesn't have Docker's embedded DNS
   resolver configured. DNS resolution only works on USER-DEFINED bridge
   networks.
   
   On the default bridge, containers can only communicate by IP address.
   This is a legacy limitation maintained for backward compatibility.
   
   Solution: Always create user-defined networks:
   docker network create my-app-net
   docker run --name api --network my-app-net myapi
   docker run --name db --network my-app-net postgres
   # api can now reach db at "db:5432"
   
   In Docker Compose, a custom network is automatically created for your
   project, which is why service names work as hostnames in Compose.

Q4: How do you ensure data persistence for a database container?
A: Container filesystems are ephemeral — data in the container's writable
   layer is lost when the container is removed.
   
   For databases, always use a named volume:
   docker run -d \
     --name postgres \
     -v postgres_data:/var/lib/postgresql/data \
     postgres:15
   
   The named volume persists even after:
   docker rm postgres                  # Container removed
   docker stop postgres                # Container stopped
   
   When you create a new container mounting the same volume, all data is there:
   docker run -d --name postgres2 -v postgres_data:/var/lib/postgresql/data postgres:15
   
   Additionally:
   - Schedule regular backups of the volume
   - For production, consider cloud storage volumes (EBS, GCP PD)
   - Use docker volume prune carefully — it deletes ALL unused volumes
   - Use docker compose down (NOT docker compose down -v) to preserve volumes

Q5: Explain Docker port publishing. What's the difference between EXPOSE and -p?
A: These are commonly confused:
   
   EXPOSE instruction in Dockerfile:
   - Pure documentation. Tells users "this container listens on this port"
   - Does NOT make the port accessible from the host
   - Useful for docker-compose automatic port mapping and documentation
   
   -p flag when running:
   - Actually creates a mapping from host port to container port
   - Uses iptables DNAT rules: traffic to host:8080 → container:80
   - Makes port accessible from outside
   
   Syntax: -p [host-ip:]host-port:container-port[/protocol]
   -p 8080:80             # All host IPs on port 8080 → container port 80
   -p 127.0.0.1:8080:80  # Only localhost → more secure
   -p 8080:80/udp         # UDP
   
   -P flag:
   - Publishes ALL EXPOSE'd ports to random ephemeral host ports
   - Useful for testing when you don't care about the exact host port
   - Find the mapped port: docker port container 80
   
   Best practice for production: Bind to specific IPs and use specific ports.
   If behind a load balancer, often no port publishing is needed at all
   (use container networking directly).

NETWORK TYPES:
  bridge     Default. Isolated. User-defined enables DNS by name.
  host       No isolation. Shares host network. Performance.
  none       No connectivity. Isolation.
  overlay    Multi-host (Docker Swarm). VXLAN.
  macvlan    Container gets own MAC. Appears on physical network.

NETWORK COMMANDS:
  docker network create name [--driver bridge] [--subnet x.x.x.0/24]
  docker network ls
  docker network inspect name
  docker network rm name
  docker network connect net container
  docker network disconnect net container
  docker network prune

RUN WITH NETWORK:
  docker run --network host myapp
  docker run --network none myapp
  docker run --network mynet --name myapp myapp

PORT PUBLISHING:
  -p 8080:80             # host:container (all IPs)
  -p 127.0.0.1:8080:80  # specific host IP
  -p 8080:80/udp         # UDP
  -P                     # All EXPOSE'd ports to random host ports
  docker port container  # Show port mappings

VOLUME TYPES:
  Named Volume    Docker-managed. -v name:/path. Persistent.
  Bind Mount      Host path. -v /host/path:/cont/path. Dev use.
  tmpfs           RAM. --tmpfs /path. No persistence. Fast. Secure.

VOLUME COMMANDS:
  docker volume create name
  docker volume ls
  docker volume inspect name
  docker volume rm name
  docker volume prune

MOUNT SYNTAX:
  -v name:/path              Named volume
  -v /host/path:/cont/path   Bind mount
  -v /host/path:/cont:ro     Bind mount (read-only)
  --tmpfs /path              tmpfs mount

PERSISTENCE SUMMARY:
  Databases:   Named volume (/var/lib/postgresql/data, etc.)
  Dev code:    Bind mount (./src:/app/src)
  Config:      Bind mount (./config.yaml:/app/config.yaml:ro)
  Temp/secrets: tmpfs

DNS IN COMPOSE/USER-DEFINED NETWORKS:
  service_name:port          # Use service name as hostname
  db:5432                    # PostgreSQL
  redis:6379                 # Redis
  # DNS only works on user-defined networks, NOT default bridge!

NETWORKING TROUBLESHOOTING:

  docker exec cont nslookup other      # Test DNS
  docker exec cont netstat -tulnp      # Listening ports
  docker run --rm --network net -it nicolaka/netshoot  # Debug container
