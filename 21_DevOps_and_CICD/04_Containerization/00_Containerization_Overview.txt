1. WHAT IS CONTAINERIZATION?
================================================================================

Definition:
  Containerization is a lightweight alternative to full machine virtualization
  that allows applications and their dependencies to run in isolated user-space
  instances called CONTAINERS.
  
  A container packages:
  - Application code
  - Runtime (Node.js, Python, Java JRE)
  - Libraries and dependencies
  - Configuration files
  - System tools needed by the application
  
  CONTAINER ≠ Virtual Machine
  A container shares the HOST OS kernel but has its own isolated:
  - Filesystem (via overlay FS)
  - Process space (via Linux namespaces)
  - Network stack (via network namespaces)
  - Resource limits (via cgroups)

The "Works on My Machine" Problem (Solved by Containers):
  
  Developer builds app locally:
    "It works on my MacBook!"
  
  QA tests on different machine:
    "It fails because Python 3.9 is not installed."
  
  Ops deploys to production:
    "It crashes because the production OS has a different SSL version."
  
  CONTAINER SOLUTION:
    Container IMAGE = Application + ALL dependencies
    Image runs identically on developer's laptop, CI server, staging, production
    "It works on my machine? Ship the machine!" — Paul Nasrat

Fundamental Concepts:
  
  CONTAINER IMAGE:
    Read-only template for creating containers.
    Immutable: Cannot change once built.
    Composed of layers (each Dockerfile instruction adds a layer).
    Stored in container registry (Docker Hub, ECR, GCR).
    
  CONTAINER:
    Running instance of a container image.
    Has a writable layer on top of the image layers.
    Isolated: Has its own process space, network, filesystem view.
    Ephemeral: Designed to be created and destroyed easily.
    
  CONTAINER REGISTRY:
    Store for container images. Similar to package registry.
    Public: Docker Hub, GitHub Container Registry.
    Private: AWS ECR, Google GCR, Azure ACR, self-hosted Harbor.

2. CONTAINERS VS VIRTUAL MACHINES
================================================================================

VIRTUAL MACHINES (VMs):
  ┌─────────────────────────────────────────────────────┐
  │              Physical Hardware                       │
  ├─────────────────────────────────────────────────────┤
  │              Hypervisor (VMware, Hyper-V, KVM)       │
  ├───────────────┬────────────────┬───────────────────┤
  │   VM 1        │   VM 2         │   VM 3            │
  │ ┌──────────┐  │ ┌──────────┐   │ ┌──────────┐     │
  │ │ Guest OS │  │ │ Guest OS │   │ │ Guest OS │     │
  │ │ (Linux)  │  │ │(Windows) │   │ │ (Linux)  │     │
  │ ├──────────┤  │ ├──────────┤   │ ├──────────┤     │
  │ │Libraries │  │ │Libraries │   │ │Libraries │     │
  │ ├──────────┤  │ ├──────────┤   │ ├──────────┤     │
  │ │  App 1   │  │ │  App 2   │   │ │  App 3   │     │
  │ └──────────┘  │ └──────────┘   │ └──────────┘     │
  └───────────────┴────────────────┴───────────────────┘
  Each VM: Full OS (1-20 GB), separate kernel, strong isolation
  Boot time: Minutes
  Overhead: Significant (full OS per app)
  Density: 10-20 VMs per physical host typical

CONTAINERS:
  ┌────────────────────────────────────────────────────┐
  │              Physical Hardware                      │
  ├────────────────────────────────────────────────────┤
  │              Host Operating System (Linux)          │
  ├────────────────────────────────────────────────────┤
  │              Container Runtime (Docker, containerd) │
  ├──────────────┬────────────────┬───────────────────┤
  │ Container 1  │ Container 2    │ Container 3        │
  │ ┌──────────┐ │ ┌──────────┐  │ ┌──────────┐      │
  │ │Libraries │ │ │Libraries │  │ │Libraries │      │
  │ ├──────────┤ │ ├──────────┤  │ ├──────────┤      │
  │ │  App 1   │ │ │  App 2   │  │ │  App 3   │      │
  │ └──────────┘ │ └──────────┘  │ └──────────┘      │
  └──────────────┴────────────────┴───────────────────┘
  All containers share host OS kernel. No separate OS per container.
  Boot time: Milliseconds to seconds
  Overhead: Minimal (just the app + libraries)
  Density: 100s of containers per host

Comparison Table:

  ATTRIBUTE          CONTAINERS         VIRTUAL MACHINES
  ───────────────────────────────────────────────────────────────
  Isolation          Process-level      Full OS-level
  OS                 Shared host kernel Full separate OS
  Boot time          Milliseconds       Minutes
  Size               MBs                GBs
  Density            100s per host      10-20 per host
  Startup            Nearly instant     Slow
  Portability        High (image)       Medium (OVA files)
  Security           Lower (shared OS)  Higher (isolated OS)
  Performance        Near-native        ~5-10% overhead
  Use case           Microservices, CI  Legacy apps, diff OS

When to Use VMs vs Containers:
  
  USE CONTAINERS FOR:
  - Microservices (many small services per host)
  - CI/CD pipelines (fast startup, isolated test environments)
  - Stateless web applications
  - Development environments (Docker Compose)
  - Cloud-native applications
  
  USE VMs FOR:
  - Applications requiring strong security isolation (multi-tenant)
  - Applications requiring different OS (Windows app on Linux host)
  - Legacy applications that can't be containerized
  - Applications with strict compliance requirements (HIPAA, PCI)
  - Databases needing dedicated I/O resources

Hybrid: VMs + Containers:
  Production cloud environments typically use both:
  - VMs provide the infrastructure (EC2 instances, GCE VMs)
  - Containers run on top of VMs for density and fast deployment
  
  AWS EKS: Kubernetes pods run in containers, which run on EC2 VMs (worker nodes)

3. HISTORY AND EVOLUTION
================================================================================

1979 — Unix chroot:
  First isolation primitive.
  Changes the apparent root directory for the current running process.
  Process cannot access files outside its chroot "jail."
  Limited: No network, CPU, memory isolation.

2000 — FreeBSD Jails:
  Enhanced chroot with network stack isolation.
  Each jail has its own IP address.
  Influenced later container technologies.

2006 — Google Process Containers (cgroups):
  Google's engineers develop control groups (cgroups).
  Resource limiting: CPU, memory, disk I/O per process group.
  Donated to Linux kernel in 2008.
  cgroups become foundational for containers.

2008 — Linux Containers (LXC):
  Combines cgroups + Linux namespaces.
  First true Linux container implementation.
  Provided full OS-level containers.

2013 — Docker:
  DotCloud (PaaS company) releases Docker as open source.
  Key innovation: EASY TO USE developer experience.
  Simple commands: docker build, docker run, docker push
  Dockerfile: Declarative container image definition
  Docker Hub: Public container registry
  Docker made containers accessible to every developer.

2014 — Kubernetes (Google):
  Container orchestration problem: How do you manage 1000s of containers?
  Google open-sources Kubernetes (based on internal Borg system).
  Solves: Scheduling, scaling, networking, storage for containers.

2015 — Open Container Initiative (OCI):
  Industry creates standards for containers.
  Docker, CoreOS, Google, and others collaborate.
  OCI Image Spec: How container images are structured
  OCI Runtime Spec: How containers are run (implemented by runc)
  Result: Vendor neutrality — images work with any OCI-compliant runtime.

2016 — containerd:
  Docker extracts the container runtime into containerd.
  Later donated to CNCF.
  containerd is now the default runtime in Kubernetes (replacing Docker in K8s).

2017-Present — Cloud-Native:
  CNCF (Cloud Native Computing Foundation): Hosts Kubernetes, containerd, etc.
  Containers become the standard deployment unit for cloud applications.
  Serverless containers: AWS Fargate, Google Cloud Run (containers without VMs)
  Security improvements: rootless containers, gVisor, Kata Containers

4. CONTAINER ARCHITECTURE
================================================================================

Linux Kernel Features Enabling Containers:

  NAMESPACES (Isolation):
    Process isolation — containers can't see each other's processes.
    
    Type             | What it isolates
    ─────────────────┼──────────────────────────────
    pid              | Process IDs (container has its own PID 1)
    net              | Network interfaces, IP, routing, firewall
    mnt              | Mount points (filesystem view)
    uts              | Hostname and domain name
    ipc              | Inter-process communication (semaphores, etc.)
    user             | User and group IDs (UID/GID mapping)
    cgroup           | Control groups root directory
    time             | System time (Linux 5.6+, rarely used)
    
    Container PID 1 is the main process. When it exits, container exits.
  
  CGROUPS (Resource Limits):
    Control Groups limit and track resource usage.
    Prevent one container from consuming all resources (noisy neighbor problem).
    
    Resources controlled:
    - cpu: CPU time allocation
    - memory: Memory limit + OOM handling
    - blkio: Block I/O (disk read/write)
    - net_cls: Network packet tagging
    - devices: Device access control
    
    Example: Limit container to 256MB RAM and 0.5 CPUs
    docker run --memory=256m --cpus=0.5 myapp
  
  OVERLAY FILESYSTEM:
    Container filesystem uses copy-on-write layers.
    
    Image layers (read-only):
    Layer 3: App code (25MB)
    Layer 2: Python libraries (80MB)
    Layer 1: Python runtime (50MB)
    Layer 0: Ubuntu base image (70MB)
    
    Container layer (read-write):
    Layer 4: Container writable layer (changes go here)
    
    Benefits:
    - Multiple containers can share the same image layers (disk efficient)
    - Container startup is fast (no copying — just mount layers)
    - Image layers are cached (rebuild only changed layers)
    
    Driver: overlay2 (default), btrfs, zfs

The Docker Architecture:

  Docker Client (docker CLI)
       │ REST API
       ▼
  Docker Daemon (dockerd)
       │
       ├── containerd (high-level runtime)
       │        │
       │        └── runc (low-level OCI runtime)
       │                │
       │                └── Creates/runs container using kernel namespaces+cgroups
       │
       ├── Docker Registry (pull/push images)
       └── Docker Volumes, Networks (manage state and connectivity)

  KEY COMPONENTS:
  
  DOCKER CLIENT (docker):
    CLI tool that sends commands to Docker daemon.
    Can connect to remote Docker daemons via TCP socket.
  
  DOCKER DAEMON (dockerd):
    Long-running process that manages containers, images, networks, volumes.
    Listens on Unix socket (/var/run/docker.sock) or TCP port.
    Uses containerd for container lifecycle management.
  
  CONTAINERD:
    High-level container runtime (manages image pull/push, storage, networking)
    OCI-compliant.
    Used directly by Kubernetes (without Docker daemon) since K8s 1.24.
  
  RUNC:
    Low-level OCI runtime that actually creates and runs containers.
    Uses Linux namespaces and cgroups.
    The reference implementation of the OCI Runtime Spec.

5. THE CONTAINER ECOSYSTEM
================================================================================

Container Runtimes:
  DOCKER:         Most popular. Full development experience.
  containerd:     Industry-standard high-level runtime (CNCF project).
  CRI-O:          Kubernetes-focused runtime implementing CRI (Container Runtime Interface).
  Podman:         Daemonless Docker alternative (rootless, no root daemon needed).

Container Orchestration:
  KUBERNETES:     Industry standard for container orchestration.
  Docker Swarm:   Docker's native orchestration. Simpler than Kubernetes.
  Amazon ECS:     AWS-proprietary container orchestration.
  Nomad:          HashiCorp's general-purpose workload orchestrator.

Container Image Registries:
  PUBLIC:
    Docker Hub:           docker pull ubuntu:22.04
    GitHub Container Reg: ghcr.io/owner/repo:tag
    Red Hat Quay:         quay.io/username/image:tag
  
  CLOUD PRIVATE:
    AWS ECR:              123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:v1
    Google GCR:           gcr.io/project-id/myapp:v1
    Azure ACR:            myregistry.azurecr.io/myapp:v1
  
  SELF-HOSTED:
    Harbor:               Open-source, enterprise features, vulnerability scanning

6. CONTAINER USE CASES
================================================================================

1. MICROSERVICES:
   Each microservice runs in its own container.
   Independent deployment, scaling, and updates.
   Technology diversity: Service A uses Node.js, Service B uses Python.
   
   User Service → users-service:v2.1.0 container
   Order Service → orders-service:v3.4.2 container
   Payment Service → payments-service:v1.8.0 container

2. CI/CD PIPELINES:
   Build/test environments in containers for reproducibility.
   Ephemeral: Fresh environment for every build.
   Fast startup: Container starts in milliseconds.
   No dependency conflicts between jobs.
   
   GitHub Actions runs each job in a fresh container.
   Jenkins agents can be Docker containers.

3. DEVELOPMENT ENVIRONMENTS:
   "Works on my machine" → Works in the container, same everywhere.
   Docker Compose: Local multi-service stack (app + database + cache).
   Consistent environment across team members.
   Onboarding: git clone + docker-compose up = working dev environment.

4. BATCH PROCESSING:
   Short-lived containers for one-off tasks.
   Run → complete → exit → delete.
   Example: Data processing job, report generation, database migration.

5. SERVERLESS / FAAS:
   AWS Lambda now supports custom container images (up to 10GB).
   Google Cloud Run: Containerized serverless HTTP services.
   Azure Container Instances: Run containers without managing servers.

6. LEGACY APPLICATION MODERNIZATION:
   "Lift and shift" old applications into containers.
   Not cloud-native, but benefits from container infrastructure.
   Step 1 toward microservices migration.

================================================================================
7. CONTAINERIZATION BENEFITS
================================================================================

1. PORTABILITY:
   Container image runs identically on developer laptop, CI server, production.
   Write once, run anywhere (as long as host OS is Linux for Linux containers).

2. CONSISTENCY:
   No more "it works on my machine." Same libraries, same runtime, same config.
   Eliminates entire class of environment-related bugs.

3. SPEED:
   Sub-second container startup (vs minutes for VMs).
   Fast CI/CD: Parallel test runs in isolated containers.
   Quick horizontal scaling: Launch 10 more containers in seconds.

4. DENSITY:
   Run 100s of containers on a single machine.
   Better hardware utilization than VMs.
   Cost savings: More workloads per server.

5. ISOLATION:
   Process, network, and filesystem isolation.
   One container's crash doesn't affect others.
   Dependency isolation: Service A uses Python 3.9, Service B uses Python 3.11.

6. INFRASTRUCTURE AS CODE:
   Dockerfile is a reproducible, versionable description of the environment.
   Environment changes go through code review.
   Audit trail of environment changes.

7. IMMUTABILITY:
   Container images don't change after build (immutable artifacts).
   No "configuration drift" — production is exactly what was tested.
   Rollback = run old image (guaranteed same behavior).

8. CONTAINERIZATION CHALLENGES
================================================================================

1. STORAGE AND STATE:
   Containers are ephemeral — data written to container is lost when it exits.
   Stateful applications (databases) require volumes for persistence.
   Volume management adds complexity.
   Kubernetes PersistentVolumes (PV) and PersistentVolumeClaims (PVC) address this.

2. NETWORKING:
   Container-to-container communication requires setup.
   Service discovery: How does Service A find Service B's IP/port?
   Load balancing across container instances.
   Kubernetes Services and DNS solve this.

3. SECURITY:
   Shared kernel means a kernel exploit affects all containers.
   Containers run as root by default (problematic).
   Image vulnerabilities: Public base images may have known CVEs.
   Solutions: Non-root users, read-only filesystems, image scanning, gVisor.

4. LOGGING AND MONITORING:
   Ephemeral containers lose logs when deleted.
   Log aggregation: Centralized logging required (ELK, Fluentd, CloudWatch).
   Metrics: Container metrics need aggregation (Prometheus + cAdvisor).

5. ORCHESTRATION COMPLEXITY:
   Managing 100s of containers manually is impossible.
   Kubernetes solves this but adds its own complexity.
   Learning curve for Kubernetes.

6. DEBUGGING:
   Different from debugging traditional processes.
   Docker exec to get shell inside container.
   Ephemeral nature: Container might not exist when you want to debug.
   Kubernetes exec / port-forward for debugging.

7. IMAGE SIZE AND SECURITY:
   Large images: Slow pull, more attack surface.
   Unoptimized Dockerfiles create large images with many layers.
   Solution: Multi-stage builds, distroless images, minimal base images.

8. WINDOWS CONTAINERS:
   Linux containers cannot run on Windows natively.
   Windows containers exist but are less common, larger, and slower.
   Docker Desktop on Mac/Windows uses a Linux VM behind the scenes.

9. KEY TERMINOLOGY
================================================================================

IMAGE vs CONTAINER:
  Image: Static, read-only template (blueprint)
  Container: Running instance of an image (house built from blueprint)

LAYER:
  Each Dockerfile instruction creates a new read-only layer.
  Layers are cached and shared between images.

REGISTRY:
  Storage for container images (Docker Hub, ECR, GCR).

TAG:
  Label on an image for versioning. myapp:v1.0, myapp:latest
  'latest' is NOT automatically the newest — it's just a tag.

DOCKERFILE:
  Text file with instructions to build a container image.
  FROM, RUN, COPY, ENV, EXPOSE, CMD, ENTRYPOINT, etc.

DOCKER COMPOSE:
  YAML file defining multi-container applications.
  Run entire application stack locally with docker-compose up.

VOLUME:
  Persistent storage that survives container restarts.
  Managed by Docker or Kubernetes, not container lifecycle.

NETWORK:
  Container networking. Types: bridge, host, none, overlay.
  Containers on same network communicate by container name.

ENTRYPOINT vs CMD:
  ENTRYPOINT: The executable to run when container starts (hard to override)
  CMD: Default arguments to ENTRYPOINT (can be overridden at runtime)

CONTAINER RUNTIME INTERFACE (CRI):
  Kubernetes standard API for container runtimes.
  Allows Kubernetes to work with any CRI-compliant runtime (containerd, CRI-O).

OCI (Open Container Initiative):
  Standards body for container formats.
  OCI Image Spec: Image format standard
  OCI Runtime Spec: Runtime behavior standard (implemented by runc)

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between a container and a virtual machine?
A: Both provide isolation, but at different levels:
   
   VMs virtualize hardware: Each VM has a full guest OS, separate kernel,
   runs on a hypervisor. Heavy: GBs of disk, minutes to start.
   Strong isolation: Separate kernel means a kernel exploit in one VM
   doesn't directly affect others.
   
   Containers virtualize the OS: Multiple containers share the host OS kernel
   but have isolated views of processes, networks, and filesystems via Linux
   namespaces and cgroups. Light: MBs of overhead, start in milliseconds.
   Weaker isolation: Shared kernel is a security consideration.
   
   The right choice:
   - Containers for microservices, CI/CD, cloud-native applications
   - VMs for strong isolation, different OS requirements, legacy applications
   
   In practice, most cloud deployments run containers ON VMs
   (K8s pods in EC2 instances, for example).

Q2: How do Linux namespaces and cgroups enable containers?
A: These are the two kernel features that make containers possible:
   
   NAMESPACES provide ISOLATION:
   Each container gets its own view of the system through namespaces:
   - pid namespace: Container's process 1 is isolated (can't see host processes)
   - net namespace: Separate network stack (own IP address, routing table)
   - mnt namespace: Own filesystem mount points (can't see host filesystems)
   - uts namespace: Own hostname
   - user namespace: Own UID/GID mapping (rootless containers)
   
   CGROUPS provide RESOURCE LIMITS:
   Control Groups limit how much of a resource a process group can use:
   - CPU: Container can use at most 0.5 CPUs
   - Memory: Container can use at most 256MB (OOM-killed if exceeded)
   - Block I/O: Limit disk read/write rates
   - Network: Rate limiting
   
   Together: A container is a process (or process group) running with
   namespace isolation (can't see others) and cgroup limits (can't starve others).

Q3: What is a container image and how are layers important?
A: A container image is an immutable, read-only template for creating containers.
   
   Images are built in layers:
   - Each Dockerfile instruction (FROM, RUN, COPY) creates a new layer
   - Layers are read-only and cached
   - Layers are stacked using overlay filesystem
   - Multiple images can share the same base layers
   
   Why layers matter:
   1. EFFICIENCY: Ubuntu base layer (70MB) is downloaded once, shared by many images
   2. CACHING: If layer N hasn't changed, Docker uses cache for layer N+1+...
      Changing only app code reuses all the dependency layers (fast rebuild)
   3. DISTRIBUTION: Only changed layers are pushed/pulled (not entire image)
   
   A container adds a writable layer on top of all image layers.
   When the container is deleted, the writable layer is gone.
   Image layers remain, ready for the next container.

Q4: Explain Docker's architecture (client-daemon-container runtime).
A: Docker follows a client-server architecture:
   
   DOCKER CLIENT (docker CLI):
   User-facing tool. Sends commands to Docker daemon via REST API.
   Can be local (same machine) or remote (different machine via TCP).
   
   DOCKER DAEMON (dockerd):
   The server. Listens on a Unix socket by default.
   Manages: images, containers, volumes, networks.
   Delegates actual container creation to containerd.
   
   CONTAINERD:
   High-level container runtime. OCI-compliant. CNCF project.
   Manages: pulling images, storage, networking, container lifecycle.
   Used directly by Kubernetes (since K8s 1.24, replacing Docker daemon in K8s).
   
   RUNC:
   Low-level runtime. Creates and runs containers.
   Uses Linux namespaces + cgroups.
   Reference implementation of OCI Runtime Spec.
   
   Flow: docker run myapp
   → docker CLI → dockerd (pull image, set up networking/storage)
   → containerd (manage container lifecycle)
   → runc (create namespaces, cgroups, start process)
   → Linux kernel (namespace + cgroup enforcement)

Q5: What are the security considerations with containers?
A: Several key security considerations:
   
   1. SHARED KERNEL: All containers share the host kernel. A kernel vulnerability
      could potentially be exploited from within a container. Mitigations:
      gVisor (Google's sandboxed runtime), Kata Containers (lightweight VMs).
   
   2. RUNNING AS ROOT: By default, container processes run as root inside the
      container. If the container escapes its isolation, root inside = root outside.
      Fix: USER instruction in Dockerfile, run as non-root user.
   
   3. IMAGE VULNERABILITIES: Public base images often contain CVEs in their packages.
      Fix: Image scanning (Trivy, Grype), regularly update base images,
      use minimal base images (distroless, Alpine).
   
   4. PRIVILEGED CONTAINERS: --privileged flag gives container full host access.
      This is essentially disabling container security.
      Fix: Never use --privileged in production.
   
   5. SECRETS IN IMAGES: Building secrets into images (passwords in ENV variables,
      credentials in COPY) is a serious risk.
      Fix: Runtime secrets (K8s Secrets, Vault), build-time secrets via BuildKit.
   
   6. READ-WRITE FILESYSTEMS: Containers with writable filesystems can be modified.
      Fix: --read-only flag, only mount writable volumes where needed.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

CONTAINER = App + libraries + runtime + config. Shares host OS kernel.
VM = App + libraries + full guest OS. Full hardware virtualization.

Container = Namespace isolation + cgroup resource limits + overlay filesystem

Image: Immutable layers (read-only template)
Container: Running instance with writable layer on top of image layers

Docker Architecture:
  CLI → dockerd → containerd → runc → Linux kernel (namespaces + cgroups)

Key Container Runtimes:
  Docker:       Full dev experience
  containerd:   CNCF standard, used by K8s
  CRI-O:        K8s-native, minimal
  Podman:       Rootless, daemonless Docker alternative

Essential Docker Commands:
  docker build -t myapp:v1 .       # Build image
  docker push myapp:v1             # Push to registry
  docker pull myapp:v1             # Pull from registry
  docker run -d -p 8080:80 myapp   # Run container
  docker ps                        # List running containers
  docker logs <container>          # View logs
  docker exec -it <container> sh   # Shell into container
  docker stop/rm <container>       # Stop/remove container
  docker images                    # List images
  docker rmi <image>               # Remove image
  docker inspect <container>       # Detailed info

Linux Kernel Features:
  Namespaces: pid, net, mnt, uts, ipc, user, cgroup → ISOLATION
  cgroups: cpu, memory, blkio, net_cls              → RESOURCE LIMITS
  Overlay FS: Layered filesystem                     → EFFICIENT STORAGE

Container vs VM Decision:
  Container: Microservices, CI/CD, cloud-native, development
  VM: Strong isolation, different OS, legacy apps, compliance

Security Best Practices (preview — see 06_Container_Security.txt for details):
  ✓ Non-root USER in Dockerfile
  ✓ Scan images for CVEs (Trivy)
  ✓ Minimal base images (Alpine, distroless)
  ✓ No --privileged flag
  ✓ Read-only filesystem where possible
  ✓ No secrets in image layers

History:
  1979: chroot | 2006: cgroups | 2008: LXC | 2013: Docker | 2014: Kubernetes
