1. DOCKER CORE CONCEPTS
================================================================================

Docker Definition:
  Docker is an open-source platform for developing, shipping, and running
  applications in containers. It provides:
  
  - DOCKER ENGINE: Runtime (dockerd + containerd + runc)
  - DOCKER CLI: Command-line interface
  - DOCKERFILE: Instruction set for building images
  - DOCKER COMPOSE: Multi-container application definition
  - DOCKER HUB: Public container image registry

The Docker Workflow:
  
  1. WRITE: Application code + Dockerfile
  2. BUILD: docker build → Container image
  3. PUSH: docker push → Registry (Docker Hub, ECR, GCR)
  4. PULL: docker pull → On any machine
  5. RUN: docker run → Container running your app
  
  Developer     CI/CD Pipeline    Production
  ─────────     ──────────────    ──────────
  Write code    docker build       docker pull
  Dockerfile    docker test        docker run
                docker push →→→→→→ (same image!)

Image Naming Convention:
  [registry/][namespace/]image-name[:tag]
  
  Examples:
  ubuntu:22.04                              # Docker Hub official
  nginx:1.25-alpine                         # Docker Hub, alpine tag
  python:3.11-slim                          # Docker Hub official
  myusername/myapp:v1.2.3                   # Docker Hub personal
  ghcr.io/owner/repo:sha-abc123             # GitHub Container Registry
  123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:v1  # AWS ECR
  
  'latest' is a tag, not magic. Bad practice to rely on 'latest' in production.
  Always use specific versions: myapp:v1.2.3 or myapp:git-sha-abc123

2. INSTALLING AND GETTING STARTED
================================================================================

Install Docker (Linux):
  # Using the official script
  curl -fsSL https://get.docker.com -o get-docker.sh
  sudo sh get-docker.sh
  
  # Add your user to docker group (avoid sudo)
  sudo usermod -aG docker $USER
  newgrp docker
  
  # Verify
  docker --version
  docker run hello-world

Install Docker Desktop (Mac/Windows):
  Download from https://docs.docker.com/desktop/
  Includes: Docker Engine, Docker CLI, Docker Compose, Kubernetes
  
  Mac: Uses a lightweight Linux VM (Lima/HyperKit) to run Linux containers
  Windows: Uses WSL2 (Windows Subsystem for Linux)

Verify Installation:
  docker version                    # Client and server versions
  docker info                       # System-wide information
  docker run hello-world            # Test with official hello-world image

3. DOCKER IMAGES — WORKING WITH IMAGES
================================================================================

Searching for Images:
  docker search ubuntu              # Search Docker Hub
  docker search --filter is-official=true ubuntu
  docker search --filter stars=100 nginx

Pulling Images:
  docker pull ubuntu:22.04          # Pull specific version
  docker pull nginx:latest          # Pull latest (avoid in production)
  docker pull python:3.11-slim      # Pull slim variant

Listing Images:
  docker images                     # List all local images
  docker images -a                  # Include intermediate images
  docker images ubuntu              # Filter by name
  docker images --format "table {{.Repository}}\t{{.Tag}}\t{{.Size}}"

Inspecting Images:
  docker inspect ubuntu:22.04       # Full JSON metadata
  docker history ubuntu:22.04       # Layer history (how image was built)
  docker image inspect nginx --format '{{.Config.ExposedPorts}}'

Tagging Images:
  docker tag myapp:latest myapp:v1.2.3        # Add version tag
  docker tag myapp:v1.2.3 myregistry.com/myapp:v1.2.3  # Add registry tag

Pushing Images:
  docker login                              # Login to Docker Hub
  docker login ghcr.io                      # Login to GitHub Container Registry
  docker login 123456789.dkr.ecr.us-east-1.amazonaws.com  # Login to AWS ECR
  
  docker push myusername/myapp:v1.2.3       # Push to Docker Hub
  docker push ghcr.io/owner/myapp:v1.2.3   # Push to GHCR

Removing Images:
  docker rmi myapp:v1.2.3           # Remove specific image
  docker rmi $(docker images -q)    # Remove all images (careful!)
  docker image prune                # Remove dangling (untagged) images
  docker image prune -a             # Remove all unused images

Building Images:
  docker build -t myapp:v1 .                    # Build from current directory
  docker build -t myapp:v1 -f Dockerfile.prod . # Use specific Dockerfile
  docker build --no-cache -t myapp:v1 .         # Force rebuild (no cache)
  docker build --platform linux/amd64 -t myapp . # Build for specific platform

Layer Caching:
  Docker caches each layer based on the instruction and its context.
  If a layer hasn't changed, Docker reuses the cached version.
  
  CACHE INVALIDATION:
  - Any instruction that changes (code, config) invalidates all subsequent layers
  - ORDER MATTERS: Put rarely-changing instructions first, often-changing last
  
  Bad (changes in code invalidate library install):
  COPY . /app           ← Changes every time code changes
  RUN pip install -r requirements.txt  ← Cache busted every code change!
  
  Good (copy requirements first, install, then copy code):
  COPY requirements.txt /app/requirements.txt  ← Only changes when deps change
  RUN pip install -r requirements.txt          ← Cache preserved unless deps change
  COPY . /app                                  ← Changes every time (expected)

4. DOCKER CONTAINERS — RUNNING AND MANAGING
================================================================================

Running Containers:
  
  BASIC:
  docker run ubuntu:22.04 echo "Hello"   # Run command and exit
  docker run -it ubuntu:22.04 bash       # Interactive shell
  docker run -d nginx:1.25               # Detached (background) mode
  
  PORT MAPPING:
  docker run -d -p 8080:80 nginx         # Host:Container port mapping
  docker run -d -p 127.0.0.1:8080:80 nginx  # Bind to specific host IP
  
  ENVIRONMENT VARIABLES:
  docker run -e ENV=production -e DB_HOST=db myapp
  docker run --env-file .env myapp       # Load from file
  
  VOLUMES:
  docker run -v /host/path:/container/path myapp    # Bind mount
  docker run -v myvolume:/container/path myapp      # Named volume
  docker run --tmpfs /tmp myapp                      # In-memory tmpfs
  
  NETWORK:
  docker run --network my-network myapp
  docker run --network host myapp       # Share host network
  
  RESOURCE LIMITS:
  docker run --memory=256m --cpus=0.5 myapp  # Limit memory and CPU
  
  NAMING:
  docker run --name my-container myapp   # Give container a name
  
  CLEANUP:
  docker run --rm myapp echo "clean"     # Auto-remove after exit

Container Lifecycle:
  
  STATES: created → running → paused → stopped → deleted
  
  docker create myapp        # Create without starting
  docker start my-container  # Start stopped container
  docker stop my-container   # Stop gracefully (SIGTERM → SIGKILL after 10s)
  docker kill my-container   # Immediate stop (SIGKILL)
  docker restart my-container # Stop + start
  docker pause my-container  # Pause (freeze all processes)
  docker unpause my-container # Unpause
  docker rm my-container     # Delete stopped container
  docker rm -f my-container  # Force delete running container

Listing Containers:
  docker ps                  # Running containers
  docker ps -a               # All containers (including stopped)
  docker ps -q               # Only IDs (for scripting)
  docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

Container Information:
  docker logs my-container           # View logs
  docker logs -f my-container        # Follow logs (tail -f equivalent)
  docker logs --tail=100 my-container # Last 100 lines
  docker logs --since=1h my-container # Logs from last 1 hour
  
  docker inspect my-container        # Full JSON metadata
  docker stats my-container          # Live resource usage (CPU, memory, I/O)
  docker top my-container            # Running processes in container
  docker port my-container           # Port mappings
  
  docker diff my-container           # Changed files in writable layer

Executing Commands in Running Container:
  docker exec -it my-container bash           # Interactive shell
  docker exec my-container ls /app            # Run command
  docker exec -u root my-container whoami     # Run as specific user
  docker exec -w /app my-container ls         # Set working directory

Copying Files:
  docker cp my-container:/app/logs /host/logs   # Copy from container
  docker cp /host/config my-container:/app/     # Copy to container

Cleanup:
  docker system prune           # Remove stopped containers, unused images, networks
  docker system prune -a        # Also remove unused volumes and ALL unused images
  docker container prune        # Remove all stopped containers
  docker volume prune           # Remove all unused volumes

5. DOCKER NETWORKING
================================================================================

Network Types:
  
  BRIDGE (default):
    Default network for containers.
    Containers can communicate by IP address.
    Port mapping (-p) exposes ports to host.
    User-defined bridge networks: containers can communicate by NAME.
    
    docker network create my-app-network
    docker run --name db --network my-app-network postgres
    docker run --name app --network my-app-network myapp
    # app can reach db at "db:5432" by container name
  
  HOST:
    Container shares host's network namespace.
    No isolation; container sees host network directly.
    Use case: High-performance networking, when port mapping overhead matters.
    docker run --network host myapp
    # Ports are directly on host (no -p needed or allowed)
  
  NONE:
    Container has no network access.
    Complete network isolation.
    Use case: Security-sensitive batch processing.
    docker run --network none myapp
  
  OVERLAY (Docker Swarm):
    Multi-host network for containers across multiple Docker hosts.
    Requires Docker Swarm or Kubernetes networking.
  
  MACVLAN:
    Container gets its own MAC address.
    Appears as physical device on network.
    Use case: Legacy apps expecting network presence.

Network Commands:
  docker network ls                              # List networks
  docker network create my-network              # Create user-defined bridge
  docker network create --driver bridge --subnet 172.20.0.0/16 my-net
  docker network inspect my-network             # Inspect network
  docker network connect my-network container   # Add container to network
  docker network disconnect my-network container # Remove from network
  docker network rm my-network                  # Delete network

DNS Resolution in Docker:
  User-defined bridge networks provide automatic DNS resolution.
  Containers can reach each other by container name.
  
  # Default bridge network: No DNS (only IP works)
  docker run --name db postgres               # On default bridge
  docker run myapp                            # Can't reach "db" by name
  
  # User-defined bridge: DNS works
  docker network create mynet
  docker run --name db --network mynet postgres
  docker run --name app --network mynet myapp  # app can ping "db"

6. DOCKER VOLUMES AND STORAGE
================================================================================

Storage Types:
  
  BIND MOUNT:
    Host directory mounted into container.
    Changes on host are immediately visible in container.
    Changes in container are immediately on host.
    
    docker run -v /host/data:/container/data myapp
    docker run --mount type=bind,source=/host/data,target=/container/data myapp
    
    Use case: Development (mount source code for live reload)
    
    Problem: Absolute host path. Not portable between machines.
  
  NAMED VOLUME (recommended for production):
    Docker-managed storage. Lives in /var/lib/docker/volumes/
    Can be shared between containers.
    Persists container restarts and deletions.
    
    docker volume create mydata
    docker run -v mydata:/container/data myapp
    
    Use case: Database data, persistent application state
  
  TMPFS MOUNT (memory):
    Stored in host's memory. Not written to disk.
    Fastest. Disappears when container stops.
    
    docker run --tmpfs /tmp myapp
    
    Use case: Sensitive data (credentials), temp files, performance

Volume Commands:
  docker volume ls                     # List volumes
  docker volume create myvolume        # Create named volume
  docker volume inspect myvolume       # Inspect volume (find mount path)
  docker volume rm myvolume            # Delete volume
  docker volume prune                  # Delete unused volumes

Volume Backup:
  # Backup named volume
  docker run --rm \
    -v myvolume:/data \
    -v /host/backup:/backup \
    ubuntu:22.04 \
    tar cvf /backup/myvolume-backup.tar /data
  
  # Restore
  docker run --rm \
    -v myvolume:/data \
    -v /host/backup:/backup \
    ubuntu:22.04 \
    tar xvf /backup/myvolume-backup.tar -C /

Storage Best Practices:
  ✓ Use named volumes for production data (not bind mounts)
  ✓ Never store database data in container filesystem
  ✓ Use tmpfs for sensitive/temp data
  ✓ Use bind mounts for development (source code)
  ✗ Don't rely on container's writable layer for important data

8. DOCKER COMPOSE
================================================================================

(Deep dive in 03_Docker_Compose.txt — this is a summary)

What is Docker Compose:
  Tool for defining and running multi-container Docker applications.
  Single YAML file defines all services, networks, and volumes.
  Single command to start everything: docker compose up

Basic docker-compose.yml:
  
  version: "3.9"
  
  services:
    web:
      build: .                       # Build from Dockerfile in current directory
      ports:
        - "8080:80"                  # Host:Container
      environment:
        - DATABASE_URL=postgresql://db:5432/myapp
      depends_on:
        db:
          condition: service_healthy # Wait for DB to be healthy
      volumes:
        - ./static:/app/static       # Bind mount for static files
      networks:
        - myapp-net
    
    db:
      image: postgres:15
      environment:
        POSTGRES_DB: myapp
        POSTGRES_USER: user
        POSTGRES_PASSWORD: password
      volumes:
        - postgres_data:/var/lib/postgresql/data  # Named volume for persistence
      networks:
        - myapp-net
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U user -d myapp"]
        interval: 10s
        timeout: 5s
        retries: 5
    
    redis:
      image: redis:7-alpine
      networks:
        - myapp-net
  
  networks:
    myapp-net:
      driver: bridge
  
  volumes:
    postgres_data:

Docker Compose Commands:
  docker compose up -d                    # Start all services (detached)
  docker compose up --build              # Rebuild images before starting
  docker compose down                    # Stop and remove containers
  docker compose down -v                 # Also remove volumes
  docker compose ps                      # Status of services
  docker compose logs -f web             # Follow logs for web service
  docker compose exec web bash           # Shell into web container
  docker compose restart web             # Restart specific service
  docker compose scale web=3             # Scale service (replicas)

Override Files:
  docker-compose.yml           # Base configuration
  docker-compose.override.yml  # Auto-loaded overrides (local dev)
  docker-compose.prod.yml      # Production overrides
  
  # Use specific files:
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up

9. DOCKER IN CI/CD PIPELINES
================================================================================

Using Docker in GitHub Actions:
  
  # .github/workflows/docker.yml
  name: Build and Push Docker Image
  
  on:
    push:
      branches: [main]
    pull_request:
      branches: [main]
  
  jobs:
    build-and-push:
      runs-on: ubuntu-latest
      
      steps:
      - name: Checkout
        uses: actions/checkout@v4
      
      - name: Set up QEMU (for multi-platform builds)
        uses: docker/setup-qemu-action@v3
      
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      
      - name: Extract metadata for Docker
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: myusername/myapp
          tags: |
            type=sha                          # git-sha-abc1234
            type=semver,pattern={{version}}   # v1.2.3
            type=semver,pattern={{major}}.{{minor}}  # v1.2
            type=ref,event=branch             # main
            type=ref,event=pr                 # pr-42
      
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64  # Multi-arch
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha              # GitHub Actions cache
          cache-to: type=gha,mode=max

Using Docker in GitLab CI:
  
  # .gitlab-ci.yml
  variables:
    DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  
  build:
    image: docker:24
    services:
      - docker:24-dind      # Docker-in-Docker
    before_script:
      - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    script:
      - docker build -t $DOCKER_IMAGE .
      - docker push $DOCKER_IMAGE
    rules:
      - if: $CI_COMMIT_BRANCH == "main"

Docker Layer Caching in CI:
  
  # GitHub Actions - use cache
  - uses: docker/build-push-action@v5
    with:
      cache-from: type=gha
      cache-to: type=gha,mode=max
  
  # GitLab CI - use registry cache
  script:
    - docker build --cache-from $CI_REGISTRY_IMAGE:cache -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE
    # Push cache image
    - docker tag $DOCKER_IMAGE $CI_REGISTRY_IMAGE:cache
    - docker push $CI_REGISTRY_IMAGE:cache

BuildKit:
  Docker's next-generation build backend.
  Benefits:
  - Parallel execution of independent build stages
  - Efficient layer caching
  - Secret mounting (no secrets in image layers)
  - SSH forwarding for private repos during build
  
  Enable:
  DOCKER_BUILDKIT=1 docker build .
  
  Or set in daemon.json:
  {"features": {"buildkit": true}}
  
  BuildKit is default in Docker 23.0+

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Docker and what problem does it solve?
A: Docker is an open-source platform for containerization. It solves the
   "works on my machine" problem — the classic scenario where code works
   in development but fails in production due to environment differences.
   
   A Docker container packages the application with ALL its dependencies:
   runtime, libraries, configurations. This container runs identically on:
   - Developer's laptop
   - CI/CD server
   - Staging environment
   - Production servers
   
   Docker also makes it easy to build (Dockerfile), share (Docker Hub),
   and run (docker run) containers. The developer experience was key to
   Docker's success — before Docker, achieving container isolation required
   deep Linux knowledge.

Q2: What is the difference between CMD and ENTRYPOINT in a Dockerfile?
A: Both define what runs when a container starts, but they behave differently:
   
   CMD: Provides default arguments. Can be OVERRIDDEN at runtime.
   ENTRYPOINT: Defines the executable. Harder to override.
   
   Example:
   ENTRYPOINT ["python", "app.py"]
   CMD ["--port", "8080"]
   
   Default run: container runs "python app.py --port 8080"
   Override CMD: docker run myimage --port 9090
                 runs "python app.py --port 9090"
   Override ENTRYPOINT: docker run --entrypoint /bin/bash myimage
                        completely replaces the entry command
   
   Common patterns:
   - Executable container: ENTRYPOINT defines the program, CMD provides defaults
   - Flexible container: Only CMD (entire command can be overridden)
   - Shell form: CMD ["python", "app.py"] vs CMD python app.py
     Use exec form (array) to avoid shell wrapping (proper signal handling)

Q3: How does Docker layer caching work, and how do you optimize for it?
A: Docker caches each layer. When rebuilding, if a layer's instruction and
   its inputs haven't changed, Docker reuses the cached version. As soon as
   any layer changes, all subsequent layers are rebuilt (cache is invalidated).
   
   Optimization principle: Order Dockerfile instructions from LEAST to MOST
   likely to change:
   
   BAD (changes to any code invalidates pip install cache):
   COPY . /app
   RUN pip install -r requirements.txt
   
   GOOD (pip install cache is preserved unless requirements change):
   COPY requirements.txt /app/requirements.txt
   RUN pip install -r requirements.txt
   COPY . /app
   
   Other optimizations:
   - Use .dockerignore to exclude files not needed in image
   - Combine RUN commands to reduce layers
   - Use multi-stage builds to keep final image lean
   - Use BuildKit for advanced caching strategies

Q4: What is Docker Compose and when would you use it?
A: Docker Compose is a tool for defining and running multi-container
   applications using a single docker-compose.yml file.
   
   Instead of running multiple docker run commands with complex flags,
   you define everything in one YAML file and start everything with
   docker compose up.
   
   Use cases:
   - Local development: App + database + cache + message queue
   - Integration testing in CI: Spin up dependent services for tests
   - Demo/prototyping: Easy to share multi-service setups
   
   It handles:
   - Service definitions (images or Dockerfiles)
   - Port mappings
   - Environment variables
   - Volume mounts
   - Service dependencies
   - Custom networks for service isolation
   
   NOT recommended for production (use Kubernetes instead).
   Compose is a single-host solution with no auto-scaling, health management,
   or multi-host networking.

Q5: How do you run Docker containers securely?
A: Several key security practices:
   
   1. Run as non-root:
      USER appuser in Dockerfile (create a non-root user)
      docker run --user 1001:1001 myapp
   
   2. Read-only filesystem:
      docker run --read-only myapp
      Mount writable volumes only where needed
   
   3. Drop capabilities:
      docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp
   
   4. No privileged mode:
      Never use --privileged in production
   
   5. Scan images:
      trivy image myapp:v1
   
   6. Use minimal base images:
      FROM python:3.11-slim instead of FROM python:3.11
      FROM distroless/python instead of full python image
   
   7. Set memory limits:
      docker run --memory=256m myapp
   
   8. Use secrets properly:
      docker secret create for Docker Swarm
      Kubernetes Secrets for K8s
      Not ENV in Dockerfile (appears in docker inspect)
