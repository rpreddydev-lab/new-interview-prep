1. WHAT IS A CI PIPELINE?
================================================================================

Definition:
  A CI Pipeline is an automated sequence of steps (stages) that run whenever
  code is pushed to a repository. It validates code quality, runs tests, builds
  artifacts, and provides feedback to developers.

Core Concepts:
  
  PIPELINE: The complete automated workflow from code push to artifact
  STAGE: A logical grouping of related steps (Build, Test, Deploy)
  JOB: A unit of work that runs on an agent/runner
  STEP: An individual task within a job (run a command, call an action)
  
  Pipeline Hierarchy:
  Pipeline
  └── Stage 1: Build
  │   └── Job: compile
  │       ├── Step: checkout
  │       ├── Step: setup JDK
  │       └── Step: run mvn compile
  └── Stage 2: Test
      ├── Job: unit-tests
      │   └── Step: run mvn test
      └── Job: integration-tests
          └── Step: run mvn verify

Pipeline Execution Models:
  
  SEQUENTIAL (simple):
  [Checkout] → [Build] → [Test] → [Scan] → [Publish]
  Each stage waits for previous stage to complete.
  
  PARALLEL (faster):
  [Checkout] → [Build] → [Unit Tests] ─┐
                                       ├→ [Scan] → [Publish]
                        [Lint] ────────┘
  Tests and Lint run in parallel, both must pass before Scan.
  
  DAG (Directed Acyclic Graph):
  Most modern CI tools support DAG-based pipelines where stages/jobs have
  explicit dependencies, enabling maximum parallelism.

2. PIPELINE STAGES IN DEPTH
================================================================================

STAGE 1: SOURCE / CHECKOUT
  Actions:
    - Clone or checkout repository at the triggering commit SHA
    - Set up the workspace directory
  
  Important: Always check out the specific commit SHA, never just HEAD.
  This ensures reproducibility.
  
  GitHub Actions:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0   # Full history for git-based tools

  GitLab CI:
    # Automatic - GitLab clones repo before every job
    variables:
      GIT_DEPTH: 0   # Full clone, not shallow

---

STAGE 2: ENVIRONMENT SETUP
  Actions:
    - Set up language runtime (Node, Python, Java, Go, etc.)
    - Configure tool versions
    - Set environment variables
  
  Principle: Pin exact versions for reproducibility.
  
  GitHub Actions example:
    - uses: actions/setup-java@v4
      with:
        java-version: '21'
        distribution: 'temurin'
    
    - uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'

---

STAGE 3: DEPENDENCY INSTALLATION
  Actions:
    - Install project dependencies
    - Use cache to avoid re-downloading unchanged dependencies
  
  Cache Key Strategy:
    Cache is valid as long as the lockfile doesn't change.
    
    npm:   Cache key = hash of package-lock.json
    Maven: Cache key = hash of pom.xml (or ~/.m2 directory)
    pip:   Cache key = hash of requirements.txt
    
  GitHub Actions caching:
    - uses: actions/cache@v4
      with:
        path: ~/.m2/repository
        key: maven-${{ hashFiles('**/pom.xml') }}
        restore-keys: maven-

---

STAGE 4: COMPILATION / BUILD
  Actions:
    - Compile source code
    - Fail fast if compilation errors exist
  
  Per language:
    Java (Maven):  mvn compile -q
    Java (Gradle): gradle compileJava
    TypeScript:    npx tsc --noEmit
    Go:            go build ./...
    Rust:          cargo build
  
  Incremental Builds:
    Problem: Recompiling everything is slow for large projects.
    Solutions:
      - Gradle Build Cache: Remote cache shares build outputs across CI agents
      - Bazel: Hermetic, distributed build system used by Google/Uber/Twitter
      - ccache: C/C++ compiler cache

---

STAGE 5: STATIC ANALYSIS AND LINTING
  Actions:
    - Code formatting checks (Prettier, Black, gofmt)
    - Linting (ESLint, Pylint, Checkstyle, golangci-lint)
    - Complexity checks (cyclomatic complexity)
    - SAST (SonarQube, Semgrep, CodeQL)
  
  Purpose: Enforce code quality standards automatically.
  
  Key tools:
    JavaScript:  ESLint, Prettier
    Python:      Pylint, Flake8, Black, mypy (type checking)
    Java:        Checkstyle, SpotBugs, PMD, SonarQube
    Go:          golangci-lint, go vet, staticcheck
    
  SonarQube Quality Gates:
    A SonarQube Quality Gate is a set of threshold-based conditions.
    Pipeline fails if Quality Gate fails.
    
    Typical conditions:
    - New code coverage >= 80%
    - No new blockers
    - No new critical vulnerabilities
    - Technical debt ratio < 5%

---

STAGE 6: UNIT TESTS
  Actions:
    - Run unit tests
    - Generate coverage report
    - Enforce coverage threshold
    - Publish test results
  
  Coverage Enforcement Example (GitHub Actions):
    # JaCoCo (Java)
    - name: Check coverage
      run: |
        mvn test jacoco:report
        # Fail if coverage < 80%
        mvn jacoco:check -Djacoco.haltOnFailure=true \
          -Djacoco.excludes='**/*Config*'
  
  Test Result Publishing:
    - JUnit XML format is the universal standard
    - All CI platforms parse JUnit XML
    - Shows test counts, durations, failures inline in PR
    
    # GitHub Actions
    - uses: actions/upload-artifact@v4
      if: always()    # Upload even on failure
      with:
        name: test-results
        path: target/surefire-reports/

---

STAGE 7: INTEGRATION TESTS
  Actions:
    - Start test infrastructure (Docker Compose / TestContainers)
    - Run integration tests
    - Tear down infrastructure
  
  Docker Compose in CI:
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: testdb
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
  
  Health checks important: Wait for service to be READY, not just started.
  Classic mistake: Start DB, immediately run tests → connection refused.

---

STAGE 8: BUILD ARTIFACT
  Actions:
    - Package application
    - Tag with version
  
  Tagging strategy:
    DEVELOPMENT: latest, dev-<sha>
    RELEASE:     v2.3.1, v2.3.1-<sha>
    
  Docker build (multi-stage for efficiency):
    # Build stage
    FROM maven:3.9-eclipse-temurin-21 AS build
    COPY . .
    RUN mvn package -DskipTests
    
    # Runtime stage (small image)
    FROM eclipse-temurin:21-jre-alpine
    COPY --from=build /target/app.jar /app.jar
    CMD ["java", "-jar", "/app.jar"]

---

STAGE 9: SECURITY SCANNING
  Actions:
    - Scan dependencies for known CVEs
    - Scan Docker image for vulnerabilities
    - Check for exposed secrets
  
  Tools:
    Dependency:   Snyk, OWASP Dependency Check, Dependabot
    Container:    Trivy, Snyk Container, Grype
    Secrets:      GitGuardian, TruffleHog, Gitleaks
    SAST:         SonarQube, Semgrep, CodeQL (GitHub)
  
  Trivy example:
    - name: Scan image
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: myapp:${{ github.sha }}
        format: 'sarif'
        output: 'trivy-results.sarif'
        severity: 'CRITICAL,HIGH'
        exit-code: '1'   # Fail pipeline on HIGH/CRITICAL

---

STAGE 10: PUBLISH / DEPLOY
  Actions:
    - Push artifact to registry (conditional: only on main/release branch)
    - Trigger downstream CD pipeline
  
  Conditional publishing:
    # Only push to registry on main branch
    if: github.ref == 'refs/heads/main'

3. PIPELINE AS CODE
================================================================================

Definition:
  Pipeline as Code means defining CI pipeline configuration in a version-
  controlled file alongside the application code.
  
  Files:
    Jenkins:        Jenkinsfile
    GitHub Actions: .github/workflows/*.yml
    GitLab CI:      .gitlab-ci.yml
    CircleCI:       .circleci/config.yml
    Azure Pipelines: azure-pipelines.yml

Benefits:
  - Version history: See how pipeline changed over time
  - Code review: Propose pipeline changes via PRs
  - Branching: Different branches can have different pipeline configs
  - Reproducibility: Deploy same pipeline to new environments
  - Testability: Lint and validate pipeline files

Example: GitHub Actions Workflow

```yaml
name: CI Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

env:
  JAVA_VERSION: '21'
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: testdb
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
        options: --health-cmd pg_isready --health-interval 5s
    
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      
      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: ${{ env.JAVA_VERSION }}
          distribution: 'temurin'
          cache: 'maven'
      
      - name: Build and test
        run: mvn verify -P ci
        env:
          DB_URL: jdbc:postgresql://localhost:5432/testdb
          DB_USER: test
          DB_PASSWORD: test
      
      - name: Upload test results
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-results
          path: target/surefire-reports/
      
      - name: SonarQube scan
        uses: SonarSource/sonarcloud-github-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  
  publish:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      
      - name: Log in to Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Build and push image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

4. PIPELINE TRIGGERS
================================================================================

Types of Triggers:

1. PUSH TRIGGER
   Fires on every commit pushed to specified branches.
   Use case: Fast feedback on every commit.
   
   GitHub Actions:
     on:
       push:
         branches: [ main, develop ]
         paths:                    # Only if relevant files changed
           - 'src/**'
           - 'pom.xml'
         paths-ignore:             # Never trigger for these
           - '**.md'
           - 'docs/**'

2. PULL REQUEST TRIGGER
   Fires when PR is opened, updated, or synchronized.
   Use case: Validate changes before merge.
   
   on:
     pull_request:
       branches: [ main ]
       types: [ opened, synchronize, reopened ]

3. SCHEDULE TRIGGER (CRON)
   Fires on a time schedule.
   Use case: Nightly full test runs, security scans.
   
   on:
     schedule:
       - cron: '0 2 * * *'    # 2 AM daily

4. MANUAL TRIGGER
   Fires when a user manually initiates it.
   Use case: On-demand deployments, releasing.
   
   on:
     workflow_dispatch:
       inputs:
         environment:
           type: choice
           options: [ staging, production ]
         version:
           required: true

5. TAG TRIGGER
   Fires when a git tag is pushed.
   Use case: Release pipelines.
   
   on:
     push:
       tags:
         - 'v[0-9]+.[0-9]+.[0-9]+'    # Semantic version tag

6. RELEASE TRIGGER
   Fires when a GitHub Release is created/published.
   
   on:
     release:
       types: [published]

7. API TRIGGER (webhook)
   Fires when called via API.
   Use case: Triggering from external systems.
   
   # GitHub Actions
   on:
     repository_dispatch:
       types: [upstream-updated]
   
   # Trigger via API
   curl -X POST https://api.github.com/repos/ORG/REPO/dispatches \
     -H "Authorization: token $TOKEN" \
     -d '{"event_type": "upstream-updated"}'

5. PARALLELISM AND OPTIMIZATION
================================================================================

1. JOB PARALLELISM
   Run independent jobs simultaneously on different runners.
   
   jobs:
     unit-test:
       runs-on: ubuntu-latest
       steps: [ ... ]
     
     lint:
       runs-on: ubuntu-latest
       steps: [ ... ]
     
     security-scan:
       runs-on: ubuntu-latest
       steps: [ ... ]
     
     build:
       needs: [unit-test, lint, security-scan]   # Wait for all three
       runs-on: ubuntu-latest
       steps: [ ... ]

2. MATRIX BUILDS
   Run the same job with different configurations in parallel.
   Use case: Test against multiple OS/version combinations.
   
   jobs:
     test:
       strategy:
         matrix:
           java-version: [17, 21]
           os: [ubuntu-latest, windows-latest]
         fail-fast: false   # Don't cancel all if one fails
       runs-on: ${{ matrix.os }}
       steps:
         - uses: actions/setup-java@v4
           with:
             java-version: ${{ matrix.java-version }}

3. TEST SHARDING / SPLITTING
   Split test suite across multiple runners.
   
   jobs:
     test:
       strategy:
         matrix:
           shard: [1, 2, 3, 4]
       steps:
         - name: Run tests
           run: |
             pytest tests/ --shard-id=${{ matrix.shard }} \
               --num-shards=4

4. CONDITIONAL STEPS
   Skip expensive steps when not needed.
   
   - name: E2E tests
     if: github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/tags/')
     run: npm run test:e2e

5. PATH FILTERING
   Only run pipeline if relevant files changed.
   
   on:
     push:
       paths:
         - 'backend/**'
         - 'shared/**'
   
   # Advanced: Per-job path filtering using dorny/paths-filter
   - uses: dorny/paths-filter@v3
     id: changes
     with:
       filters: |
         backend:
           - 'backend/**'
         frontend:
           - 'frontend/**'
   
   - name: Test backend
     if: steps.changes.outputs.backend == 'true'
     run: make test-backend

6. CACHING STRATEGIES
================================================================================

Why Cache?
  Re-downloading dependencies on every build wastes time.
  Node modules: 500MB+, Maven repo: 1GB+
  
  Caching dependencies can save 2-5 minutes per build.

GitHub Actions Cache:

  # npm
  - uses: actions/cache@v4
    with:
      path: ~/.npm
      key: npm-${{ hashFiles('package-lock.json') }}
      restore-keys: npm-
  
  # Maven
  - uses: actions/cache@v4
    with:
      path: ~/.m2/repository
      key: maven-${{ hashFiles('**/pom.xml') }}
      restore-keys: maven-
  
  # Python (pip)
  - uses: actions/cache@v4
    with:
      path: ~/.cache/pip
      key: pip-${{ hashFiles('requirements.txt') }}
      restore-keys: pip-
  
  # Go modules
  - uses: actions/cache@v4
    with:
      path: ~/go/pkg/mod
      key: go-${{ hashFiles('go.sum') }}
      restore-keys: go-

Docker Layer Caching:
  Docker builds can be cached at the layer level.
  
  # GitHub Actions: Use GitHub Cache for Docker layers
  - uses: docker/build-push-action@v5
    with:
      cache-from: type=gha
      cache-to: type=gha,mode=max
  
  # GitLab CI: Use Docker registry as layer cache
  build:
    script:
      - docker build 
          --cache-from $CI_REGISTRY_IMAGE:cache 
          --tag $CI_REGISTRY_IMAGE:cache 
          --tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
      - docker push $CI_REGISTRY_IMAGE:cache
      - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

Cache Invalidation:
  Cache is invalidated when the key changes.
  Using hash of lockfile as key = cache invalidated when dependencies change.
  
  restore-keys allows fallback to older cache if exact match not found:
    key: npm-${{ hashFiles('package-lock.json') }}
    restore-keys: |
      npm-   # Falls back to any npm-* cache if exact match not found

Remote Build Cache (Gradle):
  Gradle Build Cache shares task outputs between CI agents and local machines.
  
  # gradle.properties
  org.gradle.caching=true
  
  # settings.gradle
  buildCache {
      remote(HttpBuildCache) {
          url = 'https://cache.example.com/cache/'
          push = System.getenv('CI') == 'true'
          credentials {
              username = System.getenv('GRADLE_CACHE_USERNAME')
              password = System.getenv('GRADLE_CACHE_PASSWORD')
          }
      }
  }

7. ARTIFACTS IN PIPELINES
================================================================================

What are Pipeline Artifacts?
  Artifacts are files generated during a pipeline run that need to be:
  1. Passed between jobs in the same pipeline (e.g., compiled code)
  2. Preserved after pipeline completion (e.g., test reports, binaries)

Passing Artifacts Between Jobs:

  GitHub Actions:
    # Job 1: Build
    - uses: actions/upload-artifact@v4
      with:
        name: build-artifacts
        path: target/app.jar
        retention-days: 7
    
    # Job 2: Test (in different runner)
    - uses: actions/download-artifact@v4
      with:
        name: build-artifacts
        path: target/
  
  GitLab CI:
    build:
      artifacts:
        paths:
          - target/app.jar
        expire_in: 1 day
    
    test:
      needs: [build]    # Download artifacts from 'build' job
      script:
        - java -jar target/app.jar --test

Artifact Types:
  
  TEST REPORTS:
    - Always upload, even on failure (if: always())
    - JUnit XML format for test results
    - HTML coverage reports (Jacoco, Istanbul)
  
  BINARY ARTIFACTS:
    - JARs, WARs, native binaries
    - Short retention (7 days for PRs, 30 days for releases)
  
  DOCKER IMAGES:
    - Pushed to registry, not stored as artifacts
    - Tagged with git SHA
  
  DEBUG ARTIFACTS:
    - Screenshots, logs from failed E2E tests
    - Only upload on failure (if: failure())
    - Video recordings of failed UI tests (Cypress)

Artifact Retention Policies:
  - PR builds: 7 days
  - Main branch builds: 30 days
  - Release builds: Indefinite (in artifact registry)
  
  Cleanup is important: Unchecked artifact accumulation wastes storage.

8. ENVIRONMENT VARIABLES AND SECRETS
================================================================================

Types:
  
  PIPELINE VARIABLES (non-sensitive):
    Set in pipeline YAML, visible in logs.
    Use for: JAVA_VERSION, APP_NAME, REGISTRY, IMAGE_TAG
  
  CI PLATFORM VARIABLES (auto-set):
    GitHub: github.sha, github.ref, github.actor, github.repository
    GitLab: CI_COMMIT_SHA, CI_PIPELINE_ID, CI_PROJECT_NAME
    Use for: Tagging artifacts, generating build metadata
  
  SECRETS (sensitive):
    Masked in logs (never printed)
    Set in repository settings, not in YAML
    Use for: API keys, registry credentials, cloud credentials

GitHub Actions Secrets:
  # Organization, Repository, or Environment secrets
  # Set in Settings → Secrets and Variables → Actions
  
  Using secrets:
    env:
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
      REGISTRY_PASSWORD: ${{ secrets.GITHUB_TOKEN }}   # Auto-provided
    
    # GITHUB_TOKEN: Automatically created by GitHub, scoped to the repo
    # Expires after workflow run completes

Environment-Specific Secrets:
  GitHub Environments allow different secrets per environment (staging vs prod).
  
  jobs:
    deploy:
      environment: production   # Uses 'production' environment secrets
      steps:
        - run: deploy.sh
          env:
            DB_PASSWORD: ${{ secrets.DB_PASSWORD }}   # From 'production' env

OIDC (OpenID Connect) for Cloud Auth:
  Instead of storing cloud credentials as long-lived secrets,
  use OIDC to get short-lived tokens.
  
  GitHub Actions → AWS via OIDC:
  
    permissions:
      id-token: write    # Required for OIDC
      contents: read
    
    - name: Configure AWS credentials
      uses: aws-actions/configure-aws-credentials@v4
      with:
        role-to-assume: arn:aws:iam::123456789:role/github-actions-role
        aws-region: us-east-1
  
  Benefits:
    - No long-lived AWS credentials stored in GitHub
    - Token auto-expires after workflow
    - No rotation needed
    - Full audit trail in AWS CloudTrail

Variable Scoping:
  PIPELINE LEVEL: Available to all jobs
  JOB LEVEL: Available to all steps in that job
  STEP LEVEL: Available only to that step
  
  # GitHub Actions
  env:
    GLOBAL_VAR: "available everywhere"   # Pipeline level
  
  jobs:
    build:
      env:
        JOB_VAR: "available in this job"   # Job level
      steps:
        - name: Build
          env:
            STEP_VAR: "available here only"  # Step level
          run: |
            echo $GLOBAL_VAR $JOB_VAR $STEP_VAR

9. PIPELINE PATTERNS
================================================================================

Pattern 1: MONOREPO PIPELINES
  One repository, many services. Only build what changed.
  
  Tools:
    - Nx (JavaScript/TypeScript monorepos)
    - Turborepo (Node.js)
    - Bazel (language-agnostic)
    - Gradle project structure
  
  Strategy:
    # Use affected command to only test changed packages
    - run: npx nx affected --target=test --base=origin/main

Pattern 2: FAN-OUT / FAN-IN
  One job spawns multiple parallel jobs, then waits for all.
  
    [Trigger] → [Build] → [Test-A] ─┐
                                    ├→ [Merge Results] → [Publish]
                          [Test-B] ─┘
                          [Test-C] ─┘

Pattern 3: REUSABLE WORKFLOWS
  Extract common pipeline logic into a shared workflow.
  
  # .github/workflows/reusable-build.yml
  on:
    workflow_call:
      inputs:
        java-version:
          required: true
          type: string
  
  # .github/workflows/service-a.yml
  jobs:
    build:
      uses: ./.github/workflows/reusable-build.yml
      with:
        java-version: '21'

Pattern 4: RELEASE PIPELINE
  Separate pipeline for release candidates.
  
  Trigger: Push of tag matching v*.*.*
  Steps:
    1. Build + Test (same as CI)
    2. Create GitHub Release
    3. Build release Docker image (tagged with version)
    4. Publish to artifact registry
    5. Trigger CD pipeline for production deployment

Pattern 5: PROGRESSIVE DELIVERY PIPELINE
  CI passes → Deploy to staging → Run smoke tests → 
  Deploy to canary (5%) → Monitor metrics →
  Promote to full production

10. PIPELINE MONITORING
================================================================================

Key Metrics to Track:
  - Pipeline success rate (% of runs that pass)
  - Mean pipeline duration
  - P95 pipeline duration (95th percentile)
  - Flaky job rate (jobs that intermittently fail)
  - Queue time (waiting for runner availability)
  - Cache hit rate (% of runs that use cache)

Tools:
  - GitHub Actions: Repository Insights → Actions
  - GitLab CI: Analytics → CI/CD Analytics  
  - Datadog CI Visibility: Detailed pipeline analytics
  - Buildkite Analytics: Test failure and flakiness tracking
  - Custom: Prometheus metrics from CI API

Alerting:
  - Alert on: Build success rate < 90% over 24h
  - Alert on: Pipeline duration increase > 20%
  - Alert on: Main branch broken for > 15 minutes

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: Explain the difference between a pipeline stage, job, and step.
A: In CI/CD:
   - STEP: The smallest unit — a single command or action (run: npm test)
   - JOB: A collection of steps that execute on the same runner/agent.
     Jobs in the same pipeline run in parallel by default unless dependencies
     are specified.
   - STAGE: A logical grouping of jobs. Stages run sequentially. In Jenkins,
     stages are explicit. In GitHub Actions, ordering is controlled by the
     "needs" keyword.
   
   Example: A "build" stage contains a "compile" job and a "lint" job running
   in parallel. A "test" stage depends on "build" completing.

Q2: How would you optimize a CI pipeline that takes 45 minutes?
A: I'd approach this systematically:
   1. MEASURE: Profile which stages take the most time (build? tests? scan?)
   2. PARALLELIZE: Run lint, unit tests, security scans in parallel, not series
   3. CACHE: Ensure dependencies are cached. Check cache hit rate.
   4. TEST SPLITTING: Split test suite across multiple runners using matrix
   5. SKIP UNCHANGED: Use path filters to skip builds for unchanged services
      in a monorepo
   6. OPTIMIZE DOCKER: Use multi-stage builds, cache layers, slim base images
   7. INCREMENTAL BUILDS: Use Gradle Build Cache or Bazel for incremental builds
   8. FAST FAIL: Put fast checks (compile, lint) first, slow checks last
   
   Goal: Get to < 15 minutes. Beyond that, developers stop waiting and ignore results.

Q3: What is a matrix build and when would you use it?
A: A matrix build runs the same job with multiple combinations of parameters
   in parallel.
   
   Use cases:
   1. Cross-platform testing: Test on Linux, macOS, Windows simultaneously
   2. Multi-version testing: Test against Node 18, 20, 22 in parallel
   3. Test sharding: Split test suite into N groups, each running in parallel
   
   Example: A Node.js library should work on Node 16, 18, 20 and on both
   Linux and Windows. Matrix builds this as 3 × 2 = 6 parallel jobs.
   
   The key benefit is parallelism: matrix runs all combinations simultaneously
   rather than sequentially, dramatically reducing total pipeline time.

Q4: What is the difference between push triggers and PR triggers in CI?
A: Push triggers fire when commits are pushed to a branch. PR triggers fire
   when a PR is opened/updated.
   
   Typical usage:
   - PR trigger: Run CI on every commit to a PR. This is the fast feedback loop
     for developers. May run a reduced set of tests.
   - Push to main: Run full CI including security scans, integration tests, and
     artifact publishing. This is the gate for production-readiness.
   - Schedule trigger (cron): Run expensive tests (E2E, performance, full security
     scans) nightly rather than on every PR.
   - Tag trigger: Run release pipeline to build and publish versioned artifact.

Q5: How do you handle secrets in CI pipelines?
A: Several principles:
   1. NEVER in YAML: Secrets are never hardcoded in pipeline configuration files
   2. Platform secret stores: GitHub Secrets, GitLab CI Variables, Azure Key Vault
      linked to pipelines. These are masked in logs.
   3. OIDC over long-lived credentials: For cloud (AWS, GCP, Azure), use OIDC
      federation to get short-lived tokens instead of storing access keys.
   4. Least privilege: Each pipeline job only gets the secrets it actually needs.
      Use GitHub Environments to scope secrets to specific environments.
   5. Rotation: Regularly rotate any long-lived credentials used in CI.
   6. Audit: Review which workflows have access to sensitive secrets.
   
   Common mistake to call out: Storing AWS access keys as GitHub secrets that
   never expire. OIDC eliminates this entirely.
