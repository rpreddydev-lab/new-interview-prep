1. WHAT IS JENKINS?
================================================================================

Jenkins is an open-source automation server written in Java. It is one of the
most widely adopted CI/CD tools in the world, with over 300,000 active
installations.

History:
  2005: Hudson created by Kohsuke Kawaguchi at Sun Microsystems
  2010: Oracle acquires Sun. Community conflict over direction.
  2011: Community forks Hudson → creates Jenkins
  2016: Jenkins 2.0 — Pipeline as Code (Jenkinsfile)
  Today: Jenkins is maintained by the Jenkins community/CloudBees

Why Jenkins is Popular:
  - Open source, free
  - 1,800+ plugins covering almost every tool
  - Language and platform agnostic
  - Massive community and documentation
  - Highly customizable and extensible

Why Jenkins is Challenging:
  - Complex to set up and maintain
  - Configuration as Code historically difficult (getting better with JCasC)
  - Plugin dependency conflicts
  - Requires infrastructure management (unlike cloud-native alternatives)
  - Security hardening requires significant effort
  - Groovy DSL has a learning curve

Core Jenkins Concepts:
  JOB/PROJECT: A configurable unit of work (build, test, deploy)
  BUILD: One execution of a job
  EXECUTOR: A slot that can run a build on a node
  NODE/AGENT: A machine that runs builds
  CONTROLLER (formerly "Master"): Central Jenkins server, manages agents
  WORKSPACE: Directory on agent where build runs
  ARTIFACT: Output files saved from a build
  UPSTREAM/DOWNSTREAM: Job dependencies (upstream triggers downstream)
  PIPELINE: Sequence of stages defined as code (Jenkinsfile)

2. JENKINS ARCHITECTURE
================================================================================

Components:

  JENKINS CONTROLLER (Master):
    - Manages configuration
    - Schedules builds to agents
    - Stores build history and logs
    - Serves the web UI
    - Manages plugins
    - Should NOT run builds directly (security + performance)
  
  JENKINS AGENTS (Workers):
    - Execute build steps
    - Each agent has N executors (parallel slots)
    - Can be labeled (linux, docker, gpu, java21)
    - Can be static (always on) or ephemeral (cloud-provisioned)
    - Connect to controller via SSH, JNLP (Java Web Start), or WebSocket
  
  BUILD QUEUE:
    - Jobs wait here if no matching agent is available
    - Ordered by priority and wait time
  
  ARTIFACT STORAGE:
    - Jenkins can store artifacts locally
    - Enterprise: JFrog Artifactory, Nexus Repository Manager

Architecture Diagram:
  
  [Developers] → Push code → [Git Repository]
                                     |
                                     | Webhook trigger
                                     ↓
                            [Jenkins Controller]
                            - Web UI (port 8080)
                            - Build scheduler
                            - Plugin manager
                                     |
                        ┌────────────┼────────────┐
                        ↓            ↓            ↓
                   [Agent 1]    [Agent 2]    [Agent 3]
                   linux-build  windows-test  docker
                   executor×4   executor×2   executor×8

Controller Security Best Practices:
  - Don't run builds on controller (disable executor count: 0)
  - Run controller behind reverse proxy (Nginx/Apache)
  - Enable Security Realm (LDAP, GitHub OAuth, or built-in)
  - Enable Authorization Strategy (matrix, role-based)
  - Run on dedicated server/VM with limited access

High Availability:
  Jenkins controller is traditionally a SPOF (Single Point of Failure).
  
  Solutions:
  - CloudBees CI: Active/Standby HA setup
  - Jenkins controller on Kubernetes: StatefulSet with PVC for persistence
  - Automated backup of JENKINS_HOME directory

3. DECLARATIVE VS SCRIPTED PIPELINE
================================================================================

Two DSLs (Domain-Specific Languages) for defining Jenkins Pipelines:

  DECLARATIVE PIPELINE (recommended):
  - Introduced in Jenkins 2 (2016)
  - Opinionated structure with predefined sections
  - Easier to read and write
  - Better validation and error messages
  - Syntax checked before execution
  - Preferred for most use cases
  
  SCRIPTED PIPELINE (older):
  - Original pipeline DSL
  - Full Groovy programming language
  - Maximum flexibility
  - No structural validation
  - More complex error handling
  - Use only when declarative is insufficient

Comparison:

  Declarative:                    Scripted:
  ─────────────────────────────   ─────────────────────────
  pipeline {                      node('linux') {
    agent any                       stage('Build') {
    stages {                          sh 'mvn compile'
      stage('Build') {             }
        steps {                     stage('Test') {
          sh 'mvn compile'            sh 'mvn test'
        }                          }
      }                           }
      stage('Test') {
        steps {
          sh 'mvn test'
        }
      }
    }
  }

4. JENKINSFILE — DECLARATIVE PIPELINE
================================================================================

Basic Structure:

  pipeline {
      agent { ... }             // Where to run (required)
      
      options { ... }           // Global pipeline options
      
      environment { ... }       // Global environment variables
      
      tools { ... }             // Install tools
      
      triggers { ... }          // How to trigger this pipeline
      
      parameters { ... }        // User-configurable inputs
      
      stages {                  // Sequential stages
          stage('Name') {
              agent { ... }     // Stage-level agent (optional override)
              when { ... }      // Conditional execution
              environment { ... }
              options { ... }
              steps {           // Build steps
                  sh '...'
                  script { ... }
              }
              post { ... }      // Stage post-processing
          }
      }
      
      post {                    // Pipeline post-processing
          always { ... }
          success { ... }
          failure { ... }
          unstable { ... }
          cleanup { ... }
      }
  }

Real-World Declarative Jenkinsfile:

  pipeline {
      agent none   // Don't allocate agent globally; each stage specifies
      
      options {
          buildDiscarder(logRotator(numToKeepStr: '30'))
          timeout(time: 30, unit: 'MINUTES')
          disableConcurrentBuilds()
          timestamps()   // Prefix every log line with timestamp
      }
      
      environment {
          REGISTRY = 'registry.example.com'
          IMAGE = "myapp"
          VERSION = "${GIT_COMMIT[0..7]}"   // Short SHA
      }
      
      parameters {
          choice(
              name: 'ENVIRONMENT',
              choices: ['staging', 'production'],
              description: 'Deploy target'
          )
          booleanParam(
              name: 'SKIP_TESTS',
              defaultValue: false,
              description: 'Skip test execution'
          )
      }
      
      triggers {
          githubPush()      // GitHub webhook trigger
          cron('0 2 * * *') // Nightly at 2 AM
      }
      
      stages {
          stage('Checkout') {
              agent { label 'any' }
              steps {
                  checkout scm
                  sh 'git log --oneline -5'
              }
          }
          
          stage('Build') {
              agent { 
                  docker { image 'maven:3.9-eclipse-temurin-21' }
              }
              steps {
                  sh 'mvn clean compile -q'
              }
          }
          
          stage('Tests') {
              parallel {
                  stage('Unit Tests') {
                      agent {
                          docker { image 'maven:3.9-eclipse-temurin-21' }
                      }
                      when { expression { !params.SKIP_TESTS } }
                      steps {
                          sh 'mvn test'
                          junit 'target/surefire-reports/*.xml'
                          jacoco(execPattern: 'target/jacoco.exec',
                                 minimumLineCoverage: '80')
                      }
                  }
                  
                  stage('Integration Tests') {
                      agent {
                          docker { image 'maven:3.9-eclipse-temurin-21' }
                      }
                      when { branch 'main' }
                      steps {
                          sh 'mvn verify -P integration-tests'
                          junit 'target/failsafe-reports/*.xml'
                      }
                  }
                  
                  stage('Lint') {
                      agent { label 'linux' }
                      steps {
                          sh 'mvn checkstyle:check'
                      }
                  }
              }
          }
          
          stage('SonarQube Analysis') {
              agent { label 'linux' }
              steps {
                  withSonarQubeEnv('SonarQubeServer') {
                      sh '''
                          mvn sonar:sonar \
                            -Dsonar.projectKey=myapp \
                            -Dsonar.projectName=myapp
                      '''
                  }
                  timeout(time: 5, unit: 'MINUTES') {
                      waitForQualityGate abortPipeline: true
                  }
              }
          }
          
          stage('Package') {
              agent {
                  docker { image 'maven:3.9-eclipse-temurin-21' }
              }
              steps {
                  sh 'mvn package -DskipTests'
                  archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
              }
          }
          
          stage('Docker Build and Push') {
              agent { label 'docker' }
              when { branch 'main' }
              steps {
                  script {
                      docker.withRegistry("https://${REGISTRY}", 'registry-credentials') {
                          def image = docker.build("${REGISTRY}/${IMAGE}:${VERSION}")
                          image.push()
                          image.push('latest')
                      }
                  }
              }
          }
          
          stage('Deploy to Staging') {
              agent { label 'deploy' }
              when {
                  allOf {
                      branch 'main'
                      not { expression { params.SKIP_TESTS } }
                  }
              }
              steps {
                  sh "helm upgrade --install myapp charts/myapp \
                      --namespace staging \
                      --set image.tag=${VERSION}"
              }
          }
      }
      
      post {
          always {
              cleanWs()   // Clean workspace on every run
          }
          success {
              slackSend(color: 'good', 
                        message: "Build ${BUILD_NUMBER} succeeded: ${BUILD_URL}")
          }
          failure {
              slackSend(color: 'danger',
                        message: "Build ${BUILD_NUMBER} FAILED: ${BUILD_URL}")
              emailext(
                  to: '$DEFAULT_RECIPIENTS',
                  subject: "Build FAILED: ${JOB_NAME} #${BUILD_NUMBER}",
                  body: '${DEFAULT_CONTENT}'
              )
          }
      }
  }

Key Declarative Sections:

  agent:
    any                           // Any available agent
    none                         // No global agent, stages specify their own
    label 'linux'                 // Agent with 'linux' label
    docker { image 'node:20' }    // Docker container
    kubernetes { yaml '...' }     // Kubernetes pod (via Kubernetes plugin)

  when (conditions):
    branch 'main'                 // Only on main branch
    not { branch 'main' }         // Any branch except main
    tag 'v*'                      // When tag matching v* pushed
    changeRequest()               // On pull requests
    expression { params.DEPLOY }  // Custom Groovy expression
    allOf { ... }                 // All conditions must be true
    anyOf { ... }                 // Any condition must be true

  post conditions:
    always            // Always run (cleanup, reports)
    success           // Only if pipeline succeeded
    failure           // Only if pipeline failed
    unstable          // Tests failed but pipeline continued
    aborted           // Manually aborted
    cleanup           // Runs last, after other post conditions

5. JENKINSFILE — SCRIPTED PIPELINE
================================================================================

Full Groovy programming power, but more verbose and complex:

  // Define reusable functions
  def buildApp() {
      sh 'mvn clean package -DskipTests'
  }
  
  def testApp() {
      try {
          sh 'mvn test'
      } finally {
          // Always archive test results, even on failure
          junit allowEmptyResults: true, testResults: '**/surefire-reports/*.xml'
      }
  }
  
  // Main pipeline
  node('linux') {
      def version = ''
      
      stage('Checkout') {
          checkout scm
          version = sh(returnStdout: true, script: 'git rev-parse --short HEAD').trim()
          echo "Building version: ${version}"
      }
      
      stage('Build') {
          docker.image('maven:3.9-eclipse-temurin-21').inside('-v /root/.m2:/root/.m2') {
              buildApp()
          }
      }
      
      stage('Test') {
          docker.image('maven:3.9-eclipse-temurin-21').inside('-v /root/.m2:/root/.m2') {
              testApp()
          }
      }
      
      if (env.BRANCH_NAME == 'main') {
          stage('Docker Build') {
              docker.withRegistry('https://registry.example.com', 'registry-creds') {
                  def img = docker.build("myapp:${version}")
                  img.push()
              }
          }
      }
  }

When to Use Scripted:
  - Need complex loops (building multiple microservices dynamically)
  - Dynamic stage generation based on files present
  - Complex error handling and retry logic
  - Integrating with external systems via Groovy HTTP calls

6. JENKINS AGENTS / NODES
================================================================================

Static Agents (permanent):
  - Long-running VMs or physical machines
  - Always available
  - Connect via SSH or JNLP
  
  Configuration:
  - Manage Jenkins → Nodes → New Node
  - Set labels (e.g., linux, docker, maven)
  - Set number of executors
  - Set remote root directory

Docker Agents:
  - Spin up a Docker container for each build
  - Clean environment per build (no stale state)
  - Specify image in Jenkinsfile
  
  Requirements: Docker must be installed on the agent/host.
  
  agent {
      docker {
          image 'maven:3.9-eclipse-temurin-21'
          args '-v /root/.m2:/root/.m2'   // Mount Maven cache
          label 'docker-agent'             // Run on agent with docker label
      }
  }

Kubernetes Agents (most scalable):
  Via Kubernetes Plugin: Jenkins spins up a Kubernetes pod per build.
  
  Benefits:
  - Auto-scales: Pods created on demand, terminated after build
  - No idle agent costs
  - True isolation per build
  - Can use multiple containers in one pod
  
  agent {
      kubernetes {
          yaml '''
              apiVersion: v1
              kind: Pod
              spec:
                containers:
                - name: maven
                  image: maven:3.9-eclipse-temurin-21
                  command: [cat]
                  tty: true
                  volumeMounts:
                  - mountPath: /root/.m2
                    name: maven-cache
                - name: docker
                  image: docker:dind
                  securityContext:
                    privileged: true
                volumes:
                - name: maven-cache
                  persistentVolumeClaim:
                    claimName: maven-cache-pvc
          '''
      }
  }
  stages {
      stage('Build') {
          steps {
              container('maven') {
                  sh 'mvn package'
              }
          }
      }
  }

Cloud Agents (EC2 Plugin, Azure VM Agents, etc.):
  Jenkins can provision cloud VMs on demand.
  - Spin up when queue builds up
  - Terminate after idle timeout
  - Cost-efficient for variable workloads

8. JENKINS SHARED LIBRARIES
================================================================================

Problem: Copy-pasting Jenkinsfile across 50 microservices.
Solution: Jenkins Shared Libraries — reusable Groovy code.

Structure of a Shared Library:
  (shared-library repository)
  ├── vars/               # Global variables (functions callable from Jenkinsfile)
  │   ├── buildJava.groovy
  │   ├── deployHelm.groovy
  │   └── sendSlack.groovy
  ├── src/                # Groovy classes (more complex code)
  │   └── com/example/
  │       ├── DockerUtils.groovy
  │       └── BuildConfig.groovy
  └── resources/          # Non-Groovy files (scripts, templates)
      └── scripts/
          └── health-check.sh

Example Shared Variable (vars/buildJava.groovy):
  #!/usr/bin/env groovy
  
  def call(Map config = [:]) {
      // Default values
      def javaVersion = config.javaVersion ?: '21'
      def goals = config.goals ?: 'clean verify'
      def skipTests = config.skipTests ?: false
      
      pipeline {
          agent {
              docker { image "maven:3.9-eclipse-temurin-${javaVersion}" }
          }
          stages {
              stage('Build and Test') {
                  steps {
                      sh "mvn ${goals} ${skipTests ? '-DskipTests' : ''}"
                  }
                  post {
                      always {
                          junit allowEmptyResults: true,
                                testResults: '**/surefire-reports/*.xml'
                      }
                  }
              }
          }
      }
  }

Using Shared Library in Jenkinsfile:
  @Library('my-shared-library@main') _
  
  // Call the shared function
  buildJava(
      javaVersion: '21',
      goals: 'clean verify',
      skipTests: false
  )

Configuration in Jenkins:
  Manage Jenkins → System → Global Pipeline Libraries
  - Name: my-shared-library
  - Source code management: Git
  - URL: https://github.com/example/jenkins-shared-lib.git
  - Default version: main

Advanced Shared Library Example:
  // vars/dockerBuild.groovy
  def call(String imageName, String tag) {
      script {
          def imageTag = "${imageName}:${tag}"
          docker.withRegistry('https://registry.example.com', 'registry-creds') {
              def img = docker.build(imageTag)
              img.push()
              img.push('latest')
              
              // Scan image for vulnerabilities
              sh "trivy image --exit-code 1 --severity HIGH,CRITICAL ${imageTag}"
              
              return imageTag
          }
      }
  }
  
  // Jenkinsfile using it
  @Library('shared-lib@v2.1.0') _
  
  pipeline {
      stages {
          stage('Docker Build') {
              steps {
                  script {
                      def tag = sh(returnStdout: true, script: 'git rev-parse --short HEAD').trim()
                      dockerBuild('myapp', tag)
                  }
              }
          }
      }
  }

9. CREDENTIALS AND SECRETS
================================================================================

Jenkins Credentials Plugin:
  Types:
  - Username with password
  - SSH Username with private key
  - Secret text (API token, password)
  - Secret file
  - Certificate (PKCS#12)
  - AWS credentials (via AWS Credentials Plugin)
  - Kubernetes service account

Scopes:
  - Global: Available to all jobs
  - System: Available to Jenkins internals only
  - Folder: Available to jobs within a folder

Using Credentials in Declarative Pipeline:
  environment {
      // Bind credentials to environment variables
      REGISTRY_CREDS = credentials('docker-registry-creds')
      // Creates REGISTRY_CREDS_USR and REGISTRY_CREDS_PSW
      
      SONAR_TOKEN = credentials('sonar-token')
      // Creates SONAR_TOKEN as single value
      
      AWS_CREDS = credentials('aws-access-key')
      // Creates AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY
  }
  
  steps {
      sh '''
          echo $REGISTRY_CREDS_PSW | docker login -u $REGISTRY_CREDS_USR --password-stdin
      '''
  }

Using Credentials in Scripted Pipeline:
  // Method 1: withCredentials block
  withCredentials([
      usernamePassword(
          credentialsId: 'registry-creds',
          usernameVariable: 'REG_USER',
          passwordVariable: 'REG_PASS'
      )
  ]) {
      sh 'docker login -u $REG_USER -p $REG_PASS registry.example.com'
  }
  
  // Method 2: sshagent
  sshagent(credentials: ['deploy-ssh-key']) {
      sh 'ssh -o StrictHostKeyChecking=no user@server deploy.sh'
  }

External Secrets (HashiCorp Vault):
  // Jenkins Vault Plugin
  def secrets = [
      [path: 'secret/data/myapp', engineVersion: 2,
       secretValues: [
           [vaultKey: 'DB_PASSWORD', envVar: 'DB_PASSWORD'],
           [vaultKey: 'API_KEY', envVar: 'API_KEY']
       ]]
  ]
  
  def configuration = [vaultUrl: 'https://vault.example.com',
                       vaultCredentialId: 'vault-approle',
                       engineVersion: 2]
  
  withVault([configuration: configuration, vaultSecrets: secrets]) {
      sh 'echo $DB_PASSWORD'   // From Vault, never stored in Jenkins
  }

10. JENKINS AT SCALE — DISTRIBUTED BUILDS
================================================================================

Multi-Branch Pipeline:
  Automatically creates a pipeline for each branch in the repository.
  
  - Creates/deletes branch jobs automatically as branches are created/deleted
  - Each branch gets its own build history
  - Reads Jenkinsfile from each branch
  
  Common configuration:
  - Discover branches: All branches, or specific patterns
  - Discover PRs: Build PR merge result
  - Property strategies: Different settings per branch

Organization Folder (GitHub Organization Plugin):
  Automatically creates pipelines for ALL repositories in a GitHub organization.
  - Scans for Jenkinsfiles in all repos
  - Scales CI automatically as new repos are added

Pipeline Durability:
  Pipelines can survive Jenkins restart:
  - PERFORMANCE_OPTIMIZED: Faster, less persistent (default)
  - SURVIVABLE_NONATOMIC: Survives clean restart
  - MAX_SURVIVABILITY: Survives hard restart (slowest)

Build Timeouts and Resource Limits:
  options {
      timeout(time: 30, unit: 'MINUTES')       // Kill hung builds
      buildDiscarder(logRotator(
          numToKeepStr: '20',                   // Keep 20 builds
          artifactNumToKeepStr: '5'             // Keep artifacts for 5
      ))
      disableConcurrentBuilds(abortPrevious: true) // Cancel old build on new push
  }

Build Throttling:
  throttleJobProperty prevents too many builds running in parallel:
  - Throttle Concurrent Builds Plugin
  - throttleCategories for shared limits across jobs

Jenkins Configuration as Code (JCasC):
  Define Jenkins configuration in YAML, not through UI.
  
  jenkins.yaml example:
    jenkins:
      systemMessage: "Jenkins Configuration as Code"
      numExecutors: 0     # No builds on controller
      
      securityRealm:
        github:
          githubWebUri: "https://github.com"
          oauthScopes: "read:org,user:email"
          clientID: "${GITHUB_CLIENT_ID}"
          clientSecret: "${GITHUB_CLIENT_SECRET}"
      
      authorizationStrategy:
        roleBased:
          roles:
            global:
              - name: "admin"
                permissions:
                  - "Overall/Administer"
                entries:
                  - user: "admin-user"
  
  Benefits:
  - Infrastructure as Code for Jenkins itself
  - Version-controlled configuration
  - Reproducible Jenkins instances
  - Eliminates "snowflake" Jenkins servers

11. JENKINS X AND MODERN JENKINS
================================================================================

Jenkins X:
  A CI/CD platform built for Kubernetes, inspired by Jenkins but cloud-native.
  
  Key differences from Jenkins:
  - Native Kubernetes: Tekton pipelines, not Groovy
  - GitOps by default: Environment promotion via pull requests
  - Automated: jx boot sets up entire platform
  - Integrated: Comes with chart museum, docker registry, etc.
  
  Less adopted than expected; Tekton + ArgoCD has largely replaced it.

Jenkins on Kubernetes (modern):
  - Jenkins controller as StatefulSet
  - Kubernetes plugin for dynamic agents
  - Persistent Volume Claim for JENKINS_HOME
  - Kubernetes Secrets for credentials
  - JCasC for configuration management

12. JENKINS VS MODERN CI ALTERNATIVES
================================================================================

Jenkins vs GitHub Actions:

  Jenkins:
  + Full control over infrastructure
  + 1,800+ plugins
  + Can build private repos without internet access (air-gapped)
  + Highly customizable
  - Must manage your own infrastructure
  - Complex setup and maintenance
  - No native GitHub integration
  - Groovy DSL learning curve
  
  GitHub Actions:
  + Zero infrastructure to manage (cloud-hosted)
  + Native GitHub integration (PRs, status checks, releases)
  + Marketplace with 15,000+ actions
  + YAML is more readable
  + OIDC for cloud credentials
  - GitHub lock-in
  - Less flexible for complex custom workflows
  - Per-minute billing for private repos

Jenkins vs GitLab CI:

  Jenkins:
  + Works with any VCS
  + More plugins and customization
  - Separate server to manage
  
  GitLab CI:
  + Integrated with GitLab (no separate server)
  + Simpler YAML syntax
  + Better built-in features (environments, review apps, security scanning)
  - Tied to GitLab

When to Use Jenkins:
  - On-premises, air-gapped environments
  - Complex legacy CI workflows already built in Jenkins
  - Need a specific plugin that doesn't exist elsewhere
  - Multi-VCS (builds trigger from GitHub, GitLab, Bitbucket)
  - Team already has Jenkins expertise

When NOT to Use Jenkins (and use GitHub Actions/GitLab CI instead):
  - Starting fresh with a cloud-native setup
  - All code is on GitHub/GitLab
  - Small/medium team without dedicated DevOps engineer
  - Want to minimize CI infrastructure maintenance

13. COMMON INTERVIEW QUESTIONS & ANSWERS

Q1: What is the difference between Declarative and Scripted Jenkins Pipeline?
A: Declarative pipeline (introduced in Jenkins 2) uses a predefined structure
   with explicit sections (agent, stages, post). It's easier to read, has
   better error messages, and is validated before execution. It's the
   recommended approach for most pipelines.
   
   Scripted pipeline is full Groovy code — it's more powerful and flexible but
   harder to maintain. Use it when declarative can't express what you need, like
   dynamically generating stages at runtime or complex programmatic logic.
   
   In practice, I default to declarative and use a 'script {}' block within it
   when I need Groovy capabilities.

Q2: What is a Jenkins Shared Library and why would you use it?
A: A Jenkins Shared Library is a Git repository containing reusable Groovy code
   (functions, classes, scripts) that multiple Jenkinsfiles can reference.
   
   Why use it:
   - Don't Repeat Yourself: Define build steps once, use across 50+ repos
   - Consistency: All teams follow the same CI process
   - Maintainability: Update pipeline logic in one place
   - Abstraction: Teams write simple Jenkinsfiles that call shared functions
   
   Example: A 'buildJavaApp()' function in the shared library handles checkout,
   Maven build, test, coverage check, and SonarQube. Each repo's Jenkinsfile
   just calls buildJavaApp(javaVersion: '21') instead of duplicating 100 lines.

Q3: How does Jenkins manage credentials securely?
A: Jenkins has a Credentials Plugin that stores secrets (passwords, tokens, keys)
   in an encrypted credential store separate from pipeline configuration.
   
   Credentials are referenced by ID in pipelines, never hardcoded:
   - environment block: credentials('id') automatically masks values in logs
   - withCredentials() block: Temporarily binds credentials to env vars
   
   For enterprise setups, I prefer external secret management via HashiCorp Vault
   Plugin. Jenkins doesn't store the secrets — it fetches them from Vault at
   runtime using AppRole authentication. This enables rotation without updating
   Jenkins configuration.

Q4: How do you scale Jenkins for a large organization?
A: Several strategies:
   
   1. DYNAMIC AGENTS: Never run builds on the controller. Use Kubernetes plugin
      to spawn/terminate pods on demand. This scales horizontally automatically.
   
   2. MULTI-CONTROLLER: Use CloudBees CI with multiple controllers, each owning
      specific teams or environments.
   
   3. FOLDERS + RBAC: Organize jobs in folders, one per team. Use Role-Based
      Access Control to restrict access.
   
   4. SHARED LIBRARIES: Reduce duplication across 100s of Jenkinsfiles.
   
   5. CONFIGURATION AS CODE (JCasC): Version-controlled Jenkins configuration
      prevents manual snowflake configuration drift.
   
   6. BUILD OPTIMIZATION: Parallel stages, Docker layer caching, Gradle build
      cache to reduce build times and agent demand.

Q5: What plugins are essential for a production Jenkins setup?
A: Core: Pipeline, Blue Ocean, Git, GitHub Branch Source
   Security: Credentials, RBAC/Matrix Authorization, OWASP Dependency Check
   Quality: SonarQube Scanner, JaCoCo, Checkstyle
   Agents: Kubernetes Plugin (or AWS EC2)
   Notifications: Slack Notification, Email Extension
   Secrets: HashiCorp Vault (if using Vault)
   IaC: Configuration as Code Plugin

Q6: How would you troubleshoot a Jenkins pipeline that's randomly failing?
A: Systematic approach:
   1. Check LOGS: Console output often shows the exact failure
   2. REPRODUCE: Try to reproduce locally or in a clean environment
   3. FLAKINESS: Run the job multiple times — is it consistently failing or
      intermittently? If intermittent, might be resource contention, network
      issues, or test flakiness
   4. AGENT ISSUES: Check if failures correlate with a specific agent (label)
   5. TIMING: Check for race conditions, missing health checks on services
   6. ENVIRONMENT: Check if failure correlates with a specific branch or commit
   7. PLUGINS: Recent plugin update could have introduced a bug — check changelog
   8. REBUILD BUTTON: Try rebuilding the same commit to isolate transient failures

Jenkins Key Files:
  Jenkinsfile              Pipeline definition (lives in repo root)
  JENKINS_HOME/            All Jenkins data, jobs, configs
  jenkins.yaml             JCasC configuration

Declarative Structure:
  pipeline → agent → options → environment → tools → triggers →
  parameters → stages → stage → when → steps → post

Common Built-in Variables:
  BUILD_NUMBER, BUILD_URL, JOB_NAME, WORKSPACE, GIT_COMMIT, GIT_BRANCH,
  BRANCH_NAME (multi-branch), CHANGE_ID (PR number)

Useful Steps:
  sh 'command'                    // Shell command
  bat 'command'                   // Windows batch
  echo 'message'
  input 'Approve deployment?'     // Manual approval gate
  timeout(time: 5, unit: 'MINUTES') { ... }
  retry(3) { ... }
  sleep(time: 30, unit: 'SECONDS')
  archiveArtifacts 'target/*.jar'
  junit 'reports/*.xml'
  stash(name: 'app', includes: 'target/*.jar')
  unstash 'app'
  cleanWs()

Agent Options:
  agent any | none | { label 'name' } | { docker { image 'img' } } |
  { kubernetes { yaml '...' } }

Parallel Stages:
  parallel {
      stage('A') { ... }
      stage('B') { ... }
  }

Credential Binding:
  environment {
      MY_TOKEN = credentials('token-id')
  }

Libraries:
  @Library('shared-lib@version') _

Plugin Install (CLI):
  java -jar jenkins-cli.jar -s http://jenkins:8080 install-plugin plugin-name
