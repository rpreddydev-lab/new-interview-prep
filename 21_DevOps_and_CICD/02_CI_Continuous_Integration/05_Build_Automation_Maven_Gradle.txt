1. WHAT IS BUILD AUTOMATION?
================================================================================

Build automation is the process of automating the creation of a software build
and the associated processes: source code compilation, packaging, automated
testing, and artifact creation.

Without build automation:
  - Manually compile files: javac -cp ... MyClass.java
  - Manually resolve dependencies: Download JARs manually
  - Manually run tests: java -cp ... TestRunner
  - Inconsistent builds between developers

With build automation:
  mvn package       (Maven) — Does everything
  ./gradlew build   (Gradle) — Does everything

Key Build Automation Responsibilities:
  1. DEPENDENCY MANAGEMENT: Download and manage JARs/packages from central repos
  2. COMPILATION: Compile source code with correct classpath
  3. TESTING: Run unit and integration tests, collect results
  4. PACKAGING: Bundle compiled code into JAR/WAR/EAR/Docker image
  5. INSTALLATION: Publish artifacts to local or remote repositories
  6. REPORTING: Test results, code coverage, static analysis reports

Major Java Build Tools:
  Ant (2000):     XML-based, procedural. Flexible but verbose.
                  No dependency management (added via Ivy plugin).
  Maven (2004):   XML (pom.xml), convention over configuration.
                  Built-in dependency management (Maven Central).
  Gradle (2007):  Groovy/Kotlin DSL. Combines Maven conventions + Ant flexibility.
                  Incremental builds, build cache.
  Bazel (2015):   Google's build system. Hermetic, massively scalable.
                  Monorepo-focused.
  Buck (2013):    Facebook's build system. Similar to Bazel.

2. MAVEN OVERVIEW
================================================================================

Maven is a build automation and dependency management tool for Java (and other JVM
languages). It uses an XML-based configuration file called pom.xml.

Core Philosophy: Convention over Configuration
  Maven defines a standard project structure. If you follow it, configuration
  is minimal.
  
  Standard Directory Layout:
  my-project/
  ├── pom.xml                      # Project configuration
  ├── src/
  │   ├── main/
  │   │   ├── java/                # Production source code
  │   │   ├── resources/           # Production resources (application.properties)
  │   │   └── webapp/              # Web resources (for WAR projects)
  │   └── test/
  │       ├── java/                # Test source code
  │       └── resources/           # Test resources
  └── target/                      # Build output (generated, in .gitignore)
      ├── classes/                 # Compiled production classes
      ├── test-classes/            # Compiled test classes
      ├── surefire-reports/        # Test results
      └── myapp-1.0.0.jar          # Packaged artifact

Key Maven Concepts:
  COORDINATE: GroupId + ArtifactId + Version (GAV) uniquely identify any artifact
  REPOSITORY: Where artifacts are stored and fetched from
    - Local: ~/.m2/repository (cache on developer machine)
    - Central: repo1.maven.org/maven2 (public internet)
    - Remote: Company Nexus/Artifactory
  PHASE: Step in the build lifecycle (compile, test, package)
  GOAL: A specific task a plugin can perform (compiler:compile, surefire:test)
  PLUGIN: Extension that provides goals (Compiler Plugin, Surefire Plugin)

3. MAVEN PROJECT OBJECT MODEL (POM)
================================================================================

The pom.xml is the heart of a Maven project.

Minimal pom.xml:
  <?xml version="1.0" encoding="UTF-8"?>
  <project xmlns="http://maven.apache.org/POM/4.0.0"
           xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
           xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                               http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>jar</packaging>
  </project>

Complete Real-World pom.xml:

  <?xml version="1.0" encoding="UTF-8"?>
  <project ...>
    <modelVersion>4.0.0</modelVersion>
    
    <!-- Coordinates -->
    <groupId>com.example</groupId>
    <artifactId>order-service</artifactId>
    <version>2.1.0-SNAPSHOT</version>
    <packaging>jar</packaging>
    
    <!-- Human-readable info -->
    <name>Order Service</name>
    <description>Microservice for order management</description>
    
    <!-- Parent POM (inherit config) -->
    <parent>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-parent</artifactId>
      <version>3.2.0</version>
    </parent>
    
    <!-- Properties (variables) -->
    <properties>
      <java.version>21</java.version>
      <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
      <maven.compiler.source>21</maven.compiler.source>
      <maven.compiler.target>21</maven.compiler.target>
      <!-- Version properties for dependency management -->
      <testcontainers.version>1.19.0</testcontainers.version>
      <mapstruct.version>1.5.5.Final</mapstruct.version>
    </properties>
    
    <!-- Dependencies -->
    <dependencies>
      <!-- Compile scope (default): needed to compile and at runtime -->
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <!-- Version inherited from parent -->
      </dependency>
      
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>
      </dependency>
      
      <!-- Provided scope: provided by runtime (e.g., servlet container) -->
      <dependency>
        <groupId>jakarta.servlet</groupId>
        <artifactId>jakarta.servlet-api</artifactId>
        <scope>provided</scope>
      </dependency>
      
      <!-- Test scope: only for test compilation and execution -->
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
      </dependency>
      
      <dependency>
        <groupId>org.testcontainers</groupId>
        <artifactId>postgresql</artifactId>
        <version>${testcontainers.version}</version>
        <scope>test</scope>
      </dependency>
      
      <!-- Runtime scope: not needed to compile, needed at runtime -->
      <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <scope>runtime</scope>
      </dependency>
    </dependencies>
    
    <!-- Dependency Management (centralize versions in multi-module) -->
    <dependencyManagement>
      <dependencies>
        <dependency>
          <groupId>org.testcontainers</groupId>
          <artifactId>testcontainers-bom</artifactId>
          <version>${testcontainers.version}</version>
          <type>pom</type>
          <scope>import</scope>
        </dependency>
      </dependencies>
    </dependencyManagement>
    
    <!-- Build Configuration -->
    <build>
      <plugins>
        <!-- Spring Boot executable JAR -->
        <plugin>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-maven-plugin</artifactId>
          <configuration>
            <excludes>
              <exclude>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
              </exclude>
            </excludes>
          </configuration>
        </plugin>
        
        <!-- Surefire: unit tests -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-surefire-plugin</artifactId>
          <configuration>
            <excludes>
              <exclude>**/*IT.java</exclude>    <!-- Skip integration tests -->
            </excludes>
          </configuration>
        </plugin>
        
        <!-- Failsafe: integration tests -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-failsafe-plugin</artifactId>
          <executions>
            <execution>
              <goals>
                <goal>integration-test</goal>
                <goal>verify</goal>
              </goals>
            </execution>
          </executions>
        </plugin>
        
        <!-- JaCoCo: code coverage -->
        <plugin>
          <groupId>org.jacoco</groupId>
          <artifactId>jacoco-maven-plugin</artifactId>
          <version>0.8.11</version>
          <executions>
            <execution>
              <goals>
                <goal>prepare-agent</goal>
              </goals>
            </execution>
            <execution>
              <id>report</id>
              <phase>test</phase>
              <goals>
                <goal>report</goal>
              </goals>
            </execution>
            <execution>
              <id>check</id>
              <goals>
                <goal>check</goal>
              </goals>
              <configuration>
                <rules>
                  <rule>
                    <limits>
                      <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                      </limit>
                    </limits>
                  </rule>
                </rules>
              </configuration>
            </execution>
          </executions>
        </plugin>
      </plugins>
    </build>
    
    <!-- Profiles (different configs for different environments) -->
    <profiles>
      <profile>
        <id>ci</id>
        <properties>
          <maven.test.skip>false</maven.test.skip>
        </properties>
        <build>
          <plugins>
            <!-- Additional plugins for CI -->
          </plugins>
        </build>
      </profile>
    </profiles>
    
    <!-- Repository configuration -->
    <repositories>
      <repository>
        <id>company-nexus</id>
        <url>https://nexus.example.com/repository/maven-public/</url>
      </repository>
    </repositories>
  </project>

Dependency Scopes:
  compile (default):  Needed to compile and at runtime. Included in JAR.
  provided:           Compile time only. NOT included (e.g., servlet-api).
  runtime:            NOT needed to compile. Included at runtime (e.g., JDBC driver).
  test:               Only for tests. NOT in final artifact.
  system:             Local JAR on filesystem (avoid — not portable).
  import:             Import a BOM (Bill of Materials) in dependencyManagement.

Version Qualifiers:
  1.0.0              → Release version
  1.0.0-SNAPSHOT     → Development version (can change, always re-downloaded)
  1.0.0-RELEASE      → Deprecated release qualifier
  
  SNAPSHOT versions bypass local cache (re-downloaded if newer exists in remote).

4. MAVEN BUILD LIFECYCLE
================================================================================

Maven has three built-in lifecycles:

1. DEFAULT lifecycle (main build):
   validate → initialize → generate-sources → process-sources →
   generate-resources → process-resources → COMPILE → process-classes →
   generate-test-sources → process-test-sources → generate-test-resources →
   process-test-resources → test-compile → process-test-classes →
   TEST → prepare-package → PACKAGE → pre-integration-test →
   integration-test → post-integration-test → VERIFY →
   INSTALL → DEPLOY

2. CLEAN lifecycle:
   pre-clean → CLEAN → post-clean
   Deletes the target/ directory.

3. SITE lifecycle:
   pre-site → SITE → post-site → site-deploy
   Generates project documentation website.

Most-Used Phase Commands:
  mvn validate      Check project structure is valid
  mvn compile       Compile src/main/java
  mvn test          Compile and run tests
  mvn package       Compile, test, package (creates JAR/WAR)
  mvn verify        Package + integration tests + verify artifact quality
  mvn install       Verify + install to local repo (~/.m2)
  mvn deploy        Install + upload to remote repository
  mvn clean         Delete target/ directory
  mvn clean verify  Clean then full build+test cycle

Key: Each phase includes all previous phases.
  Running 'mvn package' also runs validate, compile, test.
  Running 'mvn install' also runs package.

Useful Flags:
  -DskipTests         Skip test execution (still compiles tests)
  -Dmaven.test.skip   Skip test compilation and execution
  -q, --quiet         Quiet output
  -X, --debug         Debug output
  -P profile-name     Activate a Maven profile
  -pl module-name     Build specific module (multi-module)
  -am                 Also build dependencies of -pl modules
  -amd                Also build dependents of -pl modules
  -T 4                Use 4 threads (parallel build)
  -T 1C               Use 1 thread per CPU core
  -o, --offline       Offline mode (use local cache only)
  -U, --update-snapshots  Force update of SNAPSHOT dependencies
  -Dmaven.repo.local=/path  Use custom local repo (CI: use project-local cache)

5. MAVEN PLUGINS AND GOALS
================================================================================

Core Plugins (built-in):

  maven-compiler-plugin:
    - compile: Compile src/main/java
    - testCompile: Compile src/test/java
    
    Configuration:
    <plugin>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <release>21</release>     <!-- Java 21 -->
        <annotationProcessorPaths>
          <path>
            <groupId>org.mapstruct</groupId>
            <artifactId>mapstruct-processor</artifactId>
            <version>${mapstruct.version}</version>
          </path>
        </annotationProcessorPaths>
      </configuration>
    </plugin>

  maven-surefire-plugin:
    - test: Run unit tests
    
    Configuration:
    <plugin>
      <artifactId>maven-surefire-plugin</artifactId>
      <configuration>
        <parallel>classes</parallel>    <!-- Run test classes in parallel -->
        <threadCount>4</threadCount>
        <includes>
          <include>**/*Test.java</include>
          <include>**/*Tests.java</include>
        </includes>
        <excludes>
          <exclude>**/*IT.java</exclude>
        </excludes>
      </configuration>
    </plugin>

  maven-failsafe-plugin:
    - integration-test: Run integration tests (during integration-test phase)
    - verify: Verify results after integration-test phase
    
    Convention: Integration tests named *IT.java or *ITCase.java

  maven-jar-plugin:
    - jar: Package compiled code into JAR
    
    For executable JARs:
    <configuration>
      <archive>
        <manifest>
          <mainClass>com.example.Main</mainClass>
        </manifest>
      </archive>
    </configuration>

  maven-war-plugin:
    - war: Package as WAR for servlet containers

  maven-resources-plugin:
    - resources: Copy resources to target/classes
    - filtering: Replace ${property} placeholders in resource files

  maven-deploy-plugin:
    - deploy: Upload artifact to remote Maven repository

  maven-install-plugin:
    - install: Install artifact to local ~/.m2 repository

Popular Third-Party Plugins:
  spring-boot-maven-plugin: Create executable Spring Boot JAR ("fat JAR")
  jacoco-maven-plugin:       Code coverage (JaCoCo)
  sonar-maven-plugin:        SonarQube analysis
  spotbugs-maven-plugin:     Static analysis
  checkstyle-maven-plugin:   Code style
  versions-maven-plugin:     Manage dependency versions (versions:display-dependency-updates)

Running a Specific Goal:
  mvn plugin:goal              (e.g., mvn compiler:compile)
  mvn groupId:artifactId:goal  (e.g., mvn org.jacoco:jacoco-maven-plugin:report)

6. MAVEN DEPENDENCY MANAGEMENT
================================================================================

Transitive Dependencies:
  If A depends on B, and B depends on C, Maven resolves C automatically.
  
  Problem: Dependency conflicts (two versions of same library)
  Solution: Maven uses "nearest wins" for conflicts.

Viewing Dependency Tree:
  mvn dependency:tree
  mvn dependency:tree -Dincludes=com.fasterxml.jackson.core  # Filter
  
  Output:
  [INFO] com.example:order-service:jar:1.0.0
  [INFO] +- org.springframework.boot:spring-boot-starter-web:jar:3.2.0:compile
  [INFO] |  +- org.springframework.boot:spring-boot-starter:jar:3.2.0:compile
  [INFO] |  |  +- org.springframework.boot:spring-boot:jar:3.2.0:compile

Excluding Transitive Dependencies:
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
      <exclusion>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-tomcat</artifactId>
      </exclusion>
    </exclusions>
  </dependency>

Bill of Materials (BOM):
  A POM file that declares versions for a set of related dependencies.
  Importing a BOM ensures compatible versions.
  
  <dependencyManagement>
    <dependencies>
      <!-- Spring Boot BOM — manages all Spring dependency versions -->
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.2.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

Checking for Updates:
  mvn versions:display-dependency-updates
  mvn versions:display-plugin-updates

settings.xml (~/.m2/settings.xml):
  Configure mirrors, proxy, authentication, and profiles.
  
  <settings>
    <mirrors>
      <mirror>
        <id>nexus</id>
        <mirrorOf>*</mirrorOf>
        <url>https://nexus.example.com/repository/maven-public/</url>
      </mirror>
    </mirrors>
    
    <servers>
      <server>
        <id>nexus</id>
        <username>deploy-user</username>
        <password>${env.NEXUS_PASSWORD}</password>  <!-- From env var -->
      </server>
    </servers>
  </settings>

7. MAVEN MULTI-MODULE PROJECTS
================================================================================

A parent pom.xml managing multiple child modules (microservices, shared libs).

Structure:
  parent-project/
  ├── pom.xml                          # Parent POM
  ├── core/
  │   └── pom.xml                      # Core module
  ├── service-a/
  │   └── pom.xml                      # Service A module
  └── service-b/
      └── pom.xml                      # Service B module

Parent pom.xml:
  <project>
    <groupId>com.example</groupId>
    <artifactId>parent-project</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>pom</packaging>   <!-- MUST be pom for parent -->
    
    <!-- List all modules -->
    <modules>
      <module>core</module>
      <module>service-a</module>
      <module>service-b</module>
    </modules>
    
    <!-- Shared configuration inherited by all children -->
    <properties>
      <java.version>21</java.version>
      <spring-boot.version>3.2.0</spring-boot.version>
    </properties>
    
    <!-- Dependency versions managed centrally -->
    <dependencyManagement>
      <dependencies>
        <dependency>
          <groupId>com.example</groupId>
          <artifactId>core</artifactId>
          <version>${project.version}</version>
        </dependency>
      </dependencies>
    </dependencyManagement>
  </project>

Child pom.xml (service-a):
  <project>
    <parent>
      <groupId>com.example</groupId>
      <artifactId>parent-project</artifactId>
      <version>1.0.0-SNAPSHOT</version>
    </parent>
    
    <artifactId>service-a</artifactId>
    <!-- version inherited from parent -->
    
    <dependencies>
      <dependency>
        <groupId>com.example</groupId>
        <artifactId>core</artifactId>
        <!-- version managed in parent dependencyManagement -->
      </dependency>
    </dependencies>
  </project>

Building Modules:
  # Build everything
  mvn clean install
  
  # Build only specific module and its dependencies
  mvn clean install -pl service-a -am
  
  # Build all modules that depend on core (after changing core)
  mvn clean install -pl core -amd
  
  # Skip specific modules
  mvn clean install -pl '!service-b'

8. GRADLE OVERVIEW
================================================================================

Gradle is a modern build automation tool using a Groovy or Kotlin DSL.
It combines the best of Maven (conventions, dependency management) and Ant
(flexibility, scripting).

History:
  2007: Gradle created (Hans Dockter)
  2012: Android build system moved to Gradle
  2017: Kotlin DSL introduced
  2023: Gradle 8.x (incremental builds, build cache, configuration cache)

Core Philosophy:
  - Convention but with flexibility to override
  - Performance: Incremental builds, build cache
  - Extensibility: Write custom tasks in Groovy/Kotlin
  - IDE Integration: Excellent IntelliJ and Android Studio support

Groovy DSL vs Kotlin DSL:
  Groovy DSL (build.gradle):   More concise, dynamic
  Kotlin DSL (build.gradle.kts): Type-safe, better IDE support (autocomplete)
  
  Trend: Kotlin DSL is preferred for new projects.

File Structure (same as Maven for standard projects):
  my-project/
  ├── build.gradle.kts      # Build script
  ├── settings.gradle.kts   # Project name and multi-project config
  ├── gradlew               # Gradle wrapper script (Unix)
  ├── gradlew.bat           # Gradle wrapper script (Windows)
  ├── gradle/
  │   └── wrapper/
  │       ├── gradle-wrapper.jar
  │       └── gradle-wrapper.properties
  └── src/
      ├── main/
      │   └── java/
      └── test/
          └── java/

Gradle Wrapper (IMPORTANT):
  Always use gradlew (Gradle wrapper) instead of the globally installed gradle.
  The wrapper downloads the correct Gradle version for the project.
  
  Why: Ensures everyone (developers, CI) uses the exact same Gradle version.
  Commit: gradlew, gradlew.bat, gradle/wrapper/ to VCS.
  
  gradle/wrapper/gradle-wrapper.properties:
    distributionUrl=https\://services.gradle.org/distributions/gradle-8.4-bin.zip

9. GRADLE BUILD SCRIPTS
================================================================================

build.gradle.kts (Kotlin DSL):

  // Apply plugins
  plugins {
      id("java")
      id("org.springframework.boot") version "3.2.0"
      id("io.spring.dependency-management") version "1.1.4"
      id("jacoco")
      id("checkstyle")
      id("com.diffplug.spotless") version "6.22.0"
  }
  
  // Project identity
  group = "com.example"
  version = "1.0.0-SNAPSHOT"
  
  // Java version
  java {
      sourceCompatibility = JavaVersion.VERSION_21
      targetCompatibility = JavaVersion.VERSION_21
  }
  
  // Dependency repositories
  repositories {
      mavenCentral()
      maven { url = uri("https://nexus.example.com/repository/maven-public/") }
  }
  
  // Dependencies
  dependencies {
      implementation("org.springframework.boot:spring-boot-starter-web")
      implementation("org.springframework.boot:spring-boot-starter-data-jpa")
      
      runtimeOnly("org.postgresql:postgresql")
      
      testImplementation("org.springframework.boot:spring-boot-starter-test")
      testImplementation("org.testcontainers:postgresql:1.19.0")
      
      // Annotation processors
      annotationProcessor("org.mapstruct:mapstruct-processor:1.5.5.Final")
      compileOnly("org.projectlombok:lombok:1.18.30")
      annotationProcessor("org.projectlombok:lombok:1.18.30")
  }
  
  // Configure test task
  tasks.withType<Test> {
      useJUnitPlatform()         // Use JUnit 5 platform
      jvmArgs("-Xmx512m")
      testLogging {
          events("passed", "skipped", "failed")
      }
      finalizedBy(tasks.jacocoTestReport)   // Always generate coverage report after tests
  }
  
  // JaCoCo coverage configuration
  jacoco {
      toolVersion = "0.8.11"
  }
  
  tasks.jacocoTestReport {
      dependsOn(tasks.test)
      reports {
          xml.required.set(true)
          html.required.set(true)
      }
  }
  
  tasks.jacocoTestCoverageVerification {
      violationRules {
          rule {
              limit {
                  minimum = "0.80".toBigDecimal()
              }
          }
      }
  }
  
  // Custom task
  tasks.register("dockerBuild") {
      group = "docker"
      description = "Build Docker image"
      dependsOn("bootJar")
      doLast {
          exec {
              commandLine("docker", "build", "-t", "myapp:${project.version}", ".")
          }
      }
  }
  
  // Source sets (override defaults if needed)
  sourceSets {
      create("integrationTest") {
          compileClasspath += sourceSets.main.get().output + sourceSets.test.get().output
          runtimeClasspath += sourceSets.main.get().output + sourceSets.test.get().output
      }
  }
  
  // Integration test task
  val integrationTest by tasks.registering(Test::class) {
      description = "Runs integration tests."
      group = "verification"
      testClassesDirs = sourceSets["integrationTest"].output.classesDirs
      classpath = sourceSets["integrationTest"].runtimeClasspath
      useJUnitPlatform()
      shouldRunAfter(tasks.test)
  }
  
  tasks.check { dependsOn(integrationTest) }
  
  // Checkstyle
  checkstyle {
      toolVersion = "10.12.3"
      configFile = file("${rootProject.projectDir}/config/checkstyle/checkstyle.xml")
  }

settings.gradle.kts:
  
  // Required: sets the root project name
  rootProject.name = "my-application"
  
  // For multi-project: include subprojects
  include("core")
  include("service-a")
  include("service-b")

10. GRADLE TASKS AND LIFECYCLE
================================================================================

Key Gradle Tasks (Java/Spring Boot):

  Standard Java Tasks:
    compileJava         Compile src/main/java
    compileTestJava     Compile src/test/java
    processResources    Copy resources
    classes             All compilation + resources (depends on above)
    jar                 Package into JAR
    assemble            Build all archives (depends on jar)
    test                Run unit tests (uses JUnit or TestNG)
    check               Run all verification (tests, checkstyle, etc.)
    build               Run assemble + check (full build)
    clean               Delete build/ directory
    javadoc             Generate Javadoc

  Spring Boot Tasks (added by Spring Boot plugin):
    bootRun             Run Spring Boot application
    bootJar             Create executable JAR (fat JAR with embedded dependencies)
    bootBuildImage      Build OCI Docker image (Cloud Native Buildpacks)

  Dependency Tasks:

  }

11. GRADLE DEPENDENCY MANAGEMENT
================================================================================

Dependency Configurations (scopes):
  
  implementation:   Compile + runtime. NOT exposed to consumers (preferred).
  api:             Compile + runtime. EXPOSED to consumers (use in libraries only).
  compileOnly:     Compile only (like provided in Maven). Annotations, Lombok.
  runtimeOnly:     Runtime only (like runtime in Maven). JDBC drivers.
  testImplementation: Test compile + runtime.
  testCompileOnly:    Test compile only.
  testRuntimeOnly:    Test runtime only.

IMPORTANT: implementation vs api:
  
  If your module B uses api() for dependency X, modules that depend on B also
  see X in their compile classpath (X leaks through).
  
  If B uses implementation() for X, modules depending on B do NOT see X
  (X is hidden — better encapsulation).
  
  Rule: Always use implementation unless you're building a library and the
  dependency type is part of your public API.

Version Catalog (Gradle 7.4+):
  Centralize dependency versions in gradle/libs.versions.toml:
  
  [versions]
  spring-boot = "3.2.0"
  testcontainers = "1.19.0"
  
  [libraries]
  spring-boot-starter-web = { module = "org.springframework.boot:spring-boot-starter-web", version.ref = "spring-boot" }
  testcontainers-postgresql = { module = "org.testcontainers:postgresql", version.ref = "testcontainers" }
  
  [plugins]
  spring-boot = { id = "org.springframework.boot", version.ref = "spring-boot" }
  
  Usage in build.gradle.kts:
  
  plugins {
      alias(libs.plugins.spring.boot)
  }
  
  dependencies {
      implementation(libs.spring.boot.starter.web)
      testImplementation(libs.testcontainers.postgresql)
  }

Platform (BOM Import):
  // Equivalent of Maven BOM import
  dependencies {
      implementation(platform("org.springframework.boot:spring-boot-dependencies:3.2.0"))
      implementation("org.springframework.boot:spring-boot-starter-web")  // No version needed
  }

Viewing Dependencies:

  ./gradlew dependencies --configuration runtimeClasspath
  ./gradlew :service-a:dependencyInsight --dependency jackson-core --configuration compileClasspath

13. INCREMENTAL BUILDS AND BUILD CACHE
================================================================================

Why Gradle is Faster:

1. INCREMENTAL BUILDS (automatic):
   Gradle tracks task inputs/outputs. If nothing changed, task is UP-TO-DATE.
   
   Example: If only test files changed, 'compileJava' is UP-TO-DATE (skipped).
   Maven: Would recompile everything.
   
   $ ./gradlew build
   :compileJava UP-TO-DATE       ← Not recompiled (sources unchanged)
   :processResources UP-TO-DATE
   :classes UP-TO-DATE
   :compileTestJava               ← Compiled (test changed)
   :test                          ← Run (test changed)

2. BUILD CACHE (opt-in):
   Stores task outputs. If same inputs seen before, restore from cache.
   Shared across builds, branches, and developers.
   
   Local cache: ~/.gradle/caches/
   Remote cache: Configure a remote HTTP cache server or Gradle Enterprise.
   
   Enable:
   # gradle.properties
   org.gradle.caching=true
   
   Remote cache (Gradle Enterprise / Develocity):
   buildCache {
       remote(HttpBuildCache::class) {
           url = uri("https://gradle-cache.example.com/cache/")
           isPush = System.getenv("CI") == "true"  // Only push from CI
           credentials {
               username = System.getenv("GRADLE_CACHE_USER")
               password = System.getenv("GRADLE_CACHE_PASSWORD")
           }
       }
   }

3. CONFIGURATION CACHE (Gradle 8+):
   Caches the result of build configuration phase.
   Skips configuration for tasks whose inputs haven't changed.
   
   Enable:
   # gradle.properties
   org.gradle.configuration-cache=true

4. DAEMON:
   Long-running background process that caches JVM startup and project data.
   Dramatically speeds up repeated builds.
   
   Enabled by default.
   # gradle.properties
   org.gradle.daemon=true

Performance Flags:
  # gradle.properties (recommended for all projects)
  org.gradle.parallel=true           # Run independent tasks in parallel
  org.gradle.caching=true            # Enable build cache
  org.gradle.daemon=true             # Enable daemon (default)
  org.gradle.jvmargs=-Xmx2g -XX:MaxMetaspaceSize=512m  # Give Gradle more memory

When to Use Maven:

When to Use Gradle:

  - Performance-sensitive large builds
  - Complex custom build logic needed
  - Spring Boot new projects (official support)
  - Want build cache and incremental builds

15. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between mvn install and mvn deploy?
A: Both install and deploy do everything that 'package' does plus more.
   
   mvn install: Takes the built artifact and installs it to the LOCAL Maven
   repository (~/.m2/repository). Other projects on the same machine can now
   depend on it.
   
   mvn deploy: Takes the built artifact and deploys it to a REMOTE Maven
   repository (Nexus, Artifactory). Other teams/projects across the organization
   can now depend on it.
   
   In CI/CD: 'mvn deploy' is used to publish release artifacts. 'mvn install'
   is used in local development to make a module available to dependent modules.

Q2: What is the difference between Maven's 'dependencyManagement' and 'dependencies'?
A: 'dependencies': Actually adds the dependency to the project. It will be
   resolved and downloaded.
   
   'dependencyManagement': Only declares versions and scopes. It does NOT add
   the dependency to the project. When a child module or the same POM later
   declares the dependency without a version, it inherits from
   'dependencyManagement'.
   
   Use case: In a multi-module project, the parent POM lists all dependency
   versions in 'dependencyManagement'. Child modules declare the dependency
   without a version — they inherit the centrally managed version. This
   prevents version drift across modules.

Q3: What are Gradle incremental builds and build cache, and why do they matter?
A: Incremental builds: Gradle tracks the inputs and outputs of each task.
   If the inputs (source files, classpath, config) and outputs (compiled classes)
   haven't changed since the last build, Gradle marks the task as UP-TO-DATE
   and skips it. This is automatic and very effective.
   
   Build cache: If a task has the same inputs as a previous run (even on a
   different machine), Gradle can restore the output from cache instead of
   running the task. This can be local (~/.gradle/caches) or remote (shared
   server). CI builds can reuse outputs from previous CI builds or even from
   developer machines.
   
   Why it matters: Maven rebuilds everything on every run. A large Maven project
   might take 10 minutes; the same project with Gradle build cache might take
   2 minutes because only changed modules need building. At Google's scale,
   Bazel (similar principles) makes monorepo builds feasible.

Q4: Explain Maven's dependency scope 'provided' vs 'compile'.
A: 'compile' (default): The dependency is available during compilation AND
   included in the final artifact (JAR/WAR). Most application dependencies.
   
   'provided': The dependency is available during compilation but NOT included
   in the final artifact. It's "provided" by the runtime environment.
   
   Example: jakarta.servlet-api (Servlet API). When deploying a WAR to Tomcat,
   Tomcat already has the Servlet API on its classpath. If you included it in
   your WAR too, you'd have classloader conflicts. So you mark it 'provided'.
   
   Spring Boot note: Spring Boot creates fat JARs (all dependencies bundled),
   so 'provided' is less common. It's mainly for traditional WAR deployments.

Q5: How do you speed up Maven builds in CI?
A: Several strategies:
   
   1. PARALLEL BUILDS: mvn clean install -T 4 (4 threads) or -T 1C (1 per CPU)
      Works for independent modules in multi-module projects.
   
   2. DEPENDENCY CACHING: Cache ~/.m2/repository based on pom.xml hash.
      CI rebuilds shouldn't re-download all dependencies.
   
   3. SKIP WHEN APPROPRIATE:
      - Skip integration tests on feature branches: -P skip-integration-tests
      - Skip Javadoc on non-release builds: -Dmaven.javadoc.skip=true
   
   4. OFFLINE MODE: After dependencies are cached, -o flag prevents
      checking for updates.
   
   5. SKIP TESTS ON SPECIFIC JOBS: Separate test job from build job.
      Build: mvn package -DskipTests
      Test: mvn test (use cached classes)
   
   6. PROFILE-BASED CONFIG: Use Maven profiles to enable expensive checks
      only in CI: mvn verify -P ci

Q6: What is the 'api' vs 'implementation' configuration in Gradle?
A: Both make a dependency available at compile time and runtime, but they
   differ in VISIBILITY to downstream consumers:
   
   'api': The dependency leaks through to consumers' compile classpath.
   If project B uses api() for library X, and project C depends on B,
   then C can directly use X's classes at compile time.
   
   'implementation': The dependency is hidden from consumers.
   If B uses implementation() for X, C can't use X directly. C would need
   to add X as its own dependency.
   
   Best practice: Use 'implementation' by default (better encapsulation,
   faster compilation because consumers don't need to recompile when X changes).
   Use 'api' only when building a library and X's types are part of your
   public method signatures.
