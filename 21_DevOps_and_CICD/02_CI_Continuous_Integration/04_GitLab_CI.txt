1. WHAT IS GITLAB CI/CD?
================================================================================

GitLab CI/CD is the built-in continuous integration, delivery, and deployment
platform integrated into GitLab. Unlike Jenkins (separate tool) or GitHub Actions
(added to GitHub), GitLab CI was designed as a core feature of GitLab.

Key Points:
  - Configuration: .gitlab-ci.yml in root of repository
  - Integrated with GitLab: Merge Requests, Issues, Environments, Monitoring
  - Runners: GitLab-provided (SaaS) or self-hosted
  - YAML-based pipeline definition (clean, readable)
  - Auto DevOps: Auto-detect and configure CI/CD without writing .gitlab-ci.yml

GitLab CI/CD Tiers:
  Free:     Basic CI/CD, 400 CI minutes/month (SaaS)
  Premium:  Multi-project pipelines, Protected environments, 10,000 min/month
  Ultimate: Security dashboards, compliance, DAST/SAST, 50,000 min/month

Why GitLab CI is Popular:
  - Zero additional tooling: VCS + CI + CD + security all in one
  - Everything in one place: Code, pipelines, deployments, monitoring
  - Container registry included
  - Auto DevOps for quick start
  - Clean YAML syntax
  - Powerful include mechanism for DRY pipelines

2. CORE CONCEPTS
================================================================================

PIPELINE:
  A collection of stages and jobs triggered by an event (push, merge, schedule).
  
  Types:
  - Branch Pipeline: Runs on push to a branch
  - Merge Request Pipeline: Runs for open MRs
  - Merged Results Pipeline: Runs on the merged result (before actual merge)
  - Merge Train: Batches multiple MRs, tests them as if merged in sequence
  - Tag Pipeline: Runs when a tag is pushed
  - Scheduled Pipeline: Runs on a cron schedule
  - Multi-project Pipeline: Triggers pipelines in other projects

STAGE:
  A phase in the pipeline. Stages run sequentially.
  All jobs in a stage run in parallel (unless dependencies defined).
  
  Default stages (if not defined): .pre, build, test, deploy, .post

JOB:
  The basic unit of work. Runs on a runner.
  Defined with: stage, script, rules, environment, artifacts, etc.

RUNNER:
  A server/container that executes jobs.
  Types: GitLab-hosted, self-hosted
  Registration: Connect to GitLab with a token, specify executor type

EXECUTOR:
  How the runner executes jobs.
  Types: Shell, Docker, Docker+Machine, Kubernetes, VirtualBox, SSH

ARTIFACT:
  Files preserved from a job and available to subsequent jobs or for download.
  Unlike passing data in memory, artifacts are stored in GitLab.

CACHE:
  Files cached between pipeline runs (not between jobs in same pipeline).
  Use for: node_modules, .m2, pip cache.

ENVIRONMENT:
  Named deployment target.
  Tracked in GitLab's Environments page with deployment history.

3. .GITLAB-CI.YML STRUCTURE
================================================================================

Full annotated .gitlab-ci.yml:

  # Define pipeline-wide default settings
  default:
    image: ubuntu:22.04     # Default Docker image for all jobs
    before_script:           # Run before every job's script
      - echo "Starting job"
    after_script:            # Run after every job (even if failed)
      - echo "Job complete"
    retry:
      max: 2                 # Retry failed jobs up to 2 times
      when: runner_system_failure  # Only retry on system failures
    timeout: 30 minutes      # Job timeout
    tags:
      - docker               # Run on runners with 'docker' tag (default)
    interruptible: true       # Allow pipeline to be cancelled on new push
  
  # Define pipeline variables
  variables:
    DOCKER_DRIVER: overlay2
    REGISTRY: registry.gitlab.com
    IMAGE_NAME: $CI_REGISTRY_IMAGE
    MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  
  # Define stages (order matters — sequential)
  stages:
    - .pre        # Special: runs before all other stages
    - validate
    - build
    - test
    - security
    - package
    - deploy-staging
    - deploy-production
    - .post       # Special: runs after all other stages
  
  # ─── Jobs ────────────────────────────────────────────────────────
  
  lint:
    stage: validate
    image: node:20
    script:
      - npm ci --cache .npm
      - npm run lint
    cache:
      key: node-$CI_COMMIT_REF_SLUG
      paths:
        - .npm/
        - node_modules/
    rules:
      - changes:
          - "**/*.js"
          - "**/*.ts"
          - package.json
  
  compile:
    stage: build
    image: maven:3.9-eclipse-temurin-21
    script:
      - mvn compile $MAVEN_OPTS -q
    cache:
      key: maven-$CI_COMMIT_REF_SLUG
      paths:
        - .m2/repository/
  
  unit-test:
    stage: test
    image: maven:3.9-eclipse-temurin-21
    services:
      - postgres:15             # Linked Docker service
    variables:
      POSTGRES_DB: testdb
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
    script:
      - mvn test $MAVEN_OPTS
    artifacts:
      when: always               # Upload even on failure
      reports:
        junit: target/surefire-reports/*.xml  # Parse as test results
        coverage_report:
          coverage_format: jacoco
          path: target/site/jacoco/jacoco.xml
      paths:
        - target/surefire-reports/
      expire_in: 7 days
    coverage: '/Total.*?([0-9]{1,3})%/'  # Regex to extract coverage %
    cache:
      key: maven-$CI_COMMIT_REF_SLUG
      paths:
        - .m2/repository/
      policy: pull              # Only restore, don't update cache
  
  sast:
    stage: security
    # Include GitLab's built-in SAST template
    extends: .sast-analyzer
  
  include:
    - template: Security/SAST.gitlab-ci.yml
    - template: Security/Dependency-Scanning.gitlab-ci.yml
  
  docker-build:
    stage: package
    image: docker:24
    services:
      - docker:24-dind
    variables:
      DOCKER_TLS_CERTDIR: "/certs"
    before_script:
      - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    script:
      - |
        docker build \
          --cache-from $IMAGE_NAME:cache \
          --tag $IMAGE_NAME:$CI_COMMIT_SHA \
          --tag $IMAGE_NAME:latest \
          .
      - docker push $IMAGE_NAME:$CI_COMMIT_SHA
      - docker push $IMAGE_NAME:latest
    rules:
      - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  
  deploy-staging:
    stage: deploy-staging
    image: bitnami/kubectl:latest
    environment:
      name: staging
      url: https://staging.example.com
      on_stop: stop-staging    # Job to run when environment is stopped
    script:
      - kubectl set image deployment/myapp myapp=$IMAGE_NAME:$CI_COMMIT_SHA
        --namespace staging
    rules:
      - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  
  stop-staging:
    stage: deploy-staging
    script:
      - kubectl delete deployment myapp --namespace staging
    environment:
      name: staging
      action: stop              # This is the teardown job
    when: manual
    rules:
      - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  
  deploy-production:
    stage: deploy-production
    environment:
      name: production
      url: https://example.com
    script:
      - kubectl set image deployment/myapp myapp=$IMAGE_NAME:$CI_COMMIT_SHA
        --namespace production
    rules:
      - if: $CI_COMMIT_TAG =~ /^v[0-9]+\.[0-9]+\.[0-9]+$/
        when: manual            # Require manual trigger for production
    needs:
      - job: docker-build
        artifacts: false

4. PIPELINE STAGES AND JOBS
================================================================================

Stages Definition:
  
  stages:
    - build     # Jobs in 'build' run first, in parallel
    - test      # After ALL 'build' jobs pass, 'test' runs
    - deploy    # After ALL 'test' jobs pass, 'deploy' runs

Job Configuration Options:

  JOB NAME:
    - Must be unique
    - Cannot start with dot (that makes it a hidden template job)
    - Convention: use-kebab-case

  stage:
    Which stage this job belongs to.

  script:
    Commands to run. Array of strings.
    script:
      - npm install
      - npm test
      
  before_script / after_script:
    Run before/after script. Job-level overrides default.

  image:
    Docker image to use for this job.
    image:
      name: maven:3.9
      entrypoint: [""]    # Override entrypoint

  services:
    Docker containers linked to the job (databases, caches, etc.)
    services:
      - name: postgres:15
        alias: db     # Access as 'db' hostname

  variables:
    Job-specific environment variables.

  rules:
    Conditional job inclusion (preferred over only/except).
    rules:
      - if: $CI_COMMIT_BRANCH == "main"   # Include if on main
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
        when: manual                       # Include but require manual trigger
      - when: never                        # Otherwise skip

  when:
    on_success (default), on_failure, always, manual, delayed, never
    
    when: manual  # Job appears in UI but requires click to run
    when: delayed
    start_in: 5 minutes   # Wait 5 min then auto-run (canary promotion)

  allow_failure:
    allow_failure: true   # Job failure doesn't fail the pipeline

  needs:
    Run job out of stage order, once specific jobs complete (DAG pipelines).
    needs:
      - compile           # Only needs compile, not entire build stage
    
    This enables more parallelism than stage-based ordering alone.

  artifacts:
    artifacts:
      paths:
        - target/app.jar    # Files to upload
      reports:
        junit: reports/*.xml     # JUnit test results
        coverage_report:
          coverage_format: jacoco
          path: coverage.xml
        sast: gl-sast-report.json
        dependency_scanning: gl-dependency-scanning-report.json
      when: always          # always / on_success / on_failure
      expire_in: 1 week
      expose_as: "Test Results"   # Label in MR

  cache:
    Persistent between pipeline runs (not between jobs in same pipeline).
    cache:
      key: $CI_COMMIT_REF_SLUG-node    # Cache per branch
      paths:
        - node_modules/
        - .npm/
      policy: pull-push    # pull: restore only; push: store only; pull-push: both

  environment:
    environment:
      name: staging
      url: https://staging.example.com

  retry:
    retry:
      max: 2
      when:
        - runner_system_failure
        - stuck_or_timeout_failure

  timeout: 1 hour 30 minutes

  parallel:
    parallel: 5    # Run 5 identical jobs in parallel (for test sharding)
    
    # Or matrix:
    parallel:
      matrix:
        - PROVIDER: aws
          REGION: [ us-east-1, eu-west-1 ]
        - PROVIDER: gcp
          REGION: [ us-central1 ]

  trigger:
    Trigger a pipeline in another project (multi-project pipeline).
    trigger:
      project: group/downstream-project
      branch: main
      strategy: depend    # Wait for downstream pipeline

5. GITLAB RUNNERS
================================================================================

Runner Types:

  SHARED RUNNERS (GitLab-hosted):
    Available to all projects on GitLab.com
    Run on GitLab's infrastructure
    Linux: 400 free minutes/month (SaaS)
    
  GROUP RUNNERS:
    Available to all projects in a group
    Self-managed, registered to a group
  
  PROJECT RUNNERS (formerly specific runners):
    Available only to one project
    Self-managed, registered to a project

Runner Executors:

  SHELL:
    Runs commands directly on the runner host shell.
    Simplest but least isolated. Good for trusted code only.
    
  DOCKER:
    Runs each job in a fresh Docker container.
    Isolated and reproducible.
    Requires Docker installed on runner host.
    Most common for CI workloads.
    
  DOCKER+MACHINE:
    Auto-scales by spinning up VMs via Docker Machine.
    Good for variable workloads on cloud VMs.
    
  KUBERNETES:
    Runs each job as a Kubernetes Pod.
    Best for scalability and isolation.
    Native cloud integration.
    
  SSH:
    Connects to a remote host via SSH and runs commands.
    
  VIRTUALBOX/PARALLELS:
    For testing OS-level functionality.

Registering a Self-Hosted Runner:
  
  # On runner machine:
  # Install runner
  curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
  sudo apt-get install gitlab-runner
  
  # Register
  gitlab-runner register \
    --url https://gitlab.com/ \
    --registration-token $REGISTRATION_TOKEN \
    --executor docker \
    --docker-image alpine:latest \
    --description "My Docker Runner" \
    --tag-list "docker,linux,production" \
    --run-untagged false \       # Only run tagged jobs
    --locked false

Targeting Runners with Tags:
  
  # Runner registration: --tag-list "linux,docker,production"
  
  # Job targeting:
  deploy-prod:
    tags:
      - production    # Only runs on runners tagged 'production'
    script:
      - ./deploy.sh

Runner Configuration (config.toml):
  [[runners]]
    name = "docker-runner"
    url = "https://gitlab.com"
    executor = "docker"
    limit = 10    # Max concurrent jobs
    
    [runners.docker]
      image = "ubuntu:22.04"
      privileged = true       # Required for Docker-in-Docker
      volumes = ["/cache", "/var/run/docker.sock:/var/run/docker.sock"]
      pull_policy = "if-not-present"  # Cache images locally

Docker-in-Docker (DinD):
  Required when building Docker images inside a Docker runner.
  
  Method 1: DinD service (recommended)
    services:
      - name: docker:24-dind
        alias: docker
    variables:
      DOCKER_HOST: tcp://docker:2376
      DOCKER_TLS_CERTDIR: "/certs"
    
    # Runner must be privileged=true
  
  Method 2: Docker socket binding (simpler but less secure)
    volumes in config.toml: /var/run/docker.sock:/var/run/docker.sock
    # Job can use host's Docker daemon directly

6. VARIABLES AND SECRETS
================================================================================

Predefined CI/CD Variables (most useful):

  CI_COMMIT_SHA            Full commit SHA
  CI_COMMIT_SHORT_SHA      Short SHA (8 chars)
  CI_COMMIT_REF_NAME       Branch or tag name
  CI_COMMIT_TAG            Tag name (only on tag pipelines)
  CI_COMMIT_MESSAGE        Commit message
  CI_COMMIT_AUTHOR         Author name and email
  CI_DEFAULT_BRANCH        Default branch (usually main)
  CI_PIPELINE_ID           Unique pipeline ID
  CI_PIPELINE_SOURCE       How pipeline was triggered (push, merge_request_event, etc.)
  CI_JOB_ID                Unique job ID
  CI_JOB_NAME              Job name
  CI_JOB_STAGE             Stage name
  CI_RUNNER_DESCRIPTION    Runner description
  CI_REGISTRY              GitLab container registry URL
  CI_REGISTRY_IMAGE        Full image path for this project
  CI_REGISTRY_USER         Auto-generated registry user for this job
  CI_REGISTRY_PASSWORD     Auto-generated registry password for this job
  CI_PROJECT_NAME          Repository name
  CI_PROJECT_NAMESPACE     Group/username
  CI_PROJECT_PATH          Namespace/project-name
  CI_MERGE_REQUEST_ID      MR ID (only in MR pipelines)
  CI_MERGE_REQUEST_SOURCE_BRANCH_NAME  Source branch of MR

Defining Variables:
  
  # In .gitlab-ci.yml (project level)
  variables:
    GLOBAL_VAR: value
  
  job-name:
    variables:
      JOB_VAR: value    # Job-level (overrides global)
    script:
      - echo $GLOBAL_VAR
      - echo $JOB_VAR
  
  # In GitLab UI: Settings → CI/CD → Variables
  # Types:
  #   Variable (plain text)
  #   File (written to a temp file, env var = path to file)
  # Options:
  #   Protected: Only used in protected branches/tags
  #   Masked: Hidden in job logs
  #   Expand variable references: $VAR expansion

Secrets Management with External Vault:
  
  # Using HashiCorp Vault
  job:
    id_tokens:
      VAULT_ID_TOKEN:
        aud: https://vault.example.com
    secrets:
      DATABASE_PASSWORD:
        vault:
          path: myapp/staging
          field: db_password
          engine:
            name: kv-v2
    script:
      - echo $DATABASE_PASSWORD  # Fetched from Vault, masked in logs

Variable Masking:
  Sensitive values defined in GitLab UI with "Masked" option are replaced with
  [MASKED] in job logs.
  
  Requirement: Value must be Base64-safe (no special chars).
  
  Variables defined in .gitlab-ci.yml are NEVER masked.
  For secrets, always use GitLab UI Variables or Vault integration.

7. ENVIRONMENTS AND DEPLOYMENTS
================================================================================

Defining Environments:
  
  deploy-staging:
    environment:
      name: staging
      url: https://staging.example.com
    script:
      - helm upgrade --install app charts/app --set image.tag=$CI_COMMIT_SHA
  
  deploy-production:
    environment:
      name: production
      url: https://example.com
      deployment_tier: production   # Sets tier (production/staging/testing/development)
    script:
      - helm upgrade --install app charts/app --set image.tag=$CI_COMMIT_TAG
    when: manual

Dynamic Environments (Review Apps):
  Create per-MR environments for testing feature branches.
  
  deploy-review:
    stage: deploy
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      url: https://$CI_COMMIT_REF_SLUG.preview.example.com
      on_stop: stop-review
    script:
      - helm upgrade --install app-$CI_COMMIT_REF_SLUG charts/app
          --set host=$CI_COMMIT_REF_SLUG.preview.example.com
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  
  stop-review:
    stage: deploy
    environment:
      name: review/$CI_COMMIT_REF_SLUG
      action: stop
    script:
      - helm uninstall app-$CI_COMMIT_REF_SLUG
    when: manual
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"

Protected Environments:
  Settings → CI/CD → Environments → Protect environment
  
  - Restrict which roles/users can deploy
  - Require approvals before deployment
  - Restrict which branches can deploy

Deployment Approval:
  # Premium/Ultimate feature
  environment:
    name: production
    deployment_tier: production
  
  # In GitLab UI: Protected environment → Required approvals: 2
  # Pipeline pauses at this job until approvers click "Run"

8. ADVANCED PIPELINE FEATURES
================================================================================

INCLUDES (reusable pipeline components):
  
  # Include remote template
  include:
    - project: 'my-group/ci-templates'
      ref: v2.0
      file: '/templates/java-build.yml'
    
    # Include local file
    - local: '.gitlab/ci/test.yml'
    
    # Include GitLab official template
    - template: Security/SAST.gitlab-ci.yml
    - template: Security/Dependency-Scanning.gitlab-ci.yml
    - template: Docker.gitlab-ci.yml
    
    # Include remote URL
    - remote: https://raw.githubusercontent.com/org/repo/main/ci.yml

EXTENDS (job inheritance):
  
  # Define a base job template
  .build-base:
    stage: build
    cache:
      key: maven-$CI_COMMIT_REF_SLUG
      paths:
        - .m2/repository/
    before_script:
      - echo "Setting up Maven..."
  
  # Extend the base
  build-service-a:
    extends: .build-base
    script:
      - mvn package -pl service-a
  
  build-service-b:
    extends: .build-base
    script:
      - mvn package -pl service-b

RULES (conditional job inclusion):
  
  rules are evaluated in order; first matching rule wins.
  
  rules:
    # Include on MR push
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: on_success
    
    # Include on main branch push
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: on_success
    
    # Include on tag, require manual trigger
    - if: $CI_COMMIT_TAG
      when: manual
    
    # Include only if certain files changed
    - changes:
        - "backend/**"
        - "Dockerfile"
      when: on_success
    
    # Default: never (job skipped in all other cases)
    - when: never

NEEDS (DAG Pipelines):
  Run jobs as soon as their dependencies complete, ignoring stage ordering.
  
  stages:
    - build
    - test
    - package
    - deploy
  
  compile:
    stage: build
    script: mvn compile
  
  unit-test:
    stage: test
    needs: [compile]     # Run as soon as compile finishes
    script: mvn test
  
  integration-test:
    stage: test
    needs: [compile]     # Also runs as soon as compile finishes
    script: mvn verify
  
  build-image:
    stage: package
    needs: [unit-test, integration-test]   # Waits for both
    script: docker build .
  
  # This creates a true DAG, not stage-based ordering.

MULTI-PROJECT PIPELINES:
  Trigger pipelines in other projects.
  
  trigger-deploy:
    stage: deploy
    trigger:
      project: group/deploy-repo
      branch: main
      strategy: depend    # Wait for downstream pipeline result
    variables:
      IMAGE_TAG: $CI_COMMIT_SHA    # Pass variable to downstream

PARENT-CHILD PIPELINES:
  Split pipeline into multiple files, run child pipelines.
  
  # Parent .gitlab-ci.yml
  stages:
    - triggers
  
  backend-pipeline:
    stage: triggers
    trigger:
      include: backend/.gitlab-ci.yml
      strategy: depend
    rules:
      - changes:
          - "backend/**"
  
  frontend-pipeline:
    stage: triggers
    trigger:
      include: frontend/.gitlab-ci.yml
    rules:
      - changes:
          - "frontend/**"

MERGE REQUEST PIPELINES:
  Run pipeline against the merged result, not just the source branch.
  
  workflow:
    rules:
      - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  
  # Now jobs only run for MRs or main branch

MERGE TRAINS:
  (Premium+) Tests multiple MRs as if merged in sequence.
  When a merge train is running, each subsequent MR is tested on top of
  the previous MR's merged state. Increases merge throughput.

PIPELINE WORKFLOWS:
  Control when an entire pipeline runs.
  
  workflow:
    name: '$CI_COMMIT_TITLE'    # Pipeline display name
    rules:
      - if: $CI_COMMIT_MESSAGE =~ /\[skip ci\]/
        when: never
      - if: $CI_PIPELINE_SOURCE == "web"
        when: always
      - when: always

9. GITLAB CI SECURITY
================================================================================

Built-in Security Scanning (available via templates):

  include:
    - template: Security/SAST.gitlab-ci.yml              # Static code analysis
    - template: Security/DAST.gitlab-ci.yml              # Dynamic analysis
    - template: Security/Dependency-Scanning.gitlab-ci.yml
    - template: Security/Container-Scanning.gitlab-ci.yml
    - template: Security/Secret-Detection.gitlab-ci.yml
    - template: Security/License-Scanning.gitlab-ci.yml

  Results appear in:
  - Merge Request Security Widget (show new vulnerabilities)
  - Security Dashboard (project/group level)
  - Vulnerability Report

Protected Variables:
  Mark CI/CD variables as "Protected" in UI.
  Protected variables only available to protected branches/tags.
  Prevents untrusted feature branches from accessing production credentials.

Protected Branches + Runners:
  Mark runners as "Protected" → only protected branches can use them.
  Production deployment runners should be protected.

Audit Logs (Premium):
  Track all CI/CD configuration changes, pipeline triggers, deployments.

Code Owner Approval for Config Changes:
  CODEOWNERS file:
    .gitlab-ci.yml @devops-team
    .gitlab/ci/ @devops-team
  
  MRs changing CI files require DevOps team approval before merge.

10. GITLAB VS GITHUB ACTIONS VS JENKINS
================================================================================

              GitLab CI       GitHub Actions    Jenkins
─────────────────────────────────────────────────────────────────
VCS           GitLab only     GitHub only       Any (Git, SVN, etc.)
CI Location   Integrated      Integrated        Separate server
Config File   .gitlab-ci.yml  .github/workflows Jenkinsfile
Config Lang   YAML            YAML              Groovy/YAML
Cloud Runners SaaS + Self     GitHub-hosted     Only self-hosted
              (400 min free)  + Self
Auto DevOps   Yes             No                No
Security      Built-in SAST,  CodeQL, third-    Plugins required
              DAST, etc.      party actions
Environments  GitLab Envs     GitHub Envs       External tooling
Review Apps   Yes (built-in)  No (third-party)  No
Merge Trains  Yes (Premium)   Merge Queue       No
Container Reg Built-in        GHCR              No
Package Reg   Built-in        GitHub Packages   No
Cost          Free-Paid       Free-Paid         Open source
                                                (infra cost)
Complexity    Medium          Low-Medium        High

GitLab Advantages:
  - All-in-one: VCS + CI + security + registry + monitoring
  - Auto DevOps (zero config CI for standard projects)
  - Built-in SAST, DAST, dependency scanning (no external tools needed)
  - Merge trains for high-throughput merging
  - Review apps for per-MR environments

GitHub Actions Advantages:
  - Larger ecosystem of third-party actions
  - Better GitHub integration (obviously)
  - Simpler for individual developers and open-source

Jenkins Advantages:
  - On-premises, air-gapped environments
  - More plugins, extreme flexibility
  - Already existing enterprise deployments

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between 'rules' and 'only/except' in GitLab CI?
A: Both control when a job runs, but 'rules' is the modern approach (introduced
   in GitLab 12.3) and is recommended over the deprecated 'only/except'.
   
   'only/except' is simpler but limited:
     only:
       - main
     except:
       - tags
   
   'rules' is more powerful:
   - Supports complex conditions (if, changes, exists)
   - Can set 'when' per rule (on_success, manual, delayed, never)
   - Can add variables per rule
   - Rules are evaluated in order; first match wins
   
   Best practice: Use 'rules' for all new pipelines.

Q2: What is a GitLab Runner and what executor types exist?
A: A GitLab Runner is a software agent that executes CI/CD jobs.
   
   Types:
   - Shared runners (GitLab-managed, available to all projects)
   - Group runners (managed by group admins)
   - Project runners (registered to one project)
   
   Executor types determine how jobs run:
   - Shell: Runs directly on the host (least isolated)
   - Docker: Each job in a fresh container (most common)
   - Kubernetes: Each job in a Kubernetes Pod (most scalable)
   - Docker+Machine: Auto-scales VMs in the cloud
   
   For production, I prefer Kubernetes executor — it auto-scales,
   provides complete isolation per job, and integrates well with cloud.

Q3: How do you implement review apps in GitLab CI?
A: Review apps are per-MR deployments — each MR gets its own ephemeral
   environment for testing.
   
   Implementation:
   1. Job with environment name: review/$CI_COMMIT_REF_SLUG
   2. Dynamic URL using the branch slug
   3. on_stop pointing to a cleanup job
   4. rules triggering on merge_request_event
   
   The 'stop' job (with when: manual or tied to MR close) destroys the
   environment. GitLab tracks these environments and shows links in the MR.
   
   Review apps are great for design/product feedback on feature branches.

Q4: What is the difference between cache and artifacts in GitLab CI?
A: ARTIFACTS:
   - Passed between jobs in the same pipeline
   - Downloaded by dependent jobs automatically (with 'needs:')
   - Stored in GitLab and downloadable from UI
   - Use for: build outputs (JARs, Docker images info, test reports)
   - expire_in: when they're deleted
   
   CACHE:
   - Stored between pipeline runs (not between jobs in same run)
   - NOT guaranteed to be available (best effort)
   - Use for: dependencies (node_modules, .m2, pip cache)
   - Speed optimization — saves re-downloading
   - Keyed by branch, commit, or custom key
   
   Common mistake: Using artifacts to pass node_modules between jobs.
   Artifacts are committed to storage and transmitted; node_modules is huge.
   node_modules should always be cache.

Q5: How do you handle multi-project pipelines in GitLab?
A: GitLab supports triggering pipelines in downstream projects.
   
   Use cases:
   - Shared library updated → trigger all dependent service pipelines
   - Monorepo split into microservices — trigger individual deployments
   - API contract changes → trigger consumer tests
   
   Implementation:
     trigger-downstream:
       trigger:
         project: group/other-repo
         branch: main
         strategy: depend   # Wait for downstream pipeline result
       variables:
         UPSTREAM_COMMIT: $CI_COMMIT_SHA
   
   With strategy: depend, the upstream pipeline fails if the downstream
   pipeline fails. Without it, it's fire-and-forget.

Q6: What is Auto DevOps in GitLab?
A: Auto DevOps is GitLab's zero-configuration CI/CD. When enabled and no
   .gitlab-ci.yml exists (or the Auto DevOps template is included), GitLab
   auto-detects the application type and configures CI/CD automatically.
   
   It includes: Auto Build (Docker), Auto Test, Auto Code Quality,
   Auto SAST, Auto Dependency Scanning, Auto Deploy (to Kubernetes),
   Auto DAST, Auto Monitoring.
   
   Great for: Quick setup, standard applications, teams without DevOps expertise.
   Limitation: Less flexible than custom .gitlab-ci.yml for complex workflows.

File: .gitlab-ci.yml (project root)

Pipeline Structure:
  stages → jobs (in stages) → script → artifacts/cache

Key Predefined Variables:
  $CI_COMMIT_SHA, $CI_COMMIT_REF_NAME, $CI_COMMIT_TAG
  $CI_DEFAULT_BRANCH, $CI_PIPELINE_SOURCE
  $CI_REGISTRY, $CI_REGISTRY_IMAGE

  $CI_PROJECT_NAME, $CI_PROJECT_PATH

Job 'when' Values:
  on_success (default), on_failure, always, manual, delayed, never

Rules Conditions:
  if: $VARIABLE == "value"
  changes: [ "path/**" ]
  exists: [ "Dockerfile" ]

Rules Source Values:
  $CI_PIPELINE_SOURCE:
    push, web, schedule, api, trigger, merge_request_event,
    parent_pipeline, pipeline, external
