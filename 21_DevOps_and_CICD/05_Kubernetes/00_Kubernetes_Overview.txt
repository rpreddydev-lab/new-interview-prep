1. WHAT IS KUBERNETES AND WHY IT EXISTS
================================================================================

The Problem Kubernetes Solves:
  At scale, running containers manually becomes impossible:
  - Which host should this container run on? (scheduling)
  - What if a container crashes? (self-healing)
  - How to update 50 containers with zero downtime? (rolling updates)
  - How to scale from 3 to 30 containers based on traffic? (autoscaling)
  - How do containers find each other across hosts? (service discovery)
  - How to manage config and secrets across hundreds of containers? (configuration)
  
  Kubernetes is a container orchestration platform that solves ALL of these.

What Kubernetes Is:
  Open-source container orchestration system.
  Originally developed by Google (based on Borg, their internal system).
  Donated to CNCF (Cloud Native Computing Foundation) in 2014.
  
  Kubernetes: Greek for "helmsman" or "pilot." K8s (8 letters between K and s).
  
  It is the OPERATING SYSTEM for cloud-native applications.
  
  Core value proposition:
  "You declare what you WANT. Kubernetes figures out HOW to make it so."

What Kubernetes Does:
  
  SERVICE DISCOVERY AND LOAD BALANCING:
    Containers can find each other by DNS name.
    Load balances traffic across container replicas.
  
  STORAGE ORCHESTRATION:
    Automatically mount storage systems (local, NFS, cloud EBS/GCP PD).
  
  AUTOMATED ROLLOUTS AND ROLLBACKS:
    Describe desired state → K8s incrementally rolls out changes.
    Roll back to previous state on failure.
  
  SELF-HEALING:
    Restart failed containers. Replace unresponsive containers.
    Reschedule containers when nodes fail.
    Don't advertise unavailable pods to clients.
  
  SECRET AND CONFIGURATION MANAGEMENT:
    Store and manage sensitive info (passwords, tokens, SSH keys).
    Deploy without rebuilding container images.
  
  HORIZONTAL SCALING:
    Scale in/out based on CPU, memory, or custom metrics.
    Scale to zero with KEDA.
  
  BIN PACKING:
    Fit containers onto nodes efficiently based on resource requests.

Kubernetes is NOT:
  ✗ Not a PaaS (Platform as a Service) — doesn't provide CI/CD, logging, monitoring
  ✗ Not limited to one type of application
  ✗ Not prescriptive about the application framework
  ✗ Not just for microservices (monoliths run fine too)
  ✗ Not just Docker (supports containerd, CRI-O via CRI)

2. KUBERNETES CORE CONCEPTS
================================================================================

Desired State vs Actual State:
  
  Kubernetes is a CONTROL LOOP (reconciliation loop):
  
  1. User declares DESIRED STATE: "I want 3 replicas of nginx"
  2. Kubernetes stores desired state in etcd
  3. Controllers watch current state, compare to desired
  4. Controllers take action to reconcile: start/stop/move containers
  5. Watch again → repeat forever
  
  desired state → etcd → controller watches → reconcile → desired state met
  
  This is the foundation of Kubernetes' self-healing capability.

Declarative vs Imperative:
  
  IMPERATIVE: Tell Kubernetes WHAT TO DO
    kubectl run nginx --image=nginx
    kubectl scale deployment myapp --replicas=5
  
  DECLARATIVE: Tell Kubernetes WHAT YOU WANT
    kubectl apply -f deployment.yaml
    # Kubernetes figures out how to achieve the desired state
  
  Production: ALWAYS use declarative (YAML files in Git = GitOps)
  
  # deployment.yaml declares: "I want 3 nginx replicas"
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: nginx
  spec:
    replicas: 3
    selector:
      matchLabels:
        app: nginx
    template:
      metadata:
        labels:
          app: nginx
      spec:
        containers:
        - name: nginx
          image: nginx:1.25

Labels and Selectors:
  Labels: Key-value pairs attached to objects. Used for identification.
  Selectors: Query mechanism to find objects by labels.
  
  Labels example:
  metadata:
    labels:
      app: myapp
      version: v1.2.3
      environment: production
      tier: backend
  
  Selector example:
  selector:
    matchLabels:
      app: myapp
      tier: backend
  
  Labels are used by:
  - Services to route traffic to pods
  - Deployments to manage pods
  - Network Policies to select pods
  - Node selectors to schedule on specific nodes

Namespaces:
  Virtual clusters within a Kubernetes cluster.
  Provide isolation, scope, and resource quotas.
  
  Default namespaces:
  default        Where objects go if namespace not specified
  kube-system    Kubernetes system components
  kube-public    Publicly accessible data (cluster info)
  kube-node-lease  Node heartbeat objects
  
  Custom namespace example:
  kubectl create namespace production
  kubectl apply -f app.yaml -n production
  
  Namespace ≠ security boundary by default (Network Policies needed)

3. KUBERNETES OBJECTS — THE BIG PICTURE
================================================================================

Object Hierarchy:
  
  POD: Smallest deployable unit. One or more containers.
    ↓ (managed by)
  REPLICASET: Maintains N replicas of pods.
    ↓ (managed by)
  DEPLOYMENT: Manages ReplicaSets. Rolling updates. Version history.
  
  STATEFULSET: Like Deployment but for stateful apps (stable identity, storage)
  DAEMONSET: One pod per node (monitoring agents, log shippers)
  JOB: Run-to-completion task
  CRONJOB: Scheduled Job
  
  SERVICE: Stable network endpoint for pods (load balancer)
  INGRESS: HTTP/HTTPS routing (L7 load balancer, TLS termination)
  
  CONFIGMAP: Non-sensitive configuration data
  SECRET: Sensitive configuration data
  
  PERSISTENTVOLUME: Storage resource
  PERSISTENTVOLUMECLAIM: Request for storage
  STORAGECLASS: Dynamic storage provisioning
  
  NODE: Worker machine
  NAMESPACE: Virtual cluster

Object YAML Structure (universal):
  
  apiVersion: apps/v1        # API group/version
  kind: Deployment           # Object type
  metadata:
    name: my-deployment      # Object name (unique within namespace)
    namespace: production    # Namespace (default if omitted)
    labels:                  # Arbitrary key-value pairs
      app: myapp
    annotations:             # Non-identifying metadata
      description: "Main application"
  spec:                      # Desired state (varies by kind)
    ...
  status:                    # Current state (managed by Kubernetes, read-only)
    ...

API Versions:
  apps/v1        Deployments, ReplicaSets, StatefulSets, DaemonSets
  v1             Pods, Services, ConfigMaps, Secrets, PVs, PVCs, Namespaces
  batch/v1       Jobs, CronJobs
  networking.k8s.io/v1    Ingress, NetworkPolicy
  rbac.authorization.k8s.io/v1  Role, ClusterRole, RoleBinding, ClusterRoleBinding
  autoscaling/v2          HPA (HorizontalPodAutoscaler)
  storage.k8s.io/v1       StorageClass

4. CONTROL PLANE VS DATA PLANE
================================================================================

The Two Sides of Kubernetes:
  
  CONTROL PLANE (Master/Management):
  - Makes decisions about the cluster
  - Runs on "control plane nodes" (formerly "master nodes")
  - Stores cluster state
  - Runs controllers
  - Serves the Kubernetes API
  
  DATA PLANE (Worker):
  - Runs actual application workloads
  - Reports back to control plane
  - Runs kubelet, kube-proxy, container runtime

Control Plane Components:
  
  API SERVER (kube-apiserver):
    Central hub of Kubernetes.
    All operations (kubectl, controllers, etc.) go through API server.
    Validates requests, persists to etcd.
    Exposes REST API.
    Horizontally scalable.
  
  ETCD:
    Distributed key-value store.
    Single source of truth for ALL cluster state.
    Strongly consistent. Uses Raft consensus.
    Critical — losing etcd = losing cluster state.
    Must be backed up regularly.
    Recommended: Odd number of nodes (3, 5) for quorum.
  
  SCHEDULER (kube-scheduler):
    Watches for unscheduled pods.
    Finds the best node based on:
    - Resource requests/limits
    - Taints and tolerations
    - Affinity/anti-affinity rules
    - Node selectors
    Assigns pod to a node (sets pod.spec.nodeName).
  
  CONTROLLER MANAGER (kube-controller-manager):
    Runs all built-in controllers in a single process:
    - Deployment Controller
    - ReplicaSet Controller
    - Node Controller (handles node failures)
    - Job Controller
    - ServiceAccount Controller
    - Namespace Controller
    Each controller runs a reconciliation loop.
  
  CLOUD CONTROLLER MANAGER (cloud-controller-manager):
    Cloud-provider-specific logic:
    - Route Controller (cloud routing tables)
    - Service Controller (cloud load balancers)
    - Node Controller (cloud instance management)
    Separate from kube-controller-manager for modularity.

Data Plane Components (per Node):
  
  KUBELET:
    Agent running on every node.
    Receives PodSpecs, ensures containers are running and healthy.
    Reports node and pod status to API server.
    Talks to container runtime via CRI (Container Runtime Interface).
    Does NOT manage containers directly started outside Kubernetes.
  
  KUBE-PROXY:
    Network proxy on every node.
    Implements the Service abstraction.
    Maintains iptables/ipvs rules for Service IP→Pod IP routing.
    Handles UDP, TCP, SCTP forwarding.
    NOT involved in actual data packet forwarding in modern CNI setups.
  
  CONTAINER RUNTIME:
    Runs containers.
    Must implement CRI (Container Runtime Interface).
    Options: containerd (default in most distros), CRI-O, Docker (via cri-dockerd)
    K8s removed Docker as direct runtime in 1.24 (uses containerd/CRI-O now)

  │  ┌──────────┐  ┌────────┐  ┌──────────────┐  │

5. THE KUBERNETES API
================================================================================

Everything Is an API Resource:
  All Kubernetes objects are accessed through the REST API.
  kubectl is just an HTTP client for the Kubernetes API.
  
  # List all API resources:
  kubectl api-resources
  
  # List API versions:
  kubectl api-versions

CRUD Operations:
  HTTP Method    kubectl         Operation
  ──────────────────────────────────────────
  POST           kubectl apply   Create
  GET            kubectl get     Read
  PUT/PATCH      kubectl apply   Update
  DELETE         kubectl delete  Delete
  WATCH          kubectl get -w  Watch (long-poll)

Custom Resources (CRDs):
  Kubernetes API can be extended with Custom Resource Definitions.
  Operators: Custom controllers that manage CRDs.
  
  Examples:
  - cert-manager: Certificate CRD → auto-provisions TLS certs
  - Prometheus Operator: ServiceMonitor CRD → auto-configures scraping
  - Argo CD: Application CRD → GitOps deployment
  - Crossplane: Cloud resource CRDs → provision cloud infra via K8s API
  
  kubectl get crds                           # List all CRDs
  kubectl get prometheusrules                # Example CRD resource

6. KUBECTL — ESSENTIAL COMMANDS
================================================================================

Cluster Information:
  kubectl version                            # Client and server versions
  kubectl cluster-info                       # Control plane URLs
  kubectl get nodes                          # List nodes
  kubectl get nodes -o wide                  # Node details (IPs, OS, runtime)
  kubectl describe node <node-name>          # Detailed node info
  kubectl config get-contexts               # List clusters/contexts
  kubectl config use-context <context>      # Switch cluster

Get Resources:
  kubectl get pods                           # Pods in current namespace
  kubectl get pods -n kube-system           # Pods in kube-system
  kubectl get pods -A                        # All namespaces
  kubectl get pods -o wide                   # More details (node, IP)
  kubectl get pods -o yaml                   # Full YAML output
  kubectl get pods -o json                   # JSON output
  kubectl get pods -w                        # Watch (live updates)
  kubectl get pods -l app=nginx             # Filter by label
  kubectl get all                            # All common resources
  kubectl get all -n my-namespace           # All in specific namespace

Creating and Applying:
  kubectl apply -f deployment.yaml          # Apply (create or update)
  kubectl apply -f ./                       # Apply all YAMLs in directory
  kubectl apply -f https://...             # Apply from URL
  kubectl create -f resource.yaml          # Create only (fails if exists)
  kubectl create deployment nginx --image=nginx  # Imperative create

Describe (detailed info):
  kubectl describe pod my-pod               # Full pod details + events
  kubectl describe deployment my-deploy    # Deployment details
  kubectl describe service my-service      # Service details
  kubectl describe node my-node            # Node details

Logs:
  kubectl logs my-pod                       # Container logs
  kubectl logs my-pod -c container-name    # Specific container in multi-container pod
  kubectl logs my-pod -f                   # Follow logs
  kubectl logs my-pod --tail=100           # Last 100 lines
  kubectl logs my-pod --since=1h           # Last hour
  kubectl logs my-pod --previous           # Previous (crashed) container logs

Exec and Port-Forward:
  kubectl exec -it my-pod -- bash          # Interactive shell
  kubectl exec my-pod -- ls /app           # Run command
  kubectl exec -it my-pod -c sidecar -- sh # Exec into specific container
  
  kubectl port-forward pod/my-pod 8080:80  # Forward local port to pod
  kubectl port-forward svc/my-svc 8080:80  # Forward local port to service
  kubectl port-forward deployment/my-dep 8080:80

Copy Files:
  kubectl cp my-pod:/app/logs /local/logs   # Copy from pod
  kubectl cp /local/file my-pod:/app/file   # Copy to pod

Editing and Patching:
  kubectl edit deployment my-deploy        # Open editor, changes applied on save
  kubectl scale deployment my-deploy --replicas=5
  kubectl set image deployment/my-deploy container=image:v2  # Update image
  kubectl rollout status deployment/my-deploy
  kubectl rollout history deployment/my-deploy
  kubectl rollout undo deployment/my-deploy  # Roll back

Delete:
  kubectl delete pod my-pod                 # Delete pod
  kubectl delete -f deployment.yaml        # Delete from YAML
  kubectl delete deployment my-deploy      # Delete deployment
  kubectl delete namespace my-ns           # Delete namespace (and everything in it!)
  kubectl delete pods --all                # Delete all pods in namespace
  kubectl delete pods -l app=nginx         # Delete pods by label

Namespace Shortcuts:
  kubectl config set-context --current --namespace=production  # Set default namespace
  # Or use kubens (third-party tool):
  kubens production

Useful Flags:
  -n namespace        Target namespace
  -A                  All namespaces
  -o yaml/json/wide   Output format
  -f file.yaml        Specify file
  -l label=value      Label selector
  --dry-run=client    Show what would happen (no changes)
  -w                  Watch for changes

8. KUBERNETES DISTRIBUTIONS AND MANAGED SERVICES
================================================================================

Managed Kubernetes Services:
  
  AWS EKS (Elastic Kubernetes Service):
  - Control plane managed by AWS
  - Integration with IAM, VPC, EBS, ALB
  - Fargate: serverless pods (no EC2 management)
  
  GKE (Google Kubernetes Engine):
  - The original managed K8s (Google created K8s)
  - Autopilot mode: fully managed nodes
  - Strong GKE-specific optimizations
  
  AKS (Azure Kubernetes Service):
  - Control plane free
  - Integration with AAD, ACR, Azure Monitor
  
  DigitalOcean DOKS, Linode LKE, Civo: Simpler alternatives

Self-Managed Distributions:
  
  kubeadm: Official tool for bootstrapping K8s clusters
  
  k3s (Rancher): Lightweight K8s for edge/IoT/dev
    Single binary, ~50MB RAM. Includes containerd, Flannel, CoreDNS, Traefik.
  
  k3d: k3s in Docker containers (great for local dev)
  
  Kind (Kubernetes in Docker): Multi-node K8s in Docker containers (CI testing)
  
  minikube: Single-node local K8s (common for learning)
  
  OpenShift (Red Hat): Enterprise K8s with built-in CI/CD, image registry, OAuth

9. WHEN TO USE KUBERNETES (AND WHEN NOT TO)
================================================================================

Use Kubernetes When:
  ✓ Multiple services with complex interactions
  ✓ Auto-scaling needed (traffic varies significantly)
  ✓ High availability requirements (multi-zone)
  ✓ Team has the expertise to operate it
  ✓ Many deployments per day (good rolling update support)
  ✓ Resource utilization matters (bin packing)
  ✓ Compliance requires strong security controls

Don't Use Kubernetes When:
  ✗ Small team (<5 engineers) without DevOps expertise
  ✗ Simple applications with single service
  ✗ Startup in early stages (over-engineering)
  ✗ Applications that don't need scaling or HA
  ✗ When Docker Compose + VMs meet all requirements
  ✗ One-off scripts and batch jobs
  
  Alternatives:
  - Docker Compose (single-host, simple apps)
  - ECS (AWS, simpler K8s alternative)
  - Cloud Run / Fargate (serverless containers)
  - Heroku / Railway / Render (simple PaaS)
  - Virtual machines (non-containerized apps)

The Kubernetes Complexity Tax:
  K8s is complex. It requires understanding of:
  - Networking (CNI, Services, Ingress, Network Policies)
  - Storage (PV, PVC, StorageClasses, CSI drivers)
  - Security (RBAC, Pod Security, Network Policies, Secrets)
  - Observability (metrics, logs, tracing)
  - Upgrades and maintenance
  
  Ask: "Does the value justify the complexity for our use case?"

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Kubernetes and what problem does it solve?
A: Kubernetes is an open-source container orchestration platform.
   It solves the operational challenges that arise when running containers
   at scale.
   
   With just Docker, you face:
   - Manual scheduling: Deciding which server to run each container on
   - No self-healing: If a container crashes, it stays down
   - No scaling: Manually scaling containers for traffic spikes
   - Service discovery: Containers can't easily find each other
   - Rolling updates: Manual process to update without downtime
   
   Kubernetes addresses all of these:
   - Scheduler places containers optimally based on resources
   - Controllers restart failed containers automatically
   - HPA/VPA scale pods based on metrics
   - Services provide stable DNS names and load balancing
   - Deployments do rolling updates with health checks and auto-rollback
   
   The key concept: You declare DESIRED STATE. Kubernetes continuously
   reconciles actual state to match desired state.

Q2: Explain the Kubernetes control plane components.
A: The control plane consists of components that manage the cluster:
   
   API SERVER: The front door to Kubernetes. All operations (kubectl, CI/CD,
   controllers) communicate through the API server. It validates requests
   and persists state to etcd.
   
   ETCD: The brain. A distributed key-value store holding ALL cluster state:
   what pods should run, what nodes exist, what secrets are stored, etc.
   If etcd is lost, the cluster state is lost. Must be backed up.
   
   SCHEDULER: Watches for pods with no assigned node, then finds the best
   node based on resource availability, affinity rules, taints/tolerations.
   Only makes the scheduling decision — kubelet actually starts the container.
   
   CONTROLLER MANAGER: Runs reconciliation loops for built-in resources.
   The Deployment Controller ensures the right number of ReplicaSets exist.
   The Node Controller marks nodes as unavailable after health check failures.
   
   Each component can run independently for HA. In managed K8s (EKS, GKE, AKS),
   these are managed by the cloud provider — you just see worker nodes.

Q3: What is the difference between a Pod, Deployment, and Service?
A: These serve different purposes and operate at different levels:
   
   POD: The smallest deployable unit. Wraps one or more containers that
   share network namespace and storage. Pods are ephemeral — they die and
   are not resurrected. You usually don't create pods directly.
   
   DEPLOYMENT: Manages the lifecycle of pods. Declares "I want N replicas
   of this pod." Creates ReplicaSets. Handles rolling updates, rollbacks,
   scaling. The ReplicaSet ensures the desired number of identical pods run.
   You create Deployments, not pods directly.
   
   SERVICE: Provides a stable network identity for a set of pods. Pods come
   and go with changing IPs, but the Service has a stable ClusterIP and DNS
   name. Routes traffic to healthy pods using label selectors. Types:
   ClusterIP (internal), NodePort (external via node IP), LoadBalancer
   (cloud load balancer).
   
   Together: Deployment manages pods → Service routes traffic to those pods.
   The Service finds the pods via the same labels the Deployment uses.

Q4: What is kubectl apply vs kubectl create?
A: Both create resources, but they work differently:
   
   kubectl create:
   - IMPERATIVE: Creates a new resource
   - Fails if the resource already exists
   - Doesn't update existing resources
   - Not suitable for GitOps workflows
   
   kubectl apply:
   - DECLARATIVE: Creates or updates a resource
   - Merges changes with existing resource if it exists
   - Records the applied configuration as an annotation
   - Idempotent: running the same apply multiple times is safe
   - THE CORRECT APPROACH for production/GitOps
   
   kubectl apply uses three-way merge:
   1. Previous applied configuration (stored as annotation)
   2. Current live configuration (from cluster)
   3. New configuration (from YAML file)
   
   Merges these to determine what changed and applies only the delta.
   This is why you can remove a field from YAML and kubectl apply will
   remove it from the live object (unlike kubectl edit or patch).

Q5: How does Kubernetes self-healing work?
A: Kubernetes self-healing operates at multiple levels:
   
   1. CONTAINER RESTARTS (liveness probes):
      If a liveness probe fails, the kubelet restarts the container.
      Back-off delay: 10s, 20s, 40s, 80s, 160s, 300s (then stays at 5min).
      This handles applications that deadlock or become unresponsive.
   
   2. POD REPLACEMENT (ReplicaSet controller):
      If a pod is deleted or fails, the ReplicaSet controller sees
      actual replicas < desired replicas and creates a new pod.
      Scheduler assigns it to an available node.
   
   3. NODE FAILURE (Node controller):
      Node controller marks node as "NotReady" after ~40s of no heartbeat.
      After ~5 min, pods on the node are marked for eviction.
      ReplicaSet creates replacement pods on healthy nodes.
   
   4. READINESS PROBES (traffic routing):
      Pods failing readiness probes are removed from Service endpoints.
      Traffic stops going to the pod until it recovers.
      Prevents sending traffic to starting or degraded pods.
   
   5. DEPLOYMENT ROLLOUTS:
      If a rolling update produces pods that fail health checks,
      the rollout pauses and can auto-rollback to the previous version.
   
   This multi-level self-healing makes K8s far more resilient than
   manually managed container infrastructure.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

CONTROL PLANE COMPONENTS:
  kube-apiserver     Central API hub, validates, persists to etcd
  etcd               Cluster state storage (back this up!)
  kube-scheduler     Assigns pods to nodes
  kube-controller-manager  Reconciliation loops (Deployment, Node, etc.)
  cloud-controller-manager  Cloud-provider integration

NODE (DATA PLANE) COMPONENTS:
  kubelet            Agent, manages pod lifecycle, talks CRI
  kube-proxy         Service network rules (iptables/ipvs)
  container runtime  containerd, CRI-O (not Docker directly in K8s 1.24+)

KEY OBJECTS:
  Pod                Smallest unit. 1+ containers, shared net/storage.
  Deployment         Manages ReplicaSets, rolling updates, rollback
  Service            Stable network endpoint (ClusterIP/NodePort/LoadBalancer)
  Ingress            HTTP/HTTPS routing, TLS termination
  ConfigMap          Non-sensitive config
  Secret             Sensitive config (base64 encoded in etcd)
