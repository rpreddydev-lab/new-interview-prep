1. WHAT IS HELM AND WHY USE IT
================================================================================

What is Helm?
  Helm is the package manager for Kubernetes.
  Like apt for Debian, npm for Node.js, pip for Python — but for K8s.
  
  Helm packages Kubernetes resources into reusable "charts."
  A chart is a bundle of YAML templates + default values.

Why Use Helm?
  
  WITHOUT HELM (raw kubectl):
  ✗ Duplicate YAML across environments (dev/staging/prod)
  ✗ Manual changes to 10+ YAML files per application
  ✗ No standardized way to package applications
  ✗ No version history or rollback of entire deployments
  ✗ No reuse of community-tested configurations
  
  WITH HELM:
  ✓ Install complex apps with one command: helm install my-postgres bitnami/postgresql
  ✓ Customize with values: --set replica.replicaCount=3
  ✓ Roll back entire release: helm rollback my-app 2
  ✓ Track what's deployed: helm list
  ✓ Reuse community charts (2000+ on Artifact Hub)
  ✓ Templating: one chart, many environments

Helm Version History:
  Helm 2: Client/server (Tiller in cluster). DEPRECATED — security issues.
  Helm 3: Client-only. No Tiller. Released Nov 2019. Current version.
  Always use Helm 3.

2. HELM CORE CONCEPTS
================================================================================

Chart:
  A package containing all Kubernetes resource templates and metadata.
  Like an npm package or Docker image.
  Can define dependencies on other charts.

Release:
  An instance of a chart running in a cluster.
  One chart can be installed multiple times = multiple releases.
  
  helm install redis-dev bitnami/redis    # Release: redis-dev
  helm install redis-prod bitnami/redis  # Release: redis-prod
  
  Releases are namespace-scoped.

Repository (Repo):
  HTTP server hosting chart packages (.tgz archives) and an index.yaml.
  Like Docker Hub but for Helm charts.
  
  Popular repos:
  - Artifact Hub: https://artifacthub.io (central discovery)
  - Bitnami: https://charts.bitnami.com/bitnami
  - Prometheus Community: https://prometheus-community.github.io/helm-charts
  - Ingress-nginx: https://kubernetes.github.io/ingress-nginx

Revision:
  Each install/upgrade of a release gets a revision number.
  Helm stores revision history as Secrets in the namespace.
  Supports rollback to any previous revision.

Values:
  Configuration parameters for a chart.
  Provided in values.yaml (defaults) or overridden by user.
  Templates reference values with: {{ .Values.key }}

3. CHART STRUCTURE
================================================================================

Chart Directory Layout:
  
  my-app/
  ├── Chart.yaml           # Chart metadata (required)
  ├── values.yaml          # Default values (required)
  ├── values.schema.json   # JSON schema for values validation (optional)
  ├── charts/              # Dependency charts (subcharts)
  │   └── redis-7.0.0.tgz
  ├── templates/           # Kubernetes YAML templates
  │   ├── _helpers.tpl     # Named templates (partials)
  │   ├── deployment.yaml
  │   ├── service.yaml
  │   ├── ingress.yaml
  │   ├── configmap.yaml
  │   ├── serviceaccount.yaml
  │   ├── hpa.yaml
  │   └── NOTES.txt        # Post-install notes (printed after helm install)
  ├── .helmignore          # Files to exclude from chart package
  └── README.md

Chart.yaml (required):
  
  apiVersion: v2          # Always v2 for Helm 3
  name: my-app            # Chart name
  description: My application Helm chart
  type: application       # application | library
  version: 1.2.3          # Chart version (SemVer)
  appVersion: "2.0.1"     # Application version (informational)
  
  # Dependencies (subcharts):
  dependencies:
  - name: postgresql
    version: "12.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled    # Values key to enable/disable
  - name: redis
    version: "17.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled
  
  keywords:
  - webserver
  - api
  maintainers:
  - name: Jane Doe
    email: jane@example.com
  home: https://github.com/example/my-app
  sources:
  - https://github.com/example/my-app

values.yaml (example):
  
  # Deployment configuration
  replicaCount: 2
  
  image:
    repository: my-company/my-app
    tag: "1.0.0"
    pullPolicy: IfNotPresent
  
  imagePullSecrets: []
  
  service:
    type: ClusterIP
    port: 80
    targetPort: 8080
  
  ingress:
    enabled: false
    className: nginx
    host: example.com
    tls: []
  
  resources:
    requests:
      cpu: "100m"
      memory: "128Mi"
    limits:
      cpu: "500m"
      memory: "512Mi"
  
  autoscaling:
    enabled: false
    minReplicas: 2
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70
  
  nodeSelector: {}
  tolerations: []
  affinity: {}
  
  env: []
  envFrom: []
  
  postgresql:
    enabled: true
    auth:
      database: mydb
      username: myuser

4. HELM TEMPLATES AND TEMPLATING ENGINE
================================================================================

Template Syntax:
  Helm uses Go's text/template engine with Sprig functions.
  Delimiters: {{ and }}
  Comments: {{/* comment */}}
  Whitespace control: {{- and -}}  (trim whitespace)
  
  Dash trims the newline/whitespace OUTSIDE the delimiter:
  {{- /* trims whitespace before this action */}}
  {{/* action */ -}}  trims whitespace after this action

Built-in Objects:
  .Values      Values from values.yaml and overrides
  .Release     Release information
    .Release.Name      Release name
    .Release.Namespace Release namespace
    .Release.Revision  Revision number
    .Release.IsInstall True on first install
    .Release.IsUpgrade True on upgrade
  .Chart       Chart.yaml content
    .Chart.Name
    .Chart.Version
    .Chart.AppVersion
  .Files       Access non-template files in chart
  .Capabilities K8s cluster info
    .Capabilities.KubeVersion.Major
    .Capabilities.APIVersions.Has "apps/v1"

Template Example — deployment.yaml:
  
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: {{ include "my-app.fullname" . }}
    namespace: {{ .Release.Namespace }}
    labels:
      {{- include "my-app.labels" . | nindent 4 }}
  spec:
    {{- if not .Values.autoscaling.enabled }}
    replicas: {{ .Values.replicaCount }}
    {{- end }}
    selector:
      matchLabels:
        {{- include "my-app.selectorLabels" . | nindent 6 }}
    template:
      metadata:
        labels:
          {{- include "my-app.selectorLabels" . | nindent 8 }}
        annotations:
          checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
      spec:
        {{- with .Values.imagePullSecrets }}
        imagePullSecrets:
          {{- toYaml . | nindent 8 }}
        {{- end }}
        containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
          - name: http
            containerPort: {{ .Values.service.targetPort }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          {{- if .Values.env }}
          env:
            {{- toYaml .Values.env | nindent 12 }}
          {{- end }}
        {{- with .Values.nodeSelector }}
        nodeSelector:
          {{- toYaml . | nindent 8 }}
        {{- end }}
        {{- with .Values.tolerations }}
        tolerations:
          {{- toYaml . | nindent 8 }}
        {{- end }}

_helpers.tpl — Named Templates (partials):
  
  {{/*
  Expand the name of the chart.
  */}}
  {{- define "my-app.name" -}}
  {{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
  {{- end }}
  
  {{/*
  Create a default fully qualified app name.
  */}}
  {{- define "my-app.fullname" -}}
  {{- if .Values.fullnameOverride }}
  {{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
  {{- else }}
  {{- $name := default .Chart.Name .Values.nameOverride }}
  {{- if contains $name .Release.Name }}
  {{- .Release.Name | trunc 63 | trimSuffix "-" }}
  {{- else }}
  {{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }}
  {{- end }}
  {{- end }}
  {{- end }}
  
  {{/*
  Common labels
  */}}
  {{- define "my-app.labels" -}}
  helm.sh/chart: {{ include "my-app.chart" . }}
  {{ include "my-app.selectorLabels" . }}
  {{- if .Chart.AppVersion }}
  app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
  {{- end }}
  app.kubernetes.io/managed-by: {{ .Release.Service }}
  {{- end }}
  
  {{/*
  Selector labels
  */}}
  {{- define "my-app.selectorLabels" -}}
  app.kubernetes.io/name: {{ include "my-app.name" . }}
  app.kubernetes.io/instance: {{ .Release.Name }}
  {{- end }}

Key Template Functions:
  FUNCTION              DESCRIPTION
  ──────────────────────────────────────────────────────────────
  toYaml                Convert Go value to YAML string
  nindent N             Add N spaces indent to each line + newline
  indent N              Add N spaces indent to each line
  default "val"         Provide default if value is empty
  quote                 Wrap in double quotes
  trunc N               Truncate to N characters
  trimSuffix "-"        Remove trailing dash
  printf "%s-%s" a b    String formatting
  include "name" .      Render a named template
  required "msg" .val   Fail if value is empty
  sha256sum             SHA256 hash (for config change detection)
  b64enc / b64dec       Base64 encode/decode
  upper / lower / title Case conversion
  contains "sub" str    String contains
  hasKey .obj "key"     Check if map has key

Conditionals and Loops:
  
  # If/else:
  {{- if .Values.ingress.enabled }}
  # ingress YAML here
  {{- else }}
  # alternative or nothing
  {{- end }}
  
  # if with AND/OR:
  {{- if and .Values.ingress.enabled .Values.ingress.tls }}
  
  # Range loop over list:
  {{- range .Values.ingress.hosts }}
  - host: {{ .host }}
  {{- end }}
  
  # Range loop over map:
  {{- range $key, $value := .Values.env }}
  - name: {{ $key }}
    value: {{ $value | quote }}
  {{- end }}
  
  # With (scoped if):
  {{- with .Values.nodeSelector }}
  nodeSelector:
    {{- toYaml . | nindent 2 }}
  {{- end }}

NOTES.txt (post-install instructions):
  
  1. Get the application URL:
  {{- if .Values.ingress.enabled }}
    http{{ if .Values.ingress.tls }}s{{ end }}://{{ .Values.ingress.host }}
  {{- else if contains "LoadBalancer" .Values.service.type }}
    export SERVICE_IP=$(kubectl get svc --namespace {{ .Release.Namespace }} {{ include "my-app.fullname" . }} \
      --template "{{range .status.loadBalancer.ingress}}{{.ip}}{{end}}")
    echo http://$SERVICE_IP:{{ .Values.service.port }}
  {{- end }}

5. VALUES AND OVERRIDES
================================================================================

Value Override Priority (highest wins):
  1. --set flag (CLI)
  2. --set-string flag (CLI, always string)
  3. -f custom-values.yaml (CLI)
  4. values.yaml in chart (defaults)

-f / --values Flag:
  # Override with file:
  helm install my-app ./my-app -f values-production.yaml
  
  # Multiple files (applied in order, later overrides earlier):
  helm install my-app ./my-app -f values-base.yaml -f values-prod.yaml

--set Flag:
  # Simple value:
  helm install my-app ./my-app --set replicaCount=3
  
  # Nested value:
  helm install my-app ./my-app --set image.tag=v2.0.0
  
  # List item:
  helm install my-app ./my-app --set ingress.hosts[0].host=example.com
  
  # Multiple values:
  helm install my-app ./my-app \
    --set replicaCount=3 \
    --set image.tag=v2.0.0 \
    --set resources.requests.memory=256Mi
  
  # String with special chars (use --set-string):
  helm install my-app ./my-app --set-string someKey="true"  # Force string "true" not bool

Values for Multiple Environments:
  
  Directory structure:
  my-app/
  ├── Chart.yaml
  ├── values.yaml            # base defaults
  ├── values-dev.yaml        # dev overrides
  ├── values-staging.yaml    # staging overrides
  └── values-prod.yaml       # production overrides
  
  # Install for production:
  helm install my-app ./my-app -f values-prod.yaml
  
  # values-prod.yaml (only overrides, not full copy):
  replicaCount: 5
  resources:
    requests:
      cpu: "500m"
      memory: "1Gi"
    limits:
      cpu: "2"
      memory: "4Gi"
  autoscaling:
    enabled: true
  ingress:
    enabled: true
    host: api.production.example.com
    tls:
    - secretName: api-tls

6. HELM COMMANDS REFERENCE
================================================================================

Installation and Upgrade:
  # Install a chart (release-name, chart):
  helm install <release> <chart> [flags]
  helm install nginx ingress-nginx/ingress-nginx
  helm install my-app ./my-app -f values-prod.yaml -n production
  helm install my-app ./my-app --set image.tag=v2 --namespace production --create-namespace
  
  # Upgrade:
  helm upgrade <release> <chart> [flags]
  helm upgrade my-app ./my-app -f values-prod.yaml
  helm upgrade --install my-app ./my-app   # Install if not exists, upgrade if exists
  helm upgrade my-app ./my-app --set image.tag=v3 --atomic  # Rollback on failure
  
  # Install/upgrade with common flags:
  --namespace, -n         Target namespace
  --create-namespace      Create namespace if not exists
  --values, -f FILE       Override values file
  --set KEY=VAL           Override individual value
  --dry-run               Simulate, don't apply
  --debug                 Print rendered templates
  --wait                  Wait until all pods ready
  --atomic                If upgrade fails, auto-rollback
  --timeout 5m            Timeout for wait

Inspection:
  # List releases:
  helm list                          # Current namespace
  helm list -A                       # All namespaces
  helm list -n production
  
  # Release status:
  helm status my-app
  helm status my-app -n production
  
  # Release history:
  helm history my-app
  
  # Get release values (what was used):
  helm get values my-app             # User-supplied values only
  helm get values my-app --all       # All values (including defaults)
  
  # Get rendered templates:
  helm get manifest my-app
  
  # Get notes:
  helm get notes my-app

Rollback:
  # Rollback to previous revision:
  helm rollback my-app
  
  # Rollback to specific revision:
  helm rollback my-app 3
  
  # View history first:
  helm history my-app

Uninstall:
  helm uninstall my-app                   # Delete release (keeps history)
  helm uninstall my-app --keep-history    # Keep history for audit
  helm uninstall my-app -n production

Charts and Repositories:
  # Add a repo:
  helm repo add bitnami https://charts.bitnami.com/bitnami
  helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
  
  # Update repos:
  helm repo update
  
  # Search repos:
  helm search repo postgres
  helm search repo bitnami/redis
  helm search hub redis           # Search Artifact Hub
  
  # Show chart info:
  helm show chart bitnami/postgresql
  helm show values bitnami/postgresql    # Default values
  helm show all bitnami/postgresql       # All info
  
  # Download chart locally:
  helm pull bitnami/postgresql --untar
  helm pull bitnami/postgresql --version 12.0.0 --untar

Development:
  # Scaffold a new chart:
  helm create my-chart
  
  # Render templates (no cluster needed):
  helm template my-app ./my-app
  helm template my-app ./my-app -f values-prod.yaml
  
  # Lint (check for syntax/logic errors):
  helm lint ./my-app
  
  # Validate against cluster API:
  helm template ./my-app | kubectl apply --dry-run=client -f -
  
  # Test a release (run test pods):
  helm test my-app
  
  # Package chart:
  helm package ./my-app
  # Creates: my-app-1.2.3.tgz
  
  # Dependency management:
  helm dependency update ./my-app    # Download dependency charts to charts/
  helm dependency list ./my-app      # Show dependency status

8. CHART TESTING AND VALIDATION
================================================================================

helm lint:
  Checks chart for common issues:
  - Required fields missing in Chart.yaml
  - Template syntax errors
  - Best practice violations
  
  helm lint ./my-app
  helm lint ./my-app -f values-prod.yaml

helm template:
  Renders templates locally without connecting to cluster.
  Use to check generated YAML:
  
  helm template my-release ./my-app | less
  helm template my-release ./my-app --debug  # Shows failed templates

helm test:
  Runs test pods defined in templates/tests/.
  Test pods have annotation: helm.sh/hook: test
  
  # templates/tests/test-connection.yaml:
  apiVersion: v1
  kind: Pod
  metadata:
    name: "{{ include "my-app.fullname" . }}-test-connection"
    annotations:
      "helm.sh/hook": test
      "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
  spec:
    restartPolicy: Never
    containers:
    - name: wget
      image: busybox
      command: ["wget", "--spider", "http://{{ include "my-app.fullname" . }}:{{ .Values.service.port }}"]
  
  helm test my-app   # Runs the test pod

chart-testing (ct):
  CLI tool for testing Helm charts.
  Detects changed charts in Git, tests them.
  Used in CI pipelines for chart linting + testing.
  
  ct lint --charts charts/
  ct install --charts charts/

Helm Hooks:
  Run additional actions at certain points in release lifecycle.
  
  Annotations:
  helm.sh/hook: pre-install | post-install | pre-upgrade | post-upgrade
               pre-delete | post-delete | pre-rollback | post-rollback | test
  
  helm.sh/hook-weight: "0"    # Execution order
  helm.sh/hook-delete-policy: before-hook-creation | hook-succeeded | hook-failed
  
  Use cases:
  - Database migration before upgrade (pre-upgrade hook)
  - Cache warming after install (post-install hook)
  - Cleanup tasks after delete (post-delete hook)
  - Connection tests (test hook)

9. HELMFILE — MULTI-CHART MANAGEMENT
================================================================================

What is Helmfile?
  Declarative spec for deploying multiple Helm releases.
  Like docker-compose but for Helm releases.
  
  # Install:
  brew install helmfile

helmfile.yaml:
  
  repositories:
  - name: bitnami
    url: https://charts.bitnami.com/bitnami
  - name: ingress-nginx
    url: https://kubernetes.github.io/ingress-nginx
  
  releases:
  - name: ingress-nginx
    namespace: ingress-nginx
    chart: ingress-nginx/ingress-nginx
    version: 4.7.1
    values:
    - values/ingress-nginx.yaml
  
  - name: cert-manager
    namespace: cert-manager
    chart: jetstack/cert-manager
    version: v1.13.0
    set:
    - name: installCRDs
      value: true
  
  - name: my-app
    namespace: production
    chart: ./charts/my-app
    values:
    - values/my-app-prod.yaml
    - values/secrets.yaml
    needs:
    - ingress-nginx/ingress-nginx    # Deploy after ingress controller

Helmfile Commands:
  helmfile sync          # Apply all releases
  helmfile diff          # Show changes without applying
  helmfile apply         # Sync with confirmation
  helmfile destroy       # Delete all releases
  helmfile template      # Render all templates
  helmfile lint          # Lint all charts

10. HELM BEST PRACTICES
================================================================================

Chart Development:
  ✓ Use helm create as a starting point
  ✓ Follow naming conventions (include "chart.fullname")
  ✓ Add required: "message" for required values
  ✓ Validate values with values.schema.json
  ✓ Use app.kubernetes.io labels (name, instance, version, managed-by)
  ✓ Include NOTES.txt with post-install instructions
  ✓ Write helm tests for critical functionality
  ✓ Use hooks for migrations and cleanup
  ✓ Document all values in values.yaml with comments

Production Usage:
  ✓ Pin chart versions (don't use latest/*)
  ✓ Store values files in Git (without secrets!)
  ✓ Use --atomic for upgrades (auto-rollback on failure)
  ✓ Use --wait for upgrades (wait until pods ready)
  ✓ Keep revision history (for rollback)
  ✓ Use Helmfile or ArgoCD for managing multiple releases
  ✓ Use OCI registries for internal charts

Anti-patterns:
  ✗ Don't hardcode environment-specific values in chart
  ✗ Don't use * version ranges for dependencies
  ✗ Don't store secrets in values.yaml (use External Secrets)
  ✗ Don't skip helm lint in CI
  ✗ Don't use latest as image.tag
  ✗ Avoid deeply nested conditions (hard to maintain)

GitOps with Helm:
  ArgoCD: Supports Helm charts natively.
  Application spec points to chart + values.
  ArgoCD renders and applies templates.
  
  apiVersion: argoproj.io/v1alpha1
  kind: Application
  metadata:
    name: my-app
    namespace: argocd
  spec:
    destination:
      server: https://kubernetes.default.svc
      namespace: production
    source:
      repoURL: https://github.com/my-org/my-app
      targetRevision: main
      helm:
        valueFiles:
        - values-prod.yaml
        parameters:
        - name: image.tag
          value: "v1.2.3"

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Helm and how does it differ from kubectl?
A: Helm is Kubernetes' package manager. The key difference:
   
   kubectl: Low-level tool. Creates/updates/deletes individual resources.
   You manage individual YAML files. No versioning, no rollback of a set.
   
   Helm: High-level package management. Groups related resources into a "release."
   Provides:
   - Templating: One chart, many environments (dev/staging/prod) with values
   - Version control: Charts are versioned. Track what's installed.
   - Atomic operations: Install/upgrade ALL resources together
   - Rollback: Helm keeps revision history → helm rollback
   - Dependency management: Charts can include other charts
   - Community packages: 2000+ charts on Artifact Hub
   
   Example of Helm's advantage:
   Installing Prometheus manually: 50+ YAML files (Deployment, Service, ServiceAccount,
   ConfigMap, CRDs, RBAC, PVCs...) that you maintain and manage.
   With Helm: helm install prometheus prometheus-community/prometheus
   Upgrade: helm upgrade prometheus ... → tracks old config, rolls out new
   Rollback: helm rollback prometheus 3

Q2: Explain how Helm values work and how to override them.
A: Helm has a hierarchical values system:
   
   1. values.yaml in chart: Defaults. Shipped with the chart.
   2. User values file (-f prod-values.yaml): Overrides specific defaults.
   3. --set flag: Highest priority CLI overrides.
   
   The merge is a deep merge, not replacement:
   
   values.yaml:
     image: {repository: nginx, tag: latest}
     resources: {requests: {cpu: 100m, memory: 128Mi}}
   
   prod-values.yaml:
     image: {tag: v1.5.0}   # Only overrides tag
   
   Result: image: {repository: nginx, tag: v1.5.0} (merged)
   
   Important: You only need to specify what you want to CHANGE in override files.
   
   For secrets in values:
   Don't put actual secrets in values files committed to Git.
   Instead use External Secrets Operator or reference a Kubernetes Secret:
   
   # values.yaml:
   secretRef:
     name: app-credentials   # K8s Secret name (not the value!)

Q3: How does Helm handle upgrades and rollbacks?
A: Helm stores release state as Kubernetes Secrets in the namespace.
   Each install/upgrade creates a new revision.
   
   Upgrade process:
   1. helm upgrade my-app ./my-app → Helm renders new templates
   2. Helm sends updated resources to Kubernetes (kubectl apply equivalent)
   3. Kubernetes performs rolling updates on changed resources
   4. Helm records new revision in Secret
   
   --atomic flag:
   If upgrade fails (pods not Ready within timeout), Helm automatically
   runs helm rollback to the previous revision. Atomic = all-or-nothing.
   
   Rollback:
   helm rollback my-app       → back to revision N-1
   helm rollback my-app 3     → back to specific revision
   Helm re-applies the rendered templates from that revision.
   
   History:
   helm history my-app        → shows all revisions with status
   
   REVISION  STATUS      CHART         APP VERSION  DESCRIPTION
   1         superseded  my-app-1.0.0  1.0.0        Install complete
   2         superseded  my-app-1.1.0  1.1.0        Upgrade complete
   3         failed      my-app-1.2.0  1.2.0        Upgrade failed
   4         deployed    my-app-1.1.0  1.1.0        Rollback to 2

Q4: What is a Helm hook and when would you use one?
A: Helm hooks let you run specific actions at points in the release lifecycle.
   They're Kubernetes resources with special annotations.
   
   Lifecycle points:
   pre-install     Before any release resources are created
   post-install    After all release resources are created
   pre-upgrade     Before any upgrade resources are updated
   post-upgrade    After upgrade
   pre-delete      Before release deletion
   post-delete     After deletion
   test            For helm test (connection tests, smoke tests)
   
   Common use cases:
   
   1. Database migrations (pre-upgrade hook):
      Run migration Job BEFORE new app pods start.
      Ensures schema is ready for new code.
      
      annotations:
        "helm.sh/hook": pre-upgrade
        "helm.sh/hook-weight": "0"
        "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
   
   2. Smoke tests (test hook):
      Run test pod that verifies app works after install.
      helm test my-app runs it.
   
   3. Cache warming (post-install hook):
      Seed initial data after install.
   
   4. Cleanup (pre-delete hook):
      Drain connections, notify monitoring before deletion.
   
   Hooks are NOT managed like regular release resources:
   - They're not deleted on helm uninstall unless hook-delete-policy says so
   - hook-delete-policy: hook-succeeded → delete pod after successful run
   - hook-weight: controls execution order when multiple hooks exist

Q5: How would you use Helm in a CI/CD pipeline?
A: Typical pipeline integration:
   
   Build stage:
   1. Build Docker image → tag with git SHA
   2. Push to registry
   
   Deploy stage with Helm:
   
   # Update image tag in values:
   helm upgrade --install my-app ./charts/my-app \
     --namespace production \
     --create-namespace \
     -f charts/my-app/values-prod.yaml \
     --set image.tag=$GIT_SHA \
     --atomic \
     --wait \
     --timeout 5m
   
   --install: Creates release if it doesn't exist (safe for first deploy)
   --atomic: Auto-rollback if pods don't start successfully
   --wait: Waits for all pods to be ready before returning success
   --set image.tag=$GIT_SHA: Inject git SHA from CI
   
   GitOps alternative (ArgoCD):
   Instead of Helm in CI, CI just pushes the image.
   ArgoCD watches Git repo. You update values-prod.yaml with new tag.
   ArgoCD detects change → deploys automatically.
   No Helm credentials needed in CI.
   
   Namespace-per-environment:
   helm upgrade --install my-app ./charts/my-app -n dev
   helm upgrade --install my-app ./charts/my-app -n staging
   helm upgrade --install my-app ./charts/my-app -n production
