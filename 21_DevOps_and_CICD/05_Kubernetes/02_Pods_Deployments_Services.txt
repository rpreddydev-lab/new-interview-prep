1. PODS — THE BASIC BUILDING BLOCK
================================================================================

What is a Pod?
  Smallest deployable unit in Kubernetes.
  One or more containers that SHARE:
  - Network namespace (same IP address, same port space)
  - IPC namespace (can use shared memory)
  - Storage volumes (optional)
  
  Containers in a pod communicate via localhost.
  Pods are EPHEMERAL — when deleted, they are gone (not restarted by default).
  You almost never create pods directly. Use Deployments/StatefulSets/etc.

Complete Pod Spec:
  
  apiVersion: v1
  kind: Pod
  metadata:
    name: my-app
    namespace: production
    labels:
      app: my-app
      version: v1.2.3
    annotations:
      prometheus.io/scrape: "true"
      prometheus.io/port: "8080"
  spec:
    # Container spec
    containers:
    - name: app
      image: my-app:v1.2.3
      ports:
      - name: http
        containerPort: 8080
        protocol: TCP
      
      # Resource requests and limits
      resources:
        requests:
          cpu: "250m"       # 0.25 cores guaranteed
          memory: "256Mi"   # 256MB guaranteed
        limits:
          cpu: "500m"       # Max 0.5 cores
          memory: "512Mi"   # Max 512MB (OOMKilled if exceeded!)
      
      # Environment variables
      env:
      - name: ENV
        value: "production"
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: password
      - name: APP_NAME
        valueFrom:
          fieldRef:
            fieldPath: metadata.name          # Pod name
      
      # Load all keys from ConfigMap as env vars
      envFrom:
      - configMapRef:
          name: app-config
      - secretRef:
          name: app-secrets
      
      # Volume mounts
      volumeMounts:
      - name: config-volume
        mountPath: /app/config
        readOnly: true
      - name: data
        mountPath: /data
      - name: tmp
        mountPath: /tmp
      
      # Liveness probe: restart container if fails
      livenessProbe:
        httpGet:
          path: /healthz
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
        failureThreshold: 3
      
      # Readiness probe: remove from Service endpoints if fails
      readinessProbe:
        httpGet:
          path: /ready
          port: 8080
        initialDelaySeconds: 5
        periodSeconds: 5
        failureThreshold: 3
      
      # Startup probe: one-time check for slow-starting apps
      startupProbe:
        httpGet:
          path: /healthz
          port: 8080
        failureThreshold: 30    # 30 * 10s = 5 minutes to start
        periodSeconds: 10
      
      # Lifecycle hooks
      lifecycle:
        postStart:
          exec:
            command: ["/bin/sh", "-c", "echo started > /tmp/started"]
        preStop:                    # Called before SIGTERM
          exec:
            command: ["/bin/sh", "-c", "/app/drain.sh"]
      
      # Security context
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        readOnlyRootFilesystem: true
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
    
    # Init containers (run before app containers, sequentially)
    initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z postgres 5432; do echo waiting; sleep 2; done']
    
    # Volumes
    volumes:
    - name: config-volume
      configMap:
        name: app-config
    - name: data
      persistentVolumeClaim:
        claimName: app-data-pvc
    - name: tmp
      emptyDir:
        medium: Memory     # tmpfs (optional, defaults to disk)
    
    # Scheduling
    nodeSelector:
      kubernetes.io/os: linux
    
    tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "app"
      effect: "NoSchedule"
    
    # Service account (for RBAC)
    serviceAccountName: my-app-sa
    
    # Graceful termination (seconds before SIGKILL after SIGTERM)
    terminationGracePeriodSeconds: 30
    
    # DNS configuration
    dnsPolicy: ClusterFirst     # Use CoreDNS (default)
    
    # Image pull secret (for private registries)
    imagePullSecrets:
    - name: registry-credentials
    
    # Restart policy (for standalone pods — Deployments always use Always)
    restartPolicy: Always       # Always / OnFailure / Never
    
    # Security context at pod level
    securityContext:
      runAsNonRoot: true
      runAsGroup: 1000
      fsGroup: 2000             # Volume ownership group

Resource Units:
  CPU:
    1 core = 1000m (millicores)
    500m = 0.5 cores
    100m = 0.1 cores
    "1" = 1000m = 1 core
  
  Memory:
    Mi = Mebibytes (1Mi = 1,048,576 bytes)
    Gi = Gibibytes
    M = Megabytes (1M = 1,000,000 bytes)
    Use Mi/Gi for predictable values
  
  QoS Classes (automatically assigned):
  Guaranteed: requests == limits for ALL containers (best, last to evict)
  Burstable:  requests set, but not equal to limits (or only for some containers)
  BestEffort: NO requests or limits set (worst, first to evict under pressure)

Pod Lifecycle States:
  Pending    → Accepted but not yet scheduled or image not pulled
  Running    → Bound to node, at least one container is running
  Succeeded  → All containers completed successfully (exit 0)
  Failed     → All containers exited, at least one with non-zero exit
  Unknown    → Node communication lost
  
  Container states:
  Waiting    → Not yet running (pulling image, waiting for init container)
  Running    → Executing
  Terminated → Exited (successfully or with error)

Init Containers:
  Run sequentially BEFORE app containers start.
  Each must complete successfully before the next starts.
  App containers don't start until ALL init containers succeed.
  
  Use cases:
  - Wait for dependencies (DB, API): until nc -z postgres 5432
  - Pre-populate volumes (git clone config)
  - Run DB migrations
  - Set up file permissions
  
  Different from app containers: no liveness/readiness probes.

2. MULTI-CONTAINER POD PATTERNS
================================================================================

Sidecar Pattern:
  Second container enhances the main container.
  
  Examples:
  - Log shipping: main app writes to /var/log → fluentd sidecar ships logs
  - Proxy: Envoy sidecar handles TLS, routing, observability
  - Sync: git-sync sidecar keeps config files updated
  
  spec:
    containers:
    - name: app
      image: my-app
      volumeMounts:
      - name: logs
        mountPath: /var/log
    - name: log-shipper
      image: fluent/fluent-bit
      volumeMounts:
      - name: logs
        mountPath: /var/log
    volumes:
    - name: logs
      emptyDir: {}

Ambassador Pattern:
  Sidecar proxy that simplifies external access.
  App talks to localhost → ambassador handles external communication.
  
  Example: App connects to localhost:5432 → ambassador connects to cloud SQL
           App doesn't need to know about cloud SQL credentials/connection pooling

Adapter Pattern:
  Transforms/normalizes output of the main container.
  
  Example: App exposes metrics in custom format → adapter translates to Prometheus format

3. REPLICASET
================================================================================

What is a ReplicaSet?
  Ensures N identical pod replicas are running at any time.
  If a pod dies → ReplicaSet creates a replacement.
  If too many → ReplicaSet deletes the excess.
  Uses label selectors to identify "its" pods.
  
  You typically don't create ReplicaSets directly — Deployments create them.

ReplicaSet YAML:
  
  apiVersion: apps/v1
  kind: ReplicaSet
  metadata:
    name: nginx-rs
  spec:
    replicas: 3
    selector:
      matchLabels:
        app: nginx
        tier: frontend
    template:                # Pod template
      metadata:
        labels:
          app: nginx
          tier: frontend
      spec:
        containers:
        - name: nginx
          image: nginx:1.25

Adopting Existing Pods:
  ReplicaSet can "adopt" pods that match its selector (even if it didn't create them).
  This can cause issues — always use unique label selectors per ReplicaSet.

4. DEPLOYMENTS
================================================================================

What is a Deployment?
  Manages ReplicaSets. Adds:
  - Rolling updates (new ReplicaSet, old one scales down)
  - Rollback (revert to previous ReplicaSet)
  - Pause/resume rollouts
  - Revision history
  
  Create Deployment → Deployment creates ReplicaSet → ReplicaSet creates Pods

Deployment YAML (full production example):
  
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: my-app
    namespace: production
    labels:
      app: my-app
    annotations:
      kubernetes.io/change-cause: "Update to v1.2.3, add feature X"
  spec:
    replicas: 3
    
    # Must match pod template labels
    selector:
      matchLabels:
        app: my-app
    
    # Update strategy
    strategy:
      type: RollingUpdate
      rollingUpdate:
        maxSurge: 1          # Max pods ABOVE desired during update (absolute or %)
        maxUnavailable: 0    # Max pods BELOW desired during update (0 = no downtime)
    
    # Keep N old ReplicaSets for rollback
    revisionHistoryLimit: 10
    
    # Wait this long before considering update progressed
    progressDeadlineSeconds: 600
    
    # Pod template (this is what gets deployed)
    template:
      metadata:
        labels:
          app: my-app
        annotations:
          prometheus.io/scrape: "true"
      spec:
        containers:
        - name: my-app
          image: my-app:v1.2.3
          ports:
          - containerPort: 8080
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5

5. DEPLOYMENT STRATEGIES
================================================================================

RollingUpdate (default):
  Gradually replace old pods with new ones.
  
  maxSurge: 1, maxUnavailable: 0  →  Zero-downtime (extra pod created first)
  maxSurge: 0, maxUnavailable: 1  →  Resource-efficient (one old pod removed first)
  maxSurge: 1, maxUnavailable: 1  →  Fast update
  
  Timeline (3 replicas, maxSurge=1, maxUnavailable=0):
  Start:   [v1][v1][v1]                    desired=3
  Step 1:  [v1][v1][v1][v2]               desired=3+1=4 (surge)
  Step 2:  [v1][v1][v2]                   v2 ready → remove one v1
  Step 3:  [v1][v1][v2][v2]               add another v2
  Step 4:  [v1][v2][v2]                   remove another v1
  ...
  End:     [v2][v2][v2]                   done

Recreate Strategy:
  Kill ALL old pods, then create new ones. Has downtime.
  Use when: old and new versions can't coexist (schema changes, etc.)
  
  strategy:
    type: Recreate

Rollout Commands:
  # Trigger a rollout by updating the image
  kubectl set image deployment/my-app my-app=my-app:v1.3.0
  
  # Check rollout status
  kubectl rollout status deployment/my-app
  
  # View rollout history
  kubectl rollout history deployment/my-app
  
  # View specific revision
  kubectl rollout history deployment/my-app --revision=3
  
  # Rollback to previous
  kubectl rollout undo deployment/my-app
  
  # Rollback to specific revision
  kubectl rollout undo deployment/my-app --to-revision=2
  
  # Pause rollout (stop mid-way for canary testing)
  kubectl rollout pause deployment/my-app
  
  # Resume
  kubectl rollout resume deployment/my-app

Triggering Rollouts:
  K8s only triggers a rollout when the pod template spec changes.
  Changing just environment variables restarts pods.
  
  # Force rollout without image change (e.g., to reload ConfigMap):
  kubectl rollout restart deployment/my-app
  # This updates an annotation with current timestamp → pod template changes → rollout

6. OTHER WORKLOAD RESOURCES
================================================================================

DaemonSet:
  Ensures one pod runs on EVERY node (or selected nodes).
  
  Use cases:
  - Log collection agents (Fluentd, Filebeat)
  - Monitoring agents (node-exporter, Datadog agent)
  - Network plugins (Cilium, Calico)
  - Storage drivers
  
  apiVersion: apps/v1
  kind: DaemonSet
  metadata:
    name: node-exporter
  spec:
    selector:
      matchLabels:
        app: node-exporter
    template:
      metadata:
        labels:
          app: node-exporter
      spec:
        containers:
        - name: node-exporter
          image: prom/node-exporter:latest
          ports:
          - containerPort: 9100
        tolerations:
        - key: node-role.kubernetes.io/control-plane
          effect: NoSchedule  # Run on control plane nodes too (for control plane monitoring)
        hostNetwork: true      # Use node's network namespace

StatefulSet (brief — detailed in separate file):
  Like Deployment but for stateful applications.
  Provides:
  - Stable, predictable pod names: pod-0, pod-1, pod-2
  - Stable network identities (headless service)
  - Ordered deployment and scaling
  - Persistent storage per pod
  
  Use cases: Databases (MySQL, PostgreSQL, MongoDB, Cassandra), Kafka, ZooKeeper

Job:
  Runs one or more pods until successful completion.
  Pods are not restarted after success.
  
  apiVersion: batch/v1
  kind: Job
  metadata:
    name: db-migration
  spec:
    completions: 1          # How many successful completions needed
    parallelism: 1          # How many pods to run at once
    backoffLimit: 4         # Retry limit
    activeDeadlineSeconds: 600  # Max runtime
    template:
      spec:
        containers:
        - name: migrate
          image: my-app:v2
          command: ["python", "manage.py", "migrate"]
        restartPolicy: OnFailure   # OnFailure or Never

CronJob:
  Creates Jobs on a schedule (cron syntax).
  
  apiVersion: batch/v1
  kind: CronJob
  metadata:
    name: backup-job
  spec:
    schedule: "0 2 * * *"        # Every day at 2 AM
    concurrencyPolicy: Forbid    # Allow / Forbid / Replace
    successfulJobsHistoryLimit: 3
    failedJobsHistoryLimit: 1
    jobTemplate:
      spec:
        template:
          spec:
            containers:
            - name: backup
              image: backup-tool:latest
              command: ["/backup.sh"]
            restartPolicy: OnFailure

7. SERVICES — NETWORKING ABSTRACTION
================================================================================

Why Services?
  Pods are ephemeral. Their IPs change constantly.
  You can't hard-code pod IPs. Services provide stable endpoints.
  
  Service provides:
  - Stable ClusterIP (virtual IP that doesn't change)
  - DNS name: <service-name>.<namespace>.svc.cluster.local
  - Load balancing across healthy pods
  - Port mapping (service port → pod port)

How Services Find Pods:
  Services use LABEL SELECTORS to identify target pods.
  This is the critical linking mechanism between Service and Deployment.
  
  Deployment pods have labels:  app: my-app, tier: backend
  Service selector:             app: my-app, tier: backend
  → Service routes traffic to these pods
  
  The SAME labels used in the Deployment selector are targeted by the Service.

Complete Service YAML:
  
  apiVersion: v1
  kind: Service
  metadata:
    name: my-app-service
    namespace: production
    labels:
      app: my-app
    annotations:
      # For AWS ALB Ingress controller
      service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
  spec:
    type: ClusterIP         # ClusterIP / NodePort / LoadBalancer / ExternalName
    
    # Must match pod labels
    selector:
      app: my-app
      tier: backend
    
    ports:
    - name: http
      protocol: TCP
      port: 80              # Port clients connect to (ClusterIP:80)
      targetPort: 8080      # Port on the container (pod port)
    - name: https
      protocol: TCP
      port: 443
      targetPort: 8443
    
    # Optional: sticky sessions (client IP affinity)
    sessionAffinity: ClientIP
    sessionAffinityConfig:
      clientIP:
        timeoutSeconds: 10800   # 3 hours

Service DNS:
  Full DNS: <name>.<namespace>.svc.cluster.local
  Within same namespace: <name>
  Cross-namespace: <name>.<namespace>
  
  Examples:
  my-app-service.production.svc.cluster.local
  my-app-service.production
  my-app-service   (if in same namespace)
  
  Port lookup: <name>.<namespace>.svc.cluster.local:<port>

8. SERVICE TYPES IN DEPTH
================================================================================

ClusterIP (default):
  Internal only. Accessible within the cluster.
  Gets a virtual IP from the service CIDR range.
  
  spec:
    type: ClusterIP
    clusterIP: None   # Headless service (no virtual IP, returns pod IPs directly)
    
  Headless Service:
    clusterIP: None → DNS returns pod IPs directly, not a virtual IP.
    Used by StatefulSets for stable pod DNS:
      pod-0.headless-svc.namespace.svc.cluster.local
    Also used by service discovery systems (Consul, Istio).

NodePort:
  Exposes service on each node's IP at a static port (30000-32767).
  ClusterIP is automatically created.
  External access: <NodeIP>:<NodePort>
  
  spec:
    type: NodePort
    ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080   # Omit to get a random port in 30000-32767 range
  
  Limitations:
  - Ports in limited range (30000-32767)
  - Node IP can change
  - Need to know which node to connect to
  - Load balancing must be done externally
  
  Use cases: Development/testing, on-premise without cloud LB support

LoadBalancer:
  Provisions an external cloud load balancer.
  Includes NodePort and ClusterIP automatically.
  
  spec:
    type: LoadBalancer
    ports:
    - port: 80
      targetPort: 8080
    loadBalancerSourceRanges:    # IP allowlist
    - "203.0.113.0/24"
    - "198.51.100.0/24"
  
  Cloud provider creates:
  - AWS: Classic ELB or NLB (with annotations)
  - GCP: Regional External Load Balancer
  - Azure: Azure Load Balancer
  
  Each LoadBalancer Service = one cloud LB = cost per service.
  Better to use one Ingress Controller with many Ingress resources.
  
  Status shows the external IP:
  kubectl get svc my-app   →  EXTERNAL-IP: 52.10.20.30

ExternalName:
  Maps a Service to an external DNS name (no selector, no proxy).
  K8s returns a CNAME record.
  
  spec:
    type: ExternalName
    externalName: my-database.rds.amazonaws.com
  
  Use case: Internal pods use my-db.production (K8s DNS) which
  resolves to an external RDS endpoint. Easy to switch without code changes.

9. ENDPOINTS AND ENDPOINTSLICES
================================================================================

Endpoints (legacy):
  K8s maintains an Endpoints object for each Service.
  Lists the pod IPs and ports that match the Service selector.
  
  kubectl get endpoints my-app-service
  # NAME              ENDPOINTS                             AGE
  # my-app-service    10.0.0.1:8080,10.0.0.2:8080         5m
  
  kube-proxy watches Endpoints → updates iptables/IPVS rules.
  CoreDNS watches Endpoints for headless services.
  
  Problem: One Endpoints object per Service. Large Endpoints (1000+ pods) = large
  updates on every change → performance issue at scale.

EndpointSlices (modern, K8s 1.21+):
  Shards endpoints across multiple objects (default: 100 endpoints per slice).
  Only changed slices are updated → much better for large deployments.
  
  kubectl get endpointslices -l kubernetes.io/service-name=my-app-service

Manual Endpoints (Services without selectors):
  Create Service without selector + manual Endpoints for:
  - External services (without ExternalName)
  - Services in a different namespace
  - Migration scenarios (point to different backend)
  
  # Service (no selector)
  apiVersion: v1
  kind: Service
  metadata:
    name: external-db
  spec:
    ports:
    - port: 5432
  ---
  # Manual Endpoints
  apiVersion: v1
  kind: Endpoints
  metadata:
    name: external-db    # Must match Service name
  subsets:
  - addresses:
    - ip: 10.100.200.1   # External IP
    ports:
    - port: 5432

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between a Pod, ReplicaSet, and Deployment?
A: They serve different purposes and work together:
   
   POD: The atomic unit of deployment. Contains one or more containers that
   share network and storage. Pods are ephemeral — when deleted or the node
   fails, the pod is gone. No automatic restart or replacement.
   
   REPLICASET: Ensures a specific number of pod replicas are running.
   Uses a label selector to identify its pods. If a pod crashes, RS creates
   a new one. BUT: ReplicaSet doesn't know how to update pods to a new version.
   It just maintains count.
   
   DEPLOYMENT: Manages ReplicaSets to provide declarative updates. When you
   change the image version, the Deployment creates a new ReplicaSet with the
   new pods and scales down the old ReplicaSet — this is a rolling update.
   It tracks revision history for rollback. Deployment wraps ReplicaSet wraps Pod.
   
   Practical rule: ALWAYS use Deployments (not ReplicaSets or bare Pods) for
   stateless applications. ReplicaSet is an implementation detail.

Q2: Explain how Kubernetes Services work and how they discover pods.
A: A Service provides a stable, abstract endpoint for a set of pods.
   
   Service discovery mechanism:
   1. Service has a label selector (e.g., app: my-app)
   2. Endpoint controller watches for pods matching the selector
   3. Creates/updates Endpoints object with current pod IPs
   4. kube-proxy watches Endpoints and updates iptables/IPVS rules
   5. Requests to ClusterIP:Port are DNAT'd to a pod IP:Port by iptables
   
   DNS resolution:
   - CoreDNS is the cluster DNS server
   - Services get DNS entry: <name>.<namespace>.svc.cluster.local
   - Pod queries CoreDNS → gets ClusterIP → traffic goes to a pod via iptables
   
   Example traffic flow for request to http://my-service:80 :
   1. Pod resolves my-service → CoreDNS → ClusterIP 10.96.100.50
   2. Pod sends packet to 10.96.100.50:80
   3. iptables on the node intercepts (in KUBE-SERVICES chain)
   4. DNAT rule changes destination to 10.0.0.1:8080 (one of the pods)
   5. Packet goes to pod. Response comes back through conntrack.
   
   Health: Only pods with passing readiness probes are in Endpoints.
   Failed readiness → removed from Endpoints → no traffic sent.

Q3: When would you use a DaemonSet vs a Deployment?
A: Based on the distribution requirement:
   
   DEPLOYMENT: N replicas distributed optimally across nodes.
   Number of pods is fixed (replicas: 3).
   Scheduler places pods for best resource utilization.
   Use for: Stateless application services, APIs, web servers.
   
   DAEMONSET: Exactly 1 pod per node (matching the selector).
   Number of pods automatically = number of qualifying nodes.
   Cannot set replicas count.
   New node added → DaemonSet automatically adds a pod.
   Node removed → pod automatically removed.
   Use for: Node-level infrastructure: monitoring agents (node-exporter,
   Datadog agent), log collectors (Fluentd, Filebeat), network plugins (Calico,
   Cilium), storage daemons.
   
   Example interview answer: "If I'm deploying Prometheus node-exporter to
   collect CPU/memory metrics from every node, I'd use a DaemonSet because
   I need exactly one exporter per node, including new nodes that join the
   cluster. If I'm deploying my API server with 3 replicas, I'd use a
   Deployment because I want 3 total instances optimally distributed."

Q4: What is a headless service and when would you use it?
A: A headless service has clusterIP: None — it has no virtual IP.
   
   Regular Service:
   DNS query for my-service → returns ClusterIP (10.96.100.50)
   Traffic goes to ClusterIP → iptables load balances to a pod
   
   Headless Service:
   DNS query for my-service → returns A records for ALL pod IPs directly
   Client does its own load balancing or connects to a specific pod
   
   Use cases:
   
   1. StatefulSets: Each pod gets a stable DNS name:
      pod-0.headless-svc.namespace.svc.cluster.local → always same pod
      Essential for databases where replicas need fixed addresses
      (MySQL primary, Kafka broker IDs, ZooKeeper ensemble)
   
   2. Service discovery with client-side load balancing:
      gRPC applications typically do client-side LB and need all endpoints
      (HTTP/1.1 keepalive makes kube-proxy LB ineffective for gRPC)
   
   3. Service mesh (Istio/Linkerd):
      The service mesh proxy gets all pod IPs for traffic management

Q5: Explain the difference between Deployment's maxSurge and maxUnavailable.
A: These control the rolling update pace and availability:
   
   maxSurge: Maximum number of pods that can exist ABOVE the desired count
   during an update. Controls how fast new pods are created.
   
   maxUnavailable: Maximum number of pods that can be BELOW the desired
   count during an update. Controls downtime tolerance.
   
   Both can be absolute numbers or percentages.
   
   Common configurations:
   
   Zero-downtime (preferred): maxSurge=1, maxUnavailable=0
   - New pod created first, old pod removed only when new is Ready
   - Always at least desired replicas running
   - Needs extra capacity (25% more at peak)
   
   Resource-efficient: maxSurge=0, maxUnavailable=1
   - Old pod removed first, then new pod created
   - Brief period with fewer pods → some reduced capacity
   - No extra resources needed
   
   Fast: maxSurge=1, maxUnavailable=1
   - Remove one old, add one new simultaneously
   - Might temporarily have one less pod
   
   Full surge: maxSurge=100%, maxUnavailable=0
   - Creates ALL new pods first, then removes ALL old pods
   - Like blue-green deploy but uses Deployment resources
   
   My recommendation: maxSurge=1, maxUnavailable=0 for production
   to guarantee no downtime. Ensure resource budget allows the extra pod.

11. QUICK REFERENCE CHEAT SHEET
================================================================================

WORKLOAD TYPES:
  Deployment        Stateless apps, rolling updates, rollback
  StatefulSet       Stateful apps, stable identity, ordered
  DaemonSet         One pod per node (monitoring, networking)
  Job               Run to completion
  CronJob           Scheduled jobs

SERVICE TYPES:
  ClusterIP         Internal only (default)
  NodePort          External via node IP:port (30000-32767)
  LoadBalancer      Cloud load balancer
  ExternalName      CNAME to external DNS
  Headless          clusterIP: None, returns pod IPs directly

DEPLOYMENT COMMANDS:
  kubectl apply -f deployment.yaml
  kubectl rollout status deployment/<name>
  kubectl rollout history deployment/<name>
  kubectl rollout undo deployment/<name>
  kubectl rollout restart deployment/<name>
  kubectl scale deployment/<name> --replicas=5
  kubectl set image deployment/<name> container=image:tag

KEY CONCEPTS:
  Labels + Selectors     Link Services to Pods, Deployments to ReplicaSets
  Endpoints              Pod IPs behind a Service (auto-managed)
  QoS Classes            Guaranteed > Burstable > BestEffort
  readinessProbe         Controls traffic routing (Service endpoints)
  livenessProbe          Controls container restart
  startupProbe           Protects slow-starting containers
  terminationGrace       Time between SIGTERM and SIGKILL

RESOURCE SPEC:
  requests.cpu: "100m"    # 0.1 cores guaranteed
  requests.memory: "128Mi"
  limits.cpu: "500m"      # Max 0.5 cores (throttled if exceeded)
  limits.memory: "512Mi"  # OOMKilled if exceeded
