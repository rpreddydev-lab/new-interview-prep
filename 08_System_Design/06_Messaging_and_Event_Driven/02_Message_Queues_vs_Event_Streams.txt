================================================================
MESSAGE QUEUES vs EVENT STREAMS
================================================================

TWO FUNDAMENTAL MESSAGING PARADIGMS
--------------------------------------

MESSAGE QUEUE (Point-to-Point):
  Producer sends a message to a queue.
  ONE consumer picks up the message and processes it.
  Message is deleted after successful processing.
  
  Producer → [Queue] → Consumer
  
  Key characteristics:
  - Message is "claimed" by one consumer (competing consumers)
  - Message disappears after consumption
  - No history or replay
  - Pull-based or push-based
  - Great for task distribution (load balancing work)
  
  Examples: RabbitMQ, AWS SQS, ActiveMQ

EVENT STREAM (Log-based):
  Producer appends an event to an ordered, immutable log.
  MULTIPLE consumers can read the log independently.
  Events are NOT deleted after reading (retained for a configurable time).
  Consumers track their position (offset) in the log.
  
  Producer → [Log/Stream] → Consumer A (at offset 50)
                          → Consumer B (at offset 45)
                          → Consumer C (at offset 50)
  
  Key characteristics:
  - Events persist and can be replayed from any offset
  - Multiple independent consumers
  - Consumers own their position (can go back)
  - Great for audit logs, event sourcing, multi-consumer fan-out
  - Ordering guaranteed within a partition
  
  Examples: Apache Kafka, AWS Kinesis, Google Pub/Sub, Redis Streams

MESSAGE QUEUE — DEEP DIVE (RabbitMQ)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RabbitMQ uses the AMQP (Advanced Message Queuing Protocol).

Components:
  Exchange: Receives messages from producers, routes to queues.
  Queue: Stores messages waiting for consumer.
  Binding: Rules connecting exchange to queue.
  
EXCHANGE TYPES:
  Direct:  Message with routing key "order.created" → queue with exact match.
  Topic:   Pattern-based routing. "order.*" matches "order.created", "order.paid".
  Fanout:  Copy message to ALL bound queues (broadcast).
  Headers: Route based on message headers (vs routing key).

ACKNOWLEDGEMENTS:
  Consumer receives message, processes, sends ACK.
  If consumer crashes before ACK, message returned to queue.
  Ensures at-least-once delivery.
  
  Manual ACK: Consumer explicitly ACKs after successful processing.
  Auto ACK:   Message removed as soon as delivered (at-most-once).

DEAD LETTER QUEUE (DLQ):
  If message fails processing multiple times (max-retry exceeded),
  move to Dead Letter Queue for manual inspection/reprocessing.
  
  Common pattern:
    Main Queue → DLQ (after 3 failures)
    DLQ → Manual review / fix and resubmit

VISIBILITY TIMEOUT (AWS SQS):
  When consumer picks up a message, it's "invisible" to other consumers.
  Consumer must delete message within visibility timeout (default: 30s).
  If consumer crashes: visibility timeout expires → message visible again.
  This prevents message loss on consumer failure.

CHOOSING BETWEEN QUEUE AND STREAM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use MESSAGE QUEUE when:
  ✓ Each message should be processed by exactly ONE consumer
  ✓ Work distribution: multiple workers competing for tasks
  ✓ Message can be discarded after processing
  ✓ No need for replay
  ✓ Examples: Sending emails, processing payments, resizing images

Use EVENT STREAM when:
  ✓ Multiple independent consumers need the same event
  ✓ Replay is needed (reprocess history, rebuild state)
  ✓ Events must be preserved (audit log, analytics)
  ✓ Consumer needs to control its own read position
  ✓ Fan-out: one event triggers multiple different services
  ✓ Examples: Audit log, CDC (Change Data Capture), analytics pipeline

HYBRID PATTERN:
  Kafka topic (stream) + consumer group per team.
  Multiple consumer groups read the same topic independently.
  Within a consumer group, each partition processed by one consumer.
  → Both fan-out (multiple groups) and load balancing (within group).
