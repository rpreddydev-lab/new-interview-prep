================================================================
MESSAGING AND EVENT-DRIVEN ARCHITECTURE — OVERVIEW
================================================================

WHY MESSAGING?
---------------
Synchronous communication (HTTP/gRPC) has fundamental limitations:
  - If Service B is slow, Service A is blocked.
  - If Service B is down, Service A's request fails.
  - Services are tightly coupled (A knows B's address).

Messaging (asynchronous communication) solves these:
  - Service A puts message in queue → returns immediately.
  - Service B processes when ready.
  - A and B don't need to be running simultaneously.
  - Decouple producers from consumers.

MESSAGING VOCABULARY:
  Producer (Publisher): Creates and sends messages.
  Consumer (Subscriber): Receives and processes messages.
  Message: Unit of data sent through the system.
  Queue: Stores messages until consumed (FIFO, typically 1:1).
  Topic: Category of messages. Multiple consumers can subscribe.
  Broker: Middleware that receives, stores, and routes messages.
  Event: An immutable record that something happened.
  Event Stream: Ordered, persistent log of events.

USE CASES FOR MESSAGING:
  ✓ Async task processing (send email, resize image, charge payment)
  ✓ Decoupling microservices (order service doesn't call email service)
  ✓ Rate limiting (queue absorbs traffic spikes)
  ✓ Fan-out (one event → multiple downstream processors)
  ✓ Audit log / activity stream
  ✓ Event sourcing (rebuild state from events)
  ✓ Real-time analytics pipelines
  ✓ Data integration between systems

DELIVERY GUARANTEES:
  At-most-once:   Message delivered 0 or 1 times. May lose messages.
                  Use for: Metrics (losing one metric OK), logs.
  
  At-least-once:  Message delivered 1+ times. May duplicate.
                  Operations must be IDEMPOTENT.
                  Use for: Payments (idempotency key prevents duplicate charges)
  
  Exactly-once:   Message delivered exactly once. Hard to achieve, expensive.
                  Kafka Transactions + idempotent producers can achieve this.
                  Truly exactly-once requires end-to-end idempotency anyway.
