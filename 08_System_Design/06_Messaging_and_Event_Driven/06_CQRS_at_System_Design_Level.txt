# CQRS at System Design Level — Complete Guide

## What Is CQRS?

Command Query Responsibility Segregation (CQRS) separates the **write model** (commands that mutate state) from the **read model** (queries that return data). They use different data stores optimized for their respective workloads.

```
Traditional (CRUD):
  Client → Single Model → Single Database
                          (handles reads AND writes)

CQRS:
  Client ─┬→ Command Side → Write DB (normalized, transactional)
           │                     │ (events emitted on change)
           │                     ↓
           │              Event Bus / Message Broker
           │                     │ (async projection)
           │                     ↓
           └→ Query Side  → Read DB  (denormalized, fast reads)
```

---

## When to Use CQRS (System Design Decision)

**Use CQRS when:**
- Read and write workloads have very different scaling requirements (e.g., 100:1 read/write ratio)
- Read models need to be tailored per use case (dashboard needs aggregated data, API needs normalized data)
- You need audit trails or temporal queries (pairs naturally with Event Sourcing)
- Different teams own read vs. write concerns

**Do NOT use CQRS when:**
- Simple CRUD domain — adds accidental complexity
- Strong consistency is required between command and query (CQRS is eventually consistent)
- Small team or early-stage product

## Key Design Decisions

### 1. How are commands validated?
- Commands go through the write model only
- Write model enforces invariants (e.g., cannot ship an order that isn't paid)
- Use domain model / aggregate roots on the command side

### 2. How is the read model kept in sync?
- Write side emits domain events on every state change
- Projection service (event consumer) rebuilds read models from events
- Read model is **eventually consistent** — there is a lag between write and read

### 3. How do you handle the consistency lag?
- UI shows "your order was placed, it will appear in your history shortly"
- Use versioned responses — command returns the expected version; client polls until query returns that version
- For critical reads, route directly to the write DB (breaks CQRS but acceptable for specific use cases)

### 4. What if the projection service fails?
- Events are durably stored in Kafka (with retention) or an Outbox table
- Projection service can replay events from the beginning to rebuild read models
- Design read models to be **idempotent** — replaying the same event twice produces the same result

## CQRS vs. Traditional Read Replicas

| Aspect | Read Replica | CQRS |
|--------|-------------|------|
| Schema | Same as primary | Totally different, query-optimized |
| Consistency lag | Seconds (replication) | Seconds to minutes (event processing) |
| Query flexibility | Same SQL schema | Any structure (JSON, document, graph) |
| Complexity | Low | High |
| Use case | Same data, reduce read load | Different data shapes per consumer |

## Interview Q&A

**Q: What problem does CQRS solve?**
A: It solves the impedance mismatch between write and read workloads. Writes need transactional consistency and normalized data. Reads need denormalized, aggregated, sometimes multi-source data. A single model cannot be optimized for both simultaneously. CQRS lets each side be optimized independently — the write model enforces domain invariants, the read model is shaped exactly for what the UI or API consumer needs.

**Q: How do you handle eventual consistency in CQRS?**
A: Several strategies: (1) Accept it — most business scenarios (showing an order list) tolerate 1-2 second lag. (2) Version-check — the command returns an expected read model version; the client retries until the query side reaches that version. (3) Return the command result directly — the API response from the command includes the new state, so the client doesn't need to immediately re-query. (4) For strict consistency, route specific reads to the write DB, but document this as a deliberate exception.

**Q: Does CQRS require Event Sourcing?**
A: No. They pair naturally but are independent. You can use CQRS with a traditional state-based write DB that emits change events via the Outbox pattern. Event Sourcing (storing events as the system of record) makes CQRS easier because events are already the mechanism for syncing read models. But CQRS does not mandate Event Sourcing.

**Q: What are the operational challenges of CQRS?**
A: (1) Two codebases, two data stores to operate. (2) Read model rebuilds — when you change a projection, you need to replay all historical events to rebuild the read model from scratch; this can take hours. (3) Debugging is harder — a bug might be in the command handler, the event, or the projection. (4) Schema evolution — changing event structure requires versioned event handling. These costs are real; CQRS should only be applied where the scale/flexibility benefit clearly justifies the complexity.
