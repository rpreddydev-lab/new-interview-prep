================================================================
DISTRIBUTED TRANSACTIONS
================================================================

WHAT ARE DISTRIBUTED TRANSACTIONS?
------------------------------------
A transaction that spans multiple services, databases, or nodes,
where all operations must succeed or all must roll back.

The problem: Each service has its own database. You can't use
a single database transaction to coordinate them.

Example: E-commerce order placement
  1. Deduct inventory (Inventory Service DB)
  2. Charge credit card (Payment Service DB)
  3. Create order record (Order Service DB)
  
  These span 3 separate databases.
  All 3 must succeed, or all 3 must be rolled back.

TWO-PHASE COMMIT (2PC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Classic protocol for distributed atomic commit.

PARTICIPANTS:
  Coordinator: Orchestrates the commit protocol (usually the initiating service)
  Participants: All services involved in the transaction

PHASE 1 — PREPARE:
  Coordinator sends PREPARE to all participants.
  Each participant:
    - Executes its local operations (but doesn't commit)
    - Writes undo and redo logs (can commit OR rollback later)
    - Responds VOTE-COMMIT (ready) or VOTE-ABORT (failed)
    - Locks all resources for this transaction (holds them!)

PHASE 2 — COMMIT/ABORT:
  If all participants voted COMMIT:
    Coordinator sends COMMIT to all.
    Participants: commit, release locks, ACK.
  
  If any participant voted ABORT (or timed out):
    Coordinator sends ROLLBACK to all.
    Participants: rollback, release locks, ACK.

Timeline:
  Coordinator ──PREPARE──→ Part1, Part2, Part3
  Coordinator ←──VOTE────  Part1(COMMIT), Part2(COMMIT), Part3(COMMIT)
  Coordinator ──COMMIT───→ Part1, Part2, Part3
  Coordinator ←──ACK─────  Part1, Part2, Part3
  → Transaction complete

PROBLEMS WITH 2PC:
  1. BLOCKING PROTOCOL:
     If coordinator fails after sending PREPARE but before COMMIT,
     participants are stuck holding locks forever.
     They can't unilaterally decide (they voted COMMIT and must wait for coordinator).
     Fix: Timeout + coordinator recovery from WAL. But still blocks during recovery.
  
  2. SLOW:
     Two network round-trips + disk writes for logging.
     Latency = 2 × network round-trip + 2 × fsync
     For cross-region: 100ms × 2 = 200ms minimum.
  
  3. COORDINATOR SPOF:
     If coordinator crashes, participants are blocked.
     Need coordinator recovery and HA.

2PC IN PRACTICE:
  Used by: PostgreSQL distributed transactions (via extension), XA transactions
  (Java JTA), Google Spanner (but with TrueTime to reduce blocking)
  
  Avoid 2PC for: High-throughput systems, cross-region transactions
  Acceptable for: Low-volume critical transactions within a single DC

THREE-PHASE COMMIT (3PC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Adds a pre-commit phase to make 2PC non-blocking.

Phase 1: canCommit? (like 2PC prepare)
Phase 2: preCommit (coordinator tells participants to get ready to commit)
Phase 3: doCommit (actually commit)

If coordinator fails during phase 2, participants can safely commit
after timeout (they know coordinator had all yes votes).

Problem: Introduces risk of inconsistency during network partitions
(partition can cause some to commit, some to abort).
Rarely used in practice due to complexity and CAP issues.

SAGA PATTERN (Modern Alternative)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Breaks a distributed transaction into a sequence of local transactions.
Each local transaction publishes an event/message to trigger the next step.
If a step fails, execute compensating transactions to undo previous steps.

KEY CONCEPT: Compensating Transactions
  Each operation has a corresponding "undo" operation.
  
  Operation:     Reserve seat on flight A
  Compensation:  Release reserved seat on flight A
  
  Operation:     Charge credit card
  Compensation:  Refund credit card

SAGA TYPES:

1. CHOREOGRAPHY SAGA:
   No central coordinator. Each service listens for events and reacts.
   
   Order Service → publishes: OrderCreated
   Inventory Service hears: OrderCreated → reserves inventory → publishes: InventoryReserved
   Payment Service hears: InventoryReserved → charges payment → publishes: PaymentProcessed
   Shipping Service hears: PaymentProcessed → ships order → publishes: OrderShipped
   
   If Payment fails:
   Payment Service → publishes: PaymentFailed
   Inventory Service hears: PaymentFailed → releases reservation → publishes: InventoryReleased
   Order Service hears: InventoryReleased → marks order as failed
   
   Pros: Simple, no central bottleneck
   Cons: Hard to track overall state (where is this saga?), cascading events complex

2. ORCHESTRATION SAGA:
   A central saga orchestrator tells each participant what to do.
   Orchestrator tracks overall state.
   
   SagaOrchestrator:
     1. Tell InventoryService: reserve item 123
        Response: success/failure
     2. If success → Tell PaymentService: charge $50
        Response: success/failure
     3. If failure → Tell InventoryService: release item 123 (compensation)
   
   Pros:
   ✓ Easy to track overall state (orchestrator has full picture)
   ✓ Compensations are explicit and centralized
   ✓ Easier to debug and monitor
   
   Cons:
   ✗ Orchestrator is a central bottleneck/SPOF
   ✗ More coupling (services depend on orchestrator)

SAGA GUARANTEES:
  Atomicity-like: Either all succeed or compensations run (best-effort atomicity)
  Isolation MISSING: Other transactions can see partial state (no ACID isolation)
                     Must design for this: use "pending" status, not committed
  Eventual consistency: All compensations eventually run

IDEMPOTENCY CRITICAL:
  Network failures may cause retries of any step.
  All operations and compensations MUST be idempotent.
  Use idempotency keys: record which saga steps have already been executed.

OUTBOX PATTERN (ensures saga step + event publish is atomic):
  Don't publish events directly from saga steps.
  Instead: Write to a local "outbox" table in the same DB transaction.
  A separate process reads the outbox and publishes to message broker.
  Guarantees: If DB write succeeds → event will eventually be published.
  (See Messaging section for full detail.)

  INTERVIEW ANSWER:
  "For transactions spanning multiple services, I avoid 2PC because
   it's blocking and slow. Instead, I use the Saga pattern with an
   orchestrator. Each step executes a local transaction and publishes
   an event. If a step fails, compensating transactions undo previous
   steps. I combine this with the Outbox Pattern to ensure events are
   reliably published. The trade-off is losing isolation — I design
   around this by using 'pending' states and idempotent operations."

TCC PATTERN (Try-Confirm-Cancel)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TCC is a business-level distributed transaction protocol popular in
Java (Apache Seata, ByteTCC) and e-commerce (Alibaba, Ant Financial).

CONCEPT: Each operation is split into three explicit phases:
  TRY:     Reserve/check resources without final commitment.
           "Is it possible to do this? Hold the resources."
  CONFIRM: Actually execute and finalize the operation.
           "All services said TRY succeeded — go ahead."
  CANCEL:  Release held resources if anything failed.
           "Some TRY failed — undo all reservations."

EXAMPLE — Booking flight + hotel:
  TRY:
    FlightService.tryBook(seat=23A) → reserves seat, marks "PENDING"
    HotelService.tryBook(room=301) → reserves room, marks "PENDING"
  
  CONFIRM (if all TRYs succeeded):
    FlightService.confirm(seat=23A) → marks seat "CONFIRMED", charges card
    HotelService.confirm(room=301) → marks room "CONFIRMED", charges card
  
  CANCEL (if any TRY failed):
    FlightService.cancel(seat=23A) → releases seat, marks "AVAILABLE"
    HotelService.cancel(room=301) → releases room, marks "AVAILABLE"

IMPLEMENTATION REQUIREMENTS:
  1. ALL THREE phases must be idempotent (network retries).
  2. TRY must be reversible by CANCEL.
  3. CONFIRM must succeed if TRY succeeded (no new failures allowed).
  4. Services must maintain PENDING state until coordinator calls CONFIRM or CANCEL.
  5. Coordinator must persist state to survive crashes and retry.

RESOURCE ISOLATION IN TCC:
  Unlike 2PC which holds DB locks during PREPARE, TCC uses application-level
  reservation. Resources are "soft-locked" in PENDING state.
  
  Benefit: No long-held DB locks. Better throughput.
  Cost: Application must implement try/confirm/cancel logic explicitly.
        Business logic complexity increases significantly.

TCC vs SAGA:
┌───────────────┬───────────────────────────┬──────────────────────────┐
│ Property      │ TCC                       │ Saga                     │
├───────────────┼───────────────────────────┼──────────────────────────┤
│ Isolation     │ Better (soft-lock via TRY)│ None (other txns see it) │
│ Rollback      │ CANCEL (pre-planned)      │ Compensating transactions │
│ Complexity    │ High (3 phases per svc)   │ Medium (1 compensate/op)  │
│ Locking       │ App-level reservation     │ None                     │
│ Use case      │ Financial, travel booking │ Order fulfillment, general│
└───────────────┴───────────────────────────┴──────────────────────────┘

OUTBOX PATTERN + CDC (Change Data Capture)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

THE DUAL-WRITE PROBLEM:
  In a Saga or event-driven system, after a local DB transaction you must
  also publish an event to a message broker (Kafka, RabbitMQ).
  
  These two operations CANNOT be wrapped in a single ACID transaction
  (DB and message broker are separate systems).
  
  Failure scenario:
    1. Service writes to DB: SUCCESS
    2. Service publishes to Kafka: CRASH
    → DB has the record, but no event was published.
    → Downstream services never know this happened.
    → System is NOW INCONSISTENT.

OUTBOX PATTERN (solving dual-write):
  Instead of writing to Kafka directly, write the "to-be-published" event
  into a local OUTBOX TABLE in the SAME database transaction as the business data.
  
  This converts the dual-write (DB + Kafka) into a single ACID transaction
  (DB write + outbox row insertion = atomic).
  
  A separate OUTBOX POLLER process reads the outbox table and publishes to Kafka.
  After successful publish, marks the outbox row as published.
  
  Schema:
    CREATE TABLE outbox_events (
      id UUID PRIMARY KEY,
      aggregate_type VARCHAR(50),   -- e.g., 'Order'
      aggregate_id UUID,            -- e.g., order_id
      event_type VARCHAR(100),      -- e.g., 'OrderCreated'
      payload JSONB,                -- event body
      created_at TIMESTAMP,
      published_at TIMESTAMP        -- null = not yet published
    );
  
  Flow:
    ┌──────────────────────────────────────────┐
    │  BEGIN TRANSACTION                       │
    │    INSERT INTO orders (...)              │
    │    INSERT INTO outbox_events (...)       │
    │  COMMIT                                  │
    └──────────────────────────────────────────┘
                        ↓
    ┌──────────────────────────────────────────┐
    │  Outbox Poller (async)                   │
    │    SELECT * FROM outbox_events           │
    │      WHERE published_at IS NULL          │
    │    → Publish each event to Kafka         │
    │    → UPDATE outbox_events                │
    │        SET published_at = NOW()          │
    └──────────────────────────────────────────┘

  Guarantees:
    ✓ At-least-once delivery: poller retries until successful publish.
    ✓ Events are NEVER lost (they're in DB until published).
    ✓ Event publishing is ordered by created_at (per aggregate_id).

CDC-BASED OUTBOX (Change Data Capture):
  Instead of a polling query, use Debezium (CDC tool) to watch the
  database's binary log (WAL / binlog) for inserts into the outbox table.
  
  Debezium tails the WAL → detects outbox inserts → publishes to Kafka.
  
  Advantages over polling:
    - Lower latency (no polling interval delay)
    - No extra DB load from polling queries
    - Can capture deletes and updates too
  
  Stack: PostgreSQL WAL → Debezium (Kafka Connect) → Kafka → consumers
  
  Used by: Debezium (Red Hat), LinkedIn, Uber, many microservices adopters.

DISTRIBUTED LOCKING WITH REDIS REDLOCK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Sometimes you don't need a full transaction — you just need ONE process
to hold a resource at a time across services (e.g., run a cron job,
process a file, coordinate a resource).

SIMPLE REDIS LOCK (SET NX PX):
  // Acquire lock: SET key value NX PX <ttl_ms>
  // NX = only if Not eXists; PX = expire in milliseconds
  String lockValue = UUID.randomUUID().toString();  // unique per holder
  boolean acquired = redis.set("lock:job-processor", lockValue,
                               SetArgs.ifAbsent().px(30_000)); // 30s TTL
  
  if (!acquired) return;  // Another instance holds the lock
  
  try {
      doWork();
  } finally {
      // Release lock ONLY if still ours (compare-and-delete)
      // Use Lua script for atomicity:
      redis.eval(
          "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
          "  return redis.call('DEL', KEYS[1]) " +
          "else return 0 end",
          1, "lock:job-processor", lockValue
      );
  }
  
  Key: The unique lockValue prevents accidentally releasing another holder's lock.
  Key: TTL prevents lock being held forever if process crashes.

REDLOCK ALGORITHM (Multi-Node Redis):
  Problem: Single Redis node is a SPOF. If Redis crashes, lock is gone.
           If Redis is partitioned, two processes might both "acquire."
  
  Redlock uses N independent Redis nodes (typically 5).
  
  ACQUIRE:
    1. Record current time T1.
    2. Try to acquire lock on ALL N nodes sequentially (with short timeout per node).
    3. Count successful acquisitions.
    4. If acquired on MAJORITY (≥ N/2 + 1) AND total time < lock TTL:
       Lock is successfully held. Effective TTL = original TTL − time_elapsed.
    5. If not majority: release all acquired locks and fail.
  
  RELEASE:
    Release lock on ALL N nodes.
  
  Why majority? Even if some nodes are down or partitioned,
  no other process can acquire a majority simultaneously.
  (At most one process can hold majority at a time.)

  CONTROVERSY — Martin Kleppmann's critique:
    Redlock is NOT safe under these conditions:
    1. Clock skew: If a node's clock jumps, TTL expires prematurely,
       allowing a second holder before the first releases.
    2. Process pauses: GC pause after acquiring lock but before doing work
       can cause TTL to expire. Lock is "held" by a paused process.
    
    Kleppmann's recommendation: Use Raft-based locks (etcd, ZooKeeper)
    for strong guarantees. Use fencing tokens alongside any lock.
    
    Antirez (Redis author) disagrees, arguing Redlock is safe enough
    for most practical scenarios where perfect correctness isn't critical.

WHEN TO USE WHAT:
  Mutex (critical correctness):       etcd / ZooKeeper + fencing tokens
  Leader election:                    etcd / ZooKeeper ephemeral nodes
  Advisory lock (best-effort):        Redis SETNX (simple, single node)
  Cross-region lock (best-effort):    Redlock (use with caution)
  Database-level lock:                SELECT FOR UPDATE (same DB txn)
