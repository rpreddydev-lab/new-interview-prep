================================================================
CONSISTENCY PATTERNS IN DISTRIBUTED SYSTEMS
================================================================

HOW DISTRIBUTED SYSTEMS ACHIEVE CONSISTENCY
---------------------------------------------
This file covers implementation patterns for achieving various
consistency levels in practice.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 1: SINGLE LEADER (PRIMARY-REPLICA)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All writes go to the leader. Reads from replicas (with lag) or leader.
Consistency level depends on read routing and replication mode.

Strong consistency: Write to leader (sync replication), read from leader.
Eventual consistency: Write to leader (async replication), read from replica.

Used by: PostgreSQL, MySQL, Redis Sentinel, MongoDB (w/replica set)

Consistency guarantee: Linearizable if reads go to leader with sync replication.
Trade-off: Leader is write bottleneck; read scaling via replicas.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 2: QUORUM (Majority Vote)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

N replicas total. Write to W replicas, read from R replicas.
Strong consistency when: W + R > N (overlap guaranteed)

Example (N=3):
  W=2, R=2: W+R=4 > 3 → Strongly consistent (1 overlap guaranteed)
  W=1, R=1: W+R=2 ≤ 3 → Eventual consistency
  W=3, R=1: W+R=4 > 3 → Strong consistency (all must write; read from any)
  W=1, R=3: Same as above

SLOPPY QUORUM:
  DynamoDB and Cassandra: If a target node is down, another healthy
  node temporarily accepts the write (hinted handoff).
  When the down node recovers, the hint is delivered.
  Trades strict consistency for availability (AP behavior).

Used by: Cassandra, DynamoDB, Riak

Consistency guarantee: Configurable from eventual to strong.
Trade-off: Network round-trips to multiple nodes per operation.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 3: MULTI-VERSION CONCURRENCY CONTROL (MVCC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Database keeps multiple versions of each row.
Reads see a snapshot of data as of transaction start time.
Writes create new versions; old versions remain until garbage collected.

Benefits:
  - Readers don't block writers; writers don't block readers
  - Each transaction sees a consistent snapshot
  - Supports snapshot isolation and repeatable read isolation

PostgreSQL MVCC:
  Each row has xmin (transaction that created it) and xmax (transaction that deleted it).
  A transaction T with transaction ID TxID sees a row if:
    xmin ≤ TxID < xmax (row was created before T, not deleted before T)
  
  This gives each transaction a consistent "snapshot" without locking.

Snapshot Isolation:
  Every transaction works on a snapshot of the DB at its start time.
  Problem: Write skew (each transaction sees old values, both commit)
  Example: Two doctors both check if ≥1 doctor is on-call (yes), both go on leave.
           Now 0 doctors on-call → violated constraint.
  Fix: Serializable Snapshot Isolation (SSI) — PostgreSQL's serializable level.

Used by: PostgreSQL, MySQL InnoDB, Oracle, CockroachDB, MongoDB

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 4: CAUSAL CONSISTENCY WITH VECTOR CLOCKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Track causal dependencies between operations.
If event A caused event B, all nodes see A before B.

Vector Clock: Each node maintains a vector of counters.
{Node1: 3, Node2: 2, Node3: 1}

When Node1 sends a message to Node2:
  Increment Node1's counter: {Node1: 4, ...}
  Node2 receives: takes max of each component + increment own:
  Node2's new clock = {Node1: 4, Node2: 3, Node3: 1}

Comparison:
  Clock A < Clock B (B happened after A): all components of A ≤ B, at least one <
  Clock A || Clock B (concurrent): neither dominates → potential conflict

Used by: Riak, Amazon DynamoDB (version vectors), distributed logs

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 5: TWO-PHASE LOCKING (2PL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ensure serializability by locking rows.

Growing phase: Acquire locks (read/write) as needed.
Shrinking phase: Once any lock is released, no new locks can be acquired.

Types:
  Shared lock (S): Multiple readers can hold simultaneously.
  Exclusive lock (X): Only one writer; blocks all other S and X locks.

Problem: DEADLOCK — two transactions each hold a lock the other wants.
Fix: Deadlock detection (cycle detection in lock dependency graph) → abort one.
Fix: Deadlock prevention (always acquire locks in the same order).

Used by: Traditional RDBMS (PostgreSQL without SSI, MySQL InnoDB)
Note: MVCC largely replaced 2PL for read-write scenarios.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 6: SAGA (Distributed Consistency Without Distributed Transactions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use compensating transactions instead of distributed locking.
(See Microservices section for full detail.)

Sequence of local transactions, each publishing an event.
If a step fails, compensating transactions undo previous steps.

Example: Order → Reserve Inventory → Charge Payment → Ship
  If Charge Payment fails: Cancel Inventory Reservation (compensation)

Provides eventual consistency, not ACID. But scales well.

CONSISTENCY MODELS — THE FULL SPECTRUM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Strongest ←─────────────────────────────────────────────────→ Weakest

Linearizability > Sequential Consistency > Causal Consistency
> Session Guarantees > Eventual Consistency

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
CRITICAL DISTINCTION: LINEARIZABILITY vs SERIALIZABILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These are DIFFERENT things. Confusing them is a common interview mistake.

LINEARIZABILITY (a.k.a. Atomic Consistency, External Consistency):
  A SINGLE-OBJECT, SINGLE-OPERATION guarantee.
  Every operation appears to execute atomically at some point between
  its invocation and its completion — as if there's a single copy of data.
  
  Key property: Once a write completes and any client reads, they see
  the new value. No client ever sees a "stale" value after a completed write.
  
  Example:
    Client A writes X=1 (completes at t=10).
    Client B reads X at t=11 → must see X=1.  [linearizable]
    Client B reads X at t=11 → sees X=0.      [NOT linearizable]
  
  Cost: Requires coordination across replicas for every operation.
        Significantly reduces throughput and increases latency.
  
  Used by: etcd, ZooKeeper, Google Spanner, CockroachDB
  Implementation: Single-leader with sync replication + leader reads,
                  or consensus (Raft) with leader lease reads.

SERIALIZABILITY (a.k.a. Isolation Level: Serializable):
  A MULTI-OBJECT, MULTI-OPERATION (transaction) guarantee.
  The result of executing concurrent transactions is equivalent to
  some SERIAL (one-at-a-time) execution order.
  
  Key property: Transactions appear as if they ran sequentially.
  Does NOT require real-time ordering between transactions.
  
  Example:
    Tx1 reads account A, then Tx2 reads account A and writes it.
    Serializable allows Tx1's read to be "placed" before Tx2 in the
    serial order even if their real-time execution overlapped.
  
  Cost: Less expensive than linearizability in theory, but hard to implement
        efficiently. Often approximated with SSI or 2PL.
  
  Used by: PostgreSQL (with SERIALIZABLE level), MySQL InnoDB, CockroachDB

STRICT SERIALIZABILITY = SERIALIZABILITY + LINEARIZABILITY:
  Transactions execute serially AND respect real-time order.
  Most expensive guarantee. Spanner achieves this with TrueTime.
  Used in: Google Spanner, FoundationDB.

COMPARISON TABLE:
┌──────────────────────┬───────────────────┬────────────────────────┐
│ Property             │ Linearizability   │ Serializability        │
├──────────────────────┼───────────────────┼────────────────────────┤
│ Scope                │ Single object/op  │ Multi-object (txn)     │
│ Real-time ordering   │ YES (required)    │ NO (just serial equiv.)│
│ Multi-key atomicity  │ NO                │ YES                    │
│ Who uses it          │ CP datastores     │ RDBMS                  │
│ Implementation       │ Consensus/leader  │ 2PL, SSI               │
└──────────────────────┴───────────────────┴────────────────────────┘

INTERVIEW TIP: "Linearizability" is about a single value behaving as
if there's one copy. "Serializability" is about transactions having
ACID isolation. Spanner has both = "strict serializability."

SESSION GUARANTEES (Client-Centric Consistency)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Full system-wide consistency is expensive. Session guarantees provide
a weaker but practically useful set of per-client guarantees.
Defined by Terry et al. (1994). Used heavily in DynamoDB, Cassandra.

1. READ YOUR WRITES (RYW):
   After a client writes a value, it always reads its own write.
   
   WITHOUT RYW: Client posts a tweet → is routed to replica A.
                Client refreshes page → is routed to replica B (no sync yet).
                Client sees their tweet has disappeared. Confusing!
   
   WITH RYW: Client tracks its own write timestamp/token.
             Reads must return data at least as fresh as that token.
   
   Implementation: Client sends "read-after-token" in requests.
                   Server waits for replication to catch up before responding.
                   OR: Always route client to same replica (sticky session).
   
   Used by: DynamoDB consistent reads, Cassandra LOCAL_QUORUM, MongoDB sessions.

2. MONOTONIC READS:
   If a client reads a value, subsequent reads will never return OLDER values.
   
   WITHOUT MONOTONIC READS: Client reads post count = 500. Refreshes. Sees 490.
                             (Was routed to a lagging replica.)
   
   WITH MONOTONIC READS: Each read is at least as fresh as the previous read.
   
   Implementation: Client tracks highest version/timestamp seen.
                   Route subsequent reads to replicas that are at least that fresh.

3. MONOTONIC WRITES:
   Writes from a single client are applied in the order they were submitted.
   If W1 happens before W2 in a session, W1 is reflected before W2 globally.
   
   Violation example: Client sends W1=set counter to 10, W2=increment counter.
                      If W2 arrives before W1 → counter becomes 11, then 10. Wrong.

4. WRITES FOLLOW READS (WFR):
   If a client reads a value X, then writes Y, the write of Y is guaranteed
   to occur after the version of X that was read.
   
   This maintains causality: "I read X, therefore wrote Y" makes sense to others.
   If another client reads Y, they can also see the X that caused it.

PRAM CONSISTENCY (Pipeline RAM):
   Combines Monotonic Reads + Monotonic Writes + Reads Your Writes.
   All writes from a single process are seen by all other processes
   in the order they were issued. Does NOT require cross-client causality.

CAUSAL CONSISTENCY:
   Stronger than PRAM. Causally related operations are seen in causal order by ALL clients.
   Concurrent (causally unrelated) operations may be seen in different orders.
   
   Causal relationship: A → B if:
     - Same process: A happened before B
     - A is a write, B is a read of the same value
     - Transitivity: if A→B and B→C then A→C
   
   Implementation: Vector clocks or dependency tracking.
   Used by: MongoDB causal sessions, some versions of Riak.

ISOLATION LEVELS (Database Transaction Anomalies)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SQL standard defines isolation levels to prevent transaction anomalies.

ANOMALIES:
  DIRTY READ:     Reading uncommitted data from another transaction.
  NON-REPEATABLE READ: Same read returns different values within a transaction
                        (another transaction committed between reads).
  PHANTOM READ:   Same query returns different ROWS (another transaction
                  inserted/deleted rows between reads).
  WRITE SKEW:     Two transactions each read overlapping data, then write
                  based on what they read, violating a constraint.
                  (Example: two doctors both read "≥1 on call" → both go off call)
  LOST UPDATE:    Two transactions read-modify-write same value; one overwrites other.

ISOLATION LEVELS VS ANOMALIES:
┌───────────────────┬───────────┬──────────────┬───────────┬────────────┐
│ Level             │Dirty Read │Non-Rep. Read │Phantom    │Write Skew  │
├───────────────────┼───────────┼──────────────┼───────────┼────────────┤
│ READ UNCOMMITTED  │ Possible  │ Possible     │ Possible  │ Possible   │
│ READ COMMITTED    │ Prevented │ Possible     │ Possible  │ Possible   │
│ REPEATABLE READ   │ Prevented │ Prevented    │ Possible* │ Possible   │
│ SNAPSHOT ISOLATION│ Prevented │ Prevented    │ Prevented │ Possible   │
│ SERIALIZABLE      │ Prevented │ Prevented    │ Prevented │ Prevented  │
└───────────────────┴───────────┴──────────────┴───────────┴────────────┘
  * MySQL InnoDB REPEATABLE READ prevents phantoms via gap locks.

DEFAULT LEVELS BY DATABASE:
  PostgreSQL:  READ COMMITTED (serializable available)
  MySQL:       REPEATABLE READ (InnoDB default)
  Oracle:      READ COMMITTED
  SQL Server:  READ COMMITTED
  CockroachDB: SERIALIZABLE (always)
  Spanner:     SERIALIZABLE (always, via TrueTime)

├─────────────────────────────────┼─────────────────────────────────┤
│ ACID single-node                │ MVCC + 2PL (standard RDBMS)     │

INTERVIEW ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: "What's the difference between linearizability and serializability?"
A: "Linearizability is a single-object guarantee: each operation appears
    to execute instantaneously at some point between invocation and response,
    respecting real-time order. Serializability is a multi-object/transaction
    guarantee: concurrent transactions produce results equivalent to some serial
    execution. Linearizability is about a single value behaving like one copy;
    serializability is about transactions having ACID isolation. Strict
    serializability (Spanner) has both — very expensive."

Q: "What is 'read your writes' and when do you need it?"
A: "After a client writes, subsequent reads from that client must reflect
    the write — even if requests hit different replicas. Without it, users
    see their own updates disappear. I'd implement it by having clients
    include a write token, and servers waiting until replication catches up
    before responding. Alternatively, use sticky sessions or strong consistency
    for write paths."

Q: "What is write skew and how do you prevent it?"
A: "Write skew occurs when two transactions each read overlapping data,
    then write based on that read, violating a constraint that required
    both reads to be consistent. Classic example: two doctors both see
    '1 doctor on call', both decide to go off call — now 0 doctors on call.
    Prevention requires SERIALIZABLE isolation (SSI in PostgreSQL) or
    explicit SELECT FOR UPDATE to take locks before reading."
