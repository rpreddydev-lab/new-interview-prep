================================================================
LEADER ELECTION
================================================================

WHAT IS LEADER ELECTION?
--------------------------
In many distributed systems, one node needs to be designated as the
"leader" (or "primary") — the single node that:
  - Coordinates distributed transactions
  - Holds the singleton lock
  - Accepts all writes (in leader-based replication)
  - Runs scheduled jobs (only one instance should run a cron job)
  - Makes cluster-wide decisions

The challenge: Nodes fail. The network partitions. We need to
reliably agree on exactly one leader at any time.

WHY IS THIS HARD?
  - A node may appear dead (network partition) but actually still be alive.
  - If we elect two leaders ("split brain"), data corruption can result.
  - We must guarantee: at most one leader is active at any time (safety).
  - We also want: a new leader elected quickly when old one fails (liveness).

APPROACH 1: RAFT-BASED ELECTION (Best Practice)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use a Raft-based coordination service (etcd, ZooKeeper, Consul).
These provide strongly consistent primitives on top of consensus.

etcd-based leader election:
  1. Each node tries to acquire a lease key in etcd with a TTL.
  2. The first node to successfully create the key becomes leader.
  3. Leader periodically renews the lease (heartbeat to etcd).
  4. If leader fails to renew → lease expires → other nodes compete.
  5. First node to acquire the key becomes new leader.
  
  etcd provides compare-and-swap (CAS): only creates key if it doesn't exist.
  This is atomic; only one node wins even with concurrent attempts.
  
  Leader detection: Other nodes watch the key; on deletion → trigger re-election.
  
  Safety: etcd uses Raft internally → at most one node holds the key at any time.

Tools using etcd for leader election:
  Kubernetes controller manager, scheduler (use etcd leader election)
  Patroni (PostgreSQL HA manager)
  Various custom microservices

ZooKeeper ephemeral nodes:
  Similar to etcd leases.
  Nodes create ephemeral znodes. Ephemeral znodes auto-delete when session dies.
  Leader = node that created a specific znode.
  Others watch the znode; when it disappears → re-election.

APPROACH 2: BULLY ALGORITHM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Classic distributed systems algorithm (not used in production today).
Each node has a unique ID. Highest-ID node wins.

PROCESS:
  1. Node X notices leader has failed (timeout on heartbeat).
  2. X sends ELECTION message to all nodes with higher ID.
  3. If nobody responds → X becomes leader. Announces COORDINATOR message.
  4. If a higher-ID node responds → X backs off.
  5. Higher-ID node repeats the process until the highest-alive node wins.

Problems:
  ✗ O(N²) messages in worst case
  ✗ New highest node always wins, even if it was recently unreliable
  ✗ Doesn't handle partitions well

RING ELECTION:
  Nodes arranged in a logical ring.
  Election message passed around ring with candidate's ID.
  Each node appends its ID if higher than current candidate's ID.
  When message returns to initiator with a winner → announce coordinator.
  
  Better message complexity: O(N) messages.
  Still not used in production; Raft is better.

APPROACH 3: LEASE-BASED ELECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A lease is a time-limited authorization to act as leader.
The leader must continuously renew its lease.
If the leader fails to renew → lease expires → other nodes elect new leader.

CHUBBY (Google's distributed lock service):
  Cell of 5 replicas running Paxos consensus.
  Clients acquire leases on files (locks).
  Application services use Chubby for leader election and config.
  
  Lease length: typically 10-20 seconds.
  Leader must renew lease every ~5 seconds to avoid expiry.
  
  On lease expiry: other nodes race to acquire the lease.
  Guaranteed: no two nodes hold the same lock simultaneously.

KEY CHALLENGE: CLOCK SKEW
  Lease relies on wall-clock time. If leader's clock runs slow,
  it may continue acting as leader after lease expires.
  Solution: Leader should stop acting as leader slightly before lease
  expiry, giving time for a new one to be elected safely.

FENCING TOKENS (Preventing Stale Leaders from Corrupting Data)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

THE PROBLEM — Stale Leader (Split Brain in Practice):

  Timeline WITHOUT fencing tokens:

  t=0:  Leader A acquires lock (token=1). Begins processing.
  t=10: Leader A experiences a long GC pause (30 seconds).
  t=15: Followers detect A as dead (timeout). B wins election.
  t=16: Leader B acquires lock (token=2). Writes record X=100.
  t=40: Leader A resumes from GC. It has no idea 30 seconds passed.
        A still thinks it holds the lock (its in-memory state says so).
  t=41: Leader A writes record X=200 to storage. CORRUPTION.
        Storage now has X=200, but B already committed downstream
        actions based on X=100.

  This is split-brain. Both leaders believe they are legitimate.
  The fundamental problem: a process cannot distinguish "I was paused"
  from "I was running normally."

SOLUTION — Fencing Tokens:

  Every time a node acquires a lock/lease, the lock service returns
  a FENCING TOKEN: a monotonically increasing integer.

  Token 1 → issued to Leader A (first election)
  Token 2 → issued to Leader B (second election, after A's lease expired)
  Token 3 → issued to Leader C (third election), etc.

  The token is INCLUDED in every write request to the storage backend.
  The storage backend tracks the MAXIMUM token it has seen.
  It REJECTS any write carrying a token lower than the max seen.

  Timeline WITH fencing tokens:

  t=40: Leader A resumes. Tries to write X=200 with token=1.
        Storage has already seen token=2 (from Leader B).
        Storage REJECTS: "token 1 is stale. Current leader token is ≥ 2."
  t=40: Leader A's write fails. A must step down or crash.
        DATA IS SAFE. Only B's writes (token=2) were committed.

IMPLEMENTATION PATTERN:

  Lock service (etcd example):
    // Acquire lock — etcd returns a revision number (the fencing token)
    LeaseGrantResponse lease = etcdClient.leaseGrant(30); // 30s TTL
    TxnResponse txn = etcdClient.txn()
        .If(new Cmp("/leader-lock", Cmp.Op.VERSION, CmpTarget.VALUE, 0))
        .Then(Op.put("/leader-lock", nodeId, PutOption.newBuilder()
                                                       .withLeaseId(lease.getID())
                                                       .build()))
        .commit();
    long fencingToken = txn.getHeader().getRevision(); // monotonically increasing

  Storage backend (write path):
    // Every write includes the fencing token in the request header
    PUT /api/storage/record/X
    X-Fencing-Token: 2
    { "value": 100 }

    // Storage validates before accepting:
    if (request.fencingToken < this.maxSeenToken) {
        throw new StaleLeaderException("Rejected: token " +
            request.fencingToken + " < current " + this.maxSeenToken);
    }
    this.maxSeenToken = Math.max(this.maxSeenToken, request.fencingToken);
    // proceed with write

KEY INSIGHT — Why the stale leader can't fake a high token:
  The fencing token comes from the lock service, not from the leader itself.
  A stale leader can only use the token it was issued. It cannot forge a
  higher token — that would require winning a new election.

WHERE FENCING TOKENS ARE USED:
  etcd: lock revision number serves as fencing token.
  ZooKeeper: ephemeral node version / zxid serves as fencing token.
  Distributed file systems: HBase uses ZooKeeper epoch numbers.
  Custom distributed caches: Redis with WATCH + monotonic version.
  Database HA: Patroni uses fencing + STONITH to prevent stale PostgreSQL primary.

WHEN FENCING ISN'T ENOUGH:
  Fencing only helps if the storage backend enforces it.
  If the storage backend doesn't check tokens (e.g., a plain database
  with no token awareness), you need additional protection:
    - STONITH: physically power off the stale node.
    - Network-level fencing: firewall the stale node out.
    - Epoch-based lease: leader stops ITSELF before lease expires.

"How would you ensure only one instance of your job scheduler runs?"
  Answer: Use a distributed lock via etcd or Redis with SETNX + TTL.
          Instance acquiring the lock runs the job.
          Lock has TTL (auto-expires if instance crashes).
          Use fencing tokens to prevent stale leaders from causing damage.

"How does Kubernetes elect a leader for its controllers?"
  Answer: Uses etcd. The controller-manager and scheduler use a leader
          election library that acquires a lease object in etcd.
          Only the leader processes events; others stand by.
          On failure: lease expires in N seconds, others race to acquire.
