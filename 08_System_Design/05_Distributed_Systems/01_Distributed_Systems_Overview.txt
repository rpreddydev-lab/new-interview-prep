================================================================
DISTRIBUTED SYSTEMS — OVERVIEW
================================================================

WHAT IS A DISTRIBUTED SYSTEM?
-------------------------------
A distributed system is a collection of autonomous computing nodes
connected over a network, coordinating to appear as a single coherent system.

Examples: Internet, Google Search, Netflix, WhatsApp, Bitcoin

CORE CHALLENGES:
  1. Partial Failures:     Some nodes fail while others run fine.
                            (Unlike a single machine: it's either up or down)
  2. Unreliable Networks:  Packets can be delayed, dropped, reordered.
  3. No Global Clock:      Can't rely on wall-clock time for ordering.
  4. Concurrency:          Many requests arrive simultaneously.
  5. Consistency:          Keeping data in sync across nodes.
  6. Coordination:         Agreeing on who is the leader, what order events happened.

DISTRIBUTED SYSTEM PRINCIPLES:

1. DESIGN FOR FAILURE — Assume everything will fail eventually.
   Every node, every disk, every network link will eventually fail.
   Design systems that remain correct when components fail.

2. MAKE OPERATIONS IDEMPOTENT
   Clients retry on failure. Operations must be safe to execute twice.
   Use idempotency keys (UUID) so retries don't cause duplicates.

3. ACCEPT EVENTUAL CONSISTENCY WHERE APPROPRIATE
   Strong consistency is expensive (coordination overhead).
   For many use cases (social feeds, like counts), eventual consistency is fine.

4. PARTITION DATA TO SCALE
   Don't try to fit everything on one machine.
   Design sharding/partitioning from the start.

5. USE ASYNCHRONOUS COMMUNICATION WHERE POSSIBLE
   Synchronous calls create coupling and cascading failures.
   Message queues decouple producers from consumers.

6. OBSERVE EVERYTHING
   You can't debug what you can't see.
   Distributed tracing, structured logs, metrics, and alerting are essential.

FAILURE TAXONOMY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Understanding HOW a node fails matters as much as IF it fails.

CRASH-STOP FAILURE:
  Node crashes and never comes back. The simplest failure model.
  Easy to detect (no heartbeat). Common assumption in Raft/Paxos.
  Real world: kernel panic, power failure, OOM killer.

CRASH-RECOVERY FAILURE:
  Node crashes but can restart and rejoin. Must handle stale state.
  Uses persistent WAL (write-ahead log) to recover committed state.
  Real world: process restart, rolling deployments.

OMISSION FAILURE:
  Node is alive but drops some messages (network packet loss).
  Harder: node might be healthy but unreachable.
  Appears identical to crash from the outside — hence timeouts are hard.

BYZANTINE FAILURE (Arbitrary / Malicious):
  Node sends incorrect, inconsistent, or malicious responses.
  Can lie, send different values to different peers, behave randomly.
  Requires Byzantine Fault Tolerance (BFT) — used in blockchains (PBFT).
  Most datacenter systems assume non-Byzantine — too expensive otherwise.

PERFORMANCE DEGRADATION (Slow Node):
  Node responds, but very slowly (GC pause, overload, I/O bottleneck).
  From the outside looks like a failed node until timeout.
  Key insight: A slow node can be WORSE than a dead one.
               It holds locks, occupies connection pools, and causes cascades.

FUNDAMENTAL PROPERTIES: SAFETY vs LIVENESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SAFETY: "Nothing bad ever happens."
  - Only one leader at a time (no split brain)
  - Data is never lost after commit
  - Reads never see data that was never written

LIVENESS: "Something good eventually happens."
  - A new leader is eventually elected after a failure
  - A request eventually gets a response
  - Progress is eventually made

THE TENSION:
  During a network partition, you MUST choose: sacrifice safety OR liveness.
  CAP theorem formalizes this.

  CP systems (prefer Safety): Refuse to serve requests during partition.
                               Example: ZooKeeper, etcd, HBase.
  AP systems (prefer Liveness): Continue serving, accept potential stale/inconsistent data.
                                 Example: Cassandra, DynamoDB, CouchDB.

DISTRIBUTED SYSTEMS MENTAL MODELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. "A DISTRIBUTED SYSTEM IS A SYSTEM WHERE THE FAILURE OF A COMPUTER
    YOU DIDN'T EVEN KNOW EXISTED CAN RENDER YOUR OWN COMPUTER UNUSABLE."
    — Leslie Lamport

2. THERE IS NO NOW IN DISTRIBUTED SYSTEMS.
   No shared global clock. Events are ordered by causality, not timestamps.
   Two events with the same timestamp on different nodes have unknown order.

3. NETWORKS ARE BROKEN BY DEFAULT.
   Assume messages can be delayed, dropped, duplicated, or reordered.
   Design your protocol to be correct in ALL these cases.

4. TIMEOUTS ARE GUESSES.
   A timeout doesn't tell you if the remote node crashed, or is slow,
   or if your own network link is broken. You cannot know.
   Choose timeout carefully: too short → false failures; too long → slow recovery.

5. RETRIES CHANGE SEMANTICS.
   Without idempotency: retry may execute operation twice.
   With idempotency: retry is safe. Always design for retries.

FALLACIES OF DISTRIBUTED COMPUTING (Peter Deutsch, 1994)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  1. The network is reliable.
  2. Latency is zero.
  3. Bandwidth is infinite.
  4. The network is secure.
  5. Topology doesn't change.
  6. There is one administrator.
  7. Transport cost is zero.
  8. The network is homogeneous.

Every one of these assumptions is WRONG. Design accordingly.

  L1 cache access:               ~0.5 ns
  L2 cache access:               ~7 ns
  Main memory (DRAM) access:     ~100 ns
  SSD random read:               ~100 μs (100,000 ns)
  HDD seek:                      ~10 ms (10,000,000 ns)

  Cross-datacenter RTT:          ~50–100 ms (different region)
  Cross-continent RTT:           ~150–250 ms (US East ↔ Europe)

  TCP timeout default:           75 seconds (too slow for microservices!)
  Cassandra quorum:              N=3, W=2, R=2 → 1 node can fail
  Raft leader election timeout:  ~150–300 ms by default
  ZooKeeper session timeout:     ~2–10 seconds (typical)
  Kafka consumer group rebalance: ~3–10 seconds (typical)

  KEY RULE: If your operation crosses a datacenter boundary, you're
            paying 50-100ms in latency per hop. Design accordingly.

Q: "What is a distributed system and why is it hard?"
A: Collection of nodes coordinating over a network. Hard because:
   (1) partial failures — some nodes die while others run,
   (2) no global clock — can't rely on timestamps for ordering,
   (3) unreliable network — messages get dropped, delayed, reordered,
   (4) concurrency — must reason about interleavings across nodes.

Q: "What's the difference between safety and liveness?"
A: Safety = bad things never happen (no corruption, no split brain).
   Liveness = good things eventually happen (progress is made).
   During partitions, you must sacrifice one. CAP captures this.

Q: "Name some fallacies of distributed computing."
A: The network is reliable; latency is zero; bandwidth is infinite;
   the network is secure. All false. Design assuming network unreliability.
