================================================================
QUORUM AND THE NWR MODEL
================================================================

WHAT IS THE NWR MODEL?
-----------------------
The NWR model is a framework for reasoning about consistency vs
availability trade-offs in leaderless/quorum-based distributed systems.

N: Total number of replicas storing a piece of data.
W: Number of replicas that must acknowledge a WRITE for it to succeed.
R: Number of replicas queried on a READ (must agree/merge).

Defined by: Amazon Dynamo (2007). Used by: Cassandra, DynamoDB, Riak.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
THE CORE RULE: W + R > N = STRONG CONSISTENCY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

If W + R > N, at least ONE replica must have participated in BOTH
the most recent write AND the current read. That overlap guarantees
the read sees the latest write.

MATHEMATICAL INSIGHT:
  Write touches W nodes. Read touches R nodes.
  If W + R > N: the write and read sets must overlap (pigeonhole principle).
  Overlap ≥ (W + R) - N nodes.

  N=3 examples:
  ┌──────┬──────┬───────────┬─────────────────────────────────────┐
  │  W   │  R   │  W+R > N? │  Consistency                        │
  ├──────┼──────┼───────────┼─────────────────────────────────────┤
  │  1   │  1   │  2 ≤ 3    │  Eventual (no overlap guaranteed)   │
  │  1   │  3   │  4 > 3    │  Strong (all replicas read)         │
  │  3   │  1   │  4 > 3    │  Strong (all replicas must ack)     │
  │  2   │  2   │  4 > 3    │  Strong (1 overlap guaranteed)      │
  │  2   │  1   │  3 = 3    │  NOT strong (no overlap guaranteed) │
  │  1   │  2   │  3 = 3    │  NOT strong                         │
  └──────┴──────┴───────────┴─────────────────────────────────────┘

CHOOSING W AND R: TUNING TRADE-OFFS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STANDARD CONFIGURATION (N=3, W=2, R=2):
  ✓ Tolerates 1 node failure for reads AND writes.
  ✓ Strong consistency (W+R=4 > 3).
  Trade-off: Both reads and writes need majority ACK (latency = 2nd fastest node).

WRITE-HEAVY OPTIMIZATION (N=3, W=1, R=3):
  ✓ Writes are fast (1 ACK needed).
  ✗ Reads must contact all 3 nodes (slow reads, high availability cost).
  ✓ Strong consistency technically (1+3=4>3), but slow reads in practice.
  Use: Write-heavy analytics pipelines where reads are rare.

READ-HEAVY OPTIMIZATION (N=3, W=3, R=1):
  ✓ Reads are fast (ask any 1 replica).
  ✗ Writes need all 3 ACKs (slow writes, low write availability).
  ✓ Strong consistency (3+1=4>3).
  Use: Read-heavy reference data that changes rarely (catalog, config).

AVAILABILITY OVER CONSISTENCY (N=3, W=1, R=1):
  ✓ Max availability: any 1 node can serve reads and writes.
  ✗ No overlap guarantee → stale reads possible.
  ✓ Tolerates up to N-1 failures.
  Use: Social media likes, view counts, anything eventually consistent.

DURABILITY FOCUS (N=3, W=3, R=1):
  ✓ Write confirmed by ALL replicas (zero data loss).
  ✗ If any replica is down, write FAILS (low write availability).
  Use: Financial audit logs, ledgers where durability > availability.

FAULT TOLERANCE: HOW MANY FAILURES CAN BE TOLERATED?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Write failure tolerance: N - W nodes can fail (still reach W).
Read failure tolerance:  N - R nodes can fail (still reach R).

For N=3, W=2, R=2:
  Write tolerates: 3 - 2 = 1 failure.
  Read tolerates:  3 - 2 = 1 failure.
  → Can survive 1 node failure for both reads and writes.

For N=5, W=3, R=3:
  Write tolerates: 5 - 3 = 2 failures.
  Read tolerates:  5 - 3 = 2 failures.
  Strong consistency (W+R=6>5).

CASSANDRA CONSISTENCY LEVELS (NWR in Practice)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Cassandra exposes NWR as named consistency levels (with N typically 3):

┌──────────────────┬───────────────────────────────────────────────┐
│ Consistency Level│ Meaning                                       │
├──────────────────┼───────────────────────────────────────────────┤
│ ANY              │ W=1 to any node (even coordinator) — max avail│
│ ONE              │ W=1 or R=1 to any replica                     │
│ TWO              │ W=2 or R=2 replicas must respond              │
│ THREE            │ W=3 or R=3 replicas must respond              │
│ QUORUM           │ W or R = ⌊N/2⌋ + 1 (majority)                │
│ LOCAL_QUORUM     │ Quorum within local datacenter only           │
│ EACH_QUORUM      │ Quorum in each datacenter (multi-DC write)    │
│ ALL              │ W=N or R=N (all replicas must respond)        │
│ LOCAL_ONE        │ ONE, but prefer local DC replica              │
│ SERIAL           │ Linearizable reads via Paxos (Lightweight Txn)│
│ LOCAL_SERIAL     │ SERIAL within local DC                        │
└──────────────────┴───────────────────────────────────────────────┘

ACHIEVING STRONG CONSISTENCY IN CASSANDRA:
  Both reads and writes at QUORUM (W=QUORUM, R=QUORUM):
  N=3: W=2, R=2. W+R=4>3. ✓ Strongly consistent.
  
  Or: Write=ALL, Read=ONE (fast reads, slow writes).
  Or: Write=ONE, Read=ALL (fast writes, slow reads — rarely used).

ACHIEVING STRONG CONSISTENCY ACROSS DATACENTERS:
  Use EACH_QUORUM for writes (write to quorum in each DC).
  Use LOCAL_QUORUM for reads within your local DC.
  This gives consistency within a DC, eventual across DCs.

SLOPPY QUORUM AND HINTED HANDOFF
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM: A target replica is down during a write. Strict quorum
would reject the write (can't reach W nodes in the "preference list").

SLOPPY QUORUM (DynamoDB, Cassandra):
  Instead of failing, write to a DIFFERENT available node not in
  the preference list. That node holds the write as a "hint."
  
  When the original target recovers, the hint is delivered.
  This is called HINTED HANDOFF.

BENEFIT: Higher write availability. System accepts writes even when
  designated replicas are temporarily unavailable.

COST: During the outage, a strict quorum read may miss the write
  (it was on a non-preference node, not counted in W+R overlap).
  
  → Sloppy quorum is NOT strongly consistent. It's an AP tradeoff.
    It sacrifices consistency for availability during partial failures.

CASSANDRA DEFAULT: Sloppy quorum is ON by default.
  To disable: set hinted_handoff_enabled = false (not recommended).

READ REPAIR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When a read contacts R replicas and finds inconsistencies (different
values or different timestamps), it can repair the stale replicas.

SYNCHRONOUS READ REPAIR:
  Wait for repair to complete before returning to client.
  Increases read latency. Guarantees convergence.
  Cassandra: read_repair_chance=1.0 forces this on every read.

ASYNCHRONOUS READ REPAIR (Background):
  Return result to client immediately.
  Trigger repair in background. Replica converges eventually.
  Default in Cassandra (read_repair_chance=0.1 means 10% of reads trigger it).

READ REPAIR IS NOT A SUBSTITUTE FOR QUORUM:
  Even with repair, if a node is down and comes back with stale data,
  a non-quorum read might return the stale value before repair runs.

LIMITATIONS OF THE NWR MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CONCURRENT WRITES TO SAME KEY:
   Even with W+R>N, two concurrent writes can create conflicts.
   The coordinator writes to W replicas, but if two coordinators
   write to different subsets, the surviving "winner" depends on
   timestamp (LWW) or conflict resolution strategy.
   
   This is NOT linearizable even with W+R>N.
   True linearizability requires consensus (Raft/Paxos), not just quorum.

2. SLOPPY QUORUM BREAKS GUARANTEES:
   As noted above, sloppy quorum drops the W+R>N guarantee.

3. TAIL LATENCY:
   Quorum reads contact R replicas and wait for all R to respond.
   Slowest of R replicas determines latency.
   Mitigation: Hedged requests (send to R+1, use fastest R responses).

4. CLOCK DEPENDENCY (LWW):
   In leaderless systems, resolving concurrent writes uses timestamps.
   Clock skew → wrong winner. Use logical clocks when possible.

INTERVIEW ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: "How do you configure Cassandra for strong consistency?"
A: "Use QUORUM for both reads and writes. With N=3, QUORUM means
    W=2 and R=2. Since W+R=4>3, at least one replica participates
    in both the write and the read, guaranteeing the latest value is seen.
    Caveat: sloppy quorum must be considered — if hinted handoff kicks in,
    the overlap guarantee can break during node failures."

Q: "Explain the NWR model and when to use W=1, R=N."
A: "NWR is a tunable consistency model for leaderless systems.
    W=number of write ACKs, R=replicas queried on read, N=total replicas.
    W+R>N gives strong consistency.
    W=1, R=N means writes are fast (any node ACKs), reads check all nodes.
    Use for write-heavy workloads with rare but critical reads,
    or read-heavy reference data that rarely changes."

Q: "What is hinted handoff and what does it sacrifice?"
A: "Hinted handoff means when a target replica is down, a write is
    temporarily stored on another node as a 'hint' and delivered later.
    It sacrifices strict quorum guarantees — during the outage, a quorum
    read might miss the write since it's on a non-preference node.
    It trades consistency for availability (AP behavior)."
