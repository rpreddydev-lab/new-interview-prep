================================================================
HIGH-LEVEL DESIGN (HLD) vs LOW-LEVEL DESIGN (LLD)
================================================================

OVERVIEW
---------
System design interviews can be broadly split into two categories:
  • HLD (High-Level Design) — Architecture and component selection
  • LLD (Low-Level Design)  — Class design, DB schema, algorithms

Both are crucial for senior engineering roles. Understanding the
difference and knowing when to go deep on each is key to acing interviews.

HIGH-LEVEL DESIGN (HLD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION
-----------
HLD describes the system architecture at a macro level — what major
components exist and how they interact. It focuses on:
  - System boundaries
  - Component responsibilities
  - Data flow between components
  - Technology choices (why Kafka vs RabbitMQ, why Redis vs Memcached)
  - API contracts (external-facing)
  - Scalability and availability strategies

WHEN IS HLD USED?
------------------
  - Designing a new product feature or system from scratch
  - Planning microservice decomposition
  - Architectural decision records (ADRs)
  - Communicating with non-engineering stakeholders

HLD ARTIFACTS
--------------
1. Architecture Diagram
   - Boxes representing services/components
   - Arrows representing data flow direction
   - Annotations for protocols (REST, gRPC, Kafka)
   - Cloud regions/zones for HA

2. API Design (External Contracts)
   - REST endpoints: GET /users/{id}, POST /tweets
   - Request/Response schemas (high level, not full JSON schema)
   - Rate limits, authentication requirements

3. Data Flow Diagram
   - How data moves from user request → storage → response
   - Read path vs write path (often different!)
   - Async vs sync steps

4. Capacity Estimation Summary
   - DAU (Daily Active Users)
   - QPS (Queries per Second) for reads and writes
   - Storage requirements per year

HLD EXAMPLE: URL Shortener
---------------------------
Components:
  Client → Load Balancer → API Gateway
         → Shortener Service → Redis Cache → MySQL DB
         → Analytics Service → Kafka → ClickHouse

Read Path:  GET /{shortCode} → LB → API GW → Shortener
                             → Check Redis → if miss: MySQL
                             → Return 301/302 Redirect

Write Path: POST /shorten → LB → API GW → Shortener
                         → Generate unique code → Store in MySQL
                         → Cache in Redis → Return short URL

HLD KEY QUESTIONS TO ANSWER
-----------------------------
□ How many requests per second can the system handle?
□ How does the system scale horizontally?
□ Where is the data stored and how is it replicated?
□ What happens if a service goes down?
□ How is the system secured?
□ How is the system monitored?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LOW-LEVEL DESIGN (LLD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION
-----------
LLD dives into the implementation details of individual components:
  - Class diagrams and relationships (OOP principles)
  - Database schema (tables, indexes, foreign keys)
  - Algorithm selection and complexity
  - Design patterns applied (Factory, Observer, Strategy, etc.)
  - Concrete API method signatures
  - Edge cases and error handling

WHEN IS LLD USED?
------------------
  - Implementing a single component or service
  - Code reviews and detailed technical discussions
  - Designing reusable libraries or frameworks
  - When asked to write code during a system design round

LLD ARTIFACTS
--------------
1. Class Diagram (UML)
   - Classes with attributes and methods
   - Inheritance, composition, aggregation relationships
   - Interfaces and abstract classes

2. Database Schema
   - Table names, column names, data types
   - Primary keys, foreign keys, indexes
   - Normalization level (1NF, 2NF, 3NF, BCNF)

3. Sequence Diagram
   - Order of method calls between objects/services
   - Shows timing and dependencies

4. Algorithm Design
   - Pseudocode for critical logic
   - Time and space complexity analysis

LLD EXAMPLE: Parking Lot System
---------------------------------
Classes:
  ParkingLot (Singleton)
    - floors: List<Floor>
    - getAvailableSpot(vehicleType): ParkingSpot
    - parkVehicle(vehicle): Ticket
    - unparkVehicle(ticket): Payment

  Floor
    - floorNumber: int
    - spots: List<ParkingSpot>
    - getAvailableSpots(type): List<ParkingSpot>

  ParkingSpot (abstract)
    - spotId: String
    - isAvailable: boolean
    - assignVehicle(vehicle): void
    - removeVehicle(): void
    Subclasses: CompactSpot, LargeSpot, HandicappedSpot

  Vehicle (abstract)
    - licensePlate: String
    - vehicleType: VehicleType
    Subclasses: Car, Truck, Motorcycle

  Ticket
    - ticketId: String
    - vehicleId: String
    - spotId: String
    - entryTime: DateTime
    - exitTime: DateTime

  Payment (Strategy Pattern)
    - processPayment(ticket): Receipt
    Strategies: HourlyPayment, DailyPayment, MonthlyPass

DB Schema:
  parking_spots(spot_id PK, floor_id FK, type, is_available)
  vehicles(vehicle_id PK, license_plate UNIQUE, type)
  tickets(ticket_id PK, vehicle_id FK, spot_id FK, entry_time, exit_time)
  payments(payment_id PK, ticket_id FK, amount, method, paid_at)

LLD KEY QUESTIONS TO ANSWER
-----------------------------
□ What design patterns are applicable?
□ How do you handle concurrency? (two cars booking same spot)
□ How do you ensure SOLID principles?
□ What are the database indexes needed?
□ What is the time complexity of core operations?
□ How do you handle edge cases (null values, invalid input)?

SOLID PRINCIPLES (Critical for LLD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

S - Single Responsibility Principle
    A class should have ONE reason to change.
    Bad:  UserService handles auth + email + DB operations
    Good: Separate AuthService, EmailService, UserRepository

O - Open/Closed Principle
    Open for extension, closed for modification.
    Bad:  if (shape == "circle") area = π*r² else if (shape == "rect")...
    Good: Shape interface with area() method; add shapes without changing code

L - Liskov Substitution Principle
    Subtypes must be substitutable for their base types.
    Bad:  Square extends Rectangle but breaks setWidth/setHeight semantics
    Good: Ensure subclass behavior is consistent with base class contract

I - Interface Segregation Principle
    No client should be forced to depend on methods it doesn't use.
    Bad:  Fat interface: Animal has fly(), swim(), run() — not all animals do all
    Good: Flyable, Swimmable, Runnable interfaces — implement as needed

D - Dependency Inversion Principle
    Depend on abstractions, not concretions.
    Bad:  OrderService directly instantiates MySQLOrderRepository
    Good: OrderService depends on IOrderRepository interface; inject implementation

COMMON DESIGN PATTERNS (LLD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Creational Patterns:
  Singleton      → Single instance (DB connection pool, config)
  Factory        → Create objects without specifying exact class
  Builder        → Step-by-step object construction (complex objects)
  Prototype      → Clone existing objects

Structural Patterns:
  Adapter        → Wrap incompatible interface
  Decorator      → Add functionality without changing class
  Facade         → Simplified interface to complex subsystem
  Proxy          → Placeholder for another object (lazy loading, auth)
  Composite      → Tree structures (file system, org chart)

Behavioral Patterns:
  Observer       → Event notification (pub-sub within app)
  Strategy       → Interchangeable algorithms (sorting, payment)
  Command        → Encapsulate requests as objects (undo/redo)
  State          → Object behavior changes with state (vending machine)
  Iterator       → Traverse collections without exposing internals
  Template Method → Define algorithm skeleton, defer steps to subclasses
  Chain of Responsibility → Pass request along handler chain

INTERVIEW TIPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For HLD Interviews:
  ✓ Always start with requirements (functional + non-functional)
  ✓ Draw boxes and arrows, not code
  ✓ Discuss trade-offs at each decision point
  ✓ Address scale explicitly with numbers
  ✓ Cover both read and write paths
  ✓ Mention monitoring and alerting

For LLD Interviews:
  ✓ Ask: "Should I focus on any particular component?"
  ✓ Start with identifying entities and their relationships
  ✓ Apply OOP principles (mention SOLID by name)
  ✓ Consider concurrency issues (race conditions, locks)
  ✓ Define interfaces before implementations
  ✓ Name relevant design patterns you are using and why

Transition from HLD to LLD:
  "Now that we have the high-level architecture, let me dive deeper
   into [component X] — I'll define the classes, their relationships,
   and the DB schema..."
