================================================================
DNS — DOMAIN NAME SYSTEM
================================================================

WHAT IS DNS?
-------------
DNS is the internet's phone book. It translates human-readable
domain names (api.example.com) into machine-readable IP addresses
(93.184.216.34).

Without DNS:
  You would need to remember IP addresses for every service.
  Changing server IPs would break all clients instantly.

With DNS:
  Clients always lookup the name → get current IP → connect.
  Server can change IPs by updating DNS record.
  DNS enables load balancing, failover, geo-routing.

DNS RESOLUTION — STEP BY STEP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Query: User types "api.example.com" in browser.

STEP 1: Browser DNS Cache
  Browser checks its own DNS cache first.
  Recent lookups are cached based on TTL.
  Hit → return IP immediately. Miss → go to step 2.

STEP 2: OS DNS Cache / Hosts File
  OS checks /etc/hosts (local overrides).
  OS checks its own resolver cache.
  Hit → return. Miss → go to step 3.

STEP 3: Recursive Resolver (ISP or Google/Cloudflare)
  OS sends query to configured DNS server (8.8.8.8, 1.1.1.1, or ISP's).
  This is the Recursive Resolver — does the heavy lifting.
  
  If resolver has it cached → return immediately.
  Otherwise → resolver queries root servers.

STEP 4: Root Name Servers (13 root server clusters worldwide)
  Resolver asks: "Who knows about .com?"
  Root server returns TLD Name Server address for .com.

STEP 5: TLD (Top-Level Domain) Name Servers
  Resolver asks .com TLD server: "Who knows about example.com?"
  TLD server returns the Authoritative Name Server for example.com.
  (This is managed by the domain registrar, e.g., GoDaddy, Route 53)

STEP 6: Authoritative Name Server
  Resolver asks example.com's authoritative server:
    "What is the IP for api.example.com?"
  Authoritative server returns the A record: 93.184.216.34

STEP 7: Response Chain
  Resolver caches the result (for TTL duration).
  Returns IP to OS → OS returns to browser.
  Browser connects to 93.184.216.34.

Total time: first lookup ~50-150ms (all hops)
  Subsequent: ~0ms (cached everywhere)

DNS RECORD TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Record:
  Maps hostname → IPv4 address.
  api.example.com → 93.184.216.34

AAAA Record:
  Maps hostname → IPv6 address.
  api.example.com → 2606:2800:220:1:248:1893:25c8:1946

CNAME Record (Canonical Name):
  Maps one name → another name (alias).
  www.example.com → example.com  (CNAME)
  Used for CDN: assets.example.com → d123.cloudfront.net
  Note: CNAME can't be on root domain (apex), use ALIAS/ANAME or A record.

MX Record:
  Mail eXchange — where to deliver email for this domain.
  example.com MX → mail.example.com (with priority)

TXT Record:
  Arbitrary text. Used for:
  - Domain verification (Google Search Console, SSL)
  - SPF (email anti-spoofing)
  - DKIM keys

NS Record (Name Server):
  Specifies the authoritative name servers for the domain.
  example.com NS → ns1.awsdns-01.com

SRV Record:
  Service location record (host + port + priority + weight).
  Used by Kubernetes, gRPC, some microservice discovery.
  _http._tcp.example.com SRV → 10 20 8080 api.example.com

PTR Record:
  Reverse DNS — IP address → hostname.
  Used for spam filtering, network logging.

TTL (TIME TO LIVE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TTL = how long (in seconds) resolvers/clients cache a DNS record.

Low TTL (30–60s):
  Pro: Changes propagate quickly (failover, blue-green deployments).
  Con: More DNS queries, higher load on name servers.
  Use for: records that change often, disaster recovery scenarios.

High TTL (3600–86400s):
  Pro: Fewer DNS queries, less load, faster for clients.
  Con: Changes are slow to propagate — old IP cached for hours.
  Use for: stable infrastructure that rarely changes.

BEST PRACTICE for failover:
  Pre-reduce TTL to 60s 24hrs BEFORE planned change.
  Make the DNS change.
  After confident, raise TTL back to 3600.

DNS-BASED LOAD BALANCING AND GEO-ROUTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DNS ROUND-ROBIN LOAD BALANCING:
  Return multiple A records for one name.
  api.example.com → 10.0.0.1, 10.0.0.2, 10.0.0.3
  DNS resolver returns them in rotation.
  
  Limitations:
  - No health checking — dead IPs still returned
  - Clients cache one IP and stick to it (TTL bypass)
  - No session affinity control
  - Crude — no weighted distribution

WEIGHTED DNS (AWS Route 53):
  Route 70% of traffic to v1 (weight=70), 30% to v2 (weight=30).
  Used for canary deployments, A/B testing, gradual rollouts.

LATENCY-BASED ROUTING (AWS Route 53):
  Route client to nearest region based on measured latency.
  User in Tokyo → routed to ap-northeast-1 (not us-east-1).

GEOLOCATION ROUTING:
  Route based on client's geographic location.
  European users → EU servers (data residency compliance, GDPR).

HEALTH-CHECK-BASED FAILOVER:
  Route 53 continuously health-checks your endpoints.
  If primary fails health check → automatically switch to failover IP.
  Combined with low TTL: failover in ~30–60 seconds.

DNS IN MICROSERVICES / KUBERNETES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kubernetes uses DNS for service discovery:
  Every Service gets a DNS name: <service-name>.<namespace>.svc.cluster.local
  CoreDNS runs inside the cluster as the DNS server.
  
  order-service.default.svc.cluster.local → ClusterIP of order-service
  
  Pods don't need to know IPs — use DNS names:
  http://payment-service/api/charge

Headless Services (clusterIP: None):
  Returns individual Pod IPs (not a VIP).
  Allows client-side load balancing (e.g., Kafka clients, Cassandra).

INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Your service changes its IP. How long until all clients use the new IP?
A: At most TTL seconds. If TTL is 3600s (1 hour), some clients may
   use the old IP for up to an hour. Mitigation: pre-lower TTL before change,
   keep old IP working during transition, use CNAME to an LB that you control.

Q: Can you use DNS for load balancing?
A: Yes (DNS round-robin) but it's crude. No health checking, clients
   cache IPs ignoring TTL, no fine-grained control. Production systems
   use a real load balancer (Nginx, HAProxy, AWS ALB) and DNS points to
   the LB's stable IP. For global traffic distribution, use Route 53
   latency-based or geolocation routing.

Q: Why does the DNS query use UDP?
A: DNS queries are small (< 512 bytes for standard queries) and latency
   is critical. UDP saves the TCP 3-way handshake overhead. For large
   responses (e.g., many records), DNS falls back to TCP.

Q: How is service discovery different from DNS in microservices?
A: DNS is static (updated manually or via IaC). Service registries
   (Consul, Eureka, Kubernetes services) are dynamic — services
   register/deregister themselves, enabling real-time health-aware routing.
   Kubernetes uses DNS backed by a dynamic registry (CoreDNS + etcd).
