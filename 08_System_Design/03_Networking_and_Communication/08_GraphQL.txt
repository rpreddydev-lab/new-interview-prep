================================================================
GRAPHQL — FLEXIBLE API QUERY LANGUAGE
================================================================

WHAT IS GRAPHQL?
-----------------
GraphQL is a query language for APIs and a server-side runtime
for executing those queries. Created by Facebook (2012), open-sourced 2015.

Core idea: Client asks for EXACTLY what it needs, nothing more, nothing less.
  - One endpoint: POST /graphql (not many REST endpoints)
  - Client defines the shape of the response
  - Strongly typed schema is the contract

GRAPHQL vs REST — THE CORE PROBLEMS GRAPHQL SOLVES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

OVER-FETCHING (REST problem):
  GET /api/users/123 returns:
  { id, name, email, phone, address, createdAt, roles, preferences, ... }
  
  Mobile app only needs: id, name.
  Wasted data = wasted bandwidth = slower on mobile.
  
  GraphQL: client asks for ONLY { id name } → gets only { id name }.

UNDER-FETCHING / N+1 REQUESTS (REST problem):
  To show a user's posts with each post's author's name:
  GET /api/users/123/posts  → 10 posts
  GET /api/users/1           → author of post 1
  GET /api/users/2           → author of post 2
  ... (10 more requests)
  Total: 11 HTTP round trips.
  
  GraphQL: single query fetches user + posts + each post's author in one call.

GRAPHQL SCHEMA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Schema = the contract between client and server (SDL — Schema Definition Language):

  type User {
    id: ID!
    name: String!
    email: String!
    posts: [Post!]!
    createdAt: String!
  }
  
  type Post {
    id: ID!
    title: String!
    content: String
    author: User!
    publishedAt: String
  }
  
  type Query {
    user(id: ID!): User
    posts(limit: Int, offset: Int): [Post!]!
  }
  
  type Mutation {
    createPost(title: String!, content: String!): Post!
    deletePost(id: ID!): Boolean!
  }
  
  type Subscription {
    postAdded: Post!
  }

! = non-nullable. [Post!]! = non-null list of non-null Posts.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OPERATIONS: QUERY, MUTATION, SUBSCRIPTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QUERY (read data):
  query GetUserWithPosts {
    user(id: "123") {
      id
      name
      posts {
        id
        title
        author {
          name
        }
      }
    }
  }
  
  Response:
  {
    "data": {
      "user": {
        "id": "123",
        "name": "Alice",
        "posts": [
          { "id": "p1", "title": "Hello World", "author": { "name": "Alice" } }
        ]
      }
    }
  }

MUTATION (write data):
  mutation CreatePost($title: String!, $content: String!) {
    createPost(title: $title, content: $content) {
      id
      title
    }
  }
  
  Variables: { "title": "My Post", "content": "..." }

SUBSCRIPTION (real-time):
  subscription OnNewPost {
    postAdded {
      id
      title
      author { name }
    }
  }
  
  Server pushes events over WebSocket when new post added.

RESOLVERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each field in the schema is resolved by a function called a RESOLVER.

  // Java (using graphql-java or Netflix DGS):
  @DgsComponent
  public class UserDataFetcher {
    @DgsQuery
    public User user(@InputArgument String id) {
      return userService.findById(id);
    }
  }
  
  @DgsComponent
  public class PostDataFetcher {
    @DgsData(parentType = "User", field = "posts")
    public List<Post> posts(DgsDataFetchingEnvironment env) {
      User user = env.getSource();
      return postService.findByUserId(user.getId());
    }
  }

Resolution is recursive: GraphQL engine traverses the query tree,
calling the appropriate resolver for each field.

THE N+1 PROBLEM IN GRAPHQL (DataLoader)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem:
  Query: 10 posts, each with their author.
  Naive resolver: fetches posts (1 DB call), then for each post fetches
  the author (10 more DB calls) = N+1 queries.

Solution: DATALOADER (batching + caching per request):
  Instead of fetching each author individually, DataLoader:
  1. Collects all author IDs requested in a single execution tick
  2. Batches them into ONE database call: SELECT * FROM users WHERE id IN (...)
  3. Maps results back to each post
  
  1 DB call for 10 posts + 1 DB call for all unique authors = 2 total.
  
  // Java with Netflix DGS:
  @DgsDataLoader(name = "users")
  public class UsersDataLoader implements BatchLoader<String, User> {
    public CompletionStage<List<User>> load(List<String> ids) {
      return CompletableFuture.supplyAsync(
        () -> userService.findAllByIds(ids)
      );
    }
  }

Always use DataLoader for nested entity resolution in GraphQL.

SECURITY CONSIDERATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QUERY DEPTH LIMITING:
  Malicious client can send deeply nested query that explodes DB load.
  query { user { posts { author { posts { author { ... } } } } } }
  Solution: set maximum query depth (e.g., 7 levels).

QUERY COMPLEXITY LIMITS:
  Assign a cost to each field. Reject queries above a complexity threshold.

RATE LIMITING:
  REST: rate limit by endpoint. GraphQL: all on /graphql — rate limit
  by complexity score, not just requests.

INTROSPECTION IN PRODUCTION:
  GraphQL allows clients to query the full schema via introspection.
  Disable in production (leaks schema to attackers).

GRAPHQL AS A BFF (BACKEND FOR FRONTEND)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Common pattern: GraphQL as an aggregation layer.
  Mobile/web client → GraphQL BFF → multiple REST/gRPC microservices

BFF (Backend For Frontend):
  One GraphQL server per client type (mobile BFF, web BFF).
  Aggregates data from many downstream services into one query.
  Hides microservice complexity from clients.
  
  Netflix, GitHub, Shopify, Twitter all use this pattern.

Q: When would you choose GraphQL over REST?
A: GraphQL shines when: clients need flexible data fetching (mobile
   apps with different screen sizes), you have many entity relationships
   to traverse, you want to avoid multiple round trips, and you're
   building a BFF aggregation layer. REST is better for simple CRUD,
   public APIs, or when HTTP caching is critical.

Q: How do you prevent the N+1 problem in GraphQL?
A: Use DataLoader pattern — batch all IDs requested in a single
   execution tick into one database query. Every nested entity resolver
   should use DataLoader, not call the DB individually.

Q: How does GraphQL handle API versioning?
A: GraphQL avoids versioning by evolving the schema:
   - Add new fields without breaking existing clients
   - Deprecate old fields with @deprecated directive
   - Remove deprecated fields only after all clients have migrated
   This enables continuous evolution without /v2/ endpoints.
