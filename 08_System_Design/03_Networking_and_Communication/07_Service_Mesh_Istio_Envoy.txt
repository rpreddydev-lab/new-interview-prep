================================================================
SERVICE MESH — ISTIO AND ENVOY
================================================================

THE PROBLEM SERVICE MESH SOLVES
---------------------------------
In a microservices architecture, every service must handle:
  - mTLS (mutual TLS) between services
  - Retries and timeouts
  - Circuit breaking
  - Distributed tracing (inject trace headers)
  - Traffic splitting (canary deployments)
  - Load balancing
  - Rate limiting
  - Observability (metrics per service pair)

WITHOUT a service mesh:
  Every team implements this in their application code.
  Different languages → different libraries → inconsistent behavior.
  Adding a new service means wiring up all of this again.

WITH a service mesh:
  All of the above is handled by infrastructure (sidecar proxies).
  Application code is clean business logic only.
  Language agnostic — mesh works the same for Java, Go, Python services.

ARCHITECTURE: SIDECAR PROXY PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every service pod gets an injected SIDECAR PROXY (Envoy).
ALL network traffic in/out of the pod goes through the sidecar.
The application doesn't know the sidecar exists.

  ┌─────────────────────────────────┐
  │ Pod A                           │
  │  ┌──────────────┐  ┌─────────┐ │
  │  │ Order Service│↔ │ Envoy   │─┼──→ network
  │  └──────────────┘  │ Sidecar │ │
  │                    └─────────┘ │
  └─────────────────────────────────┘
              ↕ (all traffic intercepted by Envoy via iptables)
  ┌─────────────────────────────────┐
  │ Pod B                           │
  │  ┌────────────────┐  ┌───────┐ │
  │  │ Payment Service│↔ │ Envoy │ │
  │  └────────────────┘  └───────┘ │
  └─────────────────────────────────┘

The mesh has two planes:
  DATA PLANE: All the Envoy sidecar proxies (actually move traffic)
  CONTROL PLANE: Istio control plane (Istiod) — configures all Envoys

ENVOY PROXY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Envoy is an open-source, high-performance L7 proxy written in C++.
Originally built by Lyft, now CNCF project.

Used as:
  - Istio's sidecar proxy
  - API Gateway (standalone)
  - Edge proxy (Envoy-based products: Contour, Ambassador, Gloo)

Key Envoy features:
  HTTP/2 and gRPC first-class support
  Dynamic configuration via xDS APIs (no restart needed)
  Rich observability: emits metrics, traces, access logs automatically
  Load balancing: round-robin, least-connections, consistent hash, maglev
  Circuit breaker built-in
  Retries with configurable retry conditions
  Health checking (active and passive)
  TLS termination + mTLS

ISTIO — THE CONTROL PLANE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Istio runs on top of Kubernetes and manages all Envoy sidecars.
Core component: Istiod (consolidated from Pilot, Citadel, Galley).

ISTIOD responsibilities:
  1. SERVICE DISCOVERY: Watches Kubernetes API for services/pods.
     Pushes service registry to all Envoys (xDS: EDS, CDS, RDS, LDS).
  
  2. CERTIFICATE MANAGEMENT: Issues X.509 certificates to every sidecar.
     Enables automatic mTLS between all services (SPIFFE identity).
     Rotates certificates automatically before expiry.
  
  3. TRAFFIC MANAGEMENT: Interprets Istio custom resources (VirtualService,
     DestinationRule) and translates to Envoy configuration.

KEY ISTIO CAPABILITIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. MUTUAL TLS (mTLS):
   Every service-to-service call is automatically encrypted + authenticated.
   Both sides present certificates — you know WHICH service is calling you.
   PeerAuthentication policy: STRICT mode (reject non-mTLS), PERMISSIVE (allow both).
   Zero code changes in applications.

2. TRAFFIC MANAGEMENT:
   VirtualService: defines routing rules for a service.
   DestinationRule: defines policies for traffic to a service (LB, circuit breaking).
   
   CANARY DEPLOYMENT (traffic splitting):
     apiVersion: networking.istio.io/v1alpha1
     kind: VirtualService
     spec:
       http:
       - route:
         - destination: { host: reviews, subset: v1 }
           weight: 90
         - destination: { host: reviews, subset: v2 }
           weight: 10
   
   HEADER-BASED ROUTING:
     Route beta users (x-beta: true header) to v2, everyone else to v1.
     Great for internal testing without separate environments.

3. CIRCUIT BREAKING:
   DestinationRule with outlierDetection:
     Eject backend from pool after N consecutive 5xx errors.
     Automatically restored after a cooldown period.

4. RETRIES AND TIMEOUTS:
   Configurable without code changes:
     VirtualService: retries: attempts: 3, perTryTimeout: 2s
     Timeout: timeout: 5s
   Applied consistently across all callers.

5. OBSERVABILITY (automatic, zero-code):
   METRICS: Envoy emits RED metrics (Rate, Error, Duration) for every service pair.
   DISTRIBUTED TRACING: Envoy propagates trace headers (B3, W3C TraceContext).
   Integrates with Jaeger, Zipkin, Datadog.
   ACCESS LOGS: Every request logged with timing, status, source, destination.

SIDECAR-LESS (eBPF) approach:
  Cilium uses Linux eBPF to intercept traffic at kernel level.
  No sidecar proxy per pod → lower resource overhead.
  Still provides mTLS, observability, network policies.
  Growing in popularity (Kubernetes 1.29+ supports sidecarless with ambient mesh in Istio too).

WHEN TO USE A SERVICE MESH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE when:
  ✓ Many microservices (10+) with complex inter-service communication
  ✓ Strict security requirements (zero-trust, mTLS everywhere)
  ✓ Multiple languages/frameworks that need consistent behavior
  ✓ Need traffic splitting for canary deployments
  ✓ Need unified observability across all services

DON'T USE when:
  ✗ Small number of services (2–5): overhead not worth it
  ✗ Monolith or macro-service architecture
  ✗ Team unfamiliar with Kubernetes/Istio (steep learning curve)
  ✗ Resource-constrained environments (each Envoy sidecar uses ~50MB RAM)

INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How is a service mesh different from an API Gateway?
A: API Gateway sits at the EDGE — it handles external client traffic,
   authentication, rate limiting, routing to internal services.
   Service mesh handles INTERNAL east-west traffic between microservices:
   mTLS, retries, circuit breaking between Service A and Service B.
   They're complementary — you often use both.

Q: How does Istio enforce mTLS without changing application code?
A: Istiod issues X.509 certs to each Envoy sidecar (via SPIFFE standard).
   Envoy intercepts all traffic (via iptables rules injected into pod).
   When Service A calls Service B, A's Envoy initiates mTLS to B's Envoy.
   B's Envoy validates A's certificate (mutual authentication).
   The application code just makes a plain HTTP call.

Q: What is the overhead of a service mesh?
A: Each Envoy sidecar adds ~50-100MB RAM and ~5-15ms latency
   (for the extra network hop through the proxy).
   At scale (100+ services), the control plane (Istiod) needs tuning.
   Trade-off: operational simplicity vs resource cost.
