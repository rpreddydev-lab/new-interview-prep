================================================================
TCP vs UDP — TRANSPORT LAYER PROTOCOLS
================================================================

WHY THIS MATTERS IN SYSTEM DESIGN
-----------------------------------
Choosing between TCP and UDP is foundational when designing:
  - Real-time systems (games, video calls, live streaming)
  - Reliable data transfer (file downloads, API calls)
  - DNS, DHCP, time synchronization (UDP)
  - Any protocol built on top (HTTP, gRPC, WebSockets use TCP; QUIC/HTTP3 uses UDP)

TCP — TRANSMISSION CONTROL PROTOCOL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TCP is a connection-oriented, reliable, ordered protocol.

THREE-WAY HANDSHAKE (Connection Establishment):
  Client → SYN        → Server   (Synchronize sequence number)
  Client ← SYN-ACK    ← Server   (Acknowledge + server's sequence)
  Client → ACK        → Server   (Connection established)
  
  Cost: ~1 RTT (round-trip time) before first byte of data.
  TLS adds another 1–2 RTTs on top.

FOUR-WAY TEARDOWN (Connection Close):
  Client → FIN → Server
  Client ← ACK ← Server
  Client ← FIN ← Server
  Client → ACK → Server
  (TIME_WAIT state: client waits 2×MSL to ensure all packets cleared)

GUARANTEES TCP PROVIDES:
  1. RELIABILITY: Lost packets are detected and retransmitted.
  2. ORDERING: Bytes arrive in the exact order they were sent.
     (Out-of-order packets are buffered and reordered.)
  3. ERROR CHECKING: Checksum on every segment.
  4. FLOW CONTROL: Receiver advertises window size — prevents sender
     overwhelming receiver's buffer. (Sliding window protocol.)
  5. CONGESTION CONTROL: Slow start, AIMD (Additive Increase, Multiplicative
     Decrease) — backs off when network is congested.

HOW TCP ACHIEVES RELIABILITY:
  - Sender assigns sequence numbers to each byte.
  - Receiver sends ACK for received segments.
  - Sender maintains timer; retransmits if no ACK received.
  - Selective ACK (SACK): receiver can ack non-contiguous segments.

TCP COSTS (tradeoffs):
  - Connection setup overhead (handshake)
  - Head-of-line blocking: one lost packet blocks all subsequent packets
    in the stream (even those already received)
  - Congestion control adds latency when network is unstable
  - Stateful: server must track connection state per client

WHEN TO USE TCP:
  ✓ Data integrity is critical (banking, file transfers, API calls)
  ✓ HTTP/HTTPS, gRPC, WebSockets, SMTP, FTP, SSH
  ✓ Ordering matters (you can't process record N before N-1)
  ✓ Any situation where losing a packet is unacceptable

UDP — USER DATAGRAM PROTOCOL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

UDP is a connectionless, unreliable, unordered protocol.
"Best effort" delivery — send and forget.

UDP HEADER: Only 8 bytes (vs TCP's 20 bytes minimum).
  Source port | Destination port | Length | Checksum

WHAT UDP DOES NOT PROVIDE:
  ✗ No connection setup
  ✗ No delivery guarantee (packets can be lost)
  ✗ No ordering guarantee (packets can arrive out of order)
  ✗ No retransmission
  ✗ No flow control
  ✗ No congestion control

UDP ADVANTAGES:
  ✓ Zero connection overhead (no handshake)
  ✓ Extremely low latency (no wait for ACK, retransmit)
  ✓ Lower per-packet overhead
  ✓ Supports multicast and broadcast (TCP does not)
  ✓ Application controls its own reliability logic

WHEN TO USE UDP:
  ✓ Real-time audio/video calls (Zoom, WebRTC) — a late packet is worse
    than a dropped packet; you can't wait for a retransmit from 200ms ago
  ✓ Online gaming — position updates are stale by the time retransmitted
  ✓ Live video streaming — slight quality degradation better than buffering
  ✓ DNS lookups — single small request/response; retry is fast
  ✓ IoT sensor data — losing one temperature reading is fine
  ✓ DHCP — cannot use TCP without IP address yet

QUIC — THE FUTURE (HTTP/3)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QUIC (Quick UDP Internet Connections) is a transport protocol built
on UDP but providing TCP-like reliability with major improvements.
It is the transport layer of HTTP/3.

QUIC advantages over TCP+TLS:
  1. 0-RTT or 1-RTT connection establishment (vs TCP's 1 RTT + TLS's 1-2 RTT)
  2. No head-of-line blocking at transport layer:
     Each QUIC stream is independent — a lost packet in stream A
     doesn't block stream B (unlike TCP where all streams share one byte stream)
  3. Connection migration: if client changes IP (WiFi → 4G),
     QUIC connection continues (identified by Connection ID, not IP:port tuple)
  4. Built-in TLS 1.3 (not bolted on)

QUIC is used by: Google (Chrome, YouTube), Cloudflare, Facebook.
HTTP/3 = HTTP semantics over QUIC.

TCP IN JAVA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// TCP Server
ServerSocket serverSocket = new ServerSocket(8080);
Socket client = serverSocket.accept();  // blocks until connection
InputStream in = client.getInputStream();
OutputStream out = client.getOutputStream();

// TCP Client
Socket socket = new Socket("localhost", 8080);
OutputStream out = socket.getOutputStream();
out.write("Hello".getBytes());

// UDP Server
DatagramSocket socket = new DatagramSocket(9090);
byte[] buf = new byte[256];
DatagramPacket packet = new DatagramPacket(buf, buf.length);
socket.receive(packet);  // blocks

// UDP Client
DatagramSocket socket = new DatagramSocket();
byte[] buf = "Hello".getBytes();
DatagramPacket packet = new DatagramPacket(buf, buf.length,
    InetAddress.getByName("localhost"), 9090);
socket.send(packet);

INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: You are designing a multiplayer FPS game. TCP or UDP?
A: UDP. In a fast-paced game, a player position update that arrives
   100ms late is worse than useless — the player has already moved.
   Drop the stale packet, use the latest state. Retransmission latency
   is unacceptable. Custom reliability for critical events (player
   death, score) can be layered on top of UDP.

Q: Why does DNS use UDP but TCP for zone transfers?
A: Standard DNS queries are small (fit in one UDP datagram < 512 bytes)
   and a client can quickly retry if no response. UDP is faster.
   Zone transfers (full DNS record replication) are large and require
   reliable delivery → TCP.

Q: What is TCP head-of-line blocking?
A: TCP delivers bytes in order. If packet 5 is lost, packets 6, 7, 8
   (already received) cannot be delivered to the application until
   packet 5 is retransmitted and arrives. HTTP/2 multiplexes streams
   over TCP but still suffers from this at the TCP layer — QUIC solves it.
