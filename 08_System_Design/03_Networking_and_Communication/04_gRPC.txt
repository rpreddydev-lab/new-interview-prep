gRPC — REMOTE PROCEDURE CALLS FOR MICROSERVICES
================================================================

WHAT IS gRPC?
--------------
gRPC (Google Remote Procedure Call) is a high-performance,
open-source RPC framework developed by Google.

Key characteristics:
  - Uses HTTP/2 as transport (multiplexing, header compression, streaming)
  - Uses Protocol Buffers (protobuf) as the IDL and serialization format
  - Strongly typed contracts via .proto files
  - Auto-generates client/server stubs in multiple languages
  - Bidirectional streaming support

PROTOCOL BUFFERS (PROTOBUF)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Define your service contract in a .proto file:

  syntax = "proto3";
  
  package order;
  
  service OrderService {
    rpc GetOrder(GetOrderRequest) returns (OrderResponse);
    rpc StreamOrders(StreamRequest) returns (stream OrderEvent);
    rpc CreateOrders(stream OrderRequest) returns (CreateSummary);
    rpc ChatOrders(stream OrderRequest) returns (stream OrderEvent);
  }
  
  message GetOrderRequest {
    string order_id = 1;     // field number (not value!)
  }
  
  message OrderResponse {
    string order_id = 1;
    string status   = 2;
    double amount   = 3;
    int64  created_at = 4;
  }

FIELD NUMBERS:
  Each field has a unique number (used in binary encoding, not field name).
  Field numbers 1–15 use 1 byte; 16–2047 use 2 bytes.
  → Put frequently used fields in 1–15 range for efficiency.
  → NEVER change field numbers (breaks binary compatibility).

BINARY ENCODING:
  Protobuf encodes as binary (not text like JSON/XML).
  3–10x smaller than JSON, 20–100x faster to serialize/deserialize.
  Not human-readable (use grpcurl or grpc-gateway for debugging).

FOUR TYPES OF gRPC CALLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. UNARY RPC (most common):
   Client sends ONE request → Server sends ONE response.
   Same as a regular function call.
   
   rpc GetUser(GetUserRequest) returns (UserResponse);
   
   Client: stub.getUser(request)  → waits for response
   Use for: CRUD operations, simple lookups.

2. SERVER STREAMING RPC:
   Client sends ONE request → Server streams MULTIPLE responses.
   
   rpc ListOrders(ListRequest) returns (stream OrderResponse);
   
   Server: for each order → send response chunk
   Client: receives stream, iterates until server closes
   Use for: downloading large datasets, real-time feeds, logs tail.

3. CLIENT STREAMING RPC:
   Client streams MULTIPLE requests → Server sends ONE response.
   
   rpc UploadChunks(stream FileChunk) returns (UploadSummary);
   
   Client: sends file in chunks → server accumulates → returns summary
   Use for: file uploads, bulk inserts, batch sensor data.

4. BIDIRECTIONAL STREAMING RPC:
   Client and server BOTH stream to each other simultaneously.
   Full-duplex communication over a single HTTP/2 connection.
   
   rpc Chat(stream ChatMessage) returns (stream ChatMessage);
   
   Use for: real-time chat, collaborative editing, live game state.

gRPC vs REST — COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌──────────────────────┬───────────────────────┬──────────────────────────┐
│ Property             │ REST (JSON over HTTP)  │ gRPC (Protobuf + HTTP/2) │
├──────────────────────┼───────────────────────┼──────────────────────────┤
│ Protocol             │ HTTP/1.1 or HTTP/2     │ HTTP/2 (required)        │
│ Payload format       │ JSON (text)            │ Protobuf (binary)        │
│ Contract definition  │ OpenAPI (optional)     │ .proto file (mandatory)  │
│ Payload size         │ Larger                 │ 3–10x smaller            │
│ Speed                │ Moderate               │ Much faster              │
│ Human readable       │ Yes                    │ No (need tools)          │
│ Browser support      │ Native                 │ No (gRPC-Web needed)     │
│ Streaming            │ SSE / WebSocket        │ Built-in (4 modes)       │
│ Code generation      │ Optional               │ Auto-generated stubs     │
│ Type safety          │ Optional (TypeScript)  │ Built-in (proto schema)  │
│ Error model          │ HTTP status codes      │ gRPC status codes        │
│ Load balancer compat │ Full                   │ Needs L7 (HTTP/2 aware)  │
└──────────────────────┴───────────────────────┴──────────────────────────┘

CHOOSE gRPC WHEN:
  ✓ Internal microservice-to-microservice communication
  ✓ Performance-critical paths (high QPS, low latency)
  ✓ Multiple language services (auto-generated stubs for each)
  ✓ Need streaming (bidirectional or server-side)
  ✓ Large binary payloads (images, audio chunks)

CHOOSE REST WHEN:
  ✓ Public-facing APIs (browsers, mobile, external partners)
  ✓ Need human-readable requests for debugging
  ✓ Simple CRUD with no streaming needs
  ✓ Team unfamiliar with protobuf tooling

HTTP/2 ADVANTAGES gRPC GETS FOR FREE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MULTIPLEXING:
  Multiple requests over a SINGLE TCP connection simultaneously.
  HTTP/1.1 problem: one request at a time per connection (head-of-line blocking).
  HTTP/2: streams share one connection — no HOL blocking.

HEADER COMPRESSION (HPACK):
  Headers compressed across requests.
  REST repeats headers on every request (Authorization, Content-Type, etc.)
  HTTP/2: only diffs are sent — huge savings for high-QPS services.

BINARY FRAMING:
  HTTP/2 sends binary frames (not text lines like HTTP/1.1).
  More efficient parsing, smaller frames.

SERVER PUSH:
  Server can push resources to client before client asks.
  (Rarely used in gRPC context, but available.)

SERVER IMPLEMENTATION:
  @GrpcService
  public class OrderServiceImpl extends OrderServiceGrpc.OrderServiceImplBase {
    @Override
    public void getOrder(GetOrderRequest request,
                         StreamObserver<OrderResponse> responseObserver) {
      Order order = orderRepository.findById(request.getOrderId());
      OrderResponse response = OrderResponse.newBuilder()
          .setOrderId(order.getId())
          .setStatus(order.getStatus())
          .setAmount(order.getAmount())
          .build();
      responseObserver.onNext(response);
      responseObserver.onCompleted();
    }
  }

CLIENT USAGE:
  @GrpcClient("order-service")
  private OrderServiceGrpc.OrderServiceBlockingStub orderStub;
  
  public Order fetchOrder(String id) {
    OrderResponse response = orderStub.getOrder(
        GetOrderRequest.newBuilder().setOrderId(id).build()
    );
    return map(response);
  }

gRPC ERROR HANDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC status codes (not HTTP codes):
  OK (0)               → Success
  CANCELLED (1)        → Client cancelled the request
  INVALID_ARGUMENT (3) → Bad request (like HTTP 400)
  NOT_FOUND (5)        → Resource not found (like HTTP 404)
  ALREADY_EXISTS (6)   → Conflict (like HTTP 409)
  PERMISSION_DENIED (7)→ Authorization failed (like HTTP 403)
  UNAVAILABLE (14)     → Service is down, retry later (like HTTP 503)
  DEADLINE_EXCEEDED (4)→ Request timed out

Error with detail:
  responseObserver.onError(
    Status.NOT_FOUND
      .withDescription("Order " + id + " not found")
      .asRuntimeException()
  );

DEADLINES AND INTERCEPTORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEADLINES:
  Every gRPC call should have a deadline (timeout).
  Propagated through the call chain (if A calls B calls C, deadline is shared).
  
  stub.withDeadlineAfter(500, TimeUnit.MILLISECONDS).getOrder(request);
  
  Best practice: always set deadlines to prevent cascading delays.

INTERCEPTORS:
  Middleware for cross-cutting concerns (like Servlet filters for REST).
  Use cases: auth (JWT validation), logging, tracing, metrics.
  
  Server-side:  implements ServerInterceptor
  Client-side:  implements ClientInterceptor

gRPC-GATEWAY (REST + gRPC TOGETHER)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: Browsers can't call gRPC directly (no HTTP/2 trailer support).
Solution: gRPC-Gateway translates REST HTTP/JSON → gRPC protobuf.

Architecture:
  Browser → REST JSON → [gRPC-Gateway proxy] → gRPC protobuf → Service

Annotation in .proto file:
  import "google/api/annotations.proto";
  rpc GetOrder(GetOrderRequest) returns (OrderResponse) {
    option (google.api.http) = { get: "/v1/orders/{order_id}" };
  }

This gives you BOTH REST and gRPC from a single service definition.

gRPC INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why does gRPC use HTTP/2 and not HTTP/1.1?
A: HTTP/2 enables multiplexing (multiple streams on one connection),
   header compression, and binary framing — all critical for
   gRPC's streaming and performance goals.

Q: How do you handle breaking changes in a protobuf API?
A: Never change field numbers. Never remove or rename fields.
   Add new fields with new numbers (old clients ignore unknown fields).
   For major changes, create a new service version (OrderServiceV2).

Q: When would you NOT use gRPC?
A: When clients are browsers (no native support), when you need
   human-readable requests for debugging/testing, when external
   partners need to integrate (REST/OpenAPI is far more accessible).

Q: How does load balancing work with gRPC?
A: gRPC uses long-lived HTTP/2 connections — traditional L4 load balancers
   (TCP) stick requests to one backend. Need L7 (application-layer) load
   balancing that understands HTTP/2 streams (Envoy, Nginx, AWS ALB).
   Client-side load balancing is also an option (client has list of backends).
