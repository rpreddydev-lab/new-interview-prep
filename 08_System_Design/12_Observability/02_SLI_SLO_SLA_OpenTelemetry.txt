SECTION 1 — OBSERVABILITY FUNDAMENTALS
================================================================================

Q1: What is observability? How is it different from monitoring?

A: MONITORING (reactive):
   - You know IN ADVANCE what can go wrong
   - You configure dashboards and alerts for those known failure modes
   - "Did the service go down?" "Is CPU > 80%?"
   - Works well for known-unknowns

   OBSERVABILITY (proactive):
   - Can you understand what is happening INSIDE the system from its OUTPUTS alone?
   - Applies when the system fails in ways you never anticipated
   - "Why is the billing service slow for only subscribers in London?"
   - Works for unknown-unknowns

   OBSERVABLE SYSTEM PROPERTIES:
   - HIGH CARDINALITY: can query by arbitrary attributes (user_id, msisdn, tariff_plan)
   - HIGH DIMENSIONALITY: many attributes per data point (region, version, pod_name)
   - EXPLORATION: explore data without pre-defining dashboards

   QUOTE: "Observability is not about having lots of data. It's about answering
   arbitrary questions about your system without having predicted them in advance."
   — Charity Majors (Honeycomb.io)

──────────────────────────────────────────────────────────────────────────────
Q2: What are the three pillars of observability?

A: THREE PILLARS:

   ┌──────────────┬───────────────────────────────────────────────────────────┐
   │ PILLAR       │ DESCRIPTION                                               │
   ├──────────────┼───────────────────────────────────────────────────────────┤
   │ METRICS      │ Numeric aggregations over time                            │
   │              │ Example: request_rate, error_rate, p99_latency_ms         │
   │              │ Tools: Prometheus, Micrometer, CloudWatch Metrics          │
   │              │ Good for: dashboards, alerting on trends                  │
   │              │ Weakness: high cardinality (per-user metrics) is expensive│
   ├──────────────┼───────────────────────────────────────────────────────────┤
   │ LOGS         │ Timestamped records of discrete events                    │
   │              │ Example: "2024-01-15 14:23:01 ERROR CDR rating failed     │
   │              │          callId=abc123 msisdn=447700900001"               │
   │              │ Tools: ELK Stack, Loki+Grafana, CloudWatch Logs           │
   │              │ Good for: debugging specific errors; audit trail           │
   │              │ Weakness: expensive to store; hard to correlate across svc │
   ├──────────────┼───────────────────────────────────────────────────────────┤
   │ TRACES       │ End-to-end journey of a single request across services    │
   │              │ Example: /rate-cdr → BillingService → TariffService →DB   │
   │              │ Each step = a SPAN; all spans for one request = a TRACE   │
   │              │ Tools: Jaeger, Zipkin, Tempo, AWS X-Ray                   │
   │              │ Good for: finding where latency comes from; dependency map │
   │              │ Weakness: sampling needed at high traffic; storage cost    │
   └──────────────┴───────────────────────────────────────────────────────────┘

   THE CORRELATION IS THE POWER:
   - Start with a METRIC alert: error rate spike at 14:23
   - Drill into LOGS: filter by timestamp → find specific error messages
   - Follow the TRACE: see exactly which service and DB call caused the error
   - All three pillars linked by: TRACE_ID embedded in logs and spans

SECTION 2 — SLI, SLO, SLA, ERROR BUDGET
================================================================================

Q3: Define SLI, SLO, and SLA with real telecom examples.

A:
   SLI — Service Level INDICATOR:
   A MEASURED metric that indicates the health of a service.
   Must be quantifiable and automatable.

   TELECOM EXAMPLES:
   - CDR Rating API availability: (successful requests / total requests) × 100%
   - Invoice generation latency: p99 response time in milliseconds
   - Subscriber lookup error rate: (5xx responses / total responses) × 100%
   - Message delivery ratio: (delivered SMSes / attempted SMSes) × 100%

   ──────────────────────────────────────────────────────────────
   SLO — Service Level OBJECTIVE:
   A TARGET value for an SLI, defining acceptable system performance.
   Set INTERNALLY by engineering/product teams.

   TELECOM EXAMPLES:
   - CDR Rating API: availability ≥ 99.9% per rolling 28 days
   - Invoice generation: p99 latency ≤ 500ms
   - Subscriber lookup: error rate ≤ 0.1%
   - SMS delivery: delivery ratio ≥ 99.5%

   SLOs should be ACHIEVABLE but ASPIRATIONAL — not 100% (that's impossible).
   Setting SLO at 99.9% for a 99.99%-capable system gives headroom for incidents.

   ──────────────────────────────────────────────────────────────
   SLA — Service Level AGREEMENT:
   A CONTRACTUAL commitment to customers with financial consequences.
   SLA is typically LESS strict than the internal SLO (buffer for safety).

   TELECOM SLA EXAMPLE:
   - "Customer portal will be available 99.5% of the time monthly"
   - If breached: customer receives service credit (e.g., 10% monthly bill refund)
   - SLA = 99.5%, internal SLO = 99.9% → 0.4% buffer before SLA breach

   RELATIONSHIP: SLI measures → SLO targets → SLA contracts
   SLO must be STRICTER than SLA to catch problems before they breach the agreement.

──────────────────────────────────────────────────────────────────────────────
Q4: What is an error budget and how is it used?

A: ERROR BUDGET = 1 − SLO

   Example: SLO = 99.9% availability per 28 days
   Error budget = 0.1% × 28 days × 24h × 60min = 40.32 minutes of downtime

   HOW IT'S USED:
   - If budget is ABUNDANT: teams can move fast, deploy often, take risks
   - If budget is NEARLY EXHAUSTED: freeze risky deployments; focus on stability
   - If budget is EXHAUSTED: incident review required; no new feature releases until recovered

   ERROR BUDGET POLICY (agreed team rules):
   ✓ If > 50% budget consumed in first 2 weeks → slow down deployments
   ✓ If 100% consumed → release freeze until next period
   ✓ Prioritize reliability work next sprint if budget burned by external causes
   ✓ Postmortem mandatory for any incident consuming > 10% of budget

   ERROR BUDGET BURN RATE ALERT (Google SRE approach):
   - Instead of alerting on SLO breach (too late), alert on BURN RATE
   - If burning budget 14× faster than normal → page on-call immediately
   - If burning 6× faster → send ticket (not urgent yet)
   - Example: 1h window with 14× burn rate = will exhaust 28-day budget in 2h

   Prometheus alert example:
   - job:slo_error_rate:ratio_rate1h > 14 * 0.001  # 14× of 0.1% budget rate

SECTION 3 — OPENTELEMETRY ARCHITECTURE
================================================================================

Q5: What is OpenTelemetry and why is it the industry standard?

A: OpenTelemetry (OTel) is a CNCF project providing:
   - Vendor-neutral APIs, SDKs, and agents for all three observability pillars
   - One standard instrumentation → export to ANY backend (Jaeger, Prometheus, Datadog...)
   - Auto-instrumentation for common frameworks (Spring, JDBC, gRPC, etc.)

   BEFORE OPENTELEMETRY (fragmented):
   Jaeger SDK → Jaeger only
   Zipkin SDK → Zipkin only
   Datadog Agent → Datadog only
   Switching backends required re-instrumenting all services

   WITH OPENTELEMETRY:
   OTel SDK → OTel Collector → [Jaeger | Zipkin | Prometheus | Datadog | Grafana Tempo]
   One SDK; swap backends by changing Collector config only

   OPENTELEMETRY ARCHITECTURE:
   ┌──────────────────────────────────────────────────────────────────────┐
   │  Your Service (JVM)                                                  │
   │  ┌─────────────────────────────────────────────────────────────┐    │
   │  │ Auto-instrumentation: Spring MVC, JDBC, Kafka, RestTemplate │    │
   │  │ Manual instrumentation: custom spans, business metrics       │    │
   │  └───────────────────────────┬─────────────────────────────────┘    │
   │                              │ OTLP (gRPC or HTTP)                   │
   └──────────────────────────────┼───────────────────────────────────────┘
                                  ▼
   ┌─────────────────────────────────────────────────────────────────────┐
   │  OTel Collector (sidecar or daemonset in K8s)                       │
   │  Receivers: OTLP, Prometheus, Jaeger, Zipkin                        │
   │  Processors: batching, sampling, attribute filtering, tail sampling  │
   │  Exporters: Jaeger, Prometheus, Grafana Tempo, Datadog, OTLP        │
   └──────────────────────────────┬──────────────────────────────────────┘
                                  │
          ┌────────────┬──────────┴──────────┬────────────────┐
          ▼            ▼                     ▼                ▼
       Jaeger       Prometheus           Grafana Tempo    Datadog
    (tracing)      (metrics)             (tracing)    (commercial)

Q6: How do you implement distributed tracing in a Spring Boot microservice?

A: SPRING BOOT + OPENTELEMETRY SETUP:

   pom.xml dependencies:
   <dependency>
     <groupId>io.micrometer</groupId>
     <artifactId>micrometer-tracing-bridge-otel</artifactId>
   </dependency>
   <dependency>
     <groupId>io.opentelemetry</groupId>
     <artifactId>opentelemetry-exporter-otlp</artifactId>
   </dependency>
   <!-- Auto-instrumentation of Spring MVC, RestTemplate, WebClient -->

   application.yml:
   management:
     tracing:
       sampling:
         probability: 0.1    # Sample 10% of requests (adjust for traffic)
   otel:
     exporter:
       otlp:
         endpoint: http://otel-collector:4317
     service:
       name: billing-service

   TRACE CONTEXT PROPAGATION (W3C TraceContext standard):
   When BillingService calls SubscriberService:
   - BillingService adds header: traceparent: 00-<traceId>-<spanId>-01
   - SubscriberService reads header, creates child span under same trace
   - Both spans appear in Jaeger as part of the same trace waterfall

   ADDING CUSTOM SPANS:
   @Autowired Tracer tracer;

   public RatedCDR rateCdr(RawCDR cdr) {
       Span span = tracer.nextSpan().name("cdr.rating").start();
       try (Tracer.SpanInScope scope = tracer.withSpan(span)) {
           span.tag("msisdn", cdr.fromMsisdn());
           span.tag("call.type", cdr.callType());
           return doRating(cdr);
       } catch (Exception e) {
           span.error(e);
           throw e;
       } finally {
           span.end();
       }
   }

   STRUCTURED LOGGING WITH TRACE CORRELATION:
   // With Micrometer Tracing + Logback/SLF4J:
   // MDC automatically populated: traceId, spanId
   LOG.info("Rating CDR {} for msisdn {}", cdr.callId(), cdr.fromMsisdn());
   // Output: [traceId=4f3a2b1c... spanId=7d9e...] Rating CDR abc123 for msisdn 447700900001
   // → Can search Loki/Elasticsearch by traceId to see all logs for one request

SECTION 4 — ALERTING STRATEGY
================================================================================

Q7: How do you design an effective alerting strategy?

A: ALERTING PRINCIPLES:

   1. ALERT ON SYMPTOMS, NOT CAUSES:
      ✓ Alert: "Error rate for CDR rating API > 5%" (symptom)
      ✗ Alert: "CPU > 80% on billing-service-pod-3" (possible cause)
      Reason: symptoms are customer-impacting; CPU spike may not matter

   2. EVERY ALERT MUST BE ACTIONABLE:
      If you receive an alert and don't know what to do → remove the alert
      Alert fatigue kills on-call effectiveness

   3. SLO-BASED ALERTS (multi-window, multi-burn-rate):
      Fast alerts (1h window): catches severe incidents quickly, may have false positives
      Slow alerts (6h window): more confident, but slower response
      Use BOTH for different severities:
      - P1 (page immediately): 1h burn rate > 14× + 5min burn rate > 14×
      - P2 (notify): 6h burn rate > 6× + 1h burn rate > 6×

   4. RUNBOOKS WITH EVERY ALERT:
      Alert config must link to a runbook:
      annotations:
        runbook_url: https://wiki.telecom.com/runbooks/billing-error-rate

   5. NOISE REDUCTION:
      - Group related alerts (alert grouping in Alertmanager)
      - Inhibition rules: suppress downstream alerts when upstream is already paging
      - Silencing: planned maintenance windows

   ALERT SEVERITY LEVELS:
   P1 — Critical: immediate page; customer-impacting; all hands
   P2 — Warning:  notify team; investigate next business hour
   P3 — Info:     ticket created; review in planning
   P4 — None:     logged for trend analysis; no human action

QUICK REFERENCE CHEAT SHEET
================================================================================

THREE PILLARS:
  Metrics  → aggregated numbers over time (Prometheus, Micrometer)
  Logs     → discrete events (ELK, Loki)
  Traces   → request journey across services (Jaeger, Zipkin, Tempo)
  Power:   link all three via traceId embedded in logs and spans

SLI / SLO / SLA:
  SLI = the measured metric (e.g., 99.95% availability)
  SLO = the internal target (e.g., ≥ 99.9%)
  SLA = the contractual commitment (e.g., ≥ 99.5%) — always less strict than SLO
  Error budget = 1 − SLO; governs deployment velocity

ERROR BUDGET ALERTS:
  Burn rate 14×  → P1 page (exhausted in ~2h)
  Burn rate 6×   → P2 ticket (exhausted in ~5 days)
  Burn rate 1×   → on track; no action

OPENTELEMETRY:
  Vendor-neutral SDK → OTel Collector → Any backend
  Auto-instruments: Spring MVC, JDBC, Kafka, gRPC
  Propagation: W3C traceparent header
  traceId in MDC → correlate logs with traces

ALERTING RULES:
  Alert on symptoms (error rate) not causes (CPU)
  Every alert must be actionable + have a runbook
  Multi-window burn rate: fast (1h) + slow (6h) for different severities
  Inhibition + grouping to reduce noise
