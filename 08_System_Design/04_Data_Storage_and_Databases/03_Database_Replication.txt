================================================================
DATABASE REPLICATION
================================================================

WHAT IS DATABASE REPLICATION?
-------------------------------
Replication is the process of copying and maintaining data across
multiple database nodes.

Goals:
  1. High Availability: If primary fails, replica takes over
  2. Read Scaling: Distribute read load across replicas
  3. Disaster Recovery: Keep data in multiple geographic locations
  4. Analytics: Run expensive queries on replica without affecting production

REPLICATION TOPOLOGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. SINGLE-LEADER (Primary-Replica / Master-Slave)
   One node (primary/master) accepts writes.
   One or more nodes (replicas/slaves) replicate from primary.
   All writes go to primary; reads can go to any node.
   
   ┌──────────┐  WAL/binlog  ┌──────────┐
   │ Primary  │ ──────────→  │ Replica 1│ (reads)
   │ (writes) │ ──────────→  │ Replica 2│ (reads)
   └──────────┘              └──────────┘
   
   Used by: MySQL, PostgreSQL, Redis
   
   Pros:
   - Consistent write ordering (single source of truth)
   - Simple conflict resolution (no write conflicts possible)
   - Read scaling (add replicas)
   
   Cons:
   - Write bottleneck (all writes to one node)
   - Primary is SPOF (mitigated by automated failover)
   - Replication lag → stale reads from replicas

2. MULTI-LEADER (Multi-Master)
   Multiple nodes can accept writes.
   Each leader replicates to the others.
   
   ┌──────────┐ ←→ ┌──────────┐
   │ Leader 1 │    │ Leader 2 │
   └──────────┘ ←→ └──────────┘
   
   Used by: MySQL with Group Replication, CockroachDB, Google Spanner
   
   Pros:
   - Multiple write paths (write scalability)
   - Allows writes in multiple geographic regions
   
   Cons:
   - WRITE CONFLICTS: Both leaders accept conflicting writes simultaneously
     "User A changes email to a@x.com on Leader 1"
     "User A changes email to b@x.com on Leader 2 simultaneously"
     Which wins? → Complex conflict resolution needed
   - Last-write-wins (LWW) using timestamp: risk of data loss
   - Custom conflict resolution logic
   
   Use sparingly. Most applications don't need it.
   Best for: Collaborative editing, multi-region writes (but use CRDTs)

3. LEADERLESS (Dynamo-style)
   No designated primary. Any node can accept reads/writes.
   Client writes to multiple nodes; majority quorum for success.
   
   Used by: Apache Cassandra, Amazon DynamoDB, Riak, Voldemort
   
   Read/Write Quorum:
     N = total replicas (replication factor)
     W = required write confirmations
     R = required read confirmations
     For strong consistency: W + R > N
     Example (N=3, W=2, R=2): W+R=4 > N=3 → strong consistency
     Example (N=3, W=1, R=1): Eventual consistency (fast but stale possible)
   
   Pros:
   - No SPOF for writes
   - Can tolerate node failures (as long as quorum available)
   - Global distribution naturally
   
   Cons:
   - Write conflicts possible (use version vectors, CRDTs, or LWW)
   - Eventual consistency by default
   - Complex to reason about

REPLICATION MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SYNCHRONOUS REPLICATION:
  Primary waits for all replicas to confirm write before ACKing client.
  
  Client → Primary writes → ACK to all replicas → All ACK → Client ACK
  
  Pros:
  - Zero data loss on failover (all replicas are up-to-date)
  - Failover can promote any replica without data loss
  
  Cons:
  - Slower writes (latency = max latency across all replicas)
  - A slow/failed replica blocks all writes
  
  Use for: Financial ledgers, critical data where data loss = catastrophic

ASYNCHRONOUS REPLICATION:
  Primary ACKs the client immediately after local write.
  Replication happens in the background.
  
  Client → Primary writes → Client ACK
                          ↓ (async)
                         Replica
  
  Pros:
  - Low write latency (no waiting for replicas)
  - Replica failures don't block writes
  
  Cons:
  - Replication lag (replicas may be seconds behind)
  - Data loss possible if primary fails before replica catches up (RPO > 0)
  
  Use for: Social media, product descriptions, low-stakes data

SEMI-SYNCHRONOUS:
  Primary waits for at least ONE replica to confirm, then ACKs client.
  Balance between durability and latency.
  MySQL default mode: "Semi-synchronous replication"
  
  Use for: General purpose; acceptable RPO with better availability than sync

REPLICATION IMPLEMENTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STATEMENT-BASED REPLICATION:
  Primary logs SQL statements; replicas re-execute them.
  Problem: Non-deterministic statements (NOW(), RAND()) differ per replica.
  Mostly deprecated.

ROW-BASED REPLICATION:
  Primary logs actual row changes (before/after).
  More reliable; replicas apply exact same changes.
  Larger log size (especially for UPDATE affecting many rows).
  MySQL default: binlog_format=ROW

WRITE-AHEAD LOG (WAL) SHIPPING (PostgreSQL):
  Primary continuously ships WAL (binary log of all changes).
  Replicas apply WAL to keep in sync.
  Also enables point-in-time recovery.

CHANGE DATA CAPTURE (CDC):
  Stream database changes as events to external consumers.
  Tools: Debezium (reads MySQL/PostgreSQL WAL → Kafka)
  Use cases:
  - Keep ElasticSearch index in sync with DB
  - Invalidate Redis cache on DB change
  - Stream changes to analytics systems
  - Audit log all database changes

FAILOVER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MANUAL FAILOVER:
  DBA manually promotes a replica to primary.
  RTO: Minutes to hours.
  Use: Non-critical systems, cost savings.

AUTOMATED FAILOVER:
  Tools detect primary failure and automatically promote replica.
  Tools: MySQL MHA, Orchestrator, MariaDB Galera, Patroni (PostgreSQL), 
         AWS RDS Multi-AZ (fully managed failover)
  
  Failover process:
  1. Detect failure (health check timeout × N)
  2. Elect new primary (most up-to-date replica OR raft consensus)
  3. Update DNS / virtual IP to point to new primary
  4. Other replicas start replicating from new primary
  5. Alert on-call team
  
  RTO: 30s–2 minutes (automatic)
  RPO: Seconds (async replication lag at time of failure)
       0 seconds (synchronous replication)

SPLIT BRAIN PROBLEM:
  Both original primary and newly promoted primary are operational
  and accepting writes simultaneously → data inconsistency.
  
  Cause: Network partition (primaries can't communicate but both
         think the other is dead).
  
  Solutions:
  a) STONITH (Shoot The Other Node In The Head): Forcefully shut down
     old primary via out-of-band management before promoting replica.
  b) Quorum-based fencing: Require majority quorum to become primary.
     With 3 nodes: 2 nodes agree on new primary = safe.
  c) Lease / epoch: Primary holds time-limited lease; on expiry, stops
     accepting writes.

REPLICATION LAG MITIGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: User writes a tweet, then reads their timeline.
If reads go to replica with replication lag, tweet is missing.

Solutions:
  1. Read-your-own-writes:
     Route reads to primary for user's own data (at least for 5 seconds after write).
     Application tracks: "user_123 wrote at time T; route their reads to primary until T+5s"

  2. Monotonic reads:
     User always reads from the same replica (sticky).
     Prevents seeing newer data then older data on refresh.
     But doesn't solve freshness.

  3. Consistent prefix reads:
     Ensure causally related writes are seen in correct order.
     Important for multi-user interactions.

  4. Reduce replication lag:
     Optimize replica for fast replication (enough IOPS, parallel apply)
     Monitor and alert on replication lag > threshold

  5. Cache invalidation:
     After writing, invalidate the cache entry.
     Next read (even from replica) will miss cache and fetch from primary.
