SQL vs NoSQL DECISION
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
RELATIONAL (SQL) DATABASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KEY CHARACTERISTICS:
  - Structured data in tables (rows and columns)
  - Fixed schema (ALTER TABLE required to change structure)
  - ACID transactions (Atomicity, Consistency, Isolation, Durability)
  - JOINs to combine data from multiple tables
  - SQL query language (standard, widely known)
  - Strong consistency

ACID PROPERTIES:
  Atomicity:   All operations in a transaction succeed or all fail.
               "Transfer $100 from A to B" — both debit and credit
               happen, or neither does.
  
  Consistency: Database always transitions from one valid state to another.
               Constraints (NOT NULL, FK, UNIQUE) are always enforced.
  
  Isolation:   Concurrent transactions don't interfere with each other.
               Read committed, Repeatable Read, Serializable levels.
  
  Durability:  Committed transactions survive crashes (WAL, fsync).

ISOLATION LEVELS:
  Read Uncommitted: Can read dirty (uncommitted) writes → rare use
  Read Committed:   Only see committed writes → PostgreSQL default
  Repeatable Read:  Same row returns same value in same transaction
  Serializable:     Transactions behave as if sequential → safest but slowest

POPULAR SQL DATABASES:
  PostgreSQL:    Open source, feature-rich (JSON support, PostGIS, partitioning)
                 Best all-around choice for new projects.
  MySQL/MariaDB: Open source, very widely used, slightly simpler than PG.
  Oracle DB:     Enterprise, expensive, extremely feature-rich.
  SQL Server:    Microsoft ecosystem, great .NET integration.
  SQLite:        Embedded, file-based, no server needed (mobile, testing).
  CockroachDB:   Distributed SQL, globally consistent, PostgreSQL-compatible.
  PlanetScale:   Serverless MySQL-compatible, horizontal sharding built-in.
  TiDB:          Distributed SQL, MySQL-compatible, HTAPworku

STRENGTHS OF SQL:
  ✓ Complex queries with JOINs, subqueries, window functions
  ✓ ACID guarantees — critical for financial, transactional data
  ✓ Strong consistency — all nodes see same data
  ✓ Mature ecosystem (ORMs, monitoring, tools)
  ✓ Normalized data avoids duplication
  ✓ Foreign key constraints enforce data integrity
  ✓ Standard SQL language — easy to switch between products

WEAKNESSES OF SQL:
  ✗ Horizontal scaling is hard (sharding is complex)
  ✗ Schema changes require migrations (downtime risk)
  ✗ Not ideal for semi-structured or evolving data
  ✗ Performance degrades with very large tables without careful indexing/partitioning
  ✗ Single primary for writes (write bottleneck at scale)

NoSQL DATABASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BASE MODEL (vs ACID):
  Basically Available:  System is available even if some nodes fail
  Soft-state:           State may change over time (even without input)
  Eventually Consistent: All replicas will converge to same value eventually

NoSQL TYPES:

1. DOCUMENT STORES (MongoDB, Couchbase, Firestore)
   Stores JSON-like documents. Each document can have different schema.
   
   {
     "_id": "user123",
     "name": "Alice",
     "email": "alice@example.com",
     "addresses": [
       {"type": "home", "city": "NYC"},
       {"type": "work", "city": "SF"}
     ]
   }
   
   Query by any field, supports nested documents.
   Great for: Product catalogs, user profiles, content management, blogs
   
   MongoDB features: Rich query language, aggregation pipeline, geo queries,
                     schema validation, transactions (v4+), Atlas (managed)
   
   When to use:
   ✓ Schema evolves frequently
   ✓ Nested/hierarchical data
   ✓ 1-to-many relationships within a document
   ✓ Flexible, semi-structured data

2. KEY-VALUE STORES (Redis, DynamoDB, Riak)
   Simple: key → value. Like a distributed hashmap.
   
   SET user:123 '{"name":"Alice","email":"alice@example.com"}'
   GET user:123
   
   Extremely fast for simple lookups.
   DynamoDB also supports single-table design with sort keys for range queries.
   
   When to use:
   ✓ Session storage, caching
   ✓ Simple lookup by ID
   ✓ Counters, rate limiting
   ✓ Real-time leaderboards (Redis sorted sets)

3. WIDE-COLUMN STORES (Cassandra, HBase, Google Bigtable)
   Tables with rows and columns, but each row can have different columns.
   Primary key consists of partition key + optional clustering columns.
   
   Data is distributed by partition key across nodes.
   Sorted within partition by clustering columns.
   
   Cassandra table:
   CREATE TABLE messages (
     conversation_id UUID,
     message_id      TIMEUUID,
     sender_id       UUID,
     content         TEXT,
     PRIMARY KEY (conversation_id, message_id)
   ) WITH CLUSTERING ORDER BY (message_id DESC);
   
   Query: SELECT * FROM messages WHERE conversation_id = ? LIMIT 50
   
   Cassandra characteristics:
   - Leaderless replication (no single master)
   - Tunable consistency: ANY, ONE, QUORUM, ALL
   - Extremely high write throughput (LSM-tree storage)
   - Great for time-series, IoT, chat messages, event logs
   
   When to use:
   ✓ Time-series data (metrics, IoT, logs)
   ✓ Massive write throughput
   ✓ Data that is naturally partitioned by a key
   ✓ Global distribution with tunable consistency

4. GRAPH DATABASES (Neo4j, Amazon Neptune, JanusGraph)
   Data stored as nodes (entities) and edges (relationships).
   Perfect for relationship-heavy data.
   
   Nodes: (User), (Product), (Category)
   Edges: (User)-[PURCHASED]->(Product)
          (User)-[FOLLOWS]->(User)
          (Product)-[BELONGS_TO]->(Category)
   
   Query language: Cypher (Neo4j), Gremlin
   MATCH (u:User)-[:FOLLOWS*2]->(friend:User)  ← 2nd-degree friends
   
   When to use:
   ✓ Social networks (friend of a friend)
   ✓ Recommendation engines (what did similar users buy?)
   ✓ Fraud detection (suspicious pattern in transaction graph)
   ✓ Knowledge graphs (semantic relationships)
   ✓ Network topology (infrastructure dependencies)

5. TIME-SERIES DATABASES (InfluxDB, TimescaleDB, Prometheus)
   Optimized for time-stamped data (metrics, events, IoT).
   
   Characteristics:
   - Automatic downsampling (aggregate old data)
   - Efficient storage (delta encoding, compression)
   - Time-range queries are very fast
   - Retention policies (auto-delete old data)
   
   InfluxDB data model:
   measurement,tag_key=tag_val field_key=field_val timestamp
   cpu,host=server1 usage=72.3 1712000000000000000
   
   When to use:
   ✓ Infrastructure monitoring (CPU, memory, disk)
   ✓ Application metrics (request rate, error count)
   ✓ IoT sensor readings
   ✓ Financial price history

REAL WORLD EXAMPLES:
  Payments (Stripe):         PostgreSQL (ACID required)
  Social graph (Facebook):   MySQL + TAO (custom graph cache)
  User sessions (Netflix):   Cassandra (key-value, massive scale)
  Chat messages (Discord):   Cassandra (time-series, write-heavy)
  Product catalog (Amazon):  DynamoDB (flexible, scale)
  Analytics (Uber):          ClickHouse (OLAP, fast aggregations)
  Search (Elasticsearch):    Elasticsearch
  Ads targeting (LinkedIn):  Kafka + Espresso (custom NoSQL)

POLYGLOT PERSISTENCE:
  Modern systems use multiple storage systems — the right tool per use case.
  Example (e-commerce):
    User accounts:        PostgreSQL (ACID, relational)
    Session data:         Redis (in-memory key-value)
    Product search:       Elasticsearch (full-text search)
    Product images:       S3 (object storage)
    Orders:               PostgreSQL (ACID transactions)
    Analytics:            BigQuery / ClickHouse (OLAP)
    Recommendations:      Neo4j or custom ML
    Notification queue:   Kafka or SQS
