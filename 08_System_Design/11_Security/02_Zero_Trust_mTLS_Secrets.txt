SECTION 1 — ZERO TRUST ARCHITECTURE
================================================================================

Q1: What is Zero Trust Architecture? How does it differ from perimeter security?

A: TRADITIONAL PERIMETER SECURITY ("Castle and Moat"):
   - Once inside the network (VPN, corporate LAN), you are trusted
   - Internal services call each other without authentication
   - Single point of failure: if perimeter is breached, attacker has full access

   ZERO TRUST ("Never Trust, Always Verify"):
   Core principle: Trust no network, no user, no device, no service by default —
   even inside your own data center or VPC. Every request must be:
   1. AUTHENTICATED: prove who you are
   2. AUTHORIZED: prove you are allowed to do this
   3. ENCRYPTED: data in transit always encrypted
   4. AUDITED: every access logged

   ZERO TRUST PILLARS:
   ┌─────────────────────────────────────────────────────────────────────┐
   │ 1. IDENTITY  → Every user and service has a verified identity       │
   │ 2. DEVICE    → Device health verified before access granted         │
   │ 3. NETWORK   → Network location provides NO implicit trust          │
   │ 4. APPLICATION → Micro-segmentation; per-request authorization      │
   │ 5. DATA      → Data classified and protected at rest and in transit │
   │ 6. VISIBILITY → Continuous monitoring; assume breach posture        │
   └─────────────────────────────────────────────────────────────────────┘

   PRACTICAL ZERO TRUST IN MICROSERVICES:
   - Service A calls Service B → must present a short-lived JWT or mTLS certificate
   - Authorization checked at service boundary (not just at API gateway)
   - Minimal blast radius: compromise of one service does NOT grant access to all others
   - Network policies (Kubernetes NetworkPolicy) restrict service-to-service paths

──────────────────────────────────────────────────────────────────────────────
Q2: How do you implement Zero Trust between microservices in Kubernetes?

A: IMPLEMENTATION LAYERS:

   LAYER 1 — mTLS (mutual TLS via service mesh):
   - Use Istio or Linkerd; each service gets a certificate from the mesh CA
   - All service-to-service traffic encrypted and mutually authenticated
   - Istio PeerAuthentication: enforce STRICT mTLS (no plaintext allowed)

   LAYER 2 — Authorization Policies:
   # Istio AuthorizationPolicy: only BillingService can call SubscriberService
   apiVersion: security.istio.io/v1beta1
   kind: AuthorizationPolicy
   metadata:
     name: subscriber-service-policy
     namespace: telecom
   spec:
     selector:
       matchLabels:
         app: subscriber-service
     rules:
     - from:
       - source:
           principals: ["cluster.local/ns/telecom/sa/billing-service"]
       to:
       - operation:
           methods: ["GET"]
           paths: ["/subscribers/*"]

   LAYER 3 — JWT validation for external requests:
   - API Gateway validates JWT from external clients
   - Passes claims as headers to downstream services (X-User-Id, X-Roles)
   - Services validate the injected headers trust origin (only accept from gateway)

   LAYER 4 — Network policies:
   # Only allow BillingService to call SubscriberService on port 8080
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: subscriber-service-netpol
   spec:
     podSelector:
       matchLabels:
         app: subscriber-service
     ingress:
     - from:
       - podSelector:
           matchLabels:
             app: billing-service
       ports:
       - port: 8080

SECTION 2 — MUTUAL TLS (mTLS)
================================================================================

Q3: Explain how mTLS works and how it differs from standard TLS.

A: STANDARD TLS (one-way):
   1. Client connects to server
   2. Server presents its certificate → client verifies (HTTPS)
   3. Server trusts the client implicitly
   Used by: browsers → web servers

   MUTUAL TLS (two-way):
   1. Client connects to server
   2. Server presents certificate → client verifies
   3. CLIENT also presents its own certificate → server verifies
   4. Both sides authenticated; encrypted channel established
   Used by: service-to-service communication, IoT devices, enterprise APIs

   mTLS CERTIFICATE FIELDS (X.509):
   - Subject: CN=billing-service, O=telecom-corp
   - Subject Alternative Name (SAN): billing-service.telecom.svc.cluster.local
   - Issuer: CN=Telecom Internal CA
   - Valid for: 24 hours (short-lived → automatic rotation)

──────────────────────────────────────────────────────────────────────────────
Q4: What are the challenges of mTLS at scale?

A: CHALLENGES AND SOLUTIONS:

   1. CERTIFICATE ROTATION AT SCALE:
      Challenge: Thousands of services each with a certificate; rotating manually = impossible
      Solution: SPIFFE/SPIRE — automated certificate issuance and rotation
               - Each workload gets a SPIFFE ID: spiffe://telecom.com/ns/billing/sa/billing-service
               - Short TTL (1h); auto-rotated by the agent
               - Service mesh (Istio, Linkerd) integrates SPIRE automatically

   2. CERTIFICATE DISTRIBUTION:
      Challenge: Certificate must be injected into each pod securely
      Solution: Kubernetes cert-manager + sidecar injection
               - cert-manager auto-creates TLS secrets from cluster CA
               - Sidecar proxy (Envoy in Istio) handles TLS termination
               - App code never touches certificates directly

   3. PERFORMANCE OVERHEAD:
      Challenge: TLS handshake adds latency to every new connection
      Solution: HTTP/2 + connection pooling → one TLS handshake per connection
               - Istio uses HTTP/2 between sidecars → multiplexed streams
               - Overhead: ~1ms per new connection; negligible with pooling

   4. DEBUGGING:
      Challenge: Traffic is encrypted → can't use tcpdump/Wireshark easily
      Solution: Istio Kiali for traffic visualization; envoy access logs;
               Jaeger for distributed tracing (traces not encrypted)

   5. LEGACY SERVICES:
      Challenge: Cannot add mTLS to legacy services immediately
      Solution: Istio PeerAuthentication PERMISSIVE mode → accepts mTLS and plaintext
               → Migrate gradually, then switch to STRICT

SECTION 3 — OAUTH2 AND OIDC IN MICROSERVICES
================================================================================

Q5: How does OAuth2/OIDC work in a microservices architecture?

A: ACTORS:
   - Resource Owner: the user (subscriber)
   - Client: the mobile app or web portal
   - Authorization Server: Keycloak, Auth0, AWS Cognito
   - Resource Server: your microservices (BillingService, SubscriberService)

   TOKEN TYPES:
   - Access Token (JWT): short-lived (15 min); presented with every API call
   - Refresh Token: long-lived (days/weeks); used to get new access token
   - ID Token (OIDC): identity information about the logged-in user

   FLOW (Authorization Code + PKCE for SPAs/mobile):
   1. App redirects user to Auth Server login page
   2. User authenticates; Auth Server issues authorization code
   3. App exchanges code for access token + refresh token (with PKCE)
   4. App sends access token in Authorization: Bearer <token> header
   5. API Gateway validates token signature against Auth Server's JWKS endpoint
   6. Gateway extracts claims (userId, roles) and passes to microservices

   JWT CLAIM EXAMPLE:
   {
     "sub": "subscriber-7891",
     "name": "John Smith",
     "roles": ["SUBSCRIBER", "PREMIUM"],
     "msisdn": "447700900001",
     "iss": "https://auth.telecom.com",
     "exp": 1699999999,
     "iat": 1699999799
   }

   SERVICE-TO-SERVICE (no user involved) — Client Credentials flow:
   1. BillingService requests token from Auth Server using client_id + client_secret
   2. Auth Server returns access token (machine-to-machine scope)
   3. BillingService calls SubscriberService with the token
   4. SubscriberService validates token and checks scope: "billing:read"

   SPRING SECURITY RESOURCE SERVER:
   @EnableWebSecurity
   public class SecurityConfig {
       @Bean
       SecurityFilterChain configure(HttpSecurity http) throws Exception {
           return http
               .oauth2ResourceServer(oauth2 -> oauth2
                   .jwt(jwt -> jwt.decoder(jwtDecoder())))
               .authorizeHttpRequests(auth -> auth
                   .requestMatchers("/subscribers/**").hasRole("BILLING")
                   .anyRequest().authenticated())
               .build();
       }

       @Bean
       JwtDecoder jwtDecoder() {
           return NimbusJwtDecoder
               .withJwkSetUri("https://auth.telecom.com/.well-known/jwks.json")
               .build();
       }
   }

SECTION 4 — SECRETS MANAGEMENT
================================================================================

Q6: How do you manage secrets (DB passwords, API keys) in a cloud-native system?

A: SECRETS MANAGEMENT TIERS:

   TIER 1 — NEVER DO THESE:
   ✗ Hardcode secrets in source code
   ✗ Store secrets in .properties files committed to git
   ✗ Pass secrets as environment variables set in CI/CD UI without rotation
   ✗ Log secrets (even partially)

   TIER 2 — MINIMUM (Kubernetes Secrets):
   - Store in K8s Secret (base64 encoded, NOT encrypted by default)
   - Enable encryption at rest: EncryptionConfiguration in K8s API server
   - Mount as environment variables or file volumes in pod spec
   - Limit access via RBAC: only the service account that needs the secret can read it

   TIER 3 — RECOMMENDED (External Secrets Operator + Vault):
   Architecture:
   Vault (HashiCorp) ←→ External Secrets Operator ←→ Kubernetes Secrets ← Pod

   - Vault stores the real secret, rotates it automatically
   - External Secrets Operator syncs from Vault to K8s Secrets
   - Pod reads from K8s Secret (mounted as env var or file)
   - If Vault rotates the secret, ESO updates the K8s Secret; pod restarts

   TIER 4 — CLOUD-NATIVE (AWS Secrets Manager):
   - AWS Secrets Manager: store, rotate, audit API keys, DB passwords
   - AWS IAM role (via IRSA in EKS): pod gets IAM role → reads secret
   - No hardcoded credentials anywhere; rotation is automatic

   VAULT DYNAMIC SECRETS EXAMPLE:
   - Vault Database Secrets Engine generates a temporary DB user on demand
   - BillingService requests a DB credential from Vault → gets unique user + password
   - Credential is valid for 1 hour; automatically revoked after
   - If BillingService is compromised, credential expires without manual rotation

   SPRING BOOT + VAULT INTEGRATION:
   # application.yml
   spring:
     cloud:
       vault:
         uri: https://vault.telecom.internal
         authentication: KUBERNETES
         kubernetes:
           role: billing-service
     config:
       import: vault://secret/billing-service

   # Vault secret auto-injected:
   @Value("${db.password}") private String dbPassword;

Q7: How do you detect and respond to a compromised secret?

A: DETECTION:
   - Audit logs from Vault / AWS Secrets Manager: who accessed what, when
   - Anomaly detection: secret accessed from unexpected IP/service identity
   - SIEM rules: alert on off-hours secret access, high-volume access

   RESPONSE (INCIDENT RUNBOOK):
   1. ROTATE immediately: regenerate the secret in Vault/Secrets Manager
   2. REVOKE old secret: ensure old value is invalid
   3. REDEPLOY services: force restart to pick up new secret
   4. AUDIT: check logs for unauthorized use of the compromised secret
   5. ROOT CAUSE: how was it exposed? Fix the gap (git history, log, misconfigured RBAC)

QUICK REFERENCE CHEAT SHEET
================================================================================

ZERO TRUST: Never trust, always verify. Authenticate + authorize every request.
PILLARS: Identity | Device | Network | Application | Data | Visibility

mTLS:
  Standard TLS: server proves identity to client
  mTLS: BOTH sides prove identity via certificates
  At scale: SPIFFE/SPIRE for automated certificate lifecycle
  Service mesh (Istio/Linkerd): transparent mTLS without app code changes

OAUTH2 FLOWS:
  User-facing apps: Authorization Code + PKCE
  Service-to-service: Client Credentials
  Token validation: API Gateway validates JWT via JWKS endpoint

SECRETS HIERARCHY:
  Worst: hardcoded | Better: K8s Secret + RBAC | Best: Vault + dynamic secrets
  Cloud: AWS Secrets Manager + IAM role (IRSA) | Never log or expose secrets

SPRING SECURITY:
  @EnableWebSecurity + SecurityFilterChain
  oauth2ResourceServer(jwt()) + JwtDecoder with jwkSetUri
  authorizeHttpRequests: role-based path restrictions
