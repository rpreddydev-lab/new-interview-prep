1. THE BIG PICTURE — JS RUNTIME MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌─────────────────────────────────────────────────┐
  │              JavaScript Runtime                 │
  │  ┌──────────────┐   ┌──────────────────────┐   │
  │  │  JS Engine   │   │     Web / Node APIs  │   │
  │  │  ┌────────┐  │   │  setTimeout, fetch,  │   │
  │  │  │  Heap  │  │   │  DOM events, I/O…    │   │
  │  │  └────────┘  │   └──────────────────────┘   │
  │  │  ┌────────┐  │   ┌──────────┐ ┌──────────┐  │
  │  │  │ Stack  │  │   │Microtask │ │Callback  │  │
  │  │  └────────┘  │   │  Queue   │ │  Queue   │  │
  │  └──────────────┘   └──────────┘ └──────────┘  │
  │                         ↑ Event Loop ↑          │
  └─────────────────────────────────────────────────┘

Components:
  • JS Engine     – parses & executes JS code (V8, SpiderMonkey, JSC)
  • Heap          – unstructured memory pool; object storage
  • Call Stack    – LIFO stack tracking execution contexts
  • Web/Node APIs – browser/Node provide async capabilities outside engine
  • Callback Queue (Macro) – holds setTimeout/setInterval/I/O callbacks
  • Microtask Queue        – holds Promise .then, queueMicrotask callbacks
  • Event Loop    – continuously checks if stack is empty, then pushes queued work

2. PARSING — FROM SOURCE CODE TO AST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Step 1: LEXING / TOKENIZING
  Source code → stream of tokens
  "let x = 5 + 3;"  →  [let] [x] [=] [5] [+] [3] [;]

Step 2: PARSING → AST (Abstract Syntax Tree)
  Tokens are structured into a tree representing the grammatical structure.

  AST for  "let x = 5 + 3":
  VariableDeclaration
    └── VariableDeclarator
          ├── Identifier: x
          └── BinaryExpression (+)
                ├── Literal: 5
                └── Literal: 3

  Tools: AST Explorer (astexplorer.net) shows the AST for any JS code.

Step 3: BYTECODE / MACHINE CODE (engine-specific)
  AST → Bytecode (interpreted by Ignition in V8) → Optimized machine code
  (compiled by TurboFan in V8) for hot code paths.

3. EXECUTION CONTEXT IN DETAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each Execution Context (EC) contains:
  1. Variable Environment  – stores var, function declarations, arguments
  2. Lexical Environment   – stores let/const (block-scoped), outer scope ref
  3. this binding          – depends on how the function was called

Scope Chain:
  When a variable is accessed, JS looks in the current EC, then outer EC,
  then outer's outer, all the way to global. This chain is determined
  LEXICALLY (where code is written), not dynamically.

  let outer = "global";
  function outer() {
    let mid = "mid";
    function inner() {
      let deep = "deep";
      console.log(outer); // found in grandparent scope
    }
    inner();
  }

4. MEMORY: STACK vs HEAP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  STACK MEMORY (primitives + references):
  - Stores: numbers, strings, booleans, null, undefined, symbols, bigints
  - Also stores the REFERENCE (pointer) to heap objects
  - Fixed-size, fast access, LIFO managed
  - Automatically freed when function exits

  HEAP MEMORY (objects, arrays, functions):
  - Dynamic allocation
  - Managed by Garbage Collector
  - Closures keep heap allocations alive

  let a = 5;              // 5 stored on stack
  let b = { x: 5 };      // reference on stack, { x:5 } on heap
  let c = b;              // c holds same reference
  c.x = 99;
  console.log(b.x);      // 99 — b and c point to same heap object

5. GARBAGE COLLECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Algorithm: Mark-and-Sweep
  1. GC starts from "roots" (global variables, call stack)
  2. Traverses all objects reachable from roots — marks them
  3. Sweeps (deletes) any object NOT marked as reachable

Memory Leak Examples:
  a) Global variables:
     function leak() { forgottenVar = "oops"; }  // no var/let/const = global

  b) Closures holding large objects:
     function createLeak() {
       const bigData = new Array(1e6).fill("data");
       return () => bigData[0]; // bigData can't be GC'd
     }

  c) Detached DOM nodes:
     let el = document.getElementById("btn");
     document.body.removeChild(el);
     // el still referenced in JS → node not GC'd

  d) Event listeners not removed:
     element.addEventListener("click", handler);
     // if element removed from DOM but handler still registered → leak

  e) setInterval not cleared:
     const id = setInterval(() => ..., 1000);
     // must clearInterval(id) when done

6. THE EVENT LOOP (SIMPLIFIED)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Execute all synchronous code in the call stack
  2. After stack is empty, drain ENTIRE microtask queue (Promises, etc.)
  3. Pick ONE macrotask from callback queue (setTimeout, I/O)
  4. Execute it (it may generate more microtasks)
  5. Drain microtask queue again
  6. Repeat

  console.log("1");
  setTimeout(() => console.log("2"), 0);
  Promise.resolve().then(() => console.log("3"));
  console.log("4");

  Output: 1, 4, 3, 2
  Explanation:
    "1" and "4" → synchronous (stack)
    "3"         → microtask queue (Promises drain first)
    "2"         → macrotask queue (setTimeout runs after microtasks)

7. HOW SCRIPTS LOAD IN BROWSER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  <script src="app.js">           – PARSER BLOCKING: stops HTML parsing until
                                    script is fetched + executed
  <script src="app.js" defer>     – fetched async, executes AFTER HTML parsed,
                                    in order; good for most scripts
  <script src="app.js" async>     – fetched async, executes IMMEDIATELY when
                                    ready (may interrupt parsing); good for
                                    independent scripts like analytics
  <script type="module">          – always deferred, strict mode by default,
                                    supports top-level await

  defer vs async:
  - Both fetch the script without blocking HTML parsing
  - defer: execution is ordered & happens after DOM is ready
  - async: execution is unordered & can happen at any time

8. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Explain the difference between the call stack and the event loop.
A: The call stack is a LIFO structure tracking currently executing functions.
   The event loop is a mechanism that watches the call stack and callback
   queues — when the stack empties, it pushes the next queued callback.

Q: Why does setTimeout(fn, 0) not execute immediately?
A: Even with delay=0, setTimeout is a macrotask and goes to the callback
   queue. The event loop only picks it up after the current call stack AND
   the microtask queue are both empty.

Q: What is the difference between concurrency and parallelism in JS context?
A: JS achieves CONCURRENCY through the event loop (single-threaded, tasks
   interleaved). True PARALLELISM requires Web Workers (separate threads).

Q: How does JavaScript manage memory?
A: Via automatic garbage collection using mark-and-sweep. Developer must
   avoid memory leaks by clearing timers, removing event listeners, and
   avoiding unnecessary closures over large data.

Q: What happens when you access an undefined variable vs an undeclared variable?
A: Undefined variable (declared but no value): evaluates to undefined.
   Undeclared variable (never declared): throws ReferenceError.
   Exception: typeof undeclaredVar → returns "undefined" (doesn't throw).
