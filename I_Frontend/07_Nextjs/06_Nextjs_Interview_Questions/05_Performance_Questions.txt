SECTION 1: CORE WEB VITALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are Core Web Vitals and how do they relate to Next.js?
A: Google's metrics for real-world user experience:
   LCP (Largest Contentful Paint): When the main content loads. Target: < 2.5s.
     Next.js helps: SSG/ISR serve HTML from CDN (fast), next/image priority
     preloads LCP image, streaming shows content fast.
   INP (Interaction to Next Paint): Responsiveness to user input. Target: < 200ms.
     Next.js helps: Server Components reduce JS bundle (less to parse/execute),
     code splitting via next/dynamic.
   CLS (Cumulative Layout Shift): Visual stability. Target: < 0.1.
     Next.js helps: next/image reserves space (no jump), next/font size-adjust
     prevents font CLS, explicit width/height on media elements.

Q: How do you measure Core Web Vitals in a Next.js app?
A: Built-in: use the reportWebVitals function (Pages Router) or next/vitals.
   Vercel Analytics: automatically captures CWV for all routes.
   Google PageSpeed Insights: analyze production URL.
   Lighthouse in DevTools: lab measurement (not real user).
   Chrome User Experience Report (CrUX): real user data by URL.
   // pages/_app.tsx (Pages Router):
   export function reportWebVitals(metric) {
     if (metric.label === 'web-vital') {
       analytics.send({ name: metric.name, value: metric.value });
     }
   }

Q: What causes poor CLS in Next.js and how do you fix it?
A: Common causes and fixes:
   - Images without dimensions: use next/image (auto-reserves space)
   - Fonts loading late: use next/font (self-hosted, size-adjust fallback)
   - Dynamic content injected above existing content: reserve space with CSS min-height
   - Ads/embeds without dimensions: always set width/height or aspect-ratio
   - Skeleton loaders must match final content dimensions

SECTION 2: BUNDLE OPTIMIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you analyze and reduce bundle size in Next.js?
A: Steps:
   1. Run next build and check the output table (shows each route's bundle size)
   2. Use @next/bundle-analyzer: ANALYZE=true npm run build → visual treemap
   3. Identify large dependencies (moment.js → date-fns, lodash → lodash-es)
   4. Use Server Components for libraries only needed on server
   5. Dynamic imports for heavy client components: next/dynamic
   6. Import only what you need (named imports): import { pick } from 'lodash-es'
   7. Set transpilePackages for packages that need it

Q: How does next/dynamic reduce bundle size?
A: next/dynamic wraps React.lazy() with SSR support. The component is split
   into a separate JS chunk loaded only when needed:
   const HeavyEditor = dynamic(() => import('./heavy-editor'));
   The HeavyEditor code is NOT in the initial bundle — it loads on demand.
   With { ssr: false }, the component is completely excluded from server render
   and only loads in the browser. Great for browser-only libraries (Leaflet, PDF).

Q: What is tree shaking and how does Next.js support it?
A: Tree shaking removes unused code at build time. Next.js's build system (SWC +
   Webpack/Turbopack) performs tree shaking on ES modules. To benefit:
   - Use ES modules (import/export), not CommonJS (require)
   - Use named imports: import { add } from 'math-lib' (not import mathLib)
   - Libraries must support ES module exports in package.json "exports" field
   - Avoid side-effectful imports that prevent tree shaking

Q: What is the "First Load JS" shown in next build output?
A: The amount of JavaScript transferred to the browser for the initial route load.
   Includes: framework runtime (React, Next.js), shared chunks, page-specific code.
   Next.js warns at > 130kB (orange) and > 170kB (red).
   Reduce with: Server Components (removed entirely), code splitting, removing unused deps.

SECTION 3: RENDERING AND CACHING PERFORMANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the most impactful rendering strategy choice for performance?
A: SSG/ISR: best performance — HTML served from CDN. No server processing per request.
   CDN TTFB: ~10-50ms.
   SSR: HTML generated per request — server processing adds latency. CDN TTFB: ~100-500ms.
   CSR: Empty HTML first, data loads in browser — slowest FCP/LCP.
   Best practice: default to SSG/ISR, use SSR only for personalized/real-time data,
   use CSR only for highly interactive client-side data.

Q: How does prefetching improve perceived performance?
A: The <Link> component automatically prefetches linked pages when they enter
   the viewport (in production). Next.js fetches the RSC payload for that route
   in the background. When user clicks, the page appears instantly — data
   is already cached. Static routes are fully prefetched; dynamic routes have
   loading states prefetched.
   Disable when not needed: <Link prefetch={false}> (e.g., nav with many links).

Q: What is the difference between using Promise.all vs sequential await in Server Components?
A: Sequential (waterfall):
   const user = await getUser(id);        // starts, waits ~100ms
   const posts = await getUserPosts(id);  // starts AFTER user, waits ~200ms
   // Total: ~300ms

   Parallel (Promise.all):
   const [user, posts] = await Promise.all([getUser(id), getUserPosts(id)]);
   // Both start simultaneously → total: ~200ms (slowest wins)
   Always use Promise.all for independent data fetches.

Q: How does the Router Cache improve navigation performance?
A: The Router Cache (client-side, in-memory) stores RSC payloads of visited routes.
   Navigating back to a previous page is instant — no server round-trip.
   Static routes stay cached 5 minutes; dynamic routes 30 seconds.
   Prefetched routes are also cached. This is why Next.js navigation feels instant
   compared to full page reloads.

Q: When does ISR NOT help with performance?
A: ISR serves stale (old) content to the FIRST request after expiration.
   That first request triggers background regeneration. So ISR still has a
   cold path for the "unlucky" first visitor after the cache expires. Mitigation:
   use on-demand revalidation via revalidatePath/revalidateTag from webhooks
   (invalidate immediately on content change instead of time-based).

SECTION 4: IMAGE AND FONT PERFORMANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the impact of image optimization on Core Web Vitals?
A: Images are the #1 cause of slow LCP. Unoptimized images are huge (4MB JPEGs)
   and slow on mobile. next/image: (1) lazy loads off-screen images (improves INP
   and bandwidth), (2) converts to WebP/AVIF (50-80% smaller), (3) serves size
   appropriate to device (no 2000px image on 400px mobile), (4) priority on LCP
   image adds preload link (faster LCP), (5) explicit dimensions prevent CLS.

Q: What is AVIF vs WebP and when does Next.js use each?
A: AVIF: ~50% smaller than WebP, ~70% smaller than JPEG. Slower to encode.
   WebP: ~25-30% smaller than JPEG/PNG. Fast encode.
   Next.js serves AVIF when browser supports it (Chrome, Firefox, most modern browsers).
   Falls back to WebP if no AVIF support, then original format.
   Configure: images: { formats: ['image/avif', 'image/webp'] }

Q: What is font-display: optional and when would you choose it?
A: optional: very brief block period (~100ms), if font hasn't loaded, use fallback
   for the entire page session (never swap mid-display). Best CLS score.
   Trade-off: users may see system font if on slow connection.
   Use when: brand font matters but CLS reduction is top priority.
   vs swap: shows system font then switches → FOUT (layout shift).
   For most apps: swap is the recommended default for brand consistency.

SECTION 5: PERFORMANCE ANTI-PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the most common Next.js performance anti-patterns?
A: 1. Using 'use client' too high in the tree — entire subtree becomes client code,
      bloats JS bundle. Fix: push 'use client' to the smallest interactive component.
   2. Sequential data fetching (waterfall) — fetch one, then another.
      Fix: Promise.all for independent data.
   3. SSR everything unnecessarily — page content that could be static (marketing).
      Fix: use SSG or ISR for content that doesn't change per user.
   4. No lazy loading — all heavy components in initial bundle.
      Fix: next/dynamic for non-critical heavy components.
   5. Missing next/image — raw <img> tags with no optimization.
      Fix: replace all <img> with next/image.
   6. No Suspense — entire page waits for slowest data source.
      Fix: Suspense boundaries around slow components.
   7. Fetching in useEffect without caching — refetch on every render.
      Fix: SWR or React Query for client-side data.
   8. Creating new Prisma client per request — connection pool exhaustion.
      Fix: global Prisma singleton.

Q: What is the "N+1 query problem" and how does it manifest in Next.js?
A: N+1: fetch a list (1 query), then for each item fetch related data (N queries).
   Example: fetch 10 posts → 10 separate author queries = 11 DB queries total.
   In App Router: happens when mapping over RSC children that each independently fetch:
   {posts.map(post => <Post id={post.id} />)}  // each Post component queries DB!
   Fix: Join data in the initial query (Prisma's include/select), or use DataLoader
   pattern for batching, or prefetch all needed data in the parent.

Q: How do you prevent excessive re-renders in a Next.js application?
A: 1. Use Server Components for static content (no React re-renders at all)
   2. Minimize 'use client' scope (fewer components that can re-render)
   3. Use useMemo, useCallback for expensive computations/stable references
   4. Use React.memo for components that receive the same props frequently
   5. Avoid creating new objects/arrays inline in JSX (creates new reference every render)
   6. Use Zustand/Jotai selectors to only re-render on relevant state slice changes
   7. useTransition for non-urgent state updates (keeps UI responsive)
