1. WHAT ARE SERVER ACTIONS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Server Actions are async functions that run EXCLUSIVELY on the server but can
be called directly from Client Components or forms without needing an API Route.

Key features:
  - Marked with 'use server' directive
  - Can be defined inline in a Server Component, or in a separate file
  - Can be called from a <form action={...}>, button onClick, or any event
  - Automatically create a POST endpoint internally (Next.js handles routing)
  - Can directly access DB, call private services, read server env vars
  - Support progressive enhancement (forms work without JS)

When to use Server Actions:
  ✓ Form submissions (create/update/delete)
  ✓ Database mutations
  ✓ Revalidating cached data after mutation
  ✓ Setting/deleting cookies
  ✓ Server-side redirects after form submission

2. 'use server' DIRECTIVE PLACEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option A — Inline in a Server Component:
  // app/posts/page.tsx (Server Component)
  export default function PostsPage() {
    async function createPost(formData: FormData) {
      'use server'; // marks THIS function as a Server Action
      const title = formData.get('title') as string;
      await prisma.post.create({ data: { title } });
      revalidatePath('/posts');
    }
    return (
      <form action={createPost}>
        <input name="title" />
        <button type="submit">Create Post</button>
      </form>
    );
  }

Option B — Dedicated actions file (recommended for reuse):
  // lib/actions.ts
  'use server'; // marks ALL exports in this file as Server Actions

  import { prisma } from './prisma';
  import { revalidatePath } from 'next/cache';

  export async function createPost(formData: FormData) {
    const title = formData.get('title') as string;
    await prisma.post.create({ data: { title } });
    revalidatePath('/posts');
  }

  export async function deletePost(id: string) {
    await prisma.post.delete({ where: { id } });
    revalidatePath('/posts');
  }

4. PASSING EXTRA ARGUMENTS WITH .bind()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Server Actions receive FormData as their last argument.
Use .bind() to pass additional arguments (e.g., the item ID for updates).

  // lib/actions.ts
  'use server';
  export async function updatePost(id: string, formData: FormData) {
    const title = formData.get('title') as string;
    await prisma.post.update({ where: { id }, data: { title } });
    revalidatePath('/posts');
  }

  // app/posts/[id]/edit/page.tsx (Server Component)
  import { updatePost } from '@/lib/actions';
  export default async function EditPage({ params }) {
    const { id } = await params;
    const post = await getPost(id);
    const updatePostWithId = updatePost.bind(null, id); // pre-bind the ID

    return (
      <form action={updatePostWithId}>
        <input name="title" defaultValue={post.title} />
        <button type="submit">Update</button>
      </form>
    );
  }

5. useFormStatus — PENDING STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

useFormStatus provides the pending state of the parent form's Server Action.
MUST be used in a CHILD component of the form (not the form itself).

  // components/submit-button.tsx
  'use client';
  import { useFormStatus } from 'react-dom';

  export function SubmitButton({ children }: { children: React.ReactNode }) {
    const { pending } = useFormStatus();
    return (
      <button type="submit" disabled={pending}>
        {pending ? 'Submitting...' : children}
      </button>
    );
  }

  // Usage:
  import { createPost } from '@/lib/actions';
  import { SubmitButton } from '@/components/submit-button';

  export default function CreateForm() {
    return (
      <form action={createPost}>
        <input name="title" />
        <SubmitButton>Create Post</SubmitButton>
      </form>
    );
  }

6. useActionState — FORM STATE & VALIDATION ERRORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

useActionState (React 19, was useFormState in React 18) manages the Server
Action's return value for displaying errors and feedback.

  // lib/actions.ts
  'use server';
  import { z } from 'zod';

  const PostSchema = z.object({
    title: z.string().min(3, 'Title must be at least 3 characters'),
    content: z.string().min(10, 'Content must be at least 10 characters'),
  });

  type ActionState = {
    errors: { title?: string[]; content?: string[] };
    message: string;
  };

  export async function createPost(
    prevState: ActionState,
    formData: FormData
  ): Promise<ActionState> {
    const validatedFields = PostSchema.safeParse({
      title: formData.get('title'),
      content: formData.get('content'),
    });

    if (!validatedFields.success) {
      return {
        errors: validatedFields.error.flatten().fieldErrors,
        message: 'Validation failed.',
      };
    }

    try {
      await prisma.post.create({ data: validatedFields.data });
      revalidatePath('/posts');
      redirect('/posts'); // redirect throws — must be outside try/catch
    } catch (error) {
      if (isRedirectError(error)) throw error; // re-throw redirect
      return { errors: {}, message: 'Database Error: Failed to create post.' };
    }
  }

  // components/create-post-form.tsx
  'use client';
  import { useActionState } from 'react';
  import { createPost } from '@/lib/actions';

  const initialState = { errors: {}, message: '' };

  export function CreatePostForm() {
    const [state, formAction] = useActionState(createPost, initialState);
    return (
      <form action={formAction}>
        <div>
          <input name="title" />
          {state.errors?.title?.map(err => (
            <p key={err} className="text-red-500">{err}</p>
          ))}
        </div>
        <div>
          <textarea name="content" />
          {state.errors?.content?.map(err => (
            <p key={err} className="text-red-500">{err}</p>
          ))}
        </div>
        {state.message && <p className="text-red-500">{state.message}</p>}
        <button type="submit">Create Post</button>
      </form>
    );
  }

8. REVALIDATION AFTER MUTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

After mutating data, invalidate cached pages to reflect fresh data:

  // Revalidate a specific path
  import { revalidatePath } from 'next/cache';
  await prisma.post.create({ data: { title } });
  revalidatePath('/posts');       // revalidates the /posts page
  revalidatePath('/posts/[id]', 'page'); // specific dynamic page

  // Revalidate by cache tag
  import { revalidateTag } from 'next/cache';
  revalidateTag('posts');         // revalidates all tagged 'posts'

  // Tags are set during fetch:
  const posts = await fetch('/api/posts', { next: { tags: ['posts'] } });

  // REDIRECT after successful mutation
  import { redirect } from 'next/navigation';
  await prisma.post.create({ data: { title } });
  revalidatePath('/posts');
  redirect('/posts'); // redirects the user after action completes

  // IMPORTANT: redirect() throws an error internally (NEXT_REDIRECT).
  // If you use try/catch, you MUST re-throw it:
  try {
    await createPostInDB(data);
    redirect('/posts'); // throws NEXT_REDIRECT
  } catch (err) {
    if (isRedirectError(err)) throw err; // MUST re-throw!
    return { message: 'Database error' };
  }

9. SECURITY IN SERVER ACTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Server Actions are POST endpoints. You must secure them:

  // ALWAYS validate and authenticate in Server Actions
  import { auth } from '@/auth';
  import { z } from 'zod';

  export async function deletePost(id: string) {
    'use server';

    // 1. Authenticate
    const session = await auth();
    if (!session?.user) throw new Error('Unauthorized');

    // 2. Authorize
    const post = await prisma.post.findUnique({ where: { id } });
    if (post?.authorId !== session.user.id) throw new Error('Forbidden');

    // 3. Validate inputs
    const validId = z.string().uuid().parse(id);

    // 4. Perform mutation
    await prisma.post.delete({ where: { id: validId } });
    revalidatePath('/posts');
  }

  // CSRF Protection: Next.js automatically adds CSRF protection for
  // form actions. For programmatic calls, ensure proper auth checks.

10. SERVER ACTIONS vs API ROUTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Aspect                 | Server Actions        | API Routes (Route Handlers)
  ─────────────────────  | ────────────────────  | ───────────────────────────
  Best for               | Form mutations, CRUD  | Public APIs, webhooks
  Protocol               | POST (auto)           | Any HTTP method
  Invocation             | Direct function call  | fetch('/api/...')
  Form integration       | Native <form action>  | Need custom fetch
  Return type            | Any JS value          | Response object
  Progressive enhancement| ✓ (works w/o JS)      | ✗
  External callers       | ✗ (internal only)     | ✓
  Revalidation           | Built-in              | Manual fetch + revalidate
  Type safety            | Full end-to-end       | Needs tRPC/Zod

  Rule of thumb:
  - Use Server Actions for mutations from your own UI
  - Use Route Handlers for public endpoints, mobile apps, webhooks, 3rd parties

11. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What are Server Actions and what problem do they solve?
A:  Server Actions are async server-only functions callable directly from the
    UI (forms or event handlers) without writing explicit API routes. They
    solve the boilerplate of creating a fetch call to a POST endpoint for every
    mutation. They also enable progressive enhancement — forms using Server
    Actions work without JavaScript.

Q2: What's the difference between 'use server' and 'use client'?
A:  'use client' marks a file/component as a client boundary — code below it
    runs in the browser. 'use server' marks a function as a Server Action —
    it runs exclusively on the server but can be called from the client.
    'use server' in a file makes ALL exports Server Actions; in a function,
    it marks just that function.

Q3: How do you show a loading state while a Server Action is pending?
A:  Two ways: (1) useFormStatus from react-dom — use in a child component of
    the form, gives { pending } boolean for disabling buttons. (2) useTransition
    from react — wrap the action call in startTransition, get isPending boolean.

Q4: How do you handle validation errors in Server Actions?
A:  Use useActionState (React 19) or useFormState (React 18). The Server Action
    receives prevState as its first argument and returns an error state object.
    The hook provides [state, formAction] — state contains errors/messages.
    Use Zod's safeParse to validate and return field-level errors.

Q5: How does redirect() work inside a Server Action?
A:  redirect() from 'next/navigation' throws a special NEXT_REDIRECT error
    internally. If you have a try/catch block, you MUST re-throw redirect errors
    or the redirect will silently fail. Use isRedirectError() from next/dist/...
    to detect and re-throw it.

Q6: Are Server Actions secure by default?
A:  They are POST endpoints with CSRF protection for form actions, but you
    MUST manually handle authentication and authorization. Always: (1) check
    session/auth, (2) validate inputs with Zod, (3) check that the user owns
    the resource being modified. Never trust client-provided IDs without
    verifying ownership server-side.

  They eliminate the API Route boilerplate for form mutations and enable
  progressive enhancement. Always validate + authenticate inside them.
