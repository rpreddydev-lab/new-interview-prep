  ISR (INCREMENTAL STATIC REGENERATION) — INTERVIEW PREP GUIDE

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. WHAT IS ISR?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Incremental Static Regeneration is the best of both worlds between SSG and SSR.
It pre-renders pages at build time (like SSG) but allows them to be updated
AFTER deployment without a full rebuild (like SSR).

Key idea: "Stale-While-Revalidate"
  - Serve the cached (possibly stale) page immediately
  - Regenerate the page in the background
  - Next request gets the fresh version

Introduced in Next.js 9.5. This was a breakthrough feature.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. ISR — PAGES ROUTER (revalidate option)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Just add `revalidate` to getStaticProps:

  // pages/blog/[slug].tsx
  export const getStaticProps: GetStaticProps = async ({ params }) => {
    const post = await fetchPost(params!.slug as string);

    return {
      props: { post },
      revalidate: 60,  // seconds: attempt regeneration every 60 seconds
    };
  };

How it works:
  1. Build time: page generated as static HTML, cached on CDN
  2. Request at t=0: cached HTML served, cache age = 0
  3. Request at t=30s: cached HTML served (still valid, age < 60s)
  4. Request at t=65s: cached HTML served (stale, age > 60s)
                       + background regeneration triggered
  5. Request at t=66s: NEW HTML served (freshly generated)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. ISR TIMELINE DIAGRAM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Time:   0s        60s       61s       62s
          │         │         │         │
  Event:  Build   Request1  Request2  Request3
          │         │         │         │
  Serve:  Static  Cached    Stale     Fresh
                            (triggers  (from
                            regen)     regen)

  The first request AFTER the revalidate window gets the stale page AND
  triggers regeneration. The NEXT request after that gets the fresh page.

4. ISR — APP ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Two ways to configure ISR in App Router:

  A) Route segment config (applies to whole segment):
     // app/blog/[slug]/page.tsx
     export const revalidate = 3600;  // revalidate every hour

     export default async function BlogPost({ params }) {
       const post = await getPost(params.slug);
       return <article>{post.content}</article>;
     }

  B) Per-fetch configuration:
     // Revalidate this specific fetch every 60 seconds
     const data = await fetch('https://api.example.com/data', {
       next: { revalidate: 60 },
     });

     // Never cache (SSR)
     const freshData = await fetch('https://api.example.com/data', {
       cache: 'no-store',
     });

     // Cache indefinitely (SSG)
     const staticData = await fetch('https://api.example.com/data', {
       cache: 'force-cache',  // default in App Router
     });

5. ON-DEMAND REVALIDATION (KEY INTERVIEW TOPIC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Instead of waiting for the revalidate timer, trigger regeneration immediately
(e.g., when a CMS publishes content). Introduced in Next.js 12.2.

Pages Router (revalidatePath):
  // pages/api/revalidate.ts
  export default async function handler(req, res) {
    // Security: check secret token
    if (req.query.secret !== process.env.REVALIDATION_SECRET) {
      return res.status(401).json({ message: 'Invalid token' });
    }

    const { slug } = req.body;

    try {
      // Revalidate a specific path
      await res.revalidate(`/blog/${slug}`);
      return res.json({ revalidated: true });
    } catch (err) {
      return res.status(500).send('Error revalidating');
    }
  }

App Router (revalidatePath + revalidateTag):
  // app/api/revalidate/route.ts
  import { revalidatePath, revalidateTag } from 'next/cache';
  import { NextRequest, NextResponse } from 'next/server';

  export async function POST(request: NextRequest) {
    const secret = request.headers.get('x-revalidate-secret');
    if (secret !== process.env.REVALIDATION_SECRET) {
      return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
    }

    const { slug, tag } = await request.json();

    if (slug) {
      revalidatePath(`/blog/${slug}`);      // revalidate specific path
      revalidatePath('/blog');             // revalidate list page too
    }

    if (tag) {
      revalidateTag(tag);                  // revalidate all pages with this tag
    }

    return NextResponse.json({ revalidated: true, timestamp: Date.now() });
  }

Using cache tags:
  // Tag fetches for granular revalidation
  const post = await fetch(`https://api/posts/${id}`, {
    next: { tags: [`post-${id}`, 'posts'] },  // tag with multiple tags
  });

  // Revalidate everything tagged 'posts'
  revalidateTag('posts');  // revalidates all fetches with this tag

6. CMS INTEGRATION PATTERN WITH ISR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  CMS (Sanity/Contentful/etc.)
       │
       │  on publish/update
       ▼
  Webhook → POST /api/revalidate?secret=xxx
       │
       ▼
  next/cache: revalidatePath('/blog/[slug]')
       │
       ▼
  Next.js regenerates the page in background
       │
       ▼
  Next request serves fresh content from CDN

This gives you:
  - Static performance (CDN delivery)
  - Content freshness on demand (no time-based revalidation needed)
  - No full site rebuild on every content change

8. EDGE CASES & GOTCHAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. ISR does NOT guarantee the revalidate interval is exact.
   revalidate: 60 means "at least 60 seconds between regenerations",
   NOT "regenerate every 60 seconds exactly". The timer resets on each gen.

2. If regeneration fails (API down, DB error), the old stale page is served.
   This is GOOD — users always get something, never a blank error page.

3. On-demand revalidation is preferred over time-based for CMS integrations.
   Webhook-triggered revalidation means you only regenerate when needed.

4. Local development: ISR behavior isn't fully replicated. Pages regenerate
   on every request in dev mode. Test ISR in production or use `next build`.

5. revalidatePath invalidates the full page cache. revalidateTag is more
   precise — only invalidates fetches with that specific tag.

6. App Router fetch cache ≠ HTTP cache. Next.js has its own server-side
   cache that persists across requests (the Data Cache). This is separate
   from the browser's HTTP cache.

9. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is ISR and how does it differ from SSG and SSR?
A:  ISR combines SSG performance with the ability to update content after
    deployment. Pages are pre-rendered at build time (like SSG) but include
    a revalidate timer. After the timer expires, the next request triggers
    background regeneration. The user always gets a response (stale or fresh),
    never a loading delay. SSG never updates without rebuild; SSR regenerates
    every request (slower).

Q2: What is "stale-while-revalidate" behavior in ISR?
A:  When a page's revalidate window expires, the next request receives the
    stale (old) cached page immediately, AND triggers background regeneration.
    The request AFTER THAT gets the newly generated page. Users never wait for
    regeneration — they always get an instant response.

Q3: What is on-demand revalidation and when would you use it?
A:  On-demand revalidation lets you invalidate and regenerate specific pages
    programmatically (via revalidatePath() or revalidateTag()) instead of
    waiting for a time-based revalidate window. Use it with CMS webhooks:
    when an editor publishes content, the CMS calls your API endpoint which
    triggers revalidation of the affected pages — near-instant content updates
    without a full site rebuild.

Q4: What happens if a page regeneration fails during ISR?
A:  Next.js continues serving the last successfully generated version (stale
    page). The failed regeneration is silently retried on the next request.
    This is a key reliability benefit — your site never goes down because of a
    failed background regeneration.

Q5: How do you implement ISR in the App Router?
A:  Two ways:
    (1) Route segment: export const revalidate = 60; — applies to all fetches
    (2) Per-fetch: fetch(url, { next: { revalidate: 60 } })
    For on-demand: import revalidatePath/revalidateTag from 'next/cache' in
    Server Actions or Route Handlers.

Q6: How does revalidateTag work?
A:  You tag fetches with metadata: fetch(url, { next: { tags: ['products'] } }).
    Then call revalidateTag('products') to invalidate ALL fetches with that tag
    across all pages. More granular than revalidatePath — you can invalidate
    only the data that changed, not the entire page.
