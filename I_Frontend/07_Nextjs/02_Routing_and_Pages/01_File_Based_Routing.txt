1. WHAT IS FILE-BASED ROUTING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

File-based routing means the file system IS the router. You don't define routes
in a config file or with a <Routes> component — the location of files within
the pages/ (Pages Router) or app/ (App Router) directory automatically
determines the URL structure.

This is one of Next.js's most fundamental and powerful features.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. PAGES ROUTER FILE-BASED ROUTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

File structure → URL mapping:
  pages/index.tsx          → /
  pages/about.tsx          → /about
  pages/blog/index.tsx     → /blog
  pages/blog/first.tsx     → /blog/first
  pages/users/[id].tsx     → /users/:id  (dynamic)
  pages/[...slug].tsx      → /* (catch-all)
  pages/[[...slug]].tsx    → / and /* (optional catch-all)

Special files in pages/:
  pages/_app.tsx           → Global app wrapper (layouts, global CSS)
  pages/_document.tsx      → Custom HTML document (<html>, <body>)
  pages/_error.tsx         → Custom error page
  pages/404.tsx            → Custom 404 page
  pages/500.tsx            → Custom 500 page
  pages/api/               → API routes (not pages, no UI)

Example — pages/about.tsx:
  export default function About() {
    return <h1>About Page</h1>;
  }
  // Accessible at: http://localhost:3000/about

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. APP ROUTER FILE-BASED ROUTING (Next.js 13+)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In the App Router, FOLDERS define routes. Files inside folders have
special reserved names that serve specific purposes.

Route definition: A folder + page.tsx inside it = a route

  app/page.tsx                     → /
  app/about/page.tsx               → /about
  app/blog/page.tsx                → /blog
  app/blog/[slug]/page.tsx         → /blog/:slug
  app/users/[id]/settings/page.tsx → /users/:id/settings

Special files in app/:
  ┌─────────────────┬──────────────────────────────────────────────┐
  │ File            │ Purpose                                      │
  ├─────────────────┼──────────────────────────────────────────────┤
  │ page.tsx        │ Unique UI; makes the route accessible        │
  │ layout.tsx      │ Shared UI wrapper (persists across nav)      │
  │ loading.tsx     │ Streaming loading UI (automatic Suspense)    │
  │ error.tsx       │ Error boundary UI                            │
  │ not-found.tsx   │ 404 UI for this segment                      │
  │ template.tsx    │ Re-mounting layout (re-runs on every nav)    │
  │ default.tsx     │ Parallel route fallback                      │
  │ route.ts        │ API endpoint (no UI)                         │
  └─────────────────┴──────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. ROUTE GROUPS (App Router)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Wrap a folder name in parentheses → creates a route group that does NOT
affect the URL but allows you to organize files and share layouts.

  app/
  ├── (marketing)/
  │   ├── layout.tsx          ← Layout only for marketing pages
  │   ├── page.tsx            → /
  │   ├── about/page.tsx      → /about
  │   └── pricing/page.tsx    → /pricing
  ├── (auth)/
  │   ├── layout.tsx          ← Auth layout (no nav bar)
  │   ├── login/page.tsx      → /login
  │   └── register/page.tsx   → /register
  └── (dashboard)/
      ├── layout.tsx          ← Dashboard layout (sidebar)
      └── dashboard/page.tsx  → /dashboard

Use cases for route groups:
  1. Apply different layouts to different sections of the app
  2. Organize code without affecting URLs
  3. Multiple root layouts (different HTML structure per group)
  4. Opt segments into layouts without changing URL structure

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. PRIVATE FOLDERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Prefix a folder with underscore → _folderName → excluded from routing entirely.
Use for colocating utilities, components, and tests with routes.

  app/
  └── blog/
      ├── _components/        ← Not a route; blog-specific components
      │   └── PostCard.tsx
      ├── _utils/             ← Not a route; blog utilities
      │   └── mdx.ts
      └── [slug]/
          └── page.tsx        → /blog/:slug

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. THE <Link> COMPONENT — CLIENT-SIDE NAVIGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Never use <a href="/about"> for internal navigation in Next.js.
Use <Link> from 'next/link' for:
  - Client-side navigation (no full page reload)
  - Automatic prefetching (in viewport links are preloaded)
  - Preserves client-side state

  import Link from 'next/link';

  // Basic usage
  <Link href="/about">About</Link>

  // Dynamic route
  <Link href={`/users/${user.id}`}>Profile</Link>

  // Object form (with query params)
  <Link href={{ pathname: '/search', query: { q: 'react' } }}>Search</Link>

  // Replace instead of push (no browser back entry)
  <Link href="/dashboard" replace>Dashboard</Link>

  // Prefetch control (default: true in production)
  <Link href="/heavy-page" prefetch={false}>Heavy Page</Link>

Prefetching behavior:
  - In production: links in the viewport are automatically prefetched
  - Prefetching loads the page's React Server Component payload
  - NOT the full page — just the RSC payload (JSON)
  - Can be disabled per-link with prefetch={false}

7. PROGRAMMATIC NAVIGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pages Router:
  import { useRouter } from 'next/router';
  const router = useRouter();
  router.push('/dashboard');
  router.replace('/login');
  router.back();
  router.query.id  // access dynamic segment

App Router:
  import { useRouter } from 'next/navigation';  // NOTE: different import!
  const router = useRouter();
  router.push('/dashboard');
  router.replace('/login');
  router.back();
  router.refresh();  // re-fetch Server Components (no page reload)

  // For reading params in App Router:
  import { useParams, useSearchParams, usePathname } from 'next/navigation';
  const params = useParams();       // { id: '123' }
  const searchParams = useSearchParams();  // URLSearchParams
  const pathname = usePathname();   // '/users/123'

  // Server-side redirect (in Server Components, Server Actions):
  import { redirect } from 'next/navigation';
  redirect('/login');  // throws internally (don't catch)

  // Server-side redirect with status:
  import { permanentRedirect } from 'next/navigation';
  permanentRedirect('/new-path');  // 308

8. ACTIVE LINK STYLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  'use client';
  import Link from 'next/link';
  import { usePathname } from 'next/navigation';

  function NavLink({ href, children }) {
    const pathname = usePathname();
    const isActive = pathname === href || pathname.startsWith(href + '/');
    return (
      <Link href={href} className={isActive ? 'font-bold text-blue-600' : ''}>
        {children}
      </Link>
    );
  }

9. SHALLOW ROUTING (Pages Router)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Updates URL without running data fetching methods (getServerSideProps, etc.)
Useful for updating query params without page re-render/data refetch.

  router.push('/dashboard?tab=settings', undefined, { shallow: true });
  // URL changes, but getServerSideProps is NOT re-run
  // Component still sees new router.query

App Router equivalent: Use useSearchParams + router.push (no shallow option
  needed — search params updates are handled differently)

10. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is file-based routing in Next.js?
A:  The file system acts as the router. A file at app/blog/[slug]/page.tsx
    automatically becomes the route /blog/:slug. No route config needed.

Q2: What's the difference between pages/ routing and app/ routing?
A:  pages/: each file exports a React component; route = file path.
    app/: each route is a folder with a page.tsx. Supports layouts, loading/
    error/not-found files per segment, Server Components by default.

Q3: What is the purpose of a layout.tsx in App Router?
A:  layout.tsx wraps child segments and persists across navigation (does not
    re-mount). Perfect for nav bars, sidebars, providers. Contrast with
    template.tsx which re-mounts on every navigation.

Q4: What is a Route Group and when would you use it?
A:  A folder wrapped in () — e.g., (marketing) — that creates a logical
    grouping WITHOUT adding a URL segment. Use to apply different layouts to
    different sections without affecting the URL, or to co-locate related
    routes.

Q5: How does prefetching work with the Link component?
A:  In production, when a <Link> enters the viewport, Next.js automatically
    prefetches the linked route's RSC payload (not the full HTML). This makes
    navigation nearly instant. Prefetching can be disabled with prefetch={false}.
    In development, prefetching is disabled to avoid excessive server requests.

Q6: What's the difference between useRouter from 'next/router' and
    'next/navigation'?
A:  next/router → Pages Router (has .query, .pathname, .push, etc.)
    next/navigation → App Router (has useRouter, useParams, useSearchParams,
    usePathname as separate hooks). Never mix them.

Q7: How do you handle navigation after a form submission?
A:  Client Component: use useRouter().push('/success') after await fetch.
    Server Action: use redirect('/success') at end of action function.
    The redirect() from 'next/navigation' works in Server Actions and throws
    internally (never wrap it in try/catch).
