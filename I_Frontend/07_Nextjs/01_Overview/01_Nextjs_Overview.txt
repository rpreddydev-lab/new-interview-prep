1. WHAT IS NEXT.JS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js is a full-stack React framework built by Vercel (formerly Zeit) that
provides a production-ready structure for building web applications. It sits on
top of React and adds server-side capabilities, routing, build optimizations,
and developer tooling that React alone does not provide.

Key Definition (for interviews):
  "Next.js is an opinionated, full-stack React framework that enables server-
  side rendering (SSR), static site generation (SSG), incremental static
  regeneration (ISR), API routes, and file-based routing out of the box,
  allowing developers to build performant, SEO-friendly web applications
  without manual configuration."

Current Version (as of 2025-2026): Next.js 15.x
  - Introduced: App Router as stable (v13), Turbopack bundler, partial
    prerendering (PPR), improved caching defaults, React 19 support.

2. CORE RENDERING STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js supports four rendering strategies — knowing WHEN and WHY to use each
is a top interview topic.

┌──────────────────┬──────────────────────────────────────────────────────────┐
│ Strategy         │ Description                                              │
├──────────────────┼──────────────────────────────────────────────────────────┤
│ SSR              │ HTML generated on every request on the server            │
│ SSG              │ HTML generated once at build time                        │
│ ISR              │ SSG + ability to regenerate pages after a set interval   │
│ CSR              │ HTML rendered in the browser via JavaScript              │
│ PPR (new)        │ Partial Prerendering — static shell + streaming dynamic  │
└──────────────────┴──────────────────────────────────────────────────────────┘

  SSR  → Use for pages needing fresh data on every request (dashboards, feeds)
  SSG  → Use for marketing pages, blogs, docs (content doesn't change often)
  ISR  → Use when you want SSG performance but allow periodic updates
  CSR  → Use for user-specific, auth-gated, highly interactive content
  PPR  → Best of SSG + streaming (available in Next.js 14+)

3. KEY FEATURES OF NEXT.JS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

a) FILE-BASED ROUTING
   - Pages directory: pages/about.tsx → /about
   - App directory:   app/about/page.tsx → /about
   - Dynamic segments: [id].tsx or [id]/page.tsx → /products/123
   - Zero-config, no react-router needed

b) API ROUTES (BUILT-IN BACKEND)
   - pages/api/users.ts → /api/users  (Pages Router)
   - app/api/users/route.ts → /api/users  (App Router)
   - Full Node.js runtime on the server

c) IMAGE OPTIMIZATION
   - <Image> component from 'next/image'
   - Automatic WebP/AVIF conversion, lazy loading, blur placeholder
   - Prevents layout shift (CLS improvement)

d) AUTOMATIC CODE SPLITTING
   - Each page is its own bundle
   - Only the JS needed for the current page loads
   - Dynamic imports with next/dynamic for component-level splitting

e) BUILT-IN CSS SUPPORT
   - CSS Modules (*.module.css) scoped to components
   - Sass support out of the box
   - Tailwind CSS integration (via PostCSS)
   - CSS-in-JS (styled-components, emotion)

f) FAST REFRESH
   - Instantaneous feedback during development
   - Preserves component state on edits
   - Powered by React Fast Refresh

g) TYPESCRIPT SUPPORT
   - First-class TypeScript support
   - tsconfig.json auto-configured
   - Built-in type definitions for Next-specific APIs

h) MIDDLEWARE
   - Runs at the Edge before a request is completed
   - Use cases: auth checks, redirects, A/B testing, geolocation
   - Lives in middleware.ts at the root

i) INTERNATIONALIZATION (i18n)
   - Built-in locale detection and routing
   - next.config.js i18n configuration

j) ANALYTICS & WEB VITALS
   - Next.js Speed Insights
   - Built-in reportWebVitals() hook

4. NEXT.JS ARCHITECTURE — HOW IT WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Request Lifecycle (SSR):
  Browser Request
       ↓
  Edge Network / CDN (Middleware runs here)
       ↓
  Next.js Server (Node.js)
       ↓
  Fetch data (DB, API, etc.)
       ↓
  React renders HTML on server
       ↓
  HTML + JSON (dehydrated state) sent to browser
       ↓
  Browser hydrates (React takes over interactivity)

Build Output:
  next build → .next/ directory
    ├── server/    (SSR pages, API routes)
    ├── static/    (static assets, JS chunks)
    ├── cache/     (ISR cache, fetch cache)
    └── BUILD_ID   (unique build identifier)

5. THE TWO ROUTERS: PAGES ROUTER vs APP ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pages Router (legacy, pre-Next.js 13):
  - pages/ directory
  - getServerSideProps, getStaticProps, getStaticPaths
  - _app.tsx, _document.tsx for customization
  - All components are client components by default

App Router (modern, Next.js 13+):
  - app/ directory
  - Server Components by default (React Server Components)
  - layout.tsx, page.tsx, loading.tsx, error.tsx, not-found.tsx
  - Data fetching directly inside components (async/await)
  - Supports Streaming, Suspense, Server Actions
  - Nested layouts without re-mounting

Both routers can COEXIST in the same project during migration.

8. HYDRATION — CRITICAL CONCEPT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What is Hydration?
  After the server sends static HTML to the browser, React "hydrates" it by
  attaching event listeners and making it interactive. The browser doesn't
  re-render the HTML — it just makes it interactive.

Hydration Mismatch:
  - Occurs when server-rendered HTML differs from client render
  - Common causes: using window/document in SSR, Date.now(), random IDs
  - Error: "Hydration failed because the initial UI does not match"
  - Fix: use useEffect for browser-only code, suppressHydrationWarning prop

Example of hydration-safe pattern:
  // WRONG — causes mismatch
  const time = new Date().toLocaleTimeString(); // differs server vs client

  // CORRECT
  const [time, setTime] = useState('');
  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);

9. NEXT.JS CONFIGURATION (next.config.js)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

/** @type {import('next').NextConfig} */
const nextConfig = {
  // Strict mode for React
  reactStrictMode: true,

  // Custom headers, redirects, rewrites
  async headers() {
    return [{ source: '/api/:path*', headers: [{ key: 'X-Frame-Options', value: 'DENY' }] }];
  },
  async redirects() {
    return [{ source: '/old', destination: '/new', permanent: true }];
  },
  async rewrites() {
    return [{ source: '/api/proxy/:path*', destination: 'https://external.api/:path*' }];
  },

  // Image optimization domains
  images: {
    remotePatterns: [{ protocol: 'https', hostname: 'cdn.example.com' }],
  },

  // Experimental features
  experimental: {
    ppr: true,                   // Partial Prerendering
    serverActions: { bodySizeLimit: '2mb' },
  },

  // Environment variables exposed to client
  env: {
    CUSTOM_KEY: process.env.CUSTOM_KEY,
  },

  // Output mode
  output: 'standalone',         // for Docker deployments
  // output: 'export',          // for pure static export (no server)
};

module.exports = nextConfig;

10. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is Next.js and why would you use it over plain React?
A:  Next.js extends React with server-side capabilities. Plain React is a
    client-side UI library — you must wire up your own router, SSR solution,
    build config, and API layer. Next.js provides all of this out-of-the-box,
    including SSR/SSG/ISR for performance and SEO, file-based routing,
    built-in API routes, image optimization, and Edge/Middleware support.

Q2: What is the difference between the App Router and Pages Router?
A:  Pages Router (pre-v13) uses pages/ directory, requires getServerSideProps/
    getStaticProps for data fetching, and all components are client-side by
    default. App Router (v13+) uses app/ directory, supports React Server
    Components by default (no JS sent to client), allows data fetching directly
    in components via async/await, supports nested layouts, Streaming, Suspense,
    and Server Actions for form mutations.

Q3: Explain the request lifecycle in Next.js SSR.
A:  1. Browser makes request → 2. Middleware runs at Edge (auth, redirects) →
    3. Request reaches Node.js server → 4. getServerSideProps (Pages) or async
    Server Component (App) fetches data → 5. React renders HTML on server →
    6. HTML + hydration payload sent to browser → 7. Browser parses HTML,
    shows content → 8. React hydrates (attaches event listeners).

Q4: What is hydration and what causes a hydration mismatch?
A:  Hydration is when React attaches event listeners to server-rendered HTML.
    A mismatch occurs when the server HTML differs from what React would render
    on the client (e.g., using Date.now(), Math.random(), window, localStorage
    during server render). Fix: move browser-only logic to useEffect.

Q5: What are React Server Components and how do they relate to Next.js?
A:  RSCs are React components that render exclusively on the server and send
    zero JS to the browser. Next.js App Router adopts RSC by default. Benefits:
    reduced bundle size, direct DB access, no waterfall fetching. They cannot
    use hooks (useState, useEffect) or browser APIs. Client Components are
    opted in with 'use client' directive.

Q6: What is Partial Prerendering (PPR)?
A:  PPR (introduced in Next.js 14) allows a single page to have both a static
    shell (prerendered at build time) and dynamic holes (streamed in at request
    time). The static shell is served instantly from CDN, while dynamic parts
    stream in. This gives the performance of SSG + freshness of SSR.
