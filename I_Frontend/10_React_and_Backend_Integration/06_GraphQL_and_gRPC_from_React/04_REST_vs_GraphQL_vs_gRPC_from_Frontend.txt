================================================================
REST vs GraphQL vs gRPC — CHOOSING FROM THE FRONTEND
================================================================

Understanding when to use each API paradigm is a key senior-level
interview topic. Each has distinct tradeoffs.

================================================================
1. QUICK REFERENCE TABLE
================================================================

  Aspect           | REST              | GraphQL           | gRPC
  -----------------|-------------------|-------------------|------------------
  Protocol         | HTTP 1.1/2        | HTTP (POST)       | HTTP/2 (gRPC-Web for browser)
  Format           | JSON (usually)    | JSON              | Protobuf (binary)
  Typing           | OpenAPI/Swagger   | Schema (SDL)      | .proto files
  Client codegen   | Optional          | Optional (codegen)| Required
  Fetching         | Fixed endpoints   | Client-specified  | Fixed RPCs
  Over-fetching    | Common            | Eliminated        | Eliminated (exact fields)
  Multiple resources| Multiple calls  | One query         | Multiple RPCs
  Real-time        | WebSocket/SSE     | Subscriptions     | Bidirectional streaming
  Caching          | HTTP cache (CDN)  | Apollo cache      | No HTTP cache
  Browser native   | Yes               | Yes               | No (needs gRPC-Web + proxy)
  Learning curve   | Low               | Medium            | High
  Best use case    | CRUD APIs, public | Complex UIs, mobile| Microservices, performance

================================================================
2. REST — WHEN TO CHOOSE
================================================================

CHOOSE REST WHEN:
  ✅ Simple CRUD operations with clear resource model
  ✅ Public API with diverse consumers (mobile, web, 3rd party)
  ✅ Team is small or less experienced
  ✅ HTTP caching is important (CDN, browser cache)
  ✅ File upload/download (multipart is natural in REST)
  ✅ Simple admin panels or dashboards with few resources
  ✅ Tight backend deadline — REST is quickest to implement

CHALLENGES:
  ❌ Over-fetching: GET /users returns all fields, you need only 3
  ❌ Under-fetching: need user + orders + profile = 3 requests
  ❌ Endpoint explosion in complex domains
  ❌ No built-in real-time (need separate WebSocket/SSE)

REST BEST PRACTICES (React side):
  - Use Axios with base instance + interceptors
  - Service layer for all API calls (not inline in components)
  - React Query for caching and state management
  - OpenAPI codegen for TypeScript types

================================================================
3. GRAPHQL — WHEN TO CHOOSE
================================================================

CHOOSE GraphQL WHEN:
  ✅ Multiple clients need different data shapes (web, mobile)
  ✅ Data has complex relationships (user → orders → products → reviews)
  ✅ Reducing round trips is critical (mobile with poor connectivity)
  ✅ Multiple teams — each team queries exactly what they need
  ✅ Rapid frontend iteration (no waiting for backend endpoint changes)
  ✅ Need subscriptions alongside queries/mutations

CHALLENGES:
  ❌ Caching is complex (no URL-based HTTP cache for POST queries)
  ❌ N+1 problem in resolvers (requires DataLoader)
  ❌ File upload non-standard (multipart/form-data workaround)
  ❌ Error handling different from HTTP (always 200, errors in body)
  ❌ Learning curve for the team
  ❌ Small apps: GraphQL is overkill

GRAPHQL BEST PRACTICES (React side):
  - Apollo Client or urql for normalized caching
  - Co-locate fragments with components (Relay pattern)
  - GraphQL Codegen for TypeScript types
  - Error policy: 'all' to handle partial data

================================================================
4. gRPC — WHEN TO CHOOSE
================================================================

CHOOSE gRPC WHEN:
  ✅ Internal microservice communication (server-to-server)
  ✅ Backend already uses gRPC (avoid protocol translation)
  ✅ Payload size and latency are critical (binary protobuf)
  ✅ Strongly typed contract between many teams
  ✅ Bidirectional streaming (not possible in REST/GraphQL)
  ✅ Language-agnostic code generation for many services

CHALLENGES:
  ❌ Browsers need gRPC-Web + Envoy proxy (extra infrastructure)
  ❌ Non-human-readable binary (harder to debug)
  ❌ Proto files are required — more setup
  ❌ Limited browser native support
  ❌ Overkill for most React-to-backend communication

gRPC BEST PRACTICES (React side):
  - Use ConnectRPC (Buf) for simpler browser integration
  - Generate TypeScript from .proto with buf
  - Handle gRPC status codes (not HTTP codes)
  - Use AbortController for cancellation

================================================================
5. DATA FETCHING COMPARISON (SAME SCENARIO)
================================================================

Scenario: Load a user profile page showing:
  user info + recent orders (last 5) + recommended products

REST APPROACH:
  const user = await GET /users/123
  const orders = await GET /users/123/orders?limit=5
  const products = await GET /products/recommended?userId=123
  // 3 sequential or parallel requests
  // May over-fetch unused fields

GRAPHQL APPROACH:
  query {
    user(id: "123") {
      id name email avatar
      recentOrders(limit: 5) {
        id total status createdAt
      }
      recommendedProducts {
        id name price imageUrl
      }
    }
  }
  // 1 request, exactly the fields needed

gRPC APPROACH:
  const user = await userClient.getUserProfile({ userId: '123', includeOrders: true, includeRecommended: true });
  // 1 RPC, binary payload, but requires proto definition and proxy

6. REAL-TIME COMPARISON
================================================================

  Feature           | REST + WebSocket   | GraphQL Subscription | gRPC Streaming
  ------------------|--------------------|-----------------------|-----------------
  Setup complexity  | Medium             | Medium-High           | High
  Protocol          | HTTP + ws://       | HTTP + ws://          | HTTP/2
  Message format    | JSON               | JSON                  | Protobuf
  Push from server  | Yes                | Yes                   | Yes
  Client-to-server  | Yes (WebSocket)    | No (separate mutation)| Yes (bidirectional)
  Spring Boot impl  | STOMP/SseEmitter   | Spring for GraphQL    | grpc-spring-boot-starter

================================================================
7. CACHING COMPARISON
================================================================

  REST:
    HTTP caching: GET /users/123 → Cache-Control: max-age=300
    CDN caches responses by URL
    Browser caches automatically
    React Query adds client-side cache on top

  GraphQL:
    No URL-based caching (all requests are POST to /graphql)
    Apollo Client normalized cache (by __typename + id)
    CDN caching requires persisted queries (query → hash → CDN by hash)
    Per-field caching possible with Apollo federation

  gRPC:
    No HTTP caching (binary protocol)
    Application-level caching only
    React Query can wrap gRPC calls for client-side caching

================================================================
8. AUTHENTICATION PATTERNS
================================================================

  REST:      Authorization: Bearer <token>  (Axios interceptor)
  GraphQL:   Same header via Apollo authLink
             Or cookie-based (Apollo passes cookies automatically)
  gRPC-Web:  Interceptor in transport config sets metadata/headers

All three ultimately deliver the token in the HTTP request.
The mechanism is the same; only the library API differs.

================================================================
9. HYBRID APPROACH (REAL WORLD)
================================================================

Many production systems use multiple protocols together:
  - REST for CRUD endpoints (user management, settings)
  - GraphQL for complex data aggregation (product catalog, feed)
  - WebSocket/SSE for real-time (notifications, chat)
  - gRPC internally (microservice-to-microservice only)

React app calls REST and/or GraphQL directly.
gRPC stays internal — the BFF layer translates to REST/GraphQL.

================================================================
10. INTERVIEW QUESTIONS
================================================================

Q: How do you decide between REST and GraphQL for a new project?
A: REST for: simple CRUD, public APIs, caching important, small team.
   GraphQL for: multiple different clients, complex data relationships,
   mobile apps needing minimal payloads, rapid frontend iteration.
   Key question: do you have multiple clients with different data needs?
   If yes, GraphQL. If it's one web app with simple needs, REST is fine.

Q: Why is REST easier to cache than GraphQL?
A: REST GET requests have unique URLs that map naturally to HTTP
   cache keys (browser cache, CDN). Cache-Control headers control
   duration. GraphQL uses POST to a single /graphql URL — HTTP caches
   don't distinguish between different queries. You need Apollo's
   client-side cache, or persisted queries (hash the query, use GET
   with the hash) for CDN caching.

Q: Can you use all three (REST, GraphQL, gRPC) in the same React app?
A: Yes. Use the right tool for each use case. React Query wraps
   any async function, so you can use it for REST, GraphQL, and gRPC
   calls alike. Apollo Client handles GraphQL. Axios handles REST.
   ConnectRPC handles gRPC-Web. You'd typically only mix REST +
   GraphQL (not gRPC in the browser). Maintain separate service
   modules for each protocol.

Q: What is schema-first development?
A: Define the API contract (REST: OpenAPI spec, GraphQL: SDL schema,
   gRPC: .proto file) before writing implementation. Benefits:
   frontend and backend teams work in parallel (mock from spec),
   auto-generate client code, catch breaking changes early.
   Tools: OpenAPI Generator, GraphQL Codegen, protoc/buf.

Q: What is the biggest advantage of gRPC over REST for microservices?
A: Strongly typed binary protocol with code generation. Every service
   gets a generated client in any language from the same .proto file.
   No miscommunication about request/response shapes. Protobuf encoding
   is 3-10x more compact than JSON. HTTP/2 multiplexing and streaming
   built in. For service-to-service calls inside Kubernetes, gRPC
   is significantly more efficient than REST+JSON.
