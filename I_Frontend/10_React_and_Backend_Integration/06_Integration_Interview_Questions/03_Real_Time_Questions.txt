================================================================
REAL-TIME COMMUNICATION INTERVIEW QUESTIONS
================================================================

Deep-dive Q&A covering WebSocket, STOMP, SSE, and real-time
React patterns.

================================================================
SECTION 1: WEBSOCKET FUNDAMENTALS
================================================================

Q: What is the WebSocket handshake and how is it initiated?
A: The client sends an HTTP GET with Upgrade: websocket and
   Sec-WebSocket-Key headers. The server responds with 101 Switching
   Protocols and Sec-WebSocket-Accept (a hash of the key).
   After this, the connection switches to the WebSocket protocol
   over the same TCP socket. WebSocket URLs use ws:// (or wss:// for
   TLS, always use wss:// in production).

Q: How is WebSocket different from HTTP?
A: HTTP is half-duplex request-response: client always initiates.
   WebSocket is full-duplex: either side can send at any time.
   WebSocket has much lower per-message overhead (no full HTTP
   headers per message, just small WebSocket frames). One persistent
   TCP connection vs. a new connection per HTTP/1.1 request
   (or multiplexed streams in HTTP/2).

Q: What WebSocket close codes do you know and when would you use them?
A: 1000 — Normal closure (intentional). 1001 — Going away
   (browser navigating away). 1006 — Abnormal closure (connection
   dropped, no close frame received). 1008 — Policy violation
   (e.g., auth failed, use to refuse bad connections). 1011 —
   Server internal error. 4000-4999 — application-defined codes.
   Always close with 1000 for intentional disconnection to prevent
   reconnect loops.

Q: How do you pass authentication to a WebSocket connection?
A: WebSocket spec doesn't support custom headers in the initial
   handshake from the browser. Options: (1) include the JWT as a
   query parameter in the URL, (2) send AUTH as the first STOMP
   message after connecting (STOMP CONNECT frame with Authorization
   header), (3) use a short-lived ticket: call a REST endpoint to
   get a one-time ticket, pass it in the WebSocket URL query param.

Q: What is ws.readyState and when should you check it?
A: 0 = CONNECTING, 1 = OPEN, 2 = CLOSING, 3 = CLOSED.
   Always check ws.readyState === WebSocket.OPEN before calling
   ws.send() — sending on a non-OPEN socket throws an error.

SECTION 2: STOMP AND SPRING BOOT
================================================================

Q: What does STOMP add over raw WebSocket?
A: STOMP is a messaging protocol that adds: named destinations
   (/topic, /queue, /app), message framing with headers, a
   publish-subscribe model, and an acknowledgement mechanism.
   Spring Boot's @MessageMapping methods are only possible because
   of STOMP routing. Raw WebSocket would require you to implement
   your own routing layer.

Q: What is the difference between /topic, /queue, and /user in STOMP?
A: /topic — broadcast: all subscribers receive each message (fan-out).
   /queue — point-to-point: typically one subscriber per queue.
   /user/{username}/... — user-specific: Spring maps to the connected
   user's session. Useful for sending private notifications.
   /app/... — routes to @MessageMapping methods, not subscriptions.

Q: How does user-specific messaging work in Spring Boot WebSocket?
A: 1. Client subscribes to /user/queue/notifications.
   2. Server calls messagingTemplate.convertAndSendToUser(username,
      "/queue/notifications", message).
   3. Spring resolves this to /user/{sessionId}/queue/notifications
      and delivers to that user's session only.
   This requires the user Principal to be set — done via the
   ChannelInterceptor on STOMP CONNECT.

Q: How do you handle reconnection with STOMP Client?
A: @stomp/stompjs Client has a built-in reconnectDelay property
   (default 5000ms). Set it in the config:
     new Client({ reconnectDelay: 5000 })
   The client automatically reconnects and re-subscribes. For more
   control, handle onDisconnect and use reconnectDelay: 0 with
   manual reconnect logic.

Q: How would you scale WebSocket to multiple server instances?
A: Replace the in-memory SimpleBroker with an external message broker:
     config.enableStompBrokerRelay("/topic", "/queue")
         .setRelayHost("rabbitmq-host")
         .setRelayPort(61613);
   All servers connect to RabbitMQ/ActiveMQ. A message sent to any
   server is relayed to the broker and delivered to subscribers on
   any server. Sticky sessions are not required.

SECTION 3: SERVER-SENT EVENTS (SSE)
================================================================

Q: How does SSE differ from WebSocket?
A: SSE is server-to-client only (one-way); WebSocket is full-duplex.
   SSE runs over plain HTTP (easier through proxies, firewalls, CDNs).
   SSE has built-in auto-reconnection with Last-Event-ID for resuming.
   WebSocket requires manual reconnection logic. SSE is simpler to
   implement on the backend (just stream text). WebSocket is better
   for bidirectional, high-frequency communication.

Q: How does SSE auto-reconnect work?
A: When the EventSource connection drops, the browser automatically
   reconnects after a brief delay. If the server has sent events with
   id: fields, the browser sends Last-Event-ID header on reconnect.
   The server can use this to resume from where it left off (replay
   missed events). The retry: field sets the reconnect delay in ms.

Q: How do you implement SSE in Spring Boot (non-reactive)?
A: Return SseEmitter from a @GetMapping endpoint with
   produces = MediaType.TEXT_EVENT_STREAM_VALUE. Create SseEmitter,
   pass it to a service that runs async work, call emitter.send()
   with SseEmitter.event() builder, call emitter.complete() when done.
   Set timeout carefully (Long.MAX_VALUE for no timeout, or a
   sensible limit for job progress).

Q: Why can't EventSource send custom Authorization headers?
A: The EventSource API is minimal and doesn't expose a headers option.
   It follows browser conventions for regular HTTP requests.
   Solutions: use cookies (sent automatically), token in URL query
   param, or use the @microsoft/fetch-event-source library which
   is built on fetch and supports full headers.

Q: When would you choose SSE over WebSocket for live dashboard data?
A: Choose SSE: the dashboard only reads server-pushed data (no user
   interaction through the same channel), the data is text/JSON,
   you need to work through corporate proxies/firewalls, you want
   built-in reconnection, or you're using HTTP/2 (SSE is very
   efficient over HTTP/2). WebSocket if the user also needs to
   send frequent updates back to the server.

SECTION 4: REACT REAL-TIME PATTERNS
================================================================

Q: How do you prevent memory leaks with WebSocket in React?
A: Return a cleanup function from useEffect that closes the WebSocket
   with code 1000. Also: set shouldReconnect = false before closing
   to prevent reconnect loop on unmount, clear reconnect timers
   (clearTimeout), and unsubscribe any STOMP subscriptions.

Q: What is the stale closure problem in WebSocket message handlers?
A: A message handler defined in useEffect captures state/prop values
   at the time the effect ran. Later state updates are not visible
   to the handler. Fix: (1) add the variable to the effect's dependency
   array (reconnects when it changes), or (2) store the variable in
   a ref and read ref.current in the handler (always current,
   no reconnect).

Q: How do you throttle high-frequency UI updates from WebSocket?
A: Buffer incoming messages in a ref (not state):
     ws.onmessage = (e) => bufferRef.current.push(JSON.parse(e.data));
   Use setInterval to flush the buffer to state every 100-200ms:
     setData(prev => [...prev, ...bufferRef.current.splice(0)]);
   This batches renders instead of one per message, reducing
   CPU/render overhead for high-frequency streams.

Q: How do you implement typing indicators (user is typing) with WebSocket?
A: On input change, send a TYPING event. The server broadcasts it
   to the room. Other clients receive it and show "{name} is typing..."
   Use a debounce on the client: only send TYPING if not sent in the
   last 1s. Use a setTimeout to auto-clear the typing indicator after
   3s of no TYPING events (in case STOP_TYPING event is missed).

Q: How do you combine React Query and WebSocket for live data?
A: Fetch initial data with useQuery (REST). Open a WebSocket to
   receive live updates. In the onmessage handler, call
   queryClient.setQueryData to update the cache. The component
   re-renders automatically. This gives you caching, loading states,
   and error handling from React Query, plus real-time freshness
   from WebSocket.

SECTION 5: SCENARIO QUESTIONS
================================================================

Q: Design a real-time chat feature with React + Spring Boot.
A: Frontend: STOMP over SockJS, useEffect to manage Client lifecycle,
   subscribe to /topic/chat/{roomId} on connect, send via
   /app/chat.send. Auth: JWT in STOMP CONNECT headers validated
   by ChannelInterceptor. Optimistic updates: add pending message
   immediately, replace with server-confirmed message using clientId.
   Cleanup: deactivate client on unmount. Pagination: load history
   via REST, receive new messages via WebSocket.
   Scale: RabbitMQ as external broker.

Q: Design a live order tracking feature.
A: When user places an order, subscribe to /user/queue/order/{orderId}
   (or SSE endpoint). Backend publishes status updates as order progresses
   (processing → packed → dispatched → delivered). SSE is sufficient
   since tracking is server-to-client only. Use SseEmitter or Flux.
   Frontend shows progress steps. On complete event, close SSE connection.

Q: How would you handle WebSocket connection loss gracefully?
A: Detect connection drop via onclose or onerror. Show a "Reconnecting..."
   indicator in the UI. Implement exponential backoff (1s, 2s, 4s...
   max 30s). On successful reconnect, re-subscribe and fetch missed
   data (REST call for messages since last timestamp). Clear the
   reconnecting indicator and show "Reconnected" briefly. If reconnect
   fails after N attempts, show "Connection lost. Please refresh."
