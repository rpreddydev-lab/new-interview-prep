================================================================
ADVANCED INTEGRATION INTERVIEW QUESTIONS
================================================================

Senior-level questions on architecture, GraphQL, gRPC, performance,
testing, and system design for React + backend integration.

================================================================
SECTION 1: ARCHITECTURE
================================================================

Q: What is the Backend for Frontend (BFF) pattern?
A: A dedicated backend service built specifically for a frontend
   client. Instead of the React app calling multiple microservices,
   it calls a single BFF that aggregates, shapes, and secures data.
   Benefits: keeps API keys/secrets server-side, aggregates data
   (reduces round trips), shapes responses to what the UI needs,
   handles auth token exchange, enables server-side rendering.
   Drawbacks: additional service to maintain.

Q: What is the difference between monolith, microservices, and BFF?
A: Monolith: one deployable unit, simple, but scaling entire app
   for one bottleneck.
   Microservices: independent services per domain, scale individually,
   but complex to orchestrate; React calling 10 services is painful.
   BFF + Microservices: React calls BFF (one endpoint), BFF aggregates
   from microservices. Best of both worlds for frontend.

Q: How do you handle API versioning from the React side?
A: Include version in base URL: /api/v1/. Keep v1 client and v2 client
   as separate Axios instances during migration. Feature-flag new
   API versions: if (featureFlags.useV2Orders) use v2Client else v1Client.
   Monitor for deprecation headers (Sunset: date header) and alert the team.

Q: What strategies exist for managing environment configuration?
A: Vite .env files (.env.development, .env.staging, .env.production)
   with VITE_ prefix. Validate all required vars at startup (throw if
   missing). Never expose secrets in VITE_ vars (visible in bundle).
   For runtime config: /config.json served by the web server (can
   be injected per-environment by K8s ConfigMap without rebuilding
   the Docker image).

Q: What is idempotency and why does it matter for API integration?
A: An idempotent operation produces the same result regardless of
   how many times it's executed. GET, PUT, DELETE are idempotent.
   POST is not. Idempotency matters for: retry logic (safely retry
   on network failure), payment/order operations (prevent duplicates),
   optimistic UI (safe to undo and redo). Use Idempotency-Key headers
   for non-idempotent operations that need safe retries.

================================================================
SECTION 2: GRAPHQL
================================================================

Q: What are the advantages of GraphQL over REST for a React SPA?
A: (1) Request exactly the data you need (no over-fetching).
   (2) Combine multiple resources in one request (no under-fetching,
   no N+1 waterfall). (3) Strongly typed schema (auto-generated
   TypeScript types). (4) Built-in subscriptions for real-time.
   (5) Introspection for tooling (GraphiQL, Apollo DevTools).
   Drawbacks: complex caching, file uploads are non-standard, overkill
   for simple CRUD apps.

Q: What is Apollo Client's normalized cache?
A: Apollo stores every GraphQL object by its __typename + id. When
   multiple queries return the same object, the cache merges them.
   When a mutation updates an object, the cache updates it everywhere
   it's referenced — all queries with that object re-render automatically.
   This eliminates manual cache synchronization. Use cache.modify()
   for operations that don't return the updated object.

Q: What is the N+1 problem in GraphQL and how is it solved?
A: A resolver for a list of posts that makes one DB call per post
   to fetch the author results in N+1 DB calls (1 for posts + N for
   authors). Solution: DataLoader (batches all author ID requests
   within a single tick into one DB query, then distributes results).
   In Spring Boot: use graphql-java-dataloader or Reactor's Flux batching.

Q: What are GraphQL fragments and why are you asked about them?
A: Fragments are reusable selection sets:
     fragment UserFields on User { id name email avatar }
   Used in queries: { user(id: 1) { ...UserFields } }
   In React (co-located): each component defines its own fragment
   for the data it needs (Relay pattern). The parent query assembles
   all fragments. This keeps components self-contained and ensures
   they always get the data they need.

Q: When would you choose REST over GraphQL?
A: REST for: simple CRUD microservices, public APIs (well-understood
   contract), file upload/download (GraphQL is awkward with multipart),
   caching at HTTP layer (REST leverages CDN/browser cache easily),
   team unfamiliar with GraphQL tooling, or where over-fetching
   isn't a problem (e.g., admin panels with few clients).

================================================================
SECTION 3: gRPC
================================================================

Q: What is gRPC-Web and why can't browsers use gRPC directly?
A: Standard gRPC requires HTTP/2 with trailer support, which browsers
   don't expose at the fetch API level. gRPC-Web is a protocol that
   wraps gRPC over HTTP/1.1 or HTTP/2 in a way browsers can use.
   A proxy (Envoy, grpc-web-proxy) translates between gRPC-Web
   (browser) and gRPC (backend). Use case: React → Envoy proxy → 
   Spring Boot gRPC service.

Q: What is Protocol Buffers and why is it faster than JSON?
A: Protobuf is a binary serialization format. It's faster because:
   (1) Binary is more compact than text JSON (3-10x smaller).
   (2) Encoding/decoding is faster than JSON parsing.
   (3) Schema (proto file) enables code generation in any language.
   Drawback: not human-readable, requires schema (proto) files.
   For browser DevTools, use the Envoy proxy which can log decoded messages.

Q: When would you use gRPC for a React frontend?
A: gRPC-Web is useful when: (1) you need streaming (server streaming
   for live updates as an alternative to SSE), (2) the backend already
   uses gRPC (internal microservices), (3) you need strongly typed
   binary protocol for performance-critical data transfer. Most React
   apps use REST or GraphQL — gRPC-Web is less common in frontend
   development but used in performance-critical enterprise apps.

SECTION 4: PERFORMANCE AND TESTING
================================================================

Q: How do you test React components that make API calls?
A: Use MSW (Mock Service Worker) — it intercepts fetch/Axios requests
   at the service worker level (in the browser) or Node.js (in Jest
   tests). Define handlers: rest.get('/api/users', (req, res, ctx) =>
   res(ctx.json([...]))). MSW is framework-agnostic and tests actual
   network layer, not mocked module internals. For unit tests:
   mock the service module directly (vi.mock/jest.mock).

Q: What is MSW and why is it better than mocking Axios?
A: MSW intercepts at the network level (service worker in browser,
   JSDOM in Node). Your app code is unaware of mocking — it uses real
   Axios/fetch. This makes tests closer to production behavior.
   Mocking Axios directly tests implementation details (internal
   Axios call) not behavior (HTTP request to URL). MSW handlers
   are reusable across unit, integration, and Storybook stories.

Q: How do you measure and improve API call performance in React?
A: (1) React DevTools Profiler to find re-render causes.
   (2) Network tab: check response times, payload sizes, request count.
   (3) Reduce requests: React Query deduplication, colocate data
   fetching with useQuery, use parallel queries (useQueries).
   (4) Reduce payload: request only needed fields, pagination/cursor.
   (5) Caching: tune staleTime/gcTime in React Query.
   (6) Prefetch: prefetchQuery on hover/focus for anticipated navigation.
   (7) Virtualize long lists: react-window, TanStack Virtual.

Q: What is a query key in React Query and how should you structure them?
A: The query key uniquely identifies a query and is used for caching,
   refetching, and invalidation. Structure as arrays:
     ['users'] — all users
     ['users', userId] — specific user
     ['users', userId, 'posts'] — user's posts
   Use queryClient.invalidateQueries({ queryKey: ['users'] }) to
   invalidate all user queries. Keys are compared with deep equality.
   Never use dynamic objects as keys — serialize them or keep stable.

Q: How do you handle optimistic updates with rollback?
A: In React Query useMutation:
   onMutate: (1) cancel in-flight queries (avoid overwriting optimistic data),
   (2) snapshot old data, (3) update cache with optimistic value,
   (4) return context = { previousData }.
   onError: use context.previousData to rollback cache.
   onSettled: always invalidate/refetch to sync with server truth.

================================================================
SECTION 5: SYSTEM DESIGN
================================================================

Q: Design the API integration for a social media feed with likes.
A: REST + React Query + optimistic updates:
   - GET /posts?page=1&limit=20 → useInfiniteQuery
   - POST /posts/{id}/like → useMutation with optimistic update
   - DELETE /posts/{id}/like → useMutation with optimistic update
   Optimistic like: increment count + set liked=true in cache immediately.
   On error: rollback to previous snapshot.
   On success: refetch post to sync exact count.
   WebSocket or SSE for receiving new posts from followed users.

Q: How would you architect the React side of a multi-tenant SaaS app?
A: (1) Tenant from subdomain (tenant.app.com) or URL path (/tenant/...).
   (2) Axios baseURL includes tenant ID. (3) All API calls go through
   one client that includes tenant context (header: X-Tenant-ID).
   (4) React Query queryKeys include tenantId to prevent cache collision.
   (5) Auth context includes tenant roles (user may have different
   roles in different tenants). (6) On tenant switch, clear query cache.

Q: How would you implement a real-time collaborative feature (like Google Docs)?
A: Operational Transformation (OT) or CRDT for conflict resolution.
   WebSocket for bidirectional sync. Each change is an operation
   (insert char at position X). The server applies OT to reconcile
   concurrent edits. In React: use Yjs (CRDT library) with WebSocket
   provider — it handles conflict resolution automatically.
   For simple cases (shared form): lock the field while someone edits,
   show "editing by Alice" indicators via WebSocket presence.

Q: What would you consider when migrating a REST API to GraphQL?
A: (1) Start with a gateway (GraphQL wrapping REST — schema stitching).
   (2) Migrate queries first (read operations are safer).
   (3) Run REST and GraphQL in parallel during transition.
   (4) Update React components one page at a time.
   (5) Replace Apollo with React Query + REST if GraphQL adds
   complexity without benefit. (6) Validate N+1 early with DataLoader.
   (7) Update auth: same JWT, but apply in Apollo's authLink middleware.
