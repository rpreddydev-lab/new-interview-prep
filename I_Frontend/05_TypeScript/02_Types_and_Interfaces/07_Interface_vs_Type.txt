1. THE QUESTION EVERYONE ASKS: interface OR type?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is one of the most frequently asked TypeScript interview questions.
Both `interface` and `type` can describe object shapes, and for simple objects,
they are mostly interchangeable. But they have important differences.

Quick verdict (TypeScript team's guidance as of TS 5.x):
  • Use `interface` for object shapes / class contracts
  • Use `type` for everything else (unions, intersections, mapped, conditional)
  • Both are fine for object shapes — be consistent within a codebase

2. SIDE-BY-SIDE SYNTAX COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Object shape — both look almost the same:
  interface UserI {
    id: number;
    name: string;
    email?: string;
    readonly createdAt: Date;
  }

  type UserT = {
    id: number;
    name: string;
    email?: string;
    readonly createdAt: Date;
  };

  // Usage is identical:
  const u1: UserI = { id: 1, name: "Alice", createdAt: new Date() };
  const u2: UserT = { id: 1, name: "Alice", createdAt: new Date() };

4. KEY DIFFERENCE 1: DECLARATION MERGING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  INTERFACE supports declaration merging:

  interface Window {
    title: string;
  }
  interface Window {        // ← same name again → MERGED
    height: number;
  }
  // Result: { title: string; height: number }

  TYPE ALIAS does NOT support re-declaration:

  type Window = { title: string };
  type Window = { height: number }; // ❌ Error: Duplicate identifier 'Window'

  WHY THIS MATTERS:
  • Libraries use declaration merging to allow users to extend their types
  • @types/node, @types/express augment built-in interfaces this way
  • If you're building a public library, prefer `interface` for extensibility

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. KEY DIFFERENCE 2: EXTENDING / COMPOSING TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  INTERFACE uses `extends`:
  interface Animal { name: string }
  interface Dog extends Animal { breed: string }
  // Dog = { name: string; breed: string }

  TYPE uses `&` (intersection):
  type Animal = { name: string }
  type Dog = Animal & { breed: string }
  // Dog = { name: string; breed: string }

  INTERFACE can extend multiple interfaces:
  interface A { a: string }
  interface B { b: number }
  interface C extends A, B { c: boolean }

  TYPE can do the same with intersections:
  type A = { a: string }
  type B = { b: number }
  type C = A & B & { c: boolean }

  INTERFACE can extend a TYPE (if it's an object type):
  type Animal = { name: string }
  interface Dog extends Animal { breed: string } // ✅

  TYPE can intersect an INTERFACE:
  interface Animal { name: string }
  type Dog = Animal & { breed: string } // ✅

  KEY DIFFERENCE in behavior:
  - extends checks compatibility eagerly — conflicts are caught immediately
  - & (intersection) is more permissive — conflicts result in `never` properties

  interface A { x: number }
  interface B extends A { x: string } // ❌ Immediate error: string not assignable to number

  type A = { x: number }
  type B = A & { x: string } // ✅ No immediate error — x becomes `never`
  const b: B = { x: 1 }; // ❌ Error only at use site

6. KEY DIFFERENCE 3: WHAT TYPE CAN DO THAT INTERFACE CANNOT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

a) Union Types:
   type ID = string | number;       // ✅ type
   interface ID = string | number;  // ❌ Not possible

b) Primitive Aliases:
   type UserID = number;            // ✅ type
   interface UserID = number;       // ❌ Not possible

c) Tuple Types:
   type Point = [number, number];   // ✅ type
   // Interface cannot express a fixed-length tuple

d) Mapped Types:
   type Optional<T> = { [K in keyof T]?: T[K] };  // ✅ type
   // Interface cannot use [K in keyof T] syntax

e) Conditional Types:
   type NonNullable<T> = T extends null | undefined ? never : T;  // ✅ type
   // Interface has no conditional type support

f) Template Literal Types:
   type EventName = `on${string}`;  // ✅ type
   // Interface cannot express template literal types

7. ERROR MESSAGE QUALITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Interfaces tend to produce cleaner error messages because TypeScript
  refers to the interface NAME in errors. Type aliases sometimes get
  fully expanded in error messages.

  interface User { name: string; email: string }
  // Error: Argument of type '{ name: string }' is not assignable to parameter of type 'User'
  //        Property 'email' is missing in type '{ name: string }' but required in type 'User'

  type User = { name: string; email: string }
  // Error: Argument of type '{ name: string }' is not assignable to parameter of type '{ name: string; email: string }'
  //        Property 'email' is missing...
  // (expanded — doesn't say "User", shows the full structure)

  Note: TypeScript has improved type alias error messages over versions.
  This difference is less pronounced in modern TypeScript.

8. RECURSIVE TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Both support recursive definitions since TypeScript 3.7:

  // Interface:
  interface TreeNode {
    value: number;
    children: TreeNode[];
  }

  // Type alias:
  type TreeNode = {
    value: number;
    children: TreeNode[];
  };

  // Both work identically for recursive object structures.

  // Type aliases have more flexibility for recursive union types:
  type JSONValue = string | number | boolean | null | JSONValue[] | { [k: string]: JSONValue };
  // (Interfaces cannot express this directly because of the union)

9. WHEN TO USE WHAT — DECISION GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Use INTERFACE when:
  ──────────────────
  ✅ Defining an object shape that classes will implement
  ✅ Building a library or SDK (allows consumers to augment types)
  ✅ Describing a class contract (implements)
  ✅ You need declaration merging (module augmentation)
  ✅ Multiple interface inheritance is cleaner than repeated intersections
  ✅ Error messages matter (name shown in errors vs expanded structure)

  Use TYPE when:
  ─────────────
  ✅ Creating a union type: type Result = Success | Failure
  ✅ Creating a primitive alias: type UserId = string
  ✅ Creating a tuple: type Pair = [string, number]
  ✅ Using mapped types: type Readonly<T> = { readonly [K in keyof T]: T[K] }
  ✅ Using conditional types: type NonNullable<T> = T extends null ? never : T
  ✅ Using template literal types: type `on${string}`
  ✅ Complex type transformations (utilities, derivations from other types)

  Default recommendation (codebase consistency):
  ─────────────────────────────────────────────
  Pick ONE approach and be consistent. Many codebases:
  • Use interface for most object shapes (React props, API types, class contracts)
  • Use type for unions, conditional types, mapped types, and utilities

10. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the main difference between interface and type in TypeScript?
    Key differences:
    1. Declaration merging: interfaces support it, types don't
    2. Expressiveness: types support unions, intersections, mapped types,
       conditional types, template literals; interfaces don't
    3. Extends syntax: interfaces use `extends`, types use `&`
    4. Error messages: interfaces typically show the type name, types sometimes expand

Q2: When would you prefer interface over type?
    • When building a library that consumers should be able to augment
    • When defining contracts for classes (implements)
    • When you need declaration merging
    • For object shapes that others will extend

Q3: When would you prefer type over interface?
    • Union types: type Status = "active" | "inactive"
    • Primitive aliases: type ID = string
    • Tuples: type Point = [number, number]
    • Any computed/transformed type (mapped, conditional, template literal)

Q4: Can a class implement a type alias?
    Yes, as long as the type is an object type (not a union or primitive):
    type Serializable = { serialize(): string }
    class Document implements Serializable { serialize() { return "..."; } }
    But you cannot implement a union type.

Q5: Can an interface extend a type alias?
    Yes: type Animal = { name: string }
    interface Dog extends Animal { breed: string } // ✅
    And a type can intersect an interface:
    type Dog = Animal & { breed: string } // ✅

Q6: Why does TypeScript recommend using `interface` for libraries?
    Because interfaces support declaration merging, library consumers can
    add properties to your interfaces without modifying your source code.
    This is the primary mechanism for module augmentation (e.g., extending
    Express's Request, extending Window).

Q7: What happens when you have conflicting properties in interface extends vs type &?
    - interface extends: compile error immediately at the extends declaration
    - type &: the conflicting property becomes `never` — error only at use site
    Use interface extends when you want immediate feedback on conflicts.

Q8: Are there performance differences between interface and type?
    Historically, interfaces were faster to compile. Modern TypeScript
    has significantly optimized type aliases. In practice, the performance
    difference is negligible for most codebases. Very complex recursive
    type aliases can sometimes be slower to evaluate.

Q9: Is it bad practice to use both interface and type in the same codebase?
    It's not inherently bad, but it's better to be consistent. Pick a
    convention: some teams use interface for all object shapes and type
    for everything else. What matters is consistency and readability.

Q10: What does the TypeScript team recommend?
     The official TypeScript docs (as of 2024) say: "We recommend using
     interface over type aliases for object types" because of the better
     error messages and declaration merging support. However, they also
     acknowledge that for many use cases, either is fine. The most important
     thing is to use `type` when you need its unique capabilities.
