1. WHAT IS tsconfig.json?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

tsconfig.json is the TypeScript project configuration file. It tells the
TypeScript compiler (tsc) HOW to compile your TypeScript project:
  • Which files to include/exclude
  • Which JavaScript version to target
  • How strict the type checking should be
  • Where to output compiled files
  • Module format (CommonJS, ESM, etc.)

Location: Usually at the root of the project.
Create it: npx tsc --init

2. FULL tsconfig.json STRUCTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

{
  "compilerOptions": {
    // ... compiler settings
  },
  "include": ["src/**/*"],         // files to include
  "exclude": ["node_modules"],     // files to exclude
  "files": ["index.ts"],           // explicit file list (rare)
  "extends": "./tsconfig.base.json" // inherit from another config
}

3. COMPILER OPTIONS — GROUPED BY PURPOSE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━ LANGUAGE AND ENVIRONMENT ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"target"
  The JavaScript version the compiler outputs.
  Values: "ES3" | "ES5" | "ES6"/"ES2015" | "ES2016" ... "ES2023" | "ESNext"

  "target": "ES2020"

  Rule of thumb:
  • Node.js apps: "ES2020" or "ESNext"
  • Browser apps: "ES5" (widest compat) or "ES2015"+ (modern browsers)
  • TypeScript's own syntax (async/await, decorators) is compiled down
    to the target version

"lib"
  The built-in type definitions (APIs) TypeScript knows about.
  If not set, defaults are based on `target`.

  "lib": ["ES2020", "DOM", "DOM.Iterable"]
  
  Common lib values:
  • "ES2020"       — ES2020 JS standard library (Map, Set, Promise, etc.)
  • "DOM"          — Browser APIs (document, window, HTMLElement)
  • "DOM.Iterable" — Iterators for DOM collections
  • "WebWorker"    — Web Worker APIs
  
  When to set lib manually: When target ≠ what APIs you use.
  E.g., target: "ES5" but want Promise types → add "ES2015.Promise" to lib.

"jsx"
  How to handle JSX in .tsx files.
  Values:
  • "preserve"     — Keep JSX as-is (for Babel to process)
  • "react"        — Transform to React.createElement(...)
  • "react-jsx"    — Transform using automatic JSX runtime (React 17+)
  • "react-native" — Keep JSX but change file extension

  "jsx": "react-jsx"  // Modern React projects (React 17+)

"useDefineForClassFields"
  Controls how class fields are compiled (TC39 spec vs legacy TypeScript).
  "useDefineForClassFields": true  // Recommended for modern targets

━━━ MODULE RESOLUTION ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"module"
  The module format for the output JS.
  Values: "CommonJS" | "ESNext" | "ES2015" | "NodeNext" | "Node16" | "UMD" | "AMD"

  "module": "CommonJS"   // Node.js (require/module.exports)
  "module": "ESNext"     // Modern browser/bundler (import/export)
  "module": "NodeNext"   // Node.js with .mjs/.cjs support

"moduleResolution"
  How TypeScript resolves imports.
  Values: "node" | "node16" | "nodenext" | "bundler" | "classic"

  "moduleResolution": "node"     // Classic Node.js (< TS 4.7)
  "moduleResolution": "bundler"  // For Vite/webpack/esbuild (TS 5.0+)
  "moduleResolution": "NodeNext" // For modern Node.js ESM

  Pairing rules:
  • module: CommonJS     → moduleResolution: node
  • module: ESNext       → moduleResolution: bundler (bundlers) or node
  • module: NodeNext     → moduleResolution: NodeNext

"baseUrl"
  Base directory for non-relative imports.
  "baseUrl": "./src"
  // Now: import { foo } from "utils/foo" resolves to ./src/utils/foo

"paths"
  Path aliases (must be used with baseUrl).
  "paths": {
    "@components/*": ["./src/components/*"],
    "@utils/*": ["./src/utils/*"],
    "@/*": ["./src/*"]
  }
  // import Button from "@components/Button"  → ./src/components/Button

  NOTE: paths in tsconfig only affects TYPE CHECKING.
        For actual resolution at runtime/build, configure webpack/vite aliases too.

"rootDir"
  Root directory of source files. Helps preserve structure in outDir.
  "rootDir": "./src"

"outDir"
  Where to emit compiled .js files.
  "outDir": "./dist"

"rootDirs"
  Treat multiple directories as one virtual root (useful in monorepos).
  "rootDirs": ["src", "generated"]

"typeRoots"
  Directories to look for @types packages.
  "typeRoots": ["./node_modules/@types", "./custom-types"]

"types"
  Limit which @types packages are included (prevents type pollution).
  "types": ["react", "node", "jest"]
  // Only these @types/* packages will be included

━━━ EMIT OPTIONS ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"declaration"
  Generate .d.ts files alongside JS output.
  "declaration": true
  → Required when publishing a library for others to use.

"declarationDir"
  Separate output directory for .d.ts files.
  "declarationDir": "./types"

"declarationMap"
  Generate .d.ts.map files (sourcemaps for type declarations).
  "declarationMap": true
  → Useful for IDE "Go to Definition" across packages.

"sourceMap"
  Generate .js.map source map files for debugging.
  "sourceMap": true
  → Maps compiled JS back to original TS for debugger.

"inlineSourceMap"
  Embed source maps inline in .js files instead of separate files.
  "inlineSourceMap": true

"removeComments"
  Strip comments from output JS.
  "removeComments": true

"noEmit"
  Type-check only — do NOT emit any files.
  "noEmit": true
  → Used with bundlers (Vite/webpack compile for you) or just for CI checks.

"noEmitOnError"
  Do not emit JS if there are type errors.
  "noEmitOnError": true  // Recommended to prevent shipping broken code

"emitDeclarationOnly"
  Only emit .d.ts files, not JS. Useful with esbuild/swc as the bundler.
  "emitDeclarationOnly": true

"importHelpers"
  Use tslib helper functions instead of inlining them in every file.
  "importHelpers": true  // Requires: npm install tslib

━━━ TYPE CHECKING — STRICT MODE ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"strict"
  The MASTER switch — enables all strict type checking options at once.
  "strict": true  // ALWAYS enable in new projects!

  What "strict: true" enables:
  ┌────────────────────────────┬────────────────────────────────────────────┐
  │ Option                     │ What it does                               │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ strictNullChecks           │ null/undefined not assignable to other types│
  │ strictFunctionTypes        │ Stricter checking of function param types  │
  │ strictBindCallApply        │ Checks bind/call/apply arguments           │
  │ strictPropertyInitialization│ Class properties must be initialized      │
  │ noImplicitAny              │ Error on implicit `any` types              │
  │ noImplicitThis             │ Error on implicit `any` for `this`         │
  │ alwaysStrict               │ Emit "use strict" in output                │
  │ useUnknownInCatchVariables │ catch(e) → e is `unknown` not `any` (TS4.4)│
  └────────────────────────────┴────────────────────────────────────────────┘

"noImplicitAny"
  Error when TypeScript can't infer a type and falls back to `any`.
  "noImplicitAny": true  // Included in strict: true

  function greet(name) { ... }  // ❌ Parameter 'name' implicitly has 'any' type

"strictNullChecks"
  null and undefined are separate from other types.
  "strictNullChecks": true  // Included in strict: true

"noImplicitReturns"
  Error if a function doesn't return on all code paths.
  "noImplicitReturns": true

  function getVal(flag: boolean): string {
    if (flag) return "yes";
    // ❌ Error: Function lacks ending return statement
  }

"noFallthroughCasesInSwitch"
  Error if a switch case falls through without `break` or `return`.
  "noFallthroughCasesInSwitch": true

"noUnusedLocals"
  Error on unused local variables.
  "noUnusedLocals": true

"noUnusedParameters"
  Error on unused function parameters.
  "noUnusedParameters": true

"exactOptionalPropertyTypes"
  Distinguishes between optional property missing vs set to undefined.
  "exactOptionalPropertyTypes": true

  interface Config { timeout?: number; }
  const cfg: Config = { timeout: undefined }; // ❌ With exactOptionalPropertyTypes

━━━ INTEROPERABILITY ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"allowJs"
  Allow JavaScript files in the TypeScript project.
  "allowJs": true  // For gradual migration from JS to TS

"checkJs"
  Type-check JavaScript files (requires allowJs: true).
  "checkJs": true

"esModuleInterop"
  Allows default imports from CommonJS modules without * syntax.
  "esModuleInterop": true  // ALWAYS enable with CommonJS modules

  Without esModuleInterop:
    import * as React from "react";  // must use * as
  With esModuleInterop:
    import React from "react";       // ✅ cleaner syntax

"allowSyntheticDefaultImports"
  Allow default imports when module doesn't explicitly export default.
  (esModuleInterop enables this automatically)
  "allowSyntheticDefaultImports": true

"resolveJsonModule"
  Allow importing .json files as modules with full type support.
  "resolveJsonModule": true
  → import config from "./config.json"; // TS knows the shape!

"isolatedModules"
  Ensures each file can be independently transpiled (required by esbuild/Babel).
  "isolatedModules": true
  → Disallows: const enums, namespace re-exports, type-only re-exports without `type`

5. PROJECT REFERENCES (tsconfig.json references)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For monorepos with multiple TypeScript packages that depend on each other:

{
  "references": [
    { "path": "../shared" },
    { "path": "../utils" }
  ]
}

Benefits:
  • Incremental builds (only recompile changed packages)
  • Proper build ordering
  • Isolated type checking per package

Compile with: tsc --build (or tsc -b)

6. include, exclude, files
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"include"
  Glob patterns for files to compile.
  Default (if omitted): all .ts/.tsx/.d.ts files in the project root

  "include": [
    "src/**/*.ts",
    "src/**/*.tsx",
    "tests/**/*.ts"
  ]

"exclude"
  Files/folders to exclude (excluded from include patterns).
  Default: always excludes node_modules, outDir

  "exclude": [
    "node_modules",
    "dist",
    "coverage",
    "**/*.spec.ts"
  ]

"files"
  Explicit list of files to include (cannot use globs).
  "files": ["src/index.ts", "src/globals.d.ts"]
  → Use when you want precise control over what gets compiled.

Priority: files > include > exclude (files always included)

7. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is tsconfig.json and why is it important?
    tsconfig.json configures the TypeScript compiler. It specifies which
    files to compile, what JS version to target, module format, type
    checking strictness, and output location. Without it, tsc uses defaults
    which may not match your project's needs.

Q2: What does "strict: true" enable?
    It enables all strict type-checking flags at once:
    strictNullChecks, strictFunctionTypes, strictBindCallApply,
    strictPropertyInitialization, noImplicitAny, noImplicitThis,
    alwaysStrict, and useUnknownInCatchVariables.
    Always use strict: true in new projects.

Q3: What is the difference between "target" and "lib"?
    - target: controls what JavaScript version the COMPILER OUTPUTS
    - lib: controls what TypeScript type definitions are AVAILABLE
    You might target ES5 for wide browser support but include ES2015.Promise
    in lib to use Promise types (assuming a polyfill is included).

Q4: What does "noEmit: true" do? When would you use it?
    noEmit: true tells TypeScript to perform type checking only without
    writing any output files. Used when:
    • Using a bundler (Vite, webpack) that handles compilation
    • Running type checks in CI without producing build artifacts
    • Using ts-jest for testing (Jest handles compilation)

Q5: What is the difference between "moduleResolution: node" and "bundler"?
    - "node": Classic Node.js resolution (looks for index.ts, .ts extensions)
    - "bundler": For modern bundlers (allows extensionless imports, conditions)
    Use "bundler" with Vite/webpack/esbuild projects (TS 5.0+).

Q6: What is "isolatedModules: true" and when is it required?
    Each .ts file must be transpilable independently without knowledge of
    other files. Required by Babel and esbuild (can't do cross-file analysis).
    This means:
    • No const enums (they need cross-file info to inline)
    • re-exports must use `export type { X }` not just `export { X }`

Q7: What is "esModuleInterop" and why should it be enabled?
    esModuleInterop allows importing CommonJS modules with default import
    syntax. Without it: import * as React from 'react'. With it:
    import React from 'react'. Also emits helper code to handle the
    difference between CJS default exports and ESM default imports.

Q8: How do you configure path aliases in TypeScript?
    Use "baseUrl" and "paths" in tsconfig:
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
    BUT: tsconfig paths only affect TypeScript's type resolution.
    You must also configure your bundler (webpack alias, vite resolve.alias)
    or use tsconfig-paths with ts-node.

Q9: What is the difference between "declaration: true" and "emitDeclarationOnly: true"?
    - declaration: true → emit .d.ts files alongside .js files
    - emitDeclarationOnly: true → emit ONLY .d.ts files (no .js)
    Use emitDeclarationOnly when a separate tool (esbuild/swc/babel)
    handles the actual JS compilation.

Q10: What is "composite: true" used for?
     Required for Project References. Enables incremental compilation and
     requires rootDir to be set. Allows tsc --build to only recompile
     changed packages in a monorepo.
