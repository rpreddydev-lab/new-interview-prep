1. CORE DIFFERENCES — SIDE BY SIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌────────────────────────┬──────────────────────────┬────────────────────────┐
  │ Feature                │ JavaScript               │ TypeScript             │
  ├────────────────────────┼──────────────────────────┼────────────────────────┤
  │ Typing                 │ Dynamic (runtime)        │ Static (compile-time)  │
  │ Type annotations       │ No                       │ Yes                    │
  │ Type inference         │ No                       │ Yes (powerful)         │
  │ Compilation needed     │ No (interpreted)         │ Yes → compiles to JS   │
  │ Interfaces             │ No                       │ Yes                    │
  │ Enums                  │ No (workarounds only)    │ Yes (native)           │
  │ Generics               │ No                       │ Yes                    │
  │ Decorators             │ Stage 3 proposal         │ Yes (stable in TS 5.0) │
  │ Access modifiers       │ # (private fields only)  │ public/private/protected│
  │ Abstract classes       │ No                       │ Yes                    │
  │ Utility types          │ No                       │ Yes (Partial, Pick...) │
  │ Null safety            │ No (null/undefined free) │ strictNullChecks       │
  │ Error detection        │ Runtime                  │ Compile time           │
  │ IDE support            │ Limited                  │ Excellent              │
  │ Refactoring safety     │ Risky                    │ Safe (compiler guides) │
  │ Learning curve         │ Lower                    │ Higher                 │
  │ Bundle size            │ Smaller (no compiler)    │ Same at runtime        │
  │ Browser support        │ Native                   │ Via compilation        │
  └────────────────────────┴──────────────────────────┴────────────────────────┘

2. TYPING: DYNAMIC vs STATIC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT — Dynamic Typing:
  Variables can hold any type, and types can change at runtime.

  let value = 42;       // number
  value = "hello";      // still valid — now a string
  value = { x: 1 };    // still valid — now an object

  // Silent bugs:
  function double(n) { return n * 2; }
  double("5");   // returns "55" (string repetition, not math!)
  double(null);  // returns 0 — silently wrong

TYPESCRIPT — Static Typing:
  Variables have a declared (or inferred) type that cannot change.

  let value: number = 42;
  value = "hello";  // ❌ Error: Type 'string' is not assignable to type 'number'

  function double(n: number): number { return n * 2; }
  double("5");   // ❌ Error: Argument of type 'string' is not assignable to 'number'
  double(null);  // ❌ Error: Argument of type 'null' is not assignable to 'number'

3. NULL AND UNDEFINED HANDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT — The Billion Dollar Mistake:
  null and undefined can be assigned to any variable.
  This causes the most common runtime errors.

  let user = getUser(); // might return null
  console.log(user.name); // TypeError: Cannot read properties of null
                           // Crashes at runtime!

TYPESCRIPT with strictNullChecks: true:
  null and undefined are NOT assignable to other types unless explicitly allowed.

  let name: string = null;     // ❌ Error with strictNullChecks
  let name: string | null = null; // ✅ Must explicitly allow null

  function getUser(): User | null {
    return Math.random() > 0.5 ? { name: "Alice" } : null;
  }

  const user = getUser();
  console.log(user.name);       // ❌ Error: user is possibly null
  console.log(user?.name);      // ✅ Optional chaining
  if (user) console.log(user.name); // ✅ After null check

4. FUNCTION CONTRACTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT:
  function createUser(id, name, role) {
    return { id, name, role };
  }

  // Caller has no idea what types are expected
  // Must read docs or source code
  createUser("abc", 123, undefined); // No error — but likely wrong

TYPESCRIPT:
  interface User {
    id: number;
    name: string;
    role: "admin" | "user" | "guest";
  }

  function createUser(id: number, name: string, role: "admin" | "user" | "guest"): User {
    return { id, name, role };
  }

  createUser("abc", 123, undefined); // ❌ Multiple compile errors
  createUser(1, "Alice", "admin");   // ✅ IDE shows parameter types as you type

5. CLASSES: JAVASCRIPT vs TYPESCRIPT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT:
  class Animal {
    constructor(name) {
      this.name = name; // No type info
    }
    speak() {
      return `${this.name} makes a sound.`;
    }
  }
  // name can be anything — no enforcement

TYPESCRIPT:
  class Animal {
    private name: string;  // access modifier + type

    constructor(name: string) {
      this.name = name;
    }

    speak(): string {
      return `${this.name} makes a sound.`;
    }
  }

  const a = new Animal("Dog");
  a.name;  // ❌ Error: Property 'name' is private

  // TypeScript also supports:
  // - readonly properties
  // - abstract classes / methods
  // - implements (interface enforcement)
  // - parameter properties shorthand
  class Person {
    constructor(
      public readonly id: number,   // shorthand for this.id = id
      private name: string          // shorthand for this.name = name
    ) {}
  }

6. ENUMS — TYPESCRIPT EXCLUSIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT workaround:
  const Direction = Object.freeze({ UP: "UP", DOWN: "DOWN" });
  // No type safety — someone can pass any string

TYPESCRIPT:
  enum Direction { Up = "UP", Down = "DOWN" }
  function move(dir: Direction) { ... }
  move(Direction.Up); // ✅
  move("UP");         // ❌ TypeScript catches this (with string enums)

  // Even better — const enums (zero runtime cost):
  const enum Status { Active = "ACTIVE", Inactive = "INACTIVE" }
  // Inlined at compile time — no object generated in JS output

7. GENERICS — TYPESCRIPT EXCLUSIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAVASCRIPT — no generics, must use workarounds:
  function getFirst(arr) { return arr[0]; }
  // Returns `any` — no type info preserved

TYPESCRIPT — generics preserve type information:
  function getFirst<T>(arr: T[]): T { return arr[0]; }

  const num = getFirst([1, 2, 3]);     // TypeScript knows: num is number
  const str = getFirst(["a", "b"]);   // TypeScript knows: str is string

  // This is how the entire standard library (Array, Promise, Map) works!

8. TYPE ASSERTIONS vs CASTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TypeScript type assertions tell the compiler "trust me, I know the type":

  const input = document.getElementById("email") as HTMLInputElement;
  input.value; // ✅ Now TS knows it's an HTMLInputElement

  // Alternative angle bracket syntax (not usable in JSX):
  const input = <HTMLInputElement>document.getElementById("email");

IMPORTANT: Type assertions do NOT change the runtime value.
  const x = "hello" as unknown as number; // TS allows this (double assertion)
  // At runtime: x is still "hello" — assertion is compile-time only!

9. MODULES AND NAMESPACES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Both JS and TS use ES Modules (import/export). TypeScript adds:
  • Type-only imports (no runtime cost):
    import type { User } from "./types";
    // Completely erased — doesn't create a module dependency at runtime

  • Namespace imports work with types:
    import * as Utils from "./utils";
    // TypeScript knows all exported types from utils

10. PRACTICAL COMPARISON: REAL-WORLD EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO: Fetch user data and display it

JAVASCRIPT:
  async function fetchUser(id) {
    const res = await fetch(`/api/users/${id}`);
    const data = await res.json();
    return data;
  }

  const user = await fetchUser(1);
  console.log(user.username); // Is this the right property? Who knows!
  // If API returns 'name' not 'username' → undefined (no error until runtime)

TYPESCRIPT:
  interface UserResponse {
    id: number;
    name: string;
    email: string;
    role: "admin" | "user";
  }

  async function fetchUser(id: number): Promise<UserResponse> {
    const res = await fetch(`/api/users/${id}`);
    return res.json() as Promise<UserResponse>;
  }

  const user = await fetchUser(1);
  console.log(user.username); // ❌ Error: Property 'username' does not exist on type 'UserResponse'
  console.log(user.name);     // ✅ IDE autocompletes this!

11. WHEN TO USE TYPESCRIPT vs JAVASCRIPT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use TypeScript when:
  ✅ Building a large or team codebase
  ✅ Creating a library or SDK used by others
  ✅ Working with complex data structures (APIs, DBs)
  ✅ Long-term maintenance is required
  ✅ You want excellent IDE support and refactoring
  ✅ Building with Angular, NestJS, or similar TS-first frameworks

Use JavaScript when:
  ✅ Writing quick scripts or one-off automations
  ✅ Building tiny projects (< 500 lines)
  ✅ You want zero build step (direct browser scripts)
  ✅ Working in an environment where TS setup is impossible

Reality: In 2025, most new professional projects use TypeScript by default.

12. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What are the main advantages of TypeScript over JavaScript?
    • Compile-time type checking catches bugs early
    • Better IDE support (autocomplete, refactoring, go-to-definition)
    • Code is self-documenting via type annotations
    • Safer refactoring in large codebases
    • Advanced OOP features (interfaces, abstract classes, generics)

Q2: Is TypeScript a different language from JavaScript?
    TypeScript is a superset of JavaScript — every JS file is valid TS.
    TypeScript adds a type system layer that is completely erased during
    compilation, producing standard JavaScript.

Q3: Does TypeScript have any runtime overhead?
    No. Types are erased at compile time. The compiled JavaScript output
    is equivalent to hand-written JavaScript with no type information.

Q4: What is the difference between structural and nominal typing?
    Structural: Compatible if they have the same shape (TypeScript uses this)
    Nominal: Compatible only if they share the same name/declaration (C#, Java)

    // In TypeScript (structural):
    interface A { x: number }
    interface B { x: number }
    let a: A = { x: 1 };
    let b: B = a; // ✅ OK — same shape!

Q5: Can you use TypeScript without any types?
    Yes — TypeScript degrades gracefully. With `noImplicitAny: false`, all
    values default to `any` and TypeScript behaves much like JavaScript.
    This enables gradual adoption.

Q6: What happens if you disable strictNullChecks?
    null and undefined become assignable to every type, which is JavaScript's
    default behavior. This is NOT recommended as it hides null reference bugs.
    Always enable strictNullChecks in new projects.

Q7: How do you convert a JavaScript project to TypeScript?
    Step 1: Install TypeScript: npm install --save-dev typescript
    Step 2: Create tsconfig.json: npx tsc --init
    Step 3: Enable allowJs: true in tsconfig to allow existing JS files
    Step 4: Rename files .js → .ts one by one
    Step 5: Fix type errors incrementally
    Step 6: Gradually enable stricter options (strict: true)
