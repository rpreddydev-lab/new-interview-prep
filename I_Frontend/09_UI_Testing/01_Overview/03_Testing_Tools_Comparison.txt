1. TEST RUNNER COMPARISON
================================================================================

A test runner is responsible for finding test files, executing them,
reporting results, and managing the lifecycle of test suites.

┌──────────────┬──────────────┬───────────────────────────────────────────────┐
│ Tool         │ Language     │ Key Features                                  │
├──────────────┼──────────────┼───────────────────────────────────────────────┤
│ Jest         │ JS/TS        │ Zero config, built-in mocking, snapshots,     │
│              │              │ coverage (Istanbul). Industry standard.        │
├──────────────┼──────────────┼───────────────────────────────────────────────┤
│ Vitest       │ JS/TS        │ Vite-native, ESM-first, Jest-compatible API,  │
│              │              │ significantly faster than Jest for Vite apps. │
├──────────────┼──────────────┼───────────────────────────────────────────────┤
│ Mocha        │ JS/TS        │ Highly flexible, needs external assertion lib  │
│              │              │ (Chai). More setup required. Less popular now. │
├──────────────┼──────────────┼───────────────────────────────────────────────┤
│ Jasmine      │ JS/TS        │ Older framework, Angular's default. Built-in  │
│              │              │ assertions and spies. Less ecosystem.          │
├──────────────┼──────────────┼───────────────────────────────────────────────┤
│ Karma        │ JS/TS        │ Angular's old test runner. Browser-based.      │
│              │              │ Being deprecated in Angular CLI.              │
└──────────────┴──────────────┴───────────────────────────────────────────────┘

2. JEST vs VITEST
================================================================================

JEST:
  - Created by Facebook (Meta), open source
  - Runs in Node.js using jsdom (fake DOM environment)
  - Requires babel/ts-jest for TypeScript
  - Uses CommonJS by default (ESM support requires configuration)
  - Well-established ecosystem, tons of resources

VITEST:
  - Created by the Vite team
  - Native ESM support — no transformation needed
  - Reuses Vite's config (no separate test config in most cases)
  - Uses the same Jest-compatible API (describe, it, expect, vi)
  - Faster cold starts and faster watch mode
  - Built-in TypeScript support

PERFORMANCE COMPARISON:
  For a large app (500 test files):
    Jest:   ~120 seconds
    Vitest: ~40 seconds  (2-3x faster)

MIGRATION FROM JEST TO VITEST:
  - Replace jest.fn() → vi.fn()
  - Replace jest.mock() → vi.mock()
  - Replace jest.spyOn() → vi.spyOn()
  - No changes to describe/it/expect/beforeEach/afterEach

WHEN TO CHOOSE:
  ✅ Jest:    CRA apps, Next.js, apps not using Vite
  ✅ Vitest:  Vite apps, SvelteKit, Nuxt 3, Astro, new React projects

3. REACT TESTING LIBRARY (RTL) vs ENZYME
================================================================================

ENZYME (by Airbnb, created 2015):
  - Renders components with shallow, mount, or static rendering
  - Allows direct access to component internals (state, instance)
  - Tests implementation details (how it works internally)
  - Shallow rendering mocks child components
  - No longer actively maintained (no React 17/18 official support)

REACT TESTING LIBRARY (RTL, by Kent C. Dodds, 2018):
  - Renders to a real DOM (via jsdom)
  - Queries elements the way a user would (by text, role, label)
  - Does NOT expose internal component state/instance
  - Tests behavior, not implementation
  - Officially recommended by React team

COMPARISON TABLE:
┌────────────────────────┬───────────────────────┬────────────────────────────┐
│ Feature                │ Enzyme                │ React Testing Library      │
├────────────────────────┼───────────────────────┼────────────────────────────┤
│ Rendering              │ Shallow / Full Mount  │ Full DOM rendering         │
│ Access to internals    │ YES (state, instance) │ NO (by design)             │
│ Philosophy             │ Test implementation   │ Test behavior              │
│ User events            │ .simulate('click')    │ userEvent.click()          │
│ Queries                │ .find('Button')       │ getByRole, getByText       │
│ React 18 support       │ ❌ Not official        │ ✅ Fully supported          │
│ Maintenance            │ Slow/abandoned        │ Actively maintained        │
│ Community              │ Declining             │ Growing, industry standard │
└────────────────────────┴───────────────────────┴────────────────────────────┘

ENZYME'S BIGGEST PROBLEM:
  Enzyme's shallow rendering led to tests like:
    const wrapper = shallow(<UserCard user={mockUser} />);
    expect(wrapper.state('isExpanded')).toBe(false);

  This test BREAKS if you refactor state from class to hooks,
  even if the component still behaves correctly for the user.

RTL'S ADVANTAGE:
    render(<UserCard user={mockUser} />);
    expect(screen.getByText(mockUser.name)).toBeInTheDocument();
    // This test survives any internal refactor

VERDICT: Always choose RTL for new React projects.

================================================================================

Both are modern E2E testing frameworks for web applications.
See full comparison in 03_E2E_Testing/05_Cypress_vs_Playwright.txt

5. MOCKING APPROACHES: MSW vs ALTERNATIVES
================================================================================

MOCKING NETWORK REQUESTS is critical for UI testing.
The goal is to control the data your components receive without relying
on a real running server.

────────────────────────────────────────────────────────────────────────────────
MSW (MOCK SERVICE WORKER) - RECOMMENDED
────────────────────────────────────────────────────────────────────────────────
  - Intercepts requests at the network level using a Service Worker
  - Works in both browsers (for development) and Node.js (for tests)
  - Defines handlers that describe how requests should be responded to
  - Does NOT mock the fetch/axios implementation itself

  // setup: msw handlers
  const handlers = [
    http.get('/api/users', () => {
      return HttpResponse.json([{ id: 1, name: 'Alice' }]);
    }),
  ];

  PROS:
    ✅ Works with any HTTP client (fetch, axios, ky, etc.)
    ✅ Realistic — doesn't mock fetch() itself
    ✅ Same handlers work in both tests and browser development
    ✅ Easy to override per-test
    ✅ TypeScript-first design in v2

  CONS:
    ❌ More setup than jest.mock()
    ❌ Requires understanding of service worker concepts

────────────────────────────────────────────────────────────────────────────────
JEST.MOCK() / vi.mock() - COMMON BUT LIMITED
────────────────────────────────────────────────────────────────────────────────
  - Mocks entire modules (e.g., the entire axios module)
  - Fast and simple for unit tests
  - Problem: Mocks the implementation, not the network

  jest.mock('axios');
  axios.get.mockResolvedValue({ data: { users: [] } });

  PROS:
    ✅ Simple, zero extra setup
    ✅ Works great for module-level mocking

  CONS:
    ❌ Couples tests to specific HTTP client (axios vs fetch)
    ❌ Doesn't test serialization, headers, or real request logic
    ❌ Doesn't work in browser environments

────────────────────────────────────────────────────────────────────────────────
NOCK - NODE-ONLY ALTERNATIVE
────────────────────────────────────────────────────────────────────────────────
  - Intercepts Node.js http/https module calls
  - Works only in Node.js (not browser)
  - Common in API integration testing

  nock('https://api.example.com')
    .get('/users')
    .reply(200, [{ id: 1, name: 'Alice' }]);

────────────────────────────────────────────────────────────────────────────────
FETCH-MOCK / JEST-FETCH-MOCK
────────────────────────────────────────────────────────────────────────────────
  - Mocks the global fetch() function
  - Simpler than MSW but less realistic

  fetchMock.mockResponseOnce(JSON.stringify({ data: 'test' }));


RECOMMENDATION:
  Use MSW for all integration and E2E tests.
  Use jest.mock() only for pure module/function mocking.

6. VISUAL REGRESSION TESTING TOOLS
================================================================================

Visual regression tests capture screenshots and compare them pixel-by-pixel
to detect unintended visual changes.

┌──────────────┬──────────────────────────────────────────────────────────────┐
│ Tool         │ Description                                                  │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ Percy        │ Cloud-based, integrates with CI, diffs in browser UI.       │
│              │ Owned by BrowserStack. Most popular.                        │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ Chromatic    │ Made by Storybook team. Tests Storybook stories visually.   │
│              │ Best choice if you already use Storybook.                   │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ BackstopJS   │ Open source, self-hosted. Good for teams without budget.    │
│              │ Uses Puppeteer under the hood.                              │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ Argos CI     │ Fast, GitHub-integrated, open source friendly.              │
├──────────────┼──────────────────────────────────────────────────────────────┤
│ Playwright   │ Built-in toHaveScreenshot() assertion. No extra tool.       │
│ Screenshots  │ Good for E2E-level visual checks.                           │
└──────────────┴──────────────────────────────────────────────────────────────┘

IMPORTANT CAVEAT:
  Visual regression tests are expensive to maintain — any intentional design
  change requires updating all baselines. Use them for stable, critical UI.

7. ACCESSIBILITY TESTING TOOLS
================================================================================

Accessibility testing verifies your UI is usable by people with disabilities.
Target standard: WCAG 2.1 (AA level for most apps, AAA for gov/medical).

AUTOMATED ACCESSIBILITY TOOLS:
┌────────────────┬───────────────────────────────────────────────────────────┐
│ Tool           │ Use Case                                                   │
├────────────────┼───────────────────────────────────────────────────────────┤
│ jest-axe       │ Run axe checks in Jest/RTL tests. Catches ~30% of a11y   │
│                │ issues. Low effort, high value.                           │
├────────────────┼───────────────────────────────────────────────────────────┤
│ axe-core       │ Core engine behind jest-axe. Can be used directly.        │
├────────────────┼───────────────────────────────────────────────────────────┤
│ Lighthouse     │ Google's audit tool. Runs in CLI or Chrome DevTools.      │
│                │ Tests performance, a11y, SEO, best practices.             │
├────────────────┼───────────────────────────────────────────────────────────┤
│ pa11y          │ CLI tool for automated a11y audits. Good for CI.          │
├────────────────┼───────────────────────────────────────────────────────────┤
│ Deque axe      │ Browser DevTools extension for manual + automated checks. │
├────────────────┼───────────────────────────────────────────────────────────┤
│ Playwright     │ Has built-in accessibility tree checks                    │
│ axe-playwright │ (getByRole, getByLabel) + axe-playwright for full audits. │
└────────────────┴───────────────────────────────────────────────────────────┘

EXAMPLE: jest-axe
  import { axe, toHaveNoViolations } from 'jest-axe';
  expect.extend(toHaveNoViolations);

  it('has no accessibility violations', async () => {
    const { container } = render(<LoginForm />);
    const results = await axe(container);
    expect(results).toHaveNoViolations();
  });

NOTE: Automated tools catch structural issues (missing alt text, missing labels,
bad contrast ratios) but cannot catch all a11y problems. Manual testing with
a screen reader (VoiceOver, NVDA) is still necessary.

8. CODE COVERAGE TOOLS
================================================================================

Code coverage measures how much of your source code is exercised by tests.

┌────────────────────┬──────────────────────────────────────────────────────┐
│ Tool               │ Description                                          │
├────────────────────┼──────────────────────────────────────────────────────┤
│ Istanbul / NYC     │ Most widely used JS coverage tool. Built into Jest.  │
├────────────────────┼──────────────────────────────────────────────────────┤
│ c8                 │ Uses V8's built-in coverage. Faster than Istanbul.   │
│                    │ Used by Vitest by default.                           │
├────────────────────┼──────────────────────────────────────────────────────┤
│ Codecov            │ Cloud service that tracks coverage over time.        │
│                    │ PR comments showing coverage diffs.                  │
├────────────────────┼──────────────────────────────────────────────────────┤
│ Coveralls          │ Similar to Codecov. Also tracks over time.           │
└────────────────────┴──────────────────────────────────────────────────────┘

COVERAGE TYPES:
  - Statement:  Has each statement been executed?
  - Branch:     Has each if/else branch been taken?
  - Function:   Has each function been called?
  - Line:       Has each line been executed?

COVERAGE THRESHOLDS IN JEST:
  // jest.config.js
  coverageThreshold: {
    global: {
      branches: 80,
      functions: 80,
      lines: 80,
      statements: 80,
    }
  }

COMMON MISCONCEPTION:
  100% coverage does NOT mean 100% correct code.
  You can have full coverage and still have bugs.
  Coverage tells you what code was RUN, not whether it was tested CORRECTLY.

9. TOOL SELECTION GUIDE
================================================================================

DECISION TREE:

Q: What build tool does your project use?
  → Vite / Vite-based (SvelteKit, Nuxt3, etc.): Use VITEST
  → Webpack / CRA / Next.js: Use JEST

Q: What UI framework?
  → React: Use REACT TESTING LIBRARY (@testing-library/react)
  → Vue: Use @testing-library/vue or Vitest + Vue Test Utils
  → Angular: Use Jest or Jasmine + Angular Testing Module
  → Svelte: Use @testing-library/svelte

Q: Do you need E2E tests?
  → Cross-browser required: PLAYWRIGHT
  → Best DX, Chrome only: CYPRESS
  → Already in Angular ecosystem: PROTRACTOR (legacy) or Playwright

Q: How do you mock API calls?
  → Integration + Unit tests: MSW (Mock Service Worker)
  → Unit tests, module-level: jest.mock() / vi.mock()
  → Node.js only integration tests: nock

Q: Do you need visual regression?
  → Already using Storybook: CHROMATIC
  → No Storybook, budget available: PERCY
  → Self-hosted, open source: BACKSTOPJS
  → Already using Playwright: Built-in screenshots

Q: Accessibility testing?
  → In unit/integration tests: jest-axe
  → CI audits: Lighthouse CI
  → Full audits: axe DevTools + manual testing
