1. GENERAL TESTING PRINCIPLES
================================================================================

PRINCIPLE 1: TEST BEHAVIOR, NOT IMPLEMENTATION
  Tests should verify what a component DOES, not HOW it does it.

  ❌ BAD (tests implementation):
    it('sets isLoading to true when fetching', () => {
      const { result } = renderHook(() => useUser());
      expect(result.current.isLoading).toBe(true);
    });

  ✅ GOOD (tests behavior):
    it('shows a loading spinner while data is being fetched', async () => {
      render(<UserProfile />);
      expect(screen.getByRole('progressbar')).toBeInTheDocument();
      await waitForElementToBeRemoved(() => screen.queryByRole('progressbar'));
    });

PRINCIPLE 2: ONE CONCEPT PER TEST
  Each test should test ONE specific scenario.
  If a test fails, you should know EXACTLY what broke.

  ❌ BAD (multiple concepts in one test):
    it('form works', async () => {
      render(<Form />);
      // Tests validation AND submission AND success state
    });

  ✅ GOOD (one concept per test):
    it('shows error when email is empty', async () => { ... });
    it('shows error when email is invalid', async () => { ... });
    it('submits form with valid data', async () => { ... });
    it('shows success message after submission', async () => { ... });

PRINCIPLE 3: TESTS SHOULD BE DETERMINISTIC
  The same test should always produce the same result.
  - Mock external dependencies (APIs, timers, random numbers)
  - Don't rely on shared state between tests
  - Don't test time-dependent behavior without mocking time

PRINCIPLE 4: TESTS ARE CODE — MAINTAIN THEM
  - Refactor tests when you refactor code
  - Delete obsolete tests
  - Review test PRs with the same rigor as code PRs
  - Keep tests DRY using helpers and factories

PRINCIPLE 5: TESTS AS DOCUMENTATION
  A well-named test suite describes what the system does.
  Reading test names should give you a mental model of the feature.

  describe('LoginForm', () => {
    describe('validation', () => {
      it('requires email field');
      it('requires password field');
      it('validates email format');
      it('shows error message for invalid input');
    });
    describe('submission', () => {
      it('calls onSubmit with credentials when form is valid');
      it('disables submit button while request is pending');
      it('shows error message when credentials are wrong');
      it('redirects to dashboard on successful login');
    });
  });

2. WRITING GOOD TEST NAMES
================================================================================

A good test name answers: "What does this test verify?"

FORMAT: "it [does something] when [condition]"
  or: "[component/function] [action] [expected result]"

❌ BAD TEST NAMES:
  it('works')
  it('test 1')
  it('renders')
  it('button click')
  it('shows error')

✅ GOOD TEST NAMES:
  it('displays user name when profile data is loaded')
  it('shows validation error when email field is left empty')
  it('disables submit button while form is submitting')
  it('calls onLogout and redirects to /login when logout is clicked')
  it('shows no products message when cart is empty')
  it('increases quantity when + button is clicked')
  it('handles API errors gracefully by showing a retry button')

USING DESCRIBE NESTING FOR CONTEXT:
  describe('ShoppingCart', () => {
    describe('when cart is empty', () => {
      it('shows empty state message');
      it('shows "Start Shopping" CTA button');
    });
    describe('when cart has items', () => {
      it('renders each item with its quantity');
      it('displays correct total price');
      it('removes item when delete button is clicked');
    });
    describe('when applying a discount code', () => {
      it('applies valid discount codes');
      it('shows error for invalid discount codes');
      it('calculates updated total after discount');
    });
  });

3. AAA PATTERN (ARRANGE - ACT - ASSERT)
================================================================================

Every test should follow the AAA structure:

ARRANGE: Set up the test environment
ACT:     Perform the action you're testing
ASSERT:  Verify the expected outcome

EXAMPLE:
  it('shows success message when form is submitted with valid data', async () => {
    // ────────── ARRANGE ──────────
    const mockSubmit = jest.fn().mockResolvedValue({ success: true });
    render(<ContactForm onSubmit={mockSubmit} />);

    // ────────── ACT ──────────
    await userEvent.type(screen.getByLabelText(/name/i), 'John Doe');
    await userEvent.type(screen.getByLabelText(/email/i), 'john@example.com');
    await userEvent.type(screen.getByLabelText(/message/i), 'Hello!');
    await userEvent.click(screen.getByRole('button', { name: /submit/i }));

    // ────────── ASSERT ──────────
    expect(await screen.findByText(/message sent successfully/i))
      .toBeInTheDocument();
    expect(mockSubmit).toHaveBeenCalledWith({
      name: 'John Doe',
      email: 'john@example.com',
      message: 'Hello!'
    });
  });

GIVEN-WHEN-THEN (BDD VARIANT):
  // GIVEN a logged-in user
  // WHEN they click the logout button
  // THEN they should be redirected to /login

  it('redirects to /login when user clicks logout', async () => {
    // GIVEN
    renderWithRouter(<App />, { initialEntries: ['/dashboard'] });
    // simulate logged in user via auth context

    // WHEN
    await userEvent.click(screen.getByRole('button', { name: /logout/i }));

    // THEN
    expect(window.location.pathname).toBe('/login');
  });

4. TEST ISOLATION AND INDEPENDENCE
================================================================================

Tests should NOT depend on each other. Each test should be able to run:
  - In any order
  - In isolation
  - In parallel

CLEANUP:
  RTL automatically cleans up the DOM after each test via afterEach.
  But you must manually clean up:
    - jest.fn() mocks (use jest.clearAllMocks() or jest.resetAllMocks())
    - Global state (localStorage, sessionStorage)
    - Timers (jest.useRealTimers() after fake timers)
    - MSW handlers (server.resetHandlers() in afterEach)

SETUP IN JEST:
  // jest.config.js
  setupFilesAfterFramework: ['./src/setupTests.ts']

  // setupTests.ts
  import '@testing-library/jest-dom';
  import { server } from './mocks/server';

  beforeAll(() => server.listen());
  afterEach(() => {
    server.resetHandlers();
    jest.clearAllMocks();
  });
  afterAll(() => server.close());

ANTI-PATTERN: Shared Mutable State
  ❌ BAD:
    let user;
    it('creates user', () => { user = createUser(); });
    it('updates user name', () => { updateUser(user, { name: 'new' }); }); // depends on above

  ✅ GOOD:
    it('creates user', () => { const user = createUser(); ... });
    it('updates user name', () => { const user = createUser(); updateUser(user, { name: 'new' }); ... });

5. WHAT TO TEST vs WHAT NOT TO TEST
================================================================================

WHAT TO TEST:
  ✅ User-visible behavior (what appears on screen)
  ✅ User interactions (clicking, typing, submitting)
  ✅ Error states (network errors, validation errors)
  ✅ Loading states (spinners, skeleton screens)
  ✅ Empty states (no data)
  ✅ Success states (after actions complete)
  ✅ Accessibility (keyboard nav, ARIA roles, labels)
  ✅ Business logic (pure functions, reducers, calculations)
  ✅ Edge cases (null values, empty arrays, max values)
  ✅ API integration (with mocked responses)

WHAT NOT TO TEST:
  ❌ Third-party library internals (React router, Redux — they have their own tests)
  ❌ CSS styles (test class existence, not computed styles)
  ❌ Exact internal state variables (test behavior instead)
  ❌ Trivial getters/setters with no logic
  ❌ Implementation details (which internal function was called)
  ❌ Generated or auto-implemented code

GREY AREAS:
  "Should I test this prop is passed to this child component?"
  → No. Test the BEHAVIOR that the prop enables in the child.

  "Should I test the default export vs named export?"
  → No. Test through usage/rendering.

  "Should I achieve 100% code coverage?"
  → No. Aim for meaningful coverage of important behaviors.
  → 80-90% for critical modules is typically a good target.

6. MANAGING TEST DATA
================================================================================

FACTORY FUNCTIONS:
  Instead of duplicating mock objects, create factory functions.

  // factories/user.ts
  export const createMockUser = (overrides = {}) => ({
    id: '1',
    name: 'Test User',
    email: 'test@example.com',
    role: 'user',
    createdAt: new Date('2024-01-01').toISOString(),
    ...overrides,
  });

  // In tests:
  const adminUser = createMockUser({ role: 'admin' });
  const unverifiedUser = createMockUser({ email: '', verified: false });

BUILDERS PATTERN:
  // For complex objects
  class ProductBuilder {
    private product = { id: '1', name: 'Test Product', price: 9.99, inStock: true };

    withName(name: string) { this.product.name = name; return this; }
    outOfStock() { this.product.inStock = false; return this; }
    withPrice(price: number) { this.product.price = price; return this; }
    build() { return { ...this.product }; }
  }

  const product = new ProductBuilder().withName('Widget').outOfStock().build();

FIXTURES FOR STATIC DATA:
  // fixtures/users.json
  {
    "alice": { "id": "1", "name": "Alice", "role": "admin" },
    "bob":   { "id": "2", "name": "Bob",   "role": "user" }
  }

TIPS:
  - Keep test data minimal — only what the test needs
  - Make test data readable (not just { a: 1, b: 2 })
  - Use realistic data (valid emails, real-looking names)
  - Use faker.js for large-scale generated data

7. HANDLING ASYNC TESTS
================================================================================

COMMON ASYNC PATTERNS IN RTL:

findBy* QUERIES (returns promise, waits automatically):
  const element = await screen.findByText(/welcome/i);
  // Waits up to 1000ms by default

waitFor() UTILITY:
  await waitFor(() => {
    expect(screen.getByText(/loaded/i)).toBeInTheDocument();
  });

waitForElementToBeRemoved():
  await waitForElementToBeRemoved(() => screen.queryByRole('progressbar'));

ACT() WRAPPER (for state updates):
  import { act } from 'react-dom/test-utils';
  // Usually handled automatically by userEvent and RTL's render.
  // Use only when manually triggering React state updates.

MOCKING TIMERS:
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  it('debounces search input', async () => {
    render(<SearchBox onSearch={mockSearch} />);
    await userEvent.type(screen.getByRole('searchbox'), 'react');
    expect(mockSearch).not.toHaveBeenCalled(); // not called yet (debounced)
    act(() => jest.runAllTimers());
    expect(mockSearch).toHaveBeenCalledWith('react');
  });

COMMON MISTAKE: Unhandled Promises
  ❌ Not awaiting async events leads to warnings and false passes:
    userEvent.click(button); // Missing await!
    expect(something).toBeInTheDocument(); // May pass before async completes

  ✅ Always await user events:
    await userEvent.click(button);
    expect(something).toBeInTheDocument();

8. TEST REFACTORING PATTERNS
================================================================================

CUSTOM RENDER FUNCTION:
  When many tests need the same providers (Router, Redux, Theme):

  // test-utils.tsx
  import { render, RenderOptions } from '@testing-library/react';
  import { MemoryRouter } from 'react-router-dom';
  import { Provider } from 'react-redux';
  import { store } from '../store';

  function AllProviders({ children }) {
    return (
      <Provider store={store}>
        <MemoryRouter>
          {children}
        </MemoryRouter>
      </Provider>
    );
  }

  export const customRender = (ui, options?: RenderOptions) =>
    render(ui, { wrapper: AllProviders, ...options });

  // In tests: import { customRender, screen } from '../test-utils';

SCREEN OBJECT QUERIES:
  Prefer using screen.getBy* over destructuring render():
  ✅ const button = screen.getByRole('button', { name: /submit/i });
  ❌ const { getByRole } = render(<Form />);

  screen is always up-to-date with the DOM. Destructured queries can
  get stale if the component re-renders.

SHARED SETUP PATTERNS:
  describe('ProductList', () => {
    const renderProductList = (props = {}) => {
      return render(<ProductList products={defaultProducts} {...props} />);
    };

    it('renders product names', () => {
      renderProductList();
      expect(screen.getByText('Widget')).toBeInTheDocument();
    });

    it('shows empty state when no products', () => {
      renderProductList({ products: [] });
      expect(screen.getByText(/no products/i)).toBeInTheDocument();
    });
  });

CUSTOM MATCHERS:
  // Extend jest-dom with your own matcher
  expect.extend({
    toHaveErrorMessage(element, message) {
      const errorId = element.getAttribute('aria-describedby');
      const errorElement = document.getElementById(errorId);
      const pass = errorElement?.textContent?.includes(message) ?? false;
      return {
        pass,
        message: () => `Expected element to have error message "${message}"`,
      };
    }
  });

9. CI/CD INTEGRATION BEST PRACTICES
================================================================================

RUNNING TESTS IN CI:
  - Run all tests on every PR
  - Block merges on test failures
  - Run E2E tests on staging only (not every PR — too slow)
  - Cache node_modules to speed up CI

EXAMPLE GITHUB ACTIONS WORKFLOW:
  name: Test
  on: [push, pull_request]
  jobs:
    test:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v3
        - uses: actions/setup-node@v3
          with: { node-version: '20' }
        - run: npm ci
        - run: npm test -- --coverage --ci
        - uses: codecov/codecov-action@v3

CI-SPECIFIC JEST FLAGS:
  --ci:         Fail on new snapshots (don't create them), treat warnings as errors
  --coverage:   Generate coverage report
  --forceExit:  Force exit after all tests complete (prevents hanging)
  --runInBand:  Run tests serially (useful when hitting CI memory limits)

PARALLELIZATION:
  Jest automatically runs test files in parallel using worker processes.
  For very large suites, use --maxWorkers=50% to avoid resource contention.

COVERAGE REPORTING:
  Upload to Codecov or Coveralls to track coverage trends over time.
  Set coverage thresholds to fail CI if coverage drops:
    coverageThreshold: { global: { lines: 80 } }

10. TEAM TESTING CULTURE
================================================================================

BUILDING A TESTING CULTURE:

1. LEAD BY EXAMPLE
   - Reviewers should ask for tests in PRs
   - Tech leads should write well-tested code
   - Share good testing patterns in team docs

2. MAKE TESTING EASY
   - Provide custom render helpers and factories
   - Document how to run tests locally
   - Set up fast CI feedback loops

3. FAIL FAST
   - Tests should fail loudly when something is wrong
   - Fix flaky tests IMMEDIATELY — don't tolerate them
   - A flaky test is worse than no test (it erodes trust)

4. COVERAGE AS A GUIDE, NOT A GOAL
   - Don't enforce 100% coverage blindly
   - Use coverage to find UNTESTED important paths
   - Not: "We need to reach 80%" → "We need to test the checkout flow"

5. TEST NAMING CONVENTIONS
   Agree on a team-wide naming convention:
   - File names: *.test.ts, *.spec.ts
   - Location: __tests__/ folder or next to component
   - Test suite: describe('<ComponentName>', () => ...)
   - Test case: it('does something when condition', () => ...)

6. ROTATION POLICY FOR E2E
   - Assign ownership of E2E tests to specific teams
   - Review E2E test failures in weekly standup
   - Budget time to maintain E2E tests (not optional)

7. DOCUMENTATION
   - Keep a testing guide in the repo (docs/testing.md)
   - Include: How to run tests, how to add factories, how to mock APIs
   - Review and update the guide quarterly

INTERVIEW INSIGHT:
  "How do you handle a team that doesn't write tests?"
  Answer: "I start by making testing easy — setting up the infrastructure,
  creating helpers and factories, and writing a clear guide. I lead by example
  by writing well-tested PRs and reviewing others' PRs with testing in mind.
  I focus on demonstrating value: showing that tests catch real bugs and
  speed up development over time, not slow it down."
