1. CORE PHILOSOPHY (BEGINNER)
================================================================================

Q: What is React Testing Library and how does it differ from Enzyme?
A: RTL is a testing utility that renders React components into a real DOM
   (via jsdom) and provides helpers to query and interact with it.

   Key difference from Enzyme:
   - RTL tests from the USER's perspective (what they see/interact with)
   - Enzyme tested from the DEVELOPER's perspective (component internals)
   - RTL does NOT expose internal state, lifecycle methods, or implementation
   - Enzyme allowed: wrapper.state(), wrapper.instance(), shallow rendering
   - RTL: none of that — you can only see the DOM

   Why RTL won: Tests that test implementation details break when you refactor
   without changing behavior. RTL tests survive refactoring.

─────────────────────────────────────────────────────────────────────────────

Q: What is the guiding principle of React Testing Library?
A: "The more your tests resemble the way your software is used, the more
   confidence they can give you." — Kent C. Dodds

   This means:
   - Query elements by accessible attributes (role, label) not CSS/data-testid
   - Interact via user events (click, type) not internal method calls
   - Assert on visible output, not component state

─────────────────────────────────────────────────────────────────────────────

Q: What does render() return and what are the most useful properties?
A: render() returns an object with:
   - screen: imported separately (not part of return) — preferred
   - rerender(ui): re-render with new props
   - unmount(): unmounts the component
   - asFragment(): returns DocumentFragment for snapshot testing
   - debug(): prints the current DOM to console
   - container: the wrapping DOM element (avoid using directly)
   - baseElement: document.body

2. QUERIES AND SELECTORS (INTERMEDIATE)
================================================================================

Q: What is the query priority order in RTL and why does it matter?
A: RTL's official priority order (most to least preferred):
   1. getByRole         — ARIA roles, most accessible
   2. getByLabelText    — Form fields with labels
   3. getByPlaceholderText — Placeholder (weak association)
   4. getByText         — Text content (for non-interactive elements)
   5. getByDisplayValue — Form control current value
   6. getByAltText      — Images with alt text
   7. getByTitle        — title attribute
   8. getByTestId       — data-testid (last resort)

   It matters because: using role/label tests that your app is ACCESSIBLE.
   A button that's only findable by data-testid but not by its role means
   screen readers can't find it either.

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between getBy, queryBy, and findBy queries?
A:
  getBy*:    Throws if element not found. Throws if more than 1 found.
             Use when element MUST be present right now.

  queryBy*:  Returns null if not found. Throws if more than 1 found.
             Use for asserting an element does NOT exist:
             expect(screen.queryByRole('alert')).not.toBeInTheDocument()

  findBy*:   Returns a Promise. Waits for element to appear (default 1000ms).
             Use for elements that appear ASYNCHRONOUSLY.

  getAllBy*:  Returns an array, throws if none found.
  queryAllBy*: Returns array (empty if none). No throws.
  findAllBy*:  Returns Promise<array>. Waits for at least one.

  GOTCHA: Using getBy for an element that loads asynchronously causes a
  test failure before the element appears. Always use findBy for async.

─────────────────────────────────────────────────────────────────────────────

Q: How do you query by ARIA role and what are some implicit ARIA roles?
A: getByRole queries by the element's ARIA role — either explicit (role="dialog")
   or implicit (native HTML elements have built-in ARIA roles).

   <button>           → role="button"
   <a href="...">     → role="link"
   <input type="text"> → role="textbox"
   <h1>-<h6>         → role="heading" (+ level option)
   <ul>, <ol>         → role="list"
   <li>               → role="listitem"
   <select>           → role="combobox"
   <table>            → role="table"
   <img alt="...">    → role="img"

   Options:
   getByRole('button', { name: /submit/i })  // accessible name (text, aria-label)
   getByRole('heading', { level: 2 })        // h2 only
   getByRole('checkbox', { checked: true })  // checked state
   getByRole('button', { hidden: true })     // include hidden elements

─────────────────────────────────────────────────────────────────────────────

Q: When should you use data-testid?
A: data-testid is a LAST RESORT. Use it only when:
   1. Element has no text, label, or accessible ARIA role
   2. You're querying a container for a within() scoped query
   3. The element is a layout wrapper with no semantic meaning

   Never use data-testid when:
   - A button with text exists → use getByRole('button', { name })
   - A labeled input exists → use getByLabelText
   - A heading exists → use getByRole('heading', { level, name })

─────────────────────────────────────────────────────────────────────────────

Q: How does the within() function work?
A: within() scopes queries to a specific container element. Useful when
   multiple identical elements appear on the page.

   const dialog = screen.getByRole('dialog');
   const submitBtn = within(dialog).getByRole('button', { name: 'Submit' });

   Without within(), getByRole('button', { name: 'Submit' }) would throw
   if that button text exists elsewhere on the page.

3. USER EVENTS AND INTERACTIONS (INTERMEDIATE)
================================================================================

Q: What is the difference between fireEvent and userEvent?
A:
  fireEvent: Dispatches a single DOM event. Low-level.
    fireEvent.click(button) → fires only the 'click' event.

  userEvent: Simulates REAL user behavior — fires the entire chain of
    events a browser fires for that action.

    userEvent.click(button) fires:
    pointerover → pointerenter → mouseover → mouseenter →
    pointermove → mousemove → pointerdown → mousedown →
    pointerup → mouseup → click

  Why it matters: Your event handlers might depend on these intermediate events.
  Also: fireEvent.change() doesn't fire keydown/keyup, which some libraries
  (like React Hook Form) rely on for validation.

  Rule: Always prefer userEvent over fireEvent.
  Exception: Testing specific edge cases where only one event fires.

─────────────────────────────────────────────────────────────────────────────

Q: How do you use userEvent in tests? What changed in v14?
A: v14 introduced the setup() pattern. You must create a user instance:

   // ✅ v14 correct way:
   const user = userEvent.setup();
   await user.click(button);
   await user.type(input, 'hello');

   // ❌ v13 way (still works but deprecated):
   userEvent.click(button);  // sync, no setup needed

   WHY SETUP(): Returns an API that preserves state between interactions
   (like a real browser session). Also supports options:
   userEvent.setup({ delay: 50, advanceTimers: jest.advanceTimersByTime })

─────────────────────────────────────────────────────────────────────────────

Q: userEvent.type() vs userEvent.keyboard() — what's the difference?
A:
  user.type(element, 'hello'):
    - Clicks the element first (moves focus)
    - Types each character one by one
    - '{enter}', '{backspace}' are special keys
    - APPENDS to existing value (doesn't clear first)

  user.keyboard('hello'):
    - Does NOT click/focus any element
    - Types in whatever element is currently focused
    - '{Enter}', '{Backspace}' are special keys
    - Useful for testing keyboard shortcuts, tab navigation

  Common mistake: Using user.type() expecting it to clear the input.
  Fix: await user.clear(input) before typing, or use user.type('[Selectall]hello').

4. ASYNC TESTING WITH RTL (INTERMEDIATE)
================================================================================

Q: Why does RTL have async utilities (waitFor, findBy)? Can't you just await render()?
A: render() is synchronous — it renders the component immediately.
   But React may schedule state updates (e.g., from useEffect) to run
   AFTER the initial render. Data fetching happens after mount.

   await render(<UserProfile id="1" />) does NOT wait for the fetch to complete.
   You need to wait for the resulting DOM change:

   render(<UserProfile id="1" />);
   const name = await screen.findByText('Alice'); // waits up to 1000ms

─────────────────────────────────────────────────────────────────────────────

Q: What is waitFor() and when do you use it over findBy*?
A: waitFor(callback) retries the callback until it stops throwing or times out.
   Use it when you need to assert multiple things, or assert something is GONE.

   findByText('Alice') is equivalent to:
   waitFor(() => screen.getByText('Alice'))

   But waitFor is more flexible:
   await waitFor(() => {
     expect(screen.getByText('Welcome')).toBeInTheDocument();
     expect(screen.getByRole('button')).not.toBeDisabled();
   });

   // Assert element is GONE:
   await waitForElementToBeRemoved(() => screen.getByRole('progressbar'));

─────────────────────────────────────────────────────────────────────────────

Q: What causes the "not wrapped in act()" warning and how do you fix it?
A: The warning appears when a state update happens AFTER your test has
   finished (or outside of React's control).

   Common causes:
   1. Async code (fetch) completes after the test ends
   2. Setting state after unmounting (event listener cleanup issue)
   3. Timer-based state updates after test ends

   Fixes:
   1. Await all async state updates in your test:
      await screen.findByText('Data loaded');
   2. For fake timers: userEvent.setup({ advanceTimers: jest.advanceTimersByTime })
   3. For cleanup: abort fetch on unmount (AbortController)

   RTL automatically wraps user events and renders in act(). You only
   need act() manually for edge cases like fake timers + userEvent.

─────────────────────────────────────────────────────────────────────────────

Q: How do you test error states and loading states?
A:
  // Loading state:
  render(<DataList />);
  expect(screen.getByRole('progressbar')).toBeInTheDocument();
  await waitForElementToBeRemoved(() => screen.getByRole('progressbar'));
  expect(screen.getByRole('list')).toBeInTheDocument();

  // Error state (with MSW):
  server.use(
    http.get('/api/data', () => HttpResponse.json({ error: 'Not found' }, { status: 404 }))
  );
  render(<DataList />);
  await screen.findByRole('alert');
  expect(screen.getByRole('alert')).toHaveTextContent(/failed to load/i);

5. MOCKING AND PROVIDERS (INTERMEDIATE)
================================================================================

Q: How do you test a component that uses React Context?
A: Wrap the component in the Provider in the render call:

   render(
     <ThemeProvider value={{ theme: 'dark' }}>
       <MyComponent />
     </ThemeProvider>
   );

   Better pattern: Create a custom render function:
   function renderWithProviders(ui, { theme = 'light' } = {}) {
     return render(
       <ThemeProvider value={{ theme }}>
         {ui}
       </ThemeProvider>
     );
   }
   renderWithProviders(<MyComponent />, { theme: 'dark' });

─────────────────────────────────────────────────────────────────────────────

Q: How does MSW (Mock Service Worker) differ from jest.mock() for API testing?
A:
  jest.mock('./api'):
  - Mocks at the MODULE level (mock the fetch function itself)
  - Tightly coupled to implementation (if you change fetch to axios, tests break)
  - Doesn't test actual network code paths

  MSW:
  - Intercepts at the NETWORK level (Service Worker / Node interceptor)
  - Tests your real fetch/axios code — only the network response is mocked
  - Same handlers work in browser (Storybook) and Node.js (Jest)
  - Closer to real-world behavior

  Use MSW for: React components with data fetching
  Use jest.mock: For mocking non-network modules (localStorage, browser APIs)

─────────────────────────────────────────────────────────────────────────────

Q: How do you test a Redux-connected component?
A: Create a test store with preloadedState and render with the Provider:

   function renderWithStore(ui, { preloadedState } = {}) {
     const store = configureStore({
       reducer: rootReducer,
       preloadedState,
     });
     return { ...render(<Provider store={store}>{ui}</Provider>), store };
   }

   const { store } = renderWithStore(<Cart />, {
     preloadedState: { cart: { items: [mockItem] } },
   });

   // Assert dispatched actions by checking resulting state:
   await user.click(screen.getByRole('button', { name: 'Remove' }));
   expect(store.getState().cart.items).toHaveLength(0);

6. ADVANCED QUESTIONS (SENIOR)
================================================================================

Q: How do you test a custom hook that depends on context?
A: Use renderHook with a wrapper:

   const wrapper = ({ children }) => (
     <AuthContext.Provider value={{ user: mockUser }}>
       {children}
     </AuthContext.Provider>
   );

   const { result } = renderHook(() => useCurrentUser(), { wrapper });
   expect(result.current.name).toBe('Alice');

─────────────────────────────────────────────────────────────────────────────

Q: What is the correct way to test focus management (accessibility)?
A:
   const user = userEvent.setup();
   render(<Modal />);
   await user.tab();
   expect(screen.getByRole('button', { name: 'Close' })).toHaveFocus();

   // Test focus trap:
   await user.tab();  // should cycle within modal
   expect(screen.getByRole('button', { name: 'Confirm' })).toHaveFocus();

   // Verify modal traps focus (didn't escape to document.body):
   await user.tab();
   expect(document.body).not.toHaveFocus();

─────────────────────────────────────────────────────────────────────────────

Q: How do you test components with portals (like modals rendered outside root)?
A: RTL renders portals correctly because it appends to document.body.
   Use screen.getByRole('dialog') to find the modal content:

   render(<ModalComponent isOpen={true} />);
   expect(screen.getByRole('dialog')).toBeInTheDocument();
   expect(screen.getByRole('heading', { level: 2 })).toHaveTextContent('Title');

   The portal's DOM is still queryable via screen because screen queries
   against the entire document, not just the render container.

7. QUICK-FIRE ANSWERS
================================================================================

Q: What does cleanup() do?
A: Unmounts components after each test. RTL calls it automatically in afterEach
   when you import from @testing-library/react. Prevents memory leaks.

Q: What is screen.debug()?
A: Prints the current DOM to the console. Useful for debugging failing tests.
   screen.debug(element) prints just that element's subtree.

Q: What is testing-playground?
A: screen.logTestingPlaygroundURL() logs a URL to testing-playground.com
   pre-loaded with your current DOM. You can click elements to get the
   recommended query for them.

Q: How do you test form submission?
A: Simulate a submit event on the form element:
   await user.click(screen.getByRole('button', { name: /submit/i }))
   Or: fireEvent.submit(screen.getByRole('form'))

Q: What is the difference between toBeInTheDocument() and toBeVisible()?
A: toBeInTheDocument(): Element exists in the DOM (even if hidden/invisible).
   toBeVisible(): Element is visible — no display:none, visibility:hidden,
   opacity:0, or hidden ancestor.

Q: Why should you import from @testing-library/user-event in tests?
A: @testing-library/user-event provides high-fidelity user interaction
   simulation. It ships separately from @testing-library/react.

Q: What does rerender() do?
A: const { rerender } = render(<Component prop="a" />);
   rerender(<Component prop="b" />);
   Re-renders the same component instance with new props.
   Equivalent to React updating a component's props in production.
