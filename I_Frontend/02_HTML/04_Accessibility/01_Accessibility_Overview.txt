1. WHAT IS WEB ACCESSIBILITY?
================================================================================

Web accessibility means designing and building websites and applications that
can be used by people of all abilities, including those with:
  - Visual impairments (blindness, low vision, color blindness)
  - Hearing impairments (deafness, hard of hearing)
  - Motor impairments (limited hand control, paralysis, tremors)
  - Cognitive impairments (dyslexia, learning disabilities, ADHD)
  - Neurological conditions (epilepsy, autism)
  - Temporary disabilities (broken arm, bright sunlight, noisy environment)
  - Situational limitations (slow connection, small screen)

Accessibility (a11y) is not a special feature added on top — it is a fundamental
aspect of quality web development that benefits all users.

World Health Organization statistics:
  - ~1.3 billion people have some form of disability (16% of world population)
  - ~2.2 billion people have vision impairment
  - ~430 million people have hearing loss
  - ~200 million people have intellectual disability

2. WHO BENEFITS FROM ACCESSIBILITY?
================================================================================

The "Curb Cut Effect" — features designed for people with disabilities
benefit everyone:

  Feature              Disability benefit     Universal benefit
  ---------------      -------------------    -----------------------
  Captions             Deaf users             Noisy environments, learning
  High contrast        Low vision             Reading in sunlight
  Keyboard nav         Motor impairment       Power users, speed
  Large click targets  Motor impairment       Mobile, touch screens
  Clear language       Cognitive disability   Non-native speakers, everyone
  Good color contrast  Color blindness        Projectors, bright light
  Alt text             Screen readers         Broken images, SEO
  Video transcripts    Deaf-blind users       Search engines, skimmability

People who directly benefit:
  - Permanent disability users (blind, deaf, motor impaired)
  - Temporary disability users (broken wrist, post-surgery)
  - Situational limitations (bright sun, driving, one hand occupied)
  - Older users (declining vision, motor control)
  - Users on assistive devices (screen readers, braille displays, switches)

3. TYPES OF DISABILITIES AND ASSISTIVE TECHNOLOGIES
================================================================================

VISUAL IMPAIRMENTS:
  Types: Blindness, low vision, color blindness, photosensitivity
  
  Assistive technologies:
    Screen readers:
      - NVDA + Firefox (Windows, free)
      - JAWS + Chrome (Windows, paid, enterprise)
      - VoiceOver + Safari (macOS/iOS, built-in)
      - TalkBack + Chrome (Android, built-in)
      - Narrator (Windows, built-in)
    
    Screen magnifiers:
      - ZoomText, Windows Magnifier, macOS Zoom
    
    Refreshable Braille displays:
      - Hardware device that renders text as tactile braille dots
    
    Key requirements:
      - All images have descriptive alt text
      - Reading order makes sense without visual layout
      - Color is not the only indicator of meaning
      - Sufficient color contrast (4.5:1 for normal text, 3:1 for large text)
      - All functionality works without a mouse

HEARING IMPAIRMENTS:
  Types: Deafness, hard of hearing, auditory processing disorders
  
  Assistive technologies: None (use visual interface directly)
  
  Key requirements:
    - All audio content has captions (synchronized text)
    - All videos have text transcripts
    - Audio-only content has transcripts
    - No audio-only alerts or notifications

MOTOR IMPAIRMENTS:
  Types: Paralysis, tremors, cerebral palsy, ALS, missing limbs, RSI
  
  Assistive technologies:
    - Keyboard only (most common — Tab, Arrow keys, Enter, Space, Escape)
    - Sip-and-puff devices (mouth-controlled)
    - Head tracking cameras
    - Eye tracking (tobii)
    - Switch controls (single button)
    - Voice control (Dragon NaturallySpeaking, Voice Control on macOS)
  
  Key requirements:
    - All functionality available via keyboard
    - No keyboard traps (focus can always escape a component)
    - Adequate click target size (minimum 44x44 CSS px)
    - No time limits (or user can extend/disable)
    - Skip navigation links

COGNITIVE IMPAIRMENTS:
  Types: Dyslexia, ADHD, autism, intellectual disability, brain injury, memory issues
  
  Key requirements:
    - Clear, plain language (aim for 8th grade reading level or lower)
    - Consistent navigation (same in same place across pages)
    - Error messages are clear and suggest corrections
    - No flashing content (can trigger seizures)
    - Adequate time to complete tasks
    - Short, focused content blocks

4. THE ACCESSIBILITY TREE AND HOW BROWSERS WORK
================================================================================

The Accessibility Tree:
  Browsers build TWO trees from HTML:
    1. DOM Tree — used by CSS and JavaScript
    2. Accessibility Tree — used by assistive technologies
  
  The accessibility tree is a parallel, simplified version of the DOM
  containing only elements that are relevant to accessibility.
  
  Each node in the accessibility tree has:
    Name        — Accessible name (what it's called: label, alt, aria-label)
    Role        — What kind of element it is (button, link, textbox, heading)
    State       — Current state (checked, expanded, invalid, disabled)
    Properties  — Additional info (aria-describedby, aria-required)
    Value       — Current value (for inputs, sliders, etc.)

  How browsers compute accessible name (in priority order):
    1. aria-labelledby (references another element's text)
    2. aria-label (explicit string)
    3. Native HTML semantics (button text, input label, img alt)
    4. title attribute (last resort — also tooltip)

  How to view the accessibility tree:
    Chrome DevTools → Elements panel → Accessibility tab
    Firefox DevTools → Accessibility panel
    Safari → Accessibility Inspector
    macOS Accessibility Inspector app

  ARIA (Accessible Rich Internet Applications):
    ARIA attributes modify the accessibility tree without changing visual output.
    They add roles, properties, and states to elements.
    Rule: Use native HTML elements first. Use ARIA only when native semantics
    aren't sufficient.

5. THE FOUR PRINCIPLES: POUR
================================================================================

WCAG 2.x is organized around four principles (POUR):

PERCEIVABLE — Information must be presentable in ways users can perceive
  - All non-text content has text alternatives (alt, captions, transcripts)
  - Captions for all pre-recorded audio in video
  - Sufficient color contrast
  - Text can be resized up to 200% without loss of content
  - No information conveyed by color alone
  - Content doesn't rely solely on shape, size, location, or orientation

OPERABLE — Interface must be operable by all users
  - All functionality available via keyboard
  - No keyboard traps
  - Skip navigation links (bypass repetitive content)
  - Users can control time limits
  - Nothing flashes more than 3 times per second
  - Page title describes content
  - Focus is visible at all times
  - Link purpose clear from text or context

UNDERSTANDABLE — Information and operation must be understandable
  - Language of page declared: <html lang="en">
  - Unusual words and abbreviations explained
  - Reading level appropriate
  - Pages work predictably (consistent navigation, no unexpected changes)
  - Labels identify purpose of all inputs
  - Error messages identify the problem and suggest correction
  - Forms warn before time-out

ROBUST — Content must be robust enough to be interpreted by diverse agents
  - Valid HTML (no unclosed tags, duplicate IDs)
  - Custom controls have correct ARIA roles
  - Status messages programmatically determinable (live regions)
  - Name, role, value determinable for all UI components

6. SEMANTIC HTML AS THE FOUNDATION
================================================================================

Native HTML elements provide built-in accessibility for free:

  Element         Role        Behavior
  ----------      --------    ----------------------------------------
  <button>        button      Keyboard focusable, activatable with Enter/Space
  <a href="">     link        Keyboard focusable, activatable with Enter
  <input>         textbox     Label associated, keyboard accessible
  <select>        listbox     Native dropdown, keyboard navigable
  <h1>-<h6>       heading     Heading level, navigation landmarks for SR
  <nav>           navigation  Landmark, navigable by region
  <main>          main        Landmark (one per page)
  <header>        banner      Landmark
  <footer>        contentinfo Landmark
  <section>       region      Landmark if has accessible name
  <article>       article     Landmark
  <aside>         complementary Landmark
  <form>          form        Landmark if has accessible name
  <ul>/<ol>       list        Announces item count
  <li>            listitem    Part of list
  <table>         table       Row/column navigation
  <dialog>        dialog      Focus trap, role announced

The "First Rule of ARIA":
  Before using ARIA, check if a native HTML element provides the same semantics.
  If it does, use the native element.
  
  ✗ <div role="button" tabindex="0" onclick="...">Click me</div>  // Avoid
  ✓ <button type="button" onclick="...">Click me</button>         // Prefer

7. QUICK ACCESSIBILITY CHECKLIST
================================================================================

Images:
  ✓ Informative images: alt="descriptive text" (no more than ~125 chars)
  ✓ Decorative images: alt="" (empty, not missing)
  ✓ Complex images (charts): alt + longdesc or adjacent text description
  ✓ Images of text: consider real text instead
  ✓ Functional images (icon buttons): alt describes function, not appearance

Forms:
  ✓ Every input has a visible, associated <label>
  ✓ Required fields identified (required + aria-required="true")
  ✓ Error messages: specific, visible, announced (role="alert")
  ✓ Related controls grouped with <fieldset> + <legend>
  ✓ autocomplete tokens where applicable

Color and contrast:
  ✓ Normal text: 4.5:1 contrast ratio (AA)
  ✓ Large text (18pt+ or 14pt bold): 3:1 contrast ratio (AA)
  ✓ UI components and focus rings: 3:1 contrast (AA)
  ✓ Not using color as the ONLY indicator
  ✓ Links distinguishable from surrounding text (not just by color)

Keyboard:
  ✓ All interactive elements focusable
  ✓ Logical tab order (matches visual/reading order)
  ✓ Visible focus indicator on all focusable elements
  ✓ No keyboard traps (can Tab/Escape out of modals)
  ✓ Skip links (skip to main content) for pages with repeated nav

Structure:
  ✓ <html lang="en"> (or correct language)
  ✓ <title> that's descriptive and unique
  ✓ Heading hierarchy: one <h1>, logical sub-levels
  ✓ ARIA landmarks: <main>, <nav>, <header>, <footer>
  ✓ No duplicate id values on the page

Media:
  ✓ Videos have captions (synchronized)
  ✓ Videos have text transcripts
  ✓ Audio has transcripts
  ✓ No content flashes more than 3 times per second

8. TESTING ACCESSIBILITY
================================================================================

Automated testing tools (catch ~30-40% of issues):
  - axe DevTools (Chrome extension) — industry standard
  - Lighthouse (Chrome DevTools → Lighthouse tab → Accessibility)
  - WAVE (WebAIM) — web.wave.io or browser extension
  - eslint-plugin-jsx-a11y — for React JSX linting
  - cypress-axe — automated a11y tests in Cypress

Manual testing (required for full coverage):
  1. Keyboard test — Tab through entire page without mouse
     Expected: All interactive elements reachable, logical order, no traps
  
  2. Screen reader test:
     - NVDA (free) + Firefox on Windows
     - VoiceOver on macOS (Cmd + F5) + Safari
     - TalkBack on Android
     Navigate with: H (headings), T (tables), F (forms), B (buttons), Tab

  3. Color contrast — check with:
     - WebAIM Contrast Checker (webaim.org/resources/contrastchecker)
     - Colour Contrast Analyser (desktop app)
     - Chrome DevTools → DevTools → CSS → inspect element → contrast ratio

  4. Zoom test — zoom to 200% with browser (Cmd/Ctrl + )
     Expected: Content reflows, no horizontal scroll, nothing disappears

  5. Color blindness simulation:
     - Chrome DevTools → Rendering → Emulate vision deficiencies

  6. Cognitive/readability:
     - Hemingway App (hemingwayapp.com) — reading level
     - Consistent navigation review

9. ACCESSIBILITY LAWS AND STANDARDS
================================================================================

WCAG (Web Content Accessibility Guidelines):
  - Published by W3C (World Wide Web Consortium)
  - Current: WCAG 2.1 (2018) — widely used reference
  - Latest: WCAG 2.2 (2023) — 9 new/modified criteria
  - Coming: WCAG 3.0 — major revision, in development
  
  Conformance levels:
    Level A   — Minimum; basic accessibility
    Level AA  — Standard requirement for most laws; "good" accessibility
    Level AAA — Highest; not required for entire sites
  
  Practically: Aim for WCAG 2.1 Level AA as the baseline.

Laws (selected):
  ADA (Americans with Disabilities Act)   — USA: applies to public accommodations;
    courts have increasingly ruled websites must comply
  
  Section 508                             — USA: Federal agencies MUST comply (WCAG AA)
  
  CVAA (21st Century Communications and  — USA: Advanced communications services
  Video Accessibility Act)
  
  EAA (European Accessibility Act)        — EU: Products and services (incl. web)
    from June 2025
  
  EN 301 549                              — European standard, references WCAG 2.1 AA
  
  Equality Act 2010                       — UK: Legal requirement
  
  AODA (Accessibility for Ontarians with  — Ontario, Canada
  Disabilities Act)

10. BUSINESS CASE FOR ACCESSIBILITY
================================================================================

Market size:
  - 1.3B people with disabilities = significant user base
  - Spending power in USA alone: $490B annually (disabled consumers)
  - Aging population (65+) = largest growing segment, often has accessibility needs

Legal risk:
  - Web accessibility lawsuits in USA: ~4,000/year (2022 data)
  - Domino's Pizza v. Robles reached Supreme Court (2019)
  - DOJ issued official guidance that ADA covers websites (2022)
  - Multi-billion dollar settlements in the EU since EAA 2025

SEO benefits:
  - Screen readers and search engines both rely on semantic HTML
  - Alt text contributes to image search indexing
  - Structured headings improve content comprehension by crawlers
  - Page titles, meta descriptions aligned with accessibility = better SEO
  - Fast, efficient DOM = better Core Web Vitals

Quality improvements:
  - Accessible code is typically cleaner and more maintainable
  - Semantic HTML reduces JavaScript complexity
  - Better mobile experience (keyboard = touch)
  - Improved usability for all users

11. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is web accessibility and why does it matter?
A: Web accessibility means ensuring websites and apps can be used by everyone,
   including people with disabilities (visual, hearing, motor, cognitive). It
   matters because ~16% of the world has some disability; it's a legal requirement
   in many jurisdictions (ADA, EAA, Section 508); it benefits all users
   (captions help in noisy environments, keyboard nav helps power users);
   it improves SEO; and it's simply the ethical standard for inclusive design.

Q2: What is WCAG and what are its conformance levels?
A: WCAG (Web Content Accessibility Guidelines) are the international standards
   for web accessibility published by W3C. WCAG 2.1 is the current widely-used
   standard. There are three levels: A (minimum), AA (the widely required
   standard — legally required in most jurisdictions), and AAA (aspirational).
   WCAG 2.1 AA is the practical target for most projects. WCAG 2.2 adds 9
   new criteria (mostly around focus, dragging, and target size).

Q3: What are the four POUR principles?
A: Perceivable (information must be presentable in ways users can perceive —
   alt text, captions, sufficient contrast), Operable (interface must be
   operable by everyone — keyboard access, no traps, skip links),
   Understandable (content and operation must be understandable — clear
   language, consistent navigation, error suggestions), and Robust (content
   must work with diverse user agents — valid HTML, correct ARIA semantics).

Q4: What is the accessibility tree?
A: The accessibility tree is a parallel data structure the browser builds
   alongside the DOM, containing only elements relevant to assistive technologies.
   Each node has a role (what it is), name (what it's called), state (checked,
   expanded, invalid), and value. Screen readers interact with the accessibility
   tree, not the visual DOM. ARIA attributes and semantic HTML shape the
   accessibility tree without changing visual appearance.

Q5: What is the first rule of ARIA?
A: Before using ARIA, check if a native HTML element provides the same
   semantics — if so, use the native element. Native elements come with
   built-in accessibility behaviors: keyboard support, focus management,
   state management, ARIA roles. For example, <button> is always better than
   <div role="button" tabindex="0"> because the button already has keyboard
   activation, focus, disabled state, and correct accessible role.

Q6: How do you test website accessibility?
A: Multiple approaches: (1) Automated tools — axe DevTools, Lighthouse,
   WAVE catch ~30-40% of issues. (2) Keyboard testing — navigate the entire
   page with only Tab, Shift+Tab, Enter, Space, Escape. (3) Screen reader
   testing — NVDA+Firefox (Windows) or VoiceOver+Safari (Mac). (4) Zoom to
   200% — content should reflow without horizontal scroll. (5) Color contrast
   — use WebAIM contrast checker, minimum 4.5:1 for normal text. Automated
   tools alone are insufficient; manual testing is essential.

Q7: What does WCAG AA require for color contrast?
A: Minimum 4.5:1 contrast ratio between text and its background for normal
   text. For large text (18pt+ or 14pt bold), the minimum is 3:1. For UI
   components (input borders, focus rings, icons) the minimum is 3:1. These
   ratios ensure readability for users with low vision and color blindness.
   Additionally, information must not be conveyed by color alone.

Q8: Who benefits from accessible design beyond disabled users?
A: The "Curb Cut Effect" applies broadly: captions help users in noisy
   environments or non-native speakers; high contrast helps in bright sunlight;
   keyboard navigation helps power users; large click targets help mobile/touch
   users; clear error messages help everyone; transcript text helps search
   engines; alt text appears when images fail to load; skip links help
   keyboard users navigate faster. Good accessibility is good UX for everyone.

Q9: What legal risks exist for inaccessible websites?
A: In the USA, the ADA (Americans with Disabilities Act) has been interpreted
   by courts to cover websites. There are ~4,000 ADA web accessibility lawsuits
   filed annually. The DOJ issued official guidance in 2022 confirming ADA covers
   websites. Federal agencies must comply with Section 508. In the EU, the
   European Accessibility Act (EAA) required compliance from June 2025.
   Non-compliance risks: lawsuits, fines, reputational damage.

Q10: What is the difference between a11y and i18n?
A: a11y (accessibility, 11 letters between 'a' and 'y') is about making content
   usable by people with disabilities — addressing perception, operation,
   understanding, and robustness for diverse abilities. i18n (internationalization)
   is about making content adaptable for different languages, regions, and cultures
   — date formats, text direction, translation. Both are inclusivity concerns
   but address different dimensions: ability vs language/culture.
