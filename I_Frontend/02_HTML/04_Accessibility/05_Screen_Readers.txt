1. WHAT ARE SCREEN READERS?
================================================================================

A screen reader is assistive technology software that reads digital content
aloud (text-to-speech) and/or outputs to a refreshable braille display.

Primary users:
  - People who are blind (full screen reader dependency)
  - People with low vision (used alongside magnification)
  - People with visual processing disorders
  - People who are deaf-blind (braille display output)
  - Some users with cognitive disabilities (for reading assistance)

How users interact:
  - Listen to text-to-speech output through headphones/speakers
  - Use keyboard to navigate (Tab, arrows, letter shortcuts)
  - Use refreshable braille display (tactile output)
  - Voice input with screen reader navigation

Screen readers access:
  - The accessibility tree (NOT the visual DOM directly)
  - Browser accessibility APIs (MSAA, IAccessible2, UIA on Windows;
    NSAccessibility on macOS; ATK/AT-SPI on Linux)

2. MAJOR SCREEN READERS AND THEIR ENVIRONMENTS
================================================================================

NVDA (NonVisual Desktop Access):
  Platform: Windows
  Cost: FREE and open source
  Browser: Works best with Firefox; also Chrome, Edge
  Voice: eSpeak NG (bundled), SAPI, RHVoice
  Market share: ~40% (2021 WebAIM survey)
  Developer use: Most commonly used for web development testing
  Key feature: Runs portably from USB drive

JAWS (Job Access With Speech):
  Platform: Windows
  Cost: Commercial (~$90/year, enterprise licenses)
  Browser: Works best with Chrome; also Firefox, Edge
  Market share: ~53% (primary use)
  Industry use: Enterprise, government, education
  Key feature: Advanced scripting for application-specific support

VoiceOver:
  Platform: macOS and iOS (Apple, built-in, FREE)
  Browser: Works best with Safari; also Chrome
  Activation: macOS: Cmd + F5; iOS: triple-click home button
  Market share: ~8% desktop, dominant on iOS
  Key feature: Rotor for navigating by element type (iOS)

TalkBack:
  Platform: Android (built-in, FREE)
  Browser: Chrome
  Key feature: Explore by touch; swipe to navigate elements

Narrator:
  Platform: Windows (built-in, FREE)
  Browser: Microsoft Edge
  Key feature: Improving rapidly; now uses UIA accessibility API

Orca:
  Platform: Linux (GNOME, FREE)
  Browser: Firefox
  Note: Less tested but important for Linux users

For developers: NVDA (Windows) or VoiceOver (macOS) are the most
practical testing tools because they're free.

3. HOW SCREEN READERS WORK
================================================================================

Step 1 — Browser builds accessibility tree from DOM:
  - Native semantics from HTML elements create nodes with role/name/state
  - ARIA attributes modify nodes in the accessibility tree
  - CSS display:none / visibility:hidden / hidden attribute removes nodes
  - aria-hidden="true" removes from accessibility tree (not visual)

Step 2 — Screen reader accesses accessibility API:
  - Windows: MSAA (Microsoft Active Accessibility), IAccessible2, UIA
  - macOS/iOS: NSAccessibility
  - Linux: AT-SPI (Assistive Technology Service Provider Interface)

Step 3 — Screen reader synthesizes speech or braille output:
  - Reads accessible name, role, state, and description
  - Announces in the pattern: "[name], [role], [state], [description]"
  - Example: "John Smith, button, disabled" or "Email, text field, required"

Step 4 — User uses keyboard to navigate:
  Screen readers offer two navigation models:
  - Browse mode (virtual cursor): Read everything including non-interactive text
  - Forms/application mode: Standard keyboard interaction with form controls

================================================================================
4. BROWSE MODE VS. FORMS MODE
================================================================================

BROWSE MODE (also called Virtual Mode, Reading Mode, Document Mode):
  The screen reader creates a virtual buffer (copy of page content)
  that the user can navigate character by character, word by word,
  or by element type (headings, links, buttons, form fields).
  
  Keys in browse mode:
    H           — Navigate to next heading
    Shift + H   — Navigate to previous heading
    B           — Next button
    F           — Next form field
    L           — Next list
    T           — Next table
    G           — Next graphic/image
    Arrow keys  — Move by character/word/line
    Tab         — Next focusable element
  
  Used for: Reading web page content, finding content by type

FORMS MODE (also called Application Mode, Interaction Mode):
  The screen reader passes keystrokes directly to the browser/application,
  allowing standard keyboard interaction.
  
  Triggered automatically when: Focus enters a form control (input, select)
  Triggered by: Enter key (on some elements), or user manually (NVDA: Insert+Space)
  
  In forms mode:
    Arrow keys type (or navigate select options)
    No letter shortcuts available for heading/link navigation
    Standard Tab key behavior applies
  
  Exited by: Escape key

role="application" on a container:
  Forces screen readers into application mode for the entire container.
  All keyboard handling must be implemented by the developer.
  Use rarely — most content should remain in browse mode.

Implications for developers:
  - In browse mode, screen readers can read all text including non-focusable
    elements like <p>, <span>, <div>
  - When building custom widgets, consider which mode users will be in
  - Custom keyboard behavior inside role="application" is fully developer-managed
  - ARIA live regions work regardless of mode

5. SCREEN READER NAVIGATION COMMANDS
================================================================================

NVDA Common Commands:
  Insert + Space    — Toggle browse/focus (forms) mode
  Insert + F7       — List of links, headings, form fields
  Insert + F6       — List of headings
  H                 — Next heading (browse mode)
  1-6               — Heading level 1-6
  K                 — Next link
  B                 — Next button
  F                 — Next form field
  T                 — Next table
  L                 — Next list
  G                 — Next graphic
  Insert + Down     — Read all (start reading from current position)
  Insert + Up       — Say current line
  Insert + Home     — Move to top of page
  Ctrl              — Stop reading
  Tab               — Next focusable element
  Shift + Tab       — Previous focusable element

VoiceOver (macOS) Commands:
  VO = Control + Option
  Cmd + F5          — Toggle VoiceOver on/off
  VO + Right/Left   — Move to next/previous element
  VO + Up/Down      — Navigate within element or change verbosity
  VO + Space        — Activate element
  VO + H            — VoiceOver help
  VO + U            — Rotor (navigate by headings, links, forms, etc.)
  VO + A            — Read all
  VO + F3           — Describe element
  Ctrl              — Stop reading
  Tab               — Next focusable element

JAWS Common Commands:
  H                 — Next heading (browse mode)
  Insert + F6       — List of headings
  Insert + F7       — List of links
  Tab               — Next focusable element
  Enter             — Activate link or enter forms mode
  Escape            — Exit forms mode
  F5                — Start reading from cursor
  Insert + Down     — Read all

6. ACCESSIBLE NAME AND HOW IT IS ANNOUNCED
================================================================================

Screen readers announce:  [NAME] [ROLE] [STATE/VALUE]

ORDER OF ANNOUNCEMENT (typical, varies by screen reader):

  Buttons:
    "[button text], button"
    "[button text], button, disabled"
    "[toggle text], button, pressed" (for aria-pressed)
  
  Links:
    "[link text], link"
    "[link text], link, opens in new window" (if indicated)
  
  Inputs:
    "[label text], text field"
    "[label text], edit, required" (NVDA)
    "[label text], text field, invalid" (with aria-invalid)
  
  Checkboxes:
    "[label text], checkbox, checked"
    "[label text], checkbox, not checked"
  
  Headings:
    "Heading level 2: [heading text]"  (or "[text], heading level 2")
  
  Images:
    "[alt text], image"
    (No alt or empty alt: "image" or filename announced)
  
  Groups:
    "[legend text], group" when entering a <fieldset>
  
  Tables:
    "Table with N rows and M columns: [caption text]"

Important for screen reader announcements:
  - Don't include role in aria-label (e.g., "Submit button" → says "Submit button, button")
  - Don't include state in aria-label (aria-expanded handles it)
  - Avoid very long accessible names — keep concise but descriptive
  - Punctuation affects TTS pacing (periods create brief pauses)
  - Avoid using ALL CAPS (some TTS reads letter-by-letter)
  - Avoid using symbols (& → "and", @ → "at", but "#" → "hashtag" or silent)

7. ANNOUNCEMENT PATTERNS
================================================================================

DESCRIBING IMAGES:
  Decorative: alt=""        — Screen reader skips entirely
  Informative: alt="..."    — Description of what image conveys
  Functional: alt="..."     — Describes action (e.g., "Play video")
  
  Alt text tips:
    - Don't start with "image of" or "picture of" (redundant — it's already "image")
    - Describe the meaning, not just the appearance
    - For complex charts: alt + adjacent text description or aria-describedby
    - Keep under 125 characters typically; longer if genuinely needed
    
    ✗ alt="img_logo_v3_final.png"
    ✗ alt="A photo showing a person"
    ✓ alt="Jane Smith, CEO"
    ✓ alt="Monthly revenue chart showing 25% growth from Q1 to Q4 2023"

LIVE REGION ANNOUNCEMENTS:
  role="alert" (assertive):
    Interrupts current speech immediately. Good for errors:
    <div role="alert">Error: Invalid email address</div>
    
  role="status" (polite):
    Waits for current speech to finish. Good for success messages:
    <div role="status">Form submitted successfully</div>
    
  Common mistake: Creating the live region element dynamically
  ✗ const alert = document.createElement('div');
    alert.setAttribute('role', 'alert');
    alert.textContent = 'Error!';
    document.body.appendChild(alert); // Often NOT announced!
  
  ✓ <!-- Live region must exist in DOM from page load -->
    <div role="alert" id="error-region"></div>
    // Then update content:
    document.getElementById('error-region').textContent = 'Error!';

LOADING STATES:
  <!-- Announce loading started -->
  <div role="status" aria-live="polite" id="loading-status">Loading...</div>
  // Replace content when done:
  document.getElementById('loading-status').textContent = 'Content loaded';

PAGE TITLE CHANGES (SPAs):
  Screen readers announce page title on page load.
  For SPA navigation, update document.title and manage focus.

TABLE ANNOUNCEMENTS:
  <table>
    <caption>Monthly Sales Data 2023</caption>
    <thead>
      <tr>
        <th scope="col">Month</th>
        <th scope="col">Sales ($)</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">January</th>
        <td>12,500</td>
      </tr>
    </tbody>
  </table>
  // Announced: "Table with 2 columns, caption: Monthly Sales Data 2023"
  // Cell: "Month, column header"
  // Data cell: "12,500, January column" (with scope context)

8. WRITING HTML FOR SCREEN READER COMPATIBILITY
================================================================================

1. Use semantic HTML:
   <button> not <div onclick="">
   <h1>-<h6> not <div class="heading">
   <nav> not <div class="nav">
   <ul><li> not <div class="list">

2. Every image needs alt:
   Informative: meaningful alt text
   Decorative: alt=""
   Never: missing alt attribute (announces filename!)

3. Every input needs a label:
   <label for="email">Email</label>
   <input id="email" type="email">
   // OR implicit:
   <label>Email <input type="email"></label>

4. Use landmarks for navigation:
   <header>, <nav>, <main>, <aside>, <footer>
   Label multiple landmarks of same type: aria-label

5. Provide heading hierarchy:
   One <h1> per page; logical h2 → h3 → h4 nesting
   Screen reader users navigate entirely by headings (65% of NVDA users)

6. Links must be descriptive:
   ✗ <a href="/more">Read more</a>
   ✓ <a href="/more">Read more about our accessibility services</a>
   ✓ <a href="/more">Read more <span class="sr-only">about our accessibility services</span></a>

7. Avoid opening links in new windows without warning:
   ✓ <a href="/doc" target="_blank">
        Annual Report (opens in new window)
     </a>
   Or use an icon with aria-label indicating behavior.

8. Table must have headers:
   Use <th scope="col"> and <th scope="row">
   Complex tables: id/headers attributes

9. Custom interactive elements need full ARIA:
   role + aria-* states + keyboard support

10. Visually hidden text for context:
    .sr-only {
      position: absolute;
      width: 1px;
      height: 1px;
      padding: 0;
      margin: -1px;
      overflow: hidden;
      clip: rect(0, 0, 0, 0);
      white-space: nowrap;
      border: 0;
    }
    // Use for supplemental screen reader text without affecting layout

9. COMMON SCREEN READER BUGS AND FIXES
================================================================================

BUG 1: Images with no alt attribute
  Screen reader announces filename (e.g., "IMG_4521.jpg, image")
  Fix: ALWAYS include alt attribute (descriptive or empty)

BUG 2: Icon buttons with no accessible name
  <button><svg>...</svg></button> → reads as "button" with no name
  Fix: Add aria-label or visually hidden text
  <button aria-label="Close dialog"><svg aria-hidden="true">...</svg></button>

BUG 3: Form inputs without labels
  Screen reader says "edit field" with no context
  Fix: Associate label with input using for/id or wrapping

BUG 4: Using placeholder as the only label
  Placeholder disappears on typing; not sufficient as label
  Fix: Always use <label>, use placeholder only for format hints

BUG 5: "Click here" / "Read more" links
  Screen reader list of links becomes unusable ("here, here, here, more, more")
  Fix: Descriptive link text or visually hidden additional context

BUG 6: Live region content injected before the region exists
  Dynamic creation of role="alert" elements not announced
  Fix: Keep live region in DOM from page load; update textContent

BUG 7: Modal without focus management
  Screen reader can read outside modal
  Fix: Trap focus in modal + aria-modal="true" + aria-labelledby

BUG 8: Custom dropdown not announced properly
  <div class="dropdown"> with no ARIA → screen reader silent
  Fix: Implement full combobox/listbox ARIA pattern

BUG 9: Missing language attribute
  Screen reader uses wrong pronunciation if <html lang=""> is absent
  Fix: <html lang="en"> (or appropriate language code)

BUG 10: Buttons activating on keydown instead of keyup
  Causes double-activation with screen readers
  Fix: Activate on click or keyup (not keydown) for custom widgets

10. TESTING WITH SCREEN READERS
================================================================================

Quick NVDA test (Windows):
  1. Download NVDA from nvaccess.org (free)
  2. Set browser to Firefox
  3. Browse mode navigation:
     - H to navigate headings → check logical hierarchy
     - Tab to navigate interactive elements → check all have names
     - T for tables → check structure and headers
     - G for graphics → check alt text is announced
  4. Form testing:
     - Tab to reach inputs → check labels are announced
     - Enter data → check validation errors announced
     - Submit form → check confirmation announced

Quick VoiceOver test (macOS):
  1. Cmd + F5 to enable
  2. VO + U → Rotor → navigate by headings, links, forms
  3. Tab through interactive elements
  4. Safari + VoiceOver is the recommended combo on macOS

Testing checklist:
  ✓ Page title announced correctly
  ✓ Heading hierarchy navigable and logical
  ✓ All images have meaningful descriptions or are silenced
  ✓ All form fields have labels
  ✓ Errors announced automatically
  ✓ Dynamic content changes announced (live regions)
  ✓ Modals trap focus and announce heading
  ✓ Custom widgets follow ARIA keyboard patterns
  ✓ No "click here" or context-free links

11. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is a screen reader and who uses it?
A: A screen reader is assistive technology software that converts digital
   content to speech or braille output, allowing people who cannot see the
   screen to access web content. Primary users include blind users, those
   with low vision, deaf-blind users (braille output), and some users with
   cognitive disabilities. Screen readers interact with the browser's
   accessibility API and the accessibility tree — not the visual DOM.

Q2: What are the major screen readers and their browser pairings?
A: NVDA (free, Windows) pairs best with Firefox and is the most common tool
   for developer testing. JAWS (paid, Windows) pairs best with Chrome and is
   dominant in enterprise. VoiceOver (built-in macOS/iOS) pairs with Safari.
   TalkBack (built-in Android) pairs with Chrome. Narrator (Windows built-in)
   pairs with Edge. For development testing, NVDA+Firefox or VoiceOver+Safari
   are the most accessible (free) options.

Q3: What is the difference between browse mode and forms mode?
A: Browse mode (virtual mode) lets screen reader users navigate all content
   including non-interactive text using single-key shortcuts (H for headings,
   B for buttons, etc.) via a virtual buffer. Forms mode (application mode)
   passes keystrokes directly to the page, allowing typing and standard keyboard
   interaction — triggered automatically when focus enters form controls. Users
   can switch manually with Insert+Space (NVDA). Custom widget developers must
   understand which mode applies to their component.

Q4: How do screen readers announce form inputs?
A: When a user tabs to a form input, the screen reader announces: the accessible
   name (from <label>, aria-label, or aria-labelledby), the role (text field,
   checkbox, etc.), and any state (required, invalid, disabled). For example:
   "Email, text field, required" for a required email input with a label. This
   is why every input MUST have an associated label — without it, the screen
   reader says only "text field" which provides no context.

Q5: Why should live regions exist in the DOM before content is injected?
A: Screen readers register event listeners on live region elements when they
   are added to the DOM. If you dynamically create a role="alert" element and
   immediately set its text content, the screen reader may not have time to
   register the listener and the announcement is missed. The correct pattern
   is to include the live region container in the HTML from page load (initially
   empty), then update its text content via JavaScript when you want to announce.

Q6: What makes alt text good or bad?
A: Good alt text: Conveys the same information the image conveys, written as
   a brief description of the meaning (not just appearance), doesn't start with
   "Image of" (redundant — screen reader already says "image"), and is ~125
   characters or less. Decorative images use alt="" to be silently skipped.
   Bad alt text: Missing alt attribute (announces filename), generic "image"
   or "photo" text, filename as alt text, overly long descriptions for simple
   images. For complex images (charts, graphs): provide a longer description
   in adjacent text or aria-describedby.

Q7: What is a common pattern for visually hidden text for screen readers?
A: The sr-only CSS utility class positions an element off-screen without
   using display:none (which would remove it from accessibility tree too).
   Properties: position:absolute, width:1px, height:1px, padding:0, 
   margin:-1px, overflow:hidden, clip:rect(0,0,0,0), white-space:nowrap.
   This allows screen readers to access supplemental context that sighted
   users get from visual context — like "Read more about [specific topic]"
   where "about [specific topic]" is sr-only.

Q8: How do you test a website with a screen reader?
A: Enable NVDA+Firefox (or VoiceOver+Safari). In browse mode: press H to
   navigate headings (check logical hierarchy), Tab to visit interactive elements
   (check all have names), G for images (check alt text), F for forms (check
   labels). Test form workflows: tab to fields, check labels announced, enter
   invalid data, check error announcement, submit, check confirmation.
   Check that modals trap focus, SPAs announce page changes, and dynamic
   content (live regions) is announced. No screen reader test is complete
   without actually listening — don't just check visually.

Q9: What is aria-modal and when is it needed?
A: aria-modal="true" on a dialog tells screen readers that the dialog is modal
   and content outside it should be treated as inaccessible — similar to
   CSS's modal overlay effect on the visual UI. Without it, screen readers
   in virtual/browse mode may still navigate outside the open dialog. However,
   aria-modal is not universally supported by all screen reader/browser
   combinations. For full cross-screen-reader support: also use aria-hidden=
   "true" on sibling elements in the background while the modal is open,
   ensuring background content is inaccessible to screen readers.

Q10: What does "keyboard trap" mean and why must it be avoided (except modals)?
A: A keyboard trap occurs when a user navigates into a widget or section and
   cannot Tab or Escape out of it. WCAG 2.1.2 (Level A) prohibits keyboard
   traps because they completely lock out keyboard/screen reader users.
   Exception: Modal dialogs intentionally trap focus within the dialog — but
   the user must be able to close the modal with Escape or a visible close
   button to escape the trap. The difference is intent: modals legitimately
   constrain focus as a feature, while accidental traps are bugs.
