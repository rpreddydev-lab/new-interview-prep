1. FORM STRUCTURE AND ATTRIBUTES QUESTIONS
================================================================================

Q1: What are the key attributes of the <form> element?
A: The most important form attributes: action — URL to submit to (defaults
   to current URL); method — GET or POST (default GET); enctype — MIME type
   for POST: "application/x-www-form-urlencoded" (default), "multipart/form-data"
   (required for file uploads), "text/plain" (rarely used); novalidate —
   disables HTML5 browser validation (useful when implementing custom validation
   UX); autocomplete — "on" or "off" for the entire form; target — where to
   open result (_self default, _blank). For accessible forms, also add an
   aria-label or aria-labelledby to make the form a landmark region.

Q2: What is the difference between GET and POST form methods?
A: GET appends form data to the URL as query parameters (?name=value&...).
   It's bookmarkable and shareable, but data is visible in URL, browser history,
   and server logs. Limit: ~2000 characters. Use for: search forms, filters,
   any idempotent data retrieval. POST sends data in the request body — not
   visible in URL, no practical size limit (server-configured). Use for:
   login, registration, payment, anything that changes server state (POST is
   not idempotent). Security: neither GET nor POST is secure without HTTPS —
   both are transmitted in plaintext over HTTP.

Q3: Why does enctype="multipart/form-data" matter for file uploads?
A: The default encoding "application/x-www-form-urlencoded" encodes all values
   as key=value pairs with percent-encoding. It cannot handle binary file data.
   "multipart/form-data" splits the body into multiple parts — each field
   (including files) gets its own section with a unique boundary separator.
   Files are transmitted as binary data without encoding. Without
   enctype="multipart/form-data", file contents are not sent — only the
   filename. When using fetch + FormData, this is set automatically by the
   browser (and you must NOT manually set Content-Type, as the browser must
   include the boundary string).

Q4: What is the purpose of <fieldset> and <legend>?
A: <fieldset> groups related form controls together, and <legend> provides
   a caption for that group. Screen readers announce the legend text when
   the user enters the fieldset: "Payment information group". Essential for:
   radio button groups (where individual labels are incomplete without group
   context: "Yes" only makes sense if you hear "Is this your primary address?
   group" first), checkbox groups, multi-section forms. <fieldset disabled>
   disables all controls inside the fieldset without touching each individually.
   Styling note: fieldset has unusual default border/margin in all browsers;
   often reset in CSS.

Q5: Why must every input have a label? What are the ways to associate them?
A: Labels provide the accessible name for form controls — screen readers
   announce the label when the user focuses the input. Without labels:
   users don't know what a field is for. Methods:
   1. Explicit: <label for="id">Text</label> + <input id="id"> (most common)
   2. Implicit (wrapping): <label>Email <input type="email"></label>
   3. aria-label="string" (when visual label is undesired but rare)
   4. aria-labelledby="id" (references another element's text)
   5. title attribute (last resort — tooltip, not reliable for AT)
   Placeholder is NOT a label — it disappears on input, has insufficient
   contrast, and is not announced as a label.

Q6: What are the differences between <button>, <input type="submit">,
    and <input type="button">?
A: <button> is the most flexible: can contain HTML (icons, styled text),
   can have pseudo-elements, supports type="submit"/"reset"/"button".
   Default type is "submit" — critical gotcha: a <button> without type in a form
   will submit the form unexpectedly. <input type="submit"> is self-closing, can
   only display text (value attribute). <input type="button"> creates a button
   outside the form flow — won't submit form, no default behavior. Best practice:
   always explicitly set type="button" on buttons that shouldn't submit:
   <button type="button" onclick="doSomething()">Click</button>.

2. INPUT TYPES AND ATTRIBUTES QUESTIONS
================================================================================

Q7: What HTML5 input types are available and what do they provide?
A: HTML5 added many input types beyond "text": email (validates @ format,
   triggers email keyboard on mobile), url (validates URL format), tel (phone
   keyboard on mobile, no validation), number (numeric spinner), range (slider),
   search (search-styled input with clear button on mobile), password (masked
   text), date/time/datetime-local/month/week (native date pickers), checkbox
   (boolean toggle), radio (one-of-group selection), file (file picker), color
   (color picker), hidden (invisible, always submitted), submit/reset/button/image
   (form controls). Each type provides: correct on-screen keyboard on mobile,
   native UI picker on some platforms, and built-in validation.

Q8: What is the difference between required, disabled, and readonly on inputs?
A: required — field must have a value for form submission (fails validation if
   empty). Announced by screen readers as "required". disabled — field is
   completely inert: not focusable, not editable, NOT submitted with form,
   styled as grayed out. aria-disabled="true" differs: keeps in tab order,
   you must prevent interaction in JavaScript, but value IS submitted.
   readonly — value cannot be changed by user but IS submitted with form,
   IS focusable, value can be changed programmatically. Use: disabled for
   fields that truly don't apply; readonly for confirmed or pre-filled data
   the user should see but not edit.

Q9: How does the autocomplete attribute work on inputs?
A: autocomplete controls browser autofill. On <form>: autocomplete="off"
   disables all autofill (often ignored by browsers for passwords). On
   individual inputs, specific tokens tell browsers what type of data to
   fill: name, email, tel, street-address, address-line1, address-line2,
   city, state, postal-code, country, cc-name, cc-number, cc-exp, cc-csc,
   new-password, current-password, one-time-code. WCAG 1.3.5 (AA) requires
   these tokens on inputs collecting personal information. They also help
   password managers fill correctly and benefit users with cognitive
   disabilities who struggle with repetitive data entry.

Q10: What is the difference between name and id on form inputs?
A: id is used for: DOM selection, label association (for/id), CSS targeting,
   URL fragment. It must be unique on the page. name is used for: form data
   submission — it's the key in the submitted key=value pair. It must be present
   for data to be submitted. For checkboxes and multi-selects, multiple elements
   share the same name, and the server receives an array. For radio buttons,
   the name groups them so only one can be selected. An input can exist without
   an id but still submit data (via name). An input with id but no name won't
   submit its value.

Q11: What is a datalist element and how does it differ from select?
A: <datalist> provides an autocomplete suggestion list for a text input — the
   user can still type freely or pick from suggestions:
   <input list="fruits" type="text" name="fruit">
   <datalist id="fruits">
     <option value="Apple">
     <option value="Banana">
   </datalist>
   <select> is a constrained dropdown — users can only pick from defined options
   (unless multiple and aria patterns allow custom). Differences: datalist allows
   free text; select enforces choice. datalist degrades gracefully (just a text
   input if not supported). select is better when you need strict validation of
   allowed values. datalist is better for search suggestions, autocomplete, where
   custom input is also valid.

3. FORM VALIDATION QUESTIONS
================================================================================

Q12: What built-in form validation attributes does HTML5 provide?
A: HTML5 validation attributes: required (field must have value), minlength/
   maxlength (character length), min/max (numeric or date range), pattern
   (regex must match), type (email, url, number each have implicit validation),
   step (determines valid numeric intervals). When a form is submitted, the
   browser checks these and shows native error messages if validation fails.
   The ValidityState API exposes 11 validity properties: valueMissing,
   typeMismatch, patternMismatch, tooShort, tooLong, rangeUnderflow, rangeOverflow,
   stepMismatch, badInput, customError, and valid.

Q13: How do you implement custom validation messages?
A: Use setCustomValidity(message) to set a custom error. If the string is
   non-empty, the field is considered invalid with that message. Clear with
   setCustomValidity('') when valid. Example:
   const pwd = document.getElementById('password');
   const confirm = document.getElementById('confirm');
   confirm.addEventListener('input', () => {
     if (confirm.value !== pwd.value) {
       confirm.setCustomValidity('Passwords do not match');
     } else {
       confirm.setCustomValidity('');
     }
   });
   Works with constraint validation (checkValidity()/reportValidity()). The
   customError validity state is set when setCustomValidity is non-empty.

Q14: What is the difference between checkValidity() and reportValidity()?
A: Both return true if all associated form controls are valid, false otherwise.
   checkValidity() — silently validates; returns boolean; fires the invalid
   event on invalid fields but doesn't show UI. reportValidity() — validates
   AND triggers native browser validation UI (shows error messages, scrolls
   to first invalid field). Use checkValidity() to programmatically test
   validity without affecting the UI. Use reportValidity() or form.submit()
   to trigger the standard validation UI. For custom validation UX (novalidate
   pattern), use checkValidity() and handle UI yourself.

Q15: What is the novalidate pattern for custom form validation UX?
A: Add novalidate attribute to the <form> element to disable browser's native
   validation UI (which is styled inconsistently across browsers). Then:
   1. Prevent default form submission
   2. Loop through form fields, call checkValidity() on each
   3. For invalid fields, read validity.* states to determine error type
   4. Set aria-invalid="true", aria-describedby pointing to error element
   5. Show custom error messages with consistent styling
   6. On error, focus the first invalid field or an error summary
   7. Clear errors on input/change as user corrects them
   This gives full control over error UX while still using the constraint
   validation API's logic.

Q16: How should form validation errors be made accessible?
A: Error messages must be: (1) textual — not just color or icon;
   (2) associated with the field via aria-describedby="error-id" on the input;
   (3) visible and near the field; (4) announced to screen readers — use
   role="alert" on error containers (announces immediately) or manage focus
   to the error/field; (5) the input should have aria-invalid="true" when
   invalid; (6) if there are multiple errors, provide an error summary at
   the top of the form listing all errors as links to the relevant fields.
   Error messages should tell users what went wrong AND how to fix it
   (WCAG 3.3.1 + 3.3.3).

4. FORM SUBMISSION QUESTIONS
================================================================================

Q17: How does traditional form submission work?
A: When a form is submitted (button click, Enter key, or form.submit()):
   1. Browser collects all enabled, named form controls with values
   2. Checkboxes/radio: only checked ones included
   3. Encodes according to enctype
   4. Sends HTTP request to action URL with method
   5. Browser navigates to response
   Only enabled, named controls are included — disabled fields and fields
   without name are excluded. Submit button's name/value included if it
   was used to submit (not for Enter key unless it's the only button).

Q18: How do you submit a form with fetch (AJAX)?
A: Two approaches:
   (1) FormData (for default encoding or file uploads):
   form.addEventListener('submit', async (e) => {
     e.preventDefault();
     const data = new FormData(form);
     const res = await fetch('/api/endpoint', { method: 'POST', body: data });
     // Don't set Content-Type manually — let browser set it with boundary
   });
   
   (2) JSON submission:
   e.preventDefault();
   const data = Object.fromEntries(new FormData(form));
   const res = await fetch('/api/endpoint', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify(data)
   });
   
   FormData handles file inputs natively. Object.fromEntries loses multi-value
   fields (checkboxes) — use formData.getAll('checkboxName') for those.

Q19: What is the FormData API?
A: FormData is a browser API that captures form field data into a key-value
   map, automatically handling multipart encoding. Created from a form element:
   new FormData(formElement) — captures current values. Or built manually:
   const fd = new FormData(); fd.append('name', 'Alice'); fd.append('file', fileInput.files[0]);
   Key methods: append(key, value) — adds entry (allows duplicates);
   set(key, value) — sets/replaces entry; get(key) — first value;
   getAll(key) — array of all values (for multi-select, checkboxes);
   has(key) — boolean; delete(key) — removes; entries()/keys()/values() —
   iterators. When passed to fetch body, the browser sets the correct
   Content-Type with boundary automatically.

Q20: What is the POST-Redirect-GET (PRG) pattern?
A: After a POST form submission that modifies server state (login, purchase,
   registration), the server redirects to a GET request rather than rendering
   the response directly. Without PRG: refreshing the confirmation page
   re-sends the POST (double submission risk — browser warns "Resend form
   data?"). With PRG: redirect after POST (HTTP 303 See Other); user's browser
   follows to GET request; refresh now safely repeats the GET, not the POST.
   Implementation: server processes POST, stores result, returns 303 redirect
   to success page. The success page is a GET and is safe to refresh/bookmark.

5. ACCESSIBILITY IN FORMS QUESTIONS
================================================================================

Q21: How do you group radio buttons accessibly?
A: Radio buttons MUST be grouped in a <fieldset> with a <legend>:
   <fieldset>
     <legend>Preferred contact method</legend>
     <label><input type="radio" name="contact" value="email"> Email</label>
     <label><input type="radio" name="contact" value="phone"> Phone</label>
   </fieldset>
   Screen readers announce "Preferred contact method, group" when entering
   the fieldset, then "Email, radio button, 1 of 2" for each option.
   Without the fieldset/legend, users hear only "Email, radio button" with
   no understanding of the question being asked. The name attribute also
   groups them functionally (only one can be selected), but this is separate
   from the accessible grouping.

Q22: What is the best practice for error message placement in forms?
A: Error messages should: (1) appear immediately after or near the relevant
   field (not just at top of form); (2) be persistent — don't hide the error
   while the user is correcting it; (3) be specific — "Email is invalid"
   not just "Error"; (4) suggest correction — "Enter a valid email like
   name@example.com"; (5) be associated with the input via aria-describedby
   so screen readers announce on focus; (6) be announced via role="alert" or
   focus management; (7) remain in correct reading order (after the field
   label, before the next field). For multiple errors: also include summary
   at form top with links to each field.

Q23: What is the autocomplete attribute's role in form accessibility?
A: autocomplete with proper tokens (WCAG 1.3.5 AA) allows browsers and
   password managers to automatically fill in personal information. This
   benefits users with cognitive disabilities and motor impairments who
   struggle to type. Tokens include: name, given-name, family-name, email,
   tel, street-address, postal-code, cc-number, new-password, current-password,
   one-time-code. Additionally, autocomplete="off" can cause issues for
   users who rely on autofill. Disable selectively only where genuinely needed
   (one-time codes, security answers). Setting autocomplete="new-password"
   prevents the browser from autofilling password fields with saved passwords
   on signup forms.

Q24: How do you make a multi-step form accessible?
A: Key considerations: (1) Indicate current step position (e.g., "Step 2 of 4")
   via visible text AND in the page <title> ("Shipping Info | Step 2 of 4");
   (2) On step change, move focus to the new step's heading or first field —
   screen reader users won't know the content changed otherwise; (3) Use
   aria-current="step" on the current step in a step indicator; (4) Save
   progress and don't require re-entry of previously provided data (WCAG 3.3.7);
   (5) Warn before session timeout with ability to extend (WCAG 2.2.1);
   (6) If data is lost on back navigation, warn users. Progress indicators
   should be in <nav> or as an ordered list with aria-label="Form progress".

Q25: How do you handle placeholder text and labels correctly?
A: Placeholder should ONLY supplement a label — never replace it. Problems
   with placeholder-as-label: (1) disappears on input, leaving no hint of
   what was required; (2) fails WCAG contrast requirements (3:1 minimum)
   in most default browser styles; (3) not reliably announced as label by
   screen readers; (4) users forget requirements when editing; (5) cannot
   indicate required fields clearly. Best pattern: always include a visible
   <label>; use placeholder for format example only: <label for="phone">
   Phone number</label> <input id="phone" type="tel" placeholder="555-555-5555">
   If design requires floating labels (label above field after typing), ensure
   the label is always visible (not just as placeholder before typing).
