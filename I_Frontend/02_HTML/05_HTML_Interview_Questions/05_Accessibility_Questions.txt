1. CORE ACCESSIBILITY CONCEPTS QUESTIONS
================================================================================

Q1: What is the difference between accessibility, usability, and inclusivity?
A: Usability is about how effectively and efficiently all users can accomplish
   goals — it's about good design for the "average" user. Accessibility
   specifically focuses on ensuring people with disabilities can use the
   product — it's about removing barriers. Inclusivity is the broader philosophy:
   designing for the full spectrum of human diversity (disability, language,
   culture, age, tech literacy). Accessible design is a subset of inclusive
   design. The "Curb Cut Effect" shows that accessibility features benefit
   everyone — captions help in noisy environments, keyboard navigation helps
   power users, high contrast helps in sunlight. Good accessibility is good
   usability for a wider audience.

Q2: What are the different types of disabilities that affect web use?
A: Visual: blindness (uses screen readers), low vision (screen magnifiers,
   high contrast, large text), color blindness (avoid color-only information).
   Hearing: deafness (needs captions and transcripts), hard of hearing (needs
   captions). Motor/physical: limited hand control, paralysis, tremors
   (keyboard-only navigation, switch controls, voice control, eye tracking).
   Cognitive: dyslexia (clear fonts, sufficient spacing), ADHD (no flashing,
   clear structure), memory issues (consistent navigation, error prevention).
   Neurological: epilepsy (nothing flashing >3/sec), autism (predictable,
   consistent behavior). Temporary: broken arm, post-surgery. Situational:
   bright sunlight, holding a baby, slow connection.

Q3: What is the accessibility tree and how does it differ from the DOM?
A: The DOM (Document Object Model) is the browser's full in-memory representation
   of the HTML document including all elements, attributes, and content. The
   accessibility tree is a parallel, simplified tree built from the DOM that
   contains only nodes relevant to assistive technologies. Elements with
   aria-hidden="true", display:none, or visibility:hidden are excluded.
   Each node has: role (what type of element), accessible name (what it's called),
   state (checked, expanded, invalid), and properties (described by, etc.).
   Screen readers communicate with the browser via accessibility APIs
   (MSAA/UIA on Windows, NSAccessibility on macOS, AT-SPI on Linux) that
   expose the accessibility tree, not the DOM directly.

Q4: What is the POUR framework?
A: POUR is the organizing framework of WCAG:
   Perceivable — information must be presentable in ways users can perceive
   (alt text, captions, sufficient contrast, reflow at 400% zoom).
   Operable — UI must be operable by all users (keyboard accessible, no traps,
   skip links, no seizure-inducing flashing, visible focus).
   Understandable — information and operation must be understandable (page
   language declared, predictable behavior, clear error messages and suggestions).
   Robust — content must work with diverse user agents and assistive
   technologies (valid HTML, ARIA name/role/value for custom controls,
   status messages via live regions). All four principles must be met for
   WCAG compliance.

Q5: What automated and manual tools do you use for accessibility testing?
A: Automated (catch ~30-40% of issues): axe DevTools (Chrome extension —
   industry standard, integrates with CI via axe-core), Lighthouse (built into
   Chrome DevTools Lighthouse tab), WAVE (WebAIM extension), eslint-plugin-
   jsx-a11y (for React development). Manual testing: keyboard navigation
   (Tab, Shift+Tab, Enter, Space, Escape through entire page), screen reader
   testing (NVDA+Firefox on Windows, VoiceOver+Safari on Mac), color contrast
   checker (WebAIM contrast checker, Colour Contrast Analyser app), 400% zoom
   test (no horizontal scrolling), color blindness simulation (Chrome DevTools
   Rendering panel → Emulate vision deficiencies). Automated alone is
   insufficient — manual testing catches the other 60-70%.

2. ARIA AND SEMANTIC HTML QUESTIONS
================================================================================

Q6: What are the five rules of ARIA?
A: (1) Don't use ARIA if native HTML provides the same semantics — prefer
   <button> over <div role="button">. (2) Don't change native semantics
   unless absolutely necessary — <h2 role="tab"> destroys heading semantics.
   (3) All interactive ARIA controls must be keyboard accessible — ARIA roles
   don't add keyboard behavior; you must implement it in JavaScript.
   (4) Don't use role="presentation" or aria-hidden="true" on focusable
   elements — creates invisible keyboard traps. (5) All interactive elements
   must have an accessible name — a button that says "button" with no context
   is unusable.

Q7: Explain the difference between aria-label, aria-labelledby,
    and aria-describedby.
A: aria-label provides an accessible name directly as an attribute string
   — use when no visible label text exists. aria-labelledby references
   another element's ID and uses that element's text content as the name
   — takes highest priority over aria-label, best when a visible label
   already exists. aria-describedby references an element providing additional
   description — announced after the name and role, used for hints, error
   messages, format instructions. Name computation priority: aria-labelledby
   → aria-label → native HTML association (<label for>) → title attribute.
   A table with aria-labelledby pointing to its caption, an input with
   aria-describedby pointing to a hint paragraph, a close button with
   aria-label="Close dialog" are all correct usages.

Q8: When would you use role="presentation" or role="none"?
A: role="presentation" (alias: role="none") removes semantic meaning from
   an element in the accessibility tree — it tells screen readers to ignore
   the element's role while still reading its content. Use cases: layout
   tables that aren't data tables (<table role="presentation"> prevents
   screen reader from announcing "table with 3 columns"); presentational
   list markup where list semantics are meaningless (nav lists where
   the <ul> semantics are not useful); icon elements that are already
   described by parent accessible name. Important: it propagates to owned
   elements but not to focusable children (focusable children keep their
   role regardless). Don't use on elements that contribute meaningful
   semantics.

Q9: What is the accessible name computation algorithm in practice?
A: Browsers compute an accessible name for each element in a defined
   priority order. For most elements: (1) aria-labelledby — concatenates
   referenced elements' text content, highest priority; (2) aria-label —
   explicit string; (3) Native semantics — button inner text, <label> for
   input, alt for image; (4) title attribute — last resort, also tooltip.
   For images specifically: aria-labelledby > aria-label > alt > title >
   empty alt (ignored) > missing alt (announces filename — bad). For inputs:
   aria-labelledby > aria-label > <label for> > <label> wrapping > title.
   Knowing this algorithm explains why aria-label on a button with text
   content overrides the text: aria-label wins over content unless
   aria-labelledby is also present.

Q10: How do live regions work and what are common mistakes?
A: Live regions automatically announce dynamic content to screen readers
   without requiring focus movement. The element must exist in the DOM
   before content is updated — this is the most common mistake. Create
   the container on page load (empty), then update textContent later.
   role="alert" (aria-live="assertive") interrupts immediately — use for
   errors and critical messages. role="status" (aria-live="polite") waits
   until speech finishes — use for confirmations and progress. aria-atomic=
   "true" reads the entire region as a unit. aria-relevant controls what
   changes trigger announcements (additions, removals, text, all). Common
   mistakes: creating the live region dynamically (not announced), inserting
   content via innerHTML (may not trigger), setting role on existing element
   after page load (role change not reliably picked up).

3. KEYBOARD AND FOCUS QUESTIONS
================================================================================

Q11: What is a keyboard trap and how do you handle it correctly?
A: A keyboard trap is when focus enters a component but cannot leave via
   Tab or arrow keys — violates WCAG 2.1.2 (Level A). It locks out keyboard
   and screen reader users. Exception: modal dialogs intentionally trap focus
   within them, but must provide an Escape key (or visible close button)
   to exit. The difference: modal trap is designed and expected; accidental
   trap is a bug. Implementation: for modals, intercept Tab and Shift+Tab
   when on the first/last focusable element to loop within the dialog.
   Also intercept Escape to close and return focus to the trigger. Use
   the native <dialog> element to get this for free.

Q12: What is the roving tabindex pattern and when do you need it?
A: Roving tabindex manages keyboard navigation within a composite widget
   (toolbar, tab list, radio group, menu) so the entire widget has a single
   Tab stop. At any time, only one element has tabindex="0" (the active/
   focused item); all others have tabindex="-1". Arrow keys move focus between
   items by: setting old item's tabindex to -1, setting new item's tabindex
   to 0, calling focus() on the new item. This matches user expectations
   (tools bars and menus shouldn't require 10 Tab presses) and follows ARIA
   Authoring Practices Guide keyboard patterns. Use for: toolbars, tab lists,
   tree views, radio button groups, grids, menus.

Q13: Why should you never use outline: none without an alternative?
A: The outline CSS property provides the visual focus indicator — the visible
   ring shown when an element is keyboard-focused. Removing it with
   outline: none or outline: 0 makes keyboard focus invisible, which:
   violates WCAG 2.4.7 Focus Visible (AA) and WCAG 2.4.11 Focus Appearance
   (AA, 2.2); makes the page unusable for keyboard-only users (they have
   no idea where focus is); creates a legal liability. The correct approach:
   style :focus-visible (not :focus) with a visible, sufficiently contrasted
   indicator — minimum 3:1 contrast and 2px outline per WCAG 2.2. The
   :focus-visible pseudo-class shows focus for keyboard navigation without
   showing a ring on mouse clicks for most elements.

Q14: How do you manage focus in a single-page application?
A: Without focus management, SPA route changes are silent to screen readers —
   the URL changes but no announcement is made. Best practices: (1) On route
   change, move focus to the <h1> of the new view (add tabindex="-1" to allow
   programmatic focus); (2) Or use a live region to announce the new page title;
   (3) Update document.title on every route change (screen readers may announce
   title on focus); (4) Skip navigation links should work on every route.
   For modal open: save focus reference → move to first modal element →
   trap focus. On modal close: restore focus to trigger. For expanded content
   (accordion): optionally move focus to first content item or leave on trigger.

Q15: What is the skip link pattern and why is it necessary?
A: A skip link is a hidden-but-focusable link, typically the first element
   in <body>, that allows keyboard users to bypass repetitive navigation and
   jump directly to main content. Required by WCAG 2.4.1 Bypass Blocks (A).
   Without it, keyboard users must Tab through every navigation link on every
   page. Implementation: <a href="#main" class="skip-link">Skip to content</a>
   styled with position:absolute, off-screen by default, visible on :focus.
   Target: <main id="main" tabindex="-1">. The tabindex="-1" on main is needed
   so the browser moves focus (not just scrolls) to the main element. Multiple
   skip links (skip to search, skip to footer) are fine for complex pages.

4. WCAG AND STANDARDS QUESTIONS
================================================================================

Q16: What is WCAG 2.1 Level AA and what does it mean in practice?
A: WCAG 2.1 Level AA is the internationally recognized standard for web
   accessibility — it includes all Level A criteria (minimum, 30 criteria)
   plus AA criteria (30 more criteria, 60 total in 2.1). It is legally
   required by Section 508 (US federal), the European Accessibility Act,
   EN 301 549, and AODA (Canada). In practice: all images have alt text,
   all form inputs have labels, all text meets 4.5:1 contrast (normal) /
   3:1 (large), all functionality keyboard accessible, skip links present,
   headings logical, errors text-described with suggestions, page language
   declared, no keyboard traps, autocomplete on personal data fields, content
   reflows at 400% zoom.

Q17: What color contrast ratios are required by WCAG and how do you test?
A: WCAG 1.4.3 (AA) requires: 4.5:1 for normal text (under 18pt or 14pt bold),
   3:1 for large text (18pt+ or 14pt+ bold). WCAG 1.4.6 (AAA) enhanced:
   7:1 normal, 4.5:1 large. WCAG 1.4.11 (AA) for UI components: 3:1 (input
   borders, icon-only buttons, focus indicators). Contrast is calculated using
   relative luminance formula (not just visual difference). Testing: WebAIM
   Contrast Checker (webaim.org/resources/contrastchecker), Colour Contrast
   Analyser (free desktop app), Chrome DevTools → Inspect element → CSS color
   property shows contrast ratio. Tip: don't rely on design tools alone —
   verify in browser with real rendering.

Q18: What is the difference between WCAG A, AA, and AAA?
A: Level A (minimum) — failing any A criterion makes content completely
   inaccessible to significantly impacted users; 30 criteria in WCAG 2.1;
   examples: alt text, keyboard access, no keyboard traps, captions for
   prerecorded video, page title. Level AA (standard) — required by most
   laws; 30 additional criteria; examples: 4.5:1 contrast, error suggestions,
   consistent navigation, reflow at 400%, autocomplete tokens, focus visible.
   Level AAA (enhanced) — not required for entire sites; some content cannot
   technically meet it; 28 additional criteria; examples: 7:1 contrast, sign
   language for video, reading level, no timing at all. Organizations should
   target AA, address all A failures first, add AAA improvements where feasible.

Q19: What is WCAG 1.3.1 Info and Relationships?
A: WCAG 1.3.1 (Level A) requires that information conveyed through visual
   formatting is also conveyed through code/semantics, so it can be perceived
   without seeing the visual formatting. Examples of failures: using bold CSS
   instead of <strong>/<h3> to indicate headings; using visual indentation
   to indicate list structure without <ul>/<ol>; placing asterisks (*) next
   to required fields without using required attribute or aria-required;
   using only color to indicate table headers without <th> elements; grouping
   form controls visually without <fieldset>/<legend>. The criterion doesn't
   mandate specific HTML elements — it requires that the programmatic
   representation reflects the visual information relationships.

Q20: What does WCAG say about images of text?
A: WCAG 1.4.5 (AA) states: avoid using images of text where text can achieve
   the same visual effect. If text as an image is used, the same information
   must be available in text form. Exceptions: logos/logotypes (where
   particular font is brand identity) and essential text (where a specific
   visual presentation is necessary to convey information). Problems with
   text images: pixelates on zoom, cannot be resized by browser text settings,
   cannot be selected/copied, not accessible to screen readers (alt text
   can compensate but loses styling benefit), poor performance (more bytes
   than text + CSS), bad for SEO. Modern solution: use web fonts (WOFF2)
   with CSS styling to achieve the desired appearance with real text.

5. PRACTICAL IMPLEMENTATION QUESTIONS
================================================================================

Q21: How do you make a modal dialog fully accessible?
A: Full accessible modal checklist: (1) Use role="dialog" (or native <dialog>
   element); (2) aria-modal="true" signals modal context to screen readers;
   (3) aria-labelledby pointing to the dialog's heading; (4) aria-describedby
   for optional description; (5) On open: save trigger reference, move focus
   to first interactive element or dialog itself (tabindex="-1"); (6) Trap
   focus inside: Tab wraps within modal, Shift+Tab wraps backward; (7) Escape
   key closes dialog; (8) On close: return focus to the original trigger;
   (9) Background content should have aria-hidden="true" while modal is open;
   (10) Visible close button with accessible name. Native <dialog> + showModal()
   handles items 6, 7, and part of 1, 3 automatically.

Q22: How do you create an accessible custom dropdown/select?
A: Implementing a combobox from scratch is one of the hardest accessibility
   patterns. Required: (1) <input> with role="combobox", aria-expanded=
   "false/true", aria-controls="listbox-id", aria-autocomplete="list",
   aria-activedescendant="selected-option-id"; (2) Listbox: role="listbox",
   id, aria-label; (3) Options: role="option", id, aria-selected;
   (4) Keyboard: Down arrow opens/navigates, Up arrow navigates, Enter selects,
   Escape closes, Home/End first/last, character keys jump to match;
   (5) Focus stays on input — not on options — aria-activedescendant
   tracks visual focus. Alternative: strongly prefer native <select> unless
   the design requirements cannot be met by it. Native select is keyboard-
   accessible and screen reader-compatible out of the box.

Q23: How do you handle dynamic content announcements (toasts, notifications)?
A: Dynamic notifications that appear outside the user's current focus area
   must use ARIA live regions to be announced by screen readers:
   For important alerts (errors, warnings): role="alert" / aria-live="assertive"
   — announces immediately. For status (success, info): role="status" /
   aria-live="polite" — waits for current speech. The container must exist
   in DOM before content is injected. Recommended pattern: maintain a single
   live region container at the top of the document, update its textContent
   (not innerHTML) when announcements are needed, clear it after a delay.
   Additionally: ensure toasts are visible long enough (not just 1-2 seconds),
   provide a way to dismiss, and don't auto-dismiss before users can read.

Q24: How do you make icon buttons accessible?
A: Icon-only buttons (no visible text) are common accessibility failures.
   Solutions: (1) aria-label="Descriptive action name":
   <button aria-label="Close dialog"><svg aria-hidden="true">...</svg></button>
   (2) Visually hidden text:
   <button><svg aria-hidden="true">...</svg>
   <span class="sr-only">Close dialog</span></button>
   (3) aria-labelledby pointing to a tooltip element.
   The svg needs aria-hidden="true" (or focusable="false" in SVG) to prevent
   double-announcement. The label should describe the action, not the icon's
   appearance: "Close" not "X mark". Ensure sufficient target size (44x44px
   recommended, 24x24px minimum per WCAG 2.5.8). Always check in screen
   reader — the button should announce the action, not "button" alone.

Q25: What are the accessibility requirements for images in different contexts?
A: (1) Informative images (product photo, portrait, chart) — alt text
   describing meaning: alt="Bar chart showing Q4 revenue of $2.4M, up 15%".
   (2) Decorative images (visual flourish, dividers, backgrounds) — empty
   alt: alt="", optionally role="presentation". Missing alt causes filename
   announcement — always include alt. (3) Functional images (icon buttons,
   logo linking home) — alt describes function: alt="Home" not alt="Logo".
   (4) Complex images (detailed charts, diagrams) — brief alt + extended
   description via aria-describedby or adjacent text. (5) Images of text —
   alt should contain the text. (6) Animated images/GIFs — check for
   seizure threshold (<3 flashes/sec); provide pause control. (7) SVG:
   <svg role="img" aria-label="..."> or <svg aria-labelledby="title-id">
   with <title id="title-id"> inside. (8) CSS background images — cannot
   have alt; convey meaning through adjacent text if informative.
