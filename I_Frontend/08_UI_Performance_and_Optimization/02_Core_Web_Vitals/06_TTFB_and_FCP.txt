================================================================
TTFB AND FCP - SERVER RESPONSE & FIRST PAINT
================================================================

TTFB - TIME TO FIRST BYTE
══════════════════════════════════════════════════════════════════

DEFINITION
──────────
TTFB measures the time from when the browser starts requesting a resource
to when the FIRST BYTE of the response starts arriving.

TTFB = Redirect Time + Service Worker Startup + Connection Setup + Server Processing Time

In other words: "How fast does the server respond?"

THRESHOLDS:
  ✅ Good:              ≤ 800ms
  ⚠️  Needs Improvement: 800ms – 1,800ms
  ❌ Poor:              > 1,800ms

WHY TTFB MATTERS:
  - TTFB is the starting point for ALL other metrics
  - High TTFB → high LCP (can't be faster than when bytes arrive)
  - High TTFB → high FCP
  - Even if everything else is perfect, slow TTFB means slow page
  
  Rule: Every millisecond of TTFB = at least 1ms of LCP
  A 2s TTFB means LCP can never be < 2s

================================================================
COMPONENTS OF TTFB
================================================================

TTFB = [Redirect time]
      + [Service Worker startup]
      + [DNS lookup]
      + [Connection (TCP + TLS)]
      + [Request sent]
      + [Waiting for server response (the main factor)]

What the browser shows in Network panel "Timing" tab:
  ┌──────────────────────────────────────────────────────────┐
  │ Queueing               │ Waiting for browser slot        │
  │ DNS Lookup             │ Domain name resolution           │
  │ Initial Connection     │ TCP handshake                   │
  │ SSL                    │ TLS negotiation                 │
  │ Request Sent           │ Sending HTTP request            │
  │ WAITING (TTFB)         │ ← Server processing time        │
  │ Content Download       │ Receiving response body         │
  └──────────────────────────────────────────────────────────┘

MEASURING TTFB IN JAVASCRIPT:
──────────────────────────────
// Navigation Timing API
const nav = performance.getEntriesByType('navigation')[0];
const ttfb = nav.responseStart - nav.startTime;
console.log('TTFB:', ttfb, 'ms');

// Web Vitals library
import { onTTFB } from 'web-vitals';
onTTFB(({ value, rating }) => {
  console.log(`TTFB: ${value}ms (${rating})`);
});

================================================================
WHAT CAUSES SLOW TTFB?
================================================================

1. SLOW SERVER-SIDE PROCESSING
  - Slow database queries (N+1 queries, missing indexes)
  - No caching → every request hits the database
  - Synchronous external API calls (chained requests)
  - Inefficient server-side rendering
  - Insufficient server resources (undersized servers under load)

2. NO CDN (Content Delivery Network)
  - All requests route to origin server (far from user)
  - Each extra 1000km ≈ +10ms latency (speed of light limitation)
  - No CDN = users in Australia wait for response from US server

3. POOR HOSTING
  - Shared hosting with resource contention
  - Single region deployment (high latency for distant users)
  - No HTTP/2 or HTTP/3

4. LARGE RESPONSE BODY
  - Uncompressed HTML (missing gzip/Brotli)
  - Too much HTML in initial response (render non-critical HTML later)

================================================================
HOW TO OPTIMIZE TTFB
================================================================

1. USE A CDN
─────────────
CDN reduces latency by serving content from an edge node close to user.

For HTML (dynamic pages):
  - Use CDN with edge caching (Vercel, Netlify, Cloudflare)
  - SSG pages: CDN caches the full HTML at the edge
  - SSR pages: CDN caches for short TTLs (stale-while-revalidate)

For static assets (JS, CSS, images):
  - Always serve from CDN
  - Set long Cache-Control headers (1 year for versioned assets)

  # Nginx: set long cache for static assets
  location ~* \.(js|css|png|jpg|webp)$ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

2. CACHING AT MULTIPLE LAYERS
───────────────────────────────
  Layer 1: Browser cache (Cache-Control headers)
  Layer 2: CDN edge cache (stale-while-revalidate)
  Layer 3: Application cache (Redis, Memcached)
  Layer 4: Database query cache

  // Express.js + Redis caching example
  const redis = require('redis');
  const client = redis.createClient();
  
  async function getCachedPage(key, generator) {
    const cached = await client.get(key);
    if (cached) return cached;
    
    const result = await generator();
    await client.setEx(key, 300, result); // Cache 5 minutes
    return result;
  }
  
  app.get('/product/:id', async (req, res) => {
    const html = await getCachedPage(
      `product:${req.params.id}`,
      () => renderProductPage(req.params.id)
    );
    res.setHeader('Content-Type', 'text/html');
    res.send(html);
  });

3. OPTIMIZE DATABASE QUERIES
──────────────────────────────
  - Add indexes on frequently queried columns
  - Fix N+1 query problems (use JOINs or data loaders)
  - Use connection pooling (avoid per-request connections)
  - Consider read replicas for heavy read workloads

  // N+1 problem example (BAD)
  const posts = await Post.findAll();
  for (const post of posts) {
    const author = await User.findById(post.authorId); // N extra queries!
  }
  
  // Fixed with JOIN (GOOD)
  const posts = await Post.findAll({
    include: [{ model: User, as: 'author' }]
  });

4. HTTP/2 OR HTTP/3
─────────────────────
  HTTP/2 benefits:
  - Multiplexing: Multiple requests over single connection (no head-of-line blocking)
  - Header compression (HPACK)
  - Server Push (deprecated in HTTP/3, replaced by Preload/Early Hints)
  
  HTTP/3 benefits:
  - Uses QUIC (UDP-based, faster connection)
  - 0-RTT connection resumption
  - Better packet loss handling (independent stream multiplexing)
  
  # Enable HTTP/2 in Nginx
  listen 443 ssl http2;

5. STREAMING SSR
─────────────────
  // Next.js 13+ App Router: streaming by default
  // React 18: renderToPipeableStream
  import { renderToPipeableStream } from 'react-dom/server';
  
  app.get('/', (req, res) => {
    const { pipe } = renderToPipeableStream(<App />, {
      onShellReady() {
        res.statusCode = 200;
        res.setHeader('content-type', 'text/html');
        pipe(res); // Start streaming HTML immediately
      },
    });
  });
  
  // Benefit: TTFB improves because first bytes arrive before
  // entire page is rendered on server

6. EDGE COMPUTING
──────────────────
  // Next.js Edge Runtime: runs at CDN edge, near user
  // Cold start: ~0ms (vs Lambda ~100-500ms)
  export const runtime = 'edge'; // in Next.js route
  
  // Cloudflare Workers: runs at 200+ edge locations
  // Vercel Edge Functions: runs at Vercel's edge network

================================================================
FCP - FIRST CONTENTFUL PAINT
══════════════════════════════════════════════════════════════════

DEFINITION
──────────
FCP measures the time from when the page starts loading to when any
part of the page's content is rendered on the screen (first text, image,
SVG, or non-white canvas).

"When does the user see that something is happening?"

THRESHOLDS:
  ✅ Good:              ≤ 1.8 seconds
  ⚠️  Needs Improvement: 1.8 – 3.0 seconds
  ❌ Poor:              > 3.0 seconds

FCP vs LCP:
  - FCP: First ANY content renders (could be a loading spinner or tiny text)
  - LCP: The LARGEST content element renders (the main content)
  - FCP ≤ LCP always (LCP happens after or at same time as FCP)
  - FCP signals "it's loading"; LCP signals "the content is ready"

================================================================
HOW FCP IS CALCULATED
================================================================

WHAT COUNTS AS FCP CONTENT:
  ✅ Text (any text rendered to screen)
  ✅ Images (including background images)
  ✅ SVG elements
  ✅ Non-white canvas elements

WHAT DOES NOT COUNT:
  ❌ White/blank page
  ❌ Loading spinners that are CSS-only (considered non-contentful by Chrome? Actually spinners DO count)
  
Note: A pure white background showing is NOT an FCP event.
The first actual content pixel triggers FCP.

MEASURING FCP:
──────────────
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'first-contentful-paint') {
      console.log('FCP:', entry.startTime, 'ms');
    }
  }
});
observer.observe({ entryTypes: ['paint'] });

// Web Vitals library
import { onFCP } from 'web-vitals';
onFCP(({ value, rating }) => console.log(`FCP: ${value}ms (${rating})`));

================================================================
CAUSES OF SLOW FCP
================================================================

1. Slow TTFB (FCP can't happen until HTML arrives)
2. Render-blocking CSS (browser won't render until CSS is parsed)
3. Render-blocking JavaScript (parser-blocking scripts)
4. Large initial HTML (lots of non-critical HTML delaying parse)
5. Slow font loading (with font-display: block, text invisible until font loads)
6. Server-side rendering not used (SPA waiting for JS → blank white screen)

================================================================
HOW TO OPTIMIZE FCP
================================================================

1. FIX TTFB FIRST
──────────────────
FCP depends entirely on TTFB. See TTFB section above.

2. ELIMINATE RENDER-BLOCKING RESOURCES
────────────────────────────────────────
  <!-- ❌ Render-blocking CSS -->
  <link rel="stylesheet" href="styles.css">
  
  <!-- ✅ Inline critical CSS -->
  <style>
    /* Critical above-the-fold CSS inlined here */
    body { margin: 0; font-family: sans-serif; }
    .hero { background: #000; color: #fff; }
  </style>
  
  <!-- ✅ Non-critical CSS loaded asynchronously -->
  <link rel="preload" href="non-critical.css" as="style"
        onload="this.onload=null; this.rel='stylesheet'">
  <noscript>
    <link rel="stylesheet" href="non-critical.css">
  </noscript>
  
  <!-- ❌ Render-blocking script -->
  <script src="app.js"></script>
  
  <!-- ✅ Deferred scripts -->
  <script src="app.js" defer></script>
  <!-- defer: downloads in parallel, executes after HTML parsing -->
  
  <!-- ✅ Async scripts (for truly independent scripts) -->
  <script src="analytics.js" async></script>
  <!-- async: downloads in parallel, executes immediately when ready -->

3. USE SERVER-SIDE RENDERING
──────────────────────────────
  Without SSR (SPA):
  1. Browser downloads HTML (mostly empty <div id="root">)
  2. Browser downloads JS bundle (large, blocking)
  3. JS executes (React bootstraps)
  4. React renders content → FCP happens
  → FCP could be 3-5s
  
  With SSR:
  1. Server renders full HTML with content
  2. Browser downloads HTML
  3. FCP happens immediately (content is in HTML)
  4. JS downloads and hydrates in background
  → FCP could be < 1s

4. FONT LOADING STRATEGY
──────────────────────────
  /* font-display: swap → shows fallback immediately, then swaps */
  @font-face {
    font-family: 'Inter';
    src: url('/fonts/inter.woff2') format('woff2');
    font-display: swap; /* FCP not blocked by font loading */
  }
  
  /* Preload fonts for faster swap */
  <link rel="preload" href="/fonts/inter.woff2" as="font"
        type="font/woff2" crossorigin="anonymous">

5. MINIMIZE INITIAL HTML SIZE
───────────────────────────────
  - Don't include large data sets in initial HTML (use JSON API)
  - Avoid deeply nested components that add HTML weight
  - Use streaming SSR to start FCP before full page renders

================================================================
RELATIONSHIP BETWEEN TTFB, FCP, AND LCP
================================================================

Typical page load timeline:
  
  0ms        TTFB starts (user navigates)
  200ms      DNS + TCP + TLS + Network overhead
  800ms      ← TTFB (server response) — target < 800ms
  900ms      ← Start of HTML parsing
  1200ms     Critical CSS parsed
  1500ms     ← FCP: First text/image renders — target < 1800ms
  2000ms     Hero image loaded and rendered
  2000ms     ← LCP: Hero image is largest element — target < 2500ms
  
  If TTFB is 2000ms:
  2000ms     TTFB
  2800ms     FCP (best case with fast everything else)
  3500ms     LCP (best case)
  → Both FCP and LCP automatically fail their thresholds!

KEY INSIGHT:
  Fix TTFB first → it unlocks improvements to FCP and LCP simultaneously.
  TTFB improvements have a multiplier effect on all subsequent metrics.

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is TTFB and why is it important?
A: TTFB (Time to First Byte) measures the time from navigation start to when
   the browser receives the first byte of the server response. It's important
   because it's the baseline for all other metrics — LCP and FCP can never
   be faster than TTFB. Target: < 800ms. It's affected by server processing
   time, database queries, CDN usage, and connection setup.

Q: How do you optimize TTFB?
A: (1) Use a CDN to serve from edge nodes close to users; (2) Cache HTML
   responses (CDN edge caching, Redis for dynamic content); (3) Optimize
   database queries (indexes, N+1 fix, connection pooling); (4) Use streaming
   SSR (React 18's renderToPipeableStream) to start streaming HTML before
   full render completes; (5) Use edge computing (Cloudflare Workers,
   Vercel Edge) for near-zero cold starts at the network edge; (6) Enable
   HTTP/2 or HTTP/3 for multiplexing and reduced connection overhead.

Q: What is FCP and how does it differ from LCP?
A: FCP (First Contentful Paint) is when ANY content first appears on screen
   (text, image, SVG). LCP is when the LARGEST content element renders.
   FCP signals "something is loading"; LCP signals "the main content is ready".
   FCP ≤ LCP always. A loading spinner could cause a good FCP but terrible LCP.
   Target FCP: ≤ 1.8s. Target LCP: ≤ 2.5s.

Q: A page has FCP of 4s but TTFB is only 600ms. What would you look at?
A: With fast TTFB, the delay is happening in the browser. I'd check for:
   (1) Render-blocking CSS — CSS must fully download and parse before FCP;
   (2) Render-blocking JS — synchronous scripts block HTML parsing;
   (3) SPA without SSR — blank HTML with only <div id="root"> means
   FCP waits for JS to download, parse, execute, and render;
   (4) Font loading with font-display: block — text is invisible until font loads.
   I'd run Lighthouse to see exactly which resources are render-blocking.

Q: How does SSR improve FCP?
A: In a client-side-only SPA, the HTML is mostly empty. The browser must
   download the JS bundle, parse it, execute it, and wait for React to render
   before FCP can happen — easily 3-5 seconds. With SSR, the server sends
   fully rendered HTML. The browser can paint that HTML immediately, achieving
   FCP in < 1.8s, while the JS hydration happens in the background. This is
   why Next.js, Remix, and other SSR frameworks dramatically improve FCP/LCP.
