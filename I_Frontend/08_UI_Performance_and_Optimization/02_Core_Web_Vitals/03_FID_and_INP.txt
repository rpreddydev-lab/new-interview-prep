================================================================
FID AND INP - INTERACTIVITY METRICS
================================================================

HISTORY: FID → INP
───────────────────
FID (First Input Delay) was the original Core Web Vital for interactivity.
It measured the delay between a user's FIRST interaction and when the browser
actually started processing it.

In March 2024, INP (Interaction to Next Paint) replaced FID.

WHY FID WAS INSUFFICIENT:
  - Only measured the INPUT DELAY of the FIRST interaction
  - Ignored how long the interaction handler actually took
  - Ignored ALL interactions after the first one
  - Could have a great FID score but terrible interactivity overall
  - Example: First click responds fast (good FID), but every click after
    takes 2 seconds to respond (INP would catch this)

================================================================
INP - INTERACTION TO NEXT PAINT
================================================================

DEFINITION
──────────
INP measures the latency of ALL user interactions (clicks, taps, keypresses)
throughout the entire page lifetime, and reports the WORST-CASE interaction.

More precisely: INP measures the time from when the user starts an interaction
to when the NEXT FRAME is painted to the screen after processing.

THRESHOLDS:
  ✅ Good:              ≤ 200ms
  ⚠️  Needs Improvement: 200ms – 500ms
  ❌ Poor:              > 500ms
  
  Measured at: 75th percentile of all page visits

WHY "NEXT PAINT"?
  - The complete interaction cycle is: input → process → VISUAL FEEDBACK
  - A click that runs JS in 10ms but takes 500ms to show a new state
    would show good FID but terrible INP
  - INP captures the full user-visible latency including render time

================================================================
HOW INP IS CALCULATED
================================================================

For each interaction, INP captures:
  
  ┌──────────────────────────────────────────────────────────┐
  │ [User Input] → [Input Delay] → [Processing Time] → [Presentation Delay] │
  │                                                          │
  │ Input Delay: Time from input to first event handler call │
  │   (main thread was busy doing other work)               │
  │                                                          │
  │ Processing Time: Time event handlers took to run         │
  │   (your JavaScript code)                                 │
  │                                                          │
  │ Presentation Delay: Time for browser to render next frame│
  │   (layout, paint, composite)                            │
  │                                                          │
  │ Total INP = Input Delay + Processing Time + Presentation │
  └──────────────────────────────────────────────────────────┘

  Total interaction duration = Input Delay + Processing Time + Presentation Delay

INP SELECTION:
  - Tracks ALL interactions during page visit
  - Reports the highest interaction duration (worst case)
  - With many interactions (> 50), ignores top 1% as outliers
  - INP = the representative worst interaction

================================================================
WHAT COUNTS AS AN INTERACTION?
================================================================

INP measures these interaction types:
  ✅ Mouse clicks
  ✅ Tap/touch on mobile
  ✅ Keyboard presses (keydown, keyup)

NOT counted by INP:
  ❌ Hover events (mouseover, mouseenter)
  ❌ Scroll events (tracked by other metrics)
  ❌ Resize/zoom
  ❌ Pointer events that don't have a visual response

================================================================
ROOT CAUSES OF POOR INP
================================================================

1. LONG INPUT DELAY
────────────────────
Problem: Main thread is busy when user clicks
Causes:
  - Long tasks blocking the main thread (JS > 50ms continuously)
  - Too much JS executing at load time (vendor scripts, analytics)
  - setInterval / setTimeout callbacks blocking the thread
  - React hydration blocking the main thread

Fix:
  - Break up long tasks using scheduler.yield() or setTimeout(fn, 0)
  - Use Web Workers for heavy computation
  - Reduce JavaScript at load time (code splitting)
  - Use requestAnimationFrame for visual updates

2. LONG PROCESSING TIME
─────────────────────────
Problem: Event handler code itself is too slow
Causes:
  - Heavy DOM manipulation in click handlers
  - Synchronous data processing (large arrays, sorting)
  - Synchronous XHR (always avoid!)
  - Multiple setState calls in React (each triggers re-render)
  - Expensive React re-renders from a single event

Fix:
  - Optimize event handler code
  - Batch state updates
  - Memoize expensive calculations
  - Use React useTransition() for non-urgent updates
  - Move heavy work to Web Workers

3. LONG PRESENTATION DELAY
────────────────────────────
Problem: Frame takes long to render after handler completes
Causes:
  - Large DOM trees (> 1500 nodes)
  - Complex CSS selectors causing expensive style recalculation
  - Layout thrashing (read/write DOM interleaving)
  - Many elements being painted simultaneously
  - Not using CSS containment

Fix:
  - Reduce DOM size
  - Use CSS containment (contain: layout style)
  - Avoid layout thrashing (batch reads, then writes)
  - Virtualize long lists (react-virtual, react-window)
  - Use CSS transforms instead of layout-triggering properties

1. YIELDING TO THE MAIN THREAD
────────────────────────────────
// Break up long tasks to reduce input delay
async function processLargeDataset(data) {
  const CHUNK_SIZE = 100;
  const results = [];
  
  for (let i = 0; i < data.length; i += CHUNK_SIZE) {
    const chunk = data.slice(i, i + CHUNK_SIZE);
    results.push(...processChunk(chunk));
    
    // Yield to browser between chunks
    // This allows pending input events to be processed
    await new Promise(resolve => setTimeout(resolve, 0));
    
    // OR use scheduler.yield() if available (Chrome 124+)
    // if ('scheduler' in window && 'yield' in scheduler) {
    //   await scheduler.yield();
    // }
  }
  
  return results;
}

2. REACT useTransition FOR NON-URGENT UPDATES
──────────────────────────────────────────────
import { useState, useTransition } from 'react';

function SearchComponent() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();
  
  function handleChange(e) {
    const value = e.target.value;
    // Urgent: update input immediately
    setQuery(value);
    
    // Non-urgent: defer filtering results
    // Browser can interrupt this to handle other inputs
    startTransition(() => {
      setResults(filterLargeList(value));
    });
  }
  
  return (
    <>
      <input value={query} onChange={handleChange} />
      {isPending && <span>Loading...</span>}
      <ResultsList results={results} />
    </>
  );
}

3. REACT useDeferredValue
──────────────────────────
import { useDeferredValue, memo } from 'react';

function App() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query); // lags behind query
  
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {/* Uses deferred (stale) query, won't block typing */}
      <ExpensiveList query={deferredQuery} />
    </>
  );
}

const ExpensiveList = memo(({ query }) => {
  // This re-renders with a delay, so typing stays fast
  const items = filterMassiveList(query);
  return <ul>{items.map(item => <li key={item.id}>{item.name}</li>)}</ul>;
});

4. DEBOUNCING EXPENSIVE WORK
──────────────────────────────
function useDebounce(value, delay) {
  const [debouncedValue, setDebouncedValue] = useState(value);
  
  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  
  return debouncedValue;
}

// In component:
const debouncedSearch = useDebounce(query, 300);
// Only run expensive search after user stops typing for 300ms

// main.js
const worker = new Worker('worker.js');

6. VIRTUAL SCROLLING FOR LARGE LISTS
───────────────────────────────────────
// Without virtualization: 10,000 DOM nodes
// With virtualization: only ~10-20 visible nodes

import { useVirtualizer } from '@tanstack/react-virtual';

function VirtualList({ items }) {
  const parentRef = useRef(null);
  
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 35, // estimated row height
  });
  
  return (
    <div ref={parentRef} style={{ height: '400px', overflow: 'auto' }}>
      <div style={{ height: `${virtualizer.getTotalSize()}px`, position: 'relative' }}>
        {virtualizer.getVirtualItems().map(virtualItem => (
          <div
            key={virtualItem.key}
            style={{
              position: 'absolute',
              top: 0,
              left: 0,
              width: '100%',
              height: `${virtualItem.size}px`,
              transform: `translateY(${virtualItem.start}px)`,
            }}
          >
            {items[virtualItem.index].name}
          </div>
        ))}
      </div>
    </div>
  );
}

================================================================
FID - FIRST INPUT DELAY (Legacy - retired March 2024)
================================================================

DEFINITION:
  Time between when the user first interacts with the page and when the
  browser is actually able to begin processing event handlers in response.

THRESHOLDS (historical):
  ✅ Good:    ≤ 100ms
  ⚠️ Needs:   100ms – 300ms
  ❌ Poor:    > 300ms

WHY IT WAS REPLACED:
  - Only measured input delay (not handler time)
  - Only measured FIRST interaction (ignored all subsequent)
  - FID didn't require a visual response in the metric
  - Sites could game FID by having a trivial first click

DIFFERENCE SUMMARY:
  FID = delay before first interaction handler fires
  INP = total latency (input delay + processing + render) of worst interaction

MEASURING INP

// Using PerformanceObserver (Event Timing API)
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.interactionId) {
      console.log({
        type: entry.name,
        duration: entry.duration,         // total INP
        inputDelay: entry.processingStart - entry.startTime,
        processingTime: entry.processingEnd - entry.processingStart,
        presentationDelay: entry.startTime + entry.duration - entry.processingEnd,
      });
    }
  }
});
observer.observe({ type: 'event', buffered: true, durationThreshold: 16 });

// Using web-vitals library (recommended)
import { onINP } from 'web-vitals/attribution';

onINP(({ name, value, attribution }) => {
  console.log({
    inp: value,
    element: attribution.interactionTarget, // Which element
    eventType: attribution.interactionType, // 'click', 'keydown', etc.
    inputDelay: attribution.inputDelay,
    processingDuration: attribution.processingDuration,
    presentationDelay: attribution.presentationDelay,
  });
});

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is INP and how does it differ from FID?
A: INP (Interaction to Next Paint) measures the latency of ALL user
   interactions throughout the page lifetime, reporting the worst case.
   FID only measured the INPUT DELAY of the FIRST interaction. INP is
   stricter: it measures the complete cycle from input → event handler
   execution → next frame painted. INP replaced FID in March 2024
   because FID was too easy to satisfy and missed real interactivity issues.

Q: What are the three components of an INP interaction?
A: (1) Input Delay — time from user input to first event handler call
   (main thread was busy); (2) Processing Time — time for event handlers
   to execute (your JS code); (3) Presentation Delay — time for the browser
   to render the next frame after handlers complete (layout/paint/composite).
   Total INP = sum of all three.

Q: A page has good FID but poor INP. What might be causing this?
A: FID only measures the first interaction's input delay. Poor INP suggests
   that subsequent interactions are slow. Possible causes: (1) heavy event
   handlers causing long processing time; (2) main thread blocking from
   ongoing JS execution (setInterval, animations); (3) large DOM causing
   long presentation delay; (4) React re-renders triggered by interactions.

Q: How do you use React's concurrent features to improve INP?
A: I use useTransition() to mark non-urgent state updates that can be
   interrupted by more urgent user input. For example, when filtering a
   large list on a search input, I keep the input update urgent but wrap
   the list filtering in startTransition(). This keeps the input responsive
   while deferring the expensive re-render. I also use useDeferredValue()
   to keep using the previous value of an expensive computation while
   the new one is being calculated.

Q: What is scheduler.yield() and when would you use it?
A: scheduler.yield() is a new browser API that yields control back to the
   browser, allowing it to process pending user input events. Unlike
   setTimeout(fn, 0), it yields at a high priority and resumes the task
   quickly. I'd use it inside long-running loops or data processing to
   prevent blocking the main thread, improving input delay for INP.
