================================================================
RESOURCE HINTS: PRELOAD, PREFETCH, PRECONNECT
================================================================

THE PROBLEM: RESOURCE DISCOVERY IS LATE
──────────────────────────────────────────
The browser can only discover resources after parsing HTML and CSS.
Without hints, the waterfall looks like:

  Time 0ms:    Start loading HTML
  Time 200ms:  HTML received, parser starts
  Time 250ms:  Discover CSS file → start loading CSS
  Time 400ms:  CSS parsed → discover font in @font-face → start font load
  Time 700ms:  Font loaded → text renders

Resource hints let you inform the browser of upcoming needs EARLY:
  Time 0ms:    Start loading HTML → <link rel="preload" as="font"> discovered
  Time 200ms:  HTML received → font ALREADY loading, CSS ALREADY loading
  Time 350ms:  Font loaded + CSS parsed → text renders immediately

================================================================
RESOURCE HINT REFERENCE TABLE
================================================================

HINT              | PRIORITY | PURPOSE                      | DOWNLOADS FILE?
──────────────────┼──────────┼──────────────────────────────┼────────────────
preload           | HIGH     | Critical for current page    | YES (immediately)
prefetch          | LOWEST   | Nice-to-have for next page   | YES (idle time)
preconnect        | MEDIUM   | Open connection, no download | NO  (DNS+TCP+TLS)
dns-prefetch      | LOW      | Just DNS lookup              | NO  (DNS only)
modulepreload     | HIGH     | Preload ES module + parse    | YES (parse too!)

================================================================
rel="preload" — CURRENT PAGE CRITICAL RESOURCES
================================================================

Force HIGH-PRIORITY early download for resources needed on this page:

  <!-- Font preload (see Font Optimization notes for why crossorigin is needed) -->
  <link rel="preload" href="/fonts/inter-regular.woff2" as="font"
        type="font/woff2" crossorigin="anonymous" />
  
  <!-- LCP hero image -->
  <link rel="preload" href="/hero.webp" as="image" />
  
  <!-- Critical CSS (inlined styles for above-fold) -->
  <link rel="preload" href="/critical.css" as="style" />
  
  <!-- Preload a script that's needed early but not parser-blocking -->
  <link rel="preload" href="/app.js" as="script" />
  
  <!-- Responsive image preload (matches srcset!) -->
  <link rel="preload" as="image"
        imagesrcset="hero-400.webp 400w, hero-800.webp 800w"
        imagesizes="(max-width: 600px) 100vw, 800px" />

COMMON preload "as" values:
  as="font"     → fonts
  as="image"    → images (including SVG)
  as="style"    → CSS files
  as="script"   → JavaScript files
  as="fetch"    → fetch()/XHR requests
  as="audio"    → audio files
  as="video"    → video files
  as="worker"   → Web Worker scripts

⚠️ WARNING — Unused preload triggers browser warning:
  If you preload a resource but don't use it within 3 seconds,
  DevTools shows: "The resource was preloaded using link preload
  but not used within a few seconds from the window's load event."
  Only preload what you KNOW will be used!

⚠️ DON'T preload things the browser already prioritizes:
  - <script> in <head> is already high priority
  - Images in the viewport with fetchpriority="high" are already prioritized
  - Double-requesting just wastes bandwidth

================================================================
rel="prefetch" — NEXT PAGE RESOURCES
================================================================

Low-priority download of resources needed for FUTURE navigation.
Browser waits for idle time, doesn't delay current page.

  <!-- JavaScript bundle for /dashboard (user likely to navigate there) -->
  <link rel="prefetch" href="/dashboard-bundle.js" as="script" />
  
  <!-- Prefetch next article image when user is reading current article -->
  <link rel="prefetch" href="/article-2-hero.jpg" as="image" />
  
  <!-- Dynamic prefetch based on hover: -->
  function prefetchOnHover(href) {
    return {
      onMouseEnter: () => {
        const link = document.createElement('link');
        link.rel = 'prefetch';
        link.href = href;
        document.head.appendChild(link);
      }
    };
  }
  
  // React Router prefetch (v6.4+ loader prefetching):
  <Link to="/dashboard" prefetch="intent">Dashboard</Link>
  // "intent": prefetch on hover/focus (when user shows intent)
  // "render": prefetch when link renders
  // "none": no prefetch
  
  // Next.js: <Link> prefetches by default on hover (in production)
  <Link href="/dashboard">Dashboard</Link>
  
  // Disable Next.js prefetch:
  <Link href="/large-page" prefetch={false}>Big Page</Link>

WHEN TO PREFETCH:
  ✅ Next step in a user flow (checkout → payment)
  ✅ Most commonly clicked links (home → product)
  ✅ After a list: clicking the first item loads the detail page
  ❌ Don't prefetch everything — wastes bandwidth
  ❌ Don't prefetch on metered connections (data plans)

================================================================
rel="preconnect" — EARLY CONNECTION SETUP
================================================================

Tells browser to open a connection (DNS + TCP + TLS handshake)
WITHOUT downloading anything. Saves ~100-300ms per third-party origin.

  <!-- Google Fonts: 2 origins needed -->
  <link rel="preconnect" href="https://fonts.googleapis.com" />
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
  
  <!-- Analytics, CDN, API server -->
  <link rel="preconnect" href="https://analytics.example.com" />
  <link rel="preconnect" href="https://api.myapp.com" />
  <link rel="preconnect" href="https://cdn.example.com" />

WHEN TO USE crossorigin ON preconnect:
  - Required for CORS resources: fonts, fetch/XHR, cross-origin scripts
  - NOT needed for: images, same-origin resources
  
PRECONNECT LIMIT: Browsers limit to ~6 active preconnects.
Only preconnect to origins used in the first few seconds.

================================================================
rel="dns-prefetch" — LIGHTER VERSION OF PRECONNECT
================================================================

Only performs DNS lookup (NOT TCP/TLS). Cheaper — good for origins
that might be used but aren't guaranteed.

  <!-- Use dns-prefetch for less certain third-party origins -->
  <link rel="dns-prefetch" href="//analytics.example.com" />
  <link rel="dns-prefetch" href="//cdn.example.com" />
  
  <!-- COMMON PATTERN: dns-prefetch as fallback for browsers that
       don't support preconnect, combined together: -->
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
  <link rel="dns-prefetch" href="//fonts.gstatic.com" />

================================================================
rel="modulepreload" — ES MODULE PRELOADING
================================================================

Like preload for scripts, but also PARSES and COMPILES the ES module,
saving even more time when the module is actually executed.

  <!-- Preload AND parse the JS module -->
  <link rel="modulepreload" href="/src/app.js" />
  
  // Vite automatically injects modulepreload for chunk dependencies!
  // No manual configuration needed with Vite.
  
  // webpack: use webpack-subresource-integrity + modulepreload plugin
  // Or manually add in HTML template

================================================================
fetchpriority ATTRIBUTE — PRIORITY HINTS
================================================================

Fine-tune browser's built-in priority for individual resources:

  <!-- Boost LCP image priority (browser underestimates critical images) -->
  <img src="hero.jpg" fetchpriority="high" loading="eager" alt="Hero" />
  
  <!-- Deprioritize below-fold images -->
  <img src="footer-logo.jpg" fetchpriority="low" loading="lazy" alt="..." />
  
  <!-- Fetch API: deprioritize analytics calls -->
  fetch('/analytics', { priority: 'low' });
  
  <!-- Script: boost priority of a critical JS file -->
  <script src="/critical.js" fetchpriority="high"></script>
  
  <!-- Deprioritize a CSS file used only for print -->
  <link rel="stylesheet" href="/print.css" fetchpriority="low" media="print" />

VALUES: "high" | "low" | "auto" (default)
SUPPORT: Chrome 101+, Safari 17.2+

================================================================
103 EARLY HINTS — SERVER-SIDE RESOURCE HINTS
================================================================

HTTP 103 Early Hints lets the SERVER send resource hints BEFORE the
full HTML response is ready (during server processing time).

  Browser →→→→→→→→→→→→→→→→ Server
                              ↓ (Server processing: DB queries, templates, etc.)
  Browser ←← 103 Early Hints (preconnect/preload hints arrive EARLY)
  Browser starts connecting/preloading...
                              ↓ (Server finishes generating HTML)
  Browser ←← 200 with full HTML

  Example HTTP response sequence:
  HTTP/1.1 103 Early Hints
  Link: <https://fonts.googleapis.com>; rel=preconnect
  Link: </fonts/inter.woff2>; rel=preload; as=font; crossorigin
  
  HTTP/1.1 200 OK
  Content-Type: text/html
  [full HTML]
  
  // Next.js automatic 103 Early Hints in App Router!
  // Vercel Edge and AWS CloudFront support sending 103
  
  // Express manual 103:
  app.get('/', (req, res) => {
    res.writeEarlyHints({
      link: [
        '<https://fonts.gstatic.com>; rel=preconnect; crossorigin',
        '</hero.webp>; rel=preload; as=image',
      ]
    });
    // ... generate actual response ...
    res.send(html);
  });

================================================================
SPECULATION RULES API — PREDICTIVE PREFETCHING
================================================================

Modern Chrome API for speculative prefetching and prerendering:

  <!-- Prefetch: download HTML/assets for likely next page -->
  <script type="speculationrules">
  {
    "prefetch": [
      {
        "urls": ["/product/1", "/product/2"],
        "eagerness": "moderate"
      }
    ]
  }
  </script>
  
  <!-- Prerender: full render in background tab! -->
  <script type="speculationrules">
  {
    "prerender": [
      {
        "where": { "selector_matches": ".product-link" },
        "eagerness": "moderate"
      }
    ]
  }
  </script>
  
  EAGERNESS values:
    "conservative" — only on pointer down (click started)
    "moderate"     — on hover (300ms delay)
    "eager"        — on hover (no delay)
    "immediate"    — on page load (prefetch right away)
  
  RESULT: Navigation to prerendered page is INSTANT (< 50ms)!
  Chrome's INP score counts soft navigations, so this dramatically
  improves navigation responsiveness.

PUTTING IT ALL TOGETHER — OPTIMIZED <head>
================================================================

  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    
    <!-- 1. PRECONNECT to required third-party origins -->
    <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
    <link rel="dns-prefetch" href="//analytics.example.com" />
    
    <!-- 2. PRELOAD critical current-page resources -->
    <link rel="preload" href="/fonts/inter-variable.woff2"
          as="font" type="font/woff2" crossorigin="anonymous" />
    <link rel="preload" href="/hero.webp" as="image" fetchpriority="high" />
    
    <!-- 3. Critical CSS (inlined to avoid render-blocking) -->
    <style>/* Critical above-fold CSS here */</style>
    
    <!-- 4. Non-critical CSS (deferred) -->
    <link rel="stylesheet" href="/styles.css" media="print"
          onload="this.media='all'" />
    
    <!-- 5. PREFETCH likely next page resources -->
    <link rel="prefetch" href="/dashboard-bundle.js" as="script" />
    
    <title>My App</title>
  </head>

================================================================
INTERVIEW ANSWERS
================================================================

Q: What's the difference between preload and prefetch?
A: Both instruct the browser to download a resource ahead of time, but
   with very different priorities and use cases. Preload is for resources
   NEEDED on the CURRENT page — it downloads at HIGH priority, immediately,
   before the browser would normally discover the resource. Use for LCP images,
   fonts, critical scripts. Prefetch is for resources needed on a FUTURE page
   — downloaded at LOWEST priority during idle time, after the current page
   has loaded. Missing the distinction causes problems: accidentally using
   preload for next-page resources wastes bandwidth and competes with current
   page resources. Using prefetch for current-page resources means they load
   too late (low priority queue).

Q: When should you use preconnect vs dns-prefetch?
A: Use preconnect when you're CERTAIN you'll use a third-party origin on the
   current page — it opens the full connection (DNS + TCP + TLS) saving
   100-300ms. Use dns-prefetch for origins you MIGHT use or use on future pages
   — it only resolves DNS (~20-100ms saved) and is lighter on browser resources.
   Best practice: pair both together for browser compatibility (preconnect for
   modern browsers, dns-prefetch as fallback). Limit preconnect to ~6 origins
   — browsers cap simultaneous preconnects. Critical for: Google Fonts, analytics,
   CDN origins, your API server if it's on a different domain.

Q: What are 103 Early Hints and why are they powerful?
A: 103 Early Hints is an HTTP status code that lets the server send resource
   hints (preload/preconnect) to the browser DURING the server's processing time
   — before the actual 200 response with HTML is ready. On slow servers (100-500ms
   TTFB due to DB queries), the browser can start downloading fonts, images, and
   CSS WHILE the server is still generating the page. This effectively eliminates
   the server processing time from the critical resource loading path. Next.js on
   Vercel sends 103 Early Hints automatically. The key advantage over HTML
   <link rel="preload"> is timing: hints arrive 100-500ms earlier, which is
   huge for resources on the critical rendering path like fonts and LCP images.

Q: How does the Speculation Rules API differ from prefetch?
A: Traditional <link rel="prefetch"> downloads the HTML for the next page but
   doesn't render it. The Speculation Rules API can PRERENDER — it creates an
   invisible hidden tab, loads the HTML, runs all JavaScript, and fully renders
   the page in the background. When the user clicks the link, the prerendered
   page is swapped in instantly (effectively 0ms navigation). This requires
   careful configuration: avoid prerendering pages with side effects (form
   submissions, analytics events on load) since they'd fire in the background.
   The "eagerness" setting controls when speculation begins — "conservative" waits
   for pointer-down (very low false-positive rate), "moderate" triggers on hover.
