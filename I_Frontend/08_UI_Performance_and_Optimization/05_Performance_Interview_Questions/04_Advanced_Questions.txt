ARCHITECTURE AND TRADE-OFFS
================================================================

Q1: How do you make performance decisions when there are trade-offs?
─────────────────────────────────────────────────────────────────────
A: I use a structured framework:
   
   1. MEASURE FIRST: Validate the problem exists with data.
      "We think LCP is slow" → check field data (CrUX/RUM).
      Don't optimize based on intuition.
   
   2. PRIORITIZE BY USER IMPACT: Which users are affected? What's the
      business impact? (Revenue? Churn? SEO ranking?)
      E.g., mobile users on 3G have 4s LCP → 40% of traffic → high priority.
   
   3. IDENTIFY TRADE-OFFS:
      - SSR vs CSR: SSR improves FCP but adds server complexity + cost
      - Code splitting vs bundle count: More chunks = more requests overhead
      - Memoization vs code complexity: React.memo adds cognitive overhead
      - Pre-rendering vs staleness: Prerendered content may be stale
   
   4. EVALUATE SOLUTIONS: For each solution, estimate:
      - Performance gain (quantified)
      - Implementation cost (engineering days)
      - Maintenance burden
      - Risk of regression
   
   5. DECIDE AND DOCUMENT: Implement, measure, document why.
      "We chose SSG over SSR because our product catalog changes at most
       hourly, and SSG gives us CDN-edge serving with no server cost."

Q2: How would you design the frontend performance strategy for a large e-commerce platform?
────────────────────────────────────────────────────────────────────────────────────────────
A: I'd approach this in layers:
   
   LAYER 1: INFRASTRUCTURE
   - Global CDN for all static assets and HTML caching
   - Edge computing for personalization (product recommendations at edge)
   - ISR (Incremental Static Regeneration) for product pages:
     → Cache at CDN, revalidate every 60s or on-demand on price change
   - Image CDN (Cloudinary/Imgix) for automatic WebP/AVIF conversion + sizing
   
   LAYER 2: LOADING STRATEGY
   - Route-based code splitting (Next.js App Router automatic splitting)
   - Critical CSS inlined for above-fold (product image, title, CTA)
   - Hero/LCP image: preloaded + fetchpriority="high" + WebP/AVIF + CDN
   - Below-fold sections lazy: reviews, related products, size guide
   - Third-party scripts (chat, reviews widget) deferred to after interaction
   
   LAYER 3: RENDERING
   - Server Components for static content (no JS shipped for product details)
   - Client Components only for interactive parts (Add to Cart button, qty)
   - Streaming: Shell renders first, product details stream in
   - Optimistic UI for cart updates (immediate feedback, sync in background)
   
   LAYER 4: RUNTIME PERFORMANCE
   - Virtualized list for search results (> 50 items)
   - Debounced search input (300ms, cancel previous request)
   - React Query / SWR for data fetching with stale-while-revalidate
   - useTransition for search results filtering
   
   LAYER 5: MONITORING
   - Lighthouse CI on every PR (fail if LCP > 2.5s or CLS > 0.1)
   - RUM with web-vitals library, segment by mobile/desktop + connection
   - Alerting if P75 LCP degrades by > 500ms on any page group
   - Weekly performance review in team standup

Q3: Compare micro-frontend architectures from a performance perspective.
─────────────────────────────────────────────────────────────────────────
A: 
   MODULE FEDERATION (Webpack 5):
   Performance: Medium — each remote adds remoteEntry.js network request.
   JavaScript negotiation overhead for shared deps.
   Benefit: Independent deployment, dynamic loading.
   Problem: Shared React singleton requirement, complex debugging.
   
   IFRAME MICRO-FRONTENDS:
   Performance: Worst — each iframe is a full browser context.
   Completely isolated (separate JS heap, layout, paint).
   Benefit: Perfect isolation, any framework.
   Problem: Communication overhead, layout constraints, not SEO-friendly.
   
   WEB COMPONENTS:
   Performance: Good — native browser feature, no framework overhead.
   Elements compose naturally, lazy loadable.
   Problem: Inconsistent SSR support, Shadow DOM complicates styling.
   
   BUILD-TIME COMPOSITION (npm packages):
   Performance: Best — single optimized bundle, full tree shaking.
   No runtime discovery overhead.
   Problem: Coupled deployment (must rebuild host when any micro-frontend changes).
   
   RECOMMENDATION: For most teams, npm packages with a monorepo (Turborepo/Nx)
   gives the best performance with manageable complexity. Module Federation
   is only worth it when teams truly need independent, runtime deployment.

Q4: How does React Server Components (RSC) change the performance model?
─────────────────────────────────────────────────────────────────────────
A: RSC is a paradigm shift: some components render ONLY on the server
   and NEVER ship JavaScript to the client.
   
   TRADITIONAL (all components → JS bundle):
   Server: HTML with shell
   Client: Downloads React + all component JS
   Client: Hydrates (attaches event listeners)
   
   WITH RSC (Next.js App Router):
   Server Components → rendered to HTML + RSC payload (not JS!)
   Client Components → rendered on server for HTML, hydrated client-side
   
   PERFORMANCE IMPACT:
   1. ZERO-COST DATA FETCHING: Server Components can fetch data directly
      (database, API) without a client-side fetch round-trip.
      Eliminates: client → API gateway → backend → client waterfall.
   
   2. SMALLER JS BUNDLE: Server Component code never goes to client.
      Heavy libraries used only in Server Components (e.g., markdown parser,
      date formatting libraries) are never bundled.
      App Router Next.js site can have 50-70% less client JS than Pages Router.
   
   3. COMPOSABLE LOADING: Suspense + Streaming with RSC means the shell
      renders first, then data-dependent sections stream in as ready.
      No loading spinner for the entire page.
   
   TRADE-OFFS:
   - No useState, useEffect, event handlers in Server Components
   - Mental model shift: "this renders server-only" vs "this runs in browser"
   - Debugging spans server and client
   - Difficult to use with non-Next.js setups

Q5: How do you handle performance in a single-page application with complex state?
────────────────────────────────────────────────────────────────────────────────────
A: COMMON ISSUES WITH COMPLEX STATE:
   - Global store triggers re-renders across unrelated components
   - Derived data computed on every render
   - Deeply nested component trees all re-rendering
   
   STRATEGIES:
   
   1. ATOMIC STATE MANAGEMENT (Jotai/Recoil):
   Each piece of state is an atom. Components subscribe only to atoms
   they read — unsubscribed components NEVER re-render.
   
   // Jotai: only components reading userAtom re-render on user change
   const userAtom = atom({ name: 'Alice' });
   const themeAtom = atom('dark');
   
   function UserBadge() {
     const user = useAtomValue(userAtom); // Only re-renders when userAtom changes
     return <span>{user.name}</span>;
   }
   
   2. SELECTOR-BASED (Zustand/Redux):
   const userName = useStore(state => state.user.name);
   // Re-renders only when state.user.name changes (selector comparison)
   
   3. DERIVED DATA WITH MEMOIZATION:
   // Instead of computing filtered items in every consumer component:
   const filteredItems = useMemo(
     () => items.filter(i => i.category === category),
     [items, category]
   );
   
   // Or use Reselect (Redux) / Jotai derived atoms for global derived state
   
   4. NORMALIZE STATE (flat structure):
   // Avoid deeply nested state (hard to update, triggers large re-renders)
   // Use normalized form: { usersById: {}, ordersByUserId: {} }
   // Redux Toolkit createEntityAdapter helps with this

Q6: "Our page has 3.0s INP on mobile. What would you investigate first?"
──────────────────────────────────────────────────────────────────────────
A: 3.0s INP is "poor" (threshold: ≤ 200ms). That means some interaction
   in the user's session takes 3 seconds to produce a visual update.
   
   INVESTIGATION STEPS:
   
   1. IDENTIFY THE INTERACTION: Use web-vitals with attribution:
      onINP(({ attribution }) => {
        console.log('Interaction type:', attribution.interactionType); // click/keydown
        console.log('Element:', attribution.interactionTarget.tagName);
        console.log('Input delay:', attribution.inputDelay); // Waiting for main thread
        console.log('Processing:', attribution.processingDuration); // Handler running
        console.log('Presentation:', attribution.presentationDelay);
      });
   
   2. IF INPUT DELAY IS HIGH (> 200ms):
      → Main thread busy when user clicked
      → Look for long tasks before the interaction
      → Common cause: timer callbacks, network response handlers, animations
      → Fix: Break up long tasks with scheduler.yield() or setTimeout(0)
   
   3. IF PROCESSING DURATION IS HIGH:
      → The click handler itself is slow
      → Open DevTools > Performance, record the interaction
      → Find what the handler calls: sorting? DOM manipulation? Layout?
      → Fix: Move heavy work to Web Worker, batch DOM reads/writes,
              use startTransition for non-critical UI updates
   
   4. IF PRESENTATION DELAY IS HIGH:
      → Browser is slow to paint after handler
      → Check: Large DOM (> 1500 nodes), complex CSS, forced sync layouts
      → Fix: Reduce DOM size, avoid layout-triggering properties,
              CSS contain: content for isolated sections

Q7: "Our team wants to migrate from CRA to Next.js for performance. How do you approach it?"
──────────────────────────────────────────────────────────────────────────────────────────────
A: MIGRATION APPROACH (incremental, low-risk):
   
   PHASE 1: ASSESSMENT (1 week)
   - Measure current CRA app performance (Lighthouse, RUM) — establish baseline
   - Audit: Dynamic imports usage, routing structure, environment variables
   - Identify: client-only code (window/document usage), third-party integrations
   
   PHASE 2: SETUP NEXT.JS (1 week)
   - Create Next.js project alongside CRA
   - Set up the same CI/CD pipeline
   - Configure environment variables (CRA REACT_APP_ → Next NEXT_PUBLIC_)
   
   PHASE 3: MIGRATE INCREMENTALLY (4-8 weeks)
   - Start with routes that benefit most from SSR/SSG (marketing pages)
   - Use getStaticProps for static data, getServerSideProps for dynamic
   - Convert App Router (if targeting Next.js 13+): layouts, server components
   - Fix client-only code: wrap in useEffect or dynamic with ssr: false
   
   PHASE 4: OPTIMIZATION (2 weeks)
   - Replace <img> with Next.js <Image> for LCP images
   - Replace <Script> with Next.js <Script strategy="afterInteractive">
   - Add font optimization: next/font
   - Enable ISR for product/content pages
   
   PHASE 5: VALIDATION (1 week)
   - Compare Lighthouse scores: new vs old
   - Check field data after 2 weeks in production
   - Fix any regressions
   
   EXPECTED IMPROVEMENTS:
   - LCP: 3.5s → 1.8s (SSR serves content in HTML)
   - TTFB: 600ms → 300ms (static pages served from CDN edge)
   - JS bundle: -30% (Next.js automatic code splitting + tree shaking)

Q8: "How would you build a high-performance infinite scroll feed?"
───────────────────────────────────────────────────────────────────
A: This is a complex problem with multiple performance dimensions:
   
   DATA FETCHING STRATEGY:
   - Cursor-based pagination (not offset): cursor = last seen item ID
   - Prefetch next page when user is 3 pages from the bottom
   - SWR or React Query: manages caching + deduplication
   - Abort in-flight requests when user scrolls quickly past threshold
   
   VIRTUALIZATION:
   - Must use windowing for 100+ items (DOM nodes are expensive)
   - react-virtuoso handles dynamic heights (posts have variable text)
   - Only ~20 DOM nodes rendered at any time regardless of loaded count
   
   MEMORY MANAGEMENT:
   - Cap total loaded items in memory (e.g., max 500 items)
   - When user scrolls far down and comes back up: refetch with cursor
   - "Virtual data set" — store all item IDs in memory, only render visible ones
   
   INTERACTION RESPONSIVENESS:
   - useTransition for filtering/sorting the feed
   - Optimistic UI for like/unlike actions (no waiting for server)
   - Scroll position restoration on back navigation (sessionStorage)
   
   LOADING STATES:
   - Skeleton screens matching post dimensions (prevents CLS)
   - Load 10 items initially, load more on scroll (no "load all 1000")
   - Debounce scroll event (50ms threshold for "near bottom" check)
   
   IMPLEMENTATION SKETCH:
   
   function Feed() {
     const parentRef = useRef(null);
     const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
       queryKey: ['feed'],
       queryFn: ({ pageParam = null }) => fetchFeedPage(pageParam),
       getNextPageParam: last => last.nextCursor,
     });
     
     const items = data?.pages.flatMap(p => p.items) ?? [];
     
     const virtualizer = useVirtualizer({
       count: hasNextPage ? items.length + 1 : items.length,
       getScrollElement: () => parentRef.current,
       estimateSize: () => 200,
       overscan: 5,  // Render 5 extra items outside viewport
     });
     
     useEffect(() => {
       const lastItem = virtualizer.getVirtualItems().at(-1);
       if (lastItem?.index >= items.length - 10 && hasNextPage) {
         fetchNextPage();
       }
     }, [virtualizer.getVirtualItems(), items.length, hasNextPage]);
     
     return (
       <div ref={parentRef} style={{ overflow: 'auto', height: '100vh' }}>
         <div style={{ height: virtualizer.getTotalSize() }}>
           {virtualizer.getVirtualItems().map(vItem => (
             <Post key={items[vItem.index]?.id} data={items[vItem.index]}
                   style={{ position: 'absolute', top: vItem.start }} />
           ))}
         </div>
       </div>
     );
   }

Q9: What is the "hydration" cost and how do you minimize it?
─────────────────────────────────────────────────────────────
A: WHAT IS HYDRATION:
   With SSR/SSG, server sends HTML. Browser renders it (FCP/LCP: fast!).
   Then React downloads JS bundle, executes it, and "hydrates" — attaches
   event listeners, recreates React fiber tree, makes the page interactive.
   
   HYDRATION COST:
   - JS bundle download: Network cost
   - JS parse/compile: CPU cost (worse on low-end mobile)
   - Reconciliation: React walks entire tree to match with server HTML
   - During hydration: Page appears interactive but ISN'T (TTI gap)
   - "Uncanny valley": Users see content but clicks don't register
   
   STRATEGIES TO MINIMIZE:
   
   1. PROGRESSIVE HYDRATION: Hydrate only visible/interactive parts first
      Below-fold sections hydrated lazily (IntersectionObserver)
      React 18 Suspense supports this natively
   
   2. PARTIAL HYDRATION (Islands Architecture — Astro):
      Most of the page is static HTML (no hydration)
      Only "islands" (interactive components) are hydrated
      Example: Static blog post, hydrate only comment form
   
   3. REACT SERVER COMPONENTS (zero hydration for server components):
      Server Components have zero client JS
      Only Client Components need hydration
      Reduces hydrated JS significantly
   
   4. SELECTIVE HYDRATION (React 18):
      Using Suspense boundaries, React can start hydrating in chunks
      If user clicks while still hydrating → that section hydrated first
   
   5. QWIK (resumability instead of hydration):
      Framework-level solution: serializes component state to HTML
      No JavaScript executed until user interaction
      Sub-millisecond TTI ("zero hydration cost")

Q10: "We're building a design system. What performance considerations matter?"
──────────────────────────────────────────────────────────────────────────────
A: 
   BUNDLE SIZE:
   - Tree-shakeable: Each component in separate file, ESM exports
   - sideEffects: false in package.json
   - Avoid CSS-in-JS runtime (Emotion/SC adds 12-25KB + runtime cost)
   - Consider CSS Modules or Vanilla Extract (zero-runtime CSS extraction)
   - Bundle analysis: What does importing just <Button> cost?
   
   RENDERING PERFORMANCE:
   - Components should be pure (same props = same output)
   - Don't use heavy dependencies in simple components
   - Document which components need React.memo (heavily re-rendered components)
   
   ANIMATION:
   - Use CSS transitions/animations over JS animations (GPU composited)
   - Only animate transform + opacity (no layout-triggering properties)
   - Provide reduced-motion variants (prefers-reduced-motion media query)
   
   ACCESSIBILITY (related to performance testing):
   - Accessible components reduce custom JS workarounds consumers write
   
   DOCUMENTATION OF PERFORMANCE CHARACTERISTICS:
   - Document which components are heavy (chart, data table)
   - Provide lazy-loaded variants for heavy components
   - Show bundle size impact in Storybook / docs
   
   ICONS:
   - Tree-shakeable icon exports (never import all icons)
   - SVG icons as React components (tree-shakeable, no sprite overhead)
   - Provide icon size estimates in docs

Q11: Design a real-time dashboard that stays performant with 1000+ data points.
────────────────────────────────────────────────────────────────────────────────
A: HIGH-LEVEL APPROACH:
   
   DATA LAYER:
   - WebSocket for real-time updates (not polling — reduces request overhead)
   - Throttle incoming updates: max 1 render per 100ms (60fps impossible with 1000 points)
   - Time-series data: circular buffer — keep last N minutes of data
     (prevents memory growth as data accumulates)
   - Batch multiple WebSocket messages into one state update (requestAnimationFrame)
   
   RENDERING:
   - Canvas-based charts (Chart.js, D3) instead of SVG for 1000+ data points
     SVG creates DOM nodes; 1000 SVG elements = 1000 DOM nodes = expensive
     Canvas renders everything in a single bitmap element
   - requestAnimationFrame for chart updates (sync with browser paint cycle)
   - Off-screen canvas for pre-rendering while main thread is free
   
   REACT LAYER:
   - useMemo for chart data transformations (don't recompute on every render)
   - Split charts into separate components with React.memo
   - useTransition for filter/time range changes (non-urgent → chart updates)
   - Don't put real-time data in React state directly (too many re-renders)
     Instead: ref for data, forceUpdate or external store signal for redraw
   
   MEMORY:
   - Implement data retention policy: only keep last 60 minutes per metric
   - WeakRef for cached chart instances (GC can reclaim if memory pressure)
   
   PERFORMANCE MONITORING:
   - Track INP specifically for filter interactions
   - Monitor memory usage — real-time apps can leak if cleanup not done
   - Use React Profiler to verify chart component isn't re-rendering too often
