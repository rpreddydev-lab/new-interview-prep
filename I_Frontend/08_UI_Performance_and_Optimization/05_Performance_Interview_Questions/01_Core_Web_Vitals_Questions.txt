================================================================
CORE WEB VITALS INTERVIEW QUESTIONS & ANSWERS
================================================================

This file contains 25+ Q&A covering LCP, INP, CLS, FCP, TTFB.
Questions are organized from foundational to senior-level.

================================================================
FOUNDATIONAL QUESTIONS
================================================================

Q1: What are Core Web Vitals and why do they matter?
─────────────────────────────────────────────────────
A: Core Web Vitals are a set of user-centric performance metrics defined
   by Google that measure real-world user experience quality:
   
   - LCP (Largest Contentful Paint): How fast does the page load? ≤ 2.5s
   - INP (Interaction to Next Paint): How responsive are interactions? ≤ 200ms
   - CLS (Cumulative Layout Shift): How visually stable is the page? ≤ 0.1
   
   They matter because:
   1. Google uses them as ranking signals — good scores = better SEO
   2. They correlate directly with user satisfaction and business metrics
   3. Google research shows 53% of users abandon sites that take > 3s to load
   4. They replaced FID (First Input Delay) in March 2024 with INP

──────────────────────────────────────────────────────────────

Q2: What are the thresholds for each Core Web Vital?
─────────────────────────────────────────────────────
A: Good / Needs Improvement / Poor:

   LCP: ≤ 2.5s   /  2.5–4.0s   /  > 4.0s
   INP: ≤ 200ms  /  200–500ms  /  > 500ms
   CLS: ≤ 0.1    /  0.1–0.25   /  > 0.25
   
   FCP (supporting): ≤ 1.8s / 1.8–3.0s / > 3.0s
   TTFB (supporting): ≤ 800ms / 800ms–1.8s / > 1.8s
   
   These are measured at the 75th percentile of all page loads
   (p75 means 75% of users experience this value or better).

──────────────────────────────────────────────────────────────

Q3: What is LCP and what elements can trigger it?
──────────────────────────────────────────────────
A: LCP (Largest Contentful Paint) measures when the largest visible content
   element finishes rendering in the viewport. It marks when the page is
   "loaded" from a user's perspective.
   
   Elements considered for LCP:
   - <img> elements
   - <image> inside <svg>
   - <video> elements (poster image)
   - Block-level elements with background-image loaded via CSS
   - Block elements containing text nodes (headings, paragraphs)
   
   NOT considered: <svg> shapes, <canvas>, <video> content itself
   
   LCP stops at first user interaction — scroll, tap, keypress.
   This is because after interaction, new content can appear and
   the browser shouldn't count post-interaction "largest" elements.

──────────────────────────────────────────────────────────────

Q4: What are the four sub-parts of LCP and how do you optimize each?
──────────────────────────────────────────────────────────────────────
A: 
   1. TIME TO FIRST BYTE (TTFB): Document request until first byte
      Optimize: CDN, server caching (Redis), database query optimization
   
   2. RESOURCE LOAD DELAY: Time between first byte and starting LCP resource
      Optimize: Preload LCP resource, inline critical CSS so resource
      discovery isn't blocked by CSS parsing
   
   3. RESOURCE LOAD DURATION: Time to download the LCP resource
      Optimize: Compress images (WebP/AVIF), CDN, proper sizing,
      fetchpriority="high" for the LCP image
   
   4. ELEMENT RENDER DELAY: Time between resource loaded and LCP painted
      Optimize: Reduce render-blocking resources, minimize main thread work

──────────────────────────────────────────────────────────────

Q5: My LCP image is 4.0s. Walk me through how you'd diagnose and fix it.
──────────────────────────────────────────────────────────────────────────
A: Step-by-step diagnosis:
   
   1. Identify the LCP element — Chrome DevTools > Performance tab,
      record page load, find the LCP marker. Or: run Lighthouse and
      check "Largest Contentful Paint element."
   
   2. Check each sub-part in DevTools:
      - Navigation start → server response: TTFB? (should be < 600ms)
      - Server response → request start: Resource load delay?
      - Request start → response end: Image download time?
      - Response end → LCP mark: Render delay?
   
   3. Common fixes based on diagnosis:
      - TTFB high? → CDN + server caching
      - Image discovered late? → Add <link rel="preload" as="image">
      - Image too large? → WebP/AVIF format, proper dimensions, CDN
      - Image not prioritized? → fetchpriority="high", never lazy load LCP
      - Render-blocking CSS? → Inline critical CSS, defer non-critical
   
   4. For Next.js: use <Image priority> on the LCP image
   
   5. Verify with Lighthouse CI: run 3+ times, take median score

INP QUESTIONS
================================================================

Q6: What is INP and how is it different from FID?
──────────────────────────────────────────────────
A: INP (Interaction to Next Paint, introduced March 2024) measures the
   latency of ALL user interactions across the entire page lifecycle.
   FID (First Input Delay) only measured the FIRST interaction's input delay.
   
   FID only measured: INPUT DELAY of first interaction
   INP measures: INPUT DELAY + PROCESSING TIME + PRESENTATION DELAY
                 for ALL interactions, then takes the WORST one
   
   INP thresholds: ≤ 200ms good, ≤ 500ms needs improvement, > 500ms poor
   FID thresholds were: ≤ 100ms good, ≤ 300ms needs improvement
   
   Why the change: FID missed cases where first input was fast but clicking
   a button later in the session caused jank. INP catches all interactions.

──────────────────────────────────────────────────────────────

Q7: Walk me through the three components of INP.
─────────────────────────────────────────────────
A: An interaction has three phases, and their sum is the INP contribution:
   
   1. INPUT DELAY (like FID): Time from user action to event handler running.
      Caused by: long tasks on main thread, other JS executing.
      Fix: Break up long tasks (scheduler.yield, setTimeout 0)
   
   2. PROCESSING TIME: Time event handler runs synchronously.
      Caused by: expensive event handlers (sorting, filtering large lists).
      Fix: Move heavy work to Web Workers, batch DOM updates,
           use useTransition/startTransition for non-urgent updates
   
   3. PRESENTATION DELAY: Time browser takes to repaint after handler.
      Caused by: large DOM, complex CSS, forced layout recalculations.
      Fix: Reduce DOM size, avoid forced synchronous layouts

──────────────────────────────────────────────────────────────

Q8: How does React 18's useTransition help improve INP?
─────────────────────────────────────────────────────────
A: useTransition marks state updates as "non-urgent" (transitions).
   The browser can INTERRUPT transition renders to handle user input,
   keeping the app responsive.
   
   Without useTransition:
   User types → React re-renders entire list synchronously (blocking)
   If list render takes 500ms → input is blocked for 500ms → bad INP
   
   With useTransition:
   User types → urgent: update input display immediately
              → non-urgent: filter list as transition
   Browser yields between each item during transition → stays responsive
   
   Code:
   const [isPending, startTransition] = useTransition();
   
   function handleSearch(e) {
     setQuery(e.target.value);           // Urgent: update input
     startTransition(() => {
       setFilteredItems(filter(items));  // Non-urgent: can be interrupted
     });
   }

CLS QUESTIONS
================================================================

Q9: How is the CLS score calculated?
──────────────────────────────────────
A: CLS is calculated as: impact fraction × distance fraction for each layout
   shift event. Multiple shifts are grouped into "session windows" (a burst
   of shifts within 1 second with max 5 second gap). The score of the worst
   session window is your CLS score.
   
   impact fraction: the portion of viewport affected by the shift
   distance fraction: the maximum distance any element moved / viewport height
   
   Example: An element covers 50% of viewport and shifts down 25%:
   CLS = 0.5 × 0.25 = 0.125 (borderline "needs improvement")
   
   Shifts caused by user interaction are excluded (expected behavior).

──────────────────────────────────────────────────────────────

Q10: What are the most common causes of CLS and how do you fix each?
──────────────────────────────────────────────────────────────────────
A: 
   1. IMAGES WITHOUT DIMENSIONS
      Cause: Browser doesn't know image size → no space reserved → shift on load
      Fix: Always set width and height: <img width="400" height="300">
           Use aspect-ratio CSS: .img { aspect-ratio: 4/3; }
   
   2. ADS AND THIRD-PARTY EMBEDS
      Cause: Ad containers injected dynamically, changing size on load
      Fix: Reserve space with min-height placeholder
           Place ads in "popcorn ads" slots that don't push content
   
   3. DYNAMIC CONTENT INJECTION
      Cause: Cookie banners, notifications injected above content
      Fix: Reserve space in DOM (invisible placeholder), then show in place
   
   4. FONT LOADING (FOUT/FOIT)
      Cause: Font swap causes text to shift when custom font loads
      Fix: font-display: optional (no FOUT but font may not appear)
           font-display: swap with CSS font-size-adjust or metric overrides
           Preload critical fonts: <link rel="preload" as="font">
   
   5. CSS ANIMATIONS
      Cause: Animations that change layout properties (height, margin, top)
      Fix: Animate transform and opacity only (these use GPU compositing)
           transform: translateY() instead of changing top/margin
   
   6. SKELETON SCREENS (wrong size)
      Cause: Skeleton doesn't match content dimensions → shift when content loads
      Fix: Match skeleton dimensions to content; fetch dimensions server-side

FCP AND TTFB QUESTIONS
================================================================

Q11: What is the relationship between TTFB, FCP, and LCP?
──────────────────────────────────────────────────────────
A: They form a cascade:
   
   TTFB: Server receives request → sends first byte of HTML
         Affects everything — no rendering can happen before HTML arrives
   
   FCP: First Contentful Paint — first text or image visible
        Depends on TTFB + render-blocking resources (CSS, fonts)
   
   LCP: Largest Contentful Paint — largest element visible
        Depends on FCP + LCP image/text download time
   
   If TTFB is 1.5s, FCP cannot be below 1.5s.
   If FCP is 2.0s, LCP is usually 2.0–4.0s.
   
   TTFB optimization: CDN, server caching, database queries, server location
   FCP optimization: Remove render-blocking resources, SSR, inline critical CSS
   LCP optimization: Preload LCP resource, image optimization, CDN

──────────────────────────────────────────────────────────────

Q12: How does server-side rendering improve FCP and LCP?
─────────────────────────────────────────────────────────
A: With CSR (SPA): Browser receives empty HTML → downloads JS bundle →
   executes JS → React renders → FCP/LCP appears. User sees blank page
   until JS executes (could be 3–5s on slow devices).
   
   With SSR: Browser receives HTML WITH content → FCP/LCP appears immediately
   (no waiting for JS). Then JS downloads and "hydrates" (attaches event listeners).
   
   Timeline comparison:
   CSR: HTML arrive (0.5s) → JS download (2s) → JS execute (1s) → FCP (3.5s)
   SSR: HTML arrive WITH content (1.0s) → FCP (1.0s)
   
   SSR trade-offs: TTI (Time to Interactive) is still delayed (hydration takes time)
   but users SEE the content much faster.
   
   Next.js improvements: React Server Components + Streaming render HTML
   incrementally, further improving FCP.

MEASUREMENT QUESTIONS
================================================================

Q13: How do you measure Core Web Vitals in production?
───────────────────────────────────────────────────────
A: Lab data (synthetic): Lighthouse, WebPageTest, CrUX lab data.
   Field data (RUM): Real User Monitoring — measure real users.
   
   Using web-vitals library:
   
   import { onLCP, onINP, onCLS } from 'web-vitals';
   
   function sendToAnalytics({ name, value, rating, id }) {
     navigator.sendBeacon('/analytics', JSON.stringify({
       metric: name,
       value: Math.round(value),
       rating,          // 'good' | 'needs-improvement' | 'poor'
       effectiveType: navigator.connection?.effectiveType,
       url: location.href,
     }));
   }
   
   onLCP(sendToAnalytics);
   onINP(sendToAnalytics);
   onCLS(sendToAnalytics);
   
   Also: Google Search Console shows CrUX field data.
   Tools: Vercel Speed Insights, Datadog RUM, New Relic, Sentry Performance.
   
   Key: Always measure at P75 (75th percentile), not average or median.
   P75 captures the experience of users with slower devices/networks.

──────────────────────────────────────────────────────────────

Q14: Why should you use the 75th percentile for Core Web Vitals?
──────────────────────────────────────────────────────────────────
A: Averages and medians are misleading because they hide the poor end
   of the distribution. If 25% of your users have a 5s LCP and the rest
   have 1s, the average might look "acceptable" but 1 in 4 users has
   a terrible experience. P75 means 75% of users experience your score
   or better — ensuring a good proportion of users have a good experience.
   It's also Google's official measurement methodology for CWV rankings.

ADVANCED/SENIOR QUESTIONS

Q15: A page has good LCP but poor CLS. How would you investigate?
──────────────────────────────────────────────────────────────────
A: Investigation workflow:
   
   1. Use Chrome DevTools > Performance panel, look for "Layout Shift" markers
      in the "Experience" row — click them to see what shifted.
   
   2. Use PerformanceObserver to get attribution:
      new PerformanceObserver(list => {
        list.getEntries().forEach(entry => {
          entry.sources.forEach(source => {
            console.log('Shifted:', source.node, 'by', entry.value);
          });
        });
      }).observe({ type: 'layout-shift' });
   
   3. Check common causes:
      - Open Network tab, filter by Img/Media — check load timing
        relative to layout shifts
      - Check for late-loading ads: look at third-party requests
      - Check if fonts cause text expansion on load
      - Check for cookie banners or notifications appearing
   
   4. Run Lighthouse: it shows "Avoid large layout shifts" with screenshots
      before/after each major shift

──────────────────────────────────────────────────────────────

Q16: How would you set up a performance monitoring system from scratch?
──────────────────────────────────────────────────────────────────────────
A: Multi-layer approach:
   
   1. CI/CD: Lighthouse CI runs on every PR, fails if CWV budgets exceeded
      (lighthouserc.js with assert.budgets for LCP/CLS/TBT)
   
   2. Synthetic monitoring: WebPageTest or Lighthouse CI scheduled runs
      from multiple global locations to catch regressions between releases
   
   3. Real User Monitoring: web-vitals library on every page, sending to
      analytics service (custom endpoint or Vercel Speed Insights).
      Segment by device type, connection speed, geography.
   
   4. Alerting: Set thresholds — alert if P75 LCP > 3s for 1 hour
      (Datadog, New Relic, or custom dashboards in Grafana)
   
   5. Attribution: Capture LCP element, CLS sources, INP interactions
      to know WHAT to fix, not just THAT something is wrong.
   
   6. Google Search Console: Monitor CrUX field data by URL group,
      correlate with organic traffic changes.

──────────────────────────────────────────────────────────────

Q17: What's the Speculation Rules API and how does it help Core Web Vitals?
─────────────────────────────────────────────────────────────────────────────
A: Speculation Rules API (Chrome 109+) enables the browser to prefetch
   or prerender pages the user is LIKELY to navigate to next — before
   they click. This makes navigation feel instant.
   
   <script type="speculationrules">
   {
     "prerender": [{ "urls": ["/product/123", "/checkout"] }],
     "prefetch": [{ "where": { "href_matches": "/products/*" } }]
   }
   </script>
   
   Prerender = full page render in background (LCP becomes near-instant)
   Prefetch = only download HTML (saves ~50% of navigation latency)
   
   For CWV: when user navigates to a prerendered page, LCP appears
   immediately — often < 100ms. This dramatically improves LCP for
   subsequent navigations. Next.js Link prefetching uses a similar
   concept but only prefetches JS chunks, not the full page render.

──────────────────────────────────────────────────────────────

Q18: Explain how INP is measured for a page with many interactions.
────────────────────────────────────────────────────────────────────
A: INP is the HIGHEST interaction latency, with some exclusions for
   statistical outliers. Specifically:
   
   - Tracks ALL interactions: clicks, taps, key presses (not scroll/hover)
   - Total interactions counted over the page session
   - Exclusion logic: if < 50 interactions, use the worst. If > 50,
     allow up to max(1, floor(N/50)) worst interactions to be excluded.
     This accounts for accidental/irrelevant interactions.
   - INP = the WORST included interaction
   
   So for a form with 20 inputs: INP reflects the slowest keypress.
   If one field is 800ms (because it triggers heavy validation) but
   all others are 50ms, INP = 800ms → "poor."
   
   This design means: you can't have ONE slow interaction anywhere
   in your app. Every interaction must be fast.

──────────────────────────────────────────────────────────────

Q19: What is "Time to Interactive" (TTI) and how does it differ from INP?
──────────────────────────────────────────────────────────────────────────
A: TTI is a LAB metric measuring when the page becomes reliably interactive
   (main thread is consistently clear of long tasks). It's measured by
   finding the point after FCP where the main thread stays quiet for 5s.
   
   INP is a FIELD metric measuring actual interaction latency experienced
   by real users throughout the session.
   
   TTI is flawed: A page could have a good TTI but still have slow INP
   if interactions later trigger expensive work. TTI focuses on the initial
   load window; INP captures the entire session.
   
   Google no longer includes TTI in Lighthouse's "Performance" score
   breakdown (it's still reported but not scored). INP in the field has
   replaced it as the primary responsiveness signal.

──────────────────────────────────────────────────────────────

Q20: How do you debug INP in Chrome DevTools?
──────────────────────────────────────────────
A: 
   1. Chrome DevTools > Performance panel > check "Web Vitals"
   2. Record while interacting with the page
   3. Look for INP markers in the Experience lane
   4. Click the INP marker to see:
      - Input delay duration (waiting for main thread)
      - Processing time (event handlers running)
      - Presentation delay (rendering after handlers)
   
   5. Identify the long tasks blocking the event:
      - Long red tasks in the main thread lane = input delay
      - Zoom into the event handler: which function takes longest?
   
   6. In the Summary panel: shows function call tree with timing
   
   7. Also: Chrome DevTools > Performance Insights panel has an
      "INP" section with automatic analysis and suggestions
   
   For production: use web-vitals library with attribution:
   onINP(({ attribution }) => {
     console.log('Slow element:', attribution.interactionTarget);
     console.log('Event type:', attribution.interactionType);
     console.log('Input delay:', attribution.inputDelay);
     console.log('Processing time:', attribution.processingDuration);
   });
