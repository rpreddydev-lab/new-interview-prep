LIGHTHOUSE
══════════════════════════════════════════════════════════════════

WHAT IS LIGHTHOUSE?
────────────────────
Lighthouse is an open-source, automated auditing tool by Google that runs
against any web page (public or authenticated) and produces reports covering:
  - Performance
  - Accessibility
  - Best Practices
  - SEO
  - Progressive Web App (PWA)

Lighthouse runs in a CONTROLLED LAB ENVIRONMENT using a simulated mid-tier
Android device on slow 3G. This is intentional — it represents a challenging
but realistic user scenario.

HOW TO RUN LIGHTHOUSE:
  1. Chrome DevTools → Lighthouse tab → Analyze page load
  2. Chrome extension (Lighthouse for Chrome)
  3. CLI: npx lighthouse https://example.com --view
  4. Lighthouse CI (for automation)
  5. PageSpeed Insights (web UI + API)
  6. WebPageTest (includes Lighthouse)

LIGHTHOUSE PERFORMANCE SCORE CALCULATION:
──────────────────────────────────────────
Score is a weighted median of these metrics:
  ┌──────────────────────────────────┬────────┐
  │ Metric                           │ Weight │
  ├──────────────────────────────────┼────────┤
  │ Total Blocking Time (TBT)        │ 30%    │
  │ Largest Contentful Paint (LCP)   │ 25%    │
  │ Speed Index                      │ 10%    │
  │ Cumulative Layout Shift (CLS)    │ 25%    │
  │ First Contentful Paint (FCP)     │ 10%    │
  └──────────────────────────────────┴────────┘

Score ranges:
  - 90–100: Green (Good)
  - 50–89:  Orange (Needs Improvement)
  - 0–49:   Red (Poor)

KEY LIGHTHOUSE DIAGNOSTICS:
  - Eliminate render-blocking resources
  - Properly size images
  - Defer offscreen images (lazy loading)
  - Remove unused CSS/JavaScript
  - Minify JS/CSS/HTML
  - Serve static assets with efficient cache policy
  - Enable text compression (gzip/brotli)
  - Avoid enormous network payloads
  - Reduce JS execution time
  - Minimize main-thread work

LIGHTHOUSE CLI OPTIONS:
──────────────────────────
# Basic usage
npx lighthouse https://example.com

# Specific categories
npx lighthouse https://example.com --only-categories=performance

# Throttling options
npx lighthouse https://example.com \
  --throttling.cpuSlowdownMultiplier=4 \
  --throttling.downloadThroughputKbps=1638

# Output formats
npx lighthouse https://example.com \
  --output=json \
  --output-path=./report.json

# No throttling (for controlled environments)
npx lighthouse https://example.com \
  --throttling-method=provided \
  --no-emulated-form-factor

LIGHTHOUSE CI CONFIGURATION:
──────────────────────────────
# .lighthouserc.js
module.exports = {
  ci: {
    collect: {
      url: ['http://localhost:3000/'],
      numberOfRuns: 5, // More runs = more reliable median
      settings: {
        // Emulate specific device
        formFactor: 'mobile',
        screenEmulation: {
          mobile: true,
          width: 360,
          height: 640,
          deviceScaleFactor: 2,
        },
      },
    },
    assert: {
      preset: 'lighthouse:no-pwa',
      assertions: {
        'categories:performance': ['error', { minScore: 0.9 }],
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'total-blocking-time': ['error', { maxNumericValue: 200 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
        'unused-javascript': ['warn', { maxLength: 0 }],
        'uses-optimized-images': 'warn',
        'uses-webp-images': 'warn',
      },
    },
    upload: {
      target: 'lhci', // or 'temporary-public-storage'
      serverBaseUrl: 'http://your-lhci-server.com',
    },
  },
};

CHROME DEVTOOLS - PERFORMANCE PANEL
================================================================

THE PERFORMANCE PANEL IN DEPTH
────────────────────────────────

HOW TO USE:
  1. Open DevTools (F12 / Cmd+Opt+I)
  2. Go to "Performance" tab
  3. Click Record (⏺) or reload with Cmd+Shift+E
  4. Interact with page
  5. Stop recording

UNDERSTANDING THE PERFORMANCE PANEL:
  ┌─────────────────────────────────────────────────────────────┐
  │ [CPU Flame Chart]                                           │
  │ [Network Requests Timeline]                                 │
  │ [Screenshots (optional)]                                    │
  │ ─────────────────────────────────────────────────────────── │
  │ FPS | CPU | NET                                             │
  │ ─────────────────────────────────────────────────────────── │
  │ [Timings: FP, FCP, LCP, DCL, L]                            │
  │ [Main Thread (Flame Chart)]                                 │
  │ [Worker Threads]                                            │
  │ [GPU]                                                       │
  │ [Network]                                                   │
  │ [Frames]                                                    │
  └─────────────────────────────────────────────────────────────┘

KEY SECTIONS:
  FPS Chart: Green = smooth, Red = jank (dropped frames)
  CPU Chart: Yellow=scripting, Purple=rendering, Green=painting
  Flame Chart: Shows call stack over time
  Long Tasks: Red triangles = tasks > 50ms (blocking)

READING THE FLAME CHART:
  - Width = duration of task/function
  - Depth = call stack (wider at top = parent, narrower below = children)
  - Color:
    → Yellow (⚡): JavaScript execution
    → Purple (🎨): Style/Layout/Paint calculations
    → Green (🖌): Painting
    → Gray: Other browser work

IDENTIFYING PERFORMANCE ISSUES:
  ✅ Long Tasks (> 50ms): Click red bar → see what function caused it
  ✅ Layout Thrashing: Alternating purple blocks in main thread
  ✅ Jank: FPS drops below 60
  ✅ Forced Reflows: "Recalculate Style" followed by "Layout" in quick succession
  ✅ Paint Storms: Too many "Paint" events

IMPORTANT SHORTCUTS:
  - Cmd+Shift+P → "Start profiling and reload page"
  - After recording: use W/A/S/D to zoom/pan timeline
  - Click a flame → bottom panel shows source location

CHROME DEVTOOLS - NETWORK PANEL
================================================================

KEY NETWORK PANEL FEATURES:
─────────────────────────────
  1. Waterfall view: Shows request timing
  2. Filter: Filter by type (JS, CSS, XHR, etc.)
  3. Throttling: Simulate 3G/4G connections
  4. Disable cache: Test cold visits
  5. Coverage: Show unused CSS/JS bytes

NETWORK WATERFALL TIMING BREAKDOWN:
  ┌────────────────────────────────────────────────────────┐
  │ Queueing     → Waiting for browser slot                │
  │ Stalled      → Any of 5 reasons (waiting for socket)  │
  │ DNS Lookup   → DNS resolution                          │
  │ Initial Conn → TCP handshake                           │
  │ SSL          → TLS negotiation                         │
  │ Request sent → Sending request headers                 │
  │ Waiting TTFB → Server processing + first byte          │
  │ Content Down → Downloading response body               │
  └────────────────────────────────────────────────────────┘

IMPORTANT NETWORK PANEL CHECKS:
  - Is the initiator chain deep? (request chains delay loading)
  - Which resources are render-blocking? (check the Lighthouse report)
  - What's the TTFB? (server or CDN issue if > 800ms)
  - Are large images being served? (look for resources > 100KB)
  - Are there too many JS files? (consider bundling)
  - Is HTTP/2 being used? (check Protocol column)
  - Are headers being used for caching? (Cache-Control, ETag)

CHROME DEVTOOLS - COVERAGE PANEL
================================================================

PURPOSE: Find unused CSS and JavaScript code

HOW TO USE:
  1. DevTools → Cmd+Shift+P → "Coverage"
  2. Click Record
  3. Interact with the page
  4. Stop
  5. See % of each file that was NOT executed (red = unused)

INTERPRETATION:
  - High unused % in a CSS file → remove dead CSS, use PurgeCSS
  - High unused % in a JS file → code split, tree shake
  - 80% unused in main.js → major opportunity for code splitting

PRACTICAL USE:
  - Click file name → opens in Sources panel with red/green highlighting
  - Red lines = code never ran
  - Combine with code splitting to lazy-load unused code

CHROME DEVTOOLS - MEMORY PANEL
================================================================

MEMORY LEAK DETECTION:
───────────────────────
  1. Take heap snapshot before action
  2. Perform action repeatedly (open/close modal, navigate back/forth)
  3. Take another heap snapshot
  4. Compare: if memory keeps growing, you have a leak

COMMON MEMORY LEAKS IN REACT:
  - Event listeners not cleaned up (removeEventListener in useEffect cleanup)
  - setInterval/setTimeout not cleared
  - Subscriptions not unsubscribed
  - Closures capturing large objects
  - DOM references held after element removal

MEMORY PANEL TOOLS:
  - Heap snapshot: Shows all objects in memory
  - Allocation instrumentation: Shows allocations over time
  - Allocation sampling: Lightweight continuous monitoring

CHROME DEVTOOLS - RENDERING PANEL
================================================================

HOW TO OPEN:
  DevTools → Three dots menu → More tools → Rendering

USEFUL OPTIONS:
  ✅ Paint flashing: Highlights areas being repainted (green flashes)
  ✅ Layout shift regions: Highlights layout shifts (blue borders)
  ✅ FPS meter: Shows real-time FPS overlay
  ✅ Scrolling performance issues: Highlights non-passive scroll listeners
  ✅ Core Web Vitals: Overlay showing LCP/CLS in real-time

OTHER ESSENTIAL PERFORMANCE TOOLS
================================================================

WEBPAGETEST (webpagetest.org):
  - Test from different locations worldwide
  - Test on real Android devices
  - Filmstrip view (screenshots of load progression)
  - Waterfall with detailed timing
  - Video comparison between sites
  - Connection view, request prioritization

PAGE SPEED INSIGHTS:
  - pagespeed.web.dev
  - Combines Lighthouse (lab) + CrUX (field) data
  - Shows P75 for real users (from Chrome's CrUX dataset)
  - Provides actionable recommendations

CHROME USER EXPERIENCE REPORT (CrUX):
  - Dataset of real user metrics from Chrome browsers
  - Available via Google Search Console, PageSpeed Insights
  - CrUX API: https://developer.chrome.com/docs/crux/api/
  - BigQuery: Full CrUX dataset for analysis

WEBPACK BUNDLE ANALYZER:
  - npm install --save-dev webpack-bundle-analyzer
  - Visual treemap of your bundle
  - Identifies large dependencies
  - Shows parsed, stat, and gzipped sizes

NEXT.JS BUNDLE ANALYZER:
  - ANALYZE=true npm run build
  - Client and server bundle breakdown

SOURCE MAP EXPLORER:
  - npx source-map-explorer 'build/static/js/*.js'
  - Analyzes actual bundle composition from source maps

INTERVIEW ANSWERS
================================================================

Q: What is Lighthouse and how does it work?
A: Lighthouse is Google's open-source automated auditing tool. It loads
   a page in a controlled environment (simulated mid-tier Android, slow 3G)
   and measures performance, accessibility, SEO, and best practices.
   The performance score is a weighted median of TBT (30%), LCP (25%),
   CLS (25%), Speed Index (10%), FCP (10%). It runs in Chrome DevTools,
   via CLI, or via Lighthouse CI for automated testing.

Q: What does the Chrome DevTools Performance panel show?
A: It shows a detailed timeline of browser activity: the FPS/CPU/network
   summary at top, then the detailed flame chart showing the call stack
   over time. Yellow = JS execution, Purple = style/layout, Green = paint.
   Long tasks (>50ms) are marked with red triangles. It helps identify
   layout thrashing, jank, and expensive JavaScript execution.

Q: How do you find unused JavaScript/CSS?
A: Chrome DevTools Coverage panel records code coverage during interaction.
   Files with high unused percentages (shown in red) are candidates for
   code splitting or dead code removal. For CSS, tools like PurgeCSS analyze
   HTML/templates to remove unused selectors. For JS, tree shaking in webpack/
   Rollup eliminates unused exports at build time.

Q: What is the difference between Lighthouse and WebPageTest?
A: Lighthouse runs in your local Chrome (or CI) in a simulated environment.
   WebPageTest tests from real locations worldwide on real network conditions
   and can test on real Android devices. WebPageTest gives filmstrip views
   (screenshots), detailed waterfall diagrams, and the ability to test from
   different geographic locations. Lighthouse is better for development/CI;
   WebPageTest for real-world analysis from different locations.

Q: How would you use Chrome DevTools to diagnose a slow page?
A: I'd start with Lighthouse for a high-level overview. Then in the Performance
   panel, I'd record a page load and look for: long tasks (>50ms, red triangles),
   render-blocking resources in the network waterfall, layout thrashing (fast-
   alternating style/layout blocks), and paint storms. I'd check the Coverage
   panel for unused code opportunities, and the Network panel for large resources,
   deep request chains, or poor caching headers. Finally I'd check the Rendering
   panel with "Paint flashing" to see what's being repainted on interaction.
