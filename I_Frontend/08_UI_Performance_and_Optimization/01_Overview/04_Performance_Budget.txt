================================================================
PERFORMANCE BUDGET - SETTING AND ENFORCING LIMITS
================================================================

WHAT IS A PERFORMANCE BUDGET?
──────────────────────────────
A performance budget is a set of limits that define acceptable performance
thresholds for a website. These are agreed-upon constraints that the team
commits not to exceed. When you exceed the budget, you must either optimize
something else or consciously accept the tradeoff.

"A performance budget is like a financial budget — if you want to add
something, you must cut something else."

TYPES OF PERFORMANCE BUDGETS:
  1. MILESTONE TIMINGS: LCP ≤ 2.5s, TTI ≤ 3.8s, FCP ≤ 1.8s
  2. QUANTITY-BASED: Total JS ≤ 300KB (gzipped), Total CSS ≤ 50KB
  3. RULE-BASED: Lighthouse score ≥ 90, no render-blocking resources
  4. CUSTOM: Total page weight ≤ 1.5MB, fewer than 50 HTTP requests

================================================================
WHY PERFORMANCE BUDGETS MATTER
================================================================

WITHOUT A BUDGET:
  - "Death by a thousand additions" — each feature adds a bit of weight
  - After 6 months: your 200KB JS bundle becomes 800KB
  - No one is responsible; no one realizes it's happening
  - Hard to fix retroactively (each feature owner defends their code)

WITH A BUDGET:
  - Creates shared responsibility and accountability
  - Shifts performance from reactive to proactive
  - Forces architectural decisions (do we really need this lib?)
  - Enables automation — CI/CD fails if budget is exceeded

================================================================
HOW TO SET A PERFORMANCE BUDGET
================================================================

APPROACH 1: COMPETITOR-BASED
──────────────────────────────
  1. Identify your top 3 competitors
  2. Measure their performance (WebPageTest, Lighthouse)
  3. Set your budget 20% better than the fastest competitor
  4. "If they can do it in 3s, you should do it in 2.4s"

APPROACH 2: METRIC-BASED (user-centric)
──────────────────────────────────────────
  Use Google's Core Web Vitals thresholds as your starting point:
  - LCP ≤ 2.5s (target 2s for buffer)
  - INP ≤ 200ms (target 150ms for buffer)
  - CLS ≤ 0.1 (target 0.05 for buffer)
  - FCP ≤ 1.8s
  - TTFB ≤ 800ms
  - TBT ≤ 200ms

APPROACH 3: QUANTITY-BASED (easiest to enforce in CI)
───────────────────────────────────────────────────────
  Translate timing goals to file size limits:
  
  On a 3G connection (1.6Mbps):
  - 1MB = ~5s to transfer (before parse/compile)
  - Budget: 300KB HTML + 50KB CSS + 300KB JS (gzipped) = under 1MB
  
  On Slow 3G (500Kbps):
  - 1MB = ~16s to transfer
  - Budget: 200KB total compressed size

RULE OF THUMB:
  For JS: Keep main thread parse/compile ≤ 3-4 seconds on a mid-tier device
  ≈ Keep JavaScript ≤ 150KB (gzipped) for the initial render

================================================================
ENFORCING PERFORMANCE BUDGETS IN TOOLING
================================================================

1. BUNDLESIZE (NPM Package)
────────────────────────────
npm install --save-dev bundlesize

// package.json
{
  "bundlesize": [
    {
      "path": "./build/static/js/main.*.js",
      "maxSize": "200 kB",
      "compression": "gzip"
    },
    {
      "path": "./build/static/css/main.*.css",
      "maxSize": "50 kB"
    },
    {
      "path": "./build/static/media/*",
      "maxSize": "100 kB"
    }
  ],
  "scripts": {
    "size": "bundlesize"
  }
}

# Run in CI
npm run size

2. SIZE-LIMIT (More powerful alternative)
───────────────────────────────────────────
npm install --save-dev size-limit @size-limit/file

// package.json
{
  "size-limit": [
    {
      "path": "dist/index.js",
      "limit": "20 kB"  // Time to execute, not just file size
    },
    {
      "path": "dist/vendor.js",
      "limit": "100 kB"
    }
  ],
  "scripts": {
    "size": "size-limit",
    "analyze": "size-limit --why"
  }
}

// size-limit even estimates execution time on specific devices!

3. WEBPACK PERFORMANCE HINTS
──────────────────────────────
// webpack.config.js
module.exports = {
  performance: {
    hints: 'error', // 'warning' | 'error' | false
    maxEntrypointSize: 250000,  // 250KB
    maxAssetSize: 250000,       // 250KB per asset
    assetFilter: (assetFilename) => {
      // Only check JS and CSS files
      return /\.(js|css)$/.test(assetFilename);
    },
  },
};

================================================================
MANAGING THE PERFORMANCE BUDGET OVER TIME
================================================================

WHEN BUDGET IS EXCEEDED:
  1. Stop the merge/deployment
  2. Identify what caused the increase (git bisect, bundle diff)
  3. Options:
     a. Optimize the new code (remove unused imports, tree shaking)
     b. Remove something else of equivalent size
     c. Split the code (lazy load the new feature)
     d. Consciously revise the budget with team agreement

TOOLS FOR BUDGET TRACKING:
  - Calibre: Continuous performance monitoring with budget alerts
  - SpeedCurve: Performance dashboards with budget visualization
  - Treo: CrUX-based monitoring with budget setting
  - Datadog: RUM with alerting

PERFORMANCE BUDGET IN TEAM WORKFLOW:
  ─────────────────────────────────────
  Design Phase:
  → Discuss feature performance impact before building
  
  PR Review:
  → Bundle diff in every PR (use Bundlewatch or similar)
  → Lighthouse CI must pass before merge
  
  Staging:
  → Run full WebPageTest against performance budget
  → Compare P75 against production baseline
  
  Production:
  → Monitor with RUM (CrUX, web-vitals library)
  → Alert on budget violations

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is a performance budget?
A: A performance budget is a set of limits on performance metrics that the
   team commits not to exceed. Examples include: "LCP ≤ 2.5s", "initial
   JS bundle ≤ 200KB gzipped", "Lighthouse score ≥ 90". It makes performance
   a shared responsibility and enables automated enforcement in CI/CD.

Q: How do you set a performance budget?
A: I use a combination of approaches: (1) User-centric: based on Core Web
   Vitals thresholds (LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1); (2) Competitive:
   20% better than top competitors; (3) Quantity-based: translate timing
   goals to file size limits (e.g., 300KB total gzipped JS for 3G users).

Q: How do you enforce a performance budget in CI/CD?
A: I use tools like Lighthouse CI with a budget.json file, or size-limit/
   bundlesize for bundle size checks. These run on every PR and fail the
   build if budgets are exceeded. For timing metrics, Lighthouse CI collects
   multiple runs and asserts against thresholds. This prevents gradual 
   performance regression over time.

Q: What happens when a PR exceeds the performance budget?
A: The CI pipeline fails and the PR is blocked from merging. The developer
   must either: optimize the new code (remove unused dependencies, lazy
   load), remove something else of equivalent weight, or get explicit team
   approval to revise the budget. This creates accountability and forces
   intentional decisions about tradeoffs.

Q: What tools do you use for ongoing performance budget monitoring?
A: Lighthouse CI in the CI pipeline for lab data, web-vitals library for
   RUM data, Calibre or SpeedCurve for continuous monitoring with alerting,
   and webpack-bundle-analyzer or @next/bundle-analyzer for local development
   analysis. I also use the CrUX API to track P75 real-user data over time.
