================================================================
REQUEST ANIMATION FRAME (rAF)
================================================================

THE PROBLEM WITH setTimeout/setInterval FOR ANIMATIONS:
──────────────────────────────────────────────────────────

  ❌ BAD — setTimeout-based animation:
  let pos = 0;
  function animate() {
    element.style.left = pos++ + 'px';
    setTimeout(animate, 16); // ~60fps target
  }
  animate();

  PROBLEMS:
  1. setTimeout fires at 16ms but the DISPLAY might refresh at 16.67ms
     → animations skip or double-paint (visual tearing)
  2. setTimeout fires even when the tab is NOT visible → wastes CPU/battery
  3. setTimeout can be throttled by the browser if the tab is hidden
  4. Multiple setTimeout animations don't synchronize with each other
  5. No guaranteed timing — timer fires when the event loop is ready

THE SOLUTION — requestAnimationFrame (rAF):
  - Browser SCHEDULES your callback to run JUST BEFORE the next repaint
  - Perfectly synchronized with the display refresh rate (60hz, 120hz, etc.)
  - Automatically PAUSED when the tab is hidden (saves battery!)
  - Provides a HIGH-PRECISION TIMESTAMP (DOMHighResTimeStamp)
  - Multiple rAF callbacks are batched into one render cycle

================================================================
requestAnimationFrame BASICS
================================================================

SYNTAX:
  const rafId = requestAnimationFrame(callback);
  cancelAnimationFrame(rafId); // Cancel scheduled callback

CALLBACK RECEIVES A TIMESTAMP:
  // The timestamp is ms since navigation start (like performance.now())
  requestAnimationFrame((timestamp) => {
    console.log(timestamp); // e.g., 1234.56789 ms
  });

BASIC ANIMATION LOOP:
  function animate(timestamp) {
    // Update position/state
    element.style.transform = `translateX(${getPosition(timestamp)}px)`;
    
    // Schedule next frame
    requestAnimationFrame(animate);
  }
  
  // Start the loop
  requestAnimationFrame(animate);

CANCELING AN ANIMATION:
  let rafId;
  
  function startAnimation() {
    function frame(timestamp) {
      // ... render frame ...
      rafId = requestAnimationFrame(frame);
    }
    rafId = requestAnimationFrame(frame);
  }
  
  function stopAnimation() {
    cancelAnimationFrame(rafId);
  }

================================================================
TIMING-BASED ANIMATION (FRAME-RATE INDEPENDENT)
================================================================

PROBLEM: If you just increment by 1 pixel per frame, animation runs at
different speeds on 60Hz vs 120Hz screens!

SOLUTION: Use the timestamp to calculate how much time has passed:

  class Animator {
    constructor() {
      this.startTime = null;
      this.duration = 1000; // 1 second animation
      this.rafId = null;
    }
    
    start() {
      this.startTime = null;
      this.rafId = requestAnimationFrame((ts) => this.frame(ts));
    }
    
    frame(timestamp) {
      if (!this.startTime) this.startTime = timestamp;
      
      const elapsed = timestamp - this.startTime;
      const progress = Math.min(elapsed / this.duration, 1); // 0 to 1
      
      // Easing function (ease-out cubic)
      const eased = 1 - Math.pow(1 - progress, 3);
      
      // Apply animation (moves 500px over 1 second)
      this.element.style.transform = `translateX(${eased * 500}px)`;
      
      if (progress < 1) {
        // Still animating — request next frame
        this.rafId = requestAnimationFrame((ts) => this.frame(ts));
      } else {
        // Animation complete
        this.onComplete?.();
      }
    }
    
    stop() {
      cancelAnimationFrame(this.rafId);
    }
  }
  
  // Result: Exactly the same animation duration on ALL screen refresh rates!
  // 60Hz: ~60 frames over 1 second
  // 120Hz: ~120 frames over 1 second (same elapsed time, smoother motion)

FLIP ANIMATION TECHNIQUE
================================================================

FLIP stands for: First → Last → Invert → Play

The most PERFORMANT way to animate layout changes (like reordering a list),
because it only uses compositor-layer properties (transform, opacity).

  CONCEPT:
  1. FIRST: Record element's position BEFORE the layout change
  2. LAST: Apply the layout change, record element's NEW position
  3. INVERT: Apply a CSS transform to make element APPEAR to be in its old position
  4. PLAY: Remove the transform (with transition) — element animates to final position

  IMPLEMENTATION:
  function flipAnimate(element, layoutChange) {
    // FIRST: Capture starting position
    const first = element.getBoundingClientRect();
    
    // LAST: Apply the layout change
    layoutChange(); // e.g., reorder DOM, change CSS class
    
    // LAST: Capture ending position
    const last = element.getBoundingClientRect();
    
    // INVERT: Calculate transform to make it LOOK like it's in the old position
    const deltaX = first.left - last.left;
    const deltaY = first.top - last.top;
    const scaleX = first.width / last.width;
    const scaleY = first.height / last.height;
    
    // Apply inversion transform (snaps back visually to original position)
    element.style.transform = 
      `translate(${deltaX}px, ${deltaY}px) scale(${scaleX}, ${scaleY})`;
    element.style.transformOrigin = 'top left';
    
    // PLAY: In next frame, remove the transform (transition handles animation)
    requestAnimationFrame(() => {
      element.style.transition = 'transform 300ms ease';
      element.style.transform = 'none'; // Animate to final position!
      
      // Clean up after animation
      element.addEventListener('transitionend', () => {
        element.style.transition = '';
        element.style.transform = '';
      }, { once: true });
    });
  }
  
  // REACT FLIP EXAMPLE (simplified):
  function SortableList({ items }) {
    const refs = useRef({});
    const prevPositions = useRef({});
    
    // Before render: record positions
    useLayoutEffect(() => {
      items.forEach(item => {
        const el = refs.current[item.id];
        if (el) {
          prevPositions.current[item.id] = el.getBoundingClientRect();
        }
      });
    });
    
    // After render: FLIP animate
    useEffect(() => {
      items.forEach(item => {
        const el = refs.current[item.id];
        const prev = prevPositions.current[item.id];
        if (!el || !prev) return;
        
        const curr = el.getBoundingClientRect();
        const deltaX = prev.left - curr.left;
        const deltaY = prev.top - curr.top;
        
        if (deltaX === 0 && deltaY === 0) return; // Didn't move
        
        el.style.transform = `translate(${deltaX}px, ${deltaY}px)`;
        
        requestAnimationFrame(() => {
          el.style.transition = 'transform 300ms ease';
          el.style.transform = '';
          el.addEventListener('transitionend', () => {
            el.style.transition = '';
          }, { once: true });
        });
      });
    }, [items]);
    
    return (
      <ul>
        {items.map(item => (
          <li key={item.id} ref={el => refs.current[item.id] = el}>
            {item.name}
          </li>
        ))}
      </ul>
    );
  }

================================================================
BATCHING DOM READS AND WRITES WITH rAF
================================================================

Layout thrashing happens when you mix DOM reads and writes.
rAF can help batch operations:

  ❌ BAD — causes layout thrashing (reflow on every iteration):
  items.forEach(item => {
    const height = item.offsetHeight; // READ (triggers reflow if DOM is dirty)
    item.style.height = height * 2 + 'px'; // WRITE (makes DOM dirty)
  });

  ✅ GOOD — batch reads, then writes:
  // OPTION 1: Separate reads and writes in same frame
  const heights = items.map(item => item.offsetHeight); // All reads first
  items.forEach((item, i) => {
    item.style.height = heights[i] * 2 + 'px'; // All writes after
  });
  
  // OPTION 2: Use two rAF calls (read now, write next frame)
  function updateHeights(items) {
    // READ phase in current frame
    const heights = items.map(item => item.offsetHeight);
    
    // WRITE phase in next frame (guaranteed fresh layout)
    requestAnimationFrame(() => {
      items.forEach((item, i) => {
        item.style.height = heights[i] * 2 + 'px';
      });
    });
  }
  
  // OPTION 3: FastDOM library (popular solution)
  // import FastDOM from 'fastdom';
  // fastdom.measure(() => { const h = el.offsetHeight; });
  // fastdom.mutate(() => { el.style.height = '100px'; });

================================================================
rAF FOR SCROLL AND INPUT THROTTLING
================================================================

Earlier in 02_Debounce_and_Throttle.txt we covered RAF-based throttle.
This is the preferred approach for visual updates tied to user input:

  // RAF Throttle — runs AT MOST once per frame
  function rafThrottle(fn) {
    let rafId = null;
    
    return function (...args) {
      if (rafId) return; // Already scheduled for this frame
      
      rafId = requestAnimationFrame(() => {
        fn.apply(this, args);
        rafId = null; // Ready for next frame
      });
    };
  }
  
  // Usage:
  const handleScroll = rafThrottle((e) => {
    // Update sticky header, parallax, etc.
    const scrollY = window.scrollY;
    header.style.opacity = Math.max(0, 1 - scrollY / 200);
  });
  
  window.addEventListener('scroll', handleScroll, { passive: true });

WEB ANIMATIONS API (WAAPI) — THE MODERN ALTERNATIVE
================================================================

WAAPI runs animations on the COMPOSITOR THREAD (off main thread!).
No JavaScript frame loop needed for CSS-animatable properties.

  // WAAPI example:
  const animation = element.animate(
    [
      { transform: 'translateX(0px)', opacity: 1 },
      { transform: 'translateX(500px)', opacity: 0 }
    ],
    {
      duration: 1000,
      easing: 'cubic-bezier(0.4, 0, 0.2, 1)',
      fill: 'forwards',
      iterations: 1
    }
  );
  
  // Control playback:
  animation.pause();
  animation.play();
  animation.reverse();
  animation.cancel();
  
  // Promise-based (resolves when animation finishes):
  await animation.finished;
  // OR
  animation.onfinish = () => console.log('Done!');
  
  // React hook for WAAPI:
  function useAnimation(ref, keyframes, options) {
    const animationRef = useRef(null);
    
    const play = useCallback(() => {
      if (!ref.current) return;
      animationRef.current = ref.current.animate(keyframes, options);
      return animationRef.current.finished;
    }, [keyframes, options]);
    
    const pause = useCallback(() => animationRef.current?.pause(), []);
    const cancel = useCallback(() => animationRef.current?.cancel(), []);
    
    return { play, pause, cancel };
  }
  
  // WHEN TO USE WAAPI vs rAF:
  // WAAPI: CSS-animatable properties (transform, opacity, color, etc.)
  //        → Compositor thread, hardware accelerated, no JS loop!
  //
  // rAF:   Custom logic, canvas rendering, physics, complex state,
  //        or properties WAAPI can't animate (like scrollTop)

REACT + rAF PATTERNS
================================================================

  // useAnimationFrame hook:
  function useAnimationFrame(callback) {
    const savedCallback = useRef(callback);
    
    useEffect(() => {
      savedCallback.current = callback;
    }, [callback]);
    
    useEffect(() => {
      let startTime = null;
      let rafId;
      
      function frame(timestamp) {
        if (!startTime) startTime = timestamp;
        const elapsed = timestamp - startTime;
        
        savedCallback.current(elapsed);
        rafId = requestAnimationFrame(frame);
      }
      
      rafId = requestAnimationFrame(frame);
      return () => cancelAnimationFrame(rafId);
    }, []);
  }
  
  // Usage:
  function AnimatedCounter() {
    const [count, setCount] = useState(0);
    const counterRef = useRef(0);
    
    useAnimationFrame((elapsed) => {
      const newCount = Math.floor(elapsed / 100); // Increment every 100ms
      if (newCount !== counterRef.current) {
        counterRef.current = newCount;
        setCount(newCount); // Only setState when value actually changes
      }
    });
    
    return <div>{count}</div>;
  }

  // IMPORTANT: Avoid setState every frame! It's expensive.
  // For animations, prefer direct DOM manipulation or CSS custom properties:
  
  function useParallax() {
    const elementRef = useRef(null);
    
    useEffect(() => {
      const handleScroll = rafThrottle(() => {
        if (elementRef.current) {
          // Direct DOM manipulation — no React re-render!
          elementRef.current.style.transform =
            `translateY(${window.scrollY * 0.5}px)`;
        }
      });
      
      window.addEventListener('scroll', handleScroll, { passive: true });
      return () => window.removeEventListener('scroll', handleScroll);
    }, []);
    
    return elementRef;
  }

================================================================
INTERVIEW ANSWERS
================================================================

Q: What's the difference between requestAnimationFrame and setTimeout(fn, 16)?
A: rAF synchronizes with the display refresh rate — if the screen refreshes
   at 60Hz, rAF fires every 16.67ms; at 120Hz, every 8.33ms. setTimeout(fn, 16)
   fires approximately every 16ms but doesn't sync with the display cycle,
   causing potential frame skips or double-painting. rAF also automatically
   pauses when the tab is hidden (saving CPU/battery), while setTimeout keeps
   firing. Finally, rAF provides a high-precision timestamp, making frame-rate-
   independent animations straightforward. Use rAF for anything that needs to
   update the screen; use setTimeout for non-visual timing.

Q: How does the FLIP animation technique improve performance?
A: FLIP (First, Last, Invert, Play) works by letting the browser perform the
   layout change instantly (cheap), then using CSS transforms to animate the
   visual transition. CSS transforms only trigger compositing — they don't
   cause reflow or repaint, making them run on the GPU at 60fps. Without FLIP,
   animating layout properties like 'left', 'top', 'width', or 'height' triggers
   layout + paint on every frame, which is expensive. FLIP "tricks" the browser
   by snapping an element to its old visual position with a transform, then
   transitioning the transform away — visually identical to animating the layout
   property, but running on the compositor thread. Libraries like Framer Motion
   use this technique internally for 'layout' prop animations.

Q: When should you use Web Animations API instead of rAF?
A: Web Animations API (WAAPI) is preferable when animating CSS-animatable
   properties like transform and opacity. WAAPI runs these on the compositor
   thread — completely off the main thread — so even if your main thread is
   busy with JS, the animation continues smoothly. rAF is better for:
   (1) Canvas rendering, (2) complex physics where you need JS calculations
   each frame, (3) animating non-CSS properties like scroll position or
   custom data visualizations, or (4) when you need precise control over
   timing logic. A common pattern: use WAAPI for UI transitions/microinteractions
   (button press, modal open) and rAF for game loops or data visualization.

Q: How do you prevent calling setState every frame in React animations?
A: React re-renders are expensive — calling setState at 60fps triggers 60
   reconciliations per second. For smooth animations, bypass React's
   state system entirely: (1) Use direct DOM manipulation via refs
   (element.style.transform = ...), (2) Use CSS custom properties
   (element.style.setProperty('--offset', value)), (3) Use the Web Animations
   API which operates outside React's control. Only use setState when the
   animation COMPLETES or when the value actually matters for other components.
   React 18's useTransition can help de-prioritize animation-triggered updates,
   but for frame-by-frame animation, direct DOM mutation via refs is the
   right pattern.
