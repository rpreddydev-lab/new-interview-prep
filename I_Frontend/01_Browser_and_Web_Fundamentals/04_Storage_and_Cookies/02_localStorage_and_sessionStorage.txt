================================================================================
  localStorage & sessionStorage — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. OVERVIEW
────────────────────────────────────────────────────────────────────────────────

  Both are part of the Web Storage API (HTML5).
  Key-value stores accessible via JavaScript.
  Store strings only (primitives must be stringified).

  window.localStorage   → persists across browser sessions
  window.sessionStorage → persists for the tab's lifetime only

────────────────────────────────────────────────────────────────────────────────
2. localStorage
────────────────────────────────────────────────────────────────────────────────

  Characteristics:
    • Persists until explicitly cleared
    • Shared across all tabs/windows of the same origin
    • Survives browser restarts
    • Synchronous API (blocking!)
    • Origin-scoped (same protocol + host + port)
    • Capacity: ~5-10MB (varies by browser, typically 5MB)

  API:
    localStorage.setItem('key', 'value');
    localStorage.getItem('key');      // returns string or null
    localStorage.removeItem('key');
    localStorage.clear();             // removes ALL keys
    localStorage.length;              // number of items
    localStorage.key(0);              // get key at index

  Storing objects (must serialize):
    const user = { name: 'Alice', age: 30 };
    localStorage.setItem('user', JSON.stringify(user));
    const user = JSON.parse(localStorage.getItem('user'));

  Common use cases:
    • User preferences (theme, language, settings)
    • Shopping cart contents
    • Draft content
    • Auth tokens (caution — see security section)
    • Application state (non-sensitive)

────────────────────────────────────────────────────────────────────────────────
3. sessionStorage
────────────────────────────────────────────────────────────────────────────────

  Characteristics:
    • Persists for the duration of the tab/window session
    • Cleared when tab is closed
    • NOT shared between tabs (each tab has its own sessionStorage)
    • Survives page refreshes within the same tab
    • Same synchronous API as localStorage
    • Capacity: ~5MB

  API: identical to localStorage
    sessionStorage.setItem('key', 'value');
    sessionStorage.getItem('key');
    sessionStorage.removeItem('key');
    sessionStorage.clear();

  Common use cases:
    • Multi-step form data (don't want to persist after leaving)
    • Temporary UI state
    • Tab-specific session data (e.g., a specific wizard flow state)

  Tab duplication behavior:
    When a user duplicates a tab (Ctrl+Shift+K / Cmd+Shift+K):
    The new tab gets a copy of the original tab's sessionStorage at
    the time of duplication — but they are independent going forward.

────────────────────────────────────────────────────────────────────────────────
4. COMPARISON: localStorage vs sessionStorage
────────────────────────────────────────────────────────────────────────────────

  ┌──────────────────────┬───────────────────────┬──────────────────────────┐
  │ Feature              │ localStorage          │ sessionStorage           │
  ├──────────────────────┼───────────────────────┼──────────────────────────┤
  │ Persistence          │ Until manually cleared│ Until tab closes         │
  │ Scope                │ All tabs, same origin │ Current tab only         │
  │ Capacity             │ ~5-10MB               │ ~5MB                     │
  │ Survives restart     │ Yes                   │ No (tab must stay open)  │
  │ Shared between tabs  │ Yes                   │ No                       │
  │ API                  │ Synchronous           │ Synchronous              │
  │ Storage event        │ Fires in other tabs   │ Fires only in same tab   │
  └──────────────────────┴───────────────────────┴──────────────────────────┘

────────────────────────────────────────────────────────────────────────────────
5. STORAGE EVENT (Cross-Tab Communication)
────────────────────────────────────────────────────────────────────────────────

  When localStorage is modified, a 'storage' event fires in ALL OTHER TABS
  of the same origin (NOT the tab that made the change).

    window.addEventListener('storage', (event) => {
      console.log(event.key);      // changed key (null if .clear() called)
      console.log(event.oldValue); // previous value
      console.log(event.newValue); // new value (null if deleted)
      console.log(event.url);      // URL of the tab that made the change
      console.log(event.storageArea); // localStorage or sessionStorage
    });

  Use case: sync state across multiple tabs (e.g., logout user from all tabs).
    // In one tab:
    localStorage.setItem('logout', Date.now());
    // In other tabs (via storage event listener):
    window.addEventListener('storage', e => {
      if (e.key === 'logout') window.location.reload();
    });

  Note: sessionStorage storage events only fire within the same tab (less useful).

────────────────────────────────────────────────────────────────────────────────
6. SECURITY CONSIDERATIONS
────────────────────────────────────────────────────────────────────────────────

  Both localStorage and sessionStorage are:
    ✗ Accessible to ALL JavaScript running on the page
    ✗ Vulnerable to XSS attacks
    ✓ Not sent automatically with HTTP requests (unlike cookies)
    ✗ Not accessible by server directly
    ✗ No expiry mechanism (localStorage)

  Auth tokens in localStorage:
    RISKY: Any XSS attack can read localStorage.
    Attackers inject script → steal token → impersonate user.

  Safer alternative:
    HttpOnly Secure cookie (inaccessible to JS) for sensitive tokens.

  Never store in localStorage:
    • Auth tokens / JWTs (if XSS is a concern)
    • Passwords
    • Credit card numbers
    • Personal Identifiable Information (PII)

────────────────────────────────────────────────────────────────────────────────
7. SYNCHRONOUS NATURE AND PERFORMANCE
────────────────────────────────────────────────────────────────────────────────

  Both APIs are synchronous — they BLOCK the main thread.
  Reading/writing large data can cause jank.

    // This blocks the main thread for the duration:
    const bigData = localStorage.getItem('largeObject'); // parse 2MB JSON?

  Best practices:
    • Keep stored values small
    • Avoid calling in tight loops
    • For large structured data: use IndexedDB (async)
    • Consider serialization cost (JSON.stringify/parse of complex objects)

  localStorage is NOT available in:
    • Web Workers (no window access)
    • Service Workers
    • Use IndexedDB or Cache API in workers

────────────────────────────────────────────────────────────────────────────────
8. STORAGE QUOTA AND ERRORS
────────────────────────────────────────────────────────────────────────────────

  When quota exceeded, setItem throws:
    try {
      localStorage.setItem('bigData', largeString);
    } catch (e) {
      if (e.name === 'QuotaExceededError') {
        console.error('Storage quota exceeded');
        // Clear old data or ask user
      }
    }

  Checking available quota (modern):
    const estimate = await navigator.storage.estimate();
    console.log(estimate.quota);  // total available bytes
    console.log(estimate.usage);  // bytes currently used
    // Note: estimate.usage covers ALL origins storage, not just localStorage

────────────────────────────────────────────────────────────────────────────────
9. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between localStorage and sessionStorage?
A: localStorage persists until explicitly cleared and is shared across all
   tabs of the same origin. sessionStorage is scoped to the current tab and
   cleared when the tab closes. Both have the same synchronous API and ~5MB
   capacity. sessionStorage is tab-isolated; localStorage fires storage
   events to other tabs on changes.

Q: What is the difference between localStorage and cookies?
A: localStorage: larger (~5MB), JS-only, not auto-sent with HTTP requests,
   no expiry. Cookies: smaller (4KB), auto-sent with every request (used
   for auth), have Secure/HttpOnly/SameSite attributes for security, can be
   set by server. LocalStorage is vulnerable to XSS; HttpOnly cookies are
   not.

Q: Is it safe to store JWT tokens in localStorage?
A: It's not recommended for sensitive tokens because localStorage is
   accessible to any JavaScript on the page, making it vulnerable to XSS
   attacks. A better approach is HttpOnly Secure SameSite cookies — the
   token is automatically sent with requests but is inaccessible to JS.

Q: How can you use localStorage for cross-tab communication?
A: Write a value to localStorage and listen for the 'storage' event in other
   tabs. The event fires in all tabs of the same origin EXCEPT the one that
   made the change. Example: logout all tabs simultaneously by setting a
   'logout' key and handling it in a storage event listener.

Q: What happens if you exceed localStorage quota?
A: setItem() throws a QuotaExceededError (DOMException). You should wrap
   writes in try/catch and handle the error gracefully — perhaps by clearing
   stale data or notifying the user.

Q: Why can't Service Workers use localStorage?
A: Service Workers run in a separate thread with no access to the window
   object. localStorage is part of the Window interface. Service Workers
   should use IndexedDB or the Cache API, both of which support async
   operations and are accessible from workers.

Q: How does sessionStorage behave when duplicating a tab?
A: When a user duplicates a browser tab, the new tab receives a copy of
   the original's sessionStorage at that moment. After duplication, the
   two sessionStorages are completely independent — changes in one don't
   affect the other.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • localStorage: persistent, origin-shared, ~5MB, synchronous, fires storage events
  • sessionStorage: tab-scoped, clears on tab close, ~5MB, synchronous
  • Both accessible to JS → XSS risk → don't store sensitive auth tokens
  • Cookies with HttpOnly are safer for auth tokens
  • Use 'storage' event for cross-tab communication via localStorage
  • Use IndexedDB for large data, complex queries, or non-main-thread access
