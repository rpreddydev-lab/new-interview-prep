1. BROWSER STORAGE MECHANISMS OVERVIEW
────────────────────────────────────────────────────────────────────────────────

  Modern browsers provide multiple storage mechanisms, each with different
  trade-offs in terms of capacity, API style, persistence, security, and
  use cases.

  Mechanisms covered:
    1. Cookies
    2. localStorage
    3. sessionStorage
    4. IndexedDB
    5. Cache API
    6. Memory (in-page JavaScript variables — not persistent)

3. USE CASE MATRIX
────────────────────────────────────────────────────────────────────────────────

  ┌────────────────────────────────────────┬─────────────────────────────────────┐
  │ Use Case                               │ Recommended Storage                 │
  ├────────────────────────────────────────┼─────────────────────────────────────┤
  │ Auth token / session ID                │ HttpOnly Secure cookie              │
  │ User preferences (theme, lang)         │ localStorage                        │
  │ Shopping cart (non-sensitive)          │ localStorage                        │
  │ Multi-step form (page-scoped)          │ sessionStorage                      │
  │ Tab-specific wizard state              │ sessionStorage                      │
  │ Large dataset (products, offline data) │ IndexedDB                           │
  │ Offline app assets (CSS, JS, HTML)     │ Cache API (Service Worker)          │
  │ Push notification subscription         │ IndexedDB (SW stores it)            │
  │ Binary data (images, audio)            │ IndexedDB (Blob) or Cache API       │
  │ Cross-tab logout                       │ localStorage + storage event        │
  │ Server-side personalization            │ Cookies (sent with requests)        │
  │ Tracking & analytics                   │ Cookies (historically, now complex) │
  └────────────────────────────────────────┴─────────────────────────────────────┘

4. CAPACITY AND QUOTA
────────────────────────────────────────────────────────────────────────────────

  Cookies:
    4KB per cookie; ~50 cookies per domain; not for data storage

  localStorage:
    5-10MB (varies by browser); typically 5MB in most browsers
    iOS Safari: 5MB; Desktop Chrome/Firefox: 10MB

  sessionStorage:
    ~5MB (same as localStorage)

  IndexedDB:
    Starts with a fixed minimum, then grows up to ~60% of available disk
    No hard limit; browser manages quota across origins
    Origin Quota group: IndexedDB + Cache API + localStorage share a pool

  Cache API:
    Shares quota with IndexedDB. Up to 60% of disk.
    Can request persistent storage with navigator.storage.persist()

  Checking quota:
    const { quota, usage } = await navigator.storage.estimate();
    console.log(`Used: ${usage} / ${quota} bytes`);

5. SECURITY COMPARISON
────────────────────────────────────────────────────────────────────────────────

  XSS Vulnerability:
    ┌───────────────┬────────────────────────────────────────────────┐
    │ Storage       │ XSS Protection                                 │
    ├───────────────┼────────────────────────────────────────────────┤
    │ Cookie        │ HttpOnly = FULLY protected (JS can't read it)  │
    │ localStorage  │ NOT protected (any JS on page can read)        │
    │ sessionStorage│ NOT protected                                  │
    │ IndexedDB     │ NOT protected (any JS can query it)            │
    │ Cache API     │ JS can access, but typically SW-managed        │
    └───────────────┴────────────────────────────────────────────────┘
    
  CSRF Vulnerability:
    ┌───────────────┬────────────────────────────────────────────────┐
    │ Storage       │ CSRF Risk                                      │
    ├───────────────┼────────────────────────────────────────────────┤
    │ Cookie        │ YES — auto-sent with cross-origin requests     │
    │               │ (mitigate: SameSite=Strict/Lax)               │
    │ localStorage  │ No — not auto-sent; manually attached to fetch │
    │ sessionStorage│ No                                             │
    │ IndexedDB     │ No                                             │
    └───────────────┴────────────────────────────────────────────────┘

  Recommendation for sensitive auth data:
    Best: HttpOnly Secure SameSite=Strict cookie (protected from XSS + CSRF)
    Avoid: localStorage for JWT/auth tokens (XSS vulnerable)

6. API STYLE COMPARISON
────────────────────────────────────────────────────────────────────────────────

  Synchronous (main thread blocking):
    • localStorage
    • sessionStorage
    • document.cookie

  Asynchronous:
    • IndexedDB (event-based; use wrappers like idb for Promise API)
    • Cache API (Promise-based)
    • Cookie Store API (modern, Promise-based, experimental)

  Worker availability:
    • Web Workers and Service Workers: CANNOT use localStorage, sessionStorage, document.cookie
    • CAN use: IndexedDB, Cache API

7. ORIGIN ISOLATION
────────────────────────────────────────────────────────────────────────────────

  Origin = protocol + hostname + port

  All browser storage is origin-scoped:
    https://example.com and http://example.com → different origins
    https://example.com and https://sub.example.com → different origins
    https://example.com:3000 and https://example.com:4000 → different origins

  Exception — Cookies:
    Domain attribute can span subdomains: Domain=.example.com
    But cannot cross to other domains (example.com ≠ other.com)

  Incognito / Private Mode:
    Storage exists for the session but is cleared when private window closes.
    Storage events and cross-tab sharing may behave differently.

9. DECISION FLOWCHART
────────────────────────────────────────────────────────────────────────────────

  When deciding which storage to use:

  ┌─────────────────────────────────────────────────────┐
  │ Does the server need to receive it automatically?   │
  │   YES → Use Cookie                                  │
  │   NO ↓                                              │
  │ Is it sensitive (auth token, session)?              │
  │   YES → HttpOnly cookie (NOT localStorage)          │
  │   NO ↓                                              │
  │ Is it tab-specific / temporary?                     │
  │   YES → sessionStorage                              │
  │   NO ↓                                              │
  │ Is it large / structured / binary / needs queries?  │
  │   YES → IndexedDB                                   │
  │ Is it network resources (HTML, JS, images)?         │
  │   YES → Cache API (Service Worker)                  │
  │ Is it small, simple, key-value, persistent?         │
  │   YES → localStorage                                │
  └─────────────────────────────────────────────────────┘

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What are the different storage options in the browser and when do you use each?
A: Cookies (4KB): auto-sent with requests, server access, expiry control —
   for auth/session. localStorage (~5MB): persistent, same-origin, sync JS —
   for user preferences, non-sensitive state. sessionStorage (~5MB): tab-scoped,
   temporary — for multi-step forms. IndexedDB (large): async, structured,
   indexed — for offline apps, large datasets. Cache API (large): Request/Response
   pairs — for offline assets in Service Workers.

Q: Where should you store a JWT access token?
A: Ideally in an HttpOnly Secure SameSite=Strict cookie set by the server.
   This prevents XSS (HttpOnly = inaccessible to JS) and CSRF (SameSite).
   If using localStorage, it's convenient but any XSS attack can steal the
   token. A common pattern: short-lived access token in memory (variable),
   refresh token in HttpOnly cookie.

Q: What is the maximum size of localStorage?
A: Approximately 5MB in most browsers (some allow 10MB). It varies by browser
   and can be configured by users. The exact limit is per origin. Exceeding
   the limit throws a QuotaExceededError.

Q: Can a Web Worker access localStorage?
A: No. Web Workers (and Service Workers) do not have access to the window
   object or any window-dependent APIs. localStorage and sessionStorage are
   not accessible from workers. Use IndexedDB or Cache API (both async, 
   worker-compatible) instead.

Q: What is the difference between Cache API and the HTTP cache?
A: HTTP cache is browser-managed based on response headers (Cache-Control,
   ETag). Developers can hint but not fully control it. Cache API is developer-
   controlled, primarily via Service Workers. Developers can write custom
   caching logic (Cache-First, Network-First, Stale-While-Revalidate), store
   any response regardless of headers, and manage invalidation manually.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Cookies: auto-sent to server; 4KB; use HttpOnly+Secure+SameSite for auth
  • localStorage: persistent, 5-10MB, sync, cross-tab, NO expiry
  • sessionStorage: tab-scoped, ~5MB, clears on tab close
  • IndexedDB: async, large capacity, structured queries, worker-accessible
  • Cache API: Request/Response pairs, offline strategies, worker-accessible
  • Auth tokens → HttpOnly cookie; user preferences → localStorage
  • All storage is origin-scoped; IndexedDB + Cache API share disk quota
================================================================================
