1. WHAT IS CLICKJACKING?
────────────────────────────────────────────────────────────────────────────────

  Clickjacking (UI Redressing) is an attack where a malicious site tricks
  users into clicking on something different from what they perceive.

  Attack mechanism:
    1. Attacker creates a page with an invisible <iframe> overlaying their UI
    2. The iframe loads a legitimate target site (e.g., bank.com)
    3. The iframe is transparent (opacity: 0) but positioned over a fake button
    4. User thinks they're clicking "Win a Prize" but actually clicking bank.com's
       "Transfer Funds" button

  What attackers can achieve:
    • Unauthorized button clicks (account deletion, purchases, transfers)
    • Stealing clicks on ads
    • Capturing webcam/microphone permission grants
    • Social engineering (Like on Facebook, Follow on Twitter)
    • Form submission on behalf of user

  Example attack HTML:
    <style>
      #target {
        position: absolute;
        top: 0; left: 0;
        width: 100%; height: 100%;
        opacity: 0;         /* invisible */
        z-index: 99;        /* on top */
      }
      #decoy {
        position: absolute;
        top: 200px; left: 300px;
      }
    </style>
    <div id="decoy">🎉 Click here to win a prize!</div>
    <iframe id="target" src="https://bank.com/transfer-page"></iframe>

2. DEFENSES AGAINST CLICKJACKING
────────────────────────────────────────────────────────────────────────────────

  2.1 X-Frame-Options Header (older standard)
    Tells browsers whether the page can be embedded in a frame.
    
    X-Frame-Options: DENY
      Page cannot be framed at all (by any origin).
    
    X-Frame-Options: SAMEORIGIN
      Page can only be framed by the same origin.
    
    X-Frame-Options: ALLOW-FROM https://trusted.com
      Allow only a specific origin. (Deprecated/limited browser support)
    
    Limitations:
      • No wildcard support
      • ALLOW-FROM poorly supported
      • Cannot specify multiple origins
      • Can be bypassed in certain scenarios (double framing attack in old browsers)

  2.2 Content-Security-Policy: frame-ancestors (modern standard)
    More powerful replacement for X-Frame-Options.
    
    frame-ancestors 'none':
      No framing allowed (equivalent to DENY).
    
    frame-ancestors 'self':
      Same-origin framing only (equivalent to SAMEORIGIN).
    
    frame-ancestors https://trusted.com https://partner.com:
      Allow specific origins (multiple allowed — not possible with XFO).
    
    Content-Security-Policy: frame-ancestors 'none'
    
    Advantages over X-Frame-Options:
      ✓ Supports multiple origins
      ✓ Handles complex scenarios (nested frames)
      ✓ Consistent across modern browsers
      ✓ More expressive syntax

  2.3 Frame Busting JavaScript (legacy, unreliable)
    JavaScript techniques to break out of frames.
    
    Basic frame buster:
      if (window !== window.top) {
        window.top.location = window.location;
      }
    
    Better version:
      if (top !== self) {
        top.location.replace(self.location.href);
      }
    
    Problems with JS frame busting:
      • Can be defeated by sandbox attribute:
        <iframe sandbox="allow-scripts" src="victim.com">
        (sandbox without allow-top-navigation prevents frame buster from working)
      • Can be defeated with onbeforeunload interception
      • Modern browsers may restrict window.top assignment from cross-origin frames
      • Unreliable compared to HTTP headers
    
    Conclusion: JS frame busting is not a reliable defense. Use HTTP headers.

────────────────────────────────────────────────────────────────────────────────
3. FRAME SANDBOX ATTRIBUTE
────────────────────────────────────────────────────────────────────────────────

  The <iframe sandbox> attribute applies restrictions to framed content.
  Used legitimately to safely embed untrusted content.
  
  Restricts (by default with sandbox):
    - Scripts
    - Forms
    - Popups
    - Same-origin access
    - Top-level navigation
  
  Can selectively re-enable:
    sandbox="allow-scripts allow-forms allow-same-origin allow-top-navigation"
  
  Note: sandbox can ALSO be used by attackers to defeat JS frame busters!
  That's why HTTP headers are the only reliable clickjacking defense.

────────────────────────────────────────────────────────────────────────────────
4. VARIANTS OF CLICKJACKING
────────────────────────────────────────────────────────────────────────────────

  Likejacking:
    Invisible Facebook Like button overlaid on content.
    User clicks "Play" but triggers a Facebook Like.

  Cursorjacking:
    Attacker shows a fake cursor offset from the real cursor.
    User thinks they're clicking one location but actually clicking another.

  Filejacking / Permission Clickjacking:
    Trick users into granting webcam, microphone, location permissions
    via browser permission dialogs overlaid under fake UI.

  Drag-and-drop Clickjacking:
    Invisible iframes can steal clipboard or text via drag operations.

  Scrolljacking (related):
    Hijacking the user's scroll events to manipulate page behavior.
    Less about security, more about bad UX.

────────────────────────────────────────────────────────────────────────────────
5. BROWSER BEHAVIOR
────────────────────────────────────────────────────────────────────────────────

  When X-Frame-Options or CSP frame-ancestors is set:
    Browser refuses to render the page inside an <iframe>.
    Error shown in console: "Refused to display '[URL]' in a frame because 
    it set 'X-Frame-Options' to 'DENY'."

  Interaction between XFO and CSP frame-ancestors:
    If both are set, frame-ancestors takes precedence in modern browsers.
    Keep both for maximum compatibility with older browsers.

6. IMPLEMENTING CLICKJACKING PROTECTION
────────────────────────────────────────────────────────────────────────────────

  Recommended headers:
    // For most apps (no framing needed):
    Content-Security-Policy: frame-ancestors 'none'
    X-Frame-Options: DENY
    
    // For apps that frame themselves (e.g., embedded widget):
    Content-Security-Policy: frame-ancestors 'self'
    X-Frame-Options: SAMEORIGIN
    
    // For apps that allow trusted third-party embedding:
    Content-Security-Policy: frame-ancestors 'self' https://partner.com

  Express.js:
    // Helmet.js handles this:
    const helmet = require('helmet');
    app.use(helmet.frameguard({ action: 'deny' }));
    app.use(helmet.contentSecurityPolicy({
      directives: {
        frameAncestors: ["'none'"]
      }
    }));

  Nginx:
    add_header X-Frame-Options "DENY";
    add_header Content-Security-Policy "frame-ancestors 'none'";

7. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is clickjacking?
A: Clickjacking is a UI redressing attack where a malicious site embeds the
   target site in an invisible or transparent <iframe> over fake UI elements.
   The user thinks they're interacting with the visible fake content, but
   their clicks go to the hidden legitimate site underneath. This can cause
   unintended actions like transfers, likes, or permission grants.

Q: How do you prevent clickjacking?
A: Using HTTP headers: (1) X-Frame-Options: DENY or SAMEORIGIN — prevents
   browsers from embedding the page in a frame. (2) CSP frame-ancestors
   'none' or 'self' — modern, more powerful alternative. Use both for
   compatibility. JavaScript frame busters are unreliable and can be defeated
   with the iframe sandbox attribute.

Q: What is the difference between X-Frame-Options and CSP frame-ancestors?
A: Both prevent framing, but frame-ancestors is more powerful: it supports
   multiple specific origins, uses the modern CSP syntax, and handles complex
   frame nesting correctly. X-Frame-Options is simpler but limited: no
   multiple origins, ALLOW-FROM is poorly supported, and can be bypassed in
   some scenarios. Use both for backward compatibility.

Q: Why is JavaScript frame busting unreliable?
A: An attacker can embed the victim page with <iframe sandbox="allow-scripts">
   which prevents top-level navigation (the main technique in frame busters).
   The frame buster code runs but can't break out of the frame. HTTP headers
   are enforced by the browser before any JS runs, making them far more reliable.

Q: What is the iframe sandbox attribute and how can it be misused?
A: sandbox adds security restrictions to embedded iframe content by default
   (no scripts, no forms, no same-origin access). You can selectively re-enable
   features with tokens. Attackers can misuse it by embedding a site with
   sandbox="allow-scripts" — this blocks the frame buster (which needs
   allow-top-navigation) while still displaying the site to overlay UI elements.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Clickjacking: invisible iframe trick to capture user clicks
  • Best defense: X-Frame-Options: DENY + CSP frame-ancestors 'none'
  • CSP frame-ancestors > X-Frame-Options (supports multiple origins)
  • JS frame busting is unreliable — can be defeated with sandbox attribute
  • frame-ancestors 'none' → no framing; 'self' → same-origin only
  • Use Helmet.js in Node.js apps to set these headers easily
