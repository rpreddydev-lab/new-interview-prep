================================================================================
  RENDERING PIPELINE — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. OVERVIEW OF THE RENDERING PIPELINE
────────────────────────────────────────────────────────────────────────────────

  The rendering pipeline converts HTML/CSS/JS into pixels on screen.
  Understanding it is crucial for performance optimization.

  Full Pipeline:
    Parse → Style → Layout → Paint → Composite

  ┌────────────────────────────────────────────────────────────────────┐
  │  HTML     → [Parser] → DOM                                         │
  │  CSS      → [Parser] → CSSOM                                       │
  │  DOM + CSSOM → [Style] → Render Tree                               │
  │  Render Tree → [Layout] → Geometry (positions & sizes)             │
  │  Geometry → [Paint] → Paint Records (draw calls)                  │
  │  Paint Records → [Raster] → Pixels per layer                       │
  │  Layers → [Composite] → Final screen image                         │
  └────────────────────────────────────────────────────────────────────┘

────────────────────────────────────────────────────────────────────────────────
2. STEP 1 — PARSE (HTML + CSS)
────────────────────────────────────────────────────────────────────────────────

  HTML Parsing:
    - Tokenizer → Tree Builder → DOM
    - Incremental (starts with first byte)
    - Parser blocking: synchronous <script> halts parsing
    - Speculative parser: scans ahead for resources to prefetch

  CSS Parsing:
    - Downloaded CSS parsed in parallel with HTML
    - Fully render-blocking: browser waits for CSSOM before moving on
    - External stylesheets: blocking until downloaded + parsed
    - Inline <style>: blocking (but no network round trip)

────────────────────────────────────────────────────────────────────────────────
3. STEP 2 — STYLE (Recalculate Styles)
────────────────────────────────────────────────────────────────────────────────

  Goal: For every DOM node, determine the final value of every CSS property

  Process:
    1. Collect all CSS rules (from stylesheets, inline styles, user-agent styles)
    2. Match rules to DOM nodes (selector matching)
    3. Apply cascade (specificity, source order, !important)
    4. Compute inherited values
    5. Convert relative → absolute values (em → px, % → px)
    6. Result: each node has a ComputedStyle

  ComputedStyle:
    window.getComputedStyle(element) — read-only computed values
    element.style — only inline styles

  Style Invalidation:
    - JavaScript changes class/attribute → styles need recalculation
    - Adding/removing DOM nodes
    - Style recalc scope: can be limited (subtree) or full document

  Selector Performance:
    Browsers match selectors RIGHT TO LEFT:
    "div .card span a" → browser first finds all <a>, then checks parent etc.
    Avoid deep selectors: .a .b .c .d .e { } (expensive matching)
    ID selectors fastest, universal * slowest

────────────────────────────────────────────────────────────────────────────────
4. STEP 3 — LAYOUT (Reflow)
────────────────────────────────────────────────────────────────────────────────

  Goal: Calculate exact position (x,y) and size (width, height) of every element

  Layout Concepts:
    • Block Formatting Context (BFC):
      - Block-level elements stack vertically
      - Margin collapse between siblings/parent-child
    
    • Inline Formatting Context:
      - Inline elements flow in a line
      - Line boxes created for each line of text

    • Box Model Calculation:
      width: content-width + padding-left + padding-right (content-box)
      height from content flow + padding + border

    • Percentage values: resolved relative to containing block

  Layout Triggers (cause reflow):
    Geometry changes:
      - Changing width, height, margin, padding, border
      - Adding/removing DOM elements
      - Changing display, position, float
      - Changing font-size (affects text metrics and thus geometry)
    Reading layout-dependent properties:
      - element.offsetWidth / offsetHeight
      - element.clientWidth / clientHeight
      - element.scrollWidth / scrollHeight
      - element.getBoundingClientRect()
      - window.innerWidth / innerHeight
      - Reading these AFTER a style change forces synchronous layout!

  Layout Types:
    Full layout: whole document recalculated (rare, very expensive)
    Incremental/Dirty layout: only affected subtree recalculated

────────────────────────────────────────────────────────────────────────────────
5. STEP 4 — PAINT
────────────────────────────────────────────────────────────────────────────────

  Goal: Generate draw instructions for each visual element

  Paint records (display list) specify:
    - Background colors / images
    - Borders (color, style, radius)
    - Text (font, size, color, position)
    - Shadows (box-shadow, text-shadow)
    - Outlines
    - Images

  Paint Order (stacking context):
    1. Background color
    2. Background image
    3. Borders
    4. Children (sorted by z-index and stacking context)
    5. Outlines

  Properties that trigger repaint (but NOT reflow):
    color, background-color, border-color, visibility, outline, box-shadow

  Properties that skip layout AND paint:
    transform, opacity → only composite step (GPU accelerated)

  Stacking Context:
    Created by: position: absolute/relative/fixed/sticky + z-index ≠ auto,
    opacity < 1, transform, filter, will-change, isolation: isolate, etc.
    Each stacking context painted as a unit relative to its container.

────────────────────────────────────────────────────────────────────────────────
6. STEP 5 — COMPOSITE
────────────────────────────────────────────────────────────────────────────────

  Modern browsers separate page into LAYERS and composite them on GPU.

  Layer Promotion (what creates a new compositing layer):
    • will-change: transform (explicit hint to browser)
    • will-change: opacity
    • CSS transform animation
    • CSS opacity animation
    • position: fixed (in some browsers)
    • <canvas>, <video>
    • Stacking contexts with certain properties (3D transforms, etc.)

  Layer Compositing:
    - Each layer is separately rasterized (painted to a GPU texture)
    - Compositor thread combines layers to produce final frame
    - Happens on GPU → very fast, doesn't block main thread
    - Can run at 60fps even when JS is busy

  Why layers matter:
    • Animating transform/opacity = only compositing (no layout or paint)
    • This is why CSS animations on transform/opacity are always 60fps

  Layer Costs:
    - Too many layers = excessive memory (each is a GPU texture)
    - Don't blindly apply will-change everywhere!
    - Use only where smooth animation is needed

────────────────────────────────────────────────────────────────────────────────
7. RASTERIZATION
────────────────────────────────────────────────────────────────────────────────

  Process of converting paint instructions to actual pixels:
    - Runs on raster threads (multiple, parallel)
    - Can use GPU rasterization (Chrome's GPU process)
    - Output: bitmaps stored in GPU memory (tiles)

  Tiling:
    - Page divided into tiles (~256×256 pixels)
    - Tiles rasterized on demand (prioritize viewport)
    - Off-screen tiles may be discarded (memory management)

────────────────────────────────────────────────────────────────────────────────
8. FRAME BUDGET AND 60FPS
────────────────────────────────────────────────────────────────────────────────

  Budget: 1 second / 60 = 16.67ms per frame

  Frame Budget Breakdown (rough):
    JS execution:     ~3-4ms
    Style recalc:     ~1-2ms
    Layout:           ~1-2ms
    Paint:            ~1-2ms
    Composite/Raster: ~6-8ms
    Browser overhead: ~1ms

  If any step exceeds budget → DROPPED FRAME → JANK

  Measuring Frame Rate:
    Chrome DevTools → Performance tab → Frame timeline
    Frames shown as green bars; red = dropped

  requestAnimationFrame (rAF):
    - Schedule visual work to happen just before next paint
    - Callback receives DOMHighResTimeStamp
    - Cancelled with cancelAnimationFrame
    - Best practice for JS animations

  requestIdleCallback:
    - Schedule non-urgent work during idle periods
    - Receives IdleDeadline object with timeRemaining()
    - Runs after frame is complete and browser is idle

────────────────────────────────────────────────────────────────────────────────
9. LAYOUT THRASHING (FORCED SYNCHRONOUS LAYOUT)
────────────────────────────────────────────────────────────────────────────────

  Problem: Reading layout properties AFTER writing styles forces browser
  to synchronously complete layout before JS continues.

  Bad pattern (layout thrashing):
    for (let i = 0; i < elements.length; i++) {
      elements[i].style.left = elements[i].offsetLeft + 10 + 'px'; // READ then WRITE in loop
      // Each iteration: write style → read layout → forced sync layout
    }

  Correct pattern (batch reads then writes):
    // First read all values
    const lefts = elements.map(el => el.offsetLeft);
    // Then write all values
    elements.forEach((el, i) => el.style.left = lefts[i] + 10 + 'px');

  FastDOM library pattern:
    fastdom.measure(() => { const h = el.offsetHeight; })
    fastdom.mutate(() => { el.style.height = h + 'px'; })

────────────────────────────────────────────────────────────────────────────────
10. CSS PROPERTIES — PERFORMANCE CLASSIFICATION
────────────────────────────────────────────────────────────────────────────────

  EXPENSIVE (triggers Layout + Paint + Composite):
    width, height, margin, padding, border, top, left, right, bottom,
    display, position, float, font-size, overflow, font-weight

  MEDIUM (triggers Paint + Composite only — no layout):
    color, background-color, background-image, border-radius,
    box-shadow, outline, visibility

  CHEAP (triggers Composite only — no layout or paint):
    transform: translate/rotate/scale
    opacity
    filter (in some cases)
    will-change

  Rule of thumb:
    Animate transform and opacity for smooth GPU-accelerated animations
    Avoid animating width/height/top/left (expensive layout triggers)

────────────────────────────────────────────────────────────────────────────────
11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What are the steps in the browser rendering pipeline?
A: Parse HTML/CSS → Style (recalculate styles) → Layout (compute geometry) →
   Paint (generate draw calls) → Rasterize (pixels per layer tile) →
   Composite (GPU combines layers). Commonly summarized as:
   Parse → Style → Layout → Paint → Composite.

Q: Why is CSS render-blocking?
A: The browser must complete CSSOM construction before rendering because a
   single CSS rule can apply to many elements. Without full CSSOM, rendering
   would cause FOUC (Flash of Unstyled Content). CSS downloads and parsing
   happens in parallel with HTML but blocks the actual rendering (and JS
   execution).

Q: What is the difference between reflow (layout) and repaint?
A: Reflow (layout): triggered by geometry changes. Recalculates positions
   and dimensions of elements. Expensive (can cascade through DOM tree).
   Repaint: triggered by visual-only changes (color, background) that don't
   affect geometry. Less expensive than reflow but still involves GPU work.
   Some changes (transform, opacity) skip both — only compositing needed.

Q: What is layout thrashing?
A: When JS alternates between writing styles and reading layout properties
   (offsetWidth, getBoundingClientRect) in a loop. Each read after a write
   forces the browser to synchronously complete layout. Fix: batch all reads
   first, then all writes.

Q: Which CSS properties are most performant to animate?
A: transform and opacity — they only trigger the compositing step and are
   handled entirely on the GPU via the compositor thread. They don't require
   layout or paint recalculation. Avoid animating width/height/top/left as
   these trigger full layout.

Q: What is a compositing layer and when should you create one?
A: A compositing layer is a separate GPU texture for a DOM element, allowing
   the compositor thread to animate it without main thread involvement.
   Create one for elements that animate transform/opacity. Use will-change:
   transform to hint to the browser. Avoid excessive layers as they consume
   GPU memory.

Q: What is will-change?
A: A CSS property that hints to the browser that an element will be changed
   in a specific way (e.g., will-change: transform). Browser can promote
   the element to its own compositing layer in advance, enabling smooth
   animations. Use sparingly — too many layers waste GPU memory.

Q: What is requestAnimationFrame?
A: A browser API to schedule a callback to run just before the next paint
   (usually 60fps). Ideal for JS-driven animations as it synchronizes with
   the display refresh rate, prevents wasted frames if tab is backgrounded,
   and provides a high-res timestamp. Better than setTimeout for animations.

Q: What is the Compositor Thread?
A: A browser thread that handles compositing independently from the main
   thread. It can scroll the page and run CSS animations on transform/opacity
   at 60fps even when the JS main thread is busy. This is why CSS animations
   are smooth even during heavy JS work.

Q: Explain the concept of layers and why too many layers is bad.
A: Layers (compositing layers) are separate GPU textures for page regions.
   They enable smooth animations (compositor doesn't need main thread).
   But each layer uses GPU memory. Too many layers (e.g., will-change on
   hundreds of elements) can cause memory pressure, slow compositing, and
   worse performance than without layers.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Pipeline: Parse → Style → Layout → Paint → Raster → Composite
  • CSS is render-blocking (CSSOM must be complete before rendering)
  • Reflow (layout) is expensive; repaint less so; composite is cheapest
  • Animate transform/opacity: GPU-only (compositor thread), always 60fps
  • Avoid layout thrashing: batch reads before writes
  • will-change: hints layer promotion — use sparingly
  • rAF: schedule visual updates in sync with display refresh
