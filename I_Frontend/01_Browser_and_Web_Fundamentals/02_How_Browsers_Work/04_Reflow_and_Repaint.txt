================================================================================
  REFLOW AND REPAINT — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. DEFINITIONS
────────────────────────────────────────────────────────────────────────────────

  REFLOW (Layout):
    - Recalculating the position and size of all affected DOM elements
    - Also called "layout" in modern Chromium terminology
    - Triggered by changes that affect GEOMETRY
    - Affects the element AND possibly all descendants AND possibly ancestors
    - Most expensive rendering operation

  REPAINT:
    - Redrawing the visual representation of elements on screen
    - Triggered by changes that affect APPEARANCE but NOT geometry
    - Does NOT change size or position
    - Less expensive than reflow (no geometry recalculation)
    - Still requires new pixels to be painted and possibly uploaded to GPU

  COMPOSITE (no layout, no paint):
    - Only the compositor layer is updated
    - Entirely GPU-based
    - Cheapest operation

  Cost order: Composite < Repaint < Reflow

────────────────────────────────────────────────────────────────────────────────
2. WHAT TRIGGERS REFLOW?
────────────────────────────────────────────────────────────────────────────────

  GEOMETRY CHANGES:
    • Changing width, height, padding, margin, border-width
    • Changing top, right, bottom, left, position
    • Changing display, float, clear
    • Changing font-size, font-family, font-weight, line-height
    • Changing overflow properties
    • text-align changes
    • Adding or removing DOM elements
    • Changing an element's content (that affects dimensions)
    • Resizing the browser window
    • Pseudo-element changes affecting layout

  READING LAYOUT PROPERTIES (force synchronous layout):
    element.offsetWidth / offsetHeight / offsetTop / offsetLeft / offsetParent
    element.clientWidth / clientHeight / clientTop / clientLeft
    element.scrollWidth / scrollHeight / scrollTop / scrollLeft
    element.getBoundingClientRect()
    element.getClientRects()
    window.innerWidth / innerHeight
    window.scrollX / scrollY / pageXOffset / pageYOffset
    window.getComputedStyle(element) — in some cases
    document.documentElement.clientWidth

  Why reading causes reflow:
    Browser batches style changes and executes lazily.
    When you READ a layout value after making DOM/style changes,
    the browser MUST flush pending changes and complete layout
    to give you an accurate value.
    This is called "Forced Synchronous Layout" (FSL).

────────────────────────────────────────────────────────────────────────────────
3. WHAT TRIGGERS REPAINT?
────────────────────────────────────────────────────────────────────────────────

  VISUAL-ONLY CHANGES (no geometry):
    • color
    • background-color, background-image
    • border-color (already sized, just different color)
    • border-radius
    • box-shadow
    • text-shadow
    • outline
    • visibility: hidden → visible (note: visibility:hidden still occupies space)
    • cursor

  Note: Every REFLOW is followed by REPAINT
        Not every REPAINT follows a REFLOW

────────────────────────────────────────────────────────────────────────────────
4. WHAT ONLY TRIGGERS COMPOSITE?
────────────────────────────────────────────────────────────────────────────────

  These properties skip Layout AND Paint — only composite is needed:
    • transform (translate, rotate, scale, skew)
    • opacity
    • filter (GPU-based filters)
    • will-change (when set to transform or opacity)
    • backface-visibility

  WHY?
    Elements with these properties are promoted to their own compositor layers.
    The compositor thread can apply transform/opacity changes without touching
    the main thread or triggering layout/paint.

────────────────────────────────────────────────────────────────────────────────
5. REFLOW SCOPE AND PROPAGATION
────────────────────────────────────────────────────────────────────────────────

  Reflow can cascade up and down the DOM tree:

  UPWARD (ancestors affected):
    A child growing in height can push siblings down, affecting parent height,
    which can affect grandparent, etc.

  DOWNWARD (descendants affected):
    Changing a container's width affects all children's percentage widths,
    text wrapping, etc.

  GLOBAL REFLOW:
    Browser window resize → Full page layout recalculation
    Very expensive — should debounce resize event handlers

  INCREMENTAL REFLOW:
    Modern browsers try to limit scope of reflow to the "dirty" subtree.
    CSS Containment (contain: layout) can explicitly limit reflow scope.

  CSS Containment:
    contain: layout   → Layout changes don't affect outside this element
    contain: paint    → Descendants can't be painted outside element bounds
    contain: size     → Element's size doesn't depend on descendants
    contain: strict   → All of the above
    content-visibility: auto → Skip rendering off-screen elements entirely

────────────────────────────────────────────────────────────────────────────────
6. LAYOUT THRASHING IN DEPTH
────────────────────────────────────────────────────────────────────────────────

  Definition:
    Repeatedly forcing the browser to do synchronous layout within a JS task
    by alternating style writes and layout reads.

  Classic bad example:
    // 1000 elements, each iteration: write → forced sync layout → write → ...
    elements.forEach(el => {
      el.style.left = el.offsetLeft + 10 + 'px';  // READ offsetLeft after WRITE style.left
    });
    // Result: 1000 forced synchronous layouts!

  Diagnosis:
    Chrome DevTools → Performance timeline
    Look for "Recalculate Style" + "Layout" events in quick succession
    "Forced reflow" warning in DevTools console

  Fix 1: Batch reads then writes
    const lefts = elements.map(el => el.offsetLeft);     // All reads
    elements.forEach((el, i) => {
      el.style.left = lefts[i] + 10 + 'px';              // All writes
    });

  Fix 2: Use requestAnimationFrame
    requestAnimationFrame(() => {
      const lefts = elements.map(el => el.offsetLeft);   // Reads
      elements.forEach((el, i) => {
        el.style.left = lefts[i] + 10 + 'px';            // Writes
      });
    });

  Fix 3: Use CSS transforms instead
    // Instead of animating left/top, use translate:
    el.style.transform = `translateX(${offset}px)`;
    // This skips layout AND paint — only composite!

────────────────────────────────────────────────────────────────────────────────
7. PRACTICAL OPTIMIZATION TECHNIQUES
────────────────────────────────────────────────────────────────────────────────

  7.1 Minimize DOM Depth
    Shallower DOM trees reflow faster.
    
  7.2 Avoid Table Layouts for Dynamic Content
    Table layout recalculates ALL cells on any cell change.
    Use CSS Grid or Flexbox instead.

  7.3 Use CSS Classes Instead of Inline Styles
    // Bad: triggers reflow/repaint per property change
    el.style.width = '100px';
    el.style.height = '100px';
    el.style.padding = '10px';
    
    // Good: one reflow triggered by class change
    el.classList.add('active');

  7.4 Toggle CSS Classes for Bulk Changes
    Batch multiple style changes into one class toggle:
    el.classList.add('expanded');  // applies all .expanded styles at once

  7.5 Use document.documentElement.classList.add for Global Changes
    Avoids per-element invalidation when changing theme, dark mode, etc.

  7.6 Avoid Querying Layout in Loops
    Cache layout values outside the loop:
    const width = container.offsetWidth;  // read once
    items.forEach(item => item.style.width = width + 'px');  // write many

  7.7 Use will-change for Animated Elements
    will-change: transform promotes to compositor layer in advance:
    .animated { will-change: transform; }
    
    ONLY use on elements you know will animate, not globally!

  7.8 Prefer CSS Animations over JS Animations
    CSS animations on transform/opacity run on compositor thread.
    JS animations blocking main thread will cause jank.
    Use Web Animations API (element.animate) for JS control with compositor.

  7.9 Use CSS Containment
    .widget {
      contain: layout paint;  /* Isolates layout and paint */
    }

  7.10 Avoid display:none Toggle for Animations
    Instead of toggling display:none (causes reflow), use:
    opacity: 0 + pointer-events: none  (repaint only)
    visibility: hidden                  (repaint only, space preserved)
    transform: scale(0)                 (composite only!)

  7.11 Use Virtual Scrolling for Long Lists
    Render only visible items. Libraries: react-window, react-virtualized.
    Reduces DOM size → less reflow scope.

────────────────────────────────────────────────────────────────────────────────
8. BROWSER BATCHING OF STYLE CHANGES
────────────────────────────────────────────────────────────────────────────────

  Browsers are smart — they batch DOM mutations:
    el.style.width = '100px';   // pending change, no reflow yet
    el.style.height = '200px';  // pending change, no reflow yet
    el.style.color = 'red';     // pending change, no reflow yet
    // When does reflow happen? At end of current script task, or when
    // a layout value is READ.

  The browser processes pending style mutations:
    1. At the end of the current JS task (before next microtask checkpoint, in some cases)
    2. When a layout-dependent property is read (FSL - Forced Synchronous Layout)
    3. When the next frame is about to be rendered

  This batching BREAKS if you read layout properties between writes:
    el.style.width = '100px';
    el.offsetWidth;             // FORCES immediate layout flush!
    el.style.height = '200px';
    el.offsetHeight;            // FORCES immediate layout flush again!

9. VISIBILITY: HIDDEN VS DISPLAY: NONE VS OPACITY: 0
────────────────────────────────────────────────────────────────────────────────

  ┌────────────────────┬─────────────┬────────────┬────────────────┬────────────┐
  │ Property           │ Rendered?   │ Space?     │ Events?        │ Cost       │
  ├────────────────────┼─────────────┼────────────┼────────────────┼────────────┤
  │ display: none      │ No (not in  │ No         │ No             │ Reflow     │
  │                    │ render tree)│            │                │            │
  ├────────────────────┼─────────────┼────────────┼────────────────┼────────────┤
  │ visibility: hidden │ Yes (paint  │ Yes        │ No (pointer)   │ Repaint    │
  │                    │ transparent)│            │ Yes (focusable)│            │
  ├────────────────────┼─────────────┼────────────┼────────────────┼────────────┤
  │ opacity: 0         │ Yes         │ Yes        │ Yes!           │ Composite  │
  │                    │             │            │ (still clicks) │ (cheapest) │
  └────────────────────┴─────────────┴────────────┴────────────────┴────────────┘

  Note: opacity: 0 elements still receive pointer events!
  Combine with pointer-events: none to prevent clicks.

10. MEASURING REFLOW/REPAINT
────────────────────────────────────────────────────────────────────────────────

  Chrome DevTools:
    Performance tab:
      - Record interaction
      - Look for "Layout" events (purple) and their duration
      - "Recalculate Style" events
      - Look for long tasks (>50ms, shown in red)
    
    Rendering panel (…menu → More tools → Rendering):
      - Paint flashing: green overlay on areas being repainted
      - Layout Shift Regions: blue overlay for CLS
      - Scrolling Performance Issues
      - Layer borders

  CSS Triggers website (csstriggers.com):
    Shows which CSS properties trigger layout/paint/composite

  Performance API:
    const p = performance.now();
    // do DOM work
    console.log(performance.now() - p); // measure duration

11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between reflow and repaint?
A: Reflow (layout) recalculates element geometry (position/size) and
   cascades through the DOM tree — very expensive. Repaint redraws visual
   appearance without geometry changes — less expensive. Composite-only
   changes (transform, opacity) skip both — cheapest, GPU-based.

Q: What causes a reflow?
A: Changes to geometry-affecting properties (width, height, padding, margin,
   font-size, display, position), adding/removing DOM elements, browser
   window resize, and reading layout properties (offsetWidth, getBoundingClientRect)
   after making DOM/style changes (forced synchronous layout).

Q: What is forced synchronous layout (layout thrashing)?
A: When JS reads layout properties (offsetWidth, getBoundingClientRect) after
   writing styles, the browser is forced to immediately flush pending layout
   work to return accurate values. Doing this in a loop causes many synchronous
   layouts. Fix: batch all reads before writes, or use CSS transforms.

Q: How do you avoid layout thrashing?
A: 1) Batch style reads before writes. 2) Cache layout values outside loops.
   3) Use CSS transforms/opacity instead of left/top/width changes.
   4) Use requestAnimationFrame to batch work. 5) Use DocumentFragment for
   bulk DOM insertions. 6) Use CSS classes to apply multiple style changes at once.

Q: Why is animating transform better than animating left/top?
A: transform and opacity only trigger compositing — handled by the GPU
   compositor thread without involving layout or paint. Animating left/top
   triggers full layout recalculation on every frame, forcing main thread
   involvement and likely causing dropped frames.

Q: What is the difference between visibility:hidden and display:none?
A: display:none removes the element from the render tree entirely (no space,
   no events) — triggers reflow. visibility:hidden keeps the element in the
   render tree (space preserved) but invisible — triggers repaint only.
   opacity:0 is visible-but-transparent, events still fire — cheapest (composite).

Q: What is CSS containment?
A: CSS contain property restricts the scope of browser optimizations.
   contain: layout limits layout changes to within the element.
   contain: paint means descendants won't paint outside bounds.
   This helps performance by allowing the browser to skip recalculation
   of areas outside the contained element.

Q: How can you check which elements are repainting in Chrome DevTools?
A: In Chrome DevTools → Rendering panel, enable "Paint flashing". Areas
   being repainted are highlighted with a green overlay. Use the Performance
   tab to record and inspect "Layout" and "Recalculate Style" events.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Reflow (layout) = geometry change = most expensive
  • Repaint = visual-only change = less expensive
  • Composite only = transform/opacity = cheapest (GPU)
  • FSL (layout thrashing): reading layout after writing styles → avoid!
  • Batch reads → then writes to prevent FSL
  • display:none → reflow; visibility:hidden → repaint; opacity:0 → composite
  • will-change: transform → layer promotion (use sparingly)
  • CSS containment (contain:) limits reflow/repaint scope
================================================================================
