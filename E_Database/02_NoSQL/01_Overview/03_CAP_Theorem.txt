================================================================
  CAP THEOREM
================================================================

  The CAP Theorem (Brewer's Theorem, 2000) states:

  A distributed data store can guarantee at most TWO of the
  following three properties simultaneously:

  C -- Consistency
  A -- Availability
  P -- Partition Tolerance

================================================================
DEFINITIONS
================================================================

  Consistency (C):
    Every read receives the most recent write or an error.
    All nodes see the same data at the same time.
    "Strong consistency"

  Availability (A):
    Every request receives a response (not necessarily the latest data).
    The system is always operational.
    "No errors, ever"

  Partition Tolerance (P):
    The system continues operating even when network communication
    between some nodes is lost or delayed.
    "Network partitions are tolerated"

================================================================
WHY YOU CANNOT HAVE ALL THREE
================================================================

  In a distributed system, network partitions WILL happen.
  When a partition occurs, you must choose:

  SCENARIO: Node A and Node B are partitioned (cannot communicate).
  Client writes new value to Node A.
  Client reads from Node B.

  Choice 1: Return stale data from Node B
    --> You chose Availability over Consistency (AP)

  Choice 2: Refuse to answer from Node B until partition heals
    --> You chose Consistency over Availability (CP)

  Partition Tolerance is NOT optional in practice
  (you cannot control whether your network drops packets).
  So the real choice is: CA (single node / no partition) or
  sacrifice C (AP) or sacrifice A (CP) during partitions.

================================================================
CAP CATEGORIES
================================================================

  CP -- Consistent + Partition Tolerant
    Returns error or timeout when partition detected.
    Data is always consistent across nodes.
    Examples: HBase, Zookeeper, MongoDB (w:majority), Cassandra (QUORUM)

  AP -- Available + Partition Tolerant
    Always responds, but may return stale data.
    Eventually consistent.
    Examples: Cassandra (default), CouchDB, DynamoDB, DNS

  CA -- Consistent + Available (No Partition Tolerance)
    Only possible in a single-node or local-network system.
    Traditional RDBMS (PostgreSQL, MySQL) fit here in a single-node setup.
    Not viable for distributed systems across datacenters.

================================================================
DATABASE CLASSIFICATION TABLE
================================================================

  Database         Category      Notes
  ---------------  -----------   ------------------------------------------
  PostgreSQL       CA            Single node ACID; Patroni/replication = CP
  MySQL            CA / CP       With sync replication = CP
  MongoDB          CP            w:majority ensures consistency
  Cassandra        AP (tunable)  Default = AP; QUORUM consistency = CP
  DynamoDB         AP            Eventually consistent by default; strong option
  Redis            CP            Single primary; Sentinel handles failover
  HBase            CP            HDFS-based; strong consistency
  CouchDB          AP            Multi-master, conflict resolution
  Zookeeper        CP            Quorum-based; used for distributed coordination
  Elasticsearch    AP            Near real-time; primary for availability

================================================================
PACELC THEOREM (EXTENSION)
================================================================

  CAP only describes behavior during partitions.
  PACELC extends it to normal operation:

  If Partition  --> Choose between Availability (A) or Consistency (C)
  Else (normal) --> Choose between Latency (L) or Consistency (C)

  Even without partitions, there is a latency vs consistency tradeoff.
  Synchronous replication = low latency sacrificed for consistency.
  Asynchronous replication = low latency, eventual consistency.

  PACELC classification:
  Database        PA/EL or PC/EC
  ----------      ----------------
  DynamoDB        PA/EL  (available + low latency by default)
  Cassandra       PA/EL  (tunable)
  PostgreSQL sync PC/EC  (consistent but higher latency)
  MongoDB         PC/EC  (w:majority)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the CAP theorem?
  A: In a distributed system you can guarantee at most two of:
     Consistency (every read sees the latest write),
     Availability (every request gets a response),
     Partition Tolerance (system works despite network partitions).
     Since partitions are inevitable, real choice is CP vs AP.

  Q: Is Cassandra CP or AP?
  A: By default AP -- prioritizes availability and returns potentially stale data.
     With QUORUM or ALL consistency levels it becomes CP,
     sacrificing availability during partitions.

  Q: Why can't a distributed system be fully CAP?
  A: Because network partitions are unavoidable in a distributed system.
     During a partition, you must choose: respond with possibly stale data (A)
     or refuse to respond until you can guarantee consistency (C).

  Q: What is the PACELC theorem?
  A: An extension to CAP. Even without partitions, systems must trade off
     between latency (respond fast with possibly stale data) and consistency
     (wait for all nodes to sync before responding).
