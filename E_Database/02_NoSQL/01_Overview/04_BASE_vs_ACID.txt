================================================================
  BASE vs ACID
================================================================

================================================================
ACID (RDBMS)
================================================================

  Atomicity     Transaction is all-or-nothing.
                All operations commit or all roll back.
                No partial updates.

  Consistency   The database moves from one valid state to another.
                All constraints (FK, CHECK, UNIQUE) remain satisfied.

  Isolation     Concurrent transactions do not interfere.
                Result is same as serial execution (serializable).

  Durability    Once committed, data survives crashes.
                WAL + fsync ensures persistence.

  Example:
    Bank transfer of $500:
    1. Debit $500 from Account A
    2. Credit $500 to Account B
    If server crashes between 1 and 2 --> ACID rolls back step 1.
    Customer balance is never wrong.

================================================================
BASE (NoSQL / Distributed Systems)
================================================================

  NoSQL systems often prioritize availability and scale over
  strict ACID guarantees.

  Basically Available
    System guarantees availability.
    Responses may be partial or stale, but system always responds.
    Failures affect only part of the system (not all nodes).

  Soft State
    The state of the system may change over time even without input.
    Due to replication propagating writes across nodes.
    The system is not in a hard consistent state at all times.

  Eventually Consistent
    Given no new updates, all replicas will converge to the same value.
    "Eventual" means within seconds to minutes typically.
    But NOT immediate -- a read right after a write may return old data.

================================================================
BASE ANALOGY
================================================================

  DNS (Domain Name System) is a classic BASE system:
  - Highly available: DNS servers always respond
  - Soft state: TTL expires, records propagate over time
  - Eventually consistent: a DNS change propagates globally in minutes

  Shopping cart in an e-commerce site is often BASE:
  - Adding an item may briefly show on one node but not another
  - Eventually all nodes agree on cart contents
  - Better to show slightly stale cart than refuse to serve the page

================================================================
ACID vs BASE COMPARISON TABLE
================================================================

  Property           ACID                            BASE
  ----------------   ----------------------------    -------------------------
  Consistency        Strict (immediate)              Eventual (may lag)
  Availability       May sacrifice (return error)    Always available
  State              Hard consistent always          Soft state (in flux)
  Write handling     Wait for all nodes to confirm   Write to any replica
  Read guarantee     Latest committed value           May return stale data
  Failure behavior   Rollback (abort transaction)    Continue with partial data
  Examples           PostgreSQL, Oracle, MySQL        Cassandra, DynamoDB, Couchbase

================================================================
TUNABLE CONSISTENCY
================================================================

  Many NoSQL databases allow tuning the consistency level per operation:

  Cassandra:
    Consistency ONE   --> fastest, reads from one replica (AP behavior)
    Consistency QUORUM--> majority of replicas must agree (CP behavior)
    Consistency ALL   --> all replicas must agree (strict CP, high latency)

  DynamoDB:
    Eventually Consistent Reads (default, cheaper, faster)
    Strongly Consistent Reads (slightly slower, higher cost, latest data)

  MongoDB:
    Read concern "local" (default, may return uncommitted data)
    Read concern "majority" (only data committed by majority)
    Write concern "majority" (write acknowledged by majority)

================================================================
WHEN DOES EVENTUAL CONSISTENCY CAUSE PROBLEMS?
================================================================

  Problem: Read-your-own-writes
    User updates profile picture.
    Reads from a different replica that hasn't synced.
    User sees old photo. Confusing UX.

  Solution: "Sticky sessions" or route user reads to the
            same replica they last wrote to (session consistency).

  Problem: Monotonic reads
    Read timestamp=5, then read timestamp=3 from another replica.
    "Going backwards in time" is disorienting.

  Solution: Consistent hashing to route same user to same replica.

================================================================
INTERVIEW Q&A
================================================================

  Q: What does BASE stand for?
  A: Basically Available, Soft State, Eventually Consistent.
     It describes the consistency model of many NoSQL systems
     that prioritize availability and scale over strict ACID guarantees.

  Q: What is eventual consistency?
  A: A guarantee that if no new updates are made, all replicas will
     converge to the same value eventually.
     Not immediate -- reads after writes may return stale data briefly.

  Q: When would you choose ACID over BASE?
  A: When correctness is critical and partial failures are unacceptable.
     Banking, payments, inventory management, medical records.

  Q: When is eventual consistency acceptable?
  A: Social media feeds, shopping cart counts, view counters,
     DNS lookups, recommendation engines -- stale data for seconds
     does not cause business harm.
