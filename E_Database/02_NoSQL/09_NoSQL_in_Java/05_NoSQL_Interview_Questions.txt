SECTION 1: NOSQL FUNDAMENTALS
================================================================

Q1. What is NoSQL, and how does it differ from relational databases?
--------------------------------------------------------------------
  NoSQL ("Not Only SQL") refers to databases that do NOT enforce
  a fixed relational schema. Key differences:

  Aspect              | RDBMS                      | NoSQL
  --------------------|----------------------------|-------------------------------
  Schema              | Fixed, predefined          | Flexible / schema-less
  Data model          | Tables with rows/columns   | Document, KV, Column, Graph
  Joins               | First-class support        | Avoided (denormalization)
  ACID transactions   | Full support               | Limited (varies by DB)
  Scaling             | Vertical (scale-up)        | Horizontal (scale-out)
  Query language      | Standard SQL               | DB-specific APIs / query lang
  Use case            | Complex transactions       | High-volume, low-latency reads

Q2. What are the four main types of NoSQL databases?
----------------------------------------------------
  1. Document Store   -- stores JSON/BSON documents; e.g. MongoDB, Couchbase
  2. Key-Value Store  -- simple map lookup; e.g. Redis, DynamoDB, Riak
  3. Column-Family    -- wide rows, column families; e.g. Cassandra, HBase
  4. Graph Database   -- nodes and edges; e.g. Neo4j, Amazon Neptune

Q3. Explain the CAP Theorem.
-----------------------------
  A distributed system can guarantee only TWO of the three:

  C -- Consistency   : every read returns the latest write
  A -- Availability  : every request gets a (non-error) response
  P -- Partition Tol.: system continues despite network partitions

  In practice P is non-negotiable (networks do partition), so the
  real trade-off is C vs A:
    - CP systems (MongoDB, HBase, Zookeeper): sacrifice availability
    - AP systems (Cassandra, CouchDB, Dynamo): sacrifice consistency

Q4. What is BASE, and how does it differ from ACID?
----------------------------------------------------
  ACID (Relational):
    Atomicity   - all-or-nothing transaction
    Consistency - data always valid per rules
    Isolation   - concurrent transactions don't interfere
    Durability  - committed data survives failures

  BASE (NoSQL):
    Basically Available - system stays available
    Soft State          - state may change over time (even w/o input)
    Eventually Consistent - system will converge to consistent state

  Trade-off: ACID gives strong guarantees at cost of performance/scale;
  BASE prioritizes availability and performance, accepts eventual consistency.

Q5. What is eventual consistency? Give a real-world example.
------------------------------------------------------------
  Eventual consistency means all replicas will converge to the same
  value if no new writes occur for a period of time.

  Example: Amazon shopping cart (Dynamo paper). If two users update
  the same cart on different replicas, both updates are accepted
  (AP system). A reconciliation algorithm later merges them. The
  cart may be briefly inconsistent across replicas but eventually
  reflects all writes.

Q6. When would you choose NoSQL over a relational database?
-----------------------------------------------------------
  Choose NoSQL when:
  - Schema changes frequently (agile product development)
  - Data is hierarchical / nested (documents)
  - Need massive horizontal write throughput (Cassandra, DynamoDB)
  - Low-latency caching layer required (Redis)
  - Data relationships are graph-like (Neo4j)
  - Full-text search is core functionality (Elasticsearch)
  - Time-series data with high write rate (InfluxDB)

  Stick with RDBMS when:
  - Complex multi-table transactions are required
  - Strong data integrity / foreign key constraints needed
  - Reporting / ad-hoc SQL queries are primary workload

SECTION 2: MONGODB

Q7. How does MongoDB store data?
---------------------------------
  MongoDB stores data as BSON (Binary JSON) documents inside
  collections (analogous to tables). Each document has a unique
  _id field (ObjectId by default). Documents in the same collection
  need NOT share the same schema.

  Database -> Collection -> Document (BSON)

Q8. What is the difference between MongoRepository and MongoTemplate?
----------------------------------------------------------------------
  MongoRepository (Spring Data Repository):
  - High-level abstraction; auto-generates queries from method names
  - Best for simple CRUD and derived queries
  - Cleaner, less boilerplate

  MongoTemplate:
  - Lower-level; gives full control over query criteria (Criteria API)
  - Required for dynamic queries built at runtime
  - Supports aggregation pipelines, bulk ops, upserts

  Rule of thumb: use Repository for 80% of cases; fall back to
  MongoTemplate for complex / dynamic queries.

Q9. How do you map a Java class to a MongoDB collection?
---------------------------------------------------------
  @Document(collection = "products")
  public class Product {
      @Id
      private String id;           // maps to MongoDB _id

      @Indexed(unique = true)
      private String skuCode;

      @Field("product_name")       // custom field name in Mongo
      private String name;

      private List<String> tags;
  }

Q10. How do you perform an aggregation pipeline in Spring Data MongoDB?
-----------------------------------------------------------------------
  Using MongoTemplate:

  Aggregation agg = Aggregation.newAggregation(
      Aggregation.match(Criteria.where("category").is("Electronics")),
      Aggregation.group("brand")
                 .count().as("total")
                 .avg("price").as("avgPrice"),
      Aggregation.sort(Sort.Direction.DESC, "total"),
      Aggregation.limit(5)
  );

  AggregationResults<BrandSummary> results =
      mongoTemplate.aggregate(agg, "products", BrandSummary.class);
  List<BrandSummary> summary = results.getMappedResults();

Q11. What indexing strategies exist in MongoDB?
-----------------------------------------------
  Type                  | When to use
  ----------------------|--------------------------------------------
  Single field          | Filter / sort on one field
  Compound index        | Queries filtering on multiple fields
  Multikey index        | Arrays -- index each element
  Text index            | Full-text search ($text queries)
  Geospatial (2dsphere) | Location-based queries
  TTL index             | Auto-expire documents after a duration
  Hashed index          | Shard key for hash-based sharding
  Wildcard index        | Dynamic / unknown field names

  Key rule: index ESR -- Equality first, Sort second, Range last.

Q12. What are MongoDB transactions, and when do you need them?
--------------------------------------------------------------
  MongoDB has supported multi-document ACID transactions since v4.0
  (replica sets) and v4.2 (sharded clusters).

  Use transactions when a single logical operation spans multiple
  documents / collections and all changes must succeed or none.

  In Spring:
  @Transactional  // works with MongoTransactionManager bean
  public void transfer(String fromId, String toId, double amount) {
      Account from = accountRepo.findById(fromId).orElseThrow();
      Account to   = accountRepo.findById(toId).orElseThrow();
      from.setBalance(from.getBalance() - amount);
      to.setBalance(to.getBalance() + amount);
      accountRepo.save(from);
      accountRepo.save(to);
  }

  Note: for single-document changes (embedded docs / arrays),
  MongoDB is atomic without a transaction.

Q13. What is the difference between embedded documents and references in MongoDB?
----------------------------------------------------------------------------------
  Embedded (denormalized):
  - Store related data inside the parent document
  - Pros: single read, no joins, atomic writes on one document
  - Cons: data duplication, document size limit (16 MB)
  - Use when: data is exclusively owned by parent, read together always

  References (normalized):
  - Store only the _id of the related document
  - Pros: no duplication, independent updates
  - Cons: requires application-level "joins" ($lookup in aggregation)
  - Use when: data is shared across entities or grows unbounded

Q15. How does Spring Cache abstraction work with Redis?
-------------------------------------------------------
  Add @EnableCaching on a @Configuration class, then annotate
  service methods:

  @Cacheable(value = "products", key = "#id")
  -- reads from cache; calls method only on cache miss

  @CachePut(value = "products", key = "#product.id")
  -- always calls method AND updates cache (write-through)

  @CacheEvict(value = "products", key = "#id")
  -- removes entry from cache (on delete/update)

  @CacheEvict(value = "products", allEntries = true)
  -- clears entire cache region

  Spring Boot auto-configures RedisCacheManager when
  spring-boot-starter-data-redis is on the classpath.

Q16. How do you implement distributed locking with Redis in Java?
-----------------------------------------------------------------
  Using Redisson (recommended):

  RedissonClient redisson = Redisson.create(config);
  RLock lock = redisson.getLock("inventory:P1:lock");

  try {
      boolean acquired = lock.tryLock(5, 10, TimeUnit.SECONDS);
      // waitTime=5s, leaseTime=10s (auto-release)
      if (acquired) {
          // critical section -- decrement inventory
      }
  } finally {
      if (lock.isHeldByCurrentThread()) {
          lock.unlock();
      }
  }

  Why not SETNX alone?  SETNX doesn't handle: node crash before
  DEL (deadlock), clock skew, fencing tokens.  Redlock algorithm
  or Redisson handles these safely.

Q17. What is Redis pipeline and when do you use it?
----------------------------------------------------
  Pipelining batches multiple commands in a single network round-trip.
  Without pipelining each command incurs RTT overhead.

  redisTemplate.executePipelined((RedisCallback<Object>) conn -> {
      for (String id : productIds) {
          conn.get(("product:" + id).getBytes());
      }
      return null;
  });

  Use when: bulk reads/writes where commands are independent
  (e.g., warming a cache for 500 product IDs at startup).

Q18. How do you set TTL on a Redis key in Spring?
--------------------------------------------------
  // Via StringRedisTemplate:
  ops.set("session:abc", "U100", Duration.ofMinutes(30));

  // Or explicitly:
  redisTemplate.expire("session:abc", Duration.ofMinutes(30));

  // Via Spring Cache config (global default TTL):
  RedisCacheConfiguration.defaultCacheConfig()
      .entryTtl(Duration.ofMinutes(10));

Q19. What is the difference between Redis persistence modes?
------------------------------------------------------------
  RDB (Snapshot):
  - Periodic point-in-time snapshots to disk
  - Fast restarts, smaller files
  - Risk: data loss since last snapshot

  AOF (Append Only File):
  - Logs every write operation; replayed on restart
  - More durable (fsync every second or every write)
  - Larger files, slower restart

  AOF + RDB hybrid (default in Redis 7):
  - Best of both; recommended for production

Q20. Explain Redis Pub/Sub vs Streams.
---------------------------------------
  Pub/Sub:
  - Fire-and-forget; no persistence
  - Subscribers must be online to receive messages
  - No consumer groups, no replay

  Streams (Redis 5+):
  - Persistent append-only log
  - Consumer groups with acknowledgment (XACK)
  - Messages can be replayed / inspected
  - Suitable as a lightweight message queue

SECTION 4: CASSANDRA
================================================================

Q21. What is Cassandra's data model?
-------------------------------------
  Cassandra uses wide-column tables:
  - Keyspace (like a database / schema)
  - Table (CQL table with partition key + optional clustering columns)
  - Row is uniquely identified by primary key

  Primary Key = Partition Key (+ Clustering Columns)
    - Partition key  -> determines which node stores the row (hash)
    - Clustering col -> determines row order within a partition

  Best practice: design tables around query patterns (query-first design).

Q22. Why must queries always include the partition key in Cassandra?
--------------------------------------------------------------------
  Cassandra distributes rows across nodes using a consistent hash of
  the partition key.  Without it:
  - The coordinator node cannot determine which node(s) hold the data
  - A full-cluster scan (ALLOW FILTERING) would be required
  - Extremely expensive at scale; essentially an anti-pattern

  Rule: every query = one partition (or a small range of partitions).

Q23. What are tombstones in Cassandra, and why are they problematic?
--------------------------------------------------------------------
  When a row or column is deleted, Cassandra writes a tombstone
  (a deletion marker) instead of removing the data immediately.
  Actual data is removed during compaction.

  Problem: if a query scans many tombstones before finding live data,
  it gets slow and may exceed tombstone_warn_threshold (default 1000)
  or tombstone_failure_threshold (default 100,000), causing errors.

  Mitigations:
  - Avoid frequent deletes in hot partitions
  - Use TTL instead of explicit deletes where possible
  - Set appropriate gc_grace_seconds and compact regularly

Q24. What is the difference between QUORUM and LOCAL_QUORUM consistency?
------------------------------------------------------------------------
  QUORUM       : majority of replicas across ALL datacenters must ack.
                 Risk: cross-DC latency; less useful for multi-DC.

  LOCAL_QUORUM : majority of replicas in the LOCAL datacenter only.
                 Recommended for multi-DC deployments; avoids cross-DC
                 round-trips while still providing strong local consistency.

  Consistency levels (ascending strength): ONE < LOCAL_QUORUM < QUORUM < ALL

Q25. How does Cassandra handle write operations?
------------------------------------------------
  1. Write goes to CommitLog (append-only, for durability)
  2. Write goes to MemTable (in-memory structure per table)
  3. MemTable is flushed to immutable SSTable on disk periodically
  4. Compaction merges SSTables, removing tombstones and duplicates

  This is why Cassandra has very high write throughput -- writes
  are sequential appends, never random I/O.

Q26. How do you model a one-to-many relationship in Cassandra?
--------------------------------------------------------------
  Cassandra does NOT support joins.  Use denormalization:

  // Query: get all orders for a user (sorted by date desc)
  @Table("orders_by_user")
  public class OrderByUser {
      @PrimaryKeyColumn(type = PrimaryKeyType.PARTITIONED)
      private UUID userId;

      @PrimaryKeyColumn(type = PrimaryKeyType.CLUSTERED,
                        ordering = Ordering.DESCENDING)
      private Instant createdAt;

      @PrimaryKeyColumn(type = PrimaryKeyType.CLUSTERED)
      private UUID orderId;

      private String status;
  }

  // Query: get all orders by status (separate table)
  @Table("orders_by_status")
  public class OrderByStatus { ... }

  Rule: one table per query pattern.  Accept data duplication.

SECTION 5: DYNAMODB
================================================================

Q27. Explain DynamoDB's primary key types.
------------------------------------------
  Simple primary key: Partition key (PK) alone -- unique per item.

  Composite primary key: Partition key (PK) + Sort key (SK).
  - All items with same PK form a "collection" sorted by SK.
  - Enables range queries: findByPkAndSkBetween(...)

  Access pattern example:
    PK = "USER#U100"    SK = "ORDER#ORD001"
    PK = "USER#U100"    SK = "ORDER#ORD002"
    PK = "USER#U100"    SK = "PROFILE"      -- heterogeneous items!

Q28. What are Global Secondary Indexes (GSI) vs Local Secondary Indexes (LSI)?
-------------------------------------------------------------------------------
  GSI (Global Secondary Index):
  - Completely different partition key than the base table
  - Can be added / removed at any time
  - Has its own provisioned throughput
  - Eventually consistent reads (by default)

  LSI (Local Secondary Index):
  - Same partition key as base table, different sort key
  - Must be defined at table creation time (cannot add later)
  - Shares base table's throughput
  - Can request strongly consistent reads

  Rule: prefer GSI for new access patterns; use LSI only if you need
  strongly consistent reads on the index.

Q29. What is the single-table design pattern in DynamoDB?
----------------------------------------------------------
  Store multiple entity types in ONE table using composite keys
  and a generic PK/SK naming convention:

  PK              | SK                 | Attributes
  ----------------|--------------------|-----------------------
  USER#U100       | PROFILE            | name, email, joinDate
  USER#U100       | ORDER#ORD001       | status, total
  USER#U100       | ORDER#ORD002       | status, total
  PRODUCT#P1      | METADATA           | name, category, price
  PRODUCT#P1      | REVIEW#R001        | rating, text

  Benefits: single GetItem/Query call, no joins, reduced cost.
  Trade-off: harder to query across entity types, complex design.

Q30. How do you query a GSI in the DynamoDB Enhanced Client?
-------------------------------------------------------------
  DynamoDbIndex<Order> statusIndex =
      orderTable.index("status-index");

  QueryConditional q = QueryConditional.keyEqualTo(
      Key.builder().partitionValue("PENDING").build());

  PageIterable<Order> pages = statusIndex.query(q);
  List<Order> pendingOrders = pages.items().stream()
      .collect(Collectors.toList());

Q31. What is DynamoDB's consistency model?
------------------------------------------
  Eventually consistent read (default):
  - Reads from any replica; may return stale data
  - Costs 0.5 RCU per 4 KB

  Strongly consistent read:
  - Reads from the leader node; always latest data
  - Costs 1 RCU per 4 KB
  - Not available on GSIs

  GetItemRequest.builder()
      .tableName("Orders")
      .key(key)
      .consistentRead(true)   // strongly consistent
      .build();

Q32. What are DynamoDB Transactions?
-------------------------------------
  TransactWriteItems -- atomically write up to 100 items across
  multiple tables in a single AWS account and region.

  enhancedClient.transactWriteItems(t -> t
      .addPutItem(orderTable, order)
      .addUpdateItem(inventoryTable,
          TransactUpdateItemEnhancedRequest.builder(Inventory.class)
              .item(inventory)
              .build())
  );

  Use for: order placement + inventory decrement must both succeed,
  or neither should.  Costs 2x the normal write capacity.

SECTION 6: SPRING DATA COMMON CONCEPTS

Q33. What is the Spring Data Repository hierarchy?
---------------------------------------------------
  Repository (marker)
    └── CrudRepository<T, ID>       -- save, findById, delete, count
          └── PagingAndSortingRepository -- findAll(Pageable/Sort)
                └── MongoRepository / CassandraRepository / etc.

  ListCrudRepository (Spring Data 3+):
  - Returns List<T> instead of Iterable<T> for findAll / saveAll.

Q34. How do derived query methods work in Spring Data?
------------------------------------------------------
  Spring Data parses the method name and generates the query:

  findBy[Criteria][Operator][...][OrderBy][Direction]

  Examples:
  findByEmailAndStatus(String email, String status)
  findByPriceLessThan(double price)
  findByNameContaining(String keyword)
  findTop5ByOrderByCreatedAtDesc()
  existsBySkuCode(String sku)
  countByCategory(String category)

  Supported keywords: And, Or, Between, LessThan, GreaterThan,
  Like, Containing, StartingWith, EndingWith, In, NotIn,
  IsNull, IsNotNull, OrderBy, Top, First, Distinct.

Q35. How do you handle pagination in Spring Data?
-------------------------------------------------
  // Repository method:
  Page<Product> findByCategory(String category, Pageable pageable);

  // Service call:
  Pageable page = PageRequest.of(0, 20, Sort.by("price").ascending());
  Page<Product> result = productRepo.findByCategory("Electronics", page);

  result.getContent();       // List<Product> for current page
  result.getTotalElements(); // total matching records
  result.getTotalPages();
  result.hasNext();

Q36. What is the difference between @Transactional in JPA vs MongoDB?
----------------------------------------------------------------------
  JPA / RDBMS:
  - Full ACID transactions; savepoints, rollback on exception
  - Managed by JpaTransactionManager / DataSourceTransactionManager

  MongoDB:
  - Multi-document transactions available since 4.0 (replica sets)
  - Requires MongoTransactionManager bean
  - Higher overhead; single-document ops are atomic without transaction

  Cassandra / Redis:
  - @Transactional is generally NOT supported (no true ACID)
  - Use lightweight transactions (IF NOT EXISTS) in Cassandra
  - Use Redis MULTI/EXEC or Lua scripts for atomicity in Redis

Q37. How do you implement reactive NoSQL access with Spring WebFlux?
--------------------------------------------------------------------
  Spring Data provides Reactive variants:

  ReactiveMongoRepository<Product, String>
  ReactiveRedisTemplate<String, String>
  ReactiveCassandraRepository<OrderByUser, UUID>

  @Service
  public class ProductService {
      @Autowired
      private ReactiveMongoRepository<Product, String> repo;

      public Flux<Product> findByCategory(String cat) {
          return repo.findByCategory(cat);  // returns Flux<Product>
      }

      public Mono<Product> findById(String id) {
          return repo.findById(id);         // returns Mono<Product>
      }
  }

  Use when: high-concurrency, non-blocking I/O (chat, streaming, IoT).

Q38. How would you implement a rate limiter using Redis?
--------------------------------------------------------
  Sliding window counter using sorted sets:

  String key = "rate:user:" + userId;
  long now = System.currentTimeMillis();
  long windowStart = now - Duration.ofMinutes(1).toMillis();

  ZSetOperations<String, String> zOps = redisTemplate.opsForZSet();
  redisTemplate.execute(new SessionCallback<>() {
      public Object execute(RedisOperations ops) {
          ops.multi();
          ops.opsForZSet().removeRangeByScore(key, 0, windowStart);
          ops.opsForZSet().add(key, String.valueOf(now), now);
          ops.opsForZSet().zCard(key);
          ops.expire(key, Duration.ofMinutes(2));
          return ops.exec();
      }
  });
  // if count > LIMIT, reject request

Q39. How would you design a leaderboard using Redis?
-----------------------------------------------------
  Use a Sorted Set (ZSET): score = user's points, member = userId.

  // Add / update score:
  zOps.add("leaderboard:weekly", "user:U100", 9850.0);
  zOps.incrementScore("leaderboard:weekly", "user:U100", 200.0);

  // Top 10 (highest score first):
  Set<String> top10 = zOps.reverseRange("leaderboard:weekly", 0, 9);

  // User's rank (0-indexed, reverse = descending):
  Long rank = zOps.reverseRank("leaderboard:weekly", "user:U100");

  // User's score:
  Double score = zOps.score("leaderboard:weekly", "user:U100");

  O(log N) for add/update, O(log N + K) for top-K range query.

Q40. You need to store 10 billion sensor readings per day. Which NoSQL
      database would you choose and why?
-----------------------------------------------------------------------
  Choose Apache Cassandra or a Time-Series DB (e.g., InfluxDB):

  Cassandra rationale:
  - Partition key: deviceId; clustering key: timestamp (DESC)
  - Extremely high write throughput (sequential appends to SSTable)
  - Built-in TTL to auto-expire old readings (e.g., keep 90 days)
  - Linear horizontal scaling by adding nodes
  - Compaction handles SSTable merging in background

  Table design:
  @Table("sensor_readings")
  PRIMARY KEY ((device_id), recorded_at) -- recorded_at DESCENDING

  Alternative: InfluxDB / TimescaleDB if you need time-series specific
  functions (downsampling, continuous queries, retention policies).

Q41. How would you cache database query results in a Spring Boot service?
-------------------------------------------------------------------------
  Pattern: Cache-Aside (lazy loading)

  @Cacheable(value = "products", key = "#id",
             unless = "#result == null")
  public Product getProduct(String id) {
      return productRepository.findById(id).orElse(null);
  }

  @CachePut(value = "products", key = "#product.id")
  public Product updateProduct(Product product) {
      return productRepository.save(product);
  }

  @CacheEvict(value = "products", key = "#id")
  public void deleteProduct(String id) {
      productRepository.deleteById(id);
  }

  Cache TTL configuration (application.yml):
  spring:
    cache:
      redis:
        time-to-live: 600000   # 10 minutes in ms

Q42. What is the N+1 problem in NoSQL, and how do you avoid it?
---------------------------------------------------------------
  N+1 occurs when code issues 1 query to fetch N parent items,
  then N additional queries to fetch related data for each.

  Example (MongoDB):
  // BAD:
  List<Order> orders = orderRepo.findByUserId(userId);  // 1 query
  orders.forEach(o -> {
      Product p = productRepo.findById(o.getProductId()); // N queries
  });

  Solutions:
  1. Embed the data (denormalize) -- store product name/price inside order
  2. Use $lookup aggregation to join in a single pipeline
  3. Fetch all referenced IDs in one query: productRepo.findAllById(ids)
  4. Use a projection to return only needed fields

Q43. How would you implement an optimistic lock in MongoDB?
-----------------------------------------------------------
  Use a @Version field; Spring Data MongoDB handles it automatically:

  @Document("accounts")
  public class Account {
      @Id private String id;
      private double balance;

      @Version
      private Long version;  // auto-incremented on each save
  }

  On save, Spring issues:
    db.accounts.updateOne(
      { _id: "...", version: <current> },
      { $set: { balance: ..., version: <current+1> } }
    )
  If no document matches (version changed by another writer),
  OptimisticLockingFailureException is thrown.

Q44. Compare Redis Pub/Sub vs Kafka for event-driven messaging.
---------------------------------------------------------------
  Feature              | Redis Pub/Sub     | Kafka
  ---------------------|-------------------|-----------------------------
  Persistence          | None (fire/forget)| Durable (configurable)
  Consumer groups      | No                | Yes
  Replay               | No                | Yes (offset-based)
  Throughput           | Very high         | Very high
  At-least-once        | No                | Yes
  Ordering             | Per channel       | Per partition
  Best for             | Ephemeral notif.  | Event sourcing, audit log

  Use Redis Pub/Sub: live notifications, real-time chat, cache invalidation.
  Use Kafka: order events, audit trails, stream processing pipelines.

Q45. How do you handle schema migration in MongoDB?
---------------------------------------------------
  MongoDB is schema-less but your application code has a schema.
  Strategies:

  1. Incremental migration in code:
     - Add default value handling in the entity class
     - Run a background job to update old documents lazily

  2. Mongock (recommended for Spring Boot):
     - Migration framework similar to Flyway/Liquibase for MongoDB
     - Tracks applied changesets in a "mongockChangeLog" collection

  @ChangeUnit(id = "add-category-field", order = "001", author = "dev")
  public class AddCategoryMigration {
      @Execution
      public void addCategory(MongoTemplate mongoTemplate) {
          Update update = Update.update("category", "UNCATEGORIZED");
          mongoTemplate.updateMulti(
              Query.query(Criteria.where("category").exists(false)),
              update, Product.class);
      }
  }

SECTION 8: QUICK-REFERENCE CHEATSHEET
================================================================

  Topic                     | Key Point
  --------------------------|--------------------------------------------------
  CAP theorem               | Can only guarantee 2 of 3; P is non-negotiable
  MongoDB write             | Atomic per document; multi-doc needs transaction
  MongoDB index             | ESR rule: Equality → Sort → Range
  Redis TTL                 | ops.set(key, val, Duration); expire(key, Duration)
  Redis lock                | Use Redisson RLock, not raw SETNX
  Cassandra partition key   | Must be in every query; determines node placement
  Cassandra consistency     | LOCAL_QUORUM for multi-DC; QUORUM for single-DC
  Cassandra delete          | Writes a tombstone; removed at compaction
  DynamoDB GSI vs LSI       | GSI = any PK, add later; LSI = same PK, at creation
  DynamoDB single-table     | One table, many entity types via PK/SK conventions
  Spring @Cacheable         | Cache-aside; use unless="#result==null" for nulls
  Spring pagination         | PageRequest.of(page, size, sort); returns Page<T>
  Spring Reactive           | ReactiveMongoRepository returns Mono/Flux
