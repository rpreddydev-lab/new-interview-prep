================================================================
  REDIS PUB/SUB AND STREAMS
================================================================

================================================================
PUB/SUB
================================================================

  Redis Pub/Sub is a message passing pattern:
  - Publishers send messages to a CHANNEL
  - Subscribers receive messages from channels they are subscribed to
  - No persistence: messages are fire-and-forget
  - If subscriber is offline when message is published, message is LOST

  SUBSCRIBE notifications        -- subscribe to channel
  PUBLISH notifications "hello"  -- send message
  UNSUBSCRIBE notifications

  Pattern subscribe:
  PSUBSCRIBE order.*             -- subscribe to all order.* channels
  PUBLISH order.created "ORD001"
  PUBLISH order.shipped "ORD001"

================================================================
PUB/SUB LIMITATIONS
================================================================

  1. No message persistence -- missed messages are gone
  2. No consumer groups -- all subscribers get every message
  3. No replay / offset tracking
  4. If Redis restarts, all subscriptions are lost

  Use Pub/Sub for:
  - Real-time notifications (chat, live feeds)
  - Cache invalidation across multiple app servers
  - Low-volume event broadcasting where loss is acceptable

  Use Redis Streams (or Kafka) for:
  - Durable messages with persistence
  - Consumer groups (partition processing)
  - Replay capability
  - High-volume event streams

================================================================
SPRING REDIS PUB/SUB
================================================================

  // Publisher:
  @Autowired RedisTemplate<String, String> redisTemplate;

  public void publishOrderEvent(String orderId) {
      redisTemplate.convertAndSend("order.created", orderId);
  }

  // Subscriber:
  @Component
  public class OrderEventListener implements MessageListener {
      @Override
      public void onMessage(Message message, byte[] pattern) {
          String body = new String(message.getBody());
          System.out.println("Received: " + body);
      }
  }

  // Config:
  @Bean
  RedisMessageListenerContainer container(RedisConnectionFactory cf,
                                          OrderEventListener listener) {
      RedisMessageListenerContainer c = new RedisMessageListenerContainer();
      c.setConnectionFactory(cf);
      c.addMessageListener(listener, new PatternTopic("order.*"));
      return c;
  }

================================================================
REDIS STREAMS
================================================================

  Redis Streams (added in Redis 5.0) is a persistent, ordered log
  similar to Apache Kafka:
  - Entries are appended (not consumed and removed)
  - Entries have auto-generated IDs: timestamp-sequence (e.g. 1705312200000-0)
  - Consumer groups track which messages each group has consumed
  - Supports replay from any point in the stream

================================================================
STREAM COMMANDS
================================================================

  XADD events * action "purchase" user_id "1001" amount "99.99"
  -- * = auto-generate ID based on timestamp

  XLEN events                    -- number of entries
  XRANGE events - +              -- all entries (- = start, + = end)
  XRANGE events - + COUNT 10     -- first 10 entries
  XREVRANGE events + - COUNT 5   -- last 5 entries (newest first)

  XREAD COUNT 5 STREAMS events 0          -- read from beginning
  XREAD COUNT 5 BLOCK 0 STREAMS events $  -- block waiting for new entries

================================================================
CONSUMER GROUPS
================================================================

  Consumer groups allow multiple workers to process a stream in parallel,
  with each message going to exactly one worker in the group.

  -- Create group:
  XGROUP CREATE events workers $ MKSTREAM
  -- $ = start from new messages only; 0 = from beginning

  -- Worker reads messages assigned to it:
  XREADGROUP GROUP workers worker1 COUNT 5 STREAMS events >

  -- Acknowledge processed message:
  XACK events workers 1705312200000-0

  -- Check pending (unacknowledged) messages:
  XPENDING events workers - + 10

  -- Claim timed-out message from dead worker:
  XCLAIM events workers worker2 10000 1705312200000-0

================================================================
STREAMS vs PUB/SUB vs KAFKA
================================================================

  Feature               Redis Pub/Sub    Redis Streams    Kafka
  ------------------    -------------    -------------    ----------
  Persistence           No               Yes              Yes
  Consumer groups       No               Yes              Yes
  Replay                No               Yes              Yes
  Message ordering      Per channel      Per stream       Per partition
  Throughput            Very high        High             Very high
  Retention             None             Configurable     Days/weeks
  Operational overhead  Low              Low              High
  Best for              Real-time fan-out Event log      Enterprise event bus

================================================================
USE CASES
================================================================

  Pub/Sub:
  - Live notifications to browser clients (via SSE/WebSocket)
  - Cache invalidation broadcast across app cluster
  - Chat messages (small scale)

  Streams:
  - Order event log (created/paid/shipped/delivered)
  - User activity tracking with replay capability
  - Microservice event bus (lightweight Kafka alternative)
  - IoT sensor data collection

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between Redis Pub/Sub and Streams?
  A: Pub/Sub: fire-and-forget, no persistence, missed messages are lost.
     Streams: persistent append-only log, consumer groups, replay support.
     Use Pub/Sub for real-time broadcasts where loss is OK.
     Use Streams where durability and replay are required.

  Q: How do Redis Streams compare to Kafka?
  A: Both are persistent ordered logs with consumer groups.
     Redis Streams: simpler to operate, lower overhead, data in memory.
     Kafka: higher throughput, longer retention, better ecosystem,
     replay days/weeks of data, better for enterprise event streaming.
