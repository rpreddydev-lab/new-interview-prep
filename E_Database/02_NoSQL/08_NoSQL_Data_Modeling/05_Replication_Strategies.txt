================================================================
  REPLICATION STRATEGIES IN NOSQL
================================================================

================================================================
WHY REPLICATE?
================================================================

  1. High Availability -- if one node fails, others serve requests
  2. Read Scalability  -- read replicas absorb read traffic
  3. Disaster Recovery -- geographic copies for regional failure
  4. Durability        -- data not lost if a single node dies

================================================================
REPLICATION FACTOR
================================================================

  RF = number of copies of each piece of data.
  RF=1 --> no redundancy, single point of failure
  RF=3 --> standard for production (tolerates 1 node failure)

  Cassandra: SET per keyspace:
  CREATE KEYSPACE myapp WITH REPLICATION = {
    'class': 'NetworkTopologyStrategy',
    'us-east-1': 3,
    'eu-west-1': 3
  };

  MongoDB: Replica Set minimum 3 members (1 primary + 2 secondaries)

================================================================
LEADER-BASED REPLICATION (SINGLE PRIMARY)
================================================================

  One primary (leader) accepts all writes.
  Secondaries replicate from primary and serve reads.

  MongoDB Replica Set:
  [Primary] --> oplogs --> [Secondary 1]
                      --> [Secondary 2]

  - Writes go to primary
  - Reads can go to primary (default, consistent) or secondaries (stale)
  - Automatic failover: secondaries hold election if primary is unreachable
  - Election needs majority (2 of 3 for RF=3)

  Pros:
  - Simple consistency model (all writes through one node)
  - Clear data lineage via replication log

  Cons:
  - Write bottleneck (single primary)
  - Election latency during failover (~10-30 seconds in MongoDB)

================================================================
LEADERLESS REPLICATION (MULTI-MASTER)
================================================================

  Any node accepts writes; nodes propagate to each other.
  Clients write/read from W/R nodes respectively.

  Cassandra: any node can accept writes for any partition.

  Quorum formula:
  W + R > RF (strong read-your-own-writes)
  W = write quorum, R = read quorum, RF = replication factor

  Example RF=3:
  W=2, R=2  --> quorum reads and writes (overlapping node guarantees latest)
  W=1, R=3  --> fast writes, slow reads
  W=3, R=1  --> slow writes, fast reads
  W=1, R=1  --> eventual consistency, fastest, may miss latest write

  DynamoDB: eventually consistent reads (default) or strongly consistent.

  Pros:
  - No single point of failure for writes
  - Can tune consistency per operation
  - Geographic distribution easier

  Cons:
  - Conflict resolution needed when concurrent writes conflict
  - Last-Write-Wins (LWW) by timestamp is common but can lose updates
  - More complex to reason about

================================================================
READ REPAIR
================================================================

  When a quorum read returns different versions from different replicas,
  the coordinator writes the latest version back to the stale replicas.
  Repairs inconsistency lazily on read.

  Used by: Cassandra, DynamoDB

================================================================
ANTI-ENTROPY / HINTED HANDOFF
================================================================

  Anti-entropy: Merkle tree comparison between nodes to find divergence.
  Background repair synchronizes out-of-sync data.

  Hinted Handoff: if target node is down during write, coordinator stores
  a "hint" and delivers the write when the node comes back online.

  Cassandra: nodetool repair runs anti-entropy manually.
  Run repair at least every gc_grace_seconds (default 10 days).

================================================================
MULTI-REGION REPLICATION
================================================================

  Active-Passive: one region serves all traffic; second is standby.
  Failover is manual or automatic. Lower complexity.

  Active-Active: both regions serve traffic; changes replicated both ways.
  Conflict resolution is critical. DynamoDB Global Tables does this.

  Cassandra NetworkTopologyStrategy: RF per datacenter.
  With LOCAL_QUORUM consistency: quorum within local DC only (low latency).
  Writes replicate asynchronously to other DCs.

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between quorum and strong consistency?
  A: Quorum ensures W + R > RF, meaning at least one node overlaps between
     write set and read set, guaranteeing you see the latest write.
     Strong consistency (linearizability) is stricter: every read returns
     the result of the most recent write, even without W+R>RF. MongoDB with
     w:majority and readConcern:majority provides strong consistency within
     replica set. Cassandra with QUORUM provides tunable strong consistency.

  Q: How does MongoDB handle primary failure?
  A: Secondaries detect primary unavailability via heartbeats. After an
     election timeout (~10s), secondaries vote. The secondary with the most
     up-to-date oplog and majority votes wins. During election, writes fail.
     With 3 members (RF=3), election needs 2 votes -- always achievable
     unless 2 nodes are down simultaneously.

  Q: What is hinted handoff?
  A: When a target replica is temporarily down, the coordinator stores the
     write as a "hint" (a note saying "deliver this to node X when it
     returns"). When the target comes back online, the hint is delivered.
     This prevents write failures during short node outages while maintaining
     eventual consistency.
