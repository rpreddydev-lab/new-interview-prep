================================================================
  ROLES AND PRIVILEGES
================================================================

  A role is a named collection of privileges.
  Users inherit privileges from their assigned roles.
  Roles can also be granted to other roles (role hierarchy).

================================================================
WHY ROLES
================================================================

  Without roles: grant same 20 privileges to each of 100 users.
  Adding a new table requires 100 GRANT statements.

  With roles: grant to the role once; users inherit automatically.
  Adding a new table: one GRANT to the role.

================================================================
CREATING AND ASSIGNING ROLES
================================================================

  Create a role:
  CREATE ROLE analyst;
  CREATE ROLE app_writer;
  CREATE ROLE admin_role;

  Grant privileges to the role:
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO analyst;
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_writer;
  GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO admin_role;

  Assign role to users:
  GRANT analyst   TO alice;
  GRANT app_writer TO bob;
  GRANT app_writer TO service_account;

  Remove role from user:
  REVOKE analyst FROM alice;

================================================================
ROLE HIERARCHY
================================================================

  Roles can be granted to other roles:
  CREATE ROLE senior_analyst;
  GRANT analyst TO senior_analyst;       -- senior_analyst includes analyst's privileges
  GRANT INSERT ON reports TO senior_analyst;

  GRANT senior_analyst TO carol;
  -- carol gets SELECT (from analyst) + INSERT on reports (from senior_analyst)

================================================================
TYPICAL PRODUCTION ROLE STRUCTURE
================================================================

  Role             Privileges
  ---------------  --------------------------------------------------
  read_only        SELECT on all tables
  app_user         SELECT, INSERT, UPDATE, DELETE + sequence USAGE
  reporting        SELECT on all tables + CONNECT to reporting schema
  migration_user   DDL: CREATE, ALTER, DROP (used by Flyway/Liquibase)
  admin            ALL PRIVILEGES (restricted to DBA accounts)

================================================================
POSTGRESQL BUILT-IN ROLES (pg_ prefixed)
================================================================

  pg_read_all_data     SELECT on all tables in all schemas
  pg_write_all_data    INSERT/UPDATE/DELETE on all tables
  pg_monitor           Access to monitoring views (pg_stat_*)
  pg_signal_backend    Can send signals to other backends
  pg_read_server_files Read files from server filesystem

  GRANT pg_read_all_data TO reporting_service;

================================================================
MYSQL USER AND ROLE MANAGEMENT
================================================================

  CREATE USER 'alice'@'localhost' IDENTIFIED BY 'password';
  CREATE ROLE 'analyst_role';
  GRANT SELECT ON mydb.* TO 'analyst_role';
  GRANT 'analyst_role' TO 'alice'@'localhost';
  SET DEFAULT ROLE 'analyst_role' TO 'alice'@'localhost';

================================================================
CHECKING ROLES
================================================================

  PostgreSQL:
  \du                           -- list all roles and their attributes
  SELECT * FROM pg_roles;       -- programmatic
  SELECT * FROM pg_auth_members WHERE roleid = (SELECT oid FROM pg_roles WHERE rolname = 'analyst');

  MySQL:
  SHOW GRANTS FOR 'alice'@'localhost';
  SELECT * FROM information_schema.ROLE_TABLE_GRANTS;

================================================================
COLUMN-LEVEL SECURITY
================================================================

  Grant access to specific columns only:
  GRANT SELECT (id, name, email) ON customers TO support_agent;
  -- support_agent cannot see phone, ssn, salary columns

  PostgreSQL Row-Level Security (RLS) for row filtering:
  ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
  CREATE POLICY user_orders ON orders
      USING (customer_id = current_setting('app.user_id')::int);
  -- Each user can only see their own orders

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the benefit of using roles over granting directly to users?
  A: Single point of management. Grant privileges to role once;
     all role members inherit automatically. When requirements change,
     update the role and all members are updated. Scales to many users.

  Q: What is Row-Level Security?
  A: A PostgreSQL feature that adds predicates to table queries
     so each user/role only sees rows they are permitted to see,
     enforced at the storage engine level independent of application logic.

  Q: How would you revoke access from a user who has multiple roles?
  A: Either revoke the specific role from the user, or if they have
     privileges from multiple roles, revoke each role individually.
     Revoking from the user directly only removes directly-granted privileges.
