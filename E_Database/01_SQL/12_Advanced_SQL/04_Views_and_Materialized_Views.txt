================================================================
  VIEWS AND MATERIALIZED VIEWS
================================================================

================================================================
VIEWS
================================================================

  A view is a named, stored SQL query.
  It behaves like a virtual table.
  No data is stored -- query runs every time the view is accessed.

  CREATE OR REPLACE VIEW active_customers AS
  SELECT id, name, email, created_at
  FROM customers
  WHERE status = 'ACTIVE';

  SELECT * FROM active_customers WHERE created_at > '2024-01-01';

  Benefits:
  - Simplify complex queries for application developers
  - Enforce row/column security (expose only certain data)
  - Provide stable API even if underlying table structure changes

================================================================
UPDATABLE VIEWS
================================================================

  A view is automatically updatable if:
  - Based on a single table (no JOINs, no GROUP BY, no DISTINCT)
  - No aggregate or window functions
  - No UNION

  UPDATE active_customers
  SET name = 'Ray'
  WHERE id = 1;
  -- Translates to: UPDATE customers SET name='Ray' WHERE id=1 AND status='ACTIVE'

  WITH CHECK OPTION:
  Prevents INSERT/UPDATE through the view if the new row
  would not be visible through the view.

  CREATE VIEW active_customers AS
  SELECT * FROM customers WHERE status = 'ACTIVE'
  WITH CHECK OPTION;

  INSERT INTO active_customers (name, status) VALUES ('Bob', 'INACTIVE');
  -- ERROR: violates check option

================================================================
SECURITY WITH VIEWS
================================================================

  Grant SELECT on the view, not on the underlying table:

  GRANT SELECT ON active_customers TO reporting_user;
  REVOKE SELECT ON customers FROM reporting_user;

  Now reporting_user can only see active customers.

================================================================
MATERIALIZED VIEWS
================================================================

  A materialized view stores the result of the query on disk.
  Unlike a regular view, it does not re-run the query each access.
  Must be refreshed explicitly to get fresh data.

  CREATE MATERIALIZED VIEW monthly_revenue_mv AS
  SELECT
      DATE_TRUNC('month', order_date) AS month,
      SUM(total)                      AS revenue,
      COUNT(*)                        AS order_count
  FROM orders
  GROUP BY 1;

  -- Access:
  SELECT * FROM monthly_revenue_mv ORDER BY month;

================================================================
REFRESHING MATERIALIZED VIEWS
================================================================

  REFRESH MATERIALIZED VIEW monthly_revenue_mv;
  -- Blocks reads during refresh (takes exclusive lock)

  REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_revenue_mv;
  -- Allows reads during refresh
  -- Requires at least one UNIQUE index on the MV

  CREATE UNIQUE INDEX ON monthly_revenue_mv (month);
  -- Now CONCURRENTLY works

================================================================
INDEXES ON MATERIALIZED VIEWS
================================================================

  Materialized views support indexes, unlike regular views.

  CREATE INDEX ON monthly_revenue_mv (month);
  CREATE INDEX ON monthly_revenue_mv (revenue DESC);

================================================================
REGULAR VIEW vs MATERIALIZED VIEW
================================================================

  Feature                Regular View        Materialized View
  -------------------    ----------------    --------------------
  Data stored?           No                  Yes (on disk)
  Always fresh?          Yes                 No (needs REFRESH)
  Index support?         No                  Yes
  Query overhead?        Every access        Only at REFRESH time
  Best for?              Security/reuse      Heavy pre-computed aggs
  Read performance       Depends on base     Very fast (precomputed)

================================================================
DROPPING VIEWS
================================================================

  DROP VIEW active_customers;
  DROP VIEW IF EXISTS active_customers;

  DROP MATERIALIZED VIEW monthly_revenue_mv;

  CASCADE -- also drops dependent views
  DROP VIEW base_view CASCADE;

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a view in SQL?
  A: A named stored query. Acts as a virtual table -- no data stored.
     Query re-runs on every access.

  Q: When would you use a materialized view?
  A: When you have expensive aggregation queries that run frequently
     and the data does not need to be real-time (stale by minutes/hours is OK).
     Example: BI dashboards showing daily revenue totals.

  Q: What is the difference between a view and a materialized view?
  A: View: virtual, no storage, always fresh, no indexes.
     Materialized view: stored on disk, stale until refreshed,
     supports indexes, fast reads.

  Q: How do you prevent stale data from being exposed in a view?
  A: For regular views: always fresh, no action needed.
     For materialized views: schedule REFRESH on a cron job or event trigger.
     Use REFRESH CONCURRENTLY if uptime during refresh is required.
