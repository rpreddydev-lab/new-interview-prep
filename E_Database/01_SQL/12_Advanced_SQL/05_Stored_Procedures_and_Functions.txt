  STORED PROCEDURES AND FUNCTIONS
================================================================

================================================================
FUNCTION VS PROCEDURE
================================================================

  Feature             Function                    Procedure
  ----------------    -----------------------     ----------------------
  Returns value?      Yes (RETURNS clause)        No (or via OUT params)
  Called via         SELECT / expression         CALL statement
  Transaction ctrl   Cannot commit/rollback      CAN commit/rollback (PG11+)
  Side effects       Usually pure (no DML)       Can do INSERT/UPDATE/DELETE
  Use case           Calculations, transforms    Multi-step business logic

================================================================
CREATE FUNCTION (PostgreSQL PL/pgSQL)
================================================================

  CREATE OR REPLACE FUNCTION calculate_discount(
      price       NUMERIC,
      pct         NUMERIC DEFAULT 10
  )
  RETURNS NUMERIC
  LANGUAGE plpgsql
  IMMUTABLE  -- result depends only on inputs, no DB lookups
  AS $$
  BEGIN
      RETURN price * (1 - pct / 100.0);
  END;
  $$;

  -- Usage:
  SELECT product_name, calculate_discount(price, 15) AS discounted
  FROM products;

================================================================
FUNCTION WITH TABLE QUERY
================================================================

  CREATE OR REPLACE FUNCTION get_orders_for_customer(cust_id INT)
  RETURNS TABLE (order_id INT, total NUMERIC, status TEXT)
  LANGUAGE plpgsql
  STABLE  -- reads DB but won't change for same args in same tx
  AS $$
  BEGIN
      RETURN QUERY
          SELECT id, total, status
          FROM orders
          WHERE customer_id = cust_id
          ORDER BY created_at DESC;
  END;
  $$;

  -- Usage:
  SELECT * FROM get_orders_for_customer(42);

================================================================
CREATE PROCEDURE (PostgreSQL PL/pgSQL)
================================================================

  CREATE OR REPLACE PROCEDURE transfer_funds(
      from_account_id INT,
      to_account_id   INT,
      amount          NUMERIC
  )
  LANGUAGE plpgsql
  AS $$
  BEGIN
      UPDATE accounts SET balance = balance - amount WHERE id = from_account_id;
      UPDATE accounts SET balance = balance + amount WHERE id = to_account_id;
      INSERT INTO audit_log (action, amount, ts) VALUES ('TRANSFER', amount, NOW());
      COMMIT;  -- Procedures can commit in PostgreSQL 11+
  END;
  $$;

  -- Usage:
  CALL transfer_funds(101, 202, 500.00);

================================================================
VOLATILITY CATEGORIES
================================================================

  IMMUTABLE  -- Returns same result for same args, no DB access.
               Best optimization; function can be inlined, indexed.
               Example: lower(text), abs(numeric)

  STABLE     -- Returns same result for same args within one transaction.
               Reads DB, but does not modify. Planner can cache per query.
               Example: to_char(date, 'YYYY-MM')

  VOLATILE   -- Default. Can return different result each call.
               Side effects. Cannot be optimized or cached.
               Example: NOW(), RANDOM(), functions that do INSERT

================================================================
SECURITY DEFINER vs INVOKER
================================================================

  SECURITY DEFINER: function runs with privileges of the function OWNER.
  Allows controlled access to tables the caller cannot see.

  SECURITY INVOKER (default): function runs with caller's privileges.

  -- Admin creates a function that gives limited delete access:
  CREATE OR REPLACE FUNCTION archive_old_orders()
  RETURNS VOID
  LANGUAGE plpgsql
  SECURITY DEFINER  -- runs as owner (dba role), not as caller
  AS $$
  BEGIN
      DELETE FROM orders WHERE created_at < NOW() - INTERVAL '3 years';
  END;
  $$;

  GRANT EXECUTE ON FUNCTION archive_old_orders() TO app_user;
  -- app_user can call but cannot directly DELETE from orders

CALLING FROM JAVA (Spring JPA)
================================================================

  // Call stored procedure with @NamedStoredProcedureQuery
  @NamedStoredProcedureQuery(
      name = "transfer",
      procedureName = "transfer_funds",
      parameters = {
          @StoredProcedureParameter(mode=IN, name="from_account_id", type=Integer.class),
          @StoredProcedureParameter(mode=IN, name="to_account_id",   type=Integer.class),
          @StoredProcedureParameter(mode=IN, name="amount",          type=BigDecimal.class)
      }
  )

  StoredProcedureQuery q = em.createNamedStoredProcedureQuery("transfer");
  q.setParameter("from_account_id", 101);
  q.setParameter("to_account_id",   202);
  q.setParameter("amount",          new BigDecimal("500.00"));
  q.execute();

  // Or with Spring @Query (PostgreSQL function returning table):
  @Query(value = "SELECT * FROM get_orders_for_customer(:custId)", nativeQuery = true)
  List<OrderDto> findOrdersForCustomer(@Param("custId") int custId);

================================================================
PROS AND CONS OF STORED PROCEDURES
================================================================

  Pros:
  - Logic close to data -- reduces round trips
  - Can be granted fine-grained execution permissions
  - Reusable across applications and languages
  - Encapsulates multi-step business logic

  Cons:
  - Hard to version-control, test, and debug
  - Couples business logic to the database
  - Harder to deploy/rollback than application code
  - Difficult to unit test without a real DB
  - Poor visibility in application logs and tracing

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between a function and a stored procedure?
  A: A function returns a value and is used in expressions or SELECT.
     A procedure performs actions (INSERT/UPDATE/DELETE) and is called with CALL.
     Procedures can commit/rollback; functions (in PostgreSQL) cannot.

  Q: What is SECURITY DEFINER used for?
  A: It makes a function execute with the owner's privileges.
     Useful for controlled access: let a low-privilege user call a function
     that internally accesses tables they can't directly query.

  Q: What does IMMUTABLE mean for a function?
  A: The function always returns the same result for the same inputs
     and has no side effects. The planner can inline/optimize it aggressively.
