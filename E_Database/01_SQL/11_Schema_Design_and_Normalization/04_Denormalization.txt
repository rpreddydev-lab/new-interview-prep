================================================================
  DENORMALIZATION
================================================================

  Denormalization is the deliberate introduction of redundancy
  to improve read performance at the cost of data integrity complexity.

================================================================
WHY DENORMALIZE
================================================================

  Normalized schemas require many JOINs for complex reports.
  JOINs across millions of rows are expensive.
  Denormalization trades write complexity for read speed.

  Common in: reporting tables, caches, data warehouses (OLAP),
             read replicas, materialized views.

================================================================
COMMON DENORMALIZATION TECHNIQUES
================================================================

  1. STORE COMPUTED COLUMNS
  Normalized: total_price computed at query time: SUM(qty * price)
  Denormalized: order.total stored column, updated on order change

  2. DUPLICATE DATA FROM LOOKUP TABLES
  Normalized: order_items has product_id FK, join products for name
  Denormalized: order_items.product_name = snapshot at order time
  Note: order history SHOULD store product name at time of purchase
        (correct behavior, not just performance trick)

  3. FLATTEN HIERARCHIES
  Normalized: employees -> departments -> locations -> regions
  Denormalized: employees.region_name (prejoined column)

  4. ADD SUMMARY/AGGREGATE COLUMNS
  Normalized: COUNT(*) from orders every time
  Denormalized: customers.order_count column, updated via trigger or app

  5. COMBINE RELATED SMALL TABLES
  Normalized: address in separate table
  Denormalized: address columns directly on customers table

================================================================
EXAMPLE: NORMALIZED vs DENORMALIZED
================================================================

  Normalized order report query:
  SELECT o.id, c.name, c.email, SUM(oi.qty * p.price) AS total
  FROM orders o
  JOIN customers c    ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id   = o.id
  JOIN products p     ON oi.product_id = p.id
  GROUP BY o.id, c.name, c.email;

  Denormalized order_report table (updated by trigger or ETL):
  SELECT id, customer_name, customer_email, total
  FROM order_report;
  -- Single table scan, no JOINs

================================================================
DENORMALIZATION METHODS
================================================================

  Method               Pros                  Cons
  -------------------  --------------------  --------------------------
  Computed columns     Simple queries        Must be maintained on write
  Materialized views   DB-managed refresh    Stale data between refreshes
  Summary tables       Fastest reads         Complex ETL to keep updated
  Data duplication     No JOINs              Risk of inconsistency
  JSONB column         Flexible schema       Complex to query inside JSON

================================================================
MATERIALIZED VIEWS
================================================================

  PostgreSQL MATERIALIZED VIEW:
  CREATE MATERIALIZED VIEW order_summary AS
  SELECT
      o.id,
      c.name AS customer_name,
      SUM(oi.qty * oi.price) AS total
  FROM orders o
  JOIN customers c    ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id   = o.id
  GROUP BY o.id, c.name;

  REFRESH MATERIALIZED VIEW order_summary;
  REFRESH MATERIALIZED VIEW CONCURRENTLY order_summary; -- non-blocking

  Regular views are NOT materialized (recomputed on every query).
  Materialized views store the result physically.

================================================================
WHEN TO DENORMALIZE
================================================================

  DO denormalize when:
  - Reporting queries are slow and JOIN optimization is exhausted
  - Read:write ratio is very high (read-heavy)
  - Historical snapshots are needed (price at time of purchase)
  - OLAP/data warehouse workload

  DON'T denormalize when:
  - Data updates are frequent and keeping redundant copies in sync is hard
  - Inconsistency risk is unacceptable
  - Proper indexing has not been tried first

================================================================
INTERVIEW Q&A
================================================================

  Q: What is denormalization and why would you do it?
  A: Deliberately adding redundancy to improve read performance.
     Useful for reporting/OLAP, caches, and summary tables where
     the query cost of JOINs outweighs the write overhead of maintenance.

  Q: What is a materialized view?
  A: A precomputed, stored query result. Unlike a regular view (which is
     a query alias), a materialized view stores data physically and can be
     indexed. Must be refreshed when base data changes.

  Q: What is the risk of denormalization?
  A: Data inconsistency. If a denormalized copy is not updated when the
     source changes, queries will return stale or incorrect data.
