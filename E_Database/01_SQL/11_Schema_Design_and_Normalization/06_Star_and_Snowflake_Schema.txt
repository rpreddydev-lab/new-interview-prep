================================================================
  STAR AND SNOWFLAKE SCHEMA
================================================================

  Used in data warehouses and OLAP systems.
  Designed for fast analytical reads, not OLTP writes.

================================================================
OLTP vs OLAP
================================================================

  OLTP (Online Transaction Processing)
  - Normalized (3NF / BCNF)
  - Many small reads/writes
  - Low latency per transaction
  - Avoids data redundancy
  - Examples: order entry, banking transactions

  OLAP (Online Analytical Processing)
  - Denormalized (Star or Snowflake)
  - Large scans over millions of rows
  - Aggregations: SUM, COUNT, AVG by dimensions
  - Read-heavy, batch-loaded
  - Examples: sales dashboards, BI reports

================================================================
FACT TABLE
================================================================

  Contains measurable, quantitative data (metrics / measures).
  Large, usually hundreds of millions of rows.
  Has FK columns to dimension tables.
  Often append-only.

  Columns:
  - Surrogate key (PK)
  - FK to each dimension (customer_key, product_key, date_key)
  - Measures: revenue, qty_sold, discount_amount, return_flag

  Example: fact_sales
  sale_id | date_key | customer_key | product_key | store_key | qty | revenue | cost

================================================================
DIMENSION TABLE
================================================================

  Contains descriptive, textual, categorical data (attributes).
  Smaller, usually thousands to millions of rows.
  Provides context to the facts.

  Example: dim_customer
  customer_key | customer_id | name | city | state | country | segment

  Example: dim_product
  product_key | product_id | name | brand | category | sub_category | size | color

  Example: dim_date
  date_key | date | day_of_week | month | quarter | year | is_holiday

================================================================
STAR SCHEMA
================================================================

  Fact table at center. Dimension tables surround it (like a star).
  Dimension tables are DENORMALIZED (flat -- all attributes in one table).

  fact_sales
    +-- dim_date       (date_key)
    +-- dim_customer   (customer_key)
    +-- dim_product    (product_key)
    +-- dim_store      (store_key)

  Advantages:
  - Simple queries -- usually just fact JOIN dimensions
  - Fewer JOINs -- good for BI tools
  - Query optimizer can cache dimensions easily
  - Easy to understand for business users

  Disadvantages:
  - Dimension tables have redundant data
  - Updates to a dimension attribute require updating many rows

================================================================
SNOWFLAKE SCHEMA
================================================================

  Like Star schema but dimension tables are NORMALIZED.
  Sub-dimensions broken into their own tables.

  dim_product --> dim_category --> dim_department
  dim_customer --> dim_city --> dim_state --> dim_country

  fact_sales
    +-- dim_date
    +-- dim_customer (city_key FK)
         +-- dim_city (state_key FK)
              +-- dim_state (country_key FK)
                   +-- dim_country
    +-- dim_product (category_key FK)
         +-- dim_category (department_key FK)
              +-- dim_department

  Advantages:
  - Less redundant storage
  - Easier dimension attribute updates
  - More normalized -- closer to OLTP design

  Disadvantages:
  - More JOINs per query
  - Slower analytical queries
  - More complex ETL and BI tool configuration

================================================================
STAR vs SNOWFLAKE COMPARISON
================================================================

  Feature               Star Schema         Snowflake Schema
  ---------------       ----------------    ----------------
  Dimension tables      Denormalized        Normalized
  Number of tables      Fewer               More
  Query complexity      Simple              More JOINs
  Query performance     Faster reads        Slower (more joins)
  Storage               More redundancy     Less redundancy
  Update ease           Harder              Easier
  ETL complexity        Simpler             More complex
  Common tools          Tableau, Power BI   Snowflake DB (ironic)

  Rule of thumb:
  Choose Star for query speed.
  Choose Snowflake when dimensions change frequently or storage matters.

================================================================
SLOWLY CHANGING DIMENSIONS (SCD)
================================================================

  Problem: Customer moves to a new city.
  How do you handle history in a dimension table?

  SCD Type 1 -- Overwrite:
    Just update the row. No history kept.
    UPDATE dim_customer SET city = 'Austin' WHERE customer_key = 42;

  SCD Type 2 -- Add new row (most common):
    Insert new row with new values.
    Mark old row as expired. Add effective_date / expiry_date columns.
    customer_key | customer_id | city    | is_current | effective_date | expiry_date
    42           | 1001        | Houston | N          | 2020-01-01     | 2023-06-30
    99           | 1001        | Austin  | Y          | 2023-07-01     | NULL

  SCD Type 3 -- Add column:
    Add a "previous_value" column.
    city_previous | city_current
    Houston       | Austin
    Simple but only keeps one history step.

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a fact table vs a dimension table?
  A: Fact table contains quantitative measures (revenue, qty) plus FK keys.
     Dimension table contains descriptive attributes (customer name, city, category).
     Fact is large; dimensions are smaller lookup tables.

  Q: What is a Star schema?
  A: One central fact table surrounded by denormalized dimension tables.
     Minimizes JOINs. Best for OLAP query performance.

  Q: How does a Snowflake schema differ from a Star schema?
  A: Snowflake normalizes the dimension tables into sub-dimension tables.
     Results in more JOINs but less data redundancy.

  Q: What is a Slowly Changing Dimension?
  A: A dimension whose attributes change over time (e.g., customer moves city).
     SCD Type 2 handles this by adding new rows and tracking effective dates.

  Q: Why not use 3NF for a data warehouse?
  A: 3NF minimizes redundancy but requires many JOINs.
     Analytics scans huge datasets -- fewer JOINs = faster queries.
     Denormalized star schema significantly improves read performance.
