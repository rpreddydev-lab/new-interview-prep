================================================================
  TRANSACTIONS AND CONCURRENCY: OVERVIEW
================================================================

  A transaction is a sequence of operations treated as a single unit.
  Concurrency control prevents transactions from interfering with each other.

================================================================
THE NEED FOR TRANSACTIONS
================================================================

  Without transactions:
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  -- Server crashes here --
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
  --> $100 vanishes: debit done, credit never happened

  With transactions:
  If crash between the two updates, ROLLBACK on recovery ensures
  neither update survives.

================================================================
CONCURRENCY PROBLEMS WITHOUT ISOLATION
================================================================

  Problem          Description
  ---------------  --------------------------------------------------
  Dirty Read       Transaction reads uncommitted data from another tx
  Non-Repeatable  Same row read twice gives different values (another
  Read             tx committed an UPDATE between reads)
  Phantom Read     Same query returns different SET of rows (another
                   tx committed INSERT/DELETE affecting the result set)
  Lost Update      Two transactions read same value, both update based
                   on read -- one update overwrites the other

================================================================
SOLUTIONS
================================================================

  Isolation levels:    Sacrifice concurrency for correctness
  MVCC:                Snapshot-based reads don't block writes
  Locking:             Pessimistic -- explicitly lock rows/tables
  Optimistic locking:  Detect conflicts at commit via version column

================================================================
MVCC (MULTI-VERSION CONCURRENCY CONTROL)
================================================================

  PostgreSQL and MySQL InnoDB use MVCC.
  Old row versions are kept alongside new versions.
  Readers see a snapshot of data at transaction start time.
  Writers create new versions; readers don't block writers.

  Advantages:
  - Readers never block writers
  - Writers never block readers
  - Better throughput than pure locking

  Cost:
  - Dead tuples accumulate (old versions)
  - VACUUM (PostgreSQL) or purge thread (MySQL) cleans them up

================================================================
INTERVIEW Q&A
================================================================

  Q: What are the four ACID properties?
  A: Atomicity (all or nothing), Consistency (valid state transitions),
     Isolation (concurrent transactions don't see each other's work),
     Durability (committed data survives crashes).

  Q: What is MVCC?
  A: Multi-Version Concurrency Control. Databases keep multiple versions
     of rows. Readers see a consistent snapshot from transaction start;
     writers create new versions. Readers don't block writers and vice versa.
