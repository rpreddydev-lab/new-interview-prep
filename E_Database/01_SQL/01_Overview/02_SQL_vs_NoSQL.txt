================================================================
  SQL vs NoSQL
================================================================

  This is one of the most common system design and architecture
  interview topics. Know when to use each and WHY.

================================================================
RELATIONAL (SQL) DATABASES
================================================================

  Structure:    Tables, rows, columns. Fixed schema.
  Query:        SQL — rich, standardized, joins across tables.
  Consistency:  ACID transactions (Atomicity, Consistency, Isolation, Durability).
  Scaling:      Primarily vertical (bigger machine); horizontal sharding is complex.
  Examples:     PostgreSQL, MySQL, Oracle, SQL Server, SQLite.

  Best for:
  - Complex relationships between entities (foreign keys, joins)
  - Financial data requiring strict ACID transactions
  - Reporting and analytics with complex queries
  - Data with well-defined, stable schema
  - Applications needing strong consistency

================================================================
NON-RELATIONAL (NOSQL) DATABASES
================================================================

  Structure:    Flexible: documents, key-value, wide-column, graph.
  Query:        DB-specific API or query language (no universal standard).
  Consistency:  Often BASE (Basically Available, Soft state, Eventually consistent).
  Scaling:      Designed for horizontal scaling (sharding, replication built-in).
  Examples:     MongoDB, Cassandra, Redis, DynamoDB, Neo4j, Elasticsearch.

  Best for:
  - Unstructured or semi-structured data
  - High write throughput / massive scale
  - Schema that changes frequently
  - Simple access patterns (key lookups, document retrieval)
  - Specific workloads: caching (Redis), graph traversal (Neo4j), full-text (Elasticsearch)

================================================================
NOSQL TYPES
================================================================

  Document:       MongoDB, CouchDB, DynamoDB
  Key-Value:      Redis, DynamoDB, Riak
  Wide-Column:    Cassandra, HBase, DynamoDB
  Graph:          Neo4j, Amazon Neptune
  Search:         Elasticsearch, Solr, OpenSearch
  Time Series:    InfluxDB, TimescaleDB

================================================================
COMPARISON TABLE
================================================================

  Feature              SQL                      NoSQL
  -------------------  -----------------------  ----------------------------
  Schema               Fixed, defined upfront   Flexible, can vary per row
  Query language       Standard SQL             DB-specific API
  Joins                First-class support      Usually avoided (denormalize)
  Transactions         Full ACID                Varies (Redis/Mongo improving)
  Scalability          Vertical (primarily)     Horizontal (designed for it)
  Consistency model    Strong (ACID)            Often eventual (BASE)
  Best for             Relations, reports       Scale, flexibility, speed
  Relationships        FK, normalization        Embedding or denormalization
  Examples             PostgreSQL, MySQL         MongoDB, Cassandra, Redis

================================================================
CAP THEOREM
================================================================

  In a distributed system, you can guarantee only 2 of 3:

  C — Consistency: all nodes see the same data at the same time
  A — Availability: every request receives a response
  P — Partition Tolerance: system works despite network partitions

  Network partitions are inevitable in distributed systems,
  so you're really choosing: CP or AP.

  SQL databases: typically CP (consistent + partition tolerant)
  Cassandra, DynamoDB: AP (available + partition tolerant, eventually consistent)
  Redis standalone: CP; Redis Cluster: AP (configurable)

================================================================
WHEN TO CHOOSE SQL
================================================================

  1. FINANCIAL / TRANSACTIONAL DATA
     Banking, order payments, inventory deduction — all-or-nothing.
     ACID required: partial failure = disaster.

  2. COMPLEX RELATIONSHIPS
     Users → Orders → OrderItems → Products → Categories
     JOINs are efficient and readable.
     NoSQL would require massive denormalization.

  3. REPORTING AND ANALYTICS
     SELECT region, SUM(revenue), COUNT(*) GROUP BY quarter
     Rich aggregation, window functions, CTEs.

  4. KNOWN, STABLE SCHEMA
     HR systems, ERP, accounting — schema is well understood.

  5. DATA INTEGRITY
     Foreign key constraints, UNIQUE constraints, CHECK constraints
     prevent corrupt data at the DB level.

================================================================
WHEN TO CHOOSE NOSQL
================================================================

  1. HUGE SCALE + HIGH WRITE THROUGHPUT
     Social media feeds, IoT sensor data, clickstream events.
     Cassandra can handle millions of writes/second per cluster.

  2. FLEXIBLE / EVOLVING SCHEMA
     Product catalog: electronics have different attributes than clothing.
     MongoDB document per product, no schema migration needed.

  3. SIMPLE ACCESS PATTERNS
     Session storage: get/set by user ID → Redis.
     User profile: get full document by userId → MongoDB.
     Complex joins are an anti-pattern in NoSQL.

  4. SPECIFIC CAPABILITIES
     Caching → Redis
     Full-text search → Elasticsearch
     Graph traversal → Neo4j
     Time series → InfluxDB

  5. GEOGRAPHIC DISTRIBUTION
     Cassandra/DynamoDB built for multi-region, multi-active deployments.

================================================================
POLYGLOT PERSISTENCE
================================================================

  Most large systems use multiple databases for different concerns:

  Example e-commerce platform:
  PostgreSQL    — orders, payments, inventory (ACID critical)
  MongoDB       — product catalog (flexible schema)
  Redis         — session cache, cart (low latency key-value)
  Elasticsearch — product search (full-text, facets)
  Cassandra     — user activity log, analytics (high write throughput)

  Rule: use the right tool for each job.
  Anti-pattern: forcing all data into one technology.

================================================================
INTERVIEW Q&A
================================================================

  Q: When would you choose SQL over NoSQL?
  A: When you have complex relationships requiring joins, strict ACID
     transactions (financial data), complex reporting needs, or a
     well-defined stable schema.

  Q: When would you choose NoSQL over SQL?
  A: For massive scale with high write throughput, flexible/evolving schema,
     simple access patterns, or workload-specific needs (caching, full-text,
     graph traversal).

  Q: What is the CAP theorem?
  A: Distributed systems can guarantee at most 2 of: Consistency, Availability,
     Partition Tolerance. Since partitions are unavoidable, real choice is
     CP (consistent) vs AP (available). SQL DBs are typically CP; Cassandra is AP.

  Q: What is BASE?
  A: Basically Available, Soft state, Eventually consistent.
     The consistency model of many NoSQL systems vs ACID in SQL.
     Data will be consistent eventually, not immediately after a write.

  Q: Can you use both?
  A: Yes — polyglot persistence. Use PostgreSQL for transactional data,
     Redis for caching, Elasticsearch for search, Cassandra for time-series.
     Each tool for its optimal workload.
