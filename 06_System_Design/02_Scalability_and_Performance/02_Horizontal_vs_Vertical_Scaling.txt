================================================================
HORIZONTAL vs VERTICAL SCALING
================================================================

OVERVIEW
---------
When a system needs to handle more load, there are two fundamental
approaches: scale up (vertical) or scale out (horizontal).

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
VERTICAL SCALING (Scale Up)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION: Add more resources to a single machine.
  - More CPU cores
  - More RAM
  - Faster/larger SSDs
  - Faster network interface cards (NICs)

Example:
  Before: 1 server — 4 CPU cores, 16 GB RAM, 500 GB SSD
  After:  1 server — 32 CPU cores, 256 GB RAM, 4 TB NVMe SSD

ADVANTAGES:
  ✓ Simple — no change to application code
  ✓ No distributed systems complexity (no need for data sync)
  ✓ Low latency (no network hops for inter-process communication)
  ✓ Easier to maintain (1 machine vs 100)
  ✓ Good for stateful systems (databases, stateful ML models)

DISADVANTAGES:
  ✗ Hard limit — there's a maximum size for a single machine
    (AWS largest instance: u-24tb1.112xlarge → 112 vCPU, 24TB RAM)
  ✗ Expensive — bigger machines cost disproportionately more
  ✗ Single point of failure — one machine = total outage if it fails
  ✗ Requires downtime during upgrade (in most cases)
  ✗ Doesn't improve fault tolerance

WHEN TO USE VERTICAL SCALING:
  - Early-stage products with small user bases
  - Legacy monolithic applications (hard to refactor for horizontal scaling)
  - Databases that are difficult to shard (PostgreSQL, MySQL initially)
  - ML inference servers with high memory needs
  - When the bottleneck is purely single-threaded (some DBs, legacy apps)

VERTICAL SCALING LIMITS (AWS examples):
  General Purpose: r6g.16xlarge → 64 vCPU, 512 GB RAM
  Memory Optimized: u-24tb1.112xlarge → 112 vCPU, 24 TB RAM
  Compute Optimized: c7g.16xlarge → 64 vCPU, 128 GB RAM

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
HORIZONTAL SCALING (Scale Out)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION: Add more machines to distribute the load.
  - Multiple identical servers behind a load balancer
  - Each server handles a portion of the total traffic

Example:
  Before: 1 server handling 10,000 req/s
  After:  10 servers each handling 1,000 req/s = 10,000 req/s total
          (add more servers as needed — 100, 1000, ...)

ADVANTAGES:
  ✓ Theoretically unlimited scale (just add more machines)
  ✓ Better fault tolerance (losing 1 of 10 servers = 10% capacity loss)
  ✓ Cost-effective at scale (commodity hardware is cheap)
  ✓ Zero downtime deployments (rolling updates)
  ✓ Geographic distribution — deploy in multiple regions/zones

DISADVANTAGES:
  ✗ Application must be stateless (or state must be externalized)
  ✗ Distributed systems complexity (partitioning, consensus, synchronization)
  ✗ More infrastructure to manage (monitoring, networking)
  ✗ Data consistency challenges
  ✗ Increased network latency for communication between nodes

PREREQUISITES FOR HORIZONTAL SCALING:
  1. Stateless Services
     - No local session state — use external session store (Redis)
     - Any server can handle any request
     - If Server A processed request 1, Server B can handle request 2
       without needing to know about request 1

  2. Load Balancer
     - Distributes incoming requests across server instances
     - Health checks to route away from unhealthy instances

  3. Shared External State
     - Sessions → Redis
     - Files → S3 or shared NFS
     - DB → central database (itself may need horizontal scaling)

  4. Idempotency
     - If a request is retried on a different server, it should not
       cause duplicate effects
     - Use idempotency keys for write operations

MAKING SERVICES STATELESS (The Key to Horizontal Scaling):
  ┌───────────────────────────────────────────────────────┐
  │  BEFORE (Stateful):                                   │
  │    Client → Server A (stores session in memory)       │
  │    Next request MUST go to Server A (sticky session)  │
  │                                                       │
  │  AFTER (Stateless):                                   │
  │    Client → Load Balancer → Any Server                │
  │    Session stored in Redis, any server reads it       │
  └───────────────────────────────────────────────────────┘

AUTO-SCALING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Auto-scaling dynamically adjusts the number of instances based on
load metrics. It's the key to cost-efficient horizontal scaling.

TYPES OF AUTO-SCALING:
  1. Target Tracking Scaling
     - Maintain a metric at a target value
     - "Keep average CPU utilization at 50%"
     - Auto-scales up when CPU > 50%, down when CPU < 50%

  2. Step Scaling
     - Scale by specific amounts at defined thresholds
     - "Add 2 instances when CPU > 70%; add 4 when CPU > 90%"

  3. Scheduled Scaling
     - Pre-emptively scale at known times
     - "Scale to 20 instances at 8am; scale down at 10pm"

  4. Predictive Scaling (ML-based)
     - Learn from historical patterns to pre-scale before traffic arrives

AUTO-SCALING CONSIDERATIONS:
  - Scale-out lag: It takes time (minutes) to provision new instances
    → Use target tracking with buffer (scale at 60% not 90%)
    → Pre-warm instances during expected traffic spikes
  - Cooldown period: Wait before scaling down to avoid thrashing
  - Health checks: New instances must pass health checks before receiving traffic
  - Warm-up time: JVM, connection pool initialization may take time

REAL-WORLD SCALING EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Netflix:
  - Horizontal scaling for streaming services (100K+ nodes on AWS)
  - Chaos Engineering (Chaos Monkey) to test resilience
  - Region-level isolation to prevent cascading failures
  - Auto-scaling based on stream count and CPU utilization

Instagram (2012 migration from vertical to horizontal):
  - Originally: 1 monolithic PostgreSQL server (vertical scaling)
  - Problem: Hitting hardware limits, single point of failure
  - Solution: Sharded PostgreSQL + read replicas + memcache
  - Scaled from 100K to 10M users during first 18 months

Twitter:
  - Fan-out service horizontally scaled across many workers
  - Redis clusters (horizontally scaled) for timeline caches
  - Separate read and write paths for different scaling strategies

INTERVIEW TALKING POINTS:
  - Always start with vertical scaling for simplicity, then migrate to
    horizontal as scale demands
  - The hardest part of horizontal scaling is the database tier
  - Stateless web/API tier is the easiest to scale horizontally
  - "We'd start with a monolith on a powerful machine, instrument it,
     identify bottlenecks, and then decompose strategically"
