================================================================
gRPC AND PROTOCOL BUFFERS
================================================================

OVERVIEW
---------
gRPC (Google Remote Procedure Call) is a high-performance, open-source
RPC (Remote Procedure Call) framework developed by Google.
It uses Protocol Buffers (protobuf) as its interface definition language
and wire format.

Widely used for microservice-to-microservice communication where:
  - Performance (low latency, high throughput) matters
  - Strong typing and code generation reduces errors
  - Bidirectional streaming is needed

PROTOCOL BUFFERS (PROTOBUF)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Protobuf is a language-neutral, platform-neutral, extensible mechanism
for serializing structured data.

DEFINING MESSAGES (.proto file):
  syntax = "proto3";
  
  package user;
  
  message User {
    int64  id         = 1;
    string name       = 2;
    string email      = 3;
    int64  created_at = 4;  // unix timestamp
  }
  
  message GetUserRequest {
    int64 user_id = 1;
  }
  
  message ListUsersRequest {
    int32 page      = 1;
    int32 page_size = 2;
  }
  
  message ListUsersResponse {
    repeated User users          = 1;
    string        next_page_token = 2;
  }
  
  service UserService {
    rpc GetUser(GetUserRequest)          returns (User);
    rpc ListUsers(ListUsersRequest)      returns (ListUsersResponse);
    rpc WatchUser(GetUserRequest)        returns (stream User);
    rpc BulkCreate(stream User)          returns (BulkCreateResponse);
    rpc Chat(stream Message)             returns (stream Message);
  }

FIELD NUMBERS:
  Each field has a unique number (1, 2, 3...).
  Field numbers 1-15 use 1 byte in the wire format (use for common fields).
  Field numbers 16-2047 use 2 bytes.
  NEVER change field numbers once deployed (breaks backward compatibility).
  You CAN add new fields; old clients ignore unknown fields.
  You CAN remove fields; mark them reserved to prevent reuse.

BINARY FORMAT EFFICIENCY:
  JSON:     { "id": 123, "name": "Alice" }  → 27 bytes
  Protobuf: field_1=123, field_2="Alice"    → ~12 bytes
  
  Protobuf is typically 3-10× smaller than JSON.
  Serialization is also 5-10× faster.

PROTOBUF vs JSON vs XML vs MessagePack:
  ┌─────────────┬──────────┬────────────┬──────────────────────────┐
  │ Format      │ Human    │ Size       │ Schema                   │
  │             │ Readable │            │                          │
  ├─────────────┼──────────┼────────────┼──────────────────────────┤
  │ JSON        │ Yes      │ Medium     │ Optional (JSON Schema)   │
  │ XML         │ Yes      │ Large      │ Yes (XSD)                │
  │ Protobuf    │ No       │ Small      │ Required (.proto)        │
  │ MessagePack │ No       │ Small      │ None                     │
  │ Avro        │ No       │ Very small │ Required (JSON schema)   │
  └─────────────┴──────────┴────────────┴──────────────────────────┘

gRPC ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC runs over HTTP/2.
HTTP/2 features that gRPC leverages:
  - Multiplexing: Many RPC calls on a single TCP connection
  - Flow control: Backpressure for streaming
  - Header compression: Reduces overhead
  - Binary framing: Efficient with protobuf

gRPC COMMUNICATION PATTERNS:

1. UNARY RPC (Request-Response, like REST):
   Client sends one request → server sends one response.
   
   rpc GetUser(GetUserRequest) returns (User);
   
   // Client call:
   User user = stub.getUser(GetUserRequest.of(userId))
   
   Use: CRUD operations, simple queries

2. SERVER STREAMING RPC:
   Client sends one request → server sends stream of responses.
   
   rpc ListLargeDataset(Query) returns (stream DataItem);
   
   // Client reads from stream until done:
   Iterator<DataItem> stream = stub.listLargeDataset(query)
   while (stream.hasNext()) {
     process(stream.next())
   }
   
   Use: Large result sets, live data feeds, file downloads

3. CLIENT STREAMING RPC:
   Client sends stream of requests → server sends one response.
   
   rpc BulkUpload(stream DataItem) returns (BulkUploadResult);
   
   // Client sends records:
   StreamObserver<DataItem> sender = stub.bulkUpload(responseObserver)
   records.forEach(r -> sender.onNext(r))
   sender.onCompleted()
   
   Use: Bulk import, file upload in chunks, telemetry data

4. BIDIRECTIONAL STREAMING RPC:
   Both client and server send streams independently.
   
   rpc Chat(stream Message) returns (stream Message);
   
   Use: Real-time chat, collaborative editing, IoT sensor data

CODE GENERATION:
  From .proto file, protoc generates:
  - Message classes (serialization/deserialization)
  - Service stub (client-side code to call the server)
  - Service interface (server-side interface to implement)
  
  Languages supported: Go, Java, Python, C++, Ruby, JavaScript, C#, PHP, Swift, Kotlin, Dart

gRPC FEATURES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LOAD BALANCING:
  gRPC connections are long-lived → traditional L7 LB doesn't work well.
  Solutions:
  a) Client-side load balancing: Client maintains list of servers,
     balances across them. Uses service discovery (Consul, Eureka).
  b) L7-aware proxy: Envoy, Nginx (with grpc_pass), Linkerd can load
     balance at the message level (not connection level).
  c) Service mesh: Istio/Linkerd handle gRPC load balancing automatically.

DEADLINE/TIMEOUT PROPAGATION:
  gRPC supports deadlines: client sets a deadline for the entire RPC call.
  Deadline propagates to all downstream services!
  If parent call has 500ms deadline, child calls budget must fit within.
  Prevents cascading failures from runaway long calls.
  
  // Set deadline: cancel if not complete within 2 seconds
  UserResponse resp = stub.withDeadlineAfter(2, TimeUnit.SECONDS)
                          .getUser(request)

METADATA (Headers):
  gRPC metadata ≈ HTTP headers.
  Used for auth tokens, trace IDs, request correlation.
  Key-value pairs sent with every call.

INTERCEPTORS (Middleware):
  Client-side and server-side interceptors for:
  - Logging and tracing (automatically log all calls)
  - Auth (validate token on every call)
  - Retry logic (retry on UNAVAILABLE status)
  - Rate limiting
  - Metrics collection

ERROR HANDLING (gRPC Status Codes):
  OK (0)                   → Success
  CANCELLED (1)            → Deadline exceeded by caller
  UNKNOWN (2)              → Unknown error
  INVALID_ARGUMENT (3)     → Client sent invalid data
  DEADLINE_EXCEEDED (4)    → Server exceeded deadline
  NOT_FOUND (5)            → Resource not found
  ALREADY_EXISTS (6)       → Resource already exists
  PERMISSION_DENIED (7)    → Auth failed
  RESOURCE_EXHAUSTED (8)   → Rate limit hit
  UNAVAILABLE (14)         → Server temporarily unavailable (retry)
  UNAUTHENTICATED (16)     → Missing/invalid credentials

HEALTH CHECKING:
  Standard gRPC health check protocol (grpc.health.v1.Health)
  rpc Check(HealthCheckRequest) returns (HealthCheckResponse)
  Status: SERVING, NOT_SERVING, SERVICE_UNKNOWN
  Used by load balancers (Kubernetes readiness probes support gRPC)

gRPC vs REST COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌────────────────────┬──────────────────────┬──────────────────────┐
│ Feature            │ gRPC                 │ REST (HTTP/JSON)     │
├────────────────────┼──────────────────────┼──────────────────────┤
│ Protocol           │ HTTP/2               │ HTTP/1.1 or HTTP/2   │
│ Payload            │ Protobuf (binary)    │ JSON (text)          │
│ Performance        │ Very high            │ Medium               │
│ Streaming          │ Bidirectional        │ SSE / WebSocket      │
│ Code generation    │ Yes (protoc)         │ Optional (OpenAPI)   │
│ Type safety        │ Strong               │ Weak (JSON)          │
│ Browser support    │ Limited (grpc-web)   │ Native               │
│ Human-readable     │ No (binary)          │ Yes (JSON)           │
│ Contract-first     │ Yes (.proto)         │ Optional             │
│ Ecosystem          │ Large (Google)       │ Massive (industry)   │
│ Debugging          │ Harder               │ Easy (curl, browser) │
│ Best for           │ Internal microsvcs   │ External APIs, web   │
└────────────────────┴──────────────────────┴──────────────────────┘

WHEN TO USE gRPC:
  ✓ Internal microservice communication (performance critical)
  ✓ Polyglot environments (auto-generated stubs for all languages)
  ✓ Streaming (bidirectional)
  ✓ Strict API contracts (schema evolution with backward compatibility)
  ✓ Real-time data (IoT, telemetry, gaming)

WHEN TO USE REST:
  ✓ Public APIs (browser, mobile, third-party clients)
  ✓ Simple CRUD with standard tooling
  ✓ When human readability and debugging ease matters
  ✓ When firewall/proxy compatibility is critical

gRPC IN PRACTICE (Architecture Patterns)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HYBRID PATTERN (most common):
  External APIs → REST (browser, mobile, third-party)
  Internal services → gRPC
  
  Client (React) ─── REST/JSON ──→ API Gateway
                                      │
                              ┌───────┴────────┐
                              │                │
                    gRPC ─→ User Service    gRPC ─→ Order Service
                              │
                    gRPC ─→ Auth Service

TRANSCODING (REST → gRPC):
  gRPC-Gateway: Generates REST/JSON proxy from .proto service annotations
  Envoy: Transcodes JSON/REST to protobuf/gRPC automatically
  
  Allows external clients to use REST while internal calls use gRPC.

USED BY:
  - Netflix: Internal microservice communication
  - Google: All internal services + many external APIs (Cloud APIs)
  - Uber: gRPC for real-time location updates
  - Square: Payment processing microservices
  - Lyft: Service mesh with Envoy (gRPC-native)
