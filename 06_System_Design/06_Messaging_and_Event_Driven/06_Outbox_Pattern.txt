================================================================
OUTBOX PATTERN
================================================================

THE PROBLEM: DUAL-WRITE INCONSISTENCY
---------------------------------------
Consider an order service that needs to:
  1. Save the order to its database.
  2. Publish an "OrderCreated" event to Kafka/RabbitMQ.

Naive implementation (WRONG):
  db.save(order)         // Step 1
  kafka.publish(event)   // Step 2

Race conditions:
  SCENARIO A: DB save succeeds, then process crashes before publishing.
    Result: Order exists in DB, but no event published.
    Effect: Inventory not updated, email not sent. Inconsistent!
  
  SCENARIO B: DB save fails (constraint violation), but event somehow published.
    Result: Event published for an order that doesn't exist in DB.
    Effect: Downstream services trying to process a ghost order.
  
  SCENARIO C: Network issue between app and Kafka.
    Result: Unpredictable — some events published, some not.

The fundamental problem: These are two separate systems.
You CANNOT atomically commit to a DB and publish to a message broker
in a single transaction (no distributed transaction).

THE OUTBOX PATTERN SOLUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IDEA: Write the event to an "outbox" table in the SAME database as your
business data. A separate process reads the outbox and publishes to
the message broker.

OUTBOX TABLE:
  CREATE TABLE outbox (
    id          UUID PRIMARY KEY,
    topic       VARCHAR(255) NOT NULL,   -- Kafka topic / queue name
    partition_key VARCHAR(255),          -- determines Kafka partition
    event_type  VARCHAR(255) NOT NULL,   -- "OrderCreated", "PaymentProcessed"
    payload     JSONB NOT NULL,          -- event data
    created_at  TIMESTAMP NOT NULL,
    published   BOOLEAN DEFAULT FALSE,   -- has it been published?
    published_at TIMESTAMP
  );

APPLICATION CODE:
  BEGIN TRANSACTION;
    INSERT INTO orders (id, user_id, amount) VALUES (...);
    INSERT INTO outbox (id, topic, event_type, payload)
      VALUES (gen_random_uuid(), 'orders', 'OrderCreated', '{"orderId":...}');
  COMMIT;
  -- Both writes happen atomically in ONE DB transaction.
  -- If transaction fails: neither row is written.
  -- If transaction succeeds: both rows written atomically.

OUTBOX PROCESSOR (separate process/thread):
  SELECT * FROM outbox WHERE published = FALSE ORDER BY created_at LIMIT 100;
  FOR EACH event:
    kafka.publish(event.topic, event.partition_key, event.payload);
    UPDATE outbox SET published = TRUE, published_at = NOW() WHERE id = event.id;

DELIVERY SEMANTICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Outbox Pattern guarantees AT-LEAST-ONCE delivery:
  - If outbox processor crashes after publishing but before marking as published:
    Event will be published AGAIN on restart (duplicate!).
  
  Solution: Consumers MUST be idempotent.
  Use event.id as idempotency key in consumer:
    IF event_id already processed (in processed_events table) → skip.
    ELSE → process + insert into processed_events.

IMPLEMENTATION APPROACHES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

APPROACH 1: POLLING THE OUTBOX TABLE
  Simple background job that polls outbox table.
  Query: SELECT * FROM outbox WHERE published = FALSE.
  Pros: Simple to implement.
  Cons: Polling adds latency (poll interval), DB load from polling.

APPROACH 2: CHANGE DATA CAPTURE (CDC) WITH DEBEZIUM (Best Practice)
  Debezium reads the database's WAL (Write-Ahead Log / binlog).
  Captures every INSERT/UPDATE/DELETE as a change event.
  Publishes change events to Kafka.
  
  For outbox table: Debezium captures INSERT into outbox table → Kafka.
  
  Advantages:
  ✓ Zero polling — events published within milliseconds of DB commit
  ✓ No additional DB load from polling
  ✓ Works even if application is down (WAL captures all changes)
  ✓ Can route different event types to different Kafka topics automatically
  
  How it works:
    PostgreSQL WAL → Debezium (logical replication slot) → Kafka Connect → Kafka
    MySQL binlog   → Debezium (binlog reader)            → Kafka Connect → Kafka
  
  Debezium Outbox Router:
    Debezium has built-in Outbox Router extension.
    Reads outbox table inserts from WAL.
    Routes to Kafka topic based on outbox.topic column.
    Transforms payload as specified.
    Marks as published (or you can use a separate cleanup job).

APPROACH 3: TRANSACTION LOG TAILING
  Similar to CDC but using native DB features.
  PostgreSQL: Logical Replication Slots, pgoutput plugin.
  MySQL: Binlog reading via Maxwell or Debezium.

OUTBOX CLEANUP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Outbox rows accumulate. Need regular cleanup.

Options:
  1. DELETE WHERE published = TRUE AND published_at < NOW() - INTERVAL '7 days'
     Run as scheduled job (cron or database scheduler).
  
  2. If using CDC: delete immediately after publishing.
     Debezium still processes the WAL entry before deletion.
  
  3. Partition outbox table by date; drop old partitions.
     Best for high-volume systems.

VARIATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

INBOX PATTERN (for idempotent consumers):
  Mirror of outbox, on the consumer side.
  When consumer receives event: write to inbox table first.
  Process inbox rows in a separate step.
  If event already in inbox: skip (deduplication).

TRANSACTIONAL INBOX:
  Consumer writes to inbox + updates state in SAME DB transaction.
  Guarantees exactly-once processing even if consumer crashes.

WHEN TO USE OUTBOX PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✓ Service writes to its own database AND needs to publish events
✓ Events must be reliably published (no lost events on crash)
✓ Can't afford distributed transactions (2PC) for performance/complexity
✓ Using Saga pattern (each saga step must reliably publish its event)
✓ CDC with Debezium already in your stack

Skip if:
✗ Events can be lost occasionally (analytics, logging)
✗ Using a transactional messaging system that already supports atomic
  DB+message operations (very rare; XA transactions)

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"The Outbox Pattern solves the dual-write problem: ensuring a DB write
 and an event publication happen atomically without a distributed transaction.
 
 Instead of writing to DB and publishing to Kafka separately (which can
 go out of sync on failures), I write the business data and the event to
 an outbox table in the same DB transaction. A separate process reads
 the outbox and publishes to Kafka.
 
 In production, I'd use Debezium CDC to tail the DB WAL instead of polling,
 for sub-second latency and no additional DB load. Consumers must be
 idempotent since the pattern guarantees at-least-once delivery.
 
 This is fundamental to reliable Saga pattern implementations — every
 saga step writes to outbox atomically with its local DB change."
