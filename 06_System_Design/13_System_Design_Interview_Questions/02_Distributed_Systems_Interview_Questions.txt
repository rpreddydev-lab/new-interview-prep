DISTRIBUTED SYSTEMS INTERVIEW QUESTIONS — MODEL ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: Explain the CAP theorem and its practical implications.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  CAP: A distributed system can guarantee at most 2 of 3:
    C — Consistency: every read gets the most recent write
    A — Availability: every request gets a (non-error) response
    P — Partition Tolerance: system continues despite network partition

  Why P is non-negotiable:
    Network partitions happen in real production (switch failure, cable cut)
    If you drop P, nodes must share memory → can't be distributed
    Therefore: real choice is CP or AP

  CP (Choose Consistency):
    During partition: refuse requests rather than return stale data
    Examples: HBase, Zookeeper, etcd, MongoDB (default)
    Use when: banking, inventory (stale data causes problems)

  AP (Choose Availability):
    During partition: return potentially stale data, accept writes
    Converge later (eventual consistency)
    Examples: Cassandra, DynamoDB, CouchDB
    Use when: shopping carts, social feeds, DNS (staleness is fine)

  The nuance: CAP is about partition time only
    PACELC captures the full tradeoff:
    "If Partitioned → C or A; Else → L (latency) or C (consistency)"
    Even without partition: strong consistency requires coordinator round-trips = higher latency


Q2: What is eventual consistency? How do you reason about it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Eventual consistency: if no new updates are made, all replicas will
  eventually converge to the same value.

  Convergence window: typically milliseconds to seconds in practice
  (cross-datacenter replication can be 50-200ms)

  Good enough for:
    Social feeds: stale feed for 200ms is fine
    Shopping cart: seeing an item not added yet (user refreshes)
    DNS: TTL-based propagation, not instant

  NOT good enough for:
    Bank transfers: debit and credit must be atomic, consistent
    Seat reservations: two people booking last seat simultaneously
    Inventory: 1 item sold to 2 people

  Techniques to reason about it:
    Use monotonic reads: user always reads own writes (read-your-writes)
    Idempotent operations: retrying won't cause double effects
    CRDTs (Conflict-free Replicated Data Types): counters, sets that
      automatically converge without coordination (Riak, Redis)


Q3: Explain the Raft consensus algorithm.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Raft solves: how do distributed nodes agree on a sequence of values?

  Three roles: Leader, Follower, Candidate

  Leader Election:
    Followers time out if no heartbeat from leader → become Candidate
    Candidate broadcasts RequestVote RPC with its term number
    Node votes for first candidate it hears from (with up-to-date log)
    Candidate wins majority (N/2+1) → becomes Leader
    Split vote → timeout → retry with new term number

  Log Replication:
    All writes go to Leader
    Leader appends to own log, sends AppendEntries RPC to all Followers
    Follower appends to log, replies success
    Once majority acknowledges → entry is "committed"
    Leader notifies followers → followers apply to state machine

  Safety guarantees:
    At most one leader per term (election majority)
    Committed entries never lost (log completeness property)
    All servers apply same commands in same order

  Used by: etcd (Kubernetes), CockroachDB, TiKV, Consul


Q4: How does consistent hashing work and why does it matter?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Problem with naive sharding: shard = hash(key) % N
    Adding/removing 1 server → N changes → remaps ~(N-1)/N = ~67% of keys
    Cache becomes worthless (mass cache miss storm)

  Consistent hashing:
    Hash space: 0 to 2^32-1, arranged in a ring
    Nodes placed on ring: hash(nodeId) → position
    Keys placed on ring: hash(key) → position
    Rule: key served by first node clockwise from key's position

  Adding a node: only keys between new node and its predecessor move
    ~1/N fraction of keys remapped → most caches still valid

  Removing a node: its keys move to successor node
    ~1/N fraction remapped

  Virtual nodes (vnodes):
    Problem: few physical nodes → uneven distribution
    Solution: each physical node has 150 virtual positions on ring
    Result: even load distribution, graceful node addition

  Used by: Amazon DynamoDB, Cassandra, Memcached (ketama), Redis Cluster
  Redis Cluster uses 16384 fixed hash slots, not pure consistent hashing


Q5: What is the difference between leader-follower and leaderless replication?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Leader-Follower (Single-Leader):
    All writes go to Leader → replicated to Followers
    Reads can go to Followers (potentially stale) or Leader (always fresh)
    Leader election (Raft/Paxos) on failure
    Examples: PostgreSQL, MySQL, MongoDB
    Pros: simple consistency, read scaling via followers
    Cons: write bottleneck at leader, leader failover complexity

  Multi-Leader:
    Multiple nodes accept writes (e.g., each data center has own leader)
    Leaders sync changes asynchronously across DCs
    Conflict: same record written on two leaders simultaneously
    Conflict resolution: last-write-wins, custom merge, CRDTs
    Examples: CouchDB, Cassandra multi-DC with LOCAL_QUORUM
    Pros: lower write latency (local DC write), offline clients
    Cons: conflict resolution complexity

  Leaderless (Dynamo-style):
    Any node accepts any write/read
    W=2, R=2, N=3 quorums for consistency
    Version vectors detect conflicts, application resolves
    Examples: DynamoDB, Cassandra, Riak
    Pros: no single point of failure, write to nearest node
    Cons: tunable consistency can be misconfigured, conflict complexity


Q6: Explain two-phase commit (2PC) and its limitations.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  2PC: atomic commit protocol across multiple distributed nodes

  Phase 1 — Prepare:
    Coordinator asks all participants: "Can you commit?"
    Each participant: writes to log, acquires locks, votes YES/NO
    If all vote YES → proceed to Phase 2

  Phase 2 — Commit:
    Coordinator sends COMMIT (or ROLLBACK if any voted NO)
    Each participant commits and releases locks

  Limitations:
    Blocking: if Coordinator crashes after Prepare but before Commit,
      all participants are stuck holding locks indefinitely (blocked state)
    Not partition-tolerant: if network partitions during Phase 2,
      some nodes commit, others don't → inconsistent state
    Performance: 2 round trips = high latency; all nodes must respond

  Alternatives:
    Saga Pattern: sequence of local transactions with compensating actions
      Each step publishes event; failure triggers reverse steps
      No distributed lock; better availability
    3PC: adds "pre-commit" phase to avoid blocking; still not partition-safe
    Paxos/Raft: consensus algorithms designed for partition tolerance


Q7: What is a bloom filter and where would you use it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Bloom filter: probabilistic data structure for set membership
    "Is item X in the set?"
    No false negatives (if says NOT in set, definitely not)
    Possible false positives (if says IN set, might not be)

  How it works:
    Bit array of M bits (all zeros initially)
    K hash functions, each maps item to 1..M
    Insert: set bits at K positions
    Query: check if ALL K bits are set → probably present; any 0 → definitely absent

  False positive rate:
    f ≈ (1 - e^(-kn/m))^k
    Tune: m=10×n gives ~1% false positive rate with k=7

  Use cases:
    Database: check bloom filter before disk read → avoid IO for missing keys
      Cassandra, HBase, LevelDB all use bloom filters per SSTable
    
    Distributed cache: before DB query, check bloom filter
      User account doesn't exist? → bloom filter → skip DB → avoid cache stampede
    
    Web crawlers: "Have we crawled this URL already?"
      Billions of URLs, bloom filter uses MB instead of GB
    
    Network: ISP blocks malicious IPs → billions of IPs in bloom filter

  Limitations:
    Cannot delete elements (use Counting Bloom Filter for deletion)
    False positives grow as filter fills up
    Fixed size — need to estimate N upfront


Q8: How do you design a distributed rate limiter?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Challenge: multiple API gateway instances must share the same counter

  Centralized counter in Redis:
    All gateway nodes atomically increment shared counter
    Lua script (atomic INCR + EXPIRE):
      local count = redis.call('INCR', key)
      if count == 1 then redis.call('EXPIRE', key, windowSeconds) end
      return count

  Algorithm choice:
    Sliding Window Counter (recommended):
      current = prev_count × (1 - elapsed/window) + curr_count
      Smooth, ~99.997% accurate, O(1) storage
    
    Token Bucket:
      tokens refilled at constant rate; bucket has max capacity
      Handles burst gracefully (allows short bursts up to max)

  Redis Cluster:
    Hash tag: key = "{user_id}:window:1706400000"
    Braces {user_id} force same shard → atomic operations safe

  Failure mode:
    Redis down → fail-open (allow all traffic) to prevent legitimate traffic blockage
    Or: local in-memory fallback counter (less accurate, avoids hard failure)

  Response: HTTP 429 Too Many Requests
    X-RateLimit-Limit: 100
    X-RateLimit-Remaining: 0
    X-RateLimit-Reset: 1706400060
    Retry-After: 30


Q9: What is a vector clock and why is it used?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Problem: in distributed systems, wall clocks can't be trusted
    (NTP sync ±100ms; clocks drift; clock can go backward)
    Can't use timestamps to determine event ordering

  Lamport Clock:
    Single counter per node; increment on each event
    Send timestamp with messages; receiver: clock = max(local, received) + 1
    Limitation: can determine A happened before B, but not concurrent events

  Vector Clock:
    Array of counters, one per node: [N1:3, N2:1, N3:5]
    Each node increments own counter
    On send: include own vector clock
    On receive: element-wise max + increment own
    
    Compare: A < B if every counter in A ≤ corresponding counter in B
    Concurrent: neither A≤B nor B≤A → conflict detected!

  Use in DynamoDB:
    Each object carries vector clock
    Concurrent writes detected → both versions kept
    Client resolves conflict on next read ("add to cart" merge)
    
  Limitations:
    Size grows with number of nodes (prune stale entries)
    Amazon DynamoDB moved to simpler "last-writer-wins" for simplicity

  Real-world insight: vector clocks detect concurrency; they don't resolve it.
  Application-level semantics decide how to merge (CRDTs automate this).


Q10: Explain the Saga pattern for distributed transactions.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Problem: microservices need atomicity across multiple services
    Can't use 2PC (blocking, not partition-tolerant)

  Saga: sequence of local transactions, each publishing events
    On failure: execute compensating transactions (undo what was done)

  Choreography:
    Services react to events from each other (no central coordinator)
    OrderService → OrderCreated → InventoryService → InventoryReserved
    → PaymentService → PaymentCompleted → ShippingService → ...
    Failure: PaymentFailed → InventoryService releases reservation → Order cancelled
    Pros: simple, decentralized; Cons: hard to track, cyclic dependencies risk

  Orchestration:
    Central Saga Orchestrator issues commands to services, waits for events
    Orchestrator: "Reserve inventory" → success → "Charge payment" → success → "Create shipment"
    On failure: Orchestrator explicitly issues compensating commands
    Pros: clear flow, easy to debug; Cons: central coordinator can be bottleneck

  Compensating transactions (idempotent!):
    Reserve inventory → compensate: release inventory
    Charge payment → compensate: issue refund
    Send notification → compensate: send cancellation email

  Key requirement: every step must be idempotent
    If Saga retries a step, executing twice should be safe
