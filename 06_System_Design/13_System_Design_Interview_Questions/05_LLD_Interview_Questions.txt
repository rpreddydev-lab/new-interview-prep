LLD INTERVIEW QUESTIONS — MODEL ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the difference between HLD and LLD?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  HLD (High-Level Design):
    System architecture: components, services, databases, data flow
    Boxes and arrows: "the user hits the API Gateway → goes to Auth Service → ..."
    Scale decisions: how many servers, which DB, caching strategy
    Focus on: non-functional requirements (latency, throughput, availability)
    Audience: architects, senior engineers, stakeholders

  LLD (Low-Level Design):
    Class design: classes, interfaces, methods, attributes
    Design patterns: which pattern solves which problem
    Code structure: how data flows within a single component
    Focus on: SOLID principles, extensibility, testability
    Audience: developers who will implement

  Example: "Design a parking lot"
    HLD: App server → ParkingService → MySQL; CDN for static
    LLD: ParkingLot (Singleton), ParkingSpot (status enum),
         PricingStrategy (interface), Vehicle hierarchy


Q2: Explain SOLID principles with concrete examples.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  S — Single Responsibility Principle:
    Class has one reason to change
    BAD: UserService.createUser() AND sendWelcomeEmail() AND generateReport()
    GOOD: UserService.createUser(), EmailService.sendWelcomeEmail(), ReportService.generate()

  O — Open/Closed Principle:
    Open for extension, closed for modification
    BAD: if (shape == "circle") area = PI*r*r; else if (shape == "rect") area = w*h;
    GOOD: Shape interface with getArea(); Circle/Rectangle implement it
    Adding a Triangle doesn't require touching existing code

  L — Liskov Substitution Principle:
    Subclass must be substitutable for parent class
    BAD: class Ostrich extends Bird { fly() { throw exception; } }
          → breaks code that calls bird.fly() expecting it to work
    GOOD: FlyingBird extends Bird; Ostrich extends Bird (without fly())

  I — Interface Segregation Principle:
    Don't force clients to implement methods they don't need
    BAD: interface Worker { work(); eat(); sleep(); }  — Robot.eat() makes no sense
    GOOD: interface Workable { work(); } interface Eatable { eat(); }
          Human implements both; Robot implements only Workable

  D — Dependency Inversion Principle:
    Depend on abstractions, not concretions
    BAD: OrderService directly instantiates MySQLOrderRepository
    GOOD: OrderService depends on OrderRepository (interface)
          MySQLOrderRepository implements OrderRepository
          Swap to MongoOrderRepository without changing OrderService


Q3: What design patterns have you used? Give a real example.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  SINGLETON: Ensures only one instance of a class
    Use: ParkingLot instance, database connection pool, logger
    Double-checked locking:
      if (instance == null) {
          synchronized(ParkingLot.class) {
              if (instance == null) instance = new ParkingLot();
          }
      }
    Better: enum Singleton (thread-safe, handles serialization)

  STRATEGY: Defines family of algorithms, makes them interchangeable
    Use: PricingStrategy (hourly/daily/monthly), SortingStrategy, PaymentStrategy
    Behavior changes at runtime without changing the class that uses it

  OBSERVER: One-to-many dependency; subject notifies observers on change
    Use: OrderService publishes OrderStatusChanged → email/SMS/warehouse listens
    Java: EventListener, PropertyChangeListener
    Prevents tight coupling between event producer and consumers

  FACTORY METHOD / ABSTRACT FACTORY:
    Factory Method: subclass decides which object to create
    Use: NotificationFactory.create(type) → EmailNotification / PushNotification / SMSNotification
    Hides instantiation logic; easy to add new types

  BUILDER: Construct complex objects step by step
    Use: QueryBuilder, HTTP request builder, complex config objects
    Pizza.builder().size(LARGE).crust(THIN).topping(PEPPERONI).build()
    Avoids telescoping constructor problem

  DECORATOR: Add behavior to objects without inheritance
    Use: Java I/O (BufferedReader wraps FileReader), logging wrapper
    Stacks behaviors: CachingRepository wraps LoggingRepository wraps DBRepository

  COMMAND: Encapsulates request as object (supports undo/redo/queue)
    Use: Chess Move class (store from/to + captured piece → undo move)
    Transaction commands, macro recording

  TEMPLATE METHOD: Define algorithm skeleton; subclasses fill in steps
    Use: Report generation: fetchData() + processData() + format() + export()
    Abstract class defines the steps; subclass provides specific implementation


Q4: How do you handle concurrency in LLD?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  Identify critical sections: where multiple threads access shared mutable state

  SYNCHRONIZED METHOD:
    synchronized void parkVehicle() → only one thread at a time
    Pros: simple; Cons: coarse-grained, performance bottleneck
    Use for: infrequent, short critical sections

  REENTRANTLOCK WITH TRYLOCK:
    ReentrantLock lock = new ReentrantLock();
    if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
        try { ... } finally { lock.unlock(); }
    } else { // timeout: handle failure case }
    Pros: timeout (avoid deadlock), tryLock (avoid blocking), fair mode
    Use for: when you need more control than synchronized

  CONCURRENTHASHMAP + ATOMICINTEGER:
    ConcurrentHashMap → segment-level locking, much faster than synchronized HashMap
    AtomicInteger/AtomicLong → lock-free increment (compare-and-swap hardware instruction)
    Use for: counters, caches, high-concurrency reads

  OPTIMISTIC LOCKING (version field):
    int version; // each update increments version
    UPDATE WHERE id=? AND version=oldVersion → check rows updated > 0
    Retry if 0 (someone else modified it)
    Use for: DB updates with low contention

  IMMUTABLE OBJECTS:
    Objects that cannot change after construction are thread-safe by definition
    Use final fields, no setters
    String, LocalDate, LocalDateTime are all immutable

  COMMON PITFALL: double-check locking without volatile
    volatile ensures visibility of changes across threads
    private volatile static Singleton instance; // required for DCL pattern


Q5: What is the difference between composition and inheritance?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Inheritance (IS-A): Dog extends Animal
    Dog IS AN Animal → can use Dog wherever Animal is expected
    Pros: code reuse, polymorphism
    Cons: tight coupling, fragile base class problem, deep hierarchies become unmaintainable

  Composition (HAS-A): Car has an Engine
    Car HAS AN Engine → delegate to engine for locomotion behavior
    Pros: loose coupling, flexible (swap Engine at runtime), testable
    Cons: more boilerplate

  Prefer Composition over Inheritance (GoF principle):
    BAD: class LoggingList extends ArrayList { ... }
      Breaking if ArrayList changes; can't swap list implementation
    
    GOOD: class LoggingList implements List {
              private final List<T> delegate;
              add(T item) { log("Adding " + item); delegate.add(item); }
          }

  When inheritance IS appropriate:
    True IS-A relationship that won't change
    Polymorphism needed (Shape → Circle, Rectangle)
    Limit to 1-2 levels deep max

  Rule of thumb: if you're inheriting to reuse code → use composition instead
                 if you need polymorphism → use inheritance (or interface)


Q6: How would you design a thread-safe LRU cache?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  LRU = Least Recently Used: evict the item not used for the longest time

  Data structure: HashMap + DoublyLinkedList
    HashMap: O(1) key → node lookup
    DoublyLinkedList: O(1) move node to front (most recently used)
    Evict: remove tail (least recently used)

  class LRUCache<K, V> {
      private final int capacity;
      private final Map<K, Node<K,V>> map;
      private final Node<K,V> head, tail;    // dummy head and tail
      private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
      
      V get(K key) {
          rwLock.writeLock().lock();  // write lock because we modify list on access
          try {
              if (!map.containsKey(key)) return null;
              Node<K,V> node = map.get(key);
              moveToFront(node);    // mark as recently used
              return node.value;
          } finally { rwLock.writeLock().unlock(); }
      }
      
      void put(K key, V value) {
          rwLock.writeLock().lock();
          try {
              if (map.containsKey(key)) {
                  map.get(key).value = value;
                  moveToFront(map.get(key));
              } else {
                  if (map.size() == capacity) evict();   // remove LRU
                  Node<K,V> node = new Node<>(key, value);
                  map.put(key, node);
                  addToFront(node);
              }
          } finally { rwLock.writeLock().unlock(); }
      }
      
      private void evict() { Node<K,V> lru = removeTail(); map.remove(lru.key); }
  }

  Thread safety options:
    synchronized on all methods (simple but coarse)
    ReentrantReadWriteLock (readers don't block each other)
    ConcurrentLinkedHashMap (Guava Cache or Caffeine — production-grade)

  Java built-in: LinkedHashMap with accessOrder=true + removeEldestEntry()
    Override: protected boolean removeEldestEntry(Map.Entry e) { return size() > capacity; }
    Wrap in Collections.synchronizedMap() for thread safety


Q7: What are common mistakes in LLD interviews?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  1. No interfaces:
     Hardcoding implementations; can't swap payment processor without rewrite
     Fix: always program to interface (PricingStrategy, not HourlyPricingStrategy)

  2. Giant God class:
     LibrarySystem.doEverything() — 2000 lines, handles booking/catalog/fines/reports
     Fix: single responsibility; separate classes per concern

  3. Missing enums:
     Using String "AVAILABLE" instead of enum BookStatus.AVAILABLE
     Fix: enums for fixed sets of values; type-safe, auto-complete

  4. Not mentioning concurrency:
     Parking lot: two cars claim last spot simultaneously
     Fix: always ask "what happens when multiple threads call this?"
          synchronized, ConcurrentHashMap, optimistic locking

  5. Deep inheritance (>2 levels):
     Animal → Mammal → DomesticAnimal → Pet → Dog → Labrador
     Fix: flatten to 1-2 levels; use composition + interfaces

  6. No design pattern justification:
     "I used Singleton" without explaining why
     Fix: state the problem the pattern solves, then show the solution

  7. No error handling:
     What if book not found? Member over limit? Card expired?
     Fix: custom exceptions, validation at entry points

  8. Skipping the "why" of tradeoffs:
     Interviewer wants to hear reasoning, not just code
     Fix: narrate your thinking; "I chose Strategy here because..."


Q8: Walk through designing a Vending Machine.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Core pattern: STATE MACHINE

  States: IDLE → HAS_MONEY → DISPENSING → CHANGE_RETURN → IDLE

  Classes:
    VendingMachine: holds state, inventory, money inserted
    State interface: insertMoney(amount), selectProduct(code), cancel()
    IdleState, HasMoneyState, DispensingState (implement State)
    
    Product: code, name, price, quantity
    Inventory: Map<String, Product>
    Coin/Bill enum

  Key behaviors:
    insertMoney(50¢): idle → hasMoney; hasMoney → add to inserted amount
    selectProduct("A1"): check inventory, check money >= price → dispense
    dispense: decrement quantity, transition to CHANGE_RETURN
    returnChange: inserted - price → return coins, back to IDLE
    cancel: return all inserted money, back to IDLE

  State pattern benefit:
    addingMoney() in IdleState just updates balance
    addingMoney() in DispensingState: "please wait, dispensing..."
    Each state handles each event differently
    No giant if-else chain on state variable

  Follow-up: "What if we run out of a product?"
    Check inventory before transitioning; show "OUT OF STOCK"
    Inventory threshold: alert maintenance at 20% remaining
