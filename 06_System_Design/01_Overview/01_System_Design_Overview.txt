================================================================
SYSTEM DESIGN OVERVIEW
================================================================

WHAT IS SYSTEM DESIGN?
-----------------------
System design is the process of defining the architecture, components,
modules, interfaces, and data flow of a system to satisfy specified
requirements. In software engineering, it covers:

  - High-Level Design (HLD): Architecture diagrams, component selection,
    data flow, API contracts.
  - Low-Level Design (LLD): Class diagrams, DB schemas, algorithm choices,
    detailed data structures.

WHY SYSTEM DESIGN MATTERS IN INTERVIEWS
-----------------------------------------
Companies like Google, Meta, Amazon, Netflix, and Microsoft use system
design interviews to evaluate a candidate's ability to:

  1. Think at scale — handle millions of users, petabytes of data.
  2. Make trade-offs — consistency vs availability, latency vs throughput.
  3. Communicate clearly — explain complex designs to stakeholders.
  4. Identify failure modes — single points of failure, bottlenecks.
  5. Iteratively refine a design — start simple, scale as needed.

CORE PILLARS OF SYSTEM DESIGN
-------------------------------
1. SCALABILITY
   - Ability to handle growing load (horizontal vs vertical scaling).
   - Stateless services, sharding, load balancing.

2. RELIABILITY
   - System works correctly even when components fail.
   - Redundancy, replication, failover mechanisms.

3. AVAILABILITY
   - System remains operational over time.
   - Measured as uptime % (e.g., 99.99% = "four nines").
   - HA designs: active-active, active-passive clusters.

4. MAINTAINABILITY
   - Easy to change, update, and debug.
   - Modular design, good observability (logs, metrics, traces).

5. PERFORMANCE
   - Low latency (response time per request).
   - High throughput (requests handled per second).

6. CONSISTENCY
   - All nodes see the same data at the same time (strong consistency)
     OR eventual consistency (replicas converge over time).

7. FAULT TOLERANCE
   - System continues to function when parts fail.
   - Circuit breakers, retries with exponential backoff, bulkheads.

8. SECURITY
   - Authentication, Authorization, Encryption at rest and in transit.
   - Defense in depth, Zero Trust principles.

NUMBERS EVERY ENGINEER SHOULD KNOW
------------------------------------

  L1 cache reference:           0.5 ns
  L2 cache reference:           7   ns
  RAM access:                 100   ns
  SSD read:                   150   μs
  HDD seek:                    10   ms
  RTT within same datacenter:   0.5 ms
  RTT cross-continent:        150   ms

Throughput:
  Single server (HTTP):  ~10,000 req/s
  Kafka (1 broker):      ~1 million msg/s
  Redis (single):        ~100,000 ops/s

Storage:
  1 Byte    = 8 bits

  1 PB      = 1,024 TB

INTERVIEW FRAMEWORK (DETAILED IN 02_How_to_Approach.txt)
---------------------------------------------------------
  Step 1: Clarify requirements (5 min)
  Step 2: Estimate scale — DAU, QPS, storage (5 min)
  Step 3: Define API contracts (3 min)
  Step 4: High-level architecture diagram (10 min)
  Step 5: Deep dive on critical components (15 min)
  Step 6: Identify bottlenecks and resolve (5 min)
  Step 7: Wrap-up: operational concerns (2 min)

TYPES OF SYSTEM DESIGN QUESTIONS
----------------------------------
1. Design a product/service:
   - URL Shortener, Twitter Feed, YouTube, Uber, WhatsApp

2. Design a system component:
   - Rate Limiter, Distributed Cache, Notification System

3. Design for scale:
   - "How would you handle 10x traffic?" — sharding, caching, CDN

4. Failure and recovery:
   - "What happens if the primary DB goes down?" — failover, replication

5. LLD questions:
   - Design a parking lot, chess game, elevator system

TRADE-OFF CHEAT SHEET
----------------------
Consistency vs Availability   → CAP theorem (pick 2 of 3: C, A, P)
Latency vs Throughput         → Batch writes improve throughput at cost of latency
Normalization vs Denormalization → Normalize for write-heavy; denormalize for reads
SQL vs NoSQL                  → SQL for ACID, NoSQL for scale/flexibility
Sync vs Async communication   → Sync for real-time; async for decoupling/resilience
Push vs Pull (feed)           → Push for low-follower (Twitter); Pull for celebrities
Strong vs Eventual Consistency→ Strong for payments; eventual for social feeds

WHAT INTERVIEWERS LOOK FOR
---------------------------
✓ Asking clarifying questions before jumping to design
✓ Thinking out loud and explaining reasoning
✓ Starting simple and evolving the design
✓ Knowing when to use which technology and WHY
✓ Acknowledging trade-offs explicitly
✓ Discussing failure modes and mitigations
✓ Estimating capacity (back of envelope)
✓ Clean, organized diagrams

RED FLAGS IN INTERVIEWS
------------------------
✗ Jumping to a specific technology without justification
✗ Ignoring non-functional requirements (latency, scale, security)
✗ Not asking about read/write ratio, user scale, consistency needs
✗ Over-engineering a simple system (premature optimization)
✗ Under-engineering a complex system (ignoring scale)
✗ Saying "just use a database" without specifying type or schema
✗ Not considering failure scenarios
