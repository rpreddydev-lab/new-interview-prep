================================================================
HOW TO APPROACH SYSTEM DESIGN INTERVIEWS
================================================================

THE INTERVIEW FORMAT
---------------------
System design interviews typically run 45–60 minutes.
You will be asked to design a system (e.g., "Design Twitter" or
"Design a distributed cache"). The interviewer expects you to:
  - Drive the conversation
  - Think out loud
  - Make and justify decisions
  - Evolve the design iteratively

There is no single correct answer — it's about the process, not the
perfect solution.

STEP-BY-STEP FRAMEWORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1: CLARIFY REQUIREMENTS (5 minutes)
-----------------------------------------
Never start designing without asking clarifying questions.
This shows maturity and prevents wasted effort.

Functional Requirements Questions:
  - "What are the core features we need to support?"
  - "Should I focus on [feature X] or all features?"
  - "Do users need real-time updates or is eventual consistency OK?"
  - "Is this read-heavy or write-heavy?"
  - "Do we need search functionality?"
  - "Is there a mobile client? Web? Both?"

Non-Functional Requirements Questions:
  - "How many daily active users do we expect?"
  - "What is the expected QPS (reads vs writes)?"
  - "What latency is acceptable? (<100ms, <500ms, <1s?)"
  - "What availability do we need? (99.9%, 99.99%?)"
  - "Are there any specific compliance/data residency requirements?"
  - "What is the expected data growth per year?"
  - "Is consistency more important than availability? (for payments: yes)"

Example for "Design Twitter":
  Clarifications to make:
  → We will support: posting tweets, following users, viewing home feed
  → We will NOT implement: DMs, ads, trending, media uploads (for now)
  → 100M DAU, 10:1 read-to-write ratio
  → Eventually consistent feed is acceptable
  → 99.99% uptime for tweet delivery

STEP 2: CAPACITY ESTIMATION (5 minutes)
-----------------------------------------
"Back of the envelope" calculations to understand the scale.

FORMULA PATTERN:
  QPS (read)  = DAU × avg_reads_per_day / 86,400
  QPS (write) = DAU × avg_writes_per_day / 86,400
  Storage/day = writes/day × avg_payload_size
  Storage/yr  = Storage/day × 365

Example for Twitter:
  - 100M DAU
  - Avg reads: 20 tweets/day → Read QPS = 100M × 20 / 86,400 ≈ 23,000 QPS
  - Avg writes: 1 tweet/week → Write QPS = 100M × (1/7) / 86,400 ≈ 165 QPS
  - Avg tweet size: 300 bytes (text + metadata)
  - Write storage: 165 writes/s × 300B = ~50 KB/s → ~1.5 GB/day → ~550 GB/yr
  - Media (10% of tweets have images, avg 300KB): 0.1 × 165 × 300KB/s ≈ 5MB/s → 430 GB/day
  - Total storage (5 years): ~800 TB

Mention bandwidth:
  - Read bandwidth: 23,000 QPS × 300B = ~7 MB/s → negligible, but with images: much larger

STEP 3: DEFINE API CONTRACTS (3 minutes)
------------------------------------------
Sketch the core APIs — this forces you to think about what the
system needs to do and what data flows in/out.

REST API Example (Twitter):
  POST   /v1/tweets
    Body: { user_id, text, media_url? }
    Returns: { tweet_id, created_at }

  GET    /v1/feed?user_id={id}&page_token={token}&limit=20
    Returns: { tweets: [...], next_page_token }

  POST   /v1/follow
    Body: { follower_id, followee_id }

  DELETE /v1/follow
    Body: { follower_id, followee_id }

Mention:
  - Authentication: JWT / OAuth 2.0 Bearer token in header
  - Rate limiting: 1000 requests/hour per user
  - Pagination: cursor-based (not offset) for feed

STEP 4: HIGH-LEVEL ARCHITECTURE (10 minutes)
----------------------------------------------
Draw the block diagram. Talk through it as you draw.

Typical components to include:
  ┌──────────────────────────────────────────────────────┐
  │  Clients (mobile, web)                               │
  │      ↓                                               │
  │  CDN (static assets)                                 │
  │      ↓                                               │
  │  Load Balancer (L7)                                  │
  │      ↓                                               │
  │  API Gateway (auth, rate limiting, routing)          │
  │      ↓                                               │
  │  [Service A] [Service B] [Service C]                 │
  │      ↓             ↓          ↓                      │
  │  Cache (Redis)  Message Queue (Kafka)                │
  │      ↓             ↓                                 │
  │  Database (Primary + Replicas)  Worker Services      │
  │      ↓                                               │
  │  Object Storage (S3 for media)                       │
  └──────────────────────────────────────────────────────┘

For Twitter specifically:
  - Tweet Service: handles creation and storage
  - Feed Service: builds home timeline
  - Fan-out Service: pushes tweets to followers' feeds
  - User Service: manages profiles and follow graph
  - Notification Service: sends push/email notifications
  - Media Service: handles image/video uploads (via S3)

Discuss:
  - Synchronous vs Asynchronous for each connection
  - Where you'd use caching and why
  - How data flows for both read and write paths
  - Where sharding/partitioning might be needed

STEP 5: DEEP DIVE ON CRITICAL COMPONENTS (15 minutes)
-------------------------------------------------------
Pick the most interesting/complex part and go deep. Usually the
interviewer will direct you, but if not, pick based on what's novel
about this system.

Questions to answer in deep dive:
  - "How does the feed generation work? (fan-out on write vs read)"
  - "How do you handle celebrity users (millions of followers)?"
  - "How does the distributed cache work?"
  - "How do you handle DB scaling?"
  - "How do you ensure exactly-once delivery of notifications?"

Depth shows: DB schema, cache eviction policy, sharding strategy,
consistency guarantees, failure handling.

Example Deep Dive: Feed Generation
  Option A — Fan-out on Write (Push Model):
    When user posts, immediately write to all followers' feed caches.
    Pro: Very fast reads (O(1) — just read from cache)
    Con: Write amplification — celebrity with 10M followers needs 10M writes
    When: Best for users with few followers

  Option B — Fan-out on Read (Pull Model):
    When user requests feed, aggregate tweets from all followed users.
    Pro: No write amplification, simple writes
    Con: Slow reads for users following many accounts
    When: Best for celebrity users

  Hybrid Model (Twitter's approach):
    - Regular users: fan-out on write → cache their feed
    - Celebrity users (>X followers): fan-out on read
    - At read time: merge precomputed feed + real-time celebrity tweets

STEP 6: IDENTIFY AND RESOLVE BOTTLENECKS (5 minutes)
------------------------------------------------------
Proactively identify single points of failure and bottlenecks.

Common bottlenecks:
  1. Database — too many writes → add replicas, shard
  2. Single service instance → add horizontal scaling, stateless design
  3. Cache miss storms (thundering herd) → cache warming, jitter
  4. Network bottleneck between DCs → async replication, CDN
  5. Message queue backlog → add consumer partitions
  6. Hot shards — one shard gets all traffic → virtual nodes

For each bottleneck, propose mitigation:
  "If the DB becomes a bottleneck, we can:
   1. Add read replicas for read traffic
   2. Use Redis to cache hot data (top 20% of tweets get 80% of reads)
   3. Shard tweets by user_id using consistent hashing"

STEP 7: OPERATIONAL CONCERNS (2 minutes)
------------------------------------------
Briefly mention how the system will be operated in production.

  - Monitoring: Metrics (QPS, error rate, latency), dashboards (Grafana)
  - Logging: Structured JSON logs, centralized in ELK stack
  - Tracing: Distributed tracing (Jaeger/Zipkin) for cross-service calls
  - Alerting: PagerDuty for P1/P2 alerts (error rate > 1%, latency > 500ms)
  - Deployments: Rolling deploys, feature flags, canary releases
  - Disaster Recovery: Multi-AZ primary DB, cross-region backups
  - Runbooks: Documented procedures for common failure scenarios

TIME MANAGEMENT GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For a 45-minute interview:
  0–5   min: Clarify requirements
  5–10  min: Capacity estimation
  10–13 min: API design
  13–25 min: High-level architecture
  25–40 min: Deep dive on 1-2 components
  40–43 min: Bottlenecks and scaling
  43–45 min: Operational concerns / wrap-up

For a 60-minute interview:
  0–7   min: Clarify requirements
  7–12  min: Capacity estimation
  12–17 min: API design
  17–33 min: High-level architecture
  33–52 min: Deep dive on 2-3 components
  52–57 min: Bottlenecks and scaling
  57–60 min: Operational concerns

COMMUNICATION TIPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE THESE PHRASES:
  "Let me start by clarifying requirements..."
  "Given that this is read-heavy, I'd prioritize caching..."
  "There's a trade-off here between X and Y. I'll go with X because..."
  "This is a bottleneck — let me think about how to address it..."
  "I've seen two approaches to this: [A] and [B]. I'll choose [A] because..."
  "What would you like me to go deeper on?"
  "Let me pause and make sure I'm on the right track — does this make sense?"

SIGNAL CONFIDENCE BY:
  - Justifying every technology choice
  - Proactively raising and resolving issues
  - Being comfortable saying "I'm not sure, but I think..." and reasoning through it
  - Drawing clean, labeled diagrams
  - Estimating when exact numbers aren't known

WHAT SIGNALS SENIORITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Junior/Mid:
  - Can describe basic components
  - Follows a structure when prompted
  - Knows popular technologies

Senior:
  - Drives the conversation
  - Identifies non-obvious failure modes
  - Makes explicit trade-offs
  - Knows internals of components (how Kafka achieves ordering)
  - Can do capacity math in their head
  - Cites real-world examples ("Instagram did X because...")

Staff/Principal:
  - Zooms out to organizational concerns (team ownership, Conway's Law)
  - Discusses versioning and migration strategies
  - Addresses data lineage, compliance, cost optimization
  - Considers evolutionary architecture

CHECKLIST (Use Before/During Interview)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Requirements:
□ Functional requirements clarified
□ Non-functional requirements noted (scale, latency, availability)
□ Scope explicitly limited (what NOT to build)

Estimation:
□ DAU/MAU established
□ Read QPS and Write QPS calculated
□ Storage per day/year estimated
□ Bandwidth estimated

Design:
□ Core APIs defined
□ High-level block diagram drawn
□ Read path explained
□ Write path explained
□ Database choice justified (SQL vs NoSQL, which one)
□ Cache strategy explained (what to cache, where, eviction policy)
□ Sharding/partitioning strategy discussed

Deep Dive:
□ Most complex component explained in detail
□ DB schema or data model shown
□ Concurrency issues addressed
□ Failure scenarios discussed

Wrap-up:
□ Single points of failure identified
□ Bottlenecks addressed
□ Monitoring/observability mentioned
□ Any open questions flagged
