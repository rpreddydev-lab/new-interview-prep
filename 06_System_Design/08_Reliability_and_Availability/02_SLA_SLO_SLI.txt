SLA, SLO, SLI — COMPLETE GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. THE THREE CONCEPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SLI — SERVICE LEVEL INDICATOR
  What it is: A carefully defined quantitative measure of some aspect of
              the level of service that is being provided
  In plain English: The ACTUAL METRIC you measure
  Examples:
    - Request success rate: (successful requests / total requests) × 100%
    - Latency p99: 99th percentile response time
    - Availability: (time service is up / total time) × 100%
    - Throughput: requests per second
    - Error rate: (failed requests / total requests) × 100%

SLO — SERVICE LEVEL OBJECTIVE
  What it is: A target value or range of values for a service level that
              is measured by an SLI
  In plain English: The INTERNAL GOAL for an SLI
  Examples:
    - Success rate SLO: ≥ 99.9%
    - p99 latency SLO: ≤ 200ms
    - Availability SLO: ≥ 99.95%
  Key point: SLOs are internal — violation doesn't automatically mean
             a penalty, but should trigger action

SLA — SERVICE LEVEL AGREEMENT
  What it is: An explicit or implicit contract with your users that
              includes consequences of meeting (or missing) the SLOs
  In plain English: The EXTERNAL CONTRACT with penalties
  Examples:
    - AWS S3: 99.9% availability; if violated, customer gets service credit
    - GCP: 99.95% monthly uptime; <95% uptime → 50% service credit
    - Twilio: 99.95% API uptime; credits issued if missed
  Key point: SLA is a SUBSET of your SLOs — you commit to customers on
             a lower bar than your internal target

HIERARCHY:
  SLI (measurement) → SLO (internal target) → SLA (external commitment)

  SLA target < SLO target < actual performance (ideally)

  Example:
    SLI: p99 latency measured via Prometheus
    SLO: p99 latency < 150ms (internal goal)
    SLA: p99 latency < 200ms (external commitment)
    Actual: p99 latency = 80ms (actual performance)


2. ERROR BUDGET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
  Error Budget = 1 - SLO (expressed as allowable "bad minutes")
  It's the amount of unreliability you're PERMITTED to have

CALCULATION:
  SLO = 99.9%
  Error Budget = 100% - 99.9% = 0.1% per month
  Monthly minutes = 30 × 24 × 60 = 43,200 minutes
  Allowed downtime/error = 43,200 × 0.001 = 43.2 minutes per month

  SLO = 99.99%
  Error Budget = 0.01%
  Allowed downtime = 43,200 × 0.0001 = 4.32 minutes per month

WHY IT MATTERS (Google SRE Model):
  Error budget is shared between:
    - Planned maintenance
    - Deployments (new features carry risk)
    - Incidents
    - Experiments

  IF budget is healthy (lots remaining):
    - Teams can release features faster
    - Can run more experiments
    - Can do more aggressive capacity changes

  IF budget is exhausted (or nearly):
    - Feature releases freeze
    - Focus shifts to reliability work
    - Root cause analysis required
    - No optional changes until budget replenishes

THIS IS THE KEY INSIGHT:
  "Error budget creates a shared language between product (move fast)
   and SRE (keep it reliable). Both sides agree on the same number."

ERROR BUDGET POLICY (example):
  ┌────────────────────────────┬────────────────────────────────────┐
  │ Budget Remaining           │ Action                             │
  ├────────────────────────────┼────────────────────────────────────┤
  │ > 50%                      │ Normal: full feature velocity       │
  │ 25% - 50%                  │ Caution: review deployment risk     │
  │ 10% - 25%                  │ Elevated: only critical releases    │
  │ < 10%                      │ Freeze: reliability work only       │
  │ 0% (exhausted)             │ Incident review, no releases        │
  └────────────────────────────┴────────────────────────────────────┘


3. CHOOSING SLIs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NOT ALL METRICS MAKE GOOD SLIs:
  Good SLI: Directly correlated with user experience
  Bad SLI: CPU utilization (high CPU doesn't always mean bad UX)

GOOGLE'S SLI CATEGORIES BY SERVICE TYPE:

User-Facing Services (APIs, websites):
  - Availability: % requests that succeed
  - Latency: % requests served under threshold (e.g., < 100ms)
  - Quality: % requests served without degradation
  Formula: SLI = (good events / valid events) × 100%

Storage Systems (databases, object stores):
  - Durability: % data written that can be read back successfully
  - Availability: % read/write requests that succeed
  - Latency: p99 read/write response time

Data Processing Pipelines (ETL, streaming):
  - Freshness: % data processed within defined time window
  - Correctness: % pipeline outputs matching expected values
  - Coverage: % input data successfully processed

LATENCY SLI SPECIFICS:
  Don't use averages! Use percentiles:
    - p50: median — 50% of requests are faster than this
    - p95: 95% of requests are faster than this
    - p99: 99% of requests are faster than this
    - p99.9: 99.9% of requests are faster than this

  Why percentiles matter:
    Average = 50ms, but p99 = 5,000ms means 1% of users wait 5 seconds
    That 1% matters — especially for your highest-value users

  IMPLEMENTATION: Use histogram metrics (Prometheus histogram, not gauge)


4. SETTING REALISTIC SLOs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

COMMON MISTAKE: Setting SLOs too tight (99.999% for everything)
  - Creates unrealistic pressure
  - Forces expensive infrastructure
  - Any maintenance violates SLO
  - On-call engineers are constantly paged

COMMON MISTAKE: Setting SLOs too loose (90%)
  - Users have a terrible experience
  - No real incentive to improve

PROCESS FOR SETTING SLOs:
  1. Look at historical data — what have you actually achieved?
  2. Ask: what do users actually need? (not what they say they want)
  3. Set SLO slightly below actual historical performance
  4. Leave room for error budget to be used intentionally
  5. Review and tighten SLOs over time as reliability improves

EXAMPLE: Setting availability SLO
  Historical data shows 99.95% over the past 6 months
  Users complain when error rate > 0.5%
  Set SLO = 99.9% (slightly looser than historical)
  Error budget = 0.1% = 43.2 min/month — room to deploy and experiment


5. SLO ALERTING — MULTI-WINDOW BURN RATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM WITH SIMPLE THRESHOLD ALERTING:
  "Alert if error rate > 0.1%" — causes too many false positives
  Missing context: how long has it been elevated? how fast is budget burning?

BURN RATE:
  How fast you're consuming error budget relative to the allowed rate
  Burn rate = 1 means consuming budget at the exact SLO rate
  Burn rate = 10 means consuming 10× faster — budget exhausted in 1/10 the time

  With SLO = 99.9%, error budget = 0.1%:
  Burn rate of 1:  0.1% errors — normal
  Burn rate of 10: 1% errors — budget gone in 3 days (not 30)
  Burn rate of 100: 10% errors — budget gone in 7.2 hours

MULTI-WINDOW BURN RATE ALERTS (Google SRE recommended):

  ┌──────────┬────────────┬────────────┬───────────────────────────┐
  │ Severity │ Long Window│ Short Window│ Burn Rate                 │
  ├──────────┼────────────┼────────────┼───────────────────────────┤
  │ Page NOW │ 1 hour     │ 5 minutes  │ > 14.4 (consumes 2% budget│
  │          │            │            │  in 1 hour)               │
  │ Page FAST│ 6 hours    │ 30 minutes │ > 6 (consumes 5% budget   │
  │          │            │            │  in 6 hours)              │
  │ Ticket   │ 3 days     │ 6 hours    │ > 3 (consumes 30% budget  │
  │          │            │            │  in 3 days)               │
  │ Ticket   │ 3 days     │ 6 hours    │ > 1 (slow burn)           │
  └──────────┴────────────┴────────────┴───────────────────────────┘

  Short window: fast reaction (don't page on a 1-minute blip)
  Long window: significance (sustained issue, not a transient spike)
  Both must be true to trigger — avoids false positives


6. REAL-WORLD SLA EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AWS S3:
  SLO: 99.99% availability (design target)
  SLA: 99.9% monthly uptime (commitment)
  Penalty: 10% service credit for 99%-99.9%, 25% for < 99%

AWS EC2:
  SLA: 99.99% monthly uptime
  Penalty: 10% credit for 99%-99.99%, 30% for < 99%

Google Cloud SQL:
  SLA: 99.95% monthly uptime
  Penalty: 10% credit for 99%-99.95%, 25% for < 99%

Stripe API:
  SLA: 99.99% uptime
  Penalty: Service credits up to 15 days

PagerDuty:
  SLA: 99.9% uptime
  Penalty: Service credits proportional to downtime

NOTE: SLAs exclude scheduled maintenance, force majeure, and often
      customer-caused issues. Always read the exclusions!


7. SLO EXAMPLES BY SYSTEM TYPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

E-COMMERCE CHECKOUT:
  SLI: % checkout requests succeeding in < 2 seconds
  SLO: 99.95% of checkout requests complete successfully in < 2s
  SLA: 99.9% uptime for checkout service
  Error Budget: 0.05% = 21.9 minutes/month

STREAMING VIDEO (YouTube-like):
  SLI: % video play requests that start within 3 seconds without buffering
  SLO: 99% of video plays start in < 3 seconds
  SLA: N/A (free consumer service — usually no SLA)
  Error Budget: 1% = 7.2 hours/month

PAYMENT API (Stripe-like):
  SLI: % payment API calls returning 2xx in < 1 second
  SLO: 99.99% success rate, p99 latency < 500ms
  SLA: 99.99% availability
  Error Budget: 0.01% = 4.32 min/month (VERY tight — need automation)

INTERNAL MICROSERVICE (user-profile-service):
  SLI: % gRPC calls succeeding, p99 latency < 50ms
  SLO: 99.9% success, p99 < 50ms
  SLA: N/A (internal service — no external contract)
  Error Budget: 0.1% = 43.2 min/month

INTERVIEW ANSWER — "Explain SLA, SLO, SLI and error budgets"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"SLI is the actual metric we measure — like p99 latency or success rate.
SLO is our internal target for that metric — 'p99 latency < 150ms'.
SLA is the external contract — 'we guarantee p99 < 200ms or you get credits'.

The SLA is intentionally looser than the SLO — the gap is a safety margin.

The error budget is 1 minus the SLO. At 99.9% SLO, we have 43 minutes/month
of allowed downtime. This budget is shared: deployments, incidents, experiments
all consume it. When budget is healthy, teams can release faster. When it's
nearly gone, we freeze features and focus on reliability.

The power is alignment: engineering and product agree on the same number.
Product can't demand 10 deploys per day if each deploy risks burning
the monthly error budget in 4 days."
