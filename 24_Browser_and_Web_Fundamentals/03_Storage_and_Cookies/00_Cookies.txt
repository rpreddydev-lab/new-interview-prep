1. WHAT ARE COOKIES?
────────────────────────────────────────────────────────────────────────────────

  Cookies are small key-value data fragments stored in the browser.
  Automatically sent with every HTTP request to the matching domain.

  Primary use cases:
    • Session management (auth tokens, login state)
    • Personalization (themes, language, preferences)
    • Tracking (analytics, advertising)

  Cookie anatomy (as a header):
    Set-Cookie: sessionId=abc123; Max-Age=3600; Domain=example.com;
                Path=/; Secure; HttpOnly; SameSite=Strict

  Reading/Writing cookies in JS:
    document.cookie = "name=value"; // write (does NOT replace all cookies)
    document.cookie; // read (returns all cookies as a string)

  Parse cookies from document.cookie:
    function getCookie(name) {
      return document.cookie
        .split('; ')
        .find(row => row.startsWith(name + '='))
        ?.split('=')[1];
    }

2. COOKIE ATTRIBUTES
────────────────────────────────────────────────────────────────────────────────

  2.1 Expiry / Lifetime
    Session cookie (no expiry attribute):
      Deleted when browser closes (stored in memory only).

    Persistent cookie:
      Expires=Thu, 01 Jan 2026 00:00:00 GMT   (absolute date)
      Max-Age=3600                             (seconds from now, takes precedence)
      
    Max-Age=0 → delete cookie immediately.
    Negative Max-Age → session cookie.

  2.2 Domain
    Domain=example.com
    Specifies which domains can receive the cookie.
    
    • If set: cookie sent to domain AND all subdomains (api.example.com, etc.)
    • If not set: only sent to the exact origin domain (no subdomains)
    • Cannot set a domain that is not the current domain or parent domain

  2.3 Path
    Path=/api
    Cookie only sent for requests matching this path prefix.
    
    Path=/ → all paths (default)
    Path=/admin → only /admin, /admin/users, etc.

  2.4 Secure
    Cookie only sent over HTTPS connections.
    Prevents sending cookie over plain HTTP (man-in-the-middle).
    
    Set-Cookie: token=abc; Secure

  2.5 HttpOnly
    Cookie inaccessible to JavaScript (document.cookie won't show it).
    Mitigates XSS attacks — attacker's script cannot steal the cookie.
    
    Set-Cookie: sessionId=xyz; HttpOnly

  2.6 SameSite (critical for CSRF prevention)
    Controls when cookies are sent with cross-site requests.
    
    SameSite=Strict:
      Cookie only sent for same-site requests.
      Never sent on cross-site navigation (clicking a link from another site).
      Most secure. Breaks links that rely on cookie state (e.g., OAuth flows).
    
    SameSite=Lax (default in modern browsers):
      Sent with same-site requests + top-level GET navigations (clicking links).
      NOT sent on cross-site POST, XHR, or iframe requests.
      Good balance of security and usability.
    
    SameSite=None:
      Sent with all cross-site requests (needed for third-party cookies).
      MUST be paired with Secure attribute.
      Set-Cookie: embed=value; SameSite=None; Secure

  2.7 Priority (Chrome-only)
    Priority=High|Medium|Low
    Used by Chrome to decide which cookies to evict when storage quota is full.

3. COOKIE TYPES
────────────────────────────────────────────────────────────────────────────────

  Session Cookies:
    No expiry date. Deleted when browser closes.
    Used for login sessions.

  Persistent Cookies:
    Have expiry date (Expires or Max-Age).
    Survive browser restarts until expiry.
    Used for "remember me", preferences.

  First-Party Cookies:
    Set by the site you are visiting.
    Sent to that same site.
    Generally accepted by browsers.

  Third-Party Cookies:
    Set by a different domain (e.g., analytics or ad script embedded in page).
    Being phased out by browsers (Safari ITP, Firefox ETP, Chrome Privacy Sandbox).
    Used for cross-site tracking and advertising.

  Secure Cookies:
    Have the Secure flag — sent only over HTTPS.

  HttpOnly Cookies:
    Have HttpOnly flag — not accessible via JS. Server-only.

  Zombie / Supercookies:
    Cookies recreated using other storage mechanisms (fingerprinting, ETag, flash).
    Used to track users even after clearing cookies.

────────────────────────────────────────────────────────────────────────────────
4. COOKIE LIMITS
────────────────────────────────────────────────────────────────────────────────

  Per-cookie size: 4096 bytes (4KB)
  Per-domain: ~50 cookies max
  Total: varies by browser (~3000+ cookies)

  Cookies over 4KB are silently dropped by browsers.

5. COOKIES AND AUTHENTICATION
────────────────────────────────────────────────────────────────────────────────

  Cookie-based Session Auth (traditional):
    1. User logs in → server creates session in DB
    2. Server sends Set-Cookie: sessionId=abc; HttpOnly; Secure
    3. Browser stores cookie
    4. Every request includes Cookie: sessionId=abc header
    5. Server validates sessionId against DB
    
    Pros: Simple; revocable immediately (delete from DB); no JS needed
    Cons: Server must store sessions (scaling challenge)

  JWT in Cookies:
    Cookie: jwt=eyJhbGci...
    Server validates JWT signature (stateless).
    HttpOnly cookie prevents XSS from stealing JWT.
    
    Pros: Stateless; can be used with CDN/edge
    Cons: Cannot revoke tokens (until expiry) unless using a denylist

  JWT in localStorage vs HttpOnly Cookie:
    localStorage: accessible by JS (XSS risk), no auto-send (no CSRF risk)
    HttpOnly Cookie: inaccessible to JS (XSS safe), auto-sent (CSRF risk with SameSite)
    Recommendation: HttpOnly cookie + SameSite=Lax/Strict for most apps

6. COOKIE API (OLDER vs MODERN)
────────────────────────────────────────────────────────────────────────────────

  document.cookie (legacy):
    • Getter returns all cookies as a flat string
    • Setter adds/updates ONE cookie per assignment (not replace-all)
    
    // Set
    document.cookie = "key=value; Max-Age=3600; Path=/";
    // Delete
    document.cookie = "key=; Max-Age=0; Path=/";
    // Read (requires parsing)
    document.cookie → "key=value; other=data"

  Cookie Store API (modern, async):
    Available in Service Workers and secure windows (experimental).
    
    // Get
    const cookie = await cookieStore.get('name');
    // Set
    await cookieStore.set({ name: 'name', value: 'val', expires: Date.now() + 86400000 });
    // Delete
    await cookieStore.delete('name');
    // Subscribe to changes (Service Worker)
    cookieStore.addEventListener('change', event => { ... });

7. THIRD-PARTY COOKIE DEPRECATION
────────────────────────────────────────────────────────────────────────────────

  Timeline:
    • Safari ITP (Intelligent Tracking Prevention): 2017+ — blocks 3rd party cookies
    • Firefox ETP (Enhanced Tracking Protection): 2019+
    • Chrome: planned to phase out 3rd party cookies (delayed to 2025+)

  Impact:
    • Cross-site tracking and ad measurement affected
    • SSO flows using cookies across domains affected
    • Embedded widgets (Disqus, Facebook Like) affected

  Alternatives:
    • Privacy Sandbox (FLoC/Topics API — Google's proposal)
    • First-party data collection
    • Server-side analytics
    • CHIPS (Cookies Having Independent Partitioned State)
      Cookie partitioned per top-level site:
      Set-Cookie: widget_session=val; Partitioned; SameSite=None; Secure

8. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between session and persistent cookies?
A: Session cookies have no expiry attribute — they're stored in memory and
   deleted when the browser is closed. Persistent cookies have Expires or
   Max-Age set — they survive browser restarts until they expire.

Q: What does HttpOnly do?
A: Makes the cookie inaccessible to JavaScript (document.cookie returns it
   empty). This is a critical security attribute that prevents XSS attacks
   from stealing authentication cookies. Server sets them; only browser
   sends them automatically.

Q: What does SameSite=Lax vs Strict vs None mean?
A: Strict: cookie only sent for same-site requests (never on cross-site
   navigation). Lax (default): sent for same-site + top-level GET navigations
   from other sites (e.g., clicking a link). None: sent with all requests
   (cross-site too), but requires Secure flag. SameSite prevents CSRF.

Q: How would you store an auth token securely?
A: Use an HttpOnly Secure SameSite=Strict/Lax cookie set by the server.
   This prevents XSS from reading the token (HttpOnly) and protects from
   CSRF (SameSite). Avoid localStorage for auth tokens as it's accessible
   to any JS on the page.

Q: What are third-party cookies and why are they being phased out?
A: Third-party cookies are set by a different domain than the one you're
   visiting (e.g., an ad network embedded on a page). They enable cross-site
   tracking. Browsers are phasing them out for privacy reasons. Alternatives
   include Privacy Sandbox APIs and server-side analytics.

Q: How do you delete a cookie?
A: Set Max-Age=0 (or set Expires to a past date) with the same Path and
   Domain that were used to set it:
   document.cookie = "key=; Max-Age=0; Path=/; Domain=example.com";

Q: What is the difference between Domain=example.com and not setting Domain?
A: Setting Domain=example.com makes the cookie available to example.com AND
   all its subdomains. Not setting Domain restricts the cookie to the exact
   host that set it (subdomains don't receive it).

  KEY TAKEAWAYS
================================================================================
  • Cookies: automatically sent with requests; 4KB limit; up to ~50 per domain
  • HttpOnly: blocks JS access; XSS mitigation
  • Secure: HTTPS-only transmission
  • SameSite=Lax/Strict: CSRF mitigation
  • Session vs Persistent: no expiry vs Expires/Max-Age set
  • Auth tokens: prefer HttpOnly Secure SameSite cookie over localStorage
  • Third-party cookies: being phased out; partitioned cookies (CHIPS) as future
