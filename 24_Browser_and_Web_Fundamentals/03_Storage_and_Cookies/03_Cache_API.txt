1. WHAT IS THE CACHE API?
────────────────────────────────────────────────────────────────────────────────

  The Cache API is a storage mechanism for Request/Response pairs.
  Primarily designed for use with Service Workers to enable offline experiences.

  Key features:
    ✓ Stores Request/Response pairs (not just strings like localStorage)
    ✓ Available in Service Workers, Web Workers, and window context
    ✓ Async API (Promise-based)
    ✓ Named caches — multiple caches per origin
    ✓ Used in offline strategies (cache-first, stale-while-revalidate, etc.)
    ✓ Persistent until explicitly deleted (not subject to browser HTTP cache)
    ✓ Quota: shared with IndexedDB quota (~60% of disk)

  Cache API vs HTTP Cache:
    HTTP Cache: managed by browser, based on HTTP headers (Cache-Control, ETag)
    Cache API: managed by developer code (usually in Service Worker)
    Both can coexist — Cache API bypasses HTTP cache controls

2. CACHE API METHODS
────────────────────────────────────────────────────────────────────────────────

  2.1 Opening / Creating a Cache
    const cache = await caches.open('my-cache-v1');
    // Opens existing cache or creates a new one

  2.2 Storing Responses
    // cache.put(request, response) — store any Request/Response pair
    const response = await fetch('/api/data');
    await cache.put('/api/data', response);
    
    // cache.add(url) — fetch URL and store it
    await cache.add('/style.css');
    
    // cache.addAll(urls) — fetch multiple URLs and store all
    await cache.addAll([
      '/',
      '/style.css',
      '/app.js',
      '/offline.html'
    ]);
    // addAll is all-or-nothing: if ONE fails, nothing is cached

  2.3 Retrieving Responses
    // cache.match(request) — search this specific cache
    const response = await cache.match('/style.css');
    if (response) {
      return response; // cache hit
    }
    
    // caches.match(request) — search ALL caches for the origin
    const response = await caches.match('/style.css');

  2.4 Listing Keys (Cached Requests)
    const keys = await cache.keys();
    keys.forEach(request => console.log(request.url));

  2.5 Deleting Entries
    // delete single entry
    await cache.delete('/old-asset.js');
    
    // delete entire named cache
    await caches.delete('my-cache-v1');
    
    // list all cache names
    const cacheNames = await caches.keys();

  2.6 Manual Response Creation
    // You can store any custom response, not just fetched ones
    const customResponse = new Response(
      JSON.stringify({ data: 'cached' }),
      {
        headers: { 'Content-Type': 'application/json' }
      }
    );
    await cache.put('/api/custom', customResponse);

3. CACHE VERSIONING
────────────────────────────────────────────────────────────────────────────────

  Since Cache API doesn't auto-expire, use versioning to manage stale caches:

    const CACHE_NAME = 'app-cache-v3'; // bump version on each deployment
    
    self.addEventListener('activate', event => {
      event.waitUntil(
        caches.keys().then(cacheNames => {
          return Promise.all(
            cacheNames
              .filter(name => name !== CACHE_NAME) // old versions
              .map(name => caches.delete(name))
          );
        })
      );
    });

  Strategy: Always use versioned cache names (e.g., 'v1', date-based, hash-based).
  Delete old versions in the SW activate event.

4. COMMON PATTERNS WITH SERVICE WORKERS
────────────────────────────────────────────────────────────────────────────────

  4.1 Precaching (Cache on Install)
    Cache critical assets during SW install.
    
    const PRECACHE = 'precache-v1';
    const PRECACHE_ASSETS = ['/', '/style.css', '/app.js'];
    
    self.addEventListener('install', event => {
      event.waitUntil(
        caches.open(PRECACHE)
          .then(cache => cache.addAll(PRECACHE_ASSETS))
      );
    });

  4.2 Cache-First Strategy
    self.addEventListener('fetch', event => {
      event.respondWith(
        caches.match(event.request).then(cached => {
          if (cached) return cached;
          return fetch(event.request).then(response => {
            const clone = response.clone();
            caches.open('dynamic').then(cache => cache.put(event.request, clone));
            return response;
          });
        })
      );
    });

  4.3 Network-First Strategy
    self.addEventListener('fetch', event => {
      event.respondWith(
        fetch(event.request)
          .then(response => {
            const clone = response.clone();
            caches.open('dynamic').then(cache => cache.put(event.request, clone));
            return response;
          })
          .catch(() => caches.match(event.request))
      );
    });

  4.4 Stale-While-Revalidate
    self.addEventListener('fetch', event => {
      event.respondWith(
        caches.open('dynamic').then(cache => {
          return cache.match(event.request).then(cached => {
            const networkFetch = fetch(event.request).then(response => {
              cache.put(event.request, response.clone());
              return response;
            });
            return cached || networkFetch;
          });
        })
      );
    });

  4.5 Offline Fallback
    self.addEventListener('fetch', event => {
      if (event.request.mode === 'navigate') {
        event.respondWith(
          fetch(event.request).catch(() => caches.match('/offline.html'))
        );
      }
    });

5. CACHE API vs HTTP CACHE vs SERVICE WORKER CACHE
────────────────────────────────────────────────────────────────────────────────

  ┌───────────────────┬────────────────────┬───────────────────────────────┐
  │ Feature           │ HTTP Cache         │ Cache API (via SW)            │
  ├───────────────────┼────────────────────┼───────────────────────────────┤
  │ Control           │ Server (headers)   │ Developer (JS code)           │
  │ Granularity       │ Per-response       │ Full control per request      │
  │ Offline support   │ Limited            │ Yes (explicit offline logic)  │
  │ Invalidation      │ Cache-Control, ETag│ Manual (explicit delete)      │
  │ Access from SW    │ No (not directly)  │ Yes                           │
  │ Stores            │ Response body only │ Request + Response pairs      │
  │ Cross-tab sharing │ Yes                │ Yes (same origin)             │
  └───────────────────┴────────────────────┴───────────────────────────────┘

6. CACHE MATCHING OPTIONS
────────────────────────────────────────────────────────────────────────────────

  cache.match(request, options):
  
  options.ignoreSearch (default: false):
    Ignore query string when matching.
    cache.match('/api/data', { ignoreSearch: true })
    Matches /api/data, /api/data?page=1, /api/data?sort=asc, etc.

  options.ignoreMethod (default: false):
    Match regardless of HTTP method (GET, POST, etc.)

  options.ignoreVary (default: false):
    Ignore Vary header differences.

7. CACHE STORAGE LIMITS AND EVICTION
────────────────────────────────────────────────────────────────────────────────

  Cache API shares quota with IndexedDB and other origins storage.
  Typical quota: 60% of total disk space.

  Check available storage:
    const estimate = await navigator.storage.estimate();
    console.log('Quota:', estimate.quota);
    console.log('Used:', estimate.usage);

  Request persistent storage (prevents eviction under storage pressure):
    const isPersisted = await navigator.storage.persist();
    if (isPersisted) {
      console.log('Storage will not be cleared without user action');
    }

  Eviction policy (without persistent storage):
    Browser may evict origins' storage when under disk pressure.
    Order: least recently used origins evicted first.

8. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the Cache API?
A: A Promise-based browser API for storing and retrieving Request/Response
   pairs. It's primarily used in Service Workers to implement offline caching
   strategies. Unlike the HTTP cache (controlled by response headers), the
   Cache API is fully controlled by developer code and persists until
   explicitly deleted.

Q: What is the difference between cache.add() and cache.put()?
A: cache.add(url) fetches the URL from the network and stores the response.
   cache.put(request, response) directly stores a provided Request/Response
   pair without making a network request. put() is used when you already have
   a response (e.g., cloned from a fetch). addAll() is all-or-nothing —
   if any URL fails to fetch, nothing gets cached.

Q: How does cache versioning work?
A: You name your caches with a version (e.g., 'app-v2'). When deploying
   updates, you bump the version in the SW file. In the activate event, delete
   all caches that don't match the current version name. This ensures old
   cached assets are cleaned up when the new SW activates.

Q: Why must you clone a response before caching it?
A: Response bodies are streams and can only be consumed ONCE. If you return
   a response to the browser AND try to put it in the cache, one of them will
   get an empty body. Calling response.clone() creates an independent copy so
   both the browser and cache get a valid response body.
   
   const response = await fetch(request);
   const clone = response.clone(); // independent copy
   cache.put(request, clone);      // store clone
   return response;                // return original to browser

Q: How is the Cache API different from the HTTP cache?
A: HTTP cache is managed by the browser based on response headers
   (Cache-Control, ETag, Expires) — developer has limited control.
   Cache API is entirely controlled by JS code, usually in Service Workers.
   It allows custom offline strategies, manual invalidation, and storing
   any Request/Response regardless of HTTP cache headers.

Q: What happens to Cache API data when disk is full?
A: Without navigator.storage.persist(), the browser may evict storage for
   least-recently-used origins. Call navigator.storage.persist() to request
   persistent storage (user may be prompted for permission) which prevents
   automatic eviction.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Cache API stores Request/Response pairs; primarily used in Service Workers
  • caches.open(name) → creates/opens a named cache
  • cache.add/addAll → fetch + store; cache.put → store existing response
  • caches.match → search across all caches; cache.match → one specific cache
  • Clone responses before using AND caching (streams are single-use)
  • Version caches (e.g., 'v2'), delete old versions in activate event
  • navigator.storage.persist() → request protection from eviction
