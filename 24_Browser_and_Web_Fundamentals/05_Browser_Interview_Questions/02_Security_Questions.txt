SECTION 1: XSS
────────────────────────────────────────────────────────────────────────────────

Q1: What is XSS and what are the three types?
──────────────────────────────────────────────
Answer:
  XSS (Cross-Site Scripting) is an injection attack where malicious scripts
  are injected into web pages viewed by other users.
  
  Types:
  
  Reflected (Non-Persistent):
    Script is in the request URL. Server includes it in response without sanitization.
    Victim clicks a crafted URL with script in the query string.
    Example: https://site.com/search?q=<script>stealCookies()</script>
  
  Stored (Persistent):
    Script is saved to the database and served to all users.
    Most dangerous — affects many users without them clicking special links.
    Example: blog comment containing <script>...</script>
  
  DOM-Based:
    Client-side JavaScript reads from an untrusted source and writes to a DOM sink.
    Server is not involved — all happens in the browser.
    Example: document.getElementById('output').innerHTML = location.hash.slice(1);

Q2: How do you prevent XSS?
─────────────────────────────
Answer:
  1. Output encoding: Escape user data before inserting into HTML.
     Use textContent (not innerHTML) for plain text.
     In templates: {{ expression }} auto-encodes; beware of unescaped output.
  
  2. Input sanitization: Use DOMPurify to sanitize rich HTML content.
     import DOMPurify from 'dompurify';
     element.innerHTML = DOMPurify.sanitize(userHtml);
  
  3. Content Security Policy (CSP): block inline scripts and unauthorized sources.
     Content-Security-Policy: script-src 'nonce-{random}' 'strict-dynamic'
  
  4. HttpOnly cookies: Even if XSS fires, cookies can't be stolen.
  
  5. Trusted Types API: Enforce that all DOM sinks receive safe typed objects.
  
  6. Framework protections: React JSX auto-escapes; avoid dangerouslySetInnerHTML.
     Angular sanitizes bindings; avoid bypassSecurityTrustHtml.

Q3: What is the difference between innerHTML and textContent?
──────────────────────────────────────────────────────────────
Answer:
  innerHTML:
    Parses the string as HTML and inserts it into the DOM.
    Scripts and event handlers in the string will execute.
    DANGEROUS for user-provided content.
    element.innerHTML = '<img src=x onerror=alert(1)>'; // XSS!
  
  textContent:
    Inserts as literal text — HTML tags are treated as text, not parsed.
    No script execution possible.
    SAFE for user-provided text content.
    element.textContent = '<img src=x onerror=alert(1)>'; // displayed as text
  
  innerText: Similar to textContent but accounts for CSS styling (not shown
  elements are excluded). Slower because it triggers reflow.

Q4: What is a CSP nonce and how does it prevent XSS?
──────────────────────────────────────────────────────
Answer:
  A nonce (number used once) is a random, unique, base64-encoded value
  generated per response by the server.
  
  Server sets header:
    Content-Security-Policy: script-src 'nonce-r4nd0mV4lu3'
  
  Server adds nonce to legitimate scripts:
    <script nonce="r4nd0mV4lu3">// allowed code</script>
  
  An attacker who injects <script>evil()</script> doesn't know the nonce
  for this request → browser blocks it.
  
  The nonce must be:
  • Unique per page load (randomized each response)
  • Cryptographically random (not guessable)
  • At least 128 bits of entropy

SECTION 2: CSRF
────────────────────────────────────────────────────────────────────────────────

Q5: What is CSRF and how does it work?
───────────────────────────────────────
Answer:
  CSRF (Cross-Site Request Forgery) tricks an authenticated user into
  making unintended requests to a site where they're logged in.
  
  Attack mechanism: Browsers auto-send cookies with every matching-domain request.
  
  Example attack:
  1. User logged into bank.com
  2. User visits evil.com which contains:
     <img src="https://bank.com/transfer?to=attacker&amount=5000">
  3. Browser requests the URL → auto-includes bank.com session cookie
  4. Bank processes the transfer as authenticated!
  
  CSRF doesn't need to read the response — it just needs the action to happen.

Q6: What are the defenses against CSRF?
────────────────────────────────────────
Answer:
  1. SameSite cookies (primary modern defense):
     SameSite=Strict: no cross-site requests include cookie.
     SameSite=Lax (default): blocks cross-site POST/AJAX but allows GET nav.
  
  2. CSRF tokens:
     Server generates random token, stores in session, embeds in form.
     Server validates token on submission.
     Attacker on different origin can't read the token → can't forge.
  
  3. Custom request headers (for AJAX):
     X-Requested-With: XMLHttpRequest or X-CSRF-Token header.
     Cross-origin form submissions can't set custom headers.
  
  4. Origin/Referer header validation:
     Verify request comes from expected origin.
     Less reliable (headers can be absent).
  
  5. Re-authentication for sensitive actions (password, 2FA).

Q7: Explain the difference between XSS and CSRF.
──────────────────────────────────────────────────
Answer:
  ┌──────────────┬────────────────────────────┬────────────────────────────┐
  │ Aspect       │ XSS                        │ CSRF                       │
  ├──────────────┼────────────────────────────┼────────────────────────────┤
  │ What it does │ Executes scripts on site   │ Makes requests as the user │
  │ Trust abused │ User trusts target site    │ Server trusts user's browser│
  │ Data theft   │ Yes (cookies, tokens, DOM) │ No (can't read responses)  │
  │ Origin       │ Injected script on victim  │ Script on attacker's site  │
  │ Prevention   │ Output encoding, CSP       │ CSRF tokens, SameSite      │
  └──────────────┴────────────────────────────┴────────────────────────────┘
  
  XSS can be used to bypass CSRF tokens (read the token from DOM and use it
  in a forged request). So XSS prevention is critical for both.

SECTION 3: CORS
────────────────────────────────────────────────────────────────────────────────

Q8: What is the Same-Origin Policy?
─────────────────────────────────────
Answer:
  The Same-Origin Policy is a browser security mechanism that restricts how
  documents or scripts from one origin can interact with resources from a
  different origin.
  
  Origin = protocol + hostname + port.
  
  SOP prevents JS on evil.com from:
  • Reading responses from bank.com
  • Accessing DOM of bank.com frames
  • Making authenticated API calls and reading results
  
  SOP allows:
  • Cross-origin writes (forms, links, redirects)
  • Cross-origin embedding (iframes, img, script, link)
  • Reading public resources without credentials

Q9: What is the difference between a preflight request and a simple CORS request?
──────────────────────────────────────────────────────────────────────────────────
Answer:
  Simple request (no preflight):
    GET, HEAD, or POST with Content-Type of text/plain, 
    application/x-www-form-urlencoded, or multipart/form-data.
    Browser sends request directly with Origin header.
    Server responds with Access-Control-Allow-Origin.
  
  Preflight request:
    Any other method (PUT, DELETE, PATCH), custom headers, JSON content type.
    Browser first sends OPTIONS request:
      Access-Control-Request-Method: PUT
      Access-Control-Request-Headers: Content-Type, Authorization
    Server responds with allowed methods/headers.
    If approved, browser makes the actual request.
  
  Purpose: Protect old servers that weren't designed for cross-origin requests
  from receiving unexpected PUT/DELETE/JSON requests.

Q10: Why doesn't CORS prevent CSRF?
──────────────────────────────────────
Answer:
  CORS prevents cross-origin JS from READING responses.
  CSRF is about cross-origin requests being SENT (state changes).
  
  Simple form POST (application/x-www-form-urlencoded) is a "simple request":
  • No CORS preflight
  • Request IS sent to the server
  • Browser blocks JS from reading the response
  • But the server already processed the transfer/action!
  
  CORS protects data confidentiality (reading), not request integrity (writing).
  Use SameSite cookies and CSRF tokens to prevent forged requests.

SECTION 4: HTTPS AND CSP
────────────────────────────────────────────────────────────────────────────────

Q11: How does the TLS handshake work?
───────────────────────────────────────
Answer:
  TLS 1.3 (simplified):
  
  1. ClientHello: Browser sends supported cipher suites, client random, key share.
  2. ServerHello: Server chooses cipher, sends server random, key share, certificate.
  3. Certificate validation:
     - Valid signature from trusted CA?
     - Domain matches CN/SAN?
     - Not expired or revoked?
  4. Key derivation: Both sides compute same session key via ECDHE (without transmitting it).
  5. Finished: Encrypted handshake confirmation.
  6. Secure communication begins with symmetric encryption.
  
  TLS 1.3 improvements: 1-RTT (was 2-RTT), mandatory forward secrecy,
  eliminated weak cipher suites.

Q12: What is HSTS and why is it important?
───────────────────────────────────────────
Answer:
  HTTP Strict Transport Security: server tells browsers to always use HTTPS.
  
  Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  
  Why it matters:
  • Prevents SSL stripping attacks: attacker intercepts first HTTP request,
    downgrades to HTTP. HSTS makes browser refuse HTTP from the start.
  • After first HTTPS visit, browser ignores any HTTP URL for the domain.
  
  HSTS Preload: domains registered at hstspreload.org are hardcoded into
  browsers — always HTTPS even on the very first visit.

Q13: What is Clickjacking and how do you prevent it?
─────────────────────────────────────────────────────
Answer:
  Clickjacking: attacker embeds target site in an invisible iframe overlay.
  User thinks they're clicking the attacker's fake UI but actually clicks
  the target site's buttons.
  
  Prevention:
  
  1. X-Frame-Options: DENY (or SAMEORIGIN) — prevents framing.
  2. CSP frame-ancestors 'none' (preferred — more flexible):
     Content-Security-Policy: frame-ancestors 'none'
  
  Supports multiple origins: frame-ancestors 'self' https://partner.com
  
  JavaScript frame busters are unreliable (defeated by sandbox attribute).
  Use HTTP headers — they're enforced before any JS runs.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • XSS: injected scripts; prevent with output encoding, CSP, DOMPurify, HttpOnly
  • CSRF: forged requests; prevent with SameSite=Lax, CSRF tokens
  • XSS can bypass CSRF tokens — fix XSS first
  • SOP: blocks cross-origin reads; CORS allows controlled cross-origin access
  • CORS preflight: OPTIONS for non-simple requests; checks allowed methods/headers
  • CORS doesn't prevent CSRF; only prevents response reading
  • TLS: encrypt in transit; certificate validates server identity
  • HSTS: force HTTPS; prevents SSL stripping
  • Clickjacking: X-Frame-Options DENY + CSP frame-ancestors 'none'
================================================================================
