SECTION 1: PERFORMANCE & CORE WEB VITALS
────────────────────────────────────────────────────────────────────────────────

Q1: What are Core Web Vitals?
──────────────────────────────
Answer:
  Google's set of metrics for user experience quality:
  
  LCP (Largest Contentful Paint):
    Time until the largest visible content element is rendered.
    Target: ≤ 2.5 seconds. Measures loading performance.
    Measured elements: <img>, <video> poster, CSS background-image, <h1>-<h6>, <p>.
    Common causes of poor LCP: slow server (TTFB), render-blocking resources,
    slow resource loading, client-side rendering.
  
  INP (Interaction to Next Paint) [replaces FID]:
    Measures responsiveness to user interactions.
    Target: ≤ 200ms. Measures input delay + processing time + render delay.
    Poor INP: long JS tasks blocking the main thread.
  
  CLS (Cumulative Layout Shift):
    Measures visual stability — unexpected layout shifts.
    Target: ≤ 0.1. Score = impact fraction × distance fraction.
    Common causes: images without dimensions, ads injected above content,
    fonts causing FOIT/FOUT shifts, dynamically injected elements.
  
  Other important metrics:
  • TTFB (Time to First Byte): server response time. Target ≤ 800ms.
  • FCP (First Contentful Paint): first text/image. Target ≤ 1.8s.
  • TTI (Time to Interactive): page consistently responds. Target ≤ 3.8s.
  • TBT (Total Blocking Time): sum of blocking portions of long tasks. Target ≤ 200ms.

Q2: How would you optimize a slow-loading web page?
─────────────────────────────────────────────────────
Answer:
  Network optimizations:
  • Reduce TTFB: server-side caching, CDN, database query optimization
  • HTTP/2 or HTTP/3 for multiplexing
  • Compress assets: gzip/brotli for text, WebP/AVIF for images
  • Use a CDN for static assets
  
  Critical Rendering Path:
  • Inline critical CSS (above-the-fold styles)
  • Defer non-critical CSS (media="print" trick or loadCSS)
  • Async/defer non-critical JS
  • Preload key resources: <link rel="preload">
  • Preconnect to third-party origins: <link rel="preconnect">
  
  JavaScript:
  • Code split: ship only what's needed per route
  • Tree-shake: remove dead code
  • Lazy load: React.lazy(), dynamic import()
  • Remove render-blocking scripts
  
  Images:
  • Lazy load below-fold images: loading="lazy"
  • Preload hero image: <link rel="preload" as="image">
  • Use correct sizes: srcset, sizes attributes
  • Next-gen formats: WebP, AVIF
  
  Runtime performance:
  • Minimize reflows/repaints; use transform/opacity for animations
  • Use requestAnimationFrame for animations
  • Virtualize long lists (react-window, react-virtual)
  • Web Workers for CPU-intensive tasks
  
  Caching:
  • Long-term caching of versioned static assets (immutable cache-control)
  • Service Worker for offline caching
  • HTTP cache headers properly configured

Q3: What is the difference between defer and async script loading?
───────────────────────────────────────────────────────────────────
Answer:
  Regular <script>:
    Downloads and executes immediately. Blocks HTML parsing.
    
  async:
    Downloads in parallel with HTML parsing.
    Executes ASAP when downloaded — pauses parsing.
    Order not guaranteed for multiple async scripts.
    Use for: independent scripts (analytics, ads).
    
  defer:
    Downloads in parallel with HTML parsing.
    Executes AFTER HTML is fully parsed, before DOMContentLoaded.
    Execution ORDER is preserved for multiple deferred scripts.
    Use for: scripts that depend on DOM or other deferred scripts.
    
  type="module":
    Deferred by default. Strict mode. Supports top-level await.
    async attribute overrides deferral.

SECTION 2: SERVICE WORKERS & PWA
────────────────────────────────────────────────────────────────────────────────

Q4: What is a Service Worker and what can it do?
─────────────────────────────────────────────────
Answer:
  A Service Worker is a JS file running in a separate worker thread (no DOM access)
  that acts as a programmable network proxy between the browser and server.
  
  Capabilities:
  • Intercept and handle fetch requests (return cached responses)
  • Implement offline functionality
  • Enable Push Notifications
  • Background Sync (defer actions until online)
  • Cache management (Cache API)
  • Communicate with pages via postMessage
  
  Requirements: HTTPS (except localhost), same origin.

Q5: Explain the Service Worker lifecycle.
───────────────────────────────────────────
Answer:
  1. Registration: navigator.serviceWorker.register('/sw.js')
  2. Download: browser downloads sw.js
  3. Install: install event fires. Cache app shell here.
     event.waitUntil(caches.open('v1').then(cache => cache.addAll(ASSETS)));
  4. Waiting: New SW installed but old SW still controls pages.
     Use self.skipWaiting() to bypass waiting.
  5. Activate: Old SW removed, new SW activates. Clean up old caches here.
     Use self.clients.claim() to immediately control open pages.
  6. Active: SW controls all in-scope pages. Handles fetch, push, sync events.
  
  Update detection: If sw.js file changes by even one byte, the new version
  goes through install → waiting → activate.

Q6: What is the difference between a Web Worker and a Service Worker?
──────────────────────────────────────────────────────────────────────
Answer:
  ┌─────────────────┬─────────────────────────────┬────────────────────────────────┐
  │ Feature         │ Web Worker                  │ Service Worker                 │
  ├─────────────────┼─────────────────────────────┼────────────────────────────────┤
  │ Purpose         │ CPU-intensive tasks         │ Network proxy, offline, push   │
  │ Scope           │ Single page                 │ All pages on same origin       │
  │ Persistence     │ Terminated when page closes │ Persists; can run in background│
  │ Network access  │ Can fetch; no interception  │ Intercepts all fetches         │
  │ DOM access      │ None                        │ None                           │
  │ Cache API       │ No (generally)              │ Yes                            │
  │ Push/Background │ No                          │ Yes                            │
  │ HTTPS required  │ No                          │ Yes (except localhost)         │
  └─────────────────┴─────────────────────────────┴────────────────────────────────┘

SECTION 3: BROWSER INTERNALS
────────────────────────────────────────────────────────────────────────────────

Q7: What is the Shadow DOM?
─────────────────────────────
Answer:
  Shadow DOM allows you to attach a hidden, encapsulated DOM tree to an element.
  
  const shadow = element.attachShadow({ mode: 'open' });
  shadow.innerHTML = '<style>p { color: red; }</style><p>Shadow content</p>';
  
  Key properties:
  • CSS encapsulation: styles inside shadow DOM don't leak out; external styles don't leak in.
  • DOM encapsulation: querySelector from outside won't find shadow DOM elements.
  • mode: 'open' → element.shadowRoot accessible from JS; 'closed' → null.
  
  Used by: custom elements, browser built-ins (<video>, <input type="range">).
  React/Vue use a Virtual DOM (in-memory representation), NOT Shadow DOM.

Q8: What is the Virtual DOM and how does React use it?
────────────────────────────────────────────────────────
Answer:
  Virtual DOM: A lightweight, in-memory representation of the real DOM.
  React maintains a VDOM tree. When state changes:
  
  1. React renders a new VDOM tree.
  2. Reconciliation: Diff new VDOM against previous VDOM.
  3. Calculate minimum set of real DOM changes (patch).
  4. Apply patch to real DOM (batched for performance).
  
  Key algorithms:
  • Heuristic diffing (O(n)): assumes same type elements = same structure.
  • key prop: helps React identify stable list items across renders.
  
  Why VDOM? Direct DOM manipulation is synchronous and can cause many reflows.
  VDOM batches changes and minimizes DOM operations.
  
  React 18 Concurrent Mode / Fiber: Interruptible rendering, priority scheduling,
  useTransition to defer non-urgent updates.

Q9: How does browser back/forward cache (bfcache) work?
─────────────────────────────────────────────────────────
Answer:
  bfcache stores an in-memory snapshot of the full page (DOM, JS heap, scroll
  position) when navigating away. Navigating back restores instantly from memory.
  
  Much faster than full page reload — no network, no JS re-execution.
  
  Pages are ineligible for bfcache if:
  • unload event listener is attached (use pagehide instead)
  • Open IndexedDB transactions
  • Pending fetch/XHR
  • window.opener references
  • Cache-Control: no-store header
  • Service Worker clients.claim() misuse
  
  Detect bfcache restore:
  window.addEventListener('pageshow', (e) => {
    if (e.persisted) { // page was restored from bfcache }
  });

SECTION 4: NETWORK AND HTTP
────────────────────────────────────────────────────────────────────────────────

Q10: What is the difference between HTTP/1.1, HTTP/2, and HTTP/3?
───────────────────────────────────────────────────────────────────
Answer:
  HTTP/1.1:
  • One request per TCP connection (without keep-alive)
  • Pipelining: send multiple requests without waiting; but HOL blocking
  • Headers are plain text (no compression)
  • Max ~6 parallel connections per domain (browser limit)
  
  HTTP/2:
  • Multiplexing: multiple requests over one TCP connection
  • Header compression (HPACK)
  • Server Push (send resources before client asks)
  • Binary framing instead of plain text
  • Still uses TCP → HOL blocking at TCP layer (packet loss blocks all streams)
  
  HTTP/3:
  • Built on QUIC (runs over UDP, not TCP)
  • Eliminates TCP HOL blocking (each stream independent)
  • Built-in TLS 1.3 (faster handshake)
  • Improved connection migration (phone switching networks)
  • 0-RTT connection resumption

Q11: What is WebSocket and when would you use it?
──────────────────────────────────────────────────
Answer:
  WebSocket is a persistent, full-duplex communication channel over a single
  TCP connection. Initiated via HTTP Upgrade handshake.
  
  const ws = new WebSocket('wss://example.com/ws');
  ws.onopen = () => ws.send('Hello');
  ws.onmessage = (e) => console.log(e.data);
  ws.onclose = () => console.log('disconnected');
  
  Use cases:
  • Real-time chat applications
  • Live collaboration (Google Docs-style)
  • Live sports scores, stock tickers
  • Multiplayer games
  • Live notifications
  
  vs Server-Sent Events (SSE):
  • SSE: one-way server→client; auto-reconnect; HTTP; text-only
  • WebSocket: full-duplex; manual reconnect; custom protocol; binary support
  
  vs HTTP polling:
  • Polling: client repeatedly asks for updates (wasteful)
  • WebSocket: server pushes updates instantly (efficient)

Q12: What is the difference between localStorage, sessionStorage, and cookies in terms of HTTP requests?
──────────────────────────────────────────────────────────────────────────────────────────────────────────
Answer:
  Cookies: automatically included in every HTTP request to the matching
  domain/path. Server can SET cookies via Set-Cookie header. Both client
  and server have access.
  
  localStorage/sessionStorage: NOT sent with HTTP requests automatically.
  Only accessible to client-side JavaScript. Server has no direct access.
  If needed in requests, must be manually added to headers:
  
  fetch('/api/data', {
    headers: { 'Authorization': 'Bearer ' + localStorage.getItem('token') }
  });
  
  This is why cookies are better for authentication — the browser handles
  sending them automatically without JS needing to access them.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Core Web Vitals: LCP (≤2.5s), INP (≤200ms), CLS (≤0.1)
  • Page optimization: critical CSS inline, defer JS, preload, CDN, compression
  • async: download parallel, execute ASAP; defer: execute after parse, ordered
  • Service Worker: network proxy, offline, push, background sync; HTTPS required
  • Shadow DOM: CSS/DOM encapsulation; Virtual DOM: React's diffing mechanism
  • bfcache: in-memory page snapshot for instant back/forward; avoid unload events
  • HTTP/2: multiplexing; HTTP/3: QUIC/UDP (no HOL blocking)
  • WebSocket: full-duplex persistent connection for real-time apps
