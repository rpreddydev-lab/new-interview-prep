Q1: What is the JavaScript Event Loop?
────────────────────────────────────────
Answer:
  JavaScript is single-threaded — one call stack, one thing at a time.
  The Event Loop is the mechanism that allows JS to handle async operations
  without blocking.
  
  Components:
  • Call Stack: LIFO; executes currently running code
  • Heap: unstructured memory for object allocation
  • Web APIs (browser) / C++ APIs (Node.js): handle timers, fetch, DOM events
  • Callback Queue (Macrotask Queue): callbacks from Web APIs wait here
  • Microtask Queue: Promise callbacks, queueMicrotask, MutationObserver
  
  Event Loop Algorithm:
  1. Execute synchronous code to completion (drain call stack)
  2. Drain ALL microtasks (Promise.then, queueMicrotask, async/await continuations)
     — including new microtasks added during this step
  3. Execute ONE macrotask (oldest setTimeout, setInterval, UI event, etc.)
  4. Drain ALL microtasks again
  5. Render update (if frame budget allows; ~16ms at 60fps)
  6. Go to step 3
  
  Key insight: Microtasks run IMMEDIATELY after current task completes,
  BEFORE the next macrotask. There is NO delay between current task and microtasks.

Q2: What is the output of the following code?
──────────────────────────────────────────────
  console.log('1');
  
  setTimeout(() => console.log('2'), 0);
  
  Promise.resolve().then(() => console.log('3'));
  
  console.log('4');

Answer:
  Output: 1, 4, 3, 2
  
  Trace:
  1. console.log('1') → prints "1" (sync)
  2. setTimeout(cb, 0) → schedules cb in macrotask queue
  3. Promise.resolve().then(cb) → schedules cb in microtask queue
  4. console.log('4') → prints "4" (sync)
  5. Sync code done. Drain microtasks → prints "3"
  6. Execute one macrotask (setTimeout) → prints "2"

Q3: What is the output of this more complex example?
─────────────────────────────────────────────────────
  console.log('start');
  
  setTimeout(() => console.log('timeout 1'), 0);
  
  Promise.resolve()
    .then(() => {
      console.log('promise 1');
      setTimeout(() => console.log('timeout 2'), 0);
    })
    .then(() => console.log('promise 2'));
  
  console.log('end');

Answer:
  Output: start, end, promise 1, promise 2, timeout 1, timeout 2
  
  Trace:
  1. "start" (sync)
  2. setTimeout('timeout 1') → macrotask queue: [T1]
  3. Promise.resolve().then(...) → microtask queue: [M1]
  4. "end" (sync)
  5. Drain microtasks:
     M1 runs: prints "promise 1", schedules T2 in macrotask queue: [T1, T2]
     .then() → queues M2 in microtask queue: [M2]
     M2 runs: prints "promise 2"
  6. Microtask queue empty. Execute T1 → "timeout 1"
  7. Drain microtasks (empty). Execute T2 → "timeout 2"

Q4: What is the output with async/await?
─────────────────────────────────────────
  async function main() {
    console.log('A');
    await Promise.resolve();
    console.log('B');
  }
  
  console.log('C');
  main();
  console.log('D');

Answer:
  Output: C, A, D, B
  
  Trace:
  1. "C" (sync)
  2. main() called → enters async function
  3. "A" (sync, inside main)
  4. await Promise.resolve() → suspends main; schedules continuation as microtask
  5. Back to call site → "D" (sync)
  6. Sync done. Drain microtasks → main resumes → "B"
  
  Key: await suspends the async function and releases control back to the caller.
  The code after await runs as a microtask continuation.

Q5: What is the difference between Promise.all, Promise.allSettled, Promise.race, and Promise.any?
────────────────────────────────────────────────────────────────────────────────────────────────────
Answer:
  Promise.all([p1, p2, p3]):
    Resolves when ALL promises resolve. Rejects immediately if ANY rejects.
    Result: array of resolved values (same order as input).
    Use case: parallel independent operations; fail-fast behavior needed.
    
  Promise.allSettled([p1, p2, p3]):
    Waits for ALL promises to settle (resolve OR reject). NEVER rejects.
    Result: array of {status: 'fulfilled', value: v} or {status: 'rejected', reason: r}
    Use case: run multiple ops; collect all results even if some fail.
    
  Promise.race([p1, p2, p3]):
    Settles with the FIRST promise to settle (resolve or reject).
    Use case: timeout pattern; use first available mirror.
    
    const withTimeout = (promise, ms) =>
      Promise.race([promise, new Promise((_, rej) => setTimeout(() => rej(new Error('Timeout')), ms))]);
    
  Promise.any([p1, p2, p3]):
    Resolves with FIRST successful promise. Rejects only if ALL reject (AggregateError).
    Use case: try multiple sources; use first that works.
    
  ┌──────────────────┬───────────────────────────┬──────────────────────────────┐
  │ Method           │ Resolves When             │ Rejects When                 │
  ├──────────────────┼───────────────────────────┼──────────────────────────────┤
  │ Promise.all      │ All resolve               │ Any one rejects              │
  │ Promise.allSettled│ All settle (any outcome) │ Never rejects                │
  │ Promise.race     │ First settles             │ First settles with rejection │
  │ Promise.any      │ First resolves            │ All reject (AggregateError)  │
  └──────────────────┴───────────────────────────┴──────────────────────────────┘

Q6: What are the common mistakes with async/await?
───────────────────────────────────────────────────
Answer:
  1. Missing await — creates unhandled promise:
     async function bad() {
       const result = fetchData(); // forgot await! result is a Promise, not data
     }
  
  2. Sequential when it should be parallel:
     // SLOW: each awaits the previous
     const a = await fetchA();
     const b = await fetchB();
     
     // FAST: parallel
     const [a, b] = await Promise.all([fetchA(), fetchB()]);
  
  3. Swallowing errors (empty catch):
     try {
       await riskyOp();
     } catch (e) {} // silently swallows error — bad!
  
  4. Unhandled promise rejection:
     async function main() { throw new Error('oops'); }
     main(); // No .catch() or try/catch → unhandledRejection
  
  5. Returning a promise inside async (unnecessary async):
     // Redundant — async wraps return in Promise already
     async function getUser(id) {
       return await fetchUser(id); // await here is unnecessary
     }

Q7: How do you handle errors in Promise chains?
────────────────────────────────────────────────
Answer:
  Method 1: .catch() at the end of chain
    fetchData()
      .then(processData)
      .then(saveData)
      .catch(err => console.error('Something failed:', err));
    
    // .catch() handles ANY rejection in the chain above it
  
  Method 2: Second argument to .then()
    fetchData()
      .then(
        data => processData(data),
        err => handleFetchError(err) // only catches fetchData errors
      );
    
    // Does NOT catch errors thrown by processData
  
  Method 3: try/catch with async/await (recommended)
    async function run() {
      try {
        const data = await fetchData();
        const processed = await processData(data);
        await saveData(processed);
      } catch (err) {
        console.error(err); // catches any error in the try block
      } finally {
        cleanup(); // always runs
      }
    }
  
  Method 4: Per-operation error handling
    const data = await fetchData().catch(err => { handleErr(err); return null; });
    if (!data) return;

SECTION 3: CLOSURES & SCOPE
────────────────────────────────────────────────────────────────────────────────

Q8: What is a closure and what are common use cases?
──────────────────────────────────────────────────────
Answer:
  A closure is a function that "remembers" its lexical scope even when executed
  outside of that scope.
  
  function makeCounter(initial = 0) {
    let count = initial; // captured by closure
    return {
      increment: () => ++count,
      decrement: () => --count,
      value: () => count
    };
  }
  const counter = makeCounter(10);
  counter.increment(); // 11
  counter.increment(); // 12
  counter.value();     // 12
  
  Common use cases:
  • Data encapsulation / private variables (module pattern)
  • Event handlers that remember context
  • Function factories / partial application
  • Memoization
  • setTimeout/callback with captured state
  
  Classic closure trap:
  for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 100); // prints 3, 3, 3 — all share same `i`
  }
  
  Fixes:
  // Fix 1: let (block scope)
  for (let i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 100); // 0, 1, 2
  }
  
  // Fix 2: IIFE to create new scope
  for (var i = 0; i < 3; i++) {
    ((j) => setTimeout(() => console.log(j), 100))(i); // 0, 1, 2
  }

Q9: Explain hoisting and the Temporal Dead Zone (TDZ).
────────────────────────────────────────────────────────
Answer:
  Hoisting: JS moves declarations (not initializations) to the top of their scope
  during compilation phase.
  
  var hoisting:
    console.log(x); // undefined (not ReferenceError — var is hoisted)
    var x = 5;
    // Compiled as: var x; console.log(x); x = 5;
  
  function hoisting:
    greet(); // "Hello" — function declarations fully hoisted
    function greet() { console.log("Hello"); }
  
  let/const hoisting:
    console.log(y); // ReferenceError: Cannot access 'y' before initialization
    let y = 5;
    // let/const ARE hoisted but NOT initialized — TDZ from binding to declaration
  
  TDZ (Temporal Dead Zone):
    The period between entering the scope and the let/const declaration line.
    Accessing the variable in TDZ throws ReferenceError.
    
    {
      // TDZ starts for `z`
      typeof z; // ReferenceError (unlike typeof var which returns 'undefined')
      let z = 5; // TDZ ends
    }
  
  Function expressions (var):
    greet(); // TypeError: greet is not a function
    var greet = function() { console.log("Hello"); }
    // var greet is hoisted (undefined), but assignment happens later

Q10: What is a memory leak and how do you detect/prevent it?
─────────────────────────────────────────────────────────────
Answer:
  A memory leak occurs when memory that is no longer needed is not released,
  causing the heap to grow over time → eventual slowdown or crash.
  
  Common leak causes:
  
  1. Forgotten event listeners:
     // Leaks — listener keeps reference to element and callback scope
     window.addEventListener('resize', heavyCallback);
     // Fix: removeEventListener when component unmounts/is no longer needed
  
  2. Closures retaining large data:
     function process() {
       const largeData = new Array(10000).fill('x');
       return () => largeData[0]; // closure keeps ALL of largeData alive
     }
  
  3. Detached DOM nodes (most common):
     let div = document.getElementById('myDiv');
     document.body.removeChild(div); // removed from DOM
     // div variable still references it — GC cannot collect
     div = null; // Fix: clear the reference
  
  4. Timers not cleared:
     const interval = setInterval(() => {}, 1000);
     // Fix: clearInterval(interval) when done
  
  5. Global variables accidentally:
     function foo() { bar = 'leaked'; } // bar becomes window.bar
  
  Detection in Chrome DevTools:
  • Memory tab → Take Heap Snapshot
  • Compare two snapshots → look for nodes added/retained
  • Allocation Timeline: allocations over time, identify growing patterns
  • Performance tab → Monitor JS Heap in real-time
  
  Prevention:
  • Use WeakMap/WeakSet for object keyed data (allows GC of key)
  • Clean up in useEffect return / componentWillUnmount
  • Use AbortController to cancel fetch on component unmount
  • Clear timers in cleanup functions

Q11: What is debounce vs throttle and when to use each?
────────────────────────────────────────────────────────
Answer:
  Both limit how often a function can be called.
  
  Debounce:
    Delays execution until the function stops being called for N ms.
    Only the LAST call in a burst runs (after quiet period).
    
    function debounce(fn, ms) {
      let timer;
      return function(...args) {
        clearTimeout(timer);
        timer = setTimeout(() => fn.apply(this, args), ms);
      };
    }
    
    Use cases: search input (wait for user to stop typing), form validation,
    window resize handler (run once after resize ends).
  
  Throttle:
    Ensures function runs at most once per N ms, even during continuous calls.
    FIRST call runs immediately; subsequent calls suppressed until delay passes.
    
    function throttle(fn, ms) {
      let lastCall = 0;
      return function(...args) {
        const now = Date.now();
        if (now - lastCall >= ms) {
          lastCall = now;
          return fn.apply(this, args);
        }
      };
    }
    
    Use cases: scroll event handler, mousemove tracking, game input,
    API rate limiting.
  
  Key difference:
  • Debounce: waits for silence, then runs once
  • Throttle: runs at regular intervals during continuous activity

Q12: What is the output of microtask vs macrotask ordering?
─────────────────────────────────────────────────────────────
Answer:
  Promise.resolve().then(() => console.log('microtask 1'));
  setTimeout(() => console.log('macrotask 1'), 0);
  Promise.resolve().then(() => {
    console.log('microtask 2');
    Promise.resolve().then(() => console.log('microtask 3'));
  });
  setTimeout(() => console.log('macrotask 2'), 0);
  
  Output: microtask 1, microtask 2, microtask 3, macrotask 1, macrotask 2
  
  Explanation:
  • All sync code runs first
  • ALL microtasks drain (including newly added ones) before first macrotask
  • microtask 3 is queued during microtask 2, but runs before any macrotask
  • macrotasks run one at a time, with microtask drain after each

Q13: How does queueMicrotask work and when to use it?
───────────────────────────────────────────────────────
Answer:
  queueMicrotask(callback) schedules a function to run in the microtask queue,
  AFTER current synchronous code and BEFORE next macrotask/render.
  
  Equivalent to: Promise.resolve().then(callback) — but without creating a Promise object.
  
  console.log('start');
  queueMicrotask(() => console.log('microtask'));
  console.log('end');
  // Output: start, end, microtask
  
  Use cases:
  • Schedule work that needs to run ASAP but after current code
  • Batch DOM updates before next render
  • Library code that needs to defer without creating Promise overhead
  
  Process.nextTick (Node.js):
  Even higher priority than microtask queue.
  nextTick queue drains BEFORE the microtask queue (Promise.then).
  
  // Node.js order:
  setImmediate(() => console.log('setImmediate'));      // macrotask
  setTimeout(() => console.log('setTimeout'), 0);       // macrotask
  Promise.resolve().then(() => console.log('Promise')); // microtask
  process.nextTick(() => console.log('nextTick'));       // next tick queue
  // Output: nextTick, Promise, setTimeout, setImmediate

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Event loop: sync → microtasks (ALL) → one macrotask → microtasks (ALL) → render
  • Microtasks: Promise.then, queueMicrotask, MutationObserver, async/await continuations
  • Macrotasks: setTimeout, setInterval, I/O, UI events, script loading
  • async/await: await suspends function, resumes as microtask continuation
  • Promise.all (fail-fast) vs allSettled (all results) vs race (first) vs any (first success)
  • Closures capture by reference, not value — use let or IIFE in loops
  • var hoisted + initialized undefined; let/const hoisted + TDZ (ReferenceError)
  • Debounce: wait for silence; Throttle: cap frequency during activity
  • Memory leaks: detached DOM, forgotten listeners, closures, uncleared timers
