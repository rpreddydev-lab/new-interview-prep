================================================================================
  CLIENT-SERVER MODEL — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS THE CLIENT-SERVER MODEL?
────────────────────────────────────────────────────────────────────────────────

The client-server model is a distributed computing architecture where:
  • CLIENT — makes requests (browser, mobile app, CLI tool)
  • SERVER — listens for requests and returns responses

  Client                               Server
    │                                    │
    │── Request (GET /page HTTP/1.1) ───>│
    │                                    │ (processes request)
    │<── Response (200 OK + HTML) ──────│
    │                                    │

Key characteristics:
  • Asymmetric: clients initiate, servers respond
  • Stateless (HTTP): each request stands alone
  • Scalable: one server can serve millions of clients

────────────────────────────────────────────────────────────────────────────────
2. TYPES OF CLIENTS
────────────────────────────────────────────────────────────────────────────────

  Thin Client:
    - Minimal local processing; relies heavily on server
    - Example: web browser (renders server-sent HTML/CSS/JS)

  Thick/Fat Client:
    - Significant local processing
    - Example: native desktop app, mobile game

  Hybrid:
    - Single Page Applications (SPAs): initial load from server,
      subsequent rendering on client

────────────────────────────────────────────────────────────────────────────────
3. SERVER TYPES
────────────────────────────────────────────────────────────────────────────────

  Web Server:
    - Serves static files (HTML, CSS, JS, images)
    - Examples: Nginx, Apache, Caddy
    - Handles HTTP/HTTPS protocol

  Application Server:
    - Executes business logic, dynamic content generation
    - Examples: Node.js, Django, Spring Boot, Rails
    - Often sits behind a web server (reverse proxy)

  Database Server:
    - Stores and queries data
    - Examples: PostgreSQL, MySQL, MongoDB, Redis

  File Server:
    - Stores and serves files
    - Examples: NFS, S3-compatible servers

  Mail Server:
    - Handles email (SMTP outgoing, IMAP/POP3 incoming)

  DNS Server:
    - Resolves domain names to IP addresses

  Proxy Server:
    - Intermediary between client and server

  CDN Edge Server:
    - Caches content geographically close to clients

────────────────────────────────────────────────────────────────────────────────
4. REQUEST-RESPONSE LIFECYCLE
────────────────────────────────────────────────────────────────────────────────

  Complete lifecycle of a web request:

  ┌─────────────────────────────────────────────────────────────┐
  │ 1. User action (click link / type URL / form submit)        │
  │ 2. Browser parses URL                                       │
  │ 3. DNS resolution (name → IP)                              │
  │ 4. TCP connection (3-way handshake)                        │
  │ 5. TLS handshake (for HTTPS)                               │
  │ 6. HTTP Request sent                                        │
  │    - Method, URL, HTTP version                             │
  │    - Headers (Host, Accept, Cookie, Authorization, etc.)   │
  │    - Body (for POST/PUT/PATCH)                             │
  │ 7. Server processes request                                 │
  │    - Route matching (URL routing)                          │
  │    - Middleware execution (auth, logging, rate limiting)   │
  │    - Business logic                                         │
  │    - Database queries                                       │
  │ 8. HTTP Response returned                                   │
  │    - Status line (HTTP/1.1 200 OK)                         │
  │    - Response headers                                       │
  │    - Response body (HTML, JSON, file, etc.)                │
  │ 9. Browser renders response                                 │
  │ 10. Connection reuse or close                              │
  └─────────────────────────────────────────────────────────────┘

────────────────────────────────────────────────────────────────────────────────
5. PROXY SERVERS
────────────────────────────────────────────────────────────────────────────────

  Forward Proxy:
    - Sits between CLIENT and internet
    - Client → Forward Proxy → Internet
    - Hides client's IP from server
    - Used for: content filtering, caching, anonymity (VPN-like)
    - Example: Corporate proxy, Squid, VPN

  Reverse Proxy:
    - Sits between internet and SERVERS
    - Client → Reverse Proxy → Backend Servers
    - Hides server infrastructure from client
    - Used for: load balancing, SSL termination, caching, WAF
    - Examples: Nginx, HAProxy, Cloudflare, AWS ALB

  Key distinction:
    Forward proxy: client-side (client knows about it)
    Reverse proxy: server-side (client doesn't know about it)

────────────────────────────────────────────────────────────────────────────────
6. LOAD BALANCING
────────────────────────────────────────────────────────────────────────────────

  Distributes traffic across multiple servers.

  Algorithms:
    Round Robin     → Requests distributed cyclically
    Weighted RR     → More traffic to more powerful servers
    Least Conn.     → Route to server with fewest active connections
    IP Hash         → Same client IP always → same server (session affinity)
    Random          → Random selection

  Layer 4 vs Layer 7 Load Balancing:
    L4 (Transport): Routes based on IP/TCP without inspecting content
      - Fast, simple, no HTTP knowledge
    L7 (Application): Routes based on HTTP content (URL, headers, cookies)
      - Can route /api → API servers, /static → CDN
      - More powerful but higher overhead

  Session Persistence (Sticky Sessions):
    - Same client always routes to same server
    - Needed when server-side session state isn't shared
    - Downside: poor load distribution when one user is very active

────────────────────────────────────────────────────────────────────────────────
7. COMMUNICATION PATTERNS
────────────────────────────────────────────────────────────────────────────────

  7.1 Request-Response (Synchronous)
    - Client waits for server response
    - HTTP REST, GraphQL queries

  7.2 Polling
    - Client repeatedly asks server: "Any new data?"
    - Simple but inefficient (many unnecessary requests)
    - Short polling: interval-based, e.g., every 5 seconds
    - Long polling: server holds request open until data available,
      then client immediately makes another request

  7.3 Server-Sent Events (SSE)
    - Server pushes updates to client over persistent HTTP connection
    - One-directional: server → client only
    - Client uses EventSource API
    - Auto-reconnects, works over HTTP/1.1
    - Use case: live feeds, dashboards, notifications

  7.4 WebSockets
    - Full-duplex, persistent, bidirectional channel
    - Upgraded from HTTP using Upgrade header
    - Very low overhead (2-byte header after handshake)
    - Use case: chat, gaming, real-time collaboration, trading
    - Not auto-reconnecting (must implement manually)

  7.5 gRPC
    - High-performance RPC framework using HTTP/2
    - Protocol Buffers (binary serialization)
    - Bidirectional streaming
    - Strong typing via .proto files
    - Use case: microservices, internal APIs

  7.6 GraphQL Subscriptions
    - Real-time over WebSockets
    - Client subscribes to specific data changes

  Comparison:
    ┌──────────────┬──────────────┬────────────┬─────────────────┐
    │ Pattern      │ Direction    │ Protocol   │ Use Case        │
    ├──────────────┼──────────────┼────────────┼─────────────────┤
    │ HTTP REST    │ C → S (sync) │ HTTP       │ Standard APIs   │
    │ Long Polling │ C → S → C   │ HTTP       │ Simple updates  │
    │ SSE          │ S → C        │ HTTP       │ Live feeds      │
    │ WebSocket    │ Bidirectional│ WS/WSS     │ Chat, gaming    │
    │ gRPC         │ Bidirectional│ HTTP/2     │ Microservices   │
    └──────────────┴──────────────┴────────────┴─────────────────┘

────────────────────────────────────────────────────────────────────────────────
8. REST vs GraphQL vs gRPC
────────────────────────────────────────────────────────────────────────────────

  REST (Representational State Transfer):
    - Resources identified by URLs
    - HTTP methods (GET, POST, PUT, DELETE) define operations
    - Stateless, simple, widely supported
    - Drawbacks: over-fetching / under-fetching

  GraphQL:
    - Single endpoint (/graphql)
    - Client specifies exactly what data it needs (no over-fetching)
    - Schema-typed (SDL — Schema Definition Language)
    - Queries, Mutations, Subscriptions
    - Drawbacks: complex caching, N+1 queries, learning curve

  gRPC:
    - Uses Protocol Buffers (binary, compact, strongly typed)
    - HTTP/2 transport (multiplexing, streaming)
    - Code generation from .proto files
    - Excellent for inter-service communication
    - Drawbacks: not browser-native (needs grpc-web)

9. CACHING IN CLIENT-SERVER
────────────────────────────────────────────────────────────────────────────────

  Browser Cache:
    - Stores HTTP responses locally
    - Controlled by: Cache-Control, Expires, ETag, Last-Modified

  HTTP Cache Headers:
    Cache-Control: no-store          → Never cache
    Cache-Control: no-cache          → Cache but validate with server
    Cache-Control: max-age=3600      → Cache for 1 hour
    Cache-Control: public            → CDN can cache
    Cache-Control: private           → Only browser can cache
    Cache-Control: immutable         → Will never change (use with hashed filenames)

  Conditional Requests:
    ETag:          Server sends fingerprint of resource
    If-None-Match: Client sends ETag back; server returns 304 if unchanged

    Last-Modified:     Server sends modification timestamp
    If-Modified-Since: Client sends timestamp; server returns 304 if unchanged

  Cache Hierarchy:
    Browser memory cache → Browser disk cache → Service Worker cache
    → CDN edge cache → Reverse proxy cache → Server-side cache (Redis)
    → Database query cache → Database

10. SCALABILITY CONCEPTS
────────────────────────────────────────────────────────────────────────────────

  Vertical Scaling (Scale Up):
    - Add more CPU/RAM to existing server
    - Simple but has hardware limits, single point of failure

  Horizontal Scaling (Scale Out):
    - Add more server instances
    - Requires load balancer, session management, distributed state
    - Theoretically unlimited

  Microservices vs Monolith:
    Monolith:     All functionality in one deployable unit
                  Simple to develop initially, hard to scale parts independently
    Microservices: Each service independently deployed and scaled
                   Complex orchestration, service mesh, more resilient

  Stateless Servers:
    - No session data stored on server
    - Any instance can handle any request
    - State stored in external store (DB, Redis, JWT)
    - Required for proper horizontal scaling

11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the client-server model?
A: An architecture where clients (browsers, apps) initiate requests and
   servers respond. Asymmetric: clients request, servers respond. Enables
   centralized resources accessible to many clients.

Q: What is the difference between a forward proxy and a reverse proxy?
A: Forward proxy sits on the client side — clients use it to access the
   internet (hides client IP). Reverse proxy sits on the server side —
   clients talk to it without knowing about backend servers (load
   balancing, SSL termination, caching).

Q: What is the difference between polling and WebSockets?
A: Polling: client repeatedly sends HTTP requests to check for new data
   (inefficient, latency depends on interval).
   WebSockets: persistent bidirectional connection, server pushes data
   immediately without client requesting. Much more efficient for
   real-time applications.

Q: When would you use Server-Sent Events vs WebSockets?
A: SSE: one-directional server → client, simpler, auto-reconnects,
   works well for notifications/feeds. Built on HTTP.
   WebSockets: bidirectional, needed for chat/gaming where client also
   sends frequent data to server. More complex setup.

Q: What is load balancing and why is it needed?
A: Load balancing distributes incoming traffic across multiple servers
   to prevent overload, improve availability, and enable horizontal
   scaling. Algorithms: round-robin, least connections, IP hash.

Q: What is the difference between L4 and L7 load balancing?
A: L4 routes based on TCP/IP headers (IP, port) — fast, no HTTP
   inspection. L7 routes based on HTTP content (URL path, headers,
   cookies) — more flexible routing decisions but higher overhead.

Q: How does HTTP caching work?
A: Server sends Cache-Control headers specifying cache duration and
   visibility. Browsers and CDNs cache responses. ETags and
   Last-Modified allow conditional requests — server returns 304 Not
   Modified if resource unchanged, saving bandwidth.

Q: What is REST and what makes an API RESTful?
A: REST is an architectural style using HTTP. RESTful APIs: stateless,
   use HTTP methods (GET/POST/PUT/DELETE) semantically, identify
   resources via URLs, use standard status codes, support HATEOAS
   (optional). Client-server separation, cacheable responses.

Q: Why are stateless servers important for scalability?
A: Stateless servers don't store session data locally, so any server
   instance can handle any request. This allows horizontal scaling —
   just add more instances behind a load balancer. State is stored
   externally (DB, Redis, JWT tokens).

Q: What is the difference between horizontal and vertical scaling?
A: Vertical: add more resources (CPU/RAM) to one server. Simple but
   limited. Horizontal: add more server instances, requires load
   balancer, stateless design. More complex but theoretically unlimited.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Client-server: asymmetric, client initiates, server responds
  • Forward proxy: hides client; Reverse proxy: hides server
  • Polling vs SSE (server-push, 1-way) vs WebSocket (bidirectional)
  • Load balancing: L4 (TCP/IP) vs L7 (HTTP content-aware)
  • Stateless servers required for proper horizontal scaling
  • HTTP caching: Cache-Control, ETags, 304 Not Modified
