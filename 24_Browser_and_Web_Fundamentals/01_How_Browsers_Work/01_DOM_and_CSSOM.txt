  DOM AND CSSOM — Complete Interview Reference

────────────────────────────────────────────────────────────────────────────────
1. THE DOM (Document Object Model)
────────────────────────────────────────────────────────────────────────────────

  The DOM is:
    • A language-neutral, platform-neutral API (spec by WHATWG/W3C)
    • An in-memory tree representation of an HTML/XML document
    • The browser's internal model that JavaScript can manipulate
    • NOT the HTML source — it's the parsed, live result

  Key principle: HTML source → Parsing → DOM Tree

  Why DOM ≠ HTML:
    1. Browser auto-corrects invalid HTML:
       <table><tr><p>text</p></tr> → DOM adds <tbody>, moves <p> out
    2. JavaScript can modify DOM after load
    3. document.body.innerHTML gives DOM serialization, not original HTML

────────────────────────────────────────────────────────────────────────────────
2. DOM TREE STRUCTURE
────────────────────────────────────────────────────────────────────────────────

  Node Types (nodeType property):
    1  → Element node       (e.g., <div>, <p>, <span>)
    2  → Attribute node     (deprecated in modern DOM)
    3  → Text node          ("Hello World" text inside elements)
    4  → CDATASection
    7  → ProcessingInstruction
    8  → Comment node       (<!-- comment -->)
    9  → Document node      (root: document)
    10 → DocumentType       (<!DOCTYPE html>)
    11 → DocumentFragment

  DOM Tree Example:
    HTML:
      <html>
        <body>
          <h1>Title</h1>
          <p class="intro">Hello</p>
        </body>
      </html>

    DOM Tree:
      Document
        └── html (Element)
              ├── head (Element)
              └── body (Element)
                    ├── h1 (Element)
                    │     └── "Title" (Text)
                    └── p.intro (Element)
                          └── "Hello" (Text)

────────────────────────────────────────────────────────────────────────────────
3. HTML PARSING → DOM CONSTRUCTION
────────────────────────────────────────────────────────────────────────────────

  Parser Steps:
    1. Bytes → Characters (using charset from <meta> or Content-Type)
    2. Characters → Tokens (Tokenization)
       - DOCTYPE token
       - Start tag token: <div class="foo">
       - End tag token: </div>
       - Comment token
       - Character token
    3. Tokens → Nodes
    4. Nodes → DOM Tree (tree construction algorithm)

  Tokenizer States:
    Data state → Tag open state → Tag name state → ...
    (Defined precisely in the HTML spec — case-insensitive for tags)

  Parser Error Recovery:
    HTML parser is forgiving — never throws errors
    Examples of auto-correction:
      • Missing <html>/<head>/<body> → inserted implicitly
      • Overlapping tags <b><i>text</b></i> → restructured
      • <table><tr> without <tbody> → <tbody> inserted
      • Tags in wrong context → moved to correct position

  Incremental Parsing:
    - Browser starts parsing HTML as first bytes arrive
    - Doesn't wait for entire document to download
    - Creates DOM nodes progressively
    - Critical for perceived performance

  Parser Blocking Resources:
    JavaScript:
      - <script> without async/defer BLOCKS HTML parsing
      - Browser must download + execute JS before continuing
      - Why? JS can call document.write() which modifies HTML stream
      - Speculative/Preload Scanner: browser peeks ahead in HTML to
        discover and preload resources even while parser is blocked

    CSS:
      - Does NOT block HTML parsing (directly)
      - DOES block script execution (JS needs to see computed styles)
      - CSS → CSSOM needed before JS runs, so effectively blocks JS
        which can block rendering

────────────────────────────────────────────────────────────────────────────────
4. SCRIPT LOADING BEHAVIORS
────────────────────────────────────────────────────────────────────────────────

  <script src="app.js">
    - Blocks HTML parsing while downloading AND executing
    - Executes in order

  <script async src="app.js">
    - Downloads in parallel (non-blocking)
    - Executes AS SOON as downloaded (may interrupt parsing)
    - Order NOT guaranteed
    - Best for: independent third-party scripts (analytics, ads)

  <script defer src="app.js">
    - Downloads in parallel (non-blocking)
    - Executes AFTER HTML parsing complete, BEFORE DOMContentLoaded
    - Order IS guaranteed
    - Best for: app scripts that need the full DOM

  <script type="module">
    - Deferred by default (like defer)
    - Always strict mode
    - Own scope (no global leakage)
    - Supports import/export

  Visual Timeline:
    Regular:  HTML──[blocking]──────────JS Execute──HTML continue
    async:    HTML─────────────────────HTML|JS Execute (whenever)
    defer:    HTML─────────────────────HTML complete──JS Execute

5. THE CSSOM (CSS Object Model)
────────────────────────────────────────────────────────────────────────────────

  What is CSSOM?
    - The CSS equivalent of the DOM
    - In-memory representation of all CSS rules
    - Used together with DOM to calculate final styles

  CSSOM Construction:
    CSS Bytes → Characters → Tokens → CSSOM Tree

  CSSOM Tree Example:
    CSS:
      body { font-size: 16px; }
      p { color: red; }
      .hero p { font-size: 24px; }

    CSSOM:
      body
        font-size: 16px
        └── p
              color: red
              font-size: 16px (inherited)
              └── .hero p
                    font-size: 24px (overrides inherited)

  CSSOM Key Characteristics:
    • Render-blocking: Browser must fully construct CSSOM before rendering
      (partial styles cause flicker / FOUC)
    • Reason: one CSS rule can affect many elements — need complete picture
    • CSS in <head> → downloaded and parsed as fast as possible

  CSSOM Access in JavaScript:
    document.styleSheets          → CSSStyleSheetList
    styleSheet.cssRules           → list of CSSRule objects
    element.style                 → inline styles (CSSStyleDeclaration)
    window.getComputedStyle(el)   → FINAL computed style (after all CSS)
    element.style.color = 'red'   → set inline style (triggers reflow if visual)

────────────────────────────────────────────────────────────────────────────────
6. RENDER TREE
────────────────────────────────────────────────────────────────────────────────

  The Render Tree = DOM + CSSOM combined:
    - Only VISIBLE nodes are in the render tree
    - Nodes with display:none are excluded
    - Nodes with visibility:hidden are INCLUDED (take up space, just invisible)
    - Pseudo-elements (::before, ::after) ARE included

  Render Tree vs DOM:
    DOM:         All nodes (including <head>, hidden elements, comments)
    Render Tree: Only visual elements with computed styles

  Creating Render Tree:
    1. Start from DOM root, traverse visible nodes
    2. For each, find matching CSSOM rules
    3. Apply cascaded styles (specificity, inheritance, cascade order)
    4. Compute final values (relative → absolute: em→px, %→px)

  RenderObject (in Blink):
    - Each visual node in DOM → corresponds to a LayoutObject
    - Text runs, images, blocks, inlines, flex containers, etc.

7. DOM APIs — DEEP DIVE
────────────────────────────────────────────────────────────────────────────────

  Querying:
    document.getElementById('id')          → Element (fastest — O(1) hash)
    document.querySelector('.class')       → First matching Element
    document.querySelectorAll('div.card')  → NodeList (static snapshot)
    document.getElementsByClassName('c')  → HTMLCollection (live)
    document.getElementsByTagName('div')  → HTMLCollection (live)

  Live vs Static Collections:
    HTMLCollection (getElementsBy*): LIVE — auto-updates when DOM changes
    NodeList (querySelectorAll): STATIC — snapshot at time of query
    NodeList (childNodes): LIVE — updates with DOM changes

  Traversal:
    element.parentNode / parentElement
    element.children (HTMLCollection — elements only)
    element.childNodes (NodeList — all nodes including text/comments)
    element.firstChild / lastChild (text nodes too)
    element.firstElementChild / lastElementChild (elements only)
    element.nextSibling / previousSibling
    element.nextElementSibling / previousElementSibling

  Creating/Modifying:
    document.createElement('div')
    document.createTextNode('Hello')
    document.createDocumentFragment()   ← very important for performance
    element.appendChild(child)
    element.insertBefore(newNode, refNode)
    element.removeChild(child)
    element.replaceChild(newNode, oldNode)
    element.cloneNode(deep)             ← deep=true copies children too

  Modern DOM Methods:
    element.append(...nodes)            ← append multiple nodes or strings
    element.prepend(...nodes)
    element.before(...nodes)
    element.after(...nodes)
    element.remove()                    ← remove self (no parent ref needed)
    element.replaceWith(...nodes)

  innerHTML vs textContent vs innerText:
    innerHTML:    Get/set HTML string (parses HTML — XSS risk if user input!)
    textContent:  Get/set ALL text content (including hidden elements)
                  Does NOT interpret HTML — safe for user input
    innerText:    Get only VISIBLE text (respects CSS visibility)
                  Triggers reflow (reads computed styles)
                  Use textContent when possible (faster)

  Attributes:
    element.getAttribute('href')
    element.setAttribute('data-id', '42')
    element.removeAttribute('disabled')
    element.hasAttribute('readonly')
    element.dataset.id                   ← access data-id attribute
    element.classList.add/remove/toggle/contains/replace

8. DOCUMENT FRAGMENT
────────────────────────────────────────────────────────────────────────────────

  Why use DocumentFragment:
    - Appending nodes to DOM one-by-one causes multiple reflows
    - DocumentFragment is an off-DOM container
    - Build your node tree in the fragment
    - Append fragment to DOM once → only ONE reflow

  Example:
    const fragment = document.createDocumentFragment();
    for (let i = 0; i < 1000; i++) {
      const li = document.createElement('li');
      li.textContent = `Item ${i}`;
      fragment.appendChild(li);  // no reflow yet
    }
    document.getElementById('list').appendChild(fragment); // ONE reflow

9. SHADOW DOM
────────────────────────────────────────────────────────────────────────────────

  Shadow DOM:
    - Encapsulated DOM subtree attached to an element
    - Styles inside shadow DOM don't leak out
    - Styles from outside don't leak in (by default)
    - Part of Web Components standard

  Terminology:
    Shadow Host:  element that hosts a shadow tree
    Shadow Root:  root of the shadow tree
    Shadow Tree:  encapsulated DOM subtree
    Slot:         <slot> — portal for "light DOM" content

  Modes:
    element.attachShadow({ mode: 'open' })   → accessible via element.shadowRoot
    element.attachShadow({ mode: 'closed' }) → NOT accessible from outside

  Use cases: Custom UI components (like <video controls>, <input type="range">)

────────────────────────────────────────────────────────────────────────────────
10. VIRTUAL DOM
────────────────────────────────────────────────────────────────────────────────

  Problem with direct DOM manipulation:
    - DOM operations are slow (cause reflow/repaint)
    - Naively updating everything on state change is expensive

  Virtual DOM (React's approach):
    - Keep a lightweight JS representation of the DOM in memory
    - On state change: create new Virtual DOM tree
    - Diff old vs new virtual DOM (reconciliation algorithm)
    - Calculate minimal set of real DOM changes
    - Batch apply changes to real DOM

  React Reconciliation:
    - Diffing algorithm: O(n) with heuristics
    - Keys help identify list items efficiently
    - Fiber architecture: work can be interrupted/resumed

  Alternatives:
    - Incremental DOM (Angular)
    - Signals/Fine-grained reactivity (Solid.js, Vue 3) — avoid VDOM entirely
    - Svelte: compiles to direct DOM manipulation

11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the DOM?
A: The Document Object Model is a tree-based in-memory representation of
   an HTML document. It's a platform-neutral API (WHATWG spec) that JS
   can use to query and manipulate the page structure and content.

Q: Is the DOM the same as the HTML source code?
A: No. The DOM is the parsed and live representation. Browsers correct
   invalid HTML (auto-insert tbody, close unclosed tags), JavaScript
   can modify it after load, and script execution can change it dynamically.

Q: What is the CSSOM?
A: CSS Object Model — the parsed in-memory representation of all CSS rules.
   Combined with the DOM to compute final styles for every element.
   It's render-blocking: rendering waits for CSSOM to be fully built.

Q: Why is CSS render-blocking?
A: The browser must fully parse all CSS before it can compute styles and
   build the render tree. Partial CSS causes FOUC (Flash of Unstyled
   Content). A single rule at the bottom of a stylesheet can affect
   elements at the top, so all CSS must be known before rendering starts.

Q: What is the difference between the DOM and Render Tree?
A: DOM includes all nodes (head, hidden elements, comments). The Render
   Tree includes only visible elements with computed styles. Elements with
   display:none are excluded; visibility:hidden are included (they take space).

Q: What is the difference between innerHTML and textContent?
A: innerHTML parses and sets HTML markup (XSS risk if setting user input).
   textContent gets/sets plain text, does not parse HTML (safe for user
   input, faster). innerText is similar but respects CSS visibility and
   triggers reflow.

Q: Why should you use DocumentFragment?
A: Appending many nodes to the DOM individually causes multiple reflows.
   DocumentFragment is an off-DOM container where you build the tree
   without triggering reflows. Appending the fragment to the DOM
   triggers only one reflow.

Q: What is the difference between querySelectorAll and getElementsByClassName?
A: querySelectorAll returns a STATIC NodeList (snapshot at time of query).
   getElementsByClassName returns a LIVE HTMLCollection that auto-updates
   as the DOM changes. querySelectorAll supports any CSS selector.

Q: What is Shadow DOM?
A: An encapsulated DOM subtree with style isolation. CSS inside a shadow
   root doesn't affect the outer page, and outer CSS doesn't affect
   shadow DOM contents. Used in Web Components and native browser widgets.

Q: What is Virtual DOM and why was it introduced?
A: Virtual DOM is a lightweight JS object tree representing the real DOM.
   Libraries like React maintain a VDOM, diff it on state changes, and
   apply only minimal required updates to the real DOM. Introduced to
   optimize UI updates and provide a declarative programming model.

Q: What are async and defer script attributes?
A: Both download scripts without blocking HTML parsing.
   async: executes as soon as downloaded (unpredictable order, may block parse).
   defer: executes after HTML is fully parsed, in order, before DOMContentLoaded.
   defer is preferred for app scripts; async for independent third-party scripts.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • DOM = parsed tree of HTML (not same as source), manipulable by JS
  • CSSOM = parsed tree of CSS; render-blocking
  • Render Tree = DOM + CSSOM, visible nodes only
  • querySelectorAll → static; getElementsBy* → live
  • DocumentFragment → batch DOM updates to minimize reflows
  • Shadow DOM → encapsulated, style-isolated component subtrees
  • async: download parallel, execute immediately; defer: execute after parse
================================================================================
