================================================================================
  BROWSER ARCHITECTURE — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. OVERVIEW
────────────────────────────────────────────────────────────────────────────────

Browser architecture has evolved from a single-process monolith to a
sophisticated multi-process system. Understanding this is critical for
performance optimization and security discussions.

────────────────────────────────────────────────────────────────────────────────
2. SINGLE-PROCESS ARCHITECTURE (OLD)
────────────────────────────────────────────────────────────────────────────────

Early browsers (IE6, early Firefox) ran everything in one process:
  - UI
  - Rendering
  - JavaScript execution
  - Networking
  - Plugins

Problems:
  • One tab crash → entire browser crashes
  • Plugin crash (Flash!) → everything freezes
  • No memory isolation between tabs
  • Long JS execution freezes entire browser UI
  • Security: any exploit has full system access

────────────────────────────────────────────────────────────────────────────────
3. MULTI-PROCESS ARCHITECTURE (MODERN)
────────────────────────────────────────────────────────────────────────────────

Chrome (Chromium) pioneered multi-process architecture in 2008.

  ┌─────────────────────────────────────────────────────────────┐
  │                    BROWSER PROCESS (1)                      │
  │  - Chrome UI (address bar, tabs, settings)                 │
  │  - Coordinates all other processes                         │
  │  - Tab/window management                                   │
  │  - Downloads, settings storage                             │
  └─────────────────┬───────────────────────────────────────────┘
                    │ IPC (Mojo)
        ┌───────────┼────────────┬───────────────┐
        ▼           ▼            ▼               ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ Renderer │ │ Renderer │ │  GPU     │ │ Network  │
  │ Process  │ │ Process  │ │ Process  │ │ Process  │
  │ (Tab A)  │ │ (Tab B)  │ │          │ │          │
  └──────────┘ └──────────┘ └──────────┘ └──────────┘
       │
  ┌─────────────────────────┐
  │  Blink (Rendering Engine)│
  │  V8 (JavaScript Engine) │
  │  Sandboxed              │
  └─────────────────────────┘

  Process Types:

    Browser Process (1 per browser instance):
      - Root/privileged process
      - Manages tabs, UI, and child processes
      - Handles permissions (camera, mic access)
      - NOT sandboxed (needs OS access)

    Renderer Process (1+ per tab/site):
      - Contains Blink rendering engine + V8 JS engine
      - SANDBOXED: no direct OS system calls
      - Communicates with browser process via IPC for privileged ops
      - Has its own memory heap and GC

    GPU Process (1 per browser):
      - Handles all GPU commands for compositing/rasterization
      - Shared across all renderer processes
      - Isolates GPU driver crashes (common source of bugs)

    Network Process (usually 1):
      - Handles all network requests (HTTP, WebSocket, etc.)
      - Manages HTTP cache, cookies, certificate verification
      - Separate from renderer for security and caching

    Plugin/Pepper Plugin Processes:
      - Each plugin in its own process
      - NPAPI plugins mostly removed (Flash = gone)

    Utility Processes:
      - Audio, printing, file utilities, etc.

    Extension/Service Worker Processes:
      - Each extension in its own process

────────────────────────────────────────────────────────────────────────────────
4. SITE ISOLATION
────────────────────────────────────────────────────────────────────────────────

  Before Site Isolation:
    - One renderer process could host multiple sites (different origins)
    - Enabled cross-origin data theft via Spectre/Meltdown side channels

  Site Isolation (Chrome 67+, 2018):
    - Each SITE (scheme + eTLD+1) gets its own renderer process
    - Different from "origin" (considers port too)
    - Site = https://example.com:443 (not subdomains)

  Benefits:
    • Spectre/Meltdown mitigated (can't read another site's memory)
    • Cross-origin iframes are in separate processes
    • Per-site process limits blast radius of security exploits

  Out-of-Process Iframes (OOPIFs):
    - Cross-origin <iframe> rendered in a different process
    - Complex coordination for hit-testing, events, scrolling

  Trade-offs:
    - More memory (each site has own process overhead)
    - More IPC communication (cross-process iframe interactions)

────────────────────────────────────────────────────────────────────────────────
5. SANDBOXING
────────────────────────────────────────────────────────────────────────────────

  Renderer processes are SANDBOXED:
    - Cannot access filesystem
    - Cannot make network requests directly
    - Cannot call privileged OS APIs
    - Must request everything through browser process via IPC

  OS Sandbox Mechanisms:
    Linux:  seccomp-bpf (system call filtering), namespaces
    macOS:  Seatbelt sandbox profiles
    Windows: Token-based sandbox, Integrity Levels, Job Objects

  What the sandbox protects against:
    - Renderer compromise → cannot escape to OS
    - Attacker exploits JS/rendering bug → still sandboxed
    - Limits impact of security vulnerabilities

────────────────────────────────────────────────────────────────────────────────
6. INTER-PROCESS COMMUNICATION (IPC)
────────────────────────────────────────────────────────────────────────────────

  Mojo (Chromium's IPC system):
    - Custom IPC framework replacing old Chrome IPC
    - Typed message passing via .mojom interface definition files
    - Supports synchronous and asynchronous messages
    - Works across process boundaries and over network

  Communication examples:
    - Renderer requests resource fetch → Network Process
    - Renderer requests cookie read/write → Browser Process
    - Renderer sends GPU draw commands → GPU Process
    - Browser Process terminates crashed Renderer

  postMessage (Web API level):
    - window.postMessage() for cross-origin/cross-frame communication
    - Structured Clone Algorithm for serializing data
    - MessageChannel for bidirectional ports
    - Used by: iframes, Web Workers, Service Workers

────────────────────────────────────────────────────────────────────────────────
7. RENDERING ENGINE INTERNALS (BLINK)
────────────────────────────────────────────────────────────────────────────────

  Blink (used in Chrome/Edge/Opera):
    - Forked from WebKit in 2013
    - Handles HTML parsing, CSS parsing, layout, painting
    - Manages the DOM, CSSOM, Render Tree, Layer Tree
    - Coordinates with V8 for JavaScript execution

  V8 (JavaScript Engine):
    - Compiles JavaScript to machine code (JIT)
    - Ignition (interpreter/bytecode compiler)
    - TurboFan (optimizing JIT compiler)
    - Manages heap memory and garbage collection

  Thread Model within Renderer:
    Main Thread:
      - HTML/CSS parsing
      - JavaScript execution (single-threaded)
      - Layout, Compositing decisions
      - Handles JS events

    Raster Threads (multiple):
      - Convert layer content to pixels (rasterization)
      - Can run in parallel

    Compositor Thread:
      - Handles scrolling and CSS animations independently
      - Does NOT need to go through main thread for smooth 60fps scroll
      - Draws pre-rasterized tiles to screen
      - Why scroll/opacity/transform feel smooth even when JS is busy

    Worker Threads:
      - For Web Workers and Service Workers
      - Separate from main thread

────────────────────────────────────────────────────────────────────────────────
8. BROWSER MEMORY
────────────────────────────────────────────────────────────────────────────────

  Each renderer process has:
    - V8 heap (JS objects, closures, functions)
    - Blink heap (DOM nodes, layout objects, style data)
    - Shared memory with GPU process (textures, layer bitmaps)
    - Native memory (C++ allocations)

  Memory Limits:
    - 32-bit browsers: ~2GB per process limit
    - 64-bit: theoretically much higher, but Chrome has per-renderer limits
    - Chrome: 4GB per renderer (64-bit), 512MB on mobile

  Process Recycling:
    - Chrome recycles renderer processes for same-site navigation
    - Swap: close old page's renderer after new page commits
    - Back/Forward Cache (bfcache): freezes pages in memory for instant back

────────────────────────────────────────────────────────────────────────────────
9. BACK/FORWARD CACHE (bfcache)
────────────────────────────────────────────────────────────────────────────────

  What it is:
    - Pages stored in memory when navigated away from
    - Restored instantly (no network, no re-parse) on back/forward

  How it works:
    - Entire JS heap and DOM state frozen when page is "hidden"
    - Resumed when user navigates back
    - pageshow event fires with persisted=true

  What prevents bfcache:
    - Unload event listeners (deprecated — avoid!)
    - Cache-Control: no-store header
    - Open IndexedDB connections
    - WebSocket connections
    - SharedArrayBuffer usage
    - Response.body reader not closed

  Event API:
    window.addEventListener('pagehide', e => { if (e.persisted) ... })
    window.addEventListener('pageshow', e => { if (e.persisted) ... })

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: Why does Chrome use a separate process per tab?
A: For isolation (crash in one tab doesn't affect others), security
   (each renderer is sandboxed), and performance (separate GC, no shared
   main thread). Drawback: higher memory usage.

Q: What is the difference between the browser process and the renderer process?
A: The browser process is the privileged root process managing the UI, tabs,
   and coordinating all other processes. The renderer process is sandboxed,
   contains Blink (rendering) + V8 (JS), and handles the actual page content.
   Renderer can't access OS resources directly — must IPC through browser.

Q: What is Site Isolation and why was it introduced?
A: Site Isolation (Chrome 67+) gives each website its own renderer process.
   Introduced to mitigate Spectre/Meltdown CPU side-channel attacks that
   could let a malicious page read another page's memory. Without isolation,
   cross-origin data could leak via shared process memory.

Q: What is sandboxing in the context of browser security?
A: Renderer processes run inside an OS sandbox that blocks direct system
   calls (no filesystem, network, or OS API access). If an attacker exploits
   a renderer bug, they're confined to the sandbox and cannot access the
   broader system.

Q: What is the compositor thread and why is it important?
A: The compositor thread handles scrolling and CSS animations independently
   from the main thread. This means scrolling and opacity/transform animations
   run at 60fps even when JS is busy (long tasks) because the compositor
   doesn't need to wait for the JS main thread.

Q: What is the back/forward cache (bfcache)?
A: A browser optimization that keeps pages in memory when navigating away,
   enabling instant restoration when using back/forward buttons. Pages are
   frozen (JS paused) and resumed. Adding 'unload' event listeners or
   Cache-Control: no-store headers prevent bfcache eligibility.

Q: What is Mojo in Chromium?
A: Mojo is Chromium's IPC (Inter-Process Communication) framework. It defines
   typed interfaces (.mojom files) for safe message passing between browser
   components across process boundaries (browser ↔ renderer ↔ GPU ↔ network).

Q: What threads exist inside a renderer process?
A: Main thread (JS, HTML/CSS parsing, layout), Compositor thread (scrolling,
   animations, no main thread needed), Raster threads (paint tiles in
   parallel), Worker threads (Web Workers, Service Workers).

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Multi-process: Browser process (privileged) + Renderer (sandboxed) +
    GPU + Network + Utility processes
  • Site Isolation: 1 renderer per site → Spectre/Meltdown protection
  • Sandbox: renderer can't access OS directly — must IPC through browser
  • Compositor thread: enables smooth scroll/animations independent of JS
  • bfcache: instant back/forward navigation (pages frozen in memory)
