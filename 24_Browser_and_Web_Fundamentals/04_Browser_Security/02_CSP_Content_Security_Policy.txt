================================================================================
  CSP (Content Security Policy) — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS CSP?
────────────────────────────────────────────────────────────────────────────────

  Content Security Policy (CSP) is an HTTP response header (or <meta> tag)
  that tells the browser which sources of content are trusted.

  Purpose:
    • Mitigate XSS by blocking inline scripts and restricting script sources
    • Prevent clickjacking (via frame-ancestors)
    • Reduce attack surface for data exfiltration

  How it works:
    Server sets the header → browser enforces the policy.
    Violations are blocked (and optionally reported to an endpoint).

  Two delivery methods:
    1. HTTP header (preferred):
       Content-Security-Policy: default-src 'self'
    2. Meta tag (limited — cannot use report-uri):
       <meta http-equiv="Content-Security-Policy" content="default-src 'self'">

────────────────────────────────────────────────────────────────────────────────
2. CSP DIRECTIVES
────────────────────────────────────────────────────────────────────────────────

  2.1 Fetch Directives (control resource loading)

    default-src:
      Fallback for all unspecified fetch directives.
      Content-Security-Policy: default-src 'self'

    script-src:
      Controls script sources.
      Content-Security-Policy: script-src 'self' https://cdn.example.com

    style-src:
      Controls stylesheets.

    img-src:
      Controls image sources.

    font-src:
      Controls font file sources.

    connect-src:
      Controls fetch(), XHR, WebSocket, EventSource URLs.
      Prevents data exfiltration to unauthorized endpoints.

    media-src:
      Controls <audio> and <video> sources.

    object-src:
      Controls <object>, <embed>, <applet>. Set to 'none' (no Flash, etc.)

    frame-src:
      Controls which URLs can be loaded in <iframe>.

    child-src:
      Controls Web Workers and nested browsing contexts (frames).

    worker-src:
      Controls Worker, SharedWorker, ServiceWorker.

    manifest-src:
      Controls Web App Manifests.

  2.2 Document Directives

    base-uri:
      Restricts <base> element's href (prevents base tag injection).
      Recommended: base-uri 'self' or 'none'

    sandbox:
      Applies restrictions similar to <iframe sandbox> attribute.

  2.3 Navigation Directives

    form-action:
      Restricts where <form> can submit to.
      form-action 'self' https://api.example.com

    frame-ancestors:
      Controls which origins can embed this page in a frame.
      Replaces X-Frame-Options header.
      frame-ancestors 'none'  → no framing (anti-clickjacking)
      frame-ancestors 'self'  → same origin only
      frame-ancestors https://trusted.com  → specific origin

  2.4 Reporting Directives

    report-uri (deprecated): /csp-report-endpoint
    report-to (modern):
      Content-Security-Policy: default-src 'self'; report-to default
      Reporting-Endpoints: default="https://example.com/csp-reports"

────────────────────────────────────────────────────────────────────────────────
3. SOURCE VALUES
────────────────────────────────────────────────────────────────────────────────

  Keyword sources:
    'self'          Only same origin
    'none'          Block all
    'unsafe-inline' Allow inline scripts/styles (DEFEATS CSP for XSS!)
    'unsafe-eval'   Allow eval(), Function(), setTimeout(str)
    'strict-dynamic' Allow scripts loaded by a trusted script (nonce-based)

  URL-based sources:
    https://cdn.example.com              exact host
    https://*.example.com               all subdomains
    https:                              any HTTPS URL
    data:                               data: URIs (be careful)

  Hash sources:
    'sha256-<hash>'  Allow a specific inline script with matching hash
    Browser computes SHA256 of the script text, compares with policy.
    
    Example:
      # The inline script: alert('Hello');
      # Compute: echo -n "alert('Hello');" | openssl dgst -sha256 -binary | base64
      Content-Security-Policy: script-src 'sha256-RpniQgt...'

  Nonce sources (recommended for inline scripts):
    'nonce-<random>'  Allow specific inline scripts with the matching nonce.
    Nonce must be unique per response, unguessable, base64-encoded.
    
    Header: Content-Security-Policy: script-src 'nonce-r4nd0m456'
    HTML: <script nonce="r4nd0m456">// allowed inline script</script>

────────────────────────────────────────────────────────────────────────────────
4. STRICT CSP (BEST PRACTICE)
────────────────────────────────────────────────────────────────────────────────

  Traditional allowlist-based CSP (NOT recommended for scripts):
    script-src 'self' https://cdn.example.com
    Problem: If attacker finds JSONP or open redirect on cdn.example.com,
    they can execute arbitrary scripts — allowlists are hard to maintain.

  Nonce-based Strict CSP (recommended):
    Content-Security-Policy:
      script-src 'nonce-{random}' 'strict-dynamic';
      object-src 'none';
      base-uri 'none';
    
    'strict-dynamic':
      Trusts scripts loaded by the nonce'd script (e.g., dynamically added <script>).
      Propagates trust to dynamically loaded scripts.
      Ignores host/scheme allowlists when present.
    
    Hash-based Strict CSP (no server-side templates):
    Content-Security-Policy:
      script-src 'sha256-<hash-of-script.js>' 'strict-dynamic';

  Minimum recommended policy:
    Content-Security-Policy:
      default-src 'self';
      script-src 'self' 'nonce-{random}';
      object-src 'none';
      base-uri 'self';
      frame-ancestors 'none';

────────────────────────────────────────────────────────────────────────────────
5. CSP AND INLINE SCRIPTS
────────────────────────────────────────────────────────────────────────────────

  Inline scripts are blocked by default when script-src is set.
  Blocked:
    <script>alert('XSS')</script>
    <button onclick="evil()">
    javascript: URLs
    eval('...')
    new Function(...)

  Allowed inline scripts (if configured):
    1. 'unsafe-inline' — enables ALL inline scripts (weakens CSP significantly)
    2. Nonce: <script nonce="abc">...</script>  with matching nonce in header
    3. Hash: script content matches the sha256/sha384/sha512 hash in header

  'unsafe-eval' specifically allows:
    eval(), new Function(), setTimeout with string arg, setInterval with string
    Avoid unless specifically required (e.g., some JS engines for games/wasm).

────────────────────────────────────────────────────────────────────────────────
6. CSP REPORT-ONLY MODE
────────────────────────────────────────────────────────────────────────────────

  Use Content-Security-Policy-Report-Only to test a policy without enforcing it.
  Browser reports violations but does NOT block them.
  
    Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report

  Workflow for deploying CSP:
    1. Deploy in report-only mode
    2. Monitor violations at report endpoint
    3. Fix legitimate violations (whitelist needed sources, add nonces)
    4. Switch to enforcing CSP header

  CSP violation report body (JSON):
    {
      "csp-report": {
        "document-uri": "https://example.com/page",
        "violated-directive": "script-src 'self'",
        "blocked-uri": "https://evil.com/bad.js",
        "line-number": 10,
        "original-policy": "script-src 'self'"
      }
    }

────────────────────────────────────────────────────────────────────────────────
7. CSP BYPASSES AND PITFALLS
────────────────────────────────────────────────────────────────────────────────

  JSONP endpoints on whitelisted domains:
    If https://cdn.example.com has a JSONP endpoint, attacker can:
    <script src="https://cdn.example.com/callback?cb=evil()"></script>
    Solution: Use nonce-based strict CSP instead of allowlists.

  Open redirects on whitelisted domains:
    Similarly, redirect to attacker-controlled script.

  'unsafe-inline' with nonces:
    If BOTH 'unsafe-inline' AND nonces are set, browsers ignore 'unsafe-inline'
    (nonce presence overrides it) — this is correct behavior.

  data: URIs:
    Including data: in img-src or script-src is dangerous — allows inline
    HTML/script embedding.

────────────────────────────────────────────────────────────────────────────────
8. RELATED SECURITY HEADERS
────────────────────────────────────────────────────────────────────────────────

  X-Frame-Options (older, simpler alternative to frame-ancestors):
    X-Frame-Options: DENY       → no framing
    X-Frame-Options: SAMEORIGIN → same origin only
    Use frame-ancestors in CSP for more fine-grained control.

  X-Content-Type-Options:
    X-Content-Type-Options: nosniff
    Prevents browser from MIME-sniffing (treating a file as different type).
    Blocks XSS via uploaded files misinterpreted as HTML.

  Permissions-Policy (formerly Feature-Policy):
    Controls which browser features can be used (camera, geolocation, etc.)
    Permissions-Policy: geolocation=(), camera=()

  Referrer-Policy:
    Controls how much info is in the Referer header.
    Referrer-Policy: strict-origin-when-cross-origin

9. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is Content Security Policy and what problem does it solve?
A: CSP is an HTTP header that declares which sources of content are trusted.
   It mitigates XSS by blocking unauthorized inline scripts and external
   script sources. Even if an attacker manages to inject a script tag, CSP
   prevents it from executing if the source isn't whitelisted. It also
   prevents clickjacking via frame-ancestors and data exfiltration via
   connect-src.

Q: What is the difference between 'unsafe-inline' and nonces in CSP?
A: 'unsafe-inline' allows ALL inline scripts, effectively disabling XSS
   protection for inline code. Nonces assign a unique random value per
   response — only inline scripts with the matching nonce attribute are
   allowed. Nonces are specific and cryptographically unguessable, making
   them far more secure than 'unsafe-inline'.

Q: What is strict-dynamic in CSP?
A: strict-dynamic trusts any script that was loaded by an already-trusted
   script (one with a valid nonce/hash). This allows dynamically inserted
   <script> elements to also execute. It makes nonce-based CSP practical for
   SPAs that inject scripts at runtime. When strict-dynamic is present, host/
   scheme allowlists are ignored for script-src.

Q: How do you deploy CSP without breaking your site?
A: Use Content-Security-Policy-Report-Only first. This reports violations
   to your endpoint without blocking anything. Monitor reports, add
   missing sources to your policy, then switch to enforcing the header.
   Always test in staging before production.

Q: What does frame-ancestors 'none' do?
A: It prevents the page from being embedded in any <iframe>, <frame>,
   <embed>, or <object> on any origin. This replaces the older
   X-Frame-Options: DENY and is the primary defense against clickjacking.

Q: What is a CSP bypass via JSONP?
A: If you whitelist a CDN domain that has a JSONP endpoint (e.g., 
   cdn.example.com/callback?cb=evil()), an attacker can use that endpoint
   to execute arbitrary code within your allowed domain. This is why
   domain allowlists are fragile and nonce-based strict CSP is preferred.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • CSP: HTTP header whitelisting trusted content sources; XSS mitigation
  • script-src 'self': allow scripts only from same origin
  • 'unsafe-inline': weakens CSP; use nonces/hashes instead
  • Nonce: unique per-response random value → specific inline scripts allowed
  • strict-dynamic: trust scripts loaded by nonce'd scripts; enables SPAs
  • frame-ancestors: anti-clickjacking; replaces X-Frame-Options
  • Deploy with Report-Only first, then enforce after testing
================================================================================
