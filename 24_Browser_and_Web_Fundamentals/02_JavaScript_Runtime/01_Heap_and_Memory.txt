────────────────────────────────────────────────────────────────────────────────
1. JAVASCRIPT MEMORY MODEL
────────────────────────────────────────────────────────────────────────────────

  JavaScript engines use two primary memory regions:

  STACK:
    • Fixed-size, fast access
    • Stores: primitive values, references (pointers), function frames
    • LIFO structure (call stack frames)
    • Automatically managed (frame popped when function returns)

  HEAP:
    • Dynamic-size, slower access
    • Stores: Objects, Arrays, Functions, Closures, DOM nodes
    • Managed by Garbage Collector
    • Memory allocated on demand, freed by GC when no longer reachable

────────────────────────────────────────────────────────────────────────────────
2. VALUE TYPES VS REFERENCE TYPES
────────────────────────────────────────────────────────────────────────────────

  Primitive Types (stored by VALUE on stack):
    undefined, null, boolean, number, bigint, string, symbol
    
    let a = 5;
    let b = a;  // b gets a COPY of 5
    b = 10;
    console.log(a); // 5 (unchanged)

  Reference Types (stored as REFERENCES — pointer to heap object):
    Objects, Arrays, Functions, Dates, RegExp, Maps, Sets, etc.
    
    let obj1 = { x: 1 };
    let obj2 = obj1;  // obj2 stores same REFERENCE (pointer)
    obj2.x = 99;
    console.log(obj1.x); // 99 (same object in heap!)

  Memory layout visualization:
    Stack:            Heap:
    a: 5              ──────────────────
    obj1: [ref]  ──►  { x: 99 }
    obj2: [ref]  ──►  (same object)

  String note:
    Strings are primitives in JS but may be stored on heap (immutable)
    They behave like value types (copy-on-assign)

3. V8 HEAP STRUCTURE
────────────────────────────────────────────────────────────────────────────────

  V8 organizes the heap into several spaces:

  ┌─────────────────────────────────────────────────────────────────┐
  │  NEW SPACE (Young Generation)                                    │
  │  ┌─────────────┐  ┌─────────────┐                              │
  │  │  From Space  │  │   To Space  │  (Scavenger GC)              │
  │  │ (active)    │  │ (inactive)  │                              │
  │  └─────────────┘  └─────────────┘                              │
  │  Size: 1-8MB, collected frequently                              │
  ├─────────────────────────────────────────────────────────────────┤
  │  OLD SPACE (Old Generation)                                      │
  │  ┌─────────────────────────────────────────────────────────┐   │
  │  │  Old Pointer Space    |    Old Data Space               │   │
  │  │  (objects with refs)  |    (objects without refs)       │   │
  │  └─────────────────────────────────────────────────────────┘   │
  │  Size: up to several GB, collected less frequently              │
  ├─────────────────────────────────────────────────────────────────┤
  │  CODE SPACE (JIT-compiled code)                                  │
  ├─────────────────────────────────────────────────────────────────┤
  │  LARGE OBJECT SPACE (objects > 256KB — not moved by GC)         │
  ├─────────────────────────────────────────────────────────────────┤
  │  MAP SPACE (hidden class descriptors / shapes)                  │
  └─────────────────────────────────────────────────────────────────┘

  Generational Hypothesis:
    "Most objects die young"
    Short-lived temp variables, loop iterations → created and quickly GC'd
    Long-lived objects (caches, singletons) survive and are promoted

4. GARBAGE COLLECTION ALGORITHMS
────────────────────────────────────────────────────────────────────────────────

  4.1 REFERENCE COUNTING (NOT used in V8, but historical)
    - Each object has a count of how many references point to it
    - Count reaches 0 → object freed
    - Problem: circular references → memory leak
    
    let a = {};
    let b = {};
    a.ref = b;  // b's count = 1
    b.ref = a;  // a's count = 1
    a = null;   // a's count drops to 1 (b.ref still points to it)
    b = null;   // b's count drops to 1 (a.ref still points to it)
    // Both have count=1 but are unreachable → LEAK with reference counting

  4.2 MARK-AND-SWEEP (V8 Major GC)
    Phase 1 — MARK:
      - Start from "roots" (global variables, current call stack, registers)
      - Traverse all reachable objects (BFS/DFS traversal)
      - Mark every reachable object as "live"
    
    Phase 2 — SWEEP:
      - Walk entire heap
      - Any unmarked object → GARBAGE → memory reclaimed
    
    Phase 3 — COMPACT (optional):
      - Move all live objects together
      - Defragments memory
      - Updates all references (pointers) to new locations
      - Eliminates fragmentation → faster future allocations
    
    Solves circular reference problem!
    Even if a and b reference each other, if nothing in roots reaches them,
    they get collected.

  4.3 SCAVENGER (Minor GC — Young Generation)
    Algorithm: Cheney's copying algorithm
    
    Step 1: New objects allocated in "From Space"
    Step 2: When From Space fills up → Scavenge triggered
    Step 3: Traverse live objects in From Space
    Step 4: Copy live objects to "To Space"
    Step 5: Objects that survived 2 collections → PROMOTED to Old Space
    Step 6: From Space and To Space roles SWAP
    
    Very fast because:
    - Only processes young generation (small)
    - Dead objects (majority!) require no work — just don't copy them
    - Living objects contiguous in To Space (no fragmentation)
    
    After scavenge: all live objects in To Space, From Space entirely free

  4.4 INCREMENTAL MARKING
    Problem: Full major GC (mark-sweep) can pause JS for 100ms+ (jank)
    Solution: Break marking into small increments (~1ms each)
    - Interleave marking work with JS execution
    - Write barriers track any reference changes during incremental marking
    - Result: Smaller individual GC pauses, better responsiveness

  4.5 CONCURRENT MARKING (V8 Orinoco GC)
    - Marking runs on BACKGROUND THREADS while JS executes on main thread
    - JS thread continues running! Almost no pause for marking
    - Only small "stop-the-world" pauses for final sync

  4.6 CONCURRENT SWEEPING
    - Sweeping also on background threads
    - Minimal impact on JS execution

  4.7 LAZY SWEEPING
    - Don't sweep entire heap at once
    - Only sweep pages as new memory is needed

────────────────────────────────────────────────────────────────────────────────
5. GC ROOTS
────────────────────────────────────────────────────────────────────────────────

  GC starts traversal from ROOTS — objects always considered live:
    • Global variables (window object and properties)
    • Variables currently in call stack frames
    • CPU registers pointing to objects
    • Closed-over variables in active closures

  Any object NOT reachable from roots = garbage = can be collected

────────────────────────────────────────────────────────────────────────────────
6. MEMORY ALLOCATION IN V8
────────────────────────────────────────────────────────────────────────────────

  Object allocation:
    new Person() → allocates in New Space From-half
    If object survives 2 scavenges → promoted to Old Space

  Fast allocation (bump pointer):
    New Space uses a simple "bump pointer" — just increment a pointer
    No complex free-list lookup needed → very fast
    Only when bump pointer reaches end of space → trigger Scavenge

  Large objects:
    Objects > 256KB → allocated directly in Large Object Space
    Not moved by GC (too expensive)

────────────────────────────────────────────────────────────────────────────────
7. MEMORY MEASUREMENT TOOLS
────────────────────────────────────────────────────────────────────────────────

  Chrome DevTools — Memory tab:
    Heap Snapshot:
      - Shows all live objects in V8 heap at a point in time
      - Shows object types, counts, sizes, retained sizes
      - Compare two snapshots to find leaks

    Heap Allocation Timeline:
      - Record allocations over time
      - See which objects were allocated and not collected

    Allocation Sampling:
      - Statistical sampling of allocations
      - Low overhead, good for production profiling

  Performance Monitor (DevTools):
    - JS heap size graph in real-time
    - DOM nodes count
    - Event listener count

  performance.measureUserAgentSpecificMemory():
    - New API (Chrome 89+) to measure memory from JS
    - Available only in cross-origin-isolated contexts

  Retained Size vs Shallow Size:
    Shallow size: size of object itself (no referenced objects)
    Retained size: total memory freed IF this object is collected
                   (object + all objects that only this object references)
    Large retained size = good candidate for memory leak investigation

8. COMMON MEMORY LEAKS
────────────────────────────────────────────────────────────────────────────────

  8.1 Accidental Global Variables
    function leak() {
      x = "I am global!"; // forgot var/let/const — goes on window!
    }
    
    Fix: 'use strict' mode → throws ReferenceError

  8.2 Forgotten Event Listeners
    const button = document.getElementById('btn');
    button.addEventListener('click', handleClick);
    // button removed from DOM but listener holds reference to handleClick
    // handleClick closure may hold references to large objects
    
    Fix:
    button.removeEventListener('click', handleClick);
    // Or use AbortController:
    const controller = new AbortController();
    button.addEventListener('click', handler, { signal: controller.signal });
    controller.abort(); // removes all listeners with this signal

  8.3 Closures Holding References
    function createClosure() {
      const largeData = new Array(1000000);  // 1M items
      return function() {
        // uses largeData
        return largeData.length;
      };
    }
    const fn = createClosure();
    // largeData stays alive as long as fn lives
    // If fn stored globally, largeData NEVER collected
    
    Fix: Set fn = null when done; don't close over large data unnecessarily

  8.4 Detached DOM Nodes
    const list = document.getElementById('myList');
    const item = list.children[0];
    list.innerHTML = ''; // removes items from DOM
    // BUT item variable still holds reference → DOM subtree not collected
    
    Fix: Clear references after DOM removal:
    item = null;

  8.5 Timers Not Cleared
    function startTimer() {
      const data = { /* large object */ };
      return setInterval(() => {
        processData(data); // closure holds data reference
      }, 1000);
    }
    // If interval not cleared → data lives forever
    
    Fix: clearInterval(timerId) when done

  8.6 Caches Without Eviction Policy
    const cache = {};
    function fetchAndCache(key, fn) {
      if (!cache[key]) cache[key] = fn();
      return cache[key];
    }
    // cache grows forever — no eviction!
    
    Fix: Use WeakMap (for object keys), LRU cache, or TTL-based eviction

  8.7 WeakRef and WeakMap for Avoiding Leaks
    WeakMap:
      - Keys MUST be objects
      - Keys held weakly (GC can collect key+value if no other reference)
      - Use for: cache with object keys, private data per object instance
      
    WeakSet:
      - Objects held weakly
      - Good for: tracking "visited" objects without preventing GC
      
    WeakRef (ES2021):
      - Holds weak reference to an object
      - .deref() returns object or undefined (if collected)
      - Use sparingly — complex lifetime management

  8.8 Console References
    console.log(largeObject) keeps largeObject alive in DevTools
    In production, avoid excessive console.logging of large objects
    DevTools keeps references to logged objects (may appear as leaks in profiling)

9. MEMORY OPTIMIZATION STRATEGIES
────────────────────────────────────────────────────────────────────────────────

  9.1 Object Pooling
    Reuse objects instead of creating new ones in hot loops:
    
    class Particle {
      constructor() { this.reset(); }
      reset() { this.x = 0; this.y = 0; this.active = false; }
    }
    const pool = Array.from({ length: 100 }, () => new Particle());
    
    function getParticle() {
      return pool.find(p => !p.active);
    }

  9.2 Avoid Creating Objects in Hot Loops
    // Bad: creates new object each iteration
    for (let i = 0; i < 1000000; i++) {
      const vec = { x: i, y: i }; // allocations → GC pressure
      process(vec);
    }
    
    // Better: reuse
    const vec = { x: 0, y: 0 };
    for (let i = 0; i < 1000000; i++) {
      vec.x = i; vec.y = i;
      process(vec);
    }

  9.3 Use Typed Arrays for Numeric Data
    // Regular array: V8 may store as double-precision floats (boxing)
    const arr = new Array(1000000);
    
    // Typed array: contiguous memory, no boxing
    const arr = new Float64Array(1000000);

  9.4 Scope Management
    Keep large objects scoped tightly:
    function process() {
      const bigData = loadData(); // loaded
      const result = compute(bigData); // computed
      // bigData eligible for GC after this function returns
      return result;
    }

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: Where are JavaScript values stored — stack or heap?
A: Primitive values (number, boolean, string, null, undefined, symbol, bigint)
   are stored by value (effectively on the stack as part of frames or directly).
   Reference types (objects, arrays, functions) are allocated on the heap;
   the variable holds a reference (pointer) to the heap location.

Q: How does JavaScript garbage collection work?
A: V8 uses generational GC. New objects go to the young generation (New Space),
   collected by a fast Scavenger (copying algorithm). Objects surviving 2+
   scavenges are promoted to the old generation, collected by a full
   Mark-Sweep-Compact algorithm. Incremental and concurrent marking minimize
   GC pauses.

Q: What is the difference between shallow size and retained size?
A: Shallow size: memory of the object itself. Retained size: total memory
   freed if the object were collected — includes all objects only reachable
   through this object. A small object with large retained size is a
   leak candidate.

Q: Why doesn't reference counting work for JavaScript?
A: Reference counting fails with circular references. If A references B
   and B references A, their counts never reach 0 even if nothing else
   references them. Mark-and-sweep solves this: if neither is reachable
   from GC roots, both are collected regardless of reference counts.

Q: What are common memory leaks in JavaScript?
A: 1) Accidental globals (forgot var/let/const).
   2) Forgotten event listeners (especially on removed DOM nodes).
   3) Closures holding large objects unnecessarily.
   4) Detached DOM nodes still referenced by JS.
   5) Uncleared timers (setInterval) with closures.
   6) Unbounded caches.

Q: What is a WeakMap and when would you use it?
A: WeakMap holds object keys weakly — if the key object has no other
   references, it (and its map entry) can be GC'd. Use for: associating
   data with objects without preventing their GC (e.g., private instance
   data, metadata caches, tracking DOM element state).

Q: How can you detect memory leaks?
A: Chrome DevTools → Memory tab. Take heap snapshots before/after
   suspected leak. Compare to find objects that should have been freed
   but weren't. Look for "Detached DOM tree" entries. Also use the
   Allocation Timeline to see allocations that weren't freed.

Q: What is the generational hypothesis in GC?
A: "Most objects die young" — newly created objects tend to become
   unreachable quickly (temp variables, loop iterations). GC exploits
   this by collecting the young generation (small) very frequently (cheap),
   and only occasionally doing expensive old generation collection.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Stack: primitives/references, fast, auto-managed by call frames
  • Heap: objects/arrays/functions, GC-managed
  • V8: Young Gen (Scavenger/copying) + Old Gen (Mark-Sweep-Compact)
  • GC roots: globals, call stack, registers — unreachable = garbage
  • Mark-and-sweep handles circular references (reference counting doesn't)
  • Common leaks: globals, forgotten listeners, detached DOM, uncleaned timers
  • WeakMap/WeakSet: weak references, key-objects can be GC'd
  • Retained size > shallow size → leak investigation priority
