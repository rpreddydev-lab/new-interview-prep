================================================================
  MERGE / UPSERT
================================================================

  UPSERT = INSERT if not exists, UPDATE if exists.
  Different databases implement this differently.

================================================================
THE PROBLEM UPSERT SOLVES
================================================================

  Without UPSERT, you need two round-trips:
  1. SELECT to check if row exists
  2. INSERT or UPDATE based on result

  Race condition: two processes can both SELECT "not found"
  and both try to INSERT --> primary key violation.

  UPSERT handles this atomically in one statement.

================================================================
POSTGRESQL: ON CONFLICT
================================================================

  ON CONFLICT DO NOTHING:
  INSERT INTO products (id, name, price)
  VALUES (1, 'Widget', 9.99)
  ON CONFLICT (id) DO NOTHING;

  ON CONFLICT DO UPDATE (EXCLUDED refers to the rejected row):
  INSERT INTO products (id, name, price)
  VALUES (1, 'Widget', 12.99)
  ON CONFLICT (id) DO UPDATE
      SET name  = EXCLUDED.name,
          price = EXCLUDED.price,
          updated_at = NOW();

  Only update if value actually changed:
  INSERT INTO products (id, name, price)
  VALUES (1, 'Widget', 12.99)
  ON CONFLICT (id) DO UPDATE
      SET price = EXCLUDED.price
  WHERE products.price <> EXCLUDED.price;

  Conflict on unique constraint name:
  INSERT INTO users (email, name)
  VALUES ('alice@example.com', 'Alice')
  ON CONFLICT ON CONSTRAINT users_email_key DO UPDATE
      SET name = EXCLUDED.name;

================================================================
MYSQL: INSERT ... ON DUPLICATE KEY UPDATE
================================================================

  INSERT INTO products (id, name, price)
  VALUES (1, 'Widget', 12.99)
  ON DUPLICATE KEY UPDATE
      name       = VALUES(name),
      price      = VALUES(price),
      updated_at = NOW();

  Note: VALUES(col) refers to the value you tried to insert.
  MySQL 8.0.19+ prefers aliases: AS new(id,name,price) + SET name=new.name

  REPLACE INTO (MySQL-specific -- deletes then inserts, loses old data):
  REPLACE INTO products (id, name, price)
  VALUES (1, 'Widget', 12.99);
  -- AVOID: triggers DELETE then INSERT, changes auto-increment, drops FK refs

================================================================
ANSI MERGE (SQL:2003 Standard)
================================================================

  MERGE INTO target_table AS tgt
  USING source_table AS src
  ON tgt.id = src.id
  WHEN MATCHED THEN
      UPDATE SET
          tgt.name  = src.name,
          tgt.price = src.price
  WHEN NOT MATCHED THEN
      INSERT (id, name, price)
      VALUES (src.id, src.name, src.price);

  With DELETE:
  MERGE INTO target_table AS tgt
  USING source_table AS src
  ON tgt.id = src.id
  WHEN MATCHED AND src.active = false THEN
      DELETE
  WHEN MATCHED THEN
      UPDATE SET tgt.name = src.name
  WHEN NOT MATCHED THEN
      INSERT (id, name) VALUES (src.id, src.name);

  Support:
  SQL Server, Oracle, DB2 -- full MERGE
  PostgreSQL               -- no MERGE until v15; use ON CONFLICT
  MySQL                    -- no standard MERGE; use ON DUPLICATE KEY

================================================================
UPSERT PATTERNS IN SPRING / JPA
================================================================

  JPA saveOrUpdate equivalent: repository.save(entity)
  - If entity has null id --> INSERT
  - If entity has non-null id --> UPDATE (or merge)

  Custom upsert with @Query (PostgreSQL):
  @Modifying
  @Query(value = """
      INSERT INTO products (id, name, price)
      VALUES (:id, :name, :price)
      ON CONFLICT (id) DO UPDATE
          SET name = EXCLUDED.name, price = EXCLUDED.price
      """, nativeQuery = true)
  void upsertProduct(long id, String name, BigDecimal price);

================================================================
COMMON USE CASES
================================================================

  1. Syncing data from external source into a table
     (ETL pipeline: source rows that may or may not exist)

  2. Idempotent writes in event-driven systems
     (replaying the same event should not create duplicates)

  3. Maintaining counters:
     INSERT INTO daily_stats (date, page, views)
     VALUES (CURRENT_DATE, '/home', 1)
     ON CONFLICT (date, page) DO UPDATE
         SET views = daily_stats.views + EXCLUDED.views;

  4. Session / cache tables: insert if new, refresh TTL if exists

================================================================
INTERVIEW Q&A
================================================================

  Q: What is UPSERT?
  A: An atomic INSERT-or-UPDATE. If the row already exists
     (based on a unique/PK conflict), update it; otherwise insert.
     Avoids race conditions inherent in separate SELECT then INSERT/UPDATE.

  Q: How does PostgreSQL implement UPSERT?
  A: `INSERT ... ON CONFLICT (col) DO UPDATE SET ...`
     EXCLUDED references the row that was rejected by the conflict.

  Q: When would you use MERGE vs ON CONFLICT?
  A: MERGE is ANSI standard and more expressive (supports DELETE).
     ON CONFLICT is PostgreSQL-specific. Use ON CONFLICT in PG,
     MERGE in SQL Server/Oracle, ON DUPLICATE KEY in MySQL.

  Q: What is the risk with REPLACE INTO?
  A: It deletes the old row then inserts a new one. This changes
     auto-increment IDs, removes rows referenced by foreign keys,
     and fires DELETE triggers. Avoid for production use.
