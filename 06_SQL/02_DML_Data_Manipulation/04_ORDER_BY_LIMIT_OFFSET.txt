================================================================
  ORDER BY, LIMIT, OFFSET — SORTING AND PAGINATION
================================================================

================================================================
ORDER BY
================================================================

  Sorts the result set. Evaluated AFTER SELECT (can use aliases).
  Default direction: ASC (ascending).

  BASIC:
  SELECT * FROM orders ORDER BY created_at DESC;      -- newest first
  SELECT * FROM products ORDER BY price ASC;          -- cheapest first
  SELECT * FROM customers ORDER BY name;              -- alphabetical (ASC default)

  MULTIPLE COLUMNS:
  SELECT * FROM products ORDER BY category_id ASC, price DESC;
  -- Sort by category first; within category, most expensive first

  ORDER BY column position (avoid in production — fragile):
  SELECT id, name, price FROM products ORDER BY 3 DESC;  -- price is column 3

  ORDER BY expression:
  SELECT id, first_name, last_name
  FROM users
  ORDER BY LOWER(last_name) ASC, LOWER(first_name) ASC;  -- case-insensitive sort

  ORDER BY CASE (custom order):
  SELECT * FROM orders
  ORDER BY
      CASE status
          WHEN 'URGENT'   THEN 1
          WHEN 'PENDING'  THEN 2
          WHEN 'SHIPPED'  THEN 3
          ELSE 4
      END;

  NULL ORDERING:
  -- PostgreSQL:
  SELECT * FROM orders ORDER BY shipped_at ASC NULLS LAST;   -- NULLs at end
  SELECT * FROM orders ORDER BY shipped_at DESC NULLS FIRST; -- NULLs at top

  -- MySQL: NULLs sort lowest (first in ASC, last in DESC)
  -- Trick for NULLs last in MySQL:
  SELECT * FROM orders ORDER BY shipped_at IS NULL ASC, shipped_at ASC;

================================================================
LIMIT AND OFFSET
================================================================

  LIMIT:  maximum number of rows to return.
  OFFSET: number of rows to skip before returning.

  -- First 10 orders:
  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;

  -- Page 1: rows 1-10
  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 0;

  -- Page 2: rows 11-20
  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 10;

  -- Page N: rows (N-1)*pageSize to N*pageSize
  -- Java: int offset = (page - 1) * pageSize;

  MySQL syntax: LIMIT offset, count
  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10, 20;  -- skip 10, return 20

================================================================
LIMIT / OFFSET PROBLEMS
================================================================

  Performance degrades at high offsets:
  LIMIT 10 OFFSET 100000 — DB still reads 100,010 rows, discards 100,000.
  Gets slower as offset increases: O(offset + limit).

  Inconsistency: rows can shift between pages if data changes between requests
  (new rows inserted, rows deleted mid-pagination).

================================================================
KEYSET PAGINATION (CURSOR-BASED) — BETTER
================================================================

  Instead of OFFSET, use the last seen row's identifier as a cursor.

  First page:
  SELECT * FROM orders
  WHERE customer_id = 42
  ORDER BY created_at DESC, id DESC
  LIMIT 10;

  Next page (using last row's values as cursor):
  SELECT * FROM orders
  WHERE customer_id = 42
    AND (created_at, id) < ('2024-01-15 14:30:00', 12345)   -- PostgreSQL row comparison
  ORDER BY created_at DESC, id DESC
  LIMIT 10;

  Benefits:
  - O(log n) with index (reads only the rows needed)
  - Stable: no rows skipped or duplicated as data changes
  - Works efficiently at any depth (page 10,000 as fast as page 1)

  Limitation:
  - No arbitrary jump to page N (sequential only)
  - Requires consistent ordering column (include ID as tiebreaker)

================================================================
TOP (SQL SERVER)
================================================================

  SQL Server uses TOP instead of LIMIT:
  SELECT TOP 10 * FROM orders ORDER BY created_at DESC;
  SELECT TOP 10 PERCENT * FROM orders ORDER BY total DESC;

  FETCH FIRST (ANSI SQL / DB2 / Oracle 12+):
  SELECT * FROM orders ORDER BY created_at DESC FETCH FIRST 10 ROWS ONLY;

PRACTICAL SPRING DATA JPA PAGINATION
================================================================

  Pageable pageable = PageRequest.of(0, 10, Sort.by("createdAt").descending());
  Page<Order> page = orderRepository.findAll(pageable);

  page.getContent()       → List<Order> for current page
  page.getTotalElements() → total rows
  page.getTotalPages()    → total pages
  page.getNumber()        → current page (0-indexed)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the problem with LIMIT/OFFSET pagination at high offsets?
  A: The database scans and discards offset rows before returning results,
     making performance O(offset). At page 1000 with page size 20,
     it reads 20,000 rows and discards 19,980.

  Q: What is keyset pagination?
  A: Instead of OFFSET, use the last seen row's value (e.g., created_at + id)
     as a cursor in the WHERE clause. Index-backed lookup → O(log n) at any depth.

  Q: How do you sort NULLs last in PostgreSQL?
  A: ORDER BY col ASC NULLS LAST

  Q: How do you implement custom sort order (e.g., specific status order)?
  A: ORDER BY CASE WHEN status='URGENT' THEN 1 WHEN status='PENDING' THEN 2 ELSE 3 END

  Q: Can you use a SELECT alias in ORDER BY?
  A: Yes. ORDER BY is evaluated after SELECT, so aliases defined in SELECT
     are available in ORDER BY.
