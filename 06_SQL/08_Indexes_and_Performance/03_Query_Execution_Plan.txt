================================================================
  QUERY EXECUTION PLAN (EXPLAIN / EXPLAIN ANALYZE)
================================================================

  The execution plan shows HOW the database will (or did) execute a query.
  Understanding it is essential for performance tuning.

================================================================
COMMANDS
================================================================

  PostgreSQL:
  EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
  EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
  EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT ...;

  EXPLAIN          -- shows estimated plan (no actual execution)
  EXPLAIN ANALYZE  -- actually runs the query and shows real timings
  BUFFERS          -- shows I/O (shared blocks hit/read)
  FORMAT JSON      -- machine-readable format for tools

  MySQL:
  EXPLAIN SELECT * FROM orders WHERE customer_id = 42;
  EXPLAIN FORMAT=JSON SELECT ...;
  EXPLAIN ANALYZE SELECT ... (MySQL 8.0.18+);

  SQL Server:
  SET STATISTICS IO ON;
  SET STATISTICS TIME ON;
  ... query ...
  -- Or use graphical "Actual Execution Plan" in SSMS

================================================================
KEY CONCEPTS IN PLAN OUTPUT
================================================================

  Node type      Operation the planner chose
  Cost           Estimated cost (startup_cost..total_cost)
  Rows           Estimated row count
  Actual Time    Real execution time (ANALYZE only)
  Loops          How many times the node was executed
  Buffers        Pages read from disk vs. cache (BUFFERS option)

================================================================
COMMON PLAN NODES
================================================================

  Node                  Meaning
  ------------------    -------------------------------------------
  Seq Scan              Full table scan (no index used)
  Index Scan            B-tree index + heap fetch for each row
  Index Only Scan       All needed columns in index; no heap fetch
  Bitmap Heap Scan      Bulk fetch using bitmap of matching pages
  Bitmap Index Scan     Build bitmap from index (precedes BitmapHeap)
  Nested Loop           For each outer row, scan inner (fast if inner indexed)
  Hash Join             Build hash table from inner, probe with outer
  Merge Join            Sort both sides, merge (efficient for large sorted sets)
  Sort                  Explicit sort (look for this in plans with ORDER BY)
  Hash Aggregate        GROUP BY with hash table
  Gather               Parallel worker coordination

================================================================
READING PLAN COST
================================================================

  (cost=0.43..8.45 rows=1 width=64)

  0.43    = startup cost (before first row returned)
  8.45    = total cost (to return all rows)
  rows=1  = estimated rows
  width=64 = estimated row size in bytes

  Costs are in relative units, not milliseconds.
  High startup cost = bad for LIMIT queries.

================================================================
EXAMPLE ANALYSIS
================================================================

  EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;

  Index Scan using idx_orders_customer on orders
      (cost=0.43..8.45 rows=3 width=64)
      (actual time=0.014..0.021 rows=3 loops=1)
    Index Cond: (customer_id = 42)
  Planning Time: 0.128 ms
  Execution Time: 0.041 ms

  GOOD: Using index, low cost, fast execution.

  Seq Scan on orders  (cost=0.00..18543.00 rows=1000000 width=64)
  Filter: (customer_id = 42)
  Rows Removed by Filter: 999997

  BAD: Full scan of 1M rows to find 3. Add index on customer_id.

================================================================
WHEN PLANNER IGNORES INDEX
================================================================

  Planner may choose full scan over index when:
  - Query returns large % of rows (threshold ~10-15%)
  - Table is very small (full scan cheaper than index overhead)
  - Statistics are stale (run ANALYZE to update)
  - Function applied to column: WHERE LOWER(name) = 'alice' (no functional index)
  - Type mismatch: WHERE bigint_col = '42'::varchar (cast disables index)
  - Index not selective enough

  Force index check (do not use in production):
  SET enable_seqscan = off;   -- PostgreSQL: force index usage for testing

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between EXPLAIN and EXPLAIN ANALYZE?
  A: EXPLAIN shows the estimated execution plan.
     EXPLAIN ANALYZE actually executes the query and shows actual
     row counts and timings. Use ANALYZE to find where estimates are wrong.

  Q: What is a Seq Scan and when is it bad?
  A: Seq Scan reads every row in the table. Bad when table is large
     and query is selective. Add an index to avoid it.
     NOT always bad for small tables or when returning most rows.

  Q: What is the difference between Index Scan and Index Only Scan?
  A: Index Scan uses the index to find row pointers, then fetches
     each row from the heap (two reads per row).
     Index Only Scan finds all needed data in the index itself
     (covering index), no heap fetch required.
