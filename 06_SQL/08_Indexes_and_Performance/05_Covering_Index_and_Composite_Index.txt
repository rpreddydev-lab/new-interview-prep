================================================================
  COVERING INDEX AND COMPOSITE INDEX
================================================================

================================================================
COVERING INDEX
================================================================

  A covering index contains ALL columns needed by a query.
  The database can answer the query from the index alone,
  without fetching the actual table row (no heap fetch).

  Query: SELECT id, status FROM orders WHERE customer_id = 42;
  Columns needed: customer_id (filter), id, status (select)

  Index: CREATE INDEX ON orders(customer_id, id, status);
  -- All needed columns are in the index: INDEX ONLY SCAN

  Without covering index:
  1. Scan index for customer_id = 42 --> get row pointers
  2. Fetch each row from heap to get id and status
  --> N heap fetches for N matching rows

  With covering index:
  1. Scan index for customer_id = 42
  2. Read id and status directly from index leaves
  --> 0 heap fetches

================================================================
PostgreSQL INCLUDE CLAUSE
================================================================

  PostgreSQL 11+: INCLUDE columns are stored in leaf nodes
  but not in the internal nodes (do not affect search/sort).

  CREATE INDEX idx_orders_customer_covering
  ON orders(customer_id) INCLUDE (id, status, total);

  Benefits:
  - customer_id used for searching/filtering
  - id, status, total available in index for SELECT without heap fetch
  - INCLUDE columns don't increase internal node size
  - Cannot filter on INCLUDE columns (they are "payload" only)

================================================================
COMPOSITE INDEX
================================================================

  A composite (multi-column) index covers queries on multiple columns.
  Column order determines which queries can use the index.

  CREATE INDEX idx_orders_cust_status ON orders(customer_id, status);

  Queries that USE this index:
  WHERE customer_id = 42                          -- leftmost prefix
  WHERE customer_id = 42 AND status = 'PENDING'   -- full prefix
  WHERE customer_id BETWEEN 10 AND 50             -- range on leftmost
  ORDER BY customer_id, status                    -- ordered scan

  Queries that CANNOT use this index:
  WHERE status = 'PENDING'                        -- skips customer_id
  WHERE status = 'PENDING' AND customer_id = 42   -- order doesn't matter
  ORDER BY status                                 -- status not leftmost

================================================================
LEFTMOST PREFIX RULE
================================================================

  For index (a, b, c):
  Supported:            a    |  a,b  |  a,b,c
  NOT supported:        b    |  b,c  |  c

  Works for:
  - Equality on leading columns + range on first non-equality
  - (a=? AND b=? AND c=?) -- all equality, all supported
  - (a=? AND b BETWEEN ? AND ?) -- equality on a, range on b, c unused

================================================================
INDEX DESIGN STRATEGIES
================================================================

  Strategy 1: Equality-first, range-second, include the rest.
  Query: WHERE status = 'PENDING' AND created_at > '2024-01-01' ORDER BY total
  Index: (status, created_at) INCLUDE (total, id)

  Strategy 2: Order of equality columns by selectivity (more selective first).
  category_id (100 categories) + status (5 statuses)
  --> (category_id, status) is better than (status, category_id)

  Strategy 3: Match ORDER BY to avoid sort node in plan.
  If query has ORDER BY customer_id, created_at, put those in index.

================================================================
DUPLICATE AND REDUNDANT INDEXES
================================================================

  Redundant: (a) is redundant if (a, b) exists -- (a) is a prefix
  Duplicate: identical index defined twice -- wastes disk and write cost

  PostgreSQL: detect redundant indexes:
  SELECT indrelid::regclass, indexrelid::regclass, pg_get_indexdef(indexrelid)
  FROM pg_index
  WHERE indrelid = 'orders'::regclass;

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a covering index?
  A: An index that contains all columns needed by a query
     (filter, join, and select columns). Enables index-only scan,
     eliminating the need to fetch rows from the table heap.

  Q: What is the leftmost prefix rule for composite indexes?
  A: A composite index (a, b, c) can be used for queries filtering
     on a, or a+b, or a+b+c, but NOT on b alone or c alone.
     The query must include the leftmost column(s) of the index.

  Q: What is the difference between including a column in the key vs INCLUDE?
  A: Key columns (a, b) are used for searching, sorting, and filtering.
     INCLUDE columns (PostgreSQL) are stored only in leaf nodes as payload
     -- available in index-only scans but not usable for filtering or ordering.
     INCLUDE keeps internal node size smaller.
