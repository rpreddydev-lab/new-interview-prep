================================================================
  INDEXES: OVERVIEW
================================================================

  An index is a separate data structure that allows the database
  to find rows without scanning the entire table.

================================================================
WHY INDEXES
================================================================

  Without index: full table scan -- O(n) rows checked.
  With index: B-tree lookup or hash lookup -- O(log n) or O(1).

  For a table with 10 million rows:
  Full scan: may read 10M rows
  B-tree index: about 24 comparisons (log2 of 10M ≈ 23)

================================================================
HOW B-TREE INDEX WORKS
================================================================

  B-tree = Balanced tree structure
  Leaves: contain the indexed column value + row pointer (CTID / RID)
  Internal nodes: guide search to correct leaf

        [50]
       /    \
    [20,35]  [70,90]
    /  |  \  /  |  \
  [10][25][40][60][80][95]

  Finding "salary = 25": traverse from root in O(log n).
  Range query "salary BETWEEN 20 AND 50": traverse to first value,
  then scan leaf nodes (linked list) until out of range.

================================================================
WHEN INDEXES HELP
================================================================

  Queries that BENEFIT from indexes:
  - Equality: WHERE id = 42
  - Range: WHERE salary BETWEEN 50000 AND 80000
  - Sorting: ORDER BY last_name (index = presorted)
  - Join: JOIN ON a.customer_id = b.id (FK indexed)
  - Prefix search: WHERE name LIKE 'Smith%'

  Queries that do NOT benefit from indexes:
  - Leading wildcard: WHERE name LIKE '%Smith%'
  - Function on column: WHERE LOWER(email) = 'alice@example.com'
  - Low-cardinality column with many matches: WHERE active = true (50%)
  - Small table (full scan faster due to overhead)

================================================================
COST OF INDEXES
================================================================

  Benefit: faster SELECT (and some UPDATE/DELETE via faster lookup)
  Cost:
  - Extra disk space (typically 10-30% of table size)
  - Slower INSERT/UPDATE/DELETE (index must be maintained)
  - More memory usage (buffer cache)

  Rule: create indexes based on actual query patterns, not preemptively.
  Too many indexes can actually slow down write-heavy tables.

================================================================
CREATING AND MANAGING
================================================================

  Create:
  CREATE INDEX idx_orders_customer ON orders(customer_id);
  CREATE UNIQUE INDEX idx_users_email ON users(email);

  Drop:
  DROP INDEX idx_orders_customer;

  PostgreSQL concurrent build (no table lock):
  CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);

  List indexes:
  \di               -- psql command
  SELECT * FROM pg_indexes WHERE tablename = 'orders';

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a database index?
  A: A separate data structure (typically B-tree) that stores column
     values with pointers to table rows, enabling fast lookup without
     full table scan.

  Q: What are the trade-offs of adding an index?
  A: Faster reads (SELECTs, JOINs, ORDER BY), but slower writes
     (INSERT/UPDATE/DELETE must maintain the index) and extra disk/memory.

  Q: Why should foreign key columns always be indexed?
  A: JOIN operations on FK columns do full scans if not indexed.
     Also, DELETE from parent table checks for child rows -- without index,
     this requires a full scan of the child table for every parent delete.
