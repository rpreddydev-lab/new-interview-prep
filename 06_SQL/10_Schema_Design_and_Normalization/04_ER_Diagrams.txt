================================================================
  ENTITY-RELATIONSHIP (ER) DIAGRAMS
================================================================

  ER diagrams visually model database structure:
  entities, attributes, and relationships.

================================================================
CORE CONCEPTS
================================================================

  Entity      A real-world object with distinct existence.
              Becomes a table. Example: Customer, Order, Product

  Attribute   A property of an entity.
              Becomes a column. Example: Customer.email, Order.total

  Relationship Association between entities.
              Becomes a FK or junction table.

  Key attribute  Uniquely identifies an entity instance (underlined in ER).
                 Becomes PK.

================================================================
CARDINALITY NOTATION
================================================================

  One-to-One (1:1)
  Each customer has at most one billing profile.
  customer <----> billing_profile

  One-to-Many (1:N)
  One customer can have many orders.
  customer <----< orders

  Many-to-Many (M:N)
  Orders can have many products; products can be on many orders.
  orders >----< products
  Implemented with a junction table: order_items(order_id, product_id)

================================================================
CROW'S FOOT NOTATION (MOST COMMON)
================================================================

  Symbol    Meaning
  |         Exactly one (mandatory)
  O         Zero (optional)
  <  (fork) Many

  customer ||----o< orders
  "One customer has zero or many orders"
  "Each order belongs to exactly one customer"

================================================================
ENTITIES AND RELATIONSHIPS: E-COMMERCE EXAMPLE
================================================================

  Entities: Customer, Order, Product, Category, Address

  Customer:
  - id (PK), name, email, created_at
  - 1:N with Order (one customer, many orders)
  - 1:N with Address (one customer, many addresses)

  Order:
  - id (PK), customer_id (FK), shipping_address_id (FK), total, status
  - M:N with Product via order_items junction
  - N:1 with Customer

  Product:
  - id (PK), name, price, stock_quantity, category_id (FK)
  - N:1 with Category
  - M:N with Order

  order_items (junction):
  - (order_id, product_id) composite PK
  - qty, unit_price (denormalized snapshot of price at order time)

  Category:
  - id (PK), name, parent_id (FK to self -- self-referential)
  - N:1 with itself (hierarchical categories)

================================================================
MAPPING ER TO TABLES
================================================================

  1. Each entity --> one table; key attribute --> PK

  2. 1:N relationship --> FK in the "N" side table
     (Order has customer_id FK pointing to Customer PK)

  3. M:N relationship --> junction table with FKs to both entities
     (order_items with order_id + product_id)

  4. 1:1 relationship --> FK in either table (usually the weaker/dependent one)
     or merge into one table if always together

  5. Self-referential --> FK in same table
     (employees.manager_id references employees.id)

================================================================
WEAK ENTITY
================================================================

  A weak entity cannot be uniquely identified by its own attributes alone.
  It depends on a strong (owner) entity.
  Example: order_items cannot exist without an order.

  In SQL: composite PK including the owner's PK as FK:
  order_items PRIMARY KEY (order_id, product_id)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a Many-to-Many relationship and how is it implemented in SQL?
  A: When each row in table A can relate to many rows in B and vice versa.
     Implemented with a junction/bridge table containing FK columns
     pointing to both tables.

  Q: What is a weak entity?
  A: An entity that cannot be uniquely identified by its own attributes.
     Depends on a "strong" entity. In SQL, its PK includes the owner's PK as FK.

  Q: How would you design a self-referential relationship?
  A: Add a FK column in the same table pointing to the PK of the same table.
     employees.manager_id REFERENCES employees(id)
