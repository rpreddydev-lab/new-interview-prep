================================================================
  AUTOCOMMIT AND IMPLICIT TRANSACTIONS
================================================================

  Autocommit: every DML statement is automatically committed
  immediately after execution if no explicit transaction is open.
  This is the DEFAULT in most databases.

================================================================
DATABASE DEFAULTS
================================================================

  Database        Default Autocommit
  ------------    ------------------
  MySQL           ON  (each statement is its own transaction)
  PostgreSQL      ON  (each statement auto-committed)
  SQL Server      ON  (unless inside explicit BEGIN TRANSACTION)
  Oracle          OFF (statements accumulate until COMMIT/ROLLBACK)
  JDBC default    ON  (connection.getAutoCommit() == true)

================================================================
DISABLING AUTOCOMMIT
================================================================

  SQL:
  SET autocommit = 0;   -- MySQL
  -- In PostgreSQL, just use BEGIN; to start explicit block
  -- In SQL Server: SET IMPLICIT_TRANSACTIONS ON;

  JDBC:
  connection.setAutoCommit(false);
  -- Now all statements accumulate until commit() or rollback()

  Spring / JPA:
  @Transactional            -- Spring disables autocommit for the block
  public void doWork() { ... }

================================================================
AUTOCOMMIT TRAP: PARTIAL SUCCESS
================================================================

  Without explicit transaction (autocommit ON):
  INSERT INTO orders (customer_id, total) VALUES (42, 99);
  -- autocommit: this is immediately committed
  INSERT INTO order_items (order_id, product_id) VALUES (999, 5);
  -- if this fails, the orders row is ALREADY committed
  -- data is now inconsistent

  With explicit transaction:
  BEGIN;
    INSERT INTO orders ...;
    INSERT INTO order_items ...;
  COMMIT;
  -- Both committed together, or both rolled back

================================================================
DDL AND AUTOCOMMIT
================================================================

  In MySQL:
  DDL (CREATE TABLE, ALTER TABLE, DROP TABLE) causes an implicit COMMIT
  before and after the statement. You cannot rollback DDL in MySQL.

  In PostgreSQL:
  DDL IS transactional. You CAN rollback a CREATE TABLE within a transaction.

  BEGIN;
    CREATE TABLE temp_test (id INT);
    INSERT INTO temp_test VALUES (1);
  ROLLBACK;
  -- temp_test does NOT exist -- DDL was rolled back

  This is why Flyway/Liquibase work differently on MySQL vs PostgreSQL.

================================================================
IMPLICIT TRANSACTION START
================================================================

  SQL Server: IMPLICIT_TRANSACTIONS ON
  Every DML starts a transaction automatically.
  You must COMMIT or ROLLBACK explicitly.
  Forgetting COMMIT leaves a dangling open transaction that blocks others.

  Most developers prefer autocommit=ON + explicit BEGIN/COMMIT blocks
  rather than implicit transaction mode.

================================================================
SPRING TRANSACTION MANAGEMENT
================================================================

  Spring's @Transactional:
  1. Gets connection from pool
  2. Sets autocommit = false
  3. Executes method body
  4. On success: calls connection.commit()
  5. On RuntimeException: calls connection.rollback()
  6. Returns connection to pool with autocommit restored

  IMPORTANT: @Transactional on a private method does NOTHING.
  Spring uses a proxy -- the proxy wraps the bean, but private methods
  are called directly on the target, bypassing the proxy.

  IMPORTANT: self-invocation bypasses proxy:
  this.transactionalMethod()   -- NO transaction
  Must inject self or use separate bean.

================================================================
OPTIMISTIC vs PESSIMISTIC LOCKING
================================================================

  These are related to transactions and concurrency:

  Optimistic: assume no conflict; check at commit time.
  - Add version column: @Version in JPA
  - On UPDATE: WHERE id = ? AND version = ?
  - If version mismatch: throw OptimisticLockException, retry

  Pessimistic: lock the row immediately when read.
  - SELECT ... FOR UPDATE   -- locks rows until transaction ends
  - JPA: LockModeType.PESSIMISTIC_WRITE
  - Prevents concurrent modifications but reduces throughput

================================================================
INTERVIEW Q&A
================================================================

  Q: What is autocommit?
  A: Mode where each DML statement is automatically committed.
     It is the default. Explicit BEGIN + COMMIT disables it temporarily.

  Q: Why is autocommit dangerous for multi-step operations?
  A: If step 1 is auto-committed and step 2 fails, you have partial data
     with no way to undo step 1. Always use explicit transactions for
     operations that must succeed or fail together.

  Q: What happens to autocommit when Spring @Transactional is used?
  A: Spring sets autocommit=false on the connection, wraps the method
     in a transaction, then commits on success or rolls back on unchecked
     exception. Autocommit is restored when the connection returns to pool.

  Q: Can you rollback DDL in PostgreSQL?
  A: Yes. PostgreSQL has fully transactional DDL. You can CREATE a table
     and ROLLBACK to undo it. MySQL does NOT support transactional DDL.
