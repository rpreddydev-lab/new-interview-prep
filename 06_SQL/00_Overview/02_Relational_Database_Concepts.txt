================================================================
  RELATIONAL DATABASE CONCEPTS
================================================================

  The relational model was invented by E.F. Codd at IBM (1970).
  Based on set theory and first-order predicate logic.

================================================================
CORE CONCEPTS
================================================================

  RELATION (TABLE):
  A named 2-dimensional structure with rows and columns.
  Mathematically: a set of tuples.
  Each row is unique (no duplicates in pure relational model).

  TUPLE (ROW / RECORD):
  A single entry in a table.
  All fields have a value (or NULL for unknown/absent).

  ATTRIBUTE (COLUMN / FIELD):
  A named, typed property of a relation.
  Each column has a domain (allowed values): INTEGER, VARCHAR(255), DATE, etc.

  DOMAIN:
  The set of allowed values for an attribute.
  Enforced by: data type, constraints, CHECK, FOREIGN KEY.

  SCHEMA:
  The structure definition of a database — the set of tables,
  their columns, data types, and constraints.
  "Schema-on-write" — structure defined before data.

================================================================
KEYS
================================================================

  CANDIDATE KEY:
  Minimal set of attributes that uniquely identifies each row.
  (One or more columns — all together must be unique and minimal.)

  PRIMARY KEY:
  The candidate key chosen to be the main identifier.
  Constraints: NOT NULL, UNIQUE.
  Best practice: surrogate key (auto-increment INT or UUID) for stability.

  NATURAL KEY:
  A primary key made of real-world data (email, SSN, ISBN).
  Pros: no extra column; Cons: can change (email can change), can be long.

  SURROGATE KEY:
  An artificial key added solely to identify rows (id INT AUTO_INCREMENT).
  Pros: stable, short, indexed efficiently.
  Cons: no inherent meaning.

  COMPOSITE KEY:
  A primary key made of multiple columns.
  Example: (order_id, line_item_id) uniquely identifies an order line.

  FOREIGN KEY:
  A column (or columns) that references the primary key of another table.
  Enforces REFERENTIAL INTEGRITY.
  Example: order.customer_id → customer.id

  UNIQUE KEY:
  Like a secondary candidate key. NOT NULL optional. Can have multiple per table.
  Example: user.email is UNIQUE but not the primary key.

================================================================
INTEGRITY CONSTRAINTS
================================================================

  ENTITY INTEGRITY:
  Primary key values must be unique and NOT NULL.
  Every row is uniquely identifiable.

  REFERENTIAL INTEGRITY:
  Foreign key values must either match an existing primary key value
  or be NULL. No orphaned foreign key references.

  ON DELETE CASCADE / RESTRICT / SET NULL:
  What happens to dependent rows when parent is deleted:
  CASCADE    → delete child rows automatically
  RESTRICT   → prevent parent deletion if children exist
  SET NULL   → set FK column to NULL in children

  DOMAIN INTEGRITY:
  Column values must be in the domain (type, length, range).
  Enforced by: data type, CHECK constraints.

  CHECK CONSTRAINT:
  Custom column-level or table-level constraint:
  CHECK (salary > 0)
  CHECK (start_date < end_date)

================================================================
RELATIONSHIPS
================================================================

  ONE-TO-ONE (1:1):
  Each row in A relates to at most one row in B.
  Implemented: FK in one table + UNIQUE constraint on FK.
  Example: User → UserProfile (each user has exactly one profile).

  ONE-TO-MANY (1:N):
  Each row in A relates to many rows in B; each B row has one A.
  Most common relationship.
  Implemented: FK in the "many" table.
  Example: Customer (1) → Orders (N).

  MANY-TO-MANY (M:N):
  Each row in A relates to many in B, and vice versa.
  Implemented via JUNCTION TABLE (associative entity):
  Example: Student → Enrollment ← Course
  CREATE TABLE enrollment (
      student_id INT REFERENCES student(id),
      course_id  INT REFERENCES course(id),
      enrolled_at TIMESTAMP,
      PRIMARY KEY (student_id, course_id)
  );

================================================================
NORMALIZATION FORMS (BRIEF INTRO)
================================================================

  The process of organizing data to reduce redundancy and dependency.
  Full coverage in 10_Schema_Design_and_Normalization.

  1NF: No repeating groups; atomic values.
  2NF: 1NF + no partial dependency on composite key.
  3NF: 2NF + no transitive dependency (non-key → non-key).
  BCNF: Stronger 3NF.
  4NF: No multi-valued dependencies.

  Practical target: 3NF or BCNF for OLTP.
  Analytics (OLAP): denormalize for query performance (star schema).

================================================================
ACID PROPERTIES
================================================================

  Atomicity:    All operations in a transaction succeed, or all fail.
  Consistency:  DB moves from one valid state to another.
  Isolation:    Concurrent transactions behave as if sequential.
  Durability:   Committed data survives failures (persisted to disk/log).

  Example (bank transfer):
  BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
  COMMIT;

  If the second UPDATE fails, the first is rolled back.
  Money can't disappear or be created.

================================================================
INDEXES
================================================================

  Index: auxiliary data structure (usually B-tree) on one or more
  columns that speeds up lookup at the cost of write overhead.

  Without index: full table scan O(n).
  With index: B-tree lookup O(log n).

  PRIMARY KEY: automatically indexed.
  FOREIGN KEY: should be indexed (for join performance).
  Common query columns (WHERE, ORDER BY, GROUP BY): candidate for index.

  Covering index: includes all columns needed by a query
  → query answered from index alone without table access.

================================================================
VIEWS
================================================================

  A named saved SELECT query. Acts like a virtual table.
  CREATE VIEW customer_orders AS
  SELECT c.name, o.id, o.total, o.status
  FROM customers c JOIN orders o ON c.id = o.customer_id;

  Uses:
  - Simplify complex queries
  - Restrict visible columns for security
  - Present a stable API while underlying schema changes

  Materialized View: view result physically stored and refreshed periodically.
  Much faster for read-heavy analytics; stale by design.

================================================================
INTERVIEW Q&A
================================================================

  Q: What is referential integrity?
  A: Foreign key values must match an existing primary key or be NULL.
     Prevents orphaned records. Enforced at DB level with FOREIGN KEY constraint.

  Q: What is the difference between primary key and unique key?
  A: Primary key: NOT NULL + UNIQUE; one per table; main row identifier.
     Unique key: values must be unique but can be NULL; multiple per table.

  Q: What is a junction table?
  A: An intermediate table implementing a many-to-many relationship.
     Contains foreign keys to both sides, plus any relationship attributes.

  Q: What are ACID properties?
  A: Atomicity (all or nothing), Consistency (valid state → valid state),
     Isolation (concurrent txns don't interfere), Durability (committed data survives failure).

  Q: What is the difference between a natural key and a surrogate key?
  A: Natural key: real-world data (email, SSN) — can change, may be complex.
     Surrogate key: artificial identifier (auto-increment int or UUID) — stable, simple.
