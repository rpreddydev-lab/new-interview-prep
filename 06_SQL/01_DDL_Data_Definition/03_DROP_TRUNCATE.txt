================================================================
  DROP vs TRUNCATE — DDL
================================================================

================================================================
DROP
================================================================

  Permanently removes a database object AND its data.
  In most RDBMS, DDL auto-commits — DROP cannot be rolled back.
  (PostgreSQL exception: DROP inside BEGIN/COMMIT can be rolled back.)

  DROP TABLE:
  DROP TABLE orders;              -- error if table doesn't exist
  DROP TABLE IF EXISTS orders;    -- safe; no error if missing

  DROP TABLE orders CASCADE;      -- drops dependent objects too (views, FKs that reference it)
  DROP TABLE orders RESTRICT;     -- fails if other objects depend on it (default)

  DROP other objects:
  DROP INDEX idx_orders_status;
  DROP VIEW customer_orders;
  DROP SCHEMA myapp CASCADE;      -- drops schema + all its tables
  DROP DATABASE legacy_app;       -- drops entire database

  CAUTION: DROP is irreversible. In production:
  1. Always take a backup first.
  2. Use IF EXISTS to avoid errors in scripts.
  3. Check for dependent objects before dropping.

================================================================
TRUNCATE
================================================================

  Removes ALL rows from a table, but keeps the table structure.
  Faster than DELETE because:
  - Does not scan row by row
  - Does not generate individual row-level undo log entries
  - Resets SERIAL/AUTO_INCREMENT counters

  TRUNCATE TABLE audit_log;
  TRUNCATE TABLE orders, order_items;    -- truncate multiple at once

  TRUNCATE TABLE orders CASCADE;         -- also truncates tables with FK to orders
  TRUNCATE TABLE orders RESTART IDENTITY;  -- reset auto-increment sequence

  Key differences across RDBMS:
  PostgreSQL:  TRUNCATE is transactional — can be inside BEGIN/ROLLBACK.
  MySQL:       TRUNCATE auto-commits; cannot be rolled back; doesn't fire triggers.
  Oracle:      TRUNCATE auto-commits; DDL.
  SQL Server:  TRUNCATE not logged per-row; can be rolled back if in explicit tx.

================================================================
DROP vs DELETE vs TRUNCATE — COMPARISON
================================================================

  Feature                 DROP TABLE       TRUNCATE         DELETE
  ----------------------  ---------------  ---------------  ----------------------
  Removes structure?      YES              NO               NO
  Removes all data?       YES (with table) YES              Depends on WHERE
  WHERE clause?           NO               NO               YES
  Can be rolled back?     PG: yes; others: no   PG: yes; MySQL: no   YES (transactional)
  Fires triggers?         NO               NO (most DBs)    YES
  Resets auto-increment?  N/A              YES              NO
  Speed                   Fast             Fast             Slow (row by row)
  Logged per row?         NO               NO               YES

================================================================
WHEN TO USE EACH
================================================================

  DROP TABLE:
  - Removing a table permanently (schema migration)
  - Cleaning up temporary or test tables
  - Part of a destructive migration step

  TRUNCATE:
  - Clear all rows quickly for re-seeding (test environments, staging)
  - Reset lookup/config tables during data refresh
  - When DELETE performance is unacceptable on large tables

  DELETE:
  - Removing specific rows (WHERE condition)
  - When you need triggers to fire
  - When you need to rollback the operation
  - Auditing: DELETE generates individual log entries

================================================================
SAFETY TIPS
================================================================

  In scripts: always use IF EXISTS to prevent errors:
  DROP TABLE IF EXISTS tmp_staging;
  DROP INDEX IF EXISTS idx_tmp;

  In production migrations:
  - Never run DROP in same transaction as schema changes unless protected
  - Prefer renaming first: RENAME TO orders_deprecated
  - Wait until code no longer references it, then drop

  Test before running on production:
  BEGIN;
  TRUNCATE TABLE orders;
  -- Review: SELECT COUNT(*) FROM orders;
  ROLLBACK;  -- safe in PostgreSQL

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between DROP, TRUNCATE, and DELETE?
  A: DROP removes the table structure and all data permanently.
     TRUNCATE removes all rows fast without individual row logging,
     keeps structure, resets sequences; can't be rolled back in MySQL.
     DELETE removes specific rows (with WHERE), transactional, fires triggers.

  Q: Why is TRUNCATE faster than DELETE?
  A: TRUNCATE deallocates data pages directly, no row-by-row log entries,
     no row-level locking. DELETE processes each row individually,
     generates undo log for each, fires triggers.

  Q: Can TRUNCATE be rolled back?
  A: In PostgreSQL: yes (DDL is transactional). In MySQL: no (auto-commits).
     Know your database — this is a common interview gotcha.

  Q: When would you use TRUNCATE over DELETE?
  A: When you need to delete ALL rows quickly (e.g., clearing a staging table),
     don't need triggers to fire, don't need a WHERE condition, and want
     auto-increment reset. Tests, data refreshes, ETL staging tables.
