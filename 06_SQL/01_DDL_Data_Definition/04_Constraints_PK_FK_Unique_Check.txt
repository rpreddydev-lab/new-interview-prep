================================================================
  CONSTRAINTS — PK, FK, UNIQUE, CHECK, NOT NULL
================================================================

  Constraints enforce data integrity rules at the database level.
  They prevent invalid data from entering the database regardless
  of what the application does.

  "Enforce constraints at the DB layer — applications have bugs,
   networks fail, manual edits happen."

================================================================
PRIMARY KEY (PK)
================================================================

  Uniquely identifies each row in a table.
  Implies: NOT NULL + UNIQUE.
  A table can have only ONE primary key (but it can be composite).

  Column-level:
  id BIGSERIAL PRIMARY KEY

  Table-level:
  PRIMARY KEY (order_id, product_id)      -- composite PK

  Best practices:
  - Surrogate key (auto-increment or UUID) is usually better than natural key.
  - Use BIGINT for tables that could grow large.
  - UUID: better for distributed systems (no coordination needed), but larger index.
  - Name convention: id (or table_name_id)

  UUID example (PostgreSQL):
  CREATE TABLE events (
      id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      ...
  );

================================================================
FOREIGN KEY (FK)
================================================================

  A column that references the primary key of another table.
  Enforces referential integrity: no orphaned child records.

  Syntax:
  customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE RESTRICT

  Or as named table constraint:
  CONSTRAINT fk_orders_customer
      FOREIGN KEY (customer_id) REFERENCES customers(id)
      ON DELETE RESTRICT
      ON UPDATE CASCADE

  ON DELETE / ON UPDATE actions:
  RESTRICT    Block deletion if children exist (safe default)
  CASCADE     Delete/update children automatically
  SET NULL    Set FK to NULL in children (FK must allow NULL)
  SET DEFAULT Set FK to default value in children
  NO ACTION   Same as RESTRICT but deferred check

  FK guidelines:
  - Always index FK columns (critical for join performance)
  - Choose ON DELETE action carefully:
    CASCADE   for strong composition (order_items → orders)
    RESTRICT  for independent entities (orders → customers)
    SET NULL  for optional relationships

================================================================
UNIQUE CONSTRAINT
================================================================

  Column values must be distinct across all rows.
  Unlike PK: allows one NULL (NULL ≠ NULL by definition).
  Multiple unique constraints per table allowed.

  Column-level:
  email VARCHAR(255) UNIQUE

  Table-level named constraint:
  CONSTRAINT uk_products_sku UNIQUE (sku)

  Multi-column unique:
  CONSTRAINT uk_enrollment UNIQUE (student_id, course_id)

  Note: UNIQUE constraint automatically creates an index.

================================================================
NOT NULL CONSTRAINT
================================================================

  Column must have a value — cannot store NULL.
  Simplest constraint; most columns should be NOT NULL.

  email VARCHAR(255) NOT NULL
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING'

  Adding NOT NULL to existing column (requires all existing rows to have values):
  UPDATE customers SET phone = '' WHERE phone IS NULL;   -- fix existing NULLs
  ALTER TABLE customers ALTER COLUMN phone SET NOT NULL;  -- then add constraint

================================================================
CHECK CONSTRAINT
================================================================

  Custom validation expression. Column-level or table-level.
  Must evaluate to TRUE for the row to be accepted.

  Simple column-level:
  price DECIMAL(10,2) CHECK (price >= 0)
  quantity INTEGER CHECK (quantity > 0)

  Named check:
  CONSTRAINT chk_salary_range CHECK (salary BETWEEN 0 AND 10000000)
  CONSTRAINT chk_email_format CHECK (email LIKE '%@%')

  Multi-column check (table-level):
  CONSTRAINT chk_date_order CHECK (start_date <= end_date)
  CONSTRAINT chk_order_status CHECK (status IN ('PENDING','SHIPPED','DELIVERED','CANCELLED'))

  Postgres domain example (reusable check):
  CREATE DOMAIN positive_money AS DECIMAL(12,2) CHECK (VALUE >= 0);
  price positive_money NOT NULL

================================================================
DEFAULT CONSTRAINT
================================================================

  Provides a fallback value when none is given in INSERT:

  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  status     VARCHAR(20) DEFAULT 'PENDING'
  is_active  BOOLEAN DEFAULT TRUE
  retry_count INTEGER DEFAULT 0

================================================================
DEFERRABLE CONSTRAINTS (PostgreSQL)
================================================================

  By default, constraints checked after each statement.
  DEFERRABLE constraints can be checked at COMMIT time:

  CONSTRAINT fk_parent FOREIGN KEY (parent_id) REFERENCES parent(id)
  DEFERRABLE INITIALLY DEFERRED;

  Use case: inserting records that mutually reference each other.

================================================================
CONSTRAINT SUMMARY TABLE
================================================================

  Constraint    Enforces                           Multiple per table?
  ----------    --------------------------------   ------------------
  PRIMARY KEY   NOT NULL + UNIQUE; row identifier  NO (one PK)
  FOREIGN KEY   Referential integrity               YES
  UNIQUE        Distinct values (NULL allowed once) YES
  NOT NULL      Value required                      YES (per column)
  CHECK         Custom expression must be true      YES
  DEFAULT       Value if not provided               YES (per column)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between PRIMARY KEY and UNIQUE?
  A: PRIMARY KEY: NOT NULL + UNIQUE; one per table; main row identifier.
     UNIQUE: values must be distinct, but NULL is allowed; multiple per table.

  Q: Should you always add a FOREIGN KEY constraint?
  A: In most cases yes — they enforce referential integrity at DB level.
     Exceptions: high-write throughput systems where FK checks add overhead,
     or microservices where foreign records live in different databases (enforce at app level).

  Q: What does ON DELETE CASCADE do?
  A: When the parent row is deleted, all child rows with FK pointing to it
     are automatically deleted. Useful for ORDER → ORDER_ITEMS (items have no meaning without order).

  Q: Can a NULL value violate a UNIQUE constraint?
  A: No. NULL is considered unknown, and by SQL standard, NULL ≠ NULL,
     so multiple NULLs are allowed in a UNIQUE column.

  Q: Why should you always index foreign keys?
  A: JOINs on FK columns require a lookup of child rows. Without an index,
     every JOIN does a full table scan of the child table. FK indexes are
     critical for any query performance involving related tables.
