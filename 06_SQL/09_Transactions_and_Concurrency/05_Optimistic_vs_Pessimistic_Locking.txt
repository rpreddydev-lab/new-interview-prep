================================================================
  OPTIMISTIC VS PESSIMISTIC LOCKING
================================================================

================================================================
PESSIMISTIC LOCKING
================================================================

  Assumes conflicts WILL happen.
  Lock the data before reading it to prevent conflicts.
  Hold the lock until the transaction ends.

  SQL: SELECT ... FOR UPDATE
  JPA: LockModeType.PESSIMISTIC_WRITE

  Example:
  BEGIN;
    SELECT * FROM inventory WHERE product_id = 5 FOR UPDATE;
    -- Lock held; nobody else can update this row
    UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 5;
  COMMIT;

  JPA:
  entityManager.find(Inventory.class, 5L, LockModeType.PESSIMISTIC_WRITE);

  Pros:
  - Prevents conflicts completely
  - No retry logic needed
  - Good for high-contention scenarios

  Cons:
  - Reduces throughput (other transactions wait)
  - Risk of deadlocks
  - Long-held locks block other users

  Use when: Conflict rate is HIGH, short transaction duration.

================================================================
OPTIMISTIC LOCKING
================================================================

  Assumes conflicts are RARE.
  Don't lock at read time. At write time, check nothing changed.
  If conflict detected: throw exception, application retries.

  Implementation: add a version column (integer or timestamp).

  SQL Pattern:
  -- Read:
  SELECT id, quantity, version FROM inventory WHERE product_id = 5;
  -- Returns: quantity=10, version=3

  -- Update (check version has not changed):
  UPDATE inventory
  SET quantity = quantity - 1, version = version + 1
  WHERE product_id = 5 AND version = 3;   -- <-- version check

  -- If 0 rows updated: someone else updated first --> conflict, retry

  JPA with @Version:
  @Entity
  public class Inventory {
      @Id
      private Long id;
      private int quantity;

      @Version                    // JPA automatically manages this
      private Long version;
  }

  When JPA generates the UPDATE:
  UPDATE inventory SET quantity=?, version=? WHERE id=? AND version=?
  If rowsAffected = 0 --> throws OptimisticLockException --> application retries

================================================================
VERSION STRATEGIES
================================================================

  Integer version:   INCREMENT on each update
  Timestamp:         Set to current timestamp on each update
                     RISK: sub-millisecond updates have same timestamp
  ETag (HTTP):       Same concept in REST APIs
                     Client sends back If-Match: "version" header

================================================================
COMPARISON TABLE
================================================================

  Feature              Pessimistic          Optimistic
  -------------------  -------------------  --------------------
  When to lock         Before read          At write time
  Lock held duration   Until tx end         Never (no lock)
  Conflict handling    Prevented up front   Detected at commit
  Retry logic needed   No                   Yes
  Throughput           Lower (blocks)       Higher (no blocks)
  Deadlock risk        Yes                  No
  Best for             High contention      Low contention
  SQL mechanism        SELECT FOR UPDATE    Version column + check
  JPA annotation       PESSIMISTIC_WRITE    @Version

================================================================
SPRING JPA RETRY ON OPTIMISTIC LOCK FAILURE
================================================================

  @Retryable(value = OptimisticLockException.class, maxAttempts = 3)
  @Transactional
  public void decrementInventory(Long productId) {
      Inventory inv = inventoryRepo.findById(productId).orElseThrow();
      inv.setQuantity(inv.getQuantity() - 1);
      inventoryRepo.save(inv);
      // If another transaction committed between read and save,
      // OptimisticLockException is thrown and @Retryable retries
  }

================================================================
INTERVIEW Q&A
================================================================

  Q: What is optimistic locking?
  A: A concurrency strategy that reads data without locking, then
     at write time checks whether the data changed (via a version column).
     If changed, throws OptimisticLockException; application retries.
     No actual DB lock held -- good for low-contention scenarios.

  Q: What is pessimistic locking?
  A: A strategy that locks the row immediately when read (SELECT FOR UPDATE).
     Other transactions must wait. Prevents conflicts but reduces throughput.
     Good for high-contention scenarios.

  Q: How does JPA @Version work?
  A: JPA adds a WHERE version = ? condition to every UPDATE.
     If the row was updated by another transaction since the read,
     rowsAffected = 0, JPA throws OptimisticLockException.

  Q: When would you choose one over the other?
  A: Pessimistic: when conflicts are frequent and the cost of retries
     is high (e.g., complex, long-running operations).
     Optimistic: when conflicts are rare and retries are cheap
     (e.g., most web CRUD with occasional concurrent access).
