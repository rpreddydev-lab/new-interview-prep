================================================================
  ACID PROPERTIES
================================================================

================================================================
A — ATOMICITY
================================================================

  All operations in a transaction succeed or all are rolled back.
  There is no partial commit.

  Bank transfer example:
  BEGIN;
    UPDATE accounts SET balance = balance - 500 WHERE id = 1;
    UPDATE accounts SET balance = balance + 500 WHERE id = 2;
  COMMIT;

  If server crashes after debit but before credit:
  - Transaction is in uncommitted state (not in commit log)
  - On recovery, database replays WAL and finds transaction incomplete
  - Both operations are rolled back
  - Balance stays unchanged, no money lost

  Implementation: Write-Ahead Log (WAL) / Redo Log + Undo Log

================================================================
C — CONSISTENCY
================================================================

  Transaction takes the database from one valid state to another.
  All data integrity rules (constraints, foreign keys, checks) must hold
  at the end of a committed transaction.

  Mid-transaction, constraints may be violated temporarily:
  - Insert order_items before inserting the parent order (within same tx)
  - Use DEFERRABLE constraints to check at COMMIT time, not per statement

  Consistency = data rules defined by the application + DB constraints.
  NOT just "no errors" -- the rules must all be satisfied.

================================================================
I — ISOLATION
================================================================

  Concurrent transactions execute as if they run serially.
  One transaction's intermediate state is invisible to others.

  Four isolation levels (weakest to strongest):
  READ UNCOMMITTED --> can see dirty reads
  READ COMMITTED   --> sees only committed data (default PG/SQL Server)
  REPEATABLE READ  --> same row read twice = same value (default MySQL)
  SERIALIZABLE     --> completely isolated, appears sequential

  Full coverage in 03_Isolation_Levels.txt.

================================================================
D — DURABILITY
================================================================

  Once COMMIT succeeds, data survives system failures.
  Power loss, crash, restart -- committed data is still there.

  Implementation:
  - Write-Ahead Log: changes written to WAL before acknowledged
  - WAL is synced to disk (fsync) before commit returns to client
  - On recovery: replay WAL to restore committed transactions

  fsync=off (PostgreSQL):
  - Faster performance (no fsync)
  - Durability sacrificed -- commit may be lost on crash
  - Only for testing/non-critical data

================================================================
ACID IN DISTRIBUTED SYSTEMS
================================================================

  Single-node ACID is well-supported.
  Distributed ACID (across multiple machines) requires:
  - 2-Phase Commit (2PC): coordinator + participants
  - XA transactions (Java: JTA)
  - High latency, reduced availability during coordinator failure

  NoSQL systems often trade ACID for availability (BASE model):
  BASE = Basically Available, Soft state, Eventually consistent

================================================================
INTERVIEW Q&A
================================================================

  Q: Explain ACID with an example.
  A: Bank transfer:
     Atomic -- debit and credit both succeed or both fail.
     Consistent -- account balance cannot go below zero (constraint).
     Isolated -- concurrent transfer doesn't see intermediate state.
     Durable -- once committed, the transfer survives a server crash.

  Q: Which ACID property does WAL enforce?
  A: Durability. WAL ensures changes are written to disk before the
     transaction is acknowledged, so they survive crashes.
     WAL also enables Atomicity via undo information for incomplete transactions.

  Q: What is the difference between ACID and BASE?
  A: ACID (relational DBs) prioritizes Consistency/Isolation.
     BASE (NoSQL) prioritizes Availability over strict consistency.
     ACID: all-or-nothing, strongly consistent.
     BASE: eventually consistent, allows temporary inconsistency.
