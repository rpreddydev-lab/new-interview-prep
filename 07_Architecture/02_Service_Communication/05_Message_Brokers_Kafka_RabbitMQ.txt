MESSAGE BROKERS: KAFKA & RABBITMQ
================================================================================

WHY MESSAGE BROKERS?
---------------------
Message brokers enable asynchronous communication between services.
They decouple producers from consumers, provide durability, and enable
fan-out (one message → many consumers).

Benefits:
  ✓ Temporal decoupling — producer and consumer can be up at different times
  ✓ Load leveling — absorb traffic spikes (queue buffers messages)
  ✓ Fan-out — one event → many consumers
  ✓ Fault tolerance — messages persist if consumer crashes
  ✓ Replay (Kafka) — reprocess historical events

KAFKA — EVENT STREAMING PLATFORM
==================================

DEFINITION:
Apache Kafka is a distributed event streaming platform designed for high-
throughput, fault-tolerant, real-time data pipelines and event streaming.
Originally developed at LinkedIn; open-sourced in 2011.

CORE CONCEPTS:

1. TOPIC
   - A category/stream of messages
   - Like a table in a database or a folder of files
   - Producers publish to topics; consumers read from topics
   - Example topics: "order-placed", "payment-processed", "user-registered"

2. PARTITION
   - Topics are split into partitions for parallelism
   - Each partition is an ordered, immutable sequence of records
   - Partitions distributed across Kafka brokers (nodes)
   - More partitions = more parallel consumers = higher throughput
   - Partition key determines which partition a message goes to
     - Same key → same partition → guaranteed ordering for that key
     - Example: orderId as partition key → all events for one order are ordered

3. OFFSET
   - Each message in a partition has a sequential offset (position)
   - Consumer tracks its offset — knows exactly where it is in the log
   - Key Kafka feature: consumers control their own position
   - Can replay from offset 0 to reprocess all historical events

4. CONSUMER GROUP
   - Multiple consumers sharing the same group-id work as a team
   - Each partition is consumed by exactly ONE consumer in a group
   - Different groups each get a full copy of all messages (fan-out)

   Topic with 4 partitions:
   Consumer Group A (3 consumers): Consumer1 gets P0+P1, Consumer2 gets P2, Consumer3 gets P3
   Consumer Group B (1 consumer): Consumer4 gets P0+P1+P2+P3 (all)

5. BROKER
   - A Kafka server that stores partitions
   - Kafka cluster = multiple brokers
   - Replication: each partition replicated across N brokers for fault tolerance

6. REPLICATION
   - replication.factor=3 → 3 copies of each partition
   - One leader per partition (handles reads/writes)
   - Two followers (replicate from leader)
   - If leader fails, a follower becomes the new leader (automatic)

KAFKA ARCHITECTURE:
  Producer → [Kafka Cluster]
                 ↕
             [Partition 0] [Leader: Broker1, Replica: Broker2, Broker3]
             [Partition 1] [Leader: Broker2, Replica: Broker1, Broker3]
             [Partition 2] [Leader: Broker3, Replica: Broker1, Broker2]
                 ↕
  Consumer Group A (3 consumers)
  Consumer Group B (1 consumer)

DELIVERY SEMANTICS:
  At-Most-Once: Messages may be lost; never duplicated
    - Producer: fire-and-forget (no acks)
    - Consumer: commit offset before processing
    - Use case: Low-importance metrics, where loss is acceptable

  At-Least-Once: Messages may be duplicated; never lost (DEFAULT for most systems)
    - Producer: acks=all, retries enabled
    - Consumer: commit offset AFTER processing
    - Requires: Idempotent consumers to handle duplicates

  Exactly-Once: No duplicates, no loss (complex, higher overhead)
    - Kafka Transactions (since 0.11)
    - Producer: enable.idempotence=true, transactional.id set
    - Consumer: isolation.level=read_committed
    - Use case: Financial systems, inventory

KAFKA IN SPRING BOOT:

  <!-- pom.xml -->
  <dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
  </dependency>

  # application.yml
  spring:
    kafka:
      bootstrap-servers: localhost:9092
      consumer:
        group-id: order-service
        auto-offset-reset: earliest
        key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
        value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      producer:
        key-serializer: org.apache.kafka.common.serialization.StringSerializer
        value-serializer: org.springframework.kafka.support.serializer.JsonSerializer

  // Producer
  @Service
  public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderPlacedEvent> kafkaTemplate;

    public void publishOrderPlaced(Order order) {
      OrderPlacedEvent event = new OrderPlacedEvent(order.getId(), order.getUserId(), order.getTotal());
      kafkaTemplate.send("order-events", String.valueOf(order.getId()), event);
      // Partition key = orderId ensures all events for one order go to same partition
    }
  }

  // Consumer
  @Service
  public class NotificationConsumer {
    @KafkaListener(topics = "order-events", groupId = "notification-service")
    public void handleOrderPlaced(OrderPlacedEvent event,
                                   @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
                                   @Header(KafkaHeaders.OFFSET) long offset) {
      log.info("Processing event: {} from topic={}, offset={}", event, topic, offset);
      emailService.sendOrderConfirmation(event.getUserId(), event.getOrderId());
    }
  }

KAFKA USE CASES:
  - Real-time event streaming (user actions, clicks, page views)
  - Log aggregation (replacing Logstash input)
  - Metrics collection
  - Event sourcing (immutable event log)
  - CDC (Change Data Capture) with Debezium
  - Stream processing with Kafka Streams / ksqlDB

RABBITMQ — MESSAGE BROKER
===========================

DEFINITION:
RabbitMQ is a traditional message broker implementing the AMQP (Advanced
Message Queuing Protocol). Open-sourced by Rabbit Technologies in 2007,
now maintained by VMware/Broadcom.

CORE CONCEPTS:

1. PRODUCER
   Sends messages to an exchange (not directly to a queue)

2. EXCHANGE
   Routes messages to queues based on routing rules.
   Types of exchanges:
   a) Direct: Routes to queue where binding key = routing key
      Producer sends key="order.created" → Queue "order-processing" (bound with same key)

   b) Fanout: Broadcasts to ALL bound queues (ignores routing key)
      Useful for notifications to multiple services

   c) Topic: Wildcard routing
      * matches one word, # matches zero or more words
      "order.#" matches "order.created", "order.shipped", "order.delivered"
      "*.failed" matches "payment.failed", "order.failed"

   d) Headers: Routes based on message headers (rarely used)

3. QUEUE
   Stores messages until consumed
   Properties:
   - Durable: Survives broker restart (stored to disk)
   - Exclusive: Used by only one connection
   - Auto-delete: Deleted when last consumer disconnects
   - Dead-letter-exchange: Where rejected messages go

4. BINDING
   The rule that connects an exchange to a queue
   (exchange, routing-key) → queue

5. CONSUMER
   Subscribes to a queue and processes messages
   Sends ACK after successful processing
   Sends NACK/Reject if processing fails → message requeued or DLQed

6. VIRTUAL HOST (vhost)
   Logical segregation within RabbitMQ (like databases in MySQL)
   Different applications use different vhosts for isolation

RABBITMQ MESSAGE FLOW:
  Producer → Exchange → [Binding with routing key] → Queue → Consumer
                                                            └→ Consumer (competing)

  For Fanout:
  Producer → FanoutExchange → Queue1 → Consumer1 (NotificationService)
                            → Queue2 → Consumer2 (AnalyticsService)
                            → Queue3 → Consumer3 (AuditService)

ACKNOWLEDGEMENTS:
  Auto-ACK: Message deleted from queue when delivered (risky — consumer may crash)
  Manual-ACK: Consumer explicitly acknowledges after successful processing
    channel.basicAck(deliveryTag, false);  // success
    channel.basicNack(deliveryTag, false, true);  // failure, requeue=true
    channel.basicNack(deliveryTag, false, false); // failure, requeue=false → DLQ

DEAD LETTER QUEUE (DLQ):
  Messages that fail processing N times → sent to Dead Letter Exchange → DLQ
  Operations team can inspect and replay or discard failed messages

  Queue declaration with DLQ:
  @Bean
  Queue orderQueue() {
    return QueueBuilder.durable("order-processing")
        .withArgument("x-dead-letter-exchange", "order-dlx")
        .withArgument("x-dead-letter-routing-key", "order-failed")
        .withArgument("x-message-ttl", 300000)  // 5 min TTL
        .build();
  }

RABBITMQ IN SPRING BOOT:

  <!-- pom.xml -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
  </dependency>

  // Config
  @Configuration
  public class RabbitConfig {
    public static final String ORDER_QUEUE = "order-processing";
    public static final String ORDER_EXCHANGE = "order-exchange";
    public static final String ORDER_ROUTING_KEY = "order.created";

    @Bean
    Queue orderQueue() { return QueueBuilder.durable(ORDER_QUEUE).build(); }

    @Bean
    TopicExchange orderExchange() { return new TopicExchange(ORDER_EXCHANGE); }

    @Bean
    Binding orderBinding() {
      return BindingBuilder.bind(orderQueue()).to(orderExchange())
                           .with(ORDER_ROUTING_KEY);
    }

    @Bean
    MessageConverter jsonConverter() { return new Jackson2JsonMessageConverter(); }
  }

  // Producer
  @Service
  public class OrderEventPublisher {
    @Autowired private RabbitTemplate rabbitTemplate;

    public void publishOrderCreated(OrderDTO order) {
      rabbitTemplate.convertAndSend(
          RabbitConfig.ORDER_EXCHANGE,
          RabbitConfig.ORDER_ROUTING_KEY,
          order
      );
    }
  }

  // Consumer
  @Service
  public class OrderProcessingConsumer {
    @RabbitListener(queues = RabbitConfig.ORDER_QUEUE)
    public void processOrder(OrderDTO order, Channel channel,
                              @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) {
      try {
        orderService.processOrder(order);
        channel.basicAck(deliveryTag, false);  // success
      } catch (Exception e) {
        channel.basicNack(deliveryTag, false, false); // fail → DLQ
      }
    }
  }

KAFKA vs RABBITMQ — DETAILED COMPARISON
========================================

Feature              │ Kafka                          │ RabbitMQ
─────────────────────┼────────────────────────────────┼───────────────────────────
Architecture         │ Distributed log (append-only)  │ Traditional message broker
Message retention    │ Configurable (days/weeks/forever)│ Deleted after ACK
Replay               │ Yes — consumers set offset     │ No — consumed and gone
Throughput           │ Very high (millions/sec)       │ High (tens of thousands/sec)
Ordering             │ Guaranteed within partition    │ Queue-level ordering
Consumer model       │ Consumer Groups + offsets      │ Competing consumers + ACK
Push/Pull            │ Pull (consumer polls)          │ Push (broker pushes to consumer)
Routing              │ Topic-based (key → partition)  │ Exchange routing (direct/fanout/topic)
Protocol             │ Custom Kafka protocol          │ AMQP (standard)
Dead Letter Queue    │ Separate topic (manual setup)  │ Built-in DLQ support
Stream processing    │ Kafka Streams / ksqlDB (built-in)│ External tools only
Persistence          │ Disk-based log (always persisted)│ Optional (in-memory or disk)
Ecosystem            │ Kafka Connect, Kafka Streams   │ STOMP, MQTT plugins
Complexity           │ Higher (ZooKeeper/KRaft setup) │ Simpler to set up
Best for             │ Event streaming, high volume   │ Task queues, routing, RPC

CHOOSING KAFKA vs RABBITMQ
===========================

Choose KAFKA when:
  - High-throughput event streaming (millions of messages/sec)
  - Need to replay events (event sourcing, audit, debugging)
  - Multiple independent consumer groups
  - Long event retention needed
  - Building event-driven microservices ecosystem
  - Need Kafka Streams for real-time processing
  - CDC (Change Data Capture)

Choose RABBITMQ when:
  - Traditional task queue (work distribution)
  - Complex message routing (topic/header exchange)
  - Simple point-to-point messaging
  - RPC-style request/reply pattern needed
  - Smaller scale / simpler setup needed
  - Built-in DLQ management is important
  - AMQP standards compliance needed

INTERVIEW QUESTIONS
====================

Q: What is Kafka and how does it differ from RabbitMQ?
A: Kafka is a distributed event streaming platform built around an append-only
   log. Messages are retained and consumers track their own offset. RabbitMQ is
   a traditional message broker — messages are deleted after ACK. Kafka is for
   high-throughput event streaming with replay; RabbitMQ for routing/task queues.

Q: What is a Kafka consumer group?
A: Multiple consumers sharing the same group-id that divide the topic partitions
   among themselves. Each partition is consumed by exactly one consumer in the
   group, enabling parallel processing. Different groups each get all messages.

Q: How does Kafka guarantee message ordering?
A: Ordering is guaranteed WITHIN a partition. Use a partition key (e.g., orderId)
   to ensure all messages for the same key go to the same partition → ordered.
   No global ordering across partitions.

Q: What delivery semantics does Kafka support?
A: At-most-once (fire and forget), at-least-once (default — may duplicate),
   exactly-once (Kafka transactions). At-least-once requires idempotent consumers.

Q: What is a Dead Letter Queue?
A: A queue where messages are routed after failing to be processed N times.
   Used to avoid blocking the main queue with "poison messages." Operations
   can inspect, fix, and replay or discard messages from the DLQ.

Q: What is the Outbox Pattern and how does it relate to Kafka?
A: The Outbox Pattern ensures reliable event publishing. Instead of directly
   publishing to Kafka (which may fail), write to a local "outbox" table in the
   same DB transaction as the business operation. A separate process reads the
   outbox and publishes to Kafka. Guarantees at-least-once publishing even if
   Kafka is temporarily unavailable.
