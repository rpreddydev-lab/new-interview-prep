SECRETS MANAGEMENT IN MICROSERVICES
================================================================================

THE PROBLEM WITH HARDCODED SECRETS
------------------------------------
Bad practice (unfortunately common):
  # application.yml — NEVER DO THIS
  spring:
    datasource:
      url: jdbc:postgresql://prod-db:5432/orders
      username: order_user
      password: SuperSecret123!   # ❌ In version control!
  
  aws:
    secret-key: AKIAIOSFODNN7EXAMPLE  # ❌ Leaked in git history!

Consequences:
  - Secrets committed to git → visible to everyone with repo access
  - Secrets in container images → leaked when image is shared
  - Rotation requires code change + deployment
  - Different secrets per environment not easily managed

SECRETS MANAGEMENT SOLUTIONS
==============================

1. ENVIRONMENT VARIABLES (minimal improvement)
   Better than hardcoding, but:
   - Visible in process list, `/proc/<pid>/environ`
   - Logged by mistake easily
   - Not centralized

   # application.yml
   spring:
     datasource:
       password: ${DB_PASSWORD}  # Injected via env var

2. KUBERNETES SECRETS
   - Base64-encoded (NOT encrypted by default!)
   - Enable encryption at rest: EncryptionConfiguration in kube-apiserver
   - Access control via RBAC

   # Create secret
   kubectl create secret generic order-db-secret \
     --from-literal=DB_PASSWORD=SuperSecret123 \
     --namespace=production

   # Mount in pod
   spec:
     containers:
     - name: order-service
       envFrom:
       - secretRef:
           name: order-db-secret
       # Or mount as file:
       volumeMounts:
       - name: secrets
         mountPath: /etc/secrets
         readOnly: true
     volumes:
     - name: secrets
       secret:
         secretName: order-db-secret

   # Encrypt etcd at rest (recommended)
   apiVersion: apiserver.config.k8s.io/v1
   kind: EncryptionConfiguration
   resources:
   - resources: ["secrets"]
     providers:
     - aescbc:
         keys:
         - name: key1
           secret: <base64-encoded-32-byte-key>
     - identity: {}

3. HASHICORP VAULT (enterprise standard)
   - Centralized secrets management
   - Dynamic secrets (generate credentials on demand)
   - Automatic rotation
   - Audit log of all secret access
   - Kubernetes integration (Vault Agent Injector / Vault CSI Provider)

   How Vault dynamic secrets work:
     Instead of a fixed DB password, Vault generates a unique, time-limited
     credential when the application requests it.

     Order Service starts → requests DB credentials from Vault
     Vault generates: order_svc_20240115_xk92 / <random-password> (TTL: 1 hour)
     Vault tells PostgreSQL: "Create this user"
     Order Service uses these credentials
     After 1 hour: Vault revokes the credentials
     If compromised: short TTL limits blast radius

4. CLOUD PROVIDER SECRETS MANAGERS
   - AWS Secrets Manager: auto-rotation, KMS encryption, CloudTrail audit
   - GCP Secret Manager: versioning, IAM, audit logs
   - Azure Key Vault: certificates + secrets + keys

SPRING BOOT + VAULT INTEGRATION
=================================

  # pom.xml
  <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-vault-config</artifactId>
  </dependency>

  # application.yml
  spring:
    cloud:
      vault:
        host: vault.production.svc.cluster.local
        port: 8200
        scheme: https
        authentication: KUBERNETES  # Use K8s service account token
        kubernetes:
          role: order-service
          kubernetes-path: kubernetes
        kv:
          enabled: true
          backend: secret
          default-context: order-service  # Reads from secret/order-service

  # Vault path: secret/order-service
  # Contains:
  {
    "db.password": "SecretDBPass",
    "jwt.secret": "JWTSigningKey",
    "stripe.api-key": "sk_prod_..."
  }

  # Spring Boot auto-injects as properties:
  @Value("${db.password}")
  private String dbPassword;

VAULT KUBERNETES AUTH:
  Vault authenticates the pod using its Kubernetes service account JWT.
  No hardcoded Vault token needed.

  # Vault policy
  vault write auth/kubernetes/role/order-service \
    bound_service_account_names=order-service \
    bound_service_account_namespaces=production \
    policies=order-service-policy \
    ttl=24h

  vault policy write order-service-policy - << EOF
  path "secret/order-service/*" {
    capabilities = ["read"]
  }
  path "database/creds/order-service" {
    capabilities = ["read"]
  }
  EOF

SECRET ROTATION STRATEGIES
============================

1. Manual rotation:
   - Update secret in Vault/Secrets Manager
   - Trigger rolling restart of services
   - Downtime risk

2. Dynamic secrets (Vault):
   - Vault generates new credentials automatically before TTL expires
   - Application requests new credentials on renewal
   - Zero manual intervention

3. Side-car / agent rotation:
   - Vault Agent Injector runs as sidecar
   - Monitors secret TTL, renews and writes to shared volume
   - Application reads from volume (file-based secrets)
   - No restart needed for the application

4. Spring Cloud Vault Config Watcher:
   - Watches for Vault secret changes
   - Triggers Spring's RefreshScope for properties
   - Zero-downtime rotation

BEST PRACTICES CHECKLIST
==========================
  ✓ Never commit secrets to git (use .gitignore + pre-commit hooks to detect)
  ✓ Use different secrets per environment (dev/staging/prod)
  ✓ Rotate secrets regularly (automated via Vault/Secrets Manager)
  ✓ Use shortest TTL practical (minimize blast radius)
  ✓ Audit all secret access (who accessed what, when)
  ✓ Encrypt secrets at rest (Vault, K8s EncryptionConfiguration)
  ✓ Use dynamic secrets where possible (DB credentials, API tokens)
  ✓ Store in environment-specific namespaces (secret/production/order-service)
  ✓ Least privilege: each service only accesses its own secrets
  ✓ Use service account authentication (no static Vault tokens)

DETECT SECRETS IN CODE
========================

Tools to prevent accidental secret commits:
  - git-secrets (AWS): scans for patterns before commit
  - Gitleaks: FOSS secret scanner for CI/CD
  - TruffleHog: deep git history scan
  - detect-secrets (Yelp): pre-commit hooks

Pre-commit hook:
  # .pre-commit-config.yaml
  repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
    - id: gitleaks

INTERVIEW QUESTIONS
====================

Q: How should secrets be managed in microservices?
A: Use a dedicated secrets manager: HashiCorp Vault (enterprise), AWS Secrets
   Manager, or Kubernetes Secrets (with etcd encryption). Never hardcode secrets
   or commit to git. Inject via environment variables or mounted files. Use
   dynamic secrets with short TTLs for databases to minimize compromise blast radius.

Q: What are dynamic secrets and why are they better?
A: Vault generates unique, time-limited credentials on demand rather than using
   static passwords. If a service's DB credentials are compromised, they expire
   in 1 hour automatically. No long-lived static passwords to rotate manually.

Q: How do you authenticate a service to Vault in Kubernetes?
A: Kubernetes auth method — Vault verifies the pod's service account JWT token.
   No static Vault token is needed. Configure Vault with the Kubernetes cluster
   endpoint and bind roles to specific service account names and namespaces.

Q: What's the problem with Kubernetes Secrets out of the box?
A: Kubernetes Secrets are only base64 encoded, not encrypted. Anyone with etcd
   access can read them. Enable etcd EncryptionConfiguration with AES or integrate
   with an external KMS (AWS KMS, GCP KMS) for true encryption at rest.
