DEPLOYMENT IN MICROSERVICES
-----------------------------
In a monolith: deploy one artifact to a set of servers.
In microservices: deploy 50 independent services, each with its own:
  - Deployment lifecycle
  - Scaling requirements
  - Configuration
  - Zero-downtime upgrade strategy

Key deployment concepts:
  1. Containerization (Docker) — package service + runtime in a portable unit
  2. Orchestration (Kubernetes) — manage containers at scale
  3. CI/CD — automate build → test → deploy pipelines
  4. Deployment strategies — blue/green, canary, rolling updates
  5. Configuration management — externalized, encrypted config
  6. Auto-scaling — HPA, KEDA, VPA for demand-driven scaling

DEPLOYMENT PIPELINE
====================

Developer → Git Push → CI/CD Pipeline:

  1. Source Control (Git)
       │
  2. CI (Build + Test)
     - Compile
     - Unit tests
     - Integration tests (TestContainers)
     - Contract tests (Pact)
     - Static analysis (Checkstyle, SpotBugs, OWASP)
     - Build Docker image
       │
  3. Image Registry (Docker Hub, ECR, GCR, ACR)
       │
  4. CD (Deploy to environments)
     - Deploy to staging (automated)
     - Integration/smoke tests
     - Deploy to production (auto or manual gate)
       │
  5. Post-deployment
     - Health checks (readiness probes)
     - Canary analysis (error rate, latency)
     - Rollback if metrics degrade

DEPLOYMENT STRATEGIES COMPARISON
==================================

Strategy         │ Downtime │ Risk    │ Rollback  │ Resource Use │ Use When
─────────────────┼──────────┼─────────┼───────────┼──────────────┼──────────────
Rolling Update   │ None     │ Medium  │ Slow      │ Normal       │ Default
Blue/Green       │ None     │ Low     │ Instant   │ 2×           │ Critical services
Canary           │ None     │ Very Low│ Quick     │ 105-110%     │ Large-scale, risky changes
Recreate         │ YES      │ High    │ Full redeploy│ Normal    │ Dev/staging only
A/B Testing      │ None     │ Very Low│ Quick     │ 105-110%     │ Feature experiments

==========================================

Factors most relevant to deployment:
  1. Codebase: One codebase per service, tracked in git

  7. Port binding: Self-contained, export services via port binding
  8. Concurrency: Scale by adding processes horizontally
  9. Disposability: Fast startup (< 30s), graceful shutdown
  10. Dev/prod parity: Keep environments as similar as possible
  11. Logs: Treat logs as event streams to stdout
  12. Admin processes: Run admin tasks as one-off processes

INTERVIEW QUESTIONS
====================

Q: What are the main differences between Blue/Green and Canary deployments?
A: Blue/Green: maintains two full environments (100% old + 100% new), switches
   all traffic instantly. Zero risk of partial failure but double resource cost.
   Rollback is instant (switch back). Canary: gradually shifts traffic (1% → 5%
   → 100%), allows monitoring for issues with real traffic on a small percentage.
   Uses ~10% extra resources. Rollback by routing all traffic back to old version.

Q: Why is containerization important for microservices?
A: Containers package the application + all dependencies + runtime in a portable,
   immutable image. Eliminates "works on my machine" — dev/staging/prod run the
   same image. Enables fast startup, resource isolation, and efficient scaling.
   Kubernetes can schedule containers on available nodes.
