================================================================================
AUTO-SCALING IN MICROSERVICES
================================================================================

WHY AUTO-SCALING?
------------------
Microservices handle variable traffic. Manual scaling is slow and expensive.
Auto-scaling ensures:
  - Enough replicas during traffic spikes (peak hours, promotions)
  - Fewer replicas when idle (save cost)
  - No human intervention required

Kubernetes Auto-Scaling Types:
  HPA (Horizontal Pod Autoscaler) — Add/remove pods (most common)
  VPA (Vertical Pod Autoscaler)   — Resize pod CPU/memory requests
  KEDA (Event-Driven Autoscaler)  — Scale based on Kafka lag, queue depth, etc.
  Cluster Autoscaler              — Add/remove nodes

────────────────────────────────────────────────────────────────────────────────

HORIZONTAL POD AUTOSCALER (HPA)
================================

Scales replicas based on metrics. Default: CPU utilization.
K8s checks metrics every 15 seconds, scales every 30-60 seconds.

CPU-based HPA:
  apiVersion: autoscaling/v2
  kind: HorizontalPodAutoscaler
  metadata:
    name: order-service-hpa
    namespace: production
  spec:
    scaleTargetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: order-service
    minReplicas: 3      # Never scale below 3 (HA requirement)
    maxReplicas: 20     # Never scale above 20 (cost guard)
    metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Target: keep CPU at 70%
    - type: Resource
      resource:
        name: memory
        target:
          type: AverageValue
          averageValue: 400Mi
    behavior:
      scaleUp:
        stabilizationWindowSeconds: 60    # Wait 60s before scaling up again
        policies:
        - type: Percent
          value: 100    # Can double replicas at once
          periodSeconds: 15
      scaleDown:
        stabilizationWindowSeconds: 300   # Wait 5 min before scaling down (avoid flapping)
        policies:
        - type: Percent
          value: 10     # Remove max 10% of pods at a time
          periodSeconds: 60

Custom metrics HPA (based on request rate from Prometheus):
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second  # Custom Prometheus metric via Prometheus Adapter
      target:
        type: AverageValue
        averageValue: "100"  # Target: 100 RPS per pod

Scaling formula:
  desiredReplicas = ceil(currentReplicas × (currentMetric / desiredMetric))

  Example: 3 pods × (90% CPU / 70% target) = ceil(3.86) = 4 pods

KEDA — EVENT-DRIVEN AUTOSCALING
================================

KEDA (Kubernetes Event-Driven Autoscaling) scales based on event sources:
  - Kafka consumer lag
  - RabbitMQ queue depth
  - Redis list length
  - AWS SQS queue length
  - Azure Service Bus
  - HTTP request rate
  - Custom Prometheus queries

KEDA can scale to ZERO (unlike HPA minimum 1):

  apiVersion: keda.sh/v1alpha1
  kind: ScaledObject
  metadata:
    name: order-processor-scaledobject
    namespace: production
  spec:
    scaleTargetRef:
      name: order-processor   # Deployment to scale
    minReplicaCount: 0        # Scale to zero when no messages!
    maxReplicaCount: 50
    cooldownPeriod: 300       # Wait 5 min before scaling back to zero
    triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: order-processor-group
        topic: order-events
        lagThreshold: "50"    # 1 replica per 50 messages of lag
        offsetResetPolicy: earliest

For HTTP-based scaling with KEDA:
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus:9090
      metricName: http_requests_total
      query: |
        sum(rate(http_server_requests_seconds_count{job="order-service"}[2m]))
      threshold: "100"   # 1 replica per 100 RPS

VERTICAL POD AUTOSCALER (VPA)
================================

Automatically adjusts CPU/memory requests (not replicas).
Useful for right-sizing requests/limits without manual tuning.

  apiVersion: autoscaling.k8s.io/v1
  kind: VerticalPodAutoscaler
  metadata:
    name: order-service-vpa
  spec:
    targetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: order-service
    updatePolicy:
      updateMode: "Auto"   # Auto: evict + resize pods. "Off": recommendations only
    resourcePolicy:
      containerPolicies:
      - containerName: order-service
        minAllowed:
          cpu: 100m
          memory: 128Mi
        maxAllowed:
          cpu: 2
          memory: 2Gi

NOTE: Do NOT use VPA + HPA on CPU/memory simultaneously (conflict).
  - HPA on CPU/memory requests: no VPA
  - HPA on custom metrics + VPA for resource tuning: OK

CLUSTER AUTOSCALER
===================

When HPA/KEDA want more pods but no nodes have capacity:
  → Cluster Autoscaler adds nodes to the cluster

  # Configured at cluster level (EKS, GKE, AKS have native integration)
  # Checks every 10 seconds for pending pods (no schedulable node)
  # Scales up the appropriate node group
  # Scales down underutilized nodes after 10 min below 50% utilization

Pod Disruption Budget (protect during scale-down):
  apiVersion: policy/v1
  kind: PodDisruptionBudget
  metadata:
    name: order-service-pdb
  spec:
    minAvailable: 2   # At least 2 pods always running (never evict all)
    selector:
      matchLabels:
        app: order-service

SCALING BEST PRACTICES
========================

1. Set meaningful resource requests (not too low, not too high)
   - HPA scales based on resource utilization vs requests
   - If requests are too low, HPA won't trigger until CPU is way over

2. Use scale-down stabilization windows
   - Prevent flapping (scale down after short traffic dip, then scale up again)
   - scaleDown.stabilizationWindowSeconds: 300 (5 minutes)

3. Set minReplicas >= 2 for production HA
   - At least 2 pods for zero-downtime rolling updates
   - PodAntiAffinity to spread across nodes

4. Pre-scale before known events
   - Promotions, marketing campaigns, scheduled batch jobs
   - kubectl scale deployment order-service --replicas=20

5. Test scaling behavior
   - Use `kubectl run load-generator --image=busybox` to generate CPU load
   - Watch: kubectl get hpa order-service-hpa --watch

INTERVIEW QUESTIONS
====================

Q: What is HPA and how does it work?
A: Horizontal Pod Autoscaler adds or removes pods based on metrics (CPU, memory,
   or custom). It checks metrics every 15 seconds, computes desired replicas as
   ceil(current × metric/target), and scales within min/maxReplicas bounds.
   Stabilization windows prevent flapping (rapid scale up/down).

Q: What is KEDA and when do you use it over HPA?
A: KEDA (Kubernetes Event-Driven Autoscaling) scales based on event sources
   like Kafka consumer lag, queue depth, or custom Prometheus metrics. Use KEDA
   when scaling should be driven by business-level signals (message backlog),
   not just infrastructure metrics (CPU%). KEDA can also scale to zero, saving
   cost for batch/async workloads.

Q: What is the relationship between resource requests and HPA?
A: HPA calculates utilization as (actual usage / resource request). If requests
   are set too low, utilization percentage is always high and HPA over-scales.
   If too high, it under-scales. Accurate resource requests (from VPA
   recommendations or load testing) are critical for HPA to work correctly.
