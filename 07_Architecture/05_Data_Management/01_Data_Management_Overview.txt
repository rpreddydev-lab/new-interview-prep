DATA MANAGEMENT IN MICROSERVICES — OVERVIEW
================================================================================

THE CORE CHALLENGE
-------------------
In monoliths, all services share a single database. Joins are trivial. ACID
transactions span multiple domain objects. Consistency is guaranteed.

In microservices, each service owns its data. This creates fundamental challenges:
  - No cross-service JOINS
  - No distributed ACID transactions
  - Queries spanning multiple services require aggregation
  - Consistency between services is eventual, not immediate

This trade-off is the hardest part of microservices architecture.

────────────────────────────────────────────────────────────────────────────────

DATABASE PER SERVICE — THE FUNDAMENTAL RULE
=============================================

Each microservice should own its data store.
Other services CANNOT directly access another service's database.

CAP THEOREM — THE FOUNDATION
==============================

In a distributed system, you can only guarantee 2 of 3 properties simultaneously:

  C — Consistency:    Every read receives the most recent write
  A — Availability:  Every request gets a response (not necessarily latest data)
  P — Partition Tolerance: System continues despite network partition

Reality: Network partitions WILL happen. So the real choice is:
  CP: Sacrifice availability when partitioned (consistent but may reject requests)
  AP: Sacrifice consistency when partitioned (available but may return stale data)

Modern interpretation: PACELC (extends CAP)
  If Partition → choose between A or C
  Else (no partition) → choose between L(atency) or C(onsistency)

Database choices:
  CP databases:  HBase, Zookeeper, MongoDB (configurable), PostgreSQL w/ sync replication
  AP databases:  Cassandra, DynamoDB, CouchDB, Riak, Eureka (service registry)

────────────────────────────────────────────────────────────────────────────────

ACID vs BASE
=============

ACID (Traditional RDBMS — strong consistency):
  A — Atomicity:   All operations in a transaction succeed or all fail
  C — Consistency: DB moves from one valid state to another
  I — Isolation:   Concurrent transactions don't interfere
  D — Durability:  Committed transactions persist even after crash

BASE (Distributed systems — eventual consistency):
  BA — Basically Available:  System guarantees availability
  S  — Soft state:           State may change without input (propagation)
  E  — Eventually Consistent: Given no new updates, all nodes converge eventually

Microservices trend toward BASE for scalability, accepting eventual consistency
for non-critical data while maintaining ACID within each individual service.

CROSS-SERVICE DATA QUERIES
============================

Problem: Order history needs user name, order items, product names.
Data lives in: Order Service, User Service, Inventory Service.

Solutions:

1. API COMPOSITION (Synchronous)
   - Service or API Gateway calls multiple services
   - Aggregates results in memory
   - Simple, but limited by slowest service

   Implementation:
     @Service
     public class OrderDetailsAggregator {
       public OrderDetailsDTO getOrderDetails(Long orderId) {
         Order order = orderService.getOrder(orderId);              // call 1
         User user = userService.getUser(order.getUserId());        // call 2
         List<Product> products = inventoryService              
           .getProducts(order.getProductIds());                     // call 3
         return OrderDetailsDTO.from(order, user, products);
       }
     }

2. CQRS + READ MODELS (Asynchronous)
   - Maintain a denormalized read model that pre-joins data
   - Populated by consuming events from multiple services
   - Fast reads; eventual consistency

3. SHARED READ DATABASE (read-only replica)
   - Multiple services write to their own databases
   - A reporting/analytics DB aggregates via CDC (Change Data Capture)
   - Used for reporting only, never for operational writes

INTERVIEW QUESTIONS
====================

Q: Why does each microservice need its own database?
A: Database-per-service enforces loose coupling. With a shared database,
   a schema change in one service breaks others. Services can't be deployed
   or scaled independently. They also can't choose different DB technologies.
   Each service owning its data enables independent evolution.

Q: How do you query data that spans multiple services?
A: Two main approaches: API Composition (call multiple services and aggregate
   synchronously — simple but limited by latency) and CQRS with event-driven
   read models (build a denormalized read model by consuming events — fast
   reads but eventual consistency).

Q: What is the difference between ACID and BASE?
A: ACID provides strong guarantees (atomicity, consistency, isolation, durability)
   for relational databases. BASE (basically available, soft state, eventually
   consistent) describes distributed systems that sacrifice strong consistency
   for availability and partition tolerance. Microservices typically use BASE
   for cross-service data and ACID within individual service boundaries.

Q: What is CAP theorem?
A: In distributed systems, only 2 of 3 can be guaranteed simultaneously:
   Consistency (every read gets latest write), Availability (every request
   gets a response), and Partition Tolerance (works despite network failures).
   Since partitions are unavoidable, choose between CP and AP.
