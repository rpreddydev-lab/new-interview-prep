RESILIENCE PATTERNS OVERVIEW
================================================================================

WHY RESILIENCE MATTERS IN MICROSERVICES
-----------------------------------------
In a distributed system, failures are not exceptional — they are expected.
Networks are unreliable. Services crash. Databases go down. Third-party APIs
time out. The question is not IF failures will happen, but WHEN.

A resilient system:
  - Degrades gracefully (partial functionality over total failure)
  - Fails fast (doesn't waste resources waiting for unresponsive services)
  - Self-heals (recovers automatically when dependencies recover)
  - Isolates failures (one service's failure doesn't cascade to everything)

Quote: "Design for failure. Accept that failure will happen and build systems
        that can handle it gracefully." — Netflix Engineering

────────────────────────────────────────────────────────────────────────────────

THE CASCADE FAILURE PROBLEM
============================

Without resilience patterns:

  Service A → Service B → Service C → Database (DOWN!)
  
  1. Database is slow/down
  2. Service C threads block waiting for DB responses
  3. Service C runs out of threads → becomes unresponsive
  4. Service B threads block waiting for Service C
  5. Service B runs out of threads → becomes unresponsive
  6. Service A threads block waiting for Service B
  7. Service A becomes unresponsive
  8. ENTIRE SYSTEM DOWN due to a database issue in Service C

This is a CASCADING FAILURE — one failure triggers a chain reaction.

THE RESILIENCE PATTERN TOOLKIT
================================

Pattern              │ Problem it Solves
─────────────────────┼─────────────────────────────────────────────────────────
Circuit Breaker      │ Stop calling a failing service; prevent cascade failures
Retry + Backoff      │ Handle transient failures with automatic retries
Bulkhead             │ Isolate failure in one component from others
Timeout              │ Don't wait forever for slow/unresponsive services
Fallback             │ Provide alternative response when service fails
Rate Limiter         │ Protect services from being overwhelmed
Hedged Request       │ Send duplicate requests to reduce tail latency

────────────────────────────────────────────────────────────────────────────────

THE FOUR RESILIENCE PRINCIPLES
================================

1. FAIL FAST
   Don't wait for a timeout that will never come.
   Set aggressive timeouts on all network calls.
   Use Circuit Breaker to fail immediately when downstream is known to be down.

2. FAIL GRACEFULLY
   Partial functionality > total failure.
   Return cached data, defaults, or degraded responses.
   Example: Can't load recommendations → show empty recommendations section
            (don't refuse to show the product page at all)

3. DEGRADE GRACEFULLY
   Identify which features are critical vs optional.
   When dependencies fail, disable optional features; keep core working.
   Example: Search history is down → still show product search (core)

4. RECOVER AUTOMATICALLY
   Systems should detect recovery and restore normal operation.
   Circuit Breaker HALF-OPEN state tests if downstream recovered.
   Retry with backoff waits for transient issues to pass.

RESILIENCE4J — THE STANDARD LIBRARY
=====================================

Resilience4j is the de-facto resilience library for Java microservices.
It replaced Netflix Hystrix (deprecated since 2018).

Spring Boot integration:
  <dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>  <!-- Required for annotations -->
  </dependency>

Resilience4j components:
  - CircuitBreaker      → Stop calling failing services
  - RateLimiter         → Limit request rate
  - Retry               → Automatic retries with backoff
  - Bulkhead            → Thread/semaphore isolation
  - TimeLimiter         → Timeout on async calls
  - Cache               → Response caching

All compose cleanly:
  @CircuitBreaker(name = "inventoryCB", fallbackMethod = "defaultInventory")
  @RateLimiter(name = "inventoryRL")
  @Retry(name = "inventoryRetry")
  @TimeLimiter(name = "inventoryTL")
  public Inventory getInventory(Long productId) { ... }

Execution order: RateLimiter → CircuitBreaker → TimeLimiter → Retry

RESILIENCE DECISION FLOWCHART
================================

Request comes in:
  ↓
[Rate Limiter]: Am I within rate limits?
  NO → 429 Too Many Requests
  YES ↓
[Circuit Breaker]: Is the circuit OPEN?
  OPEN → Return fallback immediately (fail fast)
  CLOSED/HALF-OPEN ↓
[Timeout]: Does the call complete within the time limit?
  TIMEOUT → Retry or return fallback
  SUCCESS ↓
[Retry]: Did the call fail? (transient error)
  FAILED (within retry budget) → Wait + retry
  EXCEEDED RETRIES → Return fallback
  SUCCESS ↓
[Record success/failure for Circuit Breaker]
Return response ✓

WHEN TO USE EACH PATTERN
==========================

ALL external service calls should have:
  ✓ Timeout (always — never wait indefinitely)
  ✓ Circuit Breaker (always — prevent cascade failures)

Additionally based on need:
  ✓ Retry — for transient failures (network blips, 502, 503)
  ✓ Bulkhead — when you have many different types of calls and need isolation
  ✓ Fallback — when degraded response is acceptable
  ✓ Rate Limiter — on incoming traffic (protect your service) or outgoing (respect limits)

INTERVIEW QUESTIONS
====================

Q: What is a cascading failure and how do you prevent it?
A: A cascading failure occurs when one service's failure causes dependent
   services to also fail in a chain. Prevent with Circuit Breakers (stop
   calling failing services), Timeouts (don't wait indefinitely), Bulkheads
   (isolate failure to thread pools), and Fallbacks (return degraded responses).

Q: What is Resilience4j?
A: The standard Java library for resilience patterns. Provides Circuit Breaker,
   Retry, Bulkhead, RateLimiter, TimeLimiter, and Cache. Replaced deprecated
   Netflix Hystrix. Integrates with Spring Boot via annotations and YAML config.

Q: What's the difference between Circuit Breaker and Retry?
A: Retry handles transient failures — tries again with the expectation the
   call will eventually succeed. Circuit Breaker handles persistent failures —
   stops calling the service entirely when it's clearly broken, giving it time
   to recover. They complement each other.

Q: How does a service degrade gracefully?
A: By identifying critical vs optional features. When a dependency fails, optional
   features return defaults (empty recommendations, cached prices) while critical
   features (checkout, authentication) get full error handling. Fallback methods
   provide the degraded responses.
