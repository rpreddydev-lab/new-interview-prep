MONOLITH vs MICROSERVICES vs SOA — DEEP COMPARISON
================================================================================

1. MONOLITHIC ARCHITECTURE
==========================

DEFINITION:
  An application where all components are tightly coupled and deployed as
  a single deployable unit (one WAR/JAR, one process).

STRUCTURE:
  ┌────────────────────────────────────────────────┐
  │                MONOLITH                        │
  │  ┌──────────┐  ┌──────────┐  ┌──────────────┐ │
  │  │  UI Layer│  │  Biz     │  │  Data Access │ │
  │  │          │→ │  Logic   │→ │  Layer       │ │
  │  └──────────┘  └──────────┘  └──────────────┘ │
  │                     ↓                          │
  │              Single Database                   │
  └────────────────────────────────────────────────┘

TYPES OF MONOLITHS:
  1. Single-Process Monolith: Everything in one process
  2. Modular Monolith: Modules with clear boundaries but single deploy unit
  3. Distributed Monolith (worst): Multiple services but tightly coupled —
     worst of both worlds

ADVANTAGES:
  ✓ Simple to develop initially
  ✓ Easy to test end-to-end
  ✓ Easy to deploy (one artifact)
  ✓ No distributed systems complexity
  ✓ Simple debugging (single process)
  ✓ Transactions are local (ACID)

DISADVANTAGES:
  ✗ Scaling: Must scale entire app even if only one part is under load
  ✗ Deployment: Any change requires full redeploy → slow release cycles
  ✗ Technology lock-in: Entire app uses same language/framework
  ✗ Team coupling: Large teams conflict on the same codebase
  ✗ Code base grows → "Big Ball of Mud"
  ✗ Single point of failure

WHEN MONOLITH IS APPROPRIATE:
  - Early-stage product (MVP)
  - Small team (< 5 devs)
  - Domain not well understood yet
  - Low traffic/scale needs
  - Simple CRUD applications

2. SOA (SERVICE-ORIENTED ARCHITECTURE)
=======================================

DEFINITION:
  An architectural style where application components provide services to
  other components via a communication protocol over a network. Typically
  uses an Enterprise Service Bus (ESB) for orchestration.

ORIGIN: Emerged in the late 1990s / early 2000s. Popularized by IBM, TIBCO.

STRUCTURE:
  ┌──────────┐    ┌─────────────────────────────────────────────┐
  │ Service A│←──→│                                             │
  │ Service B│←──→│         Enterprise Service Bus (ESB)        │
  │ Service C│←──→│   (Routing, Transformation, Orchestration)  │
  │ Service D│←──→│                                             │
  └──────────┘    └─────────────────────────────────────────────┘

SOA CHARACTERISTICS:
  - Services are coarse-grained (large, heavyweight)
  - Relies on SOAP, WSDL, XML-based protocols
  - ESB handles routing, protocol translation, orchestration
  - Shared data model (canonical data model)
  - Services can share databases
  - BPEL (Business Process Execution Language) for orchestration
  - Enterprise-wide service governance

ADVANTAGES OF SOA:
  ✓ Reusability of services across enterprise
  ✓ Platform/language independence via standards
  ✓ Integration of legacy systems
  ✓ Centralized governance and policy enforcement

DISADVANTAGES OF SOA:
  ✗ ESB becomes a single point of failure and bottleneck
  ✗ Heavyweight protocols (SOAP, XML) — slow and verbose
  ✗ High coupling through shared data model
  ✗ Complex governance
  ✗ ESB becomes "smart pipe" — difficult to change
  ✗ Slow deployments due to interdependencies
  ✗ High infrastructure cost

────────────────────────────────────────────────────────────────────────────────

3. MICROSERVICES ARCHITECTURE
==============================

DEFINITION:
  Fine-grained, independently deployable services each owning their own
  data, communicating via lightweight protocols, with "dumb pipes" and
  "smart endpoints."

STRUCTURE:
  ┌──────────────────────────────────────────────────────────────┐
  │                      API GATEWAY                             │
  └──────────────────────────────────────────────────────────────┘
       │              │              │              │
  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ Order   │   │Payment  │   │Inventory│   │ User    │
  │ Service │   │ Service │   │ Service │   │ Service │
  │  (DB)   │   │  (DB)   │   │  (DB)   │   │  (DB)   │
  └─────────┘   └─────────┘   └─────────┘   └─────────┘
       ↕                ↕
  [Message Broker — Kafka / RabbitMQ]

────────────────────────────────────────────────────────────────────────────────

COMPARISON TABLE
================

Feature              │ Monolith          │ SOA               │ Microservices
─────────────────────┼───────────────────┼───────────────────┼───────────────────
Service Granularity  │ Single unit       │ Coarse-grained    │ Fine-grained
Communication        │ In-process calls  │ SOAP/ESB          │ REST/gRPC/Messaging
Protocols            │ N/A               │ SOAP, WSDL, XML   │ HTTP, JSON, gRPC
Data Management      │ Shared DB         │ Shared/Canonical  │ DB per service
Deployment           │ All-or-nothing    │ Per service (hard)│ Independent
Scalability          │ Scale whole app   │ Per service       │ Fine-grained scale
Technology           │ Single stack      │ Somewhat flexible │ Polyglot
Team Structure       │ Central large team│ Center of Excellence│ Autonomous teams
Governance           │ Low overhead      │ Heavy             │ Decentralized
Failure Isolation    │ None              │ Limited           │ High (bulkheads)
ESB / Orchestration  │ None              │ ESB required      │ Choreography preferred
Coupling             │ High              │ Medium-High       │ Low
Testing              │ Simple            │ Complex           │ Complex (contract)
Operational Cost     │ Low               │ High (ESB)        │ High (infra)
Best For             │ Small teams/MVPs  │ Enterprise legacy │ Large-scale modern apps

────────────────────────────────────────────────────────────────────────────────

KEY DIFFERENCES: SOA vs MICROSERVICES
======================================

Aspect              SOA                          Microservices
──────────────────  ───────────────────────────  ────────────────────────────
Middleware          ESB (smart pipe)             Dumb pipe (broker/HTTP)
Scope               Enterprise-wide              Application/Team-wide
Data sharing        Shared canonical data model  Each service owns its data
Protocol            Heavyweight (SOAP)           Lightweight (REST/gRPC)
Service size        Coarse (e.g., "BillingService") Fine (e.g., "InvoiceService")
Reuse philosophy    Reuse services aggressively  Duplication sometimes OK
Governance          Centralized                  Decentralized
Deployment          Complex coordination         Independent per service

ANALOGY:
  SOA  = City with a central post office handling all mail routing
  Microservices = City where everyone communicates directly with each other

MODULAR MONOLITH — THE MIDDLE GROUND
=====================================

A Modular Monolith is a single deployable unit divided into well-defined
internal modules with clear boundaries, like:

  ┌─────────────────────────────────────────┐
  │              MODULAR MONOLITH           │
  │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │
  │ │  Orders  │ │Payments  │ │Inventory │ │
  │ │  Module  │ │ Module   │ │ Module   │ │
  │ └──────────┘ └──────────┘ └──────────┘ │
  └─────────────────────────────────────────┘

Benefits:
  - Complexity of monolith with better maintainability
  - No network overhead
  - Easier to migrate to microservices later (modules → services)
  - Good for teams moving from monolith

Recommended by: Sam Newman ("Building Microservices"), Martin Fowler
Strategy: Build a modular monolith first, extract to microservices when needed.

────────────────────────────────────────────────────────────────────────────────

MIGRATION PATH: MONOLITH → MICROSERVICES
==========================================

Step 1: Build a Modular Monolith first
Step 2: Identify hotspots (scalability, team conflicts, frequent deploys)
Step 3: Apply Strangler Fig pattern (extract one service at a time)
Step 4: Set up API Gateway, Service Discovery, Observability infrastructure
Step 5: Extract bounded contexts (DDD) one by one
Step 6: Migrate data — split the shared database per service

Common Mistake: Extracting microservices too early → "Distributed Monolith"
(services too tightly coupled, dependent on each other's databases or APIs)

INTERVIEW QUESTIONS
====================

Q: What's the difference between SOA and Microservices?
A: SOA uses heavyweight protocols (SOAP), relies on a central ESB, and shares
   a canonical data model. Microservices use lightweight protocols, prefer
   choreography over orchestration, and each service owns its data.
   Microservices are essentially "SOA done right" — finer-grained and more
   operationally independent.

Q: When would you choose a monolith over microservices?
A: When the team is small, the domain isn't well understood, or operational
   maturity (CI/CD, Kubernetes, observability) isn't in place. A modular
   monolith is often a better starting point.

Q: What is a "Distributed Monolith"?
A: A system with multiple services but where they are so tightly coupled
   (shared databases, synchronous chains of calls) that they must be deployed
   together. It has the complexity of microservices with none of the benefits
   of monoliths.

Q: Can you explain Conway's Law in this context?
A: Conway's Law: "Organizations design systems that mirror their communication
   structure." If teams are siloed, the system will reflect that. Microservices
   teams should own their service end-to-end (Inverse Conway Maneuver).
