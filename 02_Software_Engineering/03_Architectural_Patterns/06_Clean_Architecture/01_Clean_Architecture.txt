================================================================
  CLEAN ARCHITECTURE (UNCLE BOB)
================================================================

  Author:     Robert C. Martin ("Uncle Bob") — "Clean Architecture" (2017)
  Similar to: Hexagonal Architecture, Onion Architecture — same core idea.
  Frequency:  Medium-High for senior Java interviews; very relevant for lead roles.

----------------------------------------------------------------
CORE IDEA
----------------------------------------------------------------

  Organize code in concentric circles where:
    - INNER circles = business rules (pure, framework-independent).
    - OUTER circles = mechanisms (frameworks, databases, UI, web).

  The DEPENDENCY RULE: dependencies only point INWARD.
  Inner circles know NOTHING about outer circles.
  Outer circles know about inner circles.

  This makes the core business rules:
    - Independent of frameworks (no Spring annotations in the domain).
    - Independently testable (test domain without DB, web, or frameworks).
    - Independent of databases (swap MySQL for MongoDB without touching business rules).
    - Independent of UI/delivery mechanism.

----------------------------------------------------------------
THE FOUR CIRCLES
----------------------------------------------------------------

  OUTER → INNER:

  1. FRAMEWORKS & DRIVERS (outermost)
     - Spring Boot, Hibernate, Jackson, Kafka, REST controllers.
     - Database configuration, web frameworks, external APIs.
     - The most volatile layer — changes frequently as technology evolves.

  2. INTERFACE ADAPTERS
     - Controllers, Presenters, Gateways, Mappers.
     - Convert data between the format most convenient for use cases
       and the format most convenient for external agencies (DB, web).
     - Spring @Controller, @Repository implementations live here.

  3. USE CASES (APPLICATION BUSINESS RULES)
     - Application-specific business rules.
     - Orchestrate flow: call entities, apply business logic, call gateways.
     - NOT framework-aware. Pure Java. Testable without Spring.
     - CreateOrderUseCase, ProcessPaymentUseCase, SendNotificationUseCase.

  4. ENTITIES (innermost — ENTERPRISE BUSINESS RULES)
     - Core domain objects: Order, Customer, Payment, Product.
     - Business rules that would exist regardless of the application.
     - No framework dependencies whatsoever. Pure Java business objects.
     - Most stable — changes only when core business rules change.

----------------------------------------------------------------
DEPENDENCY RULE VISUALIZATION
----------------------------------------------------------------

  ┌─────────────────────────────────────────┐
  │  Frameworks & Drivers                   │  ← Spring, Hibernate, Kafka, REST
  │  ┌───────────────────────────────────┐  │
  │  │  Interface Adapters               │  │  ← Controllers, JPA Repos, Mappers
  │  │  ┌─────────────────────────────┐  │  │
  │  │  │  Use Cases                  │  │  │  ← Application Services
  │  │  │  ┌───────────────────────┐  │  │  │
  │  │  │  │  Entities             │  │  │  │  ← Domain: Order, Customer, Money
  │  │  │  └───────────────────────┘  │  │  │
  │  │  └─────────────────────────────┘  │  │
  │  └───────────────────────────────────┘  │
  └─────────────────────────────────────────┘

  Dependency arrows:  → all point INWARD only
  Frameworks → Adapters → Use Cases → Entities
  Entities know NOTHING about use cases, adapters, or frameworks.

----------------------------------------------------------------
CROSSING BOUNDARIES: DEPENDENCY INVERSION
----------------------------------------------------------------

  When an inner circle needs an outer circle to do something
  (e.g., Use Case needs to save to a database):

  WRONG: Use Case → calls JpaRepository directly (violates the rule).
  CORRECT: Use Case defines an interface (Gateway/Repository).
           Outer circle implements it.

  // Inner circle (Use Case) defines the port:
  public interface OrderRepository {   // lives in use-cases layer
      void save(Order order);
      Optional<Order> findById(OrderId id);
  }

  // Outer circle (Adapter) implements it:
  @Repository  // Spring annotation — only in adapter layer
  public class JpaOrderRepository implements OrderRepository {
      private final OrderJpaRepository springDataRepo;
      // ... implementation with JPA
  }

  The Use Case depends on the interface (inward dependency OK).
  The adapter depends on the Use Case interface (also pointing inward — OK).

----------------------------------------------------------------
CLEAN ARCHITECTURE vs HEXAGONAL ARCHITECTURE
----------------------------------------------------------------

  Very similar philosophies. Key differences:

  Hexagonal:
    - Two sides: primary (driving) and secondary (driven).
    - Ports and Adapters terminology.
    - Doesn't prescribe inner layering of the hexagon.

  Clean Architecture:
    - Four explicit concentric circles.
    - Separates Entities (enterprise rules) from Use Cases (app rules).
    - More prescriptive about circle boundaries.

  In practice: many teams use the terms interchangeably.
  Both achieve: framework-independent domain, inward dependencies, testability.

SPRING BOOT PROJECT STRUCTURE
----------------------------------------------------------------

  com.example/
  ├── domain/                          (Entities circle)
  │   ├── model/                       (Order, Customer, Money — pure Java)
  │   └── service/                     (Domain Services — pure business logic)
  │
  ├── application/                     (Use Cases circle)
  │   ├── port/
  │   │   ├── in/                      (CreateOrderUseCase interface)
  │   │   └── out/                     (OrderRepository interface — gateway)
  │   └── service/                     (CreateOrderService — implements use case)
  │
  ├── adapter/                         (Interface Adapters circle)
  │   ├── web/                         (OrderController, OrderRequest/Response)
  │   ├── persistence/                 (JpaOrderRepository, OrderJpaEntity)
  │   └── messaging/                   (KafkaOrderEventPublisher)
  │
  └── infrastructure/                  (Frameworks & Drivers circle)
      ├── config/                      (SpringConfig, JpaConfig, KafkaConfig)
      └── security/                    (SecurityConfig)

----------------------------------------------------------------
COMMON INTERVIEW QUESTIONS
----------------------------------------------------------------

  Q: What is Clean Architecture?
  A: Clean Architecture organizes code in concentric circles where the DEPENDENCY
     RULE states all dependencies point inward. The innermost circle (Entities) has
     pure business rules with no framework dependencies. Use Cases orchestrate these
     rules. Adapters connect to the web and databases. Frameworks and external tools
     are in the outermost circle. This makes the domain independently testable,
     framework-replaceable, and resistant to technology churn.

  Q: How does Clean Architecture differ from traditional layered architecture?
  A: Layered architecture has one-way dependencies (Controller → Service → Repository)
     but the inner layers (domain) often still depend on the database layer
     (JPA entities, Spring annotations). Clean Architecture enforces that the
     domain has ZERO dependencies on any external layer. The database and web
     frameworks are "plugins" — the app core doesn't know they exist.

  Q: What is the "Dependency Rule"?
  A: The fundamental rule: source code dependencies can only point inward (toward
     the domain). Entities don't import use case classes. Use cases don't import
     adapter classes. Adapters don't import framework-specific code (Spring) in
     the use case layer. When you need to cross the boundary outward-to-inward
     (adapter calling a use case), use an interface defined in the inner circle.

================================================================
INTERVIEW TIPS
================================================================

  - The core selling point: "the domain is testable without Spring context
    — test execution is 10x faster."
  - Connect to real pain: "before Clean Architecture, every unit test spun up
    a Spring context and required a real DB — tests took 5 minutes. After: 30s."
  - Mention that Hexagonal and Clean Architecture solve the same problem with
    slightly different terminology.
  - Don't be dogmatic: "I apply Clean Architecture pragmatically — full rigor
    for the core domain; less strict for trivial CRUD endpoints."
