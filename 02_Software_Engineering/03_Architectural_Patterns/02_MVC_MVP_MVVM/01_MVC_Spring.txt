================================================================
  MVC — MODEL VIEW CONTROLLER
================================================================

  Category:   Architectural Pattern (Presentation Layer Pattern)
  GoF?        No — predates GoF; originated in Smalltalk (1970s).
  Frequency:  Very High — foundational for all web frameworks.

----------------------------------------------------------------
INTENT
----------------------------------------------------------------

  Separate a UI-based application into three interconnected components:
    Model:      business data and business rules (state).
    View:       displays the model data to the user (UI/output).
    Controller: handles user input, updates the model, selects the view.

  Goal: separation of concerns — each component can evolve independently.

----------------------------------------------------------------
CLASSIC MVC (TRADITIONAL / SERVER-SIDE RENDERING)
----------------------------------------------------------------

  Flow:
    1. User sends HTTP request.
    2. Controller receives and parses request.
    3. Controller calls Service/Model to process business logic.
    4. Model returns data (domain objects, DTOs).
    5. Controller selects a View (template) and passes the Model.
    6. View renders HTML and returns to user.

  In Spring MVC:
    @Controller         → the Controller component
    @Service            → business logic (part of Model layer)
    @Repository + JPA   → data access (part of Model layer)
    Thymeleaf / JSP     → the View

  Example:
    @Controller
    @RequiredArgsConstructor
    public class UserController {
        private final UserService userService;

        @GetMapping("/users/{id}")
        public String getUser(@PathVariable Long id, Model model) {
            User user = userService.findById(id);
            model.addAttribute("user", user);
            return "user-detail";  // → resolves to templates/user-detail.html
        }
    }

----------------------------------------------------------------
REST MVC (API-BASED — NO VIEW)
----------------------------------------------------------------

  In REST/API applications, the "View" is replaced by JSON/XML serialization.
  @RestController = @Controller + @ResponseBody: no View template, returns data directly.

  Flow:
    1. HTTP request hits @RestController.
    2. Controller validates input, calls @Service.
    3. Service processes business logic using @Repository.
    4. Controller returns DTO → Jackson serializes to JSON response.

  Example:
    @RestController
    @RequestMapping("/api/users")
    @RequiredArgsConstructor
    public class UserController {
        private final UserService userService;

        @GetMapping("/{id}")
        public ResponseEntity<UserDto> getUser(@PathVariable Long id) {
            return ResponseEntity.ok(userService.findById(id));
        }

        @PostMapping
        public ResponseEntity<UserDto> createUser(@Valid @RequestBody CreateUserRequest req) {
            UserDto created = userService.create(req);
            URI location = URI.create("/api/users/" + created.getId());
            return ResponseEntity.created(location).body(created);
        }
    }

  Controller responsibilities (ONLY):
    - Parse / validate HTTP input.
    - Delegate to Service.
    - Map result to HTTP response (status code, headers, body).
    - Handle controller-level exceptions (@ExceptionHandler).

  Controller anti-patterns:
    - Business logic in controller → move to Service.
    - DB calls in controller → move to Repository via Service.
    - Returning domain entities (JPA entities) directly → return DTOs.

----------------------------------------------------------------
MVP — MODEL VIEW PRESENTER
----------------------------------------------------------------

  Used in: Android, Swing, older desktop UI frameworks.
  Difference from MVC: Presenter handles ALL UI logic; View is passive.

  View: displays data, forwards ALL events to Presenter.
  Presenter: fetches model, formats for View, calls View.display() methods.
  Model: same as MVC.

  Key distinction: View knows Presenter; Controller in MVC knows both View and Model.
  MVP's View is more decoupled (pure UI, no logic).

  In Java: historically used in JavaFX/Swing enterprise apps.
  Rarely asked in backend Java interviews — know the distinction.

----------------------------------------------------------------
MVVM — MODEL VIEW VIEWMODEL
----------------------------------------------------------------

  Used in: Angular, React (conceptually), JavaFX.
  ViewModel: exposes data as observable properties; View data-binds to them.
  Two-way data binding: View changes update ViewModel and vice versa.

  In Java: JavaFX uses properties/bindings for MVVM-like patterns.
  Frontend (Angular, React) architecture — know this if you do full-stack.

----------------------------------------------------------------
SPRING MVC INTERNAL FLOW (DEEP DIVE)
----------------------------------------------------------------

  Request → DispatcherServlet → HandlerMapping (finds @RequestMapping)
         → HandlerAdapter (invokes Controller method)
         → ModelAndView returned
         → ViewResolver (resolves template name to View)
         → View renders response
         → Response returned to client

  Key components:
    DispatcherServlet:    Front Controller — single entry point (Front Controller pattern).
    HandlerMapping:       maps URLs to controller methods.
    HandlerAdapter:       invokes the mapped method.
    ViewResolver:         maps view name to template file (ThymeleafViewResolver).
    HandlerInterceptor:   pre/post-process requests (logging, auth checks).
    @ControllerAdvice:    global exception handling across all controllers.

----------------------------------------------------------------
COMMON INTERVIEW QUESTIONS
----------------------------------------------------------------

  Q: What is the difference between @Controller and @RestController?
  A: @RestController = @Controller + @ResponseBody on every method.
     @Controller renders Views (templates). @RestController returns data
     serialized directly as JSON/XML to the response body. Use @RestController
     for REST APIs, @Controller for server-side rendered web pages.

  Q: What is the Front Controller pattern and how does Spring use it?
  A: Front Controller is a single centralized handler for all incoming requests
     that delegates to specific handlers. Spring's DispatcherServlet is the
     Front Controller — all requests go through it, which then routes to the
     appropriate @Controller via HandlerMapping.

  Q: Should business logic be in the Controller?
  A: Never. Controllers should only handle HTTP concerns: parse input, delegate
     to the Service layer, map results to HTTP responses. Business logic belongs
     in @Service. This keeps controllers thin, testable, and reusable.

  Q: How do you handle exceptions in Spring MVC?
  A: Three ways:
     1. @ExceptionHandler within a @Controller (local scope).
     2. @ControllerAdvice / @RestControllerAdvice (global, all controllers).
     3. ResponseEntityExceptionHandler base class for standard HTTP exceptions.
     Senior answer: use @RestControllerAdvice with Problem Details (RFC 7807)
     for consistent error responses.

================================================================
INTERVIEW TIPS
================================================================

  - Always walk through the Spring MVC request lifecycle if asked — shows
    deep understanding beyond surface-level "Controller-Service-Repository."
  - Contrast MVC with Hexagonal/Clean Architecture to show architectural breadth.
  - Mention DTOs, validation (@Valid), and proper HTTP status codes — these
    are expected of a senior Java developer.
  - Know: DispatcherServlet, HandlerMapping, ViewResolver — these appear in
    advanced Spring MVC interview questions.
