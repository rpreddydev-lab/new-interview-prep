================================================================
  DOMAIN-DRIVEN DESIGN (DDD)
================================================================

  Author:     Eric Evans — "Domain-Driven Design" (Blue Book, 2003)
  Distilled:  Vaughn Vernon — "Implementing Domain-Driven Design" (Red Book)
  Frequency:  High for 7+ YOE Java interviews; expected knowledge at senior level.

----------------------------------------------------------------
CORE PHILOSOPHY
----------------------------------------------------------------

  Focus software design on the DOMAIN (the problem space) and its LOGIC,
  not on technical frameworks or database schemas.

  The model in code should REFLECT the mental model of domain experts.
  Developers and domain experts share a common language: Ubiquitous Language.

  DDD is most valuable for:
    - Complex domains with rich business logic (finance, healthcare, logistics).
    - Large teams where multiple subdomains exist.
    - Long-lived systems that must evolve with changing business rules.

  DDD is OVERKILL for:
    - Simple CRUD applications.
    - Data-centric apps (ETL, reporting).
    - Small, short-lived projects.

----------------------------------------------------------------
STRATEGIC DDD (THE BIG PICTURE)
----------------------------------------------------------------

  UBIQUITOUS LANGUAGE
  --------------------
    A shared vocabulary between developers and domain experts.
    The same terms used in requirements, code, tests, and conversations.
    Example: In a billing system, everyone uses "Invoice," "Line Item,"
    "Payment Term" — not DB table names (BILL_HDR, LINE_ITEM_DTLS).

    In code: class names, method names, variables use domain language.
    Not: UserEntity.saveToDb() → yes: Order.confirm(), Payment.capture().


  BOUNDED CONTEXT
  ----------------
    A BOUNDED CONTEXT is a clear boundary within which a domain model applies.
    The same term can mean different things in different bounded contexts.

    Example in e-commerce:
      "Customer" in the Order context: name, shipping address, order history.
      "Customer" in the Payment context: billing address, payment methods, credit limit.
      "Customer" in the Marketing context: preferences, segments, campaigns.

    These are three SEPARATE models of "Customer" in three bounded contexts.
    DO NOT create one god-Customer class that serves all contexts.

    Each bounded context becomes a MICROSERVICE (or a module) with its own
    data model, API, and database schema.

    Context Map: diagram showing how bounded contexts relate to each other
    (Partnership, Customer-Supplier, Conformist, Anti-Corruption Layer, etc.).


  CONTEXT MAP RELATIONSHIPS
  --------------------------
    Upstream / Downstream:
      Upstream context provides a model; downstream depends on it.
      Changes in upstream can break downstream.

    Anti-Corruption Layer (ACL):
      Downstream protects itself from upstream changes by translating
      through an ACL. The external model is NEVER used directly in the
      downstream domain.

      Example: Integrating a legacy billing system.
      Create BillingAdapter that translates legacy BillRecord → your Order model.

    Shared Kernel:
      Two contexts share a small subset of the domain model.
      Risky — tight coupling. Use sparingly.


----------------------------------------------------------------
TACTICAL DDD (BUILDING BLOCKS)
----------------------------------------------------------------

  ENTITY
  -------
    An object defined by its IDENTITY, not its attributes.
    Two entities with the same attributes but different IDs are DIFFERENT objects.
    Identity persists over time even as attributes change.

    Example:
      public class Order {
          private final OrderId id;  // identity — never changes
          private OrderStatus status; // mutable — changes over lifecycle
          private final CustomerId customerId;
          // ...
      }

    Identity types: UUID (preferred — no DB roundtrip), database sequence.
    Entity == identity == mutable lifecycle.


  VALUE OBJECT
  -------------
    An object defined entirely by its ATTRIBUTES. No identity.
    Two value objects with the same attributes ARE equal (equals by value).
    Immutable — never changed; replaced.

    Example:
      public record Money(BigDecimal amount, Currency currency) {
          public Money add(Money other) {
              if (!this.currency.equals(other.currency)) throw new ...;
              return new Money(this.amount.add(other.amount), this.currency);
          }
      }

      public record Address(String street, String city, String zipCode, String country) {}

      public record Email(String value) {
          public Email {
              if (!value.matches("...")) throw new InvalidEmailException(value);
          }
      }

    Value Objects enforce invariants in their constructors.
    Replace primitive obsession: String email → Email, double price → Money.
    Java records (Java 16+) are perfect for value objects.


  AGGREGATE
  ----------
    A CLUSTER of related entities and value objects treated as a UNIT
    for data consistency. Has a single root entity: the AGGREGATE ROOT.

    Rules:
      - External objects reference ONLY the Aggregate Root, never internal entities.
      - All changes to the aggregate go through the Aggregate Root.
      - The Aggregate Root enforces all invariants within the aggregate.
      - One Aggregate = one transaction boundary (never span two aggregates in one TX).

    Example: Order Aggregate
      OrderRoot (aggregate root)
        ├── OrderItem (entity — only referenced through Order)
        ├── ShippingAddress (value object)
        └── Money totalAmount (value object)

    Repository exists per Aggregate Root:
      OrderRepository.findById(orderId) → returns the full Order aggregate.


    // Order Aggregate Root enforces business rules:
    public class Order {
        private final OrderId id;
        private final List<OrderItem> items = new ArrayList<>();
        private OrderStatus status = OrderStatus.PENDING;

        public void addItem(Product product, int quantity) {
            if (status != OrderStatus.PENDING) {
                throw new IllegalStateException("Cannot modify confirmed order");
            }
            items.add(new OrderItem(product.getId(), product.getPrice(), quantity));
        }

        public void confirm() {
            if (items.isEmpty()) throw new IllegalStateException("Cannot confirm empty order");
            this.status = OrderStatus.CONFIRMED;
            // raise domain event
            DomainEvents.raise(new OrderConfirmedEvent(this.id));
        }
    }


  DOMAIN SERVICE
  ---------------
    Business logic that doesn't naturally belong to any single Entity or Value Object.
    Stateless. Named after a domain concept.

    Use when: the operation involves multiple aggregates or external resources.

    Example:
      // Domain Service — cross-aggregate operation
      public class OrderPricingService {
          public Money calculateTotalWithTax(Order order, TaxRate taxRate) {
              Money subtotal = order.calculateSubtotal();
              return subtotal.add(taxRate.apply(subtotal));
          }
      }

    NOT the same as Spring @Service (application service / orchestration layer).
    Domain Service = pure domain logic. Application Service = orchestration + infra calls.


  REPOSITORY
  -----------
    Abstracts the persistence of aggregates. Treats the collection of aggregates
    as an in-memory collection (hiding DB complexity).

    One repository per Aggregate Root:
      OrderRepository — save, findById, findByCustomerId.

    Interface defined in the DOMAIN layer (secondary port in Hexagonal).
    Implementation (JPA, MongoDB) lives in the infrastructure layer.

    public interface OrderRepository {
        void save(Order order);
        Optional<Order> findById(OrderId id);
        List<Order> findByCustomerId(CustomerId customerId);
    }


  DOMAIN EVENT
  -------------
    Something that happened in the domain that domain experts care about.
    Past tense. Immutable. Published after aggregate state changes.

    Examples: OrderPlaced, PaymentProcessed, InventoryReserved, UserRegistered.

    // Domain Event
    public record OrderConfirmedEvent(OrderId orderId, CustomerId customerId,
                                       Money totalAmount, Instant occurredOn) {}

    Publishing in Spring:
      applicationEventPublisher.publishEvent(new OrderConfirmedEvent(...));

    Benefits:
      - Decouple aggregates: Order publishes OrderConfirmed; Inventory listens and reserves.
      - Audit trail: events are facts about what happened.
      - Basis for Event Sourcing: rebuild state from event history.


  FACTORY
  --------
    Complex aggregate creation logic encapsulated in a Factory (or static factory method).
    Ensures aggregates are created in valid states.

    public class Order {
        public static Order create(CustomerId customerId, List<CartItem> items) {
            if (items.isEmpty()) throw new IllegalArgumentException("Order needs items");
            Order order = new Order(OrderId.generate(), customerId);
            items.forEach(item -> order.addItem(item.getProduct(), item.getQuantity()));
            return order;
        }
    }

ANEMIC DOMAIN MODEL — THE DDD ANTI-PATTERN
----------------------------------------------------------------

  An Anemic Domain Model has entities/classes with only data (getters/setters)
  and no behavior. All behavior is in @Service classes.

  // ANEMIC (bad):
  public class Order {
      private Long id;
      private String status; // String, not enum
      private List<OrderItem> items;
      // ONLY getters and setters
  }

  @Service
  public class OrderService {
      public void confirmOrder(Order order) {
          // business logic scattered in service, not in the domain
          if (order.getItems().isEmpty()) throw new ...;
          order.setStatus("CONFIRMED");
      }
  }

  Problem: business rules scattered across services; domain model is just a DTO.
  The model is "brain-dead" — pure data carrier with no intelligence.

  Fix: push behavior INTO the domain model:
    order.confirm() — the Order knows how to confirm itself.
    order.addItem() — the Order enforces its own rules on item addition.


----------------------------------------------------------------
DDD IN SPRING BOOT: PRACTICAL IMPLEMENTATION
----------------------------------------------------------------

  Package structure (per bounded context):
    com.example.orders/
    ├── domain/
    │   ├── model/       (Order, OrderItem, OrderId, Money, OrderStatus)
    │   ├── event/       (OrderConfirmedEvent, OrderCancelledEvent)
    │   ├── service/     (OrderPricingService — domain service)
    │   └── repository/  (OrderRepository interface)
    ├── application/     (CreateOrderUseCase, OrderApplicationService)
    ├── adapter/
    │   ├── web/         (OrderController, OrderRequest/Response DTOs)
    │   └── persistence/ (JpaOrderRepository, OrderJpaEntity, OrderMapper)

  JPA entities (persistence model) SEPARATE from domain entities:
    Order (domain) ←→ OrderMapper ←→ OrderJpaEntity (@Entity)
    Domain entities are pure Java; JPA entities have @Entity, @Column.
    Mapper (MapStruct or manual) translates between them.


----------------------------------------------------------------
COMMON INTERVIEW QUESTIONS
----------------------------------------------------------------

  Q: What is DDD and when should you use it?
  A: DDD is an approach where the software design is driven by the complex
     business domain. It provides tactical patterns (Entity, Value Object,
     Aggregate, Repository, Domain Event) to model the domain richly in code,
     and strategic patterns (Bounded Context, Context Map) to manage large
     systems. Use it for complex domains; avoid for simple CRUD apps.

  Q: What is the difference between an Entity and a Value Object?
  A: Entity: has a unique identity (ID) that persists over time. Two entities
     with same data but different IDs are different. Example: Order (has OrderId).
     Value Object: identified by its attributes. Immutable. Two value objects
     with same attributes are equal. Example: Money(100, USD). Java records
     are ideal for Value Objects.

  Q: What is an Aggregate and why is it important?
  A: An aggregate is a cluster of domain objects (entities + value objects) with
     one Aggregate Root. All access goes through the root, which enforces invariants.
     The aggregate is the transactional boundary — one aggregate per transaction.
     This prevents partial state and enforces consistency.

  Q: What is the Anemic Domain Model?
  A: An anti-pattern where domain classes are pure data holders (getters/setters
     only) with no behavior. Business logic lives entirely in service classes.
     This leads to scattered logic, poor encapsulation, and code that's hard to
     reason about. Fix: push behavior into the domain model (Order.confirm(),
     Order.addItem() with validation).

  Q: What is a Bounded Context?
  A: A semantic boundary within which a domain model applies. Different bounded
     contexts can use the same term (e.g., "Customer") but with different meanings
     and different models. Each bounded context has its own data model, codebase,
     and often its own database. In microservices, each service typically represents
     one bounded context.

================================================================
INTERVIEW TIPS
================================================================

  - The Aggregate is the most important tactical pattern — explain it with the
    "one transaction = one aggregate" rule.
  - Always contrast with Anemic Domain Model — shows you understand the pitfall.
  - Mention Java records for Value Objects (Java 16+) — shows modern Java knowledge.
  - Connect DDD to microservices: Bounded Context → microservice boundary.
  - Mention Domain Events → enables Event-Driven and Event Sourcing.
  - Real project story: "We modeled our billing domain with aggregates — Invoice
    was the root, with LineItems as entities. This prevented the bug where
    partial invoice updates were saved."
