================================================================
  ARCHITECTURAL PATTERNS — OVERVIEW
================================================================

  Definition:
    Architectural patterns are high-level strategies for organizing entire
    systems or major subsystems. They define how components communicate,
    how responsibilities are distributed, and how the system evolves.

  Patterns vs Design Patterns:
    Design patterns (GoF): class/object level — how to structure code.
    Architectural patterns: system/application level — how to structure modules,
    services, and their interactions.

  Scope of this section:
    - Layered Architecture (N-Tier)
    - MVC / MVP / MVVM
    - Hexagonal Architecture (Ports & Adapters)
    - Clean Architecture (Uncle Bob)
    - Domain-Driven Design (DDD)
    - CQRS (Command Query Responsibility Segregation)
    - Event-Driven Architecture
    - Microservices Architecture (see 09_Microservices)

  Why architectural patterns matter for 7+ YOE Java interviews:
    - Senior developers are expected to CHOOSE and JUSTIFY architecture,
      not just implement features.
    - Common questions: "How would you structure a new Spring Boot service?"
      or "How would you refactor a monolith?"
    - You need to articulate trade-offs, not just describe what a pattern is.

  Key trade-off dimensions:
    - Testability:        how easily can you unit/integration test components?
    - Maintainability:    how easily can new features be added without ripple effects?
    - Scalability:        how does the architecture handle load growth?
    - Deployability:      how independently can parts be deployed/changed?
    - Complexity:         how much cognitive overhead does the architecture add?

================================================================
LAYERED ARCHITECTURE (N-TIER)
================================================================

  Structure (top to bottom):
    Presentation Layer  → handles HTTP, UI input/output (Controller)
    Application Layer   → orchestrates use cases (Service)
    Domain Layer        → business rules, entities, value objects
    Infrastructure Layer→ DB, messaging, file system, external APIs (Repository)

  Flow: Request enters Presentation → delegated to Service → calls Repository
        → response flows back up.

  Pros:
    Simple mental model. Easy to onboard developers.
    Separation of concerns per layer.
    Spring Boot naturally maps to this (Controller / Service / Repository).

  Cons:
    Risk of "Big Ball of Mud" — layers may become tightly coupled over time.
    Everything depends on the Domain, but Domain may accumulate infrastructure
    concerns (Anemic Domain Model).
    Poor testability of inner layers if they depend on outer infrastructure.

  Standard Spring Boot pattern:
    @RestController → @Service → @Repository (JPA/Spring Data)

================================================================
QUICK REFERENCE: WHEN TO USE WHICH PATTERN
================================================================

  Layered         → simple CRUD services; small teams; clear layer boundaries.
  MVC             → web applications; REST APIs; UI rendering.
  Hexagonal       → complex domain; high testability required; multiple I/O adapters.
  Clean Arch      → long-lived apps; framework independence desired; strict rules.
  DDD             → complex business domain; multiple bounded contexts; large team.
  CQRS            → high read/write asymmetry; complex projections; event sourcing needs.
  Event-Driven    → decoupled services; async processing; eventual consistency OK.
  Microservices   → team scalability; independent deployability; large org.
