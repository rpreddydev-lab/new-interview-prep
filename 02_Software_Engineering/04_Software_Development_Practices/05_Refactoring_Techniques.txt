SECTION 1 — WHAT IS REFACTORING?
================================================================================

Q1: Define refactoring. How is it different from rewriting?

A: Refactoring is changing the INTERNAL STRUCTURE of code without changing its
   EXTERNAL BEHAVIOUR. The system's observable outputs must remain identical
   before and after each refactoring step.

   KEY DISTINCTION:
   - Refactoring: small, safe, behavior-preserving transformations; tests stay green
   - Rewriting: replace with new implementation; different risk/cost profile

   Martin Fowler's definition: "Refactoring is a disciplined technique for
   restructuring an existing body of code, altering its internal structure without
   changing its external behavior."

   WHEN TO REFACTOR (not a dedicated phase — continuous):
   ✓ Before adding a new feature (clean up the area you're working in)
   ✓ After a bug fix (understand why it was fragile; fix the root structure)
   ✓ During code review (author refactors based on feedback)
   ✓ When you find code that's hard to understand
   ✗ NOT when you're under emergency incident pressure
   ✗ NOT without tests in place (refactoring without tests is just gambling)

SECTION 2 — CORE REFACTORING CATALOG
================================================================================

Q2: What are the most important refactoring techniques every senior developer should know?

A: FROM FOWLER'S CATALOG — 10 MOST IMPORTANT:

─────────────────────────────────────────────────────────────────────────────
1. EXTRACT METHOD (most used)
   When: Method does too much; duplicated code; comment explains a block

   BEFORE:
   public double calculateBill(Subscriber sub, List<CDR> cdrs) {
       // Calculate usage charge
       double usageCharge = 0;
       for (CDR cdr : cdrs) {
           usageCharge += cdr.duration() * planRate(sub.planId());
       }
       // Apply loyalty discount
       double discount = sub.tenureMonths() >= 24 ? usageCharge * 0.10
                       : sub.tenureMonths() >= 12 ? usageCharge * 0.05 : 0;
       return usageCharge - discount + MONTHLY_FEE;
   }

   AFTER:
   public double calculateBill(Subscriber sub, List<CDR> cdrs) {
       double usageCharge = calculateUsageCharge(sub, cdrs);
       double discount = calculateLoyaltyDiscount(sub, usageCharge);
       return usageCharge - discount + MONTHLY_FEE;
   }

   private double calculateUsageCharge(Subscriber sub, List<CDR> cdrs) {
       return cdrs.stream()
           .mapToDouble(cdr -> cdr.duration() * planRate(sub.planId()))
           .sum();
   }

   private double calculateLoyaltyDiscount(Subscriber sub, double usageCharge) {
       if (sub.tenureMonths() >= 24) return usageCharge * 0.10;
       if (sub.tenureMonths() >= 12) return usageCharge * 0.05;
       return 0;
   }
   IntelliJ: Select code block → Ctrl+Alt+M (Mac: ⌘+Option+M)

─────────────────────────────────────────────────────────────────────────────
2. EXTRACT CLASS
   When: One class does work that should be done by two (violates SRP)

   BEFORE: BillingService handles CDR parsing AND rating AND invoice generation
   AFTER:  CdrParser, TariffRatingEngine, InvoiceGenerator — each focused

─────────────────────────────────────────────────────────────────────────────
3. MOVE METHOD
   When: A method uses more features of another class than its own

   BEFORE: BillingService.calculateDiscount(Subscriber sub) — uses only Subscriber data
   AFTER:  Move calculateDiscount() to Subscriber class itself
   Result: Fewer dependencies; better cohesion; Subscriber becomes richer domain object

─────────────────────────────────────────────────────────────────────────────
4. REPLACE CONDITIONAL WITH POLYMORPHISM
   When: switch/if-else on a type field dispatches different behavior

   BEFORE:
   double rate = switch (callType) {
       case "VOICE" -> voiceRate;
       case "SMS"   -> smsRate;
       case "DATA"  -> dataRate;
       default      -> throw new IllegalArgumentException(callType);
   };

   AFTER: (Strategy pattern / polymorphism)
   interface CallRater { double rate(CDR cdr); }
   class VoiceRater implements CallRater { ... }
   class SmsRater implements CallRater { ... }
   class DataRater implements CallRater { ... }
   Map<String, CallRater> raters = Map.of("VOICE", voiceRater, "SMS", smsRater, ...);
   double rate = raters.get(callType).rate(cdr);

─────────────────────────────────────────────────────────────────────────────
5. INTRODUCE PARAMETER OBJECT
   When: Multiple parameters always travel together across method signatures

   BEFORE:
   void rateCdr(String callId, String fromMsisdn, LocalDateTime startTime,
                int durationSeconds, String callType) { ... }

   AFTER:
   record CdrKey(String callId, String fromMsisdn, LocalDateTime startTime,
                 int durationSeconds, String callType) {}
   void rateCdr(CdrKey cdr) { ... }

─────────────────────────────────────────────────────────────────────────────
6. REPLACE MAGIC NUMBER WITH SYMBOLIC CONSTANT
   BEFORE: if (duration > 14400) { // suspicious call
   AFTER:  private static final int MAX_LEGITIMATE_CALL_SECONDS = 4 * 60 * 60;
           if (duration > MAX_LEGITIMATE_CALL_SECONDS) {

─────────────────────────────────────────────────────────────────────────────
7. RENAME (Method / Variable / Class)
   The most frequently performed refactoring. Naming is the most powerful
   communication tool in code.

   BEFORE: void calc(Subscriber s, List<CDR> c) { ... }
   AFTER:  void generateMonthlyInvoice(Subscriber subscriber, List<CDR> cdrs) { ... }
   IntelliJ: Shift+F6 everywhere (propagates to all callers)

─────────────────────────────────────────────────────────────────────────────
8. REPLACE TEMP WITH QUERY
   When: A local variable stores the result of a recomputable expression

   BEFORE:
   double base = usageCharge + accessFee;
   double total = base - discount;

   AFTER (if base is always derivable):
   private double baseCharge() { return usageCharge() + ACCESS_FEE; }
   double total = baseCharge() - discount;

─────────────────────────────────────────────────────────────────────────────
9. HIDE DELEGATE (Encapsulate calls through intermediary)
   When: Clients call a chain like a.getB().getC().doSomething() (Law of Demeter)

   BEFORE: subscriber.getPlan().getRate().getPeakRate()
   AFTER:  subscriber.getPeakRate()
           // Subscriber delegates internally: return plan.getRate().getPeakRate();

─────────────────────────────────────────────────────────────────────────────
10. INLINE METHOD
    When: A method body is as clear as its name; method adds no value

    BEFORE:
    boolean isActive(Subscriber s) { return s.status() == Status.ACTIVE; }
    if (isActive(subscriber)) { ... }

    AFTER (if isActive is trivially obvious):
    if (subscriber.status() == Status.ACTIVE) { ... }

SECTION 3 — JAVA-SPECIFIC REFACTORINGS
================================================================================

Q3: What Java-specific refactoring opportunities appear most in real codebases?

A:
   1. REPLACE LOOP WITH STREAM:
      BEFORE:
      List<String> activeMsisdns = new ArrayList<>();
      for (Subscriber s : subscribers) {
          if (s.status() == Status.ACTIVE) activeMsisdns.add(s.getMsisdn());
      }

      AFTER:
      List<String> activeMsisdns = subscribers.stream()
          .filter(s -> s.status() == Status.ACTIVE)
          .map(Subscriber::getMsisdn)
          .collect(Collectors.toList());

   2. REPLACE NULL RETURN WITH OPTIONAL:
      BEFORE: public Subscriber findByMsisdn(String msisdn) { return null; }
      AFTER:  public Optional<Subscriber> findByMsisdn(String msisdn) { return Optional.empty(); }

   3. REPLACE CHECKED EXCEPTION WITH UNCHECKED:
      BEFORE: public Invoice generate() throws BillingException { ... }
      AFTER:  public Invoice generate() { ... }  // throw BillingRuntimeException

   4. REPLACE ANONYMOUS CLASS WITH LAMBDA:
      BEFORE: cdrs.sort(new Comparator<CDR>() {
                  public int compare(CDR a, CDR b) { return a.startTime().compareTo(b.startTime()); }
              });
      AFTER:  cdrs.sort(Comparator.comparing(CDR::startTime));

   5. USE RECORD FOR DATA CARRIERS:
      BEFORE: class CdrKey { private final String callId; ... getters, equals, hashCode, toString }
      AFTER:  record CdrKey(String callId, String fromMsisdn, LocalDateTime startTime) {}

   6. REPLACE INSTANCEOF CHAIN WITH SEALED/SWITCH:
      BEFORE: if (event instanceof CallStarted) { ... } else if (event instanceof CallEnded) { ... }
      AFTER:  return switch (event) {
                  case CallStarted cs -> handleStart(cs);
                  case CallEnded ce   -> handleEnd(ce);
              };

SECTION 4 — SAFE REFACTORING PROCESS
================================================================================

Q4: How do you refactor safely in a codebase with limited tests?

A: SAFE REFACTORING PROCESS (5 steps):

   1. GET TESTS IN PLACE FIRST (characterization tests)
      - Write tests that capture current behaviour — even if it's "wrong"
      - These tests lock in existing behaviour as your safety net
      - Use TestContainers/MockMvc for integration-level characterization tests

   2. SMALL STEPS — one transformation at a time
      - Extract one method, verify green, commit
      - Move one method, verify green, commit
      - Never two structural changes in one commit

   3. COMPILE AFTER EACH CHANGE
      - Static type checking catches most structural errors immediately
      - Use IDE refactoring tools (not manual search-replace) — they update references

   4. RUN TESTS AFTER EACH STEP
      - If tests go red, immediately undo the last change (don't accumulate changes)
      - `git stash` or IDE local history as rollback

   5. REVIEW THE DIFF BEFORE COMMITTING
      - Make sure only structural changes are present, not behavioural changes
      - Reviewers should only see method moves, renames, extractions — not logic changes

   KEY PRINCIPLE: Behaviour-changing code and refactoring go in SEPARATE commits.
   This makes git bisect effective and code review clear.

QUICK REFERENCE CHEAT SHEET
================================================================================

TOP 10 REFACTORINGS:
1.  Extract Method          — split overlong methods
2.  Extract Class           — split God classes (SRP)
3.  Move Method             — put methods with their data
4.  Replace Cond w/ Polymorphism — eliminate type-switch sprawl
5.  Introduce Parameter Object — reduce parameter lists
6.  Magic Number → Constant — self-documenting constants
7.  Rename                  — most frequent, most impactful
8.  Replace Temp w/ Query   — reduce local variable clutter
9.  Hide Delegate           — Law of Demeter; reduce coupling chains
10. Inline Method           — remove unnecessary indirection

JAVA-SPECIFIC:
  Loop → Stream | null → Optional | Anonymous → Lambda | Class → Record
  Checked exception → Runtime exception | instanceof chain → sealed switch

SAFE PROCESS:
  Tests first → Small steps → Compile after each → Test after each → Review diff
  Behaviour changes and refactoring in SEPARATE commits

INTELLIJ SHORTCUTS (Mac):
  Extract method:    ⌘ + Option + M
  Rename:            Shift + F6
  Extract variable:  ⌘ + Option + V
  Inline:            ⌘ + Option + N
  Move:              F6
  Safe delete:       Alt + Delete
