SECTION 1 — PURPOSE AND PRINCIPLES
================================================================================

Q1: What is the purpose of code review, and what should it NOT be?

A: CODE REVIEW PURPOSES:
   ✓ Knowledge sharing — spreads understanding of codebase across the team
   ✓ Defect detection — catches bugs, edge cases, missing error handling
   ✓ Consistency — enforces coding standards, naming, patterns
   ✓ Mentorship — junior devs learn from senior feedback; seniors stay sharp
   ✓ Architecture alignment — ensures changes fit the overall design
   ✓ Bus factor reduction — at least two people understand each change

   CODE REVIEW SHOULD NOT BE:
   ✗ A gatekeeping exercise used to delay or block work
   ✗ A style nitpick marathon (use linters/formatters to automate style)
   ✗ An ego competition ("my way is better")
   ✗ A replacement for design discussions (align BEFORE writing code)
   ✗ A blame mechanism

──────────────────────────────────────────────────────────────────────────────
Q2: What should you look for in a code review as a reviewer?

A: REVIEW CHECKLIST — ordered by importance:

   1. CORRECTNESS (highest priority)
      - Does the code do what the PR description says?
      - Are edge cases handled? (null inputs, empty collections, boundary values)
      - Are error/exception cases handled gracefully?
      - Are there off-by-one errors in loops or index calculations?

   2. SECURITY
      - Is user input validated/sanitised before use?
      - Are secrets hardcoded? (should be in env vars or secrets manager)
      - Are SQL queries parameterised? (no string concatenation)
      - Are file paths validated? (path traversal risk)
      - Is sensitive data logged?

   3. PERFORMANCE
      - Are there N+1 query patterns? (fetching inside a loop)
      - Are expensive operations in hot paths (inner loops, per-request)?
      - Is caching used where appropriate?
      - Are large collections streamed or loaded entirely into memory?

   4. DESIGN AND ARCHITECTURE
      - Does the change fit the existing architecture?
      - Is there unnecessary coupling introduced?
      - Could this logic be reused elsewhere? Should it be extracted?
      - Does it violate SOLID principles?

   5. TESTABILITY AND TESTS
      - Are there meaningful unit tests covering happy path AND error cases?
      - Are the tests readable and maintainable?
      - Do the tests test behaviour, not implementation details?
      - Is test coverage adequate for the complexity?

   6. READABILITY
      - Are names descriptive and consistent with the codebase conventions?
      - Are complex logic sections commented where necessary?
      - Is the code simple enough that a new team member could understand it?

   7. STYLE (lowest — should be automated)
      - Formatting, import ordering, etc. → Use Checkstyle/SpotBugs/SonarLint

SECTION 2 — AUTHOR BEST PRACTICES
================================================================================

Q3: What makes a good pull request from the author's perspective?

A: BEFORE SUBMITTING:
   ✓ Self-review first — read your own diff line by line
   ✓ Run tests, linters, and build locally
   ✓ Keep PRs small: < 400 lines of production code is the target
   ✓ One logical change per PR (not "refactor + feature + bugfix")
   ✓ Write a clear PR description:
     - WHAT changed
     - WHY (link to ticket/story)
     - HOW to test it
     - Any concerns or decisions the reviewer should know about

   PR DESCRIPTION TEMPLATE:
   ## Summary
   [1-2 sentence overview of the change]

   ## Motivation
   [Why is this change needed? Link to ticket: JIRA-123]

   ## Changes
   - Added SubscriberRatingService to handle CDR rating logic
   - Extracted TariffPlanRepository from BillingService (SRP)
   - Added integration tests for peak-hour boundary conditions

   ## Testing
   - Unit tests: SubscriberRatingServiceTest (15 new tests)
   - Manual: tested with sample CDR file containing 1000 records
   - Edge cases: zero-duration calls, missing tariff plan, DST boundary

   ## Concerns / Discussion Points
   - TariffPlan loading uses in-memory cache; needs review for distributed env

Q4: How do you handle review comments as an author?

A: GOOD PRACTICES:
   ✓ Respond to every comment (even just "Done" or "Fixed in commit abc123")
   ✓ If you disagree, explain why — don't silently ignore
   ✓ If you don't understand, ask for clarification before guessing
   ✓ Don't take feedback personally — it's about the code, not you
   ✓ If a fix is significant, ask for a re-review, don't just dismiss

   RESOLVING VS ACKNOWLEDGING:
   - "Done" = you made the change the reviewer suggested
   - "Discussed offline, going with X because..." = you disagreed and resolved it
   - "Will address in follow-up PR" = valid for non-blocking nits

SECTION 3 — REVIEWER ETIQUETTE
================================================================================

Q5: How should you write actionable, respectful review comments?

A: INSTEAD OF:                          BETTER:
   "This is wrong."                     "This will fail if msisdn is null —
                                         can we add a null check here?"

   "Why did you do it this way?"        "I notice you're loading all subscribers
                                         at once. For large datasets, would it be
                                         worth streaming instead? Happy to discuss."

   "This needs to be refactored."       "This method is doing both CDR parsing and
                                         rate calculation. Could we extract
                                         parseCdr() to follow SRP?"

   "Use Optional here."                 "[nit] Optional.ofNullable() here would
                                         make the null handling explicit.
                                         Up to you — not blocking."

   COMMENT PREFIXES (convention):
   [nit]      — nitpick; optional; not blocking
   [question] — asking for understanding; not a change request
   [blocker]  — must be fixed before merge
   [future]   — not for this PR; create a ticket

──────────────────────────────────────────────────────────────────────────────
Q6: How should code review be structured in terms of timing and turnaround?

A: SLA GUIDELINES (team agreement):
   - Author notifies reviewers when PR is ready (Slack, JIRA)
   - Reviewers provide first feedback within 1 business day
   - After author addresses comments, re-review within 4 hours (same day)
   - Don't let PRs sit for > 2 days without a response

   REVIEW SESSION TIME:
   - < 400 lines: spend 30–60 minutes max
   - > 400 lines: split into multiple PRs or focus review session + pair review
   - Never approve a PR just because it's been waiting long ("approval by fatigue")

   APPROVAL RULES (examples):
   - 1 approval from senior engineer for production code
   - 2 approvals for database schema changes or security-sensitive code
   - Author cannot approve their own PR

SECTION 4 — AUTOMATING CODE REVIEW
================================================================================

Q7: What tools automate code review concerns in Java projects?

A:
   STATIC ANALYSIS:
   - Checkstyle:   coding conventions, naming, formatting
   - SpotBugs:     null pointer bugs, synchronization issues, bad practices
   - PMD:          code complexity, unused code, copy-paste detection
   - SonarQube:    combines all above + security hotspots + coverage tracking
   - Error Prone:  Google's annotation-driven compiler checks
   - NullAway:     null-safety analysis using @NonNull / @Nullable

   SECURITY SCANNING:
   - OWASP Dependency-Check: CVEs in Maven/Gradle dependencies
   - Trivy: container image vulnerability scanning
   - Snyk: dependency + container scanning with fix suggestions

   CODE COVERAGE:
   - JaCoCo:       line/branch coverage; enforce minimum thresholds in CI
   - Enforce in Maven:
     <jacoco:check>
       <rules>
         <rule>
           <limits>
             <limit><counter>LINE</counter><minimum>0.80</minimum></limit>
           </limits>
         </rule>
       </rules>
     </jacoco:check>

   CI INTEGRATION:
   - All tools run in CI (GitHub Actions, Jenkins) on every PR
   - PR is BLOCKED from merging if quality gates fail
   - Review comments are posted automatically by SonarQube bot

SECTION 5 — JAVA-SPECIFIC REVIEW CHECKLIST
================================================================================

Q8: What Java-specific issues do you look for in code reviews?

A: JAVA CODE REVIEW CHECKLIST:

   NULLABILITY:
   □ All public method parameters null-checked or annotated @NonNull
   □ Optional not used as a parameter type (only as return type)
   □ No return null from methods that return Optional

   EXCEPTIONS:
   □ Specific exceptions caught, not Exception or Throwable
   □ Resources closed with try-with-resources
   □ Never swallow exceptions silently (empty catch block)
   □ Checked exceptions not used for non-recoverable errors

   CONCURRENCY:
   □ Shared mutable state protected by synchronization or concurrent collections
   □ No double-checked locking without volatile
   □ Executor services shut down properly (shutdownNow in finally)
   □ ThreadLocal values cleaned up (remove() in finally)

   COLLECTIONS:
   □ No concurrent modification during iteration (ConcurrentModificationException)
   □ HashMap with non-trivial keys has correct equals+hashCode
   □ List.of() / Map.of() used for immutable collections (Java 9+)

   PERFORMANCE:
   □ String concatenation in loops uses StringBuilder
   □ Stream.collect(Collectors.toList()) vs toUnmodifiableList() intentional
   □ No reflection in tight loops
   □ JDBC: PreparedStatement used (not Statement for user input)

   EQUALS AND HASHCODE:
   □ If equals() is overridden, hashCode() is also overridden
   □ equals() is consistent with compareTo() for sorted collections

QUICK REFERENCE CHEAT SHEET
================================================================================

PR SIZE TARGET: < 400 lines production code; < 200 is ideal
REVIEW TURNAROUND: first review within 1 business day
COMMENT PREFIXES: [blocker] | [nit] | [question] | [future]

TOP 5 THINGS TO CATCH:
1. Missing null/empty checks on public API boundaries
2. N+1 database queries in loops
3. Exception swallowing (empty catch block)
4. Shared mutable state without synchronization
5. Missing test coverage for error paths

AUTOMATE EVERYTHING STYLISTIC:
  Checkstyle → style
  SpotBugs   → null/sync bugs
  SonarQube  → overall quality gate
  JaCoCo     → coverage threshold
  OWASP DC   → dependency CVEs

AUTHOR MINDSET: "Help the reviewer understand my intent"
REVIEWER MINDSET: "Help the author improve the code"
