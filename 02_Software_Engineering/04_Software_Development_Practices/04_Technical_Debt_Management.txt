SECTION 1 — WHAT IS TECHNICAL DEBT?
================================================================================

Q1: Define technical debt and its types. How is it different from "bad code"?

A: Technical debt is the implied cost of future rework caused by choosing an
   easier (but limited) solution now instead of a better approach that would
   take longer.

   Coined by Ward Cunningham (1992) as a deliberate metaphor to financial debt:
   - PRINCIPAL: the rework needed to implement the right solution
   - INTEREST: the extra time all future development costs because of the debt
   - COMPOUNDING: interest grows as debt-laden code is built on top of debt

   "BAD CODE" vs TECHNICAL DEBT:
   - Bad code = sloppiness, incompetence, no intent
   - Technical debt = a CONSCIOUS trade-off (or accumulated shortcuts over time)
   - Both require cleanup, but technical debt is a business/strategy conversation

   TYPES OF TECHNICAL DEBT:

   1. DELIBERATE (Prudent) — "We know we should do X, but we'll ship now and fix later"
      Example: Hardcoding a tariff rate to hit a launch deadline, with a JIRA ticket created
      Risk: Low if the ticket is actually addressed

   2. ACCIDENTAL (Prudent) — "We didn't know the better approach at the time"
      Example: No ORM transaction management, adding explicit transaction handling later
      Risk: Low — normal learning/evolution

   3. DELIBERATE (Reckless) — "We don't have time for proper design"
      Example: Skipping CDR deduplication because it's hard; bugs in production
      Risk: HIGH — creates cascading problems

   4. ACCIDENTAL (Reckless) — "What's encapsulation?"
      Example: 3000-line God class with no tests
      Risk: HIGHEST — system entropy; very costly to unravel

SECTION 2 — MEASURING TECHNICAL DEBT
================================================================================

Q2: How do you measure technical debt objectively?

A: QUANTITATIVE METRICS:

   SONARQUBE DEBT RATIO (SQALE model):
   - Technical Debt Ratio = (Remediation Cost) / (Development Cost) × 100%
   - < 5%  = Grade A (clean code)
   - 5–10% = Grade B (some debt)
   - > 50% = Grade E (critical)
   - SonarQube estimates remediation time per issue (e.g., each complexity
     violation = 5 mins, each security issue = 30 mins)

   CODE COMPLEXITY (Cyclomatic Complexity):
   - McCabe's metric: number of independent paths through a method
   - Target: < 10 per method, < 30 per class
   - High complexity = hard to test, hard to understand, fragile
   - Tool: PMD, SonarQube, IntelliJ inspections

   TEST COVERAGE:
   - Low coverage = dangerous debt; untested code has unknown behaviour
   - Target: 80% line coverage for business logic; 60% overall
   - JaCoCo + Maven: fail build if coverage drops below threshold

   DUPLICATION RATIO:
   - Target: < 3% code duplication
   - Duplicated code = two places to update when logic changes → bugs
   - PMD CPD (Copy-Paste Detector), SonarQube

   BUILD AND COMPILE WARNINGS:
   - Unchecked casts, raw types, deprecated API usage
   - Treat warnings as errors in new modules: <compilerArg>-Werror</compilerArg>

   QUALITATIVE METRICS:
   - "Broken window" density: how often devs say "I'm afraid to touch X"
   - Time to onboard: how long a new dev needs to understand a module
   - Bug clustering: 80% of bugs come from 20% of the code

Q3: How do you estimate the business impact of technical debt?

A: COST OF DEBT FRAMEWORK:

   1. FEATURE VELOCITY IMPACT:
      - Before cleanup: adding feature takes 5 days (navigating complexity)
      - After cleanup: same feature takes 1 day
      - Debt cost = 4 days/feature × expected features = 40 dev-days/quarter

   2. INCIDENT/BUG RATE:
      - Debt-laden code has 3× bug rate vs clean code (based on studies)
      - Incident cost = (bug frequency) × (MTTR) × (team cost + revenue impact)

   3. OPPORTUNITY COST:
      - Time spent on workarounds and fire-fighting = time NOT spent on innovation

   PRESENTING TO STAKEHOLDERS:
   "This module currently takes 3 days to add a new tariff type due to its
    architecture. After refactoring (2 sprints), the same change will take 4 hours.
    Given our roadmap has 8 tariff changes planned this year, we save 8 × 2.6 days
    = ~21 dev-days, recovering the refactoring investment in Q2."

SECTION 3 — PRIORITIZING DEBT PAYDOWN
================================================================================

Q4: How do you decide WHICH technical debt to pay down first?

A: PRIORITIZATION FRAMEWORK (4 criteria):

   1. FREQUENCY OF CHANGE:
      - Modules that change often AND have debt compound their cost fastest
      - Use git log to find most-frequently-changed files
      - Command: git log --format=format: --name-only | sort | uniq -c | sort -rg | head -20

   2. BLAST RADIUS:
      - How many teams/services depend on this module?
      - High blast radius → high risk of regressions; high priority to clean up

   3. CURRENT PAIN:
      - Where are bugs clustered? (JIRA analysis)
      - Where do devs complain most in retrospectives?
      - Where does onboarding take longest?

   4. CLEANUP COST vs. BENEFIT:
      - A 10-day cleanup that saves 1 day/year → not worth it now
      - A 2-day cleanup that saves 20 days/quarter → do it immediately

   DEBT QUADRANT (plot for each module):
              HIGH pain / LOW change     HIGH pain / HIGH change
                  (tolerate for now)         (fix ASAP)
              LOW pain / LOW change      LOW pain / HIGH change
                  (ignore)                   (monitor)

──────────────────────────────────────────────────────────────────────────────
Q5: What strategies exist for paying down technical debt incrementally?

A: STRATEGIES:

   1. BOY SCOUT RULE ("Leave the campsite cleaner than you found it")
      - Every time you touch a file, clean up ONE small thing (rename, extract method)
      - No dedicated cleanup sprint needed; happens naturally over time
      - Caveat: don't refactor so much that code review becomes a mess

   2. STRANGLER FIG PATTERN (Martin Fowler)
      - Build the new implementation alongside the old one
      - Gradually route traffic/calls to the new system
      - Retire the old code once the new one is proven
      - Classic for migrating legacy systems without big-bang rewrites

   3. TECHNICAL DEBT SPRINTS
      - Dedicate 10–20% of each sprint to debt work (e.g., 1 out of every 5 stories)
      - OR one full sprint per quarter for targeted debt reduction
      - Must be visible on the backlog with acceptance criteria

   4. MIKADO METHOD (dependency visualization)
      - Draw a graph of what depends on what before refactoring
      - Work from leaves inward, never break the build
      - Allows safe incremental changes in complex codebases

   5. FEATURE FLAGS + PARALLEL IMPLEMENTATION
      - Write the new clean implementation behind a feature flag
      - Test in production with a small percentage of traffic
      - Remove old code once confident

SECTION 4 — PREVENTING ACCUMULATION
================================================================================

Q6: How do you prevent technical debt from accumulating in the first place?

A: PROCESS CONTROLS:

   DEFINITION OF DONE (DoD) — include debt prevention:
   □ Code reviewed by ≥ 1 senior engineer
   □ Unit tests cover happy path + error cases
   □ SonarQube quality gate passes (coverage, complexity, duplication)
   □ No new TODOs without linked JIRA tickets
   □ Architecture decision logged if new pattern introduced

   ARCHITECTURAL REVIEW:
   - Design discussions BEFORE implementation for cross-cutting concerns
   - Architecture Decision Records (ADRs) to document WHY decisions were made
   - Prevents "we didn't know there was a standard approach" debt

   DEPENDENCY HYGIENE:
   - Dependabot / Renovate Bot: auto-PRs for dependency updates
   - Keep dependencies current → prevents security + API-compatibility debt
   - OWASP Dependency-Check: block builds with HIGH CVEs

   CODE OWNERSHIP:
   - CODEOWNERS file in git: specific teams own specific directories
   - Prevents orphan code (no one responsible = no one maintains it)

   DOCUMENTATION AS CODE:
   - ADRs (Architectural Decision Records): docs/adr/0001-use-cqrs.md
   - OpenAPI specs for all REST APIs (auto-generated from code)
   - Reduces "unknown intent" debt

Q7: How did you handle technical debt in a previous project? (behavioral answer)

A: STRUCTURE: Situation → Task → Action → Result (STAR)

   EXAMPLE ANSWER:
   "In my role at [company], our CDR billing engine was a 4000-line monolithic class
   that handled parsing, rating, invoice generation, and persistence. New tariff plan
   types took 3-5 days each to add safely, and we had frequent regressions.

   I identified this as high-priority debt: the class was touched in 60% of all PRs
   (git log analysis) and had < 20% test coverage.

   I proposed a 2-sprint refactoring plan:
   1. First, we added comprehensive tests (without changing behavior) to create a
      safety net. This raised coverage to 75%.
   2. Then we applied SRP: extracted CdrParser, TariffRatingEngine, InvoiceGenerator,
      and BillingRepository as separate classes.
   3. We used the Strangler Fig pattern — each extracted class was introduced behind
      a feature flag and verified against the old output before switching.

   Result: New tariff type implementation dropped from 3-5 days to 4-6 hours.
   Bug rate in billing dropped 60% over the next quarter. The team's retrospective
   feedback was significantly more positive about working on that module."
