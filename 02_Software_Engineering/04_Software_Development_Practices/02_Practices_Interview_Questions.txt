  SOFTWARE DEVELOPMENT PRACTICES — INTERVIEW Q&A
================================================================

  Level:    Senior (7–10+ YOE)
  Frequency: High — behavioral and process questions for lead/senior roles.

SECTION 1: AGILE & PROCESS
================================================================

  Q1: Describe your experience working in an Agile team.
  -------------------------------------------------------
  A: STRUCTURE YOUR ANSWER (use STAR: Situation, Task, Action, Result):
     "At [Company], I was part of a cross-functional Scrum team of 8 developers
     working in 2-week sprints. As a senior developer, I was involved in:
     - Sprint planning: breaking down epics into user stories, estimating complexity.
     - Code reviews: enforcing architectural guidelines, mentoring junior developers.
     - Sprint retrospectives: identifying process improvements (e.g., we introduced
       feature flags to reduce deployment risk, cutting our rollback rate by 60%).
     - Technical refinement: working with the PO to clarify acceptance criteria and
       identify technical constraints before a story entered the sprint."

  Q2: How do you handle situations where business pressure conflicts with technical quality?
  ------------------------------------------------------------------------------------------
  A: This is a common tension. My approach:
     1. QUANTIFY the risk: "Shipping without tests means we have no regression safety.
        Based on our history, that likely means 2–3 production incidents next quarter."
     2. PROPOSE a middle ground: "We can ship the feature now AND create a tech debt
        ticket to add test coverage in the next sprint — I'll prioritize it myself."
     3. INVOLVE the PO: make the trade-off explicit. POs can make better decisions
        when they understand the technical risk in business terms.
     4. If overridden: document the decision, create the debt ticket, and monitor the impact.
     I've found that most POs appreciate transparency — they don't want surprises.


  Q3: What makes a good user story?
  -----------------------------------
  A: INVEST criteria:
     Independent: can be delivered without depending on other stories.
     Negotiable:  details can be discussed and refined.
     Valuable:    delivers value to the end user or business.
     Estimable:   can be estimated (not too vague or too large).
     Small:       completable in one sprint.
     Testable:    acceptance criteria are clear and verifiable.

     Format: "As a [user], I want to [action] so that [benefit]."
     Good acceptance criteria: specific, testable, covers happy path AND error cases.

     Bad story: "As an admin, I want to manage users." (Too large, not testable)
     Good story: "As an admin, I want to deactivate a user account so that they
     can no longer log in. Given an active user, when I click 'Deactivate' and
     confirm, then the user status is INACTIVE and their next login fails."

SECTION 2: TDD & TESTING
================================================================

  Q4: How do you apply TDD in a Spring Boot project?
  ---------------------------------------------------
  A: I apply TDD at the unit test level (domain and service logic):
     1. Write a failing JUnit 5 test for the use case.
     2. Implement the minimum domain/service code to pass it.
     3. Refactor while keeping tests green.

     For the persistence layer: @DataJpaTest provides a JPA slice context —
     I write repository tests after the interface is defined.
     For controllers: @WebMvcTest slices the web layer — test after the service
     contract is finalized.

     I don't TDD infrastructure configuration (Kafka config, security config) —
     this is tested through integration tests with @SpringBootTest and Testcontainers.

     Key tools: JUnit 5, AssertJ (fluent assertions), Mockito (mocking), Testcontainers.


  Q5: What is the test pyramid and how do you apply it?
  -------------------------------------------------------
  A:
     Unit Tests (base — most):
       Fast (milliseconds), isolated (mocked dependencies), many.
       Test business logic: domain services, value objects, use cases.
       Coverage target: ~80% of business logic.

     Integration Tests (middle):
       Test component interactions: controller → service → repository → DB.
       Use @SpringBootTest (partial or full context), @DataJpaTest, Testcontainers.
       Slower (seconds), fewer than unit tests.
       Cover happy path and key error scenarios.

     End-to-End / Contract Tests (apex — fewest):
       Test full system flows (HTTP request → DB → response).
       Very slow. Run in CI, not local dev loop.
       Consumer-driven contract tests (Pact) for microservice boundaries.

     Anti-pattern to avoid: Testing Ice Cream Cone — many E2E tests, few unit tests.
     E2E tests are slow, brittle, and hard to debug.


  Q6: How do you test code that depends on the current date/time?
  ---------------------------------------------------------------
  A: Never use LocalDateTime.now() or System.currentTimeMillis() directly in
     business logic — it makes tests non-deterministic.

     Use Java's Clock interface:
       // Production: inject Clock.systemUTC()
       // Test: inject Clock.fixed(Instant.parse("2025-01-01T10:00:00Z"), ZoneOffset.UTC)

       @Service
       @RequiredArgsConstructor
       public class OrderExpirationService {
           private final Clock clock;

           public boolean isExpired(Order order) {
               return order.getCreatedAt().isBefore(LocalDateTime.now(clock).minusDays(30));
           }
       }

       // Test:
       Clock fixedClock = Clock.fixed(Instant.parse("2025-02-01T00:00:00Z"), ZoneOffset.UTC);
       OrderExpirationService service = new OrderExpirationService(fixedClock);
       assertThat(service.isExpired(orderCreatedOn("2025-01-01"))).isTrue();

SECTION 3: CODE QUALITY & REVIEWS
================================================================

  Q7: What do you look for when reviewing a pull request?
  --------------------------------------------------------
  A: I review in this order (most critical first):
     1. Correctness: does it solve the stated problem? Are edge cases handled?
     2. Tests: are there meaningful tests? Are they testing behavior, not implementation?
     3. Design: does it follow existing patterns? Are concerns separated?
        Is there an Anemic Domain Model? Any God classes forming?
     4. Naming and readability: do names express intent?
     5. Error handling: are exceptions meaningful? Is nothing swallowed silently?
     6. Performance: any N+1 query issues? Unnecessary data loading?
     7. Security: SQL injection? Auth checks on sensitive endpoints?

     I use SonarQube/SpotBugs for automated checks. Human review focuses on
     design decisions that tools can't catch.


  Q8: How do you approach refactoring a large legacy method?
  ----------------------------------------------------------
  A: Mikado Method / Boy Scout Rule approach:
     1. Write characterization tests first (what does the code CURRENTLY do?).
        These tests capture current behavior — regression safety net.
     2. Extract a small, well-named method from the beast.
     3. Run all tests — they must still pass.
     4. Commit.
     5. Repeat — small incremental steps.
     Never big-bang rewrites. Keep CI green at every step.

     If the method has no tests: write a coarse-grained integration test that
     covers the method's behavior from the outside, then refactor safely.


  Q9: How do you manage and reduce technical debt?
  -------------------------------------------------
  A:
     Visibility: I maintain a technical debt log in the team's backlog with
     labels, estimated effort, and business impact (production incidents caused,
     velocity slowdown).

     Prioritization: debt that actively slows the team (flaky tests, slow builds,
     complex code everyone fears touching) is prioritized above "nice-to-have" cleanups.

     Boy Scout Rule: when implementing a feature, I clean up the surrounding code.
     Small improvements compound over time.

     Reserve capacity: I negotiate with the PO to allocate 15–20% of sprint capacity
     to debt reduction. I frame it as "investment in delivery speed."

     Avoid big rewrites: I've seen "let's rewrite it all" projects fail catastrophically.
     Prefer incremental strangler fig pattern (add new behavior in clean code; redirect
     traffic; delete old code when fully replaced).

SECTION 4: SDLC & PROCESS
================================================================

  Q10: Describe your typical development workflow for a new feature.
  -----------------------------------------------------------------
  A:
     1. Refinement: discuss story with PO; clarify acceptance criteria; identify
        edge cases; note non-functional requirements (SLAs, security, monitoring).
     2. Design: sketch the approach; identify which patterns to use; review with team.
        For complex features: write an ADR (Architecture Decision Record).
     3. Branch: create a feature branch from main (GitFlow or trunk-based).
     4. TDD: write failing test → implement → refactor.
     5. Code review: create PR; request review; address feedback.
     6. CI checks: build + unit tests + integration tests + SonarQube gate pass.
     7. Merge + deploy to staging.
     8. QA / acceptance testing.
     9. Feature flag: enable gradually in production (canary release or feature toggle).
     10. Monitor: observe metrics/alerts post-deploy; respond quickly if issues.


  Q11: What is a Definition of Done, and why does it matter?
  -----------------------------------------------------------
  A: The Definition of Done is a shared, team-agreed checklist that a story
     must satisfy before it's considered complete. Without a DoD, "done" means
     different things to different people — leading to tech debt and production issues.

     Example DoD:
       □ Code implemented and compiles.
       □ Unit tests written and passing (coverage > 80% for new code).
       □ Integration tests passing.
       □ Code reviewed and approved by at least 2 peers.
       □ Sonar quality gate passed (no critical issues, no new security hotspots).
       □ Deployed to staging.
       □ Acceptance criteria verified by PO.
       □ Monitoring dashboards and alerts configured.
       □ API documentation updated (Swagger/OpenAPI).

     As a senior developer, I help define and uphold the DoD, and push back on
     stories being called "done" when DoD criteria aren't met.


================================================================
INTERVIEW TIPS
================================================================

  - Process questions are often combined with behavioral questions (STAR method).
    Always have 2–3 real stories ready about: a disagreement you resolved, a process
    improvement you drove, a debt you tackled, a mentoring experience.
  - Senior devs are expected to INFLUENCE process, not just follow it.
    Show that you've improved practices in your team.
  - Connect practices to outcomes: "after introducing TDD, our production
    incident rate dropped 40% in 6 months."
  - On Agile: avoid being dogmatic. "I've seen Scrum work well in product teams
    and Kanban work better in support teams. I adapt to what the team needs."
