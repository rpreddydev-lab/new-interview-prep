SECTION 1 — BRANCHING STRATEGIES
================================================================================

Q1: Compare Gitflow, GitHub Flow, and Trunk-Based Development.

A:
┌─────────────────┬──────────────────────┬─────────────────────┬─────────────────────┐
│ Aspect          │ Gitflow              │ GitHub Flow         │ Trunk-Based Dev     │
├─────────────────┼──────────────────────┼─────────────────────┼─────────────────────┤
│ Main branches   │ main + develop       │ main only           │ main only           │
│ Feature work    │ feature/* branches   │ short-lived feature │ short-lived branches│
│                 │ (can be long-lived)  │ branches            │ or direct to main   │
│ Release         │ release/* branch     │ deploy from main    │ deploy from main    │
│ Hotfix          │ hotfix/* from main   │ PR from main        │ PR from main        │
│ Deploy freq.    │ 1-2× per sprint      │ Many times/day      │ Many times/day      │
│ Team size       │ Large; waterfall     │ Small-medium; agile │ Any; CI/CD mature   │
│ Best for        │ Scheduled releases   │ Web services        │ High-frequency CD   │
│ Drawback        │ Complex merge hell   │ Loose governance    │ Requires feature    │
│                 │ Long-lived branches  │                     │ flags + solid CI    │
└─────────────────┴──────────────────────┴─────────────────────┴─────────────────────┘

   GITFLOW — BRANCH LIFECYCLE:
   main ←──── release/1.2 ←─── develop ←── feature/add-roaming-rates
                                         ←── feature/fraud-detector
   hotfix/fix-billing-bug ────────────→ main + develop

   TRUNK-BASED DEVELOPMENT:
   - Developers commit directly to main (or via very short-lived branches < 24h)
   - Feature flags hide unfinished work in production
   - CI runs on EVERY commit; build must stay green
   - No "integration hell" — conflicts found immediately

──────────────────────────────────────────────────────────────────────────────
Q2: When would you use Gitflow vs Trunk-Based Development?

A: USE GITFLOW WHEN:
   - Multiple versions in production simultaneously (enterprise software, mobile apps)
   - Scheduled release cycles (quarterly releases)
   - Regulatory compliance requires explicit release gates
   - Large team with dedicated QA phase before release
   - Example: Banking core system, embedded software, packaged software

   USE TRUNK-BASED DEVELOPMENT WHEN:
   - Continuous deployment to production is the goal
   - Single version in production (web services, microservices)
   - Small-to-medium teams with good CI coverage
   - Feature flags are in place to manage partial features
   - Example: SaaS platforms, microservices, internal tooling

   HYBRID (GitHub Flow):
   - Good middle ground: PR-based workflow without Gitflow complexity
   - main is always deployable
   - Features developed on short branches, merged via PR after review

SECTION 2 — MERGE VS REBASE
================================================================================

Q3: Explain merge vs rebase. When should each be used?

A: MERGE:
   Creates a merge commit joining two branch histories.
   git checkout main && git merge feature/my-feature

   Result:
   A─B─C─────M  ← main (M = merge commit)
       \   /
        D─E     ← feature/my-feature

   ✓ Preserves complete history exactly as it happened
   ✓ Non-destructive (original commits untouched)
   ✓ Easier to understand for large teams
   ✗ Creates "merge bubbles" that clutter linear history
   ✗ git log --oneline becomes noisy

   REBASE:
   Replays your commits on top of the target branch.
   git checkout feature/my-feature && git rebase main

   Result:
   A─B─C─D'─E'  ← feature replayed on top of main
         (D, E become D', E' — same content, new SHA)

   ✓ Clean linear history — easy to read with git log
   ✓ Easy git bisect (no merge commits to skip)
   ✗ Rewrites history (D→D', E→E') — breaks shared branches
   ✗ NEVER rebase a branch that others have already pulled

   GOLDEN RULE: Never rebase public/shared branches.
   Only rebase local branches before merging via PR.

   SQUASH MERGE (GitHub/GitLab):
   All commits in a PR squashed into one commit on main.
   ✓ Clean main history; each feature = one commit
   ✗ Loses individual commit granularity; harder to bisect

   TEAM CONVENTION RECOMMENDATION:
   - Rebase your feature branch on top of main before opening a PR
   - Squash merge to main (or merge commit — team decides)
   - Never force-push to main or develop

Q4: How do you resolve a complex merge conflict?

A: STEP-BY-STEP:
   1. Pull latest main: git fetch origin && git rebase origin/main
   2. Git marks conflict files with <<<<<<< / ======= / >>>>>>>
   3. Open IntelliJ's 3-way merge tool (Resolve Conflicts)
   4. Understand BOTH sides — don't blindly accept "ours" or "theirs"
   5. If unsure about intent of the conflicting change: talk to the other author
   6. After resolving: git add <file> && git rebase --continue
   7. Run ALL tests; build the project before pushing

   PREVENTING CONFLICTS:
   - Keep PRs small and short-lived (< 2 days on a branch)
   - Communicate in standups when working on shared files
   - Use feature flags so work can be merged but hidden
   - Rebase feature branch on main daily for long-running features

SECTION 3 — COMMIT HYGIENE
================================================================================

Q5: What makes a good commit message?

A: CONVENTIONAL COMMITS FORMAT (industry standard):
   <type>(<scope>): <short description>
   [blank line]
   [body: explain WHY, not WHAT]
   [blank line]
   [footer: BREAKING CHANGE: ... / Refs: JIRA-123]

   TYPES:
   feat:     new feature
   fix:      bug fix
   refactor: no behavior change (pure refactoring)
   test:     adding or fixing tests
   docs:     documentation only
   perf:     performance improvement
   chore:    build/dependency updates, CI changes
   revert:   revert a previous commit

   EXAMPLES:
   ✓ feat(billing): add loyalty discount for subscribers with 24+ months tenure
   ✓ fix(cdr-rating): correct off-peak boundary to include 20:00 (was 19:59)
   ✓ refactor(subscriber): extract CdrParser from BillingService (SRP)
   ✓ test(fraud-detector): add concurrent call limit scenario tests
   ✗ "fixed stuff"
   ✗ "WIP"
   ✗ "small change"
   ✗ "asdf"

   COMMIT BODY (explain the WHY):
   "fix(cdr-rating): correct off-peak boundary

   The original implementation used `hour < 20`, meaning 20:00 was treated
   as peak. Per the tariff document section 3.2, off-peak starts FROM 20:00.
   Changed to `hour >= 20` to include the 20:00-20:59 slot as off-peak.

   Refs: JIRA-BILLING-442"

──────────────────────────────────────────────────────────────────────────────
Q6: What is interactive rebase and when do you use it?

A: Interactive rebase lets you edit your commit history BEFORE pushing/merging.

   git rebase -i HEAD~5   ← edit last 5 commits

   Opens editor with:
   pick abc123 feat: add CDR parser
   pick def456 WIP - still debugging
   pick ghi789 fix typo
   pick jkl012 fix another typo
   pick mno345 test: add CDR parser tests

   COMMANDS PER COMMIT:
   pick   = keep as is
   squash = squash into previous commit (combine into one)
   fixup  = like squash but discard commit message
   reword = change the commit message
   drop   = remove the commit entirely
   edit   = pause here to amend this commit

   RESULT AFTER CLEANUP:
   pick abc123 feat: add CDR parser
   squash ghi789  (merge typo fix into feat)
   squash jkl012  (merge second typo fix into feat)
   pick mno345 test: add CDR parser tests
   drop def456    (remove WIP commit)

   WHEN TO USE:
   ✓ Before opening a PR to clean up "WIP" commits
   ✓ To split one large commit into smaller logical commits
   ✓ To combine many small fixup commits into one clean commit
   ✗ NEVER on already-pushed commits if others have pulled them

SECTION 4 — FEATURE FLAGS WITH GIT
================================================================================

Q7: How do feature flags support trunk-based development?

A: Feature flags (feature toggles) let you merge code into main while hiding
   the feature from users until it's ready.

   TYPES:
   - Release toggle:   hide incomplete feature from users
   - Ops toggle:       kill switch for performance/stability (e.g., disable fraud checker)
   - Experiment toggle: A/B testing (serve feature to 10% of subscribers)
   - Permission toggle: role-based feature access

   JAVA IMPLEMENTATION:
   // Simple properties-based toggle
   @Component
   public class FeatureFlags {
       @Value("${features.new-fraud-detector:false}")
       private boolean newFraudDetectorEnabled;

       public boolean isNewFraudDetectorEnabled() { return newFraudDetectorEnabled; }
   }

   // Usage:
   if (featureFlags.isNewFraudDetectorEnabled()) {
       alerts = newFraudDetector.check(cdr);
   } else {
       alerts = legacyFraudDetector.check(cdr);
   }

   TOOLS: LaunchDarkly, AWS AppConfig, Unleash, Spring Cloud Config

   WORKFLOW WITH TRUNK-BASED:
   1. Developer adds feature flag wrapping new code
   2. Merges to main with flag OFF
   3. CI deploys to production (feature hidden)
   4. When feature is validated, flip flag ON in config
   5. After stable period, remove old code + flag (cleanup sprint)

   FLAG DEBT WARNING: Feature flags that are never cleaned up become
   technical debt. Add a "remove flag" ticket when you create the flag.

SECTION 5 — MONOREPO VS POLYREPO
================================================================================

Q8: Compare monorepo and polyrepo for a microservices architecture.

A:
┌──────────────────┬───────────────────────────┬───────────────────────────┐
│ Aspect           │ Monorepo                  │ Polyrepo                  │
├──────────────────┼───────────────────────────┼───────────────────────────┤
│ Structure        │ All services in one repo  │ One repo per service      │
│ Code sharing     │ Easy — shared libraries   │ Hard — publish artifacts  │
│ Atomic changes   │ Cross-service refactoring │ Requires coordinated PRs  │
│                  │ in one commit             │ across repos              │
│ Build system     │ Needs smart CI (Bazel,    │ Simple — build each repo  │
│                  │ Turborepo, Nx, Maven       │ independently             │
│                  │ multi-module)             │                           │
│ Team ownership   │ Shared/global ownership   │ Clear team ownership      │
│ Discovery        │ Easy — one place          │ Scattered across repos    │
│ Used by          │ Google, Meta, Uber        │ Netflix, Amazon (early)   │
└──────────────────┴───────────────────────────┴───────────────────────────┘

   MONOREPO TOOLING FOR JAVA:
   - Maven multi-module: parent pom.xml with <modules> section
   - Gradle multi-project: settings.gradle with include()
   - Bazel / Buck: build-graph-aware, incremental builds
   - Nx (polyglot): affected-only builds, dependency graph

QUICK REFERENCE CHEAT SHEET
================================================================================

BRANCHING STRATEGY SELECTION:
  Scheduled release / multi-version → Gitflow
  Web service / SaaS / microservices → Trunk-based or GitHub Flow

MERGE vs REBASE:
  Merge:  preserves history; safe for shared branches; merge commits
  Rebase: clean linear history; local branches only; never public branches
  Squash: one commit per feature; clean main; loses granularity

COMMIT MESSAGES:
  Format: <type>(<scope>): <description>
  Types: feat | fix | refactor | test | docs | perf | chore | revert
  Body: explain WHY not WHAT; ref JIRA tickets

FEATURE FLAGS:
  Types: Release | Ops | Experiment | Permission
  Lifecycle: add → merge to main (OFF) → enable → cleanup (remove)

CONFLICT PREVENTION:
  Small PRs < 2 days | Daily rebase on main | Communicate in standups
  Feature flags for parallel long-running work

INTERACTIVE REBASE COMMANDS:
  pick | squash | fixup | reword | drop | edit
  Use: before opening PR to clean up local commits
  Never: after pushing to shared branches
