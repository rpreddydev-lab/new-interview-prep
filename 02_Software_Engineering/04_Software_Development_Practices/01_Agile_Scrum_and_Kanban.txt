================================================================
  AGILE, SCRUM & SOFTWARE DEVELOPMENT METHODOLOGIES
================================================================

  Frequency:  High — senior Java developers are expected to work in and
              sometimes lead Agile teams. Behavioral and process questions
              commonly appear in 7+ YOE interviews.

----------------------------------------------------------------
WATERFALL vs AGILE
----------------------------------------------------------------

  WATERFALL (Traditional):
    Sequential phases: Requirements → Design → Implementation → Testing → Deployment.
    All requirements gathered upfront. Long release cycles (months to years).
    Change mid-project is expensive. Works for fixed-requirements projects (construction).

  AGILE (Iterative):
    Iterative, incremental delivery. Requirements evolve based on feedback.
    Short cycles (sprints). Working software delivered frequently.
    Change welcomed even late in development.

  Agile Manifesto (2001) — four values:
    Individuals and interactions   OVER  processes and tools.
    Working software               OVER  comprehensive documentation.
    Customer collaboration         OVER  contract negotiation.
    Responding to change           OVER  following a plan.

  12 Agile Principles (key ones):
    - Deliver working software frequently (weeks, not months).
    - Continuous attention to technical excellence.
    - Simplicity — the art of maximizing work NOT done.
    - Self-organizing teams.
    - Regular team reflection and process adjustment.

----------------------------------------------------------------
SCRUM
----------------------------------------------------------------

  A specific Agile framework. Three pillars: Transparency, Inspection, Adaptation.

  ROLES:
    Product Owner (PO):  owns the product backlog; prioritizes features by business value;
                         represents stakeholders; writes user stories; accepts/rejects work.
    Scrum Master (SM):   facilitates the process; removes impediments; shields team;
                         NOT the team manager — servant leader.
    Development Team:    cross-functional (devs, QA, UX); self-organizing;
                         typically 5–9 people.

  EVENTS (Ceremonies):
    Sprint Planning:     2–4 hours; select backlog items for the sprint; agree on sprint goal.
    Daily Standup:       15 min; 3 questions: done yesterday? doing today? blockers?
    Sprint Review:       demo working software to stakeholders; get feedback.
    Sprint Retrospective: team inspects and improves: what went well? what to improve?
    Sprint:              1–4 week iteration; produces a potentially shippable increment.

  ARTIFACTS:
    Product Backlog:     ordered list of everything the product needs. Maintained by PO.
    Sprint Backlog:      items selected for current sprint + sprint plan. Owned by team.
    Increment:           working, tested software produced by end of sprint.

  DEFINITION OF DONE (DoD):
    Shared checklist: code written + reviewed + tested + documented + deployed to staging.
    Critical for quality gates. Senior devs help define and enforce DoD.

  STORY POINTS:
    Relative estimate of effort/complexity (Fibonacci: 1, 2, 3, 5, 8, 13, 21).
    Team velocity: average story points completed per sprint. Used for forecasting.

----------------------------------------------------------------
KANBAN
----------------------------------------------------------------

  Continuous flow instead of time-boxed sprints.
  Visualize work on a Kanban board (To Do → In Progress → Review → Done).
  Limit Work In Progress (WIP): prevent team from taking on too much simultaneously.
  Pull system: team pulls new work when capacity is available.

  Good for: support teams, ops, maintenance work where items flow continuously.
  Less formal than Scrum — no sprints, no fixed ceremonies.

  Scrum vs Kanban:
    Scrum: sprints, velocity, ceremonies, fixed team commitment per sprint.
    Kanban: continuous flow, WIP limits, cycle time metrics, no sprints.
    ScrumBan: hybrid (sprints from Scrum + WIP limits from Kanban).

TDD — TEST-DRIVEN DEVELOPMENT
----------------------------------------------------------------

  Write tests FIRST, then code to make them pass.

  RED-GREEN-REFACTOR cycle:
    RED:    write a failing test that describes desired behavior.
    GREEN:  write the MINIMUM code to make the test pass.
    REFACTOR: clean up code while keeping tests green.

  Benefits:
    - Tests are guaranteed to exist.
    - Forces thinking about the interface/API before implementation.
    - Design emerges from the tests (testability-first design).
    - Regression safety net for every future change.
    - 100% of new code is covered by tests.

  Example TDD cycle in Java:
    // RED: test fails — method doesn't exist
    @Test
    void shouldConfirmPendingOrder() {
        Order order = Order.createPending(customerId, items);
        order.confirm();
        assertThat(order.getStatus()).isEqualTo(OrderStatus.CONFIRMED);
    }

    // GREEN: minimal implementation
    public void confirm() {
        this.status = OrderStatus.CONFIRMED;
    }

    // REFACTOR: add proper validation
    public void confirm() {
        if (this.status != OrderStatus.PENDING)
            throw new InvalidOrderStateException("Only PENDING orders can be confirmed");
        this.status = OrderStatus.CONFIRMED;
    }

  Challenges:
    - Requires discipline; slow initially, faster long-term.
    - Hard to apply for UI and infrastructure code.
    - Legacy code without tests is hard to TDD (need to add tests first).

----------------------------------------------------------------
BDD — BEHAVIOR-DRIVEN DEVELOPMENT
----------------------------------------------------------------

  Extends TDD: write tests in natural language that domain experts can understand.
  Bridges gap between business and technical teams.

  GIVEN / WHEN / THEN format:
    GIVEN: initial context (system state before action).
    WHEN:  the action/event that occurs.
    THEN:  expected outcome.

  Example:
    Feature: Order confirmation
      Scenario: Confirm a valid pending order
        GIVEN an order in PENDING status with at least one item
        WHEN the customer confirms the order
        THEN the order status should be CONFIRMED
        AND a confirmation notification should be sent

  Java tools:
    - Cucumber: write scenarios in Gherkin (GIVEN/WHEN/THEN) in .feature files.
                Step definitions in Java map to the scenario steps.
    - JBehave: similar to Cucumber.
    - Spring Boot: Cucumber integrates via @CucumberContextConfiguration.

  BDD vs TDD:
    TDD: developer-centric; tests written in code.
    BDD: business-centric; scenarios written in natural language shared with PO.
    BDD tests are typically integration/acceptance tests; TDD tests are unit tests.

CODE REVIEW PRACTICES
----------------------------------------------------------------

  Purpose:
    - Catch bugs before they reach production.
    - Ensure code adheres to team standards and architecture.
    - Knowledge sharing within the team.
    - Mentoring junior developers.
    - Second pair of eyes on design decisions.

  Effective code review checklist (reviewer perspective):
    □ Does the code solve the intended problem correctly?
    □ Are there test cases for new behavior?
    □ Is the code readable and self-documenting?
    □ Are there any obvious performance issues?
    □ Does it follow SOLID principles? Any code smells?
    □ Is error handling appropriate?
    □ Are there any security concerns (SQL injection, auth checks, etc.)?
    □ Does it break any existing functionality?

  Good code review culture:
    - Be KIND: critique code, not the person. "This method could be split" not "you did this wrong."
    - Be SPECIFIC: "Extract lines 45-60 into a private method for clarity."
    - Be TIMELY: aim to review within 24 hours; unreviewed PRs block teammates.
    - Keep PRs small: large PRs (1000+ lines) get superficial reviews. Aim for <400 lines.
    - Use automated tools first: SonarQube, Checkstyle, SpotBugs handle style/static analysis.
      Human reviewers focus on design and correctness.

  For authors:
    - Write a clear PR description: what changed, why, how to test.
    - Link to the JIRA ticket / user story.
    - Respond to all comments (resolve or discuss).
    - Don't take feedback personally.

TECHNICAL DEBT
----------------------------------------------------------------

  Definition (Ward Cunningham):
    Technical debt is the cost of future rework caused by choosing an expedient
    solution now instead of a better approach that would take longer.

  Types:
    Deliberate / Reckless: "We know it's wrong but we're shipping it anyway."
    Deliberate / Prudent:  "We'll do this quick fix and document what needs to change." ✓
    Inadvertent / Reckless: "What do you mean there's coupling?" (ignorance).
    Inadvertent / Prudent:  "Now we see how we should have done it." (learning).

  Common sources:
    - Shortcuts under deadline pressure (copy-paste code, hardcoded values).
    - Outdated dependencies (security vulnerabilities, API incompatibilities).
    - Missing test coverage (changes require full manual regression).
    - Over-engineered abstractions that are now abandoned.
    - Monolithic codebase that was never modularized.

  Managing technical debt:
    - Make it VISIBLE: maintain a tech debt backlog; estimate the cost.
    - Prioritize ruthlessly: fix debt that slows down development most.
    - Boy Scout Rule: leave the code better than you found it (small incremental improvements).
    - Reserve capacity: dedicate 10–20% of each sprint to tech debt reduction.
    - Never go dark: don't pause all feature work for a "big refactor" — do it incrementally.

  Communicating debt to non-technical stakeholders:
    Frame as business risk: "This untested module causes 3 production incidents per quarter.
    Fixing it will reduce our on-call time by 40%." (Cost of NOT fixing it.)

SDLC — SOFTWARE DEVELOPMENT LIFECYCLE
----------------------------------------------------------------

  Key phases:
    1. Planning:      scope, timeline, resources, risk assessment.
    2. Requirements:  functional and non-functional requirements; user stories.
    3. Design:        architecture, data model, API contracts, sequence diagrams.
    4. Development:   coding, code reviews, unit tests.
    5. Testing:       integration, performance, security, UAT.
    6. Deployment:    CI/CD pipeline, release notes, rollback plan.
    7. Maintenance:   monitoring, bug fixes, feature iterations.

  In Agile: these phases happen within each sprint iteratively, not sequentially.

  DevOps shifts left: testing and security start at development time (shift-left testing).

COMMON INTERVIEW QUESTIONS
================================================================

  Q: What is the difference between Scrum and Kanban?
  A: Scrum is a time-boxed framework with sprints (1–4 weeks), fixed ceremonies,
     story-pointed work, and a sprint commitment. Kanban is a continuous flow
     system with WIP limits and no time-boxing. Scrum works well for product
     feature teams with predictable planning cadences. Kanban works better for
     support, ops, or maintenance teams with unpredictable incoming work.

  Q: What is TDD and what are its benefits?
  A: TDD is writing a failing test first, then writing the minimum code to pass it,
     then refactoring. Benefits: guaranteed test coverage, design-first thinking,
     regression safety. Challenges: requires discipline, hard on legacy code.

  Q: How do you handle technical debt in your team?
  A: I make debt visible in the backlog, estimate its cost in team velocity terms,
     and allocate ~15% of each sprint to debt reduction. I apply the Boy Scout Rule
     during feature work — improve the code you touch. I frame debt to stakeholders
     as business risk ("this is causing X incidents per quarter") to gain prioritization.

  Q: How do you give and receive code review feedback?
  A: Give: be specific, constructive, and timely. Focus on the code, not the person.
     Use questions ("What do you think about...") instead of directives.
     Receive: assume positive intent. All feedback is about code quality,
     not personal judgment. Respond to every comment — either resolve or discuss.
     A good review makes both the reviewer and author better developers.
