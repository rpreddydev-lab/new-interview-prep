================================================================
  FACTORY METHOD PATTERN
================================================================

  Category:   Creational
  Intent:     Define an interface for creating an object, but let subclasses
              decide which class to instantiate. Lets a class defer
              instantiation to subclasses.
  Also known as: Virtual Constructor
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Very common in interviews and in frameworks.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Client code needs to work with products but should not be coupled to
  specific product classes. The exact type of object to create may depend
  on context, configuration, or subclass.

  Without Factory Method:
    Client code has `new EmailNotifier()` or `new SMSNotifier()` — tightly coupled.
    Adding a new type requires changing every client location.

  With Factory Method:
    Client works with abstract `Notifier`. Subclass decides which concrete
    Notifier to create. Adding new types requires no client changes.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Product          -- Abstract product interface/class.
  ConcreteProduct  -- Actual implementation of Product.
  Creator          -- Abstract class declaring the factory method.
                      May provide a default implementation.
  ConcreteCreator  -- Overrides factory method to return ConcreteProduct.
  Client           -- Calls creator.createProduct() without knowing the type.

----------------------------------------------------------------
STRUCTURE VISUALIZATION
----------------------------------------------------------------

  Creator (abstract)
    + someOperation()     <-- uses the product
    + createProduct()     <-- factory method (abstract or default)
         |
         |  overrides
         v
  ConcreteCreator
    + createProduct()     <-- returns ConcreteProduct

  Product (interface)
    + use()
         |
         |  implements
         v
  ConcreteProduct
    + use()

  Creator.someOperation() calls this.createProduct() internally.
  ConcreteCreator decides what gets returned.

----------------------------------------------------------------
FULL JAVA EXAMPLE — NOTIFICATION SYSTEM
----------------------------------------------------------------

  // Product interface
  public interface Notifier {
      void send(String message);
  }

  // Concrete Products
  public class EmailNotifier implements Notifier {
      @Override
      public void send(String message) {
          System.out.println("Email: " + message);
      }
  }

  public class SMSNotifier implements Notifier {
      @Override
      public void send(String message) {
          System.out.println("SMS: " + message);
      }
  }

  public class PushNotifier implements Notifier {
      @Override
      public void send(String message) {
          System.out.println("Push: " + message);
      }
  }

  // Creator (abstract)
  public abstract class NotificationService {
      // Factory Method — subclass defines this
      protected abstract Notifier createNotifier();

      // Template method using the factory method
      public void notifyUser(String message) {
          Notifier notifier = createNotifier();
          notifier.send(message);
      }
  }

  // Concrete Creators
  public class EmailNotificationService extends NotificationService {
      @Override
      protected Notifier createNotifier() { return new EmailNotifier(); }
  }

  public class SMSNotificationService extends NotificationService {
      @Override
      protected Notifier createNotifier() { return new SMSNotifier(); }
  }

  // Client
  public class AlertSystem {
      public static void main(String[] args) {
          NotificationService service = new EmailNotificationService();
          service.notifyUser("Your order has shipped!");

          service = new SMSNotificationService();
          service.notifyUser("OTP: 123456");
      }
  }

  Output:
    Email: Your order has shipped!
    SMS: OTP: 123456

PARAMETERIZED FACTORY METHOD (SIMPLER VARIANT)
----------------------------------------------------------------

  Instead of subclassing Creator, pass a parameter to decide product type.
  This is the "Simple Factory" — NOT a GoF pattern, but very commonly used.

    public class NotifierFactory {
        public static Notifier create(String type) {
            switch (type) {
                case "EMAIL": return new EmailNotifier();
                case "SMS":   return new SMSNotifier();
                case "PUSH":  return new PushNotifier();
                default: throw new IllegalArgumentException("Unknown type: " + type);
            }
        }
    }
    // Usage: Notifier n = NotifierFactory.create("EMAIL");

  Problem: switch/if-else grows with each new type. Violates Open/Closed Principle.
  Fix: Use a registry map:

    private static final Map<String, Supplier<Notifier>> registry = new HashMap<>();
    static {
        registry.put("EMAIL", EmailNotifier::new);
        registry.put("SMS",   SMSNotifier::new);
        registry.put("PUSH",  PushNotifier::new);
    }
    public static Notifier create(String type) {
        Supplier<Notifier> supplier = registry.get(type);
        if (supplier == null) throw new IllegalArgumentException("Unknown: " + type);
        return supplier.get();
    }

  New types: just add to registry. No switch changes.

----------------------------------------------------------------
FACTORY METHOD WITH JAVA 8+ FUNCTIONAL STYLE
----------------------------------------------------------------

  public enum NotifierType {
      EMAIL(EmailNotifier::new),
      SMS(SMSNotifier::new),
      PUSH(PushNotifier::new);

      private final Supplier<Notifier> supplier;

      NotifierType(Supplier<Notifier> supplier) { this.supplier = supplier; }

      public Notifier create() { return supplier.get(); }
  }

  // Usage:
  Notifier n = NotifierType.EMAIL.create();

----------------------------------------------------------------
FACTORY METHOD IN JAVA STANDARD LIBRARY
----------------------------------------------------------------

  Calendar.getInstance()          -- returns Calendar subclass based on locale/timezone
  NumberFormat.getInstance()      -- returns locale-specific NumberFormat
  ResourceBundle.getBundle()      -- loads locale-specific bundle
  Border.createLineBorder()       -- javax.swing returns concrete Border
  Iterator from Collection.iterator() -- each collection returns its own Iterator impl

  Spring:
    BeanFactory.getBean()         -- returns correct concrete bean by type/name
    @Bean factory method          -- @Configuration class method acts as factory method

----------------------------------------------------------------
ADVANTAGES
----------------------------------------------------------------

  1. Open/Closed: add new product types by adding new ConcreteCreator.
     No changes to existing code.
  2. Decoupling: Creator works against Product interface, not concrete types.
  3. Flexibility: ConcreteCreator can decide at runtime which product to create.
  4. Named constructors: factory methods can have descriptive names
     (Color.fromHex(), User.createGuest()).

----------------------------------------------------------------
DISADVANTAGES
----------------------------------------------------------------

  1. Class explosion: each new product requires a new ConcreteCreator subclass.
  2. Complexity: adds indirection that may be unnecessary for simple cases.
  3. Inheritance dependency: Creator must be subclassed; inflexible if subclassing
     is inconvenient (e.g., class is final).

----------------------------------------------------------------
FACTORY METHOD vs ABSTRACT FACTORY
----------------------------------------------------------------

  Factory Method:
    - One product.
    - Creation via subclassing (method override).
    - Focus: "One thing — let subclass decide which type."

  Abstract Factory:
    - Family of related products.
    - Creation via object composition (factory object passed in).
    - Focus: "Set of related things — keep family consistent."

  Abstract Factory often uses Factory Methods internally.

----------------------------------------------------------------
FACTORY METHOD vs SIMPLE FACTORY
----------------------------------------------------------------

  Simple Factory (NOT a GoF pattern):
    - One class with a static or instance method.
    - All creation logic in one place.
    - Easy but violates OCP on growth.

  Factory Method (GoF):
    - Creation delegated to subclasses.
    - Fully open/closed — new types don't require changing existing factories.
    - More complex but more extensible.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Factory Method pattern?
  A: Define an interface for creating an object, but let subclasses decide
     which concrete class to instantiate. The Creator defines a factory
     method; ConcreteCreator overrides it. Client uses abstract Creator,
     never coupling to concrete classes.

  Q: What's the difference between Factory Method and Simple Factory?
  A: Simple Factory is a static method or utility class that creates objects.
     Factory Method is an OO pattern using polymorphism — subclasses override
     a factory method. Simple Factory violates OCP when new types are added;
     Factory Method doesn't.

  Q: How does Spring use the Factory Method pattern?
  A: @Bean methods in @Configuration classes are factory methods. Spring invokes
     them to obtain bean instances. BeanFactory.getBean() also follows
     factory method semantics.

  Q: Give a real-world analogy for Factory Method.
  A: A job application form (Creator) has a section: "What vehicle do you use?"
     (factory method). The job type (subclass) determines what vehicle is created:
     delivery driver creates a Truck, cyclist creates a Bicycle.

  Q: When would you use a Supplier<T> or lambda instead of Factory Method?
  A: For simple cases where the factory logic is trivial and no subclassing
     is needed. For example, `Supplier<Notifier> factory = EmailNotifier::new`
     is cleaner than writing a full NotifierFactory class hierarchy for a simple case.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Know both the GoF Factory Method (subclass-based) and the common Simple Factory.
  - Be able to convert a switch-statement factory into a registry map — shows OCP awareness.
  - Mention named constructors: `Color.fromRGB()` vs `new Color(r,g,b)` — expressiveness benefit.
  - When drawing the UML mentally: Creator has the factory method, ConcreteCreator overrides it.
