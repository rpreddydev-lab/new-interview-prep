================================================================
  BUILDER PATTERN
================================================================

  Category:   Creational
  Intent:     Separate the construction of a complex object from its
              representation so that the same construction process can
              create different representations.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Very high in interviews. Easiest to implement and explain.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  TELESCOPING CONSTRUCTOR ANTI-PATTERN:
    A class with many optional fields leads to multiple constructors
    or one huge constructor with many null/default parameters.

    User(String name)
    User(String name, String email)
    User(String name, String email, int age)
    User(String name, String email, int age, String phone)
    ... (explodes exponentially)

    Or: new User("Alice", null, 25, null, null, "admin")  -- confusing

  BUILDER SOLUTION:
    User user = new User.Builder("Alice")
        .email("alice@example.com")
        .age(25)
        .role("admin")
        .build();

  Clear, readable, flexible. Only set the fields you need.

----------------------------------------------------------------
JAVA BUILDER — INNER STATIC CLASS PATTERN (MOST COMMON)
----------------------------------------------------------------

  public class User {
      // All fields final — immutable after construction
      private final String name;    // required
      private final String email;   // optional
      private final int    age;     // optional
      private final String phone;   // optional
      private final String role;    // optional

      // Private constructor — only Builder can call
      private User(Builder builder) {
          this.name  = builder.name;
          this.email = builder.email;
          this.age   = builder.age;
          this.phone = builder.phone;
          this.role  = builder.role;
      }

      // Getters
      public String getName()  { return name; }
      public String getEmail() { return email; }
      public int    getAge()   { return age; }

      @Override
      public String toString() {
          return "User{name=" + name + ", email=" + email +
                 ", age=" + age + ", phone=" + phone + ", role=" + role + "}";
      }

      // Static inner Builder class
      public static class Builder {
          // Required field
          private final String name;
          // Optional fields with defaults
          private String email = null;
          private int    age   = 0;
          private String phone = null;
          private String role  = "user";

          public Builder(String name) {
              this.name = name;
          }

          public Builder email(String email) { this.email = email; return this; }
          public Builder age(int age)         { this.age = age;     return this; }
          public Builder phone(String phone)  { this.phone = phone; return this; }
          public Builder role(String role)    { this.role = role;   return this; }

          // Validation + build
          public User build() {
              if (name == null || name.isEmpty()) throw new IllegalStateException("Name required");
              return new User(this);
          }
      }
  }

  // Client usage
  User user = new User.Builder("Alice")
      .email("alice@example.com")
      .age(28)
      .role("admin")
      .build();

BUILDER WITH DIRECTOR (GoF ORIGINAL FORM)
----------------------------------------------------------------

  GoF Builder adds a Director class that orchestrates the build process.
  Used when the same build steps create different product representations.

    public interface PizzaBuilder {
        PizzaBuilder size(String size);
        PizzaBuilder addCheese();
        PizzaBuilder addPepperoni();
        PizzaBuilder addSauce(String sauce);
        Pizza build();
    }

    public class MargheritaBuilder implements PizzaBuilder {
        // builds a Margherita
    }
    public class PepperoniBuilder implements PizzaBuilder {
        // builds a Pepperoni pizza
    }

    public class PizzaDirector {
        public Pizza makeSpecialtyPizza(PizzaBuilder builder) {
            return builder.size("large").addCheese().addSauce("tomato").build();
        }
    }

  Director separates the ORDER of construction steps from how they're implemented.
  In modern Java, the Director role is often omitted — client calls builder steps directly.

----------------------------------------------------------------
BUILDER VALIDATION PATTERN
----------------------------------------------------------------

  Best practice: validate inside build(), not in setters.
  Allows partial construction of the builder freely; only reject at final build().

    public User build() {
        if (name == null || name.isEmpty())
            throw new IllegalStateException("Name is required");
        if (age < 0 || age > 150)
            throw new IllegalArgumentException("Age out of range");
        if (email != null && !email.contains("@"))
            throw new IllegalArgumentException("Invalid email");
        return new User(this);
    }

----------------------------------------------------------------
BUILDER vs COPY CONSTRUCTOR / WITH METHODS
----------------------------------------------------------------

  Java 16+ Records with "wither" approach:
    record User(String name, String email, int age) {
        User withName(String name)   { return new User(name, this.email, this.age); }
        User withEmail(String email) { return new User(this.name, email, this.age); }
    }
  OK for small immutable objects; Builder preferred for many optional fields.

  Lombok @Builder (annotation-based):
    @Builder
    public class User {
        private String name;
        private String email;
        private int age;
    }
    // Lombok generates the entire Builder automatically.
    // Usage: User.builder().name("Alice").age(28).build();

  Lombok @Builder.Default for default values:
    @Builder.Default
    private String role = "user";

BUILDER IN JAVA STANDARD LIBRARY AND FRAMEWORKS
----------------------------------------------------------------

  StringBuilder / StringBuffer
    sb.append("Hello").append(" ").append("World").toString()

  ProcessBuilder (build a system process)
    new ProcessBuilder("ls", "-la").directory(new File("/tmp")).start()

  UriComponentsBuilder (Spring MVC)
    UriComponentsBuilder.fromHttpUrl("http://api.example.com")
        .path("/users/{id}").buildAndExpand(42).toUri()

  MockMvcRequestBuilders (Spring Test)
    MockMvcRequestBuilders.get("/users/1")
        .contentType(MediaType.APPLICATION_JSON)
        .header("Authorization", "Bearer token")

  WebClient.Builder (Spring WebFlux)
    WebClient.builder().baseUrl("http://service").defaultHeader(...).build()

  HttpRequest.Builder (Java 11+ HttpClient)
    HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com"))
        .GET()
        .header("Accept", "application/json")
        .build()

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Time:  O(1) per field setter, O(1) for build().
  Space: O(1) — builder holds same data as product.
  No performance overhead — just method calls and object construction.

----------------------------------------------------------------
BUILDER vs FACTORY
----------------------------------------------------------------

  Builder:
    - Complex object with many parts.
    - Client controls CONSTRUCTION STEPS.
    - Same process, different representations possible.
    - Product assembled incrementally.

  Factory (Method / Abstract):
    - Simple or medium-complexity objects.
    - Client doesn't control construction — factory decides everything.
    - One-step creation call.
    - Product returned fully formed.

  Rule of thumb:
    Many optional fields → Builder.
    Type varies but construction is simple → Factory.
    Both? Sometimes combined: Factory chooses WHICH builder to use.

----------------------------------------------------------------
IMMUTABILITY WITH BUILDER
----------------------------------------------------------------

  Builder pattern naturally creates IMMUTABLE objects:
    - All User fields are final.
    - No setters on User itself.
    - Only Builder has setters; User built once and never changed.

  This is preferred for:
    - Thread safety (no shared mutable state).
    - Domain objects / Value Objects in DDD.
    - API response objects.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What problem does the Builder pattern solve?
  A: Telescoping constructors — when a class has many optional fields,
     constructors become unmanageable. Builder provides a fluent API to
     set only the fields needed, with clear named parameters, validation
     at build time, and produces an immutable object.

  Q: Why make Builder a static inner class?
  A: Static inner class can access the outer class's private constructor.
     Being static means it doesn't require an outer class instance to create.
     This is the standard Java idiom for Builder.

  Q: What is the Director in GoF Builder?
  A: The Director orchestrates the build process — it calls the builder's
     methods in a specific sequence. Modern Java usually skips the Director
     and lets the client drive the sequence directly, which is simpler.

  Q: How is Builder different from Factory Method?
  A: Factory creates an object in ONE STEP — client just calls createProduct().
     Builder creates an object STEP BY STEP — client calls multiple setter-like
     methods and then build(). Builder is used when construction is complex.

  Q: Is Lombok @Builder the same as GoF Builder?
  A: It generates the same structure — inner static Builder class with fluent setters
     and a build() method. The pattern is the same; Lombok just eliminates boilerplate.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Always write the inner static Builder class in interviews — shows you know the pattern cold.
  - Mention validation in build() — shows defensive programming.
  - Contrast Builder vs Factory every time: "complex, multi-step" vs "simple, single-step."
  - Mention immutability — Builder naturally produces immutable objects.
  - Know Lombok @Builder for practical Java — shows framework awareness.
  - Mention UriComponentsBuilder / ProcessBuilder as standard library examples.
