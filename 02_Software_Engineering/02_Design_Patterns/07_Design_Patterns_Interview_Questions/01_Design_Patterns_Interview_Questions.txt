================================================================
  DESIGN PATTERNS — INTERVIEW QUESTIONS & ANSWERS
  (Creational + Structural + Behavioral)
================================================================

  Level:    Mid to Senior (5–10+ YOE)
  Frequency: Very High — expect at least 3–5 pattern questions per interview
  Key tip:  Know WHEN to use a pattern, WHEN NOT TO, and a Java/Spring real example.

================================================================
SECTION 1: GENERAL DESIGN PATTERN QUESTIONS
================================================================

  Q1: What are design patterns, and why do they matter?
  ------------------------------------------------------
  A: Design patterns are reusable, proven solutions to commonly occurring
     design problems in software. They are NOT code you copy — they are
     templates for solving classes of problems.

     They matter because:
       - Establish a shared vocabulary ("use Strategy here" communicates intent instantly).
       - Codify decades of industry experience (GoF: Gang of Four).
       - Improve code maintainability, flexibility, and testability.

     Three categories:
       Creational:  HOW objects are created (Singleton, Factory, Builder, Prototype).
       Structural:  HOW objects are composed (Adapter, Decorator, Proxy, Facade).
       Behavioral:  HOW objects communicate (Strategy, Observer, Command, Template Method).


  Q2: When should you NOT use a design pattern?
  -----------------------------------------------
  A: When it adds complexity without solving a real problem — an anti-pattern
     called "pattern fever." Signs you're over-engineering:
       - Only one implementation exists (interface not needed yet).
       - Team doesn't understand the pattern (hinders maintenance).
       - The pattern adds indirection without meaningful benefit.
       - YAGNI: you're designing for flexibility you don't need yet.

     Real principle: patterns solve problems. If the problem doesn't exist yet,
     don't apply the pattern. A simple, readable direct implementation often
     beats an over-abstracted "pattern-correct" solution.


  Q3: What is an Anti-Pattern? Name two common ones.
  ---------------------------------------------------
  A: Anti-patterns are common approaches that seem reasonable but consistently
     cause problems.

     God Object / God Class:
       A class that knows too much and does too much. Violates SRP.
       Symptom: a class with 50+ methods, used everywhere.
       Fix: decompose by responsibility; apply SRP.

     Singleton Overuse:
       Using Singleton for every shared resource creates hidden global state,
       breaks testability, and introduces concurrency bugs.
       Fix: use dependency injection (Spring IoC). Let the DI container manage
       single-instance lifecycle.

     Other common ones:
       - Golden Hammer: applying your favorite pattern everywhere.
       - Spaghetti Code: no clear structure; jumps between concerns.
       - Copy-Paste Programming: duplication instead of abstraction (violates DRY).
       - Magic Numbers: hardcoded values without explanation.

SECTION 2: CREATIONAL PATTERNS
================================================================

  Q4: Singleton — all implementation variants and which to prefer?
  ----------------------------------------------------------------
  A: Four safe implementations:
     1. Eager: static final field — simple, thread-safe (class loading), created at startup.
     2. Double-Checked Locking (DCL): volatile + synchronized block — lazy, thread-safe.
     3. Bill Pugh (Holder): private static inner class — lazy, thread-safe, no synchronization.
     4. Enum Singleton: immune to reflection attacks and serialization — Josh Bloch's recommendation.

     Prefer: Holder for general use; Enum when serialization safety is needed.
     In Spring: NEVER use manual Singleton — use Spring beans (default Singleton scope).
     Spring beans are testable (injectable), lifecycle-managed, and DI-compatible.

     Q: Why volatile in DCL?
     A: Without volatile, the JVM can reorder the three steps of object construction
        (allocate memory → initialize object → assign reference). Another thread could
        see a non-null but uninitialized object. volatile prevents this reordering.


  Q5: Factory Method vs Abstract Factory — what's the difference?
  ---------------------------------------------------------------
  A:
     Factory Method:
       Defines an interface for creating an object, but lets subclasses decide which
       class to instantiate. One product type, one factory method, multiple subclasses.

       Example: DocumentCreator with createDocument() → PdfCreator, WordCreator.

     Abstract Factory:
       Creates FAMILIES of related objects without specifying their concrete classes.
       Multiple product types, one factory interface per family.

       Example: UIComponentFactory with createButton() + createCheckbox().
       WindowsFactory creates WindowsButton + WindowsCheckbox.
       MacFactory creates MacButton + MacCheckbox.
       Client code works with UIComponentFactory — never knows Windows vs Mac.

     In Spring: ApplicationContext.getBean() acts as a factory. FactoryBean<T>
     is Spring's built-in factory method pattern for complex bean creation.


  Q6: Builder Pattern — when to use it and how does it differ from a constructor?
  -------------------------------------------------------------------------------
  A: Use Builder when:
     - A class has many constructor parameters (more than 3–4).
     - Some parameters are optional.
     - Order of parameters is error-prone.

     Advantages over telescoping constructors:
       - No positional parameter mistakes (username vs email swapped).
       - Self-documenting: builder.email("x").age(25).build() reads as English.
       - Can validate the object before construction (in build() method).

     In Java:
       - Lombok @Builder generates it automatically.
       - Java records have compact constructors for validation.
       - StringBuilder is a classic example.

     Example: HttpRequest.newBuilder().uri(URI).timeout(Duration).GET().build()

     GoF Builder vs Lombok @Builder:
       GoF: Director + Builder for complex step-by-step construction.
       Lombok @Builder: fluent API for field-by-field initialization.
       Lombok is overwhelmingly used in production Java code.


  Q7: Prototype Pattern — what is it and when would you use it in Java?
  --------------------------------------------------------------------
  A: Creates new objects by cloning an existing object (the prototype).
     Useful when object creation is expensive and a similar object already exists.

     Java implementation: implement Cloneable and override clone().
     Problem: clone() is shallow — nested mutable objects are shared.
     Deep clone: manually copy all nested objects, or use serialization.

     Modern alternative: copy constructors or builder-based copying:
       new User(existingUser.getName(), existingUser.getEmail())
     These are clearer and avoid clone()'s pitfalls.

     Real use: caching expensive database query results as prototypes;
     creating test data by cloning a base object and mutating specific fields.

SECTION 3: STRUCTURAL PATTERNS
================================================================

  Q8: Adapter Pattern — explain with a real Java example.
  -------------------------------------------------------
  A: Converts the interface of a class into another interface the client expects.
     Enables classes with incompatible interfaces to work together.

     Example: You have code using Iterator<T>, but a legacy library returns
     Enumeration<T>. Write an EnumerationIterator adapter that wraps Enumeration
     and implements Iterator — client code uses Iterator, adapter translates calls.

     In Spring:
       - HandlerAdapter in Spring MVC: adapts various handler types
         (methods, servlets, controllers) to the DispatcherServlet interface.
       - InputStreamReader: adapts InputStream (bytes) to Reader (chars).
       - Arrays.asList(): adapts array to List interface.


  Q9: Decorator vs Proxy — what is the difference?
  --------------------------------------------------
  A: Both wrap an object, but different intent:

     Decorator:
       ADDS behavior to an object dynamically at runtime.
       Both decorator and decorated implement the same interface.
       Client is AWARE it's using a decorator (wraps it explicitly).

       Example: BufferedInputStream wraps FileInputStream, adding buffering.
       Java I/O streams are the classic Decorator example.
       In Spring: @Transactional wraps service method with transaction behavior.

     Proxy:
       CONTROLS access to the real object (lazy loading, access control, caching, remote calls).
       Client is typically UNAWARE it's talking to a proxy.

       Example: Spring AOP creates dynamic proxies for @Transactional, @Cacheable,
       @PreAuthorize. Hibernate creates proxies for lazy-loaded associations.
       java.lang.reflect.Proxy (JDK dynamic proxy) and CGLIB are the mechanisms.


  Q10: Facade Pattern — when and why?
  ------------------------------------
  A: Provides a simplified interface to a complex subsystem.
     Hides complexity; clients interact with one simple entry point.

     Example: OrderFacade.placeOrder(request) internally calls:
       inventoryService.reserveItems()
       paymentService.charge()
       shippingService.scheduleDelivery()
       notificationService.sendConfirmation()
     Client only calls one method and is shielded from subsystem details.

     In Spring: @Service classes often act as facades — orchestrating multiple
     @Repository and other @Service calls behind a clean business method.
     Spring's JdbcTemplate is a facade over JDBC's complex Connection, Statement,
     ResultSet management.


  Q11: Composite Pattern — where does it appear in Java?
  -------------------------------------------------------
  A: Lets you treat individual objects and compositions (groups) of objects uniformly.
     Classic tree structure: both leaf and composite implement the same interface.

     Java examples:
       - File system: File and Directory both implement FileSystemNode.
       - UI: Component (Button, TextField, Panel) — Panel contains Components.
       - java.awt.Component hierarchy.

     Expression trees in stream/query builders also follow Composite:
       a Predicate can be a simple check or an AND/OR combination of Predicates.

SECTION 4: BEHAVIORAL PATTERNS
================================================================

  Q12: Strategy Pattern — real-world Java example?
  ------------------------------------------------
  A: Defines a family of algorithms, encapsulates each, makes them interchangeable.
     Enables behavior to vary independently from clients that use it.

     Example: SortContext uses a SortStrategy. Clients inject BubbleSortStrategy,
     QuickSortStrategy, or MergeSortStrategy at runtime without changing SortContext.

     In Java/Spring:
       - Comparator<T> is Strategy — pass different comparators to sort().
       - Spring Security AuthenticationStrategy.
       - Spring's PlatformTransactionManager: different strategies per database.
       - PaymentProcessor interface with CreditCardProcessor, PayPalProcessor.

     Modern Java: lambdas ARE one-method Strategy implementations:
       list.sort((a, b) -> a.getName().compareTo(b.getName()));
       The lambda is an anonymous Strategy object.


  Q13: Observer Pattern — how does Spring implement it?
  -------------------------------------------------------
  A: Defines one-to-many dependency: when one object changes state, all
     dependents are notified automatically.

     Spring implementation:
       1. Publish event: applicationEventPublisher.publishEvent(new UserCreatedEvent(user))
       2. Listen: @EventListener on a method in any @Component.

     Spring Event-driven model:
       - Synchronous by default (@EventListener).
       - Asynchronous with @Async + @EventListener.
       - @TransactionalEventListener: fires after transaction commits.

     Real use: UserService publishes UserCreatedEvent → WelcomeEmailListener,
     AuditListener, CacheInvalidationListener all react independently.
     Core service has zero knowledge of its observers.

     Java's Observable (deprecated) vs Spring Events vs Guava EventBus vs
     Reactor Flux: Spring Events are the standard in Spring Boot apps.


  Q14: Template Method Pattern — how does Spring use it?
  -------------------------------------------------------
  A: Defines the skeleton of an algorithm in a base class, deferring some steps
     to subclasses. Subclasses override specific steps without changing the algorithm's structure.

     Spring examples:
       - AbstractController: defines HTTP processing skeleton; subclasses implement
         handleRequestInternal().
       - JdbcTemplate: defines the execute-query-map skeleton; you provide the
         RowMapper (the varying step).
       - AbstractBatchConfiguration in Spring Batch.

     In your own code: define a base ReportGenerator with generate() that calls
     fetchData() + processData() + formatOutput(). Subclasses override each step.


  Q15: Command Pattern — explain with Spring use cases.
  -------------------------------------------------------
  A: Encapsulates a request as an object, allowing parameterization, queuing,
     logging, and undoable operations.

     Components: Command (interface), ConcreteCommand, Receiver, Invoker, Client.

     In Spring / Java:
       - Runnable and Callable are the Command pattern (tasks queued to ExecutorService).
       - Spring Batch StepExecution represents commands executed in sequence.
       - @Scheduled methods queued for later execution.
       - CQRS Command objects: CreateOrderCommand, CancelOrderCommand passed to
         CommandHandler — classic Command pattern.

     Undo support: maintain a history of Command objects; call undo() on each.


  Q16: Chain of Responsibility — where is it used in Java frameworks?
  -------------------------------------------------------------------
  A: Passes a request along a chain of handlers. Each handler decides to process
     or pass it to the next handler.

     Java/Spring examples:
       - Servlet FilterChain: SecurityFilter → LoggingFilter → AuthFilter → Servlet.
       - Spring Security filter chain (SecurityFilterChain).
       - Spring MVC HandlerInterceptor chain.
       - Middleware chains in any pipeline-based framework.

     Implementation: Handler interface with handle(request) and next handler reference.
     Each handler either processes or calls next.handle(request).


  Q17: State Pattern vs Strategy Pattern — what's the difference?
  ---------------------------------------------------------------
  A:
     Strategy: the algorithm/behavior is CHOSEN by the client and doesn't change
               during the object's lifetime. Client controls the strategy.
               Example: sorting algorithm selected at creation; stays fixed.

     State: the behavior changes AUTOMATICALLY as the object's INTERNAL STATE changes.
            The state object (not the client) determines which behavior runs next.
            Transitions happen inside the state objects themselves.
            Example: Order in states (PENDING → CONFIRMED → SHIPPED → DELIVERED).
            Each state's confirm(), ship(), deliver() behaves differently and
            transitions to the next state.

     Interview tip: "Strategy = behavior selected externally. State = behavior
     changes internally based on object's lifecycle."

SECTION 5: CONCURRENCY PATTERNS
================================================================

  Q18: Producer-Consumer — how do you implement it in Java?
  ----------------------------------------------------------
  A: Producer creates data and puts it in a shared buffer; Consumer takes from it.
     Decouples production rate from consumption rate.

     Java implementation with BlockingQueue:
       BlockingQueue<Task> queue = new LinkedBlockingQueue<>(capacity);

       // Producer thread:
       queue.put(task);      // blocks if full

       // Consumer thread:
       Task task = queue.take();  // blocks if empty

     BlockingQueue handles all synchronization internally.

     With ExecutorService:
       ExecutorService executor = Executors.newFixedThreadPool(N);
       executor.submit(() -> process(item));  // submit = produce; thread pool = consume

     Spring Integration / Kafka are enterprise-scale Producer-Consumer implementations.


  Q19: What threading issues can occur in a Spring application?
  -------------------------------------------------------------
  A: Spring beans are Singleton-scoped by default — one instance shared by all threads.

     If a @Service holds mutable instance state, it's a race condition:
       // DANGEROUS:
       @Service
       public class UserService {
           private List<String> tempResults = new ArrayList<>();  // shared mutable state!
       }

     Fix: make beans STATELESS (no instance-level mutable fields).
     If you need per-request state, use method-local variables or
     @Scope("request") scoped beans.

     @Transactional: Spring uses thread-local storage (TransactionSynchronizationManager)
     to bind a transaction to the current thread — safe for singleton beans.


================================================================
INTERVIEW TIPS
================================================================

  - For every pattern: explain INTENT, give a Java/Spring EXAMPLE, mention
    WHEN NOT TO USE.
  - GoF patterns you must know cold: Singleton, Factory Method, Builder,
    Strategy, Observer, Decorator, Proxy, Facade, Template Method, Chain of Responsibility.
  - Concurrency patterns are bonus points for senior roles — show you know
    BlockingQueue, volatile, and Spring's threading model.
  - Always connect patterns to frameworks you've used:
    "Decorator → Spring AOP / @Transactional"
    "Proxy → Spring's @Cacheable / Hibernate lazy loading"
    "Observer → Spring ApplicationEvents"
    "Strategy → Comparator / Spring PlatformTransactionManager"
  - When asked "design X" in an interview, call out which patterns you're
    using and WHY. This shows senior-level design thinking.
