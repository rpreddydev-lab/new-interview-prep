================================================================
  INTERFACE SEGREGATION PRINCIPLE (ISP)
================================================================

  Definition: Clients should not be forced to depend on interfaces
              they do not use.

  Robert C. Martin, 1996.

  In practice: Prefer small, focused interfaces over large, fat interfaces.
  A class implementing an interface should USE every method it implements.

----------------------------------------------------------------
THE PROBLEM: FAT INTERFACES
----------------------------------------------------------------

  A "fat" or "polluted" interface forces implementing classes to:
    - Provide empty implementations (throw or do nothing)
    - Implement methods they don't need
    - Change when unrelated clients change requirements

  This creates:
    - Unnecessary coupling between unrelated clients
    - UnsupportedOperationException everywhere (also LSP violation)
    - Hard-to-test classes (must stub/mock unneeded methods)

----------------------------------------------------------------
VIOLATION EXAMPLE
----------------------------------------------------------------

  // FAT interface — one interface for everything a "worker" does
  public interface Worker {
      void work();
      void eat();
      void sleep();
      void performMaintenance();
  }

  // Human worker: all methods make sense
  public class HumanWorker implements Worker {
      public void work()               { /* does work */ }
      public void eat()                { /* eats lunch */ }
      public void sleep()              { /* goes home */ }
      public void performMaintenance() { /* not applicable */ }
  }

  // Robot worker: can't eat or sleep — forced to implement meaninglessly
  public class RobotWorker implements Worker {
      public void work()    { /* does work */ }
      public void eat()     { throw new UnsupportedOperationException("Robots don't eat"); }
      public void sleep()   { throw new UnsupportedOperationException("Robots don't sleep"); }
      public void performMaintenance() { /* maintenance */ }
  }

  RobotWorker violates LSP (throws where parent doesn't) because the
  interface violated ISP (forced robots to "implement" eating).

----------------------------------------------------------------
FIX: SEGREGATE INTO ROLE INTERFACES
----------------------------------------------------------------

  // Segregated role interfaces
  public interface Workable {
      void work();
  }

  public interface Feedable {
      void eat();
  }

  public interface Sleepable {
      void sleep();
  }

  public interface Maintainable {
      void performMaintenance();
  }

  // Human implements only what humans do
  public class HumanWorker implements Workable, Feedable, Sleepable {
      public void work()  { /* does work */ }
      public void eat()   { /* eats lunch */ }
      public void sleep() { /* goes home */ }
  }

  // Robot implements only what robots do
  public class RobotWorker implements Workable, Maintainable {
      public void work()               { /* does work */ }
      public void performMaintenance() { /* maintenance */ }
  }

  // Client that only needs work() accepts Workable — narrowest interface
  public class WorkManager {
      public void assignWork(Workable worker) {
          worker.work();  // works for both Human and Robot
      }
  }

----------------------------------------------------------------
ISP IN PRACTICE — COLLECTION INTERFACES
----------------------------------------------------------------

  Java Collections are a great ISP example:

  Iterable<T>    -- just forEach/iterator
  Collection<T>  -- add, remove, contains, size
  List<T>        -- index-based access
  Set<T>         -- uniqueness guarantee
  Queue<T>       -- offer, poll, peek
  Deque<T>       -- double-ended operations
  Map<K,V>       -- key-value pairs

  You never implement one giant "CollectionEverything" interface.
  Each interface is a role with clear semantics.

  Client: "I only need to iterate" → accepts Iterable<T>
  Client: "I need index access"    → accepts List<T>
  Client: "I need to read only"    → accepts Collection<T> or Iterable<T>

----------------------------------------------------------------
ISP IN SPRING FRAMEWORK
----------------------------------------------------------------

  Spring makes heavy use of role interfaces:

  Ordered          -- getOrder() only
  BeanNameAware    -- setBeanName() only
  InitializingBean -- afterPropertiesSet() only
  DisposableBean   -- destroy() only
  ApplicationListener<E> -- onApplicationEvent() only
  HandlerInterceptor     -- preHandle, postHandle, afterCompletion (all optional via defaults)

  A Spring bean implements only the lifecycle hooks it needs.
  It's not forced to implement all lifecycle methods.

  HandlerInterceptor uses DEFAULT METHODS for ISP:
  interface HandlerInterceptor {
      default boolean preHandle(...)        { return true; }
      default void postHandle(...)          {}
      default void afterCompletion(...)     {}
  }

  Client implements only the methods it cares about. ISP via defaults.

----------------------------------------------------------------
ISP AND DEFAULT METHODS (JAVA 8+)
----------------------------------------------------------------

  Default methods provide backward-compatible ISP:
    - Add new methods to interfaces without breaking all implementations
    - Implementing class overrides only what's relevant

  Comparable vs Comparator:
    Comparable: compareTo() only — natural ordering
    Comparator: compare() + many default methods (reversed, thenComparing, etc.)
    Client: only has to implement compare(). Defaults provide composition.

  // ISP with defaults in custom validator
  public interface Validator<T> {
      boolean validate(T t);   // must implement

      // Default methods: compositional utilities — not required to override
      default Validator<T> and(Validator<T> other) {
          return t -> this.validate(t) && other.validate(t);
      }

      default Validator<T> or(Validator<T> other) {
          return t -> this.validate(t) || other.validate(t);
      }
  }

ISP AND DEPENDENCY INVERSION
----------------------------------------------------------------

  ISP and DIP work together:
    DIP: depend on abstractions, not concrete.
    ISP: make the abstraction as narrow as possible.

  "Depend on the narrowest interface sufficient for your needs."

  // BAD: depends on entire UserService (wide interface)
  public class ReportGenerator {
      private final UserService userService;  // has 20 methods; only need getUserById
  }

  // GOOD: depends on only what's needed
  public interface UserReader {
      Optional<User> findById(Long id);
  }

  public class ReportGenerator {
      private final UserReader userReader;  // only 1 method
  }

  UserService implements UserReader (plus other interfaces).
  ReportGenerator's dependency is testable with a one-method fake.

----------------------------------------------------------------
ISP VIOLATION DETECTION CHECKLIST
----------------------------------------------------------------

  [ ] Method throws UnsupportedOperationException
  [ ] Method has empty body where logic was expected
  [ ] Tests need to mock/stub many methods to test one behavior
  [ ] Interface has methods from unrelated concerns
  [ ] Multiple unrelated teams change the same interface

  Any YES = consider interface segregation.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is ISP and why does it matter?
  A: ISP says don't force clients to depend on methods they don't use.
     A fat interface creates accidental coupling: changing a method used by
     client A forces recompilation of client B even if B doesn't call it.
     Fix: split into role interfaces; clients depend on only their role.

  Q: How does ISP relate to LSP?
  A: Fat interfaces often force LSP violations. If an interface forces
     a class to implement inapplicable methods, the class throws
     UnsupportedOperationException — breaking the substitutability
     contract (LSP). ISP prevents the need for these empty/throwing overrides.

  Q: How does Java 8 default methods help with ISP?
  A: Default methods let interface designers add new methods without breaking
     existing implementors. Implementing classes override only what's relevant.
     HandlerInterceptor and Comparator use this to let clients implement
     only the methods they need.

  Q: How narrow should an interface be?
  A: "Interface should contain only the methods needed by a particular client."
     If two different clients use two disjoint method sets, split the interface.
     In practice: start with cohesive interfaces (related methods together);
     split when you see implementors throwing or doing nothing.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Worker/Robot example is clean and memorable.
  - Mention Java Collections as a real-world ISP hierarchy.
  - Connect ISP to testing: narrow interface = easier to mock/stub.
  - Default methods in interfaces = ISP-friendly backward compatibility.
  - "Depend on the narrowest sufficient interface" summarizes ISP + DIP.
