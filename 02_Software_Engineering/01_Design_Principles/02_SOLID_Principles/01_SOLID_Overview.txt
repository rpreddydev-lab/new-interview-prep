================================================================
  SOLID PRINCIPLES — OVERVIEW
================================================================

  SOLID is an acronym coined by Robert C. Martin (Uncle Bob).
  Five principles for writing maintainable, extensible OOP code.

  S -- Single Responsibility Principle (SRP)
  O -- Open/Closed Principle (OCP)
  L -- Liskov Substitution Principle (LSP)
  I -- Interface Segregation Principle (ISP)
  D -- Dependency Inversion Principle (DIP)

----------------------------------------------------------------
ONE-LINE DEFINITIONS
----------------------------------------------------------------

  SRP: A class should have ONE reason to change.
  OCP: Open for EXTENSION; closed for MODIFICATION.
  LSP: Subtypes must be SUBSTITUTABLE for their supertypes.
  ISP: Clients should not be forced to depend on interfaces they do NOT use.
  DIP: High-level modules should NOT depend on low-level modules.
       Both should depend on ABSTRACTIONS.

----------------------------------------------------------------
WHY SOLID?
----------------------------------------------------------------

  SOLID addresses the five main symptoms of rotting software:

  Rigidity:    hard to change (SRP, OCP)
  Fragility:   changes break unrelated code (SRP, LSP)
  Immobility:  hard to reuse (DIP)
  Viscosity:   easier to hack than to design correctly (OCP)
  Needless Complexity: over-engineered (ISP — fat interfaces)

----------------------------------------------------------------
QUICK REFERENCE TABLE
----------------------------------------------------------------

  Principle  Problem It Solves             Design Smell Detected By
  ---------  ---------------------------   ---------------------------------
  SRP        God classes; too much logic   Multiple reasons to change a class
  OCP        Modification to add feature   if/switch on type adding new case
  LSP        Subtype breaks callers        Override throws exception parent doesn't
  ISP        Forced empty method impls     "NotSupported" in implemented method
  DIP        Hard-coded concrete deps      new ConcreteClass() in high-level code

----------------------------------------------------------------
SOLID AND PATTERNS CONNECTION
----------------------------------------------------------------

  SRP  → Strategy (separate algorithm), Command (separate action)
  OCP  → Strategy (swap algorithm), Decorator (extend behavior),
          Template Method (override steps), Observer (add handler)
  LSP  → Composite (uniform treatment of leaf/branch)
  ISP  → Facade (give client only what they need),
          Role interfaces
  DIP  → Dependency Injection, Factory, Service Locator,
          Abstract Factory (depend on abstract product)

----------------------------------------------------------------
COMMON INTERVIEW TRAP
----------------------------------------------------------------

  "Isn't SOLID just good OOP?"
  Answer: SOLID makes EXPLICIT what good OOP means. Junior devs use
  inheritance, polymorphism, encapsulation but still write rigid code.
  SOLID gives you specific, actionable checks:
    - "Does this class have more than one reason to change?" (SRP)
    - "Do I need to modify existing code to add this feature?" (OCP)
  Without SOLID vocabulary, "good design" is vague.
