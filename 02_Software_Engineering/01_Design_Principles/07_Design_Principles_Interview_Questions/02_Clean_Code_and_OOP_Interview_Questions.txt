  CLEAN CODE, OOP & ARCHITECTURE PRINCIPLES — INTERVIEW Q&A
================================================================

  Level:    Mid to Senior (5–10+ YOE)
  Frequency: Medium-High — asked especially for senior/lead roles
  Key tip:  Combine principle knowledge with real stories from your projects.

================================================================
SECTION 1: CLEAN CODE PRINCIPLES
================================================================

  Q1: What does "clean code" mean to you?
  ----------------------------------------
  A: Clean code is code that is readable, maintainable, and self-explanatory.
     It should read like well-written prose. Key attributes:
       - Meaningful names: variables, methods, and classes communicate intent.
       - Small, focused methods: each does ONE thing.
       - No duplication (DRY).
       - Minimal comments: code explains itself; comments explain WHY, not WHAT.
       - Consistent formatting and conventions.
       - Graceful error handling (no swallowed exceptions, no checked exceptions
         used as control flow).

     "Any fool can write code that a computer can understand. Good programmers
     write code that humans can understand." — Martin Fowler


  Q2: How do you identify and fix code smells?
  ---------------------------------------------
  A: Common code smells and fixes:

     Long Method → extract into smaller private methods; each named for intent.
     God Class   → split into focused classes by responsibility (SRP).
     Feature Envy → a method uses another class's data excessively;
                    move the method to that class.
     Data Clumps  → group of fields always used together; extract into a class
                    (e.g., Street, City, Zip → Address value object).
     Primitive Obsession → replace primitives with meaningful types
                    (e.g., String email → Email value object with validation).
     Switch Statements → replace with polymorphism (Strategy/State pattern).
     Dead Code → remove; use version control for history.
     Magic Numbers → replace with named constants or enums.

     In Java/Spring: SonarQube flags many code smells automatically.
     In code reviews: ask "if I came back to this in 6 months, would I
     understand it immediately?"


  Q3: When should you write comments?
  -------------------------------------
  A: Write comments to explain WHY, not WHAT. The code shows what happens;
     comments explain intent, business rules, or trade-offs.

     Good comment situations:
       // Using double-checked locking for performance — see Java Memory Model
       // Business rule: orders < $5 are exempt from processing fee (per billing contract v3.2)
       // Workaround for JIRA-4521: library bug with null locale — remove after upgrade to lib v2.1

     Bad comments:
       // increment i by 1
       i++;  // This is self-evident — comment adds noise, not value.

     For public APIs: Javadoc is essential. For internal implementation:
     prefer self-documenting code over comments.


  Q4: What is refactoring, and how do you do it safely?
  -------------------------------------------------------
  A: Refactoring is restructuring existing code WITHOUT changing its external
     behavior. Key safety net: tests.

     Safe refactoring process:
       1. Ensure test coverage exists (add tests if missing).
       2. Make one small change at a time.
       3. Run tests after each change.
       4. Commit frequently.

     Common refactoring techniques:
       Extract Method: pull a block into a named method.
       Rename: improve readability.
       Move Method/Class: put code where it logically belongs.
       Introduce Parameter Object: replace parameter list with a class.
       Replace Conditional with Polymorphism.
       Replace Magic Number with Constant.

     In Java: IntelliJ IDEA's built-in refactoring tools (Shift+F6, Ctrl+Alt+M)
     make these safe and automated.

SECTION 2: DRY, KISS, YAGNI
================================================================

  Q5: What is DRY and how do you apply it without over-engineering?
  -----------------------------------------------------------------
  A: DRY (Don't Repeat Yourself) says every piece of knowledge should have
     a single, authoritative representation. It's about KNOWLEDGE duplication,
     not just code duplication.

     Examples:
       - Validation logic in controller AND service AND repository → extract to
         a shared Validator component.
       - SQL column names duplicated across multiple DTO mappers → use MapStruct
         or a shared mapping layer.
       - Configuration constants duplicated across classes → centralize in a
         @ConfigurationProperties class.

     Over-engineering trap: DRY does NOT mean "never write similar code."
     Two code blocks that look alike but serve different concerns should NOT be
     merged — they'll diverge independently. Ask: "Are they duplicating the same
     DECISION or just coincidentally similar syntax?"


  Q6: KISS — what does it mean in practice for a Java developer?
  ---------------------------------------------------------------
  A: Keep It Simple, Stupid — prefer the simplest solution that works.

     In practice:
       - Use a List.of() when you don't need mutability, not a new ArrayList<>()
         wrapped in Collections.unmodifiableList().
       - Use Optional only to express "may be absent," not as a general wrapper.
       - Avoid premature generics, decorators, or abstractions for a single use case.
       - A plain for-loop is often clearer than a complex stream pipeline.
       - Don't use reactive programming (WebFlux) if your team is unfamiliar and
         a blocking servlet model works fine for your throughput.

     Complexity always has a cost: onboarding, debugging, maintenance.
     Justify every layer of abstraction.


  Q7: YAGNI — how does it conflict with good design, and how do you balance it?
  ------------------------------------------------------------------------------
  A: YAGNI (You Aren't Gonna Need It) says don't add functionality until it's needed.
     Conflict with OCP/extensibility: OCP encourages designing extension points.

     Balance:
       - If there is ONE known implementation, don't create an interface yet.
       - When a SECOND implementation appears or is confirmed on the roadmap,
         introduce the abstraction.
       - Apply extension points at system boundaries (public APIs, integrations)
         where change is likely, not inside isolated business logic.

     Consequence of ignoring YAGNI: "dead abstractions" — interfaces with one
     implementation, factory classes that create one type, abstract base classes
     never extended. These add noise without value.

SECTION 3: SOFTWARE ARCHITECTURE PRINCIPLES
================================================================

  Q8: What is Separation of Concerns and how does Spring Boot enforce it?
  -----------------------------------------------------------------------
  A: SoC means different concerns (responsibilities) of a system should be
     separated into distinct modules or layers, so each addresses a separate concern.

     Spring Boot enforces SoC through:
       - Layered architecture: Controller → Service → Repository.
       - Each layer has a distinct role and communicates through defined contracts.
       - Cross-cutting concerns (logging, security, transactions) handled by AOP
         (@Aspect, @Transactional, @PreAuthorize) — separated from business code.
       - Spring Security separates authentication/authorization from business logic.

     Without SoC: HTTP parsing logic mixed with SQL queries mixed with business
     rules — changing one risks breaking others; impossible to test in isolation.


  Q9: What is High Cohesion and Low Coupling?
  ---------------------------------------------
  A:
     Cohesion: how closely related the elements within a module are.
       HIGH cohesion = all elements of a class serve ONE purpose.
       LOW cohesion = class does many unrelated things (God class).

     Coupling: how strongly modules depend on each other.
       LOW coupling = modules interact through well-defined abstractions; changing
       one module doesn't cascade changes to others.
       HIGH coupling = modules directly depend on internal details of others.

     Goal: HIGH cohesion + LOW coupling = modules that are independently
     testable, deployable, and understandable.

     In Spring: @Service classes are high-cohesion (one domain's business logic).
     Coupling is low because services interact through interfaces injected by Spring,
     not through direct instantiation.


  Q10: What is the Law of Demeter?
  ---------------------------------
  A: "Don't talk to strangers." A method should only call methods on:
       1. The object itself.
       2. Objects passed as parameters.
       3. Objects it creates internally.
       4. Direct component/field objects.

     Violation (train wreck / chaining through unrelated objects):
       customer.getOrder().getAddress().getCity().getZipCode()

     This creates tight coupling: changes to Order, Address, or City break
     the calling code. Fix: encapsulate traversal:
       customer.getShippingZipCode()  // hides internal structure

     In Spring REST controllers: use DTOs to prevent returning domain objects
     directly — respects Demeter by not exposing the object graph.


  Q11: What is Convention over Configuration?
  ---------------------------------------------
  A: CoC means frameworks provide sensible defaults so developers only configure
     what differs from the convention, reducing boilerplate.

     Spring Boot examples:
       - Default embedded Tomcat on port 8080 (no web.xml needed).
       - @SpringBootApplication auto-configures DataSource, JPA, Security based
         on what's on the classpath.
       - Spring MVC maps @Controller methods by convention (GET /users → findAll).
       - Spring Data JPA generates queries from method names: findByEmailAndStatus()

     Benefit: dramatically reduced configuration code. Teams follow one consistent
     way, reducing cognitive overhead and bikeshedding.

SECTION 4: JAVA-SPECIFIC PRINCIPLES
================================================================

  Q12: Why should you "Program to an Interface, not an Implementation" in Java?
  -----------------------------------------------------------------------------
  A: Declaring variables, parameters, and return types as interfaces instead of
     concrete classes provides flexibility to swap implementations without changing
     client code.

     Example:
       // BAD
       ArrayList<String> list = new ArrayList<>();  // locks to ArrayList

       // GOOD
       List<String> list = new ArrayList<>();        // can swap to LinkedList, CopyOnWriteArrayList

     In Spring:
       // BAD
       @Autowired UserServiceImpl userService;  // locks to concrete class

       // GOOD
       @Autowired UserService userService;      // any registered implementation

     This directly enables DIP, OCP, and testability (inject mocks via interface).


  Q13: Why prefer immutability in Java, and how do you achieve it?
  ----------------------------------------------------------------
  A: Immutable objects are inherently thread-safe, easier to reason about, and
     simpler to cache. They eliminate an entire class of bugs (unexpected mutation).

     How to achieve:
       - Declare class final (prevent subclassing that breaks immutability).
       - Make all fields private final.
       - No setters.
       - Return defensive copies of mutable fields (arrays, collections).
       - Use Java 16+ records: public record Point(int x, int y) {} — immutable by design.

     Spring: make @Service and @Component beans stateless (no instance-level mutable
     state). This makes them thread-safe because Spring creates one shared instance.

     Value Objects in DDD (Money, Email, Address) should always be immutable.


  Q14: What is "Fail Fast" and how does it apply in Java?
  --------------------------------------------------------
  A: Fail Fast means detect and report errors as early as possible — at construction
     time or method entry, not deep in business logic.

     In Java:
       - Validate constructor parameters immediately:
           Objects.requireNonNull(email, "email must not be null");
       - Use @NotNull, @Valid (Bean Validation) at controller and service boundaries.
       - Fail at startup (Spring context creation) if required config is missing:
           @ConfigurationProperties with @Validated
       - Throw IllegalArgumentException or IllegalStateException early rather than
         propagating null or corrupted state.

     Benefit: stack traces point to the source of the problem, not a downstream
     symptom. Debugging time drops dramatically.


  Q15: Checked vs Unchecked Exceptions — when do you use each?
  --------------------------------------------------------------
  A:
     Checked exceptions (IOException, SQLException):
       - Use when the CALLER can and should handle the exception.
       - Rare in modern Java — most frameworks (Spring, Hibernate) convert to unchecked.
       - Overuse leads to exception swallowing (catch(Exception e) {}) and
         polluted method signatures.

     Unchecked exceptions (RuntimeException):
       - Use for programming errors, precondition violations, or situations
         the caller cannot reasonably recover from.
       - IllegalArgumentException, IllegalStateException, NullPointerException.
       - Custom unchecked: OrderNotFoundException extends RuntimeException.

     Modern Java best practice (Effective Java, Item 70–72):
       - Prefer unchecked for most domain/application exceptions.
       - Use checked ONLY when the caller genuinely has a recovery path.
       - Never use exceptions for flow control (don't throw inside loops for
         normal code paths).

     Spring: all Spring exceptions (DataAccessException, etc.) are unchecked,
     allowing clean code without forced try-catch blocks.

INTERVIEW TIPS
================================================================

  - For clean code questions: have 2–3 personal stories ready ("in my last
    project, we had a method that was 300 lines long...").
  - For YAGNI vs. OCP questions: acknowledge the tension and explain how
    you decide (second variant = introduce abstraction).
  - For Java-specific questions: always connect to Java features (records,
    Optional, var, lambdas) to show modern Java knowledge.
  - Interviewers at senior level care about your REASONING, not just the
    answer. Say "I prefer X because..." and explain trade-offs.
