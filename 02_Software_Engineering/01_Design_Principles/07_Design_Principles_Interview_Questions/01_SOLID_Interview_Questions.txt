================================================================
  SOLID PRINCIPLES — INTERVIEW QUESTIONS & ANSWERS
================================================================

  Level:    Mid to Senior (5–10+ YOE)
  Frequency: Very High — asked in almost every Java interview
  Key tip:  Always answer with concrete Java/Spring examples, not theory.

================================================================
SECTION 1: SINGLE RESPONSIBILITY PRINCIPLE (SRP)
================================================================

  Q1: What is the Single Responsibility Principle?
  -------------------------------------------------
  A: SRP states that a class should have ONE reason to change — meaning it
     should be responsible to ONE actor (group of people/system that drives
     change). It is NOT simply "a class should do one thing."

     Example violation: A UserService that creates users, sends welcome emails,
     AND writes audit logs. Three different actors (dev team, marketing, compliance)
     all cause changes to the same class.

     Fix: separate into UserService (business logic), UserWelcomeEmailListener
     (email — reacts to UserCreatedEvent), UserAuditListener (audit).


  Q2: How does SRP apply in a Spring Boot project?
  -------------------------------------------------
  A: Spring naturally enforces SRP through its layered architecture:
     @Controller → handles only HTTP mapping and request/response
     @Service    → holds only business logic
     @Repository → handles only data access and exception translation
     @Component  → utility / infrastructure

     Using ApplicationEventPublisher further helps: the service publishes an
     event, and separate listeners (@EventListener) handle email, audit, etc.
     This ensures the service has exactly one reason to change.


  Q3: Can SRP lead to too many classes?
  --------------------------------------
  A: Yes, over-applying SRP creates "abstraction bloat." The test is:
     do DIFFERENT stakeholders (actors) require different changes to the
     same class? If yes, split it. If a class has multiple methods but they
     all change for the same reason, SRP is not violated.

SECTION 2: OPEN/CLOSED PRINCIPLE (OCP)
================================================================

  Q4: What is the Open/Closed Principle?
  ----------------------------------------
  A: A class should be OPEN for extension but CLOSED for modification.
     New behavior should be added by extending/implementing, not by editing
     existing tested code.

     Classic violation: a method with cascading if/else or switch-case on
     a type enum — adding a new type requires modifying the method.

     Fix: define a Strategy interface (e.g., PaymentProcessor), create one
     implementation per type. Adding a new payment type = new class only,
     no existing code touched.


  Q5: How does Spring enable OCP?
  ---------------------------------
  A: Spring's dependency injection naturally supports OCP:
     - Define an interface: PaymentProcessor
     - Register multiple implementations: CreditCardProcessor, PayPalProcessor
     - Inject List<PaymentProcessor> to get all implementations, or use
       @Qualifier / @Primary to select one
     - Adding a new payment type = new @Component class only; the calling
       service never changes

     Spring Data repositories also demonstrate OCP: JpaRepository provides
     base behavior, custom queries extend it without modifying core.


  Q6: OCP vs YAGNI — is there a tension?
  ----------------------------------------
  A: Yes. OCP encourages designing for extension points; YAGNI says don't
     add abstraction until needed. The balance: introduce OCP-based design
     when you have 2+ existing variants OR when the business domain clearly
     indicates multiple future variants. Don't prematurely abstract for a
     single implementation.

SECTION 3: LISKOV SUBSTITUTION PRINCIPLE (LSP)
================================================================

  Q7: What is LSP and when is it violated?
  ------------------------------------------
  A: Subtypes must be substitutable for their base types without altering
     correctness. If code uses a base type reference and a subtype breaks
     behavior, LSP is violated.

     Classic violations:
       - Square extends Rectangle: setting width on a Square also changes
         height, breaking the rectangle's behavior contract.
       - ReadOnlyList extends ArrayList: overrides add() to throw
         UnsupportedOperationException — clients expecting a writable list break.

     Fix for Square/Rectangle: don't use inheritance. Use a shared Shape
     interface with area() — both implement independently.


  Q8: How does LSP relate to Java interfaces and generics?
  ---------------------------------------------------------
  A: Java's type system enforces some of LSP via interfaces, but not all.
     A class CAN implement an interface and violate LSP if it weakens
     postconditions (throws unexpected exceptions) or strengthens preconditions
     (rejects inputs the interface allows).

     In generics, LSP connects to variance: List<Dog> is NOT a subtype of
     List<Animal> because you could add a Cat through the List<Animal>
     reference, breaking the Dog list's contract. This is why Java uses
     wildcards (List<? extends Animal>) for read-only usage.


  Q9: What is the "tell-tale sign" of an LSP violation?
  -------------------------------------------------------
  A: instanceof checks in client code. If you write:
       if (shape instanceof Square) { ... } else { ... }
     the client KNOWS about the subtype — the substitution broke down.
     Proper LSP: polymorphism handles behavior differences transparently.

SECTION 4: INTERFACE SEGREGATION PRINCIPLE (ISP)
================================================================

  Q10: What is ISP?
  ------------------
  A: Clients should not be forced to depend on interfaces they do not use.
     Large "fat" interfaces force implementors to provide stub/empty
     implementations for methods they don't need, creating coupling.

     Example: a Worker interface with work(), eat(), sleep(). A Robot
     implementation must provide eat() and sleep() even if those are
     meaningless for a robot.

     Fix: split into Workable (work()), Eatable (eat()), Sleepable (sleep()).
     Human implements all three. Robot implements only Workable.


  Q11: How does ISP apply in Spring/Java real-world projects?
  ------------------------------------------------------------
  A: Spring Data repositories are a great example:
     Repository < CrudRepository < PagingAndSortingRepository < JpaRepository

     Each adds more methods. If you only need basic CRUD, extend CrudRepository
     instead of JpaRepository. You don't pull in pagination/flush/native query
     methods you don't need.

     In service design: split IOrderService into IOrderQueryService (read
     operations) and IOrderCommandService (write operations) if consumers
     only need one side (CQRS-style split).

SECTION 5: DEPENDENCY INVERSION PRINCIPLE (DIP)
================================================================

  Q12: What is DIP?
  ------------------
  A: High-level modules should NOT depend on low-level modules.
     Both should depend on abstractions (interfaces/abstract classes).
     Abstractions should NOT depend on details; details depend on abstractions.

     Violation: UserService directly creates a new MySQLUserRepository().
     High-level (UserService) depends on low-level detail (MySQL implementation).

     Fix: UserService depends on UserRepository (interface). Spring injects the
     appropriate implementation. UserService never knows about MySQL, Postgres,
     or MongoDB.


  Q13: What is Dependency Injection and how does it relate to DIP?
  -----------------------------------------------------------------
  A: DIP is the PRINCIPLE; Dependency Injection is a TECHNIQUE to achieve it.
     DI frameworks (Spring) implement DIP by:
       1. High-level classes declare dependencies via interfaces (constructor injection).
       2. The IoC container resolves and injects the correct implementation at runtime.

     This means:
       - UserService is testable with a mock UserRepository (no real DB needed).
       - Switching from MySQL to PostgreSQL: change only the @Repository bean,
         not the service.


  Q14: Constructor injection vs field injection — which follows DIP better?
  --------------------------------------------------------------------------
  A: Constructor injection is preferred because:
     - Dependencies are explicit and visible in the signature.
     - Classes are testable without a Spring context (just pass a mock in the constructor).
     - Enforces immutability (final fields).
     - Fails fast at startup if a dependency is missing.

     Field injection (@Autowired on a field) hides dependencies, makes testing
     harder (requires reflection or Spring context), and allows objects to be
     created in an invalid state. It violates the principle of explicit dependencies.

SECTION 6: CROSS-CUTTING / COMBINATIONS
================================================================

  Q15: How are SOLID principles related to each other?
  -----------------------------------------------------
  A:
     SRP  → defines what a class should be (one responsibility).
     OCP  → defines how to extend behavior (without modifying).
     LSP  → defines how inheritance should work (safely substitutable).
     ISP  → defines how interfaces should be shaped (client-focused).
     DIP  → defines how dependencies should flow (toward abstractions).

     They reinforce each other:
       DIP requires interfaces → ISP says keep them small.
       OCP uses polymorphism → LSP ensures it works correctly.
       SRP creates small focused classes → easier to apply OCP and DIP.


  Q16: Which SOLID principle is most commonly violated in large codebases?
  -------------------------------------------------------------------------
  A: SRP and DIP are the most commonly violated:
     - SRP: "God classes" or "God services" accumulate all business logic.
     - DIP: tightly coupled layers where services directly instantiate repositories
       or external clients, making testing and swapping implementations impossible.

     In legacy code: SRP violations appear as large service classes with hundreds
     of methods. Fix: decompose by domain subdomain, introduce events.


  Q17: How do you apply SOLID in a microservices architecture?
  ------------------------------------------------------------
  A: SOLID applies at both class AND service level:
     SRP  → each microservice owns one bounded context (one reason to change).
     OCP  → services expose stable APIs; behavior extended via events/plugins.
     LSP  → a v2 API endpoint must remain backward-compatible with v1 clients.
     ISP  → publish only the contract (OpenAPI) a consumer needs; don't leak internals.
     DIP  → services communicate via abstractions (interfaces/events/APIs),
            not by directly calling internal DB or implementation details.


================================================================
INTERVIEW TIPS
================================================================

  - When asked about any principle, follow: Definition → Violation Example →
    Fixed Example → Real-world/Spring connection.
  - Show code when asked — even pseudo-code demonstrates understanding.
  - Connect SOLID to testability: "this makes the class unit-testable
    without needing a real database / email server."
  - A great senior answer connects the principle to a production problem
    you've actually seen: "In my previous project, we had a God service
    that violated SRP. When we decomposed it using Spring events, our
    test suite coverage improved from 40% to 85%."
  - Don't memorize acronyms — understand the WHY behind each principle.
