================================================================
  CODE SMELLS — CLEAN CODE
================================================================

  A "code smell" is a surface indication that usually corresponds to
  a deeper problem in the code. Named by Kent Beck, popularized by
  Martin Fowler in "Refactoring."

  Smells don't always mean bugs — they indicate areas where
  the design might be improved.

================================================================
BLOATERS — CODE THAT GREW TOO LARGE
================================================================

  1. LONG METHOD
     Method too long to understand on one screen.
     Symptoms: nested loops, multiple branches, mixed abstraction levels.
     Fix: Extract Method — give sub-behaviors names.
     Rule of thumb: >10-20 lines warrants review; >50 = refactor.

  2. LARGE CLASS (GOD CLASS)
     One class doing everything. Signs: dozens of methods, fields for
     completely unrelated concerns, name has "Manager" or "Processor."
     Fix: Extract Class, Extract Interface.

  3. LONG PARAMETER LIST
     >3-4 parameters. Hard to remember order; easy to pass wrong value.
     Fix: Introduce Parameter Object (group related params into a class/record).
     public OrderResult process(String id, String customerId, List<Item> items,
                                double discount, String promo, boolean rush) {}
     → public OrderResult process(OrderRequest request)

  4. PRIMITIVE OBSESSION
     Using primitives (String, int, double) where a domain object would
     express meaning and add validation.
     String phoneNumber; String email; String ssn; // all just "String"
     Fix: Replace Primitive with Object — PhoneNumber, Email, SSN classes.

  5. DATA CLUMPS
     Same group of fields/parameters appearing together in multiple places:
     double lat, double lon always appear together → extract as Coordinate class.
     Fix: Extract Class / Introduce Parameter Object.

================================================================
OBJECT-ORIENTATION ABUSERS
================================================================

  6. SWITCH STATEMENTS (and if-else instanceof chains)
     switch on type = should be polymorphism.
     if (shape instanceof Circle) ... else if (shape instanceof Rectangle)...
     Fix: Replace Conditional with Polymorphism.

  7. REFUSED BEQUEST
     Subclass inherits methods it doesn't use (override throws UnsupportedOperationException).
     LSP violation.
     Fix: Replace Inheritance with Delegation.

  8. ALTERNATIVE CLASSES WITH DIFFERENT INTERFACES
     Two classes do the same thing with different method names.
     Fix: Rename Methods, then Extract Interface / Extract Superclass.

  9. TEMPORARY FIELD
     Object field only set in certain methods; null the rest of the time.
     Fix: Extract Class (the field and its methods go together).

================================================================
CHANGE PREVENTERS — MAKE CHANGE HARD
================================================================

  10. DIVERGENT CHANGE
      One class changes for many different reasons.
      "I touch User class when user rules change, when email changes, when auth changes."
      Fix: Extract Class per change driver (SRP).

  11. SHOTGUN SURGERY
      One change requires many small changes in many different classes.
      "To add a new payment method, I must edit 7 classes."
      Fix: Move Method / Move Field to consolidate related code.

  12. PARALLEL INHERITANCE HIERARCHIES
      Every time you add a subclass to A, you must add a subclass to B.
      Fix: Merge hierarchies or use Visitor.

================================================================
DISPENSABLES — UNNECESSARY CODE
================================================================

  13. COMMENTS (that explain bad code)
      If you feel the need to write a comment, first try to refactor so
      the comment is unnecessary.

  14. DUPLICATE CODE
      Same or very similar code in multiple places.
      Fix: Extract Method / Pull Up Method / Template Method.

  15. DEAD CODE
      Code that is never executed. Methods never called, branches never taken,
      variables never read.
      Fix: Delete it. Git preserves history.

  16. SPECULATIVE GENERALITY
      Unused classes, methods, parameters added for imagined future use.
      Fix: Delete (YAGNI). If needed later: add it then.

  17. LAZY CLASS
      A class that does so little it doesn't justify existing.
      Fix: Inline Class — merge its logic into its user.

  18. DATA CLASS
      Class with only getters/setters, no behavior.
      Often means behavior that should be here is elsewhere (Tell Don't Ask).
      Fix: Move Method into the class; add behavior.

================================================================
COUPLERS — EXCESSIVE COUPLING
================================================================

  19. FEATURE ENVY
      A method seems more interested in another class's data than its own.
      public double calculateDiscount(Customer customer) {
          return customer.getMembership().getType().getDiscountRate() * getBasePrice();
      }
      This method belongs in Customer (or Membership).
      Fix: Move Method.

  20. INAPPROPRIATE INTIMACY
      One class uses internal fields or methods of another class.
      OrderService directly accessing Order's internal Map.
      Fix: Move Field, Extract Class, or introduce a public method.

  21. MESSAGE CHAINS (TRAIN WRECK)
      a.getB().getC().getD().doThing() — Law of Demeter violation.
      Fix: Hide Delegate — add method to the head of chain.

  22. MIDDLE MAN
      A class that delegates all its methods to another class with no added value.
      Fix: Remove Middle Man — call the delegate directly.

================================================================
JAVA-SPECIFIC SMELLS
================================================================

  23. RAW TYPES
      List list = new ArrayList();   // raw type
      Map map = new HashMap();
      Fix: Use generics: List<String>, Map<String, Integer>

  24. UNCHECKED EXCEPTIONS CAUGHT AND IGNORED
      try { ... } catch (Exception e) {}  // silent swallowing
      Fix: Log + rethrow, or handle properly.

  25. STATIC UTILITY CLASSES ABUSED
      util.Utils.doEverything() — misplaced functionality.
      Fix: Move methods to the class where the data lives.

  26. EXCESSIVE @AUTOWIRED ON FIELDS
      Breaks encapsulation; hinders testing.
      Fix: Constructor injection.

  27. @TRANSACTIONAL ON PRIVATE METHODS
      Has no effect (Spring proxy can't intercept private).
      Fix: Make method public or move to a different service.

  28. MUTABLE STATIC STATE (GLOBAL STATE)
      public static List<String> globalCache = new ArrayList<>();
      Fix: Inject; use Spring singleton bean.

CODE SMELL QUICK REFERENCE
================================================================

  Category            Smell                          Fix
  -----------------   ----------------------------   --------------------------
  Bloaters            Long Method                    Extract Method
  Bloaters            Large Class                    Extract Class
  Bloaters            Long Param List                Parameter Object
  Bloaters            Primitive Obsession            Value Object
  OO Abusers          Switch on Type                 Polymorphism
  OO Abusers          Refused Bequest                Replace Inherit w/ Delegate
  Change Preventers   Divergent Change               Extract Class (SRP)
  Change Preventers   Shotgun Surgery                Move Method/Field
  Dispensables        Duplicate Code                 Extract Method/Template
  Dispensables        Dead Code                      Delete
  Dispensables        Speculative Generality         Delete (YAGNI)
  Couplers            Feature Envy                   Move Method
  Couplers            Train Wreck                    Hide Delegate (LoD fix)
  Couplers            Middle Man                     Remove Middle Man
