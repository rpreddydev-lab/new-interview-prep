================================================================
  FUNCTIONS SHOULD DO ONE THING — CLEAN CODE
================================================================

  "The first rule of functions is that they should be small.
   The second rule of functions is that they should be smaller than that."
   — Robert C. Martin

  "Functions should do one thing. They should do it well.
   They should do it only." — Robert C. Martin

----------------------------------------------------------------
WHAT IS "ONE THING"?
----------------------------------------------------------------

  A function does ONE THING when you cannot meaningfully extract
  another function from it that is not merely a restatement of its implementation.

  Test: "Can I name a sub-function that does something meaningfully different?"
  If YES → current function does more than one thing → extract it.

  A function at ONE LEVEL OF ABSTRACTION does one thing:
    processOrder()                 -- high-level step
        validateOrder()            -- one concern
        calculateTotal()           -- another concern
        chargePayment()            -- another concern
        sendConfirmation()         -- another concern

  processOrder() does one thing: orchestrating the order process.
  Each sub-function does one thing at its own level.

----------------------------------------------------------------
VIOLATION: FUNCTION DOING MANY THINGS
----------------------------------------------------------------

  // BAD: reads order, validates, discounts, charges, emails — 5 things
  public void handleOrder(String orderId) {
      Order order = orderRepository.findById(orderId).orElseThrow();

      // validate
      if (order.getItems().isEmpty()) throw new InvalidOrderException();
      if (order.getCustomer() == null) throw new InvalidOrderException();

      // apply discount
      double total = order.getTotal();
      if (order.getCustomer().isPremium()) {
          total = total * 0.90;
      }

      // charge
      PaymentResult result = paymentGateway.charge(order.getCustomer(), total);
      if (!result.isSuccess()) throw new PaymentException(result.getError());

      // update status
      order.setStatus(OrderStatus.PAID);
      order.setPaidAt(Instant.now());
      orderRepository.save(order);

      // send email
      emailService.sendConfirmation(order.getCustomer().getEmail(), order);
  }

  This is 50+ lines doing 5 distinct things. Problems:
    - Hard to test any one step in isolation
    - If discount logic changes, you must touch this large function
    - If email changes, same large function touched (SRP violation)
    - Cyclomatic complexity too high

----------------------------------------------------------------
FIX: EXTRACT INTO SMALL, FOCUSED FUNCTIONS
----------------------------------------------------------------

  // CLEAN: handleOrder does one thing — orchestrate
  @Transactional
  public void handleOrder(String orderId) {
      Order order = loadOrder(orderId);
      validateOrder(order);
      double discountedTotal = applyDiscount(order);
      chargePayment(order, discountedTotal);
      confirmOrder(order);
      notifyCustomer(order);
  }

  private Order loadOrder(String orderId) {
      return orderRepository.findById(orderId)
          .orElseThrow(() -> new OrderNotFoundException(orderId));
  }

  private void validateOrder(Order order) {
      if (order.getItems().isEmpty()) throw new InvalidOrderException("No items");
      if (order.getCustomer() == null) throw new InvalidOrderException("No customer");
  }

  private double applyDiscount(Order order) {
      double total = order.getTotal();
      return order.getCustomer().isPremium() ? total * 0.90 : total;
  }

  private void chargePayment(Order order, double total) {
      PaymentResult result = paymentGateway.charge(order.getCustomer(), total);
      if (!result.isSuccess()) throw new PaymentException(result.getError());
  }

  private void confirmOrder(Order order) {
      order.setPaid(Instant.now());
      orderRepository.save(order);
  }

  private void notifyCustomer(Order order) {
      emailService.sendConfirmation(order.getCustomer().getEmail(), order);
  }

  Now:
    - Each step testable in isolation
    - Adding new step = add a method call + implement method
    - handleOrder reads like a spec: load, validate, discount, charge, confirm, notify

----------------------------------------------------------------
SINGLE LEVEL OF ABSTRACTION PER FUNCTION
----------------------------------------------------------------

  Every statement in a function should be at the SAME level of abstraction.

  // BAD: mixes high-level (process) with low-level (buffer read)
  public void processFile(Path path) {
      processHeader();    // high-level

      // low-level detail intrudes:
      byte[] buffer = new byte[4096];
      int read;
      while ((read = stream.read(buffer)) != -1) {
          processChunk(buffer, read);
      }

      processFooter();    // high-level
  }

  // GOOD: uniform abstraction level
  public void processFile(Path path) {
      processHeader();
      processBody(path);  // hides the read loop
      processFooter();
  }

  private void processBody(Path path) throws IOException {
      byte[] buffer = new byte[4096];
      int read;
      while ((read = stream.read(buffer)) != -1) {
          processChunk(buffer, read);
      }
  }

  Reading handleOrder() should feel like reading a table of contents.
  Reading processBody() should feel like reading implementation details.

----------------------------------------------------------------
FUNCTION ARGUMENTS
----------------------------------------------------------------

  Ideal: 0 arguments (niladic)
  Good:  1 argument (unary)
  OK:    2 arguments (binary)
  Avoid: 3+ arguments (triadic, polyadic)

  // BAD: 5 parameters — hard to understand in context
  public Report createReport(String title, Date from, Date to,
                             boolean includeCharts, String format)

  // GOOD: extract related params into an object
  public Report createReport(ReportRequest request)

  ReportRequest is a Value Object / Parameter Object — reduces arity.

  Avoid FLAG arguments (boolean parameters):
  // BAD: what does "true" mean?
  render(true);

  // GOOD: two separate, clearly named methods
  renderForSuperUsers();
  renderForNormalUsers();
  // OR: renderWithAdminPermissions() / renderWithUserPermissions()

  Avoid OUTPUT arguments:
  // BAD: function modifies argument — confusing
  appendFooter(report);  // is report input or output?

  // GOOD: return the result
  report = withFooter(report);
  // OR: report.appendFooter() — Tell Don't Ask

----------------------------------------------------------------
NO SIDE EFFECTS
----------------------------------------------------------------

  // BAD: name says "check" but secretly modifies session
  public boolean checkPassword(String username, String password) {
      User user = findByUsername(username);
      if (user.matchPassword(password)) {
          session.initialize();  // SIDE EFFECT — not in the name
          return true;
      }
      return false;
  }

  // GOOD: separate concerns
  public boolean isValidPassword(String username, String password) {
      User user = findByUsername(username);
      return user.matchPassword(password);  // pure: no side effects
  }

  public void startSession(User user) {
      session.initialize(user);  // clear intent, separate method
  }

  Caller decides when to call startSession() after checking the password.

----------------------------------------------------------------
COMMAND QUERY SEPARATION (CQS)
----------------------------------------------------------------

  Related principle: a function should either:
    DO something (command — changes state, returns void)
    ANSWER something (query — returns value, no state change)

  Never both.

  // BAD: name suggests query but actually mutates
  public boolean set(String attribute, String value) { ... }

  // GOOD: separate
  void setAttribute(String attribute, String value) { ... }  // command
  boolean hasAttribute(String attribute) { ... }              // query

  This removes ambiguity: caller knows a get is safe; a set changes state.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What does "function should do one thing" mean in practice?
  A: You can't extract a sub-function that does something meaningfully different.
     All statements are at the same level of abstraction. A 5-line function
     with a clear name that orchestrates is "one thing" even if it calls others.

  Q: How small should functions be?
  A: Uncle Bob says functions should rarely be more than 20 lines; often
     10 or fewer. The goal is: function body visible on screen without scrolling,
     each line at the same abstraction level, and a clear meaningful name.

  Q: What are the problems with boolean flag parameters?
  A: They force the function to do two different things based on the flag.
     Split into two named functions. Boolean parameters also make callsites
     unreadable: render(true) — what does true mean?

  Q: What is Command Query Separation?
  A: Methods should either change state OR return a value, not both.
     Queries are safe (can be called multiple times). Commands are state-changing.
     Mixing them makes code unpredictable: calling a "get" has hidden side effects.
