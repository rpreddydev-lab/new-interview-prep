================================================================
  API DESIGN PRINCIPLES
================================================================

  Scope:     REST API design, versioning, contract-first, best practices.
  Frequency: HIGH for senior Java backend developers.
             "Design a REST API for X" is a common interview task.

================================================================
SECTION 1: REST FUNDAMENTALS
================================================================

  REST = Representational State Transfer.
  Architectural style (not a protocol) defined by Roy Fielding (2000).

  6 REST CONSTRAINTS:
    1. Client-Server:       separation of concerns; client handles UI, server handles data.
    2. Stateless:           each request contains ALL information needed. No server-side
                            session state. State is in the client or the DB.
    3. Cacheable:           responses must be labelled cacheable or non-cacheable.
    4. Uniform Interface:   consistent, predictable API contract (key constraint).
    5. Layered System:      client doesn't know if it's talking to a load balancer,
                            cache, or origin server.
    6. Code on Demand:      optional — server can send executable code to client (JS).

  UNIFORM INTERFACE — 4 principles:
    - Resource identification: resources identified by URIs (/users/123).
    - Resource manipulation through representations: use HTTP verbs (GET, POST, PUT, DELETE).
    - Self-descriptive messages: Content-Type, Accept headers describe the format.
    - HATEOAS: Hypermedia as the Engine of Application State (see below).

================================================================
SECTION 2: REST MATURITY MODEL (RICHARDSON MATURITY MODEL)
================================================================

  Level 0: HTTP as a tunnel
    All requests go to one URI. HTTP is just a transport.
    Example: POST /api with action in body {"action": "getUser", "id": 123}
    This is NOT REST — it's RPC over HTTP (like SOAP).

  Level 1: Resources
    Multiple URIs — one per resource.
    GET /users/123, POST /users, GET /orders/456
    But: all use same HTTP method (usually POST for everything).

  Level 2: HTTP Verbs (most common in practice — "REST")
    Use HTTP verbs correctly:
      GET    → read (safe, idempotent)
      POST   → create (not idempotent)
      PUT    → full update/replace (idempotent)
      PATCH  → partial update (not necessarily idempotent)
      DELETE → delete (idempotent)
    Use HTTP status codes correctly.
    Most production APIs operate at this level.

  Level 3: HATEOAS
    Responses include hyperlinks to related actions.
    Client doesn't need to know URLs — they're discovered from responses.

    Example:
      GET /orders/123
      Response:
      {
        "id": 123,
        "status": "PENDING",
        "_links": {
          "confirm": { "href": "/orders/123/confirm", "method": "POST" },
          "cancel":  { "href": "/orders/123/cancel", "method": "DELETE" },
          "self":    { "href": "/orders/123", "method": "GET" }
        }
      }

    Benefit: API is self-documenting; clients are decoupled from URL structure.
    Reality: HATEOAS is rarely fully implemented in practice — very complex to maintain.
    Mention: Spring HATEOAS library provides support (EntityModel, CollectionModel).

SECTION 3: URI DESIGN BEST PRACTICES
================================================================

  NOUNS, not verbs (the HTTP verb is the action):
    ✅ GET /users            → list users
    ✅ GET /users/123        → get user 123
    ✅ POST /users           → create user
    ✅ PUT /users/123        → replace user 123
    ✅ PATCH /users/123      → update user 123 partially
    ✅ DELETE /users/123     → delete user 123
    ❌ GET /getUser          → verb in URI
    ❌ POST /createOrder     → verb in URI
    ❌ GET /deleteUser/123   → verb in URI with GET (not safe)

  PLURAL NOUNS for collections:
    ✅ /users, /orders, /products
    ❌ /user, /order, /product

  HIERARCHICAL for sub-resources:
    ✅ GET /users/123/orders         → orders of user 123
    ✅ GET /users/123/orders/456     → specific order of user 123
    ❌ /getUserOrders?userId=123     → query param for natural hierarchy

  KEEP IT FLAT (max 2–3 levels deep):
    ✅ /orders/456/items
    ❌ /users/123/addresses/456/history/789  → too deep; use /addresses/456 directly

  LOWERCASE, KEBAB-CASE:
    ✅ /product-categories, /order-items
    ❌ /productCategories, /ProductCategories

  QUERY PARAMS for filtering, sorting, pagination (not sub-resources):
    ✅ GET /orders?status=PENDING&customerId=123&page=0&size=20&sort=createdAt,desc
    ❌ GET /orders/pending/customer/123  → filtering as URI path

  ACTION ENDPOINTS (when verbs are truly needed):
    Some actions don't map cleanly to CRUD. Use sub-resources as actions:
    ✅ POST /orders/123/confirm     → confirm order
    ✅ POST /users/123/deactivate  → deactivate user
    ✅ POST /payments/123/refund   → refund payment

SECTION 4: HTTP STATUS CODES
================================================================

  2xx SUCCESS:
    200 OK          → successful GET, PUT, PATCH, DELETE (with response body).
    201 Created     → successful POST (resource created). Include Location header.
    204 No Content  → successful DELETE or PUT with no response body.

  3xx REDIRECT:
    301 Moved Permanently → resource has a new URI; update bookmarks.
    304 Not Modified      → cache is valid; no body returned (ETag/If-None-Match).

  4xx CLIENT ERRORS:
    400 Bad Request       → malformed request, validation failure.
    401 Unauthorized      → not authenticated (missing/invalid credentials).
    403 Forbidden         → authenticated but not authorized for this resource.
    404 Not Found         → resource doesn't exist.
    405 Method Not Allowed→ HTTP method not supported for this endpoint.
    409 Conflict          → state conflict (e.g., duplicate resource, concurrent update).
    422 Unprocessable Entity → valid syntax but semantic validation failure.
    429 Too Many Requests → rate limit exceeded.

  5xx SERVER ERRORS:
    500 Internal Server Error → generic unexpected server error.
    502 Bad Gateway           → upstream service failure.
    503 Service Unavailable   → server overloaded or down; include Retry-After header.
    504 Gateway Timeout       → upstream timeout.

  Key rules:
    - NEVER return 200 with an error message in the body ("200 OK with error payload").
    - Use 401 for authentication issues, 403 for authorization issues.
    - 404 for missing resources; not 400.
    - 409 for conflicts (concurrent updates, unique constraint violations).

SECTION 5: REQUEST/RESPONSE DESIGN
================================================================

  REQUEST BODY — use DTOs (never expose domain/JPA entities):
    @PostMapping("/users")
    public ResponseEntity<UserResponse> createUser(@Valid @RequestBody CreateUserRequest req) {
        UserResponse user = userService.create(req);
        URI location = URI.create("/users/" + user.getId());
        return ResponseEntity.created(location).body(user);
    }

    @Data
    public class CreateUserRequest {
        @NotBlank @Email
        private String email;

        @NotBlank @Size(min = 2, max = 50)
        private String name;

        @NotNull @Min(18)
        private Integer age;
    }

  RESPONSE STRUCTURE — consistent error format (Problem Details — RFC 7807):
    {
      "type": "https://api.example.com/errors/validation-error",
      "title": "Validation Failed",
      "status": 400,
      "detail": "Email address is invalid",
      "instance": "/users",
      "errors": [
        { "field": "email", "message": "must be a valid email address" },
        { "field": "name",  "message": "must not be blank" }
      ]
    }

  Spring Boot 3.x: ProblemDetail class supports RFC 7807 natively.
    return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Email invalid");

  PAGINATION RESPONSE:
    {
      "content": [...],
      "page": { "number": 0, "size": 20, "totalElements": 1547, "totalPages": 78 }
    }
  Spring Data's Page<T> → PagedModel<T> (with Spring HATEOAS) gives this format.

SECTION 6: API VERSIONING
================================================================

  WHY VERSION?
    APIs evolve. Breaking changes (removing fields, changing types, removing endpoints)
    must not break existing clients. Versioning enables gradual migration.

  STRATEGIES:

  1. URL PATH VERSIONING (most common, most explicit):
    /api/v1/orders, /api/v2/orders
    Pros: visible, cacheable, easy to test in browser.
    Cons: URL is not purely about the resource (version is metadata).

  2. QUERY PARAMETER VERSIONING:
    /api/orders?version=2
    Pros: same URL, optional parameter.
    Cons: query params shouldn't affect resource identity (cacheable?); easy to forget.

  3. HEADER VERSIONING:
    Accept: application/vnd.example.v2+json
    Pros: clean URLs; proper HTTP semantics (Accept header).
    Cons: harder to test (need to set headers); less visible.

  4. CONTENT NEGOTIATION (Accept header):
    Accept: application/vnd.example.orders+json;version=2
    Pros: most RESTful. Cons: complex to implement and document.

  Recommendation:
    For internal APIs: URL versioning (/v1/, /v2/) — simplest, most explicit.
    For public APIs: consider header versioning for cleaner URLs.

  BACKWARD COMPATIBILITY RULES:
    SAFE changes (non-breaking):
      ✅ Add optional new fields to responses.
      ✅ Add new optional request fields (with defaults).
      ✅ Add new endpoints.
      ✅ Add new enum values (clients should handle unknown values gracefully).

    BREAKING changes (require new version):
      ❌ Remove or rename a field.
      ❌ Change the type of a field.
      ❌ Change HTTP method of an endpoint.
      ❌ Remove an endpoint.
      ❌ Change authentication scheme.

  DEPRECATION POLICY:
    - Add Deprecation header: Deprecation: version="v1"
    - Add Sunset header: Sunset: Sat, 01 Jan 2026 00:00:00 GMT
    - Document in OpenAPI/Swagger: mark endpoint as deprecated.
    - Communicate clearly to API consumers.
    - Maintain minimum 6 months deprecation period.

SECTION 7: CONTRACT-FIRST API DESIGN
================================================================

  CONTRACT-FIRST: design the API specification (OpenAPI YAML/JSON) BEFORE
  writing any implementation code.

  Benefits:
    - Frontend and backend teams can work in parallel (frontend mocks from spec).
    - API contract reviewed and agreed before implementation effort starts.
    - Client SDKs can be auto-generated.
    - Server stubs can be auto-generated (OpenAPI Generator).
    - Contract tests validate implementation against spec.

  API-FIRST with OpenAPI (Swagger 3.x):
    openapi: "3.0.3"
    info:
      title: Order Service API
      version: "1.0.0"
    paths:
      /orders:
        post:
          summary: Create a new order
          requestBody:
            required: true
            content:
              application/json:
                schema:
                  $ref: '#/components/schemas/CreateOrderRequest'
          responses:
            '201':
              description: Order created
              headers:
                Location:
                  schema:
                    type: string
            '400':
              $ref: '#/components/responses/BadRequest'

  TOOLS:
    - springdoc-openapi: auto-generates OpenAPI spec from Spring annotations.
    - OpenAPI Generator: generates client SDKs and server stubs from spec.
    - Spring Boot + @Operation, @ApiResponse annotations (Swagger UI).

  CODE-FIRST vs CONTRACT-FIRST:
    Code-First: write code → generate spec from annotations.
      Faster to start. Spec may become inconsistent with multiple endpoints.
    Contract-First: write spec → generate stubs → implement.
      More discipline required. Better for team APIs and microservices.

SECTION 8: API SECURITY BASICS
================================================================

  Authentication (who are you?):
    - API Keys (simple, no expiry management, no user context) — for M2M.
    - JWT (JSON Web Token) — stateless, self-contained, widely used.
    - OAuth 2.0 + OpenID Connect — for user authentication + authorization.

  Authorization (what can you do?):
    - Role-based: @PreAuthorize("hasRole('ADMIN')")
    - Scope-based: JWT scopes (read:orders, write:orders).
    - Resource-level: user can only access their own resources.

  Always use HTTPS (TLS) — no exceptions for production APIs.

  Rate limiting:
    - Prevent abuse. Return 429 Too Many Requests.
    - Include Retry-After header.
    - Spring: Bucket4j library for rate limiting.

  Input validation: validate ALL input at API boundary (@Valid, @Validated).
  Never trust client-supplied data.

SECTION 9: INTERVIEW QUESTIONS
================================================================

  Q: Design a REST API for an e-commerce order system.
  -------------------------------------------------------
  A: (Walk through these points):
     Resources: /orders, /orders/{id}, /orders/{id}/items
     POST /orders              → create order (201 + Location header)
     GET /orders/{id}          → get order by ID
     GET /orders?customerId=X  → list orders for a customer (with pagination)
     POST /orders/{id}/confirm → confirm an order (action endpoint)
     POST /orders/{id}/cancel  → cancel an order
     GET /orders/{id}/items    → list items in an order
     POST /orders/{id}/items   → add item to order

     Status codes:
       201 Created + Location for POST /orders
       409 Conflict if order already confirmed (for re-confirm attempt)
       404 Not Found for non-existent order
       400 Bad Request for validation failures (RFC 7807 Problem Details)

  Q: What is the difference between PUT and PATCH?
  -------------------------------------------------
  A: PUT replaces the ENTIRE resource with the request body.
     Client must send all fields (those not sent are treated as absent/null).
     PATCH partially updates the resource — only the fields in the request body change.
     PUT is idempotent (same request = same result always).
     PATCH is not strictly guaranteed to be idempotent by the spec.
     In practice: PATCH is preferred for partial updates to avoid accidentally
     nullifying fields the client didn't intend to change.

  Q: What is HATEOAS and is it practical?
  ----------------------------------------
  A: Hypermedia As The Engine of Application State — REST Level 3.
     Responses include links to valid next actions, making the API self-discoverable.
     In theory: clients need no hardcoded URLs; they follow links.
     In practice: complex to implement correctly; clients often don't use the links;
     adds payload size. Most production APIs operate at Level 2 (HTTP verbs + status codes).
     Mention Spring HATEOAS if asked about Java support.

  Q: How do you handle API versioning?
  --------------------------------------
  A: I prefer URL path versioning (/api/v1/, /api/v2/) for its simplicity and visibility.
     I follow a backward-compatibility-first policy: never break existing clients.
     Adding fields to responses is always safe. Removing or renaming fields requires
     a new version with a deprecation period for v1.
     I set Deprecation and Sunset headers on deprecated endpoints and communicate
     the timeline to API consumers well in advance.

  Q: What is idempotency and why does it matter?
  ------------------------------------------------
  A: An operation is idempotent if calling it multiple times produces the same result.
     GET, PUT, DELETE are idempotent. POST is not.
     Matters in distributed systems: if a network request fails, can you safely retry?
     For POST (create), make it idempotent using an idempotency key:
     Client sends Idempotency-Key: <UUID> header. Server stores the result
     tied to that key — duplicate requests return the cached first response.
     This prevents double-charges, duplicate orders, etc. from network retries.

================================================================
INTERVIEW TIPS
================================================================

  - When asked to "design an API," start with: resources, URIs, HTTP verbs,
    status codes, request/response schema. Don't skip status codes.
  - Always mention RFC 7807 Problem Details for error responses — shows current
    knowledge (Spring Boot 3.x supports it natively).
  - The idempotency key pattern is a senior-level answer — shows distributed
    systems awareness.
  - Mention OpenAPI / Swagger — expected tool knowledge.
  - Security: always mention authentication (JWT/OAuth2) and HTTPS when
    designing any API.
