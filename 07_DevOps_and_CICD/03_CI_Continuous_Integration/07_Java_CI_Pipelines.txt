1. JAVA CI PIPELINE OVERVIEW
================================================================================

A Java CI pipeline typically has these stages:

  Stage 1 — Code Quality (fast, ~1 min):
    ✓ Checkstyle / SpotBugs / PMD (static analysis)
    ✓ Dependency vulnerability scan (OWASP, Snyk)

  Stage 2 — Build (~2-3 min):
    ✓ mvn compile / gradle compileJava
    ✓ Docker image build (optional at this stage)

  Stage 3 — Test (~5-15 min):
    ✓ Unit tests (JUnit 5, Mockito)
    ✓ Integration tests (with Testcontainers)
    ✓ Code coverage check (JaCoCo, minimum threshold)

  Stage 4 — Analysis (~3-5 min, optional on PR):
    ✓ SonarQube / SonarCloud analysis
    ✓ SAST scan (Semgrep, CodeQL)

  Stage 5 — Package and Publish (main branch only):
    ✓ mvn package / gradle bootJar
    ✓ Docker image build + push
    ✓ Upload to Nexus/Artifactory (JARs, WARs)

Key Java CI Principles:
  BUILD ONCE:    Build the artifact once; promote the SAME binary across envs.
  FAIL FAST:     Cheapest checks run first.
  CACHE DEPS:    Cache .m2 / Gradle cache to avoid re-downloading.
  PARALLELIZE:   Run unit + integration tests in parallel where possible.
  IMMUTABLE:     Docker image tags should include Git SHA, not just "latest".

2. MAVEN MULTI-MODULE BUILDS IN CI
================================================================================

Multi-Module Maven Project Structure:

  my-app/
  ├── pom.xml              (parent/aggregator POM)
  ├── core/
  │   └── pom.xml
  ├── service/
  │   └── pom.xml          (depends on core)
  ├── api/
  │   └── pom.xml          (depends on service)
  └── integration-tests/
      └── pom.xml          (depends on api)

Parent POM (pom.xml):

  <groupId>com.mycompany</groupId>
  <artifactId>my-app-parent</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>pom</packaging>
  
  <modules>
    <module>core</module>
    <module>service</module>
    <module>api</module>
    <module>integration-tests</module>
  </modules>
  
  <properties>
    <java.version>21</java.version>
    <spring-boot.version>3.2.0</spring-boot.version>
    <maven.compiler.source>${java.version}</maven.compiler.source>
    <maven.compiler.target>${java.version}</maven.compiler.target>
  </properties>
  
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>${spring-boot.version}</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

Useful Maven Flags for CI:

  -B                    Batch mode (non-interactive, no progress bars)
  -T 4                  Parallel build with 4 threads
  -T 1C                 1 thread per CPU core
  --no-transfer-progress Suppress download progress output (cleaner logs)
  -DskipTests           Skip test execution (not compilation)
  -Dmaven.test.skip=true Skip test compilation AND execution
  -pl core,service      Build specific modules only
  -am                   Also build modules that the specified ones depend on
  -amd                  Also build modules that depend on the specified ones
  -fae                  Fail at end (collect all failures, not stop at first)
  -U                    Force update snapshots

CI-Optimized Maven Command:

  ./mvnw -B -T 1C \
    --no-transfer-progress \
    clean verify \
    -Dspring.profiles.active=ci \
    -Djacoco.minimum.coverage=0.80

Selective Module Building (Change-Based):

  # Only build modules affected by changes:
  # Use Maven Daemon (mvnd) or Maven Wrapper with incremental build
  
  # Example: if only 'core' changed, don't rebuild 'api' and 'integration-tests'
  # Tools: Maven Incremental Build Plugin, Gradle's built-in incremental
  
  # With Maven:
  ./mvnw -B -pl core -am verify    # Build core + its dependencies

3. GRADLE MULTI-MODULE BUILDS IN CI
================================================================================

Gradle Project Structure:

  my-app/
  ├── settings.gradle.kts
  ├── build.gradle.kts         (root)
  ├── core/
  │   └── build.gradle.kts
  ├── service/
  │   └── build.gradle.kts
  └── api/
      └── build.gradle.kts

settings.gradle.kts:

  rootProject.name = "my-app"
  include("core", "service", "api")

Root build.gradle.kts:

  plugins {
      id("org.springframework.boot") version "3.2.0" apply false
      id("io.spring.dependency-management") version "1.1.4" apply false
      id("jacoco")
  }
  
  allprojects {
      repositories {
          mavenCentral()
      }
  }
  
  subprojects {
      apply(plugin = "java")
      apply(plugin = "jacoco")
      
      java {
          toolchain {
              languageVersion.set(JavaLanguageVersion.of(21))
          }
      }
      
      tasks.test {
          useJUnitPlatform()
          finalizedBy(tasks.jacocoTestReport)
      }
  }

CI-Optimized Gradle Commands:

  ./gradlew build                   # Build all modules
  ./gradlew :api:bootJar            # Build specific module
  ./gradlew test --parallel         # Run tests in parallel
  ./gradlew build --continue        # Don't stop on first failure
  ./gradlew build --build-cache     # Enable build cache
  ./gradlew build --scan            # Generate Gradle build scan
  ./gradlew dependencies            # Show dependency tree

Gradle Build Cache (Critical for CI Speed!):

  # gradle.properties in project root:
  org.gradle.caching=true
  org.gradle.parallel=true
  org.gradle.daemon=false           # Disable daemon in CI
  org.gradle.jvmargs=-Xmx2048m -XX:MaxMetaspaceSize=256m

  # Use remote build cache in CI (Gradle Enterprise or self-hosted):
  # settings.gradle.kts:
  buildCache {
      remote(HttpBuildCache::class) {
          url = uri("https://gradle-cache.company.internal/cache/")
          push = System.getenv("CI") != null    # Only push from CI
      }
  }

Gradle vs Maven for CI:

  ┌─────────────────────┬───────────────────┬───────────────────┐
  │ Feature             │ Maven             │ Gradle            │
  ├─────────────────────┼───────────────────┼───────────────────┤
  │ Build cache         │ Limited (MojoHaus)│ Built-in (strong) │
  │ Incremental build   │ Limited           │ Excellent         │
  │ Parallel build      │ -T flag           │ Built-in, smarter │
  │ Convention          │ Strong            │ Flexible          │
  │ Script language     │ XML (verbose)     │ Groovy/Kotlin     │
  │ Spring Boot support │ Excellent         │ Excellent         │
  │ Enterprise feature  │ Via plugins       │ Gradle Enterprise │
  └─────────────────────┴───────────────────┴───────────────────┘

4. DEPENDENCY CACHING STRATEGIES (.m2, GRADLE CACHE)
================================================================================

Why Caching Matters:

  Without cache: Every CI run downloads ALL Maven dependencies from Maven Central.
  A Spring Boot project: ~200-500 MB of dependencies.
  Per build: 2-5 minutes just downloading.
  With 50 builds/day = 2+ hours of pure download time.

Maven (.m2) Cache in GitHub Actions:

  - name: Cache Maven dependencies
    uses: actions/cache@v4
    with:
      path: ~/.m2/repository
      key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
      restore-keys: |
        ${{ runner.os }}-maven-
  
  # Key strategy:
  # key: OS + "maven" + hash of ALL pom.xml files
  # Cache INVALIDATED when any pom.xml changes (new/updated dep)
  # restore-keys: prefix match → restores partial cache if exact key misses

Maven (.m2) Cache in Jenkins:

  pipeline {
    agent any
    
    environment {
      MAVEN_OPTS = '-Dmaven.repo.local=.m2/repository'
    }
    
    stages {
      stage('Build') {
        steps {
          // Use local .m2 in workspace (persisted between builds on same agent)
          sh './mvnw -B -Dmaven.repo.local=.m2/repository clean verify'
        }
      }
    }
    
    post {
      always {
        // Archive test results
        junit '**/target/surefire-reports/*.xml'
      }
    }
  }
  
  // Better: use Jenkins agent with persistent volume for .m2

Gradle Cache in GitHub Actions:

  - name: Setup Gradle
    uses: gradle/actions/setup-gradle@v3
    with:
      gradle-version: wrapper    # Use gradle wrapper version
      cache-read-only: false     # Allow writing to cache
      # This action handles all Gradle caching automatically!

  # Manual approach:
  - name: Cache Gradle packages
    uses: actions/cache@v4
    with:
      path: |
        ~/.gradle/caches
        ~/.gradle/wrapper
      key: ${{ runner.os }}-gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}
      restore-keys: |
        ${{ runner.os }}-gradle-

JDK Caching in GitHub Actions:

  - name: Set up JDK 21
    uses: actions/setup-java@v4
    with:
      java-version: '21'
      distribution: 'temurin'
      cache: maven     # or 'gradle' — built-in caching!
  # actions/setup-java now has built-in Maven/Gradle cache support!

Cache Best Practices:

  1. Cache key includes dependency file hash:
     Maven: hash of pom.xml files
     Gradle: hash of *.gradle, gradle-wrapper.properties
  
  2. Use restore-keys as fallback:
     Partial cache > no cache (many deps still hit)
  
  3. Scope cache to branch/OS:
     key: ${{ runner.os }}-${{ github.ref_name }}-maven-${{ hashFiles(...)}}
  
  4. Don't cache: build output (target/, build/)
     DO cache: dependencies only (.m2/, ~/.gradle/caches/)
  
  5. Dependency proxy/mirror (enterprise):
     Run Nexus/Artifactory as Maven proxy.
     Deps cached on internal server → 100x faster than Maven Central.
     No external internet needed for builds.

5. TEST STRATEGIES IN JAVA CI
================================================================================

Test Separation (Critical for Fast CI):

  Separate tests by type using Maven/Gradle conventions:
  
  src/test/java/                Unit tests (JUnit, fast, no I/O)
  src/integration-test/java/   Integration tests (Testcontainers, Spring context)
  
  Or use naming conventions:
    *Test.java       → unit tests (Surefire)
    *IT.java         → integration tests (Failsafe)

Maven Surefire (Unit Tests):

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>3.2.5</version>
    <configuration>
      <parallel>classes</parallel>    <!-- Run test classes in parallel -->
      <threadCount>4</threadCount>
      <includes>
        <include>**/*Test.java</include>
        <include>**/*Tests.java</include>
        <include>**/*Spec.java</include>
      </includes>
      <excludes>
        <exclude>**/*IT.java</exclude>  <!-- Exclude integration tests -->
      </excludes>
      <!-- JVM args for test JVM: -->
      <argLine>
        -XX:+UseContainerSupport
        -Xmx512m
        ${argLine}  <!-- Required for JaCoCo agent injection -->
      </argLine>
    </configuration>
  </plugin>

Maven Failsafe (Integration Tests):

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <version>3.2.5</version>
    <configuration>
      <includes>
        <include>**/*IT.java</include>
        <include>**/*IntegrationTest.java</include>
      </includes>
    </configuration>
    <executions>
      <execution>
        <goals>
          <goal>integration-test</goal>
          <goal>verify</goal>
        </goals>
      </execution>
    </executions>
  </plugin>

JaCoCo Code Coverage:

  <plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>
    <executions>
      <!-- Prepare JaCoCo agent for Surefire: -->
      <execution>
        <id>prepare-agent</id>
        <goals><goal>prepare-agent</goal></goals>
      </execution>
      <!-- Generate report after tests: -->
      <execution>
        <id>report</id>
        <phase>verify</phase>
        <goals><goal>report</goal></goals>
      </execution>
      <!-- Enforce minimum coverage (FAILS BUILD if below threshold): -->
      <execution>
        <id>check</id>
        <goals><goal>check</goal></goals>
        <configuration>
          <rules>
            <rule>
              <element>BUNDLE</element>
              <limits>
                <limit>
                  <counter>LINE</counter>
                  <value>COVEREDRATIO</value>
                  <minimum>0.80</minimum>   <!-- 80% line coverage -->
                </limit>
                <limit>
                  <counter>BRANCH</counter>
                  <value>COVEREDRATIO</value>
                  <minimum>0.70</minimum>   <!-- 70% branch coverage -->
                </limit>
              </limits>
            </rule>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

Testcontainers in CI:

  Testcontainers requires Docker.
  In GitHub Actions: Docker is available by default.
  In Jenkins: Needs docker socket or DinD setup.
  
  # GitHub Actions — Testcontainers works out of the box.
  # No special config needed:
  
  @SpringBootTest
  @Testcontainers
  class OrderRepositoryIT {
    
    @Container
    static PostgreSQLContainer<?> postgres = 
        new PostgreSQLContainer<>("postgres:16-alpine");
    
    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
    
    @Autowired
    private OrderRepository orderRepository;
    
    @Test
    void shouldSaveAndRetrieveOrder() {
        Order saved = orderRepository.save(new Order("TEST-001"));
        assertThat(orderRepository.findById(saved.getId())).isPresent();
    }
  }

Test Splitting for Parallel CI:

  Run different test groups on parallel CI runners to reduce total time:
  
  # GitHub Actions matrix strategy:
  jobs:
    test:
      strategy:
        matrix:
          test-group: [unit, integration, e2e]
      steps:
        - name: Run ${{ matrix.test-group }} tests
          run: |
            case "${{ matrix.test-group }}" in
              unit) ./mvnw test -DexcludedGroups=integration ;;
              integration) ./mvnw failsafe:integration-test failsafe:verify ;;
              e2e) ./mvnw verify -Dgroups=e2e ;;
            esac

JUnit 5 Test Tagging:

  @Tag("unit")
  @Tag("integration")
  @Tag("slow")
  
  # Run only tagged tests:
  ./mvnw test -Dgroups="unit"              # Maven Surefire
  ./gradlew test --tests "*" -Pinclude-tags="unit"  # Gradle

6. CODE QUALITY IN JAVA CI
================================================================================

SpotBugs (static analysis, replaces FindBugs):

  <plugin>
    <groupId>com.github.spotbugs</groupId>
    <artifactId>spotbugs-maven-plugin</artifactId>
    <version>4.8.3.1</version>
    <configuration>
      <effort>Max</effort>
      <threshold>Medium</threshold>       <!-- Low, Medium, High -->
      <failOnError>true</failOnError>     <!-- Fail build on issues -->
      <excludeFilterFile>spotbugs-exclude.xml</excludeFilterFile>
    </configuration>
    <executions>
      <execution>
        <phase>verify</phase>
        <goals><goal>check</goal></goals>
      </execution>
    </executions>
  </plugin>

Checkstyle (coding style enforcement):

  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-checkstyle-plugin</artifactId>
    <version>3.3.1</version>
    <configuration>
      <configLocation>google_checks.xml</configLocation>  <!-- or sun_checks.xml -->
      <failOnViolation>true</failOnViolation>
      <consoleOutput>true</consoleOutput>
    </configuration>
    <executions>
      <execution>
        <phase>validate</phase>
        <goals><goal>check</goal></goals>
      </execution>
    </executions>
  </plugin>

OWASP Dependency Check (CVE scanning):

  <plugin>
    <groupId>org.owasp</groupId>
    <artifactId>dependency-check-maven</artifactId>
    <version>9.0.9</version>
    <configuration>
      <failBuildOnCVSS>7</failBuildOnCVSS>   <!-- Fail on CVSS >= 7 (HIGH) -->
      <suppressionFiles>
        <suppressionFile>owasp-suppressions.xml</suppressionFile>
      </suppressionFiles>
    </configuration>
    <executions>
      <execution>
        <goals><goal>check</goal></goals>
      </execution>
    </executions>
  </plugin>
  
  # Note: OWASP dependency check is slow (downloads NVD database).
  # Run in a separate CI stage or on schedule, not on every PR.

SonarQube/SonarCloud Analysis:

  # In pom.xml:
  <properties>
    <sonar.organization>my-org</sonar.organization>
    <sonar.host.url>https://sonarcloud.io</sonar.host.url>
    <sonar.java.coveragePlugin>jacoco</sonar.java.coveragePlugin>
    <sonar.coverage.jacoco.xmlReportPaths>
      target/site/jacoco/jacoco.xml
    </sonar.coverage.jacoco.xmlReportPaths>
    <sonar.exclusions>**/generated/**,**/*Config.java</sonar.exclusions>
  </properties>
  
  # Run:
  ./mvnw sonar:sonar \
    -Dsonar.token=$SONAR_TOKEN \
    -Dsonar.pullrequest.key=$PR_NUMBER \
    -Dsonar.pullrequest.branch=$HEAD_BRANCH \
    -Dsonar.pullrequest.base=main

7. JENKINS PIPELINE FOR JAVA (DECLARATIVE JENKINSFILE)
================================================================================

Complete Jenkinsfile for Spring Boot:

  pipeline {
    agent {
      kubernetes {
        yaml """
          apiVersion: v1
          kind: Pod
          spec:
            containers:
            - name: maven
              image: maven:3.9-eclipse-temurin-21
              command: [cat]
              tty: true
              resources:
                requests:
                  memory: "2Gi"
                  cpu: "1"
                limits:
                  memory: "4Gi"
                  cpu: "2"
              volumeMounts:
              - name: m2-cache
                mountPath: /root/.m2/repository
            - name: docker
              image: docker:24-dind
              privileged: true
              env:
              - name: DOCKER_TLS_CERTDIR
                value: ""
            volumes:
            - name: m2-cache
              persistentVolumeClaim:
                claimName: maven-cache-pvc
        """
      }
    }
    
    environment {
      APP_NAME = 'order-service'
      REGISTRY = 'my-registry.io'
      IMAGE = "${REGISTRY}/${APP_NAME}"
      GIT_SHA = sh(returnStdout: true, script: 'git rev-parse --short HEAD').trim()
      SONAR_TOKEN = credentials('sonar-token')
      REGISTRY_CREDS = credentials('registry-credentials')
    }
    
    options {
      timeout(time: 30, unit: 'MINUTES')
      disableConcurrentBuilds()
      buildDiscarder(logRotator(numToKeepStr: '20'))
    }
    
    stages {
      stage('Code Quality') {
        steps {
          container('maven') {
            sh './mvnw -B --no-transfer-progress validate checkstyle:check'
          }
        }
      }
      
      stage('Build') {
        steps {
          container('maven') {
            sh './mvnw -B -T 2 --no-transfer-progress compile'
          }
        }
      }
      
      stage('Test') {
        parallel {
          stage('Unit Tests') {
            steps {
              container('maven') {
                sh './mvnw -B test -DexcludedGroups=integration'
              }
              post {
                always {
                  junit 'target/surefire-reports/*.xml'
                  jacoco(
                    execPattern: 'target/jacoco.exec',
                    classPattern: 'target/classes',
                    sourcePattern: 'src/main/java',
                    minimumLineCoverage: '80'
                  )
                }
              }
            }
          }
          
          stage('Integration Tests') {
            steps {
              container('maven') {
                sh './mvnw -B failsafe:integration-test failsafe:verify -Dgroups=integration'
              }
              post {
                always {
                  junit 'target/failsafe-reports/*.xml'
                }
              }
            }
          }
        }
      }
      
      stage('SonarQube') {
        when { branch 'main' }
        steps {
          container('maven') {
            sh """
              ./mvnw -B sonar:sonar \
                -Dsonar.token=${SONAR_TOKEN} \
                -Dsonar.branch.name=${BRANCH_NAME}
            """
          }
        }
      }
      
      stage('Build Docker Image') {
        when { anyOf { branch 'main'; branch 'release/*' } }
        steps {
          container('docker') {
            sh """
              docker build \
                -t ${IMAGE}:${GIT_SHA} \
                -t ${IMAGE}:latest \
                --build-arg BUILD_VERSION=${GIT_SHA} \
                .
            """
          }
        }
      }
      
      stage('Push Image') {
        when { branch 'main' }
        steps {
          container('docker') {
            sh """
              echo "${REGISTRY_CREDS_PSW}" | docker login ${REGISTRY} \
                -u "${REGISTRY_CREDS_USR}" --password-stdin
              docker push ${IMAGE}:${GIT_SHA}
              docker push ${IMAGE}:latest
            """
          }
        }
      }
    }
    
    post {
      failure {
        slackSend(
          channel: '#ci-alerts',
          color: 'danger',
          message: "Build FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER} (${GIT_SHA})"
        )
      }
      success {
        slackSend(
          channel: '#ci-alerts',
          color: 'good',
          message: "Build PASSED: ${env.JOB_NAME} #${env.BUILD_NUMBER} → ${IMAGE}:${GIT_SHA}"
        )
      }
      always {
        cleanWs()
      }
    }
  }

8. GITHUB ACTIONS FOR JAVA (COMPLETE WORKFLOWS)
================================================================================

PR Validation Workflow (.github/workflows/pr-check.yml):

  name: PR Check
  
  on:
    pull_request:
      branches: [main, develop]
  
  jobs:
    quality:
      name: Code Quality
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        
        - name: Set up JDK 21
          uses: actions/setup-java@v4
          with:
            java-version: '21'
            distribution: 'temurin'
            cache: 'maven'                   # Built-in Maven cache!
        
        - name: Checkstyle
          run: ./mvnw -B --no-transfer-progress checkstyle:check
        
        - name: SpotBugs
          run: ./mvnw -B --no-transfer-progress spotbugs:check
    
    test:
      name: Tests
      runs-on: ubuntu-latest
      needs: quality           # Only run if quality passes
      strategy:
        matrix:
          test-type: [unit, integration]
      
      steps:
        - uses: actions/checkout@v4
        
        - name: Set up JDK 21
          uses: actions/setup-java@v4
          with:
            java-version: '21'
            distribution: 'temurin'
            cache: 'maven'
        
        - name: Run Unit Tests
          if: matrix.test-type == 'unit'
          run: |
            ./mvnw -B --no-transfer-progress test \
              -DexcludedGroups=integration \
              -Djacoco.minimum.coverage=0.80
        
        - name: Run Integration Tests
          if: matrix.test-type == 'integration'
          run: |
            ./mvnw -B --no-transfer-progress \
              failsafe:integration-test failsafe:verify \
              -Dgroups=integration
        
        - name: Publish Test Results
          uses: EnricoMi/publish-unit-test-result-action@v2
          if: always()
          with:
            files: '**/target/surefire-reports/*.xml'
        
        - name: Upload Coverage to Codecov
          if: matrix.test-type == 'unit'
          uses: codecov/codecov-action@v4
          with:
            files: target/site/jacoco/jacoco.xml
            flags: unittests

Main Branch CI/CD Workflow (.github/workflows/ci-cd.yml):

  name: CI/CD Pipeline
  
  on:
    push:
      branches: [main]
    release:
      types: [published]
  
  env:
    REGISTRY: ghcr.io
    IMAGE_NAME: ${{ github.repository }}
  
  jobs:
    build-and-test:
      name: Build and Test
      runs-on: ubuntu-latest
      outputs:
        image-tag: ${{ steps.meta.outputs.tags }}
        version: ${{ steps.version.outputs.version }}
      
      steps:
        - uses: actions/checkout@v4
          with:
            fetch-depth: 0         # Full history for SonarQube
        
        - name: Set up JDK 21
          uses: actions/setup-java@v4
          with:
            java-version: '21'

              clean verify \

            registry: ${{ env.REGISTRY }}

          id: meta
          uses: docker/metadata-action@v5
          with:
            images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}

              type=sha,prefix=sha-,format=short
              type=ref,event=branch
              type=semver,pattern={{version}}

            kubectl set image deployment/order-service \

10. DOCKER BUILD IN JAVA CI PIPELINE
================================================================================

Build Once, Promote Pattern:

  CI builds ONE Docker image with Git SHA tag.
  CD promotes the same image across environments by:
    1. Adding new tags (staging, prod) to existing image
    2. Updating Helm values.yaml with new image tag
    3. ArgoCD detects change and syncs

Efficient Docker Build in CI:

  # Dockerfile optimized for CI caching:
  # Mount Maven cache as BuildKit cache:
  
  # syntax=docker/dockerfile:1
  FROM eclipse-temurin:21-jdk-alpine AS builder
  WORKDIR /build
  
  # Copy POM files first (layer for dependency download)
  COPY pom.xml .
  COPY */pom.xml ./
  
  # Download dependencies (cached if pom.xml unchanged):
  RUN --mount=type=cache,target=/root/.m2 \
      ./mvnw -B dependency:go-offline
  
  # Copy source code (invalidates cache if code changes):
  COPY . .
  
  # Build (uses cached dependencies):
  RUN --mount=type=cache,target=/root/.m2 \
      ./mvnw -B --no-transfer-progress package -DskipTests
  
  # Extract layers:
  RUN java -Djarmode=layertools -jar target/*.jar extract
  
  # ─── Runtime stage ─────────────────────────────────────────
  FROM eclipse-temurin:21-jre-alpine
  RUN addgroup -S app && adduser -S app -G app
  COPY --from=builder /build/dependencies/ ./
  COPY --from=builder /build/spring-boot-loader/ ./
  COPY --from=builder /build/snapshot-dependencies/ ./
  COPY --from=builder /build/application/ ./
  USER app
  EXPOSE 8080
  ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

12. JAVA CI PERFORMANCE OPTIMIZATION
================================================================================

Build Time Reduction Checklist:

  1. Cache .m2 / Gradle cache (reduces download time dramatically)
  2. Use Maven Daemon (mvnd) — 30-50% faster startup
  3. Parallel module build: -T 1C
  4. Skip redundant lifecycle phases:
     mvn verify (not mvn package + separately run tests)
  5. Use Spring Boot thin launcher for faster test context startup
  6. Split unit and integration tests → run in parallel
  7. Use Docker layer caching with BuildKit --mount=type=cache
  8. Run Docker builds on dedicated build machines with warm caches
  9. Use Jib instead of Docker for image builds (no Docker daemon needed)
  10. Use Nexus/Artifactory as Maven proxy (internal mirror)

Maven Daemon (mvnd):

  # Install:
  brew install mvnd                        # macOS
  
  # Use (drop-in replacement for mvn/mvnw):
  mvnd clean verify                        # 30-50% faster than mvn
  
  # In CI: Less beneficial (daemon reuse limited)
  # Best for: local development

Common CI Bottlenecks for Java:

  ┌──────────────────────────────┬───────────────────────────────────────┐
  │ Bottleneck                   │ Fix                                   │
  ├──────────────────────────────┼───────────────────────────────────────┤
  │ Dependency download (2-5min) │ Cache .m2, use internal Nexus         │
  │ Test execution (10-30min)    │ Parallelize, split unit/integration   │

  └──────────────────────────────┴───────────────────────────────────────┘

13. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: How do you structure a CI pipeline for a Java multi-module Maven project?
    How do you ensure only affected modules are rebuilt?

A: Structure for multi-module CI:
   
   1. Cache layer: Download all deps once, cache .m2 with pom.xml hash as key.
   
   2. Build all: ./mvnw -B -T 1C compile (parallel, all modules)
   
   3. Test all (parallel jobs):
      Job A: unit tests (-DexcludedGroups=integration)
      Job B: integration tests (Testcontainers)
   
   4. Coverage enforcement: JaCoCo minimum 80% line coverage.
   
   5. Package (main branch only): mvn package → layered JAR → Docker build
   
   For selective module building:
   - Use -pl module-name -am (with transitive deps)
   - More advanced: tools like Apache Maven Incremental Build or Gradle's
     built-in incremental compilation
   - In large repos: use Gradle which has much better incremental support
   
   In practice at enterprise scale:
   Most teams BUILD ALL MODULES on every push for correctness guarantees.
   Selective builds are used in monorepos with hundreds of modules.
   For 5-20 module projects: build all is simpler and safer.

---

Q2: How do you handle Maven dependency caching in GitHub Actions?
    What happens if the cache is stale?

A: Two approaches:
   
   Approach 1: actions/setup-java built-in cache:
     uses: actions/setup-java@v4
     with:
       java-version: '21'
       distribution: 'temurin'
       cache: 'maven'    # Automatically caches ~/.m2/repository
   
   Approach 2: actions/cache manually:
     uses: actions/cache@v4
     with:
       path: ~/.m2/repository
       key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
       restore-keys: |
         ${{ runner.os }}-maven-
   
   Cache invalidation:
   - Key includes hash of ALL pom.xml files
   - Any pom.xml change → new cache key → cache miss → fresh download
   - restore-keys provides partial cache hit even if key doesn't match exactly
     (downloads only new/changed dependencies, uses cache for rest)
   
   Stale cache handling:
   Cache key changes → full miss → Maven downloads all dependencies fresh.
   This ensures correctness at the cost of one slower build.
   Next build hits the new cache.
   
   Enterprise recommendation:
   Run Nexus/Artifactory as a Maven proxy for your organization.
   All builds download from internal server (LAN speed, not internet).
   GitHub Actions cache becomes a secondary optimization.

---

Q3: What is the "Build Once, Deploy Many" principle and how do you implement
    it in a Java CI/CD pipeline?

A: Build Once: Build the JAR/Docker image ONCE in CI.
   Deploy Many: Promote the SAME artifact across dev → staging → prod.
   
   Why it matters:
   If you rebuild for each environment, you can't guarantee what you tested
   in staging is exactly what runs in production (dependency updates,
   build environment differences).
   
   Implementation:
   
   CI (builds once):
     ./mvnw package → target/app.jar
     docker build → myregistry/order-service:sha-abc123
     docker push
   
   CD (promotes same image):
     Dev:     kubectl set image ... order-service:sha-abc123 --ns dev
     Staging: kubectl set image ... order-service:sha-abc123 --ns staging
     Prod:    kubectl set image ... order-service:sha-abc123 --ns prod
   
   Environment-specific config via Kubernetes:
     ConfigMaps and Secrets per namespace (not baked into image)
     spring.profiles.active=production (set as env var per deployment)
     SPRING_DATASOURCE_URL changes per environment (K8s secret)
   
   Immutable image principle:
     Image tag = Git SHA (never reuse; never use :latest for deployments)
     sha-abc123 is immutable → you always know exactly what's deployed.
