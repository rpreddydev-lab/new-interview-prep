1. DEEP DIVE: GIT FLOW
================================================================================

Created by: Vincent Driessen, blog post "A successful Git branching model" (2010)
Current Status: Vincent Driessen himself added a note in 2020 saying he no longer
                recommends it for software that can be deployed continuously.

Core Structure:

  PERMANENT (Long-lived) Branches:
    main (master): Only production-ready code. Tagged with versions.
    develop: Integration branch. All features merge here first.

  TEMPORARY (Short-lived) Branches:
    feature/*: New features (from develop → back to develop)
    release/*: Release preparation (from develop → to main+develop)
    hotfix/*:  Emergency fixes (from main → to main+develop)

Complete Workflow with Commands:

  --- STARTING A FEATURE ---
  git checkout develop
  git pull origin develop
  git checkout -b feature/JIRA-456-shopping-cart
  
  # Development work...
  git add .
  git commit -m "feat(cart): add item to shopping cart"
  git commit -m "feat(cart): implement cart totals"
  git commit -m "test(cart): add unit tests for cart service"
  
  # Finish feature
  git checkout develop
  git pull origin develop        # Get latest develop
  git merge --no-ff feature/JIRA-456-shopping-cart
  git push origin develop
  git branch -d feature/JIRA-456-shopping-cart

  --- CREATING A RELEASE ---
  git checkout develop
  git checkout -b release/v2.3.0
  
  # Fix only bugs here (no new features!)
  git commit -m "fix: version number to 2.3.0"
  git commit -m "fix(checkout): resolve rounding error"
  
  # Finish release
  git checkout main
  git merge --no-ff release/v2.3.0
  git tag -a v2.3.0 -m "Release v2.3.0"
  git push origin main --tags
  
  git checkout develop
  git merge --no-ff release/v2.3.0
  git push origin develop
  git branch -d release/v2.3.0

  --- HOTFIX ---
  git checkout main
  git checkout -b hotfix/v2.3.1-payment-null-pointer
  
  git commit -m "fix(payment): handle null customer in checkout"
  
  git checkout main
  git merge --no-ff hotfix/v2.3.1-payment-null-pointer
  git tag -a v2.3.1 -m "Hotfix: payment null pointer"
  git push origin main --tags
  
  # CRITICAL: Also merge to develop!
  git checkout develop
  git merge --no-ff hotfix/v2.3.1-payment-null-pointer
  git push origin develop
  
  git branch -d hotfix/v2.3.1-payment-null-pointer

Full Branch Diagram:

  v2.0          v2.1                    v2.2
  |             |                       |
  main:    ─────●───────────────────────●─────────────── ●── (hotfix)
                                                         |
  develop: ─────────●──────────●────────────────────────●────────
                    |          |                         |
  feature-A:        ●──●──●────┘                        |
                             |                           |
  feature-B:                 ●───●───●──────────────────┘
                                      |
  release/v2.2:                        ●──● (only bugfixes)

Tooling: git-flow Extension
  # Install
  brew install git-flow-avh    # macOS
  
  # Initialize
  git flow init
  
  # Feature
  git flow feature start JIRA-456-shopping-cart
  git flow feature finish JIRA-456-shopping-cart
  
  # Release
  git flow release start v2.3.0
  git flow release finish v2.3.0
  
  # Hotfix
  git flow hotfix start v2.3.1-payment-bug
  git flow hotfix finish v2.3.1-payment-bug

When Git Flow Makes Sense:
  ✓ Mobile apps (App Store / Play Store review process = queued releases)
  ✓ On-premise enterprise software (customer deploys at their own schedule)
  ✓ SDK/library with multiple versions in use simultaneously
  ✓ Software with formal QA/sign-off before each release
  ✓ Compliance-heavy environments (banking, healthcare)
  ✓ Teams new to Git who need very explicit, documented process

When Git Flow Is Overkill:
  ✗ Web services with continuous deployment
  ✗ Teams deploying multiple times per day
  ✗ Microservices (too many repos to maintain Git Flow in all of them)
  ✗ Small teams (overhead not worth it)
  ✗ Products with zero customer-installed versions to maintain

Criticisms of Git Flow:
  1. Two long-lived branches (main + develop) add complexity and merge overhead
  2. Release branches often contain the same code as develop + minor fixes
  3. The develop branch is usually in a "deployable but not deployed" limbo
  4. Complex merge-to-both for hotfixes is error-prone
  5. Slows down CI/CD feedback cycles

2. DEEP DIVE: TRUNK-BASED DEVELOPMENT (TBD)
================================================================================

Core Definition:
  All developers commit to a single shared trunk (main/master) at least once per
  day. Feature branches are either:
    a) Non-existent (pure TBD) — commit directly to trunk
    b) Very short-lived (1-2 days max) before merging

Origin:
  Used at Google, Facebook, Twitter, Netflix, and most large tech companies.
  Supported by DORA research as a predictor of high-performing teams.

  "The Continuous Delivery" book by Jez Humble and Dave Farley (2010) strongly
  advocates for trunk-based development as the foundation for CD.

Two Variants:

  VARIANT A — PURE TBD (Google's internal model):
    - Small, frequent commits directly to trunk
    - Feature flags for all incomplete work
    - Requires high test coverage (before committing, tests must pass)
    - Monorepo-friendly
    - Google's Critique (code review) + automated testing makes this safe
  
  VARIANT B — SHORT-LIVED FEATURE BRANCHES (Most common in industry):
    - Feature branches allowed but MUST merge within 1-2 days
    - Branches never diverge significantly from trunk
    - PR process for code review still applies
    - This is what "we do trunk-based development" usually means

Workflow Example (Short-lived TBD):

  DAY 1 MORNING:
    git checkout main && git pull
    git checkout -b feature/add-search-autocomplete
    # Work on feature...
    git commit -m "feat: add search service interface"

  DAY 1 AFTERNOON:
    git fetch origin main
    git rebase origin/main           # Stay up to date with trunk
    git commit -m "feat: implement basic search logic"
    git commit -m "test: add search unit tests"
    git push origin feature/add-search-autocomplete
    # Open PR immediately (don't wait for feature to be "complete")

  DAY 2 MORNING:
    # Feature incomplete? Use feature flag:
    # if (featureFlags.get("search-autocomplete")) { ... }
    # Code review approved
    git merge feature/add-search-autocomplete → main
    # Feature is in main but behind feature flag
    git branch -d feature/add-search-autocomplete

Integration (Commit) Frequency Measurement:
  High performance: Every developer merges to trunk at least once per day
  Elite performance: Multiple times per day
  
  Metrics to track:
  - Average branch age (should be < 1 day for TBD)
  - PR open time (should be < 1 day)
  - Number of active branches per developer (should be 1-2)

Requirements for TBD to Work:
  1. Strong automated test coverage (especially unit + integration tests)
  2. Fast CI pipeline (< 10 minutes to get feedback)
  3. Feature flags infrastructure
  4. Developer discipline (don't break trunk)
  5. Code review culture (small PRs are reviewed faster)
  6. Incremental development mindset

What Happens if You Break Trunk?
  Cultural expectation: Fixing a broken build is HIGHEST PRIORITY.
  Never leave work for the day with trunk broken.
  Policy: Build failures block all merges until fixed.
  
  Prevention:
  - Required passing tests before merge (branch protection)
  - Pre-commit hooks for local validation
  - Fast CI feedback (within 5-10 minutes)

Pair Programming and TBD:
  Pair programming + TBD is powerful:
  - Code is reviewed as it's written (no separate review step)
  - Pairs can commit directly to trunk without additional review
  - Used at extreme programming (XP) shops

3. HEAD-TO-HEAD COMPARISON
================================================================================

DIMENSION              | GIT FLOW                        | TRUNK-BASED DEV
-----------------------|---------------------------------|--------------------------------
Integration frequency  | Weekly (feature branch → dev)  | Daily (to trunk)
Merge complexity       | High (main+develop+feature)     | Low (one trunk)
Long-lived branches    | Yes (main, develop)             | No
Merge conflicts        | Frequent, large                 | Rare, small
Release cadence        | Scheduled (release branches)    | Continuous
Rollback approach      | Revert merge commit             | Revert small commit or flag off
Feature incomplete     | Left on feature branch          | Feature flag on trunk
Test discipline req.   | Moderate                        | High
CI/CD suitability      | Moderate                        | Excellent
Team onboarding        | Complex (5 branch types)        | Simple (one branch)
Audit trail            | Release tags + branch history   | Commit history + feature flags
Multi-version support  | Excellent                       | Complex (needs support branches)
Scale (many engineers) | Difficult (more conflicts)      | Scales well (short branches)

Code Review:
  Git Flow: Large PRs after days/weeks of work. Hard to review thoroughly.
  TBD: Small PRs after hours/1-day of work. Easy to review, fast approval.

Build Speed Impact:
  Git Flow: Features build in isolation until merge. CI runs on feature branch.
  TBD: Everyone's code builds together immediately. Integration issues caught same day.

DORA Metrics Correlation:
  TBD practitioners:
  - Higher deployment frequency
  - Lower change failure rate
  - Lower lead time for changes
  - Lower MTTR

  Why? Because TBD forces small changes. Small changes:
  - Are easier to test
  - Have smaller blast radius when something goes wrong
  - Are easier to roll back
  - Are reviewed more thoroughly

4. FEATURE FLAGS (ENABLING TBD)
================================================================================

What Are Feature Flags?
  Runtime configuration that controls which features are active without deploying
  new code. Also called feature toggles or feature switches.

Feature Flag Types:

  1. RELEASE TOGGLES:
     - Hide incomplete features from users
     - Deployed but not released
     - Short-lived: removed once feature is fully rolled out
     
  2. EXPERIMENT TOGGLES (A/B Testing):
     - Show different experiences to different user segments
     - Used for measuring business impact of features
     - Example: 50% users see new checkout, 50% see old checkout
     
  3. OPS TOGGLES:
     - Control operational behavior (kill switches)
     - Example: Disable a resource-intensive feature during high traffic
     - Can be toggled without deployment
     
  4. PERMISSION TOGGLES:
     - Control access based on user role or plan
     - Example: Premium feature only for paying customers

Code Example:
  // Simple boolean flag
  if (FeatureFlags.isEnabled("new-recommendation-engine")) {
      return newRecommendationService.getRecommendations(userId);
  } else {
      return legacyRecommendationService.getRecommendations(userId);
  }
  
  // User-segment flag (A/B test)
  if (FeatureFlags.isEnabledForUser("new-checkout", userId)) {
      return newCheckoutFlow(cart);
  } else {
      return legacyCheckoutFlow(cart);
  }
  
  # Python example
  if feature_flags.is_enabled("dark_mode", user_id=user.id):
      return render_template("dashboard_dark.html")
  else:
      return render_template("dashboard.html")

Feature Flag Lifecycle:
  1. Create flag (disabled by default)
  2. Deploy code with flag
  3. Enable for internal users (dogfooding)
  4. Enable for beta users
  5. Gradual rollout (10% → 25% → 50% → 100%)
  6. IMPORTANT: Remove the flag and old code after full rollout
     (Feature flag debt is real — don't accumulate dead flags)

Feature Flag Platforms:
  - LaunchDarkly: Leading commercial platform
  - Unleash: Open source self-hosted
  - Flagsmith: Open source
  - AWS AppConfig: AWS managed
  - Firebase Remote Config: Google/Firebase
  - Split.io: Commercial
  
  Or: Simple database/config-based flags for small teams

Feature Flag Anti-patterns:
  - Permanent flags (they accumulate and become technical debt)
  - Too many nested flags (impossible to reason about state)
  - Not removing flags after rollout
  - Coupling business logic to flag structure (hard to refactor)

5. BRANCH BY ABSTRACTION
================================================================================

An alternative to long feature branches for large refactors.

Problem Scenario:
  You need to replace the monolithic PaymentService with a new microservice.
  The change touches 50 files. A long-lived branch would have massive conflicts.
  
  How do you make this change using TBD?

Branch by Abstraction Process:

  STEP 1: Create an abstraction layer
    // Before: Direct use of OldPaymentService
    public class OrderService {
        private OldPaymentService paymentService;  // Direct dependency
    }
    
    // After Step 1: Program to interface
    public interface PaymentService {           // Create abstraction
        PaymentResult processPayment(Order order);
    }
    public class OldPaymentService implements PaymentService { ... }
    public class OrderService {
        private PaymentService paymentService;  // Use abstraction
    }
    // COMMIT TO TRUNK - no behavior change

  STEP 2: Implement new code alongside old
    public class NewPaymentMicroserviceClient implements PaymentService {
        // New implementation...
    }
    // COMMIT TO TRUNK - new class exists but isn't used yet

  STEP 3: Route some traffic to new implementation (feature flag)
    if (featureFlags.isEnabled("new-payment-service")) {
        paymentService = new NewPaymentMicroserviceClient();
    } else {
        paymentService = new OldPaymentService();
    }
    // COMMIT TO TRUNK - gradually enable for users/tests

  STEP 4: Switch fully to new implementation
    // Remove old implementation and the abstraction if no longer needed
    // COMMIT TO TRUNK

Benefits:
  - Large refactors done in many small commits to trunk
  - Each commit is safe (no behavior change until toggle flipped)
  - Easy to revert (just flip the toggle)
  - Continuous integration of changes (no integration hell at the end)

6. REAL-WORLD EXAMPLES
================================================================================

Google (TBD + Monorepo):
  - One giant monorepo: "google3" contains billions of lines of code
  - Thousands of engineers commit to a single trunk daily
  - Automated testing runs on every commit (Presubmit testing)
  - Code review required before merge (Critique review tool)
  - Feature flags everywhere
  - No long-lived branches

Facebook/Meta (Shifted from Git Flow to TBD):
  - Moved to daily/hourly trunk-based deployments
  - "Ship early, ship often" philosophy
  - Gatekeeper system for feature flags
  - Monday-Thursday deployments to canary, Friday production push

Shopify:
  - Fully trunk-based development
  - Any engineer can deploy to production at any time
  - Feature flags control rollout
  - Modular monolith with clear module boundaries

Netflix:
  - Microservices, each with their own trunk
  - Continuous deployment from trunk
  - Spinnaker manages deployments
  - Comprehensive monitoring and canary analysis

Amazon:
  - Each team controls their own repository and deployment
  - Small, frequent deployments (23,000+ deploys/day across all teams)
  - Internal Apollo deployment system

7. MIGRATION FROM GIT FLOW TO TBD
================================================================================

Why Teams Migrate:
  - Git Flow's develop branch becomes a bottleneck
  - Increasing merge conflicts
  - Release branches block deployment velocity
  - DORA research shows TBD correlates with high performance

Migration Steps:

  PHASE 1: Preparation (2-4 weeks)
    - Increase test coverage to > 70%
    - Ensure CI runs in < 10 minutes
    - Set up feature flag infrastructure
    - Team training on TBD practices

  PHASE 2: Simplify (2-4 weeks)
    - Stop creating new release branches
    - Deploy directly from develop (if it mirrors main)
    - Move toward deploying from main
    - Start using feature flags for new features

  PHASE 3: Eliminate Develop (2-4 weeks)
    - Merge feature branches directly to main
    - Remove develop branch (protect main instead)
    - Shorten branch lifetimes aggressively

  PHASE 4: Short-lived Branches
    - Enforce: branches must merge within 2 days
    - PR size limit: 400 lines of code (small PRs)
    - Daily merges to main

  PHASE 5: Optimize
    - Enable auto-merge for PRs passing all checks
    - Reduce CI time to < 5 minutes
    - Implement better feature flag lifecycle management

Challenges During Migration:
  - Psychological: "We need the develop buffer"
  - Missing: test coverage for safe trunk commits
  - Cultural: "Code isn't done until the feature is complete"
  - Process: Existing release process tied to release branches

8. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the main difference between Git Flow and Trunk-Based Development?
A: Git Flow uses multiple long-lived branches (main, develop) and short-lived
   branches (feature, release, hotfix) with formal processes for each. Features
   are developed in isolation on branches, then integrated through develop before
   reaching main. This supports scheduled versioned releases.
   
   Trunk-Based Development has developers committing to a single shared trunk
   (main) at least daily, using feature flags to hide incomplete work. There are
   no long-lived branches. This maximizes integration frequency, reduces merge
   conflicts, and supports continuous deployment.
   
   DORA research shows TBD correlates with high-performing engineering teams.

Q2: Why is Git Flow problematic for teams deploying continuously?
A: Several reasons:
   1. The develop branch creates a "staging area" that delays getting code to
      production — everything must pass through develop before main.
   2. Release branches introduce queuing — you can't deploy until the release
      branch is finished.
   3. Feature branches may live for days/weeks, causing integration hell when
      merged to develop.
   4. Merging hotfixes to BOTH main and develop is error-prone (teams forget
      to merge to develop, causing regression in next release).
   
   Vincent Driessen himself acknowledged this in a 2020 addendum to his
   original post.

Q3: What are feature flags and why are they critical for Trunk-Based Development?
A: Feature flags (toggles) are runtime configuration switches that control
   which features are active without requiring a deployment. In TBD, they allow
   incomplete features to be merged to trunk (so CI benefits from early
   integration) while keeping the feature invisible to users.
   
   Example: Developer merges search autocomplete code to main on Monday. The
   feature flag is disabled in production. By Thursday, the feature is complete.
   The flag is enabled for 10% of users first, then gradually rolled to 100%.
   
   Feature flags also enable: A/B testing, gradual rollouts, instant kill
   switches, and permission-based features (premium features for paying users).

Q4: How does TBD handle the case where a feature takes 2 weeks to build?
A: Several techniques:
   1. Feature flags: Commit incremental progress to trunk behind a disabled flag.
      The incomplete code is deployed but invisible to users.
   2. Branch by abstraction: For large refactors, create an abstraction over
      existing code, build new implementation alongside old, switch via flag.
   3. Work decomposition: Break the 2-week feature into small incremental
      changes that each provide value independently. Each can be committed to
      trunk separately.
   4. Keystone approach: Build all the supporting pieces first, add the "keystone"
      UI/entry point last. Everything merges to trunk early, but the feature is
      only visible when the keystone is added.

Q5: Describe a situation where you would choose Git Flow over TBD.
A: I would choose Git Flow if:
   1. Building a mobile SDK used by thousands of app developers who can't all
      upgrade simultaneously — need to maintain v1.x and v2.x simultaneously.
   2. Enterprise on-premise software where customers deploy at their own schedule
      and need formal release packages.
   3. A regulated environment (medical device software, banking) requiring formal
      release documentation and sign-off before each release.
   4. A team new to Git that needs a more explicit, well-documented process before
      transitioning to the discipline required for TBD.

9. QUICK REFERENCE CHEAT SHEET
================================================================================

Git Flow:
  Branches: main, develop, feature/*, release/*, hotfix/*
  Flow: feature → develop → release → main
  Hotfix: main → hotfix → BOTH main (tag) AND develop
  Best for: Versioned software, mobile apps, enterprise
  Problem: Slows down CD, complex merges

Trunk-Based Development:
  Branches: main (trunk) only, or max 1-2 day feature branches
  Flow: feature (1-2 days) → main, directly or via tiny PRs
  Feature flags: Replace long-lived branches for incomplete work
  Best for: SaaS, continuous deployment, high-frequency teams
  Requirement: Strong tests, fast CI, feature flag infrastructure

Feature Flags:
  Types: Release, Experiment (A/B), Ops (kill switch), Permission
  Lifecycle: Create → Deploy (disabled) → Enable % → Full rollout → REMOVE
  Tools: LaunchDarkly, Unleash, Flagsmith, AWS AppConfig

Branch by Abstraction:
  For large refactors without long-lived branches:
  Interface → Old implements it → New implements it (flag) → Switch → Remove old

DORA Finding:
  Trunk-based development → higher deployment frequency, lower change failure rate

Decision:
  Frequent deployments (SaaS): TBD or GitHub Flow
  Versioned releases (SDK, enterprise): Git Flow
  Multiple environments: GitLab Flow
