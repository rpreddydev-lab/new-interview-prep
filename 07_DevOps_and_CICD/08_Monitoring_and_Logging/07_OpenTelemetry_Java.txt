1. WHAT IS OPENTELEMETRY?
================================================================================

Definition:
  OpenTelemetry (OTel) is a vendor-neutral, CNCF-graduated open standard
  for collecting and exporting telemetry data (traces, metrics, logs).
  
  It provides:
  - APIs: Language-specific interfaces for instrumentation
  - SDKs: Implementations of the APIs
  - Auto-instrumentation: Agents that instrument without code changes
  - Collector: Telemetry data pipeline
  - Specification: Wire format standards (OTLP protocol)

Why OpenTelemetry?

  BEFORE OTel:
  Each vendor (Datadog, New Relic, Dynatrace, Jaeger, Zipkin) had its own:
  - Agent
  - SDK
  - Wire format
  
  Problem: Lock-in. Switch from Jaeger to Datadog → rewrite instrumentation.

  WITH OTel:
  Instrument once → export to any backend.
  
  VENDOR NEUTRAL: Instrument with OTel SDK.
  Send to Jaeger today, Datadog tomorrow — just change the exporter.

OpenTelemetry Status (2024):
  Traces:  STABLE across all major languages
  Metrics: STABLE
  Logs:    STABLE (Java, Python, .NET)
  
  Java OTel agent: Production-ready, widely used

2. THE THREE PILLARS: TRACES, METRICS, LOGS
================================================================================

TRACES — "What happened and how long did it take?"

  A TRACE represents the lifecycle of a single request across all services.
  A TRACE contains multiple SPANS.
  
  Span:
  - Name: operation name (e.g., "GET /api/orders/{id}")
  - TraceId: unique ID for the entire trace (shared by all spans)
  - SpanId: unique ID for this specific span
  - ParentSpanId: ID of the parent span (builds the tree)
  - Start time + Duration
  - Status (OK / ERROR)
  - Attributes (key-value pairs): http.method, db.statement, http.status_code
  - Events: timestamped messages within a span ("query started", "cache miss")
  - Links: references to other traces (e.g., async messages)
  
  Example trace for "GET /orders/123":
  
  [GET /orders/123]        0ms → 120ms   (root span, API gateway)
    [GET /orders/123]      5ms → 100ms   (order-service)
      [SELECT orders]     10ms → 40ms    (DB span)
      [GET /users/456]    50ms → 80ms    (call to user-service)
        [SELECT users]    55ms → 75ms    (user-service DB span)

METRICS — "How is the system performing over time?"

  Numerical measurements over time.
  Types:
  - Counter: monotonically increasing (request count, error count)
  - Gauge: current value (JVM heap, active connections)
  - Histogram: value distribution (request latency percentiles)
  - Summary: pre-computed percentiles (p50, p95, p99)
  
  OTel Metrics → exported to Prometheus, Datadog, CloudWatch, etc.

LOGS — "What did the application print?"

  Structured log records with:
  - Timestamp
  - Severity level (TRACE, DEBUG, INFO, WARN, ERROR)
  - Body (message)
  - Attributes (key-value context)
  - TraceId and SpanId → CORRELATE logs with traces!
  
  The KEY innovation: OTel connects all three.
  See an error trace → click → see the logs for that exact trace context.

3. OPENTELEMETRY ARCHITECTURE
================================================================================

Components:

  ┌──────────────────────────────────────────────────────────────────────┐
  │                    APPLICATION (Java / Spring Boot)                  │
  │                                                                      │
  │  OTel Java Agent (auto-instrumentation)  OR  OTel SDK (manual)      │
  │                          ↓                                           │
  │              OTel Exporter (OTLP / Jaeger / Prometheus)              │
  └──────────────────────────────────────────────────────────────────────┘
                             ↓  OTLP (gRPC or HTTP)
  ┌──────────────────────────────────────────────────────────────────────┐
  │                    OPENTELEMETRY COLLECTOR                           │
  │                                                                      │
  │   Receivers → Processors → Exporters                                 │
  │   (OTLP)      (filter,     (Jaeger, Prometheus,                      │
  │               batch,        Datadog, CloudWatch)                     │
  │               enrich)                                                │
  └──────────────────────────────────────────────────────────────────────┘
                    ↓                    ↓                    ↓
               JAEGER UI           PROMETHEUS          DATADOG/NewRelic

Data Model:
  OTLP (OpenTelemetry Protocol): standard wire format over gRPC or HTTP/JSON
  All backends that support OTLP (Jaeger 1.35+, Tempo, Datadog, etc.)
  can receive directly.

4. JAVA AUTO-INSTRUMENTATION AGENT
================================================================================

What the Java Agent Does:

  A Java agent attaches to the JVM at startup (via -javaagent flag).
  Uses bytecode manipulation to automatically instrument:
  - HTTP servers (Tomcat, Jetty, Undertow, Netty)
  - HTTP clients (Apache HTTP, OkHttp, RestTemplate, WebClient, Feign)
  - JDBC drivers (all major databases)
  - Message brokers (Kafka, RabbitMQ, ActiveMQ)
  - Spring MVC, Spring WebFlux, JAX-RS
  - gRPC, Elasticsearch, Redis (Jedis, Lettuce)
  - And 100+ more libraries

No code changes required!

Download and Run:

  # Download agent:
  curl -L -o opentelemetry-javaagent.jar \
    https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar
  
  # Run Spring Boot with agent:
  java -javaagent:opentelemetry-javaagent.jar \
    -Dotel.service.name=order-service \
    -Dotel.exporter.otlp.endpoint=http://otel-collector:4317 \
    -Dotel.traces.exporter=otlp \
    -Dotel.metrics.exporter=otlp \
    -Dotel.logs.exporter=otlp \
    -jar app.jar

In Kubernetes — JAVA_TOOL_OPTIONS:

  env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -javaagent:/otel/opentelemetry-javaagent.jar
      -Dotel.service.name=order-service
      -Dotel.resource.attributes=deployment.environment=production,k8s.namespace.name=$(POD_NAMESPACE)
      -Dotel.exporter.otlp.endpoint=http://otel-collector.monitoring:4317
      -Dotel.traces.exporter=otlp
      -Dotel.metrics.exporter=otlp
      -Dotel.logs.exporter=otlp
      -Dotel.instrumentation.logback-appender.enabled=true
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef:
        fieldPath: metadata.namespace
  
  # Mount the agent from an init container:
  initContainers:
  - name: otel-agent-init
    image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-java:latest
    command: ["cp", "/javaagent.jar", "/otel/opentelemetry-javaagent.jar"]
    volumeMounts:
    - name: otel-agent
      mountPath: /otel
  
  volumes:
  - name: otel-agent
    emptyDir: {}

OTel Operator (Kubernetes-Native Auto-Instrumentation):

  The OTel Operator can inject the agent automatically via annotations:
  
  # Install OTel Operator:
  kubectl apply -f https://github.com/open-telemetry/opentelemetry-operator/releases/latest/download/opentelemetry-operator.yaml
  
  # Create Instrumentation resource:
  apiVersion: opentelemetry.io/v1alpha1
  kind: Instrumentation
  metadata:
    name: java-instrumentation
  spec:
    exporter:
      endpoint: http://otel-collector:4317
    java:
      image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-java:latest
      env:
      - name: OTEL_TRACES_SAMPLER
        value: parentbased_traceidratio
      - name: OTEL_TRACES_SAMPLER_ARG
        value: "0.1"    # 10% sampling in production
  
  # Annotate pods to inject agent:
  annotations:
    instrumentation.opentelemetry.io/inject-java: "true"

Key Agent Configuration Properties:

  otel.service.name                   Service name in traces/metrics
  otel.exporter.otlp.endpoint         OTLP endpoint (gRPC)
  otel.exporter.otlp.endpoint.http    OTLP endpoint (HTTP)
  otel.traces.exporter                otlp, jaeger, zipkin, logging, none
  otel.metrics.exporter               otlp, prometheus, logging, none
  otel.logs.exporter                  otlp, logging, none
  otel.traces.sampler                 always_on, parentbased_traceidratio, etc.
  otel.traces.sampler.arg             Sampling ratio (0.0 to 1.0)
  otel.resource.attributes            key=value,key2=value2 (added to all telemetry)
  otel.propagators                    tracecontext,baggage,b3,b3multi

Custom Spans — Adding Business Context:

  @Service
  public class OrderService {
      
      private final Tracer tracer;
      
      public OrderService(Tracer tracer) {
          this.tracer = tracer;
      }
      
      public Order processOrder(String orderId) {
          // Create a custom span:
          Span span = tracer.nextSpan()
              .name("process-order")
              .tag("order.id", orderId)
              .tag("order.channel", "web")
              .start();
          
          try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
              // Add events:
              span.event("validation-started");
              validateOrder(orderId);
              span.event("validation-completed");
              
              Order order = findOrder(orderId);
              
              if (order == null) {
                  span.tag("error", "true");
                  span.tag("order.not_found", "true");
                  throw new OrderNotFoundException(orderId);
              }
              
              return order;
          } catch (Exception e) {
              span.error(e);
              throw e;
          } finally {
              span.end();
          }
      }
  }

Custom Metrics with Micrometer:

  @Component
  public class OrderMetrics {
      
      private final Counter ordersProcessed;
      private final Counter ordersFailed;
      private final Timer orderProcessingTime;
      private final Gauge activeOrders;
      
      public OrderMetrics(MeterRegistry registry) {
          // Counter: monotonically increasing
          this.ordersProcessed = Counter.builder("orders.processed")
              .description("Total orders processed")
              .tag("type", "standard")
              .register(registry);
          
          this.ordersFailed = Counter.builder("orders.failed")
              .description("Total orders failed")
              .register(registry);
          
          // Timer: latency histogram
          this.orderProcessingTime = Timer.builder("orders.processing.time")
              .description("Order processing duration")
              .publishPercentiles(0.5, 0.95, 0.99)
              .register(registry);
          
          // Gauge: current value
          this.activeOrders = Gauge.builder("orders.active", this, 
              OrderMetrics::getActiveOrderCount)
              .description("Currently active orders")
              .register(registry);
      }
      
      public void recordOrderProcessed() {
          ordersProcessed.increment();
      }
      
      public void recordOrderFailed() {
          ordersFailed.increment();
      }
      
      public void recordProcessingTime(Duration duration) {
          orderProcessingTime.record(duration);
      }
      
      // Timer.record() pattern:
      public Order processWithTiming(String orderId) {
          return orderProcessingTime.record(() -> {
              // business logic
              return findAndProcessOrder(orderId);
          });
      }
      
      private double getActiveOrderCount() {
          // return current count from DB/cache
          return 0;
      }
  }

6. OPENTELEMETRY COLLECTOR
================================================================================

What is the OTel Collector?

  A standalone service (not embedded in your app) that:
  - Receives telemetry from applications (OTLP, Jaeger, Zipkin formats)
  - Processes it (filter, enrich, batch, sample)
  - Exports to one or more backends

Why Use the Collector?

  Without Collector:
    Every app exports directly to backend (Jaeger/Datadog/etc.)
    Backend URL hardcoded in app config
    Switch backend → update all apps
  
  With Collector:
    App sends to Collector (stable internal URL)
    Collector exports to backend (change here only)
    Collector can fan-out to multiple backends simultaneously

Collector Configuration (otel-collector-config.yaml):

  receivers:
    otlp:
      protocols:
        grpc:
          endpoint: 0.0.0.0:4317    # Receive from apps
        http:
          endpoint: 0.0.0.0:4318
    
    # Also receive Prometheus scrape targets:
    prometheus:
      config:
        scrape_configs:
          - job_name: spring-boot-apps
            kubernetes_sd_configs:
              - role: pod
  
  processors:
    # Batch for efficiency:
    batch:
      timeout: 5s
      send_batch_size: 1024
    
    # Add K8s metadata:
    k8sattributes:
      auth_type: serviceAccount
      extract:
        metadata:
          - k8s.pod.name
          - k8s.namespace.name
          - k8s.deployment.name
          - k8s.node.name
    
    # Filter noisy endpoints:
    filter/drop-health:
      traces:
        span:
          - 'attributes["http.route"] == "/actuator/health"'
    
    # Memory limiter (prevent OOM):
    memory_limiter:
      check_interval: 1s
      limit_mib: 512
  
  exporters:
    otlp/jaeger:
      endpoint: jaeger:4317
      tls:
        insecure: true
    
    prometheus:
      endpoint: "0.0.0.0:8889"     # Prometheus scrapes this
    
    otlp/tempo:                     # Grafana Tempo
      endpoint: tempo:4317
      tls:
        insecure: true
    
    datadog:
      api:
        key: ${DD_API_KEY}
    
    # Debug (print to stdout):
    debug:
      verbosity: normal
  
  service:
    pipelines:
      traces:
        receivers: [otlp]
        processors: [memory_limiter, k8sattributes, filter/drop-health, batch]
        exporters: [otlp/jaeger, otlp/tempo]
      
      metrics:
        receivers: [otlp, prometheus]
        processors: [memory_limiter, k8sattributes, batch]
        exporters: [prometheus]
      
      logs:
        receivers: [otlp]
        processors: [memory_limiter, k8sattributes, batch]
        exporters: [otlp/jaeger]

Deploy Collector in Kubernetes:

  # application.yaml:

  With Micrometer Tracing + Logback, traceId and spanId are automatically
  added to MDC. Your log pattern can include them:
  
  # logback-spring.xml:
  <pattern>
    {"timestamp":"%d{ISO8601}","level":"%level","traceId":"%X{traceId}",
    "spanId":"%X{spanId}","service":"my-app","message":"%msg"}%n
  </pattern>
  
  Result: Every log line includes the traceId → searchable in ELK/Loki.

9. CONTEXT PROPAGATION
================================================================================

Why Context Propagation Matters:

  Distributed tracing only works if the trace context (traceId, spanId)
  is passed between services via HTTP headers or message headers.
  
  Without propagation: each service sees independent spans → broken traces.
  With propagation: spans are linked → complete request journey visible.

W3C TraceContext Format (Recommended):
  
  Header: traceparent: 00-{traceId}-{spanId}-{flags}
  Example: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  
  Also: tracestate (vendor-specific metadata)

B3 Format (Zipkin/Brave):
  
  Single header: b3: {traceId}-{spanId}-{samplingState}-{parentSpanId}
  Multi header:  x-b3-traceid, x-b3-spanid, x-b3-sampled, x-b3-parentspanid

Propagation in Kafka Messages:

  // Producer: inject trace headers into Kafka record headers
  // OTel Java agent / Spring Cloud Sleuth does this automatically
  // when using KafkaTemplate
  
  // Consumer: extract trace from record headers
  // @KafkaListener is automatically instrumented by Spring Sleuth/Micrometer

  // Manual propagation example:
  @Service
  public class OrderEventPublisher {
      
      @Autowired
      private KafkaTemplate<String, OrderEvent> kafkaTemplate;
      
      @Autowired
      private Tracer tracer;
      
      public void publish(OrderEvent event) {
          // OTel agent/Sleuth auto-injects trace headers into ProducerRecord
          // If not using agent, inject manually:
          ProducerRecord<String, OrderEvent> record = 
              new ProducerRecord<>("orders", event.getId(), event);
          
          Span currentSpan = tracer.currentSpan();
          if (currentSpan != null) {
              // Inject trace context into Kafka headers
              OpenTelemetry.getPropagators()
                  .getTextMapPropagator()
                  .inject(Context.current(), record.headers(), 
                      (headers, key, value) -> headers.add(key, value.getBytes()));
          }
          
          kafkaTemplate.send(record);
      }
  }

Baggage — Passing Custom Values Across Services:

  Baggage is data attached to the trace context, propagated automatically.
  Use for business context: userId, tenantId, correlationId.
  
  // Set baggage:
  Baggage.current().toBuilder()
      .put("user.id", userId)
      .put("tenant.id", tenantId)
      .build()
      .makeCurrent();
  
  // Read baggage in downstream service:
  String userId = Baggage.current().getEntryValue("user.id");
  
  ⚠️ Warning: Baggage is propagated over the network — keep values small!

11. SAMPLING STRATEGIES
================================================================================

Why Sampling?

  100% trace collection = enormous data volume at scale.
  A service doing 10,000 RPS generates 10,000 spans/sec.
  Sampling reduces volume while preserving observability.

Sampling Types:

  HEAD-BASED SAMPLING (OTel default):
    Decision made at the START of the trace (at first span).
    Simple: 10% → sample 1 in 10 requests.
    Problem: Can miss important low-frequency errors.
  
  TAIL-BASED SAMPLING:
    Decision made AFTER the trace is complete.
    Can sample based on outcome: always sample errors, slow requests.
    Requires the OTel Collector to buffer and evaluate.

OTel Sampler Types:

  always_on:                   Sample 100% (development/debug only)
  always_off:                  Sample 0% (disable tracing)
  traceidratio:                Random ratio (e.g., 10%)
  parentbased_always_on:       Respect parent's sampling decision
  parentbased_traceidratio:    Recommended for production
  parentbased_always_off:      Disable but respect parent

Recommended Production Setup:
  
  # OTel Agent flags:
  -Dotel.traces.sampler=parentbased_traceidratio
  -Dotel.traces.sampler.arg=0.1      # 10% sampling
  
  # Spring Boot 3.x application.yaml:
  management:
    tracing:
      sampling:
        probability: 0.1              # 10%

Tail-Based Sampling in Collector:

  # Always sample traces with errors or slow spans:
  processors:
    tail_sampling:
      decision_wait: 10s             # Buffer traces for 10s
      policies:
        - name: error-traces
          type: status_code
          status_code:
            status_codes: [ERROR]
        
        - name: slow-traces
          type: latency
          latency:
            threshold_ms: 2000       # Sample if > 2 seconds
        
        - name: probabilistic-rest
          type: probabilistic
          probabilistic:
            sampling_percentage: 5   # 5% of everything else

13. LOGS CORRELATION (STRUCTURED LOGGING + TRACEID)

The Goal:
  Every log line includes traceId and spanId.
  When you find a trace with an error in Jaeger/Tempo,
  you can jump directly to the logs for that exact trace in Kibana/Loki.

Logback Configuration for Structured JSON Logging:

  <!-- pom.xml: -->
  <dependency>
    <groupId>net.logstash.logback</groupId>
    <artifactId>logstash-logback-encoder</artifactId>
    <version>7.4</version>
  </dependency>
  
  <!-- logback-spring.xml: -->
  <?xml version="1.0" encoding="UTF-8"?>
  <configuration>
    <springProperty name="APP_NAME" source="spring.application.name"/>
    
    <appender name="JSON_CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
      <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <providers>
          <timestamp/>
          <logLevel/>
          <loggerName/>
          <mdc/>                <!-- Includes traceId, spanId from MDC -->
          <message/>
          <stackTrace/>
          <pattern>
            <pattern>{"service": "${APP_NAME}", "environment": "${SPRING_PROFILES_ACTIVE:-default}"}</pattern>
          </pattern>
        </providers>
      </encoder>
    </appender>
    
    <root level="INFO">
      <appender-ref ref="JSON_CONSOLE"/>
    </root>
  </configuration>
  
  Output per log line:
  {
    "timestamp": "2024-01-15T10:30:00.123Z",
    "level": "ERROR",
    "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
    "spanId": "00f067aa0ba902b7",
    "service": "order-service",
    "environment": "production",
    "message": "Payment processing failed for order 123",
    "logger_name": "com.company.OrderService"
  }

Add Custom MDC Fields:

  // Add business context to all logs in current thread:
  MDC.put("orderId", orderId);
  MDC.put("customerId", customerId);
  MDC.put("requestId", requestId);
  
  try {
      // All log statements here include orderId, customerId
      log.info("Processing order");
      processOrder(orderId);
  } finally {
      // Always clear MDC to prevent context leaking to other requests:
      MDC.remove("orderId");
      MDC.remove("customerId");
  }
  
  // Or use a filter for HTTP request context:
  @Component
  public class MDCLoggingFilter extends OncePerRequestFilter {
      @Override
      protected void doFilterInternal(HttpServletRequest req,
              HttpServletResponse res, FilterChain chain) 
              throws IOException, ServletException {
          MDC.put("requestId", UUID.randomUUID().toString());
          MDC.put("clientIp", req.getRemoteAddr());
          try {
              chain.doFilter(req, res);
          } finally {
              MDC.clear();
          }
      }
  }

14. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between Spring Cloud Sleuth and OpenTelemetry?
    Why did Spring Boot move from Sleuth to Micrometer Tracing?

A: Spring Cloud Sleuth (Spring Boot 2.x):
   - Spring-specific distributed tracing library
   - Wired into Spring's HTTP clients, Kafka, etc.
   - Supports B3 propagation (Zipkin format)
   - Added traceId/spanId to MDC automatically
   - Limited to Spring ecosystem
   
   OpenTelemetry:
   - Vendor-neutral CNCF standard (not Spring-specific)
   - Works with any Java framework
   - Supports W3C TraceContext, B3, Jaeger propagation
   - Covers traces + metrics + logs in one standard
   - Exportable to any backend (Jaeger, Tempo, Datadog, Honeycomb)
   
   Why the move:
   Sleuth was Spring-specific and vendor-specific (primarily Zipkin).
   Industry standardized on OpenTelemetry as THE observability standard.
   Spring Boot 3 adopted Micrometer Tracing as the facade:
   - Micrometer Tracing abstracts the tracing implementation
   - OTel bridge: uses OpenTelemetry SDK underneath
   - Brave bridge: uses Zipkin Brave SDK underneath
   This gives Spring Boot users access to OTel's full ecosystem.

---

Q2: How does the OpenTelemetry Java agent work under the hood?

A: The Java agent uses bytecode instrumentation via Java's Instrumentation API.
   
   Startup:
   1. JVM loads the agent via -javaagent flag before main class
   2. Agent registers a ClassFileTransformer with the JVM
   3. As each class is loaded, the transformer intercepts it
   4. Agent rewrites bytecode of instrumented classes (Tomcat, JDBC, etc.)
   5. Inserts span creation/ending code around method calls
   
   Key mechanism: ByteBuddy library used to rewrite bytecode.
   Agent defines "advice" for each library (e.g., "before HttpServlet.service()
   start a span; after it, end the span with the response status").
   
   No reflection → low overhead.
   No source code changes needed.
   Compatible with Java 8+ (some features require 11+).

---

Q3: A distributed trace shows a missing span — the trace from service A to
    service B is not visible. What are the possible causes?

A: 1. Trace headers not propagated:
      Service A uses a manually created RestTemplate (not Spring-managed).
      OTel/Sleuth instrumentation only applies to injected beans.
      Fix: Use @Autowired RestTemplate or WebClient (Spring-managed).
   
   2. Incompatible propagation format:
      Service A uses B3 format, Service B expects W3C TraceContext.
      Fix: Standardize on W3C (W3C TraceContext is the modern standard).
   
   3. Service B is not instrumented:
      No OTel agent attached to Service B.
      Fix: Add -javaagent or OTel Operator annotation.
   
   4. Sampling mismatch:
      Service A samples 100%, Service B samples 10%.
      Service B's sampler rejects parent's decision.
      Fix: Use parentbased_traceidratio (respects parent's decision).
   
   5. Async boundary:
      Service A passes work to a thread pool; trace context not propagated.
      Fix: Use OTel Context.taskWrapping() or Spring's @Async with OTel.
   
   6. Message queue between services:
      Kafka/RabbitMQ consumers need header extraction.
      Fix: OTel agent instruments Kafka/RabbitMQ automatically.
         Manual: use TextMapPropagator to extract from message headers.

---

Q4: How do you implement sampling in production so you don't lose important
    traces but also don't generate too much data?

A: Multi-tier sampling strategy:
   
   1. Head-based sampling at 10%:
      parentbased_traceidratio with 0.1
      Captures 10% of ALL requests randomly.
   
   2. Always sample on errors:
      Use OTel Collector tail-based sampling processor.
      Policy: sample_status_code = ERROR → always sample.
   
   3. Always sample slow requests:
      Collector tail-based policy: latency > 2000ms → always sample.
   
   4. Always sample specific operations:
      For critical business operations (payment, checkout):
      Add trace flag in code: span.setAttribute("sampling.priority", 1)
      Collector policy: sample if sampling.priority attribute present.
   
   5. Force sampling for debugging:
      Add HTTP header: x-b3-sampled: 1 from Postman/curl during debugging
      With parentbased sampler, this forces sampling for that trace.
   
   Result:
   - 90% of normal traffic: not sampled (saves storage)
   - 10% random sample: captured (for baseline analysis)
   - 100% of errors: captured (catch all problems)
   - 100% of slow requests: captured (performance analysis)
