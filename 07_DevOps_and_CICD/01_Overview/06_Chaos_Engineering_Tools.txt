1. WHAT IS CHAOS ENGINEERING?
================================================================================

Definition:

  Chaos Engineering is the discipline of experimenting on a system in order
  to build confidence in the system's capability to withstand turbulent
  conditions in production.

  — Netflix Engineering, Principles of Chaos Engineering (2016)

The Core Idea:

  Production failures ARE going to happen.
  Hardware fails, networks partition, services crash, dependencies timeout.
  
  Better to discover how your system REACTS to failures:
    a) By YOU, during a controlled chaos experiment (you control it)
    b) By RANDOM production incidents (you don't control it)
  
  Chaos Engineering = Find weaknesses before your users find them.

What Chaos Engineering Is NOT:

  ✗ NOT randomly breaking things (that's reckless)
  ✗ NOT testing obvious failures that monitoring already catches
  ✗ NOT running in prod without observability and a stop button
  ✓ IS structured hypothesis-driven experiments
  ✓ IS minimizing blast radius (start in dev/staging, move to prod carefully)
  ✓ IS automated with rollback and safety mechanisms

The Chaos Engineering Loop:

  1. Define "steady state" (what does healthy look like?)
     e.g., "95th percentile latency < 200ms, error rate < 1%"
  
  2. Hypothesize: "This system remains healthy even when X fails."
  
  3. Introduce failure (controlled):
     Kill a pod, add network latency, fill disk, etc.
  
  4. Measure: Does steady state hold? If not, you found a weakness.
  
  5. Fix the weakness (resilience pattern, circuit breaker, retry, etc.)
  
  6. Automate the experiment → run continuously

2. THE CHAOS ENGINEERING PRINCIPLE (SIMIAN ARMY TO CNCF)
================================================================================

History:

  2011: Netflix creates Chaos Monkey (kills random EC2 instances in prod)
  2012: Simian Army: Chaos Gorilla (kills AZ), Chaos Kong (kills region), etc.
  2016: Netflix publishes "Principles of Chaos Engineering"
  2018: Chaos Toolkit, Gremlin, Litmus created
  2022: LitmusChaos graduates to CNCF Incubating
  2024: LitmusChaos is CNCF graduated (mature, production-ready)

Principles of Chaos Engineering:

  1. Build a Hypothesis around Steady State Behavior
  2. Vary Real-World Events (what happens in production?)
  3. Run Experiments in Production (staging is not enough!)
  4. Automate Experiments to Run Continuously
  5. Minimize Blast Radius (start small, expand carefully)

Why Prod? Why Not Just Staging?

  Staging is a simplified version of production.
  Production has:
  - Real traffic patterns (caches warmed, connections established)
  - Real data volumes (100M rows, not 1000)
  - Real dependencies at scale
  
  A service that works in staging under artificial load may NOT behave the
  same in prod. Chaos experiments in staging provide partial confidence.
  Prod chaos (with safeguards) provides full confidence.

3. WHY CHAOS ENGINEERING MATTERS FOR JAVA DEVELOPERS
================================================================================

Java-Specific Failure Modes That Chaos Engineering Reveals:

  1. JVM OOMKilled cascades:
     One service gets OOMKilled → threads blocked waiting for it →
     thread pool exhaustion → entire service unresponsive.
     Chaos: Kill pod → verify circuit breaker opens, other pods healthy.
  
  2. Long GC pause causing timeouts:
     Full GC pause (G1GC, 2-5 seconds) → downstream times out →
     caller retries → thundering herd → GC gets worse.
     Chaos: Induce GC pressure → measure latency spike impact.
  
  3. Connection pool exhaustion:
     Database goes slow → queries pile up → HikariCP pool exhausted →
     all requests to that service fail (not just DB-dependent ones!).
     Chaos: Add DB latency → verify HikariCP timeout, requests fail fast.
  
  4. Thread pool starvation:
     One slow dependency blocks all Tomcat threads →
     entire Spring Boot app unresponsive (even health endpoint!).
     Chaos: Add latency to dependency → verify resilience4j bulkhead opens.
  
  5. Spring Boot startup probe failure under load:
     Busy node → slow JVM startup → readiness probe fails →
     K8s kills pod before it's ready → rolling deploy fails.
     Chaos: Kill pod during high load → verify graceful handoff.

Senior Java Developer Value:

  Interviewers at senior level expect you to know:
  - What can go wrong at scale (experience with failure modes)
  - How to validate resilience patterns (chaos experiments)
  - How to talk about reliability quantitatively (SLOs, error budgets)
  
  Chaos engineering experience = strong signal for 7+ YOE candidate.

4. LITMUSCHOAS — CNCF-GRADUATED CHAOS FRAMEWORK
================================================================================

Overview:

  LitmusChaos is a CNCF-graduated open-source chaos engineering framework.
  It provides:
  - ChaosHub: Library of 100+ pre-built chaos experiments
  - ChaosCenter: Web UI for managing experiments
  - ChaosOperator: Runs experiments on Kubernetes via CRDs
  - Probes: Automated validation during experiments (Prometheus, HTTP, K8s)

Installation:

  # Install LitmusChaos (Helm):
  helm repo add litmuschaos https://litmuschaos.github.io/litmus-helm/
  helm install litmuschaos litmuschaos/litmus \
    --namespace litmus \
    --create-namespace \
    --set portal.frontend.service.type=NodePort
  
  # Port-forward to UI:
  kubectl port-forward svc/litmusportal-frontend-service -n litmus 9091:9091
  # UI: http://localhost:9091

Core LitmusChaos CRDs:

  ChaosEngine:      Defines WHAT experiment to run on WHAT target
  ChaosExperiment:  Defines the experiment logic (from ChaosHub)
  ChaosResult:      Stores the results of a completed experiment

ChaosEngine Example — Pod Delete:

  apiVersion: litmuschaos.io/v1alpha1
  kind: ChaosEngine
  metadata:
    name: order-service-pod-delete
    namespace: production
  spec:
    appinfo:
      appns: production             # Target namespace
      applabel: app=order-service   # Target pod selector
      appkind: deployment
    
    # Service account with permissions to delete pods:
    engineState: active
    chaosServiceAccount: litmus-admin
    
    experiments:
      - name: pod-delete
        spec:
          components:
            env:
              - name: TOTAL_CHAOS_DURATION
                value: "60"           # Run chaos for 60 seconds
              - name: CHAOS_INTERVAL
                value: "10"           # Delete pod every 10 seconds
              - name: FORCE
                value: "false"        # Graceful termination
              - name: PODS_AFFECTED_PERC
                value: "50"           # Kill 50% of matching pods
    
    # Probes: Validate steady state DURING experiment:
    jobCleanUpPolicy: delete
    monitoring: true
    engineState: active
    
    annotationCheck: "false"

Probes (Automated Validation During Experiment):

  # Add probes to ChaosEngine to validate service health during chaos:
  experiments:
    - name: pod-delete
      spec:
        probe:
          # HTTP probe: check service responds
          - name: check-api-health
            type: httpProbe
            httpProbe/inputs:
              url: "http://order-service.production/actuator/health"
              expectedResponseCode: "200"
            mode: Continuous      # Check during entire experiment
            runProperties:
              probeTimeout: 10
              interval: 5
              attempt: 3
          
          # Prometheus probe: check error rate stays below threshold
          - name: check-error-rate
            type: promProbe
            promProbe/inputs:
              endpoint: "http://prometheus.monitoring:9090"
              query: >
                sum(rate(http_server_requests_seconds_count{
                  status=~"5..",
                  service="order-service"
                }[1m])) /
                sum(rate(http_server_requests_seconds_count{
                  service="order-service"
                }[1m]))
              comparator:
                type: float
                criteria: "<="
                value: "0.05"       # Error rate must stay below 5%
            mode: Continuous
            runProperties:
              probeTimeout: 30
              interval: 20
              attempt: 3

5. CHAOS MONKEY (NETFLIX) AND SIMIAN ARMY
================================================================================

Chaos Monkey:

  Original Netflix tool. Randomly terminates EC2 instances in production.
  Forces engineers to build services that can survive instance failures.
  
  Modern version: Spinnaker Chaos Monkey (works with cloud providers)
  
  Spring Boot Chaos Monkey (for Java!):
  
  # Add to pom.xml:
  <dependency>
    <groupId>de.codecentric</groupId>
    <artifactId>chaos-monkey-spring-boot</artifactId>
    <version>3.1.0</version>
  </dependency>
  
  # application.yml:
  chaos:
    monkey:
      enabled: true
      watcher:
        component: false
        controller: false
        repository: false
        rest-controller: true      # Inject failures into REST controllers
        service: true              # Inject failures into @Service beans
      assaults:
        level: 5                   # 1-10 (10=most aggressive)
        latencyActive: true
        latencyRangeStart: 1000    # 1 second latency
        latencyRangeEnd: 5000      # 5 second latency
        exceptionsActive: true
        killApplicationActive: false  # Don't kill the JVM itself

  # Chaos Monkey can inject:
  # - Latency (random delay on method calls)
  # - Exceptions (RuntimeException on @Service, @Repository methods)
  # - Memory assaults (fill heap → trigger GC)
  # - CPU assaults (busy CPU threads)
  
  # Enable/disable via Spring Boot Actuator endpoint:
  POST /actuator/chaosmonkey/enable
  POST /actuator/chaosmonkey/disable
  GET  /actuator/chaosmonkey/status

Simian Army (Full Netflix Suite):

  Chaos Monkey:    Kill random instances
  Chaos Gorilla:   Take down an entire Availability Zone
  Chaos Kong:      Take down an entire AWS Region
  Latency Monkey:  Introduce latency in service calls
  Doctor Monkey:   Detect unhealthy instances via health checks
  Janitor Monkey:  Clean up unused cloud resources
  Security Monkey: Audit security group policies
  Conformity Monkey: Check instances against best practices
  
  Note: Netflix has largely replaced Simian Army with modern tooling (Gremlin,
  LitmusChaos). Most simian components are deprecated.

6. GREMLIN — ENTERPRISE CHAOS PLATFORM
================================================================================

What is Gremlin?

  Gremlin is a SaaS chaos engineering platform.
  Enterprise-grade, with UI, scheduling, reporting, and "Reliability Score."
  Requires Gremlin agent on each node/pod.
  
  Cost: Paid (free tier for limited experiments).
  
  Gremlin differentiators vs LitmusChaos:
  - More polished UI and UX
  - Game Days (pre-planned chaos events with teams)
  - Reliability Score (track resilience improvements over time)
  - More attack types (DNS, process killer, time travel)
  - Better audit logging for compliance

Gremlin Attack Types:

  Resource Attacks:
    CPU:    Consume N% of CPU
    Memory: Consume N MB of memory
    Disk:   Fill disk to N% capacity
    IO:     Saturate disk I/O
  
  State Attacks:
    Shutdown:   Graceful/forceful process shutdown
    Process Kill: Kill specific process (e.g., kill JVM)
    Time Travel: Shift system clock forward/backward
  
  Network Attacks:
    Latency:     Add N ms delay to network traffic
    Packet Loss: Drop N% of packets
    Blackhole:   Block all traffic to/from targets
    DNS:         Delay or block DNS resolution
    Bandwidth:   Limit network throughput

Gremlin for Java Applications:

  # Most impactful Gremlin attacks for Spring Boot:
  
  Attack 1: Process Kill (JVM killed suddenly)
  → Does your K8s deployment restart quickly enough?
  → Do in-flight requests fail gracefully?
  
  Attack 2: Network Latency on database port
  → Does HikariCP timeout correctly?
  → Does Resilience4j circuit breaker open?
  → Do metrics alert in Grafana?
  
  Attack 3: Memory fill
  → Does JVM OOMKilled trigger? Or graceful rejection?
  → Does K8s restart the pod correctly?
  → Does the PodDisruptionBudget protect against all pods dying?

7. CHAOS MESH (CNCF SANDBOX)
================================================================================

What is Chaos Mesh?

  Chaos Mesh is a CNCF sandbox project from PingCAP (TiDB creators).
  Kubernetes-native chaos engineering platform with rich UI (Chaos Dashboard).
  
  Strength: Network chaos (partition, bandwidth, packet loss) and
            JVM-specific chaos (via bytecode injection).

JVM Chaos (Unique Feature!):

  Chaos Mesh can inject failures INTO the JVM via bytecode manipulation.
  No code changes needed.
  
  apiVersion: chaos-mesh.org/v1alpha1
  kind: JVMChaos
  metadata:
    name: order-service-jvm-exception
  spec:
    action: exception                   # Inject exception
    class: com.mycompany.OrderService
    method: processOrder
    exception: "java.lang.RuntimeException"
    exceptionMessage: "Simulated payment service failure"
    selector:
      namespaces: [production]
      labelSelectors:
        app: order-service
    mode: all
    duration: "60s"
  
  # Other JVM chaos actions:
  # action: latency    → add delay to method calls
  # action: gc         → force garbage collection
  # action: return     → force method to return specific value

Installation:

  helm repo add chaos-mesh https://charts.chaos-mesh.org
  helm install chaos-mesh chaos-mesh/chaos-mesh \
    --namespace chaos-testing \
    --create-namespace
  
  # Dashboard:
  kubectl port-forward -n chaos-testing svc/chaos-dashboard 2333:2333

Chaos Mesh Experiment Types:

  PodChaos:        Pod deletion, killing, container kill
  NetworkChaos:    Delay, loss, corruption, bandwidth, partition
  StressChaos:     CPU, memory stress
  DNSChaos:        DNS resolution failures
  HTTPChaos:       HTTP request/response injection (proxy-based)
  IOChaos:         I/O errors, latency, attribute override
  JVMChaos:        Java-specific: exception, latency, GC, return value

9. RUNNING CHAOS EXPERIMENTS IN KUBERNETES
================================================================================

Experiment Execution Flow:

  1. PRE-CHAOS:
     - Verify system is at steady state (no existing incidents!)
     - Ensure monitoring/alerting is active (Prometheus + Grafana)
     - Have rollback plan ready
     - Notify on-call team (even in staging)
  
  2. RUN EXPERIMENT:
     - Start with minimal blast radius (1 pod, not all)
     - Run for short duration (30 seconds, then extend)
     - Monitor Grafana dashboards LIVE during experiment
     - Check Prometheus metrics, application logs, K8s events
  
  3. OBSERVE AND MEASURE:
     - Did steady state hold?
     - What was the latency impact?
     - Did alerts fire? (and was it within SLO?)
     - Did circuit breaker open as expected?
     - Did K8s self-heal correctly?
  
  4. POST-CHAOS:
     - Verify system returned to steady state
     - Document findings
     - Create tickets for weaknesses found
     - Fix and re-run experiment to verify fix

RBAC for LitmusChaos:

      name: pod-delete-sa
  roleRef:
    kind: Role
    name: pod-delete-role
    apiGroup: rbac.authorization.k8s.io

GameDays:

  A GameDay is a scheduled, organization-wide chaos experiment.
  Team practices responding to real failures in a controlled setting.
  
  GameDay structure:
  1. Pre-work: Define experiments, notify stakeholders, ensure monitors
  2. Run experiments: Teams observe their services during chaos
  3. Debrief: What failed? What was unexpected? What resilience worked?
  4. Remediation plan: Fix the weaknesses discovered

10. SRE INTEGRATION — CHAOS AND ERROR BUDGETS
================================================================================

SRO/SLO Concepts Review:

  SLI (Service Level Indicator): A metric measuring service health.
    Example: HTTP request success rate = (2xx responses) / (total requests)
  
  SLO (Service Level Objective): Target for an SLI.
    Example: 99.9% success rate (allows 43.8 min/month downtime)
  
  Error Budget = 100% - SLO = the allowed failure margin.
    99.9% SLO → 0.1% error budget → 43.8 min/month allowed downtime.

Chaos Engineering and Error Budgets:

  Chaos experiments CONSUME error budget (if they cause failures).
  This is intentional and the system's ability to recover determines
  whether you're within budget.
  
  Decision rules (from Google SRE book):
  ✓ If error budget is HEALTHY (> 50% remaining): Run chaos experiments
    actively, try to find weaknesses.
  ✓ If error budget is LOW (< 20% remaining): STOP chaos experiments,
    focus on reliability improvements.
  ✗ If error budget is EXHAUSTED: No new features, no chaos experiments,
    only reliability work until budget refills.

Chaos Experiment as SLO Validation:

  Hypothesis:
    "Our order-service maintains 99.9% success rate even when 50% of pods
    are deleted."
  
  Experiment:
    LitmusChaos pod-delete, 50% of pods, 5-minute duration.
    Prometheus probe monitors error rate continuously.
  
  Result A (Pass):
    Error rate stayed < 0.1%. Circuit breakers, retries, and K8s pod restart
    maintained SLO. We have evidence our SLO is achievable.
  
  Result B (Fail):
    Error rate spiked to 15%. Consumed 15× expected error budget in 5 minutes.
    Found weakness: no circuit breaker between frontend and order-service.
    Action: Add Resilience4j circuit breaker, re-run experiment.

Automated Chaos in CI/CD Pipeline:

  # Example: Run chaos experiment as part of staging pipeline:
  
  stages:
    - name: Deploy to Staging
    - name: Integration Tests
    - name: Chaos Experiment (automatic)  # After integration tests
    - name: Validate Steady State (after chaos)
    - name: Manual Approval for Prod
  
  # Chaos experiment step:
  - name: Run Chaos Experiment
    run: |
      kubectl apply -f chaos/pod-delete-staging.yaml
      sleep 120   # Wait for experiment to complete
      
      # Check chaos result:
      VERDICT=$(kubectl get chaosresult order-service-pod-delete \
        -n staging -o jsonpath='{.status.experimentStatus.verdict}')
      
      if [ "$VERDICT" != "Pass" ]; then
        echo "Chaos experiment failed! System is not resilient."
        exit 1
      fi

11. JAVA APPLICATION RESILIENCY PATTERNS (PRE-CHAOS)
================================================================================

Build These Before Running Chaos (Reduce the Blast Radius):

Pattern 1: Resilience4j (Circuit Breaker, Retry, Bulkhead):

  @Service
  public class PaymentClient {
    
    @CircuitBreaker(name = "payment-service", fallbackMethod = "paymentFallback")
    @Retry(name = "payment-service")
    @TimeLimiter(name = "payment-service")
    public CompletableFuture<PaymentResult> processPayment(PaymentRequest request) {
        return CompletableFuture.supplyAsync(() ->
            restTemplate.postForObject("/api/payments", request, PaymentResult.class)
        );
    }
    
    // Fallback: return PENDING status, retry asynchronously
    public CompletableFuture<PaymentResult> paymentFallback(
            PaymentRequest request, Exception ex) {
        log.warn("Payment service unavailable, queuing request: {}", ex.getMessage());
        eventPublisher.publishEvent(new PaymentRetryEvent(request));
        return CompletableFuture.completedFuture(PaymentResult.PENDING);
    }
  }

Pattern 2: Pod Disruption Budget:

  apiVersion: policy/v1
  kind: PodDisruptionBudget
  metadata:
    name: order-service-pdb
  spec:
    minAvailable: 2              # At least 2 pods survive disruption
    selector:
      matchLabels:
        app: order-service

Pattern 3: Graceful Shutdown:

  # application.yml:
  server:
    shutdown: graceful          # Wait for in-flight requests to complete
  spring:
    lifecycle:
      timeout-per-shutdown-phase: 30s   # Up to 30s for requests to complete

Pattern 4: Readiness Probe (Don't Route to Unhealthy Pods):

  livenessProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    initialDelaySeconds: 30     # Wait for JVM startup
    periodSeconds: 10
  
  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    initialDelaySeconds: 10
    periodSeconds: 5

What Chaos Experiments Validate:

  Circuit breaker: Kill downstream service → verify circuit opens
  Retry: Add latency → verify retry doesn't amplify load (exponential backoff)
  Bulkhead: Flood one endpoint → verify other endpoints unaffected
  Graceful shutdown: Delete pod → verify in-flight requests complete
  PDB: Node drain → verify minAvailable pods always running

12. CHAOS ENGINEERING WORKFLOW (STEP-BY-STEP)
================================================================================

Phase 1: Build Resilience First (Don't Chaos Without These):

  ☐ Multiple replicas (minReplicas >= 2 for stateless services)
  ☐ Liveness and readiness probes configured
  ☐ PodDisruptionBudget for production deployments
  ☐ Circuit breakers (Resilience4j) for downstream calls
  ☐ Retry with exponential backoff
  ☐ Timeouts on ALL external calls (HTTP, DB, Redis)
  ☐ Graceful shutdown (server.shutdown=graceful)
  ☐ Monitoring and alerting (Prometheus + Grafana dashboards)

Phase 2: Start with Controlled Environments:

  1. Unit-level chaos: Spring Boot Chaos Monkey in dev environment
     → Validate individual service behavior
  
  2. Service-level chaos in staging: LitmusChaos pod-delete
     → Validate K8s self-healing and inter-service resilience
  
  3. Infrastructure chaos in staging: Node drain, network latency
     → Validate cluster-level resilience
  
  4. Partial production chaos: 1 pod delete, minimal blast radius
     → Validate everything at real-world scale

Phase 3: Automate and Repeat:

  Add chaos experiments to your staging CI/CD pipeline.
  Run weekly GameDays for infrastructure-level chaos.
  Track: "Our chaos score" → number of experiments passing / total.
  Target: All common failure modes have passing chaos experiments.

13. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is chaos engineering and why would a Java developer care about it?

A: Chaos engineering is the practice of intentionally injecting failures
   into a system to discover weaknesses before they cause unplanned outages.
   
   For Java developers, it matters because:
   
   1. JVM has unique failure modes that only appear under specific conditions:
      - Full GC pauses causing cascading timeouts across services
      - OOMKilled pods causing connection pool exhaustion upstream
      - Thread pool starvation when one downstream service slows down
   
   2. Spring Boot applications need validation of resilience patterns:
      - Does my @CircuitBreaker actually open when the downstream fails?
      - Does graceful shutdown really wait for in-flight requests?
      - Does my readiness probe prevent traffic during startup?
   
   3. Senior developers are expected to design for failure, not just for
      the happy path. Chaos engineering is how you PROVE resilience works.
   
   Practical example:
   We deployed Resilience4j circuit breakers everywhere. Our chaos experiment
   (kill payment service pod) showed the circuit breaker was opening... but
   then immediately retrying because the retry annotation was outside the
   circuit breaker in the annotation order. The experiment caught a bug in
   our resilience configuration that would have caused cascading failures
   in production.

Q2: How does LitmusChaos work and how would you integrate it into a CI/CD pipeline?

A: LitmusChaos runs as a Kubernetes operator. You define ChaosEngine CRDs
   that specify:
   - Target: which Deployment/pod to attack
   - Experiment: what type of failure (pod-delete, network-latency, etc.)
   - Probes: HTTP/Prometheus checks to validate steady state DURING chaos
   
   Integration into CI/CD (staging environment):
   
   1. After integration tests pass:
      kubectl apply -f chaos/pod-delete-staging.yaml
      # This creates a ChaosEngine that:
      # - Deletes 30% of order-service pods every 10 seconds for 2 minutes
      # - Probes the order-service health endpoint every 5 seconds
      # - Checks Prometheus error rate < 5% continuously
   
   2. Wait for experiment completion (kubectl wait)
   
   3. Read ChaosResult:
      VERDICT=$(kubectl get chaosresult -n staging -o jsonpath='{...verdict}')
      if [ "$VERDICT" != "Pass" ]; then exit 1; fi
   
   4. If experiment fails (verdict = Fail):
      - Pipeline stops → staging deploy is NOT promoted to prod
      - Team investigates: why did health probe fail during pod deletion?
      - Fix (e.g., add circuit breaker, increase replicas) → re-run
   
   This creates a continuous resilience validation loop:
   Every deploy to staging PROVES the service survives pod failures.
   Only resilient services get promoted to production.
