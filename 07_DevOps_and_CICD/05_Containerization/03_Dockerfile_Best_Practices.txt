1. DOCKERFILE INSTRUCTION REFERENCE
================================================================================

Instruction Summary:

  FROM        — Base image (every Dockerfile starts here)
  LABEL       — Metadata (key=value pairs)
  RUN         — Execute command during build (creates new layer)
  COPY        — Copy files from build context into image
  ADD         — Like COPY but can extract archives and fetch URLs
  WORKDIR     — Set working directory (creates if doesn't exist)
  ENV         — Set environment variable (persists at runtime)
  ARG         — Build-time variable (NOT available at runtime)
  EXPOSE      — Documents what port the container listens on
  USER        — Set user for subsequent instructions and container runtime
  VOLUME      — Creates a mount point
  CMD         — Default command/arguments when container starts
  ENTRYPOINT  — Fixed executable when container starts
  HEALTHCHECK — How Docker tests if container is healthy
  SHELL       — Override default shell for RUN/CMD/ENTRYPOINT

FROM:
  FROM ubuntu:22.04                     # Use full Ubuntu image
  FROM python:3.11-slim                 # Slim Python image
  FROM alpine:3.18                      # Minimal Alpine image
  FROM scratch                          # Empty base (for static binaries)
  FROM node:18-alpine AS builder        # Named stage for multi-stage builds
  
  Best practices:
  - Always pin to a specific version tag (ubuntu:22.04 not ubuntu:latest)
  - Prefer minimal images (slim, alpine, distroless)
  - Use official images when available
  - Specify the exact digest for maximum reproducibility:
    FROM ubuntu@sha256:abc123...

LABEL:
  LABEL maintainer="team@example.com"
  LABEL version="1.2.3"
  LABEL description="My application"
  
  # OCI standard labels:
  LABEL org.opencontainers.image.source="https://github.com/owner/repo"
  LABEL org.opencontainers.image.revision="$GIT_COMMIT"
  LABEL org.opencontainers.image.version="1.2.3"

RUN:
  # Shell form (runs as /bin/sh -c "command")
  RUN apt-get update && apt-get install -y curl
  
  # Exec form (no shell, direct exec)
  RUN ["apt-get", "install", "-y", "curl"]
  
  # Multi-line RUN (single layer, no intermediate layers)
  RUN apt-get update \
      && apt-get install -y \
         curl \
         git \
         wget \
      && rm -rf /var/lib/apt/lists/*   # Clean up APT cache to reduce image size
  
  # NEVER:
  RUN apt-get update          # Creates layer
  RUN apt-get install -y curl # Can use stale cache from previous layer!
  
  # ALWAYS combine update + install in single RUN:
  RUN apt-get update && apt-get install -y curl

COPY vs ADD:
  COPY — Simple file copy from build context
  ADD  — Like COPY plus:
           - Can extract .tar archives
           - Can fetch URLs (not recommended — no caching, security risk)
  
  # COPY: Preferred for simple file copies
  COPY app.py /app/app.py
  COPY requirements.txt /app/requirements.txt
  COPY ./config/ /app/config/
  
  # ADD: Only use for tar extraction
  ADD app.tar.gz /app/           # Extracts archive
  
  # Never use ADD for URLs; use RUN curl instead:
  # BAD:
  ADD https://example.com/big_file.tar.gz /tmp/
  # GOOD:
  RUN curl -L https://example.com/big_file.tar.gz -o /tmp/big_file.tar.gz \
      && tar -xzf /tmp/big_file.tar.gz -C /app/ \
      && rm /tmp/big_file.tar.gz
  
  # COPY with ownership:
  COPY --chown=appuser:appgroup config.json /app/config.json

WORKDIR:
  WORKDIR /app                          # Set working directory
  # Creates directory if it doesn't exist
  # All subsequent RUN, COPY, CMD, ENTRYPOINT use this as CWD
  # Prefer WORKDIR over: RUN mkdir /app && cd /app
  
  # Multiple WORKDIR (they stack):
  WORKDIR /app
  WORKDIR src              # Now at /app/src
  WORKDIR ..               # Now back at /app

ENV vs ARG:
  ENV — Runtime environment variable (baked into image, available at runtime)
  ARG — Build-time variable (NOT baked into image, NOT available at runtime)
  
  ARG APP_VERSION=1.0.0           # Build arg with default
  ENV APP_VERSION=$APP_VERSION    # Promote ARG to ENV if needed at runtime
  
  # Pass ARG at build time:
  docker build --build-arg APP_VERSION=2.0.0 .
  
  # ENV persists in image (visible in docker inspect)
  ENV DATABASE_URL=postgresql://localhost/app  # WARNING: visible to anyone
  
  # NEVER put secrets in ENV or ARG in Dockerfiles
  # Secrets should come from docker run -e, Kubernetes Secrets, etc.

EXPOSE:
  EXPOSE 8080            # Document that container listens on 8080 (TCP)
  EXPOSE 8080/tcp        # Explicit TCP
  EXPOSE 5353/udp        # UDP port
  
  EXPOSE does NOT publish the port. It's documentation only.
  Actual publishing: docker run -p 8080:8080 myimage

USER:
  # Create non-root user and switch to it
  RUN groupadd -r appgroup && useradd -r -g appgroup appuser
  USER appuser
  
  # Alpine:
  RUN addgroup -S appgroup && adduser -S appuser -G appgroup
  USER appuser
  
  # Using UID:GID directly:
  USER 1001:1001

HEALTHCHECK:
  HEALTHCHECK --interval=30s --timeout=10s --retries=3 --start-period=5s \
    CMD curl -f http://localhost:8080/health || exit 1
  
  HEALTHCHECK --interval=30s --timeout=3s \
    CMD wget --quiet --tries=1 --spider http://localhost:8080/health || exit 1
  
  HEALTHCHECK NONE    # Disable inherited healthcheck
  
  States: starting → healthy / unhealthy

VOLUME:
  VOLUME /app/data       # Create mount point
  VOLUME ["/app/data", "/app/logs"]  # Multiple volumes
  
  Creates anonymous volume if user doesn't mount anything.
  Files in this path persist even if container is deleted.
  Prefer explicit volume mounts in docker run over VOLUME instruction.

2. LAYER CACHING OPTIMIZATION
================================================================================

The Golden Rule:
  ORDER INSTRUCTIONS FROM LEAST TO MOST LIKELY TO CHANGE.
  A cache miss on any layer invalidates ALL subsequent layers.

Python App — Optimized Order:
  
  # BAD: Every code change invalidates pip install
  FROM python:3.11-slim
  WORKDIR /app
  COPY . .                              # Copy everything (changes often)
  RUN pip install -r requirements.txt  # CACHE MISS every code change!
  CMD ["python", "app.py"]
  
  # GOOD: Copy requirements first, install, then copy code
  FROM python:3.11-slim
  WORKDIR /app
  COPY requirements.txt .               # Rarely changes
  RUN pip install -r requirements.txt  # Cached unless requirements change
  COPY . .                             # Changes often, but pip cache preserved
  CMD ["python", "app.py"]

Node.js App — Optimized Order:
  
  # BAD:
  COPY . .
  RUN npm ci
  
  # GOOD:
  COPY package.json package-lock.json ./
  RUN npm ci --only=production         # Cached unless package*.json changes
  COPY . .

Java/Maven App — Optimized Order:
  
  # GOOD: Cache maven dependencies
  COPY pom.xml .
  RUN mvn dependency:go-offline -B     # Download all deps (can cache!)
  COPY src ./src
  RUN mvn package -DskipTests

Go App — Optimized Order:
  
  COPY go.mod go.sum ./
  RUN go mod download                  # Cached unless go.mod/go.sum changes
  COPY . .
  RUN go build -o app .

RUN Layer Optimization:
  
  # BAD: Multiple RUN = multiple layers = larger image
  RUN apt-get update
  RUN apt-get install -y curl
  RUN apt-get install -y wget
  RUN rm -rf /var/lib/apt/lists/*       # This layer doesn't reduce size of above!
  
  # GOOD: Single RUN with cleanup
  RUN apt-get update \
      && apt-get install -y --no-install-recommends \
         curl \
         wget \
      && rm -rf /var/lib/apt/lists/*    # Cleanup in SAME layer reduces size
  
  # For pip:
  RUN pip install --no-cache-dir -r requirements.txt  # --no-cache-dir saves space
  
  # For apt: --no-install-recommends avoids installing extra packages
  RUN apt-get install -y --no-install-recommends curl

3. MULTI-STAGE BUILDS
================================================================================

Concept:
  Multi-stage builds use multiple FROM statements.
  Each FROM starts a new stage. You can COPY artifacts between stages.
  Final image only contains what you explicitly COPY to the last stage.
  
  Result: Build tools, compilers, test frameworks don't end up in production image.

Go App — Multi-Stage:
  
  # Stage 1: Build
  FROM golang:1.21 AS builder
  WORKDIR /build
  COPY go.mod go.sum ./
  RUN go mod download
  COPY . .
  RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server .
  
  # Stage 2: Production
  FROM alpine:3.18
  RUN apk add --no-cache ca-certificates tzdata
  COPY --from=builder /app/server /usr/local/bin/server
  USER 1001:1001
  EXPOSE 8080
  CMD ["/usr/local/bin/server"]
  
  # Builder image: ~1GB (golang toolchain)
  # Final image: ~20MB (just Alpine + binary)

Node.js App — Multi-Stage:
  
  # Stage 1: Install all dependencies (including dev)
  FROM node:18-alpine AS deps
  WORKDIR /app
  COPY package*.json ./
  RUN npm ci
  
  # Stage 2: Build (compile TypeScript, bundle, etc.)
  FROM node:18-alpine AS builder
  WORKDIR /app
  COPY --from=deps /app/node_modules ./node_modules
  COPY . .
  RUN npm run build
  
  # Stage 3: Production
  FROM node:18-alpine AS production
  WORKDIR /app
  ENV NODE_ENV=production
  COPY package*.json ./
  RUN npm ci --only=production && npm cache clean --force
  COPY --from=builder /app/dist ./dist
  USER node
  EXPOSE 3000
  CMD ["node", "dist/index.js"]

Java/Maven App — Multi-Stage:
  
  # Stage 1: Build with Maven
  FROM maven:3.9-eclipse-temurin-17 AS build
  WORKDIR /app
  COPY pom.xml .
  RUN mvn dependency:go-offline -B
  COPY src ./src
  RUN mvn package -DskipTests
  
  # Stage 2: Production JRE (much smaller than JDK)
  FROM eclipse-temurin:17-jre-alpine
  WORKDIR /app
  COPY --from=build /app/target/*.jar app.jar
  USER 1001
  EXPOSE 8080
  ENTRYPOINT ["java", "-jar", "app.jar"]

Python App — Multi-Stage:
  
  # Stage 1: Build dependencies
  FROM python:3.11-slim AS builder
  WORKDIR /app
  RUN pip install build
  COPY pyproject.toml setup.cfg ./
  COPY src ./src
  RUN pip install --prefix=/install .
  
  # Stage 2: Production
  FROM python:3.11-slim
  WORKDIR /app
  COPY --from=builder /install /usr/local
  COPY --from=builder /app/src ./src
  RUN useradd --system --create-home appuser
  USER appuser
  CMD ["python", "-m", "myapp"]

Target a Specific Stage:
  # Build only up to specific stage (useful for CI testing)
  docker build --target builder -t myapp:builder .
  docker build --target production -t myapp:prod .

4. MINIMAL BASE IMAGES
================================================================================

Image Size Hierarchy (Python example):
  python:3.11          ~900MB  (full Debian + development tools)
  python:3.11-slim     ~150MB  (Debian slim, minimal packages)
  python:3.11-alpine   ~50MB   (Alpine Linux)
  gcr.io/distroless/python3  ~30MB (no shell, no package manager)
  
  Size isn't just about storage — faster pulls, smaller attack surface

Image Choices:

  DEBIAN/UBUNTU BASED (python:3.11, ubuntu:22.04):
  - Full OS. Most compatible.
  - Largest size.
  - Use when: Package compatibility is critical.
  
  SLIM (python:3.11-slim, node:18-slim):
  - Reduced Debian base. Common utilities removed.
  - Good balance of compatibility and size.
  - Use when: Some system packages needed, want reasonable size.
  
  ALPINE (python:3.11-alpine, nginx:alpine):
  - musl libc instead of glibc. BusyBox instead of GNU utils.
  - Very small (~5MB base).
  - WARNING: Some Python packages (with C extensions) may not work.
  - Use when: Familiarity with Alpine differences, size is priority.
  
  DISTROLESS (gcr.io/distroless/*):
  - No shell, no package manager, no OS utilities.
  - Just the runtime (JRE, Python interpreter, etc.) + app.
  - Smallest attack surface — can't exec into container!
  - Use when: High security requirements, production-only images.
  
  SCRATCH:
  - Completely empty. No OS.
  - Use only for static binaries (Go, Rust with static linking).
  - FROM scratch
    COPY myapp /myapp
    CMD ["/myapp"]
  
  For debugging distroless:
  # Use debug variant that includes busybox shell
  FROM gcr.io/distroless/python3-debian11:debug

Distroless Examples:
  
  # Java
  FROM eclipse-temurin:17-jre AS builder
  FROM gcr.io/distroless/java17-debian11
  COPY --from=builder /app/target/app.jar /app.jar
  CMD ["java", "-jar", "/app.jar"]
  
  # Go static binary
  FROM golang:1.21 AS builder
  RUN CGO_ENABLED=0 go build -o /app main.go
  
  FROM scratch
  COPY --from=builder /app /app
  COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
  USER 1001:1001
  ENTRYPOINT ["/app"]

5. SECURITY BEST PRACTICES
================================================================================

1. Run as Non-Root User:
  
  # WORST: Running as root (default if USER not set)
  
  # BETTER: Add dedicated user
  FROM ubuntu:22.04
  RUN groupadd -r appgroup --gid=1001 \
      && useradd -r -g appgroup --uid=1001 --home=/app --shell=/sbin/nologin appuser
  WORKDIR /app
  COPY --chown=appuser:appgroup . .
  USER appuser
  
  # Alpine:
  RUN addgroup -S -g 1001 appgroup \
      && adduser -S -u 1001 -G appgroup -H -s /sbin/nologin appuser
  USER appuser

2. Never Store Secrets in Dockerfile:
  
  # NEVER in Dockerfile:
  ENV DATABASE_PASSWORD=supersecret    # Visible in docker inspect, docker history
  ARG API_KEY=supersecret             # Also visible in docker history!
  
  # Correct approach: Pass at runtime
  docker run -e DATABASE_PASSWORD=$DB_PASS myapp
  
  # Or use Docker secrets (Swarm) / Kubernetes Secrets
  
  # Or BuildKit secrets for build-time secrets (not embedded in layers):
  # syntax=docker/dockerfile:1
  FROM python:3.11-slim
  RUN --mount=type=secret,id=pip_conf,target=/etc/pip.conf \
      pip install --no-cache-dir -r requirements.txt

3. Scan Images for Vulnerabilities:
  
  # Trivy (open source, comprehensive)
  trivy image myapp:v1.2.3
  trivy image --severity CRITICAL,HIGH myapp:v1.2.3
  trivy image --exit-code 1 --severity CRITICAL myapp:v1.2.3  # Fail CI on critical
  
  # Snyk
  snyk container test myapp:v1.2.3
  
  # In CI/CD pipeline:
  - name: Scan image
    uses: aquasecurity/trivy-action@master
    with:
      image-ref: 'myapp:${{ github.sha }}'
      format: 'sarif'
      output: 'trivy-results.sarif'
      severity: 'CRITICAL,HIGH'
      exit-code: '1'

4. Minimize Attack Surface:
  
  # Use --no-install-recommends to avoid extra packages
  RUN apt-get install -y --no-install-recommends \
      ca-certificates \
      && rm -rf /var/lib/apt/lists/*
  
  # Remove build tools after use (or better: use multi-stage builds)
  RUN apt-get install -y build-essential \
      && make myapp \
      && apt-get remove -y build-essential \
      && apt-get autoremove -y \
      && rm -rf /var/lib/apt/lists/*
  
  # Use distroless for production

5. Read-Only Filesystem:
  
  # In Kubernetes:
  securityContext:
    readOnlyRootFilesystem: true
  
  # In docker run:
  docker run --read-only --tmpfs /tmp myapp

6. Use COPY not ADD:
  COPY is explicit. ADD has hidden behaviors (URL fetch, archive extraction).
  Prefer COPY unless you specifically need ADD's features.

6. IMAGE SIZE REDUCTION
================================================================================

Strategies:

  1. Use minimal base image (see section 4)
  
  2. Multi-stage builds (see section 3) — biggest impact
  
  3. Clean up in the same RUN layer:
     RUN apt-get update && apt-get install -y curl \
         && rm -rf /var/lib/apt/lists/*    # Must be in same RUN!
  
  4. Use --no-install-recommends:
     RUN apt-get install -y --no-install-recommends curl
  
  5. pip: use --no-cache-dir:
     RUN pip install --no-cache-dir -r requirements.txt
  
  6. npm: use ci and clean cache:
     RUN npm ci && npm cache clean --force
  
  7. Remove unnecessary files:
     RUN make install \
         && find / -name "*.pyc" -delete \
         && find / -name "__pycache__" -type d -exec rm -rf {} + \
         2>/dev/null || true
  
  8. Use .dockerignore (see section 7)
  
  9. Use docker-slim or crane to analyze image content:
     docker run --rm -it dslim/docker-slim build myapp:latest

Analyzing Image Size:
  # View layer sizes
  docker history myapp:v1
  
  # Dive tool — interactive layer explorer
  dive myapp:v1
  
  # Show image size
  docker images myapp

7. .DOCKERIGNORE
================================================================================

Purpose:
  Defines what to EXCLUDE from the build context sent to Docker daemon.
  
  Benefits:
  - Faster builds (less data to send to daemon)
  - Smaller images (accidentally copied files)
  - Security (prevents secrets/credentials from entering image)
  - Better caching (changes to excluded files don't invalidate cache)

Standard .dockerignore file:
  
  # VCS
  .git
  .gitignore
  .gitattributes
  
  # Documentation
  README.md
  docs/
  *.md
  
  # Development environment
  .env
  .env.*
  .vscode/
  .idea/
  *.swp
  *.swo
  .DS_Store
  
  # Dependencies (managed in container)
  node_modules/
  __pycache__/
  *.pyc
  .pytest_cache/
  .mypy_cache/
  venv/
  .venv/
  
  # Build artifacts
  dist/
  build/
  target/
  *.egg-info/
  
  # Test files
  tests/
  test/
  *_test.go
  *.test.js
  
  # Logs and temporary files
  logs/
  *.log
  tmp/
  temp/
  
  # Docker files themselves
  Dockerfile
  Dockerfile.*
  docker-compose*.yml
  
  # CI/CD
  .github/
  .gitlab-ci.yml
  Jenkinsfile

Important Notes:
  .dockerignore uses the same syntax as .gitignore.
  Must be in the same directory as Dockerfile.
  Wildcard (*) matches any string. ** matches any path.
  Use ! prefix to re-include something from an excluded pattern:
  
  *           # Exclude everything
  !src/       # But include src/
  !package.json
  !requirements.txt

8. ENTRYPOINT vs CMD — DEEP DIVE
================================================================================

Two Forms of Each:
  
  SHELL FORM (uses /bin/sh -c internally):
  CMD python app.py
  ENTRYPOINT python app.py
  
  EXEC FORM (direct exec, no shell):
  CMD ["python", "app.py"]
  ENTRYPOINT ["python", "app.py"]
  
  ALWAYS prefer exec form for CMD and ENTRYPOINT:
  - Shell form wraps in: /bin/sh -c "python app.py"
  - PID 1 is /bin/sh, not your app
  - Signals (SIGTERM) may not reach your app
  - With exec form, your app IS PID 1 and receives signals directly

Overriding Behavior:
  
  Case 1: Only CMD defined
  CMD ["python", "app.py"]
  
  docker run myimage                    → runs: python app.py
  docker run myimage python other.py   → runs: python other.py  (CMD overridden)
  docker run myimage bash               → runs: bash
  
  Case 2: Only ENTRYPOINT defined
  ENTRYPOINT ["python", "app.py"]
  
  docker run myimage                    → runs: python app.py
  docker run myimage --debug            → runs: python app.py --debug  (args appended)
  docker run --entrypoint /bin/bash myimage  → runs: /bin/bash  (ENTRYPOINT overridden)
  
  Case 3: Both ENTRYPOINT and CMD (recommended for flexible containers):
  ENTRYPOINT ["python", "app.py"]
  CMD ["--port", "8080"]                 # Default arguments
  
  docker run myimage                    → runs: python app.py --port 8080
  docker run myimage --port 9090       → runs: python app.py --port 9090
  docker run --entrypoint /bin/bash myimage  → runs: /bin/bash
  
  Case 4: ENTRYPOINT as wrapper script:
  ENTRYPOINT ["docker-entrypoint.sh"]   # Wrapper script for init tasks
  CMD ["postgres"]                      # Default command passed to script

Signal Handling Best Practice:
  
  # Problem: PID 1 doesn't receive signals properly by default
  # Use exec form or tini as init process:
  
  FROM node:18-alpine
  # Alpine includes tini (init process)
  ENTRYPOINT ["/sbin/tini", "--"]
  CMD ["node", "server.js"]
  
  # Or use exec to replace shell with app:
  #!/bin/bash
  # docker-entrypoint.sh
  exec "$@"           # exec replaces shell with CMD, PID 1 becomes your app

9. BUILD ARGUMENTS vs ENVIRONMENT VARIABLES
================================================================================

ARG — Build Time Only:
  
  # In Dockerfile:
  ARG APP_VERSION=1.0.0               # Default value
  ARG BUILD_ENV
  
  # Usage in Dockerfile:
  RUN echo "Building version $APP_VERSION"
  LABEL version="$APP_VERSION"
  
  # Override at build time:
  docker build --build-arg APP_VERSION=2.0.0 .
  docker build --build-arg BUILD_ENV=production .
  
  # ARG is NOT available after FROM (in next stage), NOT in running container
  # ARG is visible in docker history (don't use for secrets!)

ENV — Runtime Environment:
  
  # Set environment variable (persists in image)
  ENV NODE_ENV=production
  ENV PORT=3000 \
      HOST=0.0.0.0 \
      LOG_LEVEL=info
  
  # Available in container runtime:
  docker run myapp         # NODE_ENV=production, PORT=3000
  docker run -e PORT=8080 myapp  # Override at runtime
  
  # ENV values show up in docker inspect — DON'T store secrets here

Combining ARG and ENV:
  
  # Pattern: Use ARG for build-time config, promote to ENV for runtime
  ARG APP_ENV=production
  ENV APP_ENV=${APP_ENV}
  
  # This allows:
  docker build --build-arg APP_ENV=staging .  # Different environments

Cache Busting with ARG:
  
  # Problem: Docker caches RUN apt-get update
  # Solution: Use --build-arg to break cache
  ARG CACHE_BUST=1
  RUN apt-get update && apt-get upgrade -y
  
  # docker build --build-arg CACHE_BUST=$(date +%s) .  ← Forces cache miss

10. COMPLETE PRODUCTION-READY DOCKERFILE EXAMPLES
================================================================================

Python FastAPI Application:
  
  # syntax=docker/dockerfile:1
  FROM python:3.11-slim AS builder
  
  WORKDIR /app
  
  # Install system dependencies for building Python packages
  RUN apt-get update \
      && apt-get install -y --no-install-recommends \
         build-essential \
         gcc \
      && rm -rf /var/lib/apt/lists/*
  
  # Copy and install dependencies first (caching optimization)
  COPY requirements.txt ./
  RUN pip install --no-cache-dir --prefix=/install -r requirements.txt
  
  # Production stage
  FROM python:3.11-slim
  
  WORKDIR /app
  
  # Runtime system dependencies only
  RUN apt-get update \
      && apt-get install -y --no-install-recommends \
         libpq5 \
      && rm -rf /var/lib/apt/lists/* \
      && groupadd -r appgroup --gid=1001 \
      && useradd -r -g appgroup --uid=1001 --home=/app --shell=/sbin/nologin appuser
  
  # Copy installed packages from builder
  COPY --from=builder /install /usr/local
  
  # Copy application code
  COPY --chown=appuser:appgroup ./src ./src
  
  USER appuser
  
  EXPOSE 8000
  
  HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
  
  ENTRYPOINT ["python", "-m", "uvicorn"]
  CMD ["src.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]

Node.js Express Application:
  
  # syntax=docker/dockerfile:1
  
  # Install all dependencies
  FROM node:18-alpine AS deps
  WORKDIR /app
  COPY package.json package-lock.json ./
  RUN npm ci
  
  # Build TypeScript
  FROM node:18-alpine AS build
  WORKDIR /app
  COPY --from=deps /app/node_modules ./node_modules
  COPY . .
  RUN npm run build && npm run test
  
  # Production image
  FROM node:18-alpine AS production
  
  WORKDIR /app
  ENV NODE_ENV=production
  
  COPY package.json package-lock.json ./
  RUN npm ci --only=production \
      && npm cache clean --force
  
  COPY --from=build /app/dist ./dist
  
  USER node
  EXPOSE 3000
  
  HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD wget -qO- http://localhost:3000/health || exit 1
  
  CMD ["node", "dist/index.js"]

Go Static Binary:
  
  # syntax=docker/dockerfile:1
  
  FROM golang:1.21-alpine AS builder
  
  WORKDIR /build
  
  # Install dependencies
  COPY go.mod go.sum ./
  RUN go mod download
  
  # Build static binary
  COPY . .
  RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
      go build -ldflags="-w -s" -o /app/server ./cmd/server
  
  # Production: use scratch (empty) or distroless
  FROM gcr.io/distroless/static-debian11
  
  COPY --from=builder /app/server /server
  
  USER 1001:1001
  EXPOSE 8080
  ENTRYPOINT ["/server"]

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between COPY and ADD in a Dockerfile?
A: Both copy files from the build context into the image. ADD has two extra
   features: it can extract tar archives automatically and fetch from URLs.
   
   However, best practice is to ALWAYS use COPY unless you specifically need
   archive extraction. Reasons:
   - COPY is explicit — what you see is what you get
   - ADD with URLs has no caching and is a security risk
   - ADD with URLs can fail silently or fetch different content over time
   - If you need archive extraction, ADD is fine (e.g., ADD app.tar.gz /app/)
   - If you need URL fetching, use RUN curl -O instead for proper error handling
   
   Rule of thumb: Use COPY by default. Use ADD only for tar extraction.

Q2: How do multi-stage builds help reduce image size and improve security?
A: Multi-stage builds allow you to use multiple FROM statements. Each FROM
   starts a fresh stage. You COPY artifacts between stages. The final image
   only contains what you explicitly copy in the last stage.
   
   Benefits:
   1. SIZE: Build tools (compilers, SDKs, test frameworks) stay in builder stages
      and don't end up in the final image. A Go app might go from 1GB (with
      toolchain) to 20MB (just the binary).
   
   2. SECURITY: Fewer packages = smaller attack surface. No build tools = fewer
      vulnerabilities. Distroless final images have no shell, no package manager.
   
   3. CLEAN SEPARATION: Dev, test, and production concerns in one file.
   
   4. FASTER CI: Final image is smaller, so pulling and pushing is faster.
   
   Example: Java Spring Boot without multi-stage might use eclipse-temurin:17
   (full JDK, ~600MB). With multi-stage, use JDK in builder but JRE
   (eclipse-temurin:17-jre-alpine, ~100MB) in production stage.

Q3: How do you optimize Dockerfile layer caching?
A: The key insight is: Docker caches layers. A cache miss invalidates all
   subsequent layers. So you want the MOST STABLE instructions first, and
   MOST FREQUENTLY CHANGING instructions last.
   
   Best practice order for typical apps:
   1. Base image (rarely changes)
   2. System package installation (rarely changes)
   3. Copy ONLY the dependency manifest (package.json, requirements.txt)
   4. Install dependencies (changes only when manifest changes)
   5. Copy the actual application code (changes with every commit)
   6. Build the application
   
   The critical mistake to avoid:
   COPY . .               ← Changes every commit
   RUN pip install        ← Cache miss every commit!
   
   vs correct:
   COPY requirements.txt .  ← Only changes when dependencies change
   RUN pip install          ← Cached unless requirements.txt changes
   COPY . .                 ← Changes every commit, but deps are cached

Q4: Why should Docker containers run as non-root?
A: If a process in a container is compromised, running as root in the container
   can have several bad consequences:
   
   1. CONTAINER ESCAPE: If there's a container escape vulnerability, root in
      the container could become root on the host.
   
   2. FILE SYSTEM: A root process can read/write any file mounted from the host.
   
   3. PRIVILEGE ESCALATION: Root processes can install software, change
      configurations, and modify other running processes.
   
   4. COMPLIANCE: Many security standards (CIS Benchmarks, PCI-DSS) require
      non-root containers.
   
   Implementation:
   - Create a dedicated user: RUN useradd -r appuser
   - Switch to it: USER appuser
   - Kubernetes PodSecurityContext: runAsNonRoot: true, runAsUser: 1001
   - Run at runtime: docker run --user 1001:1001 myimage

Q5: What should never go into a Docker image?
A: Several categories of things should never be in Docker images:
   
   1. SECRETS AND CREDENTIALS:
      - Passwords, API keys, tokens
      - .env files, credential files
      - SSH private keys (even temporarily — docker history exposes all layers)
      - Use docker run -e, Kubernetes Secrets, or BuildKit --mount=type=secret
   
   2. DEVELOPMENT ARTIFACTS:
      - node_modules (should be installed from package.json)
      - .git directory (reveals commit history)
      - .vscode, .idea (IDE files)
   
   3. UNNECESSARY BUILD TOOLS:
      - Compilers, build dependencies (use multi-stage builds)
      - Test frameworks and test files
   
   4. LARGE UNNECESSARY FILES:
      - Documentation (README.md, docs/)
      - Log files
      - Temporary files
   
   Solution: Use .dockerignore to exclude these from the build context, and
   use multi-stage builds to avoid including build tools in the final image.

12. QUICK REFERENCE CHEAT SHEET
================================================================================

DOCKERFILE INSTRUCTIONS:
  FROM <image>:<tag>             Base image (pin to specific tag!)
  WORKDIR /app                  Set working directory
  COPY [--chown=user] src dst   Copy files (prefer over ADD)
  RUN cmd && cmd                Execute during build (combine for less layers)
  ENV KEY=value                  Runtime environment variable
  ARG KEY=default                Build-time variable (not in final image)
  EXPOSE 8080                    Document port (doesn't publish)
  USER uid:gid                   Run as non-root
  HEALTHCHECK CMD ...            Container health check
  ENTRYPOINT ["exe", "arg"]      Fixed executable (exec form)
  CMD ["arg1", "arg2"]           Default args (exec form, overridable)
  LABEL key=value                Image metadata

LAYER CACHING ORDER:
  1. Base image
  2. System packages (apt/apk)
  3. Dependency manifest (package.json, requirements.txt, go.mod)
  4. Install dependencies
  5. Copy application code
  6. Build

MULTI-STAGE BUILDS:
  FROM image AS builder   # Stage 1: Build
  ...
  FROM image AS production # Stage 2: Production
  COPY --from=builder /path /path  # Copy from stage

IMAGE SIZE HIERARCHY (small→large):
  scratch → distroless → alpine → slim → full

SECURITY CHECKLIST:
  ✓ Non-root USER
  ✓ Specific base image version
  ✓ No secrets in ENV/ARG
  ✓ --no-install-recommends
  ✓ rm -rf /var/lib/apt/lists/* in same RUN
  ✓ Multi-stage builds
  ✓ .dockerignore
  ✓ Scan with trivy
  ✓ HEALTHCHECK defined

CMD vs ENTRYPOINT:
  CMD:        Overridable default: docker run img OVERRIDE
  ENTRYPOINT: Fixed executable. Args appended. Override: --entrypoint
  Both:       ENTRYPOINT is the executable, CMD provides default arguments.
  Always use: Exec form ["executable", "arg"] not shell form

ARG vs ENV:
  ARG: Build time only. --build-arg KEY=val. Not in running container.
  ENV: Baked into image. Runtime. Visible in docker inspect.
  Both visible in docker history. NEVER store secrets in either.
