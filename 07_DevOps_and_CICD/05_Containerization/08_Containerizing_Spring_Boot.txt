1. OVERVIEW — THREE APPROACHES
================================================================================

Three main ways to containerize a Spring Boot application:

  ┌──────────────────────┬────────────────────────────────────────────┐
  │ Approach             │ Best For                                   │
  ├──────────────────────┼────────────────────────────────────────────┤
  │ Dockerfile (layered) │ Full control, CI/CD pipelines, custom base │
  │ Jib                  │ Fast builds, no Docker daemon needed        │
  │ Buildpacks           │ Convention over configuration, security     │
  └──────────────────────┴────────────────────────────────────────────┘

All three integrate with Spring Boot's Maven/Gradle plugin.
All three produce OCI-compliant container images.
The "right" answer depends on team constraints and CI/CD environment.

2. NAIVE DOCKERFILE (WHAT NOT TO DO)
================================================================================

The Most Common (Bad) Approach:

  FROM openjdk:17
  COPY target/my-app-1.0.0.jar app.jar
  ENTRYPOINT ["java", "-jar", "/app.jar"]

Problems with This Approach:

  1. ENTIRE JAR is one Docker layer
     A 50MB JAR = every build pushes 50MB to registry.
     99% of the JAR is unchanged (dependencies).
     Only 1% is your actual code change.
     Docker layer cache is invalidated on every code change.

  2. No JVM tuning
     No container-awareness flags.
     JVM may size heap for host machine, not container.

  3. openjdk:17 is HUGE (~470MB)
     Includes full JDK (compilers, tools) — only JRE needed at runtime.

  4. Running as root
     Security anti-pattern.

  5. No health check
     Kubernetes has to infer health from port availability.

  6. No signal handling
     PID 1 issue — Java doesn't receive SIGTERM properly in some cases.

3. MULTI-STAGE DOCKERFILE (PRODUCTION APPROACH)
================================================================================

Multi-Stage Dockerfile with Layered JAR:

  # ============================================================
  # Stage 1: Builder — Extract JAR layers
  # ============================================================
  FROM eclipse-temurin:21-jdk-alpine AS builder
  WORKDIR /build
  
  # Copy the fat JAR from target/
  COPY target/*.jar app.jar
  
  # Extract layers from the Spring Boot fat JAR
  RUN java -Djarmode=layertools -jar app.jar extract
  # Creates directories:
  #   dependencies/
  #   spring-boot-loader/
  #   snapshot-dependencies/
  #   application/
  
  # ============================================================
  # Stage 2: Runtime — Minimal JRE image
  # ============================================================
  FROM eclipse-temurin:21-jre-alpine
  
  # Security: create non-root user
  RUN addgroup -S appgroup && adduser -S appuser -G appgroup
  
  WORKDIR /app
  
  # Copy layers in order of change frequency (most stable first)
  # This maximizes Docker layer caching
  COPY --from=builder /build/dependencies/ ./          # Rarely changes
  COPY --from=builder /build/spring-boot-loader/ ./    # Rarely changes
  COPY --from=builder /build/snapshot-dependencies/ ./ # Sometimes changes
  COPY --from=builder /build/application/ ./           # Changes every build
  
  # Switch to non-root user
  USER appuser
  
  # Expose port
  EXPOSE 8080
  
  # Health check
  HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
    CMD wget -q --spider http://localhost:8080/actuator/health || exit 1
  
  # JVM tuning via environment variable
  ENV JAVA_TOOL_OPTIONS="\
    -XX:+UseContainerSupport \
    -XX:MaxRAMPercentage=75.0 \
    -XX:MaxMetaspaceSize=256m \
    -XX:+ExitOnOutOfMemoryError \
    -XX:+HeapDumpOnOutOfMemoryError \
    -XX:HeapDumpPath=/tmp/heap.hprof \
    -Djava.security.egd=file:/dev/./urandom"
  
  # Use Spring Boot's JarLauncher (not exec with -jar)
  ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Why Each Layer Matters:
  
  dependencies/         → External Maven dependencies (rarely changes)
                          Docker caches this layer across builds
  spring-boot-loader/   → Spring Boot launcher (changes only on SB version)
  snapshot-dependencies → SNAPSHOT jars (changes per build, before release)
  application/          → Your actual code (changes every commit)
  
  Result: Only the top 1-2 layers are rebuilt/pushed on each commit.
  Cache hit on 3 layers → push only ~500KB instead of 50MB.

Base Image Selection:

  DO use:
    eclipse-temurin:21-jre-alpine    # Azul/Eclipse, JRE only, Alpine (tiny)
    eclipse-temurin:21-jre-jammy     # Ubuntu-based (more compatible)
    amazoncorretto:21-alpine-jdk     # AWS Corretto (Amazon-maintained)
    gcr.io/distroless/java21-debian12 # Google Distroless (no shell)
  
  DO NOT use:
    openjdk:17           # Deprecated, uses full JDK (too large)
    java:8               # Ancient, unmaintained
    openjdk:latest       # Non-deterministic

Image Size Comparison:
  
  Approach                    | Size
  ----------------------------|------
  openjdk:17 (fat JAR)        | ~470MB
  eclipse-temurin:21-jre-alpine| ~220MB
  eclipse-temurin:21-jre-jammy | ~280MB
  distroless/java21            | ~185MB
  GraalVM native binary        | ~80-150MB

4. LAYERED JARS (SPRING BOOT 2.3+)
================================================================================

What Are Layered JARs?

  Spring Boot 2.3+ introduced built-in JAR layering.
  The fat JAR is structured so its contents can be extracted into separate
  Docker layers by change frequency.

Enable Layered JARs:

  Maven (pom.xml):
  
  <plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
      <layers>
        <enabled>true</enabled>   <!-- Default in Spring Boot 2.4+ -->
      </layers>
    </configuration>
  </plugin>
  
  Gradle (build.gradle):
  
  bootJar {
    layered {
      enabled = true
    }
  }

Inspect JAR Layers:
  
  # List layers:
  java -Djarmode=layertools -jar my-app.jar list
  # Output:
  #   dependencies
  #   spring-boot-loader
  #   snapshot-dependencies
  #   application
  
  # Extract layers to current directory:
  java -Djarmode=layertools -jar my-app.jar extract

Custom Layer Configuration:
  
  # layers.xml (place in src/main/resources/):
  <layers xmlns="http://www.springframework.org/schema/boot/layers"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
    <application>
      <into layer="spring-boot-loader">
        <include>org/springframework/boot/loader/**</include>
      </into>
      <into layer="application" />
    </application>
    <dependencies>
      <into layer="snapshot-dependencies">
        <include>*:*:*SNAPSHOT</include>
      </into>
      <into layer="company-dependencies">
        <include>com.mycompany:*</include>  <!-- Internal libs change often -->
      </into>
      <into layer="dependencies" />
    </dependencies>
    <layerOrder>
      <layer>dependencies</layer>
      <layer>spring-boot-loader</layer>
      <layer>snapshot-dependencies</layer>
      <layer>company-dependencies</layer>
      <layer>application</layer>
    </layerOrder>
  </layers>

5. JIB — BUILD DOCKER IMAGES WITHOUT DOCKER
================================================================================

What is Jib?

  Google's open-source tool to build optimized Docker images for Java apps
  WITHOUT requiring Docker installed or running.
  
  Jib builds images directly from Maven/Gradle to:
  - Docker daemon (local)
  - Container registry (remote) — no Docker needed!

Why Jib is Excellent for CI/CD:
  ✅ No Docker daemon required in CI (no DinD — Docker-in-Docker)
  ✅ Reproducible builds (same input → same image hash)
  ✅ Automatically layers dependencies (like layered JAR approach)
  ✅ Fast incremental builds (only pushes changed layers)
  ✅ Runs as non-root by default
  ✅ No Dockerfile to maintain

Maven Configuration (pom.xml):
  
  <plugin>
    <groupId>com.google.cloud.tools</groupId>
    <artifactId>jib-maven-plugin</artifactId>
    <version>3.4.2</version>
    <configuration>
      <from>
        <image>eclipse-temurin:21-jre-alpine</image>
      </from>
      <to>
        <image>my-registry.io/my-app</image>
        <tags>
          <tag>${project.version}</tag>
          <tag>latest</tag>
        </tags>
      </to>
      <container>
        <ports>
          <port>8080</port>
        </ports>
        <environment>
          <JAVA_TOOL_OPTIONS>
            -XX:+UseContainerSupport
            -XX:MaxRAMPercentage=75.0
            -XX:MaxMetaspaceSize=256m
            -XX:+ExitOnOutOfMemoryError
          </JAVA_TOOL_OPTIONS>
        </environment>
        <user>nobody</user>        <!-- Run as non-root -->
        <creationTime>USE_CURRENT_TIMESTAMP</creationTime>
        <labels>
          <maintainer>team@company.com</maintainer>
          <version>${project.version}</version>
        </labels>
        <jvmFlags>
          <jvmFlag>-Djava.security.egd=file:/dev/./urandom</jvmFlag>
        </jvmFlags>
      </container>
      <allowInsecureRegistries>false</allowInsecureRegistries>
    </configuration>
  </plugin>

Jib Build Commands:
  
  # Build to Docker daemon (local):
  ./mvnw jib:dockerBuild
  
  # Build directly to registry (no Docker needed):
  ./mvnw jib:build
  
  # Build to a tar archive:
  ./mvnw jib:buildTar
  
  # With specific image tag:
  ./mvnw jib:build -Dimage=my-registry.io/my-app:${GIT_SHA}

Jib in GitHub Actions (No Docker Daemon Needed):
  
  - name: Build and Push Image (Jib)
    run: |
      ./mvnw jib:build \
        -Djib.to.image=${{ secrets.REGISTRY }}/my-app:${{ github.sha }} \
        -Djib.to.auth.username=${{ secrets.REGISTRY_USER }} \
        -Djib.to.auth.password=${{ secrets.REGISTRY_PASSWORD }}

Jib Layers (Automatic):
  Jib automatically creates these layers:
  1. Base image layers (OS, JRE)
  2. Dependencies (Maven artifacts → rarely change)
  3. Resources (src/main/resources → sometimes change)
  4. Classes (compiled Java classes → change every build)

6. CLOUD NATIVE BUILDPACKS (SPRING BOOT 2.3+)
================================================================================

What Are Buildpacks?

  Cloud Native Buildpacks (CNB) are the technology behind Heroku's
  "git push → running app" magic.
  
  Spring Boot 2.3+ integrates Buildpacks via the Maven/Gradle plugin.
  No Dockerfile needed — Buildpack auto-detects your app and builds a
  production-ready image with:
  - Optimal base image (Paketo Buildpacks)
  - Security hardening
  - Build reproducibility
  - Bill of Materials (SBOM) embedded

Build with Buildpacks:
  
  # Maven:
  ./mvnw spring-boot:build-image
  
  # Gradle:
  ./gradlew bootBuildImage
  
  # Custom image name:
  ./mvnw spring-boot:build-image -Dspring-boot.build-image.imageName=my-registry/my-app:1.0

Configure in pom.xml:
  
  <plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
      <image>
        <name>my-registry.io/my-app:${project.version}</name>
        <builder>paketobuildpacks/builder-jammy-base:latest</builder>
        <env>
          <!-- JVM memory tuning via Buildpack env vars -->
          <BPE_JAVA_TOOL_OPTIONS>
            -XX:MaxRAMPercentage=75.0 -XX:MaxMetaspaceSize=256m
          </BPE_JAVA_TOOL_OPTIONS>
          <!-- Paketo buildpack memory calculator override -->
          <BPL_JVM_THREAD_COUNT>50</BPL_JVM_THREAD_COUNT>
        </env>
        <publish>true</publish>
        <pullPolicy>IF_NOT_PRESENT</pullPolicy>
      </image>
    </configuration>
  </plugin>

Paketo Buildpack Memory Calculator:
  
  Paketo's buildpack automatically calculates JVM memory settings based on
  container limits. Sets heap, metaspace, and direct memory proportionally.
  
  Override via environment variables:
  BPL_JVM_HEAP_RATIO=0.75        # Heap = 75% of container RAM
  BPL_JVM_THREAD_COUNT=50        # Expected thread count
  BPL_JVM_HEAD_ROOM=5            # Headroom % (default: 0)

Buildpacks Advantages:
  ✅ Production-secure base images (auto-patched)
  ✅ Automatic SBOM (Software Bill of Materials)
  ✅ Automatic memory calculator
  ✅ No Dockerfile to maintain
  ✅ Reproducible builds
  ✅ Supports GraalVM native (with native profile)

Buildpacks Limitations:
  ❌ Requires Docker daemon (unlike Jib)
  ❌ Slower first build (downloads buildpacks)
  ❌ Less flexible than Dockerfile for custom needs
  ❌ Harder to debug if build fails

7. APPROACH COMPARISON MATRIX
================================================================================

  ┌─────────────────────────┬────────────────┬──────────────┬─────────────┐
  │ Feature                 │ Dockerfile     │ Jib          │ Buildpacks  │
  ├─────────────────────────┼────────────────┼──────────────┼─────────────┤
  │ Docker daemon required  │ Yes            │ No           │ Yes         │
  │ Dockerfile required     │ Yes            │ No           │ No          │
  │ Layer caching           │ Manual         │ Automatic    │ Automatic   │
  │ Build speed             │ Fast           │ Very fast    │ Slower      │
  │ Customization           │ Full control   │ Limited      │ Limited     │
  │ Security hardening      │ Manual         │ Basic        │ Automatic   │
  │ SBOM support            │ Manual         │ No           │ Automatic   │
  │ Non-root user           │ Manual         │ Default      │ Default     │
  │ Native image support    │ Yes            │ Partial      │ Yes         │
  │ CI/CD simplicity        │ Medium         │ High         │ High        │
  │ Learning curve          │ High           │ Low          │ Low         │
  │ Production readiness    │ With effort    │ Good         │ Best        │
  └─────────────────────────┴────────────────┴──────────────┴─────────────┘

When to Use Each:

  Dockerfile (Layered):
    ✓ Full control required
    ✓ Custom base image (FIPS-compliant, company-approved)
    ✓ Complex build steps (native dependencies, custom tooling)
    ✓ Maximum build speed control

  Jib:
    ✓ No Docker daemon in CI (security constraint)
    ✓ Speed is critical (large number of microservices)
    ✓ Simple CRUD apps
    ✓ Kubernetes-only deployment

  Buildpacks:
    ✓ Security and compliance are top priority
    ✓ Auto-patching base images
    ✓ Teams without Docker expertise
    ✓ Want SBOM for audit/compliance

8. JVM TUNING IN CONTAINERS (SPRING BOOT SPECIFIC)
================================================================================

Essential JAVA_TOOL_OPTIONS for Spring Boot in Docker/K8s:

  export JAVA_TOOL_OPTIONS="\
    -XX:+UseContainerSupport \
    -XX:MaxRAMPercentage=75.0 \
    -XX:InitialRAMPercentage=50.0 \
    -XX:MaxMetaspaceSize=256m \
    -XX:+UseG1GC \
    -XX:MaxGCPauseMillis=200 \
    -XX:ParallelGCThreads=4 \
    -XX:ConcGCThreads=2 \
    -XX:+ExitOnOutOfMemoryError \
    -XX:+HeapDumpOnOutOfMemoryError \
    -XX:HeapDumpPath=/tmp/heap.hprof \
    -Djava.security.egd=file:/dev/./urandom \
    -Dspring.profiles.active=${SPRING_PROFILES_ACTIVE:-default}"

Why -Djava.security.egd=file:/dev/./urandom:
  SecureRandom blocks waiting for entropy in containers.
  Containers have less entropy sources than VMs.
  Urandom is non-blocking and cryptographically adequate.
  Without this: Session ID generation and SSL handshakes can hang 30+ seconds.

Spring Profiles via Environment:
  
  # Set active profile via env var in Kubernetes:
  env:
  - name: SPRING_PROFILES_ACTIVE
    value: "kubernetes,production"
  
  # Or per-environment ConfigMap:
  envFrom:
  - configMapRef:
      name: spring-env-config

Tomcat Thread Pool Tuning for Containers:
  
  # application.yaml:
  server:
    tomcat:
      threads:
        max: 50        # Reduce from default 200 for small containers
        min-spare: 10
      max-connections: 200
      accept-count: 100
    
  # Rule of thumb: max-threads ≈ container-CPU × 25

Actuator for Container Health:
  
  # application.yaml:
  management:
    server:
      port: 8081       # Separate management port (don't expose 8080 mgmt)
    endpoints:
      web:
        exposure:
          include: health,info,prometheus,metrics,loggers
    endpoint:
      health:
        probes:
          enabled: true
        show-details: always
        group:
          readiness:
            include: readinessState,db,redis   # Include dependency checks
          liveness:
            include: livenessState,diskSpace

9. SPRING BOOT DOCKER BEST PRACTICES
================================================================================

Security Best Practices:

  1. Non-root user:
     RUN addgroup -S appgroup && adduser -S appuser -G appgroup
     USER appuser
  
  2. Minimal base image:
     Use JRE-only image (not full JDK)
     eclipse-temurin:21-jre-alpine (smallest JRE)
  
  3. No COPY of secrets into image:
     Never: COPY .env /app/
     Use: Kubernetes Secrets, Vault, AWS Secrets Manager at runtime
  
  4. Read-only root filesystem:
     securityContext:
       readOnlyRootFilesystem: true
     Add writable mounts for:
       /tmp (temp files)
       /dumps (heap dumps)
       /logs (if file logging)
  
  5. Drop Linux capabilities:
     securityContext:
       capabilities:
         drop:
           - ALL
  
  6. No privileged mode:
     securityContext:
       privileged: false
       allowPrivilegeEscalation: false

Build Best Practices:

  1. Use .dockerignore:
     # .dockerignore
     .git
     .github
     target/
     *.md
     Dockerfile*
     docker-compose*
     .mvn/
     **/*.log
     **/*.iml
     .idea/
  
  2. Pin base image versions (don't use :latest):
     FROM eclipse-temurin:21.0.3_9-jre-alpine
  
  3. Cache Maven dependencies:
     # In CI, mount .m2 cache between builds:
     docker run -v ~/.m2:/root/.m2 maven:3.9-eclipse-temurin-21 mvn package

Application Best Practices:

  1. Externalize all config (12-factor app):
     - No hardcoded URLs, passwords, or environment-specific config
     - Use Spring's @ConfigurationProperties with env var overrides
     - SPRING_DATASOURCE_URL overrides spring.datasource.url

  2. Graceful shutdown:
     server:
       shutdown: graceful
     spring:
       lifecycle:
         timeout-per-shutdown-phase: 30s

  3. Log to stdout (not files):
     Containers are ephemeral — write logs to stdout/stderr.
     Log aggregation (ELK, CloudWatch) picks up stdout automatically.
     
     # application.yaml:
     logging:
       pattern:
         console: >-
           {"timestamp":"%d{ISO8601}","level":"%level",
           "service":"my-app","traceId":"%X{traceId}",
           "message":"%msg"}%n

11. HEALTH CHECKS AND GRACEFUL SHUTDOWN
================================================================================

Spring Boot Actuator Probes (Kubernetes-Native):

  Spring Boot 2.3+ automatically detects Kubernetes and enables
  /actuator/health/liveness and /actuator/health/readiness.
  
  Detection: spring.main.cloud-platform=kubernetes
  Or auto-detected from environment (KUBERNETES_SERVICE_HOST).

Liveness vs Readiness vs Startup:
  
  LIVENESS:  Is the JVM alive and not deadlocked?
             → Failure = kill the pod and restart
             → Use: spring.boot.liveness-state.enabled=true
             → Endpoint: /actuator/health/liveness
  
  READINESS: Is the app ready to serve traffic?
             → Failure = remove from load balancer (don't restart)
             → Fails during startup, maintenance, dependency outage
             → Endpoint: /actuator/health/readiness
  
  STARTUP:   Is the app done starting up?
             → Replaces initialDelaySeconds
             → Allows long startup without triggering liveness failures

Full Probe Configuration:

  # Kubernetes Deployment:
  startupProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    failureThreshold: 30
    periodSeconds: 10
    initialDelaySeconds: 10
  
  livenessProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    failureThreshold: 3
    periodSeconds: 10
    successThreshold: 1
    timeoutSeconds: 5
  
  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    failureThreshold: 3
    periodSeconds: 5
    successThreshold: 1
    timeoutSeconds: 3

Graceful Shutdown Configuration:
  
  # application.yaml:
  server:
    shutdown: graceful          # Wait for in-flight requests to complete
  spring:
    lifecycle:
      timeout-per-shutdown-phase: 30s   # Max wait time
  
  # Kubernetes pod spec:
  spec:
    terminationGracePeriodSeconds: 60   # Must be > timeout-per-shutdown-phase
    containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 5"]
            # Sleep 5s before SIGTERM to allow endpoints to deregister
            # from load balancer / service mesh before stopping

Custom Health Indicators:

  @Component
  public class DatabaseHealthIndicator implements HealthIndicator {
      
      @Autowired
      private DataSource dataSource;
      
      @Override
      public Health health() {
          try (Connection conn = dataSource.getConnection()) {
              if (conn.isValid(2)) {
                  return Health.up()
                      .withDetail("database", "PostgreSQL")
                      .withDetail("status", "connected")
                      .build();
              }
          } catch (SQLException e) {
              return Health.down()
                  .withDetail("error", e.getMessage())
                  .build();
          }
          return Health.down().build();
      }
  }

12. SPRING BOOT 3.X + GRAALVM NATIVE IMAGE
================================================================================

What Changes with Spring Boot 3.x Native:

  Spring Boot 3.0+ (with Spring Framework 6) is optimized for GraalVM.
  AOT (Ahead-of-Time) compilation happens at build time.
  Spring generates native hints for reflection, proxy, serialization.

Build Native Image:
  
  # With Maven (using Buildpacks — recommended):
  ./mvnw spring-boot:build-image -Pnative
  
  # With Maven (native executable directly):
  ./mvnw native:compile -Pnative
  
  # pom.xml profile:
  <profiles>
    <profile>
      <id>native</id>
      <build>
        <plugins>
          <plugin>
            <groupId>org.graalvm.buildtools</groupId>
            <artifactId>native-maven-plugin</artifactId>
            <extensions>true</extensions>
            <executions>
              <execution>
                <id>build-native</id>
                <goals><goal>compile-no-fork</goal></goals>
                <phase>package</phase>
              </execution>
            </executions>
            <configuration>
              <buildArgs>
                <buildArg>--no-fallback</buildArg>
                <buildArg>--gc=serial</buildArg>     <!-- Lower memory -->
                <buildArg>-O2</buildArg>             <!-- Optimization level -->
              </buildArgs>
            </configuration>
          </plugin>
        </plugins>
      </build>
    </profile>
  </profiles>

Native Image Dockerfile:
  
  # Stage 1: Build native binary
  FROM ghcr.io/graalvm/native-image:21 AS builder
  WORKDIR /build
  COPY . .
  RUN ./mvnw -Pnative native:compile -DskipTests
  
  # Stage 2: Minimal runtime (no JVM needed!)
  FROM ubuntu:22.04
  RUN apt-get update && apt-get install -y libstdc++6 && rm -rf /var/lib/apt/lists/*
  WORKDIR /app
  COPY --from=builder /build/target/my-app .
  RUN adduser --disabled-password appuser && chown appuser:appuser /app/my-app
  USER appuser
  EXPOSE 8080
  ENTRYPOINT ["/app/my-app"]

Native Image in Kubernetes:
  
  # Much smaller resource requirements:
  resources:
    requests:
      memory: "64Mi"
      cpu: "50m"
    limits:
      memory: "128Mi"
      cpu: "500m"
  
  # Faster probes (starts in <1s):
  startupProbe:
    httpGet:
      path: /actuator/health
      port: 8080
    failureThreshold: 3
    periodSeconds: 2
    initialDelaySeconds: 1

Native Image Caveats for Java Developers:
  
  1. Reflection: Must register classes
     @RegisterReflectionForBinding(MyDto.class)
  
  2. Dynamic proxies: Spring Boot auto-generates hints for @Transactional,
     @Cacheable, etc. Custom proxies may need manual hints.
  
  3. Build time is slow (5-15 minutes vs 30 seconds for JVM)
  
  4. Third-party library support varies
     Check: https://www.graalvm.org/native-image/libraries-and-frameworks/
  
  5. Testing: Run tests with native profile before deploying
     ./mvnw -Pnative test

13. SECRETS AND CONFIGURATION IN CONTAINERS
================================================================================

Configuration Hierarchy (Spring Boot):
  
  Priority (highest to lowest):
  1. Command line arguments
  2. JNDI attributes
  3. Java System properties (-D flags)
  4. OS environment variables
  5. Application properties (application.yaml)
  6. Default properties
  
  Kubernetes practice:
  - application.yaml in image (non-sensitive defaults)
  - Kubernetes ConfigMap → env vars (non-sensitive config)
  - Kubernetes Secrets → env vars (sensitive config)
  - Vault/AWS Secrets Manager → runtime fetch (very sensitive)

Kubernetes ConfigMap for Spring Boot:

  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: my-app-config
  data:
    SPRING_PROFILES_ACTIVE: "kubernetes"
    SERVER_PORT: "8080"
    SPRING_DATASOURCE_URL: "jdbc:postgresql://postgres-service:5432/mydb"
    LOGGING_LEVEL_COM_MYCOMPANY: "INFO"
  ---
  # In Deployment:
  envFrom:
  - configMapRef:
      name: my-app-config

  kubectl create secret generic my-app-secrets \
    --from-literal=SPRING_DATASOURCE_PASSWORD=mypassword \

  # In Deployment:

  - secretRef:

14. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: Explain the difference between Jib, Buildpacks, and a layered Dockerfile
    for containerizing a Spring Boot app. When would you choose each?

A: All three produce OCI container images, but differ in approach:
   
   Layered Dockerfile:
   - Manual control — you write the Dockerfile with explicit COPY layers
   - Maximizes cache efficiency (deps → loader → code)
   - Requires Docker daemon in CI (security concern)
   - Best when: custom base images, complex build steps, maximum flexibility
   
   Jib (Google):
   - Maven/Gradle plugin — no Docker daemon or Dockerfile needed
   - Builds directly to registry or local daemon
   - Automatic layering by change frequency
   - Best when: CI doesn't have Docker (security), large microservice count,
     speed is priority
   
   Buildpacks:
   - Spring Boot plugin integrates Paketo buildpacks
   - Auto-detects app type, applies security best practices
   - Automatic SBOM, auto-patched base images
   - Slowest build but most production-ready
   - Best when: security/compliance is critical, team lacks Docker expertise
   
   My production recommendation:
   - Greenfield: Buildpacks (most secure, least maintenance)
   - Large microservice fleet: Jib (fast, no Docker daemon)
   - Complex requirements: Layered Dockerfile

---

Q2: A Spring Boot container keeps failing startup with "java.lang.OutOfMemoryError:
    Java heap space" within the first 30 seconds. What do you check?

A: Systematic debug:
   
   1. Check container memory limit vs JVM heap config:
      kubectl describe pod <name> → check resources.limits.memory
      
      If -Xmx is set and higher than container limit → OOM on startup.
      If MaxRAMPercentage is set too high → JVM asks for too much heap.
   
   2. Check if UseContainerSupport is enabled:
      Java < 8u191: JVM reads host memory (e.g., 256GB) → tries to allocate
      25% heap = 64GB in a 1GB container → instant OOM.
      
      Fix: Upgrade to Java 11+ or add -XX:+UseContainerSupport.
   
   3. Check Metaspace:
      Spring Boot with many beans loads many classes at startup.
      If MaxMetaspaceSize is too small → OOM:Metaspace at startup.
      Add: -XX:MaxMetaspaceSize=256m (or increase if needed).
   
   4. Check spring.main.lazy-initialization:
      False = all beans created on startup (more startup memory pressure).
      Consider: spring.main.lazy-initialization=true for faster startup.
   
   5. Check if heap dump was captured:
      -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/
      Analyze with Eclipse MAT to see what's consuming heap at startup.

---

Q3: How do you handle a Spring Boot application that takes 2 minutes to start
    in Kubernetes and keeps getting killed?

A: This is the startup probe problem.
   
   Root cause: Kubernetes' liveness/readiness probes fail before JVM is ready
   → pod restart loop → CrashLoopBackOff.
   
   Solution — Use startupProbe (Kubernetes 1.16+):
   
     startupProbe:
       httpGet:
         path: /actuator/health/liveness
         port: 8080
       failureThreshold: 30    # 30 × 10s = 5 minutes maximum
       periodSeconds: 10
       initialDelaySeconds: 10
   
   Once startupProbe succeeds, liveness/readiness probes take over.
   
   Also improve startup time:
   - spring.main.lazy-initialization=true
   - Reduce classpath / number of auto-configured beans
   - Use AppCDS (Class Data Sharing) for 20-50% startup reduction
   - Consider GraalVM Native Image for < 1s startup

---

Q4: How do you make a Spring Boot Docker image production-secure?

A: Checklist:
   
   1. Non-root user (adduser appuser; USER appuser)
   2. JRE-only base image (not JDK)
   3. No secrets in image (use K8s Secrets or Vault)
   4. Read-only root filesystem + writable /tmp mount
   5. Drop all Linux capabilities (securityContext.capabilities.drop: ALL)
   6. No privilege escalation (allowPrivilegeEscalation: false)
   7. Pin base image versions (no :latest)
   8. Run image scanning in CI (Trivy, Grype)
   9. Log to stdout (no sensitive data in logs)
   10. -XX:+ExitOnOutOfMemoryError (fail fast, don't limp)
   11. HEALTHCHECK in Dockerfile and readiness probe in K8s
   12. .dockerignore to exclude source code, .git, credentials

RESOURCE SIZING RULE:
  Container memory = heap + 512MB (Metaspace + threads + OS)
  Example: 75% heap of 1Gi → 768MB heap + ~300MB other = 1Gi minimum

ACTUATOR ENDPOINTS:
  /actuator/health/liveness   → Kubernetes liveness probe
  /actuator/health/readiness  → Kubernetes readiness probe
  /actuator/prometheus        → Prometheus metrics scraping

  spring.lifecycle.timeout-per-shutdown-phase: 30s
  terminationGracePeriodSeconds: 60 (in pod spec)
