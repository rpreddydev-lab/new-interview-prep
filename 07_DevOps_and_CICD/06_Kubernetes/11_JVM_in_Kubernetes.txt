1. WHY JVM + KUBERNETES REQUIRES SPECIAL ATTENTION
================================================================================

The Core Problem:
  The JVM was designed in the pre-container era.
  It reads system-level resource information (CPU count, total RAM).
  In a container, those system values reflect the HOST, not the container.

  Classic symptom:
    Host machine: 64 CPU cores, 256 GB RAM
    Container limit: 2 CPU, 4 GB RAM
    JVM sees: 64 cores → creates 64 GC threads, sizes heap for 256 GB
    Result: OOMKilled, excessive GC overhead, thrashing

  This was the #1 cause of JVM application failures in early Kubernetes
  deployments (2015–2018).

The Solution Evolution:
  Java 8u191+:  -XX:+UseContainerSupport added (on by default in Java 10+)
  Java 10:      Container support backported to Java 8 update 191
  Java 11+:     Full container awareness, MaxRAMPercentage works correctly
  Java 17+:     Further G1GC improvements for containers
  Java 21+:     Virtual threads (Project Loom) change thread model entirely

Senior Interview Insight:
  Many companies still run Java 8 services in Kubernetes.
  Knowing this history demonstrates real production experience.

2. JVM CONTAINER AWARENESS HISTORY
================================================================================

Pre-Java 8u191 Behavior (Broken):
  - JVM reads /proc/meminfo → gets HOST total memory
  - JVM reads /proc/cpuinfo → gets HOST CPU count
  - Default heap (-Xmx) = 25% of HOST memory (not container limit)
  - GC thread count = HOST core count

  Example disaster:
    Host: 128 GB RAM, 32 cores
    Container limit: 1 GB RAM, 1 CPU
    JVM default heap: 32 GB (tries to allocate, OOMKilled immediately)
    GC threads: 8 (for a 1-CPU container — massive CPU throttling)

Java 8u191 / Java 10+ Fix:
  -XX:+UseContainerSupport (enabled by default from Java 10+)
  
  Now JVM reads cgroup limits:
    /sys/fs/cgroup/memory/memory.limit_in_bytes  → memory limit
    /sys/fs/cgroup/cpu/cpu.cfs_quota_us          → CPU quota
    /sys/fs/cgroup/cpu/cpu.cfs_period_us         → CPU period

  Available CPUs = ceil(quota / period)
  Example: quota=100000, period=100000 → 1.0 CPU available

Verify Container Support is Active:
  java -XX:+PrintFlagsFinal -version | grep UseContainerSupport
  # Should show: bool UseContainerSupport = true

3. USECONTAINERSUPPORT AND MAXRAMPERCENTAGE
================================================================================

Key JVM Flags for Container Memory:

  -XX:+UseContainerSupport          (default ON in Java 10+)
    Enables reading cgroup limits instead of host limits.

  -XX:MaxRAMPercentage=75.0         (RECOMMENDED — replaces -Xmx)
    Sets max heap as a percentage of container memory limit.
    DO NOT use fixed -Xmx in containers (defeats the purpose).

  -XX:InitialRAMPercentage=50.0     (optional)
    Sets initial heap size as percentage of container memory.

  -XX:MinRAMPercentage=25.0         (for containers < 200MB)
    Used when total memory is small; applies to very small containers.

Why MaxRAMPercentage Instead of -Xmx?

  BAD (static -Xmx):
    -Xmx512m
    Problem: If you scale the container limit to 2GB, JVM still uses 512MB.
    Doesn't adapt when you change resource limits.

  GOOD (percentage-based):
    -XX:MaxRAMPercentage=75.0
    Container limit: 1GB  → max heap: 768MB
    Container limit: 2GB  → max heap: 1536MB
    Container limit: 4GB  → max heap: 3072MB
    Adapts automatically to whatever limit you set in the pod spec.

Recommended Percentages by Use Case:
  
  ┌─────────────────────────────┬──────────────────────────────┐
  │ Use Case                    │ MaxRAMPercentage             │
  ├─────────────────────────────┼──────────────────────────────┤
  │ General Spring Boot app     │ 75%                          │
  │ Memory-intensive processing │ 60-70% (leave room for IO)   │
  │ App with large off-heap     │ 50% (Netty, NIO buffers)     │
  │ Very small container <512MB │ 60% (more room for OS)       │
  │ GraalVM native image        │ N/A (not heap-based)         │
  └─────────────────────────────┴──────────────────────────────┘

Setting in Kubernetes:
  
  # In Deployment YAML:
  env:
  - name: JAVA_OPTS
    value: >-
      -XX:+UseContainerSupport
      -XX:MaxRAMPercentage=75.0
      -XX:InitialRAMPercentage=50.0
      -XX:+ExitOnOutOfMemoryError
  
  # Or use JAVA_TOOL_OPTIONS (applies to any JVM, even in scripts):
  env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError"

JAVA_OPTS vs JAVA_TOOL_OPTIONS:
  JAVA_TOOL_OPTIONS: Read by the JVM launcher itself (always honored)
  JAVA_OPTS:         Read by startup scripts (spring-boot:run, etc.)
  Prefer JAVA_TOOL_OPTIONS for universal JVM processes.

4. HEAP VS NON-HEAP MEMORY IN CONTAINERS
================================================================================

JVM Memory is More Than Just Heap:

  Total JVM Memory = Heap + Non-Heap + Native Memory

  HEAP:
    - Young Generation (Eden + Survivor spaces)
    - Old Generation (Tenured)
    - Controlled by -Xms, -Xmx, MaxRAMPercentage
    - GC runs here

  NON-HEAP (Metaspace):
    - Class definitions, bytecode
    - Unlimited by default → can OOM!
    - Control with: -XX:MaxMetaspaceSize=256m
    - Spring Boot app: typically 150-300MB

  NATIVE MEMORY (off-heap):
    - JVM internal structures
    - Thread stacks (each thread: 512KB-1MB by default)
    - NIO buffers (Netty, etc.)
    - JIT compiled code cache
    - Not controlled by -Xmx!

  Memory Formula (rough sizing):
    Container Limit ≥ Heap + Metaspace + Threads + NIO buffers + OS overhead
    
    Example Spring Boot app:
      Heap:      1GB  (MaxRAMPercentage=75% of 1.5GB container)
      Metaspace: 256MB
      Threads:   100 threads × 512KB = 50MB
      NIO/JIT:   ~200MB
      OS:        ~100MB
      Total:     ~1.6GB → Container limit: 2GB

  Common Mistake:
    Setting -Xmx1g in a 1GB container → crashes!
    Heap = 1GB but total JVM memory needs 1.3-1.5GB minimum.

Best Practice — Metaspace:
  Always cap Metaspace in containers:
  -XX:MaxMetaspaceSize=256m
  
  Without this, a classloader leak → unbounded Metaspace growth → OOMKilled
  even though heap has free space.

Thread Stack Size:
  Default thread stack: 512KB (64-bit JVM)
  For high-thread-count apps: reduce to 256KB
  -Xss256k
  
  Java 21 Virtual Threads: Stack is tiny (~1KB per virtual thread)
  → Completely changes the thread memory equation.

5. CPU THROTTLING AND JVM THREAD POOLS
================================================================================

CPU Limits in Kubernetes (Critical Concept):

  CPU Request: Guaranteed minimum CPU allocation
  CPU Limit:   Hard cap — container is THROTTLED if it exceeds this

  CPU Throttling ≠ OOMKill. Throttling is silent and insidious.
  The container keeps running but gets slower.
  JVM does NOT know it's being throttled.

How Throttling Works (Linux CFS):
  CPU limit of 1.0 = 100ms of CPU per 100ms period
  If JVM uses 150ms in a 100ms period → throttled for 50ms
  
  This causes:
  - GC pause spikes (GC gets throttled mid-run)
  - HTTP request timeouts (CPU starved during request processing)
  - Thread pool starvation

JVM Thread Pool Sizing Problem:
  
  Runtime.getRuntime().availableProcessors()
  
  Pre-container awareness: returns HOST core count (e.g., 32)
  Post UseContainerSupport: returns container CPU count (e.g., 2)
  
  Many frameworks use this to size thread pools:
    - Tomcat default: max(200, 10 × cores)
    - ForkJoinPool.commonPool(): core count - 1
    - Parallel streams: uses ForkJoinPool with core count
  
  With 2 container CPUs: thread pools are correctly sized for 2 cores.
  But with CPU requests (not limits), some nuance applies.

CPU Request vs Limit for Thread Pool Sizing:
  
  Container: request=0.5 CPU, limit=2 CPU
  JVM sees:  2 CPUs (from cgroup limit)
  But gets:  0.5 CPU guaranteed (shared during contention)
  
  Recommendation: Set CPU request = CPU limit for predictable sizing.
  Or set CPU limit slightly above request.
  
  For Java apps: NEVER set CPU limit much higher than request.
  The burst model works for stateless apps but creates GC unpredictability.

Identifying Throttling:
  
  # Check container CPU throttling metrics:
  container_cpu_throttled_seconds_total   # Prometheus metric (cAdvisor)
  container_cpu_throttled_periods_total
  
  High throttling ratio = performance problems:
  throttle_ratio = throttled_periods / total_periods
  > 25% throttling = significant performance impact

6. GC SELECTION FOR CONTAINERIZED WORKLOADS
================================================================================

GC Algorithm Comparison for Kubernetes:

  ┌────────────────┬──────────────┬────────────────────────────────────┐
  │ GC             │ Available    │ Best For                           │
  ├────────────────┼──────────────┼────────────────────────────────────┤
  │ G1GC           │ Java 9+      │ General purpose (DEFAULT in Java 9+)│
  │ ZGC            │ Java 15+     │ Low-latency, large heaps           │
  │ Shenandoah     │ Java 15+     │ Low-latency (OpenJDK)              │
  │ SerialGC       │ All          │ Very small containers (<256MB heap) │
  │ ParallelGC     │ All          │ Batch/throughput workloads         │
  └────────────────┴──────────────┴────────────────────────────────────┘

G1GC in Containers (Most Common):
  
  Good defaults for Java 11-21:
  -XX:+UseG1GC                          # Explicit (default in Java 9+)
  -XX:G1HeapRegionSize=16m              # Larger regions for bigger heaps
  -XX:MaxGCPauseMillis=200              # Target pause time (best effort)
  -XX:ParallelGCThreads=4               # Limit GC threads (avoid over-threading)
  -XX:ConcGCThreads=2                   # Concurrent GC threads (half of parallel)
  -XX:InitiatingHeapOccupancyPercent=45 # Start concurrent GC earlier
  
  G1GC Thread Count Warning:
  G1GC auto-sizes threads based on available CPUs.
  With 32-CPU host and container limit of 2 CPU:
    With UseContainerSupport: sees 2 CPUs → 2-4 GC threads (correct)
    Without: sees 32 CPUs → 8+ GC threads (thrashing on 2 CPUs)

ZGC for Low-Latency Services (Java 15+):
  -XX:+UseZGC
  
  Features:
  - Sub-millisecond pause times (< 1ms regardless of heap size)
  - Scales from 8MB to 16TB heap
  - Concurrent — doesn't stop the world for most work
  
  Container considerations:
  - Requires more CPU for concurrent GC work
  - Higher memory overhead (~15-20% more RAM than G1GC)
  - Ideal for: REST APIs with latency SLAs, real-time processing
  
  Example flags:
  -XX:+UseZGC
  -XX:ConcGCThreads=2
  -XX:ZCollectionInterval=5   # Force periodic GC even when heap not full

SerialGC for Tiny Containers:
  -XX:+UseSerialGC
  
  Use when:
  - Heap < 256MB
  - Single-threaded workload (batch jobs)
  - Sidecar containers / agents
  
  SerialGC uses 1 thread → no contention in tiny containers.
  Counterintuitively better than G1GC for very small heaps.

7. JVM FLAGS REFERENCE FOR KUBERNETES
================================================================================

Essential Production Flags:

  # Memory
  -XX:+UseContainerSupport              # REQUIRED for Java 8u191-8u400
  -XX:MaxRAMPercentage=75.0             # Heap = 75% of container limit
  -XX:InitialRAMPercentage=50.0         # Initial heap = 50%
  -XX:MaxMetaspaceSize=256m             # Cap Metaspace (prevent leaks)
  -Xss256k                              # Thread stack (reduce from 512k)

  # GC
  -XX:+UseG1GC                          # Recommended for most workloads
  -XX:MaxGCPauseMillis=200              # Target pause (G1GC)
  -XX:ParallelGCThreads=4               # Limit GC threads
  -XX:ConcGCThreads=2                   # Limit concurrent GC threads

  # Failure Handling
  -XX:+ExitOnOutOfMemoryError           # Kill JVM on OOM (let K8s restart it)
  -XX:+HeapDumpOnOutOfMemoryError       # Capture heap dump for analysis
  -XX:HeapDumpPath=/dumps/heap.hprof    # Mount a volume here!
  -XX:+CrashOnOutOfMemoryError          # Alternative to ExitOnOutOfMemoryError

  # Diagnostics
  -XX:+PrintGCDetails                   # GC logging (Java 8)
  -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags  # GC logging (Java 9+)
  -XX:+DisableExplicitGC                # Prevent System.gc() calls

  # JIT
  -XX:ReservedCodeCacheSize=256m        # JIT compiled code cache
  -XX:+TieredCompilation                # Default ON — JIT with multiple tiers

Complete Recommended JAVA_TOOL_OPTIONS for Spring Boot:

  -XX:+UseContainerSupport
  -XX:MaxRAMPercentage=75.0
  -XX:InitialRAMPercentage=50.0
  -XX:MaxMetaspaceSize=256m
  -Xss256k
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200
  -XX:ParallelGCThreads=4
  -XX:ConcGCThreads=2
  -XX:+ExitOnOutOfMemoryError
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/dumps/heap.hprof
  -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m
  -Djava.security.egd=file:/dev/./urandom

8. RESOURCE REQUESTS AND LIMITS BEST PRACTICES
================================================================================

Kubernetes Resource Model:

  resources:
    requests:         # Guaranteed resources (scheduler uses this)
      memory: "512Mi"
      cpu: "500m"     # 500m = 0.5 CPU
    limits:           # Maximum allowed (OOMKill / throttle if exceeded)
      memory: "1Gi"
      cpu: "1000m"    # 1 CPU

Memory: Request vs Limit for Java:

  OPTION A — Equal request and limit (Guaranteed QoS):
    requests:
      memory: "1Gi"
    limits:
      memory: "1Gi"
    
    Kubernetes QoS: Guaranteed (highest priority, not killed first)
    Best for: Production, stateful services, databases
    JVM heap: -XX:MaxRAMPercentage=75.0 → 768MB heap
  
  OPTION B — Limit > Request (Burstable QoS):
    requests:
      memory: "512Mi"
    limits:
      memory: "1Gi"
    
    Kubernetes QoS: Burstable
    Risk: OOMKilled if node is under memory pressure
    JVM still sees limit (1Gi), sizes heap to 768MB
    But actual available: 512Mi → OOMKilled at moderate load!
    
    ⚠️ DANGER: JVM sizes heap based on LIMIT but gets KILLED at REQUEST.
    Always set memory limit = request for Java workloads!

CPU: Different story:
  CPU request = CPU limit → Guaranteed (no throttling)
  CPU request < CPU limit → Burstable (can throttle during peak)
  
  For Java: Acceptable to have limit > request for CPU.
  Throttling is non-fatal (unlike OOMKill).
  
  Recommended: memory request = limit, cpu limit = 2x request

LimitRange — Namespace Defaults:
  
  apiVersion: v1
  kind: LimitRange
  metadata:
    name: java-app-defaults
    namespace: my-namespace
  spec:
    limits:
    - type: Container
      default:              # Default limit if not specified
        memory: "512Mi"
        cpu: "500m"
      defaultRequest:       # Default request if not specified
        memory: "256Mi"
        cpu: "250m"
      max:                  # Maximum allowed
        memory: "4Gi"
        cpu: "4"
      min:                  # Minimum required
        memory: "64Mi"
        cpu: "50m"

ResourceQuota — Namespace Total:
  
  apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: java-team-quota
  spec:
    hard:
      requests.cpu: "20"
      requests.memory: "40Gi"
      limits.cpu: "40"
      limits.memory: "80Gi"
      pods: "50"

9. OOMKILLED — DIAGNOSIS AND PREVENTION
================================================================================

What is OOMKilled?

  Exit Code 137: Container killed by OOM Killer (kernel)
  
  # Check OOMKilled:
  kubectl describe pod <pod-name>
  # Look for:
  #   Last State: Terminated
  #     Reason: OOMKilled
  #     Exit Code: 137

OOMKilled Causes for Java Apps:

  1. JVM heap limit too high vs container memory limit
     Fix: MaxRAMPercentage=75 (not 90+)

  2. Metaspace unbounded
     Fix: -XX:MaxMetaspaceSize=256m

  3. Off-heap memory growth (Netty, NIO, caches)
     Fix: Limit off-heap explicitly, reduce container ratio to 60%

  4. JVM JIT code cache
     Fix: -XX:ReservedCodeCacheSize=128m (reduce if needed)

  5. Memory request < limit (Burstable + memory pressure)
     Fix: Set memory request = limit for Java pods

Diagnosis Workflow:

  Step 1: Check recent OOMKills
    kubectl get pods --all-namespaces | grep OOMKilled
  
  Step 2: Describe pod for details
    kubectl describe pod <pod> -n <namespace>
  
  Step 3: Check JVM heap dump (if configured)
    # Mount volume for heap dumps:
    volumes:
    - name: heap-dumps
      emptyDir: {}
    
    volumeMounts:
    - name: heap-dumps
      mountPath: /dumps
    
    # Then copy the dump out:
    kubectl cp <pod>:/dumps/heap.hprof ./heap.hprof
  
  Step 4: Analyze with Eclipse MAT or VisualVM
    Look for: Large retained objects, classloader leaks, unbounded caches

  Step 5: Add -XX:+ExitOnOutOfMemoryError
    JVM throws OOM → exit cleanly → Kubernetes restarts pod
    vs. JVM limps along with OOM → degraded state → user-facing errors

Prevention Checklist:
  ☐ Memory request == Memory limit for all Java pods
  ☐ MaxRAMPercentage ≤ 75%
  ☐ MaxMetaspaceSize set explicitly
  ☐ HeapDumpOnOutOfMemoryError + PVC for dumps
  ☐ ExitOnOutOfMemoryError to fail fast
  ☐ Liveness probe to restart degraded pods
  ☐ Memory usage alerts in Prometheus/Grafana (alert at 80% of limit)

10. JVM STARTUP TIME AND KUBERNETES PROBES
================================================================================

JVM Startup Time Problem:

  Cold JVM startup = 10-30 seconds for large Spring Boot apps
  Kubernetes readiness probe may fail during startup → pod restarts → 
    restart loop (CrashLoopBackOff)

Solution: initialDelaySeconds / startupProbe

  # BAD (no startup probe — readiness fails during JVM warmup):
  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    initialDelaySeconds: 10    # Not enough for large apps!
    periodSeconds: 5
  
  # GOOD — Use startupProbe to give JVM time to start:
  startupProbe:
    httpGet:
      path: /actuator/health
      port: 8080
    failureThreshold: 30        # 30 × 10s = 5 minutes maximum
    periodSeconds: 10
    initialDelaySeconds: 10     # Wait before first check
  
  livenessProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    failureThreshold: 3
    periodSeconds: 10
    successThreshold: 1
    timeoutSeconds: 5
  
  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    failureThreshold: 3
    periodSeconds: 5

Spring Boot Actuator Health Configuration:
  
  # application.yaml
  management:
    endpoint:
      health:
        probes:
          enabled: true            # Enables /liveness and /readiness
        show-details: always
    health:
      livenessState:
        enabled: true
      readinessState:
        enabled: true

JVM Warmup Strategies:

  1. Spring Boot lazy initialization:
     spring.main.lazy-initialization=true
     Reduces startup time but first requests are slow.
  
  2. JVM Class Data Sharing (CDS) / AppCDS:
     # Create archive:
     java -Xshare:dump -XX:DumpLoadedClassList=classes.lst ...
     java -XX:SharedClassListFile=classes.lst -XX:SharedArchiveFile=app.jsa ...
     
     # Use archive:
     java -Xshare:on -XX:SharedArchiveFile=app.jsa ...
     
     Reduces startup time 20-50% for Spring Boot apps.
  
  3. GraalVM Native Image:
     Compile-time native binary — startup in milliseconds.
     (see section 11)
  
  4. Class preloading (Java 21+):
     Experimental class preloading with JVM checkpointing (Project Leyden).

11. GRAALVM NATIVE IMAGE IN KUBERNETES
================================================================================

What is GraalVM Native Image?

  Compiles Java bytecode to a standalone native binary at build time.
  No JVM at runtime — binary starts in < 100ms, uses 10x less memory.

Benefits for Kubernetes:
  ✅ Startup: ~50ms vs 15-30 seconds (JVM)
  ✅ Memory: 50-100MB vs 500MB+ (JVM)
  ✅ Fast horizontal scaling (no warmup delay)
  ✅ Smaller container images (no JDK needed)
  ✅ Ideal for Lambda-style / scale-to-zero (KEDA)

Limitations:
  ❌ Dynamic class loading not supported (reflection must be configured)
  ❌ Build time is slow (minutes)
  ❌ Lower peak throughput vs JIT-compiled JVM (no adaptive optimization)
  ❌ Harder to debug in production
  ❌ Some libraries not supported (runtime proxy generation, etc.)

Spring Boot + Native (Spring Boot 3.x + GraalVM):
  
  # Build native image:
  ./mvnw spring-boot:build-image -Pnative   # Using Buildpacks
  # or
  ./mvnw native:compile -Pnative            # Using GraalVM native-image directly
  
  # pom.xml:
  <plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
    <version>0.10.0</version>
    <extensions>true</extensions>
  </plugin>

Kubernetes Deployment:
  
  # Much smaller resource requirements:
  resources:
    requests:
      memory: "128Mi"
      cpu: "100m"
    limits:
      memory: "256Mi"
      cpu: "500m"
  
  # Much faster probes:
  startupProbe:
    httpGet:
      path: /actuator/health
      port: 8080
    failureThreshold: 3     # Only 3 attempts (starts fast)
    periodSeconds: 2

When to Use Native vs JVM in K8s:
  
  ┌──────────────────────────┬─────────────────────────────┐
  │ Use JVM                  │ Use Native Image             │
  ├──────────────────────────┼─────────────────────────────┤
  │ High-throughput services │ Bursty / event-driven        │
  │ Complex reflection use   │ Simple REST / CRUD APIs      │
  │ Long-running services    │ Serverless / FaaS            │
  │ Dynamic proxies (Spring) │ Memory-constrained env       │
  │ Peak perf matters most   │ Fast startup critical        │
  └──────────────────────────┴─────────────────────────────┘

13. KUBERNETES-SPECIFIC JVM PATTERNS (JAVA 17–21)
================================================================================

Java 21 Virtual Threads in Kubernetes:

  Traditional: 1 OS thread per Java thread → expensive
  Virtual threads: Many virtual threads mapped to few OS threads → cheap
  
  impact on container sizing:
    Old (100 threads × 512KB): 50MB for thread stacks
    New (10,000 virtual threads × ~1KB): ~10MB for thread stacks
    
    Can DRAMATICALLY reduce thread stack memory requirements.
    Set -Xss to 512k (default) or even smaller for virtual threads.
  
  Spring Boot 3.2+ virtual threads:
    spring.threads.virtual.enabled=true
    → All @Async, Tomcat, scheduler threads become virtual

Kubernetes Downward API — Pod Info in JVM:

14. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: A Java application in Kubernetes keeps getting OOMKilled. Walk me through
    your debugging process.

A: Systematic approach:
   
   1. Confirm OOMKill:
      kubectl describe pod <name> → look for "OOMKilled" in Last State.
      Exit code 137 confirms kernel OOM killer.
   
   2. Check limits vs actual usage:
      kubectl top pod <name>
      Compare to resources.limits.memory in deployment YAML.
   
   3. Check JVM heap configuration:
      Is MaxRAMPercentage set? If not, JVM may be sizing heap to host memory.
      Is -Xmx set higher than container limit? → fatal.
      What Java version? Pre-8u191 → no container awareness.
   
   4. Check Metaspace:
      Is -XX:MaxMetaspaceSize set? Unbounded Metaspace is a common OOM cause.
   
   5. Off-heap analysis:
      Is the app using Netty/NIO? Large caches? Could be off-heap OOM.
      Even if heap is fine, native memory can grow.
   
   6. Get a heap dump:
      Add -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/
      Analyze with Eclipse Memory Analyzer Tool (MAT).
   
   7. Fix:
      Set memory request = memory limit.
      Add -XX:MaxRAMPercentage=75 -XX:MaxMetaspaceSize=256m -XX:+ExitOnOutOfMemoryError.

---

Q2: Why should you avoid setting a fixed -Xmx in a Kubernetes deployment?

A: Fixed -Xmx breaks the Kubernetes resource model:
   
   1. If -Xmx is too high (e.g., -Xmx1g in a 512Mi container):
      JVM tries to allocate 1GB → OOMKilled immediately on startup.
   
   2. If -Xmx is too low (e.g., -Xmx256m in a 2Gi container):
      JVM only uses 256MB heap even though 2Gi is available.
      Causes excessive GC and poor throughput — wasting paid resources.
   
   3. If you change the container limit, you must also update -Xmx:
      Manual synchronization → operational overhead → configuration drift.
   
   Solution: Use -XX:MaxRAMPercentage=75.0
   JVM reads container memory limit and calculates 75% of it.
   Change the resource limit → heap adapts automatically.
   Single source of truth: the Kubernetes pod spec.

---

Q3: What happens to JVM thread pools when container CPU limit is set to 1?

A: With -XX:+UseContainerSupport (Java 10+):
   
   Runtime.getRuntime().availableProcessors() returns 1 (from cgroup limit).
   
   Effects:
   - ForkJoinPool.commonPool(): 0 threads (max(1, cores-1) = 0 → uses 1)
   - G1GC parallel threads: ~1-2 threads
   - Spring's default async executor: 1 thread
   - Parallel streams: run on 1 thread (sequential effectively)
   
   Real-world impact:
   If your app relies on parallelism (parallel streams, CompletableFuture),
   it runs sequentially with CPU limit = 1.
   Increase CPU limit or use explicitly sized thread pools.

---

Q4: What's the difference between JVM OOM and container OOMKill?

A: Two different OOM mechanisms:
   
   JVM OOM (java.lang.OutOfMemoryError):
   - JVM's internal heap exhausted
   - Throws OutOfMemoryError, caught by application
   - JVM keeps running (degraded state)
   - With -XX:+ExitOnOutOfMemoryError: JVM exits cleanly with code 1
   - With -XX:+HeapDumpOnOutOfMemoryError: heap dump written first
   
   Container OOMKill (Linux kernel OOM Killer):
   - Container's cgroup memory limit exceeded
   - Kernel kills the process immediately (SIGKILL, exit code 137)
   - No graceful shutdown, no heap dump (usually)
   - Cannot be caught or handled by the JVM
   
   With -XX:MaxRAMPercentage=75%:
   JVM OOM would fire when heap is full (~75% of limit).
   Remaining 25% is buffer for non-heap memory.
   Container OOMKill should NOT occur if percentages are set correctly.
   
   Key insight: -XX:+ExitOnOutOfMemoryError is better than OOMKill
   because it allows graceful shutdown, heap dump collection, and
   Kubernetes to restart the pod cleanly.

---

Q5: How do you right-size a Java pod in Kubernetes?

A: Systematic right-sizing process:
   
   1. Deploy with generous limits and monitor:
      Initial: request=512Mi/500m, limit=2Gi/2
   
   2. Add Prometheus + JVM Micrometer metrics.
   
   3. Run load tests (representative production traffic).
   
   4. Observe for 1-2 weeks:
      - Peak heap usage (jvm_memory_used_bytes)
      - GC frequency and pause times
      - CPU utilization and throttling
      - container_memory_working_set_bytes (total container memory)
   
   5. Set limits:
      Memory limit = peak container memory × 1.3 (30% headroom)
      Memory request = memory limit (prevent Burstable QoS for Java)
      CPU request = average CPU usage × 1.2
      CPU limit = peak CPU × 1.5 (some burst headroom)
   
   6. Update MaxRAMPercentage accordingly.
   
   7. Use VPA (Vertical Pod Autoscaler) in recommendation mode:
      Provides automated right-sizing recommendations.

  75% heap + 256MB Metaspace + ~200MB other → use 2x heap as container limit

  Container support default ON: Java 10+
  Backported to Java 8: 8u191+
  ZGC GA: Java 15+
  Virtual Threads: Java 21+

  ✅ memory request == memory limit
  ✅ MaxRAMPercentage ≤ 75%
  ✅ MaxMetaspaceSize ≤ 256m
  ✅ ExitOnOutOfMemoryError ON
  ✅ HeapDumpOnOutOfMemoryError ON
