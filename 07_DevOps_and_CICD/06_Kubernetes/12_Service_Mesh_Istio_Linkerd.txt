1. WHAT IS A SERVICE MESH AND WHY USE ONE
================================================================================

The Problem Without a Service Mesh:

  In a microservices architecture, every service needs to handle:
  - Retries and timeouts
  - Circuit breaking
  - TLS/mTLS encryption between services
  - Load balancing
  - Distributed tracing context propagation
  - Rate limiting
  - Canary deployments at service level
  
  WITHOUT a service mesh:
  Every team implements these separately in application code.
  Different languages, different libraries, different behavior.
  No unified visibility across the entire service graph.

What a Service Mesh Does:

  Moves CROSS-CUTTING CONCERNS out of application code into the
  infrastructure layer (sidecar proxies).
  
  Application code focuses on BUSINESS LOGIC.
  Sidecar proxy handles: retries, mTLS, tracing, load balancing.

Service Mesh Components:
  
  DATA PLANE:
    Sidecar proxies (Envoy for Istio, Linkerd-proxy for Linkerd)
    Intercept all inbound/outbound traffic from each pod
    Apply traffic policies, collect telemetry
  
  CONTROL PLANE:
    Configures all data plane proxies
    Distributes certificates (mTLS)
    Provides APIs for configuration
    Istiod (Istio), Linkerd control plane

Service Mesh Capabilities:

  ┌─────────────────────────────┬──────────────────────────────────┐
  │ Capability                  │ What It Gives You                │
  ├─────────────────────────────┼──────────────────────────────────┤
  │ mTLS                        │ Encrypted, authenticated svc-svc │
  │ Traffic management          │ Canary, A/B, weight-based routing│
  │ Circuit breaking            │ Fail fast on downstream failures  │
  │ Retries and timeouts        │ Declarative, not in app code     │
  │ Observability               │ Automatic metrics + tracing      │
  │ Rate limiting               │ Per-service rate controls        │
  │ Service discovery           │ Built-in (uses K8s DNS)          │
  │ Multi-cluster routing       │ Route across clusters/regions    │
  └─────────────────────────────┴──────────────────────────────────┘

When NOT to Use a Service Mesh:
  - Small teams with < 5 microservices
  - Simple monolith or monolith-to-microservice early stage
  - High-throughput, ultra-low-latency systems (sidecar adds ~1ms)
  - Teams without ops expertise to maintain the mesh

2. SERVICE MESH ARCHITECTURE (SIDECAR PATTERN)
================================================================================

Sidecar Injection:

  Every application pod gets an automatically injected sidecar container
  (the proxy: Envoy for Istio, linkerd-proxy for Linkerd).
  
  Pod: [App Container] + [Sidecar Proxy]
  
  iptables rules redirect ALL traffic through the sidecar.
  App thinks it's talking directly to other services.
  Sidecar is transparent to application code.

Traffic Flow:
  
  Service A Pod                    Service B Pod
  ┌───────────────────┐            ┌───────────────────┐
  │  [App A]          │            │  [App B]          │
  │       ↕           │            │       ↕           │
  │  [Sidecar Envoy]  │◄──mTLS────►│  [Sidecar Envoy]  │
  └───────────────────┘            └───────────────────┘
  
  App A makes HTTP call → iptables intercepts → Sidecar A handles:
    - Outbound mTLS encryption
    - Load balancing (choose instance of Service B)
    - Retry logic
    - Timeout enforcement
    - Span creation for distributed tracing
    → Sends to Sidecar B of Service B
  
  Sidecar B handles:
    - Inbound mTLS decryption/verification
    - Rate limiting
    - Span extraction
    → Delivers plaintext to App B

Automatic Sidecar Injection (Istio):
  
  # Label namespace for auto-injection:
  kubectl label namespace my-namespace istio-injection=enabled
  
  # Or per-pod annotation:
  annotations:
    sidecar.istio.io/inject: "true"

3. ISTIO OVERVIEW AND ARCHITECTURE
================================================================================

Istio Components:

  istiod (Control Plane — single binary since Istio 1.5):
    - Pilot:    Service discovery → pushes routes to Envoy sidecars
    - Citadel:  Certificate management (mTLS PKI)
    - Galley:   Config validation and distribution
  
  Envoy Proxy (Data Plane):
    - C++ high-performance proxy
    - Handles all traffic
    - Listens on specific ports injected via iptables

Istio Custom Resources:
  
  VirtualService:      Traffic routing rules (where to send traffic)
  DestinationRule:     Policies for a destination (load balancing, mTLS, CB)
  Gateway:             Configure ingress/egress
  ServiceEntry:        Add external services to the mesh
  PeerAuthentication:  mTLS policies
  AuthorizationPolicy: Service-to-service access control
  RequestAuthentication: JWT validation

Install Istio:
  
  # Using istioctl (recommended):
  istioctl install --set profile=default
  
  # Profiles:
  #   minimal:    Just the control plane
  #   default:    Recommended for production
  #   demo:       Installs all addons (Kiali, Jaeger) — for learning
  
  # Verify:
  istioctl verify-install
  kubectl get pods -n istio-system

4. ISTIO TRAFFIC MANAGEMENT
================================================================================

VirtualService — Canary Deployment:

  # Route 90% to v1, 10% to v2:
  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: reviews-service
  spec:
    hosts:
    - reviews                         # K8s service name
    http:
    - route:
      - destination:
          host: reviews
          subset: v1                  # Defined in DestinationRule
        weight: 90
      - destination:
          host: reviews
          subset: v2
        weight: 10

DestinationRule — Define Subsets + Load Balancing:

  apiVersion: networking.istio.io/v1beta1
  kind: DestinationRule
  metadata:
    name: reviews-destination
  spec:
    host: reviews
    trafficPolicy:
      loadBalancer:
        simple: LEAST_CONN           # ROUND_ROBIN, LEAST_CONN, RANDOM, PASSTHROUGH
      connectionPool:
        tcp:
          maxConnections: 100
        http:
          http1MaxPendingRequests: 50
          http2MaxRequests: 1000
      outlierDetection:              # Circuit breaker config
        consecutiveErrors: 5
        interval: 30s
        baseEjectionTime: 30s
        maxEjectionPercent: 50
    subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2

Header-Based Routing (A/B Testing):

  # Route users with header "X-Beta-User: true" to v2:
  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: reviews-service
  spec:
    hosts:
    - reviews
    http:
    - match:
      - headers:
          x-beta-user:
            exact: "true"
      route:
      - destination:
          host: reviews
          subset: v2
    - route:                         # Default: everyone else to v1
      - destination:
          host: reviews
          subset: v1

Retry and Timeout Policies:

  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: payment-service
  spec:
    hosts:
    - payment-service
    http:
    - timeout: 5s                    # Overall request timeout
      retries:
        attempts: 3                  # Retry 3 times
        perTryTimeout: 2s            # Each attempt max 2s
        retryOn: >-
          gateway-error,connect-failure,retriable-4xx
      route:
      - destination:
          host: payment-service

Istio Ingress Gateway:

  # Expose service externally through Istio Gateway:
  apiVersion: networking.istio.io/v1beta1
  kind: Gateway
  metadata:
    name: my-gateway
  spec:
    selector:
      istio: ingressgateway
    servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: my-tls-cert   # K8s TLS secret
      hosts:
      - "api.mycompany.com"
  ---
  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: my-app-vs
  spec:
    hosts:
    - "api.mycompany.com"
    gateways:
    - my-gateway
    http:
    - route:
      - destination:
          host: my-app-service
          port:
            number: 8080

5. ISTIO MTLS AND SECURITY
================================================================================

What is mTLS?

  Mutual TLS: BOTH sides authenticate each other.
  Regular TLS: Client verifies server certificate.
  mTLS: Server also verifies client certificate.
  
  In a service mesh:
  Every service gets a SPIFFE-compliant identity certificate.
  Services authenticate each other using these certificates.
  All intra-mesh traffic is encrypted even on internal K8s network.

SPIFFE Identity:
  spiffe://cluster.local/ns/my-namespace/sa/my-service-account
  Format: spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>

PeerAuthentication — Enable mTLS:

  # STRICT mTLS for entire namespace:
  apiVersion: security.istio.io/v1beta1
  kind: PeerAuthentication
  metadata:
    name: default
    namespace: my-namespace
  spec:
    mtls:
      mode: STRICT      # STRICT=require mTLS, PERMISSIVE=allow plain or mTLS

  # Mesh-wide STRICT (in istio-system namespace):
  apiVersion: security.istio.io/v1beta1
  kind: PeerAuthentication
  metadata:
    name: default
    namespace: istio-system
  spec:
    mtls:
      mode: STRICT

AuthorizationPolicy — Zero-Trust Network:

  # Allow only "payment-service" to call "order-service":
  apiVersion: security.istio.io/v1beta1
  kind: AuthorizationPolicy
  metadata:
    name: order-service-authz
    namespace: default
  spec:
    selector:
      matchLabels:
        app: order-service
    action: ALLOW
    rules:
    - from:
      - source:
          principals:
            - "cluster.local/ns/default/sa/payment-service-account"
      to:
      - operation:
          methods: ["POST"]
          paths: ["/api/orders/*"]

JWT Validation:

  apiVersion: security.istio.io/v1beta1
  kind: RequestAuthentication
  metadata:
    name: jwt-auth
  spec:
    selector:
      matchLabels:
        app: my-api
    jwtRules:
    - issuer: "https://auth.mycompany.com"
      jwksUri: "https://auth.mycompany.com/.well-known/jwks.json"

6. ISTIO OBSERVABILITY
================================================================================

Automatic Telemetry (No Code Changes!):

  Istio sidecars automatically generate:
  
  METRICS (via Envoy → Prometheus):
    istio_requests_total               # Request count by source, dest, code
    istio_request_duration_milliseconds # Latency histogram
    istio_request_bytes                 # Request payload size
    istio_response_bytes                # Response payload size
  
  TRACES (via Envoy → Jaeger/Zipkin):
    Istio propagates trace headers (B3, W3C TraceContext)
    ⚠️ Apps must FORWARD trace headers to link spans across services
    (see section 10 for Spring Boot implementation)
  
  ACCESS LOGS:
    Every request logged by Envoy sidecar
    JSON format, includes: source, destination, status code, latency

Kiali — Service Mesh Observability Dashboard:

  Kiali is the official Istio UI:
  - Real-time service graph with traffic visualization
  - Health status per service
  - Traffic flow percentages
  - mTLS lock icons per connection
  - Circuit breaker status
  
  # Install:
  kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.20/samples/addons/kiali.yaml
  
  # Access:
  istioctl dashboard kiali

Istio + Grafana Dashboards:
  
  # Install Prometheus + Grafana:

  # Access:

7. ISTIO FAULT INJECTION AND CIRCUIT BREAKING
================================================================================

Fault Injection — Chaos Testing in Istio:

  # Inject 50% HTTP 500 errors for ratings service:
  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: ratings-vs
  spec:
    hosts:
    - ratings
    http:
    - fault:
        abort:
          percentage:
            value: 50.0
          httpStatus: 500
      route:
      - destination:
          host: ratings
  
  # Inject 7-second delay for 10% of requests:
  apiVersion: networking.istio.io/v1beta1
  kind: VirtualService
  metadata:
    name: ratings-vs
  spec:
    hosts:
    - ratings
    http:
    - fault:
        delay:
          percentage:
            value: 10.0
          fixedDelay: 7s
      route:
      - destination:
          host: ratings

Circuit Breaker via DestinationRule (OutlierDetection):

  apiVersion: networking.istio.io/v1beta1
  kind: DestinationRule
  metadata:
    name: reviews-cb
  spec:
    host: reviews
    trafficPolicy:
      connectionPool:
        tcp:
          maxConnections: 10        # Max concurrent connections
        http:
          http1MaxPendingRequests: 5
          http2MaxRequests: 100
          maxRetries: 3
      outlierDetection:
        consecutiveGatewayErrors: 5  # Eject after 5 consecutive errors
        consecutive5xxErrors: 5      # Or 5 5xx errors
        interval: 30s               # Check interval
        baseEjectionTime: 30s       # Minimum eject duration
        maxEjectionPercent: 50      # Max % of hosts to eject
        minHealthPercent: 30        # Stop ejecting if fewer healthy hosts

Difference from Resilience4j Circuit Breaker:
  
  Istio Circuit Breaker:       Infrastructure-level, language-agnostic
                               Counts connection/request errors to a service
  
  Resilience4j Circuit Breaker: Application-level, Java library
                                 Counts exceptions within the Java process
  
  RECOMMENDATION: Use both!
  Resilience4j: Fine-grained per-method circuit breaking, fallback logic
  Istio: Mesh-level protection, upstream service health management

8. LINKERD OVERVIEW
================================================================================

What is Linkerd?

  The CNCF-graduated, lightweight, ultra-simple service mesh.
  Written in Rust (linkerd2-proxy) — extremely fast and low memory.
  
  Design philosophy:
  "Ops should be able to understand the mesh."
  Linkerd chose simplicity over features vs Istio's power-over-simplicity.

Linkerd vs Istio Philosophy:
  Istio:   Full-featured, Envoy-based, complex, very configurable
  Linkerd: Simple, Rust-based proxy, fewer features, easier to operate

Install Linkerd:
  
  # Install CLI:
  curl --proto '=https' --tlsv1.2 -sSfL https://run.linkerd.io/install | sh
  
  # Pre-check:
  linkerd check --pre
  
  # Install:
  linkerd install --crds | kubectl apply -f -
  linkerd install | kubectl apply -f -
  
  # Verify:
  linkerd check
  
  # Inject sidecar (annotate namespace):
  kubectl annotate namespace my-namespace linkerd.io/inject=enabled

Linkerd Features:
  ✅ mTLS automatic (no config needed — default ON)
  ✅ Automatic metrics (HTTP success rate, latency, RPS)
  ✅ Traffic split (canary — SMI-compatible)
  ✅ Retries and timeouts via ServiceProfile
  ✅ Circuit breaking (upcoming in newer versions)
  ✅ Tap (live request inspection)
  ❌ No advanced L7 routing like Istio VirtualService
  ❌ No JWT validation built-in
  ❌ No fault injection

Linkerd CLI Commands:
  
  # View live traffic for a deployment:
  linkerd viz tap deploy/my-app
  
  # View top routes:
  linkerd viz top deploy/my-app
  
  # Service stats:
  linkerd viz stat deploy/my-app
  
  # View dashboard:
  linkerd viz dashboard

Linkerd ServiceProfile (Retries and Timeouts):
  
  apiVersion: linkerd.io/v1alpha2
  kind: ServiceProfile
  metadata:
    name: payment-service.default.svc.cluster.local
    namespace: default
  spec:
    routes:
    - name: POST /api/payments
      condition:
        method: POST
        pathRegex: /api/payments
      timeout: 5s
      isRetryable: false            # Don't retry payment calls!
    - name: GET /api/payments/{id}
      condition:
        method: GET
        pathRegex: /api/payments/.*
      timeout: 2s
      isRetryable: true             # Safe to retry GET

9. ISTIO VS LINKERD COMPARISON
================================================================================

  ┌─────────────────────────┬────────────────────────┬──────────────────────┐
  │ Feature                 │ Istio                  │ Linkerd              │
  ├─────────────────────────┼────────────────────────┼──────────────────────┤
  │ Proxy                   │ Envoy (C++)            │ linkerd2-proxy (Rust)│
  │ Proxy memory footprint  │ ~50-100MB per sidecar  │ ~10-15MB per sidecar │
  │ Proxy CPU overhead      │ Medium                 │ Very low             │
  │ mTLS                    │ Yes (config needed)    │ Yes (default ON)     │
  │ Traffic management      │ Rich (VS, DR, Gateway) │ Basic (ServiceProfile│
  │ Fault injection         │ Yes                    │ No                   │
  │ JWT validation          │ Yes                    │ No                   │
  │ WASM extensibility      │ Yes                    │ No                   │
  │ Multi-cluster           │ Yes (advanced)         │ Yes (basic)          │
  │ Learning curve          │ High                   │ Low                  │
  │ CNCF status             │ Graduated              │ Graduated            │
  │ Observability UI        │ Kiali                  │ Linkerd Viz          │
  │ SMI compatible          │ Via plugin             │ Native               │
  │ Best for                │ Complex requirements   │ Simplicity priority  │
  └─────────────────────────┴────────────────────────┴──────────────────────┘

When to Choose Istio:
  - Advanced traffic management (canary, A/B, header-based routing)
  - JWT/OIDC validation at mesh level
  - External service integration (ServiceEntry)
  - Multi-cluster with complex routing
  - Custom Envoy extensions (WASM filters)
  - You have a dedicated platform engineering team

When to Choose Linkerd:
  - Simplicity and low operational overhead
  - Low-resource environments (less sidecar overhead)
  - Quick mTLS enablement (default ON)
  - Smaller microservices architectures
  - Teams new to service mesh

10. SERVICE MESH FOR JAVA MICROSERVICES
================================================================================

Trace Header Propagation (Critical!):

  Istio/Linkerd create traces automatically BUT cannot link spans across
  services unless the app FORWARDS trace headers.
  
  The sidecar injects headers on inbound:
    x-request-id, x-b3-traceid, x-b3-spanid, x-b3-parentspanid,
    x-b3-sampled, x-b3-flags, x-ot-span-context
  
  Your Java app must forward these on outbound calls.

Spring Boot Auto-Propagation (with OpenTelemetry or Brave):
  
  # pom.xml:
  <dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
  </dependency>
  <dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
  </dependency>
  
  # Spring Boot auto-configures Brave tracing
  # Uses RestTemplate/WebClient that auto-propagates B3 headers
  
  # application.yaml:
  management:
    tracing:
      sampling:
        probability: 1.0      # 100% sampling (use 0.1 in production)
  spring:
    zipkin:
      base-url: http://zipkin.istio-system:9411

  # Using Spring Cloud Sleuth (Spring Boot 2.x):
  <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-sleuth</artifactId>
  </dependency>

Service Mesh vs Spring Cloud:

  Feature          │ Service Mesh (Istio)     │ Spring Cloud
  ─────────────────┼──────────────────────────┼──────────────────────
  Load balancing   │ Envoy (transparent)      │ Spring Cloud LoadBalancer
  Circuit breaking │ Outlier Detection        │ Resilience4j
  Retries          │ VirtualService retries   │ Resilience4j Retry
  Service discovery│ K8s DNS (transparent)    │ Eureka / Consul
  mTLS             │ Automatic                │ Manual cert management
  Language         │ Any (sidecar)            │ Java only
  Configuration    │ K8s YAML                 │ Java annotations / YAML
  Operational cost │ Mesh infrastructure      │ Library in each service

Recommendation for Java Microservices:
  
  DO NOT try to replace all Spring Cloud features with Istio.
  Use a layered approach:
  
  Layer 1 (Application): Resilience4j for in-JVM circuit breaking,
                         fallback logic, rate limiting per method
  Layer 2 (Mesh):        Istio for mTLS, canary deployments,
                         cross-service observability, L4/L7 routing
  
  They complement each other:
  Resilience4j handles business-logic-level failures.
  Istio handles infrastructure-level routing and security.

Health Checks with Istio:

  Istio sidecars can interfere with K8s probes.
  Istio 1.9+ rewrote probes to avoid this (no-op iptables for probes).
  If using older Istio, use exec probes instead of httpGet.

Sidecar Resource Configuration:
  
  # Control sidecar resources in namespace:
  kubectl annotate namespace my-namespace \
    "sidecar.istio.io/proxyCPU=100m" \
    "sidecar.istio.io/proxyMemory=128Mi" \
    "sidecar.istio.io/proxyCPULimit=200m" \
    "sidecar.istio.io/proxyMemoryLimit=256Mi"

11. SERVICE MESH VS SPRING CLOUD (RESILIENCE4J, RIBBON)
================================================================================

Historical Context:

  Spring Cloud Netflix (pre-2020):
    Ribbon:    Client-side load balancing
    Hystrix:   Circuit breaking (DEPRECATED)
    Eureka:    Service discovery
    Zuul:      API Gateway
  
  Spring Cloud Modern Stack:
    Spring Cloud LoadBalancer (replaces Ribbon)
    Resilience4j (replaces Hystrix)
    Spring Cloud Gateway (replaces Zuul)
    No built-in service discovery needed (use K8s DNS)

Does a Service Mesh REPLACE Spring Cloud?

  Partially, yes:
  ✅ Service discovery → K8s DNS replaces Eureka
  ✅ Load balancing → Envoy replaces Ribbon/Spring Cloud LB
  ✅ mTLS → Istio replaces Spring Security mutual TLS
  
  NO replacement:
  ❌ Circuit breaker fallback logic → still need Resilience4j
     (Istio CB just rejects requests; Resilience4j can execute fallback code)
  ❌ Application-level rate limiting → Resilience4j
  ❌ Retry with custom business logic → Resilience4j
  ❌ @Async, @Scheduled thread pools → Spring

Modern Architecture Pattern:
  
  Spring Boot app:
  + Resilience4j (circuit breaking, retry, rate limiting in-JVM)
  + Micrometer + OTel (metrics and traces)
  + Spring Cloud Gateway (API gateway at edge)
  
  + Kubernetes (orchestration)
  + Istio/Linkerd (mTLS, mesh-level routing, observability)
  
  Avoids:
  × Eureka (use K8s DNS)
  × Ribbon (use Envoy)
  × Spring Cloud Config (use K8s ConfigMaps/Vault)

12. EBPF-BASED SERVICE MESHES (CILIUM)
================================================================================

The Next Generation — Sidecar-Less:

  eBPF (extended Berkeley Packet Filter):
  Linux kernel technology to run programs safely in kernel space.
  Eliminates need for sidecar proxies entirely.

Cilium Service Mesh:
  Uses eBPF for observability and networking at kernel level.
  No sidecar injection required.
  Lower latency (no proxy hop) and less resource overhead.
  
  Capabilities:
  - L4 and L7 network policies (eBPF-based)
  - Transparent mTLS (without sidecar)
  - Service mesh (via Cilium Service Mesh mode)
  - Deep kernel-level observability (Hubble UI)

Istio + Ambient Mesh (Sidecar-less Istio):
  Istio 1.18+ introduced "ambient mode":
  Uses ztunnel (per-node proxy) + waypoint proxies (per-namespace).
  Eliminates per-pod sidecar overhead.
  Significant performance and resource improvement.

Senior Interview Tip:
  Knowing about eBPF and ambient mode shows you follow the ecosystem's
  evolution — a strong differentiator at senior/staff level interviews.

13. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What problem does a service mesh solve that you can't solve with just
    Resilience4j and Spring Security?

A: Service mesh solves cross-cutting infrastructure concerns at the PLATFORM
   level, not the application level.
   
   Key gaps that service mesh fills:
   
   1. mTLS across all services automatically:
      With Spring Security, each service must configure certificates, trust
      stores, and rotate certs manually. Istio provides a PKI that
      automatically issues and rotates SPIFFE certificates — zero config
      in the application.
   
   2. Language-agnostic:
      Resilience4j is Java-only. If you have a Python service talking to
      a Java service, the Python service needs its own circuit breaking lib.
      Istio's sidecar works regardless of language.
   
   3. Canary deployments at traffic level:
      Resilience4j can't split traffic 90/10 between v1/v2 of a service.
      Istio VirtualService does this declaratively.
   
   4. Unified observability:
      You'd need each team to correctly configure distributed tracing.
      Istio automatically generates L7 metrics for every request between
      every service pair — no code required.
   
   Complementary: Use BOTH. Resilience4j for fallback business logic,
   Istio for infrastructure-level protection and observability.

---

Q2: A distributed trace in Jaeger is broken — spans from service A and
    service B are not linked. What's the likely cause?

A: The application is not forwarding trace headers between services.
   
   Root cause: Istio injects trace headers (x-b3-traceid, x-b3-spanid)
   into INBOUND requests. But if your Java service makes an OUTBOUND
   HTTP call using a new RestTemplate without header propagation,
   those headers are NOT forwarded → new trace context starts → spans broken.
   
   Diagnosis:
   1. Intercept the outbound request (enable RestTemplate logging)
   2. Check if x-b3-traceid header is present in outbound request
   
   Fix:
   With Spring Boot + Micrometer Tracing (Spring Boot 3):
   → Auto-configured — use injected RestTemplate or WebClient bean.
   
   With Spring Cloud Sleuth (Spring Boot 2):
   → Use the Sleuth-instrumented RestTemplate/WebClient.
   → Never create new RestTemplate() manually.
   
   Manual fix:
   HttpServletRequest incoming = ...; // extract from thread-local
   // Copy Istio trace headers to outbound RestTemplate headers

Q3: How would you implement a canary deployment using Istio for a Java
    Spring Boot microservice?

A: Step-by-step:
   
   1. Deploy both versions with different labels:
      Deployment v1: labels: {app: payments, version: v1}
      Deployment v2: labels: {app: payments, version: v2}
      Both targeted by: Service payments (selector: app: payments)
   
   2. Create DestinationRule to define subsets:
      subsets:
      - name: v1
        labels: {version: v1}
      - name: v2
        labels: {version: v2}
   
   3. Create VirtualService with traffic split:
      http:
      - route:
        - destination: {host: payments, subset: v1}
          weight: 90
        - destination: {host: payments, subset: v2}
          weight: 10
   
   4. Monitor via Kiali/Grafana:
      Watch error rate, latency of v2 vs v1
      Prometheus queries: istio_requests_total by version
   
   5. Gradually shift traffic:
      80/20 → 50/50 → 100/0
      Update VirtualService weights incrementally.
   
   6. If problems: set weight back to 100% v1 (instant rollback)
   
   Integration with CI/CD:
   Use Flagger (built on Istio) for automated canary promotion/rollback
   based on Prometheus metrics.

Q4: What is mTLS and why does Istio make it easier than doing it yourself?

A: mTLS (Mutual TLS):
   Both client AND server present X.509 certificates.
   Each side verifies the other's identity before communicating.
   All traffic is encrypted in transit.
   
   Without Istio (manual mTLS):
   - Generate CA and service certificates
   - Distribute certs to all services as secrets
   - Configure each service's TLS settings
   - Implement certificate rotation (certs expire!)
   - Update trust stores when adding new services
   - Handle cert rotation without downtime
   → Very complex, error-prone, operational burden
   
   With Istio:
   - Citadel (part of istiod) acts as a PKI CA
   - Automatically issues SPIFFE identity certs to every service
   - Cert rotation is automatic (before expiry)
   - Sidecars handle TLS negotiation transparently
   - Set PeerAuthentication: STRICT → done
   → Zero application code changes required
