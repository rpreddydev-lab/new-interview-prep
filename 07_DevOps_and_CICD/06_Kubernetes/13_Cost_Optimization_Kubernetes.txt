1. WHY COST OPTIMIZATION MATTERS FOR JAVA DEVELOPERS
================================================================================

Cloud costs are directly tied to Kubernetes resource reservations.
Java applications are often the biggest offenders because:

  Problem 1: JVM heap over-provisioning
    Developers set -Xmx4g "just to be safe" → requests.memory=4Gi for the Pod.
    Actual usage: 800MB. You're paying for 4GB but using 0.8GB.
    At scale (50 pods): 200GB reserved, 40GB used. 80% waste.

  Problem 2: No requests/limits set
    Kubernetes scheduler can't make good placement decisions.
    Pods land on wrong nodes, cluster autoscaler doesn't work correctly.
    Can lead to OOMKilled or CPU throttling.

  Problem 3: Overprovisioned nodes that run 24/7
    Dev/staging clusters run at full capacity overnight and weekends.
    Use spot instances + cluster scale-to-zero for non-prod savings.

  Business impact:
    A startup running 20 microservices on AWS EKS:
    Without optimization: $5,000-10,000/month
    With optimization: $1,500-3,000/month (60-70% savings)

2. UNDERSTANDING KUBERNETES RESOURCE COSTS
================================================================================

How AWS/GCP/Azure Charges for Kubernetes:

  You pay for EC2 instances (nodes), not individual pods.
  The cluster determines how many nodes to provision based on pod resource requests.
  
  Cost formula:
  Total cost = Number of nodes × Node hourly price × Hours running
  
  Node count determined by:
  Sum of all pod requests.cpu → drives CPU node count
  Sum of all pod requests.memory → drives memory node count

Resource Request Impact:

  Example: 10 pods, each with requests.cpu=1, requests.memory=2Gi
  
  Without node overhead: 10 CPU, 20Gi memory needed
  With K8s system overhead (~10%): 11 CPU, 22Gi
  
  AWS m5.2xlarge: 8 vCPU, 32GB RAM, ~$0.38/hr
  Minimum nodes needed: 2 (for CPU) → 2 × $0.38 = $0.76/hr = ~$550/month
  
  If you right-size to requests.cpu=0.5, requests.memory=1Gi:
  5 CPU, 10Gi needed → 1 node → $0.38/hr = ~$275/month (50% savings!)

Node Utilization (The Hidden Metric):

  Ideally: 70-80% CPU and memory utilization on nodes.
  Common reality: 20-40% (massively over-provisioned).
  
  # Check actual node utilization:
  kubectl top nodes
  
  # Check pod actual usage vs requests:
  kubectl top pods --all-namespaces
  
  # Pod using 200m CPU but requesting 1000m CPU → 5x over-provisioned!

3. RESOURCE REQUESTS AND LIMITS (THE FOUNDATION)
================================================================================

Definitions:

  requests.cpu:    "I need at least this much CPU" → Scheduling guarantee
  limits.cpu:      "I can never use more than this" → Hard cap (throttled)
  requests.memory: "I need at least this much RAM" → Scheduling guarantee
  limits.memory:   "If I exceed this → OOMKilled"

Best Practices:

  1. Always set requests and limits.
  2. For CPU: limit can be 2-4x request (burst allowed, but throttled).
  3. For memory: limit = request for JVM apps (JVM's heap is predictable).
  4. Use Guaranteed QoS for production (request == limit).

QoS Classes (Kubernetes Priority):

  ┌──────────────────┬───────────────────────────┬────────────────────────┐
  │ QoS Class        │ Condition                 │ Eviction Priority      │
  ├──────────────────┼───────────────────────────┼────────────────────────┤
  │ Guaranteed       │ requests == limits        │ Last to be evicted     │
  │                  │ (both CPU and memory)     │ (safest for prod)      │
  ├──────────────────┼───────────────────────────┼────────────────────────┤
  │ Burstable        │ requests != limits        │ Evicted if node under  │
  │                  │ OR only requests set      │ memory pressure        │
  ├──────────────────┼───────────────────────────┼────────────────────────┤
  │ BestEffort       │ No requests or limits     │ FIRST to be evicted!   │
  └──────────────────┴───────────────────────────┴────────────────────────┘

Right-Sizing for Spring Boot:

  # Measure actual usage first:
  kubectl top pod order-service-7d4f8 --containers
  
  # Sample: 350m CPU, 420Mi memory (under normal load)
  # Peak: 800m CPU, 650Mi memory (under load)
  
  # Well-sized deployment:
  resources:
    requests:
      memory: "512Mi"          # 20% buffer above average
      cpu: "400m"              # Match average usage
    limits:
      memory: "768Mi"          # 20% buffer above peak
      cpu: "1000m"             # 2.5x request (allow CPU burst)

CPU Throttling vs OOMKilled:

  CPU exceeded limit → THROTTLED (process slows, but continues)
    Symptom: High latency, slow response times
    Fix: Increase CPU limit or optimize code
  
  Memory exceeded limit → OOMKilled (pod restarted immediately)
    Symptom: Pod restarts, CrashLoopBackOff
    Fix: Increase memory limit or fix memory leak

4. LIMITRANGE AND RESOURCEQUOTA (NAMESPACE-LEVEL CONTROLS)
================================================================================

LimitRange (Default Limits for Containers):

  Applies defaults when containers don't specify limits.
  Prevents "BestEffort" pods from being accidentally deployed.
  
  apiVersion: v1
  kind: LimitRange
  metadata:
    name: default-limits
    namespace: production
  spec:
    limits:
      - type: Container
        default:                  # Applied if container sets no limits
          cpu: "500m"
          memory: "512Mi"
        defaultRequest:           # Applied if container sets no requests
          cpu: "100m"
          memory: "128Mi"
        max:                      # Container cannot exceed these
          cpu: "4"
          memory: "4Gi"
        min:                      # Container must request at least these
          cpu: "50m"
          memory: "64Mi"
      
      - type: Pod                 # Pod-level limits
        max:
          cpu: "8"
          memory: "8Gi"

ResourceQuota (Namespace-Level Caps):

  Prevents one team's namespace from consuming all cluster resources.
  
  # Production namespace: generous limits
  apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: prod-quota
    namespace: production
  spec:
    hard:
      requests.cpu: "20"         # Total CPU requests across all pods
      requests.memory: 40Gi     # Total memory requests
      limits.cpu: "40"           # Total CPU limits
      limits.memory: 80Gi
      pods: "100"                # Max 100 pods
      services: "20"
      persistentvolumeclaims: "20"
      count/deployments.apps: "50"
  
  ---
  
  # Development namespace: tight limits
  apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: dev-quota
    namespace: development
  spec:
    hard:
      requests.cpu: "4"
      requests.memory: 8Gi
      limits.cpu: "8"
      limits.memory: 16Gi
      pods: "20"

Check Quota Usage:

  kubectl describe quota -n production
  # Shows: RESOURCE | REQUEST | LIMIT | % used

5. VERTICAL POD AUTOSCALER (VPA) FOR RIGHT-SIZING
================================================================================

What is VPA?

  VPA automatically recommends (or sets) resource requests and limits
  for containers based on ACTUAL historical usage.
  
  Three VPA modes:
  - Off:        Only provides recommendations (no action)
  - Initial:    Sets requests only when Pod is first created
  - Auto:       Continuously adjusts (restarts pod to apply changes)
  
  Note: "Auto" mode restarts pods → NOT recommended for production without
  disruption budget control. Use "Off" or "Initial" in prod, "Auto" in dev.

VPA Resource:

  apiVersion: autoscaling.k8s.io/v1
  kind: VerticalPodAutoscaler
  metadata:
    name: order-service-vpa
    namespace: production
  spec:
    targetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: order-service
    updatePolicy:
      updateMode: "Off"           # Recommendation only (safe for prod)
    resourcePolicy:
      containerPolicies:
        - containerName: order-service
          minAllowed:
            cpu: 100m             # Never recommend less than this
            memory: 128Mi
          maxAllowed:
            cpu: 4               # Never recommend more than this
            memory: 4Gi
          controlledResources:
            - cpu
            - memory

Read VPA Recommendations:

  kubectl describe vpa order-service-vpa -n production
  
  # Output (example):
  #   Container recommendations:
  #     Container Name:  order-service
  #     Lower Bound:
  #       Cpu:     215m
  #       Memory:  384Gi          ← Oops, this is probably too high; check actual
  #     Target:
  #       Cpu:     377m           ← VPA's recommended CPU request
  #       Memory:  512Mi          ← VPA's recommended memory request
  #     Upper Bound:
  #       Cpu:     1
  #       Memory:  1Gi

Using VPA Recommendations to Right-Size Manually:

  # Best workflow for production:
  1. Set VPA to "Off" mode on all deployments
  2. Run for 1-2 weeks (gather usage data)
  3. Review recommendations: kubectl describe vpa -n prod
  4. Manually update resource requests in values.yaml based on recommendations
  5. Deploy during low-traffic window

6. HORIZONTAL POD AUTOSCALER (HPA) FOR EFFICIENT SCALING
================================================================================

HPA = Scale based on metrics (CPU, memory, custom metrics).
Never pay for idle capacity during low traffic.

Basic HPA (CPU-Based):

  apiVersion: autoscaling/v2
  kind: HorizontalPodAutoscaler
  metadata:
    name: order-service-hpa
  spec:
    scaleTargetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: order-service
    minReplicas: 2               # Always have 2 for HA
    maxReplicas: 20
    metrics:
      - type: Resource
        resource:
          name: cpu
          target:
            type: Utilization
            averageUtilization: 70    # Scale when avg CPU > 70% of request

HPA with Custom Metrics (RPS, Queue Length):

  # Scale based on number of HTTP requests per second:
  metrics:
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"    # Scale when each pod handles > 100 req/s
  
  # Scale based on Kafka consumer lag:
  - type: External
    external:
      metric:
        name: kafka_consumer_lag
        selector:
          matchLabels:
            topic: orders
      target:
        type: AverageValue
        averageValue: "1000"   # Scale when lag > 1000 messages

KEDA (Kubernetes Event Driven Autoscaling):

  KEDA extends HPA with dozens of scalers (Kafka, RabbitMQ, Cron, AWS SQS).
  Scale to ZERO when idle (massive cost saving for dev/batch workloads).
  
  apiVersion: keda.sh/v1alpha1
  kind: ScaledObject
  metadata:
    name: order-processor-scaler
  spec:
    scaleTargetRef:
      name: order-processor
    minReplicaCount: 0          # Scale to ZERO when no messages!
    maxReplicaCount: 20
    triggers:
      - type: kafka
        metadata:
          topic: orders
          bootstrapServers: kafka:9092
          consumerGroup: order-processor
          lagThreshold: "50"    # 1 replica per 50 messages lag

Cost Impact of HPA:

  Without HPA: 10 replicas × 24h = 240 pod-hours/day
  With HPA (min 2, max 10, avg 4): ~100 pod-hours/day (58% savings!)

7. SPOT/PREEMPTIBLE INSTANCES IN KUBERNETES
================================================================================

What Are Spot Instances?

  Cloud providers sell unused capacity at 60-90% discount.
  Trade-off: Instance can be reclaimed (terminated) with 2-minute warning.
  
  AWS Spot:     Up to 90% cheaper than On-Demand
  GCP Spot VM:  Up to 91% cheaper
  Azure Spot:   Up to 90% cheaper

Spot Instance Strategy for Kubernetes:

  Don't put ALL workloads on spot. Mix:
  
  ┌───────────────────────┬──────────────────┬──────────────────────────┐
  │ Workload              │ Instance Type    │ Rationale                │
  ├───────────────────────┼──────────────────┼──────────────────────────┤
  │ Stateless services    │ 70% spot +       │ Can tolerate disruption  │
  │ (Spring Boot REST)    │ 30% on-demand    │ with proper HPA + health │
  │                       │                  │ checks                   │
  ├───────────────────────┼──────────────────┼──────────────────────────┤
  │ Databases, StatefulSets│ On-Demand only  │ Data loss risk too high  │
  ├───────────────────────┼──────────────────┼──────────────────────────┤
  │ CI/CD runners         │ 100% Spot        │ Build failure = retry    │
  ├───────────────────────┼──────────────────┼──────────────────────────┤
  │ Dev/staging cluster   │ 100% Spot        │ Occasional restarts OK   │
  ├───────────────────────┼──────────────────┼──────────────────────────┤
  │ Batch/ML workloads    │ 100% Spot        │ Designed for interruption│
  └───────────────────────┴──────────────────┴──────────────────────────┘

Kubernetes Node Labels for Spot:

  # AWS EKS Managed Node Group with Spot + On-Demand:
  # nodegroup-spot:    spot instances, labeled node.kubernetes.io/lifecycle=spot
  # nodegroup-ondemand: on-demand, labeled node.kubernetes.io/lifecycle=normal

  # Deploy Spring Boot on spot nodes:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: "node.kubernetes.io/lifecycle"
                operator: In
                values: ["spot"]

  # Critical stateful services on on-demand ONLY:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: "node.kubernetes.io/lifecycle"
                operator: In
                values: ["normal"]    # on-demand only

Handling Spot Interruptions Gracefully:

  1. Pod Disruption Budget (PDB):
  
  apiVersion: policy/v1
  kind: PodDisruptionBudget
  metadata:
    name: order-service-pdb
  spec:
    minAvailable: 2              # At least 2 pods must stay up during disruption
    selector:
      matchLabels:
        app: order-service
  
  2. Multiple Instance Types (diversification):
  
  # Karpenter NodePool with multiple instance types:
  # If one instance type is unavailable (no spot capacity), try others.
  
  3. Spread across zones:
  
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app: order-service
  
  4. Graceful shutdown for Java apps:
     # Pod gets SIGTERM 2 minutes before spot reclamation.
     # Spring Boot: handle graceful shutdown (in-flight requests complete)
     server.shutdown=graceful
     spring.lifecycle.timeout-per-shutdown-phase=30s

8. KARPENTER — INTELLIGENT NODE AUTOPROVISIONING
================================================================================

What is Karpenter?

  Karpenter is an open-source Kubernetes node autoprovisioner built by AWS
  (but usable with Azure, GCP via adapters).
  
  vs Cluster Autoscaler:
  Cluster Autoscaler: Adds nodes from pre-defined node groups.
  Karpenter: Creates right-sized nodes on demand based on pending pods.

Karpenter Benefits:

  ✓ Provisions nodes in <60 seconds (vs minutes with Cluster Autoscaler)
  ✓ Right-sizes nodes exactly for pending pod requirements
  ✓ Automatically selects cheapest instance type for the workload
  ✓ Consolidates underutilized nodes (bin-packing)
  ✓ Handles spot interruptions and automatic replacements
  ✓ Multi-architecture support (ARM64 Graviton for 20-40% cost savings)

NodePool (Defines How Karpenter Provisions Nodes):

  apiVersion: karpenter.sh/v1beta1
  kind: NodePool
  metadata:
    name: general-purpose
  spec:
    template:
      spec:
        requirements:
          # Allow any of these instance families:
          - key: karpenter.k8s.aws/instance-family
            operator: In
            values: [m5, m5d, m6i, m6id, m7i, c5, c6i]
          
          # Allow any size:
          - key: karpenter.k8s.aws/instance-size
            operator: In
            values: [large, xlarge, 2xlarge, 4xlarge]
          
          # Prefer ARM (Graviton) for 20% cost savings:
          - key: kubernetes.io/arch
            operator: In
            values: [arm64, amd64]
          
          # 80% spot, 20% on-demand:
          - key: karpenter.sh/capacity-type
            operator: In
            values: [spot, on-demand]
          
          # Only AZs with available EBS:
          - key: topology.kubernetes.io/zone
            operator: In
            values: [us-east-1a, us-east-1b, us-east-1c]
        
        nodeClassRef:
          apiVersion: karpenter.k8s.aws/v1beta1
          kind: EC2NodeClass
          name: default
    
    limits:
      cpu: 1000             # Max total CPU in this NodePool
    
    disruption:
      consolidationPolicy: WhenUnderutilized   # Delete underutilized nodes
      consolidateAfter: 30s                    # Wait 30s before consolidating

EC2NodeClass (AWS-Specific Config):

  apiVersion: karpenter.k8s.aws/v1beta1
  kind: EC2NodeClass
  metadata:
    name: default
  spec:
    amiFamily: AL2          # Amazon Linux 2
    role: KarpenterNodeRole
    subnetSelectorTerms:
      - tags:
          karpenter.sh/discovery: my-cluster
    securityGroupSelectorTerms:
      - tags:
          karpenter.sh/discovery: my-cluster
    blockDeviceMappings:
      - deviceName: /dev/xvda
        ebs:
          volumeSize: 50Gi
          volumeType: gp3
          encrypted: true

Karpenter Node Consolidation:

  # Karpenter actively removes underutilized nodes.
  # Example: 3 nodes each at 30% utilization → consolidate to 1 at 90%
  # This happens automatically with consolidationPolicy: WhenUnderutilized.
  
  # Cost impact: No more idle nodes! Pay only for what you use.

9. CLUSTER AUTOSCALER VS KARPENTER
================================================================================

  ┌─────────────────────────┬──────────────────────────┬──────────────────────┐
  │ Feature                 │ Cluster Autoscaler       │ Karpenter            │
  ├─────────────────────────┼──────────────────────────┼──────────────────────┤
  │ Node provisioning time  │ 3-10 minutes             │ < 60 seconds         │
  │ Instance selection      │ Predefined node groups   │ Just-in-time, optimal│
  │ Right-sizing            │ Node group sizes only    │ Any instance type    │
  │ Spot support            │ Via node groups          │ Native, intelligent  │
  │ Node consolidation      │ Limited                  │ Excellent (built-in) │
  │ ARM/Graviton support    │ Via node groups          │ Native               │
  │ Cloud providers         │ All major               │ AWS (best), Azure, GCP│
  │ Maturity                │ Very mature              │ Newer but production- │
  │                         │                          │ ready                │
  │ Complexity              │ Lower                    │ Higher               │
  └─────────────────────────┴──────────────────────────┴──────────────────────┘

When to Use Each:

  Cluster Autoscaler: When you need proven, widely-supported node scaling.
                      Multi-cloud required. Simple setup priorities.
  
  Karpenter: AWS EKS, optimizing costs aggressively, want spot diversification.
             Large clusters where node provisioning latency matters.

10. KUBECOST AND OPENCOST — COST VISIBILITY
================================================================================

Why Cost Visibility Tools?

  Without cost tools: "Our AWS bill is $50,000/month. Who's responsible?"
  With cost tools:    "order-service in prod: $1,200/month
                       cart-service in dev: $3,500/month (WAY too much!)"

Kubecost:

  Kubecost integrates with Prometheus metrics to show cost per:
  - Namespace
  - Deployment / Pod
  - Label (team, environment, feature)
  - PersistentVolume
  
  Installation:
  helm repo add kubecost https://kubecost.github.io/cost-analyzer/
  helm install kubecost kubecost/cost-analyzer \
    --namespace kubecost \
    --set kubecostToken="${KUBECOST_TOKEN}"
  
  # Port-forward to access dashboard:
  kubectl port-forward deployment/kubecost-cost-analyzer 9090 -n kubecost
  # Open: http://localhost:9090

OpenCost (CNCF Sandbox):

  OpenCost is the open-source, vendor-neutral alternative to Kubecost.
  Backed by CNCF, integrates with Prometheus + Grafana.
  
  kubectl apply -f https://raw.githubusercontent.com/opencost/opencost/develop/kubernetes/opencost.yaml
  
  # Cost API:
  curl http://localhost:9003/allocation?window=1d&aggregate=namespace

Cost Dashboard Metrics to Track:

  1. Cost per namespace (identify which team is expensive)
  2. CPU efficiency: actual CPU used / CPU requested
     Target: > 70% efficiency
  3. Memory efficiency: actual memory / requested memory
     Target: > 70% efficiency
  4. Monthly cost trend (are costs growing faster than features?)
  5. Idle cost: Cost of resources requested but unused

Example Cost Insights:

  Before optimization:
    order-service CPU efficiency: 18%   ← Massively over-provisioned!
    order-service memory efficiency: 35%
    Monthly cost: $2,400
  
  After right-sizing (VPA recommendations applied):
    CPU efficiency: 72%
    Memory efficiency: 78%
    Monthly cost: $680 (72% savings!)

11. JAVA-SPECIFIC COST OPTIMIZATION (JVM MEMORY)
================================================================================

The JVM Heap Over-Provisioning Problem:

  Team sets: -Xmx4g and requests.memory: 4Gi
  JVM heap: 4GB
  But actual application data in heap: 500MB
  
  Memory breakdown:
  JVM heap (used): 500MB
  JVM heap (reserved but empty): 3.5GB  ← You're paying for this!
  JVM non-heap (Metaspace, Code cache): ~300MB
  
  Total allocated: 4GB
  Total used: ~800MB
  Waste: ~3.2GB per pod (80% waste!)

Right-Sizing JVM Memory:

  Step 1: Measure actual heap usage under production load:
  kubectl exec -it order-service-xyz -- jcmd 1 VM.native_memory summary
  
  # Or via Prometheus (Micrometer exposes JVM metrics):
  # jvm_memory_used_bytes{area="heap"} → actual heap used
  # jvm_memory_committed_bytes{area="heap"} → heap committed
  
  Step 2: Set MaxRAMPercentage (NOT -Xmx) for container-aware sizing:
  
  # In Dockerfile / K8s deployment:
  JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75.0 -XX:+UseContainerSupport
  
  # With requests.memory: 1Gi:
  # Heap = 1024MB × 75% = 768MB
  # Non-heap + JVM overhead: ~256MB
  # Total: ~1024MB = exactly the memory limit
  
  Step 3: Start conservative, tune based on GC metrics:
  # If GC is frequent (jvm_gc_pause_seconds too high) → increase MaxRAMPercentage
  # If heap is rarely full → decrease MaxRAMPercentage

GC Selection for Cost:

  # G1GC (Java 11+, default): Good balance, moderate memory overhead
  -XX:+UseG1GC
  
  # ZGC (Java 15+): Sub-millisecond pauses, higher memory overhead
  # Not ideal for cost-sensitive workloads (reserved memory for regions)
  -XX:+UseZGC
  
  # Serial GC: Lowest memory overhead, no parallel GC threads
  # BEST for small containers (< 1 CPU, < 512MB RAM) like sidecar containers
  -XX:+UseSerialGC

Dev Cluster Cost Optimization (Scale to Zero):

  # Use KEDA to scale dev deployments to ZERO on nights/weekends:
  
  apiVersion: keda.sh/v1alpha1
  kind: ScaledObject
  metadata:
    name: order-service-dev-schedule
    namespace: dev
  spec:
    scaleTargetRef:
      name: order-service
    minReplicaCount: 0          # Scale to ZERO!
    maxReplicaCount: 1
    triggers:
      - type: cron
        metadata:
          timezone: America/New_York
          start: "0 8 * * 1-5"   # Start Mon-Fri at 8am
          end: "0 20 * * 1-5"    # Stop Mon-Fri at 8pm
          desiredReplicas: "1"
  
  # Weekends: 0 replicas = $0 for that deployment
  # Nights (8pm-8am): 0 replicas
  # Savings: ~60% of dev/staging compute costs

12. MULTI-TENANCY COST ALLOCATION
================================================================================

Labeling Strategy for Cost Allocation:

  Every Kubernetes resource should be labeled with:
    team:        "payments" / "catalog" / "platform"
    environment: "dev" / "staging" / "prod"
    cost-center: "CC-1234"
    app:         "order-service"
  
  # In deployment:
  metadata:
    labels:
      team: payments
      environment: prod
      cost-center: CC-1234
      app: order-service
  
  # Kubecost can then break down costs by label.
  # Chargeback: each team billed for their resource usage.

Showback vs Chargeback:

  Showback:    Show teams their cost without billing them.
               "payments team, you're using $5,000/month. Here's your report."
  
  Chargeback:  Actually transfer the cost to the team's budget.
               Requires FinOps process and team buy-in.
  
  Start with showback → teams self-optimize → then chargeback.

Q1: A Java microservice is costing $3,000/month on Kubernetes.
    How would you approach cost optimization?

A: Systematic approach:
   
   Step 1: Measure (don't guess):
   - kubectl top pods → actual CPU and memory usage
   - Kubecost dashboard → identify actual cost and efficiency metrics
   - Micrometer metrics → JVM heap used vs committed
   
   Step 2: Identify waste categories:
   a) Over-provisioned resources (CPU efficiency < 50%)
      Fix: Add VPA in Off mode → collect data → right-size requests
   b) JVM heap waste (requests.memory=4Gi but using 500MB)
      Fix: Use MaxRAMPercentage=75 with a right-sized memory request
   c) Over-replicated deployment (10 pods idle most of the day)
      Fix: Add HPA (min 2, max 10) → scale with actual load
   d) Running on on-demand when spot would work
      Fix: Move stateless pods to spot node group
   
   Step 3: Apply fixes:
   - Update requests/limits based on VPA recommendations
   - Switch JVM to MaxRAMPercentage
   - Add HPA with CPU target 70%
   - Move to spot instances with PDB
   
   Expected result:
   Original: $3,000/month (CPU efficiency 15%, memory efficiency 30%)
   After:    $900/month (CPU efficiency 72%, memory efficiency 75%)
   Savings:  70% cost reduction

Q2: What is Karpenter and how does it differ from Cluster Autoscaler?

A: Both scale Kubernetes nodes, but differently:
   
   Cluster Autoscaler (old approach):
   - You define node groups (e.g., m5.large spot, m5.2xlarge on-demand)
   - CA adds nodes from these pre-defined groups when pods are pending
   - Limited to the instance types you configured upfront
   - Node provisioning: 3-10 minutes
   - Node removal: conservative (fears disruption)
   
   Karpenter (new approach):
   - No predefined node groups needed
   - When pods are pending, Karpenter calculates EXACTLY what size node is
     needed for those specific pods and provisions it
   - Can use ANY EC2 instance type → selects cheapest that fits
   - Node provisioning: < 60 seconds
   - Consolidation: actively bin-packs and removes underutilized nodes
   - Handles spot diversification: automatically tries alternative instance
     types if spot capacity unavailable
   
   Concrete example:
   3 pods pending, each needing 1 CPU + 2GB:
   CA: Provisions an m5.xlarge (4 CPU, 16GB) → 3 pods + 75% waste
   Karpenter: Might provision an m5.large (2 CPU, 8GB) → 3 pods + ~25% waste
   
   Karpenter is especially powerful for:
   - Spot diversification (multiple instance types → better availability)
   - Node consolidation (automatic, aggressive)
   - ARM/Graviton adoption (auto-detects ARM-compatible workloads)
