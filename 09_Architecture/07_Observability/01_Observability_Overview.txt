OBSERVABILITY OVERVIEW
================================================================================

WHAT IS OBSERVABILITY?
-----------------------
Observability is the ability to understand the internal state of a system by
examining its external outputs (logs, metrics, traces).

In a monolith: debugging is straightforward — stack trace points to the line.
In microservices: a request touches 10 services. Something fails. Which one?
  → You need distributed observability.

The Three Pillars of Observability:
  ┌─────────────────────────────────────────────────────────────┐
  │  LOGS          METRICS         TRACES                       │
  │  ─────         ───────         ──────                       │
  │  What           How            Where                        │
  │  happened?      fast/slow?     did it happen?               │
  │                                                             │
  │  Discrete      Time-series    Distributed request           │
  │  events        aggregates     journey map                   │
  └─────────────────────────────────────────────────────────────┘

────────────────────────────────────────────────────────────────────────────────

THE THREE PILLARS IN DETAIL
=============================

1. LOGS (What happened?)
   Discrete, timestamped records of events.
   - Info: "Order #123 created for user #42"
   - Warn: "Inventory fallback triggered for product #99"
   - Error: "Payment gateway timeout after 10s"

   Challenges in microservices:
   - Logs spread across 50+ services and hundreds of pods
   - Need centralized aggregation (ELK Stack, Loki + Grafana)
   - Need correlation IDs to trace a single request across services

2. METRICS (How is the system behaving?)
   Numeric measurements over time.
   - Request rate (requests/second)
   - Latency (P50, P95, P99 response time)
   - Error rate (%)
   - JVM heap usage, CPU, thread pools

   Tools: Prometheus (collection), Grafana (visualization)
   Format: Micrometer (Spring Boot → Prometheus)

3. TRACES (Where did time go?)
   Shows the complete journey of a single request across services.
   - Trace: one request end-to-end
   - Span: one unit of work (one service call, one DB query)
   - Parent-child spans form a tree

   Tools: Jaeger, Zipkin, Tempo
   Standard: OpenTelemetry

────────────────────────────────────────────────────────────────────────────────

CORRELATION ID — THE CONNECTING THREAD
========================================
Every incoming request gets a unique Correlation ID / Trace ID.
This ID must be propagated through every service call and included in logs.
Allows reconstructing the full story of a request from all service logs.

Flow:
  Browser → API Gateway: generates X-Correlation-Id: abc-123-xyz
  API Gateway → Order Service: passes X-Correlation-Id: abc-123-xyz
  Order Service → Inventory Service: passes X-Correlation-Id: abc-123-xyz
  All three services log with this ID.

  Search: "Find all logs with correlationId=abc-123-xyz"
  → See the complete request story across all services

THE OBSERVABILITY STACK
=========================

Data Collection:
  Logs    → Logback/Log4j2 → Logstash/Fluentd → Elasticsearch / Loki
  Metrics → Micrometer → Prometheus
  Traces  → OpenTelemetry SDK → Jaeger / Tempo

Visualization:
  Elasticsearch → Kibana (ELK Stack)
  Loki + Prometheus → Grafana
  Jaeger/Tempo → Grafana (unified observability)

Alerting:
  Prometheus → Alertmanager → PagerDuty / Slack / Email

────────────────────────────────────────────────────────────────────────────────

SRE GOLDEN SIGNALS (What to Monitor)
=======================================
Google SRE defines 4 golden signals as the most important metrics:

  1. LATENCY — How long do requests take?
     - Response time P50, P95, P99
     - Error latency vs success latency separately

  2. TRAFFIC — How many requests?
     - Requests per second
     - Messages per second (Kafka)
     - Transactions per second

  3. ERRORS — What percentage fail?
     - HTTP 5xx error rate
     - Failed transactions rate
     - Circuit breaker open events

  4. SATURATION — How "full" is the system?
     - CPU utilization
     - Memory usage
     - Thread pool utilization
     - Queue depth

Alert on these 4 for every critical service.

────────────────────────────────────────────────────────────────────────────────

RED METHOD (Service-Level Metrics)
====================================
For each service, monitor:
  R — Rate:     requests per second
  E — Errors:   error rate %
  D — Duration: latency distribution

USE Method (Resource-Level Metrics)
=====================================
For each resource (CPU, DB, queue):
  U — Utilization:  % time resource is busy
  S — Saturation:   queue depth, waiting requests
  E — Errors:       error count

INTERVIEW QUESTIONS
====================

Q: What are the three pillars of observability?
A: Logs (discrete events — what happened), Metrics (numeric time-series — how
   the system is behaving over time), and Traces (distributed request journey —
   where time was spent across services). Together they answer: What happened?
   How fast? Where did it break?

Q: What is a Correlation ID and why is it important?
A: A unique ID generated per incoming request and propagated through every service
   call and included in all logs. Allows searching across all service logs to
   reconstruct the complete story of a single request. Essential for debugging
   distributed systems.

Q: What are the 4 Golden Signals from Google SRE?
A: Latency (response time), Traffic (requests per second), Errors (error rate),
   and Saturation (resource utilization). Monitor these for every critical service
   as the foundation of a monitoring strategy.

Q: What tools make up a typical observability stack?
A: Logs: ELK (Elasticsearch + Logstash + Kibana) or Loki + Grafana.
   Metrics: Prometheus + Grafana (with Micrometer for Spring Boot).
   Traces: OpenTelemetry SDK + Jaeger or Tempo (viewed in Grafana).
   Standard: OpenTelemetry for vendor-neutral instrumentation.
