================================================================================
SERVICE DISCOVERY OVERVIEW
================================================================================

THE PROBLEM
-----------
In a microservices system, services are dynamic:
  - Instances start and stop constantly (autoscaling, rolling deploys)
  - Containers get new IP addresses on every restart
  - Multiple instances run simultaneously (load balancing)

In a monolith: you just call a function. No network.
In microservices: you need to find where a service is running RIGHT NOW.

You can't hardcode IPs (they change) or hostnames (multiple instances).
You need SERVICE DISCOVERY.

────────────────────────────────────────────────────────────────────────────────

WHAT IS SERVICE DISCOVERY?
============================
A mechanism by which services find the network locations (IP:port) of
other services they need to communicate with.

Three steps:
  1. REGISTRATION: Service starts → registers itself with registry (IP:port + metadata)
  2. DISCOVERY: Caller queries registry to find service instances
  3. LOAD BALANCING: Caller selects one instance from the list

────────────────────────────────────────────────────────────────────────────────

DISCOVERY APPROACHES
=====================

1. CLIENT-SIDE DISCOVERY
   - Client queries registry directly
   - Client selects an instance using a load-balancing algorithm
   - Client calls the selected instance directly
   - Example: Spring Cloud Netflix Eureka + Ribbon
   - Example: Consul + client-side load balancer

   Client → [Service Registry] → gets list of instances
   Client (using LB algorithm) → selects instance B
   Client → Instance B directly

2. SERVER-SIDE DISCOVERY
   - Client sends request to a router/load balancer
   - Router queries the registry
   - Router forwards to an instance
   - Client doesn't know about registry
   - Example: AWS ALB, Kubernetes Service, API Gateway

   Client → [Load Balancer / API Gateway]
             → [Service Registry]
             → Instance B

3. DNS-BASED DISCOVERY (Kubernetes)
   - Kubernetes DNS: each Service gets a DNS name
   - "order-service.default.svc.cluster.local"
   - K8s kube-proxy handles routing to healthy pod
   - Effectively server-side discovery built into K8s

────────────────────────────────────────────────────────────────────────────────

SERVICE REGISTRY
=================
A database of service instances:
  - Stores: service name, host, port, health status, metadata (version, region)
  - Services register on startup, deregister on shutdown
  - Registry monitors health (heartbeats, HTTP health checks)
  - Dead instances removed automatically

Popular registries:
  - Eureka (Netflix / Spring Cloud) — most popular for Java/Spring
  - Consul (HashiCorp) — polyglot, also does config and service mesh
  - ZooKeeper (Apache) — distributed coordination, used by Kafka
  - etcd — distributed key-value (used by Kubernetes internally)
  - Kubernetes Service — built-in discovery for K8s workloads

────────────────────────────────────────────────────────────────────────────────

HEALTH CHECKING
================
Registry must know which instances are healthy to route to:

1. HEARTBEAT-BASED:
   Service sends periodic heartbeat to registry
   If heartbeat stops → registry marks instance DOWN
   Eureka: services send heartbeat every 30s; evicted after 90s without heartbeat

2. HTTP HEALTH CHECK:
   Registry polls service's /health endpoint
   Consul, Kubernetes: active HTTP checks
   Kubernetes: livenessProbe + readinessProbe

3. CLIENT HEALTH REPORTING:
   Service reports its own health status on register/heartbeat

────────────────────────────────────────────────────────────────────────────────

KUBERNETES SERVICE DISCOVERY
==============================
Kubernetes has built-in service discovery:

  1. Each Service gets a stable DNS name:
     {service-name}.{namespace}.svc.cluster.local
     "order-service.default.svc.cluster.local"

  2. kube-proxy maintains iptables/IPVS rules for routing

  3. EndpointSlice: K8s tracks healthy pod IPs behind each service

  4. Selector: Service selects pods via label selectors

  Example:
    Service: order-service (ClusterIP: 10.96.0.100)
    Pods: pod-a (10.244.1.5), pod-b (10.244.1.6), pod-c (10.244.1.7)
    → Traffic to 10.96.0.100 is distributed to pod-a/b/c by kube-proxy

  Types of K8s Services:
    - ClusterIP: Internal only (default)
    - NodePort: Exposes on each node's IP at a static port
    - LoadBalancer: External cloud load balancer
    - ExternalName: DNS alias for external service
    - Headless: Returns pod IPs directly (for StatefulSets)

────────────────────────────────────────────────────────────────────────────────

THE SELF-REGISTRATION PATTERN
================================
Service registers itself with the registry on startup:

Spring Boot + Eureka:
  @EnableEurekaClient  // or @EnableDiscoveryClient
  @SpringBootApplication
  public class OrderServiceApplication { ... }

  // application.yml
  spring:
    application:
      name: order-service
  eureka:
    client:
      service-url:
        defaultZone: http://eureka-server:8761/eureka/

On startup: order-service registers with Eureka
            {name: "order-service", host: "10.244.1.5", port: 8080}

On shutdown (graceful): deregisters itself
On unexpected crash:    Eureka evicts after missing heartbeats

INTERVIEW QUESTIONS
====================

Q: What is service discovery and why is it needed?
A: Service discovery allows services to dynamically find the network locations
   of other services. Needed because in microservices, instances have dynamic
   IPs (containers restart, autoscaling). Can't hardcode addresses.

Q: What's the difference between client-side and server-side discovery?
A: Client-side: client queries registry directly and does its own load
   balancing (e.g., Eureka + Ribbon). Server-side: client sends to a router
   which queries registry and forwards (e.g., K8s Service, API Gateway).

Q: How does service discovery work in Kubernetes?
A: K8s provides built-in DNS-based service discovery. Each Service gets a
   stable DNS name. kube-proxy routes traffic to healthy pods matching the
   service's label selector. No external registry needed.

Q: What happens when a service instance crashes?
A: In Eureka: missed heartbeats remove it from registry after 90s.
   In K8s: liveness probe fails → pod restarted; readiness probe fails →
   pod removed from service endpoints (stops receiving traffic).
