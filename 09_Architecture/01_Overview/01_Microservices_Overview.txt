================================================================================
MICROSERVICES OVERVIEW
================================================================================

DEFINITION
----------
Microservices is an architectural style that structures an application as a
collection of small, autonomous services modeled around a business domain.
Each service:
  - Runs in its own process
  - Communicates via lightweight mechanisms (HTTP/REST, gRPC, messaging)
  - Is independently deployable
  - Is owned by a small team
  - Can be written in different programming languages
  - Can use different data storage technologies

ORIGIN & HISTORY
----------------
- Term "microservices" popularized around 2011-2012
- Martin Fowler and James Lewis coined the formal definition in 2014
- Evolved from SOA (Service-Oriented Architecture) but without the heavyweight
  ESB (Enterprise Service Bus) middleman
- Netflix, Amazon, Uber, Spotify pioneered large-scale microservices adoption

CORE PRINCIPLES
---------------
1. Single Responsibility Principle (SRP) at service level
   - Each service does one thing and does it well
   - e.g., UserService handles only user management

2. Loose Coupling
   - Services don't know implementation details of other services
   - Changes in one service don't cascade to others
   - Communication through well-defined APIs/contracts

3. High Cohesion
   - Related functionality lives together in the same service
   - Organized around business capabilities, not technical layers

4. Autonomy
   - Teams can develop, deploy, and scale independently
   - "You build it, you run it" (Amazon philosophy)

5. Decentralized Data Management
   - Each service owns its own database
   - No shared databases between services
   - Leads to eventual consistency challenges

6. Failure Isolation
   - A failure in one service should not crash the entire system
   - Implemented via Circuit Breakers, Bulkheads

7. Design for Failure
   - Assume services will fail
   - Build retry logic, fallbacks, timeouts

KEY CHARACTERISTICS
-------------------

HOW TO DECOMPOSE A MONOLITH INTO MICROSERVICES
----------------------------------------------
Strategy 1: By Business Capability
  - Identify core business functions (Order, Payment, Inventory, Shipping)
  - Each function becomes a service

Strategy 2: By Subdomain (Domain-Driven Design)
  - Use DDD Bounded Contexts to identify service boundaries
  - Avoid "chatty" services that need constant coordination

Strategy 3: By Volatility
  - Extract parts that change most frequently
  - Keep stable parts as-is longer

Strategy 4: Strangler Fig Pattern
  - Incrementally replace monolith functionality
  - Route traffic gradually to new microservices
  - Old monolith "strangled" over time

COMMUNICATION PATTERNS IN MICROSERVICES
----------------------------------------
Synchronous:
  - REST (HTTP/1.1 + JSON)
  - gRPC (HTTP/2 + Protobuf) — high performance
  - GraphQL — flexible queries

Asynchronous:
  - Message Queues (RabbitMQ, ActiveMQ)
  - Event Streaming (Kafka, Kinesis)
  - Pub/Sub patterns

MICROSERVICES ARCHITECTURE COMPONENTS
--------------------------------------
  [Client] → [API Gateway] → [Service A]
                           → [Service B] → [Message Broker] → [Service C]
                           → [Service D]

  Supporting components:
  - Service Registry (Eureka, Consul)
  - Config Server (Spring Cloud Config, Consul)
  - Distributed Tracing (Jaeger, Zipkin)
  - Centralized Logging (ELK Stack)
  - Monitoring (Prometheus + Grafana)
  - Circuit Breaker (Resilience4j, Hystrix)

ADVANTAGES
----------
✓ Independent scaling — scale only what needs to scale
✓ Independent deployment — faster release cycles
✓ Technology diversity — use best tool per problem
✓ Fault isolation — one service crash doesn't take everything down
✓ Team autonomy — small teams own their services end-to-end
✓ Easier to understand — each service is small and focused
✓ Better testability — smaller units are easier to test

DISADVANTAGES / CHALLENGES
---------------------------
✗ Distributed systems complexity — network failures, latency, partitions
✗ Data consistency — no ACID across services, need eventual consistency
✗ Service coordination — distributed transactions are hard (Saga pattern)
✗ Operational overhead — more services = more infra, more monitoring
✗ Testing complexity — integration and E2E tests are harder
✗ Network latency — in-process calls become network calls
✗ Security surface — more inter-service communication to secure
✗ Versioning challenges — API contracts must be managed carefully
✗ Distributed tracing is needed to debug across services

WHEN TO USE MICROSERVICES (QUICK GUIDE)
----------------------------------------
Use when:
  - Application is large and complex
  - Team is large enough (Conway's Law alignment)
  - Need independent scaling of components
  - Different parts need different technologies
  - High deployment frequency is needed

Avoid when:
  - Small team (< 5 engineers)
  - Application is simple/early stage
  - Don't yet understand your domain well
  - Not enough operational maturity (DevOps, CI/CD, Kubernetes)

INDUSTRY EXAMPLES
-----------------
- Netflix: 700+ microservices, handles 250M+ members
- Amazon: "two-pizza team" rule, each team owns their service
- Uber: Started monolith, moved to microservices for scale
- Spotify: Squads own services aligned to business features
- Airbnb: Services like SearchService, PaymentService, ListingService

INTERVIEW TALKING POINTS
------------------------
Q: How would you define microservices?
A: Small, independently deployable services organized around business
   capabilities, each with its own data store, communicating via APIs.

Q: What problem do microservices solve?
A: They solve the scalability, deployment bottleneck, and team autonomy
   problems of monolithic applications.

Q: What's the biggest challenge with microservices?
A: Distributed data management and maintaining consistency across services
   without distributed transactions.

Q: What's Conway's Law and how does it relate?
A: "Organizations design systems that mirror their communication structure."
   Microservices teams should be structured around services — this is
   intentional in microservices design (Inverse Conway Maneuver).
