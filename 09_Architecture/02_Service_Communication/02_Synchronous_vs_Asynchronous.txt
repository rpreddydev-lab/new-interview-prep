SYNCHRONOUS vs ASYNCHRONOUS COMMUNICATION — DEEP DIVE
================================================================================

SYNCHRONOUS COMMUNICATION
==========================

DEFINITION:
  The caller sends a request and BLOCKS (waits) until the callee sends a
  response. The caller cannot proceed until the interaction is complete.

  Service A ──────[Request]──────→ Service B
  [Service A BLOCKED]
  Service A ←────[Response]────── Service B
  [Service A UNBLOCKED, continues]

PROTOCOLS:
  - REST (HTTP/1.1): Most common, text-based, widely supported
  - gRPC (HTTP/2 + Protobuf): High-performance, binary, streaming support
  - GraphQL: Flexible queries, reduces over-fetching
  - WebSocket (bidirectional): Real-time (not strictly request/response)

ADVANTAGES:
  ✓ Simplicity — easy to reason about (request → response model)
  ✓ Immediate error feedback — caller knows immediately if something failed
  ✓ Easy debugging — request/response pairs are easy to trace
  ✓ Natural consistency — if response is received, operation succeeded
  ✓ Familiar programming model — matches how humans think about interactions

DISADVANTAGES:
  ✗ Temporal Coupling — both services must be available at the same time
  ✗ Latency amplification — chained sync calls add up (100ms × 5 hops = 500ms)
  ✗ Cascading failures — slow/down service causes all callers to slow/fail
  ✗ Tight dependency — caller is coupled to availability of callee
  ✗ Resource waste — threads blocked waiting consume server resources

CASCADING FAILURE EXAMPLE:
  Service A → B → C → D (each call synchronous)
  If D is slow (500ms timeout):
    C times out → C returns 500 to B
    B times out → B returns 500 to A
    A times out → A returns 500 to User

  Without Circuit Breaker, this cascades in seconds.
  With Circuit Breaker: D's circuit opens → C gets fast failure → A degrades gracefully

ASYNCHRONOUS COMMUNICATION
===========================

DEFINITION:
  The caller sends a message and immediately continues execution. The callee
  processes the message independently, possibly much later. Communication is
  mediated by a message broker.

  Service A ──[Message]──→ [Broker]
  [Service A CONTINUES IMMEDIATELY]
  ... (later) ...
  [Broker] ──[Message]──→ Service B
  [Service B processes independently]

PATTERNS:

1. MESSAGE QUEUE (Point-to-Point)
   - One producer, one consumer per message
   - Message is consumed once and deleted
   - Tools: RabbitMQ (queues), Amazon SQS, ActiveMQ
   - Use case: Task distribution, work queues

   Producer ──→ [Queue] ──→ Consumer A (one message, one consumer)

2. PUBLISH/SUBSCRIBE
   - One producer, multiple consumers
   - Each consumer gets a copy of the message
   - Tools: Kafka topics, RabbitMQ exchanges (fanout), AWS SNS
   - Use case: Event notification to multiple services

   Producer ──→ [Topic] ──→ Consumer A
                          ──→ Consumer B
                          ──→ Consumer C

3. EVENT STREAMING (Kafka)
   - Ordered, persistent, replayable event log
   - Consumers maintain their own offset (position in log)
   - Events are NOT deleted after consumption
   - Use case: Event sourcing, audit logs, replay-able event processing

ADVANTAGES:
  ✓ Temporal Decoupling — producer and consumer don't need to run simultaneously
  ✓ Fault tolerance — broker buffers messages if consumer is down
  ✓ Independent scaling — consumers scale independently
  ✓ Fan-out — one event can trigger multiple independent workflows
  ✓ Backpressure handling — broker absorbs load spikes
  ✓ Event replay — reprocess historical events (Kafka)

DISADVANTAGES:
  ✗ Eventual Consistency — no immediate confirmation of success
  ✗ Message ordering challenges — Kafka partitions can help, but complex
  ✗ Duplicate message processing — must implement idempotency
  ✗ Complex error handling — dead letter queues, poison messages
  ✗ Harder to debug — tracing across async flows requires correlation IDs
  ✗ Infrastructure cost — message brokers are additional components to manage

SIDE-BY-SIDE COMPARISON
========================

Aspect               │ Synchronous              │ Asynchronous
─────────────────────┼──────────────────────────┼──────────────────────────
Waiting              │ Caller blocks             │ Caller continues immediately
Coupling             │ Temporally coupled        │ Temporally decoupled
Failure handling     │ Immediate error response  │ Dead letter queues, retries
Consistency          │ Strong (immediate)        │ Eventual
Latency              │ Adds up across call chain │ Low latency for caller
Scalability          │ Both must scale together  │ Independent scaling
Debugging            │ Simpler (traces inline)   │ Harder (async traces needed)
Ordering             │ Natural                   │ Requires Kafka partitions
Duplicate handling   │ Usually not needed        │ Idempotency required
Infrastructure       │ HTTP/gRPC only            │ Broker needed (Kafka, MQ)
Use case             │ Queries, CRUD, user-facing│ Events, workflows, fan-out

DEEP DIVE: FAILURE MODES
=========================

SYNCHRONOUS FAILURE MODES:
  1. Timeout — callee takes too long, caller gives up
     - Always set timeouts on sync calls! Default = infinite wait = system hang
  2. Connection refused — callee is down
  3. 5xx errors — callee encountered an error
  4. Network partition — packets lost in transit

  Mitigation:
    - Circuit Breaker (Resilience4j): Stop calling a failing service
    - Retry with exponential backoff: Try again after increasing delays
    - Timeout: Never wait indefinitely
    - Fallback: Return cached/default response when callee fails

ASYNCHRONOUS FAILURE MODES:
  1. Message lost — broker crashes before delivering
     - Mitigation: Message persistence (Kafka log, durable queues)
  2. Poison message — message that always fails processing → queue blocked
     - Mitigation: Dead Letter Queue (DLQ) after N failures
  3. Consumer crash mid-processing — message processed partially
     - Mitigation: Idempotent consumers + at-least-once delivery
  4. Consumer lag — messages accumulate faster than consumed
     - Mitigation: Scale consumers, increase partitions

DEEP DIVE: IDEMPOTENCY IN ASYNC
=================================

Why needed: Async systems guarantee "at-least-once" delivery.
            A message may be delivered and processed MORE THAN ONCE.
            (Due to retries, broker restarts, consumer failures)

Idempotent operation: The result is the same regardless of how many times
                      it's executed.

Example:
  NON-IDEMPOTENT: "Add $10 to account balance"
    → If processed twice: balance increases by $20 (WRONG!)

  IDEMPOTENT: "Set account balance to $110 if current balance is $100"
    → If processed twice: second time is no-op (CORRECT)

Implementation:
  1. Include a unique event/message ID in the message
  2. Consumer checks a "processed_events" table before processing
  3. If already processed: skip (return success)
  4. If not: process and record the event ID atomically

  Schema:
    CREATE TABLE processed_events (
      event_id VARCHAR(255) PRIMARY KEY,
      processed_at TIMESTAMP
    );

  Consumer logic:
    BEGIN TRANSACTION;
    IF NOT EXISTS (SELECT 1 FROM processed_events WHERE event_id = :id) THEN
      -- do the actual processing
      INSERT INTO processed_events (event_id, processed_at) VALUES (:id, NOW());
    END IF;
    COMMIT;

ASYNC REQUEST-REPLY PATTERN
=============================
When you need the benefits of async but still need a response:

  1. Client sends request → Service returns 202 Accepted + correlationId
  2. Service processes request asynchronously
  3. Client polls: GET /requests/{correlationId}/status
  4. OR: Service sends result to a reply queue/WebSocket
  5. Client reads from reply queue or WebSocket channel

  Used in: AWS Step Functions, long-running API calls, video processing

  Example Flow:
    POST /videos/process → 202 Accepted { "jobId": "abc123" }
    GET  /videos/process/abc123 → 200 { "status": "processing" }
    GET  /videos/process/abc123 → 200 { "status": "completed", "url": "..." }

CHOOSING THE RIGHT PATTERN
===========================

SCENARIO                                    │ RECOMMENDATION
────────────────────────────────────────────┼───────────────────────────────
User waits for response (checkout)          │ Synchronous REST/gRPC
Internal service-to-service query           │ gRPC (better perf than REST)
Order placement → notify 5 services         │ Async Pub/Sub (Kafka)
Background job (send email, generate report)│ Async Message Queue
Real-time stock price updates to browser    │ WebSocket / SSE
Long-running video encoding                 │ Async Request-Reply
Service that calls 3 others in parallel     │ Reactive programming (async)
High-frequency internal calls (1000s/sec)   │ gRPC over REST

CODE PATTERNS
==============

Spring Boot — RestTemplate (Sync):
  ResponseEntity<OrderDTO> response = restTemplate
    .getForEntity("http://order-service/orders/{id}", OrderDTO.class, orderId);

Spring Boot — WebClient (Async/Reactive):
  Mono<OrderDTO> order = webClient.get()
    .uri("/orders/{id}", orderId)
    .retrieve()
    .bodyToMono(OrderDTO.class);

Spring Boot — Kafka (Async Producer):
  kafkaTemplate.send("order-events", new OrderPlacedEvent(orderId, userId));

Spring Boot — Kafka (Async Consumer):
  @KafkaListener(topics = "order-events", groupId = "notification-service")
  public void handleOrderPlaced(OrderPlacedEvent event) {
    emailService.sendConfirmation(event.getUserId(), event.getOrderId());
  }

INTERVIEW QUESTIONS
====================

Q: What's the difference between synchronous and asynchronous communication?
A: Sync: caller blocks until response (REST, gRPC). Async: caller sends message
   and continues; broker delivers to consumer independently (Kafka, RabbitMQ).

Q: When would you use async over sync?
A: When you need to fan-out to multiple services, the operation is long-running,
   you need to absorb load spikes, or the downstream service is unreliable and
   you want temporal decoupling.

Q: What is temporal coupling and how do you avoid it?
A: Temporal coupling means both services must be available simultaneously.
   Avoid it by using a message broker — producer publishes; consumer processes
   when available. The broker persists messages in between.

Q: How do you handle duplicate messages in async systems?
A: By implementing idempotent consumers. Each message has a unique ID; the
   consumer checks a "processed_events" table before processing. If already
   processed, skip. Record the event ID atomically with the business action.

Q: What's the async request-reply pattern?
A: Used when you need async processing but still need a result. Service accepts
   request, returns 202+jobId immediately, processes async, and client either
   polls GET /jobs/{id} or receives callback via WebSocket/webhook.
