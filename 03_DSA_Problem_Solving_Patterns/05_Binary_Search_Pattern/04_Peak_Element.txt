  PEAK ELEMENT
  (LC 162 and Variants)

----------------------------------------------------------------
PROBLEM (LC 162): FIND PEAK ELEMENT
----------------------------------------------------------------

  An array may have multiple peaks. A peak element is one that is
  strictly greater than its neighbors.

  Assume: nums[-1] = nums[n] = -infinity (virtual boundaries).
  Return ANY peak index.

  Example:
    nums = [1, 2, 3, 1]  --> return 2 (nums[2]=3 is peak)
    nums = [1, 2, 1, 3, 5, 6, 4]  --> return 1 or 5

  Requirement: O(log n) solution.

----------------------------------------------------------------
KEY INSIGHT
----------------------------------------------------------------

  We don't need to find ALL peaks. Just find ANY one peak.

  Observation: if nums[mid] < nums[mid+1], a peak exists in the
  right half (at mid+1 or further right, because nums[n]=-inf
  guarantees the slope must eventually turn down).

  If nums[mid] > nums[mid+1], a peak exists in the left half
  (at mid or further left).

  Proof:
    Case 1: nums[mid] < nums[mid+1]
      If nums[mid+1] is a peak: found.
      If not: nums[mid+1] < nums[mid+2]. Continue right.
      By induction: there must be a peak in [mid+1..n-1] because
      the sequence is rising at mid and eventually falls (nums[n]=-inf).

    Case 2: nums[mid] > nums[mid+1]
      Symmetric argument: peak in [0..mid].

----------------------------------------------------------------
JAVA SOLUTION
----------------------------------------------------------------

  public int findPeakElement(int[] nums) {
      int lo = 0, hi = nums.length - 1;

      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (nums[mid] < nums[mid + 1]) {
              lo = mid + 1;  // peak is in right half
          } else {
              hi = mid;      // peak is in left half (including mid)
          }
      }
      return lo;  // lo == hi == peak index
  }

  Time: O(log n)  Space: O(1)

  Note: We check nums[mid] vs nums[mid+1] only (no need to check mid-1
  because the invariant guarantees a peak in our current [lo..hi] range).

----------------------------------------------------------------
TRACED EXAMPLE: nums=[1,2,1,3,5,6,4]
----------------------------------------------------------------

  lo=0 hi=6
  mid=3: nums[3]=3, nums[4]=5. 3 < 5 --> lo=4

  lo=4 hi=6
  mid=5: nums[5]=6, nums[6]=4. 6 > 4 --> hi=5

  lo=4 hi=5
  mid=4: nums[4]=5, nums[5]=6. 5 < 6 --> lo=5

  lo=5 hi=5 EXIT --> return 5 (nums[5]=6 is a peak) ✓
  (Also valid: return 1, nums[1]=2)

----------------------------------------------------------------
VARIANT: FIND PEAK IN MOUNTAIN ARRAY (LC 1095, LC 852)
----------------------------------------------------------------

  A "mountain array" has exactly one peak: rises then falls.
  Find the peak index.

  Same algorithm. In fact, LC 162 generalizes LC 852.

  LC 852: Mountain Array (guaranteed exactly one peak)
    Same solution works. Return lo after loop.

  LC 162: Multiple potential peaks (any monotone hill).
    Same solution, just returns one of them.

----------------------------------------------------------------
VARIANT: FIND IN MOUNTAIN ARRAY (LC 1095)
----------------------------------------------------------------

  Given a mountain array (can only query via API), find target.
  Return the minimum index.

  Step 1: Find peak index.
  Step 2: Binary search in ascending half [0..peak] for target.
  Step 3: If not found, binary search in descending half [peak..n-1].

  public int findInMountainArray(int target, MountainArray mountainArr) {
      int n = mountainArr.length();

      // Step 1: find peak
      int lo = 0, hi = n - 1;
      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (mountainArr.get(mid) < mountainArr.get(mid + 1)) lo = mid + 1;
          else hi = mid;
      }
      int peak = lo;

      // Step 2: binary search in ascending part [0..peak]
      lo = 0; hi = peak;
      while (lo <= hi) {
          int mid = lo + (hi - lo) / 2;
          int val = mountainArr.get(mid);
          if (val == target) return mid;
          else if (val < target) lo = mid + 1;
          else hi = mid - 1;
      }

      // Step 3: binary search in descending part [peak..n-1]
      lo = peak; hi = n - 1;
      while (lo <= hi) {
          int mid = lo + (hi - lo) / 2;
          int val = mountainArr.get(mid);
          if (val == target) return mid;
          else if (val > target) lo = mid + 1;  // descending: bigger is left
          else hi = mid - 1;
      }

      return -1;
  }

  Time: O(log n)  (3 binary searches, each O(log n))

----------------------------------------------------------------
VARIANT: PEAK INDEX IN MOUNTAIN ARRAY (LC 852)
----------------------------------------------------------------

  Simplest version: guaranteed mountain shape, find peak.

  public int peakIndexInMountainArray(int[] arr) {
      int lo = 0, hi = arr.length - 1;
      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (arr[mid] < arr[mid + 1]) lo = mid + 1;
          else hi = mid;
      }
      return lo;
  }

----------------------------------------------------------------
VARIANT: LOCAL MINIMUM (2D MATRIX)
----------------------------------------------------------------

  A harder variant: find a peak in a 2D matrix (element greater
  than all four neighbors). This uses a divide-and-conquer approach:

  1. Find the maximum element in the middle column.
  2. If it's a peak: return it.
  3. If left neighbor is larger: recurse on left half.
  4. If right neighbor is larger: recurse on right half.

  Time: O(n log m) for an n×m matrix.
  (Not commonly asked, but good to know about.)

----------------------------------------------------------------
COMPARISON: PEAK vs BINARY SEARCH
----------------------------------------------------------------

  Standard Binary Search:
    - Search space is fully sorted.
    - Look for a specific VALUE.
    - Move based on comparison to target.

  Peak Element Search:
    - Search space is NOT sorted (may have multiple hills).
    - Look for a LOCAL MAXIMUM.
    - Move based on the SLOPE (compare mid to mid+1).

  Mountain Array:
    - One peak, fully monotone on each side.
    - Find the peak, then do standard binary search on each half.

----------------------------------------------------------------
COMMON MISTAKES
----------------------------------------------------------------

  1. Using lo <= hi loop (Template 1) instead of lo < hi (Template 2).
     Leads to out-of-bounds: mid+1 could equal n when lo=hi=n-1.

  2. Accessing nums[mid + 1] when mid could be n - 1.
     Using lo < hi prevents this: when lo < hi, mid < hi <= n-1,
     so mid + 1 <= n - 1 (always valid).

  3. In LC 1095 descending binary search: wrong comparison direction.
     Descending: if target > nums[mid], move LEFT (hi = mid - 1).
                 if target < nums[mid], move RIGHT (lo = mid + 1).

  4. Forgetting to handle duplicates if problem has them.
     LC 162 explicitly says "distinct integers", so no issue.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Why does this work even though the array isn't sorted?
  A: Because we're not searching for a specific value. We're searching
     for a "slope change" (rising to falling). The slope comparison
     at mid tells us which direction a peak must lie. The key invariant
     is: there must always be a peak in the current search range.

  Q: What if nums[mid] == nums[mid+1]?
  A: LC 162 guarantees distinct integers, so this doesn't happen.
     If duplicates were allowed, we'd need to handle this separately
     (similar to how LC 154 handles duplicates in rotated array).

  Q: What's the loop invariant?
  A: At every iteration, a peak exists somewhere in [lo, hi].
     Initially trivially true (nums[-1] = nums[n] = -inf).
     After each step, invariant is maintained by the slope argument.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - State the key insight: "slope tells us which direction to go."
  - Draw an ASCII hill shape and show the lo/hi converging.
  - Mention the virtual boundaries (-inf at edges) to justify the algorithm.
  - Trace the example carefully showing lo and hi narrowing.
  - For LC 1095, walk through all three steps clearly.
