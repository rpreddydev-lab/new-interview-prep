================================================================
AWS MESSAGING — SQS (SIMPLE QUEUE SERVICE)
Complete Interview Preparation Guide
================================================================

1. SQS OVERVIEW
================================================================

  SQS is a fully managed message queueing service for decoupling
  and scaling microservices, distributed systems, and serverless apps.
  
  Key characteristics:
    - Pull-based: consumers POLL for messages
    - Each message processed by ONE consumer (at least once delivery)
    - Messages retained: up to 14 days (default: 4 days)
    - Max message size: 256 KB (larger via S3 + Extended Client Library)
    - Unlimited throughput (scales automatically)
    - Supports Standard queues and FIFO queues

================================================================
2. STANDARD vs FIFO QUEUES
================================================================

  STANDARD QUEUE:
    - Unlimited throughput (nearly unlimited transactions per second)
    - At-least-once delivery (rarely, duplicate messages may be delivered)
    - Best-effort ordering (order NOT guaranteed)
    - Use for: high-throughput, idempotent operations, batch processing

  FIFO QUEUE:
    - Exactly-once processing (no duplicates)
    - First-In-First-Out order guaranteed
    - Throughput: 300 msg/sec per API call, 3000/sec with batching
    - Message Group IDs: logical ordering groups (messages in same group delivered in order)
    - Queue name MUST end with .fifo
    - Use for: financial transactions, order processing where sequence matters

  ┌───────────────────┬───────────────────────┬──────────────────────────────┐
  │ Feature           │ Standard              │ FIFO                         │
  ├───────────────────┼───────────────────────┼──────────────────────────────┤
  │ Throughput        │ Unlimited             │ 300-3000 msg/sec             │
  │ Ordering          │ Best-effort           │ Guaranteed                   │
  │ Delivery          │ At-least-once         │ Exactly-once                 │
  │ Deduplication     │ No (app must handle)  │ Yes (dedup ID window 5 min)  │
  │ Use case          │ High throughput       │ Order-sensitive workflows    │
  └───────────────────┴───────────────────────┴──────────────────────────────┘

================================================================
3. KEY SETTINGS
================================================================

  VISIBILITY TIMEOUT:
    - Duration a message is INVISIBLE after being received (consumer is processing it)
    - Consumer must DELETE the message before timeout expires; otherwise it becomes
      visible again and can be received by another consumer (retry)
    - Default: 30 seconds; Max: 12 hours
    - Set based on expected processing time + buffer
    - If consumer needs more time: call ChangeMessageVisibility to extend

  MESSAGE RETENTION PERIOD:
    - How long messages stay in queue if not consumed
    - Default: 4 days; Range: 1 minute to 14 days

  DELIVERY DELAY:
    - Delay before message becomes visible in queue
    - Default: 0 seconds; Max: 15 minutes
    - Use for: workflows that need time between steps

  LONG POLLING:
    - Consumer waits up to 20 seconds for a message before returning empty response
    - Reduces number of empty responses (less cost, less CPU)
    - Short polling (default): returns immediately even if no messages
    - Enable: set WaitTimeSeconds=20 in ReceiveMessage API

  MAX RECEIVE COUNT (Dead Letter Queue setting):
    - After N failed processing attempts, move message to DLQ
    - Prevents a bad message from blocking the queue forever

================================================================
4. DEAD LETTER QUEUE (DLQ)
================================================================

  A separate queue for messages that fail processing repeatedly.
  
  Configure on source queue:
    - MaxReceiveCount: 3 → move to DLQ after 3 failed attempts
    - DLQ must be same type (Standard DLQ for Standard, FIFO DLQ for FIFO)
  
  Use cases:
    - Alert on DLQ messages (CloudWatch metric → SNS → notification)
    - Analyze why messages failed (log message content)
    - Replay fixed messages back to source queue
  
  DLQ REDRIVE:
    - After fixing the bug, redrive messages from DLQ back to source queue
    - Available in console or via StartMessageMoveTask API

  aws sqs set-queue-attributes \
    --queue-url https://sqs.us-east-1.amazonaws.com/123456789012/my-queue \
    --attributes '{
      "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:123456789012:my-dlq\",\"maxReceiveCount\":\"3\"}"
    }'

5. SQS EXTENDED CLIENT LIBRARY (LARGE MESSAGES)
================================================================

  SQS max message size = 256 KB
  For larger payloads (up to 2 GB):
    - Producer stores payload in S3, sends S3 reference in SQS message
    - Consumer reads S3 reference, fetches payload from S3, processes, deletes S3 object
  
  Java SDK:
  AmazonSQSExtendedClient sqsExtended = new AmazonSQSExtendedClient(sqsClient,
      new ExtendedClientConfiguration().withPayloadSupportEnabled(s3Client, "my-bucket")
  );
  sqsExtended.sendMessage(queueUrl, largePayload);  // Auto stores in S3 if > threshold

6. SECURITY
================================================================

  ENCRYPTION:
    - In-transit: HTTPS (TLS) — default
    - At-rest: SSE-SQS (managed by SQS) or SSE-KMS (your CMK)

  ACCESS CONTROL:
    - IAM policies on users/roles (sqs:SendMessage, sqs:ReceiveMessage, sqs:DeleteMessage)
    - SQS Queue Policies (resource-based): allow cross-account access or SNS to send messages

    # Allow SNS topic to send messages to SQS queue
    {
      "Statement": [{
        "Effect": "Allow",
        "Principal": { "Service": "sns.amazonaws.com" },
        "Action": "sqs:SendMessage",
        "Resource": "arn:aws:sqs:us-east-1:123456789012:my-queue",
        "Condition": { "ArnEquals": { "aws:SourceArn": "arn:aws:sns:us-east-1:123456789012:my-topic" } }
      }]
    }

7. JAVA SDK v2 — SQS OPERATIONS
================================================================

  import software.amazon.awssdk.services.sqs.SqsClient;
  import software.amazon.awssdk.services.sqs.model.*;
  
  private static final SqsClient sqsClient = SqsClient.create();
  private static final String QUEUE_URL = "https://sqs.us-east-1.amazonaws.com/123456789012/orders";
  
  // SEND MESSAGE
  sqsClient.sendMessage(SendMessageRequest.builder()
      .queueUrl(QUEUE_URL)
      .messageBody("{\"orderId\":\"123\",\"amount\":99.99}")
      .messageGroupId("order-group-1")         // FIFO only
      .messageDeduplicationId("order-123-v1")  // FIFO only
      .build()
  );
  
  // RECEIVE MESSAGES (long polling)
  ReceiveMessageResponse response = sqsClient.receiveMessage(
      ReceiveMessageRequest.builder()
          .queueUrl(QUEUE_URL)
          .maxNumberOfMessages(10)     // max 10 per call
          .waitTimeSeconds(20)         // long polling
          .visibilityTimeout(60)       // 60 seconds to process
          .build()
  );
  
  for (Message message : response.messages()) {
      try {
          processMessage(message.body());
          // Delete on success
          sqsClient.deleteMessage(DeleteMessageRequest.builder()
              .queueUrl(QUEUE_URL)
              .receiptHandle(message.receiptHandle())
              .build()
          );
      } catch (Exception e) {
          // Don't delete — message will reappear after visibility timeout
          // After maxReceiveCount failures, goes to DLQ
      }
  }
  
  // BATCH SEND (reduce API calls and cost)
  sqsClient.sendMessageBatch(SendMessageBatchRequest.builder()
      .queueUrl(QUEUE_URL)
      .entries(
          SendMessageBatchRequestEntry.builder().id("1").messageBody("msg1").build(),
          SendMessageBatchRequestEntry.builder().id("2").messageBody("msg2").build()
      )
      .build()
  );

8. SQS AS LAMBDA TRIGGER
================================================================

  Lambda polls SQS (event source mapping).
  
  Key behaviors:
    - Lambda scales consumers based on queue depth
    - Processes up to 10 messages per batch (configurable)
    - For standard queues: up to 60 Lambda functions per queue
    - Messages deleted ONLY if Lambda returns success
    - On failure: messages return to queue (retry) or go to DLQ after maxReceiveCount
  
  PARTIAL BATCH FAILURE:
    On error, returning success would delete ALL messages in the batch — even unprocessed ones.
    Returning failure would retry ALL messages — even successfully processed ones.
    
    Solution: SQSBatchResponse (built-in partial batch failure reporting)
    
    @Override
    public SQSBatchResponse handleRequest(SQSEvent event, Context context) {
        List<SQSBatchResponse.BatchItemFailure> failures = new ArrayList<>();
        
        for (SQSEvent.SQSMessage msg : event.getRecords()) {
            try {
                processOrder(msg.getBody());
            } catch (Exception e) {
                failures.add(SQSBatchResponse.BatchItemFailure.builder()
                    .withItemIdentifier(msg.getMessageId())
                    .build());
            }
        }
        return SQSBatchResponse.builder()
            .withBatchItemFailures(failures)
            .build();
        // Only failed items are returned to queue for retry
    }

9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between SQS Standard and FIFO queues?
A: Standard queues offer unlimited throughput, at-least-once delivery (rare duplicates),
   and best-effort ordering. FIFO queues guarantee exactly-once processing, strict FIFO
   ordering, and support message groups (different orderings per logical group), but are
   limited to 300–3,000 msg/sec. Use Standard for high-throughput idempotent operations
   (image processing, email sending). Use FIFO when order and exactly-once processing matter
   (financial transactions, sequential workflow steps, e-commerce order processing).

Q: What is the Visibility Timeout and why is it important?
A: When a consumer receives a message, SQS makes it invisible for the Visibility Timeout
   duration (default 30s). This prevents other consumers from picking up the same message
   while it's being processed. The consumer MUST delete the message before the timeout
   expires — if it doesn't (processing failed or took too long), the message becomes visible
   again for retry. Set the timeout slightly longer than your expected processing time.
   If processing takes variable time, call ChangeMessageVisibility to extend dynamically.

Q: What is a Dead Letter Queue and why use one?
A: A DLQ is a separate queue for messages that fail processing repeatedly. After
   MaxReceiveCount failed attempts on the source queue, SQS moves the message to the DLQ.
   Use DLQs to: prevent a poisoned message from looping indefinitely and clogging the queue,
   analyze what caused failures (inspect message content), alert on failures (CloudWatch
   metric on DLQ depth → SNS alarm), and replay fixed messages. Without a DLQ, bad messages
   could spin forever consuming compute and blocking real messages.

Q: What is SQS Long Polling and why is it preferred over Short Polling?
A: Short polling (default, WaitTimeSeconds=0) returns immediately with 0-N messages.
   If the queue is empty, you get empty responses and still pay per API call.
   Long polling (WaitTimeSeconds=1-20) waits up to 20 seconds for a message before
   returning. Benefits: fewer empty responses (reduced cost), lower CPU usage in consumers,
   fewer API calls charged. Only downside: slight delay for first message if previously
   empty. Use long polling for all production SQS consumers.
