1. WHY MESSAGING?
================================================================

  In microservices architectures, services need to communicate.
  Two approaches:
  
  SYNCHRONOUS (Direct API calls):
    ServiceA → HTTP/gRPC → ServiceB
    PRO: Simple, immediate response
    CON: Tight coupling — if ServiceB is down or slow, ServiceA fails/waits

  ASYNCHRONOUS (Message-based):
    ServiceA → Queue/Topic/Stream → ServiceB
    PRO: Loose coupling, resilience, independently scalable
    CON: More complex, eventual consistency

3. CORE PATTERNS
================================================================

  WORK QUEUE (SQS):
    Producer → [SQS Queue] → Consumer worker pool
    Each message processed by ONE consumer (competing consumers)
    Use for: background jobs, order processing, task queues

  FAN-OUT (SNS → multiple SQS):
    Event publisher → [SNS Topic] → SQS-A, SQS-B, SQS-C, Lambda, Email
    Same event sent to MULTIPLE subscribers in parallel
    Use for: order placed → notify inventory, shipping, email service simultaneously

  EVENT-DRIVEN (EventBridge):
    AWS service events, SaaS events, custom events → [Event Bus] → routing rules → targets
    Use for: reacting to AWS infrastructure events, orchestrating microservices

  STREAMING (Kinesis):
    IoT sensors / clickstream → [Kinesis Stream] → real-time analytics / Lambda
    High-throughput, time-ordered, replay-able
    Use for: clickstream, IoT, log ingestion, real-time dashboards

4. INTERVIEW QUESTIONS
================================================================

Q: When would you use SQS vs SNS vs Kinesis?
A: SQS is for work queues where each message should be processed by exactly ONE consumer.
   Use when: background job processing, order processing, rate limiting. SNS is for
   fan-out: one event broadcast to MULTIPLE subscribers simultaneously. Use when: an event
   needs to trigger multiple actions (order placed → email, inventory, analytics in parallel).
   Kinesis is for real-time streaming of HIGH-VOLUME ordered data that needs to be
   processed by multiple consumers and replayed. Use when: clickstream analytics, IoT data,
   real-time dashboards, multiple microservices need same stream. Rule of thumb:
   one consumer → SQS; multiple consumers of same event → SNS or Kinesis (volume/ordering
   determines which).
