4. COMMON ARCHITECTURAL PATTERNS
================================================================

  PATTERN 1: SNS → SQS FAN-OUT
  ─────────────────────────────
  Producer → SNS Topic → SQS Queue 1 (Order Processing)
                       → SQS Queue 2 (Inventory Update)
                       → SQS Queue 3 (Email Notification)
  
  Why: Decoupled, each service at its own pace.
  When: One event triggers multiple downstream services.

  PATTERN 2: EVENT-DRIVEN MICROSERVICES (EventBridge)
  ─────────────────────────────────────────────────────
  Order Service → put-event to custom bus
               → Rule 1: "OrderPlaced" → Lambda (analytics)
               → Rule 2: "OrderPlaced" → SQS (fulfillment)
               → Rule 3: "OrderCancelled" → Step Functions (refund)
  
  Why: Loose coupling; each rule independently managed.
  When: Many event types with different consumers and routing logic.

  PATTERN 3: KINESIS STREAM → MULTIPLE CONSUMERS
  ─────────────────────────────────────────────────
  Web app → Kinesis Stream → Lambda (real-time fraud detection)
                           → Kinesis Analytics (trend analysis)
                           → Kinesis Firehose (S3 archive)
  
  Why: All consumers see same data, independently at their own pace.
  When: High-throughput events needing multiple analytical uses.

  PATTERN 4: SQS + DEAD LETTER QUEUE
  ────────────────────────────────────
  Producer → SQS Main Queue → Lambda/Worker
                  ↓ (after N failures)
             SQS DLQ → CloudWatch Alarm → SNS → Email alert
  
  When: Critical background jobs that must not silently fail.

5. THROTTLING AND SCALING COMPARISON
================================================================

  SQS:
    - Standard: virtually unlimited throughput
    - FIFO: 3,000 msg/s with batching, 300 msg/s without
    - Scales automatically — no capacity planning
  
  SNS:
    - 300 publishes/s per topic (increases with support request)
    - Subscriber delivery scales automatically
  
  EventBridge:
    - Default 10,000 events/s per account per region
    - Adjustable via quota request
  
  Kinesis:
    - 1 MB/s or 1,000 records/s per shard (write)
    - 2 MB/s per shard (read, shared or dedicated w/ EFO)
    - You manually add shards or use UpdateShardCount

7. INTERVIEW QUESTIONS
================================================================

Q: When would you choose SQS over SNS?
A: SQS when you need: (1) A single consumer processing tasks (worker queue pattern), 
   (2) Consumers pulling at their own pace / decoupled throughput, (3) Visibility timeout 
   and dead-letter queues for reliable task processing, (4) Strict ordering (FIFO). 
   SNS when: multiple consumers need the same message simultaneously, you need push delivery, 
   or you want to combine with SQS for fan-out. SNS does not persist messages — if no 
   subscriber is available, message is lost. SQS persists for up to 14 days.

Q: Compare Kinesis and SQS for event streaming.
A: Key differences:
   1. Consumers: SQS messages are consumed by ONE consumer (then deleted). Kinesis 
      records can be consumed by MULTIPLE independent consumers simultaneously.
   2. Replay: SQS has no replay. Kinesis retains records for 1-365 days; consumers 
      can seek to any offset.
   3. Ordering: SQS Standard has no ordering (FIFO has ordering but low throughput). 
      Kinesis guarantees ordering within a shard.
   4. Throughput: SQS Standard scales infinitely. Kinesis requires manual shard management 
      with 1 MB/s per shard.
   5. Use case: SQS for task queues (each task handled once). Kinesis for event streaming 
      where multiple consumers need to react to the same events.

Q: How does SNS fan-out with SQS work and why is it recommended?
A: SNS fan-out: publish once to an SNS topic, and SNS pushes to multiple SQS queues 
   simultaneously. Each SQS queue can be consumed by a different microservice.
   Why recommended over direct multiple Lambda invocations: (1) SQS buffers messages if 
   downstream is slow, (2) DLQ handling per service independently, (3) Visibility timeout 
   gives retry-without-duplication semantics, (4) Services can scale independently, 
   (5) No tight coupling between producer and consumers. Direct SNS→Lambda skips the 
   buffer, which can cause throttling under high load; SQS absorbs traffic spikes.

Q: You need to trigger a Lambda when any S3 object is deleted in any bucket in your account. 
   How do you do this without modifying each bucket?
A: Use EventBridge. AWS S3 service publishes events to the Default Event Bus automatically. 
   Create an EventBridge rule with pattern:
   {"source": ["aws.s3"], "detail-type": ["Object Deleted"]}
   No bucket-level configuration needed. This is the key advantage of EventBridge over 
   S3 Event Notifications: EventBridge captures all S3 object events from all buckets 
   centrally. S3 Event Notifications require configuration per bucket and support fewer 
   destinations.
