================================================================
AWS OVERVIEW — SHARED RESPONSIBILITY MODEL
Complete Interview Preparation Guide
================================================================

1. WHAT IS THE SHARED RESPONSIBILITY MODEL?
================================================================

The Shared Responsibility Model defines who is responsible for what when
using AWS services. AWS and the customer share security and compliance
responsibilities.

Core Concept:
  AWS is responsible for "Security OF the cloud"
  Customer is responsible for "Security IN the cloud"

================================================================
2. AWS RESPONSIBILITIES (Security OF the Cloud)
================================================================

AWS manages and controls the physical and foundational layers:

  PHYSICAL INFRASTRUCTURE
  - Data center physical security (guards, locks, cameras, biometrics)
  - Hardware (servers, networking equipment, storage)
  - Decommissioning of hardware

  GLOBAL INFRASTRUCTURE
  - Regions, Availability Zones, Edge Locations
  - Backbone networking between AWS facilities

  VIRTUALIZATION LAYER
  - Hypervisor (EC2 host OS)
  - Network virtualization
  - Storage virtualization

  MANAGED SERVICE SOFTWARE
  - Underlying OS and software for managed services (RDS engine, Lambda runtime,
    DynamoDB infrastructure)
  - Patching managed database engines
  - S3 durability infrastructure

================================================================
3. CUSTOMER RESPONSIBILITIES (Security IN the Cloud)
================================================================

Customers are responsible for what they bring to and configure in the cloud:

  DATA
  - Data classification and encryption
  - Data at rest (S3 SSE, EBS encryption, RDS encryption)
  - Data in transit (TLS/HTTPS)
  - Backups and retention

  IDENTITY & ACCESS MANAGEMENT
  - IAM users, groups, roles, and policies
  - Multi-Factor Authentication (MFA)
  - Password policies and rotation
  - Cross-account access controls

  APPLICATION SECURITY
  - Application code vulnerabilities
  - Secrets management (no hardcoded credentials)
  - Dependency patching in Lambda layers or containers

  NETWORK CONFIGURATION
  - VPC design (subnets, route tables)
  - Security Groups and NACLs
  - VPN/Direct Connect configuration

  OPERATING SYSTEM (for IaaS services like EC2)
  - Guest OS patching (Windows/Linux updates)
  - Firewall configuration
  - Runtime environments on EC2

5. SHARED RESPONSIBILITIES
================================================================

Some areas are shared between AWS and the customer:

  ENCRYPTION
  - AWS provides: Encryption services (KMS, ACM), encrypted S3 storage options
  - Customer provides: Enabling encryption, key management policies,
    choosing appropriate encryption (SSE-S3 vs SSE-KMS vs client-side)

  PATCH MANAGEMENT
  - AWS: Patches managed service infrastructure
  - Customer: Patches guest OS on EC2, app dependencies, container images

  IDENTITY AND ACCESS
  - AWS: Provides IAM service, AWS Organizations, SSO infrastructure
  - Customer: Configures users, roles, policies, enables MFA

  NETWORK TRAFFIC PROTECTION
  - AWS: Physical network security, DDoS mitigation at infrastructure level
  - Customer: Security groups, NACLs, WAF rules, TLS configuration

7. INTERVIEW QUESTIONS
================================================================

Q: What does "AWS is responsible for security of the cloud" mean?
A: AWS secures the physical infrastructure: data centers, hardware servers,
   networking equipment, storage hardware, and the virtualization layer
   (hypervisor). AWS also patches managed services (RDS engine, Lambda runtimes).
   Customers never need to worry about physical break-ins to AWS data centers.

Q: What does "customer is responsible for security in the cloud" mean?
A: Customers secure what they put INTO the cloud: their data, their IAM
   configurations (users/roles/policies), application code, VPC network
   settings (security groups, NACLs), OS patches on EC2, encryption settings,
   and access management. A misconfigured S3 bucket (public access) is the
   customer's fault, not AWS's.

Q: If an EC2 instance gets compromised because the OS wasn't patched, whose
   fault is it — AWS or the customer?
A: The customer's fault. For EC2 (IaaS), the customer is responsible for
   patching the guest OS. AWS only manages the hypervisor and hardware.
   To automate OS patching, customers should use AWS Systems Manager Patch
   Manager.

Q: For RDS, what is AWS responsible for vs the customer?
A: AWS is responsible for patching the database engine (MySQL/PostgreSQL/etc.)
   and the underlying OS. The customer is responsible for: enabling encryption
   at rest, setting up security groups/VPC, IAM authentication settings,
   database user accounts and passwords, enabling multi-AZ (it's an option,
   not automatic), backup retention settings, and the data stored within.

Q: What is the shared responsibility for encryption in S3?
A: AWS provides the encryption infrastructure and services (SSE-S3, SSE-KMS,
   client-side encryption). The customer is responsible for ENABLING encryption
   (setting default encryption on the bucket, enforcing TLS via bucket policy),
   choosing the right encryption type, and managing KMS keys if using SSE-KMS.
   AWS does not automatically encrypt S3 buckets unless the customer enables it
   (though default SSE-S3 encryption is now on by default for new buckets).

Q: A security audit reveals EC2 instances have unpatched OS vulnerabilities.
   Can the customer blame AWS?
A: No. EC2 is IaaS — the customer fully controls the guest OS. AWS only
   manages the hardware and hypervisor. To prevent this, the customer should
   use AWS Systems Manager Patch Manager for automated patching, or use
   AWS Inspector to scan for vulnerabilities, or maintain up-to-date AMIs
   via EC2 Image Builder.
