================================================================
AWS NETWORKING — VPC PEERING AND TRANSIT GATEWAY
Complete Interview Preparation Guide
================================================================

1. THE PROBLEM: CONNECTING MULTIPLE VPCs
================================================================

  By default, VPCs are completely isolated from each other.
  When you need VPCs to communicate (e.g., shared services, multi-account):
    - VPC Peering:       1:1 private connection between two VPCs
    - Transit Gateway:   Hub-and-spoke — connect many VPCs and on-premises
    - PrivateLink:       Expose a service in one VPC to consumers in other VPCs (one-way)

================================================================
2. VPC PEERING
================================================================

  A networking connection between TWO VPCs that allows them to
  route traffic between each other using private IP addresses.
  
  KEY PROPERTIES:
    - Uses AWS backbone network (not internet)
    - Can be same account or cross-account
    - Can be same region or cross-region
    - CIDRs must NOT overlap (cannot peer VPCs with the same IP range)
    - NOT transitive: A↔B and B↔C does NOT mean A↔C
    - For N VPCs to all communicate: need N*(N-1)/2 peering connections

  SETUP STEPS:
    1. Requester VPC owner creates peering request
    2. Accepter VPC owner accepts it
    3. Add route to each VPC's route table pointing to the other VPC's CIDR
       via the peering connection
    4. Update Security Groups to allow traffic from the other VPC CIDR

  CLI:
  # Create peering connection
  aws ec2 create-vpc-peering-connection \
    --vpc-id vpc-A \
    --peer-vpc-id vpc-B \
    --peer-owner-id 123456789012 \
    --peer-region us-west-2  # For cross-region; omit for same region

  # Accept the connection (in account B)
  aws ec2 accept-vpc-peering-connection \
    --vpc-peering-connection-id pcx-12345678

  # Add routes in BOTH VPCs
  aws ec2 create-route \
    --route-table-id rtb-A \
    --destination-cidr-block 172.31.0.0/16 \  # VPC-B's CIDR
    --vpc-peering-connection-id pcx-12345678

  NON-TRANSITIVE PROBLEM:
    VPC-A ↔ VPC-B ↔ VPC-C
    VPC-A CANNOT reach VPC-C through VPC-B (no transitive routing)
    
    For 4 VPCs to fully mesh: 4*(4-1)/2 = 6 peering connections
    For 10 VPCs: 45 peering connections — this is unmanageable → use Transit Gateway

================================================================
3. TRANSIT GATEWAY (TGW)
================================================================

  Hub-and-spoke architecture for connecting many VPCs and on-premises networks.
  
  Each VPC connects ONCE to TGW. TGW routes between all attached VPCs.
  5 VPCs with TGW: 5 attachments (vs 10 peering connections for full mesh).
  
  SUPPORTS:
    - VPC attachments (in same or different accounts via Resource Access Manager)
    - VPN attachments (Site-to-Site VPN)
    - Direct Connect Gateway attachment
    - Other Transit Gateways (inter-region peering)

  FEATURES:
    - Route tables within TGW control which attachments can communicate
    - Use multiple route tables to segment traffic (e.g., prod VPCs cannot talk to dev VPCs)
    - Supports multicast (VPC peering does not)
    - Regional service (one per region); peer TGWs for inter-region connectivity
    - Up to 5,000 VPC attachments per TGW

  ARCHITECTURE:
             ┌──────────────────────────────────────────┐
             │         Transit Gateway (TGW)            │
             │         Route Table                      │
             └───┬──────────────────┬────────────┬──────┘
                 │                  │            │
          [VPC-A]           [VPC-B]           [VPN]
          (prod)            (staging)     (on-premises)
          10.0.0.0/16       10.1.0.0/16   192.168.0.0/24

  SETUP:
  # Create TGW
  aws ec2 create-transit-gateway \
    --description "My central TGW" \
    --options '{
      "DefaultRouteTableAssociation":"enable",
      "DefaultRouteTablePropagation":"enable"
    }'

  # Attach VPC to TGW
  aws ec2 create-transit-gateway-vpc-attachment \
    --transit-gateway-id tgw-12345678 \
    --vpc-id vpc-A \
    --subnet-ids subnet-a1 subnet-a2  # One subnet per AZ for routing

  # Update VPC route tables to route to TGW
  aws ec2 create-route \
    --route-table-id rtb-vpc-A \
    --destination-cidr-block 10.1.0.0/16 \  # VPC-B's CIDR
    --transit-gateway-id tgw-12345678

================================================================
4. TRANSIT GATEWAY ROUTE TABLES AND SEGMENTATION
================================================================

  By default, all attachments share one route table — full mesh.
  For isolation:
    Create separate TGW route tables for prod vs dev:
      - Prod route table: only routes prod VPCs and on-premises
      - Dev route table: only routes dev VPCs
      - Prod VPCs cannot route to dev VPCs

  Use case:
    - Shared services VPC (logging, monitoring, DNS) reachable from all
    - Production VPCs isolated from development VPCs
    - Security/compliance VPC can see all (for inspection) but others can't see each other

5. VPC PEERING vs TRANSIT GATEWAY
================================================================

  ┌──────────────────────┬───────────────────────────┬────────────────────────────┐
  │ Feature              │ VPC Peering               │ Transit Gateway             │
  ├──────────────────────┼───────────────────────────┼────────────────────────────┤
  │ Connectivity         │ 1:1 bilateral             │ Many-to-many hub-and-spoke │
  │ Transitivity         │ No                        │ Yes (TGW routes for you)   │
  │ Scale                │ N*(N-1)/2 connections     │ One attachment per VPC     │
  │ Cross-account        │ Yes                       │ Yes (via RAM)              │
  │ Cross-region         │ Yes                       │ Yes (inter-region peering) │
  │ Bandwidth            │ No limit                  │ Up to 50 Gbps per attach.  │
  │ Cost                 │ Data transfer only        │ Hourly + data processing   │
  │ Routing complexity   │ Manual route per peer     │ Centralized TGW route tables│
  │ Best for             │ Simple, few VPCs          │ Many VPCs, complex topology│
  └──────────────────────┴───────────────────────────┴────────────────────────────┘

6. AWS PRIVATELINK
================================================================

  Expose a service in your VPC to other VPCs WITHOUT peering or routing.
  One-directional: consumer VPCs connect to your service, NOT each other.
  
  Use case: SaaS provider exposing an API to thousands of customer VPCs.
  
  COMPONENTS:
    Provider side:
      - NLB in front of your service
      - Create an Endpoint Service pointing to the NLB
    
    Consumer side:
      - Create an Interface Endpoint in their VPC pointing to your Endpoint Service
      - An ENI is created in their subnet with a private IP
      - They call your service via the ENI's private IP (no internet)
  
  Benefits over VPC Peering for services:
    - Consumer VPCs can overlap CIDRs (not possible with peering)
    - You don't expose your entire VPC — only the specific service
    - One-way: consumers can't access other resources in provider VPC

7. INTERVIEW QUESTIONS
================================================================

Q: What is the problem with VPC Peering for large-scale networking?
A: VPC Peering is NOT transitive — A↔B and B↔C doesn't give A access to C.
   For N VPCs to fully communicate, you need N*(N-1)/2 peering connections.
   For 10 VPCs: 45 connections; for 50 VPCs: 1,225 connections. Managing hundreds
   of peering connections and their route tables becomes operationally very complex.
   Additionally, if you add a new VPC, you need to create a peering connection with
   every existing VPC. Transit Gateway solves this with a single hub attachment per VPC.

Q: When would you use VPC Peering vs Transit Gateway?
A: VPC Peering is better for simple 1:1 connectivity between a small number of VPCs
   (2–5). No additional cost beyond data transfer. Use peering for: two VPCs that
   need to communicate, simple HA setups, connecting dev and prod accounts for a
   specific resource. Use Transit Gateway when: connecting many VPCs (6+), needing
   transitive routing between VPCs AND on-premises, want centralized routing policy,
   need traffic segmentation between VPC groups, or want simplified operations at scale.

Q: What is the difference between VPC Peering and PrivateLink?
A: VPC Peering creates a network-level connection — all resources in both VPCs can
   communicate with each other (using Security Groups). It's symmetric: both sides
   can initiate connections. PrivateLink is service-level — only exposes a specific
   service (via NLB) to consumers. Consumers create an Interface Endpoint and access
   only that service's private IP. Provider's other VPC resources are not reachable.
   Use PrivateLink when: you want to expose a specific API/service to external accounts,
   when CIDRs might overlap (peering doesn't work with overlapping CIDRs), or when
   you want tighter isolation.

Q: How does Transit Gateway support hybrid cloud connectivity?
A: Transit Gateway can attach to both VPCs and VPN connections/Direct Connect Gateways.
   On-premises connects once to TGW via VPN or DX, and can reach all VPCs attached to TGW
   without needing separate VPN connections per VPC. TGW route tables control which VPCs
   the on-premises can reach. This simplifies hybrid architectures dramatically vs
   maintaining separate VPN connections to each VPC.
