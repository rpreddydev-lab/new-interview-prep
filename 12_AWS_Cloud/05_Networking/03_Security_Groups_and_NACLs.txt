================================================================
AWS NETWORKING — SECURITY GROUPS AND NACLs
Complete Interview Preparation Guide
================================================================

1. SECURITY GROUPS
================================================================

  Security Groups (SGs) act as virtual firewalls at the INSTANCE (ENI) level.
  
  Key characteristics:
    - STATEFUL: If inbound traffic is allowed, the response is automatically allowed
                (no need to add outbound rule for return traffic)
    - ALLOW rules only — no explicit DENY rules
    - Evaluate ALL rules before deciding (most permissive wins)
    - Applied to EC2, RDS, Lambda (in VPC), ECS tasks, ALB targets, etc.
    - Up to 5 security groups per network interface
    - Default: block ALL inbound, allow ALL outbound

  Rules contain:
    - Type (SSH, HTTP, Custom TCP, etc.)
    - Protocol (TCP, UDP, ICMP, all)
    - Port range
    - Source/Destination: IP CIDR (e.g., 0.0.0.0/0) OR another Security Group ID

  SG REFERENCING (most powerful feature):
    Instead of specifying IP ranges, reference another SG as the source.
    This allows: "accept traffic from anything that has SG-ALB attached"
    This is dynamic — it automatically allows new EC2 instances added to the ALB's SG.

  Example 3-tier setup:
    ALB-SG:     Inbound: 443 from 0.0.0.0/0
    App-SG:     Inbound: 8080 from ALB-SG   ← reference SG, not IP
    DB-SG:      Inbound: 3306 from App-SG   ← reference SG

  Create and configure SG:
  # Create security group
  aws ec2 create-security-group \
    --group-name app-sg \
    --description "Application servers" \
    --vpc-id vpc-12345678

  # Allow inbound HTTP on port 8080 from ALB security group
  aws ec2 authorize-security-group-ingress \
    --group-id sg-app123 \
    --protocol tcp \
    --port 8080 \
    --source-group sg-alb123

  # Allow inbound SSH from specific IP (for bastion/admin)
  aws ec2 authorize-security-group-ingress \
    --group-id sg-app123 \
    --protocol tcp \
    --port 22 \
    --cidr 10.0.1.0/24

2. NETWORK ACCESS CONTROL LISTS (NACLs)
================================================================

  NACLs act as optional firewalls at the SUBNET level.
  
  Key characteristics:
    - STATELESS: Must explicitly allow BOTH inbound AND outbound for each flow
                 (return traffic requires its own rule)
    - Supports ALLOW and DENY rules
    - Rules are evaluated in NUMBER ORDER (lowest number first)
    - First matching rule is applied (stops evaluating further)
    - Associated with subnets (one NACL per subnet; one subnet per NACL)
    - Default NACL: allows ALL inbound and ALL outbound traffic
    - Custom NACLs: deny ALL by default until you add rules

  Rule format:
    Rule # | Type    | Protocol | Port Range | Source/Dest   | Allow/Deny
    100     | HTTPS   | TCP      | 443        | 0.0.0.0/0     | ALLOW
    200     | SSH     | TCP      | 22         | 10.0.0.0/8    | ALLOW
    300     | Custom  | TCP      | 1024-65535 | 0.0.0.0/0     | ALLOW (ephemeral ports)
    *       | All     | All      | All        | 0.0.0.0/0     | DENY  (implicit deny)

  EPHEMERAL PORTS:
    Return traffic uses ephemeral (high) ports on the client side:
    Linux:   32768–60999
    Windows: 49152–65535
    AWS recommends: 1024–65535
    NACLs MUST allow these for outbound (return traffic) in both directions.

3. SECURITY GROUPS vs NACLs
================================================================

  ┌─────────────────────┬──────────────────────────┬──────────────────────────────┐
  │ Feature             │ Security Groups           │ Network ACLs (NACLs)         │
  ├─────────────────────┼──────────────────────────┼──────────────────────────────┤
  │ Level               │ Instance (ENI) level      │ Subnet level                 │
  │ State               │ Stateful (auto return)    │ Stateless (both ways needed) │
  │ Rules               │ Allow only                │ Allow and Deny               │
  │ Evaluation          │ All rules evaluated        │ Rules in order, first match  │
  │ Default behavior    │ Deny all inbound           │ Allow all (default NACL)     │
  │ Association         │ EC2 instances, ENIs        │ Subnets                      │
  │ IP blocking         │ Cannot explicitly deny     │ Can explicitly deny specific IPs│
  │ Use case            │ Fine-grained instance control│ Subnet-level protection    │
  └─────────────────────┴──────────────────────────┴──────────────────────────────┘

  WHEN TO USE NACLs:
    1. Block specific IP addresses (cannot do with SGs)
    2. Additional layer of security at subnet boundary
    3. Compliance requirements for subnet-level firewall
    4. Block access to entire subnets from other subnets

  TYPICAL SETUP:
    - Security Groups: PRIMARY layer of control (almost always sufficient)
    - NACLs: OPTIONAL additional layer (keep close to default for simplicity)

4. PRACTICAL EXAMPLES
================================================================

  BLOCK A SPECIFIC IP WITH NACL:
  # Deny an IP that's been attacking your system
  aws ec2 create-network-acl-entry \
    --network-acl-id acl-12345678 \
    --rule-number 50 \
    --protocol tcp \
    --port-range From=0,To=65535 \
    --cidr-block "203.0.113.100/32" \
    --rule-action deny \
    --ingress

  ALLOW ONLY HTTPS FROM ALB TO APP (SG):
  # App instances only accept traffic from ALB
  aws ec2 authorize-security-group-ingress \
    --group-id sg-app \
    --protocol tcp \
    --port 8080 \
    --source-group sg-alb

  # DB only accepts from App
  aws ec2 authorize-security-group-ingress \
    --group-id sg-db \
    --protocol tcp \
    --port 5432 \
    --source-group sg-app

5. COMMON CONNECTIVITY TROUBLESHOOTING
================================================================

  "I can't connect to my EC2 instance":
  Check in order:
    1. Security Group inbound rules — is port/protocol allowed?
    2. NACL inbound rules — is there a DENY before the ALLOW?
    3. NACL outbound rules — is ephemeral port range allowed? (stateless!)
    4. Route table — is there a route to your source?
    5. Internet Gateway — is one attached if it's a public subnet?
    6. Instance public IP — does the instance have one?
    7. OS-level firewall — iptables blocking anything?

  Use VPC Flow Logs to see ACCEPT/REJECT records:
    - REJECT = blocked by SG or NACL
    - ACCEPT but no response = application issue or OS firewall

6. INTERVIEW QUESTIONS
================================================================

Q: What is the fundamental difference between Security Groups and NACLs?
A: Security Groups are STATEFUL and at the INSTANCE level — return traffic is
   automatically allowed, only ALLOW rules. NACLs are STATELESS and at the
   SUBNET level — you must explicitly allow BOTH inbound and outbound for each
   connection including ephemeral (return) ports, supports both ALLOW and DENY.
   In practice: Security Groups handle 99% of access control. NACLs are used for
   an extra layer or to block specific IP addresses (which SGs cannot do — SGs
   have no explicit DENY).

Q: Why might connectivity fail even though a Security Group rule allows the traffic?
A: Multiple reasons: 1) Custom NACL on the subnet has a DENY rule before the ALLOW,
   2) NACL statelessness — inbound is allowed but outbound rule for ephemeral ports
   (1024-65535) is missing, blocking return traffic, 3) Route table doesn't have a
   route to the destination, 4) No Internet Gateway or NAT Gateway in the path,
   5) Instance doesn't have a public IP (for public internet access), 6) OS-level
   firewall (iptables/firewalld) inside the instance.

Q: A Security Group allows all outbound traffic. Can an EC2 instance in a private
   subnet browse the internet?
A: Not automatically. The SG outbound rule is necessary but not sufficient. For
   internet access from a private subnet, you also need: 1) a NAT Gateway in a
   public subnet, 2) a route in the private subnet's route table pointing 0.0.0.0/0
   to the NAT Gateway, 3) the NAT Gateway's subnet has a route to the IGW,
   4) an IGW attached to the VPC. The SG allows it, but the NAT Gateway provides
   the actual outbound path.

Q: How would you block a specific IP address from accessing your EC2 instances?
A: Use a NACL — not a Security Group, because SGs only support ALLOW rules.
   Add a NACL rule with a lower rule number than the ALLOW rules, with the specific
   /32 IP CIDR, action DENY, on the relevant subnet. Rule evaluation stops at the
   first match, so place the DENY rule (e.g., rule #50) before your ALLOW rule
   (e.g., rule #100). This blocks that IP at the subnet boundary before it even
   reaches the instance's Security Group.
