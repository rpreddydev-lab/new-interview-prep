================================================================
AWS DEVELOPER TOOLS — CODEPIPELINE
Complete Interview Preparation Guide
================================================================

1. CODEPIPELINE OVERVIEW
================================================================

  CodePipeline is a fully managed continuous delivery service.
  Orchestrates the steps to build, test, and deploy applications.
  
  KEY CONCEPTS:
    Pipeline: series of stages with sequential execution
    Stage: logical phase (Source, Build, Test, Deploy)
    Action: task within a stage (can be parallel within a stage)
    Artifact: input/output data passed between stages (stored in S3)
    Transition: connection between stages (can be disabled)

================================================================
2. PIPELINE STRUCTURE
================================================================

  ┌──────────────────────────────────────────────────────────────────┐
  │  PIPELINE EXECUTION FLOW                                         │
  │                                                                  │
  │  Stage 1: SOURCE      Stage 2: BUILD     Stage 3: STAGING       │
  │  ┌──────────┐         ┌──────────┐       ┌──────────┐           │
  │  │ GitHub   │ ──────→ │CodeBuild │ ────→ │CodeDeploy│           │
  │  │ Webhook  │         │unit tests│       │EC2/ECS   │           │
  │  └──────────┘         └──────────┘       └──────────┘           │
  │                                                ↓                 │
  │  Stage 4: APPROVAL    Stage 5: PROD                              │
  │  ┌──────────┐         ┌──────────┐                              │
  │  │ Manual   │ ──────→ │CodeDeploy│                              │
  │  │ Approval │         │Blue/Green│                              │
  │  └──────────┘         └──────────┘                              │
  └──────────────────────────────────────────────────────────────────┘

================================================================
3. ACTION TYPES
================================================================

  SOURCE:
    - S3, GitHub (via CodeStar Connection), GitLab, Bitbucket, ECR
  
  BUILD:
    - CodeBuild (most common)
    - Jenkins (via Jenkins plugin)
  
  TEST:
    - CodeBuild (run tests in a separate build)
    - Device Farm (mobile testing)
    - BlazeMeter, Ghost Inspector (third-party)
  
  DEPLOY:
    - CodeDeploy (EC2/Lambda/ECS)
    - CloudFormation (IaC deploy)
    - Elastic Beanstalk
    - ECS (direct ECS service deployment)
    - S3 (static website deploy)
    - Service Catalog, AppConfig
  
  APPROVAL:
    - Manual approval (SNS notification to approver)
    - Required before proceeding to next stage
  
  INVOKE:
    - Lambda function
    - Step Functions (wait for state machine)

================================================================
4. PARALLEL ACTIONS WITHIN A STAGE
================================================================

  Run multiple actions simultaneously within a stage:
  
  Stage: TEST
    Action 1 (runOrder=1): Integration tests (CodeBuild)
    Action 2 (runOrder=1): Security scan (CodeBuild)  ← runs in parallel
    Action 3 (runOrder=2): Load test (CodeBuild)       ← after both above succeed
  
  Use runOrder to define sequence within a stage.

5. PIPELINE AS CODE (JSON/YAML)
================================================================

  CREATE PIPELINE:
  aws codepipeline create-pipeline --pipeline file://pipeline.json
  
  pipeline.json example:
  {
    "pipeline": {
      "name": "my-java-pipeline",
      "roleArn": "arn:aws:iam::123456789012:role/CodePipelineRole",
      "artifactStore": {
        "type": "S3",
        "location": "my-codepipeline-artifacts"
      },
      "stages": [
        {
          "name": "Source",
          "actions": [{
            "name": "GitHub",
            "actionTypeId": {
              "category": "Source",
              "owner": "ThirdParty",
              "provider": "GitHub",
              "version": "1"
            },
            "configuration": {
              "Owner": "myorg",
              "Repo": "myapp",
              "Branch": "main",
              "OAuthToken": "{{resolve:secretsmanager:github-token}}"
            },
            "outputArtifacts": [{"name": "SourceCode"}]
          }]
        },
        {
          "name": "Build",
          "actions": [{
            "name": "CodeBuild",
            "actionTypeId": {
              "category": "Build",
              "owner": "AWS",
              "provider": "CodeBuild",
              "version": "1"
            },
            "configuration": {
              "ProjectName": "my-java-build"
            },
            "inputArtifacts": [{"name": "SourceCode"}],
            "outputArtifacts": [{"name": "BuildArtifact"}]
          }]
        }
      ]
    }
  }

6. TRIGGERING PIPELINES
================================================================

  SOURCE TRIGGERS:
    - GitHub webhook: push to branch triggers pipeline
    - S3: new object in bucket triggers pipeline
    - ECR: new container image triggers pipeline
  
  SCHEDULED: CloudWatch Events rule with rate/cron
  
  MANUAL: Start pipeline execution via CLI/console
  aws codepipeline start-pipeline-execution --name my-java-pipeline
  
  CROSS-PIPELINE: CodePipeline can trigger another pipeline

================================================================
7. NOTIFICATIONS AND EVENTS
================================================================

  All pipeline events published to EventBridge:
  {
    "source": ["aws.codepipeline"],
    "detail-type": ["CodePipeline Pipeline Execution State Change"],
    "detail": { "state": ["FAILED"] }
  }
  
  Notification rule (via AWS Chatbot → Slack):
  aws codestar-notifications create-notification-rule \
    --name pipeline-slack-alerts \
    --resource arn:aws:codepipeline:us-east-1:123456789012:my-java-pipeline \
    --events-types PIPELINE_EXECUTION_STARTED PIPELINE_EXECUTION_FAILED PIPELINE_EXECUTION_SUCCEEDED \
    --targets '[{"Type":"SNS","Address":"arn:aws:sns:us-east-1:123456789012:pipeline-alerts"}]'

================================================================
8. CROSS-ACCOUNT AND CROSS-REGION PIPELINES
================================================================

  CROSS-ACCOUNT:
    - Pipeline in Account A deploys to Account B
    - Use CodePipeline cross-account role assumption
    - Account B creates a role with trust policy for Account A
    - Artifact S3 bucket encrypted with customer-managed KMS key
      shared with Account B
  
  CROSS-REGION:
    - Deploy to multiple regions from single pipeline
    - Need regional artifact stores (one S3 bucket per region)
    - CloudFormation StackSets for multi-region infra deployments

================================================================
9. PIPELINE BEST PRACTICES
================================================================

  1. FAIL FAST: Unit tests in Build stage (don't wait until Deploy)
  2. IMMUTABLE ARTIFACTS: Build once, deploy same artifact to all envs
  3. ENVIRONMENT PARITY: Same artifact, different configs (env vars)
  4. MANUAL APPROVAL for Production: Human gate before prod deploy
  5. AUTOMATED ROLLBACK: CloudWatch alarm triggers CodeDeploy rollback
  6. NOTIFICATIONS: SNS/Slack on failure (don't just check pipeline manually)
  7. ARTIFACT VERSIONING: Use commit SHA as image/artifact tag (not "latest")
  8. SECRET MANAGEMENT: Never hardcode secrets in pipeline config or buildspec

================================================================
10. INTERVIEW QUESTIONS
================================================================

Q: How do you implement a multi-environment pipeline (dev → staging → prod)?
A: Three-stage deploy pipeline with approvals:
   
   1. Source: GitHub push to main branch triggers pipeline
   2. Build: CodeBuild compiles, runs unit tests, creates artifact with commit SHA tag
   3. Deploy Dev: CodeDeploy to Dev environment (automatic, no approval)
   4. Test: Integration tests against Dev (separate CodeBuild project)
   5. Approve Staging: Manual approval action (SNS notification to team lead)
   6. Deploy Staging: CodeDeploy to Staging (canary or rolling)
   7. Test Staging: Performance/load tests (CodeBuild + JMeter/Gatling)
   8. Approve Prod: Manual approval (requires two approvers via Lambda logic)
   9. Deploy Prod: CodeDeploy Blue/Green with CloudWatch alarm auto-rollback
   
   Key: same artifact (built once in step 2) deployed to all environments.
   Environment differences are in configs (Parameter Store per env), not the artifact.

Q: How does CodePipeline handle failed deployments?
A: When a stage action fails:
   1. Pipeline execution stops at the failed stage
   2. EventBridge publishes FAILED event → SNS notification → Slack/email alert
   3. Subsequent stages do NOT execute (pipeline blocked, not rolled back)
   4. CodeDeploy (deploy action): if deployment config has health check thresholds,
      it triggers rollback on its own. Otherwise the pipeline just fails.
   5. CloudWatch alarm integration (CodeDeploy): set an alarm on 5xx errors; 
      CodeDeploy monitors it during deployment and reverts if alarm fires.
   6. Fix the code, push a new commit → pipeline re-runs from source
   7. Manual re-run option: Retry the failed stage (if issue was transient)
   
   Unlike some CI tools, CodePipeline doesn't automatically retry failed stages;
   you must push a new commit or manually retry.

Q: How do you make CodePipeline aware of a GitHub repo without using CodeCommit?
A: Use a CodeStar Connection (GitHub App-based integration, newer V2 approach):
   1. In AWS Console, create a CodeStar Connection to GitHub (OAuth authorization)
   2. In pipeline Source action, use provider "CodeStarSourceConnection" and the 
      ConnectionArn along with the repo full name and branch
   3. GitHub events (push) trigger the pipeline via CodeStar webhooks
   
   This is the preferred approach (V2 source action). The older V1 used a GitHub 
   OAuth personal access token directly, which is being deprecated. V2 with CodeStar 
   Connections uses the GitHub App (more secure, doesn't require user credentials).
