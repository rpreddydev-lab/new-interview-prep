AWS IAM — USERS, GROUPS, AND ROLES
Complete Interview Preparation Guide
================================================================

1. IAM USERS IN DEPTH
================================================================

An IAM user is a permanent identity in AWS representing a person or
application.

CREATING A USER (CLI):
  aws iam create-user --user-name alice
  aws iam create-login-profile --user-name alice \
    --password "P@ssw0rd123!" --password-reset-required
  aws iam create-access-key --user-name alice

USER CREDENTIAL TYPES:
  ┌─────────────────────────────────────────────────────────────────┐
  │ Console Password  │ For AWS Management Console login            │
  │ Access Key ID     │ AKIAIOSFODNN7EXAMPLE (20 chars, starts AKIA)│
  │ Secret Access Key │ 40-char secret, shown once at creation      │
  │ MFA Device        │ Virtual (Authenticator app) or hardware     │
  └─────────────────────────────────────────────────────────────────┘

ACCESS KEY MANAGEMENT:
  - Max 2 active access keys per user (for rotation purposes)
  - Rotation best practice: Create new key → update apps → deactivate old → delete old
  - Check last used: aws iam get-access-key-last-used --access-key-id AKIAIOSFODNN7EXAMPLE

CHECKING USER INFO:
  # List all users
  aws iam list-users
  
  # Get user details
  aws iam get-user --user-name alice
  
  # List attached policies
  aws iam list-attached-user-policies --user-name alice
  
  # Generate credentials report (CSV)
  aws iam generate-credential-report
  aws iam get-credential-report

PASSWORD POLICY (Account-level):
  aws iam update-account-password-policy \
    --minimum-password-length 12 \
    --require-symbols \
    --require-numbers \
    --require-uppercase-characters \
    --require-lowercase-characters \
    --allow-users-to-change-password \
    --max-password-age 90 \
    --password-reuse-prevention 5

2. IAM GROUPS IN DEPTH
================================================================

A group is a collection of IAM users to simplify permission management.

KEY RULES:
  - No nesting: groups cannot contain other groups
  - A user can belong to up to 10 groups
  - Groups have no credentials and cannot sign in
  - Permissions are cumulative across all groups a user belongs to

EXAMPLE SETUP (Console/CLI):
  # Create group
  aws iam create-group --group-name Developers
  
  # Attach policy to group
  aws iam attach-group-policy \
    --group-name Developers \
    --policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess
  
  # Add user to group
  aws iam add-user-to-group --group-name Developers --user-name alice
  
  # List users in group
  aws iam get-group --group-name Developers

COMMON GROUPS FOR ORG STRUCTURE:
  ┌────────────────────────────────────────────────────────────────┐
  │ Administrators    │ AdministratorAccess (nearly full access)   │
  │ Developers        │ EC2, ECS, Lambda, S3, DynamoDB, CloudWatch │
  │ DataScientists    │ S3, Glue, Athena, SageMaker, Redshift      │
  │ NetworkAdmins     │ VPC, Route53, ELB, CloudFront              │
  │ BillingTeam       │ Billing read-only access                   │
  │ ReadOnly          │ SecurityAudit or ViewOnlyAccess            │
  └────────────────────────────────────────────────────────────────┘

3. IAM ROLES IN DEPTH
================================================================

A role is an identity with permission policies but no permanent credentials.
It's assumed temporarily via STS (Security Token Service).

ROLE COMPONENTS:
  1. Trust Policy (Resource-based):
     - Defines the PRINCIPAL that CAN assume this role
     - Condition: who/what can call sts:AssumeRole
  
  2. Permission Policy (Identity-based):
     - Defines what the assumed role can do
     - Actions, Resources, Conditions

ROLE TYPES:

  a) AWS Service Roles
     Purpose: Allow AWS services to call other AWS services on your behalf
     Examples:
       - Lambda execution role → CloudWatch Logs + DynamoDB
       - EC2 instance profile → S3 bucket access
       - CloudFormation service role → Create/Delete resources
     
     Trust Policy for Lambda:
     {
       "Version": "2012-10-17",
       "Statement": [{
         "Effect": "Allow",
         "Principal": { "Service": "lambda.amazonaws.com" },
         "Action": "sts:AssumeRole"
       }]
     }

  b) Cross-Account Roles
     Purpose: Allow IAM users/roles in Account B to access resources in Account A
     
     Steps:
       1. In Account A (resource account): Create role, trust Account B
       2. In Account B: Attach policy allowing sts:AssumeRole on Account A's role
       3. User in Account B: aws sts assume-role --role-arn arn:aws:iam::ACCOUNT_A:role/CrossAccess
     
     Trust Policy in Account A (trusting Account B):
     {
       "Version": "2012-10-17",
       "Statement": [{
         "Effect": "Allow",
         "Principal": { "AWS": "arn:aws:iam::ACCOUNT_B_ID:root" },
         "Action": "sts:AssumeRole"
       }]
     }

  c) Federated Identity Roles
     Purpose: Allow users authenticated externally (SAML, OIDC) to assume a role
     Trust principal: "Federated": "cognito-identity.amazonaws.com" or SAML IdP ARN

  d) Service-Linked Roles
     - Predefined by AWS for specific services
     - Cannot edit trust policy
     - Automatically created when you enable a service
     - Example: AWSServiceRoleForElasticLoadBalancing (created when you create an ELB)

EC2 INSTANCE PROFILE:
  - A container for an IAM role for EC2 instances
  - When you attach an IAM role to EC2 in console, an instance profile is auto-created
  - The EC2 metadata service (169.254.169.254) exposes temporary credentials
  - Apps on EC2 call the metadata endpoint automatically via the AWS SDK
  
  # Credentials available at:
  curl http://169.254.169.254/latest/meta-data/iam/security-credentials/my-role-name

ASSUMING A ROLE (CLI):
  aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/S3ReadRole \
    --role-session-name my-session
  
  # Returns: AccessKeyId, SecretAccessKey, SessionToken, Expiration
  # Export to environment variables to use

4. PERMISSION BOUNDARIES
================================================================

A permissions boundary is an advanced IAM feature to limit the maximum
permissions an IAM entity can have.

  - Set as a managed policy attached to a user/role
  - The EFFECTIVE permissions are the intersection of:
    identity-based policies AND the permissions boundary
  
  Example:
    Identity policy: Allow s3:*, ec2:*, rds:*
    Permissions boundary: Allow s3:*, ec2:*
    Effective permission: s3:*, ec2:* (rds:* blocked by boundary)

Use cases:
  - Allow dev teams to create IAM roles but prevent privilege escalation
  - Developers create roles that cannot exceed their own permissions

5. ROLE CHAINING AND SESSION DURATION
================================================================

Role Chaining:
  - Assuming a role from within another assumed role
  - Maximum session duration for chained roles: 1 hour (cannot extend)
  - Direct role assumption: up to 12 hours (configurable)

Session Duration:
  - Minimum: 15 minutes
  - Default: 1 hour
  - Maximum: 12 hours (configured on the role itself)
  
  aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/MyRole \
    --role-session-name session1 \
    --duration-seconds 7200  # 2 hours

6. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between IAM users, groups, and roles?
A: IAM users are permanent identities with credentials (password + access keys)
   for people or applications. IAM groups are collections of users to simplify
   policy management — policies attached to a group apply to all users in it.
   IAM roles have no permanent credentials; they issue temporary credentials via
   STS when assumed, and are used by AWS services (EC2, Lambda), federated users,
   or cross-account access. Best practice: use roles over users wherever possible.

Q: How does an EC2 instance access S3 without hardcoded credentials?
A: Attach an IAM role to the EC2 instance (via an instance profile). The EC2
   metadata service at 169.254.169.254 provides temporary credentials. The AWS
   SDK automatically fetches and refreshes these credentials. No access keys
   are stored in the code or on the instance. This is the correct, secure approach.

Q: What is a cross-account IAM role and how does it work?
A: A cross-account role allows principals in one AWS account (Account B) to
   access resources in another account (Account A). In Account A, create a role
   with a trust policy specifying Account B as the trusted principal. In Account B,
   grant users permission to call sts:AssumeRole for that role ARN. Users in B
   then assume the role to get temporary credentials for Account A's resources.

Q: What is a permissions boundary?
A: A permissions boundary is a managed policy set as the maximum permissions
   an IAM entity can ever receive. The effective permissions are the intersection
   of the entity's identity-based policies and the boundary. Even if you grant
   someone AdministratorAccess via a policy, the boundary can limit them to only
   S3 and EC2 actions. Used to let devs create roles without risking privilege escalation.

Q: Can an IAM group be nested inside another IAM group?
A: No. IAM groups cannot contain other groups. Groups can only contain IAM users.
   This is a commonly tested limitation. If you need hierarchical permission
   management, use AWS Organizations with SCPs and multiple account structure.

Q: A new developer joins. What is the proper way to give them access?
A: 1) Create an IAM user for them (or use IAM Identity Center for SSO).
   2) Add them to the appropriate IAM group (e.g., Developers) that has
      the needed policies attached. 3) Set up MFA. 4) Follow least privilege —
      don't give AdministratorAccess when they only need EC2/S3. Never share
      credentials. Never use the root account.
