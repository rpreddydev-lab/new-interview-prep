================================================================
AWS IAM — POLICIES AND PERMISSIONS
Complete Interview Preparation Guide
================================================================

1. WHAT IS AN IAM POLICY?
================================================================

An IAM policy is a JSON document that defines permissions. It specifies
what actions are allowed or denied on which AWS resources under what conditions.

================================================================
2. POLICY TYPES
================================================================

  ┌────────────────────────────────────────────────────────────────────┐
  │ POLICY TYPE        │ DESCRIPTION                                   │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ AWS Managed        │ Created and maintained by AWS                 │
  │                    │ Examples: AmazonS3FullAccess, AdministratorAccess│
  │                    │ Cannot be modified; can be attached to many   │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Customer Managed   │ Created by you; full control                  │
  │                    │ Can be attached to multiple users/groups/roles │
  │                    │ Versioning supported (up to 5 versions)       │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Inline             │ Embedded directly in a user/group/role        │
  │                    │ Deleted when the entity is deleted            │
  │                    │ 1:1 relationship (not reusable)               │
  │                    │ Use only when strict 1:1 relationship needed  │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Identity-Based     │ Attached to users/groups/roles                │
  │                    │ Defines WHAT the identity can do              │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Resource-Based     │ Attached to a resource (S3 bucket, KMS key)   │
  │                    │ Defines WHO can access the resource           │
  │                    │ Must specify Principal                        │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ SCPs               │ AWS Organizations Service Control Policies    │
  │                    │ Set maximum permissions for an entire account │
  │                    │ Apply to all IAM entities in the account      │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Permissions Boundary│ Limits max permissions of a user/role       │
  │                    │ Must be a customer managed or AWS managed policy│
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Session Policies   │ Passed when using STS to assume a role        │
  │                    │ Further restricts temporary credentials       │
  └────────────────────┴───────────────────────────────────────────────┘

3. POLICY STRUCTURE
================================================================

Every IAM policy JSON has:

  {
    "Version": "2012-10-17",        // Required; use this date
    "Id": "optional-policy-id",     // Optional unique identifier
    "Statement": [                  // Array of statements
      {
        "Sid": "UniqueStatementId", // Optional; descriptive name
        "Effect": "Allow",          // Required: "Allow" or "Deny"
        "Principal": {              // Required for resource-based only
          "AWS": "arn:aws:iam::123456789012:user/alice"
        },
        "Action": [                 // Required: service:action or "*"
          "s3:GetObject",
          "s3:PutObject"
        ],
        "Resource": [               // Required: resource ARN or "*"
          "arn:aws:s3:::my-bucket",
          "arn:aws:s3:::my-bucket/*"
        ],
        "Condition": {              // Optional: restricts when policy applies
          "StringEquals": {
            "s3:prefix": ["home/"]
          }
        }
      }
    ]
  }

KEY ELEMENTS:
  Effect:
    - "Allow" — permit the action
    - "Deny"  — explicitly deny (overrides any Allow)
  
  Action:
    - Format: "service:action" (e.g., "s3:GetObject", "ec2:StartInstances")
    - Wildcard: "s3:*" (all S3 actions), "*" (ALL actions — dangerous)
    - NotAction: inverse; allow everything EXCEPT listed actions
  
  Resource:
    - Format: ARN (arn:aws:s3:::my-bucket)
    - Wildcard: "arn:aws:s3:::*" (all S3 resources), "*" (all)
    - NotResource: inverse
  
  Principal (resource-based policies only):
    - AWS account: "AWS": "arn:aws:iam::123456789012:root"
    - IAM user: "AWS": "arn:aws:iam::123456789012:user/alice"
    - IAM role: "AWS": "arn:aws:iam::123456789012:role/MyRole"
    - AWS service: "Service": "lambda.amazonaws.com"
    - Everyone: "*" (make bucket public — avoid in production)

4. CONDITION OPERATORS AND KEYS
================================================================

Condition Structure:
  "Condition": {
    "ConditionOperator": {
      "ConditionKey": "value"
    }
  }

COMMON OPERATORS:
  StringEquals / StringNotEquals          → Exact string match
  StringLike / StringNotLike              → Supports wildcards (* and ?)
  NumericEquals / NumericLessThan         → Number comparisons
  DateEquals / DateGreaterThan            → Date comparisons
  Bool                                    → Boolean (true/false)
  IpAddress / NotIpAddress               → IP/CIDR matching
  ArnEquals / ArnLike                    → ARN comparisons
  Null                                    → Check if key exists

COMMON CONDITION KEYS:
  aws:RequestedRegion      → Restrict to specific regions
  aws:SourceIp             → Restrict to IP address range
  aws:SecureTransport      → Require HTTPS (true/false)
  aws:MultiFactorAuthPresent → Require MFA
  aws:PrincipalArn         → The ARN of the requester
  aws:CurrentTime          → Current time (for time-based access)
  s3:prefix                → S3 object prefix
  ec2:Region               → EC2 region
  aws:TagKeys              → Restrict by tag keys
  aws:ResourceTag/<key>    → Restrict by resource tag

CONDITION EXAMPLES:

  // Require HTTPS for S3
  "Condition": {
    "Bool": { "aws:SecureTransport": "false" }
  }
  // Use with Effect: "Deny" to force HTTPS

  // Require MFA
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
  // Use with Effect: "Deny" to require MFA

  // Restrict to specific IP ranges
  "Condition": {
    "IpAddress": { "aws:SourceIp": ["203.0.113.0/24", "198.51.100.0/24"] }
  }

  // Require MFA and restrict to office hours
  "Condition": {
    "Bool": { "aws:MultiFactorAuthPresent": "true" },
    "DateGreaterThan": { "aws:CurrentTime": "2024-01-01T09:00:00Z" },
    "DateLessThan": { "aws:CurrentTime": "2024-01-01T17:00:00Z" }
  }

5. IDENTITY-BASED vs RESOURCE-BASED POLICIES
================================================================

IDENTITY-BASED:
  - Attached to: IAM users, groups, roles
  - Controls: what the identity can do
  - No Principal element (implied by attachment)
  - Example: AmazonS3ReadOnlyAccess attached to alice

RESOURCE-BASED:
  - Attached to: S3 buckets, KMS keys, SQS queues, Lambda functions, SNS topics
  - Controls: who can access THIS resource
  - Must include Principal element
  - Enables cross-account access without role assumption
  
  S3 Bucket Policy (Resource-Based):
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Sid": "AllowOtherAccountRead",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::ACCOUNT_B:root" },
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }]
  }

CROSS-ACCOUNT ACCESS (two approaches):
  Option 1 (Role): Create role in Account A → Account B user assumes role
  Option 2 (Resource Policy): Attach resource policy to S3/Lambda in Account A
                              allowing Account B principal directly (no assume needed)

6. POLICY EVALUATION LOGIC (DETAILED)
================================================================

Evaluation order (most restrictive wins):

  1. ORGANIZATION SCPs — Sets the maximum boundary for the account
     If action is not allowed by SCP → DENIED (even if IAM allows)
  
  2. RESOURCE-BASED POLICIES — Check if resource explicitly allows/denies
  
  3. PERMISSIONS BOUNDARY — Limits max permissions of the identity
  
  4. SESSION POLICIES — Temporary restrictions on assumed role sessions
  
  5. IDENTITY-BASED POLICIES — Policies attached to the user/role
  
  DECISION LOGIC:
    a. Any explicit DENY? → ACCESS DENIED (regardless of allows)
    b. Any explicit ALLOW in identity-based AND boundary allows? → ALLOW
    c. Resource-based allows access + identity-based allows? → ALLOW
    d. Same account: resource-based OR identity-based allows → ALLOW
    e. Cross-account: BOTH resource-based AND identity-based must allow → ALLOW
    f. No explicit allow? → IMPLICIT DENY

IMPORTANT CROSS-ACCOUNT NOTE:
  - Within same account: resource-based ALLOW is sufficient (no identity policy needed)
  - Cross-account: BOTH resource-based policy AND caller's identity policy must allow

7. CREATING AND MANAGING POLICIES (CLI)
================================================================

  # Create a customer managed policy from a JSON file
  aws iam create-policy \
    --policy-name MyDeveloperPolicy \
    --policy-document file://developer-policy.json

  # Attach policy to a user
  aws iam attach-user-policy \
    --user-name alice \
    --policy-arn arn:aws:iam::123456789012:policy/MyDeveloperPolicy

  # Attach policy to a role
  aws iam attach-role-policy \
    --role-name LambdaExecutionRole \
    --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

  # List policies attached to a role
  aws iam list-attached-role-policies --role-name LambdaExecutionRole

  # Simulate policy evaluation
  aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::123456789012:user/alice \
    --action-names s3:GetObject \
    --resource-arns arn:aws:s3:::my-bucket/file.txt

8. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between AWS Managed and Customer Managed policies?
A: AWS Managed policies are created and maintained by AWS (e.g., AmazonS3FullAccess).
   You can use them but cannot modify them. Customer Managed policies are created
   by you — you have full control, can version them (up to 5 versions), and can
   customize them precisely. For production, Customer Managed policies are preferred
   because they let you apply least privilege more precisely than broad AWS Managed policies.

Q: What is the difference between an identity-based and a resource-based policy?
A: Identity-based policies are attached to IAM users, groups, or roles and define
   what that identity CAN DO. They have no Principal element. Resource-based policies
   are attached to AWS resources (S3, KMS, Lambda) and define WHO CAN ACCESS that
   resource — they require a Principal element. Resource-based policies enable
   cross-account access directly without requiring role assumption.

Q: If IAM allows S3:DeleteObject but SCP denies it, what happens?
A: The SCP wins — access is DENIED. SCPs in AWS Organizations set the MAXIMUM
   permissions for accounts in an OU. Even if IAM explicitly allows an action,
   if the SCP doesn't allow it, the action is blocked. SCPs don't grant permissions;
   they restrict the ceiling.

Q: How do you enforce that all S3 API calls use HTTPS?
A: Add a resource-based bucket policy with Effect: Deny, Action: s3:*, and
   Condition: Bool → aws:SecureTransport: false. This explicitly denies all
   S3 actions when the connection is not over HTTPS (secure transport is false).
   The Deny with this condition effectively forces HTTPS for all access.

Q: What is the Condition operator "BoolIfExists" used for?
A: BoolIfExists is used to handle cases where the condition key may or may not
   be present. For MFA: if you use plain Bool: aws:MultiFactorAuthPresent: false,
   it only applies when the key exists. BoolIfExists applies even when the key
   is absent (e.g., when using access keys programmatically, MFA key may not
   exist). For stricter MFA enforcement, use Deny + BoolIfExists.
