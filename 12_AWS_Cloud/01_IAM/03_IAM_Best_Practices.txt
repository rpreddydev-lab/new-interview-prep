================================================================
AWS IAM — BEST PRACTICES
Complete Interview Preparation Guide
================================================================

1. IDENTITY AND ACCESS BEST PRACTICES
================================================================

BEST PRACTICE 1: LOCK DOWN THE ROOT USER
  - Enable MFA on the root account immediately
  - Delete or do NOT create root access keys
  - Store root credentials securely (password manager)
  - Use root ONLY for tasks that require it:
    * Change account name, email, or root password
    * Change AWS Support plan
    * Close the AWS account
    * Enable IAM billing access
    * Restore IAM admin permissions
  
  CLI: Check if root has access keys (security audit)
  aws iam get-account-summary | grep -i root

---

BEST PRACTICE 2: CREATE INDIVIDUAL IAM USERS (OR USE SSO)
  - Never share credentials between users
  - One IAM user per person or application
  - Better: Use AWS IAM Identity Center (SSO) for human users
  - Assign individual users — never use a generic "admin" account

---

BEST PRACTICE 3: USE IAM GROUPS TO MANAGE PERMISSIONS
  - Assign permissions to groups, add users to groups
  - Do NOT attach policies directly to individual users (hard to manage)
  - Groups by job function: Developers, Admins, DataEngineers, ReadOnly

---

BEST PRACTICE 4: ENFORCE LEAST PRIVILEGE
  - Start with zero permissions; grant only what's needed
  - Use IAM Access Analyzer to generate least-privilege policies from activity
  - Use aws:ResourceTag conditions to restrict access to tagged resources
  - Regularly review and remove unused permissions
  - Use inline policies sparingly; prefer customer managed for reusability

---

BEST PRACTICE 5: ENABLE MFA FOR ALL USERS
  - Enable MFA for all IAM users, especially those with console access
  - Enforce MFA via IAM policy with Deny + BoolIfExists condition
  - Use virtual MFA (Google Authenticator) or hardware keys (YubiKey)
  
  Policy to require MFA for console actions:
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Sid": "DenyWithoutMFA",
      "Effect": "Deny",
      "NotAction": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ListVirtualMFADevices",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
      }
    }]
  }

---

BEST PRACTICE 6: USE IAM ROLES FOR APPLICATIONS, NOT ACCESS KEYS
  - EC2 applications: attach IAM role via instance profile
  - Lambda functions: use execution role
  - ECS tasks: use task role (taskRoleArn)
  - EKS pods: use IAM Roles for Service Accounts (IRSA)
  - Never hardcode access keys in code or config files
  
  Code smell (WRONG):
    aws.config.update({
      accessKeyId: 'AKIAIOSFODNN7EXAMPLE',  // BAD
      secretAccessKey: 'wJalrXUtnFEMI/K7MDENGbPxRfiCYEXAMPLEKEY'  // BAD
    });
  
  Correct approach:
    // SDK automatically picks up credentials from:
    // 1. EC2 instance profile / Lambda execution role
    // 2. Environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY)
    // 3. ~/.aws/credentials (local dev only)
    // 4. IAM Identity Center (SSO) profile

---

BEST PRACTICE 7: ROTATE CREDENTIALS REGULARLY
  - Access keys should be rotated every 90 days (or per policy)
  - Use IAM Credential Report to find aged credentials
  - Use IAM Access Advisor to find unused credentials/services
  - Delete unused access keys and IAM users immediately
  
  # Find access keys older than 90 days (via credential report)
  aws iam generate-credential-report
  aws iam get-credential-report | python3 -c "import sys,json,base64; 
    data=json.loads(sys.stdin.read()); print(base64.b64decode(data['Content']).decode())"

---

BEST PRACTICE 8: USE PERMISSIONS BOUNDARIES FOR DELEGATED ADMINS
  - Prevent privilege escalation when developers can create IAM entities
  - Set permissions boundary on any IAM user/role created by devs
  - Boundary = developer cannot create something with MORE permissions than they have

---

BEST PRACTICE 9: MONITOR AND AUDIT IAM ACTIVITY
  - Enable AWS CloudTrail to log all IAM API calls
  - Use Amazon GuardDuty to detect unusual IAM activity
  - Use AWS Config to check IAM compliance rules
  - Set up CloudWatch alarms for root login or unusual API patterns

---

BEST PRACTICE 10: USE AWS ORGANIZATIONS WITH SCPS
  - Use AWS Organizations to manage multiple accounts
  - Apply Service Control Policies (SCPs) to restrict actions account-wide
  - Prevent specific regions from being used (cost/compliance)
  - Deny ability to leave the organization

2. ACCESS KEY MANAGEMENT BEST PRACTICES
================================================================

NEVER DO:
  ✗ Commit access keys to Git repositories
  ✗ Put keys in environment variables in code
  ✗ Share access keys between people
  ✗ Use root user access keys
  ✗ Leave unused access keys active

ALWAYS DO:
  ✓ Use IAM roles instead of access keys for AWS services
  ✓ Rotate access keys every 90 days
  ✓ Create new key → update applications → deactivate old → delete old
  ✓ Use IAM Credential Report to audit key age
  ✓ Use AWS Secrets Manager to store app credentials (not IAM keys)

ROTATION PROCESS:
  1. aws iam create-access-key --user-name myapp
  2. Update your application with the new key
  3. Test the application works
  4. aws iam update-access-key --access-key-id OLD_KEY --status Inactive --user-name myapp
  5. Verify nothing breaks (keep inactive for a few days)
  6. aws iam delete-access-key --access-key-id OLD_KEY --user-name myapp

3. TOOLS FOR IAM BEST PRACTICES
================================================================

IAM ACCESS ANALYZER
  - Analyzes resource policies to find external access
  - Generates policy based on actual CloudTrail activity (last 90 days)
  - Validates IAM policies against best practices during creation
  - Available in IAM console: Access analyzer → Create analyzer
  
  Use cases:
  - Find S3 buckets accessible by outside accounts
  - Find roles that can be assumed by external principals
  - Generate least-privilege policy for Lambda execution roles

IAM CREDENTIAL REPORT
  - Account-level report listing all IAM users
  - Columns: username, arn, user_creation_time, password_enabled,
    password_last_used, password_last_changed, mfa_active, access_key_1_active,
    access_key_1_last_used_date, access_key_2_active, access_key_2_last_used_date
  
  Generate:
    aws iam generate-credential-report
    aws iam get-credential-report
  
  Used for: Security audits, compliance reports, finding stale credentials

IAM ACCESS ADVISOR
  - Per-user/role view: shows when each AWS service was last accessed
  - If a service was never used, remove the permission
  - Helps refine policies toward least privilege

AWS CONFIG RULES FOR IAM
  - iam-root-access-key-check: Root has no access keys
  - iam-user-mfa-enabled: All IAM users have MFA
  - iam-password-policy: Account password policy meets requirements
  - access-keys-rotated: Access keys rotated within N days
  - iam-no-inline-policy-check: No inline policies on users
  - iam-user-no-policies-check: No policies directly on users (use groups)

4. SECURITY INCIDENT RESPONSE FOR IAM
================================================================

If credentials are compromised:
  1. Immediately deactivate the access key:
     aws iam update-access-key --access-key-id COMPROMISED_KEY --status Inactive --user-name user

  2. Check CloudTrail for what was done with the key:
     aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=COMPROMISED_KEY

  3. Revoke all active sessions for assumed roles:
     Update the role's trust policy to include a Deny with aws:TokenIssueTime condition

  4. Check for any IAM changes made (new users, policies created):
     Look for CreateUser, AttachUserPolicy, CreateRole in CloudTrail

  5. Delete the compromised key and create a new one

  6. Review and remove any resources created during the incident

5. INTERVIEW QUESTIONS
================================================================

Q: What are the top 5 IAM security best practices?
A: 1) Lock down root user — enable MFA, delete root access keys, never use daily.
   2) Use IAM roles for AWS services (EC2, Lambda) — never hardcode access keys.
   3) Apply least privilege — start with zero, add only what's needed.
   4) Enable MFA for all human IAM users with console access.
   5) Monitor with CloudTrail + GuardDuty and audit with IAM Credential Report regularly.

Q: How do you prevent a developer from hardcoding AWS credentials in code?
A: Multiple layers: 1) Use IAM roles for EC2/Lambda/ECS (no keys needed).
   2) Use AWS Secrets Manager for app-level credentials. 3) Use git-secrets or
   truffleHog in CI/CD to scan for committed secrets. 4) Use IAM Access Analyzer
   to generate least-privilege role policies. 5) Enforce a company policy and
   code review. 6) Use environment variables with roles, not hardcoded keys.

Q: What happens if someone accidentally commits AWS access keys to a public GitHub repo?
A: AWS has automated scanning that detects keys in GitHub and may alert you.
   Immediate steps: 1) Deactivate the key immediately in IAM console.
   2) Check CloudTrail for any unauthorized usage in the last few hours.
   3) Assess damage — look for created resources, data accessed, IAM changes.
   4) Rotate the key. 5) Remediate any damage. 6) Consider enabling AWS GuardDuty
   for ongoing threat detection. 7) Set up git-secrets to prevent future occurrences.

Q: What is IAM Access Analyzer and when would you use it?
A: IAM Access Analyzer identifies resources (S3 buckets, IAM roles, KMS keys, etc.)
   that are shared with external entities. It uses formal verification to analyze
   policies and find unintended external access. You'd use it during security
   audits to find over-permissive resources, when generating least-privilege policies
   from CloudTrail activity, and for continuous validation of IAM policies during
   CI/CD deployments.
