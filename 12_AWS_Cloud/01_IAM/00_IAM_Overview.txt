AWS IAM — OVERVIEW
Complete Interview Preparation Guide
================================================================

1. WHAT IS AWS IAM?
================================================================

AWS Identity and Access Management (IAM) is a web service that helps
securely control access to AWS resources. With IAM, you control who can
authenticate (sign in) and who is authorized (has permissions) to use
AWS resources.

IAM is:
  - FREE — no additional charge
  - GLOBAL — not region-specific; IAM entities are available everywhere
  - EVENTUALLY CONSISTENT — changes may take a few seconds to propagate

================================================================
2. CORE IAM CONCEPTS
================================================================

PRINCIPAL
  An entity that can make requests to AWS.
  Types: IAM users, IAM roles, AWS services, federated users

AUTHENTICATION
  Verifying identity — who are you?
  Methods: username+password (console), access key ID+secret (CLI/API),
           MFA token, temporary credentials (STS)

AUTHORIZATION
  Determining permissions — what can you do?
  Evaluated via policies attached to the principal

PRINCIPAL TYPES:
  ┌─────────────────────────────────────────────────────────────────┐
  │ IAM User    │ Long-term credentials, represents a person or app │
  │ IAM Group   │ Collection of users; policies attached to group   │
  │ IAM Role    │ Temporary credentials; assumed by services/users  │
  │ Root User   │ Account owner; unrestricted; should NOT be used   │
  └─────────────────────────────────────────────────────────────────┘

================================================================
3. IAM USERS
================================================================

Definition: An IAM user is an entity created in AWS to represent a
person or application that interacts with AWS.

Credentials:
  - Console access: Username + Password (+ optional MFA)
  - Programmatic access: Access Key ID + Secret Access Key

Access Keys:
  - Used for CLI, SDK, API calls
  - Max 2 access keys per user (for rotation)
  - Should be rotated regularly (use IAM Access Advisor to check)
  - NEVER hardcode in code; use IAM roles instead

Root User:
  - Created when the AWS account is created
  - Full unrestricted access to all AWS services
  - Best practice: Enable MFA, delete root access keys, and use only for:
    * Changing account name/email
    * Enabling IAM billing access
    * Closing the AWS account
    * Changing AWS Support plan

================================================================
4. IAM GROUPS
================================================================

Definition: A collection of IAM users. Policies attached to a group
apply to all users in the group.

Rules:
  - Groups cannot contain other groups
  - A user can belong to multiple groups
  - Groups have no credentials (cannot sign in as a group)
  - Used to assign permissions to job functions (Admins, Developers, etc.)

Example:
  Group: "Developers" → AttachPolicy: AmazonS3ReadOnlyAccess + EC2FullAccess
  Users: alice, bob, carol (all inherit those permissions)

================================================================
5. IAM ROLES
================================================================

Definition: An IAM role is an IAM entity with a trust policy defining who
can ASSUME it, and permission policies defining what actions are allowed.

Key Characteristics:
  - No long-term credentials (passwords or access keys)
  - Uses temporary security credentials via STS (15 min – 12 hours)
  - Can be assumed by: AWS services, IAM users, federated users, other accounts

Role Components:
  1. Trust Policy:  defines WHO can assume the role
  2. Permission Policy: defines WHAT the role can do

Common Use Cases:
  ┌──────────────────────────────────────────────────────────────┐
  │ EC2 IAM Role      │ EC2 instance accesses S3/DynamoDB        │
  │ Lambda IAM Role   │ Lambda function accesses other services  │
  │ Cross-Account     │ Role in Account A assumed by Account B   │
  │ Federated User    │ SAML/OIDC users assume a role            │
  │ Service Role      │ CloudFormation creates resources         │
  │ Service-Linked    │ Predefined by AWS for a specific service │
  └──────────────────────────────────────────────────────────────┘

Trust Policy Example (allows EC2 to assume the role):
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }]
  }

Permission Policy Example (allows S3 read):
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"]
    }]
  }

================================================================
6. IAM POLICIES
================================================================

Definition: Documents (JSON) that define permissions.

Policy Types:
  - AWS Managed: Created/maintained by AWS (e.g., AmazonS3FullAccess)
  - Customer Managed: Created by you; can be attached to multiple identities
  - Inline: Embedded directly in a user/group/role; 1:1 relationship

Policy Structure:
  {
    "Version": "2012-10-17",          // Always this version
    "Statement": [
      {
        "Sid": "UniqueStatementId",   // Optional
        "Effect": "Allow | Deny",     // Required
        "Action": ["s3:PutObject"],   // Required (or NotAction)
        "Resource": ["arn:..."],      // Required (or NotResource)
        "Condition": { ... }          // Optional
      }
    ]
  }

================================================================
7. POLICY EVALUATION LOGIC
================================================================

AWS evaluates policies in this order:

  Step 1: EXPLICIT DENY → if any policy denies, ACCESS DENIED
  Step 2: EXPLICIT ALLOW → if any policy allows, ACCESS ALLOWED
  Step 3: IMPLICIT DENY → default if no allow found, ACCESS DENIED

  Rule: Explicit DENY always wins, even if there's an Allow.

  +-----------------------------------------------+
  |  Is there an explicit Deny?   → YES → DENY     |
  |                                ↓ NO            |
  |  Is there an explicit Allow?  → YES → ALLOW    |
  |                                ↓ NO            |
  |  IMPLICIT DENY (default)       → DENY          |
  +-----------------------------------------------+

================================================================
8. IAM ACCESS MANAGEMENT TOOLS
================================================================

  IAM Access Analyzer
    - Identifies resources shared with external entities
    - Flags overly permissive S3 buckets, IAM roles, KMS keys
    - Generates least-privilege policies from CloudTrail activity

  IAM Credentials Report
    - CSV report listing all IAM users and credential status
    - Shows: password age, MFA status, last used, access key rotation

  IAM Access Advisor
    - Shows when each service was last accessed by a user/role
    - Helps identify unused permissions for least-privilege refinement

  AWS Organizations + Service Control Policies (SCPs)
    - SCPs restrict what IAM can allow across entire AWS accounts/OUs
    - SCPs do NOT grant permissions; they set the maximum boundary

9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between an IAM user and an IAM role?
A: An IAM user has permanent long-term credentials (password + access keys)
   and represents a specific person or application. An IAM role has no
   permanent credentials; it issues temporary credentials via STS when
   assumed. Roles are used by AWS services (EC2, Lambda), cross-account
   access, and federated identity. Best practice is to use roles over
   long-term user credentials wherever possible.

Q: What is the principle of least privilege and how do you implement it in IAM?
A: Least privilege means granting only the minimum permissions required.
   In IAM: start with no permissions, add only required actions/resources,
   use conditions to restrict (e.g., MFA required, specific IP ranges),
   use IAM Access Analyzer to find unused permissions from CloudTrail, and
   use customer-managed policies for precise control over AWS managed policies.

Q: Explain the IAM policy evaluation order.
A: 1) Explicit Deny always wins. 2) If no Deny and there's an explicit
   Allow, access is granted. 3) If neither, implicit Deny applies. So
   if you have Allow S3:* and Deny S3:DeleteObject, delete will be denied
   but all other S3 actions are allowed.

Q: Why shouldn't you use the root user account for daily tasks?
A: The root user has unrestricted access to everything and cannot be
   restricted by IAM policies. If compromised, it gives full account access.
   Best practice: Enable MFA on root, delete root access keys, use the root
   only for specific tasks (billing settings, account closure, support plan
   changes), and create separate admin IAM users for daily admin tasks.

Q: A Lambda function needs to read from DynamoDB. How do you give it access?
A: Create an IAM execution role with a permission policy allowing
   dynamodb:GetItem/Query/Scan on the specific table ARN. Attach this role
   to the Lambda function (not an access key — never hardcode credentials).
   Lambda automatically receives temporary credentials from STS when the
   function runs. This follows the principle of least privilege.
