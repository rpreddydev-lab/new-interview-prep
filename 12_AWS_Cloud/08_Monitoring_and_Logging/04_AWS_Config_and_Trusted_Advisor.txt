1. AWS CONFIG ADVANCED PATTERNS
================================================================

  MULTI-ACCOUNT CONFIG AGGREGATOR:
    Collect Config data from all accounts and regions.
    
    aws configservice put-configuration-aggregator \
      --configuration-aggregator-name OrgAggregator \
      --organization-aggregation-source '{
        "RoleArn": "arn:aws:iam::123456789012:role/config-org-role",
        "AllAwsRegions": true
      }'
  
  PROACTIVE COMPLIANCE (Config + CloudFormation):
    - Use Config rules as pre-deployment checks in CloudFormation hooks
    - Prevent non-compliant resources from being created
    - CloudFormation Guard (cfn-guard): rule-based validation before deploy

  CONFORMANCE PACKS — QUERY AGGREGATE COMPLIANCE:
  aws configservice describe-aggregate-compliance-by-config-rules \
    --configuration-aggregator-name OrgAggregator \
    --filters '{"ConfigRuleName": "s3-bucket-public-read-prohibited"}'

2. AWS CONFIG — RESOURCE TIMELINE
================================================================

  View configuration change history for any resource:
  
  aws configservice get-resource-config-history \
    --resource-type AWS::EC2::SecurityGroup \
    --resource-id sg-12345678 \
    --start-time 2024-01-01T00:00:00Z \
    --end-time 2024-01-31T23:59:59Z
  
  Use cases:
    - "When was this security group changed to allow 0.0.0.0/0 on port 22?"
    - "What did this IAM role's policies look like 3 months ago?"
    - "Who last changed this S3 bucket policy?" (combine with CloudTrail)

3. OPERATIONAL MONITORING BEST PRACTICES
================================================================

  THE 4 GOLDEN SIGNALS (Google SRE):
  
  1. LATENCY: Time to serve a request (p50, p95, p99)
     CloudWatch: ALB TargetResponseTime, Lambda Duration
  
  2. TRAFFIC: Requests per second
     CloudWatch: ALB RequestCount, API Gateway Count
  
  3. ERRORS: Error rate (4xx, 5xx)
     CloudWatch: ALB HTTPCode_Target_5XX_Count, Lambda Errors
  
  4. SATURATION: How full the system is (CPU, memory, queue depth)
     CloudWatch: EC2 CPUUtilization, SQS ApproximateNumberOfMessagesVisible
  
  COMPOSITE DASHBOARD STRUCTURE:
    Row 1: Traffic (RPS) + Error Rate + P99 Latency
    Row 2: ALB health (healthy host count, connection errors)
    Row 3: Lambda metrics (invocations, errors, duration, throttles)
    Row 4: Database (RDS connections, latency, IOPS)
    Row 5: Queue depth (SQS messages visible, age of oldest message)
    Row 6: Cost (Billing alarm)

4. CLOUDWATCH ANOMALY DETECTION
================================================================

  ML-based model learns metric's normal behavior (trends, seasonality)
  and creates an expected band. Alert when metric goes outside the band.
  
  CLI:
  aws cloudwatch put-anomaly-detector \
    --namespace AWS/EC2 \
    --metric-name CPUUtilization \
    --dimensions Name=InstanceId,Value=i-1234567890abcdef0 \
    --stat Average
  
  Create alarm using anomaly detection:
  aws cloudwatch put-metric-alarm \
    --alarm-name "cpu-anomaly" \
    --comparison-operator GreaterThanUpperThreshold \
    --evaluation-periods 2 \
    --metrics '[{
      "Id": "m1",
      "MetricStat": {
        "Metric": {"Namespace": "AWS/EC2", "MetricName": "CPUUtilization",
                   "Dimensions": [{"Name": "InstanceId", "Value": "i-1234567890abcdef0"}]},
        "Period": 300,
        "Stat": "Average"
      }
    }, {
      "Id": "ad1",
      "Expression": "ANOMALY_DETECTION_BAND(m1, 2)"
    }]' \
    --threshold-metric-id ad1 \
    --alarm-actions arn:aws:sns:us-east-1:123456789012:ops-alerts

5. CLOUDWATCH SYNTHETICS (CANARIES)
================================================================

  Scheduled scripts that test your endpoints/APIs continuously.
  
  Use cases:
    - Monitor that login page loads within 3 seconds
    - Check API endpoints return correct responses
    - Verify SSL certificate validity
    - Simulate user flows (heartbeat, API canary, visual monitoring)
  
  Results:
    - Success/failure metrics to CloudWatch
    - Screenshots and HAR files to S3
    - Alert before real users experience issues
  
  Runtimes: Node.js or Python
  
  aws synthetics create-canary \
    --name api-health-check \
    --code '{"S3Bucket":"canary-code","S3Key":"canary.zip"}' \
    --artifact-s3-location s3://canary-results/ \
    --execution-role-arn arn:aws:iam::123456789012:role/canary-role \
    --schedule '{
      "Expression": "rate(5 minutes)"
    }' \
    --run-config '{
      "TimeoutInSeconds": 60,
      "ActiveTracing": true
    }' \
    --runtime-version syn-nodejs-puppeteer-7.0

6. INTERVIEW QUESTIONS
================================================================

Q: How would you set up a monitoring strategy for a new microservice on AWS?
A: Use the 4 golden signals as the foundation:
   
   1. Traffic: CloudWatch alarm on RequestCount drop > 50% for 5 min (broken deployment)
   
   2. Errors: 
      - ALB 5xx alarm: HTTPCode_Target_5XX_Count > 1% of total requests
      - Lambda error alarm: Errors > 0 for 5 consecutive minutes
      - CloudWatch Logs metric filter on ERROR/Exception → alarm
   
   3. Latency:
      - ALB p99 latency alarm: TargetResponseTime p99 > 2 seconds
      - Lambda duration alarm: Duration p99 > 80% of timeout
   
   4. Saturation:
      - SQS queue depth alarm: ApproximateNumberOfMessagesVisible > 10,000
      - Lambda throttles alarm: Throttles > 0
      - RDS connection alarm: DatabaseConnections > 80% of max_connections
   
   Additional:
      - X-Ray: enable Active tracing for end-to-end visibility
      - CloudWatch Synthetics: scheduled canary against health endpoint
      - CloudWatch Dashboard: one page showing all golden signals
      - PagerDuty/Slack integration via SNS for HIGH severity alarms

Q: What is the difference between CloudWatch metric alarms and anomaly detection alarms?
A: A metric alarm uses a fixed threshold — "alarm if CPUUtilization > 80%." This requires 
   you to know what "bad" looks like in advance.
   
   Anomaly detection uses ML to learn the metric's normal pattern (time-of-day, day-of-week 
   trends). It creates an expected band based on historical data. An anomaly alarm fires 
   when the metric deviates outside the band, regardless of absolute value.
   
   Example: A web app CPU always spikes to 60% on Monday mornings (scheduled batch). 
   A fixed 80% alarm might never fire. An anomaly alarm fires if CPU unexpectedly 
   spikes at 3am to 60% because it knows 3am should be near 5%.
   
   Use fixed thresholds for clear capacity limits (disk full, error rate).
   Use anomaly detection for metrics with regular patterns that vary by time.
