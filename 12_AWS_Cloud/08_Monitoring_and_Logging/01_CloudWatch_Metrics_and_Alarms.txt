AWS MONITORING — CLOUDWATCH METRICS & ALARMS
Complete Interview Preparation Guide
================================================================

1. CLOUDWATCH OVERVIEW
================================================================

  Amazon CloudWatch is the observability backbone of AWS:
    - Metrics: numeric time-series data from AWS services and apps
    - Logs: structured and unstructured log storage and analysis
    - Alarms: threshold-based notifications and automated actions
    - Dashboards: visual monitoring across services
    - Events/EventBridge: react to changes in AWS resources
    - ServiceLens: distributed tracing with X-Ray integration
    - Synthetics: canary scripts for endpoint monitoring
    - RUM: Real User Monitoring for browser apps
    - Contributor Insights: identify top contributors to metrics

================================================================
2. CLOUDWATCH METRICS
================================================================

  METRIC: Name + Namespace + Dimensions + Timestamps + Values
  
  Namespace: Logical grouping (e.g., AWS/EC2, AWS/RDS, AWS/Lambda)
  Dimensions: Key-value pairs that identify a specific metric instance
    Example: InstanceId=i-1234567890abcdef0
  
  STANDARD METRICS vs DETAILED MONITORING:
    Standard: Published every 5 minutes (EC2 default) — Free
    Detailed: Published every 1 minute — Small additional cost
    
    Enable detailed monitoring on EC2:
    aws ec2 monitor-instances --instance-ids i-1234567890abcdef0

  KEY METRICS PER SERVICE:
  
  EC2:
    - CPUUtilization, NetworkIn/NetworkOut
    - DiskReadBytes/DiskWriteBytes (instance store only)
    - StatusCheckFailed_Instance, StatusCheckFailed_System
    - Note: RAM utilization is NOT a default metric (need CloudWatch Agent)
  
  RDS:
    - CPUUtilization, FreeStorageSpace
    - DatabaseConnections, ReadLatency/WriteLatency
    - FreeableMemory, ReadIOPS/WriteIOPS
    - ReplicaLag (for read replicas)
  
  ALB:
    - RequestCount, TargetResponseTime
    - HTTPCode_Target_4XX_Count, HTTPCode_Target_5XX_Count
    - HealthyHostCount, UnHealthyHostCount
    - ActiveConnectionCount, ProcessedBytes
  
  Lambda:
    - Invocations, Duration, Errors, Throttles
    - ConcurrentExecutions, ProvisionedConcurrencyUtilization
    - IteratorAge (for Kinesis/DynamoDB Streams)
  
  SQS:
    - NumberOfMessagesSent, NumberOfMessagesDeleted
    - ApproximateNumberOfMessagesVisible (queue depth)
    - ApproximateAgeOfOldestMessage

3. CUSTOM METRICS
================================================================

  Send your own metrics from EC2, Lambda, on-premises, etc.
  
  CLI:
  aws cloudwatch put-metric-data \
    --namespace "MyApp/OrderService" \
    --metric-name "OrdersProcessed" \
    --value 42 \
    --dimensions ServiceName=OrderService,Environment=prod \
    --unit Count \
    --timestamp 2024-01-15T12:00:00Z
  
  HIGH RESOLUTION:
    Standard metrics: 1-minute resolution (minimum)
    High-resolution custom metrics: 1-second resolution (StorageResolution=1)
    More expensive to store and retrieve
  
  Java SDK v2:
  import software.amazon.awssdk.services.cloudwatch.CloudWatchClient;
  import software.amazon.awssdk.services.cloudwatch.model.*;
  
  private static final CloudWatchClient cwClient = CloudWatchClient.create();
  
  public void putMetric(String namespace, String metricName, double value) {
      cwClient.putMetricData(PutMetricDataRequest.builder()
          .namespace(namespace)
          .metricData(MetricDatum.builder()
              .metricName(metricName)
              .value(value)
              .unit(StandardUnit.COUNT)
              .dimensions(Dimension.builder()
                  .name("Environment")
                  .value("prod")
                  .build())
              .build())
          .build());
  }

4. CLOUDWATCH AGENT
================================================================

  Install on EC2 (or on-premises) to collect:
    - System-level metrics: RAM, disk usage, swap (not available natively)
    - Application logs: log files from /var/log/* or custom paths
    - Custom metrics via StatsD or collectd
  
  Configuration: JSON config file or via SSM Parameter Store
  
  Install via SSM Run Command (recommended):
  aws ssm send-command \
    --targets '[{"Key":"tag:Environment","Values":["prod"]}]' \
    --document-name "AWS-ConfigureAWSPackage" \
    --parameters '{"action":["Install"],"name":["AmazonCloudWatchAgent"]}'

5. CLOUDWATCH ALARMS
================================================================

  ALARM STATES:
    OK: metric within threshold
    ALARM: metric breached threshold
    INSUFFICIENT_DATA: not enough data to evaluate

  ALARM TYPES:
    Metric Alarm: based on a single CloudWatch metric
    Composite Alarm: combines multiple alarms with AND/OR logic
    Anomaly Detection Alarm: ML-based, alert when metric deviates from expected band

  CREATE ALARM (CLI):
  aws cloudwatch put-metric-alarm \
    --alarm-name "HighCPU-prod-web" \
    --alarm-description "CPU > 80% for 5 minutes" \
    --metric-name CPUUtilization \
    --namespace AWS/EC2 \
    --dimensions Name=InstanceId,Value=i-1234567890abcdef0 \
    --statistic Average \
    --period 300 \
    --evaluation-periods 1 \
    --threshold 80 \
    --comparison-operator GreaterThanOrEqualToThreshold \
    --alarm-actions arn:aws:sns:us-east-1:123456789012:ops-alerts \
    --ok-actions arn:aws:sns:us-east-1:123456789012:ops-alerts \
    --treat-missing-data notBreaching

  KEY PARAMETERS:
    Period: data point aggregation window (60, 300, 3600 seconds)
    EvaluationPeriods: how many periods to evaluate
    DatapointsToAlarm: how many data points in EvaluationPeriods must breach
      Example: 3/5 = 3 of the last 5 data points must breach threshold
    Statistic: Average, Sum, Minimum, Maximum, SampleCount
    TreatMissingData: missing, notBreaching, breaching, ignore

6. ALARM ACTIONS
================================================================

  What alarms can trigger:
    - SNS notification (email, SMS, Lambda, HTTP)
    - EC2 actions: Stop, Reboot, Terminate, Recover
    - Auto Scaling: scale in / scale out
    - Systems Manager OpsCenter: create OpsItem
    - Lambda (via SNS subscription)
  
  AUTO-SCALING BASED ON METRICS:
    Scale-out policy: CPUUtilization > 70% for 2 data points → add 1 instance
    Scale-in policy:  CPUUtilization < 30% for 10 data points → remove 1 instance
    
    Cooldown period: prevents rapid scaling back and forth

8. INTERVIEW QUESTIONS
================================================================

Q: How do you monitor RAM usage on EC2 instances with CloudWatch?
A: RAM is not a default CloudWatch metric for EC2 — it requires the CloudWatch Agent.
   Install the CloudWatch Agent on the instance (via SSM Automation or user data). 
   Configure it to collect mem_used_percent. The agent reports it to a custom namespace 
   (CWAgent by default). You can then create alarms on mem_used_percent just like 
   CPUUtilization. For containerized workloads on ECS, container-level memory metrics 
   are available natively. For Lambda, memory-related metrics (MemorySize, max memory 
   used) are in CloudWatch Logs Insights via the REPORT line.

Q: What is the difference between Period and EvaluationPeriods in a CloudWatch Alarm?
A: Period is the aggregation window for each data point (e.g., 300 seconds = 5-minute 
   averages). EvaluationPeriods is how many consecutive data points to look at when 
   deciding to alarm. DatapointsToAlarm is how many of those data points must breach.
   
   Example: Period=300, EvaluationPeriods=3, DatapointsToAlarm=2, Threshold=80%
   → Look at the last 15 minutes of average CPU; alarm if 2 out of 3 five-minute 
   averages exceed 80%. This prevents false alarms from brief spikes.
   
   Use EvaluationPeriods > DatapointsToAlarm (e.g., 3/5) for noisy metrics to 
   require sustained breach rather than occasional spike.

Q: How do you create a composite alarm and why would you use one?
A: Composite alarms combine multiple metric alarms with AND/OR logic:
   aws cloudwatch put-composite-alarm \
     --alarm-name "AppDown" \
     --alarm-rule "ALARM(HighCPU) OR ALARM(HighErrors5xx)"
   
   Use cases: (1) Reduce alert fatigue — page on-call only when BOTH CPU is high AND 
   error rate is high (real issue), not for either alone. (2) Create an umbrella alarm 
   for dashboards that shows overall service health. (3) Suppress child alarms during 
   maintenance by putting the composite alarm in OK state via actions. 
   Composite alarms don't monitor metrics directly — they combine existing alarms.
