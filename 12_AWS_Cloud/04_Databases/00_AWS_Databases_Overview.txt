1. DATABASE LANDSCAPE ON AWS
================================================================

  AWS offers both managed relational and non-relational databases,
  plus purpose-built databases optimized for specific use cases.
  
  MANAGED vs SELF-MANAGED:
    Managed (RDS, DynamoDB, etc.): AWS handles OS patching, backups,
    HA, failover, scaling. You manage schema, queries, data.
    Self-managed (EC2 + MySQL): You handle everything including patching.

3. RELATIONAL vs NON-RELATIONAL ON AWS
================================================================

  RELATIONAL (OLTP — Online Transaction Processing):
    - RDS, Aurora
    - ACID transactions
    - Structured schema (tables, rows, columns)
    - SQL queries
    - Vertical scaling primarily (though Aurora scales read replicas)
    - Use when: you need relationships between entities, strict consistency,
                JOINs, complex queries, existing SQL-based applications

  NON-RELATIONAL:
    - DynamoDB: key-value + document, single-digit ms latency, auto-scale
    - DocumentDB: MongoDB-compatible document database
    - Keyspaces: Cassandra-compatible wide-column
    - Use when: high throughput, flexible schema, horizontal scaling

  IN-MEMORY (Caching Layer):
    - ElastiCache: Redis or Memcached
    - Nanosecond to microsecond latency
    - Use in front of RDS or DynamoDB to reduce database load

  ANALYTICAL (OLAP — Online Analytical Processing):
    - Redshift: Columnar storage, petabyte-scale data warehouse
    - NOT for transactional workloads — designed for bulk analytical queries

4. DATABASE DECISION TREE
================================================================

  Need to store data?
    ↓
  Is it structured relational data with ACID requirements?
    YES → RDS (MySQL/Postgres) or Aurora
    ↓
  Do you need massive scale (millions of requests/sec) with flexible schema?
    YES → DynamoDB
    ↓
  Need to cache expensive database queries or store session data?
    YES → ElastiCache (Redis for persistence, Memcached for simple cache)
    ↓
  Need to run complex analytical SQL on large datasets (GB–PB)?
    YES → Redshift
    ↓
  Is your data JSON documents and you have a MongoDB workload?
    YES → Amazon DocumentDB
    ↓
  Graph relationships (social network, fraud detection)?
    YES → Amazon Neptune
    ↓
  Time-series IoT or metrics data?
    YES → Amazon Timestream

6. INTERVIEW QUESTIONS
================================================================

Q: How do you choose between RDS and DynamoDB?
A: Use RDS when you need: ACID transactions across multiple tables/rows,
   complex JOINs and relational queries, existing SQL-based application,
   structured schema, reporting queries. Use DynamoDB when you need:
   predictable single-digit millisecond latency at any scale, flexible schema,
   horizontal auto-scaling to millions of requests/sec, serverless/pay-per-use model,
   simple access patterns (get-by-key, scan with filter). DynamoDB does NOT support
   JOINs or complex ad-hoc queries efficiently.

Q: What is OLTP vs OLAP and which AWS services support each?
A: OLTP (Online Transaction Processing): Handles many short transactional queries —
   inserts, updates, deletes. Optimized for write throughput and low latency.
   AWS: RDS, Aurora, DynamoDB. OLAP (Online Analytical Processing): Handles complex
   analytical queries on large datasets — aggregations, GROUP BY, window functions
   over millions of rows. Optimized for read throughput. AWS: Redshift.
   Never use RDS for large analytical workloads — it will be slow and expensive.

Q: Why use ElastiCache with RDS?
A: ElastiCache is an in-memory cache that stores frequently read data in RAM,
   providing microsecond latency vs milliseconds for RDS. Benefits: reduces database
   load (fewer queries hit DB), faster response times, protects database from
   traffic spikes. Common patterns: cache-aside (app checks cache first, falls back
   to DB on miss), write-through (write to cache and DB simultaneously), session
   storage (store user sessions in Redis instead of DB/cookies).
