================================================================
AWS DATABASES — REDSHIFT DATA WAREHOUSE
Complete Interview Preparation Guide
================================================================

1. REDSHIFT OVERVIEW
================================================================

  Amazon Redshift is a fully managed, petabyte-scale data warehouse
  designed for OLAP (Online Analytical Processing) — complex analytical
  queries over large datasets.

  Key characteristics:
    - Columnar storage (vs row-based in OLTP databases)
    - Massively Parallel Processing (MPP)
    - SQL interface (PostgreSQL-compatible)
    - Integrates with S3, Glue, QuickSight, SageMaker
    - Scales from 100GB to petabytes
    - NOT for transactional workloads (OLTP) — use RDS/Aurora for that

================================================================
2. WHY COLUMNAR STORAGE?
================================================================

  ROW-BASED (OLTP — RDS, MySQL):
    [id=1, name="Alice", age=30, salary=5000]
    [id=2, name="Bob",   age=25, salary=4500]
    Good for: INSERT, UPDATE, full row retrieval (transactional)
    Bad for: SELECT AVG(salary) FROM employees → reads EVERY column of every row

  COLUMN-BASED (OLAP — Redshift):
    [id:    1, 2, 3, ...]
    [name:  "Alice", "Bob", ...]
    [age:   30, 25, ...]
    [salary: 5000, 4500, ...]
    Good for: SELECT AVG(salary) → reads ONLY the salary column
    Benefits:
      - I/O reduction: scan only needed columns
      - Compression: similar values in same column compress better
      - Vectorized execution: process blocks of column data at once

================================================================
3. REDSHIFT ARCHITECTURE
================================================================

  CLUSTER (Traditional):
    - Leader Node:  Receives queries, parses, builds execution plan, coordinates workers
    - Compute Nodes: Execute queries in parallel, store data
    - Node types:
        dc2.large / dc2.8xlarge:    Dense Compute (SSD, fast I/O)
        ra3.xlplus / ra3.4xlarge / ra3.16xlarge: Managed Storage (large hot data in memory,
                                                  cold data on S3 — decouples compute/storage)

    [Client / BI Tool]
         ↓ JDBC/ODBC
    [Leader Node]
         ↓ distributes work
    [Compute Node 1] [Compute Node 2] [Compute Node 3]
    Each node has multiple slices (parallel processing units)

  REDSHIFT SERVERLESS:
    - No cluster management — automatically scales compute
    - Pay per compute-seconds used (RPU: Redshift Processing Units)
    - Base capacity: 8–512 RPUs
    - Auto-scales for peak workloads, scales to 0 when idle
    - Same SQL interface as cluster
    - Use when: variable workload, want no operations overhead

================================================================
4. DATA DISTRIBUTION STYLES
================================================================

  How data rows are distributed across compute nodes matters for query performance.

  AUTO:
    - Small tables: REPLICATION (all nodes have all rows)
    - Large tables: Redshift chooses distribution key
    - Default for most tables

  EVEN:
    - Rows distributed in round-robin across slices
    - Good for: tables without a clear distribution key
    - Bad for: frequent JOINs (data may be on different nodes = data movement)

  KEY:
    - Rows with same value of distribution key go to the same slice
    - Best for: large tables that are frequently JOINed on that column
    - Example: DISTSTYLE KEY DISTKEY (customerId) — all rows for same customer on same node

  ALL:
    - Full copy of the table on every node (broadcast)
    - Good for: small dimension tables frequently JOINed
    - Bad for: large tables (wastes storage, expensive writes)

================================================================
5. SORT KEYS
================================================================

  Define how data is physically ordered on disk within each node.
  Allows Redshift to skip large blocks of data (zone maps).

  COMPOUND SORT KEY:
    - Prefix of sort key columns must match query predicates for benefit
    - CREATE TABLE orders (order_date DATE, ...) SORTKEY (order_date, customer_id)
    - Fast for: WHERE order_date BETWEEN ... AND (leading column used)

  INTERLEAVED SORT KEY:
    - Equal weight given to each column
    - Good for: multiple query patterns with different WHERE columns
    - More expensive to maintain on INSERT/UPDATE (VACUUM REINDEX needed)

  Auto SORTKEY: Redshift automatically chooses sort key based on query patterns

================================================================
6. LOADING DATA INTO REDSHIFT
================================================================

  COPY COMMAND (Recommended for bulk loads):
    - Loads from S3, DynamoDB, Kinesis Firehose, EMR
    - Parallel loading across all slices
    - Formats: CSV, JSON, Parquet, ORC, Avro

    COPY orders FROM 's3://my-bucket/orders/'
    IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
    FORMAT AS CSV
    IGNOREHEADER 1;

  INSERT/INSERT INTO SELECT: Fine for small amounts; slow for bulk
  
  Redshift Spectrum: Query S3 data directly (no loading needed)

================================================================
7. REDSHIFT SPECTRUM
================================================================

  Query data directly in S3 WITHOUT loading into Redshift.
  
  Architecture:
    Redshift cluster → Spectrum Layer (thousands of nodes AWS manages) → S3

  Use case:
    - Historical "cold" data stays in S3 (cheap)
    - Recent "hot" data loaded into Redshift cluster
    - Query both together with JOINs

  Requirements:
    - External schema defined in AWS Glue Data Catalog (or Hive Metastore)
    - IAM role with S3 and Glue permissions

  CREATE EXTERNAL SCHEMA spectrum_schema
  FROM DATA CATALOG
  DATABASE 'my_glue_db'
  IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftSpectrumRole'
  CREATE EXTERNAL DATABASE IF NOT EXISTS;

  SELECT r.customer_id, r.total_amount, s.year_to_date_spend
  FROM redshift_table r
  JOIN spectrum_schema.s3_historical_orders s ON r.customer_id = s.customer_id;

================================================================
8. MAINTENANCE OPERATIONS
================================================================

  VACUUM:
    - Reclaims space from deleted/updated rows (soft deletes)
    - Re-sorts unsorted rows
    - Run periodically or let Auto VACUUM handle it
    VACUUM orders;                 -- Full vacuum
    VACUUM SORT ONLY orders;       -- Re-sort only, no space reclaim
    VACUUM DELETE ONLY orders;     -- Reclaim space only

  ANALYZE:
    - Updates statistics used by query planner
    - Run after large data loads
    ANALYZE orders;

  Redshift now runs Auto VACUUM and Auto Analyze automatically.

================================================================
9. CONCURRENCY SCALING
================================================================

  When query queue is backed up, Redshift automatically adds temporary
  cluster capacity to handle concurrent queries.
  
  First 1 hour/day of concurrency scaling per cluster is FREE.

  Use case: unpredictable bursts of concurrent queries from BI tools,
  dashboards with many simultaneous users.

================================================================
10. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Redshift and RDS?
A: RDS is for OLTP (transactional) workloads — row-based storage, optimized for
   fast inserts/updates/deletes and full-row reads, handles concurrent transactions
   with ACID guarantees. Redshift is for OLAP (analytical) workloads — columnar
   storage, optimized for scanning and aggregating billions of rows efficiently,
   NOT suitable for high-volume single-row transactions. Choose RDS for your web
   app's database. Choose Redshift for your business intelligence/analytics
   platform that queries across millions of order records.

Q: Why does Redshift use columnar storage?
A: Analytical queries (SELECT AVG(sales), SUM(revenue) GROUP BY region) only need
   a few columns out of many. With row-based storage, you'd read the entire row
   (all columns) to get one value. Columnar storage reads ONLY the needed columns,
   massively reducing I/O. Additionally, columns contain similar data types/values
   that compress extremely well (e.g., a Status column with "active"/"inactive"
   compresses to near-zero). Compression further reduces I/O.

Q: What is Redshift Spectrum and when would you use it?
A: Redshift Spectrum lets you query data stored in S3 directly without loading it
   into Redshift. Use it for: large historical archives you don't want to pay Redshift
   storage for (S3 is much cheaper), "data lake" architecture where raw data lives in
   S3, or when you need to JOIN S3 data with Redshift data. It uses the Glue Data
   Catalog as a metastore. You only pay for data scanned, similar to Athena.

Q: What are distribution styles in Redshift and why do they matter?
A: Distribution style determines how rows are spread across compute nodes.
   With KEY distribution on a JOIN column, both tables' matching rows land on the
   same node — no network data movement during JOIN. With EVEN distribution, JOINs
   require broadcasting or redistributing data across nodes (expensive).
   With ALL distribution, small dimension tables are replicated everywhere to avoid
   movement during JOINs with large fact tables. Good distribution key choice can
   reduce query time from minutes to seconds for large analytical JOINs.
