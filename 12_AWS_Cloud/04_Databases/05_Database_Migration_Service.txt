================================================================
AWS DATABASES — DATABASE MIGRATION SERVICE (DMS)
Complete Interview Preparation Guide
================================================================

1. AWS DMS OVERVIEW
================================================================

  AWS DMS (Database Migration Service) helps migrate databases to AWS
  with minimal downtime.
  
  Supports:
    - Homogeneous migrations: Oracle → Oracle, MySQL → MySQL
    - Heterogeneous migrations: Oracle → Aurora PostgreSQL, SQL Server → MySQL
    - On-premises → AWS, AWS → AWS, AWS → on-premises
    - Data lake loading: relational DB → S3 (for analytics)
    - NoSQL: MongoDB → DynamoDB

================================================================
2. CORE DMS COMPONENTS
================================================================

  REPLICATION INSTANCE:
    - EC2 instance that runs the migration software
    - Connects to source and target endpoints
    - Stores migration data temporarily
    - Right-size: larger instance for large migrations, multi-AZ for resilience
    - Can support multiple migration tasks simultaneously

  SOURCE ENDPOINT:
    - Connection details for the source database
    - Supported sources: Oracle, SQL Server, MySQL, PostgreSQL, MariaDB,
      MongoDB, SAP, IBM DB2, Azure SQL, on-premises DBs

  TARGET ENDPOINT:
    - Connection details for the target database
    - Supported targets: Oracle, SQL Server, MySQL, PostgreSQL, Aurora,
      DynamoDB, S3, Redshift, Kinesis, DocumentDB, OpenSearch

  TASK:
    - Defines what data to migrate and how
    - Associated with source + target endpoints and replication instance
    - Three modes: Full Load, Full Load + CDC, CDC Only

================================================================
3. MIGRATION MODES
================================================================

  FULL LOAD:
    - Migrates all existing data from source to target
    - Simple, one-time bulk copy
    - Source DB continues running during migration
    - After full load: cutover (point app to new DB)
    - Downtime: from when you stop writes to when target is live
    - Use for: small databases or when downtime is acceptable

  FULL LOAD + CDC (Change Data Capture):
    - Phase 1: Full load of existing data
    - Phase 2: CDC continuously captures changes from source and applies to target
    - Target stays in sync with source in near-real-time
    - Minimal downtime: just the time to update connection strings
    - Use for: large databases where downtime must be minimized
    - Requires: source DB with transaction logs enabled (binary log for MySQL,
                redo log for Oracle, WAL for PostgreSQL)

  CDC ONLY:
    - Assumes target already has a copy of the data (from another method)
    - Only captures and replicates ongoing changes
    - Use for: initial load done via other means (S3 dump, backup restore),
               ongoing replication between systems

================================================================
4. CHANGE DATA CAPTURE (CDC) — HOW IT WORKS
================================================================

  MySQL: DMS reads from binary log (binlog)
    - Requires: binlog_format=ROW, binlog_row_image=FULL
    - User needs REPLICATION SLAVE, REPLICATION CLIENT privileges

  PostgreSQL: DMS uses logical replication (WAL logical decoding)
    - Requires: wal_level=logical, max_replication_slots >= tasks
    - Uses pglogical or test_decoding plugin

  Oracle: DMS reads from redo logs
    - Requires: ARCHIVELOG mode, supplemental logging enabled
    - User needs LOGMINING privilege

================================================================
5. SCHEMA CONVERSION TOOL (SCT)
================================================================

  DMS handles DATA migration. SCT handles SCHEMA + CODE conversion.
  
  AWS Schema Conversion Tool (SCT):
    - Converts source database schema to target database engine format
    - Converts stored procedures, functions, triggers, views
    - Highlights what it can auto-convert vs what needs manual review
    - Generates assessment report: % automatically converted, complexity
    - Use for HETEROGENEOUS migrations (different DB engines)

  SCT → DMS workflow:
    1. Run SCT on source schema → converts tables, views, procedures
    2. Review and fix flagged items (complex PL/SQL, Oracle-specific syntax)
    3. Apply converted schema to target DB
    4. Run DMS Full Load + CDC to migrate data

  Not needed for HOMOGENEOUS migrations (same engine):
    MySQL → MySQL: Schema is already compatible, just export/import

================================================================
6. DMS TASK SETTINGS
================================================================

  TABLE MAPPING:
    - Select which schemas, tables to include/exclude
    - Transform table/column names (e.g., rename schema from SALES to sales)
    - Filter rows (e.g., only migrate records after a date)

    {
      "rules": [
        {
          "rule-type": "selection",
          "rule-id": "1",
          "rule-name": "include-orders",
          "object-locator": { "schema-name": "dbo", "table-name": "orders" },
          "rule-action": "include"
        },
        {
          "rule-type": "transformation",
          "rule-id": "2",
          "rule-name": "lowercase-tables",
          "rule-action": "convert-lowercase",
          "rule-target": "table",
          "object-locator": { "schema-name": "%", "table-name": "%" }
        }
      ]
    }

  LOB (Large Object) HANDLING:
    - Limited LOB mode: Truncate LOBs above a max size
    - Full LOB mode: Migrate LOBs fully (slower, more resources)
    - Inline LOB mode: Use limited mode but switch to full for large ones

================================================================
7. COMMON MIGRATION ARCHITECTURES
================================================================

  ON-PREMISES MySQL → Amazon Aurora MySQL (Homogeneous):
    1. Create Aurora cluster
    2. Use DMS Full Load + CDC task
    3. Monitor replication lag
    4. When lag = 0: update application connection string
    5. Decommission on-premises MySQL

  Oracle On-Premises → Aurora PostgreSQL (Heterogeneous):
    1. Run SCT on Oracle schema → PostgreSQL DDL
    2. Review flagged items, fix Oracle-specific PL/SQL
    3. Apply schema to Aurora PostgreSQL
    4. Run DMS Full Load + CDC
    5. Test application thoroughly (SQL syntax differences)
    6. Cutover and decommission

  MySQL → S3 (Data Lake):
    - DMS task with S3 as target
    - Exports as CSV or Parquet
    - CDC continuously pushes changes to S3
    - Use Glue + Athena for analytics

================================================================
8. DMS MONITORING AND TROUBLESHOOTING
================================================================

  CloudWatch Metrics:
    - CDCLatencySource: Lag between source transaction commit and capture
    - CDCLatencyTarget: Lag between DMS applying changes to target
    - FullLoadRows: Rows migrated during full load
    - TableError: Tables with errors during migration

  Common Issues:
    - PRIMARY KEY violations: target has data from previous run
      Solution: Truncate target tables before restart
    - LOB type errors: BLOB/CLOB causing failures
      Solution: Switch LOB mode or exclude problematic columns
    - Replication lag growing: Replication instance too small
      Solution: Scale up instance; check source/target for bottlenecks

================================================================
9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Full Load and Full Load + CDC in DMS?
A: Full Load does a one-time bulk copy of all existing data. The source DB can
   continue running but changes during migration are NOT captured — there's
   downtime between stopping writes and cutover. Full Load + CDC first does the
   bulk copy, then continuously captures and applies ongoing changes from
   transaction logs. The target stays in sync, so downtime is minimal — just
   update the connection string. Use Full Load for small DBs or acceptable downtime.
   Use Full Load + CDC for large DBs or near-zero downtime requirements.

Q: When do you need AWS Schema Conversion Tool (SCT) vs just DMS?
A: SCT is needed for HETEROGENEOUS migrations — migrating between different database
   engines (Oracle → PostgreSQL, SQL Server → MySQL). It converts the schema (DDL),
   stored procedures, functions, triggers, and views. DMS handles the DATA migration.
   For HOMOGENEOUS migrations (MySQL → MySQL, PostgreSQL → PostgreSQL), SCT is not
   needed because the schemas are already compatible — just use DMS directly.

Q: How does CDC (Change Data Capture) work in DMS?
A: DMS reads transaction logs at the source database level:
   MySQL: binary log (requires binlog_format=ROW)
   PostgreSQL: WAL (write-ahead log) using logical replication
   Oracle: redo logs (requires ARCHIVELOG mode + supplemental logging)
   DMS continuously reads new log entries and applies the changes (INSERT/UPDATE/DELETE)
   to the target. This means the source DB can stay online with live traffic while
   DMS keeps the target in sync, enabling minimal-downtime migrations.

Q: What are the prerequisites for DMS CDC with MySQL?
A: The MySQL source must have: 1) binary logging enabled (binlog_format=ROW,
   log_bin=ON), 2) binlog_row_image=FULL (so DMS gets full row data, not just
   changed columns), 3) DMS user must have REPLICATION SLAVE and REPLICATION CLIENT
   privileges, 4) sufficient binary log retention (binlog_expire_logs_seconds) so
   DMS can catch up if it falls behind. For RDS MySQL, these settings can be
   enabled via parameter groups.
