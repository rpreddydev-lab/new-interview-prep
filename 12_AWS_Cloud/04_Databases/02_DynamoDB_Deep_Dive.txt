1. DYNAMODB OVERVIEW
================================================================

  DynamoDB is AWS's fully managed, serverless NoSQL database.
  
  Key characteristics:
    - Single-digit millisecond latency at any scale
    - Fully serverless: no servers to manage, scales automatically
    - Supports key-value and document data models
    - Global Tables: multi-region, multi-active replication
    - Billed for read/write capacity + storage
    - SLA: 99.99% (single region), 99.999% (Global Tables)

================================================================
2. CORE CONCEPTS
================================================================

  TABLE:
    - Collection of items (equivalent to a database table)
    - Must define a primary key at creation (cannot change after)
  
  ITEM:
    - Single record (equivalent to a row)
    - Up to 400KB per item
    - Attributes can vary between items (schema-less)
  
  ATTRIBUTE:
    - A name-value pair within an item
    - Supported types: String, Number, Binary, Boolean, Null,
                       List, Map, Set (StringSet, NumberSet, BinarySet)

  PRIMARY KEY (two types):
    1. PARTITION KEY ONLY (Hash Key):
       - Must be unique across all items
       - DynamoDB hashes the key to determine which partition stores the item
       - Example: UserId as partition key for Users table

    2. COMPOSITE KEY: PARTITION KEY + SORT KEY:
       - Partition key can repeat, but partition key + sort key must be unique
       - Items with the same partition key are stored together, sorted by sort key
       - Enables rich query operations within a partition
       - Example: UserId (PK) + OrderDate (SK) for Orders table

  Good PK design:
    - High cardinality (many unique values)
    - Uniform distribution (avoid hot partitions)
    - Never use attributes with low cardinality (e.g., boolean, status with 3 values)
    - Use composite keys like userId#timestamp for time-series data

================================================================
3. READ/WRITE CAPACITY
================================================================

  PROVISIONED CAPACITY:
    - You specify RCUs (Read Capacity Units) and WCUs (Write Capacity Units)
    - 1 WCU = 1 strongly consistent write of up to 1KB per second
    - 1 RCU = 1 strongly consistent read OR 2 eventually consistent reads of up to 4KB/second
    - Auto-scaling available (set min/max RCU/WCU)
    - Can reserve capacity (1-year or 3-year) for predictable workloads

  ON-DEMAND CAPACITY:
    - No capacity planning — scales instantly
    - Pay per request: ~$1.25/million write requests, ~$0.25/million read requests
    - More expensive at steady high load vs Provisioned
    - Best for: unpredictable workloads, new tables, spiky traffic

  SWITCHING:
    - Can switch between provisioned and on-demand up to twice per day per table

  BURST CAPACITY:
    - DynamoDB retains up to 5 minutes of unused RCU/WCU as burst capacity
    - Available for occasional spikes beyond provisioned capacity

================================================================
4. CONSISTENCY MODELS
================================================================

  EVENTUALLY CONSISTENT READ (default):
    - Reads might return stale data (milliseconds behind)
    - Consumes 0.5 RCU per 4KB
    - Cheaper, faster

  STRONGLY CONSISTENT READ:
    - Returns most up-to-date data (after all writes)
    - Consumes 1 RCU per 4KB
    - Set: ConsistentRead: true in API call
    - Not available in Global Tables (always eventually consistent across regions)

  TRANSACTIONAL READ/WRITE:
    - DynamoDB Transactions (TransactGetItems / TransactWriteItems)
    - All-or-nothing: either ALL succeed or ALL fail
    - Consumes 2 RCUs per read and 2 WCUs per write
    - Up to 100 actions per transaction, max 4MB total

================================================================
5. GLOBAL SECONDARY INDEXES (GSI) AND LOCAL SECONDARY INDEXES (LSI)
================================================================

  WHY INDEXES?
    DynamoDB can only query efficiently on partition key + sort key.
    Indexes allow querying on other attributes.

  LOCAL SECONDARY INDEX (LSI):
    - SAME partition key as base table, DIFFERENT sort key
    - Must be created at TABLE CREATION TIME (cannot add later)
    - Max 5 per table
    - Shares RCU/WCU with the base table
    - Example: UserOrders table PK=UserId, SK=OrderDate
               LSI: PK=UserId, SK=TotalAmount → query user's orders by total amount

  GLOBAL SECONDARY INDEX (GSI):
    - DIFFERENT partition key (and optionally different sort key)
    - Can be created or deleted after table creation
    - Max 20 per table
    - Has its OWN RCU/WCU provisioned separately
    - Only supports eventual consistency reads
    - Example: Orders table PK=OrderId; GSI: PK=CustomerId → query all orders by customer
    
  LSI vs GSI:
  ┌───────────────────┬────────────────────────────┬──────────────────────────────┐
  │ Feature           │ LSI                        │ GSI                          │
  ├───────────────────┼────────────────────────────┼──────────────────────────────┤
  │ Partition key     │ Same as base table         │ Any attribute                │
  │ Sort key          │ Different from base table  │ Any attribute                │
  │ Creation time     │ Only at table creation     │ Any time                     │
  │ Capacity          │ Shared with table          │ Own separate capacity        │
  │ Consistency       │ Strong or eventual         │ Eventual only                │
  │ Max count         │ 5 per table                │ 20 per table                 │
  └───────────────────┴────────────────────────────┴──────────────────────────────┘

6. QUERIES AND SCANS
================================================================

  QUERY:
    - Efficiently fetch items by partition key (required) and optionally sort key range
    - Much more efficient than Scan
    - Supports: begins_with, between, <, >, <=, >= on sort key
    - FilterExpression: applied AFTER fetching (still consumes RCU for all fetched items)

  SCAN:
    - Reads EVERY item in the table (full table scan)
    - Very expensive for large tables
    - Supports ProjectionExpression (return only specific attributes)
    - Parallel scans possible (divide table into segments, scan concurrently)
    - Avoid in production unless absolutely necessary

  PAGINATION:
    - DynamoDB returns max 1MB per call (or up to Limit)
    - If more results: response contains LastEvaluatedKey
    - Subsequent calls: pass LastEvaluatedKey as ExclusiveStartKey

================================================================
7. DYNAMODB STREAMS
================================================================

  Captures a time-ordered sequence of item-level changes.
  
  Stream record types:
    KEYS_ONLY:    Only key attributes of modified item
    NEW_IMAGE:    Entire new item after modification
    OLD_IMAGE:    Entire item before modification
    NEW_AND_OLD_IMAGES: Both before and after

  Common use cases:
    - Event-driven architectures (trigger Lambda on data change)
    - Auditing and change history
    - Cross-region replication (used by Global Tables internally)
    - Real-time analytics
    - Notification on item creation/update

  DynamoDB Streams + Lambda:
    - Lambda polls the stream (event source mapping)
    - Triggered per shard of the stream
    - Sequential processing within a shard

================================================================
8. TTL (TIME TO LIVE)
================================================================

  Automatically expire and delete items based on a timestamp attribute.
  
  - Enable TTL on a specific attribute that holds a Unix timestamp
  - DynamoDB compares attribute value to current time
  - Items with TTL < current time are marked for deletion
  - Deletion happens within 48 hours (not instantaneous)
  - TTL deletions do NOT consume WCUs
  - TTL deletions appear in DynamoDB Streams (can filter)

  Enable TTL:
  aws dynamodb update-time-to-live \
    --table-name Sessions \
    --time-to-live-specification "Enabled=true,AttributeName=expiresAt"
  
  Example item:
  { "sessionId": "abc123", "userId": "user456", "expiresAt": 1735689600 }
  # expiresAt = Unix timestamp for when session expires

================================================================
9. DYNAMODB ACCELERATOR (DAX)
================================================================

  DAX is an in-memory cache for DynamoDB.
  
  Features:
    - Microsecond read latency (vs single-digit milliseconds for DynamoDB)
    - Fully compatible with DynamoDB API (drop-in, just change endpoint)
    - Cache size: 5–100s of GB
    - Multi-AZ capable (3-node minimum recommended for HA)
    - Write-through cache (writes go to DAX and DynamoDB simultaneously)
    - TTL for cache invalidation (default: 5 minutes for query results)

  Use case:
    - Read-heavy workloads (millions of reads/second)
    - Repeated reads for the same data (e.g., product catalog, leaderboard)
    - NOT for write-heavy workloads (DAX doesn't help much)
    - NOT for eventually consistent requirements where you need latest writes

  DAX vs ElastiCache:
    DAX:         DynamoDB-specific, write-through, no code change needed beyond endpoint
    ElastiCache: Generic cache (Redis/Memcached), works with any database,
                 requires manual cache-aside pattern in application code

================================================================
10. GLOBAL TABLES
================================================================

  Multi-region, multi-active DynamoDB tables.
  
  Key features:
    - Active-active: read AND write in multiple regions
    - Replication lag: typically < 1 second
    - Last-writer-wins conflict resolution (based on timestamp)
    - Requires: DynamoDB Streams enabled
  
  Use case:
    - Global applications needing low-latency reads/writes worldwide
    - Disaster recovery with near-zero RTO/RPO
    - GDPR: store EU user data in EU region

  Create global table replicas:
  aws dynamodb create-global-table \
    --global-table-name UserProfiles \
    --replication-group '[{"RegionName":"us-east-1"},{"RegionName":"eu-west-1"},{"RegionName":"ap-southeast-1"}]'

================================================================
11. DYNAMODB TRANSACTIONS
================================================================

  ACID transactions across multiple items/tables.
  
  TransactWriteItems: Up to 100 write operations (Put, Update, Delete, ConditionCheck)
  TransactGetItems:   Up to 100 read operations atomically
  
  - All operations succeed or all roll back
  - Costs 2x RCUs/WCUs
  - Cannot span multiple accounts or regions (Global Tables do NOT support cross-region transactions)

12. JAVA SDK v2 — DYNAMODBENHANCEDCLIENT

  import software.amazon.awssdk.enhanced.dynamodb.*;
  import software.amazon.awssdk.enhanced.dynamodb.mapper.annotations.*;
  import software.amazon.awssdk.services.dynamodb.DynamoDbClient;
  
  // Model class
  @DynamoDbBean
  public class UserProfile {
      private String userId;
      private String email;
      private String status;
  
      @DynamoDbPartitionKey
      public String getUserId() { return userId; }
      public void setUserId(String id) { this.userId = id; }
  
      public String getEmail() { return email; }
      public void setEmail(String email) { this.email = email; }
  
      public String getStatus() { return status; }
      public void setStatus(String status) { this.status = status; }
  }
  
  // Initialize (static for Lambda cold start optimization)
  private static final DynamoDbClient dynamoDbClient = DynamoDbClient.create();
  private static final DynamoDbEnhancedClient enhancedClient = DynamoDbEnhancedClient.builder()
      .dynamoDbClient(dynamoDbClient)
      .build();
  private static final DynamoDbTable<UserProfile> table = enhancedClient.table(
      "UserProfiles", TableSchema.fromBean(UserProfile.class)
  );
  
  // PUT item
  UserProfile user = new UserProfile();
  user.setUserId("user123");
  user.setEmail("user@example.com");
  user.setStatus("active");
  table.putItem(user);
  
  // GET item by key
  UserProfile found = table.getItem(
      Key.builder().partitionValue("user123").build()
  );
  
  // UPDATE with expressions (low-level client)
  dynamoDbClient.updateItem(UpdateItemRequest.builder()
      .tableName("UserProfiles")
      .key(Map.of("userId", AttributeValue.fromS("user123")))
      .updateExpression("SET #status = :newStatus")
      .expressionAttributeNames(Map.of("#status", "status"))
      .expressionAttributeValues(Map.of(":newStatus", AttributeValue.fromS("inactive")))
      .returnValues(ReturnValue.ALL_NEW)
      .build()
  );
  
  // QUERY with sort key range
  QueryEnhancedRequest queryRequest = QueryEnhancedRequest.builder()
      .queryConditional(
          QueryConditional.sortBetween(
              Key.builder().partitionValue("user123").sortValue("2024-01-01").build(),
              Key.builder().partitionValue("user123").sortValue("2024-12-31").build()
          )
      )
      .build();
  
  PageIterable<UserProfile> results = ordersTable.query(queryRequest);
  results.items().forEach(order -> System.out.println(order.getOrderId()));
  
  // TRANSACT WRITE example
  dynamoDbClient.transactWriteItems(TransactWriteItemsRequest.builder()
      .transactItems(
          TransactWriteItem.builder().put(
              Put.builder()
                  .tableName("Orders")
                  .item(Map.of("orderId", AttributeValue.fromS("ord123"),
                               "status", AttributeValue.fromS("placed")))
                  .build()
          ).build(),
          TransactWriteItem.builder().update(
              Update.builder()
                  .tableName("Inventory")
                  .key(Map.of("productId", AttributeValue.fromS("prod456")))
                  .updateExpression("SET qty = qty - :dec")
                  .expressionAttributeValues(Map.of(":dec", AttributeValue.fromN("1")))
                  .conditionExpression("qty > :zero")
                  .expressionAttributeValues(Map.of(":dec", AttributeValue.fromN("1"), ":zero", AttributeValue.fromN("0")))
                  .build()
          ).build()
      )
      .build()
  );

13. INTERVIEW QUESTIONS
================================================================

Q: How does DynamoDB partition data and why does partition key design matter?
A: DynamoDB uses the partition key to determine which physical partition stores the item
   (via consistent hashing). Each partition handles a limited amount of throughput
   (~3000 RCUs and 1000 WCUs). If most traffic hits one partition key value (hot partition),
   you throttle even if your total provisioned capacity is sufficient. Good PK design:
   high cardinality (many unique values), uniform access distribution (no hot keys).
   Avoid: status codes, booleans, dates (if you query all items from a specific date).

Q: What is the difference between GSI and LSI?
A: LSI (Local Secondary Index) uses the SAME partition key as the base table but a
   different sort key. Must be created at table creation. Shares base table's capacity.
   GSI (Global Secondary Index) uses a completely DIFFERENT partition key (and optional
   sort key). Can be created/deleted at any time. Has its own separate capacity.
   GSIs support only eventual consistency; LSIs support both. Use LSI when you need
   to sort/filter within a partition by different attributes. Use GSI when you need
   to query by attributes unrelated to the original partition key.

Q: When would you use DynamoDB vs RDS?
A: Use DynamoDB for: single-digit ms latency at millions of requests/sec, flexible schema
   that changes over time, serverless scale (no capacity planning), simple access patterns
   (key lookups, range queries on sort key). Use RDS when: you need complex JOINs and
   ad-hoc SQL queries, ACID transactions across many tables, existing SQL-based app,
   strict relational data model. DynamoDB's weakness: no JOINs, no ad-hoc queries,
   must know access patterns at design time (and create GSIs for them).

Q: What is DynamoDB Streams used for?
A: DynamoDB Streams captures a time-ordered log of item-level changes (INSERT, MODIFY, REMOVE).
   Common uses: trigger Lambda on data changes (event-driven), maintain audit history,
   propagate changes to ElasticSearch/OpenSearch for full-text search, data replication to
   another table, cache invalidation (delete ElastiCache entry when DB item changes).
   Retention: 24 hours only.

Q: How do DynamoDB transactions work? What's the cost?
A: TransactWriteItems and TransactGetItems allow all-or-nothing ACID operations across
   up to 100 items and multiple tables within a single region. If any operation fails
   (including condition check failures), all operations roll back. Cost: 2x RCUs/WCUs
   compared to normal reads/writes. Use for: inventory systems (check and decrement),
   financial transfers, order placement + inventory decrement.
