2. CHOOSING THE RIGHT COMPUTE SERVICE
================================================================

Decision Tree:

  Do you need full OS control (install custom software, specific OS)?
  → YES: EC2

  Is it event-driven, stateless, short-lived (< 15 min)?
  → YES: Lambda (serverless)

  Are you using Docker containers?
  → Do you want to manage servers? NO → Fargate
  → Do you want Kubernetes? YES → EKS
  → Do you want AWS-native orchestration? YES → ECS

  Do you just want to deploy a web app with minimal infrastructure config?
  → Elastic Beanstalk

  Need to process large batch jobs with hundreds of instances?
  → AWS Batch

3. COMPUTE SCALABILITY APPROACHES
================================================================

  VERTICAL SCALING (Scale Up)
  - Change to a larger instance type (t3.micro → m5.xlarge)
  - Requires stop/start of instance
  - Limited by max instance size
  - Suitable for: monoliths that can't scale horizontally

  HORIZONTAL SCALING (Scale Out) — PREFERRED
  - Add more instances of the same size
  - No downtime required
  - AWS Auto Scaling does this automatically
  - Supported by: EC2 Auto Scaling, ECS Service Auto Scaling, Lambda concurrency

  ELASTIC SCALING
  - Automatically adds/removes instances based on demand
  - Key AWS services: Auto Scaling Groups (EC2), Application Auto Scaling (ECS/Lambda)
  - Metrics used: CPU utilization, request count, custom CloudWatch metrics

5. COMPUTE KEY CONCEPTS SUMMARY
================================================================

  EC2 AMI (Amazon Machine Image):
  - Template for EC2 instances (OS, software, configs)
  - Regional resource (can be copied across regions)
  - Can be AWS-provided, Marketplace, or custom (your golden AMI)

  Instance User Data:
  - Script that runs at EC2 launch (first boot only by default)
  - Used for bootstrapping (install software, configure app)
  - Accessed at: http://169.254.169.254/latest/user-data

  Instance Metadata:
  - Instance info accessible from within the instance
  - Endpoint: http://169.254.169.254/latest/meta-data/
  - IMDS v2 (requires session token — more secure):
    TOKEN=$(curl -X PUT -H "X-aws-ec2-metadata-token-ttl-seconds: 21600" \
            http://169.254.169.254/latest/api/token)
    curl -H "X-aws-ec2-metadata-token: $TOKEN" \
            http://169.254.169.254/latest/meta-data/instance-id

6. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between EC2, ECS, EKS, Lambda, and Fargate?
A: EC2 is IaaS — you manage virtual machines (OS patches, security, scaling).
   Lambda is serverless — event-triggered functions with no server management,
   auto-scaling, max 15-minute execution. ECS is AWS-native container orchestration;
   runs Docker containers on EC2 (you manage) or Fargate (serverless). EKS is managed
   Kubernetes on AWS; use when you need K8s portability or already use Kubernetes.
   Fargate is serverless compute for containers — no EC2 instances to manage.
   ECS/EKS can both use Fargate as the compute layer.

Q: When would you choose Lambda over EC2?
A: Lambda when: workload is event-driven (API calls, S3 events, DynamoDB streams),
   execution time < 15 minutes, traffic is spiky/unpredictable, you want zero server
   management, or you want to pay only for actual execution time. EC2 when: you need
   full OS control, run processes > 15 minutes, have consistent/predictable load
   (Reserved Instances save money), need specific instance types (GPU, high memory),
   or require custom software/agents on the OS.

Q: What is horizontal vs vertical scaling and which does AWS prefer?
A: Vertical scaling = upgrading to a larger instance (requires downtime/restart).
   Horizontal scaling = adding more instances of the same size (no downtime, elastic).
   AWS prefers horizontal scaling: it's more resilient (no single point of failure),
   supports auto-scaling dynamically, and follows the cloud best practice of multiple
   small instances over one large one. Multi-AZ with Auto Scaling Groups is the
   canonical AWS pattern.

Q: What is an AMI and how is it used?
A: An AMI (Amazon Machine Image) is a pre-configured template for EC2 instances
   containing the OS, installed software, configurations, and data volumes. When
   you launch an EC2 instance, you specify an AMI. Custom "golden AMIs" are used
   in production to pre-bake all software and configs so Auto Scaling Groups can
   launch pre-configured instances quickly without bootstrapping. AMIs are regional
   but can be copied to other regions for multi-region deployments.
