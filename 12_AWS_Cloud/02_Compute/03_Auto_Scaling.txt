================================================================
AWS COMPUTE — AUTO SCALING
Complete Interview Preparation Guide
================================================================

1. WHAT IS AUTO SCALING?
================================================================

AWS Auto Scaling automatically adjusts the number of EC2 instances (or
other compute resources) based on demand, ensuring you always have the
right number of instances.

Benefits:
  - AVAILABILITY: Maintain desired capacity; replace unhealthy instances
  - COST EFFICIENCY: Scale in when demand drops (no over-provisioning)
  - ELASTICITY: Handle traffic spikes without manual intervention

================================================================
2. AUTO SCALING GROUP (ASG)
================================================================

An Auto Scaling Group is a logical grouping of EC2 instances managed as a unit.

CORE CONFIGURATION:
  - Launch Template (or legacy Launch Configuration): defines WHAT to launch
  - Min/Desired/Max capacity: defines HOW MANY instances
  - Health checks: defines WHEN to replace instances
  - Scaling policies: defines WHEN to scale

  ┌─────────────────────────────────────────────────────────────────┐
  │                   AUTO SCALING GROUP                            │
  │  Min: 2  |  Desired: 4  |  Max: 10                             │
  │                                                                 │
  │  AZ: us-east-1a    AZ: us-east-1b    AZ: us-east-1c            │
  │  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐            │
  │  │ EC2   EC2   │  │ EC2   EC2   │  │    (spare)  │            │
  │  └─────────────┘  └─────────────┘  └─────────────┘            │
  │                                                                 │
  │  ← Spans multiple AZs for high availability                     │
  └─────────────────────────────────────────────────────────────────┘

KEY CAPACITY SETTINGS:
  Minimum: Never scale below this (ensures HA — usually 2+ across AZs)
  Desired: Target number; ASG tries to maintain this
  Maximum: Never exceed this (cost control)

================================================================
3. LAUNCH TEMPLATES
================================================================

A Launch Template defines the configuration for EC2 instances in an ASG.
It replaces the older Launch Configuration (more features, versioning).

LAUNCH TEMPLATE INCLUDES:
  - AMI ID
  - Instance type (multiple can be specified now)
  - Key pair
  - Security groups
  - IAM instance profile
  - User data (bootstrap script)
  - EBS storage configuration
  - Tags
  - Spot/On-Demand mix

CREATING A LAUNCH TEMPLATE:
  aws ec2 create-launch-template \
    --launch-template-name MyWebServerTemplate \
    --version-description "v1" \
    --launch-template-data '{
      "ImageId": "ami-0c55b159cbfafe1f0",
      "InstanceType": "t3.medium",
      "KeyName": "MyKeyPair",
      "SecurityGroupIds": ["sg-0123456789abcdef0"],
      "IamInstanceProfile": {"Name": "WebServerRole"},
      "UserData": "IyEvYmluL2Jhc2gKc3VkbyB5dW0gaW5zdGFsbCAteSBqYXZh"
    }'

4. SCALING POLICIES
================================================================

TYPE 1: TARGET TRACKING SCALING (Recommended / Simplest)
  - Define a target metric value; ASG automatically scales to maintain it
  - Similar to a thermostat
  
  Examples:
    - Average CPU utilization = 50%
    - Application Load Balancer request count per target = 1000
    - Average network in = 100MB/s
  
  CLI:
  aws autoscaling put-scaling-policy \
    --auto-scaling-group-name my-asg \
    --policy-name cpu-tracking \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration '{
      "PredefinedMetricSpecification": {
        "PredefinedMetricType": "ASGAverageCPUUtilization"
      },
      "TargetValue": 50.0
    }'

---

TYPE 2: STEP SCALING
  - Respond to CloudWatch alarms with different scaling steps
  - More complex but more control
  
  Example:
    CPU > 70% → add 2 instances
    CPU > 85% → add 5 instances
    CPU < 30% → remove 1 instance
  
  Better than simple scaling because it doesn't wait for cooldown period
  between steps.

---

TYPE 3: SIMPLE SCALING
  - Single CloudWatch alarm triggers single action
  - Cooldown period between actions (300s default)
  - Older approach; prefer Target Tracking or Step Scaling

---

TYPE 4: SCHEDULED SCALING
  - Scale based on predictable patterns
  - Set min/max/desired for specific times
  
  Example: 
    Weekday 9am EST: min=10, desired=10
    Weekend: min=2, desired=2
  
  aws autoscaling put-scheduled-update-group-action \
    --auto-scaling-group-name my-asg \
    --scheduled-action-name scale-up-morning \
    --recurrence "0 14 * * MON-FRI" \  # 9am EST (UTC-5 = 14:00 UTC)
    --min-size 10 --desired-capacity 10

---

TYPE 5: PREDICTIVE SCALING
  - Uses ML to predict load based on historical patterns
  - Proactively adds capacity before it's needed
  - Combines scheduled + dynamic scaling

5. HEALTH CHECKS AND INSTANCE REPLACEMENT
================================================================

HEALTH CHECK TYPES:
  1. EC2 Health Check (default):
     - Checks instance system/instance status
     - Replaces instances in Impaired state
  
  2. ELB Health Check:
     - Load Balancer health check determines if instance is "healthy"
     - Better for app-level health (HTTP 200 response)
     - Recommended when ASG is behind a load balancer

  REPLACEMENT PROCESS:
    1. Instance marked unhealthy
    2. ASG terminates the unhealthy instance
    3. ASG launches a replacement (using launch template)
    4. New instance added to load balancer target group
    5. ELB health check passes → instance receives traffic

================================================================
6. SCALING COOLDOWNS AND WARM-UP
================================================================

  COOLDOWN PERIOD (Simple Scaling):
    - Time to wait after scaling action before another can occur
    - Default: 300 seconds
    - Prevents rapid-fire scaling

  INSTANCE WARMUP (Step/Target Tracking):
    - Time for a new instance to start handling traffic
    - During warmup, instance metrics not counted in aggregate
    - Default: uses health check grace period

  HEALTH CHECK GRACE PERIOD:
    - Time after launch before health checks begin
    - Give the instance time to boot and start the app
    - Default: 300 seconds; increase for slow-starting apps (Java, Spring Boot)

7. MIXED INSTANCE POLICIES (SPOT + ON-DEMAND)
================================================================

Configure ASG to use a mix of Spot and On-Demand instances:

  {
    "MixedInstancesPolicy": {
      "LaunchTemplate": {
        "LaunchTemplateSpecification": {
          "LaunchTemplateName": "MyTemplate"
        },
        "Overrides": [
          {"InstanceType": "m5.large"},
          {"InstanceType": "m5a.large"},
          {"InstanceType": "m4.large"},
          {"InstanceType": "t3.large"}
        ]
      },
      "InstancesDistribution": {
        "OnDemandBaseCapacity": 2,           // First 2 instances always On-Demand
        "OnDemandPercentageAboveBaseCapacity": 20,  // 20% On-Demand, 80% Spot above base
        "SpotAllocationStrategy": "capacity-optimized"  // AWS picks lowest-interruption pools
      }
    }
  }

  SPOT ALLOCATION STRATEGIES:
    capacity-optimized: AWS picks pools with most available capacity (lower interruption)
    lowest-price: Uses cheapest Spot pools (can have higher interruption)
    price-capacity-optimized: Balanced between lowest price and capacity availability

================================================================
8. TERMINATION POLICIES
================================================================

Default Termination Policy (which instance to kill when scaling in):
  1. Select AZ with most instances
  2. Find instance with oldest launch template
  3. Find instance closest to next billing hour
  4. Randomly select if tie

Custom termination policies:
  OldestLaunchTemplate, NewestInstance, OldestInstance, ClosestToNextInstanceHour

  Best practice: Instances with more recent launch templates = more likely kept

================================================================
9. ASG WITH LOAD BALANCER
================================================================

  INTERNET → ALB → Target Group → ASG Instances
  
  ASG Registers: new instances automatically added to ALB target group
  ASG Deregisters: instance connection draining (in-flight requests complete)
  before ASG terminates the instance

  ENABLE ALB HEALTH CHECKS:
  aws autoscaling attach-load-balancer-target-groups \
    --auto-scaling-group-name my-asg \
    --target-group-arns arn:aws:elasticloadbalancing:...

10. INTERVIEW QUESTIONS
================================================================

Q: What is an Auto Scaling Group and what are Min/Desired/Max?
A: An ASG is a group of EC2 instances managed as a unit with automatic scaling.
   Min is the floor — ASG never goes below this (ensures HA — typically 2+ across
   AZs). Desired is the current target — ASG tries to maintain this number.
   Max is the ceiling — ASG never exceeds this (cost control). ASG automatically
   replaces unhealthy instances and adjusts count based on scaling policies.

Q: What is the difference between Target Tracking and Step Scaling?
A: Target Tracking scaling is like a thermostat — you set a target metric value
   (e.g., CPU = 50%) and the ASG automatically adjusts to maintain it. Simplest
   and recommended for most use cases. Step Scaling uses CloudWatch alarms with
   defined steps (e.g., CPU > 70% → add 2 instances, CPU > 90% → add 5 instances).
   More control but more complex. Use step scaling when you need fine-grained
   control over how aggressively to scale at different thresholds.

Q: How does an ASG handle unhealthy instances?
A: ASG monitors instances via EC2 or ELB health checks. When an instance is
   marked unhealthy, ASG first terminates the unhealthy instance, then launches
   a new replacement from the launch template in the same AZ. The new instance
   is added to the load balancer target group. With ELB health checks, the
   instance must pass the health check before receiving traffic.

Q: What is the health check grace period in Auto Scaling?
A: It's the time after an instance launches before ASG begins health checks.
   During this period, the ASG ignores any health check failures. This prevents
   the ASG from immediately terminating a newly launched instance that is still
   booting up. For Spring Boot applications with slow startup (30-60 seconds),
   set this to 180-300 seconds to avoid a replace-relaunch loop.

Q: What is the purpose of the cooldown period?
A: The cooldown period (default 300 seconds) prevents Auto Scaling from launching
   or terminating additional instances while a previous scaling activity is still
   in effect. This gives the new instances time to start up and reduce the metric
   value before another scaling action triggers. Only applies to Simple Scaling
   policies; Target Tracking and Step Scaling use instance warmup instead.
