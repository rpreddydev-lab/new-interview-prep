================================================================
AWS COMPUTE — ELASTIC LOAD BALANCING (ELB)
Complete Interview Preparation Guide
================================================================

1. WHAT IS ELASTIC LOAD BALANCING?
================================================================

AWS Elastic Load Balancing automatically distributes incoming application
traffic across multiple targets (EC2 instances, containers, Lambda functions,
IP addresses) in one or more AZs.

Benefits:
  - HIGH AVAILABILITY: Routes traffic only to healthy targets
  - SCALABILITY: Works with Auto Scaling Groups
  - SECURITY: SSL/TLS termination; integrates with AWS Certificate Manager
  - SINGLE ENTRY POINT: One DNS name for the entire fleet

================================================================
2. LOAD BALANCER TYPES
================================================================

TYPE 1: APPLICATION LOAD BALANCER (ALB)
  - Layer 7 (HTTP/HTTPS/WebSocket/gRPC)
  - Content-based routing (URL path, HTTP headers, query strings)
  - Best for web applications, microservices, REST APIs
  
  ROUTING RULES:
    - /api/* → API Target Group (ECS containers)
    - /images/* → Image Target Group (EC2 instances)
    - Host: api.example.com → API microservice
    - X-Request-Type: mobile → Mobile backend

---

TYPE 2: NETWORK LOAD BALANCER (NLB)
  - Layer 4 (TCP/UDP/TLS)
  - Extreme performance: millions of requests per second
  - Static IP per AZ (or Elastic IP — useful for whitelisting)
  - Lowest latency (no HTTP inspection overhead)
  
  Use cases:
  - Gaming (UDP)
  - Financial apps (low-latency TCP)
  - When you need fixed IP addresses
  - TCP pass-through (no TLS termination needed at LB)

---

TYPE 3: GATEWAY LOAD BALANCER (GWLB)
  - Layer 3 (IP traffic)
  - Deploys, scales, and manages 3rd-party virtual appliances
  - Use for: firewalls, intrusion detection systems (IDS/IPS), deep packet inspection
  - Routes traffic to network appliances then back to destination

---

TYPE 4: CLASSIC LOAD BALANCER (CLB) — LEGACY
  - Layer 4 and 7 (limited)
  - EC2-Classic network era
  - DO NOT use for new applications; migrate to ALB or NLB
  - AWS still supports but won't add new features

================================================================
3. ALB DEEP DIVE
================================================================

COMPONENTS:
  - Listener: Checks for connection requests on a specific port/protocol
  - Rules: Ordered list of conditions and actions for routing
  - Target Group: Group of registered targets (EC2, IP, Lambda, ECS)

ALB LISTENER RULES (priority order):
  Rule 1: IF path = /api/*        → Forward to API-TG
  Rule 2: IF host = blog.*        → Forward to Blog-TG
  Rule 3: IF query = ?version=2   → Forward to V2-TG
  Default: Forward to Main-TG

TARGET TYPES IN TARGET GROUPS:
  - instance: EC2 instance IDs (uses instance's private IP)
  - ip: Specific IP addresses (works with on-premises servers too)
  - lambda: Lambda function (ALB can invoke Lambda directly)

ALB STICKINESS (Session Affinity):
  - Sends requests from same client to same target
  - Uses cookie (AWSALB for ALB, AWSALBAPP for app-controlled)
  - Duration: 1 second to 7 days
  - Enable per target group
  - Use only when application has server-side session state that's not shared
    (prefer stateless apps or shared session store like Redis)

SSL/TLS TERMINATION:
  - ALB decrypts HTTPS before sending to targets (HTTP to backend)
  - Certificates managed via AWS Certificate Manager (ACM)
  - SNI (Server Name Indication) supported: multiple SSL certs per ALB
  - ALB supports TLS 1.2+ (configurable security policies)

  aws elbv2 create-listener \
    --load-balancer-arn arn:... \
    --protocol HTTPS \
    --port 443 \
    --certificates CertificateArn=arn:aws:acm:...certificate/abc \
    --default-actions Type=forward,TargetGroupArn=arn:...

FIXED RESPONSE (useful for maintenance):
  --default-actions Type=fixed-response,\
    FixedResponseConfig={StatusCode=503,MessageBody="Maintenance",ContentType=text/plain}

REDIRECT:
  Rule action: Redirect HTTP (port 80) to HTTPS (port 443)

================================================================
4. HEALTH CHECKS
================================================================

  ELB performs health checks on all registered targets.
  Traffic is only sent to HEALTHY targets.

  HEALTH CHECK SETTINGS:
    - Protocol: HTTP, HTTPS, TCP
    - Path: /health (for HTTP/HTTPS)
    - Port: traffic port or override
    - Healthy threshold: consecutive successes before marking healthy (default: 3)
    - Unhealthy threshold: consecutive failures before marking unhealthy (default: 3)
    - Timeout: seconds before a check times out (default: 5s)
    - Interval: seconds between checks (default: 30s)

  BEST PRACTICE: Create a dedicated /health endpoint in your application:
    @GetMapping("/health")
    public ResponseEntity<String> health() {
        // Check DB connectivity, cache, etc.
        return ResponseEntity.ok("UP");
    }

================================================================
5. CONNECTION DRAINING (DEREGISTRATION DELAY)
================================================================

  When an instance is deregistering (due to scale-in or health failure):
  - ELB stops sending NEW requests to the instance
  - IN-FLIGHT requests are allowed to complete (connection draining)
  - Default: 300 seconds max
  - Set to 0 to disable (immediate deregistration — data loss risk)
  - Reduce for stateless apps (30s); increase for long-running requests

================================================================
6. CROSS-ZONE LOAD BALANCING
================================================================

  WITHOUT Cross-Zone:
    AZ-A has 2 instances (each gets 25% = 50% total)
    AZ-B has 8 instances (each gets 6.25% = 50% total)
    → Uneven per-instance distribution
  
  WITH Cross-Zone:
    10 instances total across all AZs
    Each instance gets exactly 10% of traffic
    → Even distribution regardless of AZ count

  Default:
    - ALB: Cross-zone enabled by default (free)
    - NLB: Disabled by default (inter-AZ data transfer charges if enabled)
    - CLB: Disabled by default

================================================================
7. LOAD BALANCER ARCHITECTURE PATTERNS
================================================================

  INTERNET-FACING (Public):
    Internet → DNS → ALB (Public Subnets) → EC2 (Private Subnets)
    The ALB has public IPs; EC2 instances are in private subnets
    
  INTERNAL:
    App Tier (Private) → Internal ALB → Data Tier (Private)
    For microservices communication or private API endpoints

  MULTI-TIER:
    Internet
       ↓
    Public ALB (HTTPS:443, HTTP:80→redirect)
       ↓
    App EC2 Instances (Private Subnet, port 8080)
       ↓
    Internal ALB (port 80)
       ↓
    Microservice EC2/ECS (Private Subnet, port 8080)

8. ALB vs NLB COMPARISON
================================================================

  ┌─────────────────────────────────────────────────────────────┐
  │ FEATURE              │ ALB              │ NLB               │
  ├─────────────────────────────────────────────────────────────┤
  │ Layer                │ 7 (HTTP)         │ 4 (TCP/UDP)       │
  │ Routing              │ Content-based    │ IP+Port           │
  │ Static IP            │ No (DNS only)    │ Yes (per AZ)      │
  │ WebSocket            │ Yes              │ Yes               │
  │ gRPC                 │ Yes              │ No                │
  │ Lambda target        │ Yes              │ No                │
  │ Performance          │ High             │ Extreme           │
  │ SSL Termination      │ Yes              │ Yes (TLS)         │
  │ HTTP health checks   │ Yes              │ No (TCP only)     │
  │ Source IP preserved  │ Via X-Forwarded  │ Yes (preserved)   │
  │ Use case             │ Web, APIs, micro │ Gaming, Finance   │
  └─────────────────────────────────────────────────────────────┘

9. INTERVIEW QUESTIONS
================================================================

Q: What are the differences between ALB, NLB, and CLB?
A: ALB (Layer 7) is for HTTP/HTTPS applications, supports content-based routing
   (path, headers, host), can target Lambda, and best for web apps/microservices.
   NLB (Layer 4) is for TCP/UDP at extreme performance with static IPs — use for
   gaming, financial apps, or when you need source IP preservation without HTTP
   overhead. CLB is legacy (Layer 4/7), not recommended for new apps. GWLB is for
   3rd-party network appliances like firewalls.

Q: How does an ALB route traffic to different microservices?
A: ALB uses listener rules with conditions and actions. You configure rules like:
   if URL path starts with /api/ → forward to API target group; if path starts
   with /auth/ → forward to Auth service target group; if Host header matches
   admin.example.com → forward to Admin target group. Rules are evaluated in
   priority order, and a default rule handles all unmatched traffic.

Q: What is connection draining and why is it important?
A: Connection draining (deregistration delay) is the time ELB allows in-flight
   requests to complete before fully removing an instance from the pool. When an
   instance deregisters (scale-in, failure), ELB stops sending NEW requests but
   waits up to 300 seconds for existing requests to finish. Without this, users
   could get errors on in-progress requests during scale-in or deployments.
   For stateless quick-response APIs, reduce to 30-60 seconds.

Q: What is Cross-Zone Load Balancing?
A: Without cross-zone, each LB node distributes traffic only to targets in its
   AZ. If AZ-A has 2 targets and AZ-B has 8 targets, the 2 targets in AZ-A get
   25% each (50% total) while AZ-B targets get 6.25% each — uneven. With
   cross-zone enabled, all targets across all AZs receive an equal share of traffic
   regardless of how many are in each AZ. ALB has this enabled by default.

Q: How does ALB handle HTTPS/SSL termination?
A: ALB decrypts incoming HTTPS traffic at the load balancer, then sends requests
   to targets over HTTP (unencrypted) in the private subnet. SSL certificates
   are managed via ACM (AWS Certificate Manager) — free, auto-renewing. ALB
   supports SNI so you can attach multiple certificates for different domains.
   If you need end-to-end encryption to the targets, configure HTTPS on the
   targets and use HTTPS health checks.
