1. AWS SHARED RESPONSIBILITY MODEL
================================================================

  ┌─────────────────────────────────────────────────────────────┐
  │                   CUSTOMER RESPONSIBILITY                   │
  │  "Security IN the cloud"                                    │
  │                                                             │
  │  • Data encryption at rest and in transit                   │
  │  • IAM users, roles, permissions (you create them)         │
  │  • OS patching on EC2 instances                             │
  │  • Application security (code, dependencies)               │
  │  • Network/firewall configuration (SGs, NACLs)             │
  │  • Customer data classification and protection              │
  └─────────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────────┐
  │                   AWS RESPONSIBILITY                        │
  │  "Security OF the cloud"                                    │
  │                                                             │
  │  • Physical data center security                            │
  │  • Hardware, networking infrastructure                      │
  │  • Hypervisor and managed service patches                   │
  │  • RDS/Lambda/S3 infrastructure maintenance                 │
  │  • Compliance certifications (SOC, ISO, PCI)                │
  └─────────────────────────────────────────────────────────────┘
  
  Shared Services (both responsibilities):
    - Patch Management: AWS patches RDS; you patch EC2 OS
    - Configuration: AWS secures infrastructure; you secure your config
    - Awareness/Training: both

3. DEFENSE IN DEPTH
================================================================

  Layer 1: Perimeter    — WAF, Shield DDoS protection, CloudFront
  Layer 2: Network      — VPC, Subnets, NACLs, VPN/DX
  Layer 3: Host         — Security Groups, EC2 instance firewall
  Layer 4: Application  — IAM, application-level auth, input validation
  Layer 5: Data         — KMS encryption, Secrets Manager, S3 bucket policies

================================================================
4. ENCRYPTION OVERVIEW
================================================================

  AT REST:
    - S3: SSE-S3, SSE-KMS, SSE-C, Client-side
    - EBS: KMS-managed CMK
    - RDS: KMS encryption (must be set at creation)
    - DynamoDB: default SSE with AWS-owned key or KMS CMK
    - Lambda env vars: KMS

  IN TRANSIT:
    - TLS/HTTPS everywhere
    - ACM provides free SSL/TLS certificates
    - API Gateway enforces HTTPS
    - RDS: require_secure_transport parameter
    - S3 bucket policy: deny if aws:SecureTransport is false

5. AWS ORGANIZATIONS AND MULTI-ACCOUNT STRATEGY
================================================================

  AWS Organizations lets you centrally manage multiple accounts.
  
  ROOT → Organizational Units (OUs) → Member Accounts
  
  SERVICE CONTROL POLICIES (SCPs):
    - JSON policies applied at Root, OU, or account level
    - Cannot grant permissions — only RESTRICT what IAM can do
    - Even account root users are restricted by SCPs
    - Use case: prevent any account from disabling CloudTrail
  
  Example SCP — deny disabling CloudTrail:
  {
    "Effect": "Deny",
    "Action": "cloudtrail:StopLogging",
    "Resource": "*"
  }
  
  COMMON OU STRUCTURE:
    Root
    ├── Infrastructure OU (shared services)
    ├── Security OU (log archive, security tooling)
    ├── Workloads OU
    │   ├── Dev OU
    │   ├── Staging OU
    │   └── Prod OU
    └── Sandbox OU

7. INTERVIEW QUESTIONS
================================================================

Q: What is the AWS Shared Responsibility Model?
A: AWS secures "the cloud" — the physical infrastructure, hardware, networking, 
   and managed services. Customers secure "in the cloud" — their data, IAM 
   configurations, OS patching (for EC2), application code, and network settings. 
   The line shifts by service type: for EC2 (IaaS), customer is responsible for OS 
   and runtime patches; for RDS (managed), AWS patches the database engine; for Lambda 
   (serverless), AWS patches everything and customer is only responsible for their code.

Q: What are Service Control Policies (SCPs)?
A: SCPs are organizational-level policies in AWS Organizations that set permission 
   guardrails for entire accounts or OUs. They can only RESTRICT — they cannot grant 
   permissions. An SCP denying an action overrides any IAM policy that allows it, even 
   the root user. Use SCPs to: prevent disabling security services (CloudTrail, GuardDuty), 
   restrict service usage to certain regions, enforce mandatory tagging, or prevent 
   large EC2 instance types in dev accounts.

Q: Describe defense-in-depth in AWS.
A: Multiple security layers so no single failure compromises the system:
   (1) Edge: WAF rules block SQL injection/XSS; Shield protects against DDoS
   (2) Network: VPC isolation, private subnets, NACLs deny specific IPs
   (3) Host: Security Groups allow only needed ports from specific sources
   (4) Application: IAM least-privilege, Cognito authentication, input validation
   (5) Data: KMS encryption at rest, TLS in transit, Secrets Manager for credentials
   (6) Logging: CloudTrail records all API calls, GuardDuty detects anomalies
