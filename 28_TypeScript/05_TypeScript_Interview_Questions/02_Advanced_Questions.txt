SECTION 1: CONDITIONAL TYPES AND TYPE SYSTEM INTERNALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: Explain how TypeScript's type system is structural, not nominal. What are the
    practical implications?
A:  TypeScript checks assignability based on shape (properties and their types),
    not on declared class names or explicit type relationships. Two unrelated
    classes are compatible if one has at least the shape of the other.

    class Cat { name: string = ""; meow() {} }
    class Dog { name: string = ""; meow() {} }

    const c: Cat = new Dog(); // ✅ Dog satisfies Cat's shape

    Implications:
    - You cannot distinguish Cat from Dog at the type level if they share shape
    - No protection against accidental type confusion unless shapes differ
    - Brand types / opaque types solve this:
      type UserId = string & { readonly __brand: "UserId" };
      type PostId = string & { readonly __brand: "PostId" };
      // UserId and PostId are incompatible even though both are strings

Q2: What is the control flow analysis (CFA) and how does TypeScript use it?
A:  TypeScript narrows types based on code paths. After a type guard, TypeScript
    knows the variable is a specific subtype within that branch. CFA understands:
    - typeof / instanceof / in / === guards
    - Truthiness narrowing
    - Assignment narrowing
    - Assertion functions
    - The never type at unreachable code

    function process(val: string | number) {
      if (typeof val === "string") {
        val.toUpperCase(); // ✅ string here
      } else {
        val.toFixed(2); // ✅ number here — TypeScript excluded string
      }
    }

    TypeScript's CFA does NOT cross function boundaries unless you use type
    predicates (x is T) or assertion functions (asserts x is T).

Q3: What is type coercion in TypeScript and how is it different from type assertion?
A:  TypeScript has NO type coercion — it never silently converts between types.
    Type assertions (as T, <T>) are a developer directive telling TypeScript
    to treat a value as a specific type. The runtime value is unchanged.
    TypeScript will refuse an assertion if the types are not related
    (double assertion via `as unknown as T` is the escape hatch but dangerous).

    const x = "hello" as number; // ❌ Conversion of type 'string' to 'number' may be a mistake
    const y = "hello" as unknown as number; // ✅ compiles but UNSAFE — no runtime conversion

Q4: What is declaration merging and which constructs support it?
A:  Declaration merging combines multiple declarations of the same name into one.

    Interfaces support merging:
    interface Window { myLib: MyLibrary }
    interface Window { anotherThing: string }
    // Merged: Window = { myLib: ...; anotherThing: ... }

    Module augmentation (extend an external module):
    declare module "express" {
      interface Request { user?: User }
    }

    Namespace merging — namespaces can be merged with classes, enums, functions:
    class Validator { validate(s: string): boolean { return true; } }
    namespace Validator {
      export const emailRegex = /^.+@.+\..+$/;
    }
    // Validator is both a class and has a static-like namespace

    type aliases, variables, and functions do NOT merge.

Q5: What is the difference between `type A = B` and `interface A extends B`?
A:  type alias = type intersection is evaluated lazily/eagerly depending on context.
    Interface extends creates a proper inheritance relationship.

    type A = B & { extra: string };       // type alias with intersection
    interface A extends B { extra: string; } // interface extends

    Key runtime differences:
    - Both produce the same effective shape for simple cases
    - Interfaces display as the interface name in error messages (better DX)
    - Interfaces support declaration merging
    - Type aliases can represent unions, tuples, mapped/conditional types
    - Circular references work better with interfaces historically

Q6: What are ambient declarations and when do you need them?
A:  Ambient declarations describe shape without implementation — for JS code
    that has no TypeScript source. Lives in `.d.ts` files or `declare` blocks.

    declare const MY_GLOBAL: string;           // global variable from script tag
    declare function loadPolyfill(): void;      // function defined elsewhere
    declare module "*.svg" {                    // wildcard for all .svg imports
      const src: string;
      export default src;
    }
    declare module "untyped-library" {          // entire module
      export function doThing(x: number): string;
    }

    Without ambient declarations, TypeScript reports "module not found" or
    "cannot find name" errors for code that exists at runtime.

Q7: How do you implement a DeepReadonly type?
A:  Recursively apply Readonly — but you must handle only object types, not
    primitives, arrays, or functions:

    type DeepReadonly<T> =
      T extends (infer E)[]
        ? ReadonlyArray<DeepReadonly<E>>
        : T extends object
          ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
          : T;

    type Config = {
      server: { host: string; port: number };
      flags: string[];
    };
    type ImmutableConfig = DeepReadonly<Config>;
    // { readonly server: { readonly host: string; readonly port: number };
    //   readonly flags: ReadonlyArray<string> }

Q8: How do you filter keys from an object type based on the value type?
A:  Use mapped types with `as` clause (key remapping) and conditional types:

    // Keep only keys whose value extends V
    type KeysOfType<T, V> = {
      [K in keyof T]: T[K] extends V ? K : never
    }[keyof T];

    type PickByType<T, V> = Pick<T, KeysOfType<T, V>>;

    type User = { id: number; name: string; email: string; age: number; active: boolean };
    type StringFields = PickByType<User, string>; // { name: string; email: string }
    type NumericFields = PickByType<User, number>; // { id: number; age: number }

    Or using the `as` clause directly (TS 4.1+):
    type PickByType<T, V> = {
      [K in keyof T as T[K] extends V ? K : never]: T[K]
    };

Q9: What is the `infer` keyword and what are its constraints?
A:  `infer` declares a type variable within a conditional type's extends clause.
    TypeScript fills it in during type resolution.

    Constraints:
    - Only usable inside conditional type extends clause
    - Multiple infer sites in the same position are merged
    - In covariant position (return type) → union when multiple branches
    - In contravariant position (function param) → intersection
    - Cannot be used outside conditional types

    // Valid use cases:
    type FirstParam<T extends (...args: any) => any> =
      T extends (first: infer P, ...rest: any[]) => any ? P : never;

    type Head<T extends any[]> =
      T extends [infer H, ...any[]] ? H : never;

    type Tail<T extends any[]> =
      T extends [any, ...infer T] ? T : never;

Q10: How does TypeScript handle recursive types?
A:   TypeScript supports recursive type aliases (TS 3.7+):

     type JsonValue =
       | string | number | boolean | null
       | JsonValue[]
       | { [key: string]: JsonValue };

     type DeepPartial<T> = {
       [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
     };

     // Recursive conditional with depth limit using tuples:
     type Flatten<T, Depth extends any[] = []> =
       Depth["length"] extends 5
         ? T
         : T extends (infer E)[]
           ? Flatten<E, [any, ...Depth]>
           : T;

     TypeScript defers resolution of recursive types to avoid infinite loops.
     Very deep or circular recursive types can cause "Type instantiation is
     excessively deep and possibly infinite" errors.

Q11: What is the difference between TypeScript's `private` and ECMAScript's `#`?
A:
    ┌─────────────────────┬──────────────────────────┬───────────────────────────┐
    │ Feature             │ TypeScript `private`     │ ECMAScript `#`            │
    ├─────────────────────┼──────────────────────────┼───────────────────────────┤
    │ Compile-time only   │ Yes — stripped in JS     │ No — enforced at runtime  │
    │ Runtime privacy     │ No — accessible in JS    │ Yes — truly private       │
    │ Reflection access   │ Possible (any cast)      │ Not possible              │
    │ Subclass visibility │ Not inherited            │ Not inherited             │
    │ JSON.stringify      │ Included                 │ Excluded                  │
    │ Target support      │ Any ES target            │ ES2022+ required          │
    └─────────────────────┴──────────────────────────┴───────────────────────────┘

    class A {
      private tsPrivate = 1;
      #esPrivate = 2;
    }
    const a = new A();
    (a as any).tsPrivate; // ✅ accessible at runtime
    (a as any)["#esPrivate"]; // ❌ undefined — truly private

Q12: What are decorators in TypeScript 5 (TC39 Stage 3)?
A:   TC39 decorators (enabled by default in TS 5.0, no experimentalDecorators needed)
     use a context object instead of descriptor + target:

     function log(target: Function, context: ClassMethodDecoratorContext) {
       return function(this: unknown, ...args: unknown[]) {
         console.log(`Calling ${String(context.name)}`);
         return (target as Function).call(this, ...args);
       };
     }

     class Calculator {
       @log
       add(a: number, b: number) { return a + b; }
     }

     Key differences from legacy decorators:
     - Context object (kind, name, static, private, addInitializer)
     - Applied bottom-up (innermost first)
     - No PropertyDescriptor manipulation
     - Works without emitDecoratorMetadata

Q13: What is the `override` keyword in TypeScript 4.3+?
A:   `override` explicitly marks a method as overriding a base class method.
     With `noImplicitOverride: true` in tsconfig, every method that overrides
     MUST have the `override` keyword:

     class Base { greet() { return "Hello"; } }

     class Child extends Base {
       override greet() { return "Hi"; }    // ✅
       welcome() { return "Welcome"; }       // ✅ new method, no override needed
     }

     // If Base removes or renames `greet`:
     class Child2 extends Base {
       override greet() { ... } // ❌ Error: greet doesn't exist in base (if renamed)
     }

     This prevents "ghost overrides" — thinking you override a method but
     actually defining a new one with a typo.

Q14: What causes "Type instantiation is excessively deep" error and how do you fix it?
A:   This occurs with recursive conditional or mapped types that TypeScript
     cannot resolve within its recursion limit (~100 levels). Common causes:
     - Recursive types without a base case
     - Overly complex template literal type combinations
     - Deep chains of conditional types on large unions

     Fixes:
     1. Add a depth counter using tuple length:
        type Recurse<T, D extends any[] = []> =
          D["length"] extends 10 ? T : Recurse<Next<T>, [...D, 0]>;

     2. Use interface instead of type alias for recursive shapes
     3. Simplify intermediate types — break complex types into named aliases
     4. Use `@ts-ignore` as last resort on the problematic line

Q15: What is `verbatimModuleSyntax` in tsconfig and why does it matter?
A:   `verbatimModuleSyntax: true` (TS 5.0+) replaces `importsNotUsedAsValues`
     and `preserveValueImports`. It enforces that:
     - Type-only imports MUST use `import type`
     - Regular imports that only import types must be converted to `import type`
     - Prevents "elided imports" that might erase important side effects

     // Without verbatimModuleSyntax:
     import { User } from "./types"; // may or may not be erased at emit

     // With verbatimModuleSyntax:
     import type { User } from "./types"; // MUST be import type if only used as type
     import { createUser } from "./users"; // kept as-is (value import)

     Matters for bundlers like Vite/esbuild that transform each file in
     isolation — they need to know which imports are type-only to safely remove them.

Q16: How does the `satisfies` operator differ from type annotations and assertions?
A:
    ┌─────────────────────────┬──────────────────────────────┬──────────────────┐
    │                         │ Type Annotation (: Type)     │ satisfies Type   │
    ├─────────────────────────┼──────────────────────────────┼──────────────────┤
    │ Validates against type  │ Yes                          │ Yes              │
    │ Preserves literal type  │ No — widens to annotation    │ Yes              │
    │ Caught by TS            │ Error on violation           │ Error on violation│
    └─────────────────────────┴──────────────────────────────┴──────────────────┘

    type Config = { port: number | string; host: string };

    // Annotation: widens type
    const c1: Config = { port: 3000, host: "localhost" };
    c1.port.toFixed(); // ❌ Error: number | string has no toFixed

    // satisfies: validates but keeps specific type
    const c2 = { port: 3000, host: "localhost" } satisfies Config;
    c2.port.toFixed(); // ✅ TypeScript knows port is number (3000)

Q17: What is `isolatedModules` and when should you enable it?
A:   `isolatedModules: true` makes TypeScript error on features that can't be
     safely transpiled on a per-file basis (single-file transformers like Babel,
     esbuild, swc). Use it when your build tool transpiles each file in isolation.

     Errors you'll see with isolatedModules:
     - const enum usage (can't inline from other files)
     - namespace merging across files
     - `export { X }` where X is only a type (must use `export type { X }`)
     - Non-module files

     This is automatically enforced by Vite, create-react-app, ts-jest with
     isolated transforms. Keeps build tool assumptions compatible with tsc.

Q18: What is the difference between `moduleResolution: node` and `bundler`?
A:
    node: follows Node.js CommonJS resolution — looks for .js, then index.js,
    package.json main field. Requires extensions in imports for ESM.

    bundler (TS 5.0+): designed for bundlers like Vite, webpack, Rollup.
    - Allows extensionless imports (import "./foo" resolves ./foo.ts)
    - Respects package.json exports field
    - Does NOT require explicit .js extensions in relative imports
    - Enables paths/baseUrl without strict ESM requirements

    nodenext/node16: strict ESM mode — requires explicit file extensions
    in imports, respects package.json type: "module", enables .mts/.cts files.

    Use `bundler` for modern frontend projects, `nodenext` for pure Node.js ESM.
