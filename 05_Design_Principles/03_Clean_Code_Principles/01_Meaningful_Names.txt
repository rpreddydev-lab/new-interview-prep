================================================================
  MEANINGFUL NAMES — CLEAN CODE
================================================================

  Names are the most fundamental communication in code.
  A good name eliminates the need for a comment.
  A bad name requires mental translation every time you read it.

----------------------------------------------------------------
RULE 1: USE INTENTION-REVEALING NAMES
----------------------------------------------------------------

  // BAD: requires mental effort to decode
  int d;            // elapsed time in days
  List<int[]> list1;

  // GOOD: name tells the story
  int elapsedDays;
  List<int[]> flaggedCells;

  // BAD function: what does it return? what is "them"?
  public List<int[]> getThem() {
      List<int[]> list1 = new ArrayList<>();
      for (int[] x : theList) {
          if (x[0] == 4) list1.add(x);
      }
      return list1;
  }

  // GOOD: names reveal domain intent
  public List<Cell> getFlaggedCells() {
      List<Cell> flaggedCells = new ArrayList<>();
      for (Cell cell : gameBoard) {
          if (cell.isFlagged()) flaggedCells.add(cell);
      }
      return flaggedCells;
  }

----------------------------------------------------------------
RULE 2: AVOID DISINFORMATION
----------------------------------------------------------------

  // BAD: "accountList" is not a List
  Map<String, Account> accountList = new HashMap<>();
  // Naming a Map "List" creates false expectation

  // GOOD:
  Map<String, Account> accountMap = new HashMap<>();
  // OR: accounts (type-agnostic)

  // BAD: similar names, easy to misread
  XYZControllerForEfficientHandlingOfStrings
  XYZControllerForEfficientStorageOfStrings

  // BAD: l (lowercase L) looks like 1; O looks like 0
  int l = 1;
  int O = 0;
  if (O == l) ...  // impossible to read

----------------------------------------------------------------
RULE 3: MEANINGFUL DISTINCTIONS — NO NOISE WORDS
----------------------------------------------------------------

  // BAD: noise words add nothing
  class ProductInfo    // vs ProductData   — what's the difference?
  class ProductData    // these are synonyms

  void copyChars(char[] a1, char[] a2) { ... }   // a1, a2 = meaningless
  void copyChars(char[] source, char[] destination) { ... }  // clear

  // BAD noise words: Manager, Processor, Info, Data, Handler (unless precise)
  AccountManager  -- what does it manage?
  DataInfo        -- redundant: info IS data

  // GOOD: use them when they add precision:
  EventHandler    -- handles events (role is clear)
  ConnectionPool  -- manages a pool of connections (specific)

----------------------------------------------------------------
RULE 4: USE PRONOUNCEABLE NAMES
----------------------------------------------------------------

  // BAD: unpronounceable — how do you say this in code review?
  private Date genymdhms;    // generation year month day hour minute second

  // GOOD: readable, discussable
  private Date generationTimestamp;

  // BAD:
  class DtaRcrd102 { ... }

  // GOOD:
  class Customer { ... }

----------------------------------------------------------------
RULE 5: USE SEARCHABLE NAMES
----------------------------------------------------------------

  // BAD: hard to grep for 7, e, s
  for (int j = 0; j < 34; j++) {
      s += (t[j] * 4) / 5;
  }

  // GOOD: names are greppable
  int WORK_DAYS_PER_WEEK = 5;
  int WEEKS_UNTIL_DEADLINE = 4;

  for (int taskIndex = 0; taskIndex < NUMBER_OF_TASKS; taskIndex++) {
      realDaysPerTask[taskIndex] = 4 / WORK_DAYS_PER_WEEK;
  }

  Length 1 names (i, j, k) are acceptable ONLY inside tiny loop bodies
  where scope is immediately visible.

----------------------------------------------------------------
RULE 6: CLASS NAMES — NOUNS; METHOD NAMES — VERBS
----------------------------------------------------------------

  // Class names: noun or noun phrase
  Customer, Account, WikiPage, AddressParser

  // NOT verbs or vague:
  Manager, Processor, Data, Info, Handler (unless specific)

  // Method names: verb or verb phrase
  postPayment(), deletePage(), save()

  // Accessors: get/set/is prefix (JavaBeans convention)
  getName(), setName(), isActive()

  // Factory methods: use descriptive name
  Complex.fromRealNumber(5.0)   // better than: new Complex(5.0)
  User.ofEmail("alice@x.com")  // reveals intent of the constructor

----------------------------------------------------------------
RULE 7: ONE WORD PER CONCEPT — NO PUNS
----------------------------------------------------------------

  // BAD: same concept, different words (inconsistent)
  class User      { void fetch() { ... } }
  class Account   { void retrieve() { ... } }
  class Customer  { void get() { ... } }
  // Pick ONE: get/fetch/retrieve and use it everywhere.

  // BAD: same word, different concepts (pun)
  void add(Collection c, int element)  { /* adds to collection */ }
  void add(int a, int b)               { /* arithmetic addition */ }
  // "add" means TWO different things. Use "append()" or "sum()".

----------------------------------------------------------------
RULE 8: DOMAIN LANGUAGE — USE SOLUTION AND PROBLEM DOMAIN NAMES
----------------------------------------------------------------

  Solution domain (CS terms — developers know these):
    JobQueue, AccountVisitor, BinaryTree, Cache, Factory

  Problem domain (business terms — domain experts know these):
    Invoice, PurchaseOrder, ShipmentManifest, Customer, Policy

  Prefer solution domain names in infrastructure code.
  Prefer problem domain names in domain/business logic code.

  Example:
    Repository   -- solution domain (pattern name)
    OrderService -- problem domain (business concept)
    Both are appropriate in their layers.

----------------------------------------------------------------
RULE 9: AVOID MENTAL MAPPING
----------------------------------------------------------------

  // BAD: single letter for abstract iteration variable
  for (String a : accounts) {
      kludge(a);  // reader must remember "a" means account
  }

  // GOOD: explicit name
  for (String account : accounts) {
      process(account);
  }

  Exception: i, j in small for loops is idiomatic — no harm.
  Never use a, b, c, d for anything meaningful.

----------------------------------------------------------------
BOOLEAN VARIABLE / METHOD NAMES
----------------------------------------------------------------

  // BAD: not clear what "true" means
  if (flag) { ... }

  // GOOD: reads like English
  if (customer.isActive()) { ... }
  if (order.isEmpty()) { ... }
  if (!user.isVerified()) { ... }

  Boolean methods: is..., has..., can..., should..., supports...
  isValid(), hasPermission(), canExecute(), shouldRetry()

----------------------------------------------------------------
QUICK REFERENCE: GOOD VS BAD NAMES
----------------------------------------------------------------

  BAD                   GOOD
  ------------------    ----------------------------
  d                     elapsedDays
  info                  userProfile
  data                  orderData (if needed) / order
  theList               flaggedCells
  str, s, s1            userName, customerEmail
  flag                  isActive, isPaid
  manager               userRepository (specific role)
  x, y (domain)         latitude, longitude
  calc()                calculateTax()
  process()             processOrder()
  doStuff()             sendWelcomeEmail()
  temp                  temporaryBuffer (or eliminate)

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What makes a good variable name?
  A: It reveals intent without comments. Reader shouldn't need to look
     elsewhere to understand what it holds. It's pronounceable, searchable,
     uses the right domain language, and avoids noise words that add nothing.

  Q: What is the difference between intention-revealing names and comments?
  A: A good name makes the comment unnecessary. If you need a comment to
     explain a variable, the variable name failed. Comments should explain
     WHY (business reason), not WHAT (which the code should already say).
