================================================================
  OPEN/CLOSED PRINCIPLE (OCP)
================================================================

  Definition: Software entities (classes, modules, functions) should be
              OPEN for extension but CLOSED for modification.

  Bertrand Meyer (1988) original: use inheritance.
  Robert C. Martin (1996) refinement: use polymorphism + abstraction.

  In practice: you should be able to ADD new behavior WITHOUT changing
  existing, tested, deployed code.

----------------------------------------------------------------
WHY OCP MATTERS
----------------------------------------------------------------

  When a new requirement forces modification of existing classes:
    - You risk breaking existing working functionality
    - All existing tests must be re-run (regression risk)
    - If you can't modify (library, third-party), you're stuck
    - Change one class → chain of changes across codebase (rigidity)

  OCP removes the need to modify existing code to add new behavior.

----------------------------------------------------------------
VIOLATION EXAMPLE — IF-ELSE CHAINS
----------------------------------------------------------------

  // BAD: must modify calculateArea() every time a shape is added
  public class AreaCalculator {
      public double calculateArea(Object shape) {
          if (shape instanceof Circle) {
              Circle c = (Circle) shape;
              return Math.PI * c.getRadius() * c.getRadius();
          } else if (shape instanceof Rectangle) {
              Rectangle r = (Rectangle) shape;
              return r.getWidth() * r.getHeight();
          } else if (shape instanceof Triangle) {
              // ADDING THIS REQUIRED MODIFYING THIS CLASS
              Triangle t = (Triangle) shape;
              return 0.5 * t.getBase() * t.getHeight();
          }
          throw new IllegalArgumentException("Unknown shape");
      }
  }

  Every new shape = open this class again = risk regression = violates OCP.

----------------------------------------------------------------
FIX: ABSTRACTION + POLYMORPHISM
----------------------------------------------------------------

  // Open for extension (add shape), closed for modification (no if-else)
  public interface Shape {
      double area();  // each shape knows its own area formula
  }

  public class Circle implements Shape {
      private final double radius;
      public Circle(double radius) { this.radius = radius; }
      public double area() { return Math.PI * radius * radius; }
  }

  public class Rectangle implements Shape {
      private final double width, height;
      public Rectangle(double width, double height) {
          this.width = width;
          this.height = height;
      }
      public double area() { return width * height; }
  }

  // AreaCalculator never changes when new shapes are added
  public class AreaCalculator {
      public double calculateTotalArea(List<Shape> shapes) {
          return shapes.stream().mapToDouble(Shape::area).sum();
      }
  }

  // Adding Triangle = new class only. Zero changes to AreaCalculator.
  public class Triangle implements Shape {
      private final double base, height;
      public Triangle(double base, double height) {
          this.base = base;
          this.height = height;
      }
      public double area() { return 0.5 * base * height; }
  }

OCP AND STRATEGY PATTERN
----------------------------------------------------------------

  // PaymentProcessor closed for modification; open for new payment methods
  @FunctionalInterface
  public interface PaymentStrategy {
      PaymentResult pay(double amount);
  }

  @Service
  public class PaymentProcessor {
      public PaymentResult process(double amount, PaymentStrategy strategy) {
          validateAmount(amount);
          return strategy.pay(amount);  // this line never changes
      }
  }

  // Adding Crypto payment = new strategy only. PaymentProcessor unchanged.
  PaymentStrategy crypto = amount -> cryptoGateway.send(amount, walletAddress);
  processor.process(99.99, crypto);

----------------------------------------------------------------
OCP AND SPRING BEAN MAP PATTERN
----------------------------------------------------------------

  // Dispatcher closed for modification; open for new handlers
  @Service
  @RequiredArgsConstructor
  public class OrderHandler {
      private final Map<String, OrderProcessor> processors;

      public void handle(Order order) {
          OrderProcessor processor = processors.get(order.getType());
          if (processor == null) throw new IllegalArgumentException("No processor for: " + order.getType());
          processor.process(order);
      }
  }

  // Adding SUBSCRIPTION order type = new @Component bean only
  @Component("SUBSCRIPTION")
  public class SubscriptionOrderProcessor implements OrderProcessor {
      public void process(Order order) { /* subscription logic */ }
  }

  OrderHandler never changes when new order types are added.

----------------------------------------------------------------
OCP AND DECORATOR PATTERN
----------------------------------------------------------------

  Decorator is the structural implementation of OCP:
    - Existing class CLOSED (not modified)
    - New behavior added by WRAPPING with new decorator class

  // Adding logging to existing service — no modification of service
  public class LoggingPaymentGateway implements PaymentGateway {
      private final PaymentGateway delegate;
      private final Logger log = LoggerFactory.getLogger(getClass());

      public LoggingPaymentGateway(PaymentGateway delegate) {
          this.delegate = delegate;
      }

      public PaymentResult charge(double amount) {
          log.info("Charging {}", amount);
          PaymentResult result = delegate.charge(amount);
          log.info("Result: {}", result);
          return result;
      }
  }

  // PaymentGateway implementations unchanged; logging added by decoration.

----------------------------------------------------------------
COMMON OCP PATTERNS
----------------------------------------------------------------

  Pattern             How It Achieves OCP
  ----------------    -----------------------------------------------
  Strategy            New algorithm = new class; context unchanged
  Decorator           New behavior = new wrapper; component unchanged
  Template Method     New step = override in subclass; skeleton fixed
  Observer            New reaction = new listener; subject unchanged
  Composite           New element = new leaf class; structure unchanged
  Visitor             New operation = new visitor; elements unchanged
  Chain of Resp       New handler = new link; chain construction flexible

----------------------------------------------------------------
ANTI-PATTERNS THAT VIOLATE OCP
----------------------------------------------------------------

  1. instanceof chains — every new type = modify the chain
  2. switch(type) — add case to every switch site
  3. enum with behavior — adding a constant may require every switch
  4. Big factory if-else — add product = modify factory

  Fix: Replace with polymorphism or registry/map dispatch.

----------------------------------------------------------------
LIMITS OF OCP
----------------------------------------------------------------

  "Closed to modification" is aspirational. In practice:
    - First change: understand the variation, design the abstraction
    - Second change: the abstraction fits, OCP pays off
    - YAGNI: don't pre-abstract for imagined future requirements

  Be open to closing: refactor AFTER the second similar change hits.
  Over-applying OCP creates premature abstractions (YAGNI violation).

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is OCP? How do you apply it in Java?
  A: OCP says add new behavior by extension, not modification. In Java:
     extract an interface (Shape, Strategy); each new variant implements it.
     Existing code depends on the interface and never changes when a new
     implementation is added. Spring Map<String, BeanInterface> injection
     lets you register new handlers without touching the dispatcher.

  Q: How does Spring Framework apply OCP?
  A: Spring's DispatcherServlet delegates to HandlerMapping, HandlerAdapter,
     ViewResolver, MessageConverter — all interfaces. Adding new HTTP handling
     = new implementation registered as a bean. DispatcherServlet never changes.

  Q: Isn't it impossible to be completely closed to modification?
  A: Yes. OCP is an ideal. In practice: identify the LIKELY axes of change
     (different payment methods, different discount types) and close those axes.
     Don't over-abstract everything — use YAGNI; abstract when the second
     similar change arrives (Rule of Three).

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Always show the if-else violation then the polymorphism fix.
  - Connect OCP to at least one pattern (Strategy or Decorator).
  - Mention Spring's bean map pattern — shows real-world OCP.
  - Acknowledge YAGNI tension: OCP needs balancing with pragmatism.
