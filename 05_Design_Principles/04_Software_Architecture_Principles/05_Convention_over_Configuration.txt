================================================================
  CONVENTION OVER CONFIGURATION (CoC)
================================================================

  Definition: A framework provides sensible default behaviors based on
  conventions. Developers only need to configure what differs from defaults.

  Also called: "Convention over Configuration" or "Coding by Convention."
  Popularized by: Ruby on Rails (2004), Spring Boot (2014).

  Core idea: The common case should require zero configuration;
             the uncommon case should require explicit configuration.

================================================================
THE PROBLEM IT SOLVES
================================================================

  BEFORE (Spring pre-Boot, J2EE era) — heavy configuration:

  web.xml:
  <servlet>
    <servlet-name>myServlet</servlet-name>
    <servlet-class>com.example.MyServlet</servlet-class>
  </servlet>
  <servlet-mapping>
    <servlet-name>myServlet</servlet-name>
    <url-pattern>/api/*</url-pattern>
  </servlet-mapping>

  applicationContext.xml:
  <bean id="dataSource" class="org.apache.commons.dbcp.BasicDataSource">
    <property name="driverClassName" value="com.mysql.jdbc.Driver"/>
    <property name="url" value="jdbc:mysql://localhost/mydb"/>
    ...
  </bean>

  Plus: persistence.xml, beans.xml, dozens more XML files.

  Result: Hours of configuration before writing a single line of business code.

================================================================
SPRING BOOT CoC EXAMPLES
================================================================

  1. AUTO-CONFIGURED DATA SOURCE:
     If spring-boot-starter-data-jpa + h2 is on classpath →
     Spring Boot auto-creates an in-memory DataSource.
     No configuration needed for development.
     Override by setting spring.datasource.url in application.properties.

  2. EMBEDDED SERVER:
     spring-boot-starter-web → Tomcat starts on port 8080.
     To change: server.port=9090 in application.properties.

  3. JPA ENTITY MAPPING:
     @Entity class Order → maps to "order" table (lowercase class name).
     @Column is optional — field name = column name by default.
     Override: @Table(name="orders") @Column(name="order_total")

  4. SPRING MVC:
     @Controller + @RequestMapping → mapped to URL automatically.
     Return type String → view name convention (templates/name.html in Thymeleaf).

  5. COMPONENT SCAN:
     @SpringBootApplication → scans current package and sub-packages.
     No need to list each component.

  6. PROPERTY FILES:
     application.properties or application.yml → loaded automatically.
     Environment-specific: application-dev.yml, application-prod.yml.

================================================================
CONVENTIONS IN COMMON FRAMEWORKS
================================================================

  SPRING DATA JPA:
  - Method name conventions → query generation
    findByEmailAndActive(String email, boolean active)
    → SELECT * FROM user WHERE email = ? AND active = ?
  - No SQL or @Query needed for common queries

  SPRING SECURITY:
  - Default login page at /login if configured
  - Default logout at /logout
  - /css, /js, /images permitted by default
  - Configure only non-standard paths

  MAVEN:
  - src/main/java → source code
  - src/test/java → tests
  - src/main/resources → resources
  - target/ → compiled output
  No configuration needed — Maven knows where to look.

  MAVEN CONVENTION TABLE:
  Directory              | Convention
  -----------------------|------------------------------------------
  src/main/java          | Application source
  src/main/resources     | Properties, XML, templates
  src/test/java          | Unit/integration tests
  src/test/resources     | Test configurations
  target/                | Build output (auto-generated)

================================================================
COC vs EXPLICIT CONFIGURATION
================================================================

  Use Convention When:
  - Common case: Spring Boot default DataSource for development
  - Standard naming: JPA table = class name
  - Standard structure: Maven directory layout

  Override with Configuration When:
  - Non-standard DB table names (legacy DB)
  - Non-standard ports (microservice with specific port)
  - Non-standard scan packages (multi-module projects)
  - Feature flags / environment-specific beans

================================================================
BENEFITS AND TRADEOFFS
================================================================

  Benefits:
  + Drastic reduction in boilerplate
  + Faster project setup
  + Consistency across teams
  + Fewer bugs from misconfiguration
  + Self-documenting structure (follow convention = structure is obvious)

  Tradeoffs:
  - Magic: behavior happens without explicit code → harder for beginners to debug
  - Over-reliance on defaults can mask wrong assumptions
  - Requires knowing the conventions (learning curve)

  Mitigation: Spring Boot Actuator shows auto-configuration report:
  --debug flag or /actuator/conditions endpoint shows what was auto-configured and why.

================================================================
COC AND SOLID
================================================================

  CoC supports OCP at the framework level:
  - Framework provides default behavior
  - You extend/override only what you need to customize
  - Closed for modification (don't touch the framework), open for extension

  CoC supports YAGNI:
  - Don't configure what you don't need
  - The framework assumes sensible defaults

================================================================
INTERVIEW Q&A
================================================================

  Q: What is Convention over Configuration?
  A: A design philosophy where frameworks provide sensible defaults.
     Developers only configure what differs from convention. Reduces
     boilerplate significantly. Spring Boot and Maven are primary examples.

  Q: How does Spring Boot implement CoC?
  A: Auto-configuration: scans classpath for known libraries and configures
     them with defaults (DataSource from spring.datasource.*, Tomcat on 8080,
     JPA entity → table name by convention). Override with application.properties.

  Q: What's the risk of Convention over Configuration?
  A: "Magic" — behavior happens without explicit code. Harder to debug when
     something doesn't work as expected. Mitigated by reading auto-configuration
     reports (--debug, /actuator/conditions).

  Q: Give a Spring Data JPA convention example.
  A: Method named findByEmailAndStatus(String email, Status s) in a
     JpaRepository → Spring Data generates the query automatically.
     No SQL, no @Query annotation needed for this common case.
