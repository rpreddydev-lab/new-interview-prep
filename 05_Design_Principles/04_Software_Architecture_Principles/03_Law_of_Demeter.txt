================================================================
  LAW OF DEMETER (LOD) — PRINCIPLE OF LEAST KNOWLEDGE
================================================================

  "Don't talk to strangers."
  "Only talk to your immediate friends."

  Formulated at Northeastern University, 1987 (Project Demeter).
  Also called "Principle of Least Knowledge."

================================================================
FORMAL DEFINITION
================================================================

  A method M of object O may only call methods of:

  1. O itself                          (self)
  2. Objects passed as parameters to M (parameters)
  3. Objects created/instantiated by M (local creation)
  4. O's direct component objects      (fields of O)
  5. Global/static objects accessible by M

  NOT: Objects returned by calling methods on other objects (strangers).

================================================================
VIOLATION — TRAIN WRECK CODE
================================================================

  // Order has a Customer, Customer has an Address, Address has a City
  String city = order.getCustomer().getAddress().getCity();

  Problem: OrderService knows about:
  - Order
  - Customer (got from Order)
  - Address (got from Customer)
  - City (got from Address)

  If Address is restructured, OrderService must change.
  If Customer changes how it stores Address, OrderService must change.

================================================================
FIX — HIDE THE DELEGATE
================================================================

  Add a delegation method at each intermediate class:

  class Order {
      private Customer customer;
      public String getCustomerCity() {
          return customer.getCity();   // Order asks Customer
      }
  }

  class Customer {
      private Address address;
      public String getCity() {
          return address.getCity();    // Customer asks Address
      }
  }

  OrderService:
  String city = order.getCustomerCity();   // only knows Order

  Now OrderService is only coupled to Order.

================================================================
EXCEPTIONS TO THE LAW OF DEMETER
================================================================

  1. DATA OBJECTS / DTOs / RECORDS:
     Chaining on pure data objects is acceptable:
     response.getBody().getData().getItems()
     → These are value holders, not behavioral objects.
       Refactoring them adds no value.

  2. BUILDER PATTERN:
     order.withCustomer(c).withItem(i).withDiscount(d).build()
     → Builder returns itself (same object), not a new stranger.

  3. STREAM PIPELINES:
     list.stream().filter(...).map(...).collect(...)
     → Each call returns a new Stream of the same type.
       LoD is about behavioral coupling, not fluent APIs on same type.

  4. OPTIONAL CHAINING:
     Optional.ofNullable(user).map(User::getEmail).orElse("")
     → Similar to streams — safe, functional unwrapping.

================================================================
LOD AND TELL DON'T ASK
================================================================

  They reinforce each other:

  Tell Don't Ask → Don't reach into another object to get data,
                   tell it to do something with its own data.

  Law of Demeter → Don't chain through multiple objects to get data
                   from a stranger.

  Both fight Feature Envy and excessive coupling.

  BEFORE (violates both):
  double discount = order.getCustomer().getMembership().getDiscountRate();
  double final = total * (1 - discount);

  AFTER (respects both):
  double final = order.applyCustomerDiscount(total);
  // Order knows how to ask Customer; Customer knows how to ask Membership.

================================================================
LOD IN MICROSERVICES
================================================================

  LoD applies at service level too:

  Order Service should NOT reach into:
  Customer Service DB directly,
  Payment Service internal state,
  Inventory Service internal model.

  Order Service should:
  Call Customer Service API (the "neighbor")
  Receive what it needs, not crawl through Customer Service internals.

================================================================
PRACTICAL DETECTION
================================================================

  Red flags:
  - Method chains longer than 2 dots: a.b().c().d()
  - A class imports many packages it doesn't directly own
  - A test needs to mock 3 levels of objects to test one method
  - Class knows the internal structure of its dependencies' dependencies

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the Law of Demeter?
  A: A method should only call methods on: itself, its fields, its
     parameters, and objects it creates. Not on objects returned by
     calling methods on other objects. Reduces coupling to "strangers."

  Q: What is a train wreck violation?
  A: a.getB().getC().getD() — chaining through multiple objects.
     The caller is coupled to A, B, C, and D. Hiding delegates resolves it.

  Q: When is chaining acceptable?
  A: On DTOs/records (pure data), builder patterns (same object returned),
     stream/Optional pipelines (functional, same type). LoD targets
     behavioral coupling, not data access.

  Q: How does LoD relate to coupling?
  A: Each additional dot in a chain = one more coupling dependency.
     Violating LoD spreads coupling through the call graph, making code
     fragile when intermediate structures change.
