================================================================
  SEPARATION OF CONCERNS (SoC)
================================================================

  Definition: Each module, class, or layer should address one and
  only one concern (a specific piece of functionality or type of
  decision). Different concerns should be in different places.

  Coined by Edsger W. Dijkstra (1974): "On the role of scientific
  thought" — separating concerns allows each to be studied in isolation.

================================================================
WHAT IS A "CONCERN"?
================================================================

  A concern is any distinct aspect of the software, for example:

  - Business rules (what the application does)
  - Data persistence (how data is stored)
  - Security (authentication, authorization)
  - Logging / Auditing
  - Error handling
  - Transaction management
  - UI presentation
  - Caching
  - Validation

  SoC says: don't let these bleed into each other.

================================================================
VIOLATION EXAMPLE
================================================================

  @RestController
  class OrderController {

      @PostMapping("/orders")
      ResponseEntity<String> placeOrder(@RequestBody OrderDto dto) {

          // VALIDATION concern
          if (dto.getItems().isEmpty()) return ResponseEntity.badRequest().body("No items");

          // BUSINESS LOGIC concern
          double total = 0;
          for (Item i : dto.getItems()) total += i.getPrice() * i.getQty();
          if (dto.isMember()) total *= 0.9;

          // PERSISTENCE concern
          Order o = new Order(dto.getCustomerId(), dto.getItems(), total);
          entityManager.persist(o);

          // NOTIFICATION concern
          emailService.sendConfirmation(dto.getEmail(), o.getId());

          // AUDIT concern
          auditLog.record("ORDER_PLACED", o.getId());

          return ResponseEntity.ok("Order " + o.getId() + " placed");
      }
  }

  Problems:
  - Can't test business logic without a database and email server
  - Can't change persistence without touching business logic
  - Controller is the reason to change for 5 different actors

================================================================
FIXED EXAMPLE — LAYERED SEPARATION
================================================================

  Controller (HTTP concern only):
  @RestController
  class OrderController {
      private final OrderService orderService;

      @PostMapping("/orders")
      ResponseEntity<OrderResponse> placeOrder(@Valid @RequestBody OrderDto dto) {
          OrderResponse response = orderService.placeOrder(dto);
          return ResponseEntity.ok(response);
      }
  }

  Service (Business logic concern):
  @Service
  class OrderService {
      private final OrderRepository repo;
      private final ApplicationEventPublisher events;

      public OrderResponse placeOrder(OrderDto dto) {
          double total = calculateTotal(dto.getItems(), dto.isMember());
          Order order = new Order(dto.getCustomerId(), dto.getItems(), total);
          repo.save(order);
          events.publishEvent(new OrderPlacedEvent(order));  // others listen
          return new OrderResponse(order.getId(), total);
      }
  }

  Repository (Persistence concern):
  @Repository
  interface OrderRepository extends JpaRepository<Order, Long> {}

  Listener (Notification concern):
  @EventListener
  void onOrderPlaced(OrderPlacedEvent event) {
      emailService.sendConfirmation(event.getOrder());
  }

================================================================
FORMS OF SEPARATION OF CONCERNS
================================================================

  HORIZONTAL (LAYERED) SEPARATION:
  Presentation → Business Logic → Data Access → Infrastructure
  Classic MVC / Spring Layered Architecture

  VERTICAL (FEATURE/SLICE) SEPARATION:
  Orders | Customers | Inventory | Payments
  Each vertical handles its own layers
  Also called "Package by Feature" vs "Package by Type"

  CROSS-CUTTING CONCERNS:
  Logging, security, transactions — they cut across all layers.
  Managed via AOP (Aspect-Oriented Programming): @Aspect, @Around.
  Spring handles: @Transactional, @PreAuthorize, @Cacheable

================================================================
SOC AND ASPECT-ORIENTED PROGRAMMING
================================================================

  Cross-cutting concerns violate SoC if placed inline.
  AOP separates them declaratively:

  WITHOUT AOP (mixed concerns):
  void createUser(User u) {
      logger.info("Creating user");          // logging
      securityCheck();                        // security
      transactionBegin();                     // transaction
      repo.save(u);                           // business
      transactionCommit();
      logger.info("User created");
  }

  WITH AOP:
  @Service
  class UserService {
      void createUser(User u) { repo.save(u); }  // ONLY business
  }

  @Aspect — handles logging, @Transactional — handles tx, @PreAuthorize — security

================================================================
SOC IN MICROSERVICES
================================================================

  Microservices take SoC to the service level:
  - Orders service handles only order concerns
  - Payment service handles only payment concerns
  - Notification service handles only notification concerns

  Each service can be:
  - Deployed independently
  - Scaled independently
  - Changed independently

  SoC violation at service level = distributed monolith (shared DB,
  shared models, services that need each other for every operation).

================================================================
INTERVIEW Q&A
================================================================

  Q: What is Separation of Concerns?
  A: The principle that each module/class/layer should address one
     distinct concern. Different concerns (business logic, persistence,
     presentation) should be separated into different modules.

  Q: How does SoC relate to SRP?
  A: SRP is SoC at the class level. SoC is more general — it applies at
     any level: method, class, layer, service, system.

  Q: How does Spring implement SoC?
  A: Layered architecture (@Controller/@Service/@Repository separates
     concerns). AOP (@Transactional/@Cacheable/@PreAuthorize) separates
     cross-cutting concerns. Event publishing separates reaction from action.

  Q: What are cross-cutting concerns?
  A: Concerns that span multiple layers and modules: logging, security,
     transactions, caching, error handling. Handled by AOP in Spring.
