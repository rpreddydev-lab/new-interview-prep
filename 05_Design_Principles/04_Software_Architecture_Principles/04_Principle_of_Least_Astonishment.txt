================================================================
  PRINCIPLE OF LEAST ASTONISHMENT (POLA)
================================================================

  Also called: Principle of Least Surprise

  "A component of a system should behave in a way that most users
  expect it to behave; the behavior should not astonish or surprise users."

  Applies to: API design, method naming, class behavior, UI design.
  Goal: Code that does what developers expect it to do.

================================================================
WHY IT MATTERS
================================================================

  When code behaves unexpectedly:
  - Bugs introduced by incorrect mental models
  - Defensive coding and paranoia everywhere
  - Teams are afraid to use each other's APIs
  - Documentation must explain every surprise

  When code obeys POLA:
  - Developers read the name, write the call, it works
  - API is self-documenting
  - Trust between team members
  - Faster onboarding

================================================================
COMMON VIOLATIONS
================================================================

  1. METHOD NAME LIES ABOUT WHAT IT DOES

     boolean isEmpty() {
         items.clear();   // ← SURPRISE — why is a query mutating?
         return true;
     }

     Fix: isEmpty() must only check, never mutate.
     Command/Query Separation (CQS) prevents this class of surprise.

  2. UNEXPECTED SIDE EFFECTS

     double getTotal() {
         this.lastAccessed = Instant.now();   // hidden side effect
         return total;
     }

     Callers don't expect a getter to update state.

  3. RETURNING NULL FROM A COLLECTION METHOD

     List<Order> findByCustomer(long id) {
         if (!exists(id)) return null;   // SURPRISE — should return empty list
     }

     Contract surprise: callers expect a List, not a possible null.
     Fix: return Collections.emptyList()

  4. THROWING UNCHECKED EXCEPTIONS FOR NORMAL FLOW

     Order getOrder(long id) throws RuntimeException {
         if (!found) throw new RuntimeException("Not found");
     }

     Expected: Optional<Order> or a specific checked/typed exception.

  5. INCONSISTENT NAMING

     class OrderService {
         Order fetchOrder(long id) {}
         Order retrieveCustomer(long customerId) {}   // SURPRISE — retrieves Customer from OrderService?
         void commitTransaction() {}                  // SURPRISE — transaction in service?
     }

  6. UNEXPECTED MUTATION OF PARAMETERS

     void process(List<Order> orders) {
         orders.sort(...);   // SURPRISE — caller's list is now sorted
     }

     Fix: sort a copy, or document explicitly that the list is mutated.
     Better: return the sorted list as a new collection.

  7. BOOLEAN PARAMETERS THAT REVERSE BEHAVIOR

     void render(boolean premium) {}
     render(true);   // What does true mean? SURPRISE.

     Fix: renderPremium() and renderStandard() — no flag.

================================================================
GOOD API DESIGN OBEYS POLA
================================================================

  Principles that directly support POLA:

  CQS (Command Query Separation):
  - Queries (return value, no side effects) → names like get/find/is/has
  - Commands (mutate, return void or self) → names like save/add/update/delete
  Never mix — getters should never mutate.

  Consistent naming across the codebase:
  - find vs get: Optional<T> findById() vs T getById() (may throw)
  - all List-returning methods return empty list, never null

  Predictable return types:
  - findById() → Optional<T>, not T (nullable)
  - findAll() → List<T>, not null
  - save() → saved entity (with id), not void

================================================================
JAVA STDLIB EXAMPLES — FOLLOWING POLA
================================================================

  Collections.sort(list)         → modifies in place, returns void ✅
  list.stream().sorted()         → returns new stream, doesn't mutate ✅
  String.toUpperCase()           → returns NEW string (strings are immutable) ✅
  Iterator.remove()              → clearly named for mutation ✅
  Optional.map()                 → transforms safely if present ✅

  Java historical violations:
  Date.getYear() returns year - 1900   ← surprise (use LocalDate now)
  java.util.Date is mutable             ← surprise (LocalDate is immutable)

================================================================
POLA IN SPRING / FRAMEWORK APIs
================================================================

  Spring generally follows POLA:
  @Transactional: applies to whole method, commits at end → expected
  @Cacheable: first call computes, subsequent calls return cached → expected
  @EventListener: method called on event → expected

  Potential Spring surprises to know:
  - @Transactional on private methods = silently ignored (AOP proxy)
  - @Autowired with prototype scope in singleton = same instance returned
  - @Cacheable within same class = not applied (self-invocation bypass)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the Principle of Least Astonishment?
  A: Code should behave the way developers expect. Method names should
     match behavior, side effects should be explicit, return types should
     be consistent. Reduces bugs from incorrect mental models.

  Q: How does CQS relate to POLA?
  A: CQS (Command Query Separation) says methods either return a value
     or change state, never both. This directly supports POLA — developers
     know a query won't change anything, a command won't return anything
     meaningful.

  Q: Give an example of a POLA violation.
  A: A method called isEmpty() that also clears the collection.
     Or findByCustomer() that returns null instead of an empty list.
     Or a setter with a hidden side effect (like sending an email).

  Q: How do you apply POLA when designing APIs?
  A: Consistent naming conventions, CQS, return Optional instead of null
     for absent values, return empty collections instead of null, avoid
     boolean flag parameters, document any non-obvious behavior.
