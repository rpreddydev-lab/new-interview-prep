================================================================
  HIGH COHESION / LOW COUPLING
================================================================

  These two principles work as a pair and are among the most
  fundamental in software architecture.

  COHESION: How closely related the elements within a module are.
  COUPLING: How much one module depends on another.

  Goal: HIGH cohesion WITHIN modules, LOW coupling BETWEEN modules.

================================================================
COHESION EXPLAINED
================================================================

  High cohesion = the class/module does one thing and everything
  in it contributes to that one thing.

  SPECTRUM (worst to best):

  Coincidental     Parts grouped arbitrarily (Utils class, Helpers.java)
  Logical          Parts grouped by type (all input handlers together)
  Temporal         Parts executed at the same time (initialization bundle)
  Procedural       Parts follow a sequence (validate → process → save)
  Communicational  Parts operate on same data
  Sequential       Output of one is input of next (pipeline)
  Functional       All parts essential to one well-defined task   ← BEST

  Java signal of low cohesion:
  - Class named XxxManager, XxxHelper, XxxUtils
  - Class has methods that are completely unrelated to each other
  - Field only used by 2 out of 20 methods

================================================================
COUPLING EXPLAINED
================================================================

  Low coupling = modules depend on each other minimally and through
  stable interfaces, not concrete implementations.

  TYPES OF COUPLING (worst to best):

  Content Coupling     Module A directly accesses internals of B
  Common Coupling      Two modules share global state
  Control Coupling     A tells B what to do via flag argument
  Stamp Coupling       Passing whole struct when only one field needed
  Data Coupling        Passing only the data needed (method params)   ← GOOD
  Message Coupling     Communicate via events/messages               ← BEST

================================================================
EXAMPLES
================================================================

  HIGH COUPLING (BAD):
  class OrderService {
      private MySqlOrderRepository repo = new MySqlOrderRepository();  // concrete
      private SmtpEmailSender emailSender = new SmtpEmailSender();      // concrete
      // If either changes, OrderService must change
  }

  LOW COUPLING (GOOD):
  class OrderService {
      private final OrderRepository repo;        // interface
      private final NotificationService notify;  // interface
      // Constructor injection — depends on abstractions
  }

  ---

  LOW COHESION (BAD):
  class UserUtils {
      static String hashPassword(String pw) { ... }
      static void sendWelcomeEmail(User u) { ... }
      static Order buildDefaultOrder(User u) { ... }
      static String formatAddress(Address a) { ... }
  }
  // Has nothing to do with itself — random collection of utilities

  HIGH COHESION (GOOD):
  class PasswordHasher { String hash(String pw); boolean verify(String pw, String hash); }
  class UserEmailService { void sendWelcome(User u); void sendReset(User u); }
  class AddressFormatter { String format(Address a); }

================================================================
DEPENDENCY METRICS
================================================================

  Robert C. Martin defined metrics for packages:

  Ca (Afferent Coupling):  Number of classes OUTSIDE this package
                            that depend ON classes inside. How responsible
                            this package is to others.

  Ce (Efferent Coupling):  Number of classes INSIDE this package
                            that depend ON classes outside. How dependent
                            this package is on others.

  Instability (I) = Ce / (Ca + Ce)
  - I = 0: maximally stable (depended upon, depends on nothing)
  - I = 1: maximally unstable (depends on everything, nothing depends on it)

  Abstractness (A) = (abstract classes + interfaces) / total types

  Main Sequence: A + I ≈ 1
  - Stable zone: high A + low I (abstract and stable, like core interfaces)
  - Unstable zone: low A + high I (concrete and unstable, like implementations)

================================================================
PRACTICAL PATTERNS FOR LOW COUPLING
================================================================

  1. Program to interfaces, not implementations (DIP)
  2. Inject dependencies (constructor injection)
  3. Use events for decoupled notification (Observer)
  4. Use DTOs to avoid coupling layers through JPA entities
  5. Package by feature — all code for "orders" together, not
     all repositories in one package, all services in another

================================================================
HIGH COHESION vs LOW COUPLING — TENSION
================================================================

  Increasing cohesion can increase coupling:
  If you make Order responsible for calculating tax, you may need to
  couple it to a TaxRepository.

  Resolution: Cohesion guides what belongs together logically.
              DIP + injection keeps coupling low even when there's dependency.

================================================================
COHESION/COUPLING IN MICROSERVICES
================================================================

  Service level:
  - High cohesion: each service owns its data, logic, and APIs for one domain
  - Low coupling: services communicate via APIs (REST/events), not shared DB

  Anti-pattern — Distributed Monolith:
  Services are physically separate but tightly coupled through:
  - Shared database tables
  - Synchronous call chains (A calls B calls C — all must be up)
  - Shared domain model library

================================================================
INTERVIEW Q&A
================================================================

  Q: What is cohesion and coupling?
  A: Cohesion = how related the elements inside a module are (want HIGH).
     Coupling = how dependent modules are on each other (want LOW).

  Q: Why is high cohesion desirable?
  A: Related things are in one place — easier to find, understand, modify,
     test, and reuse. Low cohesion means scattered logic, hard to change
     without touching many places.

  Q: Why is low coupling desirable?
  A: You can change one module without affecting others. Enables independent
     development, testing, and deployment. Reduces cascade failures.

  Q: How do you achieve low coupling in Java/Spring?
  A: Interface-based design, dependency injection, event-driven communication,
     DTOs between layers, avoiding sharing JPA entities across service boundaries.

  Q: Can you have high cohesion AND low coupling?
  A: Yes, and that's the goal. A well-designed module/class is internally
     cohesive (single responsibility) and depends on others only through
     stable interfaces (low coupling).
