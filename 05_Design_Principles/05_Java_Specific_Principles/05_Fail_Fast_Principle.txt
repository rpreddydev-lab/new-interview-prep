================================================================
  FAIL FAST PRINCIPLE
================================================================

  "Fail fast" means detecting and reporting errors as early as possible,
  as close to the source as possible, rather than letting invalid state
  propagate through the system and produce a confusing error later.

  Coined in systems design; applied at code level as a defensive idiom.

================================================================
THE PROBLEM WITH FAILING SLOW
================================================================

  Slow fail (bad):
  void processOrder(Order order) {
      service.save(order);              // persists
      warehouse.reserve(order);        // triggers inventory
      payment.charge(order);           // charges card
      email.sendConfirmation(order);   // sends email
      // --- 4 operations later ---
      if (order.getCustomerId() == null) throw new RuntimeException("No customer");
      // ^ Exception thrown here, but damage already done
  }

  Problems:
  - Order partially saved
  - Inventory reserved
  - Payment charged
  - Email sent
  - Then exception thrown → corrupt state, refund needed

  Fast fail (good):
  void processOrder(Order order) {
      Objects.requireNonNull(order, "order must not be null");
      Objects.requireNonNull(order.getCustomerId(), "customerId must not be null");
      if (order.getItems().isEmpty()) throw new IllegalArgumentException("Order has no items");
      // Only AFTER validation do we proceed
      service.save(order);
      warehouse.reserve(order);
      payment.charge(order);
      email.sendConfirmation(order);
  }

================================================================
MECHANISMS FOR FAIL FAST IN JAVA
================================================================

  1. OBJECTS.REQUIRENONNULL
     Objects.requireNonNull(value, "fieldName must not be null");
     → Throws NullPointerException with message immediately if null.
     Use in constructors and method entry points.

     public Order(String customerId, List<Item> items) {
         this.customerId = Objects.requireNonNull(customerId, "customerId");
         this.items = List.copyOf(Objects.requireNonNull(items, "items"));
     }

  2. PRECONDITION CHECKS (Guava / manual)
     if (amount < 0) throw new IllegalArgumentException("Amount must be non-negative: " + amount);
     if (index >= size) throw new IndexOutOfBoundsException("Index: " + index + ", Size: " + size);
     // Include the bad value in the message — critical for debugging

     Guava: Preconditions.checkArgument(amount >= 0, "Amount must be non-negative: %s", amount);
     Guava: Preconditions.checkState(!items.isEmpty(), "Cannot checkout with empty cart");

  3. BEAN VALIDATION (JAKARTA / JAVAX)
     @NotNull @Valid on controller inputs:

     @PostMapping("/orders")
     ResponseEntity<OrderResponse> place(@Valid @RequestBody OrderRequest request) { ... }

     Domain object:
     public record OrderRequest(
         @NotNull String customerId,
         @NotBlank String email,
         @NotEmpty List<@Valid ItemDto> items
     ) {}

     MethodArgumentNotValidException thrown automatically before method is called.
     ConstraintViolationException on @Validated @Service methods.

  4. ASSERT (FOR DEVELOPMENT / INTERNAL INVARIANTS)
     assert invariant : "description of what went wrong";
     Note: assertions are DISABLED by default at runtime (-ea JVM flag to enable).
     Use for: internal consistency checks, post-conditions, debugging.
     Do NOT use assertions for: public API input validation (may be disabled).

  5. OPTIONAL.ORNULL / EMPTY CHECK
     Optional.ofNullable(user)
         .orElseThrow(() -> new UserNotFoundException("User not found: " + userId));

================================================================
FAIL FAST IN CONSTRUCTORS — IMMUTABLE OBJECTS
================================================================

  Immutable objects MUST fail fast in constructor because there's no other
  chance to catch invalid state:

  record Email(String value) {
      Email {
          Objects.requireNonNull(value, "Email value must not be null");
          if (!value.contains("@")) throw new IllegalArgumentException("Invalid email: " + value);
          value = value.toLowerCase();
      }
  }

  Now any attempt to create an invalid Email fails immediately.
  The system can never be in a state with an invalid Email object.

================================================================
FAIL FAST IN SYSTEMS DESIGN
================================================================

  Circuit Breaker: stops calling a failing service immediately rather
  than letting calls queue up and timeout → fail fast at service boundary.

  Startup validation: Spring's @PostConstruct or ApplicationRunner
  validates required configuration at startup:

  @PostConstruct
  void validateConfig() {
      Objects.requireNonNull(apiKey, "API_KEY environment variable not set");
  }

  → The service refuses to start rather than failing on the first request.

  Database connection pool: checked at startup, not on first query.

================================================================
FAIL FAST vs DEFENSIVE PROGRAMMING
================================================================

  Both are about handling invalid inputs, but:

  Fail Fast: Throw immediately, loudly, with context.
  Defensive: Try to continue despite invalid input (substitute defaults, skip).

  Rule of thumb:
  - If the caller passed invalid data, FAIL FAST (their bug, they should know)
  - If external data (user input, API response) is invalid, VALIDATE + HANDLE (expected)
  - If internal invariant is broken, FAIL FAST (your bug, you should know)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the fail fast principle?
  A: Detect and report errors as early and as close to the source as possible.
     Validate inputs at method/constructor entry. Don't let invalid state
     propagate deep into the call stack before the error surfaces.

  Q: How do you implement fail fast in Java?
  A: Objects.requireNonNull, IllegalArgumentException checks, Bean Validation
     (@Valid @NotNull), Guava Preconditions, constructor validation in
     immutable objects/records.

  Q: Why should you include the bad value in exception messages?
  A: Makes debugging much faster. "Amount must be non-negative: -100" tells
     exactly what happened. "Invalid input" requires reproducing the issue.

  Q: What's the difference between fail fast and defensive programming?
  A: Fail fast: throw immediately for programmer errors (invalid args, broken invariants).
     Defensive: handle gracefully for external errors (user input, third-party APIs).
     Both have their place; the question is whose fault is the error.

  Q: When should you NOT fail fast?
  A: When processing external input (UI forms, API requests) — validate and
     return user-friendly errors rather than throwing raw exceptions.
     Use Bean Validation + ControllerAdvice to map validation failures to 400 responses.
