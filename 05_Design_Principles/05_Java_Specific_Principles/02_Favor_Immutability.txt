================================================================
  FAVOR IMMUTABILITY
================================================================

  "Classes should be immutable unless there's a very good reason
  to make them mutable." — Joshua Bloch, Effective Java Item 17

  An immutable object is one whose state cannot be changed after
  construction.

================================================================
WHY IMMUTABILITY IS POWERFUL
================================================================

  1. THREAD SAFE BY DEFAULT
     Immutable objects can be shared freely between threads without
     synchronization. No data races. No need for synchronized/volatile/locks.

  2. SIMPLER REASONING
     Object state never changes → you always know what it is.
     No defensive copying of method arguments. No "did something mutate?"

  3. SAFE TO SHARE AND CACHE
     Pass to any method without worrying about side effects.
     Cache freely (the cached value can't become stale due to mutation).

  4. EXCELLENT MAP KEYS AND SET ELEMENTS
     Mutable objects as map keys break the contract if they're modified after
     insertion (hashCode changes → key "lost" in the map).
     Immutable objects are always safe as map keys.

  5. NO NEED FOR DEFENSIVE COPIES
     public String getName() { return name; }  ← safe, String is immutable
     public Date getDate() { return new Date(date.getTime()); }  ← must copy (Date is mutable)

================================================================
HOW TO CREATE AN IMMUTABLE CLASS
================================================================

  RULES:
  1. Declare class final (no subclass can break immutability)
  2. All fields private and final
  3. No setter methods
  4. Defensive copies for mutable fields in constructor (take copy of input)
  5. Defensive copies in getters for mutable fields (return copy, not reference)
  6. "With" methods return new instances instead of mutating

  EXAMPLE:
  public final class Money {
      private final long amount;        // final — can't change
      private final Currency currency;  // Currency is immutable

      public Money(long amount, Currency currency) {
          this.amount = Objects.requireNonNull(amount);
          this.currency = Objects.requireNonNull(currency);
      }

      public Money add(Money other) {
          if (!currency.equals(other.currency)) throw new IllegalArgumentException();
          return new Money(this.amount + other.amount, this.currency);  // NEW instance
      }

      public long getAmount() { return amount; }           // safe — primitive
      public Currency getCurrency() { return currency; }   // safe — Currency immutable
  }

  Usage:
  Money price = new Money(100, Currency.USD);
  Money discounted = price.add(new Money(-10, Currency.USD));
  // price is still 100; discounted is 90

================================================================
JAVA RECORD — BUILT-IN IMMUTABILITY
================================================================

  Java 16+ records are immutable value objects by default:

  record Point(double x, double y) {}          // auto: final, private, accessors, equals, hashCode, toString

  record Money(long amount, Currency currency) {
      Money {   // compact constructor for validation
          Objects.requireNonNull(currency);
          if (amount < 0) throw new IllegalArgumentException("Negative money");
      }

      Money add(Money other) {
          if (!currency.equals(other.currency)) throw new IllegalArgumentException();
          return new Money(amount + other.amount, currency);
      }
  }

  Records: ideal for DTOs, value objects, events, and return types.

================================================================
DEFENSIVE COPY PATTERN (MUTABLE FIELDS)
================================================================

  If the class must hold a mutable object (like a List or Date):

  public final class OrderSnapshot {
      private final List<Item> items;

      public OrderSnapshot(List<Item> items) {
          this.items = List.copyOf(items);   // defensive copy — isolate from caller mutation
      }

      public List<Item> getItems() {
          return Collections.unmodifiableList(items);   // defensive copy on read
      }
  }

  Java 9+ List.copyOf, Map.copyOf, Set.copyOf create unmodifiable copies.
  Java 10+ List.of, Map.of create truly unmodifiable collections.

================================================================
IMMUTABILITY IN JAVA STANDARD LIBRARY
================================================================

  Immutable:
  String, Integer, Long, Double, Boolean — all wrapper types
  BigDecimal, BigInteger
  LocalDate, LocalTime, LocalDateTime, ZonedDateTime
  URI, URL
  UUID
  Optional<T>

  Mutable (use with care):
  Date, Calendar — replaced by java.time.*
  StringBuilder / StringBuffer
  ArrayList, HashMap, HashSet — use List.of(), Map.of() for immutable

================================================================
STRINGS ARE IMMUTABLE — IMPORTANT IMPLICATIONS
================================================================

  String s = "hello";
  s.toUpperCase();   // SURPRISE: does NOT change s
  s = s.toUpperCase();   // creates new String, reassigns reference

  String interning and the String pool works because Strings are immutable.
  String concatenation in loops is expensive because each + creates a new object.
  Fix: StringBuilder for mutable string building.

================================================================
IMMUTABILITY IN CONCURRENT CODE
================================================================

  Mutable shared state = root cause of most concurrency bugs.

  If objects are immutable, they can be:
  - Published freely to any thread (no synchronization needed)
  - Cached in ConcurrentHashMap without defensive copies
  - Used in CompletableFuture pipelines safely
  - Passed to parallel streams without side effect concerns

================================================================
WHEN MUTABILITY IS ACCEPTABLE
================================================================

  - Performance-critical code where copying is too expensive
    (use local mutation, don't publish the mutable object)
  - Builder pattern: builder is mutable, product is immutable
  - JPA entities (ORM requires mutable state via setters)
  - Accumulators in complex algorithms (use locally, don't share)

================================================================
INTERVIEW Q&A
================================================================

  Q: Why should you favor immutability?
  A: Thread safety without synchronization, simpler reasoning,
     safe sharing and caching, safe use as map keys, no defensive
     copies needed.

  Q: How do you make a class immutable in Java?
  A: final class, final private fields, no setters, defensive copies
     in constructor for mutable inputs, defensive copies in getters
     for mutable fields, "with" methods return new instances.

  Q: What is a Java record and how does it help?
  A: Records (Java 16+) are immutable data carriers. Auto-generate
     equals, hashCode, toString, and accessor methods. Ideal for
     value objects, DTOs, and events.

  Q: Why is String immutable in Java?
  A: Thread safety, security (can't be changed after passing to a
     method), String pool optimization (safe to share cached instances),
     hashCode caching.

  Q: Can immutable objects still be misused?
  A: If an immutable object holds a reference to a mutable object
     (like Date or List), callers can mutate through that reference.
     Must use defensive copies for contained mutable state.
