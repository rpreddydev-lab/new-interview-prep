================================================================
  CHECKED vs UNCHECKED EXCEPTIONS IN JAVA
================================================================

  Java has two exception categories that represent different
  design philosophies about when callers must handle errors.

================================================================
THE EXCEPTION HIERARCHY
================================================================

  Throwable
  |
  +-- Error                        (JVM errors — OutOfMemoryError, StackOverflowError)
  |                                 DO NOT catch unless truly necessary
  |
  +-- Exception
      |
      +-- RuntimeException         → UNCHECKED
      |     NullPointerException
      |     IllegalArgumentException
      |     IllegalStateException
      |     IndexOutOfBoundsException
      |     UnsupportedOperationException
      |     ArithmeticException
      |     ClassCastException
      |
      +-- (other Exception subclasses) → CHECKED
            IOException
            SQLException
            ParseException
            CloneNotSupportedException

================================================================
CHECKED EXCEPTIONS
================================================================

  - Must be declared in method signature: throws IOException
  - Caller must either handle (try-catch) or re-declare (throws)
  - Compiler enforces this — won't compile otherwise

  Design intent: the exceptional condition is RECOVERABLE and
  the caller SHOULD handle it (e.g., file not found — maybe try a different path).

  Good use cases:
  - I/O operations: file not found, network failure
  - External API calls: service unavailable, parsing error
  - Business recoverable errors: InsufficientFundsException (caller can retry or notify user)

  Example:
  public String readConfig(Path path) throws IOException {
      return Files.readString(path);
  }

  Caller is forced to decide: catch the IOException or propagate it.

================================================================
UNCHECKED EXCEPTIONS (RUNTIME EXCEPTIONS)
================================================================

  - NOT required in signature
  - Caller is NOT required to handle
  - Compiler does NOT check

  Design intent: programming errors (bugs) that the caller CANNOT
  reasonably recover from (e.g., null pointer dereference = your bug).

  Good use cases:
  - Invalid arguments: IllegalArgumentException
  - Wrong state: IllegalStateException
  - Contract violation: NullPointerException (don't pass null)
  - Unsupported operations: UnsupportedOperationException

  Example:
  public Money(long amount, Currency currency) {
      if (amount < 0) throw new IllegalArgumentException("Negative amount: " + amount);
  }

  Caller is NOT forced to catch — it's their responsibility not to pass -1.

================================================================
JOSHUA BLOCH'S GUIDANCE (EFFECTIVE JAVA ITEM 70)
================================================================

  USE CHECKED WHEN:
  "The exceptional condition is reasonably expected, and the caller
  can take meaningful action to recover."

  FileNotFoundException: caller might try an alternate path
  InsufficientFundsException: caller might prompt for a different payment method

  USE UNCHECKED WHEN:
  "The exception is a programming error, or the caller cannot do
  anything useful to recover from it."

  NullPointerException: caller should not pass null (fix the bug)
  IllegalArgumentException: caller should not pass invalid arguments
  IndexOutOfBoundsException: caller should check bounds first

  KEY TEST: "Can the caller reasonably recover from this at runtime?"
  YES → Checked   |   NO → Unchecked

================================================================
THE CHECKED EXCEPTION CONTROVERSY
================================================================

  Checked exceptions were a Java-original idea — no other major language
  adopted them (C#, Kotlin, Scala use only unchecked).

  Arguments AGAINST checked exceptions:
  - They pollute API signatures (everything declares throws Exception)
  - Often lead to catch-and-ignore: catch(Exception e) {} // silence
  - Impossible to use with functional interfaces (Predicate, Function, etc.)
    which don't declare checked exceptions
  - Can be over-used for conditions that aren't truly recoverable

  Modern Java trend:
  - Spring wraps all SQLExceptions in unchecked DataAccessException
  - JPA throws unchecked exceptions
  - Many new Java APIs prefer unchecked + Optional

================================================================
CHECKED EXCEPTIONS WITH LAMBDA (THE PROBLEM)
================================================================

  Checked exceptions and lambdas don't mix well:

  // Won't compile — Files.readString throws IOException (checked)
  list.stream()
      .map(path -> Files.readString(path))   // COMPILE ERROR
      .collect(toList());

  Solutions:
  1. Wrap in a try-catch inside the lambda (ugly):
     .map(path -> { try { return Files.readString(path); }
                    catch (IOException e) { throw new RuntimeException(e); } })

  2. Extract to a helper that wraps checked in unchecked:
     static <T, R> Function<T, R> unchecked(ThrowingFunction<T, R> f) {
         return t -> { try { return f.apply(t); } catch (Exception e) { throw new RuntimeException(e); } };
     }
     .map(unchecked(Files::readString))

  3. Use Vavr's Try monad or similar functional error handling.

================================================================
EXCEPTION DESIGN BEST PRACTICES
================================================================

  1. INCLUDE CONTEXT IN EXCEPTION MESSAGE
     throw new IllegalArgumentException("Invalid discount rate: " + rate + " (must be 0.0-1.0)");
     // Include: what was wrong, the bad value, what was expected

  2. PRESERVE THE CAUSE WHEN WRAPPING
     catch (SQLException e) {
         throw new DataAccessException("Failed to load order " + orderId, e);  // pass e as cause
     }
     // Without e, the stack trace is lost — very hard to debug

  3. DON'T SWALLOW EXCEPTIONS
     catch (Exception e) {}              // TERRIBLE — exception silently lost
     catch (Exception e) { log.error("..."); }  // at minimum, log it
     catch (Exception e) { throw new RuntimeException(e); }  // or rethrow

  4. DON'T USE EXCEPTIONS FOR FLOW CONTROL
     // BAD — exception as a control signal
     try { Integer.parseInt(s); return true; } catch (NumberFormatException e) { return false; }
     // GOOD
     return s.chars().allMatch(Character::isDigit);

  5. PREFER SPECIFIC EXCEPTIONS
     throw new OrderNotFoundException(orderId);  // not throw new RuntimeException("not found")

  6. DOCUMENT UNCHECKED EXCEPTIONS WITH JAVADOC
     /**
      * @throws IllegalArgumentException if amount is negative
      * @throws NullPointerException if currency is null
      */

================================================================
CUSTOM EXCEPTION HIERARCHY
================================================================

  Good domain-specific exceptions:

  // Base: unchecked, extends RuntimeException
  public class AppException extends RuntimeException {
      public AppException(String message) { super(message); }
      public AppException(String message, Throwable cause) { super(message, cause); }
  }

  // Domain-specific subtypes
  public class OrderNotFoundException extends AppException {
      public OrderNotFoundException(long orderId) {
          super("Order not found: " + orderId);
      }
  }

  public class InsufficientInventoryException extends AppException {
      private final long itemId;
      private final int requested;
      private final int available;

      public InsufficientInventoryException(long itemId, int requested, int available) {
          super(String.format("Insufficient inventory for item %d: requested=%d, available=%d",
                              itemId, requested, available));
          this.itemId = itemId; this.requested = requested; this.available = available;
      }
  }

================================================================
SPRING EXCEPTION HANDLING
================================================================

  @ControllerAdvice + @ExceptionHandler maps domain exceptions to HTTP:

  @ControllerAdvice
  class GlobalExceptionHandler {
      @ExceptionHandler(OrderNotFoundException.class)
      @ResponseStatus(HttpStatus.NOT_FOUND)
      ErrorResponse handle(OrderNotFoundException ex) {
          return new ErrorResponse(ex.getMessage());
      }

      @ExceptionHandler(MethodArgumentNotValidException.class)
      @ResponseStatus(HttpStatus.BAD_REQUEST)
      ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
          List<String> errors = ex.getBindingResult().getFieldErrors()
              .stream().map(e -> e.getField() + ": " + e.getDefaultMessage())
              .toList();
          return new ErrorResponse("Validation failed", errors);
      }
  }

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between checked and unchecked exceptions?
  A: Checked (Exception subclasses except RuntimeException): compiler
     enforces handling; for recoverable external conditions.
     Unchecked (RuntimeException subclasses): optional handling;
     for programming errors the caller can't recover from.

  Q: When should you use a checked exception?
  A: When the caller can and should take meaningful action to recover at runtime:
     file not found (try alternate path), network failure (retry), API error (fallback).

  Q: When should you use an unchecked exception?
  A: When it's a programming error: null passed, invalid argument, wrong state.
     The fix is to fix the calling code, not wrap in try-catch.

  Q: Why does Spring use unchecked exceptions?
  A: Checked exceptions don't work well with lambda/functional APIs, pollute
     method signatures, and most DB errors aren't recoverable anyway.
     Spring wraps SQLException in unchecked DataAccessException hierarchy.

  Q: What's wrong with catch(Exception e) {}?
  A: Silently swallowing exceptions hides bugs, makes debugging impossible,
     and can leave the system in corrupt state. Always at minimum log the exception.
