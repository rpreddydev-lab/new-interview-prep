================================================================
  PROGRAM TO INTERFACE, NOT IMPLEMENTATION
================================================================

  "Program to an interface, not an implementation."
  — Gang of Four, "Design Patterns" (1994)

  Core idea: Declare variables, parameters, and return types using
  the most abstract type that still satisfies your needs.

================================================================
WHY
================================================================

  When you declare a concrete type, your code is:
  - Coupled to that specific implementation
  - Hard to swap for testing (can't inject a mock)
  - Hard to change later (if you move from ArrayList to LinkedList,
    you must find every usage)

  When you declare an interface:
  - The implementation can be swapped without changing the caller
  - Tests can inject fakes/mocks
  - Future flexibility is preserved

================================================================
EXAMPLES — COLLECTION TYPES
================================================================

  BAD (coupled to implementation):
  ArrayList<String> names = new ArrayList<>();
  HashMap<String, User> cache = new HashMap<>();
  LinkedHashSet<Order> orders = new LinkedHashSet<>();

  GOOD (programmed to interface):
  List<String> names = new ArrayList<>();
  Map<String, User> cache = new HashMap<>();
  Set<Order> orders = new LinkedHashSet<>();

  Now if you need to switch ArrayList → CopyOnWriteArrayList for
  thread safety, you only change the right-hand side:
  List<String> names = new CopyOnWriteArrayList<>();
  The rest of the code doesn't notice.

================================================================
EXAMPLES — SERVICE / REPOSITORY LAYER
================================================================

  BAD — Controller coupled to concrete:
  class OrderController {
      private MySqlOrderRepository repo = new MySqlOrderRepository();
      // Can't test without MySQL; can't swap to Postgres later
  }

  GOOD — Controller coupled to interface:
  class OrderController {
      private final OrderRepository repo;  // interface
      OrderController(OrderRepository repo) { this.repo = repo; }
  }

  Now in tests:
  OrderController ctrl = new OrderController(new InMemoryOrderRepository());

  In production Spring:
  @Service class JpaOrderRepository implements OrderRepository { ... }
  // Spring injects automatically via @Autowired

================================================================
WHERE TO USE THE PRINCIPLE
================================================================

  1. LOCAL VARIABLES:
     List<Item> items = new ArrayList<>();  ✅

  2. METHOD PARAMETERS:
     void process(Collection<Item> items)   ✅  (accepts any Collection)
     void process(ArrayList<Item> items)    ← too specific

  3. METHOD RETURN TYPES:
     public List<Order> getOrders()         ✅  (caller doesn't need to know ArrayList)
     public ArrayList<Order> getOrders()    ← leaks implementation

  4. FIELDS:
     private final Map<String, User> cache;  ✅

  5. CONSTRUCTOR/METHOD INJECTION:
     constructor receives interface, not concrete type

================================================================
HOW SPECIFIC TO BE — CHOOSING THE RIGHT INTERFACE
================================================================

  Choose the NARROWEST interface that satisfies your needs:

  If you only need to iterate: Iterable<T>
  If you need size and containment: Collection<T>
  If you need indexed access: List<T>
  If you need ordering by value: SortedSet<T> / NavigableSet<T>
  If you need key-value: Map<K,V>

  Don't always default to List when Iterable would do.
  Narrower interface = fewer constraints on callers, more flexibility.

================================================================
INTERFACE vs ABSTRACT CLASS
================================================================

  "Program to interface" usually means Java interface (not abstract class).
  But the principle extends to abstract types generally.

  Use interface when:
  - You want to define a contract without any implementation
  - Multiple inheritance is needed (a class can implement many interfaces)
  - You want the most flexible decoupling

  Use abstract class when:
  - You have shared state/implementation (template method needs it)
  - You want to force subclasses to call super (lifecycle hooks)
  - Java 8+ default methods blur this distinction somewhat

================================================================
JAVA 8+ — INTERFACE DEFAULT METHODS
================================================================

  Interfaces can now have default (concrete) methods:
  interface Validator<T> {
      boolean validate(T value);

      default Validator<T> and(Validator<T> other) {
          return value -> this.validate(value) && other.validate(value);
      }
  }

  This allows composable interfaces without abstract base classes.
  Programming to the interface still applies.

================================================================
INTERVIEW Q&A
================================================================

  Q: What does "program to interface not implementation" mean?
  A: Declare variables, parameters, and return types as interfaces
     rather than concrete classes. Enables dependency injection,
     easier testing, and future flexibility to swap implementations.

  Q: Should you always use the most abstract type?
  A: Use the narrowest interface that satisfies your needs. If you
     only need to iterate, use Iterable. If you need indexed access,
     use List. Don't over-abstract unnecessarily.

  Q: How does this relate to DIP?
  A: DIP says high-level modules should depend on abstractions.
     "Program to interfaces" is the implementation technique —
     declare types as interfaces so DI can inject any implementation.

  Q: What if you need ArrayList-specific methods?
  A: Then use ArrayList explicitly. The principle says don't use
     concrete types unless you specifically need their capabilities.
     If you need RandomAccess behavior, declare ArrayList or
     List (which allows you to check RandomAccess at runtime).
