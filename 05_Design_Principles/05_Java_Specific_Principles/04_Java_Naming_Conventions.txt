================================================================
  JAVA NAMING CONVENTIONS
================================================================

  Java naming conventions are universally followed.
  Breaking them signals inexperience to interviewers.
  The JDK, Spring, and every major framework follows these exactly.

================================================================
THE RULES AT A GLANCE
================================================================

  Element            Convention         Example
  -----------------  -----------------  ---------------------------------
  Package            all lowercase      com.example.orderservice
  Class              PascalCase         OrderService, HttpRequest
  Interface          PascalCase         Comparable, OrderRepository
  Enum               PascalCase         OrderStatus, HttpMethod
  Enum constant      ALL_CAPS           OrderStatus.PENDING
  Method             camelCase          calculateTotal, findByEmail
  Variable           camelCase          customerName, totalAmount
  Constant (static final)  ALL_CAPS    MAX_RETRY_COUNT, DEFAULT_TIMEOUT
  Generic type param  single uppercase  T, E, K, V, R, N
  Test method        camelCase + underscores ok  givenOrder_whenShipped_thenCompleted

================================================================
PACKAGES — LOWERCASE, REVERSE DOMAIN
================================================================

  Format: com.companyname.projectname.feature

  com.example.orders
  com.example.orders.api
  com.example.orders.service
  com.example.orders.repository

  NO hyphens, NO underscores, NO uppercase.
  Hyphens are forbidden in Java identifiers anyway.

================================================================
CLASSES — PascalCase (UpperCamelCase)
================================================================

  Nouns or noun phrases:
  Order, OrderService, HttpRequest, CustomerProfile

  Avoid:
  - Abbreviations: OrdSvc (bad), OrderService (good)
  - Redundant suffixes unless meaningful (don't add Impl to every impl class)
  - Names ending in "Manager" or "Processor" (usually too vague)

  Exception patterns (meaningful and conventional):
  OrderService   — service class
  OrderController — web layer class
  OrderRepository — data access interface
  OrderMapper     — DTO conversion (MapStruct)
  OrderException  — domain exception
  OrderEvent      — domain event
  OrderDto        — data transfer object
  OrderRequest    — HTTP request model
  OrderResponse   — HTTP response model
  OrderFactory    — factory class
  AbstractOrder   — abstract base class

================================================================
INTERFACES — PascalCase, behavior-describing nouns or adjectives
================================================================

  Adjective form (capability):    Comparable, Serializable, Runnable, Closeable
  Noun form (role):               Repository, Service, Handler, Callback

  DO NOT prefix with I (no IOrderRepository):
  That's a C# convention; Java does not use it.

================================================================
METHODS — camelCase, verb or verb-phrase
================================================================

  Query methods (return something, no side effect):
  getOrder(id), findByEmail(email), isActive(), hasPermission()

  Command methods (mutate state):
  saveOrder(order), deleteById(id), updateStatus(status)

  Boolean methods: is, has, can, should prefix:
  isValid(), hasItems(), canShip(), shouldRetry()

  Factory-style static methods:
  of(items), from(json), valueOf(string), create(config)

  Conversion:
  toJson(), toDomain(), toDto()

================================================================
VARIABLES — camelCase
================================================================

  Descriptive, intention-revealing:
  customerName, orderTotal, maxRetryCount

  Avoid:
  - Single letters except loop indices (i, j, k acceptable in small loops)
  - Abbreviations: custNm (bad), customerName (good)
  - Prefixes: m_total (Android convention, not standard Java)
  - Hungarian notation: strName, intCount (not Java style)

  Boolean variables: same is/has/can conventions as methods:
  boolean isActive, boolean hasError, boolean canRetry

================================================================
CONSTANTS — static final, ALL_CAPS with underscores
================================================================

  public static final int MAX_RETRY_COUNT = 3;
  public static final String DEFAULT_ENCODING = "UTF-8";
  public static final Duration CONNECTION_TIMEOUT = Duration.ofSeconds(30);

  Enum constants follow the same ALL_CAPS convention:
  enum Status { PENDING, IN_PROGRESS, COMPLETED, FAILED }

================================================================
GENERIC TYPE PARAMETERS — single letter uppercase
================================================================

  Standard conventions:
  T — general type
  E — element (collections: List<E>)
  K — key (map: Map<K,V>)
  V — value (map: Map<K,V>)
  R — return type (Function<T,R>)
  N — number

  Two-letter names for multiple params:
  BiFunction<T1, T2, R>  (or more descriptive in your own generics)

================================================================
TEST METHOD NAMING
================================================================

  Common patterns:
  methodName_stateUnderTest_expectedBehavior()
  given_when_then()

  Examples:
  calculateTotal_withMemberDiscount_appliesTenPercent()
  givenEmptyCart_whenCheckout_thenThrowsException()
  placeOrder_withValidItems_returnsOrderId()

  JUnit 5 @DisplayName for human-readable test names:
  @Test
  @DisplayName("Order placement with empty cart throws IllegalStateException")
  void emptyCartTest() { ... }

================================================================
ANNOTATION NAMING
================================================================

  Annotations: PascalCase (same as classes)
  @Override, @Autowired, @Transactional, @NotNull, @Valid

  Custom annotations:
  @Audited, @RequireAdmin, @CacheEvict

================================================================
COMMON NAMING MISTAKES TO AVOID
================================================================

  1. Using "get" prefix on mutating methods
     getAndClear()  ← confusing — implies query but mutates
     Fix: popAll() or drainTo(list)

  2. Misleading boolean names
     boolean flag;           ← no meaning
     boolean processed;      ← ambiguous (is currently being processed, or was it?)
     boolean isProcessed;    ← clear: it has been processed

  3. Generic "data" and "info" suffixes
     UserData → UserProfile
     OrderInfo → OrderSummary

  4. Numbered names
     address1, address2  → use a List<Address>

  5. Abbreviations
     usr, ord, cust → user, order, customer

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the naming convention for constants in Java?
  A: public static final ALL_CAPS_WITH_UNDERSCORES.
     Enum constants follow the same convention.

  Q: Should Java interfaces be prefixed with I?
  A: No. That's a C# convention. Java interfaces are PascalCase without prefix.
     Java names them by capability (Comparable, Runnable) or role (Repository).

  Q: What naming convention should boolean variables and methods use?
  A: Prefix with is, has, can, or should:
     isActive, hasPermission, canDelete, shouldRetry.

  Q: How should test methods be named?
  A: methodName_stateUnderTest_expectedBehavior is common.
     Or JUnit 5 @DisplayName for human-readable descriptions.
