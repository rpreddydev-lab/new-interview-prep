================================================================
  PRINCIPLES vs PATTERNS vs PARADIGMS
================================================================

  Three levels of software design vocabulary.
  Interviewers often confuse candidates by mixing these terms.
  Know the distinctions cold.

----------------------------------------------------------------
PARADIGMS (HIGHEST LEVEL)
----------------------------------------------------------------

  A paradigm is a fundamental style of programming.
  It determines the basic model of computation.

  Paradigm          Model of Computation       Key Idea
  ----------------  -------------------------  ------------------------
  Procedural        Sequence of instructions   State + procedures
  Object-Oriented   Objects sending messages   Encapsulation + polymorphism
  Functional        Function composition       Immutability + pure functions
  Declarative       Describe WHAT, not HOW     SQL, HTML, LINQ
  Reactive          Data streams + propagation RxJava, Project Reactor

  Java is multi-paradigm:
    OOP: classes, interfaces, polymorphism
    Functional: lambdas, streams, Optional (Java 8+)
    Reactive: Project Reactor (Spring WebFlux), RxJava
    Declarative: JPA JPQL, Spring @Query

  Paradigms impose discipline by REMOVING freedom:
    Functional: no shared mutable state → remove assignment
    OOP: no direct function calls → message passing
    Procedural: no arbitrary jumps → no GOTO

----------------------------------------------------------------
PRINCIPLES (MIDDLE LEVEL)
----------------------------------------------------------------

  A principle is a guideline for making design decisions.
  Principles are language-agnostic and pattern-agnostic.
  They evaluate quality: "Is this design good?"

  Properties:
    - General (apply in many situations)
    - Abstract (not a concrete solution)
    - Evaluative ("does this design violate X?")
    - Discovered, not invented (emerge from observed good practices)

  Examples:
    SOLID, DRY, KISS, YAGNI, Separation of Concerns,
    High Cohesion / Low Coupling, Encapsulate What Varies,
    Depend on Abstractions, Fail Fast

  Principles MOTIVATE patterns:
    OCP (Open/Closed) → motivates Strategy, Decorator, Template Method
    DIP (Dependency Inversion) → motivates DI, Factory, Service Locator
    LSP → motivates Composite (components must be substitutable)
    ISP → motivates Facade (clients get only what they need)

----------------------------------------------------------------
PATTERNS (LOWEST / MOST CONCRETE LEVEL)
----------------------------------------------------------------

  A pattern is a named, reusable solution to a recurring problem
  in a specific context.

  Properties:
    - Concrete (can be implemented directly)
    - Named (shared vocabulary)
    - Contextual (applies when context matches)
    - Problem-Solution pairs

  Pattern Levels:
    Architectural: MVC, Microservices, Event Sourcing, CQRS, Hexagonal
    Design (GoF): Singleton, Factory, Strategy, Observer, Decorator...
    Idioms:       Null check guard clause, Builder, Fluent interface

  Patterns IMPLEMENT principles:
    Strategy pattern implements OCP (add algorithm without modifying context)
    Decorator implements OCP (add behavior without modifying component)
    Factory Method implements DIP (depend on abstraction, not concrete)
    Observer implements SRP (subject not responsible for reactions)

----------------------------------------------------------------
COMPARISON TABLE
----------------------------------------------------------------

                 Paradigm          Principle           Pattern
  Level:         Fundamental       Guideline           Solution
  Abstract:      Very high         High                Concrete
  Prescriptive:  What not to do    What to strive for  How to solve
  Language:      Shapes language   Language-agnostic   Language-influenced
  Scope:         Entire program    Any design decision Specific problem
  Examples:      OOP, Functional   SOLID, DRY, KISS    Strategy, Singleton

----------------------------------------------------------------
HOW THEY WORK TOGETHER IN PRACTICE
----------------------------------------------------------------

  Scenario: Adding a new payment method to a checkout system.

  Without any guidance:
    Add if-else to checkout code → rigidity → OCP violated.

  Principle kicks in (OCP):
    "Checkout should not change when new payment is added."

  Paradigm constrains (OOP):
    Use polymorphism — extract PaymentStrategy interface.

  Pattern provides the solution (Strategy):
    Create new PaymentGateway implementing PaymentStrategy.
    Inject into Checkout via DI.
    Checkout never knows which strategy is active.

  Principle → reminds you there's a problem.
  Paradigm → constrains the solution space.
  Pattern → gives you the proven implementation.

----------------------------------------------------------------
INTERVIEW FORMULATION
----------------------------------------------------------------

  Q: What's the difference between a pattern and a principle?
  A: "A principle is a guideline: 'code should have one reason to change'.
     A pattern is a concrete solution: 'use Strategy when you need to swap
     algorithms'. Principles MOTIVATE patterns. For example, OCP says 'closed
     to modification' and Strategy implements that by making algorithms
     replaceable without touching the context class."

  Q: Is MVC a pattern or a paradigm?
  A: "MVC is an architectural pattern — concrete, named, problem-specific.
     It's not a paradigm because it doesn't fundamentally constrain the
     programming model; you can implement MVC in OOP, functional, or reactive style."

  Q: Are SOLID principles object-oriented only?
  A: "SRP, ISP, DIP apply broadly. OCP and LSP are more OOP-specific (class
     hierarchies, subtypes). Functional programming often achieves SRP naturally
     (small pure functions) and avoids LSP (no inheritance). Spring WebFlux
     applies DIP functionally — RouterFunction depends on Handler abstraction."
