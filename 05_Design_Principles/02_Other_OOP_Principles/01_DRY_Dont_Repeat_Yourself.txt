================================================================
  DRY — DON'T REPEAT YOURSELF
================================================================

  Definition: "Every piece of knowledge must have a single,
               unambiguous, authoritative representation within a system."
               — Andy Hunt & Dave Thomas, The Pragmatic Programmer

  DRY is NOT just about code duplication.
  DRY is about KNOWLEDGE duplication.

  If the same business rule, algorithm, or data exists in two places,
  a change requires finding all copies. Miss one = bug.

----------------------------------------------------------------
TYPES OF DRY VIOLATIONS
----------------------------------------------------------------

  1. CODE DUPLICATION — copy-paste logic
  2. DATA DUPLICATION — same constant in multiple files
  3. LOGIC DUPLICATION — same algorithm expressed differently
  4. DOCUMENTATION DUPLICATION — comment repeats what code says

----------------------------------------------------------------
VIOLATION EXAMPLE: CODE DUPLICATION
----------------------------------------------------------------

  // BAD: order validation duplicated in multiple services
  public class OrderService {
      public void placeOrder(Order order) {
          if (order == null) throw new IllegalArgumentException();
          if (order.getItems().isEmpty()) throw new InvalidOrderException("No items");
          if (order.getCustomerId() == null) throw new InvalidOrderException("No customer");
          // ... actual logic
      }
  }

  public class OrderPreviewService {
      public OrderSummary preview(Order order) {
          if (order == null) throw new IllegalArgumentException();
          if (order.getItems().isEmpty()) throw new InvalidOrderException("No items");
          if (order.getCustomerId() == null) throw new InvalidOrderException("No customer");
          // ... different logic
      }
  }

  Bug: validation rule changes in ONE place → must find all copies.

  FIX: Extract validation once:
  public class OrderValidator {
      public void validate(Order order) {
          Objects.requireNonNull(order, "Order must not be null");
          if (order.getItems().isEmpty()) throw new InvalidOrderException("No items");
          if (order.getCustomerId() == null) throw new InvalidOrderException("No customer");
      }
  }

  Both services call OrderValidator.validate(order).
  Rule changes once → fixed everywhere.

----------------------------------------------------------------
VIOLATION EXAMPLE: CONSTANT DUPLICATION
----------------------------------------------------------------

  // BAD: magic string "admin" scattered across codebase
  if (user.getRole().equals("admin")) { ... }
  if (!"admin".equals(role)) throw new AccessDeniedException();
  List<User> admins = users.stream().filter(u -> "admin".equals(u.getRole())).toList();

  FIX: Define once:
  public final class Roles {
      public static final String ADMIN = "admin";
      public static final String USER  = "user";
  }
  // Or use enum:
  public enum Role { ADMIN, USER, MODERATOR }

----------------------------------------------------------------
VIOLATION EXAMPLE: SCHEMA DUPLICATION
----------------------------------------------------------------

  // BAD: column mapping duplicated in both query and entity
  @Column(name = "order_status")
  private String status;  // in entity

  // In native query — same column name hardcoded again
  @Query("SELECT o FROM Order o WHERE o.status = 'PENDING'")
  List<Order> findPending();

  // If column renamed → must find all query strings too
  // AND entity mapping AND index definition AND migration script

  FIX: Use JPA named constants or Spring Data method names:
  List<Order> findByStatus(OrderStatus status);  // no SQL, column name derived
  // OR use enum: 'PENDING' only defined in OrderStatus enum

----------------------------------------------------------------
DRY IN DATABASE SCHEMAS
----------------------------------------------------------------

  Table normalization IS DRY for data:
    1NF, 2NF, 3NF remove data redundancy.
    Customer address stored once (1NF) not in every order row (violation).

  Denormalization is a DELIBERATE DRY violation for performance.
  Always document why denormalization is intentional.

----------------------------------------------------------------
WHEN DRY GOES TOO FAR
----------------------------------------------------------------

  Over-DRY: premature abstraction to eliminate all repetition.

  "WET code" (Write Everything Twice) > "DRY code" that's wrong abstraction:

  Example: two different forms of validation look similar now but will
  diverge in 2 months. Premature extraction into one method creates
  accidental coupling — changing one validation must carefully not break the other.

  Rule of Three (Sandi Metz / Kent Beck):
    Once: write it.
    Twice: note the duplication.
    Third time: abstract it.

  Two similar things may be coincidence. Three similar things = pattern worth naming.

----------------------------------------------------------------
DRY vs WET vs AHA
----------------------------------------------------------------

  DRY: every piece of knowledge in one place.
  WET: Write Everything Twice (pragmatic: no premature abstraction).
  AHA: Avoid Hasty Abstractions (Kent C. Dodds):
       Duplication is cheaper than the wrong abstraction.
       Don't DRY prematurely just because code looks similar.

----------------------------------------------------------------
REAL-WORLD JAVA EXAMPLES
----------------------------------------------------------------

  Java stdlib:
    - String.CASE_INSENSITIVE_ORDER — reusable Comparator, not repeated
    - Math.PI — constant defined once
    - Collections utility methods — algorithms defined once for all collections

  Spring:
    - @ExceptionHandler centralized error handling (vs duplicated try-catch)
    - AOP @Around advice for cross-cutting concerns (logging, timing, security)
    - Spring Validation (Bean Validation annotations) — validation defined in one place (entity)

  Test code:
    - @BeforeEach setup instead of repeating setup in every test
    - Test data builders / object mothers — entity creation in one place

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is DRY? Is it only about code duplication?
  A: DRY is about knowledge duplication. A piece of business logic, a constant,
     a schema definition, a validation rule — each should have one authoritative
     place. Code duplication is the most visible form, but duplication in config,
     constants, and documentation is equally harmful.

  Q: Can DRY be over-applied?
  A: Yes. "Rule of Three" prevents premature extraction. Two similar code blocks
     may be coincidence; merge them and you may couple things that should diverge.
     AHA principle: duplication is cheaper than the wrong abstraction.

  Q: How does DRY relate to SRP?
  A: SRP assigns each responsibility to one class. DRY ensures each piece of
     knowledge lives in one place. They reinforce each other: if business logic
     is duplicated across classes, SRP is likely also violated (multiple classes
     doing the same thing).

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - "DRY is about knowledge, not just copy-paste code" impresses interviewers.
  - Rule of Three and AHA show maturity (DRY is not absolute).
  - Test code DRY: @BeforeEach, test builders — shows practical awareness.
  - Connect to AOP for cross-cutting concerns (DRY at the infrastructure level).
