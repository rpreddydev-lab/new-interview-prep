================================================================
  KISS — KEEP IT SIMPLE, STUPID
================================================================

  Definition: Systems work best when kept simple rather than complex.
              Simplicity should be a key design goal.
              Unnecessary complexity should be avoided.

  Origin: US Navy design principle (1960). Kelly Johnson.

  "The most important single aspect of software development is to be
   clear about what you are trying to build." — Bjarne Stroustrup

  "Simplicity is prerequisite for reliability." — Edsger Dijkstra

----------------------------------------------------------------
WHAT KISS GUARDS AGAINST
----------------------------------------------------------------

  Over-engineering: building complex, generic, extensible systems
  for problems that don't require it.

  Symptoms of KISS violation:
    - "Clever" code that requires explanation to understand
    - Layers of abstraction with no immediate benefit
    - Framework-within-a-framework
    - Generic solution for a specific problem
    - 500-line class that could be 30 lines
    - Design patterns applied where a simple method would do

----------------------------------------------------------------
VIOLATION EXAMPLE: OVER-ENGINEERED GREETING
----------------------------------------------------------------

  // BAD: factory + strategy + builder for a greeting
  interface GreetingStrategy {
      String greet(String name);
  }

  class FormalGreeting implements GreetingStrategy {
      public String greet(String name) { return "Good day, " + name; }
  }

  class CasualGreeting implements GreetingStrategy {
      public String greet(String name) { return "Hey " + name + "!"; }
  }

  class GreetingFactory {
      public static GreetingStrategy create(String type) {
          return switch (type) {
              case "formal" -> new FormalGreeting();
              case "casual" -> new CasualGreeting();
              default -> throw new IllegalArgumentException();
          };
      }
  }

  // Usage
  String greeting = GreetingFactory.create("casual").greet("Alice");

  // SIMPLE: just a method
  public String greet(String name, boolean formal) {
      return formal ? "Good day, " + name : "Hey " + name + "!";
  }

  When the requirements are simple, the code should be simple.
  Patterns have costs (classes, indirection, learning curve).
  Patterns should be applied when the problem DEMANDS them.

----------------------------------------------------------------
VIOLATION EXAMPLE: OVER-ABSTRACTED DATA ACCESS
----------------------------------------------------------------

  // BAD: generic DAO + specification + repository + service for one CRUD table
  public interface GenericDao<T, ID> {
      T findById(ID id);
      List<T> findAll();
      void save(T entity);
      void delete(ID id);
  }

  public class GenericDaoImpl<T, ID> implements GenericDao<T, ID> {
      // Reflection-based generic implementation...
  }

  public interface UserSpecification {
      Predicate<User> toPredicate();
  }

  // ...10 more classes for 1 user table

  // SIMPLE (using Spring Data JPA):
  @Repository
  public interface UserRepository extends JpaRepository<User, Long> {
      Optional<User> findByEmail(String email);
  }

  Use the framework. Spring Data JPA already solved this.

----------------------------------------------------------------
SIMPLE CODE CHARACTERISTICS
----------------------------------------------------------------

  Simple code:
    - Does exactly what it says in the name
    - Uses the fewest moving parts to achieve the goal
    - Is obvious to a developer seeing it for the first time
    - Uses standard library / framework where available
    - Doesn't add abstraction layers that don't carry their weight

  Signs of complexity:
    - "You need to read this other class to understand this one"
    - "There's a trick here..."
    - "We might need this later"
    - Multiple levels of inheritance to get to actual behavior
    - State machine where a boolean would do

----------------------------------------------------------------
SIMPLE VS SIMPLISTIC
----------------------------------------------------------------

  Simple: the minimal design that correctly solves the problem.
          Easy to understand, extend, and maintain.

  Simplistic: oversimplified to the point of being incorrect or fragile.
              Ignores edge cases, threading, failure modes.

  KISS aims for SIMPLE, not simplistic:
    Ignoring error handling = simplistic (not simple)
    One well-named method that handles edge cases = simple

----------------------------------------------------------------
KISS AND PATTERNS
----------------------------------------------------------------

  Design patterns have costs:
    - More classes to navigate
    - Indirection makes debugger traces deeper
    - Onboarding takes longer

  Apply patterns only when the PROBLEM requires it:

  YAGNI test: "Do I have this requirement NOW?"
    YES → use pattern if complexity warrants
    NO  → use the simplest thing that works

  Red flags for pattern misapplication:
    Singleton: when you could just pass the object as a parameter
    Factory: when there's only ever one concrete type
    Observer: when there's only one listener
    Strategy: when there's only one algorithm and will never change
    Visitor: when you control the element hierarchy (just add a method)

----------------------------------------------------------------
KISS IN JAVA EVERYDAY CODE
----------------------------------------------------------------

  Prefer:
    Optional.orElse(default)      over   if (x != null) else
    Stream.filter().map().toList()  over  for loop + condition + add
    switch expression (Java 14+)    over  long if-else chain
    record                          over  DTO class with getters/setters
    String.formatted("x=%d", x)    over  "x=" + String.valueOf(x)
    List.of(a, b, c)               over  new ArrayList<>(); add; add; add;
    Files.readString(path)          over  manual buffered reader loop

  Each simplification removes code that must be read and maintained.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is KISS and when do you apply it?
  A: KISS says use the simplest solution that correctly solves the problem.
     I apply it when I notice I'm building abstractions for hypothetical
     future requirements, or when a design pattern adds complexity without
     clear current benefit. The test: can a developer new to the codebase
     understand this in 5 minutes?

  Q: How do you balance KISS with SOLID principles?
  A: SOLID principles add abstraction (interfaces, patterns). KISS prevents
     premature abstraction. The balance: apply SOLID when you have a concrete
     need (second implementation, need to test in isolation, actual change
     driver identified). Don't apply SOLID patterns speculatively.

  Q: When is a complex design justified?
  A: When the domain IS complex. A payment processing system with multiple
     gateways, retry logic, idempotency, and fraud detection NEEDS the
     complexity. KISS doesn't mean ignore real complexity — it means don't
     add ACCIDENTAL complexity on top of inherent complexity.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - "Simplest solution that correctly solves the problem" is the key phrase.
  - Don't say "I use KISS" and then show complex code. Show simple examples.
  - KISS + YAGNI are natural partners — mention both together.
  - Show Java 8+ idioms (streams, records, Optional) as "KISS in action."
