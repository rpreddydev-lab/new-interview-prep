================================================================
  YAGNI — YOU AREN'T GONNA NEED IT
================================================================

  Definition: Don't implement something until you actually need it.

  Ron Jeffries, Extreme Programming (XP), 1990s.

  "Always implement things when you actually need them, never when
   you just foresee that you might need them." — Ron Jeffries

----------------------------------------------------------------
THE PROBLEM YAGNI ADDRESSES
----------------------------------------------------------------

  Speculative generality: building features, abstractions, and
  extension points for imagined future requirements.

  Cost of speculative code:
    - Takes time to write (now, instead of actual current features)
    - Must be tested, documented, maintained
    - Creates complexity that confuses future developers
    - May never be used — pure waste
    - If requirements change, the speculation is wrong anyway

  "The cost of not doing X now is usually lower than the cost
   of doing X now and maintaining it forever." — Kent Beck

----------------------------------------------------------------
COMMON YAGNI VIOLATIONS
----------------------------------------------------------------

  1. UNUSED PARAMETERS
     "We might need a locale parameter later"
     public String formatPrice(double amount, Locale locale) {
         // locale never used
         return String.format("$%.2f", amount);
     }
     → Remove locale. Add it when needed.

  2. UNUSED EXTENSION POINTS
     Adding abstract base class for one concrete class:
     abstract class AbstractPaymentProcessor  // only one concrete subclass
         extends AbstractTransactionalPaymentProcessor  // only adds abstract method
             extends BaseProcessor { }  // no implementations

  3. PLUGIN FRAMEWORK FOR ONE PLUGIN
     Building a full plugin architecture for what will always be one use case.

  4. GENERIC SOLUTION FOR SPECIFIC PROBLEM
     Writing a generic expression evaluator when only addition is needed.

  5. FRAMEWORK EXTRACTION BEFORE DUPLICATION
     Extracting a "reusable library" from one use case before there's a second user.

----------------------------------------------------------------
YAGNI IN ACTION — BEFORE AND AFTER
----------------------------------------------------------------

  SCENARIO: User needs to calculate order discounts. Today: 10% off for all.
  Future maybe: tiered discounts based on history.

  YAGNI VIOLATION:
  // Building for imagined future:
  public interface DiscountStrategy { ... }
  public class TieredDiscountStrategy implements DiscountStrategy { ... }
  public class FlatDiscountStrategy implements DiscountStrategy { ... }
  public class DiscountStrategyFactory { ... }
  public class DiscountContext { ... }

  YAGNI COMPLIANT:
  // Build only for today's requirement:
  public double applyDiscount(double price) {
      return price * 0.90;  // 10% off — one line
  }

  When tiered discount is actually required:
    THEN extract DiscountStrategy interface.
    THEN the abstraction will be correct because you have TWO real use cases.

----------------------------------------------------------------
YAGNI AND REFACTORING
----------------------------------------------------------------

  YAGNI is safe ONLY when combined with refactoring skills.

  "Do the simplest thing now" REQUIRES "be able to refactor easily later."

  YAGNI without refactoring = technical debt accumulation.
  YAGNI with good test coverage = freedom to add complexity only when needed.

  The workflow:
    1. Write the simplest thing that works
    2. Keep tests green
    3. When SECOND similar requirement arrives → identify pattern
    4. Refactor to the right abstraction
    5. Third case confirms the abstraction is correct

  This is the Red-Green-Refactor cycle in TDD.

----------------------------------------------------------------
YAGNI vs OCP
----------------------------------------------------------------

  Tension: OCP says "be open for extension". YAGNI says "don't add extension
           points you don't need."

  Resolution: Apply OCP to KNOWN extension axes.
    Known: "We will add payment methods every month" → OCP is justified now.
    Unknown: "We might need internationalization someday" → YAGNI; wait.

  "Close the door you're going through, not the door you might go through."

  Uncle Bob's reconciliation: "Implement OCP by closing extension points
  that have ALREADY been violated once."
  First change: modify the class (accept the pain).
  Second change of the same type: abstract out the variation.

----------------------------------------------------------------
REAL-WORLD EXAMPLES OF YAGNI WASTE
----------------------------------------------------------------

  - Configuration system with 40 properties, 35 never used.
  - AbstractBaseRepository with 8 abstract methods; only 2 ever called.
  - Event bus infrastructure built before any events are published.
  - Multi-tenant architecture built for a single-tenant app.
  - Caching layer added before performance is measured.
  - Microservice split before the service has users.

  All of these added complexity, slowed delivery, and were often wrong
  when the "future requirement" finally arrived in a different form.

----------------------------------------------------------------
YAGNI AND AGILE
----------------------------------------------------------------

  YAGNI is an XP/Agile principle:
    Build for the current sprint's requirements.
    Let the backlog drive what gets built next.
    The product owner prioritizes — not the developer's imagination.

  In a waterfall project with fixed specs, YAGNI is harder to apply
  (requirements are known in advance). In agile: requirements evolve;
  building ahead means building the wrong thing.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is YAGNI? How do you balance it with good design?
  A: YAGNI says don't implement things until actually needed. Balance
     with good design: write clean, testable code for current requirements.
     When the second similar requirement arrives, THEN refactor to the right
     abstraction. The first occurrence is a hint; the second is a pattern.
     This requires test coverage to refactor safely.

  Q: When is it OK to violate YAGNI?
  A: When the cost of adding later is disproportionately high:
     - Database schema changes (hard to migrate later) — design for likely future
     - Public API design (breaking changes hurt consumers)
     - Security architecture (retrofitting auth is harder than building it in)
     These are known, high-cost change points that justify upfront design.

  Q: What is the relationship between YAGNI and technical debt?
  A: YAGNI prevents a specific type of technical debt: unused abstractions
     that must be maintained. But YAGNI requires refactoring discipline
     to avoid a different debt: underdeveloped design that's hard to extend.
     YAGNI + TDD + regular refactoring is the balanced approach.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - YAGNI, KISS, and DRY are a triangle — know how they interact.
  - "Build for two use cases, not one" is the Rule of Three in action.
  - Connect YAGNI to refactoring/TDD — safety net for "simplest now."
  - Mention specific YAGNI wastes: premature abstraction, plugin frameworks.
