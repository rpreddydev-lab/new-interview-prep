================================================================
  ENCAPSULATE WHAT VARIES
================================================================

  Definition: Identify the aspects of your application that vary
              and separate them from what stays the same.

  Head First Design Patterns, 2004.
  Foundational principle behind the Strategy, Decorator, Factory, and Observer patterns.

----------------------------------------------------------------
CORE IDEA
----------------------------------------------------------------

  Every piece of software has two parts:
    - STABLE PARTS: the skeleton, structure, core flow — rarely changes
    - VARIABLE PARTS: the specific algorithms, behaviors, policies — changes often

  ENCAPSULATE WHAT VARIES means:
    Isolate the variable parts behind an abstraction.
    Stable parts depend on the abstraction, not the variable implementation.

  When the variable part changes, ONLY that part changes.
  The stable skeleton stays untouched.

  This IS the foundational motivation for most design patterns.

----------------------------------------------------------------
EXAMPLE — PAYMENT PROCESSING
----------------------------------------------------------------

  STABLE: the order checkout flow
    1. Validate order
    2. Calculate total
    3. Process payment
    4. Send confirmation

  VARIABLE: HOW payment is processed
    - Credit card, PayPal, Crypto, Bank Transfer — each changes independently
    - New payment methods added regularly

  Without encapsulation:
    checkout() has if-else or switch on payment type.
    Every new payment method → modify checkout() → risk regression.

  With encapsulation:
    PaymentStrategy interface hides the variation.
    Checkout depends on PaymentStrategy (stable abstraction).
    Each payment method is a separate class.
    checkout() never changes.

  VARIABLE PART:  PaymentStrategy (interface + concrete impls)
  STABLE PART:    checkout() flow — calls strategy.pay()

----------------------------------------------------------------
EXAMPLE — SORTING ALGORITHM
----------------------------------------------------------------

  STABLE: the collection container, the sort request
  VARIABLE: the comparison order (natural, reversed, by field, custom)

  Without encapsulation:
    SortByNameList, SortBySalaryList, SortByAgeList extends AbstractList
    → class explosion

  With encapsulation:
    Comparator<T> encapsulates the variable part (comparison logic)
    List.sort(comparator) — stable framework, variable behavior injected

  Comparator.comparing(Employee::getSalary) — variable
  List.sort() — stable

----------------------------------------------------------------
EXAMPLE — LOGGING
----------------------------------------------------------------

  STABLE: when to log, log format structure
  VARIABLE: where logs go (console, file, database, Splunk, CloudWatch)

  Without encapsulation:
    if (env == "dev") System.out.println(msg);
    else if (env == "prod") fileWriter.write(msg);
    → scattered throughout codebase

  With encapsulation:
    Logger interface hides the destination.
    ConsoleLogger, FileLogger, CloudWatchLogger implement it.
    All callers use Logger.log(level, message) — stable.

  Java's java.util.logging, SLF4J, Log4j all follow this pattern.

----------------------------------------------------------------
IDENTIFYING WHAT VARIES
----------------------------------------------------------------

  Questions to ask when reviewing code:
    1. "If this requirement changes, how many places need editing?"
       More than one → the variation is not encapsulated.

    2. "Is there an if-else or switch on type here?"
       Usually signals variation that should be polymorphism.

    3. "Do different callers of this class need different behavior?"
       The difference = what varies.

    4. "What changes between deployments/environments?"
       Database URL, API keys, algorithms → encapsulate behind config/interface.

----------------------------------------------------------------
PATTERNS THAT IMPLEMENT THIS PRINCIPLE
----------------------------------------------------------------

  Pattern            What It Encapsulates
  ---------------    ------------------------------------------
  Strategy           Algorithm / policy
  Decorator          Added behavior (wraps and extends)
  Factory Method     Object creation (which class to instantiate)
  Abstract Factory   Family of related object creation
  Observer           Reaction to events
  State              Behavior per state
  Template Method    Concrete steps of an algorithm
  Bridge             Implementation details from abstraction
  Command            Action details (what to do, when, how)

  All of these follow the same structure:
    Variable part → hidden behind an abstraction (interface)
    Stable part   → depends on abstraction, not concrete

----------------------------------------------------------------
ENCAPSULATION AT MULTIPLE LEVELS
----------------------------------------------------------------

  Field encapsulation (basic OOP):
    private fields accessed via methods.
    Prevents direct state manipulation.

  Method encapsulation:
    Complex logic hidden in a method with a good name.
    Caller doesn't know the algorithm — just the contract.

  Interface encapsulation (Encapsulate What Varies):
    Variable behavior hidden behind interface.
    Caller doesn't know which implementation is used.

  Module encapsulation (package private):
    Implementation details not exposed outside the package.

  All levels serve the same goal: callers should not need to know
  the details of what's behind the abstraction.

----------------------------------------------------------------
SPRING EXAMPLES
----------------------------------------------------------------

  Variable: DataSource (connection details, pool implementation)
  Stable:   JdbcTemplate, @Repository using DataSource
  Encapsulated via: DataSource interface (HikariCP, H2, JNDI all implement it)

  Variable: Which MessageConverter handles HTTP body serialization
  Stable:   DispatcherServlet sending/receiving HTTP
  Encapsulated via: HttpMessageConverter interface

  Variable: Which CacheManager to use (Redis, Caffeine, EhCache, None)
  Stable:   @Cacheable annotation behavior
  Encapsulated via: CacheManager + Cache interfaces

  Variable: Authentication mechanism (JWT, OAuth2, Basic, SAML)
  Stable:   Security filter chain
  Encapsulated via: AuthenticationProvider interface

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What does "Encapsulate What Varies" mean?
  A: Identify the parts of your code that are likely to change —
     different algorithms, different behaviors per environment, different
     policies — and isolate them behind an interface. The stable parts
     depend only on the interface. When the variable part changes, the
     stable part doesn't need modification. This is the motivation behind
     Strategy, Factory, Observer, and most other patterns.

  Q: How is "Encapsulate What Varies" related to OCP?
  A: They are two sides of the same coin. OCP says "closed to modification."
     Encapsulate What Varies says "identify WHAT to close." First you identify
     the variable part (the axis of change), then you encapsulate it (create
     the abstraction), then the stable parts become closed to modification.

  Q: How do you identify what varies in a codebase?
  A: Look for: if-else/switch on type, copy-paste with one variation,
     "this will need to change when X" comments, places where tests need
     conditional setup for different scenarios, and places where requirements
     frequently change.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - "Identify what changes, isolate it" is the actionable phrase.
  - Pattern-principle connection: every major pattern encapsulates something.
  - Spring framework examples show production-level thinking.
  - Connect to OCP: this principle is the HOW behind OCP.
