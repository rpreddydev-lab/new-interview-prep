AWS CLOUD — COST OPTIMIZATION STRATEGIES
Complete Interview Preparation Guide
================================================================

1. COST OPTIMIZATION OVERVIEW
================================================================

  AWS Cost Optimization is the 5th Pillar of the Well-Architected Framework.
  Key principle: pay only for what you need, eliminate waste, right-size resources.

  CORE STRATEGIES:
  1. Right-sizing (use the correct resource size)
  2. Pricing model selection (On-Demand vs Reserved vs Savings Plans vs Spot)
  3. Elimination of waste (idle resources, orphaned volumes, oversized DBs)
  4. Architecture optimization (serverless, managed services, auto-scaling)
  5. Storage tiering (S3 lifecycle policies, Glacier)

================================================================
2. EC2 PRICING MODELS
================================================================

  ┌─────────────────────┬──────────────────────────────────────────────────────────┐
  │ Model               │ Description & Savings                                    │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ On-Demand           │ Pay per second/hour. No commitment. Most flexible.        │
  │                     │ Use for: unpredictable workloads, testing, short bursts.  │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ Reserved Instances  │ 1- or 3-year commitment. Up to 72% savings vs On-Demand. │
  │ (RI)                │ Standard RI: fixed type. Convertible RI: can change type. │
  │                     │ Use for: steady-state production workloads (DB servers,   │
  │                     │ always-on app tier). Can be sold in RI Marketplace.       │
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ Savings Plans       │ Flexible commitment ($/hour), not to specific instance.   │
  │                     │ Up to 66% savings. Two types:                            │
  │                     │ - Compute: any EC2, Lambda, Fargate across regions.       │
  │                     │ - EC2 Instance: specific family in specific region (72%). │
  │                     │ Use for: multi-service teams (prefer over RI for flexibility)│
  ├─────────────────────┼──────────────────────────────────────────────────────────┤
  │ Spot Instances      │ Spare EC2 capacity. Up to 90% savings. Can be interrupted │
  │                     │ with 2-minute warning. Use for: batch processing, CI/CD,  │
  │                     │ fault-tolerant workloads, ML training. NOT for databases. │
  └─────────────────────┴──────────────────────────────────────────────────────────┘

  CHOOSING A PRICING MODEL:
  - Baseline (always-on) load → Savings Plans / Reserved Instances
  - Predictable spiky load (business hours) → On-Demand Auto Scaling
  - Batch, fault-tolerant, interruptible → Spot Instances
  - Use Mix: Savings Plans for baseline + On-Demand/Spot for spikes

3. SAVINGS PLANS vs RESERVED INSTANCES
================================================================

  SAVINGS PLANS (recommended for most organizations):
  - Commit to a $ spend per hour (e.g., $10/hour)
  - Applies automatically to any eligible compute usage
  - More flexible: works across EC2 instance types, sizes, regions, OS
  - Compute Savings Plan: covers EC2 + Lambda + Fargate (best for microservices)
  - No Marketplace resale (can't sell unused plans)

  RESERVED INSTANCES:
  - Commit to specific: instance family + region + OS + tenancy
  - Convertible RI: can exchange for different family (lower savings: 54%)
  - Standard RI: cannot change (up to 72% savings)
  - Can be sold on RI Marketplace if unused

  RULE: Use Compute Savings Plans for Java microservices on ECS/Fargate + Lambda.
  The flexibility to cover Fargate tasks AND Lambda AND EC2 in one commitment 
  makes it superior to EC2 RIs for cloud-native Java applications.

4. SPOT INSTANCES FOR JAVA WORKLOADS
================================================================

  USE CASES FOR JAVA + SPOT:
  1. CI/CD builds (CodeBuild / Jenkins on Spot EC2)
  2. Spring Batch jobs on AWS Batch (stateless, restartable)
  3. Non-critical ECS services with Spot task capacity providers
  4. Development/staging environments

  SPOT INTERRUPTION HANDLING (Java):
  - Spot sends 2-minute warning via EC2 metadata:
    GET http://169.254.169.254/latest/meta-data/spot/termination-time
    Returns 404 if no interruption, returns timestamp if being terminated.
    
  // Poll for interruption (run in background thread):
  public class SpotTerminationMonitor {
  
      private static final String METADATA_URL = 
          "http://169.254.169.254/latest/meta-data/spot/termination-time";
  
      @Scheduled(fixedDelay = 5000)
      public void checkForTermination() {
          try {
              HttpResponse<String> response = httpClient.send(
                  HttpRequest.newBuilder().uri(URI.create(METADATA_URL)).build(),
                  HttpResponse.BodyHandlers.ofString());
              
              if (response.statusCode() == 200) {
                  log.warn("Spot interruption notice received! Initiating graceful shutdown.");
                  // Stop accepting new work
                  // Complete current task if possible
                  // Checkpoint state to S3/DB
                  applicationContext.close();
              }
          } catch (Exception ignored) { }
      }
  }

  ECS + SPOT CAPACITY PROVIDERS:
  // Capacity provider strategy: prefer Spot, fall back to On-Demand:
  capacityProviderStrategy:
    - capacityProvider: FARGATE_SPOT
      weight: 4
      base: 0
    - capacityProvider: FARGATE
      weight: 1
      base: 2      // Always keep 2 On-Demand tasks as minimum

5. RIGHT-SIZING AND WASTE ELIMINATION
================================================================

  TOOLS:
  - AWS Compute Optimizer: recommends right-sized EC2, ECS tasks, Lambda memory
  - AWS Cost Explorer: visualize spending by service, region, tag
  - Trusted Advisor: identifies idle resources, underutilized instances
  - AWS Resource Groups + Tagging: track cost by team/project/environment

  COMMON WASTE PATTERNS:
  ┌────────────────────────────────┬──────────────────────────────────────────────┐
  │ Waste Type                     │ Solution                                     │
  ├────────────────────────────────┼──────────────────────────────────────────────┤
  │ Idle EC2/RDS in dev/staging    │ Schedule stop/start (EventBridge + Lambda)   │
  │ Oversized Lambda memory        │ Use Lambda Power Tuning tool to find optimum │
  │ Old EBS snapshots              │ Lifecycle policy: delete snapshots > 90 days │
  │ Unattached EBS volumes         │ AWS Config rule: detect and alert            │
  │ Old ECR images                 │ ECR lifecycle policy: keep only last 10 tags │
  │ S3 incomplete multipart uploads│ S3 lifecycle: abort after 7 days            │
  │ Over-provisioned RDS           │ AWS Compute Optimizer for RDS recommendations│
  └────────────────────────────────┴──────────────────────────────────────────────┘

  SCHEDULE DEV ENVIRONMENT STOP (Java-relevant example):
  // EventBridge rule: every weekday at 7PM stop dev RDS and ECS:
  aws rds stop-db-instance --db-instance-identifier dev-myapp-db
  aws ecs update-service --cluster dev-cluster --service myapp --desired-count 0
  // Restart at 8AM — saves ~65% on dev environment costs

6. S3 STORAGE OPTIMIZATION
================================================================

  S3 STORAGE CLASSES (cheapest to most expensive for storage):
  ┌──────────────────────────┬─────────────────┬──────────────────────────────────┐
  │ Class                    │ Storage Cost    │ Retrieval / Use Case             │
  ├──────────────────────────┼─────────────────┼──────────────────────────────────┤
  │ Glacier Deep Archive     │ $0.00099/GB/mo  │ 12–48h retrieval. 7+ yr archive. │
  │ Glacier Flexible         │ $0.004/GB/mo    │ 1–12h retrieval. Compliance.     │
  │ Glacier Instant Retrieve │ $0.023/GB/mo    │ Milliseconds. Quarterly access.  │
  │ Standard-IA              │ $0.0125/GB/mo   │ Infrequent access. 30-day min.   │
  │ Intelligent-Tiering      │ $0.023/GB/mo    │ Auto-moves to cheaper class.     │
  │ Standard                 │ $0.023/GB/mo    │ Frequent access. Default.        │
  └──────────────────────────┴─────────────────┴──────────────────────────────────┘

  S3 LIFECYCLE POLICY (example for Java app logs):
  {
    "Rules": [
      {
        "ID": "LogRetentionPolicy",
        "Filter": { "Prefix": "app-logs/" },
        "Status": "Enabled",
        "Transitions": [
          { "Days": 30, "StorageClass": "STANDARD_IA" },
          { "Days": 90, "StorageClass": "GLACIER" },
          { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
        ],
        "Expiration": { "Days": 2555 }   // Delete after 7 years
      }
    ]
  }

  S3 INTELLIGENT-TIERING:
  - Automatically moves objects between tiers based on access patterns
  - No retrieval fee (unlike Standard-IA or Glacier)
  - Small monitoring fee per object
  - Best for: data with unpredictable access patterns
  - Not cost-effective for: very small objects (< 128 KB) or very short-lived objects

7. LAMBDA COST OPTIMIZATION
================================================================

  Lambda pricing: $0.0000166667 per GB-second + $0.20 per 1M requests

  OPTIMIZATION 1: RIGHT-SIZE MEMORY
    - More memory = more CPU = faster execution = lower GB-seconds
    - Use Lambda Power Tuning (open source): tests your Lambda at different 
      memory levels and finds the optimal cost/performance point
    
    Common finding: 512 MB may be slower AND more expensive than 1024 MB 
    (because 1024 gets more CPU, finishes faster, lower GB-seconds total)

  OPTIMIZATION 2: MINIMIZE INITIALIZATION
    - Initialize AWS clients outside handler (static) — reused on warm calls
    - Reduce deployment package size (modular SDK v2)
    - Use SnapStart or Provisioned Concurrency only where needed

  OPTIMIZATION 3: RESERVED CONCURRENCY vs PROVISIONED CONCURRENCY
    - Reserved Concurrency: limits max instances (cost control, not cost saving)
    - Provisioned Concurrency: pre-warms instances (costs money even at idle)
    - Only use Provisioned Concurrency for latency-sensitive Lambda + Java cold start

  OPTIMIZATION 4: BATCH SQS PROCESSING
    // Process 10 messages per Lambda invocation instead of 1:
    @SqsListener(value = "${queue.url}", maxNumberOfMessages = "10")
    public void processMessages(List<Order> orders) {
        // Process batch — reduces invocation count by 10x
    }
    // 10x fewer invocations = 10x fewer request charges

8. RDS COST OPTIMIZATION
================================================================

  1. AURORA SERVERLESS v2:
     - Scales from 0.5 ACU to 128 ACU in seconds
     - Scale to 0 during idle (dev/staging) — pay nothing when not in use
     - More expensive per ACU than provisioned, but cost-effective for variable load
     
     spring.datasource.url: jdbc:postgresql://aurora-serverless.cluster-xxx.rds.amazonaws.com

  2. RESERVED DB INSTANCES:
     - 1-year reservation: ~30% savings on RDS/Aurora
     - 3-year: ~40% savings
     - Use for steady-state production databases

  3. STOP NON-PROD DATABASES:
     - RDS can be stopped for up to 7 days (then auto-starts)
     - Use EventBridge + Lambda to stop/start on schedule
     - Saves 100% of instance costs during off-hours

  4. MULTI-AZ ONLY IN PRODUCTION:
     - Multi-AZ doubles DB instance cost
     - Dev/staging: single-AZ with automated backups is sufficient

  5. READ REPLICAS ONLY IF NEEDED:
     - Don't create read replicas "just in case" — they cost the same as primary
     - Add read replicas only when CPU/read latency metrics show need

9. COST ALLOCATION AND TAGGING
================================================================

  Without tagging: impossible to know which team/service is causing costs.

  MANDATORY TAGS (enforce with AWS Config / SCP):
    Environment: prod | staging | dev
    Team:        payments | orders | platform
    Service:     order-service | payment-gateway
    CostCenter:  CC-1234
    Owner:       eng-team@company.com

  AWS COST ALLOCATION TAGS:
  - Activate tags in Billing console → they appear in Cost Explorer
  - Set budget alerts per tag value:
    Budget: $5000/month for Team=payments, alert at 80% and 100%

  CDK/CloudFormation — apply tags to all resources:
  // Java CDK:
  Tags.of(this).add("Team", "payments");
  Tags.of(this).add("Environment", "prod");
  // These tags apply to ALL resources in the stack

10. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Reserved Instances and Savings Plans? 
   Which do you recommend for a Java microservices team?

A: Reserved Instances commit to a specific EC2 instance type, size, region, 
   and OS for 1 or 3 years. Very high savings (up to 72%) but inflexible — 
   if you change instance type you may not get the full discount.
   
   Savings Plans commit to a $ spend per hour across compute. Compute Savings 
   Plans apply to EC2, Fargate, AND Lambda automatically across instance types 
   and regions (up to 66% savings). EC2 Instance Savings Plans are per-family 
   (up to 72%, less flexible than Compute).
   
   For a Java microservices team on ECS/Fargate + Lambda: Compute Savings Plans 
   are best — one commitment covers Fargate tasks, Lambda invocations, and any 
   EC2. No need to track which RI applies to which service.

---

Q: How do you handle Spot instance interruptions in a Java batch job on AWS Batch?

A: AWS Batch with Spot automatically retries interrupted jobs (configurable retry 
   count). Application-level: design jobs to be restartable from checkpoints.
   
   For Spring Batch: use RDS as JobRepository — if Spot terminates mid-job, 
   the next retry restarts from the last committed step/chunk (not from beginning).
   
   For ECS Spot: monitor the instance metadata endpoint 
   (http://169.254.169.254/latest/meta-data/spot/termination-time) and on 
   2-minute warning: stop accepting new tasks, checkpoint current state to S3/DB, 
   send a SIGTERM to Spring Boot (graceful shutdown via shutdown hook).

---

Q: How do you identify and eliminate cost waste in an AWS account?

A: Multi-step approach:
   1. AWS Cost Explorer: identify top 10 cost drivers by service/tag.
   2. AWS Compute Optimizer: identify over-provisioned EC2, ECS tasks, Lambda.
   3. Trusted Advisor: find idle EC2, underutilized RDS, unassociated EIPs.
   4. Tag-based cost allocation: find untagged resources (often orphaned).
   5. Common fixes: 
      - Stop dev/staging environments on weekends (EventBridge scheduler).
      - S3 lifecycle policies for old data to Glacier.
      - Delete unattached EBS volumes (AWS Config rule alert).
      - ECR lifecycle policy: retain only last N image tags.
      - Lambda: use Power Tuning to right-size memory.
      - Apply Savings Plans to baseline compute usage.
