AWS IAM — IDENTITY FEDERATION AND SSO
Complete Interview Preparation Guide
================================================================

1. WHAT IS IDENTITY FEDERATION?
================================================================

Identity Federation allows users who already have credentials in external
identity systems to access AWS resources WITHOUT creating separate IAM users.

Key Concept: Instead of managing users in AWS, users authenticate with
their existing identity provider (IdP) and receive temporary AWS credentials.

Benefits:
  - Single Sign-On (SSO) — one login for everything
  - No separate AWS passwords to manage
  - Scales to thousands of users without creating IAM users
  - Supports corporate Active Directory, social logins, and custom systems

================================================================
2. FEDERATION TYPES
================================================================

TYPE 1: SAML 2.0 Federation (Enterprise / Corporate)
  Standard: Security Assertion Markup Language 2.0
  Use Case: Active Directory, Okta, Azure AD, PingIdentity, ADFS
  
  Flow:
    1. User authenticates to SAML IdP (e.g., Active Directory)
    2. IdP generates signed SAML assertion (XML) with user's groups/attributes
    3. User's browser POSTs SAML assertion to AWS sign-in endpoint
    4. AWS calls STS AssumeRoleWithSAML
    5. STS returns temporary credentials
    6. User accesses AWS Console or API
  
  Requirements:
    - Configure IdP with AWS as Service Provider (SP)
    - Create IAM SAML Identity Provider in AWS (trust the IdP)
    - Create IAM roles with trust policy for the SAML provider
    - Map SAML attributes to IAM roles (via SAML assertion)
  
  SAML-to-Role Mapping (in SAML assertion):
    Attribute: https://aws.amazon.com/SAML/Attributes/Role
    Value: arn:aws:iam::123456789012:role/DevRole,arn:aws:iam::123456789012:saml-provider/ADFS
  
  Create SAML provider via CLI:
    aws iam create-saml-provider \
      --saml-metadata-document file://metadata.xml \
      --name MyADFSProvider

---

TYPE 2: WEB IDENTITY / OIDC FEDERATION (Mobile / Web Apps)
  Standard: OpenID Connect (OIDC) / OAuth 2.0
  Identity Providers: Google, Facebook, Amazon, Apple, any OIDC-compatible IdP
  
  Flow:
    1. Mobile app user authenticates with Google/Facebook
    2. App receives JWT token (ID token) from IdP
    3. App calls STS AssumeRoleWithWebIdentity with the token
    4. STS validates token with the IdP, returns AWS credentials
    5. App uses credentials to access AWS (S3, DynamoDB, etc.)
  
  Note: For new applications, use Amazon Cognito instead — it handles
  this flow and adds features (user pools, sync, etc.)

---

TYPE 3: CUSTOM IDENTITY BROKER
  Use Case: When your IdP doesn't support SAML/OIDC
  
  Flow:
    1. User authenticates to your custom broker (using LDAP or other)
    2. Broker validates identity
    3. Broker calls AWS STS GetFederationToken or AssumeRole
    4. Broker returns temp credentials to user
    5. User accesses AWS
  
  The broker needs a long-term IAM user with permission to call STS.

3. AMAZON COGNITO
================================================================

Amazon Cognito provides authentication, authorization, and user management
for web and mobile applications.

COMPONENTS:

  User Pools:
    - Managed user directory (username/password, social login, SAML)
    - Handles sign-up, sign-in, account verification
    - Returns JWT tokens (ID token, access token, refresh token)
    - NOT directly related to AWS IAM permissions
    - Use case: App authentication

  Identity Pools (Federated Identities):
    - Provides temporary AWS credentials for authenticated users
    - Supports: User Pools, Google, Facebook, Apple, SAML, custom
    - Calls STS AssumeRoleWithWebIdentity behind the scenes
    - Returns AWS credentials (AccessKeyId + SecretAccessKey + SessionToken)
    - Use case: Access AWS services directly from mobile/web apps

COGNITO FLOW:
  Mobile App
    │
    ├─► Cognito User Pool ──► JWT Token
    │
    └─► Cognito Identity Pool ──► STS AssumeRoleWithWebIdentity ──► AWS Credentials
                                                                        │
                                                                    S3 / DynamoDB

JAVA COGNITO INTEGRATION (SDK v2):
  import software.amazon.awssdk.services.cognitoidentity.CognitoIdentityClient;
  import software.amazon.awssdk.services.cognitoidentity.model.*;
  
  CognitoIdentityClient cognitoClient = CognitoIdentityClient.create();
  
  // Get Cognito Identity ID
  GetIdRequest getIdRequest = GetIdRequest.builder()
      .accountId("123456789012")
      .identityPoolId("us-east-1:pool-id")
      .logins(Map.of("accounts.google.com", googleIdToken))
      .build();
  String identityId = cognitoClient.getId(getIdRequest).identityId();
  
  // Get temporary AWS credentials
  GetCredentialsForIdentityRequest credRequest = 
      GetCredentialsForIdentityRequest.builder()
          .identityId(identityId)
          .logins(Map.of("accounts.google.com", googleIdToken))
          .build();
  
  Credentials credentials = cognitoClient.getCredentialsForIdentity(credRequest).credentials();
  // credentials.accessKeyId(), credentials.secretKey(), credentials.sessionToken()

4. AWS IAM IDENTITY CENTER (SSO) — FORMERLY AWS SINGLE SIGN-ON
================================================================

AWS IAM Identity Center is the recommended way to manage human access
to multiple AWS accounts and applications.

KEY FEATURES:
  - Centralized access management for all AWS accounts in AWS Organizations
  - Built-in integrations with Okta, Azure AD, Active Directory
  - Works with SAML 2.0 applications
  - One portal URL for all accounts and apps
  - Replaces the need for IAM users in each account
  - Short-lived credentials via CLI (aws configure sso)

HOW IT WORKS:
  1. Set up AWS IAM Identity Center (enable in AWS Organizations)
  2. Connect your IdP (or use built-in user store)
  3. Create permission sets (like IAM policies)
  4. Assign users/groups from IdP to AWS accounts with permission sets
  5. Users log in at the SSO portal → pick account → get temp credentials

CLI WITH SSO:
  # Configure SSO profile
  aws configure sso
  # Prompts for: SSO start URL, region, account ID, role name
  
  # Login (opens browser for SSO authentication)
  aws sso login --profile my-sso-profile
  
  # Use the profile
  aws s3 ls --profile my-sso-profile

PERMISSION SETS:
  - Templates that define what permissions users get when assuming access to an account
  - Backed by AWS managed policies or inline policies
  - Examples: AdministratorAccess, PowerUserAccess, ReadOnlyAccess, CustomDeveloperAccess

6. INTERVIEW QUESTIONS
================================================================

Q: What is identity federation and why is it important?
A: Identity federation allows users to authenticate with an existing identity
   system (Active Directory, Google, Okta) and receive temporary AWS credentials
   without creating separate IAM users. It's important because it enables SSO
   (one login for everything), scales to large organizations (thousands of employees
   without IAM user sprawl), integrates with corporate identity systems, and follows
   the principle of not duplicating identity management.

Q: What is the difference between Cognito User Pools and Identity Pools?
A: Cognito User Pools are a user directory service that handles app authentication —
   sign-up, sign-in, JWT tokens. They manage app users but don't directly give AWS
   access. Cognito Identity Pools take authenticated users (from User Pools, Google,
   Facebook, SAML) and exchange their token for temporary AWS credentials via STS.
   Typical pattern: User Pool authenticates the user → Identity Pool gives the app
   AWS credentials to access S3/DynamoDB.

Q: When would you use SAML 2.0 federation vs AWS IAM Identity Center?
A: Both solve similar problems but at different layers. SAML federation is a lower-level
   approach where you directly configure IAM SAML providers and roles — more manual but
   more flexible. AWS IAM Identity Center (SSO) is a managed service that wraps SAML/OIDC
   and provides a user portal, multi-account assignment, and permission set management.
   For new deployments with multiple AWS accounts, IAM Identity Center is preferred.
   SAML direct federation is used when you need custom control or already have SAML
   configured and don't want to migrate to Identity Center.

Q: A company wants employees to log into AWS using their existing Active Directory
   credentials. How would you design this?
A: Option 1 (Recommended): Use AWS IAM Identity Center with Microsoft AD connector.
   Connect Identity Center to on-premises AD via AD Connector or AWS Managed Microsoft AD.
   Create permission sets, assign AD groups to AWS accounts. Employees log in at the
   SSO portal with their AD credentials.
   
   Option 2: Direct SAML federation with ADFS. Deploy ADFS (Active Directory Federation
   Services) on-premises. Configure AWS IAM SAML provider with ADFS metadata. Create
   IAM roles with trust policy for the SAML provider. Configure ADFS to release SAML
   assertions with role ARNs. Users authenticate to ADFS → get SAML assertion → AWS
   redirects them to the console with the appropriate role.

Q: How does a mobile app access DynamoDB securely without embedding AWS credentials?
A: Use Amazon Cognito. The mobile app authenticates users via Cognito User Pools (or social
   logins like Google). After authentication, the app uses Cognito Identity Pools to exchange
   the user token for temporary AWS credentials (via STS AssumeRoleWithWebIdentity).
   The app uses these short-lived credentials to call DynamoDB. Credentials auto-expire,
   and no AWS keys are embedded in the app. Different user groups can get different IAM
   roles (e.g., authenticated vs. unauthenticated roles with different DynamoDB permissions).
