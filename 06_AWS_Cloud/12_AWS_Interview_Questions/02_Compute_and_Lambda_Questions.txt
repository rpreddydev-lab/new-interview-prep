================================================================
AWS INTERVIEW QUESTIONS — COMPUTE AND LAMBDA
================================================================

Q1: What is the difference between EC2, ECS, EKS, and Lambda? When to use each?

A: EC2 (Elastic Compute Cloud): Virtual machines. You manage the OS.
   Use when:
   - Need OS-level access or specific OS configuration.
   - Long-running processes (24/7 servers, stateful apps).
   - GPU workloads (ML training, rendering).
   - Lift-and-shift migration from on-prem.
   - Software that cannot be containerized or uses proprietary licensing.

   ECS (Elastic Container Service): AWS-managed container orchestration.
   Simpler than Kubernetes. Two launch types:
   - EC2 launch type: you provision and manage EC2 nodes.
   - Fargate launch type: serverless containers — AWS manages the nodes.
   Use when: Team knows Docker but not Kubernetes. Simpler ops than EKS.

   EKS (Elastic Kubernetes Service): Managed Kubernetes control plane.
   Full Kubernetes API compatibility. Works with all Kubernetes ecosystem tools.
   Use when: Team already uses Kubernetes, need Helm/operators, multi-cloud portability.

   Lambda: Function-as-a-Service. Event-driven. No server management.
   Pay per invocation (not per idle time). Max 15-minute execution.
   Use when: Event processing, API backends, scheduled jobs, lightweight ETL,
   reacting to S3 uploads / DynamoDB streams / SQS messages.

   Decision tree:
   Need full OS control?              → EC2
   Containerized, want simple ops?   → ECS Fargate
   Need Kubernetes ecosystem?        → EKS
   Short-lived, event-driven?        → Lambda

Q2: What are Lambda cold starts? How do you minimize them, especially for Java?

A: Cold start: Lambda must initialize a new execution environment when:
   - There is no existing warm instance available.
   - Traffic spikes cause Lambda to scale out beyond warm instances.

   Cold start phases:
   1. Download the deployment package (JAR/ZIP).
   2. Start the runtime (JVM, Node.js, Python).
   3. Initialize the handler (Spring Boot context, static initializers).
   4. Execute the handler function.

   Java is worst affected: typical Spring Boot Lambda cold start = 3–10 seconds.
   Node.js: ~50–200ms. Python: ~100–300ms.

   Mitigation strategies:

   1. Provisioned Concurrency:
      Pre-warm N instances. They are always initialized, no cold start.
      Cost: you pay for provisioned environments even when idle.
      Best for: latency-sensitive production APIs.

   2. Lambda SnapStart (Java 21+ on Corretto runtime):
      Snapshots the initialized JVM state at deployment.
      On invocation, restores from snapshot instead of initializing.
      Reduces cold start from ~5s to ~200ms for Spring Boot.
      Free — no extra cost beyond normal Lambda pricing.

   3. Use lighter frameworks:
      Quarkus or Micronaut instead of Spring Boot.
      Build time DI — no runtime classpath scanning.
      Typical cold start: 200–500ms (vs. 3–10s for Spring Boot).

   4. GraalVM Native Image:
      Compile Java to native binary. Eliminates JVM startup entirely.
      Cold start: ~50–100ms. Tradeoff: slower build times, some library compatibility issues.

   5. Reduce package size:
      Only include necessary dependencies.
      Smaller JAR = faster download + initialization.

   6. Keep-warm strategy (poor man's solution):
      Schedule EventBridge rule to invoke Lambda every 5 minutes.
      Keeps one instance warm. Does NOT help with concurrent cold starts.

Q3: What is EC2 Auto Scaling? What are the scaling policy types?

A: Auto Scaling Group (ASG): automatically adjusts the number of EC2 instances
   based on demand, maintaining desired capacity and health.

   Core concepts:
   - Minimum capacity: never scale below this.
   - Maximum capacity: never scale above this.
   - Desired capacity: current target count.
   - Launch Template: defines the instance type, AMI, SG, IAM role for new instances.

   Scaling Policy Types:

   Target Tracking (recommended for most cases):
   - Maintain a metric at a target value. ASG scales in/out automatically.
   - Example: keep average CPU utilization at 50%.
   - ASG calculates the required scaling action; you just set the target.
   - Simplest to configure; AWS manages the math.

   Step Scaling:
   - Add/remove instances in steps based on CloudWatch alarm thresholds.
   - Example: +2 instances when CPU > 60%, +4 more when CPU > 80%.
   - More control for gradual vs. aggressive scaling responses.

   Simple Scaling:
   - Fixed action when an alarm fires. Cooldown period before next action.
   - Older and less flexible. Prefer target tracking or step scaling.

   Scheduled Scaling:
   - Scale on a fixed schedule (e.g., +20 instances at 7:45 AM weekdays).
   - Use for predictable traffic patterns (business hours, Black Friday).

   Predictive Scaling:
   - Uses ML to forecast traffic based on historical patterns.
   - Pre-scales BEFORE the peak arrives.
   - Best for cyclical workloads with at least 24 hours of CloudWatch history.

   Health checks:
   - ASG replaces unhealthy instances automatically.
   - Can use EC2 health checks (instance reachable) or ELB health checks (app responds 200 OK).
   - Always use ELB health checks for application-level validation.

Q4: What is the difference between ALB, NLB, and CLB?

A: CLB (Classic Load Balancer): Legacy. Avoid for all new workloads. No new features added.

   ALB (Application Load Balancer): Layer 7 — HTTP/HTTPS/WebSocket/gRPC.
   - Content-based routing:
     * Path-based: /api/* → service A, /web/* → service B
     * Host-based: api.example.com → service A, web.example.com → service B
     * Header/query string/method-based routing
   - Supports WebSocket and gRPC natively.
   - Native integration with ECS (auto-registers tasks), EKS, Lambda targets.
   - SSL/TLS termination at the ALB (offloads from app servers).
   - Returns 503 if no healthy targets in any AZ.
   Use for: Web applications, REST APIs, microservices, any HTTP workload.

   NLB (Network Load Balancer): Layer 4 — TCP/UDP/TLS.
   - Handles millions of requests per second with ultra-low latency (~microseconds).
   - Static IP per Availability Zone (useful for IP whitelisting by clients).
   - Preserves client source IP (ALB replaces it with its own IP).
   - No HTTP-level awareness — just raw TCP/UDP forwarding.
   - TLS termination supported (NLB can decrypt, or pass-through to target).
   Use for: Gaming, IoT, real-time streaming, VoIP, any non-HTTP protocol,
            when client needs to know its source IP, or when static IPs are required.

   Key interview point: ALB for HTTP workloads, NLB for TCP/UDP or performance-critical.
   You can put NLB in front of ALB when you need static IPs + HTTP routing.

Q5: How does Lambda handle concurrency? Explain reserved vs. provisioned concurrency.

A: Default concurrency limit: 1,000 concurrent executions per region (soft limit,
   increase via AWS Support).

   How Lambda scales:
   - Each concurrent invocation gets its own execution environment.
   - Lambda scales out in "bursts" of 500–3,000 new instances per minute (region-dependent).
   - Beyond burst limit: scales by 500/minute until hitting the concurrency limit.

   Reserved Concurrency:
   - Sets a MAXIMUM for a specific function.
   - Effect 1: That function cannot exceed this limit (throttles beyond it).
   - Effect 2: This capacity is reserved — other functions cannot use it.
   - Cost: Free.
   - Use to:
     * Protect downstream services (e.g., keep database connections manageable).
     * Prevent one noisy function from consuming all regional concurrency.
     * Isolate a critical function's capacity from the rest of the account.
   - Setting reserved concurrency to 0 disables the function (useful for emergency stop).

   Provisioned Concurrency:
   - Pre-initializes N execution environments.
   - These are always warm — zero cold start latency.
   - Cost: you pay per GB-hour of provisioned capacity, even when idle.
   - Use for: latency-sensitive production APIs (user-facing endpoints).
   - Can be combined with Auto Scaling (scale provisioned concurrency with Application Auto Scaling
     based on schedule or CloudWatch alarms).

   Unreserved Concurrency:
   - The pool shared by all functions that do NOT have reserved concurrency.
   - AWS recommends keeping at least 100 unreserved for account-wide operations.

Q6: What is Fargate? How does it differ from ECS with EC2 launch type?

A: ECS EC2 launch type:
   - You provision, manage, patch, and right-size the underlying EC2 instances.
   - You choose instance types (optimize for CPU/memory/GPU).
   - You manage cluster capacity (scale EC2 nodes when out of capacity for new tasks).
   - Lower per-vCPU cost than Fargate for high, sustained utilization.
   - More operational overhead. Need to manage ECS container agent, AMIs, node ASGs.

   ECS Fargate:
   - Serverless containers — AWS manages the underlying infrastructure entirely.
   - You define only CPU and memory for each task (e.g., 0.5 vCPU, 1 GB).
   - No EC2 instances to patch, manage, or right-size.
   - Pay per task CPU/memory per second (no idle EC2 cost).
   - Faster to get started. Less operational burden.
   - Slightly higher cost per vCPU than EC2 for sustained high utilization.
   - Use for: teams that want containers without infrastructure management.

   When to prefer EC2 launch type:
   - Very high, sustained container density (cost optimization).
   - Need specific instance types (GPU, high memory, burstable).
   - Need to mount instance store NVMe volumes.

   EKS also supports Fargate nodes (Fargate profiles) with the same tradeoff.
