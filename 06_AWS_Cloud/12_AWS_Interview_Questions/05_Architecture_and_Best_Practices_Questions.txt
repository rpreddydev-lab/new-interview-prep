================================================================
AWS INTERVIEW QUESTIONS — ARCHITECTURE AND BEST PRACTICES
================================================================

Q1: What is the AWS Well-Architected Framework?

A: Six pillars for designing reliable, secure, efficient, cost-effective cloud systems.

   1. OPERATIONAL EXCELLENCE:
      - Perform operations as code (IaC, runbooks, automation).
      - Make frequent, small, reversible changes (not big-bang deployments).
      - Anticipate failure — test failure scenarios (chaos engineering, Game Days).
      - Learn from all operational events and failures (blameless postmortems).
      Key services: CloudFormation, CodePipeline, CloudWatch, AWS Config.

   2. SECURITY:
      - Implement a strong identity foundation (least privilege, MFA, no long-term keys).
      - Enable traceability (CloudTrail for API calls, VPC Flow Logs, CloudWatch Logs).
      - Apply security at every layer (edge, VPC, subnet, OS, application, data).
      - Protect data in transit (TLS) and at rest (KMS encryption).
      - Automate security best practices (AWS Config rules, GuardDuty, Security Hub).
      - Prepare for security events (IR runbooks, incident response simulations).

   3. RELIABILITY:
      - Automatically recover from failure (Auto Scaling, Multi-AZ, health checks).
      - Test recovery procedures (chaos engineering, simulate AZ failure).
      - Scale horizontally to increase aggregate availability.
      - Stop guessing capacity — use Auto Scaling based on demand metrics.
      - Manage change through automation (no manual server changes).

   4. PERFORMANCE EFFICIENCY:
      - Democratize advanced technology (use managed services, not self-managed).
      - Go global in minutes (CloudFront, Route53 latency routing, multi-region).
      - Use serverless architectures (Lambda, Fargate, DynamoDB on-demand).
      - Experiment frequently — easy to try new instance types, architectures.
      - Use the right tool for the job (DynamoDB for key-value, RDS for relational).

   5. COST OPTIMIZATION:
      - Implement cloud financial management (tagging, cost allocation, budgets).
      - Adopt a consumption model (pay for what you use, scale to zero when idle).
      - Measure overall efficiency (cost per transaction, not just total bill).
      - Stop spending on undifferentiated heavy lifting (use managed services).
      - Analyze and attribute expenditure (Cost Explorer, AWS Cost and Usage Report).
      Key tools: Savings Plans, Reserved Instances, Spot Instances, Compute Optimizer.

   6. SUSTAINABILITY:
      - Minimize environmental impact.
      - Right-size workloads — idle resources waste energy.
      - Use managed services (better hardware utilization than self-managed).
      - Use regions with renewable energy commitments.
      - Adopt modern, efficient technology (Graviton instances use 60% less energy).

Q2: What is the AWS Shared Responsibility Model?

A: Defines the security responsibilities split between AWS and the customer.

   AWS is responsible FOR THE CLOUD:
   - Physical security of data centers (guards, biometric access, surveillance).
   - Hardware (servers, networking equipment, storage).
   - Hypervisor and virtualization layer.
   - Global network infrastructure.
   - Managed service infrastructure: AWS patches the OS on RDS instances,
     manages Lambda runtime updates, maintains DynamoDB hardware.

   Customer is responsible IN THE CLOUD:
   - OS patching (for EC2 — you manage the guest OS).
   - Application security (code vulnerabilities, authentication, authorization).
   - Data encryption at rest (KMS, enable per-service encryption).
   - Data encryption in transit (TLS/HTTPS, enforce at ALB and application layer).
   - IAM configuration (who can access what, least privilege, MFA enforcement).
   - Network configuration (VPC, Security Groups, NACLs, firewall rules).
   - Data backup and recovery (RDS backup retention, S3 versioning, DynamoDB backups).
   - Guest OS on EC2 (patching, anti-malware, hardening).

   The boundary shifts by service type:
   - IaaS (EC2): customer manages most things (OS, runtime, application, data).
   - PaaS (RDS, Elastic Beanstalk): AWS manages more (OS, patching, HA); customer manages app and data.
   - SaaS/Serverless (S3, Lambda, DynamoDB): AWS manages most of the stack; customer manages access control and data.

   Interview tip: "As you move from IaaS to SaaS, AWS takes on more responsibility,
   but the customer always retains responsibility for their data and access control."

Q3: What is the difference between SQS, SNS, and EventBridge? When to use each?

A: SQS (Simple Queue Service): Point-to-point message queue.
   - Model: One producer → queue → one consumer (or multiple competing consumers).
   - Pull-based: consumers POLL for messages (short polling or long polling).
   - Persistence: messages persist until consumed (retention: up to 14 days).
   - Standard queue: at-least-once delivery, best-effort ordering. Can duplicate.
   - FIFO queue: exactly-once delivery, strict ordering. Lower throughput (up to 3,000 msg/s).
   - Visibility timeout: message hidden from other consumers while being processed.
     If not deleted within the timeout, it becomes visible again (retry).
   - Dead Letter Queue (DLQ): failed messages routed here after N retries.
   Use for: Decouple producers from consumers, task queues, worker pools,
            rate-limiting downstream processing, reliable async job execution.

   SNS (Simple Notification Service): Pub/Sub fan-out.
   - Model: One message → one topic → MANY subscribers simultaneously.
   - Push-based: SNS delivers to all subscribers immediately.
   - Subscribers: SQS queues, Lambda functions, HTTP/HTTPS endpoints, email, SMS.
   - No persistence: if a subscriber is unavailable, the message is lost
     (unless the subscriber is an SQS queue, which buffers it).
   - Message filtering: subscribers can filter by message attributes.
   Use for: Fan-out (one event to many services), alerts, notifications, audit logging
            across multiple systems, triggering parallel workflows.
   Pattern: SNS → multiple SQS queues = resilient pub/sub fan-out.

   EventBridge: Event bus with content-based routing.
   - Model: Event sources → event bus → rules match events → route to targets.
   - Rules: filter events by source, detail-type, or any field in the event payload (JSON).
   - Event sources: 200+ AWS services, SaaS partners (Datadog, Zendesk, Stripe), custom apps.
   - Targets: Lambda, SQS, SNS, Step Functions, API Gateway, another event bus, Kinesis.
   - Schema registry: discover and document event schemas.
   - Event replay: archive events and replay them (for DR or debugging).
   - Pipes: point-to-point integration with filtering, transformation, enrichment.
   Use for: Event-driven microservices decoupling, reacting to AWS service events
            (EC2 state change, ECS task stopped, CodePipeline status), SaaS event integration,
            audit-driven workflows.

   Quick decision guide:
   - Simple queue + decouple one service from one service → SQS
   - One event needs to trigger MANY services → SNS or EventBridge
   - Need content-based routing with complex rules → EventBridge
   - React to AWS service events (EC2, RDS, CodePipeline events) → EventBridge
   - SaaS events (Salesforce, Stripe) → EventBridge

Q4: How would you design a fault-tolerant, highly available 3-tier web application on AWS?

A: Architecture:

   EDGE / GLOBAL LAYER:
   - Route 53 with health checks + latency routing.
   - CloudFront for static assets (HTML, JS, CSS, images) → S3 origin.
   - WAF attached to CloudFront/ALB for DDoS and OWASP protection.

   PRESENTATION TIER (Public Subnets — 2+ AZs):
   - Application Load Balancer spanning all public subnets across AZs.
   - ALB handles SSL termination (ACM certificate).
   - ALB health checks on /health endpoint.

   APPLICATION TIER (Private Subnets — 2+ AZs):
   - Auto Scaling Group of EC2 or ECS Fargate tasks in private subnets.
   - Min 2 instances / 2 AZs for HA. ASG scales on CPU or custom metrics.
   - IAM Role on instances/tasks (no hardcoded credentials).
   - Target Group: ALB routes only to healthy app instances.
   - Session state in ElastiCache Redis (not on-instance — instances are stateless).

   DATA TIER (Isolated Subnets — 2+ AZs):
   - RDS Multi-AZ PostgreSQL/MySQL in isolated subnets.
   - Security Group: only App SG can connect on port 5432/3306.
   - Automated backups + point-in-time recovery.
   - DB credentials in AWS Secrets Manager (not environment variables).
   - ElastiCache Redis cluster for application caching.

   CROSS-CUTTING:
   - VPC Gateway Endpoints for S3 and DynamoDB (free, avoids NAT for those services).
   - VPC Interface Endpoints for Secrets Manager (Lambda/ECS fetch secrets privately).
   - CloudWatch for metrics, logs, alarms + Auto Scaling policies.
   - CloudTrail for API audit log (who did what, when).
   - AWS Config for compliance rules (e.g., "all S3 buckets must have encryption").
   - Backups via AWS Backup for RDS, EBS, EFS, DynamoDB.

Q5: How do you manage secrets (DB passwords, API keys) in AWS?

A: NEVER hardcode secrets in code, config files, or environment variables in plaintext.

   AWS Secrets Manager (primary choice):
   - Stores any secret: DB passwords, API keys, OAuth tokens, SSH keys.
   - Automatic rotation for RDS/Aurora credentials (built-in Lambda rotation function).
   - Fine-grained IAM policies: only the specific role that needs the secret can retrieve it.
   - Audit: CloudTrail logs every GetSecretValue call (who, when, from where).
   - Cross-account: share secrets across accounts via resource-based policies.
   - Cost: $0.40/secret/month + $0.05 per 10,000 API calls.

   SSM Parameter Store (secondary / free tier):
   - Standard parameters: free. SecureString type: encrypted with KMS.
   - No automatic rotation. Lower cost for non-sensitive config + simple secrets.
   - Use for: application config (feature flags, non-sensitive settings) + basic secrets
     when Secrets Manager cost is a concern.

   Best practice for Spring Boot on AWS (Java interview answer):
   - Use Spring Cloud AWS: property sources that transparently resolve
     /aws-secretsmanager/my-secret or /aws-parameterstore/my-param.
   - At startup: Spring fetches secrets from Secrets Manager, injects into DataSource.
   - No secrets in application.properties. No secrets in Docker environment variables.
   - Rotation: Secrets Manager rotates the DB password; Spring Boot picks it up on
     next restart OR via refresh endpoint (Spring Cloud Config refresh).

   For Lambda:
   - Retrieve secret once per cold start. Cache in a module-level static variable.
   - Refreshing: check Secrets Manager on cache expiry (e.g., every 5 minutes) to pick up rotations.

Q6: What is CloudWatch and how does it fit into AWS observability?

A: CloudWatch is AWS's native observability service covering metrics, logs, alarms, and dashboards.

   CloudWatch Metrics:
   - Time-series numerical data points about AWS resources.
   - EC2 automatically reports: CPUUtilization, NetworkIn/Out, DiskReadOps/WriteOps (5-min default).
   - Detailed monitoring: 1-minute granularity ($0.01/metric/month extra).
   - Custom metrics: push your own data via PutMetricData API (e.g., active_users, order_rate).
   - Metric Math: compute new metrics from existing ones (e.g., error_rate = errors / requests).

   CloudWatch Logs:
   - Centralized log storage and analysis.
   - Log Group: logical container for logs from one application/service.
   - Log Stream: sequence of events from one source (one EC2 instance, one Lambda invocation).
   - Metric Filters: extract metrics from log patterns (count ERROR occurrences → alarm on it).
   - CloudWatch Logs Insights: ad-hoc query language (like SQL) for log analysis.
   - Retention: configurable per log group (1 day to never).
   - Cost: $0.50/GB ingested + $0.03/GB stored/month.

   CloudWatch Alarms:
   - States: OK, ALARM, INSUFFICIENT_DATA.
   - Actions: SNS notification (email, PagerDuty webhook), Auto Scaling policy, EC2 action.
   - Composite Alarms: combine multiple alarms with AND/OR logic.
     (Reduce alarm noise: only alert if BOTH high latency AND high error rate.)

   CloudWatch Dashboards: visualize metrics and alarm state in one view.

   Complementary services for full observability:
   - AWS X-Ray: distributed tracing — trace a request across Lambda, API Gateway, SQS, DynamoDB.
     Shows where latency comes from across services.
   - CloudTrail: API audit log (who called which AWS API, when, from where).
     Not CloudWatch — separate service for compliance and security investigation.
   - AWS Config: configuration history — what was the state of a resource at any point in time.
   - VPC Flow Logs → CloudWatch Logs: network traffic metadata for security analysis.

   Interview tip: distinguish CloudWatch (application/infrastructure metrics and logs)
   from CloudTrail (AWS API audit) from X-Ray (distributed tracing). All three
   together give the full observability picture.
