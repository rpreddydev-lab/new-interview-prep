AWS DEVELOPER TOOLS — CODEBUILD & CODEDEPLOY
Complete Interview Preparation Guide

1. CODEBUILD OVERVIEW
================================================================

  CodeBuild is a fully managed build service:
    - No build servers to provision or maintain
    - Scales automatically — no queue wait
    - Pay per build minute
    - Integrates with CodePipeline, GitHub, GitLab, Bitbucket
    - Supports Docker builds with privileged mode

================================================================
2. BUILDSPEC.YML
================================================================

  The build specification file tells CodeBuild how to build your project.
  Placed at the root of the repository (or specified in project config).
  
  COMPLETE JAVA/MAVEN BUILDSPEC:
  
  version: 0.2
  
  env:
    variables:
      JAVA_HOME: /usr/lib/jvm/java-17-amazon-corretto
    secrets-manager:
      SONAR_TOKEN: prod/sonar/token:sonarToken
    parameter-store:
      DEPLOY_ENV: /myapp/deploy/environment
  
  phases:
    install:
      runtime-versions:
        java: corretto17
      commands:
        - echo "Installing dependencies"
        - mvn dependency:go-offline -q
  
    pre_build:
      commands:
        - echo "Running unit tests"
        - mvn test
        - echo "Running code quality check"
    
    build:
      commands:
        - echo "Build started on $(date)"
        - mvn package -DskipTests
        - echo "Building Docker image"
        - docker build -t $ECR_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
        - aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
        - docker push $ECR_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION
    
    post_build:
      commands:
        - echo "Generating deployment manifest"
        - envsubst < appspec.template.yml > appspec.yml
        - echo "Build completed"
  
  artifacts:
    files:
      - target/myapp.jar
      - appspec.yml
      - scripts/**/*
    discard-paths: no
  
  cache:
    paths:
      - /root/.m2/**/*     # Cache Maven dependencies between builds
  
  reports:
    SurefireReports:
      files:
        - "target/surefire-reports/**/*"
      file-format: JUNITXML

3. CODEBUILD — KEY SETTINGS
================================================================

  BUILD ENVIRONMENT:
    - AWS managed images: amazon/aws-codebuild-standard:7.0 (Amazon Linux 2023)
    - Custom Docker image from ECR or Docker Hub
    - Privileged mode: required for Docker-in-Docker builds
    - Compute types: BUILD_GENERAL1_SMALL, MEDIUM, LARGE, 2XLARGE
  
  ENVIRONMENT VARIABLES:
    - Plain text: exposed in build logs
    - Secrets Manager: secure, not logged
    - Parameter Store: secure, supports hierarchical paths
  
  VPC INTEGRATION:
    - CodeBuild can run inside your VPC
    - Access private resources (RDS, ElastiCache, internal APIs)
    - NAT Gateway required for internet access from VPC build
  
  BUILT-IN ENV VARS:
    CODEBUILD_BUILD_ID              unique build ID
    CODEBUILD_RESOLVED_SOURCE_VERSION  commit SHA
    CODEBUILD_SOURCE_REPO_URL       repository URL
    CODEBUILD_BUILD_SUCCEEDING      1 if succeeding, 0 if failing
    AWS_DEFAULT_REGION              build region
  
  CREATE PROJECT CLI:
  aws codebuild create-project \
    --name my-java-build \
    --source '{"type":"GITHUB","location":"https://github.com/org/repo"}' \
    --artifacts '{"type":"S3","location":"my-artifacts-bucket"}' \
    --environment '{
      "type": "LINUX_CONTAINER",
      "image": "aws/codebuild/standard:7.0",
      "computeType": "BUILD_GENERAL1_MEDIUM",
      "environmentVariables": [
        {"name": "ECR_REPO", "value": "123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp"}
      ]
    }' \
    --service-role arn:aws:iam::123456789012:role/codebuild-role

4. CODEDEPLOY OVERVIEW
================================================================

  CodeDeploy automates application deployments to:
    - EC2 instances (and on-premises servers)
    - Lambda functions
    - ECS services (Blue/Green)
  
  COMPONENTS:
    Application: Logical grouping
    Deployment Group: Target compute (EC2 tag, ASG, Lambda alias, ECS service)
    Deployment Configuration: How to deploy (speed, health check thresholds)
    AppSpec File: Deployment instructions + lifecycle hooks

================================================================
5. APPSPEC.YML (EC2)
================================================================

  version: 0.0
  os: linux
  files:
    - source: /target/myapp.jar
      destination: /opt/myapp/
    - source: /scripts/
      destination: /opt/myapp/scripts/
  
  permissions:
    - object: /opt/myapp
      owner: ec2-user
      group: ec2-user
      mode: 755
  
  hooks:
    BeforeInstall:
      - location: scripts/stop-server.sh
        timeout: 60
    AfterInstall:
      - location: scripts/configure-server.sh
        timeout: 120
    ApplicationStart:
      - location: scripts/start-server.sh
        timeout: 120
    ValidateService:
      - location: scripts/health-check.sh
        timeout: 60

6. DEPLOYMENT CONFIGURATIONS
================================================================

  EC2 / ON-PREMISES:
    CodeDeployDefault.AllAtOnce         All instances simultaneously (fast, risky)
    CodeDeployDefault.HalfAtATime       50% at a time
    CodeDeployDefault.OneAtATime        One instance at a time (slowest, safest)
    Custom: specify minimum healthy hosts (count or percentage)
  
  LAMBDA:
    CodeDeployDefault.LambdaAllAtOnce    Immediate 100% traffic shift
    CodeDeployDefault.LambdaLinear10PercentEvery1Minute    Linear ramp
    CodeDeployDefault.LambdaLinear10PercentEvery10Minutes
    CodeDeployDefault.LambdaCanary10Percent5Minutes   10% for 5 min, then 100%
    CodeDeployDefault.LambdaCanary10Percent30Minutes
  
  ECS:
    Similar canary/linear options as Lambda
    Blue = current task set, Green = new task set

================================================================
7. IN-PLACE vs BLUE/GREEN DEPLOYMENT
================================================================

  IN-PLACE (EC2 only):
    - Deploy to existing instances (stop → update → start)
    - Capacity reduced during deployment
    - Rollback: re-deploy previous version (slower)
    - No extra infrastructure cost
  
  BLUE/GREEN:
    - Create new instances (Green), deploy to them
    - Shift traffic from Blue to Green (via ALB target group swap)
    - Blue remains running for fast rollback
    - Extra cost while both fleets running
    - Zero downtime, instant rollback
  
  LAMBDA BLUE/GREEN (aliases):
    - Blue = current Lambda alias version
    - Green = new version with weighted alias
    - Shift traffic gradually (canary) and rollback instantly
    - CloudWatch alarm auto-rollback: if alarm triggers during deployment,
      CodeDeploy reverts traffic to 100% Blue

================================================================
8. LIFECYCLE HOOKS (EC2)
================================================================

  Order of hook execution:
  
  ApplicationStop → DownloadBundle → BeforeInstall → Install
  → AfterInstall → ApplicationStart → ValidateService
  
  For Blue/Green:
  BeforeAllowTraffic → AllowTraffic → AfterAllowTraffic

9. CODEDEPLOY — CLI
================================================================

  PUSH APP REVISION TO S3:
  aws deploy push \
    --application-name my-java-app \
    --source my-app-directory/ \
    --s3-location s3://my-deploy-bucket/my-app.zip
  
  CREATE DEPLOYMENT:
  aws deploy create-deployment \
    --application-name my-java-app \
    --deployment-group-name prod-servers \
    --revision '{"revisionType":"S3","s3Location":{"bucket":"my-deploy-bucket","key":"my-app.zip","bundleType":"zip"}}' \
    --deployment-config-name CodeDeployDefault.OneAtATime
  
  GET DEPLOYMENT STATUS:
  aws deploy get-deployment --deployment-id d-XXXXXXXXX

10. INTERVIEW QUESTIONS
================================================================

Q: How does CodeDeploy Blue/Green work with ECS?
A: For ECS Blue/Green:
   1. BLUE: current ECS service task set serving 100% production traffic (ALB)
   2. CodeDeploy registers a new task definition (Green task set) in the same service
   3. The Green task set starts up alongside Blue
   4. CodeDeploy waits for Green tasks to reach RUNNING and health checks pass
   5. BeforeAllowTraffic hook: run integration tests against Green via test listener (port 8080)
   6. ALB shifts traffic from Blue target group to Green target group
      (canary: 10% initially, then 100% — or all at once)
   7. AfterAllowTraffic hook: cleanup tasks, notifications
   8. If CloudWatch alarm fires (e.g., 5xx errors spike) during deployment:
      CodeDeploy auto-rolls back to Blue (traffic reverts to original target group)
   9. Old Blue task set is terminated after successful deployment (or kept for rollback window)

Q: What are the lifecycle event hooks in CodeDeploy and why are they important?
A: Lifecycle hooks allow you to run custom scripts at each deployment stage:
   - BeforeInstall: pre-deployment setup (stop service, backup config, clear cache)
   - AfterInstall: post-install setup (set permissions, config file substitution)
   - ApplicationStart: start the application (systemctl start myapp)
   - ValidateService: run smoke tests/health checks to confirm successful deployment
   
   ValidateService is critical — if the health check fails, CodeDeploy marks the 
   deployment failed and triggers rollback. Without it, CodeDeploy considers any 
   deployment successful as long as files were copied, even if the app didn't start.
   Always implement ValidateService with a real health check endpoint call.

Q: How would you configure CodeBuild to only run if the buildspec exists?
A: CodeBuild requires buildspec.yml by default. You can specify an alternate path:
   - In project config: set buildspecOverride to a specific path
   - Or use CodePipeline conditional execution: add a condition stage using 
     CodeBuild with 'ls buildspec.yml && echo exists || echo missing'
   Alternatively, use GitHub Actions / GitLab CI for the conditional logic before 
   triggering CodeBuild.
