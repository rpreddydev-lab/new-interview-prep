1. SPRING BOOT ON AWS — OVERVIEW
================================================================

  Spring Boot applications on AWS can run on:
    - EC2 (traditional JAR/WAR deployment)
    - Elastic Beanstalk (PaaS, managed EC2)
    - ECS/Fargate (containerized)
    - Lambda (serverless, with Spring Cloud Function or Spring Native)
    - EKS (Kubernetes-managed containers)
  
  Spring Cloud AWS provides auto-configuration for:
    - S3 → Spring Resource abstraction
    - SQS → @SqsListener annotation
    - SNS → notification sending
    - SSM Parameter Store → Spring Environment properties
    - Secrets Manager → Spring Environment properties
    - RDS → auto-configured DataSource with IAM auth
    - DynamoDB → Spring Data-style repository

4. SSM PARAMETER STORE INTEGRATION
================================================================

  Parameters in SSM:
    /order-service/prod/db.url = jdbc:mysql://...
    /order-service/prod/db.username = admin
    /order-service/prod/app.max-connections = 50
  
  Spring application.properties:
    # Reference SSM parameters as Spring properties
    spring.datasource.url=${db.url}
    spring.datasource.username=${db.username}
  
  Or directly in @Value:
  @Value("${db.url}")
  private String dbUrl;
  
  @Value("${app.max-connections}")
  private int maxConnections;
  
  Spring Cloud AWS automatically loads /order-service/prod/* into the 
  Spring Environment on startup (before beans are created).

6. SQS INTEGRATION
================================================================

  LISTENER (auto-polling, managed thread pool):
  import io.awspring.cloud.sqs.annotation.SqsListener;
  
  @Service
  public class OrderEventListener {
  
      @SqsListener("order-processing-queue")
      public void handleOrder(OrderEvent event) {
          // Spring Cloud AWS auto-deserializes JSON → OrderEvent
          // Message ACK (delete) happens automatically on method return
          // Exception → message becomes visible again (retry)
          processOrder(event);
      }
      
      // With access to full SQS message
      @SqsListener("order-dlq")
      public void handleDLQMessage(Message<OrderEvent> message,
                                   @Header("ApproximateReceiveCount") String receiveCount) {
          log.warn("DLQ message received {} times: {}", receiveCount, message.getPayload());
      }
  }
  
  SENDER:
  import io.awspring.cloud.sqs.operations.SqsTemplate;
  
  @Service
  public class OrderService {
  
      private final SqsTemplate sqsTemplate;
  
      public void placeOrder(Order order) {
          sqsTemplate.send("order-processing-queue", order);
          // Serializes order to JSON, sends to SQS
      }
  }

7. S3 INTEGRATION
================================================================

  SPRING RESOURCE ABSTRACTION:
  @Service
  public class FileService {
  
      @Value("s3://my-bucket/reports/")
      private Resource reportResource;
      
      // Read a file from S3 using Spring's familiar Resource API
      public String readReport(String filename) throws IOException {
          Resource report = new UrlResource("s3://my-bucket/reports/" + filename);
          return StreamUtils.copyToString(report.getInputStream(), StandardCharsets.UTF_8);
      }
      
      // Upload
      @Autowired
      private S3Client s3Client;
      
      public void uploadReport(String filename, byte[] content) {
          s3Client.putObject(
              PutObjectRequest.builder()
                  .bucket("my-bucket")
                  .key("reports/" + filename)
                  .build(),
              RequestBody.fromBytes(content)
          );
      }
  }

8. RDS AUTO-CONFIGURATION
================================================================

  Spring Boot auto-configures DataSource from application properties.
  On EC2/ECS with IAM Database Authentication:
  
  application.yml:
    spring:
      datasource:
        url: jdbc:mysql://my-db.cluster.rds.amazonaws.com:3306/mydb
        username: db_user
        driver-class-name: com.mysql.cj.jdbc.Driver
        # NO PASSWORD for IAM auth — token generated programmatically
  
  @Configuration
  public class DataSourceConfig {
      
      @Bean
      public DataSource dataSource() {
          // Generate IAM auth token
          RdsUtilities rdsUtilities = RdsUtilities.builder()
              .region(Region.US_EAST_1)
              .build();
          
          String token = rdsUtilities.generateAuthenticationToken(builder ->
              builder.hostname("my-db.cluster.rds.amazonaws.com")
                     .port(3306)
                     .username("db_user")
          );
          
          // Token valid 15 minutes — need to refresh (use custom DataSource wrapper)
          HikariConfig config = new HikariConfig();
          config.setJdbcUrl("jdbc:mysql://my-db.cluster.rds.amazonaws.com/mydb"
              + "?useSSL=true&requireSSL=true");
          config.setUsername("db_user");
          config.setPassword(token);
          return new HikariDataSource(config);
      }
  }

9. HEALTH CHECKS AND ACTUATOR
================================================================

  Spring Boot Actuator + AWS health checks:
  
  <!-- pom.xml -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
  </dependency>
  
  application.yml:
    management:
      endpoints:
        web:
          exposure:
            include: health, info, metrics, prometheus
      endpoint:
        health:
          show-details: when_authorized
          probes:
            enabled: true   # /actuator/health/liveness + /actuator/health/readiness
  
  ALB/ECS health check: GET /actuator/health → 200 OK (app is ready)
  Kubernetes: liveness → /actuator/health/liveness, readiness → /actuator/health/readiness

10. INTERVIEW QUESTIONS
================================================================

Q: How does Spring Cloud AWS load configuration from SSM Parameter Store?
A: Spring Cloud AWS registers a PropertySource in the Spring Environment before the 
   application context is created (Bootstrap phase or Spring's EnvironmentPostProcessor).
   
   During startup, it calls ssm:GetParametersByPath for the configured prefix 
   (/app-name/profile/) recursively. All parameters are loaded into the Spring 
   Environment with their relative paths as property keys.
   
   /order-service/prod/db.url → property key: db.url
   /order-service/prod/db.username → property key: db.username
   
   These are then injectable via @Value("${db.url}") or @ConfigurationProperties.
   The parameters are loaded once at startup, not refreshed automatically 
   (use Spring Cloud Config with refresh scope for dynamic refresh).

Q: How do you handle SQS message failures in Spring Cloud AWS?
A: @SqsListener behavior on exception:
   - If the handler method throws an exception, Spring Cloud AWS does NOT delete 
     the message from SQS. The message becomes visible again after the Visibility 
     Timeout expires.
   - After MaxReceiveCount retries (configured on queue), message moves to DLQ.
   
   Best practices:
   1. Idempotent processing: design handlers to safely re-process the same message
   2. Catch expected exceptions and either handle or rethrow
   3. Configure a DLQ on the SQS queue for failed messages
   4. Add @SqsListener on a separate method for the DLQ queue — log, alert, manual fix
   5. Use SqsAcknowledgement for manual ack control:
      @SqsListener("queue") void handle(Order order, Acknowledgement ack) {
          try { process(order); ack.acknowledge(); }
          catch (RetryableException e) { /* let it retry */ }
          catch (FatalException e) { ack.acknowledge(); // skip unprocessable messages }
      }

Q: What are the deployment options for Spring Boot on AWS and when to use each?
A: Options by operational complexity:
   1. EC2 directly: Full control, manage OS/JVM/app yourself. For teams with 
      existing EC2 expertise or legacy compatibility.
   2. Elastic Beanstalk: PaaS wrapper for EC2. Upload JAR → Beanstalk handles 
      EC2, ALB, Auto Scaling, CloudWatch. Good for monoliths, team wants simplicity.
   3. ECS/Fargate: Dockerize Spring Boot → ECS manages containers. No EC2 management, 
      per-task IAM roles, easy scaling. Best balance for most teams.
   4. Lambda (Spring Cloud Function): Convert endpoints to functions. Cold start issue 
      mitigated with SnapStart (Java). Best for event-driven or low-traffic use cases.
   5. EKS: Kubernetes for complex microservices with advanced routing, multi-cloud 
      strategy, or existing Kubernetes expertise. Highest operational complexity.
   
   For most Java teams: ECS/Fargate for APIs, Lambda for event processors.
