1. STEP FUNCTIONS — OVERVIEW
================================================================

  AWS Step Functions is a serverless workflow orchestration service.
  It lets you coordinate multiple Lambda functions (or other AWS services)
  into workflows using state machines defined in Amazon States Language (ASL).

  TWO TYPES:
  ┌─────────────────────┬────────────────────────────────────────────────────────┐
  │ Type                │ Description                                            │
  ├─────────────────────┼────────────────────────────────────────────────────────┤
  │ Standard Workflow   │ Exactly-once execution, up to 1 year duration.         │
  │                     │ Full audit history. ~$0.025 per 1,000 state transitions │
  ├─────────────────────┼────────────────────────────────────────────────────────┤
  │ Express Workflow    │ At-least-once execution, up to 5 minutes.              │
  │                     │ High throughput (100,000/sec). Cheaper for short flows. │
  └─────────────────────┴────────────────────────────────────────────────────────┘

  KEY PRINCIPLE:
    Step Functions manages the orchestration logic (retries, error handling,
    branching, parallelism). Each Lambda is a pure "do one thing" unit.
    This keeps Lambda functions simple and individually testable.

================================================================
2. STATE TYPES (Amazon States Language)
================================================================

  ┌──────────────────┬──────────────────────────────────────────────────────────┐
  │ State Type       │ Purpose                                                  │
  ├──────────────────┼──────────────────────────────────────────────────────────┤
  │ Task             │ Invoke a Lambda, ECS task, SQS, SNS, DynamoDB, etc.     │
  │ Choice           │ Branch based on input (if/else logic)                    │
  │ Parallel         │ Run multiple branches simultaneously                     │
  │ Map              │ Process each item in an array (like forEach)             │
  │ Wait             │ Pause for a duration or until a timestamp                │
  │ Pass             │ Pass input to output (useful for testing/reshaping)      │
  │ Succeed          │ Terminate execution successfully                         │
  │ Fail             │ Terminate with an error                                  │
  └──────────────────┴──────────────────────────────────────────────────────────┘

4. JAVA LAMBDA FUNCTIONS IN STEP FUNCTIONS
================================================================

  Each Lambda in a Step Functions workflow receives the STATE INPUT as its
  event and returns the STATE OUTPUT.

  ── VALIDATE ORDER LAMBDA ────────────────────────────────────

  public class ValidateOrderFn implements RequestHandler<OrderInput, OrderResult> {
  
      @Override
      public OrderResult handleRequest(OrderInput input, Context context) {
          // Step Functions passes whatever the previous state output was
          // as this Lambda's input
          
          if (input.getItems() == null || input.getItems().isEmpty()) {
              // Throwing a named exception → Step Functions Catch can handle it
              throw new ValidationException("Order must have at least one item");
          }
          
          // Return value becomes the next state's input
          return OrderResult.builder()
              .orderId(input.getOrderId())
              .validatedAt(Instant.now().toString())
              .status("VALIDATED")
              .build();
      }
  }

  // Custom exception — Step Functions uses the simple class name as the error name:
  public class ValidationException extends RuntimeException {
      public ValidationException(String message) {
          super(message);
      }
  }
  // Step Functions Catch: "ErrorEquals": ["ValidationException"]
  // ↑ Matches the simple class name of the thrown exception

  ── PROCESS PAYMENT LAMBDA ───────────────────────────────────

  public class ProcessPaymentFn implements RequestHandler<OrderResult, PaymentResult> {
  
      private static final PaymentClient PAYMENT_CLIENT = new PaymentClient();
  
      @Override
      public PaymentResult handleRequest(OrderResult input, Context context) {
          try {
              PaymentResponse response = PAYMENT_CLIENT.charge(
                  input.getOrderId(), 
                  input.getTotalAmount()
              );
              return new PaymentResult(input.getOrderId(), response.getStatus());
              
          } catch (PaymentDeclinedException e) {
              // Step Functions catches "PaymentDeclinedException" and routes to OrderFailed
              throw e;
          }
      }
  }

5. INPUT/OUTPUT PROCESSING (InputPath, OutputPath, ResultPath)
================================================================

  These control what data flows between states:

  InputPath:   Selects a subset of the state input to pass to the Task
  ResultPath:  Where to put the Task result in the state data (default: replaces all)
  OutputPath:  Selects a subset of the (merged) state data to pass forward

  EXAMPLE:
  State input: { "orderId": "123", "userId": "u1", "payment": { "amount": 50 } }

  "InputPath": "$.payment"
  → Lambda receives: { "amount": 50 }

  "ResultPath": "$.paymentResult"
  → Full output: { "orderId": "123", "userId": "u1", "payment": {...}, "paymentResult": {...} }

  "ResultPath": null
  → Discard Lambda output, pass original input forward unchanged

  "OutputPath": "$.paymentResult"
  → Next state only sees: { "status": "APPROVED", "transactionId": "txn-456" }

  KEY INTERVIEW POINT:
  Use "ResultPath": "$.error" in Catch handlers to append the error details
  to the state data without losing the original order context.

6. WAIT FOR CALLBACK PATTERN (Human Approval / External System)
================================================================

  Step Functions can pause a workflow until an external system sends a signal.
  Used for: human approval, payment webhook, third-party confirmation.

  JAVA LAMBDA — Sending task token to external system:

  public class WaitForApprovalFn implements RequestHandler<ApprovalRequest, Void> {
  
      private static final SfnClient SFN = SfnClient.create();
      private static final SqsClient SQS = SqsClient.create();
  
      @Override
      public Void handleRequest(ApprovalRequest input, Context context) {
          // input.getTaskToken() — provided by Step Functions
          // Send token to approval system (email, SQS, database)
          
          String taskToken = input.getTaskToken();
          String orderId = input.getOrderId();
          
          // Store token in DynamoDB keyed by orderId
          // Send approval email with a link containing the token
          emailService.sendApprovalEmail(orderId, taskToken);
          
          // Lambda returns — Step Functions workflow PAUSES here
          return null;
      }
  }

  // State definition (Resource: arn:...:states:::lambda:invoke.waitForTaskToken)
  // Step Functions provides context.task.token in the input when you use:
  // "Parameters": { "orderId.$": "$.orderId", "taskToken.$": "$$.Task.Token" }

  APPROVER LAMBDA — Resuming the workflow:

  public class ApproveOrderFn implements RequestHandler<ApproveRequest, String> {
  
      private static final SfnClient SFN = SfnClient.create();
  
      public String handleRequest(ApproveRequest request, Context context) {
          if (request.isApproved()) {
              SFN.sendTaskSuccess(SendTaskSuccessRequest.builder()
                  .taskToken(request.getTaskToken())
                  .output("{\"approved\": true, \"approvedBy\": \"" 
                      + request.getApproverId() + "\"}")
                  .build());
          } else {
              SFN.sendTaskFailure(SendTaskFailureRequest.builder()
                  .taskToken(request.getTaskToken())
                  .error("ApprovalRejected")
                  .cause("Rejected by: " + request.getApproverId())
                  .build());
          }
          return "OK";
      }
  }

7. MAP STATE — PROCESSING ARRAYS WITH JAVA
================================================================

  Map state iterates over an array and processes each item.

  // State definition:
  "ProcessLineItems": {
    "Type": "Map",
    "ItemsPath": "$.lineItems",
    "MaxConcurrency": 5,                  // Max parallel Lambda invocations
    "Iterator": {
      "StartAt": "ProcessItem",
      "States": {
        "ProcessItem": {
          "Type": "Task",
          "Resource": "arn:...:function:ProcessLineItemFn",
          "End": true
        }
      }
    },
    "Next": "AggregateResults"
  }

  // Java Lambda for each item:
  public class ProcessLineItemFn 
      implements RequestHandler<LineItem, LineItemResult> {
      
      @Override
      public LineItemResult handleRequest(LineItem item, Context context) {
          // Each array element arrives as a separate Lambda invocation
          return LineItemResult.builder()
              .itemId(item.getItemId())
              .processedQty(item.getQuantity())
              .build();
      }
  }

8. STARTING A STEP FUNCTIONS EXECUTION FROM JAVA
================================================================

  // Using AWS SDK v2:
  SfnClient sfnClient = SfnClient.builder()
      .region(Region.US_EAST_1)
      .build();

  String stateMachineArn = System.getenv("STATE_MACHINE_ARN");

  StartExecutionRequest request = StartExecutionRequest.builder()
      .stateMachineArn(stateMachineArn)
      .name("order-" + orderId + "-" + System.currentTimeMillis())  // Must be unique
      .input(objectMapper.writeValueAsString(orderInput))
      .build();

  StartExecutionResponse response = sfnClient.startExecution(request);
  String executionArn = response.executionArn();  // Track execution status

  // Async start (returns immediately, workflow runs independently):
  SfnAsyncClient asyncSfn = SfnAsyncClient.create();
  CompletableFuture<StartExecutionResponse> future = 
      asyncSfn.startExecution(request);

9. STEP FUNCTIONS vs OTHER PATTERNS
================================================================

  ┌──────────────────────┬──────────────────────────────────────────────────────┐
  │ When to use          │ Why                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────────┤
  │ Step Functions       │ Multi-step workflows with branching, retries, error  │
  │                      │ handling, parallel steps, human approval, audit trail │
  ├──────────────────────┼──────────────────────────────────────────────────────┤
  │ SQS + Lambda chain   │ Simple async processing, single step or simple fan   │
  │                      │ out. Cheaper but no built-in orchestration/audit.    │
  ├──────────────────────┼──────────────────────────────────────────────────────┤
  │ EventBridge + Lambda │ Event-driven, loose coupling, multiple consumers,    │
  │                      │ no strict ordering needed.                           │
  └──────────────────────┴──────────────────────────────────────────────────────┘

  INTERVIEW RULE: Use Step Functions when you need to see the full state of 
  a long-running business process (order, loan application, user onboarding) 
  and manage errors/retries centrally rather than in each Lambda.

10. INTERVIEW QUESTIONS
================================================================

Q: What is Step Functions and when would you use it over chaining Lambda with SQS?

A: Step Functions is a serverless workflow orchestrator that manages state, 
   retries, error handling, and branching between steps. Use it over SQS chains 
   when: you need a full audit trail of each step (visible in console), you have 
   branching logic (Choice states), you need parallel execution coordination 
   (Parallel/Map states), or you need human approval (waitForTaskToken pattern). 
   SQS chains are cheaper and simpler for basic async pipelines but lack 
   centralized error management and visibility.

---

Q: How does error handling work in Step Functions?

A: Each Task state can define Retry and Catch blocks.
   Retry: retries on specified errors with exponential backoff (IntervalSeconds, 
   BackoffRate, MaxAttempts). Catch: routes to a different state when retries are 
   exhausted. The error name matches the Java exception's simple class name. 
   Use ResultPath in Catch to preserve the original input while appending error 
   details. This lets later steps (like a compensation/cleanup Lambda) know both 
   what the original order was AND what went wrong.

---

Q: Explain the waitForTaskToken pattern. When would you use it?

A: waitForTaskToken pauses the workflow until an external system calls 
   SendTaskSuccess or SendTaskFailure with the task token. Step Functions 
   provides a unique task token in the state input (via $$.Task.Token context 
   path). Use cases: human approval workflows (manager must approve a loan), 
   waiting for a third-party webhook (payment processor callback), or coordinating 
   with legacy systems that can't be called synchronously. The key advantage over 
   polling: no Lambda running (no cost) while waiting.

---

Q: Standard vs Express workflows — which do you choose and why?

A: Standard: exactly-once semantics, up to 1 year, full audit history in console. 
   Use for business-critical workflows (order processing, loan approval) where 
   you need guaranteed execution and an audit trail.
   Express: at-least-once semantics, up to 5 minutes, high throughput (100k/sec). 
   Use for high-volume, short-duration workflows (IoT data transformation, 
   real-time stream processing) where throughput matters more than audit history. 
   For Java microservices: typically Standard for business workflows, Express for 
   data processing pipelines.
