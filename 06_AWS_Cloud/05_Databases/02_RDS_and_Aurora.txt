================================================================
AWS DATABASES — RDS AND AURORA
Complete Interview Preparation Guide
================================================================

1. AMAZON RDS OVERVIEW
================================================================

  Amazon RDS (Relational Database Service) is a managed OLTP relational
  database service. AWS handles:
    - Hardware provisioning
    - Database software installation and patching
    - Automated backups and point-in-time recovery
    - High availability and failover
    - Performance monitoring (Enhanced Monitoring, Performance Insights)
  
  YOU manage:
    - Schema design and queries
    - Parameter groups (DB engine configuration)
    - VPC placement and security groups
    - Instance sizing

  SUPPORTED ENGINES:
    - MySQL          (community edition)
    - PostgreSQL     (open source)
    - MariaDB        (MySQL fork)
    - Oracle         (bring your own license or license-included)
    - Microsoft SQL Server (license-included editions)
    - Amazon Aurora MySQL / Aurora PostgreSQL (AWS-built, fastest)

================================================================
2. RDS DEPLOYMENT OPTIONS
================================================================

  SINGLE-AZ DEPLOYMENT:
    - One DB instance in one AZ
    - No automatic failover
    - Lowest cost
    - Use for: dev/test environments

  MULTI-AZ DEPLOYMENT (High Availability):
    - Synchronous replication to standby in another AZ
    - Automatic failover (1–2 minutes) if primary fails
    - Standby is NOT accessible for reads (only failover)
    - DNS endpoint is the same — applications reconnect automatically
    - Use for: production workloads

  READ REPLICAS (Horizontal Read Scaling):
    - Asynchronous replication (eventual consistency)
    - Can have UP TO 5 read replicas per DB
    - Read replicas can be in: same AZ, cross-AZ, or cross-region
    - Each has its own DNS endpoint
    - Can be promoted to standalone DB (breaks replication)
    - Use for: offload read-heavy queries, analytics, reporting

  MULTI-AZ vs READ REPLICA:
  ┌───────────────────┬──────────────────────────────┬──────────────────────────────┐
  │ Feature           │ Multi-AZ                     │ Read Replica                 │
  ├───────────────────┼──────────────────────────────┼──────────────────────────────┤
  │ Purpose           │ High availability (failover) │ Read scalability             │
  │ Replication       │ Synchronous                  │ Asynchronous                 │
  │ Accessibility     │ Standby NOT readable         │ Readable (separate endpoint) │
  │ Failover          │ Automatic                    │ Manual promote               │
  │ Regions           │ Same region (different AZ)   │ Can be cross-region          │
  │ Use case          │ Production HA                │ Read scaling, reporting       │
  └───────────────────┴──────────────────────────────┴──────────────────────────────┘

================================================================
3. RDS STORAGE
================================================================

  Storage types:
    gp2 (General Purpose SSD): 100-3000 IOPS based on size, burstable
    gp3 (General Purpose SSD): 3000 IOPS baseline, can provision more
    io1 (Provisioned IOPS):    100-64,000 IOPS, for high I/O workloads
    Magnetic:                  Legacy, not recommended

  Storage Auto-Scaling:
    - Automatically increases storage when capacity < 10%
    - No downtime, no manual intervention
    - Set a Maximum Storage Threshold to control costs
    - Enabled by default; can disable if needed

================================================================
4. RDS BACKUPS
================================================================

  AUTOMATED BACKUPS:
    - Daily full backup during maintenance window
    - Transaction logs saved every 5 minutes
    - Retention: 0–35 days (default: 7 days)
    - When enabled: supports POINT-IN-TIME RECOVERY (PITR)
      → Restore to any second within the retention period

  DB SNAPSHOTS:
    - Manual, user-triggered
    - Retained indefinitely (until you delete them)
    - Can copy snapshots to another region (DR)
    - Can share snapshots with other AWS accounts
    - Restoring = creates a NEW DB instance (doesn't overwrite)

  Restore creates a NEW DB instance:
  aws rds restore-db-instance-from-db-snapshot \
    --db-instance-identifier new-db \
    --db-snapshot-identifier my-snapshot

  PITR restore:
  aws rds restore-db-instance-to-point-in-time \
    --source-db-instance-identifier prod-db \
    --target-db-instance-identifier prod-db-restored \
    --restore-time "2024-01-15T12:00:00Z"

================================================================
5. RDS SECURITY
================================================================

  ENCRYPTION AT REST:
    - KMS encryption (AES-256)
    - Must be enabled at creation time (cannot enable on existing DB)
    - If DB is encrypted, its snapshots, backups, read replicas are encrypted
    - To encrypt an existing unencrypted DB:
        1. Take a snapshot
        2. Copy the snapshot with encryption enabled
        3. Restore from the encrypted snapshot → new encrypted DB
        4. Switch traffic to new encrypted DB

  ENCRYPTION IN TRANSIT:
    - SSL/TLS for all connections
    - Enforce SSL:
        MySQL: REQUIRE SSL in user account
        PostgreSQL: SET rds.force_ssl = 1 in parameter group

  NETWORK SECURITY:
    - Always deploy in a private subnet (no public access)
    - Security Groups control inbound access (port 3306 for MySQL, 5432 for PG)
    - IAM database authentication (MySQL/PostgreSQL only):
        Generate IAM auth token instead of password
        Token valid for 15 minutes
        aws rds generate-db-auth-token --hostname rds-host --port 3306 --username dbuser

6. AURORA OVERVIEW
================================================================

  Aurora is AWS's proprietary, high-performance relational database.
  MySQL and PostgreSQL compatible (drop-in replacement).
  
  Why Aurora?
    - 5x performance over MySQL, 3x over PostgreSQL (AWS claim)
    - Storage auto-scales from 10GB to 128TB automatically (no downtime)
    - Up to 15 read replicas (vs 5 for RDS MySQL)
    - < 30ms replica lag (vs asynchronous for RDS)
    - Automatic failover in < 30 seconds (vs 1–2 min for RDS Multi-AZ)

================================================================
7. AURORA ARCHITECTURE
================================================================

  SHARED CLUSTER STORAGE:
    - Single shared storage volume (6 copies of data across 3 AZs)
    - Write quorum: 4 out of 6 copies for write success
    - Read quorum: 3 out of 6 copies
    - Self-healing: corrupted blocks auto-replaced
    - NO replication lag (all instances read from same storage)

                         ┌─────────────────────────────────────────┐
                         │         Shared Aurora Storage            │
                         │    (6 copies across 3 AZs: 2 per AZ)   │
                         │     auto-scales from 10GB to 128TB      │
                         └──────────┬──────────────────────────────┘
                                    │
                     ┌──────────────┴──────────────────────┐
             ┌───────┴───────┐                   ┌─────────┴────────┐
             │  Writer/Primary│                   │  Readers (1–15)  │
             │ (Read + Write) │                   │  (Read Only)     │
             └───────────────┘                   └──────────────────┘

  AURORA ENDPOINTS:
    Cluster Endpoint:       Always points to the writer instance
    Reader Endpoint:        Load-balances across all read replicas
    Custom Endpoint:        You define a subset of instances
    Instance Endpoint:      Connects to a specific instance

  FAILOVER:
    - If writer fails, Aurora automatically promotes a read replica
    - Failover < 30 seconds (data already on shared storage, no data loss)
    - Priority tiers (0-15): lower tier replicas promoted first

================================================================
8. AURORA SERVERLESS
================================================================

  Aurora Serverless v2:
    - Automatically scales Aurora instances up/down instantly
    - Scales in 0.5 ACU increments (1 ACU = ~2GB RAM + proportional CPU)
    - Min 0.5 ACU, Max 128 ACU
    - Pay only for ACUs consumed (per second billing)
    - No capacity planning needed
    - Supports Multi-AZ
    - Use case: Variable/unpredictable workloads, dev/test, new applications

  Aurora Serverless v1 (older):
    - Scales in coarser increments
    - Can scale to 0 (pauses after idle period — cold start on next connection)
    - Does NOT support Multi-AZ

================================================================
9. AURORA GLOBAL DATABASE
================================================================

  For globally distributed applications requiring:
    - Low latency reads in multiple regions
    - Disaster recovery with RPO ~1 second, RTO ~1 minute

  Architecture:
    Primary Region:    One writer + up to 15 readers
    Secondary Regions: Up to 5 secondary regions (up to 16 readers each)
    Replication lag:   < 1 second (physical replication at storage level)
    
  In disaster: Promote a secondary region to primary (removes replication lag < 1 min)

  aws rds create-global-cluster \
    --global-cluster-identifier my-global-cluster \
    --source-db-cluster-identifier arn:aws:rds:us-east-1:123456789012:cluster:prod-aurora

10. RDS PARAMETER GROUPS AND OPTION GROUPS
================================================================

  PARAMETER GROUP:
    - Contains database engine configuration parameters (e.g., max_connections,
      innodb_buffer_pool_size for MySQL)
    - Default parameter group is read-only — create a custom one to modify
    - Dynamic parameters: apply immediately
    - Static parameters: require DB restart

  OPTION GROUP:
    - Some engines support optional features (e.g., Oracle TDE, SQL Server Transparent
      Data Encryption, Oracle APEX)
    - Use option groups to enable/configure these

  SUBNET GROUP:
    - Defines which subnets in your VPC the DB can be placed in
    - Always use private subnets — never place DB in public subnet

================================================================
11. RDS MONITORING
================================================================

  BASIC METRICS (every 1 minute):
    - CPU Utilization
    - DB Connections
    - Free Storage Space
    - Read/Write IOPS and Latency

  ENHANCED MONITORING (every 1 second):
    - OS-level metrics (CPU steal, memory processes)
    - Agent runs on DB instance
    - Logs to CloudWatch Logs

  PERFORMANCE INSIGHTS:
    - Visualizes database load
    - Shows top SQL queries by wait time
    - Shows waits by resource (CPU, I/O, locks)
    - Free tier: 7 days retention; paid: up to 2 years
    - Available for MySQL, PostgreSQL, Aurora

12. JAVA SDK v2 — RDS CONNECTION
================================================================

  RDS is accessed via standard JDBC — not via SDK directly.
  Use IAM auth token for passwordless connection:

  import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;
  import software.amazon.awssdk.regions.Region;
  import software.amazon.awssdk.services.rds.RdsUtilities;
  import software.amazon.awssdk.services.rds.model.GenerateAuthenticationTokenRequest;
  
  RdsUtilities utilities = RdsUtilities.builder()
      .region(Region.US_EAST_1)
      .credentialsProvider(DefaultCredentialsProvider.create())
      .build();
  
  String authToken = utilities.generateAuthenticationToken(
      GenerateAuthenticationTokenRequest.builder()
          .hostname("my-db.cluster-xyz.us-east-1.rds.amazonaws.com")
          .port(3306)
          .username("db_user")
          .build()
  );
  
  // Use authToken as the JDBC password
  String jdbcUrl = "jdbc:mysql://my-db.cluster-xyz.us-east-1.rds.amazonaws.com:3306/mydb"
                 + "?useSSL=true&requireSSL=true";
  Connection conn = DriverManager.getConnection(jdbcUrl, "db_user", authToken);

13. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between RDS Multi-AZ and Read Replicas?
A: Multi-AZ is for HIGH AVAILABILITY — synchronous replication to a standby in
   another AZ; standby is NOT readable. Automatic failover in 1–2 minutes when primary
   fails. Read Replicas are for SCALABILITY — asynchronous replication to readable
   replicas. No automatic failover; promote manually if primary fails. Use Multi-AZ
   to survive failures; use Read Replicas to scale read-heavy workloads.

Q: How does Aurora differ from RDS MySQL?
A: Same MySQL/PostgreSQL compatibility, but Aurora has: shared storage that auto-scales
   to 128TB (vs fixed provisioned in RDS), up to 15 read replicas vs 5, failover in
   < 30 seconds vs 1–2 min, < 1ms replica lag vs asynchronous replication, 6 copies of
   data across 3 AZs by default, and significantly better performance. Aurora is more
   expensive (~20% more than RDS MySQL) but delivers 5x better performance.

Q: How would you encrypt an existing unencrypted RDS database?
A: You CANNOT encrypt an existing RDS DB in-place. The process:
   1. Create a snapshot of the unencrypted DB
   2. Copy the snapshot, selecting KMS encryption during the copy
   3. Restore a new DB instance from the encrypted snapshot
   4. Update application connection strings to point to the new DB
   5. Delete the old unencrypted DB and snapshot

Q: What is Aurora Serverless and when would you use it?
A: Aurora Serverless v2 automatically scales the database capacity (in 0.5 ACU
   increments) based on actual workload. No upfront capacity planning needed and
   you pay per second for actual usage. Use it for: variable or unpredictable
   workloads, dev/test environments, new applications where you're unsure of scale,
   infrequently used applications. Don't use for: steady high-traffic production where
   you'd pay more than fixed provisioning.

Q: What is the Aurora Shared Storage Architecture?
A: Aurora doesn't replicate data block by block like RDS. It writes to a shared
   storage layer that maintains 6 copies of data across 3 AZs (2 per AZ). Writes
   succeed when 4/6 copies acknowledge. Reads only need 3/6. This means: no
   replication lag (all instances read from same storage), instant failover (new
   primary reads same storage), and storage heals itself from corruption automatically.
