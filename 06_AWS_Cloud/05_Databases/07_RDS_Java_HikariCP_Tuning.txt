AWS FOR JAVA DEVELOPERS — RDS, HIKARICP, AND CONNECTION POOLING
Complete Interview Preparation Guide

1. THE CONNECTION POOL PROBLEM ON AWS
================================================================

  In a traditional on-premise setup:
  - Fixed number of app servers → fixed connection pool → DB handles it fine

  On AWS (ECS/Lambda/EKS — elastic compute):
  - ECS can scale from 2 → 50 tasks in minutes
  - Each task has its own HikariCP connection pool (e.g., 10 connections each)
  - 50 tasks × 10 connections = 500 connections to RDS
  - RDS max_connections is limited by instance size (db.t3.medium ≈ 90 connections)
  - RESULT: "too many connections" errors, connection timeouts, app failures

  THIS IS THE #1 RDS PROBLEM in Java cloud applications at senior level.

================================================================
2. RDS MAX_CONNECTIONS BY INSTANCE CLASS
================================================================

  RDS PostgreSQL: max_connections ≈ LEAST(DBInstanceClassMemory/9531392, 5000)
  RDS MySQL:      max_connections ≈ DBInstanceClassMemory/12582880

  Approximate values:
  ┌──────────────────┬────────────────────────────┬─────────────────────────────┐
  │ Instance Class   │ Memory                     │ Approx max_connections      │
  ├──────────────────┼────────────────────────────┼─────────────────────────────┤
  │ db.t3.micro      │ 1 GB                       │ ~87                         │
  │ db.t3.medium     │ 4 GB                       │ ~416                        │
  │ db.r5.large      │ 16 GB                      │ ~1638                       │
  │ db.r5.xlarge     │ 32 GB                      │ ~3276                       │
  │ db.r5.4xlarge    │ 128 GB                     │ ~5000 (capped)              │
  └──────────────────┴────────────────────────────┴─────────────────────────────┘

  RULE: Always keep total connections well below max_connections.
  Target: max 80% of max_connections (leave headroom for admin connections).

3. HIKARICP — TUNING FOR AWS RDS
================================================================

  HikariCP is the default connection pool in Spring Boot.

  ── SPRING BOOT CONFIG (application.yml) ──────────────────────

  spring:
    datasource:
      url: jdbc:postgresql://${DB_HOST}:5432/mydb
      username: ${DB_USER}
      password: ${DB_PASSWORD}
      driver-class-name: org.postgresql.Driver
      hikari:
        # POOL SIZING
        maximum-pool-size: 5          # Max connections per app instance
        minimum-idle: 2               # Keep at least 2 idle connections warm
        
        # TIMEOUT SETTINGS
        connection-timeout: 30000     # 30s — max time to wait for a connection from pool
        idle-timeout: 600000          # 10 min — remove idle connections (below minimum-idle)
        max-lifetime: 1800000         # 30 min — max connection lifetime (rotate before RDS timeout)
        keepalive-time: 60000         # 60s — send keepalive to prevent firewall timeout
        
        # VALIDATION
        connection-test-query: SELECT 1     # For drivers that don't support isValid()
        validation-timeout: 5000            # 5s max for validation
        
        # NAMING (for monitoring)
        pool-name: OrderServicePool
        
        # LEAK DETECTION (for debugging only — disable in prod)
        leak-detection-threshold: 60000     # Warn if connection held > 60s

  ── SIZING FORMULA ────────────────────────────────────────────

  Recommended pool size per application instance:
  
  Formula (from HikariCP docs):
  pool_size = Tn × (Cm - 1) + 1
  Where: Tn = number of threads, Cm = max time to complete a query
  
  Practical rule for most Java services:
  pool_size = ceil(desired_concurrent_db_operations / number_of_app_instances)
  
  EXAMPLE:
  - ECS service: max 20 tasks
  - Each task handles 10 concurrent requests, ~50% hit DB = 5 DB ops/task
  - Total needed: 5 connections/task is the peak
  - Set maximum-pool-size: 5
  - Total connections at max scale: 20 × 5 = 100 connections
  - Verify: 100 < 80% of RDS max_connections

  COMMON MISTAKE: Setting maximum-pool-size too high.
  10 tasks × 20 pool = 200 connections "just in case" — wastes DB resources.
  HikariCP author recommendation: pool size should be SMALL (even 4–10).

4. RDS PROXY — THE SCALABILITY SOLUTION
================================================================

  RDS Proxy sits between your app and RDS, providing connection multiplexing.

  HOW IT WORKS:
    App → RDS Proxy (manages many app connections) → RDS (small pool)
    
    1,000 app connections → RDS Proxy → 20 RDS connections
    
  MULTIPLEXING:
    - RDS Proxy pins app connections to DB connections only when a transaction
      is in progress. Between transactions, it can reuse DB connections for 
      multiple app connections.
    - Result: massively reduces connections to RDS.

  KEY BENEFITS:
  ┌──────────────────────────┬──────────────────────────────────────────────────┐
  │ Benefit                  │ Detail                                           │
  ├──────────────────────────┼──────────────────────────────────────────────────┤
  │ Connection pooling       │ Multiplexes thousands of app connections to few  │
  │                          │ DB connections — solves ECS/Lambda scaling issue  │
  ├──────────────────────────┼──────────────────────────────────────────────────┤
  │ IAM Authentication       │ Apps authenticate to proxy via IAM (no password) │
  ├──────────────────────────┼──────────────────────────────────────────────────┤
  │ Secrets Manager rotation │ Proxy handles DB credential rotation transparent │
  │                          │ to app — no connection drops during rotation     │
  ├──────────────────────────┼──────────────────────────────────────────────────┤
  │ Failover acceleration    │ Reduces Multi-AZ failover time from 20–30s to   │
  │                          │ < 5 seconds (proxy maintains warm connections)   │
  └──────────────────────────┴──────────────────────────────────────────────────┘

  ── USING RDS PROXY WITH JAVA SPRING BOOT ─────────────────────

  // Point Spring Boot to Proxy endpoint (not RDS cluster endpoint):
  spring:
    datasource:
      url: jdbc:postgresql://my-proxy.proxy-xxxx.us-east-1.rds.amazonaws.com:5432/mydb

  // With IAM Authentication (no password — IAM token):
  spring:
    datasource:
      url: jdbc:postgresql://my-proxy.proxy-xxxx.us-east-1.rds.amazonaws.com:5432/mydb?ssl=true
      username: myapp_user        # IAM database user (must be created in RDS)
      password: ${RDS_IAM_TOKEN}  # Generated token — rotates every 15 minutes!

  // Generate IAM auth token (Java):
  public String generateRdsIamToken() {
      RdsUtilities rdsUtilities = RdsUtilities.builder()
          .region(Region.US_EAST_1)
          .build();
      
      return rdsUtilities.generateAuthenticationToken(builder ->
          builder
              .hostname("my-proxy.proxy-xxxx.us-east-1.rds.amazonaws.com")
              .port(5432)
              .username("myapp_user"));
  }
  // This token is valid for 15 minutes — integrate with HikariCP's 
  // DriverManager.getConnection() or a custom DataSource wrapper

  ── LAMBDA WITH RDS PROXY ─────────────────────────────────────

  Lambda + RDS is particularly problematic:
  - Each Lambda invocation creates new connections (no connection reuse across invocations)
  - Lambda can scale to thousands of concurrent executions → thousands of DB connections
  
  WITH RDS PROXY:
  - Lambda connects to RDS Proxy (fast, proxies are in VPC)
  - Proxy multiplexes Lambda connections to small pool of RDS connections
  - BEST PRACTICE: ALL Lambda → RDS connections should go through RDS Proxy

5. MULTI-AZ AND READ REPLICAS IN JAVA APPS
================================================================

  MULTI-AZ (High Availability):
  ──────────────────────────────
    - Synchronous standby in a different AZ
    - Automatic failover: DNS flips to standby in ~20–30s (< 5s with Proxy)
    - Java app: no code change needed — use cluster endpoint, failover is DNS-based
    - COST: 2x storage, extra instance cost — use for production only

  READ REPLICAS (Scale Reads):
  ─────────────────────────────
    - Asynchronous replica — slight read lag (usually < 1 second)
    - Use reader endpoint (RDS cluster) or individual replica endpoints
    - Spring Boot: two DataSources or Spring's AbstractRoutingDataSource

    // AbstractRoutingDataSource — route reads to replica, writes to primary:
    public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {
    
        private static final ThreadLocal<DataSourceType> CONTEXT = new ThreadLocal<>();
    
        public static void setRead() { CONTEXT.set(DataSourceType.READ); }
        public static void setWrite() { CONTEXT.set(DataSourceType.WRITE); }
        public static void clear() { CONTEXT.remove(); }
    
        @Override
        protected Object determineCurrentLookupKey() {
            return CONTEXT.get() != null ? CONTEXT.get() : DataSourceType.WRITE;
        }
    }
    
    // AOP aspect to automatically set context based on @Transactional(readOnly):
    @Aspect
    @Component
    public class DataSourceRoutingAspect {
    
        @Around("@annotation(transactional)")
        public Object routeDataSource(ProceedingJoinPoint jp, 
                                       Transactional transactional) throws Throwable {
            try {
                if (transactional.readOnly()) {
                    ReadWriteRoutingDataSource.setRead();
                } else {
                    ReadWriteRoutingDataSource.setWrite();
                }
                return jp.proceed();
            } finally {
                ReadWriteRoutingDataSource.clear();
            }
        }
    }
    
    // Usage:
    @Transactional(readOnly = true)   // → routed to read replica
    public List<Order> getOrders(String customerId) { ... }
    
    @Transactional                     // → routed to primary write
    public Order createOrder(OrderRequest req) { ... }

6. CONNECTION TROUBLESHOOTING ON AWS
================================================================

  SYMPTOM: "HikariPool-1 - Connection is not available, request timed out after 30000ms"

  DIAGNOSIS CHECKLIST:
  1. Check RDS CloudWatch: DatabaseConnections metric at max?
  2. Check ECS: how many tasks are running? Total connections = tasks × pool size?
  3. Check for connection leaks: connections acquired but not released?
     Enable: leak-detection-threshold: 10000 (temporarily in staging)
  4. Check for long-running transactions holding connections:
     SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction';
  5. Check VPC security groups: port 5432/3306 open from ECS task SG to RDS SG?
  6. Check RDS parameter group: max_connections value?

  MONITORING — CLOUDWATCH METRICS TO WATCH:
    RDS: DatabaseConnections, FreeableMemory, CPUUtilization
    RDS: ReadLatency, WriteLatency, CommitLatency
    App: HikariCP metrics (expose via Spring Boot Actuator + Micrometer):
    
    // application.yml:
    management:
      metrics:
        enable:
          hikaricp: true
    # Exposes: hikaricp.connections.active, .idle, .pending, .timeout
    # Push to CloudWatch via CloudWatch Metrics Exporter or CloudWatch Agent

7. INTERVIEW QUESTIONS
================================================================

Q: You deploy a Spring Boot app on ECS. At low traffic everything works, but 
   when ECS scales to 30 tasks, you start seeing database connection errors. 
   What is happening and how do you fix it?

A: The issue is connection pool exhaustion at the RDS level. Each ECS task has 
   a HikariCP pool (e.g., 10 connections) — 30 tasks × 10 = 300 connections. 
   RDS has a max_connections limit based on instance class (e.g., db.t3.medium 
   allows ~416, but actual usable is ~330 after admin overhead).
   
   Fixes:
   1. Reduce maximum-pool-size per task (e.g., 5 instead of 10).
      30 × 5 = 150 — well within limits.
   2. Enable RDS Proxy — multiplexes app connections to a small pool of RDS 
      connections. Best long-term solution for elastic ECS workloads.
   3. Upgrade RDS instance class for more max_connections headroom.
   4. Review queries: long-running transactions hold connections — fix slow queries.

---

Q: What is RDS Proxy and when should you always use it?

A: RDS Proxy is a fully managed connection proxy that sits between your app and 
   RDS. It multiplexes thousands of app connections to a small pool of RDS 
   connections by pinning connections to DB only during active transactions.
   
   Always use it for:
   - Lambda functions accessing RDS (Lambda can scale to thousands of instances 
     simultaneously — without Proxy this creates thousands of DB connections)
   - Microservices on ECS/EKS that auto-scale
   - Applications requiring IAM database authentication (Proxy handles token management)
   - Applications that need transparent DB credential rotation (no connection drops)
   
   Additional benefit: reduces Multi-AZ failover impact from 20–30 seconds to < 5 seconds.

---

Q: How do you tune HikariCP for a Spring Boot service on ECS Fargate?

A: Key settings:
   1. maximum-pool-size: set small — formula: peak_concurrent_db_ops / num_tasks.
      Typical: 5–10 per task. Verify: total connections < 80% of RDS max_connections.
   2. connection-timeout: 30 seconds — how long to wait for a pool connection.
      If exceeded: application gets an exception (fail fast, don't wait forever).
   3. max-lifetime: 1800000 (30 min) — rotate connections before RDS server-side 
      timeout. Always less than RDS wait_timeout (MySQL) or TCP keepalive limits.
   4. keepalive-time: 60000 — send keepalive to prevent AWS VPC idle connection 
      timeout (typically 350 seconds for NAT Gateway).
   5. minimum-idle: 2 — keep warm connections for first requests.
   Monitor via Spring Actuator + Micrometer: hikaricp.connections.active, .pending.

Q: Explain Aurora vs RDS for a Java Spring Boot production app.

A: RDS: managed traditional database (MySQL, PostgreSQL, Oracle, SQL Server).
   Simpler, cheaper, supports all standard DB features.
   
   Aurora: AWS-proprietary engine compatible with MySQL/PostgreSQL but redesigned.
   Key differences:
   - Storage: Aurora uses distributed, auto-scaling storage (up to 128 TB).
     RDS: fixed EBS volume provisioned manually.
   - Read replicas: Aurora replicas share storage (no replication lag for reads).
     RDS read replicas have replication lag (asynchronous).
   - Failover: Aurora Multi-AZ failover < 30 seconds (usually < 10s).
     RDS Multi-AZ: ~60–120 seconds.
   - Aurora Global: sub-second cross-region replication for multi-region.
   - Serverless v2: Aurora can auto-scale compute in fractions of ACUs.
   
   For Java Spring Boot production: choose Aurora PostgreSQL for new projects 
   — better performance, faster failover, Global DB for DR. Use RDS when cost 
   is primary concern or running legacy MySQL/PostgreSQL workloads.
