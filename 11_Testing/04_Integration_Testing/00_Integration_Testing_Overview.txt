INTEGRATION TESTING — OVERVIEW
Complete Interview Preparation Guide
================================================================

1. WHAT IS INTEGRATION TESTING?
================================================================

Integration Testing verifies that MULTIPLE components work correctly
TOGETHER — the "integration" of two or more units.

Scope:
  Unit Test       → One class in isolation (all dependencies mocked)
  Integration Test → Multiple classes working together, may include:
                      - Real database (or Testcontainers)
                      - Real message broker (Kafka)
                      - Real cache (Redis)
                      - Mocked external APIs (WireMock)
  End-to-End Test → Full system from UI to database through real network

TESTING PYRAMID context:
  Unit Tests     → Fast, many, cheap
  Integration    → Slower, fewer, test actual integration points
  E2E Tests      → Slowest, fewest, test the whole system

================================================================
2. INTEGRATION TEST SCOPE EXAMPLES
================================================================

SERVICE INTEGRATION (no HTTP):
  - OrderService + OrderRepository + real DB
  - UserService + Cache (Redis) + real cache
  - PaymentService + PaymentGateway (WireMocked) + real DB

HTTP API INTEGRATION (@SpringBootTest RANDOM_PORT):
  - Full request-response cycle through Controller + Service + Repository + DB

CONTRACT TESTS (Pact):
  - Consumer defines contract
  - Provider verifies it
  - No live calls needed — just JSON contracts

MESSAGING INTEGRATION:
  - Kafka producer + consumer with embedded/Testcontainers Kafka
  - Verify messages published and consumed correctly

4. KEY INTEGRATION TEST PRINCIPLES
================================================================

PRINCIPLE 1: Test the real integration point
  Don't mock what you're testing. If the test is about DB persistence,
  use a real database (Testcontainers), not a mock repository.

PRINCIPLE 2: Isolate each test
  Each test should start from a known state.
  Use @Transactional + rollback OR truncate/seed data before each test.

PRINCIPLE 3: Mock EXTERNAL dependencies
  Mock things outside your system boundary:
    - Third-party payment processors (WireMock)
    - External email providers (WireMock or @MockBean)
    - Third-party APIs
  But use REAL: DB, Kafka, Redis (via Testcontainers)

PRINCIPLE 4: Use test profiles
  application-test.yml should configure test-specific:
    - H2 instead of PostgreSQL (or Testcontainers for real PG)
    - No-op email services
    - Reduced connection pools

PRINCIPLE 5: Keep integration tests fast (where possible)
  - Share Testcontainers across tests (static containers + withReuse)
  - Cache Spring ApplicationContext (same @MockBean in base class)
  - Use @Transactional rollback instead of teardown scripts

5. INTEGRATION TEST LIFECYCLE IN SPRING BOOT
================================================================

  @SpringBootTest
  @ActiveProfiles("test")
  @Transactional
  class OrderServiceIT {
      
      // Before class — happens once
      @BeforeAll
      static void globalSetup() {
          // Start shared resources (if not using Testcontainers auto-start)
      }
      
      // Before each test
      @BeforeEach
      void setUp() {
          // Seed minimal test data
          // Configure WireMock stubs
          // Reset MockBeans
      }
      
      @Test
      void testCase1() { ... }
      // Transaction rolled back — testCase2 starts fresh
      
      @Test
      void testCase2() { ... }
      // Transaction rolled back again
      
      // After all — happens once
      @AfterAll
      static void globalTeardown() {
          // Stop shared resources
      }
  }

6. COMMON INTEGRATION TEST PATTERNS
================================================================

PATTERN: ROLLBACK EVERYTHING (default with @Transactional)
  @SpringBootTest
  @Transactional  // every test method rolled back
  class UserServiceIT {
      @Autowired UserRepository userRepository;
      
      @Test
      void shouldCreateUser() {
          userRepository.save(new User("alice@test.com"));
          assertEquals(1, userRepository.count());
      }  // rolled back — count is 0 for next test
  }

PATTERN: SQL SCRIPTS FOR REPRODUCIBLE STATE
  @SpringBootTest
  @Sql(scripts = "/sql/reset.sql", executionPhase = BEFORE_TEST_METHOD)
  class OrderIT {
      @Test
      void shouldProcessOrders() { ... }
  }

PATTERN: SHARED TESTCONTAINERS BASE CLASS
  @SpringBootTest
  @Testcontainers
  @ActiveProfiles("test")
  abstract class BaseIT {
      
      @Container
      static PostgreSQLContainer<?> pg = 
          new PostgreSQLContainer<>("postgres:15").withReuse(true);
      
      @DynamicPropertySource
      static void props(DynamicPropertyRegistry r) {
          r.add("spring.datasource.url", pg::getJdbcUrl);
          r.add("spring.datasource.username", pg::getUsername);
          r.add("spring.datasource.password", pg::getPassword);
      }
      
      @MockBean EmailService emailService;
  }
  
  class OrderServiceIT extends BaseIT { ... }  // same cached context
  class UserServiceIT extends BaseIT { ... }   // same cached context

PATTERN: WIREMOCK FOR EXTERNAL SERVICES
  @SpringBootTest
  @AutoConfigureWireMock(port = 0)  // random port WireMock
  class PaymentServiceIT {
      
      @Value("${wiremock.server.port}")
      int wireMockPort;
      
      @TestPropertySource(properties = {
          "app.payment.url=http://localhost:${wiremock.server.port}"
      })
      
      @BeforeEach
      void setUp() {
          stubFor(post(urlEqualTo("/payments"))
              .willReturn(okJson("{\"status\":\"success\",\"id\":\"ch_123\"}")));
      }
  }

7. INTEGRATION TEST vs UNIT TEST — WHAT TO USE WHEN
================================================================

Test UNIT when:
  - Pure business logic (calculations, transformations, validations)
  - Complex conditional logic
  - The "happy path" and edge cases within one class
  
Test INTEGRATION when:
  - SQL query correctness (JPQL, native, pagination)
  - Transaction boundaries (commit/rollback behavior)
  - Spring Security configuration (authorization rules)
  - Event handling (Kafka consumers, Spring Events)
  - Cache behavior (@Cacheable, @CacheEvict)
  - HTTP client behavior (RestTemplate with WireMock)

  Testcontainers Kafka for real Kafka.

  HTTP mock server. Stub external REST APIs.
  Verify external calls were made.
  Test error scenarios (timeouts, 500s).

  Consumer generates a pact (JSON contract).
  Provider verifies it against its implementation.
  No live service needed.

9. INTERVIEW QUESTIONS
================================================================

Q: What is integration testing and how does it differ from unit testing?
A: Unit tests test a single class in isolation (all dependencies mocked).
   Integration tests test multiple components working together, often
   involving real infrastructure like a database, message broker, or cache.

Q: When would you choose integration tests over unit tests?
A: For SQL query correctness, transaction behavior, Spring Security rules,
   Kafka producer/consumer interactions, cache annotations, and HTTP client
   behavior against real/mocked external services.

Q: What tools do you use for integration testing in Spring Boot?
A: Testcontainers for real Docker containers (DB, Kafka, Redis),
   WireMock for mocking external HTTP services,
   Pact for consumer-driven contract testing,
   Spring's EmbeddedKafka for lightweight Kafka testing,
   H2 for fast in-memory database tests.

Q: How do you ensure test isolation in integration tests?
A: Use @Transactional (rollback after each test), or @Sql scripts to
   reset state, or Testcontainers with fresh containers per test class.
   Avoid shared mutable state between tests.

Q: What is the main advantage of Testcontainers over H2?
A: Testcontainers provides a REAL database (e.g., PostgreSQL) with all
   its features — JSON columns, window functions, stored procedures,
   PostgreSQL-specific syntax. H2 is fast but may not support all features
   and has behavioral differences.

Q: How do you mock external HTTP APIs in integration tests?
A: WireMock — starts an HTTP server in the test JVM. You stub endpoints with
   stubFor(get(urlEqualTo("/path")).willReturn(okJson(responseBody))).
   The application's HTTP client calls the WireMock server instead of the real API.
