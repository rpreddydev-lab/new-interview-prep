PART 1: SPOTBUGS
================================================================

1.1 WHAT IS SPOTBUGS?
================================================================

SpotBugs (successor to FindBugs) is a static analysis tool that detects
potential bugs in Java bytecode. It doesn't compile your code — it reads
the .class files and matches patterns against a bug database.

Key Bug Categories:
  Bad Practice      — violates best practices (equals without hashCode, etc.)
  Correctness       — likely to be a bug (null dereference, infinite loop)
  Dodgy Code        — unintentional or suspicious constructs
  Malicious Code    — code that could be exploited (mutable arrays, etc.)
  Multithreaded     — concurrency issues (unsynchronized access, etc.)
  Performance       — inefficient patterns (StringBuilder vs concat in loops)
  Security          — security vulnerabilities (SQL injection patterns)

1.2 MAVEN CONFIGURATION
================================================================

  <plugin>
      <groupId>com.github.spotbugs</groupId>
      <artifactId>spotbugs-maven-plugin</artifactId>
      <version>4.8.3.1</version>
      <configuration>
          <!-- Fail on High priority issues only -->
          <maxAllowedViolations>0</maxAllowedViolations>
          <threshold>High</threshold>   <!-- High, Normal, Low, Exp, Ignore -->
          <effort>Max</effort>          <!-- Min, Default, Max -->
          
          <!-- Exclude specific bugs or files -->
          <excludeFilterFile>spotbugs-exclude.xml</excludeFilterFile>
      </configuration>
      <executions>
          <execution>
              <id>spotbugs-check</id>
              <phase>verify</phase>
              <goals><goal>check</goal></goals>
          </execution>
      </executions>
  </plugin>
  
  Commands:
    mvn spotbugs:check    # fail build if violations found
    mvn spotbugs:gui      # open SpotBugs GUI to browse issues
    mvn spotbugs:spotbugs # generate XML report (target/spotbugsXml.xml)

1.3 SPOTBUGS BUG EXAMPLES
================================================================

NULL DEREFERENCE (NP_NULL_ON_SOME_PATH):
  User user = userRepo.findById(id);  // can return null
  String email = user.getEmail();     // BUG: potential NPE
  // Fix:
  Optional<User> user = userRepo.findById(id);
  String email = user.map(User::getEmail).orElse("unknown");

EQUALS AND HASHCODE MISMATCH (HE_EQUALS_NO_HASHCODE):
  class User {
      @Override
      public boolean equals(Object o) { ... }
      // BUG: equals() defined but hashCode() missing → broken in HashMap/HashSet
      // Fix: always override hashCode() when overriding equals()
  }

MUTABLE STATIC FIELD (MS_MUTABLE_ARRAY):
  public static final List<String> ALLOWED_ROLES = Arrays.asList("ADMIN", "USER");
  // BUG: final reference but mutable contents → can be modified externally
  // Fix:
  public static final List<String> ALLOWED_ROLES = 
      Collections.unmodifiableList(Arrays.asList("ADMIN", "USER"));

IGNORED EXCEPTION (DE_MIGHT_IGNORE):
  try {
      loadConfig();
  } catch (IOException e) {
      // BUG: exception swallowed silently — hide real failures
  }
  // Fix: log or rethrow

SYNCHRONIZATION ISSUE (IS2_INCONSISTENT_SYNC):
  private int count;
  
  public synchronized void increment() { count++; }
  
  public int getCount() { return count; }  
  // BUG: getCount() not synchronized but count is modified via synchronized method

1.4 EXCLUSION FILTER
================================================================

  spotbugs-exclude.xml:
  
  <FindBugsFilter>
      <!-- Exclude specific bug type from all classes -->
      <Match>
          <Bug pattern="EI_EXPOSE_REP2" />
          <Class name="~.*Dto" />
      </Match>
      
      <!-- Exclude an entire package (e.g., generated code) -->
      <Match>
          <Package name="com.example.generated" />
      </Match>
      
      <!-- Exclude a specific method -->
      <Match>
          <Class name="com.example.LegacyService" />
          <Method name="oldMethod" />
          <Bug pattern="NP_NULL_ON_SOME_PATH" />
      </Match>
  </FindBugsFilter>

PART 2: CHECKSTYLE
================================================================

2.1 WHAT IS CHECKSTYLE?
================================================================

Checkstyle enforces a coding standard across the team. It checks source code
(not bytecode) for style violations like naming conventions, Javadoc
requirements, import ordering, indentation, line length, etc.

Popular configurations:
  Google Style Guide  — com/puppycrawl/tools/checkstyle/google_checks.xml
  Sun Coding Standard — com/puppycrawl/tools/checkstyle/sun_checks.xml
  Custom              — define your own XML ruleset

2.2 MAVEN CONFIGURATION
================================================================

  <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-checkstyle-plugin</artifactId>
      <version>3.3.1</version>
      <configuration>
          <configLocation>google_checks.xml</configLocation>  <!-- or custom path -->
          <violationSeverity>warning</violationSeverity>
          <failsOnError>true</failsOnError>
          <consoleOutput>true</consoleOutput>
          <excludes>**/generated/**/*.java</excludes>
      </configuration>
      <executions>
          <execution>
              <id>checkstyle-check</id>
              <phase>verify</phase>
              <goals><goal>check</goal></goals>
          </execution>
      </executions>
      <dependencies>
          <!-- Required to use google_checks.xml from classpath -->
          <dependency>
              <groupId>com.puppycrawl.tools</groupId>
              <artifactId>checkstyle</artifactId>
              <version>10.14.0</version>
          </dependency>
      </dependencies>
  </plugin>
  
  Commands:
    mvn checkstyle:check    # fail build on violations
    mvn checkstyle:checkstyle # generate report

2.3 COMMON CHECKSTYLE RULES
================================================================

  <module name="Checker">
      <!-- Max file length -->
      <module name="FileLength">
          <property name="max" value="400"/>
      </module>
      
      <module name="TreeWalker">
          <!-- Naming conventions -->
          <module name="TypeName"/>           <!-- Classes start with uppercase -->
          <module name="MethodName"/>         <!-- Methods start with lowercase -->
          <module name="ConstantName"/>       <!-- Constants are UPPER_CASE -->
          
          <!-- Line length -->
          <module name="LineLength">
              <property name="max" value="120"/>
          </module>
          
          <!-- Imports -->
          <module name="AvoidStarImport"/>    <!-- No import com.example.* -->
          <module name="UnusedImports"/>      <!-- No unused imports -->
          
          <!-- Braces -->
          <module name="LeftCurly"/>          <!-- { on same line -->
          <module name="NeedBraces"/>         <!-- Always use {} for if/for/while -->
          
          <!-- Whitespace -->
          <module name="WhitespaceAfter"/>    <!-- space after comma, semicolon -->
          <module name="EmptyLineSeparator"/> <!-- blank line between methods -->
          
          <!-- Javadoc -->
          <module name="JavadocMethod">
              <property name="scope" value="public"/>
          </module>
          
          <!-- Complexity -->
          <module name="CyclomaticComplexity">
              <property name="max" value="10"/>
          </module>
      </module>
  </module>

2.4 CHECKSTYLE SUPPRESSION
================================================================

  <!-- In checkstyle-suppressions.xml -->
  <!DOCTYPE suppressions PUBLIC
      "-//Checkstyle//DTD SuppressionFilter Configuration 1.2//EN"
      "https://checkstyle.org/dtds/suppressions_1_2.dtd">
  <suppressions>
      <!-- Suppress all checks in generated code -->
      <suppress files=".*[/\\]generated[/\\].*" checks=".*"/>
      
      <!-- Suppress specific check in specific file -->
      <suppress files="LegacyService.java" checks="MethodLength"/>
  </suppressions>

  # Reference in maven config:
  <suppressionsLocation>checkstyle-suppressions.xml</suppressionsLocation>

3. PMD — ADDITIONAL STATIC ANALYSIS
================================================================

PMD is similar to Checkstyle/SpotBugs but focuses on code complexity,
unused code, and overly complex constructs.

  <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-pmd-plugin</artifactId>
      <version>3.21.2</version>
      <configuration>
          <failOnViolation>true</failOnViolation>
          <printFailingErrors>true</printFailingErrors>
          <rulesets>
              <ruleset>/rulesets/java/quickstart.xml</ruleset>
          </rulesets>
      </configuration>
      <executions>
          <execution>
              <goals><goal>check</goal></goals>
          </execution>
      </executions>
  </plugin>

PMD notable rules:
  - UnusedLocalVariable       — declared but never used
  - EmptyCatchBlock           — swallowed exception
  - TooManyMethods            — class too large
  - ExcessiveMethodLength     — method too long
  - God class detection       — class doing too much

4. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between SpotBugs and Checkstyle?
A: SpotBugs analyzes compiled bytecode to find potential bugs — null
   dereferences, resource leaks, broken equals/hashCode contracts.
   Checkstyle analyzes source code to enforce style conventions —
   naming, indentation, line length, Javadoc. SpotBugs = correctness;
   Checkstyle = consistency.

Q: What is the most critical class of bugs SpotBugs detects?
A: Null dereferences (NP_*), resource leaks (OBL_UNSATISFIED_OBLIGATION),
   multithreading issues (IS2_INCONSISTENT_SYNC), and security
   vulnerabilities (SQL injection patterns, exposed mutable static fields).

Q: How do you handle legacy code that has many SpotBugs/Checkstyle violations?
A: Use exclusion filter files to suppress existing violations in legacy
   packages, while enforcing rules for new code. Track technical debt
   in SonarQube. Work down the list incrementally — fix blockers first,
   then style issues. Use the "Ratchet" pattern: never allow the count
   of violations to increase.

Q: What is cyclomatic complexity and how does it relate to testability?
A: Cyclomatic complexity is the number of independent paths through a method
   (each if/for/while/catch/case adds 1). High complexity (>10) means more
   branches to test, harder to understand, and higher chance of bugs.
   Lower complexity = easier to achieve full branch coverage in tests.

Q: Should you use Checkstyle's Google Style or create a custom style?
A: Google Style is a solid starting point and well-adopted. Customize
   for your team's preferences (line length, Javadoc requirements).
   The key is team consensus and enforcement — an unenforced style guide
   is worthless. Configure it in the CI pipeline to fail builds.
