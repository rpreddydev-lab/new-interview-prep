================================================================
TEST DOUBLES: FAKES, DUMMIES, MOCKS, STUBS, SPIES
Complete Interview Preparation Guide
================================================================

1. WHAT ARE TEST DOUBLES?
================================================================
A "Test Double" is a general term (coined by Gerard Meszaros in
"xUnit Test Patterns") for any object that STANDS IN for a real
dependency during testing.

The term comes from movie industry "stunt doubles" — a stand-in
for the real thing when the real thing would be too dangerous,
expensive, or unavailable.

Why we need test doubles:
  - Real dependencies may be slow (DB, network)
  - Real dependencies may not exist yet
  - Real dependencies may be non-deterministic (time, random)
  - Real dependencies may cause side effects (sending real emails)
  - We want to test a class in ISOLATION from its collaborators

The 5 types of test doubles (Meszaros taxonomy):
  1. Dummy
  2. Stub
  3. Fake
  4. Spy
  5. Mock

================================================================
2. DUMMY
================================================================

DEFINITION:
  Objects that are PASSED AROUND but never actually used.
  They fill parameter lists without affecting test behavior.

When to use:
  When a constructor or method requires parameters that aren't
  relevant to the test being written.

Example:
  // Method signature requires a Logger, but we're testing business logic
  // The logger isn't relevant to this test
  
  public void sendOrder(Order order, Logger logger, AuditService audit) {
      // logger and audit used internally, but we're testing order processing
  }
  
  // In test:
  Logger dummyLogger = mock(Logger.class);  // created but never verified
  AuditService dummyAudit = mock(AuditService.class);
  
  service.sendOrder(validOrder, dummyLogger, dummyAudit);
  // We don't assert anything about logger or audit
  // They're just fillers

Key characteristic:
  - Created and passed, but never interacted with in the test
  - Used purely to satisfy method signatures

3. STUB
================================================================

DEFINITION:
  Objects that provide CANNED ANSWERS to calls made during tests.
  They return predefined responses and NOTHING MORE.

Purpose:
  Control INDIRECT INPUT to the system under test.
  "When you call this method, return this specific value."

When to use:
  - When you need a dependency to return a specific value
  - To simulate different scenarios (empty list, null, specific data)
  - To avoid calling real infrastructure (DB, HTTP)

Example with Mockito:
  // Testing OrderService that depends on OrderRepository
  
  @Test
  void shouldReturnOrderWhenFound() {
      // STUB: tell the repository what to return
      Order expectedOrder = new Order("o-123", "customer-1");
      when(orderRepository.findById("o-123"))
          .thenReturn(Optional.of(expectedOrder));
      
      // The stub controls what the repository "returns"
      Optional<Order> result = orderService.findOrder("o-123");
      
      assertTrue(result.isPresent());
      assertEquals("customer-1", result.get().getCustomerId());
      
      // Notice: we DON'T verify that findById was called
      // We only care about the OUTPUT given that input
  }
  
  @Test
  void shouldReturnEmptyWhenOrderNotFound() {
      when(orderRepository.findById("nonexistent"))
          .thenReturn(Optional.empty());
      
      Optional<Order> result = orderService.findOrder("nonexistent");
      
      assertTrue(result.isEmpty());
  }

Stub for exception:
  when(paymentGateway.charge(any()))
      .thenThrow(new PaymentException("Card declined"));

Key characteristic:
  - Returns fixed, predetermined responses
  - Does NOT verify how it was called
  - Controls INCOMING data to the SUT

4. FAKE
================================================================

DEFINITION:
  Objects that have WORKING implementations, but simplified versions
  that are not suitable for production.

Purpose:
  A lightweight replacement for a real dependency that actually works,
  just without the full complexity or external connectivity.

When to use:
  - Need realistic behavior but not the production implementation
  - In-memory alternatives for speed
  - Shared across many tests in a test suite

Examples:

  IN-MEMORY REPOSITORY:
  public class FakeOrderRepository implements OrderRepository {
      private final Map<String, Order> store = new HashMap<>();
      
      @Override
      public Order save(Order order) {
          store.put(order.getId(), order);
          return order;
      }
      
      @Override
      public Optional<Order> findById(String id) {
          return Optional.ofNullable(store.get(id));
      }
      
      @Override
      public List<Order> findAll() {
          return new ArrayList<>(store.values());
      }
  }
  
  // This is a REAL implementation, just in-memory.
  // Tests use FakeOrderRepository instead of JPA repository.

  H2 IN-MEMORY DATABASE:
  // Spring Boot uses H2 for @DataJpaTest by default
  // This is a "fake" database — real SQL engine, but not production DB.
  
  IN-MEMORY MESSAGE BROKER:
  // Use an embedded Kafka or ActiveMQ instead of a real cluster

Real vs Fake examples:
  Real              | Fake
  PostgreSQL DB     | H2 in-memory / Testcontainers
  AWS S3            | MinIO (local S3-compatible server)
  Kafka cluster     | Embedded Kafka
  SMTP email server | Fake SMTP (like GreenMail or MailHog)
  Payment gateway   | Sandbox/test environment

Key characteristic:
  - Has a working implementation (not just return values)
  - Functional but simplified
  - Usually maintained as a long-term test companion
  - More effort to build but reusable

5. SPY
================================================================

DEFINITION:
  A spy WRAPS a REAL object and records how it is called.
  The real methods are still executed, but interactions are tracked.

Purpose:
  Verify that a REAL method was called with specific arguments,
  while still executing the real logic.

Contrast with Mock:
  Mock:  replaces everything, returns configured values
  Spy:   wraps real object, real methods run, interactions observed

Mockito Spy example:
  @Test
  void shouldCallEmailServiceWhenOrderCompleted() {
      // Spy on a real EmailService instance
      EmailService emailService = new EmailService(smtpConfig);
      EmailService spyEmail = Mockito.spy(emailService);
      
      OrderService orderService = new OrderService(spyEmail, orderRepo);
      
      Order order = new Order("o-123", "alice@example.com");
      orderService.completeOrder(order);
      
      // VERIFY the real method was called with correct args
      verify(spyEmail).sendConfirmation("alice@example.com", "o-123");
  }

Spy — partial stubbing:
  // Spy wraps real object but you can override specific methods
  EmailService spy = Mockito.spy(new EmailService());
  
  // Override only the SMTP sending to avoid real network call
  doNothing().when(spy).sendViaSmtp(any());
  
  // Other methods (like formatMessage) still use real implementation
  orderService.completeOrder(order);
  verify(spy).sendConfirmation(anyString(), anyString());

Key characteristic:
  - Wraps REAL objects (real constructor is called)
  - Real methods execute by default
  - Can selectively override specific methods
  - Records interactions for verification
  - Use sparingly — prefer full mocks for dependencies

6. MOCK
================================================================

DEFINITION:
  Objects pre-programmed with EXPECTATIONS about calls they will receive.
  They verify that the correct interactions happened.

Purpose:
  Verify BEHAVIOR — that the SUT calls its dependencies correctly.
  Mock = Stub + Verification capability.

When to use:
  - When you need to verify that a method was called
  - When you need to verify what arguments were passed
  - When you need to verify call count
  - When you need to control what the dependency returns

Mockito Mock example:
  @Test
  void shouldSendConfirmationEmailAfterOrderPlaced() {
      // MOCK: created with no real implementation
      EmailService mockEmail = Mockito.mock(EmailService.class);
      OrderRepository mockRepo = Mockito.mock(OrderRepository.class);
      
      when(mockRepo.save(any(Order.class)))
          .thenAnswer(inv -> inv.getArgument(0));  // return what was saved
      
      OrderService service = new OrderService(mockEmail, mockRepo);
      
      Order order = new Order("customer-1", List.of(item));
      service.placeOrder(order);
      
      // VERIFY behavior: email was sent with correct parameters
      verify(mockEmail).sendOrderConfirmation(
          "customer-1",
          argThat(o -> o.getStatus() == OrderStatus.CONFIRMED)
      );
      
      // VERIFY: exactly 1 email was sent
      verify(mockEmail, times(1)).sendOrderConfirmation(any(), any());
      
      // VERIFY: no other interactions happened
      verifyNoMoreInteractions(mockEmail);
  }

Key characteristic:
  - Created with no real implementation
  - Methods return default values (null, 0, false) unless stubbed
  - Can be configured to return specific values (stubbing)
  - Can VERIFY interactions after the test runs
  - Core Mockito feature

7. SUMMARY COMPARISON TABLE
================================================================

Type   | Has Real Impl? | Returns Values? | Verifies Calls? | Use Case
-------|----------------|-----------------|-----------------|---------------------------
Dummy  | No             | No (filler)     | No              | Fill required params
Stub   | No             | Yes (canned)    | No              | Control indirect input
Fake   | Yes (simple)   | Yes (real logic)| No              | Realistic but lightweight
Spy    | Yes (real)     | Yes (real)      | Yes             | Observe real object calls
Mock   | No             | Optional (stub) | Yes             | Verify interaction/behavior

Memory aid:
  Dummy  → "I'm just here to satisfy the signature"
  Stub   → "When you ask, I'll give you this"
  Fake   → "I work like the real thing, but simpler"
  Spy    → "I record everything the real object does"
  Mock   → "I expect to be called a specific way, and I'll fail if not"

8. MOCKING IN MOCKITO — PRACTICAL GUIDE
================================================================

Creating test doubles:
  // Method 1: Mockito.mock()
  OrderRepository repo = Mockito.mock(OrderRepository.class);
  
  // Method 2: @Mock annotation (requires MockitoExtension)
  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      @Mock OrderRepository orderRepository;
      @Mock EmailService emailService;
      @InjectMocks OrderService orderService;
  }
  
  // Method 3: MockitoAnnotations.openMocks(this)
  @BeforeEach
  void setUp() {
      MockitoAnnotations.openMocks(this);
  }

Configuring return values (Stubbing):
  // Return value
  when(repo.findById("123")).thenReturn(Optional.of(order));
  
  // Return multiple values in sequence
  when(repo.count()).thenReturn(5L, 6L, 7L);
  
  // Return based on input
  when(repo.findById(anyString())).thenAnswer(
      inv -> Optional.of(new Order(inv.getArgument(0)))
  );
  
  // Throw exception
  when(repo.findById("invalid")).thenThrow(new IllegalArgumentException());
  
  // Do nothing (for void methods)
  doNothing().when(emailService).send(any());
  
  // Throw from void method
  doThrow(new RuntimeException()).when(emailService).send(any());

Argument matchers:
  any()              // any object (including null)
  any(Class.class)   // any object of specific type  
  anyString()        // any non-null string
  anyInt()           // any int
  eq("exact")        // exact equality
  argThat(o -> o.getId() != null)  // custom lambda
  isNull()           // null
  isNotNull()        // not null

Verifying interactions:
  verify(emailService).send(expectedMessage);          // called once
  verify(emailService, times(2)).send(any());          // called exactly twice
  verify(emailService, never()).send(any());           // never called
  verify(emailService, atLeast(1)).send(any());        // at least once
  verify(emailService, atMost(3)).send(any());         // at most 3 times
  
  verifyNoInteractions(emailService);                  // no calls at all
  verifyNoMoreInteractions(emailService);              // no unverified calls

Argument Captors (capture what was passed):
  ArgumentCaptor<Order> orderCaptor = ArgumentCaptor.forClass(Order.class);
  verify(emailService).sendConfirmation(orderCaptor.capture());
  Order capturedOrder = orderCaptor.getValue();
  assertEquals("CONFIRMED", capturedOrder.getStatus().name());

Spying on real objects:
  List<String> realList = new ArrayList<>();
  List<String> spyList = Mockito.spy(realList);
  
  spyList.add("item1");        // REAL add is called
  verify(spyList).add("item1"); // interaction verified
  
  // Override specific method
  doReturn(100).when(spyList).size();  // now returns 100 instead of real size

9. WHEN TO USE EACH (INTERVIEW GUIDELINE)
================================================================

USE MOCKS WHEN:
  - Verifying that a specific interaction occurred
  - The real implementation would cause side effects (email, payment)
  - The real implementation is slow (DB, external API)
  - Testing boundary behavior (e.g., what happens when X throws exception)

USE STUBS WHEN:
  - You only need to control what a dependency returns
  - You don't care HOW MANY TIMES or WITH WHAT ARGS it was called
  - Simulating database queries returning test data

USE FAKES WHEN:
  - Multiple tests need a realistic, consistent implementation
  - An in-memory DB or broker serves the test suite well
  - Building a test helper that persists across test runs

USE SPIES WHEN:
  - You want to verify interactions on a REAL object
  - You need partial mocking (override some methods, keep others real)
  - Testing wrapper classes or decorators

USE DUMMIES WHEN:
  - A parameter is required but irrelevant to the test
  - Satisfying constructors/signatures without affecting test logic

10. OVER-MOCKING ANTI-PATTERN
================================================================

A common mistake: mocking too much.

SYMPTOMS:
  - Tests verify mock behavior, not real behavior
  - Tests pass even when production code has bugs
  - Every class in the call chain is mocked
  - Tests tightly coupled to implementation details

EXAMPLE OF OVER-MOCKING:
  // BAD: Mocking every single collaborator
  @Test
  void shouldCalculateTotal() {
      when(mockPriceCalculator.getBasePrice(item)).thenReturn(100.0);
      when(mockDiscountCalculator.getDiscount(member)).thenReturn(0.1);
      when(mockTaxCalculator.getTax(100.0)).thenReturn(10.0);
      when(mockFeeCalculator.getFee()).thenReturn(5.0);
      
      double total = orderService.calculateTotal(item, member);
      assertEquals(99.0, total);
      
      // This test only verifies that:
      // 100.0 * (1 - 0.1) + 10.0 + 5.0 = ???
      // It tells you nothing about actual calculation correctness
  }

BETTER APPROACH:
  - Use real implementations of pure calculation classes
  - Only mock infrastructure (DB, HTTP, email)
  - Test the real behavior end-to-end within a layer

GUIDELINE: "Mock at the boundary of your system, not within it."
  Boundaries: HTTP calls, database, message queues, external services.
  NOT: internal service classes, calculators, validators, mappers.

11. INTERVIEW QUESTIONS ON TEST DOUBLES
================================================================

Q: What is a test double?
A: A test double is a generic term for any object that stands in for
   a real dependency during testing. Types: Dummy, Stub, Fake, Spy, Mock.

Q: What is the difference between a Mock and a Stub?
A: Stub: provides canned answers, doesn't verify calls. Used to control
   indirect INPUT to the SUT. "When called, return this."
   Mock: pre-programmed with expectations, verifies that interactions
   happened correctly. Used to verify BEHAVIOR and calls made to dependencies.

Q: What is a Spy in Mockito?
A: A spy wraps a real object. Real methods execute, but interactions are
   recorded. You can selectively override specific methods.
   spy = real implementation + interaction tracking.

Q: What is a Fake?
A: A simplified but working implementation of a dependency.
   Example: in-memory repository that stores data in a HashMap instead of DB.
   Has real logic but not production-grade complexity.

Q: When should you use a Spy vs a Mock?
A: Use Mock when: testing against a dependency that you want full control over,
   with no real logic needed.
   Use Spy when: you want to test with a real implementation but verify
   certain methods were called, or when you need partial mocking.

Q: What is the danger of over-mocking?
A: You end up testing mock behavior instead of real behavior.
   Tests can pass while production code is broken because mocks don't
   enforce contracts between components. Prefer mocking at system boundaries.

Q: How do you capture arguments passed to a mock?
A: Using ArgumentCaptor in Mockito:
   ArgumentCaptor<Email> captor = ArgumentCaptor.forClass(Email.class);
   verify(emailService).send(captor.capture());
   assertEquals("expected@email.com", captor.getValue().getTo());
