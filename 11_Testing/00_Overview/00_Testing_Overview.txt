================================================================
TESTING OVERVIEW — Complete Interview Preparation Guide
================================================================

1. WHY TESTING MATTERS
================================================================
Software testing is the process of evaluating and verifying that a software
application does what it's supposed to do. It is a fundamental engineering
discipline that underpins software quality.

Key reasons testing matters in professional development:
  - Catches bugs EARLY when they are cheapest to fix
  - Prevents regressions when code is modified
  - Acts as living documentation of expected behavior
  - Gives developers confidence to refactor safely
  - Reduces production incidents and outages
  - Facilitates continuous delivery and deployment
  - Improves design — testable code is usually well-structured code

Cost of fixing a bug (relative):
  Requirements stage:   1x
  Design stage:         5x
  Development:          10x
  Integration/Test:     20x
  Production:           100x

This is the "shift-left" principle: find defects as early as possible.

================================================================
2. CORE TESTING TERMINOLOGY
================================================================

TEST CASE
  A set of conditions or variables used to determine whether a feature
  behaves as expected.
  Components: Given (setup) → When (action) → Then (assertion)

ASSERTION
  A statement that verifies an expected outcome is equal to actual outcome.
  Example: assertEquals(200, response.getStatusCode())

TEST SUITE
  A collection of test cases that are grouped together.

FIXTURE
  The fixed state (preconditions) required for tests to run reliably.
  Typically set up in @BeforeEach / @BeforeAll.

SUT (System Under Test)
  The component or unit being tested.

FLAKY TEST
  A test that non-deterministically fails. Common causes:
    - Race conditions (async code)
    - Time-dependent logic (using new Date() directly)
    - External dependencies (network, database)
    - Shared global state between tests
    - Random data without seeds

HAPPY PATH
  Tests that verify the expected, successful flow.

NEGATIVE / SAD PATH
  Tests that verify error handling, invalid inputs, edge cases.

BOUNDARY / EDGE CASE
  Tests with values at the boundaries of valid/invalid ranges.
  Example: testing 0, -1, MAX_INT for integer inputs.

================================================================
3. TESTING VOCABULARY — F.I.R.S.T PRINCIPLES
================================================================

Good unit tests should be:

  F — Fast
      Tests should run quickly (milliseconds). Slow tests discourage
      frequent execution. Avoid I/O, DB calls, network calls in unit tests.

  I — Independent / Isolated
      Tests should not depend on each other. Any test should be able to
      run in any order without affecting results.

  R — Repeatable
      Tests must produce the same result every time, in any environment.
      Avoid time-dependent or environment-dependent logic.

  S — Self-Validating
      Tests should automatically determine pass/fail with assertions.
      No manual inspection of logs should be needed.

  T — Timely / Thorough
      Tests should be written at the right time (TDD: before the code).
      Cover happy paths, sad paths, edge cases.

================================================================
4. WHAT MAKES A BAD TEST
================================================================

  - Tests that always pass (no assertions, trivial assertions)
  - Tests tightly coupled to implementation details
  - Tests with too many responsibilities (testing multiple concerns)
  - Tests that depend on execution order
  - Tests that use hard-coded dates, times, or IDs
  - Overly complex test setup that's harder to understand than the code
  - Tests that mock everything (testing mock behavior, not real behavior)
  - Tests that duplicate application logic

Anti-pattern: "Test after the fact" — writing tests only to hit coverage
targets, not to verify correctness.

================================================================
5. TEST DRIVEN DEVELOPMENT (TDD) OVERVIEW
================================================================

TDD is a development methodology where you write tests BEFORE writing code.

The Red-Green-Refactor cycle:
  RED    → Write a failing test for the desired behavior
  GREEN  → Write the minimum code to make the test pass
  REFACTOR → Improve code without changing behavior, keep tests green

Benefits:
  - Forces you to think about the API/interface before implementation
  - Results in high test coverage naturally
  - Produces simpler, more focused code
  - Encourages small, incremental changes

Example workflow:
  1. Write test: "should return sum of two numbers"
  2. Run → FAILS (no implementation yet)
  3. Write: return a + b;
  4. Run → PASSES
  5. Refactor if needed, re-run tests

================================================================
6. BDD (BEHAVIOR DRIVEN DEVELOPMENT) OVERVIEW
================================================================

BDD extends TDD by using natural language to describe tests.
Tests become executable specifications understandable by non-technical stakeholders.

Given-When-Then format:
  Given: initial context (preconditions)
  When:  the triggering event
  Then:  the expected outcome

Tools:
  - Cucumber (Java) — uses feature files written in Gherkin
  - JBehave (Java)
  - Spock Framework (Groovy/Java)

Example Gherkin:
  Feature: User Login
    Scenario: Successful login with valid credentials
      Given the user has an account with email "user@example.com"
      When the user logs in with correct password
      Then the user should be redirected to the dashboard

7. KEY TESTING CONCEPTS — INTERVIEW FOCUS
================================================================

WHITE BOX TESTING (Glass-box / Structural Testing)
  Tester knows the internal structure/code.
  Tests specific paths, branches, conditions.
  Example: Unit tests written by developers.

BLACK BOX TESTING (Behavioral Testing)
  Tester has no knowledge of internal implementation.
  Tests based solely on requirements and specifications.
  Example: QA testing an API endpoint without knowing its code.

GREY BOX TESTING
  Combination — partial knowledge of internals.
  Example: Integration tests that know DB schema but not application code.

REGRESSION TESTING
  Re-running existing tests after code changes to ensure nothing broke.
  The primary reason to maintain a robust test suite.

SMOKE TESTING
  A quick, shallow test to verify the system builds and basic functionality works.
  "Does it turn on and not immediately catch fire?"
  Run first in CI/CD pipeline.

SANITY TESTING
  Narrow and focused regression test to verify a specific bug fix or feature works.

EXPLORATORY TESTING
  Unscripted manual testing where testers simultaneously design and execute tests,
  exploring the system to find unexpected issues.

END-TO-END (E2E) TESTING
  Tests the entire application flow from UI to database.
  Tools: Selenium, Cypress, Playwright.
  Slow, brittle, but high-value for critical user journeys.

================================================================
8. TEST AUTOMATION STRATEGY
================================================================

Deciding what to automate:
  ✅ Automate: Regression tests, smoke tests, unit tests, API tests
  ❌ Don't automate: One-time tests, exploratory testing, usability testing

Shift-Left Testing in DevOps:
  - Tests run on every commit (CI pipeline)
  - Pull request checks require passing tests
  - Code coverage thresholds enforced by build tools

Test Automation Maturity Model:
  Level 0: No automation
  Level 1: Unit tests only
  Level 2: Unit + Integration tests
  Level 3: Automated regression suite
  Level 4: Full CI/CD with automated gates

9. COMMON INTERVIEW QUESTIONS ON TESTING BASICS
================================================================

Q: What is the difference between verification and validation?
A: Verification = "Are we building the product right?" (process check, static)
   Validation = "Are we building the right product?" (outcome check, dynamic)

Q: What is the difference between a bug, defect, and failure?
A: Bug = mistake in code (human error)
   Defect = deviation from expected behavior (found during testing)
   Failure = actual runtime malfunction observed by user

Q: What is test coverage and why is it not sufficient alone?
A: Test coverage measures percentage of code executed by tests.
   100% coverage doesn't mean no bugs — it means every line was executed
   at least once. Tests can execute code without verifying correctness.
   Coverage is a floor, not a ceiling.

Q: What is the testing pyramid?
A: Visual model showing proportion of test types:
   Unit tests (base, many, fast) → Integration tests (middle) → 
   E2E/UI tests (top, few, slow)
   The pyramid shape indicates: more low-level fast tests, fewer expensive ones.

Q: What is meant by "test isolation"?
A: Each test should be completely independent — no shared state, no ordering
   dependency. Achieved via setUp/tearDown, test doubles, and dependency injection.

Q: How do you handle non-deterministic (flaky) tests?
A: 
   - Identify root cause (time, concurrency, external dependency)
   - For time: inject a Clock and mock it in tests
   - For async: use awaitility or proper synchronization
   - For external: use mocks/stubs/WireMock
   - For DB: use @Transactional rollback or test containers with fresh state

10. TESTING IN JAVA ECOSYSTEM — TOOL OVERVIEW
================================================================

Unit Testing Frameworks:
  - JUnit 5 (Jupiter) — standard, most widely used
  - TestNG — alternative with groups, parallel execution
  - Spock — BDD-style, Groovy-based

Mocking Frameworks:
  - Mockito — most popular Java mocking library
  - EasyMock — older alternative
  - PowerMock — mocking static/final (use sparingly)
  - MockK — Kotlin-native (for Kotlin projects)

Assertion Libraries:
  - JUnit 5 Assertions — standard
  - AssertJ — fluent, readable chained assertions
  - Hamcrest — matcher-based assertions

Spring Testing:
  - Spring Test (spring-test) — base Spring testing support
  - Spring Boot Test — @SpringBootTest, @MockMvc, slices
  - Testcontainers — real DB/infrastructure in tests

Integration / API Testing:
  - RestAssured — fluent API testing
  - WireMock — HTTP stub server
  - Pact — consumer-driven contract testing

Performance Testing:
  - JMH — Java Microbenchmark Harness
  - JMeter — load testing
  - Gatling — Scala-based load testing with reports

Code Quality:
  - JaCoCo — code coverage
  - SonarQube — code quality analysis
  - PIT (Pitest) — mutation testing

11. QUICK REFERENCE — ANNOTATIONS CHEAT SHEET
================================================================

JUnit 5:
  @Test               — marks a test method
  @BeforeEach         — runs before each test
  @AfterEach          — runs after each test
  @BeforeAll          — runs once before all tests (static)
  @AfterAll           — runs once after all tests (static)
  @Disabled           — skip a test
  @DisplayName        — human-readable test name
  @Tag                — categorize tests
  @Nested             — inner class with related tests
  @ParameterizedTest  — data-driven tests
  @ExtendWith         — register extensions

Mockito:
  @Mock               — creates a mock
  @InjectMocks        — injects mocks into the SUT
  @Spy                — wraps real object with tracking
  @Captor             — captures arguments

Spring Boot Test:
  @SpringBootTest         — full application context
  @WebMvcTest             — web layer only
  @DataJpaTest            — JPA layer only
  @MockBean               — mock a Spring bean
  @TestConfiguration      — test-only bean configuration
  @Transactional          — rollback after each test
