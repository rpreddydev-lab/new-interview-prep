================================================================
TESTING PYRAMID — Complete Interview Preparation Guide
================================================================

1. WHAT IS THE TESTING PYRAMID?
================================================================
The Testing Pyramid is a concept introduced by Mike Cohn in "Succeeding with
Agile" (2009). It is a visual metaphor that describes:
  - HOW MANY tests of each type you should have
  - HOW FAST each type should run
  - HOW ISOLATED vs. integrated each type should be

The pyramid (bottom to top):

        /\
       /  \
      / E2E \           ← Few, slow, expensive
     /--------\
    / Integrat. \       ← Medium number, medium speed
   /-------------\
  /   Unit Tests  \     ← Many, fast, cheap
 /-----------------\

Bottom = Unit Tests    → Foundation, largest quantity
Middle = Integration   → Moderate quantity
Top    = E2E / UI      → Smallest quantity

================================================================
2. UNIT TESTS (BASE OF PYRAMID)
================================================================

DEFINITION:
  Tests a single unit of code in complete isolation from its dependencies.
  Dependencies are replaced with test doubles (mocks/stubs).

CHARACTERISTICS:
  ✅ Extremely fast (milliseconds per test)
  ✅ Completely isolated — no DB, no network, no filesystem
  ✅ Easy to write and maintain
  ✅ Pinpoint failures precisely
  ✅ Run on every single commit in CI
  ❌ Don't test how components interact
  ❌ Can give false confidence if mocks diverge from real behavior

SCOPE:
  - A single class or method
  - Business logic, algorithms, utility functions
  - Conditional branching and edge cases

EXAMPLE (Java/JUnit 5):
  @Test
  void shouldCalculateTotalPrice() {
      // GIVEN
      Product product = new Product("Book", 29.99, 3);
      PriceCalculator calculator = new PriceCalculator();
      
      // WHEN
      double total = calculator.calculateTotal(product);
      
      // THEN
      assertEquals(89.97, total, 0.001);
  }

QUANTITY GUIDELINE:
  Unit tests should make up ~70% of your total test suite.

================================================================
3. INTEGRATION TESTS (MIDDLE OF PYRAMID)
================================================================

DEFINITION:
  Tests how multiple components work together. Can involve real or
  near-real dependencies: actual database, message queues, file systems.

CHARACTERISTICS:
  ✅ Catches integration bugs (data format mismatch, SQL errors, etc.)
  ✅ Tests real behavior of infrastructure interactions
  ❌ Slower than unit tests (seconds to minutes)
  ❌ Require more setup (DB containers, embedded servers)
  ❌ Harder to isolate failures

TYPES:
  a) Component Integration — two or more classes working together
  b) Layer Integration — Service + Repository + Database
  c) Service Integration — microservices communicating
  d) Infrastructure Integration — testing against Testcontainers DB

EXAMPLE (Spring Boot + Testcontainers):
  @DataJpaTest
  @AutoConfigureTestDatabase(replace = NONE)
  @Testcontainers
  class OrderRepositoryIntegrationTest {
      @Container
      static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15");
      
      @Test
      void shouldSaveAndRetrieveOrder() {
          Order order = new Order("customer-1", List.of());
          orderRepository.save(order);
          
          Optional<Order> found = orderRepository.findById(order.getId());
          assertTrue(found.isPresent());
      }
  }

QUANTITY GUIDELINE:
  Integration tests should make up ~20% of your total test suite.

================================================================
4. END-TO-END TESTS (TOP OF PYRAMID)
================================================================

DEFINITION:
  Tests the entire system from the user's perspective, simulating real
  user workflows across all layers: UI → API → Service → Database.

CHARACTERISTICS:
  ✅ Highest confidence — tests the real thing
  ✅ Catches problems no other test can (config issues, network, DNS)
  ❌ Very slow (seconds to minutes per test)
  ❌ Brittle — break easily due to UI changes, timing issues
  ❌ Expensive to maintain
  ❌ Hard to debug when they fail
  ❌ Don't provide specific location of failure

TOOLS:
  - Selenium (Java) — browser automation
  - Cypress — JavaScript, fast, reliable
  - Playwright — modern, multi-browser, multi-language
  - RestAssured — for API-level E2E tests

EXAMPLE (RestAssured API E2E):
  @SpringBootTest(webEnvironment = RANDOM_PORT)
  class OrderE2ETest {
      @Test
      void shouldCreateAndRetrieveOrder() {
          // Create order
          String orderId = given()
              .contentType("application/json")
              .body("""{"customerId": "c1", "items": [...]}""")
              .when().post("/api/orders")
              .then().statusCode(201)
              .extract().path("id");
          
          // Retrieve order
          given()
              .when().get("/api/orders/" + orderId)
              .then()
              .statusCode(200)
              .body("customerId", equalTo("c1"));
      }
  }

QUANTITY GUIDELINE:
  E2E tests should make up only ~10% of your total test suite.
  Focus only on critical user journeys.

================================================================
5. VARIATIONS ON THE PYRAMID
================================================================

THE ICE CREAM CONE (Anti-Pattern)
  Many E2E tests at top, few unit tests at bottom.
  This is the OPPOSITE of what you want.
  Result: slow, brittle test suite that provides low feedback quality.
  
        /\
       /E2E\         ← Most tests (bad!)
      /-------\
     / Integr. \
    /------------\
   /  Unit Tests  \   ← Few tests (bad!)
  /----------------\

THE TESTING HONEYCOMB (Martin Fowler / Spotify Model)
  Used for microservices. Emphasizes service integration tests over unit
  tests, since microservices are often too small to benefit from isolated
  unit tests, but integration with other services matters enormously.

  Focus areas:
  - Integrated component tests (service + DB)
  - Consumer-driven contract tests
  - E2E only for critical paths

THE TESTING TROPHY (Kent C. Dodds)
  Popular in frontend/JavaScript world.
  More emphasis on integration tests, fewer pure unit tests.
  
    /\
   /E2E\
  /-----\
 / Integ \      ← Largest group
/----------\
/ Unit Tests \
/-------------\
/ Static Checks \   ← Type checking, linting

6. CHOOSING THE RIGHT TEST TYPE
================================================================

Ask yourself:
  1. Am I testing a single class/function in isolation?
     → Unit test with mocks

  2. Am I testing multiple classes working together?
     → Integration test

  3. Am I testing the whole system from a user's perspective?
     → E2E test

  4. Am I testing an API endpoint with the full Spring context?
     → Spring Boot integration test (@SpringBootTest)

  5. Am I testing just the web layer (controller + serialization)?
     → Web layer slice test (@WebMvcTest)

  6. Am I testing just the repository/DB layer?
     → Data layer slice test (@DataJpaTest)

7. TEST EXECUTION STRATEGY IN CI/CD
================================================================

Pipeline stages (order matters for fast feedback):

Stage 1 — Static Analysis (seconds)
  - Compilation, linting, type checking
  - Fail fast on syntax/type errors

Stage 2 — Unit Tests (seconds to minutes)
  - All unit tests run in parallel
  - Must pass before integration tests

Stage 3 — Integration Tests (minutes)
  - DB tests, service tests with Testcontainers
  - Spin up containers, run tests, tear down

Stage 4 — E2E Tests (minutes to hours)
  - Only run on merge to main / staging deployment
  - Focus on critical paths only

Stage 5 — Performance Tests (hours)
  - Run nightly or on release branches
  - JMeter, Gatling load tests

Best practice:
  Fast tests first — give developers quick feedback.
  Never block the entire team on a 2-hour E2E run for every commit.

8. TEST COVERAGE TARGETS BY PYRAMID LAYER
================================================================

Layer          | Coverage Goal  | Focus
---------------|----------------|-------------------------------
Unit           | 80-90%         | Business logic, edge cases
Integration    | Key flows      | DB interactions, API contracts
E2E            | Critical paths | Login, checkout, main workflows

Coverage is NECESSARY but NOT SUFFICIENT.
High coverage with poor assertions is meaningless.
Aim for MEANINGFUL coverage with MEANINGFUL assertions.

9. INTERVIEW QUESTIONS ON TESTING PYRAMID
================================================================

Q: What is the testing pyramid and why does it matter?
A: It's a visual model guiding the PROPORTION of test types. More unit tests
   (fast, cheap, isolated) than integration tests, fewer E2E tests (slow, brittle).
   Inverted pyramid (more E2E) leads to slow, unreliable test suites.

Q: Why should you have more unit tests than E2E tests?
A: Unit tests: milliseconds, precise failure info, no setup overhead.
   E2E tests: minutes, vague failure reasons, flaky, expensive maintenance.
   You get 90% of the value with 10% of the cost by prioritizing unit tests.

Q: What is the "ice cream cone" anti-pattern?
A: When a team has mostly E2E/manual tests and very few unit tests.
   Results in slow feedback loops, brittle tests, and resistance to change.

Q: When would you intentionally write more integration tests than unit tests?
A: In microservices with thin business logic, where the main risk is
   communication between services. The Honeycomb model (Spotify) advocates
   this. When logic is mostly I/O and data transformation, integration tests
   are more valuable.

Q: Can you have 100% test coverage and still have bugs?
A: YES. Coverage measures execution, not correctness.
   Example: a test that calls a function but never asserts the result
   gives 100% line coverage but catches nothing.
   Also: logic bugs can slip through when assertions are too weak.

Q: What is a "slice test" in Spring Boot?
A: A focused integration test that loads only a specific layer of the
   Spring context.
   @WebMvcTest — loads only web/controller layer
   @DataJpaTest — loads only JPA/persistence layer
   @JsonTest — loads only JSON serialization
   Faster than @SpringBootTest because context is smaller.

10. PRACTICAL PYRAMID SIZING EXAMPLE
================================================================

For a typical REST API microservice with 50 endpoints:
  Unit tests:        ~300–500  (services, validators, mappers, utilities)
  Integration tests: ~50–100   (repositories, controller slices, full flow)
  E2E tests:         ~10–20    (login, create order, process payment, etc.)

Execution time targets:
  Unit tests:        < 30 seconds
  Integration tests: < 5 minutes  
  E2E tests:         < 15 minutes (for critical paths only)
