================================================================
BDD — BEHAVIOR DRIVEN DEVELOPMENT: Complete Interview Preparation Guide
================================================================

1. WHAT IS BDD?
================================================================
Behavior-Driven Development (BDD) is a software development methodology
that extends TDD by using NATURAL LANGUAGE to describe test scenarios.

Coined by Dan North in 2006 as an evolution of TDD.

Core philosophy:
  - Tests should describe BEHAVIOR, not implementation
  - Scenarios should be readable by non-technical stakeholders
  - Collaboration between Business, QA, and Dev is built into the process
  - "Three Amigos" meetings drive test creation

Key difference from TDD:
  TDD → Developer-centric, technical, code-first
  BDD → Business-centric, natural language, behavior-first

BDD asks: "What should this software DO?" rather than "How should I code this?"

================================================================
2. GIVEN-WHEN-THEN (GWT) SYNTAX
================================================================

The heart of BDD is the Given-When-Then structure:

  Given: The initial context (preconditions / state of the world)
  When:  The triggering event or action
  Then:  The expected outcome or assertion

This maps directly to:
  Given → Arrange (setup)
  When  → Act (trigger)
  Then  → Assert (verify)

Example:
  Given the user has $100 in their account
  When the user transfers $30 to another account
  Then the user's balance should be $70
  And the recipient's balance should have increased by $30

Additional keywords:
  And  → another Given/When/Then continuation
  But  → negating continuation (But the order should not be cancelled)

3. GHERKIN LANGUAGE
================================================================

Gherkin is the structured natural language used to write BDD scenarios.
It is feature-file based and maps to executable code via step definitions.

File extension: .feature

SYNTAX:
  Feature: <High-level feature description>
    Background: <Optional: steps that run before each scenario>
    
    Scenario: <Specific scenario name>
      Given <context>
      When  <action>
      Then  <outcome>
    
    Scenario Outline: <Template scenario>
      Given I have <amount> in my account
      When I withdraw <withdraw>
      Then I should have <remaining> remaining
      
      Examples:
        | amount | withdraw | remaining |
        | 100    | 30       | 70        |
        | 200    | 50       | 150       |

FULL EXAMPLE — user_login.feature:
  Feature: User Authentication
    As a registered user
    I want to log in with my credentials
    So that I can access my account
    
    Background:
      Given the login page is displayed
    
    Scenario: Successful login with valid credentials
      Given the user has registered with email "alice@example.com"
      And the password is "SecurePass123"
      When the user submits the login form
      Then the user is redirected to the dashboard
      And the welcome message shows "Welcome, Alice"
    
    Scenario: Failed login with wrong password
      Given the user has registered with email "alice@example.com"
      When the user submits login with password "WrongPass"
      Then an error message "Invalid credentials" is displayed
      And the user remains on the login page
    
    Scenario: Account locked after 3 failed attempts
      Given the user has failed 2 login attempts
      When the user submits another wrong password
      Then the account is locked
      And a lockout email is sent to "alice@example.com"

4. CUCUMBER — BDD FRAMEWORK FOR JAVA
================================================================

Cucumber is the most popular BDD framework for Java.
It connects Gherkin feature files to Java step definitions.

Maven dependency:
  <dependency>
      <groupId>io.cucumber</groupId>
      <artifactId>cucumber-java</artifactId>
      <version>7.15.0</version>
      <scope>test</scope>
  </dependency>
  <dependency>
      <groupId>io.cucumber</groupId>
      <artifactId>cucumber-junit-platform-engine</artifactId>
      <version>7.15.0</version>
      <scope>test</scope>
  </dependency>

PROJECT STRUCTURE:
  src/
    test/
      java/
        com/example/
          steps/
            UserLoginSteps.java    ← Step definitions
          CucumberRunnerTest.java  ← Runner class
      resources/
        features/
          user_login.feature       ← Gherkin scenarios

STEP DEFINITIONS (Java):
  import io.cucumber.java.en.*;
  import static org.junit.jupiter.api.Assertions.*;
  
  public class UserLoginSteps {
      
      private LoginPage loginPage;
      private AuthService authService;
      private String response;
      
      @Given("the login page is displayed")
      public void theLoginPageIsDisplayed() {
          loginPage = new LoginPage();
          loginPage.open();
      }
      
      @Given("the user has registered with email {string}")
      public void theUserHasRegisteredWithEmail(String email) {
          authService.createUser(email, "SecurePass123");
      }
      
      @When("the user submits the login form")
      public void theUserSubmitsLoginForm() {
          response = authService.login(loginPage.getEmail(), loginPage.getPassword());
      }
      
      @Then("the user is redirected to the dashboard")
      public void theUserIsRedirectedToDashboard() {
          assertEquals("DASHBOARD", response);
      }
      
      @Then("an error message {string} is displayed")
      public void anErrorMessageIsDisplayed(String expectedMessage) {
          assertEquals(expectedMessage, loginPage.getErrorMessage());
      }
  }

CUCUMBER RUNNER:
  @Suite
  @IncludeEngines("cucumber")
  @SelectClasspathResource("features")
  @ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.example.steps")
  @ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty, html:target/cucumber-report.html")
  public class CucumberRunnerTest { }

5. PARAMETERIZED SCENARIOS — SCENARIO OUTLINE
================================================================

Scenario Outline allows data-driven BDD tests.
The Examples table provides multiple data sets.

Feature: Shopping Cart Discount
  Scenario Outline: Apply discount based on membership tier
    Given the user has <tier> membership
    And the cart total is <total>
    When the discount is applied
    Then the final price should be <expected>
    
    Examples:
      | tier     | total | expected |
      | BASIC    | 100   | 100      |
      | SILVER   | 100   | 95       |
      | GOLD     | 100   | 90       |
      | PLATINUM | 100   | 80       |

This generates 4 separate test executions — one per row.

6. HOOKS IN CUCUMBER
================================================================

Hooks run setup/teardown logic around scenarios.

  import io.cucumber.java.Before;
  import io.cucumber.java.After;
  import io.cucumber.java.BeforeAll;
  import io.cucumber.java.AfterAll;
  
  public class Hooks {
      
      @BeforeAll  // runs once before all scenarios
      public static void globalSetup() {
          DatabaseHelper.startEmbeddedDb();
      }
      
      @Before   // runs before each scenario
      public void setupScenario(Scenario scenario) {
          System.out.println("Starting: " + scenario.getName());
          DatabaseHelper.clearTables();
      }
      
      @After    // runs after each scenario
      public void teardownScenario(Scenario scenario) {
          if (scenario.isFailed()) {
              // capture screenshot or log on failure
          }
      }
      
      @AfterAll  // runs once after all scenarios
      public static void globalTeardown() {
          DatabaseHelper.stopEmbeddedDb();
      }
  }

Tagged Hooks (run only for specific tags):
  @Before("@database")
  public void setupDatabase() {
      // only runs for @database tagged scenarios
  }

7. TAGS IN CUCUMBER
================================================================

Tags categorize and filter scenarios.

In feature files:
  @smoke @login
  Scenario: Successful login
    ...
  
  @regression @payment
  Scenario: Process credit card payment
    ...

Running specific tags (Maven/CLI):
  -Dcucumber.filter.tags="@smoke"           # run smoke tests
  -Dcucumber.filter.tags="@smoke or @login" # smoke OR login
  -Dcucumber.filter.tags="@smoke and not @slow" # smoke but not slow

Annotation on runner:
  @ConfigurationParameter(
      key = FILTER_TAGS_PROPERTY_NAME, 
      value = "@smoke"
  )

8. BDD vs TDD — COMPARISON
================================================================

Aspect          | TDD                      | BDD
----------------|--------------------------|----------------------------
Focus           | Implementation           | Behavior / Business value
Language        | Code (Java/test methods) | Natural language (Gherkin)
Audience        | Developers               | Dev + QA + Business
When to write   | Before each unit         | Before features (stories)
Tool (Java)     | JUnit 5                  | Cucumber, JBehave
Granularity     | Method/class level       | Feature/scenario level
Output          | Test report              | Living documentation

TDD and BDD are COMPLEMENTARY, not competing:
  BDD scenarios → high-level acceptance tests (outer loop)
  TDD unit tests → low-level implementation tests (inner loop)
  
  The "double loop of TDD":
    Outer loop: BDD acceptance test (Failing)
      Inner loop: TDD unit tests (Red → Green → Refactor)
    Outer loop: BDD acceptance test (Now Passing)

9. THREE AMIGOS MEETING
================================================================

The "Three Amigos" is a BDD practice where:
  - Business Analyst (BA) / Product Owner
  - Developer
  - QA Engineer

...collaborate to define scenarios BEFORE development starts.

Purpose:
  - Shared understanding of requirements
  - Catch ambiguities and edge cases early
  - Create acceptance criteria in executable form
  - Reduce "development surprises" in testing phase

Process:
  1. BA presents a user story
  2. All three ask "what if?" questions
  3. Edge cases and acceptance criteria emerge
  4. Scenarios are written in Gherkin collaboratively
  5. These scenarios become acceptance tests

10. LIVING DOCUMENTATION
================================================================

One of BDD's most powerful benefits.

Feature files are:
  - Written in natural language (business-readable)
  - Executable (they ARE the tests)
  - Always up-to-date (if they're not, tests fail)

This makes them "living documentation" — unlike word documents
or comments that can go stale, feature files break when out of sync.

Tools to generate reports from Cucumber:
  - Cucumber HTML Reports (built-in)
  - Allure Reports (beautiful, widely used)
  - Extent Reports

Sample Allure setup:
  <dependency>
      <groupId>io.qameta.allure</groupId>
      <artifactId>allure-cucumber7-jvm</artifactId>
      <version>2.24.0</version>
  </dependency>

11. JBEHAVE — ALTERNATIVE BDD FRAMEWORK
================================================================

JBehave is another BDD framework for Java, older than Cucumber.
Uses .story files instead of .feature files.

Story format:
  Narrative:
  As a user
  I want to reset my password
  So that I can access my account
  
  Scenario: Password reset email sent
  
  Given the user "alice@example.com" exists
  When the user requests a password reset
  Then a reset email is sent to "alice@example.com"

Step definitions:
  @Given("the user $email exists")
  public void givenUserExists(String email) { ... }
  
  @When("the user requests a password reset")
  public void whenPasswordResetRequested() { ... }
  
  @Then("a reset email is sent to $email")
  public void thenResetEmailSent(String email) { ... }

Cucumber vs JBehave:
  Cucumber: more popular, better Spring integration, active community
  JBehave: mature, more configuration, better for complex stories

12. SPOCK FRAMEWORK (Groovy-Based BDD)
================================================================

Spock is a testing framework written in Groovy that runs on JVM.
Supports Java projects. Known for expressive, readable tests.

Example:
  class DiscountServiceSpec extends Specification {
      
      def "premium member gets 10% discount"() {
          given:
          def member = new Member(tier: PREMIUM)
          def cart = new Cart(total: 100.0)
          def service = new DiscountService()
          
          when:
          def result = service.calculate(member, cart)
          
          then:
          result == 90.0
      }
      
      @Unroll
      def "#tier member gets #discount% discount on $total"() {
          given:
          def member = new Member(tier: tier)
          def cart = new Cart(total: total)
          
          when:
          def result = new DiscountService().calculate(member, cart)
          
          then:
          result == expected
          
          where:
          tier      | total | discount | expected
          BASIC     | 100   | 0        | 100.0
          SILVER    | 100   | 5        | 95.0
          GOLD      | 100   | 10       | 90.0
          PLATINUM  | 100   | 20       | 80.0
      }
  }

Spock advantages:
  - Very readable
  - Built-in data tables (where: block)
  - Exception testing with thrown()
  - Rich mocking built-in (def service = Mock(EmailService))

13. INTERVIEW QUESTIONS ON BDD
================================================================

Q: What is BDD and how does it differ from TDD?
A: BDD extends TDD by using natural language (Given-When-Then) to describe
   tests. BDD focuses on BEHAVIOR from the business perspective and involves
   collaboration between Dev, QA, and Business. TDD is developer-centric and
   focuses on implementation via unit tests.

Q: What is Gherkin?
A: A structured natural language used to write BDD scenarios in feature files.
   Uses Given-When-Then keywords. Readable by non-technical stakeholders.
   Used by Cucumber and other BDD frameworks.

Q: What is Cucumber and how does it work?
A: Cucumber is a BDD framework that connects Gherkin feature files to Java
   step definitions. Feature files describe behavior in natural language.
   Step definitions (Java methods) implement the steps using annotations
   like @Given, @When, @Then with regex or Cucumber Expressions.

Q: What are the benefits of BDD?
A: Shared understanding between Dev/QA/Business, executable living documentation,
   acceptance criteria become automated tests, catches requirement ambiguities early,
   reduces rework due to misunderstood requirements.

Q: What is the "Three Amigos" meeting?
A: A BDD practice where Business Analyst, Developer, and QA collaborate
   to define feature scenarios before development. The goal is shared
   understanding and executable acceptance criteria.

Q: What is the difference between Scenario and Scenario Outline?
A: Scenario: single test case with hardcoded values.
   Scenario Outline: template test case parameterized with an Examples table.
   Each row in Examples generates a separate test execution.

Q: What are Cucumber hooks?
A: @Before and @After methods that run setup/teardown around each scenario.
   @BeforeAll/@AfterAll run once for all scenarios.
   Can be tagged to only run for specific scenarios.

Q: What is "living documentation" in BDD?
A: Feature files are both human-readable specifications AND executable tests.
   They can never go stale (failing tests force updates).
   They serve as always-accurate documentation for business and developers.
