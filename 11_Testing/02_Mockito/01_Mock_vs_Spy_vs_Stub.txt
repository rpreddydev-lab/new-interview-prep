================================================================
MOCKITO — MOCK vs SPY vs STUB
Complete Interview Preparation Guide
================================================================

1. CONCEPTUAL OVERVIEW
================================================================

All three are forms of TEST DOUBLES, but serve different purposes:

  MOCK:   A fake object with no real implementation.
          You PROGRAM its behavior (stubbing).
          You VERIFY interactions (did it get called? with what?).
  
  SPY:    A WRAPPER around a REAL object.
          Real methods execute by default.
          You can OVERRIDE specific methods.
          You can VERIFY interactions.
  
  STUB:   The ACT of configuring a mock/spy to return a specific value.
          (In Mockito, "stubbing" = calling when().thenReturn())

Note: In common usage:
  - "Mock" often means either a Mock OR a Stub (configured mock)
  - Purists distinguish: Mock = verify behavior, Stub = configure return value
  - Mockito blurs this: Mockito.mock() can do BOTH stubbing AND verification

================================================================
2. MOCK — DETAILED
================================================================

DEFINITION:
  A mock is created by Mockito with NO real implementation.
  Every method returns a default value unless explicitly configured:
    - Objects → null
    - Collections → empty ([], {}, Optional.empty())
    - Primitives → 0, false, etc.
    - String → ""

CREATING A MOCK:
  // Annotation style (preferred)
  @Mock
  OrderRepository orderRepository;
  
  // Programmatic style
  OrderRepository orderRepository = Mockito.mock(OrderRepository.class);
  
  // With settings
  OrderRepository orderRepository = Mockito.mock(
      OrderRepository.class, 
      withSettings().name("orderRepository").strictness(STRICT_STUBS)
  );

STUBBING A MOCK (configuring return values):
  // Return a value
  when(orderRepository.findById("o-123")).thenReturn(Optional.of(order));
  
  // Return different values on successive calls
  when(clock.now()).thenReturn(
      LocalDateTime.of(2024, 1, 1, 10, 0),   // first call
      LocalDateTime.of(2024, 1, 1, 10, 5),   // second call
      LocalDateTime.of(2024, 1, 1, 10, 10)   // subsequent calls
  );
  
  // Throw exception
  when(orderRepository.findById("bad")).thenThrow(new DatabaseException("Connection lost"));
  
  // Return based on argument (lambda)
  when(orderRepository.findById(anyString())).thenAnswer(invocation -> {
      String id = invocation.getArgument(0);
      return id.startsWith("valid-") ? Optional.of(new Order(id)) : Optional.empty();
  });
  
  // Always return the argument (useful for save() methods)
  when(orderRepository.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));

VERIFYING A MOCK:
  // Was it called?
  verify(orderRepository).findById("o-123");
  
  // How many times?
  verify(emailService, times(2)).sendReminder(any());
  verify(orderRepository, never()).delete(any());
  
  // Verify no interactions at all
  verifyNoInteractions(emailService);
  
  // Verify nothing else was called (after explicit verifies)
  verify(orderRepository).findById(any());
  verifyNoMoreInteractions(orderRepository);

MOCK OF AN ABSTRACT CLASS:
  abstract class BaseProcessor {
      abstract void process();
      
      public void validate() { /* real logic */ }
  }
  
  BaseProcessor mock = Mockito.mock(BaseProcessor.class);
  when(mock.process()).thenCallRealMethod();  // or thenReturn() for abstract
  // mock.validate() returns null/default unless stubbed or thenCallRealMethod()

3. SPY — DETAILED
================================================================

DEFINITION:
  A spy wraps a REAL object instance.
  All real methods execute by default.
  You can selectively override specific methods.
  All interactions are tracked (can verify).

CREATING A SPY:
  // Annotation style
  @Spy
  List<String> spyList = new ArrayList<>();
  
  @Spy
  EmailService emailService = new EmailService(testSmtpConfig);
  
  // Programmatic style
  EmailService real = new EmailService(testSmtpConfig);
  EmailService spy = Mockito.spy(real);
  
  // Short form (no-arg constructor required)
  OrderService spy = Mockito.spy(OrderService.class);

SPY BEHAVIOR:
  List<String> spy = Mockito.spy(new ArrayList<>());
  
  spy.add("Apple");    // real add() executes
  spy.add("Banana");   // real add() executes
  
  assertEquals(2, spy.size());  // real size() — returns 2
  assertTrue(spy.contains("Apple")); // real contains() — returns true
  
  // Verify interactions
  verify(spy).add("Apple");
  verify(spy, times(2)).add(anyString());

OVERRIDING SPECIFIC METHODS ON A SPY:
  EmailService spy = Mockito.spy(new EmailService());
  
  // Override: don't actually send email (avoid SMTP)
  doNothing().when(spy).sendViaSmtp(any());
  
  // The real method for formatting still runs!
  String formatted = spy.formatMessage(to, subject, body);  // REAL call
  spy.sendViaSmtp(formatted);  // OVERRIDDEN — does nothing

IMPORTANT: Use doReturn() with spies, not when().thenReturn():
  // CORRECT for spies:
  doReturn(cachedValue).when(spy).computeExpensive();
  
  // WRONG for spies (calls real method during stub setup):
  // when(spy.computeExpensive()).thenReturn(cachedValue);  // real method called here!
  
  // Explanation:
  // when(spy.computeExpensive()) — Mockito calls the real method to intercept it
  // If the real method has side effects or throws, this fails
  // doReturn().when() bypasses the real method during stub setup

PARTIAL MOCKING with SPY:
  UserService spy = Mockito.spy(new UserService(realRepo));
  
  // Real DB call for save(), but stub the email sending
  doNothing().when(spy).sendWelcomeEmail(any());
  
  User result = spy.registerUser("alice@example.com", "password");
  
  assertNotNull(result.getId());  // real DB generated ID
  verify(spy).sendWelcomeEmail("alice@example.com");  // email override verified

4. SPY vs MOCK — WHEN TO USE WHICH
================================================================

Use MOCK when:
  ✅ Testing a class that has external dependencies (DB, HTTP, email)
  ✅ You want full control over the dependency's behavior
  ✅ You need to verify how the dependency was called
  ✅ The real implementation would be slow or have side effects
  ✅ The dependency doesn't exist yet
  
  Example:
    Testing OrderService — mock OrderRepository (no real DB needed)

Use SPY when:
  ✅ You want to test MOST of the real behavior but override ONE piece
  ✅ Testing legacy code that's hard to fully mock
  ✅ You want to verify calls on a real object
  ✅ The cost of running the real object is acceptable
  ✅ Testing a class that has some methods you want real + some mocked
  
  Example:
    Testing an event publisher that calls various handlers —
    spy on the real publisher to verify notification patterns
    without mocking every handler

WARNING signs that you're using Spy incorrectly:
  ❌ Spying on the class under test (@InjectMocks + @Spy on same class)
  ❌ Overriding ALL methods on a spy (just use a mock then)
  ❌ Spying on external dependencies (use mock instead)

5. STUB — UNDERSTANDING THE TERM
================================================================

In Mockito context, "stubbing" means configuring a mock or spy to
return a specific value when a specific method is called.

Stubbing APIs:
  // when/then style (for mocks, and only safe for spies if method has no side effects)
  when(mock.method(args)).thenReturn(value)
  when(mock.method(args)).thenThrow(exception)
  when(mock.method(args)).thenAnswer(invocationHandler)
  when(mock.method(args)).thenCallRealMethod()
  
  // do/when style (always safe, required for void methods and spies)
  doReturn(value).when(mock).method(args)
  doThrow(exception).when(mock).method(args)
  doNothing().when(mock).voidMethod(args)
  doAnswer(handler).when(mock).method(args)
  doCallRealMethod().when(mock).method(args)

thenAnswer — powerful for dynamic responses:
  when(userRepository.findById(anyString())).thenAnswer(invocation -> {
      String id = invocation.getArgument(0, String.class);
      if (id == null) throw new IllegalArgumentException("ID null");
      return Optional.of(new User(id, "User " + id));
  });
  
  // Access invocation details:
  invocation.getMethod()          // the called method
  invocation.getArguments()       // all arguments as array
  invocation.getArgument(0)       // first argument (raw)
  invocation.getArgument(0, String.class) // typed
  invocation.getMock()            // the mock object
  invocation.callRealMethod()     // call the real method from within answer

6. DEFAULT RETURN VALUES
================================================================

When a mock method is called WITHOUT any stub configured:

Type           | Default Return Value
---------------|----------------------
Object         | null
Optional       | Optional.empty()
List/Set/Map   | empty collection
int/Integer    | 0
long/Long      | 0
double/Double  | 0.0
boolean/Boolean| false
String         | "" (empty string)
Array          | empty array
CompletableFuture | CompletableFuture.completedFuture(null)

Custom default answer:
  OrderRepository mock = Mockito.mock(
      OrderRepository.class,
      Answers.CALLS_REAL_METHODS  // calls real methods by default (like a spy)
  );
  
  OrderRepository strictMock = Mockito.mock(
      OrderRepository.class,
      Answers.RETURNS_SMART_NULLS  // returns "smart" nulls that fail when used
  );
  
  // RETURNS_DEEP_STUBS — chains of calls:
  Order mockOrder = mock(Order.class, RETURNS_DEEP_STUBS);
  when(mockOrder.getCustomer().getAddress().getCity()).thenReturn("London");
  // (careful: DEEP_STUBS often indicates violation of Law of Demeter)

7. RESETTING MOCKS
================================================================

  // Reset all stubs and verifications on a mock
  Mockito.reset(mockOrderRepository);
  
  // Reset multiple mocks
  Mockito.reset(mockRepo, mockEmail, mockInventory);

When to use reset:
  - Usually a sign of poor test design
  - Better approach: create fresh mocks in @BeforeEach
  - Sometimes needed in parameterized tests to re-configure behavior

8. PRACTICAL EXAMPLES — REAL SCENARIOS
================================================================

SCENARIO 1: Testing service with repository dependency
  @ExtendWith(MockitoExtension.class)
  class ProductServiceTest {
      
      @Mock ProductRepository productRepository;
      @InjectMocks ProductService productService;
      
      @Test
      void shouldReturnProduct() {
          Product p = new Product("p-1", "Laptop", 999.99);
          when(productRepository.findById("p-1")).thenReturn(Optional.of(p));
          
          Product result = productService.getProduct("p-1");
          
          assertEquals("Laptop", result.getName());
          verify(productRepository).findById("p-1");
      }
      
      @Test
      void shouldThrowWhenProductNotFound() {
          when(productRepository.findById("bad")).thenReturn(Optional.empty());
          
          assertThrows(ProductNotFoundException.class, 
              () -> productService.getProduct("bad"));
          
          verify(productRepository).findById("bad");
      }
  }

SCENARIO 2: Spy for logging/auditing
  @Test
  void auditServiceShouldLogAllOperations() {
      AuditService real = new AuditService(new AuditRepository());
      AuditService spy = Mockito.spy(real);
      
      UserService userService = new UserService(mockRepo, spy);
      
      userService.createUser(new User("alice", "admin"));
      userService.deleteUser("user-123");
      
      // Verify real audit log was called (real implementation runs)
      verify(spy).log("CREATE", "alice");
      verify(spy).log("DELETE", "user-123");
      
      // Verify order matters
      InOrder order = inOrder(spy);
      order.verify(spy).log("CREATE", "alice");
      order.verify(spy).log("DELETE", "user-123");
  }

SCENARIO 3: Mixing Mock and real with Spy
  @Test
  void orderProcessorShouldRetryOnTransientFailure() {
      OrderProcessor real = new OrderProcessor(mockOrderRepo, mockEmail);
      OrderProcessor spy = Mockito.spy(real);
      
      // Fail first two calls, succeed on third
      doThrow(new TransientException())
          .doThrow(new TransientException())
          .doCallRealMethod()
          .when(spy).processWithRetry(any());
      
      spy.process(order);  // should succeed on 3rd attempt
      
      verify(spy, times(3)).processWithRetry(any());
  }

9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between a Mock and a Spy in Mockito?
A: Mock: fake object with no real implementation. All methods return
   default values unless stubbed. Full control over behavior and verification.
   Spy: wraps a REAL object. Real methods execute by default. Can selectively
   override some methods. Useful for partial mocking of real objects.

Q: When would you use a Spy instead of a Mock?
A: When you need MOST of the real behavior but want to override specific
   methods (e.g., avoid network calls while keeping business logic).
   Also useful for testing legacy code or when you want to verify that
   a real object was called with specific arguments.

Q: Why should you use doReturn() instead of when().thenReturn() with spies?
A: when(spy.method()) actually CALLS the real method during stub setup
   to intercept it. If the real method has side effects or throws an
   exception, the setup fails. doReturn().when() bypasses the real method.

Q: What is the default return value of a Mockito mock for various types?
A: null for objects, 0 for primitives, false for boolean, empty string for String,
   empty collections for List/Map/Set, Optional.empty() for Optional.

Q: What does "stubbing" mean in Mockito?
A: Configuring a mock or spy to return a specific value (or throw an exception)
   when a specific method is called. Using when().thenReturn() or doReturn().when().

Q: Can you mock a final class in Mockito?
A: Yes, with Mockito 5 (mockito-core includes inline mocking by default).
   Previously required mockito-inline dependency. Uses JVM instrumentation
   rather than subclassing to mock final classes and methods.

Q: What happens if you call a mock method without stubbing it?
A: Returns the default value for the return type: null for objects,
   empty for collections, 0 for numeric primitives, false for boolean.
   With RETURNS_SMART_NULLS, the null object throws an exception when used.
