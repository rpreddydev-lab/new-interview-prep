================================================================
JUNIT 5 TEST LIFECYCLE AND EXTENSIONS
Complete Interview Preparation Guide
================================================================

1. TEST INSTANCE LIFECYCLE
================================================================
JUnit 5 creates a NEW test class instance for each @Test method by default.
This ensures test isolation.

TWO LIFECYCLE MODES:

  PER_METHOD (default)
    - Fresh instance for every test method
    - No shared state between tests
    - @BeforeAll / @AfterAll MUST be static
  
  PER_CLASS
    - Single instance for all test methods
    - @BeforeAll / @AfterAll can be instance methods (non-static)
    - Shared state — tests can interfere with each other
    - Use carefully

Setting PER_CLASS:
  @TestInstance(TestInstance.Lifecycle.PER_CLASS)
  class MyTest {
      
      private int counter = 0;  // shared across tests
      
      @BeforeAll
      void startOnce() { /* non-static OK */ }
      
      @Test void test1() { counter++; }
      @Test void test2() { System.out.println(counter); /* might be 1 */ }
  }

Global default via junit-platform.properties:
  # src/test/resources/junit-platform.properties
  junit.jupiter.testinstance.lifecycle.default = per_class

2. EXTENSION MODEL
================================================================

JUnit 5's extension model replaces JUnit 4's:
  - @RunWith(Runner.class)
  - @Rule and @ClassRule

A single @ExtendWith replaces all these.

REGISTERING EXTENSIONS:
  // Declarative (most common)
  @ExtendWith(MockitoExtension.class)
  @ExtendWith(SpringExtension.class)
  class MyTest { }
  
  // Multiple extensions
  @ExtendWith({MockitoExtension.class, TimingExtension.class})
  class MyTest { }
  
  // Programmatic (more control)
  @RegisterExtension
  static TimingExtension timing = new TimingExtension();
  
  // Auto-registration (service loader)
  // META-INF/services/org.junit.jupiter.api.extension.Extension
  // com.example.MyExtension

COMMON BUILT-IN EXTENSIONS:
  MockitoExtension      — enables @Mock, @Spy, @InjectMocks
  SpringExtension       — loads Spring ApplicationContext
  TempDirectoryExtension — provides @TempDir
  WireMockExtension     — starts WireMock server

3. EXTENSION POINTS — INTERFACES
================================================================

JUnit 5 extensions can implement these callback interfaces:

LIFECYCLE CALLBACKS:
  BeforeAllCallback          — before all tests (once)
  BeforeEachCallback         — before each test
  BeforeTestExecutionCallback — immediately before test method
  AfterTestExecutionCallback  — immediately after test method
  AfterEachCallback          — after each test
  AfterAllCallback           — after all tests

TEST MODIFICATION:
  TestInstanceFactory        — create test instances
  TestInstancePostProcessor  — post-process test instances
  ParameterResolver          — inject parameters into test methods
  ExecutionCondition         — decide if test should run

EXCEPTION HANDLING:
  TestExecutionExceptionHandler — handle exceptions thrown by tests

TEST DISCOVERY:
  TestTemplateInvocationContextProvider — for @TestTemplate

REPORTING:
  BeforeTestExecutionCallback + AfterTestExecutionCallback
  → Measure test duration, log results

4. WRITING A CUSTOM EXTENSION
================================================================

EXAMPLE 1 — Timing Extension:
  public class TimingExtension 
      implements BeforeTestExecutionCallback, AfterTestExecutionCallback {
      
      private static final String START_TIME = "startTime";
      
      @Override
      public void beforeTestExecution(ExtensionContext context) {
          context.getStore(ExtensionContext.Namespace.GLOBAL)
              .put(START_TIME, System.currentTimeMillis());
      }
      
      @Override
      public void afterTestExecution(ExtensionContext context) {
          long startTime = context.getStore(ExtensionContext.Namespace.GLOBAL)
              .get(START_TIME, long.class);
          long duration = System.currentTimeMillis() - startTime;
          
          System.out.printf("%-40s %d ms%n",
              context.getRequiredTestMethod().getName(), duration);
      }
  }
  
  // Usage:
  @ExtendWith(TimingExtension.class)
  class PerformanceCriticalTests { }

EXAMPLE 2 — Security Context Extension:
  public class SecurityContextExtension 
      implements BeforeEachCallback, AfterEachCallback {
      
      @Override
      public void beforeEach(ExtensionContext context) {
          // Check for @WithMockUser annotation on test method
          context.getRequiredTestMethod()
              .getAnnotation(WithMockUser.class);
          // Set up security context
          SecurityContextHolder.getContext()
              .setAuthentication(createMockAuthentication("testUser", "ROLE_USER"));
      }
      
      @Override
      public void afterEach(ExtensionContext context) {
          SecurityContextHolder.clearContext();
      }
      
      private Authentication createMockAuthentication(String user, String role) {
          List<GrantedAuthority> authorities = 
              AuthorityUtils.createAuthorityList(role);
          return new UsernamePasswordAuthenticationToken(user, "password", authorities);
      }
  }

EXAMPLE 3 — ExecutionCondition (conditional test):
  public class OnlyOnCICondition implements ExecutionCondition {
      
      @Override
      public ConditionEvaluationResult evaluateExecutionCondition(ExtensionContext ctx) {
          String ciEnv = System.getenv("CI");
          if ("true".equalsIgnoreCase(ciEnv)) {
              return ConditionEvaluationResult.enabled("Running on CI");
          }
          return ConditionEvaluationResult.disabled("Skipping: not on CI");
      }
  }
  
  // Custom annotation:
  @Target({ElementType.TYPE, ElementType.METHOD})
  @Retention(RetentionPolicy.RUNTIME)
  @ExtendWith(OnlyOnCICondition.class)
  public @interface OnlyOnCI { }
  
  // Usage:
  @Test
  @OnlyOnCI
  void shouldRunOnlyInCI() { ... }

EXAMPLE 4 — ParameterResolver (inject custom objects):
  public class DatabaseExtension 
      implements BeforeEachCallback, AfterEachCallback, ParameterResolver {
      
      private TestDatabase db;
      
      @Override
      public void beforeEach(ExtensionContext context) {
          db = new TestDatabase();
          db.start();
      }
      
      @Override
      public void afterEach(ExtensionContext context) {
          db.stop();
      }
      
      @Override
      public boolean supportsParameter(ParameterContext paramCtx, ExtensionContext extCtx) {
          return paramCtx.getParameter().getType() == TestDatabase.class;
      }
      
      @Override
      public Object resolveParameter(ParameterContext paramCtx, ExtensionContext extCtx) {
          return db;
      }
  }
  
  // Test that receives injected DB:
  @ExtendWith(DatabaseExtension.class)
  class MyTest {
      
      @Test
      void shouldQueryDatabase(TestDatabase db) {
          // db is injected by the extension
          db.execute("INSERT INTO users VALUES (1, 'Alice')");
          assertEquals(1, db.count("users"));
      }
  }

5. EXTENDWITH VS REGISTEREXTENSION
================================================================

@ExtendWith (declarative annotation):
  - Applied at class or method level
  - Extension instantiated by JUnit (no control over construction)
  - Cannot pass configuration to extension constructor
  
  @ExtendWith(WireMockExtension.class)
  class ApiTest { }

@RegisterExtension (programmatic field):
  - Extension instance is created manually (full control)
  - Can configure extension with constructor parameters
  - Can be static (class-scoped) or instance (test-scoped)
  
  @RegisterExtension
  static WireMockExtension wireMock = WireMockExtension.newInstance()
      .options(wireMockConfig().port(8080))
      .build();
  
  // Static = shared across all tests
  // Instance = new extension per test

6. EXTENSION CONTEXT AND STORE
================================================================

ExtensionContext provides:
  - Test method, class, annotations access
  - Store for sharing data between extension callbacks

Store usage:
  Namespace namespace = ExtensionContext.Namespace.create(MyExtension.class);
  ExtensionContext.Store store = context.getStore(namespace);
  
  // Put
  store.put("key", value);
  
  // Get with type
  String value = store.get("key", String.class);
  
  // Get or compute
  store.getOrComputeIfAbsent("key", k -> new ExpensiveObject());
  
  // Remove
  store.remove("key");

The store is automatically cleaned up when the associated scope ends.

7. CONDITIONAL TEST EXECUTION
================================================================

Built-in conditions:

  @EnabledOnOs(OS.MAC)
  @EnabledOnOs({OS.LINUX, OS.MAC})
  @DisabledOnOs(OS.WINDOWS)
  
  @EnabledOnJre(JRE.JAVA_17)
  @EnabledForJreRange(min = JRE.JAVA_11, max = JRE.JAVA_21)
  @DisabledOnJre(JRE.JAVA_8)
  
  @EnabledIfSystemProperty(named = "user.country", matches = "US")
  @DisabledIfSystemProperty(named = "env", matches = "production")
  
  @EnabledIfEnvironmentVariable(named = "CI", matches = "true")
  @DisabledIfEnvironmentVariable(named = "SKIP_INTEGRATION", matches = "true")
  
  // Custom condition via script (requires Groovy/Nashorn):
  @EnabledIf("2 * 3 == 6")
  @EnabledIf("systemProperty.get('user.country') == 'US'")
  @EnabledIf("'${os.name}'.toLowerCase().contains('linux')")
  
  // Programmatic conditions
  @EnabledIf(value = "isCI", disabledReason = "Only run on CI")
  boolean isCI() {
      return "true".equals(System.getenv("CI"));
  }

8. @TestMethodOrder — Controlling Test Order
================================================================

By default: JUnit 5 does NOT guarantee test execution order.
Use @TestMethodOrder to make order explicit.

  @TestMethodOrder(MethodOrderer.OrderAnnotation.class)
  class OrderedIntegrationTest {
      
      @Test @Order(1)
      void setupTestData() { }
      
      @Test @Order(2)
      void processOrder() { }
      
      @Test @Order(3)
      void verifyOrderStatus() { }
      
      @Test @Order(Integer.MAX_VALUE)  // run last
      void cleanup() { }
  }

Available orderers:
  OrderAnnotation   — uses @Order annotation value
  Random            — random order (with seed for reproducibility)
  MethodName        — alphabetical by method name
  DisplayName       — alphabetical by display name
  
  // Random with fixed seed for reproducibility
  @TestMethodOrder(MethodOrderer.Random.class)
  @RandomizedTest(seed = 42L)
  class RandomOrderTest { }

Global order:
  # junit-platform.properties
  junit.jupiter.testmethod.order.default = \
      org.junit.jupiter.api.MethodOrderer$OrderAnnotation

WARNING: Tests that require specific ordering are usually a design smell.
  Order-dependent tests are brittle and suggest shared state.
  Use @Order only for integration tests that intentionally have a workflow.

9. EXTENSION COMPOSITION AND META-ANNOTATIONS
================================================================

Create custom composed annotations:

  @Target(ElementType.TYPE)
  @Retention(RetentionPolicy.RUNTIME)
  @ExtendWith(MockitoExtension.class)
  @ExtendWith(TimingExtension.class)
  public @interface MockitoAndTiming { }
  
  // Spring Security test meta-annotation:
  @Target(ElementType.METHOD)
  @Retention(RetentionPolicy.RUNTIME)
  @WithMockUser(username = "admin", roles = {"ADMIN"})
  public @interface WithAdminUser { }
  
  // Usage is cleaner:
  @MockitoAndTiming
  class MyTest { }
  
  @Test
  @WithAdminUser
  void adminOnlyOperation() { }

10. PARALLEL TEST EXECUTION
================================================================

JUnit 5 supports running tests in parallel:

  # junit-platform.properties
  junit.jupiter.execution.parallel.enabled = true
  junit.jupiter.execution.parallel.mode.default = concurrent
  junit.jupiter.execution.parallel.mode.classes.default = concurrent
  
  # Thread pool configuration
  junit.jupiter.execution.parallel.config.strategy = dynamic
  junit.jupiter.execution.parallel.config.dynamic.factor = 2

Controlling parallelism per class/method:
  @Execution(ExecutionMode.CONCURRENT)
  class ParallelTest { }
  
  @Execution(ExecutionMode.SAME_THREAD)
  class SequentialTest { }

WARNING: Parallel tests require thread-safe code.
  - No shared mutable static state
  - Each test must be completely isolated
  - Watch for Spring context sharing issues

11. INTERVIEW QUESTIONS ON LIFECYCLE AND EXTENSIONS
================================================================

Q: What is the difference between PER_METHOD and PER_CLASS lifecycle?
A: PER_METHOD (default): new test instance per test method, maximum isolation.
   PER_CLASS: one instance shared by all tests, @BeforeAll can be non-static,
   but tests can share state which risks test interdependence.

Q: What replaces JUnit 4's @RunWith and @Rule in JUnit 5?
A: @ExtendWith replaces @RunWith.
   @RegisterExtension replaces @Rule/@ClassRule.
   Extensions in JUnit 5 are more composable — multiple can be added.

Q: What interfaces does a JUnit 5 extension implement?
A: Depends on what it needs to do:
   BeforeEachCallback/AfterEachCallback for lifecycle hooks,
   ParameterResolver for parameter injection,
   ExecutionCondition for conditional execution,
   TestInstanceFactory for custom instantiation.

Q: How do you control test execution order in JUnit 5?
A: @TestMethodOrder(MethodOrderer.OrderAnnotation.class) on the class,
   then @Order(n) on each test method. Usually only needed for integration
   tests with workflow dependencies.

Q: How do you share state between JUnit 5 extension callbacks?
A: Using the ExtensionContext.Store. Each extension has its own namespace.
   Data is stored as key-value pairs and automatically cleaned up.

Q: How do you run JUnit 5 tests in parallel?
A: Enable via junit-platform.properties:
   junit.jupiter.execution.parallel.enabled = true
   junit.jupiter.execution.parallel.mode.default = concurrent
   Use @Execution(SAME_THREAD) for tests that can't be parallelized.
