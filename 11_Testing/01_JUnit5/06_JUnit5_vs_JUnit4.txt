================================================================
JUNIT 5 vs JUNIT 4 — COMPLETE COMPARISON GUIDE
Complete Interview Preparation Guide
================================================================

1. OVERVIEW
================================================================
JUnit 4 was released in 2006 and dominated Java testing for over a decade.
JUnit 5 was released in 2017 as a complete rewrite with modern Java features.

Key motivation for JUnit 5:
  - JUnit 4 had a monolithic architecture (single jar)
  - Limited extensibility (only one @RunWith)
  - Poor Java 8+ integration (no lambdas, streams)
  - No native support for nested tests, dynamic tests, parameterized tests
  - Extension model was complex (Runners + Rules + ClassRules)

================================================================
2. ARCHITECTURE COMPARISON
================================================================

JUnit 4:
  - Single monolithic jar: junit-4.13.2.jar
  - Everything bundled together
  - Hamcrest included (org.hamcrest)

JUnit 5:
  - Modular: 3 sub-projects
    - JUnit Platform (infrastructure, build tool integration)
    - JUnit Jupiter (new API for writing tests)
    - JUnit Vintage (backward compatibility for JUnit 3/4)
  - Supports running multiple test engines simultaneously

================================================================

import org.junit.After;             import org.junit.jupiter.api.AfterEach;

import org.junit.runner.RunWith;    import org.junit.jupiter.api.extension.ExtendWith;
import org.junit.rules.ExpectedException; (removed — use assertThrows)

4. ANNOTATION COMPARISON TABLE
================================================================

JUnit 4 Annotation        | JUnit 5 Equivalent      | Notes
--------------------------|-------------------------|--------------------------------
@Test                     | @Test                   | Different import package
@Before                   | @BeforeEach             | More descriptive name
@After                    | @AfterEach              | More descriptive name
@BeforeClass              | @BeforeAll              | More descriptive name
@AfterClass               | @AfterAll               | More descriptive name
@Ignore                   | @Disabled               | +optional reason message
@RunWith(...)             | @ExtendWith(...)         | Multiple extensions allowed
@Rule                     | @ExtendWith or           | Extensions replace rules
                          | @RegisterExtension      |
@ClassRule                | @RegisterExtension(static) | Static field extension
@Category(...)            | @Tag(...)               | Better filtering support
@Test(expected=...)       | assertThrows(...)       | Returns exception for inspection
@Test(timeout=...)        | @Timeout(...)           | More granular timeout control
@FixMethodOrder(...)      | @TestMethodOrder(...)   | More orderers available
@RunWith(Parameterized)   | @ParameterizedTest      | Much more flexible
N/A                       | @DisplayName            | Human-readable names
N/A                       | @Nested                 | Inner test classes
N/A                       | @TestFactory            | Dynamic tests
N/A                       | @RepeatedTest           | Repeat N times

5. TEST CLASS AND METHOD VISIBILITY
================================================================

JUnit 4:
  - Test class MUST be public
  - Test methods MUST be public
  - Test methods MUST return void
  - Test methods MUST take no parameters (except @Parameterized)

  public class CalculatorTest {
      @Test
      public void shouldAdd() {  // public required
          assertEquals(5, calculator.add(2, 3));
      }
  }

JUnit 5:
  - Test class can be package-private (no public required)
  - Test methods can be package-private
  - Test methods must return void or a supported type (@TestFactory)
  - Test methods CAN accept parameters (via ParameterResolver)

  class CalculatorTest {  // no public needed
      @Test
      void shouldAdd() {  // no public needed
          assertEquals(5, calculator.add(2, 3));
      }
  }

6. ASSERTIONS COMPARISON
================================================================

JUnit 4:                                JUnit 5:
────────────────────────────────────────────────────────────
import static org.junit.Assert.*;       import static org.junit.jupiter.api.Assertions.*;

assertEquals(expected, actual)          assertEquals(expected, actual)
assertEquals(expected, actual, msg)     assertEquals(expected, actual, "message")
                                        assertEquals(expected, actual, () -> "lazy msg")

// Exception testing
@Test(expected = NullPointerException.class)
void test() { service.call(null); }     // JUnit 4 - can't inspect exception

// JUnit 5:
NullPointerException ex = assertThrows(
    NullPointerException.class,
    () -> service.call(null));
assertEquals("null input", ex.getMessage()); // Can inspect exception!

// Grouped assertions
// JUnit 4: no equivalent                JUnit 5:
                                        assertAll(
                                            () -> assertEquals("Alice", u.getName()),
                                            () -> assertEquals(30, u.getAge())
                                        );

// Message evaluation
// JUnit 4: message always computed      JUnit 5: lazy evaluation
assertEquals(exp, act,                  assertEquals(exp, act,
    "complex " + expensive.toString()); // lazy: () -> "complex " + expensive)
                                        // computed ONLY on failure

7. EXCEPTION TESTING COMPARISON
================================================================

JUnit 4 — THREE WAYS (all problematic):
  
  Way 1: @Test(expected = ...)
    @Test(expected = IllegalArgumentException.class)
    void testException() {
        service.process(null);  // PROBLEM: can't verify message
        // Any IAE thrown anywhere in method passes — ambiguous!
    }
  
  Way 2: @Rule ExpectedException
    @Rule
    public ExpectedException thrown = ExpectedException.none();
    
    @Test
    void testException() {
        thrown.expect(IllegalArgumentException.class);
        thrown.expectMessage("null input");
        service.process(null);
        // PROBLEM: rule setup before method call — confusing order
    }
  
  Way 3: try-catch (verbose)
    @Test
    void testException() {
        try {
            service.process(null);
            fail("Expected exception");
        } catch (IllegalArgumentException e) {
            assertEquals("null input", e.getMessage());
        }
    }

JUnit 5 — ONE CLEAN WAY:
  @Test
  void testException() {
      IllegalArgumentException ex = assertThrows(
          IllegalArgumentException.class,
          () -> service.process(null)
      );
      assertEquals("null input", ex.getMessage());
      // Clean, explicit, verifiable
  }

8. RUNNER AND EXTENSION MODEL COMPARISON
================================================================

JUnit 4 — RUNNER (@RunWith):
  - Only ONE runner per class
  - Can't combine runners (e.g., can't use both MockitoRunner and SpringRunner)
  
  @RunWith(MockitoJUnitRunner.class)
  class MockitoTest { }
  
  @RunWith(SpringJUnit4ClassRunner.class)
  class SpringTest { }
  
  // PROBLEM: Can't do @RunWith(MockitoRunner + SpringRunner)

JUnit 4 — RULES (@Rule / @ClassRule):
  @Rule
  public TemporaryFolder tempFolder = new TemporaryFolder();
  
  @Rule
  public ExpectedException expectedException = ExpectedException.none();
  
  @ClassRule
  public static WireMockRule wireMock = new WireMockRule(8080);
  
  // Multiple rules possible but complex

JUnit 5 — EXTENSIONS (@ExtendWith):
  // Multiple extensions! No limitation!
  @ExtendWith(MockitoExtension.class)
  @ExtendWith(SpringExtension.class)
  @ExtendWith(TimingExtension.class)
  class IntegrationTest { }
  
  // OR programmatic with configuration:
  @RegisterExtension
  static WireMockExtension wireMock = WireMockExtension.newInstance()
      .options(wireMockConfig().port(8080))
      .build();

9. PARAMETERIZED TESTS COMPARISON
================================================================

JUnit 4 — Cumbersome:
  @RunWith(Parameterized.class)
  public class CalculatorTest {
      
      private int a, b, expected;
      
      public CalculatorTest(int a, int b, int expected) {
          this.a = a;
          this.b = b;
          this.expected = expected;
      }
      
      @Parameterized.Parameters
      public static Collection<Object[]> data() {
          return Arrays.asList(new Object[][]{
              {1, 1, 2},
              {5, 3, 8},
              {0, 0, 0}
          });
      }
      
      @Test
      public void shouldAdd() {
          assertEquals(expected, calculator.add(a, b));
      }
  }
  // PROBLEMS:
  // - Separate runner (@RunWith)
  // - Constructor injection (ugly)
  // - Only ONE parameterized test per class!
  // - Confusing data format

JUnit 5 — Clean and Flexible:
  class CalculatorTest {
      
      @ParameterizedTest
      @CsvSource({"1, 1, 2", "5, 3, 8", "0, 0, 0"})
      void shouldAdd(int a, int b, int expected) {
          assertEquals(expected, calculator.add(a, b));
      }
      
      // Multiple parameterized tests in same class!
      @ParameterizedTest
      @CsvSource({"10, 5, 2", "100, 10, 10"})
      void shouldDivide(int dividend, int divisor, int expected) {
          assertEquals(expected, calculator.divide(dividend, divisor));
      }
      
      // Non-parameterized tests in same class too!
      @Test
      void shouldHandleNegativeNumbers() { }
  }

10. NESTED TESTS
================================================================

JUnit 4: No native support. Developers used workarounds.

JUnit 5:
  @DisplayName("OrderService")
  class OrderServiceTest {
      
      @Nested
      @DisplayName("when placing an order")
      class WhenPlacingOrder {
          @Test void shouldSaveToDb() { }
          @Test void shouldSendEmail() { }
      }
      
      @Nested
      @DisplayName("when cancelling an order")
      class WhenCancellingOrder {
          @Test void shouldUpdateStatus() { }
          @Test void shouldRestoreInventory() { }
      }
  }

11. DYNAMIC TESTS
================================================================

JUnit 4: Not supported.

JUnit 5:
  @TestFactory
  Stream<DynamicTest> dynamicTests() {
      return Stream.of("Java", "Python", "Go")
          .map(lang -> dynamicTest(
              lang + " should be a programming language",
              () -> assertTrue(languageRegistry.contains(lang))
          ));
  }

12. COMPLETE MIGRATION EXAMPLE
================================================================

JUnit 4 (BEFORE):
  import org.junit.*;
  import static org.junit.Assert.*;
  import org.junit.runner.RunWith;
  import org.mockito.junit.MockitoJUnitRunner;
  import org.mockito.Mock;
  import org.mockito.InjectMocks;
  
  @RunWith(MockitoJUnitRunner.class)
  public class OrderServiceTest {
      
      @Mock
      private OrderRepository orderRepository;
      
      @InjectMocks
      private OrderService orderService;
      
      @Before
      public void setUp() {
          // setup
      }
      
      @After
      public void tearDown() {
          // cleanup
      }
      
      @BeforeClass
      public static void initOnce() { }
      
      @AfterClass
      public static void cleanupOnce() { }
      
      @Test
      public void shouldPlaceOrder() {
          // ...
      }
      
      @Test(expected = IllegalArgumentException.class)
      public void shouldThrowForNullOrder() {
          orderService.placeOrder(null);
      }
      
      @Ignore("TODO: fix this")
      @Test
      public void pendingTest() { }
  }

JUnit 5 (AFTER):
  import org.junit.jupiter.api.*;
  import static org.junit.jupiter.api.Assertions.*;
  import org.junit.jupiter.api.extension.ExtendWith;
  import org.mockito.junit.jupiter.MockitoExtension;
  import org.mockito.Mock;
  import org.mockito.InjectMocks;
  
  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      
      @Mock
      OrderRepository orderRepository;
      
      @InjectMocks
      OrderService orderService;
      
      @BeforeEach
      void setUp() {
          // setup (non-public, non-static)
      }
      
      @AfterEach
      void tearDown() {
          // cleanup
      }
      
      @BeforeAll
      static void initOnce() { }
      
      @AfterAll
      static void cleanupOnce() { }
      
      @Test
      void shouldPlaceOrder() {  // no public needed
          // ...
      }
      
      @Test
      void shouldThrowForNullOrder() {
          // Returns exception for inspection!
          IllegalArgumentException ex = assertThrows(
              IllegalArgumentException.class,
              () -> orderService.placeOrder(null)
          );
          assertTrue(ex.getMessage().contains("null"));
      }
      
      @Disabled("TODO: fix this")
      @Test
      void pendingTest() { }
  }

13. RUNNING JUNIT 4 TESTS IN JUNIT 5
================================================================

JUnit Vintage allows old JUnit 4 tests to run on the JUnit 5 platform.

Dependency:
  <dependency>
      <groupId>org.junit.vintage</groupId>
      <artifactId>junit-vintage-engine</artifactId>
      <scope>test</scope>
      <exclusions>
          <exclusion>
              <groupId>org.hamcrest</groupId>
              <artifactId>hamcrest-core</artifactId>
          </exclusion>
      </exclusions>
  </dependency>

Note: spring-boot-starter-test EXCLUDES JUnit Vintage by default.
To re-include it:
  <!-- Don't exclude vintage if you need to run JUnit 4 tests -->

14. MIGRATION TIPS
================================================================

1. Start with annotations: @Before→@BeforeEach, @After→@AfterEach, etc.
2. Remove public from test classes and methods.
3. Replace @Test(expected=...) with assertThrows(...).
4. Replace @RunWith with @ExtendWith.
5. Update imports from org.junit.* to org.junit.jupiter.api.*
6. Replace Assert.* with Assertions.* (or use AssertJ)
7. Replace @Ignore with @Disabled
8. Replace @Category with @Tag

Automated migration:
  Use IntelliJ IDEA's "Migrate JUnit 4 to 5" intention action,
  or the OpenRewrite recipe for JUnit 5 migration.

15. INTERVIEW QUESTIONS ON JUNIT 4 vs JUNIT 5
================================================================

Q: What are the key differences between JUnit 4 and JUnit 5?
A: Architecture: JUnit 5 is modular (Platform + Jupiter + Vintage).
   Extensions: Multiple @ExtendWith vs single @RunWith.
   Annotations renamed: @Before→@BeforeEach, @BeforeClass→@BeforeAll.
   Exceptions: assertThrows() vs @Test(expected=...).
   New features: @Nested, @TestFactory, @ParameterizedTest improvements.
   Visibility: no public required for classes/methods.

Q: How do you test exceptions in JUnit 5 vs JUnit 4?
A: JUnit 4: @Test(expected = ...) or ExpectedException rule — can't inspect.
   JUnit 5: assertThrows() — returns the exception for full inspection.

Q: Can JUnit 4 tests run with JUnit 5?
A: Yes, using junit-vintage-engine which provides backward compatibility.
   JUnit Vintage allows existing JUnit 4 (and 3) tests to run on the JUnit 5 platform.

Q: What replaced @RunWith in JUnit 5?
A: @ExtendWith. The major improvement is that multiple extensions can be combined,
   solving the single-runner limitation of JUnit 4.

Q: What are the improvements to parameterized tests in JUnit 5?
A: JUnit 4 required a separate @RunWith(Parameterized.class) and ugly constructor
   injection. JUnit 5 uses @ParameterizedTest directly on each test method with
   rich sources: @ValueSource, @CsvSource, @MethodSource, @EnumSource, etc.
   Multiple parameterized tests can coexist in the same class.

Q: What is JUnit Vintage?
A: JUnit Vintage is a sub-module that provides a JUnit 5 TestEngine for
   running JUnit 3 and JUnit 4 tests. Enables gradual migration.
