PERFORMANCE TESTING — JMH MICRO-BENCHMARKING
Complete Interview Preparation Guide

1. WHAT IS JMH?
================================================================

JMH (Java Microbenchmark Harness) is the official benchmarking framework
from OpenJDK. It solves the inherent difficulties of benchmarking on the JVM:

Problems JMH solves:
  JIT Compilation  — JVM optimizes hot methods over time → early measures are slow
  Dead Code Elim.  — JVM might eliminate code that appears to do nothing
  Branch Prediction — CPU optimizes repeated same-direction branches
  Constant Folding — JVM precomputes constant expressions at compile time
  GC Pauses        — Full GC during benchmark skews results
  ClassLoader init — First use of a class is slow

JMH handles all of these through:
  - Warmup iterations (let JIT optimize before measuring)
  - Blackhole (prevent dead code elimination)
  - Multiple forks (fresh JVM per benchmark run)
  - Multiple measurement iterations (statistical significance)

3. BASIC BENCHMARK
================================================================

  @BenchmarkMode(Mode.AverageTime)   // measure average execution time
  @OutputTimeUnit(TimeUnit.MICROSECONDS)
  @Warmup(iterations = 5, time = 1)  // 5 warmup iterations, 1s each
  @Measurement(iterations = 10, time = 1) // 10 measurement iterations
  @Fork(2)                           // run in 2 separate JVM forks
  @State(Scope.Benchmark)            // benchmark state shared across all threads
  public class StringConcatBenchmark {
      
      private static final int N = 1000;
      
      @Benchmark
      public String concatenateWithPlus() {
          String result = "";
          for (int i = 0; i < N; i++) {
              result += i;  // creates new String each iteration
          }
          return result;
      }
      
      @Benchmark
      public String concatenateWithStringBuilder() {
          StringBuilder sb = new StringBuilder();
          for (int i = 0; i < N; i++) {
              sb.append(i);
          }
          return sb.toString();
      }
  }
  
  // Results:
  // StringConcatBenchmark.concatenateWithPlus           avgt   20   2345.123 ± 45.67 us/op
  // StringConcatBenchmark.concatenateWithStringBuilder  avgt   20    123.456 ±  2.34 us/op
  // StringBuilder is ~19x faster for 1000 concatenations

4. BENCHMARK MODES
================================================================

  @BenchmarkMode(Mode.Throughput)    // operations per unit time (ops/s)
  @BenchmarkMode(Mode.AverageTime)   // average time per operation
  @BenchmarkMode(Mode.SampleTime)    // distribution of time per op (percentiles)
  @BenchmarkMode(Mode.SingleShotTime)// single invocation time (no warmup)
  @BenchmarkMode(Mode.All)           // all modes at once

  Best practices:
    - AverageTime: for absolute performance (how fast is this method?)
    - Throughput:  for capacity (how many ops/sec can this handle?)
    - SampleTime:  for latency distribution (p99, max)

5. STATE OBJECTS AND SCOPE
================================================================

  @State — holder for benchmark data, avoiding recomputation per iteration

  @State(Scope.Benchmark)  // one instance shared by ALL threads
  @State(Scope.Thread)     // one instance per thread (default for concurrency tests)
  @State(Scope.Group)      // one instance per thread group
  
  Example with state:
  @State(Scope.Benchmark)
  public class SearchBenchmarkState {
      
      public List<Integer> data;
      
      @Setup(Level.Trial)    // before ALL iterations
      public void setup() {
          data = new ArrayList<>();
          for (int i = 0; i < 1_000_000; i++) {
              data.add(ThreadLocalRandom.current().nextInt(0, 1_000_000));
          }
      }
      
      @TearDown(Level.Trial)
      public void tearDown() {
          data = null;
      }
  }
  
  @Benchmark
  public int linearSearch(SearchBenchmarkState state) {
      int target = 500000;
      for (int val : state.data) {
          if (val == target) return val;
      }
      return -1;
  }

6. BLACKHOLE — PREVENTING DEAD CODE ELIMINATION
================================================================

  JVM might see that a return value is never used and eliminate the method.
  
  // WRONG: JVM might optimize away the entire computation
  @Benchmark
  public void badBenchmark() {
      Math.sqrt(100.0);  // result unused — JVM eliminates this!
  }
  
  // CORRECT: return the result (JMH implicitly uses it)
  @Benchmark
  public double goodBenchmark1() {
      return Math.sqrt(100.0);  // return forces computation
  }
  
  // CORRECT: use Blackhole explicitly (for multiple values)
  @Benchmark
  public void goodBenchmark2(Blackhole bh) {
      bh.consume(Math.sqrt(100.0));
      bh.consume(Math.log(100.0));
      bh.consume(Math.sin(1.5));
  }

7. PRACTICAL EXAMPLE — COMPARING COLLECTION OPERATIONS
================================================================

  @BenchmarkMode(Mode.AverageTime)
  @OutputTimeUnit(TimeUnit.NANOSECONDS)
  @Warmup(iterations = 3, time = 1)
  @Measurement(iterations = 5, time = 1)
  @Fork(1)
  @State(Scope.Benchmark)
  public class CollectionBenchmark {
      
      private List<Integer> arrayList;
      private LinkedList<Integer> linkedList;
      
      @Param({"100", "1000", "10000"})  // run with different N values
      private int size;
      
      @Setup
      public void setup() {
          arrayList = new ArrayList<>();
          linkedList = new LinkedList<>();
          for (int i = 0; i < size; i++) {
              arrayList.add(i);
              linkedList.add(i);
          }
      }
      
      @Benchmark
      public int arrayListGet() {
          return arrayList.get(size / 2);  // O(1) random access
      }
      
      @Benchmark
      public int linkedListGet() {
          return linkedList.get(size / 2); // O(n) traversal
      }
      
      @Benchmark
      public void arrayListAddFirst(Blackhole bh) {
          arrayList.add(0, 99);            // O(n) shift
          bh.consume(arrayList.remove(0)); // cleanup to avoid OOM
      }
      
      @Benchmark
      public void linkedListAddFirst(Blackhole bh) {
          linkedList.addFirst(99);         // O(1)
          bh.consume(linkedList.removeFirst());
      }
  }
  
  // Expected results show:
  // - arrayListGet is MUCH faster than linkedListGet (O(1) vs O(n))
  // - linkedListAddFirst is FASTER than arrayListAddFirst for large N

8. RUNNING JMH BENCHMARKS
================================================================

  // Programmatic runner (run from main or test)
  public static void main(String[] args) throws Exception {
      Options opt = new OptionsBuilder()
          .include(StringConcatBenchmark.class.getSimpleName())
          .warmupIterations(5)
          .measurementIterations(10)
          .forks(2)
          .build();
      new Runner(opt).run();
  }
  
  // Or: build uber-jar and run
  // mvn package -DskipTests
  // java -jar target/benchmarks.jar -wi 5 -i 10 -f 2

  <plugin>
      <groupId>org.codehaus.mojo</groupId>

              <argument>-i</argument><argument>10</argument>
              <argument>-f</argument><argument>2</argument>
          </arguments>
      </configuration>
  </plugin>

9. INTERVIEW QUESTIONS
================================================================

Q: Why can't you use System.currentTimeMillis() for Java benchmarks?
A: JVM-level optimizations like JIT compilation, dead code elimination,
   branch prediction, and constant folding make naïve timing unreliable.
   Code measured before JIT warm-up is artificially slow. The JVM might
   eliminate the measured code entirely if results aren't used. JMH
   handles warmup, multiple forks, and dead code prevention via Blackhole.

Q: What is the purpose of @Warmup in JMH?
A: Warmup iterations allow the JVM's JIT compiler to optimize the benchmark
   code (compile hot methods to native code) before measurements begin.
   Without warmup, early measurements reflect interpreted/partially compiled
   code, which is much slower than real-world JVM execution.

Q: What does @Fork(2) do in JMH?
A: Fork creates separate JVM processes for each benchmark run. @Fork(2)
   runs the benchmark in 2 completely fresh JVMs. This prevents pollution
   from other benchmarks' JIT-compiled code or class loader state. Without
   forking, a benchmark run earlier in the JVM could influence later ones.

Q: What is a Blackhole in JMH?
A: Blackhole prevents the JVM from eliminating computation through dead code
   elimination. If a benchmark computes a value but never uses the result,
   the JVM might remove the calculation entirely. Returning the value or
   calling bh.consume(value) forces the JVM to perform the computation.

Q: When would you use JMH instead of JMeter/Gatling?
A: JMH is for micro-benchmarking individual methods or algorithms —
   comparing HashMap vs TreeMap lookup, testing serialization performance,
   evaluating regex engine efficiency. JMeter/Gatling are for macro-level
   HTTP load testing of full services. JMH measures nanoseconds/microseconds;
   JMeter/Gatling measure milliseconds/seconds end-to-end.
