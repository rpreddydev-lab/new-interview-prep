1. WHAT ARE SEMANTIC ELEMENTS?
================================================================================

A semantic element clearly describes its MEANING/PURPOSE to both the browser
and the developer.

Non-semantic: <div>, <span>  — tell nothing about their content
Semantic:     <article>, <nav>, <header>  — describe their purpose

HTML5 added ~30 semantic elements to replace generic <div>/<span> wrappers.

Benefits of Semantic HTML:
  Accessibility  — Screen readers use semantic elements as navigation landmarks
  SEO            — Search engines understand page structure and content importance
  Maintainability — Code is self-documenting; easier to understand and maintain
  Styling        — CSS and DevTools are easier when elements have meaningful names
  A11y Tree      — Semantic elements map to the Accessibility Tree automatically
  Browser features — <details>, <dialog>, <progress> provide native behavior

================================================================================
2. WHY SEMANTICS MATTER
================================================================================

Accessibility Tree:
  When a browser parses HTML, it builds both the DOM tree AND the
  Accessibility Tree (AX Tree). The AX tree is what assistive technologies
  (screen readers, voice control, braille displays) use.

  Non-semantic HTML:
    <div id="nav">           → AX tree: generic container (no role)
    <div class="button">     → AX tree: generic container (no role)
    <div onclick="...">      → not keyboard accessible

  Semantic HTML:
    <nav>                    → AX tree: role="navigation" landmark
    <button>                 → AX tree: role="button" (keyboard, focus, ARIA)
    <h1>                     → AX tree: role="heading" level=1

Screen reader landmark navigation:
  NVDA/JAWS users press key shortcuts to jump between landmarks:
    H   → next heading
    1-6 → heading by level
    R   → next region/landmark
    B   → next button
    F   → next form field

If you use <div class="header"> instead of <header>, screen readers won't
recognize it as a landmark, forcing users to read through everything.

3. DOCUMENT STRUCTURE ELEMENTS
================================================================================

<header>
---------
  Purpose: Introductory content for page or section
  Allowed: in <body>, <article>, <section>, <aside>, <nav>, <main>
  Can contain: logo, h1, nav, search form
  Cannot contain: another <header>, <footer>
  ARIA role: banner (when page-level); none (when inside article/section)

  <!-- Page-level header (one per page typically) -->
  <header>
    <a href="/" aria-label="Return to homepage">
      <img src="logo.svg" alt="Company Name" width="150" height="50">
    </a>
    <nav aria-label="Main navigation">
      <ul>
        <li><a href="/products">Products</a></li>
        <li><a href="/blog">Blog</a></li>
      </ul>
    </nav>
  </header>

  <!-- Section-level header (inside article) -->
  <article>
    <header>
      <h2>Article Title</h2>
      <p>By <a rel="author" href="/author">Author</a>
         on <time datetime="2026-04-08">April 8</time></p>
    </header>
    <p>Content...</p>
  </article>

<nav>
------
  Purpose: Navigation links (major navigation blocks)
  Use for: Primary nav, breadcrumbs, pagination, table of contents
  Don't use for: Every group of links (footer links can use <ul> without <nav>
                  if not a major navigation)
  Multiple <nav>: allowed; use aria-label to distinguish them

  <nav aria-label="Main">...</nav>
  <nav aria-label="Breadcrumb">...</nav>
  <nav aria-label="Pagination">...</nav>

<main>
-------
  Purpose: Primary content of the document
  Rules:
    - UNIQUE per page (maximum one visible <main>)
    - Should NOT be inside <header>, <footer>, <aside>, <nav>, or <article>
    - Can be hidden with hidden attribute if multiple exist (SPA route trick)
    - ARIA role: main — immediately navigable landmark

  <a href="#main-content" class="skip-link">Skip to main content</a>
  <main id="main-content">
    <!-- Primary content here -->
  </main>

<article>
----------
  Purpose: Self-contained, independently distributable content
  Test: Would this content make sense if extracted and published elsewhere?
        (blog post, news article, forum post, product card, tweet, comment)
  Can contain: <header>, <footer>, <section>, other <article>
  Nested articles: a blog post (<article>) containing user comments (<article>)

  <article>
    <header><h2>Post Title</h2></header>
    <p>Post content...</p>
    <footer>
      <p>Tags: <a href="/css">CSS</a></p>
    </footer>
    <section aria-label="Comments">
      <article><!-- comment 1 --></article>
      <article><!-- comment 2 --></article>
    </section>
  </article>

<section>
----------
  Purpose: Thematic grouping of content (chapter, tab panel, step)
  Should always have a heading (<h2>, <h3>, etc.)
  Not for: generic containers (use <div> instead)
  ARIA role: region (only if has accessible name via aria-labelledby/aria-label)

  When to use section vs article vs div:
  - section: thematic grouping with heading, part of larger whole
  - article: self-contained (could stand alone)
  - div: no semantic meaning needed (styling/scripting wrapper)

  <section aria-labelledby="features-heading">
    <h2 id="features-heading">Features</h2>
    <ul>...</ul>
  </section>

<aside>
--------
  Purpose: Tangentially related content
  Use cases: sidebar, pull quotes, advertising, related links, biography
  Inside <article>: content tangentially related to article
  Outside <article>: site-level sidebar
  ARIA role: complementary

  <aside aria-label="Related articles">
    <h2>Related Reading</h2>
    <ul>...</ul>
  </aside>

<footer>
---------
  Purpose: Footer for page or section
  Can contain: author info, copyright, nav links, related links
  Multiple per page: allowed (can be footer of <article> or <section>)
  Page-level ARIA role: contentinfo; section-level: generic

  <footer>
    <nav aria-label="Footer links">...</nav>
    <address>
      <a href="mailto:info@example.com">info@example.com</a>
    </address>
    <p><small>&copy; 2026 Company Name. All rights reserved.</small></p>
  </footer>

4. TEXT-LEVEL SEMANTIC ELEMENTS
================================================================================

Element    Meaning                           Display   Example Use
--------   --------------------------------  -------   -------------------
<em>       Stress emphasis (tonal)           italic    "I *never* said that"
<strong>   Strong importance/urgency         bold      Warning messages
<b>        Stylistically bold (no importance) bold     Keywords, product names
<i>        Alternate voice/mood              italic    Foreign words, thoughts
<u>        Unarticulated annotation          underline Misspellings (with CSS)
<s>        Content no longer accurate        strike    Crossed-out price
<del>      Deleted content (edit tracking)   strike    Tracked changes
<ins>      Inserted content (edit tracking)  underline Tracked changes
<mark>     Highlighted/relevant text         highlight Search results
<cite>     Title of creative work            italic    Book/film/song title
<q>        Inline quotation                  "quoted"  Short quotes
<abbr>     Abbreviation                      -         HTML, CSS, W3C
<dfn>      Defining term                     italic    First use of term
<code>     Inline code                       mono      Variable names
<kbd>      Keyboard input                    mono      Press <kbd>Ctrl+C</kbd>
<samp>     Sample output                     mono      Terminal output
<var>      Variable                          italic    Mathematical/prog variable
<sub>      Subscript                         ↓         H₂O, footnote refs
<sup>      Superscript                       ↑         E=mc², footnotes
<small>    Fine print / legal text           smaller   Copyright, disclaimer
<ruby>     Ruby annotation (East Asian)      -         Pronunciation guides
<rt>       Ruby text                         above     Pronunciation
<rp>       Ruby parenthesis fallback         -         Fallback for ruby

Detailed examples:

<em> vs <strong> vs <b> vs <i>:
  <p>You should <em>always</em> validate your forms.</p>
  ← Stress emphasis; "always" changes sentence meaning. Screen readers change tone.

  <p><strong>Warning:</strong> This action cannot be undone.</p>
  ← Strong importance. Screen readers may announce as "Warning".

  <p>The <b>CSS box model</b> defines element spacing.</p>
  ← Keywords/important terms; no importance semantics.

  <p>The term <i lang="la">bona fide</i> means "in good faith".</p>
  ← Foreign word; not emphasis. Use lang attribute for pronunciation.

<mark>:
  <p>Search results for <b>HTML5</b>:</p>
  <p>The <mark>HTML5</mark> specification introduced semantic elements...</p>
  ← Use to highlight search terms within results. Use CSS for color.

<cite>:
  <blockquote>
    <p>The Web is more a social creation than a technical one.</p>
    <footer>— <cite>Tim Berners-Lee, Weaving the Web</cite></footer>
  </blockquote>

<abbr>:
  <abbr title="Accessible Rich Internet Applications">ARIA</abbr>
  Screen readers will expand the abbreviation when title is present.

<code>, <kbd>, <samp>, <var>:
  <p>Run <code>npm install</code> to install dependencies.</p>
  <p>Press <kbd>Ctrl</kbd>+<kbd>S</kbd> to save.</p>
  <p>The output was: <samp>Hello, World!</samp></p>
  <p>The formula is: <var>E</var> = <var>m</var><var>c</var><sup>2</sup></p>

5. GROUPING ELEMENTS
================================================================================

<figure> and <figcaption>:
  Self-contained media referenced in text. Can move without affecting flow.
  <figure>
    <img src="diagram.png" alt="Architecture diagram">
    <figcaption>Fig 1: Three-tier architecture</figcaption>
  </figure>
  
  <figure>
    <pre><code>
const sum = (a, b) => a + b;
    </code></pre>
    <figcaption>Listing 1: Arrow function syntax</figcaption>
  </figure>

  <figure>
    <blockquote>
      <p>Simplicity is the ultimate sophistication.</p>
    </blockquote>
    <figcaption>— Leonardo da Vinci</figcaption>
  </figure>

<blockquote>:
  Block-level quotation from another source.
  <blockquote cite="https://source-url.com">
    <p>Content of the quotation...</p>
  </blockquote>
  cite attribute: URL of source (not displayed; machine-readable)
  For attribution, use <footer> or <cite> inside the blockquote.

<address>:
  Contact information for the nearest <article> or <body>.
  NOT for postal addresses in general (use <p> for that).
  <address>
    <a href="mailto:info@example.com">Email us</a>
    <a href="tel:+12125551234">+1 (212) 555-1234</a>
    <a href="https://example.com">example.com</a>
  </address>

<pre>:
  Preformatted text (preserves whitespace and line breaks).
  Display in monospace font.
  <pre>
  column1    column2    column3
  value1     value2     value3
  </pre>

<hr>:
  Thematic break between paragraph-level content.
  NOT a visual divider (use CSS border for that).
  <p>First topic paragraph.</p>
  <hr>
  <p>Second unrelated topic.</p>

6. INTERACTIVE / DYNAMIC ELEMENTS
================================================================================

<details> and <summary>:
  Native disclosure widget (expandable/collapsible). No JavaScript required.
  
  <details>
    <summary>Click to expand FAQ answer</summary>
    <p>Here is the detailed answer to the question.</p>
  </details>

  <details open>  ← starts expanded
    <summary>Open by default</summary>
    <p>Content visible initially.</p>
  </details>

  CSS customization:
    details[open] summary { /* styles when open */ }
    details > summary::marker { content: "▶ "; }
    details[open] > summary::marker { content: "▼ "; }

<dialog>:
  Native modal or non-modal dialog element.
  
  <dialog id="confirm-dialog">
    <h2>Confirm Delete</h2>
    <p>Are you sure you want to delete this item?</p>
    <form method="dialog">
      <button value="cancel">Cancel</button>
      <button value="confirm">Delete</button>
    </form>
  </dialog>

  <button onclick="document.getElementById('confirm-dialog').showModal()">
    Delete Item
  </button>

  JavaScript API:
    dialog.show()       — open as non-modal
    dialog.showModal()  — open as modal (blocks background interaction)
    dialog.close()      — close (optional returnValue param)
    dialog.returnValue  — value of button that closed it

  Benefits over custom modals:
    - Automatic focus trap (Tab stays within dialog)
    - Escape key closes modal
    - ::backdrop pseudo-element for overlay styling
    - Returns to trigger element on close (accessibility)
    - Stacking context managed by browser

<meter>:
  Scalar value within a known range (gauge/measurement, NOT progress).
  <meter value="0.6" min="0" max="1" low="0.3" high="0.7" optimum="1">
    60% disk usage
  </meter>

  Attributes:
    value    — current value (required)
    min/max  — range bounds (default 0/1)
    low      — below this is "low" (yellow in some browsers)
    high     — above this is "high"
    optimum  — ideal value (determines if current is good/bad)

<progress>:
  Task completion progress (use for loading, upload, etc.)
  
  <!-- Indeterminate (unknown duration) -->
  <progress>Loading...</progress>
  
  <!-- Determinate -->
  <progress value="70" max="100">70%</progress>

<output>:
  Result of a calculation or user action.
  <form oninput="result.value = parseInt(a.value) + parseInt(b.value)">
    <input type="number" id="a" value="0"> +
    <input type="number" id="b" value="0"> =
    <output name="result" for="a b">0</output>
  </form>

7. TIME & DATA ELEMENTS
================================================================================

<time>:
  Machine-readable date/time. Invisible to users (same display as content).
  
  <time datetime="2026-04-08">April 8, 2026</time>
  <time datetime="2026-04-08T14:30:00">2:30 PM on April 8</time>
  <time datetime="2026-04-08T14:30:00+05:30">2:30 PM IST</time>
  <time datetime="PT2H30M">2 hours 30 minutes</time>
  <time datetime="2026-W15">Week 15, 2026</time>
  <time datetime="2026-04">April 2026</time>
  <time datetime="14:30">2:30 PM</time>

  datetime format (ISO 8601):
    Date:         YYYY-MM-DD
    Time:         HH:MM or HH:MM:SS
    DateTime:     YYYY-MM-DDTHH:MM:SS
    With TZ:      YYYY-MM-DDTHH:MM:SS±HH:MM
    Duration:     PT{n}H{n}M{n}S (P prefix + T for time)

  SEO benefit: Google reads datetime attribute for publish dates in rich results.
  Accessibility: Some screen readers read datetime value aloud.

<data>:
  Associates machine-readable value with content.
  <data value="UPC:012345678901">Widget X</data>
  <ul>
    <li><data value="21053">Cherry</data></li>
    <li><data value="14967">Lemon</data></li>
  </ul>

8. SEMANTIC VS NON-SEMANTIC COMPARISON
================================================================================

NON-SEMANTIC (divitis):
  <div id="header">
    <div id="logo"><img src="logo.png"></div>
    <div id="nav">
      <div class="nav-item"><a href="/">Home</a></div>
      <div class="nav-item"><a href="/about">About</a></div>
    </div>
  </div>
  <div id="main">
    <div class="article">
      <div class="article-title"><h2>Post Title</h2></div>
      <div class="article-body"><p>Content...</p></div>
    </div>
    <div class="sidebar">
      <div class="widget">...</div>
    </div>
  </div>
  <div id="footer">...</div>

SEMANTIC (HTML5):
  <header>
    <a href="/" aria-label="Homepage"><img src="logo.png" alt="Brand"></a>
    <nav aria-label="Main">
      <ul>
        <li><a href="/">Home</a></li>
        <li><a href="/about">About</a></li>
      </ul>
    </nav>
  </header>
  <main>
    <article>
      <header><h1>Post Title</h1></header>
      <p>Content...</p>
    </article>
    <aside aria-label="Sidebar">...</aside>
  </main>
  <footer>...</footer>

Differences:
  - Screen readers expose landmark navigation automatically in semantic version
  - Search engines understand content hierarchy better
  - Less CSS class naming needed (elements self-describe purpose)
  - HTML is more readable and maintainable

9. COMMON MISTAKES & ANTI-PATTERNS
================================================================================

MISTAKE 1: Using <section> instead of <div>
  ✗  <section class="container">  ← No heading, no semantic purpose
  ✓  <div class="container">       ← Generic wrapper with no semantics needed

MISTAKE 2: Multiple <main> elements visible
  ✗  <main>Page 1 content</main>
     <main>Page 2 content</main>
  ✓  One main visible at a time (others can have hidden attribute)

MISTAKE 3: Using heading elements for styling
  ✗  <h3 style="font-size: 14px">Small "header"</h3>
  ✓  <p class="subtitle">Small subtitle</p>

MISTAKE 4: Missing heading in <section>
  ✗  <section><p>Orphaned section content</p></section>
  ✓  <section><h2>Section Title</h2><p>Content</p></section>

MISTAKE 5: Using <b>/<i> when meaning matters
  ✗  <b>Warning:</b> Do not delete this file.
  ✓  <strong>Warning:</strong> Do not delete this file.

MISTAKE 6: Using <article> for every card
  ✗  <article class="product-card">  ← Is it truly self-contained/syndicate-able?
  ✓  <article class="product-card"> when each card makes sense independently

MISTAKE 7: Nesting <a> inside <a>
  ✗  <a href="/page"><a href="/other">Link</a></a>
  ✓  Restructure; interactive elements cannot be nested

MISTAKE 8: Not using aria-label on multiple <nav> elements
  ✗  <nav>...</nav><nav>...</nav>
  ✓  <nav aria-label="Main">...</nav><nav aria-label="Footer">...</nav>

10. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is the difference between <article> and <section>?
A: <article> is for self-contained content that could be independently
   distributed (blog post, news article, product card, tweet). A good test:
   "Would this make sense extracted from the page?"
   <section> is for thematic grouping within a document — a chapter, tab panel,
   or content region. It should always have a heading. When unsure, use <div>.

Q2: Can you use <header> and <footer> multiple times on a page?
A: Yes. <header> and <footer> can appear inside any sectioning element
   (<article>, <section>, <aside>, <nav>, <main>) in addition to the page level.
   Each <article> can have its own <header> (with article title, author) and
   <footer> (with tags, sharing links). The page-level <header> maps to
   ARIA "banner" landmark; the page-level <footer> maps to "contentinfo".

Q3: What is the difference between <em> and <strong>?
A: <em> represents STRESS EMPHASIS — it changes the implied meaning of a
   sentence. "I *never* said that" implies someone else said it.
   <strong> represents STRONG IMPORTANCE, URGENCY, or SERIOUSNESS.
   "Warning: <strong>Permanent action</strong>." Both affect screen readers
   (tone of voice or announcement emphasis), unlike <i> and <b>.

Q4: What is the <details> element and why is it preferred over custom JS?
A: <details>/<summary> creates a native expandable/collapsible disclosure widget.
   Benefits: no JavaScript needed, keyboard accessible (Enter/Space to toggle),
   proper ARIA semantics automatically, browser handles focus management,
   consistent across browsers, animatable with CSS (details[open]).

Q5: What's the purpose of <figure>?
A: <figure> wraps self-contained content that is referenced from the main
   content but could be moved to a different position without affecting flow —
   images, diagrams, code listings, charts, quotes. <figcaption> provides
   an accessible caption. The caption is associated with the figure, not just
   visually positioned below it.

Q6: When should you use <address>?
A: <address> provides contact information for the nearest <article> or <body>
   author/owner. It's for contact info (email, phone, URL, social media) —
   NOT for general postal addresses. Inside an <article>, it's the author's
   contact. At page level, it's the site owner's contact.

Q7: What is the difference between <b> and <strong>? Is <b> useless?
A: <strong> = semantic importance (screen readers may stress this).
   <b> = stylistically offset text without added importance (product names,
   key terms on first use, lead sentences in journalism).
   <b> is NOT useless — use it for visual distinction without semantic weight.
   If removal changes meaning, use <strong>. If purely stylistic, use <b>.

Q8: What are the ARIA landmark roles and which semantic elements map to them?
A: banner     → <header> (page-level)
   navigation → <nav>
   main       → <main>
   complementary → <aside>
   contentinfo → <footer> (page-level)
   region     → <section> (with accessible name)
   form       → <form> (with accessible name)
   search     → <search> (HTML5.3) or <form role="search">
   article    → <article> (implicit role="article")

Q9: How does <time datetime="..."> help SEO?
A: Google reads the datetime attribute to understand publish and update dates,
   which is used in rich result date displays and may influence freshness
   ranking signals. The human-readable content can be in any format, while
   the machine reads datetime in ISO 8601 format.

Q10: When would you use <mark> vs <strong> vs <em>?
A: <mark>: Highlighted text relevant to a current user ACTION (search results,
   quiz answers, scanner highlights). Like a yellow highlighter.
   <strong>: Strong importance that was always intended in the original text.
   <em>: Stress emphasis that changes the meaning of the sentence.
   Example: search page shows "learn <mark>HTML5</mark> today" — the word
   is relevant to the search, not inherently important to the sentence.
