1. WHAT IS WCAG?
================================================================================

WCAG — Web Content Accessibility Guidelines
Published by: W3C (World Wide Web Consortium) — the international web standards body
Working Group: WCAG Working Group (AGWG — Accessibility Guidelines Working Group)

WCAG is the internationally recognized technical standard for web accessibility.
It is referenced by laws in the USA (Section 508), EU (EAA, EN 301 549), UK
(Equality Act), Canada (AODA), and many other jurisdictions.

WCAG provides:
  - Testable success criteria with defined pass/fail conditions
  - Techniques (informative guidance on how to meet criteria)
  - Understanding documents (rationale and intent of each criterion)

WCAG is technology-neutral:
  It applies to HTML, CSS, JavaScript, PDF, native apps (via reference), etc.
  It doesn't prescribe HOW to implement — it defines WHAT outcomes are needed.

================================================================================
2. WCAG VERSIONS
================================================================================

WCAG 1.0 (1999) — Original, technology-specific, partially obsolete

WCAG 2.0 (2008) — Technology-neutral POUR framework (12 guidelines, 61 criteria)
  Still valid; baseline for many laws.
  
WCAG 2.1 (2018) — Adds 17 new criteria (78 total)
  Focus areas: Mobile accessibility, low vision, cognitive/learning
  New criteria: Reflow, Text Spacing, Pointer Gestures, Target Size,
  Pointer Cancellation, Label in Name, Motion Actuation, etc.
  MOST IMPORTANT: This is the current widely-implemented standard.

WCAG 2.2 (September 2023) — Adds 9 new criteria (87 total)
  Focus areas: Cognitive, mobile, low vision
  Added: Focus Appearance, Dragging Movements, Target Size Minimum,
  Consistent Help, Accessible Authentication, Redundant Entry
  Removed: 4.1.1 Parsing (effectively deprecated)

WCAG 3.0 — Major future revision (in development, not yet final)
  Will replace WCAG 2.x eventually
  Introduces new scoring model (not pass/fail)
  "Bronze/Silver/Gold" conformance model
  Will take years to finalize and be adopted

For interviews: WCAG 2.1 AA is the de facto target; know WCAG 2.2 additions.

3. CONFORMANCE LEVELS: A, AA, AAA
================================================================================

Each success criterion is assigned one of three conformance levels:

LEVEL A — MINIMUM ACCESSIBILITY
  The most basic requirements. Not meeting Level A makes content inaccessible
  to the most severely impacted users.
  Examples: images have alt text, page has a title, keyboard accessible,
  no seizure-inducing content, captions for prerecorded video.

LEVEL AA — STANDARD REQUIREMENT
  The target for most legal compliance and the realistic goal for most sites.
  Includes all Level A requirements plus additional criteria.
  Examples: contrast ratio 4.5:1, reflow at 400% zoom, link purpose clear,
  error messages suggest corrections, consistent navigation.

LEVEL AAA — ENHANCED
  The highest standard. Not required for entire websites (some content cannot
  technically meet it). Appropriate for specialized audiences.
  Examples: 7:1 contrast ratio, sign language interpretation, context-sensitive help,
  reading level, pronunciation.

Practical guidance:
  - Aim for WCAG 2.1 Level AA minimum
  - Address critical Level A failures immediately
  - Add Level AAA criteria where feasible
  - Do not declare AAA conformance for an entire site

Claiming conformance:
  Organizations publish Accessibility Conformance Reports (ACR) or
  Voluntary Product Accessibility Templates (VPAT) documenting their
  conformance with specific criteria.

4. PRINCIPLE 1: PERCEIVABLE
================================================================================

"Information and user interface components must be presentable to users
in ways they can perceive."

GUIDELINE 1.1 — TEXT ALTERNATIVES
  1.1.1 Non-text Content (A)
    All non-text content has a text alternative.
    - Images: alt attribute
    - Controls: accessible name (label, aria-label)
    - CAPTCHA: accessible alternative
    - Decorative images: alt="" (empty string, not missing)
    - Complex images: long description in addition to brief alt
    
    Failure: <img src="logo.png"> (no alt attribute)
    Pass: <img src="logo.png" alt="Acme Corp logo">
    Pass: <img src="divider.png" alt="" role="presentation"> (decorative)

GUIDELINE 1.2 — TIME-BASED MEDIA
  1.2.1 Audio-only / Video-only, Prerecorded (A)
    Provide transcript for audio-only; transcript or audio description for
    video-only (silent video).
  
  1.2.2 Captions, Prerecorded (A)
    All prerecorded videos with audio must have synchronized captions.
    <track kind="captions" src="captions.vtt" srclang="en" label="English">
  
  1.2.3 Audio Description or Text Alternative (A)
    Prerecorded videos: provide audio description OR text alternative.
  
  1.2.4 Captions, Live (AA)
    Live streaming video must have live captions.
  
  1.2.5 Audio Description, Prerecorded (AA)
    Prerecorded video must have audio descriptions of all visual information
    not communicated by audio track alone.
  
  1.2.7 Extended Audio Description (AAA)
    When pauses are insufficient for audio descriptions.
  
  1.2.8 Media Alternative (AAA)
    Full text alternative for all prerecorded synchronized media.
  
  1.2.9 Audio-only, Live (AAA)
    Text alternative (transcript) for live audio-only.

GUIDELINE 1.3 — ADAPTABLE
  1.3.1 Info and Relationships (A)
    Structure that is conveyed visually must also be in code.
    - Headings marked with <h1>-<h6>, not just styled bold text
    - Lists marked with <ul>/<ol>, not just hyphens
    - Tables use <th> with scope, not styled <td>
    - Forms have labels, not just visual proximity
    
  1.3.2 Meaningful Sequence (A)
    Reading order in code matches meaningful sequence.
    Especially important when CSS reorders visual layout.
    
  1.3.3 Sensory Characteristics (A)
    Instructions don't rely solely on sensory characteristics.
    ✗ "Click the round button on the left"
    ✓ "Click the 'Submit' button"
    
  1.3.4 Orientation (AA) [WCAG 2.1]
    Content works in both portrait and landscape.
    Don't lock orientation unless essential (e.g., piano app).
    
  1.3.5 Identify Input Purpose (AA) [WCAG 2.1]
    Form fields that collect personal info must have autocomplete tokens.
    name, email, tel, address → use HTML autocomplete attribute.
    
  1.3.6 Identify Purpose (AAA) [WCAG 2.1]
    Programmatic identification of UI components, icons, regions.

GUIDELINE 1.4 — DISTINGUISHABLE
  1.4.1 Use of Color (A)
    Color is not the only way to convey information.
    ✗ Required fields shown only by red color
    ✓ Required fields have red color AND asterisk (*) AND "required"
    
  1.4.2 Audio Control (A)
    Audio that auto-plays for more than 3 seconds has a pause/stop control.
    
  1.4.3 Contrast Minimum (AA)
    Normal text: 4.5:1 contrast ratio vs background.
    Large text (18pt+ or 14pt+ bold): 3:1 contrast ratio.
    
  1.4.4 Resize Text (AA)
    Text can be resized to 200% without loss of content or functionality.
    (CSS: avoid px for font sizes that override user preferences; use rem)
    
  1.4.5 Images of Text (AA)
    Avoid text in images (except logos). Use real text instead.
    
  1.4.6 Contrast Enhanced (AAA)
    Normal text: 7:1. Large text: 4.5:1.
    
  1.4.8 Visual Presentation (AAA)
    User control over foreground/background color, text width, line spacing.
    
  1.4.10 Reflow (AA) [WCAG 2.1]
    Content reflows at 400% zoom (320px equivalent) without horizontal scroll.
    Except for content requiring 2D layout (data tables, maps, images).
    Use responsive CSS (flexbox, grid, relative units).
    
  1.4.11 Non-text Contrast (AA) [WCAG 2.1]
    UI components (input borders, button outlines, icons) and focus indicators
    must have 3:1 contrast against adjacent colors.
    
  1.4.12 Text Spacing (AA) [WCAG 2.1]
    When users override: line height 1.5x, letter spacing 0.12em,
    word spacing 0.16em, spacing after paragraphs 2x — no content loss.
    Use relative units; don't clip text containers.
    
  1.4.13 Content on Hover or Focus (AA) [WCAG 2.1]
    Tooltip/popup on hover/focus must be: dismissible (Escape), hoverable
    (pointer can move over it), persistent (stays until dismissed).

5. PRINCIPLE 2: OPERABLE
================================================================================

"User interface components and navigation must be operable."

GUIDELINE 2.1 — KEYBOARD ACCESSIBLE
  2.1.1 Keyboard (A)
    All functionality operable via keyboard without specific timing.
  2.1.2 No Keyboard Trap (A)
    Focus can always be moved away from any component.
  2.1.3 Keyboard No Exception (AAA)
    All content keyboard accessible without exception.
  2.1.4 Character Key Shortcuts (A) [WCAG 2.1]
    Single-character keyboard shortcuts must be remappable or disable-able,
    or only active on focus.

GUIDELINE 2.2 — ENOUGH TIME
  2.2.1 Timing Adjustable (A)
    Time limits can be turned off, adjusted, or extended.
  2.2.2 Pause, Stop, Hide (A)
    Moving/blinking/scrolling content > 5 seconds: pause/stop/hide control.
    Auto-updating content: pause/stop/hide control.
  2.2.6 Timeouts (AAA) [WCAG 2.1]
    Warn users of data loss due to inactivity.

GUIDELINE 2.3 — SEIZURES AND PHYSICAL REACTIONS
  2.3.1 Three Flashes or Below Threshold (A)
    No content flashes more than 3 times per second.
  2.3.2 Three Flashes (AAA)
    No flashing content at all.

GUIDELINE 2.4 — NAVIGABLE
  2.4.1 Bypass Blocks (A)
    Skip links to bypass repeated content.
  2.4.2 Page Titled (A)
    Pages have descriptive titles.
    <title>Contact Us | Acme Corp</title>
  2.4.3 Focus Order (A)
    Focus order is logical and meaningful.
  2.4.4 Link Purpose In Context (A)
    Link purpose determinable from link text or context.
    ✗ "Click here" or "Read more"
    ✓ "Read more about Web Accessibility"
  2.4.5 Multiple Ways (AA)
    Multiple ways to find a page (search, sitemap, navigation).
  2.4.6 Headings and Labels (AA)
    Headings and labels describe purpose.
  2.4.7 Focus Visible (AA)
    Keyboard focus visible at all times.
  2.4.11 Focus Appearance (AA) [WCAG 2.2]
    Focus indicator has minimum area (2px perimeter) and contrast (3:1).
  2.4.12 Focus Not Obscured Minimum (AA) [WCAG 2.2]
    Focused component not entirely hidden by sticky headers or overlays.
  2.4.13 Focus Not Obscured Enhanced (AAA) [WCAG 2.2]
    Focused component fully visible.

GUIDELINE 2.5 — INPUT MODALITIES [WCAG 2.1]
  2.5.1 Pointer Gestures (A)
    Multi-point or path-based gestures have single-pointer alternatives.
  2.5.2 Pointer Cancellation (A)
    Single-pointer activation: use up-event (mouseup, touchend) not down.
  2.5.3 Label in Name (A)
    Accessible name of component contains its visible text.
    ✗ <button aria-label="Submit form">Send</button>  // "Send" not in name
    ✓ <button aria-label="Send contact form">Send</button>
  2.5.4 Motion Actuation (A)
    Functionality triggered by device motion has alternatives and can be disabled.
  2.5.7 Dragging Movements (AA) [WCAG 2.2]
    Drag-and-drop functionality has a single-pointer alternative.
  2.5.8 Target Size Minimum (AA) [WCAG 2.2]
    Target size is at least 24x24 CSS px (or has adequate spacing).

6. PRINCIPLE 3: UNDERSTANDABLE
================================================================================

"Information and the operation of the user interface must be understandable."

GUIDELINE 3.1 — READABLE
  3.1.1 Language of Page (A)
    <html lang="en"> — programmatic language of page.
  3.1.2 Language of Parts (AA)
    Parts in different language: lang attribute on the element.
    <p>The French word is <span lang="fr">bonjour</span>.</p>

GUIDELINE 3.2 — PREDICTABLE
  3.2.1 On Focus (A)
    Focusing an element doesn't cause unexpected context change.
    (Don't submit forms or navigate on focus)
  3.2.2 On Input (A)
    Changing input value doesn't cause unexpected context change
    unless user is warned first.
  3.2.3 Consistent Navigation (AA)
    Navigation repeated across pages appears in same relative order.
  3.2.4 Consistent Identification (AA)
    Components with same function identified consistently.
  3.2.6 Consistent Help (A) [WCAG 2.2]
    Help mechanisms (contact, chatbot, FAQ link) in consistent location.

GUIDELINE 3.3 — INPUT ASSISTANCE
  3.3.1 Error Identification (A)
    Input errors automatically detected and described in text.
    ✗ Field border turns red (no text description)
    ✓ Field border red + "Error: Email address is invalid" text
  3.3.2 Labels or Instructions (A)
    Labels or instructions for required format/constraints.
  3.3.3 Error Suggestion (AA)
    If known, suggest how to correct the error.
    ✓ "Must be a valid email like name@example.com"
  3.3.4 Error Prevention (Legal, Financial, Data) (AA)
    Submissions that cause legal/financial commitments are:
    - Reversible, OR
    - Checked for errors with opportunity to correct, OR
    - Confirmed before submission
  3.3.7 Redundant Entry (A) [WCAG 2.2]
    Info entered in previous step auto-populated or selectable (not re-entered).
  3.3.8 Accessible Authentication Minimum (AA) [WCAG 2.2]
    CAPTCHAs and authentication tests have accessible alternative.
    Don't rely solely on cognitive function tests.

7. PRINCIPLE 4: ROBUST
================================================================================

"Content must be robust enough that it can be interpreted by a wide variety
of user agents, including assistive technologies."

GUIDELINE 4.1 — COMPATIBLE
  4.1.1 Parsing (A) — DEPRECATED in WCAG 2.2
    Originally required valid HTML. Modern browsers are so tolerant that
    parsing errors rarely affect ATs. Still good practice for code quality.
    
  4.1.2 Name, Role, Value (A)
    All UI components: name and role determinable; state, properties, values
    settable and notifiable via accessibility API.
    Key test: all interactive elements must have accessible name + role.
    
  4.1.3 Status Messages (AA) [WCAG 2.1]
    Status messages not receiving focus are programmatically determinable.
    "Your cart has been updated" → role="status" or role="alert"

9. NEW CRITERIA IN WCAG 2.2
================================================================================

Nine new/modified criteria in WCAG 2.2:

  2.4.11 Focus Appearance (AA, NEW)
    Minimum focus indicator: 2px outline with 3:1 contrast vs adjacent colors.
    
  2.4.12 Focus Not Obscured Minimum (AA, NEW)
    Focused element must not be entirely hidden by sticky/fixed headers or
    overlapping content.
    
  2.4.13 Focus Not Obscured Enhanced (AAA, NEW)
    Focused element fully visible (not just partially).
    
  2.5.7 Dragging Movements (AA, NEW)
    Any drag-and-drop action has a non-dragging alternative (e.g., cut/paste,
    up/down arrows, numeric input for re-ordering).
    
  2.5.8 Target Size Minimum (AA, NEW)
    Interactive targets at least 24x24 CSS px, OR adequate spacing around
    targets to reach 24px spacing.
    
  3.2.6 Consistent Help (A, NEW)
    If help mechanisms (human contact, chatbot, FAQ, self-service support)
    are present on multiple pages, they appear in consistent location.
    
  3.3.7 Redundant Entry (A, NEW)
    Information already provided by user is auto-populated or selectable
    in multi-step processes (don't make them re-enter same info).
    
  3.3.8 Accessible Authentication Minimum (AA, NEW)
    Authentication doesn't rely solely on cognitive function test unless
    alternative is available (no "type the characters you see in the image"
    with no alternative).
    
  3.3.9 Accessible Authentication Enhanced (AAA, NEW)
    No cognitive function tests in authentication at all.
    
  4.1.1 Parsing (A, REMOVED)
    Deprecated because modern browsers handle HTML errors gracefully
    and it's no longer meaningful for ATs.

10. HOW TO APPLY WCAG IN PRACTICE
================================================================================

During Design Phase:
  - Color choices: run contrast checks (use tools like Figma plugins)
  - Interaction design: plan for keyboard before implementing mouse
  - Content: plan heading hierarchy, alt text requirements
  - Forms: plan label placement, error message content

During Development Phase:
  - Use semantic HTML as the foundation
  - Associate labels with form controls
  - Implement focus management for dynamic content
  - Add ARIA only where native HTML is insufficient
  - Test keyboard navigation continuously

Automated Testing (catches ~30-40% of WCAG issues):
  - Integrate axe-core in CI/CD pipeline
  - eslint-plugin-jsx-a11y for React
  - @testing-library/jest-dom for component tests
  - cypress-axe for end-to-end a11y tests

Manual Testing:
  - Keyboard only (Tab, arrows, Escape) — 30 minutes per page
  - Screen reader (NVDA + Firefox recommended for free testing)
  - 200% and 400% zoom tests
  - Contrast checker on colors

Publishing Conformance:
  - Accessibility Statement (required by some laws)
  - VPAT (Voluntary Product Accessibility Template) — US government procurement
  - ACR (Accessibility Conformance Report) — formal documentation

11. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is WCAG and what versions should you know about?
A: WCAG (Web Content Accessibility Guidelines) is the W3C international
   standard for web accessibility. The most important version is WCAG 2.1 (2018),
   which is referenced by most laws and regulations worldwide and is the
   practical target for most projects. WCAG 2.2 (2023) added 9 new criteria
   and deprecated 1. WCAG 3.0 is in development. For interviews, know WCAG 2.1
   AA criteria thoroughly and be aware of WCAG 2.2 additions.

Q2: What are the three WCAG conformance levels?
A: Level A is the minimum — failing any A criterion makes content inaccessible
   to severely impacted users (e.g., no alt text, no keyboard access). Level AA
   is the standard target — required by most laws (Section 508, EAA, etc.) and
   represents good accessibility. Level AAA is the highest standard, not
   required for entire sites, and may not be achievable for all content types.
   Most projects aim for WCAG 2.1 Level AA conformance.

Q3: What contrast ratios does WCAG require?
A: For normal text: 4.5:1 minimum (AA) and 7:1 enhanced (AAA). For large text
   (18pt+ or 14pt+ bold): 3:1 minimum (AA) and 4.5:1 enhanced (AAA). For UI
   components (input borders, button outlines, data visualization elements,
   focus indicators): 3:1 minimum (AA, criterion 1.4.11). These ratios are
   calculated using relative luminance of text vs background colors.

Q4: What is WCAG criterion 1.3.5 about?
A: 1.3.5 Identify Input Purpose (AA, WCAG 2.1) requires that form fields
   collecting personal information use the HTML autocomplete attribute with
   appropriate tokens so browsers and assistive technologies can identify
   the purpose. For example, inputs for name, email, phone, address should
   have autocomplete="name", autocomplete="email", autocomplete="tel",
   etc. This helps users with cognitive disabilities use autofill, and helps
   password managers and assistive technologies work correctly.

Q5: What is the Reflow criterion (1.4.10)?
A: WCAG 1.4.10 (AA, WCAG 2.1) requires that content can be presented at 400%
   zoom (equivalent to 320px viewport width) without requiring two-dimensional
   scrolling — meaning no horizontal scrolling for content that isn't inherently
   two-dimensional (like data tables or maps). This is achieved through responsive
   design: using relative units, flexible layouts (flexbox/grid), and CSS media
   queries. It ensures that users who need to zoom significantly (low vision users)
   can still access all content without horizontal scrolling.

Q6: What does WCAG criterion 4.1.2 require?
A: 4.1.2 Name, Role, Value (Level A) requires that for all UI components:
   the name (accessible name — what it's called), role (what type of component
   it is), and value (its current state/value) are programmatically determinable
   by assistive technologies. For native HTML elements, this is automatic. For
   custom components, you must add ARIA roles, properties, and states. This
   is the criterion that requires buttons to have labels, custom checkboxes
   to have aria-checked, and custom dropdowns to have proper role="listbox"
   with option roles.

Q7: What are the new criteria added in WCAG 2.2?
A: WCAG 2.2 added 9 new criteria: Focus Appearance (AA) requiring a visible
   2px+ focus indicator with 3:1 contrast; Focus Not Obscured Minimum/Enhanced
   (AA/AAA) ensuring focused elements aren't hidden behind sticky headers;
   Dragging Movements (AA) requiring non-drag alternatives; Target Size Minimum
   (AA) requiring 24x24px targets; Consistent Help (A) requiring help mechanisms
   in consistent locations; Redundant Entry (A) preventing re-entry of previously
   provided info; Accessible Authentication Minimum/Enhanced (AA/AAA) eliminating
   cognitive-only auth tests. 4.1.1 Parsing was removed.

Q8: What does WCAG say about error handling in forms?
A: Three relevant criteria: 3.3.1 Error Identification (A) — errors must be
   automatically detected and described in text (not just by color or icon).
   3.3.2 Labels or Instructions (A) — labels or instructions for required format.
   3.3.3 Error Suggestion (AA) — if the error type is known, suggest how to
   correct it. 3.3.4 Error Prevention (AA) — for legal/financial transactions,
   allow reversal or confirmation. Combined: errors need text descriptions,
   correction suggestions, and accessible announcement (role="alert" or focus
   management to the error).

Q9: What does WCAG say about links?
A: 2.4.4 Link Purpose in Context (A) — link text must make its purpose clear
   from the link text itself OR from the surrounding context (same paragraph,
   table cell, list). "Click here" and "Read more" fail unless context makes
   purpose clear. 2.4.9 Link Purpose Link Only (AAA) — link text alone must
   be sufficient without context. Additionally, 2.5.3 Label in Name (A) requires
   that if a link has visible text, the accessible name must contain that text
   (so voice control users can activate by saying the visible text).

Q10: What is the difference between WCAG techniques and success criteria?
A: Success criteria are normative (mandatory) — they define the testable
   outcomes that must be achieved. They are pass/fail. Techniques are
   informative (advisory guidance) — they describe specific ways to meet
   success criteria using particular technologies (HTML, CSS, ARIA, PDF). A
   success criterion can be met by multiple techniques. Techniques are labeled
   as "sufficient" (proven to meet the criterion), "advisory" (best practice),
   or "failures" (known ways to fail). Meeting a technique is not required —
   meeting the success criterion is what matters.
