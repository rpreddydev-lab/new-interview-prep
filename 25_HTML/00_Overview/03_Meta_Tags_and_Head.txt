1. OVERVIEW OF <head> CONTENT
================================================================================

The <head> element is a metadata container. Its content is NOT displayed on the
page but controls how the document is rendered, identified, and shared.

Elements allowed in <head>:
  <title>     — Document title (required)
  <meta>      — Metadata (charset, description, OG, etc.)
  <link>      — External resource links (CSS, favicon, canonical, etc.)
  <script>    — JavaScript (or link to JS file)
  <style>     — Inline CSS
  <base>      — Base URL for relative links
  <noscript>  — Fallback for JS-disabled browsers

ORDER MATTERS for performance:
  1. <meta charset> — FIRST (must be within first 1024 bytes)
  2. <meta viewport> — SECOND (for early responsive behavior)
  3. <title> — Third
  4. SEO/social meta tags
  5. <link rel="preconnect"> / <link rel="dns-prefetch">
  6. <link rel="stylesheet"> (render-blocking CSS)
  7. <link rel="preload">
  8. Inline <style> (if critical CSS)
  9. <script> (prefer defer; avoid blocking inline scripts)

================================================================================
2. <meta> TAG SYNTAX & CATEGORIES
================================================================================

Two attribute pairs for <meta>:
  1. name + content   → Document-level metadata
     <meta name="description" content="Page description">

  2. http-equiv + content  → HTTP header simulation
     <meta http-equiv="refresh" content="30">

  3. charset  → Character encoding (special case)
     <meta charset="UTF-8">

  4. property + content  → Open Graph / Dublin Core
     <meta property="og:title" content="Page Title">

  5. itemprop  → Schema.org microdata (rarely in <head>)

<meta> is a VOID element — no closing tag, no content.

3. CHARSET & ENCODING
================================================================================

<meta charset="UTF-8">

- MUST appear within first 1024 bytes of the document
- MUST be placed BEFORE any characters that might require the encoding
- Should be the FIRST element inside <head>
- UTF-8 covers all Unicode characters (multilingual support)
- Prevents XSS attacks via charset sniffing (UTF-7 attack)

Common encodings:
  UTF-8    — Universal (recommended; handles all languages)
  ISO-8859-1 — Latin-1 (Western European languages only)
  Windows-1252 — Windows Western (similar to ISO-8859-1)

HTTP Content-Type header vs meta charset:
  HTTP header: Content-Type: text/html; charset=UTF-8
  - Takes precedence over meta charset
  - Set by the web server
  Both should agree. If served without HTTP charset header, meta charset is used.

4. VIEWPORT META TAG (RESPONSIVE DESIGN)
================================================================================

<meta name="viewport" content="width=device-width, initial-scale=1.0">

WITHOUT viewport meta:
  Mobile browsers render at ~980px viewport width, then scale down
  Result: tiny unreadable text, no media queries matching mobile widths

WITH viewport meta:
  Device width (e.g., 375px on iPhone) becomes the CSS viewport width
  Media queries match properly; font sizes are readable

Viewport values:
  width=device-width     — CSS viewport = device physical width
  initial-scale=1.0      — 1:1 zoom (no initial zoom)
  minimum-scale=1.0      — Minimum zoom level allowed
  maximum-scale=5.0      — Maximum zoom level allowed
  user-scalable=yes      — Allow user to zoom (NEVER set no — WCAG violation)
  height=device-height   — Rarely used; set CSS viewport height

ACCESSIBILITY WARNING:
  user-scalable=no and maximum-scale=1 prevent zooming — violates WCAG 1.4.4
  Users with low vision rely on pinch-to-zoom. NEVER disable it.

Layout viewport vs Visual viewport:
  Layout viewport = size used for CSS layout calculations
  Visual viewport  = visible portion of the page (changes when user zooms)

viewport-fit (for notched phones):
  <meta name="viewport" content="width=device-width, initial-scale=1.0,
  viewport-fit=cover">
  Allows content to fill the entire screen (including notch area).
  Use safe-area-inset CSS env() variables to avoid notch overlap.

5. SEO META TAGS
================================================================================

<meta name="description" content="...">
  - Shown as the snippet in search results
  - Optimal length: 150-160 characters
  - Should be unique per page
  - Include primary keyword naturally
  - Write for humans (not stuffed with keywords)

<meta name="keywords" content="...">
  - IGNORED by Google (since 2009), Bing
  - Still used by some minor search engines
  - Should be omitted (no benefit; only noise)

<meta name="robots" content="index, follow">
  Values (comma-separated):
    index       — allow page to be indexed (default)
    noindex     — do NOT index this page
    follow      — follow links on this page (default)
    nofollow    — do NOT follow links
    noarchive   — do not show cached version in search
    nosnippet   — do not show text snippet in search result
    noimageindex — do not index images on this page
    none        = noindex, nofollow
    all         = index, follow (explicit default)
  
  Can also be set per crawler:
    <meta name="googlebot" content="noindex, nofollow">

<meta name="author" content="Author Name">
  - Identifies the document author
  - Some CMS/tools use this; minimal SEO impact

<link rel="canonical" href="https://example.com/canonical-url">
  - Tells search engines which URL is the "master" copy
  - Critical for preventing duplicate content penalties
  - Use on paginated pages, filtered views, www vs non-www, http vs https

<link rel="alternate" hreflang="es" href="https://es.example.com/">
  - Tells search engines about alternate language/region versions
  - Must be reciprocal (each page references all others)
  Example for international sites:
    <link rel="alternate" hreflang="en" href="https://example.com/en/">
    <link rel="alternate" hreflang="fr" href="https://example.com/fr/">
    <link rel="alternate" hreflang="x-default" href="https://example.com/">

6. OPEN GRAPH PROTOCOL (SOCIAL MEDIA)
================================================================================

Open Graph (OG) protocol — created by Facebook, now used by most platforms
(Facebook, LinkedIn, Slack, Discord, WhatsApp, iMessage).

When you share a URL, the platform's crawler reads OG tags to build the preview
card (title, description, image, site name).

Basic OG tags (recommended for all pages):
  <meta property="og:title"       content="Page Title">
  <meta property="og:description" content="Page description (~200 chars)">
  <meta property="og:image"       content="https://example.com/image.jpg">
  <meta property="og:url"         content="https://example.com/page">
  <meta property="og:type"        content="website">
  <meta property="og:site_name"   content="Site Name">
  <meta property="og:locale"      content="en_US">

OG image best practices:
  - Minimum: 600×315px; Recommended: 1200×630px (2:1 ratio)
  - Must be absolute URL (not relative)
  - Max file size: 8MB for Facebook
  - Use image:width and image:height for faster rendering:
    <meta property="og:image:width"  content="1200">
    <meta property="og:image:height" content="630">
    <meta property="og:image:alt"    content="Image description">

OG types:
  website, article, book, profile, music.song, music.album, video.movie

Article-specific OG:
  <meta property="article:published_time" content="2026-04-08T12:00:00Z">
  <meta property="article:author"         content="https://example.com/author">
  <meta property="article:section"        content="Technology">
  <meta property="article:tag"            content="HTML">

7. TWITTER CARDS
================================================================================

Twitter has its own separate system from Open Graph (though falls back to OG).

Card types:
  summary               — small thumbnail on left; title, description, image
  summary_large_image   — large image above content
  app                   — for mobile apps
  player                — for video/audio content

Basic Twitter Card:
  <meta name="twitter:card"        content="summary_large_image">
  <meta name="twitter:site"        content="@sitehandle">
  <meta name="twitter:creator"     content="@authorhandle">
  <meta name="twitter:title"       content="Article Title">
  <meta name="twitter:description" content="Article description">
  <meta name="twitter:image"       content="https://example.com/image.jpg">
  <meta name="twitter:image:alt"   content="Description of image">

Image requirements for summary_large_image:
  Minimum: 300×157px; Maximum: 4096×4096px; Max 5MB; JPG, PNG, WEBP, GIF
  Recommended: 1200×628px (consistent with OG)

Fallback behavior:
  If twitter:title is missing, falls back to og:title
  If twitter:image is missing, falls back to og:image
  Best practice: define both OG and Twitter tags

8. HTTP-EQUIV META TAGS
================================================================================

These simulate HTTP response headers.

<meta http-equiv="content-type" content="text/html; charset=UTF-8">
  Legacy version of charset declaration. Use <meta charset="UTF-8"> instead.

<meta http-equiv="X-UA-Compatible" content="IE=edge">
  Forces IE to use its latest rendering engine.
  Required for IE compatibility; harmless in modern browsers.
  Best placed BEFORE <meta name="viewport">.

<meta http-equiv="refresh" content="30">
  Refreshes the page after 30 seconds.
  <meta http-equiv="refresh" content="5; url=https://example.com">
  Redirects to URL after 5 seconds.
  ACCESSIBILITY WARNING: Auto-refreshes can disorient screen reader users.
  Use server-side 301/302 redirects instead.

<meta http-equiv="Content-Security-Policy" content="...">
  Sets Content Security Policy as a fallback (prefer HTTP header).
  <meta http-equiv="Content-Security-Policy"
    content="default-src 'self'; script-src 'self' https://cdn.example.com">

<meta http-equiv="cache-control" content="no-cache">
<meta http-equiv="pragma"        content="no-cache">
<meta http-equiv="expires"       content="0">
  Legacy caching hints. Use Cache-Control HTTP headers instead.

9. <link> ELEMENT (RELATIONSHIPS)
================================================================================

<link> defines relationships between the current document and external resources.
It's a VOID element (no closing tag). Primarily used in <head>.

Attribute     Description
----------    ------------------------------------------------------------
rel           Relationship type (required)
href          URL of the linked resource
type          MIME type of the linked resource
media         CSS media query (which media the stylesheet applies to)
crossorigin   CORS: "anonymous" or "use-credentials"
integrity     Subresource Integrity hash for security
sizes         Icon sizes (for rel="icon")
as            Resource type for preload
hreflang      Language of linked resource

Common rel values:
  stylesheet    — Link to CSS file
  icon          — Favicon
  apple-touch-icon — iOS home screen icon
  canonical     — Canonical URL
  alternate     — Alternative version (language, feed)
  preload       — High-priority resource (start downloading now)
  prefetch      — Next page prediction (low-priority, after load)
  preconnect    — Open connection to origin early
  dns-prefetch  — DNS lookup for external origin
  manifest      — Web App Manifest (PWA)
  modulepreload — Preload ES module
  author        — Author page link
  license       — License page link
  next/prev     — Paginated content

CORS with crossorigin:
  <link rel="preload" href="font.woff2" as="font" crossorigin="anonymous">
  Required for fonts because browsers use "anonymous" CORS for fonts by default.
  If crossorigin doesn't match the server's CORS headers, font won't load.

Subresource Integrity (SRI):
  <link rel="stylesheet" href="https://cdn.example.com/lib.css"
    integrity="sha384-abc123..." crossorigin="anonymous">
  Browser verifies hash of downloaded file against `integrity` value.
  If mismatch → resource blocked (CDN tampering protection).
  Generate at: https://www.srihash.org/

Favicon sizes:
  <link rel="icon" type="image/png" sizes="32x32" href="/icon-32.png">
  <link rel="icon" type="image/png" sizes="16x16" href="/icon-16.png">
  <link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">
  <link rel="icon" type="image/svg+xml" href="/icon.svg">  <!-- modern -->

10. RESOURCE HINTS (PERFORMANCE)
================================================================================

preload — Critical resource on CURRENT page (high priority):
  <link rel="preload" href="hero.jpg"     as="image">
  <link rel="preload" href="main.css"     as="style">
  <link rel="preload" href="app.js"       as="script">
  <link rel="preload" href="font.woff2"   as="font" type="font/woff2" crossorigin>
  <link rel="preload" href="data.json"    as="fetch" crossorigin>
  <link rel="preload" href="video.mp4"    as="video">

  WARNING: Preloaded but unused resources trigger console warning.
  Only preload resources needed for first paint (above-the-fold).

prefetch — Resource likely needed for NEXT navigation (low priority):
  <link rel="prefetch" href="/next-page.html" as="document">
  <link rel="prefetch" href="/images/product-detail.jpg" as="image">
  Fetched during browser idle time; stored in HTTP cache.

preconnect — Open TCP+TLS connection early (warm up external origin):
  <link rel="preconnect" href="https://fonts.googleapis.com">
  <link rel="preconnect" href="https://cdn.example.com" crossorigin>
  Saves 100-500ms by eliminating connection overhead.
  Use for: CDNs, API endpoints, font providers.
  Max recommended: 6 preconnect hints.

dns-prefetch — DNS-only preconnect (cheaper, for less critical origins):
  <link rel="dns-prefetch" href="https://analytics.example.com">
  Only resolves DNS, no TCP connection. Saves ~20-120ms.
  Useful for: analytics, ad networks, third-party widgets.
  Use dns-prefetch as fallback when preconnect is too expensive.

modulepreload — Preload ES module + its dependencies:
  <link rel="modulepreload" href="/js/app.mjs">

11. PWA-RELATED HEAD TAGS
================================================================================

Web App Manifest:
  <link rel="manifest" href="/manifest.json">
  
  manifest.json example:
  {
    "name": "My App",
    "short_name": "App",
    "description": "App description",
    "start_url": "/",
    "display": "standalone",
    "orientation": "portrait",
    "background_color": "#ffffff",
    "theme_color": "#2563eb",
    "icons": [
      { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
      { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
    ]
  }

Theme Color (browser chrome color):
  <meta name="theme-color" content="#2563eb">
  <meta name="theme-color" content="#ffffff" media="(prefers-color-scheme: light)">
  <meta name="theme-color" content="#1e293b" media="(prefers-color-scheme: dark)">

iOS-specific PWA:
  <meta name="apple-mobile-web-app-capable" content="yes">
  <meta name="apple-mobile-web-app-status-bar-style" content="default">
  <meta name="apple-mobile-web-app-title" content="App Name">
  <link rel="apple-touch-icon" href="/icon-180.png">
  <link rel="apple-touch-startup-image" href="/splash.png">

12. <title> BEST PRACTICES
================================================================================

<title>Page Topic — Site Name</title>

Rules:
  - Required in every HTML document
  - Shown in browser tab, bookmarks, search engine results (SERP)
  - Must be plain text (no HTML elements allowed inside)
  - Optimal length: 50-60 characters for SEO (longer gets truncated in SERP)

SEO patterns:
  <title>Article Title — Blog Name</title>           ← Articles
  <title>Product Name | Category | Shop</title>       ← E-commerce
  <title>About Us — Company Name</title>              ← Static pages
  <title>Home — Company Name | Tagline</title>        ← Homepage

Dynamic title updates (SPA):
  document.title = 'New Page Title — My App';
  For SPAs, update title on every route change for accessibility (screen
  readers announce page title after navigation).

13. <script> IN HEAD
================================================================================

Loading behaviors:
  <!-- Blocks HTML parsing (AVOID) -->
  <script src="app.js"></script>

  <!-- Downloads in parallel; executes when ready (order not guaranteed) -->
  <script src="analytics.js" async></script>

  <!-- Downloads in parallel; executes after DOM parsed (in order) -->
  <script src="app.js" defer></script>

  <!-- Inline script; always blocks parsing -->
  <script>console.log('hello');</script>

  <!-- ES Module (always deferred by default) -->
  <script type="module" src="app.mjs"></script>

type attribute:
  type="text/javascript"       — default; can be omitted
  type="module"                — ES module; deferred, strict mode
  type="application/ld+json"   — JSON-LD structured data (not executed)
  type="text/template"         — Template (not executed; access via .text)

Structured Data (JSON-LD):
  <script type="application/ld+json">
  {
    "@context": "https://schema.org",
    "@type": "Article",
    "headline": "How to Use Meta Tags",
    "author": { "@type": "Person", "name": "Author Name" },
    "datePublished": "2026-04-08"
  }
  </script>
  Used by Google for rich results (breadcrumbs, FAQs, reviews, etc.)

14. <style> vs <link rel="stylesheet">
================================================================================

<link rel="stylesheet" href="styles.css">
  - External stylesheet (can be cached across pages)
  - Render-blocking (browser downloads and parses before first paint)
  - Multiple allowed

<style>
  body { margin: 0; }
</style>
  - Inline styles (not cacheable; parsed immediately)
  - Use for Critical CSS (above-the-fold styles to prevent FOUC)
  - Can use @import inside (but @import is render-blocking and slow)

media attribute for conditional loading:
  <link rel="stylesheet" href="print.css"  media="print">
  <link rel="stylesheet" href="mobile.css" media="(max-width: 768px)">
  Non-matching media stylesheets are downloaded at LOW priority (non-blocking).

Critical CSS pattern:
  <!-- Inline critical CSS (above-the-fold) -->
  <style>
    /* Minimal styles for initial paint */
    header, nav, hero { ... }
  </style>
  <!-- Load full CSS non-blocking -->
  <link rel="preload" href="full.css" as="style"
        onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="full.css"></noscript>

15. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is the difference between name and http-equiv in <meta>?
A: name defines document-level metadata accessed by name (description, author,
   viewport). http-equiv simulates HTTP response headers (content-type,
   cache-control, refresh, X-UA-Compatible). They cannot be used together.

Q2: Why is <meta charset="UTF-8"> the most important meta tag?
A: Without it, the browser uses a heuristic or default encoding. If the
   document contains non-ASCII characters, they may be misinterpreted,
   leading to garbled text (mojibake) or XSS vulnerabilities (UTF-7 attack).

Q3: What is the Open Graph protocol and why is it needed?
A: OG is a set of meta properties that control how pages appear when shared
   on social media platforms (Facebook, LinkedIn, Slack, etc.). Without OG
   tags, platforms scrape random content for the preview, which may look bad.
   OG tags give you explicit control over title, description, and image.

Q4: What are resource hints and which should you use?
A: preload — critical resource needed immediately (fonts, hero image, above-fold JS)
   prefetch — resource needed for next page (link user is likely to click)
   preconnect — external origin you'll need soon (API, CDN, fonts.googleapis.com)
   dns-prefetch — cheaper preconnect for origins that are less time-critical

Q5: What is Subresource Integrity (SRI)?
A: An attribute on <link> and <script> that contains a cryptographic hash of
   the expected file. If a CDN is compromised and serves a modified file, the
   browser rejects it because the hash won't match. This is a CDN supply-chain
   attack defense.

Q6: What's the difference between preload and prefetch?
A: preload: current page needs this resource SOON — high priority, immediate
   prefetch: NEXT page will need this — low priority, happens in idle time
   preload must match how the resource will be used (via `as` attribute), or it
   won't be reused from cache.

Q7: Can you have multiple <title> tags?
A: No. Only the first <title> is used; subsequent ones are ignored by browsers.
   Having multiple is invalid HTML.

Q8: How does the canonical tag prevent duplicate content?
A: When the same content is accessible at multiple URLs (www vs non-www,
   http vs https, /page vs /page?utm_source=email), search engines may see
   them as duplicate content and dilute ranking. The canonical tag signals
   which URL is the "preferred" version, consolidating ranking signals.

Q9: What is JSON-LD and how is it used in <head>?
A: JSON-LD (JSON for Linked Data) is a structured data format embedded in a
   <script type="application/ld+json"> tag. It describes the page's content
   in a machine-readable way (using Schema.org vocabulary) and enables Google
   rich results (star ratings, FAQ dropdowns, breadcrumbs in search results).

Q10: How does the viewport meta tag affect media queries?
A: Without viewport meta, mobile browsers use a virtual viewport of ~980px,
   so @media (max-width: 768px) never matches on mobile (980 > 768).
   With viewport meta, the CSS viewport equals the device width (e.g., 375px
   on iPhone), so @media (max-width: 768px) correctly triggers responsive styles.
