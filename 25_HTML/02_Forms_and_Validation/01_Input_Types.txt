1. WHY INPUT TYPES MATTER
================================================================================

The type attribute on <input> changes:
  - The keyboard shown on mobile devices
  - Browser validation behavior
  - UI (date pickers, color pickers, sliders)
  - Data format expected and submitted
  - Accessibility semantics announced to screen readers

Always use the most specific type for the data — this improves UX on mobile,
allows browser validation, and communicates intent clearly.

Full list of input types:
  text, password, email, url, tel, search,
  number, range,
  date, time, datetime-local, month, week,
  checkbox, radio,
  file,
  color,
  hidden,
  submit, reset, button, image

2. TEXT & STRING INPUTS
================================================================================

type="text" — Single-line plain text (catch-all fallback)
  <input type="text" name="username" minlength="3" maxlength="20"
         pattern="[a-zA-Z0-9_]+" autocomplete="username">

  Attributes: minlength, maxlength, pattern, size, list, placeholder,
              readonly, required, autocomplete, spellcheck, inputmode

type="password" — Obscures characters
  <input type="password" name="password"
         minlength="8"
         autocomplete="current-password">
  
  Attributes: Same as text + autocomplete="current-password|new-password"
  Note: autocomplete="new-password" tells password managers this is a new
        password field (important for registration forms)

type="email" — Email address
  <input type="email" name="email"
         autocomplete="email"
         multiple>  ← allow comma-separated multiple emails
  
  Validation: Must match a@b format (browser-level check, not strict RFC 5322)
  Mobile: Shows email keyboard with @ symbol

type="url" — Web address
  <input type="url" name="website"
         placeholder="https://example.com">
  
  Validation: Must start with protocol (https://, ftp://, etc.)
  Mobile: Shows URL keyboard with / . and .com keys

type="tel" — Telephone number
  <input type="tel" name="phone"
         pattern="[0-9]{3}-[0-9]{3}-[0-9]{4}"
         placeholder="555-555-5555"
         autocomplete="tel">
  
  NOTE: type="tel" does NOT validate format (phone formats vary globally)
  You must add pattern for validation.
  Mobile: Shows numeric/phone keypad

type="search" — Search query
  <input type="search" name="q" role="searchbox"
         placeholder="Search...">
  
  Differences from text:
  - May show clear (×) button
  - In some browsers, styled differently (rounded corners)
  - Announces as "search field" to screen readers

3. NUMERIC INPUTS
================================================================================

type="number" — Numeric value with spinner
  <input type="number" name="quantity"
         min="1"
         max="99"
         step="1"
         value="1">
  
  Attributes: min, max, step, value, placeholder, readonly, required
  
  Step:
    step="1"    — Whole numbers (default for type=number)
    step="0.1"  — Allow one decimal place
    step="0.01" — Allow two decimal places
    step="any"  — Any value (no step validation)
  
  Mobile: Shows numeric keypad
  
  CAUTION: type="number" is NOT for:
    - Credit card numbers (leading zeros lost, too long for JS number)
    - Phone numbers (use type="tel")
    - Zip codes with leading zeros (use type="text" with pattern)
    Use type="number" only when the value truly IS a number and arithmetic
    on it makes sense.
  
  Getting value in JS:
    input.value      // String "42" — always a string from .value!
    input.valueAsNumber  // Number 42 — use this for math
    parseFloat(input.value)  // Alternative

type="range" — Slider
  <input type="range" name="volume"
         min="0"
         max="100"
         step="5"
         value="50"
         list="markers">  ← connect to datalist for tick marks
  
  <datalist id="markers">
    <option value="0" label="Mute">
    <option value="50" label="Mid">
    <option value="100" label="Max">
  </datalist>
  
  NOTE: range is imprecise by design; for precise values use type="number"
  For accessible range, add aria-valuemin, aria-valuemax, aria-valuenow
  if building a custom range, but native type="range" is accessible by default.

4. DATE & TIME INPUTS
================================================================================

type="date" — Calendar date picker
  <input type="date" name="birthday"
         min="1900-01-01"
         max="2024-12-31"
         value="1990-06-15">  ← YYYY-MM-DD format
  
  Value format: ISO 8601 — YYYY-MM-DD
  valueAsDate property: Returns a Date object (UTC)

type="time" — Time picker
  <input type="time" name="meeting-time"
         min="09:00"
         max="18:00"
         step="900"  ← step in seconds: 900 = 15-minute intervals
         value="10:00">
  
  Value format: HH:MM or HH:MM:SS (24-hour)

type="datetime-local" — Date and time (no timezone)
  <input type="datetime-local" name="event-start"
         min="2024-01-01T08:00"
         max="2024-12-31T20:00">
  
  Value format: YYYY-MM-DDTHH:MM

type="month" — Year and month picker
  <input type="month" name="exp-date"
         min="2024-01"
         max="2029-12">
  
  Value format: YYYY-MM
  Use case: credit card expiry date

type="week" — Year and week number
  <input type="week" name="sprint-week"
         min="2024-W01">
  
  Value format: YYYY-Www

Browser support for date/time inputs:
  Chrome, Edge, Firefox, Safari: Supported (Safari was late, improved in 2020)
  Fallback: Use a JavaScript date picker library (Flatpickr, Pikaday, etc.)
  Detect support: if (input.type === 'text') { /* no native support */ }

5. CHOICE INPUTS (CHECKBOX, RADIO)
================================================================================

type="checkbox" — One or more independent choices
  <fieldset>
    <legend>Skills</legend>
    <label>
      <input type="checkbox" name="skills" value="html"> HTML
    </label>
    <label>
      <input type="checkbox" name="skills" value="css"> CSS
    </label>
    <label>
      <input type="checkbox" name="skills" value="js" checked> JavaScript
    </label>
  </fieldset>
  
  Attributes: checked (pre-checked), indeterminate (JS-only, visual state)
  
  Submission behavior:
    - Only CHECKED checkboxes are submitted
    - Unchecked boxes submit NOTHING (not even an empty value)
    - Multiple checkboxes with same name produce multiple values
    - To know if unchecked: add a hidden input with same name as fallback
      <input type="hidden" name="newsletter" value="no">
      <input type="checkbox" name="newsletter" value="yes">
  
  Indeterminate state (JS only — no HTML attribute):
    checkbox.indeterminate = true;  // Visual only; .value is still false
    // Used for "select all" with partial selection

type="radio" — Mutually exclusive choices (only one per group)
  <fieldset>
    <legend>Preferred contact method</legend>
    <label>
      <input type="radio" name="contact" value="email" required> Email
    </label>
    <label>
      <input type="radio" name="contact" value="phone"> Phone
    </label>
    <label>
      <input type="radio" name="contact" value="mail"> Mail
    </label>
  </fieldset>
  
  Rules for radio groups:
    - All radios in a group MUST share the same name attribute
    - The name creates the group — only one per name can be selected
    - required on ANY radio in a group requires the whole group
    - Always wrap in fieldset > legend for accessibility
  
  Getting selected radio value:
    const selected = document.querySelector('input[name="contact"]:checked');
    const value = selected ? selected.value : null;

6. FILE INPUT
================================================================================

type="file" — File picker
  <label for="avatar">Profile photo</label>
  <input
    type="file"
    id="avatar"
    name="avatar"
    accept="image/png, image/jpeg, image/webp"
    capture="user"
    multiple>

Attributes:
  accept   — Comma-separated MIME types or file extensions
             "image/*" — Any image
             ".pdf, .doc, .docx" — Specific extensions
             "audio/*, video/*, image/*" — Media types
             
  multiple — Allow selecting multiple files
  
  capture  — Use device camera/microphone (mobile):
             "user"     — Front camera
             "environment" — Rear camera

Accessing selected files in JavaScript:
  const input = document.querySelector('input[type="file"]');
  
  input.addEventListener('change', () => {
    const files = input.files;  // FileList object
    
    for (const file of files) {
      console.log(file.name);    // "photo.jpg"
      console.log(file.size);    // Size in bytes
      console.log(file.type);    // "image/jpeg"
      console.log(file.lastModified);  // Timestamp
      
      // Create object URL for preview
      const url = URL.createObjectURL(file);
      img.src = url;
      // Release when done:
      img.onload = () => URL.revokeObjectURL(url);
    }
  });

  // Reset file input programmatically
  input.value = '';  // Clears selection

FileReader API:
  const reader = new FileReader();
  reader.onload = (e) => {
    console.log(e.target.result);  // File contents
  };
  reader.readAsText(file);         // Read as text
  reader.readAsDataURL(file);      // Read as base64 data URL
  reader.readAsArrayBuffer(file);  // Read as ArrayBuffer (binary)

Form submission with files requires:
  <form method="post" enctype="multipart/form-data">

7. COLOR, RANGE, HIDDEN
================================================================================

type="color" — Color picker
  <label for="theme-color">Theme color</label>
  <input type="color" id="theme-color" name="theme"
         value="#3b82f6">
  
  Value format: 6-character hex: #rrggbb (always lowercase)
  valueAsNumber: Not applicable
  
  Getting value: input.value → "#3b82f6"
  
  Note: No alpha/opacity support in native color picker.
  For design tools: use a JS color picker library (react-colorful, etc.)

type="hidden" — Hidden form field (not displayed)
  <input type="hidden" name="user-id" value="12345">
  <input type="hidden" name="csrf-token" value="abc123xyz">
  
  Common uses:
    - CSRF tokens (security)
    - User/session IDs
    - Tracking referral source
    - Pre-filled context data
  
  Important: Hidden inputs ARE submitted with the form but are NOT secure!
  Users can inspect and modify them in DevTools. Never rely on them for security.

================================================================================
8. BUTTON INPUT TYPES
================================================================================

type="submit" — Submit button (as input)
  <input type="submit" value="Submit Form">
  
  Equivalent to <button type="submit">Submit Form</button>
  Prefer <button> because it can contain HTML (icons, styled text)

type="reset" — Reset form button (as input)
  <input type="reset" value="Clear Form">
  
  WARNING: Reset buttons are rarely useful and often frustrating to users.
  They don't "cancel" — they restore fields to their initial values.
  Avoid unless specifically needed (like a quiz/calculator clear).

type="button" — Generic clickable button (as input)
  <input type="button" value="Click Me" onclick="doSomething()">
  
  Prefer: <button type="button">Click Me</button>

type="image" — Graphical submit button
  <input type="image" src="submit-icon.png" alt="Submit" width="40" height="40">
  
  Submits with coordinates of where user clicked (x=12&y=7).
  Rarely used today; use <button> with an <img> or SVG instead.

9. SEARCH, TEL, EMAIL, URL
================================================================================

Comparison table of text-like types:

Type        Mobile keyboard  Validation           Autocomplete tokens
--------    ---------------  -------------------  -------------------
text        Standard         None                 Various
search      Standard+search  None                 "on"
email       Email (@, .com)  Requires @ and .     "email"
url         URL (/, ., .com) Requires protocol    "url"
tel         Phone numeric    None                 "tel", "tel-national"
password    Standard         None                 "current-password", "new-password"

type="search" behavioral differences:
  - Some browsers add a × clear button
  - May remember previous searches
  - Press Enter submits the form (same as text)
  - aria role: "searchbox"
  
  Best practice:
  <form role="search">
    <label for="site-search">Search site</label>
    <input type="search" id="site-search" name="q" placeholder="Search...">
    <button type="submit">Search</button>
  </form>

Email validation nuances:
  - Browser validates presence of @ and a domain: user@domain.tld
  - Not strict RFC 5322 (no quoted strings, no unicode domains by default)
  - For server-validated email, do your own server-side validation too
  - multiple attribute allows comma-separated email list:
    <input type="email" name="cc" multiple>
    → user1@example.com, user2@example.com

10. AUTOCOMPLETE ATTRIBUTE DEEP DIVE
================================================================================

The autocomplete attribute helps browsers (and password managers) fill fields:

autocomplete="off"        — Disable autofill (not always respected by browsers)
autocomplete="on"         — Enable autofill (browser decides)

Personal info tokens:
  "name"                  Full name
  "given-name"            First name
  "family-name"           Last name
  "email"                 Email address
  "username"              Username/login
  "current-password"      Existing password (login forms)
  "new-password"          New password (signup/change password)
  "one-time-code"         OTP / SMS code

Address tokens:
  "street-address"        Full street address
  "address-line1"         Street line 1
  "address-line2"         Street line 2
  "city"                  City
  "state"                 State/province
  "postal-code"           ZIP/postal code
  "country"               Country

Financial tokens:
  "cc-name"               Cardholder name
  "cc-number"             Credit card number
  "cc-exp"                Expiration date (YYYY-MM)
  "cc-csc"                CVV / security code

Contact tokens:
  "tel"                   Full phone number
  "tel-country-code"      Country code (+1, +44)
  "tel-national"          National phone number

  <!-- Complete billing form example -->
  <input type="text"   name="cc-name"   autocomplete="cc-name">
  <input type="text"   name="cc-number" autocomplete="cc-number" inputmode="numeric">
  <input type="month"  name="cc-exp"    autocomplete="cc-exp">
  <input type="text"   name="cc-csc"    autocomplete="cc-csc" inputmode="numeric">

inputmode attribute (keyboard hint without changing type):
  "none"        No keyboard (custom keyboard)
  "text"        Standard text keyboard
  "decimal"     Numeric with decimal point
  "numeric"     Numeric only (no decimal)
  "tel"         Phone keypad
  "search"      Search keyboard (go key)
  "email"       Email keyboard
  "url"         URL keyboard

  <!-- Zip code — text type (preserve leading zeros), numeric keyboard -->
  <input type="text" name="zip" inputmode="numeric" pattern="[0-9]{5}">

11. INPUT STATES & PSEUDO-CLASSES
================================================================================

HTML states:
  :enabled   — Not disabled
  :disabled  — Has disabled attribute
  :read-only — Has readonly attribute
  :read-write — Not readonly and not disabled
  :required  — Has required attribute
  :optional  — Not required
  :checked   — Checked checkbox or radio
  :indeterminate — Checkbox in indeterminate state
  :valid     — Passes constraint validation
  :invalid   — Fails constraint validation
  :in-range  — Value within min/max
  :out-of-range — Value outside min/max
  :placeholder-shown — Placeholder is visible (no value)
  :focus-visible — Focused via keyboard (not mouse)
  :autofill  — Filled by browser autofill

CSS styling form states:
  input:required { border-left: 3px solid orange; }
  input:invalid:not(:placeholder-shown) { border-color: red; }
  input:valid:not(:placeholder-shown) { border-color: green; }
  input:focus-visible { outline: 2px solid #3b82f6; outline-offset: 2px; }
  input:disabled { opacity: 0.5; cursor: not-allowed; }

  /* Don't show validation styles until user has interacted */
  input:not(:placeholder-shown):invalid { ... }
  /* Or use a .was-validated class added on submit */

12. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: Why should you use specific input types (email, number, etc.) instead of
    always using type="text"?
A: Specific types improve UX on mobile (correct keyboard layout), enable
   built-in browser validation (email requires @, number accepts only numeric),
   trigger native UI controls (date pickers, color pickers, sliders), improve
   accessibility (screen readers announce input purpose), and signal to
   password managers and autofill what data belongs in each field.

Q2: What is the difference between type="number" and type="tel"?
A: Both show a numeric keyboard on mobile, but they're fundamentally different.
   type="number" represents a mathematical number — supports min, max, step,
   and arithmetic. The value property is always a number string. type="tel"
   represents a telephone number — no validation, accepts dashes, spaces,
   parentheses, and leading zeros (which type="number" would strip). Use
   type="tel" for phone numbers, type="number" for quantities and measurements.

Q3: What happens to unchecked checkboxes during form submission?
A: Unchecked checkboxes are NOT included in the form submission at all — no
   key/value pair is sent for them. This is unlike other inputs where an empty
   value is submitted. If you need to know a checkbox was intentionally
   unchecked, add a hidden input with the same name and a default "no" value
   before the checkbox — the checkbox's "yes" value will override it when checked.

Q4: How do radio buttons work — what makes them a group?
A: Radio buttons with the same name attribute form a group where only one can
   be selected at a time. Selecting one automatically deselects others in the
   group. Always wrap in <fieldset> + <legend> for accessibility (the legend
   provides the group question). The required attribute on any one radio in the
   group makes the whole group required.

Q5: What is the purpose of the accept attribute on file inputs?
A: accept filters what files the browser shows in the file picker dialog and
   helps signal to mobile devices which interface to use (camera, files app,
   etc.). Values can be MIME types ("image/png", "application/pdf"), extension
   groups ("image/*", "video/*"), or file extensions (".pdf, .docx").
   IMPORTANT: accept is a UX hint, NOT security — users can bypass it in DevTools
   or by changing file extension. Always validate file type on the server.

Q6: What is the difference between value and valueAsNumber?
A: input.value always returns a string (e.g., "42.5" for a number input, "").
   input.valueAsNumber returns the current value as a JavaScript Number
   (e.g., 42.5, or NaN if empty/invalid). Always use valueAsNumber for math
   to avoid type coercion bugs. Similarly, valueAsDate returns a Date object
   for date/time inputs.

Q7: How does type="hidden" differ from display:none on an input?
A: type="hidden" inputs are never displayed, their label is never announced to
   screen readers, and they ARE submitted with the form. An input with
   display:none is visually hidden but might still be announced by assistive
   technology (problematic), and IS submitted. type="hidden" is the correct
   way to pass data with form submission without displaying it to users. Both
   are visible in page source/DevTools — neither is secure.

Q8: What is the capture attribute and when do you use it?
A: capture is used with type="file" on mobile devices to directly invoke the
   camera or microphone instead of the file picker. capture="user" opens the
   front-facing camera; capture="environment" opens the rear camera. It's
   used in mobile web apps for profile photo upload, document scanning, or
   video recording. On desktop browsers it's ignored.

Q9: What is the difference between :invalid and :out-of-range?
A: :out-of-range specifically targets inputs where the value falls outside the
   min/max range (applies to number, date, time, range). :invalid is broader —
   it matches any input failing validation, including: empty required fields,
   pattern mismatches, type mismatches, AND out-of-range values. A field can
   be :invalid due to :out-of-range or for other validation failures.

Q10: What does autocomplete="new-password" do differently from "current-password"?
A: autocomplete="current-password" tells password managers this field is for
   an existing password (login form) — it should offer to fill saved passwords.
   autocomplete="new-password" tells password managers this field is for
   creating a NEW password — it should offer to generate a strong password
   and save it, and should NOT fill existing passwords. Using these correctly
   significantly improves UX for login and registration forms.
