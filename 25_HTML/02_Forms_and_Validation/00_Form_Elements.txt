1. THE <form> ELEMENT
================================================================================

<form> wraps form controls and defines how data is submitted.

Attributes:
  action    — URL where form data is sent (default: current URL)
  method    — HTTP method: GET or POST (default: GET)
  enctype   — Encoding type for POST (see below)
  target    — Where to show response: _self | _blank | _parent | _top | framename
  novalidate — Disables browser's built-in validation
  autocomplete — "on" | "off" — hints browser for autofill
  name      — Name of form (legacy — used by document.forms[name])
  rel       — Relationship (e.g., rel="noopener" for target=_blank)

enctype values (for method="post"):
  application/x-www-form-urlencoded  — Default; name=value pairs URL-encoded
  multipart/form-data                — REQUIRED for file uploads (<input type="file">)
  text/plain                         — For debugging only; not secure

GET vs POST:
  GET:
    - Data appended to URL as query string: ?name=John&age=30
    - Visible in browser history and server logs
    - Bookmarkable
    - Limited data length (URL length limits ~2000 chars)
    - Safe for non-sensitive search/filter forms
    - Cacheable

  POST:
    - Data in request body (not visible in URL)
    - Not bookmarkable by default
    - No size limit (server-side limits apply)
    - Required for file uploads, passwords, large data
    - Not cached by default

Example form:
  <form
    action="/api/contact"
    method="post"
    enctype="application/x-www-form-urlencoded"
    novalidate
    autocomplete="on">
    
    <!-- Form controls -->
    <button type="submit">Send</button>
  </form>

Accessing forms via JavaScript:
  document.forms['formName']   // By name attribute
  document.forms[0]            // By index
  document.querySelector('form')  // CSS selector

  form.elements['fieldName']   // Access a field by name
  form.elements.namedItem('email')
  
  form.submit()        // Submit programmatically (skips validation!)
  form.requestSubmit() // Submit programmatically (triggers validation)
  form.reset()         // Reset all fields to initial values
  form.checkValidity() // Returns false if any invalid fields

2. <fieldset> AND <legend>
================================================================================

<fieldset> groups related form controls visually and semantically.
<legend> provides a caption for the fieldset (required for accessibility).

  <fieldset>
    <legend>Personal Information</legend>
    
    <label for="fname">First Name</label>
    <input type="text" id="fname" name="firstName" required>
    
    <label for="lname">Last Name</label>
    <input type="text" id="lname" name="lastName" required>
  </fieldset>

Disabling all controls in a fieldset:
  <fieldset disabled>
    <legend>Payment (unavailable)</legend>
    <!-- All inputs, buttons, selects inside are disabled -->
    <input type="text" name="card">
    <button type="submit">Pay</button>
  </fieldset>
  Note: A disabled fieldset disables ALL controls inside it.

Styling:
  fieldset {
    border: 1px solid #d1d5db;
    border-radius: 8px;
    padding: 16px;
  }
  legend {
    padding: 0 8px;
    font-weight: bold;
    color: #374151;
  }

Use cases:
  - Group a set of radio buttons (related choices)
  - Group a set of checkboxes
  - Separate shipping and billing addresses
  - Multi-step form sections

Accessibility:
  - Screen readers announce the <legend> text before each control inside
  - For radio groups, <fieldset> + <legend> is REQUIRED for accessibility
    because the legend provides the group question
  - Example: fieldset > legend "Preferred contact method" + 3 radio buttons

3. <label>
================================================================================

<label> associates a text label with a form control.

Two association methods:

  1. Explicit (for + id):
     <label for="email-input">Email Address</label>
     <input type="email" id="email-input" name="email">

  2. Implicit (wrapping):
     <label>
       Email Address
       <input type="email" name="email">
     </label>

Benefits of properly associated labels:
  ✓ Click/tap label to focus the control (larger click target)
  ✓ Screen readers announce label when control is focused
  ✓ Required for WCAG 2.1 AA compliance

Accessibility issues to avoid:
  ✗ Placeholder as only label — placeholder disappears on input
  ✗ ARIA label instead of <label> (use both for best support)
  ✗ Labels without 'for' attribute (implicit wrapping is fine)

Label for checkboxes and radio buttons:
  Label should describe the choice, not the group (group = legend):
  <fieldset>
    <legend>Notification preferences</legend>
    <label>
      <input type="checkbox" name="notify" value="email"> Email
    </label>
    <label>
      <input type="checkbox" name="notify" value="sms"> SMS
    </label>
  </fieldset>

Multiple labels (for accessibility):
  You can have multiple labels for one input using aria-labelledby:
  <label id="date-label">Date of birth</label>
  <span id="date-hint">(DD/MM/YYYY)</span>
  <input type="text" aria-labelledby="date-label date-hint" name="dob">

4. <input>
================================================================================

The most versatile form element. Type attribute changes its entire behavior.

Common attributes (shared by all input types):
  name         — Key in submitted form data
  id           — For label association
  value        — Current value (default value is initial)
  placeholder  — Hint text (NOT a substitute for labels)
  required     — Field must be filled
  disabled     — Not submitted; not focusable
  readonly     — Displayed but not editable; IS submitted
  autofocus    — Auto-focuses on page load (use sparingly — one per page)
  autocomplete — Hint for autofill: "name", "email", "current-password", etc.
  tabindex     — Order in tab sequence (0 = natural order; -1 = skip)
  form         — Associate with form by ID (can be outside the form element)

Type-specific attributes are covered in the next file (01_Input_Types.txt).

  <!-- Text input with all common attributes -->
  <label for="username">Username</label>
  <input
    type="text"
    id="username"
    name="username"
    value=""
    placeholder="e.g. john_doe"
    required
    minlength="3"
    maxlength="20"
    pattern="[a-z0-9_]+"
    autocomplete="username"
    aria-describedby="username-hint">
  <span id="username-hint">Lowercase letters, numbers, underscores only</span>

5. <textarea>
================================================================================

Multi-line text input.

  <label for="bio">Biography</label>
  <textarea
    id="bio"
    name="bio"
    rows="5"
    cols="40"
    maxlength="500"
    placeholder="Tell us about yourself..."
    required
    autocomplete="off"
    spellcheck="true"
    wrap="soft">Initial content here</textarea>

Attributes:
  rows      — Visible number of text lines (default: 2)
  cols      — Visible width in characters (default: 20; use CSS width instead)
  maxlength — Maximum characters allowed
  minlength — Minimum characters required
  wrap      — "soft" (submit newlines as typed); "hard" (wrap to cols width with \r\n); "off"
  resize    — CSS property: resize: vertical | horizontal | both | none

IMPORTANT: Value is placed between tags (not in a value attribute):
  <textarea>This is the initial value</textarea>
  In JavaScript: textarea.value = 'new content';  // read/write

Auto-resize textarea with JavaScript:
  textarea.addEventListener('input', function() {
    this.style.height = 'auto';
    this.style.height = this.scrollHeight + 'px';
  });

6. <select>, <optgroup>, <option>
================================================================================

Dropdown selection control.

Basic select:
  <label for="country">Country</label>
  <select id="country" name="country" required>
    <option value="">-- Select a country --</option>
    <option value="us" selected>United States</option>
    <option value="uk">United Kingdom</option>
    <option value="ca">Canada</option>
  </select>

Select attributes:
  multiple    — Allow multiple selections (hold Ctrl/Cmd to multi-select)
  size        — Number of visible options (when multiple or size > 1, shows listbox)
  disabled    — Disables the select
  required    — At least one option must be selected
  name        — Form field name

  <!-- Multi-select -->
  <select name="skills" multiple size="4">
    <option value="js">JavaScript</option>
    <option value="py">Python</option>
    <option value="java">Java</option>
    <option value="go">Go</option>
  </select>

<option> attributes:
  value     — Value submitted (if omitted, text content is used)
  selected  — Pre-selects this option
  disabled  — This option is unselectable
  label     — Short label (shown if different from text)

<optgroup> — Groups options with a label:
  <select name="car">
    <optgroup label="European">
      <option value="bmw">BMW</option>
      <option value="audi">Audi</option>
    </optgroup>
    <optgroup label="American">
      <option value="ford">Ford</option>
      <option value="tesla">Tesla</option>
    </optgroup>
  </select>

Reading selected values in JavaScript:
  // Single select
  const val = select.value;

  // Multiple select — all selected values
  const selected = [...select.options]
    .filter(opt => opt.selected)
    .map(opt => opt.value);
  
  // Or
  const selected = [...select.selectedOptions].map(o => o.value);

7. <datalist>
================================================================================

Provides autocomplete suggestions for an input (not a replacement for select).

  <label for="browser">Favorite Browser</label>
  <input
    type="text"
    id="browser"
    name="browser"
    list="browsers"
    placeholder="Start typing...">

  <datalist id="browsers">
    <option value="Chrome">
    <option value="Firefox">
    <option value="Safari">
    <option value="Edge">
    <option value="Opera">
  </datalist>

Key characteristics:
  - User can type freely (not restricted to list items, unlike <select>)
  - Browser shows matching suggestions as user types
  - Suggestions are case-insensitive prefix matches (browser-dependent)
  - Works with input types: text, search, url, tel, email, number, range, date, etc.
  - The list attribute on input links to datalist by ID

  <!-- Datalist with range -->
  <input type="range" min="0" max="100" list="markers">
  <datalist id="markers">
    <option value="0">
    <option value="25">
    <option value="50">
    <option value="75">
    <option value="100">
  </datalist>
  <!-- Shows tick marks at specified positions -->

8. <button>
================================================================================

Clickable button. Preferred over <input type="button"> because it can have
child HTML content.

  <button type="submit">Submit Form</button>
  <button type="reset">Reset</button>
  <button type="button" id="cancel-btn">Cancel</button>
  <button type="button">
    <svg aria-hidden="true">...</svg>
    Save Document
  </button>

type attribute (CRITICAL):
  submit  — Submits the form (DEFAULT in forms — be explicit!)
  reset   — Resets all form fields to initial values
  button  — No default behavior (must use JavaScript)

WARNING: A <button> without a type inside a <form> defaults to type="submit".
This is a common bug where unexpected form submissions occur.

  <!-- BUG: This button submits the form! -->
  <form>
    <input type="text" name="q">
    <button>Search</button>  <!-- type="submit" by default! -->
    <button>Filter</button>  <!-- ALSO submits the form! -->
  </form>

  <!-- FIX: Be explicit -->
  <button type="submit">Search</button>
  <button type="button" onclick="openFilters()">Filter</button>

Button attributes:
  disabled            — Disables the button
  name / value        — Submitted with form data (type="submit" only)
  form                — Associate with form by ID (can be outside form)
  formaction          — Override form's action URL (type="submit")
  formmethod          — Override form's method (type="submit")
  formenctype         — Override form's enctype (type="submit")
  formnovalidate      — Submit without validation (type="submit")
  formtarget          — Override form's target (type="submit")
  autofocus           — Auto-focus on page load

Multiple submit buttons (different actions):
  <button type="submit" formaction="/save" name="action" value="save">Save</button>
  <button type="submit" formaction="/publish" name="action" value="publish">Publish</button>
  <button type="submit" formaction="/delete" formmethod="post" name="action" value="delete">Delete</button>

9. <output>
================================================================================

Represents the result of a calculation or user action.

  <form oninput="result.value = parseInt(a.value) + parseInt(b.value)">
    <label for="a">Number A:</label>
    <input type="number" id="a" name="a" value="10">
    +
    <label for="b">Number B:</label>
    <input type="number" id="b" name="b" value="20">
    =
    <output name="result" for="a b">30</output>
  </form>

Attributes:
  name — Name for the output (included in form data)
  for  — Space-separated list of IDs of inputs that contributed to the output

Semantically communicates: "this value is derived from these inputs."
Screen readers announce it appropriately.

10. <meter> AND <progress>
================================================================================

<meter> — Scalar value within a known range (gauge/rating):
  <meter
    value="0.7"
    min="0"
    max="1"
    low="0.25"
    high="0.75"
    optimum="1">
    70% used
  </meter>

  Attributes:
    value    — Current value (required)
    min      — Minimum value (default: 0)
    max      — Maximum value (default: 1)
    low      — Threshold below which is "low"
    high     — Threshold above which is "high"
    optimum  — "Ideal" value (determines which region is colored green/yellow/red)

  Use cases: disk usage, password strength, skill rating, battery level
  
  Meter bar colors (browser defaults):
    Value in optimal region  → green
    Value in "meh" region    → yellow
    Value in bad region      → red

<progress> — Progress bar for ongoing task:
  <!-- Determinate (known progress) -->
  <progress value="65" max="100">65%</progress>
  
  <!-- Indeterminate (unknown duration) — omit value attribute -->
  <progress max="100">Loading...</progress>

  Use cases: file upload, download, multi-step form, loading state

  <!-- With accessible label -->
  <label for="file-progress">Upload progress</label>
  <progress id="file-progress" value="0" max="100">0%</progress>

  Updating with JavaScript:
  const bar = document.querySelector('progress');
  bar.value = 45;  // 45%

11. FORM GROUPING AND LAYOUT PATTERNS
================================================================================

Accessible form layout:

  <!-- Complete accessible form pattern -->
  <form novalidate>
    <fieldset>
      <legend>Account Details</legend>
      
      <!-- Field with error -->
      <div class="field">
        <label for="email">
          Email address
          <abbr title="required" aria-label="required">*</abbr>
        </label>
        <input
          type="email"
          id="email"
          name="email"
          aria-required="true"
          aria-describedby="email-error email-hint"
          aria-invalid="true">
        <span id="email-hint" class="hint">
          We'll never share your email.
        </span>
        <span id="email-error" class="error" role="alert">
          Please enter a valid email address.
        </span>
      </div>

      <!-- Password with toggle -->
      <div class="field">
        <label for="password">Password</label>
        <div class="input-group">
          <input type="password" id="password" name="password" required>
          <button type="button" aria-controls="password"
                  aria-pressed="false" id="toggle-pw">
            Show
          </button>
        </div>
      </div>
    </fieldset>
    
    <button type="submit">Create Account</button>
  </form>

Form layout — CSS Grid:
  .field {
    display: grid;
    grid-template-columns: 1fr 2fr;
    align-items: start;
    gap: 8px;
    margin-bottom: 16px;
  }
  label { grid-column: 1; padding-top: 8px; font-weight: 600; }
  input, select, textarea { grid-column: 2; }
  .hint, .error { grid-column: 2; font-size: 0.85rem; }

12. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: What is the difference between GET and POST in form submission?
A: GET appends form data to the URL as a query string — it's visible in the
   address bar, bookmarkable, cached, and limited in data size. POST sends
   data in the HTTP request body — not visible in the URL, not cached by
   default, and has no practical size limit. Use GET for search/filter forms
   where sharing the URL is useful; use POST for anything sensitive (passwords),
   file uploads, or large data.

Q2: When must you use enctype="multipart/form-data"?
A: When the form contains file inputs (<input type="file">). The default
   application/x-www-form-urlencoded can only handle text (ASCII-encoded
   key=value pairs). multipart/form-data splits the request body into parts —
   one per field — allowing binary file data to be transmitted intact. Without
   this, file data is corrupted or truncated.

Q3: What is the default type of a <button> element and why does it matter?
A: The default type is "submit". This means any <button> inside a <form>
   without an explicit type attribute will submit the form when clicked.
   A common bug occurs when developers add a button for non-submission purposes
   (filter, expand, etc.) without setting type="button" — accidentally triggering
   form submission. Always explicitly set type="submit", type="reset", or
   type="button".

Q4: What is the difference between disabled and readonly on form inputs?
A: A disabled input is not interactive (can't be focused or changed), not
   submitted with the form, and visually dimmed. A readonly input is not
   editable but can be focused, tabbed to, its value is selectable and
   copyable, and it IS submitted with the form. Use disabled when the field
   is contextually irrelevant; use readonly when you want to show a value that
   should be submitted but not edited (e.g., a calculated field).

Q5: How do you associate a label with an input? Why does it matter?
A: Two methods: (1) Explicit — label's for attribute matches input's id.
   (2) Implicit — wrap the input inside the label element. Associated labels
   give users a larger click/tap target (clicking label focuses input),
   and screen readers announce the label text when the input receives focus.
   Without proper association, visually impaired users may not know what
   a field is for.

Q6: What is the difference between <select> and <datalist>?
A: <select> provides a closed choice — user must pick from the predefined list.
   <datalist> provides suggestions while allowing free text input — the user can
   select a suggestion or type anything else. Use <select> when the answer must
   be one of the valid options (e.g., country, state, file format). Use
   <datalist> for autocomplete suggestions where custom input is acceptable
   (e.g., browser preference, city name with suggestions).

Q7: What is <fieldset disabled> useful for?
A: When you set disabled on a fieldset, it disables ALL form controls inside it
   (inputs, buttons, selects, textareas) at once. This is useful for:
   (1) Multi-step forms — disable previous steps. (2) Conditional sections —
   disable a payment section when selecting "pay later". (3) While submitting —
   disable the whole form to prevent double submission. Using fieldset disabled
   is cleaner than setting disabled on each control individually.

Q8: What is the purpose of the form attribute on inputs and buttons?
A: The form attribute lets a form control be placed anywhere in the document
   (not necessarily inside the <form> tags) while still being associated with
   that form. The value should be the form's id. This is useful for layouts
   where it's impractical to wrap controls in a form (e.g., a submit button in
   a footer/toolbar that's outside the form's visual container).

Q9: What is <output> and when would you use it?
A: <output> semantically represents a calculated or user-action result. It's
   associated with its inputs via the for attribute (space-separated input IDs).
   Screen readers announce it as an interactive computation result. Use it for
   live calculations (sum, percentage, price total) that update as users
   interact with the form, as it's more semantic than a plain <span>.

Q10: What is the difference between <meter> and <progress>?
A: <progress> represents the completion status of a task (either determinate
   with value/max or indeterminate without value — shows an animated bar).
   <meter> represents a scalar value within a known range that has semantic
   optimal/low/high regions (e.g., disk usage at 85% would show red if high
   is set below that). Use progress for loading/upload; use meter for
   gauges, ratings, or measurements with qualitative interpretation.
