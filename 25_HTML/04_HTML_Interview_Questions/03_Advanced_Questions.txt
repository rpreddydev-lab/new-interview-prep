1. PERFORMANCE AND LOADING QUESTIONS
================================================================================

Q1: How does resource loading order affect page performance?
A: The browser parses HTML top-to-bottom. Resources encountered trigger
   fetches. Critical path: HTML → DOM construction → CSSOM construction →
   Render tree → Layout → Paint. CSS in <head> blocks rendering until parsed.
   Non-deferred scripts block parsing until downloaded and executed. Images
   don't block parsing but cause layout shifts if dimensions aren't set.
   Best practices: (1) <link rel="stylesheet"> in <head>; (2) <script defer>
   in <head> (downloads parallel, executes after parse); (3) <script async>
   for analytics; (4) width/height on <img> prevents CLS; (5) loading="lazy"
   on below-fold images; (6) fetchpriority="high" on LCP image.

Q2: What are resource hints and what do rel="preload", "prefetch",
    "preconnect" do?
A: Resource hints instruct the browser to fetch resources before they're
   explicitly needed:
   
   preconnect — establish TCP/TLS connection to origin early; use for
   critical third-party origins (fonts, CDN):
   <link rel="preconnect" href="https://fonts.googleapis.com">
   
   dns-prefetch — resolve DNS only (lighter weight than preconnect):
   <link rel="dns-prefetch" href="https://cdn.example.com">
   
   preload — declare current page needs a resource high priority NOW:
   <link rel="preload" href="font.woff2" as="font" crossorigin>
   <link rel="preload" href="hero.jpg" as="image" fetchpriority="high">
   
   prefetch — fetch a resource for likely future navigation (lower priority):
   <link rel="prefetch" href="/next-page.html">
   
   prerender (Chrome) — fully render a page in background for instant navigation
   
   as= attribute on preload is required — tells browser content type for
   priority and CSP checking.

Q3: What is the difference between loading="lazy" and lazy loading via JS?
A: loading="lazy" is the native browser attribute for <img> and <iframe>:
   the browser defers loading until the element is near the viewport (based
   on connection speed and estimated distance). No JavaScript required, works
   with CSS background images only if JavaScript is used. Benefits: simple,
   performant, browser-native. Limits: no control over threshold distance.
   JavaScript lazy loading (IntersectionObserver API) gives more control:
   custom thresholds, custom behavior, works for any element type (including
   CSS background images), can implement progressive loading. Use native
   loading="lazy" first; fall back to JS for custom requirements.

Q4: What is Core Web Vitals and which HTML decisions affect them?
A: Core Web Vitals (CWV) are Google's user-centric performance metrics:
   
   LCP (Largest Contentful Paint) — loading; target < 2.5s
   HTML impact: fetchpriority="high" on LCP <img>, preload the LCP image,
   avoid lazy loading the LCP image, use responsive images (srcset).
   
   INP (Interaction to Next Paint) — responsiveness; target < 200ms
   HTML impact: script defer/async (don't block main thread), code-split
   scripts, minimize blocking third-party scripts.
   
   CLS (Cumulative Layout Shift) — visual stability; target < 0.1
   HTML impact: ALWAYS set width and height on <img> (browser reserves space),
   set aspect-ratio on containers, avoid inserting content above existing content,
   font-display: swap handling.

Q5: What is the fetchpriority attribute?
A: fetchpriority is an HTML attribute (and Fetch API option) that hints
   relative priority for resource loading. Values: high, low, auto (default).
   Use cases:
   <img fetchpriority="high" src="hero.jpg" alt="...">  — LCP image
   <img fetchpriority="low" src="below-fold.jpg" alt="...">  — non-critical
   <link rel="preload" fetchpriority="high" href="critical.css" as="style">
   <script fetchpriority="low" src="analytics.js" async></script>
   
   Particularly important for LCP optimization: the browser normally discovers
   images late in parsing; fetchpriority="high" signals the preload scanner
   to prioritize the fetch. Combined with loading="eager" for above-fold,
   this can significantly improve LCP.

2. SECURITY QUESTIONS
================================================================================

Q6: What is Cross-Site Scripting (XSS) and how does HTML prevent it?
A: XSS occurs when attackers inject malicious scripts into pages viewed by
   others. HTML defenses: (1) Never set innerHTML/outerHTML with untrusted
   data — use textContent/innerText for text content; (2) Content Security
   Policy (CSP) via <meta> or HTTP header — restricts which scripts can execute:
   <meta http-equiv="Content-Security-Policy" content="default-src 'self'">
   (3) Sanitize input before rendering (DOMPurify library); (4) Use template
   literals with DOM API instead of string concatenation; (5) Set HttpOnly
   on cookies (prevents JS access). The #1 rule: never trust user input;
   encode output when rendering in HTML context.

Q7: What is Cross-Site Request Forgery (CSRF) and how do forms prevent it?
A: CSRF tricks a logged-in user into unknowingly submitting a form to a target
   site (the malicious site hosts a form pointing to bank.com and auto-submits).
   Prevention methods: (1) CSRF tokens — unique, secret value in a hidden
   form field that server validates: <input type="hidden" name="csrf_token"
   value="[unique-token]">; (2) SameSite cookie attribute — SameSite=Strict
   or SameSite=Lax prevents cookies from being sent on cross-origin form
   submissions; (3) Custom request headers — AJAX requests with a custom
   header (X-Requested-With) can't be forged by simple forms; (4) Origin/
   Referer header checking on server. CSRF primarily applies to state-changing
   requests (POST, PUT, DELETE).

Q8: What is Content Security Policy (CSP)?
A: CSP is an HTTP header (or meta tag) that tells the browser which content
   sources are allowed to load. It mitigates XSS by preventing inline scripts
   and limiting external script sources:
   <meta http-equiv="Content-Security-Policy" 
         content="default-src 'self'; script-src 'self' 'nonce-abc123'; 
                  style-src 'self' 'unsafe-inline'; img-src 'self' data:">
   
   Directives: default-src (fallback), script-src, style-src, img-src,
   connect-src, font-src, object-src, media-src, frame-src.
   
   Nonce-based CSP: each script tag gets a unique nonce attribute that
   matches the server-generated nonce in the CSP header:
   <script nonce="abc123">...</script>
   This allows specific inline scripts without 'unsafe-inline'.

Q9: What is the sandbox attribute on <iframe>?
A: The sandbox attribute applies restrictions to iframed content. Empty
   sandbox restricts everything: no scripts, no forms, no popups, no
   same-origin access:
   <iframe src="..." sandbox>  <!-- Maximum restrictions -->
   
   Permissions can be added back selectively:
   <iframe src="..." sandbox="allow-scripts allow-forms">
   
   Values: allow-scripts (JS), allow-forms (submit), allow-popups (window.open),
   allow-same-origin (treat as same origin — careful!), allow-top-navigation
   (navigate parent frame), allow-modals, allow-downloads.
   
   WARNING: sandbox="allow-scripts allow-same-origin" together allows the
   framed content to remove sandbox restrictions — never combine these unless
   you fully trust the content.

Q10: What HTML attributes improve security of external links?
A: For links opening in new tabs/windows (_blank):
   rel="noopener" — prevents the opened page from accessing the opener's
   window object via window.opener — prevents tab-napping attacks where
   the new tab redirects the original tab.
   rel="noreferrer" — also prevents sending the Referer header to the
   destination and implies noopener.
   
   <a href="https://external.com" target="_blank" rel="noopener noreferrer">
   
   Since 2021, modern browsers default target="_blank" links to imply
   noopener, but explicitly setting it is still best practice for older
   browsers and clarity.
   
   rel="nofollow" — instructs search engines not to follow the link
   (doesn't affect security but is common for UGC links).

3. APIS AND BROWSER FEATURES QUESTIONS
================================================================================

Q11: What is the History API and how does it enable SPAs?
A: The History API (window.history) allows JavaScript to manipulate the
   browser history stack without triggering page navigation:
   
   history.pushState(state, title, '/new-path') — Add entry, change URL
   history.replaceState(state, title, '/current') — Replace current entry
   window.addEventListener('popstate', (e) => e.state) — Back/forward
   history.back() / history.forward() / history.go(-2) — Navigate
   
   This is the foundation of client-side routing in React Router, Vue Router,
   etc. — URLs change, browser history works, but no server request is made.
   Challenge: server must handle all URL patterns (return index.html for any
   path) or users get 404 on hard refresh. Alternative: hash routing (/#/path)
   — older approach using URL hash, no server config needed but less clean URLs.

Q12: What are Web Workers and how do they relate to HTML?
A: Web Workers run JavaScript in a background thread, separate from the main
   thread (UI thread). They cannot access the DOM but can perform CPU-intensive
   tasks without blocking the UI.
   
   Creation: const worker = new Worker('worker.js');
   Communication: postMessage / onmessage event-based messaging.
   
   Types: Dedicated Workers (one page), Shared Workers (multiple pages/tabs),
   Service Workers (intercept network requests, enable offline, PWA).
   
   Service Workers: registered via HTML's script:
   navigator.serviceWorker.register('/sw.js')
   Power: push notifications, background sync, cache API for offline support.
   They work as a network proxy — intercept fetch requests, serve cached
   responses. Enabling PWA features.

Q13: What is the Intersection Observer API and what is it used for?
A: IntersectionObserver watches when elements enter or exit the viewport
   (or a specified root element) — without expensive scroll event listeners.
   
   Use cases: lazy loading images (polyfill or supplement loading="lazy"),
   infinite scroll, animating elements on scroll, tracking ad visibility,
   sticky header behavior.
   
   const observer = new IntersectionObserver((entries) => {
     entries.forEach(entry => {
       if (entry.isIntersecting) {
         entry.target.src = entry.target.dataset.src; // Lazy load image
         observer.unobserve(entry.target);
       }
     });
   }, { rootMargin: '200px' }); // Start loading 200px before visible
   
   document.querySelectorAll('img[data-src]').forEach(img => observer.observe(img));

Q14: What is the Mutation Observer API?
A: MutationObserver watches for DOM changes — node additions/removals,
   attribute changes, text content changes. More efficient than polling.
   
   const observer = new MutationObserver((mutations) => {
     mutations.forEach(mutation => {
       if (mutation.type === 'childList') {
         console.log('Children changed:', mutation.addedNodes);
       }
       if (mutation.type === 'attributes') {
         console.log('Attribute changed:', mutation.attributeName);
       }
     });
   });
   
   observer.observe(targetNode, {
     childList: true,    // Watch child node additions/removals
     attributes: true,   // Watch attribute changes
     subtree: true,      // Watch entire subtree
     characterData: true // Watch text content changes
   });
   observer.disconnect(); // Stop observing
   
   Use cases: custom analytics, implementing auto-save, polyfilling features,
   third-party widget observation, accessibility tree monitoring.

Q15: What is the <dialog> element and what are its advantages?
A: <dialog> is the native HTML modal/non-modal dialog element. Methods:
   dialog.showModal() — opens as modal (focus trapped, Escape closes, ::backdrop)
   dialog.show() — opens as non-modal (no focus trap)
   dialog.close(returnValue) — closes dialog
   dialog.returnValue — value passed to close()
   
   Advantages over custom div modals: (1) Native focus trapping (showModal);
   (2) Escape key closes automatically; (3) ::backdrop pseudo-element for
   overlay styling; (4) role="dialog" and aria-modal="true" built-in;
   (5) close event fires when closed; (6) Works with native form submit
   (method="dialog" on <form> closes dialog and sets returnValue);
   (7) Top-layer stacking (always above other content).
   
   Support: All modern browsers. Progressive enhancement: check if
   dialog.showModal is a function before calling.

4. WEB COMPONENTS AND SHADOW DOM QUESTIONS
================================================================================

Q16: What are Web Components? What are their three pillars?
A: Web Components are a suite of web platform APIs for creating reusable,
   encapsulated custom HTML elements. Three pillars:
   
   1. Custom Elements — Define new HTML tags with JavaScript class:
      class MyButton extends HTMLElement {
        connectedCallback() { this.innerHTML = '<button>Click me</button>'; }
      }
      customElements.define('my-button', MyButton);
      // Usage: <my-button></my-button>
   
   2. Shadow DOM — Encapsulated DOM subtree; CSS doesn't leak in or out:
      const shadow = element.attachShadow({ mode: 'open' });
   
   3. HTML Templates — Inert, reusable DOM fragments:
      <template id="my-tmpl"><p>Reusable content</p></template>
      const clone = document.importNode(template.content, true);

Q17: What is Shadow DOM and what problem does it solve?
A: Shadow DOM attaches an encapsulated DOM tree to an element that is separate
   from the main document DOM. It creates CSS and DOM encapsulation: styles
   defined inside the shadow root don't leak out, and styles from outside
   don't penetrate in (except CSS custom properties / variables).
   
   this.attachShadow({ mode: 'open' }).innerHTML = `
     <style> button { background: red; } </style>
     <button>Click</button>
   `;
   
   mode: 'open' — accessible via element.shadowRoot
   mode: 'closed' — shadowRoot returns null (not accessible externally)
   
   Solves: CSS conflicts in large applications, third-party widget isolation,
   DOM structure encapsulation. Used by: <video>, <input type="date">,
   <details> — native elements use shadow DOM internally.

Q18: What are custom element lifecycle callbacks?
A: Custom element lifecycle callbacks are methods that fire at defined
   moments:
   
   constructor() — instance created; minimal init only (no DOM manipulation,
   no attributes access)
   
   connectedCallback() — element added to DOM; do setup here (event listeners,
   rendering, resource fetching)
   
   disconnectedCallback() — element removed from DOM; clean up here (remove
   listeners, cancel fetches, clear timers)
   
   attributeChangedCallback(name, oldValue, newValue) — observed attribute
   changed; requires static get observedAttributes() { return ['attr-name']; }
   
   adoptedCallback() — element moved to a different document (rare; iframes)
   
   formAssociatedCallback / formResetCallback — for form-associated custom
   elements using ElementInternals (participate in form submission, validation).

5. RENDERING AND BROWSER BEHAVIOR QUESTIONS
================================================================================

Q19: What is the difference between the DOM and CSSOM?
A: DOM (Document Object Model) — the browser's in-memory tree representation
   of HTML structure. Built by the HTML parser as HTML is processed. JavaScript
   manipulates the DOM via document APIs. The DOM is the living document object.
   
   CSSOM (CSS Object Model) — the browser's tree representation of all CSS
   rules applicable to the page. Built by the CSS parser from stylesheets.
   Combined with the DOM to create the Render Tree (only visible nodes).
   
   The Render Tree drives Layout (calculating positions/sizes) and Painting.
   Both DOM and CSSOM must be complete before the browser renders content —
   this is why CSS in <head> is a render blocker and why JavaScript that
   modifies the DOM can cause reflows (layout recalculation) and repaints.

Q20: What is reflow and repaint, and how do you minimize them?
A: Reflow (layout) — browser recalculates element sizes and positions.
   Triggered by: changing element size, font, adding/removing elements,
   reading offsetWidth/scrollTop (forced synchronous layout).
   
   Repaint — browser re-draws pixels without recalculating layout.
   Triggered by: color changes, visibility, box-shadow, opacity.
   
   Minimizing:
   - Batch DOM reads and writes (read all before writing all)
   - Use CSS transforms/opacity for animations (GPU-composited, no reflow)
   - Use DocumentFragment to build structures before appending
   - Debounce/throttle scroll and resize handlers
   - Avoid reading layout properties in loops
   - Use will-change CSS hint to promote to separate compositor layer
   - Use requestAnimationFrame for visual updates
   - Avoid inline styles (causes per-property reflows)

Q21: What is the difference between DOMContentLoaded and load events?
A: DOMContentLoaded fires when the HTML has been fully parsed and the DOM is
   ready — external stylesheets, images, and iframes may not have loaded yet.
   It fires faster. Use for: DOM manipulation, event binding, anything that
   only needs the DOM tree.
   
   load fires when the page AND all dependent resources (images, stylesheets,
   scripts, iframes) have fully loaded. Use for: operations requiring image
   dimensions, operations that depend on all resources being ready.
   
   document.addEventListener('DOMContentLoaded', () => { /* DOM ready */ });
   window.addEventListener('load', () => { /* Everything loaded */ });
   
   Note: Scripts with async attribute don't block DOMContentLoaded.
   Deferred scripts do delay DOMContentLoaded until they execute.

Q22: How does browser caching work with HTML resources?
A: Browsers cache resources based on HTTP headers:
   Cache-Control: max-age=31536000, immutable — cache for 1 year (for
   fingerprinted assets like bundle.abc123.js)
   Cache-Control: no-cache — revalidate with server before using
   Cache-Control: no-store — don't cache at all
   ETag / Last-Modified — conditional request headers for revalidation
   
   HTML files should typically have short cache or no-cache since they
   reference fingerprinted assets. The common strategy: HTML → Cache-Control:
   no-cache (so users get latest HTML); JS/CSS/images → long cache
   (content hash in filename ensures cache busting when content changes).

Q23: What is the Critical Rendering Path?
A: The Critical Rendering Path (CRP) is the sequence of steps the browser
   performs to convert HTML, CSS, and JavaScript into pixels on screen:
   
   1. Receive HTML bytes → parse characters → tokens → nodes → DOM tree
   2. Encounter CSS link → fetch → parse → CSSOM tree
   3. Encounter script → potentially block → execute (if not deferred/async)
   4. DOM + CSSOM → Render Tree (visible nodes + computed styles)
   5. Layout — compute geometry (size, position) of each node
   6. Paint — fill pixels (text, colors, images, borders)
   7. Composite — layers combined and drawn to screen
   
   Optimization: minimize critical resources (count), minimize critical bytes
   (size), minimize critical path length (roundtrips/blocking). CSS and
   render-blocking JS extend the CRP.

Q24: What is the difference between document modes (standards vs quirks)?
A: Standards mode — browser renders according to current HTML/CSS specifications.
   Activated by <!DOCTYPE html>.
   
   Quirks mode — browser emulates bugs in Internet Explorer 5 and early
   Netscape for legacy compatibility. No DOCTYPE triggers quirks mode.
   Almost-standards mode — triggered by some legacy doctypes.
   
   Differences in quirks mode: box model includes padding and border in
   element width (IE5 box model), table cell fonts inherit differently, images
   inside tables behave differently, many CSS quirks. Modern development:
   always use <!DOCTYPE html> as the very first line to guarantee standards mode.

Q25: What are HTML parsing error recovery rules?
A: HTML5 defines specific error recovery algorithms — unlike XML (which throws
   errors on malformed markup), HTML parsers have explicit rules for handling
   invalid HTML. Examples: unclosed tags are auto-closed when a parent closes;
   unknown elements are parsed as generic containers; misnested tags are
   corrected; duplicate IDs are allowed (though invalid); missing required
   elements (<html>, <head>, <body>) are implied. This is why malformed HTML
   often "works" visually but can produce unexpected DOM structure,
   accessibility issues, and JavaScript bugs (querySelector finding elements
   in unexpected places). Use validators (validator.w3.org) to catch issues
   that browsers silently "fix" in potentially unexpected ways.
