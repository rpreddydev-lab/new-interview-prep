1. SEMANTIC ELEMENT USAGE QUESTIONS
================================================================================

Q1: What is semantic HTML and why does it matter?
A: Semantic HTML means using elements that accurately describe the meaning and
   purpose of content, not just its visual appearance. <nav> vs <div class="nav">,
   <h2> vs <div class="title">, <strong> vs <b class="bold">. It matters for:
   accessibility (screen readers use semantics to create navigation and
   understanding), SEO (search engines weight content by element type), code
   readability (self-documenting structure), browser features (<details> is
   a native accordion, <dialog> is a native modal), and standards compliance.
   The W3C WCAG accessibility standard is largely built around proper semantics.

Q2: When should you use <article> vs <section> vs <div>?
A: <article> — self-contained content that makes sense if extracted and
   redistributed: blog post, news item, comment, product card, tweet.
   <section> — thematic grouping of content that is part of a larger whole:
   book chapters, sections of a long article, a group of related features.
   Sections should have headings. <div> — generic grouping with no semantic
   meaning; use only when no other element applies (layout containers, styling
   hooks). Rule of thumb: ask "would this content make sense on its own, away
   from the page context?" → article. "Is this a distinct part of the current
   document?" → section. "Is this purely a styling/layout container?" → div.

Q3: What is the difference between <header> and <head>?
A: <head> is an HTML structural element containing machine-readable metadata
   about the document (not rendered): <title>, <meta>, <link>, <script>.
   <header> is a semantic landmark element within <body> representing
   introductory content for its nearest sectioning element (<body>, <article>,
   <section>). A page can have multiple <header> elements: one for the site
   header, one inside each <article> as the article header. <head> is singular
   per document. Common interview mistake: confusing the two because they sound
   similar.

Q4: What is the <main> element and how should it be used?
A: <main> represents the primary, unique content of a page — content that
   is not repeated across pages (not navigation, header, footer, sidebar).
   There must be only one <main> per page (though additional ones can exist
   if hidden). Screen readers provide a shortcut to jump to <main>, making
   it important for accessibility (related to WCAG 2.4.1 Bypass Blocks).
   It should not be nested inside <article>, <aside>, <header>, <footer>,
   or <nav>. Typically placed as a direct child of <body>.

Q5: When should you use <figure> and <figcaption>?
A: <figure> represents self-contained content that is referenced from the
   main flow but could be moved elsewhere without affecting the flow: images,
   diagrams, code examples, charts, tables with captions, audio/video with
   descriptions. <figcaption> provides a caption for the figure — it must be
   the first or last child of <figure>. Use <figure>/<figcaption> when the
   caption is semantically associated with the media. Example:
   <figure>
     <img src="chart.png" alt="Revenue grew 35% in 2023">
     <figcaption>Fig. 1: Annual revenue growth, 2019–2023</figcaption>
   </figure>
   This creates a semantic association vs placing caption text in a <p> nearby.

Q6: What is the <aside> element and when is it appropriate?
A: <aside> represents content that is tangentially related to the surrounding
   content — content that could be considered separate from the main content.
   Examples: sidebars, pull quotes, advertising, author bios, glossary items,
   related links sections, supplementary navigation. In an <article>, an
   <aside> might contain author info or related readings. As a direct child
   of <body>, it's the page sidebar. Incorrect use: wrapping all secondary
   column content in <aside> when that content is actually part of the main
   content flow. The key test: "Would removing this content make the main
   content less meaningful?" If yes → not aside.

Q7: What is the <time> element and what is the datetime attribute?
A: <time> semantically identifies time-related content: specific times, dates,
   durations, or date ranges. The optional datetime attribute provides a
   machine-readable format that browsers and search engines can parse, while
   the element's text content can be written in human-friendly format:
   <time datetime="2024-03-15">March 15, 2024</time>
   <time datetime="2024-03-15T09:00">9am on March 15</time>
   <time datetime="P30D">30 days</time>  (duration)
   Benefits: search engines extract dates for rich snippets, calendar apps
   can extract event times, screen readers may announce dates formatted
   for the user's locale.

2. HEADING AND STRUCTURE QUESTIONS
================================================================================

Q8: What are the rules for using headings (h1–h6)?
A: There should be one <h1> per page representing the main topic (some
   accessibility experts say multiple h1s are acceptable within landmark
   regions, but one per page is the safer convention). Headings must NOT
   skip levels downward: after <h1>, only <h2> should follow directly
   (not <h3> or lower). However, you can "close" sections and jump up
   (going from <h3> back to <h2> is fine). Headings should describe
   content hierarchy, not be used for visual styling. Screen reader users
   (65% according to WebAIM surveys) navigate pages by headings — a logical
   hierarchy is critical for usability. Use heading tags for structure;
   use CSS for visual sizing.

Q9: What is the document outline algorithm and why was it controversial?
A: HTML5 originally introduced an "outline algorithm" where heading levels
   could reset within each sectioning element (<article>, <section>, etc.)
   — meaning every section could start with <h1> and browsers would compute
   relative hierarchy. However, no browser ever implemented the outline
   algorithm in their accessibility APIs, so screen readers still use the
   literal heading levels (h1-h6). This was a significant spec/implementation
   gap. WHATWG removed the outline algorithm concept from the spec in 2022.
   The practical takeaway: always use meaningful heading levels (h1 through
   h6) relative to the whole page, regardless of sectioning element context.

Q10: Can a <p> element contain a <div>?
A: No. <p> (paragraph) is phrasing content and cannot contain flow elements
   like <div>, <h1>, <ul>, <table>, <section>. Including a <div> inside a <p>
   causes browsers to auto-close the <p> before the <div>, creating unexpected
   structure. The HTML parsing spec defines which elements can contain which
   content categories. <p> can contain phrasing content (inline elements):
   <span>, <a>, <strong>, <em>, <img>, <button>. If you need a block container
   inside a paragraph-like structure, use <div> or another appropriate block element.
   Validators and linters catch this error.

Q11: What is the <blockquote> element and when should it be used?
A: <blockquote> represents content quoted from another source. It should be
   used only for actual quotations from external sources, not for visual
   indentation (use CSS for layout indentation). The cite attribute or a
   nested <footer>/<cite> element should attribute the source:
   <blockquote cite="https://example.com/article">
     <p>"The best way to predict the future is to invent it."</p>
     <footer>— <cite>Alan Kay</cite></footer>
   </blockquote>
   For inline quotations: <q> with cite attribute. Difference: <blockquote>
   renders as block-level; <q> is inline and browsers automatically add
   quotation marks. Both have semantic meaning for indexers and AT.

3. LISTS AND TABLE QUESTIONS
================================================================================

Q12: When should you use <ul> vs <ol>?
A: Use <ol> (ordered list) when sequence matters and changing the order
   would change the meaning: steps in instructions, ranking, algorithm
   steps, legal numbered clauses. Use <ul> (unordered list) when items
   have no meaningful sequence: navigation menus, tag lists, feature lists,
   ingredient lists. Choosing correctly communicates meaning to screen
   readers (which announce "list of 5 items" for both but readers expect
   numeric context from ordered lists) and search engines. The <li> value
   attribute on ordered lists sets the number for that item. reversed attribute
   counts down. start="5" begins numbering at 5.

Q13: What is a definition list (<dl>) and when is it used?
A: <dl> represents a description list — a set of term-description pairs.
   <dt> is the term (description term), <dd> is the description/definition.
   Multiple <dt> can share one <dd> and vice versa. Appropriate uses: glossary
   terms and definitions, metadata (Author: John Smith), FAQ (question/answer),
   dictionary entries. Example:
   <dl>
     <dt>HTML</dt>
     <dd>HyperText Markup Language, the standard markup for web pages</dd>
     <dt>CSS</dt>
     <dd>Cascading Style Sheets, used for styling web pages</dd>
   </dl>
   Screen readers announce: "HTML, term. HyperText Markup Language..., definition."

Q14: How do you make a data table accessible?
A: Full accessible table structure:
   1. Use <caption> to provide a table title/description
   2. Use <thead>, <tbody>, <tfoot> for structural grouping
   3. Use <th> with scope="col" for column headers
   4. Use <th> with scope="row" for row headers
   5. For complex tables (multi-level headers): use id/headers attributes
   6. Don't use tables for layout — only for tabular data
   
   Screen readers announce table dimensions ("Table with 4 columns") and
   associate header cells with data cells. Without <th> elements, users hear
   raw data with no column/row context.

Q15: What is the difference between <th> and <td>?
A: <th> is a header cell — it labels a row or column. It has implicit
   role="columnheader" or "rowheader". Browsers render it bold and centered
   by default. The scope attribute declares its scope: scope="col" (labels
   its column), scope="row" (labels its row), scope="colgroup" (labels
   multiple columns), scope="rowgroup" (labels multiple rows).
   <td> is a data cell — regular table data. Screen readers associate data
   cells with their headers using scope or id/headers. Without proper <th>
   and scope, table navigation becomes meaningless for screen reader users
   who hear "12500" with no idea what column or row that belongs to.

4. NAVIGATION AND LANDMARK QUESTIONS
================================================================================

Q16: What are HTML5 landmark elements and why do they matter?
A: Landmark elements define the major navigational regions of a page:
   <header> (banner), <nav> (navigation), <main> (main), <aside>
   (complementary), <footer> (contentinfo), <section> with name (region),
   <form> with name (form), <search> (search). Screen reader users can
   jump between landmarks using single keystrokes (D in NVDA, R in JAWS),
   rather than reading the entire page sequentially. This corresponds to
   ARIA landmark roles. Multiple same-type landmarks need aria-label to
   distinguish them: <nav aria-label="Primary"> vs <nav aria-label="Breadcrumb">.

Q17: How should navigation (<nav>) be structured?
A: <nav> should wrap the primary navigational links. A page can have multiple
   <nav> elements — label each distinctly with aria-label:
   <nav aria-label="Primary">…</nav>
   <nav aria-label="Breadcrumb">…</nav>
   <nav aria-label="Footer">…</nav>
   Inside <nav>, links are typically in a list (<ul><li><a>) — this allows
   screen readers to announce "list of N items" giving users count context.
   Not every group of links needs <nav> — use it for major navigation blocks.
   Active page should have aria-current="page" on the current link.

Q18: What is the <details> and <summary> element?
A: <details> is a native disclosure widget — a collapsible section. <summary>
   is the visible heading/trigger (must be the first child). Clicking <summary>
   toggles the <details> open and closed via the open boolean attribute.
   No JavaScript required for basic functionality.
   <details>
     <summary>Show more</summary>
     <p>Additional content here...</p>
   </details>
   The open attribute can be set programmatically. A toggle event fires on
   state changes. Use for FAQs, optional supplementary details, advanced
   configuration. Limitation: styling the animation requires CSS transitions
   on max-height or the newer @starting-style approach. Screen readers
   announce the summary and state (expanded/collapsed).

Q19: When would you use <address>?
A: <address> provides contact information for the nearest <article> or body
   ancestor — author contact info, not general postal addresses. Placed inside
   an <article>, it's the article author's contact info. Placed in the page
   <footer>, it's the organization's contact. Appropriate content: email,
   phone, social media links, physical address if it's contact info.
   Not appropriate: arbitrary addresses in body text (use <p> for those),
   non-contact postal addresses. Example:
   <address>
     Contact us at <a href="mailto:info@example.com">info@example.com</a>
     or call <a href="tel:+15551234567">+1 (555) 123-4567</a>
   </address>

5. SEMANTIC VS NON-SEMANTIC TRADEOFFS
================================================================================

Q20: When is it acceptable to use <div> and <span>?
A: <div> is acceptable when: no other semantic element fits (pure layout
   container, styling wrapper), you need a grouping element for CSS grid/flex
   children, or a JavaScript mount point. <span> is acceptable as an inline
   styling/scripting hook with no semantic meaning needed. Signs you should
   use something else: the content is a list → <ul>/<ol>/<dl>; it's navigation
   → <nav>; it's a form → <form>; it's a primary content region → <main>;
   it's an interactive control → <button>, <a>, <input>; it's a section with
   a title → <section>. <div> and <span> are not "wrong" — they're the right
   tools for genuinely semantic-free groupings.

Q21: What is the difference between <b>, <strong>, <i>, <em>?
A: <strong> — strong importance; content is critically important; screen
   readers may change emphasis. <b> — stylistically bold without importance;
   product names, keywords, first sentence. <em> — emphasis that changes
   sentence meaning (e.g., "I never said he stole it" vs "I never SAID
   he stole it"); screen readers may stress. <i> — idiomatic text, technical
   terms, foreign phrases, thoughts — no semantic emphasis, just a different
   voice. All four render visually as bold or italic by default. Use <strong>/<em>
   when semantic meaning matters; use <b>/<i> for purely stylistic distinction
   with no change in importance; use CSS for purely visual effects.

Q22: Should you use <br> for spacing? Why or why not?
A: <br> should only be used for line breaks that are semantically meaningful —
   where the line break is part of the content: poetry, song lyrics, postal
   addresses (each line is significant). It should NOT be used for visual
   spacing between elements (multiple <br><br> as spacers). Use CSS margin,
   padding, or layout for visual spacing. Using <br> for layout creates
   accessibility issues (screen readers announce "blank" for each empty line)
   and maintenance issues (spacing is now in HTML, not CSS). Similarly, &nbsp;
   should be used only for non-breaking space that prevents unwanted wrapping,
   not for indentation or spacing.

Q23: What is the <abbr> element and how should it be used?
A: <abbr> marks up abbreviations and acronyms with their full expansion in
   the title attribute. The full meaning is announced to screen readers and
   shown as a tooltip on hover.
   <abbr title="World Wide Web Consortium">W3C</abbr>
   Best practices: use <abbr> on first occurrence of an abbreviation on a page;
   subsequent uses don't need it. The title creates a tooltip but is not
   accessible on touch devices or keyboard — for important expansions, also
   write the full form in the surrounding text on first use. Screen reader
   support varies — NVDA reads the title attribute, others may not. The
   dashed underline styling should be preserved (some resets remove it).

Q24: What is the <mark> element for?
A: <mark> represents text highlighted for reference or notation in context —
   specifically text highlighted because of its relevance to a current search
   or user action. Examples: search results with the query terms highlighted,
   text selected for comparison, code references. It renders with a yellow
   background by default. Semantically different from <strong> (importance)
   or <em> (emphasis) — <mark> means "relevant in this context". Screen
   readers don't typically announce <mark> specially, so if the highlight
   is meaningful for AT users, supplement with visually hidden text:
   <mark><span class="sr-only">Highlight start: </span>keyword<span class="sr-only"> :highlight end</span></mark>

Q25: What are void elements? List five examples and explain their behavior.
A: Void elements are HTML elements that cannot have children — they have no
   content and no closing tag. They consist of a single open tag.
   In HTML5, the trailing slash is optional: <br> and <br /> are both valid.
   
   Five examples:
   <br>    — Line break (semantic line break in poetry/addresses)
   <hr>    — Horizontal rule — thematic break between content
   <img>   — Image (src, alt are required attributes)
   <input> — Form input control
   <meta>  — Metadata (charset, viewport, description, og tags)
   
   Others: <link>, <area>, <base>, <col>, <embed>, <param>, <source>, <track>, <wbr>
   
   Important: <script>, <div>, <p>, <span> are NOT void — they require closing
   tags. Forgetting to close non-void elements causes browser auto-recovery
   that can produce unexpected DOM structure and styling bugs.
