REST = REpresentational State Transfer (Fielding, 2000)

Core constraints:
  1. Client-Server        – UI and data logic separated
  2. Stateless            – Each request has all context (no server-side session)
  3. Cacheable            – Responses labeled cacheable or not
  4. Uniform Interface    – Consistent URLs, HTTP verbs, representations
  5. Layered System       – Client need not know about intermediaries
  6. Code on Demand (opt) – Server can return executable code

  2. URI DESIGN GUIDELINES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rules:
  ✅ Nouns (resources), NOT verbs
  ✅ Plural resource names: /users, /orders, /products
  ✅ Lowercase, hyphen-separated: /product-categories
  ✅ Hierarchy for sub-resources: /users/{userId}/orders
  ✅ No trailing slash: /users (not /users/)
  ✅ Use query params for filtering/sorting/pagination: ?status=active&sort=name
  ❌ /getUsers         – verb in URI
  ❌ /UserList         – uppercase, singular
  ❌ /users/getById/5  – verb again

  Examples:
    GET    /users              → list all users
    GET    /users/{id}         → get single user
    POST   /users              → create a user
    PUT    /users/{id}         → full update
    PATCH  /users/{id}         → partial update
    DELETE /users/{id}         → delete
    GET    /users/{id}/orders  → orders for a user

  3. HTTP METHODS — CORRECT USAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Method  | Safe | Idempotent | Purpose
  ────────┼──────┼────────────┼────────────────────────────────
  GET     | Yes  | Yes        | Retrieve resource
  HEAD    | Yes  | Yes        | Like GET but no body
  POST    | No   | No         | Create resource, trigger action
  PUT     | No   | Yes        | Full replacement of resource
  PATCH   | No   | No*        | Partial update
  DELETE  | No   | Yes        | Remove resource
  OPTIONS | Yes  | Yes        | Get supported methods (CORS preflight)

  * PATCH idempotency depends on implementation.

  Safe    = does not modify server state
  Idempotent = calling N times has same effect as calling once

  4. HTTP STATUS CODES — BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  2xx — Success
    200 OK            – GET, PUT, PATCH (returns body)
    201 Created       – POST (returns new resource + Location header)
    204 No Content    – DELETE, PUT/PATCH when no body returned
    202 Accepted      – Async processing started (will complete later)

  3xx — Redirection
    301 Moved Permanently
    304 Not Modified  – conditional GET, caching

  4xx — Client errors
    400 Bad Request   – validation failure, malformed request
    401 Unauthorized  – missing/invalid authentication
    403 Forbidden     – authenticated but not authorized
    404 Not Found     – resource doesn't exist
    405 Method Not Allowed
    409 Conflict      – duplicate / optimistic lock failure
    410 Gone          – resource permanently deleted
    422 Unprocessable Entity – semantic validation error
    429 Too Many Requests    – rate limiting

  5xx — Server errors
    500 Internal Server Error
    502 Bad Gateway
    503 Service Unavailable  – overload / maintenance
    504 Gateway Timeout

  Spring ResponseEntity usage:
    return ResponseEntity.status(HttpStatus.CREATED)
                         .location(URI.create("/users/" + user.getId()))
                         .body(user);

    return ResponseEntity.noContent().build();            // 204
    return ResponseEntity.notFound().build();             // 404

  5. REQUEST & RESPONSE DESIGN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5.1 Use DTOs, not Entities directly
  • Entities expose DB structure; DTOs expose API contract.
  • Never serialize JPA entities with lazy collections — N+1 & stack overflow.
  • Use MapStruct or ModelMapper for conversion.

  @RestController
  @RequestMapping("/api/v1/users")
  public class UserController {

      @GetMapping("/{id}")
      public ResponseEntity<UserResponseDto> getUser(@PathVariable Long id) {
          User user = userService.findById(id);
          return ResponseEntity.ok(userMapper.toDto(user));
      }

      @PostMapping
      public ResponseEntity<UserResponseDto> createUser(
              @RequestBody @Valid CreateUserRequest request) {
          User user = userService.create(request);
          URI location = ServletUriComponentsBuilder
                  .fromCurrentRequest()
                  .path("/{id}")
                  .buildAndExpand(user.getId())
                  .toUri();
          return ResponseEntity.created(location).body(userMapper.toDto(user));
      }
  }

  {

  6. API VERSIONING STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Strategy          | Example                              | Pros / Cons
  ──────────────────┼──────────────────────────────────────┼───────────────────────
  URI versioning    | /api/v1/users, /api/v2/users          | Simple, visible; URL pollution
  Header versioning | X-API-Version: 2                      | Clean URLs; harder to test
  Query param       | /api/users?version=2                  | Easy; not RESTful
  Accept header     | Accept: application/vnd.myapi.v2+json | Purist; verbose

  URI versioning (most common in practice):
    @RequestMapping("/api/v1")
    public class UserV1Controller { ... }

    @RequestMapping("/api/v2")
    public class UserV2Controller { ... }

  8. HATEOAS (Hypermedia As The Engine Of Application State)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Adds navigation links to responses. Dependency:
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-hateoas</artifactId>
    </dependency>

  @GetMapping("/{id}")
  public EntityModel<UserDto> getUser(@PathVariable Long id) {
      UserDto dto = userService.findDtoById(id);
      return EntityModel.of(dto,
          linkTo(methodOn(UserController.class).getUser(id)).withSelfRel(),
          linkTo(methodOn(UserController.class).getOrders(id)).withRel("orders")
      );
  }

  Response:
    {
      "id": 1, "name": "Alice",
      "_links": {
        "self":   { "href": "/api/v1/users/1" },
        "orders": { "href": "/api/v1/users/1/orders" }
      }
    }

  9. IDEMPOTENCY KEYS FOR SAFE RETRIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Problem: Client retries a POST (e.g., payment); creates duplicate.
  Solution: Client sends Idempotency-Key header; server caches response.

  POST /api/v1/payments
  Idempotency-Key: client-uuid-here

  Server:
    1. Check if idempotency key seen before (Redis / DB).
    2. If yes → return cached response.
    3. If no  → process, store key + response, return response.

  10. CACHING HEADERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Cache-Control: max-age=3600, public     – cache for 1 hour
  Cache-Control: no-cache                 – revalidate every time
  Cache-Control: no-store                 – never cache (sensitive data)
  ETag: "abc123"                          – resource version identifier
  Last-Modified: Tue, 15 Jan 2024 10:00:00 GMT

  Spring implementation:
    @GetMapping("/{id}")
    public ResponseEntity<UserDto> getUser(@PathVariable Long id,
                                           WebRequest webRequest) {
        User user = userService.findById(id);
        String etag = "\"" + user.getVersion() + "\"";
        if (webRequest.checkNotModified(etag)) {
            return null; // 304 Not Modified
        }
        return ResponseEntity.ok()
                .eTag(etag)
                .cacheControl(CacheControl.maxAge(1, TimeUnit.HOURS))
                .body(userMapper.toDto(user));
    }

  11. SECURITY BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  • Always use HTTPS in production.
  • Implement authentication (JWT, OAuth2).
  • Authorize at both endpoint and method level.
  • Never expose internal IDs if sequential — use UUIDs.
  • Validate all input (JSR-380 @Valid).
  • Use CORS with explicit allowed origins (not "*" in prod).
  • Apply rate limiting per user/IP.
  • Set proper security headers:
      X-Content-Type-Options: nosniff
      X-Frame-Options: DENY
      Strict-Transport-Security: max-age=31536000
  • Log all security events (failed auth, 403s) with traceId.
  • Avoid verbose error messages exposing stack traces.

  13. INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the difference between PUT and PATCH?
  A: PUT replaces the entire resource; if you omit a field, it gets
     nulled out. PATCH applies a partial update—only provided fields
     change. PUT is idempotent; PATCH can be idempotent depending on
     implementation.

Q2: When should you use 201 vs 200 for a POST?
  A: 201 Created when a new resource is created. Include a Location
     header pointing to the new resource URI. 200 OK when POST is
     used as an action (e.g., /login, /calculate) that doesn't create
     a persistent resource.

Q3: What is idempotency and why is it important?
  A: An operation is idempotent if applying it multiple times has the
     same effect as applying it once. GET, PUT, DELETE are idempotent.
     POST is not. Idempotency is important for safe retry logic in
     distributed systems—e.g., if a network failure causes the client
     to retry, an idempotent PUT won't duplicate data.

Q4: How do you implement API versioning?
  A: Most common: URI versioning (/api/v1/, /api/v2/). Use it when
     breaking changes are needed. Keep v1 available for backward
     compatibility for a deprecation period. Announce deprecation via
     Sunset / Deprecation headers.

Q5: How do you handle large collections — pagination?
  A: Use Pageable with Spring Data; bind page, size, sort from query
     params. Return Page<T> which includes metadata. Cap max page size
     to prevent abuse. Use cursor-based pagination for very large,
     real-time datasets.

Q6: What is HATEOAS and when do you use it?
  A: HATEOAS embeds navigation links in responses so clients can
     discover next actions without hard-coding URLs. Useful for
     public APIs or hypermedia-driven UIs. In internal microservice
     APIs it's often skipped for simplicity.

Q7: Should you expose JPA entities directly in REST responses?
  A: No. Entities are coupled to DB schema, may have lazy collections
     (Jackson serialization error), bidirectional relationships (infinite
     recursion), and expose unnecessary data. Always map to DTOs.

Q8: How do you implement optimistic locking in a REST API?
  A: Use ETag header. Server returns ETag: "version-hash". Client
     sends If-Match: "version-hash" with PUT/PATCH. Server checks
     version; if changed → 412 Precondition Failed. This prevents
     lost updates.

Q9: What HTTP status code for rate limiting?
  A: 429 Too Many Requests. Include Retry-After header indicating
     when the client may try again.

Q10: How do you make a DELETE endpoint idempotent?
  A: Return 204 No Content even if the resource doesn't exist (or
     was already deleted). Some argue 404 is also acceptable; the
     key is that subsequent identical DELETEs don't cause errors.
