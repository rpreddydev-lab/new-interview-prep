  1. JPA FUNDAMENTALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JPA = Java Persistence API (specification, now Jakarta Persistence)
Hibernate = most popular JPA implementation (provider)

JPA defines:
  - Entity lifecycle
  - EntityManager API
  - JPQL (Java Persistence Query Language)
  - Persistence context (first-level cache)
  - Cascade types and fetch strategies

  2. ENTITY BASICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
@Table(name = "products",
       uniqueConstraints = @UniqueConstraint(columnNames = "sku"))
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "product_name", nullable = false, length = 200)
    private String name;

    @Column(precision = 10, scale = 2)
    private BigDecimal price;

    @Enumerated(EnumType.STRING)    // Store enum as string in DB
    private Category category;

    @Column(name = "created_at", updatable = false)
    private LocalDateTime createdAt;

    @Version                         // Optimistic locking
    private Long version;

    // Getters, setters, equals, hashCode...
}

GenerationType strategies:
  IDENTITY    → auto-increment column (MySQL, PostgreSQL SERIAL)
  SEQUENCE    → DB sequence object (preferred for PostgreSQL)
  TABLE       → sequence table (portable, slow)
  AUTO        → Hibernate picks best strategy for the DB
  UUID        → UUID primary key (Hibernate 6+)

  3. ENTITY LIFECYCLE STATES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  TRANSIENT ──► MANAGED ──► DETACHED ──► REMOVED
     new()      persist()    detach()     remove()
                             close()
                             serialize()

  TRANSIENT  → new Java object, no PK, not tracked by EntityManager
  MANAGED    → tracked by persistence context; changes auto-synced
  DETACHED   → was managed, but EM is closed or explicitly detached;
               changes NOT tracked; re-attach with merge()
  REMOVED    → scheduled for DELETE on flush/commit

  EntityManager API (lower-level, used internally by Spring Data):
    em.persist(entity)    → TRANSIENT → MANAGED (INSERT on commit)
    em.merge(entity)      → DETACHED  → MANAGED (UPDATE on commit)
    em.remove(entity)     → MANAGED   → REMOVED (DELETE on commit)
    em.find(Class, id)    → returns MANAGED entity (or null)
    em.detach(entity)     → MANAGED → DETACHED
    em.flush()            → sync persistence context to DB immediately
    em.clear()            → evict all entities from 1st-level cache

  4. JpaRepository METHOD REFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

public interface ProductRepository extends JpaRepository<Product, Long> {}

CrudRepository methods:
  save(entity)                   → INSERT or UPDATE (based on ID presence)
  saveAll(Iterable)              → batch save
  findById(id)                   → Optional<T>
  existsById(id)                 → boolean
  findAll()                      → List<T>
  findAllById(Iterable<ID>)      → List<T>
  count()                        → long
  deleteById(id)                 → void
  delete(entity)                 → void
  deleteAll()                    → void

JpaRepository extras:
  getReferenceById(id)           → lazy proxy (no SELECT unless accessed)
  findAll(Sort)                  → sorted list
  findAll(Pageable)              → Page<T>
  flush()                        → immediate sync to DB
  saveAndFlush(entity)           → save + flush
  saveAllAndFlush(Iterable)      → batch save + flush
  deleteInBatch(Iterable)        → single DELETE...IN query (no events)
  deleteAllInBatch()             → DELETE FROM table (fastest)

  ⚠️  deleteInBatch skips @PreRemove lifecycle callbacks and
      cascades — use with care.

  5. ENTITY LIFECYCLE CALLBACKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
public class Order {
    @PrePersist
    private void prePersist() { this.createdAt = LocalDateTime.now(); }

    @PostPersist
    private void postPersist() { System.out.println("Inserted: " + id); }

    @PreUpdate
    private void preUpdate() { this.updatedAt = LocalDateTime.now(); }

    @PostUpdate
    private void postUpdate() {}

    @PreRemove
    private void preRemove() { /* cleanup */ }

    @PostRemove
    private void postRemove() {}

    @PostLoad
    private void postLoad() { /* after SELECT */ }
}

Or use an EntityListener class (separates concern):
  @EntityListeners(AuditingEntityListener.class)

  6. EQUALS AND HASHCODE — BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IMPORTANT: Never base equals/hashCode on mutable state or
auto-generated IDs for new (transient) entities.

Recommended approaches:
  a) Business key (natural key — e.g., SKU, email):
     @Override
     public boolean equals(Object o) {
         if (this == o) return true;
         if (!(o instanceof Product p)) return false;
         return Objects.equals(sku, p.sku);
     }
     @Override
     public int hashCode() { return Objects.hash(sku); }

  b) UUID as natural key (assigned before persist):
     @Id private UUID id = UUID.randomUUID();

  c) Avoid: equals/hashCode based on auto-generated Long id
     → New entity has id=null, breaks Set/Map behavior

  7. @Embedded AND @Embeddable
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Value objects that live in the same table as the owner entity:

@Embeddable
public class Address {
    private String street;
    private String city;
    private String zipCode;
}

@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @Embedded
    @AttributeOverrides({
        @AttributeOverride(name = "street",  column = @Column(name = "home_street")),
        @AttributeOverride(name = "city",    column = @Column(name = "home_city")),
        @AttributeOverride(name = "zipCode", column = @Column(name = "home_zip"))
    })
    private Address homeAddress;

    @Embedded
    @AttributeOverrides({
        @AttributeOverride(name = "street",  column = @Column(name = "work_street")),
        @AttributeOverride(name = "city",    column = @Column(name = "work_city")),
        @AttributeOverride(name = "zipCode", column = @Column(name = "work_zip"))
    })
    private Address workAddress;
}

  8. OPTIMISTIC LOCKING WITH @Version
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
public class BankAccount {
    @Id @GeneratedValue
    private Long id;

    private BigDecimal balance;

    @Version
    private Long version;   // Hibernate manages this
}

// UPDATE bank_account SET balance=?, version=version+1
//   WHERE id=? AND version=?  ← if rows=0 → OptimisticLockException

When to use:
  - Concurrent reads are common, conflicts are rare
  - No need for DB-level row locking

Pessimistic locking:
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  Optional<BankAccount> findById(Long id);
  → SELECT ... FOR UPDATE

  9. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is a persistence context in JPA?
A: A first-level cache managed by the EntityManager for the
   duration of a transaction. All managed entities are tracked
   here. Repeated findById() in same transaction returns
   the SAME object from cache (no extra SELECT).

Q: What is the difference between save() and saveAndFlush()?
A: save() marks the entity for insert/update and commits on
   transaction end. saveAndFlush() additionally calls flush()
   immediately, pushing SQL to the DB within the same transaction
   (useful when you need the DB to reflect changes for subsequent
   queries in the same transaction).

Q: What is getReferenceById vs findById?
A: findById executes an immediate SELECT and returns Optional<T>.
   getReferenceById returns a Hibernate proxy with only the ID set;
   no SELECT until a non-ID field is accessed. Throws
   EntityNotFoundException if entity doesn't exist when proxy is
   initialized. Useful for setting FK associations without loading
   the full entity.

Q: What is @Version used for?
A: Optimistic locking. Hibernate includes the version column in
   UPDATE WHERE clauses. If another transaction has already updated
   the row (version changed), the update affects 0 rows and
   Hibernate throws OptimisticLockException, preventing lost updates.

Q: What is the difference between @Transient and transient keyword?
A: @Transient (JPA) — tells JPA to not persist this field to DB.
   transient (Java keyword) — tells Java serialization to skip
   the field. They are independent; you may need both.

Q: What are the GeneratedValue strategies?
A: IDENTITY: relies on DB auto-increment column.
   SEQUENCE: uses a DB sequence (more efficient for batch inserts).
   TABLE: dedicated sequence table (portable but slow).
   AUTO: Hibernate selects best strategy for the configured database.
   UUID (Hibernate 6+): generates UUID primary key.
