  1. WHAT IS A TRANSACTION?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A transaction is a unit of work that must be executed
atomically: either ALL operations succeed or NONE are applied.

ACID Properties:
  A — Atomicity     → all-or-nothing
  C — Consistency   → DB stays in valid state
  I — Isolation     → concurrent txns don't interfere
  D — Durability    → committed data survives crashes

Spring provides a unified transaction abstraction over:
  - JPA / Hibernate
  - JDBC (DataSourceTransactionManager)
  - JTA (distributed, XA)
  - R2DBC (reactive)

  2. @Transactional ANNOTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Service
public class OrderService {

    @Transactional              // begins txn before, commits/rollbacks after
    public Order placeOrder(OrderRequest request) {
        Order order = new Order(request);
        orderRepo.save(order);
        inventoryService.reserve(request.getItems());  // same txn
        paymentService.charge(request.getPayment());   // same txn
        return order;
    }

    @Transactional(readOnly = true)  // optimization hint
    public Order findOrder(Long id) {
        return orderRepo.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }
}

readOnly = true:
  - Tells Hibernate to skip dirty checking (no snapshot comparison)
  - Some databases use read replicas for read-only connections
  - Does NOT prevent writes — it is an optimization hint only

  3. TRANSACTION PROPAGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Propagation defines what happens when a @Transactional method
is called from another @Transactional method.

  Propagation        | Behavior
  ───────────────────┼──────────────────────────────────────────────
  REQUIRED (default) | Join existing txn; if none, create new one
  REQUIRES_NEW       | Always create NEW txn; suspend existing one
  SUPPORTS           | Join existing if present; else run without txn
  NOT_SUPPORTED      | Run WITHOUT txn; suspend existing if present
  MANDATORY          | Must have existing txn; throw if none
  NEVER              | Must NOT have a txn; throw if one exists
  NESTED             | Savepoint within existing txn (JDBC only)

Common scenarios:

  // Audit log must ALWAYS be saved even if outer txn fails
  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void logAudit(AuditEvent event) {
      auditRepo.save(event);
  }

  // Email notification — run after main txn commits
  // (Use ApplicationEventPublisher with @TransactionalEventListener)

NESTED vs REQUIRES_NEW:
  REQUIRES_NEW → completely independent txn (different connection)
  NESTED       → savepoint in SAME connection; rollback to savepoint
                 only, outer txn can still commit

  4. TRANSACTION ISOLATION LEVELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Isolation level controls what concurrent transactions can see.

  Level               | Dirty | Non-Rep | Phantom | Performance
                       Read    Read      Read
  ────────────────────┼───────┼─────────┼─────────┼────────────
  READ_UNCOMMITTED    | Yes   | Yes     | Yes     | Fastest
  READ_COMMITTED      | No    | Yes     | Yes     | Fast (default PG/Oracle)
  REPEATABLE_READ     | No    | No      | Yes     | Moderate (default MySQL)
  SERIALIZABLE        | No    | No      | No      | Slowest / most consistent

  Dirty Read     — reading UNCOMMITTED changes from another txn
  Non-Repeatable — reading same row twice, getting different values
                   (another txn committed an UPDATE between reads)
  Phantom Read   — reading same range twice, getting different rows
                   (another txn committed INSERT/DELETE between reads)

Setting isolation:
  @Transactional(isolation = Isolation.REPEATABLE_READ)
  public Order findAndLock(Long id) { ... }

  Spring default: Isolation.DEFAULT (use DB default)

  5. ROLLBACK RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Default: Spring rolls back on unchecked exceptions (RuntimeException
and Error), NOT on checked exceptions.

  @Transactional(rollbackFor = Exception.class)  // rollback on ALL exceptions
  @Transactional(rollbackFor = { IOException.class, SQLException.class })
  @Transactional(noRollbackFor = OptimisticLockException.class)  // don't rollback

Programmatic rollback:
  TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();

  6. HOW @Transactional WORKS — AOP PROXY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring wraps beans annotated with @Transactional in a proxy:

  Caller  →  TransactionInterceptor Proxy  →  Actual Service Bean
                 │ begin txn
                 │─────────────────────────────► method()
                 │◄───────────────────────────── result
                 │ commit / rollback

  Because a proxy intercepts the call, self-invocation DOES NOT work:
    // WRONG — calling this.findById() from within the same class
    // bypasses the proxy → no transaction!
    public void process() {
        this.findById(1L);  // ← no transaction because it's self-call
    }

  Fix options:
    a) Extract to a separate Spring-managed bean
    b) @Autowired self-injection (ugly, avoid)
    c) AopContext.currentProxy() (enable exposeProxy=true)

  @Transactional is only effective when called through the proxy
  (from OUTSIDE the class, via a Spring-managed caller).

  7. @TransactionalEventListener
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Execute logic tied to transaction lifecycle:

  // Publisher (inside @Transactional method)
  applicationEventPublisher.publishEvent(new OrderPlacedEvent(order));

  // Listener — runs AFTER txn commits successfully
  @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
  public void onOrderPlaced(OrderPlacedEvent event) {
      emailService.sendConfirmation(event.getOrder());
  }

  TransactionPhase options:
    AFTER_COMMIT        → default, after successful commit
    AFTER_ROLLBACK      → after rollback
    AFTER_COMPLETION    → after commit or rollback
    BEFORE_COMMIT       → just before commit (still inside txn)

  8. PROGRAMMATIC TRANSACTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use TransactionTemplate for fine-grained control:

@Service
public class PaymentService {
    private final TransactionTemplate txTemplate;

    public PaymentService(PlatformTransactionManager txManager) {
        this.txTemplate = new TransactionTemplate(txManager);
        this.txTemplate.setIsolationLevel(TransactionDefinition.ISOLATION_SERIALIZABLE);
    }

    public PaymentResult processPayment(PaymentRequest req) {
        return txTemplate.execute(status -> {
            try {
                // business logic
                return chargeCard(req);
            } catch (PaymentException ex) {
                status.setRollbackOnly();
                throw ex;
            }
        });
    }
}

  9. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is transaction propagation REQUIRED vs REQUIRES_NEW?
A: REQUIRED joins an existing transaction if present; if none, creates
   a new one. Both the caller and callee share the same transaction —
   a rollback in either affects both.
   REQUIRES_NEW always creates a NEW, independent transaction,
   suspending any existing one. Useful for operations like audit
   logging that must be committed regardless of outer transaction fate.

Q: Why doesn't @Transactional work on private methods?
A: Spring proxies only intercept public method calls coming from
   outside the class. Private methods are not part of the proxy
   interface and self-invocations bypass the proxy entirely.

Q: What is a dirty read? How to prevent it?
A: A dirty read is reading uncommitted data from another transaction
   (which might be rolled back). Prevented by using READ_COMMITTED
   or higher isolation level.

Q: What is the difference between optimistic and pessimistic locking?
A: Optimistic locking (@Version) assumes conflicts are rare; it
   detects conflicts at write time using a version column and throws
   OptimisticLockException if a conflict occurs. No DB lock is held.
   Pessimistic locking (SELECT FOR UPDATE) acquires a DB row lock
   immediately, blocking other writers. Better when conflicts are
   frequent or short-lived.

Q: When does Spring NOT rollback a transaction?
A: By default, Spring only rolls back for RuntimeException and Error,
   NOT for checked exceptions. Use rollbackFor = Exception.class to
   change this behavior.

Q: What is @TransactionalEventListener useful for?
A: Decoupling side effects (send email, notify downstream services)
   from the core transaction, ensuring they run only after the txn
   commits successfully. This avoids sending emails for transactions
   that later roll back.

Q: What problem does NESTED propagation solve vs REQUIRES_NEW?
A: NESTED uses a savepoint in the SAME DB connection. The inner
   operation can be rolled back to the savepoint independently
   without rolling back the outer transaction. REQUIRES_NEW uses a
   completely separate connection/transaction — more isolation but
   more overhead and cannot share the outer connection's locks.
