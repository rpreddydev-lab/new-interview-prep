  1. WHAT IS SPRING BATCH?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Batch is a framework for building high-volume, robust batch processing
jobs for enterprise use cases.

Common batch use cases:
  - Nightly ETL: extract from legacy DB, transform, load to data warehouse
  - File processing: parse millions of CSV/XML records from S3, persist to DB
  - Report generation: aggregate large datasets, export to PDF/Excel
  - Data migration: move records between databases
  - Billing/payroll: process millions of accounts at month-end
  - Notification: send batch emails/SMS to all users

Key features:
  - Chunk-oriented processing (read → process → write in configurable chunks)
  - Restart/resume on failure (job state persisted to a JobRepository)
  - Skip and retry policies for bad records
  - Partitioned processing (parallel processing of partitions)
  - Multi-threaded step execution
  - Flow control (sequential, conditional, parallel steps)

  2. CORE DOMAIN MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JobLauncher
    │
    └── Job  (logical unit of batch work; composed of ordered Steps)
             │
             ├── Step 1 ── Tasklet (simple one-shot operation)
             └── Step 2 ── Chunk-oriented Step
                               │
                               ├── ItemReader    (read one item at a time)
                               ├── ItemProcessor (optional transform)
                               └── ItemWriter    (write chunk of N items)

JobRepository:
  - Persists Job/Step execution state to a database
  - Enables restart from last successful chunk on failure
  - Stores JobParameters, start time, end time, exit status

JobParameters:
  - Key-value pairs that make each JobInstance unique
  - E.g., run.date=2024-01-15 makes each daily run a distinct instance

JobInstance vs JobExecution:
  - JobInstance: one logical run identified by Job + Parameters
  - JobExecution: one actual attempt to run a JobInstance
  - A failed JobInstance can have multiple JobExecutions (retries)

  4. BATCH METADATA TABLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Batch creates the following tables in your DB:

BATCH_JOB_INSTANCE       — unique job instances (Job + Parameters)
BATCH_JOB_EXECUTION      — execution attempts (start, end, status, exit code)
BATCH_JOB_EXECUTION_PARAMS — parameters for each execution
BATCH_STEP_EXECUTION     — step-level statistics (read/write/skip/commit counts)
BATCH_JOB_SEQ            — sequence for job IDs
BATCH_STEP_EXECUTION_SEQ — sequence for step IDs
BATCH_JOB_EXECUTION_SEQ  — sequence for execution IDs

These are auto-created by spring.batch.jdbc.initialize-schema=always.
In production use always use never + manage schema with Flyway/Liquibase.

  5. LAUNCHING JOBS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Service
public class JobLauncherService {

    private final JobLauncher jobLauncher;
    private final Job importOrdersJob;

    public void launch(LocalDate date) throws Exception {
        JobParameters params = new JobParametersBuilder()
            .addLocalDate("run.date", date)       // makes this instance unique per date
            .addLong("timestamp", System.currentTimeMillis())  // force re-run same date
            .toJobParameters();

        JobExecution execution = jobLauncher.run(importOrdersJob, params);
        log.info("Job status: {}", execution.getStatus());
    }
}

// Async launcher (don't block HTTP thread):
@Bean
public JobLauncher asyncJobLauncher(JobRepository jobRepository) throws Exception {
    TaskExecutorJobLauncher launcher = new TaskExecutorJobLauncher();
    launcher.setJobRepository(jobRepository);
    launcher.setTaskExecutor(new SimpleAsyncTaskExecutor());
    launcher.afterPropertiesSet();
    return launcher;
}

Q: What is the difference between a JobInstance and a JobExecution?
A: A JobInstance is a unique logical run of a Job — identified by the Job name
   + JobParameters combination. For a daily import, the date parameter creates
   a new instance each day. A JobExecution is an actual attempt to run that
   JobInstance. If a job fails and is retried, the same JobInstance has multiple
   JobExecutions. A completed JobInstance cannot be re-run.

Q: What is the JobRepository and why is it needed?
A: JobRepository persists all batch metadata (job/step execution state, read/write
   counts, status) to a database. This is what enables restart/resume: if a job
   fails at chunk 500, the next run reads the last committed checkpoint from
   JobRepository and resumes from chunk 501 instead of starting over.

Q: Why set spring.batch.job.enabled=false in production?
A: By default, Spring Batch runs all configured Jobs on application startup.
   In production, you want to control when jobs run (triggered by a scheduler,
   HTTP endpoint, or message). Setting enabled=false prevents automatic startup
   execution, so jobs only run when explicitly launched via JobLauncher.

Q: What are JobParameters used for?
A: JobParameters serve two purposes: (1) They make each JobInstance unique —
   passing run.date=2024-01-15 creates a new instance for that date.
   (2) They pass runtime configuration to the job (file paths, report dates,
   processing windows). Spring Batch uses the parameters hash to detect
   "already completed" instances and prevents re-running them.

Q: How does Spring Batch handle failures and restarts?
A: Spring Batch commits state to the JobRepository at the end of each chunk
   transaction. If the job fails mid-way, the last successful commit position
   is stored. On restart with the same JobParameters, Spring Batch resumes
   from the last committed checkpoint. Skip and retry policies can also handle
   individual bad records without failing the whole job.
