  1. WHY REACTIVE PROGRAMMING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Traditional thread-per-request model (Servlet):
  - Each request occupies a thread while waiting for I/O (DB, API, filesystem)
  - Threads are expensive (~1MB stack each)
  - Under high concurrency with slow I/O, threads pile up → thread pool exhaustion

Reactive programming model:
  - Non-blocking I/O: thread is released while waiting, reused for other work
  - Event-loop model: a small thread pool handles thousands of concurrent requests
  - Backpressure: consumer controls the rate of data production

Ideal for:
  - High-concurrency I/O-bound services (API aggregation, streaming)
  - Long-lived connections (SSE, WebSocket)
  - Services calling multiple downstream APIs in parallel

NOT ideal for:
  - CPU-bound work (computation dominates, reactive adds overhead)
  - Simple CRUD with low concurrency (unnecessary complexity)
  - Teams unfamiliar with async/reactive programming

  2. REACTIVE STREAMS SPECIFICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Reactive Streams is a standard (java.util.concurrent.Flow since Java 9)
defining four interfaces:

  Publisher<T>   — produces data
  Subscriber<T>  — consumes data
  Subscription   — link between Publisher and Subscriber; controls demand
  Processor<T,R> — both Publisher and Subscriber (transformation stage)

Backpressure protocol:
  1. Subscriber calls subscription.request(n) to signal it can handle n items
  2. Publisher emits at most n items
  3. If Subscriber needs more, it calls request(n) again
  4. This prevents fast producers from overwhelming slow consumers

  3. PROJECT REACTOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Project Reactor is Spring's reactive library. Two main types:

  Mono<T>  — 0 or 1 element  (like Optional but asynchronous)
  Flux<T>  — 0 to N elements (like Stream but asynchronous + backpressure)

Key property: Reactor types are LAZY (nothing happens until subscribed).

Mono.just("hello")         // cold source
    .map(String::toUpperCase)
    .subscribe(System.out::println);  // "HELLO" — triggers the pipeline

  4. SPRING WEBFLUX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring WebFlux is Spring's reactive web framework. It runs on:
  - Netty (default — non-blocking event loop)
  - Undertow
  - Tomcat / Jetty (with non-blocking connectors)

Two programming models:
  1. Annotated controllers (@RestController) — same annotations as Spring MVC
  2. Functional endpoints (RouterFunction + HandlerFunction)

@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService service;

    @GetMapping("/{id}")
    public Mono<Product> findById(@PathVariable Long id) {
        return service.findById(id);   // returns Mono, no blocking
    }

    @GetMapping
    public Flux<Product> findAll() {
        return service.findAll();       // returns Flux
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<Product> create(@RequestBody Mono<Product> product) {
        return product.flatMap(service::save);
    }

    // Server-Sent Events streaming
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<Product> stream() {
        return service.findAll().delayElements(Duration.ofMillis(100));
    }
}

  5. REACTIVE DATA ACCESS — R2DBC

R2DBC (Reactive Relational Database Connectivity) = non-blocking DB driver.
Unlike JDBC (blocking), R2DBC doesn't block the event loop waiting for queries.

Spring Data R2DBC repository returns Mono/Flux:

public interface ProductRepository extends ReactiveCrudRepository<Product, Long> {
    Flux<Product> findByCategory(String category);
    Mono<Long> countByCategory(String category);
}

  6. REACTIVE vs SERVLET — COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Feature                | Spring MVC (Servlet)         | Spring WebFlux (Reactive)
-----------------------|------------------------------|---------------------------
Thread model           | Thread per request           | Event loop (few threads)
Blocking I/O           | OK (thread waits)            | Must be non-blocking
Return types           | Object, ResponseEntity       | Mono<T>, Flux<T>
DB access              | JDBC / Spring Data JPA       | R2DBC / Spring Data R2DBC
HTTP client            | RestTemplate / RestClient    | WebClient
Best for               | Low-medium concurrency CRUD  | High concurrency I/O-bound
Learning curve         | Lower                        | Higher
Framework              | spring-boot-starter-web      | spring-boot-starter-webflux

Q: What is the core benefit of reactive programming?
A: Non-blocking I/O. In traditional blocking code, a thread waits idle while
   a DB query or HTTP call completes. Reactive code releases the thread during
   the wait, allowing it to serve other requests. A small thread pool can
   handle massive concurrency without thread exhaustion.

Q: What is backpressure and why does it matter?
A: Backpressure is a flow-control mechanism where the consumer signals to the
   producer how many items it can handle. Without backpressure, a fast producer
   can overwhelm a slow consumer, causing OutOfMemoryError. Reactive Streams
   handles this via subscription.request(n) — the subscriber controls the rate.

Q: When should you NOT use Spring WebFlux?
A: Avoid WebFlux for CPU-intensive tasks (gains nothing over MVC), blocking
   libraries that don't have reactive counterparts (e.g., blocking JDBC),
   simple CRUD with low concurrency (unnecessary complexity), or teams without
   reactive experience (harder to debug, different error handling patterns).

Q: What happens if you do blocking I/O in a WebFlux handler?
A: It blocks the event-loop thread, which handles many concurrent requests.
   Blocking one event-loop thread can stall all requests assigned to it,
   degrading performance dramatically. Solution: wrap blocking calls with
   Mono.fromCallable(() -> blockingOp()).subscribeOn(Schedulers.boundedElastic()).

Q: What is the difference between Mono and Flux?
A: Mono<T> represents 0 or 1 asynchronous result (like a non-blocking Optional).
   Flux<T> represents 0 to N results with backpressure (like a non-blocking Stream).
   Both are lazy — they do nothing until subscribed. They support the same
   transformation operators (map, flatMap, filter, etc.).
