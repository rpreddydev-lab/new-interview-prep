  1. WHY CACHING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Caching stores expensive computation results or DB query results in fast
storage so repeat calls return immediately without recomputing.

Benefits:
  - Reduced DB load (fewer queries)
  - Lower latency (memory/Redis vs DB)
  - Higher throughput (serve more requests with same infrastructure)

Spring Cache Abstraction:
  - Technology-agnostic @Cacheable, @CacheEvict, @CachePut annotations
  - Works with any backing store: ConcurrentHashMap (in-memory, dev),
    Redis, Ehcache, Caffeine, Hazelcast, etc.
  - AOP-based: cache logic is transparent to the method implementation

  3. SPRING CACHE ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CacheManager   — creates and manages named caches
Cache          — named cache bucket (e.g., "products", "orders")
CacheKey       — determines which cache entry to use (from method params)
CacheValue     — stored result of the cached method

Flow for @Cacheable:
  1. Intercept method call (AOP proxy)
  2. Compute cache key from method arguments
  3. Check cache for key
  4. Hit: return cached value (method NOT called)
  5. Miss: call method, store result in cache, return result

  4. CACHE ANNOTATIONS SUMMARY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Annotation       | When It Caches         | When It Evicts     | Use For
-----------------|------------------------|--------------------|-----------------
@Cacheable       | On cache miss          | Never              | Read-through cache
@CachePut        | Always (every call)    | Never              | Update cache after write
@CacheEvict      | Never                  | On method call     | Invalidate after delete/update
@Caching         | N/A (composite)        | N/A                | Multiple operations in one
@CacheConfig     | N/A (class-level config) | N/A              | Shared config for all methods

  5. CACHE PITFALLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Self-invocation problem (same as AOP):
   Calling a @Cacheable method from the same bean bypasses the proxy.
   Solution: inject the bean into itself or extract to a separate class.

2. Cache stampede (thundering herd):
   On startup or after cache expiry, many requests may hit the DB simultaneously.
   Solution: use cache providers with probabilistic early expiration or a lock.

3. Stale data:
   Cached data becomes stale after updates. Use @CacheEvict or @CachePut
   in write operations to keep cache consistent.

4. Null result caching:
   By default, Spring caches null results. Use unless="#result == null" to
   prevent caching null values.

5. Cache serialization:
   When using Redis, cached objects must be serializable. Use Jackson2
   serialization or ensure classes implement Serializable.

  6. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the Spring Cache Abstraction?
A: Spring Cache Abstraction provides technology-agnostic caching via annotations
   (@Cacheable, @CacheEvict, @CachePut). The abstraction hides the underlying
   cache provider (Redis, Ehcache, Caffeine). You switch cache providers by
   changing configuration without touching business logic.

Q: How does Spring implement caching internally?
A: Spring uses AOP proxies (same as @Transactional). @EnableCaching creates an
   AOP advisor that intercepts calls to @Cacheable methods. On cache miss,
   it calls the real method; on hit, it returns the cached value without
   calling the method. This is why self-invocation bypasses caching.

Q: What is the difference between in-process and distributed caching?
A: In-process (Caffeine, Ehcache local, ConcurrentHashMap): cache is in the
   JVM heap, extremely fast, but not shared between instances. Each pod has
   its own cache → inconsistency in multi-instance deployments. Distributed
   (Redis, Hazelcast, Memcached): cache is shared across all instances,
   consistent but involves a network call. Use distributed cache when running
   multiple pods or when cache must survive app restarts.

Q: What is a cache stampede and how do you prevent it?
A: A cache stampede (thundering herd) occurs when a cached entry expires
   and many concurrent requests all miss the cache simultaneously and hit
   the DB. Solutions: (1) Use Probabilistic Early Expiration (PER) — Caffeine
   supports this. (2) Use a distributed lock so only one thread refreshes.
   (3) Use @CacheLock patterns. (4) Asynchronous refresh in background.

Q: When would you choose Caffeine over Redis for caching?
A: Caffeine for: single-instance apps or dev environments, sub-millisecond
   latency requirements, small data sets that fit in heap, no cache sharing
   needed between pods. Redis for: multi-instance apps where all pods must
   see the same cache, cache larger than JVM heap, cache must survive
   restarts, need TTL or eviction at infrastructure level.
