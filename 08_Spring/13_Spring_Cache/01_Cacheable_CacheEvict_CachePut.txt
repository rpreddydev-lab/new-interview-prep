  1. @Cacheable — READ-THROUGH CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Cacheable caches the method's return value. On subsequent calls with the
same key, the cached value is returned without executing the method.

@Service
@CacheConfig(cacheNames = "products")   // default cache name for all methods
public class ProductService {

    // Basic — cache key = method parameter (id)
    @Cacheable("products")
    public Product findById(Long id) {
        log.debug("DB hit for product {}", id);     // only printed on cache miss
        return productRepository.findById(id).orElseThrow();
    }

    // Custom key using SpEL
    @Cacheable(value = "products", key = "#category + ':' + #page")
    public Page<Product> findByCategory(String category, int page) {
        return productRepository.findByCategory(category, PageRequest.of(page, 20));
    }

    // Conditional caching — only cache if stock > 0
    @Cacheable(value = "products", key = "#id",
               condition = "#id > 0",
               unless = "#result == null || #result.stock == 0")
    public Product findForDisplay(Long id) {
        return productRepository.findById(id).orElse(null);
    }

    // Null-safe: don't cache null results
    @Cacheable(value = "products", key = "#id", unless = "#result == null")
    public Optional<Product> findOptional(Long id) {
        return productRepository.findById(id);
    }
}

// Key attributes:
//   value/cacheNames  — cache name(s)
//   key               — SpEL expression for cache key (default: all params)
//   condition         — SpEL; evaluated BEFORE method; if false, skip cache entirely
//   unless            — SpEL; evaluated AFTER method; if true, don't cache result
//   keyGenerator      — custom KeyGenerator bean name
//   sync              — if true, synchronize cache access (prevent stampede)

  2. @CacheEvict — INVALIDATE CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@CacheEvict removes one or more entries from the cache after the method runs.

@Service
public class ProductService {

    // Evict specific key on update
    @CacheEvict(value = "products", key = "#product.id")
    public Product update(Product product) {
        return productRepository.save(product);
    }

    // Evict specific key on delete
    @CacheEvict(value = "products", key = "#id")
    public void delete(Long id) {
        productRepository.deleteById(id);
    }

    // Evict ALL entries in cache (bulk invalidation)
    @CacheEvict(value = "products", allEntries = true)
    public void reloadAll() {
        // triggered after a bulk import, for example
    }

    // Evict BEFORE method (not after)
    @CacheEvict(value = "products", key = "#id", beforeInvocation = true)
    public Product forceRefresh(Long id) {
        // evicts before, then re-caches via @Cacheable if also annotated
        return productRepository.findById(id).orElseThrow();
    }
}

  3. @CachePut — UPDATE CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@CachePut ALWAYS executes the method AND updates the cache with the result.
Used to keep cache consistent after a write operation.

@Service
public class ProductService {

    // After saving, put the result in cache so next @Cacheable read hits cache
    @CachePut(value = "products", key = "#result.id")
    public Product save(Product product) {
        return productRepository.save(product);   // always called
    }

    @CachePut(value = "products", key = "#product.id")
    public Product update(Product product) {
        Product existing = productRepository.findById(product.getId()).orElseThrow();
        existing.setName(product.getName());
        existing.setPrice(product.getPrice());
        return productRepository.save(existing);
    }
}

// @Cacheable vs @CachePut:
//   @Cacheable: skips method if cache hit (read-through pattern)
//   @CachePut:  always runs method, always updates cache (write-through pattern)

  4. @Caching — MULTIPLE OPERATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Caching combines multiple cache annotations on one method:

@Service
public class ProductService {

    // On save: put in "products" cache AND evict "categories" cache
    @Caching(
        put    = { @CachePut(value = "products", key = "#result.id") },
        evict  = { @CacheEvict(value = "categories", key = "#product.category"),
                   @CacheEvict(value = "productSummary", allEntries = true) }
    )
    public Product save(Product product) {
        return productRepository.save(product);
    }

    // Multiple cache names for @Cacheable
    @Caching(cacheable = {
        @Cacheable(value = "products"),
        @Cacheable(value = "productsBySlug", key = "#product.slug")
    })
    public Product findBySlug(String slug) {
        return productRepository.findBySlug(slug).orElseThrow();
    }
}

  5. CUSTOM KEY GENERATOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Default key strategy: if one parameter → use it as key. Multiple parameters
→ use SimpleKeyGenerator combining all params.

@Component("tenantAwareKeyGenerator")
public class TenantAwareKeyGenerator implements KeyGenerator {

    private final TenantContext tenantContext;

    @Override
    public Object generate(Object target, Method method, Object... params) {
        String tenant = tenantContext.getCurrentTenant();
        return tenant + ":" + SimpleKeyGenerator.generateKey(params);
    }
}

// Usage:
@Cacheable(value = "products", keyGenerator = "tenantAwareKeyGenerator")
public List<Product> findAll() {
    return productRepository.findAll();
}

  6. SpEL EXPRESSIONS IN CACHE ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Expression                    | Meaning
------------------------------|---------------------------------------
#paramName                    | Method parameter named 'paramName'
#p0, #a0                      | First method argument
#root.methodName              | Method name
#root.targetClass             | Target class
#root.args[0]                 | First argument via array
#result                       | Return value (only in unless/@CachePut key)
#product.id                   | Access field on parameter
#id > 0                       | Conditional expression
#category + ':' + #page       | Composite key

  7. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between @CacheEvict and @CachePut?
A: @CacheEvict removes an entry (or all entries) from the cache — used after
   delete or when you want to force a re-fetch next time. @CachePut always
   executes the method and stores the new result in the cache, keeping the
   cache populated and fresh. Use @CachePut after an update to avoid a stale
   read; use @CacheEvict when you don't need to keep the cache warm after a write.

Q: What is the difference between condition and unless in @Cacheable?
A: condition is evaluated BEFORE the method runs — if false, the annotation
   is completely ignored (no cache lookup, no cache store). unless is evaluated
   AFTER the method runs (has access to #result) — if true, the result is not
   stored in cache but the method was still called. Use condition to skip caching
   for certain inputs; use unless to prevent caching null results or undesirable values.

Q: How do you prevent caching null values?
A: Use unless = "#result == null" on @Cacheable. By default, Spring caches
   null return values, causing every call with that key to return null without
   hitting the DB. The unless clause prevents storing null results.

Q: What is the default key strategy when a method has multiple parameters?
A: SimpleKeyGenerator is used. If the method has one parameter, that parameter
   is the key. If multiple, all parameters are combined into a SimpleKey.
   If no parameters, SimpleKey.EMPTY is the key. Override with a custom key
   expression (key="#param1+':'+#param2") for predictable, readable keys.

Q: Can @Cacheable be applied to multiple caches simultaneously?
A: Yes, using value/cacheNames with an array: @Cacheable({"products", "catalog"}).
   On cache miss, the method runs once but the result is stored in all listed
   caches. On hit, Spring checks each cache in order and returns the first hit.
