  1. THE MIGRATION: WHY SLEUTH WAS DEPRECATED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Cloud Sleuth (for Spring Boot 2.x):
  - Built on Brave (the tracing library from Zipkin team)
  - Added traceId/spanId to SLF4J MDC automatically
  - Instrumented HTTP, Feign, Kafka, RabbitMQ
  - Exported spans to Zipkin via HTTP or Kafka/RabbitMQ reporters
  - Was a separate Spring Cloud project

Problem: Sleuth was tightly coupled to Brave and Zipkin.
OpenTelemetry (OTEL) became the industry standard. Spring needed to
support multiple backends without code changes.

Micrometer Tracing (Spring Boot 3.x):
  - Vendor-neutral tracing API (like SLF4J is for logging)
  - Bridges to multiple implementations: Brave, OpenTelemetry
  - Part of Micrometer ecosystem (already used for metrics)
  - Spring Boot 3.x auto-configures Micrometer Tracing via Actuator

Option A: Brave bridge (to export to Zipkin — most common)

<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>

Option B: OpenTelemetry bridge (to export to Jaeger, OTLP, AWS X-Ray, etc.)

<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-zipkin</artifactId>
    <!-- OR opentelemetry-exporter-otlp for Jaeger/Tempo/etc. -->
</dependency>

Spring Boot Actuator enables tracing auto-configuration when bridge is on classpath:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

# application.yml (Spring Boot 3.x)
management:
  tracing:
    sampling:
      probability: 1.0    # 1.0 = 100%, 0.1 = 10%
    propagation:
      type: B3            # B3, W3C (TraceContext), AWS
  zipkin:
    tracing:
      endpoint: http://localhost:9411/api/v2/spans

logging:
  pattern:
    correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-}]"
    level: "%5p ${logging.pattern.correlation}"
  # Or set in logback-spring.xml for structured logging

  5. USING MICROMETER TRACING API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Inject io.micrometer.tracing.Tracer (NOT brave.Tracer)
@Service
public class PaymentService {

    private final Tracer tracer;

    public PaymentService(Tracer tracer) {
        this.tracer = tracer;
    }

    public PaymentResult processPayment(PaymentRequest request) {
        // Create a new span
        Span span = tracer.nextSpan().name("payment-gateway-call");

        try (Tracer.SpanInScope ws = tracer.withSpan(span.start())) {
            span.tag("payment.amount", request.getAmount().toString());
            span.event("payment-started");

            PaymentResult result = callPaymentGateway(request);

            span.tag("payment.status", result.getStatus());
            return result;

        } catch (Exception ex) {
            span.error(ex);
            throw ex;
        } finally {
            span.end();
        }
    }
}

// Observation API (higher-level, preferred):
@Service
public class OrderService {

    private final ObservationRegistry observationRegistry;

    public Order createOrder(CreateOrderRequest request) {
        return Observation.createNotStarted("order.create", observationRegistry)
            .lowCardinalityKeyValue("status", "pending")
            .observe(() -> {
                // This code is observed (traced + metrics)
                return doCreateOrder(request);
            });
    }
}

  6. OBSERVATION API — THE UNIFIED ABSTRACTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Boot 3.x introduces the Observation API (Micrometer 1.10+).
An Observation produces BOTH a metric (timer) AND a trace span automatically.

  @Observed(name = "order.create", contextualName = "create-order")
  public Order createOrder(CreateOrderRequest request) {
      // auto-creates a span AND records a timer metric
  }

Enable @Observed:
  @Configuration
  @EnableObservability
  public class ObservabilityConfig {
      @Bean
      ObservedAspect observedAspect(ObservationRegistry observationRegistry) {
          return new ObservedAspect(observationRegistry);
      }
  }

  7. AUTO-INSTRUMENTATION (WHAT'S INCLUDED)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Boot 3 auto-instruments these when tracing is on the classpath:
  - Spring MVC (HTTP server requests → spans)
  - WebFlux (reactive HTTP server → spans)
  - RestTemplate / RestClient (HTTP client calls → child spans)
  - WebClient (reactive HTTP client → child spans)
  - Spring Data (JPA queries → spans)
  - Kafka / RabbitMQ listeners and templates
  - Feign clients
  - Scheduled tasks (@Scheduled → spans)

Each instrumented call propagates the trace context automatically:
  - For HTTP: via traceparent header (W3C) or X-B3-TraceId (B3)
  - For Kafka: via message headers
  - For RabbitMQ: via message headers

Q: Why was Spring Cloud Sleuth deprecated?
A: Sleuth was tightly coupled to the Brave library and Zipkin. As
   OpenTelemetry became the industry standard, Spring needed a vendor-
   neutral tracing API. Micrometer Tracing provides this — it's a facade
   over Brave or OpenTelemetry, integrated into the Micrometer ecosystem
   (which Spring Boot already uses for metrics).

Q: What is the Observation API?
A: The Observation API (Micrometer 1.10+, Spring Boot 3.x) is a unified
   abstraction that produces both a metric (timer) AND a trace span from
   a single observation. This means you don't need to separately create
   a Timer and a Span — one @Observed or Observation.observe() does both.

Q: What is the difference between micrometer-tracing-bridge-brave and bridge-otel?
A: Both implement the Micrometer Tracing API but use different underlying
   libraries. bridge-brave uses Brave (Zipkin's tracing library) — best for
   Zipkin export. bridge-otel uses OpenTelemetry SDK — best for Jaeger,
   Tempo, AWS X-Ray, or any OTLP-compatible backend. You use one or the other.

Q: How do trace IDs appear in logs with Micrometer Tracing?
A: Spring Boot 3.x auto-configures the MDC context bridge. traceId and
   spanId are put into SLF4J MDC automatically. Add %X{traceId} and
   %X{spanId} to your logback pattern, or use the auto-configured
   logging.pattern.correlation property.

Q: Is OpenTelemetry replacing Zipkin?
A: OpenTelemetry is a vendor-neutral standard for generating telemetry
   data (traces, metrics, logs). Zipkin is a specific backend for storage
   and visualization. You can use OpenTelemetry SDK to generate traces and
   export them TO Zipkin (via OTLP or Zipkin exporter). They are not
   mutually exclusive — OTel is the instrumentation layer, Zipkin is the
   backend.
