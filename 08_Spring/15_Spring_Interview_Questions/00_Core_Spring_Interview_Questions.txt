SECTION 1 — IoC AND DEPENDENCY INJECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1. What is Inversion of Control (IoC)?
────────────────────────────────────────
Answer:
  IoC is a design principle where the control of object creation and dependency
  management is transferred from the application code to an external container/
  framework. Instead of an object creating its own dependencies (new Foo()), the
  container creates and injects them.

  Traditional approach:
    class OrderService {
        private PaymentService ps = new PaymentService(); // tight coupling
    }

  IoC approach (Spring):
    class OrderService {
        private final PaymentService ps;
        public OrderService(PaymentService ps) { this.ps = ps; } // injected
    }

  Benefits:
    • Loose coupling — easier to swap implementations
    • Testability — inject mocks/stubs during testing
    • Separation of concerns — business logic vs. wiring logic
    • Centralized configuration

Q2. What is Dependency Injection (DI)?
────────────────────────────────────────
Answer:
  DI is the primary mechanism by which Spring implements IoC. The container
  "injects" dependencies into objects rather than letting objects fetch their
  dependencies.

  Three types of DI in Spring:

  1. Constructor Injection (RECOMMENDED):
     @Component
     public class OrderService {
         private final PaymentService paymentService;

         @Autowired   // optional since Spring 4.3 if only one constructor
         public OrderService(PaymentService paymentService) {
             this.paymentService = paymentService;
         }
     }
     → Immutable, null-safe, dependencies explicit, supports final fields.

  2. Setter Injection:
     @Component
     public class OrderService {
         private PaymentService paymentService;

         @Autowired
         public void setPaymentService(PaymentService ps) {
             this.paymentService = ps;
         }
     }
     → Optional/changing dependencies; allows reconfiguration after construction.

  3. Field Injection (NOT recommended for production):
     @Component
     public class OrderService {
         @Autowired
         private PaymentService paymentService;
     }
     → Convenient but hides dependencies, makes testing harder without Spring.

  Interview Tip: Always prefer constructor injection. It makes dependencies
  explicit, supports immutability, and enables unit testing without a Spring
  context.

Q3. Why is Constructor Injection preferred over Field Injection?
────────────────────────────────────────────────────────────────
Answer:
  1. Immutability: Fields can be declared final; once set, cannot be changed.
  2. Explicit dependencies: All required deps visible in constructor signature.
  3. Null safety: NPE impossible if object is successfully constructed.
  4. Testability: Can instantiate with new without Spring context in unit tests.
  5. Detects circular dependencies at startup (fail-fast) instead of at runtime.
  6. SRP enforcement: Too many constructor args signals violation of SRP.

  Field injection drawbacks:
    - Requires reflection to set private fields (bypasses encapsulation)
    - Cannot use final
    - Hard to instantiate in unit tests without @InjectMocks / Mockito hacks
    - Hides the "contract" of the class

Q4. What is the difference between BeanFactory and ApplicationContext?
────────────────────────────────────────────────────────────────────────
Answer:
  BeanFactory (org.springframework.beans.factory.BeanFactory):
    • Root interface for the Spring IoC container
    • Lazy initialization: beans created only when getBean() is called
    • Basic DI support
    • Lightweight (resource-constrained environments)
    • Does NOT support: AOP, event publishing, i18n, lifecycle callbacks

  ApplicationContext (org.springframework.context.ApplicationContext):
    • Extends BeanFactory — is a BeanFactory + enterprise features
    • Eager initialization of singleton beans at startup
    • Additional features:
        - MessageSource (i18n)
        - ApplicationEventPublisher (event system)
        - ResourceLoader
        - AOP integration
        - @Transactional, @Scheduled support
        - BeanPostProcessor / BeanFactoryPostProcessor auto-detection

  Common implementations:
    ClassPathXmlApplicationContext  — XML config from classpath
    FileSystemXmlApplicationContext — XML config from filesystem
    AnnotationConfigApplicationContext — Java/annotation-based config
    AnnotationConfigWebApplicationContext — Web apps with Java config

  Interview Tip: In real apps, always use ApplicationContext. BeanFactory is
  mainly for embedded systems or frameworks building on top of Spring.

Q5. Explain the complete Bean Lifecycle in Spring.
───────────────────────────────────────────────────
Answer:
  Spring manages beans through a well-defined lifecycle:

  STEP 1: Instantiation
    Container instantiates the bean via constructor or factory method.

  STEP 2: Populate Properties (DI)
    Container injects dependencies via constructor, setter, or field injection.

  STEP 3: BeanNameAware.setBeanName(String name)
    Container passes the bean's id/name to the bean (if it implements BeanNameAware).

  STEP 4: BeanFactoryAware.setBeanFactory(BeanFactory bf)
    Container passes itself to the bean (if it implements BeanFactoryAware).

  STEP 5: ApplicationContextAware.setApplicationContext(ApplicationContext ctx)
    Container passes the ApplicationContext (if the bean implements it).

  STEP 6: BeanPostProcessor.postProcessBeforeInitialization()
    All registered BeanPostProcessors get a chance to process the bean BEFORE
    initialization. (@PostConstruct is handled here via CommonAnnotationBPP.)

  STEP 7: InitializingBean.afterPropertiesSet() / @PostConstruct / init-method
    The bean's own initialization logic runs.

  STEP 8: BeanPostProcessor.postProcessAfterInitialization()
    All registered BeanPostProcessors run AFTER initialization.
    (This is where AOP proxies are typically created.)

  STEP 9: Bean is ready for use

  STEP 10 (Shutdown): DisposableBean.destroy() / @PreDestroy / destroy-method
    Called when the container is shut down.

  Code Example:
    @Component
    public class MyBean implements InitializingBean, DisposableBean {

        @PostConstruct
        public void init() { System.out.println("@PostConstruct"); }

        @Override
        public void afterPropertiesSet() { System.out.println("afterPropertiesSet"); }

        @PreDestroy
        public void cleanup() { System.out.println("@PreDestroy"); }

        @Override
        public void destroy() { System.out.println("DisposableBean.destroy"); }
    }
    // Output order: @PostConstruct → afterPropertiesSet → @PreDestroy → destroy

Q6. What are Bean Scopes in Spring?
────────────────────────────────────
Answer:
  Spring provides 6 built-in bean scopes:

  1. SINGLETON (default):
     • ONE instance per Spring IoC container
     • Same object returned on every getBean() call
     • Eager initialization at startup (unless lazy)
     @Scope("singleton") or just omit @Scope

  2. PROTOTYPE:
     • NEW instance each time bean is requested
     • Container does NOT manage lifecycle after creation (no @PreDestroy)
     @Scope("prototype")

  3. REQUEST (web only):
     • ONE instance per HTTP request
     • Destroyed at end of request
     @Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)

  4. SESSION (web only):
     • ONE instance per HTTP session
     @Scope(value = WebApplicationContext.SCOPE_SESSION, proxyMode = ScopedProxyMode.TARGET_CLASS)

  5. APPLICATION (web only):
     • ONE instance per ServletContext (like singleton but for web)

  6. WEBSOCKET (web only):
     • ONE instance per WebSocket session

  Singleton + Prototype Injection Problem:
    When a singleton bean depends on a prototype bean, the prototype is injected
    ONCE at creation time — effectively making it a singleton.

    Solutions:
      a) ApplicationContext.getBean() lookup (method injection)
      b) @Lookup annotation on abstract method:
         @Lookup
         public abstract PrototypeBean createPrototype();
      c) ObjectFactory<T> or Provider<T>:
         @Autowired private ObjectFactory<PrototypeBean> pbFactory;

Q7. What is @Qualifier and when do you use it?
────────────────────────────────────────────────
Answer:
  When multiple beans of the same type exist, @Autowired alone doesn't know
  which one to inject. @Qualifier specifies the bean by name.

  @Component("emailNotifier")
  public class EmailNotifier implements Notifier { ... }

  @Component("smsNotifier")
  public class SmsNotifier implements Notifier { ... }

  @Service
  public class OrderService {
      @Autowired
      @Qualifier("emailNotifier")
      private Notifier notifier;
  }

  Custom @Qualifier:
    @Qualifier
    @Target({ElementType.FIELD, ElementType.PARAMETER})
    @Retention(RetentionPolicy.RUNTIME)
    public @interface Email {}

    @Email @Component public class EmailNotifier implements Notifier { ... }

    @Autowired @Email private Notifier notifier;

Q8. What is the difference between @Component, @Service, @Repository, @Controller?
────────────────────────────────────────────────────────────────────────────────────
Answer:
  All four are stereotype annotations — they are all specializations of
  @Component and result in the class being auto-detected via component scanning.

  @Component   — Generic Spring-managed component (catch-all)
  @Service     — Service layer; purely semantic, same behavior as @Component
  @Repository  — Persistence layer; ADDITIONALLY enables Spring's persistence
                 exception translation (converts DB-specific exceptions to
                 Spring's DataAccessException hierarchy)
  @Controller  — MVC Controller; marks handler methods for web request handling

  @RestController = @Controller + @ResponseBody

  Interview Tip: The semantic distinction matters for readability and because
  @Repository specifically enables exception translation via
  PersistenceExceptionTranslationPostProcessor.

Q9. What is @Primary?
──────────────────────
Answer:
  When multiple beans of the same type exist, @Primary designates which one
  should be preferred for autowiring when no @Qualifier is specified.

  @Primary
  @Component
  public class EmailNotifier implements Notifier { ... }

  @Component
  public class SmsNotifier implements Notifier { ... }

  // EmailNotifier is injected by default
  @Autowired private Notifier notifier;

  @Primary vs @Qualifier: @Qualifier always wins over @Primary.

Q10. What is a BeanPostProcessor?
────────────────────────────────────
Answer:
  BeanPostProcessor is a callback interface that lets you modify bean instances
  AFTER the container instantiates them but before they are given to the
  application. Called for EVERY bean in the container.

  Interface methods:
    Object postProcessBeforeInitialization(Object bean, String beanName)
    Object postProcessAfterInitialization(Object bean, String beanName)

  Real-world use cases:
    • @Autowired handling (AutowiredAnnotationBeanPostProcessor)
    • @PostConstruct / @PreDestroy (CommonAnnotationBeanPostProcessor)
    • AOP proxy creation (AbstractAutoProxyCreator)
    • @Async, @Transactional processing
    • Validation

  Example — logging BPP:
    @Component
    public class LoggingBPP implements BeanPostProcessor {
        @Override
        public Object postProcessAfterInitialization(Object bean, String name) {
            System.out.println("Bean initialized: " + name);
            return bean; // MUST return bean (or a proxy)
        }
    }

  Note: BeanPostProcessors themselves are instantiated BEFORE regular beans.

Q11. What is a BeanFactoryPostProcessor?
──────────────────────────────────────────
Answer:
  BeanFactoryPostProcessor allows modification of bean DEFINITIONS (metadata)
  before any beans are instantiated. It operates on BeanDefinition objects.

  Called after all bean definitions are loaded but BEFORE beans are created.

  Common implementations:
    PropertySourcesPlaceholderConfigurer — resolves ${property} placeholders
    PropertyOverrideConfigurer — overrides bean property values
    ConfigurationClassPostProcessor — processes @Configuration classes

  Example:
    @Component
    public class MyBFPP implements BeanFactoryPostProcessor {
        @Override
        public void postProcessBeanFactory(ConfigurableListableBeanFactory bf) {
            BeanDefinition bd = bf.getBeanDefinition("myBean");
            bd.getPropertyValues().add("someProperty", "overriddenValue");
        }
    }

  BeanFactoryPostProcessor vs BeanPostProcessor:
    BFPP  → operates on bean DEFINITIONS (before instantiation)
    BPP   → operates on bean INSTANCES (after instantiation)

Q12. Explain @Configuration and @Bean.
────────────────────────────────────────
Answer:
  @Configuration marks a class as a source of bean definitions.
  @Bean marks a method whose return value is registered as a Spring bean.

  @Configuration
  public class AppConfig {

      @Bean
      public DataSource dataSource() {
          HikariDataSource ds = new HikariDataSource();
          ds.setJdbcUrl("jdbc:mysql://localhost/mydb");
          return ds;
      }

      @Bean
      public UserRepository userRepository(DataSource dataSource) {
          return new UserRepositoryImpl(dataSource);
      }
  }

  @Configuration vs @Component:
    @Configuration uses CGLIB to subclass the config class, making @Bean method
    calls intercepted so that dependencies are returned from the container
    (singleton semantics). Calling dataSource() inside the class always returns
    the SAME bean instance.

    @Component-annotated classes with @Bean methods are called "lite" mode —
    no CGLIB, calls are not intercepted, each call creates a new instance.

  proxyBeanMethods = false:
    @Configuration(proxyBeanMethods = false) — disables CGLIB; faster startup,
    but inter-@Bean-method calls create new instances (use for leaf configs).

Q13. What is @Lazy?
────────────────────
Answer:
  @Lazy delays bean initialization until it is first requested, instead of at
  startup (which is default for singletons).

  @Lazy
  @Component
  public class HeavyService { ... }

  Use cases:
    1. Expensive-to-create beans not needed at startup
    2. Break circular dependency issues (last resort)
    3. @Lazy on @Autowired injection point — injects a proxy that initializes
       the real bean on first method call:
       @Autowired @Lazy private HeavyService hs;

Q14. How does Spring resolve circular dependencies?
─────────────────────────────────────────────────────
Answer:
  A circular dependency occurs when Bean A depends on Bean B and Bean B depends
  on Bean A.

  Spring's approach (setter/field injection):
    Spring handles SINGLETON circular dependencies via a "three-level cache"
    (singletonObjects, earlySingletonObjects, singletonFactories).
    It exposes a partially-constructed bean (ObjectFactory) to resolve the cycle.

  Constructor injection + circular dependency = BeanCurrentlyInCreationException
    Spring CANNOT resolve circular dependencies when both use constructor injection
    because it needs both fully-constructed to call either constructor.

  Solutions:
    1. Redesign — remove the circular dependency (best approach)
    2. Use setter/field injection for ONE of the dependencies
    3. @Lazy on one of the injection points
    4. ApplicationContext.getBean() lookup at use time

Q15. What are Spring Profiles?
──────────────────────────────
Answer:
  Profiles allow conditional bean registration based on the active environment.

  Declaring a profile:
    @Profile("dev")
    @Configuration
    public class DevConfig {
        @Bean public DataSource dataSource() { /* H2 in-memory */ }
    }

    @Profile("prod")
    @Configuration
    public class ProdConfig {
        @Bean public DataSource dataSource() { /* MySQL */ }
    }

  Activating profiles:
    application.properties:  spring.profiles.active=dev
    JVM arg:                  -Dspring.profiles.active=dev,featureX
    Programmatically:         ctx.getEnvironment().setActiveProfiles("dev");

  Profile expressions (Spring 5.1+):
    @Profile("!prod")   — active when "prod" is NOT active
    @Profile("dev | test") — active when "dev" OR "test" is active
    @Profile("dev & featureX") — active when BOTH "dev" AND "featureX" active

Q16. What is the Spring Event System?
──────────────────────────────────────
Answer:
  Spring provides a built-in event mechanism via ApplicationEventPublisher.

  Custom Event:
    public class OrderPlacedEvent extends ApplicationEvent {
        private final Order order;
        public OrderPlacedEvent(Object source, Order order) {
            super(source);
            this.order = order;
        }
        public Order getOrder() { return order; }
    }

  Publishing:
    @Service
    public class OrderService {
        @Autowired private ApplicationEventPublisher publisher;

        public void placeOrder(Order order) {
            // ... business logic
            publisher.publishEvent(new OrderPlacedEvent(this, order));
        }
    }

  Listening (annotation-based, Spring 4.2+):
    @Component
    public class NotificationListener {
        @EventListener
        public void handleOrderPlaced(OrderPlacedEvent event) {
            // send email
        }

        @EventListener
        @Async   // async handling
        public void sendSms(OrderPlacedEvent event) { ... }
    }

  Ordered listeners:
    @EventListener @Order(1) — execute in specified order

  Transaction-bound events:
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void afterCommit(OrderPlacedEvent event) { ... }

Q17. What is the difference between @Autowired and @Inject?
───────────────────────────────────────────────────────────
Answer:
  @Autowired (Spring) vs @Inject (JSR-330):
    • @Inject has no "required" attribute (defaults to required=true)
    • @Autowired has required=false option
    • @Inject uses @Qualifier (JSR-330) instead of Spring's @Qualifier
    • Both work identically in Spring for autowiring
    • @Inject makes code portable outside Spring (CDI, Guice)

  @Value:
    Injects values from properties files, environment variables, SpEL:
    @Value("${app.name}") private String appName;
    @Value("#{systemProperties['user.home']}") private String home;

Q18. What is SpEL (Spring Expression Language)?
─────────────────────────────────────────────────
Answer:
  SpEL is a powerful expression language for querying and manipulating objects
  at runtime. Used in @Value, XML config, security expressions, etc.

  Examples:
    @Value("#{1 + 2}")                 // → 3
    @Value("#{T(Math).random() * 100}")
    @Value("#{myBean.someProperty}")
    @Value("#{systemProperties['user.dir']}")
    @Value("#{myList[0]}")
    @Value("#{myMap['key']}")
    @Value("#{myBean.name?.toUpperCase()}")  // null-safe navigation

  Used in:
    @Cacheable(key = "#id")
    @PreAuthorize("hasRole('ADMIN')")
    @Query("SELECT u FROM User u WHERE u.age > :#{#age}")

Q19. What is @Conditional?
────────────────────────────
Answer:
  @Conditional registers a bean only when a specified condition is true.
  It's the foundation of Spring Boot's auto-configuration.

  @Conditional(OnLinuxCondition.class)
  @Bean public FileWatcher linuxWatcher() { ... }

  Custom Condition:
    public class OnLinuxCondition implements Condition {
        @Override
        public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata m) {
            return ctx.getEnvironment()
                      .getProperty("os.name", "").toLowerCase().contains("linux");
        }
    }

  Spring Boot built-in @Conditional variants:
    @ConditionalOnClass(MyClass.class)     — bean exists only if class on classpath
    @ConditionalOnMissingBean(MyService.class)
    @ConditionalOnProperty("feature.enabled")
    @ConditionalOnExpression("${myFlag:false}")
    @ConditionalOnWebApplication
    @ConditionalOnJava(JavaVersion.SEVENTEEN)

Q20. What is the difference between @Component scanning and explicit @Bean definition?
───────────────────────────────────────────────────────────────────────────────────────
Answer:
  Component Scanning (@ComponentScan + @Component):
    • Spring scans specified packages for @Component-annotated classes
    • Automatic detection; less boilerplate
    • Good for application classes you own and can annotate
    @ComponentScan(basePackages = "com.example")

  Explicit @Bean:
    • You write @Bean methods in @Configuration classes
    • Required for third-party classes you cannot annotate
    • Full control over instantiation, conditional creation
    • Can be combined with @Conditional, @Profile, etc.

  Typical usage:
    • Own service/repo/controller classes → @Component / @Service / @Repository
    • Third-party library objects (DataSource, RestTemplate) → @Bean in @Configuration

Q21. How does Spring's @Transactional work internally?
────────────────────────────────────────────────────────
Answer:
  @Transactional uses Spring AOP to wrap the annotated method in a proxy.

  Mechanism:
    1. Spring creates a CGLIB or JDK dynamic proxy around the bean.
    2. When a transactional method is called on the proxy, the proxy:
       a. Obtains/begins a transaction from PlatformTransactionManager
       b. Delegates to the real method
       c. Commits on success, rolls back on RuntimeException (by default)

  Key attributes:
    propagation  — how transactions interact (REQUIRED, REQUIRES_NEW, NESTED…)
    isolation    — READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE…
    readOnly     — hint to optimize (no dirty checking, etc.)
    rollbackFor  — additional exception classes that trigger rollback
    timeout      — max seconds before transaction is forcibly rolled back

  Self-invocation problem:
    Calling a @Transactional method from WITHIN the SAME class bypasses the proxy
    → transaction is NOT started.
    Solution: Inject self-reference, use AspectJ weaving, or restructure.

Q22. What is @Scope("prototype") gotcha with @Autowired singleton?
──────────────────────────────────────────────────────────────────
Answer:
  A prototype bean injected into a singleton bean is resolved ONCE at creation
  time and shared for the lifetime of the singleton. This defeats the purpose
  of prototype scope.

  Problem example:
    @Component @Scope("prototype") class RequestContext { /* mutable state */ }

    @Service class OrderService {
        @Autowired RequestContext ctx; // ONLY ONE instance ever injected!
    }

  Correct approach (Provider):
    @Service class OrderService {
        @Autowired ObjectProvider<RequestContext> ctxProvider;

        public void process() {
            RequestContext ctx = ctxProvider.getObject(); // new instance each time
        }
    }

Q23. What is the difference between @Resource, @Autowired, and @Inject?
────────────────────────────────────────────────────────────────────────
Answer:
  @Autowired (Spring)   — by type first; @Qualifier for disambiguation
  @Inject (JSR-330)     — by type first; portable across containers
  @Resource (JSR-250)   — by name first; falls back to type; name from field name
                          (javax.annotation.Resource)

  @Resource("myBean")  — explicitly by name
  @Resource            — by field name
  @Autowired @Qualifier("myBean") — by type + qualifier

Q24. What is Environment and PropertySource in Spring?
──────────────────────────────────────────────────────
Answer:
  Environment represents the current runtime environment:
    - Profiles: which profiles are active/default
    - Properties: key-value pairs from various sources

  PropertySource hierarchy (highest priority first):
    1. JVM system properties (-Dkey=value)
    2. OS environment variables
    3. application-{profile}.properties
    4. application.properties
    5. @PropertySource annotations

  @PropertySource:
    @Configuration
    @PropertySource("classpath:custom.properties")
    public class AppConfig {
        @Autowired private Environment env;

        @Bean public MyService myService() {
            return new MyService(env.getProperty("my.property"));
        }
    }

Q25. What is a FactoryBean?
─────────────────────────────
Answer:
  FactoryBean<T> is a special bean that acts as a FACTORY to create beans of
  type T. The bean returned by getObject() is registered in the container, not
  the FactoryBean itself.

  public class ConnectionFactoryBean implements FactoryBean<Connection> {
      @Override
      public Connection getObject() throws Exception {
          return DriverManager.getConnection("jdbc:...");
      }
      @Override public Class<?> getObjectType() { return Connection.class; }
      @Override public boolean isSingleton() { return true; }
  }

  // Getting the FactoryBean itself (not the product):
  ConnectionFactoryBean fb = ctx.getBean("&connectionFactory");
  // Getting the product:
  Connection conn = ctx.getBean("connectionFactory");

  Used internally by: LocalSessionFactoryBean (Hibernate), JndiObjectFactoryBean,
  ProxyFactoryBean (AOP).

SECTION 3 — COMMON TRICKY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q. What happens if two beans have the same name?
  → Second definition overrides first (bean definition overriding).
  → Spring Boot disables overriding by default; throws error unless:
     spring.main.allow-bean-definition-overriding=true

Q. Can a @Bean method return null?
  → Yes, but it registers a null bean; autowiring will fail unless
    @Autowired(required=false) is used.

Q. What is the order of bean initialization?
  → @DependsOn("beanA") forces beanA to be created before current bean.
  → BeanFactoryPostProcessors before all others.

Q. Can you have multiple ApplicationContexts?
  → Yes. Spring MVC uses a parent-child context hierarchy:
      Root context (services, repos) — parent
      WebApplicationContext (controllers, MVC) — child
  → Child can see parent beans; parent cannot see child beans.

Q. What is @ImportResource?
  → Imports XML bean configurations into a Java @Configuration class.
  @ImportResource("classpath:legacy-beans.xml")

Q. What is @Import?
  → Imports additional @Configuration classes or regular @Component classes.
  @Import({SecurityConfig.class, PersistenceConfig.class})
  → Used heavily in Spring Boot auto-configuration via @AutoConfigureImport.
