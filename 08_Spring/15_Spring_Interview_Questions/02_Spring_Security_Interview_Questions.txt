Q1. Explain Spring Security's architecture at a high level.
─────────────────────────────────────────────────────────────
Answer:
  Spring Security is built around a Servlet filter chain. The entire security
  infrastructure is plugged in as a series of filters that execute BEFORE your
  application code.

  Key architectural components:

  1. DelegatingFilterProxy:
     A Servlet filter that delegates to a Spring-managed bean named
     "springSecurityFilterChain". This bridges the Servlet container and Spring
     ApplicationContext.

  2. FilterChainProxy (springSecurityFilterChain):
     A special Spring bean that holds a list of SecurityFilterChain instances.
     Routes each request to the matching chain.

  3. SecurityFilterChain:
     A chain of security filters applied to a matched request pattern.
     Multiple chains can be defined (e.g., one for API, one for UI).

  4. Security Filters (executed in order):
     WebAsyncManagerIntegrationFilter
     SecurityContextHolderFilter (or PersistenceFilter in older versions)
     HeaderWriterFilter
     CorsFilter
     CsrfFilter
     LogoutFilter
     UsernamePasswordAuthenticationFilter
     BasicAuthenticationFilter
     ExceptionTranslationFilter
     AuthorizationFilter (replaces FilterSecurityInterceptor in Security 6)

  5. SecurityContext:
     Holds the Authentication object for the current request.
     Stored in SecurityContextHolder (ThreadLocal by default).

  6. Authentication:
     Represents the principal (who is making the request):
     - principal: the authenticated user (UserDetails)
     - credentials: password/token (cleared after authentication)
     - authorities: list of GrantedAuthority (roles/permissions)
     - authenticated: boolean flag

Q2. What is SecurityContextHolder?
────────────────────────────────────
Answer:
  SecurityContextHolder is a static helper that provides access to the current
  security context (the Authentication object).

  Default strategy: ThreadLocal (one SecurityContext per thread)
    → Each request thread has its own SecurityContext.

  Other strategies:
    MODE_INHERITABLETHREADLOCAL: propagates to child threads (async)
    MODE_GLOBAL: single SecurityContext for entire JVM (desktop apps)

  Accessing current user:
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    String username = auth.getName();
    Collection<? extends GrantedAuthority> roles = auth.getAuthorities();

    // Type-safe access with Spring Security 6+
    @AuthenticationPrincipal UserDetails user

  Setting context manually (e.g., in tests or filters):
    SecurityContextHolder.getContext().setAuthentication(authentication);

Q3. Describe the Authentication flow in Spring Security.
─────────────────────────────────────────────────────────
Answer:
  For form login / username-password authentication:

  1. Browser submits POST /login with username + password.

  2. UsernamePasswordAuthenticationFilter intercepts the request.
     Creates an unauthenticated UsernamePasswordAuthenticationToken.

  3. Filter delegates to AuthenticationManager (specifically
     ProviderManager which holds a list of AuthenticationProviders).

  4. ProviderManager iterates providers; DaoAuthenticationProvider is used for
     form/basic auth:
       a. Calls UserDetailsService.loadUserByUsername(username)
       b. Returns UserDetails (username, encoded password, authorities)
       c. Compares provided password with stored password using PasswordEncoder

  5. If credentials match:
     - Authenticated UsernamePasswordAuthenticationToken created
     - Stored in SecurityContextHolder
     - Authentication success handler called (redirect or return 200)

  6. If credentials don't match:
     - BadCredentialsException thrown
     - Authentication failure handler called (redirect or return 401)

  Interfaces:
    AuthenticationManager      → authenticate(Authentication) → Authentication
    AuthenticationProvider     → authenticate(Authentication), supports(Class<?>)
    UserDetailsService         → loadUserByUsername(String) → UserDetails
    UserDetails                → getUsername(), getPassword(), getAuthorities()

Q4. What is the difference between Authentication and Authorization?
────────────────────────────────────────────────────────────────────
Answer:
  Authentication:
    "Who are you?" — verifying identity.
    Happens BEFORE authorization.
    Involves: credentials (username/password, token, certificate)
    Result: Authentication object in SecurityContext

  Authorization:
    "What are you allowed to do?" — checking permissions.
    Happens AFTER authentication.
    Based on: roles (ROLE_ADMIN), permissions (product:read), resource ownership
    Implemented by: AuthorizationFilter, @PreAuthorize, etc.

  Spring Security enforces authorization at two levels:
    1. Web (URL) level: securityFilterChain rules (.authorizeHttpRequests())
    2. Method level: @PreAuthorize, @PostAuthorize, @Secured, @RolesAllowed

Q5. How do you configure Spring Security (modern approach)?
─────────────────────────────────────────────────────────────
Answer:
  Spring Security 5.7+ (Spring Boot 2.7+) deprecated extending
  WebSecurityConfigurerAdapter. Use component-based configuration instead.

  @Configuration
  @EnableWebSecurity
  @EnableMethodSecurity          // enables @PreAuthorize, @PostAuthorize
  public class SecurityConfig {

      @Bean
      public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
          http
              .csrf(csrf -> csrf.disable())              // stateless APIs
              .sessionManagement(session -> session
                  .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
              .authorizeHttpRequests(auth -> auth
                  .requestMatchers("/api/auth/**").permitAll()
                  .requestMatchers("/api/admin/**").hasRole("ADMIN")
                  .requestMatchers(HttpMethod.GET, "/api/products/**").hasAnyRole("USER","ADMIN")
                  .anyRequest().authenticated())
              .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
          return http.build();
      }

      @Bean
      public AuthenticationManager authenticationManager(
              AuthenticationConfiguration config) throws Exception {
          return config.getAuthenticationManager();
      }

      @Bean
      public PasswordEncoder passwordEncoder() {
          return new BCryptPasswordEncoder(12);
      }

      @Bean
      public UserDetailsService userDetailsService(UserRepository repo) {
          return username -> repo.findByUsername(username)
              .orElseThrow(() -> new UsernameNotFoundException("User not found"));
      }
  }

Q6. What are the Spring Security 6 changes?
────────────────────────────────────────────
Answer:
  1. WebSecurityConfigurerAdapter removed (was deprecated in 5.7).
     → Use SecurityFilterChain @Bean approach.

  2. FilterSecurityInterceptor replaced by AuthorizationFilter.
     → Better performance, cleaner design.

  3. antMatchers() / mvcMatchers() / regexMatchers() replaced by requestMatchers().
     → Auto-selects between AntPathRequestMatcher / MvcRequestMatcher.

  4. HttpSecurity methods now use lambda DSL (Customizer) instead of and().

  5. Default security headers updated (stricter defaults).

  6. Authorization rules evaluated with AuthorizationManager (extensible interface).

  7. @EnableMethodSecurity replaces @EnableGlobalMethodSecurity.
     - prePostEnabled=true is now the DEFAULT.

  8. SecurityContextHolder uses HttpSessionSecurityContextRepository by default
     for session-based; DelegatingSecurityContextRepository otherwise.

Q7. How do you implement JWT authentication in Spring Security?
────────────────────────────────────────────────────────────────
Answer:
  JWT (JSON Web Token) flow:
    1. User logs in → server validates credentials → returns JWT
    2. Client sends JWT in Authorization header: Bearer <token>
    3. Server validates JWT on every request → extracts user info
    4. No server-side session needed (STATELESS)

  JWT Structure: header.payload.signature
    Header: {"alg":"HS256","typ":"JWT"}
    Payload: {"sub":"user@example.com","roles":["ADMIN"],"iat":1234,"exp":5678}
    Signature: HMACSHA256(base64(header)+"."+base64(payload), secret)

  Implementation:

  1. JwtService (token creation and validation):
    @Service
    public class JwtService {
        @Value("${security.jwt.secret}") private String secret;
        @Value("${security.jwt.expiration}") private long expiration;

        public String generateToken(UserDetails user) {
            return Jwts.builder()
                .subject(user.getUsername())
                .claim("roles", user.getAuthorities().stream()
                    .map(GrantedAuthority::getAuthority).toList())
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + expiration))
                .signWith(getSigningKey())
                .compact();
        }

        public String extractUsername(String token) {
            return extractClaim(token, Claims::getSubject);
        }

        public boolean isTokenValid(String token, UserDetails user) {
            return extractUsername(token).equals(user.getUsername())
                   && !isTokenExpired(token);
        }

        private boolean isTokenExpired(String token) {
            return extractClaim(token, Claims::getExpiration).before(new Date());
        }

        private <T> T extractClaim(String token, Function<Claims, T> resolver) {
            Claims claims = Jwts.parser()
                .verifyWith(getSigningKey()).build()
                .parseSignedClaims(token).getPayload();
            return resolver.apply(claims);
        }

        private SecretKey getSigningKey() {
            return Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
        }
    }

  2. JwtAuthenticationFilter:
    @Component
    @RequiredArgsConstructor
    public class JwtAuthenticationFilter extends OncePerRequestFilter {

        private final JwtService jwtService;
        private final UserDetailsService userDetailsService;

        @Override
        protected void doFilterInternal(HttpServletRequest request,
                HttpServletResponse response, FilterChain chain)
                throws ServletException, IOException {

            String authHeader = request.getHeader("Authorization");
            if (authHeader == null || !authHeader.startsWith("Bearer ")) {
                chain.doFilter(request, response);
                return;
            }

            String jwt = authHeader.substring(7);
            String username = jwtService.extractUsername(jwt);

            if (username != null &&
                    SecurityContextHolder.getContext().getAuthentication() == null) {

                UserDetails user = userDetailsService.loadUserByUsername(username);

                if (jwtService.isTokenValid(jwt, user)) {
                    UsernamePasswordAuthenticationToken authToken =
                        new UsernamePasswordAuthenticationToken(
                            user, null, user.getAuthorities());
                    authToken.setDetails(
                        new WebAuthenticationDetailsSource().buildDetails(request));
                    SecurityContextHolder.getContext().setAuthentication(authToken);
                }
            }
            chain.doFilter(request, response);
        }
    }

  3. SecurityConfig (stateless + JWT filter):
    http.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);

  4. Auth endpoint:
    @PostMapping("/auth/login")
    public ResponseEntity<TokenResponse> login(@RequestBody LoginRequest req) {
        authManager.authenticate(
            new UsernamePasswordAuthenticationToken(req.username(), req.password()));
        UserDetails user = userDetailsService.loadUserByUsername(req.username());
        return ResponseEntity.ok(new TokenResponse(jwtService.generateToken(user)));
    }

Q8. What is the difference between JWT and session-based authentication?
─────────────────────────────────────────────────────────────────────────
Answer:
  Session-based:
    • Server creates session, stores it (in-memory or Redis)
    • Client receives session cookie (JSESSIONID)
    • Server looks up session on each request → STATEFUL
    • Scaling challenge: sessions must be shared (sticky sessions or session store)
    • Revocation: easy (just delete session)

  JWT:
    • Server creates a signed token; no server-side storage → STATELESS
    • Client sends token in Authorization header on each request
    • Server validates signature; no DB lookup
    • Scales horizontally (no shared state)
    • Revocation: HARD (token is valid until expiry; need blacklist for early revoke)

  Interview Tip:
    JWT is preferred for microservices / REST APIs.
    Session-based is fine for monolithic web apps.

Q9. Explain OAuth2 and its flows.
──────────────────────────────────
Answer:
  OAuth2 is an AUTHORIZATION framework that allows third-party apps to access
  resources on behalf of a user WITHOUT sharing credentials.

  Key roles:
    Resource Owner       — the user
    Client               — the application requesting access
    Authorization Server — issues tokens (Keycloak, Okta, Google, Auth0)
    Resource Server      — holds protected resources (your API)

  OAuth2 Flows (Grant Types):

  1. Authorization Code Flow (web apps):
     Client → redirects user to Auth Server
     User logs in, grants consent
     Auth Server → redirects to client with authorization code
     Client → exchanges code for access token (server-to-server, code + secret)
     Client → uses access token to call API
     MOST SECURE; code exchanged server-side; client secret never exposed.

  2. Authorization Code + PKCE (SPA / mobile):
     Like Authorization Code but without client secret.
     PKCE (Proof Key for Code Exchange) prevents code interception attacks.
     code_verifier → SHA256 hash → code_challenge sent with request.

  3. Client Credentials Flow (machine-to-machine):
     Client authenticates with its own client_id + client_secret
     Receives access token; no user involvement.
     Used for microservice-to-microservice communication.

  4. Implicit Flow (deprecated — use PKCE instead):
     Access token returned directly in redirect URL.
     Token exposed in browser history/logs.

  5. Resource Owner Password Credentials (deprecated):
     Client collects username/password directly.
     NOT recommended; only for trusted first-party apps.

  OIDC (OpenID Connect):
    Extension of OAuth2 for AUTHENTICATION (not just authorization).
    Adds ID Token (JWT) containing user identity claims:
      sub, email, name, picture, iat, exp…
    Well-known endpoint: /.well-known/openid-configuration

Q10. How do you implement OAuth2 Resource Server in Spring Security?
─────────────────────────────────────────────────────────────────────
Answer:
  A Resource Server validates JWT access tokens issued by an Authorization Server.

  Dependency:
    spring-boot-starter-oauth2-resource-server

  application.properties:
    spring.security.oauth2.resourceserver.jwt.issuer-uri=https://auth.example.com
    # OR specify JWKS URI directly:
    spring.security.oauth2.resourceserver.jwt.jwk-set-uri=https://auth.example.com/.well-known/jwks.json

  Security config:
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .jwtAuthenticationConverter(jwtAuthConverter())));
        return http.build();
    }

    @Bean
    public JwtAuthenticationConverter jwtAuthConverter() {
        JwtGrantedAuthoritiesConverter grantedAuthConverter =
            new JwtGrantedAuthoritiesConverter();
        grantedAuthConverter.setAuthorityPrefix("ROLE_");
        grantedAuthConverter.setAuthoritiesClaimName("roles");

        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(grantedAuthConverter);
        return converter;
    }

Q11. How do you implement OAuth2 Login (SSO) in Spring Security?
─────────────────────────────────────────────────────────────────
Answer:
  Spring Security supports OAuth2 Login (OIDC SSO) out of the box.

  Dependency:
    spring-boot-starter-oauth2-client

  application.yml:
    spring:
      security:
        oauth2:
          client:
            registration:
              google:
                client-id: ${GOOGLE_CLIENT_ID}
                client-secret: ${GOOGLE_CLIENT_SECRET}
                scope: openid,email,profile
              github:
                client-id: ${GITHUB_CLIENT_ID}
                client-secret: ${GITHUB_CLIENT_SECRET}

  Security config:
    http.oauth2Login(oauth2 -> oauth2
        .loginPage("/login")
        .defaultSuccessUrl("/dashboard")
        .userInfoEndpoint(ui -> ui
            .userService(customOidcUserService)));

  Custom OIDC user loading:
    @Service
    public class CustomOidcUserService extends OidcUserService {
        @Override
        public OidcUser loadUser(OidcUserRequest request) throws OAuth2AuthenticationException {
            OidcUser oidcUser = super.loadUser(request);
            // persist user to DB, map custom attributes
            return oidcUser;
        }
    }

Q12. How does Method-Level Security work in Spring Security?
────────────────────────────────────────────────────────────
Answer:
  Method security secures individual methods using annotations + AOP.
  Enable with: @EnableMethodSecurity (Spring Security 5.6+ / 6+)

  @PreAuthorize (evaluates BEFORE method invocation):
    @PreAuthorize("hasRole('ADMIN')")
    public void deleteUser(Long id) { ... }

    @PreAuthorize("hasRole('USER') and #username == authentication.principal.username")
    public UserProfile getProfile(String username) { ... }

    @PreAuthorize("hasAuthority('product:write')")
    public Product createProduct(Product p) { ... }

  @PostAuthorize (evaluates AFTER; can inspect return value):
    @PostAuthorize("returnObject.owner == authentication.name")
    public Document getDocument(Long id) { ... }

  @PreFilter (filters Collection INPUT before method):
    @PreFilter("filterObject.owner == authentication.name")
    public void deleteAll(List<Document> docs) { ... }

  @PostFilter (filters Collection RETURN VALUE):
    @PostFilter("filterObject.owner == authentication.name")
    public List<Document> getAllDocuments() { ... }

  @Secured (simpler; only roles, no SpEL):
    @Secured({"ROLE_ADMIN", "ROLE_MANAGER"})
    public void manageUsers() { ... }

  @RolesAllowed (JSR-250; portable):
    @RolesAllowed("ADMIN")
    public void deleteUser(Long id) { ... }

  Enabling @Secured and @RolesAllowed:
    @EnableMethodSecurity(securedEnabled = true, jsr250Enabled = true)

  Interview Tip: @PreAuthorize with SpEL is the most powerful and flexible.
  It's the recommended approach in Spring Security 6+.

Q13. What is CSRF and how does Spring Security handle it?
──────────────────────────────────────────────────────────
Answer:
  CSRF (Cross-Site Request Forgery):
    An attacker tricks an authenticated user's browser into making an unwanted
    request to the server (e.g., fund transfer using the user's session cookie).

  Spring Security's protection:
    The CsrfFilter requires a CSRF token in every state-changing request
    (POST, PUT, DELETE, PATCH). Token is generated per session and validated.

  How it works:
    1. Server sends a CSRF token (hidden form field or header)
    2. Browser submits token with the request
    3. Server validates the token
    4. Attacker's site cannot read the CSRF token (Same-Origin Policy)

  Disabling (for stateless REST APIs — recommended):
    http.csrf(csrf -> csrf.disable());
    // JWT tokens in Authorization header are NOT automatically sent by browsers
    // → CSRF attacks are not possible for token-based APIs

  Custom CSRF token repository (for SPA):
    http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse()));
    // Token stored in XSRF-TOKEN cookie; JS reads it and sends in X-XSRF-TOKEN header

Q14. What is CORS and how do you configure it in Spring Security?
─────────────────────────────────────────────────────────────────
Answer:
  CORS (Cross-Origin Resource Sharing):
    Browser security mechanism restricting web pages from making requests to a
    different origin (protocol + host + port) than the one that served the page.

  Spring Security CORS config:
    http.cors(cors -> cors.configurationSource(corsConfigSource()));

    @Bean
    public CorsConfigurationSource corsConfigSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of("https://frontend.example.com"));
        config.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
        config.setAllowedHeaders(List.of("Authorization","Content-Type"));
        config.setAllowCredentials(true);
        config.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }

  Spring MVC level (works alongside Security):
    @CrossOrigin(origins = "https://frontend.example.com")
    @RestController
    public class OrderController { ... }

    // Global:
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/**").allowedOrigins("https://frontend.example.com");
            }
        };
    }

  Interview Tip: Configure CORS at the Spring Security level (not just MVC)
  because preflight OPTIONS requests hit security filters before reaching MVC.

Q15. Explain Session Management in Spring Security.
────────────────────────────────────────────────────
Answer:
  Session Fixation Protection:
    After successful authentication, Spring invalidates the old session and
    creates a new one (prevents session fixation attacks).
    http.sessionManagement(s -> s.sessionFixation().newSession());

  Session Creation Policy:
    ALWAYS         — always create a session
    IF_REQUIRED    — create if needed (default for web apps)
    NEVER          — never create but use if exists
    STATELESS      — never create or use sessions (for REST APIs with JWT)

  Concurrent Session Control:
    Limits the number of concurrent sessions per user:
    http.sessionManagement(s -> s
        .maximumSessions(1)
        .maxSessionsPreventsLogin(true));  // prevent new login OR expire old
    // Also register HttpSessionEventPublisher bean

Q16. What security headers does Spring Security add by default?
───────────────────────────────────────────────────────────────
Answer:
  Spring Security's HeaderWriterFilter adds:

  X-Content-Type-Options: nosniff
    → Prevents MIME-type sniffing.

  X-Frame-Options: DENY
    → Prevents clickjacking by disallowing iframe embedding.

  X-XSS-Protection: 0
    → Modern browsers no longer need this (disabled in Spring 6).

  Cache-Control: no-cache, no-store, max-age=0, must-revalidate
  Pragma: no-cache / Expires: 0
    → Prevents caching of sensitive pages.

  Strict-Transport-Security (HSTS):
    → Forces HTTPS for subsequent requests (only added on HTTPS).

  Content Security Policy (disabled by default; configure explicitly):
    http.headers(h -> h
        .contentSecurityPolicy(csp -> csp
            .policyDirectives("default-src 'self'; script-src 'self'")));

Q17. How does Spring Security handle password encoding?
────────────────────────────────────────────────────────
Answer:
  PasswordEncoder interface:
    encode(CharSequence rawPassword) → String
    matches(CharSequence raw, String encoded) → boolean
    upgradeEncoding(String encoded) → boolean (for migration)

  Implementations:
    BCryptPasswordEncoder   — RECOMMENDED; bcrypt with strength 10-12
    Argon2PasswordEncoder   — memory-hard; most secure
    Pbkdf2PasswordEncoder   — FIPS-compliant environments
    SCryptPasswordEncoder   — scrypt algorithm
    NoOpPasswordEncoder     — plain text; ONLY for testing!

  DelegatingPasswordEncoder (default since Spring Security 5):
    Encodes with a current preferred encoder.
    Decodes any supported encoding (migration-friendly).
    Format: {bcrypt}$2a$10$...

    PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
    // Uses bcrypt by default; can decode {noop}, {pbkdf2}, {scrypt}, etc.

  Best practice:
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12); // strength 12 (2^12 iterations)
    }

    // Register:
    String encoded = passwordEncoder.encode("rawPassword");
    // Verify:
    boolean match = passwordEncoder.matches("rawPassword", encoded);

Q18. How do you implement custom UserDetailsService?
─────────────────────────────────────────────────────
Answer:
  @Service
  @RequiredArgsConstructor
  public class CustomUserDetailsService implements UserDetailsService {

      private final UserRepository userRepository;

      @Override
      public UserDetails loadUserByUsername(String username)
              throws UsernameNotFoundException {
          User user = userRepository.findByEmail(username)
              .orElseThrow(() -> new UsernameNotFoundException(
                  "User not found: " + username));

          return org.springframework.security.core.userdetails.User.builder()
              .username(user.getEmail())
              .password(user.getPassword())   // already BCrypt encoded in DB
              .roles(user.getRoles().toArray(new String[0]))
              .accountExpired(!user.isActive())
              .credentialsExpired(false)
              .disabled(!user.isEnabled())
              .build();
      }
  }

  Custom UserDetails implementation:
    public class UserPrincipal implements UserDetails {
        private final User user;
        // implement all UserDetails methods
        // plus custom methods: getUser(), getId(), etc.
    }

Q19. How does Spring Security handle security exceptions?
──────────────────────────────────────────────────────────
Answer:
  ExceptionTranslationFilter handles two types of exceptions:

  1. AuthenticationException (unauthenticated):
     → Triggers AuthenticationEntryPoint (send 401 or redirect to login)

  2. AccessDeniedException (authenticated but unauthorized):
     → Triggers AccessDeniedHandler (send 403 or redirect to error page)

  Custom handlers for REST APIs (return JSON instead of redirecting):
    http.exceptionHandling(ex -> ex
        .authenticationEntryPoint((req, resp, authEx) -> {
            resp.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            resp.setContentType("application/json");
            resp.getWriter().write("{\"error\":\"Unauthorized\"}");
        })
        .accessDeniedHandler((req, resp, accessEx) -> {
            resp.setStatus(HttpServletResponse.SC_FORBIDDEN);
            resp.setContentType("application/json");
            resp.getWriter().write("{\"error\":\"Access Denied\"}");
        }));

Q. hasRole vs hasAuthority?
  hasRole("ADMIN")       → looks for authority "ROLE_ADMIN"
  hasAuthority("ADMIN")  → looks for authority "ADMIN" (exact match)
  Roles by convention are prefixed with "ROLE_"; authorities are not.

Q. What is the difference between authenticated() and fullyAuthenticated()?
  authenticated()        → user is authenticated (including remember-me)
  fullyAuthenticated()   → user authenticated with username+password THIS session
                           (not via remember-me token)

Q. How do you get the current user in a controller?
  // Option 1: SecurityContextHolder
  Authentication auth = SecurityContextHolder.getContext().getAuthentication();

  // Option 2: @AuthenticationPrincipal (injected by Spring MVC)
  @GetMapping("/me")
  public UserProfile getMe(@AuthenticationPrincipal UserDetails user) { ... }

  // Option 3: Principal from method parameter
  @GetMapping("/me")
  public String getMe(Principal principal) { return principal.getName(); }

Q. Can you use @PreAuthorize on a class?
  Yes! It applies to ALL methods in the class.
  @PreAuthorize("isAuthenticated()")
  @RestController
  public class SecureController { ... }

Q. What is Remember-Me authentication?
  Allows users to stay logged in across browser sessions.
  Uses a persistent token (DB) or a hash-based token (default).
  http.rememberMe(rm -> rm
      .tokenValiditySeconds(86400 * 7)
      .key("mySecretKey")
      .tokenRepository(persistentTokenRepository()));

Q. How do you secure WebSocket connections?
  Use @EnableWebSocketMessageBroker and add security config:
  @Autowired void configureInbound(MessageSecurityMetadataSourceRegistry msgs) {
      msgs.simpSubscribeDestMatchers("/user/**").authenticated()
          .anyMessage().authenticated();
  }
