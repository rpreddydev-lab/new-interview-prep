SECTION 1 — AOP FUNDAMENTALS
─────────────────────────────────────────────────────────────────────────────

Q1. What is Aspect-Oriented Programming (AOP) and why is it useful?
─────────────────────────────────────────────────────────────────────
Answer:
  AOP is a programming paradigm that addresses CROSS-CUTTING CONCERNS — behaviors
  that span multiple classes/layers and would otherwise be scattered through code.

  Cross-cutting concerns examples:
    • Logging / Tracing
    • Security / Authorization
    • Transaction management
    • Performance monitoring / metrics
    • Caching
    • Exception handling / retry
    • Auditing

  Without AOP: you duplicate logging/security code in every method.
  With AOP:    you define the concern ONCE in an Aspect; it's applied automatically.

  AOP Core Concepts:
    Aspect       → The module containing cross-cutting concern (annotated @Aspect)
    Join Point   → A point during execution where an Aspect can be applied
                   (In Spring AOP: ALWAYS a method execution)
    Pointcut     → Expression that selects which Join Points to intercept
    Advice       → The ACTION to take at a matched Join Point
    Target       → The bean being intercepted (the proxy wraps it)
    Proxy        → The AOP-generated object that wraps the target
    Weaving      → Linking aspects with application objects
                   (compile-time, load-time, or runtime — Spring uses runtime)

Q2. What are the different types of Advice in Spring AOP?
──────────────────────────────────────────────────────────
Answer:
  1. @Before — runs BEFORE the method:
     @Before("execution(* com.example.service.*.*(..))")
     public void logBefore(JoinPoint jp) {
         log.info("Calling: {}.{}",
             jp.getTarget().getClass().getSimpleName(),
             jp.getSignature().getName());
     }

  2. @After — runs AFTER the method (regardless of success/failure):
     @After("execution(* com.example.service.*.*(..))")
     public void logAfter(JoinPoint jp) {
         log.info("Completed: {}", jp.getSignature().getName());
     }

  3. @AfterReturning — runs AFTER method returns SUCCESSFULLY:
     @AfterReturning(pointcut = "execution(* com.example.service.*.*(..))",
                     returning = "result")
     public void logReturn(JoinPoint jp, Object result) {
         log.info("Method {} returned: {}", jp.getSignature().getName(), result);
     }

  4. @AfterThrowing — runs AFTER method throws an EXCEPTION:
     @AfterThrowing(pointcut = "execution(* com.example.service.*.*(..))",
                    throwing = "ex")
     public void logException(JoinPoint jp, Exception ex) {
         log.error("Exception in {}: {}", jp.getSignature().getName(), ex.getMessage());
     }

  5. @Around — wraps the method; most powerful; MUST call proceed():
     @Around("execution(* com.example.service.*.*(..))")
     public Object measureTime(ProceedingJoinPoint pjp) throws Throwable {
         long start = System.currentTimeMillis();
         try {
             Object result = pjp.proceed();  // call the actual method
             return result;
         } finally {
             long elapsed = System.currentTimeMillis() - start;
             log.info("{} took {} ms", pjp.getSignature().getName(), elapsed);
         }
     }

  Advice execution order (for a single method):
    @Around (before proceed)
      → @Before
        → Method executes
      → @AfterReturning / @AfterThrowing
    → @After
    → @Around (after proceed)

Q3. What is a Pointcut Expression?
────────────────────────────────────
Answer:
  Pointcut expressions define WHICH methods to intercept.

  execution (most common):
    Pattern: execution([modifier] return-type [declaring-type].method-name(params) [throws])

    // All methods in package (any return type, any class, any method, any args):
    execution(* com.example.service.*.*(..))

    // Specific method:
    execution(public void com.example.OrderService.placeOrder(..))

    // Any method starting with "find":
    execution(* find*(..))

    // Any method with a single String parameter:
    execution(* *(String))

    // Any method in OrderService or its subclasses:
    execution(* com.example.OrderService+.*(..))

  within (type-level; all methods in a class/package):
    within(com.example.service.*)        // all methods in service package
    within(com.example.service..*)       // service package + subpackages

  @annotation (methods annotated with a specific annotation):
    @annotation(org.springframework.transaction.annotation.Transactional)
    @annotation(com.example.annotation.Loggable)

  @within (class annotated with annotation):
    @within(org.springframework.stereotype.Service)

  args (methods with specific argument types):
    args(String, ..)     // first arg is String, any subsequent

  bean (Spring-specific; by bean name):
    bean(orderService)
    bean(*Service)       // beans ending in "Service"

  Combining with &&, ||, !:
    execution(* com.example.service.*.*(..)) && !execution(* find*(..))

  Named Pointcut (reusable):
    @Aspect
    @Component
    public class LoggingAspect {

        @Pointcut("execution(* com.example.service.*.*(..))")
        public void serviceLayer() {}

        @Pointcut("execution(* com.example.repository.*.*(..))")
        public void repositoryLayer() {}

        @Pointcut("serviceLayer() || repositoryLayer()")
        public void appLayer() {}

        @Before("appLayer()")
        public void logEntry(JoinPoint jp) { ... }
    }

Q4. How does Spring AOP work internally (proxy mechanism)?
───────────────────────────────────────────────────────────
Answer:
  Spring AOP uses RUNTIME WEAVING via proxies. Two proxy types:

  1. JDK Dynamic Proxy (default when target implements an interface):
     - Creates a proxy implementing the SAME interface(s) as the target
     - Uses java.lang.reflect.Proxy
     - Only interface methods can be intercepted

  2. CGLIB Proxy (when target does NOT implement an interface):
     - Creates a SUBCLASS of the target class at runtime
     - Uses byte-buddy (Spring 5+, was CGLIB before)
     - Cannot proxy final classes or final methods
     - Default in Spring Boot for @Configuration classes
     - Can be forced: @EnableAspectJAutoProxy(proxyTargetClass = true)

  Proxy creation:
    When Spring creates a bean, BeanPostProcessors check if any aspect matches.
    AbstractAutoProxyCreator wraps the bean in a proxy.

  How advice chain works:
    Call → Proxy → Interceptor chain (advisors) → Target method

  Self-invocation limitation:
    Calling a method from within the SAME class does NOT go through the proxy.
    → @Transactional, @Cacheable, @Async advice has NO EFFECT on self-calls!
    Solution: inject self as a dependency, use ApplicationContext.getBean(),
    or use AspectJ weaving.

Q5. Spring AOP vs AspectJ — what's the difference?
────────────────────────────────────────────────────
Answer:
  Spring AOP:
    • Runtime proxy-based weaving
    • Only method execution join points
    • Only Spring beans can be advised
    • Simpler; no special compiler/agent needed
    • Sufficient for 90% of enterprise use cases

  AspectJ:
    • Compile-time / post-compile / load-time weaving
    • ALL join points: field access, constructor, exception handler, etc.
    • ANY Java object (not just Spring beans)
    • Requires AspectJ compiler (ajc) or Java agent (-javaagent)
    • More powerful but more complex

  Spring can USE AspectJ annotations (@Aspect, @Pointcut, @Before, etc.)
  while still using its own proxy-based engine — this is the standard approach.

  Using full AspectJ in Spring Boot:
    @EnableLoadTimeWeaving(aspectjWeaving = ENABLED)
    + JVM argument: -javaagent:aspectjweaver.jar

Q6. How do you implement a custom @Loggable annotation with AOP?
─────────────────────────────────────────────────────────────────
Answer:
  Step 1: Define the annotation:
    @Target(ElementType.METHOD)
    @Retention(RetentionPolicy.RUNTIME)
    public @interface Loggable {
        boolean logArgs() default true;
        boolean logResult() default false;
    }

  Step 2: Create the aspect:
    @Aspect
    @Component
    @Slf4j
    public class LoggingAspect {

        @Around("@annotation(loggable)")
        public Object log(ProceedingJoinPoint pjp, Loggable loggable) throws Throwable {
            String method = pjp.getSignature().toShortString();

            if (loggable.logArgs()) {
                log.info("[ENTER] {} args={}", method, Arrays.toString(pjp.getArgs()));
            } else {
                log.info("[ENTER] {}", method);
            }

            try {
                Object result = pjp.proceed();
                if (loggable.logResult()) {
                    log.info("[EXIT] {} result={}", method, result);
                } else {
                    log.info("[EXIT] {}", method);
                }
                return result;
            } catch (Throwable e) {
                log.error("[ERROR] {} threw: {}", method, e.getMessage());
                throw e;
            }
        }
    }

  Step 3: Use the annotation:
    @Loggable(logArgs = true, logResult = true)
    public Order placeOrder(OrderRequest request) { ... }

Q7. How do you control the order of multiple aspects?
──────────────────────────────────────────────────────
Answer:
  When multiple aspects apply to the same join point, use @Order:

  @Aspect @Component @Order(1) class SecurityAspect    { ... } // first
  @Aspect @Component @Order(2) class LoggingAspect     { ... } // second
  @Aspect @Component @Order(3) class TransactionAspect { ... } // third

  Lower @Order value = HIGHER priority (runs outermost in @Around).

  For @Before: lower order = runs first.
  For @After / @AfterReturning: lower order = runs LAST (outermost returns last).

Q8. What is @EnableAspectJAutoProxy?
──────────────────────────────────────
Answer:
  Enables Spring's AOP infrastructure to process @Aspect classes.
  Added automatically by spring-boot-starter-aop.

  @Configuration
  @EnableAspectJAutoProxy
  public class AppConfig { }

  proxyTargetClass = true:
    Forces CGLIB proxies even when interfaces exist.
    @EnableAspectJAutoProxy(proxyTargetClass = true)

  exposeProxy = true:
    Makes the proxy accessible via AopContext.currentProxy()
    Allows self-invocation to go through the proxy:
    ((MyService) AopContext.currentProxy()).transactionalMethod();

─────────────────────────────────────────────────────────────────────────────

Q9. What is Reactive Programming and why does it matter?
──────────────────────────────────────────────────────────
Answer:
  Reactive Programming is an asynchronous, non-blocking programming paradigm
  based on data streams and propagation of change.

  Traditional (blocking):
    Thread requests data → Thread WAITS (blocked) → Data arrives → Thread continues
    Each concurrent request needs its own thread → limited by thread pool size

  Reactive (non-blocking):
    Thread registers callback → Thread is FREE to handle other work
    Data arrives → Thread is notified/scheduled → Continues processing
    Few threads handle thousands of concurrent connections (event loop model)

  Benefits:
    • Higher throughput with fewer threads
    • Better resource utilization
    • Backpressure support (consumer controls data flow speed)
    • Natural fit for streaming, real-time, high-concurrency scenarios

  Reactive Streams Specification (Java 9+):
    Publisher<T>     → produces data; honors backpressure
    Subscriber<T>    → consumes data
    Subscription     → connection between Publisher and Subscriber; request(n)
    Processor<T,R>   → both Publisher and Subscriber (transformation)

Q10. What is Project Reactor? Explain Mono and Flux.
──────────────────────────────────────────────────────
Answer:
  Project Reactor is the reactive library used by Spring WebFlux.
  It implements Reactive Streams specification.

  Mono<T>:
    A publisher that emits 0 or 1 item, then completes or errors.
    Like Optional<T> but async and reactive.

    Mono<String> name = Mono.just("Alice");
    Mono<String> empty = Mono.empty();
    Mono<String> error = Mono.error(new RuntimeException("fail"));
    Mono<String> deferred = Mono.fromCallable(() -> expensiveOp());
    Mono<String> fromFuture = Mono.fromFuture(someCompletableFuture);

  Flux<T>:
    A publisher that emits 0 to N items, then completes or errors.
    Like Stream<T> but async, reactive, with backpressure.

    Flux<Integer> numbers = Flux.just(1, 2, 3, 4, 5);
    Flux<Integer> range = Flux.range(1, 100);
    Flux<Integer> infinite = Flux.generate(sink -> sink.next(random.nextInt()));
    Flux<Long> ticks = Flux.interval(Duration.ofSeconds(1));  // emit 0,1,2... every sec

  Nothing happens until you SUBSCRIBE:
    name.subscribe(
        value   -> System.out.println("Got: " + value),
        error   -> System.err.println("Error: " + error),
        ()      -> System.out.println("Complete!")
    );

  Interview Tip:
    Mono = 0 or 1 element (findById, save, authenticate)
    Flux = 0 to N elements (findAll, streaming data, events)

Q11. What are common Reactor operators?
────────────────────────────────────────
Answer:
  TRANSFORMATION:
    map(fn)          → synchronous 1-to-1 transformation
    flatMap(fn)      → async 1-to-0..N; merges inner publishers (concurrent)
    concatMap(fn)    → like flatMap but preserves ORDER (sequential)
    flatMapMany(fn)  → Mono → Flux (expand one item to many)
    switchMap(fn)    → cancels previous inner publisher on new emission

  FILTERING:
    filter(predicate)        → keep matching items
    take(n)                  → take first N items
    skip(n)                  → skip first N items
    distinct()               → deduplicate
    distinctUntilChanged()   → deduplicate consecutive

  COMBINING:
    merge(p1, p2)            → interleave emissions from multiple publishers
    concat(p1, p2)           → sequential: p1 completes, then p2 starts
    zip(p1, p2, fn)          → pair emissions from two publishers
    combineLatest(p1, p2)    → combine latest from each when any emits

  ERROR HANDLING:
    onErrorReturn(fallback)         → return fallback value on error
    onErrorResume(fn)               → switch to fallback publisher on error
    onErrorMap(fn)                  → transform exception
    doOnError(consumer)             → side-effect on error (log, etc.)
    retry(n)                        → retry n times on error
    retryWhen(spec)                 → advanced retry with backoff
    timeout(Duration)               → error if no emission within duration

  SIDE EFFECTS (no value modification):
    doOnNext(consumer)    → peek at each element
    doOnComplete(fn)      → on stream completion
    doOnSubscribe(fn)     → on subscription
    doOnTerminate(fn)     → on complete or error
    log()                 → log all signals (debug)

  CONTEXT:
    subscribeOn(Scheduler) → which scheduler handles subscription + upstream
    publishOn(Scheduler)   → which scheduler handles downstream processing

  BLOCKING BRIDGING:
    .block()               → blocks until Mono completes (NEVER in reactive chain!)
    .toIterable()          → convert Flux to Iterable (blocking)
    .collectList()         → Flux<T> → Mono<List<T>>

  Example:
    Flux.range(1, 10)
        .filter(n -> n % 2 == 0)          // 2, 4, 6, 8, 10
        .map(n -> n * n)                   // 4, 16, 36, 64, 100
        .doOnNext(n -> log.info("n={}", n))
        .collectList()                     // Mono<List<Integer>>
        .subscribe(list -> log.info("Result: {}", list));

Q12. What is Backpressure?
───────────────────────────
Answer:
  Backpressure is the mechanism by which a SUBSCRIBER controls how much data
  it requests from the PUBLISHER. Prevents the subscriber from being overwhelmed.

  In Reactive Streams: Subscriber.request(n) — "give me n more items."

  Backpressure strategies in Reactor:
    BUFFER    — buffer overflow items (default; OOM risk if unbounded)
    DROP      — drop items when buffer full
    LATEST    — keep only the latest item when buffer full
    ERROR     — throw OverflowException when buffer full

  onBackpressureBuffer():
    flux.onBackpressureBuffer(1000, item -> log.warn("Dropping: {}", item),
                              BufferOverflowStrategy.DROP_LATEST)

  onBackpressureDrop():
    flux.onBackpressureDrop(dropped -> log.warn("Dropped: {}", dropped))

  In Spring WebFlux, backpressure is handled transparently by the HTTP protocol
  (TCP flow control) and Netty's event loop.

Q13. What are Schedulers in Project Reactor?
─────────────────────────────────────────────
Answer:
  Schedulers determine WHICH THREAD executes parts of the reactive pipeline.

  Schedulers.boundedElastic():
    • Elastically growing thread pool with a max bound
    • For I/O blocking operations (file I/O, blocking legacy code)
    • Default cap: 10 * CPU cores; max queue per thread: 100k

  Schedulers.parallel():
    • Fixed thread pool = number of CPU cores
    • For CPU-intensive computation

  Schedulers.single():
    • Single reusable thread
    • For lightweight, non-blocking tasks

  Schedulers.immediate():
    • Executes on current thread (no scheduling)

  subscribeOn(Scheduler):
    Affects WHERE the subscription and upstream processing happens.
    Only ONE subscribeOn per chain (the one closest to source wins).

  publishOn(Scheduler):
    Affects WHERE DOWNSTREAM operators run (from this point).
    Multiple publishOn can switch threads mid-pipeline.

  Example:
    Flux.just("path1", "path2", "path3")
        .publishOn(Schedulers.boundedElastic())   // downstream runs on I/O scheduler
        .map(path -> readFile(path))              // blocking file read → OK here
        .publishOn(Schedulers.parallel())         // switch to compute scheduler
        .map(content -> processContent(content))  // CPU work
        .subscribe(result -> log.info(result));

Q14. How do you implement a reactive REST controller with Spring WebFlux?
──────────────────────────────────────────────────────────────────────────
Answer:
  Annotation-based controller (familiar):
    @RestController
    @RequiredArgsConstructor
    @RequestMapping("/api/users")
    public class UserController {

        private final UserService userService;

        @GetMapping
        public Flux<UserDTO> getAllUsers() {
            return userService.findAll();
        }

        @GetMapping("/{id}")
        public Mono<ResponseEntity<UserDTO>> getUserById(@PathVariable Long id) {
            return userService.findById(id)
                .map(ResponseEntity::ok)
                .defaultIfEmpty(ResponseEntity.notFound().build());
        }

        @PostMapping
        @ResponseStatus(HttpStatus.CREATED)
        public Mono<UserDTO> createUser(@Valid @RequestBody Mono<CreateUserRequest> req) {
            return req.flatMap(userService::create);
        }

        @DeleteMapping("/{id}")
        @ResponseStatus(HttpStatus.NO_CONTENT)
        public Mono<Void> deleteUser(@PathVariable Long id) {
            return userService.delete(id);
        }

        // Server-Sent Events (SSE) streaming:
        @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
        public Flux<UserDTO> streamUsers() {
            return userService.findAll().delayElements(Duration.ofMillis(100));
        }
    }

  Functional routing (alternative to annotations):
    @Configuration
    public class UserRouter {

        @Bean
        public RouterFunction<ServerResponse> routes(UserHandler handler) {
            return RouterFunctions.route()
                .GET("/api/users", handler::getAllUsers)
                .GET("/api/users/{id}", handler::getUserById)
                .POST("/api/users", handler::createUser)
                .DELETE("/api/users/{id}", handler::deleteUser)
                .build();
        }
    }

    @Component
    public class UserHandler {

        private final UserService userService;

        public Mono<ServerResponse> getAllUsers(ServerRequest request) {
            return ServerResponse.ok()
                .contentType(MediaType.APPLICATION_JSON)
                .body(userService.findAll(), UserDTO.class);
        }

        public Mono<ServerResponse> getUserById(ServerRequest request) {
            Long id = Long.valueOf(request.pathVariable("id"));
            return userService.findById(id)
                .flatMap(user -> ServerResponse.ok().bodyValue(user))
                .switchIfEmpty(ServerResponse.notFound().build());
        }
    }

Q15. How do you handle errors in reactive streams?
────────────────────────────────────────────────────
Answer:
  Error handling operators:

  1. onErrorReturn — fallback value:
     userService.findById(id)
         .onErrorReturn(new UserDTO("default", "user"));

  2. onErrorResume — fallback publisher:
     userService.findById(id)
         .onErrorResume(UserNotFoundException.class,
             ex -> Mono.just(UserDTO.anonymous()));

  3. onErrorMap — transform the error:
     databaseCall()
         .onErrorMap(DataAccessException.class,
             ex -> new ServiceException("DB error", ex));

  4. doOnError — side effect (logging) without handling:
     databaseCall()
         .doOnError(ex -> log.error("DB call failed", ex));

  5. retry — retry on error:
     httpCall()
         .retry(3)
         .retryWhen(Retry.backoff(3, Duration.ofSeconds(1))
             .filter(ex -> ex instanceof IOException)
             .onRetryExhaustedThrow((spec, signal) ->
                 new ServiceUnavailableException()));

  Global error handling in WebFlux:
    @Component
    public class GlobalErrorHandler implements WebExceptionHandler {
        @Override
        public Mono<Void> handle(ServerWebExchange exchange, Throwable ex) {
            exchange.getResponse().setStatusCode(HttpStatus.INTERNAL_SERVER_ERROR);
            byte[] bytes = ("Error: " + ex.getMessage()).getBytes();
            DataBuffer buffer = exchange.getResponse().bufferFactory().wrap(bytes);
            return exchange.getResponse().writeWith(Mono.just(buffer));
        }
    }

    // Or using @ControllerAdvice with ResponseEntityExceptionHandler:
    @RestControllerAdvice
    public class ReactiveExceptionHandler {
        @ExceptionHandler(UserNotFoundException.class)
        @ResponseStatus(HttpStatus.NOT_FOUND)
        public Mono<ErrorResponse> handleNotFound(UserNotFoundException ex) {
            return Mono.just(new ErrorResponse(404, ex.getMessage()));
        }
    }

Q16. How do you use Spring Data R2DBC for reactive database access?
────────────────────────────────────────────────────────────────────
Answer:
  R2DBC (Reactive Relational Database Connectivity) is the reactive alternative
  to JDBC. Fully non-blocking.

  Dependency:
    spring-boot-starter-data-r2dbc
    r2dbc-postgresql (or r2dbc-h2 for testing)

  application.properties:
    spring.r2dbc.url=r2dbc:postgresql://localhost:5432/mydb
    spring.r2dbc.username=user
    spring.r2dbc.password=secret

  Entity (NO @Entity! Use plain class):
    @Table("users")
    public class User {
        @Id private Long id;
        private String name;
        private String email;
    }

  Repository:
    @Repository
    public interface UserRepository extends ReactiveCrudRepository<User, Long> {
        Flux<User> findByEmail(String email);
        Mono<User> findFirstByOrderByCreatedAtDesc();

        @Query("SELECT * FROM users WHERE active = :active")
        Flux<User> findByActive(boolean active);
    }

  Service:
    @Service
    @RequiredArgsConstructor
    public class UserService {
        private final UserRepository userRepository;

        @Transactional  // Reactive @Transactional (uses ReactiveTransactionManager)
        public Mono<User> create(CreateUserRequest req) {
            return userRepository.save(new User(req.name(), req.email()));
        }
    }

  Note: R2DBC does NOT support JPA features (lazy loading, cascades, JPQL).
  For complex queries, use @Query with SQL or DatabaseClient.

Q17. How do you test reactive code with StepVerifier?
──────────────────────────────────────────────────────
Answer:
  StepVerifier is the testing utility from Reactor Test (reactor-test library).

  Basic test:
    @Test
    void testFlux() {
        Flux<Integer> source = Flux.just(1, 2, 3);

        StepVerifier.create(source)
            .expectNext(1)
            .expectNext(2)
            .expectNext(3)
            .expectComplete()
            .verify();
    }

  Testing errors:
    @Test
    void testError() {
        Mono<String> source = Mono.error(new RuntimeException("boom"));

        StepVerifier.create(source)
            .expectErrorMessage("boom")
            .verify();
    }

  Testing with virtual time (for delays):
    @Test
    void testDelay() {
        Flux<Long> source = Flux.interval(Duration.ofSeconds(1)).take(3);

        StepVerifier.withVirtualTime(() -> source)
            .thenAwait(Duration.ofSeconds(3))
            .expectNext(0L, 1L, 2L)
            .expectComplete()
            .verify();
    }

  Testing WebFlux endpoints:
    @WebFluxTest(UserController.class)
    class UserControllerTest {

        @Autowired private WebTestClient webTestClient;
        @MockBean  private UserService userService;

        @Test
        void shouldReturnUser() {
            given(userService.findById(1L)).willReturn(
                Mono.just(new UserDTO("Alice", "alice@example.com")));

            webTestClient.get().uri("/api/users/1")
                .exchange()
                .expectStatus().isOk()
                .expectBody(UserDTO.class)
                .value(user -> assertThat(user.getName()).isEqualTo("Alice"));
        }
    }

Q18. What is WebClient and how is it used?
────────────────────────────────────────────
Answer:
  WebClient is the reactive HTTP client in Spring WebFlux (replaces RestTemplate
  for reactive applications; also usable in MVC apps).

  @Bean
  public WebClient webClient(WebClient.Builder builder) {
      return builder
          .baseUrl("https://api.example.com")
          .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
          .defaultHeader(HttpHeaders.AUTHORIZATION, "Bearer " + apiKey)
          .codecs(c -> c.defaultCodecs().maxInMemorySize(16 * 1024 * 1024))
          .build();
  }

  GET request:
    Mono<UserDTO> user = webClient.get()
        .uri("/users/{id}", userId)
        .retrieve()
        .bodyToMono(UserDTO.class);

  GET list:
    Flux<UserDTO> users = webClient.get()
        .uri("/users")
        .retrieve()
        .bodyToFlux(UserDTO.class);

  POST request:
    Mono<OrderDTO> order = webClient.post()
        .uri("/orders")
        .bodyValue(new CreateOrderRequest(...))
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError,
            resp -> resp.bodyToMono(String.class).map(RuntimeException::new))
        .bodyToMono(OrderDTO.class);

  With retry and timeout:
    webClient.get()
        .uri("/users/{id}", id)
        .retrieve()
        .bodyToMono(UserDTO.class)
        .timeout(Duration.ofSeconds(5))
        .retryWhen(Retry.backoff(3, Duration.ofSeconds(1)));

  WebClient vs RestTemplate:
    RestTemplate — synchronous, blocking; each call blocks a thread
    WebClient    — asynchronous, non-blocking; releases thread while waiting

AOP Tricky Questions:
─────────────────────
Q. Why doesn't @Transactional work when I call a method from within the same class?
  Because @Transactional uses AOP proxy. Same-class calls bypass the proxy.
  Fix: inject self-reference OR use @EnableAspectJAutoProxy(exposeProxy=true)
  and call ((MyService)AopContext.currentProxy()).method()

Q. Can you apply AOP to Spring Boot's own beans?
  Yes, if they are managed by Spring's ApplicationContext.

Q. What happens if you DON'T call pjp.proceed() in @Around?
  The original method is NEVER called. Useful for caching (return from cache
  without executing the method), but dangerous if done unintentionally.

Q. What's the difference between @After and @AfterReturning?
  @After     → runs always (like finally block) — success or exception
  @AfterReturning → only runs on SUCCESSFUL return (not thrown exception)

Q. Can you access method arguments in @Before advice?
  Yes, via JoinPoint.getArgs():
  @Before("execution(* placeOrder(..))")
  public void log(JoinPoint jp) {
      Object[] args = jp.getArgs();  // array of method arguments
  }
  Or via args() pointcut:
  @Before("execution(* placeOrder(..)) && args(request)")
  public void log(OrderRequest request) { ... }

Reactive Tricky Questions:
───────────────────────────
Q. What is the difference between map and flatMap in Reactor?
  map(fn)    → fn returns T (synchronous, direct value); wraps in same publisher type
  flatMap(fn) → fn returns Publisher<T> (async; inner publishers merged)

  Flux.just(1,2,3).map(n -> n * 2)          // sync: 2, 4, 6
  Flux.just(1,2,3).flatMap(n -> dbCall(n))  // async: results in any order

Q. What is cold vs hot publisher?
  Cold publisher: produces data fresh for EACH subscriber (e.g., Flux.fromIterable)
    Each subscriber gets the full stream from the beginning.
  Hot publisher: produces data regardless of subscribers (e.g., Flux.interval)
    Subscribers joining late miss earlier emissions.
  
  Convert cold to hot:
    flux.publish().connect()  → ConnectableFlux
    flux.share()              → multicasts to all current subscribers

Q. What does .block() do and when should you use it?
  .block() subscribes and blocks the calling thread until the Mono/Flux completes.
  NEVER call .block() inside a reactive pipeline — causes thread starvation.
  Only acceptable at the boundary (main method, test code, legacy bridging).

Q. What is Context in Project Reactor?
  Context is an immutable key-value store propagated through the reactive pipeline
  (like ThreadLocal but for reactive chains).
  Used for: security context, trace IDs, correlation IDs.
  
  // Write:
  Mono<String> withCtx = mono.contextWrite(Context.of("userId", userId));
  // Read:
  Mono.deferContextual(ctx -> {
      String userId = ctx.get("userId");
      return Mono.just("Processing for " + userId);
  });

Q. How is SecurityContext propagated in reactive applications?
  Spring Security provides ReactiveSecurityContextHolder:
  Mono<String> userId = ReactiveSecurityContextHolder.getContext()
      .map(ctx -> ctx.getAuthentication().getName());
  
  Must propagate via Reactor Context (SecurityContext stored in context key).

  Mono<T>        → 0 or 1 element async publisher
  Flux<T>        → 0 to N elements async publisher
  map            → sync transformation (T → T)
  flatMap        → async transformation (T → Publisher<T>); concurrent, no order guarantee
  concatMap      → async transformation; preserves ORDER (sequential)
  filter         → keep matching items
  zip            → combine emissions from multiple publishers pairwise
  merge          → interleave multiple publishers concurrently
  onErrorReturn  → fallback value on error
  onErrorResume  → fallback publisher on error
  retry(n)       → retry n times; retryWhen() for backoff
  subscribeOn    → where subscription + upstream work runs
  publishOn      → where downstream work runs (can switch mid-chain)
  Schedulers:    → boundedElastic (I/O blocking) | parallel (CPU) | single
  Cold publisher → fresh data per subscriber
  Hot publisher  → shared data; late subscribers miss past emissions
  Backpressure   → subscriber.request(n); BUFFER/DROP/LATEST/ERROR strategies
  StepVerifier   → testing reactive streams (expectNext, expectError, verify)
  WebClient      → non-blocking HTTP client (replaces RestTemplate in reactive)
  WebTestClient  → testing WebFlux controllers (reactive MockMvc equivalent)
  .block()       → NEVER in reactive chain; only at boundaries/tests
  R2DBC          → reactive relational DB (non-blocking; no JPA features)
  SSE            → produces = MediaType.TEXT_EVENT_STREAM_VALUE; returns Flux
  Context        → Reactor's immutable ThreadLocal alternative for reactive chains
