Q1. What is Spring Boot and what problems does it solve?
─────────────────────────────────────────────────────────
Answer:
  Spring Boot is an opinionated extension of the Spring Framework that provides:
    1. Auto-configuration: Automatically configures beans based on classpath
    2. Starters: Curated dependency bundles via single pom.xml entries
    3. Embedded server: No external Tomcat/Jetty needed; package as JAR
    4. Production-ready features: Actuator endpoints for metrics, health, etc.
    5. Externalized configuration: Flexible property management

  Problems solved:
    • Eliminates boilerplate Spring XML/Java configuration
    • Resolves dependency version conflicts (BOM management)
    • Simplifies deployment (fat JAR → java -jar app.jar)
    • Reduces time-to-production for microservices

Q2. How does Spring Boot Auto-Configuration work?
──────────────────────────────────────────────────
Answer:
  Auto-configuration is the heart of Spring Boot. It works through:

  1. @EnableAutoConfiguration (included in @SpringBootApplication):
     Triggers auto-configuration scanning.

  2. META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
     (Spring Boot 2.7+; previously META-INF/spring.factories):
     Lists all auto-configuration classes to be considered.

  3. Each AutoConfiguration class:
     - Is annotated with @AutoConfiguration (or @Configuration)
     - Uses @ConditionalOn* to decide whether to apply itself

  Example — DataSourceAutoConfiguration:
    @AutoConfiguration
    @ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
    @ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
    @EnableConfigurationProperties(DataSourceProperties.class)
    @Import({ DataSourcePoolMetadataProvidersConfiguration.class,
              DataSourceCheckpointRestoreConfiguration.class })
    public class DataSourceAutoConfiguration { ... }

  Conditional annotations used:
    @ConditionalOnClass          — apply if class is on classpath
    @ConditionalOnMissingClass   — apply if class is NOT on classpath
    @ConditionalOnBean           — apply if bean exists
    @ConditionalOnMissingBean    — apply if bean does NOT exist (most common!)
    @ConditionalOnProperty       — apply based on property value
    @ConditionalOnResource       — apply if resource exists
    @ConditionalOnWebApplication — apply if web app context
    @ConditionalOnJava           — apply based on JVM version

  Debug auto-configuration:
    Run with --debug flag or set:
      logging.level.org.springframework.boot.autoconfigure=DEBUG
    Or use Actuator: GET /actuator/conditions

Q3. What is @SpringBootApplication?
─────────────────────────────────────
Answer:
  @SpringBootApplication is a convenience meta-annotation combining:

  @SpringBootConfiguration  — equivalent to @Configuration (marks the class as
                               the primary configuration source)
  @EnableAutoConfiguration  — enables Spring Boot's auto-configuration mechanism
  @ComponentScan            — scans the package of the annotated class and
                               sub-packages for Spring components

  Equivalent to:
    @Configuration
    @EnableAutoConfiguration
    @ComponentScan("com.example")

  Customization:
    @SpringBootApplication(
        exclude = { DataSourceAutoConfiguration.class },
        scanBasePackages = { "com.example.app", "com.example.security" }
    )

Q4. What are Spring Boot Starters?
────────────────────────────────────
Answer:
  Starters are opinionated dependency descriptors — Maven/Gradle POMs that bring
  in a group of related dependencies with compatible, tested versions.

  Common starters:
    spring-boot-starter-web         → Tomcat + Spring MVC + Jackson
    spring-boot-starter-data-jpa    → Hibernate + Spring Data JPA + JDBC
    spring-boot-starter-security    → Spring Security core
    spring-boot-starter-test        → JUnit 5 + Mockito + AssertJ + MockMvc
    spring-boot-starter-actuator    → Production monitoring endpoints
    spring-boot-starter-cache       → Spring Cache abstraction
    spring-boot-starter-aop         → AspectJ + Spring AOP
    spring-boot-starter-mail        → JavaMailSender
    spring-boot-starter-redis       → Lettuce (Redis client) + Spring Data Redis
    spring-boot-starter-kafka       → Spring Kafka
    spring-boot-starter-webflux     → Reactor Netty + Spring WebFlux
    spring-boot-starter-validation  → Hibernate Validator (Bean Validation)

  Custom starter creation:
    autoconfigure module: holds auto-configuration classes
    starter module:       pom/gradle file with dependencies on autoconfigure +
                          user-facing deps
    Register in:          META-INF/spring/...AutoConfiguration.imports

Q5. What is the difference between spring-boot-starter-web and spring-boot-starter-webflux?
────────────────────────────────────────────────────────────────────────────────────────────
Answer:
  spring-boot-starter-web:
    • Servlet-based (blocking I/O)
    • Embedded Tomcat (default), Jetty, or Undertow
    • Spring MVC framework
    • Thread-per-request model
    • Uses @RestController, @GetMapping, etc.

  spring-boot-starter-webflux:
    • Reactive, non-blocking I/O
    • Embedded Netty (default) or Tomcat/Jetty/Undertow
    • Spring WebFlux framework
    • Event-loop model (fewer threads, high concurrency)
    • Uses @RestController OR functional routing (RouterFunction)
    • Returns Mono<T> and Flux<T> (Reactor types)

  Cannot use both simultaneously (conflict); choose based on app needs.

Q6. How does Spring Boot externalized configuration work?
──────────────────────────────────────────────────────────
Answer:
  Spring Boot supports many configuration sources with a defined priority order
  (higher number = higher precedence):

   1. Default properties (from SpringApplication.setDefaultProperties)
   2. @PropertySource annotations on @Configuration classes
   3. Config data (application.properties / application.yml)
   4. RandomValuePropertySource (random.* properties)
   5. OS environment variables
   6. Java System properties (System.getProperties())
   7. JNDI attributes
   8. ServletContext / ServletConfig init parameters
   9. Command-line arguments (--key=value)  ← HIGHEST

  File loading order (same precedence level, last wins):
    application.properties (default)
    application-{profile}.properties (profile-specific, OVERRIDES default)

  Config file locations searched:
    1. file:./config/   (current dir /config)
    2. file:./          (current dir)
    3. classpath:/config/
    4. classpath:/      (lowest)

Q7. What is @ConfigurationProperties?
──────────────────────────────────────
Answer:
  @ConfigurationProperties binds external properties to a POJO, providing
  type-safe, IDE-friendly configuration.

  application.properties:
    app.mail.host=smtp.gmail.com
    app.mail.port=587
    app.mail.username=user@gmail.com
    app.mail.retry-attempts=3

  @ConfigurationProperties(prefix = "app.mail")
  @Component                          // or use @EnableConfigurationProperties
  @Validated                          // enables JSR-303 validation
  public class MailProperties {
      @NotBlank private String host;
      @Min(1) @Max(65535) private int port;
      private String username;
      private int retryAttempts;
      // getters and setters
  }

  vs @Value:
    @Value("${app.mail.host}")      → per-field; no type safety; no IDe support
    @ConfigurationProperties        → full POJO; type-safe; IDE autocomplete
                                      with spring-boot-configuration-processor

  Record support (Spring Boot 2.6+):
    @ConfigurationProperties("app.mail")
    public record MailProperties(String host, int port) {}

Q8. How do Spring Profiles work in Spring Boot?
─────────────────────────────────────────────────
Answer:
  Profiles activate different beans and configurations per environment.

  Profile-specific properties files:
    application.properties            — common
    application-dev.properties        — dev-specific (overrides common)
    application-prod.properties       — prod-specific

  Activation:
    application.properties:     spring.profiles.active=dev
    Environment variable:       SPRING_PROFILES_ACTIVE=prod
    Command line:               --spring.profiles.active=prod
    Programmatic:               SpringApplication.setAdditionalProfiles("dev")

  Profile groups (Spring Boot 2.4+):
    spring.profiles.group.prod=prod-db,prod-cache,prod-metrics
    Activating "prod" activates all three.

  @Profile on beans:
    @Service @Profile("dev")  class MockEmailService implements EmailService { }
    @Service @Profile("prod") class RealEmailService implements EmailService { }

  @Profile("!test") — active in all profiles EXCEPT test.

Q9. What is Spring Boot's application.yml vs application.properties?
─────────────────────────────────────────────────────────────────────
Answer:
  Both serve the same purpose; YAML supports nested structure and multi-profile
  documents in a single file.

  application.properties:
    spring.datasource.url=jdbc:mysql://localhost/db
    spring.datasource.username=root
    spring.datasource.password=secret

  application.yml equivalent:
    spring:
      datasource:
        url: jdbc:mysql://localhost/db
        username: root
        password: secret

  Multi-profile YAML (deprecated Spring Boot 2.4; use profile-specific files):
    ---
    spring:
      config:
        activate:
          on-profile: dev
    server:
      port: 8080
    ---
    spring:
      config:
        activate:
          on-profile: prod
    server:
      port: 80

  Tip: YAML cannot be loaded with @PropertySource; use @ConfigurationProperties
  or spring.config.import instead.

Q10. What is Spring Boot Actuator?
────────────────────────────────────
Answer:
  Actuator provides production-ready features to monitor and manage a Spring Boot
  application via HTTP endpoints or JMX.

  Dependency:
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

  Key endpoints (accessible at /actuator/{endpoint}):

    /actuator/health        → app health + custom indicators
    /actuator/info          → app metadata (git commit, build info)
    /actuator/metrics       → Micrometer metrics (counter, timer, gauge)
    /actuator/env           → all environment properties (sensitive!)
    /actuator/beans         → all Spring beans in context
    /actuator/mappings      → all @RequestMapping URLs
    /actuator/conditions    → auto-configuration report
    /actuator/configprops   → all @ConfigurationProperties
    /actuator/loggers       → view/change log levels at runtime
    /actuator/threaddump    → current thread dump
    /actuator/heapdump      → heap dump (for memory analysis)
    /actuator/httptrace     → last 100 HTTP requests (deprecated → httpexchanges)
    /actuator/shutdown      → gracefully shut down (disabled by default!)

  Configuration:
    management.endpoints.web.exposure.include=health,info,metrics
    management.endpoints.web.exposure.include=*        # expose all
    management.endpoints.web.exposure.exclude=env,beans
    management.endpoint.health.show-details=always
    management.server.port=9090                        # separate management port

Q11. How do you create a custom Health Indicator?
──────────────────────────────────────────────────
Answer:
  Implement HealthIndicator and register it as a bean:

  @Component("database")
  public class DatabaseHealthIndicator implements HealthIndicator {

      @Autowired private DataSource dataSource;

      @Override
      public Health health() {
          try (Connection conn = dataSource.getConnection();
               Statement stmt = conn.createStatement()) {
              stmt.execute("SELECT 1");
              return Health.up()
                           .withDetail("database", "MySQL")
                           .withDetail("status", "Connected")
                           .build();
          } catch (Exception e) {
              return Health.down()
                           .withDetail("error", e.getMessage())
                           .build();
          }
      }
  }

  Response at /actuator/health:
    {
      "status": "UP",
      "components": {
        "database": {
          "status": "UP",
          "details": { "database": "MySQL", "status": "Connected" }
        }
      }
    }

  Composite health:
    @Component
    public class MyCompositeHealthIndicator extends CompositeHealthContributor { ... }

Q12. What is Micrometer and how does Spring Boot integrate with it?
────────────────────────────────────────────────────────────────────
Answer:
  Micrometer is a vendor-neutral application metrics facade (like SLF4J for
  metrics). Spring Boot auto-configures Micrometer when actuator is on classpath.

  Supported backends:
    Prometheus, Graphite, InfluxDB, DataDog, New Relic, CloudWatch, Dynatrace…

  Adding Prometheus:
    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-registry-prometheus</artifactId>
    </dependency>
    management.endpoints.web.exposure.include=prometheus
    → Exposes /actuator/prometheus for Prometheus scraping

  Custom metrics:
    @Component
    public class OrderMetrics {
        private final Counter orderCounter;
        private final Timer processingTimer;

        public OrderMetrics(MeterRegistry registry) {
            this.orderCounter = Counter.builder("orders.placed")
                .description("Total orders placed")
                .tag("region", "us-east")
                .register(registry);

            this.processingTimer = Timer.builder("orders.processing.time")
                .description("Order processing duration")
                .register(registry);
        }

        public void recordOrder() {
            orderCounter.increment();
        }

        public void timeProcessing(Runnable task) {
            processingTimer.record(task);
        }
    }

Q13. How does the embedded server work in Spring Boot?
──────────────────────────────────────────────────────
Answer:
  Spring Boot embeds Tomcat, Jetty, or Undertow inside the JAR/WAR.

  Default: Tomcat (spring-boot-starter-web includes tomcat starter).

  Switching to Jetty:
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <exclusions>
            <exclusion>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-starter-tomcat</artifactId>
            </exclusion>
        </exclusions>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-jetty</artifactId>
    </dependency>

  Configuration:
    server.port=8080
    server.servlet.context-path=/api
    server.tomcat.max-threads=200
    server.tomcat.min-spare-threads=10
    server.tomcat.connection-timeout=20000
    server.compression.enabled=true
    server.compression.mime-types=application/json,text/html
    server.ssl.key-store=classpath:keystore.p12
    server.ssl.key-store-password=changeit
    server.ssl.key-store-type=PKCS12

  Programmatic customization:
    @Bean
    public WebServerFactoryCustomizer<TomcatServletWebServerFactory> customizer() {
        return factory -> {
            factory.setPort(9000);
            factory.addConnectorCustomizers(connector ->
                connector.setMaxPostSize(10 * 1024 * 1024));
        };
    }

Q14. What is the difference between JAR and WAR deployment in Spring Boot?
──────────────────────────────────────────────────────────────────────────
Answer:
  Executable JAR (fat JAR):
    • Contains all dependencies + embedded server
    • Run with: java -jar myapp.jar
    • Default packaging for Spring Boot microservices
    • pom.xml: <packaging>jar</packaging>

  WAR deployment (external server):
    • Deploy to existing Tomcat/WildFly/WebLogic
    • pom.xml: <packaging>war</packaging>
    • Extend SpringBootServletInitializer:
        @SpringBootApplication
        public class MyApp extends SpringBootServletInitializer {
            @Override
            protected SpringApplicationBuilder configure(SpringApplicationBuilder builder) {
                return builder.sources(MyApp.class);
            }
            public static void main(String[] args) {
                SpringApplication.run(MyApp.class, args);
            }
        }
    • Mark embedded tomcat as provided:
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
            <scope>provided</scope>
        </dependency>

Q15. What is Graceful Shutdown in Spring Boot?
────────────────────────────────────────────────
Answer:
  Graceful shutdown allows in-flight requests to complete before the application
  stops (instead of abruptly killing threads).

  Configuration (Spring Boot 2.3+):
    server.shutdown=graceful
    spring.lifecycle.timeout-per-shutdown-phase=30s

  Behavior:
    1. Application receives shutdown signal (SIGTERM / actuator/shutdown)
    2. Server stops accepting NEW requests (returns 503)
    3. Waits for active requests to complete (up to timeout)
    4. Application context closes (beans destroyed, connections closed)

Q16. What testing support does Spring Boot provide?
────────────────────────────────────────────────────
Answer:
  spring-boot-starter-test includes:
    JUnit 5 (Jupiter)
    Mockito
    AssertJ
    Hamcrest
    JSONassert
    JsonPath
    Spring Test (MockMvc, TestRestTemplate, WebTestClient)

  Key annotations:

  @SpringBootTest:
    Loads the FULL application context.
    @SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
    Options: MOCK (default), RANDOM_PORT, DEFINED_PORT, NONE

  @WebMvcTest(OrderController.class):
    Loads ONLY the web layer (controllers, filters, MVC config).
    Use with @MockBean for service dependencies.

  @DataJpaTest:
    Loads only JPA-related config (repos, entities, DB).
    Uses H2 in-memory DB by default.
    Each test is transactional and rolled back.

  @DataMongoTest, @DataRedisTest, @DataJdbcTest — similar slice tests.

  @MockBean:
    Creates a Mockito mock and adds it to the Spring context.
    Replaces existing bean of the same type.

  @SpyBean:
    Wraps existing bean in a Mockito spy (real impl + verification).

  Example:
    @WebMvcTest(OrderController.class)
    class OrderControllerTest {

        @Autowired private MockMvc mockMvc;
        @MockBean  private OrderService orderService;

        @Test
        void shouldReturnOrder() throws Exception {
            given(orderService.findById(1L)).willReturn(new Order(1L, "PENDING"));

            mockMvc.perform(get("/orders/1"))
                   .andExpect(status().isOk())
                   .andExpect(jsonPath("$.status").value("PENDING"));
        }
    }

Q17. What is TestRestTemplate vs WebTestClient?
────────────────────────────────────────────────
Answer:
  TestRestTemplate:
    • Blocking; for Servlet-based (Spring MVC) integration tests
    • Available when webEnvironment = RANDOM_PORT or DEFINED_PORT
    • Auto-configured by Spring Boot test
    • @Autowired private TestRestTemplate restTemplate;

  WebTestClient:
    • Non-blocking; primarily for WebFlux but also supports MVC (via MockMvc)
    • More fluent API, better assertion support
    • @Autowired private WebTestClient webTestClient;

  WebTestClient example:
    webTestClient.get()
        .uri("/orders/1")
        .accept(MediaType.APPLICATION_JSON)
        .exchange()
        .expectStatus().isOk()
        .expectBody(Order.class)
        .value(order -> assertThat(order.getStatus()).isEqualTo("PENDING"));

Q18. Walk through the Spring Boot startup sequence.
────────────────────────────────────────────────────
Answer:
  SpringApplication.run(MyApp.class, args) triggers:

  1. Create SpringApplication instance
     - Detect WebApplicationType (SERVLET / REACTIVE / NONE)
     - Load SpringApplicationRunListeners (from spring.factories)
     - Load ApplicationContextInitializers
     - Load ApplicationListeners

  2. starting() — notify listeners

  3. Prepare Environment
     - Load application.properties / yaml
     - Apply profiles
     - Bind command-line args

  4. environmentPrepared() — listeners notified

  5. Create ApplicationContext
     - AnnotationConfigServletWebServerApplicationContext (for MVC)

  6. Prepare ApplicationContext
     - Apply initializers
     - Register @SpringBootApplication as a source
     - Load bean definitions (BeanDefinitionLoader)

  7. contextPrepared() — listeners notified

  8. Load beans (refresh() → ConfigurableApplicationContext.refresh())
     - invokeBeanFactoryPostProcessors (auto-configuration, @ComponentScan)
     - registerBeanPostProcessors
     - Initialize singletons (init beans, @PostConstruct)

  9. contextLoaded(), started() — listeners notified

  10. Start embedded web server

  11. ready() / ApplicationReadyEvent published

Q19. What is CommandLineRunner and ApplicationRunner?
──────────────────────────────────────────────────────
Answer:
  Both run code AFTER the application context is fully initialized (after
  ApplicationReadyEvent).

  CommandLineRunner — receives raw String[] args:
    @Component
    public class DataSeeder implements CommandLineRunner {
        @Override
        public void run(String... args) throws Exception {
            // seed database, run migrations, etc.
        }
    }

  ApplicationRunner — receives ApplicationArguments (parsed):
    @Component
    public class FeatureChecker implements ApplicationRunner {
        @Override
        public void run(ApplicationArguments args) throws Exception {
            if (args.containsOption("enable-feature-x")) {
                // ...
            }
        }
    }

  Order: Use @Order(1) to control execution order of multiple runners.

Q20. What is @EnableAutoConfiguration(exclude = …)?
─────────────────────────────────────────────────────
Answer:
  Excludes specific auto-configurations from being applied.

  @SpringBootApplication(exclude = {
      DataSourceAutoConfiguration.class,
      HibernateJpaAutoConfiguration.class
  })

  Or via properties (preferred for external config):
    spring.autoconfigure.exclude=\
      org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

  Use case:
    • App doesn't use a DB (exclude DataSource to avoid startup errors)
    • Using a custom DataSource configuration
    • Disabling security in tests (SecurityAutoConfiguration.class)

Q21. What are Spring Boot DevTools?
────────────────────────────────────
Answer:
  spring-boot-devtools provides developer-experience improvements:

  Automatic restart:
    • Watches classpath changes; restarts the app quickly using two classloaders
    • "Base" classloader: third-party jars (slow; only loaded once)
    • "Restart" classloader: your code (fast; reloaded on change)

  LiveReload:
    • Embedded LiveReload server; browser auto-refreshes on resource change

  Property defaults for dev:
    • Disables template caching (e.g., Thymeleaf)
    • Enables H2 console
    • Verbose logging for web requests

  Remote DevTools:
    • Can trigger remote restarts over HTTP for cloud-deployed apps

  DevTools are automatically disabled in production (when running from a JAR or
  when a specific system property is set).

Q22. What is Spring Boot's Banner?
────────────────────────────────────
Answer:
  The ASCII art printed on startup.

  Customization:
    • Place banner.txt in src/main/resources
    • Use banner.jpg / banner.png (Spring Boot renders as ASCII art)
    • Variables available: ${spring.boot.version}, ${application.version},
      ${application.formatted-version}
    • Disable: spring.main.banner-mode=off
    • Programmatic: SpringApplication.setBanner(...)

Q23. Spring Boot 3.x — Key New Features
─────────────────────────────────────────
Answer:
  Spring Boot 3.0+ (Spring Framework 6.x):

  1. Java 17+ minimum baseline
  2. Jakarta EE 9+ (javax.* → jakarta.*)
     - javax.servlet → jakarta.servlet
     - javax.persistence → jakarta.persistence
  3. Native Image support (GraalVM ahead-of-time compilation)
     - spring-boot-maven-plugin: mvn spring-boot:build-image -Pnative
     - Produces native executable (fast startup, low memory)
  4. Observability built-in
     - Micrometer Observation API replaces manual metric code
     - Auto-instrumented HTTP, JDBC, JMS, etc.
  5. Problem Details (RFC 7807) for error responses
     spring.mvc.problemdetails.enabled=true
  6. HTTP Interface Clients
     @HttpExchange("/users")
     interface UserClient {
         @GetExchange("/{id}") User findById(@PathVariable Long id);
     }
  7. Virtual Threads (Spring Boot 3.2+)
     spring.threads.virtual.enabled=true   # Project Loom integration

Q. Why might Spring Boot fail to start?
  → No DataSource configured when JPA on classpath
  → Port already in use (server.port conflict)
  → Missing required @ConfigurationProperties values (@Validated + @NotNull)
  → Bean definition conflicts (disable overriding)
  → Circular dependency with constructor injection

Q. How do you change the default port?
  → server.port=9090 in application.properties
  → java -jar app.jar --server.port=9090
  → SERVER_PORT=9090 (env variable)
  → server.port=0 → random available port (useful in tests)

Q. How do you disable a specific auto-configuration in tests?
  @SpringBootTest
  @ImportAutoConfiguration(exclude = SecurityAutoConfiguration.class)

Q. What is spring.config.import?
  Allows importing additional config sources:
  spring.config.import=optional:file:./config/extra.properties,\
                        optional:configserver:http://localhost:8888

Q. How do you read properties from multiple files?
  @PropertySource(value = {"classpath:a.properties", "classpath:b.properties"},
                  ignoreResourceNotFound = true)

Q. What happens when no active profile is set?
  → Beans annotated @Profile("default") are activated.
  → spring.profiles.default=default (can be changed)
