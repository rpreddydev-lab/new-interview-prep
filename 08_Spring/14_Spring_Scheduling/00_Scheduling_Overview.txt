  1. WHY SCHEDULING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Scheduling runs tasks at fixed times or intervals without external triggers.

Common use cases:
  - Nightly DB cleanup (delete expired sessions, old logs)
  - Periodic report generation (daily/weekly summaries)
  - Cache warm-up on schedule
  - Polling external API for updates
  - Health checks and monitoring tasks
  - Sending scheduled notifications (daily digest)
  - Syncing data with third-party services

  3. @Scheduled EXECUTION MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Attribute          | Description                        | Example
-------------------|------------------------------------|-----------------------------
fixedRate          | Run every N ms (from previous start) | fixedRate = 5000 (every 5s)
fixedDelay         | Wait N ms after previous completion  | fixedDelay = 10000
initialDelay       | Delay before first execution        | initialDelay = 30000
cron               | UNIX-like cron expression           | cron = "0 0 2 * * *"
fixedRateString    | fixedRate from property             | fixedRateString = "${task.rate}"
fixedDelayString   | fixedDelay from property            | fixedDelayString = "${task.delay}"
cronString         | Not needed — use ${} directly       | cron = "${task.cron}"

fixedRate vs fixedDelay:
  fixedRate:  task2 starts 5s after task1 STARTED (even if task1 ran 8s)
  fixedDelay: task2 starts 5s after task1 FINISHED

  4. SCHEDULING IN DISTRIBUTED SYSTEMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: in a multi-pod deployment, @Scheduled runs on ALL pods simultaneously.
For jobs that should run ONCE (not N times), this causes duplicate execution.

Solutions:
  1. ShedLock — distributed lock that prevents concurrent execution
  2. Spring Batch (already has distributed execution control)
  3. Kubernetes CronJob (dedicated pod for batch work)
  4. Database-backed locks (select for update)

ShedLock (most popular):
<dependency>
    <groupId>net.javacrumbs.shedlock</groupId>
    <artifactId>shedlock-spring</artifactId>
</dependency>
<dependency>
    <groupId>net.javacrumbs.shedlock</groupId>
    <artifactId>shedlock-provider-redis-spring</artifactId>
</dependency>

@SpringBootApplication
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "5m")
public class Application { ... }

@Service
public class DataCleanupJob {

    @Scheduled(cron = "0 0 2 * * *")
    @SchedulerLock(name = "dataCleanupJob",
                   lockAtLeastFor = "1m",    // hold lock for at least 1 min (prevents re-entry)
                   lockAtMostFor = "10m")    // release after 10 min even if execution hangs
    public void cleanupExpiredData() {
        dataRepository.deleteExpired(LocalDateTime.now().minusDays(30));
    }
}

  5. @Async — ASYNCHRONOUS METHOD EXECUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Async runs a method in a separate thread without blocking the caller.

@Service
public class NotificationService {

    // Fire-and-forget: caller doesn't wait
    @Async
    public void sendEmailAsync(String to, String subject, String body) {
        // runs in Spring's task executor (background thread)
        emailClient.send(to, subject, body);
    }

    // Async with return value (caller gets Future)
    @Async
    public CompletableFuture<String> generateReportAsync(Long reportId) {
        String report = reportGenerator.generate(reportId); // expensive
        return CompletableFuture.completedFuture(report);
    }
}

@RestController
public class OrderController {

    @PostMapping("/orders")
    public ResponseEntity<Order> create(@RequestBody CreateOrderRequest req) {
        Order order = orderService.create(req);
        notificationService.sendEmailAsync(order.getEmail(), "Order Confirmed", ...); // non-blocking
        return ResponseEntity.status(201).body(order);
    }
}

Q: What is the difference between fixedRate and fixedDelay?
A: fixedRate schedules the next execution N milliseconds after the previous
   execution STARTED. If the task takes longer than the interval, executions
   may overlap (unless the default single-threaded scheduler is used, in which
   case they queue). fixedDelay schedules the next execution N milliseconds after
   the previous execution FINISHED — guarantees a gap between executions.
   Use fixedDelay when overlapping execution would cause issues.

Q: What problem does ShedLock solve?
A: In multi-instance deployments (multiple pods), @Scheduled runs on every instance.
   For tasks that must run exactly once (DB cleanup, report generation), this causes
   duplicate work, double-counting, or conflicts. ShedLock uses a distributed lock
   (backed by Redis, DB, etc.) — only one instance acquires the lock and runs the task.

Q: How do you prevent a scheduled task from running during application shutdown?
A: Implement DisposableBean or @PreDestroy in the scheduled bean and set a
   'running' flag. When the flag is false (set in destroy()), skip execution.
   Spring also has TaskScheduler.shutdown() which stops scheduling. With Spring Boot,
   the scheduler is stopped gracefully as part of the context lifecycle.

Q: What thread runs @Scheduled tasks by default?
A: By default, all @Scheduled tasks share a single-threaded executor
   (ThreadPoolTaskScheduler with pool size 1). This means tasks run sequentially,
   not in parallel. If one long-running task delays others, configure a
   ThreadPoolTaskScheduler with a larger pool size. @Async tasks use a separate
   TaskExecutor.

Q: What happens if a @Scheduled task throws an exception?
A: The exception is caught by the scheduling infrastructure and logged, but does
   NOT stop future executions — the task continues to run on its next scheduled
   invocation. Uncaught exceptions in scheduled tasks are silently swallowed (except
   for logging). Use try-catch or @ExceptionHandler via TaskScheduler's error handler
   (implement ErrorHandler on the TaskScheduler) to handle failures.
