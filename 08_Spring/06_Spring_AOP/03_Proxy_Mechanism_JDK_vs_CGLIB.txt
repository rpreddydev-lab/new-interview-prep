================================================================
  SPRING AOP — PROXY MECHANISM: JDK vs CGLIB
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  1. HOW SPRING AOP WORKS — THE PROXY PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring AOP is proxy-based, not bytecode-weaving (unlike AspectJ).
When a bean has an aspect applied, Spring wraps it in a proxy object.
Callers interact with the proxy; the proxy delegates to the real bean
after executing advice.

  Caller → Proxy → [Advice #1 before] → [Advice #2 before]
         → Real Bean → [Advice #2 after] → [Advice #1 after]
         → Caller

Two proxy mechanisms:
  1. JDK Dynamic Proxy   → works with interfaces
  2. CGLIB Proxy         → works with classes (including no-interface classes)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  2. JDK DYNAMIC PROXY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Created by: java.lang.reflect.Proxy
Requires: the target bean implements at least one interface

How it works:
  - The proxy implements the same interface(s) as the target bean
  - Each method call is intercepted via InvocationHandler
  - The real bean is called through reflection

Example scenario:
  public interface UserService {
      User findById(Long id);
  }

  @Service
  public class UserServiceImpl implements UserService {
      @Override
      public User findById(Long id) { ... }
  }

  // Spring creates: Proxy implements UserService
  // Caller injects UserService — gets the proxy

Constraints:
  - Only interface methods are proxied
  - Internal calls to non-interface methods bypass the proxy
  - Proxy class is NOT a subclass of the implementation

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  3. CGLIB PROXY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Created by: CGLIB (Code Generation Library), included in Spring
Requires: the target class must NOT be final; methods must not be final

How it works:
  - CGLIB generates a subclass of the target class at runtime
  - The subclass overrides all non-final methods
  - Method calls are intercepted via MethodInterceptor

Example scenario:
  @Service
  public class OrderService {         // no interface
      public Order placeOrder(...) { ... }
  }

  // Spring creates: CglibOrderService$$ extends OrderService
  // Caller injects OrderService — gets the subclass proxy

When CGLIB is used:
  1. Target bean does NOT implement an interface
  2. proxyTargetClass = true is set explicitly
  3. Spring Boot uses CGLIB by default for @Configuration classes

proxyTargetClass = true:

  @EnableAspectJAutoProxy(proxyTargetClass = true)
  @Configuration
  public class AopConfig {}

  OR in application.properties (Spring Boot):
  spring.aop.proxy-target-class=true   ← default true in Spring Boot!

  4. JDK vs CGLIB COMPARISON TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Feature                  | JDK Dynamic Proxy      | CGLIB Proxy
-------------------------|------------------------|------------------------
Requires interface       | Yes                    | No
Technique                | Implements interface   | Subclasses the class
Class restriction        | None                   | Class must not be final
Method restriction       | None                   | Methods must not be final
Performance              | Slower (reflection)    | Faster (bytecode gen)
Default in Spring Boot   | No (CGLIB is default)  | Yes (since Spring 4+)
Can proxy final methods  | No                     | No
Dependency               | JDK (built-in)         | cglib / ASM (in Spring)

Spring Boot 3.x defaults to CGLIB for all @Service, @Repository, @Component.
JDK proxies used when: interface exists AND proxyTargetClass=false explicitly.

  5. THE SELF-INVOCATION PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is the most important limitation of proxy-based AOP.

When a method inside a bean calls another method in the SAME bean
using `this`, the call bypasses the proxy → NO advice is applied.

  @Service
  public class InvoiceService {

      @Transactional
      public void createInvoice(Order order) {
          // business logic
      }

      public void processOrder(Order order) {
          createInvoice(order);   // ← SELF-INVOCATION via 'this'
          // @Transactional on createInvoice() is NOT applied!
          // The proxy is bypassed.
      }
  }

Why? When `processOrder` is called from outside, the proxy intercepts it.
Inside processOrder, `createInvoice(order)` is a direct Java call on `this`
(the real bean), not through the proxy.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  6. SOLUTIONS TO SELF-INVOCATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Solution 1: Extract into a separate bean (RECOMMENDED — clean design)

  @Service
  public class InvoiceCreator {
      @Transactional
      public void createInvoice(Order order) { ... }
  }

  @Service
  public class OrderProcessor {
      @Autowired
      private InvoiceCreator invoiceCreator;  // different bean → goes through proxy

      public void processOrder(Order order) {
          invoiceCreator.createInvoice(order);  // proxy intercepts this call
      }
  }

Solution 2: Self-injection (inject yourself as a Spring bean)

  @Service
  public class InvoiceService {

      @Autowired
      private InvoiceService self;  // Spring injects the proxy

      @Transactional
      public void createInvoice(Order order) { ... }

      public void processOrder(Order order) {
          self.createInvoice(order);  // goes through proxy
      }
  }
  // Note: Can cause circular dependency. Use @Lazy to break it:
  // @Lazy @Autowired private InvoiceService self;

Solution 3: AopContext.currentProxy() (requires exposeProxy = true)

  @EnableAspectJAutoProxy(exposeProxy = true)

  @Service
  public class InvoiceService {

      @Transactional
      public void createInvoice(Order order) { ... }

      public void processOrder(Order order) {
          ((InvoiceService) AopContext.currentProxy()).createInvoice(order);
      }
  }
  // Less clean; couples business code to Spring AOP internals.

Solution 4: Use AspectJ compile-time weaving (avoids proxy entirely)
  AspectJ weaves advice at compile time or load time, so self-invocation
  also gets intercepted. Heavy setup (requires ajc compiler or agent).

  7. FINAL CLASSES AND METHODS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CGLIB cannot proxy:
  - final classes (cannot be subclassed)
  - final methods (cannot be overridden)
  - private methods
  - static methods

@Service
public final class PaymentService {   // ← CGLIB fails here!
    ...
}
// Result: BeanCreationException at startup — cannot subclass final class.

@Service
public class PaymentService {
    public final void processPayment() { ... }  // ← method-level advice won't apply
}
// Spring AOP silently skips final methods in some cases,
// or throws if proxyTargetClass is enforced.

Best practice: Never make @Service/@Component classes final.
(Records are final — do not use records as Spring beans with aspects.)

Q: When does Spring use JDK dynamic proxy vs CGLIB?
A: JDK dynamic proxy is used when the bean implements an interface AND
   proxyTargetClass=false. CGLIB is used when the bean doesn't implement
   an interface, OR proxyTargetClass=true (the Spring Boot default).
   Spring Boot 4/3 defaults to proxyTargetClass=true.

Q: What is the self-invocation problem and how do you fix it?
A: When a bean method calls another method in the same class, it goes
   through `this` (the real bean), bypassing the proxy. Aspects like
   @Transactional or custom @Around won't fire. Best fix: extract the
   method into a separate Spring-managed bean so the call goes through
   the proxy.

Q: Can Spring AOP proxy a final class?
A: No. CGLIB creates a subclass; final classes cannot be subclassed.
   This causes a BeanCreationException at startup. JDK proxies don't
   subclass but they require an interface. If your class is final and
   has no interface, Spring AOP cannot proxy it.

Q: What is proxyTargetClass=true and what are its implications?
A: It forces Spring to use CGLIB proxies even when the bean has an
   interface. This means you can inject the bean using its concrete
   class type (not just the interface). Spring Boot enables this by
   default to avoid issues with Kotlin, records, and lambda-based beans.

Q: Why does @Transactional not work on private methods?
A: Spring AOP proxies (both JDK and CGLIB) can only intercept public
   methods that are called through the proxy. Private methods are not
   visible to the proxy and cannot be overridden in a subclass, so
   @Transactional on a private method is silently ignored.
