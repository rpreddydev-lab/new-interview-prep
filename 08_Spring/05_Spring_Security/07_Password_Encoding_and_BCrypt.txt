  1. WHY HASH PASSWORDS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Passwords must NEVER be stored in plaintext. If the database is
breached, plaintext passwords expose ALL user accounts.

Hashing properties required for password storage:
  - One-way        → cannot reverse hash to get original password
  - Slow           → makes brute-force attacks computationally expensive
  - Salted         → prevents rainbow table attacks (precomputed hashes)
  - Unique per-hash→ same password produces different hashes (due to salt)

Weak approaches (DO NOT USE):
  ❌ MD5         → fast, broken, rainbow tables exist
  ❌ SHA-1/SHA-2 → fast (designed for speed, NOT password hashing)
  ❌ Encryption  → reversible (if key is stolen, all passwords exposed)

Correct approaches:
  ✅ BCrypt      → adaptive, salted, widely used
  ✅ Argon2      → winner of Password Hashing Competition, memory-hard
  ✅ SCrypt      → memory-hard, CPU-hard
  ✅ PBKDF2      → NIST-approved, used in FIPS contexts

  2. BCrypt EXPLAINED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BCrypt is based on the Blowfish cipher. It:
  - Generates a cryptographically secure random 128-bit salt
  - Performs 2^strength iterations (cost factor)
  - Produces a 60-character hash string containing:
    version + cost + salt + hash

Hash format:
  $2a$12$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
  ──┬─ ─┬─ ────────────────────────────────────────────────────────
   alg cost  22 chars salt + 31 chars hash

  $2a = BCrypt version
  12  = cost factor (2^12 = 4096 iterations)
  22-char base64 = 128-bit salt (always different for same password)

  3. SPRING SECURITY PasswordEncoder
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PasswordEncoder interface:
  String encode(CharSequence rawPassword);              // hash
  boolean matches(CharSequence rawPassword, String encodedPassword); // verify
  default boolean upgradeEncoding(String encodedPassword) // optional

// Declare as a bean
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();           // default strength: 10
}

// With custom strength (4–31, default 10)
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);        // 2^12 iterations
}

// Usage in service
@Service
public class UserService {
    private final PasswordEncoder passwordEncoder;
    private final UserRepository userRepo;

    public User register(RegisterRequest req) {
        String hashedPassword = passwordEncoder.encode(req.password());
        User user = new User(req.email(), hashedPassword);
        return userRepo.save(user);
    }

    public boolean verifyPassword(String rawPwd, String storedHash) {
        return passwordEncoder.matches(rawPwd, storedHash);
        // BCryptPasswordEncoder extracts salt from storedHash automatically
    }
}

  4. DelegatingPasswordEncoder (PASSWORD MIGRATION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Allows multiple encoding schemes simultaneously — ideal when
migrating from an old algorithm to a newer one.

Hash format with prefix:
  {bcrypt}$2a$12$...          → BCrypt
  {argon2}$argon2id$v=19$...  → Argon2
  {noop}plaintext             → NO hashing (for testing only!)

How it works:
  - encode() uses the default encoder (bcrypt)
  - matches() reads the prefix, delegates to the correct encoder
  - upgradeEncoding() tells Spring to re-hash if algorithm is outdated

PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();

// Custom factory
Map<String, PasswordEncoder> encoders = new HashMap<>();
encoders.put("bcrypt", new BCryptPasswordEncoder(12));
encoders.put("argon2", new Argon2PasswordEncoder(16, 32, 1, 65536, 10));
encoders.put("noop", NoOpPasswordEncoder.getInstance());   // dev only

DelegatingPasswordEncoder delegating =
    new DelegatingPasswordEncoder("bcrypt", encoders);

// → Encodes new passwords with bcrypt
// → Can still verify old argon2 or noop hashes
// → upgradeEncoding returns true for non-default encoders → re-hash on next login

  5. ARGON2 — THE MODERN CHOICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Winner of Password Hashing Competition (2015). Three variants:
  Argon2d  → GPU attack resistant
  Argon2i  → side-channel resistant
  Argon2id → hybrid (recommended)

Parameters:
  saltLength  → bytes of salt (min 16)
  hashLength  → bytes of output hash (min 32)
  parallelism → CPU threads
  memory      → KB of memory (higher = more memory-hard)
  iterations  → number of passes

// Dependency: spring-security-crypto includes Argon2 via Bouncy Castle
@Bean
public PasswordEncoder passwordEncoder() {
    return new Argon2PasswordEncoder(
        16,      // saltLength
        32,      // hashLength
        1,       // parallelism
        65536,   // memory (64 MB)
        10       // iterations
    );
}

  6. PASSWORD SECURITY BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✅ Use BCrypt (strength 12+) or Argon2id in production
  ✅ Never store plaintext or reversibly encrypted passwords
  ✅ Use DelegatingPasswordEncoder for forward compatibility
  ✅ Enforce minimum password length (8+ characters)
  ✅ Rate-limit login attempts (prevent brute-force)
  ✅ Lock account after N failed attempts
  ✅ Validate new passwords against a breached password list
     (HaveIBeenPwned API integration)
  ✅ Clear password fields from memory after use (use char[] not String)
  ✅ Hash on the server side — client-side hashing is not a security measure
  ❌ No MD5 / SHA-1 / SHA-256 for passwords
  ❌ No reusing salts
  ❌ No cost factor < 10 in production

  7. ACCOUNT LOCKOUT IMPLEMENTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Component
public class LoginAttemptService {
    private static final int MAX_ATTEMPTS = 5;
    private final Map<String, Integer> attemptsCache = new ConcurrentHashMap<>();

    public void loginFailed(String email) {
        attemptsCache.merge(email, 1, Integer::sum);
    }

    public void loginSucceeded(String email) {
        attemptsCache.remove(email);
    }

    public boolean isBlocked(String email) {
        return attemptsCache.getOrDefault(email, 0) >= MAX_ATTEMPTS;
    }
}

// In UserDetailsService
@Override
public UserDetails loadUserByUsername(String email) {
    if (loginAttemptService.isBlocked(email)) {
        throw new LockedException("Account locked due to too many failed attempts");
    }
    // ... load user
}

// Listen for authentication events
@Component
public class AuthenticationEventListener {
    @EventListener
    public void onFailure(AbstractAuthenticationFailureEvent event) {
        String username = event.getAuthentication().getName();
        loginAttemptService.loginFailed(username);
    }

    @EventListener
    public void onSuccess(AuthenticationSuccessEvent event) {
        String username = event.getAuthentication().getName();
        loginAttemptService.loginSucceeded(username);
    }
}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why is BCrypt preferred over SHA-256 for password hashing?
A: SHA-256 is designed to be FAST (for checksums, data integrity).
   BCrypt is designed to be SLOW and adaptive — its cost factor
   makes brute-force attacks expensive. BCrypt also automatically
   salts each hash, preventing rainbow table attacks. SHA-256 without
   salting is trivially defeated by lookup tables.

Q: What is the cost factor in BCrypt and how do you choose it?
A: The cost factor (strength) determines the number of iterations
   (2^strength). A higher cost means slower hashing. Choose the
   highest value that keeps response time under ~100ms on your
   hardware (typically 12 for production servers). Re-evaluate as
   hardware improves.

Q: How does BCrypt's matches() work if every hash is different?
A: The salt is embedded in the hash string ($2a$12$<22-char salt>...).
   During matches(), BCrypt extracts the salt from the stored hash
   and re-hashes the input with the same salt. If the results match,
   the password is correct. No separate salt storage is needed.

Q: What is DelegatingPasswordEncoder and why is it useful?
A: It allows multiple password encoding strategies to coexist.
   Each hash is prefixed with {scheme} (e.g., {bcrypt}). This enables
   smooth migration — existing hashes with old algorithms continue to
   work while new passwords use the updated algorithm. On next login
   with the old algorithm, upgradeEncoding() triggers a re-hash.

Q: What is Argon2 and how does it compare to BCrypt?
A: Argon2 is a memory-hard algorithm (winner of PHC). Unlike BCrypt
   which is only CPU-hard, Argon2 requires significant memory, making
   GPU-based attacks much more expensive. Argon2id is the recommended
   variant for password hashing. BCrypt is still excellent; Argon2
   is theoretically stronger but BCrypt is more widely supported.
