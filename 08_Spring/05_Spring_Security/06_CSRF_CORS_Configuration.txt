  1. CSRF — CROSS-SITE REQUEST FORGERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What is CSRF?
  An attack where a malicious site tricks an authenticated user's
  browser into making an unwanted request to your API.

  User is logged into bank.com (session cookie auto-sent by browser).
  User visits evil.com — hidden form POST to bank.com/transfer.
  Browser automatically sends session cookie → transaction executes!

CSRF only works because cookies are sent automatically by browsers.
If you use JWTs in Authorization headers, CSRF is NOT a concern
(headers are not sent automatically by the browser).

  2. SPRING CSRF PROTECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Security enables CSRF protection by default.
It rejects POST/PUT/PATCH/DELETE requests without a valid CSRF token.

Token approaches:
  a) Synchronizer Token Pattern (classic form apps):
     - Server generates random token, stored in session
     - Token embedded in HTML form as hidden field
     - Server validates token on form submission

  b) Cookie-to-Header (SPA-friendly):
     - Server writes CSRF token as a READABLE cookie
     - JavaScript reads cookie, sends it as a request header
     - Server checks header value matches cookie value

Cookie-based CSRF in Spring:
  http.csrf(csrf -> csrf
      .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
      .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler())
  );

  → Sets XSRF-TOKEN cookie (readable by JS — not HttpOnly)
  → Client must send it back in X-XSRF-TOKEN header or _csrf parameter

For REST APIs using JWT (stateless):
  http.csrf(csrf -> csrf.disable());  // safe because no cookies carry auth

  3. CORS — CROSS-ORIGIN RESOURCE SHARING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What is CORS?
  A browser security mechanism that restricts web pages from making
  requests to a DIFFERENT origin (domain, protocol, port).

  Same origin: https://app.example.com → https://app.example.com/api ✓
  Cross-origin: https://app.example.com → https://api.example.com    ✗ (blocked)

Preflight request:
  For non-simple requests (PUT, DELETE, custom headers), browser
  sends an OPTIONS request first to check if cross-origin is allowed.
  Server must respond with Access-Control-Allow-* headers.

CORS is a BROWSER protection. Server-to-server calls are not affected.

  4. CORS CONFIGURATION IN SPRING BOOT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option A — Global via WebMvcConfigurer (preferred for non-security):
  @Configuration
  public class WebConfig implements WebMvcConfigurer {
      @Override
      public void addCorsMappings(CorsRegistry registry) {
          registry.addMapping("/api/**")
              .allowedOrigins("https://frontend.example.com",
                               "http://localhost:3000")
              .allowedMethods("GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS")
              .allowedHeaders("*")
              .allowCredentials(true)        // for cookies/auth headers
              .maxAge(3600);                 // preflight cache duration
      }
  }

Option B — Via Spring Security HttpSecurity (required for secured APIs):
  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
      http
          .cors(cors -> cors.configurationSource(corsConfigurationSource()))
          ...
      return http.build();
  }

  @Bean
  public CorsConfigurationSource corsConfigurationSource() {
      CorsConfiguration config = new CorsConfiguration();
      config.setAllowedOrigins(List.of(
          "https://frontend.example.com",
          "http://localhost:3000"
      ));
      config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
      config.setAllowedHeaders(List.of("Authorization","Content-Type","X-Requested-With"));
      config.setExposedHeaders(List.of("Authorization","X-Total-Count"));
      config.setAllowCredentials(true);
      config.setMaxAge(3600L);

      UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
      source.registerCorsConfiguration("/api/**", config);
      return source;
  }

Option C — Per-controller/method with @CrossOrigin:
  @CrossOrigin(origins = "http://localhost:3000",
               methods = { RequestMethod.GET, RequestMethod.POST })
  @RestController
  @RequestMapping("/api/products")
  public class ProductController { ... }

  @CrossOrigin   // defaults: all origins, all methods
  @GetMapping("/{id}")
  public Product getProduct(@PathVariable Long id) { ... }

  5. CORS + SPRING SECURITY — IMPORTANT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⚠️  Spring Security MUST process CORS BEFORE authentication filters.
    If the CORS preflight (OPTIONS) request is blocked by auth rules,
    the actual request will never reach the server.

Why this matters:
  An OPTIONS preflight has no Authorization header.
  If Spring Security rejects unauthenticated OPTIONS → CORS fails.

Fix: Spring Security 6 handles this correctly when .cors() is enabled.
Spring Security automatically passes OPTIONS preflight requests
through CorsFilter before authentication when .cors() is configured.

If using a custom CORS config, ensure:
  http.cors(cors -> cors.configurationSource(corsConfigurationSource()))

Do NOT just add .requestMatchers(HttpMethod.OPTIONS).permitAll()
as this bypasses CORS negotiation entirely.

  6. allowedOrigins vs allowedOriginPatterns
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  allowedOrigins("*")          → all origins, but CANNOT use allowCredentials(true)
  allowedOriginPatterns("*")   → all origins, CAN use allowCredentials(true)
                                  (uses wildcard pattern matching)

  // For credentials + wildcard:
  config.setAllowedOriginPatterns(List.of("*"));  // or "https://*.example.com"
  config.setAllowCredentials(true);

  7. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is CSRF and how does Spring protect against it?
A: CSRF is an attack where a malicious site makes authenticated
   requests on a user's behalf using their session cookie.
   Spring protects via a CSRF token (unique per session/request)
   that must be included in state-changing requests. The token
   is validated by CsrfFilter before processing.

Q: When is it safe to disable CSRF in Spring Security?
A: When your app is a stateless REST API using JWTs in Authorization
   headers. Browsers never automatically attach custom headers, so
   CSRF attacks (which rely on automatic cookie sending) are not
   possible. If your app uses session cookies for auth, CSRF must
   be enabled.

Q: What is CORS and why does it exist?
A: CORS is a browser security policy that blocks JavaScript from
   making requests to a different origin (domain, protocol, port)
   than the page it's loaded from. It protects users from malicious
   sites that try to make API calls using the user's credentials.
   Servers explicitly opt-in to allow cross-origin requests via
   Access-Control-Allow-* headers.

Q: Why does a CORS preflight (OPTIONS) sometimes fail in Spring Security?
A: Spring Security may block the OPTIONS preflight because it has no
   Authorization header — the authentication filter returns 401
   before Spring MVC even processes the CORS headers. Fix: configure
   CORS in the Spring Security DSL (.cors()) so Spring Security's
   CorsFilter processes it before authentication filters.

Q: What is the difference between allowedOrigins("*") and allowedOriginPatterns("*")?
A: allowedOrigins("*") sets the header to *, which browsers interpret
   as allowing all origins but it CANNOT be combined with
   allowCredentials(true) (browsers reject this combination).
   allowedOriginPatterns("*") uses pattern matching — Spring reflects
   the actual Origin back, which satisfies the credentials requirement.

Q: How does @CrossOrigin differ from global CORS configuration?
A: @CrossOrigin applies only to the annotated controller or method,
   while global CORS config (WebMvcConfigurer or HttpSecurity.cors)
   applies to all endpoints matching the URL pattern. Global config
   must be used for endpoints secured by Spring Security to ensure
   CORS headers are added even when auth fails.
