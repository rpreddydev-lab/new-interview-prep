SCALABILITY & PERFORMANCE INTERVIEW QUESTIONS — MODEL ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the difference between horizontal and vertical scaling?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Vertical Scaling (Scale Up):
    Add more CPU/RAM/disk to existing machine
    Example: DB server 16 cores → 64 cores
    Pros: no code changes, simple to manage, no distributed system complexity
    Cons: hard limit (biggest machine), single point of failure, expensive
    Use for: databases initially, ML model inference

  Horizontal Scaling (Scale Out):
    Add more machines to the pool
    Example: 1 API server → 10 API servers behind load balancer
    Pros: unlimited scale in theory, fault tolerant, commodity hardware
    Cons: stateless required, data consistency complexity, distributed failures
    Use for: stateless API servers, caches, message queues

  Rule of thumb:
    Start vertical — it's simpler; go horizontal when vertical hits limits
    Design stateless from day 1 so horizontal scaling is easy later
    
    Databases scale harder horizontally → scale them vertically first,
    then add read replicas, then shard when truly needed


Q2: Explain different caching strategies (write-through, write-back, etc.)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  CACHE-ASIDE (Lazy Loading) — RECOMMENDED:
    Read: App checks cache → miss → read DB → write to cache → return
    Write: App writes to DB → DELETES (not updates) cache key
    Pros: cache only contains requested data; DELETE avoids race conditions
    Cons: cache miss on first request (cold start)
    Issue: If you UPDATE cache on write instead of delete:
      Thread A reads user → DB returns v1 → before cache write...
      Thread B updates DB to v2 → deletes cache key
      Thread A writes stale v1 to cache → cache is wrong
    Solution: DELETE on write, not update

  WRITE-THROUGH:
    Every write goes to cache AND DB synchronously
    Cache is always consistent with DB
    Pros: no stale cache; Cons: every write is slow (double write)
    Use when: read-heavy with occasional writes

  WRITE-BEHIND (Write-Back):
    Write to cache immediately, async flush to DB later
    Pros: very fast writes; Cons: data loss risk if cache crashes before flush
    Use when: high-write workloads where some data loss is acceptable
    Example: like counts, view counts (approximate is fine)

  READ-THROUGH:
    App always reads from cache
    Cache fetches from DB on miss (not the app)
    Pros: cache logic centralized; Cons: cold start penalty

  REFRESH-AHEAD:
    Cache proactively refreshes before expiry based on access patterns
    Reduces latency spikes on expiry; complex to implement


Q3: What are common performance bottlenecks and how do you identify them?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Common Bottlenecks:
    Database: slow queries, missing indexes, N+1 queries, lock contention
    Network: high latency between services, large payloads, chatty protocols
    CPU: hash computation, encryption, image/video processing
    Memory: insufficient heap (GC pressure), cache too small
    Disk I/O: random reads on spinning disk, missing buffer pool
    External APIs: slow third-party dependencies (payment, email)

  Identification Tools:
    APM (Application Performance Monitoring):
      New Relic, Datadog APM → transaction traces, slowest endpoints
    
    Database:
      EXPLAIN ANALYZE in PostgreSQL → query execution plan
      pg_stat_statements → top 10 slowest queries by total time
      Missing index: "Seq Scan" on large table = bad; "Index Scan" = good
    
    CPU profiling: async-profiler (Java), py-spy (Python) → flame graphs
    Load testing: Gatling, k6, Apache JMeter → find breaking point

  N+1 Query Problem:
    Fetching 100 posts → for each post, 1 query for comments = 101 queries
    Fix: JOIN or batch load (SELECT * WHERE post_id IN (...))

  Common fixes:
    Slow read query → add index or add cache
    N+1 → JOIN + pagination
    Slow writes → async queue the work
    CPU-bound → cache result, or move to async worker
    Lock contention → shorter transactions, optimistic locking


Q4: How does a load balancer work and what algorithms does it use?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Load balancer distributes incoming traffic across multiple servers

  Layer 4 vs Layer 7:
    L4 (Transport): routes based on IP/port, fast, no HTTP awareness
    L7 (Application): routes based on URL, headers, cookies; smarter routing

  Algorithms:
    Round Robin: server 1, 2, 3, 1, 2, 3...
      Simple; doesn't account for server capacity or current load

    Weighted Round Robin: server 1 gets 3x requests vs server 2
      Handle heterogeneous hardware

    Least Connections: send to server with fewest active connections
      Good for variable-length requests (some requests take 100ms, some 5s)

    IP Hash: hash(client_IP) → always same server
      Session affinity (sticky sessions); bad for hotspots if many users share IP

    Random: pick randomly
      Surprisingly effective at scale with many servers (law of large numbers)

    Resource-Based: route based on actual server CPU/memory metrics
      Nginx Plus, AWS ALB target group health

  Health checks:
    LB polls servers every 10 seconds (HTTP GET /health → 200 OK)
    Remove unhealthy servers from rotation automatically

  Sticky Sessions:
    Same user always hits same server (for session state)
    Better alternative: store sessions in Redis so any server handles it


Q5: Explain back-pressure and how to handle it.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Back-pressure: consumer can't keep up with producer → queue grows → OOM crash

  Scenario: Orders spike 10×; order processing takes 100ms; queue fills up
  Without back-pressure: unbounded queue → memory exhaustion → crash

  Solutions:

  1. Bounded queues: reject when full (fail fast)
     LinkedBlockingQueue(capacity) → throws RejectedExecutionException if full
     Caller gets 429/503 immediately → can retry or show error

  2. Rate limiting upstream: limit order intake to max queue can handle
     If queue > 90% full → reject new requests at API gateway

  3. Dynamic scaling: autoscale consumers when queue grows
     AWS SQS + Lambda → auto-invokes more lambdas as message count grows
     Kafka → add consumer instances when consumer lag grows

  4. Circuit Breaker: if downstream too slow → stop sending, return error immediately
     Hystrix, Resilience4j → detect failure rate threshold → open circuit

  5. Reactive streams (Project Reactor, RxJava):
     Built-in back-pressure protocol
     Publisher.subscribe(subscriber.request(N)) → subscriber controls rate

  Key insight: unbounded queues are ticking time bombs
    Always bound your queues; handle the rejection gracefully


Q6: What is a thundering herd problem and how do you solve it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Thundering herd: a single event wakes up (or directs) many processes,
  most of which do the same redundant work simultaneously

  Scenarios:
    Cache stampede: popular cache key expires → 10,000 simultaneous cache misses
      All 10K requests hit DB simultaneously → DB overwhelmed

    Service restart: cache is empty after deploy → cold start traffic spike

    Cron job: 1M jobs scheduled for midnight → DB spike

  Solutions:

  Cache Stampede:
    Locking: first thread gets DB query lock, others wait
      Mutex/singleflight (Go): only 1 DB call per key, others wait and share result
      Redis SET NX EX pattern: set lock key → only holder queries DB

    Probabilistic early expiry (PER):
      When TTL < threshold × random(), proactively refresh before expiry
      Stagger expiry across threads, prevent cliff-edge miss

    Stale-while-revalidate:
      Serve stale data while refreshing in background
      HTTP Cache-Control: stale-while-revalidate=30
      User gets instant (possibly stale) response; cache refreshes async

  Cache Pre-warming:
    Before deploy: write all hot keys to cache from DB
    After deploy: cache already warm, no stampede

  Cron job jitter:
    Instead of exact midnight: random offset 0-60s
    1M jobs over 60s = 17K/s instead of 1M/s spike


Q7: How do you calculate back-of-the-envelope estimates?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Key numbers to memorize:

  LATENCY:
    L1 cache access:        0.5 ns
    Main memory access:     100 ns
    SSD random read:        100 µs   (0.1 ms)
    Network round-trip DC:  0.5 ms
    HDD seek:               10 ms
    Network cross-country:  150 ms

  SCALE:
    10^3 = 1K      10^6 = 1M     10^9 = 1B
    1KB = 10^3     1MB = 10^6    1GB = 10^9     1TB = 10^12

  CONVERSIONS:
    1M req/day → 1M / 86400s ≈ 12 req/s
    1B req/day → 11,574 req/s ≈ 12K req/s
    
    1 billion users × 100 bytes/user = 100 GB = 0.1 TB

  FORMULA (DAU → QPS):
    QPS = DAU × requests_per_day / 86400
    Peak QPS ≈ 3× average QPS

  Example: Twitter
    300M DAU × 5 reads/day / 86400 = 17,000 reads/s (avg) → 50K peak
    300M DAU × 1 tweet/day / 86400 = 3,470 writes/s (avg) → ~10K peak

  Storage example: photos
    100M uploads/day × 200KB/photo = 20TB/day
    5-year retention: 20TB × 365 × 5 = 36.5PB


Q8: What is connection pooling and why is it important?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Database connection = expensive resource
  TCP handshake + auth = ~5-10ms per connection
  DB can handle ~100-500 concurrent connections before performance degrades

  Without pooling:
    1000 requests/s × each opens a connection = 1000 connections/s
    DB overwhelmed, connection setup adds latency to every request

  Connection Pool:
    Pre-create N connections at startup (e.g., pool size = 20)
    App borrows connection from pool → query → returns to pool
    If all borrowed: caller waits (or throws after timeout)
    Pool health-checks idle connections, reopens if dead

  Configuration:
    minIdle: minimum kept open (avoids cold start on spike)
    maxPoolSize: maximum concurrent connections
    connectionTimeout: how long to wait for available connection
    maxLifetime: rotate connections to prevent DB server-side timeout

  Pool sizing formula (from Java HikariCP team):
    pool_size = Tn × (Cm - 1) + 1
    Where Tn = max threads, Cm = average concurrent DB calls per thread
    Practical: 10-20 connections per application server instance

  PgBouncer / Pgpool-II:
    Connection pool PROXY in front of Postgres
    Useful when many app servers × many connections would exceed DB limit
    1000 app connections → PgBouncer → 20 actual DB connections
