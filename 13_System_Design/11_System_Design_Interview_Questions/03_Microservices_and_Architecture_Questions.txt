MICROSERVICES & ARCHITECTURE INTERVIEW QUESTIONS — MODEL ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: When would you choose microservices over a monolith?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Start with a monolith unless you have clear reasons not to.

  Monolith Pros:
    Simple to develop, test, debug (single codebase)
    No network latency for internal calls
    ACID transactions across all data in one DB
    Easy local development

  Move to Microservices when:
    Team size grows (Conway's Law: org structure → system architecture)
      5 teams working on monolith → everyone steps on each other's toes
      Microservices → independent teams, independent deployments
    
    Scale mismatch: checkout service needs 100× more resources than auth service
    
    Tech diversity: payments team wants Python; ML team wants TensorFlow
    
    Deployment independence: deploy catalog service without risking checkout
    
    Compliance: PCI-DSS requires isolating payment service

  Microservices Costs (often underestimated):
    Distributed transactions → Saga complexity
    Network failures between services
    Service discovery and API versioning
    Observability overhead (tracing across 50 services)
    Operational complexity (each service needs own CI/CD, monitoring)

  Recommendation: start monolith, extract services when you feel the pain


Q2: What is an API Gateway and what should it do?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  API Gateway: single entry point for all client requests

  Responsibilities:
    Authentication & Authorization: verify JWT tokens before forwarding
    Rate Limiting: enforce per-client request limits
    SSL Termination: decrypt HTTPS, forward HTTP internally
    Request Routing: /users/* → UserService; /orders/* → OrderService
    Load Balancing: distribute across service instances
    Request/Response Transformation: translate between protocols (REST ↔ gRPC)
    Request Aggregation: mobile needs 5 API calls → gateway aggregates into 1
    Observability: log all requests, emit metrics, propagate trace IDs

  What NOT to do in API Gateway:
    Business logic (violates single responsibility)
    Large data transformations (adds latency to every request)
    Storing session state (must be stateless for horizontal scaling)

  Popular choices:
    AWS API Gateway: managed, serverless integration
    Kong: open-source, plugin ecosystem
    NGINX: high performance, L7 routing
    Istio (service mesh): sidecars for East-West traffic, not just North-South

  API Gateway vs Service Mesh:
    API Gateway: North-South (client → service) — external traffic
    Service Mesh: East-West (service → service) — internal traffic
    Both often used together


Q3: Explain the Circuit Breaker pattern.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Problem: Service A calls Service B. B is slow/down.
    Without circuit breaker: A queues up thousands of slow calls → threads exhausted → A crashes too
    Cascade failure: one service takes down the whole system

  Circuit Breaker States:
    CLOSED (normal): calls pass through; failure rate monitored
    OPEN: calls immediately rejected (fast fail, error returned)
      Prevents overwhelming already-struggling downstream service
    HALF-OPEN: after timeout, allow limited test requests
      If succeed → back to CLOSED; if fail → back to OPEN

  Configuration (Resilience4j):
    failureRateThreshold: 50% (open if >50% of last 10 calls fail)
    waitDurationInOpenState: 30s (stay open 30s before half-open)
    permittedNumberOfCallsInHalfOpenState: 3 (test with 3 calls)
    slidingWindowSize: 10 (evaluate last 10 calls)

  Fallback behavior when circuit open:
    Return cached/stale data
    Return default value ("no recommendations")
    Return error to client (fast, not slow timeout)

  Implementation:
    Resilience4j (Java), Polly (.NET), Hystrix (deprecated)
    Or service mesh (Istio): circuit breaking in sidecar proxy

  Key insight: fail fast is better than slow timeout
    A 30-second timeout cascades; immediate 503 lets client retry or fail gracefully


Q4: What is the Saga pattern? When would you use it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Saga: long-running distributed transaction broken into local transactions
  Each step publishes event; failure triggers compensating transactions (rollback)

  When to use:
    Multi-service transaction (Order → Inventory → Payment → Shipment)
    Cannot use 2PC (blocking, not partition-tolerant)
    Some steps span multiple databases/services

  Choreography Saga:
    Each service listens to events and publishes own events
    No central coordinator
    OrderCreated → InventoryReserved → PaymentProcessed → OrderConfirmed
    Compensation: PaymentFailed → InventoryReleased → OrderCancelled
    Pros: simple, fully decoupled
    Cons: hard to trace flow, difficult error handling, risk of cyclic calls

  Orchestration Saga:
    Central Saga Orchestrator issues commands, waits for replies
    Orchestrator explicitly handles failures and compensation
    Pros: easy to see full business flow in one place, simpler debugging
    Cons: orchestrator can be bottleneck or single point of failure

  Compensation requirements:
    Every step must have a compensating action
    Compensating actions must be idempotent (safe to retry)
    Cannot always fully undo (e.g., email sent) → semantic undo ("order cancelled" email)

  Real-world example: Amazon order placement
    1. Reserve inventory
    2. Charge payment card
    3. Create shipment
    4. Confirm order
    If step 2 fails: release inventory (step 1 compensation)


Q5: What is service discovery and how does it work?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Problem: in Kubernetes/cloud, service instances have dynamic IP addresses
    UserService needs to call OrderService but doesn't know its IP

  Client-Side Discovery:
    Services register themselves with registry (Consul, Eureka)
    Client queries registry to find healthy instances
    Client performs its own load balancing (round-robin, etc.)
    Pros: no single point of failure in routing; Cons: client complexity

  Server-Side Discovery:
    Client → Load Balancer/Router → Registry lookup → Service
    AWS ALB + ECS: ALB consults ECS service registry
    Kubernetes: kube-proxy + CoreDNS does this transparently
    Pros: simple client; Cons: extra hop, LB must be reliable

  How services register:
    Self-registration: service calls Consul/Eureka on startup, sends heartbeats
    Third-party: orchestrator (Kubernetes) registers/deregisters on pod events

  Health checking:
    Registry marks instance unhealthy if heartbeats stop (TTL 30s)
    Client only routes to healthy instances

  Kubernetes:
    Service object: virtual IP + round-robin to matching pods
    DNS: OrderService.default.svc.cluster.local → ClusterIP
    Completely transparent to application code


Q6: Explain CQRS and Event Sourcing. When are they overkill?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  CQRS — Command Query Responsibility Segregation:
    Separate Write Model (handles commands) from Read Model (handles queries)
    Write DB: normalized (PostgreSQL) — optimized for consistency
    Read DB: denormalized (Elasticsearch, Redis) — optimized for query patterns
    
    When useful:
      Read/write scale differently (1000× more reads than writes)
      Complex query shapes (dashboards, reports) that don't match write schema
    
    When overkill:
      Simple CRUD apps where one DB model works fine
      Small team that doesn't need the operational complexity
      Read/write patterns are similar

  Event Sourcing:
    Store sequence of events, not current state
    Current state = replay all events from beginning
    
    Benefits:
      Complete audit log built-in (banking, compliance)
      Time-travel debugging (replay to any past state)
      Derive multiple read models from same event stream
    
    Costs:
      Event replay can be slow for long-lived aggregates (use snapshots)
      Schema evolution of events is hard (can't change old events)
      Eventual consistency for read models
    
    When overkill:
      Most CRUD apps (you don't need full history)
      When current state is all you care about
      Simple read-heavy systems

  "Default to simple CRUD. Add CQRS when query performance is painful.
   Add Event Sourcing when audit trail is a business requirement."


Q7: How do you handle API versioning?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Why it matters: once an API is public, you can't change it without
  breaking existing clients. Versioning allows evolution.

  Approaches:

  URL versioning: /v1/users, /v2/users
    Pros: explicit, cacheable, easy to test; Cons: ugly URLs, must update all clients
    Recommended for public APIs (easiest for clients to understand)

  Header versioning: Accept: application/vnd.myapi.v2+json
    Pros: clean URLs; Cons: harder to test in browser, less discoverable

  Query param: /users?version=2
    Pros: simple; Cons: easy to miss, affects caching

  Deprecation strategy:
    Keep v1 running for 12-18 months after v2 launch
    Sunset header: "Sunset: Sat, 01 Jan 2026 00:00:00 GMT"
    Monitor v1 traffic; contact clients still using it

  Backward-compatible changes (don't need new version):
    Adding optional fields to response
    Adding optional parameters to request
    Adding new endpoints

  Breaking changes (need new version):
    Removing fields from response
    Changing field types
    Changing URL structure
    Changing authentication method


Q8: What is the Strangler Fig pattern?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Named after the fig tree that slowly surrounds a host tree until the host dies

  Goal: migrate a monolith to microservices incrementally without big-bang rewrite

  Steps:
    1. Put a facade/proxy in front of the monolith (API Gateway)
    2. Extract one bounded context into a new service (e.g., user profiles)
    3. Route /users/* requests to the new service instead of monolith
    4. Gradually move more functionality; monolith shrinks
    5. Eventually decommission the monolith

  Key principles:
    Never stop shipping; incremental migration means business keeps running
    Start with low-risk, well-bounded features (not the payment module on day 1)
    Dual-write during transition: write to both old and new to ensure consistency
    Feature flag: route small % of traffic to new service first (canary)

  Risk mitigation:
    Dark launch: call new service but ignore result; compare with monolith output
    If outputs match → fully route to new service
    Allows testing in production without customer impact


Q9: How would you design for zero-downtime deployments?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Techniques:

  Rolling Deployment:
    Replace instances one at a time (or in batches)
    Load balancer temporarily has v1 and v2 instances
    Gradual; if v2 is bad, stop rollout, only partial blast radius
    Risk: backward-compatible DB schema changes required (v1 and v2 coexist)

  Blue-Green Deployment:
    Maintain two identical environments (Blue = current, Green = new)
    Switch load balancer from Blue to Green atomically
    If Green fails → switch back to Blue immediately
    Pros: instant rollback; Cons: 2× infra cost, data migration complexity

  Canary Deployment:
    Route 1% of traffic to new version → monitor → 10% → 50% → 100%
    Compare error rates, latency, business metrics between canary and stable
    Gradual rollout minimizes blast radius
    Tools: AWS CodeDeploy, Spinnaker, Argo Rollouts (Kubernetes)

  Feature Flags:
    Deploy code but keep feature off (flag=false)
    Turn on for 1% users (canary test without deployment)
    Tools: LaunchDarkly, Unleash, Flipt

  DB schema changes (trickiest):
    Expand-Contract Pattern:
      Step 1: Add new column (nullable), keep old column — both versions work
      Step 2: Deploy new code that writes to both columns
      Step 3: Backfill old rows to new column
      Step 4: Switch reads to new column
      Step 5: Remove old column
    
    Never: add NOT NULL column without default in one migration while service runs
