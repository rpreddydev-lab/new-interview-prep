================================================================
DATA CONSISTENCY MODELS
================================================================

WHAT IS CONSISTENCY?
---------------------
In a distributed system, consistency refers to whether all nodes in
the system see the same data at the same time.

With a single DB server, consistency is trivial.
With replicas and shards across multiple machines and geographic regions,
consistency becomes a fundamental challenge.

CONSISTENCY SPECTRUM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

From strongest to weakest:

LINEARIZABILITY (Strict Consistency)
  ↓
SEQUENTIAL CONSISTENCY
  ↓
CAUSAL CONSISTENCY
  ↓
READ-YOUR-WRITES CONSISTENCY
  ↓
MONOTONIC READ CONSISTENCY
  ↓
EVENTUAL CONSISTENCY (Weakest)

STRONG CONSISTENCY MODELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LINEARIZABILITY (Strongest):
  All operations appear to execute atomically and in a total order
  that matches real-time ordering.
  Once a write is visible to any client, it's visible to all clients.
  
  Analogy: The system behaves as if there's only one copy of the data,
           and all operations on it are atomic and instantaneous.
  
  Implementation: Single leader + synchronous replication, or Raft/Paxos
  
  Cost: High latency (synchronous replication), unavailable during partition
  
  Use when: Financial transactions, counter operations that must be exact,
             distributed locks, leader election

SEQUENTIAL CONSISTENCY:
  Operations from all processes appear in a single total order.
  Within each process, operations appear in the order they were issued.
  But: not necessarily real-time ordered (may lag behind).
  
  Weaker than linearizability: operations can appear in an order
  that doesn't match wall-clock time.

SERIALIZABLE (Database Isolation):
  In databases, serializability = transactions execute as if they
  ran sequentially, one at a time, with no interleaving.
  
  Note: Serializability ≠ Linearizability
  - Serializability: about transaction isolation
  - Linearizability: about single-operation ordering across replicas
  
  Combined: Strict Serializability (what Spanner, CockroachDB provide)

WEAKER CONSISTENCY MODELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CAUSAL CONSISTENCY:
  Operations that are causally related appear in the same order
  to all processes.
  Concurrent (causally unrelated) operations can appear in different orders.
  
  Example:
  User posts tweet A. Then post tweet B in reply to A.
  All users see A before B (causal dependency respected).
  But: concurrent tweets by different users can appear in any order.
  
  Implementation: Vector clocks, Lamport timestamps
  
  Use for: Social feeds, collaborative editing (preserves causality cheaply)

READ-YOUR-OWN-WRITES (RYOW):
  After a process writes, it always sees its own write on subsequent reads.
  Other processes may still see old values (eventual consistency for them).
  
  Example: You post a tweet → immediately see it on your profile.
           Your friend may not see it for a second.
  
  Implementation: Route the user's reads to primary for some time after write,
                  OR use session token tied to write timestamp.

MONOTONIC READ CONSISTENCY:
  If a process reads a value at time T, it will never read an older
  value at time T+1.
  No "going back in time" (seeing 10 likes → then seeing 8 likes).
  
  Implementation: Route all reads from a session to the same replica.

CONSISTENT PREFIX:
  If a sequence of writes happens in some order, any reader sees
  all writes appear in that order.
  Prevents reading part of a logical sequence.
  
  Example: Post comments where reply must appear after original.
           Consistent prefix ensures you don't see reply before original.

EVENTUAL CONSISTENCY (Weakest):
  If no new updates are made, all replicas will eventually converge
  to the same value.
  In the meantime, different nodes may return different values.
  
  Examples:
  - YouTube view count (may differ slightly across edge nodes)
  - Like/heart counts on posts
  - DNS propagation (old records cached for TTL period)
  - Amazon S3 PUT-after-GET consistency (eventually consistent for a window)
  
  Note: Amazon S3 moved to strong read-after-write consistency in 2020.

CONFLICT RESOLUTION FOR EVENTUAL CONSISTENCY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When multiple replicas accept concurrent writes, conflicts arise.
Must define how to resolve them:

LAST WRITE WINS (LWW):
  Most recent write (by timestamp) wins. Others are discarded.
  Problem: NTP clock skew can cause newer writes to be overwritten.
  Use: Where occasional data loss is acceptable (likes counts).

MERGE / CRDTs (Conflict-free Replicated Data Types):
  Design data structures where merging concurrent changes is always safe.
  
  Examples:
  - G-Counter (grow-only counter): Each node increments its own counter.
    Total count = sum of all nodes' counts. Never conflicts.
  - LWW-Register: Last-writer-wins with logical timestamps.
  - OR-Set (Observe-Remove Set): Add and remove operations without conflicts.
  - Operational Transform: Used in Google Docs for collaborative editing.
  
  Used by: Redis, Riak, Cassandra (counters)

APPLICATION-LEVEL RESOLUTION:
  Present conflicting versions to the application (or user) for resolution.
  Example: Dynamo/DynamoDB returns all conflicting versions (siblings).
           Shopping cart: "You edited your cart from two devices, merge?"
  
  Git merge conflicts are an application-level conflict resolution!

VERSION VECTORS / VECTOR CLOCKS:
  Track causality across replicas.
  Each replica maintains a vector of {node: version} pairs.
  
  [Node_A: 3, Node_B: 2, Node_C: 1]
  
  If writes from two replicas have non-comparable vectors → concurrent → conflict.
  If one dominates → it's the successor → no conflict.

DATABASE TRANSACTION ISOLATION LEVELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Isolation problems:
  DIRTY READ:         Reading uncommitted changes from another transaction
  NON-REPEATABLE READ: Same row read twice gives different values (updated by other txn)
  PHANTOM READ:       Range query returns different rows on repeat (insert by other txn)
  SERIALIZATION ANOMALY: Effect of two transactions is not equivalent to any serial order

Isolation levels (SQL standard):

┌────────────────────┬───────────┬─────────────────┬──────────────┬────────────────────┐
│ Isolation Level    │ Dirty     │ Non-Repeatable  │ Phantom      │ Serialization      │
│                    │ Read      │ Read            │ Read         │ Anomaly            │
├────────────────────┼───────────┼─────────────────┼──────────────┼────────────────────┤
│ Read Uncommitted   │ Possible  │ Possible        │ Possible     │ Possible           │
│ Read Committed     │ Prevented │ Possible        │ Possible     │ Possible           │
│ Repeatable Read    │ Prevented │ Prevented       │ Possible     │ Possible           │
│ Serializable       │ Prevented │ Prevented       │ Prevented    │ Prevented          │
└────────────────────┴───────────┴─────────────────┴──────────────┴────────────────────┘

PostgreSQL defaults: Read Committed
MySQL defaults: Repeatable Read (InnoDB)
Most banking systems: Serializable or Repeatable Read

CHOOSING CONSISTENCY LEVEL IN PRACTICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Strong Consistency Use Cases:
  ✓ Financial transactions (balance must be exact)
  ✓ Inventory management (can't oversell the last item)
  ✓ Seat booking (can't double-book a seat)
  ✓ Distributed locks (only one service holds the lock)
  ✓ User profile updates (user must see their own changes)

Eventual Consistency Use Cases:
  ✓ Social media likes, views, follower counts
  ✓ Website visitor counters
  ✓ Recommendation system data
  ✓ Notification delivery (at-least-once acceptable)
  ✓ DNS caching
  ✓ Shopping cart (Amazon originally designed Dynamo for this)

INTERVIEW ANSWER TEMPLATE:
  "For [X data], I'd use [consistency level] because [reason].
   The trade-off is [cost] but for this use case, [justification].
   If a user needs to see their own writes immediately, I'd ensure
   read-your-own-writes consistency by [mechanism]."
