DESIGN: PAYMENT SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FUNCTIONAL:
  - User pays for a product/service (e-commerce checkout)
  - Payment methods: credit/debit card, PayPal, bank transfer, wallet
  - Pay-in: charge user's payment method
  - Pay-out: transfer money to merchant's bank account
  - Refund processing
  - Payment history / statements
  - Support multi-currency (USD, EUR, GBP, ...)

NON-FUNCTIONAL:
  - 1M transactions/day ≈ 12 transactions/second average
  - Peak: 100 TPS during flash sales
  - EXACTLY-ONCE processing (charging twice = catastrophic, not charging = loss)
  - Consistency: STRONG (ACID) — no eventual consistency for money
  - Audit trail: Every transaction recorded immutably, permanently
  - Reconciliation: System must balance (total debits = total credits)
  - PCI DSS compliance (credit card data handling)
  - Availability: 99.99% (but correctness > availability — fail safe)
  - Latency: p99 < 3 seconds (user waits at checkout)

OUT OF SCOPE: Anti-fraud ML, cryptocurrency, loans


2. CORE CONCEPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DOUBLE-ENTRY BOOKKEEPING (Accounting fundamentals):
  Every financial transaction creates two entries:
    Debit one account, Credit another
  
  User buys $100 product:
    DEBIT  User Wallet Account:       -$100
    CREDIT Merchant Account:          +$100
    (Optional) CREDIT Payment Gateway: +fee
  
  Books must always balance: SUM(debits) = SUM(credits)
  NEVER update or delete ledger entries — ONLY append new entries
  Corrections via reversal entries (not modifying existing records)

IDEMPOTENCY KEY (Critical for exactly-once):
  Every payment operation requires a client-provided idempotency key
  Key = UUID generated by caller, same key on retries
  
  First call: process payment, store (idempotency_key, result)
  Subsequent calls with same key: return stored result, don't process again
  
  This handles: network timeouts, retries, at-most-once → exactly-once

PAYMENT STATES:
  PENDING → PROCESSING → COMPLETED
                      └→ FAILED
                      └→ CANCELLED
  COMPLETED → REFUND_PENDING → REFUNDED

PSP (Payment Service Provider):
  We don't store card numbers. Everything goes through Stripe/Braintree/Adyen.
  PSP handles: card processing, bank networks, 3D Secure authentication
  We store: payment_method_token (reference to PSP's stored card)

4. EXACTLY-ONCE PAYMENT PROCESSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FAILURE SCENARIOS:
  1. Payment created, PSP called, network timeout before response → retry?
     DANGER: If we retry, did we charge twice?
  
  2. PSP charged user, our DB write failed → user charged but order not fulfilled
     DANGER: User loses money, no product

SOLUTION: IDEMPOTENCY + OUTBOX PATTERN

IDEMPOTENCY KEY FLOW:
  Client generates UUID: idempotency_key = "a1b2-c3d4-e5f6"
  
  Payment Service:
    -- Transaction 1: create payment record
    BEGIN TRANSACTION;
    INSERT INTO idempotency_keys (key, status) VALUES (?, 'processing')
      ON CONFLICT (key) DO NOTHING RETURNING id;
    -- If row returned: new request, proceed
    -- If nothing returned: duplicate, look up existing result
    INSERT INTO payments (payment_id, ..., idempotency_key) VALUES (...);
    COMMIT;
    
    -- Call PSP with their own idempotency key:
    stripe.charges.create({ idempotency_key: payment_id })
    
    -- Transaction 2: update payment result
    BEGIN TRANSACTION;
    UPDATE payments SET status = 'COMPLETED', psp_ref = '...' WHERE payment_id = ?;
    INSERT INTO idempotency_keys (key, result_payment_id) VALUES (?, payment_id)
      ON CONFLICT (key) DO UPDATE SET result_payment_id = EXCLUDED.result_payment_id;
    COMMIT;
  
  On retry with same idempotency_key:
    → Find existing payment_id in idempotency_keys table
    → Return existing result (no new charge)

PSP IDEMPOTENCY:
  Stripe, Braintree, Adyen all support idempotency keys on their API
  Stripe: passes our payment_id as their idempotency key
  If we call Stripe twice with same key: guaranteed single charge

WEBHOOK-BASED CONFIRMATION:
  PSP calls us back (webhook) with final charge status
  We don't rely on synchronous response (network can fail)
  
  Stripe webhook: POST /webhooks/stripe
    { "type": "payment_intent.succeeded", "data": {...} }
  
  We update payment status based on webhook, not just API response
  Webhook signature validation: verify HMAC to prevent forgery


5. LEDGER DESIGN (DOUBLE-ENTRY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ACCOUNTS TABLE:
  account_id    BIGINT PRIMARY KEY
  user_id       BIGINT
  account_type  VARCHAR(20)  -- 'user_wallet', 'merchant', 'platform_fee', 'escrow'
  currency      VARCHAR(3)   -- ISO 4217: USD, EUR, GBP

LEDGER_ENTRIES TABLE (APPEND-ONLY — NEVER UPDATE):
  entry_id      BIGINT PRIMARY KEY (Snowflake — time-sortable)
  transaction_id BIGINT
  account_id    BIGINT
  amount        DECIMAL(20,8)  -- positive for credit, negative for debit
  running_balance DECIMAL(20,8) -- computed at time of insert
  created_at    TIMESTAMP
  description   VARCHAR(500)
  
  CONSTRAINT: no UPDATE or DELETE (enforced at DB level via trigger)

EXAMPLE: User buys $100 product, $3 platform fee
  INSERT INTO ledger_entries:
    (account: user_123_wallet,   amount: -100.00, running_balance: 50.00)
    (account: merchant_456,       amount:  +97.00)
    (account: platform_fee,       amount:   +3.00)
  
  Invariant: SUM(amount) across all entries for one transaction = 0
             -100 + 97 + 3 = 0 ✓

BALANCE CALCULATION:
  SELECT SUM(amount) FROM ledger_entries WHERE account_id = ?;
  
  Optimization for large accounts (millions of transactions):
    Store daily balance snapshots:
      (account_id, date, balance_at_end_of_day)
    
    Balance = snapshot_balance + SUM(entries since snapshot date)
    Reduces query from scanning all history to scanning only recent entries

RECONCILIATION:
  Daily job: sum all ledger entries by account
  Compare with PSP settlements (Stripe sends CSV of all charges)
  Discrepancies trigger alerts → manual investigation
  
  "The books must balance" — total credits = total debits across all accounts


6. REFUND PROCESSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Refund = REVERSE the original transaction
  NEVER delete or modify original ledger entries
  CREATE new reversal entries:
  
  Original: user paid $100 to merchant
  Refund:
    (account: merchant_456,       amount: -97.00)
    (account: platform_fee,       amount:  -3.00)
    (account: user_123_wallet,    amount: +100.00)
  
  SUM = 0 ✓, Audit trail intact, original payment preserved


7. PCI DSS COMPLIANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WE NEVER STORE CARD NUMBERS:
  Card details go directly from browser → PSP (Stripe.js handles this)
  Our servers never see the raw PAN (Primary Account Number)
  We store: PSP token only
  
  NEVER log: card numbers, CVV, full PAN in any log
  Monitor: log scanning job to detect accidental card number leaks

NETWORK SEGMENTATION:
  Payment servers in isolated PCI network segment
  No direct internet access from payment DB servers
  All traffic through proxy with audit logging

AUDIT LOGS:
  Every payment API call logged: who, what, when, from where
  Logs shipped to immutable log store (WORM — Write Once Read Many)
  Retention: 7 years (PCI DSS requirement)

INTERVIEW ANSWER — "Design a payment system"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"The core challenge is exactly-once processing. Network timeouts mean
we can't know if a payment went through — retrying could charge twice.

The solution is idempotency keys. The client generates a UUID and passes
it with every payment request. We store it in our DB atomically before
calling the PSP, and we pass the same key to the PSP's API (Stripe,
Braintree all support this). Even if we call Stripe twice, they'll only
charge once and return the same result.

The other critical concern is audit integrity. I use double-entry
bookkeeping with an append-only ledger. Every transaction creates
matching debit/credit entries summing to zero. We NEVER update or delete
ledger entries — corrections are made with new reversal entries.
This gives a complete, tamper-evident audit trail required for both
compliance and reconciliation.

For PSP communication, I don't rely solely on synchronous API responses.
The PSP sends webhooks to confirm final status — we update payment status
based on webhooks, handling the case where our API call returned a timeout
but the PSP actually succeeded.

Card data: we use PSP tokenization (Stripe.js). Raw card numbers never
reach our servers — only tokens. This moves most of PCI DSS compliance
onto Stripe and dramatically reduces our audit scope."
