CLASSIC SYSTEM DESIGN PROBLEMS — OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. FRAMEWORK FOR SOLVING HLD PROBLEMS (7 STEPS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1: CLARIFY REQUIREMENTS (5 minutes)
  Ask functional requirements:
    - What are the core features? (READ vs WRITE heavy?)
    - Who are the users?
    - What does a successful interaction look like?
  
  Ask non-functional requirements:
    - Scale? (DAU, QPS, data size)
    - Latency? (p99 < Xms)
    - Availability? (99.9%? 99.99%?)
    - Consistency? (Strong vs eventual)
    - Durability? (Can we lose data?)
  
  Out of scope (explicitly state):
    "I'll focus on X and Y, leaving Z out of scope for now"

STEP 2: BACK-OF-ENVELOPE ESTIMATION (3 minutes)
  Calculate:
    - QPS (Query Per Second): reads and writes separately
    - Storage: daily data growth × retention period
    - Bandwidth: QPS × average request/response size
    - Cache: hot data size (20% data serves 80% traffic — Pareto principle)
  
  These numbers drive architecture decisions:
    - QPS 100 → single server might be fine
    - QPS 100,000 → horizontal scaling required
    - 10TB/day storage → multi-region object storage required

STEP 3: API DESIGN
  Define key APIs before the architecture
  REST or gRPC? Synchronous or async?
  Request/response formats
  Authentication (where does the token go?)

STEP 4: HIGH-LEVEL ARCHITECTURE
  Draw the major components:
    Client → CDN/Load Balancer → API Gateway → Services → DBs/Caches
  
  Identify the critical data flows:
    - Write path (how data gets created/modified)
    - Read path (how data gets served)

STEP 5: DATA MODEL DESIGN
  What are the key entities?
  How are they related?
  SQL vs NoSQL choice and justification
  Primary keys, indexes, partitioning strategy

STEP 6: DEEP DIVES (most of the interview)
  Pick 2-3 hard problems and go deep:
    - How does the feed generation work?
    - How do you handle hot users?
    - How do you guarantee exactly-once delivery?
    - How does the search work?
    - How do you scale writes?
  
  Show depth of knowledge here — this differentiates candidates

STEP 7: BOTTLENECKS AND TRADE-OFFS
  What are the weaknesses in your design?
  What would you do differently with more time?
  What are the key trade-offs made?

COMMON DEEP DIVE TOPICS:
  - Push vs Pull for feed generation
  - How to handle celebrity/hot user problem
  - Read-heavy vs write-heavy optimization
  - Cache invalidation strategy
  - Data consistency across services
  - Message ordering and deduplication
  - Search and autocomplete
  - CDN strategy for media

3. COMMON PATTERNS ACROSS PROBLEMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCALE PATTERN: Read-heavy systems
  → Cache aggressively (Redis, Memcached)
  → CDN for static content
  → Read replicas for databases
  → Eventual consistency (OK for most social use cases)

SCALE PATTERN: Write-heavy systems
  → Message queues for async processing
  → Write to primary, propagate async
  → Kafka for high-throughput event streams
  → Sharding by user ID or entity ID

FEED GENERATION:
  Push (Fan-out on write): Pre-compute feed for all followers
    Pros: Fast reads (O(1) fetch)
    Cons: Expensive writes for celebrities (10M followers × 1 write)
  
  Pull (Fan-out on read): Compute feed at read time
    Pros: Cheap writes
    Cons: Slow reads (merge N follower feeds at query time)
  
  Hybrid: Push for regular users, pull for celebrities (> 1M followers)
    Twitter uses this approach

MEDIA UPLOAD PATTERN:
  1. Client requests presigned URL from service
  2. Client uploads directly to S3/GCS (no routing through your server)
  3. S3 triggers event notification → processing pipeline
  4. Service updates DB with object location

REAL-TIME FEATURES (chat, notifications):
  WebSockets or SSE for persistent connections
  Scale with sticky sessions + Redis pub/sub
  Or use long polling as simpler fallback

SEARCH:
  Elasticsearch for full-text search
  Inverted index: term → [document_ids]
  Async indexing: Write to primary DB → stream to Elasticsearch


4. ESTIMATION QUICK REFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCALE NUMBERS TO INTERNALIZE:
  Twitter: 300M DAU, 500M tweets/day, 300K QPS peak (reads)
  Instagram: 1B DAU, 100M photos/day, CDN serves 99% of image traffic
  WhatsApp: 2B DAU, 100B messages/day, 65M QPS
  YouTube: 2B DAU, 500 hours of video uploaded per minute
  Uber: 100M DAU, 15M trips/day, location update every 4 seconds per driver

STORAGE PER UNIT:
  1 tweet: ~300 bytes
  1 photo (compressed): ~300KB
  1 video (1 minute, 1080p): ~150MB
  1 user record: ~1KB
  1 URL entry: ~500 bytes

TIME CONVERSIONS (memorize):
  1 day = 86,400 seconds ≈ 100K seconds
  1 month ≈ 30 days = 2.5M seconds
  1 year ≈ 365 days = 30M seconds

QPS CALCULATION:
  DAU × actions per user per day / 86,400
  Example: 100M DAU, 10 reads/day average
           Read QPS = 100M × 10 / 86,400 = ~12,000 QPS
           Peak QPS = average × 2-3× = ~30,000 QPS

STORAGE CALCULATION:
  Twitter: 500M tweets/day × 300 bytes = 150GB/day
           10-year retention: 150GB × 3,650 days ≈ 550TB
           With replication (3×): 1.6 PB total

INTERVIEW TIP: HOW TO STAND OUT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Drive the discussion — don't wait to be asked
2. State trade-offs proactively — "I chose X over Y because..."
3. Acknowledge limitations — "This design breaks if..."
4. Show depth on 1-2 components rather than breadth across all
5. Use real numbers — "At 100K QPS, we need N servers because..."
6. Connect to real systems — "Twitter uses a similar approach..."
7. Ask clarifying questions early — avoid designing the wrong thing
8. Time management — don't spend all time on requirements

RED FLAGS (what to avoid):
  - Jumping to solution before understanding requirements
  - Ignoring non-functional requirements (scale, latency, availability)
  - Designing without considering failure modes
  - Not knowing the cost/latency of operations (RAM, disk, network, CPU)
  - "I'd use Kafka for everything" without justification
