LOW-LEVEL DESIGN (LLD) OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT IS LLD?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LLD focuses on the IMPLEMENTATION details of a system component:
  - Class hierarchy and object structure
  - Methods, attributes, and their access levels
  - Relationships between classes
  - Design patterns to solve recurring problems
  - Code organization and module structure

HLD vs LLD:
  HLD: "We'll use microservices. The notification service will use Kafka
        and publish to APNs/FCM for push delivery."
  
  LLD: "The NotificationService class has a sendNotification(userId, template, payload)
        method. It has a dependency on INotificationChannel interface. PushChannel
        and EmailChannel implement INotificationChannel. A NotificationFactory creates
        the correct channel based on user preferences. PriorityQueue<Notification>
        holds pending notifications sorted by priority."

WHY LLD MATTERS IN INTERVIEWS:
  Top companies (Amazon, Google, Meta, Stripe) test LLD because:
    - Clean code shows depth of software engineering skill
    - OOP mastery: inheritance, composition, polymorphism
    - Design pattern knowledge signals senior-level thinking
    - Ability to model complex domains as manageable abstractions


2. OOP FUNDAMENTALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FOUR PILLARS:

1. ENCAPSULATION: Bundle data and methods; hide internal state
   - Private fields, public methods
   - Benefits: controlled access, validation in setters, change internals freely

2. ABSTRACTION: Expose what is necessary, hide complexity
   - Abstract classes, interfaces
   - "What it does" vs "how it does it"

3. INHERITANCE: IS-A relationship (subclass is a specialized type)
   - ElectricCar IS-A Car IS-A Vehicle
   - Inherits base behavior, overrides specific parts
   - Prefer COMPOSITION over inheritance for flexibility

4. POLYMORPHISM: Same interface, different implementations
   - Method overriding (runtime polymorphism)
   - Method overloading (compile-time polymorphism)
   
   Shape s = new Circle();   // s can be Circle, Square, Triangle
   s.calculateArea();         // calls Circle's implementation


3. SOLID PRINCIPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

S — Single Responsibility Principle (SRP):
  A class should have ONLY ONE reason to change
  BAD: UserService handles authentication, database operations, and email sending
  GOOD: AuthService, UserRepository, EmailService — each does one thing
  
  Real-world violation: "God class" with 2,000 lines and 50 methods

O — Open/Closed Principle (OCP):
  Open for extension, CLOSED for modification
  Add new features by adding new classes, not editing existing ones
  BAD: if (channel == "email") {...} else if (channel == "sms") {...}
  GOOD: NotificationChannel interface → EmailChannel, SMSChannel, PushChannel
        Add new channel: implement interface, no existing code changed

L — Liskov Substitution Principle (LSP):
  Subclasses must be substitutable for their base class
  BAD: Rectangle subclass Square — setWidth(5) changes height too → breaks
  GOOD: separate Shape hierarchy where substitution holds
  
  "If it quacks like a duck but breaks like a duck in all scenarios,
  it shouldn't be a Duck subclass"

I — Interface Segregation Principle (ISP):
  Clients shouldn't depend on methods they don't use
  BAD: IAnimal { fly(), swim(), run() } — Penguin forced to implement fly()
  GOOD: IFlyable { fly() }, ISwimmable { swim() }
        Bird implements IFlyable, Fish implements ISwimmable

D — Dependency Inversion Principle (DIP):
  Depend on abstractions, not concretions
  BAD: OrderService directly instantiates MySQLOrderRepository
  GOOD: OrderService depends on IOrderRepository interface
        MySQLOrderRepository implements IOrderRepository
        → easy to switch to DynamoDBOrderRepository
        → easy to mock in unit tests


4. DESIGN PATTERNS — OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CREATIONAL PATTERNS (how objects are created):
  
  SINGLETON: Exactly one instance of a class
    ConfigManager.getInstance() — one config object shared everywhere
    Thread-safe: double-checked locking or Enum singleton (Java)
    Use sparingly: hard to test, hidden global state
  
  FACTORY: Create objects without specifying exact class
    NotificationFactory.create(type) → EmailNotification or PushNotification
    Decouple creation from usage
  
  ABSTRACT FACTORY: Factory of factories
    UIFactory → WindowsUIFactory or MacUIFactory
    Each factory creates a family of related objects
  
  BUILDER: Construct complex objects step by step
    Person.builder().name("Alice").age(30).email("alice@example.com").build()
    Avoids telescoping constructors, handles optional params

  PROTOTYPE: Clone existing objects
    objectA.clone() → deep copy with same state
    Useful when object creation is expensive (complex graph structures)

STRUCTURAL PATTERNS (how objects are composed):
  
  ADAPTER: Make incompatible interfaces work together
    LegacyPaymentGateway → StripeAdapter implementing IPaymentGateway
    Wraps old interface to match new expected interface
  
  DECORATOR: Add behavior dynamically without subclassing
    Coffee → MilkDecorator(Coffee) → SugarDecorator(MilkDecorator(Coffee))
    LoggingDecorator → CachingDecorator → DatabaseRepository
  
  FACADE: Simplified interface to complex subsystem
    HomeTheaterFacade.watchMovie() → turns on projector, dims lights, sets input
  
  COMPOSITE: Tree structure where nodes and leaves treated uniformly
    FileSystem: File and Directory both implement FileSystemItem
    Directory.getSize() recursively sums children
  
  PROXY: Surrogate object with same interface
    Types: Virtual (lazy load), Protection (access control), Remote (network call)
    LazyLoadProxy: only creates expensive object when first accessed

BEHAVIORAL PATTERNS (how objects communicate):
  
  OBSERVER: One-to-many dependency; subject notifies observers on change
    EventBus, event listeners, MVC (Model notifies Views)
  
  STRATEGY: Family of algorithms, interchangeable at runtime
    SortStrategy: QuickSort, MergeSort, BubbleSort — swap without changing caller
    PricingStrategy: StandardPricing, SurgePricing, DiscountPricing
  
  COMMAND: Encapsulate request as object
    Supports undo/redo, queueing, logging
    TextEditor: BoldCommand, ItalicsCommand, UndoCommand
  
  TEMPLATE METHOD: Define skeleton in base class, subclasses fill in steps
    DataParser base class: parseData() calls readData(), processData(), saveData()
    CSVParser and JSONParser override individual steps
  
  STATE: Object behavior changes based on internal state
    ATM: IdleState, CardInsertedState, AuthenticatedState, TransactionState
    Different methods available in each state
  
  CHAIN OF RESPONSIBILITY: Pass request through chain of handlers
    Request → AuthMiddleware → RateLimitMiddleware → LoggingMiddleware → Handler
  
  ITERATOR: Traverse collection without knowing internal structure
    for (User user : users) — hides whether users is array, list, tree
  
  MEDIATOR: Central hub for object communication
    ChatRoom mediates messages between users (no direct user-user coupling)


5. RELATIONSHIPS BETWEEN CLASSES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IS-A (Inheritance):
  Dog IS-A Animal
  Use when subtype is a true specialization of base type
  Override behaviors that differ

HAS-A (Composition/Aggregation):
  Car HAS-A Engine (composition — engine dies with car)
  Library HAS-A Books (aggregation — books exist independently)
  
  PREFER COMPOSITION OVER INHERITANCE:
    Inheritance creates tight coupling
    Composition is more flexible: change behavior at runtime by swapping components

USES-A (Dependency):
  PaymentService USES-A Logger (passed as constructor parameter)
  Loosest coupling — just uses the other object temporarily

  ───────────> Dependency (dashed arrow)

  ◇─────────── Aggregation (empty diamond at owner)
  ◆─────────── Composition (filled diamond at owner)
  △─────────── Inheritance (open triangle at parent)
  △─ ─ ─ ─ ─  Interface implementation (open triangle, dashed line)
