LLD APPROACH AND PROCESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. THE 5-STEP LLD PROCESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1: CLARIFY REQUIREMENTS (2-3 minutes)
  Ask functional questions:
    - What entities/actors are involved?
    - What operations must be supported?
    - Any edge cases to handle? (concurrent access, invalid input)
  
  Example: "Design a parking lot"
    - What types of vehicles? (car, motorcycle, truck, bus)
    - Multiple floors? Multiple entry/exit gates?
    - What pricing model? (hourly, daily, flat rate)
    - Do spots have different sizes?

STEP 2: IDENTIFY CORE ENTITIES (classes)
  Noun extraction: scan the problem for key nouns → classes
  
  "A parking lot has multiple floors. Each floor has spots.
  Vehicles enter through a gate and park in spots."
  
  Nouns: ParkingLot, Floor, ParkingSpot, Vehicle, Gate, Ticket, Payment
  
  For each entity ask:
    - What does it KNOW? (attributes)
    - What can it DO? (methods)
    - Who does it collaborate with? (relationships)

STEP 3: DEFINE RELATIONSHIPS
  For each pair of entities, determine:
    - IS-A: inheritance (Vehicle ← Car, Truck, Motorcycle)
    - HAS-A: composition/aggregation (ParkingLot has Floors, Floor has Spots)
    - USES: dependency (ParkingService uses PricingStrategy)
  
  Build a mental class diagram before writing code

STEP 4: IDENTIFY DESIGN PATTERNS
  Look for recurring patterns in the requirements:
  
  "Different pricing based on vehicle type or time" → Strategy
  "Need one ParkingLot instance" → Singleton
  "Different Vehicle types" → Inheritance hierarchy / Factory
  "Gate needs to notify system on entry/exit" → Observer
  "Multiple payment methods" → Strategy or Factory
  "Complex ticket creation" → Builder

STEP 5: CODE THE CLASSES
  Start with:
    1. Interfaces / abstract classes (contracts)
    2. Enums (status values, types)
    3. Core entity classes (with attributes)
    4. Service/manager classes (orchestration logic)
  
  Write the most important methods in full
  Sketch less important ones with brief comments


2. IDENTIFYING CLASSES — EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM: "Design an online bookstore"
  
  Actors: Customer, Admin
  Core entities: Book, Author, Category, Cart, Order, OrderItem, Payment
  Support entities: Inventory, Review, Address, Coupon
  
  Services (orchestration): CartService, OrderService, PaymentService, SearchService
  
  Patterns:
    Observer: Order status change → notify Customer via email/SMS
    Strategy: Payment method (CreditCard, PayPal, Wallet)
    Decorator: Book with/without priority shipping, with/without gift wrapping
    Iterator: Search results pagination

PROBLEM: "Design a ride-sharing system (LLD)"
  
  Actors: Rider, Driver
  Core entities: User, Trip, Location, Vehicle, Payment
  
  Patterns:
    State: Trip state machine (REQUESTED → ACCEPTED → IN_PROGRESS → COMPLETED)
    Observer: Driver notified when trip requested
    Strategy: Fare calculation (UberX, UberPool, UberXL)
    Factory: TripFactory based on ride type


3. ATTRIBUTES AND METHODS — WHAT TO INCLUDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ATTRIBUTES: Properties that define the entity's state
  - Include: ID (always), key domain properties, status, timestamps
  - Omit: Logger, connection pools (infrastructure concerns, not domain)
  
  ParkingSpot attributes: spotId, floorNumber, spotType (SMALL/MEDIUM/LARGE),
                          status (AVAILABLE/OCCUPIED), vehicleId (if occupied)
  
  Car attributes: licensePlate, vehicleType (CAR), color (optional), ownerId

METHODS: Operations the entity can perform
  CRUD operations: create, read, update, delete (for repositories)
  Business logic: calculateFare(), assignDriver(), isAvailable()
  State transitions: startTrip(), completeTrip(), cancelTrip()
  
  Don't over-spec: "I'll add getter/setters for all fields" is fine to state,
                   then focus on interesting business methods

ACCESS MODIFIERS:
  private: internal state (fields, helper methods)
  protected: accessible to subclasses
  public: external interface (API surface)
  
  Rule: fields are private, accessed via methods; public methods form the API

STATIC vs INSTANCE:
  Static: utility/factory methods (PricingStrategy.calculate()),
          constants (MAX_FLOORS = 10)
  Instance: operations on specific objects (spot.park(vehicle))


4. HANDLING CONCURRENCY IN LLD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

COMMON CONCURRENT SCENARIOS:
  - Two threads try to park in same spot simultaneously
  - Two users try to book same hotel room
  - Multiple threads update shared counter (seat count)

APPROACHES:

1. SYNCHRONIZED METHODS (Java):
   public synchronized ParkingTicket park(Vehicle vehicle) { ... }
   Simple but coarse-grained — entire method locked at once

2. REENTRANT LOCK (more fine-grained):
   private final ReentrantLock spotLock = new ReentrantLock();
   
   public boolean park(Vehicle vehicle) {
       if (spotLock.tryLock()) {
           try {
               if (status == AVAILABLE) {
                   status = OCCUPIED;
                   this.vehicle = vehicle;
                   return true;
               }
           } finally {
               spotLock.unlock();
           }
       }
       return false;
   }

3. OPTIMISTIC LOCKING (database-backed):
   version field in entity
   UPDATE spots SET status='OCCUPIED', version=version+1
   WHERE spot_id=? AND version=? AND status='AVAILABLE'
   
   If 0 rows updated: another thread got there first → retry

4. THREAD-SAFE DATA STRUCTURES:
   ConcurrentHashMap<String, ParkingSpot> spotMap  (instead of HashMap)
   AtomicInteger availableSpotCount                 (instead of int)
   BlockingQueue<Vehicle> waitingQueue              (for waiting vehicles)


5. INTERVIEW PRESENTATION TIPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT INTERVIEWERS LOOK FOR:

1. REQUIREMENTS CLARITY: Did you clarify scope before designing?
2. CORRECT ABSTRACTION LEVEL: Classes model real concepts, not just data containers
3. SOLID PRINCIPLES: Especially SRP (no God classes) and OCP (extensible)
4. APPROPRIATE DESIGN PATTERNS: Used where they add value, not everywhere
5. CLEAN CODE: Meaningful names, small focused methods, no magic numbers
6. CONCURRENCY AWARENESS: Acknowledge thread safety issues and how to handle

COMMON MISTAKES:
  ✗ Jumping to code without discussing requirements
  ✗ Making everything static (no OOP)
  ✗ Not using interfaces — hardcode concrete types everywhere
  ✗ Missing enums for states/types (using strings "AVAILABLE" everywhere)
  ✗ Ignoring concurrent access to shared resources
  ✗ Too deep inheritance hierarchy (> 2 levels is usually a smell)
  ✗ Not explaining WHY you chose a pattern

GOOD ANSWER STRUCTURE:
  "For the [entity], I'd model it as [class] with attributes [list].
   The relationship with [other entity] is [type] because [reason].
   For [behavior], I'll use [pattern] because it gives us [benefit].
   One thing to consider is concurrency — [how you handle it]."

TIME MANAGEMENT (45-minute LLD interview):
  5 min: Requirements clarification
  5 min: Entity identification and relationships (draw diagram)
  5 min: Design patterns + data structures
  25 min: Code core classes
  5 min: Extensions, concurrency, edge cases
