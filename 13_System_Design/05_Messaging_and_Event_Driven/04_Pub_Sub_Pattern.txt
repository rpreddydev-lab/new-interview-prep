================================================================
PUB/SUB PATTERN
================================================================

WHAT IS PUB/SUB?
-----------------
Publish-Subscribe (Pub/Sub) is a messaging pattern where:
  - Publishers send messages to a TOPIC (not to specific subscribers)
  - Subscribers register interest in topics they care about
  - The broker delivers messages to all interested subscribers
  - Publishers and subscribers are fully decoupled

Publishers don't know who subscribes.
Subscribers don't know who publishes.
The broker mediates all communication.

PUB/SUB vs MESSAGE QUEUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Message Queue:      1 producer → 1 consumer (competing consumers for load balance)
Pub/Sub:            1 publisher → N subscribers (fan-out)

Queue: "Someone process this work item."
Pub/Sub: "This thing happened. Everyone who cares, react."

PUB/SUB ARCHITECTURES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BASIC PUB/SUB (Redis Pub/Sub):
  Publisher publishes to a channel.
  All subscribers to that channel receive the message.
  No persistence: if subscriber is offline, message is lost.
  
  PUBLISH user-events '{"userId":"123","action":"login"}'
  SUBSCRIBE user-events    ← all current subscribers get it
  
  Use for: Real-time notifications, chat rooms, live updates
  Limitation: No replay, no persistence, no ACK

DURABLE PUB/SUB (Kafka Consumer Groups):
  Topics are persistent.
  Each consumer group is an independent subscriber.
  Groups track their offset independently.
  
  Topic: user-events
  Consumer Group 1 (Analytics): reads all events independently
  Consumer Group 2 (Notifications): reads all events independently
  Consumer Group 3 (Audit): reads all events independently
  
  Each group can be at a different offset.
  New consumer groups can read from the beginning (replay).

MANAGED PUB/SUB (AWS SNS + SQS):
  SNS (Simple Notification Service): pub/sub, fan-out
  SQS (Simple Queue Service): durable queue, at-least-once
  
  Combined: SNS topic → multiple SQS queues (fan-out queue pattern)
  
  OrderService publishes to SNS topic "order-created":
  → SQS queue for InventoryService
  → SQS queue for EmailService
  → SQS queue for AnalyticsService
  
  Each SQS queue holds messages independently.
  If EmailService is down: messages wait in its SQS queue.
  When EmailService recovers: processes messages from queue.
  
  Benefits:
  ✓ Fan-out: one SNS publish → many SQS queues
  ✓ Durability: SQS persists messages (up to 14 days)
  ✓ Independent scaling: each service scales independently
  ✓ Isolation: EmailService slowness doesn't affect InventoryService

REAL-WORLD USE CASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. NOTIFICATIONS (Uber):
   Driver accepts a ride → "TripAccepted" event published.
   Subscribers:
   - Push notification service (send notification to rider)
   - Tracking service (update map)
   - Analytics service (log event)
   - Pricing service (start metering)
   All react independently.

2. STOCK PRICES (Finance):
   Market data feed publishes stock price ticks.
   Many subscribers: trading algorithms, dashboards, alerting systems.

3. SOCIAL MEDIA FEED (Twitter):
   User tweets → "TweetCreated" event.
   Timeline service subscribes (fan-out to followers' feeds).
   Notification service subscribes (notify @mentioned users).
   Analytics subscribes.

4. MICROSERVICE COORDINATION:
   User profile updated → "UserProfileUpdated" event.
   All services that cache user data subscribe and invalidate cache.

FILTERING AND ROUTING IN PUB/SUB
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TOPIC-BASED FILTERING:
  Subscribe to specific topics.
  Simple, fast routing.
  Example: Subscribe to "orders.created" but not "orders.updated".

CONTENT-BASED FILTERING:
  Subscribe with filter expressions.
  Broker evaluates each message against subscriber's filter.
  
  Example (AWS SNS):
  Subscriber A filter: { "region": ["US", "CA"] }
  Subscriber B filter: { "region": ["EU"], "amount": [{"numeric": [">=", 1000]}] }
  
  Only matching messages are delivered to each subscriber.
  
  Use: Route different categories of events to different consumers
       without creating separate topics for every combination.

PUSH vs PULL DELIVERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PUSH (Webhook / HTTP endpoint):
  Broker calls subscriber's HTTP endpoint with each message.
  Subscriber must be running and reachable.
  Broker handles delivery retries on failure.
  
  Use: Serverless functions (Lambda), webhooks, simple subscribers.
  Risk: Subscriber overwhelmed if messages come faster than it can process.

PULL (Consumer polls broker):
  Consumer polls broker when ready for more messages.
  Consumer controls its own throughput.
  Naturally handles backpressure.
  
  Use: Kafka, SQS, high-throughput consumers.
  Kafka default: consumer polls, gets batch of records.

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Pub/Sub is a messaging pattern where publishers send to topics and
 multiple subscribers independently receive those messages. Publishers
 don't know who subscribes; subscribers don't know who publishes.
 
 For [this system], I'd use the SNS+SQS fan-out pattern:
 - SNS topic receives events from producers
 - Each consuming service has its own SQS queue subscribed to SNS
 - This gives each service durable, independent message delivery
 - A slow consumer doesn't affect other consumers
 - Services can scale their SQS consumers independently
 
 Alternatively, Kafka with consumer groups achieves the same fan-out
 with replay capabilities, better for high-throughput or if you need
 to rebuild state from historical events."
