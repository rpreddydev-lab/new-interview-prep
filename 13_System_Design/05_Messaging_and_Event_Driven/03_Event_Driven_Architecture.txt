================================================================
EVENT-DRIVEN ARCHITECTURE (EDA)
================================================================

WHAT IS EVENT-DRIVEN ARCHITECTURE?
------------------------------------
A design pattern where components communicate by producing and consuming events.
Services are decoupled: they don't call each other directly.
Instead, they react to events published by other services.

EVENT: An immutable record that something happened.
  - Events describe FACTS: "OrderWasPlaced", "PaymentWasProcessed"
  - Past tense: the thing already happened
  - Immutable: don't change an event, create a new one
  - Timestamped: when did it happen?
  - Contains context: order ID, user ID, amount, items

EVENT vs COMMAND:
  Command: "PlaceOrder" — a request to DO something (imperative)
           Can be rejected. Synchronous or async.
  Event:   "OrderPlaced" — a record that something HAPPENED
           Cannot be rejected. Always in past tense.

EDA PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. EVENT NOTIFICATION:
   Service emits event as a notification that something happened.
   Other services react if interested.
   Event carries minimal data (just what changed).
   Consumers fetch details from source service if needed.
   
   Example:
   Order Service → publishes: { eventType: "OrderPlaced", orderId: "123" }
   Inventory Service → on "OrderPlaced": call Order API to get details → update inventory
   Email Service → on "OrderPlaced": call Order API to get details → send email
   
   Pro: Event is small, source service controls data.
   Con: Consumers make extra API calls (potential for circular dependencies).

2. EVENT-CARRIED STATE TRANSFER:
   Event carries ALL the data consumers need. No callback to source.
   
   Example:
   Order Service → publishes: {
     eventType: "OrderPlaced",
     orderId: "123",
     userId: "456",
     items: [{ productId: "789", qty: 2 }],
     totalAmount: 59.99,
     shippingAddress: {...}
   }
   
   Inventory Service → reads items from event, updates inventory directly.
   Email Service → reads userId and items, sends email directly.
   
   Pro: Consumers are self-contained, no extra API calls.
   Con: Events are large; consumers cache stale data from events.

3. EVENT SOURCING:
   Store all state changes as a sequence of events.
   Current state = replay all events from the beginning.
   
   Example: Bank Account
   Events: [AccountOpened(0), Deposited(100), Withdrew(30), Deposited(50)]
   Current balance: 0 + 100 - 30 + 50 = 120
   
   "Account" object is not stored — ONLY the events are stored.
   To get current state: load and replay all events.
   
   (See Event Sourcing file for deep dive.)

ADVANTAGES OF EDA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. TEMPORAL DECOUPLING:
   Producer doesn't need consumer to be running when event is published.
   Consumer processes events when it's ready.
   Survives: consumer downtime, deployments, traffic spikes.

2. SPATIAL DECOUPLING:
   Producer doesn't know WHO consumes the event.
   New consumers can be added without changing producer.
   Easy to add new features by subscribing to existing events.

3. SCALABILITY:
   Consumers scale independently.
   Message queue / broker buffers spikes.
   Multiple consumer instances process events in parallel.

4. RESILIENCE:
   Producer failure doesn't affect consumers (events already in broker).
   Consumer failure: events wait in broker until consumer recovers.

5. AUDIT LOG:
   All events are persisted (with Kafka's retention).
   You have a complete history of everything that happened.
   Replay events to recreate state or debug issues.

CHALLENGES OF EDA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. EVENTUAL CONSISTENCY:
   After publishing event, consumers update asynchronously.
   There's a window where data is inconsistent across services.
   Must design UI/UX to handle this (optimistic updates).

2. COMPLEX DEBUGGING:
   Request flow spans multiple services via events.
   Need distributed tracing to correlate events.
   Correlation ID in event headers.

3. EVENT SCHEMA EVOLUTION:
   Events are published to many consumers.
   Changing event structure can break consumers.
   
   Schema Registry: Centralized repository of event schemas.
   Use Avro or Protobuf with schema evolution rules.
   Rules: Only add optional fields; never remove fields; never change types.
   
   Backward compatible: New consumer reads old events.
   Forward compatible:  Old consumer reads new events (ignores new fields).

4. ORDERING ISSUES:
   Events may arrive out of order (different partitions, different consumers).
   Design consumers to be tolerant of out-of-order events.
   Or: Use a single partition for causally related events (but limits parallelism).

5. IDEMPOTENT CONSUMERS (CRITICAL):
   Events may be delivered more than once (at-least-once delivery).
   Consumers MUST be idempotent: processing the same event twice = same result.
   
   Implementation: Track processed event IDs in DB.
   Before processing: check if eventId already processed → skip if yes.
   After processing: record eventId as processed.

SAGA PATTERN IN EDA (Orchestration and Choreography)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CHOREOGRAPHY (Pure EDA):
  Each service reacts to events and publishes its own.
  No central coordinator.
  
  OrderService → OrderCreated →
    InventoryService reacts → InventoryReserved →
      PaymentService reacts → PaymentProcessed →
        ShippingService reacts → OrderShipped →
          OrderService reacts → marks order complete
  
  On failure: each service publishes compensation events.

ORCHESTRATION:
  A central SagaOrchestrator tells services what to do.
  Uses events (or direct calls) to communicate.
  Orchestrator tracks state.

(Full detail in Distributed Transactions and Microservices sections.)

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Event-driven architecture decouples services by having them communicate
 through events rather than direct API calls. Services publish facts
 ('OrderPlaced') to a message broker; interested services subscribe and
 react independently. This provides temporal and spatial decoupling,
 improves resilience, and enables easy extensibility.

 The main challenges are: eventual consistency (must design for it),
 idempotent consumers (events may be delivered multiple times), and
 schema evolution (events must be versioned carefully).

 For [this system], I'd use Kafka as the event bus. Events would carry
 enough state for consumers to act without calling back to the producer.
 All consumers would use correlation IDs for distributed tracing and
 idempotency keys to handle duplicate delivery safely."
