METRICS AND MONITORING — PROMETHEUS, GRAFANA, SLOs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT ARE METRICS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Metrics: numeric measurements aggregated over time

  Characteristics:
    Low cardinality: not per-request; aggregated across many requests
    Cheap to store: a number per time interval, not full event data
    Fast to query: pre-aggregated, time-series database
    Best for: trends, thresholds, alerting, dashboards

  Format: metric_name{label1="value1", label2="value2"} numeric_value timestamp
  Example: http_requests_total{service="order-service", status="500", method="POST"} 42 1706400000


2. METRIC TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  COUNTER: monotonically increasing number (never decreases, resets to 0 on restart)
    Use for: request count, error count, bytes sent, tasks completed
    Example: http_requests_total
    Query: rate(http_requests_total[5m]) → per-second rate over 5 minutes
    Never: use counter for a value that goes up AND down

  GAUGE: current value that can go up or down
    Use for: current memory usage, active connections, queue depth, temperature
    Example: memory_usage_bytes, active_connections
    Query: memory_usage_bytes > 0.8 * total_memory → alert

  HISTOGRAM: distribution of observed values in configurable buckets
    Use for: request latency, payload sizes
    Buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10] seconds
    Produces: {_bucket le="0.1"}, {_count}, {_sum}
    Query: histogram_quantile(0.99, rate(http_duration_bucket[5m])) → p99 latency
    
  SUMMARY: pre-calculated quantiles (calculated client-side)
    Pros: accurate quantiles; Cons: cannot aggregate across instances
    Use histogram for multi-instance systems; summary for single-process


3. PROMETHEUS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Architecture:
  Pull model: Prometheus scrapes /metrics endpoint every 15s
  App exposes: http://service:8080/metrics (Prometheus format)
  Prometheus: stores in local TSDB (time-series database)

  vs Push model (StatsD, InfluxDB telegraf):
    Pull: Prometheus knows which targets exist; self-healing discovery
    Push: works through firewalls, good for short-lived jobs (Pushgateway)

Service Discovery:
  Static: list of IPs in prometheus.yml
  Dynamic: Kubernetes SD (auto-discovers pods by label selectors)
    kubernetes_sd_config: watches k8s API → updates scrape targets

Retention:
  Local TSDB: 15 days default
  Long-term: Cortex, Thanos (query across multiple Prometheus instances)
  Thanos: deduplication, object storage (S3/GCS), global view

PromQL (Prometheus Query Language):
  rate(http_requests_total{status="500"}[5m])
    → per-second rate of 5xx errors, averaged over 5 minutes
  
  sum by (service) (rate(http_requests_total[5m]))
    → total request rate per service
  
  histogram_quantile(0.99, sum by (le, service) (rate(http_duration_bucket[5m])))
    → p99 latency per service across all instances
  
  increase(payment_processed_total[1h])
    → total payment count in last 1 hour

CARDINALITY WARNING:
  Labels create a time series per unique combination
  Good: {service="checkout"} — 5 services = 5 series
  BAD: {user_id="12345"} — 10M users = 10M series → OOM
  Rule: never use high-cardinality values (user_id, order_id, trace_id) as metric labels


4. GRAFANA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grafana: universal visualization layer for metrics (and logs/traces)

  Data sources: Prometheus, InfluxDB, Elasticsearch, Loki, CloudWatch, Datadog, etc.
  Panels: Time series, Stat, Gauge, Bar chart, Heatmap, Table
  Variables: dropdown selectors that filter all panels simultaneously
  Annotations: mark deploy times, incidents on graphs

Essential dashboards to build:
  Service Overview: RED method (Rate, Error rate, Duration p50/p95/p99)
  Infrastructure: USE method (CPU util, memory, disk I/O, network)
  Business Metrics: order volume, revenue, active users
  SLO dashboard: current error budget remaining, burn rate

Dashboard-as-code:
  Grafonnet (Jsonnet), Grafana Terraform provider
  Store dashboards in Git, review via PR, deploy via CI/CD


5. SLIs, SLOs, SLAs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  SLI (Service Level Indicator): metric that measures service quality
    Request success rate, p99 latency, availability (uptime), throughput

  SLO (Service Level Objective): target value for an SLI (internal goal)
    "99.9% of requests return 2xx with latency < 200ms"
    "System available 99.95% of time per 30-day rolling window"
    SLO is set by the engineering team; not contractual

  SLA (Service Level Agreement): contractual commitment to customers
    "We guarantee 99.9% availability; if we miss, you get service credits"
    Usually a subset of the SLO (SLO=99.95%, SLA=99.9% — buffer built in)

  ERROR BUDGET:
    100% - SLO = error budget
    99.9% SLO → 0.1% budget → 43.8 min/month of allowed downtime
    
    Key insight: error budget makes reliability a shared conversation
    "We have 40 min error budget left this month — is this deploy safe?"
    Engineering and product jointly own reliability

  Error Budget Policy:
    Budget plentiful (>50%): ship features aggressively
    Budget at 50%: slow deployments, increase testing
    Budget depleted: freeze deployments, focus on reliability


6. SLO-BASED ALERTING (vs Threshold Alerting)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem with threshold alerting:
  Alert if error rate > 1% → fires constantly for brief spikes (alert fatigue)
  Alert if error rate > 5% → misses sustained 2% error rate burning budget

BURN RATE ALERTING (Google SRE recommendation):
  Alert when you're burning error budget too fast to survive the month

  Example: 99.9% SLO → 0.1% error budget per month
    Normal burn rate = 1× (exactly uses budget in 30 days)
    If burning at 14×: budget exhausted in 30/14 = ~2 days → ALERT!

  Multi-window alerting (catches both fast and slow burns):
    Fast burn: error rate > 14× normal in last 1h AND last 5min
      Page immediately (2% of monthly budget burned in 1 hour)
    Slow burn: error rate > 3× normal in last 6h AND last 30min
      Ticket/warning (20% of monthly budget burned in 6 hours)

  PromQL:
    # Error rate
    job:slo_errors:ratio1h = rate(errors[1h]) / rate(requests[1h])
    
    # Burn rate alert: 14× over 1h window
    (job:slo_errors:ratio1h / 0.001) > 14


7. METRICS BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Naming conventions:
  <namespace>_<subsystem>_<name>_<unit>
  http_server_request_duration_seconds
  order_service_payments_total
  cache_hit_ratio (no unit suffix for ratios)

Units:
  Always use base units: seconds (not milliseconds), bytes (not megabytes)
  Prometheus conventions: _total (counters), _bucket (histograms), _info (metadata)

Recording rules:
  Pre-compute expensive PromQL queries into new metrics
  Run during ingestion, not query time → dashboards load instantly
  
  rule: job:http_inbound_requests:rate5m
    expr: sum by (job) (rate(http_requests_total[5m]))

Avoid:
  Using metrics for debugging (use traces/logs instead)
  High-cardinality labels (will OOM Prometheus)
  Tracking per-user data in metrics (use logs or events)
