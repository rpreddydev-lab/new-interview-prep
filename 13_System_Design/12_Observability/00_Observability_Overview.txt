OBSERVABILITY OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT IS OBSERVABILITY?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Observability: the ability to understand the internal state of a system
by examining its external outputs (logs, metrics, traces).

Origin: control theory — a system is "observable" if you can determine
its internal state from its external outputs.

MONITORING vs OBSERVABILITY:
  Monitoring: watching known failure modes with pre-defined dashboards
    "Is the CPU above 80%?" — you know what to look for in advance
    Good for expected problems, bad for unknown unknowns

  Observability: asking arbitrary questions about behavior you didn't anticipate
    "Why is user 12345's checkout slow only on Tuesdays in Europe?"
    Requires rich, queryable telemetry data


2. THREE PILLARS OF OBSERVABILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Logs ─── Metrics ─── Traces

     LOGS                    METRICS                 TRACES
  What happened           What happened           How it happened
  Discrete events         Aggregated numbers      Request journey
  "Order #123 failed"     "Error rate: 2.1%"      "Request took 850ms:
                                                   auth=10, DB=800, cache=40"
  High detail             Low cardinality         Request-level
  High storage cost       Low storage cost        Medium storage cost
  Ad-hoc queries          Pre-aggregate queries   Flow visualization

THE FOURTH PILLAR (increasingly mentioned):
  Profiling: continuous CPU/memory profiling in production (Pyroscope, Parca)
  Events: structured business events (beyond error logs)


3. OBSERVABILITY vs MONITORING (interview distinction)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  "Monitoring tells you when something is wrong.
   Observability tells you WHY it is wrong."

  Monitoring: you define alerts for known failure modes
    Alert if CPU > 80%, error rate > 1%, latency p99 > 2s
    Reactive: you only catch problems you anticipated

  Observability: you collect rich data to answer unexpected questions
    "Why did latency spike on these 37 specific user IDs for 11 minutes?"
    Proactive: data exists before you know what to ask

  Example: your system has 100ms p99 latency normally; it spikes to 2s
    Monitoring: ALERT — latency high
    Observability (with distributed tracing): database query on shard-3
      is slow, caused by a hot key from user_id=8831 making 10K requests/min
      (a bug in their import script)
    Without tracing you'd spend hours guessing; with it, 5 minutes.


4. GOLDEN SIGNALS (Google SRE Book)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The four signals that best characterize service health:

  LATENCY: how long requests take
    Distinguish slow successful requests from fast failed ones
    Focus on p95/p99 (worst users), not just average
    Average hides tail latency: p50=100ms, p99=5000ms = most users fine, some terrible

  TRAFFIC: demand placed on the system
    Requests/second, transactions/minute, concurrent users
    Baseline for scaling decisions

  ERRORS: rate of failed requests
    Explicit: HTTP 500, exception thrown
    Implicit: HTTP 200 with wrong content, timeouts silently swallowed

  SATURATION: how "full" the service is
    CPU %, memory %, disk I/O %, connection pool usage
    Predict degradation before it causes errors


5. RED METHOD (request-oriented services)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For microservices handling requests:
  Rate: requests per second
  Errors: error rate (5xx, exceptions)
  Duration: latency distribution (p50, p95, p99)

Most useful for: APIs, gRPC services, HTTP endpoints


6. USE METHOD (resource-oriented systems)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For every resource (CPU, memory, disk, network):
  Utilization: % time resource was busy
  Saturation: amount of queued work (waits)
  Errors: error events

Most useful for: system-level monitoring (infrastructure, hardware)


7. TOOLING ECOSYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  LOGGING:
    Collection:  Fluentd, Logstash, Filebeat, Vector
    Storage:     Elasticsearch, Loki, Splunk, CloudWatch Logs
    Query:       Kibana, Grafana, Splunk SPL

  METRICS:
    Collection:  Prometheus, StatsD, Telegraf
    Storage:     Prometheus TSDB, InfluxDB, Cortex (long-term Prometheus)
    Dashboards:  Grafana (universal), Datadog, New Relic

  TRACING:
    Instrumentation: OpenTelemetry (unified SDK, vendor-neutral)
    Backends:    Jaeger (open-source), Zipkin, Tempo, Datadog APM

  ALL-IN-ONE:
    Datadog: logs + metrics + APM + infrastructure in one product
    New Relic: similar full-stack observability
    Elastic APM: ELK-based full observability
    AWS CloudWatch: logs + metrics + traces for AWS workloads


8. CORRELATING THE THREE PILLARS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The real power: linking logs, metrics, and traces together

  Correlation ID (Trace ID):
    Every request gets a unique trace_id at the entry point (API gateway)
    trace_id propagated in headers (W3C Trace Context: traceparent header)
    All logs from that request include trace_id
    All spans in tracing share trace_id
    Click on metric anomaly → filter logs by time → find trace_id → view full trace

  Example workflow:
    1. Grafana metric: error spike at 14:32:15
    2. Click "View Logs" → filter logs by time window
    3. Find error log with trace_id=abc123
    4. Click trace_id → Jaeger shows full distributed trace
    5. See: DB query on shard-2 timed out after 3 seconds
    6. Resolution in 5 minutes instead of 5 hours


9. INTERVIEW TALKING POINTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Key phrases to use:
  "Observability is about asking questions you didn't know to ask in advance"
  "The three pillars are logs, metrics, and traces — each answers different questions"
  "Correlation IDs link all three pillars for a single request"
  "Alert on SLO burn rate, not raw thresholds, to reduce alert fatigue"
  "OpenTelemetry is the industry standard for vendor-neutral instrumentation"

What interviewers want to hear:
  You know the difference between monitoring and observability
  You've thought about how to debug production issues systematically
  You understand cardinality (high-cardinality data is expensive in metrics)
  You mention structured logging (not just printf statements)
