DISTRIBUTED TRACING — OPENTELEMETRY, JAEGER, SAMPLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT IS DISTRIBUTED TRACING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Distributed tracing: tracking a single request as it flows through
multiple services in a distributed system

  Problem without tracing:
    User: "My checkout takes 8 seconds"
    Engineer: is it the API Gateway? Auth service? Inventory? Payment? DB?
    Without tracing: manual log grep across 5 services, no visibility into call graph
    With tracing: "PaymentService.validateCard() took 7.8s — external credit bureau API is slow"

  Trace: the entire end-to-end journey of one request
  Span: one unit of work within a trace (one service call, one DB query)
  Context: metadata propagated across service boundaries

  Trace structure:
    Trace ID: "abc123def456" (unique per request, shared across all services)
    
    Trace: abc123def456
    ├── [0ms - 8200ms] API Gateway (root span)
    │   ├── [10ms - 120ms] Auth Service (child span)
    │   │   └── [15ms - 90ms] Redis GET token (leaf span)
    │   ├── [130ms - 8150ms] Order Service (child span)
    │   │   ├── [140ms - 200ms] Inventory DB query
    │   │   └── [210ms - 8140ms] Payment Service ← SLOW!
    │   │       └── [220ms - 8100ms] External Credit Bureau API call


2. KEY CONCEPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TRACE ID: globally unique identifier for the entire request
  Generated at entry point (API Gateway / front door)
  Propagated via HTTP header to all downstream services
  All spans from one request share the same trace_id

SPAN ID: unique identifier for one operation within the trace
  Each service creates one span per "operation" (incoming request, DB call)
  Span has: traceId, spanId, parentSpanId, operationName, startTime, duration, tags, logs

PARENT SPAN: the span that called the current operation
  Root span has no parent (the API Gateway's incoming request)
  Child spans reference parent's spanId

SPAN ATTRIBUTES (formerly tags):
  Key-value pairs attached to a span
  http.method=POST, http.status_code=200, db.statement="SELECT...", user_id=456

SPAN EVENTS (formerly logs):
  Timestamped structured data within a span
  "Retry 1 of 3 at 14:32:01.500Z"

SPAN STATUS: OK, ERROR, UNSET
  Set to ERROR when an exception occurs, with error.message attribute


3. CONTEXT PROPAGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

How trace context flows across services:

  W3C TraceContext (standard — adopted by all major vendors):
    HTTP Header: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
    Format: version-traceId(128bit)-parentSpanId(64bit)-flags
    flags=01 means "sampled" (record this trace)

  W3C Baggage header: for propagating custom key-value pairs
    baggage: userId=456,tenantId=acme

  Each service:
    Extract context from incoming headers
    Create child span with parent = incoming span
    Inject context into outgoing headers to downstream services
    
  Code (OpenTelemetry Java):
    Tracer tracer = OpenTelemetry.getGlobalTracer("order-service");
    Span span = tracer.spanBuilder("processOrder")
                      .startSpan();
    try (Scope scope = span.makeCurrent()) {
        span.setAttribute("order.id", orderId);
        // call downstream service — OTel auto-injects traceparent header
        inventoryClient.reserve(orderId);
    } catch (Exception e) {
        span.recordException(e);
        span.setStatus(StatusCode.ERROR, e.getMessage());
        throw e;
    } finally {
        span.end();
    }


4. OPENTELEMETRY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

OpenTelemetry (OTel): CNCF standard for observability instrumentation
  Vendor-neutral: instrument once, send to any backend (Jaeger, Zipkin, Datadog, Tempo)
  Covers all three pillars: traces, metrics, logs (unified SDK)
  Replaces OpenTracing + OpenCensus (merged in 2019)

Components:
  API: language-specific interfaces (Tracer, Meter, Logger)
  SDK: implementation of the API
  Instrumentation Libraries: auto-instrumentation for popular frameworks
    Spring Boot, Django, Express, gRPC, JDBC, Redis — zero code changes
  Collector: receives, processes, exports telemetry (sidecar or standalone)
    Receive: OTLP, Jaeger, Zipkin formats
    Process: filter, sample, batch, enrich
    Export: Jaeger, Datadog, Tempo, CloudWatch

OTLP (OpenTelemetry Protocol):
  gRPC-based wire format for sending telemetry data
  App → OTLP → OTel Collector → Jaeger / Datadog / etc.

Auto-instrumentation (Java agent):
  java -javaagent:opentelemetry-javaagent.jar \
       -Dotel.service.name=order-service \
       -Dotel.exporter.otlp.endpoint=http://collector:4317 \
       -jar app.jar
  
  Automatically instruments: HTTP clients/servers, JDBC, Kafka, Redis, MongoDB
  No code changes to the application needed


5. TRACING BACKENDS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JAEGER (most popular open-source):
  Created by Uber, donated to CNCF
  Architecture:
    Agent: local sidecar (UDP receiver, batches to Collector)
    Collector: receives spans, validates, stores
    Query: search API + Jaeger UI
    Storage: Cassandra or Elasticsearch (recommended)
  
  Features: service dependency graph, find traces by service/operation/tag/duration
  Sampling: supports head-based and adaptive (tail-based-like) sampling

ZIPKIN (older, simpler):
  Created at Twitter; simpler architecture
  Good for: smaller deployments, existing Zipkin instrumentation

GRAFANA TEMPO:
  Designed to work with Grafana + Loki + Prometheus
  Object storage (S3/GCS) backend → cheap, infinite retention
  No search index by default (need trace_id to query) — by design (cheap storage)
  TraceQL: query language for traces

DATADOG APM:
  Managed, no infrastructure to maintain
  Tight integration with Datadog metrics/logs
  Flamegraph visualization, anomaly detection
  Expensive but very operator-friendly


6. SAMPLING STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: 100K requests/sec × 50 spans/trace = 5M spans/sec → too expensive to store all

HEAD-BASED SAMPLING (at trace start):
  Decision made at entry point before trace starts
  All subsequent spans follow the same decision (all or nothing per trace)
  
  Types:
    Always On: 100% — only for development/low-traffic
    Probability: sample 1% of all traces
    Rate Limiting: max N traces per second regardless of traffic
  
  Pros: simple, low overhead; Cons: misses rare important traces (1-in-10K error)

TAIL-BASED SAMPLING (after trace completes):
  Collect ALL spans; at end, decide whether to keep or discard
  Keep if: ERROR span, latency > p99, interesting attributes (VIP user, payment)
  
  Pros: keeps 100% of interesting traces; Cons: must buffer all spans in memory
  
  OpenTelemetry Collector supports tail-based sampling:
    policies: 
      - type: status_code, status_code: {status_codes: [ERROR]}
      - type: latency, latency: {threshold_ms: 1000}
      - type: probabilistic, probabilistic: {sampling_percentage: 1}

ADAPTIVE SAMPLING (Jaeger):
  Automatically adjusts sample rate per operation to maintain target trace count
  High-traffic endpoint: 0.01% → Low-traffic: 100%

BEST PRACTICE:
  Always sample: errors, slow traces (> p99 threshold), specific users
  Probability sample: 1% of healthy fast traces for representative baseline
  Never sample: specific high-value operations (payment, login)


7. READING A TRACE — WATERFALL VIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Jaeger/Zipkin waterfall visualization:

  Service          0ms    200ms   400ms   600ms   800ms
  ─────────────────────────────────────────────────────
  api-gateway      [════════════════════════════════]  800ms
  auth-service      [══]                               90ms
  order-service           [══════════════════════]     600ms
  inventory-db              [═══]                      50ms
  payment-service              [═════════════════]     500ms
  ext.credit-api                  [═══════════════]    450ms ← BOTTLENECK

  Reading the waterfall:
    Horizontal position = start time relative to trace start
    Width = duration
    Nesting shows parent-child relationship
    Wide span that starts late = its parent was waiting for something else first

  Identifying bottlenecks:
    Critical path: the sequence of spans from root to longest leaf
    In example: api-gateway → order-service → payment-service → ext.credit-api
    Optimizing ANY span not on critical path doesn't reduce total latency


8. BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DO:
  Use OpenTelemetry for vendor-neutral instrumentation
  Include business attributes on spans: user_id, order_id, product_id
  Set span status to ERROR on exceptions (with span.recordException)
  Use semantic conventions (http.method, db.system, messaging.system)
  Sample based on error/latency, not randomly

DON'T:
  Add high-cardinality attributes as span tags if you search by them
    (tracing backends index on tag values; too many = OOM)
  Create too many child spans for trivial operations (overhead)
  Log PII (user email, credit card) in span attributes

INTERVIEW TALKING POINTS:
  "Traces answer 'where did the time go?' — metrics tell you there's a problem,
   traces tell you which service and what operation is responsible"
  "W3C TraceContext is the standard for context propagation across services"
  "OpenTelemetry lets you instrument once and switch backends without code changes"
  "Tail-based sampling lets you keep 100% of errors while sampling 1% of healthy traces"
