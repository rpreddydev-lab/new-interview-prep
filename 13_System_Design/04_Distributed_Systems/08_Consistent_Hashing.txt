================================================================
CONSISTENT HASHING
================================================================

WHAT IS CONSISTENT HASHING?
-----------------------------
A technique for distributing data (or requests) across a cluster of nodes
such that when nodes are added or removed, only a small fraction of data
needs to be redistributed.

THE PROBLEM WITH SIMPLE HASHING:
  Standard approach: shard_id = hash(key) % N  (N = number of nodes)
  
  With 4 nodes:  hash("user:123") % 4 = 3 → Node 3
  Add 5th node: hash("user:123") % 5 = 0 → Node 0
  
  PROBLEM: Adding/removing one node remaps ~(N-1)/N of all keys!
  With 1000 nodes and adding 1: 999/1000 = 99.9% of keys must move!
  This causes a massive redistribution storm.

CONSISTENT HASHING SOLUTION:
  Hash both keys AND nodes onto the same ring (hash space: 0 to 2^32-1).
  Each key maps to the nearest node clockwise on the ring.
  Adding/removing one node moves only 1/N of keys.

HOW CONSISTENT HASHING WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SETUP:
  Hash ring: integer space 0..2^32-1, arranged as a circle.
  
  Place nodes on ring:
    Node A: hash("node_a") → position 100
    Node B: hash("node_b") → position 200
    Node C: hash("node_c") → position 300
  
  Ring: 0 ──── 100(A) ──── 200(B) ──── 300(C) ──── 0 (wraps)

KEY LOOKUP:
  hash("user:123") → position 150
  Look clockwise from 150: nearest node = B (at 200)
  → "user:123" maps to Node B
  
  hash("user:456") → position 50
  Look clockwise from 50: nearest node = A (at 100)
  → "user:456" maps to Node A
  
  hash("user:789") → position 350
  Look clockwise from 350: wraps to 0, then A is at 100
  → "user:789" maps to Node A (first node clockwise)

ADDING A NODE D (at position 250):
  Ring: 0 ── 100(A) ── 200(B) ── 250(D) ── 300(C) ── 0
  
  Keys between 200 and 250 that were on C → now on D
  All other keys unchanged!
  
  Only ~1/N fraction remapped (1 out of 4 → ~25% moved).
  In a 100-node cluster: ~1% of keys move on each node change.

REMOVING A NODE B:
  Ring: 0 ── 100(A) ── 300(C) ── 0
  
  Keys that were on B → now go to C (next clockwise node)
  All other keys unchanged.

VIRTUAL NODES (VNODES)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM WITH BASIC CONSISTENT HASHING:
  With few physical nodes, distribution may be uneven.
  A node placed at an unfortunate position may own too much (or too little) of the ring.
  When a node is removed, ALL its load goes to ONE neighbor (hotspot).

SOLUTION: Virtual Nodes
  Each physical node is represented by multiple virtual nodes on the ring.
  Physical Node A → Virtual nodes: A_0 (pos 50), A_1 (pos 180), A_2 (pos 320)
  Physical Node B → Virtual nodes: B_0 (pos 80), B_1 (pos 220), B_2 (pos 380)
  Physical Node C → Virtual nodes: C_0 (pos 30), C_1 (pos 150), C_2 (pos 280)
  
  Benefits:
  ✓ More uniform distribution (many small segments instead of few large ones)
  ✓ When a node fails, its load spreads across all remaining nodes (not just one)
  ✓ Can assign more virtual nodes to more powerful machines (weighted)
  
  Cassandra default: 256 virtual nodes per physical node (vnodes)
  DynamoDB: Uses virtual nodes internally

REPLICATION WITH CONSISTENT HASHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Cassandra uses consistent hashing + replication factor RF.
A key is stored on the primary node PLUS the next RF-1 clockwise nodes.

Example RF=3:
  Key maps to Node B (primary).
  Also stored on Node C and Node D (next two clockwise).
  
  For a read: contact any 1, 2, or 3 replicas depending on consistency level.
  For a write: write to all 3, wait for W confirmations.

USE CASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. DISTRIBUTED CACHES (Memcached, Redis Cluster):
   Client-side library uses consistent hashing to determine which cache
   server holds each key.
   Adding a cache server: only some keys move, rest stay.

2. DATABASE SHARDING (Cassandra, DynamoDB):
   Data distributed across shards using consistent hashing.
   New shards added without mass data migration.

3. LOAD BALANCING (Nginx consistent hashing):
   Route requests for the same session to the same backend server.
   Maintains server-side caching effectiveness.
   
   nginx config:
   upstream backend {
     hash $remote_addr consistent;
     server 10.0.0.1;
     server 10.0.0.2;
   }

4. CDN (Content Delivery Networks):
   Consistent hashing used internally to route requests to edge caches.
   URLs consistently map to the same edge node for cache hits.

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Consistent hashing solves the problem of redistributing data when
 scaling a distributed system. Simple modulo hashing requires moving
 nearly all keys when adding a node. Consistent hashing places nodes
 and keys on a ring; adding a node only affects ~1/N of keys.
 
 With virtual nodes, each physical node gets multiple positions on the
 ring for better load distribution and spreading the impact of failures.
 
 I'd use consistent hashing for: distributed cache routing (Memcached),
 database sharding (Cassandra), or session-affinity load balancing.
 
 Cassandra uses consistent hashing with 256 virtual nodes per server and
 replication factor 3, storing each key on 3 consecutive nodes."
