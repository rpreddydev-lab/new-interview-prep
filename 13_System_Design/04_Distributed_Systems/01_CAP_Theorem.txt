================================================================
CAP THEOREM
================================================================

WHAT IS CAP THEOREM?
---------------------
The CAP theorem (Brewer's theorem, 2000) states that a distributed
data store can provide at most TWO of these three guarantees simultaneously:

  C — Consistency:        Every read receives the most recent write
                           (or an error). All nodes see the same data.
  A — Availability:       Every request receives a non-error response
                           (though it may not be the most recent write).
  P — Partition Tolerance: The system continues operating even when
                           network partitions (message loss/delay) occur.

THE KEY INSIGHT:
  Network partitions WILL happen in any distributed system.
  You cannot avoid P. You must tolerate partitions.
  Therefore, the real choice is: During a partition, do you prefer C or A?

  CP System: Choose consistency over availability.
             When partition occurs, some nodes refuse to respond (error/timeout)
             to prevent returning stale data.
  
  AP System: Choose availability over consistency.
             When partition occurs, nodes continue serving requests
             but may return stale or inconsistent data.

CP SYSTEMS (Consistency + Partition Tolerance):
  Examples: HBase, Zookeeper, Redis (with Raft), MongoDB (with w=majority), 
            etcd, Consul, CockroachDB, Spanner
  
  Behavior during partition:
  - The partition minority refuses writes (returns error)
  - The partition majority continues serving (consistent subset)
  - Overall: some requests fail → not "fully available"
  
  Use when: Financial transactions, distributed locking, leader election,
             configuration management (you'd rather fail than be wrong).

AP SYSTEMS (Availability + Partition Tolerance):
  Examples: Cassandra, DynamoDB, CouchDB, Riak, DNS, web caches
  
  Behavior during partition:
  - All nodes continue accepting reads/writes
  - When partition heals, nodes sync up and resolve conflicts
  - Data may be stale or conflicting during partition
  
  Use when: Social media, caching, shopping carts, user sessions
             (you'd rather return slightly stale data than an error).

CA SYSTEMS (Consistency + Availability) — THEORETICAL:
  Would require sacrificing Partition Tolerance.
  Impossible in a distributed system (partitions always happen).
  Single-node databases are effectively "CA" (but they're not distributed).
  Examples: Traditional single-server RDBMS (MySQL, PostgreSQL single node)

CAP IN PRACTICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO: Amazon Shopping Cart (AP)
  - User adds item to cart
  - Network partition: cart service can't reach database
  - AP choice: Accept the add, show cart optimistically, sync later
  - Possible problem: User adds item on two devices simultaneously
    → Two copies of cart must be merged when partition heals
  - Amazon chose: Availability. Shopping cart merge > lost sale

SCENARIO: Bank Transfer (CP)
  - User transfers $1000 to another account
  - Network partition: can't reach account B
  - CP choice: Reject the transfer, return error to user
  - User frustrated but no money is lost or duplicated
  - Bank chose: Consistency. Correct data > transaction completion

SCENARIO: DNS (AP)
  - DNS servers continue serving cached records during network issues
  - Cached records may be stale (stale IP for a few minutes)
  - Eventual consistency: all DNS servers eventually converge
  - DNS chose: Availability. Serving old IP > serving nothing

TUNABLE CONSISTENCY (Cassandra):
  Cassandra lets you tune per-operation:
  
  Read/Write CL = ONE:       Fastest, least consistent
  Read/Write CL = QUORUM:    Medium; majority quorum
  Read/Write CL = ALL:       Slowest, most consistent
  
  Read QUORUM + Write QUORUM: Strong consistency
  Read ONE + Write ONE:       Eventual consistency
  
  This makes Cassandra effectively CP or AP based on configuration.

CAP CRITICISM AND NUANCES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Consistency in CAP ≠ Consistency in ACID
   CAP Consistency = Linearizability (all nodes see same value)
   ACID Consistency = Data satisfies integrity constraints
   These are different concepts with the same name!

2. Availability in CAP is absolute (100%)
   Real systems have partial availability (some requests succeed).
   CAP's "availability" means ALL requests must be answered.
   In practice, systems have SLAs (99.9%, 99.99%) not binary.

3. Partitions are rare in practice
   Within a single datacenter: very rare (ms-level network issues)
   Across datacenters/regions: more common
   The choice between C and A matters most for multi-region deployments.

4. PACELC theorem addresses these nuances (see next file).

INTERVIEW ANSWER:
  "CAP theorem says a distributed system can only guarantee two of:
   Consistency, Availability, Partition Tolerance. Since partitions
   are inevitable in any distributed system, the real trade-off is
   between consistency and availability during a partition.
   
   For [this system], I'd choose [CP/AP] because [reason].
   We'd achieve this using [technology] configured with [settings]."
