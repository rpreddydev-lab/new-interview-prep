================================================================
PACELC THEOREM
================================================================

WHAT IS PACELC?
----------------
PACELC (Daniel Abadi, 2012) extends CAP by acknowledging that the
trade-off between latency and consistency also exists during normal operation
(no partition).

CAP only asks: "What happens during a Partition?"
PACELC asks: "What happens ALWAYS, not just during a partition?"

PAC-ELC:
  If there is a Partition (P):
    Choose between: Availability (A) or Consistency (C)
    (same as CAP)
  
  Else (normal operation, no partition):
    Choose between: Latency (L) or Consistency (C)

THE KEY INSIGHT:
  Even without network partitions, achieving strong consistency
  requires multiple round trips for coordination (replication, quorum),
  which increases latency.
  
  High Consistency → High Latency (must wait for multiple nodes to agree)
  Low Latency → Lower Consistency (can return after writing to 1 node)

PACELC CLASSIFICATION OF SYSTEMS:
  PA/EL: During partition → availability; Else → low latency
         (DynamoDB, Cassandra, Riak, CouchDB)
         Most NoSQL systems. Fast writes, eventual consistency.
  
  PC/EC: During partition → consistency; Else → strong consistency
         (HBase, VoltDB, BigTable, Zookeeper)
         Strongly consistent, higher latency for coordination.
  
  PA/EC: During partition → availability; Else → strong consistency
         (MongoDB with default settings, MySQL replication)
         Availability during chaos, but consistent normally.
  
  PC/EL: During partition → consistency; Else → low latency
         (PNUTS — Yahoo's distributed DB)
         Rare; often theoretical.

EXAMPLES:

AMAZON DYNAMO (PA/EL):
  Partition: Accepts writes to any node (available)
  Normal: Returns immediately after single replica write (low latency)
  Cost: Eventual consistency; conflict resolution needed (LWW or CRDT)
  Best for: Shopping cart, user sessions

APACHE CASSANDRA (PA/EL):
  Partition: Leaderless; any node accepts writes (available)
  Normal: Returns after W replicas acknowledge (tunable latency vs consistency)
  Default W=1, R=1 → PA/EL; W=QUORUM, R=QUORUM → PC/EC
  Best for: IoT, time-series, write-heavy workloads

MONGODB (Defaults: PA/EC, configurable):
  Partition: Primary continues accepting writes; no quorum failover by default
  Normal: With w=majority, read-your-writes consistency; slightly higher latency
  Can be configured to PC/EC with stronger settings.

HBASE / BIGTABLE (PC/EC):
  Partition: Refuses writes if region server can't reach ZooKeeper → consistent
  Normal: All writes go through single region leader → strongly consistent
  Cost: Higher latency, single point for writes
  Best for: Financial data, inventory systems needing strict consistency

COCKROACHDB / SPANNER (PC/EC):
  Partition: Uses Raft consensus; minority partition stops accepting writes
  Normal: Serializable isolation, strong consistency (Spanner uses atomic clocks)
  Cost: Latency of consensus round-trips; ~10ms for same region
  Best for: Global financial systems, multi-region ACID transactions

LATENCY-CONSISTENCY TRADE-OFF IN NORMAL OPERATION:

Why does strong consistency increase latency?
  Leader receives write → must replicate to majority of replicas → wait for ACKs
  With N=3, W=2 replicas:
    Normal (same DC): ~1-2ms wait
    Cross-region replicas: ~50-100ms wait per write
  
  DynamoDB Global Tables (multi-region):
    With eventual consistency: ~1ms write (single region)
    With strong consistency: ~100ms write (must wait for multi-region quorum)
    Trade-off: 100x latency for strong consistency across regions.

GOOGLE SPANNER EXCEPTION:
  Spanner achieves global strong consistency with low latency using:
  1. TrueTime API — GPS and atomic clocks for very tight time bounds
  2. External consistency: transactions commit only after uncertainty window
  3. Commit wait: slightly adds latency but gives global ordering
  Result: ~10-20ms for regional, ~100ms for global transactions.
  Cost: Expensive hardware and infrastructure.

INTERVIEW ANSWER:
  "PACELC extends CAP by noting that even without partitions, there's
   a trade-off between latency and consistency. Systems like DynamoDB
   are PA/EL — available during partitions and low latency normally,
   at the cost of eventual consistency. Systems like Spanner are PC/EC
   — consistent always, but with higher latency from coordination overhead.
   
   For [this system], [high write throughput with eventual consistency]
   means I'd choose a PA/EL system like Cassandra. If [financial data
   requiring exact balances], I'd use PC/EC like CockroachDB or Spanner."
