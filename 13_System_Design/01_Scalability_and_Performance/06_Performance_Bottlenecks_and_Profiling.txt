================================================================
PERFORMANCE BOTTLENECKS AND PROFILING
================================================================

OVERVIEW
---------
A performance bottleneck is the component that limits the overall
system throughput or causes high latency. Finding and fixing
bottlenecks is the primary activity of performance engineering.

"Premature optimization is the root of all evil." — Donald Knuth
→ Measure first, optimize based on data, not assumptions.

TYPES OF BOTTLENECKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CPU BOTTLENECK
Symptom: High CPU utilization (>80%), high user CPU in profiler
Causes:
  - Complex computations (crypto, compression, serialization)
  - Inefficient algorithms (O(n²) where O(n log n) is possible)
  - Too many threads context-switching
  - Garbage collection pauses (JVM, .NET)
  - Lock contention causing busy-wait

Solutions:
  - Optimize algorithms and data structures
  - Offload computation to GPU or specialized hardware
  - Caching computed results (memoization)
  - Async processing (defer CPU work to background workers)
  - Scale horizontally (add more CPU cores via more machines)
  - Profile with CPU profilers (async-profiler, py-spy, pprof)

2. MEMORY BOTTLENECK
Symptom: High memory usage, frequent GC pauses, OOM errors, swapping
Causes:
  - Memory leaks (objects not released)
  - Large in-memory datasets (working set > RAM)
  - Memory fragmentation
  - Too many concurrent requests each holding state

Solutions:
  - Memory profilers (MAT for Java, memory_profiler for Python)
  - Fix memory leaks (close resources, clear unused caches)
  - Reduce object creation (object pooling, reuse buffers)
  - Externalize state (use Redis instead of in-process cache)
  - Pagination / streaming instead of loading all data at once
  - Tune GC settings (heap size, GC algorithm)

3. I/O BOTTLENECK (Disk)
Symptom: High iowait, slow read/write operations, disk queue depth > 1
Causes:
  - Too many small random I/O operations (worst case for spinning disks)
  - DB without proper indexes (full table scans)
  - Writing too frequently to disk (logging, checkpointing)
  - Disk is full or fragmented

Solutions:
  - Use SSDs instead of HDDs (100× faster random I/O)
  - Add database indexes for frequent query patterns
  - Reduce disk writes: batch, buffer, async writes
  - Use caching to avoid disk reads
  - Sequential I/O >> Random I/O: restructure access patterns
  - Increase IOPS by using RAID, NVMe, or distributed storage

4. NETWORK BOTTLENECK
Symptom: High network utilization, packet loss, high latency
Causes:
  - Saturated NIC bandwidth
  - Too many small network calls (chatty protocols)
  - Large payloads per request (uncompressed data)
  - Geographic distance (high RTT)

Solutions:
  - Compress payloads (gzip, zstd, protobuf instead of JSON)
  - Reduce round trips: batch requests, use HTTP/2 multiplexing
  - CDN for geographically distant users
  - Connection pooling (avoid TCP handshake overhead)
  - Upgrade network bandwidth
  - Move computation closer to data (data locality)

5. DATABASE BOTTLENECK
Symptom: High DB query latency, lock contention, high DB CPU/IO
Causes:
  - Missing indexes
  - Inefficient queries (N+1 query problem, full table scans)
  - Lock contention on hot rows
  - Connection pool exhaustion
  - Too many writes to primary DB

Solutions:
  - EXPLAIN/EXPLAIN ANALYZE to identify slow queries
  - Add appropriate indexes
  - Fix N+1 problem with eager loading / JOIN
  - Caching frequently read data in Redis
  - Read replicas to distribute reads
  - Connection pooling (PgBouncer for PostgreSQL)
  - Query optimization (rewrite, denormalize for reads)
  - Sharding for write-heavy workloads

6. CONCURRENCY BOTTLENECK
Symptom: High contention metrics, slow during high concurrency despite low CPU
Causes:
  - Lock contention (too many threads competing for same lock)
  - Database row-level locks (SELECT FOR UPDATE)
  - Thread pool exhaustion
  - Synchronous blocking in async code

Solutions:
  - Use lock-free data structures (ConcurrentHashMap, AtomicInteger)
  - Optimistic locking (compare-and-swap) instead of pessimistic
  - Reduce lock granularity (lock per item, not entire collection)
  - Partition data to avoid contention (each worker owns a subset)
  - Use async/non-blocking I/O (event loop, reactive programming)
  - Increase thread pool size (but watch for context-switch overhead)

CPU PROFILING:
  Java:        async-profiler, JFR (Java Flight Recorder), YourKit
  Python:      py-spy, cProfile, Pyflame, Austin
  Go:          pprof (built-in), trace
  Node.js:     --inspect + Chrome DevTools, clinic.js
  C/C++:       perf, gprof, Valgrind (cachegrind), Instruments (macOS)

MEMORY PROFILING:
  Java:        MAT (Eclipse), JVisualVM, JFR heap analysis
  Python:      memory_profiler, objgraph, tracemalloc
  Go:          pprof heap profile
  C/C++:       Valgrind (massif, memcheck)

DISTRIBUTED TRACING:
  Jaeger, Zipkin, AWS X-Ray, Datadog APM
  Traces show end-to-end request flow with time in each service.
  Identifies which service/component is the slowest.

DATABASE PROFILING:
  MySQL:      EXPLAIN, EXPLAIN ANALYZE, slow query log, pt-query-digest
  PostgreSQL: EXPLAIN ANALYZE, pg_stat_statements, auto_explain
  MongoDB:    explain(), MongoDB Profiler, Atlas Performance Advisor

APPLICATION PERFORMANCE MONITORING (APM):
  Datadog, New Relic, Dynatrace, Elastic APM
  Provides automatic instrumentation, distributed traces, profiling.

N+1 QUERY PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

One of the most common DB performance problems.

BAD (N+1):
  # 1 query to get 100 users
  users = SELECT * FROM users LIMIT 100
  
  # 100 queries to get each user's posts
  for user in users:
      posts = SELECT * FROM posts WHERE user_id = user.id
  
  Total: 101 queries

GOOD (JOIN or batch fetch):
  # 1 query with JOIN
  SELECT u.*, p.* FROM users u
  LEFT JOIN posts p ON p.user_id = u.id
  LIMIT 100
  
  # OR: 2 queries (fetch users, then batch-fetch posts)
  users = SELECT * FROM users LIMIT 100
  user_ids = [u.id for u in users]
  posts = SELECT * FROM posts WHERE user_id IN (user_ids)
  
  Total: 1-2 queries

Detect N+1:
  - Slow query logs show the same query pattern 100 times
  - APM tools (Datadog, New Relic) highlight N+1 patterns
  - Django Debug Toolbar, Bullet (Rails) detect during development

PERFORMANCE TESTING TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Load Testing:
  Simulate expected production load.
  Goal: Verify system handles expected traffic with acceptable latency.
  Tools: Locust, k6, JMeter, Gatling, Artillery

Stress Testing:
  Increase load beyond expected capacity until system breaks.
  Goal: Find the breaking point and observe failure behavior.
  "At 2× expected load, what fails first?"

Spike Testing:
  Sudden large increase in traffic (e.g., Black Friday, viral tweet).
  Goal: Verify system handles sudden traffic spikes without crashing.

Soak/Endurance Testing:
  Run at normal load for extended period (24-72 hours).
  Goal: Detect memory leaks, connection pool exhaustion over time.

Breakpoint Testing:
  Gradually increase load to find exact throughput ceiling.

PERFORMANCE OPTIMIZATION CHECKLIST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Database:
  □ All frequently queried columns are indexed
  □ Composite indexes for multi-column WHERE clauses
  □ EXPLAIN ANALYZE run on slow queries
  □ Connection pooling configured (PgBouncer, HikariCP)
  □ N+1 query problems eliminated
  □ Read replicas for read-heavy queries

Caching:
  □ Hot/frequently read data cached in Redis
  □ Cache hit rate > 90%
  □ Appropriate TTL per data type
  □ Cache warming in place

Network:
  □ Compression enabled (gzip/br) for HTTP responses
  □ HTTP/2 or HTTP/3 for multiplexing
  □ CDN for static and cacheable content
  □ Connection pooling for external service calls
  □ Keep-alive connections (no teardown per request)

Application:
  □ Async I/O for external calls
  □ Thread pool tuned appropriately
  □ No synchronous waits in hot paths
  □ Expensive operations moved to background workers

Infrastructure:
  □ Instances right-sized (not over or under-provisioned)
  □ Auto-scaling configured
  □ Resource limits set (prevent one service from starving others)

Observability:
  □ P50, P95, P99 latency metrics tracked per endpoint
  □ Error rates tracked
  □ Slow query logging enabled
  □ Distributed tracing deployed for cross-service debugging
