GRAPHQL OVERVIEW
================================================================

WHAT IS GRAPHQL?
-----------------
GraphQL is a query language for APIs and a runtime for executing those
queries, developed by Facebook (now Meta) in 2012 and open-sourced in 2015.

KEY IDEA: The client specifies EXACTLY what data it wants.
The server returns exactly that — no more, no less.

This solves the two main REST problems:
  Over-fetching: REST returns too much data (you only need name, email
                 but GET /users/{id} returns 30 fields)
  Under-fetching: REST returns too little (you need user + their posts,
                  requiring 2 requests; GraphQL gets both in 1)

SCHEMA (Type System):
  GraphQL is strongly typed. Schema defines what data is available.

  type User {
    id:        ID!       # ! = non-null
    name:      String!
    email:     String!
    posts:     [Post!]!  # list of non-null Posts
    createdAt: String!
  }
  
  type Post {
    id:      ID!
    title:   String!
    content: String!
    author:  User!
    likes:   Int!
  }
  
  type Query {          # Read operations
    user(id: ID!): User
    users(page: Int, limit: Int): [User!]!
    posts(authorId: ID): [Post!]!
  }
  
  type Mutation {       # Write operations
    createUser(name: String!, email: String!): User!
    createPost(title: String!, authorId: ID!): Post!
    deletePost(id: ID!): Boolean!
  }
  
  type Subscription {   # Real-time events
    postCreated: Post!
    userUpdated(userId: ID!): User!
  }

QUERIES (Client-specified data):
  # Get user's name + email only (no extra fields)
  query {
    user(id: "123") {
      name
      email
    }
  }
  
  # Get user + their posts in ONE request
  query {
    user(id: "123") {
      name
      email
      posts {
        id
        title
        likes
      }
    }
  }
  
  # Response exactly mirrors query shape:
  {
    "data": {
      "user": {
        "name": "Alice",
        "email": "alice@example.com",
        "posts": [
          { "id": "1", "title": "Hello World", "likes": 42 }
        ]
      }
    }
  }

MUTATIONS:
  mutation CreatePost($title: String!, $authorId: ID!) {
    createPost(title: $title, authorId: $authorId) {
      id
      title
      createdAt
    }
  }
  
  Variables: { "title": "My Post", "authorId": "123" }

SUBSCRIPTIONS (Real-time with WebSockets):
  subscription {
    postCreated {
      id
      title
      author {
        name
      }
    }
  }
  
  Server pushes events to client when new posts are created.
  Implemented over WebSockets (most implementations).

FRAGMENTS (Reusable query parts):
  fragment UserFields on User {
    id
    name
    email
  }
  
  query {
    user(id: "123") { ...UserFields }
    admin(id: "456") { ...UserFields }
  }

GRAPHQL SERVER INTERNALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RESOLVERS:
  Each field in the schema has a resolver function that fetches the data.
  
  // Resolver for user.posts field
  const resolvers = {
    Query: {
      user: (parent, { id }, context) => UserService.findById(id),
    },
    User: {
      posts: (user, args, context) => PostService.findByAuthor(user.id),
    }
  }
  
  GraphQL calls resolvers in a tree pattern matching the query shape.

N+1 PROBLEM IN GRAPHQL:
  Problem:
    For a query returning 100 users, each with their posts:
    - 1 resolver call to get 100 users
    - 100 resolver calls to get posts for each user
    = 101 DB queries (N+1!)
  
  Solution: DATALOADER (batching + caching)
    DataLoader collects all user.posts resolver calls in a single tick,
    then batches them into: SELECT * FROM posts WHERE author_id IN (ids)
    = 2 DB queries instead of 101
  
  DataLoader is ESSENTIAL for production GraphQL servers.

INTROSPECTION:
  GraphQL schema is self-documenting.
  Clients can query the schema itself:
  query { __schema { types { name fields { name type { name } } } } }
  
  Powers tools like GraphiQL and Apollo Explorer (interactive IDEs).

GRAPHQL SECURITY CONSIDERATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. QUERY DEPTH LIMITING:
   Deeply nested queries can trigger excessive DB calls:
   { user { posts { comments { author { posts { comments { ... } } } } } } }
   Solution: Limit query depth (e.g., max depth = 7).

2. QUERY COMPLEXITY ANALYSIS:
   Assign a cost to each field/resolver.
   Reject queries exceeding a complexity limit.
   
   query { users { posts { comments } } }  # cost = 100
   query { user(id: "1") { name } }         # cost = 2

3. RATE LIMITING:
   Rate limit by user, IP, or complexity score.
   A single complex query can be worse than 100 simple queries.

4. INTROSPECTION IN PRODUCTION:
   Disable schema introspection in production if you don't want
   to expose your full schema to potential attackers.

5. PERSISTED QUERIES:
   Client sends a hash of the query instead of full query text.
   Server only executes pre-approved queries.
   Performance benefit (smaller request) + security (no arbitrary queries).

CACHING WITH GRAPHQL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GraphQL caching is harder than REST because:
  - All queries use POST /graphql (same URL) → HTTP caching doesn't work
  - Query body is unique per client → CDN can't cache

Solutions:
  1. CDN-level caching with GET requests (persisted queries mapped to GET URLs)
  2. Client-side caching: Apollo Client / Relay — normalize response into
     local store, cache by entity (User:123, Post:456)
  3. Server-side: Cache resolver results in Redis per query hash
  4. Partial caching: Cache individual resolver results with different TTLs
     (user data: 60s, product data: 300s)

GRAPHQL vs REST vs gRPC

┌────────────────────┬───────────────┬───────────────┬───────────────┐
│ Feature            │ GraphQL       │ REST          │ gRPC          │
├────────────────────┼───────────────┼───────────────┼───────────────┤
│ Data fetching      │ Client chooses│ Fixed per URL │ Fixed per RPC │

│ Type system        │ Strong        │ Optional      │ Strong        │
│ Real-time          │ Subscriptions │ SSE/WebSocket │ Streaming     │
│ Caching            │ Complex       │ Simple (HTTP) │ Complex       │
│ Learning curve     │ Medium        │ Low           │ Medium        │
│ N+1 risk           │ Yes           │ Yes           │ Manageable    │
│ Tooling            │ Excellent     │ Excellent     │ Good          │
│ Mobile-friendly    │ Very          │ Good          │ Binary        │
│ Browser support    │ Native        │ Native        │ Limited       │
│ Best for           │ Mobile, BFF   │ Public API    │ Internal RPC  │
└────────────────────┴───────────────┴───────────────┴───────────────┘

WHEN TO CHOOSE GRAPHQL:
  ✓ Mobile apps (bandwidth constrained — minimize data transfer)
  ✓ Frontend-driven development (BFF — Backend for Frontend)
  ✓ Many client types with different data needs
  ✓ Rapidly changing UI requirements (no API versioning needed)
  ✓ Aggregating data from multiple backend services (graph of services)

WHEN NOT TO CHOOSE GRAPHQL:
  ✗ Simple, stable CRUD APIs
  ✗ File upload/download
  ✗ When N+1 cannot be solved (legacy DB without DataLoader support)
  ✗ High-throughput internal services (gRPC is more efficient)
