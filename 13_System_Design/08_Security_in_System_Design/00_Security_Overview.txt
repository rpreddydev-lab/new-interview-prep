SECURITY IN SYSTEM DESIGN — OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHY SECURITY IN SYSTEM DESIGN INTERVIEWS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Security is no longer a separate concern bolted on after design.
Senior engineers are expected to integrate security thinking from the start:
  - Where is data encrypted?
  - How are users authenticated and authorized?
  - How is the API protected from abuse?
  - What happens if an internal service is compromised?

SECURITY PRINCIPLES (CIA TRIAD):
  CONFIDENTIALITY: Data is only accessible to authorized parties
    - Encryption, access controls, authentication
  
  INTEGRITY: Data is accurate and hasn't been tampered with
    - Checksums, digital signatures, immutable audit logs
  
  AVAILABILITY: System is accessible when needed
    - DDoS protection, rate limiting, redundancy

DEFENSE IN DEPTH:
  Multiple layers of security — no single control is sufficient
  An attacker must compromise ALL layers to succeed

  Layer 1: Network perimeter (firewalls, VPC, security groups)
  Layer 2: API Gateway (rate limiting, WAF, TLS termination)
  Layer 3: Authentication (identity verification)
  Layer 4: Authorization (access control)
  Layer 5: Application (input validation, OWASP mitigations)
  Layer 6: Data (encryption at rest, column-level encryption)
  Layer 7: Audit (logging, monitoring, anomaly detection)


2. THE SECURITY LANDSCAPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

OWASP TOP 10 (2021) — Know These:
  A01 Broken Access Control:
    - Vertical: User accesses admin endpoint
    - Horizontal: User accesses another user's data (IDOR)
    - Fix: Enforce authorization at every endpoint; never trust client-supplied IDs

  A02 Cryptographic Failures:
    - Transmitting sensitive data in plaintext
    - Using weak/deprecated algorithms (MD5, SHA1, DES, RC4)
    - Not encrypting PII at rest
    - Fix: TLS 1.3 everywhere; AES-256 at rest; BCrypt for passwords

  A03 Injection (SQL, LDAP, OS, NoSQL):
    - SQL: SELECT * FROM users WHERE id = '1 OR 1=1'
    - Fix: Parameterized queries/prepared statements; never string-concatenate queries

  A04 Insecure Design:
    - No threat modeling; security not considered in design phase
    - Fix: Threat model during design; build security controls into architecture

  A05 Security Misconfiguration:
    - Default credentials (admin/admin), verbose error messages, open ports
    - Fix: Infrastructure as Code; automated security scanning; CIS benchmarks

  A06 Vulnerable and Outdated Components:
    - Libraries with known CVEs
    - Fix: SCA (Software Composition Analysis): Snyk, OWASP Dependency Check

  A07 Identification and Authentication Failures:
    - Weak passwords, no MFA, broken session management
    - Fix: Strong password policy; MFA; secure session tokens; account lockout

  A08 Software and Data Integrity Failures:
    - Unsigned deserialization, unsigned CI/CD pipeline
    - Fix: Verify signatures; use signed package repos; SLSA supply chain security

  A09 Security Logging and Monitoring Failures:
    - Not logging auth failures, not alerting on breaches
    - Fix: Centralized logging; security alerts; incident response plan

  A10 Server-Side Request Forgery (SSRF):
    - Attacker makes server fetch malicious internal URL
    - Fix: Allowlist of permitted URLs; disable internal access from user-input URLs

ATTACK SURFACE MAP:
  External Attacks → API Gateway → Services → Databases
  
  External Perimeter:
    - DDoS, brute force, OWASP attacks → WAF, Rate Limiting, Input Validation
  
  API Layer:
    - Unauthorized access → Authentication + Authorization
    - API abuse → Rate Limiting + Throttling
  
  Service-to-Service:
    - Lateral movement if one service compromised → mTLS, Zero Trust
    - Privilege escalation → Least privilege IAM roles
  
  Data Layer:
    - Data breach at rest → Encryption at rest, KMS
    - Data breach in transit → TLS 1.3, mTLS
    - Insider threat → Audit logging, column-level encryption


3. SECURITY CONTROLS BY LAYER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NETWORK LAYER:
  VPC: Private network; services not publicly accessible by default
  Security Groups: Stateful firewall rules (allow specific ports/IPs)
  NACLs: Stateless subnet-level firewall
  VPC Flow Logs: Log all network traffic for analysis
  PrivateLink: Private connectivity to AWS services (no public internet)
  VPN / Direct Connect: Encrypted tunnels for on-premises connections

APPLICATION LAYER:
  WAF (Web Application Firewall):
    - Blocks OWASP attacks (XSS, SQLi, SSRF, path traversal)
    - AWS WAF, Cloudflare WAF, ModSecurity
    - Managed rule groups (OWASP Core Rule Set)
  
  Input Validation:
    - Validate all inputs (length, format, type, range)
    - Allow-list preferred over deny-list
    - Server-side validation always (never trust client-side)
  
  CSRF Protection:
    - Synchronizer tokens (CSRF token in form + cookie check)
    - SameSite=Strict/Lax cookies
    - Custom request headers (for API calls)

  Content Security Policy (CSP):
    - Prevents XSS by whitelisting script sources
    - Content-Security-Policy: default-src 'self'; script-src 'self' cdn.trusted.com

DATA LAYER:
  Encryption at rest (AES-256, KMS envelope encryption)
  Encryption in transit (TLS 1.3)
  Tokenization (replace sensitive data with tokens — PCI DSS compliance)
  Data masking (show **** for credit card numbers in logs)
  Database activity monitoring (DAM) — log all DB queries

IDENTITY AND ACCESS:
  Authentication: Verify who you are (covered in 01_ file)
  Authorization: What you're allowed to do (covered in 01_ file)
  Least Privilege: Grant minimum permissions needed
  Role-Based Access Control (RBAC): permissions assigned to roles
  Attribute-Based Access Control (ABAC): fine-grained, policy-based
  Service Accounts: Non-human identity for service-to-service calls
  Secret Management: Vault, AWS Secrets Manager (never hardcode credentials)


4. SECURITY COMPLIANCE STANDARDS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PCI DSS (Payment Card Industry Data Security Standard):
  Required for: Any system that processes credit card data
  Key requirements:
    - Encrypt cardholder data (PAN) at rest (AES-256) and in transit (TLS)
    - Never store CVV/CVC/CVN after authorization
    - Tokenize card numbers (store token, not PAN)
    - Network segmentation: CDE (Cardholder Data Environment) isolated
    - Quarterly vulnerability scans
    - Annual penetration testing

GDPR (General Data Protection Regulation):
  Required for: Processing EU citizens' personal data
  Key requirements:
    - Consent for data collection
    - Right to erasure ("right to be forgotten")
    - Data portability (export user data)
    - Breach notification within 72 hours
    - Data minimization (collect only what's needed)
    - Privacy by design

HIPAA (Health Insurance Portability and Accountability Act):
  Required for: Healthcare data (PHI - Protected Health Information)
  Key requirements:
    - Encryption of PHI at rest and in transit
    - Access controls and audit logs
    - Business Associate Agreements (BAA) with vendors
    - AWS HIPAA eligible services (not all AWS services are covered)

SOC 2 Type II:
  Voluntary audit for service providers
  Covers: Security, availability, processing integrity, confidentiality, privacy
  Demonstrates to enterprise customers that your security controls work


5. THREAT MODELING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STRIDE MODEL:
  S - Spoofing: Impersonating another user or service
      Mitigation: Strong authentication, MFA, certificates
  
  T - Tampering: Modifying data or code
      Mitigation: Integrity checks, digital signatures, audit logs
  
  R - Repudiation: Denying an action was performed
      Mitigation: Tamper-proof audit logs, non-repudiation via signing
  
  I - Information Disclosure: Unauthorized access to data
      Mitigation: Encryption, access controls, data classification
  
  D - Denial of Service: Making a service unavailable
      Mitigation: Rate limiting, DDoS protection, redundancy
  
  E - Elevation of Privilege: Gaining higher permissions than granted
      Mitigation: Least privilege, input validation, RBAC enforcement

PROCESS:
  1. Decompose the application (architecture diagram)
  2. Identify threats per component (STRIDE)
  3. Rate severity (DREAD: Damage, Reproducibility, Exploitability,
                          Affected users, Discoverability)
  4. Define mitigations for each threat
  5. Test mitigations (penetration testing, red team)

INTERVIEW ANSWER — "How do you design a secure API?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I approach API security in layers:

1. TRANSPORT: TLS 1.3 everywhere — no exceptions. No HTTP.
   Certificate pinning for mobile clients.

2. IDENTITY: Every request is authenticated. JWTs for stateless APIs,
   short expiry (15 min access tokens), refresh tokens with rotation.
   MFA for sensitive operations.

3. AUTHORIZATION: Check authorization on every endpoint — not just at login.
   Use RBAC for role-based access. Validate that user X is accessing THEIR
   data (not just any valid user's data) — prevents IDOR attacks.

4. INPUT VALIDATION: Validate all inputs on the server side. Parameterized
   queries for all database operations — never string concatenation.

5. RATE LIMITING + WAF: Rate limit by IP and by user. Deploy WAF to block
   OWASP attack patterns.

6. AUDIT LOGGING: Log all authentication events, authorization failures,
   and data mutations with user ID, IP, timestamp — immutable log.

Defense in depth: any single control failing doesn't mean compromise."
