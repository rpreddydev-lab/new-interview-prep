ZERO TRUST ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. THE CORE PHILOSOPHY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TRADITIONAL MODEL (Castle-and-Moat):
  Assumption: "Anything inside the network perimeter is trusted"
  Thick perimeter: Firewall blocks everything external
  Fat interior: Once inside, everything can talk to everything
  
  Problem 1: Perimeter is porous (VPN, phishing, supply chain)
  Problem 2: Lateral movement — attacker inside → compromises everything
  Problem 3: Cloud/remote work destroyed the concept of "inside the network"
  
  Famous failure: 2013 Target breach — HVAC vendor compromised → 
                  lateral movement → 40M credit cards stolen

ZERO TRUST PRINCIPLE:
  "Never trust, always verify"
  "Assume breach"
  
  Core tenets:
    1. Verify explicitly: Always authenticate and authorize every request
       Never trust because of network location
    2. Use least privilege access: Minimal access by default; just-in-time
    3. Assume breach: Design as if attacker is already inside
       Limit blast radius, encrypt internal traffic, log everything

WHAT CHANGES:
  Old: Trust based on network location (inside firewall = trusted)
  New: Trust based on identity, device posture, and context

  Old: VPN grants broad internal access
  New: Per-application access based on identity + device health

  Old: Internal services communicate freely (no mTLS)
  New: Every service-to-service call is authenticated and authorized (mTLS)


2. ZERO TRUST PILLARS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IDENTITY (WHO are you?):
  Strong authentication for every request
  - MFA required (not just username/password)
  - Identity Provider (IdP): Okta, Azure AD, Google Workspace
  - Single Sign-On (SSO): One identity across all applications
  - Device certificates: Machine identity in addition to user identity
  - SCIM provisioning: Automatic user provisioning/deprovisioning
  - Continuous verification: Re-authenticate on context change (new IP, long idle)

DEVICE (WHAT device are you using?):
  Every device must be known and healthy before access is granted
  - Device enrollment: Register devices with MDM (Mobile Device Management)
  - Device health checks:
    - OS up to date (no critical patches missing)
    - Antivirus running and updated
    - Full disk encryption enabled
    - Screen lock configured
  - Managed vs unmanaged: Higher trust for managed corporate devices
  - Device certificates: Issued by corporate CA; proves device enrollment
  - Endpoint Detection and Response (EDR): CrowdStrike, Carbon Black

NETWORK (WHERE are you?):
  Network location is NOT sufficient for trust, but is a signal
  - Micro-segmentation: Network divided into small zones; limit blast radius
  - Deny-all default: Only explicitly permitted traffic flows
  - mTLS everywhere: Encrypt and authenticate all service-to-service traffic
  - No flat internal network: Services can't reach each other by default
  - Software-Defined Perimeter (SDP): Network access defined by policy

APPLICATIONS (WHAT are you accessing?):
  Applications verify identity + context before granting access
  - Application-level authorization (not just network ACL)
  - Per-application access policies (different policies per app)
  - Attribute-Based Access Control (ABAC): time of day, location, risk score
  - API gateway enforces policy centrally

DATA (WHAT data are you accessing?):
  Protect data regardless of location
  - Data classification: Public, Internal, Confidential, Restricted
  - Encryption at rest: Data encrypted everywhere, not just perimeter
  - DLP (Data Loss Prevention): Prevent exfiltration
  - Rights Management: Encrypt files; only authorized identities can open


3. GOOGLE'S BEYONDCORP — ZERO TRUST IN PRACTICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HISTORY:
  2009: Google attacked by Chinese state hackers (Operation Aurora)
  2010: Google started building BeyondCorp
  2014: Published BeyondCorp research paper
  2017: Google employees work without VPN (access via BeyondCorp)
  2020: Google Cloud released BeyondCorp Enterprise as a product

CORE ARCHITECTURE:
  No VPN. All applications accessed via HTTPS through an Access Proxy.
  Access decisions based on: User identity + Device identity + Device state

  User → Internet → Access Proxy → [Identity Aware Proxy] → Internal App
  
  Every request to the Access Proxy:
    1. User must have valid Okta/Google SSO session
    2. Device must have valid device certificate (enrolled corporate device)
    3. Device health check: OS patched, disk encrypted, AV running
    4. Risk-based policy: Normal user from known device on office hours → allow
                         Same user from unmanaged device at 3am → MFA challenge

DEVICE INVENTORY DATABASE:
  Every corporate device registered with:
    - Hardware ID, serial number
    - OS version, patch level
    - Installed software
    - Enrollment certificate
  
  Health status updated continuously by MDM (Jamf for macOS, Intune for Windows)

ACCESS POLICY (example):
  Policy for "internal-wiki.google.com":
    Allow IF:
      user.ldap_group IN ["engineering", "product"]
      AND device.is_enrolled == true
      AND device.os_patch_level >= "2024-01-01"
      AND device.disk_encrypted == true
    
  Policy for "prod-payments-dashboard.google.com":
    Allow IF:
      user.ldap_group IN ["payments-team"]
      AND device.is_corp_owned == true
      AND session.mfa_verified == true
      AND context.risk_score < 40

RESULT:
  No firewall needed for internal applications
  Employees work from home, coffee shops, anywhere — same policy
  Contractors access only specific apps (not entire network)
  Blast radius of compromised account: limited to that user's permitted apps


4. MICRO-SEGMENTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM WITH FLAT NETWORKS:
  Traditional internal network: All servers in one big subnet
  If attacker compromises Server A → can scan entire subnet
  Can reach Server B, C, D, databases, admin interfaces
  LATERAL MOVEMENT is trivial

MICRO-SEGMENTATION:
  Divide network into small zones; each zone has strict boundaries
  Allow only explicitly required communication between zones

  Traditional:
    Internet → Firewall → FLAT INTERNAL NETWORK
                          (everything talks to everything)

  Micro-segmented:
    Internet → Firewall → Web Tier VPC (only 443)
                          ↓ (only specific API calls)
                          App Tier VPC (no public internet)
                          ↓ (only DB port 5432)
                          DB Tier VPC (no public internet, no outbound)

IMPLEMENTATION OPTIONS:

1. VPC SEGMENTATION (AWS):
   Separate VPCs for different tiers/environments
   VPC Peering or PrivateLink for selective connectivity
   Security groups: Allow only specific port/IP combinations
   
   Payment service VPC security group:
     Inbound: Allow 443 from API Gateway VPC only
     Inbound: Allow 5432 from payment-service only → DB
     Outbound: Allow 443 to stripe.com, paypal.com only
     DENY all other traffic

2. KUBERNETES NETWORK POLICIES:
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: allow-payment-to-db
     namespace: production
   spec:
     podSelector:
       matchLabels:
         app: postgres
     policyTypes: [Ingress]
     ingress:
     - from:
       - podSelector:
           matchLabels:
             app: payment-service
       ports:
       - port: 5432
   
   Default deny-all:
   spec:
     podSelector: {}        # All pods in namespace
     policyTypes: [Ingress, Egress]
     # No ingress or egress rules = deny all

3. SERVICE MESH (Istio):
   mTLS between all services automatically
   Authorization policies:
   apiVersion: security.istio.io/v1beta1
   kind: AuthorizationPolicy
   metadata:
     name: allow-payment-service
     namespace: production
   spec:
     selector:
       matchLabels:
         app: postgres
     rules:
     - from:
       - source:
           principals: ["cluster.local/ns/production/sa/payment-service"]
       to:
       - operation:
           ports: ["5432"]


5. PRIVILEGED ACCESS MANAGEMENT (PAM)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  Admin accounts are high-value targets
  Standing privileged access: Admin has root 24/7 (even when not needed)
  If admin account is compromised: attacker has root immediately

PRIVILEGED ACCESS WORKSTATIONS (PAW):
  Dedicated locked-down workstations for admin tasks only
  No email, no web browsing on PAW
  Separate from regular user workstations

JUST-IN-TIME (JIT) ACCESS:
  Admin access granted ON DEMAND for specific time window
  Access revoked automatically after time expires
  
  Process:
    1. Engineer requests "sudo on prod-db-01 for 2 hours"
    2. Request reviewed (manually or automatically based on policy)
    3. Approved: SSH certificate issued valid for 2 hours
    4. Engineer SSHes with time-limited cert
    5. After 2 hours: cert expires, access gone
  
  Tools: HashiCorp Vault SSH secrets engine, CyberArk, BeyondTrust

PRIVILEGED SESSION RECORDING:
  All privileged sessions recorded (keystrokes, screen)
  Stored in tamper-proof audit log
  "If you know you're being recorded, you behave better"
  Required for: SOC 2, HIPAA, PCI DSS compliance

BREAK-GLASS PROCEDURE:
  Emergency access for critical incidents
  Credentials stored in sealed physical envelope (or HSM)
  Require two-person rule: Two people must co-authorize
  Alert triggered immediately when used
  Full audit trail of all actions

INTERVIEW ANSWER — "What is Zero Trust and how would you implement it?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Zero Trust replaces the old castle-and-moat model — where the network
perimeter was the security boundary — with 'never trust, always verify.'

In practice this means three things:

1. IDENTITY-BASED ACCESS: Every user and service must prove identity
   on every request. For humans: SSO + MFA + device health check via MDM.
   For services: mTLS with certificates, short-lived AWS IAM roles,
   or SPIFFE/SPIRE service identity. No 'I'm inside the network therefore trusted.'

2. LEAST PRIVILEGE: Users and services get only the permissions they need,
   for only as long as they need them. JIT access for admin operations.
   Network policies that deny everything and allow only specific flows.

3. ASSUME BREACH: Design as if attackers are already inside. Encrypt 
   service-to-service traffic (mTLS via Istio). Micro-segment the network
   so a compromised service can't reach unrelated databases. Log and monitor
   all internal traffic.

Following Google's BeyondCorp model, I'd put all internal apps behind
an identity-aware proxy. No VPN — employees access internal tools via HTTPS,
but only if their device is managed, patched, and their identity is verified."
