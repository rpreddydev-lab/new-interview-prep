AUTHENTICATION AND AUTHORIZATION AT SCALE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. AUTHENTICATION vs AUTHORIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AUTHENTICATION (AuthN):
  "Who are you?"
  Verifying the identity of a user or system
  Examples: Password check, biometric, certificate, API key

AUTHORIZATION (AuthZ):
  "What are you allowed to do?"
  Verifying what an authenticated identity is permitted to do
  Examples: Role-based access, resource ownership check, policy evaluation

COMMON CONFUSION:
  A valid JWT proves you're authenticated — it does NOT prove you're
  authorized to access a specific resource.
  Both checks must happen on EVERY request.


2. SESSION MANAGEMENT — COOKIE vs TOKEN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SESSION COOKIE (traditional, stateful):
  Flow:
    1. User submits username/password
    2. Server validates, creates session record in Redis/DB
    3. Server returns Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict
    4. Browser sends cookie on all subsequent requests
    5. Server looks up session_id → retrieves user context
  
  Pros:
    - Easy to invalidate (delete session from store)
    - Server always has fresh session data
    - Simple to implement
  
  Cons:
    - Server-side session store required (Redis, DB)
    - Sticky session issue (request must hit same server, OR share Redis)
    - Cross-domain difficult (SameSite cookie restrictions)
    - Doesn't scale easily to microservices
  
  Cookie security flags:
    HttpOnly: JavaScript cannot read cookie → prevents XSS cookie theft
    Secure: Cookie only sent over HTTPS
    SameSite=Strict: Cookie not sent in cross-site requests → prevents CSRF
    SameSite=Lax: Cookie not sent in cross-site POST (allows GET navigations)

JWT (JSON Web Token, stateless):
  Structure: header.payload.signature
  
  Header:  { "alg": "RS256", "typ": "JWT" }  (Base64URL encoded)
  Payload: {
    "sub": "user123",
    "email": "alice@example.com",
    "roles": ["user", "admin"],
    "iat": 1700000000,   (issued at)
    "exp": 1700000900    (expires — 15 minutes later)
  }
  Signature: HMAC-SHA256(base64(header) + "." + base64(payload), secret)
             OR RSA private key signature (preferred for microservices)
  
  Validation (client can decode, server must verify signature):
    1. Decode header — get algorithm
    2. Fetch public key (for RSA) or use shared secret (for HMAC)
    3. Verify signature — reject if invalid
    4. Check exp claim — reject if expired
    5. Check iss (issuer), aud (audience) claims
  
  Pros:
    - Stateless — no server-side session store
    - Works across services (each service validates JWT independently)
    - Rich payload — user roles/claims embedded
    - Perfect for microservices
  
  Cons:
    - Cannot invalidate before expiry (no revocation by default)
    - If secret key leaked: ALL JWTs become forgeable
    - Should be short-lived (15 min access token)
    - Payload is Base64URL encoded, NOT encrypted — don't store secrets in it

JWT REVOCATION STRATEGIES:
  Problem: JWT with 1-hour expiry can't be invalidated if user logs out
           or account is suspended
  Solutions:
    1. Short expiry (15 minutes): Reduce window of vulnerability
    2. Refresh token rotation: Invalidate refresh tokens in DB
    3. Token blocklist (Redis): Store "jti" (JWT ID) of revoked tokens
       Check on every request: O(1) lookup in Redis
       Downside: Stateful (undermines stateless benefit)
    4. Version field: User has token_version in DB; JWT carries version
       If JWT version < DB version, reject. Allows per-user invalidation.


3. OAUTH 2.0 — AUTHORIZATION FRAMEWORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PURPOSE: Allow a third-party application to access a user's resources
         without sharing the user's password

ROLES:
  Resource Owner: The user who owns the data
  Client: The third-party application requesting access
  Authorization Server: Issues access tokens (Google, GitHub, Auth0)
  Resource Server: The API holding the user's data

FLOWS (Grant Types):

AUTHORIZATION CODE FLOW (most secure — for web apps with backend):
  1. Client redirects user to Authorization Server:
     GET https://auth.server.com/authorize?
       response_type=code&
       client_id=my_app&
       redirect_uri=https://myapp.com/callback&
       scope=read:profile email&
       state=random_csrf_token
  
  2. User logs in and approves access
  
  3. Authorization Server redirects to callback with code:
     GET https://myapp.com/callback?code=AUTH_CODE&state=random_csrf_token
  
  4. Backend exchanges code for tokens (server-to-server, secret required):
     POST https://auth.server.com/token
     { grant_type: authorization_code, code: AUTH_CODE,
       client_id: my_app, client_secret: MY_SECRET,
       redirect_uri: https://myapp.com/callback }
  
  5. Authorization Server returns:
     { access_token: "jwt...", refresh_token: "...", expires_in: 900 }
  
  6. Client calls Resource Server with: Authorization: Bearer jwt...

PKCE (Proof Key for Code Exchange) — for SPAs and mobile apps:
  Problem: SPAs and mobile apps can't safely store client_secret
  Solution: Use code_verifier (random string) + code_challenge (SHA256 hash)
  Client sends code_challenge in step 1; server verifies code_verifier in step 4
  No client_secret needed — prevents authorization code interception attacks

CLIENT CREDENTIALS FLOW (machine-to-machine):
  For service-to-service authentication (no user involved)
  POST /token { grant_type: client_credentials, client_id, client_secret }
  Returns access token valid for the service itself

COMMON MISTAKE: Using Implicit Flow (deprecated) for SPAs
  Tokens returned in URL fragment — visible in browser history, logs
  Use Authorization Code + PKCE instead


4. OPENID CONNECT (OIDC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT: Identity layer on top of OAuth 2.0
PURPOSE: OAuth 2.0 is for AUTHORIZATION (access tokens).
         OIDC adds AUTHENTICATION (who the user is).

ADDS TO OAUTH 2.0:
  ID Token: A JWT containing user identity claims
  Userinfo endpoint: GET /userinfo → {sub, name, email, picture}
  Standard claims: sub, name, email, picture, locale, phone_number
  Discovery document: /.well-known/openid-configuration (all endpoints)
  
  ID Token payload:
  {
    "iss": "https://accounts.google.com",
    "sub": "110169484474386276334",   (stable unique user ID)
    "aud": "your_client_id",
    "email": "user@gmail.com",
    "exp": 1700001800,
    "iat": 1700000000
  }

OIDC vs OAuth2:
  Use OAuth2 alone: "I want to access user's Google Drive files"
  Use OIDC: "I want to log in with Google" (get user identity)
  Use both together: "Login with Google" + "Access their Drive files"


5. PASSWORD SECURITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NEVER store plaintext passwords.
NEVER use MD5 or SHA-1 for passwords (fast hash → brute-forceable).

CORRECT APPROACH: Adaptive hashing algorithms
  BCrypt:
    - Slow by design (tunable work factor)
    - Incorporates salt automatically
    - bcrypt.hash("password", 12) — 12 = work factor (2^12 iterations)
    - Work factor 12: ~250ms per hash on modern CPU
    - Work factor should increase as CPUs get faster
  
  Argon2 (modern recommendation):
    - Winner of Password Hashing Competition (2015)
    - Configurable time, memory, and parallelism
    - argon2id variant recommended (time=3, memory=64MB, parallelism=4)
    - Resistant to GPU attacks (memory-hard)
  
  PBKDF2:
    - NIST-recommended, FIPS 140-2 compliant
    - Required for US government systems
    - Less memory-hard than Argon2

SALT: Random value added to password before hashing
  Prevents rainbow table attacks (precomputed hash lookups)
  BCrypt/Argon2 automatically generate and store salt

PEPPERS: Application-level secret added to all passwords
  Stored in application config (NOT in database)
  Even if DB is breached, attacker needs both DB and pepper to crack passwords

ACCOUNT LOCKOUT:
  Lock account after N failed attempts (5-10 typical)
  Exponential delays between attempts: 1s, 2s, 4s, 8s...
  CAPTCHA after 3 failures
  Alert user of failed login attempts


6. MULTI-FACTOR AUTHENTICATION (MFA)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FACTORS:
  Something you know: Password, PIN, security questions
  Something you have: Phone (TOTP app, SMS), hardware token (YubiKey)
  Something you are: Biometric (fingerprint, face)

TOTP (Time-based One-Time Password) — RFC 6238:
  Standard: Google Authenticator, Authy, 1Password
  Algorithm:
    1. During setup: Server generates 160-bit secret, shown as QR code
    2. Secret stored in authenticator app AND server
    3. At login: TOTP = HMAC-SHA1(secret, floor(time/30))
    4. 6-digit code changes every 30 seconds
    5. Server computes same code and compares
    6. Window: Accept codes from ±1 time step (clock drift tolerance)
  
  Advantages: No SMS dependency, works offline, phishing-resistant
  
SMS OTP:
  Weaknesses: SIM swapping, SS7 attacks, carrier-level intercept
  Only use as fallback when TOTP isn't available

WEBAUTHN / FIDO2 (Passkeys):
  Strongest MFA — phishing-resistant hardware-bound credentials
  Uses public-key cryptography:
    1. Registration: Browser generates key pair; public key stored on server
    2. Authentication: Browser signs challenge with private key (device-bound)
  Stored in device secure enclave (TPM, Secure Enclave)
  Cannot be phished — credential bound to origin (no replay on fake site)
  Supported by: Apple, Google, Microsoft, GitHub, Dropbox


7. AUTHORIZATION MODELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RBAC (Role-Based Access Control):
  Permissions assigned to roles; users assigned to roles
  
  User → Role → Permissions
  alice → admin → [read, write, delete, manage_users]
  bob   → editor → [read, write]
  carol → viewer → [read]
  
  Pros: Simple, easy to audit, scales well for coarse-grained access
  Cons: Role explosion (hundreds of roles for fine-grained access)

ABAC (Attribute-Based Access Control):
  Permissions based on attributes of user, resource, and environment
  
  Policy: ALLOW if:
    user.department == resource.owner_department
    AND resource.classification == "public" OR user.clearance >= resource.classification
    AND request.time >= business_hours
  
  Pros: Extremely fine-grained; context-aware (time of day, IP, device)
  Cons: Complex to define and audit; policy evaluation can be slow
  Used by: AWS IAM, Google Cloud IAM

PBAC (Policy-Based Access Control):
  Define explicit policies; evaluate against request context
  Open Policy Agent (OPA): Policy-as-code; Rego language
  
  package authz.api
  allow {
    input.method == "GET"
    input.path == "/documents"
    input.user.roles[_] == "reader"
  }

OWNERSHIP / RESOURCE-BASED:
  Each resource has an owner; only owner (and admins) can modify
  Critical for IDOR prevention:
    WRONG: GET /orders/{orderId}  → return order (any authenticated user)
    RIGHT: GET /orders/{orderId}  → verify order.userId == request.userId
                                    OR user has admin role

API KEY AUTHENTICATION (service-to-service):
  Simple shared secret in HTTP header:
  Authorization: ApiKey sk-prod-abc123
  
  Store: Hash the API key in DB (SHA-256); never store plaintext
  Rotate: Support multiple active keys during rotation
  Scope: Limit what each key can do
  Rate limit: Per API key

INTERVIEW ANSWER — "How do you implement authentication at scale?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"For a distributed system serving millions of users, I use JWTs:

Users authenticate via the auth service, which issues a short-lived
access token (JWT, 15 minutes) and a long-lived refresh token (7 days).
The refresh token is stored in an HttpOnly Secure SameSite=Strict cookie —
inaccessible to JavaScript. The access token is in memory only.

Each microservice validates the JWT independently using the auth service's
public key — no session store lookup required. I keep JWTs short-lived
to minimize exposure from token theft.

For OAuth2 social login, I use Authorization Code + PKCE flow for web
and mobile clients. For service-to-service calls, Client Credentials flow
with client ID/secret stored in AWS Secrets Manager — never in code.

For authorization, every endpoint checks: 'Is this user authorized to
perform this action on this resource?' — not just at the API gateway,
but at the service level too. IDOR prevention requires checking that
users only access their own data.

I require MFA for admin actions and account recovery using TOTP (not SMS).
Passwords are hashed with Argon2id — never with MD5 or SHA1."
