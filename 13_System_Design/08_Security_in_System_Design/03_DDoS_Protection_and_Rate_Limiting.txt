DDoS PROTECTION AND RATE LIMITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. DDoS — DISTRIBUTED DENIAL OF SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
  Attempt to make a service unavailable by overwhelming it with traffic
  from many distributed sources (botnet)
  "Distributed" because traffic comes from thousands of IPs (hard to block)

WHY DIFFICULT TO DEFEND:
  - Traffic looks legitimate at packet level
  - No single source IP to block
  - Attack volume can exceed upstream bandwidth
  - Application-layer attacks are hard to distinguish from real users
  - Amplification attacks can be enormous (millions of rps from small botnet)

DDoS ATTACK TYPES:

VOLUMETRIC ATTACKS (Layer 3/4 — Network):
  Goal: Saturate upstream bandwidth / overwhelm routers
  Volume: Can reach Tbps (Terabits per second)
  
  UDP Flood:
    Send massive UDP packets to random ports
    Target tries to reply with ICMP "unreachable" — exhausts bandwidth
  
  ICMP Flood (Ping Flood):
    Massive ICMP echo requests
    Target must process each one; bandwidth saturated
  
  DNS Amplification:
    Attacker sends DNS queries with forged source IP (victim's IP)
    DNS server sends large responses to victim
    Amplification factor: Up to 100× (10 bytes in → 1000 bytes out)
  
  NTP Amplification:
    Similar to DNS, using NTP "monlist" command
    Amplification factor: Up to 556×
  
  Memcached Amplification:
    Amplification factor: Up to 50,000× (largest ever seen)
    February 2018: GitHub attacked at 1.35 Tbps using Memcached

PROTOCOL ATTACKS (Layer 4):
  Goal: Exhaust server resources (connection tables, state machines)
  
  SYN Flood:
    Send TCP SYN packets without completing handshake (never send ACK)
    Server allocates resources for each half-open connection
    SYN backlog queue fills up; legitimate connections refused
    
    Mitigation: SYN cookies — server doesn't allocate state until handshake complete
                Server encodes state into initial sequence number
  
  ACK Flood:
    Send TCP ACK packets for non-existent connections
    Server must look up each in connection table → CPU exhaustion

APPLICATION LAYER ATTACKS (Layer 7 — hardest to defend):
  Goal: Exhaust application resources (DB connections, CPU, memory)
  Volume: Low bandwidth, high CPU cost per request
  
  HTTP Flood:
    Thousands of bots send legitimate-looking HTTP GET/POST requests
    Indistinguishable from real users at packet level
    Mitigation: Rate limiting, bot detection, CAPTCHAs
  
  Slowloris:
    Open many connections, send HTTP headers extremely slowly
    Never complete the request → keep connection alive
    Server connection pool exhausted; legitimate requests blocked
    
    Mitigation: Connection timeouts, maximum connections per IP
  
  Algorithmic Complexity Attack:
    Send requests that trigger worst-case algorithm performance
    Example: Hash table with carefully crafted keys that all hash to same bucket
    O(1) lookup becomes O(N) → server melts
    
    Example: RegexDOS — send input that triggers catastrophic backtracking
    in regex engine (polynomial or exponential time)


2. DDoS MITIGATION STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ANYCAST DIFFUSION:
  Distribute attack traffic across global network
  Attacker targeting one IP → traffic spread to 100+ PoPs worldwide
  Each PoP handles a fraction → no single location overwhelmed
  Used by: Cloudflare (320+ Tbps network capacity), Akamai

BGP BLACKHOLING (Null Routing):
  ISP routes attack traffic to /dev/null (null route)
  The attacked IP stops receiving all traffic (good AND bad)
  Last resort — takes down the service for everyone
  RTBH (Remote Triggered Black Hole) — upstream ISP initiates

SCRUBBING CENTERS:
  Traffic rerouted through specialized cleaning centers
  Scrubbers filter attack traffic; clean traffic forwarded to origin
  Akamai Kona, Cloudflare Magic Transit, AWS Shield Advanced

UPSTREAM FILTERING:
  Work with ISP/transit provider to block traffic upstream
  Before it reaches your network

LAYER 7 MITIGATION:
  Challenge-response: CAPTCHA, JavaScript challenges
  Rate limiting: Limit requests per IP, per user
  IP reputation: Block known bad IPs (threat intelligence feeds)
  Behavioral analysis: Machine learning to detect attack patterns
  Device fingerprinting: Browser fingerprint to identify bots

CLOUD PROVIDERS:
  AWS Shield Standard (free):
    - Always-on Layer 3/4 protection
    - SYN/UDP flood protection, reflection attack mitigation
    - Included for all AWS customers
  
  AWS Shield Advanced ($3,000/month + data transfer costs):
    - Enhanced Layer 3/4/7 protection
    - DDoS Response Team (DRT) 24/7 support
    - Near real-time visibility
    - Cost protection (AWS won't charge for DDoS-related scaling)
    - Web ACL with AWS WAF
  
  Cloudflare:
    - Free tier includes DDoS protection
    - Anycast network: 320+ Tbps capacity
    - Automatic L3/4/7 mitigation
    - Magic Transit: BGP-announced IP space with Cloudflare scrubbing


3. RATE LIMITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PURPOSES:
  1. Prevent abuse (brute force, scraping, DDoS)
  2. Ensure fair usage (one user can't monopolize resources)
  3. Cost control (limit expensive operations)
  4. SLA enforcement (don't exceed what you can serve)

WHAT TO RATE LIMIT BY:
  Per IP: Limit requests per IP address (L4)
  Per User: Limit authenticated user's request rate
  Per API Key: Limit service-to-service clients
  Per Endpoint: Different limits for different operations
    GET /search: 100/minute (expensive)
    POST /login: 5/minute (brute force protection)
    POST /message: 30/minute (spam protection)

RATE LIMITING ALGORITHMS:

TOKEN BUCKET (most popular, allows bursting):
  - Bucket holds up to N tokens (N = burst capacity)
  - Tokens refill at R tokens/second (R = sustained rate)
  - Each request consumes 1 token
  - If bucket empty: reject request (HTTP 429)
  
  Example: R=100 req/s, N=200 tokens burst capacity
    Idle for 2 seconds: accumulates 200 tokens (at cap)
    Burst of 200 requests: all pass (consume all tokens)
    Next 100 requests: pass at 100/s rate
    If burst exceeds 200: excess requests rejected
  
  Key property: ALLOWS BURSTING above sustained rate

LEAKY BUCKET (smooth output, no bursting):
  - All requests enter a queue (bucket)
  - Requests processed at constant rate (drip rate)
  - If queue full: reject request
  
  Key property: Smooths traffic — output is constant regardless of burst
  Use for: Upstream APIs that can't handle bursts

FIXED WINDOW COUNTER:
  - Count requests in fixed time windows (e.g., 60 seconds)
  - If count > limit: reject
  
  Example: 100 req/minute
    Window 1 (0-60s): First 100 pass, rest rejected
    Window 2 (60-120s): Counter resets, first 100 pass again
  
  PROBLEM: Boundary exploit
    At t=59s: 100 requests (limit hit for window 1)
    At t=61s: 100 requests (new window for window 2)
    In 2 seconds, user made 200 requests (2× limit)

SLIDING WINDOW LOG:
  - Maintain timestamp log of all requests
  - For each new request: count requests within last 60 seconds
  - If count > limit: reject
  
  Pros: Precise, no boundary exploit
  Cons: Memory-heavy (store every request timestamp)

SLIDING WINDOW COUNTER (best of both):
  - Approximate sliding window using two fixed windows
  - Weight current window's count + previous window's count
    by their overlap with the sliding window
  
  current_count = prev_window_count × (1 - elapsed/window_size)
                + current_window_count
  
  Memory-efficient, good accuracy (~0.003% error in experiments)
  USED BY: Cloudflare, NGINX, Redis-based rate limiters


4. DISTRIBUTED RATE LIMITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM:
  Multiple API servers; each has its own in-memory counter
  User A sends 100 req to Server 1, 100 req to Server 2
  Each server thinks: "100 requests — within limit of 100"
  Actual rate: 200 — DOUBLE the limit

SOLUTION: Centralized rate limit store

REDIS-BASED RATE LIMITING:
  Atomic increment + expiry with Lua script (or Redis INCRBY):
  
  -- Lua script (executed atomically in Redis)
  local count = redis.call('INCR', key)
  if count == 1 then
    redis.call('EXPIRE', key, window_seconds)
  end
  if count > limit then
    return 0  -- reject
  else
    return 1  -- allow
  end
  
  Key: "rate_limit:{user_id}:{window_start}"
  Atomic: No race conditions between INCR and EXPIRE

REDIS CLUSTER CONSIDERATIONS:
  Rate limit key for user A should always go to the same Redis shard
  Key: "rate_limit:{user_id}" — use user_id as hash tag
  Redis Cluster hash slots: {user_id} ensures same slot
  
  Replication: Rate limiter can tolerate losing Redis data briefly
               Losing counter data means a brief window of no rate limiting
               NOT a catastrophic failure

RATE LIMITER AT API GATEWAY vs APPLICATION:
  API Gateway (preferred for most):
    - Kong, AWS API Gateway, NGINX — built-in rate limiting
    - Centralized — applies before request reaches service
    - Consistent policy across all services
  
  Application-level:
    - More granular (per-operation, per-business-logic)
    - Handles rate limiting that needs user context
    - Example: Free tier vs paid tier → different rate limits
               Only application knows the user's tier


5. RATE LIMIT RESPONSE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HTTP 429 Too Many Requests
Headers to include:
  Retry-After: 30           (seconds until they can retry)
  X-RateLimit-Limit: 100   (their limit)
  X-RateLimit-Remaining: 0  (how many remaining in window)
  X-RateLimit-Reset: 1700000060  (Unix timestamp when window resets)

Response body:
  {
    "error": "rate_limit_exceeded",
    "message": "Too many requests. Please retry after 30 seconds.",
    "retry_after_seconds": 30
  }

GRACEFUL CLIENTS:
  Good API clients respect Retry-After
  Implement exponential backoff when receiving 429s
  Don't hammer the API upon receiving 429 — that makes it worse


6. WAF (WEB APPLICATION FIREWALL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT IT DOES:
  Inspects HTTP/HTTPS requests
  Blocks known attack patterns (OWASP Top 10)
  Can block based on: IP, geography, headers, request body, rate

MANAGED RULE GROUPS (AWS WAF examples):
  AWSManagedRulesCommonRuleSet: OWASP Top 10 basics
  AWSManagedRulesSQLiRuleSet: SQL injection patterns
  AWSManagedRulesKnownBadInputsRuleSet: Log4j, Spring4Shell
  AWSManagedRulesAmazonIpReputationList: Amazon threat intelligence IPs
  
  Custom rules:
    Block requests with User-Agent: "sqlmap" (SQL injection tool)
    Block requests with path: "/../../../etc/passwd" (path traversal)
    Rate-based rule: Block IP after 2000 requests in 5 minutes

WAF PLACEMENT:
  CloudFront → WAF → ALB → Application
  (WAF at CloudFront: Edge protection, global)
  (WAF at ALB: Regional, for non-CloudFront traffic)

WAF IN COUNT MODE vs BLOCK MODE:
  New rules: Start in COUNT mode (log but don't block)
  Monitor for false positives
  After validation: Switch to BLOCK mode
  Always have a manual override for emergencies

INTERVIEW ANSWER — "How would you design a rate limiter?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I'd use a token bucket algorithm backed by Redis for distribution.

Each user gets a bucket of N tokens (burst capacity). Tokens refill
at R per second (sustained rate). Each request consumes a token.
If the bucket is empty, return HTTP 429 with Retry-After header.

In Redis: INCR + EXPIRE in a Lua script for atomicity. Key is
'rate_limit:{user_id}:{window}'. Redis Cluster with hash tags ensures
all rate limit state for a user hits the same shard.

For DDoS protection at a larger scale, I'd deploy at the API Gateway
(Kong/AWS API Gateway) so the rate limit check happens before the
request hits any application server — saving compute.

For DDoS specifically, I'd use AWS Shield with CloudFront in front
of everything. Cloudflare's Anycast absorbs volumetric attacks before
they reach origin. A WAF with OWASP managed rules handles Layer 7.

Different rate limits per tier: free users get 100/min, paid users
1,000/min — stored in user metadata, enforced at the application level."
