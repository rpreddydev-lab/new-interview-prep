RELIABILITY & AVAILABILITY — COMPLETE OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CORE DEFINITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RELIABILITY
  Definition: Probability that a system performs its required functions
              under stated conditions for a specified time period
  Focus: Correctness and consistency over time
  Measurement: MTTF, MTBF (see below)
  Example: A database that never returns wrong data, even under load

AVAILABILITY
  Definition: Fraction of time a system is operational and accessible
  Formula:    Availability = Uptime / (Uptime + Downtime)
  Focus: Time-based — is the service UP right now?
  Example: 99.99% availability = 52.6 minutes of downtime per year

DURABILITY
  Definition: Guarantee that stored data will not be lost
  Focus: Data persistence over time
  Example: S3 offers 11 nines (99.999999999%) durability
  Note: A durable system can still be unavailable (e.g., maintenance)

RESILIENCY
  Definition: Ability of a system to recover gracefully from failures
  Focus: Recovery speed and continuity
  Example: Auto-scaling group replaces a failed instance in 60 seconds

KEY INSIGHT: These are related but distinct:
  - A system can be AVAILABLE but not RELIABLE (up, but returning wrong data)
  - A system can be RELIABLE but not AVAILABLE (correct when up, but often down)
  - A system can be DURABLE but not AVAILABLE (data safe, but service is down)


2. THE NINES TABLE — AVAILABILITY TARGETS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌────────────────┬──────────────────┬──────────────────┬──────────────────┐
│ Availability   │ Downtime/Year    │ Downtime/Month   │ Downtime/Week    │
├────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 90%  (1 nine)  │ 36.5 hours       │ 72 hours         │ 16.8 hours       │
│ 99%  (2 nines) │ 87.6 hours       │ 7.3 hours        │ 1.68 hours       │
│ 99.9% (3 nine) │ 8.76 hours       │ 43.8 minutes     │ 10.1 minutes     │
│ 99.95%         │ 4.38 hours       │ 21.9 minutes     │ 5 minutes        │
│ 99.99% (4nine) │ 52.6 minutes     │ 4.4 minutes      │ 1.01 minutes     │
│ 99.999% (5nine)│ 5.26 minutes     │ 26.3 seconds     │ 6.05 seconds     │
│ 99.9999%(6nine)│ 31.5 seconds     │ 2.63 seconds     │ 0.6 seconds      │
└────────────────┴──────────────────┴──────────────────┴──────────────────┘

REAL-WORLD TARGETS:
  Consumer apps (e.g., blog):    99% — 87.6 hours downtime/year acceptable
  E-commerce:                    99.9% — tolerate ~9 hours downtime/year
  Business SaaS (e.g., Salesforce): 99.99% — 52 minutes/year
  Telecom, banking, healthcare:  99.999% — 5 minutes/year
  Space/medical/nuclear systems: 99.9999%+

COMPOSITE AVAILABILITY (services in series):
  If Service A = 99.9% and Service B = 99.9%:
  Total = 99.9% × 99.9% = 99.8%

  Rule: Every dependency REDUCES total availability
  With 10 dependencies each at 99.9%: 99.9%^10 = 99.0%

COMPOSITE AVAILABILITY (redundant services in parallel):
  If Service A has 99% availability and you add a replica:
  Total = 1 - (1 - 99%)^2 = 1 - 0.01^2 = 99.99%

  Rule: Redundancy dramatically IMPROVES availability


3. KEY METRICS: MTTF, MTTR, MTBF
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MTTF — Mean Time To Failure
  Definition: Average time a system runs before its first failure
  Formula:    MTTF = Total operational time / Number of failures
  Used for:   Non-repairable components (e.g., hard drives)
  Example:    Hard drive with MTTF of 300,000 hours (34 years)
              Does NOT mean it will last 34 years — 1/3 fail before MTTF

MTTR — Mean Time To Repair (or Recover)
  Definition: Average time to restore a system after a failure
  Formula:    MTTR = Total repair time / Number of repairs
  Goal:       Minimize this — faster recovery → higher availability
  Components: Detection time + Response time + Repair time + Restart time
  Example:    Automated failover: MTTR ~30 seconds
              Manual on-call incident: MTTR ~30-60 minutes

MTBF — Mean Time Between Failures
  Definition: Average time between consecutive failures (includes repair time)
  Formula:    MTBF = MTTF + MTTR
  Used for:   Repairable systems
  Example:    Server fails every 1,000 hours and takes 5 hours to fix
              MTBF = 1,000 + 5 = 1,005 hours

AVAILABILITY FROM MTBF AND MTTR:
  Availability = MTTF / (MTTF + MTTR) = MTTF / MTBF

  Example:
    MTTF = 1,000 hours
    MTTR = 1 hour
    Availability = 1,000 / 1,001 = 99.9%

  To reach 99.99%:
    With MTTF = 1,000 hours:
    MTTR must be ≤ 0.1 hours = 6 minutes!

  KEY INSIGHT: To improve availability, either:
    1. Increase MTTF (better hardware, more testing, redundancy)
    2. Decrease MTTR (faster detection, automation, runbooks)


4. FAILURE MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HARDWARE FAILURES:
  - Disk failure (HDDs: ~1-5% annual failure rate; SSDs: lower but not zero)
  - Memory errors (cosmic rays cause ~1 bit flip/GB/month)
  - Power supply failure
  - Network card failure
  - Rack-level: PDU (power distribution unit) failure
  - Data center: flood, fire, power outage

SOFTWARE FAILURES:
  - Bugs / logic errors
  - Memory leaks (process slowly consumes all RAM)
  - Deadlocks (two threads wait for each other's locks forever)
  - Infinite loops / runaway processes
  - Configuration errors (most common cause of outages)
  - Dependency failures (library version incompatibility)
  - Thundering herd (all nodes retry simultaneously after outage)

NETWORK FAILURES:
  - Packet loss
  - High latency (congestion, routing loops)
  - Network partition (two halves of cluster can't communicate)
  - DNS failures (cache poisoning, resolver outage)
  - BGP misconfigurations (Facebook 2021: 6-hour outage)

HUMAN ERRORS:
  - Accidental deletion (most common cause of data loss)
  - Misconfiguration during deployment
  - Wrong command on wrong server
  - Capacity planning mistakes
  NOTE: ~80% of all outages have a human-error component

OVERLOAD / CAPACITY:
  - Traffic spike beyond provisioned capacity
  - Cascading failure (one service fails → others overloaded)
  - Resource exhaustion (CPU, memory, file descriptors, connections)
  - Slow queries consuming all DB connections

BYZANTINE FAILURES:
  - Component fails in arbitrary/unexpected ways
  - Returns wrong data instead of failing clearly
  - Hardest to detect and handle
  - Example: disk silently corrupting writes (silent data corruption)


5. FAILURE PATTERNS AND BEHAVIORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FAIL-STOP:
  Component stops operating and notifies others of failure
  Best case — easy to detect and handle
  Example: A server that crashes and stops responding

FAIL-SLOW:
  Component continues operating but with degraded performance
  Worst case for availability — everything slows down, nothing fails cleanly
  Example: A network link with 50% packet loss, causing retries everywhere
  Strategy: Timeouts and circuit breakers to detect and isolate

FAIL-SILENT (or fail-partial):
  Component fails but appears healthy to health checks
  Example: Service responds to health checks but fails real requests
  Strategy: Synthetic monitoring (send real test transactions)

CASCADING FAILURES:
  One failure causes others, which cause more:
  User → API → Service A → DB connection pool exhausted
             → Service B → also trying to hit same DB
                         → Service B times out
                                    → User retries
                                               → More load on API
  Prevention: Circuit breakers, bulkheads, load shedding

CORRELATED FAILURES:
  Multiple components fail simultaneously due to shared cause
  Example: All servers in one AZ fail during AZ power outage
  Example: All replicas crash due to same software bug
  Strategy: Geographic distribution, diverse hardware vendors


6. RELIABILITY DESIGN PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

REDUNDANCY:
  - Active-Active: Multiple instances all serving traffic
  - Active-Passive: Hot/warm standby ready to take over
  - N+1: Always have one more instance than needed
  - Geographic: Multi-AZ, Multi-region

ISOLATION:
  - Bulkhead Pattern: Separate resource pools per consumer
  - Cell Architecture: Independent cells; failures don't cross cells
  - Failure Domains: Hardware in different racks/AZs/regions

TIMEOUTS AND RETRIES:
  - Every network call must have a timeout
  - Retry with exponential backoff + jitter
  - Idempotent operations required for safe retry
  - Retry budget (don't retry indefinitely)

CIRCUIT BREAKERS:
  - Detect repeated failures and "open" the circuit
  - Fail fast instead of waiting for timeout
  - Half-open state to probe recovery

GRACEFUL DEGRADATION:
  - Core features continue when non-critical dependencies fail
  - Example: Show cached product data if recommendation service is down
  - Fallback values, default responses

CHAOS ENGINEERING:
  - Proactively inject failures to find weaknesses
  - "If we don't test for failure, we're just hoping it doesn't happen"

IMMUTABLE INFRASTRUCTURE:
  - Never modify running servers; replace them
  - Ensures known good state, fast recovery via re-deployment


7. RELIABILITY vs PERFORMANCE TRADE-OFFS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

REPLICATION:
  Pro: Increases availability (tolerate node failures)
  Con: Increases latency (write must propagate), storage cost

SYNCHRONOUS REPLICATION:
  Pro: Guarantees no data loss (strong durability)
  Con: Increases write latency, reduces availability during replica lag

ASYNCHRONOUS REPLICATION:
  Pro: Low write latency, high availability
  Con: Potential data loss on failover (RPO > 0)

QUORUM READS/WRITES (e.g., Cassandra with RF=3, W=2, R=2):
  Pro: Tolerates node failures while guaranteeing consistency
  Con: Higher latency than single-node reads/writes

HEALTH CHECKS AND LOAD BALANCER PROBES:
  Pro: Traffic redirected away from unhealthy instances automatically
  Con: Small window of failures before detection; brief traffic disruption

INTERVIEW ANSWER — "How do you design a highly available system?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I approach high availability across four dimensions:

1. ELIMINATE SINGLE POINTS OF FAILURE
   - Every component has at least N+1 redundancy
   - Active-active preferred over active-passive where possible
   - Geographic distribution across at least 2 AZs, 2 regions for 5-nines

2. DETECT FAILURES FAST
   - Health checks (liveness + readiness) at every tier
   - Synthetic monitoring — real transactions, not just pings
   - Alerting with SLO-based burn rate alerts (not just raw error rates)
   - Target MTTD (mean time to detect) under 2 minutes

3. RECOVER FAST (minimize MTTR)
   - Automated failover — no human in the loop for common failures
   - Runbooks for on-call engineers
   - Canary deployments to catch bad releases early
   - Feature flags for instant rollback without redeployment

4. PREVENT CASCADING FAILURES
   - Circuit breakers on all outbound calls
   - Timeouts on every network request
   - Bulkhead pattern — separate thread pools per downstream
   - Rate limiting and load shedding at the edge

For a concrete target: to hit 99.99% (52 minutes downtime/year),
with MTTF of 1,000 hours, MTTR must be under 6 minutes.
Automation is the only way to achieve that consistently."
