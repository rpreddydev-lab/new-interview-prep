1. WHAT IS CHAOS ENGINEERING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
  "The discipline of experimenting on a system in order to build
   confidence in the system's capability to withstand turbulent
   conditions in production."
   — Netflix Chaos Engineering team

THE CORE IDEA:
  Things WILL break in production. The question is: do you find out
  during a planned chaos experiment with a prepared team, or at 3am
  during Black Friday with a panicked team?

  "We prefer to find weaknesses before they become incidents."

THE FUNDAMENTAL INSIGHT:
  Testing individual components is not enough. In distributed systems,
  failures emerge from interactions between components — behaviors that
  unit/integration tests never reveal.

  Example: Your service handles DB connection failures correctly.
           Your cache handles eviction correctly.
           But when both happen simultaneously: 30 threads try to
           regenerate the cache, all hit the DB, triggering a thundering
           herd that exhausts the DB connection pool → complete outage.

CHAOS ENGINEERING vs RANDOM TESTING:
  NOT randomly breaking things hoping something goes wrong
  IS structured scientific experimentation:
    1. Define steady state (what "healthy" looks like)
    2. Hypothesize that steady state continues during experiment
    3. Inject controlled failure
    4. Observe: does steady state hold?
    5. Fix weaknesses found


2. NETFLIX'S SIMIAN ARMY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Netflix pioneered chaos engineering when they moved to AWS (2008-2011).
They needed to validate that their system was truly resilient.

CHAOS MONKEY (2011):
  What: Randomly terminates EC2 instances in production during business hours
  Why: Force engineers to build services that survive instance failures
       "If we don't kill our own instances, Amazon will at the worst time"
  Result: Teams had to implement proper health checks, graceful degradation,
          auto-scaling — or face customer-visible incidents

CHAOS GORILLA:
  Simulates the failure of an entire AWS Availability Zone
  Verifies that the system can lose a full AZ and continue serving traffic
  Less frequent than Chaos Monkey (AZ failures are rare but catastrophic)

CHAOS KONG:
  Simulates the failure of an entire AWS Region
  Netflix runs quarterly Chaos Kong exercises
  Tests full regional failover — DNS changes, traffic rerouting, data sync

LATENCY MONKEY:
  Introduces artificial delays in RESTful client-server communication
  Simulates degraded network — a failure mode much more common than crashes
  Tests: Do timeouts work? Do circuit breakers trip? Do fallbacks activate?

CONFORMITY MONKEY:
  Checks if instances follow Netflix best practices (not a failure injector)
  Finds instances that are incorrectly configured or violate standards
  Terminates non-conforming instances (forces teams to fix configs)

SECURITY MONKEY:
  Finds security violations and misconfigured AWS resources
  Example: Security groups with 0.0.0.0/0 rules, unencrypted S3 buckets

DOCTOR MONKEY:
  Runs health checks on every instance
  Checks memory, CPU, disk, application health
  Removes instances that are degraded (before they cause incidents)

JANITOR MONKEY:
  Finds and deletes unused AWS resources (old snapshots, unused ELBs)
  Reduces costs and attack surface

10-18 MONKEY (Localization-Configuration):
  Tests Netflix UI in multiple languages/regions
  Detects configuration drift across regions


3. PRINCIPLES OF CHAOS ENGINEERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PRINCIPLE 1: BUILD A HYPOTHESIS AROUND STEADY STATE BEHAVIOR
  Steady state: A measurable output indicating normal system behavior
  Examples:
    - Request success rate > 99.9%
    - p99 latency < 200ms
    - Transactions processed per second > 1,000
  
  Hypothesis: "When we kill one of three database replicas,
               the request success rate remains above 99.9%"
  
  NOT: "When we kill a DB replica, nothing bad happens"
       (too vague — you can't measure "nothing bad")

PRINCIPLE 2: VARY REAL-WORLD EVENTS
  Inject failures that actually happen in production:
    - Instance/process crashes (most common)
    - Network latency spikes (very common)
    - Packet loss and corruption
    - Disk full errors
    - Clock drift
    - DNS resolution failures
    - Dependency slowness / timeouts
    - Resource exhaustion (CPU, memory, file descriptors)
    - Malformed inputs (traffic replay attacks)

PRINCIPLE 3: RUN EXPERIMENTS IN PRODUCTION
  Staging environments don't reflect production:
    - Traffic patterns differ
    - Data volume differs
    - Caching behavior differs
    - Third-party integrations behave differently
  
  Counter-intuitive: Running chaos in production is safer than finding
  weaknesses during an unplanned production incident
  
  START SMALL: Begin with least critical service, small blast radius
  GRADUALLY EXPAND to more critical services as confidence grows

PRINCIPLE 4: AUTOMATE EXPERIMENTS TO RUN CONTINUOUSLY
  Manual chaos experiments: Run quarterly/monthly
  Continuous automated chaos: Runs constantly in background
  Netflix: Chaos Monkey runs daily in production
  
  This reveals failures introduced by new code, configuration changes,
  scaling changes — not just point-in-time weaknesses

PRINCIPLE 5: MINIMIZE BLAST RADIUS
  Limit the scope of failure injection:
    - Target 1% of traffic, not 100%
    - Target non-critical services first
    - Have an automated "abort" if metrics deviate too far
    - Run during business hours when team is available
  
  Progressive chaos:
    Week 1: Kill 1 of 10 instances (10% blast radius)
    Week 2: Kill 1 of 5 instances (20%)
    Week 3: Simulate AZ failure
    Month 2: Simulate regional failure


4. THE CHAOS ENGINEERING PROCESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1: DEFINE STEADY STATE
  What metrics define "the system is healthy"?
  
  Example for an order service:
    - Order creation success rate > 99.9%
    - p99 order creation latency < 500ms
    - No increase in error log rate
    - Database connection pool utilization < 80%

STEP 2: FORM HYPOTHESIS
  "We believe that [steady state] will continue [if we inject failure X]"
  
  Example: "We believe that order creation success rate remains > 99.9%
            when one of three order-service replicas is terminated"

STEP 3: DESIGN EXPERIMENT
  Choose the failure mode:
    - Kill a process / container
    - Introduce 100ms network latency to DB connections
    - Fill disk to 95%
    - Exhaust CPU with competing process
    - Block DNS resolution for external dependency
  
  Choose scope (blast radius):
    - Which instances? (% of traffic)
    - Duration of experiment (5 minutes)
    - Abort conditions (if success rate drops below 95%, abort immediately)

STEP 4: RUN EXPERIMENT
  Monitor dashboards during execution
  Automated abort if abort conditions triggered
  Team on standby to respond

STEP 5: ANALYZE AND FIX
  Did steady state hold? → Confidence gained
  Did steady state break? → Found a weakness! Fix it.
  
  Common fixes:
    - Add circuit breaker
    - Add health check / remove unhealthy instance faster
    - Improve graceful degradation
    - Fix resource leak
    - Improve timeout configuration

STEP 6: EXPAND
  Start narrow → expand scope → increase severity


5. CHAOS EXPERIMENTS CATALOG
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

INFRASTRUCTURE FAILURES:
  Kill a service instance / pod
  Kill 50% of instances simultaneously
  Kill an entire Availability Zone
  Simulate a region outage
  Reboot a database primary node

NETWORK FAILURES:
  Add 100ms latency to specific service calls
  Add 1% packet loss
  Block all network from service A to service B (partition)
  Saturate network bandwidth (90% utilization)
  DNS failures (return NXDOMAIN for a dependency)

RESOURCE EXHAUSTION:
  Fill disk to 100%
  Consume 90% of available memory (memory pressure)
  Max out CPU with competing process
  Exhaust thread pool / connection pool
  Open thousands of file descriptors

DATA / APPLICATION:
  Corrupt a database record
  Expire all cache keys simultaneously (cache stampede)
  Inject malformed responses from a dependency
  Inject clock drift (NTP manipulation)
  Replay traffic from a previous time period

DEPLOYMENT-RELATED:
  Deploy a version with intentional slowness
  Deploy a config change that increases error rate
  Drain traffic from one AZ during peak hours


6. GAME DAYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
  A scheduled rehearsal where the team intentionally breaks the system
  and practices their incident response
  
  Named after military "field exercises" (game days)

FORMAT:
  Duration: 4-8 hours
  Team: On-call engineers, SREs, service owners
  Facilitator: Chaos team / SRE lead
  
  Schedule:
    9:00 AM: Briefing — objectives, safety procedures, abort conditions
    9:30 AM: Start monitoring dashboards, establish baseline
   10:00 AM: Inject first failure scenario
   10:30 AM: Analyze results, debrief
   11:00 AM: Inject second scenario
   12:00 PM: Lunch break
    1:00 PM: More complex scenario (multi-failure)
    3:00 PM: Final debrief — what worked, what didn't, action items

SCENARIOS (typical game day):
  Scenario 1: Kill payment service replica
    Expected: Kubernetes restarts, no user impact
    Test: Does readiness probe work? Does LB route away during restart?
  
  Scenario 2: Simulate DB slowness (add 500ms latency)
    Expected: Circuit breaker opens, fallback activates
    Test: Do timeouts fire? Does circuit breaker trip?
  
  Scenario 3: Kill entire AZ
    Expected: Traffic fails over to surviving AZ within 30 seconds
    Test: Does Route 53 health check remove AZ? Does LB balance correctly?

OUTCOMES FROM GAME DAYS:
  Incomplete runbooks (engineers can't find DR procedures)
  Missing monitoring / alerts (team doesn't notice failures quickly)
  Misconfigured circuit breakers (not protecting the right services)
  Single-point-of-failure discovered (only one DNS resolver configured)
  Alert fatigue (too many low-value alerts drowned out critical one)


7. CHAOS ENGINEERING TOOLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NETFLIX CHAOS MONKEY (open source):
  Language: Spinnaker plugin
  Target: EC2 instances
  Usage: Randomly terminates instances during business hours
  GitHub: Netflix/chaosmonkey

GREMLIN (SaaS):
  Commercial chaos engineering platform
  Supports: CPU, memory, disk, network, process attacks
  Features: Templates, scheduling, reporting, rollback
  Integration: Kubernetes, AWS, GCP, Azure, bare metal

CHAOS TOOLKIT (open source):
  Python-based framework for defining chaos experiments
  Declarative JSON/YAML experiment definitions
  Extensive integrations (AWS, GCP, k8s, Spring, Slack)
  
  Example experiment.json:
  {
    "title": "Can we survive a DB replica failure?",
    "description": "Kill one DB replica and verify availability",
    "steady-state-hypothesis": {
      "title": "System is healthy",
      "probes": [{
        "name": "success-rate",
        "type": "probe",
        "provider": {
          "type": "http",
          "url": "http://metrics.internal/success_rate",
          "expected_status": 200
        }
      }]
    },
    "method": [{
      "type": "action",
      "name": "kill-db-replica",
      "provider": {
        "type": "process",
        "path": "kubectl",
        "arguments": ["delete", "pod", "db-replica-2"]
      }
    }]
  }

LITMUS CHAOS (Kubernetes-native open source):
  Cloud-native chaos experiments for Kubernetes
  ChaosExperiment CRDs
  Hub with pre-built experiments
  Integrates with Argo Workflows

AWS FAULT INJECTION SIMULATOR (FIS):
  Native AWS chaos engineering service
  Targets: EC2, ECS, EKS, RDS, AZ
  Pre-built fault actions
  IAM-controlled — respects AWS permissions model

CHAOS MESH (CNCF project):
  Kubernetes-native chaos engineering platform
  Network chaos, pod kill, stress testing, time manipulation
  Dashboard for visualizing experiments


8. WHEN TO START CHAOS ENGINEERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PREREQUISITES:
  - Basic monitoring and alerting in place (if you can't detect failures, chaos is useless)
  - On-call rotation with incident response procedures
  - Basic redundancy (otherwise chaos will just cause an outage)
  - Deployment pipeline that can quickly revert bad changes

STARTING POINT:
  Begin in staging/pre-production environment
  Start with the simplest experiment: kill a single instance
  Verify that Kubernetes/auto-scaling replaces it correctly
  Verify monitoring detects the failure and alerts

MATURITY LEVELS:
  Level 1: Kill individual instances in pre-production
  Level 2: Kill instances in production (Chaos Monkey)
  Level 3: Network failure injection (latency, packet loss)
  Level 4: AZ-level failure injection
  Level 5: Regional failure injection (Chaos Kong)
  Level 6: Continuous automated chaos + game days

INTERVIEW ANSWER — "What is chaos engineering and why does Netflix use it?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Chaos engineering is the practice of deliberately injecting failures
into production systems to find weaknesses before they cause incidents.

Netflix started with Chaos Monkey, which randomly kills EC2 instances
during business hours. The idea: if AWS can kill your instance at any time,
you better design your system to handle that — or discover the failure
during a Netflix workday instead of at 3am.

The key principle is scientific: define 'steady state' as measurable
metrics (success rate > 99.9%), form a hypothesis ('we'll survive a
replica failure'), inject the failure, and measure whether steady state
holds. If it breaks, you found a real weakness to fix.

The counterintuitive insight: deliberately breaking things in production
(with a prepared team, during business hours, with small blast radius)
is SAFER than discovering the same weakness during an unplanned incident.

I'd start any team with a simple game day: kill one instance, verify
Kubernetes replaces it, verify monitoring detects the brief spike. Then
progressively expand to network failures, AZ failures, and multi-service
scenarios."
