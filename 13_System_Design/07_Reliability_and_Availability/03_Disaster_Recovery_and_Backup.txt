DISASTER RECOVERY AND BACKUP — COMPLETE GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. RPO AND RTO — THE TWO KEY METRICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RPO — RECOVERY POINT OBJECTIVE
  Definition: Maximum acceptable amount of data loss measured in time
  Question: "If a disaster happens right now, how much data can we afford to lose?"
  Unit: Time (seconds, minutes, hours)
  
  Examples:
    RPO = 0: Zero data loss — synchronous replication required
    RPO = 1 minute: Can tolerate losing up to 1 minute of data
    RPO = 24 hours: Daily backup is acceptable
  
  Determines BACKUP FREQUENCY:
    If RPO = 1 hour, you must backup at least every hour
    If RPO = 0, you need synchronous replication (not backups)

RTO — RECOVERY TIME OBJECTIVE
  Definition: Maximum acceptable time to restore the system after a disaster
  Question: "How long can the business tolerate the system being down?"
  Unit: Time (seconds, minutes, hours, days)
  
  Examples:
    RTO = 1 minute: Automatic failover required
    RTO = 4 hours: On-call engineer can manually restore
    RTO = 24 hours: Full restore from backup acceptable

RELATIONSHIP BETWEEN RPO AND RTO:
  Tighter = More Expensive

  ┌──────────────────────────────────────────────────────────┐
  │ Loose RPO / Loose RTO  ←————————→  Tight RPO / Tight RTO│
  │ Cheap                                          Expensive │
  │ Daily backup            Pilot Light    Active-Active      │
  │ Recovery: 24h           Recovery: 2h   Recovery: seconds  │
  └──────────────────────────────────────────────────────────┘

EXAMPLES BY BUSINESS TYPE:
  ┌──────────────────────┬──────────┬──────────┬────────────────────┐
  │ System               │ RPO      │ RTO      │ Approach           │
  ├──────────────────────┼──────────┼──────────┼────────────────────┤
  │ Banking core ledger  │ 0        │ < 1 min  │ Active-Active sync │
  │ E-commerce orders    │ 1 min    │ 5 min    │ Sync replication   │
  │ SaaS user data       │ 1 hour   │ 4 hours  │ Hourly backups     │
  │ Analytics warehouse  │ 24 hours │ 24 hours │ Daily snapshots    │
  │ Dev/test environment │ 1 week   │ 1 week   │ Weekly backup      │
  └──────────────────────┴──────────┴──────────┴────────────────────┘


2. BACKUP TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FULL BACKUP:
  What: Complete copy of all data
  Pros: Fast recovery — restore single file
  Cons: Slow to take, large storage, can only run infrequently
  Frequency: Weekly or monthly
  Recovery: Restore the single full backup

INCREMENTAL BACKUP:
  What: Only data that changed since the LAST BACKUP (full or incremental)
  Pros: Fast backup, low storage
  Cons: Slow recovery — need full + every incremental in sequence
  Frequency: Daily or hourly
  Recovery: Full backup + Mon incremental + Tue incremental + Wed incremental...
  Chain failure: If any incremental is corrupted, all later restores fail

DIFFERENTIAL BACKUP:
  What: All data changed since the LAST FULL BACKUP
  Pros: Faster recovery than incremental (only need full + latest diff)
  Cons: Gets larger over time (accumulates all changes since last full)
  Frequency: Daily
  Recovery: Full backup + latest differential
  Middle ground: Between full and incremental

COMPARISON:
  ┌──────────────┬─────────────────┬─────────────────┬──────────────────┐
  │ Type         │ Backup Speed    │ Storage Used    │ Recovery Speed   │
  ├──────────────┼─────────────────┼─────────────────┼──────────────────┤
  │ Full         │ Slow            │ High            │ Fast             │
  │ Incremental  │ Fast            │ Low             │ Slow             │
  │ Differential │ Medium          │ Medium (grows)  │ Medium           │
  └──────────────┴─────────────────┴─────────────────┴──────────────────┘

TYPICAL STRATEGY: Full + Incremental
  Sunday: Full backup
  Mon-Sat: Incremental backups
  Recovery: Last Sunday full + each day's incremental up to failure point


3. THE 3-2-1 BACKUP RULE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RULE: 3 copies of data, on 2 different media types, with 1 offsite copy

3 COPIES:
  - Original data (production database)
  - First backup (local NAS or another DB replica)
  - Second backup (cloud storage)
  Reason: One backup might fail. Two backups means one failure is tolerable.

2 MEDIA TYPES:
  - e.g., local disk + cloud object storage
  - e.g., SSD + magnetic tape (for archival)
  Reason: Prevents media-type failure (e.g., all SSDs fail due to same firmware bug)

1 OFFSITE:
  - At least one copy in a different physical location
  - Cloud storage (S3, GCS) is the most common offsite
  Reason: Protects against physical disasters (fire, flood, theft)

MODERN EXTENSION — 3-2-1-1-0:
  3 copies, 2 media, 1 offsite, 1 immutable copy, 0 errors verified
  The immutable copy prevents ransomware from encrypting backups
  S3 Object Lock (WORM: Write Once Read Many) is the typical implementation


4. DATABASE BACKUP STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LOGICAL BACKUPS (PostgreSQL: pg_dump, MySQL: mysqldump):
  What: Export data as SQL INSERT statements or binary dump
  Pros: Database-agnostic, can restore to different version, portable
  Cons: Slow for large databases, requires service restart for consistent dump
  Recovery time: Hours for large databases (re-insert all rows)
  Use for: Small databases, migration, point-in-time schemas
  
  Command: pg_dump -Fc mydb > backup.dump
  Restore: pg_restore -d mydb backup.dump

PHYSICAL BACKUPS (file-level copies):
  What: Copy actual database files (data directory)
  Pros: Fast backup and restore, handles any DB size
  Cons: Must be consistent (DB must be stopped OR use hot backup tools)
  Tools: pg_basebackup, Percona XtraBackup (MySQL hot backup)
  
  pg_basebackup: Consistent online backup of PostgreSQL data directory

WAL SHIPPING / CONTINUOUS ARCHIVING (PostgreSQL WAL, MySQL binlog):
  What: Stream Write-Ahead Log to backup storage continuously
  Enables: Point-in-time recovery (PITR) — restore to any second in history
  How:
    1. Take base backup (pg_basebackup)
    2. Continuously archive WAL files to S3
    3. To restore to time T: restore base backup + replay WAL up to T
  RPO: Seconds (WAL archived continuously)
  RTO: Time to restore base + replay WAL (proportional to WAL size)
  
  PostgreSQL configuration:
    archive_mode = on
    archive_command = 's3cmd put %p s3://backups/wal/%f'
    wal_level = replica

SNAPSHOT BACKUPS (EBS snapshots, RDS automated backups):
  What: Block-level snapshot of storage volume
  AWS EBS:
    - Incremental snapshots (only changed blocks)
    - RPO: 1 hour (if running hourly snapshots)
    - RTO: 5-30 minutes (attach volume to new instance)
    - Stored in S3 (durability: 11 nines)
  
  AWS RDS Automated Backups:
    - Daily snapshot + continuous transaction log backup
    - Retention: 0-35 days
    - PITR: Restore to any second within retention window
    - RPO: ~5 minutes (latest restorable time)
    - RTO: 30-60 minutes (new RDS instance creation)
    - Cross-region copy available

REDIS / CACHE BACKUP:
  RDB: Periodic snapshots (fork + write to disk) — compact, fast restore
  AOF: Append-only file — logs every write operation, configurable fsync
  Both: Use RDB for backups + AOF for crash recovery
  
  AWS ElastiCache: Automatic backups to S3


5. DISASTER RECOVERY STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TIER 1: BACKUP AND RESTORE
  Description: Backup data to cheap storage; restore on a new system on failure
  RPO: Hours to days (depends on backup frequency)
  RTO: Hours to days (time to provision infrastructure + restore data)
  Cost: Very cheap (storage only; no running standby)
  
  Setup:
    - Regular backups to S3 / Glacier
    - CloudFormation/Terraform templates stored (Infrastructure as Code)
    - Runbooks documented
  
  Use for: Dev/test, non-critical data, cost-constrained startups

TIER 2: PILOT LIGHT
  Description: Core infrastructure (just the DB tier) always running in DR region
               Other components started up on failover
  RPO: Minutes (async replication lag)
  RTO: 30-60 minutes (start application servers, update DNS)
  Cost: Low (pay only for minimal core services)
  
  "Pilot light" = a small flame kept alive, can ignite the larger system
  
  Setup:
    - DR region: DB replica running (receiving async replication)
    - DR region: AMIs / container images pre-built and ready
    - Failover: Launch app servers, update Route 53 DNS, promote DB replica

TIER 3: WARM STANDBY
  Description: Scaled-down version of full production stack always running in DR
  RPO: Minutes (async replication lag)
  RTO: Minutes (scale up the warm standby; DNS cutover)
  Cost: Medium (running 10-25% capacity in DR region)
  
  Setup:
    - DR region: Full application stack running at reduced capacity (1 of 3 servers)
    - Data replicated continuously to DR DB
    - On failover: Scale up DR (add more servers), update DNS
    - DNS TTL: 60 seconds (pre-set low for fast cutover)

TIER 4: HOT STANDBY / ACTIVE-ACTIVE
  Description: Full production stack in DR region; both regions serving traffic
  RPO: Near zero (seconds with sync replication; minutes with async)
  RTO: Seconds (just remove failed region from DNS rotation)
  Cost: High (double infrastructure)
  
  Setup:
    - Route 53 / Anycast: distribute traffic across both regions
    - Data replicated synchronously (Aurora Global Database)
    - On failover: DNS health check removes failed region automatically
    - Users redirected to surviving region within 30-60 seconds (DNS TTL)
  
  Used by: Netflix, Amazon, Google — mission-critical systems

COST VS RTO SPECTRUM:
  ┌─────────────────────────────────────────────────────────────┐
  │ Cost                                                        │
  │ ↑                                                           │
  │ █████  Active-Active (near-zero RTO, near-zero RPO)        │
  │ ████   Hot Standby                                          │
  │ ███    Warm Standby  (10-30 min RTO)                        │
  │ ██     Pilot Light   (30-60 min RTO)                        │
  │ █      Backup/Restore (hours RTO)                           │
  │ ──────────────────────────────→ RTO (Recovery Time)        │
  └─────────────────────────────────────────────────────────────┘


6. DR TESTING — CRITICAL OFTEN NEGLECTED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"A backup you've never tested is not a backup — it's hope."

TYPES OF DR TESTS:

1. TABLETOP EXERCISE:
   Walkthrough of DR procedures without actual execution
   Frequency: Quarterly
   Goal: Identify gaps in documentation and procedures

2. PARTIAL FAILOVER TEST:
   Restore a specific service or dataset in DR environment
   Validate data integrity, connectivity, performance
   Frequency: Monthly

3. FULL FAILOVER TEST (Game Day):
   Actually switch production traffic to DR region
   Netflix does this regularly with Chaos Engineering
   Frequency: Annually (or more for critical systems)

WHAT TO TEST:
  - Can you actually restore from backup? (Measure RTO)
  - Is the restored data correct? (Validate RPO)
  - Do applications work in DR environment?
  - Can you switch DNS within target RTO?
  - Can you communicate during an incident?

AUTOMATED BACKUP VALIDATION:
  - Daily restore test of backup to isolated environment
  - Run automated queries to check data integrity
  - Alert if backup validation fails
  - AWS Backup: supports cross-region restore and validation


7. RUNBOOK FOR DR FAILOVER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Example: Active-Passive Multi-Region (primary: us-east-1, DR: us-west-2)

DETECTION (0-5 minutes):
  [ ] CloudWatch alarm triggers (service down > 2 minutes)
  [ ] On-call engineer paged via PagerDuty
  [ ] Engineer confirms: "Is this a regional failure or service bug?"
  [ ] Escalate to incident commander

DECISION (5-10 minutes):
  [ ] Assess if service can recover without failover
  [ ] If regional outage: initiate DR failover
  [ ] Notify stakeholders (status page update)

FAILOVER EXECUTION (10-30 minutes):
  [ ] Promote DR replica to primary (DB)
      aws rds promote-read-replica --db-instance-id dr-replica
  [ ] Verify data integrity on new primary
  [ ] Scale up DR application servers to full capacity
  [ ] Update Route 53 DNS records to point to DR region
      (Pre-set TTL to 60 seconds for fast propagation)
  [ ] Verify health checks pass in DR region
  [ ] Test a real transaction

POST-FAILOVER (30-60 minutes):
  [ ] Monitor error rates and latency in DR region
  [ ] Status page update: "Service restored, operating in DR mode"
  [ ] Begin root cause analysis on primary region failure
  [ ] Plan fail-back procedure (when primary is healthy again)

FAIL-BACK (once primary is healthy):
  [ ] Restore primary region infrastructure
  [ ] Replicate data from DR back to primary
  [ ] Test primary region end-to-end
  [ ] Schedule maintenance window for DNS switchback
  [ ] Execute fail-back during low-traffic period

INTERVIEW ANSWER — "Walk me through a DR strategy"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I start by defining RPO and RTO based on business requirements —
these drive all architecture decisions.

For a payment system with RPO=0 and RTO=1 minute: I'd need
synchronous replication across regions and active-active deployment
with automatic DNS failover — expensive but necessary.

For user-generated content with RPO=5 minutes and RTO=30 minutes:
Warm standby in a second region with async replication is fine.
WAL shipping to S3 gives continuous archiving for PITR.

I follow the 3-2-1 rule for backups: three copies, two media types,
one offsite. For databases: base backup + continuous WAL shipping gives
point-in-time recovery to any second.

Most importantly: I test DR quarterly. An untested DR plan fails when
you need it most."
