================================================================
SERVICE DISCOVERY AND REGISTRY
================================================================

THE PROBLEM
------------
In a microservices architecture, services need to call each other.
But services run as dynamic containers — their IPs and ports change
constantly (auto-scaling, failures, redeployments).

You can't hardcode IPs in your code:
  ✗ productService.call("10.0.1.45:8080")  // hardcoded, breaks on redeploy

You need a way to dynamically discover where a service is running.

SERVICE REGISTRY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A service registry is a database of service instances and their locations.
  - Service starts → registers itself (IP, port, metadata).
  - Service stops → deregisters itself (or TTL expires).
  - Callers query the registry to find service instances.

INFORMATION STORED:
  Service name: "order-service"
  Instance ID:  "order-service-instance-3"
  Host:         "10.0.1.45"
  Port:         8080
  Health status: healthy/unhealthy
  Metadata:     zone=us-east-1a, version=2.3.1

POPULAR REGISTRIES:
  Netflix Eureka (Java, Spring Cloud)
  HashiCorp Consul (any language, DNS-based)
  Apache Zookeeper (general coordination service)
  AWS Cloud Map (managed, integrates with ECS/EKS)
  Kubernetes DNS (built-in for K8s environments)
  etcd (used internally by Kubernetes)

SERVICE DISCOVERY PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CLIENT-SIDE DISCOVERY:
   Client queries the registry directly.
   Client picks an instance (load balancing logic in client).
   Client calls the chosen instance.
   
   ServiceRegistry.getInstances("order-service")
   → [{host:10.0.1.45, port:8080}, {host:10.0.1.46, port:8080}]
   → client picks one (round-robin, random, least-connections)
   → client calls: http://10.0.1.45:8080/orders
   
   Pros:
   ✓ Simple, no additional hop
   ✓ Client controls load balancing algorithm
   
   Cons:
   ✗ Each client must implement discovery + load balancing logic
   ✗ Every language/platform needs a registry client library
   ✗ Registry coupling in application code
   
   Examples: Netflix Ribbon (deprecated), Spring Cloud LoadBalancer with Eureka

2. SERVER-SIDE DISCOVERY:
   Client calls a load balancer (no registry knowledge in client).
   Load balancer queries registry, routes request to a service instance.
   
   Client → Load Balancer → Registry → Instance
   
   Client only knows the load balancer's address (static).
   Load balancer handles discovery and routing.
   
   Pros:
   ✓ Client is simple (no registry knowledge)
   ✓ Works for any client language
   ✓ Centralized load balancing logic
   
   Cons:
   ✗ Extra network hop (client → LB → service)
   ✗ Load balancer can be a bottleneck/SPOF (need HA LB)
   
   Examples: AWS ALB with ECS service discovery, Kubernetes Services, Istio

SERVICE REGISTRATION PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SELF-REGISTRATION:
  Service registers itself on startup, deregisters on shutdown.
  Service sends heartbeats to maintain registration.
  
  Application code:
  @PostConstruct
  void registerService() {
    registry.register(ServiceInfo.of("order-service", getIP(), 8080));
  }
  
  @PreDestroy
  void deregisterService() {
    registry.deregister(instanceId);
  }
  
  Pros: Service owns its registration.
  Cons: Registration logic in every service (coupling).

THIRD-PARTY REGISTRATION:
  An external registrar watches for service instances (via orchestration platform).
  Registers/deregisters on behalf of services.
  Service has no registry code.
  
  Examples:
  - Kubernetes: Pod starts → K8s automatically updates Service endpoints.
  - Netflix Prana: sidecar process that handles registration.
  - Consul agent: sidecar that registers the main process.
  
  Pros: Services don't need registry code.
  Cons: Requires additional component (registrar or sidecar).

KUBERNETES SERVICE DISCOVERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kubernetes has built-in service discovery via DNS.

Services have stable DNS names:
  <service-name>.<namespace>.svc.cluster.local
  
  Example: order-service.default.svc.cluster.local

Client calls: http://order-service/orders
Kubernetes DNS resolves to the ClusterIP of the Service.
kube-proxy routes to one of the healthy pod IPs (load balances).

Services are an abstraction over pods:
  Service selector: app=order-service
  Service watches pods with that label.
  Endpoints: list of healthy pod IPs:ports for that service.
  kube-proxy updates iptables/IPVS rules to route to current pods.

No client-side registry code needed in Kubernetes.
Just use the service name as the hostname.

SERVICE MESH (Istio, Linkerd)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Service mesh adds a sidecar proxy to every service instance.
All network communication goes through the sidecar.

Sidecar (Envoy proxy) handles:
  - Service discovery (maintains routing table)
  - Load balancing
  - Circuit breaking
  - TLS encryption (mTLS)
  - Retries and timeouts
  - Traffic shaping (canary deployments, A/B testing)
  - Observability (metrics, tracing)

Control plane (Istiod) manages:
  - Service registry (which instances are healthy)
  - Policy configuration
  - Certificate authority for mTLS

Benefits:
  ✓ No service discovery / circuit breaking code in applications
  ✓ Consistent behavior across all services
  ✓ Works with any language/framework
  ✓ Centralized observability

Cons:
  ✗ Additional latency (~1ms per hop through sidecar)
  ✗ Operational complexity (another system to manage)
  ✗ Resource overhead (sidecar per pod)

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"In microservices, service discovery allows services to find each
 other dynamically as instances scale up/down. In Kubernetes
 (which I'd use for orchestration), this is built-in: each service
 gets a stable DNS name that load-balances across healthy pods.
 
 For more complex needs, a service mesh like Istio provides sidecar
 proxies that handle discovery, load balancing, circuit breaking, and
 mTLS — all without application code changes.
 
 For non-Kubernetes environments, I'd use Consul (HashiCorp) with
 server-side discovery: services register with Consul; an Envoy
 sidecar handles routing based on Consul's service registry."
