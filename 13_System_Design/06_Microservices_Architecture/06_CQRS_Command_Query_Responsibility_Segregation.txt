================================================================
CQRS — COMMAND QUERY RESPONSIBILITY SEGREGATION
================================================================

WHAT IS CQRS?
--------------
CQRS separates the READ model (queries) from the WRITE model (commands).
Commands change state. Queries read state. They use DIFFERENT models.

TRADITIONAL (CRUD) APPROACH:
  One unified model for reads and writes.
  Same database table serves both SELECT and INSERT/UPDATE/DELETE.
  Same object model (e.g., Order entity) used for both.

CQRS APPROACH:
  Commands: Change state. Validation, business rules. Optimized for writes.
  Queries: Read state. Return DTOs/views. Optimized for reads.
  Separate models, potentially separate databases.

WHY CQRS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM 1 — READS AND WRITES HAVE DIFFERENT NEEDS:
  Writes: Complex business logic, validations, transactions.
          Usually touch one or few rows at a time.
  Reads: Often need joins across many tables.
         Return denormalized views (all info for a screen).
         Should be fast, no locking.
  
  A normalized schema (good for writes) makes reads complex.
  A denormalized schema (good for reads) makes writes complex.
  CQRS solves this by using BOTH.

PROBLEM 2 — SCALE MISMATCH:
  Most applications: 10x more reads than writes.
  CQRS lets you scale reads and writes independently.
  Read store: many replicas, CDN-cached, eventually consistent.
  Write store: single primary, strongly consistent, fewer replicas.

PROBLEM 3 — COMPLEXITY OF DOMAIN MODEL:
  Rich domain models with validation and business rules are great for writes.
  But exposing them directly for reads is inefficient (load unnecessary data).
  CQRS: write side uses rich domain model; read side uses simple DTOs.

SIMPLE CQRS (Same DB)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Simplest form: separate command and query classes but same database.

CommandHandler (writes):
  PlaceOrderCommand:
    - Validate order (product exists, user has credit)
    - Apply business rules (max qty per user)
    - Write to order_items, orders table (normalized)
    - Publish OrderPlaced event

QueryHandler (reads):
  GetOrderDetailsQuery:
    - SELECT o.id, o.status, oi.product_name, oi.qty, p.price
      FROM orders o JOIN order_items oi JOIN products p ...
    - Returns a flat OrderDetailsDTO

Same DB, but clean separation in code.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FULL CQRS (Separate Read and Write Stores)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Write side: Normalized relational DB (PostgreSQL, MySQL).
            Strong consistency, ACID transactions.
            Optimized for writes.

Read side: Denormalized read store, optimized for queries.
           Could be: Elasticsearch (search), Redis (fast lookup),
           MongoDB (flexible documents), separate PostgreSQL read replica.

Synchronization: Write side publishes events → Read side updates its store.

Flow:
  1. Client sends PlaceOrderCommand
  2. Command handler writes to PostgreSQL (write store)
  3. Handler publishes OrderPlaced event to Kafka
  4. Read-side event handler receives OrderPlaced
  5. Updates Elasticsearch order_index with denormalized order data
  6. Client queries GetOrdersQuery → hits Elasticsearch (fast!)

EVENTUAL CONSISTENCY:
  Read store is updated asynchronously → slightly stale.
  Write completes → event published → read store updated within ~100ms.
  
  For the user who just placed an order: show optimistic update in UI.
  Or: add flag to route that user's queries to write DB for a short window.

CQRS + EVENT SOURCING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CQRS pairs naturally with Event Sourcing:

Write side: Stores events (not current state).
            When a command is processed, save an event.
            Current state = replay all events.

Read side (Projections): Subscribe to events, build read-optimized views.
  - OrderSummaryProjection: maintains order_summary table (id, status, total)
  - OrderTimelineProjection: maintains timeline view for order detail page
  - UserOrderHistoryProjection: all orders per user in Redis
  
  Multiple projections can consume the same events.
  New projections can be built by replaying history.

EVENT STORE → EVENTS → multiple PROJECTIONS (read models)

WHEN TO USE CQRS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use CQRS when:
  ✓ Read and write workloads are significantly different
  ✓ Complex domain with rich business rules for writes
  ✓ Read performance is critical (need denormalized views)
  ✓ Different scaling requirements for reads vs writes
  ✓ Using Event Sourcing

Avoid CQRS when:
  ✗ Simple CRUD application (over-engineering)
  ✗ Small team that can't maintain two models
  ✗ Strict consistency needed everywhere (eventual consistency not acceptable)
  ✗ No clear benefit: reads and writes have same shape

INTERVIEW ANSWER:
  "CQRS separates the read model from the write model. Commands go to
   a write handler that uses a rich domain model with business rules and
   writes to a normalized database. Queries go to a read handler that
   returns denormalized DTOs from an optimized read store (could be the
   same DB, a read replica, or Elasticsearch for complex queries).
   
   The main benefit is that reads and writes are optimized independently.
   I'd use full CQRS with separate stores when read and write patterns
   diverge significantly — e.g., a social feed where writes are simple
   but reads require fan-out across millions of users."
