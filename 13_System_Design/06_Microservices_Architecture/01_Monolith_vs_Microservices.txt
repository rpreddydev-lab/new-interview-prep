================================================================
MONOLITH vs MICROSERVICES
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
MONOLITH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All application code is deployed as a single unit.
Functions call each other directly (in-process calls).
Typically one database.

TYPES OF MONOLITHS:
  Modular Monolith: Well-structured with clear internal modules.
                    Each module has its own package/namespace.
                    Good step before microservices.
  
  Ball of Mud: No clear separation of concerns. Spaghetti code.
               Every part depends on every other part.
               (The anti-pattern to avoid)

STRENGTHS OF MONOLITH:
  ✓ Simple to develop initially (no distributed system complexity)
  ✓ Simple deployment (one artifact to deploy)
  ✓ Simple testing (test whole system together)
  ✓ No network overhead for in-process calls
  ✓ Easy cross-module transactions (single DB ACID transaction)
  ✓ Simple debugging (one log stream, no distributed tracing needed)
  ✓ No service discovery, API gateway needed

WEAKNESSES OF MONOLITH:
  ✗ Hard to scale individual components (must scale everything)
  ✗ Deployments require the whole application (large, slow, risky)
  ✗ Team scaling: all engineers work on same codebase → conflicts
  ✗ Technology lock-in: one language, one runtime for everything
  ✗ Fault isolation: one bug can crash the entire application
  ✗ As codebase grows: slow builds, slow tests, high cognitive load
  ✗ Difficult to adopt new technologies incrementally

WHEN MONOLITH IS RIGHT:
  ✓ Startup/early stage (domain not yet understood)
  ✓ Small team (< 5-8 engineers)
  ✓ Simple application with homogeneous scaling needs
  ✓ Tight consistency requirements throughout
  ✓ Limited operations/DevOps capacity

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
MICROSERVICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Application split into independently deployable services.
Each service is a separate process with its own database.

STRENGTHS OF MICROSERVICES:
  ✓ Independent deployment: teams deploy without coordination
  ✓ Independent scaling: scale only what needs scaling
  ✓ Technology freedom: each service can use best tool
  ✓ Fault isolation: one service failure doesn't cascade (with circuit breakers)
  ✓ Team independence: Conway's Law — architecture mirrors org structure
  ✓ Easier to understand each service in isolation (small codebase per service)

WEAKNESSES OF MICROSERVICES:
  ✗ Distributed systems complexity (partial failures, network issues)
  ✗ Operational overhead (many services to monitor, deploy, scale)
  ✗ Service discovery, API gateway, load balancers needed
  ✗ Distributed transactions are hard (Saga pattern needed)
  ✗ Data consistency is harder (eventual consistency)
  ✗ Higher latency for cross-service calls (network hops vs in-process)
  ✗ Testing is harder (need to test services in combination)
  ✗ Debugging: distributed tracing needed

CONWAY'S LAW:
  "Organizations design systems that mirror their own communication structure."
  If you have 3 teams (Frontend, Backend, DB), you'll build a 3-layer system.
  For microservices: organize teams around bounded contexts, not layers.
  "Team owns a service end-to-end: code, data, deployment, monitoring."
  Amazon's model: Two-pizza teams (6-10 people) own a service.

THE RECOMMENDED PATH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Start with a monolith (or modular monolith). Migrate to microservices
as you understand the domain and your team grows."

Martin Fowler's "Monolith First" pattern:
  1. Build a well-structured modular monolith.
  2. As team grows and bottlenecks appear, extract services.
  3. Use Strangler Fig pattern for gradual migration.

Signs it's time to extract a service:
  - This module has significantly different scaling requirements.
  - Multiple teams are fighting over this module.
  - This module needs a different technology (ML model, real-time).
  - This capability needs different deployment frequency.
  - This module is a system boundary (3rd party integration).

SERVICE DECOMPOSITION STRATEGIES:
  By Business Capability: Order service, Payment service, User service
  By Bounded Context (DDD): follow domain model boundaries
  By Subdomain: Core domain (differentiating), supporting, generic

ANTI-PATTERNS TO AVOID:
  Distributed Monolith: "Microservices" that are tightly coupled, deploy together.
                         Worst of both worlds.
  Too Fine-Grained: Nano-services (dozens of tiny services) → chaos.
                    Each service should do something meaningful.
  Shared Database: Multiple services sharing a database → coupling.
                   Database-per-service is required for true independence.
  Chatty Services: Service A makes 10 synchronous calls to Service B per request.
                   Latency compounds. Combine or use caching.

INTERVIEW ANSWER:
  "I'd start with a modular monolith for a new system, with clear
   internal boundaries corresponding to bounded contexts. As the team
   grows and scaling requirements diverge, I'd extract services using
   the Strangler Fig pattern — routing new traffic to a new service
   while the monolith handles legacy traffic, until the monolith is
   fully replaced.
   
   The key microservices principles I'd enforce: database-per-service,
   async communication via events for loose coupling, sync HTTP/gRPC
   only for real-time user-facing requests."
