================================================================
MICROSERVICES ARCHITECTURE — OVERVIEW
================================================================

WHAT ARE MICROSERVICES?
------------------------
Microservices is an architectural style where an application is built
as a suite of small, independently deployable services.
Each service:
  - Runs in its own process
  - Has its own database (database-per-service pattern)
  - Communicates over a well-defined API (HTTP/gRPC/events)
  - Is owned by a single team
  - Can be deployed independently

Contrast with MONOLITH: single deployable unit with all functionality.

CHARACTERISTICS OF GOOD MICROSERVICES:
  Single Responsibility: One service, one bounded context.
  Loose Coupling: Services interact only via published APIs.
  High Cohesion: All code in a service relates to one capability.
  Independently Deployable: No coordination needed with other teams.
  Isolated Failures: One service failing doesn't cascade to all.
  Technology Freedom: Each service can use different language/DB.

BOUNDED CONTEXT (Domain-Driven Design):
  A logical boundary within which a domain model is defined and applicable.
  A service should correspond to a bounded context.
  
  Example: E-commerce
  - Order Context: Order, LineItem, OrderStatus
  - Inventory Context: Product, Stock, Warehouse
  - Payment Context: Transaction, Refund, PaymentMethod
  - Notification Context: Notification, Template, Channel
  
  Each context has its own model. "Product" means different things:
  In Inventory: ProductId, SKU, stockCount, location
  In Payments: ProductId, price (not stock, not location)
  In Orders: ProductId, name, quantity, unitPrice
  
  Each service maintains its own model — no shared domain model.

COMMON PATTERNS:
  ┌─────────────────────────────────────────────────────┐
  │ Client → API Gateway → [Service A, Service B, ...]  │
  │                              ↕ events               │
  │                         Message Broker              │
  │                              ↕ events               │
  │              [Service C, Service D, ...]            │
  └─────────────────────────────────────────────────────┘

WHEN TO USE MICROSERVICES:
  ✓ Large team (10+ engineers) working on the same codebase
  ✓ Different parts of system have very different scaling requirements
  ✓ Need independent deployment frequency per domain
  ✓ Different components have different technology requirements
  ✓ High reliability requirements (isolate failures)

WHEN NOT TO USE MICROSERVICES:
  ✗ Small team (< 5-8 engineers) — overhead too high
  ✗ Early-stage startup — domain not well-understood yet
  ✗ Simple application — unnecessary complexity
  ✗ Strong consistency requirements everywhere — harder with services
