================================================================
API GATEWAY PATTERN
================================================================

WHAT IS AN API GATEWAY?
------------------------
An API Gateway is a single entry point for all clients to access
backend services. It acts as a reverse proxy that routes requests,
aggregates responses, and applies cross-cutting concerns.

Without API Gateway:
  Client → Service A directly
  Client → Service B directly  → Complex: clients know all service details
  Client → Service C directly

With API Gateway:
  Client → API Gateway → Service A
                       → Service B
                       → Service C  → Simple: clients know only the gateway

API GATEWAY RESPONSIBILITIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. ROUTING:
   Route /api/orders/* to Order Service.
   Route /api/users/* to User Service.
   Route /api/search/* to Search Service.

2. AUTHENTICATION & AUTHORIZATION:
   Validate JWT tokens before forwarding.
   If invalid → reject with 401.
   Pass user identity to downstream services.
   Services don't need to implement auth themselves.

3. RATE LIMITING:
   Limit requests per user, per IP, per API key.
   Prevents abuse and DDoS.

4. REQUEST AGGREGATION (Composition):
   One client request → gateway calls multiple services → aggregates results.
   Example: Homepage request → User + Feed + Recommendations → one response.
   Reduces client round-trips (especially on mobile networks).

5. PROTOCOL TRANSLATION:
   Client speaks REST → Gateway translates to gRPC for backend.
   Client sends HTTPS → Gateway sends HTTP internally.

6. LOAD BALANCING:
   Distribute requests across multiple service instances.

7. CACHING:
   Cache responses for common queries.
   Reduces load on backend services.

8. SSL TERMINATION:
   Handle HTTPS at the gateway.
   Internal communication can be plain HTTP.

9. REQUEST/RESPONSE TRANSFORMATION:
   Add headers, transform request format, sanitize inputs.
   Remove sensitive fields from responses.

10. OBSERVABILITY:
    Centralized logging, metrics, distributed tracing for all requests.

POPULAR API GATEWAYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NGINX: High-performance reverse proxy. Widely used.
       Configured via nginx.conf.

Kong: Open-source, plugin-based. Runs on NGINX.
      Plugins for auth, rate limiting, logging, etc.
      Control plane (DB) + data plane (proxy).

AWS API Gateway: Managed, integrates with Lambda, IAM, Cognito.
                 Great for serverless architectures.

Netflix Zuul / Spring Cloud Gateway: Java-based. Spring ecosystem.
                                      Netflix uses Zuul as edge gateway.

Istio Ingress Gateway: For Kubernetes, uses Envoy.
                       Traffic management at entry point.

Apigee (Google): Enterprise API management. 
                  Analytics, developer portal, monetization.

BACKEND FOR FRONTEND (BFF) PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM: Different clients have different needs.
  Mobile app: needs lightweight responses, conserve bandwidth.
  Desktop web: can handle richer data, different layout.
  3rd-party partner: needs specific API format.
  
  One generic gateway must serve all → compromises for every client.

SOLUTION: Dedicated gateway (BFF) per frontend type.

  Mobile App → Mobile BFF → Backend Services
  Web App → Web BFF → Backend Services
  Partner API → Partner BFF → Backend Services
  
  Each BFF:
  - Aggregates data specifically for that client's needs
  - Transforms responses to optimal format
  - Managed by the frontend team
  - Independent deployments per frontend

BENEFITS:
  ✓ Optimized per client (mobile gets lighter payload)
  ✓ Frontend teams own their BFF (no shared API bottleneck)
  ✓ Cleaner separation of concerns
  ✓ Independent iteration per frontend type

USED BY: Netflix (different BFFs for TV, mobile, web), Spotify, SoundCloud

API GATEWAY vs SERVICE MESH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌─────────────────────────┬─────────────────────┬──────────────────────┐
│ Feature                 │ API Gateway         │ Service Mesh         │
├─────────────────────────┼─────────────────────┼──────────────────────┤
│ Traffic type            │ North-South         │ East-West            │
│                         │ (external→internal) │ (service→service)    │
│ Where applied           │ Edge (entry point)  │ Every service-to-svc │
│ Authentication          │ Yes (client auth)   │ mTLS between services│
│ Rate limiting           │ Yes                 │ Not typical          │
│ Request aggregation     │ Yes                 │ No                   │
│ Service discovery       │ No                  │ Yes                  │
│ Circuit breaking        │ Limited             │ Yes                  │
│ Observability           │ Partial             │ Comprehensive        │
└─────────────────────────┴─────────────────────┴──────────────────────┘

Use BOTH: API Gateway for external traffic; service mesh for internal.

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"The API Gateway is the single entry point for all client traffic.
 It handles cross-cutting concerns: routing requests to services,
 authenticating JWT tokens, rate limiting, SSL termination, and
 request aggregation. This keeps individual services lean — they
 don't implement auth or rate limiting themselves.
 
 I'd use the BFF (Backend for Frontend) pattern for systems with
 diverse clients — a dedicated gateway per client type (mobile, web,
 partner API), each optimized for that client's needs.
 
 For a Kubernetes deployment, I'd use an Ingress Gateway (Nginx or
 Istio) for external traffic plus a service mesh (Istio) for internal
 service-to-service traffic with mTLS and circuit breaking."
