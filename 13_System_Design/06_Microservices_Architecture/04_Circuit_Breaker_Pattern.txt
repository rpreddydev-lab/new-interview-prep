================================================================
CIRCUIT BREAKER PATTERN
================================================================

THE PROBLEM: CASCADING FAILURES
---------------------------------
In a microservices architecture, Service A calls Service B.
If Service B is slow or failing:
  - A's requests to B pile up, waiting for timeout (30s default).
  - A's threads/connections are exhausted waiting for B.
  - A becomes slow or unresponsive.
  - Service C, which calls A, also starts failing.
  - The failure cascades through the entire system.

This is called a CASCADING FAILURE and it's one of the most common
causes of complete system outages in distributed systems.

CIRCUIT BREAKER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Inspired by electrical circuit breakers: trips when current is too high,
preventing fire and allowing the circuit to cool down.

The circuit breaker wraps calls to an external service.
It monitors failures and OPENS (blocks calls) when failures exceed threshold.

THREE STATES:

CLOSED (Normal operation):
  Requests flow through to the external service.
  Failures are counted.
  If failure rate > threshold → OPEN.

OPEN (Blocking):
  Requests are IMMEDIATELY REJECTED without calling the service.
  Returns fallback response (cached data, default, error).
  After a timeout (e.g., 30 seconds) → HALF-OPEN.

HALF-OPEN (Probing):
  A limited number of requests are allowed through (probe).
  If probes SUCCEED → back to CLOSED (service recovered).
  If probes FAIL → back to OPEN (service still unhealthy).

STATE TRANSITION:
  
  CLOSED ──(failure rate > 50%)──→ OPEN
    ↑                                 │
    │                         (after 30s timeout)
    │                                 ↓
    └───(probe succeeds)──── HALF-OPEN
                                      │
                              (probe fails)
                                      ↓
                                   OPEN

BENEFITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. FAST FAILURE:
   When circuit is open, requests fail immediately (microseconds).
   No waiting for timeout (30s). Much better user experience.

2. PREVENTS RESOURCE EXHAUSTION:
   Caller's thread pool/connections aren't held waiting for failing service.
   Resources freed immediately for other work.

3. ALLOWS RECOVERY:
   Failed service gets breathing room (no more traffic).
   Overloaded service can drain its queue and recover.
   
4. FAIL FAST + FALLBACK:
   Caller can implement fallback behavior (return cached data, degraded response).
   Better than hanging indefinitely.

CONFIGURATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Key configuration parameters:

failure_threshold:         Percentage of requests that must fail to open circuit.
                           Example: 50% failures in last 10 requests.

failure_count_threshold:   Minimum number of requests before evaluating rate.
                           Example: Must have at least 5 requests before circuit can open.
                           Prevents false opens on startup with few requests.

timeout_duration:          How long circuit stays OPEN before trying HALF-OPEN.
                           Example: 30 seconds.

probe_request_count:       How many requests to allow in HALF-OPEN state.
                           Example: 3 probe requests.

success_threshold:         How many consecutive probes must succeed to close.
                           Example: 3 successes → CLOSED.

FALLBACK STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When circuit is open, what do you return to the caller?

1. CACHED RESPONSE:
   Return last known good response.
   Use Redis or in-memory cache.
   Example: Product price service down → return last cached price.

2. DEFAULT VALUE:
   Return a safe default.
   Example: Recommendation service down → return top-10 popular items.

3. DEGRADED RESPONSE:
   Return a partial response (without the failing service's data).
   Example: Profile enrichment service down → return basic user profile.

4. QUEUE FOR LATER:
   Accept the request, queue it, process when service recovers.
   Example: Notification service down → queue email for later delivery.

5. ERROR (Explicit Failure):
   Return an error immediately.
   Use when there's no safe fallback.
   Example: Payment service down → return "payment unavailable" error.

RESILIENCE4J (Java, modern):
  CircuitBreaker breaker = CircuitBreaker.ofDefaults("paymentService");
  
  Supplier<PaymentResponse> sup = CircuitBreaker.decorateSupplier(
    breaker,
    () -> paymentClient.charge(request)
  );
  
  Try<PaymentResponse> result = Try.ofSupplier(sup)
    .recover(CallNotPermittedException.class, ex -> fallbackPayment());

HYSTRIX (Netflix, now legacy but widely referenced):
  @HystrixCommand(fallbackMethod = "getDefaultProducts")
  public List<Product> getProducts(String userId) {
      return productService.getProducts(userId);
  }
  
  private List<Product> getDefaultProducts(String userId) {
      return popularProductCache.getTopProducts();
  }

Service Mesh (Istio/Envoy):
  Circuit breaking configured at infrastructure level (YAML), not in code.
  Works for any language without code changes.
  
  outlierDetection:
    consecutiveGatewayErrors: 5
    interval: 30s
    baseEjectionTime: 30s
    maxEjectionPercent: 100

RELATED PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TIMEOUT:
  Don't wait forever. Set timeout on every external call.
  Typical: 100ms-2s for microservice calls, 5-30s for external APIs.
  Combine with circuit breaker: timeout → failure → circuit opens.

RETRY WITH EXPONENTIAL BACKOFF:
  Retry failed requests, but with increasing delays.
  Base delay: 100ms, then 200ms, 400ms, 800ms, 1600ms.
  Add jitter (randomness) to prevent retry storms.
  Only retry idempotent operations.
  
  DO NOT retry inside circuit breaker (retries amplify load on failing service).
  Retry at a higher level, outside the circuit breaker.

BULKHEAD (Resource Isolation):
  Separate thread pools / connection pools per external service.
  If Service B's thread pool is exhausted, Service C's pool is unaffected.
  Named after ship hull compartments (flooding one compartment doesn't sink ship).
  
  Example: Service A has:
    - Thread pool A (10 threads) for calls to Service B
    - Thread pool B (10 threads) for calls to Service C
  If B is slow, its pool is exhausted but C's pool is untouched.

INTERVIEW ANSWER:
  "The Circuit Breaker pattern prevents cascading failures in microservices.
   It wraps external calls with a state machine: CLOSED (normal), OPEN
   (blocking, fast fail), and HALF-OPEN (probing recovery). When a service
   fails, the circuit opens and returns fallback responses immediately
   instead of waiting for timeout — preventing thread exhaustion.
   
   I'd combine it with: timeout (don't wait forever), retry with
   exponential backoff (for transient failures), and bulkhead (isolate
   thread pools per dependency). In production I'd use Resilience4J (Java)
   or configure it in the service mesh (Istio) for language-agnostic coverage."
