MICROSERVICES + KUBERNETES INTEGRATION — SPRING BOOT
================================================================================

WHY KUBERNETES FOR MICROSERVICES?
-----------------------------------
Kubernetes (K8s) is the de facto platform for running microservices in production.
It solves: deployment, scaling, self-healing, service discovery, config management,
secret management, and traffic routing — all the operational concerns of microservices.

This file focuses on the INTEGRATION POINTS between Spring Boot and Kubernetes:
health probes, resource configuration, ConfigMaps, Secrets, graceful shutdown,
and production-ready deployment manifests.

LIVENESS AND READINESS PROBES
================================

Critical for Kubernetes to manage Spring Boot services correctly.

LIVENESS PROBE:
  "Is this container alive (or should K8s restart it)?"
  If liveness fails → K8s restarts the container.
  Use: detect deadlocks, OOM states that don't crash the process.
  DO NOT: fail liveness for downstream dependency failures (DB down → don't restart app).

READINESS PROBE:
  "Is this container ready to receive traffic?"
  If readiness fails → K8s removes the pod from Service load balancer (no traffic).
  Use: detect that app is still starting, or temporarily overwhelmed.
  This is the right probe to fail when a downstream dependency is unavailable.

STARTUP PROBE:
  "Has the container finished starting up?"
  Replaces liveness during slow startup (prevents premature liveness restarts).
  Once startup succeeds → liveness takes over.

SPRING BOOT ACTUATOR — HEALTH ENDPOINTS:

  pom.xml:
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

  application.yml:
    management:
      endpoint:
        health:
          show-details: always
          probes:
            enabled: true      # Enables /actuator/health/liveness and /actuator/health/readiness
      health:
        livenessstate:
          enabled: true
        readinessstate:
          enabled: true
      endpoints:
        web:
          exposure:
            include: health,info,metrics,prometheus

  Endpoints exposed:
    /actuator/health/liveness   → {"status": "UP"} — for liveness probe
    /actuator/health/readiness  → {"status": "UP"} — for readiness probe

CUSTOM HEALTH INDICATORS:

  @Component
  public class KafkaHealthIndicator implements HealthIndicator {

    private final KafkaConsumerFactory<?, ?> consumerFactory;

    @Override
    public Health health() {
      try (var consumer = consumerFactory.createConsumer()) {
        consumer.listTopics(Duration.ofSeconds(2));
        return Health.up().withDetail("kafka", "reachable").build();
      } catch (Exception e) {
        // Kafka down → READINESS fails (stop traffic), but don't fail LIVENESS
        return Health.down()
            .withDetail("kafka", "unreachable")
            .withException(e)
            .build();
      }
    }
  }

  @Component
  public class DatabaseHealthIndicator implements HealthIndicator {
    // Spring Boot auto-configures DataSourceHealthIndicator if DataSource is present
    // Custom: check DB with lightweight query
  }

KUBERNETES DEPLOYMENT WITH PROBES:

  # deployment.yaml
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: order-service
    namespace: ecommerce
  spec:
    replicas: 3
    selector:
      matchLabels:
        app: order-service
    template:
      metadata:
        labels:
          app: order-service
          version: "1.5.0"
      spec:
        containers:
          - name: order-service
            image: my-registry/order-service:1.5.0
            ports:
              - containerPort: 8080
                name: http
              - containerPort: 8081
                name: management   # Separate management port

            # ── Resource Limits (MANDATORY in production) ──────────────────────
            resources:
              requests:
                cpu: "250m"       # 0.25 CPU cores (guaranteed)
                memory: "512Mi"   # 512MB RAM (guaranteed)
              limits:
                cpu: "1000m"      # 1 CPU core (max burst)
                memory: "1Gi"     # 1GB RAM (OOMKill if exceeded)

            # ── Startup Probe (prevents premature liveness restarts) ───────────
            startupProbe:
              httpGet:
                path: /actuator/health/liveness
                port: management
              failureThreshold: 30    # Allow up to 30 * 10s = 5 minutes for startup
              periodSeconds: 10

            # ── Liveness Probe ──────────────────────────────────────────────────
            livenessProbe:
              httpGet:
                path: /actuator/health/liveness
                port: management
              initialDelaySeconds: 0   # Startup probe handles delay
              periodSeconds: 10
              failureThreshold: 3
              timeoutSeconds: 3

            # ── Readiness Probe ─────────────────────────────────────────────────
            readinessProbe:
              httpGet:
                path: /actuator/health/readiness
                port: management
              initialDelaySeconds: 0
              periodSeconds: 5
              failureThreshold: 3
              timeoutSeconds: 3

CONFIGMAPS — EXTERNALIZING CONFIGURATION
==========================================

ConfigMaps store non-sensitive configuration (features, URLs, tuning params).

CREATE ConfigMap:
  # configmap.yaml
  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: order-service-config
    namespace: ecommerce
  data:
    APPLICATION_NAME: order-service
    LOG_LEVEL: INFO
    PAYMENT_SERVICE_URL: http://payment-service.ecommerce.svc.cluster.local
    KAFKA_BOOTSTRAP_SERVERS: kafka:9092
    FEATURE_EXPRESS_SHIPPING: "true"
    application.yaml: |            # Mount as a file (Spring will load it)
      spring:
        datasource:
          hikari:
            maximum-pool-size: 20
            minimum-idle: 5

CONSUME as environment variables:
  spec:
    containers:
      - name: order-service
        envFrom:
          - configMapRef:
              name: order-service-config   # Injects all keys as env vars
        env:
          - name: SPRING_PROFILES_ACTIVE
            valueFrom:
              configMapKeyRef:
                name: order-service-config
                key: SPRING_PROFILE

CONSUME as mounted file:
  spec:
    volumes:
      - name: config-volume
        configMap:
          name: order-service-config
    containers:
      - name: order-service
        volumeMounts:
          - name: config-volume
            mountPath: /config          # Spring Boot loads /config/application.yaml automatically
            readOnly: true

SPRING BOOT + CONFIGMAP (spring-cloud-kubernetes):
  <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-kubernetes-client-config</artifactId>
  </dependency>

  application.yml:
    spring:
      cloud:
        kubernetes:
          config:
            enabled: true
            name: order-service-config
            namespace: ecommerce

SECRETS — SENSITIVE CONFIGURATION
=====================================

Secrets store sensitive data: DB passwords, API keys, JWT signing keys.
K8s Secrets are base64-encoded (NOT encrypted by default — enable encryption at rest).

CREATE Secret:
  # secret.yaml — DO NOT commit to Git! Use sealed-secrets or Vault.
  apiVersion: v1
  kind: Secret
  metadata:
    name: order-service-secrets
    namespace: ecommerce
  type: Opaque
  data:
    DB_PASSWORD: cGFzc3dvcmQxMjM=          # base64 of "password123"
    JWT_SECRET_KEY: bXlzdXBlcnNlY3JldA==   # base64 of "mysupersecret"
    STRIPE_API_KEY: c2tfdGVzdF9hYmMxMjM=   # base64 of actual key

  # Or create via kubectl (values auto-base64 encoded):
  kubectl create secret generic order-service-secrets \
    --from-literal=DB_PASSWORD=password123 \
    --from-literal=JWT_SECRET_KEY=mysupersecret

CONSUME as environment variables:
  spec:
    containers:
      - name: order-service
        envFrom:
          - secretRef:
              name: order-service-secrets
        env:
          - name: SPRING_DATASOURCE_PASSWORD
            valueFrom:
              secretKeyRef:
                name: order-service-secrets
                key: DB_PASSWORD

SPRING BOOT property mapping:
  # SPRING_DATASOURCE_PASSWORD (env var) → spring.datasource.password (property)
  # Spring Boot automatically maps env var conventions to property names

PRODUCTION SECRET MANAGEMENT:
  Option 1: K8s Secrets (acceptable for non-regulated)
  Option 2: Sealed Secrets (encrypted in Git via kubeseal)
  Option 3: HashiCorp Vault + K8s Vault Agent (enterprise-grade)
  Option 4: AWS Secrets Manager with ExternalSecrets Operator
  Option 5: Azure Key Vault with CSI driver

VAULT INTEGRATION WITH SPRING BOOT:
  <dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-vault-config</artifactId>
  </dependency>

  bootstrap.yml:
    spring:
      cloud:
        vault:
          host: vault.ecommerce.svc.cluster.local
          port: 8200
          authentication: KUBERNETES     # Use K8s service account token
          kubernetes:
            role: order-service
          kv:
            enabled: true
            backend: secret
            application-name: order-service

GRACEFUL SHUTDOWN
==================

Critical for zero-downtime rolling deployments.
When K8s terminates a pod (rolling update), it sends SIGTERM.
Without graceful shutdown: in-flight requests are abruptly cut off → 5xx errors.

  application.yml:
    server:
      shutdown: graceful           # Wait for in-flight requests to complete
    spring:
      lifecycle:
        timeout-per-shutdown-phase: 30s   # Max wait before forcing shutdown

K8s configuration:
  spec:
    containers:
      - name: order-service
        lifecycle:
          preStop:
            exec:
              command: ["sleep", "5"]   # Wait for K8s to remove pod from LB
    terminationGracePeriodSeconds: 60   # K8s allows 60s before SIGKILL

ORDER OF EVENTS on rolling update:
  1. K8s sends SIGTERM to old pod
  2. PreStop hook runs (sleep 5) → wait for LB to stop routing
  3. Spring receives SIGTERM → sets readiness to DOWN → no new requests
  4. Spring waits for in-flight requests to complete (up to 30s)
  5. Spring shuts down
  6. K8s sends SIGKILL if process still alive after terminationGracePeriodSeconds

KAFKA CONSUMER GRACEFUL SHUTDOWN:
  @Bean
  public KafkaListenerEndpointRegistry endpointRegistry() {
    return new KafkaListenerEndpointRegistry();
  }

  // Spring handles this automatically with server.shutdown=graceful
  // Kafka listeners stop polling on shutdown, commit offsets for current batch

HORIZONTAL POD AUTOSCALING (HPA)
===================================

  apiVersion: autoscaling/v2
  kind: HorizontalPodAutoscaler
  metadata:
    name: order-service-hpa
    namespace: ecommerce
  spec:
    scaleTargetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: order-service
    minReplicas: 2
    maxReplicas: 20
    metrics:
      - type: Resource
        resource:
          name: cpu
          target:
            type: Utilization
            averageUtilization: 70     # Scale up when CPU > 70%
      - type: Resource
        resource:
          name: memory
          target:
            type: Utilization
            averageUtilization: 80
    behavior:
      scaleUp:
        stabilizationWindowSeconds: 60
        policies:
          - type: Pods
            value: 4
            periodSeconds: 60
      scaleDown:
        stabilizationWindowSeconds: 300    # Wait 5 min before scaling down

SPRING BOOT JVM OPTIMIZATION FOR CONTAINERS:

  JAVA_OPTS: >-
    -XX:+UseContainerSupport          # JVM respects container CPU/mem limits
    -XX:MaxRAMPercentage=75.0         # Use 75% of container memory for heap
    -XX:InitialRAMPercentage=50.0
    -XX:+UseG1GC                      # G1GC for latency-sensitive services
    -XX:MaxGCPauseMillis=200
    -Djava.security.egd=file:/dev/./urandom  # Faster SecureRandom in containers
    -Dspring.profiles.active=${SPRING_PROFILES_ACTIVE:production}

COMPLETE DEPLOYMENT MANIFEST
================================

  # order-service-deployment.yaml
  ---
  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: order-service-config
    namespace: ecommerce
  data:
    SPRING_PROFILES_ACTIVE: production
    KAFKA_BOOTSTRAP_SERVERS: kafka.ecommerce.svc.cluster.local:9092
    LOG_LEVEL: INFO
  ---
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: order-service
    namespace: ecommerce
    labels:
      app: order-service
  spec:
    replicas: 3
    strategy:
      type: RollingUpdate
      rollingUpdate:
        maxSurge: 1          # Allow 1 extra pod during update
        maxUnavailable: 0    # Never have fewer than desired replicas
    selector:
      matchLabels:
        app: order-service
    template:
      metadata:
        labels:
          app: order-service
        annotations:
          prometheus.io/scrape: "true"
          prometheus.io/path: /actuator/prometheus
          prometheus.io/port: "8081"
      spec:
        serviceAccountName: order-service-sa
        terminationGracePeriodSeconds: 60
        containers:
          - name: order-service
            image: my-registry/order-service:1.5.0
            imagePullPolicy: Always
            ports:
              - containerPort: 8080
                name: http
              - containerPort: 8081
                name: management
            envFrom:
              - configMapRef:
                  name: order-service-config
              - secretRef:
                  name: order-service-secrets
            env:
              - name: JAVA_OPTS
                value: "-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0 -XX:+UseG1GC"
              - name: POD_NAME          # Useful for logging correlation
                valueFrom:
                  fieldRef:
                    fieldPath: metadata.name
              - name: POD_NAMESPACE
                valueFrom:
                  fieldRef:
                    fieldPath: metadata.namespace
            resources:
              requests:
                cpu: "250m"
                memory: "512Mi"
              limits:
                cpu: "1000m"
                memory: "1Gi"
            startupProbe:
              httpGet:
                path: /actuator/health/liveness
                port: management
              failureThreshold: 30
              periodSeconds: 10
            livenessProbe:
              httpGet:
                path: /actuator/health/liveness
                port: management
              periodSeconds: 10
              failureThreshold: 3
            readinessProbe:
              httpGet:
                path: /actuator/health/readiness
                port: management
              periodSeconds: 5
              failureThreshold: 3
            lifecycle:
              preStop:
                exec:
                  command: ["sleep", "5"]
  ---
  apiVersion: v1
  kind: Service
  metadata:
    name: order-service
    namespace: ecommerce
  spec:
    selector:
      app: order-service
    ports:
      - name: http
        port: 80
        targetPort: 8080
      - name: management
        port: 8081
        targetPort: 8081
    type: ClusterIP

INTERVIEW QUESTIONS — MICROSERVICES + K8s
==========================================

Q: What is the difference between a liveness probe and readiness probe in K8s?
A: Liveness: "Is the app alive?" If it fails, K8s restarts the container. Use for
   detecting deadlocks or unrecoverable states. Don't fail liveness for dependency
   issues (DB down).
   Readiness: "Is the app ready to serve traffic?" If it fails, K8s removes the
   pod from the load balancer — no new traffic. Use for startup, overload, or
   when dependencies are unavailable. Liveness failures → restart; Readiness
   failures → traffic stop (no restart).

Q: How do you configure Spring Boot to expose liveness/readiness endpoints for K8s?
A: Set management.endpoint.health.probes.enabled=true and enable livenessstate and
   readinessstate health groups. Spring Boot automatically integrates with K8s
   liveness/readiness states. K8s probes hit /actuator/health/liveness and
   /actuator/health/readiness. Use a startup probe for slow-starting apps to
   prevent liveness restarting during startup.

Q: How do you implement graceful shutdown for a Spring Boot service in K8s?
A: Set server.shutdown=graceful and spring.lifecycle.timeout-per-shutdown-phase=30s.
   K8s sends SIGTERM on pod termination; Spring sets readiness to DOWN (stops
   accepting new traffic), waits for in-flight requests to complete, then shuts
   down. Add a preStop sleep(5) to wait for K8s to deregister the pod from the
   load balancer before Spring starts rejecting traffic.

Q: How do you manage secrets in Kubernetes for Spring Boot services?
A: K8s Secrets (base64-encoded) can be injected as env vars or mounted files.
   Spring Boot reads them via standard environment variables (spring.datasource.password
   → SPRING_DATASOURCE_PASSWORD). For production: use Sealed Secrets (encrypted in
   Git), HashiCorp Vault (spring-cloud-starter-vault-config with K8s auth), or
   cloud-native solutions like AWS Secrets Manager + External Secrets Operator.

Q: Why should you always set resource requests and limits for Spring Boot pods?
A: Without requests: K8s cannot schedule the pod correctly — it may be evicted when
   a node is under pressure. Without limits: a pod can consume all node resources,
   starving other pods. JVM (without -XX:+UseContainerSupport) ignores container
   limits and sees the full host memory → OOMKill. UseContainerSupport ensures
   the JVM respects container boundaries. MaxRAMPercentage controls heap size as
   a percentage of container memory.
