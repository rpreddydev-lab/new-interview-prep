================================================================================
THE TWELVE-FACTOR APP METHODOLOGY
================================================================================

OVERVIEW
--------
The Twelve-Factor App is a methodology for building software-as-a-service
applications that:
  - Use declarative formats for setup automation
  - Have a clean contract with the underlying OS
  - Are suitable for deployment on modern cloud platforms
  - Minimize divergence between development and production
  - Can scale up without significant changes to tooling or architecture

Originally documented by Adam Wiggins (Heroku) around 2011-2012.
Critical reading for anyone building microservices/cloud-native applications.

────────────────────────────────────────────────────────────────────────────────

THE 12 FACTORS
==============

FACTOR 1: CODEBASE
───────────────────
"One codebase tracked in version control, many deploys."

  - One repo per app/service (not one repo for all services together)
  - Multiple deploys from the same codebase: dev, staging, production
  - Multiple apps sharing the same code → extract to a shared library

  Violation: Two different services in the same repo that get deployed separately
  Violation: Code deployed to production that's not tracked in git

  Microservices angle:
    - Each microservice = its own git repository
    - One service, multiple environment deployments (dev/staging/prod)
    - Config differences handled in environment (Factor 3)

FACTOR 2: DEPENDENCIES
───────────────────────
"Explicitly declare and isolate dependencies."

  - All dependencies must be explicitly declared (pom.xml, package.json,
    requirements.txt, go.mod)
  - Never rely on system-wide packages ("it works on my machine")
  - Use dependency isolation: virtualenv (Python), node_modules, Maven local repo

  Example:
    BAD:  "We need ImageMagick installed on the server"
    GOOD: Include image processing as a library dependency

  Microservices angle:
    - Docker images bake in all dependencies → perfectly reproducible
    - Container = application + all its dependencies

FACTOR 3: CONFIG
─────────────────
"Store config in the environment."

  - Config = anything that varies between environments (dev, staging, prod)
    - Database URLs
    - External API keys
    - Feature flags
    - Port numbers
  - Store in environment variables, NOT in code
  - NEVER commit credentials to source control

  BAD:
    String dbUrl = "jdbc:postgresql://prod-db:5432/mydb";
    String apiKey = "sk-abc123";

  GOOD:
    String dbUrl = System.getenv("DATABASE_URL");
    String apiKey = System.getenv("PAYMENT_API_KEY");

  Microservices angle:
    - Kubernetes ConfigMaps for non-sensitive config
    - Kubernetes Secrets or Vault for sensitive config
    - Spring Cloud Config Server for centralized config management

FACTOR 4: BACKING SERVICES
────────────────────────────
"Treat backing services as attached resources."

  - Backing services: databases, queues, SMTP, caches
  - Treat them as attached resources, not integral components
  - Should be swappable by changing a URL/config, not code

  Example: Switching from MySQL to PostgreSQL should require only a config
           change, not a code rewrite.

  Backing services include:
    - PostgreSQL, MySQL, MongoDB (databases)
    - Redis, Memcached (caches)
    - RabbitMQ, Kafka (message queues)
    - S3, GCS (object storage)
    - SendGrid, Mailgun (email providers)

  Microservices angle:
    - Service A talks to its PostgreSQL DB via DATABASE_URL env var
    - In testing: DATABASE_URL points to a test DB
    - In production: DATABASE_URL points to production DB
    - No code change required

FACTOR 5: BUILD, RELEASE, RUN
──────────────────────────────
"Strictly separate build and run stages."

  Three stages:
    1. BUILD: Convert source code to executable artifact (JAR, Docker image)
    2. RELEASE: Combine build artifact with config for a target environment
    3. RUN: Execute the release in the execution environment

  Rules:
    - Cannot change code at runtime (immutable releases)
    - Every release gets a unique release ID (timestamp or version)
    - Rollback = deploy previous release ID

  Microservices / CI-CD angle:
    BUILD:   mvn package → target/app.jar  (or docker build → image)
    RELEASE: app.jar + env=production config → release-20240108
    RUN:     kubectl rollout deploy my-service (run the release)

FACTOR 6: PROCESSES
────────────────────
"Execute the app as one or more stateless processes."

  - Processes are STATELESS and share-nothing
  - Any data that needs to persist must be stored in a backing service (DB, cache)
  - Never rely on in-memory session state, local disk, or "sticky sessions"

  BAD: User session stored in memory of Service instance A
       → User's next request hits instance B → session lost
  GOOD: Store session in Redis, referenced by session ID in cookie

  Why this matters for scaling:
    - Stateless services can be horizontally scaled trivially
    - Load balancer can route any request to any instance
    - Instances can be killed/replaced at any time (cloud autoscaling)

  Microservices angle:
    - Kubernetes Pods are ephemeral — stateless processes are natural fit
    - Persistent state goes to databases, Redis, S3

FACTOR 7: PORT BINDING
───────────────────────
"Export services via port binding."

  - App is self-contained; it exports HTTP/gRPC by binding to a port
  - No dependency on runtime injection of a web server
  - The app IS the server (not deployed into a container like Tomcat separately)

  Example:
    - Spring Boot embeds Tomcat and listens on PORT=8080
    - Node.js: app.listen(process.env.PORT || 3000)
    - Go: http.ListenAndServe(":"+port, handler)

  Microservices angle:
    - Each microservice is self-contained, binds its own port
    - Kubernetes Service abstraction handles service-to-service routing
    - Docker/K8s maps container port to external port

FACTOR 8: CONCURRENCY
──────────────────────
"Scale out via the process model."

  - Scale by adding more processes (horizontal scaling), not bigger machines
  - Different workloads can be handled by different process types:
    - Web processes: handle HTTP requests
    - Worker processes: process background jobs/messages
    - Scheduler: run periodic tasks

  Process types example for an e-commerce app:
    web:     Handle HTTP API requests (8 instances)
    worker:  Process order emails from queue (4 instances)
    crawler: Scrape product prices (2 instances)
    cron:    Daily report generation (1 instance, scheduled)

  Microservices angle:
    - K8s Deployments for web processes
    - K8s Jobs for batch/scheduled tasks
    - HPA (HorizontalPodAutoscaler) for automatic scaling

FACTOR 9: DISPOSABILITY
─────────────────────────
"Maximize robustness with fast startup and graceful shutdown."

  - Processes start fast (< a few seconds) for easy scaling
  - Processes shut down gracefully on SIGTERM:
    - Stop accepting new requests
    - Finish in-flight requests
    - Return jobs to queue if processing fails

  Graceful Shutdown in Spring Boot:
    server.shutdown=graceful
    spring.lifecycle.timeout-per-shutdown-phase=20s

  Disposability enables:
    - Fast autoscaling (spin up new instances quickly)
    - Safe rolling deployments (kill old, start new gracefully)
    - Crash recovery (restart failed pods quickly)

  Microservices angle:
    - K8s terminationGracePeriodSeconds for shutdown window
    - Liveness/Readiness probes to control when traffic is routed

FACTOR 10: DEV/PROD PARITY
────────────────────────────
"Keep development, staging, and production as similar as possible."

  Three gaps to eliminate:
    1. Time gap: Don't let code sit for weeks before production deploy
    2. Personnel gap: Developers who write code should deploy and monitor it
    3. Tools gap: Same backing services in all environments
                  BAD: SQLite in dev, PostgreSQL in prod
                  GOOD: PostgreSQL everywhere (use Docker)

  Microservices angle:
    - Docker Compose for local dev environments with real services
    - Minikube/Kind for local K8s testing
    - Same Helm charts with different value files per environment

FACTOR 11: LOGS
────────────────
"Treat logs as event streams."

  - Apps should NOT manage log files
  - Write all logs to stdout (unbuffered)
  - Execution environment captures and routes log streams

  BAD:
    logger.setLogFile("/var/log/myapp.log");  // App manages its own logs

  GOOD:
    System.out.println(logMessage);           // Just write to stdout
    // or use a logger that writes to stdout by default

  Log aggregation handled externally:
    - Kubernetes: Logs captured from stdout by Fluentd/Fluent Bit
    - Shipped to: Elasticsearch, Splunk, CloudWatch, Datadog

  Microservices angle:
    - Structured logging (JSON) to stdout
    - Correlation IDs in logs for distributed tracing
    - ELK Stack, Loki+Grafana for log aggregation

FACTOR 12: ADMIN PROCESSES
────────────────────────────
"Run admin/management tasks as one-off processes."

  - Admin tasks (database migrations, one-time scripts, REPL) should run
    in an identical environment to regular processes
  - Run in the same codebase and configuration as the app

  Examples:
    - Database migrations: flyway:migrate
    - One-time data backfills
    - Django: manage.py migrate
    - Interactive REPL for debugging

  Microservices angle:
    - Kubernetes Jobs / Init Containers for migrations
    - Run migrations before deploying new pods
    - Never run migrations manually on production servers

QUICK SUMMARY TABLE
====================

Factor      │ Key Principle
────────────┼─────────────────────────────────────────────────────────────
1. Codebase │ One repo per service, many deploys
2. Deps     │ Explicit dependency declaration, isolation
3. Config   │ Config in env vars, never in code
4. Services │ Treat DBs/caches/queues as attached resources
5. Build    │ Strict build → release → run separation
6. Processes│ Stateless, share-nothing processes
7. Port     │ Self-contained, exports via port binding
8. Concur.  │ Scale via horizontal processes, not vertical
9. Disposal │ Fast start, graceful shutdown
10. Parity  │ Dev = Prod (same tools, same infra)
11. Logs    │ Stdout streams, not managed files
12. Admin   │ One-off admin tasks in same environment

EXTENSIONS: BEYOND 12 FACTORS
==============================

Later additions proposed by Kevin Hoffman ("Beyond the 12-Factor App", 2016):

13. API First — Design and document APIs before implementation
14. Telemetry — Expose health, metrics, tracing from every service
15. Auth & Security — Zero-trust between services, JWT/mTLS

INTERVIEW QUESTIONS
====================

Q: What is the 12-Factor App methodology?
A: A set of 12 best practices for building cloud-native, scalable, maintainable
   applications. Key ones: config in environment variables, stateless processes,
   treat backing services as attached resources, log to stdout, and maintain
   dev/prod parity.

Q: How does Factor 3 (Config) apply to microservices?
A: Never hardcode config or credentials. Use environment variables, injected
   via Kubernetes ConfigMaps and Secrets. For complex config, use a Config
   Server (Spring Cloud Config). This enables the same Docker image to run in
   dev, staging, and prod with different configurations.

Q: What does "stateless processes" (Factor 6) mean for scaling?
A: Stateless services can be horizontally scaled freely — any instance can
   handle any request. State lives in external stores (Redis, DB). This is
   why K8s can spin up 10 replicas of a service and any pod can serve any
   request.

Q: Why should logs go to stdout (Factor 11)?
A: It separates the concern of log generation (the app) from log routing
   and storage (the platform). The app doesn't care where logs go — Kubernetes
   and Fluentd handle collection and forwarding to ELK/Datadog. Simplifies
   the app and standardizes log handling.

Q: What is "dev/prod parity" and why does it matter?
A: Keeping development and production environments as similar as possible to
   prevent "works on my machine" problems. Use Docker to run the same database
   version locally. Deploy frequently (CI/CD) to minimize time gaps. Developers
   should deploy and own their services in production.
