SERVICE COMMUNICATION OVERVIEW
================================================================================

WHY COMMUNICATION MATTERS
--------------------------
In a microservices architecture, services must communicate to fulfill business
operations. Unlike a monolith where calls are in-process (nanoseconds), service
communication involves:
  - Network calls (milliseconds)
  - Serialization/deserialization
  - Failure modes (timeouts, connection refused, partial failures)
  - Protocol negotiation
  - Service discovery

The communication design is one of the most impactful architectural decisions
in a microservices system.

────────────────────────────────────────────────────────────────────────────────

COMMUNICATION DIMENSIONS
=========================

Dimension 1: SYNCHRONOUS vs ASYNCHRONOUS
  Synchronous:  Caller waits for a response before proceeding
  Asynchronous: Caller sends message and continues; response comes later (or not)

Dimension 2: POINT-TO-POINT vs PUBLISH/SUBSCRIBE
  P2P: One sender → One receiver (REST, gRPC, direct queue)
  Pub/Sub: One sender → Many receivers (Kafka topics, SNS)

Dimension 3: REQUEST/RESPONSE vs EVENT-DRIVEN
  Request/Response: Client sends request, expects a response (REST, gRPC)
  Event-Driven:     Service publishes event; others react (Kafka, RabbitMQ)

Dimension 4: PUSH vs PULL
  Push: Server pushes data to client (WebSockets, SSE, gRPC streaming)
  Pull: Client polls server for updates (polling, long-polling)

===============================

────────────────────────────────────────────────────────────────────────────────

SYNCHRONOUS COMMUNICATION
==========================

Definition: Caller sends a request and BLOCKS until it receives a response.

Flow:
  Service A ──────[Request]──────→ Service B
  Service A ←────[Response]────── Service B

Protocols:
  - REST (HTTP/1.1 + JSON/XML)
  - gRPC (HTTP/2 + Protobuf)
  - GraphQL (HTTP + JSON)
  - SOAP (HTTP + XML) — legacy

Advantages:
  ✓ Simple to understand (familiar request/response model)
  ✓ Immediate response → easy error handling
  ✓ Simple to debug and trace
  ✓ Works naturally with API contracts

Disadvantages:
  ✗ Temporal coupling — caller must be available when callee is available
  ✗ Cascading failures — if Service B is slow, Service A is slow too
  ✗ Hard to scale independently under load
  ✗ Tight dependency chains (Service A → B → C → D)

When to use:
  - Query operations that need immediate results
  - Simple CRUD operations
  - External-facing APIs
  - When user is waiting for a response

────────────────────────────────────────────────────────────────────────────────

ASYNCHRONOUS COMMUNICATION
===========================

Definition: Caller publishes a message and continues; the callee processes it
            independently (possibly much later).

Flow:
  Service A ──[Message]──→ [Broker] ──[Message]──→ Service B
  Service A continues work immediately.

Patterns:
  - Message Queue (RabbitMQ, SQS): One consumer processes each message
  - Pub/Sub (Kafka, SNS): Multiple consumers can receive the same message
  - Event Streaming: Ordered, replayable event log (Kafka)

Advantages:
  ✓ Temporal decoupling — publisher and consumer don't need to run simultaneously
  ✓ Services can scale independently
  ✓ Fault tolerance — broker holds messages if consumer is down
  ✓ Natural backpressure handling
  ✓ Enables Event Sourcing, CQRS patterns

Disadvantages:
  ✗ Eventual consistency — no immediate response to confirm success
  ✗ More complex error handling (dead letter queues, idempotency)
  ✗ Message ordering challenges (Kafka partitions help)
  ✗ Harder to debug and trace
  ✗ Duplicate message handling required

When to use:
  - Long-running operations
  - Fire-and-forget notifications
  - Fan-out to multiple services
  - Event-driven workflows
  - Decoupling services that don't need immediate responses

────────────────────────────────────────────────────────────────────────────────

CHOOSING BETWEEN SYNC AND ASYNC
=================================

Use Synchronous when:
  □ User is waiting for an immediate response
  □ Operation is fast and the called service is reliable
  □ You need strong consistency (immediate confirmation)
  □ Simple query operations

Use Asynchronous when:
  □ Operation is long-running (e.g., send email, process video)
  □ Multiple services need to react to the same event
  □ Need to decouple producers from consumers
  □ Need temporal decoupling (consumer may be temporarily down)
  □ Need to handle spikes (buffer load in queue)

HYBRID PATTERN (Async Request-Reply):
  1. Client sends request → service returns 202 Accepted + jobId
  2. Service processes asynchronously
  3. Client polls GET /jobs/{jobId} for status
  4. Or: Service pushes notification via WebSocket/Webhook when done

COMMUNICATION IN PRACTICE: ORDERING SERVICE EXAMPLE
======================================================

Order Placement:
  Customer → [API Gateway] → [OrderService]

  OrderService (synchronous calls):
    → [InventoryService]: Check stock (sync — need immediate answer)
    → [PricingService]: Get final price (sync — needed before order confirmation)

  OrderService (asynchronous events):
    → Publishes "OrderPlaced" event to Kafka

  Async consumers of "OrderPlaced":
    [PaymentService]: Process payment
    [NotificationService]: Send confirmation email
    [AnalyticsService]: Record sale
    [WarehouseService]: Start fulfillment

This hybrid approach: synchronous for immediate query data,
                      asynchronous for downstream workflows.

API DESIGN BEST PRACTICES
==========================

1. Define clear API contracts (OpenAPI/Swagger for REST, proto files for gRPC)
2. Version your APIs (v1, v2) to avoid breaking changes
3. Use standard HTTP status codes correctly
4. Implement idempotency for write operations (especially async)
5. Document error responses as well as success responses
6. Use pagination for collection endpoints
7. Apply proper authentication and authorization on every service

INTERVIEW QUESTIONS
====================

Q: How do microservices communicate with each other?
A: Via synchronous (REST, gRPC) or asynchronous (message brokers like Kafka,
   RabbitMQ) communication. Sync is used when immediate response is needed;
   async is used for decoupling, long-running operations, and fan-out events.

Q: When would you choose async over sync communication?
A: When the operation is long-running, multiple services need to react,
   or you need temporal decoupling. Example: "Order placed" event published
   to Kafka → Payment, Notification, Warehouse all react independently.

Q: What's temporal coupling and why does it matter?
A: Temporal coupling means both services must be running simultaneously for
   communication to succeed. With async messaging, if the consumer is down,
   the message is held in the broker. With sync REST calls, the consumer
   must be up — creating brittleness.

Q: What protocols are used in microservices communication?
A: REST (HTTP + JSON) for external and simple internal APIs, gRPC for
   high-performance internal service calls, Kafka for event streaming and
   async messaging, RabbitMQ for task queues.
