GENERICS AND INHERITANCE
==========================

COVARIANCE, CONTRAVARIANCE, AND INVARIANCE
-------------------------------------------
  These terms describe how subtyping relationships carry over to parameterized types.

  COVARIANT: If A is a subtype of B, then Type<A> is also a subtype of Type<B>
  CONTRAVARIANT: If A is a subtype of B, then Type<B> is a subtype of Type<A>
  INVARIANT: Neither — no subtype relationship between Type<A> and Type<B>

  Arrays in Java are COVARIANT:
    String[] is a subtype of Object[]  (String IS-A Object)
    Object[] arr = new String[3];      // ✅ compiles
    arr[0] = 42;                       // ❌ ArrayStoreException at RUNTIME

  Generic types in Java are INVARIANT:
    List<String> is NOT a subtype of List<Object>
    List<Object> list = new ArrayList<String>(); // ❌ compile error
    // This is intentional — prevents the array-store problem at compile time

  WHY INVARIANT?
    If List<String> were assignable to List<Object>:
      List<Object> obj = new ArrayList<String>();
      obj.add(42);           // would insert Integer into List<String>!
      String s = ((List<String>) obj).get(0); // ClassCastException — runtime disaster

  WILDCARDS ADD FLEXIBILITY:
    List<? extends Object>  = any list (covariant behavior for reads)
    List<? super String>    = list of String or supertypes (contravariant behavior for writes)

GENERIC CLASS INHERITANCE PATTERNS
------------------------------------
  Pattern 1 — Preserve generic parameter:
    class Container<T> { ... }
    class SortedContainer<T extends Comparable<T>> extends Container<T> { ... }

    SortedContainer<String> sc = new SortedContainer<>();
    Container<String> c = sc;  // ✅ SortedContainer<String> IS-A Container<String>
    Container<Integer> ci = sc; // ❌ not SortedContainer<Integer>

  Pattern 2 — Bind the type parameter:
    class StringContainer extends Container<String> { ... }
    // StringContainer is NOT generic anymore — T is fixed to String

    StringContainer sc = new StringContainer();
    Container<String> c = sc;  // ✅ works
    // Container<Integer> ci = sc; // ❌ not related

  Pattern 3 — Raw type (AVOID):
    class BadContainer extends Container { ... } // raw — loses type safety

ASSIGNING GENERIC TYPES (RULES)
---------------------------------
  Box<String>    → Box<Object>:    ❌ not compatible (invariant)
  Box<String>    → Box<String>:    ✅ same type
  Box<String>    → Box<?>:         ✅ wildcard accepts any
  Box<String>    → Box<? extends String>: ✅
  Box<String>    → Box<? extends Object>: ✅
  Box<Object>    → Box<? super String>: ✅
  Box<Number>    → Box<? super Integer>: ✅ (Number is supertype of Integer)
  Box<Integer>   → Box<? super Integer>: ✅ (Integer is supertype of itself)

  Summary:
    Box<? extends T> = any Box<X> where X is T or subtype of T  (read-only view)
    Box<? super T>   = any Box<X> where X is T or supertype of T (write-only view)

MULTIPLE INTERFACE IMPLEMENTATION WITH GENERICS
-------------------------------------------------
  A class can implement the same generic interface only ONCE with a specific type argument.
  This is because of type erasure — implementing the same interface twice would create
  conflicting bridge methods.

  // ❌ CANNOT implement same interface twice with different type args:
  class Broken implements Comparator<String>, Comparator<Integer> {} // compile error

  // ✅ CAN implement different generic interfaces:
  class Range<T extends Comparable<T>> implements Comparable<Range<T>>, Iterable<T> { ... }

COVARIANT RETURN TYPES WITH GENERICS
--------------------------------------
  Java allows covariant return types — a subclass method can return a more specific type.
  This works with generics too.

  class Animal { }
  class Dog extends Animal { }

  class AnimalFactory {
      public Animal create() { return new Animal(); }
  }

  class DogFactory extends AnimalFactory {
      @Override
      public Dog create() { return new Dog(); }  // ✅ covariant return
  }

  // With generics:
  interface Cloneable<T> {
      T clone();
  }

  class Point implements Cloneable<Point> {
      @Override
      public Point clone() { return new Point(x, y); }
  }

GENERIC TYPE AND INSTANCEOF
-----------------------------
  Because of type erasure, you CANNOT use instanceof with parameterized types:

  Object obj = new ArrayList<String>();
  if (obj instanceof ArrayList<String>) { } // ❌ compile error
  if (obj instanceof ArrayList<?>)      { } // ✅ wildcard allowed
  if (obj instanceof ArrayList)         { } // ✅ raw type allowed (but unchecked)

  // Java 16+ pattern matching (still can't check type parameter):
  if (obj instanceof ArrayList<?> list) {   // ✅
      System.out.println(list.size());
  }

OVERRIDING GENERIC METHODS
----------------------------
  When overriding a generic method, the type parameters must be compatible:

  class Base {
      public <T> T process(T input) { return input; }
  }

  class Sub extends Base {
      @Override
      public <T> T process(T input) { return input; } // ✅ same signature
  }

  // Cannot narrow the type parameter in override:
  class BadSub extends Base {
      // @Override
      public <T extends String> T process(T input) { return input; } // NOT an override — different method
  }

GENERIC METHOD VS GENERIC CLASS WHEN TO USE WHICH
--------------------------------------------------
  Use GENERIC CLASS when:
  - Multiple methods in the class all need to work with the same type
  - The type is fundamental to the class's identity (Box<T>, List<T>)

  Use GENERIC METHOD when:
  - The type relationship is specific to one method
  - Static utility methods (Collections.sort, Collections.min)
  - You want type inference from arguments

  // Class-level T: all methods share T
  class Sorter<T extends Comparable<T>> {
      private List<T> items;
      public void add(T item) { items.add(item); }
      public T min() { return Collections.min(items); }
  }

  // Method-level T: independent per method call
  class Util {
      public static <T extends Comparable<T>> T clamp(T v, T min, T max) { ... }
      public static <T> List<T> repeat(T item, int n) { ... }
  }

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Is List<Integer> a subtype of List<Number>?
A: No. Generics are invariant — List<Integer> and List<Number> have no subtype relationship
   even though Integer is a subtype of Number. This prevents adding a Double to what's really
   a List<Integer>. Use List<? extends Number> to accept List<Integer> in a read-only context.

Q: What does it mean for generics to be invariant, and why?
A: Invariant means: no subtype relationship between generic types even when the type arguments
   have a subtype relationship. List<String> is NOT a subtype of List<Object>.
   This is intentional — it provides compile-time type safety. Arrays are covariant but
   unsound (allows runtime ArrayStoreException). Generics are invariant and sound.

Q: Can you implement the same generic interface twice with different type arguments?
A: No. Due to type erasure, both implementations would produce the same bridge method
   signatures. The compiler rejects this as it would create a conflict.
   Example: implementing both Comparable<String> and Comparable<Integer> is not allowed.

Q: What is the difference between T[] and List<T>?
A: T[] (generic array): cannot be created with new T[] due to erasure. Arrays are covariant —
   String[] is-a Object[] — which can lead to runtime ArrayStoreException.
   List<T>: can be created (new ArrayList<>()), invariant (List<String> is NOT List<Object>),
   type-safe at compile time. Preferred in generic code. No risk of array store exceptions.
