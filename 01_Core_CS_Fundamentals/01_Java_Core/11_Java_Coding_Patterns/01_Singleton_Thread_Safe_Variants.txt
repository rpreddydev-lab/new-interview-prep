SINGLETON — THREAD-SAFE VARIANTS
==================================

OVERVIEW
--------
  A Singleton ensures only one instance of a class exists for the lifetime of the JVM.
  Key challenges: thread safety, lazy initialization, serialization safety, reflection attacks.

VARIANT 1: EAGER INITIALIZATION
---------------------------------
  // Simple, thread-safe — instance created when class loads (JVM class loading is thread-safe)
  public class EagerSingleton {
      // Allocated when class is loaded by the classloader (before any thread can call getInstance)
      private static final EagerSingleton INSTANCE = new EagerSingleton();

      private EagerSingleton() {
          // prevent reflection: throw exception if already instantiated
          if (INSTANCE != null) throw new IllegalStateException("Use getInstance()");
      }

      public static EagerSingleton getInstance() {
          return INSTANCE;
      }
  }
  // Pro: simplest, truly thread-safe without any synchronization overhead
  // Con: instance created even if never used (if constructor is expensive, wastes resources)

VARIANT 2: SYNCHRONIZED METHOD (LAZY)
---------------------------------------
  public class SynchronizedSingleton {
      private static SynchronizedSingleton instance;

      private SynchronizedSingleton() {}

      // Every call to getInstance() acquires the monitor — severe contention bottleneck
      public static synchronized SynchronizedSingleton getInstance() {
          if (instance == null) {
              instance = new SynchronizedSingleton();
          }
          return instance;
      }
  }
  // Pro: lazy, thread-safe
  // Con: synchronized on every call — unnecessary cost after initialization

VARIANT 3: DOUBLE-CHECKED LOCKING (DCL)
-----------------------------------------
  public class DCLSingleton {
      // volatile is CRITICAL: prevents reordering of alloc/init/assign steps
      private static volatile DCLSingleton instance;

      private DCLSingleton() {}

      public static DCLSingleton getInstance() {
          if (instance == null) {                  // first check (no lock — fast path)
              synchronized (DCLSingleton.class) {
                  if (instance == null) {          // second check (with lock — safe path)
                      instance = new DCLSingleton();
                  }
              }
          }
          return instance;  // fast path: no synchronization after initialization
      }
  }
  // Pro: lazy, thread-safe, low overhead after initialization
  // Con: subtle — requires volatile; tricky to get right

VARIANT 4: INITIALIZATION-ON-DEMAND HOLDER (BEST PRACTICE)
-----------------------------------------------------------
  public class HolderSingleton {
      private HolderSingleton() {}

      // Inner class loaded lazily by the JVM only when getInstance() is first called.
      // Class loading is inherently thread-safe (JVM serializes class initialization).
      // The static initializer runs exactly once with full thread safety — no synchronization needed.
      private static final class InstanceHolder {
          static final HolderSingleton INSTANCE = new HolderSingleton();
      }

      public static HolderSingleton getInstance() {
          return InstanceHolder.INSTANCE;  // triggers lazy load of InstanceHolder on first call
      }
  }
  // Pro: lazy, thread-safe, no synchronization overhead, simple
  // Con: none — this is the recommended pattern for most use cases

VARIANT 5: ENUM SINGLETON (SERIALIZATION-SAFE)
-----------------------------------------------
  public enum EnumSingleton {
      INSTANCE;

      private int connectionCount;

      public int getConnectionCount() { return connectionCount; }
      public void setConnectionCount(int count) { this.connectionCount = count; }
      public void connect() { /* ... */ }
  }

  // Usage:
  EnumSingleton.INSTANCE.connect();

  // Pro: serialization-safe (enum deserialization doesn't create new instances),
  //      reflection-safe (cannot invoke private constructor via reflection on enums),
  //      simplest thread-safe lazy-ish initialization (enum constants initialized at class load)
  // Con: cannot lazily initialize with a parameter; looks unusual to some; cannot subclass

SERIALIZATION PITFALL
----------------------
  If a Singleton implements Serializable, deserialization creates a NEW instance!
  Fix: override readResolve():

  public class SerializableSingleton implements Serializable {
      private static final long serialVersionUID = 1L;
      private static final SerializableSingleton INSTANCE = new SerializableSingleton();
      private SerializableSingleton() {}
      public static SerializableSingleton getInstance() { return INSTANCE; }

      // Called by the serialization mechanism after deserialization
      protected Object readResolve() {
          return INSTANCE;  // return existing instance instead of deserialized one
      }
  }

REFLECTION ATTACK PREVENTION
------------------------------
  Reflection can access private constructors:
  Constructor<Singleton> c = Singleton.class.getDeclaredConstructor();
  c.setAccessible(true);
  Singleton s2 = c.newInstance();  // bypasses private! creates second instance

  Defense: throw exception in constructor if instance already exists.
  public class DefendedSingleton {
      private static final AtomicBoolean instanceCreated = new AtomicBoolean(false);
      private DefendedSingleton() {
          if (!instanceCreated.compareAndSet(false, true)) {
              throw new IllegalStateException("Singleton already instantiated");
          }
      }
      // ...
  }
  // Enum singleton is immune to reflection attacks (JVM prohibits reflective enum instantiation).

COMPARISON TABLE
-----------------
  | Variant               | Lazy? | Thread-Safe? | Serialization? | Reflection? | Overhead |
  |-----------------------|-------|--------------|----------------|-------------|----------|
  | Eager initialization  | No    | Yes          | With readResolve | Needs guard | None    |
  | Synchronized method   | Yes   | Yes          | With readResolve | Needs guard | High    |
  | DCL + volatile        | Yes   | Yes          | With readResolve | Needs guard | Minimal |
  | Holder idiom          | Yes   | Yes          | With readResolve | Needs guard | None    |
  | Enum singleton        | No*   | Yes          | Built-in       | Built-in    | None    |
  (* loaded at first class access — lazier than eager if enum class loaded late)

INTERVIEW DISCUSSION POINTS
-----------------------------
  Q: Why is DCL broken without volatile?
  A: new Singleton() is not atomic. The JIT can reorder: allocate memory → assign reference
     → run constructor. Without volatile, a second thread may see non-null instance
     before the constructor finishes — using a partially initialized object.

  Q: What's the simplest correct thread-safe singleton?
  A: Holder idiom (if you need lazy init) or Enum singleton (if you need serialization safety).

  Q: How do Spring and CDI handle singleton scope?
  A: Spring's @Component / @Bean default is singleton scope — the IoC container manages
     one instance per ApplicationContext. You don't need to implement Singleton pattern
     yourself; the framework's DI container is the "singleton registry."
