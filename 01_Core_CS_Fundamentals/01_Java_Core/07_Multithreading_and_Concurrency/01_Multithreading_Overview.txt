MULTITHREADING OVERVIEW
========================

WHAT IS MULTITHREADING?
------------------------
  Multithreading allows multiple threads of execution to run concurrently within
  a single Java process. Each thread has its own:
  - Program counter (which instruction to execute next)
  - Stack (local variables and method call frames)
  - Thread-local storage

  All threads in a process SHARE:
  - Heap memory (objects, instance fields)
  - Static fields
  - Open file descriptors and I/O streams

WHY MULTITHREADING?
--------------------
  ✅ Responsiveness — UI thread stays live while background work happens
  ✅ Throughput — multiple CPU cores utilized simultaneously
  ✅ Resource sharing — threads share heap memory; cheaper than multiple processes
  ✅ Asynchronous I/O — one thread can block on I/O while another computes
  ✅ Parallelism — split large workloads across cores (Fork/Join, parallel streams)

  Trade-offs:
  ❌ Complexity — race conditions, deadlocks, visibility issues
  ❌ Harder to test and debug (non-deterministic interleaving)
  ❌ Synchronization overhead can reduce throughput if overused
  ❌ Memory overhead per thread (~512KB-1MB stack by default)

PROCESS vs THREAD
------------------
  Aspect            | Process                   | Thread
  ------------------|---------------------------|-------------------------------
  Memory            | Own address space          | Shared heap within process
  Isolation         | Fully isolated             | Shares heap — risk of races
  Creation cost     | High (fork/exec)           | Low (Java Thread object)
  Communication     | IPC (pipes, sockets, etc.) | Shared memory (synchronized)
  Crash impact      | Isolated — other procs OK  | Can crash whole JVM
  Java equivalent   | ProcessBuilder / Runtime.exec | Thread / ExecutorService

JAVA THREAD MODEL
------------------
  Java maps threads to OS native threads (1:1 mapping in HotSpot JVM).
  Each Java Thread → one OS kernel thread.
  - Context switches are managed by the OS scheduler
  - Thread scheduling is preemptive (OS decides when to switch)
  - Thread priority is a HINT to the OS, not guaranteed

  Java 21+ introduced Virtual Threads (Project Loom):
  - Lightweight threads managed by the JVM, not the OS
  - Many virtual threads multiplexed onto few OS threads (M:N)
  - Ideal for blocking I/O workloads — see file 15

CONCURRENCY vs PARALLELISM
----------------------------
  Concurrency: dealing with multiple tasks at once (may not be simultaneous)
  Parallelism: executing multiple tasks SIMULTANEOUSLY (requires multiple cores)

  Single-core CPU: concurrency without parallelism — interleaved execution
  Multi-core CPU: concurrency WITH parallelism — truly simultaneous on different cores

  Java enables both through threads. Parallel Streams and Fork/Join exploit parallelism.

THREAD PRIORITY
----------------
  Thread.setPriority(int) — 1 (MIN) to 10 (MAX), default 5 (NORM)
  The JVM passes hints to the OS; actual behavior is platform-dependent.
  Don't rely on priority for correctness — use synchronization primitives instead.

  Thread.MIN_PRIORITY  = 1
  Thread.NORM_PRIORITY = 5  ← default
  Thread.MAX_PRIORITY  = 10

DAEMON THREADS
---------------
  Regular threads: JVM waits for all to finish before exiting
  Daemon threads: JVM exits when only daemon threads remain (background/support tasks)

  Thread t = new Thread(() -> { /* background work */ });
  t.setDaemon(true);   // must be set BEFORE start()
  t.start();

  Examples of daemon threads: GC thread, JIT compiler thread, finalizer thread.

KEY CONCURRENCY PROBLEMS
--------------------------
  1. Race Condition — two threads read/modify shared state without proper synchronization,
     producing nondeterministic results depending on thread scheduling order.

  2. Visibility Problem — changes made by one thread may not be visible to another
     thread due to CPU caching and instruction reordering. Solved with volatile/synchronized.

  3. Atomicity Problem — compound operations (read-modify-write) that appear atomic
     in source code are NOT atomic at the CPU level (e.g., i++ is three instructions).

  4. Deadlock — Thread A holds lock X, waits for lock Y; Thread B holds Y, waits for X.
     Neither can proceed.

  5. Livelock — threads keep responding to each other's state but make no progress.

  6. Starvation — one thread never gets CPU time because higher-priority threads always win.

JAVA CONCURRENCY PACKAGES
---------------------------
  java.lang.Thread           — base threading class
  java.lang.Runnable         — task interface (no return, no throw)
  java.util.concurrent.*     — rich concurrency toolkit:
    ├── Callable<V>           — task that returns a value and can throw
    ├── ExecutorService       — thread pool management
    ├── Future<V>             — handle to async computation result
    ├── CompletableFuture<V>  — composable async pipelines (Java 8+)
    ├── Lock, ReentrantLock   — explicit lock objects (more flexible than synchronized)
    ├── Atomic* classes       — lock-free atomic operations
    ├── BlockingQueue         — thread-safe producer-consumer queues
    ├── CountDownLatch        — coordination primitive (one-time count-down)
    ├── CyclicBarrier         — synchronize N threads at a checkpoint
    ├── Semaphore             — control access to limited resources
    └── ConcurrentHashMap     — thread-safe map without full-table locking

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is a thread and how does it differ from a process?
A: A thread is a lightweight unit of execution within a process. Processes have
   separate address spaces and communicate via IPC. Threads within the same process
   share the heap and static fields, making communication fast but requiring
   synchronization to avoid race conditions. Creating a thread is cheaper than
   creating a process.

Q: What are the main problems with multithreaded programming?
A: Race conditions (non-atomic compound operations on shared state), visibility issues
   (stale cached values not seen by other threads), deadlock (circular lock dependencies),
   livelock (threads spinning without progress), and starvation (a thread never scheduled).
   Java addresses these with: synchronized, volatile, Lock objects, Atomic* classes,
   and concurrent data structures.

Q: What is the difference between concurrency and parallelism?
A: Concurrency is about dealing with multiple tasks at once — tasks may interleave on a
   single core (time-slicing). Parallelism is about executing tasks simultaneously on
   multiple cores. Concurrency is a design concept; parallelism is an execution property.
   A concurrent program may or may not run in parallel depending on available CPU cores.

Q: What are daemon threads in Java?
A: Daemon threads run in the background and do not prevent the JVM from exiting.
   When all non-daemon threads finish, the JVM terminates even if daemon threads are still
   running. Set with t.setDaemon(true) before start(). GC, JIT, and finalizer threads are
   daemon threads. Never use daemon threads for tasks that must complete (data writes, etc.).
