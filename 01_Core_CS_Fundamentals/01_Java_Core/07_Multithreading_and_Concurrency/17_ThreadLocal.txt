THREADLOCAL
============

WHAT IS ThreadLocal?
---------------------
  ThreadLocal<T> provides per-thread storage — each thread has its own INDEPENDENT copy
  of the variable, invisible to other threads. No synchronization needed because threads
  never share the value.

  Think of it as a Map<Thread, T> — but the current thread is always the implicit key.

CREATING AND USING
-------------------
  // Declaration — usually static and final (one ThreadLocal instance, per-thread values)
  private static final ThreadLocal<SimpleDateFormat> dateFormat =
      ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

  // Access: get() / set() / remove()
  String today = dateFormat.get().format(new Date());  // per-thread instance

  // Manual set:
  ThreadLocal<String> userId = new ThreadLocal<>();
  userId.set("user-123");       // sets for current thread
  String id = userId.get();     // "user-123" in this thread, null in others
  userId.remove();              // clean up — CRITICAL in thread pools!

  // withInitial: provide a Supplier for the default value on first get():
  ThreadLocal<List<String>> threadList =
      ThreadLocal.withInitial(ArrayList::new);  // each thread gets its own ArrayList

COMMON USE CASES
-----------------
  1. Non-thread-safe objects shared across a method call chain:
     SimpleDateFormat, Random (pre-Java 7), JDBC Connection (without pool)

  2. Security/request context in web frameworks:
     Spring's SecurityContextHolder stores the authenticated user in a ThreadLocal.
     RequestContextHolder stores the current HTTP request.
     This allows any code in the request thread to access the user without passing it
     through every method parameter.

  3. Database transaction management:
     JDBC connections or EntityManagers stored per-thread so that begin(), commit(),
     rollback() always operate on the correct connection for the current thread.

  4. Avoiding object recreation in tight loops:
     ThreadLocal<byte[]> buffer = ThreadLocal.withInitial(() -> new byte[1024]);

THREADLOCAL IN WEB FRAMEWORKS (SPRING EXAMPLE)
-------------------------------------------------
  // Spring stores the Security context per-thread:
  SecurityContext ctx = SecurityContextHolder.getContext();  // ThreadLocal-backed
  Authentication auth = ctx.getAuthentication();
  String username = auth.getName();

  // Every request's thread can call this anywhere in the call stack
  // without passing the authentication object as a method parameter

MEMORY LEAK HAZARD
--------------------
  ⚠️ CRITICAL: In thread pools, threads are REUSED across many requests.
  If ThreadLocal.remove() is not called, the value persists into the next request!

  Consequences:
  1. Security: user A's auth context leaks to user B's request
  2. Memory: objects accumulate in the ThreadLocalMap and are never GC'd
     (ThreadLocalMap entry key is a WeakReference to the ThreadLocal — the ThreadLocal
     can be GC'd if no strong reference, but the VALUE is strongly referenced by the entry —
     potential memory leak if the ThreadLocal is static and the value is not removed)

  // ✅ Always remove in a try-finally:
  threadLocal.set(contextObject);
  try {
      processRequest();
  } finally {
      threadLocal.remove();  // MANDATORY in thread pools
  }

InheritableThreadLocal
-----------------------
  Child threads inherit the parent thread's values at the time of child creation.

  InheritableThreadLocal<String> requestId = new InheritableThreadLocal<>();
  requestId.set("req-abc");

  Thread child = new Thread(() -> {
      System.out.println(requestId.get()); // "req-abc" — inherited from parent
  });
  child.start();

  Note: The child gets a COPY of the parent's value at fork time — subsequent changes
  in the parent are NOT reflected in the child. For virtual threads and structured
  concurrency, use ScopedValue (Java 21+) instead.

ScopedValue (Java 21+ Preview)
--------------------------------
  ScopedValue is the modern, virtual-thread-safe alternative to ThreadLocal for
  structured concurrency. Values are immutable and scoped to a specific call stack frame.

  static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

  ScopedValue.where(REQUEST_ID, "req-xyz").run(() -> {
      // REQUEST_ID.get() == "req-xyz" inside this scope
      handleRequest();
  });
  // Outside the scope: REQUEST_ID.get() throws NoSuchElementException

  Advantages over ThreadLocal:
  ✅ Immutable — no set(); value can't be accidentally changed mid-scope
  ✅ Automatically scoped — no need to call remove()
  ✅ Works correctly with virtual threads (ThreadLocal has pinning issues at scale)
  ✅ Naturally propagates to structured sub-tasks

THREADLOCAL INTERNAL MECHANICS
--------------------------------
  Each Thread object holds a ThreadLocalMap field.
  ThreadLocalMap is a custom HashMap with:
  - Key: WeakReference to the ThreadLocal instance
  - Value: The stored T value (strong reference)

  Because the key is a WeakReference, when a ThreadLocal instance is GC'd (goes out of scope),
  the key becomes null — but the VALUE remains (strong reference from the Map entry).
  This is the memory leak: stale entries with null keys, live values. remove() cleans them.

THREADLOCAL vs INSTANCE FIELD vs STATIC FIELD
----------------------------------------------
  Storage            | Shared between threads?    | Notes
  -------------------|----------------------------|-------------------------------------------
  Static field       | Yes — all threads          | Requires synchronization
  Instance field     | Yes (for shared instances) | Requires synchronization if shared
  ThreadLocal field  | No — per thread copy       | No synchronization needed; remove() in pools

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is ThreadLocal and when should you use it?
A: ThreadLocal provides each thread with its own independent copy of a variable, eliminating
   the need for synchronization when threads each operate on their own state. Use it for:
   non-thread-safe objects (SimpleDateFormat), per-request context in web frameworks
   (security context, transaction context), or avoiding expensive per-call object creation.

Q: What is the ThreadLocal memory leak and how do you prevent it?
A: In thread pools, threads are reused. If ThreadLocal values are set without calling remove(),
   they persist in the thread's ThreadLocalMap across requests — causing data leaks (security)
   and memory leaks (values never GC'd because the ThreadLocalMap holds strong references
   to values). Prevention: always call threadLocal.remove() in a finally block at the end
   of the unit of work (request, task, job).

Q: What is the difference between ThreadLocal and InheritableThreadLocal?
A: ThreadLocal values are isolated per thread — child threads start with null (or the initial
   value). InheritableThreadLocal copies the parent thread's value to child threads at the
   moment the child is created. Subsequent parent changes don't propagate to the child.
   This is useful for propagating request IDs or user context to spawned threads.
