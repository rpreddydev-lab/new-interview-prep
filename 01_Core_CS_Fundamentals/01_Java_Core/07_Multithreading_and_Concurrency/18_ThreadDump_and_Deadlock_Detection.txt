THREAD DUMP AND DEADLOCK DETECTION
=====================================

WHAT IS A THREAD DUMP?
------------------------
  A thread dump is a snapshot of ALL threads running in a JVM at a specific moment.
  For each thread it shows:
  - Thread name, ID, priority, daemon status
  - Thread state (RUNNABLE, BLOCKED, WAITING, TIMED_WAITING)
  - Full stack trace — every method call on the thread's stack
  - Lock information — what locks the thread holds and waits for

  Thread dumps are the primary tool for diagnosing:
  - Deadlocks
  - Infinite loops / high CPU threads
  - Stuck threads (waiting forever)
  - Thread leaks (unexpectedly many threads)
  - Contention hotspots

HOW TO GENERATE A THREAD DUMP
-------------------------------
  1. kill -3 <pid>          (Linux/macOS) — sends SIGQUIT, prints to stdout
  2. jstack <pid>           (JDK tool) — prints thread dump to stdout
  3. jstack -l <pid>        — include lock information (CRITICAL for deadlock detection)
  4. jcmd <pid> Thread.print — modern alternative to jstack
  5. VisualVM → Threads tab → Thread Dump button (GUI)
  6. JConsole → Threads → Detect Deadlock button
  7. Java Flight Recorder (JFR) — continuous, low-overhead profiling

  // Programmatically from code:
  ThreadMXBean tmxb = ManagementFactory.getThreadMXBean();
  ThreadInfo[] threads = tmxb.dumpAllThreads(true, true); // with monitors and sync
  for (ThreadInfo ti : threads) {
      System.out.println(ti);
  }

READING A THREAD DUMP
----------------------
  Sample thread dump entry:

    "worker-thread-1" #15 prio=5 os_prio=0 tid=0x00007f daemon
       java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.BankService.transfer(BankService.java:45)
        - waiting to lock <0x000000076ae04768> (a com.example.Account)
        - locked <0x000000076ae04700> (a com.example.Account)
        at com.example.TransferTask.run(TransferTask.java:22)

  Reading the key parts:
  - "worker-thread-1" — thread name
  - #15 — thread ID
  - prio=5 — thread priority
  - daemon — if present, it's a daemon thread
  - State: BLOCKED — waiting for intrinsic lock
  - "waiting to lock <0x...>" — lock it needs
  - "locked <0x...>" — lock it currently holds
  - Stack trace — sequence of method calls

DETECTING DEADLOCK IN A THREAD DUMP
--------------------------------------
  The JVM automatically detects intrinsic lock deadlocks and prints:

    Found one Java-level deadlock:
    ==============================
    "thread-1":
      waiting to lock monitor 0x000000076ae04768 (object of com.example.Account),
      which is held by "thread-2"
    "thread-2":
      waiting to lock monitor 0x000000076ae04700 (object of com.example.Account),
      which is held by "thread-1"

  Java stack information for the threads listed above:
  ===================================================
  "thread-1":
    at com.example.BankService.transfer(BankService.java:45)
    - waiting to lock <0x...> (Account[id=2])
    - locked <0x...> (Account[id=1])
  "thread-2":
    at com.example.BankService.transfer(BankService.java:45)
    - waiting to lock <0x...> (Account[id=1])
    - locked <0x...> (Account[id=2])

  Look for: "Found one Java-level deadlock" in the dump output.
  ReentrantLock deadlocks are also reported by modern JVMs (not all versions).

DETECTING DEADLOCK PROGRAMMATICALLY
--------------------------------------
  long[] deadlockedIds = tmxb.findDeadlockedThreads();  // intrinsic + j.u.c. locks
  long[] monitorIds    = tmxb.findMonitorDeadlockedThreads(); // intrinsic locks only

  if (deadlockedIds != null) {
      ThreadInfo[] info = tmxb.getThreadInfo(deadlockedIds, true, true);
      for (ThreadInfo ti : info) {
          System.err.println("DEADLOCK: " + ti.getThreadName());
          System.err.println("  Waiting for: " + ti.getLockName());
          System.err.println("  Held by:     " + ti.getLockOwnerName());
      }
  }

HIGH CPU THREAD DIAGNOSIS
--------------------------
  1. Find the process PID: jps or top
  2. Find the hot thread (high CPU): top -H -p <pid>
     → Note the TID (thread ID in decimal)
  3. Convert TID to hex: printf '%x\n' <tid>  → e.g., 0x3f2a
  4. In jstack output, find the thread with nid=0x3f2a
  5. Examine its stack trace — usually shows a tight loop or hot lock

COMMON THREAD ISSUES AND THEIR DUMP SIGNATURES
-------------------------------------------------
  Issue           | Thread State  | Dump Pattern
  ----------------|---------------|--------------------------------------------
  Deadlock        | BLOCKED       | Circular "waiting to lock" / "locked" entries
  Infinite loop   | RUNNABLE      | Same stack frame repeated; no lock waiting
  Stuck I/O       | RUNNABLE      | java.net / java.io in stack
  Lock contention | BLOCKED       | Many threads "waiting to lock" same monitor
  Thread leak     | WAITING/TIMED | Many threads in wait() / sleep() / park()
  Thread starvation| RUNNABLE    | High-priority threads starving others

COMMON INTERVIEW QUESTIONS
---------------------------
Q: How do you detect a deadlock in a running Java application?
A: Generate a thread dump with jstack <pid> or jcmd <pid> Thread.print. The JVM
   detects intrinsic lock deadlocks and prints "Found one Java-level deadlock" followed
   by the thread names and the locks they hold and are waiting for. VisualVM and JConsole
   also provide "Detect Deadlock" buttons. Programmatically, use
   ManagementFactory.getThreadMXBean().findDeadlockedThreads() — returns IDs of
   deadlocked threads, or null if none.

Q: How do you identify a high-CPU thread in a Java process?
A: (1) Use top -H -p <pid> to see per-thread CPU on Linux. (2) Note the thread ID (TID)
   of the hottest thread in decimal. (3) Convert to hex with printf '%x\n' <tid>. (4) Run
   jstack <pid> and search for nid=0x<hex>. (5) Examine the stack trace — a tight loop
   or hot synchronized block typically appears at the top.

Q: What information does a thread dump contain?
A: For each thread: name, ID, priority, daemon status, current state (RUNNABLE, BLOCKED,
   WAITING, TIMED_WAITING, TERMINATED), the full stack trace, the locks it currently
   holds (locked <address>), and the lock it is waiting for (waiting to lock <address>).
   This information is sufficient to diagnose deadlocks, contention hotspots, stuck
   threads, and infinite loops.
