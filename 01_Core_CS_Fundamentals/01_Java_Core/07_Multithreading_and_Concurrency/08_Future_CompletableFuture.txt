FUTURE AND COMPLETABLEFUTURE
==============================

FUTURE<V> — BASIC ASYNC RESULT
---------------------------------
  Future<V> represents the result of an asynchronous computation.
  Obtained by submitting a Callable to an ExecutorService.

  ExecutorService pool = Executors.newFixedThreadPool(4);
  Future<Integer> future = pool.submit(() -> heavyComputation());

  // Do other work while computation runs...

  try {
      Integer result = future.get();         // blocks until result ready
      Integer r2     = future.get(5, SECONDS); // blocks with timeout
  } catch (ExecutionException e) {
      Throwable cause = e.getCause();        // exception from Callable
  } catch (TimeoutException e) {
      future.cancel(true);                   // interrupt the running task
  }

  Future limitations:
  - get() is blocking — ties up the calling thread
  - Cannot chain multiple async steps
  - Cannot combine multiple Futures
  - No way to run a callback when done

COMPLETABLEFUTURE<T> — COMPOSABLE ASYNC PIPELINES
---------------------------------------------------
  Introduced in Java 8. Implements both Future<T> and CompletionStage<T>.
  Allows non-blocking, chainable asynchronous computation.

  CREATING:
  CompletableFuture.supplyAsync(Supplier<T>)         — async task returning T
  CompletableFuture.runAsync(Runnable)               — async task returning void
  CompletableFuture.completedFuture(value)           — already-completed CF
  CompletableFuture.failedFuture(throwable)          — already-failed CF (Java 9+)

  // Default uses ForkJoinPool.commonPool(). Custom pool:
  CompletableFuture.supplyAsync(() -> compute(), myExecutor)

TRANSFORMATION (thenApply / thenCompose)
------------------------------------------
  thenApply(fn)     — synchronous map: T → U (runs in completing thread)
  thenApplyAsync(fn)— same but runs fn in a new thread from pool
  thenCompose(fn)   — flatMap: T → CompletableFuture<U> (avoids nesting)

  CompletableFuture.supplyAsync(() -> fetchUser(userId))    // CF<User>
      .thenApply(user -> enrichUser(user))                  // CF<EnrichedUser>
      .thenApply(eu -> eu.toDTO())                          // CF<UserDTO>
      .thenAccept(dto -> System.out.println(dto))           // CF<Void>
      .exceptionally(ex -> { log.error("Failed", ex); return null; });

CONSUMING RESULTS (thenAccept / thenRun)
------------------------------------------
  thenAccept(Consumer<T>)  — receive result, return void
  thenRun(Runnable)        — no result, just run after completion

COMBINING FUTURES
------------------
  thenCombine(other, BiFunction)   — when BOTH complete, combine results
  thenAcceptBoth(other, BiConsumer)— when BOTH complete, consume both results
  runAfterBoth(other, Runnable)    — run when both complete

  CompletableFuture<String> cfA = CompletableFuture.supplyAsync(() -> "Hello");
  CompletableFuture<String> cfB = CompletableFuture.supplyAsync(() -> " World");

  cfA.thenCombine(cfB, (a, b) -> a + b)
     .thenAccept(System.out::println);  // "Hello World"

EITHER FUTURE (applyToEither)
--------------------------------
  applyToEither(other, fn)     — use result of WHICHEVER completes first
  acceptEither(other, consumer)— consume result of whichever completes first

  // Race two sources — use the faster result:
  CompletableFuture<Data> fromCache = fetchFromCache();
  CompletableFuture<Data> fromDB    = fetchFromDB();
  fromCache.applyToEither(fromDB, data -> processData(data));

WAITING FOR ALL / ANY
------------------------
  CompletableFuture.allOf(cf1, cf2, cf3)  — completes when ALL complete (returns CF<Void>)
  CompletableFuture.anyOf(cf1, cf2, cf3)  — completes when ANY completes (returns CF<Object>)

  CompletableFuture<?>[] futures = { fetchA(), fetchB(), fetchC() };
  CompletableFuture.allOf(futures)
      .thenRun(() -> System.out.println("All done!"))
      .join();

ERROR HANDLING
---------------
  exceptionally(Function<Throwable, T>)   — recover from exception (like catch)
  handle(BiFunction<T, Throwable, U>)     — always called; both result and exception may be null
  whenComplete(BiConsumer<T, Throwable>)  — side-effect when done; does NOT transform result

  CompletableFuture.supplyAsync(() -> riskyOp())
      .exceptionally(ex -> defaultValue)           // recover
      .thenApply(result -> transform(result))
      .handle((res, ex) -> {
          if (ex != null) return "error";
          return res.toString();
      });

COMPLETING MANUALLY
--------------------
  CompletableFuture<String> cf = new CompletableFuture<>();

  // From another thread or callback:
  cf.complete("result");                // complete normally
  cf.completeExceptionally(new RuntimeException("failed"));  // complete with error
  cf.cancel(false);                     // cancel

ASYNC VARIANTS
---------------
  Every stage method has an Async version: thenApplyAsync, thenComposeAsync, etc.
  - Without Async suffix: stage runs in the thread that completes the preceding stage
  - With Async suffix: stage runs in ForkJoinPool.commonPool() or provided Executor
  - Always use Async for stages that do I/O or heavy work to avoid blocking the completing thread

COMPLETE PIPELINE EXAMPLE
--------------------------
  CompletableFuture<OrderSummary> pipeline =
      CompletableFuture.supplyAsync(() -> fetchOrder(orderId), ioPool)
          .thenComposeAsync(order -> fetchUser(order.getUserId()), ioPool)
          .thenApplyAsync(user -> buildSummary(order, user), computePool)
          .exceptionally(ex -> {
              log.error("Order pipeline failed", ex);
              return OrderSummary.empty();
          });

  OrderSummary result = pipeline.join();  // like get() without checked exceptions

Future vs CompletableFuture
-----------------------------
  Aspect                  | Future<T>                   | CompletableFuture<T>
  ------------------------|-----------------------------|-------------------------------
  Blocking get            | Yes (only way to get result)| Yes, but avoidable with callbacks
  Non-blocking callbacks  | ❌ No                        | ✅ thenApply, thenAccept, etc.
  Chaining                | ❌ No                        | ✅ Composable pipeline
  Combining multiple      | ❌ No                        | ✅ allOf, anyOf, thenCombine
  Manual completion       | ❌ No                        | ✅ complete(), completeExceptionally()
  Error recovery          | Catch ExecutionException     | ✅ exceptionally(), handle()
  Java version            | Java 5                      | Java 8+

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between thenApply and thenCompose?
A: thenApply is like map — it applies a function T → U to the result, wrapping it in
   a new CompletableFuture<U>. thenCompose is like flatMap — the function returns a
   CompletableFuture<U> itself, and thenCompose "flattens" the nesting to give
   CompletableFuture<U> instead of CompletableFuture<CompletableFuture<U>>. Use
   thenCompose when the next step is also async (returns a CF).

Q: How do you handle exceptions in CompletableFuture?
A: Use exceptionally(fn) to recover from any exception (like a catch block — fn provides
   a fallback value), handle(BiFunction) for both success and failure in one stage, or
   whenComplete for side effects without transformation. Unhandled exceptions are captured
   in the CF and rethrown when get()/join() is called.

Q: What is the difference between get() and join()?
A: Both block until the CF completes. get() is declared to throw checked exceptions
   (InterruptedException, ExecutionException). join() throws unchecked exceptions
   (CompletionException wrapping the cause). join() is often preferred in pipeline chains
   because it doesn't force you to handle checked exceptions at every step.
