LOCKS: ReentrantLock AND ReadWriteLock
========================================

WHY EXPLICIT LOCKS?
--------------------
  synchronized is simple but limited:
  - Cannot try to acquire a lock without blocking
  - Cannot interrupt a thread waiting for a lock
  - Cannot have multiple conditions per lock
  - No fairness guarantee

  java.util.concurrent.locks provides explicit Lock objects that solve these limitations.

ReentrantLock
--------------
  The most commonly used explicit lock — same reentrancy as synchronized but with extra features.

  import java.util.concurrent.locks.ReentrantLock;

  public class SafeCounter {
      private int count = 0;
      private final ReentrantLock lock = new ReentrantLock();

      public void increment() {
          lock.lock();          // acquire lock — blocks if held by another thread
          try {
              count++;
          } finally {
              lock.unlock();    // ALWAYS unlock in finally — even if exception thrown
          }
      }

      public int getCount() {
          lock.lock();
          try { return count; }
          finally { lock.unlock(); }
      }
  }

  CRITICAL: Always use try-finally around lock.unlock() to guarantee the lock
  is released even when an exception is thrown inside the protected block.
  Forgetting unlock() causes permanent deadlock.

ReentrantLock KEY METHODS
---------------------------
  Method                              | Description
  ------------------------------------|----------------------------------------------------
  lock()                              | Acquire; block indefinitely if not available
  unlock()                            | Release the lock
  tryLock()                           | Non-blocking attempt; returns true if acquired
  tryLock(long, TimeUnit)             | Timed attempt; throws InterruptedException
  lockInterruptibly()                 | Block but respond to interruption
  isHeldByCurrentThread()             | Check if current thread holds the lock
  isLocked()                          | Check if any thread holds the lock
  getHoldCount()                      | Reentry count for current thread
  new ReentrantLock(true)             | Fair lock — longest-waiting thread gets lock first

TRYLOCK — NON-BLOCKING ACQUISITION
-------------------------------------
  Avoids deadlock by backing off if a lock is unavailable:

  if (lock.tryLock()) {
      try {
          // do work safely
      } finally {
          lock.unlock();
      }
  } else {
      // Could not acquire — do something else or retry
      System.out.println("Lock not available, skipping");
  }

  // Timed tryLock:
  if (lock.tryLock(500, TimeUnit.MILLISECONDS)) {
      try { /* work */ }
      finally { lock.unlock(); }
  } else {
      throw new TimeoutException("Could not acquire lock within 500ms");
  }

FAIR vs UNFAIR LOCKS
---------------------
  Unfair (default): new ReentrantLock() — threads that just released may re-acquire immediately.
    → Higher throughput (no queue management overhead)
    → Risk of starvation for waiting threads

  Fair: new ReentrantLock(true) — granted to the longest-waiting thread.
    → Lower throughput
    → Prevents starvation
    → Use when fairness is a correctness requirement (rate limiting, resource allocation)

CONDITION OBJECTS (MULTIPLE CONDITIONS)
-----------------------------------------
  Lock.newCondition() creates a Condition — equivalent to a single wait-set.
  One lock can have MULTIPLE conditions, unlike synchronized (which has one).

  ReentrantLock lock = new ReentrantLock();
  Condition notFull  = lock.newCondition();
  Condition notEmpty = lock.newCondition();

  // Producer:
  lock.lock();
  try {
      while (buffer.isFull()) notFull.await();  // releases lock, waits
      buffer.add(item);
      notEmpty.signal();  // wake a consumer
  } finally { lock.unlock(); }

  // Consumer:
  lock.lock();
  try {
      while (buffer.isEmpty()) notEmpty.await();  // releases lock, waits
      Object item = buffer.remove();
      notFull.signal();  // wake a producer
  } finally { lock.unlock(); }

  Condition methods:
    await()         — release lock and wait (like Object.wait())
    signal()        — wake one waiter (like Object.notify())
    signalAll()     — wake all waiters (like Object.notifyAll())
    awaitNanos(n)   — wait with nanosecond timeout

ReadWriteLock
--------------
  When reads are frequent but writes are rare, ReadWriteLock maximizes throughput:
  - Multiple threads can hold the READ lock simultaneously (concurrent reads)
  - WRITE lock is exclusive — no reader OR other writer allowed

  import java.util.concurrent.locks.ReadWriteLock;
  import java.util.concurrent.locks.ReentrantReadWriteLock;

  public class ThreadSafeCache<K, V> {
      private final Map<K, V> cache = new HashMap<>();
      private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
      private final Lock readLock  = rwLock.readLock();
      private final Lock writeLock = rwLock.writeLock();

      public V get(K key) {
          readLock.lock();        // ← multiple threads can read concurrently
          try {
              return cache.get(key);
          } finally {
              readLock.unlock();
          }
      }

      public void put(K key, V value) {
          writeLock.lock();       // ← exclusive — all readers/writers blocked
          try {
              cache.put(key, value);
          } finally {
              writeLock.unlock();
          }
      }
  }

  ReadWriteLock rules:
  - Read lock can be acquired by many threads if no writer holds write lock
  - Write lock can only be acquired by ONE thread when no readers OR writers hold it
  - Write lock is EXCLUSIVE: blocks all readers while held
  - Read lock is SHARED: multiple readers allowed concurrently

LOCK COMPARISON
----------------
  Feature                    | synchronized | ReentrantLock | ReadWriteLock
  ---------------------------|--------------|---------------|---------------
  Auto-release on exit       | ✅ Yes       | ❌ Manual     | ❌ Manual
  tryLock (non-blocking)     | ❌ No        | ✅ Yes        | ✅ Yes
  Timed lock acquisition     | ❌ No        | ✅ Yes        | ✅ Yes
  Interruptible wait         | ❌ No        | ✅ Yes        | ✅ Yes
  Fair scheduling            | ❌ No        | ✅ Optional   | ✅ Optional
  Multiple conditions        | ❌ One       | ✅ Unlimited  | ✅ Unlimited
  Concurrent reads           | ❌ No        | ❌ No         | ✅ Yes
  Complexity                 | Low          | Medium        | Medium-High

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the advantage of ReentrantLock over synchronized?
A: ReentrantLock offers features not available with synchronized: tryLock() for
   non-blocking acquisition (avoiding deadlock), lockInterruptibly() for responding
   to interrupts during lock wait, timed lock attempts (tryLock(timeout, unit)),
   fair scheduling (new ReentrantLock(true)), and multiple Condition objects per lock
   (useful for producer-consumer with separate not-full and not-empty conditions).

Q: What is a ReadWriteLock and when should you use it?
A: ReadWriteLock maintains two locks: a shared read lock (multiple threads can hold
   simultaneously) and an exclusive write lock (only one thread, blocks all readers).
   Use it when reads are much more frequent than writes, and reads don't modify state.
   Example: a config cache or dictionary read by many threads but updated rarely.

Q: What happens if you forget to call unlock() in a ReentrantLock?
A: The lock is NEVER released, causing all other threads waiting for it to block forever
   (deadlock). This is why unlock() must ALWAYS be called in a finally block. With
   synchronized, the lock is released automatically when the block exits — with explicit
   locks, it's entirely the developer's responsibility.
