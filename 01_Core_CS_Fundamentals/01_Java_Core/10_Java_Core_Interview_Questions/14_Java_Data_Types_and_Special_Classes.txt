SECTION 1 — BigDecimal vs double for Financial Calculations
===============================================================================

Q1: Why should you never use double or float for monetary calculations?
-----------------------------------------------------------------------
A:
  double and float use IEEE 754 binary floating-point — they CANNOT represent most
  decimal fractions exactly. This causes silent rounding errors.

  Example:
    System.out.println(0.1 + 0.2);   // 0.30000000000000004 — NOT 0.3!
    System.out.println(1.03 - 0.42); // 0.6100000000000001

  In financial systems this is unacceptable — billing $0.30 as $0.30000000000000004
  causes cents-level discrepancies that compound over millions of transactions.

  Use BigDecimal for:
  - All monetary amounts
  - Tax calculations
  - Interest rates and compounding
  - Any decimal precision requirement

Q2: How do you correctly create BigDecimal values?
--------------------------------------------------
A:
  WRONG — BigDecimal from double:
    new BigDecimal(0.1)   // = 0.1000000000000000055511151231257827021181583404541015625
    // Inherits the binary representation imprecision!

  CORRECT — BigDecimal from String:
    new BigDecimal("0.1")        // exactly 0.1
    new BigDecimal("1.05")       // exactly 1.05

  CORRECT — BigDecimal.valueOf(double):
    BigDecimal.valueOf(0.1)      // uses Double.toString(0.1) = "0.1" internally → exact
    // Equivalent to new BigDecimal("0.1") for common decimal values

  Rule: ALWAYS use new BigDecimal("string") or BigDecimal.valueOf() — NEVER new BigDecimal(double).

Q3: How do you perform arithmetic and rounding with BigDecimal?
---------------------------------------------------------------
A:
  BigDecimal is IMMUTABLE — all operations return a new BigDecimal.

  Arithmetic:
    BigDecimal a = new BigDecimal("10.50");
    BigDecimal b = new BigDecimal("3.00");
    a.add(b)         // 13.50
    a.subtract(b)    // 7.50
    a.multiply(b)    // 31.5000 (scale = sum of scales)
    a.divide(b)      // 3.5

  Division and rounding — MUST specify scale and RoundingMode:
    a.divide(b, 2, RoundingMode.HALF_UP)   // 3.50 — safe
    a.divide(b)  // if non-terminating → throws ArithmeticException!

  RoundingMode options:
    HALF_UP     — round towards nearest, ties go up (common financial rounding)
    HALF_EVEN   — banker's rounding (ties round to nearest even digit — minimizes bias)
    CEILING     — round towards positive infinity
    FLOOR       — round towards negative infinity
    UP          — round away from zero
    DOWN        — round towards zero
    UNNECESSARY — throws if rounding is needed (use for verification)

  Scaling:
    bd.setScale(2, RoundingMode.HALF_UP)  // ensures exactly 2 decimal places

  Comparison — NEVER use equals() for comparison if scale differs:
    new BigDecimal("2.0").equals(new BigDecimal("2.00"))   // false (different scale!)
    new BigDecimal("2.0").compareTo(new BigDecimal("2.00")) // 0 (same value) ← use this

  Interview answer: "I use compareTo() not equals() for BigDecimal value equality, because
  2.0 and 2.00 are equal in value but not equal in scale."

Q4: What is the typical pattern for money handling in Java?
-----------------------------------------------------------
A:
  Best practice: wrap BigDecimal in a domain Money/Amount value object:

  final class Money {
      private final BigDecimal amount;
      private final Currency currency;

      private Money(BigDecimal amount, Currency currency) {
          this.amount = amount.setScale(2, RoundingMode.HALF_UP);
          this.currency = currency;
      }

      public static Money of(BigDecimal amount, Currency currency) {
          return new Money(Objects.requireNonNull(amount), Objects.requireNonNull(currency));
      }

      public Money add(Money other) {
          if (!this.currency.equals(other.currency))
              throw new IllegalArgumentException("Currency mismatch");
          return new Money(this.amount.add(other.amount), this.currency);
      }

      @Override public boolean equals(Object o) { ... }  // compareTo-based
      @Override public int hashCode() { ... }
      @Override public String toString() { return currency.getSymbol() + amount.toPlainString(); }
  }

  Why wrap it:
  - Enforces scale/rounding on every operation
  - Currency mismatch caught at domain level (not data layer)
  - equals/hashCode respect both value and currency
  - Aligns with Domain-Driven Design value object pattern

SECTION 2 — java.time API (Java 8+)
===============================================================================

Q5: What are the core types in java.time and when do you use each?
------------------------------------------------------------------
A:
  LocalDate          — date only (year, month, day). No time, no timezone.
                       Use for: birthdays, hire dates, schedules (any date without clock time)
    LocalDate.now()
    LocalDate.of(2024, 6, 15)
    LocalDate.parse("2024-06-15")

  LocalTime          — time only (hour, minute, second, nanos). No date, no timezone.
                       Use for: business hours, time-of-day rules

  LocalDateTime      — date + time, but NO timezone.
                       Unambiguous within one timezone context; problematic across zones.
                       Use for: local scheduling (meeting at 9am, stored for display only)

  ZonedDateTime      — date + time + timezone (ZoneId like "Europe/London", "Asia/Kolkata").
                       Use for: storing when something actually happened in absolute time.
                       "Order placed at 2024-06-15T14:30:00+05:30[Asia/Kolkata]"
                       Correct for DST transitions.

  OffsetDateTime     — date + time + fixed UTC offset (+05:30). No DST rules.
                       Use for: audit logs, API timestamps (RFC 3339 / ISO 8601 format).
                       Simpler than ZonedDateTime when you don't need DST awareness.

  Instant            — a point on the UTC timeline (nanosecond precision since epoch).
                       Machine-readable timestamp. Use for: event logs, sorting by time,
                       calculating elapsed time.
                       Instant.now()  →  2024-06-15T09:00:00Z

  Year, YearMonth, MonthDay — partial date types for specific use cases.

  Rule of thumb:
    Storing when something happened → Instant or ZonedDateTime
    Displaying local time to a user → LocalDateTime
    Date-only operations (age, birthday) → LocalDate
    Cross-timezone scheduling → ZonedDateTime

Q6: What is the difference between Duration and Period?
--------------------------------------------------------
A:
  Duration — measures time in hours, minutes, seconds, nanoseconds (time-based).
    Used with LocalTime, LocalDateTime, Instant.
    Duration.ofHours(2)
    Duration.between(start, end)
    Duration.parse("PT2H30M")   // 2 hours 30 minutes (ISO-8601)

  Period — measures time in years, months, days (date-based, calendar-aware).
    Used with LocalDate.
    Period.ofMonths(3)
    Period.between(startDate, endDate)
    Period.parse("P1Y2M3D")     // 1 year 2 months 3 days

  Why the distinction matters:
    "2 months after March 31" = May 31  (Period — month-aware)
    "60 days after March 31" ≠ May 31   (Duration — exact seconds/days)
    Adding 1 month handles different month lengths correctly; adding 30 days does not.

  Elapsed time calculation:
    Duration elapsed = Duration.between(Instant.now(), futureInstant);
    long minutes = elapsed.toMinutes();

Q7: How do you format and parse dates in java.time?
---------------------------------------------------
A:
  DateTimeFormatter is thread-safe and immutable (unlike SimpleDateFormat!).

  Built-in formatters:
    DateTimeFormatter.ISO_LOCAL_DATE        // "2024-06-15"
    DateTimeFormatter.ISO_LOCAL_DATE_TIME   // "2024-06-15T14:30:00"
    DateTimeFormatter.ISO_ZONED_DATE_TIME   // "2024-06-15T14:30:00+05:30[Asia/Kolkata]"
    DateTimeFormatter.ISO_INSTANT           // "2024-06-15T09:00:00Z"

  Custom formatter:
    DateTimeFormatter fmt = DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm");
    String formatted = LocalDateTime.now().format(fmt);   // "15/06/2024 14:30"
    LocalDateTime parsed = LocalDateTime.parse("15/06/2024 14:30", fmt);

  Locale-sensitive formatting:
    DateTimeFormatter fmt = DateTimeFormatter.ofLocalizedDate(FormatStyle.MEDIUM)
        .withLocale(Locale.UK);

  Why DateTimeFormatter instead of SimpleDateFormat:
    SimpleDateFormat is NOT thread-safe — sharing one instance across threads
    causes data corruption. DateTimeFormatter IS thread-safe — share safely as a constant.

Q8: How do you handle timezone conversion?
------------------------------------------
A:
  ZoneId zones = ZoneId.of("America/New_York");
  ZonedDateTime nyTime = ZonedDateTime.now(ZoneId.of("America/New_York"));
  ZonedDateTime londonTime = nyTime.withZoneSameInstant(ZoneId.of("Europe/London"));
  // withZoneSameInstant: same moment in time, different local representation

  // vs withZoneSameLocal (changes the instant):
  ZonedDateTime sameClock = nyTime.withZoneSameLocal(ZoneId.of("Europe/London"));
  // Same "clock time" but different absolute moment — usually wrong for conversions

  Converting to UTC:
    Instant utcInstant = nyTime.toInstant();  // UTC representation
    ZonedDateTime utc = nyTime.withZoneSameInstant(ZoneOffset.UTC);

  Available zone IDs:
    ZoneId.getAvailableZoneIds()   // set of all IANA timezone IDs

  Interview answer: "I always store timestamps as Instant or OffsetDateTime in UTC in
  the database, then convert to the user's local timezone for display. This avoids DST
  bugs and makes sorting/comparing trivial."

SECTION 3 — Reference Types: Weak, Soft, Phantom
===============================================================================

Q9: What are the four Java reference types and how do they differ?
------------------------------------------------------------------
A:
  Strong Reference (default):
    Object obj = new Object();
    // obj will NOT be GC'd as long as this reference exists.

  SoftReference<T>:
    SoftReference<byte[]> cache = new SoftReference<>(loadData());
    - GC WILL collect softly-reachable objects, but only as a last resort before OOM.
    - Objects survive minor GCs; cleared in major GCs when heap pressure is high.
    - Use for: memory-sensitive caches (image caches, data caches).
      Cache stays warm under low memory pressure; evicts under high pressure.
    - Access: softRef.get() → null if already collected.

  WeakReference<T>:
    WeakReference<Widget> weakRef = new WeakReference<>(widget);
    - GC WILL collect weakly-reachable objects at the NEXT GC cycle.
    - Weaker than SoftReference — cleared eagerly.
    - Use for: canonicalized maps (WeakHashMap), listener registries where you don't want
      to prevent the listener from being GC'd.
    - WeakHashMap: entries are automatically removed when the key becomes weakly reachable.

  PhantomReference<T>:
    ReferenceQueue<Object> queue = new ReferenceQueue<>();
    PhantomReference<Object> ref = new PhantomReference<>(obj, queue);
    - GC enqueues a PhantomReference into the ReferenceQueue AFTER finalization.
    - get() ALWAYS returns null — you cannot retrieve the referent.
    - Use for: resource cleanup after object is GC'd (replacement for finalize()).
      Java 9 Cleaner uses PhantomReference internally.

  Summary table:
  | Type      | Cleared when          | get() after GC | Use case                    |
  |-----------|----------------------|----------------|-----------------------------|
  | Strong    | Never (while held)   | N/A            | Normal object references    |
  | Soft      | Last resort (OOM)    | null           | Memory-sensitive caches     |
  | Weak      | Next GC cycle        | null           | Canonicalization, WeakHashMap|
  | Phantom   | After finalization   | Always null    | Post-GC cleanup, Cleaner    |

Q10: What is WeakHashMap and when should you use it?
----------------------------------------------------
A:
  WeakHashMap<K, V> is a Map where keys are held via WeakReference.
  When a key is no longer strongly referenced elsewhere, the GC can collect it,
  and the entry is automatically removed from the map.

  Use case: caching metadata associated with objects that you don't own:
    WeakHashMap<Widget, String> tooltips = new WeakHashMap<>();
    tooltips.put(widget, "This is a button");
    // When widget goes out of scope and is GC'd, the entry is automatically removed.
    // No manual cleanup needed — prevents memory leaks.

  NOT suitable for: data that must persist as long as the application runs, or
  where the key equality matters for the cache (keys might be GC'd unexpectedly).

  Alternative: Caffeine / Guava CacheBuilder with weakKeys() and softValues().

SECTION 4 — Comparable vs Comparator (Full Coverage)
===============================================================================

Q11: What is the difference between Comparable and Comparator?
--------------------------------------------------------------
A:
  Comparable<T> (java.lang):
  - Implemented BY the class itself — defines its NATURAL ordering.
  - Single method: int compareTo(T other)
  - The class "knows" how to compare itself to another instance.
  - Used by: Collections.sort(list), TreeSet, TreeMap, Arrays.sort — without extra args.
  - Example: Integer, String, LocalDate all implement Comparable.

  class Employee implements Comparable<Employee> {
      String name; int salary;
      @Override public int compareTo(Employee o) {
          return Integer.compare(this.salary, o.salary);  // natural order: by salary
      }
  }

  Comparator<T> (java.util):
  - An EXTERNAL strategy object — defines an alternative ordering.
  - Single method: int compare(T o1, T o2)
  - Passed to sort methods, TreeSet/TreeMap constructors, Stream.sorted().
  - Can define multiple orderings for the same class.

  Comparator<Employee> byName = Comparator.comparing(Employee::getName);
  Comparator<Employee> bySalaryDesc = Comparator.comparingInt(Employee::getSalary).reversed();

Q12: What is the Comparable.compareTo() contract?
-------------------------------------------------
A:
  compareTo(o) must return:
  - negative  — this object is LESS than o
  - zero      — this object is EQUAL to o
  - positive  — this object is GREATER than o

  Contract rules:
  1. Antisymmetry: sgn(x.compareTo(y)) == -sgn(y.compareTo(x))
  2. Transitivity: if x.compareTo(y) > 0 && y.compareTo(z) > 0 → x.compareTo(z) > 0
  3. Consistency: if x.compareTo(y) == 0 → sgn(x.compareTo(z)) == sgn(y.compareTo(z))
  4. Recommended (not required): x.compareTo(y) == 0 → x.equals(y)
     Violating this causes "inconsistent with equals" — TreeMap behavior differs from HashMap!

  Implementation tips:
    // WRONG: subtraction can overflow (Integer.MIN_VALUE - 1 = Integer.MAX_VALUE)
    return this.age - other.age;

    // CORRECT: use Integer.compare()
    return Integer.compare(this.age, other.age);
    return Double.compare(this.salary, other.salary);
    return this.name.compareTo(other.name);

Q13: How do you use Comparator chaining (thenComparing)?
---------------------------------------------------------
A:
  Comparator.comparing() + .thenComparing() creates multi-level sorts:

  // Sort by department, then by salary descending, then by name ascending
  Comparator<Employee> multiLevel = Comparator
      .comparing(Employee::getDepartment)              // primary: dept alphabetical
      .thenComparingInt(Employee::getSalary).reversed() // secondary: salary desc
      .thenComparing(Employee::getName);               // tertiary: name alpha

  employees.sort(multiLevel);
  // or: employees.stream().sorted(multiLevel).collect(toList());

  Null-safe comparators:
    Comparator<Employee> nullFirst = Comparator.nullsFirst(
        Comparator.comparing(Employee::getName));
    Comparator<Employee> nullLast = Comparator.nullsLast(
        Comparator.comparing(Employee::getName));

  Natural order convenience:
    Comparator.naturalOrder()   // uses Comparable.compareTo()
    Comparator.reverseOrder()   // reverses natural order

  Interview answer: "I chain comparators with thenComparing() for multi-key sorting —
  the equivalent of SQL ORDER BY dept ASC, salary DESC, name ASC in Java."

Q14: What is the difference between Collections.sort, List.sort, and Arrays.sort?
----------------------------------------------------------------------------------
A:
  Arrays.sort(T[] array, Comparator):
  - Sorts arrays in place.
  - Uses Timsort (hybrid merge sort + insertion sort) for objects → O(n log n), STABLE.
  - Uses dual-pivot quicksort for primitives (int[], double[], etc.) → O(n log n), NOT stable
    (but primitives have no identity so stability is irrelevant).

  Collections.sort(List<T>, Comparator) (Java 2+):
  - Delegates to list.toArray(), sorts the array, writes back.
  - O(n log n), STABLE (Timsort).

  List.sort(Comparator) (Java 8+):
  - Instance method on List — same algorithm as Collections.sort.
  - More natural to call on a list instance.
  - list.sort(Comparator.naturalOrder())

  Stream.sorted(Comparator):
  - Creates a new sorted stream (does not modify source).
  - Use when you want a sorted view without mutating the original list.

  Stability: "stable" means equal elements maintain their original relative order.
  Important when sorting by one key and needing to preserve a previous sort by another key.

SECTION 5 — LinkedHashMap, ArrayDeque, EnumMap
===============================================================================

Q15: How do you implement an LRU cache using LinkedHashMap?
-----------------------------------------------------------
A:
  LinkedHashMap maintains insertion order (default) OR access order.
  Access order = most-recently accessed element is last, least-recently is first.
  Combined with removeEldestEntry(), this builds a simple LRU cache in 5 lines:

  class LRUCache<K, V> extends LinkedHashMap<K, V> {
      private final int capacity;

      LRUCache(int capacity) {
          super(capacity, 0.75f, true);  // true = access order (not insertion order)
          this.capacity = capacity;
      }

      @Override
      protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
          return size() > capacity;  // evict when over capacity
      }
  }

  LRUCache<Integer, String> cache = new LRUCache<>(3);
  cache.put(1, "A"); cache.put(2, "B"); cache.put(3, "C");
  cache.get(1);      // access 1 → moves to end (most recent)
  cache.put(4, "D"); // capacity exceeded → evicts 2 (least recently used)
  // cache: {3=C, 1=A, 4=D}

  Interview answer: "LinkedHashMap with access-order and removeEldestEntry is the simplest
  LRU implementation in Java. For thread-safe LRU in production, I'd use Caffeine's
  Caffeine.newBuilder().maximumSize(n).build()."

Q16: Why use ArrayDeque instead of Stack or LinkedList as a queue?
------------------------------------------------------------------
A:
  ArrayDeque<T> implements Deque<T> (double-ended queue) using a resizable array.

  As a STACK (LIFO):
    Deque<String> stack = new ArrayDeque<>();
    stack.push("a");   // equivalent to addFirst()
    stack.pop();       // equivalent to removeFirst()
    stack.peek();      // view top without removing

  As a QUEUE (FIFO):
    Deque<String> queue = new ArrayDeque<>();
    queue.offer("a");  // add to tail
    queue.poll();      // remove from head
    queue.peek();      // view head without removing

  Why NOT Stack (java.util.Stack):
  - Stack extends Vector → synchronized — every method has a lock overhead
  - Legacy class; not recommended since Java 2
  - Extends Vector which exposes index-based access (nonsensical for a stack)

  Why NOT LinkedList as a queue:
  - Node-per-element overhead: each element has prev + next pointers (24 bytes overhead/element)
  - Poor cache locality (nodes scattered in heap)
  - ArrayDeque: contiguous array → better cache performance, less GC pressure

  Why ArrayDeque:
  - No synchronization overhead
  - Better performance than Stack and LinkedList for stack/queue use cases
  - Efficient resizing (doubles when full, like ArrayList)
  - NOT thread-safe — use ArrayBlockingQueue or LinkedBlockingDeque for concurrent use

  Rule: "Use ArrayDeque whenever you need a stack or queue in single-threaded code."

Q17: What is EnumMap and when is it better than HashMap?
---------------------------------------------------------
A:
  EnumMap<K extends Enum<K>, V> is a Map implementation specialized for enum keys.

  Map<Day, String> schedule = new EnumMap<>(Day.class);
  schedule.put(Day.MONDAY, "Team standup");
  schedule.put(Day.FRIDAY, "Sprint review");

  Why EnumMap is better than HashMap for enum keys:
  - Internally backed by an array indexed by enum ordinal — O(1) get/put
  - NO hashing overhead (no hashCode() calls, no bucket chains)
  - Zero collisions — ordinal is guaranteed unique
  - Maintains NATURAL ORDER of enum declaration on iteration
  - Extremely compact — no Node objects
  - Null keys NOT allowed (like ConcurrentHashMap)

  Performance: EnumMap is consistently faster than HashMap for enum keys —
  the array access is a single indirect memory operation.

  Use cases:
  - State machine transitions (Map<State, List<Transition>>)
  - Configuration per enum value (Map<Environment, Properties>)
  - Counting/accumulation by enum (Map<Category, Long>)
  - Feature flags per tier (Map<SubscriptionTier, Set<Feature>>)

SECTION 6 — Collections Utility Methods
===============================================================================

Q18: What are the most important Collections utility methods?
-------------------------------------------------------------
A:
  Sorting:
    Collections.sort(list)                  // natural order, modifies list
    Collections.sort(list, comparator)      // custom order
    Collections.reverse(list)              // reverse current order
    Collections.shuffle(list)              // random order
    Collections.shuffle(list, random)      // deterministic shuffle with seed

  Min/Max:
    Collections.min(collection)            // min by natural order
    Collections.max(collection, comparator)// max by custom order

  Frequency/Cardinality:
    Collections.frequency(collection, obj) // count occurrences of obj
    Collections.disjoint(c1, c2)           // true if no common elements

  Fill/Copy:
    Collections.fill(list, obj)            // sets all elements to obj
    Collections.copy(dest, src)            // dest must be at least as large as src
    Collections.nCopies(n, obj)            // immutable List of n copies of obj

  Unmodifiable views:
    Collections.unmodifiableList(list)     // view; throws on mutation; reflects original changes
    Collections.unmodifiableSortedMap(map) // etc.
    // vs List.copyOf(list) — truly immutable snapshot (Java 10+)

  Synchronized wrappers:
    Collections.synchronizedList(list)     // wrap with coarse-grained lock
    // prefer ConcurrentHashMap / CopyOnWriteArrayList for most concurrent use

  Singleton / Empty:
    Collections.singleton(obj)             // immutable Set with one element
    Collections.singletonList(obj)         // immutable List with one element
    Collections.emptyList()                // immutable empty list
    Collections.emptyMap()                 // immutable empty map

Q19: What is the difference between fail-fast and fail-safe iterators?
----------------------------------------------------------------------
A:
  Fail-fast iterators (most java.util collections):
  - The iterator maintains a modCount (modification counter) at creation.
  - Each next()/remove() call checks if modCount matches the collection's modCount.
  - If the collection is structurally modified outside the iterator while iterating,
    ConcurrentModificationException is thrown immediately.
  - Examples: ArrayList, HashMap, HashSet, LinkedList iterators.

  // Classic fail-fast trap:
  for (String s : list) {
      if (s.equals("x")) list.remove(s);  // ConcurrentModificationException!
  }
  // Fix: use iterator.remove() or collect-then-remove or removeIf()

  list.removeIf(s -> s.equals("x"));  // CORRECT — internal iterator + remove

  Fail-safe iterators (java.util.concurrent collections):
  - Operate on a SNAPSHOT or use versioning — never throw ConcurrentModificationException.
  - CopyOnWriteArrayList: iterator works on the array copy taken at iterator creation.
    Mutations after iterator creation are NOT visible to the iterator.
  - ConcurrentHashMap: weakly consistent iteration — may see some but not all updates
    made after the iterator was created.

  | Feature                    | Fail-fast          | Fail-safe                  |
  |----------------------------|--------------------|----------------------------|
  | CME on structural change   | YES                | NO                         |
  | Sees concurrent mutations  | No (throws)        | Partially (weakly consistent)|
  | Memory overhead            | Low                | Higher (snapshot/versioning)|
  | Examples                   | ArrayList, HashMap | CopyOnWriteArrayList, CHM  |

SECTION 7 — HashMap null Key Behavior
===============================================================================

Q20: How does HashMap handle null keys? How does it differ from Hashtable and ConcurrentHashMap?
-------------------------------------------------------------------------------------------------
A:
  HashMap:
  - Allows EXACTLY ONE null key.
  - The null key is always stored in bucket 0 (index 0 in the array).
  - HashMap checks for null key explicitly before calling hashCode():
    if (key == null) → place in bucket 0
  - Allows multiple null values (any value can be null).

  Hashtable (legacy):
  - Does NOT allow null keys or null values.
  - Throws NullPointerException on put(null, value) or put(key, null).
  - All methods are synchronized (slow, coarse-grained).
  - Effectively replaced by ConcurrentHashMap.

  ConcurrentHashMap:
  - Does NOT allow null keys or null values.
  - Reason: null introduces ambiguity in concurrent context.
    In a non-concurrent map: map.containsKey(key) == false → key absent.
    In a concurrent map: map.get(key) returning null could mean the key is absent
    OR the value was set to null. With concurrent reads/writes, there's no safe way
    to distinguish — so null is banned entirely.

  TreeMap:
  - Null keys NOT allowed (Comparable.compareTo(null) throws NullPointerException).
  - Unless a custom Comparator that handles null is provided.

  Summary:
  | Map type           | null key | null value |
  |--------------------|----------|------------|
  | HashMap            | ONE      | Yes        |
  | LinkedHashMap      | ONE      | Yes        |
  | TreeMap            | No       | Yes        |
  | Hashtable          | No       | No         |
  | ConcurrentHashMap  | No       | No         |
  | EnumMap            | No       | Yes        |

SECTION 8 — String Pool Deep Dive
===============================================================================

Q21: What is the String Pool and how does String.intern() work?
---------------------------------------------------------------
A:
  The String Pool (also called String Intern Pool or String Constant Pool) is a special
  area in the JVM Heap (Metaspace in Java 7 and before; heap in Java 8+) that stores
  unique String instances.

  String literals are automatically interned:
    String a = "hello";   // stored in pool
    String b = "hello";   // returns SAME pool object as a
    a == b  → true         // same reference

  new String() bypasses the pool:
    String c = new String("hello");  // creates NEW object on heap (NOT in pool)
    a == c  → false                  // different objects

  intern() method:
    String d = c.intern();           // looks up "hello" in pool; returns pool reference
    a == d  → true                   // now same pool reference

  Java 8+ Pool location:
  - Moved from PermGen to the main Heap — can be GC'd; no more PermGen OOM for interned strings.

  When to use intern():
  - Large data sets with many repeated string values (e.g., reading millions of city names)
    — share one instance instead of thousands of copies → saves heap.
  - WARNING: interning millions of unique strings can bloat the pool and cause GC pressure.
    Use only for HIGH-CARDINALITY repetition.

  Compile-time constants:
    final String prefix = "hello";
    String e = prefix + " world";   // concatenated at compile time → "hello world" in pool
    // Because prefix is final and a compile-time constant → inlined by compiler

Q22: What is the Integer cache and how does it relate to String pool?
---------------------------------------------------------------------
A:
  Java caches Integer objects for values -128 to 127 (inclusive).
  Integer.valueOf(n) for n in this range always returns the SAME cached object.

    Integer a = Integer.valueOf(127);
    Integer b = Integer.valueOf(127);
    a == b  → true (cached — same object)

    Integer c = Integer.valueOf(128);
    Integer d = Integer.valueOf(128);
    c == d  → false (outside cache — new objects)

  This also applies to autoboxing:
    Integer x = 100;  // autoboxed via Integer.valueOf(100) — cached
    Integer y = 100;
    x == y  → true

    Integer p = 200;  // outside cache
    Integer q = 200;
    p == q  → false  ← common interview trap!

  Same caching for: Boolean (TRUE/FALSE), Byte (-128..127), Short (-128..127),
  Character (0..127), Long (-128..127 in some JVMs).

  Rule: ALWAYS use .equals() for wrapper type comparison — never == unless you
  deliberately check reference identity.

  Upper cache bound is configurable: -XX:AutoBoxCacheMax=N can extend the Integer cache
  (only upward, not downward — lower bound stays -128).

Q23: How does the Java ClassLoader delegation model work?
---------------------------------------------------------
A:
  The ClassLoader hierarchy follows PARENT DELEGATION (also called parent-first delegation):
  When a ClassLoader is asked to load a class, it FIRST delegates to its parent.
  Only if the parent cannot find the class does the child attempt to load it.

  ClassLoader hierarchy:
    Bootstrap ClassLoader  (built into JVM, loads java.*, javax.*, sun.*)
          ↑ parent
    Extension/Platform ClassLoader  (loads from JDK ext/ directory; Java 9+: module classes)
          ↑ parent
    Application (System) ClassLoader  (loads from classpath — your app classes)
          ↑ parent
    Custom ClassLoader  (if your app defines one — for frameworks, hot-deploy)

  Why parent delegation?
  - Security: prevents malicious code from replacing core JDK classes (e.g., java.lang.String).
    If a user defined java.lang.String, the Bootstrap loader would always load the real one first.
  - Consistency: ensures core classes are loaded once, shared across the JVM.

  Class.forName() vs ClassLoader.loadClass():
    Class.forName("com.example.Foo")      // loads + initializes (runs static blocks)
    ClassLoader.loadClass("com.example.Foo") // loads but does NOT initialize

Q24: What causes a ClassNotFoundException vs NoClassDefFoundError?
------------------------------------------------------------------
A:
  ClassNotFoundException (checked exception):
  - Thrown at runtime when Class.forName() or ClassLoader.loadClass() cannot find the class.
  - The class was not on the classpath at all when explicitly requested.
  - Common causes: missing JAR, wrong classpath configuration, JDBC driver not present.

  NoClassDefFoundError (unchecked error):
  - Thrown when a class WAS successfully compiled (found at compile time) but is NOT
    available at runtime when the JVM tries to load it during normal class usage.
  - Or when a class failed to initialize (static block threw an exception) — subsequent
    attempts to use the class throw NoClassDefFoundError.
  - Common causes: JAR present at compile time but missing at runtime, class initializer
    failure, corrupted class file.

  Key distinction:
    ClassNotFoundException: requested explicitly, class not found → checked → handle it.
    NoClassDefFoundError: class was expected to be there, not found → error → fix classpath.

QUICK ANSWER CHEAT SHEET — DATA TYPES & SPECIAL CLASSES
===============================================================================

BigDecimal:
  new BigDecimal(0.1)           → WRONG (inherits binary imprecision)
  new BigDecimal("0.1")         → CORRECT (exact)
  BigDecimal.valueOf(0.1)       → CORRECT (uses toString internally)
  .divide(b, 2, HALF_UP)        → must specify scale + rounding (else ArithmeticException)
  .compareTo() not .equals()    → 2.0 != 2.00 via equals; 2.0 == 2.00 via compareTo

java.time:
  LocalDate                     → date only, no timezone
  LocalDateTime                 → date+time, no timezone
  ZonedDateTime                 → date+time+timezone (DST-aware)
  OffsetDateTime                → date+time+fixed offset (for APIs/logs)
  Instant                       → UTC point in time (machine timestamp)
  Duration                      → time-based (hours/minutes/seconds)
  Period                        → date-based (years/months/days)
  DateTimeFormatter             → thread-safe (vs SimpleDateFormat — NOT thread-safe)
  withZoneSameInstant()         → same moment, different timezone
  withZoneSameLocal()           → same clock display, different moment (usually wrong)

References:
  Strong                        → never GC'd while held
  SoftReference                 → GC'd last resort before OOM → caches
  WeakReference                 → GC'd at next cycle → WeakHashMap, listeners
  PhantomReference              → after finalization, get()=null → cleanup (Cleaner)
  WeakHashMap                   → keys held weakly → auto-removal on GC

Comparable vs Comparator:
  Comparable.compareTo()        → natural ordering, defined IN the class
  Comparator.comparing()        → external ordering strategy
  return Integer.compare(a, b)  → CORRECT (no overflow)
  return a - b                  → WRONG (Integer overflow)
  .thenComparing()              → multi-level sort (SQL: ORDER BY a, b, c)
  Comparator.nullsFirst/Last()  → null-safe comparators
  Collections.sort/List.sort    → Timsort, O(n log n), STABLE
  Arrays.sort on primitives     → dual-pivot quicksort, NOT stable (irrelevant for primitives)

LinkedHashMap / LRU:
  new LinkedHashMap<>(cap, 0.75f, true) → access-order mode
  override removeEldestEntry()          → evict when over capacity → LRU cache

ArrayDeque:
  stack: push/pop/peek → faster than Stack (no synchronization)
  queue: offer/poll/peek → faster than LinkedList (no node overhead)
  NOT thread-safe: use ArrayBlockingQueue/LinkedBlockingDeque for concurrent use

EnumMap:
  Array-backed, ordinal-indexed → no hashing, zero collisions
  O(1) operations, natural enum order iteration
  Use over HashMap<EnumType, V> always for enum keys

Fail-fast vs Fail-safe:
  Fail-fast: ArrayList/HashMap iterator → ConcurrentModificationException on mutation
  Fix: use iterator.remove() or list.removeIf() or collect-then-remove
  Fail-safe: CopyOnWriteArrayList (snapshot iterator), ConcurrentHashMap (weakly consistent)

HashMap null behavior:
  HashMap: ONE null key allowed (bucket 0), many null values
  Hashtable: NO nulls (NPE)
  ConcurrentHashMap: NO nulls (ambiguity in concurrent reads)
  TreeMap: NO null key (compareTo(null) throws NPE)

String Pool:
  Literals: automatically interned → "abc" == "abc" → true
  new String(): on heap, NOT in pool → new String("abc") == "abc" → false
  .intern(): move to pool → new String("abc").intern() == "abc" → true
  Integer cache: -128..127 cached → Integer.valueOf(127) == Integer.valueOf(127) → true
  Integer.valueOf(128) == Integer.valueOf(128) → FALSE — always use .equals()

ClassLoader:
  Parent delegation: Bootstrap → Platform → Application → Custom
  Class.forName(): loads AND initializes (static blocks run)
  ClassLoader.loadClass(): loads, does NOT initialize
  ClassNotFoundException: explicit load, class not found (checked)
  NoClassDefFoundError: class found at compile time, missing at runtime (error)
