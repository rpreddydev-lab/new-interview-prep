Java Tricky Yes/No — Quick-Fire Interview Questions
=====================================================
Format: Question => Answer + Why (one-liner reason)
These are "Is this valid?", "Will this compile?", "Is this true?" questions.
Interviewers fire these rapidly — you must answer instantly and correctly.


==============================================================================
SECTION 1: Compile or Not? (Static Analysis)
==============================================================================

Q: Can an interface have a constructor?
A: NO — interfaces cannot have constructors. Only abstract classes and
   concrete classes can. There is no object state to initialize in an interface.

Q: Can an abstract class have a constructor?
A: YES — abstract classes CAN have constructors. They are called via super()
   when a subclass is instantiated. You just cannot do "new AbstractClass()".

Q: Can an abstract class have no abstract methods?
A: YES — a class can be declared abstract with zero abstract methods.
   This simply prevents direct instantiation.

Q: Can an interface have private methods?
A: YES — since Java 9, interfaces can have private methods to share helper
   logic between default methods. They cannot be called from outside.

Q: Can an interface have static methods?
A: YES — since Java 8. But they are NOT inherited by implementing classes.
   Must be called as InterfaceName.method().

Q: Can a class extend multiple classes?
A: NO — Java does not support multiple class inheritance. A class can extend
   only ONE class (abstract or concrete).

Q: Can a class implement multiple interfaces?
A: YES — a class can implement any number of interfaces.

Q: Can an interface extend multiple interfaces?
A: YES — an interface CAN extend multiple interfaces.
   e.g., interface C extends A, B {}  — perfectly valid.

Q: Can a final class be extended?
A: NO — final classes cannot be subclassed. e.g., String, Integer.

Q: Can a final method be overridden?
A: NO — final methods cannot be overridden in any subclass.
   They CAN be overloaded.

Q: Can a final variable be changed after assignment?
A: NO — once assigned, a final variable cannot be reassigned.
   But if it's a reference type, the OBJECT it points to can be mutated.

Q: Can a static method be overridden?
A: NO — static methods are HIDDEN, not overridden. Resolved at compile time
   based on reference type, not runtime object type.

Q: Can a private method be overridden?
A: NO — private methods are not visible to subclasses, so they cannot
   be overridden. A subclass can declare the same method but it is a NEW method.

Q: Can a constructor be private?
A: YES — private constructors are used in Singleton pattern, utility classes
   (e.g., Collections, Math), and factory method patterns.

Q: Can a constructor be static?
A: NO — constructors are never static. They are instance-level initializers.

Q: Can a constructor be final?
A: NO — constructors are not inherited, so final has no meaning for them.

Q: Can a constructor be abstract?
A: NO — constructors cannot be abstract. Abstract implies subclass override,
   which constructors don't support.

Q: Can a constructor return a value?
A: NO — constructors have no return type (not even void). They implicitly
   return the newly created object.

Q: Can we have a return statement in a constructor?
A: YES — a bare "return;" (with no value) is allowed inside a constructor
   to exit early. Returning a value is a compile error.

Q: Can we override the main() method?
A: NO — static methods cannot be overridden. But you CAN overload main()
   with different parameters. JVM only calls main(String[] args) specifically.

Q: Can main() be final?
A: YES — you can declare public static final void main(String[] args).
   The JVM can still invoke it. It just prevents subclass hiding.

Q: Can we declare a class inside a method?
A: YES — these are called local classes. They have access to effectively
   final local variables of the enclosing method.

Q: Can an enum extend a class?
A: NO — all enums implicitly extend java.lang.Enum. Java does not allow
   multiple inheritance, so enums cannot extend any other class.

Q: Can an enum implement an interface?
A: YES — enums can implement interfaces. Each constant provides
   the implementation.

Q: Can an enum have abstract methods?
A: YES — if the enum declares an abstract method, each constant must provide
   its own implementation (as an anonymous class body).

Q: Can we create an instance of an enum using new?
A: NO — enum instances are created only by the JVM at class loading time.
   You cannot use "new" to create enum instances.

Q: Can a try block exist without a catch block?
A: YES — try-finally (without catch) is perfectly valid. Also try-with-
   resources can exist without catch or finally.

Q: Can we catch multiple exceptions in a single catch block?
A: YES — since Java 7: catch (IOException | SQLException e) {}

Q: Can we rethrow a checked exception as unchecked?
A: YES — you can wrap it: throw new RuntimeException(checkedException);
   This converts it to unchecked.

Q: Can a static block throw a checked exception?
A: NO — static initializer blocks cannot throw checked exceptions. If a
   checked exception occurs, it must be caught within the block or wrapped
   in ExceptionInInitializerError (which is unchecked).

Q: Can we have multiple static blocks in a class?
A: YES — multiple static blocks are allowed. They execute in order of
   appearance when the class is loaded.

Q: Can we have multiple instance initializer blocks?
A: YES — multiple instance blocks are allowed. They all execute before the
   constructor, in declaration order.

Q: Can a local variable be declared static?
A: NO — local variables (inside methods) cannot be static. static only
   applies to class-level members.

Q: Can an interface variable be non-static or non-final?
A: NO — all interface variables are implicitly public static final
   (constants). You cannot declare instance variables in an interface.

Q: Can we assign null to a primitive variable?
A: NO — primitives (int, double, boolean, etc.) cannot hold null.
   Only reference types can be null.

Q: Can a catch block catch both Error and Exception?
A: YES — catch (Throwable t) catches everything. But catching Error is
   generally a bad practice (only for top-level framework handlers).

Q: Is it valid to declare a variable of type void?
A: NO — void is not a data type. It is only a method return type keyword.

SECTION 2: True or False — Java Concepts
==============================================================================

Q: Java is 100% object-oriented.
A: FALSE — Java has primitive types (int, char, boolean, etc.) which are
   NOT objects. A purely OO language has only objects (e.g., Smalltalk).

Q: String is a primitive type in Java.
A: FALSE — String is a class (java.lang.String). It's just given special
   syntax support (literal "hello" and + operator).

Q: Strings are immutable in Java.
A: TRUE — once created, a String object's content cannot be changed.
   Any "modification" returns a new String object.

Q: StringBuffer is thread-safe.
A: TRUE — all StringBuffer methods are synchronized.

Q: StringBuilder is thread-safe.
A: FALSE — StringBuilder is NOT synchronized. Use StringBuffer for
   multi-threaded scenarios (or handle synchronization externally).

Q: == always compares content for wrapper types.
A: FALSE — == compares REFERENCES for wrapper types (Integer, Long, etc.).
   Exception: values in cache range (-128 to 127) may appear to compare
   content due to the integer cache. Always use .equals().

Q: An overriding method must have the exact same return type.
A: FALSE — since Java 5, COVARIANT return types are allowed. The overriding
   method can return a subtype of the original return type.

Q: An overriding method can throw broader checked exceptions.
A: FALSE — it can only throw NARROWER or the SAME checked exceptions, or
   unchecked exceptions. Throwing a broader checked exception is a compile error.

Q: Java supports multiple inheritance of state.
A: FALSE — Java does NOT allow multiple class inheritance (no multiple
   inheritance of state/fields). Interfaces only provide behavior, not state.

Q: Java supports multiple inheritance of behavior via interfaces.
A: TRUE — since Java 8, interfaces can have default methods, giving
   a class behavior from multiple interfaces.

Q: A class can implement the same interface twice.
A: FALSE — redundant, and causes a compile error if the interface appears
   twice in implements clause.

Q: A default method in an interface can be overridden.
A: TRUE — implementing classes can override default methods.

Q: Garbage collection guarantees memory will be freed immediately.
A: FALSE — GC runs at JVM's discretion. There is NO guarantee of when
   (or even if) an object will be collected.

Q: System.gc() forces immediate garbage collection.
A: FALSE — System.gc() is only a REQUEST/hint to the JVM. The JVM may
   choose to ignore it.

Q: finalize() is called before an object is garbage collected.
A: FALSE (practically) — finalize() was deprecated in Java 9 and removed
   in Java 18. Even when it existed, there was NO guarantee it would be
   called before collection or called at all.

Q: volatile guarantees atomicity.
A: FALSE — volatile only guarantees VISIBILITY (all threads see the latest
   value). It does NOT make compound operations (like i++) atomic.

Q: synchronized guarantees visibility.
A: TRUE — entering a synchronized block flushes cached writes; exiting
   makes writes visible to other threads. Synchronized provides both
   mutual exclusion AND visibility.

Q: wait() releases the lock.
A: TRUE — wait() releases the monitor lock and suspends the thread.
   sleep() does NOT release the lock.

Q: Checked exceptions must be declared or caught.
A: TRUE — checked exceptions (subclasses of Exception but NOT
   RuntimeException) must either be caught or declared with throws.

Q: RuntimeException is a checked exception.
A: FALSE — RuntimeException and its subclasses are UNCHECKED exceptions.
   They do NOT need to be declared or caught (though they can be).

Q: Error is a checked exception.
A: FALSE — Error (and its subclasses) are UNCHECKED. They represent
   serious JVM-level problems not meant to be caught in normal code.

Q: A HashMap allows null keys.
A: TRUE — HashMap allows ONE null key and multiple null values.

Q: A Hashtable allows null keys.
A: FALSE — Hashtable does NOT allow null keys or null values. Throws NPE.

Q: A TreeMap allows null keys.
A: FALSE — TreeMap does NOT allow null keys (it needs to compare keys
   for sorting). Throws NullPointerException.

Q: LinkedHashMap maintains insertion order.
A: TRUE — LinkedHashMap maintains a doubly-linked list to preserve
   insertion order (or access order if configured).

Q: HashSet guarantees element order.
A: FALSE — HashSet makes NO guarantee about iteration order. Use
   LinkedHashSet for insertion order or TreeSet for sorted order.

Q: ArrayList is synchronized.
A: FALSE — ArrayList is NOT thread-safe. Use Collections.synchronizedList()
   or CopyOnWriteArrayList for thread safety.

Q: Vector is synchronized.
A: TRUE — Vector is a legacy synchronized version of ArrayList.
   It is generally replaced by ArrayList + external sync or CopyOnWriteArrayList.

Q: Iterator is fail-fast for ArrayList.
A: TRUE — ArrayList's iterator uses modCount to detect structural changes.
   Any modification outside the iterator throws ConcurrentModificationException.

Q: You can remove elements from a List using Iterator.remove() safely.
A: TRUE — Iterator.remove() is the only safe way to remove elements
   during iteration with a fail-fast iterator.

Q: Autoboxing can throw a NullPointerException.
A: TRUE — unboxing null throws NPE. e.g., Integer x = null; int y = x; => NPE.

Q: The ternary operator always returns the same type for both branches.
A: FALSE — if branches have different types, Java finds the MOST SPECIFIC
   COMMON type (may be Object). e.g., (true ? "a" : 1) has type Object.

Q: Static methods can access instance variables directly.
A: FALSE — static methods belong to the CLASS, not an instance. They cannot
   access non-static (instance) fields or methods without an object reference.

Q: Instance methods can access static variables directly.
A: TRUE — instance methods can access both static and instance members.

Q: An interface can extend another interface.
A: TRUE — and it can extend MULTIPLE interfaces. This is how interface
   inheritance works.

Q: A class must implement all methods of an interface it implements.
A: FALSE — if the class is ABSTRACT, it doesn't need to implement all methods.
   Only concrete classes must implement all abstract interface methods.

Q: Two objects that are equal (equals() returns true) must have the
   same hashCode().
A: TRUE — this is the equals/hashCode CONTRACT. Violating it breaks
   HashMap, HashSet, and all hash-based collections.

Q: Two objects with the same hashCode() must be equal.
A: FALSE — hash COLLISIONS are allowed. Different objects can have the
   same hashCode() but not be equal. hashCode() doesn't imply equality.

Q: instanceof returns true for null.
A: FALSE — null instanceof <AnyType> always returns false. Never throws NPE.

Q: Java passes objects by reference.
A: FALSE (nuanced) — Java is ALWAYS pass-by-value. For objects, the VALUE
   passed is the REFERENCE (memory address). You can mutate the object via
   that reference, but you cannot make the caller's variable point to a
   different object.

Q: A thread can start() more than once.
A: FALSE — calling start() on an already-started thread throws
   IllegalThreadStateException. Create a new Thread object to run again.

Q: Calling run() directly on a Thread creates a new thread.
A: FALSE — calling run() directly just executes the method in the CURRENT
   thread. Only start() creates a new OS thread.

SECTION 3: Is This Valid Java? (Trick Syntax Questions)
==============================================================================

Q: Is this valid?  int[] arr = new int[-1];
A: NO — valid syntax (compiles fine), but throws NegativeArraySizeException
   at RUNTIME.

Q: Is this valid?  int[] arr = new int[0];
A: YES — a zero-length array is perfectly valid. arr.length == 0.

Q: Is this valid?  String s = null; int len = s.length();
A: Compiles YES, Runtime NO — NullPointerException at runtime.

Q: Is this valid?  int x; System.out.println(x);
A: NO — local variables must be initialized before use. Compile error:
   "variable x might not have been initialized".

Q: Is this valid?  class A { A a = new A(); }
A: YES — an instance field can be an instance of the same class. This is
   valid (used in linked structures). The field will be null if not assigned.

Q: Is this valid?  interface I { int x = 10; }
A: YES — implicitly public static final int x = 10. All interface
   fields are constants.

Q: Is this valid?  enum E { A, B; void method() {} }
A: YES — enums can have methods. The semicolon after the last constant
   is required before declaring members.

Q: Is this valid?  abstract class A { abstract void m() {} }
A: NO — abstract methods cannot have a body ({}). They must end with ;

Q: Is this valid?  class A { void m() {} }  class B extends A { int m() { return 1; } }
A: NO — changing only the return type (void to int) is NOT a valid override
   and NOT a valid overload (same parameters). Compile error.

Q: Is this valid?  try {} catch (Exception e) {} catch (RuntimeException e) {}
A: NO — RuntimeException is a subclass of Exception. Since Exception is
   caught first, the RuntimeException catch is UNREACHABLE. Compile error.

Q: Is this valid?  class A extends A {}
A: NO — a class cannot extend itself. Compile error.

Q: Is this valid?  int i = 01000;
A: YES — 01000 is an OCTAL literal (leading 0 = octal). Value = 512.

Q: Is this valid?  int i = 0b1010;
A: YES — 0b prefix = binary literal (Java 7+). Value = 10.

Q: Is this valid?  int i = 1_000_000;
A: YES — underscores in numeric literals are allowed (Java 7+) for
   readability. Value = 1000000.

Q: Is this valid?  double d = 1_000_.0;
A: NO — underscores cannot be adjacent to a decimal point. Compile error.

Q: Is this valid?  String s = "line1\nline2";
A: YES — \n is a newline escape character. Perfectly valid.

Q: Is this valid?  switch(null) {}
A: Compiles YES, Runtime NO — throws NullPointerException when switch
   tries to call null.hashCode() internally.

Q: Is this valid?  int x = true ? 1 : "hello";
A: NO — int cannot hold a String. Even in a ternary with mixed types,
   the result type must be compatible with the target variable.

Q: Is this valid?  List<int> list = new ArrayList<>();
A: NO — generics do NOT work with primitives. Use List<Integer>.
   This is a consequence of type erasure.

Q: Is this valid?  int[] a = {1,2,3}; Object o = a;
A: YES — arrays are objects in Java. An int[] can be assigned to Object.

Q: Is this valid?  void method(int... x, int y) {}
A: NO — varargs parameter MUST be the LAST parameter. Compile error.

Q: Is this valid?  void method(int x, int... y) {}
A: YES — varargs as the last parameter is perfectly valid.

SECTION 4: Which is Faster / Better? (Concept Decisions)
==============================================================================

Q: String concatenation with + in a loop — is it efficient?
A: NO — each + creates a new String object (String is immutable). This
   leads to O(n²) object creation. Use StringBuilder in loops.

Q: Is HashMap faster than TreeMap for get/put?
A: YES — HashMap is O(1) average. TreeMap is O(log n) due to tree traversal.
   Use TreeMap only when you need sorted order.

Q: Is ArrayList faster than LinkedList for random access?
A: YES — ArrayList is O(1) for get(index). LinkedList is O(n) — must
   traverse from head/tail.

Q: Is LinkedList faster than ArrayList for insertions at the middle?
A: YES (in theory) — LinkedList insert is O(1) once you have the node.
   But finding the node is O(n), so practically ArrayList wins for most cases.

Q: Should you use Hashtable in new code?
A: NO — Hashtable is a legacy synchronized class. Use ConcurrentHashMap
   for thread-safe maps. It has much better concurrency performance.

Q: Is ConcurrentHashMap fully synchronized like Hashtable?
A: NO — ConcurrentHashMap locks at the BUCKET level (segment level in older
   Java), not the whole map. Far more concurrent than Hashtable.

Q: Should you use Vector in new code?
A: NO — Vector is legacy. Use ArrayList with external synchronization or
   CopyOnWriteArrayList instead.

Q: Is it safe to use == to compare enums?
A: YES — enum constants are singletons. == is both safe and preferred
   over equals() for enums.

Q: Is it safe to use == to compare Integer objects?
A: NO — Integer objects outside the -128 to 127 cache will be different
   objects even with the same value. Always use .equals().

Q: Should you declare serialVersionUID explicitly?
A: YES — without it, Java auto-generates one based on class structure.
   Any field/method change will change it, breaking deserialization.

SECTION 5: Exception — Checked or Unchecked?
==============================================================================

Q: NullPointerException — checked or unchecked?
A: UNCHECKED — extends RuntimeException. No need to declare or catch.

Q: ArrayIndexOutOfBoundsException — checked or unchecked?
A: UNCHECKED — extends IndexOutOfBoundsException extends RuntimeException.

Q: ClassCastException — checked or unchecked?
A: UNCHECKED — extends RuntimeException.

Q: IOException — checked or unchecked?
A: CHECKED — extends Exception (not RuntimeException). Must be declared
   or caught.

Q: FileNotFoundException — checked or unchecked?
A: CHECKED — extends IOException extends Exception.

Q: SQLException — checked or unchecked?
A: CHECKED — extends Exception. Always requires try/catch or throws.

Q: StackOverflowError — checked or unchecked?
A: NEITHER — it is an ERROR (extends VirtualMachineError extends Error).
   Errors are uncaught in normal code.

Q: OutOfMemoryError — checked or unchecked?
A: NEITHER — it is an ERROR. Same category as StackOverflowError.

Q: ArithmeticException — checked or unchecked?
A: UNCHECKED — extends RuntimeException. Thrown for e.g. divide by zero.

Q: NumberFormatException — checked or unchecked?
A: UNCHECKED — extends IllegalArgumentException extends RuntimeException.

Q: IllegalArgumentException — checked or unchecked?
A: UNCHECKED — extends RuntimeException.

Q: IllegalStateException — checked or unchecked?
A: UNCHECKED — extends RuntimeException.

Q: CloneNotSupportedException — checked or unchecked?
A: CHECKED — extends Exception. Must be handled when overriding clone().

Q: InterruptedException — checked or unchecked?
A: CHECKED — extends Exception. Always handle when calling Thread.sleep(),
   wait(), or join().

SECTION 6: Access Modifiers — Yes or No?
==============================================================================

Q: Can a public class member be accessed from a different package?
A: YES — public is accessible from everywhere.

Q: Can a protected member be accessed from a different package?
A: YES — but ONLY through INHERITANCE (subclass). Not through a plain
   object reference from a different package.

Q: Can a default (package-private) member be accessed from a subclass
   in a different package?
A: NO — default access is package-scoped only. Subclasses in a different
   package cannot access it.

Q: Can a private member be accessed by the same class's static methods?
A: YES — private members are accessible within the SAME CLASS (all
   methods, static or instance). Only other classes are blocked.

Q: Can an inner class access private members of the outer class?
A: YES — non-static inner classes have full access to ALL members
   (including private) of the enclosing class.

Q: Can a static nested class access instance members of the outer class?
A: NO — static nested classes do NOT have an implicit reference to the
   outer class instance. They can only access STATIC members of the outer class.

SECTION 7: Generics — Yes or No?
==============================================================================

Q: Can you use a primitive type as a generic type parameter?
A: NO — generics only work with reference types. Use Integer, Double, etc.
   List<int> is a compile error. This is a consequence of type erasure.

Q: Does Java retain generic type information at runtime?
A: NO — generics are erased at compile time (type erasure). At runtime,
   List<String> and List<Integer> are both just List.

Q: Can you do instanceof check with a generic type? e.g., obj instanceof T
A: NO — due to type erasure, T is unknown at runtime. Compile error.
   You can do obj instanceof List<?> but not obj instanceof List<String>.

Q: Can a generic class extend another generic class?
A: YES — e.g., class Child<T> extends Parent<T> is valid.

Q: Can a generic method be in a non-generic class?
A: YES — generic methods are independent of whether the class is generic.
   e.g., public <T> T identity(T t) { return t; } in a plain class.

Q: Is List<String> a subtype of List<Object>?
A: NO — generics are INVARIANT. List<String> is NOT a subtype of List<Object>.
   Use List<? extends Object> for a read-only covariant reference.

Q: Can you add elements to a List<? extends Number>?
A: NO — upper-bounded wildcard (? extends T) is read-only (producer).
   You cannot add because the exact type is unknown.

Q: Can you add Integer elements to a List<? super Integer>?
A: YES — lower-bounded wildcard (? super T) allows adding T or subtypes.
   This follows the PECS rule: Producer Extends, Consumer Super.

Q: Can you create a generic array? e.g., new T[10]
A: NO — generic array creation is NOT allowed due to type erasure.
   Compile error. Use ArrayList<T> instead.

Q: Can two different generic instantiations be == equal?
A: Only their Class objects can be == equal (both are the same raw class).
   e.g., new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()
   is TRUE. The objects themselves are different instances.

Q: Can a bounded type parameter have multiple bounds?
A: YES — e.g., <T extends Comparable<T> & Serializable> is valid.
   Class bound must come first, interface bounds follow with &.

Q: Is it possible to have a generic exception class?
A: NO — you cannot have a generic class that extends Throwable.
   e.g., class MyException<T> extends Exception is a compile error.

SECTION 8: Java 8-21 Features — Yes or No?
==============================================================================

Q: Can a lambda expression throw a checked exception?
A: YES — but only if the functional interface's abstract method declares
   that checked exception in its throws clause. Otherwise, you must
   wrap it in a RuntimeException.

Q: Is a lambda expression an instance of a class?
A: YES — at runtime, a lambda is an object (instance generated via
   invokedynamic). But it has no accessible class name at source level.

Q: Can a lambda capture a local variable that is reassigned later?
A: NO — lambdas can only capture EFFECTIVELY FINAL local variables.
   Any reassignment of the variable after capture causes a compile error.

Q: Can a lambda capture an instance field that changes?
A: YES — lambdas capture "this" for instance fields. Since fields are
   accessed via the object reference (not copied), they can change freely.

Q: Is Optional a replacement for null?
A: NO — Optional is intended as a RETURN TYPE to signal "value may be absent".
   It should NOT be used as a method parameter or field type.

Q: Can Optional hold a null value?
A: NO — Optional.of(null) throws NullPointerException.
   Use Optional.ofNullable(value) to handle potential nulls.

Q: Are Streams reusable after a terminal operation?
A: NO — once a terminal operation is called, the stream is CLOSED.
   Reusing it throws IllegalStateException.

Q: Are Stream intermediate operations lazy?
A: YES — operations like filter(), map(), sorted() are lazy. They only
   execute when a terminal operation (forEach, collect, count) is called.

Q: Is Stream.forEach() guaranteed to be ordered?
A: NO — for parallel streams, forEach() may process elements in any order.
   Use forEachOrdered() to preserve encounter order.

Q: Can a default method in an interface access instance fields?
A: NO — interfaces have no instance fields. Default methods can only
   access what the interface defines (constants, other default/static methods)
   or what the implementing class exposes via the interface's abstract methods.

Q: Can a functional interface have more than one abstract method?
A: NO — a functional interface must have EXACTLY ONE abstract method.
   It can have default, static, and private methods in addition.

Q: Is @FunctionalInterface annotation mandatory for functional interfaces?
A: NO — it is optional. Without it, any interface with exactly one abstract
   method qualifies. @FunctionalInterface just adds a compile-time check.

Q: Can a record class extend another class?
A: NO — records implicitly extend java.lang.Record and Java does not allow
   multiple class inheritance. Records cannot extend any other class.

Q: Can a record implement an interface?
A: YES — records can implement any number of interfaces.

Q: Are record fields mutable?
A: NO — record components are implicitly private and final. Records are
   immutable by design.

Q: Can a sealed class be in a different package than its permitted subclasses?
A: NO — permitted subclasses must be in the SAME package (or same module)
   as the sealed class.

Q: Can var be used for method parameters?
A: NO — var is only for LOCAL variable declarations. It cannot be used for
   method parameters, fields, or return types.

Q: Can var be assigned null?
A: NO — the compiler needs to INFER the type from the initializer.
   var x = null; gives the compiler nothing to infer from — compile error.

Q: Is String::length a valid method reference?
A: YES — it is an instance method reference on the String type.
   Equivalent to (String s) -> s.length().

Q: Can you use method references for constructors?
A: YES — ClassName::new is a constructor reference.
   e.g., Supplier<List<String>> s = ArrayList::new;

SECTION 9: Concurrency — Yes or No?
==============================================================================

Q: Can two threads enter different synchronized methods on the same object
   at the same time?
A: NO — synchronized instance methods all lock on "this". Only one thread
   can hold the lock at a time, regardless of which synchronized method it is in.

Q: Can two threads enter synchronized methods on DIFFERENT objects
   at the same time?
A: YES — each object has its own monitor. Different objects = different locks
   = no mutual exclusion between them.

Q: Can a thread re-enter a synchronized block it already holds the lock for?
A: YES — Java's synchronized is REENTRANT. A thread that already holds
   a lock can acquire it again without deadlocking.

Q: Does ReentrantLock require manual unlock?
A: YES — unlike synchronized, ReentrantLock must be explicitly unlocked
   in a finally block. Forgetting to unlock causes deadlocks.

Q: Is AtomicInteger.incrementAndGet() thread-safe?
A: YES — AtomicInteger uses CAS (Compare-And-Swap) hardware instructions
   for lock-free atomic operations. Fully thread-safe.

Q: Can synchronized(null) be used?
A: NO — synchronizing on a null reference throws NullPointerException.

Q: Can deadlock occur with a single thread?
A: NO — deadlock requires at least TWO threads holding locks and waiting
   for each other. A single thread cannot deadlock with itself (locks are
   reentrant).

Q: Does making a method synchronized prevent all race conditions?
A: NO — synchronization only protects threads using THAT SAME LOCK.
   If some code accesses shared state without the lock, races still occur.

Q: Can a daemon thread prevent JVM shutdown?
A: NO — the JVM shuts down when all NON-DAEMON threads finish.
   Daemon threads are killed automatically at JVM shutdown.

Q: Does Thread.sleep() release the object monitor lock?
A: NO — sleep() pauses the thread but holds any locks it has acquired.
   Use wait() to release the lock while pausing.

Q: Is ConcurrentHashMap null-key safe?
A: NO — ConcurrentHashMap does NOT allow null keys or null values.
   This is by design to avoid ambiguity in concurrent contexts.

Q: Can you call notify() without holding the lock?
A: NO — notify() and notifyAll() MUST be called from within a synchronized
   block on the same object. Otherwise IllegalMonitorStateException is thrown.

Q: Is ExecutorService.shutdown() immediate?
A: NO — shutdown() initiates an orderly shutdown: previously submitted
   tasks are executed, but no new tasks are accepted. Use shutdownNow()
   to attempt immediate termination.

Q: Can a Future.get() block indefinitely?
A: YES — Future.get() blocks until the task completes. Use
   get(timeout, unit) to set a time limit and avoid indefinite blocking.

Q: Is synchronized keyword reentrant in Java?
A: YES — a thread can enter a synchronized block/method it already holds.
   This prevents self-deadlock and is guaranteed by the Java spec.


==============================================================================
SECTION 10: JVM, Memory & Class Loading — Yes or No?
==============================================================================

Q: Are String literals stored in the heap?
A: YES — the String Pool is part of the heap (moved to heap in Java 7+;
   was in PermGen before). String literals go into the pool in the heap.

Q: Does new String("hello") create two objects?
A: YES (potentially) — one object in the String pool (if "hello" is not
   already there) and one on the heap from new. If already in pool, only one
   new heap object is created.

Q: Is the String pool shared across threads?
A: YES — the String pool is a JVM-wide shared structure. All threads
   share the same pool.

Q: Can you force a String into the pool?
A: YES — call string.intern(). It returns the pool reference, adding the
   string to the pool if not already there.

Q: Does a class get loaded as soon as the JVM starts?
A: NO — classes are loaded LAZILY, only when first needed (first access
   of a static member, first instantiation, or Class.forName()).

Q: Does accessing Foo.class trigger static initialization?
A: NO — using the class literal (Foo.class) triggers class LOADING but
   NOT static initialization. Accessing a static field or creating an
   instance triggers initialization.

Q: Can a class be loaded by two different ClassLoaders?
A: YES — and they are treated as DIFFERENT classes by the JVM even if
   the bytecode is identical. This is the basis of classloader isolation
   in app servers.

Q: Is the JVM stack shared between threads?
A: NO — each thread has its OWN private stack. Heap is shared across threads.

Q: Can an object be garbage collected while a method is still running on it?
A: NO — while a method is executing on an object, there is a reference
   to it on the call stack, keeping it reachable. GC won't collect it.

Q: Does making an object reference null guarantee it gets garbage collected?
A: NO — GC only collects objects with NO reachable strong references.
   Setting one reference to null helps, but other references to the same
   object may still exist. GC timing is also not guaranteed.

Q: Is the Metaspace (Java 8+) bounded by default?
A: NO — by default, Metaspace grows as needed up to native memory limits.
   Unlike PermGen, it doesn't have a fixed default cap. Set -XX:MaxMetaspaceSize
   explicitly to bound it.

Q: Can StackOverflowError be caught?
A: YES — it extends Error which extends Throwable. You can catch it with
   catch (StackOverflowError e). But it generally indicates a design problem.


==============================================================================
SECTION 11: Immutability & Cloning — Yes or No?
==============================================================================

Q: Is String immutable in Java?
A: YES — String's internal char array is final and private with no setters.
   Every "modification" produces a new String object.

Q: Can you make a class immutable without using final?
A: PARTIALLY — you need: private fields, no setters, defensive copies in
   constructor and getters, no overridable methods. But without final on the
   class, subclasses could break immutability.

Q: Does making all fields final make a class immutable?
A: NO — final references prevent reassignment but not mutation of the
   referenced object. e.g., a final List can still have items added.

Q: Does Object.clone() do a deep copy?
A: NO — Object.clone() performs a SHALLOW copy. Nested objects are NOT
   cloned; only the references are copied. Deep copy requires custom logic.

Q: Must a class implement Cloneable to be cloned?
A: YES — calling clone() on a class that doesn't implement Cloneable throws
   CloneNotSupportedException. Cloneable is a marker interface.

Q: Can an immutable object be used safely in multi-threaded environments?
A: YES — immutable objects are inherently thread-safe. Since their state
   cannot change, no synchronization is needed.

Q: Is Integer immutable?
A: YES — all wrapper classes (Integer, Long, Double, etc.) are immutable.

Q: Is StringBuilder immutable?
A: NO — StringBuilder is MUTABLE. That is its purpose (unlike String).


==============================================================================
SECTION 12: Classic Trap Topics — Yes or No? (Most Frequently Missed)
==============================================================================

--- Trap 1: finally vs return ---

Q: If a method has both a return in try and a return in finally, which return wins?
A: FINALLY wins. The return in finally overrides the return in try. This is
   a known Java trap — the try return value is discarded.
   Example:
     int x() { try { return 1; } finally { return 2; } }  // returns 2

Q: Does finally always execute?
A: YES — with one exception: if the JVM is killed (System.exit() or hard
   crash), finally does NOT run. In all normal flows (including exceptions),
   finally always executes.

Q: Can finally suppress an exception thrown in try?
A: YES — if finally also throws an exception, the original try exception is
   lost (silently suppressed). This is a major silent bug trap.

Q: Can you use return inside a finally block?
A: YES — it compiles and runs. But doing so is a terrible practice because
   it hides the original exception or return value from try/catch.

--- Trap 2: try-with-resources ---

Q: Does try-with-resources require a catch or finally block?
A: NO — try-with-resources can stand alone: try (Resource r = ...) {}
   The resource is closed automatically. catch and finally are optional.

Q: If both the try body and the close() method throw exceptions, which is kept?
A: The try body exception is kept; the close() exception is SUPPRESSED
   (attached to primary via Throwable.addSuppressed). The opposite of the
   plain finally trap.

Q: Can you open multiple resources in one try-with-resources?
A: YES — try (A a = new A(); B b = new B()) {}. They close in reverse order
   (B closes first, then A).

Q: Does AutoCloseable.close() have to throw a checked exception?
A: NO — close() can declare any exception or none. AutoCloseable.close()
   declares throws Exception, but Closeable.close() declares throws IOException.
   You can override it to throw nothing.

--- Trap 3: Integer / Wrapper Cache Ranges ---

Q: Does Integer cache values only from -128 to 127?
A: YES (by default). Integer.valueOf(127) == Integer.valueOf(127) is TRUE.
   Integer.valueOf(128) == Integer.valueOf(128) is FALSE (different objects).

Q: Does Long have the same cache range as Integer (-128 to 127)?
A: YES — Long also caches -128 to 127. Same trap applies.

Q: Does Double cache any values?
A: NO — Double (and Float) do NOT cache any values. Double.valueOf(1.0)
   always creates a new object.

Q: Does Character cache values 0 to 127?
A: YES — Character caches values 0–127 (the ASCII range).

Q: Can the Integer cache upper bound be changed?
A: YES — the upper bound can be increased via JVM flag
   -XX:AutoBoxCacheMax=<size>. The lower bound (-128) is always fixed.

--- Trap 4: Default Method Diamond Problem ---

Q: If two interfaces both define a default method with the same signature,
   and a class implements both — does it compile?
A: NO — the class MUST override the method to resolve the conflict. The
   compiler forces you to pick one or provide your own implementation.

Q: Can a class call a specific interface's default method to resolve a conflict?
A: YES — use InterfaceName.super.method(). Example:
   InterfaceA.super.greet(); inside the overriding class.

Q: If a class inherits a concrete method AND an interface has a default with
   the same signature, does the class method or the default win?
A: The CLASS method ALWAYS wins over an interface default. Concrete class
   trumps interface default.

Q: Can an interface override another interface's default method?
A: YES — an interface can re-declare a default method (or declare it abstract),
   which then takes precedence for classes implementing that child interface.

--- Trap 5: Switch Expressions (Java 14+) ---

Q: Can a switch expression (not statement) be used where a value is expected?
A: YES — switch expressions produce a value: int x = switch (day) { case MON -> 1; ... }

Q: Does a switch expression require a default case?
A: YES (usually) — if the switch does not cover all possible values, a default
   is required or the compiler will refuse. For enums covering all constants,
   default is optional.

Q: Can a switch case in the new arrow syntax fall through to the next case?
A: NO — arrow cases (case X -> ...) do NOT fall through. Traditional colon
   cases (case X:) still do fall through unless you use break.

Q: Can a switch expression throw an exception instead of yielding a value?
A: YES — you can use throw inside a switch expression arm. Example:
   case UNKNOWN -> throw new IllegalArgumentException("bad value");

--- Trap 6: Text Blocks (Java 15+) ---

Q: Are leading whitespace characters in a text block significant?
A: NO (by default) — Java strips the common leading indentation automatically
   based on the position of the closing """. This is called "incidental whitespace."

Q: Can a text block contain a backslash escape like \n?
A: YES — text blocks support all Java escape sequences. They also support
   \<line-terminator> (line continuation) and \s (to prevent whitespace trimming).

Q: Does a text block start on the same line as the opening """?
A: NO — the opening """ must be followed by a newline. Content starts on
   the NEXT line. A text block cannot begin on the same line as opening """.

--- Trap 7: Pattern Matching instanceof (Java 16+) ---

Q: In pattern matching instanceof, is the bound variable available in the
   else branch?
A: NO — the variable is only in scope when the instanceof is TRUE (the if-true
   branch). It is NOT available in the else branch.

Q: Can you use pattern matching instanceof with a final variable?
A: YES — the bound pattern variable is effectively final by default.

Q: Does pattern matching instanceof still return false for null?
A: YES — null instanceof Anything always returns FALSE. Pattern matching
   does not change this rule.

Q: Can you combine pattern matching instanceof with && in a single if?
A: YES — this is a key use case: if (obj instanceof String s && s.length() > 5)
   The variable s is in scope for the right side of &&.

--- Trap 8: char / byte / short Arithmetic Promotion ---

Q: What is the type of (byte + byte) in Java?
A: int — Java promotes byte, short, and char to int before ANY arithmetic.
   byte a = 1; byte b = 2; byte c = a + b; // COMPILE ERROR — result is int.

Q: Can you assign the result of (char + char) to a char without a cast?
A: NO — char + char produces an int. You need an explicit cast: (char)(a + b).

Q: Is (byte)(byte + byte) safe to use?
A: COMPILES, yes. But it can silently truncate values — it is an explicit
   narrowing cast, so the compiler allows it, but overflow is silent.

Q: Does Java promote float to double automatically?
A: YES — in mixed float/double expressions, float is promoted to double.
   But int is NOT automatically promoted to float — you need a cast or literal
   suffix (1.0f).
