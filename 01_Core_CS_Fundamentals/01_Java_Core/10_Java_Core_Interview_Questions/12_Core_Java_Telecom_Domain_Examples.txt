SECTION 1: OOP FUNDAMENTALS
==============================================================================

------------------------------------------------------------------------------
1.1 CLASS & OBJECT
------------------------------------------------------------------------------
Concept : A class is a blueprint; an object is a real instance.

Telecom : "Subscriber" is a class (a template). Each actual customer
          (John, Mary, Bob) is an object — a live instance with their own
          phone number, balance, and plan.

Code sketch:
  class Subscriber {
      String msisdn;          // mobile number
      String name;
      double balance;
  }
  Subscriber john = new Subscriber();
  john.msisdn = "9876543210";

Interview answer:
  "In a telecom system, Subscriber is the class that defines what a customer
   looks like — fields like MSISDN, name, balance. Every actual customer
   such as John or Mary is a separate object in memory with their own data."

------------------------------------------------------------------------------
1.2 ENCAPSULATION
------------------------------------------------------------------------------
Concept : Hide internal state; expose only controlled access via getters/setters.

Telecom : A SIM card's IMSI (internal identifier) is never exposed to the
          subscriber. You only see your phone number, not the IMSI stored
          inside the chip. The carrier controls how data is read/written.

Code sketch:
  class SimCard {
      private String imsi;           // hidden — never exposed directly
      private boolean active;

      public boolean isActive() { return active; }

      public void activate(String authCode) {
          if (isValidAuthCode(authCode)) {
              this.active = true;
          }
      }
      // No public setter for imsi — only the carrier can set it
  }

Interview answer:
  "Encapsulation in telecom: a SimCard hides its IMSI number behind private
   access. External code cannot directly read or change the IMSI — it can
   only call isActive() or activate(). This prevents subscribers from
   tampering with internal SIM state, just like real SIM cards."

------------------------------------------------------------------------------
1.3 INHERITANCE
------------------------------------------------------------------------------
Concept : Child class inherits fields and methods from parent; adds specialization.

Telecom : All telecom products are BillingAccount at the base. A Prepaid
          account and a Postpaid account both inherit billing logic but
          behave differently for payments.

Code sketch:
  class BillingAccount {
      String accountId;
      double balance;
      void generateInvoice() { /* common logic */ }
  }

  class PrepaidAccount extends BillingAccount {
      void recharge(double amount) { balance += amount; }
  }

  class PostpaidAccount extends BillingAccount {
      double creditLimit;
      void billMonthlyUsage(double usage) { balance -= usage; }
  }

Interview answer:
  "In telecom billing, we have a BillingAccount base class with common
   invoice logic. PrepaidAccount and PostpaidAccount extend it. They
   inherit generateInvoice() but add their own recharge() and
   billMonthlyUsage() methods. This avoids duplicating billing logic
   across both account types."

------------------------------------------------------------------------------
1.4 POLYMORPHISM
------------------------------------------------------------------------------
Concept : One interface, many implementations. Method overriding at runtime.

Telecom : A NetworkService interface is implemented by VoiceService,
          DataService, and SMSService. A single method processRequest()
          behaves differently for each — a call setup is different from
          an SMS delivery.

Code sketch:
  interface NetworkService {
      void processRequest(Request request);
  }

  class VoiceService implements NetworkService {
      public void processRequest(Request r) { /* set up voice call */ }
  }

  class DataService implements NetworkService {
      public void processRequest(Request r) { /* route data packet */ }
  }

  class SMSService implements NetworkService {
      public void processRequest(Request r) { /* deliver SMS via SMSC */ }
  }

  // Polymorphic call
  NetworkService service = getServiceForRequest(request);
  service.processRequest(request);  // right implementation runs at runtime

Interview answer:
  "In our telecom platform, the request router holds a NetworkService
   reference. At runtime it could point to VoiceService, DataService, or
   SMSService. The same processRequest() call invokes different logic
   depending on the actual object — that's runtime polymorphism. We never
   need to write if-else for service type; the JVM dispatches the right one."

------------------------------------------------------------------------------
1.5 ABSTRACTION
------------------------------------------------------------------------------
Concept : Hide implementation details; expose only what the client needs.

Telecom : A subscriber just dials a number. They don't know about SS7
          signaling, HLR lookups, or MSC routing. The network abstracts
          all that — "just dial, we handle the rest."

Code sketch:
  abstract class CallProcessor {
      // Client only calls this
      public final void initiateCall(String fromMsisdn, String toMsisdn) {
          authenticateSubscriber(fromMsisdn);
          routeThroughNetwork(fromMsisdn, toMsisdn);
          startBillingSession(fromMsisdn);
      }
      protected abstract void authenticateSubscriber(String msisdn);
      protected abstract void routeThroughNetwork(String from, String to);
      protected abstract void startBillingSession(String msisdn);
  }

Interview answer:
  "initiateCall() is the abstracted API — the caller just passes two MSISDNs.
   Internally it authenticates via HLR, routes via the switching network,
   and starts a CDR billing session. None of that complexity leaks to the
   caller. The abstract methods force each network type (2G/4G/5G) to
   implement their own routing strategy."

------------------------------------------------------------------------------
1.6 INTERFACE vs ABSTRACT CLASS
------------------------------------------------------------------------------
Concept : Interface = pure contract (what to do). Abstract class = partial
          implementation + shared state (how to do some things).

Telecom Example:
  Interface  -> Billable  (any entity that can be billed)
  Abstract   -> TelecomProduct (common fields like productId, subscriberId)

Code sketch:
  interface Billable {
      double calculateCharge();
      String getInvoiceDescription();
  }

  abstract class TelecomProduct implements Billable {
      protected String productId;
      protected String subscriberId;
      protected LocalDate activationDate;

      // Shared logic for all products
      public boolean isActive() {
          return activationDate != null && activationDate.isBefore(LocalDate.now());
      }
      // calculateCharge() left to concrete subclasses
  }

  class VoicePlan extends TelecomProduct {
      private int includedMinutes;
      public double calculateCharge() { /* voice-specific pricing */ }
      public String getInvoiceDescription() { return "Voice Plan - " + productId; }
  }

  class DataPlan extends TelecomProduct {
      private long includedGB;
      public double calculateCharge() { /* data-specific pricing */ }
      public String getInvoiceDescription() { return "Data Plan " + includedGB + "GB"; }
  }

Interview answer:
  "Billable is an interface — any product (voice, data, SMS, roaming) must
   implement it, but they share no code. TelecomProduct is abstract — it
   holds common fields like productId and subscriberId and provides isActive()
   since that logic is identical for all products. Concrete classes like
   VoicePlan only implement the charging logic specific to them."


==============================================================================
SECTION 2: STRING AND IMMUTABILITY
==============================================================================

------------------------------------------------------------------------------
2.1 STRING IMMUTABILITY
------------------------------------------------------------------------------
Concept : String objects cannot be changed after creation. Every modification
          creates a new object.

Telecom : An MSISDN (mobile number) is immutable — once assigned to a SIM,
          it doesn't change. If a subscriber ports to another carrier, a NEW
          MSISDN record is created; the old one isn't modified.

Code sketch:
  String msisdn = "9876543210";
  String withCountryCode = "+91" + msisdn;  // new String object; msisdn unchanged
  System.out.println(msisdn);              // still "9876543210"

Interview answer:
  "MSISDN is a perfect analogy for String immutability. Once a number is
   assigned, you don't mutate it — you create a new formatted string like
   '+91' + msisdn. The original msisdn string is untouched. This is why
   String is safe to use as a HashMap key in subscriber lookup tables — its
   hashCode never changes mid-lookup."

------------------------------------------------------------------------------
2.2 STRING POOL
------------------------------------------------------------------------------
Concept : String literals are shared from a pool; new String() bypasses the pool.

Telecom : Network codes like MCC (Mobile Country Code) "404" and MNC
          (Mobile Network Code) "10" are fixed constants shared everywhere.
          Using literals puts them in the pool — one copy for the whole JVM.

Code sketch:
  String mcc1 = "404";    // from string pool
  String mcc2 = "404";    // same pool reference
  System.out.println(mcc1 == mcc2);      // TRUE — same object
  System.out.println(mcc1.equals(mcc2)); // TRUE — same content

  String mcc3 = new String("404");       // new heap object, outside pool
  System.out.println(mcc1 == mcc3);      // FALSE — different objects

Interview answer:
  "MCC '404' is used millions of times per second in routing tables. String
   pooling means all those references point to the same object in memory —
   huge efficiency gain. That's why we always use literals for fixed network
   codes and always compare them with equals(), not ==, because new String()
   bypasses the pool."

------------------------------------------------------------------------------
2.3 STRINGBUILDER vs STRING (in loops)
------------------------------------------------------------------------------
Concept : Use StringBuilder for repeated concatenations; String + in a loop
          creates excessive garbage.

Telecom : Building a CDR (Call Detail Record) row by appending caller ID,
          duration, timestamp, and charge fields — done millions of times
          per hour. StringBuilder is critical for performance.

Code sketch:
  // BAD — creates a new String object on every + in a billing engine loop
  String cdr = "";
  cdr += callerId + "|";
  cdr += duration + "|";
  cdr += timestamp + "|";
  cdr += charge;   // 4 new String objects created

  // GOOD — one mutable buffer, one final toString()
  StringBuilder cdr = new StringBuilder();
  cdr.append(callerId).append("|")
     .append(duration).append("|")
     .append(timestamp).append("|")
     .append(charge);
  String cdrRow = cdr.toString();

Interview answer:
  "A CDR system processes millions of records per hour. Using String + in
   a loop creates a new String object per append — exponential memory
   pressure. StringBuilder uses a single char array buffer and only creates
   the final String once. In our billing system, switching from String + to
   StringBuilder cut GC pause time by 40%."

SECTION 3: COLLECTIONS FRAMEWORK
==============================================================================

------------------------------------------------------------------------------
3.1 ARRAYLIST vs LINKEDLIST
------------------------------------------------------------------------------
Concept : ArrayList — fast random access, slow middle inserts.
          LinkedList — fast inserts/deletes, slow random access.

Telecom :
  ArrayList -> Subscriber list for sequential billing report (random access needed)
  LinkedList -> Call queue in an IVR system where calls are added/removed
                from front and back constantly

Code sketch:
  // ArrayList: best when we iterate over all subscribers for invoicing
  List<Subscriber> billingBatch = new ArrayList<>();
  billingBatch.get(5000);  // O(1) direct access by index

  // LinkedList: best for a call waiting queue (add to tail, remove from head)
  Deque<Call> callQueue = new LinkedList<>();
  callQueue.offer(incomingCall);   // add to tail
  Call nextCall = callQueue.poll(); // remove from head — O(1)

Interview answer:
  "For batch billing, we load all subscribers into an ArrayList and iterate
   sequentially — O(1) get(i) makes it fast. For the IVR call queue, we
   use LinkedList as a Deque — calls arrive at the tail and agents pick from
   the head. Insertions and removals are O(1) at both ends with LinkedList,
   which is critical when thousands of calls are queued per second."

------------------------------------------------------------------------------
3.2 HASHMAP
------------------------------------------------------------------------------
Concept : Key-value store with O(1) average lookup using hashCode + equals.

Telecom : Subscriber lookup by MSISDN. Millions of requests per second need
          O(1) access to subscriber records — HashMap is the in-memory cache.

Code sketch:
  Map<String, Subscriber> subscriberCache = new HashMap<>();

  // Load subscriber into cache
  subscriberCache.put("9876543210", new Subscriber("John", "Postpaid"));

  // O(1) lookup on every incoming call or data request
  Subscriber sub = subscriberCache.get(incomingMsisdn);
  if (sub == null) {
      sub = subscriberRepository.findByMsisdn(incomingMsisdn); // DB fallback
      subscriberCache.put(incomingMsisdn, sub);
  }

Interview answer:
  "In our HLR (Home Location Register) simulation, we cache subscriber data
   in a HashMap keyed by MSISDN. On every call setup, we do an O(1) lookup
   instead of a database query. String's hashCode is stable because String
   is immutable — safe as a HashMap key. We override equals() and hashCode()
   on any custom key objects to prevent lookup failures."

------------------------------------------------------------------------------
3.3 TREEMAP (SORTED ORDER)
------------------------------------------------------------------------------
Concept : TreeMap maintains keys in natural sorted order; O(log n) operations.

Telecom : Tariff plans sorted by price for display. Rate tiers sorted by
          data usage thresholds so the billing engine can do floor/ceiling
          lookups efficiently.

Code sketch:
  // Rate tiers: key = GB threshold, value = rate per extra GB
  TreeMap<Integer, Double> dataTiers = new TreeMap<>();
  dataTiers.put(5,  0.10);   // 0-5 GB: $0.10/GB
  dataTiers.put(20, 0.08);   // 5-20 GB: $0.08/GB
  dataTiers.put(50, 0.05);   // 20-50 GB: $0.05/GB

  // Find the rate tier for a subscriber who used 12 GB
  int usedGB = 12;
  Map.Entry<Integer, Double> tier = dataTiers.floorEntry(usedGB);
  // Returns entry (5, 0.10) — the highest threshold <= 12

Interview answer:
  "Rate tiers are a perfect TreeMap use case. The key is the GB threshold
   and the value is the unit price. TreeMap keeps tiers sorted automatically.
   When a subscriber uses 12 GB, floorEntry(12) gives us the correct tier
   (5 GB threshold -> $0.10/GB) in O(log n) — far cleaner than scanning
   a list or a chain of if-else blocks."

------------------------------------------------------------------------------
3.4 HASHSET / LINKEDHASHSET
------------------------------------------------------------------------------
Concept : HashSet — unique elements, no order. LinkedHashSet — unique +
          insertion order.

Telecom :
  HashSet      -> Blocked number list. Fast O(1) check: "is this MSISDN blocked?"
  LinkedHashSet -> Recently dialed numbers in insertion order (most recent last)

Code sketch:
  // HashSet for spam/fraud blocked list
  Set<String> blockedNumbers = new HashSet<>();
  blockedNumbers.add("9999999999");
  blockedNumbers.add("8888888888");

  // O(1) block check on every outgoing call
  if (blockedNumbers.contains(destinationMsisdn)) {
      throw new CallBlockedException("Number is blocked: " + destinationMsisdn);
  }

  // LinkedHashSet for call history in order
  Set<String> recentlyDialed = new LinkedHashSet<>();
  recentlyDialed.add("1111111111");
  recentlyDialed.add("2222222222");
  recentlyDialed.add("1111111111"); // duplicate — ignored, order preserved

Interview answer:
  "The fraud engine uses a HashSet for blocked MSISDNs — O(1) contains()
   check on every call. For the 'recently dialed' UI feature, we use
   LinkedHashSet — it prevents duplicates (no point showing the same number
   twice) and maintains the order calls were placed. Both are better than
   a List here: HashSet has no order concern, LinkedHashSet adds order."

------------------------------------------------------------------------------
3.5 QUEUE / PRIORITY QUEUE
------------------------------------------------------------------------------
Concept : Queue = FIFO. PriorityQueue = highest-priority element served first.

Telecom :
  Queue         -> FIFO SMS delivery queue
  PriorityQueue -> Emergency call queue — 999/911 calls jump ahead of normal calls

Code sketch:
  // Emergency call queue — higher priority calls served first
  PriorityQueue<Call> emergencyQueue = new PriorityQueue<>(
      Comparator.comparingInt(Call::getPriority).reversed()
  );

  emergencyQueue.offer(new Call("9876543210", 1));   // normal call, priority 1
  emergencyQueue.offer(new Call("1111111111", 10));  // emergency, priority 10
  emergencyQueue.offer(new Call("2222222222", 5));   // urgent, priority 5

  Call next = emergencyQueue.poll();  // returns the 999 call (priority 10) first

Interview answer:
  "Emergency services can't wait in a FIFO queue. We use PriorityQueue with
   a Comparator that sorts by call priority descending. A 999 emergency call
   with priority 10 is dequeued before a normal call with priority 1, even
   if the normal call arrived earlier. poll() always gives the highest
   priority call in O(log n)."

------------------------------------------------------------------------------
3.6 CONCURRENTHASHMAP
------------------------------------------------------------------------------
Concept : Thread-safe HashMap without full synchronization. Segment-level
          locking (or CAS in Java 8+). Allows concurrent reads always and
          concurrent writes to different buckets.

Telecom : Real-time active call registry. Hundreds of threads (one per
          network node) simultaneously read/write the active call table —
          which calls are live, their duration, and their billing state.

Code sketch:
  ConcurrentHashMap<String, ActiveCall> activeCallRegistry = new ConcurrentHashMap<>();

  // Thread from Node A (adding new call)
  activeCallRegistry.put(callId, new ActiveCall(callerId, calleeId));

  // Thread from Billing (reading duration for CDR generation)
  ActiveCall call = activeCallRegistry.get(callId);

  // Atomic update — increment duration counter without a lock
  activeCallRegistry.compute(callId, (id, c) -> {
      c.incrementDuration();
      return c;
  });

  // Remove on call end
  activeCallRegistry.remove(callId);

Interview answer:
  "The active call registry is the hottest data structure in a telco. Every
   second, nodes add new calls, billing threads read them, and call-end
   events remove them — all concurrently. ConcurrentHashMap allows unlimited
   concurrent reads and concurrent writes to different buckets. We never
   block a billing read because a node is registering a new call in a
   different bucket."

SECTION 4: GENERICS
==============================================================================

------------------------------------------------------------------------------
4.1 GENERIC CLASS
------------------------------------------------------------------------------
Concept : Type-safe containers that work for any type, checked at compile time.

Telecom : A paginated response wrapper used by every telecom API —
          whether returning Subscribers, CDRs, or Invoices.

Code sketch:
  class PagedResponse<T> {
      private List<T> data;
      private int totalCount;
      private int page;
      private int pageSize;

      // Works for any return type — compile-time safety
      public List<T> getData() { return data; }
  }

  PagedResponse<Subscriber> subscribers = subscriberService.getAll(page, size);
  PagedResponse<Invoice>    invoices    = billingService.getInvoices(page, size);

Interview answer:
  "Every telecom API returns paginated data — subscribers, CDRs, invoices.
   Rather than writing PagedSubscriberResponse, PagedInvoiceResponse etc.,
   we use a generic PagedResponse<T>. The type parameter T is checked at
   compile time, so getSubscribers() returns PagedResponse<Subscriber> —
   no cast needed, no ClassCastException at runtime."

------------------------------------------------------------------------------
4.2 BOUNDED WILDCARDS (? extends / ? super)
------------------------------------------------------------------------------
Concept : extends = read (producer), super = write (consumer). PECS rule.

Telecom :
  extends -> reading from a list of any TelecomProduct subtypes for reporting
  super   -> writing into a collection that can accept any specific plan type

Code sketch:
  // PRODUCER (read-only) — calculate total revenue from any product list
  double totalRevenue(List<? extends TelecomProduct> products) {
      return products.stream()
                     .mapToDouble(TelecomProduct::calculateCharge)
                     .sum();
  }

  // Works for List<VoicePlan>, List<DataPlan>, List<TelecomProduct> — all safe

  // CONSUMER (write) — copy specific plans into a general product bucket
  void addToBucket(List<? super VoicePlan> bucket, VoicePlan plan) {
      bucket.add(plan);
  }

  List<TelecomProduct> allProducts = new ArrayList<>();
  addToBucket(allProducts, voicePlan);   // valid — TelecomProduct is super of VoicePlan

Interview answer:
  "PECS: Producer Extends, Consumer Super. The revenue calculator reads from
   the list — it's a producer of data for us — so we use ? extends
   TelecomProduct. It accepts List<VoicePlan>, List<DataPlan>, or any subtype.
   The addToBucket method writes into the list — consumer — so ? super VoicePlan
   accepts List<TelecomProduct> or any ancestor. This gives flexibility
   without losing type safety."

SECTION 5: EXCEPTION HANDLING
==============================================================================

------------------------------------------------------------------------------
5.1 CHECKED vs UNCHECKED EXCEPTIONS
------------------------------------------------------------------------------
Concept : Checked = must be declared/caught (recoverable). Unchecked = runtime
          programming errors.

Telecom :
  Checked   -> InsufficientBalanceException (recoverable — top up the account)
  Checked   -> NetworkUnavailableException  (recoverable — retry later)
  Unchecked -> NullPointerException         (programming error — msisdn was null)
  Unchecked -> IllegalArgumentException     (bad input — negative recharge amount)

Code sketch:
  // Checked — callers MUST handle it
  class InsufficientBalanceException extends Exception {
      private double shortfall;
      public InsufficientBalanceException(double shortfall) {
          super("Balance short by: " + shortfall);
          this.shortfall = shortfall;
      }
  }

  void deductCharge(String msisdn, double charge) throws InsufficientBalanceException {
      Subscriber sub = getSubscriber(msisdn);
      if (sub.getBalance() < charge) {
          throw new InsufficientBalanceException(charge - sub.getBalance());
      }
      sub.deduct(charge);
  }

  // Caller is forced to handle it
  try {
      billingService.deductCharge("9876543210", 29.99);
  } catch (InsufficientBalanceException e) {
      notificationService.sendLowBalanceAlert(msisdn, e.getShortfall());
  }

Interview answer:
  "InsufficientBalanceException is checked because it's a business condition
   the caller must handle — they might alert the user or suspend the service.
   Hiding it as unchecked would let callers silently ignore it. An
   IllegalArgumentException for a negative recharge amount is unchecked —
   that's a programming bug in the caller, not a recoverable business scenario."

------------------------------------------------------------------------------
5.2 CUSTOM EXCEPTION HIERARCHY
------------------------------------------------------------------------------
Concept : Domain-specific exception hierarchy gives callers fine-grained control.

Telecom :
  TelecomException (base)
  ├── BillingException
  │   ├── InsufficientBalanceException
  │   └── PaymentGatewayException
  └── NetworkException
      ├── SignalLostException
      └── RoamingNotPermittedException

Code sketch:
  class TelecomException extends Exception {
      private String errorCode;
      public TelecomException(String errorCode, String message) {
          super(message);
          this.errorCode = errorCode;
      }
  }
  class BillingException    extends TelecomException { ... }
  class NetworkException     extends TelecomException { ... }
  class InsufficientBalanceException extends BillingException { ... }

  // Caller can catch at any level of specificity
  try { ... }
  catch (InsufficientBalanceException e) { /* top-up prompt */    }
  catch (BillingException e)            { /* generic billing err */}
  catch (TelecomException e)            { /* last resort */        }

Interview answer:
  "We built a TelecomException hierarchy. A billing microservice catches
   InsufficientBalanceException to send a top-up alert. An API gateway
   catches TelecomException at the top level to return an error code to the
   mobile app. This hierarchy lets each layer catch exactly the exceptions
   it can handle and let the rest propagate."

------------------------------------------------------------------------------
5.3 FINALLY AND TRY-WITH-RESOURCES
------------------------------------------------------------------------------
Concept : finally always runs; try-with-resources auto-closes resources.

Telecom : A CDR file writer or a database connection for rating — MUST be
          closed even if an exception occurs during writing.

Code sketch:
  // Old way — manual finally (error-prone: what if close() also throws?)
  CDRWriter writer = null;
  try {
      writer = new CDRWriter("/data/cdrs/batch_001.cdr");
      writer.write(callRecords);
  } catch (IOException e) {
      log.error("CDR write failed", e);
  } finally {
      if (writer != null) writer.close();
  }

  // Modern way — try-with-resources (auto-close, suppressed exceptions handled)
  try (CDRWriter writer = new CDRWriter("/data/cdrs/batch_001.cdr")) {
      writer.write(callRecords);
  } catch (IOException e) {
      log.error("CDR write failed", e);
  }
  // writer.close() is called automatically — even if write() throws

Interview answer:
  "CDR files in a billing system must be closed properly — an unclosed file
   means corrupted CDRs and wrong invoices. try-with-resources guarantees
   CDRWriter.close() is called even if write() throws. If both write() and
   close() throw, the close() exception is suppressed and attached to the
   primary exception, not silently swallowed — unlike the old finally pattern."


==============================================================================
SECTION 6: MULTITHREADING AND CONCURRENCY
==============================================================================

------------------------------------------------------------------------------
6.1 THREAD LIFECYCLE AND CREATION
------------------------------------------------------------------------------
Concept : Thread states: NEW -> RUNNABLE -> RUNNING -> BLOCKED/WAITING -> TERMINATED

Telecom : Each incoming call creates a thread. The thread authenticates the
          subscriber, waits for HLR response (WAITING), receives it
          (RUNNABLE), then processes the call (RUNNING).

Code sketch:
  // Runnable approach — preferred (doesn't waste Thread inheritance)
  class CallProcessor implements Runnable {
      private Call call;
      public CallProcessor(Call call) { this.call = call; }

      @Override
      public void run() {
          authenticate(call.getCaller());      // may block on HLR
          routeCall(call);
          startBilling(call);
      }
  }

  Thread callThread = new Thread(new CallProcessor(incomingCall));
  callThread.start();

  // Better — use ExecutorService (thread pool) instead of raw threads
  ExecutorService callPool = Executors.newFixedThreadPool(200);
  callPool.submit(new CallProcessor(incomingCall));

Interview answer:
  "Raw Thread creation per call doesn't scale — a million simultaneous calls
   means a million threads and the JVM crashes. We use ExecutorService with
   a fixed pool of 200 threads. Incoming calls are submitted as tasks; the
   pool manages thread lifecycle, reuse, and queue management automatically."

------------------------------------------------------------------------------
6.2 SYNCHRONIZED
------------------------------------------------------------------------------
Concept : Only one thread at a time can execute a synchronized method/block.

Telecom : Shared balance deduction — two threads (voice charge + data charge)
          must not deduct simultaneously from the same account balance.

Code sketch:
  class SubscriberAccount {
      private double balance;

      // Without synchronized — race condition: both threads read balance = 100,
      // both deduct 50, both write 50 back — actual balance should be 0 but is 50!
      public synchronized void deduct(double amount) throws InsufficientBalanceException {
          if (balance < amount) throw new InsufficientBalanceException(amount - balance);
          balance -= amount;
      }

      public synchronized double getBalance() { return balance; }
  }

Interview answer:
  "Balance deduction is a classic race condition. Without synchronized, two
   concurrent charges on a prepaid account (one for a call, one for data)
   both read balance = $10, both see it's enough for a $6 charge, and both
   deduct — leaving the account at $4 instead of $-2. With synchronized, only
   one thread runs deduct() at a time — the second one sees the true remaining
   balance and throws InsufficientBalanceException."

------------------------------------------------------------------------------
6.3 VOLATILE
------------------------------------------------------------------------------
Concept : Guarantees visibility of writes to other threads. NOT atomic.

Telecom : A 'network maintenance' flag that one admin thread sets and all
          call-processing threads read. Without volatile, threads may cache
          the old flag value and keep accepting calls during downtime.

Code sketch:
  class NetworkController {
      private volatile boolean maintenanceMode = false;

      // Admin thread calls this
      public void enableMaintenance() { maintenanceMode = true; }

      // Hundreds of call threads check this
      public void processCall(Call call) {
          if (maintenanceMode) {
              throw new NetworkUnavailableException("Network under maintenance");
          }
          // ... process call
      }
  }

Interview answer:
  "When the NOC (Network Operations Center) enables maintenance mode, all
   call-processing threads must see the change immediately. Without volatile,
   each thread may have maintenanceMode = false cached in its CPU register —
   calls still get processed during downtime. volatile forces every write to
   go to main memory and every read to come from main memory. It doesn't make
   the assignment atomic, but a single boolean flip is already atomic in Java."

------------------------------------------------------------------------------
6.4 REENTRANTLOCK
------------------------------------------------------------------------------
Concept : Explicit lock with tryLock (timeout), lockInterruptibly, and
          fairness settings. More flexible than synchronized.

Telecom : Number portability (MNP) process — a subscriber's number is being
          ported. The porting process must acquire a lock on that MSISDN.
          If the lock is taken (another porting request), we want to fail
          fast rather than wait forever.

Code sketch:
  class PortingService {
      private ConcurrentHashMap<String, ReentrantLock> msisdnLocks = new ConcurrentHashMap<>();

      public void portNumber(String msisdn, String targetCarrier) throws PortingException {
          ReentrantLock lock = msisdnLocks.computeIfAbsent(msisdn, k -> new ReentrantLock());

          boolean acquired = false;
          try {
              acquired = lock.tryLock(5, TimeUnit.SECONDS);
              if (!acquired) {
                  throw new PortingException("Porting already in progress for: " + msisdn);
              }
              // Safe to port — no concurrent porting for this MSISDN
              executePorting(msisdn, targetCarrier);
          } catch (InterruptedException e) {
              Thread.currentThread().interrupt();
          } finally {
              if (acquired) lock.unlock();   // ALWAYS release in finally
          }
      }
  }

Interview answer:
  "MNP porting must be single-threaded per MSISDN — you can't port the same
   number twice simultaneously. ReentrantLock.tryLock(5, SECONDS) gives us
   a timeout: if another porting request holds the lock, we fail after 5
   seconds with a clear error instead of deadlocking. synchronized has no
   timeout capability. We always unlock in finally — forgetting to unlock
   with ReentrantLock causes a deadlock that synchronized would avoid."

6.5 EXECUTORSERVICE AND THREAD POOLS
------------------------------------------------------------------------------
Concept : Thread pool reuses threads for tasks. Avoids thread creation overhead.
          Types: fixed, cached, scheduled, work-stealing.

Telecom : Batch invoice generation for 10 million subscribers at month-end.
          Cannot create 10 million threads. Use a fixed pool of 100 threads
          to process all subscribers in batches.

Code sketch:
  ExecutorService billingPool = Executors.newFixedThreadPool(100);
  List<Future<InvoiceResult>> futures = new ArrayList<>();

  for (Subscriber sub : allSubscribers) {
      Future<InvoiceResult> future = billingPool.submit(() -> {
          return invoiceGenerator.generate(sub);   // runs in pool thread
      });
      futures.add(future);
  }

  // Collect all results
  for (Future<InvoiceResult> f : futures) {
      InvoiceResult result = f.get();    // blocks until that invoice is done
      persistInvoice(result);
  }

  billingPool.shutdown();
  billingPool.awaitTermination(1, TimeUnit.HOURS);

Interview answer:
  "Month-end billing for 10 million subscribers would take hours single-
   threaded. We use a fixed pool of 100 threads — each thread processes one
   subscriber, generates the invoice, and picks the next one from the queue.
   Future.get() lets us collect results in order. shutdown() + awaitTermination()
   ensures all invoices are written before we declare the billing run complete."

------------------------------------------------------------------------------
6.6 ATOMIC CLASSES
------------------------------------------------------------------------------
Concept : Lock-free thread-safe operations using CAS (Compare-And-Swap).

Telecom : Real-time call counter — how many concurrent calls are active
          right now. Updated by hundreds of threads without a lock.

Code sketch:
  class CallCounterService {
      private AtomicInteger activeCallCount = new AtomicInteger(0);
      private AtomicLong    totalCallsToday = new AtomicLong(0);

      public void onCallStarted() {
          activeCallCount.incrementAndGet();   // thread-safe, no lock
          totalCallsToday.incrementAndGet();
      }

      public void onCallEnded() {
          activeCallCount.decrementAndGet();   // thread-safe, no lock
      }

      public int getActiveCalls() { return activeCallCount.get(); }
  }

Interview answer:
  "Every call start/end event hits the counter from different threads.
   Using synchronized int would serialize all updates — a bottleneck.
   AtomicInteger.incrementAndGet() uses a CAS instruction at the CPU level:
   'compare the current value with what I read, if it matches, swap in
   new value, else retry.' No lock, no contention, no blocking — ideal for
   high-frequency counters like active call count."

7.2 STREAMS
------------------------------------------------------------------------------
Concept : Pipeline of operations (filter, map, reduce) on collections.

   subscriber's calls in one line — what used to be a 30-line loop. Streams

7.3 OPTIONAL
------------------------------------------------------------------------------
Concept : Explicit null handling. Avoids NullPointerException.

Telecom : Looking up a subscriber's add-on plan — they may or may not have
          one. Returning null is dangerous; Optional is explicit.

Code sketch:
  // Return Optional instead of null
  Optional<RoamingPlan> findRoamingPlan(String msisdn) {
      return Optional.ofNullable(roamingPlanRepository.findByMsisdn(msisdn));
  }

  // Caller handles presence/absence explicitly
  Optional<RoamingPlan> roaming = subscriberService.findRoamingPlan(msisdn);

  // Safe access — no NPE possible
  roaming.ifPresent(plan -> applyRoamingRate(call, plan));

  // Default when absent
  double rate = roaming.map(RoamingPlan::getRatePerMinute).orElse(defaultRate);

  // Throw if business logic requires it to exist

Interview answer:
  "Before Optional, findRoamingPlan() returned null for subscribers without

   production during international travel peaks. Optional makes the
   absent case explicit in the type signature. orElse(defaultRate) handles
   absence cleanly. orElseThrow() is used when roaming must exist — like
   when a call is already connected on roaming and billing needs the rate."

7.4 FUNCTIONAL INTERFACES AND METHOD REFERENCES

      cdr.getDurationMinutes() * voiceRatePerMinute;

      (cdr.getDataUsageMB() / 1024.0) * dataRatePerGB;

  // Predicate<CDR>
  Predicate<CDR> isRoaming = cdr -> cdr.getNetworkType() == ROAMING;

Interview answer:
  "We use Function<CDR, Double> as the rater strategy. VoiceRater and
   DataRater are lambdas matching that signature — swapped at runtime based
   on CDR type, no if-else in the billing engine. Predicate composition with
   .and() and .or() builds complex filtering rules cleanly. Method references
   like Subscriber::getMsisdn are more readable than lambda boilerplate —
   they directly document 'I'm calling this method.'"

7.5 COMPLETABLEFUTURE
------------------------------------------------------------------------------
Concept : Async, non-blocking computation. Chain dependent tasks. Combine
          multiple async results.

Telecom : Validating a subscriber for a new plan purchase requires three
          independent checks: credit score, KYC status, and fraud flag.
          Do all three in parallel and combine.

Code sketch:
  CompletableFuture<Boolean> creditCheck = CompletableFuture.supplyAsync(
      () -> creditService.checkScore(msisdn)
  );
  CompletableFuture<Boolean> kycCheck = CompletableFuture.supplyAsync(
      () -> kycService.isVerified(msisdn)
  );
  CompletableFuture<Boolean> fraudCheck = CompletableFuture.supplyAsync(
      () -> fraudService.isClean(msisdn)
  );

  // Combine — all three must be true
  CompletableFuture<Boolean> eligibility =
      CompletableFuture.allOf(creditCheck, kycCheck, fraudCheck)
          .thenApply(v ->
              creditCheck.join() && kycCheck.join() && fraudCheck.join()
          );

  boolean eligible = eligibility.get(3, TimeUnit.SECONDS);

Interview answer:
  "Without CompletableFuture, we'd call creditService, kycService, and
   fraudService sequentially — 3 x 500ms = 1.5 seconds per customer. With
   supplyAsync + allOf, all three run in parallel — total latency drops to
   ~500ms (the slowest one). thenApply combines results once all complete.
   get(3, SECONDS) fails fast with a timeout if any service hangs."

7.7 SEALED CLASSES (Java 17+)
------------------------------------------------------------------------------
Concept : Restrict which classes can extend a parent. Exhaustive pattern
          matching possible.

Telecom : A telecom event hierarchy — only known event types are valid.
          Sealed ensures no unexpected event type enters the system.

Code sketch:
  sealed interface TelecomEvent
      permits CallEvent, DataEvent, SMSEvent, PortingEvent {}

  record CallEvent(String msisdn, int durationSec)    implements TelecomEvent {}
  record DataEvent(String msisdn, long bytesUsed)     implements TelecomEvent {}
  record SMSEvent(String msisdn, String destination)  implements TelecomEvent {}
  record PortingEvent(String msisdn, String newCarrier) implements TelecomEvent {}

  // Exhaustive pattern matching — compiler warns if a case is missing
  double charge = switch (event) {
      case CallEvent  ce -> ce.durationSec() * VOICE_RATE;
      case DataEvent  de -> (de.bytesUsed() / 1_000_000_000.0) * DATA_RATE;
      case SMSEvent   se -> SMS_FLAT_RATE;
      case PortingEvent pe -> PORTING_FEE;
  };   // no default needed — sealed = exhaustive

Interview answer:
  "A telecom event bus accepts events from network nodes. With sealed
   TelecomEvent, we guarantee only these four types exist — no surprises
   from a rogue event type corrupting the billing engine. The switch
   expression is exhaustive — if we add a new event type (e.g., MMS),
   the compiler forces us to add a new case. No silent billing gaps."

SECTION 8: JVM INTERNALS

------------------------------------------------------------------------------
8.1 MEMORY AREAS: HEAP, STACK, METASPACE
------------------------------------------------------------------------------
Concept : Stack — per-thread, method frames. Heap — shared objects.
          Metaspace — class metadata.

Telecom Analogy:
  Stack    -> Each call-processing thread has its own call context (local vars)
  Heap     -> Shared subscriber objects, CDRs, plan objects
  Metaspace-> The class definitions (Subscriber.class, CDR.class) — loaded once

Interview answer:
  "Each call-processing thread in our gateway has its own stack — local
   variables like callId, duration, and ratingResult are thread-safe without
   synchronization because they live on the thread's stack. The Subscriber
   and CDR objects they reference live on the heap — shared, and therefore
   requiring synchronization when mutated. Subscriber.class itself lives in
   Metaspace — loaded once, used by all threads. An OutOfMemoryError in the
   heap during a traffic surge means we need to tune -Xmx. In Metaspace,
   it means too many dynamically generated classes (e.g., from a Groovy
   scripting engine for rating rules)."

------------------------------------------------------------------------------
8.2 GARBAGE COLLECTION
------------------------------------------------------------------------------
Concept : JVM automatically reclaims unused heap objects. Minor GC (young gen)
          is fast; Major/Full GC (old gen) is slow and can pause the app.

Telecom : CDR objects are short-lived — created when a call ends, written to
          storage, then discarded. These fill young gen and are collected
          quickly. Subscriber cache objects are long-lived — they fill old gen.

Interview answer:
  "CDRs are classic young-gen objects in a telco: created per call, processed,
   written to the CDR file, then eligible for GC within seconds. The JVM's
   young-gen (Eden space) collects them cheaply in Minor GC with no pause.
   The subscriber cache — holding millions of subscriber objects across the
   day — fills old gen. We monitor Full GC pauses because a Full GC pause
   of 2 seconds during peak call hours causes call drops. We use G1GC or
   ZGC which limit pause times to milliseconds even on large heaps."

------------------------------------------------------------------------------
8.3 CLASS LOADING
------------------------------------------------------------------------------
Concept : Classes are loaded lazily on first use. ClassLoader hierarchy:
          Bootstrap -> Extension -> Application. Parent delegation model.

Telecom : Telecom platforms use plugins for new services (e.g., a new
          roaming partner integration). Custom ClassLoaders load partner
          jars at runtime without restarting the platform.

Interview answer:
  "Our telecom OSS/BSS platform uses a plugin architecture for carrier
   integrations. Each partner's adapter jar is loaded by a custom
   ClassLoader at runtime when that partner is onboarded — no platform
   restart. The parent delegation model ensures the core platform classes
   (Subscriber, CDR) are loaded once by the application ClassLoader and
   shared; only the partner-specific classes are loaded by the plugin
   ClassLoader. Class.forName() with a custom loader is how we bootstrap
   each plugin."

SECTION 10: COMPARABLE vs COMPARATOR
==============================================================================

------------------------------------------------------------------------------
Concept : Comparable — natural ordering defined IN the class.
          Comparator  — external ordering, passed at sort time.

Telecom :
  Comparable  -> CDR has a natural order by call start time
  Comparator  -> Sort CDRs by charge (for high-value report) or by duration
                 (for longest call report) — multiple orderings needed

Code sketch:
  class CDR implements Comparable<CDR> {
      LocalDateTime callStart;
      double charge;
      int durationSeconds;

      // Natural order: chronological by call start time
      @Override
      public int compareTo(CDR other) {
          return this.callStart.compareTo(other.callStart);
      }
  }

  // External Comparators for different report sorts
  Comparator<CDR> byCharge   = Comparator.comparingDouble(CDR::getCharge).reversed();
  Comparator<CDR> byDuration = Comparator.comparingInt(CDR::getDurationSeconds).reversed();
  Comparator<CDR> byCallee   = Comparator.comparing(CDR::getDestinationMsisdn);

  // Usage
  List<CDR> cdrs = cdrRepository.findByMsisdn(msisdn);
  cdrs.sort(byCharge);   // highest charge first — for invoice report
  cdrs.sort(byDuration); // longest call first — for usage report
  Collections.sort(cdrs); // natural order (chronological) — for statement

Interview answer:
  "CDR's natural sort is chronological — that's the default a customer
   expects when viewing their call statement. Comparable defines that once.
   But reports need different sorts: billing team wants highest charge first,
   customer service wants longest call first. These are Comparators — external
   strategies that don't pollute the CDR class. We compose Comparators with
   .reversed() and .thenComparing() for multi-level sorts."

Concept : A nested class declared static. No implicit reference to outer class
          instance. Used for helper types logically grouped with the outer class.

Telecom : CDR has a nested Builder class. The Builder needs no CDR instance —
          it constructs one.

Code sketch:
  class CDR {
      private final String msisdn;
      private final int durationSeconds;
      private final double charge;

      private CDR(Builder b) {
          this.msisdn = b.msisdn;
          this.durationSeconds = b.durationSeconds;
          this.charge = b.charge;
      }

      public static class Builder {          // static — no CDR instance needed
          private String msisdn;
          private int durationSeconds;
          private double charge;

          public Builder msisdn(String v)    { this.msisdn = v; return this; }
          public Builder duration(int v)     { this.durationSeconds = v; return this; }
          public Builder charge(double v)    { this.charge = v; return this; }
          public CDR build()                 { return new CDR(this); }
      }
  }

  CDR cdr = new CDR.Builder()
      .msisdn("9876543210")
      .duration(120)
      .charge(2.40)
      .build();

Interview answer:
  "CDR.Builder is static because it constructs a CDR — it doesn't need an
   existing CDR instance to exist. A non-static inner Builder would secretly
   hold a reference to an outer CDR object, which makes no sense here. The
   Builder pattern also solves the 'telescoping constructor' problem CDR
   had with 8+ fields — now construction is readable and order-independent."

SECTION 13: ENUM — Telecom Use Cases
==============================================================================

------------------------------------------------------------------------------
13.1 ENUM BASICS — Fixed Set of Constants
------------------------------------------------------------------------------
Concept : Type-safe named constants. Cannot use new. Can have fields, methods.

Telecom : Network types (2G, 3G, 4G, 5G), subscription status, CDR status —
          all fixed, known sets of values.

Code sketch:
  enum NetworkType {
      TWO_G, THREE_G, FOUR_G, FIVE_G;

      public boolean supportsVideoCall() {
          return this == FOUR_G || this == FIVE_G;
      }
  }

  enum CDRStatus {
      INITIATED, CONNECTED, COMPLETED, FAILED, DROPPED;

      public boolean isBillable() {
          return this == COMPLETED;   // only completed calls are billed
      }
  }

  // Usage
  CDR cdr = ...;
  if (cdr.getStatus().isBillable()) {
      billingEngine.charge(cdr);
  }

  NetworkType type = NetworkType.FOUR_G;
  System.out.println(type.supportsVideoCall()); // true

Interview answer:
  "CDRStatus as an enum prevents invalid states — no magic String '\"COMPLTED\"'
   typo can ever enter the billing engine. isBillable() puts the business
   rule where it belongs — in the constant itself. When a new status is added
   (e.g., SUSPENDED), we add it to the enum and the compiler flags every
   switch statement that doesn't handle it."

------------------------------------------------------------------------------
13.2 ENUM IN SWITCH (Exhaustive Pattern Matching)
------------------------------------------------------------------------------
Concept : switch on enum covers all cases — compiler warns on missing ones.

Telecom : Routing an event to the correct handler based on CDRStatus.

Code sketch:
  double calculateCharge(CDR cdr) {
      return switch (cdr.getStatus()) {
          case COMPLETED -> cdr.getDurationSeconds() * RATE_PER_SECOND;
          case DROPPED   -> DROPPED_CALL_FEE;   // partial charge
          case FAILED    -> 0.0;                // no charge
          case INITIATED, CONNECTED -> 0.0;     // still in progress
      };
  }

Interview answer:
  "Switch on CDRStatus with arrow syntax is exhaustive — if we add a new
   status, the compiler forces us to handle it here. No default needed, no
   silent 0.0 for an unhandled state. The billing engine can never silently
   skip a chargeable status."

------------------------------------------------------------------------------
13.3 ENUM AS SINGLETON (Thread-Safe)
------------------------------------------------------------------------------
Concept : Enum guarantees one instance per constant — JVM handles thread safety.

Telecom : RatingEngine as a singleton — only one instance should rate all
          calls, no double-initialization risk.

Code sketch:
  enum RatingEngine {
      INSTANCE;

      private final Map<NetworkType, PricingStrategy> strategies = new HashMap<>();

      RatingEngine() {
          strategies.put(NetworkType.FOUR_G,  new PeakHourPricing());
          strategies.put(NetworkType.FIVE_G,  new PeakHourPricing());
          strategies.put(NetworkType.THREE_G, new OffPeakPricing());
      }

      public double rate(CDR cdr) {
          PricingStrategy s = strategies.get(cdr.getNetworkType());
          return s.calculateCharge(cdr);
      }
  }

  // Usage — no synchronization needed
  double charge = RatingEngine.INSTANCE.rate(cdr);

Interview answer:
  "Enum singleton is the safest Singleton implementation in Java. The JVM
   guarantees exactly one instance of INSTANCE is created even with multiple
   threads — no synchronized block, no volatile, no double-checked locking.
   It's also serialization-safe: deserializing an enum always returns the
   same instance, unlike a class-based singleton which can break on
   deserialization."

SECTION 14: PASS BY VALUE vs PASS BY REFERENCE
==============================================================================

------------------------------------------------------------------------------
Concept : Java is ALWAYS pass-by-value. For objects, the VALUE passed is the
          reference (memory address) — not the object itself.

Telecom Example 1 — Primitive (true pass by value):
  void applyBonus(double balance) {
      balance += 10.0;   // changes local copy only — caller's balance unchanged
  }

  double accountBalance = 100.0;
  applyBonus(accountBalance);
  System.out.println(accountBalance);  // still 100.0 — not 110.0

Telecom Example 2 — Object reference (reference value is passed):
  void activateSubscriber(Subscriber sub) {
      sub.setActive(true);      // modifies the OBJECT the reference points to
      sub = new Subscriber();   // only changes local copy of reference
  }

  Subscriber john = new Subscriber("9876543210");
  activateSubscriber(john);
  System.out.println(john.isActive());  // TRUE — object was mutated via reference
  System.out.println(john.getMsisdn()); // "9876543210" — john still points to original

Interview answer:
  "Java passes the VALUE of the reference, not the reference itself. When we
   pass a Subscriber to activateSubscriber(), the method gets a copy of the
   memory address pointing to John's object. Calling sub.setActive(true)
   mutates John's object in the heap — the caller sees the change. But
   sub = new Subscriber() only changes the method's local copy of the
   address — John in the caller still points to the original object. Common
   interview trick: 'does Java pass by reference?' — NO, always by value."

SECTION 15: EQUALS() AND HASHCODE() CONTRACT
==============================================================================

------------------------------------------------------------------------------
Concept : If equals() is true, hashCode() must be equal.
          If hashCode() is equal, equals() may or may not be true.
          Both must be overridden together.

Telecom : Subscriber lookup in a HashSet and as HashMap keys — if we forget
          to override hashCode(), two "equal" subscribers are treated as
          different keys.

Code sketch:
  class Subscriber {
      private String msisdn;   // unique identifier

      @Override
      public boolean equals(Object o) {
          if (this == o) return true;
          if (!(o instanceof Subscriber)) return false;
          Subscriber other = (Subscriber) o;
          return Objects.equals(this.msisdn, other.msisdn);
      }

      @Override
      public int hashCode() {
          return Objects.hash(msisdn);   // MUST override — same msisdn -> same hash
      }
  }

  // Without overriding both — BREAKS HashMap/HashSet:
  Map<Subscriber, Invoice> invoiceMap = new HashMap<>();
  Subscriber s1 = new Subscriber("9876543210");
  invoiceMap.put(s1, invoice);

  Subscriber s2 = new Subscriber("9876543210");  // same msisdn, different object
  invoiceMap.get(s2);   // returns NULL without proper hashCode() — wrong bucket!

Interview answer:
  "The subscriber invoice map is keyed by Subscriber. Without overriding
   hashCode(), two Subscriber objects with the same MSISDN land in different
   buckets — get() returns null even when the key 'exists.' equals() alone
   is not enough for HashMap — it only runs within a bucket after hashCode()
   picks the right one. We use Objects.hash(msisdn) to derive hashCode from
   the same field as equals. Contract: equal objects MUST have equal hashCodes."

SECTION 16: IMMUTABLE CLASS DESIGN
==============================================================================

------------------------------------------------------------------------------
Concept : An immutable class cannot be modified after construction.
          Rules: final class, all fields private+final, no setters, defensive
          copies for mutable fields, return copies from getters.

Telecom : TariffPlan — once published, a plan's pricing must never change.
          Concurrent billing threads read it without locks because it's immutable.

Code sketch:
  public final class TariffPlan {                    // final — no subclassing
      private final String planId;
      private final double ratePerMinute;
      private final List<String> includedCountries;  // mutable — must be guarded

      public TariffPlan(String planId, double ratePerMinute, List<String> countries) {
          this.planId = planId;
          this.ratePerMinute = ratePerMinute;
          // Defensive copy — don't trust the passed-in list
          this.includedCountries = List.copyOf(countries);
      }

      public String getPlanId()       { return planId; }
      public double getRatePerMinute(){ return ratePerMinute; }

      // Return unmodifiable view — caller can't mutate our internal list
      public List<String> getIncludedCountries() {
          return Collections.unmodifiableList(includedCountries);
      }
      // No setters anywhere
  }

Interview answer:
  "TariffPlan is immutable because thousands of billing threads read it
   simultaneously. Since no thread can ever change its state, zero
   synchronization is needed — huge performance gain. The five rules:
   1) final class prevents subclass from adding mutable state,
   2) all fields final and private,
   3) no setters,
   4) defensive copy of the List in the constructor,
   5) return unmodifiable view from getter. Forgetting defensive copy is
   the most common mistake — a caller could mutate the original list and
   change the 'immutable' object's data."

SECTION 17: CONCURRENCY — ADVANCED PATTERNS
==============================================================================

------------------------------------------------------------------------------
17.1 DEADLOCK
------------------------------------------------------------------------------
Concept : Two threads each hold a lock the other needs → both block forever.

Telecom : Thread A holds lock on AccountA and waits for AccountB.
          Thread B holds lock on AccountB and waits for AccountA.
          Happens in inter-account transfers (prepaid top-up from a credit).

Code sketch (deadlock scenario):
  // Thread 1: transfer from account "9876" to "1111"
  synchronized(account9876) {
      synchronized(account1111) { account9876.debit(50); account1111.credit(50); }
  }

  // Thread 2: transfer from account "1111" to "9876" (reverse direction)
  synchronized(account1111) {
      synchronized(account9876) { account1111.debit(30); account9876.credit(30); }
  }
  // Deadlock: Thread1 holds 9876 lock, Thread2 holds 1111 lock — both wait

Fix — always acquire locks in the same consistent order:
  void transfer(Account from, Account to, double amount) {
      Account first  = from.getId().compareTo(to.getId()) < 0 ? from : to;
      Account second = first == from ? to : from;
      synchronized(first) {
          synchronized(second) {
              from.debit(amount);
              to.credit(amount);
          }
      }
  }

Interview answer:
  "Inter-account transfers deadlock when two threads take locks in opposite
   order. The fix is lock ordering — always acquire the lock for the
   lower account ID first. Both threads then try to lock in the same order,
   so one waits while the other completes. No circular dependency, no
   deadlock. In production we also use ReentrantLock.tryLock() with a
   timeout as a second line of defense."

------------------------------------------------------------------------------
17.2 COUNTDOWNLATCH — Wait for Multiple Events
------------------------------------------------------------------------------
Concept : Main thread waits for N worker threads to complete before proceeding.

Telecom : Before launching a new tariff plan, wait for all regional servers
          (North, South, East, West) to confirm they've loaded the new rates.

Code sketch:
  int regionCount = 4;
  CountDownLatch readyLatch = new CountDownLatch(regionCount);

  for (String region : List.of("North", "South", "East", "West")) {
      executorService.submit(() -> {
          rateLoader.loadForRegion(region);   // push new tariff to that region
          readyLatch.countDown();             // signal: this region is ready
      });
  }

  // Main thread (plan activation) blocks until all 4 regions are ready
  boolean allReady = readyLatch.await(30, TimeUnit.SECONDS);
  if (!allReady) {
      throw new PlanActivationException("Not all regions confirmed within 30s");
  }
  tariffPlanService.activatePlan(newPlan);    // now safe to go live

Interview answer:
  "Going live with a new tariff before all regional billing nodes have loaded
   it causes pricing inconsistency — some subscribers get the old rate, some
   the new. CountDownLatch(4) blocks the plan activation until all four
   regional loaders call countDown(). If any region takes more than 30 seconds,
   await() returns false and we abort the activation. CountDownLatch is
   one-time — once it reaches zero it can't be reset. For repeating barriers
   we use CyclicBarrier."

------------------------------------------------------------------------------
17.3 BLOCKINGQUEUE — Producer-Consumer
------------------------------------------------------------------------------
Concept : Thread-safe queue where producers wait if full, consumers wait if empty.

Telecom : CDR generation (producer) and CDR file-writing (consumer) run at
          different speeds. BlockingQueue decouples them and provides
          natural backpressure.

Code sketch:
  BlockingQueue<CDR> cdrQueue = new ArrayBlockingQueue<>(10_000);

  // Producer — call-end events generate CDRs
  Runnable producer = () -> {
      while (true) {
          CDR cdr = waitForCallEnd();      // blocks until a call ends
          cdrQueue.put(cdr);              // blocks if queue is full (backpressure)
      }
  };

  // Consumer — writes CDRs to billing storage
  Runnable consumer = () -> {
      while (true) {
          CDR cdr = cdrQueue.take();      // blocks if queue is empty
          cdrStorage.write(cdr);
      }
  };

  executorService.submit(producer);
  executorService.submit(consumer);

Interview answer:
  "Call-end events spike during peak hours — the CDR generator produces
   faster than the file writer consumes. Without BlockingQueue, we'd lose
   CDRs or overflow memory. ArrayBlockingQueue(10_000) caps the backlog.
   put() blocks the producer if 10,000 CDRs are waiting — natural
   backpressure that prevents unbounded memory growth. take() blocks the
   consumer when quiet. This producer-consumer pattern is in every high-
   throughput telecom system."

------------------------------------------------------------------------------
17.4 THREADLOCAL — Per-Thread Context
------------------------------------------------------------------------------
Concept : Each thread has its own isolated copy of a variable. No sharing,
          no synchronization needed.

Telecom : Billing session context — each billing thread processes one
          subscriber's invoice. The subscriber context must be accessible
          throughout the thread's call stack without passing it as a parameter.

Code sketch:
  class BillingContext {
      private static final ThreadLocal<String> currentMsisdn = new ThreadLocal<>();

      public static void set(String msisdn) { currentMsisdn.set(msisdn); }
      public static String get()            { return currentMsisdn.get(); }
      public static void clear()            { currentMsisdn.remove(); }  // CRITICAL
  }

  // In the billing thread:
  try {
      BillingContext.set(subscriber.getMsisdn());
      invoiceGenerator.generate();      // can call BillingContext.get() anywhere
      taxCalculator.apply();            // no need to pass msisdn as parameter
      pdfRenderer.render();
  } finally {
      BillingContext.clear();           // MUST clear — thread pool reuses threads!
  }

Interview answer:
  "Each billing thread handles one subscriber at a time, but dozens of
   helper classes (TaxCalculator, PdfRenderer, AuditLogger) all need the
   current subscriber's MSISDN. Passing it through every method signature
   is messy. ThreadLocal gives each thread its own msisdn slot — no sharing,
   no synchronization. Critical rule: always call remove() in finally. Thread
   pools reuse threads — without clear(), thread 5 picks up subscriber A's
   MSISDN when it starts processing subscriber B."

------------------------------------------------------------------------------
17.5 FORK/JOIN AND PARALLEL STREAMS
------------------------------------------------------------------------------
Concept : ForkJoinPool splits a large task into subtasks recursively, then
          joins the results. Parallel streams use ForkJoinPool internally.

Telecom : Month-end fraud scan — check all 10 million CDRs for anomalies.
          Divide CDR list into halves recursively, scan each partition in
          parallel, combine results.

Code sketch:
  // Using parallel streams — simpler syntax for CDR fraud scan
  List<CDR> suspiciousCDRs = allCDRs.parallelStream()
      .filter(cdr -> fraudDetector.isSuspicious(cdr))
      .collect(Collectors.toList());

  // Explicit ForkJoinPool with custom parallelism (don't pollute common pool)
  ForkJoinPool customPool = new ForkJoinPool(8);
  List<CDR> suspicious = customPool.submit(() ->
      allCDRs.parallelStream()
             .filter(cdr -> fraudDetector.isSuspicious(cdr))
             .collect(Collectors.toList())
  ).get();
  customPool.shutdown();

Interview answer:
  "Sequential fraud scan of 10 million CDRs takes 10 minutes. parallelStream()
   splits the work across 8 cores — ~75 seconds. We use a custom ForkJoinPool
   rather than the common pool to avoid starving other parallel stream users
   in the JVM. The rule: parallelStream() is only beneficial when the task
   is CPU-bound, stateless, and the data set is large enough that parallel
   overhead is worth it. For I/O-bound tasks (DB queries), use async
   CompletableFuture instead."

SECTION 18: SOLID PRINCIPLES — Telecom Examples
==============================================================================

------------------------------------------------------------------------------
S — Single Responsibility Principle
------------------------------------------------------------------------------
Each class does ONE thing. A class that handles billing AND sends SMS AND
writes CDRs has three reasons to change — violates SRP.

Telecom:
  BAD:  class BillingService { deductCharge(); sendSMSAlert(); writeCDR(); generatePDF(); }
  GOOD: class ChargeCalculator { }   // calculates the charge only
        class SMSNotifier { }        // sends SMS only
        class CDRWriter { }          // writes CDR only
        class InvoicePdfGenerator { }// generates PDF only

Interview answer:
  "When the SMS gateway vendor changed, we had to modify BillingService —
   a class that handles core financial logic. That's SRP violation. We split
   it: ChargeCalculator only calculates, SMSNotifier only notifies. Now a
   gateway change touches only SMSNotifier, not the billing core."

------------------------------------------------------------------------------
O — Open/Closed Principle
------------------------------------------------------------------------------
Open for extension, closed for modification. Add new behavior by adding
new classes, not editing existing ones.

Telecom:
  Adding a new pricing rule (e.g., 5G premium rate) should NOT require
  editing BillingEngine. Add a new PricingStrategy implementation.

  // BillingEngine never changes — new strategies plug in via the interface
  class FiveGPremiumPricing implements PricingStrategy {
      public double calculateCharge(CDR cdr) { return cdr.getDurationSec() * 0.25; }
  }

Interview answer:
  "Every time marketing launched a promotion, developers had to open
   BillingEngine and add another if-else. Any regression could break all
   existing pricing. After refactoring to Strategy pattern, new pricing
   rules are new classes. BillingEngine is closed for modification —
   it just calls strategy.calculateCharge(). Zero regression risk."

------------------------------------------------------------------------------
L — Liskov Substitution Principle
------------------------------------------------------------------------------
A subclass must be usable wherever its parent is used, without breaking behavior.

Telecom:
  If PostpaidAccount extends BillingAccount, it must honor all BillingAccount
  contracts. If BillingAccount.deduct() guarantees no NPE, PostpaidAccount
  must not break that.

  BAD: PostpaidAccount.generateInvoice() throws UnsupportedOperationException
       — violates LSP (parent says it works, child says it doesn't)
  GOOD: PostpaidAccount.generateInvoice() generates a postpaid invoice

Interview answer:
  "We had a CorporateAccount that extended BillingAccount but overrode
   generateInvoice() to throw UnsupportedOperationException — corporate
   invoicing was handled by a separate system. This violated LSP: code
   that accepted BillingAccount and called generateInvoice() broke at
   runtime with corporate accounts. Fix: separate interface InvoiceGeneratable
   — only accounts that support it implement it."

------------------------------------------------------------------------------
I — Interface Segregation Principle
------------------------------------------------------------------------------
Don't force clients to implement interfaces they don't use. Prefer small,
focused interfaces.

Telecom:
  BAD:  interface TelecomAccount { deductCharge(); generateInvoice(); sendSMS();
        portNumber(); roamingEnable(); manageESIM(); }
        — a basic prepaid account must implement esim management it doesn't support

  GOOD: interface Billable          { deductCharge(); generateInvoice(); }
        interface SMSCapable        { sendSMS(); }
        interface Portable          { portNumber(); }
        interface ESIMCapable       { manageESIM(); }

  PrepaidAccount  implements Billable, SMSCapable, Portable { ... }
  CorporateAccount implements Billable, SMSCapable, Portable, ESIMCapable { ... }

Interview answer:
  "When we added eSIM management to TelecomAccount, all existing account
   types — including a basic IoT SIM that just sends data — had to implement
   manageESIM(). ISP violation. We split into focused interfaces: IoTSim
   implements only DataCapable; a flagship smartphone account implements
   Billable + SMSCapable + ESIMCapable. Each class only implements what it
   actually supports."

------------------------------------------------------------------------------
D — Dependency Inversion Principle
------------------------------------------------------------------------------
High-level modules should not depend on low-level modules. Both should
depend on abstractions.

Telecom:
  BAD:  BillingEngine directly uses PostgresBillingRepository (concrete class)
  GOOD: BillingEngine depends on BillingRepository (interface)
        PostgresBillingRepository and CassandraBillingRepository implement it

Code sketch:
  // DIP compliant
  interface BillingRepository {
      void saveInvoice(Invoice invoice);
      List<Invoice> findByMsisdn(String msisdn);
  }

  class BillingEngine {
      private final BillingRepository repository;   // depends on abstraction

      public BillingEngine(BillingRepository repository) {   // injected
          this.repository = repository;
      }
  }

  // Wiring (in Spring: @Bean / @Autowired)
  BillingEngine engine = new BillingEngine(new PostgresBillingRepository());

Interview answer:
  "Our BillingEngine originally imported PostgresBillingRepository directly.
   When we migrated to Cassandra for scale, BillingEngine had to change —
   a core billing class shouldn't know about storage details. After DIP:
   BillingEngine depends on BillingRepository interface. Swapping Postgres
   for Cassandra only changes the wiring — BillingEngine doesn't change.
   This is what Spring's dependency injection enforces architecturally."

SECTION 19: TYPE CASTING — Widening, Narrowing, ClassCastException
==============================================================================

------------------------------------------------------------------------------
Concept : Widening (automatic, safe). Narrowing (explicit cast, may lose data).
          ClassCastException at runtime when cast is invalid.

Telecom Examples:

  // WIDENING — safe, automatic
  int callDurationSeconds = 125;
  long totalDurationMs = callDurationSeconds;   // int -> long, no cast needed
  double charge = callDurationSeconds * 0.05;  // int * double -> double

  // NARROWING — explicit cast, data loss risk
  double preciseCharge = 2.789;
  float chargeForLegacySystem = (float) preciseCharge;  // loses precision
  int roundedDuration = (int) 125.9;   // truncates to 125 — not rounded

  // ClassCastException — wrong reference type cast
  NetworkService service = new SMSService();
  VoiceService voice = (VoiceService) service;  // ClassCastException at runtime!
  // service points to SMSService — cannot be cast to VoiceService

  // Safe cast with instanceof check
  if (service instanceof VoiceService voice) {  // pattern matching (Java 16+)
      voice.setVoiceQuality(HD);
  }

Interview answer:
  "In billing, we widen int call duration to long for total monthly duration —
   automatic and safe. When sending charges to a legacy system that uses float,
   we narrow with explicit cast — and we know we lose sub-cent precision,
   which is acceptable. ClassCastException happens when our event processing
   casts a TelecomEvent to CallEvent but it's actually an SMSEvent. Pattern
   matching instanceof catches it at compile time — both the check and the
   cast in one statement, no ClassCastException possible."


==============================================================================
SECTION 20: AUTOBOXING / UNBOXING TRAPS
==============================================================================

------------------------------------------------------------------------------
Concept : Java auto-converts between primitives and wrapper types. Silent
          NullPointerException and unexpected == behavior are the traps.

Telecom Traps:

  // Trap 1: NullPointerException from unboxing null
  Map<String, Integer> callCountByMsisdn = new HashMap<>();
  int count = callCountByMsisdn.get("9876543210");
  // get() returns null (not in map) -> unboxing null Integer to int -> NPE!

  // Fix
  int count = callCountByMsisdn.getOrDefault("9876543210", 0);

  // Trap 2: == on autoboxed Integer (-128 to 127 cache)
  Integer calls1 = 100;
  Integer calls2 = 100;
  System.out.println(calls1 == calls2);  // TRUE — cached

  Integer roamingCost1 = 500;
  Integer roamingCost2 = 500;
  System.out.println(roamingCost1 == roamingCost2);  // FALSE — not cached!
  System.out.println(roamingCost1.equals(roamingCost2));  // TRUE — always use equals

  // Trap 3: Performance — autoboxing in a tight loop
  Long totalUsageBytes = 0L;
  for (CDR cdr : millionCDRs) {
      totalUsageBytes += cdr.getBytes();  // unboxes Long, adds, reboxes — millions of objects!
  }
  // Fix: use primitive long
  long totalUsageBytes = 0L;

Interview answer:
  "Three autoboxing traps we hit in production: NPE when unboxing null from
   a HashMap (subscriber had no call count yet — fix: getOrDefault), wrong
   == comparison for roaming costs above 127 (fix: always use equals() on
   wrappers), and creating millions of Long objects in a CDR accumulation
   loop (fix: use primitive long). Autoboxing is convenient but hides
   these costs. In performance-critical billing loops, always use primitives."
