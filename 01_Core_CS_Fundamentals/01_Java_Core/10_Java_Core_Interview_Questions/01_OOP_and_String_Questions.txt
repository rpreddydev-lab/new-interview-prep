OOP AND STRING QUESTIONS
=========================

Q1: What is the difference between abstract class and interface in Java?
------------------------------------------------------------------------
A:
  Abstract Class:
  - Can have instance state (fields)
  - Can have constructors
  - Can have abstract and concrete methods
  - A class can extend only ONE abstract class
  - Methods can be any access modifier
  - Use when: you want to share code among closely related classes

  Interface:
  - No instance state (only public static final constants)
  - No constructors
  - All methods implicitly public; can have default/static/private methods (Java 8+/9+)
  - A class can implement MANY interfaces
  - Use when: you want to define a contract/capability for unrelated classes

  Java 8+ blurred the line: interfaces can have default methods with implementations.
  Key remaining difference: abstract class can have mutable instance fields; interface cannot.

  | Feature             | Abstract Class         | Interface                   |
  |---------------------|------------------------|-----------------------------|
  | State (fields)      | Yes                    | Only public static final    |
  | Constructors        | Yes                    | No                          |
  | Method visibility   | Any                    | public (default/static/private Java 8/9+) |
  | Multiple inheritance| Single                 | Multiple                    |
  | Constructor call    | super()                | N/A                         |

Q2: What is the difference between == and .equals() in Java?
------------------------------------------------------------
A:
  == compares REFERENCES (memory addresses) for objects; for primitives, compares VALUES.
  .equals() compares CONTENT — depends on how the class overrides Object.equals().

  Object.equals() default: same as == (reference comparison). Subclasses override it.

  String s1 = new String("hello");
  String s2 = new String("hello");
  s1 == s2       → false (different heap objects)
  s1.equals(s2)  → true  (same content)

  Common pitfalls:
  - Integer cache: Integer.valueOf(127) == Integer.valueOf(127) → TRUE (cached -128..127)
  - Integer.valueOf(128) == Integer.valueOf(128) → FALSE (outside cache)
  - Always use .equals() for object content comparison
  - null.equals(...) → NullPointerException; use Objects.equals(a, b) for null safety

Q3: What is method overloading vs method overriding?
----------------------------------------------------
A:
  Overloading (compile-time / static polymorphism):
  - Same class, same method name, DIFFERENT parameter types or counts
  - Resolved at compile time based on declared type of arguments
  - Return type, access modifier can differ

  Overriding (runtime / dynamic polymorphism):
  - Subclass redefines a method inherited from superclass
  - Same name, same parameters, same (or covariant) return type
  - At least as accessible as the superclass method
  - Resolved at runtime via virtual dispatch (vtable lookup)
  - @Override annotation — compiler enforces it IS an override

  Key: overloading → compile-time decision. Overriding → runtime decision.

Q4: What is the difference between String, StringBuilder, and StringBuffer?
---------------------------------------------------------------------------
A:
  String: immutable — every modification creates a new object.
  StringBuilder: mutable, NOT thread-safe. Preferred for single-threaded string building.
  StringBuffer: mutable, thread-safe (all methods synchronized). Slower than StringBuilder.

  Performance: StringBuilder > StringBuffer > String (for repeated modifications)
  Thread safety: only StringBuffer; StringBuilder needs external synchronization.

  Note: Java 9+ invokedynamic-based + concatenation can be as fast as StringBuilder
  for simple, non-loop concatenations. Always use StringBuilder inside loops.

  String s = "hello" + " world";              // compiled to single literal — fast
  for (...) { result += s; }                  // BAD — O(n²) object creation
  for (...) { sb.append(s); } sb.toString();  // GOOD — O(n)

Q5: Explain the four pillars of OOP with Java examples.
-------------------------------------------------------
A:
  1. ENCAPSULATION: bundling data + methods; restricting direct field access.
     - private fields + public getters/setters
     - Protects invariants (e.g., age can't be negative)

  2. ABSTRACTION: hiding implementation details; exposing only what is necessary.
     - Abstract classes and interfaces define contracts without revealing how
     - e.g., List interface: you use add/get without knowing if it's ArrayList or LinkedList

  3. INHERITANCE: subclass inherits fields/methods from superclass; enables code reuse.
     - extends keyword
     - IS-A relationship
     - Pitfall: deep inheritance hierarchies become fragile; prefer composition

  4. POLYMORPHISM: one interface, many implementations.
     - Method overriding (runtime polymorphism via dynamic dispatch)
     - Method overloading (compile-time polymorphism)
     - e.g., List<Animal> animals; animals.add(new Dog()); animals.add(new Cat());
       each animal.speak() calls the correct implementation at runtime

Q6: What are the rules for hashCode() and equals() contracts in Java?
----------------------------------------------------------------------
A:
  Contract (from Object Javadoc):
  1. Reflexive: x.equals(x) == true
  2. Symmetric: x.equals(y) == y.equals(x)
  3. Transitive: if x.equals(y) && y.equals(z) → x.equals(z)
  4. Consistent: repeated calls return same result (without object modification)
  5. Null: x.equals(null) == false (never throw NPE)

  hashCode contract:
  - If x.equals(y), then x.hashCode() == y.hashCode() (MANDATORY)
  - If !x.equals(y), hashCode MAY differ (not required but highly desirable for HashMap performance)

  Common mistake: overriding equals() without overriding hashCode() → object can't be
  found in a HashMap/HashSet after being stored (hash bucket mismatch).

Q7: What is the significance of the final keyword in Java?
---------------------------------------------------------
A:
  final variable: can be assigned exactly once; effectively final is sufficient for lambdas.
  final method: cannot be overridden in subclasses.
  final class: cannot be subclassed (e.g., String, Integer).

  final + static = compile-time constant (inlined by the compiler).
  final field in constructor: JMM guarantees visibility — final fields are safe to share
  after construction without synchronization (freeze guarantee).

  final does NOT mean immutable for objects — the reference is constant but the object's
  state may still change (e.g., final List<String> list = new ArrayList(); list.add("x"); // works).

Q8: What is the difference between composition and inheritance? When to prefer each?
------------------------------------------------------------------------------------
A:
  Inheritance (IS-A): Dog extends Animal
  - Subclass exposes all public/protected API of the superclass (fragile)
  - Changes in the superclass can break subclasses (brittle base class problem)
  - Java only allows single inheritance

  Composition (HAS-A): Car has an Engine
  - The class delegates to contained objects
  - Looser coupling — can swap implementations at runtime
  - Works with interfaces (dependency injection)

  Prefer composition:
  - When the relationship is "uses" rather than "is"
  - When you don't control the superclass (inheritance can expose implementation details)
  - When you need to mix behaviors from multiple sources

  Effective Java (Bloch): "Favor composition over inheritance."
  Exception: use inheritance when a genuine IS-A relationship exists and you control
  the hierarchy (e.g., AbstractList subclasses in Collections Framework).
