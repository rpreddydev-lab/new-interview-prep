ADVANCED JAVA QUESTIONS
========================

Q1: What is the Double-Checked Locking (DCL) pattern and why does it need volatile?
------------------------------------------------------------------------------------
A:
  DCL is used to implement a thread-safe, lazily-initialized singleton while minimizing
  synchronization overhead:

  class Singleton {
      private static volatile Singleton instance;  // MUST be volatile!
      private Singleton() {}
      public static Singleton getInstance() {
          if (instance == null) {                   // first check (no lock)
              synchronized (Singleton.class) {
                  if (instance == null) {           // second check (with lock)
                      instance = new Singleton();   // multiple steps: alloc, init, assign
                  }
              }
          }
          return instance;
      }
  }

  Why volatile is required:
  instance = new Singleton() is NOT atomic. It consists of:
  1. Allocate memory for the object
  2. Initialize the object (constructor call)
  3. Assign the reference to instance

  Without volatile, the JIT/CPU can reorder steps — e.g., assign the reference (step 3)
  BEFORE completing initialization (step 2). Another thread passes the first null check,
  sees a non-null instance, and uses a partially initialized object.

  volatile prevents this reordering via a happens-before edge on the write.
  Alternative: use enum singleton (Effective Java) or initialization-on-demand holder idiom:

  // Holder idiom — lazy, thread-safe, no volatile:
  class Singleton {
      private Singleton() {}
      private static class Holder {
          static final Singleton INSTANCE = new Singleton();  // class loading is thread-safe
      }
      public static Singleton getInstance() { return Holder.INSTANCE; }
  }

Q2: What is the difference between Callable and Runnable?
---------------------------------------------------------
A:
  Runnable: functional interface with void run() — cannot return a value, cannot throw
  checked exceptions.

  Callable<V>: functional interface with V call() throws Exception — can return a value
  of type V and can throw checked exceptions.

  ExecutorService.submit(Runnable) → Future<?> (get() returns null)
  ExecutorService.submit(Callable<V>) → Future<V> (get() returns the computed value)

  FutureTask<V> implements both Runnable and Future — wraps a Callable so it can be
  submitted as a Runnable while still providing a Future result.

Q3: What is CompletableFuture and how does it improve over Future?
-----------------------------------------------------------------
A:
  Future<T> limitations:
  - get() is BLOCKING — thread stalls waiting for result
  - Cannot compose multiple futures
  - No callback API
  - Cannot complete manually / no error propagation pipeline

  CompletableFuture<T> (Java 8+):
  - Implements both Future<T> and CompletionStage<T>
  - Non-blocking composition via callbacks (thenApply, thenCompose, thenAccept, thenRun)
  - Error handling: exceptionally(), handle(), whenComplete()
  - Combining: allOf(), anyOf(), thenCombine()
  - Can be completed manually: complete(value), completeExceptionally(ex)
  - Java 9+: orTimeout(), completeOnTimeout(), delayedExecutor()

  CompletableFuture<String> result = CompletableFuture.supplyAsync(() -> fetchUser(id))
      .thenApply(user -> user.getName())
      .exceptionally(ex -> "Unknown User");

  Compose vs Apply:
  thenApply(Function<T, R>) — map (sync transform, returns CompletableFuture<R>)
  thenCompose(Function<T, CompletableFuture<R>>) — flatMap (async chain; avoids nested futures)

Q4: What is method hiding vs method overriding?
-----------------------------------------------
A:
  Method overriding (instance methods):
  When a subclass provides a new implementation of an inherited instance method.
  Resolution at RUNTIME via dynamic dispatch (based on actual object type).

  class Parent { void show() { System.out.println("Parent"); } }
  class Child extends Parent { @Override void show() { System.out.println("Child"); } }
  Parent p = new Child();
  p.show();  // "Child" — runtime dispatch

  Method hiding (static methods):
  Static methods cannot be overridden — they are resolved at COMPILE TIME based on
  the declared (static) type of the reference.
  If a subclass defines a static method with the same signature as the superclass static method,
  it HIDES the parent's method (not overrides it).

  class Parent { static void greet() { System.out.println("Parent static"); } }
  class Child extends Parent { static void greet() { System.out.println("Child static"); } }
  Parent p = new Child();
  p.greet();  // "Parent static" — compile-time type is Parent; static → no dispatch

  Key: @Override on a static method would cause a compile error — static methods can't be overridden.

Q5: What is the difference between deep copy and shallow copy in Java?
----------------------------------------------------------------------
A:
  Shallow copy: copies the object's primitive fields by value, but object reference fields
  are copied as references — both the original and the copy point to the SAME inner objects.
  Changes to a nested object through either reference affect both.

  Deep copy: recursively copies all nested objects too — the original and the copy are
  completely independent.

  Java copy mechanisms:
  - Object.clone() + Cloneable: implements shallow copy by default.
    Override clone() to perform deep copy manually.
    Cloneable is a marker interface; clone() is protected in Object — must override and make public.
  - Copy constructor: new MyObject(other) — manually copy all fields; deep copy if needed.
  - Serialization trick: serialize to byte stream then deserialize → deep copy (slow).
  - Library: libraries like Apache Commons BeanUtils, ModelMapper, Kryo for deep copying.
  - Java records: created immutable — no copying needed for value semantics.

  Effective Java recommendation: prefer copy constructors/factories over clone().

Q6: What are inner classes and their types in Java?
----------------------------------------------------
A:
  Static nested class:
  - Declared with static inside another class
  - Does NOT have access to the enclosing class's instance members
  - Instantiated independently: new Outer.Nested()
  - Use when the nested class doesn't need an enclosing instance (logically grouped utility)

  Inner class (non-static nested):
  - Has access to all members (including private) of the enclosing instance
  - Requires an enclosing instance: outer.new Inner()
  - Holds an implicit reference to the enclosing instance → can cause memory leaks
    (if the inner class is long-lived, it keeps the outer alive)
  - Example: Iterator implementations inside Collection classes

  Local class:
  - Declared inside a method. Can access effectively final local variables.
  - Rarely used directly; lambda expressions are usually cleaner.

  Anonymous class:
  - Unnamed class declared and instantiated in one expression.
  - Pre-Java 8 substitute for lambdas:
    Runnable r = new Runnable() { public void run() { ... } };
  - Java 8+: lambda is almost always cleaner.

Q7: What is the principle behind the Java Collections.unmodifiableXxx wrappers?
-------------------------------------------------------------------------------
A:
  Collections.unmodifiableList(list), unmodifiableMap(map), etc. return a wrapper view
  that delegates read operations to the original collection but throws
  UnsupportedOperationException for all mutating operations (add, remove, set, put, clear).

  Important nuances:
  - The wrapper is a VIEW — if the original collection is modified, the wrapper reflects those changes.
    It is "read-only" not "immutable."
  - To create a truly immutable snapshot: List.of() / List.copyOf() (Java 9+) create
    genuinely immutable lists that can never change even if the source changes.

  List<String> mutable = new ArrayList<>(List.of("a", "b", "c"));
  List<String> readOnly = Collections.unmodifiableList(mutable);
  mutable.add("d");
  System.out.println(readOnly.size());  // 4 — reflects the mutation!

  List<String> immutable = List.copyOf(mutable);  // snapshot; truly immutable
  mutable.add("e");
  System.out.println(immutable.size());  // still 4

Q8: What is the purpose of the transient keyword?
-------------------------------------------------
A:
  transient marks a field to be EXCLUDED from Java object serialization.
  When an object is serialized (written to a byte stream via ObjectOutputStream),
  transient fields are NOT serialized — they are reset to their type's default value
  upon deserialization (null for objects, 0 for int, false for boolean).

  Use cases:
  - Sensitive data: passwords, credentials — don't persist to disk/network
  - Derived/cached fields: can be recomputed after deserialization (e.g., cached hash)
  - Non-serializable fields: Logger, InputStream — would cause NotSerializableException
  - Thread-specific state: Thread, Lock objects

  class User implements Serializable {
      String username;         // serialized
      transient String password;  // NOT serialized
      transient Logger log;    // NOT serialized (Logger not Serializable)
  }

  Note: static fields are not serialized regardless of transient (static is class-level, not instance-level).
  The serialVersionUID should be declared explicitly to avoid InvalidClassException across versions.
