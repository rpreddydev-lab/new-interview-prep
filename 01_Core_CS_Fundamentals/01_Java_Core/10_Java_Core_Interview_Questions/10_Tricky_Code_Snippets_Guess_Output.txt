Java Tricky Code Snippets — Guess the Output
==============================================
These are classic "guess the output" questions frequently asked in Java interviews.
Each snippet tests a specific deep concept. Study the explanation carefully.


==============================================================================
CATEGORY 1: String Pool & Equality
==============================================================================

Snippet 1.1 — String == vs equals
----------------------------------
    String a = "hello";
    String b = "hello";
    String c = new String("hello");

    System.out.println(a == b);        // ?
    System.out.println(a == c);        // ?
    System.out.println(a.equals(c));   // ?

Output:
    true
    false
    true

Explanation:
- a and b both point to the same object in the String Pool  =>  == is true
- c is created with new, so it's a new heap object          =>  == is false
- .equals() compares content                                =>  true


Snippet 1.2 — String Concatenation and Pool
--------------------------------------------
    String s1 = "Java";
    String s2 = "Java";
    String s3 = s1 + s2;           // runtime concat
    String s4 = "Java" + "Java";   // compile-time constant

    System.out.println(s3 == "JavaJava");  // ?
    System.out.println(s4 == "JavaJava");  // ?

Output:
    false
    true

Explanation:
- s3 = s1 + s2 is runtime concatenation => creates a new heap object => == is false
- s4 = "Java" + "Java" is a compile-time constant expression => folded to "JavaJava"
  in the pool => == is true


Snippet 1.3 — String intern()
-------------------------------
    String a = new String("test").intern();
    String b = "test";
    System.out.println(a == b);  // ?

Output:
    true

Explanation:
  intern() returns the pool reference. Both a and b now point to the same pool object.


Snippet 1.4 — substring and memory
------------------------------------
    String s = "Hello World";
    String sub = s.substring(0, 5);
    System.out.println(sub);             // ?
    System.out.println(sub == "Hello");  // ?

Output:
    Hello
    false

Explanation:
  substring() creates a new String object on the heap, not interned in the pool.
  So == is false even though content matches "Hello".

CATEGORY 2: Integer Cache & Autoboxing
==============================================================================

Snippet 2.1 — Integer Cache (-128 to 127)
------------------------------------------
    Integer a = 127;
    Integer b = 127;
    Integer c = 128;
    Integer d = 128;

    System.out.println(a == b);  // ?
    System.out.println(c == d);  // ?

Output:
    true
    false

Explanation:
- Java caches Integer objects from -128 to 127 (IntegerCache).
  So a and b are the same object.
- 128 is outside the cache range => two separate heap objects => == is false.
- Always use .equals() to compare Integer values!


Snippet 2.2 — null unboxing NullPointerException
--------------------------------------------------
    Integer x = null;
    int y = x;   // ?
    System.out.println(y);

Output:
    NullPointerException

Explanation:
  Unboxing null => Java tries to call x.intValue() on a null reference => NPE.


Snippet 2.3 — Integer arithmetic
----------------------------------
    Integer a = 1000;
    Integer b = 1000;
    System.out.println(a + b);          // ?
    System.out.println(a + b == 2000);  // ?

Output:
    2000
    true

Explanation:
  Arithmetic operators + trigger unboxing, so the operation is done as int.
  The result 2000 is an int, and == 2000 compares with an int literal => true.


Snippet 2.4 — Long vs long comparison
---------------------------------------
    Long a = 100L;
    long b = 100L;
    System.out.println(a == b);       // ?
    System.out.println(a.equals(b));  // ?

Output:
    true
    true

Explanation:
- a == b: b is a primitive => a is unboxed to long for comparison => values match => true
- a.equals(b): b is autoboxed to Long => Long.equals(Long) compares values => true

CATEGORY 3: Operator Precedence & Tricky Expressions
==============================================================================

Snippet 3.1 — Post vs Pre Increment
-------------------------------------
    int i = 5;
    int j = i++ + ++i;
    System.out.println(i);  // ?
    System.out.println(j);  // ?

Output:
    7
    12

Explanation:
- i++ returns 5, then i becomes 6
- ++i increments first => i becomes 7, returns 7
- j = 5 + 7 = 12,  i = 7


Snippet 3.2 — Compound Assignment
-----------------------------------
    byte b = 10;
    b = b + 1;     // compile error?
    b += 1;        // compile error?
    System.out.println(b);

Output:
    Compile error on line 2 only

Explanation:
- b + 1 promotes b to int => assigning int to byte needs explicit cast => compile error
- b += 1 is equivalent to b = (byte)(b + 1) => implicit cast included => no error,
  prints 11


Snippet 3.3 — Integer division truncation
-------------------------------------------
    System.out.println(5 / 2);           // ?
    System.out.println(5 / 2.0);         // ?
    System.out.println(5.0 / 2);         // ?
    System.out.println((double) 5 / 2);  // ?

Output:
    2
    2.5
    2.5
    2.5

Explanation:
  Integer division truncates. If either operand is double/float, result is floating point.


Snippet 3.4 — Conditional with mixed types
--------------------------------------------
    int i = 10;
    System.out.println(i > 5 ? "yes" : 100);  // ?

Output:
    yes

Explanation:
  The ternary operator returns type based on the most specific common type of both
  branches. "yes" is a String, 100 autoboxed to Integer. The result is Object.
  Prints "yes".


Snippet 3.5 — char arithmetic
-------------------------------
    char c = 'A';
    System.out.println(c + 1);          // ?
    System.out.println((char)(c + 1));  // ?

Output:
    66
    B

Explanation:
  'A' + 1 => char is promoted to int (65) + 1 = 66.
  Casting back to char gives 'B'.

CATEGORY 4: Inheritance & Polymorphism
==============================================================================

Snippet 4.1 — Method Overriding (Runtime Polymorphism)
--------------------------------------------------------
    class Animal {
        String name = "Animal";
        void sound() { System.out.println("Generic sound"); }
    }
    class Dog extends Animal {
        String name = "Dog";
        void sound() { System.out.println("Woof"); }
    }

    Animal a = new Dog();
    System.out.println(a.name);   // ?
    a.sound();                    // ?

Output:
    Animal
    Woof

Explanation:
- Fields are resolved at compile time (reference type Animal) => a.name is "Animal"
- Methods are resolved at runtime (actual object Dog)         => a.sound() calls Dog.sound()
- This is the classic field hiding vs method overriding distinction!


Snippet 4.2 — super() call order
----------------------------------
    class A { A() { System.out.println("A"); } }
    class B extends A { B() { System.out.println("B"); } }
    class C extends B { C() { System.out.println("C"); } }

    new C();

Output:
    A
    B
    C

Explanation:
  Every constructor implicitly calls super() first.
  Chain: C() => B() => A(), but A prints first as execution flows top-down.


Snippet 4.3 — Static method hiding (not overriding)
-----------------------------------------------------
    class Parent {
        static void display() { System.out.println("Parent"); }
    }
    class Child extends Parent {
        static void display() { System.out.println("Child"); }
    }

    Parent p = new Child();
    p.display();   // ?

Output:
    Parent

Explanation:
  Static methods are NOT overridden — they are hidden.
  Resolved at compile time based on reference type (Parent) => Parent.display().


Snippet 4.4 — Covariant return types
--------------------------------------
    class Base    { Base    get() { return this; } }
    class Derived extends Base { @Override Derived get() { return this; } }

    Base b = new Derived();
    System.out.println(b.get().getClass().getSimpleName());  // ?

Output:
    Derived

Explanation:
  Covariant return type is valid. The actual object is Derived.
  Since get() is overridden, runtime dispatch calls Derived.get(),
  which returns this (a Derived instance).

CATEGORY 5: Static & Initialization Order
==============================================================================

Snippet 5.1 — Static block vs instance block order
----------------------------------------------------
    class Test {
        static { System.out.println("Static Block"); }
        { System.out.println("Instance Block"); }
        Test() { System.out.println("Constructor"); }
    }

    new Test();
    new Test();

Output:
    Static Block
    Instance Block
    Constructor
    Instance Block
    Constructor

Explanation:
- Static block runs ONCE when the class is loaded
- Instance block runs before constructor EVERY TIME an object is created


Snippet 5.2 — Static variable initialization
----------------------------------------------
    class A {
        static int x = getX();
        static int y = 10;
        static int getX() { return y; }  // y not initialized yet!
    }

    System.out.println(A.x);
    System.out.println(A.y);

Output:
    0
    10

Explanation:
  Static fields are initialized in declaration order. When getX() is called,
  y is still 0 (default value). So x = 0.


Snippet 5.3 — final static fields
-----------------------------------
    class Const {
        static final int A = 10;
        static final int B;
        static { B = 20; }
    }

    System.out.println(Const.A + Const.B);  // ?

Output:
    30

Explanation:
  A is a compile-time constant (inlined by compiler).
  B is a runtime constant (assigned in static block). Both work fine.

CATEGORY 6: Exception Handling
==============================================================================

Snippet 6.1 — finally always runs
-----------------------------------
    static int test() {
        try { return 1; }
        finally { return 2; }
    }
    System.out.println(test());  // ?

Output:
    2

Explanation:
  finally always executes, even when return is in try.
  The finally return 2 overrides the try return 1.


Snippet 6.2 — finally with exception
--------------------------------------
    static void test() {
        try { throw new RuntimeException("try"); }
        finally { System.out.println("finally"); }
    }
    test();

Output:
    finally
    Exception in thread "main" java.lang.RuntimeException: try

Explanation:
  finally always runs. Since finally doesn't swallow the exception,
  the RuntimeException propagates after finally completes.


Snippet 6.3 — Multiple catch blocks
-------------------------------------
    try {
        int[] arr = new int[5];
        arr[10] = 1;
    } catch (ArrayIndexOutOfBoundsException e) {
        System.out.println("caught: " + e.getMessage());
    } catch (Exception e) {
        System.out.println("general");
    } finally {
        System.out.println("finally");
    }

Output:
    caught: Index 10 out of bounds for length 5
    finally

Explanation:
  First matching catch block is executed. finally always runs regardless.


Snippet 6.4 — try-with-resources order
----------------------------------------
    class Resource implements AutoCloseable {
        String name;
        Resource(String n) { this.name = n; System.out.println("Open: " + n); }
        public void close()  { System.out.println("Close: " + name); }
    }

    try (Resource r1 = new Resource("A"); Resource r2 = new Resource("B")) {
        System.out.println("Using resources");
    }

Output:
    Open: A
    Open: B
    Using resources
    Close: B
    Close: A

Explanation:
  Resources are opened in declaration order, closed in REVERSE order (like a stack).
  This is guaranteed by try-with-resources.


Snippet 6.5 — Checked exceptions in overriding
------------------------------------------------
    class Base  { void method() throws IOException {} }
    class Child extends Base {
        @Override
        void method() throws Exception {}  // compile error?
    }

Output:
    Compile Error

Explanation:
  Overriding methods cannot throw BROADER checked exceptions than the parent.
  Exception is broader than IOException => compile error.
  The reverse (narrower or unchecked) is allowed.

CATEGORY 7: Collections & Generics Tricks
==============================================================================

Snippet 7.1 — List.of() is immutable
--------------------------------------
    List<String> list = List.of("a", "b", "c");
    list.add("d");   // ?

Output:
    UnsupportedOperationException

Explanation:
  List.of() (Java 9+) returns an immutable list.
  Any structural modification throws UnsupportedOperationException.


Snippet 7.2 — ArrayList remove(int) vs remove(Object)
-------------------------------------------------------
    List<Integer> list = new ArrayList<>(Arrays.asList(1, 2, 3));
    list.remove(1);
    System.out.println(list);  // ?

Output:
    [1, 3]

Explanation:
  remove(1) calls remove(int index) => removes element at index 1 (value 2).
  To remove by value, use list.remove(Integer.valueOf(1)).


Snippet 7.3 — HashMap null key
--------------------------------
    Map<String, Integer> map = new HashMap<>();
    map.put(null, 1);
    map.put(null, 2);
    System.out.println(map.get(null));  // ?
    System.out.println(map.size());     // ?

Output:
    2
    1

Explanation:
  HashMap allows ONE null key. The second put(null, 2) OVERWRITES the first.
  Size remains 1.


Snippet 7.4 — ConcurrentModificationException
-----------------------------------------------
    List<String> list = new ArrayList<>(Arrays.asList("a", "b", "c"));
    for (String s : list) {
        if (s.equals("b")) list.remove(s);  // ?
    }

Output:
    ConcurrentModificationException

Explanation:
  Modifying a collection while iterating with enhanced for loop (uses iterator
  internally) triggers ConcurrentModificationException.
  Use Iterator.remove() or removeIf() instead.


Snippet 7.5 — TreeMap natural ordering
----------------------------------------
    Map<Integer, String> map = new TreeMap<>();
    map.put(3, "three");
    map.put(1, "one");
    map.put(2, "two");
    System.out.println(map);  // ?

Output:
    {1=one, 2=two, 3=three}

Explanation:
  TreeMap stores entries in natural (sorted) order of keys.
  Insertion order doesn't matter.

CATEGORY 8: Multithreading Tricks
==============================================================================

Snippet 8.1 — Non-atomic i++
------------------------------
    // Two threads each running 1000 times:
    static int count = 0;
    // Thread 1 and Thread 2 both do: count++;
    // What is the final value?

Output:
    Any value between 1 and 2000 (not guaranteed to be 2000)

Explanation:
  count++ is NOT atomic — it's 3 steps: read, increment, write.
  Without synchronization, race condition leads to lost updates.
  Use AtomicInteger or synchronized.


Snippet 8.2 — Volatile does not guarantee atomicity
-----------------------------------------------------
    volatile int counter = 0;
    // Multiple threads doing counter++
    // Is it thread-safe?

Output:
    No — volatile ensures VISIBILITY, NOT atomicity

Explanation:
  volatile ensures all threads see the latest value (no CPU cache),
  but counter++ is still 3 non-atomic steps.
  Use AtomicInteger.incrementAndGet().


Snippet 8.3 — Thread.sleep() doesn't release lock
---------------------------------------------------
    synchronized(this) {
        Thread.sleep(1000);
    }

Explanation:
  Thread.sleep() does NOT release the lock.
  Other threads waiting on this monitor are blocked for the full sleep duration.
  Use wait() to release the lock while waiting.

---------------------------------------------
    Object obj = "Hello";

    Object obj = "Hello";
    if (obj instanceof String s) {

    5

Explanation:

Explanation:

  Narrowing cast silently loses data.

CATEGORY 10: Interface & Abstract Class Tricks
==============================================================================

Snippet 10.1 — Default method conflict
----------------------------------------
    interface A { default void hello() { System.out.println("A"); } }
    interface B { default void hello() { System.out.println("B"); } }
    class C implements A, B {
        // what happens?
    }

Output:
    Compile Error — C must override hello()

Explanation:
  When a class implements two interfaces with the same default method,
  it MUST override it to resolve the ambiguity. Otherwise, compile error.


Snippet 10.2 — Interface static methods are not inherited
-----------------------------------------------------------
    interface Greeting {
        static void hello() { System.out.println("Hello from interface"); }
    }
    class MyClass implements Greeting {}

    MyClass.hello();  // ?

Output:
    Compile Error

Explanation:
  Interface static methods are NOT inherited by implementing classes.
  You must call Greeting.hello() directly.


Snippet 10.3 — Abstract class constructor
-------------------------------------------
    abstract class Shape {
        Shape() { System.out.println("Shape created"); }
        abstract void draw();
    }
    class Circle extends Shape {
        Circle() { System.out.println("Circle created"); }
        void draw() { System.out.println("Drawing Circle"); }
    }

    new Circle();

Output:
    Shape created
    Circle created

Explanation:
  Abstract classes CAN have constructors.
  They are called via super() when a subclass is instantiated.

CATEGORY 11: Java 8+ Lambda & Stream Tricks
==============================================================================

Snippet 11.1 — Stream is lazy
-------------------------------
    List<Integer> list = Arrays.asList(1, 2, 3, 4, 5);
    Stream<Integer> stream = list.stream()
        .filter(x -> {
            System.out.println("filter: " + x);
            return x > 2;
        });
    System.out.println("Before terminal");
    stream.forEach(System.out::println);

Output:
    Before terminal
    filter: 1
    filter: 2
    filter: 3
    3
    filter: 4
    4
    filter: 5
    5

Explanation:
  Streams are LAZY — intermediate operations (filter) are NOT executed
  until a terminal operation (forEach) is called.


Snippet 11.2 — Stream reuse throws exception
----------------------------------------------
    Stream<String> stream = Stream.of("a", "b", "c");
    stream.forEach(System.out::println);
    stream.forEach(System.out::println);  // ?

Output:
    a
    b
    c
    IllegalStateException: stream has already been operated upon or closed

Explanation:
  A Stream cannot be reused after a terminal operation.
  Create a new stream each time.


Snippet 11.3 — Capturing effectively final variables
------------------------------------------------------
    int x = 10;
    Runnable r = () -> System.out.println(x);
    x = 20;  // compile error?
    r.run();

Output:
    Compile Error

Explanation:
  Lambda expressions can only capture EFFECTIVELY FINAL local variables.
  Reassigning x after the lambda captures it makes it non-effectively-final
  => compile error.


Snippet 11.4 — Optional.get() without check
---------------------------------------------
    Optional<String> opt = Optional.empty();
    System.out.println(opt.get());  // ?

Output:
    NoSuchElementException: No value present

Explanation:
  Calling .get() on an empty Optional throws NoSuchElementException.
  Always use isPresent(), ifPresent(), orElse(), or orElseThrow().

CATEGORY 12: equals() and hashCode() Contract
==============================================================================

Snippet 12.1 — Overriding equals without hashCode
---------------------------------------------------
    class Point {
        int x, y;
        Point(int x, int y) { this.x = x; this.y = y; }

        @Override
        public boolean equals(Object o) {
            Point p = (Point) o;
            return this.x == p.x && this.y == p.y;
        }
        // hashCode NOT overridden
    }

    Set<Point> set = new HashSet<>();
    set.add(new Point(1, 2));
    System.out.println(set.contains(new Point(1, 2)));  // ?

Output:
    false

Explanation:
  HashSet first uses hashCode() to find the bucket.
  Since hashCode() is NOT overridden, two equal Point objects have different
  hash codes => different buckets => contains() returns false.
  ALWAYS override both equals() AND hashCode() together!

CATEGORY 13: Miscellaneous Classics
==============================================================================

Snippet 13.1 — main method overloading
----------------------------------------
    public class Main {
        public static void main(String[] args) {
            System.out.println("main with args");
        }
        public static void main() {
            System.out.println("main without args");
        }
    }

Output:
    main with args

Explanation:
  JVM always calls main(String[] args) specifically.
  The other is just a regular overloaded method, not the entry point.


Snippet 13.2 — Switch fall-through
------------------------------------
    int x = 2;
    switch (x) {
        case 1: System.out.println("One");
        case 2: System.out.println("Two");
        case 3: System.out.println("Three");
        default: System.out.println("Default");
    }

Output:
    Two
    Three
    Default

Explanation:
  Without break, switch FALLS THROUGH to subsequent cases.
  Execution starts at matching case 2 and continues through all remaining cases.


Snippet 13.3 — String is immutable
------------------------------------
    String s = "Hello";
    s.concat(" World");
    System.out.println(s);  // ?

Output:
    Hello

Explanation:
  String is immutable. concat() returns a new String object,
  but the result is not assigned. s still points to "Hello".


Snippet 13.4 — Tricky null comparison
---------------------------------------
    String s = null;
    System.out.println(s == null);         // ?
    System.out.println(null == null);      // ?
    System.out.println("hello".equals(s)); // ?
    System.out.println(s.equals("hello")); // ?

Output:
    true
    true
    false
    NullPointerException

Explanation:
- s == null          => true  (reference is null)
- null == null       => true  (always)
- "hello".equals(s) => false (equals() handles null argument gracefully)
- s.equals("hello") => NPE   (calling method on null reference)
  Best practice: always call .equals() on a known non-null object.


Snippet 13.5 — Infinite recursion on toString
----------------------------------------------
    class Node {
        String name;
        Node next;
        @Override
        public String toString() {
            return name + " -> " + next;  // recursive if circular reference
        }
    }

Output:
    StackOverflowError (if circular reference exists)

Explanation:
  If next eventually points back to this, calling toString() triggers
  infinite recursion => StackOverflowError.


Snippet 13.6 — Varargs ambiguity
----------------------------------
    static void print(Object o)    { System.out.println("Object: " + o); }
    static void print(Object... o) { System.out.println("Varargs"); }

    print("hello");  // ?

Output:
    Object: hello

Explanation:
  Java PREFERS the more specific method (fixed arity over varargs) when both match.
  print(Object) is chosen over print(Object...).


Snippet 13.7 — Inner class accessing outer private members
------------------------------------------------------------
    class Outer {
        private int x = 10;
        class Inner {
            void show() { System.out.println(x); }  // can access private?
        }
    }

    new Outer().new Inner().show();  // ?

Output:
    10

Explanation:
  Inner classes have access to ALL members (including private) of the enclosing
  outer class. This is a special Java language rule.

CATEGORY 16: Enum Tricks
==============================================================================

Snippet 16.1 — Enum == vs equals
----------------------------------
    enum Day { MON, TUE, WED }

    Day d1 = Day.MON;
    Day d2 = Day.MON;
    System.out.println(d1 == d2);       // ?
    System.out.println(d1.equals(d2));  // ?

Output:
    true
    true

Explanation:
  Enum constants are SINGLETONS — there is only one instance per constant.
  Both == and equals() are safe and equivalent for enums.


Snippet 16.2 — Enum ordinal and name
--------------------------------------
    enum Color { RED, GREEN, BLUE }

    System.out.println(Color.GREEN.ordinal());  // ?
    System.out.println(Color.GREEN.name());     // ?
    System.out.println(Color.GREEN.toString()); // ?

Output:
    1
    GREEN
    GREEN

Explanation:
  ordinal() returns the zero-based position (GREEN is at index 1).
  name() and toString() both return the constant name as a String.


Snippet 16.3 — Enum with abstract method
------------------------------------------
    enum Operation {
        ADD {
            @Override
            public int apply(int a, int b) { return a + b; }
        },
        MUL {
            @Override
            public int apply(int a, int b) { return a * b; }
        };

Snippet 18.1 — wait() must be in synchronized block

Explanation:
  wait(), notify(), notifyAll() MUST be called from within a synchronized block

Snippet 18.2 — notify() vs notifyAll()
----------------------------------------

    // Thread 2 and Thread 3 are both waiting on obj.
    // How many threads are woken?

Output:
    Only ONE thread is woken (chosen arbitrarily by JVM)

Explanation:
  notify() wakes exactly ONE waiting thread (JVM chooses which one).
  notifyAll() wakes ALL waiting threads. Usually notifyAll() is safer to avoid
  missed signals.


Snippet 18.3 — Deadlock classic pattern
-----------------------------------------
    Object lock1 = new Object();
    Object lock2 = new Object();

    Thread t1 = new Thread(() -> {
        synchronized(lock1) { synchronized(lock2) { /* work */ } }
    });
    Thread t2 = new Thread(() -> {
        synchronized(lock2) { synchronized(lock1) { /* work */ } }
    });

    t1.start(); t2.start();
    // What can happen?

Output:
    Possible DEADLOCK — t1 holds lock1 waiting for lock2,
    t2 holds lock2 waiting for lock1.

Explanation:
  Classic deadlock: circular lock dependency. Prevention: always acquire locks
  in the SAME global order. Or use tryLock() with timeout.


Snippet 18.4 — ThreadLocal isolation
--------------------------------------
    ThreadLocal<Integer> tl = ThreadLocal.withInitial(() -> 0);

    Thread t1 = new Thread(() -> {
        tl.set(100);
        System.out.println("T1: " + tl.get());  // ?
    });
    Thread t2 = new Thread(() -> {
        System.out.println("T2: " + tl.get());  // ?
    });

    t1.start(); t1.join();
    t2.start(); t2.join();

Output:
    T1: 100
    T2: 0

Explanation:
  ThreadLocal gives each thread its OWN COPY of the variable. t2 never set it,
  so it gets the initial value 0. Changes in t1 don't affect t2.


Snippet 18.5 — synchronized on different objects
--------------------------------------------------
    class Counter {
        int count = 0;
        synchronized void increment() { count++; }
    }

    Counter c1 = new Counter();
    Counter c2 = new Counter();

    // Thread 1 calls c1.increment()
    // Thread 2 calls c2.increment()
    // Are they synchronized?

Output:
    NO — they synchronize on DIFFERENT objects (c1 and c2)

Explanation:
  synchronized on an instance method locks on "this". c1 and c2 are separate
  instances, so threads do NOT block each other. For shared locking, use a
  static synchronized method or a shared lock object.


Snippet 18.6 — happens-before guarantee
-----------------------------------------
    int x = 0;
    volatile boolean flag = false;

    // Thread 1:
    x = 42;
    flag = true;

    // Thread 2:
    if (flag) System.out.println(x);  // ?

Output:
    42  (guaranteed)

Explanation:
  A write to a volatile variable HAPPENS-BEFORE any subsequent read of that
  variable. So if Thread 2 sees flag=true, it is GUARANTEED to also see x=42.
  Without volatile, x=42 might not be visible to Thread 2.

Snippet 21.1 — Inconsistent compareTo breaks TreeSet

    class BadKey implements Comparable<BadKey> {

CATEGORY 22: Fail-Fast vs Fail-Safe Iterators

Snippet 22.1 — Fail-fast: ArrayList iterator
----------------------------------------------
    List<String> list = new ArrayList<>(Arrays.asList("a", "b", "c"));
    Iterator<String> it = list.iterator();
    list.add("d");          // structural modification
    it.next();              // ?

Output:
    ConcurrentModificationException

Explanation:
  ArrayList's iterator is FAIL-FAST. It checks a modCount internally.
  Any structural modification after iterator creation throws CME on next().


Snippet 22.2 — Fail-safe: CopyOnWriteArrayList
------------------------------------------------
    List<String> list = new CopyOnWriteArrayList<>(Arrays.asList("a","b","c"));
    for (String s : list) {
        if (s.equals("b")) list.add("d");  // modification during iteration
    }
    System.out.println(list);  // ?

Output:
    [a, b, c, d]   (no ConcurrentModificationException)

Explanation:
  CopyOnWriteArrayList is FAIL-SAFE — it iterates over a snapshot copy.
  Modifications affect the underlying list but NOT the current iteration.
  Safe but memory-expensive.


Snippet 22.3 — Iterator.remove() is safe
------------------------------------------
    List<String> list = new ArrayList<>(Arrays.asList("a", "b", "c"));
    Iterator<String> it = list.iterator();
    while (it.hasNext()) {
        if (it.next().equals("b")) it.remove();  // safe removal
    }
    System.out.println(list);  // ?

Output:
    [a, c]

Explanation:
  Iterator.remove() is the ONLY safe way to remove elements during iteration.
  It updates modCount correctly so no CME is thrown.

Snippet 24.1 — Stack vs Heap
------------------------------
    void method() {
        int x = 10;           // stack
        String s = "hello";   // reference on stack, object in heap (pool)
        Object o = new Object(); // reference on stack, object on heap
    }
    // After method returns, what happens?

Output:
    x and the references (s, o) are popped from the stack.
    The Object on heap becomes eligible for GC.
    "hello" in String pool is NOT collected (pool is GC-rooted).

Explanation:
  Local variables live on the STACK. Objects live on the HEAP.
  Stack frames are automatically freed when method returns.


Snippet 24.2 — Soft vs Weak reference behavior
------------------------------------------------
    Object obj = new Object();
    WeakReference<Object> weak = new WeakReference<>(obj);

    obj = null;   // remove strong reference
    System.gc();

    System.out.println(weak.get());  // ?

Output:
    null  (most likely — WeakReference is cleared on GC)

Explanation:
  WeakReference is cleared by GC as soon as no strong references exist.
  SoftReference is cleared only under MEMORY PRESSURE.
  Use WeakReference for caches (e.g., WeakHashMap), SoftReference for
  memory-sensitive caches.


Snippet 24.3 — OutOfMemoryError vs StackOverflowError
-------------------------------------------------------
    // Case 1:
    void infinite() { infinite(); }
    infinite();  // ?

    // Case 2:
    List<byte[]> list = new ArrayList<>();
    while(true) { list.add(new byte[1024 * 1024]); }  // ?

Output:
    Case 1: StackOverflowError   (call stack exhausted)
    Case 2: OutOfMemoryError     (heap exhausted)

Explanation:
  StackOverflowError: each method call adds a frame to the call stack.
  Infinite recursion fills the stack.
  OutOfMemoryError: heap runs out of space for new objects.


Snippet 24.4 — Class loading: when does static block run?
-----------------------------------------------------------
    class Lazy {
        static { System.out.println("Loaded!"); }
        static int VALUE = 42;
    }

    // Case 1: just referencing the class name in a comment — does it load?
    // Case 2: Class.forName("Lazy") — does it load?
    // Case 3: Lazy.class — does it load?

Output:
    Case 1: No — no actual reference
    Case 2: Yes — Class.forName() triggers class loading and static init
    Case 3: No — class literal (.class) does NOT trigger static initialization

Explanation:
  Class is loaded and initialized when:
  - First instance is created (new Lazy())
  - Static method/field is accessed (Lazy.VALUE)
  - Class.forName() is called
  NOT when just using the class literal (Lazy.class).

Snippet 25.1 — this() constructor chaining order

Output:
    -727379968   (int overflow!)
    1000000000000  (correct — promoted to long)

Explanation:
  i * i: both ints => result is int => OVERFLOWS.
  l * i: one operand is long => i is promoted to long => no overflow.
  Always use L suffix or cast when multiplying large numbers.

CATEGORY 31: Math & Number Edge Cases

Snippet 31.1 — Math.round() edge cases
----------------------------------------
    System.out.println(Math.round(0.5));   // ?
    System.out.println(Math.round(-0.5));  // ?
    System.out.println(Math.round(1.5));   // ?

Output:
    1
    0
    2

Explanation:
  Math.round() uses "half-up" rounding: adds 0.5 then floors.
  round(0.5)  = floor(1.0) = 1
  round(-0.5) = floor(0.0) = 0  (NOT -1 — this surprises many!)
  round(1.5)  = floor(2.0) = 2


Snippet 31.2 — Math.floor vs Math.ceil vs Math.round
------------------------------------------------------
    System.out.println(Math.floor(2.9));   // ?
    System.out.println(Math.ceil(2.1));    // ?
    System.out.println(Math.floor(-2.1));  // ?
    System.out.println(Math.ceil(-2.9));   // ?

Output:
    2.0
    3.0
    -3.0
    -2.0

Explanation:
  floor() rounds DOWN (toward negative infinity).
  ceil()  rounds UP   (toward positive infinity).
  For negatives: floor(-2.1) = -3.0, ceil(-2.9) = -2.0 — many get these wrong!


Snippet 31.3 — Integer.MIN_VALUE negation trap
------------------------------------------------
    int x = Integer.MIN_VALUE;
    System.out.println(-x);         // ?
    System.out.println(Math.abs(x)); // ?

Output:
    -2147483648
    -2147483648

Explanation:
  Integer.MIN_VALUE = -2147483648. Its negation and Math.abs() BOTH return the
  same negative value due to integer overflow. There is no positive equivalent
  in 32-bit int. This is a well-known interview trap!
