IO AND GENERICS QUESTIONS
==========================

Q1: What is the difference between InputStream/OutputStream and Reader/Writer?
-----------------------------------------------------------------------------
A:
  InputStream / OutputStream:
  - Operate on RAW BYTES (byte — 8 bits)
  - Use for: binary data (images, audio, video, network protocols, serialized objects)
  - Base classes: InputStream (read()), OutputStream (write())
  - Key subclasses: FileInputStream, BufferedInputStream, ByteArrayInputStream,
    DataInputStream, ObjectInputStream (deserialization)

  Reader / Writer:
  - Operate on CHARACTERS (char — Unicode, 16-bit in Java)
  - Use for: text data (files, console, network text)
  - Handle character encoding (UTF-8, UTF-16, etc.) — translate bytes ↔ chars
  - Key subclasses: FileReader/Writer, BufferedReader/Writer, InputStreamReader/Writer
    (bridge between byte and character streams with explicit charset)

  Bridge classes:
  InputStreamReader(InputStream, Charset) — converts byte stream → char stream
  OutputStreamWriter(OutputStream, Charset) — converts char stream → byte stream

  Best practice: always specify charset explicitly:
  new InputStreamReader(stream, StandardCharsets.UTF_8)
  // Never rely on default charset (platform-dependent, causes portability bugs)

Q2: What is NIO.2 and how does it differ from classic java.io?
--------------------------------------------------------------
A:
  Classic java.io:
  - File class — limited: no metadata, no symbolic link support, no atomic operations
  - All methods return boolean (no exceptions for failures — hard to diagnose)
  - Streams are byte/char oriented
  - No asynchronous I/O
  - No file system watching

  java.nio (Java 4) — NIO (New I/O):
  - Channels + Buffers (non-blocking I/O, Selector-based multiplexing)
  - ByteBuffer — direct vs heap; positions, limits, marks
  - FileChannel, SocketChannel, ServerSocketChannel, DatagramChannel
  - Selectors — single thread handles multiple channels (basis of Netty, servlet containers)

  java.nio.file (Java 7) — NIO.2:
  - Path interface (replaces File) — immutable, proper API
  - Files utility class — rich methods: copy, move, delete, createTempFile, readAllLines,
    walk (file tree), find
  - FileSystem / FileSystems — abstract filesystem support
  - WatchService — watch directories for creation/modification/deletion events
  - Links: Files.createSymbolicLink(), Files.isSymbolicLink()
  - Atomic moves: Files.move(src, dst, ATOMIC_MOVE)
  - Better exception handling: throws IOException (not silent boolean)

  // NIO.2 examples:
  Path path = Paths.get("/data/config.yml");
  List<String> lines = Files.readAllLines(path, StandardCharsets.UTF_8);
  Files.write(path, "content".getBytes(StandardCharsets.UTF_8), StandardOpenOption.APPEND);
  Files.walk(Paths.get("/data")).filter(Files::isRegularFile).forEach(System.out::println);

Q3: What is BufferedReader/Writer and why should you buffer I/O?
----------------------------------------------------------------
A:
  Unbuffered I/O: every read()/write() call goes to the OS (system call) — extremely slow.
  One character at a time → thousands of system calls for a text file.

  Buffered I/O: wraps a stream/reader with an internal buffer (default 8 KB).
  Reads/writes fill/flush the buffer — far fewer system calls; one 8KB read from OS serves
  thousands of individual get() calls.

  BufferedReader br = new BufferedReader(new FileReader("file.txt"));
  br.readLine();  // reads a full line efficiently

  BufferedWriter bw = new BufferedWriter(new FileWriter("out.txt"));
  bw.write("line"); bw.newLine();  // buffered; flushed to OS in blocks
  bw.flush();  // or bw.close()

  Rule: always wrap FileReader/FileInputStream with BufferedReader/BufferedInputStream
  for production code. The overhead is negligible; the performance improvement is massive.

  Modern alternative (NIO.2):
  Files.readAllLines(path)    — reads entire file; internally buffered
  Files.lines(path)           — lazy Stream<String>; reads line by line
  Files.readString(path)      — reads entire file as String (Java 11+)
  Files.writeString(path, str) — writes String to file (Java 11+)

Q4: What is the difference between List.of() and Arrays.asList()?
-----------------------------------------------------------------
A:
  Arrays.asList(T... a):
  - Returns a FIXED-SIZE list backed by the original array
  - Cannot add/remove elements (throws UnsupportedOperationException)
  - CAN set/replace existing elements (the underlying array is mutable)
  - Returns null if the array contains nulls
  - The list is a VIEW of the array — changes to the array reflect in the list and vice versa

  List.of(T... a) (Java 9+):
  - Returns a TRULY IMMUTABLE list
  - Cannot add/remove/set (all mutating operations throw UnsupportedOperationException)
  - Does NOT allow null elements (throws NullPointerException)
  - Not backed by any mutable structure — safe to share without defensive copies
  - Better performance (more compact internal representation)

  | Feature              | Arrays.asList()   | List.of() (Java 9+) |
  |----------------------|-------------------|---------------------|
  | Null elements        | Allowed           | NOT allowed          |
  | Set elements         | Allowed           | NOT allowed          |
  | Add/remove           | Not allowed       | Not allowed          |
  | Backed by array      | Yes               | No                  |
  | True immutable       | No (set works)    | Yes                 |

Q5: What are bounded type parameters in generics?
-------------------------------------------------
A:
  Bounded type parameters constrain what types can be used as type arguments.

  Upper bound (extends): T must be X or a subtype of X.
  <T extends Number>  — T can be Integer, Double, Long, etc.
  <T extends Comparable<T>>  — T must implement Comparable for itself

  Lower bound (super — only on wildcards, not on type parameters):
  <? super Integer>  — unknown type that is Integer or a supertype (Number, Object)

  Multiple bounds:
  <T extends Comparable<T> & Serializable>  — T must implement both
  (only one class bound; interfaces can be multiple; class must come first)

  Why bounded type parameters?
  class MinMax<T extends Comparable<T>> {
      T findMin(List<T> list) { return list.stream().min(Comparator.naturalOrder()).orElseThrow(); }
  }
  // Without the bound, T.compareTo() wouldn't be available — compiler can't know T has that method.

Q6: What is a generic class with multiple type parameters?
---------------------------------------------------------
A:
  A class can declare multiple type parameters, each acting as a placeholder for a distinct type.

  class Pair<A, B> {
      private final A first;
      private final B second;
      public Pair(A first, B second) { this.first = first; this.second = second; }
      public A getFirst() { return first; }
      public B getSecond() { return second; }
  }

  // Usage:
  Pair<String, Integer> pair = new Pair<>("Alice", 30);
  String name = pair.getFirst();
  int age = pair.getSecond();

  Common JDK examples:
  Map.Entry<K, V>
  Function<T, R>
  BiFunction<T, U, R>

Q7: How does try-with-resources work with multiple resources?
------------------------------------------------------------
A:
  try-with-resources (Java 7+) automatically calls close() on AutoCloseable resources
  when the try block exits (normally or exceptionally).

  Multiple resources are declared separated by semicolons:
  try (ResourceA a = new ResourceA(); ResourceB b = new ResourceB(a)) {
      // use a and b
  }  // b.close() called first, then a.close() — reverse declaration order

  Resources are closed in REVERSE ORDER of declaration — important when resources depend
  on each other (b depends on a → close b first, then a).

  Exception handling:
  - If the try body throws exception X, and close() throws exception Y:
    X is the primary exception (propagated); Y is added as a suppressed exception.
  - Retrieve with: x.getSuppressed()
  - This is superior to old finally — primary exception is never silently lost.

  Java 9 enhancement: effectively final resource variables can be used directly:
  Connection conn = getConnection();
  try (conn) { ... }   // conn declared outside; auto-closed inside try

Q8: What is the difference between I/O blocking and non-blocking in Java?
--------------------------------------------------------------------------
A:
  Blocking I/O (classic java.io, java.net):
  - read() / accept() block the calling thread until data is available
  - Thread is suspended (waiting) — consumes OS thread resource while idle
  - Simple to program (sequential flow); poor scalability at high connection counts
  - Model: one thread per connection (or request) — thread-per-request

  Non-blocking I/O (java.nio — Selectors, Channels):
  - Channel.read() returns immediately: either reads data or returns 0 (not ready)
  - A Selector multiplexes many channels on a single thread:
    selector.select() — blocks until at least one channel is ready; returns ready keys
  - One thread can handle thousands of concurrent connections
  - Used by: Netty, Undertow, Vert.x; basis for reactive servers
  - More complex to program (state machine needed)

  Asynchronous I/O (java.nio.file.AsynchronousFileChannel, AsynchronousSocketChannel):
  - Initiates an I/O operation; register a CompletionHandler callback invoked when done
  - No thread blocks during I/O
  - Supported on all platforms with Java NIO.2

  Java 21 virtual threads:
  - Platform thread blocking → wasted OS thread → scalability problem
  - Virtual thread blocking (on I/O, lock, sleep) → JVM parks the virtual thread;
    carrier thread is freed → no OS thread wasted
  - Net effect: blocking java.io code scales like non-blocking NIO when using virtual threads
  - Enables thread-per-request simplicity at NIO scalability
