JAVA MEMORY MODEL (JMM) — INTERVIEW QUESTIONS
==============================================

Q1: What is the Java Memory Model (JMM)?
-----------------------------------------
A:
  The JMM is a specification (JSR-133, Java 5+) that defines:
  1. How threads interact through memory (shared variables)
  2. When a write by one thread becomes visible to another
  3. What reorderings the compiler/JVM/CPU are allowed to perform

  Without JMM guarantees, optimizations like instruction reordering,
  CPU caching, and register allocation can make multi-threaded code behave
  unpredictably. The JMM provides a contract: follow these rules and your
  concurrent code will behave correctly.

  The JMM does NOT describe physical memory (heap/stack) — that is the
  runtime memory layout. The JMM describes VISIBILITY and ORDERING rules.

─────────────────────────────────────────────────────────────
Q2: What is the happens-before relationship?
─────────────────────────────────────────────────────────────
A:
  happens-before (hb) is the FUNDAMENTAL ordering guarantee in the JMM.

  If action A happens-before action B, then:
    - All memory writes performed by A are visible to B
    - A is ordered before B (no reordering across the hb edge)

  Key happens-before rules:

  1. Program Order Rule:
     Each action in a thread happens-before every subsequent action
     in the SAME thread.

  2. Monitor Lock Rule (synchronized):
     Unlocking a monitor (exiting synchronized block) happens-before
     every subsequent lock of that SAME monitor.
     → writes before unlock are visible after the next lock

  3. Volatile Variable Rule:
     A write to a volatile field happens-before every subsequent read
     of that SAME volatile field.

  4. Thread Start Rule:
     Thread.start() on a thread T happens-before any action in T.
     → everything the starting thread wrote before start() is visible
       inside the new thread.

  5. Thread Termination Rule:
     All actions in thread T happen-before Thread.join() returns.
     → after join(), you can safely read results computed by T.

  6. Transitivity:
     If A hb B and B hb C, then A hb C.

  7. Object Construction Rule:
     The completion of an object's constructor happens-before the
     finalizer of that object begins.

  8. CompletableFuture / Future:
     Actions before future.complete() happen-before actions after future.get().

Q3: What does volatile guarantee and NOT guarantee?
─────────────────────────────────────────────────────────────
A:
  GUARANTEES:
  ✅ Visibility: A write to a volatile is immediately visible to all threads.
  ✅ Ordering: volatile reads/writes cannot be reordered with each other
     or with surrounding non-volatile accesses (limited fence semantics).
  ✅ Atomicity for reads and writes of long/double (which are otherwise
     non-atomic on 32-bit JVMs).

  DOES NOT GUARANTEE:
  ❌ Atomicity for compound actions:
       volatile int count;
       count++;  // NOT atomic: read → increment → write are 3 separate ops
       // Use AtomicInteger instead.

  ❌ Mutual exclusion — multiple threads can still interleave.

  Example of what volatile DOES fix:
    class Stopper {
        private volatile boolean stopped = false;  // volatile required!
        public void stop() { stopped = true; }
        public void run() {
            while (!stopped) { doWork(); }  // sees updated value
        }
    }
  Without volatile, the JIT may cache `stopped` in a register and loop forever.

─────────────────────────────────────────────────────────────
Q4: What is instruction reordering and how does the JMM control it?
─────────────────────────────────────────────────────────────
A:
  Modern CPUs and the JIT compiler reorder instructions for performance
  as long as the result appears correct within a single thread (intra-thread
  consistency). But this can break multi-threaded programs.

  Example of dangerous reordering:
    // Thread 1                    // Thread 2
    data = compute();              if (ready) {
    ready = true;                      process(data);  // may see stale data!
                                   }

  If `ready` is not volatile, the CPU/JIT can reorder the two Thread 1
  writes — `ready = true` may become visible BEFORE `data = compute()`.

  Fix: declare `ready` as volatile.
  The volatile write to `ready` creates a memory barrier that prevents
  reordering of preceding writes across it.

  Types of memory barriers (conceptual, JVM-level):
    LoadLoad   — no load can be reordered before another load
    StoreStore — no store can be reordered before another store
    LoadStore  — no load can be reordered before a store
    StoreLoad  — strongest barrier; prevents all reordering (used for volatile)

Q5: Why is the double-checked locking idiom broken without volatile?
─────────────────────────────────────────────────────────────
A:
  class Singleton {
      private static Singleton instance;  // NOT volatile — BROKEN
      public static Singleton getInstance() {
          if (instance == null) {
              synchronized (Singleton.class) {
                  if (instance == null)
                      instance = new Singleton();
              }
          }
          return instance;
      }
  }

  Problem: `instance = new Singleton()` is 3 steps:
    1. Allocate memory
    2. Initialize object (constructor)
    3. Assign reference to `instance`

  The JVM/CPU can reorder to: 1 → 3 → 2.
  A second thread may see a non-null `instance` (step 3 done) but a
  partially initialized object (step 2 not yet done) → NPE or corruption.

  Fix: declare `instance` as volatile.
  The volatile write to `instance` ensures all preceding writes (initialization)
  happen-before the reference assignment is visible to other threads.

─────────────────────────────────────────────────────────────
Q6: What is the difference between synchronized and volatile?
─────────────────────────────────────────────────────────────
A:
  Aspect            | volatile              | synchronized
  ──────────────────┼───────────────────────┼──────────────────────────────
  Visibility        | ✅ guaranteed         | ✅ guaranteed
  Atomicity         | ✅ reads/writes only  | ✅ compound actions too
  Mutual exclusion  | ❌                    | ✅
  Blocking          | ❌ (non-blocking)     | ✅ (can block waiting for lock)
  Use case          | flags, status, refs   | compound check-then-act operations

─────────────────────────────────────────────────────────────
Q7: What is the "out-of-thin-air" safety guarantee?
─────────────────────────────────────────────────────────────
A:
  The JMM guarantees that a thread will never see a value that was never
  written — even in the absence of synchronization for primitives (except
  long/double). The JVM initializes all fields to default values (0, null,
  false) before any thread can observe them, preventing truly garbage values.

  Exception: 64-bit long and double are NOT atomically written on 32-bit
  JVMs — a thread could see a "torn" value. Declare them volatile if shared.

─────────────────────────────────────────────────────────────
Q8: What is false sharing and how do you prevent it?
─────────────────────────────────────────────────────────────
A:
  CPUs load memory in cache lines (~64 bytes). If two threads write to
  different variables that share a cache line, each write invalidates the
  other thread's cache line — causing heavy cache coherence traffic.
  This is false sharing.

  Example:
    long[] counters = new long[2];
    // Thread 1 increments counters[0]
    // Thread 2 increments counters[1]
    // Both are on the same cache line → false sharing!

  Fix 1: Padding — add unused fields to push variables to separate lines:
    @jdk.internal.vm.annotation.Contended  // Java 8+
    long counter1;
    long counter2;

  Fix 2: Use LongAdder / LongAccumulator which are already padded.

  Fix 3: Use per-thread data (ThreadLocal) and aggregate at the end.

─────────────────────────────────────────────────────────────
Q9: How do final fields relate to the JMM?
─────────────────────────────────────────────────────────────
A:
  The JMM provides a special guarantee for final fields:
  Once an object's constructor completes, the values of final fields
  are guaranteed to be visible to ALL threads without synchronization —
  as long as the reference to the object is not published before the
  constructor finishes (no "this" escape).

  This is why immutable objects are inherently thread-safe:
    class ImmutablePoint {
        final int x, y;
        ImmutablePoint(int x, int y) { this.x = x; this.y = y; }
    }
  Any thread receiving a reference to a fully constructed ImmutablePoint
  will see the correct x and y values without any locks.

─────────────────────────────────────────────────────────────
Q10: What is "safe publication" of an object?
─────────────────────────────────────────────────────────────
A:
  Publishing an object means making it visible to other threads.
  Safe publication guarantees that a fully initialized object is visible.

  Safe publication mechanisms:
  ✅ Initialize in a static initializer:
       static final Singleton instance = new Singleton();

  ✅ Store in a volatile field

  ✅ Store in an AtomicReference

  ✅ Store in a final field (with no this-escape)

  ✅ Store in a properly synchronized field
       synchronized(lock) { sharedRef = new MyObj(); }

  Unsafe publication (do NOT do):
  ❌ Store reference in a non-volatile, non-synchronized field without
     any other happens-before guarantee — other threads may see a
     partially constructed object.
