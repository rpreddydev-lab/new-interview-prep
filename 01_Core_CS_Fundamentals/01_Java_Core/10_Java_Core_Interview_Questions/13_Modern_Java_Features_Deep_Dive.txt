SECTION 1 — Optional<T>
===============================================================================

Q1: What is Optional and why was it introduced?
------------------------------------------------
A:
  Optional<T> is a container object that may or may not contain a non-null value.
  Introduced in Java 8 to express "absence of a value" explicitly in the type system,
  replacing the silent null return.

  Before Optional:
    User findUser(String id) { return null; }  // caller forgets to null-check → NPE

  With Optional:
    Optional<User> findUser(String id) { ... }  // caller is forced to handle absence

  Creation:
    Optional.of(value)          // throws NPE if value is null
    Optional.ofNullable(value)  // safe — null becomes Optional.empty()
    Optional.empty()            // explicitly empty

  Checking:
    opt.isPresent()   // true if value present
    opt.isEmpty()     // true if empty (Java 11+)

Q2: What is the difference between orElse(), orElseGet(), and orElseThrow()?
-----------------------------------------------------------------------------
A:
  orElse(T other):
  - Returns value if present; returns `other` if empty.
  - `other` is ALWAYS EVALUATED regardless of whether the Optional is empty.
  - BAD when `other` is an expensive computation or has side effects.

  orElseGet(Supplier<T> supplier):
  - Returns value if present; calls `supplier.get()` only if empty.
  - `supplier` is called LAZILY — only when needed.
  - PREFER over orElse() when fallback is expensive (DB call, object construction).

  orElseThrow(Supplier<X> exceptionSupplier):
  - Returns value if present; throws exception from supplier if empty.
  - Java 10+: orElseThrow() with no args throws NoSuchElementException.

  Example of the orElse trap:
    String name = findUser(id)
        .orElse(generateDefaultName());    // generateDefaultName() ALWAYS runs!
    String name = findUser(id)
        .orElseGet(() -> generateDefaultName()); // generateDefaultName() only when empty

  Interview answer: "I always prefer orElseGet over orElse when the fallback involves
  any computation. orElse is fine only for constants or cheap literals."

Q3: How do you chain transformations on Optional?
-------------------------------------------------
A:
  map(Function<T, R>): transforms the value if present; returns Optional<R>.
    If mapper returns null, result is Optional.empty().

  flatMap(Function<T, Optional<R>>): like map but for when the mapper itself
    returns Optional<R>. Avoids Optional<Optional<R>>.

  filter(Predicate<T>): keeps the value only if predicate returns true; otherwise empty.

  Example — chaining:
    Optional<String> city = findUser(id)
        .map(User::getAddress)          // Optional<Address>
        .filter(addr -> addr.isVerified())
        .map(Address::getCity)          // Optional<String>
        .map(String::toUpperCase);

  ifPresent(Consumer<T>): performs action if value present; no-op if empty.
  ifPresentOrElse(Consumer, Runnable): Java 9+ — action if present, else run fallback.

Q4: What are the anti-patterns of Optional?
--------------------------------------------
A:
  1. Optional as a field:
     class User { Optional<String> nickname; }  // BAD
     Optional is not Serializable. Use null for optional fields and expose Optional
     only in getter return types.

  2. Optional as a method parameter:
     void process(Optional<String> name) { ... }  // BAD
     Forces callers to wrap values in Optional. Use method overloading or null instead.

  3. Using isPresent() + get() instead of map/orElse:
     if (opt.isPresent()) { String s = opt.get(); }  // verbose anti-pattern
     Use: opt.map(s -> ...).orElse(...) — functional style.

  4. Optional.of() on potentially null values:
     Optional.of(map.get(key))  // NPE if key absent! Use Optional.ofNullable().

  5. Returning null instead of Optional.empty():
     Optional<User> findUser() { return null; }  // defeats the purpose entirely

  Rule: Optional is designed for return types only where null is a meaningful absence.

SECTION 2 — Stream Collectors Deep Dive
===============================================================================

Q5: What are the most important Collectors methods and what do they do?
-----------------------------------------------------------------------
A:
  Collectors.toList()         — collect to mutable ArrayList (pre-Java 16)
  Collectors.toUnmodifiableList() — collect to immutable list (Java 10+)
  Stream.toList()             — shorthand for unmodifiable list (Java 16+)
  Collectors.toSet()          — collect to HashSet (no order, no duplicates)
  Collectors.toMap(keyMapper, valueMapper) — collect to HashMap
  Collectors.joining()        — concatenate strings
  Collectors.counting()       — count elements
  Collectors.summingInt/Long/Double() — sum a numeric field
  Collectors.averagingInt/Long/Double() — average
  Collectors.summarizingInt() — returns IntSummaryStatistics (count, sum, min, max, avg)
  Collectors.groupingBy()     — group by a classifier function → Map<K, List<V>>
  Collectors.partitioningBy() — split by predicate → Map<Boolean, List<V>>
  Collectors.collectingAndThen() — wrap a collector and post-process the result
  Collectors.teeing()         — apply two collectors simultaneously, merge results (Java 12+)

Q6: How does Collectors.toMap() work and what pitfalls exist?
--------------------------------------------------------------
A:
  Basic form: Collectors.toMap(keyMapper, valueMapper)
    Map<String, Integer> nameToAge = users.stream()
        .collect(Collectors.toMap(User::getName, User::getAge));

  Pitfall 1 — Duplicate keys:
    If two elements map to the same key, toMap() throws IllegalStateException.
    Fix: provide a merge function (third argument):
      Collectors.toMap(User::getDept, User::getSalary, Integer::max)
      // keep the higher salary when department is duplicated

  Pitfall 2 — null values:
    toMap() does NOT allow null values (HashMap.put(key, null) would fail).
    Fix: use Collectors.toUnmodifiableMap() or filter nulls first, or use
    a custom map: Collectors.toMap(k, v, merge, HashMap::new)

  Pitfall 3 — insertion order not preserved:
    Default is HashMap. For LinkedHashMap (insertion order):
      Collectors.toMap(k, v, (e1, e2) -> e1, LinkedHashMap::new)

Q7: How does groupingBy() work? Show a multi-level grouping example.
---------------------------------------------------------------------
A:
  Single-level grouping:
    Map<String, List<User>> byDept = users.stream()
        .collect(Collectors.groupingBy(User::getDepartment));
    // key: department name, value: list of users in that dept

  Counting within groups (downstream collector):
    Map<String, Long> countByDept = users.stream()
        .collect(Collectors.groupingBy(User::getDepartment, Collectors.counting()));

  Multi-level (nested) grouping:
    Map<String, Map<String, List<User>>> byDeptThenCity = users.stream()
        .collect(Collectors.groupingBy(User::getDepartment,
            Collectors.groupingBy(User::getCity)));
    // byDeptThenCity.get("Engineering").get("London") → list of engineers in London

  Average salary by department:
    Map<String, Double> avgSalaryByDept = users.stream()
        .collect(Collectors.groupingBy(User::getDepartment,
            Collectors.averagingDouble(User::getSalary)));

  Interview answer: "groupingBy is the streams equivalent of SQL GROUP BY. The second
  argument (downstream collector) is the aggregation you'd put in SELECT."

Q8: What is partitioningBy() and when is it more appropriate than groupingBy()?
--------------------------------------------------------------------------------
A:
  partitioningBy(Predicate) always returns Map<Boolean, List<T>> — exactly two groups.
  groupingBy(Function) returns Map<K, List<T>> — potentially many groups.

  Use partitioningBy when the classification is binary (pass/fail, active/inactive):
    Map<Boolean, List<User>> activeVsInactive = users.stream()
        .collect(Collectors.partitioningBy(User::isActive));
    List<User> active = activeVsInactive.get(true);
    List<User> inactive = activeVsInactive.get(false);

  With downstream collector:
    Map<Boolean, Long> countActiveVsInactive = users.stream()
        .collect(Collectors.partitioningBy(User::isActive, Collectors.counting()));

Q9: What does Collectors.joining() do?
---------------------------------------
A:
  joining() — concatenates all strings (delimiter-free):
    "Java8Java11Java17"

  joining(delimiter):
    stream.collect(Collectors.joining(", "))  // "Java8, Java11, Java17"

  joining(delimiter, prefix, suffix):
    stream.collect(Collectors.joining(", ", "[", "]"))  // "[Java8, Java11, Java17]"

  Very useful for building comma-separated lists, CSV rows, SQL IN clauses.

  Example: generate SQL IN clause:
    String inClause = ids.stream()
        .map(String::valueOf)
        .collect(Collectors.joining(", ", "WHERE id IN (", ")"));

SECTION 3 — Method References (All 4 Types)
===============================================================================

Q10: What are the four types of method references in Java 8?
-------------------------------------------------------------
A:
  Method references are shorthand for lambdas that only call a single method.
  Syntax: ClassName::methodName or instance::methodName

  TYPE 1 — Static method reference: ClassName::staticMethod
    // Lambda:         n -> Integer.parseInt(n)
    // Reference:      Integer::parseInt
    Function<String, Integer> parser = Integer::parseInt;
    List<Integer> nums = strs.stream().map(Integer::parseInt).collect(toList());

  TYPE 2 — Instance method reference (bound): instance::instanceMethod
    // Lambda:         s -> s.toUpperCase()  (specific instance, 'this' bound)
    String prefix = "Hello";
    Supplier<String> upper = prefix::toUpperCase;
    // Lambda:         str -> myObj.process(str)
    Consumer<String> c = myLogger::log;

  TYPE 3 — Instance method reference (unbound): ClassName::instanceMethod
    // Lambda:         (String s) -> s.toUpperCase()  (instance is the first argument)
    // Reference:      String::toUpperCase
    Function<String, String> upper = String::toUpperCase;
    // Lambda:         (String s, String t) -> s.compareTo(t)
    Comparator<String> cmp = String::compareTo;

  TYPE 4 — Constructor reference: ClassName::new
    // Lambda:         () -> new ArrayList<>()
    Supplier<List<String>> listFactory = ArrayList::new;
    // Lambda:         (String s) -> new User(s)
    Function<String, User> userFactory = User::new;

  Distinction Type 2 vs Type 3:
    Type 2 (bound): the instance is fixed at reference creation time.
    Type 3 (unbound): the instance is the FIRST argument supplied at invocation time.

Q11: When should you prefer method references over lambdas?
------------------------------------------------------------
A:
  Prefer method references when:
  - The lambda just delegates to one existing method without transformation.
  - It improves readability (self-documenting names).
    stream.filter(User::isActive)            // clear intent
    stream.filter(u -> u.isActive())         // slightly more verbose, no gain

  Prefer lambdas when:
  - The logic involves multiple operations or conditions.
    stream.filter(u -> u.getAge() > 18 && u.isActive())  // lambda clearer here
  - The method name would require more context to understand.

SECTION 4 — Records (Java 16+)
===============================================================================

Q12: What is a Java Record and what does it automatically generate?
-------------------------------------------------------------------
A:
  A record is a transparent data carrier — a concise class for modeling immutable data.
  Declared with the `record` keyword; fields listed in the header are called components.

  record Point(int x, int y) {}

  The compiler automatically generates:
  - private final fields for each component
  - Public accessor methods named exactly like the component (not getX() — just x())
  - A canonical constructor taking all components
  - equals() based on all components
  - hashCode() based on all components
  - toString() showing all components

  Usage:
    Point p = new Point(3, 4);
    p.x();      // 3 — NOT p.getX()
    p.y();      // 4
    p.equals(new Point(3, 4));   // true
    p.toString();  // "Point[x=3, y=4]"

Q13: What are the restrictions on Records?
------------------------------------------
A:
  Records are IMPLICITLY:
  - final (cannot be extended)
  - extends java.lang.Record (cannot extend another class)

  Records CANNOT:
  - Declare instance fields outside the record header (no extra state)
  - Be abstract
  - Have mutable state (fields are final)

  Records CAN:
  - Implement interfaces
  - Have static fields and static methods
  - Have instance methods (non-mutating)
  - Have multiple constructors (but non-canonical must delegate to canonical)
  - Override accessor methods, equals, hashCode, toString
  - Have a compact canonical constructor (for validation):
    record Range(int min, int max) {
        Range {  // compact constructor — no parameter list, assignments auto-done
            if (min > max) throw new IllegalArgumentException("min > max");
        }
    }

Q14: When should you use Records vs classes vs Lombok @Data?
-------------------------------------------------------------
A:
  Use Records when:
  - You need a simple, immutable data carrier (DTOs, value objects, query results)
  - The object's identity is defined entirely by its data (equals/hashCode by value)
  - No inheritance needed

  Use plain class when:
  - Mutable state is required (records can't mutate fields)
  - You need to extend another class
  - Custom equals/hashCode that don't cover all fields

  Records vs Lombok @Data:
  - Records are first-class language feature — no annotation processor, no compile-time magic
  - @Data generates getters (getX()) but records generate accessors (x()) — different style
  - Records enforce immutability; @Data does not
  - Records work perfectly with pattern matching; @Data does not integrate as natively
  - Prefer records in Java 16+ for new code; @Data for legacy codebases

SECTION 5 — Sealed Classes (Java 17+)
===============================================================================

Q15: What are sealed classes and why are they useful?
-----------------------------------------------------
A:
  A sealed class (or interface) restricts which other classes/interfaces may extend or
  implement it. Declared with the `sealed` keyword and a `permits` clause.

  public sealed interface Shape permits Circle, Rectangle, Triangle {}
  public record Circle(double radius) implements Shape {}
  public record Rectangle(double w, double h) implements Shape {}
  public record Triangle(double base, double height) implements Shape {}

  Each permitted subtype must be declared as one of:
  - `final` — no further extension allowed
  - `sealed` — further restricted extension
  - `non-sealed` — open to any extension (escape hatch)

  Why sealed classes?
  1. Closed hierarchies: you know ALL possible subtypes at compile time.
  2. Exhaustive switch: the compiler verifies that switch covers all permitted subtypes.
  3. Expressive domain modeling: algebraic data types (like Scala case classes, Kotlin sealed).
  4. Safe pattern matching: no default needed if all cases are covered.

Q16: How do sealed classes interact with pattern matching switch?
----------------------------------------------------------------
A:
  With a sealed hierarchy, switch can be exhaustive without a default case:

  sealed interface Shape permits Circle, Rectangle, Triangle {}
  record Circle(double r) implements Shape {}
  record Rectangle(double w, double h) implements Shape {}
  record Triangle(double b, double h) implements Shape {}

  double area(Shape shape) {
      return switch (shape) {
          case Circle c    -> Math.PI * c.r() * c.r();
          case Rectangle r -> r.w() * r.h();
          case Triangle t  -> 0.5 * t.b() * t.h();
          // No default needed — compiler knows all subtypes!
      };
  }

  If you add a new permitted subtype (e.g., Pentagon), the compiler immediately
  flags every switch that is no longer exhaustive — compile-time safety net.

  This is the primary advantage over non-sealed hierarchies where you'd need
  a default case (or risk missing a subtype at runtime).

SECTION 6 — Text Blocks (Java 15+)
===============================================================================

Q17: What is a Text Block and what problems does it solve?
----------------------------------------------------------
A:
  A text block is a multi-line string literal delimited by triple double quotes (""").
  Introduced in Java 15 (final). Eliminates manual string concatenation and escape hell.

  Before text blocks:
    String json = "{\n" +
                  "  \"name\": \"Alice\",\n" +
                  "  \"age\": 30\n" +
                  "}";

  With text block:
    String json = """
            {
              "name": "Alice",
              "age": 30
            }
            """;

  Rules:
  - Opening """ must be on its own line (content starts on the next line).
  - Trailing """ determines indentation removal (incidental whitespace stripped).
  - The compiler removes the common leading whitespace of all content lines.
  - Closing """ on its own line adds a final newline; on the last content line removes it.

  Special escapes in text blocks:
    \   (backslash at end of line) — suppress newline (line continuation)
    \s  — force a trailing space (otherwise trimmed)

  Text blocks preserve embedded double quotes without escaping:
    String html = """
            <div class="container">
                <p>Hello</p>
            </div>
            """;

Q18: How is incidental whitespace handled in text blocks?
---------------------------------------------------------
A:
  The compiler determines the "re-indentation" by finding the minimum indentation
  of all non-blank content lines and the closing """.

  """
          SELECT *
          FROM users
          WHERE id = ?
          """
  → indentation stripped to zero (closing """ has same indent as content)

  Tip: position the closing """ to control how much whitespace is stripped.
  Moving closing """ to column 0 preserves all indentation in the content.

SECTION 7 — Switch Expressions (Java 14+ final, Java 21 pattern matching)
===============================================================================

Q19: What is the difference between switch statement and switch expression?
---------------------------------------------------------------------------
A:
  Switch STATEMENT (traditional — pre-Java 14):
    switch (day) {
        case MONDAY:
        case TUESDAY:
            result = "Weekday";
            break;
        case SATURDAY:
        case SUNDAY:
            result = "Weekend";
            break;
        default:
            result = "Unknown";
    }
  Problems: fall-through bugs (missing break), no return value, verbose.

  Switch EXPRESSION (Java 14+ — final):
    String result = switch (day) {
        case MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY -> "Weekday";
        case SATURDAY, SUNDAY -> "Weekend";
    };
  // Arrow syntax: no fall-through, expression yields a value

  Multiple statements with yield:
    int value = switch (status) {
        case ACTIVE -> 1;
        case PENDING -> {
            log.info("Pending");
            yield 0;   // yield returns the value from a block
        }
        case INACTIVE -> -1;
    };

  Key differences:
  - Arrow (->) cases cannot fall through
  - Switch expression MUST be exhaustive (compiler error if a case is missing)
  - yield exits a block case with a value; return exits the enclosing method

Q20: What is pattern matching switch (Java 21)?
------------------------------------------------
A:
  Java 21 (JEP 441, final) extends switch to match on types and deconstruct patterns.

  Object obj = ...;
  String result = switch (obj) {
      case Integer i   -> "Integer: " + i;
      case String s    -> "String: " + s;
      case null        -> "null value";
      default          -> "Other: " + obj;
  };

  Guarded patterns (with when):
    switch (shape) {
        case Circle c when c.radius() > 100 -> "Large circle";
        case Circle c                        -> "Small circle";
        case Rectangle r when r.w() == r.h() -> "Square";
        case Rectangle r                     -> "Rectangle";
    }

  Combined with sealed classes → exhaustive, no default needed.

  Interview answer: "Pattern matching switch replaces complex instanceof chains and
  polymorphic dispatch with a single, type-safe, exhaustive switch block."

SECTION 8 — var keyword (Java 10+)
===============================================================================

Q21: What is var in Java and what are its rules?
-------------------------------------------------
A:
  var (Java 10+) enables local variable type inference — the compiler infers the type
  from the initializer. It is NOT dynamic typing; the type is still static and fixed.

    var list = new ArrayList<String>();  // inferred as ArrayList<String>
    var name = "Alice";                  // inferred as String
    var i = 42;                          // inferred as int

  RULES — var is ONLY allowed for:
  - Local variable declarations with an initializer
  - Variables in for loops: for (var item : collection) { ... }
  - Variables in try-with-resources: try (var conn = getConnection()) { ... }
  - Lambda parameters (Java 11+): (var x, var y) -> x + y  (allows annotations on params)

  var is NOT allowed for:
  - Method parameters:            void process(var x) { }   // COMPILE ERROR
  - Fields:                       class Foo { var x = 1; } // COMPILE ERROR
  - Return types:                 var compute() { }         // COMPILE ERROR
  - null initializer:             var x = null;             // COMPILE ERROR (type unknown)
  - Array initializers:           var arr = { 1, 2, 3 };   // COMPILE ERROR

  var with generics — diamond operator:
    var map = new HashMap<String, List<Integer>>();  // fully inferred
    // Removes the redundant type on the right side

Q22: When should you use var and when should you avoid it?
----------------------------------------------------------
A:
  Use var when:
  - The type is obvious from the right-hand side (new XxxClass(), factory method):
    var executor = Executors.newFixedThreadPool(4);  // clear enough
  - Long generic types make the declaration unwieldy:
    Map<String, List<UserSummaryDto>> map = new HashMap<>();  // verbose
    var map = new HashMap<String, List<UserSummaryDto>>();    // cleaner
  - For loop variables in enhanced for: for (var entry : map.entrySet()) { ... }

  Avoid var when:
  - The type is not obvious from the context:
    var result = process(data);  // what type is result? unreadable without IDE
  - It reduces code clarity in complex expressions:
    var x = a.b().c().d();  // reader must trace through the chain
  - It hides important type distinctions (int vs long vs double):
    var timeout = 30;  // is this seconds? milliseconds? what type exactly?

SECTION 9 — String Methods Added in Java 11–21
===============================================================================

Q23: What important String methods were added after Java 8?
------------------------------------------------------------
A:
  Java 11 additions:
    isBlank()         — true if string is empty or contains only whitespace
                        (better than isEmpty() which misses " ")
    strip()           — removes leading and trailing whitespace (Unicode-aware)
    stripLeading()    — removes leading whitespace only
    stripTrailing()   — removes trailing whitespace only
    repeat(int n)     — returns string repeated n times: "ab".repeat(3) = "ababab"
    lines()           — returns Stream<String> of lines (splits on line terminators)

    Difference: trim() uses ASCII whitespace (<=\u0020); strip() uses Character.isWhitespace()
    which handles Unicode whitespace characters too. Always prefer strip() in Java 11+.

  Java 12 additions:
    indent(int n)     — adjusts indentation of each line by n spaces (positive = add, negative = remove)
    transform(Function<String, R>) — applies a function to the string and returns the result
      "hello".transform(String::toUpperCase)  // "HELLO"

  Java 15 additions (text block support):
    formatted(Object... args) — like String.format() but as an instance method
      "Hello, %s!".formatted("Alice")  // "Hello, Alice!"
    stripIndent()     — strips incidental whitespace (used by text blocks internally)
    translateEscapes() — translates escape sequences (\n, \t, etc.) in the string

  Java 21:
    No major new String methods, but String now works seamlessly with
    pattern matching switch and sequenced collections.

Q24: What is the difference between String.trim() and String.strip()?
----------------------------------------------------------------------
A:
  trim():
  - Removes characters with code point <= 32 (\u0020 = space, \t, \n, \r, etc.)
  - Does NOT handle Unicode-defined whitespace (e.g., \u2000–\u200A thin spaces,
    \u3000 ideographic space)
  - Legacy method (Java 1.0)

  strip() (Java 11+):
  - Uses Character.isWhitespace() — handles full Unicode whitespace set
  - Correct for international text processing
  - Used internally by text blocks

  Example:
    String s = "\u2000hello\u2000";
    s.trim().equals("hello")   // false — \u2000 not removed by trim()
    s.strip().equals("hello")  // true  — strip handles Unicode whitespace

  Rule: always use strip() in new Java 11+ code.

SECTION 10 — instanceof Pattern Matching (Java 16+)
===============================================================================

Q25: What is instanceof pattern matching and how does it work?
--------------------------------------------------------------
A:
  Traditional instanceof required an explicit cast:
    if (obj instanceof String) {
        String s = (String) obj;  // redundant cast
        System.out.println(s.length());
    }

  Pattern matching instanceof (Java 16+):
    if (obj instanceof String s) {
        System.out.println(s.length());  // s is String, already cast and bound
    }
  - `s` is called a pattern variable — bound only in the scope where the condition is true.
  - In the `else` branch, `s` is NOT in scope (the condition was false).

  With negation:
    if (!(obj instanceof String s)) {
        return;  // early exit for non-String
    }
    // s is in scope here — String guaranteed
    System.out.println(s.length());

  Combined with conditions:
    if (obj instanceof String s && s.length() > 5) {
        // both conditions true; s is a String of length > 5
    }

Q26: How does instanceof pattern matching work with records and deconstruction (Java 21)?
------------------------------------------------------------------------------------------
A:
  Java 21 (JEP 440, final) adds record patterns — destructuring in instanceof and switch:

  record Point(int x, int y) {}
  record Line(Point start, Point end) {}

  instanceof record pattern:
    if (obj instanceof Point(int x, int y)) {
        System.out.println(x + ", " + y);  // x and y directly available
    }

  Nested record pattern:
    if (obj instanceof Line(Point(int x1, int y1), Point(int x2, int y2))) {
        // all four components directly available
    }

  In switch:
    Object shape = ...;
    switch (shape) {
        case Point(int x, int y) -> System.out.println("Point at " + x + "," + y);
        case Circle(double r)    -> System.out.println("Circle r=" + r);
        default                  -> System.out.println("Other");
    }

  Interview answer: "Record patterns eliminate the verbose pattern of instanceof-cast-then-
  access. You get type checking and deconstruction in one step — much closer to functional
  pattern matching in Scala or Kotlin."

SECTION 11 — Streams: Terminal vs Intermediate, Lazy Evaluation
===============================================================================

Q27: What is the difference between intermediate and terminal stream operations?
--------------------------------------------------------------------------------
A:
  Intermediate operations:
  - Return a new Stream — the pipeline is NOT executed yet.
  - LAZY: nothing runs until a terminal operation is called.
  - Examples: filter(), map(), flatMap(), sorted(), distinct(), limit(), skip(),
              peek(), mapToInt(), mapToLong(), mapToDouble()

  Terminal operations:
  - Consume the stream — trigger the actual pipeline execution.
  - Return a result or side effect (not a Stream).
  - After a terminal op, the stream is CONSUMED and cannot be reused.
  - Examples: collect(), forEach(), findFirst(), findAny(), anyMatch(), allMatch(),
              noneMatch(), count(), min(), max(), reduce(), toArray(), sum()

  Lazy evaluation example:
    List<String> names = users.stream()
        .filter(u -> { System.out.println("filter: " + u.name); return u.age > 18; })
        .map(u -> { System.out.println("map: " + u.name); return u.name; })
        .findFirst();  // ONLY processes elements until first match is found
    // If the first user is over 18, only ONE filter + ONE map executes!
    // Lazy evaluation enables short-circuit optimization.

  Interview answer: "Intermediate operations build a pipeline description. Nothing runs
  until a terminal operation is called. This enables lazy evaluation and short-circuit
  optimization — findFirst on a filter stops as soon as the first match is found."

Q28: What do anyMatch, allMatch, noneMatch, and reduce do?
----------------------------------------------------------
A:
  anyMatch(Predicate): true if at least one element matches. Short-circuits on first match.
    boolean hasMajor = ages.stream().anyMatch(age -> age >= 18);

  allMatch(Predicate): true if ALL elements match. Short-circuits on first non-match.
    boolean allMajor = ages.stream().allMatch(age -> age >= 18);

  noneMatch(Predicate): true if NO element matches. Short-circuits on first match.
    boolean noNegative = ages.stream().noneMatch(age -> age < 0);

  reduce(identity, BinaryOperator): combines elements using an associative function:
    int sum = numbers.stream().reduce(0, Integer::sum);       // 0 + n1 + n2 + ...
    int product = numbers.stream().reduce(1, (a, b) -> a * b);

  reduce without identity returns Optional (stream may be empty):
    Optional<Integer> max = numbers.stream().reduce(Integer::max);

  Interview: "anyMatch/allMatch/noneMatch are short-circuiting — they don't process the
  full stream if the answer is known early. reduce is the general aggregation primitive
  that collect() is built on top of."

Q29: What is the difference between findFirst() and findAny()?
--------------------------------------------------------------
A:
  findFirst():
  - Returns the first element in encounter order.
  - On sequential streams: deterministic — always returns the same element.
  - On parallel streams: forces synchronization to determine encounter order — slower.

  findAny():
  - Returns ANY element (no guarantee which one).
  - On sequential streams: usually returns the first (implementation detail, not guaranteed).
  - On parallel streams: returns whichever thread finds one first — faster.

  Rule: use findFirst() when order matters; findAny() when you just need "any one element"
  and may run the stream in parallel.
