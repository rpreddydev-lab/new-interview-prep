CHECKED vs UNCHECKED EXCEPTIONS
==================================

DEFINITIONS
------------
  Checked Exceptions:
    - Subclass of Exception but NOT RuntimeException
    - Compiler ENFORCES that you either catch them or declare them with throws
    - Represent EXTERNAL conditions the caller should know about and handle
    - Examples: IOException, SQLException, ClassNotFoundException, InterruptedException

  Unchecked Exceptions:
    - Subclass of RuntimeException (or Error)
    - Compiler does NOT enforce handling — optional to catch
    - Represent PROGRAMMING ERRORS (bugs), not external failures
    - Examples: NullPointerException, IllegalArgumentException, ClassCastException

COMPILER ENFORCEMENT: HOW IT WORKS
-------------------------------------
  // Checked — compiler requires handling:
  public void readFile(String path) throws IOException {  // ← must declare
      FileReader fr = new FileReader(path);               // throws checked FileNotFoundException
  }

  // Option 1: Declare with throws (propagate to caller)
  public void process() throws IOException {
      readFile("data.txt");
  }

  // Option 2: Catch and handle
  public void process() {
      try {
          readFile("data.txt");
      } catch (IOException e) {
          log.error("File read failed", e);
          // handle or rethrow
      }
  }

  // Unchecked — no compile-time requirement:
  public void divide(int a, int b) {
      int result = a / b; // throws ArithmeticException — no declaration needed
  }

WHEN TO USE CHECKED EXCEPTIONS
--------------------------------
  Use checked exceptions when:
  ✅ The caller can MEANINGFULLY recover from the failure
  ✅ The failure is an EXPECTED external condition, not a programming error
  ✅ You want to document failure modes in the method's API (throws clause = contract)
  ✅ Dealing with I/O, network, database, parsing, or external systems

  Examples:
    - File not found → caller might ask user to choose a different file
    - Database connection failed → caller might retry or fail gracefully
    - Malformed XML → caller might log and skip that entry
    - Thread interrupted → caller might clean up and stop

WHEN TO USE UNCHECKED EXCEPTIONS
-----------------------------------
  Use unchecked exceptions when:
  ✅ The exception represents a PROGRAMMING ERROR (null check, invalid argument)
  ✅ The caller CANNOT reasonably recover — it's a bug, not a condition
  ✅ Propagating the exception through many layers would pollute signatures
  ✅ Building a framework/library where forcing checked exceptions is too restrictive

  Examples:
    - Null pointer → fix the code, don't catch NPE everywhere
    - Index out of bounds → array access bug, fix the logic
    - Illegal argument → validate inputs before calling (IAE signals caller's mistake)
    - Unsupported operation → indicates a programming mistake using the wrong type

THE CHECKED EXCEPTION CONTROVERSY
------------------------------------
  Checked exceptions are a Java-specific design (unique among major languages).
  They are debated in the industry:

  Arguments FOR checked exceptions:
  + Forces callers to acknowledge possible failures
  + Method signature documents what can go wrong
  + Prevents accidentally swallowing errors

  Arguments AGAINST checked exceptions:
  - Pollute method signatures throughout a call chain
  - Force wrapping in try/catch even when you can't do anything useful
  - Code inside lambdas/streams cannot throw checked exceptions (interface mismatch)
  - Modern frameworks (Spring, Hibernate) often wrap checked exceptions in unchecked ones

  // Problem: checked exceptions inside lambdas:
  List<String> paths = List.of("a.txt", "b.txt");

  // ❌ Does not compile — lambda can't throw checked IOException
  paths.forEach(p -> readFile(p));

  // ✅ Must wrap:
  paths.forEach(p -> {
      try { readFile(p); }
      catch (IOException e) { throw new RuntimeException(e); }
  });

  // ✅ Or use a helper functional interface that allows checked exceptions
  @FunctionalInterface
  interface ThrowingConsumer<T> {
      void accept(T t) throws Exception;
  }

WRAPPING CHECKED AS UNCHECKED (EXCEPTION TRANSLATION)
-------------------------------------------------------
  A common pattern in frameworks is to wrap checked exceptions in unchecked ones
  to avoid polluting signatures while preserving the original cause:

  // Spring's DataAccessException wraps all JDBC checked exceptions:
  try {
      // JDBC code throwing checked SQLException
      connection.prepareStatement(sql).execute();
  } catch (SQLException e) {
      throw new DataAccessException("Query failed", e); // unchecked, cause preserved
  }

  // Always preserve the original cause in the constructor:
  throw new RuntimeException("Failed to load config", e); // ✅ cause preserved
  throw new RuntimeException("Failed to load config");    // ❌ cause lost!

THROWS CLAUSE AND INHERITANCE
--------------------------------
  When overriding a method, the subclass CAN:
  - Declare the SAME checked exceptions as the parent
  - Declare a NARROWER (more specific) checked exception
  - Declare NO checked exceptions (eliminate the throws clause)
  - Declare unchecked exceptions freely

  The subclass CANNOT:
  - Declare NEW or BROADER checked exceptions than the parent

  Example:
    class Parent {
        void open() throws IOException { }
    }
    class Child extends Parent {
        @Override
        void open() throws FileNotFoundException { }  // ✅ narrower (FileNotFoundException ⊂ IOException)
        // void open() throws Exception { }           // ❌ broader — won't compile
        // void open() { }                            // ✅ no exception — allowed
    }

COMPARISON TABLE
-----------------
  Aspect                  | Checked Exception         | Unchecked Exception
  ------------------------|---------------------------|------------------------------
  Superclass              | Exception (not RuntimeEx) | RuntimeException / Error
  Compiler enforces?      | Yes                       | No
  Must declare throws?    | Yes (or catch it)         | No
  Represents              | External condition        | Programming error / bug
  Caller can recover?     | Usually yes               | Usually no
  Common examples         | IOException, SQLException | NPE, IAE, ClassCastException
  Framework trend         | Being phased out (Spring) | Preferred in modern APIs
  Lambda compatible?      | No (causes compile error) | Yes

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between checked and unchecked exceptions?
A: Checked exceptions (subclass of Exception but not RuntimeException) must be declared
   with throws or caught — the compiler enforces this. They represent recoverable external
   conditions. Unchecked exceptions (RuntimeException or Error subclasses) don't require
   explicit handling — they represent programming bugs where the caller cannot meaningfully recover.

Q: Why can't lambdas throw checked exceptions?
A: Lambda expressions must match the functional interface they're used with.
   Standard interfaces like Consumer<T>, Function<T,R> don't declare throws in their
   abstract method signatures. Since lambdas can't add new checked exceptions that
   don't appear in the interface, any checked exception inside a lambda body won't compile.
   The workaround is to catch and rethrow as unchecked, or define a custom functional
   interface that declares throws Exception.

Q: Is it good practice to catch Exception or Throwable?
A: Catching Exception is generally bad practice because it catches ALL exceptions —
   both checked (like IOException) AND unchecked (like NullPointerException, bugs).
   This can silently swallow bugs. Catching Throwable is even worse — it also catches Errors
   like OutOfMemoryError. Only framework/top-level handlers (servlet containers, test runners)
   should catch Exception or Throwable, and only for logging purposes.

Q: When would you convert a checked exception to an unchecked?
A: When the checked exception cannot be recovered from at the current layer (wrapping in
   a RuntimeException to propagate cleanly), or when you're building a framework/library
   that should not force callers to handle checked exceptions (e.g., Spring's DataAccessException
   wraps all SQLExceptions). Always preserve the original cause: new RuntimeException(message, cause).
