CUSTOM EXCEPTIONS
==================

WHY CREATE CUSTOM EXCEPTIONS?
-------------------------------
  Custom exceptions allow you to:
  - Give meaningful names to domain-specific errors
  - Carry additional context (error codes, affected fields, etc.)
  - Create exception hierarchies that match your domain
  - Separate application-layer concerns from low-level I/O or SQL exceptions
  - Enable callers to catch errors at the right level of abstraction

  Instead of: throw new RuntimeException("User not found with id: " + id);
  Use:         throw new UserNotFoundException(id);

BASIC CUSTOM EXCEPTION
------------------------
  // Unchecked custom exception (extend RuntimeException)
  public class UserNotFoundException extends RuntimeException {

      private final long userId;

      public UserNotFoundException(long userId) {
          super("User not found with ID: " + userId);
          this.userId = userId;
      }

      public UserNotFoundException(long userId, Throwable cause) {
          super("User not found with ID: " + userId, cause);
          this.userId = userId;
      }

      public long getUserId() {
          return userId;
      }
  }

  // Usage:
  public User findUser(long id) {
      return userRepository.findById(id)
          .orElseThrow(() -> new UserNotFoundException(id));
  }

CHECKED CUSTOM EXCEPTION
--------------------------
  // Extend Exception (not RuntimeException) for checked behavior
  public class InsufficientFundsException extends Exception {

      private final BigDecimal balance;
      private final BigDecimal amount;

      public InsufficientFundsException(BigDecimal balance, BigDecimal amount) {
          super(String.format("Insufficient funds: balance=%.2f, requested=%.2f", balance, amount));
          this.balance = balance;
          this.amount = amount;
      }

      public BigDecimal getBalance()  { return balance; }
      public BigDecimal getAmount()   { return amount; }
      public BigDecimal getShortfall() { return amount.subtract(balance); }
  }

  // Caller MUST handle:
  public void withdraw(BigDecimal amount) throws InsufficientFundsException {
      if (balance.compareTo(amount) < 0) {
          throw new InsufficientFundsException(balance, amount);
      }
      balance = balance.subtract(amount);
  }

EXCEPTION HIERARCHY FOR LARGE APPLICATIONS
---------------------------------------------
  Build a hierarchy so callers can catch at any level of granularity:

  ApplicationException (base — unchecked)
  ├── ServiceException
  │   ├── UserServiceException
  │   │   ├── UserNotFoundException
  │   │   └── UserAlreadyExistsException
  │   └── OrderServiceException
  │       ├── OrderNotFoundException
  │       └── OrderAlreadyProcessedException
  └── RepositoryException
      ├── DataAccessException
      └── OptimisticLockException

  // Base exception:
  public class ApplicationException extends RuntimeException {
      private final String errorCode;

      public ApplicationException(String errorCode, String message) {
          super(message);
          this.errorCode = errorCode;
      }

      public ApplicationException(String errorCode, String message, Throwable cause) {
          super(message, cause);
          this.errorCode = errorCode;
      }

      public String getErrorCode() { return errorCode; }
  }

  // Specific subclass:
  public class UserNotFoundException extends ApplicationException {
      public UserNotFoundException(long id) {
          super("USER_NOT_FOUND", "User not found: " + id);
      }
  }

  // Caller can catch at different levels:
  try {
      userService.findUser(id);
  } catch (UserNotFoundException e) {       // most specific
      return ResponseEntity.notFound().build();
  } catch (UserServiceException e) {        // broader
      return ResponseEntity.badRequest().body(e.getMessage());
  } catch (ApplicationException e) {        // catch-all for domain exceptions
      return ResponseEntity.internalServerError().body("Application error");
  }

THE FOUR CONSTRUCTORS CONVENTION
-----------------------------------
  By convention, each exception class should provide four constructors
  matching the four Throwable constructors:

  public class MyException extends RuntimeException {
      // 1. No args
      public MyException() { super(); }

      // 2. Message only
      public MyException(String message) { super(message); }

      // 3. Message + cause
      public MyException(String message, Throwable cause) { super(message, cause); }

      // 4. Cause only (message defaults to cause.toString())
      public MyException(Throwable cause) { super(cause); }
  }

  This makes the exception maximally flexible for callers.

ENRICHED EXCEPTIONS WITH CONTEXT
-----------------------------------
  Add domain-relevant fields to communicate exactly what went wrong:

  public class ValidationException extends RuntimeException {
      private final Map<String, String> fieldErrors; // field → error message

      public ValidationException(Map<String, String> fieldErrors) {
          super("Validation failed: " + fieldErrors.keySet());
          this.fieldErrors = Collections.unmodifiableMap(new HashMap<>(fieldErrors));
      }

      public Map<String, String> getFieldErrors() { return fieldErrors; }

      public boolean hasError(String field) { return fieldErrors.containsKey(field); }
  }

  // Usage:
  Map<String, String> errors = new HashMap<>();
  if (user.getName() == null) errors.put("name", "Name is required");
  if (user.getEmail() == null) errors.put("email", "Email is required");
  if (!errors.isEmpty()) throw new ValidationException(errors);

BEST PRACTICES FOR CUSTOM EXCEPTIONS
--------------------------------------
  ✅ Extend RuntimeException for domain/service layer exceptions (modern practice)
  ✅ Extend Exception for I/O, protocol, or recoverable API conditions
  ✅ Provide at least the message and message+cause constructors
  ✅ Add meaningful getters for context fields
  ✅ Keep the message string informative and consistent
  ✅ Build a hierarchy for large applications — don't create flat one-off exceptions
  ✅ Include error codes for logging and API responses
  ❌ Don't extend Throwable directly — always use Exception or RuntimeException
  ❌ Don't create exceptions that duplicate existing ones (use IllegalArgumentException, etc.)
  ❌ Don't put sensitive data (passwords, SSNs) in exception messages — they appear in logs

SERIALIZATION AND serialVersionUID
------------------------------------
  Exceptions are Serializable (Throwable implements Serializable).
  If you add fields, declare serialVersionUID to avoid deserialization issues:

  public class MyException extends RuntimeException {
      private static final long serialVersionUID = 1L;  // ← always declare in serializable classes
      private final int code;
      // ...
  }

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Should custom exceptions be checked or unchecked?
A: Modern Java practice (Spring, Hibernate, most frameworks) favors UNCHECKED exceptions
   (extend RuntimeException) for domain/service exceptions. This avoids polluting method
   signatures and prevents the "declares throws" cascade through every method layer.
   Checked custom exceptions are still appropriate for APIs where the caller is expected
   to explicitly handle specific recoverable conditions (e.g., InsufficientFundsException
   in a banking API where the UI should show the shortfall).

Q: What constructors should a custom exception have?
A: At minimum: one that takes a message String, and one that takes both a message String
   and a Throwable cause. The cause is critical — it enables exception chaining so the
   original root cause is not lost when wrapping. Many also provide the four conventional
   constructors matching Throwable: no-arg, message, message+cause, cause-only.

Q: How do you add extra context to an exception?
A: Declare private final fields for the context data, populate them in the constructor,
   and expose them via getters. Example: UserNotFoundException(long userId) stores
   userId as a field and exposes getUserId(). This lets the catch block extract the
   structured information rather than parsing a message string.
