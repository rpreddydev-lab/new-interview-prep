TRY-WITH-RESOURCES
====================

OVERVIEW
---------
  Introduced in Java 7 to automate resource cleanup (close()).
  Replaces error-prone try/finally resource management.
  Any class implementing java.lang.AutoCloseable can be used.

SYNTAX
-------
  try (ResourceType res = new ResourceType(...)) {
      // use res
  } catch (Exception e) {
      // handle
  }
  // res.close() is called automatically here — even if an exception was thrown

  // Multiple resources — closed in REVERSE order of declaration:
  try (Connection conn = dataSource.getConnection();
       PreparedStatement ps = conn.prepareStatement(sql)) {
      ps.setInt(1, id);
      ps.executeQuery();
  } catch (SQLException e) {
      log.error("DB error", e);
  }
  // Closing order: ps.close() first, then conn.close()

AUTOCLOSEABLE vs CLOSEABLE
----------------------------
  java.lang.AutoCloseable — introduced in Java 7
    void close() throws Exception  ← base interface for try-with-resources

  java.io.Closeable — extends AutoCloseable, for I/O resources
    void close() throws IOException  ← narrower exception type

  Any class implementing AutoCloseable works in try-with-resources.
  Closeable is idempotent (safe to close multiple times) by contract.
  AutoCloseable's contract does not require idempotence — document if it is.

SUPPRESSED EXCEPTIONS
-----------------------
  Before try-with-resources, if both the try body AND the finally close() threw exceptions,
  the finally exception suppressed the original. The original was silently lost.

  try-with-resources solves this:
  - If both the try body throws AND close() throws:
    → The BODY exception is the PRIMARY exception (visible)
    → The CLOSE exception is ADDED as a SUPPRESSED exception
    → Both are preserved and accessible

  Example:
    class BrokenResource implements AutoCloseable {
        @Override
        public void close() throws Exception {
            throw new Exception("close failed");
        }
    }

    try (BrokenResource r = new BrokenResource()) {
        throw new RuntimeException("body failed");  // PRIMARY exception
        // r.close() throws "close failed" → becomes SUPPRESSED
    } catch (Exception e) {
        System.out.println("Primary: " + e.getMessage());           // "body failed"
        System.out.println("Suppressed count: " + e.getSuppressed().length); // 1
        System.out.println("Suppressed[0]: " + e.getSuppressed()[0].getMessage()); // "close failed"
    }

  If the body completes normally but close() throws, the close exception IS the primary exception.

CLOSE ORDER WITH MULTIPLE RESOURCES
--------------------------------------
  Resources are closed in REVERSE order of declaration — like a stack (LIFO).
  This ensures that a resource opened first and possibly depending on another is closed last.

  try (A a = new A();    // opened first, closed LAST
       B b = new B();    // opened second, closed second
       C c = new C()) {  // opened third, closed FIRST
      // use a, b, c
  }
  // Close order: C → B → A

CUSTOM AUTOCLOSEABLE
----------------------
  Implementing AutoCloseable to participate in try-with-resources:

  public class DatabaseTransaction implements AutoCloseable {
      private final Connection connection;
      private boolean committed = false;

      public DatabaseTransaction(Connection connection) throws SQLException {
          this.connection = connection;
          this.connection.setAutoCommit(false);
      }

      public void commit() throws SQLException {
          connection.commit();
          committed = true;
      }

      @Override
      public void close() throws SQLException {
          if (!committed) {
              connection.rollback();  // auto-rollback on exception
          }
          connection.setAutoCommit(true);
          connection.close();
      }
  }

  // Usage — clean transaction management:
  try (DatabaseTransaction tx = new DatabaseTransaction(conn)) {
      // do work
      tx.commit();
  } catch (SQLException e) {
      // tx.close() auto-rolls back if commit wasn't called
      log.error("Transaction failed", e);
  }

JAVA 9 EFFECTIVELY FINAL VARIABLES
--------------------------------------
  Before Java 9: only freshly declared variables could be used in try-with-resources.
  Java 9+: can use effectively final variables declared outside the try statement.

  // Java 7/8:
  try (InputStream is = Files.newInputStream(path)) { ... }  // must declare inline

  // Java 9+:
  InputStream is = Files.newInputStream(path);
  // ... other code ...
  try (is) {  // ← effectively final variable, OK in Java 9+
      // use is
  }

COMPARISON: try-with-resources vs try-finally
-----------------------------------------------
  Aspect                   | try-finally               | try-with-resources
  -------------------------|---------------------------|------------------------------
  Resource closing         | Manual in finally         | Automatic
  Suppressed exceptions    | Original lost (silently!) | Preserved via getSuppressed()
  Close order              | Manual (must sequence)    | LIFO (automatic)
  Null check on close      | Must check res != null    | Auto-handled (null checked)
  Code verbosity           | High (nested try/catch)   | Low (clean)
  Java version             | All versions              | Java 7+
  Supports multiple res    | Nested try blocks         | Single try header

  // Old way — error prone:
  BufferedReader br = null;
  try {
      br = new BufferedReader(new FileReader("file.txt"));
      return br.readLine();
  } catch (IOException e) {
      throw new RuntimeException(e);
  } finally {
      if (br != null) {
          try { br.close(); } catch (IOException e) { /* ignored */ }
      }
  }

  // New way — clean and correct:
  try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
      return br.readLine();
  }

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is AutoCloseable? How does it relate to try-with-resources?
A: AutoCloseable is a functional interface in java.lang with a single method:
   void close() throws Exception. Any class implementing it can be used as a resource
   in try-with-resources. The JVM automatically calls close() at the end of the
   try block, whether the block completes normally or throws an exception.

Q: What happens if close() throws an exception in try-with-resources?
A: If both the try body AND close() throw:
   - The body exception becomes the PRIMARY exception (returned to caller)
   - The close() exception is added as a SUPPRESSED exception via addSuppressed()
   - Both are preserved; call e.getSuppressed() to access the close exception
   This is better than try-finally where the finally exception silently replaces the body exception.

Q: In what order are multiple resources closed?
A: Reverse order of declaration (LIFO — last opened, first closed). This mirrors the
   typical resource dependency: if B depends on A, you open A then B, and must close B
   before A to avoid using a closed resource. 

Q: Can you use try-with-resources without a catch block?
A: Yes. The catch and finally clauses are optional with try-with-resources:
     try (InputStream is = ...) { ... }  // valid — close() exception propagates up
   Any exceptions thrown are propagated to the caller. A catch block is only needed
   if you want to handle specific exceptions locally.
