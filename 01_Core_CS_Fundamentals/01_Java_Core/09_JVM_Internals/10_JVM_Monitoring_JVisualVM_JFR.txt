JVM MONITORING: JVISUALVM, JFR, AND TOOLS
==========================================

WHY MONITORING MATTERS
-----------------------
  JVM monitoring allows you to diagnose:
  - Memory leaks (heap growing unboundedly)
  - CPU hotspots (methods consuming excessive CPU)
  - GC pressure (too-frequent or too-long GC pauses)
  - Thread contention / deadlocks
  - Slow I/O, excessive allocations, off-heap memory growth

  Production rule: ALWAYS profile before optimizing.
  "Premature optimization is the root of all evil." — Knuth

KEY JVM MONITORING TOOLS
--------------------------
  CLI tools (come with JDK):
  - jstat    — GC statistics (live)
  - jcmd     — multifunctional: heap dumps, thread dumps, GC, JFR
  - jstack   — thread dump (deadlock detection)
  - jmap     — heap histogram, heap dumps
  - jinfo    — inspect/set JVM flags at runtime

  GUI tools:
  - VisualVM      — visual heap/CPU/thread monitor, profiler, heap dump analyzer
  - JMC (Java Mission Control) — analyze JFR recordings, advanced profiling

  Profilers:
  - JFR (Java Flight Recorder) — low-overhead, production-safe continuous recording
  - Async-profiler              — CPU and allocation profiling, flame graphs
  - YourKit / JProfiler         — commercial profilers with deep introspection

JSTAT — GC STATISTICS
----------------------
  jstat -gcutil <pid> <interval_ms> <count>
  jstat -gcutil 12345 1000 10    # every 1 second, 10 samples

  Columns in -gcutil:
  S0, S1   — Survivor space utilization (%)
  E        — Eden utilization (%)
  O        — Old generation utilization (%)
  M        — Metaspace utilization (%)
  YGC      — Young GC count
  YGCT     — Young GC total time (seconds)
  FGC      — Full GC count
  FGCT     — Full GC total time (seconds)
  GCT      — Total GC time

  Other useful jstat modes:
  jstat -gc <pid>          — GC stats with capacities and used sizes
  jstat -gccapacity <pid>  — min/max/current capacity of each memory pool
  jstat -gcnew <pid>       — Young gen stats only
  jstat -gcold <pid>       — Old gen stats only
  jstat -class <pid>       — Classloading stats (loaded, unloaded, bytes)
  jstat -compiler <pid>    — JIT compilation stats

JCMD — MULTIFUNCTIONAL TOOL
-----------------------------
  jcmd <pid> <command>

  Common commands:
  jcmd 12345 help                      # list all available commands
  jcmd 12345 VM.version                # JVM version
  jcmd 12345 VM.flags                  # all JVM flags (including defaults)
  jcmd 12345 VM.system_properties      # system properties
  jcmd 12345 GC.run                    # trigger GC (for testing — not production!)
  jcmd 12345 GC.heap_info              # heap summary (used, capacity, GC type)
  jcmd 12345 GC.heap_dump /tmp/heap.hprof  # heap dump
  jcmd 12345 Thread.print              # thread dump (all threads + stack traces)
  jcmd 12345 VM.native_memory          # native memory tracking (requires -XX:+NativeMemoryTracking=summary)
  jcmd 12345 Compiler.directives_print # print JIT compiler directives

JSTACK — THREAD DUMPS
-----------------------
  jstack <pid>                    # print all thread stack traces
  jstack -l <pid>                 # include lock info (detects deadlocks)

  Output includes:
  - Thread name, ID, state (RUNNABLE / BLOCKED / WAITING / TIMED_WAITING)
  - Stack trace for each thread
  - Lock info (which lock a thread holds, which it's waiting for)
  - "Found one Java-level deadlock:" section — automatic deadlock detection

  Typical deadlock detection workflow:
  1. jstack -l <pid> > thread_dump.txt
  2. Search for "deadlock" or "BLOCKED" in output
  3. Identify thread A holds lock X, waiting for lock Y;
     thread B holds lock Y, waiting for lock X

JMAP — HEAP HISTOGRAMS AND DUMPS
---------------------------------
  jmap -histo <pid>               # class-by-class heap histogram (live + dead)
  jmap -histo:live <pid>          # force GC first, then show only live objects
  jmap -dump:format=b,file=/tmp/heap.hprof <pid>  # full heap dump
  jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>  # dump only live objects (smaller)

  Heap histogram output:
   num     #instances         #bytes  class name
     1:       1234567      987654321  [B   (byte arrays)
     2:        345678      234567890  java.lang.String
     ...

  When to use: investigating OOM, memory leaks, large heap growth
  Warning: -dump causes a STW pause for heap snapshot — avoid on production at peak load!
  Prefer: jcmd 12345 GC.heap_dump or JFR for production.

VISUALVM — GRAPHICAL MONITORING
---------------------------------
  Free, ships with JDK (or standalone download from visualvm.github.io).
  Connects to local or remote JVM via JMX.

  Key panels:
  - Overview: JVM args, system properties, PID, uptime
  - Monitor: live CPU %, heap used/committed, PermGen/Metaspace, loaded classes, threads
  - Threads: timeline of all threads (running/sleeping/waiting/waiting-monitor), deadlock detector
  - Sampler: lightweight CPU and memory sampling profiler (production-safe at low overhead)
  - Profiler: exact instrumentation profiler (higher overhead — use with caution)
  - Heap Dump: load and analyze .hprof files — object histogram, dominators tree, OQL queries

  Use case: ad-hoc investigation, local development profiling, heap dump analysis.

JAVA FLIGHT RECORDER (JFR)
---------------------------
  JFR is the premier low-overhead production profiler (< 1% overhead in continuous mode).
  Built into HotSpot JVM (OpenJDK 11+ with JEP 328, also backported to 8u272+).
  Records events: GC events, method profiling, allocation profiling, I/O events, lock contention,
  exceptions, class loading, JIT compilation, thread events, custom events.

  Starting a JFR recording:
  # At JVM startup:
  java -XX:StartFlightRecording=filename=/tmp/recording.jfr,duration=60s,settings=profile MyApp

  # Via jcmd (while running):
  jcmd <pid> JFR.start name=myRecording settings=profile duration=120s filename=/tmp/rec.jfr
  jcmd <pid> JFR.dump name=myRecording filename=/tmp/rec.jfr
  jcmd <pid> JFR.stop name=myRecording

  # With Java API (custom events):
  @Name("com.example.MyEvent")
  @Label("My Custom Event")
  class MyEvent extends jdk.jfr.Event {
      @Label("Message") String message;
  }
  // Usage:
  MyEvent event = new MyEvent();
  event.message = "something important";
  event.commit();

  JFR settings:
  default  — very low overhead, limited data (safe for continuous production recording)
  profile  — more detailed data, slightly higher overhead (for targeted investigation)

JAVA MISSION CONTROL (JMC)
---------------------------
  GUI tool for analyzing JFR recordings.
  Open a .jfr file → see:
  - Event Browser: all recorded events by category and timestamp
  - Memory view: GC pause timeline, heap utilization, allocation rate
  - Method Profiling: hottest methods (CPU flame view or list)
  - Lock Instances: lock contention (which lock blocked most threads, most time)
  - Thread view: thread state timeline
  - Allocation Profiling: where allocations happen (object type + call stack)
  - I/O view: file/socket read/write latencies

  Download: jdk.java.net/jmc or bundled with some JDK distributions.

ASYNC-PROFILER
--------------
  Open-source, native profiler using Linux perf_events / AsyncGetCallTrace.
  Avoids "safepoint bias" that afflicts JFR and VisualVM sampling profilers.
  Can produce CPU flame graphs, allocation flame graphs, lock flame graphs.

  Usage:
  # CPU profiling:
  ./profiler.sh -d 30 -f /tmp/cpu_flamegraph.html <pid>
  # Allocation profiling:
  ./profiler.sh -e alloc -d 30 -f /tmp/alloc_flamegraph.html <pid>

  Key advantages over JFR sampling:
  - Samples at any point — not just JVM safepoints
  - Captures native code and kernel frames in same flame graph
  - Very low overhead

ENABLING JMX FOR REMOTE MONITORING
-------------------------------------
  JVM flags for remote VisualVM/JMC connection:
  -Dcom.sun.management.jmxremote
  -Dcom.sun.management.jmxremote.port=9999
  -Dcom.sun.management.jmxremote.ssl=false
  -Dcom.sun.management.jmxremote.authenticate=false
  -Djava.rmi.server.hostname=<host>

  For production, always use SSL and authentication!

TOOL COMPARISON TABLE
----------------------
  | Tool            | Best For                       | Overhead | Production Safe? |
  |-----------------|--------------------------------|----------|-----------------|
  | jstat           | Live GC stats (CLI)            | Minimal  | Yes             |
  | jcmd            | Heap/thread dumps, JFR control | Minimal  | Yes (careful)   |
  | jstack          | Thread dump / deadlock detect  | Minimal  | Yes             |
  | jmap            | Heap dump / histogram          | Medium   | Careful (STW)   |
  | VisualVM        | GUI monitoring, heap analysis  | Low-Med  | Caution         |
  | JFR             | Continuous profiling           | Very Low | Yes (<1%)       |
  | JMC             | JFR analysis (GUI)             | N/A      | Offline         |
  | async-profiler  | CPU/alloc flame graphs         | Low      | Yes             |

COMMON MONITORING WORKFLOW
---------------------------
  1. Detect problem (high latency, OOM, high CPU).
  2. jstat -gcutil <pid> 1000 → is GC the cause?
  3. If GC: -Xlog:gc* logs → find pause patterns, which GC phase is slow.
  4. If OOM: jcmd GC.heap_dump → analyze with JMC/VisualVM (histogram, dominator tree).
  5. If CPU: JFR 60s recording → JMC method profiling → find hotspot.
  6. If threads: jstack -l → look for BLOCKED, deadlock sections.
  7. If allocation rate high: JFR alloc profiling or async-profiler -e alloc.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What's the difference between jstack and jcmd Thread.print?
A: Both produce a thread dump showing all threads' stack traces and lock info.
   jstack is a dedicated tool; jcmd Thread.print is the jcmd equivalent. jcmd is preferred
   as it's more general-purpose and jstack is technically deprecated in some JDK versions.
   Both can detect deadlocks when using lock information.

Q: What is Java Flight Recorder and why is it preferred for production profiling?
A: JFR is a continuous event-recording mechanism built into the HotSpot JVM. Its overhead
   is typically below 1% in default mode, making it safe for always-on production use.
   It records GC events, CPU sampling, allocation profiling, lock contention, I/O events,
   and more. Unlike jmap (which causes STW pauses) or heavy profilers (which add
   significant overhead), JFR is designed to run continuously without impacting
   application performance significantly.

Q: How do you diagnose a memory leak in production?
A: (1) Confirm leak: jstat -gcutil shows Old Gen constantly growing and not being reclaimed
   after Full GC. (2) Take heap dumps at intervals: jcmd GC.heap_dump /tmp/heap1.hprof,
   wait, heap2.hprof. (3) Compare histograms in JMC or VisualVM — find the class with
   growing instance count. (4) Use the dominator tree to find what's keeping those objects
   alive. (5) Trace back through reference chains to find the GC root that's unintentionally
   holding references (e.g., static Map, thread-local, listener not deregistered).
