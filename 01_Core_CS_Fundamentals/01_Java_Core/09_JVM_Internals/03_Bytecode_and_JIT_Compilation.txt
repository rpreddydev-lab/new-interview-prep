BYTECODE AND JIT COMPILATION
==============================

JAVA COMPILATION PIPELINE
---------------------------
  Source (.java) → javac → Bytecode (.class) → JVM → JIT → Native Machine Code

  Step 1: javac compiles Java source to platform-independent bytecode
  Step 2: JVM interprets bytecode, identifies hot code
  Step 3: JIT compiles hot bytecode to optimized native code for the host CPU

BYTECODE BASICS
----------------
  Java bytecode is a compact instruction set for the JVM's stack-based virtual machine.
  Each bytecode instruction is 1–5 bytes. Key instruction categories:

  - Load/store: iload, istore, aload, astore (push/pop from operand stack)
  - Arithmetic: iadd, isub, imul, idiv, irem, lneg, dneg
  - Control flow: if_icmpeq, goto, tableswitch, lookupswitch
  - Method calls: invokevirtual, invokestatic, invokespecial, invokeinterface, invokedynamic
  - Object: new, getfield, putfield, getstatic, putstatic, instanceof, checkcast
  - Type conversions: i2l, i2d, l2i, d2f, etc.
  - Stack: pop, dup, swap

  // Simple example:
  int add(int a, int b) { return a + b; }
  // Compiled to approximately:
  //   iload_1     ; push a
  //   iload_2     ; push b
  //   iadd        ; pop a and b, push a+b
  //   ireturn     ; return top of stack

READING BYTECODE
-----------------
  // Disassemble with javap:
  javap -c ClassName.class       // shows bytecode
  javap -verbose ClassName.class // shows constant pool, stack size, local vars

  // Example output for: return x * 2 + 1;
  //  0: iload_1       // push x (local var 1)
  //  1: iconst_2      // push constant 2
  //  2: imul          // multiply
  //  3: iconst_1      // push constant 1
  //  4: iadd          // add
  //  5: ireturn       // return

INVOKEDYNAMIC (JAVA 7+)
-------------------------
  invokedynamic is the key to lambda and stream performance.
  Instead of generating an anonymous class at compile time, the compiler emits an
  invokedynamic instruction that calls a "bootstrap method" at FIRST CALL ONLY.
  The bootstrap method sets up the call site (usually using LambdaMetafactory).

  Why this matters:
  - Lambdas are NOT compiled to anonymous inner classes (unlike Java 7 and earlier)
  - invokedynamic lets the JVM optimize the linkage — may avoid object creation entirely
  - Future-proof: implementation can improve without recompiling source

  // Lambda source:
  Runnable r = () -> System.out.println("Hi");

  // Bytecode (conceptual):
  //   invokedynamic  #id:run (LambdaMetafactory.metafactory(...))
  // First call: LambdaMetafactory dynamically creates an implementation class
  // Subsequent calls: directly use the cached linkage

JIT COMPILATION
----------------
  The JVM starts with a bytecode interpreter. It profiles execution and identifies
  "hot spots" (methods/loops called frequently). The JIT compiler then compiles
  these to native code.

  HotSpot JIT has two compilers:
  C1 (Client Compiler):
  - Fast compilation, moderate optimizations
  - Inlining, trivial dead code elimination
  - Used for quick startup

  C2 (Server Compiler):
  - Slow compilation, aggressive optimizations
  - Loop unrolling, escape analysis, speculative optimizations, deoptimization
  - Used for long-running code paths

  Tiered Compilation (default since Java 8):
  Interpretation → C1 (profiling) → C1 (full optimized) → C2
  Methods are promoted through tiers based on call count and loop back-edges.

JIT OPTIMIZATIONS
------------------
  Method Inlining:
  - The most important JIT optimization
  - Replaces a method call with the method body inline — eliminates call overhead
  - Enables further optimizations on the combined code
  - Limit: by default, methods >35 bytes are not inlined (-XX:MaxInlineSize=35)

  Escape Analysis:
  - Determines if an object "escapes" the current method (returned, stored in a field)
  - Non-escaping objects can be allocated on the STACK instead of the heap
  - Eliminates GC pressure for short-lived objects
  - Enables lock elision: if an object doesn't escape, synchronized on it is a no-op

  Loop Unrolling:
  - Replicates the loop body N times to reduce loop overhead and enable further optimization

  Dead Code Elimination:
  - Removes code the compiler can prove is never executed

  Speculative Optimizations + Deoptimization:
  - JIT may assume a virtual call always targets one implementation (monomorphic call site)
  - If the assumption is violated (different subclass loaded), JIT "deoptimizes" —
    falls back to interpreter, recompiles with updated profile

ON-STACK REPLACEMENT (OSR)
----------------------------
  Normally JIT compilation happens between method calls.
  OSR allows JIT to compile a method WHILE it's running a long loop —
  the JVM replaces the stack frame mid-execution with the JIT-compiled version.

JVM FLAGS FOR JIT
------------------
  -XX:+PrintCompilation          — log compiled methods
  -XX:+PrintInlining             — log inlining decisions
  -XX:-TieredCompilation         — disable tiered, use only C2
  -XX:+UseSerialGC               — for testing without GC overhead
  -XX:CompileThreshold=N         — calls before C1 compilation (default varies)
  -XX:MaxInlineSize=N            — maximum bytecode size for inlining
  -server / -client              — select JIT mode (largely ignored with tiered compilation)

AHEAD-OF-TIME COMPILATION
--------------------------
  GraalVM Native Image compiles Java to native executables ahead of time.
  Pros: instant startup, no JIT warmup, smaller footprint — ideal for serverless/containers.
  Cons: reflection/dynamic class loading restricted, slower peak throughput vs JIT,
        requires closed-world assumption (all classes known at build time).

  // Build native image:
  native-image -jar myapp.jar myapp
  ./myapp  // runs as native binary, no JVM needed

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is JIT compilation and why does Java use it?
A: JIT (Just-In-Time) compilation converts frequently executed bytecode to native machine
   code at runtime. Java uses it because purely interpreted execution is 10-100x slower
   than native, but ahead-of-time compilation sacrifices portability. JIT combines both:
   the program starts quickly via interpretation, and the JIT profile identifies hot code
   paths and compiles them to optimized native code. The result is near-native performance
   for long-running applications while retaining portability.

Q: What is tiered compilation?
A: Tiered compilation uses both C1 and C2 compilers in stages. A method first runs in the
   interpreter while profiling. Then C1 compiles it quickly with light optimization and
   continues profiling. When the method becomes very hot, C2 compiles it aggressively with
   full optimization. This balances startup speed (C1 is fast) with peak throughput (C2 is
   optimal for hot code). Tiered compilation is the default since Java 8.

Q: What is escape analysis and why is it important?
A: Escape analysis determines whether an object reference can "escape" the method that
   created it — through return values, field stores, or passing to other methods. Objects
   that don't escape can be allocated on the stack (stack allocation) instead of the heap,
   which eliminates GC pressure and avoids synchronization overhead. It also enables lock
   elision: if an object never escapes its creating thread, synchronized blocks on it are
   unnecessary and can be removed by the JIT.

Q: What is invokedynamic and how does it relate to lambdas?
A: invokedynamic (Java 7) is a JVM instruction that defers method linkage to runtime.
   For lambdas, javac emits an invokedynamic instruction pointing to a bootstrap method
   (LambdaMetafactory). The first time the lambda is encountered, the bootstrap method
   creates an implementation (using method handles), caches it, and links the call site.
   This avoids generating anonymous inner classes at compile time, keeping bytecode size
   small, and lets the JVM optimize lambda creation (potentially avoiding object allocation).
