REFERENCE TYPES: STRONG, WEAK, SOFT, PHANTOM
=============================================

OVERVIEW
---------
  Java provides four types of references that control how the GC interacts
  with objects. All are in java.lang.ref.*

  Strongest → Weakest:
    Strong > Soft > Weak > Phantom

  The GC can only collect an object when there is NO strong reference pointing to it.
  Weaker references allow the GC to collect objects under various conditions.

─────────────────────────────────────────────────────────────
1. STRONG REFERENCE (default)
─────────────────────────────────────────────────────────────
  Object obj = new Object();  // strong reference

  As long as 'obj' is reachable, the GC will NEVER collect it.
  Set to null to make it eligible for GC:
    obj = null;

─────────────────────────────────────────────────────────────
2. SOFT REFERENCE (java.lang.ref.SoftReference)
─────────────────────────────────────────────────────────────
  Object is collected ONLY when the JVM is LOW ON MEMORY (before OOM).
  Ideal for memory-sensitive caches.

  SoftReference<MyData> soft = new SoftReference<>(new MyData());

  MyData data = soft.get();  // returns null if GC collected it
  if (data == null) {
      data = loadFromDB();
      soft = new SoftReference<>(data);
  }

  JVM guarantees soft references are cleared before throwing OutOfMemoryError.

  Use case:
  - Image/thumbnail caches
  - Parsed document caches
  - Any cache where stale-on-pressure is acceptable

  ⚠️ Not a perfect cache solution — GC behavior is JVM-implementation dependent.
     Consider Guava's Cache or Caffeine with explicit eviction policies instead.

─────────────────────────────────────────────────────────────
3. WEAK REFERENCE (java.lang.ref.WeakReference)
─────────────────────────────────────────────────────────────
  Object is collected at the NEXT GC cycle once no strong/soft references exist.
  Much more aggressively collected than SoftReference.

  WeakReference<MyObject> weak = new WeakReference<>(new MyObject());

  MyObject obj = weak.get();  // may return null even during normal operation

  Use case:
  - Canonicalized mappings (WeakHashMap)
  - Listener/callback registries where lifecycle is tied to the key
  - Preventing memory leaks in event systems

  WeakHashMap Example:
  -----------------------
    Map<Key, Value> map = new WeakHashMap<>();
    // When the Key object has no strong references elsewhere,
    // the GC can collect it AND the corresponding entry is automatically removed.
    // Great for metadata/attribute maps where key lifecycle drives entry lifecycle.

  Real usage — ThreadLocal internals:
    ThreadLocalMap uses WeakReference<ThreadLocal<?>> as keys.
    When the ThreadLocal variable goes out of scope (no strong ref), the key
    becomes weakly reachable and is collected on next GC — but the VALUE may
    still leak if the thread (thread pool thread) is long-lived!
    → Always call ThreadLocal.remove() in a finally block.

─────────────────────────────────────────────────────────────
4. PHANTOM REFERENCE (java.lang.ref.PhantomReference)
─────────────────────────────────────────────────────────────
  The WEAKEST reference. get() ALWAYS returns null.
  An object with only a phantom reference has been finalized but not yet reclaimed.

  PhantomReference is used for PRE-MORTEM CLEANUP — a safer alternative to finalize().

  Usage requires a ReferenceQueue:
  ---------------------------------
    ReferenceQueue<MyResource> queue = new ReferenceQueue<>();
    PhantomReference<MyResource> phantom = new PhantomReference<>(res, queue);

    // In a cleanup thread:
    Reference<?> ref;
    while ((ref = queue.poll()) != null) {
        // The object is about to be reclaimed — perform native/off-heap cleanup
        ((MyCleanupRef) ref).cleanup();
    }

  How it works:
    1. Object becomes phantom-reachable (no strong/soft/weak refs)
    2. GC finalizes the object (runs finalizer if any)
    3. GC enqueues the PhantomReference in the ReferenceQueue
    4. Your cleanup code dequeues and performs resource release
    5. GC reclaims memory

  Use case:
  - Managing off-heap / native resources (NIO DirectByteBuffer)
  - Resource cleanup without finalizers (Java 9+ Cleaner API preferred)
  - Tracking object lifecycle for profiling/instrumentation

  Java 9+ Cleaner API (preferred over raw PhantomReference):
  -----------------------------------------------------------
    import java.lang.ref.Cleaner;

    class NativeResource {
        private static final Cleaner CLEANER = Cleaner.create();
        private final Cleaner.Cleanable cleanable;
        private final long nativePtr;

        NativeResource(long nativePtr) {
            this.nativePtr = nativePtr;
            // Register cleanup action — must NOT hold a reference to 'this'!
            this.cleanable = CLEANER.register(this, new CleanAction(nativePtr));
        }

        private static class CleanAction implements Runnable {
            private final long ptr;
            CleanAction(long ptr) { this.ptr = ptr; }
            public void run() { freeNative(ptr); }  // native call
        }

        public void close() { cleanable.clean(); }
    }

─────────────────────────────────────────────────────────────
REFERENCE QUEUE (java.lang.ref.ReferenceQueue)
─────────────────────────────────────────────────────────────
  SoftReference, WeakReference, and PhantomReference can all be created
  with an optional ReferenceQueue.

  When the referent becomes eligible and the reference is cleared by GC,
  the Reference object is enqueued in the ReferenceQueue.

  Your code polls or blocks on the queue to detect reclamation:
    ref = queue.remove();  // blocks until enqueued
    ref = queue.poll();    // non-blocking, returns null if empty

─────────────────────────────────────────────────────────────
COMPARISON TABLE
─────────────────────────────────────────────────────────────
  Reference Type | get() | Collected When         | Use Case
  ───────────────┼───────┼────────────────────────┼─────────────────────────────
  Strong         | obj   | Never (while reachable) | Default
  Soft           | obj/null | JVM low on memory    | Memory-sensitive caches
  Weak           | obj/null | Next GC cycle        | WeakHashMap, canonicalization
  Phantom        | null  | After finalization       | Off-heap cleanup, Cleaner

─────────────────────────────────────────────────────────────
COMMON INTERVIEW QUESTIONS
─────────────────────────────────────────────────────────────
  Q: Why does WeakHashMap help prevent memory leaks?
  A: Entries are automatically removed when their keys become weakly reachable
     (no strong references). Useful for metadata maps tied to object lifecycle.

  Q: Why should you prefer Cleaner over finalize()?
  A: finalize() has unpredictable timing, can resurrect objects, delays GC,
     and is deprecated since Java 9. Cleaner runs cleanup in a separate thread
     and uses PhantomReferences — predictable and safer.

  Q: Can a SoftReference be cleared even when memory is not low?
  A: Yes — the JVM may clear soft references based on usage policies
     (e.g., -XX:SoftRefLRUPolicyMSPerMB controls how long an unused soft
     reference survives per MB of free heap).

  Q: What is the ThreadLocal memory leak problem?
  A: ThreadLocalMap keys are WeakReferences to ThreadLocal objects. When the
     ThreadLocal goes out of scope, the key is collected but the VALUE remains
     strongly referenced via the ThreadLocalMap entry. In thread pool threads
     (long-lived), this value is never removed unless you call remove().
