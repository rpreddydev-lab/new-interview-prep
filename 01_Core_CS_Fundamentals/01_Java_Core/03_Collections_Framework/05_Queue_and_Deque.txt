QUEUE AND DEQUE
================

THE QUEUE INTERFACE
--------------------
  java.util.Queue<E> extends Collection<E>
  Represents a First-In-First-Out (FIFO) data structure.

  Two sets of methods — differ in exception-throwing behavior:
  ┌──────────┬─────────────────────────────┬─────────────────────────────┐
  │ Operation│ Throws exception             │ Returns special value        │
  ├──────────┼─────────────────────────────┼─────────────────────────────┤
  │ Insert   │ add(e)   — throws if full   │ offer(e) — returns false    │
  │ Remove   │ remove() — throws if empty  │ poll()   — returns null     │
  │ Examine  │ element()— throws if empty  │ peek()   — returns null     │
  └──────────┴─────────────────────────────┴─────────────────────────────┘

  NOTE: In unbounded queues (LinkedList, ArrayDeque), add() and offer() behave the same.
        Bounded queues (like ArrayBlockingQueue) distinguish them.

  FIFO rule: elements enter at the tail and leave at the head.

THE DEQUE INTERFACE
--------------------
  java.util.Deque<E> extends Queue<E>
  Double-Ended Queue — elements can be added/removed from BOTH ends.
  Can be used as: Queue (FIFO), Stack (LIFO), or Deque.

  Key methods:
    addFirst(e) / offerFirst(e) — insert at front
    addLast(e)  / offerLast(e)  — insert at back   (same as Queue's add/offer)
    removeFirst()/ pollFirst()  — remove from front (same as Queue's remove/poll)
    removeLast() / pollLast()   — remove from back
    peekFirst()  / peekLast()   — examine without removing
    push(e)                     — addFirst (stack behavior)
    pop()                       — removeFirst (stack behavior)
    peek()                      — peekFirst

ARRAYDEQUE
-----------
Internal Structure: Circular array (resizable)
  - Backed by a circular Object[] array
  - head and tail indices track the front and back
  - Default initial capacity: 16; doubles when full
  - NULL elements are NOT allowed (null signals empty slots internally)

Key Operations:
  addFirst/addLast   → O(1) amortized
  removeFirst/Last   → O(1)
  peekFirst/Last     → O(1)
  contains()         → O(n)

  Faster than LinkedList for both Queue and Stack operations due to:
    - Better cache locality (contiguous memory)
    - No per-element node allocation overhead

Example — as Queue (FIFO):
  Deque<String> queue = new ArrayDeque<>();
  queue.offer("A");    // addLast
  queue.offer("B");
  queue.offer("C");
  System.out.println(queue.poll()); // "A" — removes from front
  System.out.println(queue.peek()); // "B" — front, no removal

Example — as Stack (LIFO):
  Deque<String> stack = new ArrayDeque<>();
  stack.push("X");   // addFirst
  stack.push("Y");
  stack.push("Z");
  System.out.println(stack.pop());  // "Z" — removes from front (LIFO)
  System.out.println(stack.peek()); // "Y"

Example — as Deque:
  Deque<Integer> deque = new ArrayDeque<>();
  deque.addFirst(1);
  deque.addLast(2);
  deque.addFirst(0);   // [0, 1, 2]
  deque.removeLast();  // removes 2 → [0, 1]

LINKEDLIST AS QUEUE/DEQUE
--------------------------
  LinkedList implements both List and Deque.
  It can be used as a Queue or Deque, but ArrayDeque is generally preferred
  because it is faster (no per-node allocation) and memory-efficient.

  Queue<String> q = new LinkedList<>();  // works fine
  // prefer:
  Queue<String> q = new ArrayDeque<>();  // better performance

BLOCKING QUEUES (java.util.concurrent)
----------------------------------------
  BlockingQueue<E> extends Queue<E>
  - Supports blocking put() (waits if full) and take() (waits if empty)
  - Essential for Producer-Consumer pattern

  Implementations:
    ArrayBlockingQueue   — bounded, backed by fixed-size array
    LinkedBlockingQueue  — optionally bounded, backed by linked nodes
    PriorityBlockingQueue — unbounded, ordered by priority
    SynchronousQueue     — zero capacity: each put() must match a take()
    DelayQueue           — elements become available after a delay

  Example — Producer-Consumer:
    BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

    // Producer thread
    new Thread(() -> {
        try { queue.put(42); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }).start();

    // Consumer thread
    new Thread(() -> {
        try { int val = queue.take(); System.out.println("Got: " + val); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }).start();

STACK REPLACEMENT GUIDE
------------------------
  ❌ OLD (legacy):       Stack<String> stack = new Stack<>();
  ✅ NEW (recommended):  Deque<String> stack = new ArrayDeque<>();

  ArrayDeque.push(e)  = addFirst(e)
  ArrayDeque.pop()    = removeFirst()
  ArrayDeque.peek()   = peekFirst()

COMPARISON TABLE
-----------------
  Feature              | LinkedList       | ArrayDeque       | ArrayBlockingQueue
  ---------------------|------------------|------------------|--------------------
  Internal structure   | Linked nodes     | Circular array   | Fixed array
  Null elements?       | ✅ Allowed       | ❌ Not allowed   | ❌ Not allowed
  Bounded?             | ❌ Unbounded     | ❌ Unbounded     | ✅ Fixed capacity
  Blocking?            | ❌ No            | ❌ No            | ✅ put/take block
  Performance          | Slower (GC alloc)| Faster (array)   | Thread-safe
  Implements Deque?    | ✅ Yes           | ✅ Yes           | ❌ No
  Preferred use        | Rare             | Stack/Queue/Deque| Producer-Consumer

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What's the difference between offer() and add() in a Queue?
A: add() throws IllegalStateException if the queue is full (bounded queue).
   offer() returns false instead of throwing. For unbounded queues like ArrayDeque,
   both behave identically. Prefer offer/poll/peek (value-returning) over add/remove/element.

Q: Why use ArrayDeque instead of Stack for stack operations?
A: Stack extends Vector, which synchronizes every method — expensive overhead.
   ArrayDeque is unsynchronized, faster, uses a resizable circular array with O(1) amortized
   push/pop, and is the officially recommended replacement for Stack.

Q: Can you put null in an ArrayDeque?
A: No. ArrayDeque uses null as a sentinel to detect empty slots internally. Adding null throws
   NullPointerException. LinkedList does allow null elements, but this makes it hard to
   distinguish "element was null" from "queue is empty" when using poll().

Q: What is a Deque and when would you use it?
A: A Deque (double-ended queue) supports add/remove from both front and back.
   Use cases: implementing a stack (LIFO), a queue (FIFO), sliding window problems,
   monotonic deque in algorithms, BFS/DFS with specific traversal requirements.
   ArrayDeque is the go-to implementation — fast, memory-efficient.
