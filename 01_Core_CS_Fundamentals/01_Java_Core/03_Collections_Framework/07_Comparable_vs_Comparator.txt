COMPARABLE vs COMPARATOR
==========================

WHY DO WE NEED ORDERING INTERFACES?
-------------------------------------
  Java needs a way to compare objects to:
  - Sort collections (Collections.sort, Arrays.sort)
  - Use in sorted structures (TreeSet, TreeMap, PriorityQueue)
  - Determine object order in general

  Two mechanisms exist:
  1. Comparable — the object knows how to compare itself (natural ordering)
  2. Comparator — an external object defines the comparison (custom ordering)

COMPARABLE<T>
--------------
  Package: java.lang
  Interface:
    public interface Comparable<T> {
        int compareTo(T other);
    }

  Return values:
    negative  → this < other
    zero      → this == other
    positive  → this > other

  - Implemented by the CLASS ITSELF
  - Defines ONE "natural" ordering for the class
  - Used automatically by TreeSet, TreeMap, PriorityQueue, Collections.sort (no extra args)

  Example:
    public class Employee implements Comparable<Employee> {
        private String name;
        private int salary;

        public Employee(String name, int salary) {
            this.name = name;
            this.salary = salary;
        }

        @Override
        public int compareTo(Employee other) {
            return Integer.compare(this.salary, other.salary); // natural order: by salary
        }
    }

    List<Employee> employees = new ArrayList<>();
    employees.add(new Employee("Alice", 90000));
    employees.add(new Employee("Bob", 75000));
    employees.add(new Employee("Charlie", 85000));

    Collections.sort(employees);  // uses compareTo — sorts by salary
    // [Bob=75000, Charlie=85000, Alice=90000]

    TreeSet<Employee> tset = new TreeSet<>(employees);  // also uses compareTo

  Built-in Comparable types: Integer, Long, Double, String, LocalDate, BigDecimal, etc.
  String.compareTo() — lexicographic order
  Integer.compareTo() — numeric order

COMPARATOR<T>
--------------
  Package: java.util
  Functional Interface:
    @FunctionalInterface
    public interface Comparator<T> {
        int compare(T o1, T o2);
    }

  Return values: same as Comparable — negative, zero, positive

  - An EXTERNAL separate class/lambda (decoupled from the type)
  - Defines CUSTOM ordering — you can create multiple Comparators for the same class
  - Passed as argument to sort methods and sorted data structures

  Example:
    // Sort employees by name
    Comparator<Employee> byName = Comparator.comparing(Employee::getName);

    // Sort employees by salary descending
    Comparator<Employee> bySalaryDesc = Comparator.comparingInt(Employee::getSalary).reversed();

    // Chained: first by department, then by salary within department
    Comparator<Employee> combined = Comparator.comparing(Employee::getDepartment)
                                              .thenComparingInt(Employee::getSalary);

    employees.sort(byName);
    employees.sort(bySalaryDesc);
    employees.sort(combined);

    // As lambda
    employees.sort((e1, e2) -> e1.getName().compareTo(e2.getName()));

    // PriorityQueue with Comparator
    PriorityQueue<Employee> pq = new PriorityQueue<>(bySalaryDesc);
    // Or TreeSet with Comparator
    TreeSet<Employee> byNameSet = new TreeSet<>(byName);

COMPARATOR FACTORY METHODS (Java 8+)
--------------------------------------
  Comparator.comparing(keyExtractor)          // sort by string/object field
  Comparator.comparingInt(keyExtractor)        // sort by int field (avoids boxing)
  Comparator.comparingLong(keyExtractor)       // sort by long field
  Comparator.comparingDouble(keyExtractor)     // sort by double field
  .reversed()                                  // reverse any comparator
  .thenComparing(keyExtractor)                 // add secondary sort
  .thenComparingInt(...)                       // secondary sort by int
  Comparator.naturalOrder()                    // T must implement Comparable
  Comparator.reverseOrder()                    // reverse of natural order
  Comparator.nullsFirst(comparator)            // null values come first
  Comparator.nullsLast(comparator)             // null values come last

  Examples:
    // Sort strings by length, then alphabetically for same length
    Comparator<String> complex = Comparator.comparingInt(String::length)
                                           .thenComparing(Comparator.naturalOrder());

    // Handle nulls safely
    Comparator<String> safe = Comparator.nullsFirst(Comparator.naturalOrder());

    // Reverse order for max-heap in PriorityQueue
    PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());

COMPARISON TABLE
-----------------
  Feature                | Comparable                  | Comparator
  -----------------------|-----------------------------|-----------------------------
  Package                | java.lang                   | java.util
  Method                 | compareTo(T other)          | compare(T o1, T o2)
  Implemented by         | The class itself            | External class or lambda
  Orderings per class    | ONE (natural ordering)      | MANY (multiple strategies)
  Modifies class?        | YES — must implement        | NO — class unchanged
  Used in sort/tree by   | Default (no extra arg)      | Passed as argument
  Override              | Tight coupling               | Loose coupling
  Null safety            | Depends on implementation   | nullsFirst/nullsLast helpers

WHEN TO USE WHICH
------------------
  Use Comparable when:
    - The class has ONE obvious natural ordering (e.g., integers by value, dates by time)
    - You own the class and the ordering won't change
    - You want the class to work naturally in TreeSet/TreeMap/PriorityQueue without extra args

  Use Comparator when:
    - You need MULTIPLE ordering strategies for the same class
    - You don't own the class (can't modify it to implement Comparable)
    - The ordering is context-specific (e.g., sort employees by name in one place, salary in another)
    - You want to sort by composite keys (chained comparators)
    - You need to handle nulls safely

PITFALL: SUBTRACTION TRAP
---------------------------
  // ❌ WRONG — integer overflow!
  Comparator<Integer> bad = (a, b) -> a - b;
  // If a = Integer.MIN_VALUE, b = 1: a - b overflows to a large positive → wrong order

  // ✅ CORRECT
  Comparator<Integer> good = Integer::compare;  // or Comparator.comparingInt(x -> x)
  // or: (a, b) -> Integer.compare(a, b)

CONTRACT
---------
  compareTo/compare must be:
  1. Consistent: sgn(x.compareTo(y)) == -sgn(y.compareTo(x))
  2. Transitive: if x < y and y < z then x < z
  3. Consistent with equals (recommended, not required):
       x.compareTo(y) == 0 should imply x.equals(y)
       TreeSet/TreeMap use compareTo for equality — if inconsistent with equals,
       behavior differs from HashSet/HashMap.

  Example of inconsistency trap:
    BigDecimal a = new BigDecimal("1.0");
    BigDecimal b = new BigDecimal("1.00");
    a.equals(b);          // false — different scale
    a.compareTo(b) == 0;  // true  — same numeric value
    // TreeSet treats them as equal; HashSet treats them as different!

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What's the key difference between Comparable and Comparator?
A: Comparable is implemented BY the class and defines its natural ordering (one ordering).
   Comparator is EXTERNAL to the class and defines custom orderings (multiple possible).
   Comparable: compareTo(T other) with one arg; Comparator: compare(T o1, T o2) with two args.

Q: Can you have multiple natural orderings using Comparable?
A: No. A class can implement Comparable only once, providing one natural ordering.
   For multiple orderings, create multiple Comparators.

Q: What happens in a TreeMap if compareTo() says two keys are equal but equals() says they differ?
A: TreeMap uses compareTo() (not equals()) to determine key equality.
   If compareTo() returns 0, the second put() OVERWRITES the first.
   The map behaves inconsistently with the equals() contract.
   Best practice: ensure compareTo() and equals() are consistent.

Q: What is Comparator.thenComparing() used for?
A: It creates a composite comparator for secondary sort keys. When the primary comparator
   considers two elements equal, thenComparing breaks the tie using the secondary comparator.
   Example: sort employees by department first, then by salary within the same department.
