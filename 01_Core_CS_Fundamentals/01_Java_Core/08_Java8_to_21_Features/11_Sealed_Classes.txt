JAVA SEALED CLASSES
====================

WHAT ARE SEALED CLASSES?
-------------------------
  Sealed classes (Java 17 — JEP 409, preview in Java 15/16) restrict which classes or
  interfaces can extend or implement them. The sealed class explicitly declares its
  permitted subclasses using the permits clause.

  This makes the class hierarchy closed and exhaustive — the compiler knows all
  possible subtypes, enabling exhaustive pattern matching and better domain modeling.

  // Syntax:
  public sealed class Shape permits Circle, Rectangle, Triangle {
      // common behavior
  }

  public final class Circle extends Shape {
      private final double radius;
      public Circle(double radius) { this.radius = radius; }
      public double radius() { return radius; }
  }

  public final class Rectangle extends Shape {
      private final double width, height;
      public Rectangle(double w, double h) { this.width = w; this.height = h; }
      public double width()  { return width; }
      public double height() { return height; }
  }

  public non-sealed class Triangle extends Shape {
      // Reopens the hierarchy — any class can now extend Triangle
  }

PERMITTED SUBCLASS MODIFIERS
------------------------------
  Each direct subclass/subinterface of a sealed type must be one of:
  - final        — cannot be extended further (closes the branch)
  - sealed       — further restricts its own subclasses (hierarchical sealing)
  - non-sealed   — reopens the hierarchy from this point (explicitly unseals)

  // Hierarchical sealing:
  public sealed interface Expr permits Literal, BinaryExpr, UnaryExpr {}

  public record Literal(int value) implements Expr {}  // records are implicitly final

  public sealed interface BinaryExpr extends Expr permits AddExpr, MulExpr {}
  public record AddExpr(Expr left, Expr right) implements BinaryExpr {}
  public record MulExpr(Expr left, Expr right) implements BinaryExpr {}

  public non-sealed interface UnaryExpr extends Expr {}  // anyone can implement UnaryExpr

LOCATION REQUIREMENTS
----------------------
  Permitted subclasses must:
  1. Be in the same package (or same module for named modules)
  2. Be known to the compiler when the sealed class is compiled
  3. Directly extend/implement the sealed class (no skipping levels)

  // If all classes are in the same source file, permits clause can be inferred:
  // (no need to write permits when all subclasses are in the same file)
  public sealed interface Shape {
      record Circle(double r) implements Shape {}
      record Rectangle(double w, double h) implements Shape {}
  }

SEALED INTERFACES
------------------
  Sealed classes work equally with interfaces:

  public sealed interface JsonValue
      permits JsonNull, JsonBoolean, JsonNumber, JsonString, JsonArray, JsonObject {}

  public record JsonNull() implements JsonValue {}
  public record JsonBoolean(boolean value) implements JsonValue {}
  public record JsonNumber(double value) implements JsonValue {}
  public record JsonString(String value) implements JsonValue {}
  public record JsonArray(List<JsonValue> items) implements JsonValue {}
  public record JsonObject(Map<String, JsonValue> fields) implements JsonValue {}

SEALED CLASSES AND PATTERN MATCHING
-------------------------------------
  The primary motivation for sealed classes is enabling exhaustive switch expressions.
  When the compiler knows all permitted subclasses, it can verify that all cases
  are handled without a default:

  double area(Shape shape) {
      return switch (shape) {
          case Circle c    -> Math.PI * c.radius() * c.radius();
          case Rectangle r -> r.width() * r.height();
          case Triangle t  -> computeTriangleArea(t);
          // No default needed! Compiler verifies exhaustiveness
          // because Shape is sealed with exactly Circle, Rectangle, Triangle
      };
  }

  // With nested sealed hierarchy:
  int eval(Expr expr) {
      return switch (expr) {
          case Literal(int v)         -> v;
          case AddExpr(Expr l, Expr r) -> eval(l) + eval(r);
          case MulExpr(Expr l, Expr r) -> eval(l) * eval(r);
      };
  }

SEALED CLASSES VS ENUM
------------------------
  | Aspect                   | Enum                          | Sealed Class                       |
  |--------------------------|-------------------------------|-------------------------------------|
  | Values                   | Fixed singleton values        | Separate class instances            |
  | State per variant        | Only common fields            | Each subclass has its own fields    |
  | Instantiation            | One instance per constant     | Many instances per subclass         |
  | Methods per variant      | Common + switch              | Polymorphic override per subclass   |
  | Suitable for             | Constants, state machines     | Data variants with different shapes |
  | Pattern matching support | Yes (Java 21+)                | Yes (exhaustive)                    |

  // Use sealed class when variants have different data/structure:
  sealed interface Result<T> permits Success, Failure {}
  record Success<T>(T value) implements Result<T> {}
  record Failure<T>(String error) implements Result<T> {}

  // vs enum when variants are simple constants:
  enum Season { SPRING, SUMMER, FALL, WINTER }

SEALED CLASSES VS PLAIN ABSTRACT CLASS
-----------------------------------------
  | Aspect              | Abstract Class              | Sealed Class                    |
  |---------------------|-----------------------------|---------------------------------|
  | Subclass control    | Open — anyone can extend    | Closed — only permitted types   |
  | Exhaustiveness      | No guarantee                | Compiler-verified               |
  | Pattern matching    | Requires default            | Can be exhaustive without default|
  | Module boundary     | Can extend from anywhere    | Must be in same package/module  |

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What are sealed classes and why were they introduced?
A: Sealed classes (Java 17) restrict which classes can extend or implement them using
   the permits clause. They were introduced to model closed, exhaustive class hierarchies —
   like algebraic data types in functional languages. The key benefit is enabling
   exhaustive pattern matching in switch expressions: when the compiler knows all permitted
   subtypes, it can warn if any case is missing, without requiring a default branch.
   This makes sealed classes ideal for modeling domain variants like ASTs, Result types,
   JSON values, and geometric shapes.

Q: What are the three modifiers a permitted subclass can use?
A: (1) final — the subclass cannot be extended further, closing that branch completely.
   (2) sealed — the subclass is itself sealed and must declare its own permits clause,
   allowing hierarchical sealing. (3) non-sealed — the subclass explicitly reopens the
   hierarchy from that point, allowing anyone to extend it. This last option intentionally
   creates a "hole" in the sealed hierarchy.

Q: What is the difference between sealed classes and enums?
A: Enums define a fixed set of singleton constants, all sharing the same class structure.
   Sealed classes define a fixed set of subtypes, each of which is a full class with its
   own fields, constructors, and methods. Sealed classes allow variants with different
   data (e.g., Circle(radius) vs Rectangle(width, height)); enums cannot have
   per-variant different instance state. Use enums for constants/states; use sealed
   classes for data variants with different structures (algebraic data types).

Q: How do sealed classes interact with pattern matching?
A: When a sealed class or sealed interface is used as the selector in a switch expression,
   the compiler can verify that all permitted subtypes are covered. If they are, no default
   case is required, and adding a new permitted subclass will cause a compile error in all
   switch expressions that don't handle the new type — giving a compile-time safety net
   rather than a runtime bug. This is the primary motivation for sealed classes.
