JAVA MODULE SYSTEM (JPMS — Java Platform Module System)
Java 9+
============================================================

1. WHY MODULES? — THE PROBLEM WITH CLASSPATH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Before Java 9, the classpath had major problems:
  1. JAR Hell          → duplicate classes in multiple JARs, unpredictable loading
  2. No encapsulation  → ANY public class was accessible from anywhere
  3. No explicit deps  → no way to declare what a JAR depends on
  4. Monolithic JDK    → entire rt.jar (~60MB) was always loaded

JPMS (Project Jigsaw) solved this by:
  - Strong encapsulation: only explicitly exported packages are accessible
  - Reliable configuration: dependencies declared and validated at startup
  - Scalable platform: create custom JREs with only needed modules

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. module-info.java — THE MODULE DESCRIPTOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Placed at the ROOT of the source tree (not inside a package).
Location: src/main/java/module-info.java

// Full example
module com.example.orderservice {

    // REQUIRES — declare dependencies on other modules
    requires java.sql;                           // standard JDK module
    requires spring.context;                     // Spring module
    requires transitive com.example.common;      // transitive: consumers also get this dep

    // EXPORTS — make packages visible to other modules
    exports com.example.orderservice.api;         // all modules can access
    exports com.example.orderservice.dto to com.example.frontend;  // only specific modules

    // OPENS — allow deep reflection into the package (needed by frameworks)
    opens com.example.orderservice.model;        // open to ALL for reflection
    opens com.example.orderservice.config to spring.core, spring.beans; // targeted

    // USES — declares that this module uses a service (java.util.ServiceLoader)
    uses com.example.PaymentProvider;

    // PROVIDES — declares that this module provides a service implementation
    provides com.example.PaymentProvider
        with com.example.orderservice.impl.StripePaymentProvider;
}

3. KEY DIRECTIVES EXPLAINED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

─────────────────────────────────────────
requires
─────────────────────────────────────────
Declares a compile-time AND runtime dependency on another module.
  requires java.net.http;

requires transitive:
  Implied readability — if module A requires transitive B,
  then any module requiring A also automatically reads B.
  USE CASE: Library modules that expose types from their dependencies.

requires static:
  Compile-time only dependency (optional at runtime).
  USE CASE: Optional features, annotation-only dependencies.

─────────────────────────────────────────
exports
─────────────────────────────────────────
Makes a package's public types accessible to other modules.
Types in non-exported packages are INACCESSIBLE even if public.
  exports com.example.api;
  exports com.example.internal to com.example.client;  // qualified

─────────────────────────────────────────
opens
─────────────────────────────────────────
Allows REFLECTIVE access to a package (needed by Spring, Jackson, Hibernate).
  opens com.example.model;              // all modules
  opens com.example.model to spring.core;  // only spring.core

DIFFERENCE from exports:
  exports → compile-time + runtime type access (but no reflection on private members)
  opens   → runtime reflective access only (field.setAccessible(true) works)
  open module → all packages are open to reflection (open modifier on module declaration)

─────────────────────────────────────────
uses / provides (ServiceLoader pattern)
─────────────────────────────────────────
The module system integrates with java.util.ServiceLoader:

// Consumer module
uses com.example.spi.LoggingProvider;

// ServiceLoader usage
ServiceLoader<LoggingProvider> loader = ServiceLoader.load(LoggingProvider.class);
loader.forEach(provider -> provider.log("message"));

// Provider module
provides com.example.spi.LoggingProvider
    with com.example.logging.Slf4jLoggingProvider;

4. JDK PLATFORM MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The JDK itself is modularized. Key platform modules:

  java.base           → core (java.lang, java.util, java.io) — auto-required by all
  java.sql            → JDBC API
  java.net.http       → HttpClient (Java 11+)
  java.logging        → java.util.logging
  java.xml            → XML/DOM/SAX/XSLT
  java.management     → JMX
  java.desktop        → AWT/Swing
  jdk.httpserver      → built-in HTTP server
  jdk.jshell          → JShell API
  java.se             → aggregator module for all standard Java SE modules

List all modules: java --list-modules
Describe a module: java --describe-module java.sql

5. TYPES OF MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Named Module:
  - Has a module-info.java
  - Strong encapsulation and reliable configuration enforced
  - Lives on the MODULE PATH

Unnamed Module:
  - JARs placed on the CLASSPATH (no module-info.java)
  - Reads ALL other modules; exports ALL packages
  - Backward compatibility mechanism — all old code works
  - Cannot be targeted in qualified exports/opens

Automatic Module:
  - Named JAR placed on the MODULE PATH (no module-info.java)
  - Module name derived from JAR filename (hyphens → dots, version stripped)
  - Reads all other modules; exports all packages
  - Bridge between named modules and old classpath JARs
  - Name can be set via MANIFEST.MF: Automatic-Module-Name: com.example.foo

Open Module:
  open module com.example.app { ... }
  All packages are open to reflection — useful during migration.

6. COMPILATION AND RUNNING WITH MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# Compile
javac --module-source-path src -d out -m com.example.orderservice

# Run
java --module-path out -m com.example.orderservice/com.example.Main

# Run with --add-opens (for reflection without opens in module-info)
java --module-path out \
     --add-opens com.example.model/com.example.model=spring.core \
     -m com.example.app/com.example.Main

# Common JVM flags for backward compat
--add-opens java.base/java.lang=ALL-UNNAMED
--add-opens java.base/java.util=ALL-UNNAMED
--illegal-access=warn   (removed in Java 17, was present in 9-16)

7. CREATING CUSTOM JRE WITH jlink
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

jlink allows creating a minimal custom JRE with only the required modules:

jlink \
  --module-path $JAVA_HOME/jmods \
  --add-modules java.base,java.sql,java.net.http \
  --output custom-jre \
  --compress=2 \
  --no-header-files \
  --no-man-pages

# Results in a ~30MB custom JRE instead of a 200MB+ full JDK
# Ideal for Docker containers

Spring Boot 3 + GraalVM Native Image leverage this heavily.

8. MIGRATION FROM CLASSPATH TO MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Step 1: Run on Java 11+ with --classpath (everything as unnamed module)
Step 2: Identify dependencies using jdeps tool:
        jdeps --class-path libs/*.jar -m com.example.app
Step 3: Place JARs on --module-path as automatic modules
Step 4: Add module-info.java with requires for each dependency
Step 5: Open packages needed by frameworks (Spring, Jackson, Hibernate)
Step 6: Fix split packages (same package in multiple JARs — not allowed in modules)

COMMON MIGRATION ISSUES:
  - Split packages → must consolidate to one module
  - Reflective access warnings → add opens directives
  - Internal JDK API usage (sun.*, com.sun.*) → use --add-exports as temp fix
  - Third-party JARs without module-info → use as automatic modules

9. MODULES IN SPRING BOOT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Boot apps typically run on the CLASSPATH (unnamed module) for
maximum compatibility. Adding module-info.java requires:

  opens com.example.model to spring.core, spring.beans, spring.context;
  opens com.example.config to spring.core, spring.beans;

Spring Boot 3+ supports GraalVM Native Image which requires module-like
analysis of the application for ahead-of-time compilation.

10. INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What problem does the Java Module System solve?
A: JAR Hell (duplicate/conflicting JARs), lack of encapsulation (any public
   class was accessible), no explicit dependency declaration, and monolithic JDK.

Q: What is the difference between exports and opens?
A: exports makes a package's types accessible at compile + runtime normally.
   opens allows reflective access (field.setAccessible, method.invoke) at runtime.
   Frameworks like Spring need opens to inject/proxy beans.

Q: What is an unnamed module?
A: Any JAR on the classpath without module-info.java. It reads all modules
   and exports all packages — backward compatibility for old code.

Q: What is an automatic module?
A: A JAR on the MODULE PATH without module-info.java. Gets a name from the
   filename, reads all other modules, exports all packages. Acts as bridge
   between named and unnamed modules.

Q: What is requires transitive?
A: Makes a dependency implied — consumers of your module also automatically
   get access to the transitive dependency without requiring it explicitly.

Q: How do you use jlink and why is it useful?
A: jlink creates a custom minimal JRE with only the modules your app needs.
   Useful for Docker images (reduces size from 200MB to 30-50MB).

Q: What is a split package and why is it a problem with JPMS?
A: A split package is when two modules provide classes in the same package.
   JPMS forbids this — a package can only be owned by one module.

Q: How would you add reflection access to a module's private field without
   modifying module-info.java?
A: Use JVM flag: --add-opens com.example.module/com.example.model=ALL-UNNAMED
   This is a temporary workaround — preferred solution is opens in module-info.
