1. WHAT ARE ANNOTATIONS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Annotations are metadata markers applied to code elements (classes, methods,
fields, parameters, packages) that carry information used by:
  - Compilers        (e.g., @Override, @SuppressWarnings)
  - Frameworks       (e.g., @Autowired, @Entity, @Test)
  - Code generators  (e.g., Lombok's @Data, MapStruct's @Mapper)
  - Runtime logic    (e.g., @Transactional, @Cacheable)

Annotations do NOT change program semantics directly — they are read by tools.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. BUILT-IN JAVA ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Override             → compiler checks method actually overrides a superclass method
@Deprecated           → marks element as outdated; compiler warns on usage
@SuppressWarnings     → suppresses specific compiler warnings
@FunctionalInterface  → compiler ensures interface has exactly one abstract method
@SafeVarargs          → suppresses unchecked varargs warnings on generic methods

3. META-ANNOTATIONS — DEFINING CUSTOM ANNOTATION BEHAVIOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Meta-annotations are annotations applied TO annotation declarations.

─────────────────────────────
@Retention(RetentionPolicy.X)
─────────────────────────────
Controls WHERE the annotation information survives:

  SOURCE  → present in source code only; discarded by compiler
            Example: @Override, @SuppressWarnings, Lombok's @Data
            USE: Code analysis, compile-time tools

  CLASS   → stored in .class bytecode, NOT available at runtime (default)
            Example: @NonNull in some libraries
            USE: Bytecode manipulation tools (ASM, ByteBuddy)

  RUNTIME → stored in bytecode AND available via reflection at runtime
            Example: @Autowired, @Transactional, @Entity
            USE: Frameworks that read annotations at runtime

─────────────────────────────
@Target(ElementType.X)
─────────────────────────────
Restricts which code elements can be annotated:

  TYPE             → class, interface, enum, record
  METHOD           → method declaration
  FIELD            → field (instance or static)
  PARAMETER        → method parameter
  CONSTRUCTOR      → constructor
  LOCAL_VARIABLE   → local variable
  ANNOTATION_TYPE  → another annotation
  PACKAGE          → package declaration
  TYPE_USE         → any use of a type (Java 8+, e.g. @NonNull List<@NonNull String>)
  MODULE           → module declaration (Java 9+)

─────────────────────────────
@Inherited
─────────────────────────────
If a class is annotated with an @Inherited annotation, its SUBCLASSES
automatically inherit that annotation too.
NOTE: Only works for CLASS-level annotations, not method/field.

─────────────────────────────
@Documented
─────────────────────────────
Includes the annotation in Javadoc output.

─────────────────────────────
@Repeatable (Java 8+)
─────────────────────────────
Allows an annotation to be applied multiple times to the same element.

@Repeatable(Schedules.class)
@interface Schedule {
    String cron();
}
@interface Schedules { Schedule[] value(); }

// Usage:
@Schedule(cron = "0 0 8 * * ?")
@Schedule(cron = "0 0 20 * * ?")
public void runJob() { ... }

4. CREATING CUSTOM ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Custom method-level annotation for audit logging
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@Documented
public @interface AuditLog {
    String action() default "";          // annotation element
    boolean logArgs() default true;
    String[] roles() default {};
}

// Annotation elements:
//   - Allowed types: primitives, String, Class, enum, annotation, arrays thereof
//   - Can have default values (default keyword)
//   - If only one element needed, name it 'value' → @MyAnnotation("x")

// Usage
@AuditLog(action = "CREATE_ORDER", logArgs = false)
public Order createOrder(OrderRequest request) { ... }

// Reading at runtime (via reflection)
Method method = clazz.getDeclaredMethod("createOrder", OrderRequest.class);
if (method.isAnnotationPresent(AuditLog.class)) {
    AuditLog audit = method.getAnnotation(AuditLog.class);
    System.out.println(audit.action()); // "CREATE_ORDER"
}

5. SPRING PATTERN — ANNOTATION-DRIVEN AOP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// 1. Define custom annotation
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface LogExecutionTime {}

// 2. Create AOP aspect that intercepts it
@Aspect
@Component
public class LoggingAspect {
    @Around("@annotation(LogExecutionTime)")
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed();
        System.out.println("Took: " + (System.currentTimeMillis() - start) + "ms");
        return result;
    }
}

// 3. Use it
@LogExecutionTime
public void processReport() { ... }

This is the foundation of how @Transactional, @Cacheable, @Async work in Spring.

6. COMPILE-TIME ANNOTATION PROCESSING (APT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Java Annotation Processing Tool (APT) runs DURING COMPILATION.
Processors can:
  - Validate annotations and emit compiler errors/warnings
  - Generate new source files, config files, or documentation

API:
  - javax.annotation.processing.Processor (interface)
  - AbstractProcessor (extend this)
  - ProcessingEnvironment → access to Filer, Messager, Elements, Types
  - RoundEnvironment     → elements annotated in the current round

// Basic custom processor structure
@SupportedAnnotationTypes("com.example.AuditLog")
@SupportedSourceVersion(SourceVersion.RELEASE_21)
public class AuditLogProcessor extends AbstractProcessor {

    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment roundEnv) {
        for (Element element : roundEnv.getElementsAnnotatedWith(AuditLog.class)) {
            // Validate, generate code, etc.
            if (element.getKind() != ElementKind.METHOD) {
                processingEnv.getMessager().printMessage(
                    Diagnostic.Kind.ERROR,
                    "@AuditLog must be on a method", element);
            }
        }
        return true; // claim these annotations
    }
}

// Register processor:
// META-INF/services/javax.annotation.processing.Processor file
// containing: com.example.AuditLogProcessor

Processing rounds:
  - javac calls processors repeatedly until no new files are generated
  - Each call = one round; processors can generate new files which trigger more rounds

7. REAL-WORLD ANNOTATION PROCESSORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LOMBOK (@Data, @Builder, @Slf4j, @AllArgsConstructor):
  - Retention: SOURCE
  - Processor generates boilerplate code (getters, setters, toString, etc.)
  - Modifies the AST directly (uses non-standard sun.* APIs — controversial)

MAPSTRUCT (@Mapper, @Mapping):
  - Retention: SOURCE
  - Generates type-safe mapper implementation classes at compile time
  - Zero reflection at runtime → very fast

DAGGER 2 (@Component, @Inject, @Module):
  - DI framework for Android; generates DI code at compile time
  - Retention: RUNTIME for some, SOURCE/CLASS for generated code

HIBERNATE VALIDATOR (@NotNull, @Size, @Email — javax.validation):
  - Retention: RUNTIME
  - Read at runtime by Hibernate Validator / Spring to validate beans

QueryDSL, AutoValue, Immutables — all use APT to generate code.

8. ANNOTATION INHERITANCE AND COMPOSITION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Java does NOT support annotation inheritance for methods/fields.
But Spring uses meta-annotations for composition:

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Controller
@ResponseBody
public @interface RestController {}  // composed of @Controller + @ResponseBody

Spring's AnnotationUtils.findAnnotation() and MergedAnnotations API
recursively search meta-annotations, enabling composed annotations to work
exactly like their component annotations.

9. INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between @Retention(SOURCE), CLASS, and RUNTIME?
A: SOURCE → discarded at compile time (Lombok, @Override).
   CLASS  → in bytecode but not available via reflection (default, rare use).
   RUNTIME → in bytecode + accessible via reflection (Spring, JPA, JUnit).

Q: How does Lombok work? Is it annotation processing?
A: Yes, Lombok is an annotation processor with @Retention(SOURCE).
   It hooks into the compiler's AST to add methods/constructors/fields
   before compilation completes — no runtime overhead.

Q: Why would you create a custom annotation?
A: For cross-cutting concerns: audit logging, permission checks, rate limiting,
   metric recording. Combined with Spring AOP it avoids boilerplate in business logic.

Q: What is the difference between compile-time and runtime annotation processing?
A: Compile-time (APT): runs during javac, generates new source/class files.
   Runtime: annotations are read via reflection while the app runs.
   Compile-time is zero-overhead at runtime; runtime adds reflection cost.

Q: Can annotations extend other annotations?
A: No — Java does not support annotation inheritance directly.
   Spring uses meta-annotations (annotations on annotations) to compose
   behavior, read via AnnotationUtils.findAnnotation().

Q: How does @Transactional work internally?
A: Spring's startup scans beans for @Transactional using reflection.
   For each annotated bean, Spring wraps it in a proxy (JDK or CGLIB).
   On method calls, the proxy checks the annotation, opens a transaction,
   calls the real method, then commits or rolls back.

Q: What is @Inherited and what are its limitations?
A: @Inherited makes a class-level annotation automatically present on
   subclasses. Limitation: only applies to CLASS target; method and field
   annotations are NEVER inherited.
