================================================================
  RED-BLACK TREE
================================================================

----------------------------------------------------------------
WHAT IS A RED-BLACK TREE?
----------------------------------------------------------------
A Red-Black Tree is a self-balancing BST where each node is
colored RED or BLACK, and a set of coloring rules guarantee
that the tree height stays O(log n).

  Properties (all must hold simultaneously):
    1. Every node is either RED or BLACK.
    2. The root is BLACK.
    3. All NULL (leaf sentinel) nodes are BLACK.
    4. If a node is RED, both its children are BLACK.
       (No two consecutive red nodes on any path.)
    5. Every path from a node to any of its descendant NULL
       nodes passes through the same number of BLACK nodes.
       (Black-height property.)

  Visualization:
           B:30
          /     \
        R:20    R:40
        /  \       \
      B:15  B:25   B:50

  B = black, R = red

  Height guarantee:
    Black-height = k  =>  total height <= 2k
    Because at most every other node can be red.
    So height h <= 2 * log2(n + 1)  -->  h = O(log n)

  Compare: AVL height <= 1.44 * log n  (stricter)
           R-B height <= 2 * log n    (more relaxed)

----------------------------------------------------------------
WHY RED-BLACK OVER AVL?
----------------------------------------------------------------
  Fewer rotations on insert/delete:
    Insert:  at most 2 rotations (AVL: at most 1, but R-B
             may need color changes up the tree first)
    Delete:  at most 3 rotations (AVL: O(log n) rotations)

  Amortized performance:
    R-B tree has O(1) amortized rotations for insert.
    This makes R-B better for write-heavy workloads.

  Used in:
    Java TreeMap, TreeSet, LinkedHashMap (bucket to tree)
    Linux Completely Fair Scheduler (CFS)
    C++ std::map, std::set
    Many database index implementations

----------------------------------------------------------------
RECOLORING AND ROTATIONS
----------------------------------------------------------------
After insertion, the tree fixes violations bottom-up.
There are three cases during fix-up:

  INSERT always inserts a RED node.
  If parent is BLACK: no violation, done.
  If parent is RED: violation of Property 4 (red-red), fix.

  Notation: z = newly inserted node, uncle = sibling of parent.

  CASE 1: Uncle is RED
    Recolor: parent and uncle -> BLACK, grandparent -> RED
    Move z up to grandparent, continue fixup.
    No rotation needed.

  CASE 2: Uncle is BLACK AND z is inner grandchild (LR or RL)
    Rotate parent in opposite direction to convert to Case 3.
    (z is now outer grandchild)

  CASE 3: Uncle is BLACK AND z is outer grandchild (LL or RR)
    Rotate grandparent in opposite direction.
    Swap colors of parent and grandparent.
    Done -- no further fixup needed.

  Case 1 may repeat up the tree (O(log n) recolorings).
  Cases 2 and 3 each require at most 1 or 2 rotations and
  terminate immediately.
  Total rotations per insert: at most 2.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------
  Operation       Time         Space
  -----------------------------------------
  Search          O(log n)     O(log n) stack
  Insert          O(log n)     O(log n) stack
  Delete          O(log n)     O(log n) stack
  Rotation        O(1)         O(1)
  Recoloring      O(log n)     O(log n)
  Space total     O(n)         O(n)

----------------------------------------------------------------
JAVA USAGE — TREEMAP AND TREESET
----------------------------------------------------------------
  Java does NOT expose Red-Black Tree directly.
  Use TreeMap<K, V> (sorted map) and TreeSet<E> (sorted set).

  TreeMap operations:
    put(k, v)          O(log n)
    get(k)             O(log n)
    remove(k)          O(log n)
    containsKey(k)     O(log n)
    firstKey()         O(log n)
    lastKey()          O(log n)
    floorKey(k)        O(log n)
    ceilingKey(k)      O(log n)
    headMap(toKey)     O(1) + O(log n) to navigate
    tailMap(fromKey)   O(1) + O(log n)
    subMap(from, to)   O(1) + O(log n)

  Iteration: O(n) inorder traversal.

  TreeSet mirrors TreeMap for sets.

  Java HashMap (Java 8+) uses Red-Black Tree within buckets:
    When a bucket's chain > 8 entries, it converts from
    LinkedList to TreeMap-like structure -> O(log n) per bucket.

----------------------------------------------------------------
RED-BLACK TREE vs AVL TREE — DETAILED COMPARISON
----------------------------------------------------------------
  Criteria              AVL                Red-Black
  ---------------------------------------------------------------
  Balance factor        Strict (+/-1)      Relaxed (2k height)
  Height                <= 1.44 log n      <= 2 log n
  Search speed          Faster             Slightly slower
  Insert rotations      At most 1          At most 2
  Delete rotations      O(log n)           At most 3
  Rebalance cost        Higher             Lower
  Memory per node       +1 int (height)    +1 bit (color)
  Write throughput      Lower              Higher
  Read throughput       Higher             Slightly lower
  Real-world use        Some DBs, rarely   Java, Linux, C++
  Implementation        Moderate           Complex

----------------------------------------------------------------
INTERVIEW QUESTIONS
----------------------------------------------------------------

Q: What are the 5 Red-Black Tree properties?
A: 1. Every node is red or black.
   2. The root is black.
   3. All null (sentinel leaf) nodes are black.
   4. If a node is red, both children are black
      (no two consecutive reds on any path).
   5. Every root-to-null path has the same number of black nodes
      (uniform black-height).
   These 5 properties together guarantee height O(log n).

Q: How does the height guarantee work mathematically?
A: From property 5, the black-height from root to any null is k.
   From property 4, at most every other node can be red.
   So the longest root-to-null path has at most 2k nodes.
   The minimum tree with black-height k has 2^k - 1 nodes
   (all black, perfect tree). So n >= 2^k - 1, meaning
   k <= log2(n+1). Total height h <= 2k <= 2*log2(n+1) = O(log n).

Q: Why does Java use Red-Black Tree instead of AVL for
   TreeMap and TreeSet?
A: Java's workloads tend to be write-heavy in server applications.
   Red-Black Trees have O(1) amortized rotations for insert
   (at most 2 rotations total) vs AVL's potential O(log n)
   rotations for delete. The slightly looser balance means
   lookups are marginally slower, but inserts and deletes are
   faster. For general-purpose sorted maps in Java, this
   trade-off favors Red-Black Trees.

Q: What happens when a HashMap bucket chain exceeds 8?
A: Since Java 8, HashMap converts the bucket's linked list to
   a TreeNode-based Red-Black Tree structure. This changes
   per-bucket worst-case from O(n) to O(log n). It converts
   back to a linked list when the bucket size drops below 6
   (the threshold is lower to avoid thrashing). This change
   was introduced to mitigate hash flooding DoS attacks.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------
  1. Know all 5 R-B properties by memory -- examiners ask this
  2. Property 4 (no two consecutive reds) + property 5
     (uniform black-height) are the key balancing constraints
  3. R-B height guarantee: h <= 2 * log2(n+1)
  4. Java uses R-B for TreeMap, TreeSet, and HashMap buckets
  5. In practice, you never implement R-B from scratch in
     interviews -- but you MUST know the properties and why
     they guarantee O(log n), and when to use TreeMap vs HashMap
  6. For interview problems requiring sorted dynamic sets,
     reach for TreeSet or TreeMap (O(log n) operations)
