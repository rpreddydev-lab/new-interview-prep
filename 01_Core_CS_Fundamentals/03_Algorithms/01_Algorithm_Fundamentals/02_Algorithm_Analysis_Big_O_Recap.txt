NOTATION REVIEW
----------------------------------------------------------------
  O(f(n))     -- Big-O:    upper bound (worst case)
  Omega(f(n)) -- Big-Omega: lower bound (best case)
  Theta(f(n)) -- Big-Theta: tight bound (average = worst for many algos)

  In interviews, "complexity" almost always means Big-O worst case.

  Order of growth (slowest to fastest growth):
  O(1) < O(log n) < O(sqrt n) < O(n) < O(n log n) < O(n^2) < O(n^3) < O(2^n) < O(n!)

----------------------------------------------------------------
RECURRENCE RELATIONS
----------------------------------------------------------------
  T(n) = 2T(n/2) + O(n)     -- Merge Sort    -> O(n log n)
  T(n) = 2T(n/2) + O(1)     -- Binary Search tree balanced -> O(log n)
  T(n) = T(n-1) + O(n)      -- Selection Sort -> O(n^2)
  T(n) = 2T(n-1) + O(1)     -- Tower of Hanoi -> O(2^n)
  T(n) = T(n/2) + O(1)      -- Binary Search  -> O(log n)
  T(n) = aT(n/b) + f(n)     -- Master Theorem applies

  Master Theorem shortcut:
    T(n) = aT(n/b) + n^c
    Let k = log_b(a)
    If c > k: O(n^c)         -- work at root dominates
    If c = k: O(n^c * log n) -- all levels equal
    If c < k: O(n^k)         -- leaves dominate

----------------------------------------------------------------
AMORTIZED ANALYSIS
----------------------------------------------------------------
Amortized analysis gives the average cost per operation over
a sequence of operations, even if individual operations vary.

  Example: Dynamic Array doubling
    Single resize: O(n) to copy
    But across n push operations: total work = n + n/2 + n/4 + ... = O(n)
    Amortized cost per push: O(1)

  Techniques:
    Aggregate: total cost / number of operations
    Accounting: assign credits to cheap ops to "pay" for expensive ones
    Potential: use a potential function phi(state)

  Key amortized complexities:
    ArrayList.add():          O(1) amortized
    HashMap put/get:          O(1) amortized
    Monotonic stack push/pop: O(1) amortized over n operations
    Union-Find find:          O(alpha(n)) amortized

----------------------------------------------------------------
BESST / AVERAGE / WORST CASE
----------------------------------------------------------------
  Algorithm     Best      Average    Worst
  -----------------------------------------------
  QuickSort     O(n logn) O(n log n) O(n^2)
  MergeSort     O(n logn) O(n log n) O(n log n)
  HeapSort      O(n logn) O(n log n) O(n log n)
  Binary Search O(1)      O(log n)   O(log n)
  HashMap get   O(1)      O(1)       O(n)  (all keys same bucket)

  Why QuickSort still preferred despite O(n^2) worst case?
    1. Cache-friendly in-place partitioning
    2. Randomized pivot makes O(n^2) astronomically unlikely
    3. Small constant factor vs MergeSort
    Java Arrays.sort for primitives uses dual-pivot Quicksort.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------
  1. When asked for complexity: give worst case unless asked otherwise
  2. Always justify: "O(n log n) because we sort first, then O(n) scan"
  3. Space complexity often forgotten -- always include it
  4. Recursive algorithms: space = O(call stack depth) minimum
  5. If algorithm is O(n^2) and n <= 1000: acceptable (10^6 ops)
     If n <= 10^5: need O(n log n); if n <= 10^6: need O(n); etc.
