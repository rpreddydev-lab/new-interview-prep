AMORTIZED ANALYSIS
===================

INTRODUCTION
-------------
  Standard Big-O analysis gives worst-case cost per operation.
  Amortized analysis gives the AVERAGE cost per operation over a
  SEQUENCE of operations — not a probabilistic average, but a
  guaranteed average in the worst case across all operations.

  Key insight: an occasionally expensive operation can be "amortized"
  (spread out) over many cheap operations that precede it.

  Amortized ≠ Average Case:
  - Average case uses probability over inputs
  - Amortized is a deterministic guarantee over a sequence of ops

─────────────────────────────────────────────────────────────
WHY AMORTIZED ANALYSIS MATTERS
─────────────────────────────────────────────────────────────
  Some data structures have operations that are OCCASIONALLY expensive
  but CHEAP on average:

  Examples:
  - ArrayList.add(): usually O(1), but O(n) when the array doubles
  - HashMap.put(): usually O(1), but O(n) during resize/rehash
  - Stack operations with multipop
  - Splay tree operations

  Per-operation worst case would say "ArrayList.add() is O(n)" — true
  but misleading. Amortized analysis correctly says O(1) amortized.

─────────────────────────────────────────────────────────────
THREE METHODS OF AMORTIZED ANALYSIS
─────────────────────────────────────────────────────────────

METHOD 1: AGGREGATE METHOD
---------------------------
  Compute the total cost T(n) of n operations, then divide by n.
  Amortized cost per operation = T(n) / n.

  Example: Dynamic Array (ArrayList)
  ------------------------------------
  Start with capacity 1. When full, double capacity and copy all elements.

  Resizes happen at sizes: 1, 2, 4, 8, 16, ..., n
  Cost of copying at each resize: 1, 2, 4, 8, 16, ..., n

  Total copy cost for n insertions:
    = 1 + 2 + 4 + ... + n
    = 2n - 1   (geometric series)
    ≈ O(n)

  n insertions cost O(n) total → O(1) amortized per insertion.

  Even though one insertion costs O(n) (the doubling), amortized = O(1).

─────────────────────────────────────────────────────────────
METHOD 2: ACCOUNTING METHOD (BANKER'S METHOD)
----------------------------------------------
  Assign each operation a "charge" (amortized cost).
  - If charge > actual cost → store the surplus as "credit"
  - If charge < actual cost → spend stored credit to cover the deficit
  - Credit must NEVER go negative (invariant).

  Amortized cost = charge per operation (if the invariant holds)

  Example: Dynamic Array — Accounting Method
  -------------------------------------------
  Assign amortized cost of 3 to each insertion:
    - 1 unit: pay for the actual insertion
    - 2 units: store as credit (1 for future move of this element + 1 spare)

  When doubling occurs (n elements → copy to 2n array):
    - n elements must be moved
    - Each element has 2 units of stored credit
    - Total credit = 2n ≥ cost of copying = n  ✅

  So amortized cost per insertion = 3 = O(1). ✅

─────────────────────────────────────────────────────────────
METHOD 3: POTENTIAL METHOD (PHYSICIST'S METHOD)
------------------------------------------------
  Define a "potential function" Φ that maps a data structure state to
  a non-negative number representing stored "energy."

  Amortized cost of operation i = actual cost + ΔΦ
  where ΔΦ = Φ(after) − Φ(before)

  Total amortized cost = actual total cost + Φ(final) − Φ(initial)
  If Φ(initial) = 0 and Φ(final) ≥ 0, total amortized ≥ total actual.

  Example: Dynamic Array — Potential Method
  ------------------------------------------
  Let Φ = 2 × (number of elements) − capacity

  Initially: Φ = 2×0 − 1 = −1 → normalize to 0 at start (capacity=1, size=0)
  Use: Φ = 2 × size − capacity

  Before doubling: size = capacity = n  → Φ = 2n − n = n
  After doubling and inserting: size = n+1, capacity = 2n → Φ = 2(n+1) − 2n = 2

  Amortized cost of doubling insertion:
    actual = n (copy) + 1 (insert)
    ΔΦ = 2 − n
    amortized = (n+1) + (2 − n) = 3 = O(1) ✅

  Normal insertion (no resize): size = k, capacity = m (k < m)
    actual = 1
    ΔΦ = (2(k+1) − m) − (2k − m) = 2
    amortized = 1 + 2 = 3 = O(1) ✅

─────────────────────────────────────────────────────────────
KEY EXAMPLES IN JAVA
─────────────────────────────────────────────────────────────
  Data Structure         | Operation      | Worst Case | Amortized
  ───────────────────────┼────────────────┼────────────┼──────────
  ArrayList              | add(e)         | O(n)       | O(1)
  HashMap                | put(k,v)       | O(n)       | O(1)
  ArrayDeque             | addLast(e)     | O(n)       | O(1)
  StringBuilder          | append(s)      | O(n)       | O(1)
  Stack (array-backed)   | push/pop       | O(n)       | O(1)
  Splay Tree             | find/insert    | O(n)       | O(log n)
  Union-Find (path comp.)| find/union     | O(n)       | O(α(n)) ≈ O(1)

  α(n) = inverse Ackermann function — grows extremely slowly, effectively O(1).

─────────────────────────────────────────────────────────────
GROWTH FACTOR ANALYSIS
─────────────────────────────────────────────────────────────
  The doubling strategy (grow by 2×) is not the only option.
  Java uses different growth factors in different structures:

  ArrayList:  grows by 50%  → newCapacity = (old * 3) / 2 + 1
              Amortized still O(1), but wastes less memory than 2× doubling

  HashMap:    grows by 2× (power of 2 required for bit-masking)
              Default load factor 0.75 → resize at 75% full

  ArrayDeque: grows by 2×

  StringBuilder: grows by 2× + 2

  Why not grow by a fixed amount (e.g., +10)?
    Growing by 10 → n/10 resizes → total copy cost = 10+20+...+n = O(n²) total
    O(n) amortized per op — much worse.
    Must grow multiplicatively to get O(1) amortized.

─────────────────────────────────────────────────────────────
COMMON INTERVIEW QUESTIONS
─────────────────────────────────────────────────────────────
  Q: Why is ArrayList.add() considered O(1) amortized?
  A: While occasional resizes cost O(n) to copy elements, the doubling
     strategy ensures this happens so rarely that averaged over all n
     insertions the total cost is O(n), giving O(1) per operation.

  Q: What is the difference between amortized and average-case complexity?
  A: Average-case uses probability over random inputs. Amortized is a
     deterministic bound on a sequence of worst-case operations — no
     probability involved.

  Q: How does Union-Find achieve nearly O(1) per operation?
  A: Through path compression (flatten the tree on find) and union by rank
     (always attach smaller tree to larger). Together they give amortized
     O(α(n)) — inverse Ackermann — which is ≤ 4 for any practical n.

  Q: Why must the potential function never go negative?
  A: A negative potential would mean we have "spent" credit we haven't earned,
     making the amortized bound invalid. The invariant Φ ≥ 0 ensures that
     total amortized cost ≥ total actual cost.
