================================================================
  SEARCH IN ROTATED SORTED ARRAY
  (LC 33, LC 81, LC 153, LC 154)
================================================================

----------------------------------------------------------------
PROBLEM (LC 33): SEARCH IN ROTATED SORTED ARRAY
----------------------------------------------------------------

  A sorted array was rotated at some unknown pivot.
  Find target. Return index or -1.

  Example:
    nums = [4, 5, 6, 7, 0, 1, 2], target = 0  --> 4
    nums = [4, 5, 6, 7, 0, 1, 2], target = 3  --> -1

  Key constraint: All values are DISTINCT (LC 33).

----------------------------------------------------------------
CORE INSIGHT
----------------------------------------------------------------

  After rotation, the array has TWO sorted halves.
  When we compute mid, at least ONE of [lo,mid] or [mid,hi] is sorted.

  Determine which half is sorted, then check if target is in that half.
  If yes: search that half. If no: search the other half.

  HOW TO CHECK WHICH HALF IS SORTED:
    if nums[lo] <= nums[mid]:  left half [lo..mid] is sorted
    else:                      right half [mid..hi] is sorted

  IF LEFT HALF IS SORTED:
    if nums[lo] <= target < nums[mid]:  target in left half, hi = mid - 1
    else:                               target in right half, lo = mid + 1

  IF RIGHT HALF IS SORTED:
    if nums[mid] < target <= nums[hi]:  target in right half, lo = mid + 1
    else:                               target in left half, hi = mid - 1

----------------------------------------------------------------
JAVA SOLUTION (LC 33)
----------------------------------------------------------------

  public int search(int[] nums, int target) {
      int lo = 0, hi = nums.length - 1;

      while (lo <= hi) {
          int mid = lo + (hi - lo) / 2;

          if (nums[mid] == target) return mid;

          if (nums[lo] <= nums[mid]) {  // left half is sorted
              if (nums[lo] <= target && target < nums[mid]) {
                  hi = mid - 1;
              } else {
                  lo = mid + 1;
              }
          } else {  // right half is sorted
              if (nums[mid] < target && target <= nums[hi]) {
                  lo = mid + 1;
              } else {
                  hi = mid - 1;
              }
          }
      }
      return -1;
  }

  Time: O(log n)  Space: O(1)

----------------------------------------------------------------
TRACED EXAMPLE: nums=[4,5,6,7,0,1,2], target=0
----------------------------------------------------------------

  lo=0 hi=6 mid=3: nums[3]=7 != 0
    nums[0]=4 <= nums[3]=7: left is sorted
    4 <= 0 < 7? NO --> lo = mid+1 = 4

  lo=4 hi=6 mid=5: nums[5]=1 != 0
    nums[4]=0 <= nums[5]=1: left is sorted
    0 <= 0 < 1? YES --> hi = mid-1 = 4

  lo=4 hi=4 mid=4: nums[4]=0 == 0 --> return 4 ✓

----------------------------------------------------------------
PROBLEM (LC 81): WITH DUPLICATES
----------------------------------------------------------------

  Same as LC 33 but duplicates are allowed.

  Difficulty: nums[lo] == nums[mid] is ambiguous — can't tell which half is sorted.

  Example:
    [1, 0, 1, 1, 1], target = 0
    lo=0 hi=4 mid=2: nums[0]==nums[2]==1, can't determine sorted half.

  Handle by: when nums[lo] == nums[mid], shrink lo by 1 (lo++).
  This skips the ambiguous leftmost duplicate. Worst case: O(n).

  public boolean search(int[] nums, int target) {
      int lo = 0, hi = nums.length - 1;

      while (lo <= hi) {
          int mid = lo + (hi - lo) / 2;
          if (nums[mid] == target) return true;

          if (nums[lo] == nums[mid]) {
              lo++;  // handle ambiguity
          } else if (nums[lo] < nums[mid]) {  // left is sorted
              if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
              else lo = mid + 1;
          } else {  // right is sorted
              if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
              else hi = mid - 1;
          }
      }
      return false;
  }

  Time: O(log n) average, O(n) worst case (all duplicates)

----------------------------------------------------------------
PROBLEM (LC 153): FIND MINIMUM IN ROTATED SORTED ARRAY
----------------------------------------------------------------

  All values distinct. Find the minimum element.

  Key insight: minimum is at the rotation point (the "dip").

  If no rotation: nums[mid] could be minimum if left half is ascending.
  The minimum is in the "unsorted" (rotated) half.

  When is right half sorted but left is rotated?
    --> nums[mid] > nums[hi]: rotation is in right, minimum is in right.
  When is left half fully sorted?
    --> nums[mid] <= nums[hi]: no rotation in right, minimum is at lo or in left.

  public int findMin(int[] nums) {
      int lo = 0, hi = nums.length - 1;

      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (nums[mid] > nums[hi]) {
              lo = mid + 1;  // min is in right half (past mid)
          } else {
              hi = mid;      // min is in left half (including mid)
          }
      }
      return nums[lo];
  }

  Time: O(log n)  Space: O(1)

  Trace: [3, 4, 5, 1, 2]
    lo=0 hi=4 mid=2: nums[2]=5 > nums[4]=2 --> lo=3
    lo=3 hi=4 mid=3: nums[3]=1 <= nums[4]=2 --> hi=3
    lo=3 hi=3 exit --> nums[3]=1 ✓

----------------------------------------------------------------
PROBLEM (LC 154): FIND MINIMUM WITH DUPLICATES
----------------------------------------------------------------

  Same as LC 153 but with duplicates.

  Ambiguity: when nums[mid] == nums[hi], can't tell which side has min.
  Example: [2, 2, 2, 0, 1] — nums[mid]=2, nums[hi]=1... wait,
  but [1, 1, 2, 1, 1]: nums[mid]=2, nums[hi]=1 → min in right.
  [1, 1, 1, 1, 1]: nums[mid]=1, nums[hi]=1 → can't determine.

  Handle: when nums[mid] == nums[hi], hi-- (shrink high by 1).
  Correctness: we're not losing the minimum — if nums[hi] == nums[mid],
  and nums[mid] is the min, nums[hi] is also that value, so hi-- is safe.

  public int findMin(int[] nums) {
      int lo = 0, hi = nums.length - 1;

      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (nums[mid] > nums[hi]) lo = mid + 1;
          else if (nums[mid] < nums[hi]) hi = mid;
          else hi--;  // nums[mid] == nums[hi]: shrink ambiguity
      }
      return nums[lo];
  }

  Time: O(log n) average, O(n) worst case

----------------------------------------------------------------
COUNTING: HOW MANY ROTATIONS?
----------------------------------------------------------------

  The index of the minimum element = number of rotations.

  Just run findMin and return the index (lo at end of search).

  public int countRotations(int[] nums) {
      int lo = 0, hi = nums.length - 1;
      while (lo < hi) {
          int mid = lo + (hi - lo) / 2;
          if (nums[mid] > nums[hi]) lo = mid + 1;
          else hi = mid;
      }
      return lo;  // index of minimum = number of rotations
  }

COMPARISON TABLE
----------------------------------------------------------------

  Problem     Duplicates    Goal              Condition for lo=mid+1
  -------     ----------    ----              ----------------------
  LC 33       No            Find target       See two-case analysis
  LC 81       Yes           Find target       Same + lo++ on equal
  LC 153      No            Find minimum      nums[mid] > nums[hi]
  LC 154      Yes           Find minimum      Same + hi-- on equal

----------------------------------------------------------------
COMMON MISTAKES
----------------------------------------------------------------

  1. Using nums[lo] vs nums[hi] as the pivot reference incorrectly.
     For "find minimum": compare mid with hi (not lo).
     For "find target": compare lo with mid to determine sorted half.

  2. Boundary conditions: use <= for target check in sorted half.
     "nums[lo] <= target && target < nums[mid]" — strict on mid side
     to avoid checking nums[mid] again (already checked for equality).

  3. Duplicates: forgetting the lo++ (LC 81) or hi-- (LC 154) step.

  4. Infinite loop: if lo = mid when lo < hi, can loop forever.
     Always ensure lo advances to mid+1 or hi shrinks.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Why compare nums[lo] with nums[mid] (not nums[hi])?
  A: To determine which half is sorted. If nums[lo] <= nums[mid],
     the left half [lo..mid] is sorted (no rotation in it).
     If nums[lo] > nums[mid], the rotation is somewhere in the left half,
     meaning the right half [mid..hi] is sorted.

  Q: What's different between LC 33 and LC 153?
  A: LC 33 searches for a specific target. LC 153 finds the minimum.
     Both use the same rotation insight but different search conditions.

  Q: Why does O(n) worst case happen for duplicates versions?
  A: When many elements are the same (e.g., [1,1,1,1,0,1,1]), we can't
     determine the sorted half and must shrink by 1, degenerating to O(n).

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Draw the two "humps" of a rotated array on whiteboard.
  - State clearly: "at mid, one half must be cleanly sorted."
  - Go through the two cases (left sorted, right sorted) systematically.
  - Mention duplicates as a follow-up variant.
  - Use LC 153 (find min) as the building block — LC 33 builds on same idea.
