================================================================
  HASHING — INTRODUCTION
================================================================

----------------------------------------------------------------
WHAT IS HASHING?
----------------------------------------------------------------
Hashing is the process of converting a key (any data type)
into a fixed-size integer index using a hash function.
This index is used to store or retrieve data in a hash table.

  key  -->  hash function  -->  index  -->  bucket in array

  Example:
    key = "alice"
    hash("alice") = 1274382
    index = 1274382 % 16 = 14   (table of size 16)
    store value at array[14]

  Goal: distribute keys uniformly across the table to
  achieve O(1) average-case access.

----------------------------------------------------------------
WHAT IS A HASH FUNCTION?
----------------------------------------------------------------
A hash function maps a key to an integer index.

  Requirements of a good hash function:
    1. Deterministic: same key always produces same hash
    2. Uniform distribution: spreads keys evenly across buckets
    3. Fast to compute: O(1) or O(k) where k = key length
    4. Avalanche effect: small change in key -> large hash change

  Simple example (for string keys):
    hash = 0
    for each char c in key:
      hash = 31 * hash + c
    index = hash % tableSize

  Java's String.hashCode():
    s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]
    Uses prime 31 because it minimizes collisions and
    31 * i = (i << 5) - i  (fast bit-shift optimization)

  Java's Object.hashCode():
    Default returns the memory address (identity hash).
    Override hashCode() when you override equals().

----------------------------------------------------------------
HASH TABLE STRUCTURE
----------------------------------------------------------------
  A hash table is an array of buckets.
  Each bucket can hold one or more key-value pairs
  (depending on collision strategy).

  Internal structure:
    buckets[0]  --> null
    buckets[1]  --> ("bob", 25)
    buckets[2]  --> ("alice", 30) --> ("carol", 22)  [chain]
    buckets[3]  --> null
    ...
    buckets[n-1]--> null

  Key metrics:
    n          = number of keys stored
    m          = number of buckets (table size)
    Load factor = n / m

  Load factor controls performance:
    Low load factor  (< 0.5)  --> few collisions, wastes space
    High load factor (> 0.75) --> many collisions, slow ops
    Java HashMap default load factor: 0.75
    Java resizes (rehashes) when load factor exceeds threshold

----------------------------------------------------------------
HASH COLLISIONS
----------------------------------------------------------------
A collision occurs when two different keys hash to the same
bucket index.

  Example:
    hash("alice") % 8 = 3
    hash("david") % 8 = 3   --> COLLISION

  Collisions are UNAVOIDABLE for large key spaces
  (pigeonhole principle: if keys > buckets, at least one
  bucket must hold multiple keys).

  Collision resolution strategies:
    1. Chaining (separate chaining)
       Each bucket holds a linked list (or tree) of entries.
       Java HashMap uses this approach.

    2. Open Addressing (probing)
       On collision, find another empty slot in the same array.
       Subtypes: linear probing, quadratic probing, double hashing
       Covered in detail in 17_Collision_Resolution_Techniques.txt

----------------------------------------------------------------
HASHING COMPLEXITY
----------------------------------------------------------------
  Operation       Average Case    Worst Case
  ---------------------------------------------------------------
  Insert          O(1)            O(n)  -- all keys collide
  Search          O(1)            O(n)
  Delete          O(1)            O(n)
  Space           O(n)            O(n)

  Average case O(1) assumes a good hash function and
  reasonable load factor.

  Worst case O(n) occurs when all keys hash to the same bucket
  (degenerate case -- all in one chain).

  Java HashMap improvement (Java 8+):
    When a chain exceeds 8 entries, it converts from
    LinkedList to a Red-Black Tree --> O(log n) worst case
    per bucket instead of O(n).
    Converts back to list when size drops below 6.

----------------------------------------------------------------
HASHING vs OTHER DATA STRUCTURES
----------------------------------------------------------------
  Feature              HashMap       TreeMap       Array
  ---------------------------------------------------------------
  Access by key        O(1) avg      O(log n)      O(1) by index
  Search by value      O(n)          O(n)          O(n)
  Insert               O(1) avg      O(log n)      O(n)
  Delete               O(1) avg      O(log n)      O(n)
  Sorted order         No            Yes           No
  Range queries        No            Yes           With sorted arr
  Min / Max            O(n)          O(log n)      O(n)
  Null keys            One null key  No null keys  N/A
  Memory               Higher        Higher        Lower

  Use HashMap when: O(1) lookup is priority, order doesn't matter
  Use TreeMap when: sorted order, range queries, floor/ceiling
  Use Array when:   integer keys in known range (frequency count)

----------------------------------------------------------------
HASHING IN JAVA — KEY CONTRACTS
----------------------------------------------------------------

  equals() and hashCode() CONTRACT (critical):
    If a.equals(b) is true, then a.hashCode() == b.hashCode()
    MUST always hold.

    The reverse is NOT required:
    a.hashCode() == b.hashCode() does NOT mean a.equals(b)
    (this is just a collision).

  CONSEQUENCES OF BREAKING THE CONTRACT:
    If you override equals() but NOT hashCode():
      Two "equal" objects may hash to different buckets.
      HashMap.get(key) will fail to find the value even though
      the key "equals" the stored key.
      This is one of the most common Java bugs.

  Rule: Always override both equals() AND hashCode() together.

  Example of correct override:
    @Override
    public int hashCode() {
      return Objects.hash(field1, field2);
    }
    @Override
    public boolean equals(Object o) {
      if (this == o) return true;
      if (!(o instanceof MyClass)) return false;
      MyClass other = (MyClass) o;
      return Objects.equals(field1, other.field1) &&
             Objects.equals(field2, other.field2);
    }

----------------------------------------------------------------
HASH FUNCTION QUALITY — WHAT TO WATCH FOR
----------------------------------------------------------------

  CLUSTERING
    When many keys hash to the same small range of buckets.
    Caused by poor hash function or bad table size choice.
    Using a prime number as table size reduces clustering.

  HASH FLOODING (DoS attack)
    An attacker can craft input strings that all hash to the
    same bucket, degrading HashMap from O(1) to O(n).
    Java 8+ Red-Black Tree in buckets mitigates this.
    Java uses randomized hash seeds for String in some contexts.

  INTEGER KEY BEST PRACTICE
    For integer keys, using the key itself as hash is fine
    but mixing bits improves distribution:
    key ^ (key >>> 16)   (Java HashMap's spread() function)

----------------------------------------------------------------
REHASHING
----------------------------------------------------------------
When the load factor exceeds the threshold, the hash table
resizes (usually doubles) and all entries are rehashed.

  Java HashMap:
    Default initial capacity: 16 (power of 2)
    Default load factor: 0.75
    Resize threshold: 16 * 0.75 = 12 entries
    New capacity on resize: 32, 64, 128...

  Cost of rehash: O(n) -- must recompute all indices
  Amortized cost per insert: O(1)

  Why power of 2 for capacity?
    index = hash & (capacity - 1)  is faster than hash % capacity
    Bitwise AND works correctly only when capacity is a power of 2.

----------------------------------------------------------------
INTERVIEW QUESTIONS
----------------------------------------------------------------

Q: What makes a good hash function?
A: It must be deterministic (same key = same hash), fast to
   compute (O(1) ideally), and produce a uniform distribution
   across all buckets. It should also have the avalanche effect
   (small change in key causes large change in hash) to prevent
   clustering. For string keys, polynomial rolling hash with a
   prime multiplier (like 31) is standard.

Q: What is the equals/hashCode contract in Java and why
   does it matter?
A: If two objects are equal (a.equals(b) == true), they must
   have the same hashCode. If you break this by overriding
   equals but not hashCode, the HashMap will compute a different
   bucket for your "equal" object and fail to find the stored
   value. Always override both together using Objects.hash().

Q: What happens when a HashMap's load factor exceeds 0.75?
A: The map resizes: capacity doubles (16 -> 32 -> 64...).
   All entries are rehashed to new bucket indices.
   This costs O(n) for the resize but keeps average O(1)
   per operation amortized. New threshold = new capacity * 0.75.

Q: Why does Java use a power of 2 for HashMap capacity?
A: Index computation: index = hash & (capacity - 1).
   Bitwise AND is faster than modulo (%). This trick only works
   when capacity is a power of 2 because (2^k - 1) in binary
   is all 1s, making AND equivalent to modulo.

Q: How does Java HashMap handle worst-case O(n) per bucket?
A: Since Java 8, when a bucket's chain exceeds 8 nodes,
   it's converted from a LinkedList to a Red-Black Tree,
   giving O(log n) per operation within that bucket instead
   of O(n). It converts back to a list when size drops to 6.
   This defends against hash flooding attacks.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------
  1. Always mention O(1) average AND O(n) worst case for
     HashMap -- not just O(1)
  2. Know the equals/hashCode contract cold -- it's a
     frequent Java-specific interview topic
  3. Understand load factor and rehashing -- shows depth
  4. Java 8 TreeBin (bucket -> Red-Black Tree) is worth
     mentioning in senior-level interviews
  5. For counting frequencies, int[26] or int[128] is
     faster than HashMap for fixed character sets
