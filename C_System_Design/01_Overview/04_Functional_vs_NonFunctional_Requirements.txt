================================================================
FUNCTIONAL vs NON-FUNCTIONAL REQUIREMENTS
================================================================

OVERVIEW
---------
Gathering the right requirements is the first and most critical step
in a system design interview. Rushing to design without requirements
is a red flag. Requirements fall into two categories:

  1. Functional Requirements (FR)  — What the system DOES
  2. Non-Functional Requirements (NFR) — How well it does it

FUNCTIONAL REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION
-----------
Functional requirements describe the specific behaviors, features,
and operations the system must support. They answer: "WHAT must the
system do?"

FORMAT: "The system shall [action] for [actor]"

EXAMPLES BY SYSTEM:

URL Shortener (e.g., bit.ly):
  FR1: Users can shorten a long URL into a short URL
  FR2: When a short URL is accessed, redirect to the original long URL
  FR3: Users can optionally provide a custom alias
  FR4: Links expire after a configurable TTL (default: never)
  FR5: Users can view click analytics for their URLs
  NOT in scope: User accounts, link editing, bulk import (unless asked)

Twitter/X:
  FR1: Users can post tweets (text, images, video)
  FR2: Users can follow/unfollow other users
  FR3: Users see a home timeline of followed accounts' tweets
  FR4: Users can like, retweet, and reply to tweets
  FR5: Users can search tweets by keyword or hashtag
  NOT in scope: DMs, ads, trending, Spaces (unless asked)

Uber:
  FR1: Riders can request a ride from location A to B
  FR2: Drivers can accept/reject ride requests
  FR3: Real-time tracking of driver location on map
  FR4: Automatic fare calculation based on distance/time
  FR5: Riders and drivers can rate each other post-trip
  NOT in scope: Driver background checks, fleet management, promotions

WhatsApp:
  FR1: Users can send/receive text messages to individuals
  FR2: Users can send/receive media (images, video, docs)
  FR3: Group chats with up to 256 members
  FR4: Message delivery receipts (sent ✓, delivered ✓✓, read ✓✓ blue)
  FR5: End-to-end encryption for all messages
  NOT in scope: Stories, Payments, Business accounts (unless asked)

HOW TO ELICIT FUNCTIONAL REQUIREMENTS IN INTERVIEWS:
  "Let me make sure I understand what we're building.
   The core features are:
   1. [feature 1]
   2. [feature 2]
   3. [feature 3]
   Are these correct? And should I also consider [feature 4]?"

  Then explicitly state what you're NOT building:
  "To keep scope manageable, I'll skip [X] and [Y] for now.
   We can add those later if time permits."

NON-FUNCTIONAL REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION
-----------
Non-functional requirements describe the quality attributes of the
system — how well it performs its functions. They answer: "HOW WELL
must the system do it?"

NFRs directly drive architectural decisions.

KEY NON-FUNCTIONAL REQUIREMENTS:

1. SCALABILITY
   - How many users/requests must the system support?
   - Current: 1M users. Peak: 5M users (Black Friday, events).
   - Must support 10× growth in 2 years without re-architecture.
   Impact: Horizontal scaling, stateless services, sharding, caching

2. PERFORMANCE / LATENCY
   - P99 latency ≤ 200ms for feed reads
   - P99 latency ≤ 500ms for tweet posting
   - Real-time map update ≤ 1 second for Uber tracking
   Impact: Caching strategy, DB indexing, CDN, async processing

3. AVAILABILITY
   - 99.9%   = 8.76 hours downtime/year  (three nines)
   - 99.99%  = 52.6 minutes downtime/year (four nines)
   - 99.999% = 5.26 minutes downtime/year (five nines)
   Impact: Redundancy, failover, multi-region deployment

   AVAILABILITY CALCULATION:
     Availability = (Total Time - Downtime) / Total Time
     For SLA negotiations, distinguish between:
       - Planned downtime (maintenance windows)
       - Unplanned downtime (failures)

4. RELIABILITY / DURABILITY
   - Messages must be delivered at-least-once (no loss)
   - User data must be durable (no data loss even on hardware failure)
   - Payment transactions must be exactly-once
   Impact: Replication factor, write-ahead logs, idempotent operations

5. CONSISTENCY
   - Strong consistency: All reads see latest writes (payments, banking)
   - Eventual consistency: Reads may be slightly stale (social feeds, likes)
   - Read-your-own-writes: You always see your own writes immediately
   Impact: Quorum reads/writes, sync vs async replication, Raft/Paxos

6. MAINTAINABILITY
   - MTTR (Mean Time to Repair) should be < 30 minutes
   - System should be easy to debug with good observability
   - New features should be deployable without full system restart
   Impact: Microservices, CI/CD, feature flags, structured logging

7. SECURITY
   - Data encrypted at rest (AES-256) and in transit (TLS 1.3)
   - GDPR compliance (right to erasure, data portability)
   - Authentication: OAuth 2.0 + MFA for sensitive operations
   Impact: Encryption, RBAC, audit logging, key management

8. COST EFFICIENCY
   - Storage cost optimization (tiered storage: hot/warm/cold)
   - Compute cost: right-sizing instances, auto-scaling
   Impact: Data compression, archival policies, spot instances

9. FAULT TOLERANCE
   - System degrades gracefully; non-critical features fail without
     bringing down the whole system
   - No single point of failure
   Impact: Circuit breakers, bulkhead pattern, graceful degradation

10. DISASTER RECOVERY
    - RTO (Recovery Time Objective): Maximum acceptable downtime after failure
    - RPO (Recovery Point Objective): Maximum acceptable data loss
    - E.g., RTO = 1 hour, RPO = 5 minutes
    Impact: Backup frequency, replication lag, failover automation

COMMON TRADE-OFFS BETWEEN NFRs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consistency vs Availability (CAP Theorem):
  You cannot have both strong consistency AND 100% availability when
  there is a network partition. Must choose:
  → Banking/payments: prefer consistency (risk of data loss is unacceptable)
  → Social media: prefer availability (stale likes count is OK)

Latency vs Consistency:
  Strong consistency = sync writes to all replicas = higher latency
  Eventual consistency = async writes = lower latency but stale reads
  → Real-time counters: accept eventual (likes/views can be approximate)
  → Financial balances: must be strongly consistent

Throughput vs Latency:
  Batch processing improves throughput but increases latency per item
  → Log ingestion: batch is fine (we care about total throughput)
  → API responses: low latency is critical (batch writes don't work)

Scalability vs Cost:
  More replicas, more shards = higher cost but better performance
  → Use tiered storage (hot/warm/cold) to optimize cost
  → Right-size instances; avoid over-provisioning

REQUIREMENTS GATHERING CHEAT SHEET

Always ask:
  □ How many users? (DAU, MAU, peak concurrent)
  □ Read vs write ratio?
  □ Acceptable latency? (P99)
  □ Availability requirement? (nines)
  □ Consistency level? (strong vs eventual)
  □ Data retention? (how long to keep data)
  □ Geographic distribution? (single region vs multi-region)
  □ Any regulatory/compliance requirements?
  □ Budget constraints? (affects choice of managed vs self-hosted)
  □ Mobile/web/both?
  □ Any existing infrastructure to reuse?

TYPICAL VALUES TO ASSUME (if not given):
  - Social media app: 100M DAU, 10:1 read:write ratio
  - Payment system: 100K TPS, strong consistency, 99.99% availability
  - Chat app: 50M DAU, 1:1 read:write, low latency < 100ms
  - Video platform: 1B DAU, very read-heavy, eventual consistency OK
  - Rate limiter: 10,000 QPS per service, low latency is critical
