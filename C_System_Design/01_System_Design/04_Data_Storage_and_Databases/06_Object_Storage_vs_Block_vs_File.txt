================================================================
OBJECT STORAGE vs BLOCK STORAGE vs FILE STORAGE
================================================================

THREE PARADIGMS OF STORAGE
----------------------------
Understanding the differences between storage types is critical for
choosing the right solution in system design.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
OBJECT STORAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT IT IS:
  Stores data as objects in a flat namespace.
  An object = data (bytes) + metadata (key-value pairs) + unique ID (key).
  Access via HTTP REST API: PUT /bucket/key, GET /bucket/key.
  
  Example:
  Bucket: user-avatars
  Key: user/123/avatar.jpg
  Metadata: { "content-type": "image/jpeg", "user-id": "123", "size": "48200" }
  Data: [binary JPEG bytes]

CHARACTERISTICS:
  - Immutable: Cannot edit bytes in-place; must replace the entire object
  - Flat namespace: No real directories (just key prefixes)
  - Eventual consistency: (historically; AWS S3 now strong consistent)
  - Massive scale: Stores exabytes; AWS S3 stores trillions of objects
  - Durability: 11 nines (99.999999999%) by default (3+ replicas)
  - Cheap: ~$0.02/GB/month for S3 Standard
  - Global CDN integration: Distribute objects via CloudFront

ACCESS PATTERNS:
  PUT /bucket/key    → Upload/replace entire object
  GET /bucket/key    → Download entire object
  DELETE /bucket/key → Delete object
  HEAD /bucket/key   → Get metadata without downloading
  LIST /bucket?prefix=user/123/  → List objects with prefix
  
  NO: partial updates, seeking to byte offset, in-place modification

STORAGE CLASSES (S3 example):
  S3 Standard:          Hot data, accessed frequently (~$0.023/GB/mo)
  S3 Standard-IA:       Infrequent access; lower storage cost, retrieval fee
  S3 One Zone-IA:       Single AZ, cheaper; risk if AZ fails
  S3 Glacier:           Archival; retrieval 1-5 minutes (~$0.004/GB/mo)
  S3 Glacier Deep:      Cold archive; retrieval 12 hours (~$0.00099/GB/mo)
  S3 Intelligent-Tiering: Auto moves between tiers based on access patterns

LIFECYCLE POLICIES:
  Automatically transition or delete objects based on age.
  Example:
    Day 0:   Upload to S3 Standard
    Day 30:  Move to S3 Standard-IA (accessed infrequently now)
    Day 90:  Move to S3 Glacier
    Day 365: Delete permanently

OBJECT VERSIONING:
  S3 can keep all versions of an object.
  Protects against accidental deletion or overwrites.
  Old versions incur storage cost.
  Combined with lifecycle: delete old versions after N days.

PRESIGNED URLS:
  Generate a time-limited, signed URL to give direct access to an object.
  Client can upload directly to S3 without going through your server.
  
  Server: presigned_url = s3.generate_presigned_url('put_object', 'bucket', 'key', expiry=300)
  Client: PUT presigned_url (direct upload to S3)
  
  Benefits: Your server isn't a bottleneck for large file uploads.
  Security: URL expires, no credentials exposed.

USE CASES FOR OBJECT STORAGE:
  ✓ User-uploaded files (profile pictures, documents, videos)
  ✓ Application backups and database dumps
  ✓ Static website hosting
  ✓ Data lake for analytics (store raw logs, event data)
  ✓ Software distribution (app binaries, firmware updates)
  ✓ ML model storage
  ✓ Immutable audit logs (write once, never modify)

BLOCK STORAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT IT IS:
  Raw storage blocks presented to a computer as a disk drive.
  The OS formats it with a file system (ext4, NTFS, XFS) or uses it raw.
  Low-level I/O: read/write at arbitrary byte offsets.
  Attached to a single server (or multiple via SAN with locking).

CHARACTERISTICS:
  - Very low latency (microseconds for NVMe SSDs)
  - Random read/write at any byte offset
  - Must be formatted with a file system before use
  - Attached to a single instance (typically)
  - Can be detached and re-attached to another instance

AWS EBS (Elastic Block Store):
  - Persistent block storage for EC2 instances
  - Types:
    gp3 (SSD): General purpose; 3000 IOPS baseline, up to 16K IOPS
    io2 (SSD): High performance databases; up to 64K IOPS, sub-ms latency
    st1 (HDD): Throughput-optimized; cheap, sequential access
    sc1 (HDD): Cold data; cheapest EBS option
  
  - EBS Multi-Attach: io2 volumes can attach to up to 16 instances (with clustering)
  - Snapshots: Point-in-time backups stored in S3
  - Encryption: At-rest and in-transit with KMS

USE CASES FOR BLOCK STORAGE:
  ✓ Relational databases (PostgreSQL, MySQL data files)
  ✓ OS boot volumes
  ✓ High-performance transactional applications
  ✓ Virtual machine disk images
  ✓ Anywhere requiring low latency random I/O

FILE STORAGE (NAS / Network File System)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHAT IT IS:
  Shared file system accessible by multiple servers simultaneously.
  Presents a hierarchical directory structure.
  Accessed via NFS (Linux) or SMB/CIFS (Windows).
  Multiple servers can read/write the same files concurrently.

CHARACTERISTICS:
  - POSIX-compatible (ls, cat, cp — standard file operations)
  - Multiple clients mount the same filesystem simultaneously
  - File locking for concurrent access control
  - Shared state (all clients see same files)

AWS EFS (Elastic File System):
  - Managed NFS for AWS EC2 instances
  - Auto-scales (no capacity planning needed)
  - Multiple AZs (highly available)
  - Performance modes: General Purpose, Max I/O
  - Throughput modes: Bursting, Provisioned

USE CASES FOR FILE STORAGE:
  ✓ Shared configuration files (multiple app instances need same config)
  ✓ Content management (web assets shared across web servers)
  ✓ Home directories (user files accessible from any server)
  ✓ Lift-and-shift migrations (apps expecting a file system)
  ✓ ML training data (datasets too large for local disk, shared across GPU instances)
  ✓ Rendering farms (shared project files)

DECISION GUIDE: WHICH STORAGE TO USE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I need to store user-uploaded profile pictures at scale."
  → Object Storage (S3): unlimited scale, cheap, CDN-friendly ✓

"I need low-latency storage for my PostgreSQL database."
  → Block Storage (EBS gp3/io2): low latency random I/O ✓

"Multiple EC2 instances need to read/write the same configuration files."
  → File Storage (EFS): POSIX shared filesystem ✓

"I need to store 5PB of raw logs for analytics."
  → Object Storage (S3): cheap, data lake, query with Athena ✓

"I need to store a relational database backup."
  → Object Storage (S3): cheap, durable, access occasionally ✓

"A Docker container needs its own writable layer."
  → Block Storage (local ephemeral SSD on EC2): fast, temporary ✓

"Machine learning pipeline needs shared training datasets across 100 GPU nodes."
  → File Storage (EFS/FSx for Lustre): shared concurrent access ✓
  OR Object Storage (S3 + FUSE mount for smaller datasets) ✓

"Real-time video streaming chunks (immutable, read-heavy)."
  → Object Storage (S3 + CloudFront CDN): immutable chunks, global delivery ✓

IN SYSTEM DESIGN INTERVIEWS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For any system that involves user-uploaded content (Google Drive, YouTube,
Instagram, WhatsApp):
  ALWAYS state: "Files stored in S3 (or equivalent object storage).
                  URL/key stored in database. CDN in front for reads."

Never try to store large binary files IN a relational database:
  ✗ "Store video as BLOB in MySQL" — bad: DBs are for structured data,
                                        not large binary files.
  ✓ "Store video in S3, store the S3 key in MySQL" — good pattern.

Chunked uploads (for large files):
  1. Client requests upload URL for each chunk (presigned S3 URLs)
  2. Client uploads chunks in parallel (multipart upload)
  3. S3 assembles them after all parts uploaded
  4. Record metadata in DB
  
  Advantages: Resumable uploads, parallel upload, no proxy bottleneck
