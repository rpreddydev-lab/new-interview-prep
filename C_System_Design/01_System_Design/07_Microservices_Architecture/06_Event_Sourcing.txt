================================================================
EVENT SOURCING
================================================================

WHAT IS EVENT SOURCING?
------------------------
Event Sourcing stores all changes to application state as a sequence
of events. The current state is computed by replaying these events.

TRADITIONAL STATE STORAGE (CRUD):
  Store the CURRENT STATE only.
  Update: overwrite the current value.
  History is lost.
  
  Table: orders
  | id | status    | total |
  | 1  | shipped   | 59.99 |
  
  When order was placed? When shipped? What was original total? → LOST.

EVENT SOURCING:
  Store ALL STATE CHANGES as events.
  Current state = apply all events from the beginning.
  History is preserved forever.
  
  Event Store: orders-events
  [OrderPlaced,    orderId=1, total=59.99, timestamp=T1]
  [PaymentCharged, orderId=1, amount=59.99, timestamp=T2]
  [OrderShipped,   orderId=1, trackingNum=ABC, timestamp=T3]
  
  To get current state: replay all 3 events → status=shipped, total=59.99, trackingNum=ABC.

KEY CONCEPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AGGREGATE:
  A cluster of domain objects treated as a unit.
  All events for an aggregate are stored under the same aggregate ID.
  Example: Order (includes order items, payment, status).

EVENT:
  Immutable record of what happened.
  Past tense: OrderPlaced, PaymentFailed, ItemShipped.
  Contains: aggregate ID, event type, data, timestamp, event version.

APPLY/PROJECT:
  Function that applies an event to current state to produce new state.
  State + Event → New State
  
  def apply(state, event):
    if event is OrderPlaced:
      state.status = "pending"
      state.total = event.total
    elif event is OrderShipped:
      state.status = "shipped"
      state.trackingNumber = event.trackingNumber
    return state
  
  Replay: reduce(events, initial_state, apply)

SNAPSHOT:
  For aggregates with many events, replaying from start is slow.
  Periodically take a snapshot of current state.
  Next load: start from snapshot + replay only events after snapshot.
  
  Snapshot: { orderId: 1, status: "paid", total: 59.99 } at event #500
  On load: start from snapshot, apply events #501, #502, #503...

ADVANTAGES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. COMPLETE AUDIT LOG:
   Every change is recorded with who, what, when.
   Regulatory compliance (financial, healthcare).
   Debug production issues by examining exact sequence of events.

2. TEMPORAL QUERIES:
   "What was the state of order 123 at 3pm yesterday?"
   Replay events up to that timestamp.
   Traditional DB: you'd need separate audit tables.

3. EVENT REPLAY:
   Bug fix: "Our discount calculation was wrong for 3 months."
   Fix the calculation code.
   Replay all affected events → state is now correct.
   
   Feature recomputation: Add new analytics feature.
   Replay historical events to populate new metrics from the start.

4. MULTIPLE VIEWS (CQRS):
   Same event stream → multiple read models (projections).
   Each projection optimized for its query pattern.
   New views added by replaying events.

5. NATURAL INTEGRATION BUS:
   Events flow to other services naturally.
   Each service maintains its own projection from shared events.

CHALLENGES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. EVENTUAL CONSISTENCY:
   Read models (projections) updated asynchronously.
   There's a window where data is stale.

2. SCHEMA EVOLUTION:
   Events are immutable; you can't change past events.
   If business logic changes, old events must still be interpreted correctly.
   Solution: Event upcasting — transform old event format to new format on read.
   Versioning: EventV1, EventV2. Code handles both versions.

3. QUERYING:
   Can't do "SELECT * FROM orders WHERE status = 'pending'".
   Must query projections (read models), not the event store.
   Event store is append-only; not optimized for ad-hoc queries.

4. COMPLEXITY:
   Higher cognitive overhead than CRUD.
   Team must understand aggregates, events, projections.
   Debugging requires replaying events.

5. EVENTUAL PROJECTION CATCHUP:
   If projection falls behind (consumer lag), queries return stale data.
   Need monitoring on projection lag.

IMPLEMENTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EVENT STORE OPTIONS:
  EventStoreDB (purpose-built event store)
  Kafka (append-only log, natural event store with log compaction)
  PostgreSQL: events table (aggregate_id, event_type, version, payload, timestamp)
  Axon Framework (Java): handles event sourcing + CQRS automatically

POSTGRESQL EVENT STORE:
  CREATE TABLE events (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id UUID NOT NULL,
    aggregate_type VARCHAR(100) NOT NULL,
    event_type   VARCHAR(100) NOT NULL,
    version      BIGINT NOT NULL,
    payload      JSONB NOT NULL,
    metadata     JSONB,
    created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    UNIQUE (aggregate_id, version)  -- optimistic locking
  );
  
  Load aggregate:
  SELECT * FROM events WHERE aggregate_id = ? ORDER BY version ASC;
  
  Save event (with optimistic locking):
  INSERT INTO events (aggregate_id, aggregate_type, event_type, version, payload)
  VALUES (?, ?, ?, expected_version + 1, ?)
  ON CONFLICT (aggregate_id, version) → THROW ConcurrentModificationException

WHEN TO USE EVENT SOURCING:
  ✓ Strong audit requirements (finance, healthcare, legal)
  ✓ Need to rebuild state or fix historical bugs
  ✓ Multiple views needed from same data (CQRS pair)
  ✓ Complex domain where understanding history is valuable
  ✓ Microservices integration via events

WHEN NOT TO USE:
  ✗ Simple CRUD (massive over-engineering)
  ✗ Simple reporting needs (use a reporting DB instead)
  ✗ Team doesn't understand the pattern (misimplemented = disaster)
  ✗ Low volume, low complexity domains

INTERVIEW ANSWER:
  "Event Sourcing stores all state changes as immutable events.
   Current state is derived by replaying events. Benefits: complete
   audit log, temporal queries, replay for bug fixes, natural integration
   via events. Challenges: eventual consistency, schema evolution, and
   querying requires read projections.
   
   I'd pair Event Sourcing with CQRS: events go to an append-only
   event store; multiple projections subscribe and build read-optimized
   views. I'd use it for financial transactions or compliance-heavy
   domains — not for simple CRUD-heavy services."
