HLD INTERVIEW QUESTIONS — MODEL ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: Walk me through how you would approach a system design interview.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Step 1 — Clarify requirements (5 min):
    Functional: what the system does (features)
    Non-functional: scale, latency, consistency, availability

  Step 2 — Back-of-envelope estimation (3 min):
    Users → requests/sec → storage/day → bandwidth

  Step 3 — High-level design (10 min):
    Draw the big boxes: client, API gateway, services, DB, cache, CDN

  Step 4 — Deep dive (20 min):
    Pick 2-3 hard components (the ones the interviewer is hinting at)
    Go deep on data model, bottlenecks, tradeoffs

  Step 5 — Wrap up (5 min):
    Identify bottlenecks, monitoring, failure modes, scale-out plan

  Key habits:
    - Always mention tradeoffs, never just pick one option
    - Draw a diagram (even text-art) as you explain
    - Ask before assuming ("should I prioritize consistency or availability?")


Q2: How would you design a URL shortener like bit.ly?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Requirements: shorten URL → 7-char code; redirect; analytics

  Encoding:
    Base62 (a-zA-Z0-9): 62^7 = 3.5 trillion URLs — enough for centuries
    Two approaches:
      Hash: MD5(longUrl) → take first 7 chars → collision check in DB
      Counter: auto-increment ID → base62 encode

  Why counter wins:
    No collision check needed, predictable, no birthday problem
    Use distributed counter (Twitter Snowflake / pre-allocated ranges)

  Data model: { short_code, long_url, created_at, user_id, click_count }

  Redirect:
    HTTP 301 (permanent) — browser caches, no second request → less load
    HTTP 302 (temporary) — every redirect hits server → accurate analytics
    Choose 302 for analytics accuracy

  Scale:
    Read-heavy (100:1 read:write ratio)
    Cache hot short codes in Redis: GET shortCode → longUrl → redirect
    Cache hit rate ~99% for popular links
    DB: simple KV or MySQL with index on short_code


Q3: How do you handle 10 million concurrent users?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Layer 1 — CDN: serve static assets (JS/CSS/images) → no origin server load
  Layer 2 — Load balancer: distribute HTTP requests across API servers
  Layer 3 — Stateless API servers: horizontal scaling (add boxes)
  Layer 4 — Caching: Redis for hot reads (80/20 rule → cache top 20%)
  Layer 5 — Database: read replicas for read-heavy, sharding if write-heavy
  Layer 6 — Async: queue heavy operations (email, notifications, video processing)

  Stateless is key: sessions stored in Redis, not in-memory
  Consistent hashing for cache so scaling doesn't invalidate all keys


Q4: What are the tradeoffs between SQL and NoSQL databases?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:

  Choose SQL (PostgreSQL/MySQL) when:
    - Data is relational (joins matter — orders, products, customers)
    - ACID transactions required (banking, payments, inventory)
    - Schema is stable and well-defined
    - Complex queries (aggregations, reporting)

  Choose NoSQL when:
    - Massive scale (>1TB), horizontal sharding needed
    - Schema flexibility (user-generated content, product catalogs)
    - Specific access patterns:
        DynamoDB — single-table design, key-value/document
        Cassandra — time-series, high-write, wide rows
        Redis    — caching, leaderboards, pub/sub
        MongoDB  — flexible documents, nested data
        Neo4j    — graph queries (social networks)

  Common mistake: "NoSQL scales, SQL doesn't"
  Reality: PostgreSQL scales to billions of rows with read replicas + sharding
  Use what fits your data model and access pattern


Q5: How does a CDN (Content Delivery Network) work?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  CDN = global network of edge servers close to users

  Flow: User requests image → DNS resolves to nearest CDN edge (Anycast routing)
        Edge has it cached → serve directly (latency 20ms vs 200ms to origin)
        Edge doesn't have it → fetch from origin → cache → serve

  Cache control:
    Cache-Control: max-age=86400 (static assets cached 1 day)
    Cache-Control: no-store (dynamic API responses — not cached)
    CDN respects origin Cache-Control headers

  Use cases:
    Static assets: JS/CSS/images (high cache hit, long TTL)
    Video streaming: HLS segments cached at edge, origin protected
    Dynamic content: CDN can still reduce TCP handshake latency (keep-alive)
    DDoS protection: CDN absorbs traffic before it hits origin

  Invalidation:
    Versioned filenames (app.v3.js) → no invalidation needed, new URL
    CDN purge API (Cloudflare/CloudFront) for emergency invalidation


Q6: What is the difference between synchronous and asynchronous communication?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Synchronous (REST/gRPC):
    Caller waits for response
    Tight coupling — if downstream is slow/down, caller is too
    Simpler to implement, easier debugging, immediate response
    Use when: client needs response now (fetch user profile, search)

  Asynchronous (Kafka/SQS/RabbitMQ):
    Producer publishes message; consumer processes later
    Loose coupling — downstream failure doesn't affect producer
    Natural backpressure — consumer processes at its own pace
    Use when: order confirmation email, video transcoding, notifications
              heavy computation, fanout to multiple consumers

  Hybrid: most real systems use both
    "Place order" → synchronous API (immediate response to user)
    "Send confirmation email" → publish event to Kafka (async)


Q7: How does database sharding work and what are the challenges?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Sharding = split data across multiple DB servers (horizontal partitioning)
  Each shard holds a subset of rows

  Sharding strategies:
    Hash sharding: shard = hash(user_id) % N
      Pros: even distribution
      Cons: resharding when N changes (consistent hashing helps)

    Range sharding: shard 1=A-G, shard 2=H-N, shard 3=O-Z
      Pros: range queries efficient (all users A-G on one shard)
      Cons: hot spots if names cluster (too many "Smiths")

    Directory sharding: lookup table maps key → shard
      Pros: flexible, can rebalance without hashing
      Cons: lookup table becomes bottleneck, single point of failure

  Challenges:
    Cross-shard joins: must join in application layer (slow)
    Cross-shard transactions: use Saga or 2PC (complex)
    Resharding: adding shard N+1 requires moving data (can't avoid downtime)
    Hotspots: celebrities in social network all land on same shard

  Rule of thumb: shard as late as possible; exhaust read replicas first


Q8: Design a key-value store (simplified DynamoDB).
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Operations: get(key) → value, put(key, value), delete(key)

  Architecture:
    Client → Coordinator node (routing layer)
    Coordinator → Data node (via consistent hashing on key)
    Each key replicated on N=3 nodes (preference list)

  Consistent hashing:
    Hash ring 0→2^32, key hashed to position, clockwise to first N nodes
    Adding/removing node only redistributes ~1/N keys

  Replication & Quorum:
    W=2, R=2, N=3: any 2 nodes confirm write → write succeeds
    R+W > N guarantees reading at least 1 node with latest write
    Tunable: W=1, R=3 for fast writes; W=3, R=1 for fast reads

  Conflict resolution:
    Vector clocks: each write tagged with logical clock
    If two writes happen concurrently → both kept, application resolves
    DynamoDB uses "last-writer-wins" with server-side timestamps

  Storage engine:
    LSM tree (Log-Structured Merge): append-only writes → fast writes
    Memtable (in-memory) → SSTable (disk) → Compaction
    Used by Cassandra, LevelDB, RocksDB


Q9: What is the difference between push and pull architectures?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Push (Fan-out on Write):
    When event occurs → immediately push to all recipients
    Example: tweet posted → push to all 1000 followers' timelines in Redis
    Pros: read is O(1) — just read from precomputed timeline
    Cons: write fan-out is expensive for celebrities (Lady Gaga → 100M writes)
    Best for: users with few followers, read-heavy systems

  Pull (Fan-in on Read):
    Read time: query all followed accounts' latest posts, merge sort
    Example: Twitter "following" query joining multiple user timelines
    Pros: no write amplification, celebrities are fine
    Cons: read is O(following_count) — slow for users following 10K accounts
    Best for: celebrities/influencers, write-heavy systems

  Hybrid (Twitter, Instagram):
    Regular users: push (fan-out on write, precomputed timeline)
    Celebrities (>1M followers): pull (merge at read time)
    Merge result: precomputed timeline + celebrity posts merged in memory


Q10: How would you design a real-time leaderboard?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Answer:
  Use Redis Sorted Set (ZSET) — O(log N) per operation

  Operations:
    ZADD leaderboard <score> <user_id>    → add/update score
    ZINCRBY leaderboard <delta> <user_id> → increment score
    ZREVRANGE leaderboard 0 9 WITHSCORES  → top 10 players
    ZREVRANK leaderboard <user_id>        → user's rank (0-indexed)
    ZSCORE leaderboard <user_id>          → user's score

  Score updates:
    User earns points → ZINCRBY leaderboard 50 user:123
    Atomic, thread-safe, no race conditions

  Scale:
    Single leaderboard up to 2^32-1 members (plenty for any game)
    Sharding: ZADD shard:{user_id % N}:leaderboard ...
    Merge: aggregate top-K from each shard (parallel ZREVRANGE)
    Daily/weekly: separate ZSET per time window, TTL-expire old ones

  Persistence: Redis AOF or snapshot → survive restarts
    Primary source of truth in DB, Redis as cache for O(log N) rank queries
