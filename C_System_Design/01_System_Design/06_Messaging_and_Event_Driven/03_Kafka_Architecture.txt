================================================================
KAFKA ARCHITECTURE
================================================================

WHAT IS KAFKA?
---------------
Apache Kafka is a distributed, partitioned, replicated commit log.
Designed by LinkedIn (2011). Open-sourced via Apache.

Core properties:
  - High throughput (millions of messages/second)
  - Low latency (< 10ms at scale)
  - Durability (persistent, replicated log)
  - Scalability (horizontal partitioning)
  - Replayable (consumers control their offset)
  - Fault tolerant (replication)

KAFKA COMPONENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BROKER:
  A Kafka server. Multiple brokers = a Kafka cluster.
  Each broker stores some partitions and handles requests.
  Typical: 3-30 brokers for a production cluster.

TOPIC:
  A named category of messages.
  Like a table in a database, but immutable/append-only.
  Examples: "user-events", "order-created", "payment-processed"

PARTITION:
  A topic is split into N partitions.
  Each partition is an ordered, immutable sequence of messages.
  Messages within a partition are ordered by offset.
  Partitions are distributed across brokers.
  
  ┌──────────────────────────────────────┐
  │ Topic: order-events (3 partitions)   │
  │                                      │
  │ Partition 0: [msg0][msg1][msg3][msg7] │
  │ Partition 1: [msg2][msg5][msg8]       │
  │ Partition 2: [msg4][msg6][msg9]       │
  └──────────────────────────────────────┘
  
  Parallelism: More partitions = more parallel consumers.
  Ordering: Only guaranteed WITHIN a partition, not across partitions.
  Scaling: Number of consumers ≤ number of partitions.

OFFSET:
  Each message has a unique sequential ID within its partition (offset).
  Consumer tracks: "I've processed up to offset 42 on partition 1."
  Consumer can reset offset to replay from any point.
  Offsets are stored in a special Kafka topic: __consumer_offsets.

PRODUCER:
  Sends messages to Kafka topics.
  Producer decides which partition to send to:
    - By key: hash(key) % num_partitions → same key always → same partition
    - Round-robin: if no key → distributes evenly across partitions
    - Custom partitioner: custom logic
  
  Key-based partitioning ensures ordering for a specific entity (user, order).
  Example: All events for user_123 → partition 1 (always same partition)
           Guarantees user_123 events are consumed in order.

CONSUMER:
  Reads messages from a topic partition at its own pace.
  Maintains offset: tells broker where it is.
  Can commit offset (mark as processed) at any rate.
  Can seek to any offset (replay from any point).

CONSUMER GROUP:
  Multiple consumers working together to consume a topic.
  Each partition is assigned to exactly ONE consumer in the group.
  Max parallelism: 1 consumer per partition (extra consumers idle).
  
  Topic with 4 partitions, Consumer Group with 2 consumers:
    Consumer A: partitions 0, 1
    Consumer B: partitions 2, 3
  
  Topic with 4 partitions, Consumer Group with 4 consumers:
    Consumer A: partition 0
    Consumer B: partition 1
    Consumer C: partition 2
    Consumer D: partition 3
  
  Different consumer groups read the SAME topic independently.
  → Fan-out: Analytics team + Notification service + Audit service
    all subscribe to "user-events" topic, each with own group.

KAFKA REPLICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each partition is replicated across N brokers (replication factor).
  Replication factor 3: 1 leader + 2 followers.

LEADER: Handles all reads/writes for that partition.
FOLLOWERS: Replicate from leader; ready to take over if leader fails.
ISR (In-Sync Replicas): Followers that are fully caught up to leader.

Producer ACK settings:
  acks=0: Fire and forget. No wait for ACK. Fastest, can lose messages.
  acks=1: ACK from leader only. Leader failure before replication = data loss.
  acks=all (acks=-1): ACK from all ISR replicas. Slowest, most durable.
                      Combined with min.insync.replicas=2 → safe.

min.insync.replicas=2:
  If fewer than 2 replicas are in-sync, reject writes.
  Prevents data loss when leader fails before replication.

KAFKA STORAGE AND RETENTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka stores messages on disk in segment files.
Segments are append-only logs; old segments are deleted based on policy.

Retention policies:
  Time-based: Delete messages older than N days (default: 7 days).
  Size-based: Delete oldest segment when topic exceeds N GB.
  Log compaction: Keep only the LATEST message per key.
                  Use for: current state of entities (user settings, prices).

Log compaction:
  Before: [user:1=A] [user:2=B] [user:1=C] [user:2=D]
  After:  [user:1=C] [user:2=D]  (only latest value per key kept)
  
  Consumer starting from beginning sees current state.
  Used by: Kafka Connect for syncing DB state.

KAFKA PERFORMANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Why is Kafka so fast?

1. SEQUENTIAL DISK WRITES:
   Appending to an ordered log is sequential I/O.
   Sequential disk write: ~200-400 MB/s (even on spinning disk!)
   Random disk write: ~0.1-2 MB/s
   Sequential I/O is nearly as fast as memory for throughput.

2. ZERO-COPY (sendfile syscall):
   Normal: disk → kernel buffer → user buffer → kernel socket buffer → network
   Zero-copy: disk → kernel buffer → network (skip user space copy)
   Reduces CPU usage dramatically for consumers.

3. BATCHING:
   Producer batches multiple messages before sending.
   Consumer reads batches of messages at once.
   Reduces network overhead per message.

4. COMPRESSION:
   Batches can be compressed (gzip, snappy, lz4, zstd).
   Compresses well because batch contains similar messages.
   Reduces network bandwidth and storage.

5. PAGE CACHE:
   Kafka relies on OS page cache (keep hot data in RAM).
   Producer writes to page cache → OS flushes to disk async.
   Consumer reads from page cache (often no disk I/O needed!).
   Kafka process itself uses minimal memory (delegates to OS).

THROUGHPUT: LinkedIn processes trillions of messages/day with Kafka.
            1.4 trillion messages/day with ~7 million messages/second.

KAFKA GUARANTEES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ordering: Within a partition, messages are strictly ordered.
          Across partitions, no ordering guarantee.

Delivery: At-least-once by default (consumer can re-read on failure).
          Exactly-once with: idempotent producer + transactional API.

Durability: With acks=all and min.insync.replicas=2: very durable.
            Data survives broker failures.

KAFKA STREAMS AND KSQL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KAFKA STREAMS: Java library for stream processing on Kafka data.
  Filter, map, aggregate, join topics.
  Stateful (windowed aggregations with local RocksDB state store).
  
  Example: Count orders per user per hour:
  KStream<String, Order> orders = builder.stream("orders");
  orders.groupByKey()
        .windowedBy(TimeWindows.of(Duration.ofHours(1)))
        .count()
        .toStream()
        .to("order-counts-per-hour");

KSQL / Confluent ksqlDB: SQL interface on top of Kafka Streams.
  CREATE TABLE order_counts AS
    SELECT user_id, COUNT(*) AS count
    FROM orders
    WINDOW TUMBLING (SIZE 1 HOUR)
    GROUP BY user_id;

┌────────────────┬─────────────────────┬──────────────────────────────┐
│ Feature        │ Kafka               │ RabbitMQ                     │
├────────────────┼─────────────────────┼──────────────────────────────┤
│ Model          │ Log-based stream    │ Queue (AMQP)                 │
│ Replay         │ Yes (offset-based)  │ No (deleted after ACK)       │
│ Throughput     │ Millions/sec        │ Thousands/sec                │
│ Ordering       │ Per-partition       │ Per-queue (FIFO)             │
│ Consumers      │ Many (fan-out)      │ Competing consumers          │
│ Message TTL    │ Configurable        │ Per-queue or per-message     │
│ Routing        │ Key-based partition │ Exchange/routing key (flex)  │
│ Complexity     │ Higher ops          │ Simpler to manage            │
│ Best for       │ Event streaming     │ Task queues, RPC, routing    │
└────────────────┴─────────────────────┴──────────────────────────────┘

USE KAFKA WHEN:
  ✓ Need high throughput (> 100K messages/sec)
  ✓ Multiple consumers need the same events (fan-out)
  ✓ Need to replay events from any point in time
  ✓ Building event sourcing systems
  ✓ Real-time analytics pipelines (Kafka Streams)
  ✓ Change data capture (Debezium → Kafka)

USE RABBITMQ WHEN:
  ✓ Task queue (jobs to distribute among workers)
  ✓ Need complex routing (topic/header/fanout exchanges)
  ✓ Need request-reply messaging (RPC over messaging)
  ✓ Simpler ops and smaller scale
  ✓ Need priority queues
