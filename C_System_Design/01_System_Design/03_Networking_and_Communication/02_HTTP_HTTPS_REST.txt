HTTP (HyperText Transfer Protocol)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HTTP is an application-layer protocol for transferring data on the web.
It follows a request-response model: client sends request, server responds.

HTTP REQUEST STRUCTURE:
  Method + URL + Version
  Headers (key: value pairs)
  [Blank line]
  Body (optional)

  Example:
    POST /api/users HTTP/1.1
    Host: api.example.com
    Content-Type: application/json
    Authorization: Bearer eyJhbGci...
    
    {"name": "Alice", "email": "alice@example.com"}

HTTP RESPONSE STRUCTURE:
  Version + Status Code + Reason
  Headers
  [Blank line]
  Body

  Example:
    HTTP/1.1 201 Created
    Content-Type: application/json
    Location: /api/users/123
    
    {"id": 123, "name": "Alice", "created_at": "2026-04-08T10:00:00Z"}

HTTP METHODS:
  GET     → Retrieve resource (safe, idempotent, no body)
  POST    → Create resource (not idempotent, has body)
  PUT     → Replace entire resource (idempotent, has body)
  PATCH   → Partial update (not necessarily idempotent, has body)
  DELETE  → Delete resource (idempotent, no body)
  HEAD    → Like GET but response has no body (check headers/existence)
  OPTIONS → Check allowed methods (used in CORS preflight)

SAFE: No side effects (GET, HEAD, OPTIONS)
IDEMPOTENT: Same result if called multiple times (GET, PUT, DELETE)
  → Critical for retry logic: never auto-retry POST (creates duplicates)

HTTP STATUS CODES (Must Know):
  1xx Informational:
    100 Continue
    101 Switching Protocols (WebSocket upgrade)
  
  2xx Success:
    200 OK
    201 Created
    202 Accepted (async, will process later)
    204 No Content (successful, no response body)
  
  3xx Redirection:
    301 Moved Permanently (search engines update index)
    302 Found (temporary redirect)
    304 Not Modified (cached response is still valid)
    307 Temporary Redirect (method preserved)
    308 Permanent Redirect (method preserved)
  
  4xx Client Errors:
    400 Bad Request (invalid syntax)
    401 Unauthorized (not authenticated)
    403 Forbidden (authenticated but not authorized)
    404 Not Found
    405 Method Not Allowed
    409 Conflict (e.g., duplicate resource)
    410 Gone (permanently deleted)
    422 Unprocessable Entity (validation error)
    429 Too Many Requests (rate limited)
  
  5xx Server Errors:
    500 Internal Server Error
    501 Not Implemented
    502 Bad Gateway (upstream server error)
    503 Service Unavailable (overloaded or down)
    504 Gateway Timeout (upstream didn't respond in time)

HTTP HEADERS (Critical):
  Request Headers:
    Authorization: Bearer <token>    (auth)
    Content-Type: application/json   (body format)
    Accept: application/json         (desired response format)
    Cache-Control: no-cache          (cache directives)
    X-Request-ID: abc123             (correlation ID for tracing)
    User-Agent: Mozilla/5.0...       (client info)
    If-None-Match: "etag_value"      (conditional request)
    If-Modified-Since: Thu, 01 Jan   (conditional request)
    Origin: https://app.example.com  (CORS)

  Response Headers:
    Content-Type: application/json
    Cache-Control: max-age=3600
    ETag: "abc123"
    Location: /api/users/123  (after 201 Created)
    Retry-After: 60           (after 429, seconds to wait)
    X-RateLimit-Limit: 1000
    X-RateLimit-Remaining: 42
    X-RateLimit-Reset: 1680000000

HTTPS (TLS/SSL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HTTPS = HTTP + TLS (Transport Layer Security)
  - Encrypts all traffic (prevents eavesdropping)
  - Server authentication (prevents man-in-the-middle)
  - Data integrity (prevents tampering)

TLS HANDSHAKE (TLS 1.3):
  1. Client → Server: ClientHello (supported cipher suites, random)
  2. Server → Client: ServerHello + Certificate + Finished
  3. Client validates certificate (from trusted CA)
  4. Client → Server: Encrypted handshake data
  [1 RTT overhead — TLS 1.3 improved from TLS 1.2's 2 RTT]

0-RTT (Session Resumption):
  For returning clients, TLS 1.3 allows 0-RTT with session ticket.
  Replay attack risk for non-idempotent requests — only use for GETs.

Certificate Types:
  DV (Domain Validated): Verifies domain ownership only (Let's Encrypt)
  OV (Org Validated):    Verifies domain + organization identity
  EV (Extended Validation): Strictest; shows company name in browser
  Wildcard:              *.example.com covers all subdomains

Certificate Rotation:
  Always have automated certificate renewal (Let's Encrypt + Certbot, 
  AWS ACM auto-renews). Manual processes → cert expiry → outage.

mTLS (Mutual TLS):
  Both client AND server present certificates and verify each other.
  Used for service-to-service authentication within a cluster.
  Service mesh (Istio, Linkerd) implements mTLS automatically.

REST (Representational State Transfer)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

REST is an architectural style for building APIs over HTTP.
It is not a protocol — it's a set of constraints.

REST CONSTRAINTS (Fielding's 6 constraints):
  1. Client-Server: Separation of concerns (UI vs data storage)
  2. Stateless: Each request contains all info needed (no server session)
  3. Cacheable: Responses must indicate if they're cacheable
  4. Uniform Interface: Standard resource-based URLs, HTTP methods
  5. Layered System: Client doesn't know if it's talking to server directly
  6. Code on Demand (optional): Server can send executable code to client

RESOURCE-ORIENTED DESIGN:
  URLs represent resources (nouns), not actions (verbs).
  HTTP methods define the action.

  BAD (RPC-style):
    POST /createUser
    POST /deleteUser
    POST /getUserById

  GOOD (REST):
    POST   /users           (create)
    DELETE /users/{id}      (delete)
    GET    /users/{id}      (read by id)
    GET    /users?page=1    (list)
    PUT    /users/{id}      (full update)
    PATCH  /users/{id}      (partial update)

NESTED RESOURCES:
  /users/{user_id}/posts                  (all posts by user)
  /users/{user_id}/posts/{post_id}        (specific post by user)
  /users/{user_id}/posts/{post_id}/comments  (comments on post)
  
  Don't nest more than 2 levels deep — becomes unwieldy.
  Alternative: /posts/{post_id}/comments (flat with filter)

REST API VERSIONING:
  Method 1 — URL versioning (most common):
    /v1/users, /v2/users
  
  Method 2 — Header versioning:
    Accept: application/vnd.myapi.v2+json
  
  Method 3 — Query parameter:
    /users?version=2
  
  Best practice: URL versioning (v1, v2) is visible and unambiguous.
  Maintain v1 for backward compatibility; deprecate with sunset date.

PAGINATION:
  Offset-based (simple):
    GET /posts?offset=0&limit=20    (page 1)
    GET /posts?offset=20&limit=20   (page 2)
    Problem: If items are inserted/deleted, pages shift → duplicates/gaps

  Cursor-based (recommended):
    GET /posts?limit=20
    Response: { data: [...], next_cursor: "eyJpZCI6MjB9" }
    GET /posts?cursor=eyJpZCI6MjB9&limit=20
    Pro: Stable pagination; no duplicates or gaps
    Con: Cannot jump to page N directly

  Keyset-based:
    GET /posts?after_id=20&limit=20
    WHERE id > 20 ORDER BY id LIMIT 20
    Fast for large offsets (uses index scan, not full scan)

FILTERING AND SORTING:
  GET /posts?author_id=123&status=published&sort=created_at:desc
  GET /users?created_after=2026-01-01&role=admin

RATE LIMITING HEADERS (for API clients):
  X-RateLimit-Limit: 1000
  X-RateLimit-Remaining: 234
  X-RateLimit-Reset: 1712574400   (Unix timestamp)
  Retry-After: 3600               (if limit hit: seconds to wait)

IDEMPOTENCY IN REST:
  For POST requests (which create resources), provide idempotency key:
  Idempotency-Key: unique-client-generated-id

  Server: if key already seen → return previous response without re-creating.
  Critical for payments: if POST /payments fails halfway, client retries
  with same idempotency key → no duplicate charge.

REST vs RPC vs GraphQL:
  REST:     Standard, cacheable, widely understood. Overfetch/underfetch.
  gRPC:     Binary, typed, streaming. Great for microservices.
  GraphQL:  Client controls what data it gets. Great for mobile/complex UIs.

REST BEST PRACTICES CHECKLIST:
  □ Use nouns not verbs in URLs
  □ Use proper HTTP methods (GET, POST, PUT, PATCH, DELETE)
  □ Return appropriate status codes
  □ Validate and sanitize all inputs
  □ Version the API (/v1/, /v2/)
  □ Use cursor-based pagination for large lists
  □ Include metadata in list responses (total count, next page)
  □ Accept and return JSON with Content-Type: application/json
  □ Compress responses (gzip/br)
  □ HTTPS only — no HTTP
  □ Rate limit all endpoints
  □ Idempotency keys for non-idempotent operations
  □ Correlation/trace IDs in headers
  □ Consistent error format: { error: { code, message, details } }
