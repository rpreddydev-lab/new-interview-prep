================================================================
BACK OF THE ENVELOPE ESTIMATIONS
================================================================

WHY ESTIMATION MATTERS
-----------------------
Capacity estimation tells you:
  - How many servers you need
  - What database technology to choose (SQL vs NoSQL)
  - Whether caching is necessary and how large
  - How much storage to provision
  - Whether a single machine can handle the load

Engineers who can estimate quickly and accurately demonstrate
strong engineering judgment — a key signal in system design interviews.

UNITS AND CONVERSIONS TO MEMORIZE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TIME:
  1 minute  =    60 seconds
  1 hour    =  3,600 seconds   (≈ 3.6K)
  1 day     = 86,400 seconds   (≈ 100K)   ← KEY NUMBER
  1 month   =  2,592,000 sec  (≈ 2.5M)
  1 year    = 31,536,000 sec  (≈ 30M)

STORAGE:
  1 KB  = 10^3  bytes  = 1,000 bytes
  1 MB  = 10^6  bytes  = 1,000 KB
  1 GB  = 10^9  bytes  = 1,000 MB
  1 TB  = 10^12 bytes  = 1,000 GB
  1 PB  = 10^15 bytes  = 1,000 TB

  (In practice, 1 KB = 1,024 bytes, but use 1,000 for rough math)

THROUGHPUT:
  Typical web server:     10,000 req/s
  Redis (single node):   100,000 ops/s
  MySQL (single node):    ~5,000 writes/s, ~50,000 reads/s
  Kafka (1 partition):   ~1M messages/s
  SSD sequential read:   ~500 MB/s
  HDD sequential read:   ~100 MB/s
  Network (1 Gbps NIC):  ~125 MB/s
  Network (10 Gbps NIC): ~1.25 GB/s

LATENCY (Jeff Dean's numbers, approximate):
  L1 cache:                  0.5 ns
  L2 cache:                    7 ns
  RAM read:                  100 ns  = 0.1 μs
  4KB SSD random read:       150 μs
  1MB SSD sequential read:     1 ms
  Disk seek (HDD):            10 ms
  Same datacenter roundtrip: 0.5 ms
  Cross-datacenter (US→EU): 150 ms
  Global roundtrip (US→AU): 250 ms

ESTIMATION FORMULAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

QPS (Queries Per Second):
  QPS = DAU × actions_per_user_per_day / 86,400
  Peak QPS = Average QPS × 2  (assume 2× peak for safety)

  NOTE: 86,400 ≈ 100,000 for rough math, use 10^5

Storage per Day:
  Storage/day = writes_per_day × avg_object_size
  writes_per_day = write_QPS × 86,400

Storage for N Years:
  Total Storage = Storage/day × 365 × N

Bandwidth:
  Bandwidth = QPS × avg_request_size

Number of Servers (rough):
  # servers = total_QPS / QPS_per_server
  QPS_per_server = 10,000 (commodity web server, conservative)

WORKED EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EXAMPLE 1: URL Shortener (like bit.ly)
---------------------------------------
Assumptions:
  - 100M URLs shortened per day (write-heavy at creation, but smaller)
  - 10:1 read:write ratio → 1B redirects per day
  - Avg URL length: 2,000 bytes (long URL)
  - Short code: 8 chars + metadata ≈ 500 bytes per record
  - Retain URLs for 5 years

Calculations:
  Write QPS  = 100M / 86,400 ≈ 1,157 → ~1.2K QPS
  Read  QPS  = 1B   / 86,400 ≈ 11,574 → ~12K QPS
  Peak  Read = 12K × 2 = 24K QPS

  Storage/day  = 100M × 500B = 50GB/day
  Storage/5yr  = 50GB × 365 × 5 ≈ 90TB

  Bandwidth (read) = 12K QPS × 500B = 6 MB/s (manageable with CDN)

Implications:
  → Cache for reads (12K QPS — Redis can handle easily)
  → DB for writes (1.2K QPS — single MySQL server is fine initially)
  → Need ~100TB storage over 5 years → consider S3 or Cassandra
  → Short code must be unique globally → Base62 encoding of MD5/counter

EXAMPLE 2: Twitter / Social Feed
----------------------------------
Assumptions:
  - 150M DAU
  - Average user posts 1 tweet per day (some more, many none)
  - Average user reads feed 20 times per day (20 tweets each read)
  - Average tweet size: 300 bytes (text + metadata)
  - Media: 10% of tweets contain image (avg 3MB compressed), 1% video

Calculations:
  Write QPS (tweets)   = 150M × 1 / 86,400 ≈ 1,736 → ~2K QPS
  Read  QPS (timeline) = 150M × 20 / 86,400 ≈ 34,722 → ~35K QPS
  Read  QPS (per page) = 35K × 20 tweets   = 700K tweet reads/s

  Peak write QPS = 2K × 3 = 6K QPS (during events/news)
  Peak read  QPS = 35K × 3 = 105K QPS

  Text Storage/day  = 2K × 86,400 × 300B = 51.8GB ≈ 52 GB/day
  Text Storage/5yr  = 52 × 365 × 5 ≈ 95 TB

  Image Storage/day = 2K × 0.1 × 86,400 × 3MB ≈ 51.8 TB/day  [!]
  → This is massive — must use CDN + tiered storage + compression

  Note: 150M × 20 × 300B / 86,400 ≈ 10 MB/s for text bandwidth
  With images: orders of magnitude higher → CDN is non-negotiable

Implications:
  → Cache timelines in Redis (precomputed fan-out)
  → Shard tweets table by user_id (avoid hot partitions)
  → Media in S3 + CloudFront CDN
  → 35K read QPS → need 4-5 servers for reads (10K QPS each)
  → Celebrity users: hybrid fan-out strategy

EXAMPLE 3: WhatsApp (Chat System)
------------------------------------
Assumptions:
  - 2B MAU, 500M DAU
  - Each user sends 40 messages/day
  - Average message size: 100 bytes (text)
  - Media: 30% of messages are media (avg 100KB)
  - Messages retained 30 days on server (then purged if delivered)

Calculations:
  Write QPS (messages) = 500M × 40 / 86,400 ≈ 231K → ~230K QPS
  Read  QPS ≈ Write QPS (each message is read by at least 1 recipient)
  
  Text messages/day = 500M × 40 = 20B messages/day
  Text Storage/day  = 20B × 100B = 2TB/day
  Text Storage/30d  = 2TB × 30   = 60TB

  Media messages/day = 20B × 0.3 = 6B media messages
  Media Storage/day  = 6B × 100KB = 600TB/day  [!]
  → Not feasible to store ALL media; use expiration or user-managed

  Connections: 500M concurrent WebSocket connections
  → Need ~500M / 64K connections per server ≈ ~7,812 servers
  → (Each modern server can handle ~65,536 TCP connections)

Implications:
  → 230K msg/sec → Kafka for message fanout
  → WebSocket for real-time delivery; fallback to long-polling
  → Sharding by conversation_id for message storage
  → End-to-end encryption: client-side keys, server stores ciphertext only
  → Media: store in S3, only link in message; expire after 90 days

EXAMPLE 4: YouTube / Video Platform
--------------------------------------
Assumptions:
  - 2B MAU, 500M DAU
  - 500 hours of video uploaded per minute (read: YouTube stat)
  - 1B videos watched per day
  - Avg video size: 500MB raw, 50MB after compression (720p)
  - Avg video duration: 7 minutes

Calculations:
  Upload QPS = 500 hours/min = 30,000 hours/hour
    = 30,000 × 60min × 60s / 86,400  ... simpler:
    = 500 × 60 / 60 = 500 uploads/s (of 7-min videos)

  Storage upload/day = 500/min × 60min/hr × 24hr × 50MB
    = 720,000 videos/day × 50MB = 36 PB/day  [!]
    → YouTube stores 4K, 1080p, 720p, 360p → 4× multiplier = 144 PB/day
    → Infeasible for small companies; use aggressive CDN + compression

  Watch QPS = 1B/day / 86,400 ≈ 11,574 → ~12K video starts/sec
  Bandwidth (watch) = 12K × 5 Mbps (video bitrate) = 60 Gbps
    → MUST use CDN; no single data center can serve this

Implications:
  → CDN is the single most important component for YouTube
  → Video processing pipeline: upload → transcode → distribute to CDN
  → Metadata in MySQL, video files in distributed blob storage
  → Recommendation engine: separate service (ML)
  → Read-heavy: >99% of traffic is reads

ESTIMATION TIPS AND TRICKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Round aggressively:
   Use powers of 10: 86,400 ≈ 100,000; 150M ≈ 10^8
   This makes mental math easy and still gives correct order of magnitude

2. Always multiply by a safety factor:
   - Peak load = 2× or 3× average
   - Storage = 1.5× calculated (overhead, replication, OS)
   - With replication factor 3, multiply storage by 3

3. Work in consistent units:
   Convert everything to the same unit before calculating
   (e.g., all sizes in bytes, all times in seconds)

4. Use the 80/20 rule for caching:
   Top 20% of content gets 80% of reads
   → Cache size ≈ 20% of total data set for 80% hit rate

5. Think about replication overhead:
   - If replication factor = 3, storage cost triples
   - If read replicas = 3, read throughput triples

6. Think about compression:
   - Text compresses ~5-10× (gzip)
   - Images: already compressed; minimal gain
   - Video: H.264/H.265 already very efficient

7. Estimation doesn't need to be exact:
   If your number is within 2× of reality, that's good enough to
   drive the right architectural decisions.
