================================================================
CLOCK SYNCHRONIZATION AND VECTOR CLOCKS
================================================================

THE PROBLEM WITH TIME IN DISTRIBUTED SYSTEMS
---------------------------------------------
Every node has its own local clock (real-time hardware clock).
These clocks drift and are never perfectly synchronized.

Why does ordering matter?
  - We need to determine: "Did event A happen before event B?"
  - For conflict resolution in multi-leader replication
  - For causal consistency (ensure reply comes after post)
  - For distributed tracing (reconstruct timeline of events)

CLOCK ISSUES:
  Clock drift:     Physical clocks run at slightly different rates.
                   Even atomic clocks drift: ~1 μs/day
                   Common server clocks: 10-100 ms/hour drift
  
  NTP correction:  NTP syncs clocks to ~1-10ms accuracy in LAN,
                   ~50-100ms over the internet.
                   Problem: NTP can go BACKWARDS (slew or step correction).
  
  Leap seconds:    UTC occasionally inserts a leap second.
                   Causes 23:59:60 — programs often crash.
  
  Time zone bugs:  Daylight saving time causes repeated hour.

CONSEQUENCE: Cannot use wall-clock timestamps for distributed event ordering!
  If event A on Node 1 at 12:00:00.100 and event B on Node 2 at 12:00:00.090,
  we can't conclude A happened before B — Node 2's clock might be 50ms behind.

LAMPORT TIMESTAMPS (Logical Clocks)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Leslie Lamport, 1978. Assigns logical timestamps to preserve causal ordering.

ALGORITHM:
  Each node maintains a counter L (starts at 0).
  
  1. Before any event: L = L + 1
  2. Before sending a message: L = L + 1; attach L to message
  3. On receiving a message with timestamp T: L = max(L, T) + 1

HAPPENS-BEFORE RELATION:
  A → B (A happened before B) if:
    - A and B are on the same node, and A occurred first, OR
    - A sends a message that B receives
  
  Lamport clock guarantees: if A → B, then L(A) < L(B).
  But NOT the converse: L(A) < L(B) does NOT mean A → B.
  Concurrent events can have any Lamport order.

LIMITATION:
  Can't detect concurrent events.
  If L(A) < L(B), can't tell if A caused B or they're just concurrent.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
VECTOR CLOCKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Extension of Lamport clocks that CAN detect concurrent events.

ALGORITHM:
  Each node N_i maintains a vector V_i = [c_1, c_2, ..., c_n]
  where c_j = node i's knowledge of node j's logical clock.
  
  Initially: V_i = [0, 0, ..., 0]
  
  1. Before local event: V_i[i] += 1
  2. Before sending: V_i[i] += 1; attach V_i to message
  3. On receiving message with vector V_msg:
     V_i[j] = max(V_i[j], V_msg[j]) for all j
     V_i[i] += 1

EXAMPLE (3 nodes A, B, C):
  A does local event:   V_A = [1,0,0]
  A sends to B:         V_A = [2,0,0]; message carries [2,0,0]
  B receives from A:    V_B = [2,1,0] (max element-wise + own increment)
  B sends to C:         V_B = [2,2,0]; message carries [2,2,0]
  C receives from B:    V_C = [2,2,1]
  
  Meanwhile, independently:
  C does local event:   V_C_alt = [0,0,1]
  
  These two clocks for C are: [2,2,1] and [0,0,1]
  They are CONCURRENT: neither dominates the other.

COMPARISON OF VECTOR CLOCKS:
  V1 < V2 (V1 happened-before V2): All components of V1 ≤ V2, at least one <
  V1 = V2 (same event): All components equal
  V1 || V2 (concurrent): Neither V1 < V2 nor V2 < V1
  
  V1=[2,2,1] vs V2=[0,0,1]:
  V1[0]=2 > V2[0]=0 → V1 has seen events V2 hasn't.
  V2[2]=1 = V1[2]=1 → same on C
  But V1[0]=2 > V2[0]=0 → not ≤ across all
  → CONCURRENT

USED BY: Amazon Dynamo, Riak, vector clock-aware databases

SCALING ISSUE: Vector clocks have O(N) size for N nodes.
Large clusters → large clocks → overhead.
Solution: Version vectors (only track nodes that actually wrote the data).

GOOGLE TRUETIME (Spanner)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Google Spanner uses GPS receivers and atomic clocks in each datacenter.
TrueTime API: Returns time as an interval [earliest, latest].
The actual current time is guaranteed to be within this interval.
Typical interval: ±4ms (±ε).

EXTERNAL CONSISTENCY with TrueTime:
  To commit a transaction at timestamp T_commit:
  1. Assign T_commit = TrueTime.now().latest
  2. Wait until TrueTime.now().earliest > T_commit (commit wait)
  3. Then apply the commit
  
  This "commit wait" (usually ~7ms) ensures that when clients read
  at timestamp T, all transactions that committed before T are visible.
  
  Result: Global linearizable transactions across the world!
  Cost: Extra latency for commit wait.

HYBRID LOGICAL CLOCKS (HLC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Combines wall-clock time and logical clocks.
HLC = (physical_time, logical_counter)

Properties:
  - Clock never goes backward (monotonically increasing)
  - Tracks causality (like vector clocks)
  - Stays close to physical time (unlike pure logical clocks)
  - Compact: single value (unlike vector clocks)

Used by: CockroachDB (uses HLC for transaction ordering)

PRACTICAL IMPLICATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LAST-WRITE-WINS (LWW) WITH WALL CLOCK:
  Use timestamp to determine which write wins.
  Problem: Clock skew means a "later" write (by wall clock) may have
  arrived first logically. Can silently lose data.
  Use only when: Occasional data loss is acceptable and clock skew is bounded.
  Better: LWW with Lamport timestamps or HLC.

DON'T USE System.currentTimeMillis() for ordering in distributed systems!
  Instead: Use logical clocks, vector clocks, or HLC.
           Or delegate to a centralized timestamp service.

INTERVIEW ANSWER:
  "In distributed systems, we can't rely on wall-clock timestamps for
   event ordering because of clock skew and NTP corrections. Instead,
   we use logical clocks:
   - Lamport clocks: simple counter, ensures causal ordering.
   - Vector clocks: per-node counters, detects concurrent events.
   - HLC (Hybrid Logical Clocks): combines physical + logical, used by CockroachDB.
   - TrueTime (Google Spanner): GPS/atomic clocks with bounded uncertainty.
   
   For most distributed systems, if I need causal ordering, I'd use
   logical timestamps or a centralized sequence generator."
