================================================================
CONSISTENCY PATTERNS IN DISTRIBUTED SYSTEMS
================================================================

HOW DISTRIBUTED SYSTEMS ACHIEVE CONSISTENCY
---------------------------------------------
This file covers implementation patterns for achieving various
consistency levels in practice.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 1: SINGLE LEADER (PRIMARY-REPLICA)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All writes go to the leader. Reads from replicas (with lag) or leader.
Consistency level depends on read routing and replication mode.

Strong consistency: Write to leader (sync replication), read from leader.
Eventual consistency: Write to leader (async replication), read from replica.

Used by: PostgreSQL, MySQL, Redis Sentinel, MongoDB (w/replica set)

Consistency guarantee: Linearizable if reads go to leader with sync replication.
Trade-off: Leader is write bottleneck; read scaling via replicas.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 2: QUORUM (Majority Vote)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

N replicas total. Write to W replicas, read from R replicas.
Strong consistency when: W + R > N (overlap guaranteed)

Example (N=3):
  W=2, R=2: W+R=4 > 3 → Strongly consistent (1 overlap guaranteed)
  W=1, R=1: W+R=2 ≤ 3 → Eventual consistency
  W=3, R=1: W+R=4 > 3 → Strong consistency (all must write; read from any)
  W=1, R=3: Same as above

SLOPPY QUORUM:
  DynamoDB and Cassandra: If a target node is down, another healthy
  node temporarily accepts the write (hinted handoff).
  When the down node recovers, the hint is delivered.
  Trades strict consistency for availability (AP behavior).

Used by: Cassandra, DynamoDB, Riak

Consistency guarantee: Configurable from eventual to strong.
Trade-off: Network round-trips to multiple nodes per operation.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 3: MULTI-VERSION CONCURRENCY CONTROL (MVCC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Database keeps multiple versions of each row.
Reads see a snapshot of data as of transaction start time.
Writes create new versions; old versions remain until garbage collected.

Benefits:
  - Readers don't block writers; writers don't block readers
  - Each transaction sees a consistent snapshot
  - Supports snapshot isolation and repeatable read isolation

PostgreSQL MVCC:
  Each row has xmin (transaction that created it) and xmax (transaction that deleted it).
  A transaction T with transaction ID TxID sees a row if:
    xmin ≤ TxID < xmax (row was created before T, not deleted before T)
  
  This gives each transaction a consistent "snapshot" without locking.

Snapshot Isolation:
  Every transaction works on a snapshot of the DB at its start time.
  Problem: Write skew (each transaction sees old values, both commit)
  Example: Two doctors both check if ≥1 doctor is on-call (yes), both go on leave.
           Now 0 doctors on-call → violated constraint.
  Fix: Serializable Snapshot Isolation (SSI) — PostgreSQL's serializable level.

Used by: PostgreSQL, MySQL InnoDB, Oracle, CockroachDB, MongoDB

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 4: CAUSAL CONSISTENCY WITH VECTOR CLOCKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Track causal dependencies between operations.
If event A caused event B, all nodes see A before B.

Vector Clock: Each node maintains a vector of counters.
{Node1: 3, Node2: 2, Node3: 1}

When Node1 sends a message to Node2:
  Increment Node1's counter: {Node1: 4, ...}
  Node2 receives: takes max of each component + increment own:
  Node2's new clock = {Node1: 4, Node2: 3, Node3: 1}

Comparison:
  Clock A < Clock B (B happened after A): all components of A ≤ B, at least one <
  Clock A || Clock B (concurrent): neither dominates → potential conflict

Used by: Riak, Amazon DynamoDB (version vectors), distributed logs

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 5: TWO-PHASE LOCKING (2PL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ensure serializability by locking rows.

Growing phase: Acquire locks (read/write) as needed.
Shrinking phase: Once any lock is released, no new locks can be acquired.

Types:
  Shared lock (S): Multiple readers can hold simultaneously.
  Exclusive lock (X): Only one writer; blocks all other S and X locks.

Problem: DEADLOCK — two transactions each hold a lock the other wants.
Fix: Deadlock detection (cycle detection in lock dependency graph) → abort one.
Fix: Deadlock prevention (always acquire locks in the same order).

Used by: Traditional RDBMS (PostgreSQL without SSI, MySQL InnoDB)
Note: MVCC largely replaced 2PL for read-write scenarios.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PATTERN 6: SAGA (Distributed Consistency Without Distributed Transactions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use compensating transactions instead of distributed locking.
(See Microservices section for full detail.)

Sequence of local transactions, each publishing an event.
If a step fails, compensating transactions undo previous steps.

Example: Order → Reserve Inventory → Charge Payment → Ship
  If Charge Payment fails: Cancel Inventory Reservation (compensation)

Provides eventual consistency, not ACID. But scales well.

CHOOSING A CONSISTENCY PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌─────────────────────────────────┬─────────────────────────────────┐
│ Need                            │ Pattern                         │
├─────────────────────────────────┼─────────────────────────────────┤
│ ACID single-node                │ MVCC + 2PL (standard RDBMS)     │
│ Read scaling with consistency   │ Single leader + sync replication │
│ Write scaling + eventual        │ Quorum (Cassandra) PA/EL        │
│ Write scaling + strong          │ Quorum W+R>N (QUORUM+QUORUM)    │
│ Multi-service transactions      │ Saga pattern                    │
│ Collaborative editing           │ OT or CRDTs                     │
│ Distributed locks               │ Raft-based (etcd, Zookeeper)    │
│ Global transactions (expensive) │ Spanner (TrueTime + 2PC)        │
└─────────────────────────────────┴─────────────────────────────────┘
