DATA ENCRYPTION AT REST AND IN TRANSIT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. ENCRYPTION FUNDAMENTALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY ENCRYPT?
  Data at rest: If storage media is stolen/breached, data is unreadable
  Data in transit: Prevents eavesdropping, man-in-the-middle attacks
  
  Compliance requirements:
    PCI DSS: Encrypt cardholder data
    HIPAA: Encrypt PHI at rest and in transit
    GDPR: Encryption is a key mitigation for breach liability

SYMMETRIC ENCRYPTION:
  Same key for encryption and decryption
  Fast — suitable for bulk data encryption
  Algorithm: AES (Advanced Encryption Standard)
    AES-128, AES-256 (key size in bits — AES-256 preferred)
    Modes: GCM (Galois/Counter Mode) — provides confidentiality AND integrity
           CTR (Counter Mode) — confidentiality only
           CBC (Cipher Block Chaining) — avoid (padding oracle attacks)
  
  Challenge: Key distribution — how do both parties get the same key securely?

ASYMMETRIC ENCRYPTION:
  Public key: encrypt, verify signatures (can be shared freely)
  Private key: decrypt, create signatures (must stay secret)
  Algorithms:
    RSA-2048, RSA-4096: Classic; 2048 minimum; 4096 for long-lived keys
    ECC (Elliptic Curve): Smaller keys, same security — P-256, P-384, X25519
    RSA is slower than ECC for equivalent security
  
  Use cases: TLS handshake key exchange, digital signatures, key wrapping

KEY EXCHANGE — DIFFIE-HELLMAN:
  Allows two parties to establish a shared secret over an insecure channel
  Neither party transmits the shared secret — they derive it independently
  
  Simple analogy:
    Alice and Bob agree on public base values (g, p)
    Alice: sends g^a mod p
    Bob: sends g^b mod p
    Shared secret = g^(a*b) mod p (both can compute, eavesdropper cannot)
  
  ECDH (Elliptic Curve DH): Modern, much faster than classic DH
  ECDHE: Ephemeral DH — new keys per session → Perfect Forward Secrecy

PERFECT FORWARD SECRECY (PFS):
  Each session uses unique ephemeral keys
  Compromise of long-term private key does NOT reveal past session keys
  Required for modern TLS — ECDHE key exchange
  Without PFS: One compromised private key decrypts ALL past recorded traffic


2. ENCRYPTION IN TRANSIT — TLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TLS (Transport Layer Security) — Replaces deprecated SSL
Current version: TLS 1.3 (RFC 8446, 2018)
Deprecated: SSL 2.0, SSL 3.0, TLS 1.0, TLS 1.1 — all must be disabled

TLS 1.3 HANDSHAKE (simplified):
  1. ClientHello: TLS version, cipher suites, key share (ECDH public key)
  2. ServerHello: Chosen cipher suite, key share, certificate
  3. Key derivation: Both compute shared secret via ECDHE
  4. Server sends Finished (HMAC of entire handshake)
  5. Client sends Finished
  6. Encrypted data transfer begins
  
  Total round trips: 1 RTT (vs 2 RTT for TLS 1.2)
  0-RTT resumption: For reconnects, can send data in first message
                    (replay attack risk — only for idempotent GET requests)

TLS CIPHER SUITES (TLS 1.3 only 5 supported, all strong):
  TLS_AES_128_GCM_SHA256
  TLS_AES_256_GCM_SHA384
  TLS_CHACHA20_POLY1305_SHA256
  (and 2 more)

CERTIFICATE VALIDATION:
  Server certificate signed by Certificate Authority (CA)
  CA chain: Root CA → Intermediate CA → Leaf certificate
  Browser/client trusts Root CAs (bundled OS/browser CA store)
  
  Certificate contains: domain name (CN/SAN), public key, expiry, issuer
  Client checks: signature valid, not expired, hostname matches, not revoked
  
  Certificate Transparency (CT) logs: Public log of all issued certificates
  Detects unauthorized cert issuance (e.g., someone getting cert for your domain)

LET'S ENCRYPT:
  Free, automated CA
  ACME protocol for automatic cert issuance and renewal
  Cert expiry: 90 days (forces frequent rotation)
  Certbot handles auto-renewal

CERTIFICATE PINNING:
  App hardcodes expected certificate or public key
  Prevents MITM even with compromised CA
  Pins: Full cert (brittle — breaks on renewal) or public key hash (better)
  
  Certificate Public Key Hash (HPKP alternative):
    Expected-Public-Key: sha256/...base64...
    (HTTP header or hardcoded in mobile app)
  
  Risk: If private key is lost, app is bricked until update
  Use for: High-security mobile apps, internal services

MTLS (Mutual TLS):
  Both client AND server authenticate with certificates
  Client presents its certificate; server validates it
  Used for: Service-to-service authentication in microservices
            Zero Trust networking
  
  Flow:
    1. TLS handshake (server presents certificate)
    2. Server requests client certificate
    3. Client presents certificate
    4. Server validates client certificate against trusted CA
  
  Infrastructure: Service mesh (Istio) handles mTLS automatically
                  Sidecar proxies (Envoy) handle cert rotation

HSTS (HTTP Strict Transport Security):
  HTTP header telling browsers to ONLY use HTTPS:
  Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  
  Prevents protocol downgrade attacks
  preload: Browsers include site in hardcoded HTTPS-only list


3. ENCRYPTION AT REST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FULL DISK ENCRYPTION (FDE):
  Entire disk encrypted at block level
  Transparent to applications — files read/written normally
  Only protects against theft of physical media
  
  Technologies: Linux LUKS, macOS FileVault, Windows BitLocker
  AWS: EBS volumes with encryption (AES-256); transparent to EC2
  
  Key stored in hardware TPM (Trusted Platform Module)
  Doesn't protect against: Attacker who gains access while disk is mounted

DATABASE-LEVEL ENCRYPTION:
  Transparent Data Encryption (TDE):
    Encrypts database files and backups on disk
    Transparent to SQL queries — decrypted in memory
    Oracle, SQL Server, PostgreSQL (pgcrypto extension)
    AWS RDS: Enabled at instance creation; cannot be changed later
    
  LIMITATION: TDE doesn't protect against a compromised DBA who can
              read the data through SQL queries

COLUMN-LEVEL / FIELD-LEVEL ENCRYPTION:
  Encrypt specific sensitive columns, not entire DB
  Application encrypts data BEFORE writing to DB
  DB stores ciphertext; only authorized services can decrypt
  
  Use cases:
    - PII (SSN, credit card, medical records)
    - Encryption per tenant (multi-tenant SaaS)
    - Sensitive fields that DBAs should not see
  
  Example:
    Plaintext SSN: "123-45-6789"
    AES-256-GCM encrypted: [base64 encoded ciphertext]
    Stored in DB: "AQIDBAUGBwgJCgsMDQ4PEB..."
    
  Searchability challenge:
    Cannot do: WHERE ssn = '123-45-6789' (it's encrypted in DB)
    Solutions:
      - Deterministic encryption (same plaintext → same ciphertext for equality checks)
        Risk: Frequency analysis possible
      - Hash index: Store SHA-256(ssn) in separate index column for equality search
      - Application decrypts, then compares (slow for large tables)
      - Searchable encryption / Homomorphic encryption (research-stage)


4. KEY MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

THE KEY MANAGEMENT PROBLEM:
  "Where do you store the key that encrypts your data?"
  If key is stored with data: Attacker who gets data gets key too
  Solution: Separate the key from the data it protects

ENVELOPE ENCRYPTION:
  The standard pattern for encryption at scale
  
  Two layers of keys:
    DEK (Data Encryption Key): Randomly generated per object/record
    KEK (Key Encryption Key): Master key that encrypts DEKs
                              Stored in KMS (Key Management Service)
  
  Encryption process:
    1. Generate random DEK for each record
    2. Encrypt the data with DEK (AES-256-GCM)
    3. Encrypt the DEK with KEK (via KMS)
    4. Store: encrypted data + encrypted DEK together
  
  Decryption process:
    1. Read encrypted data + encrypted DEK
    2. Call KMS to decrypt the DEK with KEK
    3. Decrypt data with plaintext DEK
    4. Zero out the plaintext DEK from memory immediately
  
  Benefits:
    - Rotate KEK without re-encrypting all data (just re-wrap DEKs)
    - Compromise of DEK → only one record exposed
    - Compromise of KEK → all DEKs can be decrypted, but KEK is in KMS
    - KMS controls who can use KEK (IAM policies)

AWS KMS:
  Managed HSM (Hardware Security Module)
  Keys never leave HSM — KMS performs crypto on your behalf
  
  CreateKey: Create a new CMK (Customer Master Key)
  Encrypt(KeyId, Plaintext) → Ciphertext (up to 4KB)
  Decrypt(CipherText) → Plaintext (KMS determines key from ciphertext)
  GenerateDataKey(KeyId) → {Plaintext DEK, Encrypted DEK}
  
  KMS Audit: Every key usage logged to CloudTrail
  Key rotation: Automatic annual rotation or manual
  Multi-region keys: Replicate keys across regions for DR
  
  COST: $1/key/month + $0.03 per 10,000 API calls

HASHICORP VAULT:
  Open-source secrets management
  
  Secrets engines:
    KV: Simple key-value secret storage
    PKI: Certificate authority — issue/revoke X.509 certificates
    Database: Dynamic short-lived DB credentials
    AWS: Dynamic short-lived AWS IAM credentials
    Transit: Encryption-as-a-service (like KMS)
  
  Dynamic secrets:
    "Please give my app DB credentials for 1 hour"
    Vault creates DB user, gives app credentials, revokes after 1 hour
    Advantage: No long-lived credentials to steal
  
  Vault auth methods:
    Kubernetes: Pod's service account token → Vault token
    AppRole: Machine-to-machine authentication
    AWS IAM: EC2 instance role → Vault token

KEY ROTATION:
  Regularly rotate encryption keys to limit exposure window
  Rotation requires re-encryption of data with new key (expensive for large data)
  Envelope encryption makes this feasible: Only re-encrypt DEKs, not all data
  
  Schedule: KEK: Annually or on suspected compromise
            DEK: Per-object (already fresh for each record)
  
  On suspicion of compromise: Immediate rotation + incident response


5. SECRETS MANAGEMENT — DON'T HARDCODE CREDENTIALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ANTI-PATTERN:
  DB_PASSWORD = "super_secret_123"  ← in code
  api_key = "sk-prod-abcdef"        ← in config file committed to Git

  Once in Git, it's FOREVER (git history preserves it even after deletion)

CORRECT APPROACHES:

1. ENVIRONMENT VARIABLES (minimum viable security):
   export DB_PASSWORD="$(aws secretsmanager get-secret-value ...)"
   Set in deployment pipeline; not stored in code
   
2. AWS SECRETS MANAGER:
   Store secrets; application fetches at startup or runtime
   Auto-rotation for RDS/Redshift/DocumentDB credentials
   Fine-grained IAM control over who can retrieve
   Cost: $0.40/secret/month + $0.05 per 10,000 API calls
   
   Python example:
   import boto3
   client = boto3.client('secretsmanager')
   response = client.get_secret_value(SecretId='prod/db/password')
   password = response['SecretString']

3. KUBERNETES SECRETS (encrypted at rest in etcd):
   kubectl create secret generic db-secret --from-literal=password=mypassword
   Mounted as environment variable or volume in pod
   
   Better: Store in Vault/KMS, inject with Secrets Store CSI Driver

4. VAULT AGENT SIDECAR:
   Vault Agent runs as sidecar container
   Fetches secrets on pod start; writes to shared memory volume
   Handles renewal and rotation automatically

INTERVIEW ANSWER — "How do you protect sensitive data at rest?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"I use envelope encryption via AWS KMS:

Each sensitive record gets a randomly generated DEK (AES-256-GCM).
The DEK encrypts the data. The DEK itself is then encrypted by a KEK
stored in KMS. We store the encrypted data + encrypted DEK together.

KMS never exposes the KEK — all crypto happens inside the HSM.
KMS logs every key usage to CloudTrail, so we have full auditability.

For column-level encryption of PII: application encrypts before writing
to the database. DBAs and DB-level attackers see ciphertext.

For TDE (transparent data encryption): whole-disk via AWS RDS encryption,
protecting backup media from physical theft.

Key rotation is handled by re-wrapping DEKs with a new KEK — no need
to re-encrypt all data. This makes annual rotation feasible.

All secrets (DB passwords, API keys) are stored in AWS Secrets Manager,
never hardcoded or committed to Git."
