================================================================
STRANGLER FIG PATTERN
================================================================

WHAT IS THE STRANGLER FIG PATTERN?
------------------------------------
A migration strategy for incrementally replacing a monolithic system
with microservices, one feature at a time.

Named after the strangler fig tree: a vine that wraps around a tree,
gradually replacing it. The old tree eventually dies; the fig remains.

WHY NOT BIG-BANG MIGRATION?
  Rewriting an entire monolith at once ("Big Bang" rewrite) is VERY risky:
  - Takes years
  - Team must maintain OLD system while building NEW one
  - New system must reach feature parity before launch
  - Integration is validated only at the end
  - High probability of failure: Google's Wave, Netscape 6, Healthcare.gov
  
  Martin Fowler: "If you do a big bang rewrite, the only guaranteed result
  is a big bill."

HOW STRANGLER FIG WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1: ADD A FACADE/PROXY
  Introduce an API Gateway or reverse proxy in front of the monolith.
  All traffic still goes to monolith initially.
  Proxy is transparent (pass-through).
  
  Client → Proxy → Monolith (100% of traffic)

STEP 2: EXTRACT A SERVICE
  Build a new microservice for one feature/domain (e.g., User Profile).
  Deploy the new service alongside the monolith.
  
  Client → Proxy → Monolith (still 100% of traffic initially)
                 → New UserProfile Service (deployed but no traffic yet)

STEP 3: ROUTE TRAFFIC TO NEW SERVICE
  Configure proxy to route specific paths to new service.
  /api/users/* → New UserProfile Service
  Everything else → Monolith
  
  Client → Proxy → /api/users/* → New UserProfile Service
                 → Other routes  → Monolith

STEP 4: SHADOW TRAFFIC (Optional but recommended)
  Before fully switching, run shadow testing:
  Route real traffic to BOTH old and new service.
  Compare responses — must be identical.
  New service receives traffic but responses are discarded (shadow).
  Validate new service is correct without affecting users.

STEP 5: REMOVE FROM MONOLITH
  Once new service is stable in production:
  Delete the corresponding code from the monolith.
  Monolith is now smaller.

STEP 6: REPEAT
  Extract another domain → route traffic → delete from monolith.
  Over time: monolith shrinks, new services multiply.
  Eventually: monolith is gone (or handles only untouched legacy features).

DATA MIGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CHALLENGE: Monolith and new service may need the same data.
During the transition, both the monolith and new service may write
to user profiles → data is split across two databases.

STRATEGIES:

A. NEW SERVICE CALLS MONOLITH API (Short-term):
   New UserProfile Service reads/writes to the monolith's data via API.
   Temporarily couples new service to monolith.
   Use only until full migration is complete.

B. SHARED DATABASE (Anti-pattern but pragmatic for transition):
   New service directly accesses monolith's database (shared DB).
   Only acceptable as TEMPORARY step during migration.
   Long-term: must move to database-per-service.

C. SYNCHRONIZATION:
   New service has its own DB.
   Sync data from monolith to new service's DB (CDC / batch sync).
   Write to new service's DB; read from it.
   After migration: stop sync, monolith code removed.

D. DUAL WRITE:
   Both monolith and new service write to their respective DBs.
   Consistency maintained via events or sync jobs.
   Gradually shift reads to new service to verify consistency.
   Once confident: cut over completely to new service.

WHAT TO EXTRACT FIRST?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Prioritize extraction by:

1. HIGHEST BUSINESS VALUE:
   Features that are frequently changing or need independent deployment.
   Example: Recommendation engine (constantly tuned by ML team).

2. CLEAR BOUNDARIES:
   Features with well-defined APIs and minimal coupling to monolith.
   Example: Authentication/authorization service.

3. DIFFERENT SCALING REQUIREMENTS:
   Features that need more (or less) scale than the monolith.
   Example: Image processing (CPU-intensive, scale independently).

4. DIFFERENT TECHNOLOGY NEEDS:
   Features that would benefit from a different technology stack.
   Example: Search functionality → Elasticsearch microservice.

AVOID EXTRACTING FIRST:
  ✗ Core transaction processing (high coupling, risk of data inconsistency)
  ✗ Features with complex data dependencies across many monolith tables
  ✗ Features that change together with other features (extract as a unit)

INTERVIEW ANSWER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"The Strangler Fig pattern incrementally migrates a monolith to
 microservices. Rather than a risky big-bang rewrite, we:
 1. Put an API gateway/proxy in front of the monolith.
 2. Extract one bounded context to a new service.
 3. Route that service's traffic through the proxy to the new service.
 4. Verify with shadow traffic before full cutover.
 5. Remove the code from the monolith.
 6. Repeat for each domain.
 
 The key challenge is data: during transition, the new service may
 need access to monolith data. I'd use CDC (Debezium) to sync data
 to the new service's database, then cut over when confident.
 
 I'd extract high-value, low-coupling boundaries first — like auth,
 notifications, or search — before tackling the core transactional
 domains that have deep dependencies."
