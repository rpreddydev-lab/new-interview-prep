================================================================
LOAD BALANCING
================================================================

WHAT IS A LOAD BALANCER?
--------------------------
A load balancer distributes incoming network traffic across multiple
servers (backend pool) to ensure:
  - No single server is overwhelmed
  - High availability (traffic is routed away from failed servers)
  - Optimal resource utilization

Load Balancer sits between the client and the server pool:
  Client → Load Balancer → [Server 1, Server 2, Server 3, ...]

LAYER 4 (L4) vs LAYER 7 (L7) LOAD BALANCERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

L4 Load Balancer (Transport Layer):
  - Operates on TCP/UDP — sees IP address and port only
  - Does NOT inspect HTTP content (headers, URL, cookies)
  - Very fast and low overhead
  - Cannot do content-based routing
  - Examples: AWS NLB (Network Load Balancer), HAProxy (TCP mode)

  Use when:
    - Extremely low latency required
    - Non-HTTP traffic (gRPC, MQTT, game servers)
    - Millions of concurrent connections

L7 Load Balancer (Application Layer):
  - Operates on HTTP/HTTPS — can inspect headers, URL, cookies, body
  - Can route based on content (path-based, host-based routing)
  - Supports SSL termination (decrypts HTTPS, forwards HTTP internally)
  - Can do A/B testing, canary deployments, rate limiting
  - Higher overhead than L4 but much more flexible
  - Examples: AWS ALB (Application Load Balancer), Nginx, Traefik

  Use when:
    - HTTP/HTTPS workloads
    - Microservices with different routing rules
    - Need SSL termination at LB level
    - A/B testing or canary releases

L7 Routing Examples:
  /api/users/*    → User Service
  /api/payments/* → Payment Service
  /api/media/*    → Media Service
  Host: admin.example.com → Admin Service
  Header: X-Version=v2 → New Service Version (canary)

LOAD BALANCING ALGORITHMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. ROUND ROBIN (Default)
   Distributes requests sequentially in rotation.
   Server 1 → Server 2 → Server 3 → Server 1 → ...
   
   Pro:  Simple, even distribution if all servers are equal
   Con:  Doesn't account for server load or response time
   Best: Homogeneous servers with similar request processing time

2. WEIGHTED ROUND ROBIN
   Same as round robin but servers with higher weight get more requests.
   Server 1 (weight 3): → → → Server 2 (weight 1): →
   Cycle: [S1, S1, S1, S2, S1, S1, S1, S2, ...]
   
   Pro:  Handles heterogeneous server pools (different CPU/RAM)
   Con:  Static weights; doesn't adapt to real-time load
   Best: Mixed hardware where one server is 3× more powerful

3. LEAST CONNECTIONS
   Route to the server with the fewest active connections.
   If S1 has 10 connections and S2 has 2, next request goes to S2.
   
   Pro:  Handles long-lived connections well (WebSockets, file transfers)
   Con:  Slightly more complex state tracking
   Best: Heterogeneous request durations (some requests take much longer)

4. LEAST RESPONSE TIME
   Route to the server with the lowest average response time AND
   fewest active connections.
   
   Pro:  Best for optimizing user experience
   Con:  Requires monitoring response time per server
   Best: When server performance varies dynamically

5. IP HASH (Sticky Sessions / Session Affinity)
   Hash the client IP address to consistently route to the same server.
   hash(client_ip) % num_servers → always the same server
   
   Pro:  Client always goes to same server (useful for stateful services)
   Con:  Breaks if server is added/removed (hash changes)
         Uneven distribution if many clients share an IP (NAT)
   Better alternative: Use consistent hashing or session in Redis

6. CONSISTENT HASHING
   Servers and requests are placed on a ring using a hash function.
   Each request is routed to the nearest server clockwise on the ring.
   When a server is added/removed, only a portion of keys remapped.
   
   Pro:  Minimal redistribution on server addition/removal
   Con:  More complex to implement
   Best: Distributed caches (Redis Cluster), CDN routing

7. RANDOM
   Route to a randomly selected server.
   Pro:  Simple, stateless, no tracking needed
   Con:  Uneven distribution with small server counts
   Best: Large server pools where statistical evenness kicks in

HEALTH CHECKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Load balancers perform health checks to detect server failures:

PASSIVE HEALTH CHECKS:
  Monitor actual traffic responses. If a server returns 5xx errors
  above a threshold, mark it unhealthy and stop routing to it.

ACTIVE HEALTH CHECKS:
  Periodically send health probe requests (e.g., GET /health).
  If no 200 response within timeout, mark server unhealthy.

HEALTH CHECK ENDPOINT BEST PRACTICES:
  - /health or /healthz
  - Returns 200 with JSON: {"status": "ok", "version": "1.2.3"}
  - Checks DB connectivity, cache connectivity, disk space
  - Shallow health check (just the service) vs deep (dependencies)
  - Response time < 100ms (don't compute in health check)

UNHEALTHY SERVER HANDLING:
  1. Stop routing new requests to unhealthy server
  2. Drain existing connections (configurable drain timeout)
  3. Continue health checks to detect recovery
  4. Resume routing when server passes health check N times in a row

SSL TERMINATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SSL Termination at the Load Balancer:
  Client → [HTTPS] → LB → [HTTP] → Backend Servers

Advantages:
  - Offloads TLS processing from backend servers (CPU-intensive)
  - Single place to manage SSL certificates
  - Backend communication can use plain HTTP (faster within trusted VPC)

SSL Passthrough:
  Client → [HTTPS] → LB → [HTTPS] → Backend Servers
  LB does not decrypt — just forwards encrypted traffic.
  Backend servers handle TLS.

  When to use passthrough:
  - End-to-end encryption requirement (compliance)
  - Content-based routing not needed (L4 LB)

GLOBAL LOAD BALANCING (GeoDNS / Global Traffic Manager)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For global services, distribute traffic across geographic regions:

1. GeoDNS (DNS-based GLB):
   - DNS resolves to different IPs based on requester's geographic location
   - US-East users → us-east load balancer
   - EU users → eu-west load balancer
   - Asia users → ap-southeast load balancer
   
   Limitation: DNS TTL means stale responses for minutes; not instant failover

2. Anycast (BGP-based):
   - Multiple servers share the same IP address globally
   - BGP routing directs traffic to the nearest server
   - Used by Cloudflare, Google (8.8.8.8 DNS resolves to nearest server)
   - True instant failover (BGP reconvergence in seconds)

3. Application-Level GLB (AWS Global Accelerator, Cloudflare):
   - Routes traffic through the cloud provider's global backbone
   - Anycast entry point → optimal path to regional backend
   - Health checks at region level; instant failover

LOAD BALANCER HIGH AVAILABILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The load balancer itself must not be a single point of failure!

Active-Passive HA:
  - Primary LB handles all traffic
  - Secondary LB is on standby
  - Virtual IP (VIP) floats between them via VRRP/Keepalived
  - Failover: ~1-3 seconds

Active-Active HA:
  - Multiple LBs share the load
  - Anycast or GeoDNS distributes across them
  - No failover needed (existing LBs absorb failed node's traffic)

Cloud Managed Load Balancers:
  - AWS ALB/NLB: Fully managed, highly available, auto-scaling
  - GCP Load Balancer: Global anycast, built-in DDoS protection
  - Azure Load Balancer: Zone-redundant

  - AWS ALB: Load balancer + some API gateway features
  - Kong/AWS API Gateway: Full API gateway with LB built in

COMMON INTERVIEW QUESTIONS ON LOAD BALANCING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you handle session stickiness without sticky sessions?
A: Store sessions in an external distributed store (Redis). All servers
   can read the session from Redis for any request. No stickiness needed.

Q: What happens when you add a new server with Round Robin?
A: The new server starts receiving its fair share immediately. If it has
   a warm-up period (JVM, connection pool), use a "slow start" feature
   in Nginx/HAProxy that gradually increases its weight.

Q: How do you do zero-downtime deployments with a load balancer?
A: Rolling deployment:
   1. Take Server 1 out of rotation (LB stops sending traffic)
   2. Deploy new version to Server 1
   3. Health check Server 1 → passes
   4. Put Server 1 back in rotation
   5. Repeat for Server 2, 3, ...
   OR: Blue-Green deployment — spin up entire new fleet, switch LB.

Q: What is the difference between load balancing and service mesh?
A: Load balancer: external traffic distribution at the edge
   Service mesh (Istio, Linkerd): internal service-to-service communication,
   load balancing, circuit breaking, mTLS, observability within the cluster
