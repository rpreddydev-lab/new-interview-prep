WHAT IS AN API GATEWAY?
------------------------
An API Gateway is a server that acts as an entry point for all client
requests. It sits between clients and backend services, providing:
  - Single entry point for all APIs
  - Cross-cutting concerns handled once (not in every service)
  - Protocol translation and request routing

Without API Gateway:
  Client → direct call to each microservice (chaos)
  
With API Gateway:
  Client → API Gateway → routes to appropriate microservice

CORE FUNCTIONS:
  1. Request Routing
     Route based on URL path, headers, method, or body content.
     /api/users/*   → User Service
     /api/orders/*  → Order Service
     /api/payments/* → Payment Service
     Host: admin.api.com → Admin Service

  2. Authentication & Authorization
     Validate JWT tokens, API keys, OAuth2 tokens.
     Reject unauthenticated requests BEFORE they hit services.
     Extract user context (user_id, roles) and pass to services.
     Services trust the gateway — don't re-validate (reduces overhead).

  3. Rate Limiting
     Limit requests per user/IP/API key per time window.
     Returns 429 Too Many Requests when limit exceeded.
     Protects backend services from DDoS and runaway clients.

  4. SSL/TLS Termination
     Handle HTTPS at the gateway; communicate with services via HTTP
     (within trusted VPC/cluster).

  5. Request/Response Transformation
     Add/remove headers (X-User-ID, X-Request-ID)
     Transform JSON format between client and service versions
     Aggregate multiple service responses into one (API composition)

  6. Caching
     Cache common responses at the gateway level.
     Reduces load on backend services for common queries.

  7. Load Balancing
     Distribute requests across multiple instances of each service.

  8. Circuit Breaking
     If a service is failing, stop sending requests to it temporarily.
     Return cached response or error immediately.

  9. Request Logging & Metrics
     Log all requests/responses (audit trail, debugging).
     Emit metrics per endpoint (latency, error rate, throughput).

  10. Protocol Translation
      REST/JSON external → gRPC internal
      WebSocket external → message queue internal
      GraphQL → REST backend services

BACKEND FOR FRONTEND (BFF) PATTERN:
  Instead of one API gateway for all clients, create a gateway
  per client type:
    Mobile BFF     → optimized for mobile (smaller payloads, aggregated)
    Web BFF        → optimized for web app
    Third-party BFF → public API, versioned, rate limited

WHAT IS RATE LIMITING?
-----------------------
Rate limiting restricts the number of requests a client can make
within a time window. Protects against:
  - DDoS attacks (malicious traffic flooding)
  - Abuse by automated scripts
  - Unintentional runaway clients (infinite retry loops)
  - Ensures fair usage (one client can't starve others)

RATE LIMITING DIMENSIONS:
  - Per IP address (coarse; NAT breaks this)
  - Per user/account (more accurate)
  - Per API key (for third-party API access)
  - Per endpoint (different limits for different routes)
  - Per server (global limit across all instances)

RATE LIMITING ALGORITHMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. TOKEN BUCKET (Most Common)
   A bucket holds tokens (capacity = max burst size).
   Tokens refill at a constant rate (e.g., 100 tokens/second).
   Each request consumes 1 token.
   If no tokens: reject request (429).

   Properties:
   - Allows bursting up to bucket capacity
   - Smooth average rate = token refill rate
   - Simple to implement with atomic operations

   Redis implementation:
     tokens = redis.GET(user_key)
     if tokens >= 1:
         redis.DECR(user_key)
         allow request
     else:
         return 429

   Refill: Background job (or lazy refill based on time elapsed)

2. LEAKY BUCKET
   Requests enter a queue (bucket). A worker processes them at
   a fixed rate (like water leaking from bucket).
   If queue is full: reject.

   Properties:
   - Smooths out bursts (requests are queued, not rejected)
   - Fixed output rate regardless of input burst
   - Memory overhead for queue
   
   vs Token Bucket:
   - Token bucket: allows bursting, requests processed immediately
   - Leaky bucket: no bursting, queue-based, stable output rate

3. FIXED WINDOW COUNTER
   Count requests per time window (e.g., 1000 req/hour).
   Reset counter at start of each hour.

   Simple:
     counter = redis.INCR("rate:user_123:hour:1712")
     if counter > 1000:
         return 429

   Problem: Burst at window boundary!
   Example: 999 requests at 12:59 + 999 requests at 13:00 = 1998 req in 2 minutes.

4. SLIDING WINDOW LOG
   Store timestamp of every request in a sorted set.
   Count requests within the last window (e.g., last 60 seconds).
   Evict old timestamps.

   redis.ZADD("rate:user_123", now, request_id)
   redis.ZREMRANGEBYSCORE("rate:user_123", 0, now - window)
   count = redis.ZCARD("rate:user_123")
   if count > limit: return 429

   Pro:  Very accurate, no boundary burst problem
   Con:  High memory usage (stores every request timestamp)
   Best: When accuracy is critical

5. SLIDING WINDOW COUNTER
   Hybrid of fixed window and sliding window.
   current_window_count + (previous_window_count × overlap%)

   Example (1000 req/minute limit):
   At 12:30 (30% into current minute):
     previous_window = 800 requests (last minute: 12:00-12:59)
     current_window  = 200 requests (this minute so far)
     overlap = 70% of previous window still "in" the last 60 seconds
     approximate_count = 200 + (800 × 0.70) = 760

   Pro:  Low memory, reasonably accurate
   Con:  Approximation (not exact) — acceptable for most use cases

DISTRIBUTED RATE LIMITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM: Rate limiter must work across multiple gateway instances.
  Server 1 sees 500 requests from user_123.
  Server 2 sees 600 requests from user_123.
  Each allows them — user exceeds global limit of 1000.

SOLUTION: Central store (Redis) for counters.
  All gateway instances read/write the same Redis key.
  Redis INCR is atomic — no race conditions.

  user_key = "rate:{user_id}:{window}"
  count = redis.INCR(user_key)
  redis.EXPIRE(user_key, window_seconds)  # if count == 1 (first in window)
  if count > limit: return 429

CHALLENGES:
  - Redis becomes a bottleneck for very high traffic
    Solution: Redis Cluster (shard rate limit keys)
  - Network latency to Redis (adds ~0.5ms per request)
    Solution: Local cache with async sync to Redis (approximate limit)
  - Redis failure → rate limiting fails open or closed
    Solution: Fail open (allow requests) with local fallback limits

RATE LIMITING HEADERS (communicate limits to clients):
  X-RateLimit-Limit:     1000    (max requests per window)
  X-RateLimit-Remaining: 234     (remaining requests this window)
  X-RateLimit-Reset:     1712574400  (Unix timestamp when window resets)
  Retry-After:           3600    (seconds to wait if rate limited)

DESIGN CONSIDERATIONS FOR RATE LIMITER (Interview)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Requirements:
  - Configurable: different limits per endpoint, per user tier
  - Distributed: works across multiple gateway nodes
  - Low latency: adds < 1ms to every request
  - Accurate: doesn't allow significantly more than configured limit
  - Visible: clients know their limits and remaining quota

Design:
  - Store: Redis (atomic INCR, TTL, Cluster for scale)
  - Algorithm: Token bucket or sliding window counter
  - Key structure: "rl:{service}:{user_id}:{endpoint}:{window}"
  - Eviction: TTL = window size
  - Return: 429 with Retry-After header
  - Log: rejected requests for alerting / abuse investigation

Handling Redis failure:
  - Primary: Redis for accuracy
  - Fallback: Local in-memory counter (approximate)
  - Alert on Redis unavailability
