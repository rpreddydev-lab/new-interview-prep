ALERTING AND DASHBOARDS — ALERTMANAGER, SLO ALERTING, ON-CALL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT MAKES A GOOD ALERT?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Good alert properties (from Google SRE Book):
  Actionable: the recipient can do something about it
  Relevant: it indicates real user impact (or imminent impact)
  Urgent: requires response within the notification window
  Accurate: low false positive rate (otherwise ignored/silenced)

Test every alert against:
  "If this fires at 3am, does the on-call engineer need to wake up?"
  If NO → it's not a page; make it a ticket or warning

Alert tiers:
  PAGE (immediate): user impact NOW; on-call woken up within minutes
    SLO burn rate critical, error rate spike, complete service outage
  
  TICKET (business hours): important but not urgent
    Disk at 80%, cache hit rate declining, dependency deprecated
  
  LOG (FYI): informational, no action needed
    Successful backups, cron job completions


2. ALERT FATIGUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Alert fatigue: too many alerts → engineers start ignoring them
  Most dangerous state: more false positive pages than real ones
  Engineers "numb" to alerts → miss real incidents

Causes:
  Alerting on symptoms that don't affect users (CPU high, GC pauses)
  Too-tight thresholds (alert on 5min spike that self-resolves)
  Duplicate alerts (same root cause fires 20 different alerts)
  No context in alert (just "ERROR RATE HIGH" — no what/where/why)

Solutions:
  SLO-based alerting: only alert when error budget is burning
  Alert deduplication (Alertmanager's group_by)
  Alert inhibition: if service is DOWN, suppress all dependent alerts
  Runbook links: every alert must link to troubleshooting runbook
  Alert review: weekly review of alerts that fired but required no action


3. PROMETHEUS ALERTMANAGER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Alertmanager: receives alerts from Prometheus, handles routing and notification

Architecture:
  Prometheus evaluates alert rules → fires alerts to Alertmanager
  Alertmanager: deduplicate → group → route → notify

  prometheus-rule.yml:
    groups:
    - name: order-service
      rules:
      - alert: HighErrorRate
        expr: |
          rate(http_requests_total{service="order-service",status=~"5.."}[5m])
          / rate(http_requests_total{service="order-service"}[5m]) > 0.05
        for: 2m                  # must be true for 2 min before firing
        labels:
          severity: critical
          team: checkout
        annotations:
          summary: "Order service error rate > 5%"
          description: "Error rate is {{ $value | humanizePercentage }}"
          runbook: "https://wiki/runbooks/order-service-errors"

  alertmanager.yml:
    global:
      slack_api_url: 'https://hooks.slack.com/...'
    
    route:
      group_by: ['alertname', 'service']    # group alerts by these labels
      group_wait: 30s                        # wait before sending first group
      group_interval: 5m                     # wait before sending new alerts
      repeat_interval: 4h                    # re-notify if still firing
      receiver: default
      routes:
        - match: { severity: critical }
          receiver: pagerduty-critical
        - match: { team: checkout }
          receiver: slack-checkout-team
    
    receivers:
      - name: pagerduty-critical
        pagerduty_configs:
        - service_key: '<pagerduty-key>'
      
      - name: slack-checkout-team
        slack_configs:
        - channel: '#checkout-alerts'
          text: '{{ .CommonAnnotations.summary }}'

Alertmanager features:
  Grouping: combine 20 "high memory" alerts from 20 pods into 1 notification
  Inhibition: silence cart alerts if payment service is completely down
  Silencing: maintenance windows (silence by label for 2 hours)
  Routing tree: route by severity → team → environment


4. SLO-BASED ALERTING DEEP DIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Multi-window multi-burn-rate alerting (Google recommendation):

  SLO: 99.9% availability (0.1% error budget) per 30-day rolling window
  Monthly budget in seconds: 30 × 24 × 60 × 60 × 0.001 = 2,592 seconds

  TIER 1 — CRITICAL PAGE (2 conditions must be true):
    Condition 1: error rate > 14× budget rate in last 1 hour
    Condition 2: error rate > 14× budget rate in last 5 minutes
    
    14× burn rate: burns 14% of monthly budget per hour (full budget in ~2 days)
    Why two windows? 1h ensures it's sustained; 5min ensures it's still happening now

  TIER 2 — PAGE (2 conditions must be true):
    Condition 1: error rate > 6× budget rate in last 6 hours
    Condition 2: error rate > 6× budget rate in last 30 minutes
    
    6× burn rate: burns 20% of monthly budget per 6 hours (full in ~5 days)

  TIER 3 — TICKET (business hours):
    Error rate > 3× budget rate in last 3 days AND last 6 hours
    Slow burn: not urgent but trend is bad

  PromQL for error budget:
    # Target error rate (for 99.9% SLO)
    # 0.001 = 1 - 0.999
    
    # 1-hour window burn rate
    (sum(rate(http_requests_total{job="order", status=~"5.."}[1h]))
    / sum(rate(http_requests_total{job="order"}[1h])))
    / 0.001 > 14
    
    # AND 5-minute fast confirmation
    (sum(rate(http_requests_total{job="order", status=~"5.."}[5m]))
    / sum(rate(http_requests_total{job="order"}[5m])))
    / 0.001 > 14


5. GRAFANA DASHBOARDS — BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Golden Signals Dashboard (per service):
  Row 1: RED method overview
    Requests/sec (stat panel)
    Error rate % (gauge 0-100%)
    p50/p95/p99 latency (time series)
  
  Row 2: Infrastructure
    CPU utilization per instance (time series, multi-line)
    Memory usage (time series)
    Active connections (stat)
  
  Row 3: Dependencies
    Downstream service error rates
    Cache hit ratio
    Queue depth/lag (if using Kafka/SQS)
  
  Row 4: Business metrics
    Orders/min, payments/min, active users (depends on service)

SLO Dashboard:
  Current availability (% past 30 days) → big stat panel, red if SLO breached
  Error budget remaining (% and time) → countdown-style
  Burn rate over time (time series) → annotated with deploys
  Budget consumption calendar (heatmap per day)

Dashboard variables (Grafana template variables):
  $service — dropdown to switch between order/payment/user service
  $environment — production / staging / development
  $datacenter — us-east, eu-west, ap-southeast
  All panels filter by these variables → single dashboard for all contexts

Dashboard-as-code:
  Store in Git as JSON or Grafonnet (Jsonnet)
  PR review for dashboard changes
  Deploy via Grafana HTTP API or Terraform grafana provider


6. INCIDENT MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

On-call rotation:
  PagerDuty / Opsgenie: schedule management, escalation policies
  Primary on-call → 10min no ack → Secondary → 30min → Manager

Incident severity:
  SEV1: complete service outage, revenue impact, customer data loss
    All hands; incident commander assigned; comms every 15min
  SEV2: major feature broken, significant user impact
    Small team; comms every 30min
  SEV3: minor degradation, no revenue impact
    Business hours; slack update only

Incident Response Flow:
  DETECT: alert fires (automated) or user report (ticket)
  TRIAGE: is it real? what's the severity? who's on-call?
  DIAGNOSE: dashboards → metrics → traces → logs; identify root cause
  MITIGATE: rollback deploy, enable circuit breaker, scale up, redirect traffic
  RESOLVE: permanent fix deployed; verify SLO metrics recovering
  POSTMORTEM: 48 hours later; blameless; what happened, why, action items

Runbook (Operational Playbook):
  For every alert, a runbook should exist:
    What this alert means
    How to verify (which dashboard/query)
    Likely root causes (top 5)
    Mitigation steps (step-by-step commands)
    Escalation path (who to call if not resolved in 30 min)


7. ERROR TRACKING (vs Logging)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Specialized tools for exception tracking:
  Sentry: captures exceptions with full stack trace, groups similar errors
    De-duplication: 1000 occurrences of same error → 1 issue
    Shows: first seen, last seen, affected users, release version
    Release tracking: did this error start after deploy v2.3.1?

  Rollbar, Bugsnag: similar to Sentry

  Advantages over log grep:
    Automatic grouping of similar errors
    Per-error occurrence count and trend
    User breadcrumbs (what did user do before the crash)
    Deploy correlation
    Alert when a new error type appears


8. INTERVIEW TALKING POINTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Key phrases:
  "Every alert should be actionable — if it fires at 3am, someone must need to do something"
  "Alert on user impact, not resource thresholds"
  "SLO-based burn rate alerting eliminates false positives while catching slow burns"
  "Alertmanager groups and deduplicates — 50 pod alerts → 1 notification"
  "Every alert needs a runbook — the on-call engineer should never be guessing"
  "Post-mortems are blameless — we fix systems, not people"

What to show you know:
  Difference between symptom-based (error rate) vs cause-based (CPU high) alerts
    → Always alert on symptoms; diagnose causes during incident
  Multi-window burn rate alerting (fast burn: 1h+5m, slow burn: 6h+30m)
  Alertmanager routing, inhibition, silencing
  Error budget as a shared team metric (engineering + product conversation)
