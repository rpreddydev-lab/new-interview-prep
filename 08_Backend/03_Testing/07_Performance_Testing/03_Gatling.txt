PERFORMANCE TESTING — GATLING
Complete Interview Preparation Guide

1. WHAT IS GATLING?
================================================================

Gatling is a modern load testing tool designed for developers.
Key advantages over JMeter:
  - Code-based simulations (Scala or Java DSL) → version-controlled, reviewable
  - Excellent HTML reports with percentile graphs out of the box
  - Designed for CI/CD integration
  - More efficient (Akka-based non-blocking I/O → fewer resources per VU)
  - Real-time metrics

3. SIMULATION STRUCTURE (Java DSL)
================================================================

  import io.gatling.javaapi.core.*;
  import io.gatling.javaapi.http.*;
  import static io.gatling.javaapi.core.CoreDsl.*;
  import static io.gatling.javaapi.http.HttpDsl.*;
  
  public class OrderApiSimulation extends Simulation {
      
      // 1. HTTP Protocol config (shared base URL, headers)
      HttpProtocolBuilder httpProtocol = http
          .baseUrl("https://staging.api.example.com")
          .acceptHeader("application/json")
          .contentTypeHeader("application/json")
          .header("Authorization", "Bearer test-token-123");
      
      // 2. Scenario: sequence of HTTP requests
      ScenarioBuilder placeOrderScenario = scenario("Place Order")
          .exec(
              http("Get Product")
                  .get("/api/products/P-001")
                  .check(status().is(200))
                  .check(jsonPath("$.price").saveAs("price"))   // extract for reuse
          )
          .pause(1)    // 1 second think time
          .exec(
              http("Place Order")
                  .post("/api/orders")
                  .body(StringBody("""
                      {"productId": "P-001", "quantity": 2, "totalPrice": #{price}}
                  """))
                  .check(status().is(201))
                  .check(jsonPath("$.orderId").saveAs("orderId"))
          )
          .pause(Duration.ofMillis(500))
          .exec(
              http("Get Order Status")
                  .get("/api/orders/#{orderId}")
                  .check(status().is(200))
                  .check(jsonPath("$.status").is("PENDING"))
          );
      
      {
          // 3. Load profile (injection profile)
          setUp(
              placeOrderScenario.injectOpen(
                  atOnceUsers(5),                           // immediate spike
                  nothingFor(Duration.ofSeconds(5)),        // pause
                  rampUsers(50).during(Duration.ofSeconds(30)),  // ramp to 50
                  constantUsersPerSec(20).during(Duration.ofSeconds(60)) // hold
              )
          )
          .protocols(httpProtocol)
          .assertions(
              global().responseTime().percentile(95).lt(500),   // p95 < 500ms
              global().successfulRequests().percent().gte(99.0) // >= 99% success
          );
      }
  }

4. INJECTION PROFILES
================================================================

OPEN MODEL (new users arrive at a rate, regardless of system capacity):
  atOnceUsers(100)                           // 100 users immediately
  rampUsers(100).during(20)                  // ramp 100 users over 20s
  constantUsersPerSec(10).during(60)         // 10 new users/sec for 60s
  rampUsersPerSec(10).to(50).during(30)      // ramp from 10 to 50 users/sec
  stressPeakUsers(500).during(20)            // spike to 500, distribute over 20s

CLOSED MODEL (maintain N concurrent users at all times):
  constantConcurrentUsers(50).during(60)     // always 50 concurrent users
  rampConcurrentUsers(10).to(100).during(30) // ramp from 10 to 100 concurrent

5. FEEDER — TEST DATA
================================================================

  // CSV feeder
  FeederBuilder<String> userFeeder = csv("test-data/users.csv").random();
  // users.csv: userId,email,password
  
  // JSON feeder
  FeederBuilder<Object> productFeeder = jsonFile("test-data/products.json").circular();
  
  // Programmatic feeder
  FeederBuilder<Integer> quantityFeeder = Iterator.continually(
      Map.of("quantity", ThreadLocalRandom.current().nextInt(1, 10))
  )::next;
  
  // Use in scenario
  ScenarioBuilder scenario = scenario("Buy Products")
      .feed(userFeeder)           // injects userId, email vars from CSV
      .feed(quantityFeeder)       // injects quantity var
      .exec(
          http("Place Order")
              .post("/api/orders")
              .body(StringBody("""
                  {"userId": "#{userId}", "quantity": #{quantity}}
              """))
      );

6. ASSERTIONS AND THRESHOLDS
================================================================

  .assertions(
      // Global assertions (all requests)
      global().responseTime().mean().lt(200),              // avg < 200ms
      global().responseTime().percentile(95).lt(500),      // p95 < 500ms
      global().responseTime().percentile(99).lt(1000),     // p99 < 1 second
      global().successfulRequests().percent().gte(99.5),   // 99.5% success rate
      global().requestsPerSec().gte(50.0),                 // throughput >= 50 TPS
      
      // Per-request assertions
      forAll().responseTime().percentile(99).lt(2000),     // all requests p99 < 2s
      
      // Specific request assertions
      details("Place Order").responseTime().percentile(95).lt(300)
  );

  If assertions fail → Gatling exits with non-zero code → CI build fails.

7. RUNNING GATLING
================================================================

  # Run all simulations
  mvn gatling:test
  
  # Run specific simulation
  mvn gatling:test -Dgatling.simulationClass=OrderApiSimulation
  
  # With custom properties
  mvn gatling:test \
    -Dbase.url=https://staging.example.com \
    -Dusers=100 \
    -Dduration=300
  
  # Use system properties in simulation
  String baseUrl = System.getProperty("base.url", "http://localhost:8080");
  int users = Integer.parseInt(System.getProperty("users", "10"));
  
  Reports: target/gatling/orderapisimulation-*/index.html

8. GATLING REPORT HIGHLIGHTS
================================================================

  The HTML report includes:
    - Response Time Distribution histogram
    - Response Time Percentiles over Time (line graph)
    - Requests/sec over Time
    - Active Users over Time
    - Per-request breakdown with p50/p75/p95/p99 columns
    - Response status breakdown (2xx/3xx/4xx/5xx counts)

  Key graph: "Response Time Percentiles over Time"
    → Shows if latency increases under sustained load (memory leak indicator)
    → Flat line = stable; increasing line = degradation under load

9. GATLING VS JMETER COMPARISON
================================================================

Feature               | JMeter              | Gatling
----------------------|---------------------|-------------------
Test definition       | XML (.jmx)          | Java/Scala code
Version control       | Poor (XML noise)    | Excellent
Default reports       | Basic               | Beautiful HTML
CI/CD integration     | Via plugin          | Native, exit codes
Protocol support      | Very broad          | HTTP, WebSocket, gRPC
Concurrency model     | Thread-per-user     | Async (Akka) — efficient
Learning curve        | Low (GUI)           | Medium (code-based)
Distributed           | Built-in            | Gatling Enterprise only
Open source           | Yes (full)          | Yes (limited; Enterprise paid)

10. INTERVIEW QUESTIONS
================================================================

Q: How is Gatling different from JMeter?
A: Gatling simulations are code (Java/Scala DSL) — reviewable, git-tracked.
   JMeter uses XML (.jmx) files. Gatling is async (Akka-based) so it can
   simulate many users with fewer threads/resources. JMeter is thread-based.
   Gatling generates superior HTML reports by default and integrates naturally
   into CI/CD via Maven exit codes.

Q: What is an "open model" vs "closed model" injection in Gatling?
A: Open model: new users arrive at a rate regardless of how many are currently
   active (e.g., rampUsers(100)). Resembles real traffic where users keep
   arriving. Closed model: maintains a fixed number of concurrent users —
   when one leaves, a new one starts. Better for testing specific concurrency
   levels (e.g., 50 concurrent checkout sessions).

Q: How do you fail a CI build with Gatling?
A: Define assertions in the setUp() block, such as
   global().responseTime().percentile(95).lt(500). If the assertion fails,
   Gatling exits with a non-zero status code, which causes the Maven build
   and CI pipeline to fail.

Q: What is a "feeder" in Gatling?
A: A feeder provides dynamic test data to scenarios. CSV feeders read from
   a file; JSON feeders from JSON; programmatic feeders from code. Each
   virtual user gets data from the feeder (random, circular, or queue).
   Allows realistic testing with varied users, products, or order amounts.
