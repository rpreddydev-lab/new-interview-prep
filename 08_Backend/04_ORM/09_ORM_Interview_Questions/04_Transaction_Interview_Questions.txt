Transaction & Locking Interview Questions — 45 Essential Q&A
================================================================

ACID AND FUNDAMENTALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What does ACID stand for?
A: Atomicity — all operations succeed or all roll back.
   Consistency — DB moves from one valid state to another.
   Isolation — concurrent transactions don't see each other's partial work.
   Durability — committed changes survive crashes (persisted to disk/WAL).

Q2: How does Spring implement @Transactional?
A: AOP proxy. Spring wraps the bean with a JDK dynamic proxy (interface) or
   CGLIB proxy (concrete class). The proxy intercepts the method call:
   opens a transaction, calls the real method, commits on success, rolls back
   on exception. The original bean is never @Transactional — the proxy is.

Q3: What is the default rollback behavior of @Transactional?
A: Rolls back for unchecked exceptions (RuntimeException and Error).
   Does NOT roll back for checked exceptions (Exception subclasses).
   Override with rollbackFor = Exception.class or noRollbackFor = MyRuntimeEx.class.

Q4: What is transaction isolation?
A: Degree to which one transaction is shielded from others' in-flight changes.
   Higher isolation = fewer anomalies but more locking = less concurrency.
   Standard levels: READ_UNCOMMITTED < READ_COMMITTED < REPEATABLE_READ < SERIALIZABLE.

Q5: What is the default isolation level in Spring / most databases?
A: Spring default: Isolation.DEFAULT (uses DB default).
   PostgreSQL default: READ_COMMITTED.
   MySQL InnoDB default: REPEATABLE_READ.

PROPAGATION LEVELS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q6: What is the default transaction propagation?
A: REQUIRED — if a transaction exists, join it; otherwise create a new one.
   The most common. All work shares one transaction; if any part fails, all roll back.

Q7: What is REQUIRES_NEW propagation?
A: Suspends the current transaction and starts a completely independent new one.
   The new transaction commits/rolls back independently of the outer transaction.
   Use case: audit logging — log must persist even if the main transaction rolls back.
   Danger: both transactions hold locks simultaneously → deadlock potential.

Q8: What is NESTED propagation?
A: Executes within a savepoint inside the current transaction (JDBC savepoint support needed).
   If nested rolls back, only the savepoint is undone; outer transaction continues.
   Unlike REQUIRES_NEW, NESTED participates in the outer transaction's commit/rollback.
   Use case: partial retry of a sub-operation within a larger unit of work.

Q9: What is MANDATORY propagation?
A: The calling method MUST have an active transaction; throws
   IllegalTransactionStateException if none exists. Used to enforce that a method
   is always called within a transaction context (e.g., repository method that
   expects a transaction is already managing it).

Q10: What is NEVER propagation?
A: The method must NOT have an active transaction. Throws exception if one exists.
   Use for methods that should only run in non-transactional context.

Q11: What is NOT_SUPPORTED propagation?
A: Suspends any existing transaction. Executes without a transaction.
   Use for read-only operations where you explicitly don't want transactional overhead,
   or for non-transactional JNDI lookups.

Q12: What is SUPPORTS propagation?
A: If a transaction exists, joins it. If not, executes without a transaction.
   Use for read operations that can optionally participate in a transaction.
   Risky: behavior differs depending on whether called from transactional or
   non-transactional code — avoid in ambiguous contexts.

ISOLATION LEVELS AND ANOMALIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q13: What is a dirty read?
A: Reading uncommitted changes from another transaction. Prevented by
   READ_COMMITTED and higher. Example: tx2 reads balance modified by tx1
   which then rolls back — tx2 saw data that never existed.

Q14: What is a non-repeatable read?
A: Reading the same row twice within one transaction gets different values
   because another committed transaction modified it between the two reads.
   Prevented by REPEATABLE_READ and higher.

Q15: What is a phantom read?
A: Executing the same query twice within one transaction returns different
   ROWS because another transaction inserted/deleted matching rows.
   Prevented only by SERIALIZABLE.

Q16: When would you use SERIALIZABLE isolation?
A: Financial operations requiring absolute correctness — e.g., preventing
   double-booking of a resource, concurrent lottery draws, balance transfer
   from aggregate query. Very high cost: row-range locking, low concurrency.
   Usually overkill; pessimistic locking (FOR UPDATE) is more targeted.

Q17: What isolation level prevents dirty reads but not phantom reads?
A: READ_COMMITTED. Each query sees the latest committed snapshot.
   Re-reading the same range may yield different rows (phantoms) if
   another tx committed inserts/deletes between the two reads.

OPTIMISTIC LOCKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q18: How does optimistic locking work?
A: Adds a @Version field (int/long/Timestamp). On UPDATE:
   WHERE id=? AND version=?. If the version mismatches (another tx updated),
   UPDATE affects 0 rows → Hibernate throws OptimisticLockException.
   No DB locking — allows maximum concurrency; conflict detected at commit time.

Q19: What exception is thrown on optimistic lock conflict?
A: javax.persistence.OptimisticLockException (JPA) or
   org.hibernate.StaleObjectStateException (Hibernate-native).
   Spring wraps it in ObjectOptimisticLockingFailureException.

Q20: How do you handle OptimisticLockException?
A: Catch and retry the transaction. Using Spring Retry:
   @Retryable(value=OptimisticLockingFailureException.class, maxAttempts=3).
   Always reload the entity before retrying — the stale version is why it failed.

Q21: What is OPTIMISTIC_FORCE_INCREMENT lock mode?
A: Increments the @Version even if the entity wasn't modified.
   Use when you need to signal that an entity was accessed (read but not written),
   e.g., preventing concurrent reads of a "claim" from all proceeding with stale data.

Q22: When is optimistic locking better than pessimistic?
A: When conflicts are rare. Most reads/writes succeed without conflict.
   No DB lock held → higher concurrency, no deadlock risk.
   Better for web apps where users hold "state" in the client between page loads.

PESSIMISTIC LOCKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q23: What is PESSIMISTIC_WRITE?
A: Issues SELECT ... FOR UPDATE. Prevents other transactions from reading
   (with shared lock) or writing the locked rows until transaction commits.
   Use for: inventory deduction, balance transfers, seat booking.

Q24: What is PESSIMISTIC_READ?
A: Issues SELECT ... FOR SHARE. Allows other transactions to read (also acquire
   FOR SHARE) but blocks FOR UPDATE. Use when you want to prevent modifications
   while allowing concurrent reads.

Q25: How do you apply pessimistic lock in Spring Data JPA?
A: @Lock(LockModeType.PESSIMISTIC_WRITE) on a repository method:
   @Lock(LockModeType.PESSIMISTIC_WRITE)
   Optional<Account> findById(Long id);
   Spring Data appends FOR UPDATE to the generated SQL.

Q26: What is SKIP LOCKED and when do you use it?
A: jakarta.persistence.lock.timeout = -2 signals SKIP LOCKED (PostgreSQL/Oracle).
   SELECT ... FOR UPDATE SKIP LOCKED returns only rows not currently locked.
   Use for queue-like processing: multiple workers pick different rows from a
   queue table without blocking each other. Each worker gets its own batch of unlocked rows.

Q27: How do you prevent deadlocks with pessimistic locking?
A: (1) Always lock resources in the same ORDER across transactions.
   (2) Set a lock timeout: jakarta.persistence.lock.timeout=5000ms (don't wait forever).
   (3) Minimize time holding locks — do all locking at start, process quickly.
   (4) Use SKIP LOCKED for queue patterns to avoid contention.

TRANSACTION PITFALLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q28: What is self-invocation and why does it break @Transactional?
A: When a bean's method calls another method in the SAME class:
   this.saveInternal() — this refers to the real object, not the proxy.
   The proxy is bypassed → no transaction is started/joined.
   Fixes: (1) inject self as a Spring bean (@Autowired private MyService self);
   (2) move method to a different @Service; (3) use TransactionTemplate explicitly.

Q29: Why is @Transactional on a private method ignored?
A: Spring AOP proxies (JDK dynamic proxy or CGLIB) cannot intercept private methods.
   Spring does not wrap private methods in transactional advice. The annotation
   is silently ignored. Always put @Transactional on public methods.

Q30: What is the "swallowed exception" pitfall?
A: Catching an exception inside a @Transactional method prevents it from propagating
   to the AOP proxy. The proxy sees no exception → commits the transaction even
   though an error occurred. Fix: either rethrow, or call TransactionAspectSupport
   .currentTransactionStatus().setRollbackOnly() if you need to handle the exception.

Q31: What is the "long transaction" anti-pattern?
A: Keeping a transaction open while calling external services (HTTP calls, file I/O):
   (1) DB connection held for entire duration — connection pool starvation.
   (2) Locks held longer — more contention.
   Fix: do external calls BEFORE opening the transaction; open transaction only
   for the DB operations.

Q32: What happens if @Transactional(readOnly=true) performs a write?
A: Depends on DB. PostgreSQL with read replica: routing sends to replica → write fails.
   On primary: the JDBC driver may raise an error depending on DB configuration.
   Hibernate itself does not prevent writes on readOnly=true — it only skips dirty
   checking. The isolation happens at the connection/DataSource routing level.

Q33: Why is @Transactional on a @RestController a bad practice?
A: Controller handles HTTP concerns (serialization, status codes). Mixing with
   transaction boundary couples HTTP request lifetime to DB transaction.
   Lazy loading during Jackson serialization fires queries inside the transaction.
   Better: @Transactional on @Service; controller only orchestrates calls.

DIRTY CHECKING AND FLUSH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q34: What is dirty checking and how does it work?
A: Hibernate stores a hydrated snapshot (original column values) when an entity
   is loaded. On flush: compares snapshot to current values field-by-field.
   Changed fields → auto-generated UPDATE. No explicit save() call needed.

Q35: What can accidentally trigger an UPDATE?
A: (1) Modifying an entity field inside @Transactional without intending to persist.
   (2) Calling a setter in a @Transactional read method.
   (3) Cascading — parent save cascades to associated entities that are modified.
   Fix: use DTO projections for reads; use @Immutable for truly read-only entities.

Q36: What is FlushMode and when would you change it?
A: AUTO (default): flush before queries that might be affected by pending changes.
   COMMIT: flush only on commit (risky — queries may see stale state).
   MANUAL: never auto-flush.
   Change to COMMIT for batch read loops to prevent unnecessary flushes
   before each query.

SCENARIO QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q37: A checked exception is thrown in a @Transactional method. The transaction
     commits. Why? How do you fix it?
A: Spring only rolls back for unchecked exceptions by default. A checked exception
   propagates past the AOP advice, which then COMMITS.
   Fix: @Transactional(rollbackFor = Exception.class) — rolls back for any Throwable.
   Or throw a RuntimeException wrapper.

Q38: REQUIRES_NEW in an audit service causes a deadlock. Explain and fix.
A: REQUIRES_NEW starts a second transaction while the first is still active.
   Both hold locks on overlapping rows → deadlock.
   Fix: (1) Order locks consistently across transactions.
   (2) Save audit asynchronously (@Async) after the outer transaction commits.
   (3) Publish an event (Spring ApplicationEvent) with @TransactionalEventListener
   (AFTER_COMMIT) — audit saves only after the main transaction succeeds.

Q39: You need a method to run in its own transaction, independent of the caller.
     Which propagation do you use?
A: REQUIRES_NEW — suspends caller's transaction, starts fresh, commits/rolls back
   independently.
   Warning: ensure no shared row locks between the two transactions.

Q40: An operation must roll back a sub-step but keep the outer transaction.
     How?
A: Use NESTED propagation (savepoint-based). The inner method's rollback only
   undoes work since the savepoint. The outer transaction continues.
   Alternatively: catch the exception from the inner call, handle it,
   and continue outer transaction (but don't let the exception propagate
   to the AOP proxy).

Q41: How do you implement optimistic locking in a REST API where the user
     edits a form for several minutes?
A: Include the version field in the response payload. On save, send version back.
   Service checks: if (request.version != entity.version) throw ConflictException(409).
   Or use @Version and let OptimisticLockException surface as 409 Conflict.
   This is the "offline optimistic lock" / HTTP ETag pattern.

Q42: Two processes both query inventory count (50) and both try to decrement by 30.
     Both succeed, leaving -10. What went wrong and how do you fix it?
A: Lost update — both read 50, both write 20, second write overwrites first.
   Fix A: @Version optimistic locking — second update throws OptimisticLockException.
   Fix B: PESSIMISTIC_WRITE — SELECT FOR UPDATE blocks the second read until
   the first transaction commits.
   Fix C: Bulk UPDATE: UPDATE inventory SET qty = qty - 30 WHERE id=? AND qty >= 30
   — DB-level atomic decrement, check rows_affected.

Q43: What is @TransactionalEventListener and how does it improve reliability?
A: Spring application event listener that fires AFTER the transaction commits
   (AFTER_COMMIT phase by default). Use for: sending email after user save,
   publishing to Kafka after order save, triggering async audit.
   Ensures the event fires only when the DB change is durable — not if the
   transaction rolls back.

Q44: Can you rollback in a @Transactional(readOnly=true) method?
A: Yes — readOnly=true doesn't prevent rollback. It's a hint for:
   dirty checking skip, read-replica routing. If a RuntimeException is thrown,
   the transaction still rolls back (though it was a read-only tx, so rollback
   is a no-op for data). readOnly=true is a performance hint, not a constraint.

Q45: What is programmatic transaction management and when do you use it?
A: TransactionTemplate or PlatformTransactionManager for fine-grained control:
   transactionTemplate.execute(status -> {
     // some work
     if (error) status.setRollbackOnly();
     return result;
   });
   Use when: (1) @Transactional annotation approach doesn't work (self-invocation,
   lambda inside loop); (2) you need to commit partway through a loop;
   (3) you need conditional rollback without exceptions.
