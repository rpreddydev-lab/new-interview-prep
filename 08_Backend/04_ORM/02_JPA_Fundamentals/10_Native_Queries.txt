1. WHEN TO USE NATIVE QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use native queries when:
  ✓ Complex SQL that JPQL can't express (CTEs, window functions, PIVOT)
  ✓ DB-specific features (PostgreSQL JSONB, MySQL FULLTEXT, Oracle CONNECT BY)
  ✓ Performance-critical aggregations or joins
  ✓ Bulk operations that bypass entity management

2. NATIVE QUERIES VIA ENTITYMANAGER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Returns List<Object[]> — each Object[] is one row
List<Object[]> rows = em.createNativeQuery(
    "SELECT id, email, first_name FROM users WHERE active = 1"
).getResultList();
for (Object[] row : rows) {
    Long id = ((Number) row[0]).longValue();
    String email = (String) row[1];
    String firstName = (String) row[2];
}

// Map to entity class (columns must match @Column names)
List<User> users = em.createNativeQuery(
    "SELECT * FROM users WHERE active = 1", User.class
).getResultList();

// With parameters (ALWAYS use ?1 or :name — NEVER string concat!)
List<User> result = em.createNativeQuery(
    "SELECT * FROM users WHERE email = :email AND active = :active",
    User.class
).setParameter("email", email)
 .setParameter("active", true)
 .getResultList();

// Single result
User user = (User) em.createNativeQuery(
    "SELECT * FROM users WHERE id = ?1", User.class
).setParameter(1, id).getSingleResult();

3. NATIVE QUERIES IN SPRING DATA JPA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Repository
public interface UserRepository extends JpaRepository<User, Long> {

    // Simple native query mapping to entity
    @Query(value = "SELECT * FROM users WHERE active = 1",
           nativeQuery = true)
    List<User> findActiveUsers();

    // With parameters
    @Query(value = "SELECT * FROM users WHERE email = :email",
           nativeQuery = true)
    Optional<User> findByEmailNative(@Param("email") String email);

    // Native query returning DTO via projection interface
    @Query(value = """
        SELECT u.id, u.email, COUNT(o.id) as order_count
        FROM users u
        LEFT JOIN orders o ON o.user_id = u.id
        GROUP BY u.id, u.email
        """, nativeQuery = true)
    List<UserOrderStats> getUserOrderStats();

    // Bulk DML (UPDATE / DELETE)
    @Modifying
    @Transactional
    @Query(value = "UPDATE users SET active = 0 WHERE last_login < :date",
           nativeQuery = true)
    int deactivateOldUsers(@Param("date") LocalDate date);

    // Native query with pagination (REQUIRES countQuery!)
    @Query(
        value = "SELECT * FROM users WHERE department = :dept ORDER BY last_name",
        countQuery = "SELECT COUNT(*) FROM users WHERE department = :dept",
        nativeQuery = true
    )
    Page<User> findByDepartment(@Param("dept") String dept, Pageable pageable);
}

4. DTO PROJECTIONS WITH NATIVE QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Method 1: Interface-based projection (Spring Data)
  // Column aliases in SQL must match getter names (case-insensitive)
  public interface UserOrderStats {
      Long getId();
      String getEmail();
      Long getOrderCount();    // maps to alias "order_count"
  }

  @Query(value = """
      SELECT u.id        as id,
             u.email     as email,
             COUNT(o.id) as order_count
      FROM users u LEFT JOIN orders o ON o.user_id = u.id
      GROUP BY u.id, u.email
      """, nativeQuery = true)
  List<UserOrderStats> getUserOrderStats();

Method 2: Class-based DTO with @SqlResultSetMapping
  @SqlResultSetMapping(
      name = "UserOrderStatsMapping",
      classes = @ConstructorResult(
          targetClass = UserOrderStatsDto.class,
          columns = {
              @ColumnResult(name = "id", type = Long.class),
              @ColumnResult(name = "email"),
              @ColumnResult(name = "order_count", type = Long.class)
          }
      )
  )
  @NamedNativeQuery(
      name = "User.orderStats",
      query = "SELECT u.id, u.email, COUNT(o.id) as order_count " +
              "FROM users u LEFT JOIN orders o ON o.user_id = u.id " +
              "GROUP BY u.id, u.email",
      resultSetMapping = "UserOrderStatsMapping"
  )
  @Entity
  public class User { ... }

  // Execution:
  List<UserOrderStatsDto> stats =
      em.createNamedQuery("User.orderStats", UserOrderStatsDto.class)
        .getResultList();

5. ADVANCED SQL FEATURES WITH NATIVE QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Window functions (PostgreSQL):
  @Query(value = """
      SELECT
          u.id,
          u.email,
          SUM(o.total) OVER (PARTITION BY u.id) as user_total,
          RANK() OVER (ORDER BY SUM(o.total) DESC) as rank
      FROM users u
      JOIN orders o ON o.user_id = u.id
      """, nativeQuery = true)
  List<UserRankDto> getUserRanking();

CTE (Common Table Expression):
  @Query(value = """
      WITH monthly_totals AS (
          SELECT user_id, SUM(total) as monthly_total
          FROM orders
          WHERE MONTH(created_at) = :month
          GROUP BY user_id
      )
      SELECT u.*, mt.monthly_total
      FROM users u
      JOIN monthly_totals mt ON mt.user_id = u.id
      ORDER BY mt.monthly_total DESC
      """, nativeQuery = true)
  List<Object[]> getUsersWithMonthlyTotal(@Param("month") int month);

PostgreSQL JSONB query:
  @Query(value = "SELECT * FROM users WHERE preferences->>'theme' = :theme",
         nativeQuery = true)
  List<User> findByThemePreference(@Param("theme") String theme);

6. IMPORTANT CAVEATS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. SQL Injection:
   NEVER concatenate user input into native queries!
   Always use named parameters: WHERE email = :email
   Or positional: WHERE email = ?1

2. Persistence Context Not Updated by Bulk Native DML:
   After a native UPDATE/DELETE, call em.clear() or
   add @Modifying(clearAutomatically = true) in Spring Data JPA:
   @Modifying(clearAutomatically = true, flushAutomatically = true)

3. Database Portability Lost:
   Native queries are DB-specific. If you switch DBs, you must
   rewrite native queries. Use JPQL for DB-agnostic queries.

4. Pagination with Native Queries Requires countQuery:
   Spring Data JPA cannot auto-generate a count query for native SQL.
   You MUST provide countQuery explicitly with @Query.

5. Hibernate's Flush Before Native Queries:
   Unlike JPQL, Hibernate does NOT auto-flush dirty entities before
   native SQL queries. Use @Modifying(flushAutomatically = true) or
   call em.flush() manually before native queries if needed.

7. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you run a native SQL query in JPA?
A: Via em.createNativeQuery(sql, resultClass) or @Query(nativeQuery=true)
   in Spring Data JPA. Always use named/positional parameters.

Q: What happens after a native bulk UPDATE in JPA?
A: The DB is updated, but the persistence context (1st-level cache) still
   holds old entity state. You must call em.clear() or use
   @Modifying(clearAutomatically = true) to evict stale entities.

Q: How do you paginate native queries in Spring Data JPA?
A: Provide both value (the actual query) and countQuery (the count query)
   in @Query, because Spring cannot auto-generate count from native SQL:
   @Query(value="...", countQuery="SELECT COUNT(*) ...", nativeQuery=true)

Q: What is an interface-based projection with native queries?
A: Declare a projection interface with getter methods whose names match
   the SQL alias names in the native query. Spring Data creates a dynamic
   proxy implementation at runtime. Column aliases must match exactly.
