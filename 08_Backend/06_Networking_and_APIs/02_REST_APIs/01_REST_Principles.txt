================================================================================
REST PRINCIPLES — IN DEPTH
================================================================================

WHAT IS REST?
--------------
REST (Representational State Transfer) is an architectural style for distributed
hypermedia systems, introduced by Roy Fielding in his 2000 PhD dissertation.

REST is NOT a protocol or a standard — it is a set of architectural constraints.
An API that follows REST constraints is called "RESTful."

================================================================================
1. THE 6 REST CONSTRAINTS
================================================================================

CONSTRAINT 1: CLIENT-SERVER
  - Separation of concerns between UI/client and data storage/server
  - Client and server evolve independently
  - Server is not concerned with UI; client is not concerned with data storage
  BENEFIT: Portability of UI, scalability of server components

CONSTRAINT 2: STATELESSNESS
  - Each request from client to server must contain ALL information needed
  - Server stores NO client session state between requests
  - Any session state is kept entirely on the client side
  BENEFIT: Visibility, reliability, scalability (any server can handle any request)
  IMPLICATION: Use tokens (JWT) or cookies rather than server-side sessions
  CAVEAT: Database state is not "session state" — server CAN store persistent data

CONSTRAINT 3: CACHEABILITY
  - Responses must define whether they are cacheable or non-cacheable
  - Clients and intermediaries can cache cacheable responses
  BENEFIT: Reduces server load, improves performance
  HOW: HTTP Cache-Control, ETag, Last-Modified headers

CONSTRAINT 4: UNIFORM INTERFACE
  The single most important constraint; distinguishes REST from other styles.
  Has 4 sub-constraints:
  
  4a. IDENTIFICATION OF RESOURCES
      Resources are identified by URIs (e.g., /users/42)
      The resource and its representation are separate concepts
      Server can return JSON, XML, HTML for same resource URI
      
  4b. MANIPULATION OF RESOURCES THROUGH REPRESENTATIONS
      Client holds representation (e.g., JSON) + enough metadata to modify/delete
      Sending a representation back to server modifies the resource
      
  4c. SELF-DESCRIPTIVE MESSAGES
      Each message contains enough info to describe how to process it
      Content-Type header describes the media type
      Methods describe the action (GET, POST, etc.)
      
  4d. HATEOAS (Hypermedia as the Engine of Application State)
      Responses include links to related actions/resources
      Client discovers available operations from hypermedia
      (Rarely implemented fully in practice)

CONSTRAINT 5: LAYERED SYSTEM
  - Client cannot tell if it's connected directly to server or intermediary
  - Intermediaries: load balancers, caches, gateways, proxies
  BENEFIT: Encapsulation, scalability, security (can add layers without client change)

CONSTRAINT 6: CODE ON DEMAND (Optional)
  - Server can send executable code to client (JavaScript)
  - Extends client functionality without pre-deployment
  EXAMPLE: Browser downloads and executes JavaScript
  This is the only optional constraint

2. RESOURCES — THE CORE CONCEPT
================================================================================

WHAT IS A RESOURCE?
  Any information that can be named: a document, an image, a collection,
  a service, a person, an order, a concept.

RESOURCE vs REPRESENTATION
  Resource: Conceptual entity (User with id=42)
  Representation: State of that resource at a point in time (JSON/XML/HTML)
  Same resource → different representations based on Accept header

RESOURCE NAMING CONVENTIONS:
  ✅ Use NOUNS (not verbs) — resources are things, not actions
  ✅ Use plural nouns for collections
  ✅ Use lowercase with hyphens for readability
  ✅ Use hierarchy to show relationships
  ❌ Avoid verbs in URIs

  GOOD EXAMPLES:
    GET    /users              → list all users
    POST   /users              → create a user
    GET    /users/42           → get user 42
    PUT    /users/42           → replace user 42
    PATCH  /users/42           → partial update user 42
    DELETE /users/42           → delete user 42
    GET    /users/42/orders    → get orders belonging to user 42
    GET    /orders/99/items    → get items in order 99

  BAD EXAMPLES:
    POST /createUser           ❌ (verb in URI)
    GET  /getUserById?id=42    ❌ (RPC style, verb, query param for ID)
    POST /deleteUser/42        ❌ (wrong method + verb)
    GET  /user                 ❌ (singular for collection)

RESOURCE IDENTIFICATION IN URI:
  /users/{id}           → path variable for specific resource
  /users?role=admin     → query parameter for filtering collection
  /users/42/activate    → exception: actions on resource (use sparingly)
  /search?q=alice       → search as a resource (acceptable)

3. REST vs OTHER ARCHITECTURAL STYLES
================================================================================

REST vs RPC (Remote Procedure Call)
  REST: Resources and uniform interface; noun-centric
  RPC: Action-centric (invoking procedures); e.g., /getUserById, /sendEmail
  gRPC: Modern RPC using Protocol Buffers; better performance for internal services

REST vs GraphQL
  REST:    Multiple endpoints per resource; over/under fetching common
  GraphQL: Single endpoint; client specifies exact fields needed; flexible queries
  REST wins: Caching (per URL), simplicity, HTTP-native semantics
  GraphQL wins: Complex data requirements, mobile clients, rapid UI iteration

REST vs SOAP
  REST:    Lightweight, JSON/XML, HTTP verbs, no strict standard
  SOAP:    XML-only, strict WSDL contract, built-in WS-Security, WS-ReliableMessaging
  REST wins: Simplicity, developer experience, tooling
  SOAP wins: Enterprise security requirements, transactional guarantees

REST vs WebSockets
  REST:      Request-response, stateless, cacheable; good for CRUD
  WebSocket: Persistent bidirectional connection; good for real-time (chat, live data)
  Use REST for standard API operations; WebSocket for real-time event streaming.

4. STATELESSNESS IN DEPTH
================================================================================

WHAT STATELESSNESS MEANS:
  Server processes each request independently.
  No HTTP session with server-side session objects.
  Each request carries all authentication info (token, API key).

BENEFITS OF STATELESSNESS:
  - Horizontal scaling: any server instance handles any request
  - Reliability: server crash doesn't lose session state
  - Simplicity: no session synchronization between instances
  - Cacheability: requests can be cached (stateful requests can't)

AUTHENTICATION WITHOUT SERVER-SIDE STATE:
  JWT (JSON Web Token): Token contains claims; server validates signature
  API Keys: Sent in header; server validates against database/cache
  OAuth2 Bearer Token: Validated via introspection or JWT signature

IF YOU NEED SESSION-LIKE STATE:
  Store in client (JWT payload, cookies)
  Store in distributed cache (Redis) — still considered stateless from server's PoV
  Database persistence

5. RICHARDSON MATURITY MODEL (PREVIEW)
================================================================================

Level 0: HTTP as transport (SOAP, XML-RPC) — single endpoint, one method
Level 1: Resources — individual URIs per resource
Level 2: HTTP Verbs — proper use of GET, POST, PUT, DELETE, status codes
Level 3: Hypermedia (HATEOAS) — responses include links to next actions

Most "RESTful" APIs in practice are at Level 2.
Level 3 is theoretically correct REST but rarely implemented.
(Detailed in 01_Richardson_Maturity_Model.txt)

6. REAL-WORLD REST API DESIGN DECISIONS
================================================================================

QUESTION: Should I nest resources deeply?
  GET /companies/1/departments/5/employees/42  ← Too deep, hard to use
  GET /employees/42                            ← Better; use query params for filter
  GET /employees?companyId=1&departmentId=5    ← Clear and flexible
  Rule: Maximum 2 levels of nesting is a good guideline.

QUESTION: How to handle actions that don't map to CRUD?
  Option 1: Model as resource:  POST /payments (creates payment = triggers charge)
  Option 2: Sub-resource:       PUT /orders/42/status  { "status": "shipped" }
  Option 3: RPC-style endpoint: POST /orders/42/cancel  (acceptable for complex actions)
  Option 4: Use PATCH:          PATCH /orders/42  { "status": "cancelled" }

QUESTION: What about versioning?
  /v1/users, /v2/users           → URL versioning (easy, explicit)
  Accept: application/vnd.api+json;version=2  → Header versioning
  (Detailed in 02_API_Design/00_API_Versioning.txt)

7. INTERVIEW QUESTIONS — REST PRINCIPLES
================================================================================

Q1: What are the 6 constraints of REST?
    Client-Server, Stateless, Cacheable, Uniform Interface, Layered System,
    Code on Demand (optional). The Uniform Interface is the most distinctive,
    with sub-constraints: resource identification by URI, manipulation through
    representations, self-descriptive messages, and HATEOAS.

Q2: What does statelessness mean? How do you handle authentication?
    Server stores no client session state between requests. Each request must
    contain all necessary information. Authentication via JWT (self-contained
    token) or Bearer token validated per-request via introspection or
    shared secret verification.

Q3: What is the difference between REST and RPC?
    REST is resource-centric using URIs as nouns and HTTP methods as verbs.
    RPC (gRPC, XML-RPC) is action-centric — you call remote procedures.
    REST leverages HTTP semantics (caching, status codes, content negotiation).
    gRPC uses Protocol Buffers and is more efficient for internal microservice
    communication where HTTP semantics aren't as important.

Q4: Is a stateless API always better?
    For public/web APIs: yes — enables horizontal scaling, simplicity.
    Trade-off: Client must send auth info on every request (overhead).
    Some operations are inherently stateful (multi-step wizards, long transactions)
    — handled via resources that track state (e.g., checkout sessions).

Q5: What's wrong with using GET to delete a resource?
    GET is safe (no side effects) and idempotent. Using GET for mutations breaks
    these guarantees. Browsers prefetch GET links. Crawlers follow GET links.
    Security scanners call all GET endpoints. Use DELETE for deletion.
