================================================================================
PROXY AND REVERSE PROXY — IN DEPTH
================================================================================

WHAT IS A PROXY?
-----------------
A proxy server is an intermediary that sits between a client and a server,
forwarding requests and responses. There are two fundamentally different types:

  Forward Proxy: intermediary for clients (sits on client side)
  Reverse Proxy: intermediary for servers (sits on server side)

The direction of "who the proxy represents" is the key distinction.

================================================================================
1. FORWARD PROXY
================================================================================

A forward proxy represents clients — the server doesn't know the real client.

  [Client] ──→ [Forward Proxy] ──→ [Server/Internet]
  
  Server sees the proxy's IP, not the client's IP.

USE CASES:
  - Corporate firewall: all outbound traffic routed through proxy for filtering
  - Anonymity / VPN: hide client IP from destination servers
  - Content filtering: block specific sites
  - Caching: cache responses for multiple clients (Squid proxy)
  - Access control: employees can only reach approved sites

TRANSPARENT PROXY:
  Client doesn't know a proxy exists — traffic silently intercepted.
  Often used by ISPs or corporate networks.

CONNECT TUNNEL (HTTPS Proxying):
  For HTTPS, the proxy can't decrypt traffic — it creates a TCP tunnel.
  
  Client sends:  CONNECT api.example.com:443 HTTP/1.1
  Proxy replies: HTTP/1.1 200 Connection Established
  Now client and server communicate through the tunnel; proxy is a blind pipe.

CONFIGURING FORWARD PROXY IN JAVA:
  // System properties
  System.setProperty("https.proxyHost", "proxy.corp.com");
  System.setProperty("https.proxyPort", "8080");
  System.setProperty("https.nonProxyHosts", "localhost|*.internal.com");
  
  // WebClient with explicit proxy
  HttpClient httpClient = HttpClient.create()
      .proxy(proxy ->
          proxy.type(ProxyProvider.Proxy.HTTP)
               .host("proxy.corp.com")
               .port(8080)
               .username("user")
               .password(s -> "password")
               .nonProxyHosts("localhost|*.internal.com")
      );
  
  WebClient webClient = WebClient.builder()
      .clientConnector(new ReactorClientHttpConnector(httpClient))
      .build();

2. REVERSE PROXY
================================================================================

A reverse proxy represents servers — the client doesn't know the real server.

  [Client] ──→ [Reverse Proxy] ──→ [Server1]
                                ──→ [Server2]
                                ──→ [Server3]
  
  Client sees only the proxy's address; server sees proxy's IP.

USE CASES:
  - Load balancing: distribute requests across server instances
  - SSL termination: handle TLS at proxy; plain HTTP to backends
  - Caching: cache responses to reduce backend load
  - Compression: gzip/brotli compression at proxy layer
  - Static file serving: serve static assets; forward API requests to app
  - Authentication: validate tokens before passing to backend
  - DDoS protection: absorb and filter malicious traffic
  - Rate limiting: enforce per-client limits at proxy level
  - Canary deployments: route % of traffic to new version

COMMON REVERSE PROXIES:
  Nginx      - most popular; high performance; event-driven
  Apache     - flexible; module-based
  HAProxy    - specialized for L4/L7 load balancing
  Traefik    - cloud-native; auto-discovers services in Docker/K8s
  Envoy      - CNCF; used in Istio service mesh; L7 proxy
  AWS ALB    - Application Load Balancer (managed reverse proxy)

3. NGINX AS REVERSE PROXY
================================================================================

BASIC REVERSE PROXY CONFIG:
  # /etc/nginx/sites-available/myapp
  upstream app_servers {
      least_conn;  # or: round_robin (default), ip_hash, weight
      server app1:8080 weight=3;
      server app2:8080 weight=1;
      server app3:8080 backup;      # only used if others fail
      
      keepalive 32;  # keep connections to backends alive
  }
  
  server {
      listen 80;
      listen 443 ssl http2;
      server_name api.example.com;
      
      # SSL configuration
      ssl_certificate     /etc/ssl/certs/example.crt;
      ssl_certificate_key /etc/ssl/private/example.key;
      ssl_protocols       TLSv1.2 TLSv1.3;
      ssl_ciphers         HIGH:!aNULL:!MD5;
      
      # Redirect HTTP to HTTPS
      if ($scheme != "https") {
          return 301 https://$host$request_uri;
      }
      
      location /api/ {
          proxy_pass         http://app_servers;
          proxy_http_version 1.1;
          proxy_set_header   Connection "";          # enable keepalive
          
          # Pass real client info to backend
          proxy_set_header   Host              $host;
          proxy_set_header   X-Real-IP         $remote_addr;
          proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
          proxy_set_header   X-Forwarded-Proto $scheme;
          proxy_set_header   X-Forwarded-Port  $server_port;
          
          # Timeouts
          proxy_connect_timeout  5s;
          proxy_send_timeout     30s;
          proxy_read_timeout     30s;
          
          # Buffering
          proxy_buffering    on;
          proxy_buffer_size  4k;
          proxy_buffers      4 32k;
      }
      
      # Serve static files directly (no backend needed)
      location /static/ {
          root /var/www/;
          expires 1y;
          add_header Cache-Control public;
          gzip_static on;
      }
  }

LOAD BALANCING ALGORITHMS:
  round_robin    : Default; requests distributed equally
  least_conn     : Route to server with fewest active connections
  ip_hash        : Same client IP always goes to same server (sticky sessions)
  hash $variable : Hash-based routing on custom variable
  random         : Random selection with optional least_conn parameter

4. IMPORTANT PROXY HEADERS
================================================================================

X-Forwarded-For:
  Contains the original client IP (and chain of proxies).
  Format: X-Forwarded-For: client, proxy1, proxy2
  First value is original client (if proxy chain is trustworthy).

X-Real-IP:
  Nginx-specific header containing the direct client IP.
  Easier to parse than X-Forwarded-For.

X-Forwarded-Proto:
  Original scheme (http or https) — important because backend may receive
  plain HTTP from proxy even though client used HTTPS.
  Use this to determine if request was originally secure.

X-Forwarded-Port:
  Original port used by the client.

Forwarded (RFC 7239 standard header):
  Standardized replacement for X-Forwarded-* headers:
  Forwarded: for=192.0.2.1;proto=https;host=api.example.com

SPRING BOOT: TRUST PROXY HEADERS:
  # application.yml
  server:
    tomcat:
      remote-ip-header: X-Real-IP        # or X-Forwarded-For
      protocol-header: X-Forwarded-Proto
      internal-proxies: "10\\.\\d{1,3}\\.\\d{1,3}\\.\\d{1,3}|192\\.168\\.\\d{1,3}\\.\\d{1,3}"
      # Only trust X-Forwarded-* from these IP ranges
  
  # Or programmatically (Spring Boot 3):
  @Bean
  public FilterRegistrationBean<ForwardedHeaderFilter> forwardedHeaderFilter() {
      FilterRegistrationBean<ForwardedHeaderFilter> bean = new FilterRegistrationBean<>();
      bean.setFilter(new ForwardedHeaderFilter());
      bean.setOrder(Ordered.HIGHEST_PRECEDENCE);
      return bean;
  }
  
  // Now request.getRemoteAddr() returns real client IP
  // request.getScheme() returns "https" if X-Forwarded-Proto: https

5. SSL TERMINATION AT PROXY
================================================================================

SSL termination: TLS is terminated at the reverse proxy; traffic to backends
is plain HTTP (inside trusted network) or TLS again (re-encryption).

Benefits of SSL termination:
  - Backend servers don't need TLS certificates or TLS processing overhead
  - Single certificate management point
  - Load balancer can inspect/modify HTTP headers (can't with TLS passthrough)

TLS passthrough (alternative):
  Proxy forwards encrypted TCP stream directly to backend.
  Backend terminates TLS; load balancer cannot see HTTP.
  Use SNI routing: proxy routes based on hostname in TLS handshake.

Backend re-encryption:
  Proxy terminates TLS → new TLS connection to backend.
  Used in high-security environments; end-to-end encryption.

6. PROXY IN MICROSERVICES (SERVICE MESH)
================================================================================

Sidecar Proxy (Envoy):
  Each microservice gets a sidecar Envoy proxy deployed in the same pod.
  All traffic (inbound and outbound) flows through the sidecar.
  
  [Service A] ←→ [Envoy Sidecar A] ──→ [Envoy Sidecar B] ←→ [Service B]
  
  The control plane (Istio, Linkerd) configures all sidecars centrally.
  Features: mTLS between all services, tracing, traffic splitting, retries,
            circuit breaking — all without application code changes.

Service Mesh benefits:
  - Mutual TLS everywhere (zero-trust networking)
  - Observability: distributed tracing, metrics for all service calls
  - Traffic management: canary deployments, A/B testing at proxy level
  - Resilience: circuit breaking, retries configured centrally

7. INTERVIEW QUESTIONS — PROXY AND REVERSE PROXY
================================================================================

Q1: What is the difference between a forward proxy and a reverse proxy?
    A forward proxy represents clients — it intercepts outbound client requests
    and forwards them to the internet. The destination server sees the proxy's IP,
    not the client's. Used for corporate filtering, caching, anonymization.
    A reverse proxy represents servers — it receives inbound requests from the
    internet and forwards them to backend servers. The client sees only the proxy.
    Used for load balancing, SSL termination, caching, security. The mnemonic:
    forward proxy is "client-side"; reverse proxy is "server-side".

Q2: How does Nginx know the real client IP when acting as a reverse proxy?
    Nginx sets X-Real-IP and X-Forwarded-For headers before forwarding to
    backends. X-Forwarded-For contains: "client, proxy1, proxy2" — each proxy
    appends the previous node's IP. The backend reads X-Real-IP for a clean
    single IP, or parses the first value of X-Forwarded-For. In Spring Boot,
    configure server.tomcat.remote-ip-header=X-Real-IP and Spring's
    ForwardedHeaderFilter, so request.getRemoteAddr() returns the real client
    IP rather than the proxy's IP. Always validate that proxy headers only come
    from trusted proxy IPs to prevent IP spoofing.

Q3: What is SSL termination and why is it common at the proxy layer?
    SSL termination means the TLS connection ends at the reverse proxy — the
    proxy decrypts the request and forwards it to backends as plain HTTP (inside
    the private network). It's common because: (1) only one server needs
    certificates, simplifying cert management, (2) TLS handshakes are
    computationally expensive — terminating at one high-performance proxy is
    more efficient than every backend doing TLS, (3) the proxy can inspect and
    modify HTTP headers (impossible with end-to-end TLS). The assumption is that
    the internal network between proxy and backends is trusted.

Q4: What is a service mesh and how is it different from a traditional reverse proxy?
    A traditional reverse proxy (like Nginx) is a centralized component — all
    traffic flows through one server. A service mesh deploys sidecar proxies
    (like Envoy) alongside every microservice instance. Traffic between any
    two services flows through their respective sidecars. The control plane
    (Istio) configures all sidecars uniformly. This gives you mutual TLS between
    all services, per-service observability, and fine-grained traffic control
    without modifying any application code. The tradeoff: operational complexity
    (running proxy in every pod, control plane overhead).

Q5: What is the X-Forwarded-For header and how do you prevent spoofing?
    X-Forwarded-For contains the client IP chain: each proxy prepends the IP
    of the connection it received from. Example: if client 1.2.3.4 goes through
    proxy 10.0.0.1 to reach your server, the header is "1.2.3.4, 10.0.0.1".
    Spoofing risk: a malicious client can send "X-Forwarded-For: 127.0.0.1" to
    appear as localhost and bypass IP-based restrictions. Defense: only trust
    X-Forwarded-For from known proxy IPs (configure internal-proxies in Tomcat).
    Take the leftmost "unforged" IP — the IP added by your trusted edge proxy,
    not the entire chain provided by the client. Or use Nginx's $remote_addr
    to set X-Real-IP (which clients cannot spoof since Nginx overwrites it).
