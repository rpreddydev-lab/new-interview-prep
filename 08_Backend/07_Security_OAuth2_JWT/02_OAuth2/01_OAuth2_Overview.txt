================================================================
OAUTH2 OVERVIEW
================================================================

WHAT IS OAUTH2?
----------------
OAuth 2.0 is an industry-standard AUTHORIZATION FRAMEWORK (RFC 6749).
It enables an application (client) to obtain limited access to a user's
resources on another service (resource server), WITHOUT exposing credentials.

Key Insight: OAuth2 delegates access — "I authorize App X to access
my Google Drive on my behalf" without giving App X my Google password.

OAuth2 is about DELEGATION and AUTHORIZATION, NOT authentication.
(OIDC is the authentication layer built on top of OAuth2.)

================================================================
THE PROBLEM OAUTH2 SOLVES
================================================================

BEFORE OAuth2 (credential sharing anti-pattern):
  1. You want app "PhotoPrint" to access your Google Photos
  2. PhotoPrint asks for your Google username/password
  3. PhotoPrint has full access to your Google account forever
  PROBLEMS:
    - PhotoPrint could do anything with your Google account
    - You can't revoke access without changing your password
    - If PhotoPrint is breached, your Google credentials are stolen

WITH OAuth2:
  1. PhotoPrint redirects you to Google's authorization page
  2. You log in to Google directly (PhotoPrint never sees your password)
  3. Google issues a token to PhotoPrint with LIMITED scope (read:photos)
  4. PhotoPrint uses the token to access only your photos
  5. You can revoke the token anytime without changing your password

================================================================
OAUTH2 ROLES
================================================================

ROLE               DESCRIPTION                           EXAMPLE
---------------------------------------------------------------------------
Resource Owner     The user who owns the data            You (end user)
Client             App requesting access                 PhotoPrint App
Authorization Server  Issues tokens after auth           Google OAuth Server
Resource Server    Hosts protected resources             Google Photos API

IMPORTANT DISTINCTION:
  Authorization Server = where tokens are issued (login + consent)
  Resource Server = where the API lives (validates tokens)
  In small systems these can be the same service.

================================================================
OAUTH2 TOKENS
================================================================

ACCESS TOKEN
  - Credential used to access protected resources
  - Short-lived (typically 15 min to 1 hour)
  - Sent in: Authorization: Bearer <token>
  - Can be JWT or opaque (random string)

REFRESH TOKEN
  - Long-lived credential to get new access tokens
  - Typically days to weeks lifetime
  - NOT sent to resource servers — only to authorization server
  - Should be securely stored (never in localStorage)

AUTHORIZATION CODE
  - Short-lived, single-use code
  - Returned to redirect_uri after user consents
  - Exchanged for tokens at the token endpoint
  - Valid for ~10 minutes

================================================================
OAUTH2 ENDPOINTS
================================================================

AUTHORIZATION ENDPOINT  : /oauth2/authorize
  - Client redirects user here to get authorization
  - User logs in and grants consent

TOKEN ENDPOINT          : /oauth2/token
  - Exchange authorization code / credentials for tokens
  - Backend-to-backend, POST request

INTROSPECTION ENDPOINT  : /oauth2/introspect
  - Check if a token is valid and get its metadata
  - Used by resource servers for opaque tokens

REVOCATION ENDPOINT     : /oauth2/revoke
  - Invalidate a token

JWKS ENDPOINT           : /.well-known/jwks.json
  - Public keys to verify JWT signatures

DISCOVERY ENDPOINT      : /.well-known/oauth-authorization-server
                    OR  : /.well-known/openid-configuration (OIDC)
  - Metadata about the server's capabilities and endpoints

================================================================
OAUTH2 GRANT TYPES (FLOWS)
================================================================

1. Authorization Code          → Web apps, most secure
2. Authorization Code + PKCE   → Mobile/SPA, modern standard
3. Client Credentials          → Machine-to-machine (no user)
4. Device Code                 → Devices without browsers (TV, CLI)
5. Implicit                    → DEPRECATED (tokens in URL — unsafe)
6. Resource Owner Password     → DEPRECATED (sends credentials to client)

CHOOSING THE RIGHT GRANT TYPE:
  Who is authenticating?   → Use this grant:
  ---------------------------------------------------
  User + Browser/Web App   → Authorization Code
  User + SPA/Mobile        → Authorization Code + PKCE
  Service/Background Job   → Client Credentials
  Smart TV / IoT Device    → Device Code
  NEVER use Implicit or ROPC for new applications

================================================================
OAUTH2 SCOPES
================================================================

Scopes define what the client is ALLOWED to do with the access token.
They represent permissions granted by the resource owner.

Examples:
  read:profile     → read user profile
  write:orders     → create/update orders
  admin:users      → manage users (highly privileged)
  openid           → required for OIDC (get ID token)
  email            → access user's email (OIDC scope)
  offline_access   → request a refresh token

SCOPE REQUEST:
  Client requests scopes during authorization.
  Resource owner approves (or the AS auto-approves based on policy).
  Access token contains only APPROVED scopes.

SCOPE VALIDATION IN RESOURCE SERVER:
  @PreAuthorize("hasAuthority('SCOPE_read:orders')")
  public List<Order> getOrders() { ... }

  // Spring auto-prefixes 'SCOPE_' to JWT scope claims

================================================================
OAUTH2 TOKEN TYPES
================================================================

JWT (JSON Web Token):
  - Self-contained (all info in the token)
  - Resource server validates locally (no AS call)
  - Can't be revoked until expiry (use short TTL)

Opaque Token:
  - Random string — no embedded data
  - Resource server must call AS introspection endpoint to validate
  - Can be revoked instantly
  - Hides token metadata from client

================================================================
OAUTH2 SECURITY CONSIDERATIONS
================================================================

  ✓ Always use PKCE for public clients (SPA, mobile)
  ✓ Validate redirect_uri strictly (prevent open redirectors)
  ✓ Use short-lived access tokens
  ✓ Rotate refresh tokens (refresh token rotation)
  ✓ Bind refresh tokens to client (detect theft)
  ✓ Use state parameter to prevent CSRF in authorization flow
  ✓ Use code_challenge for PKCE
  ✓ Never use implicit or ROPC grant for new apps
  ✓ Validate all token claims (iss, aud, exp, nbf)

OPEN REDIRECTOR ATTACK:
  If redirect_uri is not strictly validated:
  ?redirect_uri=https://evil.com  → attacker gets the authorization code

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What problem does OAuth2 solve?
A: It allows users to grant limited, revocable access to their resources on
   one service to another service, without sharing credentials. Replaces
   the dangerous anti-pattern of giving your password to third-party apps.

Q: What are the OAuth2 roles?
A: Resource Owner (user), Client (app requesting access), Authorization
   Server (issues tokens), Resource Server (holds protected resources).

Q: What is the difference between an access token and a refresh token?
A: Access token is short-lived and used to access APIs. Refresh token is
   long-lived and used ONLY to obtain new access tokens from the
   Authorization Server (not sent to resource servers).

Q: What grant type should you use for a SPA?
A: Authorization Code with PKCE. Never the old Implicit grant (deprecated).

Q: What is the difference between scopes in OAuth2 and roles?
A: Scopes are permissions granted to the CLIENT (what the app can do on
   behalf of the user). Roles are permissions of the USER themselves.
   Example: the app may have read:orders scope, but the user may have
   the ADMIN role allowing them to delete orders too.

Q: Is OAuth2 an authentication protocol?
A: No. OAuth2 is an AUTHORIZATION framework. It tells you what a client is
   ALLOWED to do, not who the user is. OpenID Connect (OIDC) is built on
   OAuth2 and adds identity/authentication via the ID Token.
