DEVICE AUTHORIZATION FLOW (RFC 8628)
=====================================

=== CONCEPT ===

OAuth 2.0 Device Authorization Grant (Device Flow) is designed for devices that:
  - Have limited input capability (no keyboard/browser)
  - Cannot run a browser directly

Use cases:
  - Smart TVs (e.g., "Sign in to Netflix on your TV")
  - CLI tools (e.g., GitHub CLI, AWS CLI)
  - IoT devices
  - Gaming consoles

=== FLOW STEPS ===

Step 1: Device requests authorization
  POST /oauth2/device_authorization
  Body: client_id=cli-app&scope=read:repos

  Response:
  {
    "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
    "user_code": "WDJB-MJHT",
    "verification_uri": "https://github.com/login/device",
    "verification_uri_complete": "https://github.com/login/device?user_code=WDJB-MJHT",
    "expires_in": 900,
    "interval": 5
  }

Step 2: Device shows user code to user
  "Visit https://github.com/login/device and enter: WDJB-MJHT"

Step 3: User goes to URL on their phone/laptop and enters code
  (Normal browser-based OAuth login happens on the secondary device)

Step 4: Device POLLS token endpoint
  POST /oauth2/token
  Body: grant_type=urn:ietf:params:oauth:grant-type:device_code
        &device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS
        &client_id=cli-app

  Responses while waiting:
    {"error": "authorization_pending"} → keep polling
    {"error": "slow_down"}             → increase polling interval by 5s
    {"error": "expired_token"}         → device_code expired, restart

  Success response (after user approves):
    {"access_token": "...", "token_type": "Bearer", "scope": "read:repos"}

Step 5: Device uses access token for API calls

=== COMPARISON WITH AUTHORIZATION CODE FLOW ===

Authorization Code:
  Device → redirect_uri → browser → auth server → callback to redirect_uri
  Requires: browser, redirect URI registration, port listening

Device Flow:
  Device → polling → auth server | User → separate browser
  Requires: polling only (no redirect URI needed for device)
  Perfect for: headless servers, IoT, CLI tools

=== POLLING BEST PRACTICES ===

- Poll at minimum interval specified in response (default 5s)
- Handle slow_down: increase interval by 5s on each slow_down response
- Handle expires_in: stop polling and inform user to restart
- Use exponential backoff strategy
- Show countdown timer to user: "Code expires in 14:32"

=== SECURITY CONSIDERATIONS ===

1. User code should be short and easy to type (WDJB-MJHT format)
2. Short expiry for device_code (usually 15 minutes)
3. One-time use: after approval, device_code is invalidated
4. Rate limiting on polling endpoint (slow_down response)
5. HTTPS required for all endpoints
6. Client authentication: public clients (no secret) or confidential clients

=== SPRING AUTHORIZATION SERVER ===

Spring Authorization Server supports Device Flow since 1.1:

@Configuration
public class AuthorizationServerConfig {

    @Bean
    public RegisteredClientRepository registeredClientRepository() {
        RegisteredClient deviceClient = RegisteredClient.withId(UUID.randomUUID().toString())
            .clientId("device-client")
            .clientAuthenticationMethod(ClientAuthenticationMethod.NONE) // public client
            .authorizationGrantType(AuthorizationGrantType.DEVICE_CODE)
            .authorizationGrantType(AuthorizationGrantType.REFRESH_TOKEN)
            .scope("read")
            .clientSettings(ClientSettings.builder()
                .requireProofKey(true)  // PKCE recommended
                .build())
            .build();
        return new InMemoryRegisteredClientRepository(deviceClient);
    }

    @Bean
    public AuthorizationServerSettings authorizationServerSettings() {
        return AuthorizationServerSettings.builder()
            .deviceAuthorizationEndpoint("/oauth2/device_authorization")
            .deviceVerificationEndpoint("/oauth2/device_verification")
            .build();
    }
}
