================================================================
CLIENT CREDENTIALS GRANT — Machine-to-Machine (M2M)
================================================================

WHAT IS CLIENT CREDENTIALS?
-----------------------------
The Client Credentials grant is designed for server-to-server communication
where there is NO user involved. The client (service) authenticates directly
with its own credentials to obtain an access token.

Use cases:
  - Microservice A calling Microservice B
  - Background jobs / scheduled tasks
  - Data pipelines
  - Internal automation scripts
  - API integrations (e.g., sending emails via SendGrid API)

================================================================
FLOW
================================================================

CLIENT (Service A)                     AUTHORIZATION SERVER
       |                                       |
       | POST /oauth2/token                    |
       | grant_type=client_credentials         |
       | client_id=service-a                   |
       | client_secret=my-secret               |
       | scope=read:orders                     |
       |-------------------------------------->|
       |                                       |
       | 200 OK                                |
       | {                                     |
       |   "access_token": "eyJ...",           |
       |   "token_type": "Bearer",             |
       |   "expires_in": 3600,                 |
       |   "scope": "read:orders"              |
       | }                                     |
       |<--------------------------------------|
       |                                       |
       | GET /api/orders                       |
       | Authorization: Bearer eyJ...          |
       |-------------------------------------->| RESOURCE SERVER
       |                                       |
       | 200 OK [orders data]                  |
       |<--------------------------------------|

KEY POINTS:
  - No user, no browser, no redirect
  - No refresh token (just re-authenticate when token expires)
  - Client authenticates with client_id + client_secret
  - Token contains client's identity (sub = client_id)

================================================================
TOKEN REQUEST DETAILS
================================================================

POST /oauth2/token HTTP/1.1
Host: auth-server.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(service-a:my-secret)    ← HTTP Basic auth

Body:
  grant_type=client_credentials
  &scope=read:orders%20write:reports

OR send credentials in body (less preferred):
  grant_type=client_credentials
  &client_id=service-a
  &client_secret=my-secret
  &scope=read:orders

RESPONSE:
{
  "access_token": "eyJhbGciOiJSUzI1NiJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:orders"
}

NOTE: No id_token (OIDC), no refresh_token in client credentials flow.

================================================================
JWT PAYLOAD FOR CLIENT CREDENTIALS TOKEN
================================================================

{
  "iss": "https://auth-server.com",
  "sub": "service-a",               ← client_id (not a user!)
  "aud": "https://api.app.com",
  "exp": 1713484800,
  "iat": 1713481200,
  "scope": "read:orders",
  "client_id": "service-a"
}

================================================================
SPRING SECURITY — CLIENT SIDE CONFIGURATION
================================================================

# application.yml
spring:
  security:
    oauth2:
      client:
        registration:
          order-service:
            client-id: inventory-service
            client-secret: ${CLIENT_SECRET}
            authorization-grant-type: client_credentials
            scope: read:inventory, write:stock
        provider:
          order-service:
            token-uri: https://auth-server.com/oauth2/token

// WebClient with automatic token management
@Configuration
public class WebClientConfig {

    @Bean
    public OAuth2AuthorizedClientManager authorizedClientManager(
            ClientRegistrationRepository clientRegistrationRepository,
            OAuth2AuthorizedClientRepository authorizedClientRepository) {

        OAuth2AuthorizedClientProvider provider =
            OAuth2AuthorizedClientProviderBuilder.builder()
                .clientCredentials()
                .build();

        DefaultOAuth2AuthorizedClientManager manager =
            new DefaultOAuth2AuthorizedClientManager(
                clientRegistrationRepository, authorizedClientRepository);
        manager.setAuthorizedClientProvider(provider);
        return manager;
    }

    @Bean
    public WebClient webClient(OAuth2AuthorizedClientManager clientManager) {
        ServletOAuth2AuthorizedClientExchangeFilterFunction oauth2 =
            new ServletOAuth2AuthorizedClientExchangeFilterFunction(clientManager);
        oauth2.setDefaultClientRegistrationId("order-service");
        return WebClient.builder()
            .baseUrl("https://api.inventory.com")
            .apply(oauth2.oauth2Configuration())
            .build();
    }
}

// Using the WebClient (token injected automatically)
@Service
public class InventoryClient {

    private final WebClient webClient;

    public InventoryClient(WebClient webClient) {
        this.webClient = webClient;
    }

    public Flux<Item> getItems() {
        return webClient.get()
            .uri("/items")
            .retrieve()
            .bodyToFlux(Item.class);
    }
}

================================================================
TOKEN CACHING — IMPORTANT PERFORMANCE CONCERN
================================================================

DO NOT request a new token for EVERY API call — it's wasteful!

Spring's OAuth2AuthorizedClientManager handles caching automatically:
  - Stores token in OAuth2AuthorizedClientRepository
  - Re-uses until near expiry
  - Automatically refreshes when expired

MANUAL TOKEN CACHING EXAMPLE:
@Service
public class TokenService {

    private final WebClient webClient;
    private String cachedToken;
    private Instant tokenExpiry;

    public String getToken() {
        if (cachedToken == null || Instant.now().isAfter(tokenExpiry.minusSeconds(60))) {
            // Request new token with 60-second buffer before expiry
            TokenResponse response = webClient.post()
                .uri("/oauth2/token")
                .bodyValue("grant_type=client_credentials&scope=read:orders")
                .retrieve()
                .bodyToMono(TokenResponse.class)
                .block();
            cachedToken = response.getAccessToken();
            tokenExpiry = Instant.now().plusSeconds(response.getExpiresIn());
        }
        return cachedToken;
    }
}

================================================================
SPRING AUTHORIZATION SERVER — REGISTERING A CLIENT
================================================================

@Bean
public RegisteredClientRepository registeredClientRepository() {
    RegisteredClient serviceA = RegisteredClient.withId(UUID.randomUUID().toString())
        .clientId("service-a")
        .clientSecret("{bcrypt}" + new BCryptPasswordEncoder().encode("my-secret"))
        .clientAuthenticationMethod(ClientAuthenticationMethod.CLIENT_SECRET_BASIC)
        .authorizationGrantType(AuthorizationGrantType.CLIENT_CREDENTIALS)
        .scope("read:orders")
        .scope("write:reports")
        .tokenSettings(TokenSettings.builder()
            .accessTokenTimeToLive(Duration.ofHours(1))
            .build())
        .build();

    return new InMemoryRegisteredClientRepository(serviceA);
}

================================================================
SECURITY CONSIDERATIONS
================================================================

1. PROTECT CLIENT SECRETS:
   ✓ Store in secrets manager (Vault, AWS Secrets Manager)
   ✓ Never hardcode in source code
   ✓ Rotate regularly
   ✓ Use different secrets per environment

2. SCOPE MINIMIZATION:
   ✓ Request ONLY the scopes needed
   ✓ Create separate clients for different service-pairs
   ✓ Audit scope usage regularly

3. CLIENT AUTHENTICATION METHODS:
   Method                     Security
   ------------------------------------------------------------------
   client_secret_basic        Good (HTTP Basic, secret over HTTPS)
   client_secret_post         OK (secret in POST body)
   private_key_jwt            Best (no shared secret, asymmetric)
   tls_client_auth (mTLS)     Best (mutual TLS, certificate-based)

4. PRIVATE KEY JWT (most secure alternative to client_secret):
   Client signs a JWT assertion with its private key.
   AS verifies with client's registered public key.
   No shared secret transmitted at all.

   POST /oauth2/token
     grant_type=client_credentials
     &client_assertion_type=urn:ietf:params:oauth2:client-assertion-type:jwt-bearer
     &client_assertion=<signed-JWT>
     &scope=read:orders

CLIENT CREDENTIALS vs OTHER FLOWS
================================================================

Feature                 Client Credentials    Auth Code    ROPC
-----------------------------------------------------------------
User involved           No                    Yes          Yes
Refresh token           No                    Yes          Yes
Consent screen          No                    Yes          No
Client secret needed    Yes                   Yes          Yes
Use case                M2M services          Web/Mobile   DEPRECATED
Forward secrecy         Depends on AS         Yes          No

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: When would you use Client Credentials grant?
A: When a service needs to authenticate itself (no user context) to access
   another service's API — typical in microservices. E.g., Order Service
   calling Inventory Service.

Q: Does Client Credentials have a refresh token?
A: No. Since there's no user session to maintain, clients simply re-authenticate
   with their credentials when the token expires. Spring handles this
   automatically via OAuth2AuthorizedClientManager.

Q: How do you secure client secrets in a microservices environment?
A: Use environment variables injected at runtime, or secrets managers like
   HashiCorp Vault or AWS Secrets Manager. Never hardcode in source. Rotate
   regularly. Use private_key_jwt or mTLS for highest security.

Q: How does Spring WebClient integrate with OAuth2 Client Credentials?
A: Configure spring.security.oauth2.client.registration with
   grant-type: client_credentials. Use
   ServletOAuth2AuthorizedClientExchangeFilterFunction to automatically
   obtain and attach Bearer tokens to outgoing requests. Token caching
   and renewal is handled automatically.

Q: What is the sub claim in a Client Credentials token?
A: The sub (subject) claim is the client_id of the calling service, not a
   user ID. This helps the resource server identify WHICH service is calling.
