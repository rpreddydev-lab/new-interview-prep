================================================================
KEYCLOAK — OPEN SOURCE IDENTITY AND ACCESS MANAGEMENT
================================================================

WHAT IS KEYCLOAK?
------------------
Keycloak is an open-source Identity and Access Management (IAM) solution
from Red Hat / JBoss. It provides:
  - Authentication (OIDC, SAML 2.0, LDAP, Social Login)
  - Authorization (Fine-grained policy engine)
  - User Federation (LDAP, Active Directory)
  - Single Sign-On (SSO) and Single Sign-Out
  - MFA (OTP, WebAuthn)
  - User Management Console
  - Customizable themes
  - Client adapters for Spring, Node.js, etc.

CURRENT VERSION: Keycloak 24+ (based on Quarkus)
ALTERNATIVES: Auth0, Okta, Azure AD (Entra ID), AWS Cognito, FusionAuth

================================================================
KEYCLOAK CORE CONCEPTS
================================================================

REALM:
  Isolated tenant/namespace in Keycloak.
  Contains: users, clients, roles, groups, identity providers.
  Default realm: "master" (admin only — don't use for apps)
  Best practice: create a separate realm per environment (dev, staging, prod)
                 or per application domain.
  URL pattern: https://keycloak.example.com/realms/{realm-name}

CLIENT:
  An application registered with Keycloak.
  Types:
    - Confidential (server-side app with secret)
    - Public (SPA, mobile — no secret)
    - Bearer-only (services that only accept tokens, never login)
  Settings: redirect URIs, allowed scopes, grant types, token settings

USER:
  Identity that can authenticate with Keycloak.
  Attributes: username, email, firstName, lastName, custom attributes.
  Credentials: password, OTP, WebAuthn keys.

ROLE:
  Permission labels assigned to users or service accounts.
  Types:
    - Realm roles    : apply across all clients in the realm
    - Client roles   : specific to a single client application
  Groups can also have roles.

GROUP:
  Hierarchical collection of users.
  Groups inherit roles.
  Roles assigned to group → all group members inherit those roles.

IDENTITY PROVIDER (IdP):
  External login providers: Google, GitHub, Facebook, SAML IdPs, etc.
  Keycloak acts as a broker — users log in via external IdP.

CLIENT SCOPE:
  Reusable scope definition — which claims to include when requested.
  Assigned to clients (default or optional scopes).

PROTOCOL MAPPER:
  Transforms data into token claims.
  Examples:
    - User attribute mapper   : add custom attribute to token
    - Role mapper            : add user roles to token
    - Audience mapper        : add specific audience to token
    - Hardcoded claim        : always include a specific claim

SPRING BOOT INTEGRATION WITH KEYCLOAK
================================================================

# application.yml — Resource Server (validate JWT from Keycloak)
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.example.com/realms/myrealm
          # OR use JWKS directly:
          # jwk-set-uri: https://keycloak.example.com/realms/myrealm/protocol/openid-connect/certs

// Security Config for Resource Server
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthConverter()))
            );
        return http.build();
    }

    @Bean
    public JwtAuthenticationConverter jwtAuthConverter() {
        JwtGrantedAuthoritiesConverter converter = new JwtGrantedAuthoritiesConverter();
        // Keycloak puts roles in realm_access.roles
        converter.setAuthoritiesClaimName("realm_access.roles");
        converter.setAuthorityPrefix("ROLE_");

        JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();
        jwtConverter.setJwtGrantedAuthoritiesConverter(keycloakRolesConverter());
        return jwtConverter;
    }

    // Custom converter for Keycloak's role format
    private Converter<Jwt, Collection<GrantedAuthority>> keycloakRolesConverter() {
        return jwt -> {
            Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
            List<String> roles = realmAccess != null
                ? (List<String>) realmAccess.get("roles")
                : Collections.emptyList();

            return roles.stream()
                .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                .collect(Collectors.toList());
        };
    }
}

KEYCLOAK JWT STRUCTURE
================================================================

Keycloak Access Token payload (example):
{
  "exp": 1713484800,
  "iat": 1713481200,
  "jti": "unique-id",
  "iss": "https://keycloak.example.com/realms/myrealm",
  "aud": "account",
  "sub": "f2f9e4b5-1234-5678-9012-abcdef012345",
  "typ": "Bearer",
  "azp": "my-spring-app",
  "session_state": "session-id-here",
  "acr": "1",
  "realm_access": {
    "roles": ["default-roles-myrealm", "USER", "ADMIN"]
  },
  "resource_access": {
    "my-spring-app": {
      "roles": ["app-admin"]
    },
    "account": {
      "roles": ["view-profile"]
    }
  },
  "scope": "openid email profile",
  "sid": "session-id",
  "email_verified": true,
  "name": "John Doe",
  "preferred_username": "johndoe",
  "given_name": "John",
  "family_name": "Doe",
  "email": "john@example.com"
}

KEYCLOAK-SPECIFIC CLAIMS:
  realm_access.roles    : Roles assigned at realm level
  resource_access        : Roles per client (service-specific)
  preferred_username    : Username (use sub for stable identity)
  azp                   : The client that requested the token
  session_state         : Keycloak session ID (for session management)

KEYCLOAK ADMIN REST API
================================================================

Keycloak provides a REST API for management operations:

// Get admin token first
POST /realms/master/protocol/openid-connect/token
  grant_type=client_credentials
  &client_id=admin-cli
  &client_secret=<admin-secret>

// Create user
POST /admin/realms/myrealm/users
Authorization: Bearer <admin-token>
{
  "username": "newuser",
  "email": "new@example.com",
  "enabled": true,
  "credentials": [{"type": "password", "value": "temp123", "temporary": true}]
}

// Assign role to user
POST /admin/realms/myrealm/users/{userId}/role-mappings/realm
Authorization: Bearer <admin-token>
[{"id": "role-id", "name": "ADMIN"}]

// Spring Boot Admin Client
@Service
public class KeycloakAdminService {

    private final Keycloak keycloak; // Keycloak Admin Client SDK

    public UserRepresentation getUser(String userId) {
        return keycloak.realm("myrealm").users().get(userId).toRepresentation();
    }

    public void assignRole(String userId, String roleName) {
        RealmResource realm = keycloak.realm("myrealm");
        RoleRepresentation role = realm.roles().get(roleName).toRepresentation();
        realm.users().get(userId).roles().realmLevel().add(List.of(role));
    }
}

KEYCLOAK AUTHORIZATION SERVICES
================================================================

Keycloak has built-in fine-grained authorization:

RESOURCES: Things to protect (/api/orders)
SCOPES:    Actions on resources (view, create, delete)
POLICIES:  Rules for access (role-based, user-based, JS rules, aggregate)
PERMISSIONS: Bind resources + scopes to policies

Types of Policies:
  - Role Policy      : user must have specific role
  - User Policy      : specific user has access
  - Time Policy      : access during certain time period
  - JS Policy        : custom JavaScript logic
  - Aggregate Policy : combine multiple policies (AND/OR)

Use Keycloak Authorization Services when:
  ✓ Fine-grained, dynamic authorization
  ✓ Policies maintained by ops team (not developers)
  ✓ Complex ABAC scenarios

Otherwise, use Spring Security's @PreAuthorize for simpler cases.

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is a Keycloak realm and why should you create separate realms?
A: A realm is an isolated namespace in Keycloak with its own users, clients,
   roles, and configuration. Create separate realms per domain or environment
   (dev/staging/prod) to avoid interference and apply different security
   policies. Never use the "master" realm for applications.

Q: How does Keycloak store roles in JWT tokens?
A: Realm-level roles are in realm_access.roles. Client-specific roles are
   in resource_access.{client-id}.roles. Custom protocol mappers can add
   roles to different claim paths. Spring Security needs a custom
   JwtAuthenticationConverter to extract Keycloak roles into GrantedAuthority.

Q: How do you configure Spring Boot as a Resource Server with Keycloak?
A: Set spring.security.oauth2.resourceserver.jwt.issuer-uri to the Keycloak
   realm URL. Spring auto-discovers JWKS from the issuer metadata. Configure
   JwtAuthenticationConverter to map Keycloak's realm_access.roles to Spring
   Security authorities.

Q: What is the difference between realm roles and client roles in Keycloak?
A: Realm roles are global to the realm — a user with ADMIN realm role has
   that role across all clients. Client roles are specific to one client
   application — a user with app-admin client role for "my-app" only has
   that role within "my-app" context.

Q: How do you handle Keycloak's role claim format in Spring Security?
A: Implement a custom JwtAuthenticationConverter that reads
   jwt.getClaim("realm_access").get("roles") and converts them to
   Spring's GrantedAuthority with ROLE_ prefix. Register it as a bean
   and configure it in SecurityFilterChain's jwt() configuration.
