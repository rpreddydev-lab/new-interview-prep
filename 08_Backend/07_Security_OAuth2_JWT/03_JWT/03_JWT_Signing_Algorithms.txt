================================================================
JWT SIGNING ALGORITHMS
================================================================

JWT signatures ensure integrity (token wasn't tampered with) and
authenticity (issued by the expected party).

Two categories:
  1. Symmetric  — single shared secret (HMAC)
  2. Asymmetric — key pair: private signs, public verifies (RSA, ECDSA)

================================================================
HMAC ALGORITHMS (Symmetric)
================================================================

ALGORITHMS: HS256, HS384, HS512
  HS256 = HMAC with SHA-256 (256-bit output)
  HS384 = HMAC with SHA-384
  HS512 = HMAC with SHA-512 (most secure)

HOW IT WORKS:
  signature = HMAC(algorithm, message, secret)
  message   = base64url(header) + "." + base64url(payload)

  Verification: recompute HMAC and compare with constant-time comparison

KEY CHARACTERISTICS:
  ✓ Fast (software implementation)
  ✓ Simple — single key
  ✗ Same key used for signing AND verifying
  ✗ Anyone with the key can forge tokens
  ✗ Key must be shared with ALL resource servers
  ✗ If key is compromised, attacker can forge any token

WHEN TO USE HS256:
  ✓ All components (AS + RS) are in the SAME application/system
  ✓ You fully control all services that validate tokens
  ✓ Performance is critical, key management is tight
  ✗ Never share the secret across organizational boundaries

KEY REQUIREMENTS:
  ✓ Use cryptographically random key (NOT a password)
  ✓ Minimum 256 bits (32 bytes) for HS256
  ✓ Rotate regularly
  ✓ Store in secrets manager (Vault, env var)

EXAMPLE — GENERATING A STRONG HS256 KEY:
  // Generate 256-bit key
  SecretKey key = KeyGenerator.getInstance("HmacSHA256")
      .generateKey(); // 256-bit by default

  // Or from random bytes
  byte[] keyBytes = new byte[32]; // 256 bits
  new SecureRandom().nextBytes(keyBytes);
  SecretKey key = new SecretKeySpec(keyBytes, "HmacSHA256");

  // In Spring Security
  @Bean
  public JwtDecoder jwtDecoder() {
      SecretKeySpec secretKey = new SecretKeySpec(
          "your-256-bit-secret-here".getBytes(), "HmacSHA256");
      return NimbusJwtDecoder.withSecretKey(secretKey).build();
  }

================================================================
RSA ALGORITHMS (Asymmetric)
================================================================

ALGORITHMS: RS256, RS384, RS512, PS256, PS384, PS512
  RS256 = RSA PKCS#1 v1.5 padding + SHA-256 (most common)
  RS512 = RSA PKCS#1 v1.5 padding + SHA-512
  PS256 = RSA-PSS padding + SHA-256 (more secure padding, recommended)

HOW IT WORKS:
  SIGN   (AS):  signature = RSA_SIGN(SHA256(message), privateKey)
  VERIFY (RS):  RSA_VERIFY(SHA256(message), signature, publicKey)

KEY PAIR:
  Private Key → kept secret by Authorization Server ONLY
  Public Key  → published in JWKS endpoint, known by everyone

KEY CHARACTERISTICS:
  ✓ Only AS has private key → only AS can sign tokens
  ✓ Public key can be shared freely → resource servers verify without a secret
  ✓ Key rotation via JWKS kid mechanism
  ✓ Multiple resource servers, external parties can all verify
  ✗ Slower than HMAC
  ✗ Larger tokens (RSA-2048 signature is 256 bytes)

KEY SIZE RECOMMENDATIONS:
  RSA-2048 → Minimum for new systems
  RSA-3072 → Recommended
  RSA-4096 → High security (slower)

EXAMPLE — RSA KEY GENERATION:
  // Generate RSA key pair
  KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
  generator.initialize(2048);
  KeyPair keyPair = generator.generateKeyPair();
  RSAPrivateKey privateKey = (RSAPrivateKey) keyPair.getPrivate();
  RSAPublicKey  publicKey  = (RSAPublicKey)  keyPair.getPublic();

  // In Spring Authorization Server
  @Bean
  public JWKSource<SecurityContext> jwkSource() {
      KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
      generator.initialize(2048);
      KeyPair keyPair = generator.generateKeyPair();
      RSAKey rsaKey = new RSAKey.Builder((RSAPublicKey) keyPair.getPublic())
          .privateKey(keyPair.getPrivate())
          .keyID("key-2024")
          .build();
      return new ImmutableJWKSet<>(new JWKSet(rsaKey));
  }

  // In Resource Server (verify with public key from JWKS)
  @Bean
  public JwtDecoder jwtDecoder() {
      return NimbusJwtDecoder
          .withJwkSetUri("https://auth-server.com/.well-known/jwks.json")
          .build();
  }

================================================================
ECDSA ALGORITHMS (Asymmetric — Elliptic Curve)
================================================================

ALGORITHMS: ES256, ES384, ES512
  ES256 = ECDSA with P-256 curve + SHA-256
  ES384 = ECDSA with P-384 curve + SHA-384
  ES512 = ECDSA with P-521 curve + SHA-512

HOW IT WORKS:
  Similar to RSA but using elliptic curve mathematics.

KEY CHARACTERISTICS:
  ✓ Much smaller key sizes for equivalent security
  ✓ Faster signing and verification than RSA
  ✓ Smaller signature sizes (ES256 = 64 bytes vs RS256 = 256 bytes)
  ✓ Better for constrained environments (IoT, mobile)
  ✗ Slightly more complex implementation
  ✗ Less widely supported than RSA (but adoption growing)

COMPARISON:
  Security Level   RSA Key Size   ECDSA Key Size
  128-bit          RSA-3072       P-256 (256 bits)
  192-bit          RSA-7680       P-384 (384 bits)
  256-bit          RSA-15360      P-521 (521 bits)

EXAMPLE:
  KeyPairGenerator generator = KeyPairGenerator.getInstance("EC");
  generator.initialize(new ECGenParameterSpec("P-256"));
  KeyPair keyPair = generator.generateKeyPair();

  ECKey ecKey = new ECKey.Builder(Curve.P_256, (ECPublicKey) keyPair.getPublic())
      .privateKey(keyPair.getPrivate())
      .keyID("ec-key-2024")
      .build();

================================================================
ALGORITHM COMPARISON TABLE
================================================================

Algorithm   Type         Key Size    Sig Size   Speed    Security
----------------------------------------------------------------------
HS256       Symmetric    256+ bits   32 bytes   Fastest  Good (shared secret risk)
HS512       Symmetric    512+ bits   64 bytes   Fast     Good (shared secret risk)
RS256       Asymmetric   2048 bits   256 bytes  Medium   Excellent
RS512       Asymmetric   4096 bits   512 bytes  Slow     Excellent
PS256       Asymmetric   2048 bits   256 bytes  Medium   Excellent+ (better padding)
ES256       Asymmetric   256 bits    64 bytes   Fast     Excellent (small keys)
ES512       Asymmetric   521 bits    132 bytes  Fast     Excellent

RECOMMENDATIONS:
  Public-facing OAuth2 AS  → RS256 or ES256 (can share public key widely)
  Internal services only   → HS256 (if all services are trusted and controlled)
  Performance-critical     → ES256 (smaller, faster than RS256)
  Long-term security       → PS256 or ES256

================================================================
ALGORITHM CONFUSION ATTACK (Critical Vulnerability)
================================================================

BACKGROUND:
  Some early JWT libraries allowed the algorithm in the token HEADER
  to determine HOW the token is verified.

RS256 → HS256 ATTACK:
  1. Server uses RS256 and publishes its public key in JWKS
  2. Attacker changes token header: "alg": "HS256"
  3. Attacker SIGNS the token with HS256 using the SERVER'S PUBLIC KEY
     (which is publicly available!)
  4. Vulnerable server: "alg is HS256, verify with HMAC using my public key"
  5. Verification passes! Attacker has forged a token!

"NONE" ATTACK:
  Attacker changes alg to "none" and removes the signature.
  Vulnerable servers accept unsigned tokens.

PREVENTION:
  ✓ ALWAYS hardcode the expected algorithm server-side
  ✓ NEVER trust the "alg" header to choose verification method
  ✓ Explicitly configure your JWT library's algorithm

// Spring Security — explicitly set algorithm
@Bean
public JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
        .withJwkSetUri(jwksUri)
        .jwsAlgorithm(SignatureAlgorithm.RS256)  ← EXPLICIT, ignore header
        .build();
    return decoder;
}

// For HMAC — only accept HS256
@Bean
public JwtDecoder jwtDecoder(@Value("${jwt.secret}") String secret) {
    SecretKeySpec key = new SecretKeySpec(secret.getBytes(), "HmacSHA256");
    return NimbusJwtDecoder.withSecretKey(key)
        .macAlgorithm(MacAlgorithm.HS256)  ← explicit
        .build();
}

================================================================
KEY ROTATION
================================================================

WHY ROTATE KEYS?
  - Limit blast radius if private key is compromised
  - Compliance requirements
  - Cryptographic best practices

HOW TO ROTATE GRACEFULLY:
  1. Generate new key pair (new kid)
  2. Publish BOTH old and new keys in JWKS endpoint
  3. New tokens issued with new key (new kid in header)
  4. Resource servers automatically pick up new key from JWKS
  5. Wait for all old tokens to expire (access token TTL = 15 min)
  6. Remove old key from JWKS

JWKS with multiple keys:
  {
    "keys": [
      { "kid": "key-2024", "alg": "RS256", "n": "...", "e": "AQAB" },
      { "kid": "key-2023", "alg": "RS256", "n": "...", "e": "AQAB" }
    ]
  }

Spring caches JWKS and refreshes when it encounters an unknown kid.

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the difference between HS256 and RS256?
A: HS256 is symmetric — same secret for signing and verification, so all
   services must share the secret. RS256 is asymmetric — private key signs
   (only AS has it), public key verifies (shared freely via JWKS). RS256 is
   preferred for distributed systems.

Q: What is the algorithm confusion attack?
A: If a server trusts the token's alg header to choose the verification
   algorithm, an attacker can change alg from RS256 to HS256 and sign with
   the public key (which is known). The server verifies HS256 with its public
   key, which succeeds. Prevention: always hardcode the expected algorithm.

Q: Why is ES256 gaining popularity over RS256?
A: ECDSA keys are much smaller (256 bits vs 2048 bits for equivalent security),
   signatures are smaller (64 vs 256 bytes), and operations are faster. Better
   for mobile, IoT, and high-throughput systems.

Q: How does key rotation work with JWT?
A: The AS generates a new key pair, assigns a new kid, and publishes both
   old and new keys in JWKS. New tokens use the new kid. Resource servers
   fetch the new key from JWKS when they see an unfamiliar kid. After all
   old tokens expire, the old key is removed from JWKS.

Q: What is PS256 and how is it different from RS256?
A: Both use RSA, but PS256 uses RSA-PSS padding (Probabilistic Signature
   Scheme) while RS256 uses the older PKCS#1 v1.5 padding. RSA-PSS is
   considered more cryptographically sound and is recommended for new systems.
