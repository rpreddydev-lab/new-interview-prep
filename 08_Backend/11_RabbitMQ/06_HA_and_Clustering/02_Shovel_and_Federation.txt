RABBITMQ SHOVEL AND FEDERATION
================================

Overview
--------
Both Shovel and Federation move messages between RabbitMQ brokers.

  Shovel    — actively pumps messages from source to destination (one-way pump)
  Federation — federates exchanges/queues across brokers (pull-based, policy-driven)

Plugins:
  rabbitmq-plugins enable rabbitmq_shovel rabbitmq_shovel_management
  rabbitmq-plugins enable rabbitmq_federation rabbitmq_federation_management

---

SHOVEL
------
A Shovel continuously reads messages from a source (queue or exchange) and
publishes them to a destination on the same or different broker.

Use Cases:
  - Move messages between data centers
  - Migrate queues to a new broker with zero downtime
  - Bridge on-prem RabbitMQ to cloud RabbitMQ
  - Offload messages from an overloaded cluster

Static Shovel (defined in rabbitmq.conf):
  shovel.my_shovel.source.protocol = amqp091
  shovel.my_shovel.source.uris = amqp://source-host/%2f
  shovel.my_shovel.source.queue = orders.queue
  shovel.my_shovel.destination.uris = amqp://dest-host/%2f
  shovel.my_shovel.destination.queue = orders.queue.copy
  shovel.my_shovel.ack_mode = on-confirm
  shovel.my_shovel.reconnect_delay = 5

Dynamic Shovel (via Management API / HTTP):
  PUT /api/parameters/shovel/%2f/my-shovel
  {
    "value": {
      "src-protocol": "amqp091",
      "src-uri": "amqp://source-host",
      "src-queue": "orders.queue",
      "dest-protocol": "amqp091",
      "dest-uri": "amqp://dest-host",
      "dest-queue": "orders.queue.copy",
      "ack-mode": "on-confirm"
    }
  }

Ack Modes:
  on-confirm  — waits for destination to confirm before acking source (safest)
  on-publish  — acks source after publish to destination (potential loss on failure)
  no-ack      — never acks source (fastest, least safe)

Shovel States:
  starting → running → stopped/terminated
  Shovel auto-reconnects on failure (reconnect-delay configurable).

FEDERATION
----------
Federation allows queues or exchanges to be "federated" — connected across brokers
so consumers on a downstream broker can consume messages produced upstream.

Key Difference from Shovel:
  Federation is policy-driven and pull-based — messages only move when there is demand.
  Shovel always pumps all messages regardless of downstream demand.

Exchange Federation:
  - Upstream exchanges publish messages
  - Downstream exchange has a federated link to upstream
  - Messages flow downstream when local subscribers exist
  - Useful for: fan-out across regions, multi-datacenter pub/sub

Queue Federation:
  - Downstream queue pulls messages from upstream when local queue is empty
  - Useful for: load balancing across clusters

Federation Setup:
  1. Define an upstream:
     PUT /api/parameters/federation-upstream/%2f/my-upstream
     {
       "value": {
         "uri": "amqp://upstream-host",
         "expires": 3600000,
         "message-ttl": 60000,
         "max-hops": 1
       }
     }

  2. Define a policy that applies federation:
     PUT /api/policies/%2f/federate-orders
     {
       "pattern": "^orders\.",
       "definition": {
         "federation-upstream": "my-upstream"
       },
       "apply-to": "exchanges"
     }

max-hops: Prevents message loops in multi-hop federation topologies (default: 1).

---

Shovel vs Federation Comparison
---------------------------------
  | Aspect               | Shovel                      | Federation                   |
  |----------------------|-----------------------------|------------------------------|
  | Direction            | One-way pump                | Pull-based on demand         |
  | Configuration        | Per-connection              | Policy-based                 |
  | Message deduplication| No                          | No                           |
  | Use case             | Migration, bridging         | Multi-region pub/sub, HA     |
  | Active transfer      | Always                      | Only when consumers exist    |
  | Message order        | Preserved                   | Not guaranteed across hops   |
  | Loop prevention      | Manual                      | max-hops parameter           |

Common Production Patterns
---------------------------

Active-Passive DR with Shovel:
  - Primary cluster handles all traffic
  - Shovel replicates critical queues to DR cluster
  - On failover: DNS/LB switch to DR, Shovel stops

Global Fan-Out with Federation:
  - Central exchange in us-east-1
  - Federated exchanges in eu-west-1, ap-southeast-1
  - Local consumers receive messages routed from central

Zero-Downtime Migration:
  1. Create Shovel from old cluster → new cluster
  2. Redirect new producers to new cluster
  3. Let Shovel drain old queue
  4. Redirect consumers to new cluster
  5. Delete Shovel
