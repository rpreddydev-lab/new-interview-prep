================================================================
GRAPHQL DIRECTIVES — IN DEPTH
================================================================

1. WHAT ARE DIRECTIVES?
------------------------
Directives are annotations that modify the behavior of a type, field, argument,
or fragment. They start with `@`. They are the extension mechanism of GraphQL.

Two categories:
  a) BUILT-IN DIRECTIVES — defined in the GraphQL spec
  b) CUSTOM DIRECTIVES   — defined by the schema author

Directives have "locations" that specify where they can be applied.

2. BUILT-IN DIRECTIVES
-----------------------

  2.1 @skip — Skip a field based on a condition
  -----------------------------------------------
  ```graphql
  directive @skip(if: Boolean!) on
    FIELD | FRAGMENT_SPREAD | INLINE_FRAGMENT

  query GetUser($hideEmail: Boolean!) {
    user(id: "1") {
      name
      email @skip(if: $hideEmail)    # not included if $hideEmail is true
    }
  }
  ```

  2.2 @include — Include a field based on a condition
  ----------------------------------------------------
  ```graphql
  directive @include(if: Boolean!) on
    FIELD | FRAGMENT_SPREAD | INLINE_FRAGMENT

  query GetUser($withDetails: Boolean!) {
    user(id: "1") {
      name
      ... @include(if: $withDetails) {
        email
        phone
        address { city country }
      }
    }
  }
  ```

  @skip vs @include:
  - `@skip(if: true)` = skip the field = same as `@include(if: false)`
  - They are logically opposite; don't use both on the same field
  - Choose based on which reads more naturally

  2.3 @deprecated — Mark a field, enum value, or argument as deprecated
  -----------------------------------------------------------------------
  ```graphql
  type User {
    username: String @deprecated(reason: "Use 'handle' instead")
    handle: String!
    profilePicture: String @deprecated(reason: "Use 'avatar' instead")
    avatar: String
  }

  enum Status {
    ACTIVE
    INACTIVE
    DELETED @deprecated(reason: "Use ARCHIVED instead")
    ARCHIVED
  }
  ```

  @deprecated:
  - Signals to clients: don't use this field
  - Tools like GraphiQL show deprecated fields with a strikethrough
  - The field still works — it just signals intent to remove
  - Introspection shows `isDeprecated: true` and the reason
  - Best practice: always provide a reason with an alternative

  2.4 @specifiedBy — Custom scalar specification URL
  ---------------------------------------------------
  ```graphql
  scalar UUID @specifiedBy(url: "https://tools.ietf.org/html/rfc4122")
  scalar DateTime @specifiedBy(url: "https://scalars.graphql.org/andimarek/date-time.html")
  ```

  Points to the specification document for the custom scalar.
  Used for documentation and tooling.

3. DIRECTIVE LOCATIONS
-----------------------
Directives can only appear at specific locations, defined in the schema:

  EXECUTABLE DIRECTIVE LOCATIONS (used in queries/mutations):
  ─────────────────────────────────────────────────────────────
  QUERY                — on query operations
  MUTATION             — on mutation operations
  SUBSCRIPTION         — on subscription operations
  FIELD                — on fields in selection sets
  FRAGMENT_DEFINITION  — on named fragment definitions
  FRAGMENT_SPREAD      — on ...fragmentName spreads
  INLINE_FRAGMENT      — on ... on Type {} inline fragments
  VARIABLE_DEFINITION  — on variable declarations

  TYPE SYSTEM DIRECTIVE LOCATIONS (used in schema SDL):
  ────────────────────────────────────────────────────────
  SCHEMA                 — on the schema definition
  SCALAR                 — on scalar type definitions
  OBJECT                 — on object type definitions
  FIELD_DEFINITION       — on field definitions in object types
  ARGUMENT_DEFINITION    — on argument definitions
  INTERFACE              — on interface type definitions
  UNION                  — on union type definitions
  ENUM                   — on enum type definitions
  ENUM_VALUE             — on enum value definitions
  INPUT_OBJECT           — on input type definitions
  INPUT_FIELD_DEFINITION — on input type field definitions

4. CUSTOM DIRECTIVES
---------------------

  4.1 Declaring a Custom Directive
  ---------------------------------
  ```graphql
  # Auth directive: requires a minimum role
  directive @auth(requires: Role = USER) on FIELD_DEFINITION

  # Field-level caching
  directive @cacheControl(
    maxAge: Int
    scope: CacheScope = PUBLIC
  ) on FIELD_DEFINITION | OBJECT

  # Rate limiting per field
  directive @rateLimit(
    max: Int!
    window: String! = "1m"
  ) on FIELD_DEFINITION

  # String transformation
  directive @upper on FIELD_DEFINITION
  directive @lower on FIELD_DEFINITION
  directive @trim on FIELD_DEFINITION

  # Length validation for inputs
  directive @length(min: Int, max: Int!) on ARGUMENT_DEFINITION | INPUT_FIELD_DEFINITION

  enum CacheScope {
    PUBLIC
    PRIVATE
  }
  ```

  4.2 Using Custom Directives in Schema
  --------------------------------------
  ```graphql
  type Query {
    adminDashboard: Dashboard! @auth(requires: ADMIN)
    users: [User!]! @auth(requires: MODERATOR)
    publicPosts: [Post!]! @cacheControl(maxAge: 300, scope: PUBLIC)
    me: User @auth
  }

  type Mutation {
    createUser(input: CreateUserInput! @length(max: 500)): User!
    deleteUser(id: ID!): Boolean! @auth(requires: ADMIN) @rateLimit(max: 10, window: "1m")
  }

  type User {
    id: ID!
    name: String! @upper
    email: String! @auth(requires: ADMIN)  # Only admins can see emails
    bio: String @trim
  }
  ```

5. IMPLEMENTING CUSTOM DIRECTIVES IN JAVA (Spring for GraphQL)
---------------------------------------------------------------

  5.1 SchemaDirectiveWiring Approach (graphql-java)
  --------------------------------------------------
  ```java
  // @upper directive implementation
  public class UpperCaseDirective implements SchemaDirectiveWiring {

    @Override
    public GraphQLFieldDefinition onField(SchemaDirectiveWiringEnvironment<GraphQLFieldDefinition> env) {
      GraphQLFieldDefinition field = env.getElement();
      DataFetcher<?> originalFetcher = env.getCodeRegistry()
        .getDataFetcher(env.getFieldsContainer(), field);

      DataFetcher<?> uppercaseFetcher = dataFetchingEnvironment -> {
        Object value = originalFetcher.get(dataFetchingEnvironment);
        if (value instanceof String s) return s.toUpperCase();
        return value;
      };

      env.getCodeRegistry().dataFetcher(
        FieldCoordinates.coordinates(env.getFieldsContainer(), field),
        uppercaseFetcher
      );
      return field;
    }
  }

  // Register in configuration:
  @Bean
  public RuntimeWiringConfigurer runtimeWiringConfigurer() {
    return builder -> builder
      .directiveWiring(new UpperCaseDirective());
  }
  ```

  5.2 @auth Directive Implementation
  ------------------------------------
  ```java
  public class AuthDirective implements SchemaDirectiveWiring {

    @Override
    public GraphQLFieldDefinition onField(SchemaDirectiveWiringEnvironment<GraphQLFieldDefinition> env) {
      GraphQLFieldDefinition field = env.getElement();
      GraphQLDirective directive = field.getDirective("auth");
      String requiredRole = directive.getArgument("requires").getValue().toString();

      DataFetcher<?> originalFetcher = env.getCodeRegistry()
        .getDataFetcher(env.getFieldsContainer(), field);

      DataFetcher<?> authFetcher = dataFetchingEnvironment -> {
        // Get authenticated user from context
        GraphQLContext context = dataFetchingEnvironment.getGraphQlContext();
        User currentUser = context.get("currentUser");

        if (currentUser == null) {
          throw new GraphQLException("Unauthenticated");
        }
        if (!currentUser.hasRole(requiredRole)) {
          throw new GraphQLException("Unauthorized: requires role " + requiredRole);
        }
        return originalFetcher.get(dataFetchingEnvironment);
      };

      env.getCodeRegistry().dataFetcher(
        FieldCoordinates.coordinates(env.getFieldsContainer(), field),
        authFetcher
      );
      return field;
    }
  }
  ```

6. FEDERATION DIRECTIVES (Apollo Federation)
---------------------------------------------
Apollo Federation adds its own set of directives for schema composition:

```graphql
# Mark a type as an entity (cross-subgraph)
type User @key(fields: "id") {
  id: ID!
  name: String!
}

# Extend a type from another subgraph
extend type User @key(fields: "id") {
  id: ID! @external          # Field owned by the Users subgraph
  orders: [Order!]!          # Field owned by this Orders subgraph
}

# Reference external field but don't resolve here
type Product {
  id: ID!
  name: String!
  vendor: User! @provides(fields: "name")
}

# Require fields from another subgraph for this resolver
type ShippingEstimate {
  estimatedDays: Int! @requires(fields: "product { weight dimensions { length } }")
}

# Mark a field as external (defined elsewhere)
# @external
# @key(fields: "...") — entity key field(s)
# @provides(fields: "...") — declare what fields you can provide
# @requires(fields: "...") — declare required external fields
# @extends — extend a type from another subgraph
# @shareable — allow multiple subgraphs to resolve same field
# @override — override a field from another subgraph
# @inaccessible — hide from gateway schema
# @tag — metadata tagging
```

7. DEFER AND STREAM DIRECTIVES
--------------------------------
Incremental delivery directives (experimental in many implementations):

```graphql
# @defer — send this fragment after the initial response
query GetProfile {
  user(id: "1") {
    name
    email
    ... @defer(label: "slow-stats") {
      followerCount      # Computed slowly
      postCount          # Requires extra query
    }
  }
}

# @stream — stream list items as they resolve
query GetFeed {
  feed @stream(initialCount: 3) {
    id
    title
    summary
  }
}
```

Client receives a multipart HTTP response with the initial payload followed
by the deferred/streamed patches.

8. BEST PRACTICES WITH DIRECTIVES
-----------------------------------
  ✓ Use @deprecated liberally — it communicates intent without breaking clients
  ✓ Custom directives for cross-cutting concerns (auth, caching, logging)
  ✓ Document all custom directives with descriptions and examples
  ✓ Prefer schema-level auth directives over scattered resolver checks
  ✓ Use @cacheControl to hint to CDNs and reverse proxies
  ✗ Don't overuse custom directives — they add complexity
  ✗ Don't use directives for business logic that belongs in resolvers
  ✗ Don't expose internal directives (like @internal) through introspection

9. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the difference between @skip and @include?
A: They are logical opposites. `@skip(if: true)` means "don't include this
   field" while `@include(if: true)` means "do include this field". Use
   whichever reads more naturally: `showEmail @include(if: $isAdmin)` or
   `email @skip(if: $hideEmail)`.

Q: Can custom directives modify the schema behavior?
A: Yes. Custom directives implemented with SchemaDirectiveWiring can wrap
   resolvers to add authentication checks, caching, transformations, logging,
   rate limiting, etc. They run at schema build time and wrap the existing
   DataFetcher with additional behavior.

Q: What is the @deprecated directive and when should you use it?
A: @deprecated marks a field, argument, or enum value as deprecated. Use it
   whenever you need to change the API contract: add the new field/value,
   mark the old one @deprecated with a reason pointing to the new one,
   and only remove the old one when analytics show zero client usage.

Q: How many custom directives can you define?
A: There's no limit. But keep them focused on cross-cutting concerns (auth,
   caching, validation, rate limiting) rather than business logic. Too many
   directives make the schema hard to understand.

Q: What are the Apollo Federation directives?
A: @key (entity identifier), @external (field from another subgraph),
   @provides (declare what fields you can provide), @requires (need fields
   from another subgraph), @extends (extend a type from another subgraph),
   @shareable (multiple subgraphs can resolve this field), @override
   (take ownership of a field from another subgraph), @inaccessible
   (hide from composed schema), @tag (metadata).

Q: What does "directive location" mean?
A: It specifies where in the schema or query a directive can appear. For
   example, `directive @auth on FIELD_DEFINITION` means @auth can only
   appear on field definitions in the SDL. If you try to use it elsewhere
   (like on an enum), you get a schema validation error.
