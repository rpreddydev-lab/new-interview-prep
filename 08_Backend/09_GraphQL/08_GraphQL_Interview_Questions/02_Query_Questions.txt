GRAPHQL QUERY & MUTATION INTERVIEW QUESTIONS — IN DEPTH
================================================================

Q1: What is the difference between a query and a mutation in GraphQL?
A: Both are client-to-server operations, but they differ semantically:
   Query — read-only. Safe to retry, can be cached, resolvers can run
   in parallel. Analogous to HTTP GET.
   Mutation — writes/side effects. Resolvers run serially (top to bottom,
   one at a time). Cannot be safely retried without idempotency keys.
   Note: GraphQL doesn't enforce this — nothing prevents a query from
   having side effects technically. The distinction is semantic convention.

Q2: How does GraphQL execute multiple mutations in one request?
A: Multiple root-level mutations in a single request are executed SERIALLY,
   in the order they appear. This is specified by the GraphQL spec to prevent
   race conditions. However, multiple queries execute in parallel.
   ```graphql
   mutation {
     deletePost(id: "1")     # runs first
     deletePost(id: "2")     # runs after the first completes
   }
   ```

Q3: What are GraphQL variables and why should you use them?
A: Variables externalize arguments from query strings, preventing:
   - SQL injection / injection attacks (values never interpolated)
   - Query string changes invalidating persisted query hashes
   - Caching issues (query string stays stable, only variables change)
   ```graphql
   query GetUser($id: ID!) {    # $id is a variable
     user(id: $id) { name }
   }
   # Sent separately: { "id": "1" }
   ```
   Best practice: ALWAYS use variables, never interpolate values into queries.

Q4: What are fragments and when would you use them?
A: Fragments are reusable selection sets:
   ```graphql
   fragment UserBasic on User { id name email }
   query { users { ...UserBasic } }
   query { me { ...UserBasic } }
   ```
   Use cases: (1) DRY principle — reuse field sets across queries.
   (2) Colocation — define fragments in the component that uses those fields
   (Relay pattern). (3) Conditional selection with inline fragments:
   `... on User { name }` for interface/union fields.
   Named fragments are expanded before execution — no performance overhead.

Q5: What is the @skip and @include directive? How are they different?
A: Both conditionally include or exclude fields, but with opposite logic:
   `field @include(if: $condition)` — include the field IF condition is true
   `field @skip(if: $condition)` — skip the field IF condition is true
   ```graphql
   query GetUser($showEmail: Boolean!, $skipAge: Boolean!) {
     user(id: "1") {
       name
       email @include(if: $showEmail)   # include if true
       age   @skip(if: $skipAge)        # skip if true (opposite!)
     }
   }
   ```
   Both use Boolean non-null arguments. If both are used on the same field,
   @skip takes priority.

Q6: What is an alias in GraphQL?
A: An alias renames a field in the response:
   ```graphql
   {
     alice: user(id: "1") { name }   # response: { "alice": { "name": "Alice" } }
     bob: user(id: "2") { name }     # response: { "bob": { "name": "Bob" } }
   }
   ```
   Aliases are required when: (1) querying the same field multiple times
   with different arguments. (2) resolving naming conflicts between fields.
   Aliases don't affect complexity — they're purely response key overrides.

Q7: What is the difference between a named query and an anonymous query?
A: Anonymous: `{ user { name } }` — unnamed, fine for simple one-off queries
   Named: `query GetUser { user { name } }` — has an operation name
   Named queries are required when: (1) using variables (variables go with
   the operation name). (2) sending multiple operations in one request
   (must specify which to execute). (3) debugging (name appears in logs).
   Best practice: always name operations in production code.

Q8: What is introspection in GraphQL?
A: Introspection is the ability to query the schema itself:
   ```graphql
   { __schema { types { name } } }        # All types
   { __type(name: "User") { fields { name } } }  # Type details
   { __typename }                          # Current type name
   ```
   Uses: schema exploration, code generation (graphql-codegen), IDE
   autocompletion, documentation tools. Should be disabled in production
   (exposes full schema to attackers). The 3 built-in meta-fields:
   __typename (on every object), __type(name:), __schema.

Q9: How do you request data from a union type in GraphQL?
A: Use inline fragments with type conditions:
   ```graphql
   {
     search(query: "graphql") {
       ... on User { name email }         # Only if result is User
       ... on Post { title author { name } }  # Only if result is Post
       ... on Article { title url }       # Only if result is Article
     }
   }
   ```
   `__typename` is always available without fragments:
   ```graphql
   search(query: "x") { __typename ... on User { name } }
   ```

Q10: What happens when you query a nullable field that returns null?
A: The field is set to null in the response. If the field is non-null (!),
   the error propagates to the nearest nullable parent.
   ```json
   { "data": { "user": { "name": null, "email": null } } }
   ```
   If `name` is `String!` (non-null) and returns null:
   ```json
   { "data": { "user": null }, "errors": [{ "path": ["user", "name"] }] }
   ```
   The entire `user` object becomes null because `name!` failed.

Q11: What is the difference between a query with multiple root fields and
     batched requests?
A: Multiple root fields in ONE operation:
   ```graphql
   { user(id: "1") { name }  post(id: "2") { title } }
   ```
   These run in parallel in one HTTP request.
   Batched requests: multiple separate operations in ONE HTTP POST:
   ```json
   [
     { "query": "{ user(id: \"1\") { name } }" },
     { "query": "{ post(id: \"2\") { title } }" }
   ]
   ```
   This is client-side batching at the HTTP layer (Apollo Client supports this).
   Both reduce network round-trips, but multiple root fields is preferred
   as it's a single GraphQL operation.

Q12: What is an operation type and what are the valid operation types?
A: An operation type is the keyword at the start of a GraphQL document:
   `query`, `mutation`, or `subscription`.
   Anonymous shorthand `{ field }` is equivalent to `query { field }`.
   Cannot use shorthand if: (1) the operation is not a query. (2) you
   need to declare variables. (3) you need to name the operation.

Q13: How do you send variables with null vs omitting them entirely?
A: There is a semantic difference:
   - Null: `"email": null` — explicitly set to null (update to null)
   - Omit: variable not in the variables object — unset/not provided
   In mutations, distinguish: updateUser(id: "1", email: null) means
   "clear the email field"; omitting email means "don't change it".
   Schema must use Optional/nullable pattern to support both cases.

Q14: What is the difference between @include and frontend conditional rendering?
A: @include with a variable: the decision is made on the client and the
   field is not even fetched if false. The server doesn't execute the
   resolver for excluded fields — saves bandwidth and server work.
   Frontend conditional rendering: the data is fetched but not displayed.
   Use @include when you want to conditionally skip the data entirely;
   use frontend rendering when you've already fetched the data.
