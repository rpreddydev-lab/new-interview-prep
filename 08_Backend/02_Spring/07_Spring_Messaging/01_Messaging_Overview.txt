  1. WHAT IS MESSAGING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Messaging enables asynchronous, decoupled communication between
application components or microservices via a message broker.

Benefits:
  - Decoupling: producer and consumer evolve independently
  - Scalability: consumers scale independently from producers
  - Resilience: broker buffers messages when consumer is down
  - Backpressure: broker absorbs traffic spikes
  - Replay: messages can be replayed (Kafka) or re-queued (RabbitMQ)

Messaging vs HTTP:
  HTTP: synchronous, tight coupling, caller waits for response
  Messaging: asynchronous, loose coupling, fire-and-forget or eventual

Spring provides a broker-agnostic abstraction layer:

  Message<T>        → wrapper around payload + headers
  MessageChannel    → destination for sending
  MessageHandler    → processes a received message
  MessagingTemplate → template for send/receive operations
  @MessageMapping   → route incoming messages (WebSocket/STOMP)

org.springframework.messaging package — core abstractions
spring-messaging module is shared by Spring MVC (WebSocket/STOMP),
Spring Integration, Spring Cloud Stream, and Spring for Kafka/RabbitMQ.

Spring Cloud Stream provides a higher-level abstraction over Kafka/RabbitMQ
using Binders and functional programming model (java.util.function).

Dependency:
  spring-cloud-starter-stream-kafka
  spring-cloud-starter-stream-rabbit

// Producer: return a Supplier or Function
@Bean
public Supplier<OrderEvent> produceOrder() {
    return () -> new OrderEvent("ORDER-123", "CREATED");
}

// Consumer: return a Consumer
@Bean
public Consumer<OrderEvent> processOrder() {
    return event -> {
        log.info("Processing order: {}", event.getOrderId());
    };
}

// Processor: Function<IN, OUT> — consume and produce
@Bean
public Function<OrderEvent, ShipmentEvent> orderToShipment() {
    return order -> new ShipmentEvent(order.getOrderId());
}

application.yml:
  spring:
    cloud:
      stream:
        bindings:
          produceOrder-out-0:
            destination: orders-topic
          processOrder-in-0:
            destination: orders-topic
            group: order-processor-group
        kafka:
          binder:
            brokers: localhost:9092

Advantage: swap Kafka for RabbitMQ by changing the binder dependency.

// Access message headers in listeners
@KafkaListener(topics = "orders")
public void handleOrder(
    @Payload OrderEvent event,
    @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
    @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
    @Header(KafkaHeaders.OFFSET) long offset) {

    log.info("topic={} partition={} offset={}", topic, partition, offset);
}

Message Converters:
  - StringMessageConverter      → plain text
  - MappingJackson2MessageConverter → JSON (most common)
  - ByteArrayMessageConverter   → binary/raw
  - GenericMessageConverter     → type-based delegation

Configure JSON converter for Kafka/RabbitMQ:
  @Bean
  public MessageConverter jsonMessageConverter() {
      return new Jackson2JsonMessageConverter();
  }

  7. TRANSACTIONAL MESSAGING (OUTBOX PATTERN)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: Save to DB and publish to Kafka — what if one fails?

Naive approach (WRONG):
  @Transactional
  public void createOrder(Order order) {
      orderRepo.save(order);
      kafkaTemplate.send("orders", event);  // if DB rolls back, event already sent!
  }

Outbox Pattern (CORRECT):
  @Transactional
  public void createOrder(Order order) {
      orderRepo.save(order);
      // Write event to outbox table (SAME transaction)
      outboxRepo.save(new OutboxMessage("orders", toJson(event)));
  }

  // Separate process (scheduler or CDC) reads outbox and publishes to Kafka
  @Scheduled(fixedDelay = 1000)
  public void pollOutbox() {
      List<OutboxMessage> messages = outboxRepo.findUnpublished();
      for (OutboxMessage msg : messages) {
          kafkaTemplate.send(msg.getTopic(), msg.getPayload());
          msg.setPublished(true);
          outboxRepo.save(msg);
      }
  }

Alternatives:
  - Debezium (CDC) reads outbox via database change log
  - Kafka Transactions (exactly-once with transactional producer)

Q: What is the difference between a queue and a topic?
A: A queue (point-to-point) delivers each message to one consumer.
   A topic (pub-sub) delivers each message to all subscribed consumers.
   RabbitMQ uses queues; Kafka uses topics with consumer groups (each
   group gets a copy, but within a group messages are load-balanced).

Q: When would you choose Kafka over RabbitMQ?
A: Use Kafka for: high-throughput event streaming, message replay, event
   sourcing, ordered events within a partition, long-term retention.
   Use RabbitMQ for: complex routing (direct/fanout/topic/headers
   exchanges), request-reply (RPC), short-lived tasks, priority queues.

Q: What is the Outbox Pattern and why is it needed?
A: The Outbox Pattern solves the dual-write problem: ensuring that both
   a DB write and a message publish either both succeed or both fail.
   By writing the event to an "outbox" table in the same transaction as
   the domain entity, and having a separate process read and publish
   the outbox, you get atomic DB + message semantics.

Q: What does @TransactionalEventListener solve?
A: It allows publishing an event after the current transaction commits
   successfully. Unlike @EventListener (which fires immediately),
   @TransactionalEventListener(phase = AFTER_COMMIT) ensures the event
   is only fired if the transaction committed — no phantom events on rollback.

Q: What is exactly-once delivery in Kafka?
A: Kafka supports exactly-once semantics (EOS) via idempotent producers
   (acks=all + enable.idempotence=true) and transactional producers.
   In Spring Kafka: set producerFactory to use transactional.id and
   kafkaTemplate.executeInTransaction(). Most systems accept at-least-once
   + idempotent consumers as a simpler alternative.
