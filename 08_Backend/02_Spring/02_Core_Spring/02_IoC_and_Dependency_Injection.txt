================================================================
  IoC AND DEPENDENCY INJECTION — IN DEPTH
================================================================

================================================================
WHAT IS INVERSION OF CONTROL?
================================================================

  IoC is a design principle where the CONTROL of object creation
  and dependency wiring is inverted from application code to a
  framework/container.

  Without IoC (tight coupling):
  ─────────────────────────────
    public class OrderService {
        // Hard-coded instantiation — tightly coupled
        private PaymentService paymentService = new PaymentService();
        private NotificationService notifier  = new EmailNotificationService();
    }

  With IoC (loose coupling):
  ──────────────────────────
    @Service
    public class OrderService {
        private final PaymentService paymentService;
        private final NotificationService notifier;

        // Spring injects whatever implements these interfaces
        public OrderService(PaymentService paymentService,
                            NotificationService notifier) {
            this.paymentService = paymentService;
            this.notifier       = notifier;
        }
    }

DEPENDENCY INJECTION — DETAILED MECHANICS
================================================================

  Spring resolves dependencies in this order:
    1. Find beans matching the required TYPE
    2. If multiple matches → check for @Primary
    3. If still ambiguous → check @Qualifier name
    4. If still unresolved → throw NoUniqueBeanDefinitionException

  ── CONSTRUCTOR INJECTION (BEST PRACTICE) ──────────────────────

  @Service
  public class UserService {

      private final UserRepository userRepository;
      private final PasswordEncoder passwordEncoder;

      // @Autowired optional for single constructor (Spring 4.3+)
      public UserService(UserRepository userRepository,
                         PasswordEncoder passwordEncoder) {
          this.userRepository   = userRepository;
          this.passwordEncoder  = passwordEncoder;
      }
  }

  Why constructor injection is preferred:
    • Fields can be final → immutability
    • All dependencies visible in constructor signature
    • Works perfectly in plain unit tests:
        UserService svc = new UserService(
            mock(UserRepository.class),
            mock(PasswordEncoder.class));
    • Spring detects circular dependency at startup (BeanCreationException)

  ── SETTER INJECTION ────────────────────────────────────────────

  @Service
  public class ReportGenerator {

      private DataExporter exporter;

      @Autowired
      public void setExporter(DataExporter exporter) {
          this.exporter = exporter;
      }
  }

  When to use:
    • Optional dependencies (add @Autowired(required = false))
    • When a circular dependency truly cannot be avoided

  ── FIELD INJECTION (AVOID) ─────────────────────────────────────

  @Service
  public class SomeService {
      @Autowired
      private SomeDependency dep;   // violates SOLID, not testable
  }

  Problems:
    • Reflection-based — bypasses constructor visibility
    • Cannot declare final fields
    • Unit testing requires Spring context or reflection hacks
    • Hides class complexity (you don't see how many deps it has)

================================================================
@AUTOWIRED — RESOLUTION RULES
================================================================

  Step-by-step resolution:

  1. By TYPE: Find all beans matching the parameter type.
     @Autowired UserRepository repo;  // finds UserRepository bean

  2. By NAME (if ambiguous): match field/parameter name to bean name.
     @Autowired
     UserRepository userRepository;  // tries bean named "userRepository"

  3. @Qualifier: Explicit name hint.
     @Autowired
     @Qualifier("postgresUserRepository")
     UserRepository userRepository;

  4. @Primary: Mark one bean as default when multiple exist.
     @Bean
     @Primary
     public UserRepository postgresUserRepository() { ... }

  5. Optional injection:
     @Autowired(required = false)
     Optional<MetricsCollector> metricsCollector;

     // Or use Java Optional:
     @Autowired
     Optional<FeatureFlag> featureFlag;

QUALIFIERS AND PRIMARY — CODE EXAMPLES
================================================================

  Scenario: Two implementations of PaymentGateway

  @Component("stripeGateway")
  public class StripeGateway implements PaymentGateway { ... }

  @Component("paypalGateway")
  @Primary                          // default choice
  public class PaypalGateway implements PaymentGateway { ... }

  @Service
  public class CheckoutService {

      // Injects PaypalGateway (marked @Primary)
      @Autowired
      private PaymentGateway defaultGateway;

      // Injects StripeGateway via explicit @Qualifier
      @Autowired
      @Qualifier("stripeGateway")
      private PaymentGateway stripeGateway;
  }

@VALUE — INJECTING CONFIGURATION PROPERTIES
================================================================

  # application.properties
  app.max-retries=3
  app.base-url=https://api.example.com
  app.timeout=5000

  @Service
  public class ApiClient {

      @Value("${app.base-url}")
      private String baseUrl;

      @Value("${app.max-retries:5}")    // default = 5 if property missing
      private int maxRetries;

      @Value("${app.timeout}")
      private long timeoutMs;

      // SpEL expression
      @Value("#{systemProperties['os.name']}")
      private String osName;
  }

INJECTING COLLECTIONS AND MAPS
================================================================

  When multiple beans implement same interface:

  @Component
  public class PaymentProcessor {

      // All beans of type PaymentGateway injected as List
      @Autowired
      private List<PaymentGateway> gateways;

      // Injected as Map: key = bean name, value = bean instance
      @Autowired
      private Map<String, PaymentGateway> gatewayMap;
  }

  // Ordering: implement Ordered or use @Order(1)
  @Component
  @Order(1)
  public class PrimaryGateway implements PaymentGateway { ... }

INJECT (@javax.inject.Inject) vs @AUTOWIRED
================================================================

  Feature               | @Autowired (Spring)    | @Inject (JSR-330)
  ----------------------|------------------------|---------------------
  required attribute    | Yes (default true)     | No
  @Qualifier equivalent | @Qualifier("name")     | @Named("name")
  Source                | Spring-specific        | Java standard (JSR-330)
  In Spring apps        | Preferred              | Works but less features

================================================================
LAZY INJECTION — @Lazy
================================================================

  // Bean is NOT created until first use
  @Service
  @Lazy
  public class HeavyService {
      public HeavyService() {
          System.out.println("Expensive initialization...");
      }
  }

  // Inject lazily (proxy created at injection time, real bean later)
  @Service
  public class AppStartup {
      @Autowired
      @Lazy
      private HeavyService heavyService;
  }

  Common use: break circular dependency between singletons.

================================================================
PROTOTYPE BEAN INSIDE SINGLETON — THE PROBLEM
================================================================

  Problem:
    @Service                  // singleton
    public class TaskRunner {
        @Autowired
        private TaskContext ctx;   // prototype — injected ONCE
    }
    // ctx is always the SAME instance → prototype semantics lost

  Solution 1: ObjectProvider<T>
    @Service
    public class TaskRunner {
        @Autowired
        private ObjectProvider<TaskContext> ctxProvider;

        public void run() {
            TaskContext ctx = ctxProvider.getObject(); // new each call
        }
    }

  Solution 2: @Lookup
    @Service
    public abstract class TaskRunner {
        @Lookup
        protected abstract TaskContext createContext();

        public void run() {
            TaskContext ctx = createContext(); // new each call
        }
    }

  Solution 3: ApplicationContextAware (verbose, avoid)
    ctx = applicationContext.getBean(TaskContext.class);

================================================================
INTERVIEW QUESTIONS — IoC AND DI
================================================================

  Q: What is the difference between IoC and DI?
  A: IoC is the principle (don't call us, we'll call you).
     DI is the pattern used to implement IoC in Spring (inject
     collaborators rather than create them).

  Q: Explain @Autowired resolution order.
  A: (1) by type → (2) by field/parameter name → (3) @Qualifier
     → (4) @Primary → exception if still ambiguous.

  Q: Why is constructor injection preferred over field injection?
  A: Immutability, testability without Spring, explicit dependencies,
     and early detection of circular dependencies.

  Q: How does Spring handle optional dependencies?
  A: Use @Autowired(required=false), Java Optional<T>, or
     ObjectProvider<T>.

  Q: What happens if you have two @Primary beans of the same type?
  A: Spring throws NoUniqueBeanDefinitionException since @Primary
     must be unique per type.

  Q: How to inject a prototype bean into a singleton correctly?
  A: Use ObjectProvider<T>.getObject() or @Lookup method injection.
