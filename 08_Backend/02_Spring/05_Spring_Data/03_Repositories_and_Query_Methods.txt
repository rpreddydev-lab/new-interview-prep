  2. DERIVED QUERY METHODS (METHOD NAME DSL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Data parses method names to generate JPQL automatically.

Naming anatomy:
  find  By  Name  And  Price  LessThan
  ──┬──  ──  ─┬─  ───  ──┬──  ────┬────
   verb     field  conj  field  keyword

Subject keywords:
  find…By  / read…By / get…By   → SELECT
  query…By                       → SELECT (alias)
  count…By                       → SELECT count(*)
  exists…By                      → SELECT CASE WHEN count>0...
  delete…By / remove…By          → DELETE

Condition keywords:
  And / Or / Not / Between / LessThan / LessThanEqual
  GreaterThan / GreaterThanEqual / After / Before
  IsNull / IsNotNull / Like / NotLike / StartingWith
  EndingWith / Containing / In / NotIn / True / False
  IgnoreCase / OrderBy / Asc / Desc / Top / First

Examples:
  // SELECT * FROM products WHERE name = ?
  List<Product> findByName(String name);

  // SELECT * FROM products WHERE price < ? AND active = ?
  List<Product> findByPriceLessThanAndActiveTrue(BigDecimal price);

  // SELECT * FROM products WHERE name LIKE '%keyword%'
  List<Product> findByNameContainingIgnoreCase(String keyword);

  // SELECT * FROM products WHERE category IN (...)
  List<Product> findByCategoryIn(List<Category> categories);

  // SELECT * FROM products WHERE createdAt BETWEEN ? AND ?
  List<Product> findByCreatedAtBetween(LocalDateTime from, LocalDateTime to);

  // SELECT * FROM products ORDER BY price DESC LIMIT 5
  List<Product> findTop5ByOrderByPriceDesc();

  // Pagination + filtering
  Page<Product> findByCategory(Category cat, Pageable pageable);

  // Existence check
  boolean existsBySku(String sku);

  // Count
  long countByCategory(Category cat);

  // Delete
  void deleteByCategoryAndActiveFalse(Category cat);

  3. RETURN TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Return type               | Description
  ──────────────────────────┼──────────────────────────────────────
  T                         | Single result, exception if >1 or null
  Optional<T>               | Single result, empty if not found
  List<T>                   | Multiple results
  Page<T>                   | Results with pagination metadata
  Slice<T>                  | Page without count query
  Stream<T>                 | Java Stream (must close in @Transactional)
  Flux<T>                   | Reactive (Spring Data R2DBC)
  Mono<T>                   | Reactive single result

  Stream<Product> findAllByCategory(Category cat);
  // Must be used with try-with-resources inside @Transactional

  4. PROJECTIONS — PARTIAL DATA RETRIEVAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Interface-based projection (most common):
  public interface ProductSummary {
      String getName();
      BigDecimal getPrice();
  }

  List<ProductSummary> findByCategory(Category cat);

  → Spring generates proxy; Hibernate optimizes SELECT to only
    fetch name and price columns.

Class-based (DTO) projection:
  public record ProductDto(String name, BigDecimal price) {}

  @Query("SELECT new com.example.dto.ProductDto(p.name, p.price) " +
         "FROM Product p WHERE p.category = :cat")
  List<ProductDto> findDtoByCategory(@Param("cat") Category cat);

Dynamic projection (caller specifies type):
  <T> List<T> findByCategory(Category cat, Class<T> type);

  // Usage:
  repo.findByCategory(cat, ProductSummary.class);  // projection
  repo.findByCategory(cat, Product.class);          // full entity

Nested projections:
  public interface OrderSummary {
      Long getId();
      CustomerSummary getCustomer();  // nested projection

      interface CustomerSummary {
          String getFirstName();
          String getLastName();
      }
  }

  5. CUSTOM QUERY — @Query ANNOTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JPQL query:
  @Query("SELECT p FROM Product p WHERE p.price > :minPrice " +
         "AND p.category = :category")
  List<Product> findExpensive(@Param("minPrice") BigDecimal min,
                               @Param("category") Category cat);

Native SQL:
  @Query(value = "SELECT * FROM products WHERE price > :minPrice",
         nativeQuery = true)
  List<Product> findExpensiveNative(@Param("minPrice") BigDecimal min);

Modifying query (UPDATE/DELETE):
  @Modifying
  @Transactional
  @Query("UPDATE Product p SET p.price = p.price * :factor " +
         "WHERE p.category = :cat")
  int applyDiscount(@Param("factor") double factor,
                    @Param("cat") Category cat);

  @Modifying
  @Transactional
  @Query("DELETE FROM Product p WHERE p.expiresAt < :now")
  int deleteExpired(@Param("now") LocalDateTime now);

  ⚠️  @Modifying without clearAutomatically=true won't update
     first-level cache — stale data may be seen until context
     refresh. Use clearAutomatically = true for safety:
     @Modifying(clearAutomatically = true, flushAutomatically = true)

  6. SPECIFICATIONS (DYNAMIC QUERIES)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Extend JpaSpecificationExecutor<T> for criteria-based queries:

public interface ProductRepository
    extends JpaRepository<Product, Long>,
            JpaSpecificationExecutor<Product> {}

// Specification factory methods (best in a utility class)
public class ProductSpecs {

    public static Specification<Product> hasCategory(Category cat) {
        return (root, query, cb) ->
            cat == null ? cb.conjunction()
                        : cb.equal(root.get("category"), cat);
    }

    public static Specification<Product> priceBetween(
                BigDecimal min, BigDecimal max) {
        return (root, query, cb) ->
            cb.between(root.get("price"), min, max);
    }

    public static Specification<Product> nameContains(String keyword) {
        return (root, query, cb) ->
            keyword == null ? cb.conjunction()
                : cb.like(cb.lower(root.get("name")),
                           "%" + keyword.toLowerCase() + "%");
    }
}

// Compose and execute
Specification<Product> spec = where(hasCategory(ELECTRONICS))
        .and(priceBetween(new BigDecimal("100"), new BigDecimal("1000")))
        .and(nameContains("phone"));

Page<Product> result = repo.findAll(spec, PageRequest.of(0, 10));

  7. CUSTOM REPOSITORY IMPLEMENTATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Step 1: Define a custom interface
  public interface ProductRepositoryCustom {
      List<Product> findByComplexCriteria(SearchCriteria criteria);
  }

Step 2: Implement it (must end in "Impl")
  public class ProductRepositoryImpl implements ProductRepositoryCustom {
      @PersistenceContext
      private EntityManager em;

      @Override
      public List<Product> findByComplexCriteria(SearchCriteria criteria) {
          CriteriaBuilder cb = em.getCriteriaBuilder();
          CriteriaQuery<Product> q = cb.createQuery(Product.class);
          Root<Product> root = q.from(Product.class);
          // build predicates dynamically...
          return em.createQuery(q).getResultList();
      }
  }

Step 3: Extend both in the repository interface
  public interface ProductRepository
      extends JpaRepository<Product, Long>,
              ProductRepositoryCustom {}

  → Spring automatically discovers ProductRepositoryImpl
    by convention (interface name + "Impl" suffix)

  8. NAMED QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined on the entity class:
  @Entity
  @NamedQuery(name = "Product.findBySku",
              query = "SELECT p FROM Product p WHERE p.sku = :sku")
  public class Product { ... }

  // Then in repository (Spring Data matches by name):
  Optional<Product> findBySku(@Param("sku") String sku);

  Or use @NamedNativeQuery for SQL.
  Named queries are validated at startup — good for catching errors early.

Q: How does Spring Data generate query implementations from method names?
A: Spring Data uses a PartTree parser to analyze the method name, extract
   subject (find, count, delete) and criteria (ByName, AndPrice, etc.),
   then constructs a JPQL query or JPA CriteriaQuery accordingly.

Q: When should you use Specification vs derived query methods?
A: Derived queries are great for fixed, known predicates. Specifications
   shine when the query varies based on runtime conditions (optional
   filters, search forms), as they are composable and type-safe.

Q: What is a projection and why use it?
A: A projection selects only a subset of entity fields, reducing
   the amount of data fetched from DB. Interface projections allow
   Hibernate to optimize the SELECT list. DTO projections via @Query
   are even more efficient for complex mappings.

Q: What does @Modifying do in Spring Data?
A: It tells Spring Data the @Query is a modification operation
   (UPDATE/DELETE), not a SELECT. Without it, Spring throws
   InvalidDataAccessApiUsageException. It also supports
   clearAutomatically and flushAutomatically flags.

Q: What is the difference between findBy and getBy?
A: Both generate equivalent queries. Conventional: findBy for
   collections (List/Page/Slice) and getBy/readBy for single
   results. Modern convention prefers findBy everywhere.

Q: How do you implement dynamic sorting in Spring Data?
A: Pass a Sort object as a method parameter or include it in
   the Pageable. For derived queries:
   List<Product> findByCategory(Category cat, Sort sort);
   Called as: repo.findByCategory(cat, Sort.by("price").descending())

Q: Can you test Spring Data repositories in isolation?
A: Yes — use @DataJpaTest, which loads only JPA-related beans and
   uses an embedded database (H2 by default). It is much faster
   than @SpringBootTest.
