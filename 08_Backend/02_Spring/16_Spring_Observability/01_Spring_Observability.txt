SPRING OBSERVABILITY (SPRING BOOT 3)
=====================================

=== OVERVIEW ===

Spring Boot 3 introduced first-class observability through Micrometer Observation API.
Key change from Boot 2: Sleuth is GONE, replaced by Micrometer Tracing.

Observability pillars:
  Metrics → Micrometer (Prometheus, Datadog, etc.)
  Tracing → Micrometer Tracing (Zipkin, Jaeger, OTLP)
  Logging → SLF4J + MDC (trace/span IDs injected automatically)

All three are unified through the Observation API.

=== DEPENDENCIES ===

pom.xml (Spring Boot 3):
  <!-- Core observability (Micrometer + Actuator) -->
  <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-actuator</artifactId>
  </dependency>

  <!-- Micrometer Tracing bridge for Brave (Zipkin) -->
  <dependency>
      <groupId>io.micrometer</groupId>
      <artifactId>micrometer-tracing-bridge-brave</artifactId>
  </dependency>
  <dependency>
      <groupId>io.zipkin.reporter2</groupId>
      <artifactId>zipkin-reporter-brave</artifactId>
  </dependency>

  <!-- OR: OpenTelemetry bridge (for Jaeger/OTLP) -->
  <dependency>
      <groupId>io.micrometer</groupId>
      <artifactId>micrometer-tracing-bridge-otel</artifactId>
  </dependency>
  <dependency>
      <groupId>io.opentelemetry</groupId>
      <artifactId>opentelemetry-exporter-otlp</artifactId>
  </dependency>

  <!-- Prometheus metrics -->
  <dependency>
      <groupId>io.micrometer</groupId>
      <artifactId>micrometer-registry-prometheus</artifactId>
  </dependency>

=== OBSERVATION API ===

ObservationRegistry is the central entry point for creating observations.
An Observation can generate metrics AND traces simultaneously.

@Service
public class OrderService {

    private final ObservationRegistry observationRegistry;

    public Order createOrder(CreateOrderRequest req) {
        return Observation.createNotStarted("order.create", observationRegistry)
            .lowCardinalityKeyValue("order.type", req.getType())
            .highCardinalityKeyValue("customer.id", req.getCustomerId())
            .observe(() -> {
                // business logic here
                Order order = orderRepository.save(new Order(req));
                return order;
            });
    }
}

Low cardinality tags → added to metrics (few distinct values: "type=premium")
High cardinality tags → added to trace spans only (many distinct values: customer IDs)

=== @OBSERVED ANNOTATION ===

Spring AOP-based shortcut for observation:

@Configuration
@EnableMethodObservation  // enables @Observed AOP support
public class ObservabilityConfig { }

@Service
public class ProductService {

    @Observed(
        name = "product.fetch",
        contextualName = "fetching-product",
        lowCardinalityKeyValues = {"service", "product-service"}
    )
    public Product getProduct(String id) {
        return productRepository.findById(id).orElseThrow();
    }
}

@Observed automatically:
  - Creates a Micrometer span (trace)
  - Records metric: product.fetch (timer with success/failure tags)
  - Injects trace/span ID into MDC for log correlation

=== AUTO-INSTRUMENTED COMPONENTS ===

Spring Boot auto-instruments these out-of-the-box:
  - HTTP requests (Spring MVC, WebFlux) → http.server.requests metric + trace
  - HTTP client calls (RestTemplate, WebClient, RestClient) → trace propagation
  - Spring Data repositories → db query spans
  - Spring Messaging (Kafka, RabbitMQ) → message tracing
  - Spring Batch jobs/steps → job execution metrics
  - @Scheduled methods → scheduling metrics

=== TRACE PROPAGATION ===

Trace context is propagated across service boundaries via HTTP headers:
  Brave/B3 format:   X-B3-TraceId, X-B3-SpanId, X-B3-Sampled
  W3C TraceContext:  traceparent, tracestate (recommended standard)

Spring Boot auto-propagates these headers when using:
  - RestTemplate (bean, not new RestTemplate())
  - WebClient (builder-configured)
  - FeignClient
  - Kafka producers/consumers (via Spring Kafka)
  - RabbitMQ (via Spring AMQP)

=== MDC LOG CORRELATION ===

With Micrometer Tracing, traceId and spanId are automatically added to MDC.
Configure logback pattern to include them:

logback-spring.xml:
  <pattern>
      %d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level
      [traceId=%X{traceId}] [spanId=%X{spanId}]
      %logger{36} - %msg%n
  </pattern>

Output:
  2024-01-15 10:30:45 [http-nio-8080-exec-1] INFO
  [traceId=5b6b2d4a3c1f0e2a] [spanId=7f8e9a0b]
  com.example.OrderService - Creating order for customer 123

Search ELK/Splunk by traceId → see all logs from all services for one request.

=== CONFIGURATION ===

application.yml:
  management:
    tracing:
      sampling:
        probability: 1.0    # 1.0 = 100% sampling (dev); 0.1 = 10% (prod)
    endpoints:
      web:
        exposure:
          include: health, info, metrics, prometheus
    metrics:
      distribution:
        percentiles-histogram:
          http.server.requests: true   # enable histogram for latency percentiles

  logging:
    pattern:
      correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-}]"

  spring:
    zipkin:
      base-url: http://zipkin:9411

=== CUSTOM METRICS ===

@Component
public class OrderMetrics {
    private final Counter orderCounter;
    private final Timer orderTimer;
    private final Gauge activeOrderGauge;

    public OrderMetrics(MeterRegistry registry, OrderRepository repo) {
        this.orderCounter = Counter.builder("orders.created")
            .tag("region", "us-east")
            .description("Total orders created")
            .register(registry);

        this.orderTimer = Timer.builder("orders.processing.duration")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);

        Gauge.builder("orders.active", repo, OrderRepository::countActive)
            .register(registry);
    }

    public void recordOrderCreated() { orderCounter.increment(); }

    public void timeOrderProcessing(Runnable task) {
        orderTimer.record(task);
    }
}

=== SPRING BOOT 2 → 3 MIGRATION NOTE ===

Spring Boot 2 (with Spring Cloud Sleuth):
  spring-cloud-starter-sleuth → REMOVED
  spring-cloud-sleuth-zipkin → REMOVED
  Brave is still used internally but via Micrometer Tracing

Spring Boot 3:
  micrometer-tracing-bridge-brave (for Zipkin/Brave)
  micrometer-tracing-bridge-otel (for OpenTelemetry)
  No Spring Cloud Sleuth dependency needed

MDC keys changed:
  Sleuth: traceId, spanId (same keys, compatible)
  Micrometer: traceId, spanId (same, backward compatible for most log patterns)
