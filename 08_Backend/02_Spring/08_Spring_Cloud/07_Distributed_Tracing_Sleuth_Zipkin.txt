  1. WHY DISTRIBUTED TRACING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In microservices, a single user request may touch 10 services.
When something is slow or fails, it's hard to tell which service is at fault.

Distributed tracing assigns a single trace ID to a request and creates
span IDs for each service call. All logs across all services share the
same trace ID, enabling end-to-end visibility.

Key concepts:
  Trace ID → unique ID for the entire distributed request lifecycle
  Span     → unit of work within one service; has start time, end time, tags
  Parent Span → each service creates a child span of the calling service's span
  Baggage  → key-value pairs propagated with the trace context

  [API Gateway]        traceId=abc123, spanId=1111
    → [Order Service]  traceId=abc123, spanId=2222, parentSpanId=1111
      → [Payment]      traceId=abc123, spanId=3333, parentSpanId=2222
      → [Inventory]    traceId=abc123, spanId=4444, parentSpanId=2222

  2. SPRING CLOUD SLEUTH (Spring Boot 2.x — HISTORICAL CONTEXT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Cloud Sleuth was the distributed tracing library for Spring Boot 2.x.
It auto-instrumented RestTemplate, Feign, Kafka, RabbitMQ, and added
traceId/spanId to SLF4J MDC.

IMPORTANT: Spring Cloud Sleuth reached end of life in 2023.
For Spring Boot 3.x, use Micrometer Tracing instead (see next file).

Spring Boot 2.x / Sleuth dependency:
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-sleuth</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-sleuth-zipkin</artifactId>
</dependency>

# application.yml (Sleuth + Zipkin)
spring:
  zipkin:
    base-url: http://localhost:9411
  sleuth:
    sampler:
      probability: 1.0   # 100% sampling (use 0.1 = 10% in production)

What Sleuth did automatically:
  - Added X-B3-TraceId, X-B3-SpanId, X-B3-ParentSpanId headers to HTTP calls
  - Put traceId and spanId in MDC → appeared in logs:
    [order-service,abc123,2222] → [appName, traceId, spanId]
  - Instrumented RestTemplate, Feign, WebClient, Kafka consumer/producer

  3. ZIPKIN — THE TRACING BACKEND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Zipkin is an open-source distributed tracing system:
  - Receives spans via HTTP (default), Kafka, RabbitMQ
  - Stores spans in-memory (dev), Cassandra, Elasticsearch (production)
  - Provides UI to visualize traces, service dependency graph, latency histograms

Run Zipkin locally:
  docker run -d -p 9411:9411 openzipkin/zipkin

Zipkin UI: http://localhost:9411

Span data sent to Zipkin:
  - traceId, spanId, parentSpanId
  - service name, host, port
  - start timestamp, duration
  - tags (HTTP method, URL, status code)
  - annotations (events: cs=client-sent, cr=client-received, etc.)

  4. TRACE PROPAGATION FORMATS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Format          | Headers Used                              | Standard
----------------|-------------------------------------------|----------
B3 (Zipkin)     | X-B3-TraceId, X-B3-SpanId, X-B3-Sampled | Zipkin default
B3 Single       | b3: {traceId}-{spanId}-{flags}            | Compact B3
W3C TraceContext| traceparent, tracestate                   | IETF standard
OpenTelemetry   | traceparent (W3C) + OTLP export format    | CNCF standard

Sleuth supported B3 and W3C by default.
Micrometer Tracing (Spring Boot 3.x) uses OpenTelemetry / W3C TraceContext
and can export to Zipkin, Jaeger, or any OTLP-compatible backend.

  5. CUSTOM SPANS AND TAGS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Spring Cloud Sleuth (Spring Boot 2.x):
@Service
public class PaymentService {

    @Autowired
    private Tracer tracer;  // brave.Tracer from Sleuth

    public PaymentResult processPayment(PaymentRequest request) {
        // Create a custom child span
        Span span = tracer.nextSpan().name("payment-gateway-call");
        try (Tracer.SpanInScope ws = tracer.withSpanInScope(span.start())) {
            span.tag("payment.amount", request.getAmount().toString());
            span.tag("payment.currency", request.getCurrency());

            PaymentResult result = callPaymentGateway(request);
            span.tag("payment.result", result.getStatus());
            return result;

        } catch (Exception ex) {
            span.error(ex);
            throw ex;
        } finally {
            span.finish();
        }
    }
}

  6. LOG CORRELATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Sleuth automatically puts trace/span IDs into SLF4J MDC.
In logback/log4j2 pattern, include %X{traceId} and %X{spanId}:

# logback-spring.xml
<pattern>
    %d{HH:mm:ss.SSS} [%thread] %-5level [%X{traceId},%X{spanId}] %logger{36} - %msg%n
</pattern>

Sample log output:
  14:32:01.123 [http-nio-1] INFO  [abc12345,2222def3] OrderController - Creating order

Now you can grep by traceId across all service logs to reconstruct
the full request journey.

  7. SAMPLING STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In high-traffic production, tracing 100% of requests is expensive.
Use sampling to control what percentage gets traced.

  sampler.probability=1.0  → 100% (dev/staging)
  sampler.probability=0.1  → 10%  (production, high traffic)
  sampler.probability=0.0  → 0%   (tracing disabled)

Adaptive sampling: only trace requests that exceed a latency threshold,
or always trace error responses regardless of sampling rate.

  8. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the purpose of distributed tracing in microservices?
A: To track a single user request as it flows through multiple services.
   Each service logs with the same trace ID, so you can correlate logs,
   identify bottlenecks (which service is slow), find error sources, and
   visualize service dependency graphs.

Q: What is the difference between a Trace and a Span?
A: A Trace represents the entire journey of a request across all services
   (one trace = one traceId). A Span represents the work done by a single
   service (one service = one or more spans). Spans form a tree: each child
   span has a parentSpanId pointing to the caller's spanId.

Q: How does trace context propagate between services?
A: Via HTTP headers — the calling service includes X-B3-TraceId,
   X-B3-SpanId in the outgoing HTTP request. The receiving service reads
   these headers, creates a child span with the received traceId and
   parentSpanId, and continues. Sleuth/Micrometer handle this automatically
   for RestTemplate, WebClient, Feign, and Kafka.

Q: What is Zipkin and what alternative backends exist?
A: Zipkin is the most popular open-source tracing backend for Spring
   applications. Alternatives: Jaeger (CNCF, popular with Kubernetes),
   Tempo (Grafana stack), AWS X-Ray (managed), Datadog APM,
   Elastic APM. Micrometer Tracing supports OTLP export to any
   OpenTelemetry-compatible backend.

Q: Is Spring Cloud Sleuth still relevant?
A: No — Sleuth reached end of life in 2023. For Spring Boot 3.x,
   use Micrometer Tracing (part of the Spring Boot Actuator auto-configuration).
   The concepts (trace ID, span ID) are identical; only the API and
   library differ.
