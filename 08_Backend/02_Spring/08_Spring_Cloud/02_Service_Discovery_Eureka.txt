  1. WHY SERVICE DISCOVERY?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

In microservices, services run on dynamic IPs (containers, cloud).
Hard-coding IPs/ports doesn't work.

Without service discovery:
  Order Service → http://192.168.1.42:8081/inventory  (hardcoded — breaks on restart)

With service discovery:
  Services register by name to a Registry.
  Clients look up the name → get a list of healthy instances → call one.
  Order Service → lookup "inventory-service" → http://host-3:8083/inventory

  2. EUREKA ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Eureka Server  → Service registry (stores name → [instance list])
Eureka Client  → Each microservice; registers itself, renews heartbeat,
                 and fetches registry for service lookup

Flow:
  1. Service starts → sends POST /eureka/apps/{appName} to Eureka Server
  2. Eureka stores: appName, instanceId, host, port, status, metadata
  3. Client renews heartbeat every 30s (evicted after 90s without renewal)
  4. Clients fetch full registry at startup, then deltas every 30s
  5. Client looks up service by name → picks an instance (load balanced)

Eureka Self-Preservation Mode:
  Eureka stops evicting instances when it detects a significant drop in
  renewals (network partition scenario). Prevents mass de-registration
  during partial network failures.
  Disable in dev: eureka.server.enable-self-preservation=false

    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-server</artifactId>

@EnableEurekaServer
public class EurekaServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(EurekaServerApplication.class, args);
    }

# application.yml (Eureka Server)
server:
  port: 8761

spring:
  application:
    name: eureka-server

eureka:
  client:
    register-with-eureka: false      # server doesn't register itself
    fetch-registry: false            # server doesn't fetch from itself
  server:
    enable-self-preservation: false  # dev only

  5. CALLING SERVICES BY NAME — LOAD BALANCER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option A: @LoadBalanced RestTemplate

@Configuration
public class RestTemplateConfig {

    @Bean
    @LoadBalanced  // Spring Cloud LoadBalancer intercepts calls
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}

@Service
public class OrderService {

    @Autowired
    private RestTemplate restTemplate;

    public Inventory getInventory(Long productId) {
        // Use service name (not IP:port) — LoadBalancer resolves it
        return restTemplate.getForObject(
            "http://inventory-service/api/inventory/" + productId,
            Inventory.class
        );
    }
}

Option B: @LoadBalanced WebClient (reactive)

@Bean
@LoadBalanced
public WebClient.Builder webClientBuilder() {
    return WebClient.builder();
}

Run multiple Eureka servers — they peer-replicate:

# eureka-peer1 application.yml
spring:
  application:
    name: eureka-server
eureka:
  client:
    service-url:
      defaultZone: http://peer2:8762/eureka/,http://peer3:8763/eureka/
  instance:
    hostname: peer1

# All clients point to all Eureka nodes:
eureka:
  client:
    service-url:
      defaultZone: http://peer1:8761/eureka/,http://peer2:8762/eureka/

Even if one Eureka node goes down, clients have a cached registry
and can still resolve service names.

  7. HEALTH CHECK INTEGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

By default, Eureka uses heartbeat to determine if an instance is UP.
With Actuator, you can push the actual health status:

# application.yml
eureka:
  client:
    healthcheck:
      enabled: true   # push /actuator/health status to Eureka

management:
  endpoints:
    web:
      exposure:
        include: health, info
  endpoint:
    health:
      show-details: always

If health is DOWN (e.g., DB down), Eureka marks the instance as OUT_OF_SERVICE
and stops routing traffic to it — more accurate than heartbeat alone.

  8. INTERVIEW Q&A
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does Eureka differ from DNS-based service discovery?
A: Eureka maintains a registry with live health status and metadata.
   DNS doesn't inherently know if a service is healthy, and DNS TTLs
   can cause stale resolution. Eureka updates in near-real-time and
   supports health-aware load balancing. Cloud providers (AWS, GCP)
   also offer native service discovery alternatives.

Q: What is Eureka self-preservation mode?
A: When Eureka doesn't receive enough heartbeats (< 85% of expected),
   it assumes a network partition and stops evicting instances. This
   prevents mass de-registration of healthy instances during a network
   blip. In dev, disable it to see evictions happen quickly.

Q: How does @LoadBalanced work with Eureka?
A: @LoadBalanced wraps RestTemplate (or WebClient) with a
   LoadBalancerInterceptor. When you use a service name (e.g.,
   http://inventory-service/...), the interceptor calls
   Spring Cloud LoadBalancer which looks up instances from the
   cached Eureka registry and picks one using round-robin.

Q: What happens when Eureka Server is unavailable?
A: Each Eureka client caches the registry locally. If the server
   is temporarily unavailable, clients continue using the cached
   registry for service discovery. If the server is down for long,
   instances can't renew and may eventually be marked stale.

Q: What alternatives exist to Eureka?
A: Consul (by HashiCorp — key-value store + service mesh + health checks),
   Zookeeper (Apache — CP system), AWS Cloud Map, Kubernetes DNS-based
   discovery (Services + CoreDNS), Nacos (popular in Chinese ecosystem).
