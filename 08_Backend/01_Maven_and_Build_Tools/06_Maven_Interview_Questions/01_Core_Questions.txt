POM & PROJECT STRUCTURE
─────────────────────────────────────────────────────────────────────────────────

Q1: What is a POM file and what are its mandatory elements?
A:  POM (Project Object Model) is the fundamental unit of Maven — an XML file
    (pom.xml) that describes the project, its dependencies, build configuration,
    and metadata. Mandatory elements: <modelVersion> (always 4.0.0),
    <groupId>, <artifactId>, and <version>. Together these form the GAV
    coordinates that uniquely identify an artifact.

Q2: What is the Super POM?
A:  Every pom.xml implicitly inherits from the Super POM, which is bundled
    inside Maven itself. It defines: the standard directory layout (src/main/java,
    src/test/java), default plugin versions and configurations, default lifecycle
    bindings, and the Maven Central repository. View it with:
    mvn help:effective-pom

Q3: What is the effective POM?
A:  The effective POM is the result of merging the project's pom.xml with all
    parent POMs up to the Super POM. It shows the complete resolved configuration
    including all inherited plugins, dependencies, and properties.
    Command: mvn help:effective-pom

Q4: What is the difference between <dependencyManagement> and <dependencies>?
A:  <dependencies> directly adds a dependency to the project's classpath.
    <dependencyManagement> only declares a version and scope for an artifact —
    it does NOT add the dependency to the classpath. Child modules (or the same
    POM) must still declare the dependency in <dependencies> to actually use it,
    but they can omit the version (it's inherited from dependencyManagement).
    Used in parent POMs to centralize version management.

Q5: What is the difference between <pluginManagement> and <plugins>?
A:  <plugins> in <build> actually runs the plugin during the build.
    <pluginManagement> only pre-configures a plugin (version, config) without
    running it. Child modules inherit the pluginManagement configuration but
    must declare the plugin in their own <plugins> section to actually activate it.

LIFECYCLE & PHASES
─────────────────────────────────────────────────────────────────────────────────

Q6: What are Maven's three build lifecycles?
A:  1. default — the main build lifecycle: validate → compile → test → package
                  → verify → install → deploy
    2. clean   — cleans build outputs: pre-clean → clean → post-clean
    3. site    — generates project documentation: pre-site → site → post-site
                  → site-deploy
    Each lifecycle is a sequence of phases. Running a phase runs all previous
    phases in that lifecycle first.

Q7: What is the difference between a phase and a goal?
A:  A phase is a step in the Maven lifecycle (e.g., compile, test, package).
    A goal is a specific action provided by a plugin (e.g., compiler:compile,
    surefire:test). Goals are bound to phases. Running a phase (mvn compile)
    executes all goals bound to that phase and all preceding phases.
    You can also run a goal directly: mvn compiler:compile (skips lifecycle).

Q8: What happens when you run "mvn package"?
A:  Maven runs all phases from the beginning of the default lifecycle up to and
    including "package": validate → initialize → generate-sources →
    process-sources → generate-resources → process-resources → compile →
    process-classes → generate-test-sources → process-test-sources →
    generate-test-resources → process-test-resources → test-compile →
    process-test-classes → test → prepare-package → package.
    The result is a JAR/WAR file in target/.

Q9: What is the difference between "mvn install" and "mvn deploy"?
A:  mvn install runs the build and copies the artifact to the LOCAL Maven
    repository (~/.m2/repository/). Makes it available to other local projects.
    mvn deploy does everything install does, plus uploads the artifact to the
    REMOTE repository configured in <distributionManagement>. Used in CI.

Q10: How do you skip tests in Maven? What is the difference between two approaches?
A:  -DskipTests  — skips test EXECUTION but still compiles test classes
    -Dmaven.test.skip=true — skips BOTH compilation and execution of tests
    Use -DskipTests when you want the test classes available (e.g., for IDE
    debugging) but don't want to run them. Use maven.test.skip=true for the
    fastest possible build (skips compileTestJava).

DEPENDENCY SCOPES
─────────────────────────────────────────────────────────────────────────────────

Q11: What are Maven's dependency scopes?
A:  • compile  — default; available in all classpaths (compile, test, runtime);
                 packaged in JAR/WAR; transitively included
    • provided  — compile + test classpaths; NOT packaged (container provides at runtime);
                  not transitive. Example: servlet-api, Lombok
    • runtime   — runtime + test classpaths; packaged; not visible at compile time.
                  Example: JDBC driver (code uses java.sql interfaces only)
    • test      — test compile + runtime only; NOT packaged. Example: JUnit, Mockito
    • system    — like provided but requires <systemPath> (avoid — not portable)
    • import    — only in <dependencyManagement>; imports a BOM's version management

Q12: Why is Lombok's scope "provided"?
A:  Lombok generates code at compile time via annotation processing. The Lombok JAR
    is only needed during compilation — the generated bytecode has no runtime
    dependency on Lombok. Marking it "provided" means: include on the compile
    classpath but do NOT package it in the JAR/WAR (reducing artifact size and
    avoiding unnecessary runtime classpath entries).

Q13: Why would you use "runtime" scope for a JDBC driver?
A:  Your code uses only the java.sql.* interfaces (java.sql.Connection,
    java.sql.PreparedStatement), which are part of the JDK. The JDBC driver
    implementation (e.g., org.postgresql:postgresql) is only needed at runtime
    via java.util.ServiceLoader or Class.forName(). Since it's never referenced
    in source code, it's not needed at compile time — "runtime" scope is correct.

─────────────────────────────────────────────────────────────────────────────────
PLUGINS
─────────────────────────────────────────────────────────────────────────────────

Q14: What is a Maven plugin and how does it work?
A:  A Maven plugin is a collection of goals (Mojos — Maven plain Old Java Objects).
    Each Mojo implements a specific action. Plugins are bound to lifecycle phases
    in the POM (or by default by the packaging type). When Maven runs a lifecycle
    phase, it executes all goals bound to that and preceding phases in order.

Q15: What plugins are essential for a Spring Boot project?
A:  • spring-boot-maven-plugin — packages the app as an executable fat JAR,
      provides spring-boot:run goal for local development
    • maven-compiler-plugin — compile with Java 21, annotation processing
    • maven-surefire-plugin — run unit tests (JUnit 5 requires 3.x)
    • maven-failsafe-plugin — run integration tests (verify phase)
    • maven-resources-plugin — handle src/main/resources with filtering

Q16: What does the Maven Shade plugin do?
A:  It creates an "uber JAR" (fat JAR) that includes all dependencies inside the
    JAR, producing a single deployable artifact. Key features: class relocation
    (repackages deps to avoid classpath conflicts), manifest transformation (sets
    Main-Class), service transformer (merges META-INF/services files).
    For Spring Boot apps, the spring-boot-maven-plugin is preferred over Shade.

REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

Q17: What is the difference between local, central, and remote repositories?
A:  Local — ~/.m2/repository/ on your machine. Maven always checks here first.
    Central — Maven Central (repo.maven.apache.org). The default remote repo for
              all open-source Java libraries. Managed by Sonatype.
    Remote — any other repository: your corporate Nexus/Artifactory, Spring repos,
              JBoss repos, etc. Declared in pom.xml or settings.xml.
    Resolution order: local → remote (declared order) → central.

Q18: What is a mirror in Maven settings.xml?
A:  A mirror redirects all requests matching a mirrorOf pattern to a different URL.
    Most common use: redirect all requests to a corporate Nexus proxy instead of
    going to Maven Central directly. This centralizes caching and allows companies
    to apply security policies on dependency downloads.
    mirrorOf="*" → all repos, mirrorOf="central" → Central only,
    mirrorOf="*,!internal-repo" → all except internal-repo.

PROPERTIES
─────────────────────────────────────────────────────────────────────────────────

Q19: What types of properties can be used in Maven?
A:  • Project properties: ${project.version}, ${project.groupId}, ${project.artifactId}
    • POM-defined: <properties><my.version>1.0</my.version></properties> → ${my.version}
    • Settings properties: ${settings.localRepository}
    • Environment variables: ${env.HOME}, ${env.JAVA_HOME}
    • System properties: ${java.version}, ${user.home}
    • Command-line: mvn -Dproperty=value → ${property}

Q20: What does "resource filtering" do in Maven?
A:  When filtering is enabled on a resource directory, Maven replaces ${variable}
    placeholders in resource files (properties, YAML, XML) with their Maven
    property values at build time. Useful for injecting version numbers, build
    timestamps, or environment-specific values into application.properties.
    <resources><resource><filtering>true</filtering></resource></resources>
