RELEASE PROCESS
─────────────────────────────────────────────────────────────────────────────────

Q1: Walk me through the Maven release process using the maven-release-plugin.
A:  The release plugin has two main goals:
    release:prepare — (1) checks for SNAPSHOT dependencies (fails if any),
    (2) replaces SNAPSHOT version with release version in pom.xml,
    (3) runs the build to verify it compiles and tests pass,
    (4) commits the release pom to SCM, (5) tags the commit in SCM,
    (6) bumps the version to the next SNAPSHOT, (7) commits again.
    release:perform — (1) checks out the SCM tag, (2) builds the project,
    (3) deploys to the remote repository, (4) cleans up workspace.
    Problems with this plugin: slow (builds twice), requires SCM access, creates
    two commits and a tag atomically. Many teams prefer a "Git Flow" or
    GitHub Actions-based release that avoids the plugin.

Q2: What is semantic versioning and how does it apply to Maven?
A:  SemVer: MAJOR.MINOR.PATCH
    MAJOR — breaking change (API incompatibility)
    MINOR — new backwards-compatible features
    PATCH — backwards-compatible bug fixes
    Pre-release: 1.0.0-SNAPSHOT (dev), 1.0.0-RC1 (release candidate)
    Maven compares versions lexicographically with some special rules:
    SNAPSHOT < 1.0-alpha < 1.0-beta < 1.0-RC1 < 1.0 < 1.0.1
    Maven's <versionRange> in plugin configurations uses [min,max) notation.

Q3: What is the flatten-maven-plugin and why is it needed with CI-friendly versioning?
A:  With CI-friendly versioning, pom.xml contains ${revision} as the version.
    When Maven installs/deploys the artifact, the POM is uploaded as-is — with
    the literal ${revision} placeholder. When consumers try to use that POM,
    Maven cannot resolve ${revision} → broken dependency resolution.
    The flatten-maven-plugin replaces all property placeholders in the POM
    with their resolved values BEFORE installing/deploying, creating a "flat"
    POM without property references. Essential for CI-friendly versioning.

SETTINGS & SECURITY
─────────────────────────────────────────────────────────────────────────────────

Q4: How do you encrypt repository credentials in Maven?
A:  Maven supports master password encryption in settings.xml:
    1. Create master password: mvn --encrypt-master-password <password>
       → stores {master-encrypted-value} in ~/.m2/settings-security.xml
    2. Encrypt the server password: mvn --encrypt-password <password>
       → use the output {encrypted-value} in settings.xml <password>
    3. settings.xml stores only encrypted values — safe to commit to SCM
    Alternative (modern, CI-preferred): store credentials as environment variables
    and reference them in settings.xml as ${env.NEXUS_PASSWORD}.

Q5: Where can Maven profiles be defined and what are the activation mechanisms?
A:  Defined in: pom.xml, ~/.m2/settings.xml (user-global), Maven install settings.xml
    Activation mechanisms:
    1. CLI: mvn -P profile-name (explicit activation)
    2. Property: <activation><property><name>env</name><value>prod</value></property></activation>
    3. File presence/absence: <activation><file><exists>config.xml</exists></file></activation>
    4. OS: <activation><os><name>Windows 11</name><arch>amd64</arch></os></activation>
    5. JDK version: <activation><jdk>[21,)</jdk></activation>
    6. activeByDefault: true (active unless any other profile is activated)

ARTIFACT REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

Q6: What is the difference between Nexus Repository Manager and Artifactory?
A:  Both are enterprise artifact repository managers with similar core features.
    Nexus (Sonatype): Originally called Sonatype Nexus; has Nexus IQ (security
    scanning). Repository types: hosted, proxy, group. Free OSS version (Nexus OSS).
    Artifactory (JFrog): More commercial; deep CI/CD integration (JFrog Pipeline);
    JFrog Xray for security; virtual repositories. Tighter IDE/build tool plugins.
    Both support Maven, npm, PyPI, Docker, Helm and more. Choice often driven
    by enterprise licensing, existing infrastructure, or security tooling needs.

Q7: What repository types does Nexus support and how do they work?
A:  Hosted — stores artifacts you publish (your releases, snapshots)
    Proxy — caches artifacts from a remote repo (Maven Central, Spring repos).
    When an artifact is requested, Nexus checks its cache; on miss, fetches
    from the remote and caches it.
    Group — a virtual repo that aggregates hosted + proxy repos into a single URL.
    Developers configure just the group URL — Nexus searches all member repos.
    Typical setup: hosted-releases + hosted-snapshots + proxy-central → public-group

CI/CD & PERFORMANCE
─────────────────────────────────────────────────────────────────────────────────

Q8: What Maven flags should you always use in CI/CD pipelines?
A:  -B (--batch-mode) — disables interactive prompts; formats output without ANSI
    colors; essential for CI log readability
    -fae (--fail-at-end) — build all modules even if some fail; then report all
    failures at once (vs default: stop on first failure)
    -T 1C — parallel module build using 1 thread per CPU core (check plugin safety)
    --no-transfer-progress — suppresses verbose artifact download progress bars
    -Dorg.slf4j.simpleLogger.log.org.apache.maven.cli.transfer.Slf4jMavenTransferListener=warn
    — alternative way to quiet transfer logs
    Also important: use the Maven Wrapper (./mvnw) so CI uses the committed version.

Q9: How do you set up Maven dependency caching in GitHub Actions?
A:  Use the actions/setup-java action with cache: 'maven':
    - uses: actions/setup-java@v4
      with:
        java-version: '21'
        distribution: 'temurin'
        cache: 'maven'             # automatically caches ~/.m2/repository
    This hashes pom.xml files and restores the cache on subsequent runs.
    Alternatively, use actions/cache directly with key: hashFiles('**/pom.xml').
    For Gradle: cache: 'gradle' hashes *.gradle.kts and libs.versions.toml.

Q10: What is SonarQube and how do you integrate it with Maven?
A:  SonarQube is a static code analysis platform that measures code quality
    (bugs, code smells, security hotspots, test coverage, duplications).
    Maven integration:
    mvn sonar:sonar \
      -Dsonar.projectKey=my-app \
      -Dsonar.host.url=https://sonar.example.com \
      -Dsonar.login=${SONAR_TOKEN}
    Typically run after the verify phase (so coverage data from JaCoCo is available).
    In GitHub Actions, use the sonarqube-scan-action or run sonar:sonar directly.

DEPENDENCY MANAGEMENT ADVANCED
─────────────────────────────────────────────────────────────────────────────────

Q11: What is a BOM (Bill of Materials) and when should you create one?
A:  A BOM is a Maven POM with packaging=pom that contains only <dependencyManagement>
    entries — version declarations for a set of related artifacts. Consumers import
    it with scope=import in their <dependencyManagement>. Create a BOM when:
    (1) you publish multiple related artifacts that must be used together
    (e.g., jackson-core, jackson-databind, jackson-annotations should share versions),
    (2) you want to centralize version management for your organization's internal libs,
    (3) you provide a platform for others to build on (like Spring Boot does).

Q12: What happens with transitive BOMs — does importing a BOM import the BOMs it imports?
A:  Yes — when a BOM imports another BOM (scope=import), and you import that first
    BOM, you also get the effect of the nested BOM imports transitively. However,
    entries in the outer BOM take precedence over the nested BOMs. This is how
    spring-boot-dependencies works — it imports multiple BOMs (Spring Framework BOM,
    Jackson BOM, etc.) and you get all of their version management with a single import.

Q13: How do you deal with a CVE in a transitive dependency you cannot easily upgrade?
A:  Options (in order of preference):
    1. Upgrade the direct dependency that pulls in the vulnerable transitive —
       often the new version of the direct dep upgrades it too.
    2. Add the vulnerable artifact explicitly with a patched version in
       <dependencyManagement> — pins the version without needing exclusions.
    3. Use an exclusion + explicit patched dep:
       Exclude the vulnerable transitive, then add the patched version directly.
    4. Suppress in OWASP Dependency-Check with documented justification (last resort)
       if you've verified the vulnerability is not exploitable in your use case.
    Document all version pins with a comment explaining the CVE number and fix version.

TROUBLESHOOTING
─────────────────────────────────────────────────────────────────────────────────

Q14: A build that worked locally fails in CI with dependency resolution errors.
     What do you check?
A:  1. Maven version mismatch — use ./mvnw to ensure same version everywhere
    2. settings.xml differences — CI uses /etc/maven/settings.xml; developer uses
       ~/.m2/settings.xml. Check mirrors, server credentials, proxy settings
    3. Repository availability — is the corporate Nexus accessible from CI?
       Check NEXUS_URL env var, credentials, network access
    4. SNAPSHOT freshness — CI might use --no-snapshot-updates; add -U to force check
    5. Offline mode — CI might pass --offline or -o; remove if dependencies not cached
    6. Local repo corruption — CI may have stale .lastUpdated files; run with
       mvn dependency:purge-local-repository or delete the cache
    7. Java version — CI might use different JDK; verify with: mvn -version

Q15: What is "NoSuchMethodError" or "ClassNotFoundException" at runtime despite
     a successful build, and how do you diagnose it?
A:  These are classpath conflicts — two versions of the same class are on the
    classpath; the wrong one was loaded at runtime.
    Diagnosis:
    mvn dependency:tree -Dverbose | grep -i <artifact>
    Look for "omitted for conflict" lines — Maven picked a version you didn't expect.
    Also check: mvn dependency:analyze for used-undeclared deps.
    Fix: Declare the correct version in <dependencyManagement>, or use exclusions
    to remove the conflicting version, then add the correct one directly.
    At runtime: add -verbose:class to JVM args to see which JAR loaded the class.
