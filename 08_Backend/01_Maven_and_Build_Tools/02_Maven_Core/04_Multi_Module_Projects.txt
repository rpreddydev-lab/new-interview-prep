================================================================================
  MAVEN MULTI-MODULE PROJECTS
================================================================================

WHAT IS A MULTI-MODULE PROJECT?
────────────────────────────────
A multi-module Maven project (also called a "multi-module build" or "reactor build")
is a collection of related Maven projects managed together under a single parent POM.

It enables:
  • Building all modules with a single command
  • Sharing common configuration (plugins, dependencies, properties) via parent POM
  • Managing internal dependencies between modules
  • Consistent versioning across all modules

─────────────────────────────────────────────────────────────────────────────────
TYPICAL STRUCTURE
─────────────────────────────────────────────────────────────────────────────────

  e-commerce-platform/          ← Root aggregator (parent) pom.xml
  ├── pom.xml                   ← packaging=pom, lists all modules
  ├── common-utils/             ← Shared utilities module
  │   ├── pom.xml               ← Has <parent> pointing to root
  │   └── src/...
  ├── product-service/          ← Business domain module
  │   ├── pom.xml
  │   └── src/...
  ├── order-service/
  │   ├── pom.xml
  │   └── src/...
  ├── api-gateway/
  │   ├── pom.xml
  │   └── src/...
  └── parent-pom/               ← (optional) Pure parent POM, not aggregator
      └── pom.xml

─────────────────────────────────────────────────────────────────────────────────
ROOT AGGREGATOR POM
─────────────────────────────────────────────────────────────────────────────────

  The root pom.xml has:
  • <packaging>pom</packaging>  — no source code, just configuration
  • <modules> list              — declares all child module directories

  <?xml version="1.0" encoding="UTF-8"?>
  <project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>e-commerce-platform</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>pom</packaging>   <!-- CRITICAL: must be "pom" -->

    <name>E-Commerce Platform</name>

    <!-- Common properties for all modules -->
    <properties>
      <java.version>21</java.version>
      <maven.compiler.source>${java.version}</maven.compiler.source>
      <maven.compiler.target>${java.version}</maven.compiler.target>
      <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
      <spring.boot.version>3.2.0</spring.boot.version>
    </properties>

    <!-- BOM imports apply to all children -->
    <dependencyManagement>
      <dependencies>
        <dependency>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-dependencies</artifactId>
          <version>${spring.boot.version}</version>
          <type>pom</type>
          <scope>import</scope>
        </dependency>
        <!-- Reference internal modules here to manage their versions -->
        <dependency>
          <groupId>com.example</groupId>
          <artifactId>common-utils</artifactId>
          <version>${project.version}</version>
        </dependency>
      </dependencies>
    </dependencyManagement>

    <!-- Common plugins for all modules -->
    <build>
      <pluginManagement>
        <plugins>
          <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.11.0</version>
          </plugin>
          <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.1.2</version>
          </plugin>
        </plugins>
      </pluginManagement>
    </build>

    <!-- List all child modules (must match directory names) -->
    <modules>
      <module>common-utils</module>
      <module>product-service</module>
      <module>order-service</module>
      <module>api-gateway</module>
    </modules>

  </project>

─────────────────────────────────────────────────────────────────────────────────
CHILD MODULE POM
─────────────────────────────────────────────────────────────────────────────────

  Each child module's pom.xml has a <parent> section referencing the root POM:

  <?xml version="1.0" encoding="UTF-8"?>
  <project>
    <modelVersion>4.0.0</modelVersion>

    <!-- Inherit from parent -->
    <parent>
      <groupId>com.example</groupId>
      <artifactId>e-commerce-platform</artifactId>
      <version>1.0.0-SNAPSHOT</version>
      <relativePath>../pom.xml</relativePath>  <!-- path to parent pom.xml -->
    </parent>

    <!-- Only artifactId needed; groupId and version inherited -->
    <artifactId>product-service</artifactId>
    <packaging>jar</packaging>  <!-- or war, or omit for default jar -->

    <dependencies>
      <!-- Use internal module as dependency — version managed by parent -->
      <dependency>
        <groupId>com.example</groupId>
        <artifactId>common-utils</artifactId>
        <!-- No version needed: managed in parent's <dependencyManagement> -->
      </dependency>
      <!-- External deps — versions managed by BOM imported in parent -->
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
      </dependency>
    </dependencies>

    <build>
      <plugins>
        <plugin>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-maven-plugin</artifactId>
          <!-- Config inherited from parent's pluginManagement if declared there -->
        </plugin>
      </plugins>
    </build>

  </project>

─────────────────────────────────────────────────────────────────────────────────
REACTOR — BUILD ORDER AND DEPENDENCY RESOLUTION
─────────────────────────────────────────────────────────────────────────────────

  The REACTOR is Maven's mechanism for building multi-module projects.
  It analyzes inter-module dependencies and determines the correct build order.

  If order-service depends on common-utils, Maven automatically builds
  common-utils BEFORE order-service, regardless of the order in <modules>.

  Example output:
  [INFO] Reactor Build Order:
  [INFO]   e-commerce-platform [pom]
  [INFO]   common-utils [jar]
  [INFO]   product-service [jar]
  [INFO]   order-service [jar]   ← built after common-utils
  [INFO]   api-gateway [jar]

─────────────────────────────────────────────────────────────────────────────────
USEFUL REACTOR COMMANDS
─────────────────────────────────────────────────────────────────────────────────

  # Build the entire project
  mvn clean install

  # Build a specific module (and all its dependencies: -am = also-make)
  mvn -pl order-service -am clean install

  # Build a specific module and all modules that depend on it (-amd = also-make-dependents)
  mvn -pl common-utils -amd clean install

  # Build multiple specific modules
  mvn -pl product-service,order-service -am clean install

  # Skip building the root module (useful for monorepos)
  mvn -pl !e-commerce-platform clean install

  # Build from a specific directory recursively
  mvn -f order-service/pom.xml clean install

  # Resume a failed build from a specific module
  mvn -rf :order-service clean install   # -rf = resume-from

  # Build in parallel (N threads or 1 per CPU core with "1C")
  mvn -T 4 clean install            # 4 threads
  mvn -T 1C clean install           # 1 thread per CPU core

─────────────────────────────────────────────────────────────────────────────────
AGGREGATOR vs PARENT
─────────────────────────────────────────────────────────────────────────────────

  These are two separate concerns that are often combined in the root POM but
  can also be separate POMs:

  AGGREGATOR POM:
  • Has <modules> listing child directories
  • Enables building all modules with one command from the root
  • Does NOT have to be the parent of those modules

  PARENT POM:
  • Referenced via <parent> in child POMs
  • Provides inherited configuration (properties, dependencyManagement, plugins)
  • Does NOT have to aggregate modules

  Combined (most common — single root pom.xml does both):
  <packaging>pom</packaging>
  <modules>...</modules>     ← aggregation
  <dependencyManagement>...  ← parenting
  <pluginManagement>...

  Separate (large enterprise pattern):
  ├── company-parent/pom.xml          ← Just a parent (BOM, common config)
  └── e-commerce-platform/pom.xml     ← Just an aggregator (lists modules)
      ├── <parent> → company-parent
      └── <modules> → [product-service, order-service, ...]

─────────────────────────────────────────────────────────────────────────────────
INHERITANCE RULES
─────────────────────────────────────────────────────────────────────────────────

  Child modules INHERIT from parent:
  ✔ groupId (if not overridden)
  ✔ version (if not overridden)
  ✔ <properties>
  ✔ <dependencyManagement>
  ✔ <pluginManagement>
  ✔ <repositories>
  ✔ <distributionManagement>

  Child modules do NOT automatically inherit:
  ✗ <dependencies> (these would be added to every single child — bad!)
  ✗ <plugins> (would run in every child — bad!)

  This is intentional: parent manages VERSIONS, children declare USAGE.
  Only put <dependencies> in parent if truly every child needs them.

─────────────────────────────────────────────────────────────────────────────────
MANAGING VERSIONS ACROSS MODULES
─────────────────────────────────────────────────────────────────────────────────

  All modules in a multi-module project should typically share the same version.
  Use the versions plugin to update all at once:

  # Set new version on root and all child modules:
  mvn versions:set -DnewVersion=2.0.0-SNAPSHOT
  mvn versions:commit   # Remove backup pom files

  # Alternative: use -DprocessAllModules=true
  mvn versions:set -DnewVersion=2.0.0-SNAPSHOT -DprocessAllModules=true

  # Or use the older tycho/releng approach with a batch script

  For CI/CD, use the ${revision} property (Maven 3.5+):
  Root POM:
  <version>${revision}</version>
  <properties>
    <revision>1.0.0-SNAPSHOT</revision>
  </properties>
  
  Build with: mvn -Drevision=1.2.3 clean deploy
  (Each child POM also uses ${revision} via ${project.version})
  Requires the flatten-maven-plugin to resolve for deployment.

─────────────────────────────────────────────────────────────────────────────────
SPRING BOOT IN MULTI-MODULE PROJECTS
─────────────────────────────────────────────────────────────────────────────────

  Common pattern: Spring Boot parent POM + custom modules

  Option A: Inherit from spring-boot-starter-parent
  ──────────────────────────────────────────────────
  Root pom.xml:
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.0</version>
  </parent>

  Pro: Very simple, gets all Spring Boot configuration for free
  Con: Can only have one parent; can't use your company's parent POM

  Option B: Import spring-boot-dependencies BOM (recommended for multi-module)
  ────────────────────────────────────────────────────────────────────────────
  Root pom.xml (inheriting from company parent, importing Spring Boot BOM):
  <parent>
    <groupId>com.example</groupId>
    <artifactId>company-parent</artifactId>
    <version>5.0.0</version>
  </parent>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.2.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  Pro: Can still use your own parent POM
  Con: Slightly more verbose; need to add spring-boot-maven-plugin manually

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is a Maven multi-module project?
A: A collection of Maven projects managed together under a parent/aggregator POM.
   The root POM has <packaging>pom</packaging> and lists child modules in <modules>.
   Maven's reactor analyzes inter-module dependencies and builds them in the correct
   order. All modules share common configuration inherited from the parent POM.

Q: What is the Maven Reactor?
A: The Reactor is Maven's component that handles multi-module builds. It reads all
   module POMs, determines their inter-dependencies, builds a directed acyclic graph,
   and executes builds in topological order (dependencies before dependents).

Q: What is the difference between an aggregator POM and a parent POM?
A: An aggregator POM lists child modules (<modules>) so Maven can build them all
   together. A parent POM provides shared configuration via inheritance (<parent>).
   These are usually the same POM but can be separate. Aggregation is about BUILD
   COORDINATION; parenting is about CONFIGURATION INHERITANCE.

Q: How do you build only a specific module in a multi-module project?
A: Use: mvn -pl <module-name> -am clean install
   -pl specifies which modules to build.
   -am (also-make) also builds modules that the selected module depends on.
   -amd (also-make-dependents) builds modules that depend on the selected module.

Q: How do you manage dependency versions across all modules?
A: Declare versions in the parent POM's <dependencyManagement>. Child modules
   declare dependencies without versions — they inherit them from the parent.
   Use "mvn versions:set -DnewVersion=X.Y.Z" to update all modules at once.

Q: What is the difference between <dependencies> and <dependencyManagement> in a
   parent POM?
A: <dependencyManagement> centralizes versions — it does NOT add dependencies to
   child modules. <dependencies> in a parent POM are inherited by ALL children.
   Only put things in parent <dependencies> if truly every single child needs them
   (e.g., test dependencies like JUnit if you want them everywhere). Prefer
   <dependencyManagement> + child <dependencies> for explicit control.
