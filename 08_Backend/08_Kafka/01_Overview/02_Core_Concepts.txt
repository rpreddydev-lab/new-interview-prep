1. TOPICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A TOPIC is a named, logical channel to which producers write and from which
  consumers read. Think of it as a category or feed name.

Key properties:
  - Topics are identified by name (e.g., "orders", "user-events", "payments")
  - Topics are split into PARTITIONS for scalability
  - Topics can be replicated across brokers for fault-tolerance
  - Topics have a configurable retention period (time-based or size-based)
  - Topics are NOT queues — multiple consumers can read the same topic

Topic naming best practices (interview talking point):
  - Use lowercase with hyphens: "user-signup-events" (not "UserSignupEvents")
  - Be descriptive: <domain>-<entity>-<event-type> e.g., "payment-transactions-processed"
  - Avoid generic names like "events" or "messages"

Creating a topic (CLI):
  kafka-topics.sh --create \
    --bootstrap-server localhost:9092 \
    --topic orders \
    --partitions 6 \
    --replication-factor 3

Topic configuration (important config keys):
  retention.ms          = 604800000  (7 days, default)
  retention.bytes       = -1         (unlimited size by default)
  cleanup.policy        = delete | compact
  min.insync.replicas   = 2          (minimum ISR for acks=all)
  segment.bytes         = 1073741824 (1 GB per log segment)

2. PARTITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A PARTITION is the fundamental unit of parallelism and ordering in Kafka.
  Each topic is divided into one or more partitions.

Key properties:
  - Each partition is an ordered, immutable sequence of records
  - Records within a partition have a unique sequential offset (0, 1, 2, ...)
  - Partitions are distributed across brokers
  - ONE consumer per partition per consumer group at any time
  - Ordering is guaranteed WITHIN a partition, not across partitions

Partition assignment:
  - If message has a key → partition = hash(key) % numPartitions
  - If message has no key → round-robin across partitions (pre-2.4)
    or sticky partitioning (2.4+) for batching efficiency

Choosing the right number of partitions:
  - More partitions = more parallelism = higher throughput
  - More partitions = more memory, file handles, leader election overhead
  - Rule of thumb: max(desired_throughput_MB/s ÷ consumer_throughput_MB/s, 
                       desired_throughput_MB/s ÷ producer_throughput_MB/s)
  - Common starting point: 3-12 partitions for most use cases
  - LinkedIn / Uber use topics with hundreds of partitions

WARNING: You CAN increase partitions but CANNOT decrease them (without
         deleting and recreating the topic). Increasing partitions breaks
         key-based ordering guarantees for existing keys.

Partition diagram:
  Topic: orders (3 partitions)
  
  Partition 0: [offset 0] [offset 1] [offset 2] [offset 3] → ...
  Partition 1: [offset 0] [offset 1] [offset 2]             → ...
  Partition 2: [offset 0] [offset 1] [offset 2] [offset 3] [offset 4] → ...

3. OFFSETS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  An OFFSET is a unique, monotonically increasing integer that identifies
  a record's position within a partition.

Types of offsets:
  - Log-end offset (LEO): The offset of the NEXT record to be written
  - High-watermark (HW): The last offset replicated to ALL ISR replicas
  - Current consumer offset: Where a consumer group is currently reading
  - Committed offset: The last offset explicitly committed by consumer

Offset storage:
  - Before Kafka 0.9: Stored in ZooKeeper
  - Kafka 0.9+: Stored in internal topic __consumer_offsets (default)
    - Compacted topic with 50 partitions by default
    - Key: <group-id, topic, partition>; Value: <offset, metadata, timestamp>

Consumer offset types:
  - auto.offset.reset = "earliest" → start from offset 0
  - auto.offset.reset = "latest"   → start from the latest (new messages only)
  - auto.offset.reset = "none"     → throw exception if no committed offset

Offset management strategies:
  1. Auto-commit (enable.auto.commit=true): periodic background commit
     - Risky: can cause duplicates if crash before next commit
  2. Manual sync commit (commitSync()): blocks until broker acknowledges
     - Slower but safer
  3. Manual async commit (commitAsync()): fire-and-forget
     - Faster but no retry on failure
  4. Manual per-partition commit: most fine-grained control

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. BROKERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A BROKER is a Kafka server. It receives messages from producers, stores them
  on disk, and serves them to consumers.

Key responsibilities:
  - Store partition data (log files on disk)
  - Handle producer requests (receive, replicate, acknowledge)
  - Handle consumer fetch requests
  - Participate in replication (as leader or follower)
  - Manage partition leader election (in KRaft mode, via the controller quorum)

Cluster composition:
  - A Kafka cluster has multiple brokers (e.g., 3, 5, or more)
  - Each broker has a unique broker.id
  - One broker acts as the CONTROLLER (metadata management)
  - Each partition has one LEADER broker and N-1 FOLLOWER brokers

Broker storage:
  - Data stored in log.dirs (e.g., /var/kafka/data)
  - Each partition is a directory: /var/kafka/data/orders-0/
  - Inside: segment files (.log), index files (.index), timeindex (.timeindex)

5. PRODUCERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A PRODUCER is a client application that publishes (writes) records to Kafka
  topics.

Key concepts:
  - Producers decide which partition to send a message to
  - Producers batch messages for efficiency (batch.size, linger.ms)
  - Producers can be configured for different durability levels (acks)
  - Producers can be idempotent (exactly-once per partition)
  - Producers can use transactions (atomic writes across partitions/topics)

Producer record structure:
  ProducerRecord {
    String topic;         // required
    Integer partition;    // optional (override partitioner)
    Long timestamp;       // optional (event time)
    K key;                // optional (determines partition)
    V value;              // required (the payload)
    Headers headers;      // optional (metadata, routing info)
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. CONSUMERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A CONSUMER is a client application that reads (subscribes to) records from
  Kafka topics.

Key concepts:
  - Consumers use a PULL model (they request data, not pushed to them)
  - Consumers track their position via OFFSETS
  - Consumers belong to a CONSUMER GROUP
  - Each partition is consumed by exactly ONE consumer in a group
  - Multiple consumer groups can read the same topic independently

Consumer poll loop:
  while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
      process(record);
    }
    consumer.commitSync(); // or commitAsync()
  }

7. CONSUMER GROUPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  A CONSUMER GROUP is a set of consumers that cooperatively read from a set of
  topics. Each partition in a topic is assigned to exactly ONE consumer in the
  group at any time.

Consumer group mechanics:
  - All consumers in a group share the same group.id
  - Kafka distributes partitions evenly across consumers in the group
  - If #consumers > #partitions → some consumers are idle
  - If #consumers < #partitions → some consumers read multiple partitions

Multiple consumer groups:
  - Each group maintains its OWN offset per partition
  - Group A and Group B can both read the same topic from the beginning
  - This enables fan-out: same event consumed by multiple services

Group coordinator:
  - A broker that manages group membership and offset commits for a group
  - The group coordinator broker is determined by:
    partition = abs(hash(group.id)) % numPartitionsOfConsumerOffsetsTopic
    → that partition's leader is the coordinator

Diagram:
  Topic: orders (4 partitions)
  
  Consumer Group A (order-processor):
    Consumer A1 → Partition 0, Partition 1
    Consumer A2 → Partition 2, Partition 3
  
  Consumer Group B (analytics):
    Consumer B1 → Partition 0
    Consumer B2 → Partition 1
    Consumer B3 → Partition 2
    Consumer B4 → Partition 3

8. REPLICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  Each partition is replicated across multiple brokers for fault tolerance.

Key terms:
  - Replication Factor: Number of copies of each partition (e.g., 3)
  - Leader: The broker that handles all read/write for a partition
  - Follower: Replica that copies from the leader
  - ISR (In-Sync Replica): Followers that are caught up with the leader
    (within replica.lag.time.max.ms, default 30 seconds)
  - OSR (Out-of-Sync Replica): Followers that have fallen behind

Fault tolerance:
  - With replication factor 3: can tolerate 2 broker failures and still read
    (with acks=1); can tolerate 1 broker failure and still write with durability
    (with acks=all + min.insync.replicas=2)

Leader election:
  - If leader fails, Kafka elects a new leader from the ISR
  - The new leader must have all messages up to the HW (high-watermark)

9. RECORDS / MESSAGES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Kafka RECORD (message) structure:
  - Offset: Position in partition (assigned by broker, sequential)
  - Timestamp: Producer-assigned (CREATE_TIME) or broker-assigned (LOG_APPEND_TIME)
  - Key: Optional bytes. Used for partitioning and log compaction
  - Value: The actual message payload (bytes, JSON, Avro, Protobuf, etc.)
  - Headers: Key-value metadata pairs (e.g., tracing IDs, content-type)
  - Checksum: CRC32 for data integrity

Serialization:
  - Kafka stores raw bytes — serialization is the producer/consumer's responsibility
  - Common: StringSerializer, ByteArraySerializer, JsonSerializer (Spring)
  - Recommended for schema evolution: Apache Avro with Schema Registry

10. LOG COMPACTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Definition:
  Log compaction ensures that Kafka retains AT LEAST the LAST message for each
  unique key. Old records with the same key are eventually deleted (compacted).

cleanup.policy = compact:
  - Useful for "latest state" per entity (like a database change log)
  - tombstone: publishing null value for a key marks it for deletion
  - Compaction runs in background — does not block reads/writes

Use cases:
  - User profile updates (keep latest profile per user-id)
  - Configuration store (keep latest config per config-key)
  - Database CDC with Debezium (keep latest row state)

Compacted vs Delete (cleanup policies):
  - "delete": Remove records after retention.ms or retention.bytes exceeded
  - "compact": Keep latest record per key indefinitely
  - "compact,delete": Compact AND delete old compacted records after retention

11. KAFKA CONTROLLER (ZOOKEEPER vs KRAFT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Old model (ZooKeeper):
  - ZooKeeper stores cluster metadata (brokers, topics, partitions, ISR lists)
  - One broker is elected as the "Controller" via ZooKeeper leader election
  - Controller manages partition leadership changes and broker join/leave events
  - ZooKeeper election: ~30-60 seconds for recovery after controller failure
  - PROBLEM: ZooKeeper is a separate system to deploy, monitor, and tune

New model (KRaft — Kafka Raft):
  - Kafka manages its own metadata using a built-in Raft consensus protocol
  - A quorum of controllers (3 or 5 brokers) manage metadata in __cluster_metadata
  - Faster metadata propagation, simpler architecture
  - Recovery time improved from ~30 seconds to < 1 second
  - Supports millions of partitions per cluster (vs ~200K with ZooKeeper)

12. KEY INTERVIEW QUESTIONS FOR THIS TOPIC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is a Kafka partition and why is it important?
A: A partition is the unit of ordering, parallelism, and replication in Kafka.
   Messages within a partition are strictly ordered by offset. More partitions
   allow more consumers to read in parallel. Ordering is guaranteed per partition
   but not across partitions.

Q: What is an offset? Where is it stored?
A: An offset is a unique integer ID for a record within a partition. Consumer
   offsets are stored in the internal __consumer_offsets topic (since Kafka 0.9).

Q: What is the difference between a partition's "LEO" and "HW"?
A: LEO (Log End Offset) is where the NEXT write will go. HW (High Watermark) is
   the last offset that has been replicated to ALL ISR replicas. Consumers can
   only read up to the HW — this ensures they only see committed, durable data.

Q: How does Kafka ensure ordering?
A: Kafka guarantees ordering WITHIN a partition. To ensure a set of messages
   (e.g., all events for one user) are ordered, use the same message KEY —
   this routes all messages for that key to the same partition.

Q: What happens when a consumer group has fewer consumers than partitions?
A: Some consumers will be assigned multiple partitions. All partitions will
   still be consumed. If there are MORE consumers than partitions, the extra
   consumers remain idle (no partition assignment).

Q: What is log compaction?
A: A cleanup strategy where Kafka keeps only the latest record per key in a
   topic. Older records with the same key are discarded. Useful for representing
   "current state" like a changelog or config store.

Q: What is the ISR and why does it matter?
A: ISR (In-Sync Replicas) is the set of replicas currently caught up with the
   leader. When acks=all is configured, the producer waits for ALL ISR replicas
   to acknowledge. If ISR shrinks below min.insync.replicas, writes are rejected
   to prevent data loss.
