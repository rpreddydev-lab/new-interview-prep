================================================================
  DECORATOR PATTERN
================================================================

  Category:   Structural
  Intent:     Attach additional responsibilities to an object dynamically.
              Decorators provide a flexible alternative to subclassing for
              extending functionality.
  Also known as: Wrapper
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Very high in interviews. Java I/O streams are a prime example.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Without Decorator — subclass explosion:
    Coffee
      Espresso
      EspressoWithMilk
      EspressoWithSugar
      EspressoWithMilkAndSugar
      Latte
      LatteWithSugar
      ... (exponential with each new add-on)

  With Decorator:
    Espresso decorated with MilkDecorator, decorated with SugarDecorator.
    Each decorator wraps and enhances. Stack decorators in any combination.
    M base drinks × N add-ons = M+N classes (not M×N).

  Decorator vs Inheritance:
    Inheritance: adds behavior STATICALLY at compile time.
    Decorator:   adds behavior DYNAMICALLY at runtime.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Component          -- Common interface for wrapped and wrapping objects.
  ConcreteComponent  -- The real object being decorated.
  Decorator          -- Abstract wrapper; holds reference to a Component.
  ConcreteDecorator  -- Extends Decorator; adds specific behavior before/after
                        delegating to the wrapped component.
  Client             -- Works with Component interface; stacks decorators freely.

----------------------------------------------------------------
FULL JAVA EXAMPLE — COFFEE SHOP
----------------------------------------------------------------

  // Component interface
  public interface Coffee {
      String getDescription();
      double getCost();
  }

  // Concrete Component
  public class Espresso implements Coffee {
      @Override public String getDescription() { return "Espresso"; }
      @Override public double getCost()         { return 1.00; }
  }

  // Abstract Decorator
  public abstract class CoffeeDecorator implements Coffee {
      protected final Coffee coffee;     // wrapped component

      public CoffeeDecorator(Coffee coffee) { this.coffee = coffee; }

      @Override public String getDescription() { return coffee.getDescription(); }
      @Override public double getCost()         { return coffee.getCost(); }
  }

  // Concrete Decorators
  public class MilkDecorator extends CoffeeDecorator {
      public MilkDecorator(Coffee coffee) { super(coffee); }

      @Override public String getDescription() { return coffee.getDescription() + ", Milk"; }
      @Override public double getCost()         { return coffee.getCost() + 0.25; }
  }

  public class SugarDecorator extends CoffeeDecorator {
      public SugarDecorator(Coffee coffee) { super(coffee); }

      @Override public String getDescription() { return coffee.getDescription() + ", Sugar"; }
      @Override public double getCost()         { return coffee.getCost() + 0.10; }
  }

  public class VanillaDecorator extends CoffeeDecorator {
      public VanillaDecorator(Coffee coffee) { super(coffee); }

      @Override public String getDescription() { return coffee.getDescription() + ", Vanilla"; }
      @Override public double getCost()         { return coffee.getCost() + 0.50; }
  }

  // Client
  public class Main {
      public static void main(String[] args) {
          Coffee order = new Espresso();
          System.out.println(order.getDescription() + " $" + order.getCost());
          // Espresso $1.0

          order = new MilkDecorator(order);
          System.out.println(order.getDescription() + " $" + order.getCost());
          // Espresso, Milk $1.25

          order = new SugarDecorator(order);
          order = new VanillaDecorator(order);
          System.out.println(order.getDescription() + " $" + order.getCost());
          // Espresso, Milk, Sugar, Vanilla $1.85
      }
  }

----------------------------------------------------------------
DECORATOR CALL CHAIN VISUALIZATION
----------------------------------------------------------------

  Client calls: vanillaDecorator.getCost()

  VanillaDecorator.getCost()
    --> SugarDecorator.getCost()   (inner coffee)
          --> MilkDecorator.getCost()   (inner coffee)
                --> Espresso.getCost()  // returns 1.00
              returns 1.00 + 0.25 = 1.25
        returns 1.25 + 0.10 = 1.35
    returns 1.35 + 0.50 = 1.85

  Chain of delegation — each layer adds its contribution and passes through.

----------------------------------------------------------------
DECORATOR IN JAVA I/O (CANONICAL EXAMPLE)
----------------------------------------------------------------

  Java I/O is built entirely on the Decorator pattern:

  InputStream (Component)
    FileInputStream       (ConcreteComponent - reads bytes from file)
    BufferedInputStream   (Decorator - adds buffering)
    DataInputStream       (Decorator - adds typed reads: readInt, readLong)
    GZIPInputStream       (Decorator - adds decompression)
    CipherInputStream     (Decorator - adds decryption)

  Usage:
    InputStream is =
        new GZIPInputStream(                // decompress
            new BufferedInputStream(        // buffer for efficiency
                new FileInputStream("data.gz"),  // raw file read
                8192
            )
        );

  Each wrapper adds a behavior; the underlying stream is the ConcreteComponent.
  Add or remove decorators independently. Same InputStream interface throughout.

  Writer hierarchy (same structure):
    FileWriter → BufferedWriter → PrintWriter

----------------------------------------------------------------
DECORATOR FOR CROSS-CUTTING CONCERNS
----------------------------------------------------------------

  Logging Decorator:
    public class LoggingService implements UserService {
        private final UserService delegate;

        public LoggingService(UserService delegate) { this.delegate = delegate; }

        @Override
        public User findById(Long id) {
            log.info("findById called with id: {}", id);
            User result = delegate.findById(id);
            log.info("findById returned: {}", result);
            return result;
        }
    }

  Retry Decorator:
    public class RetryService implements UserService {
        private final UserService delegate;
        private final int maxRetries;

        @Override
        public User findById(Long id) {
            for (int i = 0; i < maxRetries; i++) {
                try { return delegate.findById(id); }
                catch (Exception e) { if (i == maxRetries-1) throw e; }
            }
            throw new RuntimeException("All retries failed");
        }
    }

  Stack them: new RetryService(new LoggingService(new RealUserService()), 3)

DECORATOR IN SPRING
----------------------------------------------------------------

  Spring uses Decorator pattern extensively:

  Spring Security HttpSecurity filter wrapping:
    HttpServletRequest is wrapped in SecurityContextHolderAwareRequestWrapper,
    CsrfGrantingServletRequest, etc. — each adds security behavior.

  @Transactional, @Cacheable, @Async (via AOP Proxy = Decorator at runtime):
    Spring wraps your bean in a proxy that adds transaction, caching, or async
    behavior before/after calling the real method.

  Collections.unmodifiableList() / synchronizedList():
    Decorates any List to add read-only or thread-safe behavior.

  TransactionAwareDataSourceProxy:
    Decorates DataSource to add transaction awareness.

----------------------------------------------------------------
DECORATOR vs INHERITANCE
----------------------------------------------------------------

  Inheritance:
    - Compile-time. Fixed relationships. Class hierarchy grows.
    - Adding one more behavior requires new subclass combinations.
    - Combinatorial explosion for multiple add-ons.

  Decorator:
    - Runtime. Flexible. Objects composed dynamically.
    - Adding one decorator adds the behavior to ANY component.
    - O(M + N) classes vs O(M × N) for inheritance.

  Rule: Prefer Decorator (composition) over inheritance when behavior combinations
  can vary at runtime or grow combinatorially.

----------------------------------------------------------------
DECORATOR vs PROXY
----------------------------------------------------------------

  Decorator:
    - Adds NEW behavior (logging, retry, decoration).
    - Client typically KNOWS it's wrapped (selects decorators).
    - Focused on enrichment.

  Proxy:
    - Controls ACCESS to the real object (lazy load, auth, caching).
    - Client is UNAWARE of the proxy (transparent substitution).
    - Focused on control.

  Both implement the same interface as the wrapped object.
  Key difference: PURPOSE. Decorator enriches; Proxy controls.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Time: O(d) per method call, where d = number of decorator layers.
        In practice, d is small (2-5), so effectively O(1).
  Space: O(d) — each decorator holds one reference.
  Adding new decorator: O(1) code change (new class).
  Removing behavior: O(1) — just remove that decorator from the chain.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Decorator pattern?
  A: It attaches additional responsibilities to an object dynamically by
     wrapping it in a decorator that shares the same interface. Decorators
     add behavior before/after delegating to the wrapped component.
     Provides a flexible alternative to subclassing for extending behavior.

  Q: What's the canonical Java example of Decorator?
  A: Java I/O streams. BufferedInputStream wraps FileInputStream.
     GZIPInputStream wraps BufferedInputStream. Each adds behavior
     (buffering, decompression) while all share the InputStream interface.

  Q: How does Decorator differ from Proxy?
  A: Both wrap an object with the same interface.
     Decorator: adds NEW behavior (enrichment). Client often picks the decorators.
     Proxy: controls access (guard, cache, lazy load). Client is unaware of proxy.

  Q: How does Decorator differ from Inheritance?
  A: Inheritance is static (compile-time). Decorator is dynamic (runtime).
     With inheritance, combinations of behaviors require M×N subclasses.
     With Decorator, M components + N decorators combine freely at runtime.

  Q: What are the disadvantages of Decorator?
  A: Can result in many small objects that are hard to understand and debug.
     Decorators must be applied in the right order (order matters).
     Identity issues: the wrapped object's class is not the decorator's class.
     equals() and hashCode() from the inner object may not work as expected.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Java I/O streams is the must-know example — be able to explain it fluently.
  - Coffee shop / pizza toppings are classic interview examples to code.
  - Know the distinction: Decorator enriches, Proxy controls.
  - Mention Collections.unmodifiableList() and synchronizedList() as quick examples.
  - In Spring: @Transactional / @Cacheable AOP proxies are essentially Decorators.
