================================================================
  PROXY PATTERN
================================================================

  Category:   Structural
  Intent:     Provide a surrogate or placeholder for another object to
              control access to it.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Very high. Fundamental to Spring AOP — every @Transactional,
              @Cacheable, @Async uses a proxy.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Direct access to an object may not be possible or desirable because:
    - Object is expensive to create (lazy initialization).
    - Object is remote (RPC/RMI).
    - Access requires permission check.
    - Method calls should be logged or cached.
    - Cross-cutting concerns shouldn't pollute core logic.

  Proxy interposes itself between client and real object,
  controlling WHEN and HOW the real object is accessed.

----------------------------------------------------------------
PROXY TYPES
----------------------------------------------------------------

  1. VIRTUAL PROXY (Lazy Initialization):
     Real object is expensive to create. Proxy delays creation until needed.
     Example: Large image loaded only when first displayed.

  2. PROTECTION PROXY (Access Control):
     Controls who can access the real object.
     Example: Admin check before allowing operation.

  3. REMOTE PROXY:
     Represents an object in another address space (network, process).
     Example: RMI stub, gRPC client stub.

  4. CACHING PROXY (Smart Reference):
     Caches results of expensive operations.
     Example: Spring @Cacheable proxy.

  5. LOGGING PROXY:
     Logs method calls before/after delegating.
     Example: Spring AOP logging aspect.

  6. SMART PROXY:
     Performs additional actions (reference count, locking, etc.).

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Subject (interface)   -- Common interface for RealSubject and Proxy.
  RealSubject           -- The real object doing the actual work.
  Proxy                 -- Holds reference to RealSubject.
                           Controls access; may add behavior before/after.
  Client                -- Works with Subject interface; transparent to whether
                           it has Proxy or RealSubject.

----------------------------------------------------------------
FULL JAVA EXAMPLE — PROTECTION PROXY
----------------------------------------------------------------

  // Subject interface
  public interface UserService {
      User findById(long id);
      void deleteUser(long id);
  }

  // Real Subject
  public class UserServiceImpl implements UserService {
      @Override
      public User findById(long id) {
          System.out.println("DB: fetching user " + id);
          return new User(id, "Alice");
      }

      @Override
      public void deleteUser(long id) {
          System.out.println("DB: deleting user " + id);
      }
  }

  // Protection Proxy
  public class UserServiceProxy implements UserService {
      private final UserService realService;
      private final String currentUserRole;

      public UserServiceProxy(UserService service, String role) {
          this.realService = service;
          this.currentUserRole = role;
      }

      @Override
      public User findById(long id) {
          // Allow all authenticated users
          return realService.findById(id);
      }

      @Override
      public void deleteUser(long id) {
          // Only ADMIN can delete
          if (!"ADMIN".equals(currentUserRole)) {
              throw new SecurityException("Access denied: only ADMIN can delete users");
          }
          realService.deleteUser(id);
      }
  }

  // Client
  UserService service = new UserServiceProxy(new UserServiceImpl(), "USER");
  service.findById(1);        // OK
  service.deleteUser(1);      // throws SecurityException

  UserService adminService = new UserServiceProxy(new UserServiceImpl(), "ADMIN");
  adminService.deleteUser(1); // OK

VIRTUAL PROXY EXAMPLE — LAZY IMAGE LOADING
----------------------------------------------------------------

  public interface Image {
      void display();
  }

  public class RealImage implements Image {
      private final String filename;

      public RealImage(String filename) {
          this.filename = filename;
          loadFromDisk();     // EXPENSIVE — happens on construction
      }

      private void loadFromDisk() {
          System.out.println("Loading: " + filename);  // simulates heavy I/O
      }

      @Override
      public void display() {
          System.out.println("Displaying: " + filename);
      }
  }

  // Virtual Proxy — delays creation of RealImage until display() is called
  public class ImageProxy implements Image {
      private RealImage realImage;        // null until needed
      private final String filename;

      public ImageProxy(String filename) {
          this.filename = filename;       // no I/O here
      }

      @Override
      public void display() {
          if (realImage == null) {
              realImage = new RealImage(filename);    // load only on first display
          }
          realImage.display();
      }
  }

  // Client
  Image img1 = new ImageProxy("photo1.jpg");
  Image img2 = new ImageProxy("photo2.jpg");
  // No loading yet

  img1.display();  // Loading: photo1.jpg then Displaying: photo1.jpg
  img1.display();  // Displaying: photo1.jpg (already loaded)
  // img2 never loaded — never displayed

CACHING PROXY EXAMPLE
----------------------------------------------------------------

  public class CachingUserServiceProxy implements UserService {
      private final UserService realService;
      private final Map<Long, User> cache = new HashMap<>();

      public CachingUserServiceProxy(UserService service) {
          this.realService = service;
      }

      @Override
      public User findById(long id) {
          return cache.computeIfAbsent(id, realService::findById);
      }

      @Override
      public void deleteUser(long id) {
          cache.remove(id);       // invalidate cache
          realService.deleteUser(id);
      }
  }

JDK DYNAMIC PROXY (JAVA REFLECTION)
----------------------------------------------------------------

  Java provides built-in dynamic proxy creation for interfaces:

    UserService proxy = (UserService) Proxy.newProxyInstance(
        UserService.class.getClassLoader(),
        new Class[]{ UserService.class },
        (proxyObj, method, args) -> {
            System.out.println("Before: " + method.getName());
            Object result = method.invoke(realService, args);
            System.out.println("After: " + method.getName());
            return result;
        }
    );

  JDK Proxy:
    - Works ONLY for interfaces (not concrete classes).
    - Uses reflection — slightly slower than direct calls.
    - Used by Spring for interface-based beans.

  CGLIB Proxy (Spring also uses this):
    - Creates proxy by SUBCLASSING the target class.
    - Works for concrete classes (no interface required).
    - Cannot proxy final classes or final methods.
    - Spring uses CGLIB when @Transactional is applied to a class without an interface.

----------------------------------------------------------------
SPRING AOP — PROXY IN PRACTICE
----------------------------------------------------------------

  Every @Transactional, @Cacheable, @Async, @Retryable works via proxy.

  @Service
  public class OrderService {
      @Transactional
      public void placeOrder(Order order) {
          // Spring wraps this in a proxy that:
          // 1. Begins transaction BEFORE placeOrder()
          // 2. Calls real placeOrder()
          // 3. Commits transaction AFTER (or rolls back on exception)
      }
  }

  Proxy chain at runtime:
    Client --> OrderServiceProxy --> OrderServiceImpl

  Critical Spring Proxy GOTCHA:
    Self-invocation does NOT go through proxy:
      public void process() {
          this.placeOrder(order);  // <-- calls real method, NOT proxy!
                                   // @Transactional NOT applied!
      }
    Fix: inject self-reference, or use AopContext.currentProxy(), or restructure.

----------------------------------------------------------------
PROXY vs DECORATOR vs ADAPTER
----------------------------------------------------------------

  Proxy:
    - Controls ACCESS to the real subject.
    - Client is UNAWARE of proxy (transparent substitution).
    - Focus: guard, lazy init, cache, log.

  Decorator:
    - Adds NEW behavior to the subject.
    - Client often KNOWS it's composing decorators.
    - Focus: enrichment, stacking behaviors.

  Adapter:
    - Changes the INTERFACE.
    - Makes incompatible interfaces compatible.
    - Focus: interface translation.

  Both Proxy and Decorator share the same interface as the wrapped object.
  KEY DIFFERENCE: Purpose.
    Proxy = control (guard, lazy, cache).
    Decorator = enhance (add new behavior).

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Time: O(1) per method — one extra indirection.
       Caching Proxy: O(1) amortized (cache hit).
       Remote Proxy: O(network latency).
  Space: O(1) — holds one reference to real subject.

  Spring AOP proxies: negligible overhead per call in practice.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Proxy pattern?
  A: A surrogate that controls access to another object. Proxy and real subject
     share the same interface. The proxy intercepts calls and can add behavior
     (lazy init, access control, caching, logging) before/after delegating.

  Q: What are the types of proxies?
  A: Virtual (lazy init), Protection (access control), Remote (network calls),
     Caching (memoize results), Logging (method call auditing), Smart (reference count).

  Q: How does Spring use the Proxy pattern?
  A: Spring AOP wraps beans in proxy objects for cross-cutting concerns.
     @Transactional, @Cacheable, @Async, @Retryable all generate proxies.
     JDK dynamic proxy is used for interface-based beans;
     CGLIB subclass proxy is used for concrete classes.

  Q: What is the self-invocation gotcha in Spring?
  A: When a @Transactional method calls another @Transactional method in the same
     class via `this.method()`, it bypasses the proxy — the transaction advice
     does NOT apply. Fix by injecting the bean reference or using AopContext.

  Q: How is JDK Proxy different from CGLIB Proxy?
  A: JDK Proxy: uses java.lang.reflect.Proxy; requires a target interface.
     CGLIB: subclasses the target class; works without an interface but can't
     proxy final classes/methods. Spring uses CGLIB when no interface is present.

  Q: How is Proxy different from Decorator?
  A: Proxy controls access (transparent, client unaware). Decorator adds new
     behavior (client knows it's stacking decorators). Both use same interface,
     different intents.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Spring @Transactional is the must-know Proxy example for Spring developers.
  - Know the self-invocation gotcha — frequently asked in Spring interviews.
  - JDK Proxy = needs interface. CGLIB = subclasses, works without interface.
  - For coding: implement Protection Proxy or Caching Proxy — straightforward.
  - Distinguish from Decorator every time: "control access" vs "add behavior."
  - Know all 5+ proxy types by name — interviewers often ask "what types of proxy exist?"
