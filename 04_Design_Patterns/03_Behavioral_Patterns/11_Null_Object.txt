================================================================
  NULL OBJECT PATTERN
================================================================

  Category:   Behavioral
  Intent:     Avoid null references by providing a default object that does
              nothing (or provides sensible defaults). Eliminates null checks
              by using an object that conforms to the interface with no-op behavior.
  GoF:        Not in original 23; introduced later by Bobby Woolf (1996).
  Frequency:  Moderate. Widely used in practice, especially in Spring
              (Optional, NullSafe wrappers), logging (SLF4J NOPLogger),
              testing (mock/stub behaviors).

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Code scattered with:
    if (logger != null) logger.log("...");
    if (customer != null) customer.sendEmail(...);
    if (discountStrategy != null) price = discountStrategy.apply(price);

  Every null check: risk of forgetting one → NullPointerException.
  Verbose code that mixes null-safety with business logic.

  With Null Object:
    Replace null with a NoOp object implementing the same interface.
    Methods do nothing (or return defaults).
    Client code never needs to check for null.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  AbstractObject   -- Interface or abstract class; defines real behavior.
  RealObject       -- Actual implementation with real logic.
  NullObject       -- Implements interface with do-nothing / default behavior.
                      Returned instead of null when no real object exists.

----------------------------------------------------------------
LOGGER EXAMPLE (Classic Use Case)
----------------------------------------------------------------

  // Interface
  public interface Logger {
      void log(String message);
      void error(String message, Throwable t);
  }

  // Real implementation
  public class ConsoleLogger implements Logger {
      @Override
      public void log(String message) {
          System.out.println("[INFO] " + message);
      }

      @Override
      public void error(String message, Throwable t) {
          System.err.println("[ERROR] " + message + ": " + t.getMessage());
      }
  }

  // Null Object — does nothing
  public class NullLogger implements Logger {
      // Singleton is fine — stateless
      private static final NullLogger INSTANCE = new NullLogger();
      public static NullLogger getInstance() { return INSTANCE; }

      @Override
      public void log(String message)              { /* no-op */ }

      @Override
      public void error(String message, Throwable t) { /* no-op */ }
  }

  // Service that accepts a logger (injected)
  public class OrderService {
      private final Logger logger;

      public OrderService(Logger logger) {
          // Use NullLogger if none provided — never store null
          this.logger = (logger != null) ? logger : NullLogger.getInstance();
      }

      public void processOrder(Order order) {
          logger.log("Processing order: " + order.getId());
          // ... business logic ...
          logger.log("Order processed.");
      }
  }

  // Usage
  OrderService withLogging    = new OrderService(new ConsoleLogger());
  OrderService withoutLogging = new OrderService(null);  // uses NullLogger — safe

  withLogging.processOrder(order);     // logs to console
  withoutLogging.processOrder(order);  // runs silently — no null check needed in service

  // SLF4J already uses this pattern:
  Logger log = LoggerFactory.getLogger(OrderService.class);
  // If SLF4J has no binding, it uses NOPLogger — a Null Object.

CUSTOMER / DISCOUNT EXAMPLE
----------------------------------------------------------------

  // Interface
  public interface DiscountStrategy {
      double apply(double price);
  }

  // Real strategies
  public class PercentageDiscount implements DiscountStrategy {
      private final double percent;
      public PercentageDiscount(double percent) { this.percent = percent; }
      @Override
      public double apply(double price) { return price * (1 - percent / 100); }
  }

  // Null Object — no discount
  public class NoDiscount implements DiscountStrategy {
      public static final NoDiscount INSTANCE = new NoDiscount();
      @Override
      public double apply(double price) { return price; }  // unchanged
  }

  // Customer with optional discount
  public class Customer {
      private final String name;
      private final DiscountStrategy discount;

      public Customer(String name, DiscountStrategy discount) {
          this.name     = name;
          this.discount = (discount != null) ? discount : NoDiscount.INSTANCE;
      }

      public double checkout(double price) {
          return discount.apply(price);  // no null check needed
      }
  }

  Customer vip     = new Customer("Alice", new PercentageDiscount(20));
  Customer regular = new Customer("Bob", null);   // gets NoDiscount

  System.out.println(vip.checkout(100.0));      // 80.0
  System.out.println(regular.checkout(100.0));  // 100.0

JAVA OPTIONAL — MODERN APPROACH
----------------------------------------------------------------

  Java 8's Optional<T> is the modern alternative to Null Object for return values.

  // Without Optional (Null Object needed):
  public Customer findCustomerById(Long id) {
      Customer c = repo.find(id);
      return c != null ? c : Customer.GUEST;  // Null Object
  }

  // With Optional:
  public Optional<Customer> findCustomerById(Long id) {
      return Optional.ofNullable(repo.find(id));
  }

  // Usage
  findCustomerById(id)
      .map(Customer::getEmail)
      .ifPresent(email -> sendEmail(email));

  // When to use Null Object vs Optional:
  //   Optional:    when the absence is a valid, expected return case (find by ID)
  //   Null Object: when you want default behavior / do-nothing for missing dependency
  //                (injected services, strategies, handlers)

----------------------------------------------------------------
NULL OBJECT IN SPRING
----------------------------------------------------------------

  Spring extensively uses Null Object / safe defaults:
    - ApplicationEventMulticaster: SimpleApplicationEventMulticaster by default
    - JdbcTemplate: returns Collections.emptyList() instead of null
    - Optional<T> parameter injection: Spring injects Optional.empty() if bean absent
    - CollectionUtils.isEmpty() treats null as empty collection

  // Spring boot auto-configuration often uses Null Objects:
  @Bean
  @ConditionalOnMissingBean
  public CacheManager cacheManager() {
      return new NoOpCacheManager();   // Null Object for cache
  }

----------------------------------------------------------------
NULL OBJECT vs OPTIONAL vs SPECIAL CASE
----------------------------------------------------------------

  Null Object:
    Object with no-op or default behavior.
    Follows the interface — clients treat it like real objects.
    Good for injected dependencies (services, strategies, listeners).

  Optional<T>:
    Wrapper indicating "might not have a value."
    Forces caller to handle absence explicitly.
    Good for return values of lookup/search operations.

  Special Case (Fowler):
    Subtype for a special scenario — more behavior than just no-op.
    Example: GuestUser with limited permissions (not just null-safe).

  Comparison table:
  -----------------------------------------------------------------------
  Concern              Null Object        Optional       Special Case
  -----------------------------------------------------------------------
  Null checks needed?  No                 No             No
  Has behavior?        Default/no-op      No (wrapper)   Custom behavior
  Returned from?       Factories/inject   Search/find    Factories/repos
  Runtime polymorphism Yes                No             Yes
  Java 8+ preferred?   Yes for deps       Yes for results  Yes for complex
  -----------------------------------------------------------------------

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Space: O(1) — typically a singleton (stateless, thread-safe).
  Time:  O(1) per method call — methods are no-ops.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Null Object pattern?
  A: Replace null with an object that conforms to the expected interface
     but performs no-op or default behavior. Eliminates null checks.
     Clients don't know whether they have a real or null object — same interface.

  Q: When to use Null Object vs Optional?
  A: Null Object: for injected dependencies (logger, strategy, handler) where
     you want default/no-op behavior without null checks in client code.
     Optional: for return values of searches/lookups where absence is expected
     and the caller must decide what to do.

  Q: Real-world examples?
  A: SLF4J NOPLogger (no bound logging framework), Spring NoOpCacheManager,
     NoDiscount strategy, NullCommandHandler in command processing,
     Collections.emptyList() as a no-op collection.

  Q: What is the risk of Null Object?
  A: Silent failures — if no-op behavior silently swallows errors, bugs may
     be hard to diagnose. Always ensure no-op is intentional; consider logging
     in the Null Object so at least a trace exists.

  Q: Special Case vs Null Object?
  A: Null Object does nothing (or returns defaults). Special Case has meaningful
     business behavior for a specific scenario. GuestUser (with limited features)
     is a Special Case; NullLogger (does nothing) is a Null Object.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Logger / NullLogger is the classic example — know it cold.
  - Mention SLF4J NOPLogger as the stdlib example.
  - Know the Null Object vs Optional trade-off clearly.
  - Make Null Objects singletons (stateless → thread-safe, cheap).
  - Mention the silent failure risk — shows maturity in design thinking.
