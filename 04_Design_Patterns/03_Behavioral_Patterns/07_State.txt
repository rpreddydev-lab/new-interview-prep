================================================================
  STATE PATTERN
================================================================

  Category:   Behavioral
  Intent:     Allow an object to alter its behavior when its internal state
              changes. The object will appear to change its class.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  High. Order workflows, traffic lights, connection lifecycles,
              vending machines, game character states, UI components.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  An object behaves differently depending on its current state.
  Without State pattern: one class with massive if-else or switch on state variable.
  Each state transition logic scattered through the class.
  Adding a new state requires modifying many if-else branches.

  With State pattern:
    Each state = its own class.
    Context delegates to current State object.
    State transitions encapsulated in State classes.
    Adding new state = new class, no change to Context or other states (OCP).

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Context       -- Holds current State reference. Delegates requests to it.
                   Has setState() to change current state.
                   May pass itself to State methods for transitions.

  State         -- Interface; one method per behavior that depends on state.

  ConcreteState -- One class per state.
                   Implements behavior for that state.
                   May call context.setState(new OtherState()) to transition.

----------------------------------------------------------------
ORDER WORKFLOW EXAMPLE
----------------------------------------------------------------

  Order States: NEW --> PAID --> SHIPPED --> DELIVERED | CANCELLED

  // State interface
  public interface OrderState {
      void pay(OrderContext ctx);
      void ship(OrderContext ctx);
      void deliver(OrderContext ctx);
      void cancel(OrderContext ctx);
  }

  // Context
  public class OrderContext {
      private OrderState currentState;
      private String     orderId;

      public OrderContext(String id) {
          this.orderId      = id;
          this.currentState = new NewState();
      }

      public void setState(OrderState state) { this.currentState = state; }

      // Delegate to current state
      public void pay()     { currentState.pay(this); }
      public void ship()    { currentState.ship(this); }
      public void deliver() { currentState.deliver(this); }
      public void cancel()  { currentState.cancel(this); }

      public String getId() { return orderId; }
  }

  // NEW State
  public class NewState implements OrderState {
      @Override
      public void pay(OrderContext ctx) {
          System.out.println("Payment received for order " + ctx.getId());
          ctx.setState(new PaidState());
      }

      @Override
      public void ship(OrderContext ctx) {
          throw new IllegalStateException("Cannot ship unpaid order.");
      }

      @Override
      public void deliver(OrderContext ctx) {
          throw new IllegalStateException("Cannot deliver unpaid order.");
      }

      @Override
      public void cancel(OrderContext ctx) {
          System.out.println("Order " + ctx.getId() + " cancelled.");
          ctx.setState(new CancelledState());
      }
  }

  // PAID State
  public class PaidState implements OrderState {
      @Override
      public void pay(OrderContext ctx) {
          System.out.println("Already paid.");
      }

      @Override
      public void ship(OrderContext ctx) {
          System.out.println("Order " + ctx.getId() + " shipped.");
          ctx.setState(new ShippedState());
      }

      @Override
      public void deliver(OrderContext ctx) {
          throw new IllegalStateException("Not yet shipped.");
      }

      @Override
      public void cancel(OrderContext ctx) {
          System.out.println("Cancelled paid order — refund issued.");
          ctx.setState(new CancelledState());
      }
  }

  // SHIPPED State
  public class ShippedState implements OrderState {
      @Override
      public void pay(OrderContext ctx)   { System.out.println("Already paid."); }

      @Override
      public void ship(OrderContext ctx)  { System.out.println("Already shipped."); }

      @Override
      public void deliver(OrderContext ctx) {
          System.out.println("Order " + ctx.getId() + " delivered.");
          ctx.setState(new DeliveredState());
      }

      @Override
      public void cancel(OrderContext ctx) {
          throw new IllegalStateException("Cannot cancel shipped order.");
      }
  }

  // Delivered and Cancelled states follow same structure.

  // Usage
  OrderContext order = new OrderContext("ORD-001");
  order.pay();      // Payment received
  order.ship();     // Shipped
  order.deliver();  // Delivered
  order.cancel();   // IllegalStateException — already delivered

STATE MACHINE VISUALIZATION
----------------------------------------------------------------

                  pay()           ship()         deliver()
  [NEW] ---------> [PAID] -------> [SHIPPED] ---------> [DELIVERED]
    |                 |
    | cancel()        | cancel() (refund)
    v                 v
  [CANCELLED]     [CANCELLED]

----------------------------------------------------------------
ENUM-BASED STATE MACHINE (Simpler for simple workflows)
----------------------------------------------------------------

  public enum OrderStatus {
      NEW {
          @Override public OrderStatus pay()    { return PAID; }
          @Override public OrderStatus cancel() { return CANCELLED; }
      },
      PAID {
          @Override public OrderStatus ship()   { return SHIPPED; }
          @Override public OrderStatus cancel() { return CANCELLED; }
      },
      SHIPPED {
          @Override public OrderStatus deliver(){ return DELIVERED; }
      },
      DELIVERED {}, CANCELLED {};

      public OrderStatus pay()     { throw new IllegalStateException("Not allowed in " + this); }
      public OrderStatus ship()    { throw new IllegalStateException("Not allowed in " + this); }
      public OrderStatus deliver() { throw new IllegalStateException("Not allowed in " + this); }
      public OrderStatus cancel()  { throw new IllegalStateException("Not allowed in " + this); }
  }

  OrderStatus status = OrderStatus.NEW;
  status = status.pay();    // PAID
  status = status.ship();   // SHIPPED
  status = status.cancel(); // IllegalStateException

  When to use Enum vs Class: Enum for simple/no-data transitions.
  Class hierarchy for complex behavior (many methods, shared data, sub-states).

SPRING STATEMACHINE
----------------------------------------------------------------

  Spring provides a full state machine library:
  spring-statemachine-core

  @Configuration
  @EnableStateMachine
  public class StateMachineConfig extends StateMachineConfigurerAdapter<States, Events> {

      @Override
      public void configure(StateMachineStateConfigurer<States, Events> states) throws Exception {
          states.withStates()
              .initial(States.NEW)
              .end(States.DELIVERED)
              .end(States.CANCELLED)
              .states(EnumSet.allOf(States.class));
      }

      @Override
      public void configure(StateMachineTransitionConfigurer<States, Events> transitions) throws Exception {
          transitions
              .withExternal().source(States.NEW).target(States.PAID).event(Events.PAY)
              .and()
              .withExternal().source(States.PAID).target(States.SHIPPED).event(Events.SHIP);
      }
  }

----------------------------------------------------------------
STATE vs STRATEGY
----------------------------------------------------------------

  Both replace if-else with polymorphism. Key differences:

  State:                              Strategy:
  ------------------------------------------------
  Object changes ITSELF               Client chooses algorithm
  States know about other states      Strategies are independent
  Transitions in state classes         No transitions in strategies
  Context has one current state        Context holds the algorithm
  State can call context.setState()    Strategy doesn't call context
  Lifecycle: states change over time  Configured once (usually)
  ------------------------------------------------

  State: "What I do depends on what state I'm in RIGHT NOW"
  Strategy: "What algorithm should I use for this task?"

----------------------------------------------------------------
COMMON EXAMPLES
----------------------------------------------------------------

  Traffic light:  RED -> GREEN -> YELLOW -> RED
  Vending machine: IDLE -> HAS_COIN -> ITEM_SELECTED -> DISPENSING -> IDLE
  TCP connection: CLOSED -> LISTEN -> SYN_RCVD -> ESTABLISHED -> FIN_WAIT -> CLOSED
  Thread lifecycle: NEW -> RUNNABLE -> BLOCKED -> WAITING -> TERMINATED
  Game character: IDLE -> RUNNING -> JUMPING -> ATTACKING -> DEAD

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Space: O(n) — n state classes; O(1) per Context (one current state reference).
  Time:  O(1) per method call — delegates directly to current state object.

  vs if-else: State eliminates O(n) condition chains.
              But adds O(n) classes — class explosion for many states.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the State pattern?
  A: Allows an object to change its behavior when its internal state changes.
     The object holds a reference to a State object. Each state is a class
     that implements the state interface. Delegates behavior to the current
     state. State transitions happen by swapping the state object.

  Q: When to use State vs large if-else?
  A: Use State when the number of states > 3-4 and behavior differs significantly
     per state. If-else becomes unmaintainable as states multiply. State pattern
     provides O(1) dispatch, clear encapsulation, and easy addition of new states.

  Q: State vs Strategy?
  A: State: object's behavior changes AUTOMATICALLY as it transitions through
     states. States may trigger transitions. Strategy: client explicitly selects
     the algorithm. Strategies don't transition; no awareness of other strategies.

  Q: How are transitions managed?
  A: Two approaches: (1) Transitions in ConcreteState — each state calls
     context.setState(new NextState()). States know about others.
     (2) Transitions in Context — Context has a transition table. States
     return result, context decides next state. Context approach better for
     complex workflows; State approach simpler for small machines.

  Q: Real-world examples?
  A: Order workflow (NEW/PAID/SHIPPED/DELIVERED), TCP connection lifecycle,
     Spring StateMachine, UI component states (enabled/disabled/focused),
     thread lifecycle (NEW/RUNNABLE/WAITING/TERMINATED).

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Order workflow is the most interview-friendly example — implement it cleanly.
  - Know the Enum-based shortcut for simple state machines.
  - Mention Spring StateMachine for complex workflows in microservices.
  - State vs Strategy contrast is a very common interview question.
  - Thread.State enum is a built-in Java example of the State pattern.
