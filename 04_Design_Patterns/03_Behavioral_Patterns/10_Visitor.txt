================================================================
  VISITOR PATTERN
================================================================

  Category:   Behavioral
  Intent:     Represent an operation to be performed on elements of an object
              structure. Visitor lets you define a new operation without
              changing the classes of the elements on which it operates.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Moderate. AST traversal (compilers), serialization, export formats,
              tax calculation across different element types.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  You have a stable object structure (hierarchy of classes that rarely changes).
  You need to add new operations frequently.

  Without Visitor:
    Add a method to every class in the hierarchy per operation.
    Changing 20 classes every time a new operation is needed.
    Violates Single Responsibility (classes mix domain + operations).
    Violates Open/Closed (must modify existing classes).

  With Visitor:
    Operations defined in separate Visitor classes.
    Each element class has ONE method: accept(Visitor v).
    New operation = new Visitor class. Zero changes to element classes.

  KEY TRADE-OFF:
    Visitor: easy to add operations, hard to add new element types.
    Strategy/Polymorphism: easy to add element types, hard to add operations.
    Use when element hierarchy is STABLE and operations are VARIED.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Visitor         -- Interface; one visit(ConcreteElement) method per element type.
  ConcreteVisitor -- Implements all visit() methods; one per operation.
  Element         -- Interface; declares accept(Visitor v).
  ConcreteElement -- Implements accept() by calling visitor.visit(this) — DOUBLE DISPATCH.
  ObjectStructure -- May hold a collection of Elements; iterates and accepts.

----------------------------------------------------------------
DOUBLE DISPATCH EXPLAINED
----------------------------------------------------------------

  Problem with single dispatch: polymorphic call resolves to the runtime type of
  the RECEIVER but NOT the argument type.

  Without Visitor:
    void process(Shape shape) { ... }     // doesn't dispatch on Shape's type
    // Compile-time type of shape used — always calls the base overload

  With Visitor (double dispatch):
    Step 1: shape.accept(visitor)  -- dispatches on shape's runtime type (Circle vs Square)
    Step 2: visitor.visit(this)    -- dispatches on visitor's runtime type inside accept()
    Both runtime types resolved at runtime.

  // Element dispatches to itself
  public class Circle implements Shape {
      @Override
      public void accept(ShapeVisitor visitor) {
          visitor.visitCircle(this);  // "I am Circle — call the circle-specific method"
      }
  }

  // Visitor receives the specific type
  public class AreaCalculator implements ShapeVisitor {
      @Override
      public void visitCircle(Circle c) { area += Math.PI * c.getRadius() * c.getRadius(); }

      @Override
      public void visitSquare(Square s) { area += s.getSide() * s.getSide(); }
  }

----------------------------------------------------------------
SHAPE AREA AND EXPORT EXAMPLE
----------------------------------------------------------------

  // Element interface
  public interface Shape {
      void accept(ShapeVisitor visitor);
  }

  // Concrete elements
  public class Circle implements Shape {
      private final double radius;
      public Circle(double radius) { this.radius = radius; }
      public double getRadius() { return radius; }

      @Override
      public void accept(ShapeVisitor visitor) { visitor.visitCircle(this); }
  }

  public class Square implements Shape {
      private final double side;
      public Square(double side) { this.side = side; }
      public double getSide() { return side; }

      @Override
      public void accept(ShapeVisitor visitor) { visitor.visitSquare(this); }
  }

  public class Triangle implements Shape {
      private final double base, height;
      public Triangle(double base, double height) { this.base = base; this.height = height; }
      public double getBase()   { return base; }
      public double getHeight() { return height; }

      @Override
      public void accept(ShapeVisitor visitor) { visitor.visitTriangle(this); }
  }

  // Visitor interface — one method per element type
  public interface ShapeVisitor {
      void visitCircle(Circle c);
      void visitSquare(Square s);
      void visitTriangle(Triangle t);
  }

  // Concrete Visitor 1: Area calculation
  public class AreaCalculator implements ShapeVisitor {
      private double totalArea = 0;

      @Override
      public void visitCircle(Circle c) {
          totalArea += Math.PI * c.getRadius() * c.getRadius();
      }

      @Override
      public void visitSquare(Square s) {
          totalArea += s.getSide() * s.getSide();
      }

      @Override
      public void visitTriangle(Triangle t) {
          totalArea += 0.5 * t.getBase() * t.getHeight();
      }

      public double getTotal() { return totalArea; }
  }

  // Concrete Visitor 2: SVG export (new operation — no changes to Shape classes)
  public class SvgExporter implements ShapeVisitor {
      private final StringBuilder svg = new StringBuilder();

      @Override
      public void visitCircle(Circle c) {
          svg.append(String.format("<circle r=\"%.1f\"/>\n", c.getRadius()));
      }

      @Override
      public void visitSquare(Square s) {
          svg.append(String.format("<rect width=\"%.1f\" height=\"%.1f\"/>\n",
              s.getSide(), s.getSide()));
      }

      @Override
      public void visitTriangle(Triangle t) {
          svg.append(String.format("<!-- triangle base=%.1f height=%.1f -->\n",
              t.getBase(), t.getHeight()));
      }

      public String getSvg() { return svg.toString(); }
  }

  // Usage
  List<Shape> shapes = List.of(
      new Circle(5),
      new Square(4),
      new Triangle(3, 6)
  );

  AreaCalculator calc = new AreaCalculator();
  SvgExporter    exporter = new SvgExporter();

  for (Shape shape : shapes) {
      shape.accept(calc);
      shape.accept(exporter);
  }

  System.out.printf("Total area: %.2f%n", calc.getTotal());  // ~109.42
  System.out.println(exporter.getSvg());

AST VISITOR (COMPILER USE CASE)
----------------------------------------------------------------

  Compilers use Visitor extensively for:
    - Type checking
    - Code generation
    - Optimization passes
    - Pretty-printing

  interface ExprVisitor<T> {
      T visitLiteral(Literal lit);
      T visitBinaryOp(BinaryOp op);
      T visitVariable(Variable var);
  }

  class Interpreter implements ExprVisitor<Double> {
      @Override
      public Double visitLiteral(Literal lit)     { return lit.getValue(); }
      @Override
      public Double visitBinaryOp(BinaryOp op)    { return evaluate(op); }
      @Override
      public Double visitVariable(Variable var)   { return env.get(var.getName()); }
  }

  class PrettyPrinter implements ExprVisitor<String> {
      @Override
      public String visitLiteral(Literal lit)     { return lit.getValue().toString(); }
      @Override
      public String visitBinaryOp(BinaryOp op)    { return "(" + op.getLeft().accept(this)
                                                    + " " + op.getOp() + " "
                                                    + op.getRight().accept(this) + ")"; }
      @Override
      public String visitVariable(Variable var)   { return var.getName(); }
  }

----------------------------------------------------------------
VISITOR IN JAVA STDLIB / FRAMEWORKS
----------------------------------------------------------------

  Java NIO:
    Files.walkFileTree(path, new SimpleFileVisitor<Path>() {
        @Override
        public FileVisitResult visitFile(Path file, BasicFileAttributes attrs) {
            System.out.println(file);
            return FileVisitResult.CONTINUE;
        }
    });

  SimpleFileVisitor<T> is the ConcreteVisitor.
  FileVisitResult controls traversal (CONTINUE, TERMINATE, SKIP_SUBTREE).

  Java XML: org.xml.sax.ContentHandler — SAX parser calls visitor methods.

  ANTLR: Generated ParseTreeVisitor for grammar-based visitors.

  Spring Security: ExpressionVisitor for security expression trees.

----------------------------------------------------------------
PROS AND CONS
----------------------------------------------------------------

  PROS:
    + Open/Closed: add operations without modifying element classes.
    + Single Responsibility: operations in separate visitor classes.
    + Accumulate state across visits (AreaCalculator's totalArea).
    + Multiple visitors can traverse the same structure.

  CONS:
    - Breaking change: adding a new element type requires modifying ALL visitors.
    - Encapsulation: visitors may need access to element internals.
    - Verbose: requires accept() on every element and visit() on every visitor.
    - Complexity: double dispatch can be confusing.

  If element hierarchy changes frequently: DON'T use Visitor. Use polymorphism.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Space: O(n) per Visitor — one visit() method per element type.
  Time:  O(n) traversal — each element accept() + visitor visit().

  Adding new operation: O(1) — one new visitor class.
  Adding new element:   O(k) — must add visit() to k existing visitors.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Visitor pattern?
  A: Separates operations from the object structure. Each element has an
     accept(visitor) method. Visitors define visit(element) per type.
     New operations = new Visitor. Enables double dispatch — resolves both
     element's runtime type and visitor's runtime type.

  Q: What is double dispatch?
  A: Java uses single dispatch — virtual call resolves on receiver's runtime type.
     Visitor achieves double dispatch: (1) element.accept(visitor) dispatches on
     element type, (2) visitor.visit(this) dispatches on visitor type.
     Both runtime types are resolved dynamically.

  Q: When to use Visitor?
  A: When element hierarchy is stable (rarely new types) and operations are frequent
     (new operations often). Good for AST traversal, serialization, export formats.

  Q: What is the main drawback?
  A: Adding a new element type requires modifying ALL existing visitor implementations.
     The "expression problem": Visitor makes operations easy, element addition hard.

  Q: Java example of Visitor in stdlib?
  A: Files.walkFileTree() with SimpleFileVisitor<Path>. The FileVisitor interface
     has visitFile(), preVisitDirectory(), postVisitDirectory(), visitFileFailed().

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Show the shape example with two visitors (area + export) — shows OCP clearly.
  - Explain double dispatch clearly — most candidates struggle with this.
  - Know Files.walkFileTree() as the stdlib Visitor example.
  - State the trade-off: Visitor = easy operations, hard element addition.
  - Mention AST traversal in compilers for a strong technical impression.
