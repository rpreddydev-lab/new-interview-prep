================================================================
  MEDIATOR PATTERN
================================================================

  Category:   Behavioral
  Intent:     Define an object that encapsulates how a set of objects interact.
              Mediator promotes loose coupling by keeping objects from
              referring to each other explicitly. Lets you vary interactions
              independently.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Moderate. Very common in event-driven and GUI systems.
              MQ brokers, chat systems, air traffic control are classic examples.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  When many objects need to communicate with each other, the number of
  connections grows as O(n²). Each object holds references to all others.
  Changing one object requires changing all related objects.

  Without Mediator (tight coupling):
    ComponentA --> ComponentB
    ComponentA --> ComponentC
    ComponentB --> ComponentA
    ComponentB --> ComponentC
    ComponentC --> ComponentA
    ComponentC --> ComponentB
    6 connections for 3 components. n*(n-1) connections.

  With Mediator (hub-and-spoke):
    ComponentA --> Mediator
    ComponentB --> Mediator
    ComponentC --> Mediator
    Mediator --> (routes to appropriate components)
    3 connections. O(n) connections.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Mediator          -- Interface; defines communication contract with colleagues.
  ConcreteMediator  -- Implements Mediator; holds references to all colleagues;
                       implements coordination logic.
  Colleague         -- Interface or base class for components.
  ConcreteColleague -- Communicates only through the Mediator, not directly.

----------------------------------------------------------------
CHAT ROOM EXAMPLE
----------------------------------------------------------------

  // Mediator interface
  public interface ChatMediator {
      void sendMessage(String message, User sender);
      void addUser(User user);
  }

  // Colleague
  public abstract class User {
      protected ChatMediator mediator;
      protected String name;

      public User(ChatMediator mediator, String name) {
          this.mediator = mediator;
          this.name     = name;
      }

      public abstract void send(String message);
      public abstract void receive(String message);
  }

  // Concrete Colleague
  public class ChatUser extends User {
      public ChatUser(ChatMediator mediator, String name) {
          super(mediator, name);
      }

      @Override
      public void send(String message) {
          System.out.println(name + " sends: " + message);
          mediator.sendMessage(message, this);   // route through mediator
      }

      @Override
      public void receive(String message) {
          System.out.println(name + " received: " + message);
      }
  }

  // Concrete Mediator
  public class ChatRoom implements ChatMediator {
      private final List<User> users = new ArrayList<>();

      @Override
      public void addUser(User user) { users.add(user); }

      @Override
      public void sendMessage(String message, User sender) {
          for (User user : users) {
              if (user != sender) {          // don't echo back to sender
                  user.receive(message);
              }
          }
      }
  }

  // Usage
  ChatMediator chatRoom = new ChatRoom();
  User alice = new ChatUser(chatRoom, "Alice");
  User bob   = new ChatUser(chatRoom, "Bob");
  User carol = new ChatUser(chatRoom, "Carol");

  chatRoom.addUser(alice);
  chatRoom.addUser(bob);
  chatRoom.addUser(carol);

  alice.send("Hello everyone!");
  // Output:
  // Alice sends: Hello everyone!
  // Bob received: Hello everyone!
  // Carol received: Hello everyone!

RUNWAY / AIR TRAFFIC CONTROL EXAMPLE
----------------------------------------------------------------

  // Mediator
  public interface ATCTower {
      void requestLanding(Aircraft aircraft);
      void requestTakeoff(Aircraft aircraft);
  }

  // Colleague
  public interface Aircraft {
      String getId();
      void clearToLand();
      void clearToTakeoff();
  }

  // Concrete Mediator
  public class ControlTower implements ATCTower {
      private boolean runwayOccupied = false;
      private final Queue<Aircraft> landingQueue  = new LinkedList<>();
      private final Queue<Aircraft> takeoffQueue  = new LinkedList<>();

      @Override
      public void requestLanding(Aircraft aircraft) {
          if (runwayOccupied) {
              System.out.println(aircraft.getId() + " queued for landing.");
              landingQueue.offer(aircraft);
          } else {
              runwayOccupied = true;
              aircraft.clearToLand();
              // After landing complete (event), release runway
          }
      }

      @Override
      public void requestTakeoff(Aircraft aircraft) {
          if (runwayOccupied) {
              System.out.println(aircraft.getId() + " queued for takeoff.");
              takeoffQueue.offer(aircraft);
          } else {
              runwayOccupied = true;
              aircraft.clearToTakeoff();
          }
      }

      public void runwayFreed() {
          runwayOccupied = false;
          if (!landingQueue.isEmpty())  landingQueue.poll().clearToLand();
          else if (!takeoffQueue.isEmpty()) takeoffQueue.poll().clearToTakeoff();
      }
  }

GUI FORM MEDIATOR (Smart Form Interactions)
----------------------------------------------------------------

  Scenario: Login form — username field, password field, login button.
  Login button enabled only when both username and password are non-empty.
  Without Mediator: each field holds reference to the button — tight coupling.
  With Mediator: form itself acts as mediator — components notify mediator, which updates state.

  public class LoginForm implements Mediator {
      private JTextField usernameField;
      private JPasswordField passwordField;
      private JButton loginButton;

      public void componentChanged(Component component) {
          loginButton.setEnabled(
              !usernameField.getText().isEmpty() &&
              passwordField.getPassword().length > 0
          );
      }
  }

  // Components call: mediator.componentChanged(this) on change events.
  // No direct coupling between text fields and button.

JAVA STDLIB EXAMPLES
----------------------------------------------------------------

  java.util.concurrent.Executor  -- mediates task submission and thread management.
  java.util.Timer                -- mediates scheduled tasks.
  ExecutorService                -- mediates Runnable/Callable and thread pool.

  Swing: LayoutManager mediates between container and child components.

  Spring MVC: DispatcherServlet is a Mediator — coordinates HandlerMapping,
              HandlerAdapter, ViewResolver, MessageConverters.

  Message Brokers: RabbitMQ / Kafka / ActiveMQ — pure Mediator pattern.
    Producers don't know consumers. Broker routes messages.

----------------------------------------------------------------
MEDIATOR vs OBSERVER
----------------------------------------------------------------

  Mediator:                           Observer:
  ----------------------------------------
  Central object coordinates         Subject broadcasts to subscribers
  Colleagues call mediator            Observers subscribe to subject
  One-to-many AND many-to-one        One-to-many (push model)
  Mediator knows all colleagues       Subject doesn't know observer types
  Logic in mediator                   Logic in observers
  Good for complex, specific rules    Good for generic notification
  ----------------------------------------

  Mediator controls WHEN and WHAT to send.
  Observer just broadcasts THAT something happened.

  Note: Mediator CAN be implemented using Observer (mediator subscribes to
        colleagues, colleagues listen to mediator events).

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Space:  O(n) — mediator holds references to n colleagues.
  Time:   O(n) per message — mediator may notify all colleagues.
          Centralized logic in mediator can become complex (God Object risk).

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Mediator pattern?
  A: Centralizes communication between objects. Instead of objects talking
     directly to each other (creating O(n²) dependencies), all communicate
     through a mediator (O(n) dependencies). Decouples colleagues — they
     only know about the mediator interface.

  Q: Real-world examples?
  A: Chat room (users talk through ChatRoom), air traffic control (planes
     through tower), Spring DispatcherServlet (controllers/views through
     dispatcher), message brokers (producers/consumers through broker).

  Q: Mediator vs Facade?
  A: Facade: simplifies interface to a subsystem. One-way (client uses facade,
     subsystem components don't use facade). Structural pattern.
     Mediator: coordinates bidirectional communication between colleagues.
     Colleagues communicate through mediator. Behavioral pattern.

  Q: What's the risk of Mediator?
  A: The mediator can become a God Object — concentrating too much logic
     centrally. All interaction rules live in one place, which may grow
     complex and hard to maintain.

  Q: Mediator vs Observer?
  A: Mediator has specific coordination logic and knows its colleagues.
     Observer is generic broadcast — subject doesn't know observer types.
     Mediator can be implemented using Observer internally.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Mention message brokers as real-world Mediator (Kafka, RabbitMQ).
  - Spring DispatcherServlet is a perfect Mediator example.
  - Know the God Object risk as the main downside.
  - The chat room example is the simplest to implement in an interview.
  - Contrast with Observer: both decouple, but Mediator has coordination logic.
