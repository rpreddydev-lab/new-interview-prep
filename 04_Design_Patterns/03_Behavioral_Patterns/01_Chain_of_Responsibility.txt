================================================================
  CHAIN OF RESPONSIBILITY PATTERN
================================================================

  Category:   Behavioral
  Intent:     Avoid coupling the sender of a request to its receiver by
              giving more than one object a chance to handle the request.
              Chain the receiving objects and pass the request along the
              chain until an object handles it.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  High. Spring Security filter chain is the canonical real-world example.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  A request needs to be processed, but which handler should handle it is
  determined dynamically. You don't want the sender to know which handler
  will process it, and you may need to add or remove handlers at runtime.

  Examples:
    - HTTP request processing: authentication → authorization → rate limiting → business logic.
    - Form validation: null check → length check → format check → business rule check.
    - Expense approval: team lead (up to $1000) → manager (up to $10000) → VP (unlimited).
    - Logging levels: DEBUG → INFO → WARN → ERROR (each level filters or forwards).

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Handler (interface)     -- Declares handleRequest(). Optionally sets next handler.
  ConcreteHandler         -- Handles if capable; otherwise passes to next.
  Client                  -- Sets up the chain; sends request to first handler.

----------------------------------------------------------------
STRUCTURE VISUALIZATION
----------------------------------------------------------------

  Client --> [Handler1] --> [Handler2] --> [Handler3] --> null
              (handles or forwards)

  Handler1: if can handle → handle and STOP.
            else → pass to next.

  Request may be:
    - Handled by first capable handler (classic CoR).
    - Processed by ALL handlers in sequence (pipeline variant).

----------------------------------------------------------------
FULL JAVA EXAMPLE — EXPENSE APPROVAL
----------------------------------------------------------------

  // Handler interface
  public abstract class ApprovalHandler {
      protected ApprovalHandler next;

      public ApprovalHandler setNext(ApprovalHandler next) {
          this.next = next;
          return next;         // enable method chaining for setup
      }

      public abstract void approve(ExpenseRequest request);
  }

  // Request object
  public class ExpenseRequest {
      private final String requester;
      private final double amount;
      private boolean approved = false;

      public ExpenseRequest(String requester, double amount) {
          this.requester = requester; this.amount = amount;
      }
      public double getAmount()   { return amount; }
      public String getRequester(){ return requester; }
      public boolean isApproved() { return approved; }
      public void approve(String by) {
          System.out.printf("$%.0f approved by %s for %s%n", amount, by, requester);
          this.approved = true;
      }
  }

  // Concrete Handlers
  public class TeamLeadHandler extends ApprovalHandler {
      @Override
      public void approve(ExpenseRequest req) {
          if (req.getAmount() <= 1000) {
              req.approve("Team Lead");
          } else if (next != null) {
              next.approve(req);
          } else {
              System.out.println("No one could approve: $" + req.getAmount());
          }
      }
  }

  public class ManagerHandler extends ApprovalHandler {
      @Override
      public void approve(ExpenseRequest req) {
          if (req.getAmount() <= 10000) {
              req.approve("Manager");
          } else if (next != null) {
              next.approve(req);
          } else {
              System.out.println("No one could approve: $" + req.getAmount());
          }
      }
  }

  public class VPHandler extends ApprovalHandler {
      @Override
      public void approve(ExpenseRequest req) {
          req.approve("VP");   // VP approves all
      }
  }

  // Client — set up chain
  public class Main {
      public static void main(String[] args) {
          ApprovalHandler teamLead = new TeamLeadHandler();
          ApprovalHandler manager  = new ManagerHandler();
          ApprovalHandler vp       = new VPHandler();

          // Chain: teamLead --> manager --> vp
          teamLead.setNext(manager).setNext(vp);

          teamLead.approve(new ExpenseRequest("Alice",   500));   // Team Lead
          teamLead.approve(new ExpenseRequest("Bob",    5000));   // Manager
          teamLead.approve(new ExpenseRequest("Carol", 50000));   // VP
      }
  }

  Output:
    $500 approved by Team Lead for Alice
    $5000 approved by Manager for Bob
    $50000 approved by VP for Carol

----------------------------------------------------------------
PIPELINE VARIANT (ALL HANDLERS PROCESS)
----------------------------------------------------------------

  In the pipeline variant, EVERY handler processes the request.
  No early termination. Used in HTTP filter chains, validation pipelines.

    public interface Filter {
        void process(Request req, FilterChain chain);
    }

    public class FilterChain {
        private final List<Filter> filters;
        private int index = 0;

        public void proceed(Request req) {
            if (index < filters.size()) {
                filters.get(index++).process(req, this);
            }
        }
    }

    class AuthFilter implements Filter {
        public void process(Request req, FilterChain chain) {
            System.out.println("Auth check...");
            chain.proceed(req);     // continue to next filter
        }
    }

    class RateLimitFilter implements Filter {
        public void process(Request req, FilterChain chain) {
            System.out.println("Rate limit check...");
            chain.proceed(req);
        }
    }

  This is exactly how javax.servlet.Filter and Spring Security FilterChain work.

----------------------------------------------------------------
CHAIN OF RESPONSIBILITY IN JAVA / SPRING
----------------------------------------------------------------

  javax.servlet.Filter (Servlet API):
    - Each Filter calls chain.doFilter(req, resp) to pass to next.
    - Can short-circuit by NOT calling chain.doFilter (reject request).
    - Used for auth, logging, compression, CORS, CSRF.

  Spring Security FilterChain:
    - SecurityFilterChain is a list of SecurityFilter objects.
    - Each filter handles one concern (auth, session, CSRF, rate limit).
    - UsernamePasswordAuthenticationFilter → BasicAuthFilter → ExceptionTranslationFilter → ...

  Spring HandlerInterceptor:
    - preHandle() → controller → postHandle() → afterCompletion().
    - Multiple interceptors form a chain.

  Exception handlers (Spring @ExceptionHandler):
    - Multiple @ExceptionHandler methods tried in order until one matches.

  Logback/Log4j level filtering:
    - TRACE → DEBUG → INFO → WARN → ERROR → FATAL.
    - Each level "handles" its log events.

----------------------------------------------------------------
CLASSIC vs PIPELINE COMPARISON
----------------------------------------------------------------

  Classic (GoR):
    - ONE handler handles the request; rest skip.
    - Example: expense approval, support ticket escalation.
    - Request stops at first capable handler.

  Pipeline (Filter Chain):
    - ALL handlers process the request sequentially.
    - Example: HTTP filter chain, validation pipeline.
    - Request passes through all handlers.

  Both are valid usages of the pattern. Clarify which variant you mean in interviews.

----------------------------------------------------------------
ADVANTAGES
----------------------------------------------------------------

  1. Decoupling: sender doesn't know which handler processes the request.
  2. Flexibility: add, remove, or reorder handlers without changing sender or handlers.
  3. Open/Closed: new handlers can be added without modifying existing chain.
  4. Single Responsibility: each handler focuses on one concern.

----------------------------------------------------------------
DISADVANTAGES
----------------------------------------------------------------

  1. No guarantee of handling: request may reach end of chain unhandled.
  2. Debugging: harder to trace which handler processed what.
  3. Performance: request traverses multiple handlers even when first one could handle.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Handle: O(k) where k = position of handler that processes the request.
          Worst case O(n) — traverses full chain.
  Space: O(n) — chain of n handler references.

  In practice (e.g., Spring Security): chain length is fixed, overhead is minimal.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Chain of Responsibility pattern?
  A: Multiple handlers are chained together. A request is passed along the chain
     until one handler processes it (or all handlers in a pipeline variant).
     The sender doesn't know which handler will process the request.

  Q: What's the difference between CoR and a simple if-else chain?
  A: CoR uses polymorphism — handlers are objects that can be added/removed/reordered
     at runtime. if-else is hardcoded. CoR follows Open/Closed Principle;
     adding a new handler doesn't touch existing code.

  Q: How does Spring Security use Chain of Responsibility?
  A: Spring Security creates a SecurityFilterChain — a list of security filters.
     Each filter handles one security concern and calls chain.doFilter() to continue.
     A filter can short-circuit (reject) by NOT calling chain.doFilter().

  Q: What happens if no handler processes the request?
  A: In classic CoR: the request goes unhandled (potential issue — must handle this case,
     e.g., throw exception or have a default handler at end of chain).
     In pipeline: all handlers run, then the main logic executes.

  Q: How is CoR different from Decorator?
  A: Decorator: ALL wrappers process the operation. Enhances/enriches the result.
     CoR (classic): only ONE handler processes; others skip. Selects handler.
     CoR (pipeline): all handlers process, but may short-circuit; focuses on filtering.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Spring Security FilterChain is the must-know real-world example.
  - Know both variants: classic (one handles) and pipeline (all handle).
  - Be able to code the abstract handler with setNext() returning next (for method chaining setup).
  - Expense approval hierarchy is the cleanest interview coding example.
  - Mention that javax.servlet.Filter is the Java standard library example.
