================================================================
  STRATEGY PATTERN
================================================================

  Category:   Behavioral
  Intent:     Define a family of algorithms, encapsulate each one, and make
              them interchangeable. Strategy lets the algorithm vary
              independently from clients that use it.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  VERY HIGH. One of the most commonly used patterns.
              Sorting, pricing rules, payment methods, compression algorithms,
              routing strategies, authentication mechanisms.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Multiple algorithms exist for a task (sorting: quicksort, mergesort).
  Multiple behaviors exist based on context (discount: regular, vip, holiday).
  Without Strategy: one class with if-else per algorithm type.
  Adding a new algorithm requires modifying the class — violates OCP.

  With Strategy:
    Each algorithm = a class implementing the Strategy interface.
    Context holds a reference to a Strategy.
    Swap strategies at runtime without changing the Context.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Strategy          -- Interface; declares the algorithm method.
  ConcreteStrategy  -- Each implements the algorithm differently.
  Context           -- Holds a Strategy reference.
                       Delegates algorithm execution to current Strategy.
                       Client can set/change the strategy.

----------------------------------------------------------------
PAYMENT EXAMPLE
----------------------------------------------------------------

  // Strategy interface
  public interface PaymentStrategy {
      boolean pay(double amount);
  }

  // Concrete Strategies
  public class CreditCardPayment implements PaymentStrategy {
      private final String cardNumber;
      private final String cvv;

      public CreditCardPayment(String cardNumber, String cvv) {
          this.cardNumber = cardNumber;
          this.cvv        = cvv;
      }

      @Override
      public boolean pay(double amount) {
          System.out.printf("Charging $%.2f to credit card ending %s%n",
              amount, cardNumber.substring(cardNumber.length() - 4));
          return true;  // call bank API in real code
      }
  }

  public class PayPalPayment implements PaymentStrategy {
      private final String email;

      public PayPalPayment(String email) { this.email = email; }

      @Override
      public boolean pay(double amount) {
          System.out.printf("Processing $%.2f via PayPal for %s%n", amount, email);
          return true;
      }
  }

  public class CryptoPayment implements PaymentStrategy {
      private final String walletAddress;

      public CryptoPayment(String wallet) { this.walletAddress = wallet; }

      @Override
      public boolean pay(double amount) {
          System.out.printf("Sending $%.2f in BTC to wallet %s%n", amount, walletAddress);
          return true;
      }
  }

  // Context
  public class ShoppingCart {
      private final List<Item> items = new ArrayList<>();
      private PaymentStrategy paymentStrategy;

      public void setPaymentStrategy(PaymentStrategy strategy) {
          this.paymentStrategy = strategy;
      }

      public void addItem(Item item) { items.add(item); }

      public boolean checkout() {
          double total = items.stream()
              .mapToDouble(Item::getPrice)
              .sum();
          return paymentStrategy.pay(total);
      }
  }

  // Usage
  ShoppingCart cart = new ShoppingCart();
  cart.addItem(new Item("Book", 29.99));
  cart.addItem(new Item("Coffee", 12.50));

  cart.setPaymentStrategy(new CreditCardPayment("4111111111111234", "123"));
  cart.checkout();   // Charging $42.49 to credit card ending 1234

  cart.setPaymentStrategy(new PayPalPayment("user@example.com"));
  cart.checkout();   // Processing $42.49 via PayPal for user@example.com

SORTING STRATEGY (Classic GoF Example)
----------------------------------------------------------------

  public interface SortStrategy<T extends Comparable<T>> {
      void sort(List<T> list);
  }

  public class QuickSort<T extends Comparable<T>> implements SortStrategy<T> {
      @Override
      public void sort(List<T> list) { /* quicksort implementation */ }
  }

  public class MergeSort<T extends Comparable<T>> implements SortStrategy<T> {
      @Override
      public void sort(List<T> list) { /* mergesort implementation */ }
  }

  // Java Comparator IS a Strategy for comparison algorithms
  List<Person> people = new ArrayList<>(...);
  people.sort(Comparator.comparingInt(Person::getAge));         // sort by age
  people.sort(Comparator.comparing(Person::getName));           // sort by name
  people.sort(Comparator.comparingInt(Person::getAge).reversed()); // desc

  // Comparator<T> is the Strategy interface.
  // Lambda expressions ARE Strategy instances.

LAMBDA AS STRATEGY (Java 8+)
----------------------------------------------------------------

  If Strategy has ONE method (functional interface), use lambdas:

  // Define functional strategy
  @FunctionalInterface
  public interface DiscountStrategy {
      double applyDiscount(double originalPrice);
  }

  // Strategies as lambdas — no boilerplate classes
  DiscountStrategy noDiscount       = price -> price;
  DiscountStrategy tenPercent       = price -> price * 0.90;
  DiscountStrategy fixedTwentyOff   = price -> Math.max(0, price - 20.0);
  DiscountStrategy memberDiscount   = price -> price * 0.85;

  // Use in context
  double finalPrice = noDiscount.applyDiscount(100.0);    // 100.0
  double sale       = tenPercent.applyDiscount(100.0);    // 90.0

  // Map of strategies by key
  Map<String, DiscountStrategy> strategies = new HashMap<>();
  strategies.put("NONE",   price -> price);
  strategies.put("PROMO10", price -> price * 0.90);
  strategies.put("VIP",    price -> price * 0.80);

  String code    = "PROMO10";
  double result  = strategies.getOrDefault(code, price -> price)
                              .applyDiscount(100.0);   // 90.0

VALIDATION STRATEGY (Real-World Spring Use Case)
----------------------------------------------------------------

  // Validation using Strategy
  @FunctionalInterface
  public interface Validator<T> {
      ValidationResult validate(T object);
  }

  // Spring Validator interface IS a Strategy
  @Component
  public class UserAgeValidator implements Validator<User> {
      @Override
      public ValidationResult validate(User user) {
          return user.getAge() >= 18
              ? ValidationResult.valid()
              : ValidationResult.invalid("Must be at least 18");
      }
  }

  // Composite validation — chain of strategies
  @Service
  public class UserValidationService {
      private final List<Validator<User>> validators;

      public UserValidationService(List<Validator<User>> validators) {
          this.validators = validators;
      }

      public List<ValidationResult> validateAll(User user) {
          return validators.stream()
              .map(v -> v.validate(user))
              .filter(ValidationResult::isInvalid)
              .collect(Collectors.toList());
      }
  }

STRATEGY vs TEMPLATE METHOD
----------------------------------------------------------------

  Strategy:                           Template Method:
  -----------------------------------------------
  Interface-based                     Abstract class-based
  Algorithm varies entirely           Algorithm skeleton fixed, steps vary
  Composition (HAS-A)                 Inheritance (IS-A)
  Change at runtime                   Fixed at compile time
  Multiple implementations            Single implementation with overrides
  More flexible (Java multi-impl)     Less flexible (single inheritance)
  Prefer when: algorithm is the only  Prefer when: algorithm structure shared,
  variable, or runtime switching      only steps differ
  -----------------------------------------------

  Rule of thumb: Strategy = WHAT algorithm to run (whole thing).
                 Template = HOW to run THIS algorithm (fill in steps).

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Space:  O(1) — one Strategy reference per Context.
  Time:   O(1) switching — swap strategy reference.
          Algorithm performance depends on the strategy chosen.

  Class count: O(n) strategy classes for n algorithms.
               Java 8+ lambdas eliminate boilerplate for functional strategies.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Strategy pattern?
  A: Defines a family of algorithms, encapsulates each in a class, and makes
     them interchangeable. The Context delegates work to a Strategy interface.
     Clients can swap strategies at runtime. Eliminates conditional logic;
     open for extension (new strategies), closed for modification (context).

  Q: Real-world examples?
  A: Payment methods (credit card, PayPal, crypto), sorting algorithms,
     discount pricing rules, compression algorithms, authentication strategies,
     routing in GPS, Spring's TransactionManager, Comparator in Java collections.

  Q: How does Java 8 improve the Strategy pattern?
  A: If the Strategy interface is a functional interface (one method),
     lambda expressions serve as strategy instances without boilerplate classes.
     Comparator, Predicate, Function, Runnable are all Strategy functional interfaces.

  Q: Strategy vs Template Method?
  A: Strategy: entire algorithm interchangeable (composition/interface).
     Template Method: skeleton fixed in base class, steps overridden in subclasses.
     Strategy preferred in Java (composition > inheritance, avoids single-inheritance
     limitation). Template Method preferred when algorithm structure is shared.

  Q: How to avoid creating too many strategy classes?
  A: Use lambdas for stateless strategies (Java 8+).
     Use a Map<String, Strategy> for lookup-based selection.
     Enum-based strategies for a fixed closed set.

INTERVIEW TIPS
----------------------------------------------------------------

  - Implement the payment example cleanly — very common interview ask.
  - Show the lambda version immediately after the class version.
  - Map<key, Strategy> pattern for runtime dispatch is highly practical.
