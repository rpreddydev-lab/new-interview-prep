================================================================
  THREAD POOL PATTERN
================================================================

  Category:   Concurrency
  Intent:     Pre-create a pool of threads to execute submitted tasks.
              Reuse threads rather than creating a new thread per task,
              reducing overhead and providing resource control.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Creating a new thread per task is expensive:
    - Thread creation: ~0.5-1ms OS-level resource allocation.
    - Thread consumes ~256KB-2MB stack memory.
    - JVM can support only a limited number of threads (~1000s).

  With Thread Pool:
    - Threads created once; reused for many tasks.
    - Bounded pool size prevents resource exhaustion.
    - Queue absorbs task bursts.
    - Graceful shutdown and lifecycle management.

----------------------------------------------------------------
JAVA THREAD POOL: ExecutorService
----------------------------------------------------------------

  ExecutorService API:
    submit(Runnable)            --> Future<?>
    submit(Callable<T>)         --> Future<T>
    invokeAll(Collection<Callable<T>>)  --> List<Future<T>> (waits for all)
    invokeAny(Collection<Callable<T>>)  --> T (returns first result)
    shutdown()                  -- no new tasks; completes queued tasks
    shutdownNow()               -- interrupts all running threads; returns unstarted tasks
    awaitTermination(long, TimeUnit)    -- blocks until terminated or timeout
    isShutdown()                -- returns true after shutdown() called
    isTerminated()              -- returns true when all tasks complete post-shutdown

----------------------------------------------------------------
THREADPOOLEXECUTOR — FULL CONTROL
----------------------------------------------------------------

  ThreadPoolExecutor(
      int corePoolSize,          // min threads always kept alive
      int maximumPoolSize,       // max threads created
      long keepAliveTime,        // idle time before non-core thread is terminated
      TimeUnit unit,
      BlockingQueue<Runnable> workQueue,
      ThreadFactory threadFactory,
      RejectedExecutionHandler handler
  )

  Thread lifecycle in pool:
    1. Task submitted.
    2. If threads < corePoolSize: create new thread.
    3. If threads >= corePoolSize: try to enqueue in workQueue.
    4. If queue is full AND threads < maximumPoolSize: create new non-core thread.
    5. If queue is full AND threads == maximumPoolSize: apply RejectedExecutionHandler.

  // Typical config example
  ThreadPoolExecutor executor = new ThreadPoolExecutor(
      4,                               // corePoolSize
      16,                              // maximumPoolSize
      60L,                             // keepAliveTime
      TimeUnit.SECONDS,
      new ArrayBlockingQueue<>(200),   // bounded task queue
      Executors.defaultThreadFactory(),
      new ThreadPoolExecutor.CallerRunsPolicy()  // rejection handler
  );

----------------------------------------------------------------
FACTORY METHODS (Executors class)
----------------------------------------------------------------

  Executors.newFixedThreadPool(n):
    corePoolSize = n, maxPoolSize = n.
    Unbounded LinkedBlockingQueue.
    Fixed concurrency. Safe for CPU-bound tasks.
    Risk: queue grows unbounded → OOM if tasks faster than processing.

  Executors.newCachedThreadPool():
    corePoolSize = 0, maxPoolSize = Integer.MAX_VALUE.
    SynchronousQueue (no buffering).
    Creates threads on demand; terminates idle threads after 60s.
    Risk: too many threads for I/O burst → resource exhaustion.
    Best for: many short-lived tasks with low latency requirement.

  Executors.newSingleThreadExecutor():
    One thread, unbounded queue.
    Tasks processed sequentially in submission order.
    Use for: ordered task execution, background serialized work.

  Executors.newScheduledThreadPool(n):
    Supports delayed and periodic tasks.
    scheduleAtFixedRate(), scheduleWithFixedDelay().

  NOTE: Sonar/best practice discourages Executors factory methods because:
    - newFixedThreadPool has UNBOUNDED queue → OOM.
    - newCachedThreadPool has UNBOUNDED threads → resource exhaustion.
    Prefer explicit ThreadPoolExecutor with bounded queue.

----------------------------------------------------------------
REJECTION POLICIES
----------------------------------------------------------------

  When queue full AND maxPoolSize reached, RejectedExecutionHandler is called:

  AbortPolicy (default):
    Throws RejectedExecutionException.
    Use when task loss is unacceptable and caller must handle.

  CallerRunsPolicy:
    Calling thread runs the task itself.
    Provides natural backpressure — slows down the caller.
    Use for graceful degradation.

  DiscardPolicy:
    Silently discards the task.
    Use when task loss is acceptable (e.g., metrics).

  DiscardOldestPolicy:
    Discards the oldest queued task; retries submit.
    Use when newest data is more important.

  Custom:
    Implement RejectedExecutionHandler.
    Log + retry, send to dead letter queue, etc.

SPRING THREADPOOLTASKEXECUTOR
----------------------------------------------------------------

  @Configuration
  public class AsyncConfig implements AsyncConfigurer {

      @Bean
      public ThreadPoolTaskExecutor taskExecutor() {
          ThreadPoolTaskExecutor exec = new ThreadPoolTaskExecutor();
          exec.setCorePoolSize(4);
          exec.setMaxPoolSize(16);
          exec.setQueueCapacity(200);
          exec.setKeepAliveSeconds(60);
          exec.setThreadNamePrefix("async-task-");
          exec.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
          exec.initialize();
          return exec;
      }

      @Override
      public Executor getAsyncExecutor() {
          return taskExecutor();
      }
  }

  @Service
  public class EmailService {
      @Async
      public CompletableFuture<Void> sendEmail(String to) {
          // runs in thread pool
          return CompletableFuture.completedFuture(null);
      }
  }

FUTURE AND COMPLETABLEFUTURE
----------------------------------------------------------------

  // Submit and get result later
  ExecutorService executor = Executors.newFixedThreadPool(4);

  Future<Integer> future = executor.submit(() -> {
      Thread.sleep(1000);
      return 42;
  });

  // ... do other work ...
  Integer result = future.get();           // blocks until done
  Integer result2 = future.get(2, SECONDS); // with timeout

  // Check state
  future.isDone();      // true if done (normally, exceptionally, or cancelled)
  future.isCancelled(); // true if cancelled via future.cancel()
  future.cancel(true);  // interrupt running task

  // CompletableFuture (async pipeline)
  CompletableFuture<String> cf = CompletableFuture
      .supplyAsync(() -> fetchUser(userId), executor)   // async step
      .thenApplyAsync(user -> enrichUser(user), executor) // async transform
      .thenApply(user -> user.toString())                // sync transform
      .exceptionally(ex -> "default");                   // error handling

  // Wait for multiple futures
  CompletableFuture<Void> all = CompletableFuture.allOf(cf1, cf2, cf3);
  all.join();  // blocks until all complete

  // Race: first to complete wins
  CompletableFuture<String> first = CompletableFuture.anyOf(cf1, cf2)
      .thenApply(obj -> (String) obj);

----------------------------------------------------------------
THREAD POOL SIZING GUIDELINES
----------------------------------------------------------------

  CPU-bound tasks (pure computation):
    Optimal pool size ≈ number of CPU cores.
    Too many threads: context switching overhead.
    poolSize = Runtime.getRuntime().availableProcessors()

  I/O-bound tasks (database, network, file):
    Threads spend time waiting; more threads can be active.
    poolSize = CPU_cores * (1 + wait_time / compute_time)
    Rule of thumb: poolSize = CPU_cores * 2  (or higher for high I/O wait)

  Mixed: profile and tune based on throughput measurements.

  Spring Boot Tomcat default: max 200 threads (spring.servlet.tomcat.max-threads).
  HikariCP default pool: 10 connections.
  For microservices: match DB pool size to thread pool to avoid starvation.

----------------------------------------------------------------
VIRTUAL THREADS (JAVA 21 — PROJECT LOOM)
----------------------------------------------------------------

  Traditional: Platform threads (OS threads). Expensive. ~1MB stack.
  Virtual threads: Lightweight JVM-scheduled threads. Millions possible.

  // Java 21+
  ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
  executor.submit(() -> { /* I/O-bound task */ });

  Benefits:
    - One virtual thread per task (no pooling needed for I/O).
    - Automatically yields when blocked (no OS thread wasted on waiting).
    - Simpler code than reactive (write sequential code, get async throughput).

  When to still use fixed thread pools:
    - CPU-bound tasks (virtual threads don't help).
    - Limiting concurrency explicitly (e.g., max 4 concurrent DB connections).

----------------------------------------------------------------
SHUTDOWN BEST PRACTICES
----------------------------------------------------------------

  void shutdownGracefully(ExecutorService executor) throws InterruptedException {
      executor.shutdown();                      // no new tasks accepted
      if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
          executor.shutdownNow();               // interrupt running threads
          if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
              System.err.println("Pool did not terminate.");
          }
      }
  }

  // Spring Boot: ExecutorService beans are auto-shutdown on context close.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Thread creation cost:   O(1) amortized (threads reused).
  Task submission:        O(1) — enqueue to BlockingQueue.
  Task execution:         O(1) overhead + task duration.
  Space:                  O(n) — n threads × stack size + queue memory.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is a Thread Pool and why use it?
  A: A pool of pre-created threads that execute submitted tasks.
     Avoids per-task thread creation overhead (~1ms). Controls max concurrency.
     Bounded queue prevents memory explosion. Reuses threads across tasks.

  Q: What are the ThreadPoolExecutor parameters?
  A: corePoolSize: always-kept threads. maximumPoolSize: max threads.
     keepAliveTime: how long idle non-core threads live. workQueue: task buffer.
     rejectedExecutionHandler: what to do when queue full + max threads reached.

  Q: What are the thread pool factory methods and their risks?
  A: newFixedThreadPool: unbounded queue → OOM.
     newCachedThreadPool: unbounded threads → resource exhaustion.
     Best practice: explicit ThreadPoolExecutor with bounded queue.

  Q: How do you size a thread pool?
  A: CPU-bound: n = number of CPU cores.
     I/O-bound: n = cores * (1 + wait/compute ratio). Typically cores * 2+.
     Measure actual throughput and tune.

  Q: What is CallerRunsPolicy?
  A: When queue is full and max threads reached, the submitting (caller) thread
     executes the task itself. Provides natural backpressure — slows down producers
     when consumers are overwhelmed.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Always mention bounded queue when discussing thread pools.
  - Know the 5 ThreadPoolExecutor constructor parameters.
  - Know all 4 rejection policies and their trade-offs.
  - Know Future vs CompletableFuture — CF is far more powerful.
  - Mention Virtual Threads (Java 21) for I/O-bound tasks.
