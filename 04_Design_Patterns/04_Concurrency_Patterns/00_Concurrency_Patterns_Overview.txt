================================================================
  CONCURRENCY PATTERNS — OVERVIEW
================================================================

  Concurrency patterns solve problems that arise when multiple threads or
  processes access shared resources simultaneously. They manage thread safety,
  coordination, and efficient resource utilization.

----------------------------------------------------------------
WHY CONCURRENCY PATTERNS MATTER
----------------------------------------------------------------

  Multi-threaded code introduces:
    - Race conditions: two threads read-modify-write simultaneously.
    - Deadlock: two threads wait on each other indefinitely.
    - Starvation: a thread never gets CPU time.
    - Livelock: threads keep responding to each other without progress.
    - Visibility: changes in one thread not seen by others without sync.
    - Atomicity: compound operations not atomic by default.

  Java provides: synchronized, volatile, java.util.concurrent (JUC) package.
  Patterns: standard solutions to recurring concurrency problems.

----------------------------------------------------------------
PATTERNS AT A GLANCE
----------------------------------------------------------------

  Pattern                  Problem                          Key Mechanism
  -----------------------------------------------------------------------
  Producer-Consumer        Decouple production/consumption  BlockingQueue
  Read-Write Lock          Multiple readers, single writer  ReentrantReadWriteLock
  Thread Pool              Manage thread lifecycle/reuse    ExecutorService, ThreadPoolExecutor
  Active Object            Async method execution           Command queue + dedicated thread
  Scheduler                Time-based task execution        ScheduledExecutorService
  Semaphore & Mutex        Limit concurrent access count    Semaphore, synchronized/ReentrantLock

----------------------------------------------------------------
JAVA CONCURRENCY TOOLKIT (java.util.concurrent)
----------------------------------------------------------------

  Executors:
    Executors.newFixedThreadPool(n)
    Executors.newCachedThreadPool()
    Executors.newSingleThreadExecutor()
    Executors.newScheduledThreadPool(n)

  Queues:
    ArrayBlockingQueue<T>       -- bounded FIFO blocking queue
    LinkedBlockingQueue<T>      -- optionally bounded FIFO blocking queue
    PriorityBlockingQueue<T>    -- unbounded priority-ordered queue
    ConcurrentLinkedQueue<T>    -- non-blocking unbounded queue

  Synchronizers:
    CountDownLatch              -- wait for n events to complete
    CyclicBarrier               -- all threads meet at a barrier
    Semaphore                   -- limit concurrent access count
    Phaser                      -- flexible multi-phase barrier
    Exchanger<T>                -- two threads swap data at a sync point

  Locks:
    ReentrantLock               -- explicit lock with tryLock(), lockInterruptibly()
    ReentrantReadWriteLock      -- separate read/write locks
    StampedLock                 -- optimistic reads (Java 8+)

  Atomic classes:
    AtomicInteger, AtomicLong, AtomicBoolean
    AtomicReference<T>
    AtomicIntegerArray, AtomicLongArray
    LongAdder, DoubleAdder (high-contention counters)

  Concurrent Collections:
    ConcurrentHashMap<K,V>
    CopyOnWriteArrayList<T>
    CopyOnWriteArraySet<T>
    ConcurrentSkipListMap<K,V>  -- sorted concurrent map

  Futures:
    Future<T>                   -- result of async computation
    CompletableFuture<T>        -- compose async pipelines (Java 8+)
    ForkJoinPool, ForkJoinTask  -- divide-and-conquer parallelism

----------------------------------------------------------------
KEY JAVA CONCURRENCY CONCEPTS
----------------------------------------------------------------

  synchronized:
    - Mutual exclusion on a monitor (object lock).
    - Provides visibility guarantee (happens-before).
    - Can synchronize on instance (this) or class (ClassName.class).
    - NOT reentrant-safe for nested synchronized on different objects → deadlock risk.

  volatile:
    - Ensures visibility of variable changes across threads.
    - Does NOT guarantee atomicity of compound operations.
    - i++ is NOT atomic even with volatile.
    - Prevents instruction reordering across the volatile read/write.
    - Use for flags, single-write multiple-read scenarios.

  happens-before:
    - Memory model guarantee: writes before unlock are visible after lock.
    - volatile write happens-before volatile read.
    - Thread.start() happens-before the started thread's first action.
    - Thread.join() happens-before the join returns.

  Thread Safety Levels:
    1. Immutable              -- No synchronization needed. (String, Integer)
    2. Thread-safe            -- Internal sync. (ConcurrentHashMap, AtomicInteger)
    3. Conditionally safe     -- Multiple operations on same object need external sync.
    4. Not thread-safe        -- External sync required. (HashMap, ArrayList)

----------------------------------------------------------------
COMMON PITFALLS
----------------------------------------------------------------

  1. Deadlock:
     Thread A holds Lock 1, waits for Lock 2.
     Thread B holds Lock 2, waits for Lock 1.
     Fix: always acquire locks in the same order.
          Use tryLock() with timeout: lock.tryLock(100, MILLISECONDS).

  2. Race Condition:
     check-then-act not atomic.
     Fix: use synchronized or AtomicReference for compound operations.

  3. Memory Visibility:
     Thread B may never see Thread A's writes without sync.
     Fix: volatile, synchronized, or atomic classes.

  4. Spurious Wakeup:
     Object.wait() can return without notify().
     Fix: always check condition in a while loop, not if:
     while (!condition) { lock.wait(); }

  5. Thread Starvation:
     Low-priority threads never get CPU.
     Fix: use fair locks: new ReentrantLock(true).

  6. ConcurrentModificationException:
     Modifying collection while iterating.
     Fix: CopyOnWriteArrayList, or ConcurrentHashMap, or synchronized copy.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is a race condition?
  A: Two or more threads access shared mutable state without proper synchronization,
     and the outcome depends on the timing/ordering of their execution.
     Example: count++ is read-increment-write, non-atomic — concurrent threads may
     both read the same value before either writes back.

  Q: What is the difference between synchronized and volatile?
  A: synchronized: mutual exclusion + visibility. Prevents concurrent access.
     volatile: visibility only. Variable reads/writes are not cached; all threads
     see the most recent value. Does NOT prevent race conditions on compound ops.

  Q: What is a deadlock and how do you prevent it?
  A: Deadlock: threads circularly wait for each other's locks.
     Prevention: (1) always acquire multiple locks in consistent global order,
     (2) use tryLock(timeout) to back off if lock unavailable,
     (3) use higher-level abstractions (ConcurrentHashMap, BlockingQueue).

  Q: What is the Java Memory Model (JMM)?
  A: Rules governing how thread reads/writes to shared memory are ordered.
     Key concept: happens-before. A write happens-before a read if they are
     connected by a happens-before chain (synchronized, volatile, thread start/join).
     Without happens-before, thread may see stale values.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Know BlockingQueue API (put, take, offer, poll) cold.
  - Know ExecutorService lifecycle: submit → Future → shutdown() → awaitTermination().
  - Know the difference between synchronized and volatile.
  - Know how to detect and prevent deadlocks.
  - CompletableFuture composition is a very common modern Java concurrency topic.
