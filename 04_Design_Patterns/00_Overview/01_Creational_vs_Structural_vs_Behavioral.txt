================================================================
  CREATIONAL vs STRUCTURAL vs BEHAVIORAL PATTERNS
================================================================

  Three meta-categories introduced by GoF to classify the 23 patterns.
  Each category addresses a different aspect of object-oriented design.

----------------------------------------------------------------
CATEGORY OVERVIEW
----------------------------------------------------------------

  Category      | Count | Focus
  --------------|-------|---------------------------------------------------
  Creational    |   5   | HOW objects are created
  Structural    |   7   | HOW classes/objects are composed
  Behavioral    |  11   | HOW objects communicate and distribute responsibility

----------------------------------------------------------------
1. CREATIONAL PATTERNS
----------------------------------------------------------------

  Focus: Object CREATION mechanisms. Decouple client from the
         specific class being instantiated. Answer: "Who creates the object?"

  SINGLETON
    Intent: Ensure a class has exactly ONE instance; provide global access.
    Example: Logger, Configuration, Thread Pool, Spring @Component (default).
    Key: private constructor + static getInstance() + volatile for thread safety.

  FACTORY METHOD
    Intent: Define an interface for creating an object, but let SUBCLASSES
            decide which class to instantiate.
    Example: BeanFactory.getBean(), abstract Creator with factory method.
    Benefit: Adding new product type only requires new subclass.

  ABSTRACT FACTORY
    Intent: Provide an interface for creating FAMILIES of related objects.
    Example: UI toolkit factory (WinButton, MacButton, LinuxButton), JPA provider.
    Difference from Factory Method: creates multiple related products, not just one.

  BUILDER
    Intent: Separate construction of a complex object from its representation.
    Example: StringBuilder, Lombok @Builder, UriComponentsBuilder.
    Benefit: Supports step-by-step construction; same process, different results.

  PROTOTYPE
    Intent: Create new objects by copying (cloning) an existing instance.
    Example: Object.clone(), Spring prototype bean scope.
    When: Object creation is expensive; clone is cheaper than new construction.

  Memory hook: "Can She Flirt And Build Plenty?"
    (C)reational = (S)ingleton + (F)actory Method + (A)bstract Factory + (B)uilder + (P)rototype

----------------------------------------------------------------
2. STRUCTURAL PATTERNS
----------------------------------------------------------------

  Focus: How classes and objects are COMPOSED to form larger structures.
         Deal with relationships between entities.

  ADAPTER
    Intent: Convert one interface into another that clients expect.
            Make incompatible interfaces work together.
    Example: InputStreamReader(InputStream), Spring HandlerAdapter, CSV to JSON.
    Types: Class Adapter (via inheritance), Object Adapter (via composition).

  BRIDGE
    Intent: Decouple an abstraction from its implementation so both can vary independently.
    Example: Shape (Circle, Square) + DrawingAPI (SVG, Raster). Shape holds reference to API.
    vs Adapter: Adapter makes incompatible things work. Bridge designs for independent variation.

  COMPOSITE
    Intent: Compose objects into tree structures (part-whole hierarchies).
            Treat individual objects and compositions uniformly.
    Example: File system (File + Directory), GUI widgets (Button + Panel), XML/JSON trees.
    Key: Component interface (shared), Leaf (no children), Composite (has children).

  DECORATOR
    Intent: Add responsibilities to an object DYNAMICALLY without subclassing.
    Example: Java I/O (BufferedReader → FileReader), Spring interceptors, logging.
    vs Inheritance: Decorator adds behavior at runtime; inheritance at compile time.

  FACADE
    Intent: Provide a simplified interface to a complex subsystem.
    Example: SLF4J over Log4j/Logback, JdbcTemplate over raw JDBC, Spring's RestTemplate.
    Key: Facade doesn't prevent direct access to subsystem — it provides convenience.

  FLYWEIGHT
    Intent: Use sharing to efficiently support large numbers of fine-grained objects.
    Example: String interning in Java, Integer cache (-128..127), font objects in word processors.
    Key: Separate intrinsic state (shared) from extrinsic state (per-instance, passed at runtime).

  PROXY
    Intent: Provide a surrogate/placeholder to control access to another object.
    Types:
      - Virtual Proxy: lazy initialization (load image only when displayed).
      - Protection Proxy: access control.
      - Remote Proxy: represent remote object.
      - Caching Proxy: cache expensive results.
    Example: Spring AOP proxy (@Transactional, @Cacheable), JDK dynamic proxy, CGLIB.

  Memory hook: "All Bears Can Dance For Powerful Princes"
    (A)dapter + (B)ridge + (C)omposite + (D)ecorator + (F)acade + flyweight + (P)roxy

----------------------------------------------------------------
3. BEHAVIORAL PATTERNS
----------------------------------------------------------------

  Focus: How objects COMMUNICATE and distribute responsibility.
         Define algorithms and control flow.

  CHAIN OF RESPONSIBILITY
    Intent: Pass request through chain of handlers; each decides to handle or forward.
    Example: Spring Security FilterChain, servlet filters, exception handlers.
    Key: Handler holds reference to next handler. Client sends to first.

  COMMAND
    Intent: Encapsulate a request as an object. Supports undo, queue, log.
    Example: Runnable/Callable, menu actions, transaction scripts, macros.
    Participants: Command (interface), ConcreteCommand, Receiver, Invoker, Client.

  INTERPRETER
    Intent: Define grammar and interpreter for a language.
    Example: SQL parsing, regex, expression evaluators.
    Less common in modern practice — often replaced by parser libraries.

  ITERATOR
    Intent: Provide a way to sequentially access elements without exposing internals.
    Example: java.util.Iterator, enhanced for-loop, Stream API.
    Java: Iterable<T>.iterator() — required for for-each loop support.

  MEDIATOR
    Intent: Define an object that encapsulates how objects interact. Reduces direct coupling.
    Example: Air traffic control, chat room (mediator = server), MVC (Controller as mediator).
    vs Observer: Mediator centralizes communication; Observer broadcasts to all listeners.

  MEMENTO
    Intent: Capture and externalize object state for later restoration (undo).
    Example: Text editor undo, game save points, transaction rollback.
    Key: Originator creates Memento; Caretaker holds it; only Originator accesses internals.

  OBSERVER
    Intent: Define one-to-many dependency. When subject changes, all dependents notified.
    Example: Spring ApplicationEvent/ApplicationListener, java.util.Observable (deprecated),
             Event listeners in GUI, RxJava, Kafka consumer.
    Key: Publisher/Subscriber. Loose coupling.

  STATE
    Intent: Allow object to alter its behavior when its internal STATE changes.
    Example: Vending machine, order workflow, traffic light, Spring StateMachine.
    vs Strategy: State manages transitions; Strategy is swapped externally by client.

  STRATEGY
    Intent: Define a family of algorithms; encapsulate each; make them interchangeable.
    Example: Comparator<T>, sorting algorithms, payment methods, compression codecs.
    Key: Context holds reference to Strategy; Strategy can be changed at runtime.

  TEMPLATE METHOD
    Intent: Define the skeleton of an algorithm in a base class; let subclasses
            fill in specific steps without changing the algorithm structure.
    Example: JdbcTemplate, AbstractList, Servlet lifecycle (init/service/destroy).
    vs Strategy: Template Method uses inheritance; Strategy uses composition.

  VISITOR
    Intent: Separate algorithm from the object structure it operates on.
    Example: Compiler AST traversal, tax calculators on product types.
    Adds new operations without modifying existing classes (but adding new types is hard).

----------------------------------------------------------------
CATEGORY COMPARISON — KEY INSIGHT
----------------------------------------------------------------

  Creational:  Answer "WHAT is created?"
  Structural:  Answer "HOW is it assembled?"
  Behavioral:  Answer "HOW does it behave and communicate?"

  Example applying all three categories to a NOTIFICATION SYSTEM:
    Creational:  Factory Method creates the right Notifier (Email vs SMS).
    Structural:  Decorator adds retry behavior around the base Notifier.
    Behavioral:  Observer triggers all registered Notifiers when event fires.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What's the difference between Decorator and Proxy?
  A: Decorator adds NEW behavior/responsibilities (wraps to enhance).
     Proxy controls ACCESS to an existing object (wraps to guard or cache).
     Both share the same interface as the wrapped object.

  Q: What's the difference between Strategy and Template Method?
  A: Template Method uses INHERITANCE — base class defines the algorithm skeleton,
     subclasses override steps. Strategy uses COMPOSITION — algorithm is
     encapsulated in a separate object injected at runtime.

  Q: What's the difference between Observer and Mediator?
  A: Observer: objects subscribe directly to a publisher; broadcasting.
     Mediator: objects route all communication THROUGH a central mediator object;
     reduces direct coupling between objects.

  Q: What's the difference between Factory Method and Abstract Factory?
  A: Factory Method creates ONE product; subclass decides which type.
     Abstract Factory creates FAMILIES of related products; factory object
     provides multiple creation methods for related types.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Most commonly asked in interviews: Singleton, Factory, Builder, Observer, Strategy,
    Decorator, Proxy, Adapter, Template Method, Command, Chain of Responsibility.
  - Know which category each pattern belongs to — interviewers often ask this directly.
  - Be ready to say: "I would use Strategy here because we need to swap algorithms
    at runtime without changing the client code."
  - Compare patterns when asked: "How is Adapter different from Decorator?" (common interview trap).
