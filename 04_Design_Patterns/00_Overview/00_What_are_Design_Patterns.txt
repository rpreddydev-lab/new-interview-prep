================================================================
  WHAT ARE DESIGN PATTERNS?
================================================================

  Design patterns are reusable, well-documented solutions to commonly
  occurring problems in software design. They are NOT code you can copy
  directly — they are TEMPLATES describing how to solve a problem
  that can be adapted to many different situations.

  Origin: "Gang of Four" (GoF) — Erich Gamma, Richard Helm, Ralph Johnson,
  John Vlissides. Book: "Design Patterns: Elements of Reusable Object-Oriented Software" (1994).
  23 original patterns organized into 3 categories.

----------------------------------------------------------------
WHY DESIGN PATTERNS MATTER
----------------------------------------------------------------

  1. Shared vocabulary: "Use a Singleton here" communicates intent instantly.
  2. Proven solutions: battle-tested, avoids reinventing the wheel.
  3. Code quality: patterns enforce separation of concerns, open/closed principle.
  4. Interview signal: knowing patterns shows architectural thinking.

----------------------------------------------------------------
THE THREE CATEGORIES (GoF)
----------------------------------------------------------------

  1. CREATIONAL (how objects are created):
     Abstract object creation. Decouples system from how objects are constructed.
     Patterns: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

  2. STRUCTURAL (how objects are composed):
     Organize classes/objects to form larger structures.
     Patterns: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.

  3. BEHAVIORAL (how objects interact and communicate):
     Patterns of communication between objects.
     Patterns: Chain of Responsibility, Command, Interpreter, Iterator,
               Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.

----------------------------------------------------------------
BEYOND GoF: ADDITIONAL PATTERN CATEGORIES
----------------------------------------------------------------

  4. CONCURRENCY PATTERNS (thread safety, parallel execution):
     Producer-Consumer, Thread Pool, Read-Write Lock, Active Object, Monitor.

  5. ARCHITECTURAL PATTERNS (system-level organization):
     MVC, MVP, MVVM, Event-Driven, Microservices, Layered Architecture.

  6. ENTERPRISE PATTERNS (distributed systems, web apps):
     Repository, Unit of Work, DAO, Service Layer, CQRS, Event Sourcing.

  These extend GoF's original 23 patterns to modern software needs.

----------------------------------------------------------------
PATTERN STRUCTURE
----------------------------------------------------------------

  Every pattern is described with:
    - Name: unique identifier and vocabulary term.
    - Intent: one-sentence purpose.
    - Motivation: the problem it solves.
    - Applicability: when to use it.
    - Structure: UML class diagram.
    - Participants: the classes/interfaces involved.
    - Collaborations: how participants work together.
    - Consequences: trade-offs and effects.
    - Implementation: hints and pitfalls.
    - Known uses: examples in real systems.
    - Related patterns: what it's similar to / different from.

----------------------------------------------------------------
DESIGN PATTERN vs ALGORITHM vs ARCHITECTURE
----------------------------------------------------------------

  Design Pattern:
    - Mid-level reusable solution to recurring OO design problem.
    - Describes relationships and interactions between objects/classes.
    - Example: Observer pattern for event notification.

  Algorithm:
    - Low-level step-by-step computational procedure.
    - Describes exact operations to transform data.
    - Example: QuickSort, Dijkstra's.

  Architecture Pattern:
    - High-level structural template for entire systems or subsystems.
    - Example: Microservices, Event-Driven, Layered (MVC).

----------------------------------------------------------------
WHEN DESIGN PATTERNS ARE (NOT) NEEDED
----------------------------------------------------------------

  Use them when:
    - You recognize a recurring problem that a pattern addresses.
    - You need extensibility, configurability, testability.
    - Code grows complex and needs clear structure.
    - Working in teams where shared vocabulary matters.

  Don't force them when:
    - Simple code doesn't need abstraction overhead.
    - YAGNI — "You Aren't Gonna Need It." Don't add complexity upfront.
    - Over-engineering with patterns adds more complexity than value.

----------------------------------------------------------------
DESIGN PATTERN FREQUENCY IN INTERVIEWS
----------------------------------------------------------------

  Very commonly asked:
    Singleton, Factory/Abstract Factory, Builder, Observer, Strategy,
    Decorator, Command, Proxy, Adapter, Iterator, Template Method.

  Less common but valuable:
    Composite, Facade, Flyweight, Chain of Responsibility, State,
    Mediator, Visitor.

  Asked in system design context:
    Repository, DAO, Service Layer, CQRS, Event Sourcing.

----------------------------------------------------------------
REAL-WORLD DESIGN PATTERNS IN JAVA/SPRING
----------------------------------------------------------------

  Pattern              Java/Spring Example
  -----------------    -----------------------------------------
  Singleton            Spring @Component (default scope), Logger
  Factory Method       BeanFactory.getBean(), valueOf() methods
  Abstract Factory     JPA provider configuration (Hibernate)
  Builder              StringBuilder, Lombok @Builder, UriComponentsBuilder
  Prototype            Object.clone(), Spring prototype scope
  Adapter              InputStreamReader(InputStream), Spring HandlerAdapter
  Decorator            Java I/O streams (BufferedReader wraps FileReader)
  Proxy                Spring AOP (@Transactional, @Cacheable), JDK dynamic proxy
  Observer             ApplicationEvent / ApplicationListener in Spring
  Strategy             Comparator<T>, Spring Authentication strategies
  Template Method      JdbcTemplate, RestTemplate, AbstractController
  Command              Runnable, Callable, Spring @Scheduled
  Iterator             java.util.Iterator, enhanced for-loop
  Composite            Component trees, XML/JSON parsers
  Chain of Resp.       Spring Security Filter Chain, javax.Servlet filters
  State                Spring StateMachine, workflow engines
  Flyweight            String interning, Integer cache (-128..127)

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the GoF "Gang of Four"?
  A: The four authors who wrote the seminal "Design Patterns" book (1994).
     They catalogued 23 object-oriented design patterns in 3 categories.

  Q: Is a design pattern reusable code?
  A: No — it's a reusable IDEA/TEMPLATE. You implement the pattern yourself
     adapted to your language and context.

  Q: What's the most important benefit of using design patterns in a team?
  A: Shared vocabulary. Saying "use Observer for this" immediately communicates
     the intended structure without lengthy explanation.

  Q: Are design patterns language-specific?
  A: GoF patterns are OO-paradigm-specific. Most apply to Java, C++, C#, Python etc.
     Some are less relevant in functional languages where functions are first-class.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Be able to name all 23 GoF patterns and categorize them (Creational/Structural/Behavioral).
  - For each pattern: know INTENT, one real-world example, and one Java example.
  - Don't over-use patterns in code — interviewers also value simplicity.
  - Know the Spring examples — many Spring internals are pattern implementations.
