================================================================
  CREATIONAL PATTERNS — OVERVIEW
================================================================

  Creational patterns abstract the OBJECT CREATION process.
  They decouple the client code from the specific classes being instantiated,
  making the system more flexible and easier to change.

  Core question answered: "How should objects be created?"

----------------------------------------------------------------
THE 5 GoF CREATIONAL PATTERNS + BONUS
----------------------------------------------------------------

  Pattern           Problem Solved                               Key Mechanism
  ----------------  -------------------------------------------  ---------------------------
  Singleton         Ensure exactly one instance exists           Private constructor + static field
  Factory Method    Subclass decides which class to create       Override factory method
  Abstract Factory  Create families of related objects           Factory interface with multiple create methods
  Builder           Construct complex objects step-by-step       Builder class + method chaining
  Prototype         Clone existing objects cheaply               clone() / copy constructor
  Object Pool       Reuse expensive objects instead of recreating Pool of pre-created instances (bonus)

----------------------------------------------------------------
WHEN TO USE EACH
----------------------------------------------------------------

  Singleton:
    - Shared resource: Logger, Configuration, Thread Pool, Cache.
    - Only ONE instance must exist at all times.
    - Caution: avoid for services that should be testable — prefer DI.

  Factory Method:
    - Client should not know the exact class being created.
    - Subclasses need to control which concrete class is instantiated.
    - Adding new products without changing existing code.

  Abstract Factory:
    - Must create families of related objects (e.g., OS-specific widgets).
    - Products must be used together; enforce consistency within a family.
    - Multiple product families need to be swappable (e.g., DB provider).

  Builder:
    - Object has many optional parameters (avoid telescoping constructors).
    - Complex construction process with multiple steps.
    - Need to create different representations of the same construction process.

  Prototype:
    - Object creation is expensive; copying is cheaper.
    - Classes to instantiate are specified at runtime.
    - Copy of an object is needed, customized slightly (registry of prototypes).

  Object Pool:
    - Object creation and teardown is expensive (DB connections, threads, parsers).
    - Objects are used briefly and can be reused.

----------------------------------------------------------------
QUICK CODE SKELETON COMPARISON
----------------------------------------------------------------

  SINGLETON (double-checked locking):
  -------
    public class Config {
        private static volatile Config instance;
        private Config() {}
        public static Config getInstance() {
            if (instance == null) {
                synchronized (Config.class) {
                    if (instance == null) {
                        instance = new Config();
                    }
                }
            }
            return instance;
        }
    }

  FACTORY METHOD:
  -------
    abstract class Notifier {
        abstract void send(String message);
        // other shared logic
    }
    class EmailNotifier extends Notifier { void send(String msg) { ... } }
    class SMSNotifier  extends Notifier { void send(String msg) { ... } }

    abstract class NotifierFactory {
        abstract Notifier createNotifier();     // <-- factory method
    }
    class EmailFactory extends NotifierFactory {
        Notifier createNotifier() { return new EmailNotifier(); }
    }

  ABSTRACT FACTORY:
  -------
    interface UIFactory {
        Button createButton();
        TextField createTextField();
    }
    class WindowsUIFactory implements UIFactory { ... }
    class MacUIFactory     implements UIFactory { ... }

  BUILDER:
  -------
    public class Pizza {
        private String size;
        private boolean cheese, pepperoni;

        private Pizza(Builder b) { this.size=b.size; this.cheese=b.cheese; ... }

        public static class Builder {
            private String size;
            private boolean cheese, pepperoni;
            public Builder(String size) { this.size = size; }
            public Builder cheese()     { this.cheese = true; return this; }
            public Builder pepperoni()  { this.pepperoni = true; return this; }
            public Pizza build()        { return new Pizza(this); }
        }
    }
    // Usage: Pizza p = new Pizza.Builder("large").cheese().pepperoni().build();

  PROTOTYPE:
  -------
    public class Employee implements Cloneable {
        private String name;
        private List<String> skills;

        @Override
        public Employee clone() {
            try {
                Employee e = (Employee) super.clone();
                e.skills = new ArrayList<>(this.skills); // deep copy
                return e;
            } catch (CloneNotSupportedException ex) { throw new RuntimeException(ex); }
        }
    }

----------------------------------------------------------------
RELATIONSHIPS AND TRADE-OFFS
----------------------------------------------------------------

  Factory Method vs Abstract Factory:
    - Factory Method: ONE product; subclass decides.
    - Abstract Factory: MULTIPLE related products; factory object provides all.
    - Abstract Factory often uses Factory Methods internally.

  Builder vs Factory:
    - Factory: creates object in one step; client doesn't control steps.
    - Builder: creates object in multiple steps; client controls the process.
    - Use Builder when construction is complex; Factory when creation is simple.

  Prototype vs Builder:
    - Prototype: copy existing, then tweak.
    - Builder: construct fresh from scratch via step-by-step.

  Singleton vs Static Class:
    - Static class can't be passed around as object or implement interfaces.
    - Singleton is a real object — can implement interfaces, be subclassed.
    - Singleton testable (mockable via interface); static methods are not easily mockable.

----------------------------------------------------------------
CREATIONAL PATTERNS IN SPRING
----------------------------------------------------------------

  Spring heavily leverages Creational patterns under the hood:

    Singleton  -->  Default bean scope. ApplicationContext holds one instance per bean.
    Prototype  -->  @Scope("prototype") creates new instance per injection.
    Factory    -->  BeanFactory, FactoryBean<T>, @Bean factory methods in @Configuration.
    Builder    -->  UriComponentsBuilder, MockMvcRequestBuilders, WebClient.Builder.
    Abstract Factory  -->  TransactionManagerFactory, DataSourceFactory.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What problem do Creational patterns solve?
  A: They decouple the process of object creation from the code that uses the
     objects, making the system more flexible and easier to extend or change.

  Q: Why not just use "new" everywhere?
  A: "new" tightly couples code to a concrete class. Creational patterns
     introduce an indirection — the client depends on an interface, not
     an implementation. This makes it easy to swap implementations without
     changing client code.

  Q: Which creational pattern does Spring's @Bean use?
  A: Factory Method — the @Bean annotated method in @Configuration is
     essentially a factory method that Spring invokes to create a bean.

  Q: When is Singleton scope dangerous?
  A: When the Singleton holds mutable state. Multiple threads may corrupt
     the shared state. Also, Singletons hide dependencies and make
     unit testing hard (can't be easily replaced with a mock).

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Know the five GoF creational patterns cold: name, intent, one-line Java example.
  - Be ready to code Singleton (thread-safe with DCL) and Builder (inner static Builder class).
  - Abstract Factory is commonly asked for "Design a UI framework" or "Design DB-agnostic layer."
  - Mention that Spring solves most of these for you — show awareness that in real apps, @Autowired
    + @Component often replaces manual pattern implementation.
