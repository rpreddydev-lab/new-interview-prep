================================================================
  SINGLETON PATTERN
================================================================

  Category:   Creational
  Intent:     Ensure a class has exactly ONE instance and provide a global
              access point to it.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Very high in interviews. Most commonly asked creational pattern.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Some resources must have exactly one shared instance:
    - Configuration settings read from a file/env
    - Logger (central logging facility)
    - Thread pool (pre-allocated pool of threads)
    - Connection pool (e.g., HikariCP)
    - Registry of resources

  Without Singleton: multiple instances created, potentially inconsistent
  state, wasted resources.

----------------------------------------------------------------
IMPLEMENTATION VARIANTS
----------------------------------------------------------------

  1. EAGER INITIALIZATION (thread-safe, simple)
  -----------------------------------------------
    public class Singleton {
        private static final Singleton INSTANCE = new Singleton();

        private Singleton() {}

        public static Singleton getInstance() {
            return INSTANCE;
        }
    }

    Pros:  Thread-safe (class loading is thread-safe by JVM).
           Simple. No synchronization overhead at call time.
    Cons:  Created even if never used (eager). Wastes memory if creation is heavy.

  2. LAZY INITIALIZATION — DOUBLE-CHECKED LOCKING (DCL)
  -------------------------------------------------------
    public class Singleton {
        private static volatile Singleton instance;

        private Singleton() {}

        public static Singleton getInstance() {
            if (instance == null) {                    // first check (no lock)
                synchronized (Singleton.class) {
                    if (instance == null) {            // second check (with lock)
                        instance = new Singleton();
                    }
                }
            }
            return instance;
        }
    }

    Why volatile?
      Without volatile, object publication may be incomplete — another thread
      may see instance as non-null before the constructor finishes executing
      (CPU instruction reordering). volatile ensures full visibility.

    Pros:  Lazy (created only when needed). Thread-safe. Fast (only one sync block).
    Cons:  Slightly complex. Requires Java 5+ for volatile fix.

  3. BILL PUGH / INITIALIZATION-ON-DEMAND HOLDER (preferred)
  ------------------------------------------------------------
    public class Singleton {
        private Singleton() {}

        private static class Holder {
            private static final Singleton INSTANCE = new Singleton();
        }

        public static Singleton getInstance() {
            return Holder.INSTANCE;
        }
    }

    How it works: Holder class is not loaded until getInstance() is called.
    JVM guarantees class initialization is thread-safe. No synchronization needed.

    Pros:  Lazy. Thread-safe without synchronization. Cleanest approach.
    Cons:  Slightly less obvious to junior readers.

  4. ENUM SINGLETON (Josh Bloch's recommendation)
  -------------------------------------------------
    public enum Singleton {
        INSTANCE;

        public void doSomething() { ... }
    }
    // Usage: Singleton.INSTANCE.doSomething();

    Pros:  Thread-safe. Handles serialization automatically (prevents duplicate via deserialization).
           Prevents reflection attacks.
    Cons:  Less flexible — can't extend a class (enums can't extend anything else).
           Some find it unnatural for non-enum semantics.

  5. SYNCHRONIZED METHOD (simplest thread-safe, bad performance)
  ---------------------------------------------------------------
    public static synchronized Singleton getInstance() {
        if (instance == null) instance = new Singleton();
        return instance;
    }
    // DON'T USE: synchronizes on EVERY call, not just first. Extreme performance penalty.

----------------------------------------------------------------
SINGLETON THREAD SAFETY VISUALIZATION
----------------------------------------------------------------

  Thread A                Thread B              instance field
  --------                --------              --------------
  getInstance()                                 null
  first check: null
  enters sync block
  second check: null
  creates instance                              <being constructed...>
  volatile write                                <INSTANCE written>
  exits sync block
                          getInstance()
                          first check: non-null <-- sees completed instance (volatile)
                          returns INSTANCE

  WITHOUT volatile:
    Thread B may see instance as non-null but object construction not yet complete.
    volatile prevents this instruction reordering.

----------------------------------------------------------------
SINGLETON WITH REFLECTION ATTACK PROTECTION
----------------------------------------------------------------

  Reflection can break Singleton by calling private constructor:
    Constructor<Singleton> c = Singleton.class.getDeclaredConstructor();
    c.setAccessible(true);
    Singleton s2 = c.newInstance(); // BREAKS Singleton!

  Protection (throw exception in constructor if already instantiated):
    private Singleton() {
        if (instance != null) {
            throw new RuntimeException("Use getInstance() — reflection not allowed");
        }
    }

  Best protection: use ENUM Singleton — immune to reflection attacks by JVM design.

----------------------------------------------------------------
SINGLETON WITH SERIALIZATION PROTECTION
----------------------------------------------------------------

  Deserialization creates a new instance, breaking Singleton.
  Fix: implement readResolve():

    protected Object readResolve() {
        return getInstance();
    }

  Enum Singleton handles this automatically.

----------------------------------------------------------------
SINGLETON IN SPRING
----------------------------------------------------------------

  Spring manages Singleton beans automatically with the IoC container.
  Default scope is Singleton — one instance per ApplicationContext.

    @Service
    public class UserService { ... }
    // Spring creates ONE instance, injects it wherever @Autowired appears.

  Spring Singleton vs GoF Singleton:
    - Spring: one instance per ApplicationContext (can have multiple contexts).
    - GoF: one instance per JVM ClassLoader.
    - In practice, Spring Singleton is fine for most needs.

  Spring Singleton is PREFERRED over manual GoF Singleton in Spring apps:
    - Testable (can inject mocks via constructor injection).
    - No global static state.
    - Lifecycle managed (init, destroy).

----------------------------------------------------------------
COMMON INTERVIEW PROBLEMS USING SINGLETON
----------------------------------------------------------------

  1. Implement a Logger class as Singleton.
  2. Design a thread-safe Connection Pool Manager (Singleton holding pool).
  3. Design a Cache Manager (Singleton with Map<String, Object>).
  4. Implement a Configuration Reader (reads once, shared everywhere).
  5. LRU Cache design (singleton cache with eviction).

  Java Logger Example:
  -------
    public class AppLogger {
        private static volatile AppLogger instance;
        private final java.util.logging.Logger logger;

        private AppLogger() {
            logger = java.util.logging.Logger.getLogger("AppLogger");
        }

        public static AppLogger getInstance() {
            if (instance == null) {
                synchronized (AppLogger.class) {
                    if (instance == null) instance = new AppLogger();
                }
            }
            return instance;
        }

        public void log(String message) { logger.info(message); }
    }

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  getInstance() call:
    - Eager / Holder: O(1) — no synchronization needed.
    - DCL: O(1) amortized — first call pays sync cost, all subsequent O(1).
    - Synchronized method: O(1) but contended — every call acquires monitor lock.

  Space: O(1) — one instance total.

----------------------------------------------------------------
ANTI-PATTERN WARNING
----------------------------------------------------------------

  Singleton OVERUSE is an anti-pattern:
    - Creates hidden global state.
    - Breaks testability (hard to mock static getInstance()).
    - Violates Dependency Inversion Principle.
    - Makes code hard to parallelize (shared mutable state).

  Rule of thumb:
    Singleton is appropriate ONLY for truly stateless or immutable resources
    (logger, config) OR when managed by a DI container (Spring).
    NEVER use Singleton for services that hold mutable user/domain state.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Why do we need volatile in double-checked locking?
  A: Without volatile, the JVM can reorder instructions. After entering sync block,
     `instance = new Singleton()` involves three steps: allocate memory, init object,
     assign reference. The assignment can be reordered BEFORE initialization, so another
     thread sees non-null but uninitialized object. volatile prevents this reordering.

  Q: What is the Bill Pugh Singleton?
  A: Uses a private static inner Holder class. JVM guarantees class initialization
     is atomic and thread-safe. The Holder class is loaded only when getInstance()
     is called — lazy without any synchronization overhead.

  Q: How would you break a Singleton?
  A: Reflection (call private constructor), serialization/deserialization (creates new object),
     multiple ClassLoaders (each has its own static state). Enum Singleton is immune to all three.

  Q: How does Spring Singleton differ from GoF Singleton?
  A: GoF = one instance per ClassLoader (JVM-wide). Spring = one instance per
     ApplicationContext. Spring Singleton is preferred because it's DI-managed,
     testable, and has lifecycle callbacks.

  Q: Is Singleton thread-safe?
  A: Eager and Holder variants are thread-safe by default. DCL requires volatile.
     Synchronized method is thread-safe but has performance issues. Enum is
     always thread-safe. The INSTANCE itself may or may not be thread-safe depending
     on its own internal state management.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Always write DCL with volatile in interviews — shows thread safety awareness.
  - Mention Bill Pugh as the "cleanest" approach if asked for best practice.
  - Know to say: "In modern Java/Spring, I'd use DI instead of manual Singleton."
  - Be ready to explain WHY volatile is needed — instruction reordering.
  - Know how to break and protect a Singleton (reflection, serialization, enum).
