================================================================
  DEPENDENCY INJECTION AND SPRING IOC CONTAINER
================================================================

  DI is the most important pattern in enterprise Java.
  It implements Inversion of Control: instead of objects creating
  their own dependencies, the container injects them from outside.

----------------------------------------------------------------
THE PROBLEM DI SOLVES
----------------------------------------------------------------

  Without DI (tightly coupled):

  public class OrderService {
      // Hard-coded dependency — impossible to test without DB
      private final OrderRepository repo = new JpaOrderRepository();
      private final EmailService email = new SmtpEmailService();
  }

  Problems:
    - Cannot swap implementations without changing OrderService
    - Cannot unit-test OrderService without real DB and SMTP
    - OrderService controls lifecycle (created here, can't share)
    - Circular dependencies: A creates B creates A = StackOverflow


  With DI (loosely coupled):

  public class OrderService {
      private final OrderRepository repo;
      private final EmailService email;

      // Constructor injection: dependencies injected from outside
      public OrderService(OrderRepository repo, EmailService email) {
          this.repo = repo;
          this.email = email;
      }
  }

  // Test: inject fakes
  OrderService svc = new OrderService(new InMemoryOrderRepository(), new FakeEmailService());

  // Production: Spring injects real implementations

----------------------------------------------------------------
THREE INJECTION STYLES
----------------------------------------------------------------

  1. CONSTRUCTOR INJECTION (RECOMMENDED)
     =====================================
     @Service
     public class PaymentService {
         private final PaymentGateway gateway;
         private final AuditLog auditLog;

         // @Autowired optional since Spring 4.3 if single constructor
         @Autowired
         public PaymentService(PaymentGateway gateway, AuditLog auditLog) {
             this.gateway = gateway;
             this.auditLog = auditLog;
         }
     }

     Pros:
       - Dependencies explicit in constructor signature
       - Enables final fields (immutable bean)
       - Fails fast at startup if bean missing
       - Easy to test without Spring (just call new)
       - No circular dependency at startup (detects early)

  2. SETTER INJECTION (FOR OPTIONAL DEPENDENCIES)
     ================================================
     @Service
     public class NotificationService {
         private AuditLog auditLog;  // optional — has default behavior

         @Autowired(required = false)
         public void setAuditLog(AuditLog auditLog) {
             this.auditLog = auditLog;
         }
     }

     When: optional dependency with fallback default (Null Object).
     Risk: bean used before setter called (partial initialization).

  3. FIELD INJECTION (AVOID)
     ==========================
     @Service
     public class OrderService {
         @Autowired  // IntelliJ warns: field injection not recommended
         private OrderRepository repo;
     }

     Problems:
       - Cannot make field final
       - Cannot test without Spring context or reflection hacks
       - Breaks encapsulation (field is hidden)
       - Circular dependencies easier to create silently

@QUALIFIER AND @PRIMARY — CHOOSING BETWEEN MULTIPLE IMPLEMENTATIONS
----------------------------------------------------------------

  When multiple beans implement the same interface:

  public interface DiscountService {
      double apply(double price);
  }

  @Service("studentDiscount")
  public class StudentDiscountService implements DiscountService {
      public double apply(double price) { return price * 0.80; }
  }

  @Service("veteranDiscount")
  public class VeteranDiscountService implements DiscountService {
      public double apply(double price) { return price * 0.75; }
  }

  // Injection options:

  // 1. @Qualifier — name-based selection
  @Autowired
  @Qualifier("studentDiscount")
  private DiscountService discountService;

  // 2. @Primary — default selection if no @Qualifier present
  @Service
  @Primary
  public class DefaultDiscountService implements DiscountService { ... }

  // 3. Inject all implementations (Map — keys = bean names)
  @Autowired
  private Map<String, DiscountService> discountServices;
  // key="studentDiscount", key="veteranDiscount"

  // 4. Inject List<DiscountService> — all implementations (unordered)
  @Autowired
  private List<DiscountService> allDiscounts;

  // 5. @Order or Ordered interface — control list order
  @Service
  @Order(1)
  public class PriorityDiscountService implements DiscountService { ... }

----------------------------------------------------------------
BEAN SCOPES
----------------------------------------------------------------

  Scope          Description                 Typical Use
  -----------    --------------------------  ---------------------
  singleton      ONE instance per context    Services, repositories
  prototype      NEW instance each inject    Stateful beans, mutable beans
  request        ONE per HTTP request        Request-scoped data
  session        ONE per HTTP session        User session state
  application    ONE per ServletContext      App-wide state
  websocket      ONE per WebSocket session   WebSocket handler state

  // Declare scope:
  @Bean
  @Scope("prototype")
  public UserPreferences userPreferences() {
      return new UserPreferences();
  }

  Injecting prototype into singleton — PROBLEM:
  Singleton holds reference to ONE prototype instance (defeats purpose).

  Fix 1: ObjectProvider<T> (Spring-recommended)
  @Service
  public class OrderProcessor {
      @Autowired
      private ObjectProvider<OrderContext> contextProvider;

      public void process(Order order) {
          OrderContext ctx = contextProvider.getObject(); // new each time
      }
  }

  Fix 2: @Lookup (method injection)
  @Service
  public abstract class OrderProcessor {
      @Lookup
      protected abstract OrderContext createContext();  // Spring overrides this
  }

  Fix 3: ApplicationContextAware (verbose, avoid)

@PROFILE — ENVIRONMENT-SPECIFIC BEANS
----------------------------------------------------------------

  @Configuration
  public class DataSourceConfig {

      @Bean
      @Profile("dev")
      public DataSource h2DataSource() {
          return new EmbeddedDatabaseBuilder()
              .setType(H2)
              .build();
      }

      @Bean
      @Profile("prod")
      public DataSource prodDataSource() {
          return new HikariDataSource(prodConfig());
      }
  }

  // Activate: spring.profiles.active=prod in application.properties
  // Or: @ActiveProfiles("dev") in test class

  @Profile("!prod")  -- active when NOT prod
  @Profile({"dev","staging"})  -- active in dev OR staging

----------------------------------------------------------------
@CONDITIONAL — PROGRAMMATIC BEAN REGISTRATION
----------------------------------------------------------------

  @Bean
  @ConditionalOnProperty(name = "feature.audit", havingValue = "true")
  public AuditService auditService() {
      return new DatabaseAuditService();
  }

  @Bean
  @ConditionalOnMissingBean(AuditService.class)
  public AuditService noOpAuditService() {
      return new NoOpAuditService();   // Null Object pattern
  }

  @Bean
  @ConditionalOnClass(name = "com.amazonaws.services.s3.AmazonS3")
  public StorageService s3StorageService() { ... }

  Common conditions:
    @ConditionalOnProperty    -- config property value
    @ConditionalOnMissingBean -- no bean of that type exists
    @ConditionalOnBean        -- a bean of that type exists
    @ConditionalOnClass       -- class is on classpath
    @ConditionalOnExpression  -- SpEL expression true

----------------------------------------------------------------
CONFIGURATION STYLES
----------------------------------------------------------------

  1. @Component + @Autowired (component scanning)
     Spring scans packages; finds @Component/@Service/@Repository/@Controller
     and creates beans automatically.

  2. @Configuration + @Bean (Java config)
     @Configuration
     public class AppConfig {
         @Bean
         public OrderService orderService(OrderRepository repo, EmailService email) {
             return new OrderService(repo, email);
         }

         @Bean
         public OrderRepository orderRepository(DataSource ds) {
             return new JpaOrderRepository(ds);
         }
     }
     Use when: third-party classes (can't annotate), complex initialization logic.

  3. XML config — legacy; avoid in new projects.

  @Bean method parameters = constructor injection by type from container.

----------------------------------------------------------------
CIRCULAR DEPENDENCY — DETECTION AND FIX
----------------------------------------------------------------

  Spring detects circular constructor injection at startup.
  Example: A requires B; B requires A → BeanCurrentlyInCreationException.

  Fixes (in order of preference):
    1. Refactor: extract common behavior to C; A and B depend on C
    2. @Lazy on one constructor parameter (deferred initialization)
    3. Use setter injection for one side (not recommended)
    4. ObjectProvider<B> in A (late resolution)

  @Service
  public class ServiceA {
      private final ObjectProvider<ServiceB> serviceBProvider;
      // ObjectProvider resolves on first call, not at startup
  }

----------------------------------------------------------------
SPRING DI PATTERNS SUMMARY
----------------------------------------------------------------

  Pattern                   Spring Implementation
  ----------------------    ------------------------------------------
  Factory                   BeanFactory, @Bean methods, ObjectFactory
  Strategy                  @Qualifier selects implementation
  Composite                 List<StrategyInterface> injection
  Singleton                 Default @Scope
  Prototype                 @Scope("prototype") + ObjectProvider
  Null Object               @ConditionalOnMissingBean + no-op bean
  Observer                  @EventListener
  Decorator/Proxy           @Transactional, @Cacheable, @Async (CGLIB)
  Template Method           JdbcTemplate, RestTemplate, JpaRepository

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Constructor vs setter vs field injection — which is best and why?
  A: Constructor injection. Dependencies explicit, enables final fields (immutable),
     fails fast at startup, easy to unit test without Spring (just use new).
     Field injection hides dependencies and prevents final fields.

  Q: How does Spring resolve multiple implementations?
  A: By type first. If ambiguous: @Qualifier selects by name, @Primary marks default.
     Inject Map<String, Interface> to get all by name, List<Interface> to get all.

  Q: What is the difference between @Component, @Service, @Repository, @Controller?
  A: All are @Component specializations. Same bean creation behavior.
     @Repository: enables exception translation (Spring DataAccessException wrapping).
     @Controller/@RestController: processed by MVC dispatcher.
     @Service: no extra behavior; semantic annotation for clarity.

  Q: How do you inject a prototype-scoped bean into a singleton?
  A: Use ObjectProvider<T>.getObject() (preferred). Or @Lookup method injection.
     Direct field injection gets only one instance (prototype purpose defeated).

  Q: What is @ConditionalOnMissingBean used for?
  A: Auto-configuration override pattern. Library provides default bean with
     @ConditionalOnMissingBean. Application can override by defining its own bean.
     Spring Boot auto-configurations use this heavily.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Lead with WHY DI: testability, replaceability, lifecycle management.
  - Constructor injection is the single most important recommendation.
  - Scope + ObjectProvider shows advanced understanding.
  - Map<String, Interface> injection pattern = no if-else strategy dispatch.
  - @Profile + @ConditionalOnProperty = environment-specific config.
