SECTION 1: CREATIONAL PATTERNS
================================================================

Q: How do you implement a thread-safe Singleton in Java?
   Five ways in order of preference:

   1. Enum Singleton (BEST — Josh Bloch)
      public enum AppConfig {
          INSTANCE;
          public String get(String key) { return props.getProperty(key); }
      }
      Thread-safe, serialization-safe, reflection-safe by JVM guarantee.

   2. Holder (Bill Pugh) — lazy + thread-safe without synchronized
      private static class Holder {
          private static final Singleton INSTANCE = new Singleton();
      }
      public static Singleton getInstance() { return Holder.INSTANCE; }

   3. DCL + volatile — understand WHY volatile is needed
      private static volatile Singleton instance;
      // volatile prevents write reordering: alloc → init → assign
      // Without volatile: another thread may see half-initialized object

   4. Eager static final — simplest, always initialized
   5. Synchronized method — correct but slow


Q: Factory Method vs Abstract Factory — when to use each?
   Factory Method: one product family, subclasses decide which class to create.
   Abstract Factory: multiple related product families; ensures compatibility.
   Example: Factory Method = Document.createPage(); Abstract Factory = UITheme
   where each theme provides createButton()+createTextField()+createMenu() together.


Q: What is the Builder pattern? When is it better than a constructor?
   When: 4+ parameters, many optional, need validation before construction,
   want immutable objects. Java idiom: static inner Builder class with fluent
   setters + build() that validates. Lombok @Builder automates this.
   Avoid: Lombok @Builder with JPA entities (removes no-arg constructor).


Q: How does Prototype differ from copying an object?
   Prototype implements Cloneable and overrides clone() or provides a copy()
   factory method. Key issue: shallow vs deep copy. Deep copy: copy all mutable
   fields recursively. Java clone() is shallow by default — must manually deep copy.
   Alternative: copy constructor or serialization-based deep copy.


Q: What is the Object Pool pattern? When is it beneficial?
   Maintains a pool of reusable objects to avoid expensive creation.
   Examples: JDBC connection pools (HikariCP), thread pools (ThreadPoolExecutor),
   ByteBuffer pools. Beneficial when: creation cost is high, objects are frequent,
   short-lived, and their state can be reset. Risk: stale objects, resource leaks
   if not returned to pool.

SECTION 2: STRUCTURAL PATTERNS
================================================================

Q: Adapter vs Facade vs Proxy — differentiate clearly.

   Adapter:  converts one interface to another. Old interface → target interface.
             Example: InputStreamReader adapts InputStream to Reader.
             Purpose: compatibility between incompatible interfaces.

   Facade:   simplifies a complex subsystem behind one entry point.
             Example: ServiceFacade with placeOrder() hiding DB+cache+queue.
             Purpose: reduce complexity, not convert interface.

   Proxy:    same interface as subject; controls access, adds cross-cutting concern.
             Types: Virtual (lazy init), Remote (network), Protection (security),
             Smart (ref counting, caching). Spring @Transactional = proxy.
             Purpose: interception/control, not conversion.

   Memory aid: Adapter changes interface. Facade simplifies. Proxy same interface.


Q: What is the Composite pattern? Give an example.
   Treats individual objects and compositions of objects uniformly through a
   common interface. Classic: File/Directory (both implement FileSystemEntry).
   Operations like getSize(), list() work on both leaf (File) and branch (Directory).
   Pitfall: type-checking (instanceof) breaks the pattern. Never add addChild()
   to the Component interface if leaves don't support it (violates LSP).


Q: How is Decorator different from Proxy?
   Both wrap an object and implement the same interface.
   Decorator: ADDS new behavior (BufferedInputStream adds buffering).
   Proxy: CONTROLS access to existing behavior (no new functionality, just interception).
   @Transactional proxy adds TX lifecycle but doesn't change method behavior.
   Decorator changes what the method DOES; Proxy changes WHEN/WHETHER it runs.


Q: Where is the Bridge pattern used in Java?
   Bridge: separate abstraction hierarchy from implementation hierarchy.
   Example: JDBC — java.sql.Connection is abstraction; OracleDriver/MySQLDriver
   are implementations. Your code depends on Connection; swapping driver = swap impl.
   AWT/Swing: Component (abstraction) + ComponentPeer (platform implementation).
   When to use: want to extend both independently; avoid 2*N subclass explosion.


Q: Flyweight pattern — explain and give a Java example.
   Share common state (intrinsic) among many objects; keep unique state (extrinsic) outside.
   Java String pool: identical strings share one object in pool.
   Integer cache: Integer.valueOf(-128..127) returns cached instances.
   Java chars in String: sharing reference to char[].
   When to use: millions of fine-grained objects with significant shared state.
   Intrinsic = shared, immutable. Extrinsic = context-specific, passed in.

SECTION 3: BEHAVIORAL PATTERNS
================================================================

Q: Strategy vs Template Method — key difference?
   Both define algorithms, but:
   Template Method: skeleton in base class (final method); steps in subclasses.
                    Inheritance-based. Algorithm structure fixed. Subclass fills steps.
   Strategy:        algorithm encapsulated in separate class/lambda.
                    Composition-based. Algorithm entirely replaceable at runtime.
   Template Method: IS-A, compile-time. Strategy: HAS-A, runtime.
   Modern preference: Strategy with lambdas over Template Method (avoids inheritance).


Q: Command vs Strategy — what's the difference?
   Strategy: encapsulates HOW to do something (algorithm).
             execute() called immediately; varies the algorithm.
   Command:  encapsulates WHAT to do (action + receiver + params).
             Stores for later: undo, queue, log. Can be undone/redone.
   Key: Command supports deferred execution and undo. Strategy does not.


Q: How does Iterator work in Java? Explain fail-fast.
   Iterator<E> has hasNext(), next(), remove(). for-each compiles to iterator calls.
   Fail-fast: ArrayList/HashMap track modCount. If collection modified during iteration
   (outside of iterator.remove()), next() throws ConcurrentModificationException.
   Fail-safe: CopyOnWriteArrayList, ConcurrentHashMap iterate over snapshot — no exception.
   Safe removal during iteration: iterator.remove() or collection.removeIf().


Q: Chain of Responsibility vs Decorator — how are they different?
   Chain of Responsibility: one request, multiple handlers, each decides pass-or-stop.
                             Purpose: decouple sender from receiver; first handler stops chain.
   Decorator: ALL wrappers in the chain execute; adds behavior rather than choosing a handler.
   CoR = OR (first handler wins). Decorator = AND (all add behavior).


Q: Observer vs Mediator — how do they relate?
   Observer: Subject broadcasts to all observers; observers register directly.
             Decouples subject from observers; observers still couple to subject's events.
   Mediator: Centralizes all interactions; objects communicate THROUGH mediator only.
             No direct object-to-object coupling except to mediator.
   Mediator can be implemented using Observer (Subject = Mediator, observers = colleagues).
   Observer: 1-to-N broadcast. Mediator: N-to-N controlled coordination.


Q: What is the State pattern? How does it prevent if-else chains?
   Each state is a class; context delegates operations to current state object.
   Invalid operations throw IllegalStateException in respective state.
   Adding a new state = new class, zero changes to existing code (OCP).
   vs. if-else/switch: one blob of conditions grows with each state; hard to test.
   Use Enum state machine when transitions are simple and states are few (<5).


Q: Visitor pattern — when to use, what problem does it solve?
   Add operations to a class hierarchy WITHOUT modifying the classes.
   Element has accept(Visitor v); v.visit(this) = double dispatch.
   Easy to add operation (new Visitor class). Hard to add element (all Visitors change).
   When to use: stable element hierarchy, frequent new operations (compilers, AST).
   When NOT to use: elements change frequently; breaks encapsulation.


Q: Memento vs Command for undo — which to choose?
   Memento: full snapshot of state at each step. Simple undo: restore snapshot.
            Memory-expensive if object is large.
   Command: stores inverse operation. execute() does action; undo() reverses it.
            Memory-efficient; complex for side-effectful operations.
   Combined: Command records what was done, Memento stores before-snapshot in Command.


Q: What is the Null Object pattern and when is it preferable to Optional?
   Null Object: provides default no-op implementation of an interface.
                Used for injected dependencies (logger, discount strategy).
                Caller never null-checks; no-op methods do nothing.
   Optional: return value from search/find that may find nothing.
             Forces caller to handle absence explicitly.
   Rule: Null Object = injectable dependency with default. Optional = return type for absent value.

SECTION 4: CONCURRENCY PATTERNS
================================================================

Q: Why is DCL (Double-Checked Locking) broken without volatile?
   Object creation is three steps: allocate memory, initialize object, assign reference.
   JVM/CPU may reorder to: allocate, assign, initialize.
   Second thread sees non-null reference and uses partially-initialized object.
   volatile forces happens-before: write to instance is visible to all threads
   AFTER all fields are written (no reordering).


Q: How does BlockingQueue implement Producer-Consumer?
   put() blocks producer when queue is full (natural backpressure).
   take() blocks consumer when queue is empty.
   Eliminates manual wait/notify loops. Thread-safe internal locking.
   ArrayBlockingQueue: bounded, fair option. LinkedBlockingQueue: optionally bounded,
   higher throughput (separate head/tail locks). SynchronousQueue: zero capacity, direct handoff.


Q: What is the difference between ReentrantLock and synchronized?
   synchronized: built-in, always fair=false, auto-release, no tryLock.
   ReentrantLock: explicit lock/unlock (must use try-finally), tryLock with timeout,
   lockInterruptibly(), fair mode option (new ReentrantLock(true)), Condition variables.
   Choose ReentrantLock when: need tryLock, timeout, interruptible, or fine-grained conditions.


Q: Explain ReadWriteLock and when it outperforms ReentrantLock.
   Multiple readers can hold readLock simultaneously. Writer needs exclusive writeLock.
   Beneficial when reads >> writes (ratio > 5:1). If writes are frequent, overhead
   of managing read/write locks may be worse than single lock.
   StampedLock: adds optimistic reads (no lock; validate afterward; fallback on conflict).


Q: What happens if an exception is thrown inside a scheduled periodic task?
   ScheduledExecutorService silently swallows the exception and cancels the future schedule.
   The task will NEVER run again. No error thrown to the caller.
   Fix: wrap every scheduled task body in try-catch; log all exceptions.
   Spring @Scheduled: same risk; Spring logs exception but continues scheduling.


Q: CountDownLatch vs CyclicBarrier — differences?
   CountDownLatch: one-time; main thread waits; workers call countDown().
                   Once 0, never resets.
   CyclicBarrier: reusable; N threads all wait for each other at barrier;
                  optional Runnable when all arrive; resets for next phase.
   Use CountDownLatch: main waits for N workers to finish.
   Use CyclicBarrier: N threads must all reach a checkpoint before any proceeds.


Q: What is the difference between Semaphore and Mutex?
   Mutex: binary lock with OWNERSHIP — the thread that locks must unlock.
          ReentrantLock is a mutex.
   Semaphore: counting synchronizer, NO OWNERSHIP — any thread can release.
              Use for: limiting concurrent access to N resources, signaling.
   Binary Semaphore (N=1) ≠ Mutex: no ownership enforcement.

SECTION 5: JAVA-SPECIFIC AND SPRING QUESTIONS
================================================================

Q: How does Spring implement Singleton, Factory, Strategy, Decorator internally?
   Singleton: @Component/@Bean beans are singleton scoped per ApplicationContext.
   Factory: BeanFactory, ObjectFactory<T>, @Bean factory methods.
   Strategy: HandlerMapping, ViewResolver, TransactionManager, DataSource — all strategy.
   Decorator: CGLIB proxy for @Transactional, @Cacheable, @Async.
   Composite: CompositeHealthIndicator, CompositeMeterRegistry.


Q: What pattern does Spring @Transactional use? How does it work?
   Proxy pattern (specifically dynamic proxy / CGLIB proxy).
   Spring generates a subclass (CGLIB) or interface proxy (JDK) at runtime.
   The proxy wraps your bean, intercepts method calls, starts/commits/rolls back TX.
   @Transactional on self-calls does NOT work (call goes around proxy).


Q: How does Spring implement Dependency Injection as a pattern?
   DI is an application of Inversion of Control + Strategy + Factory.
   The IoC Container (BeanFactory) plays Factory (creates objects).
   @Qualifier selects which Strategy implementation to inject.
   Constructor injection preferred: dependencies explicit, facilitates testing,
   enables immutable beans (final fields), no partial initialization.


Q: When should you use constructor vs setter injection?
   Constructor: mandatory dependencies; guarantees complete state; immutable beans.
   Setter: optional dependencies with default; allows circular dependencies (avoid).
   Field (@Autowired on field): NOT recommended — breaks encapsulation, hard to test.
   Spring team recommends constructor injection for all required dependencies.


Q: How do you test a class using design patterns?
   Strategy/Observer: inject mock or lambda in test — no need for mocking framework.
   Command: unit-test execute() and undo() in isolation.
   Factory/Abstract Factory: test what the factory creates, not the factory itself.
   Template Method: write abstract test method in base test class; concrete tests fill steps.
   Decorator: test each decorator independently + integration of full chain.

SYSTEM DESIGN PATTERN QUESTIONS
================================================================

Q: Design a notification system supporting Email, SMS, Push.
   Answer structure:
   - NotificationStrategy interface (Strategy pattern)
   - Map<Channel, NotificationStrategy> bean map in Spring
   - Observer pattern: OrderService publishes event; NotificationService listens
   - @EventListener + @Async for non-blocking delivery
   - @TransactionalEventListener(AFTER_COMMIT) to avoid sending on rollback
   - Retry with Decorator or Spring @Retryable on strategy

Q: How would you implement undo/redo in a text editor?
   - Command pattern: each edit = Command with execute() + undo()
   - UndoManager holds Deque<Command> undoStack + redoStack
   - execute: push to undo; clear redo
   - undo: pop undo, execute undo(), push to redo
   - OR: Memento if commands are hard to reverse (full snapshot)
   - Bounded history: removeLast() when deque exceeds MAX_HISTORY

Q: Implement a plugin-based pricing engine.
   - PricingStrategy interface (Strategy)
   - @Component beans auto-registered; injected as Map<String, PricingStrategy>
   - Chain of strategies via Decorator or Composite
   - Configuration: @ConfigurationProperties maps key → strategy bean name
   - Spring @Profile for environment-specific pricing (dev vs prod)
