================================================================
  DECORATOR PATTERN IN JAVA — I/O STREAMS AND BEYOND
================================================================

  Decorator adds behavior to an object at runtime by wrapping it.
  Java's I/O stream hierarchy is the most famous use of Decorator.
  Java 8+ extends this to Functions, Streams, and Comparators.

----------------------------------------------------------------
DECORATOR STRUCTURE RECAP
----------------------------------------------------------------

  Component interface
        ^
        |
  ConcreteComponent         <-- base implementation
        ^
        |
  Decorator (abstract)      <-- wraps Component, delegates to it
        ^
        |
  ConcreteDecoratorA        <-- adds behavior A
  ConcreteDecoratorB        <-- adds behavior B

  Key property: Decorator implements the SAME interface as the
  component it wraps. Client doesn't know if it's talking to the
  base or a chain of decorators.

----------------------------------------------------------------
JAVA I/O STREAMS — THE CANONICAL DECORATOR
----------------------------------------------------------------

  InputStream / OutputStream hierarchy:

  InputStream (Component)
    |-- FileInputStream        (ConcreteComponent — bytes from file)
    |-- ByteArrayInputStream   (ConcreteComponent — bytes from array)
    |-- FilterInputStream      (Decorator base)
          |-- BufferedInputStream   (adds buffering — reduces syscalls)
          |-- DataInputStream       (adds readInt, readDouble, etc.)
          |-- GZIPInputStream       (adds decompression)
          |-- CheckedInputStream    (adds checksum verification)
          |-- CipherInputStream     (adds decryption)

  // Wrapping chain: file → buffer → decompress → decrypt
  InputStream in = new CipherInputStream(
                       new GZIPInputStream(
                           new BufferedInputStream(
                               new FileInputStream("data.bin"),
                               8192   // 8KB buffer
                           )
                       ),
                       cipher
                   );

  // All decorators are just InputStream — consistent API.
  // Decompression is transparent to the caller reading bytes.

  Same pattern for Reader/Writer hierarchy:
  Reader → InputStreamReader (bridge) → BufferedReader (buffering)
  Writer → OutputStreamWriter         → BufferedWriter → PrintWriter

  // Classic: wrap FileWriter in BufferedWriter in PrintWriter
  try (PrintWriter out = new PrintWriter(new BufferedWriter(
          new FileWriter("output.txt")))) {
      out.println("Hello Decorator");
  }

  // Modern NIO.2: Files.newBufferedWriter creates the chain for you
  try (BufferedWriter out = Files.newBufferedWriter(Path.of("output.txt"))) {
      out.write("Hello");
  }

----------------------------------------------------------------
CUSTOM DECORATOR — COFFEE SHOP EXAMPLE
----------------------------------------------------------------

  // Component
  public interface Coffee {
      String getDescription();
      double getCost();
  }

  // Concrete Component
  public class SimpleCoffee implements Coffee {
      public String getDescription() { return "Simple Coffee"; }
      public double getCost() { return 1.00; }
  }

  // Abstract Decorator
  public abstract class CoffeeDecorator implements Coffee {
      protected final Coffee wrapped;

      protected CoffeeDecorator(Coffee coffee) {
          this.wrapped = coffee;
      }

      public String getDescription() { return wrapped.getDescription(); }
      public double getCost() { return wrapped.getCost(); }
  }

  // Concrete Decorators
  public class MilkDecorator extends CoffeeDecorator {
      public MilkDecorator(Coffee c) { super(c); }
      public String getDescription() { return wrapped.getDescription() + ", Milk"; }
      public double getCost() { return wrapped.getCost() + 0.25; }
  }

  public class VanillaDecorator extends CoffeeDecorator {
      public VanillaDecorator(Coffee c) { super(c); }
      public String getDescription() { return wrapped.getDescription() + ", Vanilla"; }
      public double getCost() { return wrapped.getCost() + 0.50; }
  }

  public class ShotDecorator extends CoffeeDecorator {
      public ShotDecorator(Coffee c) { super(c); }
      public String getDescription() { return wrapped.getDescription() + ", Extra Shot"; }
      public double getCost() { return wrapped.getCost() + 0.75; }
  }

  // Usage — wrap at runtime
  Coffee order = new ShotDecorator(
                     new VanillaDecorator(
                         new MilkDecorator(
                             new SimpleCoffee()
                         )
                     )
                 );

  System.out.println(order.getDescription());
  // "Simple Coffee, Milk, Vanilla, Extra Shot"
  System.out.println(order.getCost());  // 2.50

  Adding a new add-on = new Decorator class. Zero changes to existing code.

FUNCTION.ANDTHEN() — FUNCTIONAL DECORATOR
----------------------------------------------------------------

  Function<T,R> supports decoration via andThen() and compose():

  Function<String, String> f = s -> s.trim();
  Function<String, String> g = s -> s.toUpperCase();
  Function<String, String> h = s -> "[" + s + "]";

  // Decorate f with g then h
  Function<String, String> decorated = f.andThen(g).andThen(h);
  decorated.apply("  hello  ");  // "[HELLO]"

  // andThen: f then g  (left to right)
  // compose: f.compose(g) = g runs first (right to left)

  // Practical: build configurable processing pipeline
  List<Function<Order, Order>> processors = new ArrayList<>();
  processors.add(order -> applyTax(order));
  processors.add(order -> applyDiscount(order));
  processors.add(order -> applyShipping(order));

  Function<Order, Order> pipeline = processors.stream()
      .reduce(Function.identity(), Function::andThen);

  Order processed = pipeline.apply(rawOrder);

  This IS the pipeline/chain pattern using Decorator semantics.

----------------------------------------------------------------
STREAM PIPELINE AS DECORATOR CHAIN
----------------------------------------------------------------

  Java Stream operations (map, filter, peek, limit) are lazy decorators
  over a source. Each intermediate operation wraps the stream without
  materializing data.

  List<String> result = Stream.of("  Alice ", " bob ", "CAROL")
      .map(String::trim)          // decorator: trim
      .map(String::toLowerCase)   // decorator: lowercase
      .filter(s -> s.length() > 3)// decorator: filter by length
      .peek(System.out::println)  // decorator: side-effect inspect
      .sorted()                   // decorator: ordering
      .limit(10)                  // decorator: cap size
      .collect(Collectors.toList()); // terminal: materialize

  Nothing executes until collect(). Each call wraps previous stream.
  This matches Decorator: same Stream interface, wraps previous, adds behavior.

  Custom Collector = Decorator for aggregation logic.

DECORATOR WITH INTERFACE DEFAULT METHODS
----------------------------------------------------------------

  Interface default methods let you add decorating behavior without
  abstract classes:

  public interface Validator<T> {
      boolean validate(T t);

      // Built-in decorator methods
      default Validator<T> and(Validator<T> other) {
          return t -> this.validate(t) && other.validate(t);
      }

      default Validator<T> or(Validator<T> other) {
          return t -> this.validate(t) || other.validate(t);
      }

      default Validator<T> negate() {
          return t -> !this.validate(t);
      }
  }

  // Usage — compose validators
  Validator<String> notEmpty   = s -> !s.isBlank();
  Validator<String> validEmail = s -> s.contains("@");
  Validator<String> notTooLong = s -> s.length() <= 100;

  Validator<String> emailValidator = notEmpty.and(validEmail).and(notTooLong);

  emailValidator.validate("user@example.com");  // true
  emailValidator.validate("");                   // false

  This is exactly how Predicate.and() / Predicate.or() works internally.

----------------------------------------------------------------
DECORATOR COMPARISON WITH OTHER PATTERNS
----------------------------------------------------------------

  Pattern        Key difference
  -----------    --------------------------------------------------------
  Decorator      Same interface; runtime wrapping; add one behavior
  Proxy          Same interface; controls ACCESS (lazy load, security)
  Adapter        Converts ONE interface to another; structural
  Composite      Tree structure of same-type components; NOT sequential
  Chain of Resp  One request processed by ONE handler; Decorator adds all

  Decorator vs Inheritance:
    Inheritance: behavior added at compile-time; combinatorial explosion (class per combo)
    Decorator: behavior added at runtime; mix-and-match dynamically

  Example: 3 behaviors (A, B, C)
    Inheritance: ABC, AB, AC, BC, A, B, C = 7 classes
    Decorator: 3 classes + runtime composition

SPRING FRAMEWORK DECORATOR EXAMPLES
----------------------------------------------------------------

  HttpServletRequest decorators:
    ContentCachingRequestWrapper -- caches body for later reads
    HttpServletRequestWrapper    -- base class for custom decorators

  Spring Security:
    SecurityContextRepository  -- each impl wraps storage behavior
    OAuth2AuthorizedClientRepository -- delegates to sub-repository

  WebMvcConfigurer:
    ResourceHandlerRegistry.addResourceHandler() chains resource resolvers
    (CachingResourceResolver wraps PathResourceResolver)

  @Transactional:
    Spring generates a proxy (special kind of Decorator) around your bean.
    Proxy implements same interface; delegates to actual bean; adds TX logic.

  @Cacheable:
    Another proxy that wraps method call; returns cached value if present.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Decorator pattern? How is it different from inheritance?
  A: Decorator adds behavior at runtime by wrapping an object that implements
     the same interface. Inheritance adds behavior at compile-time and leads
     to class explosion when combining behaviors.

  Q: Where does Java use Decorator in the standard library?
  A: I/O streams: BufferedInputStream wraps FileInputStream; GZIPInputStream
     wraps BufferedInputStream. Also: Collections.unmodifiableList(),
     Collections.synchronizedList(), Optional.

  Q: How does Collections.unmodifiableList() use Decorator?
  A: It wraps any List and overrides mutating methods (add/remove/set)
     to throw UnsupportedOperationException. Reads delegate to the wrapped list.
     Same List interface, added (restricting) behavior.

  Q: How does Function.andThen() implement Decorator?
  A: andThen() returns a new Function that applies this function then the next.
     The original function is wrapped — same interface (Function), added behavior.

  Q: What is the risk of deep Decorator chains?
  A: Hard to debug (many layers of indirection), performance overhead per call,
     incorrect order of decoration causes bugs, toString/equals may not reflect
     the wrapped chain correctly.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Lead with I/O streams — interviewers expect this example.
  - Know Collections.unmodifiableList() and Collections.synchronizedList().
  - Show Function.andThen() as modern functional decorator.
  - Decorator vs Proxy: Decorator adds behavior, Proxy controls access.
  - Decorator vs Inheritance: runtime composition vs compile-time hierarchy.
