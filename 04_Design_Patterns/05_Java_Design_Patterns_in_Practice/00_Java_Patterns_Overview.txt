================================================================
  DESIGN PATTERNS IN JAVA PRACTICE — OVERVIEW
================================================================

  This folder shows how GoF design patterns manifest in real Java codebases,
  with modern Java idioms (lambdas, streams, records, var), Spring Boot,
  and common libraries.

----------------------------------------------------------------
WHY PATTERNS LOOK DIFFERENT IN MODERN JAVA
----------------------------------------------------------------

  GoF patterns were written for C++/Smalltalk.
  Java 8+ features eliminate boilerplate:

  Old (Java < 8):                     Modern Java:
  -----------------------------------------------
  Anonymous class Strategy             Lambda expression
  Observer listener class             Method reference / @EventListener
  Command class                       Runnable / Callable
  Builder with setters                Lombok @Builder / record
  Null Object                         Optional<T>
  Factory map + if-else               Map<String, Supplier<T>> + lambdas
  -----------------------------------------------

  Key insight: Functional interfaces (Strategy, Command, Observer, Comparator)
  can now be expressed as lambdas — no boilerplate class needed.
  Patterns are still the CONCEPT; lambdas are the IMPLEMENTATION.

----------------------------------------------------------------
JAVA 8+ PATTERN MODERNIZATIONS
----------------------------------------------------------------

  1. STRATEGY → Lambda
     Old: new TaxStrategy() anonymous class
     New: amount -> amount * 0.1    (lambda IS the strategy)

  2. COMMAND → Runnable / Callable
     Old: new PrintCommand(doc) implements Command
     New: () -> printer.print(doc)  (lambda IS the command)

  3. FACTORY → Supplier<T> in Map
     Old: if-else / switch creating new objects
     New: Map.of("PDF", PdfParser::new, "CSV", CsvParser::new)

  4. OBSERVER → Consumer<T>
     Old: implements EventListener { onEvent(event) }
     New: eventSource.addListener(event -> process(event))

  5. NULL OBJECT → Optional<T>
     Old: CustomerNullObject implements Customer
     New: Optional.ofNullable(customer).ifPresent(c -> c.notify())

  6. BUILDER → Record (Java 16+) for immutable value objects
     Old: Builder with 10 setters
     New: record Person(String name, int age) {} (compact, immutable)
          or: Lombok @Builder

  7. DECORATOR → Function.compose() / andThen()
     Old: new LoggingDecorator(new ValidationDecorator(service))
     New: Function<Input, Output> pipeline = validate.andThen(process).andThen(log)

----------------------------------------------------------------
PATTERN SELECTION GUIDE — QUICK REFERENCE
----------------------------------------------------------------

  NEED TO CREATE OBJECTS:
    Simple object, single step          --> Factory Method or static factory
    Complex object, many params         --> Builder
    Family of related objects           --> Abstract Factory
    Copy existing object                --> Prototype
    Reuse expensive objects             --> Object Pool
    Ensure single instance              --> Singleton (or Spring @Component)

  NEED TO COMPOSE OBJECTS:
    Incompatible interfaces             --> Adapter
    Separate abstraction/implementation --> Bridge
    Part-whole tree structure           --> Composite
    Add behavior at runtime             --> Decorator
    Simplify complex system             --> Facade
    Share many small similar objects    --> Flyweight
    Control access / lazy / security    --> Proxy

  NEED TO DEFINE BEHAVIORS:
    Family of algorithms                --> Strategy
    Encapsulate a request               --> Command
    Sequential notification             --> Observer
    Object changes behavior with state  --> State
    Algorithm skeleton with steps       --> Template Method
    Pass request through a chain        --> Chain of Responsibility
    Reduce object coupling              --> Mediator
    Traverse without exposing structure --> Iterator
    Save/restore object state           --> Memento
    New operations on stable hierarchy  --> Visitor
    Interpret language/grammar          --> Interpreter
    Safe "do nothing" default           --> Null Object

----------------------------------------------------------------
COMBINED PATTERNS — REAL ARCHITECTURE
----------------------------------------------------------------

  E-commerce Order System:
    Singleton:        DatabaseConnectionPool
    Factory Method:   PaymentProcessorFactory.create(paymentType)
    Builder:          Order.builder().items(items).customer(c).build()
    Strategy:         ShippingCalculator (Standard, Express, Overnight)
    Observer:         OrderEventPublisher → @EventListener (email, inventory, audit)
    State:            Order states: NEW → PAID → SHIPPED → DELIVERED
    Command + Memento: UndoableOrderAction with undo stack
    Chain of Resp.:   Spring Security → Authentication → Authorization → Audit

  The patterns work TOGETHER. Real systems use 5-10 patterns simultaneously.

----------------------------------------------------------------
WHEN NOT TO USE PATTERNS
----------------------------------------------------------------

  Avoid patterns when:
    - Simple 2-class problem doesn't need abstraction (YAGNI).
    - Pattern adds 5 classes for a problem solved in 10 lines.
    - Team doesn't know the pattern — adds cognitive load.
    - Pattern used for its own sake, not for the problem it solves.

  Signs of pattern overuse:
    - Classes named "AbstractFactory for a single implementation.
    - Visitor with only one visitor.
    - Strategy with only one strategy.
    - Builder for objects with 2 fields.
