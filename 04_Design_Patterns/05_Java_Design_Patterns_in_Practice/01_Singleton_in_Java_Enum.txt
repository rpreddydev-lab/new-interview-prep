================================================================
  SINGLETON IN JAVA — ENUM AND ALL VARIANTS
================================================================

  The Singleton pattern ensures a class has only ONE instance and provides
  a global access point. Java provides multiple implementation strategies,
  each with different thread-safety and attack-resistance properties.

----------------------------------------------------------------
1. EAGER INITIALIZATION
----------------------------------------------------------------

  public final class EagerSingleton {
      private static final EagerSingleton INSTANCE = new EagerSingleton();

      private EagerSingleton() { }

      public static EagerSingleton getInstance() { return INSTANCE; }
  }

  Thread-safe: YES (class loading is single-threaded by JVM).
  Lazy:        NO — instance created at class load even if never used.
  Use when:    Instance creation is cheap, or class is always used.

----------------------------------------------------------------
2. SYNCHRONIZED METHOD (SIMPLEST LAZY — AVOID)
----------------------------------------------------------------

  public final class SynchronizedSingleton {
      private static SynchronizedSingleton instance;

      private SynchronizedSingleton() { }

      public static synchronized SynchronizedSingleton getInstance() {
          if (instance == null) {
              instance = new SynchronizedSingleton();
          }
          return instance;
      }
  }

  Thread-safe: YES.
  Problem:     synchronized on every call — huge performance bottleneck.
               After initialization, no need to lock — but always does.
  AVOID in production.

----------------------------------------------------------------
3. DOUBLE-CHECKED LOCKING (DCL)
----------------------------------------------------------------

  public final class DCLSingleton {
      private static volatile DCLSingleton instance;  // volatile REQUIRED

      private DCLSingleton() { }

      public static DCLSingleton getInstance() {
          if (instance == null) {                    // first check (no lock)
              synchronized (DCLSingleton.class) {
                  if (instance == null) {            // second check (with lock)
                      instance = new DCLSingleton();
                  }
              }
          }
          return instance;
      }
  }

  Thread-safe:  YES — volatile prevents partial construction visibility.
  Lazy:         YES — created only on first call.
  Performance:  Good — only synchronized on first creation.

  WHY volatile IS REQUIRED:
    instance = new DCLSingleton() is NOT atomic. Three steps:
      1. Allocate memory.
      2. Initialize object.
      3. Assign reference to instance.
    Without volatile, steps 2 and 3 can be REORDERED.
    Thread B could see a non-null but uninitialized object.
    volatile: all writes happen-before reads.

  DCL works in Java 5+ (when the memory model was fixed for volatile).
  DCL is BROKEN in Java 1.4 and below.

----------------------------------------------------------------
4. BILL PUGH HOLDER (PREFERRED LAZY IMPLEMENTATION)
----------------------------------------------------------------

  public final class HolderSingleton {
      private HolderSingleton() { }

      private static class Holder {
          private static final HolderSingleton INSTANCE = new HolderSingleton();
      }

      public static HolderSingleton getInstance() {
          return Holder.INSTANCE;   // class loaded lazily on first call
      }
  }

  Thread-safe:  YES — JVM class loading is atomic. Holder class loaded once.
  Lazy:         YES — Holder class not loaded until getInstance() is first called.
  Performance:  BEST — no synchronization at all after initialization.
  Simple:       YES — no volatile, no synchronized.

  How it works:
    Inner static class Holder is not loaded when HolderSingleton is loaded.
    Holder loads only when HolderSingleton.getInstance() is first called.
    JVM guarantees: class initialization is atomic and happens-once.
    INSTANCE field is set during class initialization — guaranteed by JLS.

  PREFERRED for most lazy singleton implementations.

----------------------------------------------------------------
5. ENUM SINGLETON (JOSH BLOCH RECOMMENDED)
----------------------------------------------------------------

  public enum EnumSingleton {
      INSTANCE;

      private String config;

      public void setConfig(String config) { this.config = config; }
      public String getConfig()             { return config; }

      public void doOperation() {
          System.out.println("Singleton operation with config: " + config);
      }
  }

  // Usage
  EnumSingleton.INSTANCE.setConfig("production");
  EnumSingleton.INSTANCE.doOperation();

  WHY ENUM IS THE BEST SINGLETON:

  1. THREAD SAFETY:
     JVM guarantees enum values are instantiated exactly once.
     No synchronization needed. No volatile. No DCL.

  2. SERIALIZATION SAFE:
     Standard class singleton: readObject() creates a NEW instance.
     Must override readResolve() to return INSTANCE.
     Enum: JVM guarantees deserialization returns the SAME instance.

  3. REFLECTION SAFE:
     Standard class: reflection can call private constructor via
     Constructor.setAccessible(true) — creates a second instance.
     Fix: throw exception in private constructor.
     Enum: JVM PREVENTS creating enum instances via reflection.
     Constructor.newInstance() on an enum throws IllegalArgumentException.

  4. SIMPLE:
     5 lines of code. No patterns to get wrong.

  Limitation: enum cannot extend another class (single inheritance used by enum).
              If you need inheritance, use Holder pattern instead.

----------------------------------------------------------------
REFLECTION ATTACK ON CLASS SINGLETON
----------------------------------------------------------------

  // Attacker's code — BYPASSES private constructor
  HolderSingleton s1 = HolderSingleton.getInstance();

  Constructor<HolderSingleton> constructor =
      HolderSingleton.class.getDeclaredConstructor();
  constructor.setAccessible(true);
  HolderSingleton s2 = constructor.newInstance();  // second instance!

  System.out.println(s1 == s2);  // false — BROKEN

  DEFENSE in private constructor:
  private HolderSingleton() {
      if (Holder.INSTANCE != null) {
          throw new IllegalStateException("Singleton already created!");
      }
  }

  But this only works if Holder.INSTANCE is set BEFORE reflection attack.
  Order-of-operations issue makes this fragile.
  Enum eliminates the problem entirely.

----------------------------------------------------------------
SERIALIZATION ATTACK ON CLASS SINGLETON
----------------------------------------------------------------

  // Standard singleton without readResolve — breaks on deserialization
  byte[] bytes = serialize(HolderSingleton.getInstance());
  HolderSingleton deserialized = deserialize(bytes);  // NEW instance!

  Fix: implement readResolve() in singleton class:
  protected Object readResolve() {
      return Holder.INSTANCE;   // return the ONE instance
  }

  Enum: automatic protection — no readResolve needed.

----------------------------------------------------------------
SPRING SINGLETON vs JAVA SINGLETON
----------------------------------------------------------------

  Java Singleton:
    ONE instance per ClassLoader.
    Multiple ClassLoaders (common in Java EE) → multiple instances.

  Spring Singleton:
    ONE instance per ApplicationContext.
    Multiple contexts → multiple instances (one per context).
    @Scope("singleton") is DEFAULT scope.
    NOT a GoF singleton — just single instance within container.

  Spring @Component / @Service / @Repository:
    Default scope = singleton (within context).
    To get a new instance every time: @Scope("prototype").

  Testing with Spring:
    Each test can create its own ApplicationContext → separate singletons.
    Tests are isolated. GoF singleton would share across tests.

----------------------------------------------------------------
WHEN TO USE WHICH SINGLETON
----------------------------------------------------------------

  Criteria           --> Implementation
  -----------------------------------------------
  Simple, always used --> Eager (static final field)
  Must be lazy, no inheritance needed --> Holder (Bill Pugh)
  Enum (Josh Bloch recommended, short) --> Enum singleton
  Fine-grained control, needs inheritance --> DCL with volatile
  -----------------------------------------------

  NEVER use: synchronized getInstance() (performance).
  PREFER Enum unless inheritance is required.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What are the different ways to implement Singleton in Java?
  A: (1) Eager static field, (2) synchronized method (avoid),
     (3) Double-checked locking with volatile, (4) Holder/Bill Pugh inner class,
     (5) Enum singleton. Enum is Josh Bloch's recommendation — thread-safe,
     reflection-safe, serialization-safe by default.

  Q: Why does DCL need volatile?
  A: Object creation has 3 steps: allocate, initialize, assign.
     Without volatile, JVM can reorder assign before initialize.
     Another thread sees non-null but uninitialized object.
     volatile ensures writes to instance happen-before reads.

  Q: Why is Enum singleton serialization-safe?
  A: JVM guarantees that during deserialization, enum constants are resolved
     by their name — returning the EXISTING instance. readResolve() is not needed.
     Standard class singleton would create a new instance on deserialization.

  Q: How does Enum prevent reflection attacks?
  A: JVM prohibits creating enum instances via reflection.
     Constructor.newInstance() on an enum throws IllegalArgumentException.
     Standard class singletons must manually guard against it in the constructor.

  Q: Spring singleton vs GoF singleton?
  A: Spring: one instance per ApplicationContext.
     GoF: one instance per ClassLoader.
     Multiple Spring contexts → multiple "singletons" (one each).
     Spring supports isolation; GoF is truly global.
