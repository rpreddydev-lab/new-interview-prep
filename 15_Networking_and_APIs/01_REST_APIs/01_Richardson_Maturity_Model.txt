================================================================================
RICHARDSON MATURITY MODEL — IN DEPTH
================================================================================

OVERVIEW
---------
The Richardson Maturity Model (RMM), introduced by Leonard Richardson in 2008
and popularized by Martin Fowler, provides a way to grade REST APIs from 0 to 3
based on how closely they adhere to REST principles.

The model identifies how well an API leverages HTTP as a protocol rather than
just using it as a transport tunnel.

================================================================================
LEVEL 0 — THE SWAMP OF POX (Plain Old XML)
================================================================================

Characteristics:
  - HTTP is used as a tunneling mechanism only
  - Single URI endpoint for all operations
  - Single HTTP method (usually POST)
  - All operation semantics encoded in the request body
  - Examples: SOAP, XML-RPC, early-era "REST" APIs

EXAMPLE:
  All requests go to: POST /appointmentService

  Get available slots:
  POST /appointmentService
  {
    "action": "getAvailableSlots",
    "date": "2026-04-08",
    "doctor": "Dr. Smith"
  }

  Book appointment:
  POST /appointmentService
  {
    "action": "bookAppointment",
    "date": "2026-04-08",
    "doctor": "Dr. Smith",
    "patient": "John Doe",
    "slot": "14:00"
  }

  Cancel appointment:
  POST /appointmentService
  {
    "action": "cancelAppointment",
    "appointmentId": "12345"
  }

PROBLEMS:
  - No HTTP caching (POST responses not cached)
  - Action tunneling — HTTP has no visibility into what's happening
  - No standard error handling (everything is 200 with error in body)
  - Cannot leverage HTTP tooling (browsers, proxies, CDNs)

================================================================================
LEVEL 1 — RESOURCES
================================================================================

Characteristics:
  - Individual URIs for individual resources
  - Still often uses single HTTP method (POST)
  - Resources are identifiable and addressable
  - No proper use of HTTP verbs

EXAMPLE:
  Each resource has its own URI, but all operations still use POST:

  Get available slots:
  POST /doctors/drsmith/slots
  { "date": "2026-04-08" }

  Book appointment:
  POST /appointments
  { "doctor": "drsmith", "slot": "14:00", "patient": "john-doe" }

  Cancel appointment:
  POST /appointments/12345
  { "action": "cancel" }

IMPROVEMENT OVER LEVEL 0:
  - Resources are now identifiable (can be bookmarked, linked to)
  - Decomposed single endpoint into meaningful resource URIs
  - Easier to understand, document, and route

REMAINING PROBLEMS:
  - Still not using HTTP verbs meaningfully
  - "action" field still appears in body
  - No proper status codes

================================================================================
LEVEL 2 — HTTP VERBS
================================================================================

Characteristics:
  - Proper use of HTTP methods (GET, POST, PUT, DELETE, PATCH)
  - Meaningful HTTP status codes
  - Leverages HTTP caching for GETs
  - This is the level that most "RESTful APIs" reach in practice

EXAMPLE:
  Get available slots:
  GET /doctors/drsmith/slots?date=2026-04-08
  → 200 OK
  [{ "id": "s1", "time": "14:00", "available": true }, ...]

  Book appointment (creates resource):
  POST /appointments
  { "doctorId": "drsmith", "slotId": "s1", "patientId": "john-doe" }
  → 201 Created
  { "id": "a123", "status": "confirmed" }
  Location: /appointments/a123

  Get appointment:
  GET /appointments/a123
  → 200 OK
  { "id": "a123", "doctor": "drsmith", "time": "14:00", "status": "confirmed" }

  Cancel appointment:
  DELETE /appointments/a123
  → 204 No Content

  Or partial update:
  PATCH /appointments/a123
  { "status": "cancelled" }
  → 200 OK

WHY THIS MATTERS:
  - GET requests are safe and cacheable → CDN, browser, proxy can cache
  - DELETE communicates intent to LBs, logging systems, proxies
  - Status codes allow generic error handling (401 → redirect to login, 429 → retry)
  - Makes API discoverable and self-documenting

MOST PRODUCTION APIs ARE HERE.
This level gives you 80% of REST's benefits.

================================================================================
LEVEL 3 — HYPERMEDIA CONTROLS (HATEOAS)
================================================================================

Characteristics:
  - Responses include links to available next actions (hypermedia)
  - Client discovers API through embedded links
  - No out-of-band documentation needed for navigation
  - HATEOAS: Hypermedia as the Engine of Application State

EXAMPLE — Get available slots (includes next actions as links):
  GET /doctors/drsmith/slots?date=2026-04-08
  → 200 OK
  {
    "slots": [
      {
        "id": "s1",
        "time": "14:00",
        "available": true,
        "_links": {
          "book": {
            "href": "/appointments",
            "method": "POST"
          }
        }
      }
    ],
    "_links": {
      "self": { "href": "/doctors/drsmith/slots?date=2026-04-08" },
      "doctor": { "href": "/doctors/drsmith" },
      "nextDay": { "href": "/doctors/drsmith/slots?date=2026-04-09" }
    }
  }

EXAMPLE — Book appointment (result includes links to next actions):
  POST /appointments
  → 201 Created
  {
    "id": "a123",
    "status": "confirmed",
    "_links": {
      "self":   { "href": "/appointments/a123", "method": "GET" },
      "cancel": { "href": "/appointments/a123", "method": "DELETE" },
      "doctor": { "href": "/doctors/drsmith",   "method": "GET" },
      "reschedule": { "href": "/appointments/a123", "method": "PUT" }
    }
  }

BENEFITS OF LEVEL 3:
  - Client doesn't need to hardcode URLs
  - Server can change URLs without breaking clients (links are followed, not hardcoded)
  - Self-documenting: response tells you what to do next
  - True decoupling of client and server

WHY LEVEL 3 IS RARELY IMPLEMENTED:
  - Complex to implement and maintain
  - Most clients ignore links and hardcode URLs anyway
  - Increases response size
  - Documentation (OpenAPI/Swagger) often replaces discoverability
  - Most teams settle at Level 2 which provides sufficient benefits

HATEOAS STANDARDS:
  HAL (Hypertext Application Language): _links property, _embedded for sub-resources
  JSON-LD: Linked Data with @context, @id
  Siren: Entities, actions, links structure
  Collection+JSON: For collection resources

HAL EXAMPLE:
  {
    "id": 42,
    "name": "Alice",
    "_links": {
      "self":   { "href": "/users/42" },
      "orders": { "href": "/users/42/orders" },
      "update": { "href": "/users/42", "method": "PUT" },
      "delete": { "href": "/users/42", "method": "DELETE" }
    },
    "_embedded": {
      "latestOrder": {
        "id": 99,
        "status": "shipped",
        "_links": {
          "self": { "href": "/orders/99" }
        }
      }
    }
  }

================================================================================
SUMMARY TABLE
================================================================================

LEVEL  NAME          KEY FEATURE                    EXAMPLE
-----  ------------  -----------------------------  -----------------------
0      The Swamp     Single endpoint, one method    POST /service {"action":"x"}
1      Resources     Multiple URIs per resource     POST /users, POST /orders
2      HTTP Verbs    Proper methods + status codes  GET /users, DELETE /users/42
3      HATEOAS       Embedded links in responses    _links in response body

The model is a progression — each level adds semantics and leverages HTTP more fully.

================================================================================
MATURITY LEVEL IN PRACTICE
================================================================================

WHAT MOST COMPANIES DO: Level 2
  - Clean resource URIs
  - Proper HTTP methods
  - Correct status codes
  - This is what interviewers expect you to know and design

WHAT INTERVIEWERS WANT TO HEAR:
  "I design Level 2 RESTful APIs using proper HTTP methods, meaningful URIs,
   and correct status codes. I'm familiar with HATEOAS (Level 3) but in
   practice teams usually use OpenAPI/Swagger for discoverability instead."

SPRING BOOT — HATEOAS SUPPORT:
  Spring HATEOAS library: adds links to responses
  
  @GetMapping("/users/{id}")
  public EntityModel<User> getUser(@PathVariable Long id) {
      User user = userService.findById(id);
      return EntityModel.of(user,
          linkTo(methodOn(UserController.class).getUser(id)).withSelfRel(),
          linkTo(methodOn(UserController.class).getAllUsers()).withRel("users"));
  }

  Output:
  {
    "id": 42,
    "name": "Alice",
    "_links": {
      "self":  { "href": "http://localhost:8080/users/42" },
      "users": { "href": "http://localhost:8080/users" }
    }
  }

================================================================================
INTERVIEW QUESTIONS — RICHARDSON MATURITY MODEL
================================================================================

Q1: What is the Richardson Maturity Model?
    A grading system for REST APIs: Level 0 (single endpoint), Level 1
    (resources), Level 2 (HTTP verbs + status codes), Level 3 (HATEOAS).
    It shows how well an API leverages HTTP as a protocol.

Q2: What level do most production APIs reach and why?
    Level 2. It provides clean resource-oriented design with proper HTTP
    semantics (caching via GET, status codes for error handling) without the
    complexity of HATEOAS. Most clients and API consumers don't follow hypermedia
    links anyway — they rely on documentation.

Q3: What is HATEOAS and why is it valuable in theory?
    Hypermedia as the Engine of Application State. Responses include links to
    available next actions. Client navigates the API by following links rather
    than hardcoding URLs. Value: server can change URLs without breaking clients;
    self-documenting; complete decoupling. In practice, OpenAPI specs serve this
    purpose more pragmatically.

Q4: What's wrong with a Level 0 API?
    HTTP is only a transport tunnel. No caching benefit (single POST endpoint).
    No visibility for proxies/LBs. All responses are 200. Error handling requires
    parsing the body. Hard to debug, log, and monitor. Doesn't leverage decades
    of HTTP infrastructure.
