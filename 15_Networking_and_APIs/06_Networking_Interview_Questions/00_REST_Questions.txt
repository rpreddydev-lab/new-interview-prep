================================================================================
REST API INTERVIEW QUESTIONS — COMPREHENSIVE Q&A
================================================================================

This file contains deep-dive interview questions on REST APIs, HTTP methods,
status codes, idempotency, HATEOAS, and API design. Answers are written at
senior/staff engineer interview level.

================================================================================
SECTION 1: REST FUNDAMENTALS
================================================================================

Q: What is REST and what are its 6 architectural constraints?
A: REST (Representational State Transfer) is an architectural style for
   distributed hypermedia systems, defined by Roy Fielding in his 2000 PhD
   dissertation. The 6 constraints are:
   
   1. Client-Server: Separation of concerns; UI and data storage are separate.
      Client doesn't need to know how data is stored; server doesn't need to
      know about UI. This allows them to evolve independently.
   
   2. Stateless: Each request must contain all information needed to process it.
      Server stores no client session state. Enables horizontal scaling —
      any server can handle any request.
   
   3. Cacheable: Responses must explicitly indicate if they can be cached.
      Cache-Control, ETag, Last-Modified headers. Reduces server load.
   
   4. Uniform Interface: Resources identified by URIs; manipulated through
      representations; self-descriptive messages; HATEOAS. Decouples client
      and server evolution.
   
   5. Layered System: Client doesn't know if it's talking to origin server,
      cache, load balancer, or proxy. Enables transparent intermediaries.
   
   6. Code on Demand (optional): Server can extend client by transferring
      executable code (JavaScript). Only optional constraint.
   
   The most important for interviews: stateless, uniform interface, client-server.

Q: What is the difference between REST and SOAP?
A: SOAP (Simple Object Access Protocol) is a protocol with strict standards:
   - XML envelope required
   - WSDL for contract definition
   - Built-in WS-* standards (WS-Security, WS-Transaction, WS-ReliableMessaging)
   - Stateful operations supported
   - Any transport (HTTP, SMTP, JMS)
   
   REST is an architectural style:
   - JSON, XML, or any format
   - Informal contract (OpenAPI/Swagger)
   - No built-in security or transaction standards
   - Stateless by definition
   - HTTP exclusively
   
   Use SOAP when: enterprise integration with strict contracts, WS-* compliance
   required, or legacy systems.
   Use REST when: public APIs, mobile clients, simpler contracts.

Q: What is the Richardson Maturity Model?
A: A 4-level model for measuring REST "maturity":
   Level 0 - HTTP as transport tunnel (all POSTs to one endpoint, XML-RPC/SOAP)
   Level 1 - Resources (separate URIs per resource: /orders, /users)
   Level 2 - HTTP Verbs (GET to read, POST to create, PUT to update, DELETE)
   Level 3 - Hypermedia (HATEOAS — responses contain links for state navigation)
   
   Most "REST APIs" are Level 2. True REST (Fielding's definition) requires
   Level 3 (HATEOAS). In interviews, explain that most APIs are pragmatically
   Level 2 and that's acceptable for most use cases.

Q: Why is statelessness important, and what are its trade-offs?
A: Benefits:
   - Horizontal scalability: any node handles any request (no affinity)
   - Failure recovery: if a node dies, re-route request (no session to restore)
   - Simplicity: server doesn't manage per-client state
   
   Trade-offs:
   - Larger payloads: client must resend authentication/context each time
   - Performance: can't leverage server-side session cache
   - Re-authentication overhead: JWT must be validated each request
   
   Alternative: stateful services use sticky sessions or distributed session
   stores (Redis), which sacrifices some horizontal scaling simplicity.

SECTION 2: HTTP METHODS AND IDEMPOTENCY
================================================================================

Q: Explain the difference between idempotent and safe HTTP methods.
A: Safe methods: do not modify server state. They have no side effects.
   GET, HEAD, OPTIONS are safe.
   
   Idempotent methods: calling N times has the same effect as calling once.
   GET, HEAD, OPTIONS, PUT, DELETE are idempotent.
   POST and PATCH are neither safe nor idempotent (generally).
   
   Examples:
   - GET /users/1 — same response each time, no change: safe + idempotent
   - DELETE /users/1 — first call deletes, subsequent calls return 404 but
     state is same (user absent): idempotent, not safe
   - PUT /users/1 {name: "Alice"} — always results in user named Alice: idempotent
   - POST /orders — creates a new order each time: not idempotent, not safe
   
   Idempotency is crucial for retry logic — only retry idempotent operations
   unless you add idempotency keys.

Q: When would you use PUT vs PATCH?
A: PUT replaces the entire resource representation. Client must send the complete
   resource. If a field is missing, it's set to null/default.
   
   PATCH partially updates a resource. Client sends only the fields to change.
   More bandwidth-efficient for large objects with minor changes.
   
   PATCH is more complex to implement correctly:
   - Concurrent partial updates can conflict (need ETag/If-Match)
   - JSON Merge Patch (RFC 7396): send partial JSON, null means delete field
   - JSON Patch (RFC 6902): array of operations: add, remove, replace, move
   
   Example JSON Patch:
   PATCH /users/1
   [{"op": "replace", "path": "/email", "value": "new@email.com"},
    {"op": "remove", "path": "/middleName"}]
   
   In practice: PATCH for partial updates of large resources; PUT when the
   whole resource is always sent (common in form-based UIs).

Q: What HTTP status codes should GET, POST, PUT, DELETE return?
A: GET:
     200 OK — resource found
     404 Not Found — resource doesn't exist
     304 Not Modified — with ETag/If-None-Match; content unchanged
   
   POST (create):
     201 Created — resource created; Location header with new resource URI
     202 Accepted — async operation started; returns job URL for polling
     400 Bad Request — invalid input
     409 Conflict — duplicate resource
   
   PUT/PATCH:
     200 OK — updated, returns updated resource
     204 No Content — updated, no body returned
     404 Not Found — resource doesn't exist
     409 Conflict — version conflict (ETag mismatch)
   
   DELETE:
     204 No Content — deleted successfully (no body needed)
     404 Not Found — resource didn't exist
     200 OK — if returning the deleted resource

Q: What is the difference between 401 and 403?
A: 401 Unauthorized: Authentication is required or failed. The client is not
   authenticated (no token, expired token, invalid token). Despite the name
   "Unauthorized", it means "unauthenticated". Response should include
   WWW-Authenticate header indicating how to authenticate.
   
   403 Forbidden: Client is authenticated but doesn't have permission for
   this resource. The server understood who you are but refuses access.
   
   Mnemonic: 401 = "Who are you?" (authentication); 403 = "I know who you are
   but you can't come in" (authorization).
   
   Security note: To prevent resource enumeration, some APIs return 404 instead
   of 403 when a resource exists but the user can't access it.

SECTION 3: API DESIGN
================================================================================

Q: How do you design a RESTful API for a resource with sub-resources?
A: Model hierarchical resources with nested paths:
   /users/{userId}/orders         — orders belonging to a user
   /users/{userId}/orders/{orderId}
   
   Rules:
   1. Don't exceed 2-3 levels of nesting (becomes unwieldy)
   2. If sub-resource makes sense standalone, provide a top-level endpoint too:
      /orders/{orderId} — for accessing order without knowing user
   3. Use noun plurals: /users not /user, /orders not /order
   4. Use query params for filtering, not path:
      /orders?status=PENDING&userId=123 — filter at collection level
   
   Non-CRUD actions — use sub-resources as verbs as last resort:
   POST /orders/{id}/cancel      — cancel an order
   POST /accounts/{id}/activate  — activate account
   This is slightly REST-impure but widely accepted.

Q: How do you version a REST API? What's the best approach?
A: Four common strategies:
   
   1. URI path: /api/v1/users → /api/v2/users
      Pros: explicit, cacheable, easy to route in gateways
      Cons: "dirty" URIs per Fielding; must update all links
   
   2. Query parameter: /api/users?version=2
      Pros: easy to implement; default version possible
      Cons: often not cached by proxies; easy to forget
   
   3. Header: Accept-Version: v2 (or custom X-API-Version: 2)
      Pros: clean URIs; preferred by REST purists
      Cons: invisible in browser; harder to test; CDN caching issues
   
   4. Content negotiation: Accept: application/vnd.myapp.v2+json
      Pros: most RESTful; uses HTTP as intended
      Cons: complex; poorly supported by some clients
   
   Best practice: URI versioning (/v1, /v2) is most practical — teams can
   deploy, route, and deprecate versions independently. Use it for breaking
   changes; use content negotiation for minor variations.

Q: How do you handle pagination in a REST API?
A: Three main approaches:
   
   1. Offset-based (most common):
      GET /orders?page=2&size=20
      Response: {"content": [...], "totalElements": 500, "totalPages": 25}
      Problem: inconsistent with concurrent writes (page drift)
   
   2. Cursor-based (for large/real-time datasets):
      GET /orders?after=eyJpZCI6MTAwfQ&limit=20
      Response: {"items": [...], "nextCursor": "eyJpZCI6MTIwfQ"}
      Cursor encodes last item position (base64 JSON); stable with writes
      Twitter, Facebook, Instagram use cursor pagination
   
   3. Keyset pagination:
      GET /orders?after_id=100&limit=20
      Uses indexed column directly; highly efficient at any offset
      No random access to arbitrary page
   
   Best practice: use cursor/keyset for large/dynamic datasets;
   offset for small datasets where users need page navigation.

SECTION 4: ADVANCED REST TOPICS
================================================================================

Q: What is HATEOAS and is it practical?
A: HATEOAS (Hypermedia As The Engine Of Application State) is Level 3 REST:
   responses contain links describing available state transitions.
   
   {
     "orderId": 123,
     "status": "PENDING",
     "_links": {
       "self": {"href": "/orders/123"},
       "cancel": {"href": "/orders/123/cancel", "method": "POST"},
       "payment": {"href": "/orders/123/payment"}
     }
   }
   
   Benefits:
   - Client doesn't hardcode URLs — discovers them from responses
   - Server can change URL structure without breaking clients
   - Self-documenting — client knows what it can do next
   
   Practical reality: rarely implemented fully in industry because:
   - Complex to implement correctly
   - Most clients are generated from OpenAPI spec anyway
   - URL changes are rare in practice; versioning handles them
   - Increases payload size and response parsing complexity
   
   Answer: understand it for interviews; use Spring HATEOAS if required,
   but most teams stop at Level 2 REST.

Q: How do you handle errors in a REST API?
A: Use RFC 7807 Problem Details for HTTP APIs:
   Content-Type: application/problem+json
   {
     "type": "https://api.example.com/errors/validation-error",
     "title": "Validation Failed",
     "status": 422,
     "detail": "One or more fields are invalid",
     "instance": "/orders/create/attempt-123",
     "errors": [
       {"field": "email", "message": "Invalid email format"},
       {"field": "quantity", "message": "Must be positive"}
     ],
     "timestamp": "2024-01-15T10:30:00Z",
     "traceId": "abc123"
   }
   
   Key principles:
   - Use appropriate HTTP status codes (don't always return 200 with error body)
   - Be consistent: same structure for all errors
   - Include field-level details for validation errors
   - Include traceId for debugging
   - Don't expose stack traces or internal details in production

Q: What is content negotiation?
A: The mechanism where client and server agree on the format of the response.
   
   Client specifies preferred formats:
   Accept: application/json, application/xml;q=0.9, */*;q=0.8
   (q=quality factor, 0-1; default 1.0)
   
   Server responds with:
   Content-Type: application/json  (what it actually sent)
   
   If server can't satisfy Accept: returns 406 Not Acceptable
   
   Spring MVC content negotiation:
   @GetMapping(value = "/orders/{id}", 
               produces = {MediaType.APPLICATION_JSON_VALUE, MediaType.APPLICATION_XML_VALUE})
   public Order getOrder(@PathVariable Long id) { ... }
   
   Also used for versioning:
   Accept: application/vnd.company.v2+json

SECTION 5: SPRING REST SPECIFICS
================================================================================

Q: What is the difference between @RequestBody and @ModelAttribute?
A: @RequestBody: deserializes the HTTP request body (JSON/XML) into an object.
   Used for POST/PUT/PATCH with Content-Type: application/json.
   Spring uses HttpMessageConverter (Jackson by default).
   
   @ModelAttribute: binds request parameters, path variables, and form data
   to an object. Used for form submissions (Content-Type:
   application/x-www-form-urlencoded) or when binding multiple query params.
   
   Example:
   POST /orders with body {"item": "book", "qty": 3} → use @RequestBody
   GET /orders?status=PENDING&userId=1 → use @ModelAttribute OrderFilter filter
   POST /form with HTML form fields → use @ModelAttribute

Q: How does Spring Boot's exception handling work for REST APIs?
A: Three approaches (best to least preferred):
   
   1. @RestControllerAdvice (best — centralized):
   @RestControllerAdvice
   public class GlobalExceptionHandler {
       @ExceptionHandler(NotFoundException.class)
       public ResponseEntity<ProblemDetail> handleNotFound(NotFoundException ex) {
           ProblemDetail problem = ProblemDetail.forStatusAndDetail(
               HttpStatus.NOT_FOUND, ex.getMessage());
           return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
       }
       
       @ExceptionHandler(MethodArgumentNotValidException.class)
       public ResponseEntity<ProblemDetail> handleValidation(
               MethodArgumentNotValidException ex) {
           ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.UNPROCESSABLE_ENTITY);
           problem.setProperty("errors", ex.getBindingResult().getFieldErrors()
               .stream().map(e -> Map.of("field", e.getField(),
                                         "message", e.getDefaultMessage()))
               .toList());
           return ResponseEntity.unprocessableEntity().body(problem);
       }
   }
   
   2. @ExceptionHandler in @RestController (local — only handles that controller)
   3. ResponseStatusException (inline — throw in method body)
