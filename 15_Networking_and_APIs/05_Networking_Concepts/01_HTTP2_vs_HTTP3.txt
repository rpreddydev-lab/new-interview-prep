================================================================================
HTTP/2 vs HTTP/3 — IN DEPTH
================================================================================

HTTP EVOLUTION OVERVIEW
------------------------
  HTTP/0.9 (1991): Single-line GET only
  HTTP/1.0 (1996): Request headers; new TCP connection per request
  HTTP/1.1 (1997): Persistent connections, pipelining, chunked transfer
  HTTP/2  (2015): Binary framing, multiplexing, server push, header compression
  HTTP/3  (2022): QUIC transport, 0-RTT, connection migration

HTTP/1.1 is still dominant in the wild; HTTP/2 is widely supported;
HTTP/3 (QUIC) is growing rapidly (supported by major browsers and CDNs).

================================================================================
1. HTTP/1.1 — BASELINE
================================================================================

FEATURES:
  - Persistent connections (keep-alive, reuse TCP)
  - Pipelining (send multiple requests without waiting — poorly supported)
  - Text-based headers (wasteful, no compression)
  - One request per TCP connection at a time effectively (HOL blocking)
  - Chunked transfer encoding

PROBLEMS:
  Head-of-Line Blocking (HOL):
    Even with pipelining, responses must arrive in order.
    If request #1 is slow, requests #2, #3, #4 wait (even if responses are ready).
    
    Solution: Domain sharding (spread requests across 6 connections per domain)
    Downside: DNS lookups + TLS handshakes × 6

  Header overhead:
    Each request includes full HTTP headers (User-Agent, Cookie, Accept etc.)
    No compression — repeated identical headers on every request.
    A page with 100 requests: 100 × 2KB headers = 200KB of header data.

================================================================================
2. HTTP/2 — BINARY MULTIPLEXING
================================================================================

KEY IMPROVEMENTS:

1. BINARY FRAMING:
   HTTP/2 replaces text-based protocol with binary frames.
   Frame types: DATA, HEADERS, SETTINGS, WINDOW_UPDATE, RST_STREAM, GOAWAY...
   Binary = easier to parse; less error-prone; no ambiguity in line endings.

2. STREAM MULTIPLEXING:
   Multiple request/response pairs share ONE TCP connection via "streams".
   Each stream has a stream ID (odd = client initiated, even = server initiated).
   Streams are interleaved — frame from stream 3 can be sent between frames of stream 1.
   Result: eliminates application-layer HOL blocking.

   HTTP/1.1: ──req1──────────────resp1──req2──────resp2──
   HTTP/2:   ──[S1:req]──[S2:req]──[S1:resp]──[S2:resp]──
             (interleaved, parallel, single connection)

3. HEADER COMPRESSION (HPACK):
   First request: full headers sent and indexed in a table.
   Subsequent requests: only changed headers sent (delta encoding).
   Static table: 61 pre-defined header entries (method: GET = index 2, etc.)
   Dynamic table: built during connection for repeated custom headers.
   Result: header overhead drops ~85-90%.

4. SERVER PUSH:
   Server proactively sends resources client will need before client requests them.
   Example: With GET /index.html, server also pushes style.css and script.js.
   Client can cancel pushes it doesn't need (RST_STREAM).
   Status: Deprecated in Chrome/Firefox (2022) due to poor real-world adoption.

5. STREAM PRIORITIZATION:
   Streams can have weights (1-256) and dependencies.
   High-priority streams (HTML) served before lower-priority (analytics JS).
   Replaced by HTTP/3 Extensible Priorities (RFC 9218).

REMAINING PROBLEM WITH HTTP/2:
  TCP Head-of-Line Blocking:
    HTTP/2 eliminates APPLICATION-layer HOL blocking via multiplexing.
    BUT TCP still delivers bytes in order. If one TCP packet is lost,
    ALL streams on that connection stall until the lost packet is retransmitted.
    Multiplexing 100 streams on one TCP = 100x amplification of HOL at TCP level.
    This is the motivation for HTTP/3.

================================================================================
3. HTTP/3 — QUIC TRANSPORT
================================================================================

HTTP/3 replaces TCP+TLS with QUIC (Quick UDP Internet Connections):

QUIC PROPERTIES:
  - Built on UDP (bypasses TCP entirely)
  - TLS 1.3 integrated (not an add-on)
  - Stream-level reliability and ordering (loss in one stream ≠ blocking others)
  - 0-RTT connection establishment (no round trip for returning connections)
  - Connection migration (IP address change doesn't break connection)

WHY UDP FOR A RELIABLE PROTOCOL?
  QUIC implements its own reliability on top of UDP — but with stream-level
  granularity. Lost packet → retransmit only affects the ONE stream that
  owns those bytes, not all streams on the connection.

0-RTT vs HTTPS LATENCY:
  HTTP/1.1 + TLS 1.2 : 3 RTT before first byte (TCP: 1RTT + TLS1.2: 2RTT)
  HTTP/2 + TLS 1.3   : 2 RTT (TCP: 1RTT + TLS1.3: 1RTT)
  HTTP/3 + QUIC (new): 1 RTT (QUIC+TLS combined handshake)
  HTTP/3 + QUIC (resume): 0 RTT (cached session: send data immediately)

CONNECTION MIGRATION:
  Problem: Mobile user switches from WiFi to cellular. TCP uses (src_ip, src_port,
  dst_ip, dst_port) as 4-tuple identifier → WiFi → cellular changes src_ip → TCP
  connection breaks → full reconnect + TLS handshake.
  
  QUIC solution: Connection identified by 64-bit Connection ID (not IP:port).
  If IP changes, client sends new IP with same Connection ID → connection survives.
  Critical for mobile users and seamless video streaming.

HTTP/3 PROTOCOL STACK:
  HTTP/3 (Application framing)
  QPACK   (Header compression — HPACK adapted for QUIC)
  QUIC    (Transport: reliability, multiplexing, flow control)
  UDP     (Datagram)
  IP
  Ethernet/WiFi

4. COMPARISON TABLE
================================================================================

Feature                  | HTTP/1.1   | HTTP/2     | HTTP/3
-------------------------|------------|------------|------------------
Protocol                 | Text       | Binary     | Binary (QUIC)
Transport                | TCP        | TCP        | UDP (QUIC)
TLS                      | External   | External   | Built-in (TLS 1.3)
Multiplexing             | No         | Yes        | Yes
App-level HOL blocking   | Yes        | No         | No
Transport HOL blocking   | Yes        | Yes        | No
Header compression       | No         | HPACK      | QPACK
Server Push              | No         | Yes (deprecated)| Deprecated
0-RTT connection         | No         | No         | Yes (returning clients)
Connection migration     | No         | No         | Yes (mobile)
Head of line blocking    | Both       | TCP only   | None
Connections per origin   | 6          | 1          | 1
Priority                 | No         | Stream weights| Extensible Priorities

5. ENABLE HTTP/2 IN SPRING BOOT
================================================================================

# application.properties
server.http2.enabled=true

# Must use HTTPS for browser-initiated HTTP/2 (h2)
# h2c = HTTP/2 cleartext (no TLS) — for service-to-service

# For embedded Tomcat (default in Spring Boot):
server.ssl.key-store=classpath:keystore.p12
server.ssl.key-store-password=changeit
server.ssl.key-store-type=PKCS12
server.ssl.key-alias=tomcat

# For Spring WebFlux (Netty):
# HTTP/2 is supported natively; enable via:
server.http2.enabled=true

HTTP/2 client (RestClient / WebClient):
  // Spring WebFlux WebClient automatically uses H2 if server supports it
  // For RestTemplate:
  HttpClient httpClient = HttpClient.create()
      .protocol(HttpProtocol.H2); // or H2C for cleartext
  
  WebClient client = WebClient.builder()
      .clientConnector(new ReactorClientHttpConnector(httpClient))
      .build();

6. HTTP/3 ADOPTION STATUS
================================================================================

As of 2025:
  Browsers: Chrome, Firefox, Safari, Edge — all support HTTP/3
  CDNs: Cloudflare (default), AWS CloudFront, Fastly, Akamai
  Web servers: nginx (with QUIC patch), Caddy, LiteSpeed
  Java: JDK 21+ with loom; Netty 5 adds QUIC; Armeria framework supports H3
  Spring Boot: HTTP/3 support via Netty QUIC (experimental in 2024)

DEPLOYMENT PATTERN:
  Use CDN (Cloudflare, CloudFront) that handles HTTP/3 at the edge.
  CDN → backend communication can use HTTP/1.1 or HTTP/2 on your infrastructure.
  This gives HTTP/3 benefits without changing your app servers.

HOW CLIENT DISCOVERS HTTP/3:
  Server sends Alt-Svc header:
    Alt-Svc: h3=":443"; ma=86400
  This tells client: "try HTTP/3 on port 443 for next 86400 seconds"
  Client caches this and uses QUIC on next visit (hence 0-RTT possible on return)

7. INTERVIEW QUESTIONS — HTTP/2 vs HTTP/3
================================================================================

Q1: What is HTTP/2 multiplexing and what problem does it solve?
    HTTP/1.1 effectively sends one request at a time per connection (pipelining
    is poorly supported). Multiple connections per domain (up to 6) were the
    workaround. HTTP/2 multiplexing allows multiple request/response streams to
    share a single TCP connection simultaneously, eliminating application-level
    head-of-line blocking. Each stream is independent — a slow stream doesn't
    block others. This reduces connections from 6 to 1, lowering overhead.

Q2: What is head-of-line blocking in HTTP/2 and why does HTTP/3 solve it?
    HTTP/2 solves application-level HOL (one slow request doesn't block others)
    but TCP still delivers bytes sequentially. If a TCP packet is dropped, ALL
    HTTP/2 streams on that connection wait for retransmission, even streams whose
    data was already received. HTTP/3 uses QUIC (UDP-based) where each stream has
    independent reliability. A lost packet only blocks the specific stream it
    belongs to — other streams continue unaffected.

Q3: What is 0-RTT in QUIC and what are its security trade-offs?
    When a client reconnects to a server it previously connected to, QUIC can
    send application data in the first packet (0 round trips before data). This
    is possible because session tickets from the previous TLS 1.3 session are
    cached and used to derive a key without a new handshake. Trade-off: 0-RTT
    data is vulnerable to replay attacks — a network attacker can replay the
    0-RTT data. Solution: servers should only accept idempotent requests (GET, HEAD)
    as 0-RTT data. Never 0-RTT for POST/payment operations.

Q4: What is HPACK and why was it introduced in HTTP/2?
    HTTP/1.1 sends full headers on every request — repeated headers like
    User-Agent, Accept, Cookie add significant overhead on pages with many requests.
    HPACK (HTTP/2 Header Compression) uses a static table (61 common headers)
    and a dynamic table (built during connection) to encode repeated headers as
    1-2 byte indexes instead of full strings. Header overhead drops ~85%.
    QPACK in HTTP/3 adapts this for QUIC (where streams can arrive out of order).

Q5: How would you enable HTTP/2 in a Spring Boot application?
    Add server.http2.enabled=true to application.properties. For browser-facing
    HTTP/2 (h2), TLS is required (configure SSL keystore). Spring Boot on Netty
    (WebFlux) supports HTTP/2 natively. On Tomcat, HTTP/2 also works with SSL.
    For h2c (cleartext H2 for service-to-service), configure via HttpClient.
    In production, CDNs (Cloudflare, CloudFront) provide HTTP/2 and HTTP/3 at
    the edge while the backend uses HTTP/1.1 or HTTP/2 internally.
