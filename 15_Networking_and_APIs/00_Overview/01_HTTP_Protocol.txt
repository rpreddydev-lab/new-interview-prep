================================================================================
HTTP PROTOCOL — IN DEPTH
================================================================================

WHAT IS HTTP?
--------------
HTTP (HyperText Transfer Protocol) is an application-layer, stateless,
request-response protocol used for transmitting hypermedia documents and APIs.
It runs on top of TCP (or QUIC for HTTP/3).

================================================================================
1. HTTP REQUEST STRUCTURE
================================================================================

REQUEST LINE
  <METHOD> <Request-URI> <HTTP-Version>
  Example: GET /api/users/42 HTTP/1.1

REQUEST HEADERS (common ones)
  Host           : example.com                 (required in HTTP/1.1)
  Accept         : application/json
  Content-Type   : application/json
  Authorization  : Bearer <token>
  Content-Length : 128
  Cache-Control  : no-cache
  If-None-Match  : "etag-value"
  Connection     : keep-alive
  User-Agent     : Mozilla/5.0 ...

REQUEST BODY (for POST/PUT/PATCH)
  { "name": "Alice", "email": "alice@example.com" }

================================================================================
2. HTTP RESPONSE STRUCTURE
================================================================================

STATUS LINE
  <HTTP-Version> <Status-Code> <Reason-Phrase>
  Example: HTTP/1.1 200 OK

RESPONSE HEADERS (common ones)
  Content-Type      : application/json; charset=UTF-8
  Content-Length    : 256
  ETag              : "abc123"
  Cache-Control     : max-age=3600
  Location          : /api/users/42   (used with 201/301/302)
  X-Request-Id      : uuid            (correlation/tracing)
  Retry-After       : 60              (used with 429/503)
  WWW-Authenticate  : Bearer realm="api"

RESPONSE BODY
  { "id": 42, "name": "Alice" }

================================================================================
3. HTTP METHODS
================================================================================

METHOD   SAFE  IDEMPOTENT  DESCRIPTION
-------  ----  ----------  ----------------------------------------------------
GET      YES   YES         Retrieve resource; no side effects
HEAD     YES   YES         Same as GET but no body; used for metadata/cache check
POST     NO    NO          Create resource or trigger action; not idempotent
PUT      NO    YES         Replace entire resource; idempotent
PATCH    NO    NO*         Partial update; idempotent IF applied same patch
DELETE   NO    YES         Delete resource; repeated call returns 404 (still idempotent)
OPTIONS  YES   YES         Describe communication options; used for CORS preflight
CONNECT  NO    NO          Establishes tunnel (used by proxies for HTTPS)
TRACE    YES   YES         Echo back request for debugging (usually disabled)

*PATCH is conditionally idempotent depending on the patch semantics.

SAFE     = Does not modify server state
IDEMPOTENT = Calling N times produces same result as calling once

WHY IDEMPOTENCY MATTERS:
  In distributed systems, network failures cause retries. If your operation
  is idempotent, retries are safe. POST operations need idempotency tokens
  (e.g., Idempotency-Key header) to handle this.

================================================================================
4. HTTP VERSIONS
================================================================================

HTTP/1.0 (1996)
  - New TCP connection per request (expensive)
  - No keep-alive by default

HTTP/1.1 (1997) — still widely used
  - Persistent connections (keep-alive) by default
  - Pipelining support (but head-of-line blocking still an issue)
  - Chunked transfer encoding
  - Host header mandatory (enables virtual hosting)
  - Conditional GET (If-Modified-Since, ETag)

HTTP/2 (2015)
  - Binary framing (not text-based)
  - Multiplexing: multiple requests over single TCP connection simultaneously
  - Header compression (HPACK)
  - Server Push: server can proactively send resources
  - Stream prioritization
  - Still suffers from TCP head-of-line blocking (at transport layer)
  - Requires TLS in practice (browsers enforce it)

HTTP/3 (2022)
  - Built on QUIC (UDP-based transport)
  - Solves transport-layer head-of-line blocking
  - Faster connection establishment (0-RTT or 1-RTT handshake)
  - Built-in TLS 1.3
  - Better performance on lossy/mobile networks
  - Stream-level independence in QUIC

HEAD-OF-LINE BLOCKING EXPLAINED:
  HTTP/1.1: Second request must wait for first to complete (no multiplexing)
  HTTP/2  : Multiple streams but one TCP connection; a lost packet blocks ALL streams
  HTTP/3  : Each QUIC stream is independent; packet loss only affects that stream

================================================================================
5. HTTP CACHING
================================================================================

Cache-Control DIRECTIVES:
  max-age=3600        : Cache valid for 3600 seconds
  no-cache            : Must revalidate with server before using cached response
  no-store            : Do not store response at all (sensitive data)
  public              : Can be cached by any cache (CDN, proxy)
  private             : Only cached by browser, not shared caches
  must-revalidate     : Once stale, must revalidate (not serve stale)
  s-maxage=600        : Override max-age for shared caches (CDNs)
  immutable           : Content will never change; skip revalidation

CONDITIONAL REQUESTS:
  ETag / If-None-Match         : Hash-based validation
  Last-Modified / If-Modified-Since : Time-based validation
  If server returns 304 Not Modified → client uses cached copy

CACHE HIERARCHY:
  Browser Cache → Reverse Proxy / CDN → Origin Server

6. HTTP HEADERS DEEP DIVE
================================================================================

CONTENT NEGOTIATION
  Accept: application/json, text/html;q=0.9, */*;q=0.8
  Accept-Language: en-US, en;q=0.5
  Accept-Encoding: gzip, deflate, br
  Content-Type: application/json  (response)
  Vary: Accept-Encoding            (tell caches to vary by this header)

SECURITY HEADERS
  Strict-Transport-Security (HSTS): max-age=31536000; includeSubDomains
  Content-Security-Policy (CSP)   : script-src 'self'
  X-Frame-Options                 : DENY / SAMEORIGIN
  X-Content-Type-Options          : nosniff
  Referrer-Policy                 : no-referrer-when-downgrade

RATE LIMITING / PAGINATION HEADERS
  X-RateLimit-Limit   : 1000
  X-RateLimit-Remaining: 837
  X-RateLimit-Reset   : 1718000000  (epoch)
  Link: <...?page=2>; rel="next", <...?page=10>; rel="last"

AUTHENTICATION
  Authorization: Basic base64(user:pass)
  Authorization: Bearer <jwt_token>
  Authorization: Digest ...
  Cookie: session_id=abc123
  Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict

================================================================================
7. HTTP CONNECTION MANAGEMENT
================================================================================

PERSISTENT CONNECTIONS (HTTP/1.1 default)
  - Single TCP connection reused for multiple request/response cycles
  - Server can close after timeout (keep-alive timeout)
  - Connection: close  overrides keep-alive

PIPELINING (HTTP/1.1, rarely used)
  - Multiple requests sent without waiting for responses
  - Still has head-of-line blocking issue
  - Buggy in many proxies; largely abandoned in favour of HTTP/2

HTTP/2 MULTIPLEXING
  - Multiple logical streams over one TCP connection
  - Stream = independent request/response pair
  - No need for multiple TCP connections or domain sharding tricks

CONNECTION POOLING (relevant for Java apps)
  - Client maintains pool of established TCP/TLS connections
  - RestTemplate / WebClient / OkHttp / Apache HttpClient all support this
  - Key settings: maxConnections, maxIdleTime, connectionTimeout, readTimeout

8. WHAT HAPPENS WHEN YOU TYPE A URL? (Classic Interview Question)
================================================================================

Step-by-step:

1.  BROWSER CACHE CHECK        : Check if URL response is cached
2.  DNS RESOLUTION             : Resolve domain to IP
                                  - Browser DNS cache → OS cache → Hosts file
                                  - Recursive resolver → Root nameserver
                                  - TLD nameserver → Authoritative nameserver
3.  TCP CONNECTION             : 3-way handshake (SYN → SYN-ACK → ACK)
4.  TLS HANDSHAKE (HTTPS)      : Client Hello → Server Hello + Cert
                                  → Key Exchange → Finished (see TLS section)
5.  HTTP REQUEST SENT          : GET / HTTP/1.1 + headers
6.  SERVER PROCESSES REQUEST   :
     - Load Balancer → Web Server (Nginx) → App Server (Tomcat/Node)
     - App logic: auth check, DB query, business logic
7.  HTTP RESPONSE RETURNED     : 200 OK + headers + body (HTML/JSON)
8.  BROWSER RENDERS            : Parse HTML → Build DOM → Fetch CSS/JS/Images
                                  → CSSOM → Render tree → Layout → Paint
9.  SUBSEQUENT REQUESTS        : Connection may be reused (keep-alive/HTTP2)

KEY FOLLOW-UP POINTS:
  - How do you speed this up? → CDN, caching, HTTP/2, DNS prefetch, preconnect
  - What if DNS fails?        → NXDOMAIN, fallback to other resolvers
  - What if TLS cert invalid? → Browser shows warning/blocks

9. IMPORTANT HTTP CONCEPTS FOR INTERVIEWS
================================================================================

CHUNKED TRANSFER ENCODING
  - Server streams large response in chunks
  - Used when total Content-Length is unknown (generated content, streaming)
  - Transfer-Encoding: chunked header

MULTIPART REQUESTS
  - Content-Type: multipart/form-data
  - Used for file uploads
  - Each part has its own Content-Disposition and Content-Type

REDIRECTS
  301 Permanent Redirect : Browsers cache; change bookmarks; method may change to GET
  302 Found              : Temporary; do not cache; method may change to GET  
  303 See Other          : After POST/PUT; redirect to result with GET
  307 Temporary Redirect : Temporary; method must NOT change
  308 Permanent Redirect : Permanent; method must NOT change

RANGE REQUESTS (Byte Serving)
  Request:  Range: bytes=0-1023
  Response: 206 Partial Content + Content-Range: bytes 0-1023/4096
  Used for: Video streaming, resumable downloads

10. INTERVIEW QUESTIONS — HTTP PROTOCOL
================================================================================

Q1: What is the difference between HTTP/1.1, HTTP/2, and HTTP/3?
    HTTP/1.1: text-based, persistent connections, one request at a time per connection,
    head-of-line blocking. HTTP/2: binary, multiplexed streams over one TCP connection,
    header compression, server push — but still has TCP-level HOL blocking. HTTP/3:
    uses QUIC over UDP, eliminates HOL blocking at transport level, faster handshake.

Q2: What does "stateless" mean in HTTP? How do you maintain session state?
    Each request is independent; server has no memory of previous requests.
    State maintained via: cookies (server-side sessions), JWT tokens (client-side),
    or distributed session stores (Redis).

Q3: What's the difference between PUT and PATCH?
    PUT replaces the entire resource (client sends full representation).
    PATCH applies a partial update (client sends only changed fields).
    PUT is idempotent; PATCH may or may not be.

Q4: What HTTP status code would you return for a validation error?
    400 Bad Request (syntax/format error) or 422 Unprocessable Entity
    (syntactically valid but semantically wrong — most RESTful APIs prefer 422).

Q5: How does HTTP caching work?
    Browser stores response with headers (Cache-Control, ETag, Last-Modified).
    On next request, sends If-None-Match or If-Modified-Since. Server returns
    304 Not Modified if unchanged → browser uses cached copy, saving bandwidth.

Q6: Explain Content-Type vs Accept header.
    Content-Type: describes the format of the body being SENT (request or response).
    Accept: tells server what format the CLIENT wants in response.

Q7: What is a CORS preflight request?
    Browser sends OPTIONS request before cross-origin request with custom headers
    or non-simple methods. Server responds with Access-Control headers specifying
    what's allowed. Browser only proceeds if allowed.

Q8: What is the difference between 401 and 403?
    401 Unauthorized: client is not authenticated (no or invalid credentials).
    403 Forbidden: client is authenticated but not authorized for this resource.
