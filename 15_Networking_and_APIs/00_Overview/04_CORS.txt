================================================================================
CORS — CROSS-ORIGIN RESOURCE SHARING — IN DEPTH
================================================================================

WHAT IS CORS?
--------------
CORS is a browser security mechanism that controls how web pages can request
resources from a different origin than the one that served the page.

ORIGIN = scheme + hostname + port
  https://api.example.com:443  ← all three parts define an origin

Same Origin:
  https://example.com/page1   → requests → https://example.com/api  ✅ ALLOWED
Cross Origin:
  https://app.example.com     → requests → https://api.example.com  ❌ BLOCKED by CORS

================================================================================
1. THE SAME-ORIGIN POLICY (SOP)
================================================================================

The Same-Origin Policy is a browser security model that prevents scripts on
one origin from reading responses from a different origin without permission.

This protects against Cross-Site Request Forgery (CSRF) and data theft.

WHAT SOP BLOCKS:
  - AJAX/fetch requests to different origin (reading response)
  - Access to cookies/localStorage of different origin
  - Reading iframe content from different origin

WHAT SOP DOES NOT BLOCK:
  - Loading scripts, images, stylesheets (src= / href=)
  - Form submissions (POST — but response can't be read)
  - Redirects

CORS is the mechanism that RELAXES same-origin restrictions in a controlled way.

================================================================================
2. SIMPLE REQUESTS vs PREFLIGHT REQUESTS
================================================================================

SIMPLE REQUEST (No Preflight Required):
  Conditions: Method is GET, HEAD, or POST
              AND Content-Type is one of:
                application/x-www-form-urlencoded
                multipart/form-data
                text/plain
              AND no custom headers
              AND no credentials with non-standard headers

  Browser sends request directly. Server includes CORS headers in response.
  Browser either allows or blocks script access to the response.

  EXAMPLE:
  Request:
    GET /api/data HTTP/1.1
    Host: api.example.com
    Origin: https://app.example.com    ← Browser adds this automatically

  Response:
    HTTP/1.1 200 OK
    Access-Control-Allow-Origin: https://app.example.com
    Content-Type: application/json

PREFLIGHT REQUEST (OPTIONS):
  Required when:
    - Method is PUT, DELETE, PATCH, CONNECT, TRACE, or OPTIONS
    - Content-Type is application/json (or other non-simple types)
    - Custom headers are present (e.g., Authorization, X-Custom-Header)
    - With-credentials mode with non-simple combinations

  Browser sends OPTIONS request first to check if actual request is allowed.
  Only proceeds with actual request if server grants permission.

  PREFLIGHT EXCHANGE:
  ┌──────────────┐                           ┌──────────────┐
  │   Browser    │                           │   API Server │
  └──────┬───────┘                           └──────┬───────┘
         │ OPTIONS /api/users HTTP/1.1               │
         │ Origin: https://app.example.com           │
         │ Access-Control-Request-Method: POST       │
         │ Access-Control-Request-Headers: Authorization, Content-Type
         │ ─────────────────────────────────────────>│
         │                                           │
         │ HTTP/1.1 204 No Content                   │
         │ Access-Control-Allow-Origin: https://app.example.com
         │ Access-Control-Allow-Methods: GET, POST, PUT, DELETE
         │ Access-Control-Allow-Headers: Authorization, Content-Type
         │ Access-Control-Max-Age: 86400             │
         │ <─────────────────────────────────────────│
         │                                           │
         │ [Browser decides: allowed! Sends actual]  │
         │                                           │
         │ POST /api/users HTTP/1.1                  │
         │ Origin: https://app.example.com           │
         │ Authorization: Bearer xyz                 │
         │ Content-Type: application/json            │
         │ ─────────────────────────────────────────>│
         │                                           │
         │ HTTP/1.1 201 Created                      │
         │ Access-Control-Allow-Origin: https://app.example.com
         │ <─────────────────────────────────────────│

3. CORS HEADERS
================================================================================

REQUEST HEADERS (sent by browser):
  Origin                            : https://app.example.com
  Access-Control-Request-Method     : POST      (preflight only)
  Access-Control-Request-Headers    : Authorization, Content-Type (preflight)

RESPONSE HEADERS (sent by server):

  Access-Control-Allow-Origin
    - Specific origin: Access-Control-Allow-Origin: https://app.example.com
    - Wildcard:        Access-Control-Allow-Origin: *
    - NOTE: Wildcard cannot be used with credentials (cookies/auth headers)

  Access-Control-Allow-Methods
    - Access-Control-Allow-Methods: GET, POST, PUT, DELETE, PATCH, OPTIONS

  Access-Control-Allow-Headers
    - Access-Control-Allow-Headers: Authorization, Content-Type, X-Request-Id

  Access-Control-Max-Age
    - How long (seconds) the browser can cache preflight response
    - Access-Control-Max-Age: 86400   (24 hours)
    - Reduces preflight requests significantly

  Access-Control-Allow-Credentials
    - Access-Control-Allow-Credentials: true
    - Allows cookies/auth headers to be sent cross-origin
    - REQUIRES specific origin in Allow-Origin (not *)

  Access-Control-Expose-Headers
    - Which response headers the browser script can access
    - Default: only simple headers (Cache-Control, Content-Type, etc.)
    - Access-Control-Expose-Headers: X-Custom-Header, X-Request-Id

4. CORS WITH CREDENTIALS
================================================================================

When sending cookies or Authorization headers cross-origin:

JavaScript:
  fetch('https://api.example.com/data', {
    credentials: 'include'   // Send cookies
  });

  // Or with Authorization header:
  fetch('https://api.example.com/data', {
    headers: { 'Authorization': 'Bearer token' }
  });

Server MUST:
  1. Return specific origin (not *):  Access-Control-Allow-Origin: https://app.example.com
  2. Return:                          Access-Control-Allow-Credentials: true

If server returns * with credentials → browser blocks the response.

SECURITY NOTE: Be careful exposing Access-Control-Allow-Credentials: true.
This allows the browser to include cookies. Combined with wildcard origin,
this would be a major security vulnerability (hence it's not allowed).

5. CORS IN SPRING BOOT
================================================================================

METHOD 1: @CrossOrigin annotation on controller/method
  @RestController
  @CrossOrigin(origins = "https://app.example.com")
  public class UserController {

      @GetMapping("/users")
      @CrossOrigin(origins = "*", maxAge = 3600)
      public List<User> getUsers() { ... }
  }

METHOD 2: Global CORS Configuration via WebMvcConfigurer
  @Configuration
  public class CorsConfig implements WebMvcConfigurer {

      @Override
      public void addCorsMappings(CorsRegistry registry) {
          registry.addMapping("/api/**")
                  .allowedOrigins("https://app.example.com", "https://admin.example.com")
                  .allowedMethods("GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS")
                  .allowedHeaders("Authorization", "Content-Type", "X-Request-Id")
                  .exposedHeaders("X-Custom-Header")
                  .allowCredentials(true)
                  .maxAge(3600);
      }
  }

METHOD 3: CORS via Spring Security (when Spring Security is active)
  // Spring Security intercepts before Spring MVC — must configure here too
  @Bean
  SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
      http.cors(cors -> cors.configurationSource(corsConfigurationSource()))
          .csrf().disable()
          ...;
      return http.build();
  }

  @Bean
  CorsConfigurationSource corsConfigurationSource() {
      CorsConfiguration config = new CorsConfiguration();
      config.setAllowedOrigins(List.of("https://app.example.com"));
      config.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
      config.setAllowedHeaders(List.of("*"));
      config.setAllowCredentials(true);
      config.setMaxAge(3600L);

      UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
      source.registerCorsConfiguration("/**", config);
      return source;
  }

IMPORTANT: If you use Spring Security, configure CORS in the SecurityFilterChain.
           @CrossOrigin annotations won't work for requests rejected by Spring Security.

6. CORS IN API GATEWAY
================================================================================

When using an API Gateway (AWS API Gateway, Spring Cloud Gateway, Kong):
  - Configure CORS at the gateway level
  - Don't configure at application level (duplication causes double headers → error)

AWS API Gateway CORS:
  - Enable CORS per method or globally
  - Gateway adds Access-Control-Allow-Origin header to all responses
  - For Lambda integration: can configure in console or via SAM/CloudFormation

Spring Cloud Gateway:
  spring:
    cloud:
      gateway:
        globalcors:
          corsConfigurations:
            '[/**]':
              allowedOrigins: "https://app.example.com"
              allowedMethods:
                - GET
                - POST
                - PUT
                - DELETE
              allowedHeaders: "*"
              allowCredentials: true
              maxAge: 3600

7. COMMON CORS ERRORS AND FIXES
================================================================================

ERROR 1: "No 'Access-Control-Allow-Origin' header is present"
  Cause:  Server not sending CORS headers
  Fix:    Add CORS configuration to server

ERROR 2: "The value of the 'Access-Control-Allow-Origin' header in the response
          must not be the wildcard '*' when the request's credentials mode is 'include'"
  Cause:  Using credentials with wildcard origin
  Fix:    Replace * with specific origin in Access-Control-Allow-Origin

ERROR 3: "Request header field Authorization is not allowed by
          Access-Control-Allow-Headers in preflight response"
  Cause:  Authorization not listed in Access-Control-Allow-Headers
  Fix:    Add Authorization to allowedHeaders

ERROR 4: CORS works in GET but not POST/PUT
  Cause:  Preflight OPTIONS request is being blocked (e.g., by security layer)
  Fix:    Ensure OPTIONS method is allowed and returns CORS headers
          In Spring Security: .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()

ERROR 5: Double CORS headers (browser sees 2 Access-Control-Allow-Origin values)
  Cause:  CORS configured both in app and in API Gateway/nginx (double)
  Fix:    Configure CORS in one place only

8. CORS vs CSRF
================================================================================

CORS and CSRF are related but distinct:

CORS: Browser mechanism that prevents cross-origin READS.
      Prevents one website from reading another website's API responses.

CSRF: Attack where malicious site causes browser to make authenticated
      requests to your API using victim's cookies.
      
RELATIONSHIP:
  CORS does NOT fully prevent CSRF (form submissions and simple requests skip preflight)
  CSRF tokens or SameSite cookies are the proper CSRF defense.

  SameSite=Strict: Cookie only sent for same-site requests
  SameSite=Lax:    Cookie sent for top-level navigations, not for cross-site subrequests
  SameSite=None:   Cookie sent for all requests (requires Secure)

9. INTERVIEW QUESTIONS — CORS
================================================================================

Q1: What is CORS and why does it exist?
    CORS is a browser mechanism that controls cross-origin HTTP requests.
    It exists because of the Same-Origin Policy — browsers block scripts from
    reading responses from different origins to protect against data theft.
    CORS allows servers to explicitly grant permission to specific origins.

Q2: What is a preflight request? When is it triggered?
    An OPTIONS request sent by the browser before a cross-origin request that
    has custom headers, non-simple methods (PUT/DELETE), or non-simple content
    types (application/json). The browser asks the server "are you OK with this
    type of request from this origin?" before sending the actual request.

Q3: Can you use Access-Control-Allow-Origin: * with credentials?
    No. Browsers explicitly block this combination. When using credentials
    (cookies or Authorization header), you must specify the exact origin.
    This is a security feature to prevent CSRF-like attacks.

Q4: How would you configure CORS in a Spring Boot application with Spring Security?
    You must configure CORS in the Spring Security filter chain using
    CorsConfigurationSource bean and http.cors(). @CrossOrigin annotations
    are processed by Spring MVC AFTER Security filters — requests may be
    rejected before reaching MVC if not configured at the security level.

Q5: What is the difference between CORS and CSRF?
    CORS controls which origins browsers allow to READ cross-origin responses
    (browser enforcement). CSRF is an attack where malicious sites trick
    browsers into making authenticated requests using stored cookies.
    CORS headers are a server directive to the browser. CSRF tokens are
    a request validation mechanism. Both address cross-origin concerns but
    from different angles.

Q6: What does Access-Control-Max-Age do?
    Caches the preflight response for the specified seconds. Browser won't
    send another OPTIONS request for that URL during this period.
    Reduces network overhead for frequent cross-origin API calls.

Q7: Why does CORS not protect against all cross-origin requests?
    CORS only applies to XMLHttpRequest/fetch initiated by JavaScript.
    Form submissions, script/image/iframe src= attributes bypass CORS.
    This is why CSRF tokens are still needed for form-based attacks.
