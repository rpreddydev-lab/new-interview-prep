EXCHANGES, QUEUES, AND BINDINGS
================================

THE ROUTING MODEL:
  Producer → Exchange → [Binding with routing key] → Queue → Consumer

=== EXCHANGE TYPES ===

1. DIRECT EXCHANGE
   - Routes messages to queues where binding key == routing key (exact match)
   - Default exchange is a direct exchange with empty name
   - Use case: task distribution to specific worker queues

   Example:
   Exchange: "orders"
   Binding:  queue "order-processing" with key "order.created"
   Producer: publish with routingKey="order.created" → goes to "order-processing"

2. FANOUT EXCHANGE
   - Ignores routing key — broadcasts to ALL bound queues
   - Use case: notifications, pub/sub, broadcast events

   Example:
   Exchange: "notifications"
   Queues bound: "email-queue", "sms-queue", "push-queue"
   Any message published → goes to all 3 queues

3. TOPIC EXCHANGE
   - Pattern-based routing using wildcards in routing key
   - * = matches exactly one word
   - # = matches zero or more words
   - Routing key format: "word.word.word"

   Example:
   Binding key: "order.*.created" → matches "order.us.created", "order.eu.created"
   Binding key: "order.#"        → matches "order.created", "order.us.priority.created"

4. HEADERS EXCHANGE
   - Routes based on message header attributes, not routing key
   - Uses x-match: "all" (all headers must match) or "any" (any header matches)
   - Use case: complex routing conditions

=== QUEUES ===

Queue Properties:
- durable: survives broker restart (stored on disk)
- exclusive: used by only one connection, deleted when connection closes
- auto-delete: deleted when last consumer unsubscribes
- arguments: extra settings (TTL, max-length, dead-letter exchange, etc.)

Queue Types (RabbitMQ 3.8+):
- Classic: default, simple FIFO
- Quorum: replicated across nodes (recommended for durability)
- Stream: append-only log (similar to Kafka topics) — RabbitMQ 3.9+

Queue Arguments (x-arguments):
- x-message-ttl: TTL per message in milliseconds
- x-expires: how long queue can be unused before deletion
- x-max-length: max number of messages; oldest dropped on overflow
- x-dead-letter-exchange: where to route rejected/expired messages
- x-queue-type: "classic", "quorum", or "stream"

=== BINDINGS ===

- A binding connects an exchange to a queue
- Can include an optional routing key (used by direct/topic exchanges)
- One exchange can be bound to many queues
- One queue can be bound to many exchanges

Default Binding:
- Every queue is automatically bound to the default exchange "" (empty name)
- Routing key = queue name
- Allows publishing directly to a queue by name

=== MESSAGES ===

Message Properties:
- routing_key: used by exchange for routing
- content_type: e.g., "application/json"
- delivery_mode: 1=transient (memory), 2=persistent (disk)
- expiration: message TTL in milliseconds (as string)
- headers: arbitrary key-value pairs
- message_id, correlation_id, reply_to: for RPC patterns
- priority: 0-9 for priority queues

Persistent Messages:
- delivery_mode=2 + durable queue = survives broker restart
- Slight performance cost due to disk writes

Interview Tip:
- Quorum queues are now preferred over classic durable queues for reliability
- Fanout is fastest (no routing key evaluation)
- Topic is the most flexible exchange type
