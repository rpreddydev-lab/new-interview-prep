================================================================================
REDIS DATA STRUCTURES — OVERVIEW FOR INTERVIEWS
================================================================================

1. WHY REDIS HAS RICH DATA STRUCTURES
───────────────────────────────────────
Unlike Memcached (pure key → blob), Redis provides server-side data structures.
This means you can manipulate data IN Redis without fetching it to the client:
  - Increment a counter:         INCR hits:page:home
  - Push to a list:              LPUSH queue:emails "msg"
  - Add to a sorted set:         ZADD leaderboard 100 "player1"
  - Get set intersection:        SINTERSTORE result set1 set2

No deserialization → modify → serialize → write cycle.
Operations are atomic. Less network round trips.


2. COMPLETE DATA STRUCTURE REFERENCE
──────────────────────────────────────
  Type          │ Internal Encoding       │ Max size  │ Typical use case
  ──────────────┼─────────────────────────┼───────────┼─────────────────────────
  String        │ int / embstr / raw      │ 512 MB    │ Cache, counters, flags
  List          │ listpack / quicklist    │ 2^32-1    │ Queue, stack, timeline
  Set           │ listpack / intset /     │ 2^32-1    │ Tags, unique members
                │ hashtable               │           │
  Sorted Set    │ listpack / skiplist +   │ 2^32-1    │ Leaderboard, ranking
                │ hashtable               │           │
  Hash          │ listpack / hashtable    │ 2^32-1    │ Objects, user profiles
  Stream        │ radix tree + listpack   │ unbounded │ Event log, MQ
  Bitmap        │ (String underneath)     │ 512 MB    │ Active users, feature flags
  HyperLogLog   │ (String underneath)     │ 12 KB     │ Unique count estimation
  Geospatial    │ (Sorted Set underneath) │ 2^32-1    │ Proximity search


3. MEMORY ENCODING (COMPACT vs FULL)
─────────────────────────────────────
Redis uses compact encodings for small collections to save memory.
When the collection grows beyond a threshold, it upgrades to a full encoding.

  Type        │ Compact (small)     │ Full (large)      │ Thresholds (defaults)
  ────────────┼─────────────────────┼───────────────────┼───────────────────────
  List        │ listpack            │ quicklist         │ listpack-max-size 128
  Hash        │ listpack            │ hashtable         │ hash-max-listpack-entries 128
  Set         │ listpack / intset   │ hashtable         │ set-max-intset-entries 512
  Sorted Set  │ listpack            │ skiplist+hashtable│ zset-max-listpack-entries 128

  OBJECT ENCODING key   → shows current encoding
  OBJECT REFCOUNT key   → reference count (memory sharing)
  OBJECT IDLETIME key   → seconds since last access (LRU)
  OBJECT FREQ key       → access frequency (LFU)
  OBJECT HELP           → all OBJECT subcommands


4. TIME COMPLEXITIES — QUICK REFERENCE
────────────────────────────────────────
  String:     SET/GET → O(1). APPEND → O(1). STRLEN → O(1).
  List:       LPUSH/RPUSH → O(1). LRANGE → O(S+N). LINDEX → O(N).
  Set:        SADD/SMEMBERS/SISMEMBER → O(1) avg. SUNION/SINTER → O(N*M).
  Sorted Set: ZADD → O(log N). ZRANGE → O(log N + M). ZRANK → O(log N).
  Hash:       HSET/HGET → O(1). HGETALL → O(N).
  Stream:     XADD → O(1). XREAD → O(N). XRANGE → O(N).


5. KEY NAMING CONVENTIONS
───────────────────────────
  Redis keys are binary-safe strings. Use structured, hierarchical names:
    object-type:id:field
    Examples:
      user:42:profile
      session:abc123
      product:999:views
      rate:user:42:api
      leaderboard:monthly

  Best practices:
    - Colon as separator (most common convention)
    - Include resource type + identifier
    - Avoid very long key names (wastes memory; key itself is stored)
    - Avoid spaces and special chars (command parsing issues)
    - Max key size: 512 MB (but keep keys short, < 100 chars)


6. COMMON OPERATIONS ACROSS ALL TYPES
────────────────────────────────────────
  DEL key [key …]          → delete one or more keys
  UNLINK key [key …]       → async delete (non-blocking)
  EXISTS key [key …]       → 1 if exists, 0 if not
  TYPE key                  → string / list / set / zset / hash / stream
  RENAME key newkey         → rename key
  EXPIRE key seconds        → set TTL
  PEXPIRE key milliseconds  → set TTL in ms
  TTL key                   → remaining TTL in seconds (-1=none, -2=gone)
  PTTL key                  → remaining TTL in ms
  PERSIST key               → remove TTL
  SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]  → iterate keys

  OBJECT ENCODING key       → check internal encoding
  DEBUG OBJECT key          → detailed object info (dev only)
  MEMORY USAGE key          → bytes used by this key


7. INTERVIEW INSIGHT: WHY ENCODING MATTERS
────────────────────────────────────────────
  Interviewers love asking: "How is a sorted set implemented internally?"

  Small sorted set (≤128 elements, each ≤64 bytes):
    → listpack (contiguous block of memory): cache-friendly, low overhead

  Large sorted set:
    → skiplist (for O(log N) rank/range) + hashtable (for O(1) member lookup)
    → Two data structures maintained simultaneously!

  This dual-structure is why both ZRANK (log N) and ZSCORE (O(1)) are fast.
  The hashtable holds member→score, the skiplist holds sorted score→member.


8. CHOOSING THE RIGHT DATA STRUCTURE
───────────────────────────────────────
  Need to store:
    A simple value (string, number, JSON blob)    → String
    An ordered sequence (queue, stack, timeline)  → List
    A set of unique items (tags, online users)     → Set
    Items with a score/rank (leaderboard, scores) → Sorted Set
    An object with named fields (user profile)    → Hash
    An event log with consumer groups             → Stream
    Flags/presence per user (DAU bitmap)          → Bitmap (on String)
    Approximate unique counts (analytics)         → HyperLogLog
    Location-based queries (nearby drivers)       → Geo (on Sorted Set)
