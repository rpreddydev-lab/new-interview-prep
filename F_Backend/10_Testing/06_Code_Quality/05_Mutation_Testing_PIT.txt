CODE QUALITY — MUTATION TESTING WITH PIT (PITEST)
Complete Interview Preparation Guide
================================================================

1. WHAT IS MUTATION TESTING?
================================================================

Mutation testing evaluates the QUALITY of your test suite, not just coverage.

How it works:
  1. PIT takes your source code and creates many "mutants" — versions with
     small changes (mutations) like replacing + with -, changing > to >=,
     removing a return statement, etc.
  2. Your test suite runs against each mutant.
  3. If a test FAILS → the mutant is "killed" ✅ (tests caught the change)
  4. If ALL tests PASS → the mutant "survived" ❌ (tests didn't detect the bug)
  
Mutation Score = Killed Mutants / (Killed + Survived) × 100%
  - High mutation score → test suite is sensitive to code changes
  - Low mutation score → tests pass but don't verify behavior

Example:
  Original: return a + b;
  Mutant:   return a - b;
  
  Test: assertEquals(5, add(2, 3));  // passes with +, fails with - → KILLED ✅
  
  But:  assertNotNull(add(2, 3));    // passes with both + and - → SURVIVED ❌

2. COMMON MUTATION OPERATORS
================================================================

Operator                | Original     → Mutant
------------------------|----------------------------------
Arithmetic Operator     | a + b        → a - b, a * b
Relational Operator     | x > 0        → x >= 0, x < 0
Conditional Boundary    | i < 10       → i <= 10
Negate Conditional      | if (flag)    → if (!flag)
Return Value Mutator    | return value → return null / 0 / false
Remove Conditionals     | if (...)     → always true / always false
Void Method Calls       | doSomething()→ (remove the call)
Constructor Calls       | new Obj(x)   → new Obj()
Increments              | i++          → i--

3. MAVEN CONFIGURATION
================================================================

  <plugin>
      <groupId>org.pitest</groupId>
      <artifactId>pitest-maven</artifactId>
      <version>1.15.3</version>
      
      <!-- Required for JUnit 5 -->
      <dependencies>
          <dependency>
              <groupId>org.pitest</groupId>
              <artifactId>pitest-junit5-plugin</artifactId>
              <version>1.2.1</version>
          </dependency>
      </dependencies>
      
      <configuration>
          <!-- Target classes to mutate -->
          <targetClasses>
              <param>com.example.service.*</param>
              <param>com.example.domain.*</param>
          </targetClasses>
          
          <!-- Test classes to run (exclude integration tests) -->
          <targetTests>
              <param>com.example.*Test</param>
          </targetTests>
          
          <!-- Mutation score threshold — fail build below this -->
          <mutationThreshold>70</mutationThreshold>
          <coverageThreshold>80</coverageThreshold>
          
          <!-- Mutators to apply -->
          <mutators>
              <mutator>STRONGER</mutator>  <!-- Good balance set -->
              <!-- Alternatives: DEFAULTS, ALL, CONDITIONALS_BOUNDARY -->
          </mutators>
          
          <!-- Threads for faster execution -->
          <threads>4</threads>
          
          <!-- Report format -->
          <outputFormats>
              <outputFormat>HTML</outputFormat>
              <outputFormat>XML</outputFormat>
          </outputFormats>
          
          <!-- Exclude slow/integration tests -->
          <excludedClasses>
              <param>com.example.*IT</param>
              <param>com.example.config.*</param>
          </excludedClasses>
      </configuration>
  </plugin>
  
  Commands:
    mvn org.pitest:pitest-maven:mutationCoverage  # run mutation testing
    mvn test-compile pitest:mutationCoverage       # compile + mutate
  
  Report: target/pit-reports/YYYYMMDDHHMI/index.html

5. PRACTICAL EXAMPLE: CATCHING WEAK TESTS
================================================================

  SOURCE CODE:
    public class DiscountCalculator {
        public double applyDiscount(double price, int couponCode) {
            if (couponCode == 10) {
                return price * 0.90;   // 10% discount
            }
            return price;
        }
    }
  
  WEAK TEST (high line coverage, low mutation score):
    @Test
    void testDiscount() {
        DiscountCalculator calc = new DiscountCalculator();
        double result = calc.applyDiscount(100.0, 10);
        assertTrue(result > 0);   // passes even if formula is wrong!
    }
    
    Mutations survived:
      - return price * 0.90  →  return price * 0.80   ✅ tests still pass!
      - couponCode == 10     →  couponCode != 10       ✅ tests still pass!
    
  STRONG TEST (kills mutations):
    @Test
    void shouldApplyTenPercentDiscountForCoupon10() {
        double result = calc.applyDiscount(100.0, 10);
        assertEquals(90.0, result, 0.001);   // exact value assertion
    }
    
    @Test
    void shouldNotApplyDiscountForOtherCoupons() {
        double result = calc.applyDiscount(100.0, 20);
        assertEquals(100.0, result, 0.001);  // no discount case
    }
    
    Now all mutations are killed: conditional change fails test 2,
    formula change fails test 1.

6. PITEST IN CI/CD
================================================================

  # Separate step to avoid slowing main build
  - name: Run mutation tests
    run: mvn org.pitest:pitest-maven:mutationCoverage
    # Run on schedule (nightly) or only on main branch
    # PIT takes ~3-10x longer than regular tests
  
  # Archive report
  - uses: actions/upload-artifact@v4
    with:
      name: pit-report
      path: target/pit-reports/

  Strategy: Run PIT nightly or on main branch merges.
  Don't run on every PR commit (too slow).

7. MUTATION TESTING VS CODE COVERAGE
================================================================

Scenario                         | Line Coverage | Mutation Score
---------------------------------|---------------|---------------
Tests with no assertions         |     100%      |      0%
Tests assert wrong value         |     100%      |     Low
Tests assert correct values      |     100%      |    High
Untested edge cases              |      60%      |     Low

The gap between coverage and mutation score reveals test superficiality.

8. INTERVIEW QUESTIONS
================================================================

Q: What is a "mutant" in mutation testing?
A: A mutant is a modified version of the source code where exactly one
   small change has been made — e.g., + replaced with -, a return value
   changed to null, or a conditional inverted. If your tests detect the
   change (test fails), the mutant is "killed." If tests pass, the mutant
   "survived" — indicating the test isn't verifying that logic.

Q: What is the mutation score and what's a good target?
A: Mutation score = killed mutations / total mutations × 100%. A score
   above 70-80% is generally good. Perfect scores (100%) are rarely
   necessary and can be counterproductive (over-specifying behavior).
   Focus on improving scores for critical business logic classes.

Q: How is mutation testing different from code coverage?
A: Coverage tells you which code was executed. Mutation testing tells you
   whether your tests would CATCH bugs. 100% code coverage is achievable
   with tests that have no assertions. Mutation testing requires meaningful
   assertions — if a mutation survives, you need better tests.

Q: Why is mutation testing slow and how do you manage this?
A: PIT creates hundreds/thousands of mutants and runs the entire test
   suite against each. This takes 3-10x longer than normal tests. Manage
   by: (1) targeting only production code (exclude configs/DTOs), (2) running
   on a schedule (nightly) rather than every PR, (3) using multiple threads
   (-Dthreads=4), (4) excluding slow integration tests.

Q: A method has 100% branch coverage but a mutation score of 45%. What does this mean?
A: Tests exercise all branches but don't meaningfully verify the results.
   For example, tests use assertTrue(result != null) instead of
   assertEquals(expected, result). The tests pass even when the computed
   values are wrong. Fix by adding specific value assertions.
