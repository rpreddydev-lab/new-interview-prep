================================================================
MOCKITO — VERIFY AND INORDER
Complete Interview Preparation Guide
================================================================

1. WHAT IS VERIFICATION IN MOCKITO?
================================================================

Verification checks HOW a mock was interacted with AFTER the fact:
  - Was the method called?
  - How many times was it called?
  - Was it called with the right arguments?
  - Was it called in a specific order?
  - Were there any UNEXPECTED interactions?

Key difference from stubbing:
  STUBBING → sets up WHAT to return (before the call)
  VERIFICATION → checks IF/HOW it was called (after the call)

Basic syntax:
  verify(mockObject).methodName(args);
  verify(mockObject, VerificationMode).methodName(args);

================================================================
2. BASIC VERIFY
================================================================

  @Test
  void shouldCallRepositoryOnce() {
      // Act
      userService.createUser(new User("alice@example.com", "Alice"));
      
      // Assert — verify exactly one call with specific argument
      verify(userRepository).save(any(User.class));
      
      // More specific:
      verify(userRepository).save(argThat(u -> 
          u.getEmail().equals("alice@example.com")
      ));
  }

VERIFYING WITH EXACT ARGUMENT:
  verify(emailService).sendWelcomeEmail("alice@example.com", "Alice");
  
  // With argument matchers (if mixing, all must be matchers):
  verify(emailService).send(eq("alice@example.com"), anyString());

VERIFY RETURNS THE MOCK (chaining available in some cases):
  // Note: verify() returns the mock for syntactic sugar but isn't typically chained

3. VERIFICATION MODES — TIMES, NEVER, AT LEAST, AT MOST
================================================================

TIMES(n) — exact count:
  verify(paymentService, times(1)).charge(any());  // exactly once
  verify(logger,         times(3)).info(anyString());  // exactly 3 times
  
  // times(1) is the DEFAULT — both equivalent:
  verify(repo).findById("user-1");
  verify(repo, times(1)).findById("user-1");

NEVER — method must NOT have been called:
  verify(fraudService, never()).flag(any());
  verify(auditLog, never()).delete(anyString());

AT_LEAST(n):
  verify(retryService, atLeast(1)).attempt(anyString());
  verify(batchProcessor, atLeast(3)).processBatch(any());
  
  // shorthand:
  verify(service, atLeastOnce()).call();  // atLeast(1)

AT_MOST(n):
  verify(cache, atMost(5)).get(anyString());   // no more than 5 times
  verify(rateLimiter, atMost(1)).permit(any()); // at most once

ONLY — method called AND no other methods on that mock:
  verify(paymentRepo, only()).save(any());
  // Fails if ANY other method on paymentRepo was called

FULL EXAMPLE:
  @Test
  void batchProcessorShouldCallAppropriateServicesForEachItem() {
      List<Item> items = List.of(item1, item2, item3);
      
      batchService.processAll(items);
      
      verify(itemProcessor, times(3)).process(any(Item.class));
      verify(itemProcessor).process(item1);
      verify(itemProcessor).process(item2);
      verify(itemProcessor).process(item3);
      
      verify(successLogger, atLeast(1)).logSuccess(anyString());
      verify(failureLogger, never()).logFailure(anyString(), any());
  }

4. VERIFY NO INTERACTIONS
================================================================

verifyNoInteractions(mock):
  Asserts that the mock had absolutely no interactions (no methods called).
  
  @Test
  void cacheHitShouldNotCallDatabase() {
      when(cache.get("user-1")).thenReturn(Optional.of(cachedUser));
      
      userService.getUser("user-1");
      
      // Cache was hit — DB should never be touched
      verifyNoInteractions(userRepository);
  }

verifyNoMoreInteractions(mock):
  After verifying expected calls, assert NO ADDITIONAL calls were made.
  
  @Test
  void placeOrderShouldSaveAndSendEmail() {
      orderService.placeOrder(cart);
      
      // Verify expected interactions
      verify(orderRepository).save(any(Order.class));
      verify(emailService).sendConfirmation(anyString(), any(Order.class));
      
      // Assert nothing else was called
      verifyNoMoreInteractions(orderRepository);
      verifyNoMoreInteractions(emailService);
  }

IGNORING STUBS in verifyNoMoreInteractions:
  // When stubs are configured, verifyNoMoreInteractions counts stubbed calls too.
  // Use ignoreStubs() to exclude them:
  
  @Test
  void shouldNotCallRepositoryWithUnexpectedArgs() {
      when(repo.findById("valid")).thenReturn(Optional.of(user));
      
      service.processIfExists("valid");
      
      verify(repo).findById("valid");
      verifyNoMoreInteractions(ignoreStubs(repo));  // ignores the stubbed findById call
  }

WARNING: verifyNoMoreInteractions() can make tests fragile.
  - If the production code evolves to call one additional method, test breaks
  - Prefer explicit verify() for important interactions, not catching everything
  - Use it only when "no extra calls" is a BUSINESS REQUIREMENT

5. INORDER — ORDERED VERIFICATION
================================================================

InOrder verifies that mocks were called in a SPECIFIC ORDER.

BASIC USAGE:
  @Test
  void transactionShouldBeginThenCommit() {
      service.executeTransaction(data);
      
      InOrder inOrder = inOrder(transactionManager);
      
      inOrder.verify(transactionManager).begin();
      inOrder.verify(transactionManager).execute(data);
      inOrder.verify(transactionManager).commit();
      // If rollback() was called between begin and commit, this test PASSES
      // (inOrder only checks that verified calls happened in order, not exclusively)
  }

INORDER ACROSS MULTIPLE MOCKS:
  @Test
  void auditLogShouldRecordBeforeEmailSent() {
      notificationService.sendWithAudit(user, message);
      
      // Order matters ACROSS mocks:
      InOrder inOrder = inOrder(auditRepository, emailClient);
      
      inOrder.verify(auditRepository).log(any(AuditEntry.class));
      inOrder.verify(emailClient).send(any(EmailRequest.class));
      
      // If emailClient.send() was called BEFORE auditRepository.log(), this fails
  }

INORDER WITH TIMES:
  @Test
  void retryLogicShouldAttemptBeforeLoggingFailure() {
      retryService.executeWithRetry(task);
      
      InOrder inOrder = inOrder(taskExecutor, failureLogger);
      
      inOrder.verify(taskExecutor, times(3)).execute(task);  // retried 3 times
      inOrder.verify(failureLogger).logFinalFailure(task, any(Exception.class));
  }

INORDER WITH NO MORE INTERACTIONS:
  InOrder inOrder = inOrder(mock1, mock2);
  
  inOrder.verify(mock1).firstMethod();
  inOrder.verify(mock2).secondMethod();
  inOrder.verifyNoMoreInteractions();  // No more ordered interactions

6. INTERACTION BETWEEN STUBBING AND VERIFICATION
================================================================

You CAN stub AND verify the same method:

  @Test
  void shouldFetchUserAndLogAccess() {
      when(userRepository.findById("user-1")).thenReturn(Optional.of(user));
      
      userService.getAndLogUser("user-1");
      
      // Both fine:
      verify(userRepository).findById("user-1");  // verification of stubbed call
  }

STRICT_STUBS and verification:
  With STRICT_STUBS (default in MockitoExtension):
  - Stubbed invocations that are also verified are OK
  - Stubbed invocations that are NOT verified cause UnnecessaryStubbingException
  - Unstubbed invocations that are verified — verification passes if they happened

7. VERIFY AT SPECIFIC TIME — timeout() AND after()
================================================================

For asynchronous behavior testing:

timeout(millis) — verify the call happened within specified milliseconds:
  // Asynchronous notification — should arrive within 500ms
  verify(notificationHub, timeout(500)).notify(anyString());
  
  // With times:
  verify(eventBus, timeout(1000).times(3)).publish(any());

after(millis) — wait the full duration, then verify (unlike timeout which passes early):
  verify(asyncService, after(100).never()).doSomething(); // check nothing happened
  verify(asyncService, after(500).atLeastOnce()).processAsync(any());

WARNING:
  - These introduce real time delays into tests
  - Prefer making async code synchronous in tests (e.g., CountDownLatch)
  - Or use Awaitility library for async assertions

8. VERIFY — COMMON PATTERNS
================================================================

PATTERN: Verify order of save then publish
  @Test
  void userCreationShouldSaveThenPublishEvent() {
      userService.createUser(createRequest);
      
      InOrder inOrder = inOrder(userRepository, eventPublisher);
      inOrder.verify(userRepository).save(any(User.class));
      inOrder.verify(eventPublisher).publish(any(UserCreatedEvent.class));
  }

PATTERN: Verify not called when condition not met
  @Test
  void shouldNotSendEmailIfUserOptedOut() {
      User user = User.builder().email("alice@test.com").emailOptOut(true).build();
      when(userRepository.findById("user-1")).thenReturn(Optional.of(user));
      
      orderService.sendOrderConfirmation("user-1", order);
      
      verify(emailService, never()).send(any());
  }

PATTERN: Verifying multiple calls with different args
  @Test
  void auditServiceShouldLogAllOperations() {
      adminService.createUser(user);
      adminService.updateRole(user, "admin");
      adminService.deleteUser(user.getId());
      
      verify(auditService).log(eq("CREATE"), eq(user.getId()), anyString());
      verify(auditService).log(eq("UPDATE_ROLE"), eq(user.getId()), eq("admin"));
      verify(auditService).log(eq("DELETE"), eq(user.getId()), anyString());
      
      verify(auditService, times(3)).log(anyString(), anyString(), anyString());
  }

PATTERN: Verify with custom matcher message
  verify(emailService).send(argThat(email -> {
      assertThat(email.getTo()).isEqualTo("alice@test.com");
      assertThat(email.getSubject()).startsWith("Order Confirmation");
      return true;  // always return true; assertions fail if wrong
  }));
  // Note: exceptions inside argThat cause ArgumentsAreDifferent, not AssertionError

9. VERIFY INTERNALS — HOW MOCKITO TRACKS CALLS
================================================================

Mockito wraps every mock with an InvocationContainer that records:
  - Method name
  - Arguments passed
  - When it was called (call count)

When verify() is called:
  1. Mockito creates a VerificationMode (times/never/atLeast)
  2. Scans InvocationContainer for matching invocations
  3. If count doesn't match VerificationMode → VerificationError thrown

Why order of verify doesn't matter (unless using InOrder):
  verify(repo).findById("user-1");  // checks entire recorded history
  verify(cache).put("user-1", any()); // also checks entire history
  // Both independent checks, no order requirement

10. COMMON MISTAKES
================================================================

MISTAKE 1: Verifying before the method under test runs
  verify(repo).save(any());  // fails — method not called yet!
  service.createUser(request);
  
  CORRECT: Always call method under test BEFORE verify.

MISTAKE 2: Forgetting to use InOrder for ordering
  verify(transactionManager).commit();
  verify(transactionManager).begin();
  // This PASSES even if commit() was called before begin()!
  // Use InOrder if order matters.

MISTAKE 3: Verifying on wrong mock object
  // Using the real service when you meant the mock:
  verify(realService).method();  // VerificationError: not a mock!
  verify(mockService).method();  // correct

MISTAKE 4: Mixing argument matchers incorrectly
  verify(service).call("literal", anyInt());  // fails! Mix requires eq()
  verify(service).call(eq("literal"), anyInt());  // correct

MISTAKE 5: verifyNoMoreInteractions catching expected calls
  verify(repo).findById("user-1");
  verifyNoMoreInteractions(repo);  // passes
  // But if code also calls repo.findAll() internally, this fails!
  // Only use verifyNoMoreInteractions when you truly want to catch ALL extras

11. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between verify() and when() in Mockito?
A: when() is used BEFORE the SUT method call to configure what the mock
   returns (stubbing). verify() is used AFTER to assert the method was
   called with the expected arguments and number of times.

Q: What does verifyNoMoreInteractions() do, and when should you use it?
A: It asserts that no methods on the mock were called beyond what was
   already explicitly verified. Use it sparingly — only when "no extra
   calls" is a real business requirement. It makes tests fragile to
   legitimate production code changes.

Q: What is InOrder and how does it work?
A: InOrder creates an ordered verifier that checks that mocked methods
   were called in a specific sequence. Works across multiple mocks.
   InOrder inOrder = inOrder(mock1, mock2);
   inOrder.verify(mock1).method1();
   inOrder.verify(mock2).method2();

Q: What is the difference between times(1) and the default verify()?
A: No difference — verify(mock).method() uses times(1) implicitly.

Q: How do you verify a method was never called?
A: verify(mock, never()).method(args);
   Or verifyNoInteractions(mock) for the entire mock.

Q: Can you verify both the number of calls and the order?
A: Yes — use InOrder with times():
   inOrder.verify(mock, times(3)).retryMethod();
   inOrder.verify(logger).logFinalError();

Q: What is ignoreStubs() used for?
A: When calling verifyNoMoreInteractions(), Mockito also counts stubbed
   method invocations. ignoreStubs(mock) excludes those stubbed calls
   from the "no more interactions" check.

Q: How do you test asynchronous code with verify?
A: Use verify(mock, timeout(millis)).method(). It waits up to the
   specified time for the invocation to happen. For production code,
   prefer Awaitility or CountDownLatch over timeout() in tests.
