SPRING BOOT TESTING — OVERVIEW
Complete Interview Preparation Guide
================================================================

1. SPRING BOOT TESTING PHILOSOPHY
================================================================

Spring Boot provides a rich testing support stack that lets you:
  - Load the FULL application context (@SpringBootTest)
  - Load SLICE contexts for specific layers only (fast, focused)
  - Replace beans with mocks (@MockBean)
  - Test REST endpoints without running a server (MockMvc)
  - Test REST endpoints WITH a running server (TestRestTemplate / WebTestClient)

THE CORE PRINCIPLE — TEST SLICES:
  Full Context: @SpringBootTest
    → Loads ALL beans, all configuration, all auto-configuration
    → Slow, but tests full integration
    
  Test Slices: @WebMvcTest, @DataJpaTest, @DataMongoTest, etc.
    → Loads ONLY the beans relevant to the slice
    → Much faster, more focused
    → Common dependencies must be mocked with @MockBean

2. DEPENDENCY SETUP
================================================================

spring-boot-starter-test already includes:
  - JUnit 5 (Jupiter)
  - Mockito (mockito-core, mockito-junit-jupiter)
  - AssertJ
  - Hamcrest
  - Spring Test (MockMvc, etc.)
  - JSONPath (jayway)
  - JSONAssert
  - Testcontainers (basic; need specific modules separately)

  <!-- pom.xml — all testing in one line -->
  <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
  </dependency>

3. TESTING ANNOTATIONS OVERVIEW
================================================================

CLASS-LEVEL ANNOTATIONS:

@SpringBootTest
  - Loads the full ApplicationContext
  - Can configure: webEnvironment (NONE, MOCK, RANDOM_PORT, DEFINED_PORT)
  - Use for integration tests

@WebMvcTest(Controller.class)
  - Loads only web layer: Controller, ControllerAdvice, Filters, WebMvcConfigurer
  - Does NOT load Service, Repository, etc. → mock with @MockBean
  - Auto-configures MockMvc

@DataJpaTest
  - Loads only JPA components: @Entity, @Repository, DataSource, JPA config
  - Does NOT load Service, Controller → no @MockBean needed
  - Auto-configures embedded H2 (or Testcontainers)
  - Each test wrapped in @Transactional by default

@DataMongoTest
  - Loads only MongoDB components
  - Uses embedded MongoDB by default

@DataRedisTest
  - Loads only Redis components

@DataR2dbcTest
  - Loads R2DBC components (reactive)

@JsonTest
  - Loads only JSON serialization/deserialization config
  - Auto-configures ObjectMapper, Jackson

@RestClientTest
  - Tests REST clients (@RestClient, RestTemplate)
  - Auto-configures MockRestServiceServer

FIELD-LEVEL ANNOTATIONS:

@MockBean
  - Creates and registers a Mockito mock in the ApplicationContext
  - Replaces any existing bean of that type

@SpyBean
  - Wraps an existing Spring bean as a Mockito spy

@Autowired
  - Standard Spring DI — works in test classes too

@Value
  - Inject properties from test application.properties

4. TEST CONFIGURATION FILES
================================================================

Typical structure for Spring Boot tests:
  src/
    main/
      java/
        com.example.app/
      resources/
        application.yml          ← production config
    test/
      java/
        com.example.app/
          service/
            UserServiceTest.java
          controller/
            UserControllerTest.java
          integration/
            UserIntegrationTest.java
      resources/
        application-test.yml     ← test-specific config overrides

PROPERTY OVERRIDES IN TESTS:
  @SpringBootTest
  @TestPropertySource(properties = {
      "app.feature.flag=true",
      "spring.datasource.url=jdbc:h2:mem:testdb"
  })
  class FeatureFlagTest { ... }
  
  // Or use @DynamicPropertySource for dynamic values (Testcontainers):
  @DynamicPropertySource
  static void setProperties(DynamicPropertyRegistry registry) {
      registry.add("spring.datasource.url", dataSource::getJdbcUrl);
      registry.add("spring.datasource.username", dataSource::getUsername);
  }

5. APPLICATION CONTEXT CACHING
================================================================

Spring Boot TEST caches the ApplicationContext between test classes.

Same context is reused if:
  - Same @SpringBootTest configuration
  - Same @MockBean / @SpyBean declarations
  - Same @TestPropertySource / @ActiveProfiles

Context is INVALIDATED if:
  - @MockBean types differ between test classes
  - @DirtiesContext is used
  - Different application properties

This means: @MockBean slows tests because it requires a new context.
BEST PRACTICE: Consolidate @MockBean usage in a base test class.

  @SpringBootTest
  @ActiveProfiles("test")
  abstract class BaseIntegrationTest {
      @MockBean EmailService emailService;    // shared mock
      @MockBean ExternalPaymentGateway gw;   // shared mock
  }
  
  // All subclasses reuse the SAME cached ApplicationContext!
  class OrderServiceIT extends BaseIntegrationTest { ... }
  class UserServiceIT extends BaseIntegrationTest { ... }

6. @DirtiesContext
================================================================

Forces the ApplicationContext to be closed and recreated.
Use SPARINGLY — very expensive.

  @SpringBootTest
  @DirtiesContext  // context destroyed after this class
  class StatefulServiceTest { ... }
  
  // Fine-grained:
  @DirtiesContext(classMode = ClassMode.AFTER_EACH_TEST_METHOD)
  // → new context for EVERY test method (very expensive, avoid unless necessary)

When to use:
  - Test modifies application-wide state (e.g., static variables, singletons)
  - Test corrupts shared resources
  - Usually a sign of poor design — prefer Testcontainers with transaction rollback

7. TEST LIFECYCLE IN SPRING
================================================================

  @SpringBootTest
  class MyServiceTest {
      
      @Autowired MyService myService;
      @MockBean ExternalService externalService;
      
      @BeforeEach
      void setUp() {
          // Runs BEFORE each test
          // Spring context already initialized
          // MockBean already reset (Mockito resets mocks between tests)
      }
      
      @Test
      void testOne() { ... }
      
      @Test
      void testTwo() { ... }
      // MockBean is automatically reset between testOne and testTwo
  }

TRANSACTIONAL TESTS:
  @DataJpaTest
  @Transactional  // (already applied by @DataJpaTest)
  class UserRepositoryTest {
      // Each test wrapped in a transaction that is ROLLED BACK after the test
      // → data doesn't persist between tests
  }
  
  @SpringBootTest
  @Transactional  // explicitly add for integration tests
  class UserServiceIT {
      // Same rollback behavior
  }
  
  // To COMMIT a transaction in a test (rare):
  @Test
  @Commit
  void testThatMustCommit() { ... }

    feature:
      new-checkout: true

  class CheckoutServiceTest { ... }

CONDITIONAL BEANS IN TESTS:
  @TestConfiguration
  public class TestBeans {
      
      @Bean
      @Profile("test")
      public EmailService testEmailService() {
          return new NoOpEmailService();  // does nothing — no real emails
      }
  }

9. COMMON PATTERNS AND BEST PRACTICES
================================================================

PATTERN: Shared base test class for integration tests
  @SpringBootTest(webEnvironment = RANDOM_PORT)
  @ActiveProfiles("test")
  @Sql(scripts = "/test-data.sql", executionPhase = BEFORE_TEST_METHOD)
  @Sql(scripts = "/cleanup.sql", executionPhase = AFTER_TEST_METHOD)
  public abstract class BaseIT {
      @MockBean EmailService emailService;
      // All ITs share same context — fast!
  }

PATTERN: Builder test data
  static Order testOrder(String customerId) {
      return Order.builder()
          .id(UUID.randomUUID().toString())
          .customerId(customerId)
          .status(OrderStatus.PENDING)
          .total(new BigDecimal("99.99"))
          .build();
  }

ANTI-PATTERN: Loading full context for unit tests
  @SpringBootTest  // ← Don't do this for service unit tests!
  class UserServiceTest {
      @Autowired UserService userService;
  }
  
  // BETTER:
  @ExtendWith(MockitoExtension.class)
  class UserServiceTest {
      @Mock UserRepository userRepository;
      @InjectMocks UserService userService;
  }

10. TEST SLICES QUICK REFERENCE
================================================================

Annotation          | What's loaded                        | MockBean needed for
--------------------|--------------------------------------|--------------------
@SpringBootTest     | Everything                           | Nothing (all real)
@WebMvcTest         | Controller, ControllerAdvice, MVC    | Services, Repos
@DataJpaTest        | Entity, Repository, DataSource, JPA  | Services
@DataMongoTest      | Mongo repos, MongoTemplate           | Services
@JsonTest           | Jackson / ObjectMapper               | Nothing usually
@RestClientTest     | RestTemplate, client beans           | Server (MockServer)
@WebFluxTest        | Router, Handler, WebFilter (reactive)| Services
@DataR2dbcTest      | R2DBC components                     | Services

11. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between @SpringBootTest and @WebMvcTest?
A: @SpringBootTest loads the entire ApplicationContext (all beans).
   @WebMvcTest loads only the web layer (controller, ControllerAdvice,
   filters). It's much faster and focused. Service and repository beans
   must be provided via @MockBean.

Q: What is a test slice in Spring Boot?
A: A test slice annotation (like @WebMvcTest, @DataJpaTest) loads only
   the beans relevant to a specific layer/technology, not the full context.
   This makes tests faster and more focused.

Q: How does @MockBean differ from @Mock?
A: @Mock (Mockito) creates a mock in the test class scope only.
   @MockBean (Spring) adds a mock to the Spring ApplicationContext,
   replacing any existing bean. Required when the SUT is a Spring-managed
   bean that autowires the dependency.

Q: What is ApplicationContext caching and why does it matter?
A: Spring caches and reuses ApplicationContexts between test classes that
   have the same configuration. If each class uses different @MockBean,
   a new context must be created for each — slowing down tests.
   Solution: shared base class with all needed @MockBeans.

Q: What is @DynamicPropertySource and when is it used?
A: Used to register properties dynamically at runtime. Typical use:
   Testcontainers starts a real Docker container (DB, Redis), and
   @DynamicPropertySource registers its connection URL into Spring's
   property system so the application connects to the container.

Q: How does @DataJpaTest handle data isolation between tests?
A: Each test is wrapped in a transaction that is automatically rolled back
   after the test. This prevents data from one test affecting another.

Q: What is @TestConfiguration?
A: A @Configuration class in the test scope that provides test-specific
   beans without being picked up by the production component scan.
   The @SpringBootTest will find it and include it in the test context.
