================================================================
JUNIT 5 ANNOTATIONS — @BeforeEach, @AfterEach, Lifecycle
Complete Interview Preparation Guide
================================================================

1. TEST LIFECYCLE OVERVIEW
================================================================
JUnit 5 defines a precise lifecycle for test execution.
Understanding this lifecycle is critical for writing correct setup/teardown.

DEFAULT LIFECYCLE (PER-METHOD):
  For each @Test method:
    1. New test class instance is created
    2. @BeforeAll methods (static) — only once per class
    3. @BeforeEach methods run
    4. @Test method runs
    5. @AfterEach methods run
    6. Test instance is discarded
  
  After all tests complete:
    7. @AfterAll methods run

PER-CLASS LIFECYCLE:
  @TestInstance(TestInstance.Lifecycle.PER_CLASS)
  - One test class instance for ALL tests
  - @BeforeAll/@AfterAll do NOT need to be static
  - Shared state between tests (use carefully)

================================================================
2. @BeforeEach — Setup Before Every Test
================================================================

DEFINITION:
  Runs before each individual @Test, @ParameterizedTest, 
  @RepeatedTest, or @TestFactory method.

PURPOSE:
  - Initialize objects used in every test
  - Reset state to a known clean starting point
  - Set up mocks, test data, database state

EXAMPLE:
  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      
      @Mock private OrderRepository orderRepository;
      @Mock private EmailService emailService;
      @Mock private InventoryService inventoryService;
      
      private OrderService orderService;
      
      @BeforeEach
      void setUp() {
          // Runs before EACH test
          orderService = new OrderService(orderRepository, emailService, inventoryService);
          
          // Common stub setup (override per-test if needed)
          when(orderRepository.save(any(Order.class)))
              .thenAnswer(invocation -> invocation.getArgument(0));
      }
      
      @Test
      void shouldPlaceOrder() {
          // orderService is freshly created, mocks are clean
          Order order = new Order("customer-1", List.of(item));
          orderService.placeOrder(order);
          verify(emailService).sendConfirmation(any());
      }
      
      @Test
      void shouldCancelOrder() {
          // Another freshly created orderService instance
          // No contamination from previous test
          orderService.cancelOrder("o-123");
          verify(orderRepository).updateStatus("o-123", CANCELLED);
      }
  }

MULTIPLE @BeforeEach METHODS:
  You can have multiple @BeforeEach methods.
  Execution order within the class: not guaranteed (unless @Order is used).
  
  @BeforeEach
  void initDatabase() { ... }
  
  @BeforeEach
  void initMocks() { ... }

INHERITANCE:
  @BeforeEach in parent class runs BEFORE @BeforeEach in child class.
  
  abstract class BaseServiceTest {
      @BeforeEach
      void baseSetup() {
          SecurityContextHolder.clearContext();
      }
  }
  
  class UserServiceTest extends BaseServiceTest {
      @BeforeEach
      void userServiceSetup() {
          // Runs AFTER baseSetup()
          userService = new UserService(mockRepo);
      }
  }

3. @AfterEach — Cleanup After Every Test
================================================================

DEFINITION:
  Runs after each individual test method, even if the test FAILED.

PURPOSE:
  - Release resources (file handles, DB connections)
  - Reset global state (thread locals, security context)
  - Clean up temp files or directories
  - Log test completion

EXAMPLE:
  @AfterEach
  void tearDown() {
      // Always runs, even if test threw an exception
      SecurityContextHolder.clearContext();
      MDC.clear();  // clear logging context
      tempFile.delete();
  }

GUARANTEES:
  - Runs even if @BeforeEach failed (JUnit 5 behavior)
  - Runs even if the @Test method throws an exception
  - Reports failures independently

4. @BeforeAll — Once Before All Tests
================================================================

DEFINITION:
  Runs ONCE before any test in the class is executed.

REQUIREMENTS:
  - Must be static (unless @TestInstance(PER_CLASS) is used)
  - Only ONE class instance is created for the lifecycle

PURPOSE:
  - Expensive one-time setup
  - Starting embedded servers, DBs, containers
  - Loading test data that is shared across all tests

EXAMPLE:
  class DatabaseIntegrationTest {
      
      private static EmbeddedPostgres postgres;
      private static DataSource dataSource;
      
      @BeforeAll
      static void startDatabase() {
          postgres = EmbeddedPostgres.builder()
              .setPort(5432)
              .start();
          
          dataSource = postgres.getPostgresDatabase();
          
          // Run schema migrations once
          Flyway.configure()
              .dataSource(dataSource)
              .load()
              .migrate();
      }
      
      @AfterAll
      static void stopDatabase() {
          if (postgres != null) {
              postgres.close();
          }
      }
      
      @BeforeEach
      void clearData() {
          // Cheap per-test cleanup (delete rows, not restart DB)
          dataSource.getConnection()
              .createStatement()
              .execute("DELETE FROM orders");
      }
  }

WITH @TestInstance(PER_CLASS) — non-static:
  @TestInstance(TestInstance.Lifecycle.PER_CLASS)
  class SharedInstanceTest {
      
      private List<String> sharedState = new ArrayList<>();
      
      @BeforeAll
      void initOnce() {
          // NOT static — works because PER_CLASS lifecycle
          sharedState.add("initialized");
      }
      
      @Test
      void test1() {
          sharedState.add("test1");
          assertEquals(2, sharedState.size());
      }
      
      @Test
      void test2() {
          // DANGER: sharedState already has "initialized" AND "test1"
          // Tests are now dependent on execution order!
          assertEquals(3, sharedState.size()); // might fail if order changes
      }
  }

WARNING with PER_CLASS: 
  Shared state can make tests depend on each other.
  Use PER_CLASS only when setup is too expensive to repeat per test,
  AND you ensure no shared mutable state is modified by tests.

================================================================
5. @AfterAll — Cleanup After All Tests
================================================================

DEFINITION:
  Runs ONCE after ALL tests in the class have completed.
  Must be static (unless @TestInstance(PER_CLASS)).

PURPOSE:
  - Stop embedded servers/DBs
  - Release expensive resources
  - Final cleanup

EXAMPLE:
  @AfterAll
  static void globalCleanup() {
      embeddedKafka.stop();
      wireMockServer.stop();
      redis.close();
  }

6. EXECUTION ORDER — COMPLETE LIFECYCLE ILLUSTRATION
================================================================

class ServiceTest {
    
    @BeforeAll
    static void beforeAll() {
        System.out.println("1. @BeforeAll — runs ONCE");
    }
    
    @BeforeEach
    void beforeEach() {
        System.out.println("2. @BeforeEach — runs before each test");
    }
    
    @Test
    void firstTest() {
        System.out.println("3. @Test — firstTest");
    }
    
    @AfterEach
    void afterEach() {
        System.out.println("4. @AfterEach — runs after each test");
    }
    
    @Test
    void secondTest() {
        System.out.println("3. @Test — secondTest");
    }
    
    @AfterAll
    static void afterAll() {
        System.out.println("5. @AfterAll — runs ONCE after all");
    }
}

Output:
  1. @BeforeAll — runs ONCE
  2. @BeforeEach — runs before each test
  3. @Test — firstTest
  4. @AfterEach — runs after each test
  2. @BeforeEach — runs before each test
  3. @Test — secondTest
  4. @AfterEach — runs after each test
  5. @AfterAll — runs ONCE after all

7. @DisplayName — Human-Readable Test Names
================================================================

Makes test reports more readable, especially for non-technical stakeholders.

  @DisplayName("Order Service — business logic tests")
  class OrderServiceTest {
      
      @Test
      @DisplayName("Should apply 10% discount for gold members")
      void shouldApplyGoldMemberDiscount() { }
      
      @Test
      @DisplayName("Should throw OrderNotFoundException when order ID doesn't exist")
      void shouldThrowExceptionForMissingOrder() { }
      
      @ParameterizedTest(name = "Tier={0}, Input={1}, Expected={2}")
      @CsvSource({"GOLD, 100, 90", "SILVER, 100, 95"})
      void discountTest(String tier, double input, double expected) { }
  }

Without @DisplayName, IDE/reports show: shouldApplyGoldMemberDiscount()
With @DisplayName: "Should apply 10% discount for gold members"

8. @Disabled — Skipping Tests
================================================================

  @Test
  @Disabled("Temporarily disabled — ticket JIRA-456 not resolved")
  void brokenIntegrationTest() { }
  
  @Disabled("All tests in this class are WIP")
  class WorkInProgressTest { }

IMPORTANT: Never leave @Disabled without a reason comment or ticket reference.
Disabled tests with no reason become permanently disabled and forgotten.

9. @Timeout — Time-Bound Tests
================================================================

  @Test
  @Timeout(value = 500, unit = TimeUnit.MILLISECONDS)
  void shouldCompleteWithinTimeout() throws InterruptedException {
      Thread.sleep(400);  // passes — 400ms < 500ms
  }
  
  @Test
  @Timeout(2)  // default unit is SECONDS
  void shouldProcessBatchWithinTwoSeconds() {
      batchService.processBatch(1000_items);
  }

Class-level timeout (applies to all tests in class):
  @Timeout(value = 1, unit = TimeUnit.SECONDS)
  class FastTests {
      @Test void test1() { }
      @Test void test2() { }
      // Each test must complete within 1 second
  }

Difference from assertTimeout():
  @Timeout annotation: test FAILS if it exceeds time (checked after execution)
  assertTimeoutPreemptively(): test is ABORTED immediately when time runs out

10. @RepeatedTest
================================================================

Run the same test N times (useful for flakiness detection, performance):
  
  @RepeatedTest(5)
  void shouldBeIdempotent() {
      String result = service.generateUniqueId();
      assertNotNull(result);
      assertTrue(result.startsWith("ORD-"));
  }
  
  // With custom display name
  @RepeatedTest(value = 3, name = "Run {currentRepetition} of {totalRepetitions}")
  void shouldHandleConcurrentAccess(RepetitionInfo info) {
      System.out.println("Repetition: " + info.getCurrentRepetition());
      // test concurrent access
  }

11. PRACTICAL PATTERNS FOR SETUP/TEARDOWN
================================================================

PATTERN 1: Reset mocks in @BeforeEach
  @BeforeEach
  void resetMocks() {
      Mockito.reset(orderRepository, emailService);
  }

PATTERN 2: Use @MockitoSettings for strict stubs
  @MockitoSettings(strictness = Strictness.STRICT_STUBS)
  // Reports unused stubs as test failures — keeps tests clean

PATTERN 3: Database cleanup with @Sql
  @Sql(scripts = "classpath:clear-data.sql", 
       executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
  @Test
  void testWithCleanDatabase() { }

PATTERN 4: Temp directory with @TempDir
  @TempDir
  Path tempDir;
  
  @Test
  void shouldCreateFileInTempDirectory() throws IOException {
      Path file = tempDir.resolve("test.txt");
      Files.writeString(file, "content");
      assertTrue(Files.exists(file));
  }

PATTERN 5: Shared expensive resource with @BeforeAll + PER_CLASS
  @TestInstance(TestInstance.Lifecycle.PER_CLASS)
  class ExpensiveSetupTest {
      private TestcontainersDB db;
      
      @BeforeAll
      void startDatabase() {
          db = new TestcontainersDB();
          db.start();
      }
      
      @BeforeEach
      void cleanRows() {
          db.truncateTables();  // cheap per-test reset
      }
      
      @AfterAll
      void stopDatabase() {
          db.stop();
      }
  }

12. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between @BeforeEach and @BeforeAll?
A: @BeforeEach runs before every test method. @BeforeAll runs once before
   all tests and must be static (unless PER_CLASS lifecycle is used).

Q: When would you use @BeforeAll vs @BeforeEach?
A: @BeforeAll for expensive one-time setup (starting containers, loading
   static test data). @BeforeEach for resetting state between tests (clean
   mocks, fresh object instances, clear DB rows).

Q: What is @TestInstance(PER_CLASS)?
A: Makes JUnit use ONE instance of the test class for all tests instead
   of creating a new instance per test. Allows @BeforeAll/@AfterAll to
   be non-static. Risk: shared mutable state between tests.

Q: Does @AfterEach run if a test method fails?
A: Yes. Cleanup methods always run regardless of test outcome, ensuring
   resources are properly released even when tests fail.

Q: What is @TempDir?
A: JUnit 5 extension that provides a temporary directory for tests.
   The directory is automatically deleted after the test completes.

Q: How do you skip a test in JUnit 5?
A: @Disabled annotation with an optional reason string.
   For conditional skipping: @EnabledOnOs, @EnabledIfEnvironmentVariable, etc.
