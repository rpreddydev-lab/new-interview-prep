================================================================
PERFORMANCE TESTING — JMETER
Complete Interview Preparation Guide
================================================================

1. WHAT IS JMETER?
================================================================

Apache JMeter is an open-source load testing tool. It simulates concurrent
users sending HTTP (and other protocol) requests and measures performance.

Key Features:
  - GUI for building test plans + command-line for CI/CD
  - Supports HTTP, REST, GraphQL, JDBC, Kafka, FTP, WebSocket
  - Built-in listeners for real-time results
  - Scripting with Groovy/BeanShell
  - Distributed testing (multiple JMeter nodes)

================================================================
2. JMETER TEST PLAN STRUCTURE
================================================================

  Test Plan
  └── Thread Group (simulates virtual users)
      ├── Config Elements
      │   ├── HTTP Request Defaults      (base URL, port)
      │   ├── HTTP Header Manager        (Content-Type, Authorization)
      │   └── CSV Data Set Config        (load test data from file)
      ├── HTTP Samplers                  (individual API calls)
      ├── Timers                         (think time between requests)
      ├── Assertions                     (response validation)
      ├── Pre-Processors                 (before request: set variables)
      ├── Post-Processors                (after request: extract variables)
      └── Listeners                      (results: summary, graphs, trees)

================================================================
3. THREAD GROUP SETTINGS
================================================================

  Thread Group Configuration:
    Number of Threads   — virtual users (VUs)
    Ramp-Up Period      — time to start all threads (seconds)
    Loop Count          — how many times each thread runs (or Forever)
    Duration            — run for N seconds (alternative to Loop Count)
  
  Ramp-Up Example:
    Threads = 100, Ramp-Up = 20s → JMeter adds 5 threads every second
    → Gradual load increase, avoids sudden spike
    
  Hold Load Example (for soak testing):
    Use "Thread Group" with:
      Threads = 50
      Ramp-Up = 30
      Duration = 3600  (1 hour)
      
  Stepped Ramp-Up (Concurrency Thread Group plugin):
    0 → 50 → 100 → 150 → 200 users, stepping every 60 seconds

4. HTTP SAMPLER CONFIGURATION
================================================================

  HTTP Request Sampler:
    Method:      POST
    Server Name: api.example.com
    Port:        443
    Path:        /api/orders
    Protocol:    https
    
    Parameters/Body:
    {
      "customerId": "${customerId}",     // variable from CSV
      "productId": "${productId}",
      "quantity": ${quantity}
    }
  
  HTTP Header Manager:
    Content-Type:  application/json
    Authorization: Bearer ${token}       // extracted from login response

5. RESPONSE ASSERTIONS
================================================================

  // Response Code assertion
  Assertion: Response Code = 200
  
  // JSON assertion (via JSON Extractor + comparison)
  JSON Path:   $.status
  Expected:    SUCCESS
  
  // Response time assertion (SLA enforcement)
  Duration Assertion: Response Time < 500ms
  
  // Text contains assertion
  Contains: "orderId"

6. VARIABLE EXTRACTION (CORRELATION)
================================================================

  Scenario: Login → use token for subsequent requests
  
  Step 1: POST /auth/login
    Response: {"token": "eyJhbGci..."}
  
  Step 2: JSON Extractor (Post-Processor on Step 1)
    Variable Name:   token
    JSON Path:       $.token
    Match No:        1
    
  Step 3: HTTP Header Manager (on subsequent requests)
    Authorization: Bearer ${token}

  CSV Data Set Config:
    Filename:        test-data/users.csv
    Variable Names:  customerId,productId,quantity
    Delimiter:       ,
    Recycle:         true  (loop through file)

7. RUNNING JMETER FROM COMMAND LINE (CI/CD)
================================================================

  # Non-GUI mode (required for performance, NOT GUI for actual tests)
  jmeter -n \
    -t test-plans/order-api-load-test.jmx \
    -l results/results.jtl \
    -e -o results/html-report/ \
    -Jthreads=100 \
    -Jrampup=30 \
    -Jduration=300 \
    -Jhost=staging.api.example.com
  
  # Key flags:
  #   -n            non-GUI mode
  #   -t            test plan file (.jmx)
  #   -l            log results to .jtl file
  #   -e -o         generate HTML report from results
  #   -J            override JMeter properties

  Maven plugin for JMeter:
  <plugin>
      <groupId>com.lazerycode.jmeter</groupId>
      <artifactId>jmeter-maven-plugin</artifactId>
      <version>3.8.0</version>
      <configuration>
          <testFilesDirectory>${project.basedir}/src/test/jmeter</testFilesDirectory>
          <resultsDirectory>${project.build.directory}/jmeter/results</resultsDirectory>
          <generateReports>true</generateReports>
          <errorRateThresholdInPercent>1</errorRateThresholdInPercent>
      </configuration>
  </plugin>

8. IMPORTANT JMETER LISTENERS
================================================================

  View Results Tree         — detailed per-request results (debug only, disabled in load)
  Summary Report            — aggregate stats: #samples, avg, min, max, p90, error%
  Aggregate Report          — like summary but grouped by request label
  Response Time Graph       — latency over time (visual)
  Active Threads Over Time  — thread ramp-up graph
  Throughput Shaper Timer   — control exact TPS rate (constant throughput)

  IMPORTANT: Disable View Results Tree during actual load tests!
  It buffers all response bodies in memory → skews results and can OOM JMeter.

================================================================
9. DISTRIBUTED JMETER TESTING
================================================================

  For very high load (1000+ VUs), use distributed mode:
    1. JMeter Controller (master)     → orchestrates the test
    2. JMeter Agent nodes (slaves)    → each runs a portion of threads
  
  # Start agent on slave machine:
  jmeter-server -Djava.rmi.server.hostname=192.168.1.20
  
  # Run from controller with remote nodes:
  jmeter -n -t test.jmx -R 192.168.1.20,192.168.1.21 -l results.jtl

10. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Thread Group and Concurrency Thread Group?
A: Thread Group starts N threads during the ramp-up period and each runs
   the test plan a fixed number of times or for a fixed duration. Concurrency
   Thread Group (plugin) maintains a target concurrency level — if threads
   finish early, new ones are started to maintain the target VU count.
   Better for realistic sustained load simulations.

Q: Why should you not use the GUI mode for actual load tests?
A: JMeter's GUI mode uses significant resources for rendering the live view.
   This interferes with the load generation — results are skewed. Always
   use -n (non-GUI) mode for real tests, and use listeners like Summary
   Report that don't buffer response bodies.

Q: What is correlation in JMeter?
A: Correlation is extracting dynamic values from responses (like session
   tokens or IDs) and using them in subsequent requests. Without it, tests
   would always send hardcoded values. Use JSON/Regex/XPath extractors as
   post-processors to capture values and reference them with ${varName}.

Q: How do you simulate realistic user think time in JMeter?
A: Use Timers: Constant Timer (fixed delay), Gaussian Random Timer (random
   around a mean), or Uniform Random Timer. Add them as children of the
   sampler or thread group. Think time simulates real users pausing between
   clicks — without it, JMeter sends requests as fast as possible.

Q: How do you enforce SLAs in JMeter?
A: Use Duration Assertions on samplers to fail requests that exceed a
   latency threshold. Set errorRateThresholdInPercent in the Maven plugin
   configuration. Use the Response Time Assertions. Review the Summary
   Report's p90/p99 columns and compare against SLA targets.
