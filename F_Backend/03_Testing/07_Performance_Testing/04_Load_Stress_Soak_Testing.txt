================================================================
PERFORMANCE TESTING — LOAD, STRESS, AND SOAK TESTING
Complete Interview Preparation Guide
================================================================

1. LOAD TESTING
================================================================

Definition:
  Tests the system under EXPECTED production load to verify it meets
  performance requirements.

Goal:
  - Validate SLAs (response time, throughput, error rate)
  - Establish a performance baseline for regression detection
  - Confirm system handles peak day traffic (e.g., Black Friday)

Typical Profile:
  - Ramp up to target load over 5-10 minutes (avoid cold-start skew)
  - Hold steady at target load for 30-60 minutes
  - Ramp down
  
  Gatling:
    rampUsers(200).during(Duration.ofMinutes(10))       // warm up
    constantUsersPerSec(50).during(Duration.ofMinutes(30)) // steady state
  
Example Acceptance Criteria:
  | Metric           | Threshold  |
  |------------------|------------|
  | p95 latency      | < 300ms    |
  | p99 latency      | < 1000ms   |
  | Error rate       | < 0.5%     |
  | Throughput       | >= 200 TPS |

================================================================
2. STRESS TESTING
================================================================

Definition:
  Pushes the system BEYOND normal load to find the breaking point
  and understand failure behavior.

Goals:
  - Find maximum capacity (what's the peak TPS the system can sustain?)
  - Understand failure mode (graceful degradation vs crash)
  - Verify system recovers after overload is removed
  - Test circuit breakers, rate limiters, queue overflow

Typical Profile:
  - Start at normal load
  - Incrementally increase by 20-25% every 5-10 minutes
  - Continue until errors appear or latency spikes unacceptably
  - Then reduce load and observe recovery
  
  Gatling:
    rampUsersPerSec(10).to(500).during(Duration.ofMinutes(30))
  
  JMeter:
    Stepped Thread Group: 0 → 50 → 100 → 200 → 500 users, step every 5 min

What to observe:
  - At what load does error rate exceed 1%? → system capacity
  - Does latency degrade linearly or suddenly spike? → queue saturation point
  - After removing load, does system recover to normal? → elasticity
  - What fails first: app server CPU? DB connections? Memory?

================================================================
3. SOAK TESTING (ENDURANCE TESTING)
================================================================

Definition:
  Runs at NORMAL load for an extended period (hours to days) to detect
  problems that only appear over time.

Goals:
  - Detect memory leaks (heap grows continuously)
  - Find connection pool exhaustion (connections not released)
  - Discover thread leaks (thread count climbs over time)
  - Detect disk space issues (log/temp file accumulation)
  - Validate caching behavior (cache eviction, expiry correctness)

Typical Profile:
  - Ramp up to normal load over 10 minutes
  - Hold at 50-70% of peak load for 4-24 hours
  
  Gatling:
    rampUsers(100).during(Duration.ofMinutes(10))
    constantUsersPerSec(30).during(Duration.ofHours(8))

Memory Leak Indicators:
  ┌─────────────────────────────────────┐
  │ Heap Used (MB)                      │
  │ 800 │                 ▓▓▓▓▓▓▓▓     │  ← leak: heap never drops
  │ 600 │           ▓▓▓▓▓▓             │
  │ 400 │      ▓▓▓▓▓                   │
  │ 200 │ ▓▓▓▓▓                        │
  │   0 └─────────────────────────────  │
  │     1h    2h    4h    6h    8h      │
  └─────────────────────────────────────┘

Healthy heap (with GC cycles):
  ▓ drop ▓ drop ▓ drop (saw-tooth pattern, stable maximum)

Leaking heap:
  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ (continually rising)

================================================================
4. SPIKE TESTING
================================================================

Definition:
  Tests system behavior when load SUDDENLY increases by a large amount
  (e.g., flash sale, viral social media event).

Typical Profile:
  - Normal load for 5 minutes
  - Immediate spike to 5-10x normal load
  - Hold spike for 2-5 minutes
  - Return to normal
  
  Gatling:
    constantUsersPerSec(20).during(Duration.ofMinutes(5))   // baseline
    atOnceUsers(500)                                          // spike
    nothingFor(Duration.ofMinutes(3))                        // hold spike
    constantUsersPerSec(20).during(Duration.ofMinutes(5))   // normal

Questions to answer:
  - Does auto-scaling kick in fast enough? (cloud environments)
  - Are queues/buffers large enough to absorb the burst?
  - Does the system shed load gracefully (429 Too Many Requests)?
  - Does it fully recover after the spike?

================================================================
5. VOLUME TESTING
================================================================

Definition:
  Tests with large amounts of DATA (not concurrent users).

Scenarios:
  - Database with 100M rows vs 10K rows
  - Large file uploads (10GB vs 10MB)
  - Long-running batch jobs with large datasets

Purpose:
  - Detect performance cliffs due to missing indexes
  - Identify N+1 query problems that only appear at scale
  - Validate pagination and streaming for large result sets

================================================================
6. PERFORMANCE BASELINE AND REGRESSION DETECTION
================================================================

Process:
  1. Run load test and record results (e.g., p95 = 180ms, TPS = 250)
  2. This becomes the baseline
  3. On every release, run the same test
  4. Alert if p95 increases by > 20% or TPS drops by > 10%
  
  This catches:
    - New inefficient queries introduced by developers
    - N+1 query regressions
    - Memory allocation increases
    - Thread contention in new synchronization code

7. COMPARISON TABLE
================================================================

| Type     | Load Level     | Duration    | Detects                  |
|----------|----------------|-------------|--------------------------|
| Load     | Expected peak  | 30-60 min   | SLA violations           |
| Stress   | Above peak     | Until fail  | Breaking point           |
| Soak     | Normal         | 4-24 hours  | Leaks, exhaustion        |
| Spike    | Sudden surge   | Minutes     | Elasticity, burst buffer |
| Volume   | Varies         | Varies      | Data scale limits        |

================================================================
8. INTERVIEW QUESTIONS
================================================================

Q: What is the purpose of a ramp-up period in load testing?
A: A ramp-up period gradually increases virtual users instead of hitting
   full load instantly. This avoids an artificial spike that doesn't reflect
   real traffic, allows the JVM to JIT-compile hot paths, and lets you
   observe how the system performs as load increases progressively.

Q: How do you detect a memory leak from a soak test?
A: Monitor heap usage over time via JMX or APM tools. A memory leak shows
   as continuously rising heap that never plateaus — the saw-tooth GC pattern
   is absent. Also look for increasing GC frequency/duration, growing thread
   count, and connection pool exhaustion. Heap dumps before and after help
   identify which objects are accumulating.

Q: What's the difference between stress testing and spike testing?
A: Stress testing gradually increases load beyond capacity to find the
   breaking point and observe graceful degradation. Spike testing introduces
   a sudden, massive burst of load (like a viral event) to test how quickly
   the system absorbs it or sheds load, and whether it recovers.

Q: At what point during your development cycle should performance tests run?
A: Performance tests should run: (1) before initial release to establish
   baselines, (2) on every release or weekly to detect regressions,
   (3) after any significant architecture changes (new caching, DB changes).
   Full soak tests (8h+) run less frequently (monthly or pre-release).
   Micro-benchmarks (JMH) can run on every commit for critical algorithms.
