================================================================
TYPES OF TESTING — Complete Interview Preparation Guide
================================================================

1. OVERVIEW — CLASSIFICATION OF TESTING TYPES
================================================================

Testing can be classified along several dimensions:

  By SCOPE:      Unit → Integration → System → Acceptance
  By KNOWLEDGE:  White Box → Grey Box → Black Box
  By EXECUTION:  Manual → Automated
  By PURPOSE:    Functional vs. Non-Functional

This file covers ALL major testing types you must know for interviews.

================================================================
2. FUNCTIONAL TESTING TYPES
================================================================

These tests verify that the software does what it's SUPPOSED TO DO.

──────────────────────────────────────────────────────────────
A. UNIT TESTING
──────────────────────────────────────────────────────────────
Scope:     Single class/method
Isolation: Complete (mocks for all dependencies)
Speed:     Milliseconds
Tool:      JUnit 5, Mockito

Tests the SMALLEST testable unit of logic.
Written by developers, run continuously.

Example:
  Testing that DiscountService.applyDiscount(100, 10) returns 90.

──────────────────────────────────────────────────────────────
B. INTEGRATION TESTING
──────────────────────────────────────────────────────────────
Scope:     Multiple components / layers
Isolation: Partial (real DB, mocked external services)
Speed:     Seconds to minutes
Tool:      Spring Boot Test, Testcontainers

Tests that components work TOGETHER correctly.

Types of integration:
  1. Big Bang — integrate all components at once and test
  2. Top-Down — test high-level components first, stub lower ones
  3. Bottom-Up — test lower modules first, build up
  4. Incremental — combine top-down and bottom-up

Example:
  Testing that OrderService correctly persists an Order to PostgreSQL
  through the OrderRepository.

──────────────────────────────────────────────────────────────
C. SYSTEM TESTING
──────────────────────────────────────────────────────────────
Scope:     Entire application (deployed)
Isolation: None — the full real system
Speed:     Minutes to hours
Tool:      Selenium, Postman, RestAssured

Tests the complete, integrated system against requirements.
Performed by QA team, not usually developers.

──────────────────────────────────────────────────────────────
D. ACCEPTANCE TESTING (UAT)
──────────────────────────────────────────────────────────────
Scope:     Complete system (business perspective)
Purpose:   Verify the system meets BUSINESS requirements
Speed:     Long-running
Actors:    Business stakeholders, end users

Two types:
  Alpha Testing — done internally by QA/employees
  Beta Testing  — done externally by real end users before release

──────────────────────────────────────────────────────────────
E. END-TO-END (E2E) TESTING
──────────────────────────────────────────────────────────────
Tests complete user workflows across all layers.
UI → API Gateway → Services → DB → response rendered.

Focus on critical user journeys:
  - User registers, logs in
  - User adds item to cart and checks out
  - User resets password

Tool: Selenium, Cypress, Playwright, RestAssured

──────────────────────────────────────────────────────────────
F. API TESTING
──────────────────────────────────────────────────────────────
Tests REST/SOAP/GraphQL APIs directly (no UI).
Verifies request/response format, status codes, error handling.
Faster and more stable than UI E2E tests.

Tools:
  - Postman (manual + automated)
  - RestAssured (Java, fluent API)
  - Karate (DSL for API testing)

Example:
  given()
    .header("Authorization", "Bearer " + token)
    .body(orderPayload)
  .when()
    .post("/api/orders")
  .then()
    .statusCode(201)
    .body("id", notNullValue())
    .body("status", equalTo("PENDING"));

──────────────────────────────────────────────────────────────
G. REGRESSION TESTING
──────────────────────────────────────────────────────────────
Re-running existing tests after code changes to ensure nothing broke.
The core purpose of maintaining an automated test suite.

Full regression: run all tests
Selective regression: run tests related to changed areas
Automated regression: CI/CD runs them on every push

──────────────────────────────────────────────────────────────
H. SMOKE TESTING
──────────────────────────────────────────────────────────────
A quick, superficial test to verify the system starts and
basic functionality works before deeper testing begins.

"Does it smoke?" (like turning on electrical equipment)

In CI/CD:
  Run smoke tests first to fail fast before running full suite.
  Example: Can the application start? Does /health return 200?

──────────────────────────────────────────────────────────────
I. SANITY TESTING
──────────────────────────────────────────────────────────────
Narrow regression test focused on verifying a specific
bug fix or new feature without running the full test suite.

Difference: Smoke = broad and shallow, Sanity = narrow and deep.

──────────────────────────────────────────────────────────────
J. CONTRACT TESTING
──────────────────────────────────────────────────────────────
Verifies that a consumer and provider agree on the API contract.
Used in microservices to prevent integration failures.

Consumer-driven contracts (CDC):
  The consumer defines expected request/response format.
  The provider must fulfill those expectations.

Tool: Pact
  Consumer writes a pact (contract file)
  Provider verifies against published pact

Example flow:
  1. Consumer writes test defining expected API format
  2. Pact generates a contract JSON file
  3. CI publishes contract to Pact Broker
  4. Provider's CI downloads and verifies contract
  5. Both sides know integration works without deploying together

3. NON-FUNCTIONAL TESTING TYPES
================================================================

These tests verify HOW WELL the system performs, not what it does.

──────────────────────────────────────────────────────────────
A. PERFORMANCE TESTING (umbrella term)
──────────────────────────────────────────────────────────────
Encompasses load, stress, soak, and spike testing.

──────────────────────────────────────────────────────────────
B. LOAD TESTING
──────────────────────────────────────────────────────────────
Simulates expected production load to verify system handles it.

Goal: Verify normal and peak-load performance meets SLAs.
Metric: Response time, throughput, error rate under expected load.

Example: "Can our checkout API handle 1000 concurrent users?"

Tools: JMeter, Gatling, k6

──────────────────────────────────────────────────────────────
C. STRESS TESTING
──────────────────────────────────────────────────────────────
Pushes system BEYOND normal limits to find the breaking point.

Goal: Find the failure threshold and how the system behaves on failure.
      Does it crash? Degrade gracefully? Recover?

Metric: At what load does the system fail?

──────────────────────────────────────────────────────────────
D. SOAK / ENDURANCE TESTING
──────────────────────────────────────────────────────────────
Runs the system under expected load for a LONG PERIOD (hours/days).

Goal: Find memory leaks, resource exhaustion, thread leaks.
Metric: Does performance degrade over time?

──────────────────────────────────────────────────────────────
E. SPIKE TESTING
──────────────────────────────────────────────────────────────
Suddenly increases load dramatically and observes behavior.

Goal: Verify system can handle unexpected traffic spikes and recover.
Example: Traffic doubles instantly during a flash sale.

──────────────────────────────────────────────────────────────
F. VOLUME TESTING (Flood Testing)
──────────────────────────────────────────────────────────────
Tests the system with a large VOLUME of data (not concurrent users).

Goal: Does performance degrade when processing millions of records?
Example: Running batch jobs with 10M rows.

──────────────────────────────────────────────────────────────
G. SCALABILITY TESTING
──────────────────────────────────────────────────────────────
Tests the system's ability to scale up or out.

Horizontal scaling: adding more instances
Vertical scaling: adding more resources to one instance

Goal: Verify that doubling resources approximately doubles capacity.

──────────────────────────────────────────────────────────────
H. SECURITY TESTING
──────────────────────────────────────────────────────────────
Verifies the system is protected against known attacks.

Types:
  - Penetration Testing (pen testing): ethical hacking
  - Vulnerability scanning: automated scan for known CVEs
  - SQL injection testing: malicious SQL in input fields
  - XSS testing: cross-site scripting attacks
  - Authentication/Authorization tests: can user access what they shouldn't?

Tools: OWASP ZAP, Burp Suite, SonarQube (SAST), Snyk

──────────────────────────────────────────────────────────────
I. USABILITY TESTING
──────────────────────────────────────────────────────────────
Tests how easy the system is for users to use.
Performed with real users observing their interactions.
Not automatable — requires human judgment.

──────────────────────────────────────────────────────────────
J. ACCESSIBILITY TESTING (A11Y)
──────────────────────────────────────────────────────────────
Verifies the system is usable by people with disabilities.
Standards: WCAG 2.1 (Web Content Accessibility Guidelines)

Tools: axe, Lighthouse, NVDA (screen reader)

──────────────────────────────────────────────────────────────
K. COMPATIBILITY TESTING
──────────────────────────────────────────────────────────────
Tests across different environments:
  - Browser compatibility (Chrome, Firefox, Safari, Edge)
  - OS compatibility (Windows, macOS, Linux)
  - Device compatibility (Desktop, tablet, mobile)
  - Database version compatibility

──────────────────────────────────────────────────────────────
L. RELIABILITY / RESILIENCE TESTING
──────────────────────────────────────────────────────────────
Tests how the system behaves under failures.

Chaos engineering: deliberately inject failures to test resilience.
Tools: Netflix Chaos Monkey, Chaos Toolkit

Example: Kill a database pod randomly and verify the app recovers.

4. SPECIALIZED TESTING TYPES
================================================================

MUTATION TESTING
  Intentionally introduces bugs (mutations) into the code and verifies
  that existing tests CATCH those bugs.
  
  If tests don't fail on a mutation → tests are too weak.
  A mutation that "survives" (tests still pass) reveals a gap.
  
  Tool: PIT (Pitest) for Java
  
  Example mutation: changing > to >= in a condition
  Test suite should fail when this mutation is introduced.

A/B TESTING
  Releases two versions of a feature to different user segments.
  Measures which version performs better (conversion rate, etc.).
  Not a QA activity — a product/business decision tool.

CANARY TESTING
  Releases a new version to a SMALL SUBSET of users first.
  Monitors for errors before full rollout.
  Related to deployment strategies (canary deployment).

SHADOW TESTING
  Routes production traffic to a new version in parallel WITHOUT
  affecting users. Compares responses between old and new.

FEATURE FLAG TESTING
  Testing features that are deployed but hidden behind feature flags.
  Allows testing in production without affecting all users.

5. TESTING BY EXECUTION METHOD
================================================================

MANUAL TESTING
  Human tester executes test cases manually.
  Best for: exploratory, usability, ad-hoc testing.
  Costly, time-consuming, error-prone for repetitive tasks.

AUTOMATED TESTING
  Scripts execute tests automatically.
  Best for: regression, unit, integration, load.
  Requires upfront investment, but saves time over many runs.

When to automate:
  ✅ Tests run frequently
  ✅ Tests are deterministic (same result every time)
  ✅ Tests take too long to run manually
  ❌ Don't automate: one-time tests, exploratory, unstable UIs

SEMI-AUTOMATED / RECORD-PLAYBACK
  Record user actions and replay them.
  Tools: Selenium IDE
  Fragile — UI changes break recordings easily.

6. TESTING BY LEVEL OF KNOWLEDGE
================================================================

WHITE BOX TESTING (Glass Box / Structural)
  Tester knows internal implementation details.
  Tests specific code paths, branches, conditions.
  Metrics: Code coverage, branch coverage, path coverage.
  
  Who: Developers writing unit/integration tests.
  Goal: Maximize code coverage and test all paths.

BLACK BOX TESTING (Behavioral / Specification-Based)
  Tester has NO knowledge of implementation.
  Tests based only on requirements and specifications.
  Inputs → System → Verify outputs.
  
  Who: QA team, business analysts.
  Goal: Validate behavior against requirements.
  
  Techniques:
    - Equivalence Partitioning: group inputs into valid/invalid classes
    - Boundary Value Analysis: test at boundaries (0, 1, MAX-1, MAX)
    - Decision Table Testing: test all combinations of conditions
    - State Transition Testing: test state machine transitions

GREY BOX TESTING
  Partial knowledge of internals.
  Example: knows DB schema, tests through API.
  Combines white and black box approaches.

7. TEST DESIGN TECHNIQUES
================================================================

EQUIVALENCE PARTITIONING
  Divide input data into partitions where all values behave the same.
  Test one value per partition instead of every value.
  
  Example: Age validation (0-17 invalid, 18-120 valid, >120 invalid)
  Test: -1, 15, 18, 100, 121 (one from each partition + boundary)

BOUNDARY VALUE ANALYSIS (BVA)
  Bugs often lurk at the boundaries of valid ranges.
  Test at: min, min+1, max-1, max, min-1 (just outside), max+1 (just outside)
  
  Example: Field accepts 1-50 characters
  Test: 0, 1, 2, 49, 50, 51

DECISION TABLE TESTING
  Test all combinations of conditions and their expected actions.
  
  Example: Discount rules
  | Member? | Coupon? | Order > $100? | Discount |
  |---------|---------|---------------|----------|
  | Yes     | Yes     | Yes           | 25%      |
  | Yes     | Yes     | No            | 20%      |
  | Yes     | No      | Yes           | 10%      |
  | No      | Yes     | Yes           | 15%      |
  ...etc.

STATE TRANSITION TESTING
  Models system as a state machine.
  Test valid transitions, invalid transitions, and edge paths.
  
  Example: Order states:
  PENDING → CONFIRMED → SHIPPED → DELIVERED
                      ↓
                   CANCELLED

PAIRWISE / ALL-PAIRS TESTING
  When testing multiple parameters, test all PAIRS of values rather than
  all combinations. Catches most bugs with fewer test cases.
  
  Tool: PICT (Microsoft), AllPairs

8. INTERVIEW QUESTIONS ON TYPES OF TESTING
================================================================

Q: What is the difference between load testing and stress testing?
A: Load testing verifies behavior under EXPECTED normal and peak load.
   Stress testing pushes BEYOND expected limits to find the breaking point.
   Soak testing runs at normal load for extended periods to find resource leaks.

Q: What is regression testing and why is it important?
A: Running existing tests after code changes to verify nothing broke.
   Important because: changes in one area can unexpectedly break another.
   A comprehensive automated regression suite enables fearless refactoring.

Q: What is exploratory testing?
A: Unscripted testing where the tester simultaneously designs and executes
   tests, exploring the system to find unexpected behaviors.
   Cannot be fully automated — requires human creativity and intuition.

Q: What is acceptance testing?
A: Verifying the system meets business requirements from the stakeholder
   perspective. Often involves actual users (UAT) validating real workflows.

Q: Difference between smoke test and sanity test?
A: Smoke: broad and shallow — quick check that the system builds/starts.
   Sanity: narrow and deep — verifies a specific bug fix or feature works.
   Smoke runs on every deployment; sanity runs after targeted changes.

Q: What is mutation testing?
A: Testing the tests. Introduces artificial bugs (mutations) and checks
   if tests catch them. If tests still pass after a mutation, they're weak.
   PIT (Pitest) is the main Java tool for mutation testing.

Q: What is contract testing and when would you use it?
A: In microservices, consumer and provider agree on an API contract.
   Consumer writes tests defining expected behavior.
   Provider verifies it can fulfill those expectations.
   Prevents integration failures without deploying services together.
   Use with Pact framework.

Q: What is the difference between alpha and beta testing?
A: Alpha: internal testing by employees/QA in a controlled environment.
   Beta: external testing by a subset of real end users before general release.
