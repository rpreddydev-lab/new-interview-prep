================================================================
INTEGRATION TESTING — CONTRACT TESTING WITH PACT
Complete Interview Preparation Guide
================================================================

1. WHAT IS CONTRACT TESTING?
================================================================

Contract testing verifies that two services (consumer + provider) can
communicate correctly WITHOUT deploying both together.

Traditional Integration Test (E2E):
  Consumer App ──► Provider App ──► DB
  Problem: Brittle, slow, requires full environment

Contract Test (Pact):
  Consumer tests → generates a "pact" (contract file)
  Provider tests → verifies the contract against real code
  No need to run both together!

Key Concepts:
  Consumer  — the service that makes HTTP requests
  Provider  — the service that serves HTTP responses
  Pact      — JSON file describing interactions
  Pact Broker — centralized store for pact files (Pactflow or self-hosted)

================================================================
2. CONSUMER-DRIVEN CONTRACT TESTING FLOW
================================================================

  1. Consumer team writes Pact consumer test
       - Defines what requests they make and what response they NEED
       - Test runs against a local mock server (PactMockServer)
       - Generates a pact file: consumer-provider.json
  
  2. Pact file shared (via Pact Broker or Git)
  
  3. Provider team writes Pact provider verification test
       - Pact reads the contract file
       - Replays each interaction against the real Provider code
       - Verifies the provider response matches the consumer's expectations
  
  4. If provider changes its API and breaks the contract → provider test FAILS
       - Provider team is notified before deploying to production

4. CONSUMER PACT TEST
================================================================

  @ExtendWith(PactConsumerTestExt.class)
  @PactTestFor(providerName = "product-service", port = "8080")
  class ProductApiConsumerPactTest {
      
      // Define the contract: what the consumer expects from the provider
      @Pact(consumer = "order-service", provider = "product-service")
      public RequestResponsePact getProductByIdPact(PactDslWithProvider builder) {
          return builder
              .given("product P-1 exists")               // provider state
              .uponReceiving("a request for product P-1") // description
              .path("/api/products/P-1")
              .method("GET")
              .headers("Accept", "application/json")
              .willRespondWith()
              .status(200)
              .headers(Map.of("Content-Type", "application/json"))
              .body(new PactDslJsonBody()
                  .stringValue("id", "P-1")
                  .stringType("name")               // any string value
                  .numberType("price")              // any numeric value
                  .booleanValue("inStock", true)
              )
              .toPact();
      }
      
      @Test
      @PactTestFor(pactMethod = "getProductByIdPact")
      void shouldFetchProductById(MockServer mockServer) {
          // Configure the client to use WireMock's url (the Pact mock server)
          ProductApiClient client = new ProductApiClient(mockServer.getUrl());
          
          Product product = client.getProduct("P-1");
          
          assertNotNull(product);
          assertEquals("P-1", product.getId());
          assertNotNull(product.getName());
          assertTrue(product.getPrice() > 0);
      }
      
      // Define another interaction
      @Pact(consumer = "order-service", provider = "product-service")
      public RequestResponsePact getProductNotFoundPact(PactDslWithProvider builder) {
          return builder
              .given("product P-999 does not exist")
              .uponReceiving("a request for a non-existent product")
              .path("/api/products/P-999")
              .method("GET")
              .willRespondWith()
              .status(404)
              .body(new PactDslJsonBody()
                  .stringType("error")
                  .stringValue("code", "PRODUCT_NOT_FOUND")
              )
              .toPact();
      }
      
      @Test
      @PactTestFor(pactMethod = "getProductNotFoundPact")
      void shouldHandle404WhenProductNotFound(MockServer mockServer) {
          ProductApiClient client = new ProductApiClient(mockServer.getUrl());
          
          assertThrows(ProductNotFoundException.class, () -> client.getProduct("P-999"));
      }
  }

The pact file is generated at: target/pacts/order-service-product-service.json

      }

================================================================

  @Provider("product-service")
  @PactFolder("src/test/pacts")           // local pact files
  @SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
  class ProductServicePactVerificationTest {
      
      @LocalServerPort int port;
      
      @BeforeEach
      void setupPact(PactVerificationContext context) {
          context.setTarget(new HttpTestTarget("localhost", port));
      }
      
      @TestTemplate
      @ExtendWith(PactVerificationInvocationContextProvider.class)
      void verifyPact(PactVerificationContext context) {
          context.verifyInteraction();
      }
      
      // Handle provider states (setup test data)
      @State("product P-1 exists")
      void productP1Exists() {
          // Insert test product into DB (or mock service)
          productRepository.save(new Product("P-1", "Widget", 9.99, true));
      }
      
      @State("product P-999 does not exist")
      void productP999DoesNotExist() {
          // Ensure P-999 is NOT in DB
          productRepository.deleteById("P-999");
      }
  }

7. USING PACT BROKER
================================================================

  # Push pact to Pact Broker (after consumer tests)
  pact publish target/pacts \
    --broker-base-url https://your-broker.pactflow.io \
    --broker-token YOUR_TOKEN \

  # Provider verification with Pact Broker
  @Provider("product-service")

  )
  @SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
  class ProductServicePactBrokerVerificationTest {
      // same @State methods...
  }
  
  # can-i-deploy: check if it's safe to deploy
  pact-broker can-i-deploy \
    --pacticipant product-service \
    --version 2.0.0 \
    --to-environment production \
    --broker-base-url https://your-broker.pactflow.io

8. MATCHING RULES — PactDslJsonBody
================================================================

  new PactDslJsonBody()
      // Exact value match
      .stringValue("status", "ACTIVE")
      
      // Type matching (any string, number, bool, etc.)
      .stringType("name")             // any String
      .numberType("price")            // any Number
      .integerType("quantity")        // any Integer
      .booleanType("inStock")         // any Boolean
      
      // Regex match
      .stringMatcher("email", "[a-z]+@[a-z]+\\.com", "test@example.com")
      
      // UUID
      .uuid("id")                     // matches UUID format
      
      // Date/Time
      .date("createdDate", "yyyy-MM-dd")
      .datetime("updatedAt", "yyyy-MM-dd'T'HH:mm:ss")
      
      // Array with min length
      .minArrayLike("items", 1)       // array with at least 1 element
          .stringType("sku")
          .numberType("qty")
      .closeArray();

9. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between contract testing and integration testing?
A: Integration testing requires both services running simultaneously. Contract
   testing decouples them — the consumer defines what it needs in a "pact"
   file, and the provider verifies independently against that contract. This
   enables faster feedback and catches breaking API changes before deployment.

Q: What is a "provider state" in Pact?
A: Provider states describe the data setup the provider needs to verify an
   interaction. E.g., "product P-1 exists" means the provider's @State method
   must ensure P-1 is in the DB before Pact replays the consumer's request.

Q: What happens if a provider changes their API and breaks a contract?
A: The provider's Pact verification test fails. The CI pipeline for the
   provider blocks the deployment. The provider team is notified to either
   fix the API change or coordinate with the consumer team.

Q: What is a Pact Broker?
A: A centralized server that stores pact files. Consumers publish pacts after
   their tests. Providers fetch pacts for verification. The Broker tracks
   which contract versions are compatible and supports "can-i-deploy" checks.

Q: What are matching rules and why are they important?
A: Matching rules define how Pact compares actual vs expected values.
   Exact match: "status" must be "ACTIVE". Type match: "name" must be a String
   (any value). Without matching rules, tests would be brittle (fail if
   provider returns "Widget Pro" instead of "Widget"). Use type matchers
   for flexible but meaningful contracts.

Q: How does Pact fit into a CI/CD pipeline?
A: 1. Consumer CI: run consumer Pact tests → publish pact to broker
   2. Provider CI: verify pact from broker → publish verification results
   3. Before deploying either service: run `can-i-deploy` to confirm that
      the version to deploy is compatible with deployed versions in the target
      environment.
