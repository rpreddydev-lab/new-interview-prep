INTERVIEW QUESTIONS — CODE QUALITY AND PERFORMANCE TESTING
Complete Interview Preparation Guide

================================================================
CODE QUALITY QUESTIONS
================================================================

Q1: What is code coverage? What types does JaCoCo measure?
A: Code coverage measures how much of the production code is executed
   by the test suite. JaCoCo measures:
   - Instruction coverage: individual bytecode instructions (finest grain)
   - Line coverage: source lines touched
   - Branch coverage: if/switch true/false branches taken
   - Method coverage: methods with at least one executed instruction
   - Class coverage: classes with at least one tested method
   
   Branch coverage is more meaningful than line coverage because it
   detects untested conditions (e.g., null path never tested).

---

Q2: Can you have 100% code coverage and still have bugs?
A: Yes. Coverage only means code was executed, NOT that behavior was
   correctly verified. A test that calls a method but has no assertions
   (e.g., assertNotNull(result)) achieves 100% coverage but doesn't
   verify correctness. Mutation testing (PIT) addresses this by checking
   whether tests actually catch behavioral changes.

---

Q3: How do you fail a build if code coverage drops below 80%?
A: Configure the JaCoCo Maven plugin's check goal:
   <execution>
     <goals><goal>check</goal></goals>
     <configuration>
       <rules>
         <rule>
           <element>BUNDLE</element>
           <limits>
             <limit>
               <counter>LINE</counter>
               <value>COVEREDRATIO</value>
               <minimum>0.80</minimum>
             </limit>
           </limits>
         </rule>
       </rules>
     </configuration>
   </execution>
   Run mvn verify — if coverage < 80%, the build fails.

---

Q4: What is technical debt in SonarQube?
A: Technical debt is the estimated effort (in minutes/hours) to remediate
   all code smells in the project. SonarQube calculates it based on issue
   types and severity. The Maintainability Rating (A–E) is derived from
   the ratio of tech debt to development time. Grade A means debt < 5% of
   total development time. Technical debt grows if code smells accumulate.

---

Q5: What is the difference between a Bug and a Vulnerability in SonarQube?
A: Bug — a defect that will likely cause incorrect behavior at runtime.
   Examples: null pointer dereference, resource leak, broken equals/hashCode.
   
   Vulnerability — a security issue that could be exploited.
   Examples: SQL injection potential, hardcoded credentials, weak cipher.
   
   Security Hotspot — sensitive code requiring manual review to determine
   if it's actually a vulnerability (e.g., using MD5 for non-security use).

---

Q6: What is cyclomatic complexity and why does it matter?
A: Cyclomatic complexity is the number of independent execution paths through
   a method. Each if/else/for/while/case/catch adds 1. A method with no
   branches has complexity 1.
   
   Why it matters: higher complexity = more test cases needed for full
   branch coverage, harder to understand/maintain, higher bug probability.
   Target: <= 10 per method. Above 15 is a strong code smell.
   
   SonarQube uses "cognitive complexity" — a variant that weighs nesting depth.

---

Q7: What is mutation testing and what does a 45% mutation score mean?
A: Mutation testing (PIT) modifies production code (changes + to -, negates
   conditions, removes return values) and checks if tests detect each change.
   Killed = tests caught it; Survived = tests didn't notice.
   Mutation score = killed / total mutations × 100%.
   
   45% mutation score means 55% of code mutations were NOT caught by tests.
   This indicates tests exist but lack meaningful assertions — they cover
   code but don't verify the correct behavior.

---

Q8: How do you suppress a SonarQube rule without disabling it globally?
A: Three approaches:
   1. @SuppressWarnings("java:S1234") — inline annotation with the Sonar rule key
   2. // NOSONAR comment on the specific line — suppresses all rules for that line
   3. Project-level exclusion in sonar.issue.ignore.multicriteria — exclude a rule
      for specific files/packages (e.g., legacy or generated code)
   
   Use sparingly with documented justification. Excessive suppression defeats
   the purpose of static analysis.

---

Q9: What is SpotBugs and what kind of bugs does it detect?
A: SpotBugs analyzes compiled Java bytecode for known bug patterns.
   Key categories:
   - Null dereference (NP_*): calling methods on potentially-null references
   - Resource leaks (OBL_*): not closing streams/connections
   - Broken equals/hashCode (HE_*): equals without hashCode
   - Mutable static fields (MS_*): exposing mutable arrays/collections
   - Synchronization issues (IS_*): inconsistent locking
   - Performance (DM_*): using new Integer() instead of Integer.valueOf()

---

Q10: How does JaCoCo integrate with SonarQube?
A: JaCoCo generates a jacoco.xml report during the test phase. SonarQube
   reads this file during analysis. Configure via:
   sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
   
   Run: mvn verify sonar:sonar
   JaCoCo runs during verify (tests + coverage), then sonar:sonar reads
   the report and uploads coverage data to the SonarQube server.

================================================================
PERFORMANCE TESTING QUESTIONS
================================================================

Q11: What is the difference between load testing and stress testing?
A: Load testing: apply expected production load to verify SLAs are met.
   Goal: confirm normal operation meets requirements.
   
   Stress testing: gradually push beyond capacity to find the breaking point.
   Goal: find max capacity and observe failure mode (graceful degradation?
   crash? auto-recovery?).

---

Q12: What is p99 latency and why is it more meaningful than average?
A: p99 (99th percentile) latency means 99% of requests are faster than this value.
   Average hides outliers — if 99% of requests take 10ms but 1% take 10 seconds,
   the average might look acceptable (e.g., 110ms) while real users experience
   severe slowdowns.
   
   At 1M requests/day: 1% = 10,000 users experiencing 10-second waits.
   Always define SLAs using percentiles (p95, p99), not averages.

---

Q13: What does soak testing reveal that load testing doesn't?
A: Soak testing runs at normal load for hours. It reveals:
   - Memory leaks: heap grows continuously instead of saw-tooth GC pattern
   - Connection pool exhaustion: DB connections not properly released
   - Thread leaks: thread count climbs over time
   - Disk space issues: logs or temp files fill disk
   - Cache pollution: unbounded cache growth
   
   These issues don't appear in short load tests (30-60 min) because they
   take time to manifest.

---

Q14: What is JMH and when would you use it?
A: JMH (Java Microbenchmark Harness) measures performance of individual Java
   methods or algorithms at the microsecond/nanosecond level.
   
   Use JMH when: comparing algorithms (ArrayList vs LinkedList lookup),
   optimizing hot paths (serialization, regex), evaluating API design
   choices (StringBuilder vs String concatenation).
   
   JMeter/Gatling = HTTP-level load testing (milliseconds, end-to-end).
   JMH = method-level micro-benchmarking (nanoseconds, JVM internals).

---

Q15: Why can't you simply use System.currentTimeMillis() for Java benchmarks?
A: JVM optimizations make naïve timing unreliable:
   - JIT compilation: first N invocations are interpreted (slow), then compiled
   - Dead code elimination: JVM might remove code whose result is never used
   - Constant folding: JVM pre-computes constant expressions at compile time
   - Branch prediction: repeated same-branch patterns are CPU-optimized
   
   JMH handles all of these: warmup iterations (JIT optimization before measuring),
   Blackhole (prevents dead code elimination), multiple forks (fresh JVM state),
   statistical rigor (error margins, multiple iterations).

---

Q16: What does @Warmup do in JMH?
A: @Warmup(iterations = 5, time = 1) runs the benchmark method for 5 iterations
   of 1 second each WITHOUT recording measurements. This allows the JVM to:
   - JIT-compile the benchmark method to native code
   - Stabilize CPU cache state
   - Reach steady-state behavior
   
   Measurements taken after warmup reflect production JVM behavior, not
   slow interpreter startup.

---

Q17: How do you set SLA thresholds in Gatling?
A: Use assertions in the setUp() block:
   setUp(scenario.inject(...))
     .protocols(httpProtocol)
     .assertions(
       global().responseTime().percentile(95).lt(500),   // p95 < 500ms
       global().successfulRequests().percent().gte(99.5) // 99.5% success rate
     );
   
   If assertions fail, Gatling exits with non-zero code → CI pipeline fails.
   This enables automated SLA enforcement in CI/CD.

---

Q18: How do you simulate a network error with JMeter?
A: JMeter doesn't natively simulate network errors at the infrastructure level.
   For connection errors and slow responses, use WireMock in the same test
   environment: configure WireMock to return Fault.CONNECTION_RESET or
   withFixedDelay(). Alternatively, use chaos engineering tools (Toxiproxy,
   Chaos Monkey) in integration/staging environments during load tests.

---

Q19: What is the "Constant Throughput Timer" in JMeter?
A: The Constant Throughput Timer paces requests to achieve a target throughput
   (requests per minute) rather than sending as fast as possible. This creates
   more realistic load patterns matching expected TPS.
   
   Without it: JMeter floods the server as fast as possible.
   With it: JMeter paces requests to match your expected TPS (e.g., 600/min = 10/sec).

---

Q20: In your experience, what do you monitor during a load test?
A: Server-side:
   - CPU utilization (spike → CPU-bound; gradual growth → memory leak)
   - Heap memory and GC frequency/duration (JMX, APM tools)
   - Thread pool usage (BLOCKED threads → contention)
   - DB connection pool (exhaustion → long queues)
   - DB slow query log (index misses under load)
   - HTTP error rates (5xx spike → server-side errors)
   
   Client-side (JMeter/Gatling):
   - p95/p99 response time trends (increasing trend → degradation)
   - Throughput (TPS) vs. target
   - Error rate
   
   The goal is to correlate client-side latency with server-side resource usage.
