RESILIENCE PATTERNS OVERVIEW
==============================

What is Resilience?
- The ability of a system to handle failures gracefully and recover quickly
- In microservices: services fail — resilience prevents cascade failures
- Goal: fail fast, degrade gracefully, recover automatically

Why Resilience Patterns?
- In a system of 30 microservices, if each has 99.9% uptime:
  System availability = 0.999^30 = ~97% uptime → 9 days of downtime/year!
- One slow service can exhaust threads in calling service → cascade failure
- Need patterns to isolate, limit, and recover from failures

=== RESILIENCE4J ===

Resilience4j is the standard resilience library for Java/Spring Boot:
- Lightweight, functional — no external dependencies (unlike Hystrix)
- Works with Spring Boot via spring-cloud-starter-circuitbreaker-resilience4j
- Provides: CircuitBreaker, Retry, RateLimiter, Bulkhead, TimeLimiter, Cache
- Hystrix (Netflix) is deprecated — Resilience4j is the successor

Dependencies:
  <dependency>
    <groupId>io.github.resilience4j</groupId>

  </dependency>

=== THE 5 CORE PATTERNS ===

1. CIRCUIT BREAKER
   - Detects repeated failures and opens the circuit to stop calling a failed service
   - States: CLOSED (normal) → OPEN (failures detected) → HALF-OPEN (probe)
   - Prevents cascading failures, gives failing services time to recover

2. RETRY
   - Automatically retries a failed operation N times
   - With exponential backoff and jitter to avoid thundering herd
   - For transient failures (network blip, temporary service unavailability)

3. RATE LIMITER
   - Limits the rate of calls to a service (N calls per period)
   - Protects downstream services from being overwhelmed
   - Also protects your service from upstream hammering

4. BULKHEAD
   - Isolates components so failure in one doesn't affect others
   - Limits concurrent calls or thread pool per downstream service
   - Prevents one slow dependency from exhausting all threads

5. TIME LIMITER
   - Limits how long an operation can take (timeout)
   - Essential for async operations (CompletableFuture, WebClient)
   - Works together with Circuit Breaker

=== COMBINING PATTERNS ===

Recommended order (decorator pattern — outermost first):
  Retry(CircuitBreaker(RateLimiter(TimeLimiter(Bulkhead(function)))))

Execution order (innermost first):
  Bulkhead → TimeLimiter → RateLimiter → CircuitBreaker → Retry

Why this order:
- Bulkhead: check concurrency limit first (fail fast)
- TimeLimiter: wrap actual call with timeout
- RateLimiter: limit call rate
- CircuitBreaker: detect failures, open if needed
- Retry: retry failed attempts (wraps circuit breaker — retry opens circuit faster)

=== FALLBACK PATTERN ===

When all resilience attempts fail, return a fallback:
- Default response ("Service temporarily unavailable")
- Cached data from previous successful call
- Empty result that client can handle gracefully
- Response from alternative source

@CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
public PaymentResult processPayment(PaymentRequest request) {
    return paymentService.process(request);
}

private PaymentResult paymentFallback(PaymentRequest request, Exception ex) {
    log.warn("Payment service unavailable, using fallback", ex);
    return PaymentResult.pending("Service temporarily unavailable");
}

=== RESILIENCE METRICS ===

Resilience4j exposes Micrometer metrics automatically:
- resilience4j.circuitbreaker.state — CLOSED/OPEN/HALF_OPEN
- resilience4j.circuitbreaker.failure.rate
- resilience4j.circuitbreaker.calls (success, failed, not-permitted)
- resilience4j.retry.calls (success-without-retry, success-with-retry, failed)
- resilience4j.bulkhead.available.concurrent.calls
- resilience4j.ratelimiter.available.permissions

Alert on:
- Circuit breaker OPEN state
- High failure rate (> 50%)
- Bulkhead queue full
- Rate limiter rejections

=== KEY INTERVIEW POINTS ===

- Hystrix is deprecated — Resilience4j is the modern Java resilience library
- Circuit breaker prevents cascading failures — doesn't fix the underlying issue
- Retry + exponential backoff + jitter prevents thundering herd on recovery
- Bulkhead isolates failures — one slow service can't take down the whole app
- Always define a fallback — degraded functionality > complete failure
- Test resilience patterns with chaos engineering (kill services intentionally)
