1. CORE KAFKA COMPONENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Apache Kafka (core)
  - Distributed broker: stores and serves event streams
  - Producer API, Consumer API, Streams API, Connect API
  - Admin API: programmatic topic/cluster management
  - Latest version: 3.9.x (as of 2026)

ZooKeeper (legacy, deprecated since 3.7)
  - Distributed coordination service used for cluster metadata
  - Replaced by KRaft (Kafka's built-in Raft consensus)

KRaft (Kafka Raft)
  - Built-in consensus protocol for metadata management
  - No external dependency required
  - Active-active controller quorum (3 or 5 controllers)

2. KAFKA CONNECT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Framework for connecting Kafka to external systems without writing custom code.
  Pre-built connectors for hundreds of systems.

Architecture:
  Source Connector:  External System → Kafka Topic
  Sink Connector:    Kafka Topic → External System

Modes:
  - Standalone: Single process (for dev/testing)
  - Distributed: Scalable, fault-tolerant worker cluster

Popular Source Connectors:
  - Debezium (MySQL, PostgreSQL, MongoDB, Oracle) — CDC
  - JDBC Source Connector — poll-based DB ingestion
  - Kafka Connect S3 Source — read from S3
  - Twitter/X Connector, REST API connectors

Popular Sink Connectors:
  - Kafka Connect S3 Sink — write Kafka data to S3 (in Parquet/JSON/Avro)
  - Elasticsearch Sink — search indexing
  - JDBC Sink — write to databases
  - Snowflake / BigQuery / Redshift Sink — data warehousing
  - MongoDB, Cassandra, Redis sinks

Key concepts:
  - Task: Unit of work within a connector (can be parallelized)
  - Worker: JVM process running connector tasks
  - Converter: Transforms data format (JSON, Avro, Protobuf)
  - Transforms (SMT — Single Message Transforms): Modify messages in-flight
    e.g., ExtractField, ReplaceField, InsertField, MaskField, TimestampConverter

Configuration example (JDBC Source):
  {
    "name": "jdbc-orders-source",
    "config": {
      "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
      "connection.url": "jdbc:postgresql://localhost:5432/mydb",
      "table.whitelist": "orders",
      "mode": "timestamp",
      "timestamp.column.name": "updated_at",
      "topic.prefix": "postgres-"
    }
  }

3. KAFKA STREAMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Java library for building real-time stream processing applications that
  read from and write to Kafka. No separate cluster needed.

Key features:
  - Embedded in your application (just a library dependency)
  - Stateful processing with local state stores (RocksDB)
  - Windowing (tumbling, hopping, session, sliding)
  - Exactly-once semantics (EOS)
  - Interactive queries (query state stores from outside the app)
  - KStream: event-by-event processing (append log semantics)
  - KTable: changelog / materialized view semantics
  - GlobalKTable: broadcast table replicated to all tasks

Example use cases:
  - Real-time aggregation (clicks per user per minute)
  - Joining streams (user events + user profile data)
  - Filtering and routing
  - Anomaly detection with stateful patterns
  - Metrics computation

Maven dependency:
  <dependency>
    <groupId>org.apache.kafka</groupId>
    <artifactId>kafka-streams</artifactId>
    <version>3.9.0</version>
  </dependency>

4. KSQLDB (PREVIOUSLY KSQL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  SQL-based stream processing engine built on Kafka Streams.
  Write SQL queries that run continuously against Kafka topics.

Types of queries:
  - Push queries: Continuously stream results (live, unbounded)
  - Pull queries: Point-in-time lookup against materialized view

Example ksqlDB queries:
  -- Create a stream
  CREATE STREAM orders (
    order_id VARCHAR,
    user_id VARCHAR,
    amount DOUBLE
  ) WITH (KAFKA_TOPIC='orders', VALUE_FORMAT='JSON');

  -- Create a persistent aggregation
  CREATE TABLE user_total_spend AS
  SELECT user_id, SUM(amount) AS total
  FROM orders
  GROUP BY user_id
  EMIT CHANGES;

  -- Push query (live stream)
  SELECT * FROM orders WHERE amount > 1000 EMIT CHANGES;

Deployment:
  - ksqlDB server is a separate JVM process
  - Connects to Kafka cluster
  - Can be clustered for high availability

Confluent Cloud includes ksqlDB as a managed service.

5. CONFLUENT SCHEMA REGISTRY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Centralized service for managing and enforcing schemas for Kafka messages.
  Prevents schema-breaking changes from corrupting downstream consumers.

Supported formats:
  - Apache Avro (most common)
  - Apache Protobuf
  - JSON Schema

How it works:
  1. Producer registers schema → Schema Registry assigns an ID
  2. Producer sends: [magic byte][schema_id (4 bytes)][avro payload]
  3. Consumer fetches schema by ID from registry, deserializes payload

Compatibility modes:
  - BACKWARD: New schema can read data written by old schema (consumers upgrade first)
  - FORWARD: Old schema can read data written by new schema (producers upgrade first)
  - FULL: Both backward and forward compatible (safest)
  - NONE: No compatibility check (dangerous)

Benefits:
  - Schema evolution without breaking producers/consumers
  - Self-documenting message formats
  - Smaller message size (schema not embedded, just schema ID)
  - Compile-time type safety with generated classes

Example (Avro schema):
  {
    "type": "record",
    "name": "Order",
    "fields": [
      {"name": "orderId", "type": "string"},
      {"name": "userId", "type": "string"},
      {"name": "amount", "type": "double"},
      {"name": "status", "type": {"type": "enum", "name": "OrderStatus",
        "symbols": ["PENDING", "PAID", "SHIPPED", "DELIVERED"]}}
    ]
  }

6. APACHE FLINK (Kafka's common stream processor partner)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Separate distributed stream processing framework, often used WITH Kafka
  for large-scale stateful stream processing.

Comparison with Kafka Streams:
  Feature          Kafka Streams            Apache Flink
  ─────────────────────────────────────────────────────
  Deployment       Library (in your app)    Separate cluster
  Kafka dependency Required                 Optional (multiple sources)
  Complexity       Lower                    Higher
  Scalability      Good                     Excellent (true cluster)
  State backends   RocksDB (local)          RocksDB, JVM heap, remote
  Checkpointing    Kafka-based              Distributed snapshots
  SQL support      Limited (ksqlDB)         Flink SQL (production grade)
  ML integration   Limited                  Flink ML libraries

Use Kafka Streams when: App is already Java/JVM, small-medium scale
Use Flink when: Large scale, complex processing, non-Kafka sources

7. MIRRORMAKER 2 (CROSS-CLUSTER REPLICATION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Replicate Kafka topics across clusters (e.g., DC-to-DC, active-passive failover,
  cloud migration).

Features:
  - Replicates topics, consumer group offsets, ACLs
  - Configurable lag between source and target cluster
  - Bidirectional replication possible
  - Built on Kafka Connect framework

Use cases:
  - Multi-datacenter active-passive disaster recovery
  - Cross-cloud replication
  - Aggregation of regional clusters to a central cluster

Confluent's commercial alternative: Cluster Linking (lower latency, bi-directional)

8. CONFLUENT PLATFORM vs APACHE KAFKA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Apache Kafka (open source, free):
  - Core broker, Producer/Consumer/Streams/Connect APIs
  - Community supported

Confluent Platform (commercial, adds):
  - Schema Registry
  - ksqlDB
  - Control Center (GUI for monitoring)
  - Confluent REST Proxy
  - Tiered storage
  - Cluster Linking
  - Role-Based Access Control (RBAC)
  - Audit log

Confluent Cloud (fully managed Kafka):
  - No infrastructure to manage
  - Serverless connectors, ksqlDB, Schema Registry
  - Pay-per-use
  - Used by many startups and enterprises to avoid operational overhead

AWS MSK (Managed Streaming for Apache Kafka):
  - AWS-managed Kafka cluster
  - Integrates with IAM, CloudWatch, VPC
  - No ZooKeeper to manage (MSK handles it)
  - Cheaper than Confluent Cloud for pure Kafka use cases

10. DEBEZIUM — DEEP DIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What it is: Open-source CDC platform built on Kafka Connect
Creator: Red Hat (now part of IBM)

How it works:
  - Reads database transaction logs (not query-based polling)
  - MySQL: Binary Log (binlog)
  - PostgreSQL: Logical Replication (WAL / pgoutput / decoderbufs)
  - MongoDB: Oplog
  - Oracle: LogMiner
  - SQL Server: SQL Server CDC feature

Published event format (envelope):
  {
    "before": { ... old row state ... },  // null for INSERT
    "after":  { ... new row state ... },  // null for DELETE
    "source": { table, db, server, lsn, ts_ms },
    "op":     "c" | "u" | "d" | "r"  // create, update, delete, read (snapshot)
  }

Benefits:
  - No application changes needed
  - Low latency (milliseconds behind the transaction)
  - Full history from initial snapshot
  - Schema evolution awareness

11. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between Kafka Connect and Kafka Streams?
A: Kafka Connect is for integrating Kafka with external systems (databases, S3,
   Elasticsearch) via pre-built connectors. Kafka Streams is a library for
   processing and transforming data WITHIN Kafka (reading topics, processing,
   writing to other topics). Connect = integration; Streams = processing.

Q: What is Schema Registry and why is it important?
A: Schema Registry stores and enforces schemas (Avro/Protobuf/JSON Schema) for
   Kafka messages. It ensures that schema changes are compatible, preventing
   producers from sending data that breaks consumers. It also reduces message
   size (schema ID instead of full schema inline) and enables type-safe codegen.

Q: When would you use Kafka Streams vs Apache Flink?
A: Kafka Streams is a library embedded in your Java app — simpler to deploy,
   no separate cluster. Use it for moderate-scale processing in Kafka-only
   pipelines. Flink is a full distributed cluster for massive-scale, complex
   stateful processing, or when you need multiple data sources (not just Kafka).

Q: What is Debezium and how does it work?
A: Debezium is a CDC tool that reads database transaction logs (MySQL binlog,
   PostgreSQL WAL) and publishes every INSERT/UPDATE/DELETE as a Kafka event.
   It requires no application code changes and captures changes in milliseconds
   after they occur in the database.

Q: What is ksqlDB and when would you use it?
A: ksqlDB lets you write SQL queries that run continuously against Kafka topics.
   Use it when you want stream processing without writing Java code — for
   filtering, aggregating, joining, or enriching Kafka streams using SQL syntax.
   It's ideal for analytics teams or when rapid prototyping is needed.
