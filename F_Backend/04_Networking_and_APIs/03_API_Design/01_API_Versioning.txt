================================================================================
API VERSIONING — IN DEPTH
================================================================================

WHY API VERSIONING?
--------------------
APIs are contracts with consumers. Once published, breaking changes will break
existing clients. Versioning allows you to evolve your API while maintaining
backward compatibility for existing consumers.

WHAT IS A BREAKING CHANGE?
  - Removing or renaming a field in the response
  - Removing or renaming an endpoint
  - Changing the data type of a field
  - Adding a required field to the request
  - Changing the meaning/semantics of a field
  - Changing authentication/authorization behavior
  - Removing a supported HTTP method

WHAT IS NOT A BREAKING CHANGE (Backward-Compatible):
  - Adding new optional fields to response
  - Adding new endpoints
  - Adding new optional request fields
  - Adding new enum values (be careful if clients fail on unknown values)
  - Changing internal implementation without changing contract

1. VERSIONING STRATEGIES
================================================================================

STRATEGY 1: URL PATH VERSIONING (Most Common)
  Include version in the URL path.
  
  https://api.example.com/v1/users
  https://api.example.com/v2/users
  
  PROS:
  ✅ Explicit and visible
  ✅ Easy to route at load balancer / gateway level
  ✅ Easy to test with browsers and curl
  ✅ Can be bookmarked and shared
  ✅ Logs and metrics clearly show which version
  ✅ CDN-friendly (version in URL = different cache key)
  
  CONS:
  ❌ Not "RESTful" — resource URI changes but resource identity doesn't
  ❌ URL proliferation (v1/users, v2/users, etc.)
  
  EXAMPLES: Stripe (/v1/), Twilio (/2010-04-01/), GitHub (/v3/)

STRATEGY 2: QUERY PARAMETER VERSIONING
  Version specified as query parameter.
  
  https://api.example.com/users?version=1
  https://api.example.com/users?api-version=2.0
  
  PROS:
  ✅ URI stays "clean" (same resource URI)
  ✅ Optional; defaults to latest
  
  CONS:
  ❌ Easy to forget or miss
  ❌ Hard to route at gateway level
  ❌ Poor cache behavior (version in query string)
  ❌ Less explicit than URL path
  
  EXAMPLES: AWS APIs (?Version=2022-01-01), Azure (api-version=2024-01-01)

STRATEGY 3: CUSTOM REQUEST HEADER VERSIONING
  Version specified in a custom HTTP header.
  
  Accept-Version: v1
  X-API-Version: 2.0
  API-Version: 1
  
  PROS:
  ✅ Clean URLs
  ✅ Semantically correct (same resource, different version)
  
  CONS:
  ❌ Not visible in URL (hard to share, test, debug)
  ❌ Requires custom header documentation
  ❌ Cannot test directly in browser
  
  EXAMPLES: GitHub (X-GitHub-Media-Type header)

STRATEGY 4: ACCEPT HEADER VERSIONING (Media Type Versioning)
  Use content negotiation through the Accept header.
  
  Accept: application/vnd.example.v1+json
  Accept: application/vnd.example.v2+json
  Accept: application/json;version=2
  
  PROS:
  ✅ Most "RESTful" — leverages HTTP content negotiation
  ✅ URI identifies resource; version identifies representation
  
  CONS:
  ❌ Harder to test and debug
  ❌ Must be explicitly set in client code
  ❌ Complex to implement
  ❌ Breaks caching (Vary: Accept header needed)
  
  EXAMPLES: GitHub API (application/vnd.github.v3+json)

STRATEGY 5: HOSTNAME/SUBDOMAIN VERSIONING
  Version in the subdomain.
  
  https://v1.api.example.com/users
  https://v2.api.example.com/users
  
  PROS:
  ✅ Completely separate services possible
  ✅ Different infrastructure per version
  
  CONS:
  ❌ DNS/TLS cert complexity
  ❌ Overkill for most use cases

2. COMPARISON TABLE
================================================================================

STRATEGY          VISIBILITY  REST PURITY  EASE OF USE  CACHING   ROUTING
---------------   ----------  -----------  -----------  --------  --------
URL Path          HIGH        MODERATE     EASY         GOOD      EASY
Query Parameter   MEDIUM      MODERATE     EASY         POOR      MEDIUM
Custom Header     LOW         MODERATE     MEDIUM       OK        MEDIUM
Accept Header     LOW         HIGH         COMPLEX      POOR      COMPLEX
Subdomain         HIGH        MODERATE     COMPLEX      GOOD      EASY

RECOMMENDATION: URL path versioning for most APIs.
Media type versioning if you're a REST purist building public platform APIs.

3. VERSIONING SEMANTICS
================================================================================

VERSION NUMBER FORMATS:
  Integer: v1, v2, v3         — Simple, most common for APIs
  Date:    2024-01-15          — AWS/Azure style; clear release history
  Semver:  1.2.3               — Rarely for APIs (complex contract)

MAJOR vs MINOR VERSIONING:
  MAJOR version (v1 → v2): Breaking changes
  MINOR version (v1.1):     Additive changes, new features
  PATCH:                     Bug fixes (same contract)
  
  Most REST APIs only version on breaking changes (major only):
    /v1/users  →  /v2/users

4. VERSION LIFECYCLE MANAGEMENT
================================================================================

VERSION STATES:
  CURRENT   : Latest, actively maintained, new clients should use
  DEPRECATED: Older version, still supported but not recommended, scheduled for EOL
  SUNSET    : Retired, returning 410 Gone or 400

DEPRECATION HEADERS (RFC 8594):
  Deprecation: Sun, 01 Jan 2028 00:00:00 GMT
  Sunset:      Mon, 01 Jul 2028 00:00:00 GMT
  Link:        <https://api.example.com/v2/users>; rel="successor-version"

BEST PRACTICES:
  - Announce deprecation 6-12 months before EOL (for public APIs)
  - Send email notifications to registered developers
  - Log requests to deprecated endpoints
  - Return Deprecation header in every response on deprecated versions
  - Provide migration guide

VERSION SUPPORT POLICY EXAMPLES:
  Google APIs: Support for N and N-1 major versions
  Stripe: Support all versions ever shipped (impressive but expensive)
  GitHub: 3 API versions simultaneously

5. SPRING BOOT — IMPLEMENTING API VERSIONING
================================================================================

OPTION 1: URL PATH VERSIONING
  @RestController
  @RequestMapping("/v1/users")
  public class UserControllerV1 {
      @GetMapping
      public List<UserV1Dto> getUsers() { ... }
  }
  
  @RestController
  @RequestMapping("/v2/users")
  public class UserControllerV2 {
      @GetMapping
      public Page<UserV2Dto> getUsers(@RequestParam int page, @RequestParam int size) { ... }
  }

OPTION 2: CONTENT NEGOTIATION (Accept Header)
  @GetMapping(value = "/users", produces = "application/vnd.example.v1+json")
  public UserV1Dto getUserV1() { ... }
  
  @GetMapping(value = "/users", produces = "application/vnd.example.v2+json")
  public UserV2Dto getUserV2() { ... }

OPTION 3: HEADER-BASED IN SPRING
  @GetMapping(value = "/users", headers = "X-API-Version=1")
  public UserV1Dto getUserV1() { ... }
  
  @GetMapping(value = "/users", headers = "X-API-Version=2")
  public UserV2Dto getUserV2() { ... }

OPTION 4: REQUEST MAPPING PARAM
  @GetMapping(value = "/users", params = "version=1")
  public UserV1Dto getUserV1() { ... }

APPROACH WITH SHARED LOGIC (Recommended Pattern):
  
  // Core service with versioned operations
  @Service
  public class UserService {
      public User findById(Long id) { ... }            // Core logic
      public UserV1Dto toV1Dto(User user) { ... }      // V1 mapping
      public UserV2Dto toV2Dto(User user) { ... }      // V2 mapping (new fields)
  }
  
  // V1 Controller
  @RestController
  @RequestMapping("/v1/users")
  public class UserControllerV1 {
      @GetMapping("/{id}")
      public UserV1Dto getUser(@PathVariable Long id) {
          return userService.toV1Dto(userService.findById(id));
      }
  }
  
  // V2 Controller  
  @RestController
  @RequestMapping("/v2/users")
  public class UserControllerV2 {
      @GetMapping("/{id}")
      public UserV2Dto getUser(@PathVariable Long id) {
          return userService.toV2Dto(userService.findById(id));
      }
  }

6. API GATEWAY LEVEL VERSIONING
================================================================================

Routing different versions to different services at gateway level:

Spring Cloud Gateway:
  spring:
    cloud:
      gateway:
        routes:
          - id: users-v1
            uri: lb://user-service-v1
            predicates:
              - Path=/v1/users/**
          
          - id: users-v2
            uri: lb://user-service-v2
            predicates:
              - Path=/v2/users/**

This allows completely separate service deployments per version —
useful for significant architectural changes between versions.

7. EVOLUTION WITHOUT VERSIONING (Robustness Principle)
================================================================================

POSTEL'S LAW: "Be liberal in what you accept, conservative in what you send."

Design for forward and backward compatibility:
  - Additive changes don't need versioning
  - Clients should ignore unknown fields in responses (non-strict deserialization)
  - Client libraries should handle missing fields gracefully

AVOID NEW VERSION IF YOU CAN:
  Adding a new endpoint:              No new version needed ✅
  Adding optional response fields:    No new version needed ✅
  Adding optional request fields:     No new version needed ✅
  Deprecating a field (keep it, add warning): Borderline
  Removing a field:                   NEEDS new version ❌
  Changing field type:                NEEDS new version ❌
  Removing endpoint:                  NEEDS new version ❌

8. INTERVIEW QUESTIONS — API VERSIONING
================================================================================

Q1: What are the different approaches to API versioning?
    URL path (/v1/users), query parameter (?version=1), custom header
    (X-API-Version: 1), Accept header (application/vnd.api.v1+json), subdomain
    (v1.api.example.com). URL path is most common because it's explicit, easy to
    route, test, and debug. Accept header is most REST-purist but complex.

Q2: When should you create a new API version?
    Only for breaking changes: removing/renaming fields, changing field types,
    making optional fields required, removing endpoints, changing semantics.
    Non-breaking changes (adding optional fields, new endpoints) don't need a
    new version — just document them in changelog.

Q3: How do you deprecate an API version?
    Add Deprecation and Sunset response headers. Announce to developers well
    in advance (6-12 months for public APIs). Log requests to deprecated endpoints.
    Provide migration guide. After sunset, return 410 Gone or redirect to new version.

Q4: How do you support multiple API versions simultaneously?
    Separate controllers per version sharing common service layer. OR separate
    microservices per version routed at API gateway level. Keep core business
    logic in shared services; version-specific logic in DTO mappers and controllers.

Q5: What is the Robustness Principle and how does it apply to API versioning?
    "Be conservative in what you send, liberal in what you accept." Clients should
    ignore unknown fields in responses (forward compatibility). Servers should accept
    extra fields in requests. This allows additive API evolution without new versions.
    Jackson's default behavior ignores unknown fields — align with this.
