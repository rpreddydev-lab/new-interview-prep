1. WHAT IS A KAFKA PRODUCER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Kafka producer is a client that publishes (writes) records to Kafka topics.
The producer is responsible for:
  - Choosing which topic and partition to write to
  - Serializing the key and value to bytes
  - Batching messages for efficiency
  - Compressing batches
  - Sending to the appropriate broker (partition leader)
  - Handling retries on failure
  - Managing acknowledgements

2. PRODUCER INTERNALS — SEND FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When producer.send(record) is called:

  1. SERIALIZATION
     - Key → bytes using key.serializer
     - Value → bytes using value.serializer

  2. PARTITIONING
     - Determine target partition using Partitioner
     - hash(key) % numPartitions, or round-robin/sticky if no key

  3. RECORD ACCUMULATOR (in-memory buffer)
     - Message goes into RecordAccumulator (per-partition deque of ProducerBatch)
     - Messages accumulate until batch.size bytes or linger.ms expires
     - buffer.memory limits total buffer size (default 32 MB)
     - If buffer is full: producer blocks (max.block.ms) then throws BufferExhaustedException

  4. SENDER THREAD
     - Background I/O thread reads ready batches from RecordAccumulator
     - Groups batches by broker (leader)
     - Compresses each batch (if compression.type is set)
     - Sends ProduceRequest to broker

  5. BROKER RESPONSE
     - Broker returns RecordMetadata (topic, partition, offset, timestamp) on success
     - On error: retriable errors (LEADER_NOT_AVAILABLE, etc.) → retried automatically
     - Non-retriable errors (INVALID_MESSAGE, etc.) → returned to callback

  6. CALLBACK / FUTURE
     - Async: producer.send(record, callback) — callback invoked with result
     - Sync: producer.send(record).get() — blocks until broker acks

3. PRODUCER RECORD STRUCTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ProducerRecord<K, V> {
  String topic;           // REQUIRED: which topic to write to
  Integer partition;      // OPTIONAL: explicit partition override
  Long timestamp;         // OPTIONAL: event time (defaults to current time)
  K key;                  // OPTIONAL: determines partition (and enables log compaction)
  V value;                // REQUIRED: the payload
  Iterable<Header> headers; // OPTIONAL: metadata (tracing IDs, content type, etc.)
}

Examples:

  // Basic
  ProducerRecord<String, String> record = new ProducerRecord<>("orders", orderId, orderJson);

  // With explicit partition
  ProducerRecord<String, String> record = new ProducerRecord<>("orders", 0, orderId, orderJson);

  // With headers
  ProducerRecord<String, String> record = new ProducerRecord<>("orders", null, orderId, orderJson);
  record.headers().add("X-Correlation-ID", correlationId.getBytes());
  record.headers().add("X-Source-Service", "order-service".getBytes());

4. PRODUCER CONFIGURATION REFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Core configs:
  bootstrap.servers         = "broker1:9092,broker2:9092"
  key.serializer            = org.apache.kafka.common.serialization.StringSerializer
  value.serializer          = org.apache.kafka.common.serialization.StringSerializer
  client.id                 = "my-producer"    (for monitoring/debugging)

Durability / reliability:
  acks                      = all   (0=no ack, 1=leader ack, all=ISR ack)
  retries                   = 2147483647 (Integer.MAX_VALUE — recommended)
  delivery.timeout.ms       = 120000  (total time for delivery including retries)
  max.in.flight.requests    = 5   (concurrent unacked requests per connection)
  enable.idempotence        = true  (exactly-once per partition, no duplicates on retry)

Throughput / batching:
  batch.size                = 16384  (16 KB — max bytes per batch per partition)
  linger.ms                 = 0      (wait time before sending incomplete batch)
  buffer.memory             = 33554432 (32 MB — total producer buffer)
  compression.type          = none   (none | gzip | snappy | lz4 | zstd)
  max.block.ms              = 60000  (how long to block when buffer is full)

Network:
  request.timeout.ms        = 30000  (timeout waiting for broker response)
  send.buffer.bytes         = 131072 (TCP send buffer)
  receive.buffer.bytes      = 32768  (TCP receive buffer)

5. PRODUCER MODES: FIRE-AND-FORGET, SYNC, ASYNC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. FIRE AND FORGET (acks=0 or acks=1 with no callback):
   producer.send(record);
   → No error handling, no guarantee
   → Use for: metrics, non-critical logging
   → Highest throughput

2. SYNCHRONOUS SEND (blocking):
   RecordMetadata metadata = producer.send(record).get();
   → Blocks until broker acks
   → Safe but lowest throughput
   → Use for: low-volume, critical messages

3. ASYNCHRONOUS SEND (recommended for production):
   producer.send(record, (metadata, exception) -> {
     if (exception != null) {
       log.error("Failed to send", exception);
       // handle retry or DLQ
     } else {
       log.info("Sent to {}-{} @ offset {}", 
         metadata.topic(), metadata.partition(), metadata.offset());
     }
   });
   → Non-blocking, handles errors via callback
   → Best balance of throughput and reliability

6. PRODUCER RETRIES AND ORDERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Retries: When should the producer retry?
  Retriable errors (producer retries automatically):
    - LEADER_NOT_AVAILABLE (leader election in progress)
    - NOT_ENOUGH_REPLICAS
    - REQUEST_TIMED_OUT
    - NETWORK_EXCEPTION

  Non-retriable errors (callback receives exception):
    - INVALID_REQUIRED_ACKS
    - MESSAGE_TOO_LARGE
    - OFFSET_METADATA_TOO_LARGE

Retry ordering problem:
  - With retries=5 and max.in.flight.requests=5:
    - Batch 1 sent → fails → in retry queue
    - Batch 2 sent → succeeds
    - Batch 1 retried → succeeds
    → Result: Batch 2 in partition before Batch 1 → OUT OF ORDER!

  Solutions:
    a) max.in.flight.requests.per.connection=1
       → Strict ordering, but hurts throughput
    b) enable.idempotence=true (RECOMMENDED)
       → Sets max.in.flight.requests=5 AND ensures ordering + no duplicates
       → Producer assigns sequence numbers; broker rejects out-of-order duplicates

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does a Kafka producer work internally?
A: The producer serializes the key/value, determines the partition (via key hash
   or round-robin), accumulates messages into batches in an in-memory buffer
   (RecordAccumulator), and a background Sender thread dispatches ready batches
   to broker leaders. Batches are compressed if configured. The producer handles
   retries for retriable errors and invokes callbacks when complete.

Q: What is linger.ms and why would you tune it?
A: linger.ms is how long the producer waits to accumulate messages into a batch
   before sending. Default is 0 (send immediately). Increasing it (e.g., 5-20ms)
   allows larger batches, improving throughput and compression efficiency at the
   cost of slightly higher latency. Good trade-off for high-throughput use cases.

Q: How do you prevent message loss in a Kafka producer?
A: Set acks=all (wait for all ISR replicas), enable.idempotence=true (avoid
   duplicates on retry), retries=Integer.MAX_VALUE (retry indefinitely within
   delivery.timeout.ms), and ensure min.insync.replicas >= 2 on the broker.

Q: What is the difference between batch.size and linger.ms?
A: batch.size is the maximum bytes per batch per partition. linger.ms is the
   maximum wait time before sending an incomplete batch. The batch is sent when
   EITHER limit is reached — whichever comes first (full batch OR time expires).

Q: Can Kafka guarantee message ordering with retries enabled?
A: Not by default. With retries > 0 and max.in.flight > 1, a retry can arrive
   after subsequent batches, causing reordering. The solution is
   enable.idempotence=true, which assigns sequence numbers to each record and
   has the broker reject out-of-order duplicates, ensuring ordering with retries.
