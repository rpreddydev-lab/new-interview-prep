1. KStream — UNBOUNDED EVENT STREAM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KStream represents an UNBOUNDED SEQUENCE of immutable records.
Every record is an independent event. New records are APPENDED, never replace old ones.

  Think: append-only log, event log, activity stream

  Input: order-events topic
    t=1  key="order-1"  value="PLACED"
    t=2  key="order-1"  value="PAYMENT_RECEIVED"
    t=3  key="order-2"  value="PLACED"
    t=4  key="order-1"  value="SHIPPED"

  KStream sees ALL 4 records. Each is an independent event.
  There are TWO events for order-1 at t=1 and t=2 — both are kept.

Creating a KStream:
  StreamsBuilder builder = new StreamsBuilder();
  KStream<String, String> stream = builder.stream("order-events");

Common KStream operations:
  .filter(predicate)            → keep only matching records
  .filterNot(predicate)         → keep non-matching records
  .map((k, v) -> new KeyValue<>(newKey, newValue))   → transform key AND value
  .mapValues(v -> transform(v)) → transform value only (key unchanged)
  .flatMap(...)                 → one-to-many transformation (split one record into many)
  .flatMapValues(...)           → one-to-many on value only
  .peek((k, v) -> log(k, v))   → side-effect without changing the stream
  .branch(predicate1, pred2...) → split stream into multiple sub-streams (Kafka 2.8 deprecated; use split())
  .split().branch(...)          → split stream (3.0+)
  .merge(otherStream)           → combine two streams into one
  .to("output-topic")           → terminal: write to Kafka topic

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. KTable — CHANGELOG STREAM (MATERIALIZED VIEW)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KTable represents the LATEST VALUE PER KEY — like a continuously-updated
database table, materialized from a Kafka topic.

  Think: current state, latest snapshot, aggregation result, reference data

  Input: user-profiles topic
    key="user-1"  value='{"name":"Alice","city":"NYC"}'
    key="user-2"  value='{"name":"Bob","city":"SF"}'
    key="user-1"  value='{"name":"Alice","city":"LA"}'   ← UPDATE, replaces prior

  KTable only keeps the LATEST value per key:
    user-1 → {"name":"Alice","city":"LA"}    (updated)
    user-2 → {"name":"Bob","city":"SF"}

  A record with a null value = TOMBSTONE = DELETE from the table

Creating a KTable:
  KTable<String, String> profiles = builder.table("user-profiles");

Common KTable operations:
  .filter(predicate)       → filter current key-value pairs
  .mapValues(...)          → transform values
  .toStream()              → convert KTable back to a KStream of change events
  .join(otherTable, ...)   → join with another KTable

KTable backing state:
  - Backed by a local RocksDB state store
  - Changes written to a changelog topic for fault tolerance
  - If you close and reopen with same application.id → state restored from changelog

3. KStream vs KTable — COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌─────────────────────────┬──────────────────────────┬───────────────────────────────┐
  │ Aspect                  │ KStream                  │ KTable                        │
  ├─────────────────────────┼──────────────────────────┼───────────────────────────────┤
  │ Model                   │ Event stream             │ Changelog / materialized view │
  │ Semantics per key       │ All records kept         │ Latest record only            │
  │ Record type             │ Insert (append)          │ Upsert (update or insert)     │
  │ Null value              │ Null event               │ TOMBSTONE (delete the key)    │
  │ State store             │ None (stateless ops) /   │ Always backed by state store  │
  │                         │ RocksDB for stateful     │                               │
  │ Typical data            │ Orders, clicks, logs     │ User profiles, product catalog│
  │ Changelog topic         │ Only for stateful ops    │ Yes (the source topic IS the  │
  │                         │ (aggregations, joins)    │ changelog)                    │
  │ toStream()              │ N/A                      │ Converts back to KStream      │
  └─────────────────────────┴──────────────────────────┴───────────────────────────────┘

Intuitive rule:
  - "I care about every event" → KStream
  - "I care about the current state" → KTable

4. GLOBALKTABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GlobalKTable is like KTable but the ENTIRE topic is available on EVERY instance,
regardless of partition assignment.

Regular KTable:
  - Each Streams instance only has data for its assigned partitions
  - KStream-KTable join requires both to be co-partitioned (same # of partitions,
    same partitioning key)

GlobalKTable:
  - ALL instances hold ALL data (broadcasted)
  - Can join a KStream to a GlobalKTable on ANY key — no co-partitioning required
  - Used for: lookup tables, reference data, small dimension tables

Example: Enrich orders with product names

  GlobalKTable<String, String> products = builder.globalTable("products");

  KStream<String, Order> orders = builder.stream("orders");

  // Non-windowed join: for each order, look up product name
  orders.join(
    products,
    (orderKey, order) -> order.getProductId(),  // key extractor (from order → product key)
    (order, product) -> enrich(order, product)   // merger
  ).to("enriched-orders");

  // No co-partitioning needed because GlobalKTable has the full dataset locally

Trade-offs:
  - Higher memory: all partitions loaded locally on every instance
  - Higher bandwidth: every instance reads all partitions on startup
  - Not suitable for very large tables (millions+ records)
  - Best for small, frequently-read reference data (< 1M records)

5. JOINING KStream AND KTable
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KStream-KTable join (lookup enrichment):
  KStream<String, Order> orders = builder.stream("orders");
  KTable<String, Customer> customers = builder.table("customers");

  KStream<String, EnrichedOrder> enriched = orders.join(
    customers,
    (order, customer) -> new EnrichedOrder(order, customer)
  );

  Behavior:
  - For each order record, looks up the CURRENT value in the KTable by key
  - If no matching KTable entry: produces null (inner join) or keeps order (left join)
  - KStream-KTable joins are NOT windowed (KTable always reflects latest state)
  - Requires co-partitioning: same number of partitions AND same partitioner

KStream-KStream join (event correlation within time window):
  KStream<String, Click> clicks = builder.stream("clicks");
  KStream<String, Purchase> purchases = builder.stream("purchases");

  clicks.join(
    purchases,
    (click, purchase) -> correlate(click, purchase),
    JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5))
  ).to("click-purchases");

  // Any click and purchase with the same key within 5 minutes of each other → output

KTable-KTable join (merge two state tables):
  KTable<String, Order> orders = builder.table("orders");
  KTable<String, Payment> payments = builder.table("payments");

  KTable<String, OrderPayment> merged = orders.join(payments,
    (order, payment) -> new OrderPayment(order, payment));
  // Both sides use KTable semantics: latest value per key, updated on any change

6. REPARTITIONING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When you change the key of a record (via .map() or .selectKey()), subsequent
operations that need data co-located by key (joins, aggregations) require
REPARTITIONING — writing through an internal Kafka topic.

  orders.map((orderId, order) -> new KeyValue<>(order.getCustomerId(), order))
       .groupByKey()  // triggers repartition because key changed
       .count()

Auto-repartition:
  - Kafka Streams detects when a key change requires repartition
  - Creates a hidden internal topic: <app-id>-<name>-repartition
  - Records are written to this topic, then re-read by the downstream task
  - Ensures all records with the same new key go to the same partition/task

Manual repartition:
  stream.repartition(Repartitioned.with(keySerde, valueSerde).withNumberOfPartitions(8))
  // Explicitly control partition count and naming

Co-partitioning requirement for joins:
  - KStream-KTable and KStream-KStream joins require BOTH topics to have the
    same number of partitions AND to use the same partitioning logic
  - If not co-partitioned, Kafka Streams will throw a TopologyException at startup
  - Solutions: create topics with matching partition counts, or use repartition()
    before joining, or use GlobalKTable (bypasses co-partitioning requirement)

7. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the fundamental difference between KStream and KTable?
A: KStream is an append-only event stream where every record is an independent
   event — all records are kept. KTable is a changelog stream representing the
   LATEST value per key (like a database table continuously updated). A new record
   with the same key replaces the previous value in a KTable. A null value in a
   KTable is a tombstone (DELETE). Use KStream for event logs (orders, clicks);
   use KTable for current state (user profiles, inventory counts).

Q: What is a GlobalKTable and when would you use it?
A: A GlobalKTable loads the ENTIRE topic across ALL partitions on every Streams
   instance. Unlike a regular KTable (which only has data for its assigned
   partitions), a GlobalKTable enables joining with any key without co-partitioning.
   It's used for small, frequently-accessed lookup/reference tables (product catalog,
   user preferences, configuration). Trade-off: higher memory and startup time since
   every instance must load the full dataset.

Q: What does co-partitioning mean in Kafka Streams?
A: Co-partitioning means two topics have the same number of partitions and use the
   same partitioning logic for their keys. This is required for KStream-KTable and
   KStream-KStream joins because Kafka Streams pairs up partition N of topic A with
   partition N of topic B on the same task. If they're not co-partitioned, records
   with the same key may land on different tasks and never join. Solution: create
   topics with matching partition counts, or use repartition() / GlobalKTable.

Q: When does Kafka Streams trigger an automatic repartition?
A: When you change a record's key (via .map(), .selectKey(), .flatMap()), Kafka
   Streams marks the stream as "repartition needed". The next key-based operation
   (groupByKey, join) triggers the repartition: Streams writes through an auto-
   created internal repartition topic so that downstream tasks receive all records
   with the same key together.

Q: What is a KTable tombstone and what does it mean?
A: A tombstone is a record with a NULL value in a KTable. It signals a DELETE — the
   key is removed from the materialized view. If a topic has key="user-1", value=null,
   the KTable removes user-1 from its state store. This is important for managing
   state size: old keys that are no longer relevant should be tombstoned to prevent
   unbounded state growth.
