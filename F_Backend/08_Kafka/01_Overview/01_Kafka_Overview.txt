1. WHAT IS KAFKA?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Apache Kafka is a distributed, high-throughput, fault-tolerant, publish-subscribe
messaging system originally developed at LinkedIn in 2010. It was open-sourced
in 2011 and graduated to an Apache top-level project in 2012.

Key classification:
  - It is BOTH a message broker AND a distributed streaming platform
  - Think of it as a distributed commit log (ordered, immutable, append-only)
  - Designed to handle TRILLIONS of events per day

Official definition:
  "Kafka is used for building real-time data pipelines and streaming apps.
   It is horizontally scalable, fault-tolerant, and wicked fast."

Timeline:
  2010 — LinkedIn engineers (Jay Kreps, Neha Narkhede, Jun Rao) create Kafka
          to handle activity tracking (page views, clicks, likes) at scale
  2011 — Open-sourced under Apache License
  2012 — Apache Top-Level Project
  2014 — Jay Kreps, Neha Narkhede, Jun Rao found Confluent
  2016 — Kafka Streams introduced (0.10.x)
  2017 — Kafka Connect added; Exactly-once semantics (0.11.x)
  2019 — KIP-500 proposal to remove ZooKeeper dependency
  2021 — KRaft mode introduced (preview) — Apache Kafka 2.8+
  2022 — KRaft mode production-ready in Kafka 3.3+
  2024 — ZooKeeper mode officially deprecated in Kafka 3.7+

3. THE FUNDAMENTAL PROBLEM KAFKA SOLVES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: In a microservices architecture with N source systems and M target
systems, you need N × M integrations — each with its own protocol, format,
and failure handling. This creates a "spaghetti of pipelines."

Traditional approach: Direct point-to-point integration
  - System A → System B (REST/DB call)
  - System A → System C (REST/DB call)
  - System A → System D (REST/DB call)
  ... becomes unmanageable at scale

Kafka solution: Decouple producers from consumers via a central streaming hub
  - Any system PUBLISHES events to Kafka
  - Any system SUBSCRIBES to Kafka topics independently
  - Producers don't know/care about consumers (decoupling)
  - Consumers don't know/care about producers (decoupling)

Result: N + M integrations instead of N × M

4. KAFKA AS A DISTRIBUTED COMMIT LOG
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The core abstraction: Kafka is a persistent, ordered, immutable log

Properties of the commit log:
  1. ORDERED     — Messages within a partition are strictly ordered
  2. IMMUTABLE   — Once written, records cannot be modified
  3. PERSISTENT  — Written to disk (not in-memory queue)
  4. REPLAYABLE  — Consumers can re-read from any offset
  5. DISTRIBUTED — Partitions spread across multiple brokers

Why log-based matters:
  - Traditional queues: message is deleted once consumed
  - Kafka log: message retained for a configurable period (e.g., 7 days)
  - Multiple consumers can read the SAME message at different times
  - This enables event sourcing, audit trails, time-travel debugging

Diagram:
  Offset:   0   1   2   3   4   5   6   7   8   ...
  Partition: [A] [B] [C] [D] [E] [F] [G] [H] [I] →  (append-only)
                             ↑                  ↑
                    Consumer-1 (at 4)   Consumer-2 (at 8)

5. KAFKA vs TRADITIONAL MESSAGE QUEUES (HIGH LEVEL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Feature               Kafka                    Traditional MQ (RabbitMQ/SQS)
─────────────────────────────────────────────────────────────────────────────
Model                 Pub/Sub + Log             Queue (push/pull)
Message retention     Configurable (days/weeks) Deleted after consume
Message ordering      Per-partition guaranteed  Best-effort / per-queue
Consumer model        Pull-based                Push or Pull
Replay/rewind         Yes (by offset)           No (once consumed, gone)
Throughput            Millions msg/sec          Thousands msg/sec
Horizontal scaling    Native (partitions)       Limited
Consumer independence Multiple groups, any time Single consumer per message
Protocol              Custom binary TCP          AMQP, MQTT, HTTP
Use case              Event streaming, logs     Task queues, work dispatch

6. KAFKA'S FOUR CORE APIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. PRODUCER API
   - Allows applications to PUBLISH streams of records to topics
   - Applications: microservices publishing events, CDC tools, log shippers

2. CONSUMER API
   - Allows applications to SUBSCRIBE to topics and process records
   - Applications: analytics engines, notification services, databases

3. STREAMS API (Kafka Streams)
   - Allows applications to act as stream processors
   - Reads from input topics, transforms/aggregates, writes to output topics
   - Built-in library (no separate cluster needed)

4. CONNECT API (Kafka Connect)
   - Reusable connectors for integrating Kafka with external systems
   - Source Connectors: pull data from DBs/APIs → Kafka
   - Sink Connectors: push data from Kafka → DBs/APIs/S3

7. KAFKA PERFORMANCE CHARACTERISTICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka achieves extreme throughput through:

a) SEQUENTIAL DISK I/O
   - Hard drives do sequential reads/writes at ~100-600 MB/s (vs random: ~1-2 MB/s)
   - Kafka writes logs sequentially → disk I/O is as fast as RAM for sequential ops
   - OS page cache exploited for buffering reads/writes

b) ZERO-COPY OPTIMIZATION (sendfile syscall)
   - Traditional I/O: Disk → Kernel Buffer → User Space → Socket Buffer → NIC
   - Zero-copy: Disk → Kernel Buffer → NIC (bypasses user space entirely)
   - Reduces CPU usage and system calls dramatically

c) BATCHING
   - Messages are batched before being sent to brokers
   - Reduces network round-trips and per-message overhead
   - Configurable: batch.size, linger.ms

d) MESSAGE COMPRESSION
   - Entire batches compressed with gzip, snappy, lz4, zstd
   - Lower network bandwidth, faster disk I/O

e) PARTITIONING
   - Distributes load across multiple brokers and CPUs
   - Enables horizontal scaling of both producers and consumers

Real-world numbers:
  - LinkedIn: 7 trillion messages/day (2022)
  - Single Kafka broker: ~1 million messages/second
  - Latency: end-to-end < 10ms (with acks=1), < 5ms with tuning

8. KAFKA GUARANTEES (KEY PROMISES)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Messages produced to a partition are appended in order
2. A consumer group reads a partition by one consumer at a time
3. A topic with N replicas can tolerate N-1 broker failures
4. "At-least-once" by default; "exactly-once" with idempotent/transactional config
5. Messages are stored durably for a configurable retention period

9. WHEN TO USE KAFKA (AND WHEN NOT TO)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE KAFKA WHEN:
  ✓ High-throughput event streaming (millions events/sec)
  ✓ Multiple consumers need to read the same messages
  ✓ Message replay/rewind is required
  ✓ Audit trails / event sourcing / CQRS
  ✓ Decoupling microservices at scale
  ✓ Real-time data pipelines (ETL/ELT)
  ✓ Change Data Capture (CDC)

DON'T USE KAFKA WHEN:
  ✗ Simple task queue with only one consumer (use SQS/RabbitMQ)
  ✗ Request-response pattern needed (use REST/gRPC)
  ✗ Very low message volume with simple routing (operational overhead not worth it)
  ✗ Individual message TTL required (Kafka has topic-level retention only)
  ✗ Complex routing/filtering per message needed (use RabbitMQ exchanges)

10. KEY INTERVIEW QUESTIONS FOR THIS TOPIC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is Kafka and why was it created?
A: Kafka is a distributed streaming platform created at LinkedIn to handle
   high-volume event data (user activity, metrics, logs). It solves the
   N×M integration problem by acting as a central event hub, decoupling
   producers from consumers and enabling replayable, durable message streams.

Q: How does Kafka differ from a traditional message queue?
A: Traditional queues delete messages after consumption; Kafka retains them.
   Traditional queues typically serve one consumer per message; Kafka allows
   any number of consumer groups to read the same data independently.
   Kafka also provides strict ordering per partition and replay capability.

Q: What makes Kafka so fast?
A: Sequential disk I/O (leveraging OS page cache), zero-copy sendfile(),
   batch writes, message compression, and partitioned parallelism.

Q: Is Kafka a database?
A: No, but it has database-like properties. It's a persistent log store with
   configurable retention. It doesn't support queries, but Kafka Streams / ksqlDB
   add SQL-like stream processing on top.

Q: What is the difference between Kafka's Producer API, Consumer API, Streams API, and Connect API?
A: Producer publishes, Consumer reads, Streams processes in real-time within
   Kafka, Connect integrates external systems with Kafka via reusable connectors.
