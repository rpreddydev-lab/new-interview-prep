2. SENDING MESSAGES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pattern 1 — Fire and Forget (acks=0 or no error handling):
  producer.send(new ProducerRecord<>("orders", "order-123", orderJson));
  // No guarantee of delivery, no callback

Pattern 2 — Synchronous (blocking):
  try {
    RecordMetadata metadata = producer.send(
        new ProducerRecord<>("orders", "order-123", orderJson)
    ).get(); // blocks until broker acks
    
    log.info("Sent to topic={} partition={} offset={}",
        metadata.topic(), metadata.partition(), metadata.offset());
  } catch (ExecutionException e) {
    log.error("Failed to send message", e.getCause());
  } catch (InterruptedException e) {
    Thread.currentThread().interrupt();
  }

Pattern 3 — Asynchronous with Callback (RECOMMENDED for production):
  producer.send(
    new ProducerRecord<>("orders", "order-123", orderJson),
    (RecordMetadata metadata, Exception exception) -> {
      if (exception != null) {
        log.error("Failed to produce message for key={}. Error: {}",
            "order-123", exception.getMessage());
        // Consider: send to DLQ, alert, retry with exponential backoff
      } else {
        log.debug("Message produced: topic={} partition={} offset={}",
            metadata.topic(), metadata.partition(), metadata.offset());
      }
    }
  );

  // IMPORTANT: flush or close to ensure buffered messages are sent
  producer.flush(); // blocks until all buffered messages are sent
  // OR: producer.close(); // flushes and then releases resources

record.headers()

4. SERIALIZERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Built-in serializers:
  StringSerializer         → String → byte[] (UTF-8)
  IntegerSerializer        → Integer → byte[4]
  LongSerializer           → Long → byte[8]
  ByteArraySerializer      → byte[] → byte[] (pass-through)
  ByteBufferSerializer     → ByteBuffer → byte[]
  UUIDSerializer           → UUID → byte[] (string representation)

Custom serializer:
  public class OrderSerializer implements Serializer<Order> {
    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public byte[] serialize(String topic, Order data) {
      if (data == null) return null;
      try {
        return objectMapper.writeValueAsBytes(data);
      } catch (JsonProcessingException e) {
        throw new SerializationException("Failed to serialize Order", e);
      }
    }
  }
  // Register: props.put(VALUE_SERIALIZER_CLASS_CONFIG, OrderSerializer.class.getName())

5. PRODUCER TRANSACTION API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Transactional producer ensures ATOMIC writes across multiple topics/partitions.
Required for exactly-once semantics in producer-only scenarios.

Setup:
  props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-producer-1");
  props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
  // enable.idempotence is auto-set to true with transactional.id

  KafkaProducer<String, String> producer = new KafkaProducer<>(props);
  producer.initTransactions(); // registers producer with broker

Usage:
  try {
    producer.beginTransaction();
    
    // Write to multiple topics atomically
    producer.send(new ProducerRecord<>("orders", orderId, orderJson));
    producer.send(new ProducerRecord<>("inventory-updates", productId, updateJson));
    producer.send(new ProducerRecord<>("notifications", userId, notificationJson));
    
    // OPTIONAL: commit consumer offsets transactionally (read-process-write pattern)
    // producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    
    producer.commitTransaction(); // all messages visible atomically
  } catch (ProducerFencedException | OutOfOrderSequenceException e) {
    // Fatal — a newer producer with same transactional.id took over
    producer.close();
    throw e;
  } catch (KafkaException e) {
    producer.abortTransaction(); // none of the messages are visible
    throw e;
  }

transactional.id must be unique per producer instance AND persistent across restarts.
If a new producer starts with the same transactional.id, the old one is "fenced" (killed).

kafka.producer:type=producer-metrics,client-id=<id>
  record-send-rate            → messages/sec being sent
  record-error-rate           → errors/sec (should be 0 in healthy system)
  record-retry-rate           → retries/sec (non-zero means transient issues)
  request-latency-avg         → avg broker round-trip time
  request-latency-max         → max broker round-trip time
  record-queue-time-avg       → avg time in RecordAccumulator buffer
  batch-size-avg              → avg bytes per batch (tune batch.size + linger.ms)
  compression-rate-avg        → avg compression ratio
  buffer-available-bytes      → free bytes in buffer.memory (watch for saturation)

7. COMPLETE PRODUCTION-READY PRODUCER EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Component
public class OrderEventProducer {
  private final KafkaProducer<String, String> producer;
  private static final Logger log = LoggerFactory.getLogger(OrderEventProducer.class);
  private static final String TOPIC = "orders";

  public OrderEventProducer() {
    Properties props = new Properties();
    props.put(BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
    props.put(KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
    props.put(VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
    
    // Reliability settings
    props.put(ACKS_CONFIG, "all");
    props.put(ENABLE_IDEMPOTENCE_CONFIG, "true");
    props.put(RETRIES_CONFIG, Integer.MAX_VALUE);
    props.put(DELIVERY_TIMEOUT_MS_CONFIG, 120_000);
    props.put(MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
    
    // Throughput settings
    props.put(BATCH_SIZE_CONFIG, 32768);         // 32 KB
    props.put(LINGER_MS_CONFIG, 5);              // 5ms batching window
    props.put(COMPRESSION_TYPE_CONFIG, "lz4");   // fast compression
    
    this.producer = new KafkaProducer<>(props);
  }

  public CompletableFuture<RecordMetadata> sendOrder(String orderId, String orderJson) {
    CompletableFuture<RecordMetadata> future = new CompletableFuture<>();
    
    ProducerRecord<String, String> record =
        new ProducerRecord<>(TOPIC, orderId, orderJson);
    
    producer.send(record, (metadata, exception) -> {
      if (exception != null) {
        log.error("Failed to send order {}. Error: {}", orderId, exception.getMessage());
        future.completeExceptionally(exception);
      } else {
        log.debug("Order {} sent to {}-{} @ offset {}",
            orderId, metadata.topic(), metadata.partition(), metadata.offset());
        future.complete(metadata);
      }
    });
    
    return future;
  }

  @PreDestroy
  public void close() {
    log.info("Closing producer...");
    producer.close(Duration.ofSeconds(30));
  }
}

8. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between producer.send().get() and async send?
A: .get() is synchronous — it blocks the calling thread until the broker
   acknowledges. This is safe but serializes sends (slow). Async send with
   a callback is non-blocking — the producer batches and sends in background,
   notifying via callback on success/failure. Async with callbacks is
   recommended for high-throughput production use.

Q: What does producer.flush() do?
A: flush() blocks until all buffered (not yet sent) messages in the RecordAccumulator
   are sent and acknowledged by brokers. It's useful before shutting down or
   at checkpoints to ensure all pending messages are durable. producer.close()
   implicitly calls flush() first.

Q: How do you implement exactly-once in a Kafka producer?
A: Enable idempotent producer (enable.idempotence=true) which prevents duplicates
   during retries by assigning sequence numbers per partition. For atomic
   multi-topic writes, use transactional producer: set transactional.id,
   call initTransactions(), then wrap each write in beginTransaction() /
   commitTransaction() / abortTransaction().

Q: What happens if the RecordAccumulator buffer is full?
A: The producer blocks the calling thread for up to max.block.ms (default 60s).
   If buffer isn't freed within that time, a BufferExhaustedException is thrown.
   This is a back-pressure signal — producers are outpacing the network/broker.
   Fix by tuning buffer.memory, batch.size, linger.ms, or scaling brokers.

Q: Why should you set retries=Integer.MAX_VALUE and use delivery.timeout.ms instead?
A: Kafka recommends not setting retries directly and instead controlling total
   delivery time via delivery.timeout.ms. The broker internally retries for
   the duration of delivery.timeout.ms. Setting retries=MAX_VALUE + delivery.timeout.ms=120s
   means: retry as many times as needed within 120 seconds total. This is
   cleaner than a fixed retry count which ignores how long each retry takes.
