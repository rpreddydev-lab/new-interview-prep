1. THE DUPLICATE MESSAGE PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Without idempotence, retries can cause duplicates:

Scenario:
  1. Producer sends Batch A to leader (offset 100)
  2. Leader writes Batch A to log (offset 100 assigned)
  3. Leader sends ack to producer
  4. Network failure: ack is LOST in transit
  5. Producer doesn't receive ack → considers it a failure
  6. Producer RETRIES → sends Batch A again
  7. Leader writes Batch A AGAIN (offset 101) → DUPLICATE!

This results in: at-least-once delivery (message written at least once, possibly more)

The problem is fundamental to any distributed system:
  - You can't distinguish "message not received" from "ack not received"
  - Without idempotence, you must choose: duplicates (retry) OR loss (no retry)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. HOW IDEMPOTENT PRODUCER WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka's idempotent producer solves the duplicate problem by assigning:
  - PID (Producer ID): Unique ID assigned by broker when producer initializes
  - Sequence Number: Per-partition, monotonically increasing counter per batch

Protocol:
  1. Producer starts → calls InitProducerIdRequest → broker assigns PID=123
  2. Producer sends Batch A: {PID=123, partition=0, sequenceNum=0}
  3. Broker receives → writes to log (sequence 0, offset 100)
  4. Broker records: PID=123, partition=0, lastSeqNum=0
  5. Ack lost → producer retries Batch A with SAME {PID=123, seq=0}
  6. Broker sees: PID=123, seq=0 already exists → DEDUPLICATES → returns success
  7. No duplicate written!

Key guarantee: EXACTLY ONCE per partition per producer (for the producer's lifetime)

Scope of deduplication:
  - Per partition, per PID
  - Broker keeps a in-memory window of the last 5 sequence numbers per PID/partition
  - If the producer crashes and restarts: it gets a NEW PID → dedup history is lost
    (but this is fine because a crash+restart means no in-flight duplicates)

3. ENABLING IDEMPOTENT PRODUCER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");

When enable.idempotence=true is set, Kafka AUTOMATICALLY enforces:
  - acks=all (cannot override to lower value)
  - retries=Integer.MAX_VALUE (retry until delivery.timeout.ms)
  - max.in.flight.requests.per.connection=5 (max for ordering guarantee)

If you try to set conflicting values with enable.idempotence=true:
  e.g., acks=1 AND enable.idempotence=true → ConfigException at startup

Kafka 3.0+ change:
  - enable.idempotence is TRUE BY DEFAULT in Kafka 3.0+
  - Changing to false is possible but not recommended

4. ORDERING GUARANTEE WITH IDEMPOTENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: Without idempotence, with max.in.flight=5 and retries:
  - Batch 1 sent (seq=0) → fails (network error)
  - Batch 2 sent (seq=1) → succeeds (offset 100)
  - Batch 1 retry → succeeds (offset 101)
  → OUT OF ORDER: batch 2 at offset 100, batch 1 at offset 101

With idempotence and max.in.flight.requests=5:
  - Broker tracks sequence numbers
  - If batch 1 (seq=0) arrives AFTER batch 2 (seq=1): broker returns 
    OutOfOrderSequenceException
  - Producer resends in correct order
  - Result: strict ordering within a partition, even with retries

max.in.flight.requests.per.connection with idempotence:
  - Kafka 2.0 and earlier: must be 1 for ordering
  - Kafka 2.1+: up to 5 concurrent in-flight requests with ordering guaranteed
    (Kafka handles reordering with the sequence number protocol)
  - Setting to 1 is still correct but unnecessarily limits throughput

5. IDEMPOTENCE vs TRANSACTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Idempotent producer:
  - Scope: exactly-once per partition per producer session
  - Writes to SINGLE partition atomically
  - PID is NOT persistent across producer restarts
  - Does NOT protect against: writing to multiple partitions/topics atomically

Transactional producer (builds on idempotence):
  - Scope: atomic writes across MULTIPLE partitions/topics
  - Uses transactional.id (persistent across restarts — MUST be unique per app instance)
  - Writes are wrapped in begin/commit/abort transaction
  - Consumers with isolation.level=read_committed only see committed transactions
  - Enables the full "exactly-once" read-process-write pipeline

When to use which:
  - Idempotent only: producing to a single topic, no transactions needed
  - Transactions: atomic multi-topic write OR read-process-write exactly-once

6. PRODUCER FENCING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: With transactional producers, what if two instances run with the same
transactional.id? (e.g., app restart before old instance dies)

Producer Fencing:
  - Each transactional.id has an "epoch" counter on the broker
  - When a new producer calls initTransactions() with the same transactional.id:
    - Broker increments the epoch for that transactional.id
    - Old producer (lower epoch) is FENCED: all its writes are rejected
    - Old producer receives ProducerFencedException on next request

Effect:
  - Ensures only ONE active producer per transactional.id at a time
  - Old "zombie" producer instances are automatically blocked
  - This is the mechanism for safe producer failover in Kafka Streams

ProducerFencedException handling:
  catch (ProducerFencedException e) {
    // Fatal: cannot recover, must create new producer
    producer.close(); // do NOT call abortTransaction
    throw e;
  }

7. PID AND EPOCH INTERNALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PID (Producer ID):
  - Assigned by the broker when InitProducerIdRequest is received
  - For non-transactional idempotent producers: new PID on each restart
  - For transactional producers: PID persisted to the transaction coordinator
    (stored in the __transaction_state topic)

Producer Epoch:
  - Monotonically increasing per transactional.id
  - Incremented on each initTransactions() call
  - Used for producer fencing
  - Combined with PID: (PID, epoch) uniquely identifies a producer instance

Sequence number:
  - Per (PID, partition): starts at 0, increments per batch sent
  - Broker keeps in-memory circular buffer of last 5 sequence numbers per PID+partition
  - Duplicate detection: if seq <= lastKnownSeq → reject (duplicate)
  - Out-of-order detection: if seq > lastKnownSeq + 1 → OutOfOrderSequenceException

9. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is an idempotent producer and why do you need it?
A: An idempotent producer prevents duplicate messages when a producer retries
   after a failed ack. Without it, if an ack is lost in transit, the producer
   retries and the broker writes the message twice. With idempotence enabled,
   the producer stamps each batch with a PID + sequence number. The broker
   deduplicates based on these: if it sees the same (PID, partition, seq) again,
   it discards the duplicate and returns success.

Q: What configs are automatically set when you enable idempotence?
A: enable.idempotence=true automatically enforces: acks=all (strongest durability),
   retries=Integer.MAX_VALUE (retry indefinitely within delivery.timeout.ms),
   and max.in.flight.requests.per.connection=5 (maintains ordering with retries).
   You cannot set acks to a weaker value with idempotence enabled.

Q: What is the difference between idempotent producer and transactional producer?
A: Idempotent producer prevents duplicates for writes to a SINGLE partition per
   producer session — it gets a PID from the broker and uses sequence numbers.
   Transactional producer adds atomic, all-or-nothing writes across MULTIPLE
   topics/partitions. It uses a persistent transactional.id and enables
   read-process-write exactly-once semantics with consumer offset coordination.

Q: What is producer fencing?
A: When a new producer starts with the same transactional.id, the broker
   increments the epoch. Any old producer instance (lower epoch) is fenced —
   its requests are rejected with ProducerFencedException. This ensures only one
   active producer per transactional.id at a time, preventing "zombie" producers
   from creating duplicate writes after a restart or crash.

Q: Can an idempotent producer guarantee exactly-once across multiple topics?
A: No. Idempotent producer only guarantees exactly-once per partition per session.
   For atomic writes across multiple topics/partitions, you need the transactional
   producer API (transactional.id + beginTransaction/commitTransaction).
