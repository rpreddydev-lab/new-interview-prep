================================================================
JWT vs OPAQUE TOKENS
================================================================

Two fundamentally different token strategies. Choosing between them
(or combining them) is a common architecture decision.

================================================================
DEFINITIONS
================================================================

JWT (JSON Web Token) — SELF-CONTAINED TOKEN:
  - Token contains its own data (claims encoded in payload)
  - Can be validated WITHOUT contacting the issuer
  - Structure: header.payload.signature (Base64URL encoded)
  - Example: eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyMTIzIn0.SIGNATURE

OPAQUE TOKEN — REFERENCE TOKEN:
  - Random string with NO embedded meaning
  - Points to data stored server-side at the Authorization Server
  - Must query the AS (introspection endpoint) to get information
  - Example: 8Nfbm3kdvXlwT2a7p9QEzRuK

================================================================
SIDE-BY-SIDE COMPARISON
================================================================

FEATURE                     JWT                         OPAQUE TOKEN
---------------------------------------------------------------------------
Token size                  Large (~500-1000 bytes)     Small (~30-50 bytes)
Self-contained              Yes                         No
Server-side state           None (stateless)            Yes (AS stores data)
Validation method           Local signature check       AS introspection call
Network call to validate    No                          Yes (per request or cached)
Validation speed            Fast                        Slower (network RTT)
AS availability required    No (after key cache)        Yes (for every validation)
Revocation                  Difficult (wait for expiry) Immediate
Payload visibility          Yes (readable by anyone)    No (hidden from bearer)
Token size impact           Large Authorization headers Small headers
Refresh required on role Δ  Yes (claims are stale)     No (AS has current data)
Best for                    Stateless microservices     High revocation needs

================================================================
JWT — ADVANTAGES
================================================================

1. STATELESS VALIDATION:
   Resource server validates by checking the signature with a public key.
   No AS call = no network latency, no AS bottleneck.

2. HORIZONTAL SCALING:
   Any instance of any microservice can validate independently.
   No shared state between services needed.

3. CROSS-DOMAIN USE:
   JWT can be validated by services that don't have a connection to the AS.
   Third-party services can validate your tokens if they have your JWKS.

4. RICH CLAIM SET:
   Embed user info, roles, scopes directly in token.
   Reduces DB lookups in downstream services.

5. STANDARDIZED:
   RFC 7519, OIDC, OAuth2 all built around JWT.
   Universal library support.

================================================================
JWT — DISADVANTAGES
================================================================

1. REVOCATION PROBLEM:
   Once issued, a JWT is valid until expiry.
   If a user is suspended/compromised → token still works for up to 15 min.

2. STALE CLAIMS:
   If user's role changes after token is issued, old claims persist until
   token expires. Refresh token flow is needed to get fresh claims.

3. TOKEN SIZE:
   JWT payload + signature can be 500-1500 bytes.
   Adds overhead to every HTTP request.

4. SENSITIVE DATA RISK:
   Developers often put sensitive data in payload, forgetting it's readable.
   Misconfigured JWTs can leak PII.

5. ALGORITHM COMPLEXITY:
   Multiple algorithms, known attacks (alg:none, RS256→HS256 confusion).
   Requires careful library configuration.

================================================================
OPAQUE TOKEN — ADVANTAGES
================================================================

1. IMMEDIATE REVOCATION:
   AS marks token as revoked → next introspection call returns active:false.
   No need to wait for expiry.

2. HIDDEN METADATA:
   Token is just an opaque string. Bearer can't decode it.
   Useful for privacy or hiding business logic from clients.

3. ALWAYS CURRENT:
   AS looks up current data at introspection time.
   Role changes take effect immediately.

4. SMALL TOKEN SIZE:
   Just a random string (e.g., 32 chars) in the Authorization header.
   Negligible HTTP overhead.

5. NO ALGORITHM COMPLEXITY:
   No crypto decisions. AS stores and retrieves data from DB/cache.

================================================================
OPAQUE TOKEN — DISADVANTAGES
================================================================

1. AS BOTTLENECK:
   Every resource server call requires an AS introspection call.
   AS becomes a critical single point of failure.
   Mitigated by caching introspection responses.

2. NETWORK LATENCY:
   Add ~10-50ms per request (introspection call + token cache lookup).
   Not suitable for very high-throughput, low-latency APIs.

3. TIGHT COUPLING:
   Resource servers depend on AS availability.
   Hard to deploy resource servers independently.

4. CACHE INVALIDATION COMPLEXITY:
   Caching introspection responses improves performance but
   delays revocation taking effect (cache TTL = revocation delay).

================================================================
HYBRID APPROACHES
================================================================

APPROACH 1: PHANTOM TOKEN PATTERN
  Used by: Kong API Gateway, Nginx, Envoy
  
  API Gateway receives opaque token from client:
    Client → [opaque token] → API Gateway
    API Gateway → [introspect opaque token] → AS
    AS returns JWT-like response to Gateway
    Gateway forwards JWT to backend services
    Backend services validate JWT locally

  Benefits:
    - Clients never see JWTs (privacy)
    - Backend services validate locally (fast)
    - Revocation at gateway level (opaque → fast revocation)

APPROACH 2: TOKEN EXCHANGE (RFC 8693)
  External clients use opaque tokens.
  Internal services receive JWTs via token exchange.
  Keeps internal token format internal.

APPROACH 3: SHORT-LIVED JWTs + REFRESH
  Keep JWT TTL very short (5-15 minutes).
  Rely on refresh token flow for session management.
  Acceptable revocation window = access token TTL.

================================================================
WHEN TO USE WHICH
================================================================

USE JWT WHEN:
  ✓ Microservices architecture (stateless validation)
  ✓ Multiple resource servers need to validate independently
  ✓ AS is a separate team/system (can't call for every request)
  ✓ High throughput, low latency API
  ✓ Cross-organizational token sharing
  ✓ Short token TTL acceptable for your revocation needs

USE OPAQUE TOKENS WHEN:
  ✓ Immediate revocation is critical (banking, healthcare)
  ✓ User account suspension must take effect instantly
  ✓ Token metadata must remain private
  ✓ Simple architecture (single AS + few resource servers)
  ✓ Token size matters (e.g., cookies with size limits)
  ✓ Claims may change frequently (roles, permissions)

USE HYBRID WHEN:
  ✓ External clients + internal microservices
  ✓ Need privacy + performance
  ✓ API Gateway can mediate between token types

================================================================
IMPLEMENTATION IN SPRING SECURITY
================================================================

// JWT Resource Server
http.oauth2ResourceServer(oauth2 -> oauth2
    .jwt(jwt -> jwt
        .jwkSetUri("https://auth-server.com/.well-known/jwks.json")
    )
);

// Opaque Token Resource Server
http.oauth2ResourceServer(oauth2 -> oauth2
    .opaqueToken(opaque -> opaque
        .introspectionUri("https://auth-server.com/oauth2/introspect")
        .introspectionClientCredentials("rs-client", "rs-secret")
    )
);

// Custom caching introspector for performance
@Bean
public OpaqueTokenIntrospector introspector() {
    SpringOpaqueTokenIntrospector delegate = new SpringOpaqueTokenIntrospector(
        "https://auth-server.com/oauth2/introspect",
        "rs-client", "rs-secret");

    // Wrap with caching
    return token -> {
        String cacheKey = DigestUtils.sha256Hex(token);  // hash for key safety
        return cache.get(cacheKey, () -> delegate.introspect(token));
    };
}

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the fundamental difference between JWT and opaque tokens?
A: JWT is self-contained — all claims are embedded and validation happens
   locally. Opaque tokens are references to server-side data — the resource
   server must call the AS introspection endpoint to validate and retrieve
   claims. JWTs are stateless; opaque tokens require AS state.

Q: How do you handle JWT revocation?
A: JWT can't be truly revoked. Strategies: (1) Short TTL (15 min) limits
   exposure. (2) Token denylist in Redis — check jti on every request.
   (3) For critical cases, use opaque tokens or hybrid phantom token pattern.

Q: What is the phantom token pattern?
A: API Gateway exchanges external opaque tokens for internal JWTs via
   token introspection. External clients get small, revocable opaque tokens.
   Internal microservices receive JWTs for fast stateless validation. Best
   of both worlds.

Q: Can opaque tokens be cached? What's the tradeoff?
A: Yes — cache introspection responses to avoid AS calls on every request.
   Tradeoff: revocation takes effect only after cache TTL expires. Set cache
   TTL shorter than token lifetime but long enough for performance benefit.
   Example: 60-second cache TTL means up to 60s for revocation to propagate.

Q: Why might you prefer opaque tokens for a banking application?
A: Immediate revocation is critical — if an account is compromised, you need
   the token invalidated instantly, not 15 minutes from now. Opaque tokens
   support this; JWTs do not without a denylist.
