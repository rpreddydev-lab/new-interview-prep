========================================================
SECRETS MANAGEMENT
========================================================

Secrets are sensitive configuration values: database passwords, API keys,
TLS certificates, encryption keys, OAuth2 client secrets, SMTP credentials, etc.

Secrets Management = how you store, access, rotate, and audit these secrets
securely across your application infrastructure.

BAD practice: Hardcoding secrets in code or config files
GOOD practice: Centralized secrets management with access control and audit trail

========================================================
1. SECRETS MANAGEMENT PRINCIPLES
========================================================

Core Principles:
  1. Never hardcode secrets in source code
  2. Never commit secrets to version control
  3. Least privilege: each service only accesses the secrets it needs
  4. Secret rotation: regularly rotate credentials without downtime
  5. Audit: log all secret access (who, when, what)
  6. Encryption at rest and in transit
  7. Short-lived secrets where possible (TTL-based)

Secrets lifecycle:
  Create → Store (encrypted) → Distribute → Use → Rotate → Revoke/Delete

Common places secrets SHOULD NOT be:
  ✗ application.properties / application.yml (checked into Git)
  ✗ Dockerfile / docker-compose.yml
  ✗ Environment variables set directly in shell scripts
  ✗ Slack messages, email, issue trackers
  ✗ Logging output

========================================================
2. HASHICORP VAULT
========================================================

Vault is the most popular open-source secrets management tool.
Spring Boot integrates with Vault via Spring Cloud Vault.

Key Vault features:
  - Dynamic secrets (generates short-lived DB credentials on demand)
  - Secrets engines (KV, database, PKI, AWS, etc.)
  - Lease and renewal (automatic TTL)
  - Access policies (fine-grained per-service access control)
  - Audit logging (all access logged)
  - Encryption as a Service (Transit engine)

2.1 SPRING CLOUD VAULT INTEGRATION

Dependencies:
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-vault-config</artifactId>
</dependency>

bootstrap.yml (loaded before application context):
spring:
  cloud:
    vault:
      host: vault.example.com
      port: 8200
      scheme: https
      authentication: APPROLE            # Service authentication method
      app-role:
        role-id: ${VAULT_ROLE_ID}        # Non-secret, can be in env var
        secret-id: ${VAULT_SECRET_ID}    # Short-lived, injected by Vault agent
      kv:
        enabled: true
        backend: secret                  # KV v2 mount path
        default-context: application     # Reads secret/data/application
        application-name: order-service  # Reads secret/data/order-service

application.yml:
# Values come from Vault automatically:
spring:
  datasource:
    url: ${database.url}               # Mapped from Vault secret
    username: ${database.username}
    password: ${database.password}

2.2 VAULT KV SECRETS ENGINE

Commands to manage secrets in Vault:

# Enable KV v2 secrets engine
vault secrets enable -path=secret kv-v2

# Store a secret
vault kv put secret/order-service \
    database.url="jdbc:postgresql://db:5432/orders" \
    database.username="order_service" \
    database.password="s3cur3P@ssw0rd"

# Read a secret
vault kv get secret/order-service

# Update a secret (creates new version)
vault kv patch secret/order-service database.password="n3wP@ssw0rd"

# Policy for order-service (least privilege)
vault policy write order-service - <<EOF
path "secret/data/order-service" {
    capabilities = ["read"]
}
path "secret/data/application" {
    capabilities = ["read"]
}
EOF

# Create AppRole for order-service
vault auth enable approle
vault write auth/approle/role/order-service \
    token_policies="order-service" \
    token_ttl=1h \
    token_max_ttl=4h \
    secret_id_ttl=24h \
    secret_id_num_uses=10

# Get role-id (non-secret, include in app config)
vault read auth/approle/role/order-service/role-id

# Get secret-id (secret, inject via CI/CD or Vault Agent)
vault write -f auth/approle/role/order-service/secret-id

2.3 VAULT DYNAMIC DATABASE SECRETS

Vault can generate short-lived, unique database credentials per service:

# Configure database secrets engine
vault secrets enable database
vault write database/config/orders-db \
    plugin_name=postgresql-database-plugin \
    allowed_roles="order-service" \
    connection_url="postgresql://{{username}}:{{password}}@db:5432/orders" \
    username="vault" \
    password="vault-password"

vault write database/roles/order-service \
    db_name=orders-db \
    creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
    default_ttl="1h" \
    max_ttl="24h"

# Spring Cloud Vault automatically fetches dynamic DB credentials:
spring:
  cloud:
    vault:
      database:
        enabled: true
        role: order-service
        backend: database

# Now spring.datasource.username and spring.datasource.password
# are AUTOMATICALLY set to the dynamically generated credentials!
# They expire in 1 hour and Vault Agent renews them automatically.

2.4 VAULT AGENT (KUBERNETES)

Vault Agent runs as a sidecar, authenticates to Vault, fetches secrets,
and writes them as files or environment variables to the app container.

Kubernetes Auth with Vault:
vault auth enable kubernetes
vault write auth/kubernetes/config \
    kubernetes_host="https://kubernetes.default.svc" \
    kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt

vault write auth/kubernetes/role/order-service \
    bound_service_account_names=order-service \
    bound_service_account_namespaces=production \
    policies=order-service \
    ttl=1h

Kubernetes deployment with Vault Agent annotations:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "order-service"
        vault.hashicorp.com/agent-inject-secret-config: "secret/data/order-service"
        vault.hashicorp.com/agent-inject-template-config: |
          {{- with secret "secret/data/order-service" -}}
          database.password={{ .Data.data.password }}
          {{- end }}

========================================================
3. AWS SECRETS MANAGER
========================================================

AWS Secrets Manager is a fully managed service for storing and rotating secrets.

3.1 Spring Boot with AWS Secrets Manager

<!-- Spring Cloud AWS -->
<dependency>
    <groupId>io.awspring.cloud</groupId>
    <artifactId>spring-cloud-aws-starter-secrets-manager</artifactId>
</dependency>

application.yml:
spring:
  cloud:
    aws:
      secretsmanager:
        enabled: true
      region:
        static: us-east-1
  config:
    import: "aws-secretsmanager:/myapp/production/"

# Secrets in AWS will be available as Spring properties:
# /myapp/production/database → parsed and injected as properties

3.2 Managing Secrets via AWS CLI

# Create a secret
aws secretsmanager create-secret \
    --name "/myapp/production/database" \
    --secret-string '{"url":"jdbc:postgresql://db:5432/orders","username":"app","password":"s3cr3t"}'

# Update/rotate a secret
aws secretsmanager rotate-secret \
    --secret-id "/myapp/production/database" \
    --rotation-lambda-arn arn:aws:lambda:...

# Access policy (IAM)
{
    "Version": "2012-10-17",
    "Statement": [{
        "Effect": "Allow",
        "Action": ["secretsmanager:GetSecretValue"],
        "Resource": "arn:aws:secretsmanager:us-east-1:*:secret:/myapp/production/*"
    }]
}

========================================================

application.yml (reference env vars):

    url: ${DATABASE_URL}

    password: ${DATABASE_PASSWORD}

  secret: ${JWT_SECRET}

  client-secret: ${OAUTH2_CLIENT_SECRET}

Docker Compose (inject at runtime, NOT hardcoded in file):
services:
  app:
    image: my-app
    env_file:
      - .env.production  # NOT committed to Git

Kubernetes Secrets:
# Create secret
kubectl create secret generic app-secrets \
    --from-literal=DATABASE_PASSWORD=s3cr3t \
    --from-literal=JWT_SECRET=mykey

# Reference in deployment:
envFrom:
  - secretRef:
      name: app-secrets

IMPORTANT: Kubernetes secrets are base64 encoded (not encrypted by default).
Use Sealed Secrets, External Secrets Operator, or Vault for encryption at rest.

========================================================
5. SECRETS ROTATION
========================================================

5.1 Database Credential Rotation (Zero Downtime)

Step-by-step rotation:
  1. Create new DB password (old still works)
  2. Update secret in Vault/Secrets Manager with new password
  3. Application fetches new credentials (via dynamic secrets or config refresh)
  4. Validate new credentials work
  5. Revoke old credentials from DB

With Vault dynamic secrets (automatic):
  - Vault generates unique credentials per instance
  - Each has a TTL (e.g., 1 hour)
  - Application's Vault Agent renews lease before expiry
  - Old credentials automatically revoked when lease expires
  - No manual rotation process needed!

5.2 JWT Signing Key Rotation

  1. Generate new RSA key pair
  2. Add to JWKS (publish public key)
  3. Start signing new tokens with new private key (new kid)
  4. Resource servers auto-discover new key (unknown kid → re-fetch JWKS)
  5. Wait for all tokens signed with old key to expire
  6. Remove old public key from JWKS

5.3 API Key Rotation

  1. Generate new API key
  2. Add to database (old key still active)
  3. Notify client via email/webhook
  4. Client updates their configuration
  5. Verify new key works
  6. Revoke old key (grace period: 7 days)

5.4 Spring Cloud Config Refresh

With Spring Cloud Config + actuator, secrets can be refreshed at runtime:

# Trigger secrets refresh (GET from Vault, update Spring context)
POST /actuator/refresh

# Or watch for changes:
spring:
  cloud:
    vault:
      config:
        lifecycle:
          enabled: true
          expiry-threshold: PT5S  # Refresh 5 seconds before expiry

6. ENCRYPTION PATTERNS
========================================================

6.1 Jasypt (Java Simplified Encryption) — Encrypt values in properties files

<dependency>
    <groupId>com.github.ulisesbocchio</groupId>
    <artifactId>jasypt-spring-boot-starter</artifactId>
</dependency>

# application.yml — encrypted values:
spring:
  datasource:
    password: ENC(eDUm0QUdTNHiC5mGbKmLPg==)  # Jasypt encrypted

# Supply master password at startup (NOT in code):
java -jar app.jar --jasypt.encryptor.password=${JASYPT_MASTER_PASSWORD}

6.2 Envelope Encryption

Data Key (DEK):  Used to encrypt data (per-record)
Key Encryption Key (KEK): Encrypts the DEK (stored in KMS)

  plaintext data → encrypt with DEK → ciphertext
  DEK → encrypt with KEK (KMS) → encrypted DEK
  Store: (ciphertext + encrypted DEK) together

To decrypt:
  Decrypt DEK using KMS (authenticated call)
  Decrypt data using plaintext DEK

Used by AWS KMS, GCP KMS, Azure Key Vault

========================================================
7. ANTI-PATTERNS TO AVOID
========================================================

NEVER do this:

// Hardcoded credentials:
DataSource ds = new DataSource();
ds.setPassword("s3cr3t");  // ← visible to anyone reading code

// In application.properties:
spring.datasource.password=s3cr3t  // ← committed to Git!

// In Dockerfile:
ENV DB_PASSWORD=s3cr3t  // ← visible in docker history

// Logging secrets (BIGGEST mistake):
log.info("Connecting with password: {}", password);  // ← in log files!

ALWAYS do this:
  - Reference env vars: spring.datasource.password=${DB_PASSWORD}
  - Use a secrets manager (Vault, AWS Secrets Manager)
  - Add .env* files to .gitignore
  - Scan for secrets in CI/CD (detect-secrets, gitleaks, truffleHog)

Scanning tools:
  git-secrets: Pre-commit hook that blocks secret commits
  truffleHog: Scans git history for high-entropy strings
  gitleaks: Fast, configurable secrets scanner
  detect-secrets: Yelp's tool with custom regexes

========================================================
8. COMMON INTERVIEW QUESTIONS
========================================================

Q: How do you handle secrets in a Spring Boot application?
A: In production: use a secrets manager like HashiCorp Vault or AWS Secrets Manager.
   Inject secrets at runtime via environment variables or Spring Cloud Vault/AWS.
   Never hardcode secrets in code or commit them to version control.
   For Kubernetes: use Kubernetes Secrets backed by Vault with External Secrets Operator.

Q: What is the benefit of dynamic secrets in HashiCorp Vault?
A: Vault generates unique, short-lived credentials for each requesting service.
   These expire automatically (e.g., DB credentials valid for 1 hour). This means:
   no long-lived passwords to steal, each service has unique credentials (breach
   isolation), and rotation is automatic. Contrast with static secrets where one
   breach exposes permanent credentials.

Q: What is AppRole authentication in Vault?
A: AppRole is a machine-to-machine authentication method for Vault. Each service
   gets a role-id (non-secret, like a username) and a secret-id (short-lived, like
   a password). The role-id can be in app config; the secret-id is injected by the
   deployment pipeline or Vault Agent. Together they authenticate to Vault and get
   a token with the service's policies.

Q: How would you rotate a database password without application downtime?
A: 1) Create new password in the database (keep old active)
   2) Update secret in Vault/Secrets Manager
   3) Trigger Spring Cloud Config refresh (or Vault Agent renewal)
   4) Application fetches new credentials
   5) Verify connectivity with new credentials
   6) Revoke old password from database
   With Vault dynamic secrets, this is fully automatic — Vault generates
   unique credentials per instance with auto-expiry.

Q: What are the risks of storing secrets in Kubernetes Secrets?
A: Kubernetes Secrets are base64 encoded, not encrypted, by default.
   Anyone with kubectl access can base64 decode them. Risks:
   - Stored in etcd without encryption unless configured
   - Visible in YAML files
   Solutions: Enable etcd encryption at rest, use Sealed Secrets,
   External Secrets Operator (fetch from Vault/AWS SM), or Vault Agent sidecar.

Q: What is envelope encryption?
A: Two-layer encryption: a Data Encryption Key (DEK) encrypts the actual data,
   and a Key Encryption Key (KEK) stored in KMS encrypts the DEK. Only the
   encrypted DEK + ciphertext are stored. To decrypt, you call KMS to decrypt
   the DEK (requires authentication), then use the DEK locally. This prevents
   KMS from seeing your data while keeping key control centralized.
