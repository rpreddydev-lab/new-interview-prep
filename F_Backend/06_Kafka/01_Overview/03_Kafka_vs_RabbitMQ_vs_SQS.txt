1. OVERVIEW OF EACH SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

APACHE KAFKA (2011)
  - Distributed streaming platform / persistent commit log
  - Created by LinkedIn; open-sourced as Apache project
  - Pull-based, partitioned, replayable event log
  - Best for: High-throughput event streaming, fan-out, replay, CQRS

RABBITMQ (2007)
  - Traditional message broker implementing AMQP protocol
  - Created by Rabbit Technologies, now part of VMware/Broadcom
  - Push-based, routing-rich, transient by default
  - Best for: Complex routing, task queues, RPC patterns, smaller scale

AWS SQS (2006)
  - Fully managed message queue service by Amazon
  - Two flavors: Standard Queue and FIFO Queue
  - HTTP/HTTPS based, no broker to manage
  - Best for: Simple decoupling in AWS ecosystem, serverless, low-maintenance

3. MESSAGING MODELS EXPLAINED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KAFKA — Log-based Pub/Sub:
  Producer → Topic (Partition 0, 1, 2, ...) → Consumer Group A
                                             → Consumer Group B
                                             → Consumer Group C
  - Every group reads the FULL topic independently
  - Each group tracks its own offset
  - Messages are NOT deleted after consumption
  - Multiple different systems can all process the same event

RABBITMQ — Exchange-based Routing:
  Producer → Exchange ──(direct)──→ Queue A → Consumer 1
                      ──(fanout)──→ Queue B → Consumer 2
                      ──(topic)───→ Queue C → Consumer 3
  - Exchange types: direct, fanout, topic, headers
  - Queues bind to exchanges with routing keys
  - Message is removed after consumer acknowledges (ack)
  - If no queue matches routing key, message is dropped (unless configured)

SQS — Simple Queue:
  Producer → Queue → Consumer 1 receives message (invisible to others)
                   → Message deleted after Consumer 1 processes + deletes it
  - One consumer receives each message
  - Visibility timeout: message hidden from others while being processed
  - If not deleted in time, message becomes visible again (retry)

4. ORDERING GUARANTEES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KAFKA:
  - STRICT ordering within a partition (by offset)
  - No global ordering across partitions
  - Ordering for a specific entity: use a consistent key → same partition
  - With single partition (numPartitions=1): global ordering (limits throughput)

RABBITMQ:
  - FIFO ordering per queue, but only if using a single consumer
  - With multiple consumers, ordering is NOT guaranteed
  - Quorum queues (RabbitMQ 3.8+) provide better durability but same ordering

SQS Standard:
  - BEST-EFFORT ordering (no guarantee)
  - At-least-once delivery (possible duplicates)
  - Delivered in roughly the order received, but no strict guarantee

SQS FIFO:
  - STRICT first-in, first-out per message group ID
  - Exactly-once processing within 5-minute deduplication window
  - Lower throughput: 300 msg/sec (3000 with batching)
  - Deduplication by content hash or explicit deduplication ID

5. DELIVERY SEMANTICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KAFKA:
  - At-most-once:  acks=0, no retries
  - At-least-once: acks=1 or acks=all with retries (default)
  - Exactly-once:  idempotent producer + Kafka Streams transactions OR
                   producer transactions with read-process-write

RABBITMQ:
  - At-most-once:  autoAck=true (no ack required)
  - At-least-once: manual ack + persistent messages + durable queues
  - No built-in exactly-once; must handle at application layer

SQS Standard:
  - At-least-once delivery (messages may be delivered more than once)
  - No exactly-once (must deduplicate at application layer)

SQS FIFO:
  - Exactly-once processing within 5-minute deduplication window
  - Content-based deduplication or explicit MessageDeduplicationId

6. WHEN TO CHOOSE EACH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CHOOSE KAFKA WHEN:
  ✓ Need to process millions of events per second
  ✓ Multiple independent services need to read the same events
  ✓ Need message replay (rewind to any past offset)
  ✓ Event sourcing / CQRS architecture
  ✓ Building real-time analytics or data pipelines
  ✓ Audit trail / long-term event storage
  ✓ Stream processing (with Kafka Streams / ksqlDB)
  ✓ Change Data Capture (CDC from databases)

CHOOSE RABBITMQ WHEN:
  ✓ Need complex routing logic (by routing key, pattern, headers)
  ✓ Building task queues or work queues with competing consumers
  ✓ Request-Reply / RPC patterns
  ✓ Need per-message TTL, priority queues, or delayed messages
  ✓ Multiple protocols needed (AMQP, MQTT, STOMP)
  ✓ Lower throughput with rich routing is the primary requirement
  ✓ Legacy systems using AMQP

CHOOSE SQS WHEN:
  ✓ Already in the AWS ecosystem (minimize ops overhead)
  ✓ Simple producer-consumer decoupling without complex requirements
  ✓ Serverless (Lambda triggers from SQS)
  ✓ Don't want to manage infrastructure
  ✓ Moderate throughput
  ✓ Long message retention (up to 14 days) without managing clusters
  ✓ SQS FIFO for strict ordering + exactly-once in AWS

7. HYBRID ARCHITECTURES (REAL WORLD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Many enterprises use BOTH Kafka and traditional queues:

Pattern 1: Kafka as the backbone + SQS for Lambda triggers
  Kafka → Kafka Connect → SQS → Lambda (per-message processing)

Pattern 2: Kafka + RabbitMQ for different workloads
  - Kafka: Event streaming, analytics, audit logs (high volume)
  - RabbitMQ: Email notifications, task dispatch, low-volume complex routing

Pattern 3: Kafka for ingestion, SQS for fan-out to AWS services
  Mobile App → API → Kafka → Kafka Consumer → SQS → Lambda → DynamoDB

8. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why would you choose Kafka over RabbitMQ?
A: Kafka is preferred when: (1) very high throughput is needed, (2) multiple
   independent consumers need the same events, (3) message replay is required,
   (4) building event-driven architectures with audit trails, or (5) real-time
   stream processing. RabbitMQ is better for complex routing, task queues, and
   RPC patterns with lower volume.

Q: What is the key architectural difference between Kafka and SQS?
A: Kafka is a persistent distributed log — messages are retained regardless of
   consumption and multiple consumer groups can read independently with replay.
   SQS is a transient queue — each message is consumed once and deleted. Kafka
   also requires managing your own cluster (or using Confluent Cloud), whereas
   SQS is fully managed by AWS.

Q: Can Kafka replace RabbitMQ completely?
A: Not always. Kafka lacks native support for: per-message TTL, priority queues,
   complex routing logic (exchange/binding patterns), and request-reply patterns.
   If your use case needs any of those, RabbitMQ may still be the right choice.
   However, Kafka covers the majority of modern event-driven use cases better.

Q: How does SQS FIFO differ from Kafka's ordering guarantee?
A: SQS FIFO guarantees strict ordering per message group ID with exactly-once
   processing but has limited throughput (300/sec per group). Kafka guarantees
   strict ordering per partition and can handle millions/sec by having more
   partitions. Both use a grouping concept (SQS MessageGroupId ≈ Kafka partition key).

Q: What is the "fan-out" problem and how does Kafka solve it?
A: Fan-out means one event needs to be processed by multiple systems. With SQS
   you'd need to duplicate the message into multiple queues (via SNS). With
   RabbitMQ you'd need multiple bindings. Kafka solves this natively — multiple
   consumer groups independently read the same topic without any duplication.
