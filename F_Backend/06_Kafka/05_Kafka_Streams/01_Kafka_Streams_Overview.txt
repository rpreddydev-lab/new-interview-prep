1. WHAT IS KAFKA STREAMS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka Streams is a lightweight, embeddable Java library for building real-time
stream processing applications that read from and write to Kafka topics.

Key characteristics:
  - LIBRARY, not a cluster: no separate processing cluster to manage
  - Embedded in your Java/Kotlin/Scala application as a dependency
  - Scales horizontally by running more instances of your application
  - Fault-tolerant: uses Kafka changelog topics and local state store backups
  - Exactly-once processing: supported via exactly-once-v2 semantics
  - Low operational overhead: just deploy your JAR; Kafka handles coordination

Kafka Streams vs other stream processors:

  ┌───────────────────┬───────────────────┬───────────────────┬────────────────┐
  │ Feature           │ Kafka Streams     │ Apache Flink      │ Apache Spark   │
  ├───────────────────┼───────────────────┼───────────────────┼────────────────┤
  │ Deployment        │ Library (JVM)     │ Standalone cluster│ Standalone     │
  │ Latency           │ Milliseconds      │ Milliseconds      │ Seconds (micro)│
  │ State management  │ RocksDB (local)   │ RocksDB / memory  │ External store │
  │ EOS               │ Yes (EOS v2)      │ Yes               │ Limited        │
  │ Language          │ Java/Kotlin       │ Java/Python/SQL   │ Java/Python/R  │
  │ Operational cost  │ Low (in-app)      │ High (cluster)    │ High (cluster) │
  │ SQL support       │ ksqlDB (separate) │ Flink SQL          │ Spark SQL      │
  │ Source/sink       │ Kafka only        │ Many connectors   │ Many connectors│
  └───────────────────┴───────────────────┴───────────────────┴────────────────┘

When to choose Kafka Streams:
  ✓ Source AND sink are Kafka topics
  ✓ Want low operational overhead (no extra cluster)
  ✓ Need sub-second latency
  ✓ Java/JVM application
  ✗ Need to read from multiple non-Kafka sources
  ✗ Complex ML pipelines / GPU processing
  ✗ Team is not JVM-based

2. TOPOLOGY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Kafka Streams application defines a TOPOLOGY: a directed acyclic graph (DAG)
of stream processing nodes.

Node types:
  SOURCE node:   reads from a Kafka topic → feeds records into the topology
  PROCESSOR node: transforms, filters, or aggregates records
  SINK node:     writes results back to a Kafka topic

  [ orders-topic ] → [filter: status=PAID] → [mapValues: enrichOrder] → [ enriched-orders-topic ]
       SOURCE                PROCESSOR               PROCESSOR                  SINK

Two APIs for building topologies:
  1. HIGH-LEVEL DSL (StreamsBuilder): functional, declarative style
     - KStream, KTable, KGroupedStream, etc.
     - Most common; covers 90%+ of use cases
  
  2. LOW-LEVEL PROCESSOR API: explicit processor nodes + punctuations
     - Full control over state stores, scheduling, and output
     - Use for complex custom logic not expressible in DSL

3. BASIC APPLICATION STRUCTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Maven dependency:
  // <groupId>org.apache.kafka</groupId>
  // <artifactId>kafka-streams</artifactId>

  Properties props = new Properties();
  props.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-processor");  // unique app name
  props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
  props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass());
  props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass());
  // Optional: enable exactly-once
  props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);

  StreamsBuilder builder = new StreamsBuilder();

  // Build topology
  KStream<String, String> ordersStream = builder.stream("orders");
  
  ordersStream
    .filter((key, value) -> value.contains("PAID"))
    .mapValues(value -> enrich(value))
    .to("enriched-orders");

  // Start the application
  KafkaStreams streams = new KafkaStreams(builder.build(), props);
  
  // Graceful shutdown
  Runtime.getRuntime().addShutdownHook(new Thread(streams::close));
  
  streams.start();

APPLICATION_ID_CONFIG is critical:
  - Used as the consumer group ID for the source topics
  - Used as the prefix for internal changelog topics (e.g., order-processor-counts-changelog)
  - All instances of the same application must share the same application.id
  - Changing it is like creating a brand new consumer group (reads from auto.offset.reset)

4. TASKS AND THREADS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka Streams internally creates TASKS for parallelism.

Stream Task:
  - One task per source partition
  - Task processes records from ONE input partition (maintains ordering per partition)
  - Tasks are the unit of parallelism AND the unit of fault tolerance

Thread:
  - Each Kafka Streams instance runs one or more StreamThreads
  - Each StreamThread runs one or more tasks
  - num.stream.threads (default=1): number of threads per instance

Scaling:
  - Scale vertically: increase num.stream.threads (more threads per JVM)
  - Scale horizontally: run more application instances (more JVM processes)
  - Max parallelism = max partition count across all source topics

Example:
  Topic: orders (6 partitions)
  → 6 tasks created
  → Instance 1 with num.stream.threads=3 → handles tasks 0,1,2
  → Instance 2 with num.stream.threads=3 → handles tasks 3,4,5

  If Instance 1 dies → its tasks reassigned to Instance 2 (it takes all 6 tasks)
  This is like consumer group rebalancing — Kafka Streams uses the same mechanism

5. STATE STORES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For stateful operations (aggregations, joins, windowing), Kafka Streams uses
LOCAL STATE STORES backed by RocksDB (an embedded key-value store).

Types:
  - Persistent (RocksDB): survives restarts; data on local disk
  - In-memory: fast but lost on restart (needs restore from changelog)

Fault tolerance via changelog topics:
  - Every write to a state store is ALSO written to a Kafka changelog topic
    (e.g., my-app-counts-changelog)
  - If an instance dies, another instance restores the state by replaying the changelog
  - Standby replicas (num.standby.replicas): pre-warm state stores on idle instances
    for faster failover

Interactive queries:
  - Query your state stores from outside the application via REST API
  - KafkaStreams.store() returns a ReadOnlyKeyValueStore / ReadOnlyWindowStore
  - Build microservices that serve query results from local state

  ReadOnlyKeyValueStore<String, Long> store =
    streams.store(StoreQueryParameters.fromNameAndType(
      "word-counts", QueryableStoreTypes.keyValueStore()));
  
  Long count = store.get("hello");

7. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is Kafka Streams and how does it differ from a regular Kafka consumer?
A: Kafka Streams is a client library for stream processing. A regular Kafka consumer
   just reads records and lets you handle processing manually. Kafka Streams provides
   high-level abstractions (KStream, KTable, windowing, joins, aggregations), built-in
   state management (RocksDB with changelog-backed fault tolerance), exactly-once
   semantics, and automatic scaling via task assignment. It runs embedded in your
   application — no separate cluster needed.

Q: How does Kafka Streams achieve fault tolerance?
A: Each stateful operation writes to a local RocksDB store AND to a Kafka changelog
   topic. If a Streams instance fails, another instance picks up its tasks and restores
   state by replaying the changelog topic. With num.standby.replicas > 0, standby
   instances keep warm copies of state stores, allowing near-instant failover without
   a full replay.

Q: What is application.id and why is it so important?
A: application.id serves as the Kafka consumer group ID for the Streams app, meaning
   all instances with the same application.id share topic partitions. It's also used
   as the prefix for internal repartition and changelog topics. Changing it causes
   Kafka Streams to create a new consumer group (reads from scratch per
   auto.offset.reset) and creates new internal topics — effectively treating it as
   an entirely new application.

Q: How does Kafka Streams scale horizontally?
A: By running multiple instances of the application with the same application.id.
   Kafka Streams creates one task per source partition. Tasks are distributed among
   all running instances via Kafka's consumer group protocol. Adding a new instance
   triggers a rebalance that redistributes tasks. Increasing num.stream.threads adds
   in-JVM parallelism. The maximum useful parallelism equals the maximum partition
   count across source topics.

Q: When would you choose Flink or Spark Streaming over Kafka Streams?
A: Choose Flink/Spark when: you need to read from non-Kafka sources (databases, S3,
   HDFS, HTTP), you require complex ML pipelines, your team is Python-based, you need
   very sophisticated windowing/CEP beyond what Kafka Streams offers, or you need
   cross-cluster processing. Kafka Streams is ideal when: all inputs and outputs are
   Kafka topics, you want minimal operational overhead (no extra cluster), latency must
   be sub-second, and you're in a JVM environment.
