================================================================
OPENID CONNECT (OIDC) — OVERVIEW
================================================================

WHAT IS OIDC?
--------------
OpenID Connect (OIDC) is an identity layer built ON TOP of OAuth2.
It adds AUTHENTICATION to OAuth2's authorization framework.

  OAuth2 alone  → "What can this app do?" (authorization)
  OAuth2 + OIDC → "Who is the user?" (authentication) + authorization

OIDC is defined by the OpenID Foundation (not IETF like OAuth2).
Latest version: OpenID Connect Core 1.0 (2014, still current standard).

================================================================
WHY OIDC?
================================================================

PROBLEM WITH PLAIN OAUTH2 FOR AUTHENTICATION:
  OAuth2 access tokens tell you what the APP is allowed to do,
  NOT who the USER is.

  Multiple providers implemented OAuth2 for authentication differently:
  - Different endpoints, different token formats, different claim names
  - No standard way to ask "who is logged in?"

OIDC SOLUTION:
  Standardizes:
    1. ID Token (JWT with user identity claims)
    2. UserInfo Endpoint (get more user info)
    3. Standard claim names (sub, name, email, picture, ...)
    4. Discovery Document (/.well-known/openid-configuration)
    5. Standard flows and responses

================================================================
OIDC vs OAUTH2 — KEY ADDITION
================================================================

OAUTH2:
  - Authorization only
  - Access Token (what the app can do)
  - Refresh Token (get new access tokens)

OIDC ADDS:
  + ID Token (who the user is — JWT with user claims)
  + UserInfo Endpoint (GET /userinfo for additional claims)
  + Standard discovery document
  + Standard scopes: openid, profile, email, address, phone
  + Logout specifications (RP-Initiated Logout)

TO GET AN ID TOKEN: include "openid" in the scope:
  scope=openid email profile

================================================================
OIDC FLOWS
================================================================

OIDC defines three flows:
  1. Authorization Code Flow  → most secure (server-side apps)
  2. Implicit Flow            → DEPRECATED
  3. Hybrid Flow              → ID Token immediately + code for access token

AUTHORIZATION CODE FLOW WITH OIDC:
  Same as OAuth2 Authorization Code Flow but:
  - scope includes "openid"
  - Response includes id_token in addition to access_token
  - nonce parameter added to prevent replay

================================================================
THE OIDC AUTHORIZATION REQUEST
================================================================

GET /oauth2/authorize
  ?response_type=code
  &client_id=my-app
  &redirect_uri=https://app.com/callback
  &scope=openid email profile           ← MUST include "openid"
  &state=csrf-random-value
  &nonce=unique-per-request-value       ← OIDC: prevent ID token replay
  &prompt=login                         ← optional: force re-authentication
  &max_age=3600                         ← optional: max seconds since last auth
  &login_hint=user@example.com          ← optional: hint for login form

SCOPE VALUES:
  openid      → REQUIRED for OIDC, triggers ID token issuance
  profile     → name, family_name, given_name, picture, website...
  email       → email, email_verified
  address     → address (structured)
  phone       → phone_number, phone_number_verified
  offline_access → request refresh token

================================================================
THE OIDC TOKEN RESPONSE
================================================================

{
  "access_token":  "eyJ...",    ← OAuth2 access token (for API calls)
  "token_type":    "Bearer",
  "expires_in":    900,
  "refresh_token": "8xLOx...", ← OAuth2 refresh token
  "id_token":      "eyJ...",   ← OIDC: user identity JWT
  "scope":         "openid email profile"
}

The id_token is a JWT containing user identity claims.
The access_token is for calling the resource server (APIs).
Don't use the access_token to get user identity — use the id_token!

================================================================
ID TOKEN — OIDC CORE
================================================================

The ID Token is a JWT issued by the IdP that contains:
{
  "iss": "https://accounts.google.com",
  "sub": "10769150350006150715113082367",  ← unique user ID
  "aud": "my-client-id",                  ← MUST be validated
  "exp": 1713484800,
  "iat": 1713481200,
  "nonce": "unique-per-request-value",    ← replay prevention
  "acr": "1",                             ← authentication context class
  "amr": ["pwd"],                         ← authentication method
  "azp": "my-client-id",
  "auth_time": 1713481200,                ← when user authenticated
  "name": "John Doe",
  "given_name": "John",
  "family_name": "Doe",
  "email": "john@example.com",
  "email_verified": true,
  "picture": "https://photos.google.com/..."
}

KEY VALIDATION FOR ID TOKEN (stricter than access token):
  ✓ iss — must match expected IdP URL
  ✓ aud — must contain YOUR client_id
  ✓ exp — not expired
  ✓ iat — recent (within clock skew)
  ✓ nonce — must match what you sent (if sent)
  ✓ alg — not "none"
  ✓ at_hash — if present, validate against access_token hash
  ✓ acr — authentication strength (if required)

================================================================
OIDC DISCOVERY DOCUMENT
================================================================

Every OIDC provider publishes a discovery document:
  GET /.well-known/openid-configuration

Example (Google):
  https://accounts.google.com/.well-known/openid-configuration

Contains:
{
  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "userinfo_endpoint": "https://openidconnect.googleapis.com/v1/userinfo",
  "revocation_endpoint": "https://oauth2.googleapis.com/revoke",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "scopes_supported": ["openid", "email", "profile"],
  "response_types_supported": ["code"],
  "claims_supported": ["sub", "name", "email", ...],
  "id_token_signing_alg_values_supported": ["RS256"],
  "subject_types_supported": ["public"]
}

Spring Security automatically uses this for auto-configuration:
  spring.security.oauth2.client.provider.google.issuer-uri=
      https://accounts.google.com

================================================================
OIDC vs SAML
================================================================

                OIDC                        SAML 2.0
-----------------------------------------------------------------
Format          JSON/JWT                    XML
Binding         HTTP redirect / POST        POST / Redirect / Artifact
Mobile support  Excellent                   Poor
Complexity      Low                         High
Standard        OpenID Foundation           OASIS
Use case        Modern web/mobile apps      Enterprise SSO
Federation      Good                        Excellent (legacy)
Token format    JWT                         XML Assertion

Enterprises often have SAML for legacy systems (Active Directory)
and OIDC for modern applications. IdPs like Okta bridge both.

================================================================
OIDC PROVIDER EXAMPLES
================================================================

GOOGLE:
  Discovery: https://accounts.google.com/.well-known/openid-configuration
  sub: unique numeric user ID (stable)

MICROSOFT (Azure AD / Entra ID):
  Discovery: https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration
  sub: unique object ID (per-tenant)

KEYCLOAK:
  Discovery: https://keycloak.example.com/realms/{realm}/.well-known/openid-configuration

AUTH0:
  Discovery: https://{domain}/.well-known/openid-configuration

================================================================
SPRING SECURITY OIDC CONFIGURATION
================================================================

# application.yml
spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ${GOOGLE_CLIENT_ID}
            client-secret: ${GOOGLE_CLIENT_SECRET}
            scope: openid, email, profile
          keycloak:
            client-id: my-app
            client-secret: ${KC_SECRET}
            scope: openid, email, profile
            authorization-grant-type: authorization_code
        provider:
          keycloak:
            issuer-uri: https://keycloak.example.com/realms/myrealm

// Spring Security config
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .anyRequest().authenticated()
        )
        .oauth2Login(oauth2 -> oauth2
            .userInfoEndpoint(userInfo -> userInfo
                .oidcUserService(oidcUserService())
            )
        );
    return http.build();
}

// Custom OIDC user service to add custom claims to Principal
@Bean
public OidcUserService oidcUserService() {
    OidcUserService delegate = new OidcUserService();
    return new OidcUserService() {
        @Override
        public OidcUser loadUser(OidcUserRequest request) throws OAuth2AuthenticationException {
            OidcUser user = delegate.loadUser(request);
            // Load additional roles from DB or custom claims
            return user;
        }
    };
}

// Access user info
@GetMapping("/profile")
public Map<String, Object> profile(Authentication auth) {
    OidcUser user = (OidcUser) auth.getPrincipal();
    return Map.of(
        "sub", user.getSubject(),
        "name", user.getFullName(),
        "email", user.getEmail(),
        "picture", user.getPicture()
    );
}

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the difference between OAuth2 and OIDC?
A: OAuth2 is an authorization framework — it controls what an app can do.
   OIDC is an identity layer on top of OAuth2 that adds authentication —
   it tells you who the user is. OIDC adds the ID Token, UserInfo endpoint,
   standardized scopes, and discovery document.

Q: What is the ID token and how is it different from an access token?
A: The ID token is an OIDC-specific JWT containing user identity claims
   (sub, name, email, etc.) intended for the CLIENT application to know
   who is logged in. The access token is for calling protected APIs.
   Don't use the access token to identify the user.

Q: What is the nonce parameter in OIDC?
A: A random value included in the authorization request and embedded in the
   ID token by the AS. The client verifies the nonce on receipt to prevent
   ID token replay attacks.

Q: What is the OIDC discovery document?
A: A JSON document at /.well-known/openid-configuration that describes the
   IdP's capabilities: endpoints (authorize, token, userinfo, jwks), supported
   scopes, supported algorithms, etc. Clients use it for auto-configuration.
   Spring Security supports this via issuer-uri configuration.

Q: How does OIDC handle logout?
A: OIDC defines RP-Initiated Logout: the client redirects the user to the
   IdP's end_session_endpoint with id_token_hint and post_logout_redirect_uri.
   The IdP terminates the user's SSO session and redirects back.
