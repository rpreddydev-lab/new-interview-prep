================================================================
HTTPS AND TLS (Transport Layer Security)
================================================================

WHY HTTPS?
-----------
HTTP sends data as plain text — anyone on the network can read it.
HTTPS = HTTP + TLS encryption → data is encrypted in transit.

Without HTTPS:
  - Passwords visible in network logs
  - Session cookies can be stolen (session hijacking)
  - Man-in-the-Middle (MITM) attacks trivial

================================================================
TLS (Transport Layer Security)
================================================================

WHAT IS TLS?
-------------
TLS is a cryptographic protocol that provides:
  1. Confidentiality  — Encrypts data so only sender/receiver can read
  2. Integrity        — Detects tampering via MAC (Message Auth Code)
  3. Authentication   — Server (and optionally client) proves identity via certificate

TLS VERSIONS
-------------
TLS 1.0  — Deprecated (2020), vulnerable to BEAST, POODLE
TLS 1.1  — Deprecated (2020)
TLS 1.2  — Still widely used, secure with proper cipher suites
TLS 1.3  — Current standard (2018), faster, stronger, simpler
           - Removed weak cipher suites
           - 1-RTT handshake (vs 2-RTT in 1.2)
           - 0-RTT resumption (with replay attack caveats)

SSL vs TLS:
  SSL (Secure Sockets Layer) is the old, deprecated predecessor to TLS.
  "SSL" is commonly used as a term but technically means TLS today.

================================================================
TLS HANDSHAKE (TLS 1.2)
================================================================

CLIENT                          SERVER
  |                               |
  |--- ClientHello ─────────────>|  (TLS version, cipher suites, random)
  |<-- ServerHello ──────────────|  (chosen cipher suite, random)
  |<-- Certificate ──────────────|  (server's X.509 certificate)
  |<-- ServerHelloDone ──────────|
  |                               |
  |  [Client verifies cert]       |
  |--- ClientKeyExchange ───────>|  (pre-master secret, encrypted w/ server pub key)
  |--- ChangeCipherSpec ────────>|
  |--- Finished ────────────────>|  (verify handshake integrity)
  |                               |
  |<-- ChangeCipherSpec ──────────|
  |<-- Finished ─────────────────|
  |                               |
  |=== Encrypted Application Data ===|

TLS 1.3 HANDSHAKE (Simplified — 1-RTT)
----------------------------------------
CLIENT                          SERVER
  |--- ClientHello + KeyShare ──>|  (client sends DH key share upfront)
  |<-- ServerHello + KeyShare ───|  (server sends its DH key share)
  |<-- {Certificate} ────────────|  (encrypted already!)
  |<-- {CertificateVerify} ──────|
  |<-- {Finished} ───────────────|
  |--- {Finished} ──────────────>|
  |=== Application Data =========|

Key improvement: Keys derived immediately → no RSA key exchange (forward secrecy by default)

================================================================
X.509 CERTIFICATES
================================================================

WHAT IS A CERTIFICATE?
-----------------------
A digital document that binds a public key to an identity.
Issued by a Certificate Authority (CA).

CERTIFICATE CONTENTS
---------------------
- Subject       : The entity (domain, organization)
- Issuer        : The CA that signed it
- Public Key    : The entity's public key
- Validity      : Not Before / Not After dates
- Serial Number : Unique ID
- Signature     : CA's digital signature
- SANs          : Subject Alternative Names (hostnames covered)

CERTIFICATE CHAIN
------------------
Browser trusts Root CA
  → Root CA signs Intermediate CA
    → Intermediate CA signs Server Certificate

This chain allows CAs to protect their root keys offline while
intermediate CAs handle day-to-day signing.

CERTIFICATE AUTHORITIES (CAs)
-------------------------------
Public CAs   : DigiCert, Let's Encrypt (free!), Comodo, GlobalSign
Private CAs  : Internal enterprise CAs (HashiCorp Vault, CFSSL)

Let's Encrypt:
  - Free, automated, open CA
  - Certificates valid 90 days (auto-renewed via ACME protocol)
  - Widely used for public-facing services

================================================================
CIPHER SUITES
================================================================

A cipher suite defines the algorithms used for:
  KEY EXCHANGE     : ECDHE, DHE (provides forward secrecy)
  AUTHENTICATION   : RSA, ECDSA
  ENCRYPTION       : AES-256-GCM, ChaCha20-Poly1305
  MAC/HASH         : SHA-256, SHA-384

Example cipher suite name:
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
       ^         ^       ^           ^
   Key exchange  Auth  Encryption   Hash

STRONG CIPHER SUITES (TLS 1.3 defaults — all have forward secrecy):
  - TLS_AES_256_GCM_SHA384
  - TLS_CHACHA20_POLY1305_SHA256
  - TLS_AES_128_GCM_SHA256

WEAK/DEPRECATED (avoid):
  - RC4 — broken
  - 3DES (SWEET32 attack)
  - RSA key exchange (no forward secrecy)
  - MD5, SHA-1 for MAC

================================================================
FORWARD SECRECY
================================================================

DEFINITION:
  Even if the server's private key is compromised in the future,
  past session keys cannot be decrypted.

HOW:
  Achieved using ephemeral Diffie-Hellman (ECDHE/DHE).
  Each session generates a new ephemeral key pair.
  Session key is derived from ephemeral keys, not the private key.

WHY IMPORTANT:
  Without forward secrecy, an attacker recording encrypted traffic today
  can decrypt it later if they obtain the private key.

HTTPS IN SPRING BOOT
================================================================

# application.properties
server.port=8443
server.ssl.enabled=true
server.ssl.key-store=classpath:keystore.p12
server.ssl.key-store-password=changeit
server.ssl.key-store-type=PKCS12
server.ssl.key-alias=myapp

# Force HTTPS redirect (HTTP → HTTPS)
server.ssl.protocol=TLS
server.ssl.enabled-protocols=TLSv1.2,TLSv1.3

// HTTP to HTTPS redirect config
@Bean
public TomcatServletWebServerFactory servletContainer() {
    TomcatServletWebServerFactory factory = new TomcatServletWebServerFactory() {
        @Override
        protected void postProcessContext(Context context) {
            SecurityConstraint constraint = new SecurityConstraint();
            constraint.setUserConstraint("CONFIDENTIAL");
            SecurityCollection collection = new SecurityCollection();
            collection.addPattern("/*");
            constraint.addCollection(collection);
            context.addConstraint(constraint);
        }
    };
    factory.addAdditionalTomcatConnectors(httpConnector());
    return factory;
}

@Bean
public Connector httpConnector() {
    Connector connector = new Connector(TomcatServletWebServerFactory.DEFAULT_PROTOCOL);
    connector.setScheme("http");
    connector.setPort(8080);
    connector.setSecure(false);
    connector.setRedirectPort(8443);
    return connector;
}

================================================================
HSTS (HTTP Strict Transport Security)
================================================================

HEADER: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Tells browser: "Only access this site over HTTPS for the next year."
  - Prevents SSL stripping attacks
  - Preload: include in browser's built-in HSTS list

In Spring Security:
  http.headers(headers -> headers
      .httpStrictTransportSecurity(hsts -> hsts
          .includeSubDomains(true)
          .maxAgeInSeconds(31536000)
      )
  );

================================================================
CERTIFICATE PINNING
================================================================

Pin a specific certificate or public key in your mobile/client app.
Prevents MITM even with a rogue CA.

Risks: App breaks if cert rotates without updating pin.
Use: High-security mobile apps (banking).

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the difference between HTTP and HTTPS?
A: HTTPS adds TLS encryption on top of HTTP, providing confidentiality,
   integrity, and server authentication. HTTP sends data as plain text.

Q: What happens during a TLS handshake?
A: Client and server negotiate TLS version and cipher suite, server presents
   its certificate, keys are exchanged to derive symmetric session keys,
   then both sides confirm the handshake and begin encrypted communication.

Q: What is forward secrecy and why is it important?
A: Forward secrecy ensures that past session keys can't be decrypted even if
   the server's private key is later compromised. Achieved via ephemeral
   DH key exchange (ECDHE/DHE).

Q: What is TLS 1.3's main improvement over 1.2?
A: Reduced handshake to 1 round trip (1-RTT), removed weak cipher suites,
   forward secrecy by default (no RSA key exchange), and faster 0-RTT
   session resumption.

Q: How do you configure HTTPS in Spring Boot?
A: Provide a keystore (JKS/PKCS12) with the certificate and private key,
   configure server.ssl.* properties. For production, use a CA-signed cert
   or Let's Encrypt.

Q: What is HSTS?
A: HTTP Strict Transport Security — a response header that tells browsers to
   only connect via HTTPS for a specified duration, preventing SSL stripping.

Q: What is certificate pinning?
A: Hardcoding the expected certificate or public key hash in the client app.
   Prevents MITM attacks even if a CA is compromised, but risks app breakage
   on cert rotation.
