================================================================
OIDC vs OAUTH2 — DETAILED COMPARISON
================================================================

QUICK SUMMARY:
  OAuth2 = AUTHORIZATION framework (what can the app do?)
  OIDC   = AUTHENTICATION layer ON TOP OF OAuth2 (who is the user?)

OIDC REQUIRES OAuth2 — it's an extension, not a replacement.
OAuth2 CAN exist without OIDC (for pure authorization use cases).

================================================================
WHAT OAUTH2 PROVIDES
================================================================

1. TOKEN TYPES:
   - Access Token    : Authorize resource access
   - Refresh Token   : Get new access tokens

2. GRANT TYPES:
   - Authorization Code
   - Client Credentials
   - Device Code
   - (Implicit & ROPC — deprecated)

3. ENDPOINTS:
   - Authorization Endpoint  : /oauth2/authorize
   - Token Endpoint          : /oauth2/token
   - Revocation Endpoint     : /oauth2/revoke

4. CONCEPTS:
   - Scopes (resource permissions)
   - Client (app), Resource Owner (user), AS, RS

5. WHAT IT DOES NOT DEFINE:
   - No standard way to get user identity
   - No standard token format (access token can be anything)
   - No standard discovery mechanism
   - No user claims standard

================================================================
WHAT OIDC ADDS ON TOP OF OAUTH2
================================================================

1. NEW TOKEN TYPE:
   - ID Token : JWT that represents user identity
                Contains: sub, iss, aud, exp, iat, nonce + user claims

2. NEW ENDPOINT:
   - UserInfo Endpoint  : GET /userinfo → returns current user claims

3. NEW STANDARD SCOPES:
   - openid    : Trigger ID token issuance (required for OIDC)
   - profile   : User profile claims (name, picture, etc.)
   - email     : Email and email_verified
   - address   : Structured address
   - phone     : Phone number and verification
   - offline_access : Request refresh token

4. NEW PARAMETERS:
   - nonce      : Replay attack prevention for ID token
   - prompt     : Control re-authentication (login, none, consent, select_account)
   - max_age    : Max seconds since last authentication
   - login_hint : Pre-fill the login form
   - id_token_hint : For logout

5. NEW ENDPOINTS:
   - Discovery  : /.well-known/openid-configuration
   - JWKS       : /.well-known/jwks.json (key published)
   - End Session: /connect/endsession (logout)

6. STANDARDIZED CLAIMS:
   sub, name, given_name, family_name, email, email_verified,
   picture, profile, phone_number, address, birthdate, etc.

7. LOGOUT SPECIFICATION:
   - RP-Initiated Logout
   - Front-Channel Logout
   - Back-Channel Logout

================================================================
AUTHENTICATION VS AUTHORIZATION — IN OIDC CONTEXT
================================================================

USER AUTHENTICATION FLOW (OIDC):
  1. User's browser redirected to IdP with scope=openid
  2. User authenticates at IdP (password, MFA, etc.)
  3. IdP issues ID Token → client knows WHO the user is
  4. Result: Security context established (who is logged in)

AUTHORIZATION FLOW (OAuth2):
  1. Client requests specific scopes (read:orders, write:profile)
  2. User consents to those permissions
  3. Access Token issued with those scopes
  4. Result: Client authorized to perform specific actions

IN COMBINED FLOW:
  scope=openid email read:orders
  → ID Token: authentication (who is the user)
  → Access Token: authorization (read:orders permission)

================================================================
OIDC SESSION MANAGEMENT AND LOGOUT
================================================================

SESSION CONCEPTS:
  - IdP session    : User's session at the Identity Provider (SSO session)
  - RP session     : User's session at the Relying Party (your app)

SSO (Single Sign-On) is naturally supported:
  - User logs into App A via Keycloak
  - User visits App B (same Keycloak realm)
  - App B redirects to Keycloak → Keycloak detects existing session
  - App B receives tokens without user re-entering credentials

LOGOUT FLOWS:

1. RP-INITIATED LOGOUT (most common):
   Client initiates logout by redirecting user to:
   GET /connect/endsession
     ?id_token_hint=eyJ...      ← user's ID token
     &post_logout_redirect_uri=https://app.com/logged-out

   IdP terminates SSO session.
   User redirected to post_logout_redirect_uri.

2. FRONT-CHANNEL LOGOUT:
   IdP notifies all RPs by loading hidden iframes:
   <iframe src="https://app.com/logout?sid=session-id"/>
   Each RP clears its local session.
   Issue: popup blockers, iframe restrictions reduce reliability.

3. BACK-CHANNEL LOGOUT (most reliable):
   IdP sends POST logout token (JWT) to each RP's backchannel logout URI.
   POST https://app.com/logout
     logout_token=eyJ...
   RP validates and terminates session.
   No browser involvement — works reliably.

// Spring Security: OIDC logout
http.logout(logout -> logout
    .logoutSuccessHandler(
        oidcLogoutSuccessHandler(clientRegistrationRepository)
    )
);

private OidcClientInitiatedLogoutSuccessHandler oidcLogoutSuccessHandler(
        ClientRegistrationRepository repo) {
    OidcClientInitiatedLogoutSuccessHandler handler =
        new OidcClientInitiatedLogoutSuccessHandler(repo);
    handler.setPostLogoutRedirectUri("{baseUrl}/logged-out");
    return handler;
}

================================================================
PROMPT PARAMETER VALUES (OIDC)
================================================================

prompt=none:
  Don't show login UI. If user has active SSO session → get tokens silently.
  If no session → return error (login_required).
  Use case: Silent token refresh, check if user is still logged in.

prompt=login:
  Always force re-authentication (ignore existing SSO session).
  Use case: Step-up authentication, sensitive operations.

prompt=consent:
  Always show consent screen.
  Use case: Remind user what they've authorized.

prompt=select_account:
  Show account selector (if multiple accounts signed in).
  Use case: Multi-account Google-like experience.

COMMON USE CASES
================================================================

SCENARIO                  USE
----------------------------------------------------------------------
Website login (SSO)       OIDC Authorization Code + ID Token
Check who is logged in    Read ID Token claims (sub, email, name)
Call an API               OAuth2 Access Token (from same flow)
M2M API calls             OAuth2 Client Credentials (no OIDC needed)
Silent token refresh      OAuth2 Refresh Token flow
Check active session      prompt=none
Force re-auth             prompt=login
Get fresh user data       UserInfo Endpoint
Logout everywhere         RP-Initiated + Back-Channel Logout

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What does OIDC add to OAuth2?
A: OIDC adds the authentication layer: (1) ID Token — JWT proving user
   identity, (2) UserInfo endpoint — fetch user claims, (3) Standard
   claims (sub, email, name...), (4) Discovery document, (5) Logout
   specifications, (6) Standard scopes (openid, profile, email).

Q: Can you use OAuth2 without OIDC for authentication?
A: Technically yes (many apps did this before OIDC), but it was
   non-standard and each provider had different conventions. OIDC
   standardizes authentication on top of OAuth2. Without OIDC, you have
   no standard way to get user identity or validate who is logged in.

Q: What is SSO and how does OIDC enable it?
A: SSO (Single Sign-On) allows users to authenticate once and access
   multiple applications without re-logging in. OIDC enables SSO via
   IdP session management — if a user has an active session at the IdP
   (e.g., Keycloak), subsequent apps can get tokens silently using
   prompt=none.

Q: What is the difference between front-channel and back-channel logout?
A: Front-channel: IdP notifies RPs via browser iframes — client-side,
   unreliable (blocked by browsers). Back-channel: IdP sends logout
   token via direct HTTP POST to RP's endpoint — server-to-server,
   reliable, recommended for production.

Q: When would you NOT need OIDC?
A: Pure machine-to-machine (M2M) authorization — no user involved, so
   no need for user identity. Client Credentials grant with OAuth2 is
   sufficient. Also for simple API key-based access with no SSO requirement.
