CORE gRPC INTERVIEW QUESTIONS
================================================================

This file contains the most commonly asked interview questions
with detailed answers. Study these to crack gRPC interviews.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Q1: What is gRPC and how does it differ from REST?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC (Google Remote Procedure Call) is an open-source RPC framework
that uses HTTP/2 as the transport and Protocol Buffers (protobuf)
as the interface definition language and serialization format.

Key differences from REST:

  gRPC vs REST — Quick comparison:
  ┌──────────────┬──────────────────────────┬──────────────────────────┐
  │ Aspect       │ gRPC                     │ REST                     │
  ├──────────────┼──────────────────────────┼──────────────────────────┤
  │ Transport    │ HTTP/2 (multiplexed)      │ HTTP/1.1 or HTTP/2       │
  │ Serialization│ Binary (protobuf)         │ JSON (text)              │
  │ Contract     │ .proto file (strict)      │ OpenAPI (optional)       │
  │ Streaming    │ Native (4 modes)          │ SSE, WebSocket (limited) │
  │ Perf         │ ~5-10x faster            │ Baseline                 │
  │ Browser      │ Not directly             │ Yes                      │
  │ Code gen     │ Automatic (all languages)│ Optional (Swagger)       │
  └──────────────┴──────────────────────────┴──────────────────────────┘

Choose gRPC for:
  - Internal microservice communication
  - Low latency / high throughput requirements
  - Strongly typed contracts between services
  - Polyglot environments
  - Bidirectional streaming (chat, IoT, trading)

Choose REST for:
  - Public APIs consumed by browsers
  - Third-party integrations
  - Simple CRUD APIs where tooling maturity matters

Q2: Explain the four types of gRPC service methods.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Unary RPC:
   Client sends ONE request, server sends ONE response.
   Like a regular function call.
   rpc GetOrder(GetOrderRequest) returns (Order);
   Use: GetUser, CreateOrder, Login, Search

2. Server Streaming RPC:
   Client sends ONE request, server sends a STREAM of responses.
   rpc ListOrders(ListOrdersRequest) returns (stream Order);
   Use: Real-time event feeds, file download, stock prices

3. Client Streaming RPC:
   Client sends a STREAM of requests, server sends ONE response.
   rpc UploadFile(stream FileChunk) returns (UploadFileResponse);
   Use: File upload, batch insert, sensor data aggregation

4. Bidirectional Streaming RPC:
   Both client and server send independent streams simultaneously.
   rpc Chat(stream ChatMessage) returns (stream ChatMessage);
   Use: Chat, trading systems, IoT device control, collaboration

All four use a single HTTP/2 stream. The difference is how many
messages each side sends and when they complete.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Q3: How does gRPC use HTTP/2?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC requires HTTP/2 and uses several of its features:

1. Multiplexing:
   Multiple gRPC calls can fly simultaneously over a single TCP
   connection. No head-of-line blocking. Each gRPC call = one
   HTTP/2 stream. HTTP/2 streams are identified by stream IDs.

2. Header Compression (HPACK):
   gRPC metadata (authorization headers, trace IDs) is compressed
   using HPACK, reducing overhead significantly for repeated calls.

3. Full-duplex streaming:
   HTTP/2 allows both client and server to send data at any time
   on the same stream. This enables bidirectional streaming.

4. Flow control:
   HTTP/2 flow control prevents fast senders from overwhelming slow
   receivers. gRPC uses this for back-pressure in streaming RPCs.

gRPC HTTP/2 frame mapping:
  Client request:   HEADERS + DATA (+ END_STREAM for unary)
  Server response:  HEADERS + DATA + TRAILERS (+ END_STREAM)
  Trailers carry:   grpc-status, grpc-message
  
5 key HTTP/2 headers gRPC adds:
  :method = POST
  :scheme = https (or http)
  :path = /package.ServiceName/MethodName
  content-type = application/grpc
  grpc-timeout = 5000m (optional deadline)

Q4: What is the role of Protocol Buffers in gRPC?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Protocol Buffers serve THREE roles in gRPC:

1. Interface Definition Language (IDL):
   The .proto file defines the service contract — method signatures,
   request types, response types. This is the source of truth.

2. Serialization Format:
   Messages are serialized to a binary wire format using field number
   + wire type tags, variable-length integers (varints), and packed
   repeated fields. This makes it 3-10x smaller and faster than JSON.

3. Code Generator:
   protoc compiles .proto files into language-specific code —
   message classes (getters/setters/builders), service base classes,
   and stub implementations. For Java + gRPC, it generates:
     - YourMessage.java (the data class)
     - YourServiceGrpc.java (base class + stubs)

Why protobuf over JSON?
  - Binary encoding: 3-5x smaller payloads
  - Faster serialization: no parsing of text delimiters
  - Strongly typed: compile-time errors for wrong types
  - Schema evolution: backward/forward compatible by design
  - Multi-language: same .proto generates code for all languages

Q5: How does gRPC handle errors?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC uses a Status model instead of HTTP status codes.
Every RPC terminates with Status.OK or an error code + description.

Key status codes:
  OK                  - Success
  INVALID_ARGUMENT    - Bad request data (validation failure)
  NOT_FOUND           - Resource not found
  ALREADY_EXISTS      - Create conflict
  PERMISSION_DENIED   - Authenticated but not authorized
  UNAUTHENTICATED     - No valid credentials
  FAILED_PRECONDITION - Business rule / state violation
  ABORTED             - Optimistic lock conflict (retry)
  DEADLINE_EXCEEDED   - Request timed out
  UNAVAILABLE         - Service temporarily down (retry)
  INTERNAL            - Unexpected server error

Server sends error:
  responseObserver.onError(
      Status.NOT_FOUND
          .withDescription("Order " + id + " not found")
          .asException());

Client receives error:
  catch (StatusRuntimeException e) {
    Status.Code code = e.getStatus().getCode();
    String desc = e.getStatus().getDescription();
  }

Rich error details (field violations, retry hints):
  Use google.rpc.Status with Any-packed detail types:
  BadRequest (field violations), RetryInfo (backoff hint), etc.
  StatusProto.toStatusRuntimeException(richStatus)

Q6: What is a Channel in gRPC?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A ManagedChannel is a logical connection to a gRPC server.

Key characteristics:
  - ONE channel can multiplex THOUSANDS of concurrent RPCs
  - Channel manages the underlying TCP connection(s) automatically
  - Channel handles reconnection (exponential backoff)
  - Channel manages load balancing across multiple backends
  - Channel monitors connection health

Channel states: IDLE → CONNECTING → READY ↔ TRANSIENT_FAILURE → SHUTDOWN

Best practices:
  ✅ Create ONE channel per target service (at startup)
  ✅ Reuse the same channel for all stubs and all calls
  ✅ Never create a channel per request (too expensive)
  ✅ Shut down the channel when the application closes

ManagedChannel channel = ManagedChannelBuilder
    .forAddress("order-service.example.com", 9090)
    .usePlaintext()
    .keepAliveTime(30, TimeUnit.SECONDS)
    .build();

// Multiple stubs — all share the same channel
OrderServiceGrpc.OrderServiceBlockingStub blockingStub = 
    OrderServiceGrpc.newBlockingStub(channel);
OrderServiceGrpc.OrderServiceStub asyncStub = 
    OrderServiceGrpc.newStub(channel);

Q7: Explain gRPC deadlines and why they're important.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A deadline is an absolute point in time by which the RPC must complete.
gRPC transmits deadlines as a grpc-timeout header (HTTP/2).

Why deadlines are critical:
  - Without deadlines, slow upstream services block threads forever
  - Thread pool exhaustion causes a cascade failure
  - Every gRPC call MUST have a deadline in production

Timeout vs Deadline:
  - Timeout: relative ("5 seconds from now")
  - Deadline: absolute ("complete by 14:00:03.123 UTC")
  - gRPC uses deadlines internally for propagation correctness

Setting a deadline:
  stub.withDeadlineAfter(5, TimeUnit.SECONDS).createOrder(request);

Propagating to child calls:
  Deadline d = Context.current().getDeadline();
  childStub.withDeadline(d).checkInventory(childRequest);

Without propagation: if client has 1s left but child gets a new 5s
deadline, the child wastes 4s of work after the client gives up.

Server checking deadline:
  if (Context.current().isCancelled()) { /* stop early */ }
  // In streaming: serverObserver.isCancelled()

Q8: How does gRPC achieve load balancing?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

gRPC's HTTP/2 multiplexing means standard L4 load balancers don't
work — all calls on one TCP connection go to the same server.

Solutions:

1. Client-side load balancing:
   - Client resolves all backend IPs (via DNS or service discovery)
   - Client maintains connections to all backends
   - "round_robin" policy distributes RPCs across all connections
   - In Kubernetes: use a headless service (clusterIP: None) for DNS
     to return all pod IPs

2. L7 Proxy (Envoy/Istio/Linkerd):
   - Envoy proxy intercepts gRPC calls at HTTP/2 stream level
   - Routes each stream to a different backend
   - Works with regular K8s ClusterIP services
   - Adds features: circuit breaking, retries, observability

3. Look-aside LB (gRPC-LB protocol):
   - Client queries an LB service for backend addresses
   - Client connects directly to recommended backends
   - Used internally at Google; complex to deploy elsewhere

Q9: What is metadata in gRPC and how do you use it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Metadata is gRPC's equivalent of HTTP headers — key-value pairs
sent alongside the RPC.

Two phases:
  Headers: sent at start of call (request metadata, initial response metadata)
  Trailers: sent at end of call (status code, error details, final metadata)

Key types:
  ASCII: String values, key must NOT end in "-bin"
  Binary: byte[] values, key MUST end in "-bin"

Client sending metadata:
  Metadata metadata = new Metadata();
  metadata.put(Metadata.Key.of("authorization", ASCII_STRING_MARSHALLER),
      "Bearer " + token);
  stub = MetadataUtils.attachHeaders(stub, metadata);

Server reading metadata:
  // In interceptor:
  String authHeader = headers.get(AUTHORIZATION_KEY);

Server sending metadata:
  serverObserver.sendHeaders(initialMetadata);  // headers
  // Trailers sent automatically with onCompleted()

Common use: authorization tokens, trace IDs, tenant IDs,
rate limit headers, rich error details (in trailers).

Q10: How do you write tests for gRPC services?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Three levels of testing:

1. Unit tests (fastest):
   - No Spring context, no gRPC server
   - Mock dependencies with Mockito
   - Use a TestStreamObserver to capture responses
   - Test service logic directly

2. In-process integration tests:
   - Use InProcessServerBuilder + InProcessChannelBuilder
   - No TCP, but full gRPC serialization + interceptors
   - Test interceptors and error handling
   - @SpringBootTest or @GrpcTest

3. E2E tests:
   - Real server on a port
   - Real clients connecting over network
   - Test TLS, load balancing, service mesh

Key class: TestStreamObserver<T> implements StreamObserver<T>
  - Captures all onNext(), onError(), onCompleted() calls
  - Use assertCompleted(), getValues(), getStatusRuntimeException()

// Unit test pattern:
TestStreamObserver<CreateOrderResponse> observer = new TestStreamObserver<>();
orderService.createOrder(request, observer);
observer.assertCompleted();
assertEquals("order-1", observer.getSingleValue().getOrderId());
