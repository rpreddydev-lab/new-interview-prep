Q1: How does protobuf encoding work? What makes it compact?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Protobuf serializes each field as: field_tag + value
  field_tag = (field_number << 3) | wire_type

Wire types:
  0 = Varint    (int32, int64, bool, enum)
  1 = 64-bit    (double, fixed64)
  2 = Length-delimited (string, bytes, embedded messages, repeated fields)
  5 = 32-bit    (float, fixed32)

Varint encoding (the key to compactness):
  - Small integers (0-127) fit in 1 byte
  - Large integers use up to 10 bytes
  - No field name transmitted — just the number (1, 2, 3...)
  - Missing optional fields = zero bytes (not null)

Example:
  message Order { int32 quantity = 1; }
  quantity = 150 → field tag 0x08 (field 1, wire type 0) + varint 0x9601
  quantity = 1   → field tag 0x08 + varint 0x01
  quantity unset → nothing (0 bytes)

vs JSON:
  {"quantity":150}  → 16 bytes
  Protobuf          → 3 bytes

NO field names, NO string delimiters, NO brackets.
Binary encoding is ~3-5x smaller than JSON.

Q2: What are the rules for backward and forward compatibility?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Backward compatibility: new code reads old data
Forward compatibility: old code reads new data

SAFE changes (do not break either direction):
  ✅ Add a new optional field with a NEW field number
  ✅ Remove a field (mark it as reserved)
  ✅ Rename a field (field number still used in wire format)
  ✅ Change scalar field types compatibly (int32 → int64)

BREAKING changes (avoid these):
  ❌ Change a field's number
  ❌ Change a field's wire type (e.g., int32 → string)
  ❌ Reuse a deleted field number for a different field
  ❌ Change a repeated field to singular (data loss)
  ❌ Rename an enum value (breaks JSON serialization)

Unknown fields rule (critical to forward compat):
  Old code receiving a message with new fields it doesn't know:
  → Protobuf stores those bytes as "unknown fields"
  → The old code ignores them (doesn't crash)
  → If the old code serializes and forwards the message,
    unknown fields are PRESERVED (not dropped)

Reserved fields (prevent accidental reuse):
  // NEVER reuse these field numbers or names
  message Order {
    reserved 5, 10, 15;
    reserved "old_customer_id", "legacy_status";
    string customer_id = 1;
  }

Q3: What is the difference between int32, sint32, and fixed32?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All three are 32-bit integers in proto but differ in wire encoding:

int32:
  - Wire type: Varint
  - Small positive numbers: 1-5 bytes (efficient)
  - NEGATIVE numbers: 10 bytes (treated as 64-bit uint internally)
  - Use for: counts, IDs, ages, non-negative values

sint32:
  - Wire type: Varint with ZigZag encoding
  - ZigZag maps: 0→0, -1→1, 1→2, -2→3, 2→4...
  - Negative numbers are efficient (1-5 bytes like small positives)
  - Use for: temperatures, coordinates, any negative numbers

fixed32:
  - Wire type: 32-bit (always 4 bytes)
  - Always fixed 4 bytes — no varint overhead
  - Faster to compare than varint (no decoding needed)
  - Use for: when values are often > 2^28 (like large IDs, hashes)

Cheat sheet:
  uint32: only positive, varaint — like int32 but no sign
  sfixed32: always 4 bytes, signed — like C int32_t in memory
  
Summary:
  Use int32/int64 for non-negative values
  Use sint32/sint64 for potentially negative values
  Use fixed32/fixed64 for large values or when fixed size is needed

Q4: What is a oneof field and when do you use it?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

oneof is a union type — at most ONE field in the group can be set.

Use cases:
  1. Polymorphic messages (e.g., different payment methods)
  2. Discriminated unions (event types with different payloads)
  3. Optional fields where you want to distinguish "not set" from defaults

Example:
  message PaymentMethod {
    oneof payment_type {
      CreditCard credit_card = 1;
      BankTransfer bank_transfer = 2;
      CryptoWallet crypto = 3;
    }
  }
  
  message Event {
    string id = 1;
    int64 timestamp = 2;
    oneof payload {
      OrderCreated order_created = 3;
      OrderCancelled order_cancelled = 4;
      PaymentProcessed payment_processed = 5;
    }
  }

Rules:
  - Setting one field in oneof clears ALL other fields in the group
  - Cannot use repeated in oneof
  - Cannot use map in oneof
  - Java generates a PayloadCase enum to check which field is set:
    switch (event.getPayloadCase()) {
      case ORDER_CREATED -> ...
      case ORDER_CANCELLED -> ...
      case PAYLOAD_NOT_SET -> ...
    }

Proto3 vs proto2 semantics:
  In proto3, oneof is the primary way to detect field presence
  (you can check which oneof case is set, unlike regular singular fields
  where you can't tell 0/false/"" from "not set").

Q5: What are Well-Known Types and why are they used?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Well-Known Types (WKT) are standard proto messages from google/protobuf/:

google.protobuf.Timestamp:
  - Represents UTC time as {seconds, nanos}
  - DO NOT use int64 for timestamps — Timestamp has semantic meaning
  - JSON maps to: "2024-01-15T10:30:00Z" (RFC 3339)
  - Java utility: Timestamps.fromMillis(), Timestamps.toMillis()

google.protobuf.Duration:
  - Represents a duration as {seconds, nanos}
  - JSON maps to: "5.5s"

google.protobuf.FieldMask:
  - List of field paths: paths = ["name", "address.city"]
  - Used for partial updates (only update specified fields)
  - Essential for PATCH-style RPCs

google.protobuf.Any:
  - Wraps any proto message with its type URL
  - Used for polymorphic payloads, error details
  - any.pack(myMessage) / any.unpack(MyMessage.class)

google.protobuf.Struct:
  - Represents arbitrary JSON-like data
  - Use when schema is unknown at design time
  - Avoid overuse — loses type safety

Wrapper types (StringValue, Int32Value, BoolValue, etc.):
  - Allow distinguishing "not set" from default value in proto3
  - StringValue allows null (vs "" for unset String)
  - JSON maps: StringValue("hello") → "hello", null → not set

Q6: What is the difference between proto2 and proto3?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌──────────────────────────┬──────────────────┬──────────────────────┐
│ Feature                  │ proto2           │ proto3               │
├──────────────────────────┼──────────────────┼──────────────────────┤
│ Default syntax           │ Less common now  │ ✅ Recommended       │
│ required / optional      │ Yes              │ No (all are optional) │
│ Field presence detection │ hasField() works │ Only with oneof/WKTs │
│ Default values           │ Custom defaults  │ Type defaults only   │
│ Enums                    │ Strict           │ Unknown enum = 0     │
│ Services                 │ Yes (optional)   │ Yes                  │
│ JSON mapping             │ Limited          │ Standard spec        │
│ map<K,V>                 │ No (use Entry)   │ Yes                  │
└──────────────────────────┴──────────────────┴──────────────────────┘

Key proto3 behaviors to know:
  - Unset singular fields have type defaults (0, false, "", null for msg)
  - Cannot distinguish "user set field to 0" from "field was never set"
  - Solution: use google.protobuf.Int32Value wrapper for nullable numbers
  - Unknown enum values are preserved (not rejected) for forward compat

Most new gRPC services use proto3.

Q7: How does protobuf handle schema evolution in practice?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Real-world schema evolution strategy:

Step 1: Add new required fields as optional
  Don't add "required" fields (proto3 doesn't have them anyway).
  New fields should be optional with sensible defaults.

Step 2: Never delete — reserve instead
  message Order {
    // Old field removed, but reserve its number
    reserved 3;
    reserved "customer_name";  // won't be reused accidentally
  }

Step 3: Use API versioning for major breaking changes
  package com.example.order.v1;  → com.example.order.v2;
  
  Create a new v2 service alongside v1.
  Run both in parallel during migration.
  Deprecate v1 after clients migrate.

Step 4: Use buf for automated compatibility checks
  buf breaking --against '.git#branch=main'
  # CI/CD step that prevents breaking changes from merging

Step 5: Migration example
  v1: message Order { string status = 3; }
  v2: message Order { 
        reserved 3; reserved "status";  // old string removed
        OrderStatus status_enum = 6;    // new typed enum
      }
  
  // During transition: write both fields, read v1 until all clients updated
  // Then remove v1 field writes

Q8: Why can't you reuse a field number in protobuf?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The protobuf wire format has NO field names — only field numbers.
When a field is removed, old serialized data may still have that
field number in it.

Example of the danger:
  v1: message Order { int32 status = 3; }  // status as int
  // Remove field 3 (status)...
  v2: message Order { string new_field = 3; }  // reuse field 3!
  
  Now: old data has field 3 as a Varint (wire type 0)
       new code expects field 3 as Length-delimited (wire type 2)
       
       Result: parse error or silent data corruption!

The solution: use reserved to prevent reuse:
  message Order {
    reserved 3;  // never reuse this number
    reserved "status";  // never reuse this field name
  }

If another developer tries:
  message Order {
    string status = 3;  // ERROR: field 3 is reserved
    int32 old_field = 3;  // ERROR: cannot use reserved number
  }
Protoc will reject the .proto file at compile time.
