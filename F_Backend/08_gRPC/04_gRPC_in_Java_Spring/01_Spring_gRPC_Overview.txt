SPRING BOOT + gRPC - OVERVIEW AND SETUP
================================================================

----------------------------------------------------------------
1. WHY USE SPRING WITH gRPC?
----------------------------------------------------------------

gRPC is Java-framework-agnostic by design, but most Java backends
use Spring Boot. Integrating the two gives you:

  ✅ Dependency injection for gRPC service implementations
  ✅ Application context (datasources, repositories, configs)
  ✅ Spring Security integration for auth interceptors
  ✅ Micrometer metrics for gRPC calls
  ✅ Actuator health endpoints
  ✅ Configuration via application.yml
  ✅ Spring lifecycle (graceful shutdown)
  ✅ Test slices (@SpringBootTest, @GrpcTest)

Two popular integration libraries:
  1. grpc-spring-boot-starter (by LogNet / yidongnan)
     - Maven: net.devh:grpc-spring-boot-starter
     - Most widely used; annotation-driven
     
  2. spring-grpc (by Spring team — newer, Spring 6.x)
     - Maven: org.springframework.grpc:spring-grpc-spring-boot-autoconfigure
     - Official Spring project, available from Spring 3.3+

This guide primarily uses grpc-spring-boot-starter as it is most
commonly seen in interviews and production systems.

3. APPLICATION.YML CONFIGURATION
----------------------------------------------------------------

# ──────────────────────────────────────────────────────────────
# gRPC Server Configuration
# ──────────────────────────────────────────────────────────────
grpc:
  server:
    port: 9090          # default is 9090; use -1 to disable
    address: 0.0.0.0    # bind to all interfaces
    
    # TLS (see 04_Reliability_and_Security/02_TLS_and_Authentication.txt)
    security:
      enabled: false    # set to true for TLS
      certificate-chain: classpath:server.crt
      private-key: classpath:server.key
      
    # Max message sizes
    max-inbound-message-size: 4MB
    max-inbound-metadata-size: 8KB
    
    # Keep-alive
    keep-alive-time: 30s
    keep-alive-timeout: 5s
    permit-keep-alive-without-calls: true
    
    # Health service (grpc.health.v1)
    health-service-enabled: true
    
    # Reflection (allows grpcurl introspection)
    reflection:
      enabled: true

# ──────────────────────────────────────────────────────────────
# gRPC Client Configuration
# ──────────────────────────────────────────────────────────────
grpc:
  client:
    order-service:                  # name used in @GrpcClient("order-service")
      address: static://localhost:9090
      negotiation-type: plaintext   # or TLS
      deadline: 5000ms
      
    inventory-service:
      address: discovery:///inventory-service   # with Consul/Eureka
      negotiation-type: tls
      
    payment-service:
      address: dns:///payment.svc.cluster.local:9090
      negotiation-type: tls

5. AUTOCONFIGURATION WHAT GETS WIRED AUTOMATICALLY
----------------------------------------------------------------

grpc-spring-boot-starter autoconfigures:

SERVER SIDE:
  ✅ NettyServerBuilder with configured port/TLS
  ✅ All @GrpcService beans are registered as gRPC services
  ✅ All @GrpcGlobalServerInterceptor beans are added
  ✅ Graceful shutdown hook
  ✅ gRPC health check service (grpc.health.v1.Health)
  ✅ Server reflection service (if enabled)
  ✅ Metrics via Micrometer (if on classpath)

CLIENT SIDE:
  ✅ ManagedChannel created per client name in config
  ✅ Channels are managed (keep-alive, reconnect)
  ✅ @GrpcClient injects the appropriate channel/stub
  ✅ Shutdown of channels on application close

Nothing else needed — no manual NettyServerBuilder, no manual
channel creation in most cases.

6. HEALTH CHECKS
----------------------------------------------------------------

grpc-spring-boot-starter auto-registers the standard gRPC health service.

Accessing it:
  # Using grpcurl
  grpcurl -plaintext localhost:9090 grpc.health.v1.Health/Check

  # With a service name
  grpcurl -plaintext -d '{"service":"com.example.OrderService"}' \
    localhost:9090 grpc.health.v1.Health/Check

Custom health updates:
  @Component
  public class DatabaseHealthIndicator implements ApplicationListener<ContextRefreshedEvent> {
    
    private final HealthStatusManager healthStatusManager;
    private final DataSource dataSource;
    
    @Override
    public void onApplicationEvent(ContextRefreshedEvent event) {
      try (Connection c = dataSource.getConnection()) {
        healthStatusManager.setStatus(
            "com.example.OrderService",
            HealthCheckResponse.ServingStatus.SERVING);
      } catch (Exception e) {
        healthStatusManager.setStatus(
            "com.example.OrderService",
            HealthCheckResponse.ServingStatus.NOT_SERVING);
      }
    }
  }

7. ACTUATOR INTEGRATION
----------------------------------------------------------------

With spring-boot-actuator on classpath:

# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, info, metrics, grpc
  endpoint:
    health:
      show-details: always

Micrometer metrics (auto-registered when micrometer-core is present):
  grpc.server.calls.total{method="OrderService/CreateOrder", status="OK"}
  grpc.server.calls.total{method="OrderService/CreateOrder", status="INVALID_ARGUMENT"}
  grpc.server.timer{...}  ← p50, p95, p99 latencies

8. INTERVIEW KEY POINTS
----------------------------------------------------------------

Q: What does @GrpcService do vs a regular @Service?
A: @GrpcService is a Spring stereotype annotation (like @Service) that
   additionally tells grpc-spring-boot-starter to register the bean as
   a gRPC service with the Netty server. Under the hood, it's @Component
   + a marker that the autoconfiguration picks up to call
   serverBuilder.addService(yourBean). The bean still participates
   fully in Spring's DI container.

Q: How does grpc-spring-boot-starter start the gRPC server?
A: It uses a GrpcServerLifecycle bean (implements SmartLifecycle). On
   application startup, it builds a NettyServer with all @GrpcService
   beans, interceptors, and TLS config. On application shutdown,
   it calls server.shutdown() (graceful, waiting for in-flight RPCs)
   followed by server.awaitTermination().

Q: Can you run both HTTP/REST and gRPC on the same Spring Boot application?
A: Yes. The Netty gRPC server runs on a separate port (default 9090)
   from the Spring Boot embedded Tomcat/Netty HTTP server (default 8080).
   Both can run in the same JVM. Requests are routed by port. There is
   no conflict unless you try to run gRPC on the same port as HTTP/1.1.

Q: How do you configure different gRPC clients for different environments?
A: Use Spring profiles in application.yml:
     spring.profiles.active: prod
   And then:
     grpc.client.order-service.address: static://localhost:9090  # default
   With profile-specific overrides in application-prod.yml:
     grpc.client.order-service.address: dns:///order.internal:9090
