DEPENDENCY DECLARATION
───────────────────────
  dependencies {
      // Explicit version string
      implementation("com.google.guava:guava:32.1.3-jre")

      // Version catalog (modern approach)
      implementation(libs.google.guava)

      // Project dependency (subproject)
      implementation(project(":shared-utils"))

      // File dependency (local JAR)
      implementation(fileTree(mapOf("dir" to "libs", "include" to listOf("*.jar"))))

      // Module with classifier
      implementation("org.lwjgl:lwjgl:3.3.3:natives-linux")
  }

DEPENDENCY CONFIGURATIONS
─────────────────────────────────────────────────────────────────────────────────

  Configuration          Compiles  Packaged  Transitive  Description
  ─────────────────────  ────────  ────────  ──────────  ─────────────────────
  implementation         ✅        ✅        Hidden      Default; not exposed
  api                    ✅        ✅        Exposed     For library authors
  compileOnly            ✅        ❌        ❌          Provided at runtime
  runtimeOnly            ❌        ✅        Hidden      Runtime-only (drivers)
  testImplementation     ✅ test   ❌        Hidden      Test compile + runtime
  testCompileOnly        ✅ test   ❌        ❌          Test compile only
  testRuntimeOnly        ❌        ❌        Hidden      Test runtime only
  annotationProcessor    ✅ proc   ❌        ❌          APT (Lombok, MapStruct)

  Note: "api" configuration requires the "java-library" plugin, not "java":
  plugins { `java-library` }  // enables api configuration

  When to use each:
  • implementation  — your service/app's dependencies (default choice)
  • api             — library: types from this dep appear in your public API
  • compileOnly     — Lombok, Servlet API (provided by container)
  • runtimeOnly     — JDBC driver (code uses java.sql interfaces only)
  • testImplementation — JUnit, Mockito, TestContainers
  • annotationProcessor — Lombok, MapStruct, Dagger

TRANSITIVE DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  Viewing the dependency tree:
  ./gradlew dependencies                          # all configurations
  ./gradlew dependencies --configuration runtimeClasspath  # specific config
  ./gradlew :module:dependencies --configuration compileClasspath

  Example output:
  runtimeClasspath
  +--- org.springframework.boot:spring-boot-starter-web:3.2.0
  |    +--- org.springframework.boot:spring-boot-starter:3.2.0
  |    |    +--- org.springframework:spring-core:6.1.0
  |    |    \--- ...
  |    \--- org.springframework:spring-webmvc:6.1.0
  \--- com.fasterxml.jackson.core:jackson-databind:2.16.0

  (*) — dependency omitted (duplicate, higher version already selected)
  -> — version was resolved to a different version (conflict resolution)

CONFLICT RESOLUTION
─────────────────────────────────────────────────────────────────────────────────

  DEFAULT: Gradle picks the HIGHEST version requested in the graph.
  (Maven picks the NEAREST version — the one closest to the root.)

  Example: If A depends on guava:30.0 and B depends on guava:32.0,
  Gradle selects guava:32.0 automatically.

  To see why a version was selected:
  ./gradlew dependencyInsight --dependency guava --configuration runtimeClasspath

  Override version (force a specific version):
  ─────────────────────────────────────────────
  // Option 1: Force on specific dependency
  dependencies {
      implementation("com.google.guava:guava") {
          version { strictly("31.1-jre") }
      }
  }

  // Option 2: Force globally via resolutionStrategy
  configurations.all {
      resolutionStrategy {
          force("com.google.guava:guava:31.1-jre")
      }
  }

  // Option 3: Prefer (soft request — overridden by strict)
  dependencies {
      implementation("com.google.guava:guava") {
          version { prefer("31.1-jre") }
      }
  }

  Fail on version conflict (fail build instead of picking highest):
  ──────────────────────────────────────────────────────────────────
  configurations.all {
      resolutionStrategy {
          failOnVersionConflict()
      }
  }

EXCLUDING TRANSITIVE DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  // Exclude from a specific dependency
  dependencies {
      implementation("org.springframework.boot:spring-boot-starter-web") {
          exclude(group = "org.springframework.boot", module = "spring-boot-starter-tomcat")
      }
      implementation("org.springframework.boot:spring-boot-starter-undertow")
  }

  // Exclude globally from all configurations
  configurations.all {
      exclude(group = "commons-logging", module = "commons-logging")
  }

  // Exclude when using a project dependency
  dependencies {
      implementation(project(":shared")) {
          exclude(group = "org.old", module = "old-library")
      }
  }

DEPENDENCY CONSTRAINTS
─────────────────────────────────────────────────────────────────────────────────

  Constraints let you influence the version chosen for a transitive dependency
  WITHOUT adding it as a direct dependency:

  dependencies {
      constraints {
          // Require a minimum version for transitive
          implementation("com.google.guava:guava") {
              version { require("32.0-jre") }
              because("CVE fix requires 32.0+")
          }
          // Reject a vulnerable version range
          implementation("org.apache.logging.log4j:log4j-core") {
              version { reject("[2.0, 2.15)") }
              because("CVE-2021-44228 Log4Shell")
          }
      }
  }

PLATFORMS (GRADLE EQUIVALENT OF MAVEN BOM)
─────────────────────────────────────────────────────────────────────────────────

  Option 1 — Import a Maven BOM as a platform:
  ─────────────────────────────────────────────
  dependencies {
      implementation(platform("org.springframework.boot:spring-boot-dependencies:3.2.0"))
      implementation(platform("software.amazon.awssdk:bom:2.21.0"))

      // No version needed — BOM manages it
      implementation("org.springframework.boot:spring-boot-starter-web")
      implementation("software.amazon.awssdk:s3")
  }

  Option 2 — enforced platform (BOM versions override consumer's request):
  ──────────────────────────────────────────────────────────────────────────
  dependencies {
      implementation(enforcedPlatform("org.springframework.boot:spring-boot-dependencies:3.2.0"))
  }
  // Warning: enforcedPlatform downgrades are forced — use with caution

  Option 3 — Create your own Gradle platform:
  ─────────────────────────────────────────────
  // In a subproject's build.gradle.kts:
  plugins {
      `java-platform`
  }

  dependencies {
      constraints {
          api("com.google.guava:guava:32.1.3-jre")
          api("org.slf4j:slf4j-api:2.0.9")
      }
  }

  // Consume it:
  dependencies {
      implementation(platform(project(":my-platform")))
      implementation("com.google.guava:guava")  // version from platform
  }

DEPENDENCY LOCKING
─────────────────────────────────────────────────────────────────────────────────

  Problem: SNAPSHOT or dynamic versions (latest.release, 1.+) can change
  between builds — breaks reproducibility.
  Solution: Dependency locking records exact resolved versions in a lockfile.

  Enable locking:
  ─────────────────
  // build.gradle.kts
  dependencyLocking {
      lockAllConfigurations()
  }

  Generate lockfile (run once):
  ──────────────────────────────
  ./gradlew dependencies --write-locks

  This creates gradle/dependency-locks/*.lockfile with contents like:
  com.google.guava:guava:32.1.3-jre=compileClasspath,runtimeClasspath

  Commit the lockfile to version control.
  Now every build uses the exact same versions.

  Update lockfile (intentional upgrade):
  ────────────────────────────────────────
  ./gradlew dependencies --update-locks "com.google.guava:guava"
  ./gradlew dependencies --write-locks  # update all

─────────────────────────────────────────────────────────────────────────────────
DYNAMIC VERSIONS AND SNAPSHOT HANDLING
─────────────────────────────────────────────────────────────────────────────────

  // Dynamic versions (generally avoid in production):
  implementation("org.example:lib:1.+")         // Latest 1.x
  implementation("org.example:lib:latest.release") // Latest release

  // Snapshots
  implementation("org.example:lib:1.0-SNAPSHOT")

  // Control how often Gradle checks for updated dynamic versions:
  configurations.all {
      resolutionStrategy.cacheDynamicVersionsFor(24, TimeUnit.HOURS)
      resolutionStrategy.cacheChangingModulesFor(4, TimeUnit.HOURS)
  }

  // Force refresh (ignore cache):
  ./gradlew build --refresh-dependencies

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY VERIFICATION (CHECKSUM VERIFICATION)
─────────────────────────────────────────────────────────────────────────────────

  Gradle can verify the checksum of every resolved dependency against a
  trusted manifest — prevents supply chain attacks.

  Bootstrap verification metadata:
  ./gradlew --write-verification-metadata sha256 dependencies

  Creates: gradle/verification-metadata.xml
  Commit this file. Future builds fail if checksums don't match.

RESOLUTION STRATEGY PATTERNS
─────────────────────────────────────────────────────────────────────────────────

  configurations.all {
      resolutionStrategy {
          // Force all commons-logging to use SLF4J bridge
          dependencySubstitution {
              substitute(module("commons-logging:commons-logging"))
                  .using(module("org.slf4j:jcl-over-slf4j:2.0.9"))
          }

          // Fail if using a dynamic version
          failOnDynamicVersions()

          // Fail if using a changing version (SNAPSHOT)
          failOnChangingVersions()

          // Force a version
          force("org.yaml:snakeyaml:2.0")
      }
  }

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: How does Gradle resolve version conflicts?
A: Gradle picks the highest requested version (unlike Maven which picks nearest).
   You can override this with resolutionStrategy.force() for a specific version,
   or use strictly() on a dependency to require an exact version. Use
   failOnVersionConflict() to detect conflicts explicitly during CI.

Q: What is the difference between platform() and enforcedPlatform() in Gradle?
A: platform() imports a BOM but allows the consumer to override individual versions
   (the platform provides recommendations, not mandates). enforcedPlatform() forces
   all versions from the BOM, even downgrading if necessary. Gradle recommends
   platform() — use enforcedPlatform() only when strict consistency is needed.

Q: What is Gradle dependency locking and why use it?
A: Dependency locking records exact resolved versions in lockfiles and enforces
   them on subsequent builds. This makes builds reproducible — even if the remote
   repository changes (SNAPSHOT updated, dynamic version resolves differently).
   Essential for production applications. The lockfile is committed to source control.

Q: How do you exclude a transitive dependency in Gradle?
A: Either on a per-dependency basis:
     implementation("group:artifact") { exclude(group="...", module="...") }
   Or globally from all configurations:
     configurations.all { exclude(group="...", module="...") }

Q: What is the difference between "implementation" and "api" in Gradle?
A: Both are compile + runtime classpath. "api" exposes the dependency transitively
   to consumers (they see it at compile time). "implementation" hides it — consumers
   only have it at runtime. Use "api" sparingly (only when your public API exposes
   types from that dependency). Requires the java-library plugin to use "api".
