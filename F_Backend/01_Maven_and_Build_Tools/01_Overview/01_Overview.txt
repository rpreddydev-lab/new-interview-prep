WHAT IS A BUILD TOOL?
─────────────────────
A build tool automates the process of transforming source code into a deployable
artifact. It handles:
  • Compilation     – converting .java → .class files
  • Testing         – running unit / integration tests
  • Packaging       – assembling JAR / WAR / EAR artifacts
  • Dependency management – downloading and linking third-party libraries
  • Deployment      – publishing artifacts to a repository or server
  • Code quality    – running static analysis, coverage, linting

Without a build tool, developers would have to run javac manually, set classpaths
by hand, track library versions in spreadsheets, and copy JARs around. Build tools
eliminate all that toil.

─────────────────────────────────────────────────────────────────────────────────
THE BIG THREE IN THE JAVA ECOSYSTEM
─────────────────────────────────────────────────────────────────────────────────

1. Apache Ant (2000)
   ─────────────────
   • XML-based scripting tool (build.xml)
   • Procedural: you define WHAT to do and HOW to do it step by step
   • No built-in dependency management (used Ivy as an add-on)
   • Very flexible, but verbose and hard to maintain for large projects
   • Still found in legacy enterprise codebases
   • Key concept: "tasks" (compile, copy, jar, etc.)

2. Apache Maven (2004)
   ────────────────────
   • XML-based, convention-over-configuration
   • Declarative: you describe WHAT you want; Maven decides HOW
   • First-class dependency management via pom.xml + Maven Central
   • Strict project structure (src/main/java, src/test/java, etc.)
   • Fixed lifecycle phases (validate → compile → test → package → ...)
   • Most widely used Java build tool in enterprise environments
   • Key files: pom.xml, settings.xml, .m2/ local repository

3. Gradle (2012)
   ──────────────
   • Groovy/Kotlin DSL-based (build.gradle / build.gradle.kts)
   • Hybrid: convention-over-configuration + fine-grained customisation
   • Incremental builds, build cache → much faster than Maven for large projects
   • Default build tool for Android (Google's choice)
   • Gaining adoption in Spring, Quarkus, and microservice stacks
   • Key files: build.gradle, settings.gradle, gradle.properties

─────────────────────────────────────────────────────────────────────────────────
WHY MAVEN DOMINATES ENTERPRISE JAVA
─────────────────────────────────────────────────────────────────────────────────
  ✔ Maven Central – the world's largest public artifact repository (~10M artifacts)
  ✔ Standardised directory layout understood by every IDE
  ✔ Predictable lifecycle that CI/CD pipelines can rely on
  ✔ Rich plugin ecosystem (Surefire, Failsafe, Shade, Spring Boot, etc.)
  ✔ BOM (Bill of Materials) makes version management in large orgs trivial
  ✔ Deep Spring Boot integration – Spring Initializr generates pom.xml by default

─────────────────────────────────────────────────────────────────────────────────
MAVEN STANDARD DIRECTORY LAYOUT
─────────────────────────────────────────────────────────────────────────────────

  project-root/
  ├── pom.xml                        ← Project Object Model (the heart of Maven)
  ├── src/
  │   ├── main/
  │   │   ├── java/                  ← production source code
  │   │   ├── resources/             ← production resources (application.properties, etc.)
  │   │   └── webapp/                ← web application content (WAR projects)
  │   └── test/
  │       ├── java/                  ← test source code
  │       └── resources/             ← test resources
  └── target/                        ← generated output (never commit this!)
      ├── classes/                   ← compiled .class files
      ├── test-classes/
      ├── surefire-reports/          ← test reports
      └── myapp-1.0.0.jar            ← final artifact

Following this layout means zero configuration for compilation, testing, and
packaging — Maven "knows" where to find things.

─────────────────────────────────────────────────────────────────────────────────
KEY CONCEPTS (QUICK REFERENCE)
─────────────────────────────────────────────────────────────────────────────────

  Concept              Description
  ──────────────────── ─────────────────────────────────────────────────────────
  POM                  Project Object Model — XML descriptor for a project
  GAV Coordinates      groupId:artifactId:version — uniquely identifies an artifact
  Repository           Storage for artifacts (local ~/.m2, remote Maven Central)
  Plugin               Provides goals that implement lifecycle phases
  Goal                 A single unit of work (e.g., compiler:compile, surefire:test)
  Phase                A named step in the build lifecycle
  Lifecycle            Ordered sequence of phases (default, clean, site)
  Dependency Scope     When a dependency is on the classpath (compile, test, runtime...)
  SNAPSHOT             Mutable development version (1.0.0-SNAPSHOT)
  Release              Immutable production version (1.0.0)
  BOM                  Bill of Materials — centralises version management
  Wrapper (mvnw)       Embeds a specific Maven version in the project repo
  Profile              Conditional build configuration activated by env/property

─────────────────────────────────────────────────────────────────────────────────
MAVEN LIFECYCLE OVERVIEW (default lifecycle)
─────────────────────────────────────────────────────────────────────────────────

  validate   → Validates the project structure is correct
  initialize → Initialises build state (e.g., set properties)
  compile    → Compiles source code
  test       → Runs unit tests
  package    → Creates the artifact (JAR/WAR/EAR)
  verify     → Runs integration tests and checks
  install    → Installs artifact to local ~/.m2 repo
  deploy     → Copies artifact to remote repository

Each later phase automatically runs all earlier phases.
"mvn package" runs validate→initialize→compile→test→package.

─────────────────────────────────────────────────────────────────────────────────
COMMON MAVEN COMMANDS
─────────────────────────────────────────────────────────────────────────────────

  mvn clean                      Delete target/ directory
  mvn compile                    Compile main sources
  mvn test                       Compile + run tests
  mvn package                    Compile + test + create JAR/WAR
  mvn verify                     Compile + test + integration test + verify
  mvn install                    package + install to local repo
  mvn deploy                     install + upload to remote repo
  mvn clean install              Most common CI command
  mvn clean install -DskipTests  Skip test execution (not recommended in prod CI)
  mvn dependency:tree            Show full dependency tree
  mvn dependency:analyze         Find unused/undeclared dependencies
  mvn help:effective-pom         Show the merged/effective POM
  mvn versions:display-dependency-updates  Show available dependency upgrades

INTERVIEW QUICK-HITS ON OVERVIEW
─────────────────────────────────────────────────────────────────────────────────

Q: What is Maven and why is it used?
A: Maven is a build automation and dependency management tool for Java projects.
   It uses a declarative XML file (pom.xml) and a convention-over-configuration
   approach to standardise how Java projects are built, tested, and deployed.

Q: What are the three lifecycles in Maven?
A: 1. default (or build) – handles compilation, testing, packaging, deployment
   2. clean – handles deleting old build output (target/)
   3. site – handles generating project documentation

Q: What is the difference between a plugin goal and a lifecycle phase?
A: A phase (e.g., compile) is a named step in a lifecycle. A goal (e.g.,
   compiler:compile) is the actual unit of work provided by a plugin. Phases
   are bound to goals — when a phase executes, it triggers the bound goals.

Q: What is GAV?
A: GroupId:ArtifactId:Version — the three coordinates that uniquely identify
   every Maven artifact. Example: org.springframework.boot:spring-boot-starter:3.2.0

Q: What is the local repository?
A: ~/.m2/repository — a local cache of all downloaded artifacts. Maven checks
   here before reaching out to remote repositories, speeding up builds.
