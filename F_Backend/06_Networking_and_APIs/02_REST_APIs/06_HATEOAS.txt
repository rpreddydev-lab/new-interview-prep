================================================================================
HATEOAS — HYPERMEDIA AS THE ENGINE OF APPLICATION STATE
================================================================================

DEFINITION
-----------
HATEOAS is the final REST constraint (Level 3 of Richardson Maturity Model).
It requires that a REST client interact with a network application entirely
through hypermedia provided dynamically by application servers.

The client enters the application through a single fixed URL.
All future actions the client may take are discovered dynamically from
hypermedia links included in the server's responses.

"The client should need no prior knowledge about how to interact with
an application beyond a generic understanding of hypermedia."
— Roy Fielding

================================================================================
1. THE CORE IDEA
================================================================================

WITHOUT HATEOAS (Level 2 API):
  Client knows EVERY endpoint by reading API documentation.
  If server changes a URL, client breaks.
  Client hardcodes: POST https://api.example.com/v1/orders/42/cancel

WITH HATEOAS (Level 3 API):
  Client starts at root endpoint.
  Server provides links for all available actions.
  Client follows links; doesn't hardcode URLs.
  Server can change URLs; clients follow new links.

ANALOGY:
  Web browsing is the perfect HATEOAS example:
  - You start at google.com (single entry point)
  - Click links to navigate (discover URLs dynamically)
  - You never hardcode URLs — you follow links
  - Google can change its URL structure; links still work

REST APIs should work the same way.

================================================================================
2. WHAT HYPERMEDIA LOOKS LIKE
================================================================================

EXAMPLE — Order resource with HATEOAS links:

  GET /orders/42
  → 200 OK
  {
    "id": 42,
    "status": "PENDING",
    "total": 150.00,
    "createdAt": "2026-04-08T10:00:00Z",
    "_links": {
      "self":    { "href": "/orders/42",        "method": "GET"    },
      "cancel":  { "href": "/orders/42/cancel", "method": "POST"   },
      "payment": { "href": "/orders/42/payment","method": "POST"   },
      "items":   { "href": "/orders/42/items",  "method": "GET"    },
      "customer":{ "href": "/customers/7",      "method": "GET"    }
    }
  }

After cancellation, the server returns different links:

  POST /orders/42/cancel
  → 200 OK
  {
    "id": 42,
    "status": "CANCELLED",
    "_links": {
      "self":   { "href": "/orders/42",    "method": "GET"    },
      "refund": { "href": "/orders/42/refund", "method": "POST" }
    }
  }
  
  NOTE: "cancel" and "payment" links are GONE because order is cancelled.
        "refund" link appears because it's now a valid action.

LINKS REFLECT AVAILABLE ACTIONS AT CURRENT STATE:
  State: PENDING    → links: cancel, payment
  State: CONFIRMED  → links: ship, cancel
  State: SHIPPED    → links: track
  State: DELIVERED  → links: return, review
  State: CANCELLED  → links: refund

This is "application state driven by hypermedia" — the title of the concept.

================================================================================
3. HYPERMEDIA FORMATS
================================================================================

HAL (Hypertext Application Language) — Most Common
  - _links for link relations
  - _embedded for embedded sub-resources
  - Media type: application/hal+json

  {
    "id": 42,
    "name": "Alice",
    "_links": {
      "self":   { "href": "/users/42" },
      "orders": { "href": "/users/42/orders" },
      "update": { "href": "/users/42", "method": "PUT" },
      "delete": { "href": "/users/42", "method": "DELETE" }
    },
    "_embedded": {
      "latestOrder": {
        "id": 99,
        "status": "shipped",
        "_links": {
          "self": { "href": "/orders/99" }
        }
      }
    }
  }

JSON-LD (JSON Linked Data)
  - W3C standard; used by Google for structured data
  - @context, @id, @type for semantic meaning
  - More complex; used in semantic web / knowledge graphs

  {
    "@context": "http://schema.org",
    "@type": "Order",
    "@id": "/orders/42",
    "orderNumber": 42,
    "orderStatus": "OrderProcessing"
  }

Siren
  - Entities, actions (with fields), links
  - More explicit about actions and their input schemas
  
  {
    "class": ["order"],
    "properties": { "id": 42, "status": "PENDING" },
    "entities": [...],
    "actions": [
      {
        "name": "cancel-order",
        "method": "POST",
        "href": "/orders/42/cancel",
        "fields": [{ "name": "reason", "type": "text" }]
      }
    ],
    "links": [
      { "rel": ["self"], "href": "/orders/42" }
    ]
  }

Collection+JSON
  - Specifically for collection resources
  - Items, queries, template for creating new items

4. LINK RELATIONS
================================================================================

IANA REGISTERED LINK RELATIONS (Standard):
  self       : Link to current resource
  next       : Next page in collection
  prev       : Previous page in collection
  first      : First page in collection
  last       : Last page in collection
  related    : Related resource
  edit       : URI to edit this resource
  alternate  : Alternate representation
  collection : The collection this item belongs to
  item       : An item in a collection
  up         : Parent resource in hierarchy
  describedby: URI of documentation

CUSTOM LINK RELATIONS:
  Use absolute URI to avoid collision:
  "https://api.example.com/rels/cancel-order"

5. SPRING HATEOAS
================================================================================

DEPENDENCY:
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-hateoas</artifactId>
  </dependency>

BASIC HATEOAS RESPONSE:

  @RestController
  @RequestMapping("/users")
  public class UserController {

      @GetMapping("/{id}")
      public EntityModel<User> getUser(@PathVariable Long id) {
          User user = userService.findById(id);
          
          return EntityModel.of(user,
              // Self link
              linkTo(methodOn(UserController.class).getUser(id)).withSelfRel(),
              // Collection link
              linkTo(methodOn(UserController.class).getAllUsers()).withRel("users"),
              // Related resource
              linkTo(methodOn(OrderController.class).getUserOrders(id)).withRel("orders")
          );
      }

      @GetMapping
      public CollectionModel<EntityModel<User>> getAllUsers() {
          List<EntityModel<User>> users = userService.findAll().stream()
              .map(user -> EntityModel.of(user,
                  linkTo(methodOn(UserController.class).getUser(user.getId())).withSelfRel()
              ))
              .collect(Collectors.toList());
          
          return CollectionModel.of(users,
              linkTo(methodOn(UserController.class).getAllUsers()).withSelfRel()
          );
      }
  }

OUTPUT:
  {
    "id": 42,
    "name": "Alice",
    "_links": {
      "self":   { "href": "http://localhost:8080/users/42" },
      "users":  { "href": "http://localhost:8080/users"   },
      "orders": { "href": "http://localhost:8080/users/42/orders" }
    }
  }

REPREPRESENTATION MODEL (inheritance approach):
  public class UserModel extends RepresentationModel<UserModel> {
      private Long id;
      private String name;
      // getters/setters
  }

  UserModel model = new UserModel();
  model.setId(user.getId());
  model.add(linkTo(methodOn(UserController.class).getUser(id)).withSelfRel());

PAGINATION LINKS:
  @GetMapping
  public PagedModel<EntityModel<User>> getAllUsers(Pageable pageable) {
      Page<User> page = userService.findAll(pageable);
      return pagedResourcesAssembler.toModel(page, userModelAssembler);
  }

  Output includes:
  "_links": {
    "first": { "href": "/users?page=0&size=20" },
    "prev":  { "href": "/users?page=0&size=20" },
    "self":  { "href": "/users?page=1&size=20" },
    "next":  { "href": "/users?page=2&size=20" },
    "last":  { "href": "/users?page=9&size=20" }
  }

6. STATE MACHINE + HATEOAS
================================================================================

HATEOAS SHINES in resources that have state machines.
Links reflect ONLY valid actions for CURRENT state.

ORDER STATE MACHINE:
  DRAFT → PENDING → CONFIRMED → SHIPPED → DELIVERED
                 ↘ CANCELLED ← ─────────┘

  State: DRAFT
  Links: submit, delete

  State: PENDING
  Links: confirm, cancel

  State: CONFIRMED
  Links: ship, cancel

  State: SHIPPED
  Links: deliver, track
  (No longer cancellable)

  State: DELIVERED
  Links: return, review, reorder

JAVA STATE-DRIVEN LINK GENERATION:
  public EntityModel<Order> toModel(Order order) {
      List<Link> links = new ArrayList<>();
      links.add(linkTo(methodOn(OrderController.class).getOrder(order.getId())).withSelfRel());
      
      switch (order.getStatus()) {
          case DRAFT:
              links.add(linkTo(methodOn(OrderController.class).submitOrder(order.getId())).withRel("submit"));
              links.add(linkTo(methodOn(OrderController.class).deleteOrder(order.getId())).withRel("delete"));
              break;
          case PENDING:
              links.add(linkTo(methodOn(OrderController.class).confirmOrder(order.getId())).withRel("confirm"));
              links.add(linkTo(methodOn(OrderController.class).cancelOrder(order.getId())).withRel("cancel"));
              break;
          case CONFIRMED:
              links.add(linkTo(methodOn(OrderController.class).shipOrder(order.getId())).withRel("ship"));
              break;
          case SHIPPED:
              links.add(linkTo(methodOn(OrderController.class).deliverOrder(order.getId())).withRel("deliver"));
              break;
      }
      
      return EntityModel.of(order, links);
  }

7. HATEOAS IN PRACTICE — HONEST ASSESSMENT
================================================================================

WHY IT'S NOT WIDELY ADOPTED:
  1. Clients still read API docs / OpenAPI specs — don't follow links dynamically
  2. Most clients are written against specific API versions, not "discovered"
  3. Increases response size (bandwidth cost)
  4. Complex to implement and maintain (link generation logic)
  5. Client-side link parsing adds complexity
  6. Changes to URL structure still break clients if they cache links across sessions

WHERE IT ADDS VALUE:
  1. Long-lived, stable API contracts (public APIs)
  2. State machine resources (orders, workflows, tickets)
  3. Pagination (next/prev links are widely adopted even without full HATEOAS)
  4. Embedded resource navigation
  5. APIs with many complex state transitions

PRAGMATIC APPROACH (What most teams do):
  - Implement pagination links (next, prev, first, last) — universally useful
  - Use OpenAPI/Swagger for API discovery
  - Add self links to responses
  - Optionally add state-driven action links for workflow resources

================================================================================
8. INTERVIEW QUESTIONS — HATEOAS
================================================================================

Q1: What is HATEOAS and what problem does it solve?
    Hypermedia as the Engine of Application State. Server embeds links to
    available next actions in responses. Solves the tight coupling between
    client and server URLs — client follows links instead of hardcoding URIs.
    If server changes URLs, links update and clients adapt without code changes.

Q2: Why is HATEOAS rarely fully implemented in practice?
    Clients typically read OpenAPI/Swagger docs and hardcode URLs. Full HATEOAS
    requires clients to parse links dynamically — complex and rarely done.
    Adds response size overhead. Teams usually settle at Level 2 (HTTP verbs)
    and use documentation for discovery. Pagination links are a common partial
    HATEOAS adoption.

Q3: How does Spring HATEOAS work?
    Spring HATEOAS provides EntityModel, CollectionModel, PagedModel wrappers
    and WebMvcLinkBuilder for type-safe link generation using methodOn().
    Links are added to response objects and serialized as _links in HAL format.
    The spring-boot-starter-hateoas dependency configures HAL automatically.

Q4: How does HATEOAS relate to state machines?
    HATEOAS naturally models resources with state machines. The links in the
    response reflect ONLY the valid transitions from current state. A PENDING
    order includes cancel/confirm links; a SHIPPED order does not include cancel.
    This prevents invalid state transitions and makes the API self-documenting.

Q5: What's the difference between HAL and JSON-LD?
    HAL is a simple hypermedia format with _links and _embedded; lightweight and
    widely adopted in REST APIs. JSON-LD is a W3C standard for Linked Data
    with @context, @id, @type for semantic meaning; used in knowledge graphs
    and Google structured data; more complex but richer semantic capabilities.
