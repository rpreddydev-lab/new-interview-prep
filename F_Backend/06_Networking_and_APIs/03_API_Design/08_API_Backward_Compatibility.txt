API BACKWARD COMPATIBILITY
===========================

=== WHY BACKWARD COMPATIBILITY MATTERS ===

APIs are contracts. Clients depend on them.
Breaking changes = client failures, deployment coordination nightmares.

In microservices: multiple services call your API.
Breaking a contract can cause:
  - Dependent services failing at runtime
  - Cascading failures
  - Emergency rollbacks and incidents

Goal: existing clients continue working without code changes when API evolves.

=== WHAT IS A BREAKING CHANGE? ===

Breaking (NON-backward-compatible):
  - Removing a field from response
  - Renaming a field (orderId → id)
  - Changing a field's type (String → Integer)
  - Removing a required request field (breaking clients that send it)
  - Adding a REQUIRED request field (breaks clients that don't send it)
  - Changing HTTP method (POST → PUT)
  - Changing status codes (200 → 201 for same operation)
  - Changing URL structure (/users/{id} → /accounts/{id})
  - Removing an endpoint entirely

Non-breaking (backward-compatible / additive):
  - Adding new OPTIONAL fields to response
  - Adding new OPTIONAL request parameters
  - Adding new endpoints
  - Adding new enum values (usually — clients should handle unknown values)
  - Deprecating (marking as deprecated without removing)
  - Adding new HTTP methods to same resource

=== STRATEGIES FOR BACKWARD COMPATIBILITY ===

1. ADDITIVE CHANGES ONLY (preferred)
   Never remove or change existing fields.
   Only add new optional fields.
   Clients that don't know about new fields simply ignore them.

   Old response:        New response:
   { "name": "Alice" }  { "name": "Alice", "email": "alice@ex.com" }

   Both old and new clients can handle this.

2. DEPRECATION CYCLE
   Phase 1: Mark old field/endpoint as deprecated.
     - Response header: Deprecation: true, Sunset: Sat, 01 Jun 2025 00:00:00 GMT
     - API docs updated
     - Email/notify API consumers

   Phase 2: Keep deprecated items working for a grace period (3-12 months).

   Phase 3: Remove deprecated items after all clients have migrated.

3. FIELD ALIASING
   Keep old field AND add new field (both point to same data):
   {
     "userId": 123,         // old (deprecated but still works)
     "customerId": 123      // new preferred field
   }

4. DEFAULT VALUES FOR NEW REQUIRED FIELDS
   If adding a required field, add it as optional with a sensible default:
   // Old: process(String action)
   // New: process(String action, String mode = "STANDARD")
   New clients pass mode, old clients don't → default applies.

=== API VERSIONING STRATEGIES ===

When backward compatibility is impossible, version the API.

1. URI VERSIONING (most common)
   /api/v1/users
   /api/v2/users
   Clear, explicit, cacheable.
   Cons: URL proliferation, clients must update URLs.

2. HEADER VERSIONING
   GET /api/users
   Accept: application/vnd.company.v2+json
   or: API-Version: 2
   Clean URLs, harder to test/share URLs.

3. QUERY PARAMETER VERSIONING
   GET /api/users?version=2
   Easy to test, but pollutes URL params.

4. CONTENT NEGOTIATION (Accept header)
   Accept: application/vnd.myapi.v2+json
   REST-purist approach, harder to implement.

Spring implementation of URI versioning:
  @RestController
  @RequestMapping("/api")
  public class UserController {

      @GetMapping("/v1/users/{id}")
      public UserV1Response getUserV1(@PathVariable Long id) { ... }

      @GetMapping("/v2/users/{id}")
      public UserV2Response getUserV2(@PathVariable Long id) { ... }
  }

=== CONSUMER-DRIVEN CONTRACT TESTING ===

Pact framework: consumers define the contract, providers verify it.
  1. Consumer writes Pact test → generates pact file (JSON contract)
  2. Provider verifies against pact file
  3. If provider breaks the contract → CI fails before deployment

This prevents breaking changes from reaching consumers.

=== TOLERANT READER PATTERN ===

Clients should be written to tolerate API changes:
  - Ignore unknown fields (Jackson does this by default)
  - Don't use strict response validation (only validate what you need)
  - Handle unexpected enum values gracefully

Jackson configuration:
  @JsonIgnoreProperties(ignoreUnknown = true) // on DTO class
  // or globally:
  mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);

=== EVOLVE API EXAMPLE ===

Scenario: Change "name" to separate "firstName" + "lastName"

Step 1 (backward-compatible — additive):
  {
    "name": "Alice Smith",     // kept for backward compat
    "firstName": "Alice",      // new
    "lastName": "Smith"        // new
  }

Step 2 (deprecation period):
  Mark "name" as deprecated in docs and with Deprecation header.
  Notify all API consumers to use firstName/lastName.

Step 3 (after grace period):
  Release new major version (v2) that drops "name".
  Keep v1 alive during transition, eventually sunset.

=== SUNSET HEADER ===

RFC 8594: Sunset HTTP response header for deprecation date.

HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Jun 2025 00:00:00 GMT
Link: <https://api.example.com/v2/users>; rel="successor-version"

Spring implementation:
  @GetMapping("/v1/users/{id}")
  public ResponseEntity<UserResponse> getUser(@PathVariable Long id) {
      return ResponseEntity.ok()
          .header("Deprecation", "true")
          .header("Sunset", "Sat, 01 Jun 2025 00:00:00 GMT")
          .header("Link", "<https://api.example.com/v2/users/" + id +
                  ">; rel=\"successor-version\"")
          .body(userService.getUserV1(id));
  }
