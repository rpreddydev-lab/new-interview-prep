================================================================
MOCKITO — ANNOTATIONS
@Mock, @Spy, @InjectMocks, @Captor, @MockBean, @SpyBean
Complete Interview Preparation Guide
================================================================

1. OVERVIEW — WHY ANNOTATIONS?
================================================================

Annotations eliminate boilerplate from:
  // Without annotations:
  UserRepository userRepository = Mockito.mock(UserRepository.class);
  EmailService emailService = Mockito.mock(EmailService.class);
  ArgumentCaptor<User> captor = ArgumentCaptor.forClass(User.class);
  UserService userService = new UserService(userRepository, emailService);
  
  // With annotations:
  @Mock UserRepository userRepository;
  @Mock EmailService emailService;
  @Captor ArgumentCaptor<User> captor;
  @InjectMocks UserService userService;

Annotations are processed by:
  1. @ExtendWith(MockitoExtension.class)  ← JUnit 5 (preferred)
  2. MockitoAnnotations.openMocks(this)  ← Manual (any test framework)
  3. @RunWith(MockitoJUnitRunner.class)  ← JUnit 4 (legacy)

================================================================
2. @Mock
================================================================

Creates a Mockito mock for the annotated field.
All methods return default values unless stubbed.

  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      
      @Mock OrderRepository orderRepository;
      @Mock PaymentGateway paymentGateway;
      @Mock EmailService emailService;
      
      // All three are fresh mocks for each test (PER_METHOD lifecycle)
  }

OPTIONS on @Mock:
  @Mock(name = "primaryRepo")
  OrderRepository orderRepository;
  // Sets the mock's name — useful in error messages
  
  @Mock(answer = Answers.RETURNS_DEEP_STUBS)
  OrderService orderService;
  // Sets the default answer strategy
  
  @Mock(strictness = Mock.Strictness.LENIENT)
  ExternalService externalService;
  // Per-mock strictness override (Mockito 4+)

STRICTNESS — controlling how strict a mock is:
  // Class level (default: STRICT_STUBS with MockitoExtension)
  @MockitoSettings(strictness = Strictness.LENIENT)
  class PaymentServiceTest { ... }
  
  // Method level — mark individual stubs lenient
  lenient().when(repo.findById(anyString())).thenReturn(Optional.empty());

3. @Spy
================================================================

Creates a Mockito spy wrapping a REAL object.

  @ExtendWith(MockitoExtension.class)
  class AuditServiceTest {
      
      @Spy
      AuditLogger auditLogger = new AuditLogger(new FileAuditStorage("/tmp/audit"));
      // ^ Must provide the instance (real object)
      
      @Spy
      List<String> spyList = new ArrayList<>();
      // Works for standard library classes too
  }

NO-ARG CONSTRUCTOR shortcut:
  @Spy
  OrderProcessor orderProcessor;  // Mockito will call new OrderProcessor()
  // ONLY works if the class has a public no-arg constructor

COMMON USAGE WITH InjectMocks:
  @Spy
  PasswordEncoder passwordEncoder = new BCryptPasswordEncoder();
  
  @InjectMocks
  UserService userService;
  // UserService gets the real BCryptPasswordEncoder injected as a spy

OVERRIDING METHODS ON @Spy:
  @Test
  void shouldUseRealLogicExceptSmtp() {
      doNothing().when(auditLogger).flushToDisk();   // override disk I/O
      doReturn(true).when(auditLogger).isEnabled();  // override config check
      
      auditLogger.log("CREATE", "user-1");  // real log() method runs
      
      verify(auditLogger).log("CREATE", "user-1");
      verify(auditLogger, never()).flushToDisk();  // overridden — never called
  }

4. @InjectMocks
================================================================

Creates an instance of the class under test and INJECTS mocks/spies
into it automatically.

  @InjectMocks UserService userService;
  // Creates new UserService() and injects @Mock/@Spy fields

INJECTION STRATEGIES (tried in order):
  1. Constructor injection — largest constructor whose parameters match
  2. Setter injection — setters that match mock types
  3. Field injection — direct field assignment via reflection

CONSTRUCTOR INJECTION (preferred):
  // Production code:
  public class UserService {
      private final UserRepository userRepository;
      private final EmailService emailService;
      
      public UserService(UserRepository userRepository, EmailService emailService) {
          this.userRepository = userRepository;
          this.emailService = emailService;
      }
  }
  
  // Test code:
  @Mock UserRepository userRepository;
  @Mock EmailService emailService;
  @InjectMocks UserService userService;
  // → UserService(userRepository, emailService) called automatically

FIELD INJECTION (less desirable production design but works):
  // Production code uses @Autowired on field:
  @Service
  public class UserService {
      @Autowired
      private UserRepository userRepository;
  }
  
  // Test: @InjectMocks sets field directly via reflection

IMPORTANT CAVEATS:
  ❌ @InjectMocks does NOT call @PostConstruct
  ❌ @InjectMocks fails SILENTLY if injection fails (no exception)
     → Always verify the mock was actually injected (check it's not null)
  ❌ Cannot inject into final fields
  ❌ Does NOT work with static dependencies

VERIFICATION THAT INJECTION WORKED:
  @BeforeEach
  void setUp() {
      // If using openMocks manually:
      MockitoAnnotations.openMocks(this);
      
      // Verify injection actually happened:
      assertNotNull(userService);
  }

ALTERNATIVE — manual construction (more explicit):
  @BeforeEach
  void setUp() {
      userService = new UserService(userRepository, emailService, clock);
      // Constructor injection — dependencies are explicit
  }

5. @Captor
================================================================

Shorthand for ArgumentCaptor creation.

  @Captor ArgumentCaptor<User> userCaptor;
  @Captor ArgumentCaptor<List<Order>> orderListCaptor;  // handles generic types
  
  @Test
  void testCapture() {
      service.process(data);
      
      verify(repository).save(userCaptor.capture());
      User captured = userCaptor.getValue();
      
      assertEquals("alice@test.com", captured.getEmail());
  }

TYPE-SAFE GENERIC CAPTORS:
  // @Captor avoids unchecked warnings for generic types:
  @Captor ArgumentCaptor<Map<String, Object>> mapCaptor;  // clean
  
  // vs programmatic (needs @SuppressWarnings):
  @SuppressWarnings("unchecked")
  ArgumentCaptor<Map<String, Object>> mapCaptor = 
      (ArgumentCaptor) ArgumentCaptor.forClass(Map.class);

6. INITIALIZATION STRATEGIES
================================================================

STRATEGY 1: @ExtendWith(MockitoExtension.class) — PREFERRED for JUnit 5
  @ExtendWith(MockitoExtension.class)
  class UserServiceTest {
      @Mock UserRepository userRepository;
      @Spy AuditLogger auditLogger = new AuditLogger();
      @Captor ArgumentCaptor<User> captor;
      @InjectMocks UserService userService;
      
      // All initialized before each test, torn down after
      // STRICT_STUBS enabled by default
  }

STRATEGY 2: MockitoAnnotations.openMocks(this) — manual init
  class UserServiceTest {
      @Mock UserRepository userRepository;
      @InjectMocks UserService userService;
      
      private AutoCloseable closeable;
      
      @BeforeEach
      void setUp() {
          closeable = MockitoAnnotations.openMocks(this);
      }
      
      @AfterEach
      void tearDown() throws Exception {
          closeable.close();  // cleans up to avoid memory leaks
      }
  }
  
  // Use when: 
  // - JUnit 4 (but have @RunWith(MockitoJUnitRunner.class) instead)
  // - TestNG
  // - Integrating Mockito into non-JUnit tests

STRATEGY 3: Programmatic (no annotations)
  class UserServiceTest {
      UserRepository userRepository;
      UserService userService;
      
      @BeforeEach
      void setUp() {
          userRepository = Mockito.mock(UserRepository.class);
          userService = new UserService(userRepository);
      }
  }
  
  // Use when:
  // - You want explicit, readable test setup
  // - @InjectMocks would be ambiguous (multiple constructors)
  // - Building parameterized setups

7. @MockBean and @SpyBean — SPRING SPECIFIC
================================================================

These are Spring Boot Test annotations, NOT Mockito annotations.
They work with the Spring ApplicationContext.

@MockBean:
  - Adds a Mockito mock to the Spring ApplicationContext
  - Replaces any existing bean of that type
  - Used in @SpringBootTest, @WebMvcTest, @DataJpaTest
  
  @SpringBootTest
  class UserControllerIntegrationTest {
      
      @Autowired MockMvc mockMvc;
      
      @MockBean UserService userService;   // replaces real UserService in context
      @MockBean EmailService emailService; // replaces real EmailService in context
      
      @Test
      void shouldReturnUser() throws Exception {
          when(userService.findById("user-1")).thenReturn(testUser);
          
          mockMvc.perform(get("/users/user-1"))
              .andExpect(status().isOk())
              .andExpect(jsonPath("$.id").value("user-1"));
      }
  }

@SpyBean:
  - Wraps an EXISTING Spring bean with a Mockito spy
  - Real implementation runs by default
  - You can stub specific methods
  
  @SpringBootTest
  class AuditServiceTest {
      
      @SpyBean AuditService auditService;  // wraps real bean
      
      @Test
      void auditServiceShouldLogButNotSendMetrics() {
          doNothing().when(auditService).sendMetrics(any());  // override metrics call
          
          auditService.log("CREATE", payload);
          
          // Real log() method ran, metrics suppressed
          verify(auditService).log("CREATE", payload);
          verify(auditService, never()).sendMetrics(any());
      }
  }

@MockBean vs @Mock COMPARISON:

Feature               | @Mock              | @MockBean
----------------------|--------------------|-------------------------
Framework             | Mockito only       | Spring Boot Test
Lives in              | Test class         | Spring ApplicationContext
Resets per test       | Yes                | Yes (for @SpringBootTest)
Context restart needed| No                 | Yes if changed per class
Use in               | Unit tests          | Integration tests
Performance          | Fast               | Slow (loads context)

IMPORTANT: @MockBean causes the ApplicationContext to be recreated
for each test class that uses different @MockBean configurations.
This slows down test suites. Group tests with same @MockBean configs.

8. @MockitoSettings — CLASS-LEVEL CONFIGURATION
================================================================

  @ExtendWith(MockitoExtension.class)
  @MockitoSettings(strictness = Strictness.LENIENT)
  class LenientMockTest {
      // All mocks in this class use LENIENT strictness
      // Unused stubs won't throw UnnecessaryStubbingException
  }

STRICTNESS LEVELS:
  Strictness.STRICT_STUBS  — default with MockitoExtension
    - Detects unnecessary stubs (stubs never called → exception)
    - Detects mismatched stubbing args (arg mismatch → clear message)
    
  Strictness.LENIENT       — old Mockito default
    - No checks for unnecessary stubs
    - No checks for mismatched args
    - OK for old/legacy code or when stubs are shared across tests
    
  Strictness.WARN          — middle ground
    - Logs warnings for unused stubs instead of throwing exceptions
    - Good transitional setting when migrating to STRICT_STUBS

9. COMPLETE CLASS EXAMPLE
================================================================

  @ExtendWith(MockitoExtension.class)
  class OrderPlacementServiceTest {
      
      // ======== MOCKS (external dependencies) ========
      @Mock OrderRepository orderRepository;
      @Mock InventoryService inventoryService;
      @Mock PaymentGateway paymentGateway;
      @Mock EmailService emailService;
      @Mock Clock clock;
      
      // ======== SPY (real impl, but trackable) ========
      @Spy
      OrderIdGenerator idGenerator = new UuidOrderIdGenerator();
      
      // ======== CAPTORS ========
      @Captor ArgumentCaptor<Order> orderCaptor;
      @Captor ArgumentCaptor<PaymentRequest> paymentCaptor;
      @Captor ArgumentCaptor<EmailRequest> emailCaptor;
      
      // ======== SYSTEM UNDER TEST ========
      @InjectMocks OrderPlacementService orderService;
      
      @BeforeEach
      void setUpCommonStubs() {
          Instant fixedNow = Instant.parse("2024-06-15T12:00:00Z");
          when(clock.instant()).thenReturn(fixedNow);
          when(clock.getZone()).thenReturn(ZoneId.of("UTC"));
          
          when(inventoryService.isAvailable(anyString(), anyInt())).thenReturn(true);
          when(paymentGateway.charge(any())).thenReturn(
              PaymentResult.success("ch_test_123")
          );
          when(orderRepository.save(any())).thenAnswer(inv -> {
              Order o = inv.getArgument(0);
              o.setId("ord-generated-id");
              return o;
          });
      }
      
      @Test
      void shouldCreateOrderWithCorrectFields() {
          CartDto cart = CartDto.of("cust-1", List.of(
              CartItemDto.of("SKU-001", 2, new BigDecimal("49.99"))
          ));
          
          Order placed = orderService.place(cart);
          
          assertNotNull(placed.getId());
          assertEquals("cust-1", placed.getCustomerId());
          
          verify(orderRepository).save(orderCaptor.capture());
          Order savedOrder = orderCaptor.getValue();
          assertEquals(OrderStatus.CONFIRMED, savedOrder.getStatus());
          assertEquals(new BigDecimal("99.98"), savedOrder.getTotal());
      }
      
      @Test
      void shouldChargePaymentBeforeSavingOrder() {
          orderService.place(cart);
          
          InOrder inOrder = inOrder(paymentGateway, orderRepository);
          inOrder.verify(paymentGateway).charge(any());
          inOrder.verify(orderRepository).save(any());
      }
      
      @Test
      void shouldNotSendEmailIfInventoryUnavailable() {
          when(inventoryService.isAvailable("SKU-999", anyInt())).thenReturn(false);
          
          CartDto cart = CartDto.of("cust-1", List.of(
              CartItemDto.of("SKU-999", 1, new BigDecimal("9.99"))
          ));
          
          assertThrows(InsufficientInventoryException.class, 
              () -> orderService.place(cart));
          
          verifyNoInteractions(paymentGateway);
          verifyNoInteractions(emailService);
          verify(orderRepository, never()).save(any());
      }
  }

10. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between @Mock and @InjectMocks?
A: @Mock creates a mock of the annotated type.
   @InjectMocks creates an instance of the class under test and injects
   all @Mock and @Spy fields into it via constructor/setter/field injection.

Q: How does @InjectMocks determine which constructor to use?
A: It tries constructor injection first (largest constructor with matching
   parameter types), then setter injection, then field injection via reflection.

Q: What's the difference between @MockBean and @Mock?
A: @Mock (Mockito) creates a mock used only within the test class.
   @MockBean (Spring) adds a Mockito mock to the Spring ApplicationContext,
   replacing any existing bean of that type. Used in Spring integration tests.

Q: When should you use @Spy vs @Mock?
A: @Mock for full control (fake all behavior).
   @Spy when you need the real implementation for most methods but want
   to override specific ones or track interactions.

Q: What happens if @InjectMocks fails to inject?
A: It fails SILENTLY — no exception is thrown but the field remains null
   or the real dependency remains unset. Always verify non-null in setup.

Q: How do you initialize Mockito annotations without JUnit 5?
A: MockitoAnnotations.openMocks(this) in @BeforeEach.
   Store the returned AutoCloseable and call .close() in @AfterEach.

Q: What does @MockitoSettings(strictness = LENIENT) do?
A: Changes the strictness for the entire test class to LENIENT, disabling
   UnnecessaryStubbingException checks. Useful for shared stubs in @BeforeEach
   where not all tests use every stub.

Q: Can @SpyBean spy on a @Repository bean in Spring?
A: Yes. @SpyBean wraps the actual Spring-managed bean with a Mockito spy.
   The real Spring Data JPA repository methods execute, but you can
   override or verify specific method calls.
