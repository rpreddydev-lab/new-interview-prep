MOCKITO OVERVIEW — Complete Interview Preparation Guide
================================================================

1. WHAT IS MOCKITO?
================================================================
Mockito is the most popular Java mocking framework.
It allows you to create mock objects, configure their behavior,
and verify interactions in unit tests.

Version: Mockito 5.x (current, requires Java 11+)
         Mockito 4.x (requires Java 8+)

GitHub: https://github.com/mockito/mockito

Core capabilities:
  ✅ Create mock objects for interfaces and classes
  ✅ Configure return values (stubbing)
  ✅ Configure exceptions to be thrown
  ✅ Verify method calls (how many times, with what args)
  ✅ Capture arguments passed to mocks
  ✅ Spy on real objects
  ✅ Mock static methods (Mockito 3.4+)
  ✅ Mock constructors (Mockito 3.4+)

3. THREE WAYS TO USE MOCKITO
================================================================

WAY 1: MockitoExtension (Recommended for JUnit 5)
  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      @Mock OrderRepository orderRepository;
      @Mock EmailService emailService;
      @Spy List<String> spyList = new ArrayList<>();
      @Captor ArgumentCaptor<Order> orderCaptor;
      @InjectMocks OrderService orderService;
      
      // Annotations are initialized automatically by MockitoExtension
  }

WAY 2: MockitoAnnotations.openMocks() (manual initialization)
  class OrderServiceTest {
      @Mock OrderRepository orderRepository;
      @InjectMocks OrderService orderService;
      
      AutoCloseable closeable;
      
      @BeforeEach
      void setUp() {
          closeable = MockitoAnnotations.openMocks(this);
      }
      
      @AfterEach
      void tearDown() throws Exception {
          closeable.close();
      }
  }

WAY 3: Mockito.mock() directly (programmatic)
  class OrderServiceTest {
      
      @Test
      void shouldPlaceOrder() {
          OrderRepository mockRepo = Mockito.mock(OrderRepository.class);
          EmailService mockEmail = Mockito.mock(EmailService.class);
          OrderService service = new OrderService(mockRepo, mockEmail);
          
          when(mockRepo.save(any())).thenAnswer(inv -> inv.getArgument(0));
          
          service.placeOrder(new Order("c-1", List.of(item)));
          verify(mockEmail).sendConfirmation(any());
      }
  }

4. BASIC MOCKITO WORKFLOW
================================================================

The typical test structure with Mockito:

  @ExtendWith(MockitoExtension.class)
  class OrderServiceTest {
      
      // Step 1: Declare mocks
      @Mock private OrderRepository orderRepository;
      @Mock private EmailService emailService;
      @Mock private InventoryService inventoryService;
      
      // Step 2: Declare SUT (System Under Test)
      @InjectMocks private OrderService orderService;
      
      @Test
      void shouldPlaceOrderSuccessfully() {
          // Step 3: GIVEN — Configure mock behavior (stubbing)
          Order order = new Order("customer-1", List.of(new Item("Book", 29.99)));
          when(orderRepository.save(any(Order.class)))
              .thenReturn(order.withId("o-generated-id").withStatus(CONFIRMED));
          when(inventoryService.isAvailable(any()))
              .thenReturn(true);
          doNothing().when(emailService).sendConfirmation(any());
          
          // Step 4: WHEN — Execute the code under test
          OrderResult result = orderService.placeOrder(order);
          
          // Step 5: THEN — Assert outcomes
          assertEquals("o-generated-id", result.getOrderId());
          assertEquals(CONFIRMED, result.getStatus());
          
          // Step 6: VERIFY — Verify interactions
          verify(orderRepository).save(any(Order.class));
          verify(inventoryService).isAvailable(any());
          verify(emailService).sendConfirmation(any());
      }
  }

5. MOCKITO STRICTNESS LEVELS
================================================================

Mockito has three strictness levels that affect how it handles unused stubs
and other potential issues:

LENIENT (least strict):
  - No warnings for unused stubs
  - No detection of argument mismatches
  - Use rarely — hides potential issues
  
  Mockito.mock(OrderRepository.class, LENIENT)
  Or: @MockitoSettings(strictness = Strictness.LENIENT)

WARN (default in older versions):
  - Warns about unused stubs
  - Detects potential stub mismatches

STRICT_STUBS (recommended):
  - Fails tests if stubs are set up but not used (unused stubs = likely test bug)
  - Detects incorrect stub arguments (stub for "a" but actual call was "b")
  - Makes tests cleaner and catches common mistakes
  
  @ExtendWith(MockitoExtension.class)     // defaults to STRICT_STUBS in mockito-junit-jupiter
  
  // Or explicitly:
  @MockitoSettings(strictness = Strictness.STRICT_STUBS)
  class MyTest { }

STRICT_STUBS benefits:
  - Detects: when(repo.findById("a")).thenReturn(x) but service called findById("b")
  - Fails fast on unused stubs (tests that set up mocks they don't use)
  - Promotes "use it or lose it" mock setup

6. COMMON MOCKITO METHODS — CHEAT SHEET
================================================================

STUBBING (configure return values):
  when(mock.method()).thenReturn(value)
  when(mock.method()).thenReturn(v1, v2, v3)   // sequence
  when(mock.method()).thenThrow(exception)
  when(mock.method()).thenAnswer(inv -> inv.getArgument(0))
  when(mock.method()).thenCallRealMethod()
  
  // For void methods:
  doNothing().when(mock).voidMethod()
  doThrow(exception).when(mock).voidMethod()
  doAnswer(inv -> ...).when(mock).voidMethod()
  doReturn(value).when(spy).method()  // use with spies

VERIFYING (check interactions):
  verify(mock).method()
  verify(mock, times(3)).method()
  verify(mock, never()).method()
  verify(mock, atLeast(1)).method()
  verify(mock, atMost(5)).method()
  verify(mock, atLeastOnce()).method()
  
  verifyNoInteractions(mock)         // no methods called
  verifyNoMoreInteractions(mock)     // no unverified calls
  
  InOrder inOrder = inOrder(mock1, mock2);
  inOrder.verify(mock1).method1();
  inOrder.verify(mock2).method2();

ARGUMENT MATCHERS:
  any()              any(Class.class)
  anyString()        anyInt()       anyLong()      anyDouble()
  anyList()          anyMap()       anyCollection()
  eq("exact")        
  isNull()           isNotNull()
  argThat(predicate)
  
  // Use either ALL matchers or NO matchers in one call
  // WRONG: when(m.method(anyString(), "literal"))
  // RIGHT: when(m.method(anyString(), eq("literal")))

RESETTING:
  Mockito.reset(mock)               // clear all stubs and verifications

7. MOCKITO ANNOTATIONS SUMMARY
================================================================

@Mock
  Creates a mock object. All methods return default values unless stubbed.
  Default returns: null for objects, 0 for numbers, false for boolean, empty for collections.

@Spy
  Creates a spy wrapping a real instance. Real methods execute unless overridden.
  Requires a real instance to be provided.

@InjectMocks
  Creates an instance of the SUT and injects @Mock and @Spy fields.
  Injection strategies (tried in order):
  1. Constructor injection (preferred)
  2. Setter injection
  3. Field injection (least preferred)

@Captor
  Creates an ArgumentCaptor for capturing method arguments.
  Equivalent to ArgumentCaptor.forClass(Type.class).

@MockBean (Spring Boot only)
  Creates a Spring-managed mock bean in the application context.
  Different from @Mock — registers in Spring context, can replace a @Component.

8. MOCKITO IN ACTION — COMPREHENSIVE EXAMPLE
================================================================

  @ExtendWith(MockitoExtension.class)
  class PaymentServiceTest {
      
      @Mock private PaymentGateway paymentGateway;
      @Mock private OrderRepository orderRepository;
      @Mock private NotificationService notificationService;
      @Captor private ArgumentCaptor<PaymentRequest> paymentCaptor;
      @Captor private ArgumentCaptor<Notification> notificationCaptor;
      
      @InjectMocks private PaymentService paymentService;
      
      @Test
      void shouldProcessPaymentSuccessfully() {
          // GIVEN
          Order order = Order.builder()
              .id("o-123")
              .customerId("c-456")
              .total(99.99)
              .status(PENDING)
              .build();
          
          PaymentResult successResult = new PaymentResult("txn-789", SUCCESS);
          
          when(orderRepository.findById("o-123")).thenReturn(Optional.of(order));
          when(paymentGateway.charge(any(PaymentRequest.class))).thenReturn(successResult);
          when(orderRepository.save(any(Order.class))).thenAnswer(inv -> inv.getArgument(0));
          
          // WHEN
          PaymentResponse response = paymentService.processPayment("o-123", paymentMethod);
          
          // THEN — Assert outcome
          assertThat(response.getTransactionId()).isEqualTo("txn-789");
          assertThat(response.getStatus()).isEqualTo(SUCCESS);
          
          // VERIFY — Capture and inspect payment request
          verify(paymentGateway).charge(paymentCaptor.capture());
          PaymentRequest capturedRequest = paymentCaptor.getValue();
          assertThat(capturedRequest.getAmount()).isCloseTo(99.99, offset(0.01));
          assertThat(capturedRequest.getOrderId()).isEqualTo("o-123");
          
          // VERIFY — Order was updated to PAID
          ArgumentCaptor<Order> orderCaptor = ArgumentCaptor.forClass(Order.class);
          verify(orderRepository).save(orderCaptor.capture());
          assertThat(orderCaptor.getValue().getStatus()).isEqualTo(PAID);
          
          // VERIFY — Notification sent
          verify(notificationService).send(notificationCaptor.capture());
          assertThat(notificationCaptor.getValue().getType()).isEqualTo(PAYMENT_SUCCESS);
          assertThat(notificationCaptor.getValue().getRecipient()).isEqualTo("c-456");
      }
      
      @Test
      void shouldHandlePaymentGatewayFailure() {
          // GIVEN
          when(orderRepository.findById("o-123")).thenReturn(Optional.of(order));
          when(paymentGateway.charge(any())).thenThrow(new PaymentGatewayException("Gateway timeout"));
          
          // WHEN + THEN
          PaymentException ex = assertThrows(
              PaymentException.class,
              () -> paymentService.processPayment("o-123", paymentMethod)
          );
          assertThat(ex.getMessage()).contains("Gateway timeout");
          
          // VERIFY: Order NOT saved as paid on failure
          verify(orderRepository, never()).save(any());
          
          // VERIFY: Failure notification sent
          verify(notificationService).send(argThat(n -> n.getType() == PAYMENT_FAILED));
      }
  }

9. MOCKITO BEST PRACTICES
================================================================

DO:
  ✅ Use @ExtendWith(MockitoExtension.class) — enables strict stubs
  ✅ Only mock what you need for the specific test
  ✅ Verify the most important interactions
  ✅ Use ArgumentCaptor for complex argument assertions
  ✅ Name mocks descriptively (mockEmailService, not just mock)
  ✅ Test one scenario per test method

DON'T:
  ❌ Mock value objects (String, Integer, DTOs) — use real instances
  ❌ Mock the class under test (@InjectMocks is the SUT, @Mock is its deps)
  ❌ Over-mock — don't mock every single thing
  ❌ Verify every single interaction — verify what MATTERS
  ❌ Use MockitoAnnotations.initMocks() — deprecated; use openMocks() or extension
  ❌ Mock interfaces you own just to avoid running code — use real implementations

10. INTERVIEW QUESTIONS ON MOCKITO OVERVIEW
================================================================

Q: What is Mockito and what problem does it solve?
A: Mockito is a Java mocking framework that creates test doubles for
   dependencies. It solves the problem of testing classes in isolation —
   instead of needing a real database or email server, you create mock
   objects that simulate their behavior.

Q: What is the difference between @Mock and @InjectMocks?
A: @Mock: creates a mock object for a dependency.
   @InjectMocks: creates an instance of the class being tested and
   injects @Mock and @Spy fields into it as dependencies.

Q: What are the three ways to initialize Mockito annotations?
A: 1. @ExtendWith(MockitoExtension.class) — recommended for JUnit 5
   2. MockitoAnnotations.openMocks(this) in @BeforeEach
   3. Mockito.mock() directly in tests (programmatic, no annotations)

Q: What is STRICT_STUBS and why is it useful?
A: Strictness mode that fails tests when stubs are defined but not used,
   or when actual calls don't match stub expectations.
   Useful for detecting mismatched test setup and keeping tests clean.

Q: What does @InjectMocks injection try in order?
A: 1. Constructor injection (Mockito looks for constructors)
   2. Setter injection (Mockito looks for setters)
   3. Field injection (direct field access)
   Constructor injection is most explicit and preferred.
