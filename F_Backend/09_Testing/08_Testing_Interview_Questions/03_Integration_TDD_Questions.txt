INTERVIEW QUESTIONS — INTEGRATION TESTING AND TDD/BDD
Complete Interview Preparation Guide
================================================================

================================================================
INTEGRATION TESTING QUESTIONS
================================================================

Q1: What is the difference between unit tests and integration tests?
A: Unit tests test a single class/method in isolation — all dependencies
   are mocked. Fast (< 50ms each), deterministic, no external systems.
   
   Integration tests test multiple components working together: service +
   repository + real database, or service + Kafka, or HTTP controller + service.
   Slower, require external systems (or containers), verify real wiring.
   
   Both are essential: unit tests for logic, integration tests for real behavior.

---

Q2: What is Testcontainers? When would you use it?
A: Testcontainers is a Java library that starts real Docker containers for tests.
   Common uses: PostgreSQL, MySQL, Redis, Kafka, Elasticsearch containers.
   
   Use when: you want to test against a real database (not H2), need production-
   like behavior (specific DB features, procedures), or test Kafka integration.
   
   Use @Container with @Testcontainers, and @DynamicPropertySource to inject
   the container's JDBC URL/port into the Spring context.

---

Q3: What is @ServiceConnection in Spring Boot 3.1+?
A: @ServiceConnection automatically reads the container's connection info and
   configures the matching Spring properties without @DynamicPropertySource:
   
   @Container
   @ServiceConnection
   static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15");
   
   Spring Boot recognizes the container type and sets spring.datasource.url,
   username, password automatically. Cleaner, less boilerplate.

---

Q4: What lifecycle strategies exist for Testcontainers in Spring Boot tests?
A: 1. @Container + static field: container starts once per test class.
   2. @Container + instance field: restarts per test method (slow, rarely needed).
   3. Static shared container (base class): @Container on abstract base class,
      shared across all test classes that extend it (fastest — one container per JVM).
   4. Manual start with @BeforeAll: container.start() / @AfterAll: container.stop()
   
   Best practice: static field on abstract base test class for maximum reuse.

---

Q5: How does H2 differ from Testcontainers for DB tests?
A: H2 is an in-memory DB that starts in-process. Very fast but may behave
   differently from production PostgreSQL/MySQL (different SQL dialect,
   missing features like arrays, JSON operators, custom functions).
   
   Testcontainers starts the real DB engine in Docker. Slower to start but
   tests run against the exact same database as production. Required for:
   PostgreSQL-specific features, custom DB functions, migration validation.

---

Q6: How do you test a Kafka consumer in Spring Boot?
A: Use @EmbeddedKafka (from spring-kafka-test) to start an in-process Kafka.
   Produce messages using KafkaTemplate. Since consumption is async, use
   Awaitility to poll until the expected state change (e.g., DB record updated):
   
   await().atMost(ofSeconds(5))
       .untilAsserted(() -> assertEquals(OrderStatus.PAID, repo.findById(id).getStatus()));
   
   For production-like tests, use KafkaContainer from Testcontainers.

---

Q7: What is WireMock and when would you use it?
A: WireMock is a mock HTTP server. Use it when your service calls external HTTP
   APIs (payment gateways, notification services, 3rd-party APIs). Instead of
   calling the real external service, requests go to WireMock which returns
   pre-configured responses.
   
   Allows testing: error scenarios (503, network timeout), slow responses,
   malformed JSON, and verifying that your service sends the correct request.

---

Q8: How do you test an external API timeout with WireMock?
A: Use withFixedDelay() to simulate a slow response:
   stubFor(post(urlEqualTo("/api/payments"))
       .willReturn(aResponse()
           .withStatus(200)
           .withFixedDelay(5000)   // 5 second delay
       )
   );
   If your service has a 2 second timeout configured, it will throw a
   timeout exception before WireMock sends the response. Verify your
   service handles this gracefully.

---

Q9: What is contract testing and how does Pact work?
A: Contract testing verifies consumer-provider API compatibility without
   deploying both together. Pact enables consumer-driven contracts:
   1. Consumer writes a test that defines the API interactions it expects.
   2. Pact generates a "pact file" (JSON contract).
   3. Provider verifies it can satisfy that contract.
   If the provider changes the API and breaks the contract, the provider test fails.
   Enables independent deployment of microservices.

---

Q10: How do you ensure integration test isolation (no test data bleed)?
A: Options:
   1. @Transactional on test class: each test runs in a transaction that
      rolls back after the test. Default for @DataJpaTest.
   2. @Sql(scripts = "cleanup.sql", executionPhase = AFTER_TEST_METHOD)
   3. Testcontainers: start fresh container per test class (expensive but clean)
   4. Database cleaner library: explicitly DELETE FROM tables in @AfterEach
   5. Use separate schema per test (rarely practical)
   
   Most common: @Transactional for repository tests, explicit cleanup for
   integration tests that need committed transactions.

TDD / BDD QUESTIONS
================================================================

Q11: What is TDD? Describe the Red-Green-Refactor cycle.
A: Test-Driven Development is a practice where you write a FAILING test first,
   then write the minimal code to make it pass, then refactor.
   
   Red:    Write a failing test for the next piece of functionality.
           The test should fail because the code doesn't exist yet.
   Green:  Write the simplest code to make the test pass.
           Don't over-engineer — just make it work.
   Refactor: Clean up the code (extract methods, remove duplication)
           while keeping all tests green.
   
   Repeat for each feature increment.

---

Q12: What are the benefits of TDD?
A: - Forces you to think about API design before implementation
   - Ensures every feature has a test (100% coverage by design)
   - Smaller, focused methods (you only write what's needed to pass tests)
   - Faster debugging (tests pinpoint exactly what broke)
   - Confident refactoring (green tests = behavior preserved)
   - Living documentation (tests describe expected behavior)
   - Reduces debugging time overall (catch bugs immediately)

---

Q13: What is BDD? How is it different from TDD?
A: BDD (Behavior-Driven Development) extends TDD with natural language
   specifications (Given-When-Then) that non-technical stakeholders can read.
   
   TDD focuses on the developer's perspective: write a failing unit test.
   BDD focuses on business behavior: write a scenario in Gherkin language,
   then implement step definitions that map to test code.
   
   Gherkin: Feature → Scenario → Given/When/Then
   Tools: Cucumber (Java), JBehave, Serenity BDD

---

Q14: Write a Gherkin scenario for placing an order.
A:  Feature: Order Placement
      
      Scenario: Successful order for in-stock product
        Given the customer "cust-1" has a valid payment method
        And the product "P-001" has 10 units in stock
        When the customer places an order for 3 units of "P-001"
        Then the order should be created with status "PENDING"
        And the inventory for "P-001" should be reduced to 7 units
        And a confirmation email should be sent to the customer
      
      Scenario: Order rejected when product is out of stock
        Given the product "P-001" has 0 units in stock
        When the customer places an order for 1 unit of "P-001"
        Then the order should be rejected with error "OUT_OF_STOCK"

---

Q15: What is the Test Pyramid? Describe the three layers.
A: The Test Pyramid describes the recommended distribution of test types:
   
   Top (E2E / UI Tests) — fewest, slowest, most brittle, most realistic
     Browser/API tests; catch integration issues but expensive to maintain.
   
   Middle (Integration Tests) — moderate number
     Service + DB, Controller + Service; catch wiring and data issues.
   
   Bottom (Unit Tests) — most numerous, fastest, cheapest
     Individual classes; fast feedback, easy to maintain.
   
   Anti-pattern: "Ice Cream Cone" — many UI tests, few unit tests.
   Modern variant: "Testing Trophy" (emphasizes integration tests slightly more).

---

Q16: What is the "Detroit School" vs "London School" of TDD?
A: Detroit (Classicist): Test behavior through the real class hierarchy.
   Use real collaborators; only mock external systems (DB, HTTP). Write
   tests after understanding the design. Emphasized by Kent Beck.
   
   London (Mockist): Mock ALL collaborators. Each test isolates exactly
   one class. Design emerges from outside-in through the mock interactions.
   More tests per class, finer granularity.
   
   In practice: mix both — Detroit for domain logic, London for services
   with many external dependencies.

---

Q17: What are F.I.R.S.T. principles for unit tests?
A: Fast     — runs in milliseconds; the entire suite in seconds
   Independent — no test depends on another; any order should work
   Repeatable  — same result every time (no time/random/external dependency)
   Self-validating — assertion built into the test; no manual inspection needed
   Timely  — written before or alongside the code being tested (not after release)

---

Q18: What is mutation testing and how does it relate to TDD?
A: Mutation testing (PIT) introduces small changes to production code (mutants)
   and checks if tests fail. If tests pass for a mutant — the tests aren't
   verifying that behavior.
   
   TDD produces high mutation scores naturally because tests are written to
   describe exactly what the code should do — any deviation (mutation) fails
   those specific assertions. A low mutation score on TDD'd code indicates
   the tests were written without meaningful assertions.
