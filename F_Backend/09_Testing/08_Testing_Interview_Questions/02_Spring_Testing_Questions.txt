================================================================
INTERVIEW QUESTIONS — SPRING BOOT TESTING
Complete Interview Preparation Guide
================================================================

Q1: What does @SpringBootTest do? What are the webEnvironment options?
A: @SpringBootTest loads the full ApplicationContext for integration testing.
   webEnvironment options:
   - MOCK (default): loads context but no real HTTP server; use with MockMvc
   - RANDOM_PORT: starts real embedded server on random port; use with TestRestTemplate
   - DEFINED_PORT: starts server on application.properties port
   - NONE: loads context without web layer (service/repo testing only)
   
   RANDOM_PORT is preferred over DEFINED_PORT to avoid port conflicts in CI.

---

Q2: What is @WebMvcTest and how is it different from @SpringBootTest?
A: @WebMvcTest is a test slice that loads ONLY the web layer components:
   @Controller, @ControllerAdvice, @JsonComponent, Filters, WebMvcConfigurer.
   It does NOT load @Service, @Repository, or @Component beans.
   Use @MockBean to mock services in @WebMvcTest tests.
   
   @SpringBootTest loads the FULL context (all layers).
   @WebMvcTest is faster — use for focused controller tests.

---

Q3: What is @DataJpaTest and what does it configure?
A: @DataJpaTest is a slice for JPA repository testing. It:
   - Auto-configures Spring Data JPA repositories
   - Uses embedded H2 database by default
   - Wraps each test in a transaction that rolls back after the test
   - Does NOT load @Service or @Controller beans
   
   Use TestEntityManager for setting up test data.
   Add @AutoConfigureTestDatabase(replace = NONE) to use a real DB
   (e.g., with Testcontainers).

---

Q4: What is @MockBean? How is it different from @Mock?
A: @MockBean adds a Mockito mock to the Spring ApplicationContext.
   @Mock creates a Mockito mock outside Spring — for plain unit tests.
   
   @MockBean replaces the real bean in the context. Every @Autowired field
   of that type gets the mock. Required for @WebMvcTest (services aren't
   loaded) and useful in @SpringBootTest to isolate external dependencies.
   
   PERFORMANCE TIP: Place @MockBean on a shared base class. @MockBean causes
   context reload only if the mock type changes, not if it's moved to base class.

---

Q5: What is MockMvc and how do you use it?
A: MockMvc is a test helper for HTTP requests without starting a real server.
   @Autowired MockMvc mockMvc;
   
   mockMvc.perform(post("/api/orders")
       .contentType(MediaType.APPLICATION_JSON)
       .content(objectMapper.writeValueAsString(request)))
     .andExpect(status().isCreated())
     .andExpect(jsonPath("$.orderId").isNotEmpty())
     .andDo(print());
   
   Used with MOCK webEnvironment. @WebMvcTest auto-configures MockMvc.

---

Q6: What is the difference between MockMvc and TestRestTemplate?
A: MockMvc — tests in the servlet layer without a real server. Works with
   @WebMvcTest or MOCK web environment. Fast, detailed assertions on responses.
   
   TestRestTemplate — makes real HTTP calls to a real embedded server.
   Requires RANDOM_PORT or DEFINED_PORT web environment.
   Use TestRestTemplate for full end-to-end integration tests.
   
   WebTestClient — reactive alternative to MockMvc; works with WebFlux.
   Can also be used for REST API testing with the fluent assertion style.

---

Q7: What is @DynamicPropertySource?
A: Allows setting Spring properties from dynamic values known only at runtime
   (e.g., the port of a Testcontainers container):
   
   @DynamicPropertySource
   static void configureProperties(DynamicPropertyRegistry registry) {
       registry.add("spring.datasource.url", postgres::getJdbcUrl);
       registry.add("spring.datasource.username", postgres::getUsername);
   }
   
   Spring Boot 3.1+ can use @ServiceConnection instead as a cleaner alternative.

---

Q8: How does Spring Boot optimize test performance with context caching?
A: Spring caches the ApplicationContext between tests that share the same
   configuration. If multiple test classes use identical @SpringBootTest
   config, they share one context. 
   
   Context cache keys: configuration classes, active profiles, property sources,
   context loader, web environment. If any differ, a new context is created.
   
   @DirtiesContext marks a test as having modified the context → forces reload
   for subsequent tests. Use sparingly as it's expensive.
   
   Using @MockBean forces a separate context per test class unless all classes
   declaring the same mocks use an abstract base class.

Q9: How do you test Spring Security with @WebMvcTest?
A: Spring Security auto-configuration is included in @WebMvcTest.
   Use @WithMockUser to simulate an authenticated user:
   
   @Test
   @WithMockUser(username = "admin", roles = {"ADMIN"})
   void shouldAllowAdminAccess() throws Exception {
       mockMvc.perform(get("/admin/reports"))
           .andExpect(status().isOk());
   }
   
   @Test
   void shouldReturn401ForUnauthenticated() throws Exception {
       mockMvc.perform(get("/admin/reports"))
           .andExpect(status().isUnauthorized());
   }
   
   For custom UserDetails: use @WithUserDetails or @WithSecurityContext.

---

Q10: How do you test exception handling in @WebMvcTest?
A: Stub the service mock to throw an exception. Verify the correct HTTP status
   and error response body from the @ControllerAdvice:
   
   when(orderService.getOrder("ord-999"))
       .thenThrow(new OrderNotFoundException("ord-999"));
   
   mockMvc.perform(get("/api/orders/ord-999"))
       .andExpect(status().isNotFound())
       .andExpect(jsonPath("$.error").value("ORDER_NOT_FOUND"))
       .andExpect(jsonPath("$.message").value(containsString("ord-999")));

---

Q11: What is @TestConfiguration?
A: @TestConfiguration defines additional beans only used in tests. It doesn't
   prevent component scanning of production beans (unlike @Configuration used
   in tests). Use cases:
   - Define a fake bean for a test (e.g., a local clock)
   - Override a production bean with a test version
   
   Standalone: import with @Import(TestConfig.class) in the test class.
   Nested: declare as a static nested class inside the test — auto-detected.

---

Q12: How do you manage test data with @DataJpaTest?
A: Options:
   1. TestEntityManager: entityManager.persistAndFlush(entity)
   2. Direct repository save: productRepo.save(product)
   3. @Sql annotation: @Sql("classpath:test-data.sql") on test method
   4. @Sql with scripts config: use BEFORE_TEST_METHOD and AFTER_TEST_METHOD
   
   Since @DataJpaTest wraps in a transaction that rolls back after each test,
   data is automatically cleaned up. Use @Commit or @Transactional(propagation=NOT_SUPPORTED)
   if you need to verify across transactions.

Q13: How do you write a full-stack integration test with Testcontainers?
A: 
   @SpringBootTest(webEnvironment = RANDOM_PORT)
   @Testcontainers
   class OrderIT {
     @Container
     static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:15");
     
     @DynamicPropertySource
     static void props(DynamicPropertyRegistry r) {
       r.add("spring.datasource.url", db::getJdbcUrl);
       r.add("spring.datasource.username", db::getUsername);
       r.add("spring.datasource.password", db::getPassword);
     }
     
     @Autowired TestRestTemplate restTemplate;
     
     @Test
     void shouldCreateOrder() {
       ResponseEntity<OrderDto> resp = restTemplate.postForEntity(
           "/api/orders", request, OrderDto.class);
       assertEquals(201, resp.getStatusCode().value());
     }
   }

Q14: What is @SpyBean?
A: @SpyBean wraps a real Spring bean as a Mockito spy. The real implementation
   is used unless specific methods are stubbed. Useful when you need to verify
   calls on a real service or partially override behavior:
   
   @SpyBean OrderService orderService;
   
   // In test:
   doReturn(mockResult).when(orderService).expensiveComputation(any());
   // All other methods of orderService work normally

---

Q15: How do you test async @Async service methods in Spring Boot?
A: Option 1: Synchronous in test — override the ThreadPoolTaskExecutor
   in a @TestConfiguration to use a synchronous executor (runs on the same thread).
   Option 2: Awaitility polling for the expected state change.
   Option 3: Use @EnableAsync with SyncTaskExecutor in test profile:
   
   @TestConfiguration
   static class TestAsyncConfig implements AsyncConfigurer {
       @Override
       public Executor getAsyncExecutor() {
           return new SyncTaskExecutor(); // runs synchronously
       }
   }
