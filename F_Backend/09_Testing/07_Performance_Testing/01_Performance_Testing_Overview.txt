PERFORMANCE TESTING — OVERVIEW
Complete Interview Preparation Guide
================================================================

1. WHAT IS PERFORMANCE TESTING?
================================================================

Performance testing evaluates how a system behaves under various load conditions.
It measures throughput, response time, resource utilization, and stability.

Goals:
  - Identify performance bottlenecks before production
  - Establish performance baselines
  - Validate SLAs (Service Level Agreements)
  - Ensure system degrades gracefully under load

================================================================
2. TYPES OF PERFORMANCE TESTING
================================================================

Type              | Description                          | When to Use
------------------|--------------------------------------|------------------
Load Testing      | Normal expected load                 | Pre-release baseline
Stress Testing    | Above normal load until failure      | Find breaking point
Soak/Endurance    | Normal load over long duration       | Memory leaks, DB conn exhaustion
Spike Testing     | Sudden extreme load burst            | Flash sales, viral events
Volume Testing    | Large data volumes                   | Data-intensive operations
Scalability Test  | Gradually increasing load            | Find scaling limits
Benchmark         | Micro-level method/code performance  | Optimize algorithms

3. KEY PERFORMANCE METRICS
================================================================

Metric              | Description                    | Target (typical)
--------------------|--------------------------------|------------------
Response Time (avg) | Average time per request       | < 200ms (API)
Response Time (p95) | 95th percentile latency        | < 500ms
Response Time (p99) | 99th percentile latency        | < 1000ms
Throughput (TPS/RPS)| Requests per second handled    | Depends on SLA
Error Rate          | % of failed requests           | < 0.1%
CPU Usage           | CPU % under load               | < 70% at peak
Memory Usage        | Heap usage, GC activity        | Stable (no growth)
Connection Pool     | DB connection utilization      | < 80%

NOTE: p99 latency matters more than average in production!
A slow 1% of requests affects 1 in 100 users. For 1M req/day → 10,000 users.

5. PERFORMANCE TESTING METRICS FROM JVM
================================================================

  Important JVM metrics to monitor during performance tests:
  
  // Heap usage
  MemoryMXBean mem = ManagementFactory.getMemoryMXBean();
  long heapUsed = mem.getHeapMemoryUsage().getUsed();
  long heapMax = mem.getHeapMemoryUsage().getMax();
  
  // GC metrics (pause frequency/duration → sign of memory pressure)
  for (GarbageCollectorMXBean gc : ManagementFactory.getGarbageCollectorMXBeans()) {
      System.out.println(gc.getName() + ": " + gc.getCollectionCount() + " collections");
      System.out.println("  Total time: " + gc.getCollectionTime() + "ms");
  }
  
  // Thread count
  ThreadMXBean threads = ManagementFactory.getThreadMXBean();
  System.out.println("Active threads: " + threads.getThreadCount());

  Key concern: Increasing GC frequency/duration under load → memory leak

7. LOAD TESTING BEST PRACTICES
================================================================

  1. Test in a production-like environment
     (different hardware → different results)
  
  2. Warm up the JVM before measuring
     (JIT compilation skews early results)
  
  3. Use realistic data volumes
     (empty DB performs very differently from 1M rows)
  
  4. Simulate realistic user behavior
     (think time between requests, varied endpoints)
  
  5. Monitor server-side metrics too
     (don't just look at client-side latency)
  
  6. Establish baselines early
     (run on every release to detect regressions)
  
  7. Test both happy path AND error paths
     (validation failures, connection errors)

8. INTERVIEW QUESTIONS
================================================================

Q: What is the difference between load testing and stress testing?
A: Load testing applies expected normal load to verify the system meets
   performance requirements. Stress testing pushes beyond normal load to
   find the breaking point. Load testing validates your SLAs; stress
   testing discovers your system's limits and failure mode.

Q: What is the difference between average latency and p99 latency?
A: Average can mask outliers. p99 latency is the 99th percentile — 99% of
   requests are faster than this. In production, high p99 means 1 in 100
   users experiences slow responses. For an API serving 1M requests/day,
   that's 10,000 degraded experiences. SLAs should be defined on percentiles,
   not averages.

Q: What is soak testing and what does it find?
A: Soak testing (endurance testing) runs at normal load for an extended
   period (hours to days). It detects: memory leaks (heap grows over time),
   connection pool exhaustion (DB connections not released), thread leaks,
   disk space exhaustion, and cache memory growth.

Q: What should you monitor on the server side during a load test?
A: CPU usage, heap memory and GC frequency/duration, thread count, DB
   connection pool utilization, disk I/O, network throughput, and external
   service response times. Client-side latency alone is insufficient.
