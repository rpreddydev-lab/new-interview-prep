================================================================
GRAPHQL CORE CONCEPTS
================================================================

1. SCHEMA
---------
The Schema is the backbone of every GraphQL API. It defines:
  - All types that exist in the API
  - The relationships between those types
  - Every query, mutation, and subscription available

The schema acts as a CONTRACT between client and server. Written in SDL
(Schema Definition Language), it is language-agnostic. The runtime validates
every incoming operation against it.

Root types (entry points into the graph):
  ```graphql
  schema {
    query:        Query        # required — read operations
    mutation:     Mutation     # optional — write operations
    subscription: Subscription # optional — real-time
  }
  ```

  Shorthand (implicit schema definition, most common):
  ```graphql
  type Query { ... }
  type Mutation { ... }
  type Subscription { ... }
  ```

2. TYPES
--------
GraphQL has 6 named type categories:

  a) SCALAR     — Leaf values: Int, Float, String, Boolean, ID + custom scalars
  b) OBJECT     — Named set of fields, each with a type (e.g., type User {...})
  c) INTERFACE  — Abstract type with shared fields; objects implement it
  d) UNION      — One of several Object types; no shared fields required
  e) ENUM       — Restricted set of string values (e.g., ACTIVE, INACTIVE)
  f) INPUT      — Object used only as argument to mutations/queries

  Type modifiers:
  - String    → nullable String (can return null)
  - String!   → non-null String (runtime error if resolver returns null)
  - [String]  → nullable list of nullable Strings
  - [String!] → nullable list of non-null Strings
  - [String!]! → non-null list of non-null Strings

3. FIELDS
---------
Every type is made of fields. A field has:
  - A name
  - A return type (scalar or another type)
  - Optional arguments
  - Optional description

  ```graphql
  type Query {
    # Field 'user' with argument 'id' returns nullable User
    user(id: ID!): User

    # Field 'users' with pagination args returns non-null list
    users(first: Int = 10, after: String): [User!]!
  }
  ```

4. RESOLVERS
------------
A resolver is a function on the server that fetches the data for a specific
field. Every field in the schema CAN have a resolver; if none is provided,
a default resolver looks for a property with the same name on the parent object.

  Resolver signature (JavaScript):
  (parent, args, context, info) => value

  - parent:  the return value of the parent resolver (or root value)
  - args:    the arguments passed to this field in the query
  - context: shared object per request (auth, DB connections, DataLoader)
  - info:    metadata about the field (AST node, path, schema)

  Java equivalent (Spring for GraphQL):
  ```java
  @QueryMapping
  public User user(@Argument String id) {
    return userRepository.findById(id).orElseThrow();
  }
  ```

5. QUERIES
----------
A Query reads data. It maps to the Query root type.

  Syntax:
  ```graphql
  query GetUser {
    user(id: "1") {
      id
      name
      email
    }
  }
  ```

  Shorthand (anonymous, operation type omitted — only valid for single query):
  ```graphql
  {
    user(id: "1") {
      name
    }
  }
  ```

6. MUTATIONS
------------
A Mutation writes data. It maps to the Mutation root type. Mutations execute
serially (unlike queries which may execute in parallel).

  ```graphql
  mutation CreateUser {
    createUser(input: { name: "Bob", email: "bob@example.com" }) {
      id
      name
    }
  }
  ```

7. SUBSCRIPTIONS
----------------
A Subscription sets up a persistent connection and receives a stream of events.
Typically uses WebSockets.

  ```graphql
  subscription {
    messageAdded(channelId: "general") {
      id
      body
      sender { name }
    }
  }
  ```

8. VARIABLES
------------
Variables decouple dynamic values from the query structure and prevent
injection attacks. They are typed and validated.

  ```graphql
  query GetUser($userId: ID!) {
    user(id: $userId) {
      name
    }
  }
  ```
  Variables JSON: { "userId": "1" }

9. FRAGMENTS
------------
Fragments are reusable field selections. They promote DRY in queries.

  Named Fragment:
  ```graphql
  fragment UserFields on User {
    id
    name
    email
  }

  query {
    user(id: "1") { ...UserFields }
  }
  ```

  Inline Fragment (used with interfaces/unions):
  ```graphql
  query {
    search(text: "Alice") {
      ... on User  { name email }
      ... on Post  { title author { name } }
    }
  }
  ```

10. DIRECTIVES
--------------
Directives modify the behavior of fields or types. Built-in directives:

  @include(if: Boolean!) — include field only if condition is true
  @skip(if: Boolean!)    — skip field if condition is true
  @deprecated(reason: String) — marks a field as deprecated in schema

  ```graphql
  query GetUser($withEmail: Boolean!) {
    user(id: "1") {
      name
      email @include(if: $withEmail)
    }
  }
  ```

  Custom directives (e.g., @auth, @upper, @rateLimit) can be defined and
  executed server-side.

11. INTROSPECTION
-----------------
GraphQL schemas are self-describing. Clients can query the schema itself:

  ```graphql
  { __schema { types { name } } }
  { __type(name: "User") { fields { name type { name } } } }
  ```

  This powers tools like GraphiQL, Apollo Sandbox, code generators. 
  IMPORTANT: Disable introspection in production to avoid schema leaking.

12. CONTEXT
-----------
Context is an object shared across all resolvers for a single request.
It is populated when the request arrives and typically contains:
  - The authenticated user (from JWT/session)
  - Database connections / repositories
  - DataLoader instances
  - Logger, request ID, etc.

  Java (Spring for GraphQL):
  ```java
  // Context is populated from the servlet request
  // Access via @ContextValue or directly in resolvers
  ```

13. THE DATA GRAPH CONCEPT
--------------------------
GraphQL treats data as a GRAPH (nodes = objects, edges = relationships).
A query is a traversal of this graph starting from one of the root fields.

  Example graph traversal:
  Query → user(id:1) → User node → posts field → [Post] nodes → comments → ...

  This is why the "N+1 problem" emerges: each hop in the graph can trigger
  a new database query if not batched.

14. OPERATION NAMING (BEST PRACTICE)
--------------------------------------
Always name operations for:
  - Debugging and logging
  - Performance tracing
  - Persisted query lookup

  ```graphql
  query GetUserProfile { ... }    ← named
  mutation UpdateUserEmail { ... } ← named
  { user(id: 1) { name } }        ← anonymous — avoid in production
  ```

15. KEY INTERVIEW TALKING POINTS
----------------------------------
  • "The schema is both documentation and validation — it's the API contract"
  • "Resolvers are just functions; they can call DB, REST APIs, or anything"
  • "Context enables dependency injection into resolvers"
  • "Fragments are not just DRY — they're the building blocks of Relay's
    component-collocated data fetching"
  • "Directives extend schema language — @auth is a common custom directive
    for field-level authorization"
  • "Introspection is powerful for tooling but should be disabled in
    production to prevent schema enumeration attacks"
