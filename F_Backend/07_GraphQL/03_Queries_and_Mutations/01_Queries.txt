================================================================
GRAPHQL QUERIES — IN DEPTH
================================================================

1. WHAT IS A QUERY?
--------------------
A Query is the read operation in GraphQL. It maps to the `Query` root type
in the schema. Queries are designed to be SIDE-EFFECT FREE — they only
read data, they don't modify state.

Query fields can execute in PARALLEL (the runtime may run sibling fields
concurrently for better performance).

2. QUERY SYNTAX
----------------
```graphql
# Full syntax with operation type and operation name
query GetUser {
  user(id: "1") {
    id
    name
    email
  }
}

# Shorthand: anonymous query (omit 'query' keyword)
# Only valid when there's exactly one operation in the document
{
  user(id: "1") {
    name
  }
}
```

3. QUERY ANATOMY
-----------------
```
query GetUserProfile($userId: ID!, $withPosts: Boolean = true) {
  ─────── ─────────── ────────────────────────────────────────
     │         │               │
  keyword  operation        variable
            name           definitions

  user(id: $userId) {          # root field + argument
    id                         # scalar field
    name
    email
    profile {                  # object field (nested)
      bio
      avatarUrl
    }
    posts(first: 10) @include(if: $withPosts) {   # conditional field
      title
      publishedAt
    }
  }
}
```

4. FIELD SELECTION
-------------------
You must explicitly select every field you want returned. No wildcards (*).

```graphql
# What you ask for is what you get
query {
  product(id: "42") {
    id          # ← included
    name        # ← included
    price       # ← included
    # category  ← NOT included (not asked for)
    # tags      ← NOT included (not asked for)
  }
}
```

Object types REQUIRE sub-field selection:
```graphql
# ERROR: 'product' is an object type — you can't return it without sub-fields
query { product(id: "42") }

# CORRECT:
query { product(id: "42") { id name } }
```

Scalar types CANNOT have sub-field selections:
```graphql
# ERROR: 'name' is a String — it's a scalar, no sub-fields
query { product(id: "42") { name { value } } }

# CORRECT:
query { product(id: "42") { name } }
```

5. ARGUMENTS
------------
Fields can accept arguments to filter, sort, or parameterize results:

```graphql
query {
  # Required argument
  user(id: "1") { name }

  # Optional argument with default in schema
  products(first: 20) { name price }

  # Multiple arguments
  orders(
    status: PENDING
    from: "2026-01-01"
    to: "2026-12-31"
    first: 50
    after: "cursor123"
  ) {
    edges {
      node { id total status }
    }
    pageInfo { hasNextPage endCursor }
  }
}
```

6. ALIASES
----------
Fetch the same field multiple times with different arguments using aliases:

```graphql
query GetMultipleUsers {
  alice: user(id: "1") {
    name
    email
  }
  bob: user(id: "2") {
    name
    email
  }
  charlie: user(id: "3") {
    name
    email
  }
}
```

Response:
```json
{
  "data": {
    "alice": { "name": "Alice", "email": "alice@ex.com" },
    "bob":   { "name": "Bob",   "email": "bob@ex.com" },
    "charlie": { "name": "Charlie", "email": "charlie@ex.com" }
  }
}
```

Also useful for renaming fields in the response:
```graphql
query {
  product(id: "42") {
    productId: id         # renamed from 'id' to 'productId'
    productName: name     # renamed
    unitPrice: price      # renamed
  }
}
```

7. MULTIPLE FIELDS IN ROOT QUERY
----------------------------------
A single query can fetch multiple root-level fields (they execute in parallel):

```graphql
query Dashboard {
  currentUser: me {
    id
    name
    notificationCount
  }
  recentOrders: orders(first: 5, orderBy: { field: CREATED_AT, direction: DESC }) {
    edges { node { id status total } }
  }
  popularProducts: products(first: 10, orderBy: { field: POPULARITY, direction: DESC }) {
    edges { node { id name price } }
  }
  announcements: posts(category: ANNOUNCEMENT, first: 3) {
    edges { node { id title } }
  }
}
```

This replaces 4 REST requests with 1 GraphQL request!

8. INLINE FRAGMENTS FOR INTERFACES AND UNIONS
----------------------------------------------
```graphql
query GetFeed {
  feed {
    __typename             # Always available: tells you the concrete type
    ... on TextPost {
      id
      title
      body
      author { name }
    }
    ... on ImagePost {
      id
      imageUrl
      caption
      author { name }
    }
    ... on VideoPost {
      id
      videoUrl
      duration
      author { name }
    }
  }
}
```

9. NAMED FRAGMENTS
-------------------
Reuse common field selections:

```graphql
fragment UserBasicInfo on User {
  id
  name
  email
  avatar
}

fragment UserFullInfo on User {
  ...UserBasicInfo     # spread a fragment inside another fragment
  phone
  address {
    city
    country
  }
  roles
}

query {
  user(id: "1") {
    ...UserFullInfo
    posts(first: 5) {
      title
      ...PostMeta
    }
  }
}

fragment PostMeta on Post {
  id
  publishedAt
  category
  viewCount
}
```

10. VARIABLES
--------------
Always use variables for dynamic values in production:

```graphql
query GetUserPosts(
  $userId: ID!
  $status: PostStatus
  $first: Int = 10
  $after: String
) {
  user(id: $userId) {
    name
    posts(status: $status, first: $first, after: $after) {
      edges {
        cursor
        node {
          id
          title
          publishedAt
        }
      }
      pageInfo {
        hasNextPage
        endCursor
      }
    }
  }
}
```

Variables are sent in the request JSON:
```json
{
  "query": "...",
  "variables": {
    "userId": "user-123",
    "status": "PUBLISHED",
    "first": 20,
    "after": null
  }
}
```

Benefits of variables:
  ✓ Prevent injection attacks (arguments are typed and sanitized)
  ✓ Enable query deduplication/caching (query text is constant)
  ✓ Support persisted queries (hash the static query text)
  ✓ Better readability

11. DIRECTIVES IN QUERIES
--------------------------
```graphql
query GetUserProfile(
  $userId: ID!
  $isAdmin: Boolean!
  $skipPrivate: Boolean!
) {
  user(id: $userId) {
    name
    email @include(if: $isAdmin)          # Only include for admins
    phone @skip(if: $skipPrivate)          # Skip if private mode
    ... @include(if: $isAdmin) {          # Fragment of admin-only fields
      role
      createdAt
      lastLoginAt
    }
  }
}
```

12. QUERY COLOCATED WITH COMPONENTS (CLIENT PATTERN)
-----------------------------------------------------
In React/Apollo, queries are typically colocated with the component:

```javascript
// UserCard.jsx
const GET_USER = gql`
  query GetUser($id: ID!) {
    user(id: $id) {
      id
      name
      email
      avatar
    }
  }
`;

function UserCard({ userId }) {
  const { loading, error, data } = useQuery(GET_USER, {
    variables: { id: userId }
  });
  // ...
}
```

Relay takes this further: fragments are colocated with components and
composed up to the root query automatically.

13. PAGINATION QUERY PATTERNS
-------------------------------
```graphql
# Cursor-based (preferred):
query GetProducts($after: String, $first: Int = 20) {
  products(first: $first, after: $after) {
    edges {
      cursor
      node { id name price }
    }
    pageInfo {
      hasNextPage
      endCursor
    }
    totalCount
  }
}

# Offset-based (simpler):
query GetProducts($page: Int = 1, $pageSize: Int = 20) {
  products(page: $page, pageSize: $pageSize) {
    items { id name price }
    total
    page
    totalPages
  }
}
```

14. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the difference between anonymous and named queries?
A: A named query has an explicit operation name (e.g., `query GetUser { ... }`).
   Anonymous queries omit the name (`{ user(id: 1) { name } }`). Named queries
   are required when: there are multiple operations in a document, you're using
   persisted queries (hashed by name), or you want meaningful logs and traces.
   Best practice: always name queries.

Q: Can you send multiple operations in one GraphQL request?
A: You can have multiple operations in a document, but you can only EXECUTE
   one per request. You must specify which operation to execute via the
   `operationName` field in the request. This is used for persisted query
   documents that contain multiple named operations.

Q: How does query field execution order work?
A: Within a Query operation, fields at the same level can execute in
   parallel. However, the execution IS depth-first in terms of the AST
   traversal. The runtime may parallelize I/O operations for sibling fields.
   Mutations are the exception: top-level mutation fields always execute
   serially.

Q: What is a field alias in GraphQL?
A: An alias renames a field in the response. Syntax: `alias: field`. This
   lets you query the same field multiple times with different arguments
   (e.g., two different users) or rename fields to match client expectations
   without changing the schema.

Q: What happens if you query a field that doesn't exist?
A: The query fails validation before execution. The server returns an error:
   "Cannot query field 'nonExistentField' on type 'User'." No data is
   returned, and no resolver is called.

Q: Why should you avoid the query shorthand in production?
A: Anonymous shorthand queries (without `query` keyword and name) cannot be
   named, which means: they can't be used with persisted queries (which rely
   on operation names), they produce generic log entries making debugging
   harder, and Apollo Studio / observability tools can't track them by name.
