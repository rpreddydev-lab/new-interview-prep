1. WHAT IS FLYWAY?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Flyway is a database migration tool that:
- Applies versioned SQL scripts in order (V1, V2, V3...)
- Tracks applied migrations in flyway_schema_history table
- Each script runs ONCE and never again
- Fails fast if a previously applied script is modified (checksum check)

2. SETUP IN SPRING BOOT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// pom.xml:
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
    <!-- version managed by Spring Boot BOM -->
</dependency>

// For MySQL 8+:
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>

// application.properties:
spring.datasource.url=jdbc:postgresql://localhost:5432/mydb
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration     # default location
spring.flyway.baseline-on-migrate=false            # don't baseline existing DBs
spring.flyway.validate-on-migrate=true             # validate checksum on every run

// Combine with Hibernate validate:
spring.jpa.hibernate.ddl-auto=validate

3. FILE NAMING CONVENTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pattern: V{version}__{description}.sql
         R__{description}.sql  (repeatable — always re-runs if checksum changes)
         U{version}__{description}.sql  (undo — Flyway Pro)

Double underscore (__) separates version from description.

Examples:
  src/main/resources/db/migration/
    V1__create_users_table.sql
    V2__create_orders_table.sql
    V2.1__add_order_status_column.sql   ← sub-version
    V3__add_email_index.sql
    R__create_reporting_views.sql        ← repeatable: runs when file changes
    R__refresh_user_stats_view.sql

Rules:
  - Version must be unique and sequential
  - Cannot edit an already-applied script (checksum violation)
  - New scripts must have higher version numbers

4. EXAMPLE MIGRATION SCRIPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V1__create_users_table.sql:
  CREATE TABLE users (
      id BIGSERIAL PRIMARY KEY,
      email VARCHAR(255) NOT NULL UNIQUE,
      first_name VARCHAR(100),
      last_name VARCHAR(100),
      status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
      created_at TIMESTAMP NOT NULL DEFAULT NOW(),
      version BIGINT NOT NULL DEFAULT 0
  );

  CREATE INDEX idx_users_email ON users(email);
  CREATE INDEX idx_users_status ON users(status);

V2__create_orders_table.sql:
  CREATE TABLE orders (
      id BIGSERIAL PRIMARY KEY,
      user_id BIGINT NOT NULL REFERENCES users(id),
      total DECIMAL(10, 2) NOT NULL,
      status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
      created_at TIMESTAMP NOT NULL DEFAULT NOW(),
      version BIGINT NOT NULL DEFAULT 0
  );

  CREATE INDEX idx_orders_user_id ON orders(user_id);
  CREATE INDEX idx_orders_status ON orders(status);

V3__add_phone_to_users.sql:
  ALTER TABLE users ADD COLUMN phone VARCHAR(20);

V4__rename_status_to_order_status.sql:
  ALTER TABLE orders RENAME COLUMN status TO order_status;
  -- This requires a corresponding entity annotation change too:
  -- @Column(name = "order_status")

5. FLYWAY_SCHEMA_HISTORY TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Flyway tracks applied migrations:

flyway_schema_history:
  installed_rank | version | description              | type | script                          | checksum    | installed_on        | success
  1              | 1       | create users table       | SQL  | V1__create_users_table.sql      | 12345678    | 2024-01-01 10:00:00 | true
  2              | 2       | create orders table      | SQL  | V2__create_orders_table.sql     | 87654321    | 2024-01-01 10:00:01 | true
  3              | 3       | add phone to users       | SQL  | V3__add_phone_to_users.sql      | 11223344    | 2024-01-05 11:00:00 | true

On startup, Flyway:
1. Reads all V*.sql files from locations
2. Compares to flyway_schema_history
3. Runs any unapplied scripts in order
4. Fails if a previously applied script's checksum changed

6. HANDLING FLYWAY ERRORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Error 1: Checksum mismatch (edited applied migration)
  FlywayException: Validate failed: Migration checksum mismatch for migration version 2
  Fix: NEVER edit applied migrations. Create a new V5 to fix the issue.
  Emergency fix (dev only): flyway repair (clears failed migration history)

Error 2: Out-of-order migration
  By default, Flyway requires migrations to be in order.
  spring.flyway.out-of-order=true  ← allow out-of-order (for feature branches)

Error 3: Migration failed mid-way
  If a migration fails partway through:
  - Flyway marks the migration as failed in history table (success=false)
  - App will fail to start until resolved
  - Fix the migration, then flyway repair to clear the failed entry
  - Note: Wrap migrations in transactions where possible (PostgreSQL supports it)

7. BEST PRACTICES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. NEVER modify applied migration scripts — create new ones
2. Use descriptive names: V5__add_product_category_index.sql
3. Write backward-compatible migrations (expand-contract pattern):
   - Phase 1: ADD new column (nullable or with default)
   - Phase 2: Deploy code that writes to both old and new column
   - Phase 3: Backfill data
   - Phase 4: Make column non-null / rename / drop old column
4. Test migrations locally before pushing
5. Use transactions in migrations (PostgreSQL DDL is transactional)
6. Keep Hibernate ddl-auto=validate to verify entity-schema alignment
7. Use flyway.clean-disabled=true in production!

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is Flyway and why use it over Hibernate DDL auto?
A: Flyway is a versioned database migration tool. Unlike Hibernate DDL auto
   (which modifies schema on-the-fly without tracking), Flyway applies
   explicitly written SQL scripts in order, tracks each in flyway_schema_history,
   and ensures every environment applies exactly the same changes in the same
   order. This gives you auditability, reproducibility, and rollback capability.

Q: What happens if you modify an already-applied Flyway migration?
A: Flyway will throw FlywayException: checksum mismatch. It detects that
   the file content changed vs what was recorded in flyway_schema_history.
   NEVER modify applied migrations — create a new migration script instead.

Q: What is a repeatable migration in Flyway (R__ prefix)?
A: Repeatable migrations run every time their checksum changes. They are
   not versioned. Use them for database objects that can be recreated (views,
   stored procedures, functions) — Flyway recreates them whenever the
   file changes.

Q: How does Flyway handle failed migrations?
A: If a migration fails, it records the failure in flyway_schema_history
   (success=false). The application fails to start. After fixing the
   issue, run flyway repair to remove the failed entry, then Flyway will
   attempt the migration again. In PostgreSQL, wrapping in a transaction
   means a failed migration auto-rolls-back.

Q: What is the expand-contract pattern in database migrations?
A: It's a zero-downtime migration strategy:
   1. Expand: add new column (nullable) — backward compatible with old code
   2. Migrate: update code to read/write both columns
   3. Contract: backfill data, then drop old column
   This allows rolling deployments without downtime.
