1. WHAT IS LIQUIBASE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Liquibase is a database migration tool using a "changelog" file containing
ordered "changesets." Each changeset has a unique author+id and runs once.

Key differences from Flyway:
  - Uses XML/YAML/JSON/SQL format (DB-agnostic DSL)
  - Built-in rollback support
  - Preconditions (run only if condition is met)
  - Context support (run only in specific environments)

Master changelog (db/changelog/db.changelog-master.xml):
  <?xml version="1.0" encoding="UTF-8"?>
  <databaseChangeLog
      xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
                          http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-latest.xsd">

      <include file="db/changelog/001-create-users.xml"/>
      <include file="db/changelog/002-create-orders.xml"/>
      <include file="db/changelog/003-add-phone-to-users.xml"/>
  </databaseChangeLog>

4. CHANGESET EXAMPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

001-create-users.xml:
  <databaseChangeLog ...>
      <changeSet id="001" author="alice">
          <createTable tableName="users">
              <column name="id" type="BIGINT" autoIncrement="true">
                  <constraints primaryKey="true" nullable="false"/>
              </column>
              <column name="email" type="VARCHAR(255)">
                  <constraints nullable="false" unique="true"/>
              </column>
              <column name="first_name" type="VARCHAR(100)"/>
              <column name="status" type="VARCHAR(20)" defaultValue="ACTIVE">
                  <constraints nullable="false"/>
              </column>
              <column name="created_at" type="TIMESTAMP" defaultValueDate="CURRENT_TIMESTAMP">
                  <constraints nullable="false"/>
              </column>
              <column name="version" type="BIGINT" defaultValueNumeric="0">
                  <constraints nullable="false"/>
              </column>
          </createTable>
          <createIndex tableName="users" indexName="idx_users_email">
              <column name="email"/>
          </createIndex>

          <rollback>
              <dropTable tableName="users"/>
          </rollback>
      </changeSet>
  </databaseChangeLog>

003-add-phone-to-users.xml:
  <databaseChangeLog ...>
      <changeSet id="003" author="bob">
          <addColumn tableName="users">
              <column name="phone" type="VARCHAR(20)"/>
          </addColumn>

          <rollback>
              <dropColumn tableName="users" columnName="phone"/>
          </rollback>
      </changeSet>
  </databaseChangeLog>

  databaseChangeLog:
    - changeSet:
        id: "001"
        author: alice
        changes:
          - createTable:
              tableName: users
              columns:
                - column:
                    name: id
                    type: BIGINT
                    autoIncrement: true
                    constraints:
                      primaryKey: true
                      nullable: false
                - column:
                    name: email
                    type: VARCHAR(255)
                    constraints:
                      nullable: false
                      unique: true
        rollback:
          - dropTable:
              tableName: users

7. PRECONDITIONS AND CONTEXTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Precondition (run changeset only if table doesn't exist):
  <changeSet id="006" author="dave">
      <preConditions onFail="MARK_RAN">
          <not><tableExists tableName="users"/></not>
      </preConditions>
      <createTable tableName="users"> ... </createTable>
  </changeSet>

Context (run only in specific environments):
  <changeSet id="007" author="eve" context="test">
      <insert tableName="users">
          <column name="email" value="test@example.com"/>
      </insert>
  </changeSet>

  spring.liquibase.contexts=test   # only apply test-context changesets

8. DATABASECHANGELOG TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Liquibase tracks applied changesets in: databasechangelog

Columns:
  id, author, filename, dateexecuted, orderexecuted,
  exectype, md5sum, description, comments, tag, liquibase, contexts

A changeset is identified by (id, author, filename) — must be unique.

9. FLYWAY vs LIQUIBASE DECISION GUIDE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Choose Flyway when:
  - Team prefers writing plain SQL
  - Simpler mental model (sequential version numbers)
  - Smaller team, startup, or less complex migrations

Choose Liquibase when:
  - Need DB-agnostic migrations (abstract createTable, addColumn)
  - Need built-in rollback support
  - Need preconditions or context-based migrations
  - Enterprise environment with complex multi-environment setups

10. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does Liquibase track applied changesets?
A: Liquibase stores applied changeset metadata in the databasechangelog table
   (id, author, filename, md5sum, dateexecuted). It identifies each changeset
   by the combination of id + author + filename. Any attempt to re-run an
   already-applied changeset with a modified checksum results in an error.

Q: What is the advantage of Liquibase over Flyway?
A: Liquibase offers a DB-agnostic DSL (XML/YAML) that can generate the
   appropriate SQL for different databases. It has built-in rollback scripts,
   preconditions, and context-based migrations. Flyway uses plain SQL and
   is simpler but DB-specific and lacks built-in rollback.

Q: What is a precondition in Liquibase?
A: A precondition is a check that must pass before a changeset runs.
   E.g., "only run if this table does NOT exist." onFail can be: HALT
   (error), MARK_RAN (skip and mark as applied), WARN, or CONTINUE.

Q: Can you use SQL in Liquibase changesets?
A: Yes. Use the <sql> or <sqlFile> tag inside a changeset when you need
   DB-specific SQL (e.g., PostgreSQL extensions, complex procedures).
   You can also use the dbms attribute to limit execution to specific databases.

Q: What are Liquibase contexts?
A: Contexts allow changesets to be tagged for specific environments.
   A changeset with context="test" only runs when Liquibase is configured
   with the "test" context. Useful for seeding test data or applying dev-only
   changesets without affecting production.
