1. WHAT IS A TRANSACTION?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A transaction is a unit of work that either:
  - COMMITS: all changes become visible and durable
  - ROLLS BACK: all changes are undone as if they never happened

ACID properties:
  Atomicity    — all or nothing (full commit or full rollback)
  Consistency  — DB constraints always satisfied before/after
  Isolation    — concurrent transactions don't see each other's partial work
  Durability   — committed data survives crashes (write-ahead logging)

2. TRANSACTION IN SPRING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring manages transactions via @Transactional (declarative) using
AOP proxies. The underlying mechanism:
  - Spring wraps the @Transactional method in a proxy
  - Before method: begins transaction (or joins/creates per propagation)
  - After method (no exception): COMMIT
  - After method (RuntimeException or Error): ROLLBACK
  - After method (checked exception): COMMIT by default! (see below)

@Service
@Transactional            // applies to all public methods
public class OrderService {

    @Transactional        // overrides class-level setting
    public Order createOrder(OrderRequest req) {
        User user = userRepo.findById(req.getUserId()).orElseThrow();
        Order order = new Order(user, req.getTotal());
        return orderRepo.save(order);
        // commit on success, rollback on RuntimeException
    }
}

4. ROLLBACK RULES — CRITICAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Default rollback rules:
  RuntimeException (unchecked) → ROLLBACK
  Error                        → ROLLBACK
  Checked Exception            → COMMIT (no rollback!)

Override rollback rules:
  @Transactional(rollbackFor = Exception.class)           // rollback on all exceptions
  @Transactional(rollbackFor = {IOException.class})       // rollback on specific checked
  @Transactional(noRollbackFor = IllegalStateException.class)  // don't rollback on this

5. LOCKING STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Optimistic Locking:
  - Assume no conflicts; detect conflicts at commit time
  - Uses a @Version field (int/Long/timestamp)
  - Throws OptimisticLockException if version mismatch on UPDATE
  - No DB lock held — good for high concurrency reads

Pessimistic Locking:
  - Acquire DB lock immediately on SELECT
  - SELECT FOR UPDATE or SELECT FOR SHARE
  - Blocks other transactions until the lock is released
  - Use when conflict probability is high

6. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What does @Transactional do in Spring?
A: It wraps the method in an AOP proxy that begins a transaction before
   execution, commits on successful return, and rolls back on RuntimeException
   or Error. It manages the Hibernate Session lifecycle within the transaction
   scope.

Q: Does @Transactional roll back on checked exceptions?
A: No, by default. Spring only rolls back on RuntimeException and Error.
   For checked exceptions (like IOException), it commits unless you set
   @Transactional(rollbackFor = Exception.class).

Q: What is the difference between optimistic and pessimistic locking?
A: Optimistic: no DB lock is acquired; a version column is checked at
   UPDATE time. If the version changed, an OptimisticLockException is thrown.
   Good for high read, low conflict scenarios.
   Pessimistic: a DB lock (SELECT FOR UPDATE) is acquired immediately on read.
   Other transactions block until the lock is released. Good for high conflict,
   write-heavy scenarios.
