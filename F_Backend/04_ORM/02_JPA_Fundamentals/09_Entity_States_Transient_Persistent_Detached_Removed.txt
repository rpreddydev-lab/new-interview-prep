================================================================
JPA Entity States: Transient, Persistent, Detached, Removed
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. THE FOUR ENTITY STATES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

                     em.persist()
  TRANSIENT ────────────────────────────► PERSISTENT
  (new User())                            (in persistence context)
      ▲                                        │
      │  em.detach(), close(), clear()         │ em.remove()
      │◄───────────────────────────────────────▼
  DETACHED                                 REMOVED
  (no longer tracked)                     (scheduled for DELETE)
      │
      │ em.merge()
      └──────────────────────────────────► PERSISTENT
                                          (new managed copy returned)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. TRANSIENT STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When: A new Java object created with `new`, not yet associated with
      any persistence context.

Characteristics:
  ✗ Not tracked by any EntityManager
  ✗ No corresponding DB row (or there might be one, but JPA doesn't know)
  ✗ Not in the persistence context
  ✗ Changes are not auto-synchronized to DB

Transitions out:
  → PERSISTENT: em.persist(entity)
  → PERSISTENT: em.merge(entity) — if ID is null or matches no existing entity

Code:
  User user = new User();           // TRANSIENT
  user.setEmail("alice@example.com");
  user.setFirstName("Alice");
  // At this point: no DB row, not tracked, id = null

  em.persist(user);                  // → PERSISTENT
  // Now: tracked, id will be set on flush/commit

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. PERSISTENT (MANAGED) STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When: Entity is associated with an active persistence context.

Characteristics:
  ✓ Tracked by EntityManager
  ✓ Has a DB row (existing) or will have one (pending INSERT)
  ✓ Changes to fields are auto-detected (dirty checking)
  ✓ All changes flushed to DB on transaction commit or explicit flush()
  ✓ Same entity loaded twice in same context = same Java object (identity)

Transitions in:
  ← from TRANSIENT: em.persist(entity)
  ← from DETACHED:  em.merge(entity) — returns new managed copy
  ← from DB:        em.find(), query execution

Transitions out:
  → DETACHED: em.detach(entity), em.clear(), context closes
  → REMOVED:  em.remove(entity)

Code:
  @Transactional
  public void updateEmail(Long userId, String newEmail) {
      User user = em.find(User.class, userId);  // PERSISTENT
      user.setEmail(newEmail);                   // dirty field — tracked
      // commit → Hibernate issues: UPDATE users SET email=? WHERE id=?
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. DETACHED STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When: Entity WAS persistent but its persistence context closed
      (transaction ended), or it was explicitly detached.

Characteristics:
  ✗ No longer tracked by any EntityManager
  ✗ Changes to fields are NOT synchronized to DB
  ✓ Has an ID (was previously persisted)
  ✓ Still has data from when it was detached
  ✓ Can be re-attached with em.merge()

Common causes of detachment:
  - Transaction ends (Spring @Transactional method returns)
  - em.detach(entity) called explicitly
  - em.clear() called (detaches ALL entities)
  - EntityManager closed (em.close())
  - Entity returned from @Transactional method to non-transactional caller

LazyInitializationException:
  Common problem with detached entities + lazy collections:
  @Transactional
  public User getUser(Long id) {
      return userRepository.findById(id).orElseThrow();
      // Entity is detached when this method returns!
  }

  // In controller (no transaction):
  User user = service.getUser(1L);
  user.getOrders().size();  // 💥 LazyInitializationException!
  // Because orders are lazily loaded and entity is now detached

Fixes:
  1. Use @Transactional at higher layer
  2. Use DTO — load everything inside @Transactional
  3. Use JOIN FETCH to load eagerly
  4. Use @EntityGraph
  5. Use @Transactional(readOnly = true) on controller (broad, careful)

Re-attaching with merge():
  @Transactional
  public User reattach(User detachedUser) {
      detachedUser.setFirstName("Updated");
      User managed = em.merge(detachedUser);  // copy state to managed entity
      return managed;
      // managed entity now has "Updated" firstName
      // detachedUser is still detached!
  }

5. REMOVED STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When: em.remove(managedEntity) is called on a MANAGED entity.

Characteristics:
  ✗ Entity still exists in memory
  ✓ Scheduled for DELETE from DB on flush/commit
  ✗ Should not be used after remove() is called

Code:
  @Transactional
  public void deleteUser(Long id) {
      User user = em.find(User.class, id);
      if (user != null) {
          em.remove(user);  // → REMOVED state
          // On commit: DELETE FROM users WHERE id = ?
      }
  }

  // WRONG: Trying to remove a detached entity:
  User detached = ...; // loaded in previous transaction
  em.remove(detached); // 💥 IllegalArgumentException: Detached entity
  // FIX: merge first
  em.remove(em.merge(detached)); // ✓

  // Canceling a remove (re-persist):
  em.persist(removedEntity);  // goes back to PERSISTENT

6. COMPLETE STATE TRANSITION TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Action                    | From State   | To State
──────────────────────────|──────────────|──────────────────
em.persist(e)             | Transient    | Persistent
em.persist(e)             | Detached     | throws IllegalArgumentException
em.persist(e)             | Persistent   | Persistent (no-op)
em.persist(e)             | Removed      | Persistent (undo remove)
em.find() / query         | n/a (in DB)  | Persistent
em.merge(e)               | Transient    | Persistent (new managed copy)
em.merge(e)               | Detached     | Persistent (new managed copy)
em.merge(e)               | Persistent   | Persistent (same obj, no-op)
em.remove(e)              | Persistent   | Removed
em.remove(e)              | Detached     | throws IllegalArgumentException
em.detach(e)              | Persistent   | Detached
em.clear()                | Persistent   | Detached (all entities)
Transaction ends/em.close | Persistent   | Detached

7. PRACTICAL EXAMPLE — FULL LIFECYCLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Service
public class UserService {

    @PersistenceContext
    private EntityManager em;

    @Transactional
    public Long createUser(String email) {
        User user = new User(email);    // TRANSIENT
        em.persist(user);               // → PERSISTENT
        // user.id is null here (before flush)
        em.flush();                     // INSERT executed NOW
        // user.id is now set
        return user.getId();
    }

    @Transactional
    public void updateUser(Long id, String newEmail) {
        User user = em.find(User.class, id);  // PERSISTENT (loaded)
        user.setEmail(newEmail);               // dirty field, auto-tracked
        // No em.save() needed — on commit: UPDATE issued
    }

    @Transactional
    public void deleteUser(Long id) {
        User user = em.find(User.class, id);  // PERSISTENT
        if (user != null) {
            em.remove(user);                   // → REMOVED
        }
        // On commit: DELETE FROM users WHERE id = ?
    }

    // User returned from @Transactional → DETACHED in caller
    public User getUser(Long id) {
        return em.find(User.class, id);  // returns DETACHED entity after method
    }

    @Transactional
    public User updateDetached(User detachedUser) {
        // Re-attach and update:
        return em.merge(detachedUser);   // returns new PERSISTENT copy
    }
}

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the four JPA entity states?
A: Transient (new, not tracked), Persistent (managed by EM),
   Detached (was managed, context closed), Removed (scheduled for DELETE).

Q: What causes LazyInitializationException?
A: Accessing a lazily-loaded collection or association on a DETACHED entity
   (after the transaction/EntityManager has closed). The fix is to load the
   data within the transaction, use JOIN FETCH, or use DTO projections.

Q: What is the difference between em.remove() and a DELETE query?
A: em.remove() works on a single MANAGED entity. It goes through the
   lifecycle (fires @PreRemove callbacks), respects cascades, and deletes
   via object identity. A DELETE query (JPQL or native) is bulk DML that
   bypasses the persistence context, is faster for bulk ops, but doesn't
   fire lifecycle callbacks or update in-memory entities.

Q: What happens to entities when a @Transactional method returns?
A: The transaction commits (flush + commit), and all managed entities
   become DETACHED when the EntityManager scope ends. The caller receives
   a detached entity. Any lazy access on it will throw LazyInitializationException.

Q: Why does merge() return a new object instead of modifying the input?
A: Merge copies the state of the passed object into a managed entity instance.
   If a managed entity with the same ID already exists in the context,
   merge copies to it and returns it. If not, it creates a new managed copy.
   The original detached object is never altered. Always use the return value.
