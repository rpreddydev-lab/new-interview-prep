SPRING DATA PROJECTIONS
========================

=== CONCEPT ===

Projections allow you to retrieve a SUBSET of data from an entity.
Instead of loading the entire entity with all its fields, return only what's needed.

Benefits:
  - Performance: less data transferred from DB
  - Security: don't expose sensitive fields (passwords, internal IDs)
  - Flexibility: different views of same entity for different use cases

Three types: Interface Projections, Class (DTO) Projections, Dynamic Projections.

=== INTERFACE PROJECTIONS (CLOSED) ===

Define an interface with getter methods matching entity fields:

Entity:
  @Entity
  public class User {
      private Long id;
      private String firstName;
      private String lastName;
      private String email;
      private String passwordHash;  // sensitive — don't expose
      private LocalDateTime createdAt;
  }

Closed Interface Projection:
  public interface UserSummary {
      String getFirstName();
      String getLastName();
      String getEmail();
      // passwordHash NOT included
  }

Repository:
  public interface UserRepository extends JpaRepository<User, Long> {
      List<UserSummary> findByLastName(String lastName);
      Optional<UserSummary> findProjectedById(Long id);
  }

Spring Data generates a proxy implementing the interface.
Only projected fields are included in the SQL SELECT.

Generated SQL:
  SELECT u.first_name, u.last_name, u.email FROM user u WHERE u.last_name = ?
  (NOT: SELECT * FROM user)

=== INTERFACE PROJECTIONS (OPEN — WITH SPELEXPRESSIONS) ===

Open projections can compute derived values using @Value and SpEL:

public interface UserView {
    @Value("#{target.firstName + ' ' + target.lastName}")
    String getFullName();

    String getEmail();

    // Compute at projection time
    @Value("#{target.createdAt.getYear()}")
    int getRegistrationYear();
}

Limitation: @Value SpEL → loads entire entity from DB, then computes.
No SQL optimization — use closed projections for performance.

=== CLASS (DTO) PROJECTIONS ===

Use a class (record or DTO) with matching constructor:

// DTO record (Java 16+)
public record UserDto(String firstName, String email) {}

// Or traditional DTO class
public class UserDto {
    private final String firstName;
    private final String email;

    public UserDto(String firstName, String email) {
        this.firstName = firstName;
        this.email = email;
    }
    // getters...
}

Repository with JPQL constructor expression:
  @Query("SELECT new com.example.dto.UserDto(u.firstName, u.email) " +
         "FROM User u WHERE u.active = true")
  List<UserDto> findActiveUserDtos();

  // Or using Spring Data interface + constructor
  List<UserDto> findByActive(boolean active);  // works if constructor args match

SQL: only firstName and email selected.
Less proxy overhead than interface projection.
Better for complex computations (done in Java, not SpEL).

=== DYNAMIC PROJECTIONS ===

Same repository method returns different projections based on type parameter:

public interface UserRepository extends JpaRepository<User, Long> {
    <T> List<T> findByDepartment(String department, Class<T> type);
    <T> Optional<T> findById(Long id, Class<T> type);
}

Usage:
  // Get full entity
  List<User> users = repo.findByDepartment("Engineering", User.class);

  // Get summary projection
  List<UserSummary> summaries = repo.findByDepartment("Engineering",
                                                       UserSummary.class);

  // Get DTO projection
  List<UserDto> dtos = repo.findByDepartment("Engineering", UserDto.class);

Great for generic utility methods or APIs where caller chooses detail level.

=== NESTED PROJECTIONS ===

Project across associations:

public interface OrderSummary {
    Long getId();
    OrderStatus getStatus();
    CustomerInfo getCustomer();  // nested projection

    interface CustomerInfo {
        String getName();
        String getEmail();
    }
}

Spring Data will JOIN and project both Order and Customer fields.

=== CHOOSING THE RIGHT TYPE ===

Type                | SQL Optimization | Computed Fields | Simplicity
--------------------|------------------|-----------------|----------
Closed Interface    | ✅ Yes           | ❌ No           | ✅ High
Open Interface      | ❌ No (loads all) | ✅ SpEL        | ✅ Medium
Class/DTO Projection| ✅ Yes           | ✅ Constructor  | ✅ High
Dynamic Projection  | ✅ Yes           | Depends on type | ✅ Medium

=== PRACTICAL EXAMPLE ===

// For REST API list endpoint — use summary projection (performance)
@GetMapping("/users")
public List<UserSummary> listUsers() {
    return userRepository.findAll(UserSummary.class);  // lightweight
}

// For REST API detail endpoint — use full entity or detailed DTO
@GetMapping("/users/{id}")
public UserDetailDto getUser(@PathVariable Long id) {
    return userRepository.findById(id, UserDetailDto.class)
        .orElseThrow(() -> new UserNotFoundException(id));
}

// For admin API — use full entity
@GetMapping("/admin/users/{id}")
public User getFullUser(@PathVariable Long id) {
    return userRepository.findById(id).orElseThrow(...);
}
