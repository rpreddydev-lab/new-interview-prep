@OneToOne Relationship in JPA
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OneToOne: one instance of A is associated with exactly one instance of B.

Examples:
  User         ↔ UserProfile   (user has one profile)
  Employee     ↔ ParkingSpot   (one parking spot per employee)
  Order        ↔ Invoice       (one invoice per order)

Default fetch: EAGER (always change to LAZY!)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. UNIDIRECTIONAL @ONETONE (FK in owner's table)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
@Table(name = "employees")
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    @JoinColumn(name = "parking_spot_id", unique = true)
    private ParkingSpot parkingSpot;   // FK: employees.parking_spot_id
}

@Entity
@Table(name = "parking_spots")
public class ParkingSpot {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String spotNumber;
    // No reference back to Employee (unidirectional)
}

Generated DDL:
  CREATE TABLE employees (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(255),
    parking_spot_id BIGINT UNIQUE,
    FOREIGN KEY (parking_spot_id) REFERENCES parking_spots(id)
  );

3. BIDIRECTIONAL @ONETONE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String email;

    @OneToOne(mappedBy = "user",           // inverse side — no FK here
              cascade = CascadeType.ALL,
              fetch = FetchType.LAZY,
              orphanRemoval = true)
    private UserProfile profile;

    // Helper method to keep both sides in sync:
    public void setProfile(UserProfile profile) {
        if (profile == null) {
            if (this.profile != null) {
                this.profile.setUser(null);
            }
        } else {
            profile.setUser(this);
        }
        this.profile = profile;
    }
}

@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String bio;
    private String avatarUrl;

    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", unique = true)  // FK here (owning side)
    private User user;
}

Usage:
  User user = new User();
  user.setEmail("alice@example.com");

  UserProfile profile = new UserProfile();
  profile.setBio("Software Engineer");

  user.setProfile(profile);  // sets both sides
  userRepository.save(user); // cascades to UserProfile too

4. @ONETONE WITH SHARED PRIMARY KEY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An alternative design: UserProfile shares the same PK as User.
No separate FK column — the PK of UserProfile IS the FK to User.

@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id
    private Long id;  // same as User.id

    @OneToOne(fetch = FetchType.LAZY)
    @MapsId           // maps the @Id to the FK
    @JoinColumn(name = "id")  // user_profiles.id → users.id
    private User user;

    private String bio;
}

@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToOne(mappedBy = "user", cascade = CascadeType.ALL,
              fetch = FetchType.LAZY)
    private UserProfile profile;
}

Benefits of shared PK:
  ✓ No extra FK column
  ✓ Never loses the parent reference
  ✓ Clean schema

5. LAZY LOADING ISSUE WITH @ONETONE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEM: @OneToOne LAZY does not always work on the INVERSE side.

Hibernate needs to check if the UserProfile exists for this User.
To create a proxy, it needs to know "is there a profile?". If it doesn't
know (no FK on User side), it MUST query the DB → can't be truly lazy!

  On the OWNING side (has @JoinColumn):
    → Lazy works perfectly (Hibernate checks the FK column directly)

  On the INVERSE side (has mappedBy):
    → Hibernate 5: always EAGER unless using bytecode enhancement
    → Hibernate 6: improved, but still potential issue

Solutions:
  1. Use bytecode enhancement (Hibernate-specific, complex)
  2. Use @LazyToOne(LazyToOneOption.NO_PROXY) (Hibernate 5)
  3. Move FK to User table (make User the owner) for true lazy
  4. Use Optional<UserProfile> and handle null manually
  5. Use @Column(name="profile_exists") as a flag (hack)
  6. Map UserProfile lazily via DTO, not entity navigation

6. CASCADE AND ORPHAN REMOVAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@OneToOne(mappedBy = "user",
          cascade = CascadeType.ALL,     // persist, merge, remove, refresh, detach
          orphanRemoval = true)
private UserProfile profile;

Behavior:
  user.setProfile(null);      // profile entity gets DELETE'd (orphanRemoval)
  userRepo.delete(user);      // also DELETE's profile (cascade REMOVE)

When NOT to cascade:
  // If ParkingSpot can be assigned to multiple employees over time,
  // don't cascade REMOVE (deleting an Employee shouldn't delete the spot)
  @OneToOne(fetch = FetchType.LAZY)   // no cascade
  @JoinColumn(name = "parking_spot_id")
  private ParkingSpot parkingSpot;

7. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: In a bidirectional @OneToOne, which side is the owning side?
A: The side with @JoinColumn (the side that has the FK column in its table).
   The other side uses mappedBy. JPA only updates the FK based on changes
   to the owning side.

Q: Why does @OneToOne LAZY not always work?
A: On the INVERSE side (mappedBy), Hibernate doesn't know whether the
   associated entity exists without querying the DB. It can't create a
   meaningful proxy, so it may fall back to EAGER loading. Use bytecode
   enhancement or restructure the relationship to make the FK-holding side
   the one you navigate FROM to get true lazy loading.

Q: What is @MapsId?
A: @MapsId on a @OneToOne mapping means the @Id of the entity is derived
   from the FK to the parent. The child entity's primary key IS the foreign
   key, creating a "shared primary key" design.

Q: When should you use orphanRemoval=true on @OneToOne?
A: When the child entity's lifecycle is fully owned by the parent.
   E.g., UserProfile only makes sense in the context of User. If you
   remove the profile reference from User, the profile row should be deleted.
