================================================================
Hibernate vs JPA — Key Differences
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. CONCEPTUAL RELATIONSHIP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  JPA  = Specification (interface + annotations, no runtime code)
  Hibernate = Implementation of JPA (+ its own extensions)

  Think of it like:
    JPA       ≈ JDBC (the interface)
    Hibernate ≈ MySQL Connector/J (the driver/implementation)
    Or:
    JPA       ≈ Servlet API
    Hibernate ≈ Tomcat / Jetty

2. SIDE-BY-SIDE API COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JPA (Standard)                 | Hibernate Native (Extra)
───────────────────────────────|──────────────────────────────────────
EntityManagerFactory           | SessionFactory
EntityManager                  | Session
EntityTransaction              | Transaction
EntityManager.persist()        | Session.persist() (same)
EntityManager.merge()          | Session.merge() (same)
EntityManager.find()           | Session.get()
EntityManager.getReference()   | Session.load()
EntityManager.remove()         | Session.remove() / delete()
EntityManager.refresh()        | Session.refresh()
EntityManager.clear()          | Session.clear()
EntityManager.detach()         | Session.evict()
EntityManager.contains()       | Session.contains()
EntityManager.flush()          | Session.flush()
JPQL                           | HQL (superset; extra functions)
Criteria API                   | Criteria API (same JPA standard)
@NamedQuery                    | @NamedQuery (same)
@Entity, @Table, @Id, etc.     | Same JPA annotations
@Version                       | Same
@OneToMany, etc.               | Same
@Cacheable                     | @Cache + CacheConcurrencyStrategy
No standard 2LC control        | SessionFactory.getCache() + evict*
No filter concept              | @FilterDef, @Filter, session.enableFilter()
No soft delete standard        | @SQLDelete, @Where, @SQLRestriction
No audit standard              | Hibernate Envers (@Audited)
No natural ID standard         | @NaturalId + session.byNaturalId()
No dynamic SQL                 | @DynamicInsert, @DynamicUpdate
No multi-tenancy standard      | TenantIdentifierResolver
No batch fetch config          | @BatchSize, hibernate.default_batch_fetch_size
No read-only entity marking    | session.setReadOnly(), @Immutable
No StatelessSession            | StatelessSession (for bulk ops)
No ScrollableResults           | ScrollableResults + ScrollMode
No custom user types           | UserType, CompositeUserType

3. NOTABLE HIBERNATE-SPECIFIC ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
  Entity or collection 2LC configuration

@NaturalId
  Marks a business key field; enables session.byNaturalId() lookup

@Immutable
  Entity is never modified after creation; skips dirty checking

@DynamicInsert / @DynamicUpdate
  Generate SQL with only non-null / changed columns

@SQLDelete, @SQLUpdate, @SQLInsert
  Override auto-generated SQL with custom SQL

@Where (deprecated in Hibernate 6 → @SQLRestriction)
  Add a persistent WHERE condition to entity/collection queries

@Filter / @FilterDef
  Dynamic where conditions that can be enabled/disabled per session

@BatchSize
  Configure batch fetching for lazy collections

@Check
  Add DB-level check constraint to DDL

@Type
  Map field to a custom Hibernate type

@Any, @ManyToAny
  Polymorphic association to any entity type

4. PRACTICAL EXAMPLES OF HIBERNATE EXTRAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── @NaturalId ────────────────────────────────────────────────
@Entity
public class User {
    @Id @GeneratedValue private Long id;

    @NaturalId
    @Column(nullable = false, unique = true)
    private String email;
}

// Efficient lookup by natural ID (2LC aware):
User user = session.byNaturalId(User.class)
                   .using("email", "alice@example.com")
                   .load();

── Soft Delete with @SQLDelete + @SQLRestriction ─────────────
@Entity
@SQLDelete(sql = "UPDATE users SET deleted_at = NOW() WHERE id = ?")
@SQLRestriction("deleted_at IS NULL")   // Hibernate 6
// @Where(clause = "deleted_at IS NULL") // Hibernate 5
public class User {
    @Id @GeneratedValue private Long id;
    private String email;
    private LocalDateTime deletedAt;
}

// session.remove(user) → executes UPDATE users SET deleted_at=NOW()
// all queries automatically add WHERE deleted_at IS NULL

── @Filter — Runtime Configurable WHERE ───────────────────────
@FilterDef(
    name = "activeFilter",
    parameters = @ParamDef(name = "isActive", type = Boolean.class)
)
@Filter(name = "activeFilter", condition = "active = :isActive")
@Entity
public class User {
    @Id @GeneratedValue private Long id;
    private boolean active;
}

// Enable per session:
session.enableFilter("activeFilter").setParameter("isActive", true);
List<User> onlyActive = session.createQuery("FROM User", User.class).list();
session.disableFilter("activeFilter");

── @Immutable ─────────────────────────────────────────────────
@Entity
@Immutable  // no dirty checking, read-only, can't be updated
public class AuditLog {
    @Id @GeneratedValue private Long id;
    private String action;
    private LocalDateTime happenedAt;
}

── Hibernate Envers (Audit) ──────────────────────────────────
@Entity
@Audited  // creates users_AUD table automatically
public class User {
    @Id @GeneratedValue private Long id;
    private String email;
}

// Query history:
AuditReader reader = AuditReaderFactory.get(entityManager);
List<Number> revisions = reader.getRevisions(User.class, userId);
User userAtRevision = reader.find(User.class, userId, revisionNumber);

5. WHEN TO USE JPA STANDARD API vs HIBERNATE NATIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use JPA Standard API when:
  ✓ You want portability (might switch from Hibernate to EclipseLink)
  ✓ Writing library code that should work with any JPA provider
  ✓ Team prefers standard APIs

Use Hibernate Native when:
  ✓ Need soft delete, filters, @NaturalId, Envers
  ✓ Need fine-grained cache control
  ✓ Bulk batch operations (StatelessSession)
  ✓ Need @DynamicUpdate for partial updates
  ✓ You're using Spring Boot (Hibernate is the default provider anyway)

Reality: In most Spring Boot applications, you use JPA API for most things
(EntityManager, @Query) but also use Hibernate-specific features
(@DynamicUpdate, @SQLRestriction, 2LC annotations).

6. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Name 5 features Hibernate provides that are NOT in JPA spec.
A: (1) Second-level cache with concurrency strategies (@Cache)
   (2) @NaturalId for business key entity lookup
   (3) Soft deletes via @SQLDelete + @SQLRestriction
   (4) Dynamic filters (@FilterDef / @Filter) per session
   (5) Hibernate Envers for audit history (@Audited)
   Bonus: StatelessSession, @DynamicUpdate, @Immutable

Q: If you code only against the JPA API, can you still use all Hibernate features?
A: JPA-only code gives you entity CRUD, JPQL, Criteria API, @NamedQuery,
   and @Version. For Hibernate extras (2LC, filters, @NaturalId), you need
   to either use Hibernate annotations (@Cache, @Filter) or unwrap the
   EntityManager to get the Hibernate Session.

Q: What is the @Filter annotation?
A: A Hibernate annotation that adds a dynamic SQL WHERE condition to queries.
   Unlike @SQLRestriction (always applied), a @Filter can be enabled or
   disabled per session. Useful for multi-tenancy, soft deletes with override,
   or feature flags at the data access level.

Q: What is Hibernate Envers?
A: An add-on module (hibernate-envers) that automatically tracks entity
   changes in audit tables (e.g., users_AUD). Mark entities with @Audited.
   Hibernate creates revision tables and records before/after state on every
   update. You can query historical states via AuditReader.
