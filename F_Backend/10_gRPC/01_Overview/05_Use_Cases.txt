================================================================
gRPC USE CASES
================================================================

----------------------------------------------------------------
1. MICROSERVICES INTERNAL COMMUNICATION
----------------------------------------------------------------

The PRIMARY and most common use case for gRPC.

Why gRPC excels for microservices:
  - Each service is likely written in a different language
  - High call frequency (thousands of inter-service calls/sec)
  - Need strict API contracts to prevent integration bugs
  - Low latency is critical for user-facing service chains

Typical microservice stack using gRPC:
  
  [Mobile App / Browser]
         │  REST / GraphQL
  [API Gateway / BFF]
         │
  ┌──────┴──────────────────────────────┐
  │         INTERNAL GRPC NETWORK       │
  │                                     │
  │  [OrderService] ──gRPC──→ [InventoryService]
  │       │                           │
  │       └──gRPC──→ [PaymentService] │
  │                       │           │
  │                  [FraudService] ←─┘
  └─────────────────────────────────────┘

Benefits observed in production:
  - Netflix: adopted gRPC for their studio technology platform
  - Lyft: gRPC for all internal service communication
  - Google Cloud APIs: almost entirely gRPC-based
  - Square: gRPC for payment processing microservices

2. REAL-TIME STREAMING APPLICATIONS
----------------------------------------------------------------

2.1 IoT (Internet of Things)
  
  Device → Server streaming:
    - Temperature sensors stream readings every second
    - Client streaming: device batches and streams sensor data
    - Server streaming: server pushes configuration updates to devices
    - Bidirectional: real-time telemetry + command/control
  
  Example:
    service DeviceTelemetry {
      rpc StreamSensorData(stream SensorReading) returns (Ack);
      rpc SubscribeToCommands(DeviceId) returns (stream Command);
    }
  
  Why gRPC beats MQTT here:
    - Type-safe payloads (protobuf vs raw bytes in MQTT)
    - Built-in TLS and auth
    - Back-pressure via HTTP/2 flow control
    - Works well with existing microservice infrastructure

2.2 Financial Trading Systems
  
  Use bidirectional streaming for:
    - Client streams: order requests
    - Server streams: order fills, market data updates, position changes
  
  service TradingService {
    rpc ExecuteTrades(stream OrderRequest) returns (stream TradeEvent);
    rpc StreamMarketData(MarketDataRequest) returns (stream Quote);
  }
  
  Critical gRPC properties for trading:
    - Microsecond-level latency (binary protobuf beats JSON)
    - Low overhead on repeated market data messages
    - Deadline support (cancel stale orders automatically)

2.3 Real-Time Dashboards and Monitoring
  
  Server streaming for metrics:
    service MetricsService {
      rpc StreamMetrics(MetricsFilter) returns (stream MetricsUpdate);
    }
  
  Client subscribes once, server pushes updates continuously.
  Alternative to polling every 5 seconds (wasteful).

2.4 Chat and Collaboration
  
  Bidirectional streaming for real-time messaging:
    service ChatService {
      rpc Chat(stream ChatMessage) returns (stream ChatMessage);
    }
  
  vs WebSocket alternative:
    - gRPC gives type safety on messages
    - Automatic reconnection via channel retry policies
    - Better multi-language support

3. MOBILE CLIENTS (BANDWIDTH CONSTRAINED)
----------------------------------------------------------------

Mobile apps have:
  - Limited bandwidth (especially 3G/4G vs WiFi)
  - Higher latency connections
  - Battery constraints (CPU-intensive JSON parsing drains battery)

gRPC advantages for mobile:
  - Protobuf payloads are 5-10x smaller → less data usage
  - Faster encoding/decoding → less CPU → less battery drain
  - Connection multiplexing → fewer TCP handshakes

gRPC clients for mobile:
  - gRPC-Swift: native iOS/macOS client
  - gRPC-Kotlin: Android native client
  - gRPC-Dart: Flutter (both Android and iOS)

Caveat: Mobile clients often use gRPC-Web or gRPC-Gateway to connect
to backend gRPC services, since direct HTTP/2 from browsers/apps can
have proxy issues.

Real example: Google's internal mobile apps use gRPC/protobuf for
all server communication, claiming significant bandwidth and latency
improvements over JSON REST.

----------------------------------------------------------------
4. POLYGLOT ENVIRONMENTS
----------------------------------------------------------------

Problem without gRPC:
  - Java service team writes a REST API
  - Python ML team consumes it with requests library
  - Go service team also consumes it
  - Node.js frontend BFF also consumes it
  - Every team maintains their own client code
  - When API changes, every team must update manually
  - Type mismatches and contract drift happen often

With gRPC:
  - ONE .proto file defines the API contract
  - Run protoc to generate Java, Python, Go, Node.js client stubs
  - All clients are guaranteed to be compatible with the server
  - API changes are enforced: won't compile if contract violated

Example multi-language setup:
  
  order.proto
  ├── protoc → OrderServiceGrpc.java (server implementation)
  ├── protoc → order_pb2_grpc.py (Python ML client)
  ├── protoc → order.pb.go (Go service client)
  └── protoc → order_grpc.ts (TypeScript BFF client)

5. LARGE DATA TRANSFERS
----------------------------------------------------------------

Chunked/streaming transfers via client streaming:

  service FileService {
    rpc UploadFile(stream FileChunk) returns (UploadResult);
    rpc DownloadFile(FileRequest) returns (stream FileChunk);
  }
  
  message FileChunk {
    bytes data = 1;
    string filename = 2;
    int64 offset = 3;
  }

Benefits over HTTP multipart upload:
  - Progress tracking per chunk
  - Back-pressure (client adjusts upload rate)
  - Resume capability (track offset)
  - Compression per chunk (gzip encoding)

AWS S3 uses gRPC internally for intra-datacenter large object transfers.

----------------------------------------------------------------
6. BACKEND FOR FRONTEND (BFF) PATTERN
----------------------------------------------------------------

BFF aggregates multiple gRPC backend calls for frontend clients:

  [Mobile App]
      │ REST
  [BFF Service (Node.js)]
      │ gRPC ──→ [UserService (Java)]
      │ gRPC ──→ [OrderService (Go)]
      │ gRPC ──→ [ProductService (Python)]

BFF makes 3 gRPC calls (potentially in parallel), aggregates
the data, and returns a single optimized REST/JSON response.

This pattern:
  - Shields internal gRPC services from browser incompatibility
  - Optimizes data for each client type (mobile vs desktop)
  - Allows backend teams to use gRPC freely
  - Frontend team works with familiar REST/JSON

7. SERVICE MESH INTEGRATION (ADVANCED)
----------------------------------------------------------------

Modern service meshes (Istio, Linkerd) have native gRPC support:

Features enabled by gRPC + service mesh:
  - Automatic mTLS between all services
  - gRPC-aware load balancing (round-robin at RPC level, not connection level)
  - Circuit breakers per gRPC method
  - Distributed tracing (headers propagated automatically)
  - Traffic splitting (canary deployments: 10% to new OrderService v2)
  - Retry policies (configured in mesh, not application code)

gRPC health checking protocol:
  service Health {
    rpc Check(HealthCheckRequest) returns (HealthCheckResponse);
    rpc Watch(HealthCheckRequest) returns (stream HealthCheckResponse);
  }
  
  Health check response statuses:
    UNKNOWN = 0
    SERVING = 1
    NOT_SERVING = 2
    SERVICE_UNKNOWN = 3

Kubernetes + gRPC:
  - Kubernetes health probes support gRPC (since K8s 1.24)
  - livenessProbe and readinessProbe can use gRPC health check
  - No need to add an HTTP health endpoint just for K8s probes

----------------------------------------------------------------
8. API GATEWAYS AND PROXIES
----------------------------------------------------------------

8.1 Envoy Proxy
  - Google's Envoy is the de facto gRPC proxy
  - L7 proxy with deep gRPC protocol understanding
  - Features: retries, timeouts, circuit breaking, observability
  - Used by Istio as the sidecar proxy
  
  Envoy gRPC capabilities:
    - HTTP/JSON → gRPC transcoding (gRPC-JSON transcoder filter)
    - gRPC → gRPC load balancing (per-stream, not per-connection)
    - gRPC → REST transcoding for upstream services
    - gRPC Web filter (for browser clients)
    - gRPC stats filter (Prometheus metrics per service/method)

8.2 Kong, AWS API Gateway
  - Support gRPC routing and proxying
  - Rate limiting per gRPC method
  - JWT authentication for gRPC calls

9. MACHINE LEARNING SERVING (TENSORFLOW SERVING)
----------------------------------------------------------------

TensorFlow Serving uses gRPC as its primary protocol:
  
  service PredictionService {
    rpc Predict(PredictRequest) returns (PredictResponse);
    rpc MultiInference(MultiInferenceRequest) returns (MultiInferenceResponse);
    rpc GetModelMetadata(GetModelMetadataRequest) returns (GetModelMetadataResponse);
  }

Why gRPC for ML serving:
  - Large input tensors: binary encoding is crucial
  - High throughput: 1000s of inference requests/second
  - Low latency: protobuf is fast to encode/decode numpy arrays
  - Streaming: stream batch predictions

Triton Inference Server (NVIDIA): also uses gRPC
ONNX Runtime Server: gRPC support
MLflow Serving: gRPC endpoint option

10. KUBERNETES OPERATORS AND CONTROL PLANES
----------------------------------------------------------------

Kubernetes API server itself uses gRPC internally.
Custom Kubernetes operators often use gRPC for:
  - Watch streams (server streaming): watch for pod state changes
  - Control plane components communicating with node agents

Container runtimes (containerd, CRI-O) use CRI (Container Runtime
Interface) — a gRPC interface:
  
  service RuntimeService {
    rpc RunPodSandbox(RunPodSandboxRequest) returns (RunPodSandboxResponse);
    rpc StopPodSandbox(StopPodSandboxRequest) returns (StopPodSandboxResponse);
    rpc CreateContainer(CreateContainerRequest) returns (CreateContainerResponse);
    rpc StartContainer(StartContainerRequest) returns (StartContainerResponse);
  }
  
  service ImageService {
    rpc ListImages(ListImagesRequest) returns (ListImagesResponse);
    rpc PullImage(PullImageRequest) returns (PullImageResponse);
  }

CSI (Container Storage Interface) and CNI (Container Network Interface)
also use gRPC for communication between Kubernetes and storage/network plugins.

11. USE CASE DECISION MATRIX
----------------------------------------------------------------

  Use Case                    │ gRPC │ REST │ GraphQL
  ─────────────────────────────┼──────┼──────┼─────────
  Microservice-to-microservice │  ✅  │  ⚠️  │   ❌
  Public API (third-party)     │  ⚠️  │  ✅  │   ✅
  Real-time streaming          │  ✅  │  ❌  │   ⚠️
  Mobile (bandwidth critical)  │  ✅  │  ⚠️  │   ✅
  Browser clients              │  ❌  │  ✅  │   ✅
  Large file transfers         │  ✅  │  ⚠️  │   ❌
  Polyglot environments        │  ✅  │  ⚠️  │   ⚠️
  ML model serving             │  ✅  │  ⚠️  │   ❌
  IoT high-frequency data      │  ✅  │  ❌  │   ❌
  CRUD operations (simple)     │  ⚠️  │  ✅  │   ✅
  Flexible client queries      │  ❌  │  ❌  │   ✅
  
  ✅ = Best fit    ⚠️ = Works but not ideal    ❌ = Poor fit

----------------------------------------------------------------
12. INTERVIEW ANSWER: "WHEN WOULD YOU USE gRPC?"
----------------------------------------------------------------

"I would choose gRPC primarily for internal microservice-to-microservice
communication where performance, strong typing, and streaming matter.

Specifically, I'd use gRPC when:
1. We have multiple services in different languages and need a
   type-safe, auto-generated contract
2. High throughput is required (financial systems, data pipelines)
3. Real-time streaming is needed (IoT, trading, live dashboards)
4. Bandwidth is a constraint (mobile, IoT devices)

I'd pair it with a REST or GraphQL gateway at the edge for
external clients that can't handle gRPC natively."
