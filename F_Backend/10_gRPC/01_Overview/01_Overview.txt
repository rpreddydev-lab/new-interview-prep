gRPC - COMPREHENSIVE OVERVIEW
================================================================

----------------------------------------------------------------
1. WHAT IS gRPC?
----------------------------------------------------------------
gRPC (Google Remote Procedure Call) is a modern, open-source,
high-performance RPC (Remote Procedure Call) framework developed
by Google and released in 2015. It enables efficient communication
between distributed services across different languages and platforms.

Core Idea:
  - A client calls a method on a server as if it were a local method.
  - The serialization, network transport, and deserialization are
    abstracted away by the framework.
  - Services and messages are defined using Protocol Buffers (protobuf),
    a language-neutral, platform-neutral, extensible mechanism for
    serializing structured data.

Key Components:
  ┌─────────────────────────────────────────────────────┐
  │  .proto file  →  protoc compiler  →  Generated code │
  │                                                     │
  │  Client Stub  →  gRPC channel  →  Server Handler   │
  └─────────────────────────────────────────────────────┘

----------------------------------------------------------------
2. HISTORY AND MOTIVATION
----------------------------------------------------------------
Before gRPC:
  - Google used an internal system called "Stubby" for inter-service RPC.
  - Stubby handled ~10 billion RPCs/second across Google's infrastructure.
  - REST over HTTP/1.1 was the dominant external API pattern but lacked:
      * Strong typing / schema enforcement
      * Code generation
      * Efficient binary serialization
      * Bi-directional streaming
      * Multiplexing

gRPC was created to:
  1. Open-source a battle-tested RPC framework
  2. Use HTTP/2 for transport (multiplexing, header compression, streaming)
  3. Use Protocol Buffers for efficient serialization
  4. Support multiple programming languages natively
  5. Enable all four communication patterns (unary, server/client/bidi streaming)

----------------------------------------------------------------
3. HOW gRPC WORKS - STEP BY STEP
----------------------------------------------------------------

Step 1: Define the service in a .proto file
  ┌──────────────────────────────────────────┐
  │ syntax = "proto3";                       │
  │ package order;                           │
  │                                          │
  │ service OrderService {                   │
  │   rpc CreateOrder (OrderRequest)         │
  │       returns (OrderResponse);           │
  │ }                                        │
  │                                          │
  │ message OrderRequest {                   │
  │   string product_id = 1;                 │
  │   int32  quantity   = 2;                 │
  │ }                                        │
  │                                          │
  │ message OrderResponse {                  │
  │   string order_id = 1;                   │
  │   string status   = 2;                   │
  │ }                                        │
  └──────────────────────────────────────────┘

Step 2: Compile with protoc to generate language-specific code
  - Java: OrderServiceGrpc.java + OrderRequest.java + OrderResponse.java
  - Python: order_pb2.py + order_pb2_grpc.py
  - Go: order.pb.go

Step 3: Implement server logic
  - Extend the generated abstract base class (or implement interface)
  - Override the RPC methods with actual business logic

Step 4: Create a gRPC channel (client side)
  - Channel = persistent connection to a server address
  - Stub = client-side object used to call remote methods

Step 5: Make RPC calls
  - Client calls stub.createOrder(request)
  - Framework serializes request to protobuf binary
  - Sends over HTTP/2
  - Server deserializes, calls handler, serializes response
  - Client receives and deserializes response

----------------------------------------------------------------
4. KEY FEATURES
----------------------------------------------------------------

4.1 Language Agnostic
  - Officially supported: Java, Go, Python, C++, Node.js, Ruby,
    C#, Dart, Kotlin, Swift, PHP, Objective-C
  - Community support for many more
  - A Java client can call a Python server seamlessly

4.2 Strongly Typed Contracts
  - .proto files serve as the API contract
  - Both client and server code is generated from the SAME .proto file
  - Type mismatches are caught at compile time, not runtime
  - Schema changes are versioned and backward compatible

4.3 HTTP/2 Transport
  - Binary framing (not text like HTTP/1.1)
  - Header compression (HPACK)
  - Multiplexing: multiple requests on a single TCP connection
  - Full-duplex communication (both sides can send simultaneously)
  - Stream prioritization
  - Server push capabilities

4.4 Protocol Buffers Serialization
  - Binary format: 5-10x smaller than JSON
  - Serialization/deserialization: 3-10x faster than JSON
  - Self-describing schema with field numbers (not field names on wire)
  - Backward and forward compatible with proper field numbering

4.5 Four Communication Patterns
  - Unary RPC (1 request → 1 response)
  - Server Streaming (1 request → many responses)
  - Client Streaming (many requests → 1 response)
  - Bidirectional Streaming (many requests ↔ many responses)

4.6 Built-in Features
  - Deadlines / Timeouts
  - Cancellation (propagated across service boundaries)
  - Retries with exponential backoff
  - Load balancing (client-side and proxy-side)
  - Authentication (TLS, token-based via metadata)
  - Interceptors (middleware pattern)
  - Health checking protocol (standard)
  - Reflection (server can describe its own API)

6. gRPC vs OTHER RPC FRAMEWORKS
----------------------------------------------------------------

  Framework    | Transport  | Serialization | Streaming | Code Gen
  -------------|------------|---------------|-----------|----------
  gRPC         | HTTP/2     | Protobuf      | Yes (4)   | Yes
  REST         | HTTP/1.1+  | JSON/XML      | No        | No
  GraphQL      | HTTP/1.1+  | JSON          | Limited   | Optional
  Thrift       | TCP/binary | Thrift binary | Yes       | Yes
  SOAP         | HTTP/1.1   | XML           | No        | Yes (WSDL)
  JSON-RPC     | HTTP       | JSON          | No        | No

7. WHEN TO USE gRPC
----------------------------------------------------------------

USE gRPC WHEN:
  ✅ Microservices communicating internally (service-to-service)
  ✅ High-throughput, low-latency requirements
  ✅ Polyglot environments (multiple languages)
  ✅ Streaming data (IoT, real-time updates, large file transfers)
  ✅ Strong type safety and schema enforcement needed
  ✅ Mobile clients where bandwidth efficiency matters

DON'T USE gRPC WHEN:
  ❌ Public-facing APIs where browser clients need direct access
     (requires gRPC-Web or gRPC Gateway as workaround)
  ❌ Simple CRUD with minimal performance requirements
  ❌ Team unfamiliar with protobuf and extra tooling overhead
  ❌ Third-party clients that only understand REST/JSON

----------------------------------------------------------------
8. gRPC ECOSYSTEM
----------------------------------------------------------------

  gRPC-Web      : Allows browsers to call gRPC services via a proxy
  gRPC Gateway  : Transcodes REST/JSON to gRPC and vice versa
  grpc-health   : Standard health check protocol
  grpc-reflect  : Server reflection (allows tools like grpcurl)
  Envoy Proxy   : Production-grade gRPC proxy/load balancer
  grpcurl       : CLI tool to call gRPC services (like curl for gRPC)
  BloomRPC/Kreya/Postman : GUI tools for testing gRPC

----------------------------------------------------------------
9. QUICK MENTAL MODEL FOR INTERVIEWS
----------------------------------------------------------------

"gRPC is to microservice-to-microservice communication what
 REST is to client-to-server web communication. It's faster
 (binary + HTTP/2), strongly typed (protobuf contract), and
 supports streaming — making it ideal for high-performance
 internal APIs and real-time data pipelines."

Key numbers to remember:
  - Protobuf is ~5-10x more compact than JSON
  - gRPC serialization is ~3-10x faster than JSON
  - HTTP/2 supports up to 100 concurrent streams per connection
  - Google Stubby (gRPC's predecessor) handled 10B RPCs/sec
