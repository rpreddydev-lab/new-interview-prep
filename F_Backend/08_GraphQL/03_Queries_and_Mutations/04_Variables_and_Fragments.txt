PART 1: VARIABLES

1. WHAT ARE VARIABLES?
-----------------------
Variables allow you to parameterize GraphQL operations. Instead of
hardcoding values inside the query string, you declare variables and pass
them separately in the request's `variables` JSON.

Without variables (BAD — string interpolation):
```javascript
// NEVER do this — SQL-injection equivalent!
const query = `{ user(id: "${userId}") { name } }`;
```

With variables (CORRECT):
```graphql
query GetUser($userId: ID!) {
  user(id: $userId) { name }
}
```
```json
{ "query": "...", "variables": { "userId": "user-123" } }
```

2. VARIABLE SYNTAX
-------------------
Variables are declared in the operation definition:

```graphql
query OperationName($var1: Type1, $var2: Type2 = defaultValue) {
  field(arg: $var1, otherArg: $var2) { ... }
}
```

  - `$` prefix: all variable names start with `$`
  - Type annotation: every variable must declare its type
  - Default values: optional, specified after `=`
  - Non-null: add `!` to require the variable (error if missing/null)

3. VARIABLE TYPES
------------------
Variables can be of any input type:

```graphql
# Scalars
query Q1($id: ID!, $age: Int, $price: Float, $active: Boolean) { ... }

# Enums
query Q2($status: OrderStatus = PENDING) { ... }

# Input types
query Q3($filter: ProductFilter, $input: CreateUserInput!) { ... }

# Lists
query Q4($ids: [ID!]!, $tags: [String!]) { ... }

# Nested non-null
query Q5($items: [OrderItemInput!]!) { ... }
```

4. VARIABLE EXAMPLES
---------------------
```graphql
# Fetching paginated, filtered, sorted list
query SearchProducts(
  $query: String!
  $filter: ProductFilter
  $orderBy: ProductOrderBy
  $first: Int = 20
  $after: String
) {
  products(
    search: $query
    filter: $filter
    orderBy: $orderBy
    first: $first
    after: $after
  ) {
    edges {
      cursor
      node {
        id
        name
        price
        inStock
      }
    }
    pageInfo {
      hasNextPage
      endCursor
    }
    totalCount
  }
}
```

Variables:
```json
{
  "query": "laptop",
  "filter": {
    "minPrice": 500,
    "maxPrice": 2000,
    "inStock": true,
    "categoryIds": ["cat-1", "cat-2"]
  },
  "orderBy": {
    "field": "PRICE",
    "direction": "ASC"
  },
  "first": 10
}
```

5. VARIABLE DEFAULTS
---------------------
```graphql
query GetUsers(
  $first: Int = 20           # Default 20 if not provided
  $after: String             # null by default (optional)
  $status: UserStatus = ACTIVE  # Default ACTIVE
  $sortDir: SortDirection = DESC
) {
  users(first: $first, after: $after, status: $status, sortDir: $sortDir) {
    edges { node { id name } }
  }
}
```

Rules:
  - Nullable variables get `null` as default if not specified
  - Non-null variables (`$id: ID!`) with no default MUST be provided
  - Default in variable declaration overrides schema default

6. VARIABLE VALIDATION
-----------------------
Variables are validated against their declared type:
  - Type mismatch → error before execution
  - Missing required variable → error before execution
  - Wrong enum value → error
  - Non-null variable is null → error

This is GraphQL's injection protection mechanism.

7. USING VARIABLES WITH DIRECTIVES
------------------------------------
```graphql
query GetUser($id: ID!, $isAdmin: Boolean!, $skipPrivate: Boolean = false) {
  user(id: $id) {
    name
    email @include(if: $isAdmin)
    phone @skip(if: $skipPrivate)
    ... @include(if: $isAdmin) {
      role
      createdAt
      lastLoginAt
    }
  }
}
```

8. WHAT ARE FRAGMENTS?
-----------------------
Fragments are reusable pieces of query logic. They define a set of fields
on a specific type that can be spread into any query.

Benefits:
  ✓ DRY: avoid repeating field selections
  ✓ Colocation: each component defines its own data requirements
  ✓ Consistency: same fields every time you query a type

9. NAMED FRAGMENTS
-------------------
```graphql
# Define the fragment
fragment UserBasicInfo on User {
  id
  name
  email
  avatar
}

fragment PostSummary on Post {
  id
  title
  excerpt
  publishedAt
  author {
    ...UserBasicInfo      # Fragment can include other fragments
  }
}

# Use fragments in queries
query GetHomePage {
  featuredPosts: posts(featured: true, first: 5) {
    edges {
      node {
        ...PostSummary     # Spread the fragment
        category { name }
      }
    }
  }
  currentUser: me {
    ...UserBasicInfo
    notifications(unread: true) { count }
  }
}
```

10. INLINE FRAGMENTS
---------------------
Inline fragments have no name — they're defined inline, typically for
type conditions (interfaces and unions):

```graphql
query GetFeed {
  feed(first: 20) {
    edges {
      node {
        __typename          # The concrete type name
        ... on TextPost {   # Only selected if __typename == "TextPost"
          id
          title
          body
          author { name }
        }
        ... on ImagePost {
          id
          imageUrl
          caption
          dimensions { width height }
        }
        ... on VideoPost {
          id
          videoUrl
          duration
          thumbnailUrl
        }
        ... on SharedPost { # Re-shared content
          id
          originalPost {
            ...on TextPost { id title body }
            ...on ImagePost { id imageUrl }
          }
          sharedBy { name }
        }
      }
    }
  }
}
```

11. FRAGMENT TYPE CONDITIONS
-----------------------------
A fragment must specify the type it applies to:

```graphql
fragment X on User { ... }        # Applies to User type
fragment Y on Node { id }         # Applies to Node interface (any implementing type)
fragment Z on SearchResult { ... } # Applies to SearchResult union
```

When you spread a fragment, it only applies if the runtime type matches:

```graphql
query {
  node(id: "1") {
    id                    # Always applies (from Node interface)
    ...UserFields         # Only applies if this node is a User
    ...ProductFields      # Only applies if this node is a Product
  }
}

fragment UserFields on User {
  name
  email
}

fragment ProductFields on Product {
  name
  price
}
```

12. FRAGMENT COMPOSITION (THE RELAY PATTERN)
---------------------------------------------
Relay popularized "component-collocated fragments": each component defines
its own data requirements as a fragment, and they're composed into the
root query automatically.

```graphql
# UserCard component's data requirements
fragment UserCard_user on User {
  id
  name
  avatar
}

# PostCard component's data requirements
fragment PostCard_post on Post {
  id
  title
  excerpt
  author {
    ...UserCard_user   # PostCard includes UserCard's fragment
  }
  publishedAt
}

# FeedPage component composes PostCard's fragment
fragment FeedPage_post on Post {
  ...PostCard_post
  category { name }
}

# Root query uses all composed fragments
query FeedQuery($first: Int = 20) {
  posts(first: $first) {
    edges {
      node {
        ...FeedPage_post
      }
    }
  }
}
```

This pattern means:
  - Frontend components are self-contained data-wise
  - Adding a field to a component? Just add it to that component's fragment
  - No need to thread props through parent components

13. FRAGMENT VARIABLES (NOT STANDARD YET)
------------------------------------------
Fragments don't support variables natively in the GraphQL spec. Fragments
use variables from the surrounding query:

```graphql
query Q($withDetails: Boolean!) {
  user(id: "1") {
    ...UserFragment  # Fragment can access $withDetails from Q
  }
}

fragment UserFragment on User {
  name
  details @include(if: $withDetails) {
    bio phone address { city }
  }
}
```

The variable MUST be declared in the operation definition, even if used only
in a fragment.

14. FRAGMENT CYCLES (FORBIDDEN)
---------------------------------
Fragments cannot reference themselves directly or indirectly:

```graphql
# ERROR: Fragment cycle!
fragment A on User {
  friends {
    ...B
  }
}

fragment B on User {
  ...A   # Cycle: A → B → A
}
```

GraphQL validation rejects this. Use pagination and separate queries for
recursive/self-referential data.

15. PRACTICAL PATTERNS WITH FRAGMENTS
---------------------------------------
```graphql
# Pagination cursor fragment
fragment PaginationInfo on PageInfo {
  hasNextPage
  hasPreviousPage
  startCursor
  endCursor
}

# Common error fragment
fragment ErrorInfo on UserError {
  field
  message
  code
}

# Mutation with fragments
mutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {
    post {
      ...PostSummary
    }
    userErrors {
      ...ErrorInfo
    }
  }
}
```

16. __TYPENAME IN FRAGMENTS
----------------------------
Always include `__typename` when working with interfaces/unions to help
clients (Apollo Client, etc.) correctly identify types in the cache:

```graphql
query GetNotifications {
  notifications {
    __typename   # Required for Apollo's cache to work correctly
    id
    createdAt
    ... on OrderNotification { order { id status } }
    ... on MessageNotification { sender { name } preview }
    ... on SystemNotification { message severity }
  }
}
```

17. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the purpose of variables in GraphQL?
A: Variables separate dynamic values from the query structure. Benefits:
   (1) Security: prevents injection attacks (values are typed/sanitized),
   (2) Performance: query text is static → enables persisted queries and
       query hashing/caching,
   (3) Readability: query structure is clear, values are in a separate JSON.

Q: What is the difference between named and inline fragments?
A: Named fragments are defined separately with a name and spread with `...Name`.
   They're reusable across multiple queries. Inline fragments (`... on Type {}`)
   are defined inline within a selection set, typically for type conditions
   on interfaces/unions. Both can be used anywhere in queries, mutations, and
   subscriptions.

Q: Can fragments be nested (one fragment include another)?
A: Yes. A fragment can spread other named fragments, creating composable
   data requirements. This is the foundation of Relay's component-collocated
   fragment pattern. The only restriction: no circular fragment references.

Q: Where are fragment variables scoped?
A: Fragment variables come from the enclosing operation definition. If a
   fragment uses `$variable`, that variable must be declared in the query/
   mutation/subscription that spreads the fragment. Fragments themselves
   cannot declare variables (this is a limitation of the current spec;
   fragment arguments are being discussed as a future addition).

Q: What does `__typename` do and why is it important?
A: `__typename` is a meta-field that returns the runtime type name of an
   object (e.g., "User", "Product"). It's crucial for: (1) client-side
   type switching after querying a union/interface, (2) Apollo Client's
   normalized cache (uses `__typename` + `id` as cache key), (3) debugging.

Q: What is the Relay fragment pattern and why is it valuable?
A: Each UI component defines its data requirements as a GraphQL fragment
   named `ComponentName_typeName`. Parent components compose child fragments
   into their own. The root query is the composition of all component fragments.
   Benefits: self-contained components, no prop drilling, precise data
   fetching, easy refactoring (change a component's data, change its fragment).
