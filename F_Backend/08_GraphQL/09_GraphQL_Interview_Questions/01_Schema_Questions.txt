GRAPHQL SCHEMA INTERVIEW QUESTIONS — IN DEPTH
================================================================

Q1: What are the named type categories in GraphQL?
A: There are six named type categories:
   (1) Scalar — leaf types: Int, Float, String, Boolean, ID, + custom
   (2) Object — types with fields: type User { id: ID!, name: String! }
   (3) Interface — abstract set of fields; object types implement it
   (4) Union — type that can be one of several object types (no common fields)
   (5) Enum — restricted set of string values: enum Status { ACTIVE, INACTIVE }
   (6) Input — object types used only in arguments/variables
   Plus wrapping types: NonNull (!) and List ([]).

Q2: What is the difference between an Interface and a Union in GraphQL?
A: Interface defines a common set of fields that implementing types MUST have.
   Clients can query interface fields without inline fragments.
   Union says "this field can return one of these types" — no shared fields.
   To query specific fields on a union member, you MUST use inline fragments.
   Use Interface when types share common fields (e.g., Node { id: ID! }).
   Use Union for disjoint types that have nothing in common (e.g., SearchResult
   can be User | Post | Document — none share fields).

Q3: Why can't you use regular Object types as mutation arguments?
A: Object types can have circular references, interfaces, and union fields
   that make them unsuitable as inputs. GraphQL spec requires Input types
   for mutation arguments because: (1) Input types have no resolver logic
   — they're plain data containers. (2) They cannot reference output types.
   (3) They can define default values. (4) The separation makes the schema
   intent clearer (this is data going IN vs data coming OUT).

Q4: What are NonNull (!) and List types in GraphQL?
A: These are "wrapping types" that modify other types.
   NonNull (!) means the field will never return null; if it does,
   GraphQL propagates an error. List ([]) wraps a type in an array.
   They can be combined: [User!]! means "non-null list of non-null Users".
   [User!] means the list itself can be null but each element is non-null.
   [User]! means non-null list but elements can be null.
   [User] means list and elements can both be null.

Q5: What are the three root types in GraphQL and their purposes?
A: Query — read-only operations (safe to retry, can be cached, run in parallel)
   Mutation — write operations (must be idempotent when possible, run serially)
   Subscription — real-time event streams over WebSocket/SSE
   A schema must have at least a Query type. Mutation and Subscription are optional.

Q6: What is the ID scalar in GraphQL?
A: ID is a special built-in scalar for unique identifiers. It serializes to
   String in responses but can accept both String and Int as input.
   Using ID communicates semantic intent ("this is an identifier") rather
   than just a String or Int. It's opaque — clients shouldn't parse it.
   Relay global IDs encode base64(TypeName:localId) for cross-type uniqueness.

Q7: What is schema-first vs code-first GraphQL?
A: Schema-first: write .graphqls schema files, implement resolvers to match.
   The schema is the source of truth. Used by graphql-java and Spring for GraphQL.
   Advantages: human-readable contract, language-agnostic, versioned separately.
   Code-first: annotate Java/Kotlin classes, auto-generate schema from code
   (e.g., graphql-kotlin, Netflix DGS). The code is the source of truth.
   Advantages: no schema-code sync issues, less ceremony.
   Disadvantages: schema can become Java-centric; harder for API consumers.

Q8: What is the Node interface and why is it used?
A: ```graphql
   interface Node { id: ID! }
   ```
   The Node interface (Relay specification) gives every type a globally
   unique ID. It enables a root-level `node(id: ID!): Node` query that
   can fetch ANY type by its ID. Client frameworks (Apollo Client) use it
   for normalized caching — same ID across types = same cached object.
   The ID encodes the type: base64("User:1") → avoids collisions between
   User ID 1 and Post ID 1.

Q9: How do you model pagination in a GraphQL schema?
A: Two common patterns:
   (1) Offset-based: `users(page: Int, size: Int): UserPage`
       Simple but has issues with live data (cursor is more stable).
   (2) Cursor-based (Relay Connection Spec):
       `users(first: Int, after: String): UserConnection`
       Connection has: `edges: [UserEdge!]!` and `pageInfo: PageInfo!`
       Edge has: `node: User!` and `cursor: String!`
       PageInfo has: `hasNextPage`, `hasPreviousPage`, `startCursor`, `endCursor`
   Cursor-based is more robust for real-time data and is the industry standard.

Q10: What is a payload type in GraphQL mutations?
A: A mutation payload is a dedicated return type wrapping the mutation result:
   ```graphql
   type CreatePostPayload {
     post: Post           # null if failed
     userErrors: [UserError!]!  # empty if succeeded
   }
   ```
   Benefits: (1) Can include userErrors for business-rule failures.
   (2) Can add metadata (e.g., created timestamp, affected row count).
   (3) Allows future additions without breaking clients.
   (4) Consistent pattern across all mutations.

Q11: What is the Relay specification?
A: Relay is a JavaScript client framework by Facebook that imposes conventions
   on GraphQL schemas for optimal caching and performance:
   (1) Node interface: every type has a globally unique ID
   (2) Connection pattern: all list fields use edges/nodes/pageInfo
   (3) Mutations return payload types
   These conventions allow Relay's normalized cache to update efficiently.
   Even non-Relay clients benefit from these schema patterns.

Q12: What are GraphQL schema directives and when would you use a custom one?
A: Directives annotate schema elements or query documents with metadata:
   @deprecated, @skip, @include are built-in.
   Custom directives add cross-cutting concerns to the schema:
   - @auth(role: ADMIN) — declarative authorization
   - @cacheControl(maxAge: 300) — caching hints
   - @rateLimit(max: 10, window: "1m") — rate limiting per field
   - @deprecated(reason: "...") — deprecation
   Custom directives use SchemaDirectiveWiring (Java) to wrap DataFetchers.

Q13: What is an enum in GraphQL and how does it map to Java?
A: An enum defines a fixed set of allowed values:
   ```graphql
   enum Status { ACTIVE INACTIVE SUSPENDED }
   ```
   In Java, this maps to a Java enum. Spring for GraphQL auto-converts.
   Enums serialize to their string name in responses. Note: internal Java
   enum values can differ from schema names (e.g., INACTIVE in schema
   might map to Status.DISABLED in Java with a custom resolver).

Q14: What is a custom scalar in GraphQL?
A: Built-in scalars (Int, Float, String, Boolean, ID) aren't enough for
   domain types. Custom scalars let you define: Date, DateTime, BigDecimal,
   UUID, Email, URL, JSON, etc. They have three coercion functions:
   serialize (output → JSON), parseValue (JSON input → Java), parseLiteral
   (inline literal → Java). Use graphql-java-extended-scalars for common ones.
