  1. THE CIRCUIT BREAKER PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Without circuit breakers, a failing downstream service causes cascading
failures — callers pile up waiting for timeouts, exhaust thread pools,
and the entire system degrades.

Circuit Breaker States:
  CLOSED   → normal operation; calls pass through; failure rate monitored
  OPEN     → calls fail immediately without hitting the downstream service
             (fail fast, fallback executed)
  HALF_OPEN → after a wait, a limited number of test calls pass through;
              if they succeed → back to CLOSED; if fail → back to OPEN

Transition rules:
  CLOSED → OPEN      when failure rate exceeds threshold (e.g., > 50%)
  OPEN   → HALF_OPEN after waitDurationInOpenState (e.g., 30 seconds)
  HALF_OPEN → CLOSED if permitted calls succeed
  HALF_OPEN → OPEN   if permitted calls fail

  2. RESILIENCE4J MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Module           | Description
-----------------|----------------------------------------------
CircuitBreaker   | Open/close based on failure rate or slow calls
Retry            | Retry on exception with backoff
TimeLimiter      | Fail if call exceeds timeout
Bulkhead         | Limit concurrent calls (thread-pool or semaphore)
RateLimiter      | Limit calls per time window
Cache            | Lightweight in-memory caching

# application.yml
resilience4j:

  circuitbreaker:
    instances:
      paymentService:
        sliding-window-type: COUNT_BASED       # or TIME_BASED
        sliding-window-size: 10                # last 10 calls evaluated
        minimum-number-of-calls: 5             # need at least 5 before opening
        failure-rate-threshold: 50             # open if ≥ 50% fail
        slow-call-rate-threshold: 80           # open if ≥ 80% calls are slow
        slow-call-duration-threshold: 2s       # slow = takes > 2 seconds
        wait-duration-in-open-state: 30s       # stay open for 30s
        permitted-number-of-calls-in-half-open-state: 3
        automatic-transition-from-open-to-half-open-enabled: true
        record-exceptions:
          - java.lang.Exception

  retry:
    instances:
      paymentService:
        max-attempts: 3
        wait-duration: 500ms
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2
        retry-exceptions:
          - java.io.IOException
          - org.springframework.web.client.HttpServerErrorException
        ignore-exceptions:
          - org.springframework.web.client.HttpClientErrorException.BadRequest

  timelimiter:
    instances:
      paymentService:
        timeout-duration: 3s
        cancel-running-future: true

  bulkhead:
    instances:
      paymentService:
        max-concurrent-calls: 10        # semaphore bulkhead
        max-wait-duration: 100ms

  ratelimiter:
    instances:
      paymentService:
        limit-for-period: 100           # max 100 calls
        limit-refresh-period: 1s        # per second
        timeout-duration: 0ms           # fail immediately if limit exceeded

  5. ANNOTATION-BASED USAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Service
public class PaymentService {

    // CircuitBreaker + TimeLimiter + Retry (stacked via annotations)
    @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
    @TimeLimiter(name = "paymentService")
    @Retry(name = "paymentService")
    @Bulkhead(name = "paymentService", type = Bulkhead.Type.SEMAPHORE)
    public CompletableFuture<PaymentResult> processPayment(PaymentRequest request) {
        return CompletableFuture.supplyAsync(() ->
            paymentGateway.charge(request.getAmount(), request.getCardToken())
        );
    }

    // Fallback — MUST have same return type and parameters + Throwable
    private CompletableFuture<PaymentResult> paymentFallback(
            PaymentRequest request, Throwable ex) {
        log.error("Payment fallback triggered: {}", ex.getMessage());
        return CompletableFuture.completedFuture(
            PaymentResult.failed("PAYMENT_SERVICE_UNAVAILABLE")
        );
    }
}

Note on annotation stacking order (outermost to innermost):
  Retry → CircuitBreaker → TimeLimiter → Bulkhead

  6. PROGRAMMATIC API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Service
public class InventoryClient {

    private final CircuitBreakerRegistry circuitBreakerRegistry;
    private final RestClient restClient;

    public ProductStock checkStock(Long productId) {
        CircuitBreaker cb = circuitBreakerRegistry.circuitBreaker("inventoryService");

        return cb.executeSupplier(() ->
            restClient.get()
                .uri("http://inventory-service/api/stock/{id}", productId)
                .retrieve()
                .body(ProductStock.class)
        );
    }

    // With fallback using Try
    public ProductStock checkStockWithFallback(Long productId) {
        CircuitBreaker cb = circuitBreakerRegistry.circuitBreaker("inventoryService");

        return Try.ofSupplier(CircuitBreaker.decorateSupplier(cb, () ->
            fetchStock(productId)))
            .recover(CallNotPermittedException.class, e -> ProductStock.unavailable())
            .recover(Exception.class, e -> ProductStock.unavailable())
            .get();
    }
}

Q: What are the three states of a circuit breaker and what triggers each?
A: CLOSED (normal) → OPEN when failure rate exceeds threshold.
   OPEN (failing fast, no calls to downstream) → HALF_OPEN after
   waitDurationInOpenState. HALF_OPEN (testing recovery) → CLOSED if
   test calls succeed, → OPEN if they fail.

Q: What is the difference between Circuit Breaker and Retry?
A: Retry re-attempts a failed call immediately (with optional backoff) —
   useful for transient failures. Circuit Breaker stops calling a service
   entirely when failure rate is high — prevents overwhelming an already-
   struggling service. They complement each other: Retry handles individual
   failures; CircuitBreaker handles systematic failure.

Q: What is the Bulkhead pattern?
A: Bulkhead limits the number of concurrent calls to a service. Semaphore
   bulkhead uses a counter (max concurrent calls); thread-pool bulkhead
   uses a separate thread pool per service. Prevents one slow service from
   consuming all threads/resources and affecting unrelated services.

Q: What happens when a CircuitBreaker annotation method is called and the circuit is OPEN?
A: Spring throws CallNotPermittedException. If a fallbackMethod is defined,
   it is called with the original request + exception as arguments. The
   fallback returns a default/cached response.

Q: How is Resilience4j different from Hystrix?
A: Hystrix is deprecated (Netflix put it in maintenance mode in 2018).
   Resilience4j is lightweight (no Thread pool per command by default,
   uses semaphore/FunctionalInterfaces), modular (separate jars per
   pattern), reactive-friendly (Reactor/RxJava support), and Spring Boot
   auto-configured. Resilience4j is the recommended replacement.
