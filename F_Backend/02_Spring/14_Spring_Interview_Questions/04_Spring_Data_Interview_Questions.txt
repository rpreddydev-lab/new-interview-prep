Q1. What is Spring Data JPA and how does it relate to JPA/Hibernate?
─────────────────────────────────────────────────────────────────────
Answer:
  JPA (Jakarta Persistence API):
    A specification defining a standard ORM interface for Java.
    Defines: @Entity, @Id, EntityManager, JPQL, etc.

  Hibernate:
    The most popular JPA IMPLEMENTATION. It implements the JPA spec plus
    additional Hibernate-specific features (HQL, second-level cache, etc.).

  Spring Data JPA:
    An ABSTRACTION layer on top of any JPA implementation.
    Eliminates boilerplate DAO/Repository code by providing:
      - Repository interfaces (CrudRepository, JpaRepository, etc.)
      - Derived query methods (findByLastNameAndAge)
      - JPQL / native query support via @Query
      - Pagination and sorting support
      - Specification API (dynamic queries)
      - Auditing support (@CreatedDate, @LastModifiedDate)

  Stack: Spring Data JPA → JPA (spec) → Hibernate (impl) → JDBC → Database

Q2. Explain the Spring Data Repository hierarchy.
──────────────────────────────────────────────────
Answer:
  Repository<T, ID>
    └── CrudRepository<T, ID>
          save(S entity), saveAll(Iterable<S>)
          findById(ID), findAll(), findAllById(Iterable<ID>)
          existsById(ID), count()
          delete(T), deleteById(ID), deleteAll()
          └── PagingAndSortingRepository<T, ID>
                findAll(Sort sort)
                findAll(Pageable pageable) → Page<T>
                └── JpaRepository<T, ID>          ← MOST COMMONLY USED
                      saveAndFlush(T)
                      saveAllAndFlush(Iterable<S>)
                      deleteAllInBatch()
                      deleteInBatch(Iterable<T>)
                      getById(ID)   (lazy reference; getOne deprecated)
                      findAll(Example<S>)    (Query by Example)
                      flush()

  Reactive variants:
    ReactiveCrudRepository     → returns Mono<T> / Flux<T>
    ReactiveSortingRepository
    R2dbcRepository (Spring Data R2DBC)

  Custom base repository:
    @NoRepositoryBean                            // tells Spring not to create instance
    public interface SoftDeleteRepository<T, ID> extends JpaRepository<T, ID> {
        List<T> findAllActive();
    }

Q3. How do derived query methods work?
────────────────────────────────────────
Answer:
  Spring Data parses the method name and generates the JPQL query automatically.

  Naming conventions:
    find…By, read…By, get…By, query…By, search…By — SELECT
    count…By                                       — COUNT
    exists…By                                      — EXISTS
    delete…By, remove…By                           — DELETE

  Examples:
    List<User> findByLastName(String lastName);
    Optional<User> findByEmail(String email);
    List<User> findByAgeGreaterThan(int age);
    List<User> findByAgeBetween(int min, int max);
    List<User> findByLastNameContainingIgnoreCase(String part);
    List<User> findByActiveTrue();
    List<User> findByLastNameAndFirstName(String last, String first);
    List<User> findByLastNameOrFirstName(String last, String first);
    List<User> findByAddressCity(String city);  // traverses associations
    long countByActive(boolean active);
    boolean existsByEmail(String email);
    void deleteByLastName(String lastName);

    // With sorting:
    List<User> findByActiveOrderByLastNameAsc(boolean active);

    // With pagination:
    Page<User> findByActive(boolean active, Pageable pageable);
    Slice<User> findByActive(boolean active, Pageable pageable);

  Limiting results:
    User findFirstByOrderByLastNameAsc();
    List<User> findTop3ByActiveOrderByCreatedAtDesc(boolean active);

Q4. What is the difference between @Query JPQL and Native Query?
────────────────────────────────────────────────────────────────
Answer:
  JPQL (Java Persistence Query Language):
    Object-oriented query language; works on entities (not tables/columns).
    Database-agnostic.

    @Query("SELECT u FROM User u WHERE u.email = :email AND u.active = true")
    Optional<User> findActiveByEmail(@Param("email") String email);

    // Named parameters (:param) — recommended
    // Positional parameters (?1) — avoid for readability

    // Update / Delete:
    @Modifying
    @Transactional
    @Query("UPDATE User u SET u.active = false WHERE u.lastLoginAt < :date")
    int deactivateInactiveUsers(@Param("date") LocalDateTime date);

  Native Query:
    Raw SQL; works on tables/columns.
    Database-specific; but sometimes necessary for performance or complex SQL.

    @Query(value = "SELECT * FROM users WHERE email = :email",
           nativeQuery = true)
    Optional<User> findByEmailNative(@Param("email") String email);

    // Native query with pagination:
    @Query(value = "SELECT * FROM users WHERE active = 1",
           countQuery = "SELECT COUNT(*) FROM users WHERE active = 1",
           nativeQuery = true)
    Page<User> findAllActive(Pageable pageable);

  @Modifying annotation:
    Required for UPDATE/DELETE queries.
    clearAutomatically = true: clears the persistence context after execution
    flushAutomatically = true: flushes before execution

Q5. How does Pagination and Sorting work in Spring Data?
─────────────────────────────────────────────────────────
Answer:
  Pageable interface:
    Created using PageRequest:
    Pageable pageable = PageRequest.of(0, 10, Sort.by("lastName").ascending()
                                                  .and(Sort.by("firstName")));

  Page<T>:
    Full page result with metadata:
    page.getContent()           → List<T>
    page.getTotalElements()     → total records across all pages
    page.getTotalPages()        → total number of pages
    page.getNumber()            → current page (0-based)
    page.getSize()              → page size
    page.isFirst() / isLast()   → boundary checks
    page.hasNext() / hasPrevious()

  Slice<T>:
    Lighter than Page — no total count query.
    Knows if there's a next page (hasNext()) but not total count.
    More efficient for large datasets or "load more" UI patterns.

  REST Controller example:
    @GetMapping("/users")
    public Page<UserDTO> getUsers(
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "20") int size,
            @RequestParam(defaultValue = "lastName") String sortBy) {

        Pageable pageable = PageRequest.of(page, size, Sort.by(sortBy));
        return userRepository.findAll(pageable)
                             .map(userMapper::toDto);
    }

  Spring Data Web Support (auto-resolves Pageable from request params):
    @EnableSpringDataWebSupport in config
    GET /users?page=0&size=20&sort=lastName,asc&sort=firstName,asc

Q6. Explain @Transactional propagation levels.
──────────────────────────────────────────────
Answer:
  Propagation defines how transactions interact when methods call each other.

  REQUIRED (default):
    Use existing transaction if present; otherwise create new one.
    Both methods share the same transaction.
    If inner method fails and outer catches: outer is also marked for rollback!
    → Most common; use for service-to-service calls.

  REQUIRES_NEW:
    Always create a NEW transaction; suspend existing one.
    Inner transaction commits/rolls back independently.
    Use case: audit logging that should succeed even if main tx fails.

  NESTED:
    Create a NESTED transaction (savepoint) within existing transaction.
    Inner transaction can roll back independently (to savepoint); outer continues.
    Outer rollback also rolls back inner.
    Only supported by JDBC (not JTA/XA).

  SUPPORTS:
    Use existing transaction if present; otherwise run non-transactionally.
    Use for read-only operations that don't require a transaction.

  NOT_SUPPORTED:
    Always run non-transactionally; suspend existing transaction.

  MANDATORY:
    Must be called within an existing transaction; throws if none exists.

  NEVER:
    Must NOT be called within a transaction; throws if one exists.

  Example:
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAuditLog(AuditEvent event) { ... }

Q7. Explain @Transactional isolation levels.
─────────────────────────────────────────────
Answer:
  Isolation prevents concurrency anomalies between transactions.

  Anomalies:
    Dirty Read:           reading uncommitted data of another tx
    Non-Repeatable Read:  re-reading same row yields different result (update)
    Phantom Read:         re-executing query yields different rows (insert/delete)

  Isolation Levels:
                          Dirty Read  Non-Rep Read  Phantom Read
    READ_UNCOMMITTED         YES          YES           YES
    READ_COMMITTED           NO           YES           YES   (most DBs default)
    REPEATABLE_READ          NO           NO            YES   (MySQL InnoDB default)
    SERIALIZABLE             NO           NO            NO    (slowest)

  @Transactional(isolation = Isolation.REPEATABLE_READ)
  public SomeData getConsistentData(Long id) { ... }

  DEFAULT: uses the database's default isolation level.

Q8. What happens when @Transactional is used on a private method?
──────────────────────────────────────────────────────────────────
Answer:
  @Transactional has NO effect on private methods.

  Reason: Spring uses CGLIB/JDK proxies. When you call a private method,
  it's called directly on the bean (not through the proxy), so the
  transactional interceptor never runs.

  Same issue with:
    - private methods
    - protected methods (with JDK proxy)
    - self-invocation (calling @Transactional method from same class)

  Solution: Move the transactional logic to a separate Spring bean, or use
  AspectJ compile-time/load-time weaving (not proxy-based).

Q9. What is the difference between @Transactional readOnly = true and false?
────────────────────────────────────────────────────────────────────────────
Answer:
  @Transactional(readOnly = true):
    • Hint to the framework and database that no write operations will occur
    • Hibernate optimizations:
        - Skips dirty checking (no snapshot comparison at flush)
        - Doesn't flush persistence context at all
        - Potentially routes to read replica (if configured)
    • Slight performance boost for read-heavy operations
    • Does NOT prevent writes at DB level (just a hint)

  Best practice:
    @Transactional(readOnly = true) on service classes/methods that only read
    @Transactional on methods that write

    @Service
    @Transactional(readOnly = true)   // default for all methods
    public class UserService {

        public List<User> findAll() { return userRepo.findAll(); } // readOnly

        @Transactional   // overrides class-level; readOnly = false
        public User create(CreateUserRequest req) { ... }
    }

Q10. What is the N+1 Select Problem and how do you solve it?
─────────────────────────────────────────────────────────────
Answer:
  N+1 Problem:
    When fetching N parent entities, JPA fires 1 query for parents + N queries
    for each child collection (one per parent) = N+1 queries total.

  Example:
    List<Order> orders = orderRepo.findAll(); // 1 query: SELECT * FROM orders
    for (Order o : orders) {
        o.getItems().size(); // N queries: SELECT * FROM items WHERE order_id = ?
    }
    // For 100 orders → 101 queries!

  Solutions:

  1. EAGER loading (bad practice for collections!):
     @OneToMany(fetch = FetchType.EAGER)
     — Always loads children, even when not needed; cartesian product issues.

  2. JOIN FETCH in JPQL (BEST for specific queries):
     @Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.status = 'ACTIVE'")
     List<Order> findActiveOrdersWithItems();
     — Single query with JOIN; fetches all data at once.

  3. @EntityGraph:
     @EntityGraph(attributePaths = {"items", "customer"})
     List<Order> findByStatus(String status);
     — Spring Data generates JOIN FETCH automatically.

  4. @NamedEntityGraph:
     @NamedEntityGraph(name = "Order.detail",
         attributeNodes = {
             @NamedAttributeNode("items"),
             @NamedAttributeNode(value = "customer", subgraph = "customer-address")
         })
     @Entity class Order { ... }

  5. Batch fetching (Hibernate-specific):
     @BatchSize(size = 20) on the collection
     — Hibernate fetches children in batches (20 at a time instead of 1).

  6. @Fetch(FetchMode.SUBSELECT):
     — Hibernate fetches all children with a single IN subselect query.

  Interview Tip: Detect N+1 with:
    - Hibernate statistics: spring.jpa.properties.hibernate.generate_statistics=true
    - Datasource-proxy / p6spy — logs every SQL query

Q11. Explain FetchType LAZY vs EAGER.
──────────────────────────────────────
Answer:
  LAZY (default for @OneToMany, @ManyToMany):
    The related entities are NOT loaded until explicitly accessed.
    Queries triggered on first access of the collection/association.
    Risk: LazyInitializationException if accessed outside a transaction.

  EAGER (default for @ManyToOne, @OneToOne):
    The related entities are loaded IMMEDIATELY with the parent.
    Always fetched, even if not needed.

  Best practices:
    • All relationships should be LAZY by default.
    • Use JOIN FETCH, @EntityGraph, or projections to eagerly load WHEN needed.
    • Never make @OneToMany or @ManyToMany EAGER → cartesian product / N+1.

  LazyInitializationException fix:
    1. Ensure access is within a transaction (@Transactional on service).
    2. Use JOIN FETCH to load eagerly in the query.
    3. Use @Transactional(readOnly=true) in controller (Open Session in View) —
       DISCOURAGED; leads to performance issues.
    4. Use DTOs/projections — avoid entity exposure outside service layer.

Q12. What is Optimistic vs Pessimistic Locking?
────────────────────────────────────────────────
Answer:
  Optimistic Locking:
    Assumes conflicts are RARE; doesn't lock rows.
    Detects conflict at COMMIT time using a version field.
    If two transactions read + modify same row, the second commit fails
    with OptimisticLockException.

    @Entity
    public class Product {
        @Id private Long id;
        @Version private Integer version;  // auto-incremented by JPA
        private int stock;
    }

    Use case: high-read, low-write scenarios (shopping cart, blog posts).
    Retry logic often needed on OptimisticLockException.

  Pessimistic Locking:
    Locks the row at READ time; other transactions must wait.
    Used when conflicts are LIKELY and data integrity is critical.

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);

    Lock modes:
      PESSIMISTIC_READ  — shared lock; others can read but not write
      PESSIMISTIC_WRITE — exclusive lock; others cannot read or write
      PESSIMISTIC_FORCE_INCREMENT — exclusive lock + increments @Version

    Use case: financial transactions, inventory management.
    Risk: deadlocks if not careful; performance impact.

Q13. How do you map One-to-Many and Many-to-Many relationships?
───────────────────────────────────────────────────────────────
Answer:
  One-to-Many (bidirectional):
    @Entity
    public class Order {
        @Id @GeneratedValue private Long id;

        @OneToMany(mappedBy = "order",     // "order" = field in OrderItem
                   cascade = CascadeType.ALL,
                   fetch = FetchType.LAZY,
                   orphanRemoval = true)
        private List<OrderItem> items = new ArrayList<>();

        // helper methods to maintain bidirectional sync:
        public void addItem(OrderItem item) {
            items.add(item);
            item.setOrder(this);
        }
    }

    @Entity
    public class OrderItem {
        @Id @GeneratedValue private Long id;

        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "order_id")
        private Order order;
    }

  Many-to-Many:
    @Entity
    public class Student {
        @ManyToMany(cascade = {CascadeType.PERSIST, CascadeType.MERGE})
        @JoinTable(
            name = "student_course",
            joinColumns = @JoinColumn(name = "student_id"),
            inverseJoinColumns = @JoinColumn(name = "course_id"))
        private Set<Course> courses = new HashSet<>();
    }

    @Entity
    public class Course {
        @ManyToMany(mappedBy = "courses")
        private Set<Student> students = new HashSet<>();
    }

  CascadeType values:
    PERSIST — cascade save
    MERGE   — cascade update
    REMOVE  — cascade delete (careful with M2M!)
    REFRESH — cascade refresh from DB
    DETACH  — cascade detach from context
    ALL     — all of the above

  orphanRemoval = true: when item removed from collection, it's deleted from DB.

Q14. What are Spring Data Projections?
───────────────────────────────────────
Answer:
  Projections fetch only SPECIFIC fields from the database instead of full entities.
  Improves performance by reducing data transfer.

  1. Interface-based Projection (closed):
     interface UserSummary {
         String getFirstName();
         String getLastName();
         String getEmail();
     }
     List<UserSummary> findByActive(boolean active);
     → Spring generates a proxy; SELECT firstName, lastName, email FROM users

  2. Open Projection (SpEL in interface):
     interface UserSummary {
         @Value("#{target.firstName + ' ' + target.lastName}")
         String getFullName();
     }

  3. Class-based Projection (DTO):
     public record UserDTO(String firstName, String lastName, String email) {}

     @Query("SELECT new com.example.UserDTO(u.firstName, u.lastName, u.email) " +
            "FROM User u WHERE u.active = true")
     List<UserDTO> findActiveUserDTOs();

  4. Dynamic Projection:
     <T> List<T> findByActive(boolean active, Class<T> type);
     // Call: repo.findByActive(true, UserSummary.class)

Q15. What is the Specifications API (Criteria API)?
────────────────────────────────────────────────────
Answer:
  Specification<T> enables type-safe, dynamic query building using JPA Criteria API.
  Repository must extend JpaSpecificationExecutor<T>.

  interface UserRepository extends JpaRepository<User, Long>,
                                     JpaSpecificationExecutor<User> {}

  Building specifications:
    public class UserSpecifications {
        public static Specification<User> hasEmail(String email) {
            return (root, query, cb) ->
                email == null ? cb.conjunction() : cb.equal(root.get("email"), email);
        }

        public static Specification<User> isActive() {
            return (root, query, cb) -> cb.isTrue(root.get("active"));
        }

        public static Specification<User> olderThan(int age) {
            return (root, query, cb) -> cb.greaterThan(root.get("age"), age);
        }
    }

  Composing specifications:
    Specification<User> spec = where(hasEmail(email))
        .and(isActive())
        .and(olderThan(18));

    Page<User> result = userRepository.findAll(spec, pageable);

  Use case: Dynamic search/filter APIs where different combinations of
  filters are applied depending on input.

Q16. How does Spring Data Auditing work?
─────────────────────────────────────────
Answer:
  Spring Data automatically populates audit fields like creation/modification
  timestamps and users.

  Enable:
    @EnableJpaAuditing(auditorAwareRef = "auditorProvider")
    @Configuration public class JpaConfig { ... }

  Entity:
    @Entity
    @EntityListeners(AuditingEntityListener.class)
    public class Order {
        @CreatedDate
        @Column(updatable = false)
        private LocalDateTime createdAt;

        @LastModifiedDate
        private LocalDateTime updatedAt;

        @CreatedBy
        @Column(updatable = false)
        private String createdBy;

        @LastModifiedBy
        private String lastModifiedBy;
    }

  AuditorAware (who is making changes):
    @Component("auditorProvider")
    public class SecurityAuditorAware implements AuditorAware<String> {
        @Override
        public Optional<String> getCurrentAuditor() {
            return Optional.ofNullable(SecurityContextHolder.getContext()
                .getAuthentication())
                .map(Authentication::getName);
        }
    }

Q17. How does Spring Cache abstraction work?
─────────────────────────────────────────────
Answer:
  Spring Cache provides a consistent caching API regardless of the underlying
  cache provider (ConcurrentHashMap, Caffeine, Redis, EhCache, etc.).

  Enable: @EnableCaching on a @Configuration class.

  @Cacheable — cache the result; skip method if cache hit:
    @Cacheable(value = "users", key = "#id")
    public User findById(Long id) { /* DB call */ }
    // Second call with same id → return from cache, no DB call

  @CachePut — always execute method AND update cache:
    @CachePut(value = "users", key = "#user.id")
    public User update(User user) { return userRepo.save(user); }

  @CacheEvict — remove entry from cache:
    @CacheEvict(value = "users", key = "#id")
    public void delete(Long id) { userRepo.deleteById(id); }

    @CacheEvict(value = "users", allEntries = true)
    public void clearAll() { }

  @Caching — combine multiple cache operations:
    @Caching(
        evict = {
            @CacheEvict("users"),
            @CacheEvict(value = "usersByEmail", key = "#user.email")
        }
    )
    public void deleteUser(User user) { }

  @CacheConfig — class-level default:
    @CacheConfig(cacheNames = "users")
    @Service
    public class UserService { ... }

  Condition and Unless:
    @Cacheable(value="users", condition="#id > 0", unless="#result == null")

  Redis cache config:
    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .disableCachingNullValues()
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair.fromSerializer(
                    new GenericJackson2JsonRedisSerializer()));
        return RedisCacheManager.builder(factory).cacheDefaults(config).build();
    }

Q18. What is the difference between save() and saveAndFlush()?
───────────────────────────────────────────────────────────────
Answer:
  save(entity):
    Persists entity to persistence context (first-level cache).
    Actual SQL may be delayed until transaction commit or manual flush.
    Hibernate batches SQL by default → better performance.

  saveAndFlush(entity):
    Persists AND immediately flushes the persistence context → SQL executed NOW.
    Useful when you need the DB to reflect changes before further processing
    within the same transaction.
    Slightly less performant (no batching).

Q19. What is the difference between getById(), findById(), and getReferenceById()?
────────────────────────────────────────────────────────────────────────────────
Answer:
  findById(id):
    → Optional<T>; immediately issues SELECT query; null-safe.
    Use when you need the full entity or want to handle "not found".

  getReferenceById(id) (formerly getById, formerly getOne):
    → T; returns a LAZY PROXY; no immediate SELECT.
    SELECT issued only when you actually access a property.
    Throws EntityNotFoundException if entity doesn't exist at access time.
    Use when you only need the reference (e.g., setting a FK relationship):
      order.setCustomer(customerRepo.getReferenceById(customerId));

Q20. How do you handle schema migrations in Spring Boot?
─────────────────────────────────────────────────────────
Answer:
  spring.jpa.hibernate.ddl-auto options:
    none         — no action (for production)
    validate     — validates schema vs entities; fails if mismatch
    update       — updates schema (dangerous in production)
    create       — drops and creates every startup
    create-drop  — creates on startup, drops on shutdown

  RECOMMENDED: Use Flyway or Liquibase for production schema management.

  Flyway:
    spring-boot-starter-data-jpa + flyway-core
    spring.flyway.enabled=true
    SQL files in: src/main/resources/db/migration/
    File naming: V{version}__{description}.sql
      V1__Create_users_table.sql
      V2__Add_email_index.sql
    Flyway tracks applied migrations in flyway_schema_history table.

  Liquibase:
    spring.liquibase.change-log=classpath:db/changelog/master.xml
    Supports XML, YAML, JSON, SQL changesets.
    Tracks in databasechangelog table.

Q21. What is a First-Level Cache vs Second-Level Cache in Hibernate?
─────────────────────────────────────────────────────────────────────
Answer:
  First-Level Cache (Session Cache):
    • Per EntityManager (Session) / per transaction
    • Always enabled; cannot be disabled
    • Entities loaded within a transaction are cached in the session
    • Guarantees no duplicate instances of the same entity within a session
    • Cleared on transaction commit / EntityManager close

  Second-Level Cache:
    • Shared across EntityManagers (sessions); application-level
    • Optional; disabled by default
    • Providers: EhCache, Caffeine, Redis, Infinispan, Hazelcast
    • Reduces DB hits across different transactions

    Enable:
      spring.jpa.properties.hibernate.cache.use_second_level_cache=true
      spring.jpa.properties.hibernate.cache.region.factory_class=\
          org.hibernate.cache.jcache.JCacheRegionFactory

    @Entity
    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
    public class Product { ... }

  Query Cache:
    Caches JPQL query RESULTS (not just entities).
    Must enable separately:
      spring.jpa.properties.hibernate.cache.use_query_cache=true
    @QueryHints({ @QueryHint(name = HINT_CACHEABLE, value = "true") })
