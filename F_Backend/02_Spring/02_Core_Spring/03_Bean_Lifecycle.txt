================================================================
  SPRING BEAN LIFECYCLE — IN DEPTH
================================================================

================================================================
OVERVIEW
================================================================

  Spring manages the entire lifecycle of beans — from creation
  to destruction. Understanding this is critical for:
    • Proper resource management (DB connections, thread pools)
    • Custom initialization / cleanup logic
    • Performance optimization

================================================================
BEAN LIFECYCLE PHASES (SINGLETON SCOPE)
================================================================

  1.  Bean Definition Loading
  2.  BeanFactory Post Processing (BeanFactoryPostProcessor)
  3.  Bean Instantiation (constructor called)
  4.  Property Population (@Autowired, @Value, setter injection)
  5.  BeanPostProcessor — postProcessBeforeInitialization()
  6.  @PostConstruct method (JSR-250)
  7.  InitializingBean.afterPropertiesSet()
  8.  Custom init-method (initMethod in @Bean or XML)
  9.  BeanPostProcessor — postProcessAfterInitialization()
  10. Bean READY (in use by application)
  11. @PreDestroy method (JSR-250)
  12. DisposableBean.destroy()
  13. Custom destroy-method

================================================================
INITIALIZATION HOOKS — ORDER
================================================================

  Order  | Mechanism                          | Code
  -------|------------------------------------|--------------------------
  1st    | @PostConstruct                     | @PostConstruct void init()
  2nd    | InitializingBean.afterPropertiesSet| implements InitializingBean
  3rd    | @Bean(initMethod = "setup")        | void setup() { ... }

  Best practice: Use @PostConstruct (Java standard, no Spring coupling).

  ── @PostConstruct EXAMPLE ──────────────────────────────────────

  @Service
  public class CacheWarmer {

      @Autowired
      private ProductRepository repo;

      private List<Product> hotProducts;

      @PostConstruct
      public void warmCache() {
          // Called AFTER injection, before bean is available
          hotProducts = repo.findTop100ByOrderBySalesDesc();
          System.out.println("Cache warmed with " + hotProducts.size() + " products");
      }
  }

  ── InitializingBean EXAMPLE ────────────────────────────────────

  @Service
  public class ConnectionPool implements InitializingBean {

      private DataSource dataSource;

      @Override
      public void afterPropertiesSet() throws Exception {
          // Validate configuration after injection
          if (dataSource == null) throw new IllegalStateException("DataSource required");
          dataSource.getConnection().close(); // test connectivity
      }
  }

  ── Custom init-method EXAMPLE ──────────────────────────────────

  @Bean(initMethod = "initialize", destroyMethod = "shutdown")
  public KafkaConsumer kafkaConsumer() {
      return new KafkaConsumer();
  }

================================================================
DESTRUCTION HOOKS — ORDER
================================================================

  Order  | Mechanism                   | Code
  -------|-----------------------------|---------------------------------
  1st    | @PreDestroy                 | @PreDestroy void cleanup()
  2nd    | DisposableBean.destroy()    | implements DisposableBean
  3rd    | @Bean(destroyMethod="...")  | void close() { ... }

  ── @PreDestroy EXAMPLE ─────────────────────────────────────────

  @Service
  public class SchedulerService {

      private ScheduledExecutorService scheduler =
          Executors.newScheduledThreadPool(4);

      @PreDestroy
      public void shutdown() {
          System.out.println("Shutting down scheduler...");
          scheduler.shutdown();
          try {
              if (!scheduler.awaitTermination(5, TimeUnit.SECONDS)) {
                  scheduler.shutdownNow();
              }
          } catch (InterruptedException e) {
              scheduler.shutdownNow();
          }
      }
  }

  NOTE: @PreDestroy is NOT called for prototype-scoped beans
        (Spring doesn't track prototype instances after creation).

================================================================
BeanPostProcessor — DEEP DIVE
================================================================

  BeanPostProcessor intercepts EVERY bean after creation.
  Spring itself uses it extensively:
    - AutowiredAnnotationBeanPostProcessor  → processes @Autowired
    - CommonAnnotationBeanPostProcessor     → processes @PostConstruct, @PreDestroy
    - PersistenceAnnotationBeanPostProcessor→ processes @PersistenceContext

  Custom BeanPostProcessor:
  ──────────────────────────
  @Component
  public class LoggingBeanPostProcessor implements BeanPostProcessor {

      @Override
      public Object postProcessBeforeInitialization(Object bean, String beanName) {
          System.out.println("Before init: " + beanName);
          return bean; // return original or a wrapper/proxy
      }

      @Override
      public Object postProcessAfterInitialization(Object bean, String beanName) {
          System.out.println("After init: " + beanName);
          // This is where AOP proxies are created by Spring
          return bean;
      }
  }

================================================================
BeanFactoryPostProcessor — MODIFYING BEAN DEFINITIONS
================================================================

  Runs BEFORE any bean is instantiated. Used to modify bean
  definitions (e.g., PropertySourcesPlaceholderConfigurer).

  @Component
  public class CustomBeanFactoryPostProcessor
      implements BeanFactoryPostProcessor {

      @Override
      public void postProcessBeanFactory(
              ConfigurableListableBeanFactory beanFactory) {
          BeanDefinition bd = beanFactory.getBeanDefinition("myService");
          bd.setScope(BeanDefinition.SCOPE_PROTOTYPE);
          System.out.println("Modified scope of myService");
      }
  }

================================================================
AWARE INTERFACES — CALLBACKS FOR FRAMEWORK INTERNALS
================================================================

  Interface                  | What it injects
  ---------------------------|------------------------------------------
  BeanNameAware              | Bean's own name in container
  BeanFactoryAware           | BeanFactory reference
  ApplicationContextAware    | Full ApplicationContext
  EnvironmentAware           | Environment (properties/profiles)
  MessageSourceAware         | MessageSource (i18n)
  ResourceLoaderAware        | ResourceLoader
  ApplicationEventPublisherAware | Event publisher

  Example:
  @Component
  public class DynamicRouter implements ApplicationContextAware {

      private ApplicationContext context;

      @Override
      public void setApplicationContext(ApplicationContext ctx) {
          this.context = ctx;
      }

      public void routeToHandler(String type) {
          EventHandler handler = context.getBean(type, EventHandler.class);
          handler.handle();
      }
  }

  PREFER: @Autowired ApplicationContext ctx
  (same result, cleaner, avoids interface coupling)

================================================================
LIFECYCLE DIAGRAM (SINGLETON)
================================================================

  Container startup
       │
       ├─► Load BeanDefinitions (XML / annotations / @Configuration)
       │
       ├─► BeanFactoryPostProcessor.postProcessBeanFactory()
       │      (property placeholder resolution, definition tweaks)
       │
       ├─► Instantiate singleton beans
       │      Constructor / factory-method called
       │
       ├─► Populate properties
       │      @Autowired, @Value, setter injection
       │
       ├─► Aware callbacks (BeanNameAware, ApplicationContextAware…)
       │
       ├─► BeanPostProcessor.postProcessBeforeInitialization()
       │
       ├─► @PostConstruct
       │
       ├─► InitializingBean.afterPropertiesSet()
       │
       ├─► Custom init-method
       │
       ├─► BeanPostProcessor.postProcessAfterInitialization()
       │      ← AOP proxy creation happens here
       │
       ├─► Bean READY FOR USE
       │
  Container shutdown (ctx.close() or JVM shutdown hook)
       │
       ├─► @PreDestroy
       ├─► DisposableBean.destroy()
       └─► Custom destroy-method

================================================================
PROTOTYPE BEAN LIFECYCLE DIFFERENCE
================================================================

  • Spring creates a new instance every time one is requested.
  • Spring does NOT call @PreDestroy / DisposableBean.destroy()
    on prototypes — YOUR code is responsible for cleanup.
  • BeanPostProcessors DO apply to prototypes (before/after init).

================================================================
INTERVIEW QUESTIONS — BEAN LIFECYCLE
================================================================

  Q: What is the order of lifecycle callbacks in Spring?
  A: @PostConstruct → afterPropertiesSet → custom init-method
     (all after property injection). Destruction: @PreDestroy →
     destroy() → custom destroy-method.

  Q: What is BeanPostProcessor and where is it used?
  A: An extension point to intercept all beans before/after init.
     Spring uses it to create AOP proxies and process @Autowired.

  Q: Is @PreDestroy called for prototype beans?
  A: No. Spring doesn't track prototype instances after creation,
     so @PreDestroy is never called for prototypes.

  Q: What is the difference between BeanPostProcessor and
     BeanFactoryPostProcessor?
  A: BeanFactoryPostProcessor runs before bean instantiation and
     modifies BeanDefinitions. BeanPostProcessor runs after
     instantiation and modifies bean instances.

  Q: When would you use @PostConstruct vs constructor init?
  A: @PostConstruct runs after all dependencies are injected
     (constructor runs before injection). Use @PostConstruct when
     initialization logic needs injected dependencies.
