  1. AUTHENTICATION VS AUTHORIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Authentication = Who are you?
  → Verify identity via credentials (username/password, JWT, certificate)
  → Produces an Authentication object with principal + authorities

Authorization = What can you do?
  → Check if authenticated user has permission to perform an action
  → Implemented via roles, permissions, and access rules

  2. AUTHENTICATION FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Request with credentials
      │
  AuthenticationFilter (e.g., UsernamePasswordAuthenticationFilter)
      │  Creates UsernamePasswordAuthenticationToken (unauthenticated)
      ▼
  AuthenticationManager (ProviderManager)
      │  Delegates to registered AuthenticationProviders
      ▼
  AuthenticationProvider (DaoAuthenticationProvider)
      │  1. Calls UserDetailsService.loadUserByUsername(username)
      │  2. Calls PasswordEncoder.matches(rawPwd, encodedPwd)
      │  3. Returns authenticated token on success
      ▼
  SecurityContextHolder.getContext().setAuthentication(token)
      │
  Request proceeds to controller

On failure:
  AuthenticationException → 401 Unauthorized
  (handled by AuthenticationEntryPoint)

  3. CUSTOM AUTHENTICATION — LOGIN ENDPOINT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@RestController
@RequestMapping("/api/auth")
public class AuthController {

    private final AuthenticationManager authManager;
    private final JwtService jwtService;

    @PostMapping("/login")
    public ResponseEntity<TokenResponse> login(
            @RequestBody @Valid LoginRequest request) {

        // Throws BadCredentialsException if invalid
        Authentication auth = authManager.authenticate(
            new UsernamePasswordAuthenticationToken(
                request.email(), request.password()));

        SecurityUserAdapter userDetails = (SecurityUserAdapter) auth.getPrincipal();
        String token = jwtService.generateToken(userDetails);

        return ResponseEntity.ok(new TokenResponse(token));
    }
}

  4. AUTHORIZATION — URL BASED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

.authorizeHttpRequests(auth -> auth
    // Public endpoints (no authentication required)
    .requestMatchers("/api/auth/**", "/api/public/**").permitAll()
    .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()

    // Role-based
    .requestMatchers("/api/admin/**").hasRole("ADMIN")      // checks ROLE_ADMIN
    .requestMatchers("/api/manager/**").hasAnyRole("ADMIN", "MANAGER")

    // Authority-based (more granular, no ROLE_ prefix)
    .requestMatchers("/api/reports").hasAuthority("READ_REPORTS")
    .requestMatchers("/api/users/delete").hasAuthority("DELETE_USER")

    // Authenticated only
    .anyRequest().authenticated()
)

hasRole("ADMIN")          → checks for GrantedAuthority "ROLE_ADMIN"
hasAuthority("ADMIN")     → checks for GrantedAuthority "ADMIN" exactly
                            (no ROLE_ prefix added)

Order matters: requestMatchers are evaluated in declaration order.
More specific rules must come BEFORE broader ones.

  5. AUTHORIZATION — METHOD LEVEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Enable method security:
  @Configuration
  @EnableMethodSecurity  // Spring Security 6 (replaces @EnableGlobalMethodSecurity)
  public class SecurityConfig { ... }

@PreAuthorize  — checked BEFORE method execution
@PostAuthorize — checked AFTER method execution (can access return value)
@PreFilter     — filter input collection
@PostFilter    — filter output collection

Examples:
  @PreAuthorize("hasRole('ADMIN')")
  public void deleteUser(Long id) { ... }

  @PreAuthorize("hasAuthority('READ_ORDERS') or #userId == authentication.name")
  public List<Order> getOrders(String userId) { ... }

  // Access return value with returnObject
  @PostAuthorize("returnObject.owner == authentication.name")
  public Document getDocument(Long id) { ... }

  // SpEL expressions
  @PreAuthorize("hasRole('ADMIN') and #user.tenantId == authentication.details.tenantId")
  public void updateUser(User user) { ... }

  // Use custom bean in expression
  @PreAuthorize("@orderService.canAccess(#orderId, authentication)")
  public Order getOrder(Long orderId) { ... }

  6. ROLES VS AUTHORITIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Spring Security treats roles as authorities with a ROLE_ prefix:
  - ROLE_ADMIN is stored as a GrantedAuthority
  - hasRole("ADMIN") checks for "ROLE_ADMIN"
  - hasAuthority("ADMIN") checks for exactly "ADMIN"
  - hasAuthority("ROLE_ADMIN") is equivalent to hasRole("ADMIN")

Best practice: Use fine-grained permissions (authorities) rather than
just roles for complex applications:

  enum Permission {
      USER_READ, USER_WRITE, USER_DELETE,
      ORDER_READ, ORDER_WRITE
  }

  // Load in UserDetailsService
  List<GrantedAuthority> authorities = user.getRoles().stream()
      .flatMap(role -> role.getPermissions().stream())
      .map(p -> new SimpleGrantedAuthority(p.name()))
      .collect(Collectors.toList());

  7. CUSTOM ACCESS DENIED HANDLER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Component
public class CustomAccessDeniedHandler implements AccessDeniedHandler {

    @Override
    public void handle(HttpServletRequest request,
                       HttpServletResponse response,
                       AccessDeniedException ex) throws IOException {
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json");
        response.getWriter().write(
            """
            {"error":"FORBIDDEN","message":"You don't have permission to access this resource"}
            """);
    }
}

// Register in security config:
http.exceptionHandling(ex -> ex
    .authenticationEntryPoint(customEntryPoint)     // 401
    .accessDeniedHandler(customAccessDeniedHandler) // 403
);

  8. REMEMBER-ME AND SESSION MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Session management (for stateful apps):
  .sessionManagement(session -> session
      .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
      .maximumSessions(1)                    // prevent concurrent sessions
      .maxSessionsPreventsLogin(true)        // block new login if max reached
      .expiredUrl("/login?expired")
  )

For stateless REST APIs:
  .sessionManagement(session -> session
      .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
  )

Q: What is the difference between 401 and 403 in Spring Security?
A: 401 Unauthorized means the request lacks valid authentication credentials.
   Spring returns 401 when authentication fails (AuthenticationException).
   403 Forbidden means the user is authenticated but lacks permission.
   Spring returns 403 when authorization fails (AccessDeniedException).

Q: What is AuthenticationManager vs AuthenticationProvider?
A: AuthenticationManager (ProviderManager) is the facade — it receives
   an Authentication token and delegates to a list of AuthenticationProviders.
   AuthenticationProvider does the actual work: DaoAuthenticationProvider
   loads UserDetails and verifies the password. You can register multiple
   providers for different authentication mechanisms.

Q: What is the difference between hasRole and hasAuthority?
A: hasRole("ADMIN") automatically prepends "ROLE_" and checks for
   "ROLE_ADMIN" in granted authorities. hasAuthority("ADMIN") checks
   for exactly "ADMIN". Use hasRole for role-based checks (when storing
   "ROLE_" prefix), hasAuthority for fine-grained permission checks.

Q: How does @PreAuthorize differ from URL-based security?
A: URL-based security (.authorizeHttpRequests) operates at the HTTP
   layer in the filter chain — protects based on URL patterns.
   @PreAuthorize operates at the method level using Spring AOP —
   works anywhere (service, repository, not just controllers).
   Method security provides finer granularity and can access method
   arguments and return values in SpEL expressions.

Q: What is SessionCreationPolicy.STATELESS?
A: It tells Spring Security never to create or use an HTTP session
   for authentication. Each request must carry full credentials
   (e.g., JWT). This is appropriate for REST APIs where the server
   should not maintain session state. SecurityContext is not saved
   between requests.
