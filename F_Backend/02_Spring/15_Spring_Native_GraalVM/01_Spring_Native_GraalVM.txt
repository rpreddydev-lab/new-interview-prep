SPRING NATIVE AND GRAALVM
==========================

=== CONCEPT ===

GraalVM Native Image compiles a Java application AHEAD-OF-TIME (AOT) into
a native executable. No JVM needed at runtime.

Traditional JVM:
  Source → Bytecode (.class) → JVM interprets/JIT-compiles at runtime
  Startup: 3-10 seconds, High memory footprint (JVM heap + metaspace)

Native Image:
  Source → Bytecode → GraalVM AOT compiler → OS native binary (ELF/Mach-O)
  Startup: <100ms, Much lower memory footprint

Spring Boot 3.x has first-class Native Image support (Spring Framework 6+).
Spring Boot 2.x needed spring-native experimental library (deprecated).

=== KEY BENEFITS ===

1. Fast startup: <100ms vs seconds — critical for serverless (AWS Lambda, Azure Functions)
2. Low memory: ideal for container environments (fewer resources, lower cost)
3. No JVM overhead: smaller container images
4. Instant peak performance: no JIT warmup period

=== KEY LIMITATIONS ===

1. Dynamic features need hints:
   - Reflection (Class.forName, Method.invoke)
   - JNI (Java Native Interface)
   - Dynamic proxies (CGLIB)
   - Resource loading (getResourceAsStream)
   GraalVM cannot automatically handle these — must provide hints or reachability metadata.

2. Long build time: native compilation is slow (minutes vs seconds for JAR)
3. Not all libraries support native (improving rapidly)
4. Debugging is harder than JVM
5. Profile-guided optimization not available in all scenarios

=== BUILD SETUP ===

pom.xml:
  <parent>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-parent</artifactId>
      <version>3.2.0</version>
  </parent>

  <build>
      <plugins>
          <plugin>
              <groupId>org.graalvm.buildtools</groupId>
              <artifactId>native-maven-plugin</artifactId>
          </plugin>
          <plugin>
              <groupId>org.springframework.boot</groupId>
              <artifactId>spring-boot-maven-plugin</artifactId>
          </plugin>
      </plugins>
  </build>

Build native executable:
  ./mvnw -Pnative native:compile

Build native Docker image (using Buildpacks, no Docker knowledge needed):
  ./mvnw -Pnative spring-boot:build-image

=== AOT PROCESSING ===

Spring Boot 3 adds an AOT processing phase between compile and runtime.
During AOT processing Spring:
  1. Analyzes all @Bean, @Component, @Configuration definitions
  2. Generates Java source code for bean factory (no reflection at runtime)
  3. Generates native-image hints (reflect-config.json, proxy-config.json, etc.)

Generated sources are in: target/spring-aot/main/sources/
Generated hints are in:   target/spring-aot/main/resources/META-INF/native-image/

You can inspect these to understand what Spring is doing.

=== PROVIDING CUSTOM HINTS ===

For code GraalVM cannot analyze statically:

Method 1: @RegisterReflectionForBinding
  @RegisterReflectionForBinding(MyDto.class)  // on @Configuration class
  Registers all fields/methods for reflection (useful for JSON serialization).

Method 2: RuntimeHintsRegistrar
  @Component
  @ImportRuntimeHints(MyHints.class)
  public class MyConfig { }

  public class MyHints implements RuntimeHintsRegistrar {
      @Override
      public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
          // Reflection hint
          hints.reflection()
               .registerType(MyService.class, MemberCategory.INVOKE_DECLARED_METHODS);
          // Resource hint
          hints.resources().registerPattern("data/*.json");
          // Proxy hint
          hints.proxies().registerJdkProxy(MyInterface.class);
          // Serialization hint
          hints.serialization().registerType(MySerializable.class);
      }
  }

Method 3: reachability-metadata.json (manual, in META-INF/native-image/)
  For third-party libraries — contribute to GraalVM reachability metadata repo.

=== TESTING NATIVE IMAGE ===

Test in JVM mode with AOT processing (fast):
  ./mvnw -PnativeTest test

This catches most native-related issues without full native compilation.
Runs tests against AOT-generated code in JVM mode.

Full native test (slow, most accurate):
  ./mvnw -Pnative test

=== COMMON ISSUES AND FIXES ===

Issue: ClassNotFoundException at runtime
Fix: Add reflection hint for the class

Issue: NoClassDefFoundError for dynamic proxy
Fix: hints.proxies().registerJdkProxy(TheInterface.class)

Issue: Resource not found
Fix: hints.resources().registerPattern("myfile.json")

Issue: Cannot serialize/deserialize with Jackson
Fix: @RegisterReflectionForBinding(MyDto.class) or Jackson native support module

Issue: @Value with SpEL expressions not working
Fix: Simple @Value("${prop}") works. Complex SpEL may need AOT support.

=== SUPPORTED LIBRARIES ===

First-class native support (Spring Boot 3):
  - Spring Web (MVC and WebFlux)
  - Spring Data (JPA, MongoDB, Redis)
  - Spring Security
  - Spring Batch
  - Spring Integration
  - Micrometer + Prometheus

=== GRAALVM NATIVE VS JVM — WHEN TO CHOOSE ===

Choose Native Image:
  - Serverless functions (Lambda) — cold start matters
  - CLI tools
  - Microservices with tight resource budgets
  - Many short-lived instances

Stay with JVM:
  - Long-running services (JIT eventually outperforms native)
  - Applications using many non-native-compatible libraries
  - When development iteration speed matters more
  - When debugging complexity is a concern
