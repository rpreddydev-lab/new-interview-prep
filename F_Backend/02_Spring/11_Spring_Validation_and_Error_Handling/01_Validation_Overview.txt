@Valid vs @Validated:
  @Valid    — standard JSR-380; triggers default validation group; cannot specify groups
  @Validated — Spring's; required for method-level validation in services; supports groups

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    // Validate request body
    @PostMapping
    public ResponseEntity<Order> create(@Valid @RequestBody CreateOrderRequest request) {
        ...
    }

    // Validate path variable
    @GetMapping("/{id}")
    public Order findById(@PathVariable @Positive Long id) {
        ...
    }

    // @Validated on class enables method-level validation for path vars and params
}

// Service-level validation
@Service
@Validated
public class OrderService {

    public Order placeOrder(@Valid CreateOrderRequest request) { ... }

    public Order findById(@Positive @NotNull Long id) { ... }
}

Groups allow different validations for create vs update operations.

// Define group marker interfaces
public interface OnCreate {}
public interface OnUpdate {}

public class ProductRequest {

    @Null(groups = OnCreate.class)      // must be null on create (ID auto-generated)
    @NotNull(groups = OnUpdate.class)   // must be present on update
    private Long id;

    @NotBlank(groups = {OnCreate.class, OnUpdate.class})
    private String name;

    @Positive(groups = OnCreate.class)
    private BigDecimal price;
}

@PutMapping("/{id}")
public Product update(
    @PathVariable Long id,
    @Validated(OnUpdate.class) @RequestBody ProductRequest request) {
    ...
}

@PostMapping
public Product create(
    @Validated(OnCreate.class) @RequestBody ProductRequest request) {
    ...
}

  5. GLOBAL ERROR HANDLING WITH @ControllerAdvice
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@RestControllerAdvice
public class GlobalExceptionHandler {

    // Bean validation failures (invalid request body)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ProblemDetail handleValidationErrors(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                f -> f.getDefaultMessage() != null ? f.getDefaultMessage() : "invalid",
                (a, b) -> a + "; " + b));    // merge duplicate field errors

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        pd.setProperty("errors", errors);
        return pd;
    }

    // @PathVariable / @RequestParam constraint violations
    @ExceptionHandler(ConstraintViolationException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ProblemDetail handleConstraintViolation(ConstraintViolationException ex) {
        Map<String, String> errors = ex.getConstraintViolations().stream()
            .collect(Collectors.toMap(
                v -> v.getPropertyPath().toString(),
                ConstraintViolation::getMessage));
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Constraint violation");
        pd.setProperty("errors", errors);
        return pd;
    }

    // Business domain exceptions
    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ProblemDetail handleNotFound(OrderNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    // Catch-all
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ProblemDetail handleUnexpected(Exception ex) {
        log.error("Unexpected error", ex);
        return ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR, "An unexpected error occurred");
    }
}

Spring Boot 3.x / Spring 6 introduces ProblemDetail implementing RFC 7807.

Standard JSON shape:
{
  "type": "https://example.com/errors/order-not-found",
  "title": "Order Not Found",
  "status": 404,
  "detail": "Order with ID 42 does not exist",
  "instance": "/api/orders/42"
}

// Enable RFC 7807 problem responses for built-in exceptions:
# application.yml
spring:
  mvc:
    problemdetails:
      enabled: true  # Spring Boot 3.x default: true

// ProblemDetail with custom properties:
ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Order already exists");
pd.setTitle("Duplicate Order");
pd.setType(URI.create("https://myapp.com/errors/duplicate-order"));
pd.setProperty("orderId", existingOrderId);

Q: What is the difference between @Valid and @Validated?
A: @Valid is the standard Jakarta Bean Validation annotation — it triggers
   validation using the default group. It works for @RequestBody in controllers.
   @Validated is Spring's annotation — it additionally supports validation groups
   (to apply different rules for create vs update) and enables method-level
   validation on service beans (path vars, return values). For basic @RequestBody
   validation, both work; for groups or service-level, use @Validated.

Q: What exception is thrown when @Valid validation fails?
A: MethodArgumentNotValidException for @RequestBody failures. This extends
   BindException and contains BindingResult with all field errors. For @PathVariable
   and @RequestParam constraint violations (when @Validated is on the class),
   ConstraintViolationException is thrown.

Q: What is @ControllerAdvice and how does it differ from @ExceptionHandler?
A: @ExceptionHandler on a controller method handles exceptions only within that
   controller. @ControllerAdvice (+ @RestControllerAdvice = @ControllerAdvice +
   @ResponseBody) is a global exception handler that applies to all controllers.
   It centralizes error handling, preventing repetition across many controllers.

Q: What is RFC 7807 / ProblemDetail?
A: RFC 7807 is a standard HTTP error response format with fields: type (URI
   identifying the error type), title (human-readable summary), status (HTTP
   code), detail (specific explanation), instance (URI of the specific occurrence).
   Spring 6 / Spring Boot 3 natively supports ProblemDetail as a return type from
   @ExceptionHandler methods. Enable spring.mvc.problemdetails.enabled=true.

Q: Where should business rule validation live — controller or service?
A: Input format validation (@NotNull, @Size, @Email) belongs in the controller
   layer via Bean Validation annotations on DTOs. Business rule validation (e.g.,
   "user cannot place more than 10 orders per day", "product must be in stock")
   belongs in the service layer, where domain logic is encapsulated. Mixing
   business rules into DTO annotations couples domain logic to the API layer.
