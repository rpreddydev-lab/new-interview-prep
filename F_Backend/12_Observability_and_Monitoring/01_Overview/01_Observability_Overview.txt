OBSERVABILITY OVERVIEW — THE THREE PILLARS
==========================================

What is Observability?
- The ability to understand the internal state of a system from its external outputs
- Coined from control theory — a system is observable if you can determine its
  internal state from its outputs
- In software: observability = Metrics + Logs + Traces (the "three pillars")

Why Observability Matters (for 7-year Java developers):
- Microservices make debugging hard — requests span many services
- Traditional logging is insufficient for distributed systems
- Need correlated data to trace failures across service boundaries

=== THE THREE PILLARS ===

1. METRICS
   - Numerical measurements over time (counters, gauges, histograms)
   - Aggregated data — good for dashboards and alerting
   - Example: requests/sec, error rate, JVM heap usage, p99 latency
   - Tools: Micrometer, Prometheus, Grafana

2. LOGS
   - Timestamped records of discrete events
   - Structured (JSON) logs are far more useful than plain text
   - Example: "Order 12345 failed: payment gateway timeout"
   - Tools: SLF4J, Logback, Log4j2, ELK Stack (Elasticsearch, Logstash, Kibana)

3. TRACES
   - End-to-end request path across distributed services
   - Each operation = a "span"; correlated spans form a "trace"
   - Shows WHERE time is spent across service calls
   - Tools: OpenTelemetry, Jaeger, Zipkin, AWS X-Ray

=== OBSERVABILITY vs MONITORING ===

Monitoring:
- Predefined dashboards and alerts for known failure modes
- "Is the system up? Is error rate high?"
- Reactive — responds to known problems

Observability:
- Ability to ask arbitrary questions about system state
- "Why is order service slow only for users in EU?"
- Proactive — enables exploration of unknown problems

You need BOTH — monitoring catches what you know will break;
observability helps debug what you didn't anticipate.

=== OBSERVABILITY IN SPRING BOOT ===

Spring Boot Actuator:
- Exposes health, metrics, info, env endpoints
- Foundation for observability in Spring

Micrometer:
- Vendor-neutral metrics facade (like SLF4J for metrics)
- Built into Spring Boot — auto-instruments JVM, HTTP, DB, cache metrics
- Backends: Prometheus, Datadog, CloudWatch, Influx, Dynatrace

Spring Boot Observability (3.x):
- spring-boot-starter-actuator + micrometer-tracing
- Auto-instruments all incoming/outgoing HTTP calls
- Propagates trace context automatically (B3, W3C TraceContext)

OpenTelemetry (OTel):
- CNCF standard for telemetry — metrics, logs, traces
- OTel SDK for Java replaces vendor-specific agents
- OTel Collector: receives, processes, exports telemetry
- Replacing Zipkin/Jaeger SDKs as the standard

=== CORRELATION ID PATTERN ===

- Generate a unique ID at the entry point (API gateway or first service)
- Propagate via HTTP headers (X-Correlation-ID, traceparent)
- Include in all log statements for that request
- Enables reconstructing the full journey of a request across services

Spring: MDC (Mapped Diagnostic Context) holds correlation ID for logging
Tracing: trace ID serves as the correlation ID automatically

=== HEALTH CHECKS ===

Types:
- Liveness: is the app alive? (restart if not) → /actuator/health/liveness
- Readiness: is the app ready to serve traffic? → /actuator/health/readiness
- Startup: has app finished starting up? → used by Kubernetes startupProbe

Spring Boot Actuator auto-adds:
- DB connectivity health check
- Redis connectivity health check
- Disk space check
- Kafka health check

Custom health indicator:
  @Component
  public class PaymentServiceHealth implements HealthIndicator {
      public Health health() {
          return paymentServiceUp() ? Health.up().build()
                                    : Health.down().withDetail("reason", "timeout").build();
      }
  }

=== KEY INTERVIEW POINTS ===

- Observability is not just logging — metrics and traces are equally important
- Structured JSON logging is mandatory in microservices
- OpenTelemetry is becoming the industry standard
- Spring Boot 3 has first-class observability with Micrometer Tracing
- Liveness ≠ Readiness — common Kubernetes misconfiguration to avoid
