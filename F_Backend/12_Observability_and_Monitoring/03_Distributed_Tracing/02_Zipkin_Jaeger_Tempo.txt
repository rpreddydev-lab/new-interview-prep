ZIPKIN, JAEGER, AND DISTRIBUTED TRACING BACKENDS
==================================================

Overview
--------
Distributed tracing backends collect, store, and visualize trace data.
Spring Boot 3 uses Micrometer Tracing (with OpenTelemetry or Brave) to instrument code.
The trace data is exported to a backend like Zipkin, Jaeger, or Grafana Tempo.

Concepts:
  Trace    — end-to-end request journey (has a unique trace ID)
  Span     — single unit of work within a trace (has span ID + parent span ID)
  Context  — trace ID + span ID propagated via HTTP headers or AMQP headers

---

Spring Boot 3 Tracing Setup
-----------------------------
Dependencies:
  <!-- Micrometer Tracing with Brave (Zipkin-compatible) -->
  <dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
  </dependency>
  <dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
  </dependency>

  <!-- OR: Micrometer Tracing with OpenTelemetry -->
  <dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
  </dependency>
  <dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
  </dependency>

Configuration:
  management:
    tracing:
      sampling:
        probability: 1.0   # 1.0 = 100% sampling (reduce in production: 0.1)
    zipkin:
      tracing:
        endpoint: http://zipkin:9411/api/v2/spans

Spring auto-instruments:
  - RestTemplate / WebClient (HTTP calls)
  - Spring MVC / WebFlux (incoming requests)
  - Spring Data (DB queries — requires separate spans)
  - Spring Kafka / AMQP (message publishing and consuming)
  - @Scheduled tasks

---

Zipkin
------
Open-source tracing system originally by Twitter.
Simple, lightweight, easy to run locally.

Run locally:
  docker run -d -p 9411:9411 openzipkin/zipkin

UI: http://localhost:9411

Architecture:
  App → Reporter → Collector → Storage (in-memory / MySQL / Elasticsearch / Cassandra) → UI

Features:
  - Trace search by service name, operation, duration, trace ID
  - Service dependency graph
  - Latency percentiles per service

Trace propagation headers (B3 format):
  X-B3-TraceId: abc123
  X-B3-SpanId: def456
  X-B3-ParentSpanId: ghi789
  X-B3-Sampled: 1

---

Jaeger
------
Open-source tracing by Uber, now CNCF project.
Better suited for large-scale deployments than Zipkin.
Native support for OpenTelemetry.

Run locally (all-in-one):
  docker run -d \
    -p 5775:5775/udp \
    -p 6831:6831/udp \
    -p 16686:16686 \
    -p 14268:14268 \
    jaegertracing/all-in-one:latest

UI: http://localhost:16686

Architecture:
  Agent (sidecar) → Collector → Storage (Elasticsearch / Cassandra / Badger) → Query + UI

Features:
  - Adaptive sampling — dynamically adjust sample rates per service
  - Service performance monitoring (RED metrics from traces)
  - Trace comparison
  - Kubernetes native (jaeger-operator)

Send traces to Jaeger via OTLP:
  management:
    otlp:
      tracing:
        endpoint: http://jaeger:4318/v1/traces

---

Grafana Tempo
-------------
High-scale, cost-effective trace storage by Grafana Labs.
Stores traces as objects (S3, GCS, Azure Blob) — no indexing overhead.
Integrates tightly with Grafana (correlate traces with metrics and logs).

Architecture:
  App → OTLP Collector → Tempo → Grafana (TraceQL queries)

TraceQL query example:
  {.service.name = "orders-service" && duration > 500ms}

Correlation:
  - In Grafana: click a Loki log line → jump to related trace in Tempo
  - Click a Prometheus spike → see traces at that time in Tempo

Trace Propagation Between Services
------------------------------------
Trace context must be forwarded across service boundaries.

HTTP (RestTemplate / WebClient — auto-propagated by Spring):
  Sends W3C Trace Context headers:
    traceparent: 00-abc123-def456-01
    tracestate: (vendor-specific)

  Or B3 headers (Zipkin/Brave):
    X-B3-TraceId / X-B3-SpanId / X-B3-Sampled

Feign Client — auto-propagated.
Spring Kafka / AMQP — auto-propagated via message headers when observationEnabled=true.

Manual span creation:
  @Autowired
  Tracer tracer;

  public void processOrder(Order order) {
      Span span = tracer.nextSpan().name("process-order").start();
      try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
          span.tag("order.id", order.getId());
          orderService.process(order);
      } catch (Exception e) {
          span.error(e);
          throw e;
      } finally {
          span.end();
      }
  }

Sampling Strategies
-------------------
  Always sample (dev/test): probability: 1.0
  Rate-based (production):  probability: 0.1  (10% of requests)
  Adaptive (Jaeger):        dynamically adjusts per service/operation
  Head-based:               decision made at trace start (default)
  Tail-based:               decision after trace completes (keeps errors/slow traces)
                            — requires Jaeger remote sampling or OpenTelemetry Collector
