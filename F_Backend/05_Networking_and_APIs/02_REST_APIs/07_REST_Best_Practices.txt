================================================================================
REST BEST PRACTICES — IN DEPTH
================================================================================

This file consolidates REST API design best practices for production-grade
systems. These are patterns tested by major tech companies (Stripe, GitHub,
Twitter, Google) and expected in senior-level interviews.

================================================================================
1. URI DESIGN BEST PRACTICES
================================================================================

USE NOUNS, NOT VERBS:
  ✅ GET  /orders
  ✅ POST /orders
  ❌ GET  /getOrders
  ❌ POST /createOrder

USE PLURAL NOUNS FOR COLLECTIONS:
  ✅ /users, /orders, /products
  ❌ /user, /order, /product

USE HIERARCHICAL RELATIONSHIPS SPARINGLY (max 2 levels):
  ✅ GET /users/42/orders
  ❌ GET /companies/1/departments/5/teams/3/employees/42  (too deep)
  
  Alternative for deep hierarchies:
  ✅ GET /employees/42?departmentId=5  (flatten with query params)

KEEP PATHS LOWERCASE WITH HYPHENS:
  ✅ /order-items, /user-profiles
  ❌ /orderItems, /UserProfiles, /order_items

ACTIONS ON RESOURCES (When CRUD doesn't fit):
  ✅ POST /orders/42/cancel        (action as sub-resource)
  ✅ POST /orders/42/items         (add item to order)
  ✅ POST /emails/send             (trigger action)
  ✅ PATCH /orders/42 { "status": "CANCELLED" }  (preferred for simple status change)

QUERY PARAMETERS FOR FILTERING, SORTING, PAGINATION:
  GET /users?role=admin&active=true&sort=lastName&order=asc&page=2&size=20

DON'T PUT VERSIONS IN EVERY PATH COMPONENT:
  ✅ /v1/users/42/orders
  ❌ /v1/users/42/v1/orders

2. REQUEST DESIGN BEST PRACTICES
================================================================================

REQUEST BODY:
  - Use camelCase for JSON field names (JavaScript convention)
  - Always validate at schema level (required fields, data types)
  - Always validate at business rule level (referential integrity, ranges)
  - Reject extra fields (or ignore — be explicit about your policy)

CONTENT NEGOTIATION:
  - Support Content-Type: application/json as primary
  - Use Accept header for response format negotiation
  - Default to JSON if Accept: */* or missing

ACCEPT HEADER:
  Accept: application/json         → return JSON
  Accept: application/xml          → return XML (if supported)
  Accept: */*                      → return default (JSON)
  Accept: application/json, text/html;q=0.9  → prefer JSON, accept HTML

AVOID BREAKING CHANGES IN REQUEST SCHEMA:
  - Adding new optional fields: safe
  - Removing fields: breaking change
  - Changing field types: breaking change
  - Making optional fields required: breaking change

3. RESPONSE DESIGN BEST PRACTICES
================================================================================

CONSISTENT RESPONSE ENVELOPE:
  Some teams wrap ALL responses in an envelope:
  {
    "data": { "id": 42, "name": "Alice" },
    "meta": { "requestId": "req-123", "timestamp": "2026-04-08T10:00:00Z" }
  }
  
  Others return resource directly:
  { "id": 42, "name": "Alice" }
  
  Choose ONE style and stick to it. Direct resource is simpler.
  Envelope useful when you need to consistently include metadata.

RETURN ONLY WHAT'S NEEDED:
  Don't expose internal fields (database IDs you don't want to expose, internal state)
  Use DTOs / response models, not entity classes directly
  Consider GDPR: don't return PII unnecessarily

NULL vs MISSING FIELDS:
  Option 1: Omit null fields (cleaner, smaller payload)
  Option 2: Include null fields (explicit, easier client parsing)
  
  Jackson: @JsonInclude(JsonInclude.Include.NON_NULL) → omit nulls
  Be consistent across your API.

DATES AND TIMES:
  ✅ Use ISO 8601: "2026-04-08T10:00:00Z"  (UTC with Z suffix)
  ✅ Or: "2026-04-08T10:00:00+00:00"
  ❌ Avoid Unix timestamps (hard to read)
  ❌ Avoid non-standard formats ("04/08/2026")

CURRENCY AND DECIMALS:
  ✅ Use integer cents: { "amount": 1500, "currency": "USD" }  (represents $15.00)
  ❌ Avoid floats: { "amount": 15.00 }  (floating point precision issues)

BOOLEAN FIELDS:
  ✅ Use is/has prefix: isActive, hasAddress, isVerified

PAGINATION RESPONSE:
  {
    "data": [...],
    "pagination": {
      "page": 2,
      "size": 20,
      "totalElements": 450,
      "totalPages": 23,
      "hasNext": true,
      "hasPrevious": true
    },
    "_links": {
      "first": { "href": "/users?page=0&size=20" },
      "prev":  { "href": "/users?page=1&size=20" },
      "self":  { "href": "/users?page=2&size=20" },
      "next":  { "href": "/users?page=3&size=20" },
      "last":  { "href": "/users?page=22&size=20" }
    }
  }

4. ERROR RESPONSE BEST PRACTICES
================================================================================

STANDARD ERROR FORMAT (what interviewers love to see):
  {
    "error": "VALIDATION_FAILED",          // Machine-readable error code
    "message": "Request validation failed", // Human-readable message
    "requestId": "req-abc123",             // For support/debugging
    "timestamp": "2026-04-08T10:00:00Z",
    "path": "/api/users",
    "details": [                           // Optional: field-level errors
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "Must be a valid email address"
      },
      {
        "field": "age",
        "code": "OUT_OF_RANGE",
        "message": "Must be between 0 and 150"
      }
    ]
  }

RULES FOR ERROR RESPONSES:
  1. NEVER return 200 with error in body
  2. Include requestId for correlating with logs
  3. Don't expose stack traces, SQL errors, or internal paths
  4. Machine-readable error codes for programmatic handling
  5. Human-readable messages for debugging (not user display)
  6. Field-level errors for validation failures
  7. Consistent format across all endpoints

SPRING BOOT — GLOBAL EXCEPTION HANDLER:
  @RestControllerAdvice
  public class GlobalExceptionHandler {

      @ExceptionHandler(MethodArgumentNotValidException.class)
      public ResponseEntity<ErrorResponse> handleValidation(
              MethodArgumentNotValidException ex, HttpServletRequest req) {
          
          List<FieldError> details = ex.getBindingResult().getFieldErrors().stream()
              .map(e -> new FieldError(e.getField(), "INVALID_VALUE", e.getDefaultMessage()))
              .toList();
          
          return ResponseEntity.status(400)
              .body(new ErrorResponse("VALIDATION_FAILED", "Validation error",
                    UUID.randomUUID().toString(), req.getRequestURI(), details));
      }

      @ExceptionHandler(ResourceNotFoundException.class)
      public ResponseEntity<ErrorResponse> handleNotFound(
              ResourceNotFoundException ex, HttpServletRequest req) {
          return ResponseEntity.status(404)
              .body(new ErrorResponse("NOT_FOUND", ex.getMessage(),
                    UUID.randomUUID().toString(), req.getRequestURI(), null));
      }

      @ExceptionHandler(Exception.class)
      public ResponseEntity<ErrorResponse> handleGeneral(
              Exception ex, HttpServletRequest req) {
          log.error("Unexpected error for request {}", req.getRequestURI(), ex);
          return ResponseEntity.status(500)
              .body(new ErrorResponse("INTERNAL_ERROR", "An unexpected error occurred",
                    UUID.randomUUID().toString(), req.getRequestURI(), null));
      }
  }

5. SECURITY BEST PRACTICES
================================================================================

AUTHENTICATION:
  - Use OAuth2 / JWT Bearer tokens for most APIs
  - API keys for service-to-service (simpler key management)
  - Basic Auth: only over HTTPS, usually for legacy/simple internal tools
  - Never send credentials in URL query parameters

AUTHORIZATION:
  - Check permissions at service layer, not just controller
  - Principle of least privilege: return 403 for forbidden resources
  - Avoid 404 for forbidden (sometimes reveal resource existence)

INPUT VALIDATION:
  - Validate at API boundary before any processing
  - Sanitize to prevent SQL injection, XSS, command injection
  - Reject unexpected fields (don't let clients set internalState)
  - Enforce size limits (body size, string length, array length)
  - Spring: @Valid, @Validated, @RequestBody with DTO validation

RATE LIMITING:
  - Protect every public endpoint
  - Return 429 with Retry-After
  - Rate limit by user, API key, IP (in order of preference)

SENSITIVE DATA:
  - Mask/redact in logs: passwords, tokens, SSN, card numbers
  - Don't include sensitive data in error messages
  - Use HTTPS everywhere (HSTS header)

6. VERSIONING BEST PRACTICES
================================================================================

(Detailed in 02_API_Design/00_API_Versioning.txt)

QUICK REFERENCE:
  - Version at the URL path: /v1/users (most common, most explicit)
  - Never make breaking changes without a new version
  - Support N-1 versions simultaneously
  - Deprecation: announce with Deprecation: date header, documentation, changelog
  - Sunset header for decommission date: Sunset: Sat, 01 Jan 2028 00:00:00 GMT

7. DOCUMENTATION BEST PRACTICES
================================================================================

USE OPENAPI (SWAGGER):
  - Document every endpoint, request/response schema, error codes
  - Keep documentation as code (generated from annotations, not separate)
  - Include examples for all schemas

SPRING BOOT + SPRINGDOC:
  <dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.x.x</version>
  </dependency>

  Access: http://localhost:8080/swagger-ui.html

8. PERFORMANCE BEST PRACTICES
================================================================================

CACHING:
  - Set Cache-Control headers on GET responses
  - Use ETag for conditional GET support
  - Cache static reference data aggressively (max-age=86400)
  - Never cache sensitive or user-specific data in shared caches

PAGINATION:
  - Always paginate collections (default 20-100 items max)
  - Use cursor-based pagination for large, frequently changing datasets
  - Never allow unlimited page sizes (cap at reasonable limit)

PARTIAL RESPONSES (Field Filtering):
  GET /users/42?fields=id,name,email
  Reduces bandwidth for clients that don't need all fields.
  
  Google API style:
  GET /users/42?fields=name,address(city,zip)

COMPRESSION:
  - Enable GZIP/Brotli compression on server (Nginx/Tomcat)
  - Supported automatically if client sends Accept-Encoding: gzip

ASYNC FOR LONG OPERATIONS:
  - Operations > 1-2 seconds should be async (202 Accepted pattern)
  - Provide polling URL or webhook callback

CONNECTION POOLING:
  - Configure HTTP client connection pools (Spring's RestTemplate/WebClient)
  - maxConnections, maxIdleTime to match server capacity

9. API DESIGN CHECKLIST (INTERVIEW REFERENCE)
================================================================================

RESOURCE DESIGN:
  ☑ Nouns, not verbs in URIs
  ☑ Plural nouns for collections
  ☑ Hierarchical relationships (max 2 levels)
  ☑ Lowercase with hyphens

HTTP METHODS:
  ☑ GET for retrieval (safe, idempotent)
  ☑ POST for creation
  ☑ PUT for full replacement (idempotent)
  ☑ PATCH for partial update
  ☑ DELETE for removal (idempotent)

STATUS CODES:
  ☑ 201 Created with Location header for POST
  ☑ 204 No Content for DELETE
  ☑ 400 for validation errors
  ☑ 401/403 for auth issues
  ☑ 404 for missing resources
  ☑ 409 for conflicts
  ☑ 422 for business rule violations
  ☑ 429 for rate limiting with Retry-After

ERRORS:
  ☑ Consistent error format with code, message, requestId
  ☑ Never 200 with error in body
  ☑ Field-level errors for validation

SECURITY:
  ☑ HTTPS everywhere
  ☑ Authentication on protected endpoints
  ☑ Input validation
  ☑ Rate limiting

DOCUMENTATION:
  ☑ OpenAPI/Swagger spec
  ☑ Examples for all schemas
  ☑ Changelog for versions

10. INTERVIEW QUESTIONS — REST BEST PRACTICES
================================================================================

Q1: How do you design a REST endpoint for an action that doesn't map to CRUD?
    Model the action as a resource: POST /orders/42/cancel creates a cancellation.
    Or use PATCH to update state: PATCH /orders/42 { "status": "CANCELLED" }.
    Prefer state change via PATCH when it's a simple status transition.
    Use POST with action as sub-resource for complex operations with their own
    lifecycle or data (POST /payments, POST /shipments).

Q2: How do you handle breaking changes in a REST API?
    Use versioning (URL path /v1, /v2). Never make breaking changes in the same
    version. Support old versions with deprecation period (Deprecation + Sunset
    headers). Communicate changes in changelog. Additive changes (new fields,
    new endpoints) are safe in same version; removing/changing fields requires
    new version.

Q3: What headers would you return on a rate-limited response?
    HTTP 429 Too Many Requests + Retry-After: 60 (seconds to wait).
    Also: X-RateLimit-Limit (max requests), X-RateLimit-Remaining (left in window),
    X-RateLimit-Reset (epoch when quota resets).

Q4: How do you handle large collections in a REST API?
    Always paginate. Offer page-based (page, size) or cursor-based pagination.
    Cursor pagination is better for large, frequently changing datasets (stable,
    no duplicates/skips). Return pagination metadata (totalElements, totalPages)
    and navigation links (next, prev, first, last). Cap max page size.

Q5: Should you return the updated resource after a PUT/PATCH?
    Prefer 200 OK with updated resource body — reduces an extra GET round trip.
    204 No Content is acceptable if client can compute the updated state or doesn't
    need it. Consistency matters most — pick one and apply it throughout the API.
