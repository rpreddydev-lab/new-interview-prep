================================================================================
SSL/TLS HANDSHAKE — IN DEPTH
================================================================================

OVERVIEW
---------
TLS (Transport Layer Security) is the cryptographic protocol that secures
communication over the internet. It replaced SSL (Secure Sockets Layer).

Current versions:
  SSL 3.0  : Deprecated (POODLE attack, 2014)
  TLS 1.0  : Deprecated (RFC 8996, 2021)
  TLS 1.1  : Deprecated (RFC 8996, 2021)
  TLS 1.2  : Still widely used; secure with correct cipher suites
  TLS 1.3  : Current standard (2018); faster, simpler, more secure

HTTPS = HTTP over TLS.
The "S" in wss://, smtps://, ldaps:// means the same TLS protection.

================================================================================
1. TLS 1.2 HANDSHAKE
================================================================================

Full TLS 1.2 handshake takes 2 RTTs before application data can flow:

  Client                                    Server
    |                                          |
    |──── ClientHello ────────────────────────→|  (cipher suites, TLS version,
    |     (random_C, client_random,            |   ClientHello random nonce)
    |      supported cipher suites)            |
    |                                          |
    |←─── ServerHello ────────────────────────|  (chosen cipher suite)
    |←─── Certificate ────────────────────────|  (server's X.509 cert)
    |←─── ServerHelloDone ────────────────────|
    |                                          |
    | (client validates certificate:           |
    |  chain of trust, expiry, hostname,       |
    |  revocation via OCSP)                    |
    |                                          |
    |──── ClientKeyExchange ──────────────────→|  (pre-master secret,
    |     (pre-master secret encrypted         |   encrypted with server's public key)
    |      with server public key)             |
    |──── ChangeCipherSpec ───────────────────→|
    |──── Finished ───────────────────────────→|  (MAC of all handshake messages)
    |                                          |
    |←─── ChangeCipherSpec ────────────────────|
    |←─── Finished ────────────────────────────|
    |                                          |
    |══ Encrypted Application Data ══════════>|  (TLS record)

MASTER SECRET DERIVATION:
  Pre-master secret + client_random + server_random → master secret
  Master secret → session keys (4 keys: client/server × encrypt/MAC)

Session resumption (abbreviated handshake):
  Client sends Session ID or Session Ticket from previous connection.
  Server accepts → skips certificate exchange.
  Result: 1 RTT instead of 2.

================================================================================
2. TLS 1.3 HANDSHAKE
================================================================================

TLS 1.3 reduces handshake to 1 RTT (from 2) and optionally 0-RTT for resumption.

Key changes from 1.2:
  - Removed: RSA key exchange, DHE-RSA with static keys, CBC cipher modes, RC4, 3DES
  - Forward secrecy always required (ECDHE or DHE)
  - Simplified cipher suites (only 5 in TLS 1.3 vs 37+ in TLS 1.2)
  - Certificate and finished messages encrypted earlier in handshake
  - Session tickets only for resumption (no session IDs)

  Client                                    Server
    |                                          |
    |──── ClientHello ────────────────────────→|  (supported groups,
    |     (key_share: client's ECDH public key,|   ClientHello nonce,
    |      supported cipher suites)            |   key_share hint)
    |                                          |
    |←─── ServerHello ────────────────────────|  (key_share: server's ECDH pubkey)
    |←─── {EncryptedExtensions} ──────────────|  (encrypted from here on)
    |←─── {Certificate} ──────────────────────|
    |←─── {CertificateVerify} ────────────────|
    |←─── {Finished} ─────────────────────────|
    |                                          |
    |──── {Finished} ─────────────────────────→|
    |                                          |
    |══ Encrypted Application Data ══════════>|  (1 RTT total)

0-RTT Resumption (2nd connection):
  Client sends application data in FIRST packet using session ticket key.
  No round trips before data arrives at server.
  Caveat: replay attacks possible (only safe for idempotent requests).

================================================================================
3. KEY CONCEPTS IN TLS
================================================================================

CERTIFICATES (X.509):
  A certificate binds a public key to an identity (domain name).
  Fields: Subject (CN=example.com), Issuer (Let's Encrypt), Validity period,
          Public key, Subject Alternative Names (SANs), Serial number, Signature.

CERTIFICATE CHAIN:
  Server cert → Intermediate CA cert → Root CA cert
  Browsers trust Root CAs (stored in OS/browser trust store).
  Chain validated by verifying each signature up to a trusted root.
  Certificate must be valid (not expired, not revoked, hostname matches).

SNI (Server Name Indication):
  TLS extension. Client includes the target hostname in ClientHello.
  Server uses this to select the correct certificate (for virtual hosting).
  Without SNI: one certificate per IP address.
  With SNI: many sites on same IP with different certificates.

OCSP (Online Certificate Status Protocol):
  Client queries OCSP responder to check if certificate is revoked.
  Adds latency. Solution: OCSP Stapling — server fetches and caches OCSP
  response, staples it to TLS handshake. Client trusts stapled response.

FORWARD SECRECY (Perfect Forward Secrecy - PFS):
  If an attacker records encrypted traffic today and later compromises the
  server's private key, can they decrypt old traffic?
  
  No PFS (RSA key exchange): Pre-master secret encrypted with server's static
  private key → compromise of private key decrypts ALL historical sessions.
  
  PFS (ECDHE): Ephemeral Diffie-Hellman key exchange → new key pair per session.
  Compromising the static private key doesn't decrypt past sessions.
  
  TLS 1.3 mandates PFS. TLS 1.2 should use ECDHE cipher suites.

CIPHER SUITE:
  Negotiated algorithm combination:
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
  │   │      │    │            │
  │   │      │    │            └─ MAC algorithm (SHA384)
  │   │      │    └─────────────── Symmetric encryption (AES-256-GCM)
  │   │      └──────────────────── Authentication (RSA signature)
  │   └─────────────────────────── Key exchange (ECDHE)
  └─────────────────────────────── Protocol

  TLS 1.3 cipher suites (only 5):
    TLS_AES_128_GCM_SHA256
    TLS_AES_256_GCM_SHA384
    TLS_CHACHA20_POLY1305_SHA256
    TLS_AES_128_CCM_SHA256
    TLS_AES_128_CCM_8_SHA256

4. CERTIFICATE TYPES
================================================================================

DV (Domain Validation):
  Proves control of domain only. Automated (Let's Encrypt). Minutes to issue.
  Padlock in browser. No company info shown.

OV (Organization Validation):
  Proves domain + organization identity. Manual CA review.
  Shows company name in certificate details.

EV (Extended Validation):
  Rigorous legal/physical validation. Banks, payment processors.
  Previously showed green bar in browser (removed in 2019).

Wildcard: *.example.com — covers any single-level subdomain
Multi-SAN: covers multiple specific domains in one certificate
Self-signed: signed by itself, not a CA — rejected by browsers (dev use only)

5. MUTUAL TLS (mTLS)
================================================================================

In standard TLS, only the SERVER presents a certificate.
In mTLS, BOTH client and server present certificates.

Use cases:
  - Service-to-service authentication in microservices
  - API authentication (replacing API keys)
  - Zero-trust network security (Istio service mesh)

mTLS handshake addition:
  After server sends Certificate:
  Server → CertificateRequest   (server requests client cert)
  Client → Certificate          (client sends its cert)
  Client → CertificateVerify   (proves possession of private key)

SPRING BOOT mTLS:
  # Server requires client certificate
  server.ssl.client-auth=need        # need = required, want = optional, none = disabled
  server.ssl.trust-store=classpath:truststore.p12
  server.ssl.trust-store-password=changeit

  # Client sends certificate
  SSLContext sslContext = SSLContextBuilder.create()
      .loadKeyMaterial(keyStore, keyPassword)
      .loadTrustMaterial(trustStore, null)
      .build();
  
  CloseableHttpClient httpClient = HttpClients.custom()
      .setSSLContext(sslContext)
      .build();

6. COMMON TLS ISSUES
================================================================================

Certificate expired:
  Solution: Use Let's Encrypt with auto-renewal (certbot renew)
  Monitor with: echo | openssl s_client -connect host:443 2>/dev/null | 
    openssl x509 -noout -dates

Hostname mismatch:
  Subject CN or SAN doesn't match request hostname.
  Solution: include all hostnames in SAN; use wildcard cert.

Untrusted CA:
  Certificate chain doesn't chain to a trusted root.
  Solution: install intermediate cert on server; use trusted CA.

Mixed content:
  HTTPS page loads HTTP resources → browser blocks/warns.
  Solution: all assets must be HTTPS.

BEAST, POODLE, HEARTBLEED, DROWN:
  Attacks on old SSL/TLS versions and cipher suites.
  Solution: disable TLS < 1.2; use AEAD cipher suites; update OpenSSL.

7. INTERVIEW QUESTIONS — TLS HANDSHAKE
================================================================================

Q1: How does TLS 1.3 improve on TLS 1.2?
    Three main improvements: 1) 1-RTT handshake (vs 2 in 1.2) by combining
    key exchange in the first message. 2) 0-RTT resumption for returning clients.
    3) Forward secrecy always required — removed static RSA key exchange.
    Also: removed weak cipher suites (RC4, 3DES, CBC mode), simplified to
    5 cipher suites, encrypted more of the handshake earlier (certificate is
    now encrypted), faster connection establishment.

Q2: What is Perfect Forward Secrecy and why does it matter?
    PFS ensures that compromising today's private key doesn't decrypt past
    recorded sessions. Achieved by using ephemeral Diffie-Hellman key exchange
    (ECDHE) where a new key pair is generated per session. Even if the server's
    long-term private key is stolen, the session keys (derived from ephemeral
    DH keys that are discarded) cannot be recomputed. TLS 1.3 mandates PFS.
    TLS 1.2 with RSA key exchange does NOT have PFS.

Q3: What is SNI and why is it needed?
    Server Name Indication is a TLS extension where the client includes the
    target hostname in the ClientHello message. Before SNI, a server needed a
    unique IP per domain because TLS negotiates before the HTTP Host header is
    seen. With SNI, many domains can share the same IP, and the server selects
    the correct certificate based on the SNI hostname. Required for virtual
    hosting with TLS. Older clients (pre-2012) don't support SNI.

Q4: What is the difference between one-way TLS and mutual TLS (mTLS)?
    One-way TLS: only the server presents a certificate; client verifies server
    identity. Standard HTTPS — we verify we're talking to the real google.com.
    mTLS: both client and server present certificates. The server also verifies
    the client's identity. Used for service-to-service auth in microservices
    (Istio), API clients, IoT devices. More secure than API keys because keys
    are never transmitted — only certificates (which prove private key possession
    via CertificateVerify message).

Q5: What is OCSP stapling?
    OCSP (Online Certificate Status Protocol) lets clients check if a certificate
    has been revoked. Standard OCSP: client queries OCSP responder on every
    connection — adds latency and creates privacy issue (CA sees which sites you visit).
    OCSP Stapling: server periodically fetches its own OCSP response and caches it.
    The stapled OCSP response is included in the TLS handshake. Client trusts it
    because it's signed by the CA. No extra round trip; no privacy leak.
    Enable in Nginx: ssl_stapling on; ssl_stapling_verify on;
