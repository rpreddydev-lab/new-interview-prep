================================================================================
PART A: DNS — DOMAIN NAME SYSTEM
================================================================================

WHAT IS DNS?
-------------
DNS is the internet's distributed hierarchical naming system. It maps human-
readable domain names (e.g., api.example.com) to machine-readable IP addresses
(e.g., 93.184.216.34). Often called the "phone book of the internet."

DNS runs on UDP port 53 (or TCP for large responses / zone transfers).

================================================================================
A.1 DNS RECORD TYPES
================================================================================

RECORD   DESCRIPTION                               EXAMPLE
-------  ----------------------------------------  ---------------------------
A        IPv4 address                              api.example.com → 1.2.3.4
AAAA     IPv6 address                              api.example.com → ::1
CNAME    Alias to another hostname                 www → example.com
MX       Mail server for domain                    example.com → mail.example.com
NS       Authoritative nameservers for domain      example.com → ns1.registrar.com
TXT      Arbitrary text (SPF, DKIM, verification) v=spf1 include:sendgrid.net ~all
SOA      Start of Authority (zone metadata)        Serial, refresh, retry, expire
PTR      Reverse DNS (IP → hostname)               1.2.3.4 → server.example.com
SRV      Service location (host + port)            _sip._tcp.example.com
CAA      Certificate Authority Authorization       issue "letsencrypt.org"

TTL (Time To Live): How long (seconds) a resolver can cache the answer.
  Low TTL  (60s)    → Fast propagation of changes; more DNS queries
  High TTL (86400s) → Less load on DNS; slow failover

================================================================================
A.2 DNS RESOLUTION — STEP BY STEP
================================================================================

Query: user types "api.example.com" in browser

Step 1: BROWSER CACHE
  Browser checks its own DNS cache. If found and TTL not expired → use it.

Step 2: OS CACHE / HOSTS FILE
  OS checks its DNS cache (/etc/hosts, systemd-resolved, nscd).
  /etc/hosts overrides DNS (used for local dev, blocking ads).

Step 3: RECURSIVE RESOLVER (your ISP or 8.8.8.8 / 1.1.1.1)
  OS sends query to configured DNS resolver (stub resolver → recursive resolver).
  Recursive resolver does the work on client's behalf.

Step 4: ROOT NAMESERVER
  If recursive resolver has no cache, asks a root nameserver (.) 
  13 root nameserver clusters (a.root-servers.net through m.root-servers.net).
  Root responds: "I don't know, but here are the .com TLD nameservers."

Step 5: TLD NAMESERVER
  Recursive resolver asks .com TLD nameserver.
  TLD responds: "I don't know, but here are example.com's authoritative nameservers."

Step 6: AUTHORITATIVE NAMESERVER
  Recursive resolver asks example.com's authoritative nameserver.
  Returns actual A/AAAA record: api.example.com → 93.184.216.34

Step 7: RESPONSE CACHED AND RETURNED
  Recursive resolver caches response (per TTL).
  Returns IP to client's OS → browser opens TCP connection to 93.184.216.34.

FULL RESOLUTION DIAGRAM:
  Browser → OS → Recursive Resolver → Root NS → TLD NS → Auth NS → IP

ITERATIVE vs RECURSIVE RESOLUTION:
  Recursive: Each party resolves fully and returns final answer (typical for client)
  Iterative: Each party returns referral (nameservers do iterative between each other)

================================================================================
A.3 DNS CACHING AND TTL
================================================================================

TTL STRATEGY:
  During normal operation: High TTL (3600s to 86400s) → fewer queries, lower load
  Before DNS migration/failover: Lower TTL to 60-300s → faster propagation
  After migration: Return TTL to normal

NEGATIVE CACHING (NXDOMAIN):
  "Negative TTL" from SOA record caches non-existent domain responses.
  Prevents re-querying for domains that don't exist.

DNS PROPAGATION:
  When you update a DNS record, old TTL must expire across all resolvers.
  "DNS propagation delay" = up to TTL seconds worldwide (usually 24-48h for high TTL).

================================================================================
A.4 DNS ADVANCED TOPICS
================================================================================

DNS OVER HTTPS (DoH)
  Traditional DNS: UDP/TCP on port 53 — unencrypted, observable by ISP/network
  DoH: DNS queries sent over HTTPS to a DoH resolver (e.g., 1.1.1.1/dns-query)
  Benefits: Privacy, resistance to DNS hijacking
  Providers: Cloudflare (1.1.1.1), Google (8.8.8.8), NextDNS

DNS OVER TLS (DoT)
  DNS queries over TLS on port 853
  Similar privacy benefits to DoH but on a dedicated port

DNSSEC
  Adds cryptographic signatures to DNS records to prevent spoofing/poisoning.
  Not encryption — still readable; but tamper-evident.
  Uses RRSIG, DNSKEY, DS, NSEC records.

DNS LOAD BALANCING
  Round-Robin DNS: Multiple A records for same domain; resolver rotates
    api.example.com → 1.2.3.4
    api.example.com → 1.2.3.5
    api.example.com → 1.2.3.6
  Limitation: No health checking; clients may get IPs of failed servers.
  Workaround: Low TTL + health-check-based DNS (Route 53, Cloudflare).

GEO DNS / ANYCAST
  Return different IPs based on client's geographic location.
  CDNs use Anycast: same IP announced from multiple PoPs; routing sends to nearest.

PART B: LOAD BALANCING
================================================================================

WHAT IS LOAD BALANCING?
------------------------
Load balancing distributes incoming network traffic across multiple servers to
ensure no single server is overwhelmed, improving availability and throughput.

================================================================================
B.1 LOAD BALANCER PLACEMENT IN ARCHITECTURE
================================================================================

  Internet
     │
  [DNS]
     │
  [CDN / WAF]  ← Optional: Cloudflare, Akamai
     │
  [Load Balancer (L4 or L7)]  ← ALB, Nginx, HAProxy
     │         │         │
  [Server1] [Server2] [Server3]
     │         │
  [Database]  [Cache]

================================================================================
B.2 TYPES OF LOAD BALANCERS
================================================================================

LAYER 4 LOAD BALANCER (Transport Layer)
  - Operates on TCP/UDP (IP + port)
  - Routing based on source/dest IP and port
  - Cannot inspect HTTP content (no URL-based routing)
  - Very fast and efficient; lower latency
  - Examples: AWS NLB, HAProxy (TCP mode), nginx (stream module)
  - Use case: High-throughput, low-latency (databases, gaming, streaming)

LAYER 7 LOAD BALANCER (Application Layer)
  - Operates on HTTP/HTTPS (URL, headers, cookies, body)
  - Can route based on URL path, host, headers
  - Can terminate TLS, add headers, modify requests
  - More CPU overhead than L4
  - Examples: AWS ALB, Nginx (http mode), HAProxy (http mode), Traefik
  - Use case: Microservices routing, A/B testing, canary deploys

GLOBAL SERVER LOAD BALANCING (GSLB)
  - Routes requests across data centers/regions
  - Uses DNS + health checks to pick best region
  - Examples: AWS Route 53 with health checks, Cloudflare Load Balancing

================================================================================
B.3 LOAD BALANCING ALGORITHMS
================================================================================

ALGORITHM              DESCRIPTION                              USE CASE
--------------------   ---------------------------------------- ----------------
Round Robin            Requests cycled across servers           Equal-capacity servers
Weighted Round Robin   Servers get proportional share           Mixed-capacity servers
Least Connections      Route to server with fewest active conns Variable request length
Least Response Time    Route to fastest-responding server       Latency-sensitive
IP Hash / Sticky       Same client IP always → same server      Stateful apps, caching
Random                 Random server selection                  Simple, stateless
Resource-Based         Route based on CPU/memory utilization    Dynamic workloads
Consistent Hashing     Hash key maps to server ring             Cache locality, sharding

ROUND ROBIN EXAMPLE:
  Requests 1,2,3,4,5,6 → Server A, B, C, A, B, C

WEIGHTED ROUND ROBIN:
  Server A (weight 3), Server B (weight 1) → A,A,A,B,A,A,A,B ...
  Use when servers have different capacity (different instance types)

LEAST CONNECTIONS:
  Ideal when requests vary in duration (long vs short tasks)
  L4 LB can't do this (no connection state); L7 LB tracks active connections

IP HASH (STICKY SESSIONS VIA LB):
  hash(client_IP) % N → always same server
  Problem: if server goes down or N changes, hash breaks
  Solution: Consistent hashing minimizes remapping on change

================================================================================
B.4 SESSION PERSISTENCE (STICKY SESSIONS)
================================================================================

PROBLEM: Some apps store session state in server memory. If requests from the
         same user go to different servers, session is lost.

SOLUTIONS:
  1. Sticky Sessions (Cookie-based affinity)
     LB sets a cookie (e.g., AWSALB) that maps user to specific server.
     Problem: Load becomes uneven if session durations vary.

  2. Shared Session Store
     Store sessions in Redis/Memcached. Any server can serve any request.
     Better scalability; preferred for cloud-native apps.

  3. Stateless Design
     Store state in client (JWT tokens) or database. No sticky sessions needed.
     Best practice for horizontal scaling.

================================================================================
B.5 HEALTH CHECKS
================================================================================

PASSIVE HEALTH CHECKS:
  LB detects failures by monitoring responses to real traffic.
  Threshold: N consecutive failures → mark server down.

ACTIVE HEALTH CHECKS:
  LB proactively pings servers (HTTP GET /health, TCP connect, DNS query).
  Faster detection; catches servers before they fail under load.

TYPES:
  TCP health check   : Establish TCP connection → success
  HTTP health check  : GET /health → 200 OK expected
  HTTPS health check : Same with TLS
  gRPC health check  : grpc.health.v1.Health.Check

HEALTH CHECK RESPONSE (best practice):
  GET /health → 200 OK
  {
    "status": "UP",
    "checks": {
      "database": "UP",
      "redis": "UP",
      "diskSpace": "UP"
    }
  }

  Spring Boot Actuator: GET /actuator/health (built-in)

GRACEFUL REMOVAL:
  1. LB stops sending new requests (drain)
  2. In-flight requests complete
  3. Server safely taken offline
  Connection draining timeout: typically 30-300 seconds

================================================================================
B.6 AWS LOAD BALANCERS (Common Interview Context)
================================================================================

AWS ALB (Application Load Balancer) — Layer 7
  - HTTP/HTTPS/gRPC/WebSocket
  - Path-based routing (/api/* → backend, /web/* → frontend)
  - Host-based routing (api.example.com vs www.example.com)
  - Weighted target groups (canary deployments)
  - Native integration with ECS, EKS, Lambda

AWS NLB (Network Load Balancer) — Layer 4
  - TCP/UDP/TLS
  - Ultra-low latency, handles millions of requests/second
  - Static IP per AZ (useful for whitelisting)
  - Preserves source IP

AWS CLB (Classic Load Balancer) — Legacy
  - Basic L4+L7, largely superseded by ALB/NLB

================================================================================
B.7 LOAD BALANCING IN MICROSERVICES — CLIENT-SIDE vs SERVER-SIDE
================================================================================

SERVER-SIDE LOAD BALANCING (Traditional)
  Client → Load Balancer → Service Instances
  LB is a centralized component; client doesn't know about instances.
  Examples: AWS ALB, Nginx, HAProxy

CLIENT-SIDE LOAD BALANCING
  Client knows about all service instances (from service registry like Consul/Eureka).
  Client picks which instance to call (round robin, random, least connections).
  Examples: Netflix Ribbon, Spring Cloud LoadBalancer, Envoy sidecar
  Benefits: No single point of failure LB; LB logic in client

SERVICE MESH (Advanced)
  Sidecar proxy (Envoy/Istio) handles LB, retries, circuit breaking transparently.
  App code doesn't implement LB at all.
  Examples: Istio, Linkerd, Consul Connect

================================================================================
B.8 INTERVIEW QUESTIONS — DNS AND LOAD BALANCING
================================================================================

Q1: What happens during a DNS lookup?
    Browser → OS cache → recursive resolver → root nameserver → TLD nameserver
    → authoritative nameserver → IP address returned, cached by TTL.

Q2: What is a CNAME record and when would you use it?
    CNAME maps one hostname to another (alias). Used when a domain points to
    another domain (e.g., www → example.com, or custom domain → CDN hostname).
    Cannot have CNAME at the zone apex (root domain) — use ALIAS/ANAME records.

Q3: What load balancing algorithm would you use for a chat application?
    Sticky sessions (consistent hashing / IP hash) to route users to the same
    server maintaining their WebSocket connection. Or better: externalize session
    state to Redis so any server can serve any user (preferred).

Q4: How does a load balancer detect a server failure and stop routing to it?
    Active health checks: LB pings /health endpoint. After N consecutive failures
    (configurable), marks server as unhealthy and removes from rotation.
    Passive: monitors error rates in real traffic.

Q5: What is the difference between L4 and L7 load balancing?
    L4 routes based on IP/port (TCP/UDP); cannot inspect HTTP content; fast.
    L7 inspects HTTP headers, URL, cookies; enables path-based routing,
    header injection, SSL termination; more CPU overhead.

Q6: What is sticky sessions and what problems can it cause?
    Routes same client to same server (cookie or IP hash). Problem: hot spots
    if some users generate more traffic; server failure loses all their sessions.
    Prefer stateless design or distributed session stores.

Q7: How would you handle a zero-downtime deployment with a load balancer?
    Rolling deploy: LB removes server → deploy new version → health check passes
    → LB adds back → repeat for each server. OR blue-green deploy: spin up
    new fleet, shift traffic via LB, keep old fleet for rollback.
