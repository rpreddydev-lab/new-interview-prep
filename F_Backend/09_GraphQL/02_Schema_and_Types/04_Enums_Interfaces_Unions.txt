GRAPHQL ENUMS, INTERFACES, AND UNIONS — IN DEPTH
================================================================

PART 1: ENUMS
═══════════════════════════════════════════════════

1. WHAT ARE ENUMS?
------------------
Enums (Enumeration types) represent a restricted set of named values.
When a field returns an enum, it can ONLY be one of the declared values.
When an argument expects an enum, it ONLY accepts declared values.

```graphql
enum OrderStatus {
  PENDING
  PROCESSING
  SHIPPED
  DELIVERED
  CANCELLED
  REFUNDED
}

type Order {
  id: ID!
  status: OrderStatus!
}
```

2. ENUM CONVENTIONS
--------------------
- Values are ALL_CAPS by convention (SCREAMING_SNAKE_CASE)
- Enum type names are PascalCase
- Add descriptions to document meaning:

```graphql
"""
The lifecycle status of an order.
"""
enum OrderStatus {
  "Order received but not yet confirmed"
  PENDING
  "Order confirmed and being prepared"
  PROCESSING
  "Order has been handed to carrier"
  SHIPPED
  "Order received by customer"
  DELIVERED
  "Order was cancelled before shipping"
  CANCELLED
  "Payment refunded after cancellation or return"
  REFUNDED
}
```

3. ENUMS AS ARGUMENTS
----------------------
```graphql
type Query {
  orders(
    status: OrderStatus
    sortBy: OrderSortField
    sortDirection: SortDirection = DESC
  ): [Order!]!
}

enum OrderSortField {
  CREATED_AT
  TOTAL_AMOUNT
  STATUS
}

enum SortDirection {
  ASC
  DESC
}
```

4. ENUM INTERNAL VALUES (SERVER-SIDE MAPPING)
----------------------------------------------
The GraphQL enum value (e.g., `PENDING`) doesn't have to match the internal
server representation. You can map them:

Java (graphql-java):
```java
public enum OrderStatus {
  PENDING("pending"),
  PROCESSING("processing"),
  SHIPPED("shipped"),
  DELIVERED("delivered"),
  CANCELLED("cancelled"),
  REFUNDED("refunded");

  private final String dbValue;

  OrderStatus(String dbValue) { this.dbValue = dbValue; }
  public String getDbValue() { return dbValue; }
}
```

The GraphQL runtime uses the Java enum's name() (PENDING, SHIPPED, etc.)
to match the SDL enum values.

5. ENUM BEST PRACTICES
------------------------
  ✓ Use enums for any restricted set of values (statuses, roles, directions)
  ✓ Add descriptions to each value explaining its meaning
  ✓ Consider adding an UNKNOWN value for defensive handling of future values
  ✓ Expose stable names (clients will hardcode these!)
  ✗ Don't add too many values to a single enum — consider splitting
  ✗ Don't use String when an enum is more appropriate (misses validation)

6. WHAT ARE INTERFACES?
------------------------
An Interface is an abstract type that defines a contract. Any Object type
that implements an interface MUST include all of the interface's fields.
Interfaces allow polymorphic queries — a field can return different concrete
types, all guaranteed to share interface fields.

```graphql
interface Node {
  id: ID!
}

interface Searchable {
  title: String!
  description: String
  relevanceScore: Float
}
```

7. IMPLEMENTING AN INTERFACE
-----------------------------
```graphql
interface Timestamped {
  createdAt: DateTime!
  updatedAt: DateTime
}

type Article implements Node & Timestamped {
  id: ID!                # from Node
  createdAt: DateTime!   # from Timestamped
  updatedAt: DateTime    # from Timestamped
  title: String!
  body: String!
  author: User!
}

type Comment implements Node & Timestamped {
  id: ID!
  createdAt: DateTime!
  updatedAt: DateTime
  body: String!
  author: User!
  article: Article!
}
```

8. QUERYING INTERFACE FIELDS
------------------------------
```graphql
# Field returning an interface type
type Query {
  node(id: ID!): Node          # Can return User, Product, Order, etc.
  feed: [FeedItem!]!           # FeedItem is an interface
}

interface FeedItem {
  id: ID!
  createdAt: DateTime!
}

type Post implements FeedItem { ... }
type Video implements FeedItem { ... }
type Poll implements FeedItem { ... }
```

Querying:
```graphql
query GetFeed {
  feed {
    id          # Available on all FeedItem types (interface field)
    createdAt   # Available on all FeedItem types
    # Type-specific fields require inline fragments:
    ... on Post  { title body }
    ... on Video { url duration }
    ... on Poll  { question options { text votes } }
  }
}
```

9. INTERFACE RESOLUTION (SERVER)
----------------------------------
When a resolver returns an object for an interface field, the server needs
to know WHICH concrete type it is. This is done via __resolveType:

Java (graphql-java / Spring):
```java
@Bean
public RuntimeWiringConfigurer runtimeWiringConfigurer() {
  return builder -> builder
    .type("Node", typeWiring -> typeWiring
      .typeResolver(env -> {
        Object obj = env.getObject();
        if (obj instanceof User) return env.getSchema().getObjectType("User");
        if (obj instanceof Product) return env.getSchema().getObjectType("Product");
        if (obj instanceof Order) return env.getSchema().getObjectType("Order");
        return null;
      })
    );
}
```

Or with ClassNameTypeResolver (maps Java class name to GraphQL type name):
```java
.typeResolver(new ClassNameTypeResolver())
```

10. THE NODE INTERFACE PATTERN (RELAY)
---------------------------------------
The Node interface is a foundational pattern for globally unique IDs:

```graphql
interface Node {
  id: ID!
}

type Query {
  node(id: ID!): Node
  nodes(ids: [ID!]!): [Node]!
}
```

IDs encode type + database ID:
  - User with DB id=42 → GraphQL id = base64("User:42") = "VXNlcjo0Mg=="
  - Product with DB id=99 → "UHJvZHVjdDo5OQ=="

The `node` query decodes the ID, extracts the type, routes to the right
repository, and returns the entity. This is foundational to Relay.

11. INTERFACE INHERITANCE (IMPLEMENTING INTERFACES)
-----------------------------------------------------
An Interface CAN implement another Interface (spec 2021+):

```graphql
interface Entity {
  id: ID!
}

interface Auditable implements Entity {
  id: ID!
  createdAt: DateTime!
  updatedAt: DateTime
}

type Product implements Auditable {
  id: ID!
  createdAt: DateTime!
  updatedAt: DateTime
  name: String!
}
```

12. WHAT ARE UNIONS?
---------------------
A Union type represents one of several possible Object types. Unlike
interfaces, union members don't need to share any fields.

```graphql
union SearchResult = User | Product | Article | Category

type Query {
  search(query: String!): [SearchResult!]!
}
```

13. QUERYING UNIONS
--------------------
Because there are no shared fields, you MUST use inline fragments for all fields:

```graphql
query Search($query: String!) {
  search(query: $query) {
    __typename        # Always available — tells you the concrete type
    ... on User    { id name email }
    ... on Product { id name price category { name } }
    ... on Article { id title publishedAt author { name } }
    ... on Category { id name productCount }
  }
}
```

Response:
```json
{
  "data": {
    "search": [
      { "__typename": "User", "id": "1", "name": "Alice", "email": "alice@ex.com" },
      { "__typename": "Product", "id": "99", "name": "iPhone 15", "price": 999.0, "category": {"name": "Electronics"} },
      { "__typename": "Article", "id": "5", "title": "GraphQL Guide", "publishedAt": "2026-04-08", "author": {"name": "Bob"} }
    ]
  }
}
```

14. UNION RESOLUTION (SERVER)
-------------------------------
Same as interface: requires __resolveType:

```java
.type("SearchResult", typeWiring -> typeWiring
  .typeResolver(env -> {
    Object obj = env.getObject();
    GraphQLSchema schema = env.getSchema();
    if (obj instanceof User)     return schema.getObjectType("User");
    if (obj instanceof Product)  return schema.getObjectType("Product");
    if (obj instanceof Article)  return schema.getObjectType("Article");
    return null;
  })
)
```

15. INTERFACE vs UNION — DECISION GUIDE
-----------------------------------------
Use INTERFACE when:
  ✓ Types share common fields that make sense to query without fragments
  ✓ You want to enforce a structural contract
  ✓ Types are "is-a" relationships (Post IS-A FeedItem)
  ✓ Example: `interface FeedItem { id: ID!, createdAt: DateTime! }`

Use UNION when:
  ✓ Types are unrelated in structure
  ✓ You need to return heterogeneous results (search, notifications)
  ✓ No shared fields make sense
  ✓ Example: `union SearchResult = User | Product | Post`

  Can you use both? YES — a union can contain types that implement interfaces:
  ```graphql
  interface Identifiable { id: ID! }
  type User implements Identifiable { id: ID!, name: String! }
  type Product implements Identifiable { id: ID!, name: String!, price: Float! }
  union SearchResult = User | Product
  ```

16. PRACTICAL EXAMPLES
-----------------------

  Error handling with Union (Result type pattern):
  ```graphql
  union CreateUserResult = User | ValidationError | DuplicateEmailError

  type ValidationError {
    field: String!
    message: String!
  }

  type DuplicateEmailError {
    existingUserId: ID!
    message: String!
  }

  type Mutation {
    createUser(input: CreateUserInput!): CreateUserResult!
  }
  ```

  Notification feed with Interface:
  ```graphql
  interface Notification {
    id: ID!
    read: Boolean!
    createdAt: DateTime!
  }

  type OrderNotification implements Notification {
    id: ID!
    read: Boolean!
    createdAt: DateTime!
    order: Order!
    message: String!
  }

  type MessageNotification implements Notification {
    id: ID!
    read: Boolean!
    createdAt: DateTime!
    sender: User!
    preview: String!
  }
  ```

17. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the difference between Interface and Union?
A: Interface requires member types to share common fields and enforces a
   structural contract. Union allows completely unrelated types with no
   shared fields. Use Interface for "is-a" relationships with shared structure;
   use Union for heterogeneous collections like search results.

Q: How does the server know which concrete type a resolver returned?
A: Via the __resolveType function (type resolver). When a field returns an
   abstract type (Interface or Union), the executor calls __resolveType with
   the resolved object and expects back the GraphQL type name. Without this,
   the server throws an error.

Q: Can a single type implement multiple interfaces?
A: Yes. Use the `&` separator: `type User implements Node & Timestamped &
   Searchable { ... }`. The type must include all fields from all implemented
   interfaces.

Q: Can you have a Union of Interface types?
A: No. Unions can only contain Object types, not Interfaces. However, a Union
   can contain Object types that themselves implement an Interface.

Q: What is `__typename` and why is it important?
A: `__typename` is a meta-field available on every Object, Interface, and Union
   type. It returns the runtime type name (e.g., "User", "Product"). It's
   essential for handling union/interface results on the client, and Apollo
   Client uses it (with `id`) as the normalized cache key.

Q: What is the Node interface and why is it important?
A: Node is a standard interface from the Relay spec with a single field:
   `id: ID!`. The root Query type has a `node(id: ID!): Node` field. All
   entities that implement Node get globally unique IDs. This enables Apollo
   Client's normalized cache (caches by `TypeName:id`) and Relay's refetching
   mechanism.
