PERSISTED QUERIES IN GRAPHQL — IN DEPTH
================================================================

1. WHAT ARE PERSISTED QUERIES?
--------------------------------
Persisted Queries (also called Automatic Persisted Queries / APQ) are a
technique where the client and server agree on a hash-based identifier for
a query, so subsequent requests only send the hash instead of the full
query string.

Benefits:
  - Smaller request payloads (hash vs full query)
  - Better caching (GET requests with query hash as URL parameter)
  - Improved security (server can whitelist known queries)

Two variants:
  a) Automatic Persisted Queries (APQ) — client-driven, hash as ID
  b) Trusted/Whitelisted Documents — server holds approved query registry

2. HOW APQ WORKS
-----------------
APQ flow (Apollo spec):

```
First request (cache miss):
1. Client sends: { extensions: { persistedQuery: { version: 1, sha256Hash: "abc..." } } }
   (no query string)
2. Server responds: { errors: [{ message: "PersistedQueryNotFound" }] }
3. Client sends: full query string + hash

Second+ request (cache hit):
1. Client sends: { extensions: { persistedQuery: { version: 1, sha256Hash: "abc..." } } }
   (no query string)
2. Server looks up hash in cache → executes stored query
3. Server returns data normally
```

After the first round-trip, all subsequent requests use only the hash.
For GET requests:
```
GET /graphql?extensions={"persistedQuery":{"version":1,"sha256Hash":"abc..."}}
```

3. IMPLEMENTING APQ IN SPRING FOR GRAPHQL
-------------------------------------------
Spring for GraphQL has built-in support via GraphQlSource with
InMemoryPersistedQueryStore:

```java
@Configuration
public class PersistedQueryConfig {

  @Bean
  public GraphQlSourceBuilderCustomizer persistedQueryCustomizer() {
    return builder -> builder
      .configureGraphQl(b -> b
        .preparsedDocumentProvider(new PersistedQuerySupport(
          new InMemoryPersistedQueryCache(Map.of())  // start empty, builds up at runtime
        ))
      );
  }
}
```

Or with Redis-backed cache for distributed deployments:
```java
@Bean
public PreparsedDocumentProvider persistedQueryProvider(RedisTemplate<String, String> redis) {
  return new PersistedQuerySupport(new RedisPersistedQueryCache(redis));
}

// Custom Redis implementation
public class RedisPersistedQueryCache implements PersistedQueryCache {
  private final RedisTemplate<String, String> redis;
  private static final String PREFIX = "graphql:pq:";

  @Override
  public Optional<String> getQuery(String queryId) {
    return Optional.ofNullable(redis.opsForValue().get(PREFIX + queryId));
  }

  @Override
  public void saveQuery(String queryId, String queryDocument) {
    redis.opsForValue().set(PREFIX + queryId, queryDocument, Duration.ofDays(7));
  }
}
```

4. WHITELISTED (TRUSTED) DOCUMENTS
-------------------------------------
A stricter security model: only pre-approved queries are allowed.
Unknown queries are rejected, even if syntactically valid.

```java
@Configuration
public class TrustedDocumentConfig {

  // Load allowed queries from a registry file built at CI/CD time
  @Bean
  public PreparsedDocumentProvider trustedDocumentsProvider() {
    Map<String, String> registry = loadRegistry();  // hash → query string

    return (executionInput, computeFunction) -> {
      String queryId = getQueryId(executionInput);  // extract from extensions

      if (queryId != null) {
        String cachedQuery = registry.get(queryId);
        if (cachedQuery == null) {
          // Unknown query hash — reject!
          throw new UnknownQueryException("Unknown query: " + queryId);
        }
        // Use the server-side copy of the query (ignore client-provided query)
        ExecutionInput trusted = executionInput.transform(b -> b.query(cachedQuery));
        return computeFunction.apply(trusted);
      }

      // If no hash provided and arbitrary queries are disabled
      if (arbitraryQueriesDisabled()) {
        throw new QueryNotPermittedException("Only persisted queries allowed");
      }

      return computeFunction.apply(executionInput);
    };
  }

  private Map<String, String> loadRegistry() {
    // Load from JSON file generated by graphql-codegen or similar
    return Map.of(
      "sha256:abc123", "query GetUser($id: ID!) { user(id: $id) { name email } }",
      "sha256:def456", "query ListPosts { posts { id title } }"
    );
  }
}
```

5. CI/CD INTEGRATION FOR TRUSTED QUERIES
------------------------------------------
Best practice: auto-generate the query registry during the CI/CD pipeline.

```
Development:
  1. Developer writes queries in the frontend app
  2. CI/CD runs: graphql-codegen extract → generates query registry
  3. Registry committed to repo (tracked in version control)

Deployment:
  4. Frontend app bundles query hashes (not full queries)
  5. Backend loads registry from classpath
  6. Only registered queries execute; all others rejected
```

Using Apollo's query extraction:
```bash
# Extract all queries from frontend code
npx apollo client:extract --endpoint=http://localhost:8080/graphql queries.json

# Format: { "queryId1": "query string 1", "queryId2": "query string 2" }
```

6. CACHING WITH PERSISTED QUERIES
-----------------------------------
Persisted queries enable HTTP GET for caching (POST can't be cached by CDNs):

```
# Client sends as GET (cacheable by CDN/proxy):
GET /graphql?operationName=GetUser&variables={"id":"1"}&extensions={"persistedQuery":{"version":1,"sha256Hash":"abc"}}

# CDN caches response for this exact hash+variables combo
# Subsequent identical requests served from CDN cache, not app server
```

For public (non-authenticated) queries, this drastically reduces server load.

7. DISABLING AD-HOC QUERIES IN PRODUCTION
-------------------------------------------
The ultimate security measure: only accept persisted queries in production.

```java
@Override
public Mono<WebGraphQlResponse> intercept(WebGraphQlRequest request, Chain chain) {
  if (!isProductionProfile()) {
    return chain.next(request); // Allow ad-hoc in dev/staging
  }

  String document = request.getDocument();
  String queryId = extractQueryId(request);  // From extensions

  if (queryId == null && document != null) {
    // Ad-hoc query without a persisted ID — reject in prod
    return Mono.just(WebGraphQlResponse.create(
      ExecutionResult.newExecutionResult()
        .addError(GraphqlErrorBuilder.newError()
          .message("Ad-hoc queries are not allowed in production. Use persisted queries.")
          .errorType(ErrorType.FORBIDDEN)
          .build())
        .build()
    ));
  }

  return chain.next(request);
}
```

8. INTROSPECTION AND PERSISTED QUERIES
-----------------------------------------
Persisted queries complement introspection disabling:
  - Disable introspection in production (stops schema discovery)
  - Require persisted queries (stops arbitrary execution)
  - Together: very strong security posture

```yaml
spring:
  graphql:
    schema:
      introspection:
        enabled: false  # Only disable in production!
```

9. APAQ HASH GENERATION (SHA-256)
------------------------------------
The query ID is a SHA-256 hash of the normalized query document:

```java
import java.security.MessageDigest;
import java.util.HexFormat;

public class QueryHasher {
  public static String hash(String queryDocument) throws NoSuchAlgorithmException {
    MessageDigest digest = MessageDigest.getInstance("SHA-256");
    byte[] hash = digest.digest(queryDocument.getBytes(StandardCharsets.UTF_8));
    return HexFormat.of().formatHex(hash);  // Java 17+
  }
}
```

Client (JavaScript):
```javascript
import { createHash } from 'crypto';
const queryHash = createHash('sha256').update(query).digest('hex');
```

10. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is an Automatic Persisted Query (APQ)?
A: APQ is a protocol where the client sends a SHA-256 hash of the query
   instead of the full query string. On the first request with an unknown
   hash, the server responds with "PersistedQueryNotFound" and the client
   retries with the full query. Subsequent requests only need the hash.
   Benefits: smaller payloads, GET-based caching, optional query whitelisting.

Q: What is the difference between APQ and Trusted Documents?
A: APQ: Client can register new queries at runtime. Server stores hashes as
   clients discover them. Flexible but allows any valid query to run.
   Trusted Documents: Only pre-approved queries (compiled at build time into
   a registry) are accepted. Unknown hashes are rejected. Stricter security
   but requires CI/CD integration and limits client flexibility.

Q: How do persisted queries improve performance?
A: (1) Smaller request payload — hash is ~64 chars vs potentially KB of query.
   (2) Enable HTTP GET requests (instead of POST) for non-mutating operations,
   which CDNs can cache. (3) Parsed documents can be cached server-side by
   hash, avoiding parsing the same query string repeatedly.

Q: How do you implement persisted queries in Spring for GraphQL?
A: Implement or configure a PreparsedDocumentProvider. For APQ, use
   InMemoryPersistedQueryCache (or Redis for distributed). For trusted
   documents, build a query registry at CI/CD time, load it on startup,
   and reject unknown query IDs in the PreparsedDocumentProvider.

Q: Can you cache GraphQL responses at the CDN level?
A: Yes, but only for HTTP GET requests (POSTs are not cacheable by CDNs).
   Persisted queries enable GET: `GET /graphql?extensions=...&variables=...`.
   For public, non-authenticated queries, CDN caching works well.
   For authenticated queries, use per-user caching (Authorization header
   as cache key) or skip CDN caching and use application-level caching.

Q: Should you disable introspection in production?
A: Yes for public APIs. Introspection exposes the full schema structure,
   which helps attackers craft targeted queries or find deprecated endpoints.
   Keep introspection enabled in development and staging. For trusted
   internal teams, you may whitelist introspection by role/header.
