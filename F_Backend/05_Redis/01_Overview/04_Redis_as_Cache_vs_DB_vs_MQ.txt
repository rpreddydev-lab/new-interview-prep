REDIS AS CACHE vs DATABASE vs MESSAGE QUEUE — DEEP DIVE FOR INTERVIEWS
================================================================================

1. THE THREE ROLES OF REDIS
─────────────────────────────
Redis is uniquely versatile. Unlike most tools that serve one purpose, Redis can
act as all three at once — or be dedicated to one role.

  ┌────────────────────────────────────────────────────────────────┐
  │          CACHE           │  DATABASE  │    MESSAGE QUEUE       │
  │   (fast data access)     │ (primary   │  (async communication) │
  │                          │  store)    │                        │
  └────────────────────────────────────────────────────────────────┘

Most common real-world use: Cache in front of a relational DB.
Less common but powerful: Redis as a primary store (sessions, leaderboards).
Increasingly popular: Redis Streams as a lightweight message broker.


2. REDIS AS A CACHE
────────────────────

2a. What it means:
  Redis sits between your application and the primary database (Postgres, MySQL,
  MongoDB, etc.). Frequently accessed data is stored in Redis. On a cache HIT
  the DB is not queried at all.

2b. Key properties:
  - Data is EXPENDABLE: losing the cache is acceptable (can rebuild from DB)
  - TTL is almost always set to prevent stale data and memory overflow
  - Eviction policies handle memory pressure automatically
  - Strong consistency is NOT required (eventual consistency tolerated)

2c. Configuration for caching role:
  maxmemory 4gb
  maxmemory-policy allkeys-lru   # evict LRU keys when full
  # No persistence needed (optional for warm restarts)
  save ""                         # disable RDB
  appendonly no                   # disable AOF

2d. Cache patterns (details in 02_Caching_Patterns):
  - Cache-Aside (Lazy Loading): most common
  - Read-Through / Write-Through: transparent caching
  - Write-Behind (Write-Back): async persistence

2e. Strengths as a cache:
  ✓ Extremely fast (sub-ms latency)
  ✓ Built-in TTL and eviction
  ✓ Simple integration (get/set pattern)
  ✓ Works with any backend DB

2f. Weaknesses:
  ✗ Cache invalidation complexity (stale data)
  ✗ Cold start problem (empty cache after restart)
  ✗ Memory limit: can only cache a working set, not all data


3. REDIS AS A PRIMARY DATABASE
────────────────────────────────

3a. What it means:
  Redis is the authoritative source of truth. No separate SQL/NoSQL DB.
  Persistence (RDB/AOF) ensures data survives restarts.

3b. When it makes sense:
  - Data fits in RAM (or with Redis Cluster, fits across cluster RAM)
  - Access patterns are key-value lookups (not complex SQL joins)
  - Data structures map well to Redis types (leaderboards → ZSet)
  - High read/write throughput with simple schema

3c. Real-world examples where Redis IS the DB:
  - Session store (session_id → session_data): hundreds of millions of sessions
  - Leaderboards (userId → score in ZSet): games, competition sites
  - Rate limit counters: per-user API counters
  - Real-time inventory counters: ticket availability
  - Shopping cart: HSET cart:user:42 item:1 2 item:2 1
  - User profile cache: HSET user:42 name "Alice" email "a@b.com" age 30

3d. Configuration for DB role:
  appendonly yes
  appendfsync everysec      # or always for max durability
  save 900 1
  save 300 10
  save 60 10000
  # No maxmemory eviction (don't want data evicted!)
  maxmemory-policy noeviction   # return error instead of evicting

3e. RedisJSON (module) for document storage:
  JSON.SET user:42 $ '{"name":"Alice","orders":[1,2,3]}'
  JSON.GET user:42 $.name
  JSON.ARRAPPEND user:42 $.orders 4

3f. Strengths as a DB:
  ✓ Sub-millisecond reads and writes
  ✓ Rich data structure operations server-side (no ORM needed for simple ops)
  ✓ Atomic operations (no transaction management needed for simple cases)
  ✓ Horizontal scaling (Redis Cluster)

3g. Weaknesses as a DB:
  ✗ All data must fit in RAM (expensive at scale)
  ✗ No SQL / complex joins
  ✗ No ACID transactions across multiple keys
  ✗ No secondary indexes (without RediSearch module)
  ✗ Schema-less: easy to have inconsistent data
  ✗ Not suitable for large documents or binary blobs (use blob storage)


4. REDIS AS A MESSAGE QUEUE / MESSAGE BROKER
──────────────────────────────────────────────

4a. What it means:
  Redis decouples producers and consumers. Producers write messages; consumers
  read and process them asynchronously.

4b. Three mechanisms:

  ── Approach 1: List as Queue ──
    LPUSH queue:emails '{"to":"a@b.com","subject":"Welcome"}'
    BRPOP queue:emails 0   # blocking pop, consumer waits

    Simple FIFO queue. BRPOP is efficient (no polling).
    Drawback: message is gone once popped — no acknowledgment, no retry.

  ── Approach 2: Pub/Sub ──
    PUBLISH events:user-signup '{"userId":42}'
    SUBSCRIBE events:user-signup

    Fan-out to multiple consumers. Fire-and-forget.
    Drawback: No persistence. Disconnected consumers miss messages.

  ── Approach 3: Redis Streams (BEST for MQ use case) ──
    XADD stream:orders * orderId 42 amount 99.99
    XREADGROUP GROUP workers consumer1 COUNT 10 STREAMS stream:orders >
    XACK stream:orders workers 1234567890-0

    Consumer groups: multiple consumers each get different messages
    Acknowledgment: message stays in pending list until ACKed
    Replay: consumer can re-read from any offset
    Persistence: stream data can be persisted with AOF/RDB

    Comparison to Kafka:
      Redis Streams                     │ Kafka
      ──────────────────────────────────┼────────────────────────
      In-memory (optional persistence)  │ Disk-based (durable)
      Low latency (< 1ms)               │ Higher latency (1-10ms)
      Simpler setup                     │ Complex (Zookeeper/KRaft)
      Limited retention (MAXLEN)        │ Configurable long retention
      Single broker (or cluster)        │ Distributed partitions
      No message ordering guarantee     │ Per-partition ordering
      Good for: small-medium workloads  │ Good for: high-volume event streaming

4c. Configuration for MQ role:
  appendonly yes         # persistence for durability
  appendfsync everysec
  # Streams auto-trim
  XADD stream:orders MAXLEN ~ 100000 * orderId 42   # keep ~100K messages

4d. Strengths as MQ:
  ✓ Very low latency
  ✓ Simple to set up (no separate Kafka/RabbitMQ cluster)
  ✓ Streams have consumer groups, ACKs, dead-letter patterns
  ✓ Integrated with existing Redis infrastructure

4e. Weaknesses as MQ:
  ✗ Not designed for massive (billions of events) long-term retention
  ✗ Less feature-rich than Kafka (no compacted topics, no exactly-once semantics)
  ✗ Pub/Sub has no persistence → use Streams instead if durability matters


5. CHOOSING THE RIGHT ROLE: DECISION FRAMEWORK
───────────────────────────────────────────────

  Ask these questions:

  1. Does losing this data matter permanently?
     NO  → Pure cache (no persistence, allkeys-lru eviction)
     YES → DB or MQ role (enable persistence, noeviction)

  2. Is the access pattern key-value or does it need SQL?
     Key-value / rich data structures → Redis as DB is viable
     Complex joins / reporting         → Use PostgreSQL/MySQL as primary DB

  3. Do you need async decoupling between services?
     YES, simple        → Redis List (LPUSH/BRPOP)
     YES, with ACK/replay → Redis Streams
     YES, high volume    → Kafka/RabbitMQ

  4. Does all data fit comfortably in RAM?
     YES → Redis as primary DB is feasible
     NO  → Redis as cache only; use disk-based DB for primary storage

  5. Do you need complex querying (filter, aggregate, search)?
     NO  → Redis native commands
     YES → Add RediSearch module or use separate DB

Real-world architecture (most common):
  [App] → [Redis Cache (TTL, LRU)] → [PostgreSQL / MySQL] (source of truth)
        → [Redis Streams] → [Worker services]


6. HYBRID USAGE EXAMPLE: E-COMMERCE PLATFORM
──────────────────────────────────────────────
  Same Redis cluster serving 3 roles:

  Cache role:
    product:1234 → cached product JSON (TTL 10 min)
    search:results:"shoes" → cached search results (TTL 5 min)

  DB role:
    session:abc123 → user session (persistent, TTL 30 min)
    cart:user:42 → shopping cart Hash (persistent)
    rate:user:42:api → rate limit counter (volatile)
    leaderboard:monthly → top customers Sorted Set (persistent)

  MQ role:
    stream:orders → new order events (consumers: inventory, email, analytics)
    stream:inventory → stock change events

─────────────────────────────────────
  Role      │ RDB    │ AOF    │ maxmemory-policy  │ Notes
  ──────────┼────────┼────────┼───────────────────┼──────────────────────
  Cache     │ OFF    │ OFF    │ allkeys-lru        │ Speed priority

  Database  │ ON     │ ON     │ noeviction         │ Durability priority
  MQ        │ ON     │ ON     │ noeviction         │ Message durability


8. INTERVIEW QUESTIONS & ANSWERS
───────────────────────────────────
  Q: Can Redis replace a traditional database?
  A: For specific use cases yes — session storage, leaderboards, counters,
     shopping carts. But it cannot replace a relational DB for complex queries,
     large datasets that don't fit in RAM, or ACID guarantees across entities.

  Q: How is Redis different from Kafka for messaging?
  A: Redis Streams are in-memory (fast, low latency), simpler to operate, but
     limited retention and no partition-level ordering guarantee. Kafka is
     disk-based, designed for massive long-term event storage, complex routing,
     and exactly-once semantics. Use Redis Streams for moderate workloads, Kafka
     for high-volume event-driven architectures.

  Q: How do you prevent Redis-as-DB from losing data?
  A: Enable both RDB (periodic snapshots) and AOF (appendonly yes,
     appendfsync everysec). Set maxmemory-policy noeviction so Redis never
     silently drops data. Use replicas for HA. Use Redis Cluster for scale.

  Q: What eviction policy do you use for cache vs DB?
  A: Cache: allkeys-lru (or allkeys-lfu for frequency-based). This evicts the
     least recently/frequently used keys when memory is full — fine for a cache.
     Database: noeviction — Redis returns an error rather than losing data.
