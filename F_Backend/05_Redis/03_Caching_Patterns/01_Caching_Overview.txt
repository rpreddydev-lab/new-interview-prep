REDIS CACHING PATTERNS — OVERVIEW FOR INTERVIEWS
================================================================================

1. WHY CACHING MATTERS
───────────────────────
A typical database query takes 1-100 ms. A Redis GET takes < 1 ms.
For a page with 20 DB queries → 20-2000 ms. With Redis cache → < 20 ms.

Caching is about serving frequently-accessed data faster by storing
computed/fetched results closer to the application.

Cache hit rate is the key metric:
  hit_rate = cache_hits / (cache_hits + cache_misses)
  A 90% hit rate means only 10% of requests hit the database.
  99% hit rate = massive DB offload.


2. THE CACHING TRILOGY: WHAT, WHEN, HOW LONG
──────────────────────────────────────────────
  WHAT to cache:
    ✓ Expensive computation results
    ✓ Frequently read, rarely changed data (product catalog, config, translations)
    ✓ Results of DB queries (SELECT * FROM products WHERE id=42)
    ✓ API responses (external service calls)
    ✗ DO NOT cache: highly dynamic data (stock prices, live scores without care)
    ✗ DO NOT cache: security-sensitive, must-be-current data (account balance)

  WHEN to cache:
    - On first miss (lazy loading / cache-aside): only cache what's actually needed
    - On write (write-through): immediately after write to DB
    - Pre-warm (eager loading): fill cache before traffic hits

  HOW LONG to cache (TTL):
    - Too short: cache miss rate high, defeats purpose
    - Too long: stale data, cache invalidation needed
    - Rule: TTL = acceptable staleness window
    - User profile: 5-15 min | Product catalog: 1 hr | Config: 1 hr
    - Real-time data: TTL = 0-30 seconds


3. CACHE INVALIDATION — THE HARDEST PROBLEM
─────────────────────────────────────────────
Phil Karlton: "There are only two hard things in Computer Science: cache
invalidation and naming things."

Strategies:
  a) TTL-based: let the cache expire naturally. Simple. Accepts staleness.
  b) Event-driven: on write to DB, explicitly delete/update the cache key.
     "Write-invalidate": DEL the key on update.
     "Write-update": SET the new value in cache on update.
  c) Pub/Sub invalidation: on DB write, publish to Redis channel, all app
     nodes subscribe and clear their local caches (client-side caching).
  d) Versioned keys: cache:v2:product:42 — bump version on schema change.


4. OVERVIEW OF MAIN PATTERNS
──────────────────────────────
  Pattern          │ Who reads  │ Who writes │ Consistency │ Complexity
  ─────────────────┼────────────┼────────────┼─────────────┼────────────
  Cache-Aside      │ App reads  │ App writes │ Eventual    │ Simple
  Read-Through     │ Cache auto │ App writes │ Eventual    │ Medium
  Write-Through    │ Either     │ Cache+DB   │ Strong      │ Medium
  Write-Behind     │ Either     │ Cache only │ Eventual    │ Complex
  Write-Around     │ App reads  │ DB only    │ Strong*     │ Simple

  *Write-Around: write goes directly to DB bypassing cache, cache updated on
   next read miss. Avoids caching write-heavy data that's rarely re-read.


5. KEY METRICS TO MONITOR
───────────────────────────
  Cache hit rate:   > 90% is healthy; < 80% investigate
  Eviction rate:    High eviction = cache too small or too many unique keys
  Miss latency:     Time to serve a cache miss (DB query time)
  Memory usage:     Track against maxmemory
  Key expiry rate:  How many keys expire per second

  Redis INFO stats:
  keyspace_hits:    cumulative cache hits
  keyspace_misses:  cumulative cache misses
  evicted_keys:     keys evicted due to maxmemory
  expired_keys:     keys that reached TTL

  INFO stats | grep -E "keyspace|evicted|expired"


6. CACHING ANTI-PATTERNS
─────────────────────────
  ✗ Caching everything unconditionally: wastes memory on data never re-read
  ✗ No TTL on cache entries: stale data forever, memory fills up
  ✗ Very short TTL on expensive queries: cache invalidated before reuse
  ✗ Cache key collisions: key="user:42" used for two different things
  ✗ Caching null/error responses: negative caching requires careful handling
  ✗ Not handling cache stampede (thundering herd): see 05_Cache_Stampede_and_Warming
  ✗ Synchronous cache writes on the request path with Write-Behind: complex failure modes


7. PATTERN SELECTION GUIDE
────────────────────────────
  Q: Data is read often, written rarely?
     → Cache-Aside with long TTL (most common)

  Q: Need guaranteed cache freshness on every write?
     → Write-Through

  Q: Need to absorb write spikes, DB write latency is a bottleneck?
     → Write-Behind (Write-Back)

  Q: Data is write-heavy but rarely read back immediately?
     → Write-Around (skip cache on write)

  Q: Need to pre-fill cache before traffic starts?
     → Cache Warming


8. INTERVIEW QUICK-REFERENCE
──────────────────────────────
  "What caching pattern do you use?"
  → "Cache-Aside for most cases — app checks Redis first, on miss queries DB
     and populates the cache. For write-heavy scenarios with latency SLAs, we
     consider Write-Behind. For strong consistency requirements, Write-Through."

  "How do you handle cache invalidation?"
  → "We use a combination: short TTLs as a safety net + explicit invalidation
     (DEL the key) on updates. For distributed caches, we use Pub/Sub or a
     cache-tag system to invalidate related keys atomically."
