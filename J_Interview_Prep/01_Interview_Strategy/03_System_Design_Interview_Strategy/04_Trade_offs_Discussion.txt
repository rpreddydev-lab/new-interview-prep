--------------------------------------------------------------------------------
1. WHY TRADE-OFFS ARE THE CORE OF SYSTEM DESIGN
--------------------------------------------------------------------------------

In system design, there is rarely a "best" answer. There are only choices
that are better or worse for a specific set of requirements.

Great engineers don't say: "Use PostgreSQL."
They say: "For this read-heavy, schema-fixed workload with complex joins,
  PostgreSQL is the best choice because of its ACID guarantees and rich
  query support. If we needed to scale horizontally to 10TB+, we might
  need to consider Cassandra despite losing join support."

The BECAUSE and the ALTERNATIVE are what make you sound senior.

WHAT INTERVIEWERS ARE EVALUATING:
  - Do you know WHY you're making each choice?
  - Can you articulate what you're GIVING UP?
  - Do you consider the requirements before picking a technology?
  - Are you aware that different requirements might change your answer?

JUNIOR ANTI-PATTERN:
  "I'd use microservices with Kafka, Redis, and Elasticsearch."
  (list of buzzwords, no justification)

SENIOR PATTERN:
  "Given our read-heavy workload with a 100:1 ratio, I'd use Redis to cache
  frequently accessed data. The trade-off is cache coherence - we'll have
  eventual consistency, which is acceptable since feed data doesn't need
  to be perfectly real-time. If consistency were critical (e.g., banking),
  we'd need a different approach like write-through caching or forgoing
  caching entirely."

--------------------------------------------------------------------------------
2. THE MAJOR TRADE-OFF AXES IN SYSTEM DESIGN
--------------------------------------------------------------------------------

TRADE-OFF AXIS 1: CONSISTENCY vs. AVAILABILITY
  
  Background: CAP Theorem states that in a distributed system experiencing
  a network partition, you must choose between Consistency and Availability.
  
  CONSISTENCY (CP):
  - All nodes see the same data simultaneously
  - Reads always return the most recent write
  - Risk: System becomes unavailable during partition
  - Use when: Financial transactions, inventory management, user auth
  - Technologies: PostgreSQL, ZooKeeper, etcd
  
  AVAILABILITY (AP):
  - System remains operational even during failures
  - May return stale data temporarily
  - Risk: Different users might see different data
  - Use when: Social feeds, product catalogs, DNS
  - Technologies: Cassandra, DynamoDB (with eventual consistency), Couchbase
  
  DISCUSSION FORMAT:
  "This system needs high availability - users should always be able to
  see their feed, even if some tweets take a few seconds to appear after
  posting. So I'd choose AP and accept eventual consistency.
  If this were a payment system, I'd flip this and choose strong consistency
  even at the cost of availability."

TRADE-OFF AXIS 2: SQL vs. NoSQL

  SQL (Relational):
  ✓ ACID transactions
  ✓ Complex queries with joins
  ✓ Schema enforcement (data integrity)
  ✓ Mature tooling and operations
  ✗ Harder to scale horizontally
  ✗ Schema changes require migrations
  Use when: Complex relationships, financial data, reporting, moderate scale

  NoSQL - Document (MongoDB, Couchbase):
  ✓ Flexible schema (store varied objects)
  ✓ Good for hierarchical data
  ✓ Horizontal scaling
  ✗ Weak join support
  ✗ Variable ACID guarantees
  Use when: CMS, user profiles, product catalogs

  NoSQL - Wide Column (Cassandra, HBase):
  ✓ Exceptional write throughput
  ✓ Linear horizontal scaling
  ✓ Tunable consistency
  ✗ No joins; must denormalize
  ✗ Limited query flexibility
  Use when: Time-series data, high write volume, messaging history

  NoSQL - Key-Value (Redis, DynamoDB):
  ✓ O(1) lookups by key
  ✓ Extremely fast
  ✗ Limited query patterns (only by key)
  Use when: Sessions, caching, leaderboards, shopping carts

  NoSQL - Graph (Neo4j, Amazon Neptune):
  ✓ Relationship-first queries
  ✓ Deep traversals are fast
  ✗ Not suitable for non-graph data
  Use when: Social graphs, fraud detection, recommendation engines

  THE SQL vs. NOSQL DECISION FRAMEWORK:
  1. Do you need ACID transactions? → SQL
  2. Do you need complex joins? → SQL
  3. Do you need > 100K writes/sec? → NoSQL
  4. Do you need horizontal scaling to PB+ data? → NoSQL
  5. Is schema flexible/variable? → NoSQL
  6. Is the data structure a graph? → Graph DB

TRADE-OFF AXIS 3: SYNCHRONOUS vs. ASYNCHRONOUS

  SYNCHRONOUS (REST/gRPC):
  ✓ Simple to reason about
  ✓ Immediate feedback (success/failure)
  ✓ Easy to debug
  ✗ Caller blocks while waiting
  ✗ Tight coupling between services
  ✗ Upstream latency compounds with downstream latency
  Use when: Read operations, user-facing requests needing immediate result

  ASYNCHRONOUS (Kafka, RabbitMQ, SQS):
  ✓ Decouples producer from consumer
  ✓ Handles traffic spikes (queue buffers)
  ✓ Failure isolation (producer unaffected by consumer failure)
  ✓ Enables fan-out (multiple consumers)
  ✗ Eventual consistency only
  ✗ More complex debugging (distributed tracing needed)
  ✗ Message ordering challenges
  ✗ At-least-once delivery → need idempotent consumers
  Use when: Notifications, background processing, event streaming, fan-out

  EXAMPLE DISCUSSION:
  "When a user posts a tweet, I'll write to the DB synchronously since
  the user needs immediate confirmation. But distributing to followers'
  feeds is async via Kafka. The user doesn't need to wait for 10 million
  notifications to complete before seeing 'Tweet Posted'. This decouples
  the critical write path from the fan-out."

TRADE-OFF AXIS 4: PUSH vs. PULL (Fan-out)

  PUSH (Fan-out on write):
  - When user posts, immediately push to all followers' feed caches
  ✓ Fast reads (feed is pre-computed)
  ✓ Simple read logic
  ✗ Expensive writes (especially for celebrities with 10M+ followers)
  ✗ Wasted work if followers never check their feed

  PULL (Fan-out on read):
  - When user opens feed, query all followed users' recent posts
  ✓ Cheap writes
  ✗ Slow reads for users following many accounts
  ✗ N+1 query problem (need to query each followed user separately)

  HYBRID (Best of both):
  - Push for regular users (< N followers, e.g., 10,000)
  - Pull for celebrities (> N followers)
  - Cache celebrity posts separately; merge at read time

  EXAMPLE DISCUSSION:
  "I'd use a hybrid approach. For regular users with < 10K followers,
  fan-out on write is efficient. For celebrities, fan-out on write would
  cause writes that touch millions of user cache entries simultaneously,
  causing write amplification and hotspot issues in Redis. Instead,
  celebrity tweets are stored separately and merged at read time."

TRADE-OFF AXIS 5: HORIZONTAL vs. VERTICAL SCALING

  VERTICAL (scale up):
  - Add more CPU/RAM/disk to existing servers
  ✓ Simple - no code changes needed
  ✗ Has a hard limit (biggest server available)
  ✗ Single point of failure
  ✗ Usually more expensive at high scale

  HORIZONTAL (scale out):
  - Add more servers
  ✓ Theoretically unlimited scale
  ✓ No single point of failure
  ✗ Need stateless services (sessions can't be server-local)
  ✗ Data distribution becomes complex
  ✗ More operational complexity

  PREFERENCE: Start vertical (simpler), add horizontal as scale demands.
  For databases specifically: read replicas first, then sharding.

TRADE-OFF AXIS 6: MICROSERVICES vs. MONOLITH

  MONOLITH:
  ✓ Simple to develop and deploy
  ✓ No network calls between components
  ✓ Easy to test locally
  ✓ Single deployment unit
  ✗ As it grows: slow to build, hard to scale specific parts
  ✗ Team coordination becomes difficult
  ✗ Technology lock-in
  Use when: Early stage, small team, moderate traffic

  MICROSERVICES:
  ✓ Each service independently deployable and scalable
  ✓ Technology diversity possible
  ✓ Team autonomy (own service end-to-end)
  ✗ Network latency between services
  ✗ Distributed tracing required
  ✗ Operational complexity (many services to manage)
  ✗ Data consistency across services is hard
  Use when: Large team, different scaling requirements per service, mature infra

  STANDARD INTERVIEW ANSWER:
  "At scale, I'd design this as separate services for the main domains
  (user, content, feed, notifications) but acknowledge that in the early
  days a well-structured monolith would have been fine. The decision to
  break it apart is driven by team size and different scaling needs."

TRADE-OFF AXIS 7: CACHING STRATEGIES

  CACHE-ASIDE (Lazy Loading) - Most common:
  - App checks cache first; on miss, reads from DB, stores in cache
  ✓ Only caches what's needed
  ✗ First access is always slow (cold start)
  ✗ Cache can be stale

  WRITE-THROUGH:
  - On every write to DB, also write to cache
  ✓ Cache always fresh
  ✗ Caches things that may never be read (cache bloat)
  ✗ Write latency increases

  WRITE-BEHIND (Write-Back):
  - Write to cache first; persist to DB asynchronously
  ✓ Very fast writes (only one write operation)
  ✗ Risk of data loss if cache fails before DB write
  Use when: Write-heavy, can tolerate small data loss

  REFRESH-AHEAD:
  - Pre-emptively refresh cache before it expires (for hot items)
  ✓ Prevents cache misses for popular items
  ✗ May cache items that won't be requested

  EXAMPLE DISCUSSION:
  "For user profile data, I'd use cache-aside with a 5-minute TTL.
  Profiles are read frequently but changed rarely, so this is a great
  cache candidate. On cache miss, we load from DB and populate the cache.
  The stale profile risk is acceptable - a user won't notice if their
  own recently-updated profile takes a few minutes to refresh globally."

3. HOW TO STRUCTURE A TRADE-OFF DISCUSSION IN AN INTERVIEW
--------------------------------------------------------------------------------

TRADE-OFF DISCUSSION TEMPLATE:

  "For [component/decision], I'm considering [option A] vs [option B].
  
  [Option A] gives us [advantage 1] and [advantage 2], but the trade-off
  is [disadvantage 1], which means [real-world implication].
  
  [Option B] gives us [advantage 3] but requires [extra complexity].
  
  Given our requirements of [specific requirement from scoping phase],
  I'd choose [option A/B] because [specific reason tied to requirements].
  
  If the requirements changed - for example if [scenario], then [option B]
  would become the better choice."

EXAMPLE APPLIED:
  "For storing user session data, I'm choosing Redis over database sessions.
  Redis gives us sub-millisecond reads and is purpose-built for this use case,
  but the trade-off is that Redis is an in-memory store - if it goes down,
  users get logged out. We mitigate this with Redis Sentinel for HA and
  persist sessions to DB as backup.
  
  Given our requirement for <10ms latency for authentication checks,
  Redis is the right choice. If we needed fully durable sessions where
  losing them is unacceptable, we'd use a DB with a caching layer."

4. QUICK REFERENCE - TRADE-OFF CHEAT SHEET
--------------------------------------------------------------------------------

| DECISION              | OPTION A              | OPTION B              | CHOOSE A WHEN      |
|-----------------------|-----------------------|-----------------------|--------------------|
| Consistency/Avail.    | Strong Consistency    | High Availability     | Banking, inventory |
| Database type         | SQL (PostgreSQL)      | NoSQL (Cassandra)     | Complex joins, ACID|
| Communication         | Synchronous (REST)    | Async (Kafka)         | User-facing reads  |
| Fan-out               | Push (write time)     | Pull (read time)      | Normal scale users |
| Scaling               | Vertical              | Horizontal            | Low scale          |
| Service arch          | Monolith              | Microservices         | Small team/early   |
| Cache strategy        | Cache-aside           | Write-through         | Read-heavy data    |
| ID generation         | UUID                  | Snowflake             | Need sortable IDs  |
| Storage               | SQL DB                | Object Store (S3)     | Structured data    |
| Search                | DB LIKE queries       | Elasticsearch         | At scale >1M docs  |
