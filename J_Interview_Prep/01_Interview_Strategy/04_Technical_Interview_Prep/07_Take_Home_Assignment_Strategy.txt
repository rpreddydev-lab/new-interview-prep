================================================================================
TAKE-HOME ASSIGNMENT STRATEGY
================================================================================
Purpose: Take-home coding assignments are increasingly common, especially at
         startups, growth-stage companies, and senior roles. They are your
         chance to show production-quality work — not just algorithm knowledge.
         This guide covers how to approach, complete, and submit them to win offers.
================================================================================

--------------------------------------------------------------------------------
1. WHAT IS A TAKE-HOME ASSIGNMENT?
--------------------------------------------------------------------------------

A take-home is a coding project sent to you before an on-site interview.
You complete it on your own time (typically 3-7 days) and submit via GitHub or email.
It may then be reviewed live with the hiring team in a follow-up "code review" session.

TYPICAL FORMATS:
  - Build a small API or service (REST endpoints for a resource)
  - Implement a specific algorithm or data processing task
  - Build a small CLI tool or script
  - Extend an existing codebase (fork + add feature)
  - Debug and improve a broken codebase

WHAT COMPANIES ARE EVALUATING:
  1. Code quality: Is it clean, readable, and well-organized?
  2. Correctness: Does it actually work? Does it handle edge cases?
  3. Design decisions: Are they thoughtful and justified?
  4. Testing: Is there a test suite? Is it meaningful?
  5. Documentation: Can another engineer understand and run this?
  6. Communication: How do you justify trade-offs in the README?

--------------------------------------------------------------------------------
2. BEFORE YOU START
--------------------------------------------------------------------------------

READ THE INSTRUCTIONS TWICE:
  - Understand exactly what is being asked before writing a single line
  - Note: time limit, language/framework requirements or preferences
  - Note: what is in scope vs. explicitly out of scope
  - Note: how to submit (GitHub repo, zip, Google Drive, PR)

CLARIFY AMBIGUITIES BEFORE STARTING:
  - If you're confused about requirements, EMAIL the recruiter or hiring manager
  - Example: "The problem says to support pagination — should I implement cursor-based
    or offset-based? I'll default to cursor-based for scalability, but wanted to check."
  - This shows professional communication and reduces risk of building the wrong thing
  - Limit to 1-2 genuine questions; don't ask things you can reasonably decide

TIME PLANNING:
  - Don't use all the time given; submit 24 hours before deadline
  - Estimate: design (30 min) + implementation (4-6 hrs) + testing (1-2 hrs) + README (1 hr)
  - Total: 7-10 hours of focused work; spread over 2-3 days

RESIST OVER-ENGINEERING:
  - Do what's asked; do it well
  - Adding unused features can signal poor scope management
  - BUT: do signal what you WOULD add given more time in the README

--------------------------------------------------------------------------------
3. ARCHITECTURE AND DESIGN PHASE
--------------------------------------------------------------------------------

SPEND 30 MINUTES DESIGNING BEFORE CODING:
  - What are the entities/models?
  - What are the API endpoints or interfaces?
  - What does the data flow look like?
  - What trade-offs will you make and why?

MAKE DECISIONS DELIBERATELY:
  Bad: "I used MySQL because I know MySQL"
  Good: "I used PostgreSQL because the data is relational, ACID guarantees are needed
         for financial consistency, and it supports JSON columns for flexible metadata."

LAYER YOUR APPLICATION PROPERLY (for Java/Spring):
  Controller   → handles HTTP; validates input; calls service
  Service      → business logic; transaction boundary
  Repository   → data access; no business logic
  Model/Entity → data representation
  DTOs         → request/response objects (separate from entity)

KEEP IT SIMPLE BY DEFAULT:
  - Single module app is fine for most take-homes
  - Docker is a bonus, not required (unless specified)
  - Don't add Redis, Kafka, or microservices unless the problem requires it
  - Use a simple H2 in-memory DB unless persistence across restarts is required

--------------------------------------------------------------------------------
4. IMPLEMENTATION BEST PRACTICES
--------------------------------------------------------------------------------

CODE QUALITY CHECKLIST:
  [ ] Method names are verbs; class names are nouns; variables are descriptive
  [ ] No "magic numbers" — use named constants
  [ ] No duplicate code — extract shared logic to helper methods
  [ ] No god classes — single responsibility per class
  [ ] Proper package structure (com.company.project.controller, .service, etc.)
  [ ] Consistent style (spaces, braces, line length)

ERROR HANDLING:
  - Don't let exceptions propagate uncaught to the user as 500 errors
  - Return proper HTTP status codes:
    200 OK, 201 Created, 204 No Content
    400 Bad Request (validation error), 404 Not Found, 409 Conflict
    500 Internal Server Error (unhandled)
  - Return meaningful error messages in a consistent JSON format:
    {"error": "Book not found", "status": 404}

INPUT VALIDATION:
  - Never trust input; validate at the controller layer
  - Check: null fields, empty strings, negative numbers where not allowed,
    invalid enum values, malformed UUIDs
  - Use Java Bean Validation (@NotNull, @NotBlank, @Min, @Max) with @Valid

JAVA-SPECIFIC BEST PRACTICES:
  - Use final on variables that shouldn't change
  - Use Optional<T> instead of returning null
  - Use records or immutable DTOs for request/response objects
  - Prefer constructor injection over field @Autowired
  - Use interface types for fields (List<> over ArrayList<>)
  - Use var where type is obvious; avoid where it reduces clarity

AVOID COMMON PITFALLS:
  - Don't commit secrets (API keys, passwords) to git
    → Use application.properties or environment variables
  - Don't hardcode URLs, ports, or credentials in code
  - Don't ignore thread safety if the assignment involves concurrent operations
  - Don't use raw SQL strings when JPA/ORM is available
  - Don't return entity objects directly from REST endpoints (separation of concerns)

--------------------------------------------------------------------------------
5. TESTING STRATEGY
--------------------------------------------------------------------------------

WHAT TO TEST:
  1. Unit tests: service layer business logic (mock dependencies with Mockito)
  2. Integration tests: API endpoints end-to-end (Spring MockMvc or RestAssured)
  3. Edge case tests: null inputs, empty collections, boundary values

MINIMUM TEST COVERAGE FOR A TAKE-HOME:
  - At least 1 unit test per service method
  - At least 1 happy-path integration test per endpoint
  - At least 2 edge case / error tests

JAVA TESTING STACK:
  JUnit 5 (@Test, @BeforeEach, @AfterEach, @ParameterizedTest)
  Mockito (mock(), when(), verify(), ArgumentCaptor)
  Spring Boot Test (@SpringBootTest, @WebMvcTest, @DataJpaTest)
  MockMvc (perform(get("/api/books/1")).andExpect(status().isOk()))
  AssertJ (assertThat(result).isNotNull().hasSize(3))

EXAMPLE UNIT TEST STRUCTURE:
  @Test
  void getBook_whenBookExists_returnsBook() {
      // Arrange
      Book book = new Book(1L, "Clean Code", "Robert Martin");
      when(bookRepository.findById(1L)).thenReturn(Optional.of(book));
      // Act
      BookDto result = bookService.getBook(1L);
      // Assert
      assertThat(result).isNotNull();
      assertThat(result.title()).isEqualTo("Clean Code");
  }

  @Test
  void getBook_whenBookNotFound_throwsNotFoundException() {
      when(bookRepository.findById(99L)).thenReturn(Optional.empty());
      assertThatThrownBy(() -> bookService.getBook(99L))
          .isInstanceOf(BookNotFoundException.class);
  }

--------------------------------------------------------------------------------
6. THE README: YOUR MOST IMPORTANT ARTIFACT
--------------------------------------------------------------------------------

The README is read by every reviewer before looking at your code.
A strong README can win an interview; a weak one loses it.

REQUIRED SECTIONS:

1. OVERVIEW (2-3 sentences)
   What does this app do? What was the assignment?
   "A REST API for a book lending library, supporting CRUD operations on books
   and tracking loans per user."

2. TECH STACK AND REASONING
   "Java 17 + Spring Boot 3 + PostgreSQL (via Spring Data JPA). I chose PostgreSQL
   because the loan/book relationship is naturally relational, and ACID guarantees
   are important for tracking lending state correctly."

3. HOW TO RUN
   MUST INCLUDE exact commands:
     git clone <url>
     cd project
     ./mvnw spring-boot:run
     # API is now at http://localhost:8080
   Include: Java version required, any environment variables needed
   Bonus: Docker instructions if provided

4. API ENDPOINTS
   List all endpoints in a table:
   | Method | Path               | Description              | Auth Required |
   |--------|--------------------|--------------------------|---------------|
   | GET    | /api/books         | List all books           | No            |
   | POST   | /api/books         | Create a book            | Yes           |
   | GET    | /api/books/{id}    | Get book by ID           | No            |
   | PUT    | /api/books/{id}    | Update a book            | Yes           |
   | DELETE | /api/books/{id}    | Delete a book            | Yes           |

5. DESIGN DECISIONS AND TRADE-OFFS
   This is WHERE YOU STAND OUT.
   Examples:
   "I chose offset-based pagination for simplicity, but noted that cursor-based
   would be needed for large datasets to avoid performance degradation."
   "I stored timestamps in UTC and left timezone conversion to the client."
   "I used soft deletes (deleted_at column) to preserve audit trail."

6. WHAT I WOULD ADD WITH MORE TIME
   Shows you think beyond the scope given.
   Examples:
   - "Authentication with JWT (currently placeholder)"
   - "Rate limiting on the API with a token bucket algorithm"
   - "Metrics with Micrometer/Prometheus"
   - "Event-driven notifications via Kafka when a loan is overdue"
   - "More comprehensive integration tests with Testcontainers"

7. ASSUMPTIONS
   State what you assumed when requirements were ambiguous:
   "I assumed a book can only have one active loan at a time."
   "I assumed user IDs are provided by the client (auth system out of scope)."

--------------------------------------------------------------------------------
7. SUBMITTING YOUR ASSIGNMENT
--------------------------------------------------------------------------------

GITHUB REPO CHECKLIST:
  [ ] Repository is public (or link is shared with reviewers)
  [ ] .gitignore is present (excludes target/, .idea/, .env, *.class)
  [ ] No secrets committed (check git log)
  [ ] Commit history is clean and meaningful
      Bad: "fix", "asdf", "wip"
      Good: "Add book lending endpoint", "Add unit tests for BookService", "Fix NPE on missing userId"
  [ ] README.md is complete and clear
  [ ] Tests are present and pass: mvn test should succeed
  [ ] Application runs from scratch with documented commands

COMMIT HISTORY TIPS:
  - Make ~5-10 meaningful commits, not 1 giant commit
  - This demonstrates how you work incrementally
  - Structure: first commit (scaffold) → domain model → repository layer →
    service layer → controller layer → tests → README polish

SUBMISSION EMAIL TEMPLATE:
  "Hi [Name],
  I've completed the take-home assignment. Here is my submission:
  GitHub: [link]
  
  A few notes on my approach:
  - I used [tech stack] because [brief reason]
  - I focused on [X] and [Y]; given more time I would add [Z]
  - Instructions to run are in the README
  
  Looking forward to discussing the design choices. Please let me know if you
  have any issues accessing the repo.
  
  Thanks,
  [Your Name]"

--------------------------------------------------------------------------------
8. THE FOLLOW-UP CODE REVIEW SESSION
--------------------------------------------------------------------------------

Most companies that give take-homes follow up with a 30-60 min live code review.
This is NOT a new interview; it's a conversation about YOUR code.

WHAT TO EXPECT:
  - "Walk me through your approach"
  - "Why did you choose X over Y?"
  - "How would you extend this to handle [new requirement]?"
  - "What would you change if this were going to production?"
  - "How would this scale to 10M users?"
  - Live coding: "Add a new endpoint for [feature]" in your own code

HOW TO PREPARE:
  1. Re-read your own code 1 day before the review
  2. Know every design decision and be ready to justify it
  3. Have a clear answer for "what would you improve?"
  4. Be ready to extend your code live — your own codebase is familiar

POSTURE DURING CODE REVIEW:
  - Be open to feedback; don't get defensive
  - "That's a great point — I considered X but chose Y because..."
  - "I knew that was a trade-off; given more time I'd address it by..."
  - Showing awareness of limitations is a STRENGTH, not a weakness
