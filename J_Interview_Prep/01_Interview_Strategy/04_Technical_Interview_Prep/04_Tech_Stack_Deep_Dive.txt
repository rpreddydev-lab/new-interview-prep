TECH STACK DEEP DIVE: WHAT INTERVIEWERS ACTUALLY PROBE
================================================================================
Purpose: Understand the technologies that appear in system design and technical
         interviews. Know not just WHAT they are but WHY they exist, what
         trade-offs they make, and WHEN to use them.
================================================================================

--------------------------------------------------------------------------------
1. DATABASES
--------------------------------------------------------------------------------

RELATIONAL DATABASES (PostgreSQL, MySQL)
  WHAT: Structured, tabular data with SQL query language; ACID guarantees
  WHY USED: Strong consistency, complex joins, mature tooling, well-understood
  WHEN TO CHOOSE:
    - Need transactions (financial, e-commerce)
    - Schema is well-defined and changes infrequently
    - Complex queries with joins across multiple tables
    - Data fits on one server or needs read replicas (< 1 TB, < 100K QPS)

  SCALING PATTERNS:
    - Vertical scaling (bigger hardware) — simple but has limits
    - Read replicas — scale reads; primary handles all writes
    - Sharding (partitioning) — horizontal split; complex but necessary at high scale
    - Connection pooling (PgBouncer) — DB connections are expensive; pool them

  INTERVIEW SIGNALS:
    - "What happens when your MySQL primary goes down?" → Replica failover, RPO/RTO
    - "How would you shard a users table?" → shard by user_id range or hash
    - "What index types does PostgreSQL support?" → B-tree, Hash, GiST, GIN, BRIN

NOSQL: KEY-VALUE (Redis, DynamoDB)
  Redis:
    - In-memory; sub-millisecond latency
    - Use cases: caching, session storage, rate limiting, pub/sub, Lua scripting
    - Persistence options: RDB snapshots, AOF (append-only file), or both
    - Cluster mode: shards data across nodes; each node has primary + replica
    - Data types: String, List, Hash, Set, Sorted Set, HyperLogLog, Geo, Streams
    - KNOW: Redis is single-threaded for commands; networking is the bottleneck

  DynamoDB:
    - AWS-managed; virtually unlimited scale; single-digit ms latency
    - Key-value + document; no joins; denormalize data by access pattern
    - Tables are partitioned by partition key; range key optional
    - Global secondary indexes (GSI) for alternate access patterns
    - DynamoDB Streams for change data capture
    - On-demand vs. provisioned capacity modes

NOSQL: DOCUMENT (MongoDB, Firestore)
  MongoDB:
    - Stores JSON-like BSON documents; flexible schema
    - Good for: content management, catalogs, user profiles (varying attributes)
    - Replica sets for HA; sharding for horizontal scale
    - Aggregation Pipeline for complex analytics
    - Bad for: complex multi-document transactions (they exist in MongoDB 4+ but are costly)

NOSQL: WIDE-COLUMN (Cassandra, HBase)
  Cassandra:
    - Ring topology; peer-to-peer; no single point of failure
    - Tunable consistency: W + R > N = strong, or W + R <= N = eventual
    - Primary key = partition key (distribution) + clustering key (sort order within partition)
    - Excellent write throughput (SSTables; writes go to memtable then flush)
    - Bad for: ad hoc queries, JOINs, strong consistency requirements
    - Use cases: time-series data, IoT, messaging systems, activity feeds

NOSQL: GRAPH (Neo4j, Amazon Neptune)
  - Nodes and edges; efficient for traversals (friend-of-friend, recommendations)
  - Query language: Cypher (Neo4j)
  - Use when relationship traversal is the dominant access pattern
  - Overkill for most systems; only use when your data IS a graph

SEARCH ENGINE (Elasticsearch, Apache Solr)
  - Inverted index for full-text search; near real-time
  - Not a primary DB; use as secondary index updated via CDC (Change Data Capture)
  - Elasticsearch supports: full-text search, fuzzy matching, aggregations, geo-search
  - Shards + replicas for scale; heap size tuned to avoid GC pauses
  - KNOW: Elasticsearch is eventually consistent with the primary DB

TIME-SERIES (InfluxDB, TimescaleDB, Prometheus)
  - Optimized for append-heavy, time-ordered data (metrics, logs, IoT)
  - Efficient range queries over time windows
  - Data retention policies (auto-expire old data)
  - TimescaleDB = PostgreSQL extension; familiar SQL syntax

2. MESSAGING / STREAMING
--------------------------------------------------------------------------------

APACHE KAFKA
  ARCHITECTURE:
    - Distributed log: topics divided into partitions across brokers
    - Producers append to partitions; consumers read in order within a partition
    - Consumer groups: each partition is consumed by exactly 1 consumer per group
    - Offset: consumer tracks its position in a partition
    - Replication: each partition has a leader replica + N-1 follower replicas
    - ZooKeeper / KRaft: manages cluster metadata, leader election

  KEY PROPERTIES:
    - Messages are retained for a configurable duration (not deleted on consume)
    - High throughput: millions of events/sec per broker
    - Ordering guaranteed within a partition; not across partitions
    - At-least-once delivery by default; exactly-once possible (idempotent producers + transactions)

  USE CASES:
    - Event streaming / event sourcing
    - Data pipeline (ETL / ELT)
    - Log aggregation (replace N direct connections to analytics)
    - Change Data Capture (CDC) with Debezium

  INTERVIEW QUESTIONS:
    "How do you ensure ordering?" → Use a single partition or partition by a key
    "How do you scale Kafka consumers?" → Add partitions; add consumers to group
    "What's the difference between RabbitMQ and Kafka?" →
      Kafka: log-based (durable, replay); RabbitMQ: broker-based (queue model, delete-on-ack)

RABBITMQ / ACTIVEMQ (Traditional Message Brokers)
  - Classic queue model: messages deleted when acknowledged by consumer
  - Good for: task queues, work distribution, RPC patterns
  - Not ideal for: high-throughput event streaming (Kafka wins here)
  - Routing: direct, topic, fanout, headers exchanges

REDIS STREAMS
  - Lightweight Kafka alternative for simpler use cases
  - XADD, XREAD, XGROUP, XACK commands
  - Good for: small-scale event processing within a Redis-first stack

AWS SQS / SNS
  - SQS: Simple Queue Service; managed message queue; supports standard + FIFO queues
  - SNS: Simple Notification Service; pub/sub; fan-out to multiple SQS queues + email/SMS
  - SNS → SQS fan-out pattern: common in AWS architectures

3. CACHING
--------------------------------------------------------------------------------

REDIS (as cache)
  Strategies:
    Cache-Aside (Lazy Loading): App checks cache first; on miss, reads DB then writes cache
    Write-Through: Write to cache AND DB on every write; cache always consistent
    Write-Behind (Async): Write to cache; async flush to DB; risk of data loss
    Read-Through: Cache fetches from DB on miss automatically (library handles it)

  TTL: Always set an expiry (TTL) to prevent stale data and cache bloat
  Eviction: LRU (Least Recently Used) most common; also LFU, allkeys-random

CDN (CloudFront, Fastly, Cloudflare)
  - Cache static assets at edge nodes globally
  - Cache-Control headers control what CDN caches and for how long
  - Invalidation: explicit purge API or cache key versioning (?v=abc123)
  - Reduces latency for users far from origin
  - Absorbs massive traffic spikes (e.g., Black Friday, viral content)

APPLICATION-LEVEL CACHE
  - In-process cache (Guava Cache, Caffeine in Java)
  - Useful for: data that doesn't change often, JVM-local hot paths
  - Invalidation challenge: each instance has its own cache; can diverge

DATABASE QUERY CACHE
  - MySQL has a query cache (deprecated in 8.0; use app-level caching instead)
  - PostgreSQL relies on OS page cache; tune shared_buffers to match your hot data

4. LOAD BALANCERS AND PROXIES
--------------------------------------------------------------------------------

LAYER 4 vs. LAYER 7 LOAD BALANCING:
  L4 (TCP): Routes based on IP+port; fast; no content inspection
  L7 (HTTP): Routes based on URL, headers, cookies; can do SSL termination, health checks

ALGORITHMS:
  Round Robin: Distribute sequentially
  Least Connections: Route to server with fewest active connections
  IP Hash: Route same client IP to same server (sticky sessions — use with caution)
  Weighted Round Robin: Distribute proportionally based on server capacity

NGINX:
  - Web server, reverse proxy, L7 load balancer
  - Event-driven; handles 50K+ concurrent connections per instance
  - Config: upstream {} block + server {} block with proxy_pass

AWS ALB (Application Load Balancer):
  - L7; supports HTTP/2, WebSocket, path-based routing, host-based routing
  - Integrates with Auto Scaling groups, ECS, Lambda

AWS NLB (Network Load Balancer):
  - L4; handles millions of requests/sec at very low latency
  - Use for: TCP/UDP traffic, extreme throughput requirements

API GATEWAY:
  - Entry point for microservices; handles auth, rate limiting, routing, SSL
  - Kong, AWS API Gateway, Traefik, NGINX
  - Rate limiting: token bucket or leaky bucket algorithm per client

5. SERVICE DISCOVERY AND ORCHESTRATION
--------------------------------------------------------------------------------

SERVICE DISCOVERY:
  - In microservices, services must find each other dynamically
  - Server-side discovery: client asks load balancer; LB queries registry
  - Client-side discovery: client queries registry; client load-balances itself
  - Tools: Consul, Eureka (Netflix), AWS Cloud Map, Kubernetes DNS

KUBERNETES:
  - Container orchestration; schedules pods (containers) on nodes
  - Services: abstract pods behind a stable DNS name + virtual IP
  - Ingress: HTTP routing rules to internal services
  - ConfigMaps / Secrets: configuration and credentials injection
  - Horizontal Pod Autoscaler: scales pods based on CPU/memory metrics
  - Liveness probe + Readiness probe: health checking for rolling deploys

DOCKER:
  - Containerization: packages app + dependencies into portable image
  - Dockerfile: recipe for building an image
  - docker-compose: multi-container dev environment
  - Image layers: cached; only changed layers rebuild (optimizes CI/CD speed)

SERVICE MESH:
  - Cross-cutting concerns (mTLS, retries, circuit breakers) handled by sidecar proxy
  - Tools: Istio (popular), Linkerd
  - Sidecar (Envoy proxy) injected into every pod; app code has no networking logic

CIRCUIT BREAKER:
  - Pattern to prevent cascading failures: after N failures, open the circuit
  - Open state: calls fail-fast (no waiting for timeout)
  - Half-open state: let a few calls through to test recovery
  - Java: Resilience4j (modern), Hystrix (Netflix, now maintenance mode)

6. MONITORING, OBSERVABILITY, AND ALERTING
--------------------------------------------------------------------------------

THE THREE PILLARS OF OBSERVABILITY:
  1. Metrics: Numerical measurements over time (QPS, latency, error rate, CPU)
  2. Logs: Structured event records (JSON logs to ELK/CloudWatch/Splunk)
  3. Traces: End-to-end request path across services (Jaeger, Zipkin, AWS X-Ray)

METRICS STACK (common):
  Prometheus → collects metrics via scrape endpoints
  Grafana → visualizes Prometheus metrics as dashboards
  AlertManager → sends alerts (PagerDuty, Slack) when metrics breach thresholds

KEY METRICS TO MONITOR:
  - SLI (Service Level Indicator): what you measure (latency P99, error rate)
  - SLO (Service Level Objective): target (P99 < 200ms, error rate < 0.1%)
  - SLA (Service Level Agreement): contractual commitment to customers (legal)
  - Error budget: time/requests you can fail before violating SLO

LOGGING:
  - Structured JSON logs (not plain text) → machine-parseable
  - Fields: timestamp, level, service, traceId, userId, message, durationMs
  - Centralized log store: Elasticsearch + Kibana (ELK), Splunk, CloudWatch Logs
  - Log levels: ERROR, WARN, INFO, DEBUG (log at right level; don't log everything)

DISTRIBUTED TRACING:
  - Each request gets a unique traceId; each service adds spans
  - Visualize: which service added latency? Where did the error originate?
  - Instrumentation: OpenTelemetry (standard); backends: Jaeger, Zipkin

--------------------------------------------------------------------------------
7. CI/CD AND DEVOPS
--------------------------------------------------------------------------------

CI (Continuous Integration):
  - Every code push triggers: build → lint → unit tests → integration tests
  - Fast feedback loop; catch bugs before merge
  - Tools: GitHub Actions, Jenkins, CircleCI, GitLab CI

CD (Continuous Delivery / Deployment):
  - Delivery: push to staging automatically; production requires manual approval
  - Deployment: push to production automatically on passing tests
  - Feature flags: deploy code that is not yet live; toggle per user segment

DEPLOYMENT STRATEGIES:
  Blue/Green: Two identical environments; switch traffic at once; easy rollback
  Canary: Route X% of traffic to new version; monitor; gradually increase
  Rolling: Update pods one by one; some pods run old version during update
  A/B Testing: Route by user attributes; statistical comparison of outcomes

INFRASTRUCTURE AS CODE:
  - Terraform: declarative cloud resource provisioning (AWS, GCP, Azure)
  - AWS CloudFormation: AWS-native IaC
  - Ansible: configuration management (run on existing servers)
  - Helm: Kubernetes application packaging
