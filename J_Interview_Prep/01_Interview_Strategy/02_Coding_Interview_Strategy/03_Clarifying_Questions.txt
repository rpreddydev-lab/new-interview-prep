================================================================================
CLARIFYING QUESTIONS - WHAT TO ASK AND WHEN
================================================================================
Last Updated: April 2026
Purpose: Master the art of asking the right questions before coding.
         This separates junior from senior engineering mindset in interviews.
================================================================================

--------------------------------------------------------------------------------
1. WHY CLARIFYING QUESTIONS MATTER
--------------------------------------------------------------------------------

Asking good clarifying questions signals:
  - Senior engineering mindset (real engineers clarify before building)
  - Attention to requirements and edge cases
  - You won't waste time solving the wrong problem
  - You collaborate rather than work in isolation
  - You think about correctness before speed

Not asking clarifying questions signals:
  - Impulsive coding tendency
  - May miss requirements in real work
  - Less experienced in production software

THE HIRING BAR RULE:
  A senior engineer who asks no clarifying questions will be dinged.
  A junior engineer who asks thoughtful questions will be praised.
  Asking good questions is a SIGNAL, not a delay.

TIMING:
  - Ask clarifying questions BEFORE you write any code
  - Ask them AFTER reading the problem (not while reading)
  - 2-5 questions is usually ideal; 1 is too few, 10+ is too many
  - If a question is answered by re-reading the problem, don't ask it

--------------------------------------------------------------------------------
2. THE COMPLETE CLARIFYING QUESTION TAXONOMY
--------------------------------------------------------------------------------

GROUP 1: INPUT QUESTIONS
  These clarify what you're receiving:

  Q1.1 - Input Size/Scale:
  "What is the maximum size of the input? Is n up to 10^4 or 10^6?"
  WHY: Determines whether O(n²) is acceptable or if O(n log n)/O(n) is required.

  Q1.2 - Input Type:
  "Are the values in the array always integers, or could they be floats?"
  WHY: Affects how you do comparisons and what precision to worry about.

  Q1.3 - Input Range:
  "Can values be negative? What's the possible range?"
  WHY: Affects initialization values (using INT_MIN vs 0 for max), overflow risk.

  Q1.4 - Input Validity:
  "Can the input be null or empty? Should I handle that?"
  WHY: Determines whether you add null/empty checks at the start.

  Q1.5 - Sorted/Unsorted:
  "Is the input array guaranteed to be sorted?"
  WHY: A sorted array opens up binary search, two pointers, etc.

  Q1.6 - Uniqueness:
  "Can there be duplicate values? Duplicate keys?"
  WHY: Affects whether you can use a set vs a map, and how to handle ties.

GROUP 2: OUTPUT QUESTIONS
  These clarify what you're producing:

  Q2.1 - Output Format:
  "Should I return the length, or the actual subarray/substring?"
  WHY: Changes whether you track a count or a start/end index.

  Q2.2 - Multiple Valid Answers:
  "If there are multiple valid answers, should I return any one of them
   or a specific one (e.g., the lexicographically smallest)?"
  WHY: Affects tie-breaking logic in your algorithm.

  Q2.3 - No Valid Answer:
  "If no valid answer exists, should I return -1, empty array, null,
   or throw an exception?"
  WHY: Critical for edge case handling.

  Q2.4 - Return Type:
  "Should the output be an int, or could it require long due to overflow?"
  WHY: Sum/product of large arrays can overflow int in Java (2^31 ≈ 2.1 billion).

GROUP 3: CONSTRAINT QUESTIONS
  These define problem boundaries:

  Q3.1 - Modifying Input:
  "Can I modify the input array in place?"
  WHY: Some solutions are more elegant with in-place modification; some
       interviewers want you to preserve input (common in system-like questions).

  Q3.2 - Extra Space:
  "Is there a constraint on extra space used? Should I aim for O(1) space?"
  WHY: Some problems have O(1) space solutions that are considerably harder.

  Q3.3 - Time Complexity Target:
  "Is there a specific time complexity you're looking for?"
  WHY: Helps you know whether your approach is on the right track.

  Q3.4 - Character Set:
  "For string problems: is the input limited to lowercase English letters,
   or can it be any ASCII/Unicode character?"
  WHY: Affects whether you can use an int[26] array vs a HashMap.

  Q3.5 - Tree/Graph Specific:
  "For trees: is it a BST? Are values unique?"
  "For graphs: is it directed or undirected? Weighted? Can there be cycles?"
  WHY: BST property changes available algorithms. Graph properties define approach.

GROUP 4: PROBLEM UNDERSTANDING VERIFICATION
  These confirm your understanding:

  Q4.1 - Restate the Problem:
  "Let me make sure I understand: I have [input], I need to find/return
  [output], and the constraint is [constraint]. Is that right?"
  WHY: Catch misunderstanding before coding. Gets a confirmation nod.

  Q4.2 - Verify with Example:
  "With the example [1, 3, 2, 5], the answer would be 3 because...
  is that correct?"
  WHY: Tests your understanding against a concrete case.

  Q4.3 - Edge Case Verification:
  "If the input is [], the expected output is 0/null/error?"
  WHY: Explicitly confirms edge case handling expectation.

3. QUESTION TEMPLATES BY PROBLEM TYPE
--------------------------------------------------------------------------------

FOR ARRAY PROBLEMS:
  ✓ "Can input be empty or null?"
  ✓ "What's the value range? Can values be negative?"
  ✓ "Can there be duplicates?"
  ✓ "Is the array sorted?"
  ✓ "What's the max array size?"
  ✓ "Can I modify the array in-place?"

FOR STRING PROBLEMS:
  ✓ "What characters can the string contain? Lowercase? ASCII? Unicode?"
  ✓ "Is the string case-sensitive?"
  ✓ "Can the string be empty?"
  ✓ "Is length up to 10^4 or 10^5?"
  ✓ "Should the answer be case-insensitive?"

FOR TREE PROBLEMS:
  ✓ "Is this a BST or a general binary tree?"
  ✓ "Can the tree be empty (null root)?"
  ✓ "Can there be duplicate values in the tree?"
  ✓ "What is the max depth of the tree?"
  ✓ "Are values guaranteed to be unique?"

FOR GRAPH PROBLEMS:
  ✓ "Is this a directed or undirected graph?"
  ✓ "Can there be cycles?"
  ✓ "Can there be disconnected components?"
  ✓ "Are there edge weights? Are they always positive?"
  ✓ "Are the nodes numbered 0 to n-1 or 1 to n?"

FOR LINKED LIST PROBLEMS:
  ✓ "Can the list be empty?"
  ✓ "Can there be cycles in the list?"
  ✓ "Does the list have a tail pointer or is it singly linked?"
  ✓ "Can there be duplicate values?"

FOR DYNAMIC PROGRAMMING:
  ✓ "What's the maximum value of n?"
  ✓ "Are there any constraints on the values of individual elements?"
  ✓ "Can the result overflow a 32-bit int?"

FOR DESIGN PROBLEMS (HashMap, LRU Cache, etc.):
  ✓ "What operations need to be supported?"
  ✓ "What are the time complexity requirements per operation?"
  ✓ "Is there a size constraint (e.g., max capacity)?"
  ✓ "Do I need thread safety?"

4. HOW TO ASK QUESTIONS WELL
--------------------------------------------------------------------------------

BAD WAY:
  "What is the input?"
  "What do I return?"
  "Are there edge cases?"
  (Too vague; shows you haven't thought about the problem)

GOOD WAY:
  "Looking at the problem, I want to confirm: the input can have negative
   numbers? And the output should be the subarray sum itself, not just its
   length? Also, with empty input, I'd return 0?"
  (Specific, demonstrates you've processed the problem, efficient)

RULES FOR ASKING:
  1. Think first, then ask. Identify what you actually need to know.
  2. Group multiple questions into one natural conversation.
  3. Frame questions as confirmations ("Can I assume X?") when you can.
  4. Don't ask questions whose answers are in the problem statement.
  5. Don't ask for the solution: "What algorithm should I use?" - too direct.

WHAT INTERVIEWERS LOVE TO HEAR:
  "I'm going to ask a few clarifying questions before I start coding..."
  (Shows you have a process)

  "I want to make sure I handle this correctly - can the input be empty?"
  (Shows attention to robustness)

  "Is performance critical here, or is correctness the priority right now?"
  (Shows engineering judgment)

WHAT TO DO WHEN INTERVIEWER SAYS "MAKE YOUR OWN ASSUMPTIONS":
  This is an invitation to show engineering judgment.
  State your assumptions clearly:
  "I'll assume the input is valid (not null), values can be negative,
   and n won't exceed 10^5. I'll also assume we need to return -1 if
   no valid answer exists. Let me proceed with those assumptions."
  
  This shows you can self-scope. This is a SENIOR SIGNAL.

--------------------------------------------------------------------------------
5. QUESTIONS NOT TO ASK (COMMON MISTAKES)
--------------------------------------------------------------------------------

DON'T ASK:
  ✗ "What data structure should I use?" - This is your job to decide.
  ✗ "What algorithm should I use?" - Same.
  ✗ "Is this a dynamic programming problem?" - Figure it out yourself.
  ✗ "What's the time complexity you're looking for?" - Ask only after
    you've stated your approach; asking first looks like you're shortcutting.
  ✗ "Does this make sense to you?" (asked before you've said anything)
  ✗ Questions answered explicitly in the problem statement.
  ✗ "Is my solution good?" - This is a question, not a clarification.

DON'T:
  - Ask the same question twice
  - Forget to incorporate the answers you receive
  - Ask questions AND start coding simultaneously
  - Ask questions to DELAY coding (this is transparent and annoying)

--------------------------------------------------------------------------------
6. WHEN TO ASK DURING CODING (NOT JUST AT START)
--------------------------------------------------------------------------------

Mid-coding clarifications ARE okay, for:

  - An unexpected edge case you encounter while coding:
    "As I'm implementing this, I realized: if k > n, should I return
     n or -1? I'll handle it as returning n (the full array sum) unless
     you tell me otherwise."

  - Ambiguous specification becomes relevant:
    "Now that I'm at this point, if there are two valid answers of equal
     length, which should I prefer? I'll return the first one found."

  - Discovering an assumption was wrong:
    "Wait, actually this doesn't work if values can be negative - I assumed
     non-negative earlier. Let me revisit."

HOW TO ASK MID-CODING:
  Don't stop cold. Say it naturally:
  "As I write this, I want to confirm one thing: [question]. For now
   I'll proceed with [assumption] and we can adjust if needed."
  
  This keeps momentum while surfacing important issues.

7. PRACTICE DRILL - CLARIFYING QUESTIONS EXERCISE
--------------------------------------------------------------------------------

EXERCISE: For each of these problem statements, write down the clarifying
questions you would ask. Then compare with the checklist above.

Problem 1: "Find the longest substring without repeating characters."
  Your questions:
  [ ] ______________________
  [ ] ______________________
  [ ] ______________________
  Good questions: Is it case-sensitive? Only lowercase? What's the max length?
  What to return if input is empty? Return the length or the substring itself?

Problem 2: "Given a binary tree, find the maximum path sum."
  Your questions:
  [ ] ______________________
  [ ] ______________________
  Good questions: Can node values be negative? Is it a BST or general tree?
  Does the path have to go through the root? Can it be a single node path?

Problem 3: "Design a data structure that supports push, pop, top, and
            retrieving the minimum element, all in O(1) time."
  Your questions:
  [ ] ______________________
  [ ] ______________________
  Good questions: Should pop() and top() throw exception on empty or return null?
  Is this single-threaded (no concurrency needed)? Are values integers?

--------------------------------------------------------------------------------
8. THE "CONFIDENT ASSUMPTION" TECHNIQUE
--------------------------------------------------------------------------------

Sometimes you can make an educated assumption instead of asking:

SITUATION: You're not sure if the input can be null.

OPTION A (asking):
  "Can the input be null?"
  
OPTION B (confident assumption, more senior signal):
  "I'll add a null check at the start as a defensive coding practice.
  In a production system, I'd typically validate inputs at the service
  boundary. Is that approach okay with you?"

WHEN TO USE OPTION B:
  - When the assumption is industry-standard practice
  - When asking might seem like a basic oversight question
  - When you have enough context to make a reasonable assumption
  - When you want to show defensive coding habits

This technique shows engineering maturity: you address edge cases proactively
rather than waiting to be told about them.
