================================================================
  SOFTWARE ARCHITECTURE PRINCIPLES — OVERVIEW
================================================================

  Architecture principles guide decisions at the system and module
  level — above individual classes, below full system design patterns.

  They answer: "How should components relate to each other?"
               "What makes a module good or bad?"
               "How do we structure the system to survive change?"

================================================================
THE PRINCIPLES AT A GLANCE
================================================================

  Principle                        One-Line Summary
  -------------------------------  ------------------------------------------
  Separation of Concerns (SoC)     Each piece addresses one distinct concern
  High Cohesion / Low Coupling     Parts inside a module stick together;
                                   modules depend minimally on each other
  Law of Demeter (LoD)             Only talk to your immediate neighbors
  Principle of Least Astonishment  Code should behave as developers expect
  Convention over Configuration    Sensible defaults; only configure exceptions
  Package Cohesion Principles      Package by feature/change, not by type
  Package Coupling Principles      Depend in one direction; minimize cycles

================================================================
WHY ARCHITECTURE PRINCIPLES MATTER
================================================================

  1. Changeability: Systems with good architecture are cheaper to change.
  2. Testability: Low-coupling systems are easy to unit-test in isolation.
  3. Understandability: High cohesion means related code is co-located.
  4. Reusability: Focused, cohesive modules can be reused without dragging
     unrelated dependencies.

================================================================
HOW THESE RELATE TO SOLID
================================================================

  SOLID is class-level.
  Architecture principles extend to module/package/service level.

  SRP  → Separation of Concerns (same idea, broader scope)
  ISP  → Package Cohesion (don't force clients to depend on unneeded)
  DIP  → Package Coupling (depend on abstractions, not concrete modules)

================================================================
INTERVIEW FREQUENCY
================================================================

  High:      Separation of Concerns, Cohesion/Coupling, Law of Demeter
  Medium:    Package Principles (Robert Martin's REP/CCP/CRP/ADP/SDP/SAP)
  Context:   Convention over Configuration (Spring, Rails questions)
  Principle: Least Astonishment (API design and usability discussions)
