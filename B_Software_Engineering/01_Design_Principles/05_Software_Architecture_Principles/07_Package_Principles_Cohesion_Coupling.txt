================================================================
  PACKAGE PRINCIPLES — COHESION AND COUPLING
================================================================

  Defined by Robert C. Martin in "Agile Software Development:
  Principles, Patterns, and Practices."

  Six principles governing how to organize classes into packages
  (analogous to SOLID for classes, but applied at the package level).

  Split into two groups:
  - Package Cohesion Principles (3): what belongs in a package
  - Package Coupling Principles (3): how packages depend on each other

================================================================
PACKAGE COHESION PRINCIPLES
================================================================

  1. REP — REUSE/RELEASE EQUIVALENCY PRINCIPLE
     "The granule of reuse is the granule of release."
     Classes in a package should be releasable together.
     They form a cohesive group that makes sense to version together.

     Violation: putting unrelated utilities in one package.
     Fix: if class A and class B aren't released/versioned together,
          they don't belong in the same package.

  2. CCP — COMMON CLOSURE PRINCIPLE
     "Classes that change together are packaged together.
      Classes that change for different reasons are separated."
     Package-level SRP.

     If a new feature requires touching 5 classes in 5 different packages,
     your packaging is wrong — those 5 classes should be together.

     Package by feature (not by type) follows CCP:
     - GOOD: com.example.orders (Order, OrderService, OrderRepo, OrderController)
     - BAD: com.example.controllers + com.example.services + com.example.repositories
            (a feature change touches all three packages)

  3. CRP — COMMON REUSE PRINCIPLE
     "Classes that are reused together belong together."
     "Don't force users of a package to depend on things they don't use."
     Package-level ISP.

     If you import one class from a package, you shouldn't have to
     deal with the transitive dependencies of unrelated classes in that package.

================================================================
PACKAGE BY TYPE vs PACKAGE BY FEATURE
================================================================

  PACKAGE BY TYPE (violates CCP, CRP):
  com.example.controllers
    OrderController, UserController, ProductController
  com.example.services
    OrderService, UserService, ProductService
  com.example.repositories
    OrderRepository, UserRepository, ProductRepository

  Problems:
  - Adding an "Order" feature touches 3+ packages
  - Difficult to see what an "order" is without reading 3 packages
  - Teams can't own a feature without owning pieces of many packages

  ---

  PACKAGE BY FEATURE (follows CCP):
  com.example.order
    Order, OrderController, OrderService, OrderRepository
  com.example.user
    User, UserController, UserService, UserRepository
  com.example.product
    Product, ProductController, ProductService, ProductRepository

  Benefits:
  - Adding an "Order" feature = touch only com.example.order
  - Teams can own a whole feature
  - Encapsulation: order internals hidden from other features

================================================================
PACKAGE COUPLING PRINCIPLES
================================================================

  4. ADP — ACYCLIC DEPENDENCIES PRINCIPLE
     "Allow no cycles in the package dependency graph."

     If package A depends on B which depends on C which depends back on A
     → you have a cycle.

     A <--> B is especially dangerous: you can't release one without the other.

     Detect cycles: tools like JDepend, SonarQube, IntelliJ "Dependency Analysis."
     Break cycles by: extracting a third package C that both A and B depend on,
                      or inverting a dependency (DIP).

  5. SDP — STABLE DEPENDENCIES PRINCIPLE
     "Depend in the direction of stability."
     A package should only depend on packages that are MORE stable than itself.

     Stability: a stable package is one that many others depend on (Ca is high),
                and that depends on few others (Ce is low).

     Instability I = Ce / (Ca + Ce)
     I = 0 → maximally stable (everyone depends on it, it depends on nothing)
     I = 1 → maximally unstable (depends on everything, nothing depends on it)

     If a volatile (unstable) package is depended upon by a stable one →
     change in the volatile breaks the stable. Violation.

     Fix: Stable packages should be abstract (interfaces, base classes).

  6. SAP — STABLE ABSTRACTIONS PRINCIPLE
     "A package should be as abstract as it is stable."

     Stable packages (many depend on them) should contain mostly
     abstract classes and interfaces — so they can be extended without
     changing.

     Pairs with SDP: Stable → Abstract. Unstable → Concrete.

     Main Sequence: A + I ≈ 1
     - Zone of Pain: Stable + Concrete (I=0, A=0) → rigid, hard to extend
     - Zone of Uselessness: Unstable + Abstract (I=1, A=1) → no one uses it

================================================================
PRACTICAL SPRING PROJECT STRUCTURE
================================================================

  Well-organized Spring project following CCP + SDP:

  src/main/java/com/example/
  |
  +-- shared/                          STABLE, HIGH ABSTRACTION
  |     Money.java (value object)
  |     Result.java (generic result)
  |
  +-- order/                           FEATURE PACKAGE (CCP)
  |     Order.java
  |     OrderRepository.java (interface)
  |     OrderService.java
  |     OrderController.java
  |     OrderDto.java
  |     impl/
  |       JpaOrderRepository.java      ← concrete, unstable, depends on JPA
  |
  +-- customer/                        FEATURE PACKAGE (CCP)
  |     Customer.java
  |     CustomerRepository.java
  |     CustomerService.java
  |     ...
  |
  +-- config/                          CONFIGURATION (stable, changes rarely)
        SecurityConfig.java
        DataSourceConfig.java

  Dependency direction: config → order/customer → shared
  No cycles. Concrete impls depend on abstractions (SDP/SAP).

================================================================
INTERVIEW Q&A
================================================================

  Q: What are the package cohesion principles?
  A: REP (release together), CCP (change together), CRP (reuse together).
     Together they define what classes belong in the same package.

  Q: What is the Common Closure Principle?
  A: Classes that change for the same reason should be in the same package.
     Package-level SRP. "Package by feature" follows this; "package by type" violates it.

  Q: What is the Acyclic Dependencies Principle?
  A: No cycles in the package dependency graph. Cycles make it impossible to
     release one package without the others. Break cycles with a shared
     extracted package or by inverting a dependency.

  Q: What is the Stable Dependencies Principle?
  A: Depend in the direction of stability. Unstable (frequently changing)
     packages should depend on stable ones, not vice versa. Prevents
     volatile code from forcing changes in stable code.

  Q: Should you always package by feature?
  A: In most business applications, yes. Package by feature follows CCP,
     allows team ownership, and makes the codebase navigate more naturally.
     Package by type is only appropriate for small projects or technical
     frameworks where technical type IS the organizing principle.
