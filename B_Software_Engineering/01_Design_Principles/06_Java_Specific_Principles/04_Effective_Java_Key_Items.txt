================================================================
  EFFECTIVE JAVA — KEY ITEMS (Joshua Bloch)
================================================================

  "Effective Java" by Joshua Bloch is the canonical Java best-practices
  reference. Third edition (2018) covers Java 9.
  Every senior Java developer is expected to know these items.

================================================================
CHAPTER 1: CREATING AND DESTROYING OBJECTS
================================================================

  ITEM 1: CONSIDER STATIC FACTORY METHODS INSTEAD OF CONSTRUCTORS

  Benefits:
  - Have meaningful names: BigInteger.probablePrime() vs new BigInteger(...)
  - Not required to create a new object: Boolean.valueOf(true) returns cached
  - Can return a subtype: Collections.unmodifiableList() returns internal type
  - Can vary returned type by parameter: EnumSet.of() returns RegularEnumSet or JumboEnumSet

  Naming conventions:
  of(...)          aggregate / factory  → Set.of(a, b, c)
  from(...)        type conversion       → Date.from(instant)
  valueOf(...)     value-type factory    → Integer.valueOf(42)
  getInstance(...) singleton variant    → Calendar.getInstance()
  create(...)      same as newInstance  → general factory

  ---

  ITEM 2: CONSIDER A BUILDER WHEN FACED WITH MANY CONSTRUCTOR PARAMETERS

  (Covered in depth in 04_Design_Patterns/01_Creational_Patterns/04_Builder.txt)
  Use when: 4+ optional parameters; telescoping constructors become unreadable.
  Java 14+ records reduce the need for builders for simple value objects.

  ---

  ITEM 3: ENFORCE SINGLETON WITH A PRIVATE CONSTRUCTOR OR AN ENUM TYPE

  Enum singleton is the most reliable approach (serialization-safe, reflection-safe):
  public enum AppConfig {
      INSTANCE;
      private final String apiUrl = System.getenv("API_URL");
      public String getApiUrl() { return apiUrl; }
  }

  ---

  ITEM 4: ENFORCE NON-INSTANTIABILITY WITH A PRIVATE CONSTRUCTOR

  For utility classes (e.g., java.util.Arrays):
  public final class StringUtils {
      private StringUtils() { throw new AssertionError("No instances"); }
      public static String capitalize(String s) { ... }
  }

  ---

  ITEM 7: ELIMINATE OBSOLETE OBJECT REFERENCES

  Manual memory management trap in Java:
  class Stack {
      private Object[] elements;
      private int size;

      public Object pop() {
          if (size == 0) throw new EmptyStackException();
          return elements[--size];   // BUG: reference kept — memory leak
      }

      public Object popFixed() {
          Object result = elements[--size];
          elements[size] = null;    // FIXED: null out the reference
          return result;
      }
  }

  WeakReference for caches. WeakHashMap for mappings where key lifecycle
  determines value lifecycle.

CHAPTER 4: CLASSES AND INTERFACES
================================================================

  ITEM 15: MINIMIZE ACCESSIBILITY OF CLASSES AND MEMBERS

  Make everything as private as possible.
  Prefer: private → package-private → protected → public
  Once public, it's part of your API forever.

  ITEM 16: IN PUBLIC CLASSES, USE ACCESSOR METHODS NOT PUBLIC FIELDS

  public class Point { public double x; public double y; }  ← BAD (can't add validation later)
  public class Point { private double x; public double getX() { return x; } }  ← GOOD

  Except for record types and package-private classes.

  ITEM 17: MINIMIZE MUTABILITY

  (Covered in 02_Favor_Immutability.txt)
  Make every field final unless it must be mutable.

  ITEM 18: FAVOR COMPOSITION OVER INHERITANCE

  (Covered in 05_Design_Principles/02_Other_OOP_Principles/04_Composition_over_Inheritance.txt)
  Inheritance violates encapsulation. Composition is safer.

  ITEM 19: DESIGN AND DOCUMENT FOR INHERITANCE OR ELSE PROHIBIT IT

  If a class is not designed for inheritance, declare it final.
  Document which methods are safe to override.
  @Override ensures compile-time check.

CHAPTER 5: GENERICS
================================================================

  ITEM 26: DON'T USE RAW TYPES

  List list = new ArrayList();    ← raw type, no type safety
  List<String> list = new ArrayList<>();  ← typed, safe

  Raw types are for backward compatibility only. Never use in new code.

  ITEM 28: PREFER LISTS TO ARRAYS

  Arrays are covariant: String[] is a subtype of Object[].
  Generics are invariant: List<String> is NOT a subtype of List<Object>.
  Arrays are reified (type checked at runtime).
  Generics are erased (type erased at runtime).
  Mixing arrays and generics is a bad idea.

  ITEM 31: PECS — PRODUCER EXTENDS, CONSUMER SUPER

  Use <? extends T> when the collection PRODUCES values (you only read):
  void process(List<? extends Shape> shapes) { shapes.forEach(s -> s.draw()); }

  Use <? super T> when the collection CONSUMES values (you only add):
  void addShapes(List<? super Circle> list) { list.add(new Circle()); }

CHAPTER 7: LAMBDAS AND STREAMS
================================================================

  ITEM 42: PREFER LAMBDAS TO ANONYMOUS CLASSES

  Anonymous class:
  Comparator<String> c = new Comparator<String>() {
      public int compare(String a, String b) { return a.length() - b.length(); }
  };

  Lambda:
  Comparator<String> c = (a, b) -> a.length() - b.length();
  // Better: Comparator.comparingInt(String::length)

  ITEM 43: PREFER METHOD REFERENCES TO LAMBDAS

  Lambda:      elements.forEach(e -> System.out.println(e));
  Method ref:  elements.forEach(System.out::println);

  Method reference types:
  Static:      Integer::parseInt
  Instance (bound):    str::toUpperCase     (str is a specific instance)
  Instance (unbound):  String::toUpperCase  (instance provided by stream)
  Constructor: ArrayList::new

  ITEM 44: FAVOR USE OF STANDARD FUNCTIONAL INTERFACES

  Don't define custom @FunctionalInterface if a standard one fits:
  Predicate<T>    : T → boolean
  Function<T,R>   : T → R
  Consumer<T>     : T → void
  Supplier<T>     : () → T
  UnaryOperator<T>: T → T
  BinaryOperator<T>: (T, T) → T

  ITEM 45: USE STREAMS JUDICIOUSLY

  Streams are great for: filter/map/reduce operations, bulk data processing.
  Not ideal for: stateful operations, modification of external state,
                 code needing checked exceptions (streams don't propagate them well).

CHAPTER 9: GENERAL PROGRAMMING
================================================================

  ITEM 57: MINIMIZE SCOPE OF LOCAL VARIABLES

  Declare variables where first used, not at top of method.
  Use for-each instead of index loops when possible.

  ITEM 61: PREFER PRIMITIVE TYPES TO BOXED PRIMITIVES

  Integer vs int:
  Integer a = null;  // can be null — NPE risk
  int a = 0;         // can't be null — safe

  Auto-unboxing null → NullPointerException.
  Boxed comparisons: (a == b) compares references, not values.
  Use primitives for performance-critical code.

  ITEM 63: BEWARE THE PERFORMANCE OF STRING CONCATENATION

  String result = "";
  for (Item item : items) result += item.toString();  // O(n²) — new String each iteration

  StringBuilder sb = new StringBuilder();
  for (Item item : items) sb.append(item.toString());  // O(n)
  String result = sb.toString();

  Or: String.join, Collectors.joining in streams.

CHAPTER 10: EXCEPTIONS
================================================================

  ITEM 69: USE EXCEPTIONS ONLY FOR EXCEPTIONAL CONDITIONS

  Never use exceptions for normal flow control.
  Don't catch exceptions to detect iteration end — use hasNext().

  ITEM 70: USE CHECKED EXCEPTIONS FOR RECOVERABLE CONDITIONS
           AND RUNTIME EXCEPTIONS FOR PROGRAMMING ERRORS

  (Covered in 06_Prefer_Checked_vs_Unchecked_Exceptions.txt)

  ITEM 76: STRIVE FOR FAILURE ATOMICITY

  A failed method call should leave the object in the state it was in
  before the call. Validate parameters before mutating state.

================================================================
CHAPTER 11: CONCURRENCY
================================================================

  ITEM 78: SYNCHRONIZE ACCESS TO SHARED MUTABLE DATA

  volatile guarantees visibility, not atomicity.
  AtomicInteger, AtomicReference for lock-free atomic ops.
  synchronized for compound check-then-act operations.

  ITEM 81: PREFER CONCURRENCY UTILITIES TO WAIT AND NOTIFY

  Use: CountDownLatch, CyclicBarrier, Semaphore, BlockingQueue,
       ConcurrentHashMap, CompletableFuture.
  Avoid: low-level wait/notify unless implementing a concurrency primitive.

INTERVIEW Q&A
================================================================

  Q: What is the static factory method pattern (Effective Java Item 1)?
  A: Use static methods with meaningful names instead of constructors.
     Advantages: named (BigInteger.probablePrime), cached instances
     (Boolean.valueOf), can return subtypes, can vary return type.

  Q: When should you use a builder (Item 2)?
  A: When a class has 4+ optional constructor parameters.
     Avoids telescoping constructors. Makes construction readable.

  Q: What is PECS?
  A: Producer Extends, Consumer Super. Use <? extends T> when reading
     from a collection; <? super T> when adding to it.

  Q: Why prefer method references over lambdas (Item 43)?
  A: More concise, clearly states intent. Four types: static, bound
     instance, unbound instance, constructor reference.

  Q: What is the failure atomicity principle?
  A: Failed operations should leave objects in their pre-call state.
     Validate all parameters before performing any mutations.
