================================================================
  WHAT ARE DESIGN PRINCIPLES?
================================================================

  Design principles are general guidelines that guide how software
  should be structured. They are NOT patterns (concrete solutions)
  and NOT algorithms (step-by-step procedures). They are heuristics —
  rules of thumb that lead to better software over time.

  A principle answers: "Is this design good?"
  A pattern answers:   "How do I solve this specific problem?"

----------------------------------------------------------------
WHY DESIGN PRINCIPLES MATTER IN INTERVIEWS
----------------------------------------------------------------

  Interviewers assess whether you:
    - Write code that can change without cascading breakage
    - Understand WHY code rots (rigidity, fragility, opacity)
    - Make design decisions consciously rather than by accident

  Code rot symptoms:
    Rigidity:     change one thing → must change many things
    Fragility:    change one thing → breaks unrelated things
    Immobility:   cannot reuse code without dragging in dependencies
    Viscosity:    easier to hack than to do the right thing
    Complexity:   unnecessary abstractions, redundant structures

----------------------------------------------------------------
CATEGORIES OF DESIGN PRINCIPLES
----------------------------------------------------------------

  1. SOLID Principles (Robert C. Martin)
     - Single Responsibility (SRP)
     - Open/Closed (OCP)
     - Liskov Substitution (LSP)
     - Interface Segregation (ISP)
     - Dependency Inversion (DIP)

  2. Other OOP Principles
     - DRY: Don't Repeat Yourself
     - KISS: Keep It Simple, Stupid
     - YAGNI: You Aren't Gonna Need It
     - Composition over Inheritance
     - Encapsulate What Varies
     - Program to Interfaces, Not Implementations
     - Law of Demeter (LoD) / Principle of Least Knowledge
     - Tell Don't Ask
     - Fail Fast

  3. Clean Code Principles (Robert C. Martin)
     - Meaningful names
     - Small functions with single purpose
     - No side effects in functions
     - Error handling via exceptions, not error codes
     - Comments explain WHY, not WHAT
     - Boy Scout Rule: leave code cleaner than you found it

  4. Software Architecture Principles
     - Separation of Concerns (SoC)
     - High Cohesion, Low Coupling
     - Hollywood Principle (Don't Call Us, We'll Call You)
     - Convention over Configuration
     - Principle of Least Astonishment

  5. Java-Specific Principles
     - Favor immutability
     - Defensive copying
     - Minimize scope of variables
     - Prefer checked exceptions for recoverable conditions
     - Use generics for type safety

----------------------------------------------------------------
THE RELATIONSHIP BETWEEN PRINCIPLES
----------------------------------------------------------------

  SOLID is the foundation — each principle attacks one failure mode:

  SRP  -- class does too much → split by responsibility
  OCP  -- new feature forces class modification → extend, don't modify
  LSP  -- subclass breaks contract → maintain substitutability
  ISP  -- fat interface forces unused methods → split interfaces
  DIP  -- high-level code depends on details → depend on abstractions

  DRY and KISS are complementary:
    DRY prevents knowledge duplication (change in one place propagates).
    KISS prevents over-engineering (often violates YAGNI simultaneously).

  YAGNI keeps KISS honest:
    "We'll need this later" is the most common rationalization for over-design.

  LoD and Tell-Don't-Ask enforce encapsulation:
    Object should not expose internal structure to callers.

----------------------------------------------------------------
HOW TO DISCUSS PRINCIPLES IN INTERVIEWS
----------------------------------------------------------------

  Framework for answering any principle question:
    1. State the principle in one sentence
    2. Explain what problem it solves
    3. Give a Java code example of violation
    4. Show the fixed version
    5. Name real-world consequences of ignoring it

  Example answer structure for SRP:
    "SRP says a class should have one reason to change. If a class
    both handles HTTP request parsing AND sends emails, a change to
    email format forces touching HTTP-parsing code. Fix: split into
    RequestParser and EmailSender. Real consequence: merge conflicts,
    unexpected test failures when only one concern changed."

----------------------------------------------------------------
QUICK REFERENCE: PRINCIPLE → PROBLEM SOLVED
----------------------------------------------------------------

  Principle           Problem Solved
  ------------------  -----------------------------------------------
  SRP                 God classes with too many responsibilities
  OCP                 Modification triggers cascading changes
  LSP                 Subclass surprises caller of supertype
  ISP                 Empty method implementations / forced coupling
  DIP                 Hard-coded dependencies, untestable code
  DRY                 Copy-paste bugs, multiple places to update
  KISS                Clever code nobody can maintain
  YAGNI               Unused abstractions cluttering the codebase
  Composition>Inherit Inheritance hierarchy explosion, fragile base
  LoD                 Train wrecks: a.getB().getC().doThing()
  Tell Don't Ask      Anemic domain model, logic outside data
  Fail Fast           Cryptic errors far from the actual bug site
  High Cohesion       Scattered logic, hard to find related code
  Low Coupling        Ripple effects from change, hard to test
