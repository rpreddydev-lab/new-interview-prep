================================================================
  SINGLE RESPONSIBILITY PRINCIPLE (SRP)
================================================================

  Definition: A class should have ONE, and only one, reason to change.

  Uncle Bob's phrasing: "A module should be responsible to one,
  and only one, actor." (actor = group of people/system that
  drives a reason to change)

----------------------------------------------------------------
THE CORE IDEA
----------------------------------------------------------------

  A "responsibility" = a reason to change.

  If a class changes for multiple reasons:
    - Changes for reason A may break functionality for reason B
    - Merges become difficult (team A and team B both touch the file)
    - Tests are harder (must cover all responsibility combinations)
    - Reuse is impossible (can't take one responsibility without the other)

  SRP ≠ "a class should do only one thing".
  SRP = "a class should be changed by only one actor/concern".

  A UserService that creates users, sends welcome emails, and writes
  audit logs has THREE reasons to change:
    - Business rules about users change (actor: business team)
    - Email template changes (actor: marketing team)
    - Audit format changes (actor: compliance team)

----------------------------------------------------------------
VIOLATION EXAMPLE
----------------------------------------------------------------

  // BAD — three responsibilities in one class
  public class UserService {
      public void createUser(User user) {
          // Responsibility 1: business rules
          if (user.getEmail() == null) throw new InvalidUserException();
          userRepository.save(user);

          // Responsibility 2: email notification
          String subject = "Welcome to the platform!";
          emailSender.send(user.getEmail(), subject);

          // Responsibility 3: audit logging
          auditLog.write("USER_CREATED", user.getId(), LocalDateTime.now());
      }
  }

  Problems:
    - If email template changes → touch UserService (core business logic file)
    - If audit format changes → touch UserService again
    - To test business logic: need email + audit infrastructure
    - Cannot reuse user creation logic without email side effect

----------------------------------------------------------------
FIXED: SEPARATE BY RESPONSIBILITY
----------------------------------------------------------------

  // Responsibility 1: user creation business rules only
  @Service
  @RequiredArgsConstructor
  public class UserService {
      private final UserRepository userRepository;
      private final ApplicationEventPublisher eventPublisher;

      public User createUser(CreateUserCommand command) {
          User user = User.from(command);
          userRepository.save(user);
          eventPublisher.publishEvent(new UserCreatedEvent(user));
          return user;
      }
  }

  // Responsibility 2: email notification (reacts to event)
  @Component
  @RequiredArgsConstructor
  public class UserWelcomeEmailListener {
      private final EmailService emailService;

      @EventListener
      public void onUserCreated(UserCreatedEvent event) {
          emailService.sendWelcome(event.getUser().getEmail());
      }
  }

  // Responsibility 3: audit logging
  @Component
  public class UserAuditListener {
      @EventListener
      public void onUserCreated(UserCreatedEvent event) {
          auditLog.record("USER_CREATED", event.getUser().getId());
      }
  }

  Now:
    - Marketing changes email → only UserWelcomeEmailListener changes
    - Compliance changes audit → only UserAuditListener changes
    - UserService unit test: no email or audit infrastructure needed
    - Email listener and audit listener independently reusable

----------------------------------------------------------------
SRP IN PRACTICE — HOW FAR TO SPLIT?
----------------------------------------------------------------

  Common over-application mistake: one class per method = too much.
  SRP is about ACTOR not method count.

  Test: "If requirement X changes, how many classes change?"
    One class   → good granularity
    Two classes → possible violation (but may be intentional coupling)

  Natural split boundaries:
    Service classes:     business logic (core)
    Repository classes:  data access
    Mapper/Converter:    data transformation
    Validator classes:   validation rules
    Event listeners:     side effects (email, audit, cache)
    Factory classes:     object creation
    Controller classes:  HTTP handling / request mapping

  Spring project naturally enforces SRP via layers:
    @Controller  → HTTP layer
    @Service     → business logic
    @Repository  → data access
    @Component   → utility / infrastructure

----------------------------------------------------------------
SRP AT METHOD LEVEL
----------------------------------------------------------------

  SRP applies to methods too. A method should do one thing.

  // BAD: method does parsing + validation + saving + notification
  public void processOrder(String json) {
      Order order = parseJson(json);
      if (!order.isValid()) throw new InvalidOrderException();
      orderRepository.save(order);
      emailService.sendConfirmation(order);
  }

  // BETTER: orchestration method delegates to focused methods
  public void processOrder(String json) {
      Order order = parse(json);
      validate(order);
      save(order);
      notify(order);
  }

  Each extracted method is independently testable and reusable.

----------------------------------------------------------------
REAL-WORLD EXAMPLES IN JAVA STDLIB / SPRING
----------------------------------------------------------------

  - java.io.FileReader: ONLY opens files for reading (reading, not parsing)
  - java.io.BufferedReader: ONLY adds buffering to a Reader
  - Jackson ObjectMapper: serialization/deserialization (one concern)
  - Spring @Controller: ONLY HTTP mapping, delegates to @Service
  - Spring @Repository: ONLY data access, wraps exceptions
  - Spring Converter<S,T>: ONLY one conversion direction

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is SRP? Give an example of violation.
  A: SRP says a class should have one reason to change. A UserService
     that handles creation, sends emails, and writes audit logs violates
     SRP because three different teams (dev, marketing, compliance) would
     cause changes to the same file. Fix: separate concerns, use events.

  Q: How is SRP different from "do one thing"?
  A: "Do one thing" is too vague. A UserService does "one thing" (manage users)
     but may have many responsibilities. SRP is about actors: who causes this code
     to change? If multiple different stakeholders drive changes, split it.

  Q: Can SRP lead to too many tiny classes?
  A: Yes — over-applying SRP creates abstraction bloat. Balance: split when
     there are clearly different change drivers. Don't split just because
     a class has multiple methods. The test is: do different stakeholders
     require different changes to the same class?

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Always frame SRP in terms of "reason to change" not "size of class."
  - Show before/after code — violation then fix.
  - Mention event-driven approach as a clean SRP solution in Spring.
  - Connect to testing: single responsibility = single setup in unit tests.
