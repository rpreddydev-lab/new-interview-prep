================================================================
  BRIDGE PATTERN
================================================================

  Category:   Structural
  Intent:     Decouple an abstraction from its implementation so that
              the two can vary independently.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  Moderate in interviews. Often confused with Adapter.
              Commonly asked: "How would you design a shape+color system?"

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Class explosion with inheritance. When two dimensions of variation
  exist (shape TYPE and PLATFORM, or shape TYPE and COLOR), inheritance
  creates an explosion of subclasses.

  Without Bridge — Inheritance hierarchy explosion:
    Shape
      Circle
        RedCircle
        BlueCircle
      Square
        RedSquare
        BlueSquare
    Adding new color → add 2 new classes.
    Adding new shape → add N×color classes.
    M shapes × N colors = M×N subclasses. EXPLOSION.

  With Bridge — Two separate hierarchies composed:
    Shape (abstraction) --> holds reference to --> Color (implementation)
      Circle                                         Red
      Square                                         Blue
    M shapes + N colors = M+N classes. ✅

  Any shape can work with any color independently.

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Abstraction      -- Defines high-level control interface.
                      Holds a reference to an Implementor.
  RefinedAbstraction -- Extends Abstraction; adds more behavior.
  Implementor      -- Interface for implementation classes.
                      Defines low-level primitive operations.
  ConcreteImplementor -- Implements Implementor.

  Bridge = Abstraction HAS-A Implementor (composition, not inheritance).

----------------------------------------------------------------
FULL JAVA EXAMPLE — SHAPES AND RENDERING
----------------------------------------------------------------

  // Implementor interface
  public interface DrawingAPI {
      void drawCircle(double x, double y, double radius);
      void drawSquare(double x, double y, double side);
  }

  // Concrete Implementors
  public class SVGDrawingAPI implements DrawingAPI {
      public void drawCircle(double x, double y, double radius) {
          System.out.printf("SVG: <circle cx='%.1f' cy='%.1f' r='%.1f'/>%n", x, y, radius);
      }
      public void drawSquare(double x, double y, double side) {
          System.out.printf("SVG: <rect x='%.1f' y='%.1f' width='%.1f' height='%.1f'/>%n", x, y, side, side);
      }
  }

  public class RasterDrawingAPI implements DrawingAPI {
      public void drawCircle(double x, double y, double radius) {
          System.out.printf("Raster: Circle at (%.1f,%.1f) r=%.1f%n", x, y, radius);
      }
      public void drawSquare(double x, double y, double side) {
          System.out.printf("Raster: Square at (%.1f,%.1f) side=%.1f%n", x, y, side);
      }
  }

  // Abstraction
  public abstract class Shape {
      protected DrawingAPI drawingAPI;      // BRIDGE to implementation

      protected Shape(DrawingAPI drawingAPI) {
          this.drawingAPI = drawingAPI;
      }

      public abstract void draw();
      public abstract void resize(double factor);
  }

  // Refined Abstractions
  public class Circle extends Shape {
      private double x, y, radius;

      public Circle(double x, double y, double radius, DrawingAPI api) {
          super(api);
          this.x = x; this.y = y; this.radius = radius;
      }

      @Override
      public void draw() {
          drawingAPI.drawCircle(x, y, radius);
      }

      @Override
      public void resize(double factor) { radius *= factor; }
  }

  public class Square extends Shape {
      private double x, y, side;

      public Square(double x, double y, double side, DrawingAPI api) {
          super(api);
          this.x = x; this.y = y; this.side = side;
      }

      @Override
      public void draw() {
          drawingAPI.drawSquare(x, y, side);
      }

      @Override
      public void resize(double factor) { side *= factor; }
  }

  // Client
  public class Main {
      public static void main(String[] args) {
          DrawingAPI svg    = new SVGDrawingAPI();
          DrawingAPI raster = new RasterDrawingAPI();

          Shape c1 = new Circle(1, 2, 3, svg);
          Shape c2 = new Circle(4, 5, 6, raster);
          Shape s1 = new Square(0, 0, 5, svg);

          c1.draw();   // SVG: <circle cx='1.0' cy='2.0' r='3.0'/>
          c2.draw();   // Raster: Circle at (4.0,5.0) r=6.0
          s1.draw();   // SVG: <rect x='0.0' y='0.0' width='5.0' height='5.0'/>

          // Switch implementation at runtime!
          c1 = new Circle(1, 2, 3, raster);
          c1.draw();   // Raster: Circle at (1.0,2.0) r=3.0
      }
  }

----------------------------------------------------------------
WHEN TO USE BRIDGE
----------------------------------------------------------------

  1. Two dimensions of variation: (type × platform), (shape × color), (report × format).
  2. Want to avoid permanent binding between abstraction and implementation.
  3. Both abstraction and implementation should be extensible via subclassing.
  4. Changes in implementation should not impact client code.
  5. Want to SHARE implementation between multiple abstractions.

----------------------------------------------------------------
BRIDGE IN JAVA STANDARD LIBRARY
----------------------------------------------------------------

  JDBC:
    - java.sql.Driver is the Implementor (abstract).
    - DriverManager is the Abstraction.
    - MySQLDriver, OracleDriver, H2Driver are Concrete Implementors.
    - Your code talks to java.sql.Connection (abstraction) — DB vendor handles it.

    Connection conn = DriverManager.getConnection(url);
    // Your code doesn't know or care if it's MySQL, PostgreSQL, or H2.

  AWT/Swing Peer Architecture:
    - Component (abstraction) bridges to ComponentPeer (OS-specific implementation).
    - Button on Windows uses WindowsButtonPeer; on Mac uses MacButtonPeer.

----------------------------------------------------------------
BRIDGE vs ADAPTER
----------------------------------------------------------------

  Bridge:
    - DESIGNED upfront to allow independent variation.
    - Both sides can be extended independently.
    - Solves the class-explosion problem proactively.

  Adapter:
    - Applied AFTER THE FACT to make incompatible things work.
    - Fixes existing incompatibility.
    - One side (Adaptee) is fixed; Adapter translates.

  Key: Bridge = designed for flexibility. Adapter = fixing existing incompatibility.

----------------------------------------------------------------
BRIDGE vs STRATEGY
----------------------------------------------------------------

  Bridge (Structural):
    - Separates ABSTRACTION from IMPLEMENTATION.
    - The implementor defines HOW the abstraction operates at a low level.
    - Both hierarchies evolve independently.

  Strategy (Behavioral):
    - Defines interchangeable ALGORITHMS.
    - Client knows it's selecting an algorithm.
    - Focuses on varying behavior, not structure.

  They look similar (both use composition to delegate), but:
    Bridge separates two-level hierarchies.
    Strategy just plugs in different algorithms.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Time: O(1) per operation — just delegates to implementor.
  Space: O(1) — one reference to implementor.
  Class count: M abstractions + N implementations (vs M×N without bridge).

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Bridge pattern?
  A: It decouples abstraction from implementation so both can vary independently.
     Instead of using inheritance to combine two dimensions (e.g., shape type and
     rendering API), Bridge uses composition: the abstraction holds a reference
     to the implementor, reducing M×N class combinations to M+N.

  Q: What is the "class explosion" problem and how does Bridge solve it?
  A: If you have M shapes and N rendering methods, inheritance creates M×N
     subclasses (CircleOnSVG, CircleOnRaster, SquareOnSVG...). Bridge separates
     the two hierarchies — M shapes + N renderers — and uses composition to combine
     them. You get M+N classes instead of M×N.

  Q: How is Bridge different from Adapter?
  A: Bridge is designed upfront for independent variation. Adapter is a retrofit
     solution to make existing incompatible interfaces work together.

  Q: Give a real Java example of Bridge.
  A: JDBC is the prime example. java.sql.Connection is the abstraction.
     The JDBC Driver (MySQL, PostgreSQL, H2) is the implementation.
     Your code talks to Connection — the underlying database is swappable.

  Q: Can the implementation be changed at runtime with Bridge?
  A: Yes — since implementation is held by composition (not hardcoded inheritance),
     you can swap the implementor at runtime if the setter is exposed.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - JDBC is the canonical real-world Bridge example — know it well.
  - When asked "how would you design shapes with multiple rendering APIs?" → Bridge.
  - Contrast with Adapter clearly: Bridge = designed-in. Adapter = retrofit.
  - The diagram: Abstraction → [HAS-A] → Implementor.
  - Don't confuse Bridge with Decorator — Bridge has two separate hierarchies;
    Decorator wraps the SAME hierarchy.
