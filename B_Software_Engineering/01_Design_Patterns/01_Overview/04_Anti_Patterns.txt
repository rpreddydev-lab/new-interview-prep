================================================================
  ANTI-PATTERNS
================================================================

  An anti-pattern is a common response to a recurring problem that appears
  effective but is counterproductive in practice. They are named bad
  practices — recognizing them is as important as knowing good patterns.

  Origin: Term coined by Andrew Koenig (1995), popularized by "AntiPatterns"
  book by Brown, Malveau, McCormick, Mowbray (1998).

----------------------------------------------------------------
WHY ANTI-PATTERNS MATTER IN INTERVIEWS
----------------------------------------------------------------

  - Shows you know WHAT NOT TO DO — as important as what to do.
  - Demonstrates code quality awareness and engineering maturity.
  - Senior roles especially expect recognition of anti-patterns in legacy code.
  - Common in code review, refactoring, and design review discussions.

----------------------------------------------------------------
CORE ANTI-PATTERNS IN OOP / JAVA
----------------------------------------------------------------

  1. GOD CLASS (also: "Blob")
     -------------------------
     What: One class knows too much and does too much. Hundreds of methods,
           thousands of lines. Violates Single Responsibility Principle (SRP).
     Smell: UserManager with 50+ methods; one class controlling everything.
     Fix: Decompose into smaller, focused classes. Apply SRP.
     Example: A class handling user auth, order processing, report generation, email sending.

  2. SINGLETON OVERUSE
     ------------------
     What: Making every shared service a Singleton. Introduces global state,
           tight coupling, and breaks testability (can't mock/replace).
     Smell: Singletons for Configuration, Logger, Database, and every utility.
     Fix: Dependency injection. Singletons should be rare; Spring manages this for you.
     When acceptable: Logger (stateless), configuration manager (truly global + read-only).

  3. SPAGHETTI CODE
     ---------------
     What: Code with tangled control flow — massive if/else chains, deeply
           nested loops, goto-style logic, no clear structure.
     Smell: Methods with 200+ lines, nesting level > 4, no helper methods.
     Fix: Extract methods, early returns, apply Strategy/State patterns for conditional logic.

  4. GOLDEN HAMMER
     --------------
     What: Applying the same tool/pattern/technology to every problem because
           you know it well. "If all you have is a hammer, everything is a nail."
     Smell: Using microservices for a 3-page app; applying Hibernate to a CSV parser.
     Fix: Match tool to problem. Evaluate requirements before choosing tech.

  5. COPY-PASTE PROGRAMMING (Lava Flow)
     ------------------------------------
     What: Code duplicated across the codebase instead of shared via abstraction.
           Modified in one place but forgotten in others. Also known as WET code
           (Write Everything Twice).
     Smell: Same 30-line block in 5 different classes.
     Fix: Extract to a shared method, utility class, or apply Template Method.

  6. MAGIC NUMBERS / STRINGS
     -------------------------
     What: Hardcoded literals scattered through code with no explanation.
     Smell: `if (code == 42)`, `status = "ACTIVE"` in 15 different places.
     Fix: Named constants (`static final int MAX_RETRIES = 3`), enums, config values.

  7. PREMATURE OPTIMIZATION
     -----------------------
     What: Optimizing code before profiling identifies actual bottlenecks.
           "The root of all evil." (Knuth)
     Smell: Complex caching, bit tricks, and micro-optimizations in business logic.
     Fix: Write clean, correct code first. Profile before optimizing.
           Use BigO analysis to identify algorithmic improvements first.

  8. DEAD CODE
     ----------
     What: Code that is never executed — commented-out blocks, unreachable
           branches, unused methods and classes.
     Smell: `// Old implementation kept just in case`, methods never called.
     Fix: Delete it. Version control (Git) keeps history — dead code adds noise.

  9. FEATURE ENVY
     -------------
     What: A method that uses data from another class more than its own.
           Suggests the method belongs in the other class.
     Smell: `order.customer.address.city` accessed repeatedly in OrderService.
     Fix: Move the method. Apply "Tell, Don't Ask."

  10. INAPPROPRIATE INTIMACY
      -----------------------
      What: Two classes that are too tightly coupled — accessing each other's
            private/internal details directly.
      Smell: Class A accesses internal fields of Class B via getters proliferation.
      Fix: Encapsulate and expose behavior, not data. Consider Mediator pattern.

  11. REFUSED BEQUEST
      ----------------
      What: Subclass inherits methods from parent but doesn't use or throws
            UnsupportedOperationException for most of them.
      Smell: `class Square extends Rectangle` overrides setWidth to also set height.
      Fix: Favor composition over inheritance. Use interfaces for behavior contracts.

  12. POLTERGEIST (Ghost Class)
      --------------------------
      What: Classes with no real responsibility — exist just to pass data between
            other classes or wrap a single method.
      Smell: `DataTransferHelper`, `ManagerFactory` doing nothing meaningful.
      Fix: Inline the logic into the appropriate class. Remove the middleman.

  13. BOAT ANCHOR
      ------------
      What: Keeping unused parts of the system "in case they're needed later."
      Smell: Full module for a feature that was cancelled.
      Fix: YAGNI — remove unused code. Restore from Git if needed later.

  14. HARD CODING
      ------------
      What: Embedding environment-specific values (URLs, credentials, ports) directly
            in code instead of configuration.
      Smell: `String url = "jdbc:mysql://prod-db:3306/mydb"` in source code.
      Fix: Use environment variables, application.properties, Spring @Value, secrets manager.

----------------------------------------------------------------
ARCHITECTURAL ANTI-PATTERNS
----------------------------------------------------------------

  1. BIG BALL OF MUD
     ----------------
     What: A haphazardly structured, sprawling system with no discernible architecture.
           Everything depends on everything else. Most common legacy codebase shape.
     Why: Deadlines, no design up front, incremental patching.
     Fix: Strangler Fig Pattern — incrementally replace subsystems with clean modules.

  2. DISTRIBUTED MONOLITH
     ---------------------
     What: Microservices that are still tightly coupled — must be deployed together,
           share the same database, and fail together. Worst of both worlds.
     Smell: 8 "services" all connecting to the same DB schema.
     Fix: Enforce bounded contexts. Each service owns its data. Use async events.

  3. NANOSERVICES
     -------------
     What: Decomposing into too many tiny services with high coordination overhead.
           Network calls for trivial operations. Opposite failure mode from Big Ball of Mud.
     Smell: `UserNameService`, `UserEmailService` as separate deployments.
     Fix: Aggregate into bounded context services. Balance cohesion vs separation.

  4. SHARED DATABASE ANTI-PATTERN
     ------------------------------
     What: Multiple services (or teams) sharing a single database schema.
     Problem: Schema changes break all consumers; no service autonomy; coupling at data level.
     Fix: Each service owns its schema. Use API contracts and events for data sharing.

  5. INFINITE CALLBACK HELL (Callback Pyramid of Doom)
     ---------------------------------------------------
     What: Deeply nested async callbacks leading to unreadable code.
     Language: Common in JavaScript/Node.js; also Java pre-CompletableFuture.
     Fix: Use Promises, async/await, CompletableFuture chain, or reactive streams.

----------------------------------------------------------------
DATABASE ANTI-PATTERNS
----------------------------------------------------------------

  1. N+1 QUERY PROBLEM
     ------------------
     What: Fetching list of N items, then executing N separate queries for related data.
     Example: Load 100 orders, then for each order separately load the customer.
     Fix: Use JOIN queries, eager loading (`@ManyToOne(fetch = EAGER)` carefully),
          or batch fetching (`@BatchSize`, JOIN FETCH in JPQL).

  2. IMPLICIT COLUMNS
     -----------------
     What: `SELECT * FROM users` — selecting all columns when only 2 are needed.
     Problem: Over-fetches data; breaks when columns are added/reordered.
     Fix: Always name columns explicitly in SQL.

  3. ENTITY-ATTRIBUTE-VALUE (EAV) OVERUSE
     ----------------------------------------
     What: Storing arbitrary key-value pairs instead of using proper schema.
     Example: `(entity_id=42, attr_name="email", attr_value="foo@bar.com")`.
     Problem: Loses type safety, indexing, and constraints. Joins become nightmares.
     Fix: Design proper schema. Use JSONB columns for truly dynamic attributes in Postgres.

----------------------------------------------------------------
ANTI-PATTERNS vs DESIGN PATTERNS — CONTRAST
----------------------------------------------------------------

  Design Pattern              Anti-Pattern Counterpart
  --------------------------  ----------------------------------
  Strategy (swap algorithms)  Golden Hammer (use one approach everywhere)
  Facade (simplify API)       Big Ball of Mud (no structure at all)
  Observer (loose coupling)   Inappropriate Intimacy (tight coupling)
  Composite (tree structure)  Poltergeist (pointless intermediary classes)
  Builder (clear construction) Telescoping Constructor (anti-pattern Builder solves)
  Factory (decouple creation) Hard Coding (tight to specific instantiation)
  Single Responsibility       God Class

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What's the difference between a design pattern and an anti-pattern?
  A: A design pattern is a proven good solution. An anti-pattern looks like
     a good solution but causes problems in practice. Both are named — the
     name of an anti-pattern is a shorthand for "this common mistake."

  Q: Is Singleton an anti-pattern?
  A: It can be. Singleton is a GoF pattern, but OVERUSE of Singleton is an
     anti-pattern. It creates global state, breaks testability, and hides
     dependencies. In modern Java/Spring, prefer dependency injection over
     manual Singletons.

  Q: What is the N+1 problem and how do you fix it?
  A: N+1 occurs when you load a collection of N items and then run a separate
     query for each item's related data. Fix: use JOIN FETCH in JPQL, eager
     loading judiciously, or Hibernate's @BatchSize annotation.

  Q: What's the God Class anti-pattern?
  A: A class that does too much — violates Single Responsibility Principle.
     Refactor by splitting into focused classes, each with one clear reason to change.

  Q: What anti-pattern does the Builder pattern fix?
  A: The "Telescoping Constructor" anti-pattern — where a class has many constructors
     with different combinations of optional parameters, making instantiation unreadable.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - When asked "What would you improve in this code?" — look for these anti-patterns.
  - Know the N+1 problem cold — it comes up in nearly every backend interview.
  - Be able to say: "This looks like a God Class — I'd decompose it using SRP."
  - Don't just name the anti-pattern; always pair it with the fix.
  - "I once refactored a Singleton abuse into Spring-managed DI — made it fully testable."
