================================================================
  BOY SCOUT RULE — CLEAN CODE
================================================================

  "Always leave the campground cleaner than you found it."
  — Boy Scouts of America

  Applied to code by Robert C. Martin (Uncle Bob):
  "Leave the code cleaner than you found it."

  Meaning: Every time you touch a file, make it slightly better
  even if the improvement is unrelated to your current task.

================================================================
WHY IT MATTERS
================================================================

  Code naturally decays over time without attention (entropy).
  The Boy Scout Rule fights entropy incrementally — no big
  "refactoring sprint" needed.

  Without it:
  - Every fix piles on more mess
  - Technical debt compounds
  - Eventually code becomes unmaintainable
  - "We need to rewrite everything" crisis

  With it:
  - Each commit leaves codebase slightly better
  - Technical debt is repaid continuously
  - No massive refactoring projects needed
  - Code quality trends upward over time

================================================================
PRACTICAL EXAMPLES
================================================================

  WHAT "SLIGHTLY BETTER" LOOKS LIKE:

  1. Rename a confusing variable you just read past
     Before: int d = 5;
     After:  int daysSinceModified = 5;

  2. Extract a method with a good name from a long method
     Before: 50-line processOrder()
     After:  processOrder() + validateOrder() + calculateTotal()

  3. Remove a dead code block you noticed
     Before: // old logic kept "just in case"
     After:  deleted (git has it if needed)

  4. Add a missing null check
     Before: String name = user.getName().trim();
     After:  String name = user == null ? "" : user.getName().trim();

  5. Replace a magic number with a constant
     Before: if (retries > 3) throw ...
     After:  if (retries > MAX_RETRIES) throw ...

  6. Simplify a nested conditional
     Before: three-level if nesting
     After:  guard clauses

  7. Delete a useless comment
     Before: // increments i
              i++;
     After:  i++;

================================================================
SCOPE AND LIMITS
================================================================

  BOY SCOUT RULE = SMALL IMPROVEMENTS ONLY.

  Do NOT:
  - Refactor the entire class while fixing a bug
  - Rename everything in a file on a feature branch
  - Restructure architecture mid-sprint

  The improvements should:
  - Take a few minutes at most
  - Not require their own test suite
  - Not change observable behavior (pure refactoring)
  - Be in the same vicinity as your current change

  "Clean the campfire ring you used. Don't relandscape the whole park."

================================================================
TECHNICAL DEBT AND THE BOY SCOUT RULE
================================================================

  Technical debt categories:
  ------------------------------------------------------------------
  Type              | Description                  | BSR Can Fix?
  ------------------------------------------------------------------
  Reckless Debt     | "No time for design"         | Partially
  Prudent Debt      | Deliberate shortcut, noted   | Partially
  Accidental Debt   | Wrong decision at the time   | YES — small steps
  Gradual Decay     | Code written well, aged       | YES — constant BSR
  ------------------------------------------------------------------

  The Boy Scout Rule is most powerful against Gradual Decay.
  Each touch improves a small area — over months, the whole
  codebase trends cleaner.

================================================================
BOY SCOUT RULE IN TEAM SETTINGS
================================================================

  Individual discipline: Every developer applies BSR on every touch.

  Code Review: Reviewers should celebrate small unrelated improvements
  (rename, extract) unless they affect scope/risk.

  PR hygiene tip: Separate "refactoring" commits from "feature" commits
  in the same PR so they're easy to review independently.

  Team norm: "Leave it better" is a shared value, not individual heroism.
  Document it in your team's contributing guide.

================================================================
BOY SCOUT RULE vs YAGNI vs REFACTORING SPRINTS
================================================================

  Boy Scout Rule:
  - Incremental, opportunistic, happens constantly
  - Scope: tiny improvements near touched code
  - Cost: minutes
  - Risk: minimal

  YAGNI:
  - Preventive: don't add what isn't needed now
  - Complementary: BSR cleans up past YAGNI violations

  Refactoring Sprint:
  - Planned, deliberate, large scope
  - Should be rarely needed if BSR is practiced consistently
  - Use when a whole subsystem is unsalvageable incrementally

================================================================
RELATIONSHIP TO OTHER PRINCIPLES
================================================================

  Clean Code + BSR:
  Clean code gives you the "what to improve" — BSR gives you the "when."

  Technical Debt Metaphor:
  BSR = paying minimum interest continuously vs letting debt balloon
  until bankruptcy (rewrite).

  SRP + BSR:
  If you're in a method that violates SRP, extract one concern now.
  Don't do both — just better than before.

  Broken Windows Theory (from software):
  One messy area signals "this is okay here" — others follow.
  BSR prevents the first broken window; or fixes it before others appear.

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the Boy Scout Rule in software?
  A: Leave the code cleaner than you found it. Every time you modify
     a file, make one small improvement — rename, extract, delete dead code.
     Over time this fights entropy and prevents technical debt buildup.

  Q: How does the Boy Scout Rule relate to technical debt?
  A: It's a continuous debt-repayment strategy. Instead of letting
     debt compound until you need a big refactoring project, you pay
     it in small installments every time you touch the code.

  Q: How do you balance Boy Scout Rule with delivery speed?
  A: Keep improvements tiny — minutes, not hours. Rename a variable,
     extract a method. If the improvement would take more than 5 minutes
     and isn't related to your current task, create a tech debt ticket
     instead of doing it now.

  Q: Can the Boy Scout Rule make code reviews harder?
  A: Only if unrelated changes mix with feature changes. Best practice:
     separate commits or separate PRs for refactoring vs features.

  Q: What's the difference between Boy Scout Rule and a refactoring sprint?
  A: BSR = incremental, constant, low-risk, opportunistic.
     Refactoring sprint = planned, large scope, high risk. If BSR is
     practiced consistently, you rarely need refactoring sprints.

================================================================
SUMMARY
================================================================

  Boy Scout Rule in one sentence:
  "Make the code slightly better every single time you touch it."

  Power: Cumulative. 100 tiny improvements = enormous quality gain.
  Cost: Near zero per touch.
  Risk: Minimal (pure refactoring, backed by tests).

  Combined with: Clean Code principles (what to improve),
                 Refactoring techniques (how to improve safely),
                 TDD (tests ensure behavior unchanged).
