================================================================
  REFACTORING TECHNIQUES — CLEAN CODE
================================================================

  Refactoring: changing internal structure of code WITHOUT changing
  observable behavior. Goal: improve readability, reduce complexity,
  make future change easier.

  "Leave the code cleaner than you found it." — Boy Scout Rule
  "First make it work, then make it right." — Kent Beck

================================================================
CORE PRINCIPLES OF REFACTORING
================================================================

  1. Small, safe steps — one transformation at a time
  2. Always backed by tests (tests prove behavior unchanged)
  3. Commit before refactoring (safety net + clean diff)
  4. Refactor separately from feature addition

================================================================
METHOD-LEVEL REFACTORINGS
================================================================

  EXTRACT METHOD
  --------------
  Take a fragment of code and put it in a new method with a name
  that explains its purpose.

  BEFORE:
  void printReceipt(Order order) {
      System.out.println("Order: " + order.getId());
      double total = 0;
      for (Item i : order.getItems()) total += i.getPrice();
      if (order.isMember()) total *= 0.9;
      System.out.println("Total: " + total);
  }

  AFTER:
  void printReceipt(Order order) {
      printHeader(order);
      System.out.println("Total: " + calculateTotal(order));
  }

  private void printHeader(Order order) {
      System.out.println("Order: " + order.getId());
  }

  private double calculateTotal(Order order) {
      double subtotal = order.getItems().stream()
          .mapToDouble(Item::getPrice).sum();
      return order.isMember() ? subtotal * 0.9 : subtotal;
  }

  ---

  INLINE METHOD
  -------------
  When a method body is as clear as the method name, remove the
  indirection.

  BEFORE:
  boolean isSpecial(int n) { return n > 10; }
  if (isSpecial(count)) ...

  AFTER:
  if (count > 10) ...

  ---

  RENAME METHOD / VARIABLE / CLASS
  ---------------------------------
  The most important refactoring. If you have to think about what
  something does, rename it.

  int d = 5;          → int daysSinceLastLogin = 5;
  void proc()         → void handleUserRegistration()
  class Data          → class CustomerProfile

================================================================
PARAMETER REFACTORINGS
================================================================

  INTRODUCE PARAMETER OBJECT
  ---------------------------
  Replace a group of parameters that always travel together with
  a single object.

  BEFORE:
  double calculate(int year, int month, int day, int hours, int minutes) {}

  AFTER:
  record TimePoint(int year, int month, int day, int hours, int minutes) {}
  double calculate(TimePoint time) {}

  ---

  REMOVE FLAG ARGUMENT (BOOLEAN PARAM)
  ------
  BEFORE:
  void render(boolean premium) {}   // caller: render(true) — what does true mean?

  AFTER:
  void renderPremium() {}
  void renderStandard() {}

================================================================
CLASS-LEVEL REFACTORINGS
================================================================

  EXTRACT CLASS
  -------------
  When one class does the work of two, create a new class and move
  the relevant fields and methods.

  BEFORE:
  class User {
      String name; String email;
      String street; String city; String zip;   // address group
      double lat; double lon;                   // coordinate group
  }

  AFTER:
  class User { String name; String email; Address address; }
  record Address(String street, String city, String zip, Coordinate location) {}
  record Coordinate(double lat, double lon) {}

  ---

  INLINE CLASS
  ------------
  When a class does too little (Lazy Class smell), fold it into another.

  ---

  MOVE METHOD / MOVE FIELD
  -------------------------
  When a method/field is used more by another class than its own.
  Fix Feature Envy: move the envying method to the class it envies.

  BEFORE: (in OrderService)
  double applyMemberDiscount(Customer customer, double price) {
      return customer.getMembership().getDiscountRate() * price;
  }

  AFTER: (in Customer)
  double applyDiscount(double price) {
      return membership.getDiscountRate() * price;
  }

================================================================
CONDITIONAL REFACTORINGS
================================================================

  REPLACE CONDITIONAL WITH POLYMORPHISM
  --------------------------------------
  Replace type-code switches with polymorphic objects.

  BEFORE:
  double area(Shape s) {
      if (s.type == CIRCLE) return Math.PI * s.radius * s.radius;
      if (s.type == RECTANGLE) return s.width * s.height;
      throw new IllegalArgumentException();
  }

  AFTER:
  interface Shape { double area(); }
  record Circle(double radius) implements Shape {
      public double area() { return Math.PI * radius * radius; }
  }
  record Rectangle(double width, double height) implements Shape {
      public double area() { return width * height; }
  }

  ---

  REPLACE NESTED CONDITIONAL WITH GUARD CLAUSES
  -----------------------------------------------
  Flatten deeply nested if-else by returning/throwing early.

  BEFORE:
  void process(Order o) {
      if (o != null) {
          if (o.isValid()) {
              if (o.getItems().size() > 0) {
                  doProcess(o);
              }
          }
      }
  }

  AFTER:
  void process(Order o) {
      if (o == null) return;
      if (!o.isValid()) return;
      if (o.getItems().isEmpty()) return;
      doProcess(o);
  }

  ---

  DECOMPOSE CONDITIONAL
  ---------------------
  Extract complex conditions into well-named boolean methods.

  BEFORE:
  if (date.before(SUMMER_START) || date.after(SUMMER_END)) { ... }

  AFTER:
  if (isOffSeason(date)) { ... }
  private boolean isOffSeason(Date d) {
      return d.before(SUMMER_START) || d.after(SUMMER_END);
  }

================================================================
INHERITANCE REFACTORINGS
================================================================

  REPLACE INHERITANCE WITH DELEGATION (COMPOSITION)
  --------------------------------------------------
  When a subclass uses only part of superclass methods, delegate instead.

  BEFORE: class Stack extends Vector  // inherits unrelated methods

  AFTER:
  class Stack<T> {
      private final Deque<T> delegate = new ArrayDeque<>();
      public void push(T item) { delegate.push(item); }
      public T pop() { return delegate.pop(); }
  }

  ---

  PULL UP METHOD / PUSH DOWN METHOD
  -----------------------------------
  If two subclasses share identical behavior → Pull Up to superclass.
  If superclass has a method only one subclass uses → Push Down.

  ---

  EXTRACT SUPERCLASS / EXTRACT INTERFACE
  ----------------------------------------
  When multiple classes share similar behavior:
  → Extract Interface if only the contract matters
  → Extract Superclass if shared implementation exists

================================================================
DATA REFACTORINGS
================================================================

  REPLACE PRIMITIVE WITH OBJECT (VALUE OBJECT)
  ----------------------------------------------
  BEFORE: String email; // no validation, just a String
  AFTER:
  record Email(String value) {
      Email { if (!value.contains("@")) throw new IllegalArgumentException(); }
  }

  ---

  REPLACE MAGIC NUMBER WITH CONSTANT
  ------------------------------------
  BEFORE: if (speed > 299792458) throw ...
  AFTER:  static final double SPEED_OF_LIGHT = 299_792_458;
          if (speed > SPEED_OF_LIGHT) throw ...

================================================================
SAFE REFACTORING CHECKLIST
================================================================

  Before starting:
  [ ] Tests cover the code being refactored (or add them first)
  [ ] Code compiles and tests pass
  [ ] Commit current state

  During refactoring:
  [ ] One transformation at a time
  [ ] Run tests after each step
  [ ] Don't add new functionality simultaneously

  After refactoring:
  [ ] Tests still pass
  [ ] No new smells introduced
  [ ] Code more readable than before

================================================================
REFACTORING VS FEATURE ADDITION
================================================================

  Rule: NEVER refactor and add features in the same commit.
  Reason: If something breaks, you can't tell if it was
          the refactoring or the new feature.

  Workflow:
  1. Refactor first (tests still pass)
  2. Commit "Refactor: extract calculateTotal method"
  3. Add feature (on top of cleaner code)
  4. Commit "Feature: add member discount"

================================================================
INTERVIEW Q&A
================================================================

  Q: What is refactoring?
  A: Restructuring existing code without changing its external behavior.
     Always backed by tests. Done in small, safe steps.

  Q: When should you NOT refactor?
  A: When there are no tests (add tests first), when close to a deadline
     (document the debt), when code is about to be deleted.

  Q: How do you refactor safely?
  A: Write tests first, small steps, run tests after each step, commit
     before starting. IDE-assisted refactoring (rename, extract) is safest.

  Q: What is technical debt?
  A: The accumulated cost of shortcuts taken in code. Like financial debt,
     it accrues "interest" — every future change costs more. Refactoring pays it down.

  Q: What is the difference between refactoring and rewriting?
  A: Refactoring: small, incremental, always working, tested.
     Rewriting: replace large chunks, high risk, often breaks things.
     Martin Fowler: "If it's hard to refactor, that's a design smell."
