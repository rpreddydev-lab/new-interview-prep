================================================================
  CLEAN CODE — OVERVIEW
================================================================

  Clean Code is Robert C. Martin's collection of practices for
  writing code that is readable, maintainable, and changeable.

  "Clean code reads like well-written prose." — Grady Booch

  "Any fool can write code that a computer can understand.
   Good programmers write code that humans can understand." — Martin Fowler

  "Clean code always looks like it was written by someone who cares."
   — Michael Feathers

----------------------------------------------------------------
WHY CLEAN CODE MATTERS
----------------------------------------------------------------

  Code is READ far more than it is WRITTEN.
    - Code review: others read it
    - Debugging: you read it days/weeks/months later
    - Onboarding: new teammates read it
    - Maintenance: every change starts with reading

  "Messy code slows us down. We spend more time reading to understand
   than actually making changes." — Robert C. Martin

  Studies: developers spend 10x more time reading code than writing it.

----------------------------------------------------------------
CLEAN CODE CATEGORIES
----------------------------------------------------------------

  1. MEANINGFUL NAMES
     - Intention-revealing names
     - Avoid noise words (Manager, Data, Info)
     - Use searchable names (not single letters)
     - Class names = nouns; method names = verbs

  2. FUNCTIONS / METHODS
     - Do one thing (SRP at method level)
     - Small (typically <20 lines)
     - Single level of abstraction
     - No side effects (pure functions when possible)
     - Avoid output arguments; prefer return values

  3. COMMENTS
     - Code should explain itself (no comments needed)
     - Comments explain WHY, not WHAT
     - No redundant comments, misleading comments
     - Don't comment out dead code — delete it

  4. ERROR HANDLING
     - Prefer exceptions over error codes
     - Don't return null (use Optional, throw, or Null Object)
     - Fail fast: detect errors at boundary, not deep in logic
     - Clean up resources in finally / try-with-resources

  5. CODE SMELLS (symptoms of bad code)
     - Long method, large class, long parameter list
     - Duplicate code, dead code, speculative generality
     - Feature envy, inappropriate intimacy, data clumps
     - Switch statements, primitive obsession

  6. REFACTORING TECHNIQUES
     - Extract method/class
     - Rename (most impactful improvement)
     - Replace conditional with polymorphism
     - Introduce parameter object
     - Replace primitive with object

  7. BOY SCOUT RULE
     "Leave the campground cleaner than you found it."
     Every time you touch code, make a small improvement.

----------------------------------------------------------------
THE CLEAN CODE LITMUS TEST
----------------------------------------------------------------

  Good code = code where:
    1. The name tells you what it does without reading the body
    2. A function does exactly what its name says — no more
    3. Adding a feature requires minimal change to existing code
    4. Tests exist and run in seconds
    5. No surprises when reading
