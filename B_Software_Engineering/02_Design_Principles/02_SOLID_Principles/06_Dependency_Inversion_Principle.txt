================================================================
  DEPENDENCY INVERSION PRINCIPLE (DIP)
================================================================

  Definition:
    A. High-level modules should NOT depend on low-level modules.
       Both should depend on ABSTRACTIONS.
    B. Abstractions should NOT depend on details.
       Details (concrete implementations) should depend on abstractions.

  Robert C. Martin, 1996.

  "Inversion" because traditional dependency goes from high-level
  to low-level (business logic → specific DB driver). DIP INVERTS
  this: both depend on an abstraction that belongs to the high-level layer.

----------------------------------------------------------------
TRADITIONAL vs INVERTED DEPENDENCY
----------------------------------------------------------------

  TRADITIONAL (violation):

  OrderService (high-level)
       |
       | depends on (new XxxRepository inside)
       v
  MySqlOrderRepository (low-level)

  OrderService is tightly coupled to MySQL. Cannot:
    - Test without a real MySQL database
    - Switch to PostgreSQL without changing OrderService
    - Mock the repository in unit tests


  INVERTED (DIP-compliant):

  OrderService (high-level)        MySqlOrderRepository (low-level)
       |                                     |
       | depends on                          | depends on
       v                                     v
       OrderRepository (abstraction) <-------+

  Both depend on the abstraction. MySqlOrderRepository IMPLEMENTS it.
  OrderService never sees MySQL — only the interface.

----------------------------------------------------------------
VIOLATION EXAMPLE
----------------------------------------------------------------

  // BAD: high-level hardcodes low-level dependency
  public class OrderService {
      // Direct instantiation = tight coupling
      private final MySqlOrderRepository repository = new MySqlOrderRepository();
      private final SmtpEmailService emailService = new SmtpEmailService("smtp.gmail.com", 587);

      public void placeOrder(Order order) {
          repository.save(order);
          emailService.sendConfirmation(order.getCustomerEmail());
      }
  }

  Problems:
    - Cannot test without MySQL and Gmail SMTP
    - Cannot swap implementations without opening this class
    - SRP violated: managing dependency lifecycle + business logic

----------------------------------------------------------------
FIX: DEPEND ON ABSTRACTIONS
----------------------------------------------------------------

  // Define abstractions (owned by the high-level layer)
  public interface OrderRepository {
      void save(Order order);
      Optional<Order> findById(Long id);
  }

  public interface EmailService {
      void sendConfirmation(String emailAddress);
  }

  // High-level module depends on abstractions — never on concrete classes
  @Service
  @RequiredArgsConstructor
  public class OrderService {
      private final OrderRepository orderRepository;  // interface
      private final EmailService emailService;         // interface

      public void placeOrder(Order order) {
          orderRepository.save(order);
          emailService.sendConfirmation(order.getCustomerEmail());
      }
  }

  // Low-level modules implement abstractions
  @Repository
  public class JpaOrderRepository implements OrderRepository {
      public void save(Order order) { /* JPA/Hibernate */ }
      public Optional<Order> findById(Long id) { /* JPA */ return null; }
  }

  @Component
  public class SmtpEmailService implements EmailService {
      public void sendConfirmation(String emailAddress) { /* SMTP */ }
  }

  // Test: inject fakes — no Spring needed
  OrderRepository fakeRepo = new InMemoryOrderRepository();
  EmailService fakeMail = email -> emailsSent.add(email);
  OrderService svc = new OrderService(fakeRepo, fakeMail);

----------------------------------------------------------------
WHO OWNS THE ABSTRACTION?
----------------------------------------------------------------

  KEY insight: the abstraction belongs to the high-level module's package,
  NOT the low-level module's package.

  // Package structure showing ownership:
  com.company.order.service
      OrderService.java          (high-level)
      OrderRepository.java       (abstraction — owned by service layer)
      EmailService.java          (abstraction — owned by service layer)

  com.company.order.infrastructure
      JpaOrderRepository.java    (low-level — depends on abstraction)
      SmtpEmailService.java      (low-level — depends on abstraction)

  This means: changing the DB technology changes ONLY the infrastructure
  package. The service package never changes. Dependency arrow points
  from infrastructure toward the domain (inverted from traditional).

  This is the "Ports and Adapters" (Hexagonal) architecture pattern.

----------------------------------------------------------------
DIP AND SPRING DEPENDENCY INJECTION
----------------------------------------------------------------

  Spring's IoC container IS the implementation of DIP:

  @Autowired OrderRepository orderRepository;
  // Spring injects JpaOrderRepository at runtime
  // OrderService sees only the interface

  Spring selects implementation via:
    - @Primary: default when multiple exist
    - @Qualifier: explicit name selection
    - @Profile: environment-specific implementation
    - @ConditionalOnProperty: feature-flag controlled

  // Swap implementations without changing OrderService:
  @Profile("test")
  @Repository
  public class InMemoryOrderRepository implements OrderRepository { ... }

  @Profile("prod")
  @Repository
  public class JpaOrderRepository implements OrderRepository { ... }

----------------------------------------------------------------
DIP AND FACTORY PATTERN
----------------------------------------------------------------

  When Spring is not available, Factory implements DIP:

  public class RepositoryFactory {
      public static OrderRepository create(String type) {
          return switch (type) {
              case "jpa"    -> new JpaOrderRepository();
              case "memory" -> new InMemoryOrderRepository();
              default -> throw new IllegalArgumentException("Unknown: " + type);
          };
      }
  }

  OrderRepository repo = RepositoryFactory.create("jpa");
  OrderService svc = new OrderService(repo, emailService);

  Factory is the "glue" that creates concrete objects so that
  high-level code never calls new on low-level classes.

----------------------------------------------------------------
DIP AND TESTING
----------------------------------------------------------------

  DIP makes unit testing trivial:

  // No Spring, no database, no SMTP — pure unit test
  class OrderServiceTest {
      private OrderService orderService;
      private List<Order> savedOrders = new ArrayList<>();
      private List<String> sentEmails = new ArrayList<>();

      @BeforeEach
      void setup() {
          OrderRepository fakeRepo = order -> savedOrders.add(order);
          EmailService fakeMail    = email -> sentEmails.add(email);
          orderService = new OrderService(fakeRepo, fakeMail);
      }

      @Test
      void placeOrder_savesAndSendsEmail() {
          Order order = new Order("user@example.com", 99.99);
          orderService.placeOrder(order);
          assertEquals(1, savedOrders.size());
          assertTrue(sentEmails.contains("user@example.com"));
      }
  }

  Without DIP: this test requires spinning up a DB and mail server.

----------------------------------------------------------------
DIP vs DI (DEPENDENCY INJECTION)
----------------------------------------------------------------

  DIP is the PRINCIPLE (high-level doesn't depend on low-level).
  DI is one TECHNIQUE to achieve DIP (inject via constructor/setter).

  DI can exist without DIP:
    Injecting new ConcreteService() still has a concrete dependency.

  DIP can exist without DI framework:
    Manual factory + constructor injection achieves DIP without Spring.

  Spring IoC = DI framework = practical implementation of DIP.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is DIP? Why is it the most important SOLID principle?
  A: DIP says high-level business logic should not depend on low-level
     infrastructure details. Both depend on abstractions. It's crucial
     because it enables: unit testing without infrastructure, swappable
     implementations, and keeping business logic clean. Spring's entire
     IoC/DI container exists to implement DIP.

  Q: What's the difference between Dependency Inversion and Dependency Injection?
  A: DIP is the principle: depend on abstractions. DI is a technique (constructor
     injection, setter injection) to fulfill that principle. Spring IoC is a DI
     framework. You can satisfy DIP using manual factories without a DI framework.

  Q: Who should own the interface — the high-level or low-level module?
  A: The HIGH-LEVEL module. The abstraction should be in the same package as
     the business logic, not the infrastructure. Infrastructure depends on the
     domain's abstractions. This is the Ports and Adapters / Hexagonal pattern.

  Q: How does DIP enable testing?
  A: High-level code depends on interfaces. In tests, inject lightweight fakes
     (in-memory implementations, lambdas). No database, no network, no SMTP.
     Test runs in milliseconds with deterministic behavior.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - State both parts of DIP (high-level/low-level; abstraction/details).
  - Show the before (new Concrete()) and after (interface injection).
  - "Abstraction owned by high-level" is the nuanced point interviewers love.
  - Connect to Spring: @Autowired is DIP in action.
  - Connect to testing: DIP = fast, isolated unit tests.
