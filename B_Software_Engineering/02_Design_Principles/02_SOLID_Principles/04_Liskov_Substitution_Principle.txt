================================================================
  LISKOV SUBSTITUTION PRINCIPLE (LSP)
================================================================

  Definition: If S is a subtype of T, then objects of type T may be
              replaced with objects of type S without altering any of
              the desirable properties of the program.

  Barbara Liskov, 1987.

  Informal: "If it looks like a duck and quacks like a duck but needs
             batteries, you probably have the wrong abstraction."

  Practical: A subclass must HONOR the contract of its superclass.
             Callers of the supertype should not need to know about
             subtypes and should not be surprised.

----------------------------------------------------------------
LSP CONTRACT REQUIREMENTS
----------------------------------------------------------------

  A subtype must not:
    1. Throw exceptions the parent does not throw (strengthen preconditions... actually:)
    2. Add stronger preconditions (be MORE restrictive on inputs)
    3. Add weaker postconditions (guarantee LESS on outputs)
    4. Override a method to throw UnsupportedOperationException
    5. Change invariants the parent guarantees

  Formal rules:
    Preconditions: subtype may only WEAKEN (accept more)
    Postconditions: subtype may only STRENGTHEN (return more/better)
    Invariants: must be preserved
    No new exceptions beyond parent's declared types

----------------------------------------------------------------
CLASSIC VIOLATION: SQUARE IS-A RECTANGLE?
----------------------------------------------------------------

  // Looks correct geometrically, but violates LSP
  public class Rectangle {
      protected int width;
      protected int height;

      public void setWidth(int width)   { this.width = width; }
      public void setHeight(int height) { this.height = height; }

      public int getArea() { return width * height; }
  }

  public class Square extends Rectangle {
      @Override
      public void setWidth(int width) {
          this.width = width;
          this.height = width;   // SURPRISE: setting width changes height
      }

      @Override
      public void setHeight(int height) {
          this.width = height;   // SURPRISE: setting height changes width
          this.height = height;
      }
  }

  // Test that works for Rectangle but FAILS for Square
  public void testArea(Rectangle r) {
      r.setWidth(5);
      r.setHeight(4);
      assert r.getArea() == 20;  // FAILS for Square: 4*4=16, not 20
  }

  // Caller must instanceof-check to handle Square specially — LSP violated
  // The substitution principle is broken.

  FIX: Don't extend — use separate hierarchy or make both immutable:

  public interface Shape {
      int area();
  }

  public record Rectangle(int width, int height) implements Shape {
      public int area() { return width * height; }
  }

  public record Square(int side) implements Shape {
      public int area() { return side * side; }
  }

  // No substitution problem: both implement Shape; neither pretends to be the other.

----------------------------------------------------------------
VIOLATION: UNSUPPORTED OPERATION
----------------------------------------------------------------

  // Java's own LSP violation in early collections
  List<Integer> fixed = List.of(1, 2, 3);  // unmodifiable
  fixed.add(4);  // throws UnsupportedOperationException

  // AbstractList.add() default = throw UnsupportedOperationException
  // List contract says add() adds element; fixed list breaks contract.

  // Same problem with Collections.unmodifiableList() — runtime surprise.
  // Fix: immutable list type should not implement mutable List interface.
  //      (Java chose backward compatibility over LSP here.)

  Your code: if you override a method to throw UnsupportedOperationException,
  you are almost certainly violating LSP.

----------------------------------------------------------------
VIOLATION: STRENGTHENED PRECONDITION
----------------------------------------------------------------

  public class Animal {
      public void feed(Food food) {
          // accepts any Food
      }
  }

  public class VeganAnimal extends Animal {
      @Override
      public void feed(Food food) {
          if (food instanceof Meat) {  // MORE RESTRICTIVE than parent
              throw new IllegalArgumentException("Cannot feed meat!");
          }
          // ...
      }
  }

  // Code written for Animal now breaks when given VeganAnimal:
  animal.feed(new Meat());  // works for Animal, throws for VeganAnimal
  // Caller must know concrete type — LSP violated.

  FIX: don't narrow the acceptable inputs in a subtype.
       Or redesign: make FoodType a generic parameter; type system enforces it.

----------------------------------------------------------------
LSP VIOLATION DETECTION CHECKLIST
----------------------------------------------------------------

  Does the subclass:
    [ ] Throw a new exception type not in parent's signature?
    [ ] Override a method with throw new UnsupportedOperationException()?
    [ ] Require caller to instanceof-check before using?
    [ ] Have a method that does nothing (empty override) when parent did something?
    [ ] Accept fewer inputs than parent (strengthen precondition)?
    [ ] Guarantee less than parent (weaken postcondition)?

  Any YES = likely LSP violation.

----------------------------------------------------------------
LSP IN JAVA STDLIB — GOOD EXAMPLES
----------------------------------------------------------------

  ArrayList extends AbstractList extends List:
    - All List contracts honored
    - add(), remove(), get(), size() work as expected
    - No surprises

  LinkedList extends AbstractSequentialList:
    - Also implements Deque; all Deque operations honored
    - Implements List; all List operations honored

  TreeMap extends AbstractMap, implements SortedMap:
    - All Map operations work as expected
    - Additional: keySet() returns sorted keys (strengthened postcondition — OK)

  Comparable<T>.compareTo():
    Any Comparable must satisfy: sgn(x.compareTo(y)) = -sgn(y.compareTo(x))
    Violating this causes TreeMap, PriorityQueue to behave incorrectly.

----------------------------------------------------------------
LSP AND DESIGN PATTERNS
----------------------------------------------------------------

  Composite: Leaf and Composite both implement Component — only works if
             both HONOR the same contract. If Leaf.add() throws, client
             must instanceof-check — LSP violated.

  Strategy: All strategies implement the same interface contract.
            A strategy that does nothing (no-op) is OK if the contract
            allows it (Null Object). One that throws is not OK.

  Template Method: subclass fills steps but must not violate the overall
                   contract that the template method guarantees.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is LSP? Explain with an example.
  A: LSP says subtypes must be substitutable for supertypes without
     surprising callers. Classic violation: Square extending mutable Rectangle.
     Setting width on a Square also changes height — breaks code written
     for Rectangle. Fix: make both extend an immutable Shape interface
     instead of inheriting from each other.

  Q: How does UnsupportedOperationException relate to LSP?
  A: Collections.unmodifiableList() and List.of() return unmodifiable Lists
     that throw UnsupportedOperationException on add()/remove(). The List
     contract says these operations should work. Runtime surprise = LSP violation.
     Proper fix would be a separate ReadOnlyList interface, but Java chose
     backward compatibility.

  Q: What is the difference between LSP and polymorphism?
  A: Polymorphism means subtypes can be used where supertypes are expected (language feature).
     LSP adds a behavioral constraint: substitution must not BREAK the program.
     You can have polymorphism without LSP (Square-Rectangle). LSP ensures
     that polymorphism is SAFE: no surprises when using a subtype.

  Q: How do you detect LSP violations in code review?
  A: Look for: instanceof checks in code that should accept the base type,
     UnsupportedOperationException overrides, empty method overrides,
     methods that throw new exceptions not in the base type's signature.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Square/Rectangle example is the go-to. Know it cold.
  - Connect to Java's own violations (unmodifiable collections).
  - "No instanceof needed when using subtype" = practical LSP test.
  - Link to Composite pattern: depends on LSP working correctly.
