================================================================
  COMPOSITION OVER INHERITANCE
================================================================

  Definition: Favor composing objects with desired behaviors (HAS-A)
              over extending class hierarchies (IS-A) when building
              complex functionality.

  GoF Design Patterns book, Principle #2 (after "Program to interface").

----------------------------------------------------------------
WHY INHERITANCE IS PROBLEMATIC
----------------------------------------------------------------

  1. FRAGILE BASE CLASS PROBLEM
     A change to the superclass can break all subclasses.
     Subclasses depend on implementation details of the parent
     that may change without warning.

  2. INHERITANCE EXPOSES INTERNALS
     Subclass can see (and override) protected methods.
     Encapsulation is reduced — white-box reuse.

  3. COMBINATORIAL EXPLOSION
     To combine 3 behaviors (A, B, C):
       Inheritance: A, B, C, AB, AC, BC, ABC = 7 classes
       Composition: 3 classes, combined at runtime

  4. INFLEXIBLE AT RUNTIME
     Inheritance is set at compile time.
     You cannot switch from BubbleSortList to QuickSortList at runtime.

  5. WRONG MODELING
     "Is a" relationships break down in complex domains.
     Stack should NOT extend Vector (historical Java mistake).

----------------------------------------------------------------
JAVA MISTAKE: STACK EXTENDS VECTOR
----------------------------------------------------------------

  java.util.Stack extends java.util.Vector.

  Stack IS-A Vector? No — a Stack should only expose push/pop/peek.
  But because it extends Vector, Stack also exposes:
    insertElementAt(), setElementAt(), removeElementAt() — breaks Stack semantics.

  Should have been: Stack HAS-A Vector (or ArrayDeque).
  Modern Java: use Deque<T> (ArrayDeque, LinkedList) instead of Stack.

  Lesson: "works like a" ≠ "is a". Check if the subtype should
  expose ALL of the parent's public API. If not — use composition.

----------------------------------------------------------------
COMPOSITION EXAMPLE — SORT BEHAVIOR
----------------------------------------------------------------

  // INHERITANCE: cannot change sort algorithm at runtime
  class BubbleSortedList<T> extends ArrayList<T> {
      // hardwired to bubble sort
  }

  class QuickSortedList<T> extends ArrayList<T> {
      // hardwired to quick sort
  }

  // To get a list that's both sorted and logged: ListLoggedBubbleSorted extends... ?

  // COMPOSITION: inject behavior
  public class SortableList<T> {
      private final List<T> items = new ArrayList<>();
      private Comparator<T> sortStrategy;  // injected — swappable at runtime

      public void setSortStrategy(Comparator<T> strategy) {
          this.sortStrategy = strategy;
      }

      public void sort() {
          items.sort(sortStrategy);
      }

      public void add(T item) { items.add(item); }
      public List<T> getItems() { return Collections.unmodifiableList(items); }
  }

  SortableList<Integer> list = new SortableList<>();
  list.setSortStrategy(Comparator.naturalOrder());   // quicksort internally
  list.setSortStrategy(Comparator.reverseOrder());   // swap at runtime — zero new classes

----------------------------------------------------------------
COMPOSITION EXAMPLE — SERVICE BEHAVIOR
----------------------------------------------------------------

  // INHERITANCE PROBLEM: behavior locked into hierarchy
  class Service { void execute() { /* core */ } }
  class LoggingService extends Service { void execute() { log; super.execute(); } }
  class CachingService extends LoggingService { ... }
  class MetricsService extends CachingService { ... }
  // Can't reorder; can't pick just logging without caching; combinatorial explosion

  // COMPOSITION: Decorator pattern
  interface Service {
      void execute();
  }

  class CoreService implements Service {
      public void execute() { /* core logic */ }
  }

  class LoggingDecorator implements Service {
      private final Service delegate;
      public LoggingDecorator(Service s) { this.delegate = s; }
      public void execute() { log.info("Before"); delegate.execute(); log.info("After"); }
  }

  class CachingDecorator implements Service {
      private final Service delegate;
      // ... check cache; delegate.execute(); store in cache
  }

  // Mix and match at runtime
  Service service = new LoggingDecorator(new CachingDecorator(new CoreService()));
  Service minimal  = new CoreService();                        // no logging, no caching
  Service logOnly  = new LoggingDecorator(new CoreService()); // only logging

----------------------------------------------------------------
WHEN IS INHERITANCE APPROPRIATE?
----------------------------------------------------------------

  Inheritance IS correct when:
    1. IS-A relationship is genuine and stable (Dog IS-A Animal)
    2. You want to reuse AND extend (template method with concrete steps)
    3. Subtype should expose ALL of parent's public API (no empty overrides)
    4. Behavioral substitution holds (LSP satisfied)
    5. Sealed hierarchy under your control (enum-like polymorphism)

  Inheritance IS wrong when:
    - Only want one or two methods from parent
    - Parent has methods that break subtype's invariants
    - Need to combine behaviors at runtime
    - "Is-a" is really "is-like-a" or "works-like-a"

----------------------------------------------------------------
JAVA EXAMPLES OF COMPOSITION PREFERENCE
----------------------------------------------------------------

  BAD inheritance:         GOOD composition:
  Stack extends Vector     ArrayDeque or composition
  Properties extends Hashtable  Wrap Map internally
  HttpServlet: extends + overrides service()  →  Route handler injected into dispatcher

  Spring Bean injection IS composition:
    OrderService HAS-A OrderRepository (injected)
    vs. OrderService extends BaseOrderWithRepository (wrong)

  Java 8 Functional Interfaces:
    Predicate.and()/or() = composing behaviors
    Function.andThen()/compose() = composing transformations

  Collections.unmodifiableList(list):
    WRAPS (composes) the original list — does not extend ArrayList.

----------------------------------------------------------------
COMPOSITION MECHANICS IN JAVA
----------------------------------------------------------------

  // Field composition (most common)
  public class OrderService {
      private final OrderRepository repository;  // HAS-A
      private final EmailService emailService;   // HAS-A
  }

  // Constructor injection
  public OrderService(OrderRepository repository, EmailService emailService) {
      this.repository = repository;
      this.emailService = emailService;
  }

  // Delegation: expose limited interface
  public class SafeList<T> {
      private final List<T> delegate = new ArrayList<>();

      public void add(T item) { delegate.add(item); }
      public T get(int index) { return delegate.get(index); }
      // Does NOT expose remove(), set() — controlled API
  }

  // Compare: SafeList extends ArrayList would expose everything

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Why prefer composition over inheritance?
  A: Inheritance creates tight coupling to the parent's implementation,
     is fixed at compile time, leads to combinatorial class explosion,
     and the fragile base class problem breaks subclasses when parent changes.
     Composition is more flexible: behaviors are injected, swappable at runtime,
     and combined without new classes.

  Q: When IS inheritance appropriate?
  A: When the IS-A relationship is genuine, stable, and the subtype should
     expose the full parent API (LSP satisfied). Template Method is a valid
     use: abstract class defines skeleton; subclasses fill concrete steps.
     Also: AbstractList, HttpServlet, AbstractProcessor patterns.

  Q: How does Java's Stack extending Vector violate this principle?
  A: Stack IS-NOT Vector. Extending Vector exposes insertElementAt(),
     setElementAt() — operations that don't belong on a Stack. Stack HAS-A
     Vector (uses it internally for storage). The composition model would
     have wrapped Vector and exposed only push/pop/peek.

  Q: How does Spring use composition over inheritance?
  A: Spring beans are composed via DI — OrderService HAS-A OrderRepository
     rather than extends. Decorators (proxy for @Transactional, @Cacheable)
     wrap beans. Strategy injection via Map<String, Interface> composes
     behavior at runtime.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Stack extends Vector = immediate memorable Java violation.
  - Show the combinatorial explosion of inheritance vs. composition.
  - Decorator pattern = composition in action (mention it).
  - "HAS-A vs IS-A" is the one-line answer. Then add nuance.
