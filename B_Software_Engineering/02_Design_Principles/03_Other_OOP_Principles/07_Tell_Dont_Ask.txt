================================================================
  TELL DON'T ASK (AND LAW OF DEMETER)
================================================================

  Two related principles about where behavior should live and
  how objects should interact.

================================================================
TELL DON'T ASK (TDA)
================================================================

  Definition: Tell objects what to do; don't ask them for their state
              and then make decisions outside.

  "You should tell your objects what you want them to do,
   not ask them questions about their state and then make the
   decision yourself." — Martin Fowler

----------------------------------------------------------------
THE PROBLEM: ASKING THEN DECIDING
----------------------------------------------------------------

  // BAD: asking for state, deciding outside the object
  public void checkoutOrder(Order order) {
      if (order.getStatus() == OrderStatus.PAID &&
          order.getItems().size() > 0 &&
          order.getCustomer().isVerified()) {
          // logic that belongs in Order
          order.setStatus(OrderStatus.SHIPPED);
          order.setShippedAt(Instant.now());
      }
  }

  Problems:
    - Logic about Order scattered outside Order
    - Order's rules duplicated everywhere Order is used
    - Changing Order validation = find all places that ask+decide
    - Order is an anemic data container (no real behavior)

----------------------------------------------------------------
FIX: TELL THE OBJECT
----------------------------------------------------------------

  // GOOD: tell Order to ship itself
  public class Order {
      private OrderStatus status;
      private List<OrderItem> items;
      private Customer customer;
      private Instant shippedAt;

      // Order knows its own rules
      public void ship() {
          if (status != OrderStatus.PAID) {
              throw new IllegalStateException("Cannot ship unpaid order");
          }
          if (items.isEmpty()) {
              throw new IllegalStateException("Cannot ship empty order");
          }
          if (!customer.isVerified()) {
              throw new IllegalStateException("Customer not verified");
          }
          this.status = OrderStatus.SHIPPED;
          this.shippedAt = Instant.now();
      }
  }

  // Caller just tells Order to ship — no asking, no external decisions
  public void checkoutOrder(Order order) {
      order.ship();  // Order handles its own rules
  }

  Benefits:
    - Validation in one place (Order) — DRY
    - Order is a rich domain model with behavior
    - checkoutOrder() simplified; doesn't need to know Order's internals
    - Adding new constraint: change Order.ship() only

----------------------------------------------------------------
ANEMIC DOMAIN MODEL — THE TELL-DON'T-ASK VIOLATION
----------------------------------------------------------------

  Anemic Domain Model (Martin Fowler antipattern):
    Domain classes = pure data containers (getters/setters only).
    Business logic scattered in Service classes.

  // Anemic
  public class Order {
      private OrderStatus status;  // just data
      public OrderStatus getStatus() { return status; }
      public void setStatus(OrderStatus status) { this.status = status; }
  }

  // Fat service with all the logic
  public class OrderService {
      public void ship(Order order) {
          if (order.getStatus() == PAID) {  // asking
              order.setStatus(SHIPPED);     // then telling
          }
      }
  }

  Rich Domain Model (TDA-compliant):
    Business rules inside the domain object.
    Service orchestrates; domain objects execute.

  When Anemic is OK:
    Simple CRUD apps with no real domain logic.
    DTOs, records, value objects — deliberately data-only.
    JPA entities with framework constraints (need no-arg constructor, etc.).

================================================================
LAW OF DEMETER (LOD) — PRINCIPLE OF LEAST KNOWLEDGE
================================================================

  Definition: A method of object O should only invoke methods of:
    1. O itself
    2. Objects passed as arguments
    3. Objects created within the method
    4. Direct component objects of O

  Never: objects returned from calling other methods.

  One-liner: "Only talk to your immediate friends."

  Visual: Talk to your friends; don't talk to strangers your friends know.

----------------------------------------------------------------
TRAIN WRECK CODE — LOD VIOLATION
----------------------------------------------------------------

  // BAD: a.getB().getC().doThing() — "train wreck"
  double tax = order.getCustomer()
                    .getAddress()
                    .getCity()
                    .getTaxRate();

  Problems:
    - Caller knows: Order has Customer, Customer has Address, Address has City
    - Deep knowledge of the object graph
    - Changing Address to not have City → cascade of broken callers
    - Every caller must be updated when structure changes

  // BAD in Spring service
  double discount = cart.getUser()
                        .getMembership()
                        .getDiscountPolicy()
                        .getDiscount(cart.getTotal());

----------------------------------------------------------------
FIX: DELEGATE THROUGH LAYERS
----------------------------------------------------------------

  // GOOD: each class delegates one level only
  public class Order {
      public double getTaxRate() {
          return customer.getTaxRate();  // Order asks Customer (friend)
      }
  }

  public class Customer {
      public double getTaxRate() {
          return address.getTaxRate();  // Customer asks Address (friend)
      }
  }

  public class Address {
      public double getTaxRate() {
          return city.getTaxRate();     // Address asks City (friend)
      }
  }

  // Caller now:
  double tax = order.getTaxRate();  // ONE level — friend only

  Benefits:
    - Caller doesn't know the internal structure
    - Changing Address to compute tax without City → only Address changes
    - Caller chain doesn't break

----------------------------------------------------------------
DATA OBJECTS EXCEPTION
----------------------------------------------------------------

  LoD applies to BEHAVIORAL objects (services, domain objects).

  It does NOT apply to DTOs, records, and data structures
  where the purpose is to carry data:

  // This is fine — no behavior, just traversing data
  String city = orderDto.shippingAddress().city();

  The principle protects behavioral coupling, not data access.
  Chaining on value objects / records is idiomatic Java.

----------------------------------------------------------------
JAVA BUILDER EXCEPTION
----------------------------------------------------------------

  Fluent builders violate LoD technically but are intentionally designed that way:

  User user = User.builder()
                  .name("Alice")
                  .email("alice@example.com")
                  .build();

  Builder.builder() returns Builder; each setter returns Builder.
  This is safe: the entire chain is within the same object (the Builder).
  No external object graph traversal.

----------------------------------------------------------------
TDA AND LOD INTERACTION
----------------------------------------------------------------

  Tell Don't Ask: put behavior with data.
  Law of Demeter: don't expose your internal structure.

  Both principles guard against the Anemic Domain Model + Service Bloat combination.
  Both guide toward rich, encapsulated domain objects.

  Combined violation example:
    order.getCustomer().getAddress().getCity()  (LoD violation)
    + caller then decides logic based on city (TDA violation)

  Combined fix:
    order.getApplicableTaxRate()  (one call; delegate inside; logic inside)

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is Tell Don't Ask?
  A: Tell objects WHAT to do rather than asking their state and deciding outside.
     Behavior belongs with data. If you're calling getters on an object to make
     a decision about it, that decision logic probably belongs inside the object.

  Q: What is the Law of Demeter?
  A: Only talk to immediate friends: the object itself, its fields, method parameters,
     and objects it creates. Never call methods on the return value of another method
     (no train wrecks: a.getB().getC().doX()). Change to the object graph
     stays contained.

  Q: What is an Anemic Domain Model and why is it considered bad?
  A: Domain classes with only getters/setters; all logic in service classes.
     Bad because: business rules scattered (DRY violation), classes have no
     meaningful behavior (TDA violation), services become fat and untestable.
     Rich domain model: behavior lives with the data that drives it.

  Q: Does LoD apply to method chaining (streams, builders)?
  A: Not literally — the principle applies to object GRAPH traversal (asking for
     another object's object). Stream chaining operates on the same stream object.
     Builder chaining returns the same builder. These don't violate the spirit of LoD.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - "Train wreck" is the memorable LoD violation image.
  - Anemic Domain Model = TDA violation; know Fowler's definition.
  - Show how to fix: add a method to the domain object instead of extracting state.
  - LoD exceptions: DTOs, records, builders — shows balanced judgment.
