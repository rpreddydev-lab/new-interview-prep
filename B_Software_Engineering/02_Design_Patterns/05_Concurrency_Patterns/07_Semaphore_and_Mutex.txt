================================================================
  SEMAPHORE AND MUTEX PATTERNS
================================================================

  Category:   Concurrency
  Intent:     Control access to a shared resource.
              Mutex (Mutual Exclusion Lock): ONE thread at a time.
              Semaphore: UP TO N threads at a time.

----------------------------------------------------------------
MUTEX (MUTUAL EXCLUSION LOCK)
----------------------------------------------------------------

  A mutex allows only one thread to hold the lock at a time.
  All other threads block until the lock is released.

  Java Implementations:
    1. synchronized keyword (intrinsic lock / monitor lock)
    2. ReentrantLock (explicit, more flexible)

  SYNCHRONIZED:
    // Instance-level lock (each object is its own monitor)
    public synchronized void increment() {
        count++;   // only one thread at a time
    }

    // Block-level (more granular, better performance)
    public void process() {
        // ... unsynchronized code ...
        synchronized (this) {
            count++;   // only this block is synchronized
        }
        // ... more unsynchronized code ...
    }

    // Class-level lock (shared across all instances)
    public static synchronized void classLevelOp() {
        staticCounter++;
    }

  REENTRANTLOCK (explicit):
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();         // acquire mutex
        try {
            count++;
        } finally {
            lock.unlock();   // ALWAYS in finally
        }
    }

    // Advanced features vs synchronized:
    lock.tryLock()                    // acquire if available; else return false
    lock.tryLock(timeout, unit)       // wait up to timeout
    lock.lockInterruptibly()          // interruptible waiting
    lock.newCondition()               // multiple condition variables
    new ReentrantLock(true)           // fair mode: FIFO order

----------------------------------------------------------------
REENTRANT LOCK vs SYNCHRONIZED
----------------------------------------------------------------

  Feature                    synchronized        ReentrantLock
  ---------------------------------------------------------------
  Syntax                     Simple keyword       Explicit lock/unlock
  Requires try-finally?      No                   YES (mandatory)
  Interruptible wait         No                   Yes (lockInterruptibly)
  Timed try lock             No                   Yes (tryLock(t, unit))
  Multiple conditions        One (wait/notify)    Multiple (newCondition())
  Fairness option            No                   Yes (new RRLK(true))
  Reentrant                  Yes                  Yes
  Performance                Optimized by JVM     Slightly more overhead
  Best for                   Simple sync          Complex lock management
  ---------------------------------------------------------------

  Prefer synchronized unless you need: timed locks, interruptible locking,
  fair ordering, or multiple condition variables.

CONDITION VARIABLES (with ReentrantLock)
----------------------------------------------------------------

  // Two conditions on one lock
  private final ReentrantLock    lock      = new ReentrantLock();
  private final Condition        notFull   = lock.newCondition();
  private final Condition        notEmpty  = lock.newCondition();
  private final Object[]         buffer    = new Object[10];
  private int                    count, head, tail;

  public void put(Object item) throws InterruptedException {
      lock.lock();
      try {
          while (count == buffer.length) notFull.await();   // wait if full
          buffer[tail] = item;
          tail = (tail + 1) % buffer.length;
          count++;
          notEmpty.signal();   // signal waiting consumer
      } finally {
          lock.unlock();
      }
  }

  public Object take() throws InterruptedException {
      lock.lock();
      try {
          while (count == 0) notEmpty.await();   // wait if empty
          Object item = buffer[head];
          head = (head + 1) % buffer.length;
          count--;
          notFull.signal();    // signal waiting producer
          return item;
      } finally {
          lock.unlock();
      }
  }

  // WARNING: Always use while() not if() for condition checks.
  // Spurious wakeups: await() can return without signal.
  while (!condition) { await(); }   // CORRECT
  if (!condition)    { await(); }   // WRONG — spurious wakeup risk

SEMAPHORE
----------------------------------------------------------------

  A semaphore has a count N (permits).
  acquire(): decrement count; block if count == 0.
  release(): increment count; wake one blocked thread.

  N=1 semaphore ≈ mutex (but NOT the same — see below).
  N>1 semaphore: throttle concurrency to N threads.

  Java Semaphore:
    Semaphore semaphore = new Semaphore(N);
    semaphore.acquire();     // block until permit available
    semaphore.release();     // return permit
    semaphore.tryAcquire()   // non-blocking attempt
    semaphore.tryAcquire(timeout, unit)  // timed attempt
    semaphore.availablePermits()

----------------------------------------------------------------
SEMAPHORE FOR RESOURCE POOL THROTTLING
----------------------------------------------------------------

  // Limit concurrent database connections to 10
  public class ConnectionThrottler {
      private final Semaphore permits = new Semaphore(10, true); // fair

      public Connection getConnection() throws InterruptedException {
          permits.acquire();   // wait for permit
          return pool.borrowConnection();
      }

      public void releaseConnection(Connection conn) {
          pool.returnConnection(conn);
          permits.release();   // always release!
      }
  }

  // Always release in finally:
  permits.acquire();
  try {
      useResource();
  } finally {
      permits.release();
  }

----------------------------------------------------------------
SEMAPHORE FOR RATE LIMITING
----------------------------------------------------------------

  // Allow at most 5 concurrent requests to an API
  public class RateLimiter {
      private final Semaphore semaphore = new Semaphore(5);

      public String callExternalApi(String url) throws InterruptedException {
          semaphore.acquire();
          try {
              return httpClient.get(url);
          } finally {
              semaphore.release();
          }
      }
  }

----------------------------------------------------------------
SEMAPHORE FOR SIGNALING (N=0 INITIAL)
----------------------------------------------------------------

  // Thread A waits for thread B to complete initialization
  Semaphore ready = new Semaphore(0);  // starts at 0

  // Thread B (initializer)
  new Thread(() -> {
      initializeSystem();
      ready.release();       // signal: initialization done
  }).start();

  // Thread A (waiter)
  ready.acquire();           // block until B signals
  useSystem();

----------------------------------------------------------------
MUTEX vs SEMAPHORE — KEY DIFFERENCES
----------------------------------------------------------------

  Mutex (ownership):                       Semaphore (count):
  -------------------------------------------------------------------
  Owner: only the locking thread can unlock   No ownership: any thread can release
  Reentrant possible                          Not reentrant by default
  Protects a single critical section          Controls access count / signaling
  Used for mutual exclusion                   Used for throttling or signaling
  -------------------------------------------------------------------

  Critical difference: A mutex MUST be unlocked by the SAME thread that locked it.
  A semaphore CAN be released by a different thread (useful for signaling).

  Binary Semaphore (N=1) vs Mutex:
    Both allow 1 thread at a time, BUT:
    Mutex: owner-based (prevents releasing from another thread).
    Binary semaphore: any thread can release — good for inter-thread signaling.

----------------------------------------------------------------
COUNTDOWNLATCH AND CYCLICBARRIER (RELATED SYNCHRONIZERS)
----------------------------------------------------------------

  CountDownLatch:
    One-time use. Count down to 0, then all waiting threads proceed.
    Cannot be reset.

    CountDownLatch latch = new CountDownLatch(3);

    // Workers
    executor.submit(() -> { doWork1(); latch.countDown(); });
    executor.submit(() -> { doWork2(); latch.countDown(); });
    executor.submit(() -> { doWork3(); latch.countDown(); });

    // Main thread waits for all 3
    latch.await();   // blocks until count reaches 0
    System.out.println("All done!");

    Use: wait for N tasks to complete (e.g., service startup checks).

  CyclicBarrier:
    Reusable. All threads wait at a barrier; when all arrive, proceed.
    Can be reset and reused for multiple phases.

    CyclicBarrier barrier = new CyclicBarrier(3, () ->
        System.out.println("Phase complete!"));  // action when all arrive

    Runnable worker = () -> {
        doPhase1Work();
        barrier.await();   // wait for all others
        doPhase2Work();
        barrier.await();
    };

    Use: multi-phase parallel processing where all must complete each phase together.

  CountDownLatch vs CyclicBarrier:
    CountDownLatch: countdown from N to 0 (one-shot, workers signal main).
    CyclicBarrier:  N threads wait for each other (reusable, peer-to-peer).

----------------------------------------------------------------
PHASER (FLEXIBLE BARRIER)
----------------------------------------------------------------

  Phaser: supports dynamic registration/deregistration; multiple phases.
  More flexible than CountDownLatch or CyclicBarrier.

  Phaser phaser = new Phaser(3);  // 3 registered parties

  // Register dynamically
  phaser.register();

  // Arrive (like countDown + await)
  phaser.arriveAndAwaitAdvance();  // arrive at current phase; wait for others

  // Deregister
  phaser.arriveAndDeregister();

  Use: parallel algorithms with variable number of workers per phase.

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Semaphore.acquire()/release():  O(1) — CAS or monitored operation.
  CountDownLatch.countDown()/await(): O(1) per operation.
  CyclicBarrier.await():          O(n) — last thread wakes all n waiters.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is a Mutex?
  A: Mutual exclusion lock — only one thread can hold it at a time.
     Java: synchronized keyword or ReentrantLock. The thread that locks it must
     unlock it. Prevents race conditions on shared state.

  Q: What is a Semaphore? How is it different from Mutex?
  A: Semaphore has N permits. acquire() blocks if 0 permits; release() adds one.
     Mutex is owner-based (only locker can unlock). Semaphore is count-based (any
     thread can release). Binary semaphore (N=1) is NOT the same as mutex due to
     no ownership. Semaphore is used for throttling or inter-thread signaling.

  Q: What is the difference between CountDownLatch and CyclicBarrier?
  A: CountDownLatch: count down to 0, then waiting threads proceed. One-shot, not reusable.
     CyclicBarrier: all N threads wait at barrier; when all arrive, proceed. Reusable.
     Latch: workers signal main. Barrier: peers synchronize with each other.

  Q: When to use tryLock() over lock()?
  A: tryLock() for deadlock avoidance — if you can't get the lock, back off and
     try a different order or retry later. Also for non-blocking "attempt" semantics.

  Q: Why use while() and not if() with await()?
  A: Spurious wakeups — Java's wait/await can return without a corresponding signal.
     Always re-check the condition after waking: while(!condition) { await(); }

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Know ReentrantLock features vs synchronized (tryLock, fair, conditions).
  - Know the Semaphore for throttling pattern — very common use case.
  - CountDownLatch vs CyclicBarrier is a classic interview question.
  - Spurious wakeup: always while() not if() — shows deep Java knowledge.
  - Mutex vs binary semaphore: ownership difference is a subtle but important point.
