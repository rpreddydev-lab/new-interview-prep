================================================================
  OBSERVER PATTERN
================================================================

  Category:   Behavioral
  Intent:     Define a one-to-many dependency between objects so that when
              one object changes state, all its dependents are notified and
              updated automatically.
  GoF:        Yes — one of the original 23 patterns.
  Frequency:  VERY HIGH. Foundation of event-driven programming, MVC, reactive
              systems, Spring Events, Kafka, GUI frameworks.
  Also known as: Publish-Subscribe (loosely), Listener, Event, Dependents.

----------------------------------------------------------------
PROBLEM SOLVED
----------------------------------------------------------------

  Object A changes state. Objects B, C, D need to react.
  Without Observer: A holds references to B, C, D — tight coupling.
  A must know about all its dependents. Adding E requires modifying A.

  With Observer: A maintains a list of Observer interfaces.
  B, C, D register with A. A notifies via interface.
  Adding E: just register E — A unchanged.

  Core principle: Open for extension (new observers), closed for modification (Subject).

----------------------------------------------------------------
PARTICIPANTS
----------------------------------------------------------------

  Subject (Observable):
    - Maintains a list of Observer references.
    - subscribe(Observer o) / unsubscribe(Observer o)
    - notifyObservers(data) -- calls update() on all registered observers.

  Observer:
    - Interface with update() method.

  ConcreteSubject:
    - Has state. Calls notifyObservers() when state changes.

  ConcreteObserver:
    - Implements Observer.
    - Reacts to notification in update().

----------------------------------------------------------------
MANUAL IMPLEMENTATION
----------------------------------------------------------------

  // Observer interface
  public interface StockObserver {
      void update(String ticker, double price);
  }

  // Subject interface
  public interface StockSubject {
      void subscribe(StockObserver observer);
      void unsubscribe(StockObserver observer);
      void notifyObservers();
  }

  // Concrete Subject
  public class StockMarket implements StockSubject {
      private final List<StockObserver> observers = new ArrayList<>();
      private final Map<String, Double> prices    = new HashMap<>();

      @Override
      public void subscribe(StockObserver observer) {
          observers.add(observer);
      }

      @Override
      public void unsubscribe(StockObserver observer) {
          observers.remove(observer);
      }

      @Override
      public void notifyObservers() {
          for (StockObserver o : observers) {
              prices.forEach(o::update);   // broadcast all prices
          }
      }

      public void setPrice(String ticker, double price) {
          prices.put(ticker, price);
          notifyObservers();    // notify on state change
      }
  }

  // Concrete Observers
  public class AlertSystem implements StockObserver {
      private final double threshold;
      public AlertSystem(double threshold) { this.threshold = threshold; }

      @Override
      public void update(String ticker, double price) {
          if (price < threshold) {
              System.out.println("ALERT: " + ticker + " dropped to " + price);
          }
      }
  }

  public class Dashboard implements StockObserver {
      @Override
      public void update(String ticker, double price) {
          System.out.printf("Dashboard updated: %s = $%.2f%n", ticker, price);
      }
  }

  // Usage
  StockMarket market = new StockMarket();
  market.subscribe(new AlertSystem(100.0));
  market.subscribe(new Dashboard());

  market.setPrice("AAPL", 95.0);
  // ALERT: AAPL dropped to 95.0
  // Dashboard updated: AAPL = $95.00

  market.setPrice("GOOG", 2800.0);
  // Dashboard updated: GOOG = $2800.00

JAVA BUILT-IN: java.util.Observable (DEPRECATED Java 9+)
----------------------------------------------------------------

  // Old way — DO NOT USE in new code
  class OldStock extends java.util.Observable {
      void setPrice(double price) {
          setChanged();
          notifyObservers(price);
      }
  }

  // Reason deprecated:
  //   1. Observable is a CLASS not interface — prevents flexible inheritance.
  //   2. setChanged() is protected — subclass must call it (odd design).
  //   3. Thread-safety issues — notify and subscribe not synchronized properly.

  Modern alternative: Use EventListener, PropertyChangeSupport, or custom interfaces.

  PropertyChangeSupport (JavaBeans standard):

  public class BeanStock {
      private final PropertyChangeSupport pcs = new PropertyChangeSupport(this);
      private double price;

      public void addPropertyChangeListener(PropertyChangeListener l) {
          pcs.addPropertyChangeListener(l);
      }

      public void setPrice(double newPrice) {
          double oldPrice = this.price;
          this.price = newPrice;
          pcs.firePropertyChange("price", oldPrice, newPrice);
      }
  }

SPRING APPLICATION EVENTS (SPRING'S OBSERVER PATTERN)
----------------------------------------------------------------

  // 1. Define event (DTO for the event data)
  public class OrderCreatedEvent extends ApplicationEvent {
      private final Order order;

      public OrderCreatedEvent(Object source, Order order) {
          super(source);
          this.order = order;
      }

      public Order getOrder() { return order; }
  }

  // 2. Publisher (Subject) — inject ApplicationEventPublisher
  @Service
  public class OrderService {
      @Autowired private ApplicationEventPublisher publisher;

      public void createOrder(Order order) {
          // ... save order ...
          publisher.publishEvent(new OrderCreatedEvent(this, order));
      }
  }

  // 3. Listeners (Observers) — just annotate with @EventListener
  @Component
  public class EmailNotificationListener {
      @EventListener
      public void handleOrderCreated(OrderCreatedEvent event) {
          sendEmail(event.getOrder().getCustomerEmail());
      }
  }

  @Component
  public class InventoryListener {
      @EventListener
      public void handleOrderCreated(OrderCreatedEvent event) {
          reserveStock(event.getOrder());
      }
  }

  @Component
  public class AuditListener {
      @EventListener
      @Async   // fire in background thread
      public void handleOrderCreated(OrderCreatedEvent event) {
          auditLog(event.getOrder());
      }
  }

  // Adding a new listener doesn't change OrderService. Classic OCP.

  // Transactional events — run AFTER the transaction commits:
  @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
  public void handleOrderCreated(OrderCreatedEvent event) { ... }

THREAD SAFETY
----------------------------------------------------------------

  Problem: observers list modified (subscribe/unsubscribe) while notifyObservers() runs.

  Solution 1: CopyOnWriteArrayList (iterates snapshot, no lock needed for iteration):
    private final List<StockObserver> observers = new CopyOnWriteArrayList<>();

  Solution 2: Synchronized + copy before notify:
    private synchronized void notifyObservers() {
        List<StockObserver> copy = new ArrayList<>(observers);
        for (StockObserver o : copy) o.update(...);
    }

  Solution 3: Reactive Streams (Reactor/RxJava):
    Flux<StockPrice> priceStream = ...;
    priceStream.subscribe(price -> dashboard.update(price));

----------------------------------------------------------------
PUSH vs PULL MODEL
----------------------------------------------------------------

  PUSH: Subject sends data with the notification.
    observer.update(String ticker, double price)   // data pushed
    + Observer gets what it needs immediately.
    - Subject must know what data observer needs.

  PULL: Subject sends only "I changed", observer fetches data.
    observer.update(StockMarket source)    // observer calls source.getPrice()
    + Subject decoupled from data format.
    + Observer fetches exactly what it needs.
    - Observer must know subject's API.

  Java PropertyChangeListener uses PULL: event contains source reference.
  Spring ApplicationEvent uses PUSH: event contains the relevant data.

----------------------------------------------------------------
OBSERVER PATTERN VARIATIONS
----------------------------------------------------------------

  1. Event Bus (Guava EventBus):
     Global mediator; objects post/listen without direct references.
     @Subscribe annotation on listener methods.
     eventBus.post(new OrderEvent(order));

  2. Reactive Streams (Project Reactor / RxJava):
     Publisher<T> / Subscriber<T>
     Backpressure support — subscriber controls consumption rate.
     Mono<T>, Flux<T> in Spring WebFlux.

  3. WeakReference Observers:
     Use WeakReference<Observer> to prevent memory leaks.
     Subject won't prevent GC of unsubscribed observers.

  4. Filtered Subscription:
     Observers subscribe with a filter predicate.
     Subject only notifies observers whose filter matches.

----------------------------------------------------------------
MEMORY LEAK TRAP
----------------------------------------------------------------

  Common bug: forget to unsubscribe observers.
  Subject holds strong reference → observer lives as long as subject → memory leak.

  Fix:
  1. Always provide unsubscribe() and call it when done (in close/dispose).
  2. Use WeakReference<Observer> in observer list.
  3. Lifecycle-aware listeners (Android LiveData / Spring auto-unregisters beans).

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------

  Time:  O(n) per notification — n = number of registered observers.
  Space: O(n) — subject stores n observer references.

  Order of notification: undefined unless explicitly ordered.
  If order matters: use sorted list with priority, or chain of responsibility.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: What is the Observer pattern?
  A: A one-to-many dependency: when Subject changes state, all registered
     Observers are automatically notified. Subject is decoupled from observers —
     it only knows the Observer interface. Core of event-driven programming.

  Q: Observer vs Mediator?
  A: Observer: Subject broadcasts to all subscribers (one-to-many, generic).
     Mediator: Object orchestrates interaction between specific colleagues
     (bidirectional, has coordination logic). Observer is simpler/more generic.

  Q: How does Spring implement Observer?
  A: Spring ApplicationEventPublisher + @EventListener. Publisher calls
     publishEvent(). Any bean with @EventListener for that event type is invoked.
     Supports @Async for background listeners, @TransactionalEventListener
     for post-commit events.

  Q: Push vs pull model?
  A: Push: data included in notification (observer doesn't need to query back).
     Pull: only "changed" notification sent; observer pulls needed data from subject.
     Push is simpler. Pull is more flexible — observer decides what data to fetch.

  Q: What's the memory leak problem with Observer?
  A: If observers are not unsubscribed, the subject holds strong references
     preventing garbage collection. Fix: always unsubscribe, use WeakReference,
     or lifecycle-aware components.

  Q: Why was java.util.Observable deprecated?
  A: Class (not interface) prevents flexible inheritance, setChanged() is
     protected causing awkward design, and thread-safety issues.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Know the Spring @EventListener pattern — most common use in Java interviews.
  - Implement StockMarket / event system from scratch when asked.
  - Always mention memory leak risk (unsubscribe) — shows production thinking.
  - Know Reactive Streams (Reactor/RxJava) as the modern evolution.
  - Know CopyOnWriteArrayList for thread-safe observer lists.
