================================================================
  WHEN TO USE DESIGN PATTERNS
================================================================

  Design patterns solve specific recurring OO design problems.
  Knowing WHEN to apply a pattern — and when NOT to — is as important
  as knowing the patterns themselves.

----------------------------------------------------------------
THE CORE RULE: IDENTIFY THE DESIGN PROBLEM FIRST
----------------------------------------------------------------

  Never start with "I'll apply pattern X."
  Start with: "What problem am I solving?"

  Problem                               --> Pattern to consider
  -----------------------------------   ---------------------------------
  Need one shared instance              --> Singleton
  Client shouldn't know concrete class  --> Factory Method / Abstract Factory
  Object has many optional fields       --> Builder
  Too expensive to create from scratch  --> Prototype
  Incompatible interfaces               --> Adapter
  Adding behavior without subclassing   --> Decorator
  Tree structure (part-whole)           --> Composite
  Simplify messy subsystem              --> Facade
  Control access / lazy load / cache    --> Proxy
  Notify multiple objects of state change --> Observer
  Swap algorithms at runtime            --> Strategy
  Skeleton algorithm, vary steps        --> Template Method
  Pass request through chain            --> Chain of Responsibility
  Encapsulate request, support undo     --> Command
  Object behavior changes with state    --> State
  Save and restore state                --> Memento
  Reduce coupling between many objects  --> Mediator

----------------------------------------------------------------
DECISION FRAMEWORK: QUESTIONS TO ASK
----------------------------------------------------------------

  1. Is there a CREATION problem?
       - Do I need to control how many instances exist?
           --> Singleton
       - Do I need to decouple creation from usage?
           --> Factory Method or Abstract Factory
       - Is construction complex, telescoping constructors getting unmanageable?
           --> Builder
       - Is copying cheaper than creating?
           --> Prototype

  2. Is there a STRUCTURAL problem?
       - Do I need to make two incompatible interfaces work together?
           --> Adapter
       - Do I need to add behavior at runtime, not compile-time?
           --> Decorator
       - Do I need to simplify a complex API?
           --> Facade
       - Do I need to control/guard access to an object?
           --> Proxy
       - Do I have tree structures (files/folders, UI components)?
           --> Composite
       - Do I need to share data between many similar objects?
           --> Flyweight

  3. Is there a BEHAVIORAL problem?
       - Do I have many objects needing to react to changes in another?
           --> Observer
       - Do I need interchangeable algorithms?
           --> Strategy
       - Do I have an algorithm skeleton but want to vary steps?
           --> Template Method
       - Do I need undo/redo support?
           --> Command + Memento
       - Does object behavior depend on internal state?
           --> State
       - Do I have many interconnected objects creating tight coupling?
           --> Mediator
       - Do I need to process a request through a sequence of handlers?
           --> Chain of Responsibility

----------------------------------------------------------------
THE YAGNI PRINCIPLE (WHEN NOT TO USE PATTERNS)
----------------------------------------------------------------

  YAGNI = "You Aren't Gonna Need It."

  Rule: Don't add abstraction until you actually need it.
  Applying a pattern "just in case" adds complexity without value.

  Common over-engineering traps:
    - Singleton everywhere:
        Creates hidden global state, breaks testability, violates DI principle.
    - Factory for trivial objects:
        If you only ever create one type, a factory is unnecessary indirection.
    - Observer for simple one-to-one communication:
        Use a direct method call if there's only one listener.
    - Builder for a 2-field object:
        Unnecessary verbosity; just use a constructor.

  The Rule of Three (Martin Fowler):
    First time: just write the code.
    Second time: note the repetition.
    Third time: refactor and apply a pattern.

----------------------------------------------------------------
WHEN PATTERNS EMERGE NATURALLY (REFACTORING TO PATTERNS)
----------------------------------------------------------------

  Smell                                          Pattern to introduce
  -------------------------------------------    ----------------------------------
  Telescoping constructors (many overloads)      Builder
  switch on type/class everywhere                Strategy or Factory Method
  Tight coupling to concrete implementations     Dependency Injection + Factory/Abstract Factory
  Class explosion from subclass combinations     Decorator or Bridge
  Large class doing too many things              Facade or Command
  Duplicated algorithm code in subclasses        Template Method
  Listeners needing manual wiring                Observer
  Object behavior changing based on field value  State
  Cross-cutting concerns (logging, auth, cache)  Proxy or Decorator

PATTERNS IN JAVA STANDARD LIBRARY (LEARN TO RECOGNIZE)
----------------------------------------------------------------

  Pattern           Java Standard Library Example
  ----------------  -----------------------------------------
  Singleton         Runtime.getRuntime(), Desktop.getDesktop()
  Factory Method    Calendar.getInstance(), Border.create*(...)
  Abstract Factory  DocumentBuilderFactory (XML parsing)
  Builder           StringBuilder, ProcessBuilder, Stream.Builder
  Prototype         Object.clone()
  Adapter           Arrays.asList() (array → List), InputStreamReader
  Decorator         BufferedReader(FileReader), Collections.unmodifiableList()
  Composite         Component tree in Swing (JPanel > JButton)
  Proxy             Reflection-based Proxy: java.lang.reflect.Proxy
  Flyweight         Integer.valueOf(-128..127) cache, String.intern()
  Iterator          java.util.Iterator, Iterable / for-each
  Observer          java.util.Observable (deprecated), PropertyChangeListener
  Strategy          Comparator<T>, Executor implementations
  Template Method   AbstractList (implements contains in terms of iterator)
  Command           Runnable, Callable, FutureTask
  Chain of Resp.    javax.servlet.Filter chain
  State             javax.faces.lifecycle.Lifecycle, StateMachine
  Visitor           javax.lang.model.element.ElementVisitor

----------------------------------------------------------------
APPLYING PATTERNS IN SYSTEM DESIGN INTERVIEWS
----------------------------------------------------------------

  When discussing system design, mention patterns to show architectural awareness.

  Scenario                               Patterns to mention
  ------------------------------------   ----------------------------------------
  Designing a notification service       Observer, Strategy (channel: SMS/email/push)
  Designing an order processing system   State (order lifecycle), Command (operations), Chain (validation)
  Designing a payment gateway            Strategy (payment methods), Facade (simplify third-party APIs)
  Designing a cache layer                Proxy (transparent caching), Singleton (cache manager)
  Designing a report generator           Template Method (skeleton), Factory (report type), Strategy (format)
  Designing a plugin system              Factory Method, Chain of Responsibility
  Designing a UI form builder            Builder, Composite (nested form elements)

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Can you overuse design patterns?
  A: Yes — over-engineering. Patterns add abstraction overhead. Use them when
     they solve a real recurring problem, not just to show knowledge.
     Simpler code is always preferable when patterns add no value.

  Q: How do you decide which pattern to use?
  A: Identify the problem first. Is it about creation, composition, or
     communication? Then map to the pattern that solves that specific force.
     Recognize the pattern from "code smells" like telescoping constructors,
     switch statements on type, or tight coupling.

  Q: What's the difference between recognizing and applying patterns?
  A: Recognizing is reading existing code and identifying patterns in use.
     Applying is choosing a pattern when designing new code.
     Both require understanding INTENT, not just structure.

  Q: Is it OK to modify a GoF pattern?
  A: Yes — patterns are guidelines, not strict rules. Adapt them to your
     language, framework, and context. The intent matters; the exact structure
     can vary.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - In coding interviews: "I'd use Builder here because construction has many optional fields."
  - In design interviews: "The Observer pattern fits — many components need to react to state changes."
  - Always explain WHY you chose the pattern, not just which one.
  - Mention trade-offs: "Singleton is convenient but creates hidden global state — in production I'd prefer DI."
  - Know that Spring heavily relies on Proxy, Template Method, and Observer — expect those in Spring interviews.
