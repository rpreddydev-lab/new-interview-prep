================================================================
gRPC vs REST vs GraphQL - DEEP COMPARISON
================================================================

----------------------------------------------------------------
1. FOUNDATIONAL PHILOSOPHY
----------------------------------------------------------------

REST (Representational State Transfer)
  - Resource-oriented: every "thing" has a URL
  - Stateless: no session state on server between requests
  - Leverages HTTP verbs semantically (GET, POST, PUT, DELETE, PATCH)
  - Returns whatever format client wants (usually JSON)
  - Created by Roy Fielding in his 2000 PhD dissertation

GraphQL
  - Query language for APIs, not an architecture style
  - Client specifies EXACTLY what data it needs (no over/under-fetching)
  - Single endpoint: POST /graphql
  - Schema-first using SDL (Schema Definition Language)
  - Created by Facebook in 2012, open-sourced in 2015

gRPC
  - Action-oriented: define "services" with "methods" (procedures)
  - Contract-first using .proto files
  - Binary protocol over HTTP/2
  - Code generation for client and server
  - Created by Google, open-sourced in 2015

----------------------------------------------------------------
2. PROTOCOL & TRANSPORT LAYER
----------------------------------------------------------------

REST:
  - HTTP/1.1 (mostly), HTTP/2 supported but rarely used fully
  - Text-based: headers and body are human-readable
  - One request per TCP connection (HTTP/1.1) or multiplexed (HTTP/2)
  - Connection overhead is significant for many small requests

GraphQL:
  - HTTP/1.1 or HTTP/2 (typically HTTP/1.1 in practice)
  - JSON over HTTP POST (or GET for queries)
  - Same connection overhead as REST
  - Subscriptions use WebSocket for real-time

gRPC:
  - HTTP/2 exclusively (this is a hard requirement)
  - Binary framing with HEADERS + DATA frames
  - Full multiplexing: thousands of concurrent streams on 1 TCP connection
  - Header compression via HPACK (~85% reduction in header size)
  - Native bidirectional streaming built into the protocol

  Comparison Table:
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │ Feature      │ REST         │ GraphQL      │ gRPC         │
  ├──────────────┼──────────────┼──────────────┼──────────────┤
  │ Protocol     │ HTTP/1.1+    │ HTTP/1.1+    │ HTTP/2 only  │
  │ Format       │ JSON/XML     │ JSON         │ Protobuf     │
  │ Streaming    │ SSE/WS       │ WS (subscr.) │ Native (4)   │
  │ Multiplexing │ No (HTTP1.1) │ No           │ Yes          │
  │ Header Comp  │ No           │ No           │ Yes (HPACK)  │
  └──────────────┴──────────────┴──────────────┴──────────────┘

----------------------------------------------------------------
3. SERIALIZATION FORMAT
----------------------------------------------------------------

REST - JSON:
  - Human-readable text format
  - No schema enforcement at protocol level (only via OpenAPI/Swagger)
  - Field names transmitted with every request (redundant data)
  - Parsing is CPU-intensive (text → object)
  - Example JSON size for a simple order: ~200 bytes
    {
      "orderId": "ORD-12345",
      "customerId": "CUST-678",
      "productId": "PROD-999",
      "quantity": 2,
      "status": "PENDING"
    }

GraphQL - JSON:
  - Same JSON format as REST for responses
  - Query itself is also text-based
  - Flexible: response shape matches query shape exactly
  - Still CPU-intensive JSON parsing

gRPC - Protocol Buffers:
  - Binary encoding: field number + wire type + value
  - Field names NOT transmitted over wire (field numbers used instead)
  - Same order as binary: ~50-60 bytes for same data as above
  - Significantly faster encode/decode

  Wire format example:
    Field 1 (orderId), type=string: 0x0A 0x09 "ORD-12345"
    Field 2 (quantity), type=int32: 0x10 0x02
    → compact, no field name, no quotes

  Performance Comparison:
  ┌──────────────┬─────────────────┬──────────────────┐
  │              │ JSON (REST)     │ Protobuf (gRPC)  │
  ├──────────────┼─────────────────┼──────────────────┤
  │ Payload size │ ~200 bytes      │ ~50 bytes        │
  │ Serialize    │ ~1000 ns/op     │ ~100 ns/op       │
  │ Deserialize  │ ~3000 ns/op     │ ~400 ns/op       │
  │ Human read   │ ✅ Yes          │ ❌ No            │
  │ Schema       │ Optional        │ Required         │
  └──────────────┴─────────────────┴──────────────────┘

----------------------------------------------------------------
4. API CONTRACT & SCHEMA
----------------------------------------------------------------

REST:
  - No built-in schema enforcement
  - OpenAPI (Swagger) is widely used but optional and often out of sync
  - Client and server can drift independently
  - Breaking changes discovered at runtime
  - Versioning done via URL (v1/orders, v2/orders) or headers

GraphQL:
  - SDL (Schema Definition Language) defines types, queries, mutations
  - Schema is the single source of truth, introspective at runtime
  - Client queries are validated against schema before execution
  - Schema versioning: additive changes are non-breaking, deprecation
    annotations mark fields being removed
  - Single endpoint, no URL versioning needed

gRPC:
  - .proto file is the strict, strongly-typed contract
  - Code is generated from .proto — client and server guaranteed to match
  - Field numbering enables backward/forward compatibility
  - Changes must follow rules (never reuse/remove field numbers)
  - Service versioning via package namespacing (order.v1, order.v2)

  CONTRACT STRENGTH:
    REST (weakest) < GraphQL (medium) < gRPC (strongest)

----------------------------------------------------------------
5. OVER-FETCHING AND UNDER-FETCHING
----------------------------------------------------------------

Over-fetching (getting more data than needed):
  REST:    GET /users/123 returns ALL user fields even if you only
           need the name. You always get the full resource.
  GraphQL: SOLVED - client specifies exact fields needed
  gRPC:    Still possible (response message has all fields), but
           less wasteful due to binary compression + field omission

Under-fetching (needing multiple requests):
  REST:    GET /order/123, then GET /user/456, then GET /product/789
           = 3 network round trips (N+1 problem)
  GraphQL: SOLVED - single query can fetch order + user + product
  gRPC:    Same issue as REST; each service call is one RPC
           Solved at architecture level with aggregating services

Practical Impact:
  - Mobile apps: GraphQL wins for bandwidth efficiency
  - Microservices: gRPC wins (binary, streaming, contracts)
  - Internal dashboards: GraphQL avoids building multiple REST endpoints

----------------------------------------------------------------
6. STREAMING CAPABILITIES
----------------------------------------------------------------

REST:
  - Server-Sent Events (SSE): server pushes text events to client
  - WebSocket: bidirectional, but not part of REST
  - Long-polling: hacky, creates load
  - No native streaming in HTTP/1.1 for requests

GraphQL:
  - Subscriptions over WebSocket (real-time notifications)
  - No native request streaming (queries are atomic)
  - Third-party libs (Apollo, Relay) handle subscription complexity

gRPC:
  - FOUR NATIVE STREAMING MODES:
    1. Unary:              request → response
    2. Server Streaming:   request → stream of responses
    3. Client Streaming:   stream of requests → response
    4. Bidirectional:      stream of requests ↔ stream of responses
  - All over a single HTTP/2 connection
  - No additional protocol needed (unlike WebSocket for GraphQL subscriptions)
  - Back-pressure: flow control built into HTTP/2

----------------------------------------------------------------
7. CODE GENERATION
----------------------------------------------------------------

REST:
  - No native code generation
  - OpenAPI Generator can produce client SDKs from Swagger specs
  - Often manually maintained, drift between spec and implementation

GraphQL:
  - GraphQL Code Generator can produce typed queries/mutations
  - Client-side typed hooks for React, Angular, etc.
  - Server-side resolvers can be generated with types
  - Better than REST but not as integrated as gRPC

gRPC:
  - Code generation is MANDATORY and CENTRAL to the workflow
  - protoc compiler generates:
    * Message classes (fully serializable data objects)
    * Service base class (server implements this)
    * Client stub (client uses this to call server)
  - Generated code is always in sync with .proto definition
  - Multi-language: same .proto generates Java, Go, Python, etc.
  - No manual SDK maintenance required

----------------------------------------------------------------
8. BROWSER SUPPORT
----------------------------------------------------------------

REST:    ✅ Native browser support (XMLHttpRequest, fetch API)
GraphQL: ✅ Native browser support (POST requests with JSON)
gRPC:    ❌ Browsers do NOT support HTTP/2 trailers (required by gRPC)

gRPC Browser Workarounds:
  1. gRPC-Web: A slightly modified protocol that works in browsers
     - Requires Envoy proxy or similar to translate gRPC-Web to gRPC
     - Limited: only unary and server streaming (no client streaming)

  2. gRPC Gateway: Transcodes REST/JSON requests to gRPC
     - Browser sends normal REST/JSON
     - Gateway converts to gRPC and calls the service
     - Response converted back to JSON

  3. Connect Protocol (new): Works in browsers without proxy

----------------------------------------------------------------
9. ERROR HANDLING
----------------------------------------------------------------

REST:
  - HTTP status codes (200, 400, 404, 500, etc.)
  - Error body is custom JSON (no standard)
  - Problem Details (RFC 7807) is a standard but rarely followed
  - Error meaning varies by team

GraphQL:
  - Always returns HTTP 200 (even on errors!)
  - Errors are in the "errors" field of response body:
    { "data": null, "errors": [{"message": "Not found", "path": ["user"]}] }
  - Partial success: some fields succeed, some have errors
  - Makes monitoring harder (no HTTP 4xx/5xx to alert on)

gRPC:
  - Predefined status codes (similar to HTTP but richer):
    * OK (0), CANCELLED (1), UNKNOWN (2), INVALID_ARGUMENT (3)
    * NOT_FOUND (5), ALREADY_EXISTS (6), PERMISSION_DENIED (7)
    * RESOURCE_EXHAUSTED (8), FAILED_PRECONDITION (9)
    * ABORTED (10), DEADLINE_EXCEEDED (4), UNIMPLEMENTED (12)
    * INTERNAL (13), UNAVAILABLE (14), UNAUTHENTICATED (16)
  - Rich error details via google.rpc.Status + error details proto
  - Consistent across all languages and services

----------------------------------------------------------------
10. TOOLING & ECOSYSTEM
----------------------------------------------------------------

REST:
  - Postman, Insomnia, curl - universally known
  - Swagger UI for interactive docs
  - Mature ecosystem, every language supports HTTP
  - Browser DevTools show all requests

GraphQL:
  - GraphiQL / Apollo Studio - built-in playground
  - Good introspection support
  - Apollo Client (JS), urql (JS), gqlient (Go)

gRPC:
  - grpcurl (curl-like CLI for gRPC)
  - Postman (supports gRPC as of v9.7)
  - BloomRPC, Kreya - GUI clients
  - gRPC server reflection needed for dynamic tools
  - Less mature tooling compared to REST

----------------------------------------------------------------
11. PERFORMANCE BENCHMARKS (GENERAL RULE OF THUMB)
----------------------------------------------------------------

Typical benchmarks (varies by payload and use case):

  REST/JSON vs gRPC/Protobuf:
  - Payload size:     gRPC is 5-10x smaller
  - Latency:          gRPC is 2-7x faster for small payloads
  - Throughput:       gRPC handles 5-10x more requests per second
  - CPU usage:        gRPC uses less CPU due to binary serialization

  Note: For large payloads (images, large JSON), differences narrow.
  For tiny payloads (ping-like), gRPC overhead is proportionally larger.

----------------------------------------------------------------
12. DECISION GUIDE - WHICH TO USE?
----------------------------------------------------------------

Use REST when:
  ✅ Building a public API consumed by unknown third-party clients
  ✅ Developers need simple curl/browser access for debugging
  ✅ CRUD-heavy resources (users, products, orders)
  ✅ Team has limited infrastructure expertise
  ✅ Cacheability is important (GET requests cached by CDN/browser)

Use GraphQL when:
  ✅ Client has complex, variable data requirements (dashboards, mobile)
  ✅ Multiple frontend teams need different data shapes
  ✅ Reducing over-fetching/under-fetching is critical
  ✅ BFF (Backend for Frontend) pattern
  ✅ Rapid frontend development without backend changes

Use gRPC when:
  ✅ Microservice-to-microservice internal communication
  ✅ High throughput / low latency requirements
  ✅ Streaming (real-time, large data, IoT)
  ✅ Polyglot environment (Java backend, Go sidecar, Python ML)
  ✅ Strict API contracts required (financial, healthcare systems)
  ✅ Bandwidth constrained environments (mobile, embedded)

Common Hybrid Patterns:
  - gRPC internally + REST Gateway externally (gRPC-Gateway)
  - GraphQL for client-facing BFF + gRPC for internal microservices
  - REST for public APIs + gRPC for data pipeline microservices

----------------------------------------------------------------
13. INTERVIEW ANSWER TEMPLATE
----------------------------------------------------------------

"REST, GraphQL, and gRPC solve different problems at different
 layers. REST is resource-oriented, human-friendly, and ideal
 for public APIs. GraphQL lets clients request exactly the data
 they need, solving over/under-fetching for complex frontend needs.
 gRPC is contract-first, binary, and HTTP/2 native — making it
 the best choice for high-performance internal microservice
 communication, especially when you need streaming or cross-language
 type safety.

 In practice, many systems use all three: gRPC internally between
 microservices, a REST/GraphQL gateway facing external clients,
 and GraphQL for mobile/web frontends that need flexible data fetching."
