================================================================
PROTOCOL BUFFERS (PROTOBUF) - DEEP DIVE
================================================================

----------------------------------------------------------------
1. WHAT ARE PROTOCOL BUFFERS?
----------------------------------------------------------------

Protocol Buffers (protobuf) is Google's language-neutral,
platform-neutral, extensible mechanism for serializing structured
data. It is the default serialization format for gRPC.

Analogy: Think of protobuf like XML or JSON, but:
  - Smaller (binary, not text)
  - Faster to encode/decode
  - Strongly typed with a defined schema
  - Language agnostic code generation

Key distinction: The schema (.proto file) is the contract.
The binary data is just the encoded form. You ALWAYS need
the .proto to decode a protobuf message.

----------------------------------------------------------------
2. WHY PROTOBUF INSTEAD OF JSON/XML?
----------------------------------------------------------------

Problem with JSON/XML:
  1. Field names repeated in EVERY message (redundant bytes)
  2. No schema enforcement at the protocol level
  3. Text parsing is slow (string → number conversion, etc.)
  4. No native type system (JSON has only string, number, bool, null, array, object)
  5. XML is extremely verbose

Protobuf Solution:
  1. Field NUMBERS used instead of field names on wire (1 byte vs "productId" = 9 bytes)
  2. .proto file IS the schema — enforced by generated code
  3. Binary encoding — no text parsing
  4. Rich type system: int32, int64, float, double, bool, string, bytes, enums, nested messages
  5. Compact and self-describing with field numbers

----------------------------------------------------------------
3. WIRE FORMAT DEEP DIVE
----------------------------------------------------------------

Every protobuf field on the wire is encoded as:
  [ Tag ] [ Value ]
  
  Tag = (field_number << 3) | wire_type

Wire Types:
  ┌───────────┬────────┬─────────────────────────────────┐
  │ Wire Type │ Value  │ Used For                        │
  ├───────────┼────────┼─────────────────────────────────┤
  │ Varint    │   0    │ int32, int64, uint32, uint64,   │
  │           │        │ sint32, sint64, bool, enum      │
  ├───────────┼────────┼─────────────────────────────────┤
  │ 64-bit    │   1    │ fixed64, sfixed64, double       │
  ├───────────┼────────┼─────────────────────────────────┤
  │ Len-delim │   2    │ string, bytes, embedded msgs,  │
  │           │        │ packed repeated fields          │
  ├───────────┼────────┼─────────────────────────────────┤
  │ 32-bit    │   5    │ fixed32, sfixed32, float        │
  └───────────┴────────┴─────────────────────────────────┘

Example encoding:
  message Product {
    string name = 1;    // field 1
    int32  price = 2;   // field 2
  }
  
  For: name="Laptop", price=999
  
  Field 1 (name), wire type=2 (len-delim):
    Tag = (1 << 3) | 2 = 0x0A
    Length = 6 (bytes in "Laptop")
    Value = 0x4C 0x61 0x70 0x74 0x6F 0x70
    → 0x0A 0x06 4C 61 70 74 6F 70

  Field 2 (price), wire type=0 (varint):
    Tag = (2 << 3) | 0 = 0x10
    Value = 999 in varint = 0xE7 0x07
    → 0x10 0xE7 0x07

  Total: 10 bytes vs JSON {"name":"Laptop","price":999} = 27 bytes

Varint Encoding (Variable Length Integer):
  - Uses 7 bits per byte for data, 1 bit as "more bytes follow" flag
  - Small numbers (0-127) fit in 1 byte
  - Large numbers use multiple bytes
  - int32 uses 1-5 bytes (vs always 4 bytes for fixed int)
  - Negative numbers: use sint32 (zigzag) to avoid 10-byte encoding

ZigZag Encoding for Negative Numbers:
  sint32 uses ZigZag: 0→0, -1→1, 1→2, -2→3, 2→4, ...
  Formula: (n << 1) ^ (n >> 31)
  This ensures small negative numbers are also small on the wire.

----------------------------------------------------------------
4. SCALAR FIELD TYPES
----------------------------------------------------------------

Integer Types:
  int32    - Standard 32-bit. Negative values use 10 bytes (use sint32 for negatives)
  int64    - Standard 64-bit. Same issue with negatives.
  uint32   - Unsigned 32-bit. Cannot hold negatives.
  uint64   - Unsigned 64-bit. Cannot hold negatives.
  sint32   - Signed 32-bit with ZigZag encoding. Efficient for negatives.
  sint64   - Signed 64-bit with ZigZag encoding.
  fixed32  - Always 4 bytes. Use when value is usually > 2^28.
  fixed64  - Always 8 bytes. Use when value is usually > 2^56.
  sfixed32 - Signed fixed 32-bit.
  sfixed64 - Signed fixed 64-bit.

Floating Point:
  float    - 32-bit IEEE 754
  double   - 64-bit IEEE 754

Other:
  bool     - true/false, encoded as 0 or 1
  string   - UTF-8 encoded text, max 2^32 bytes
  bytes    - Arbitrary byte sequence, max 2^32 bytes

Choosing the right integer type:
  - Values always positive → uint32/uint64
  - Values rarely negative → int32/int64
  - Values frequently negative → sint32/sint64
  - Values always large (>268M) → fixed32/fixed64

----------------------------------------------------------------
5. COMPOSITE TYPES
----------------------------------------------------------------

Enums:
  enum OrderStatus {
    ORDER_STATUS_UNSPECIFIED = 0;  // ALWAYS have a zero value
    ORDER_STATUS_PENDING     = 1;
    ORDER_STATUS_CONFIRMED   = 2;
    ORDER_STATUS_SHIPPED     = 3;
    ORDER_STATUS_DELIVERED   = 4;
    ORDER_STATUS_CANCELLED   = 5;
  }
  
  Rules:
  - First enum value MUST be 0 (default value)
  - Use prefix (ORDER_STATUS_) to avoid naming collisions
  - Unknown enum values preserved as integer in proto3
  - Enums can be nested inside messages

Nested Messages:
  message Order {
    string order_id = 1;
    Address shipping_address = 2;  // nested message
    
    message Address {
      string street = 1;
      string city   = 2;
      string zip    = 3;
    }
  }

Repeated Fields (Arrays/Lists):
  message Order {
    repeated OrderItem items = 1;  // list of items
  }
  
  message OrderItem {
    string product_id = 1;
    int32  quantity   = 2;
  }
  
  - Default is empty list (not null)
  - In proto3, repeated fields use "packed" encoding for scalar types
    (all values concatenated with a single tag)

Maps:
  message ProductCatalog {
    map<string, Product> products = 1;  // key must be integer or string
  }
  
  Equivalent to:
    repeated KeyValue { string key = 1; Product value = 2; }
  
  Map rules:
  - Keys: int32, int64, uint32, uint64, sint32, sint64, fixed32,
    fixed64, sfixed32, sfixed64, bool, string
  - Keys CANNOT be: float, double, bytes, enum, or message
  - Maps cannot be repeated
  - Map field order is not guaranteed

Oneof (Union/Variant):
  message SearchResult {
    oneof result {
      Product product       = 1;
      Category category     = 2;
      string   error_message = 3;
    }
    string search_query = 4;  // can be outside oneof
  }
  
  - Only one field in oneof can be set at a time
  - Setting one clears the others
  - Useful for discriminated unions
  - Cannot have repeated fields in oneof

Any:
  import "google/protobuf/any.proto";
  
  message Response {
    google.protobuf.Any details = 1;  // can hold any message type
  }
  
  - Packs type URL + serialized bytes
  - Useful for plugin-style APIs
  - Requires careful handling to unpack correctly

Well-Known Types (pre-built messages from Google):
  google.protobuf.Timestamp     - Date/time (seconds + nanos)
  google.protobuf.Duration      - Time duration
  google.protobuf.StringValue   - Nullable string (wrapper)
  google.protobuf.Int32Value    - Nullable int32 (wrapper)
  google.protobuf.BoolValue     - Nullable bool (wrapper)
  google.protobuf.FieldMask     - Partial update field specification
  google.protobuf.Empty         - No-field message (for void RPC returns)
  google.protobuf.Struct        - Dynamic JSON-like structure

6. PROTO2 vs PROTO3
----------------------------------------------------------------

  Feature              | proto2          | proto3
  ---------------------|-----------------|-----------------------------
  Field labels         | required/optional/repeated | optional/repeated
  Default values       | Custom or type default | Type default always
  Field presence       | Yes (has_field) | No (proto3 optional added back)
  Enums                | Closed          | Open (unknown values kept)
  Groups               | Yes (deprecated)| No
  Extensions           | Yes             | No (use Any instead)
  Service definitions  | Yes             | Yes
  Required fields      | Yes (BAD!)      | No (required removed)
  Syntax line          | syntax="proto2";| syntax="proto3";

Required fields (proto2) — WHY THEY ARE BAD:
  - Marked with 'required' keyword
  - If a required field is missing, parsing fails with an exception
  - This creates a deployment nightmare: you MUST update all servers
    before all clients, making rolling deployments impossible
  - This is why proto3 removed 'required' entirely

Proto3 Optional (added in 2020):
  - Proto3 originally lost field presence (no way to tell if int32=0
    means "not set" or "actually zero")
  - The optional keyword was added back to proto3
  - message Foo { optional int32 x = 1; }
  - Now has_x() method is available

----------------------------------------------------------------
7. FIELD NUMBERS
----------------------------------------------------------------

Rules:
  - Field numbers 1-15 use 1 byte for tag (most common fields)
  - Field numbers 16-2047 use 2 bytes for tag
  - Maximum field number: 2^29 - 1 = 536,870,911
  - Reserved range: 19000-19999 (protobuf internal use)
  - You can NEVER change a field number once deployed
  - You can NEVER reuse a deleted field number

Best Practices:
  - Reserve fields 1-15 for frequently-used fields
  - Use reserved keyword for deleted fields to prevent accidental reuse:
    
    message Order {
      reserved 3, 7;                    // numeric field numbers
      reserved "legacy_status", "flag"; // field names
      string order_id = 1;
      // field 3 was "customer_name" - now deleted
    }

8. PACKAGES AND IMPORTS
----------------------------------------------------------------

Package Declaration:
  syntax = "proto3";
  package com.company.order.v1;
  
  - Prevents naming conflicts between message types
  - Maps to Java package, Go package, etc.
  - Best practice: include version (v1, v2) in package name

Imports:
  import "google/protobuf/timestamp.proto";
  import "google/protobuf/empty.proto";
  import "common/money.proto";  // custom shared types
  
  - Public imports re-export imported definitions
  - Weak imports: optional dependency (avoid in production)
  - Import paths are relative to proto search paths given to protoc

Options:
  option java_package = "com.company.order.v1";
  option java_outer_classname = "OrderProto";
  option java_multiple_files = true;  // generate separate .java files
  option go_package = "github.com/company/order/v1";
  option optimize_for = SPEED;  // SPEED, CODE_SIZE, or LITE_RUNTIME

10. PROTOBUF BEST PRACTICES
----------------------------------------------------------------

Naming Conventions:
  - Message names: PascalCase (OrderItem, CustomerProfile)
  - Field names: snake_case (order_id, customer_name)
  - Enum type names: PascalCase (OrderStatus)
  - Enum value names: UPPER_SNAKE_CASE with prefix (ORDER_STATUS_PENDING)
  - Service names: PascalCase (OrderService)
  - RPC method names: PascalCase (CreateOrder, ListOrders)

Versioning Strategy:
  - Never break backward compatibility in place
  - Use package versioning: com.company.order.v1 → v2
  - Follow additive-only rule for v1 fields
  - Create v2 when breaking changes needed

Common Mistakes:
  ❌ Reusing field numbers for different fields
  ❌ Changing field types (int32 → string)
  ❌ Removing fields without marking them reserved
  ❌ Using too-large field numbers for common fields (1-15 are cheapest)
  ❌ Using float for currency (use int64 cents or google.type.Money)
  ❌ Not prefixing enum values (name collisions)

----------------------------------------------------------------
11. INTERVIEW KEY POINTS
----------------------------------------------------------------

Q: Why does protobuf use field numbers instead of field names?
A: Field numbers encode to 1-2 bytes on the wire, while field names
   can be 5-20+ bytes each. This makes payloads significantly smaller.
   It also enables forward/backward compatibility: if the schema adds
   a new field, old decoders just skip unknown field numbers.

Q: What happens when protobuf encounters an unknown field?
A: Proto3 preserves unknown fields (added in proto3.5+).
   The parser saves them and re-serializes them if the message
   is re-serialized. This enables forward compatibility.

Q: Can you have null values in protobuf?
A: Proto3 scalar fields have default values (0, "", false) and
   cannot distinguish "not set" from "set to default". To represent
   null, use the optional keyword (proto3 optional) or wrapper types
   (google.protobuf.StringValue). Better yet, redesign to avoid null.
