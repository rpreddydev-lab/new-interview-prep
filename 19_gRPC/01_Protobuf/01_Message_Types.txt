================================================================
PROTOBUF MESSAGE TYPES - IN DEPTH
================================================================

----------------------------------------------------------------
1. MESSAGE DEFINITION FUNDAMENTALS
----------------------------------------------------------------

A message is the fundamental unit in protobuf. It's like a class
or struct that defines a structured data type.

Basic syntax:
  message MessageName {
    type field_name = field_number;
  }

Every field has:
  1. Type (scalar, message, enum, etc.)
  2. Name (unique within message, snake_case)
  3. Field number (unique within message, immutable once assigned)

Example:
  message Employee {
    string   employee_id  = 1;
    string   first_name   = 2;
    string   last_name    = 3;
    string   email        = 4;
    int32    department_id = 5;
    bool     is_active    = 6;
  }

----------------------------------------------------------------
2. SCALAR VALUE TYPES
----------------------------------------------------------------

NUMERIC TYPES (choose carefully for size vs performance):

int32 / int64:
  - Standard signed integers
  - Varint encoded (variable length: small numbers → fewer bytes)
  - Negative values encoded as large varints (10 bytes for int32!)
  - Use for: IDs, counts, quantities (non-negative preferred)

uint32 / uint64:
  - Unsigned integers
  - Cannot hold negative values
  - Efficient for bit flags, hash values, lengths

sint32 / sint64:
  - Signed integers with ZigZag encoding
  - MUCH more efficient for negative numbers
  - Use when: values can be negative (temperature, balance changes)
  
  ZigZag mapping:
    0 → 0, -1 → 1, 1 → 2, -2 → 3, 2 → 4, -3 → 5, 3 → 6
    Negative values become small positive numbers before varint encoding

fixed32 / fixed64:
  - Always exactly 4/8 bytes
  - No varint overhead
  - Use when: value is usually large (> 2^28 for fixed32)
  - Good for: Unix timestamps in seconds, GUIDs, hash values

sfixed32 / sfixed64:
  - Signed version of fixed32/fixed64

float / double:
  - IEEE 754 floating point
  - Never use for money/currency (precision loss!)
  - Use for: coordinates, percentages, ML weights, scientific data

bool:
  - Encodes as varint 0 (false) or 1 (true)
  - Uses 1 byte on the wire

STRING AND BYTES:

string:
  - UTF-8 encoded text
  - Length-delimited (prefix with byte count)
  - Empty string is the default (not null)

bytes:
  - Raw binary data
  - Same wire format as string but treated as opaque bytes
  - Use for: images, files, encrypted data, custom binary formats

----------------------------------------------------------------
3. FIELD LABELS
----------------------------------------------------------------

In proto3, there are two types of fields:

Singular (default, no keyword needed):
  string name = 1;   // zero or one occurrence

Repeated:
  repeated string tags = 1;   // zero or more occurrences (list/array)

Optional (proto3 optional):
  optional string middle_name = 1;  // has presence tracking

The old proto2 "required" label was removed in proto3 — it created
deployment hazards and is considered an anti-pattern.

----------------------------------------------------------------
4. REPEATED FIELDS (ARRAYS/LISTS)
----------------------------------------------------------------

message ShoppingCart {
  string           cart_id = 1;
  repeated CartItem items  = 2;  // 0 or more items
}

message CartItem {
  string product_id = 1;
  int32  quantity   = 2;
  int64  price_cents = 3;
}

Packed encoding:
  In proto3, scalar repeated fields use packed encoding by default:
  - All values stored together with a single tag
  - More efficient than repeating the tag for each value
  
  Example: repeated int32 scores = 1; with values [1, 2, 3]
  Packed:   tag(1) + length(3) + varint(1) + varint(2) + varint(3)
  Unpacked: tag(1)+varint(1) + tag(1)+varint(2) + tag(1)+varint(3)

Java API for repeated fields:
  // Build
  ShoppingCart cart = ShoppingCart.newBuilder()
      .setCartId("CART-001")
      .addItems(CartItem.newBuilder()
          .setProductId("P1")
          .setQuantity(2)
          .setPriceCents(999)
          .build())
      .addItems(CartItem.newBuilder()
          .setProductId("P2")
          .setQuantity(1)
          .setPriceCents(2499)
          .build())
      .build();
  
  // Read
  List<CartItem> items = cart.getItemsList();       // unmodifiable list
  int count = cart.getItemsCount();                  // size
  CartItem first = cart.getItems(0);                 // by index
  
  // Modify (via builder)
  ShoppingCart.Builder builder = cart.toBuilder();
  builder.addItems(newItem);
  builder.removeItems(0);  // remove by index
  builder.clearItems();     // remove all

5. NESTED MESSAGES
----------------------------------------------------------------

Messages can be nested inside other messages:

message Order {
  string order_id = 1;
  
  // Can reference nested type by full path
  ShippingInfo shipping = 2;
  BillingInfo  billing  = 3;
  
  // Nested message defined inside Order
  message ShippingInfo {
    string tracking_number = 1;
    Address destination    = 2;
    
    // Further nested
    message Address {
      string line1       = 1;
      string line2       = 2;
      string city        = 3;
      string state       = 4;
      string postal_code = 5;
      string country     = 6;
    }
  }
  
  message BillingInfo {
    string invoice_number = 1;
    int64  amount_cents   = 2;
  }
}

Accessing nested type from outside:
  Order.ShippingInfo.Address address = Order.ShippingInfo.Address.newBuilder()
      .setLine1("123 Main St")
      .setCity("San Francisco")
      .build();

When to use nested vs top-level messages:
  - Nest when: message is ONLY meaningful in context of outer message
  - Top-level when: message is reused across multiple other messages

----------------------------------------------------------------
6. ENUM TYPES
----------------------------------------------------------------

Enums represent a fixed set of values:

// Top-level enum
enum PaymentStatus {
  PAYMENT_STATUS_UNSPECIFIED = 0;  // Required zero value
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_COMPLETED   = 2;
  PAYMENT_STATUS_FAILED      = 3;
  PAYMENT_STATUS_REFUNDED    = 4;
}

// Enum with aliases (allow_alias option)
enum PaymentStatusAliased {
  option allow_alias = true;
  PAYMENT_STATUS_UNSPECIFIED = 0;
  PAYMENT_STATUS_PENDING     = 1;
  PAYMENT_STATUS_IN_PROGRESS = 1;  // alias for PENDING (same value)
  PAYMENT_STATUS_COMPLETED   = 2;
}

// Enum nested in message
message Payment {
  string payment_id = 1;
  int64  amount     = 2;
  
  enum Method {
    METHOD_UNSPECIFIED  = 0;
    METHOD_CREDIT_CARD  = 1;
    METHOD_BANK_TRANSFER = 2;
    METHOD_CRYPTO       = 3;
  }
  
  Method method        = 3;
  PaymentStatus status = 4;
}

Java enum handling:
  // Accessing enum values
  Payment.Method method = payment.getMethod();
  int number = payment.getMethodValue();  // returns integer value
  
  // Switch on enum
  switch (method) {
    case METHOD_CREDIT_CARD:
      // ...
      break;
    case METHOD_BANK_TRANSFER:
      // ...
      break;
    case UNRECOGNIZED:
      // Unknown value from newer proto version
      break;
  }
  
  // Set by enum value
  payment.toBuilder().setMethod(Payment.Method.METHOD_CREDIT_CARD);
  // Set by int value
  payment.toBuilder().setMethodValue(1);

Proto3 open enum semantics:
  - Unknown enum values are KEPT (not rejected)
  - Accessible via getMethodValue() as an integer
  - This enables forward compatibility:
    Old server receives new enum value → keeps it, passes it along

Proto2 closed enum semantics:
  - Unknown enum values cause an error during parsing
  - Backward incompatibility hazard

7. ONEOF - VARIANT/UNION TYPE
----------------------------------------------------------------

Oneof allows exactly one of several fields to be set at a time.

message Notification {
  string notification_id = 1;
  string user_id         = 2;
  
  oneof content {
    OrderConfirmation order_confirmation = 3;
    ShipmentUpdate    shipment_update    = 4;
    PaymentReceipt    payment_receipt    = 5;
    string            custom_message    = 6;
  }
}

Rules:
  1. Only one oneof field can be set at a time
  2. Setting a new field clears the previous field
  3. Fields in oneof cannot be repeated
  4. A oneof cannot be repeated itself
  5. Fields in oneof cannot have field numbers that overlap with non-oneof fields

Java API:
  // Check which variant is set
  Notification.ContentCase contentCase = notification.getContentCase();
  
  switch (contentCase) {
    case ORDER_CONFIRMATION:
      OrderConfirmation oc = notification.getOrderConfirmation();
      break;
    case SHIPMENT_UPDATE:
      ShipmentUpdate su = notification.getShipmentUpdate();
      break;
    case CUSTOM_MESSAGE:
      String msg = notification.getCustomMessage();
      break;
    case CONTENT_NOT_SET:
      // No content set
      break;
  }
  
  // Set a variant
  Notification notification = Notification.newBuilder()
      .setNotificationId("N-001")
      .setCustomMessage("Welcome!")  // sets custom_message, clears others
      .build();

Use case — request/response with multiple types:
  message CreateEntityRequest {
    oneof entity {
      User    user    = 1;
      Product product = 2;
      Order   order   = 3;
    }
  }

8. MAP FIELDS
----------------------------------------------------------------

Maps provide a dictionary/hashmap structure:

message FeatureFlags {
  map<string, bool>   flags          = 1;
  map<string, string> config_values  = 2;
  map<int64, Product> product_cache  = 3;
}

Valid key types: bool, int32, int64, uint32, uint64, sint32, sint64,
                 fixed32, fixed64, sfixed32, sfixed64, string
Invalid key types: float, double, bytes, enum, message

Wire format: Map is equivalent to repeated KeyValue pair messages.
This means map fields are NOT sorted in any particular order.

Java API:
  FeatureFlags flags = FeatureFlags.newBuilder()
      .putFlags("dark_mode", true)
      .putFlags("beta_features", false)
      .putConfigValues("api_version", "v2")
      .build();
  
  // Access
  boolean darkMode = flags.getFlagsOrDefault("dark_mode", false);
  boolean required = flags.getFlagsOrThrow("required_flag");  // throws if missing
  
  Map<String, Boolean> allFlags = flags.getFlagsMap();  // unmodifiable view

9. GOOGLE PROTOBUF WELL-KNOWN TYPES
----------------------------------------------------------------

9.1 google.protobuf.Timestamp
  Represents a point in time (UTC):
    seconds: Unix timestamp (seconds since 1970-01-01T00:00:00Z)
    nanos: nanosecond adjustment [0, 999999999]
  
  Usage:
    import "google/protobuf/timestamp.proto";
    
    message Event {
      google.protobuf.Timestamp occurred_at = 1;
    }
  
  Java conversion:
    import com.google.protobuf.Timestamp;
    import com.google.protobuf.util.Timestamps;
    
    Timestamp now = Timestamps.fromMillis(System.currentTimeMillis());
    Timestamp specific = Timestamp.newBuilder()
        .setSeconds(1705312200L)
        .setNanos(0)
        .build();
    
    // To Instant
    Instant instant = Instant.ofEpochSecond(
        timestamp.getSeconds(), timestamp.getNanos());

9.2 google.protobuf.Duration
  Represents a time duration:
    seconds: signed seconds [-315,576,000,000, +315,576,000,000]
    nanos: signed nanoseconds [-999999999, 999999999]
  
  Usage: timeouts, TTLs, intervals

9.3 google.protobuf.FieldMask
  Specifies a subset of fields in a message:
    paths: ["name", "address.city", "items"]
  
  Used for partial updates (UPDATE only specified fields):
    message UpdateOrderRequest {
      Order     order      = 1;
      FieldMask field_mask = 2;
    }

9.4 google.protobuf.Any
  Can hold any protobuf message type:
    type_url: "type.googleapis.com/com.example.Order"
    value: <serialized Order bytes>
  
  Use case: plugin systems, extensible APIs, dynamic routing
  
  Java:
    Any any = Any.pack(order);  // serializes with type URL
    if (any.is(Order.class)) {
      Order unpackedOrder = any.unpack(Order.class);
    }

9.5 google.protobuf.Struct
  Represents a JSON-like dynamic structure:
  Values can be: null, bool, number, string, list, or struct
  
  Use when: embedding arbitrary JSON in a protobuf message
  
  Performance note: Much less efficient than typed messages;
  avoid in high-performance paths.

9.6 Wrappers (google/protobuf/wrappers.proto)
  BoolValue, BytesValue, DoubleValue, FloatValue, Int32Value,
  Int64Value, StringValue, UInt32Value, UInt64Value
  
  Each wraps a single `value` field.
  Purpose: nullable scalar fields in proto3.
  
  // Nullable string
  message Profile {
    google.protobuf.StringValue nickname = 1;  // can be null
  }
  
  // Check if set
  boolean hasNickname = profile.hasNickname();
  String nickname = hasNickname ? profile.getNickname().getValue() : null;

10. RESERVED FIELDS
----------------------------------------------------------------

When you delete or rename fields, mark them reserved:

message User {
  string user_id    = 1;
  string username   = 2;
  // deleted: string email = 3;
  // deleted: bool is_admin = 4;
  string first_name = 5;
  string last_name  = 6;
  
  reserved 3, 4;                 // reserve field NUMBERS
  reserved "email", "is_admin"; // reserve field NAMES
}

Why both number AND name reserved?
  - Number reservation: prevents old binary clients from
    misinterpreting recycled field numbers
  - Name reservation: prevents new code from using old names
    (compile-time error if someone tries to add email = 3)

Reserved ranges:
  reserved 100 to 199;  // reserve a range
  reserved 200 to max;  // reserve to max field number

----------------------------------------------------------------
11. EXTENSIONS AND ANY (PROTO2 vs PROTO3)
----------------------------------------------------------------

Proto2 had Extensions to add fields to a message from another .proto file.
Proto3 removed extensions; use Any or composition instead.

Proto2 (legacy):
  message Foo {
    extensions 100 to 199;  // allow extensions in this range
  }
  extend Foo {
    optional string bar = 100;
  }

Proto3 alternative with Any:
  message Extension {
    google.protobuf.Any extra_data = 1;
  }

Proto3 alternative with composition:
  message Request {
    CommonFields common   = 1;
    ExtraFields  extended = 2;  // add extra fields here
  }

----------------------------------------------------------------
12. INTERVIEW KEY QUESTIONS
----------------------------------------------------------------

Q: What is the difference between int32 and sint32?
A: Both are signed 32-bit integers, but sint32 uses ZigZag encoding.
   For negative numbers, sint32 uses far fewer bytes on the wire.
   int32 encodes negative numbers as large 10-byte varints.
   Use sint32 when your field frequently holds negative values.

Q: Can a protobuf message have a field with a null value?
A: In proto3, scalar fields cannot be null — they have default values
   (0, "", false). To represent null, use the optional keyword
   (generates has_XXX() method), or use wrapper types like
   google.protobuf.StringValue.

Q: What happens if the client sends a message with unknown fields?
A: Proto3 (since 3.5+) preserves unknown fields. The receiver keeps
   them in the message and will re-serialize them if the message is
   forwarded. This enables forward compatibility: old servers can
   pass messages with new fields through without losing them.

Q: Why must the first enum value always be 0?
A: In proto3, the default value for any enum field is the first defined
   value. The spec requires the first value to be 0 so the default is
   well-defined. Additionally, in C/C++ zero initialization is common.
   Best practice: name it UNSPECIFIED or UNKNOWN to signal "not set".
