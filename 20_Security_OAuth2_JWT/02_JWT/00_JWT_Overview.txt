================================================================
JWT (JSON Web Token) — OVERVIEW
================================================================

WHAT IS JWT?
-------------
JWT (JSON Web Token) is a compact, URL-safe means of representing claims
between two parties. It is an open standard (RFC 7519).

A JWT is a self-contained token — it carries all necessary information
within itself. The receiver can validate it WITHOUT contacting the issuer.

ANALOGY:
  JWT is like a sealed, tamper-evident envelope:
  - You can read the address (header/payload = base64)
  - But you can't modify it without breaking the seal (signature)
  - The receiver verifies the seal was made by the expected sender

================================================================
WHY JWT?
================================================================

BEFORE JWT (Opaque tokens / Sessions):
  - Server must store session data
  - Every request requires a DB/cache lookup
  - Hard to scale horizontally (sticky sessions or shared session store)
  - Hard to share auth across multiple services

WITH JWT:
  ✓ Stateless — no server-side storage required
  ✓ Self-contained — all claims embedded in token
  ✓ Cross-service — any service with the public key can validate
  ✓ Compact — URL-safe, fits in HTTP headers
  ✓ Extensible — add any custom claims
  ✗ Can't be revoked (until expiry) — requires short TTL + refresh tokens

================================================================
JWT STRUCTURE
================================================================

A JWT has three parts separated by dots (.):

  HEADER.PAYLOAD.SIGNATURE

  eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9        ← Header
  .eyJzdWIiOiJ1c2VyMTIzIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE3MTM0ODE yMDB9  ← Payload
  .SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature

Each part is BASE64URL encoded (NOT encrypted, just encoded!).

================================================================
PART 1: HEADER
================================================================

Contains: algorithm used and token type

{
  "alg": "RS256",    ← Signing algorithm
  "typ": "JWT"       ← Token type
}

Common algorithms:
  HS256   — HMAC with SHA-256 (symmetric — shared secret)
  RS256   — RSA with SHA-256 (asymmetric — private/public key)
  ES256   — ECDSA with SHA-256 (asymmetric — smaller keys)

================================================================
PART 2: PAYLOAD (CLAIMS)
================================================================

Contains the actual data (claims = statements about an entity).

{
  "iss": "https://auth-server.com",         ← Issuer
  "sub": "user-12345",                      ← Subject (user ID)
  "aud": ["https://api.app.com"],           ← Audience
  "exp": 1713484800,                        ← Expiration time (Unix)
  "iat": 1713481200,                        ← Issued at
  "nbf": 1713481200,                        ← Not before
  "jti": "unique-jwt-id-abc123",            ← JWT ID (prevents replay)
  "name": "John Doe",                       ← Custom claim
  "email": "john@example.com",              ← Custom claim
  "roles": ["USER", "ADMIN"],               ← Custom claim
  "scope": "openid email read:orders"       ← OAuth2 scopes
}

REGISTERED CLAIMS (standard, from RFC 7519):
  iss  — Issuer: who issued the token (URL of AS)
  sub  — Subject: who the token is about (user ID or client ID)
  aud  — Audience: who the token is intended for (resource server URL)
  exp  — Expiration time: Unix timestamp, reject after this
  nbf  — Not Before: Unix timestamp, reject before this
  iat  — Issued At: Unix timestamp, when it was issued
  jti  — JWT ID: unique ID for this token (idempotency, replay prevention)

PUBLIC CLAIMS: Defined by IANA JWT Claims Registry
PRIVATE CLAIMS: Custom, application-specific claims

================================================================
PART 3: SIGNATURE
================================================================

The signature ensures the token was NOT tampered with and was issued
by the expected party.

FOR HS256 (HMAC — symmetric):
  HMAC-SHA256(
    base64url(header) + "." + base64url(payload),
    secret
  )
  → Single shared secret — anyone with the secret can BOTH sign and verify

FOR RS256 (RSA — asymmetric):
  SHA256withRSA(
    base64url(header) + "." + base64url(payload),
    privateKey
  )
  → Signed with private key
  → Verified with public key (JWKS endpoint)
  → Only the AS needs the private key → more secure

VERIFICATION:
  Receiver recomputes the signature and checks it matches.
  If payload was modified → signature won't match → reject!

IMPORTANT: JWT is SIGNED (integrity), NOT ENCRYPTED (confidentiality)!
  The payload is readable by anyone who has the token.
  Don't put sensitive data in JWT payload unless it's also encrypted (JWE).

================================================================
JWE — JSON Web Encryption (Encrypted JWT)
================================================================

If you need to hide payload contents:
  JWE: header.encrypted_key.iv.ciphertext.auth_tag

Content is ENCRYPTED, not just signed.
Used for: passing sensitive claims across services, internal tokens.

Regular JWT usage: signing (JWS) only — payload visible.
JWE adds confidentiality on top of integrity.

================================================================
JWT IN HTTP REQUESTS
================================================================

Bearer Token Authentication:
  Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...

In OAuth2:
  Token Type = "Bearer"
  → Just present the token — no proof of possession

================================================================
JWT LIFECYCLE
================================================================

ISSUE:
  AS signs token with private key, sets exp ~15min from now

USE:
  Client sends Bearer token in every API request

VALIDATE (Resource Server):
  1. Parse header (get alg)
  2. Fetch public key from JWKS endpoint (cached)
  3. Verify signature
  4. Check exp (not expired)
  5. Check iss (expected issuer)
  6. Check aud (this server is the intended audience)
  7. Extract claims, set up SecurityContext

EXPIRE:
  Token is rejected after exp timestamp
  Client uses refresh token to get new access token

REVOKE:
  JWT cannot be "revoked" before expiry (it's stateless)
  Mitigations:
    - Keep access tokens short-lived (15 min)
    - Maintain a token blacklist/denylist (adds state back)
    - Use refresh token rotation (detect theft)

================================================================
DECODING A JWT (Don't confuse decode with verify!)
================================================================

Base64URL decode is NOT verification!
Anyone can decode a JWT and read the payload.
The signature verification step is what provides security.

DECODE (any tool, no key needed):
  Base64URL decode the payload → readable JSON

VERIFY (requires public key or shared secret):
  1. Decode header to get algorithm
  2. Fetch verification key
  3. Recompute signature and compare

TOOLS:
  jwt.io     — Online JWT debugger (paste token, see decoded)
  jwt-cli    — Command line tool

NEVER use jwt.io with production tokens containing real user data!

================================================================
JWKS (JSON Web Key Set)
================================================================

The JWKS endpoint publishes the authorization server's public keys
so resource servers can verify JWT signatures.

GET /.well-known/jwks.json

Response:
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "key-id-1",
      "n": "...",          ← RSA modulus
      "e": "AQAB"          ← RSA exponent
    }
  ]
}

Resource servers CACHE these keys and only refresh when encountering
an unknown kid (key ID) in a token's header.

Key Rotation:
  AS can publish multiple keys in JWKS.
  Tokens include kid in header to identify which key to use.
  Allows graceful key rotation without downtime.

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is a JWT and what are its three parts?
A: JWT is a compact, self-contained token (RFC 7519). Three parts:
   (1) Header — algorithm and token type, (2) Payload — claims about the
   user/session, (3) Signature — cryptographic proof of integrity.
   All parts are Base64URL encoded and separated by dots.

Q: Is the JWT payload encrypted?
A: No! The payload is Base64URL ENCODED, not encrypted — anyone can decode
   it. JWT only guarantees integrity (signature verification), not
   confidentiality. Use JWE (JSON Web Encryption) if you need encryption.

Q: What is the difference between HS256 and RS256?
A: HS256 uses a single shared secret for both signing and verification
   (symmetric). RS256 uses asymmetric keys — the AS signs with a private
   key and resource servers verify with the public key. RS256 is preferred
   because only the AS needs the private key.

Q: Why can't you revoke a JWT?
A: JWTs are stateless — validation is done locally without contacting the
   issuer. There's no central registry to check against. Mitigations: short
   TTL (15 min), token blacklist (adds state), or use opaque tokens.

Q: What claims should you always validate?
A: exp (not expired), iss (expected issuer URL), aud (this server is the
   intended audience), and nbf (not used before valid time).

Q: What is a JWKS endpoint?
A: A public endpoint published by the AS that lists its public keys in
   JSON Web Key Set format. Resource servers use it to verify JWT signatures
   without contacting the AS per-request. Keys are cached and refreshed
   when a new key ID (kid) is encountered.
