================================================================
JWT STRUCTURE — DEEP DIVE
================================================================

A JWT looks like this:
  eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImtleS0xIn0
  .eyJzdWIiOiJ1c2VyLTEyMyIsIm5hbWUiOiJKb2huIERvZSIsImlhdCI6MTcxMzQ4MTIwMCwiZXhwIjoxNzEzNDg0ODAwfQ
  .SIGNATURE_HERE

Three parts: HEADER . PAYLOAD . SIGNATURE
Each part is Base64URL encoded (NOT standard Base64 — uses - instead of +, _ instead of /)

================================================================
PART 1: HEADER
================================================================

RAW JSON:
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-1"
}

BASE64URL ENCODED:
  eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImtleS0xIn0

FIELDS EXPLAINED:
  alg (Algorithm):
    Required. The signing algorithm.
    SYMMETRIC (shared secret):
      HS256  — HMAC-SHA256
      HS384  — HMAC-SHA384
      HS512  — HMAC-SHA512
    ASYMMETRIC (private/public key):
      RS256  — RSA PKCS#1 v1.5 + SHA-256
      RS384  — RSA PKCS#1 v1.5 + SHA-384
      RS512  — RSA PKCS#1 v1.5 + SHA-512
      PS256  — RSA-PSS + SHA-256 (more secure RSA padding)
      ES256  — ECDSA + SHA-256 (P-256 curve) — compact keys
      ES384  — ECDSA + SHA-384 (P-384 curve)
      ES512  — ECDSA + SHA-512 (P-521 curve)
    NONE:
      none   — NEVER ACCEPT! Security vulnerability.

  typ (Type):
    Optional. Usually "JWT".
    "at+JWT" = access token (RFC 9068)
    Can be omitted; when present, must be validated.

  kid (Key ID):
    Optional but HIGHLY RECOMMENDED.
    Identifies which key to use for verification.
    Critical for key rotation — multiple keys can be published in JWKS.
    Token includes kid → receiver looks up the specific key from JWKS.

  cty (Content Type):
    Used for nested JWTs (JWT within JWE).
    Usually omitted.

================================================================
PART 2: PAYLOAD (CLAIMS)
================================================================

RAW JSON:
{
  "iss": "https://auth.example.com",
  "sub": "user-12345",
  "aud": ["https://api.example.com"],
  "exp": 1713484800,
  "iat": 1713481200,
  "nbf": 1713481200,
  "jti": "abc-123-unique-id",
  "name": "John Doe",
  "email": "john@example.com",
  "email_verified": true,
  "roles": ["USER", "ADMIN"],
  "scope": "openid email read:orders",
  "azp": "my-client-id",
  "sid": "session-abc"
}

CLAIM CATEGORIES:
-----------------

REGISTERED CLAIMS (RFC 7519) — standard, short names by convention:

  iss  (Issuer)
    - Who issued the token
    - Must be a URL identifying the AS
    - MUST validate: check this matches your expected AS URL
    - Example: "https://accounts.google.com"

  sub  (Subject)
    - Who the token is ABOUT
    - Unique identifier for the user (or client for M2M)
    - Stable across tokens for the same user
    - Example: "user-12345", "google|12345678"

  aud  (Audience)
    - Who the token is INTENDED FOR
    - Resource server(s) that should accept this token
    - MUST validate: your server must be listed in aud
    - Example: ["https://api.myapp.com", "https://reports.myapp.com"]
    - Prevents token reuse across different services

  exp  (Expiration Time)
    - Unix timestamp when the token expires
    - MUST validate: reject if current time > exp
    - Include clock skew tolerance (typically 30-60 seconds)
    - Example: 1713484800 = 2024-04-19 00:00:00 UTC

  iat  (Issued At)
    - Unix timestamp when token was issued
    - Optional to validate, useful for auditing
    - Can detect very old tokens being replayed

  nbf  (Not Before)
    - Unix timestamp before which token is NOT valid
    - Useful for tokens that become valid in the future
    - SHOULD validate: reject if current time < nbf

  jti  (JWT ID)
    - Unique identifier for this specific token instance
    - Use for preventing replay attacks
    - Store used JTIs in cache, reject duplicates

PUBLIC CLAIMS — registered in IANA JWT Claims Registry:
  name, given_name, family_name, email, email_verified,
  phone_number, address, picture, profile, website, gender,
  birthdate, zoneinfo, locale, updated_at

PRIVATE/CUSTOM CLAIMS — application-specific:
  roles, permissions, tenant_id, organization, custom_attr
  Use URN or URL namespacing to avoid collisions:
    "https://api.myapp.com/roles": ["ADMIN"]

================================================================
CLAIM VALIDATION RULES
================================================================

MANDATORY VALIDATIONS:
1. Signature verification (always)
2. exp — token not expired
3. iss — issuer matches expected value
4. aud — audience contains this resource server

RECOMMENDED VALIDATIONS:
5. nbf — current time >= not-before
6. iat — token not unreasonably old
7. alg — algorithm matches expected (never accept "none")

OPTIONAL BUT GOOD:
8. jti — not already used (replay prevention, requires state)
9. azp — authorized party (for OIDC, the client_id)

CLOCK SKEW:
  Clocks between servers may differ slightly.
  Add ±30-60 second tolerance to exp and nbf checks.

================================================================
PART 3: SIGNATURE
================================================================

The signature prevents tampering. If any byte in header or payload
changes, the signature becomes invalid.

HOW IT'S COMPUTED:
  input = BASE64URL(header) + "." + BASE64URL(payload)

  HS256: signature = HMAC-SHA256(input, sharedSecret)
  RS256: signature = RSA_SIGN(SHA256(input), privateKey)
  ES256: signature = ECDSA_SIGN(SHA256(input), privateKey)

HOW IT'S VERIFIED:
  HS256: HMAC-SHA256(input, sharedSecret) == received_signature
  RS256: RSA_VERIFY(SHA256(input), signature, publicKey)
  ES256: ECDSA_VERIFY(SHA256(input), signature, publicKey)

SIGNATURE ENCODING:
  DER encoding for ECDSA is converted to R||S (concat) for JWT.
  RSA signatures are just the raw bytes, Base64URL encoded.

JWT DECODE EXAMPLE (Java)
================================================================

// Using Spring Security's JWT decoder
@Bean
public JwtDecoder jwtDecoder() {
    return NimbusJwtDecoder
        .withJwkSetUri("https://auth-server.com/.well-known/jwks.json")
        .build();
}

// Usage in security config
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.oauth2ResourceServer(oauth2 -> oauth2
        .jwt(jwt -> jwt.decoder(jwtDecoder()))
    );
    return http.build();
}

// Custom JWT validation
@Bean
public JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
        .withJwkSetUri("https://auth-server.com/.well-known/jwks.json")
        .build();

    OAuth2TokenValidator<Jwt> defaultValidators = JwtValidators.createDefault();
    OAuth2TokenValidator<Jwt> audienceValidator = token -> {
        List<String> audiences = token.getAudience();
        if (audiences.contains("https://api.myapp.com")) {
            return OAuth2TokenValidatorResult.success();
        }
        return OAuth2TokenValidatorResult.failure(
            new OAuth2Error("invalid_token", "Invalid audience", null));
    };

    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        defaultValidators, audienceValidator));
    return decoder;
}

// Access claims in controller
@GetMapping("/me")
public ResponseEntity<UserInfo> me(Authentication auth) {
    Jwt jwt = (Jwt) auth.getPrincipal();

    String userId = jwt.getSubject();                    // sub
    String email = jwt.getClaimAsString("email");
    List<String> roles = jwt.getClaimAsStringList("roles");
    Instant issuedAt = jwt.getIssuedAt();
    Instant expiresAt = jwt.getExpiresAt();

    return ResponseEntity.ok(new UserInfo(userId, email));
}

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the difference between Base64 and Base64URL?
A: Base64 uses '+' and '/' characters and '=' padding. Base64URL replaces
   '+' with '-' and '/' with '_', and removes '=' padding. This makes it
   safe for use in URLs and HTTP headers without encoding.

Q: What are the mandatory claims to validate in a JWT?
A: signature, exp (not expired), iss (expected issuer), aud (this server
   is in the audience list). Also check alg header matches expected
   algorithm.

Q: What is the aud claim and why is it important?
A: The audience claim identifies intended recipients of the token. A resource
   server MUST verify it is listed in aud. Without this check, a token issued
   for service A could be used against service B (confused deputy attack).

Q: What is the jti claim used for?
A: JWT ID — a unique identifier for the token. Used to prevent replay attacks
   by storing used JTIs and rejecting duplicates. Requires server-side state,
   which partially defeats JWT's statelessness benefit.

Q: Why should you never trust the alg header to determine how to verify?
A: Attackers can manipulate the alg header (e.g., set it to "none" or change
   RS256 to HS256 and sign with the server's public key). Always use a fixed,
   configured algorithm for verification, ignoring the header's claim.
