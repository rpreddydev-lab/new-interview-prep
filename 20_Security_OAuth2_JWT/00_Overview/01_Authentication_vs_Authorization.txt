================================================================
AUTHENTICATION vs AUTHORIZATION
================================================================

QUICK DISTINCTION
------------------
Authentication (AuthN) = "Who are you?"          → Verify identity
Authorization  (AuthZ) = "What can you do?"      → Enforce permissions

You must authenticate FIRST, then authorize.

================================================================
AUTHENTICATION
================================================================

DEFINITION
-----------
The process of verifying that a user/system is who they claim to be.

COMMON AUTHENTICATION MECHANISMS
----------------------------------
1. Username + Password      — Most common, weakest on its own
2. Multi-Factor Auth (MFA)  — Something you know + have + are
3. OAuth2 / OIDC            — Delegate authentication to IdP
4. API Keys                 — For machine-to-machine
5. Certificates (mTLS)      — Mutual TLS for service-to-service
6. Biometrics               — Fingerprint, face ID (usually mobile)
7. SAML                     — Enterprise SSO (XML-based)
8. Magic Links              — Passwordless, email-based login

MFA FACTORS
------------
Type                 Example
------------------------------------------------
Something you know   Password, PIN, security Q
Something you have   TOTP (Google Authenticator), hardware token (YubiKey)
Something you are    Fingerprint, Face ID, retina scan
Somewhere you are    Geolocation-based (rarely used alone)

AUTHENTICATION PROTOCOLS
--------------------------
- HTTP Basic Auth : base64(username:password) in Authorization header — insecure without HTTPS
- Session/Cookie  : Server stores session state, sends cookie to browser
- OAuth2 + OIDC   : Industry standard for federated identity
- SAML 2.0        : XML-based, common in enterprise environments
- LDAP/Active Dir : Common for internal corporate directories

SESSION vs TOKEN-BASED AUTHENTICATION
---------------------------------------
                    Session-Based           Token-Based (JWT)
Server State        Stateful (session store) Stateless
Scalability         Harder (sticky sessions) Easier (no server state)
Storage             Server-side              Client-side
Revocation          Easy (delete session)    Hard (need blacklist/short TTL)
Use Case            Traditional web apps     APIs, SPAs, microservices

================================================================
AUTHORIZATION
================================================================

DEFINITION
-----------
The process of determining whether an authenticated principal is allowed to
perform an action or access a resource.

AUTHORIZATION MODELS
---------------------
1. RBAC (Role-Based Access Control)
   - Permissions assigned to roles, roles assigned to users
   - Example: ADMIN, USER, MODERATOR roles
   - Simple to manage, widely used

2. ABAC (Attribute-Based Access Control)
   - Decisions based on attributes of user, resource, environment
   - Example: "User.department == Resource.department AND time == business_hours"
   - Fine-grained, flexible, complex to implement

3. PBAC (Policy-Based Access Control)
   - Central policy engine (e.g., OPA - Open Policy Agent)
   - Policies written in Rego language
   - Best for large, complex systems

4. ACL (Access Control List)
   - Per-resource list of who can do what
   - Example: Unix file permissions

5. Scope-Based (OAuth2)
   - Tokens carry "scopes" — what the token is allowed to do
   - Example: read:user, write:orders, admin:all

SPRING SECURITY AUTHORIZATION EXAMPLES
----------------------------------------
// RBAC via annotations
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }

// Multiple roles
@PreAuthorize("hasAnyRole('ADMIN', 'MODERATOR')")

// OAuth2 scope check
@PreAuthorize("hasAuthority('SCOPE_read:orders')")

// Expression-based (ABAC)
@PreAuthorize("#userId == authentication.name")
public User getUser(String userId) { ... }

// HTTP Security (method-level)
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/api/**").hasAuthority("SCOPE_api.read")
    .anyRequest().authenticated()
);

================================================================
AUTHENTICATION vs AUTHORIZATION — SIDE-BY-SIDE
================================================================

Aspect              Authentication                  Authorization
-----------------------------------------------------------------------
Question            Who are you?                    What can you do?
When                First step                      After authentication
Failure HTTP Code   401 Unauthorized                403 Forbidden
Handled by          IdP / Login system              Resource server / App
Spring class        AuthenticationManager           AccessDecisionManager
Data source         User credentials store          Roles/Permissions store
OAuth2 relevance    Access Token issuance           Scope validation

NOTE ON HTTP STATUS CODES:
  401 = "You're not authenticated (or token is invalid/expired)"
  403 = "You ARE authenticated, but you don't have permission"

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the difference between 401 and 403?
A: 401 means authentication failed or not provided — the client must
   authenticate. 403 means the client IS authenticated but lacks permission.

Q: Can you be authorized without being authenticated?
A: In most systems, no. Authorization assumes a verified identity. However,
   some systems allow anonymous access to public resources (technically
   unauthenticated but "authorized" for public endpoints).

Q: How does OAuth2 handle authentication vs authorization?
A: OAuth2 is primarily an AUTHORIZATION framework (delegates access via tokens
   and scopes). OIDC (built on OAuth2) adds AUTHENTICATION via the ID Token.

Q: What is the principle of least privilege in authorization?
A: Grant only the minimum permissions needed. A service that only reads orders
   should have read:orders scope, not admin:all.

Q: How would you implement RBAC in Spring Security?
A: Assign roles to users in the database, load them in UserDetailsService,
   and enforce via @PreAuthorize("hasRole('ROLE_ADMIN')") or
   HttpSecurity.authorizeHttpRequests() rules.

Q: What is the difference between RBAC and ABAC?
A: RBAC assigns permissions to roles which are assigned to users — simple and
   coarse-grained. ABAC evaluates policies based on multiple attributes
   (user attributes, resource attributes, environment) — fine-grained but
   complex to manage.
