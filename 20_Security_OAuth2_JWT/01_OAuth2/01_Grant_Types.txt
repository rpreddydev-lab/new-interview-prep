================================================================
OAUTH2 GRANT TYPES (FLOWS)
================================================================

A grant type defines HOW a client obtains an access token.
Different use cases require different flows. Choosing the wrong one
is a security vulnerability.

================================================================
1. AUTHORIZATION CODE GRANT (RFC 6749 Section 4.1)
================================================================

BEST FOR: Web apps with a backend server (server-side rendering, BFF pattern)
SECURITY: Highest — code → token exchange happens server-to-server

FLOW:
  1. User clicks "Login with Google"
  2. Client redirects to Authorization Server (AS):
       GET /oauth2/authorize
         ?response_type=code
         &client_id=my-app
         &redirect_uri=https://app.com/callback
         &scope=openid email
         &state=random-csrf-token

  3. User logs in and consents at AS
  4. AS redirects back to app:
       GET /callback?code=AUTH_CODE&state=random-csrf-token

  5. Backend exchanges code for tokens (server-to-server POST):
       POST /oauth2/token
         grant_type=authorization_code
         &code=AUTH_CODE
         &redirect_uri=https://app.com/callback
         &client_id=my-app
         &client_secret=my-secret   ← only for confidential clients

  6. AS returns: { access_token, refresh_token, id_token, expires_in }

WHY NOT RETURN TOKENS DIRECTLY IN STEP 4?
  Code is single-use, short-lived, and delivered via browser redirect.
  Tokens are returned server-to-server (not exposed in URL/browser history).
  Client secret is used server-side, never exposed to browser.

STATE PARAMETER:
  Generated by client, verified on callback.
  Prevents CSRF attacks on the OAuth2 flow.
  If state received ≠ state sent → reject.

================================================================
2. AUTHORIZATION CODE + PKCE (RFC 7636)
================================================================

BEST FOR: SPAs, mobile apps, native apps (public clients — no client_secret)
WHY NEEDED: Public clients can't keep a client_secret. PKCE replaces it.

PKCE = Proof Key for Code Exchange

HOW PKCE WORKS:
  1. Client generates:
       code_verifier  = random 43-128 char string (high entropy)
       code_challenge = BASE64URL(SHA256(code_verifier))

  2. Sends code_challenge with authorization request:
       GET /oauth2/authorize
         ?response_type=code
         &client_id=spa-app
         &redirect_uri=https://spa.com/callback
         &scope=openid
         &state=xyz
         &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
         &code_challenge_method=S256

  3. Gets back authorization code (same as step 4 above)

  4. Exchanges code + code_verifier (not challenge!) for token:
       POST /oauth2/token
         grant_type=authorization_code
         &code=AUTH_CODE
         &redirect_uri=https://spa.com/callback
         &client_id=spa-app
         &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

  5. AS verifies: SHA256(code_verifier) == stored code_challenge
     If not → reject

WHY PKCE IS SECURE:
  Even if the authorization code is intercepted (via browser history,
  referrer logs, etc.), the attacker can't exchange it without knowing
  the code_verifier, which was never transmitted.

USE PKCE EVEN FOR CONFIDENTIAL CLIENTS (Best Practice since OAuth 2.1):
  OAuth 2.1 (upcoming standard) requires PKCE for all authorization code flows.

================================================================
3. CLIENT CREDENTIALS GRANT (RFC 6749 Section 4.4)
================================================================

BEST FOR: Service-to-service (M2M) — no user involved
EXAMPLE: A cron job, a microservice calling another microservice

FLOW:
  1. Service directly calls token endpoint:
       POST /oauth2/token
         grant_type=client_credentials
         &client_id=service-a
         &client_secret=secret123
         &scope=read:orders

  2. AS validates client credentials, returns:
       { access_token, expires_in, token_type: "Bearer" }

  3. Service uses access_token to call Resource Server

NOTE: No user, no refresh token (just get a new one when needed).
      Token should be cached until near expiry.

SPRING SECURITY CLIENT CONFIGURATION:
  # application.yml
  spring:
    security:
      oauth2:
        client:
          registration:
            service-b:
              client-id: service-a
              client-secret: secret123
              authorization-grant-type: client_credentials
              scope: read:orders
          provider:
            service-b:
              token-uri: https://auth-server/oauth2/token

  // Inject WebClient with auto token management:
  @Bean
  public WebClient webClient(OAuth2AuthorizedClientManager clientManager) {
      ServletOAuth2AuthorizedClientExchangeFilterFunction oauth2 =
          new ServletOAuth2AuthorizedClientExchangeFilterFunction(clientManager);
      oauth2.setDefaultClientRegistrationId("service-b");
      return WebClient.builder()
          .apply(oauth2.oauth2Configuration())
          .build();
  }

================================================================
4. DEVICE CODE GRANT (RFC 8628)
================================================================

BEST FOR: Devices with limited UI (Smart TVs, CLIs, IoT)
EXAMPLE: Logging into Netflix on a smart TV

FLOW:
  1. Device requests device code:
       POST /oauth2/device_authorization
         &client_id=my-tv
         &scope=openid

  2. AS returns:
       {
         device_code: "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
         user_code: "WDJB-MJHT",
         verification_uri: "https://example.com/activate",
         interval: 5,
         expires_in: 1800
       }

  3. Device shows: "Go to example.com/activate and enter code WDJB-MJHT"

  4. Device POLLS token endpoint every 5 seconds:
       POST /oauth2/token
         grant_type=urn:ietf:params:oauth2:grant-type:device_code
         &device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS
         &client_id=my-tv

  5. Meanwhile, user goes to URL, enters code, logs in on their phone/laptop

  6. Next poll succeeds → AS returns access_token

================================================================
5. IMPLICIT GRANT — DEPRECATED ❌
================================================================

NEVER USE FOR NEW APPLICATIONS.

What it did: Returned access_token directly in the URL fragment (#) after auth.

WHY DEPRECATED:
  - Tokens exposed in browser history, referrer logs, server logs
  - No client authentication
  - Vulnerable to token leakage
  - Replaced by Authorization Code + PKCE for public clients

================================================================
6. RESOURCE OWNER PASSWORD CREDENTIALS (ROPC) — DEPRECATED ❌
================================================================

NEVER USE FOR NEW APPLICATIONS.

What it did: Client sent username/password directly to token endpoint.

WHY DEPRECATED:
  - Client sees the user's credentials (defeats purpose of OAuth2)
  - No consent screen
  - Can't use MFA
  - Acceptable ONLY for migrating legacy apps temporarily

================================================================
GRANT TYPE SELECTION GUIDE
================================================================

Application Type                    Grant Type
-------------------------------------------------------------------
Web App (server-side, backend)      Authorization Code
SPA (React, Angular, Vue)           Authorization Code + PKCE
Mobile App (iOS, Android)           Authorization Code + PKCE
Service-to-Service (no user)        Client Credentials
Smart TV / IoT / CLI                Device Code
NEVER use                           Implicit, ROPC

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the purpose of the authorization code grant?
A: It allows a user to grant a client access to their resources without
   exposing their credentials. The code-for-token exchange happens
   server-to-server, keeping tokens away from the browser.

Q: Why was the implicit grant deprecated?
A: Tokens were returned directly in the URL fragment, exposing them in
   browser history, server logs, and referrer headers. Authorization Code
   with PKCE is safer for public clients.

Q: What is the difference between Authorization Code and Client Credentials?
A: Authorization Code involves a user (user delegates access).
   Client Credentials is machine-to-machine (no user involved, client
   authenticates with its own credentials).

Q: When should you use PKCE?
A: Always for public clients (SPAs, mobile apps) that can't keep a
   client secret. OAuth 2.1 recommends PKCE for ALL clients.

Q: How does PKCE prevent authorization code interception?
A: The client generates a code_verifier and sends its SHA256 hash
   (code_challenge) with the auth request. Even if an attacker intercepts
   the authorization code, they can't exchange it without the original
   code_verifier, which was only held in memory by the legitimate client.

Q: What grant type would you use for a background job?
A: Client Credentials — there's no user involved, the service authenticates
   directly with its client_id and client_secret to obtain an access token.
