================================================================
ID TOKEN — OIDC
================================================================

WHAT IS THE ID TOKEN?
----------------------
The ID token is a JWT issued by an OIDC Identity Provider (IdP)
that represents the authenticated user's identity.

It is the CORE of OIDC — the mechanism by which the client application
learns WHO the user is.

KEY DISTINCTION:
  ID Token   → for the CLIENT (who is the user?)
  Access Token → for the RESOURCE SERVER (what can the app do?)

NEVER use the access token to get user identity.
NEVER use the ID token to call APIs (it's not meant for that).

================================================================
ID TOKEN STRUCTURE
================================================================

A standard ID token JWT contains:

HEADER:
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-id-from-jwks"
}

PAYLOAD:
{
  // ----- REQUIRED OIDC CLAIMS -----
  "iss": "https://accounts.google.com",       ← Issuer (IdP URL)
  "sub": "10769150350006150715113082367",      ← Subject (unique user ID)
  "aud": "my-client-id",                      ← Audience (YOUR client_id)
  "exp": 1713484800,                          ← Expiration
  "iat": 1713481200,                          ← Issued at

  // ----- OPTIONAL STANDARD CLAIMS -----
  "nonce": "n-0S6_WzA2Mj",                   ← Replay prevention
  "auth_time": 1713481200,                    ← When user authenticated
  "acr": "1",                                 ← Authentication Context Class Ref
  "amr": ["pwd", "otp"],                      ← Authentication Methods Refs
  "azp": "my-client-id",                      ← Authorized Party (if aud has 1 entry)
  "at_hash": "77QmUPtjPfzWtF2AnpK9RQ",       ← Access Token hash

  // ----- PROFILE SCOPE CLAIMS -----
  "name": "John Doe",
  "given_name": "John",
  "family_name": "Doe",
  "middle_name": "Michael",
  "nickname": "johny",
  "preferred_username": "johndoe",
  "profile": "https://example.com/users/johndoe",
  "picture": "https://example.com/users/johndoe/pic.jpg",
  "website": "https://johndoe.com",
  "gender": "male",
  "birthdate": "1990-01-01",
  "zoneinfo": "America/Chicago",
  "locale": "en-US",
  "updated_at": 1713480000,

  // ----- EMAIL SCOPE CLAIMS -----
  "email": "john@example.com",
  "email_verified": true,

  // ----- PHONE SCOPE CLAIMS -----
  "phone_number": "+15551234567",
  "phone_number_verified": true,

  // ----- ADDRESS SCOPE CLAIMS -----
  "address": {
    "formatted": "123 Main St, Springfield, IL 62701",
    "street_address": "123 Main St",
    "locality": "Springfield",
    "region": "IL",
    "postal_code": "62701",
    "country": "US"
  }
}

================================================================
REQUIRED CLAIM DESCRIPTIONS
================================================================

iss (Issuer):
  URL of the OpenID Provider that issued the token.
  MUST match the configured issuer URL.
  Example: "https://accounts.google.com"

sub (Subject):
  Unique identifier for the user at the IdP.
  Case-sensitive, max 255 characters.
  MUST be stable for a given user — same user always gets same sub.
  Use sub as the primary user identifier in your database.
  IMPORTANT: sub may differ across different clients at the same IdP
  (pairwise subject identifiers — privacy protection).

aud (Audience):
  The client(s) this ID token is intended for.
  MUST contain YOUR client_id.
  MUST be validated — prevents token substitution across clients.
  If only one value: may be a string. Otherwise an array.

exp (Expiration):
  Unix timestamp when the token expires.
  MUST reject if current time > exp.
  ID tokens typically expire 10-15 minutes after issuance.

iat (Issued At):
  Unix timestamp when the token was issued.
  SHOULD validate it's not unreasonably old.

================================================================
OPTIONAL CLAIM DESCRIPTIONS
================================================================

nonce:
  Random string included in auth request, mirrored in ID token.
  Client MUST verify nonce matches what was sent.
  Prevents ID token replay attacks.
  MUST include if you sent a nonce in the auth request.

auth_time:
  Time when user actually authenticated.
  Different from iat — if SSO session reused, auth_time is older.
  Required when max_age was specified in the request.

acr (Authentication Context Class Reference):
  Level of authentication used.
  "0" = unauthenticated, "1" = password, "2" = MFA
  NIST SP 800-63 levels: aal1, aal2, aal3
  Validate if you require MFA: acr == "aal2"

amr (Authentication Methods References):
  Array of authentication methods used.
  "pwd" = password, "otp" = OTP, "face" = biometric
  "mfa" = multiple factors, "sms" = SMS OTP

azp (Authorized Party):
  The client the token was issued to (if different from aud).
  Required when aud is a single value.

at_hash (Access Token Hash):
  First 128 bits of SHA-256 of the access token, Base64URL encoded.
  Binds the ID token to the access token.
  Validate to ensure ID token and access token were issued together.

================================================================
ID TOKEN VALIDATION CHECKLIST
================================================================

1.  Decrypt if JWE (if encrypted)
2.  Verify signature using IdP's public key from JWKS
3.  iss == expected issuer URL
4.  aud contains your client_id
5.  exp > current time (with small clock skew tolerance ≤ 5 min)
6.  iat ≤ current time (with clock skew)
7.  nonce == nonce you sent (if you sent one)
8.  sub is present and non-empty
9.  If auth_time present: current_time - auth_time <= max_age (if max_age sent)
10. at_hash matches SHA-256(access_token) if present
11. alg is NOT "none" and matches expected algorithm

// Spring Security validates these automatically via JwtDecoder
// with issuer-uri configured:
spring:
  security:
    oauth2:
      client:
        provider:
          keycloak:
            issuer-uri: https://keycloak.example.com/realms/myrealm
        registration:
          keycloak:
            scope: openid, email, profile

================================================================
ACCESSING ID TOKEN CLAIMS IN SPRING SECURITY
================================================================

// After OAuth2 login, the principal is OidcUser
@GetMapping("/profile")
public Map<String, Object> profile(
        @AuthenticationPrincipal OidcUser oidcUser) {

    // Standard OIDC claims
    String userId    = oidcUser.getSubject();         // sub
    String issuer    = oidcUser.getIssuer().toString(); // iss
    String name      = oidcUser.getFullName();         // name
    String email     = oidcUser.getEmail();            // email
    Boolean verified = oidcUser.getEmailVerified();   // email_verified
    String picture   = oidcUser.getPicture();          // picture
    Instant authTime = oidcUser.getAuthenticatedAt();  // auth_time

    // ID Token itself
    OidcIdToken idToken = oidcUser.getIdToken();
    String rawTokenValue = idToken.getTokenValue();
    Map<String, Object> allClaims = idToken.getClaims();

    // Custom claims
    String tenantId = idToken.getClaimAsString("tenant_id");
    List<String> roles = idToken.getClaimAsStringList("roles");

    return Map.of(
        "id", userId,
        "name", name,
        "email", email
    );
}

================================================================
SUBJECT IDENTIFIER TYPES
================================================================

PUBLIC subject:
  Same sub value for all clients at the same IdP.
  Easy user federation across apps.
  Google uses this: same sub for all your apps.

PAIRWISE subject:
  Different sub value for each client application.
  Privacy benefit: can't correlate user across apps.
  More complex for account federation.
  Some IdPs (Okta) support pairwise by configuration.

RECOMMENDATION:
  Use sub as your internal user identifier.
  Map IdP sub → your internal user ID in your database.
  Never use email as a primary ID (users can change email).

================================================================
ID TOKEN vs USERINFO ENDPOINT
================================================================

Both provide user claims, but differ in:

                    ID Token                    UserInfo
------------------------------------------------------------------
What                JWT in token response       HTTP GET /userinfo
When                Received at login only       Can call anytime
Claims              Limited (requested scopes)   Can return more
Freshness           Snapshot at login time       Current at call time
Requires network    No (self-contained)          Yes
Validation          Signature verification       Trust (authenticated call)
Storage             Client stores it             No storage needed

STRATEGY:
  Use ID Token for: initial authentication, basic user info at login
  Use UserInfo for: get more claims, get fresh claims after profile update

================================================================
COMMON INTERVIEW QUESTIONS
================================================================

Q: What is the ID token and how does it differ from the access token?
A: The ID token is an OIDC-specific JWT that tells the CLIENT who the user
   is (identity claims: sub, name, email). The access token tells RESOURCE
   SERVERS what the app is allowed to do. You validate the ID token to
   establish user identity, and use the access token to call APIs.

Q: Why must you validate the aud claim in an ID token?
A: The aud (audience) claim must contain YOUR client_id. Without this
   validation, you could accept an ID token issued for a different client
   application — an attacker could use another app's ID token to log into
   yours (token substitution attack).

Q: What is the nonce claim used for?
A: The nonce is a random value the client includes in the authorization
   request. The IdP embeds it in the ID token. The client verifies the
   nonce on receipt. This prevents ID token replay attacks — an attacker
   can't reuse a stolen ID token from a different session.

Q: What is the sub claim and how should you use it?
A: sub is the unique, stable identifier for the user at the IdP. Use it as
   the primary key to map to your internal user records. Don't use email —
   users can change it. sub is guaranteed to be stable for a given user.

Q: What is the at_hash claim?
A: At_hash is the Base64URL-encoded SHA-256 hash of the access token, binds
   the ID token to the specific access token issued at the same time.
   Prevents an attacker from swapping out the access token while keeping
   the same ID token.
