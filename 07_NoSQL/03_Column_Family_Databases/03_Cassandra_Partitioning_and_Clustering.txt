================================================================
  CASSANDRA PARTITIONING AND CLUSTERING
================================================================

================================================================
PARTITIONING
================================================================

  Cassandra distributes data across nodes using a partition key.
  The partition key is hashed using the Murmur3 hash function
  to produce a token (64-bit integer).
  Each node is responsible for a range of tokens.

  Partition Key "user:1001" --> hash --> token -5890305157234189120
  That token falls in node 3's range --> data stored on node 3
  (and RF-1 other nodes for replication)

================================================================
CONSISTENT HASHING
================================================================

  Cassandra uses consistent hashing on a ring of token values.
  Nodes are evenly spaced on the ring.
  Virtual nodes (vnodes) assign multiple token ranges per physical node.

  Benefits of vnodes:
  - More even load distribution
  - Easier cluster expansion (new node takes token ranges from many nodes)
  - Faster recovery (data comes from multiple nodes in parallel)

================================================================
REPLICATION STRATEGIES
================================================================

  SimpleStrategy:
  - Copies to the next RF nodes on the ring clockwise
  - Only for single datacenter (dev/test use)

  NetworkTopologyStrategy (production):
  - Specify replica count per datacenter
  - Spreads replicas across racks within each DC

  CREATE KEYSPACE production_app
  WITH REPLICATION = {
      'class': 'NetworkTopologyStrategy',
      'us-east': 3,
      'eu-west': 3
  };

================================================================
CLUSTERING COLUMNS
================================================================

  Within a partition, rows are physically sorted by clustering columns.
  This enables efficient range queries within a partition.

  PRIMARY KEY (partition_key, cluster1, cluster2)

  -- Sorting declared at table creation:
  WITH CLUSTERING ORDER BY (cluster1 ASC, cluster2 DESC)

  Allowed query patterns on clustering columns:
  - Equality on leading columns, range on last:
    WHERE pk = ? AND cluster1 = ? AND cluster2 > ?  --> OK
    WHERE pk = ? AND cluster1 > ?                   --> OK
    WHERE pk = ? AND cluster2 > ?                   --> NOT OK (skip cluster1)

================================================================
READ PATH
================================================================

  1. Coordinator hashes partition key --> determines responsible nodes
  2. Coordinator sends read to replicas (based on consistency level)
  3. Replicas check memtable first (in-memory write buffer)
  4. If not in memtable, check row cache (if enabled)
  5. Check Bloom filter (probabilistic: is key in this SSTable?)
  6. Check partition key cache
  7. Read from SSTable on disk
  8. Coordinator does read repair if replicas disagree
  9. Returns result to client

================================================================
WRITE PATH
================================================================

  1. Coordinator sends write to all replica nodes (based on consistency level)
  2. Each replica:
     a. Appends to Commit Log (WAL for durability)
     b. Writes to Memtable (in-memory buffer)
  3. When Memtable is full --> flushed to SSTable on disk
  4. SSTables are immutable; updates/deletes create new SSTables
  5. Compaction periodically merges SSTables

  Cassandra writes are extremely fast because:
  - Sequential writes (no random I/O -- Commit Log is append-only)
  - Writes go to Memtable first (memory write)
  - No UPDATE-in-place on disk

================================================================
COMPACTION
================================================================

  SSTable files accumulate over time.
  Compaction merges multiple SSTables:
  - Removes tombstones (deleted data)
  - Merges duplicate entries
  - Produces fewer, larger SSTables
  - Improves read performance

  Compaction strategies:
  SizeTieredCompactionStrategy (STCS):   default, good for write-heavy
  LeveledCompactionStrategy (LCS):       better read performance, more I/O
  TimeWindowCompactionStrategy (TWCS):   best for time-series, groups by time window

================================================================
BLOOM FILTER
================================================================

  A probabilistic data structure that quickly checks:
  "Is this partition key POSSIBLY in this SSTable?"

  - If Bloom filter says NO  --> skip that SSTable (definitive)
  - If Bloom filter says YES --> may or may not be there (check SSTable)
  - False positives possible; false negatives NEVER
  - Dramatically reduces disk I/O for key lookups

================================================================
INTERVIEW Q&A
================================================================

  Q: How does Cassandra distribute data across nodes?
  A: By hashing the partition key with Murmur3 to get a token.
     Each node owns a range of tokens. Data goes to the node(s)
     responsible for that token range.

  Q: What are virtual nodes (vnodes) in Cassandra?
  A: Each physical node manages multiple token ranges (virtual nodes).
     Enables better load balancing and faster node addition/removal.

  Q: What is the write path in Cassandra?
  A: Write goes to Commit Log (durability) and Memtable (performance).
     Memtable is periodically flushed to immutable SSTables on disk.
     Compaction merges SSTables over time.

  Q: Why is Cassandra optimized for writes but reads can be slower?
  A: Writes are sequential (append to Commit Log + Memtable) = O(1) per write.
     Reads may need to check multiple SSTables (before compaction) = I/O overhead.
     Bloom filters minimize unnecessary SSTable checks.
     LeveledCompaction improves reads at the cost of more compaction I/O.
