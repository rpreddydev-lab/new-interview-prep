================================================================
  GRAPH DATABASE USE CASES
================================================================

================================================================
1. SOCIAL NETWORKS
================================================================

  Data: Users, FOLLOWS, FRIEND, BLOCKED, LIKED relationships.

  Queries:
  - Friends of friends (depth-2 traversal)
  - Mutual friends between two users
  - Shortest path between two users
  - Influencer detection (highest in-degree count)
  - Community detection (graph clustering)

  Why graph?
  In relational, finding 5-hop friendship chains requires 5 JOINs.
  In Neo4j: MATCH path = (a:User)-[:FRIEND*5]-(b:User)
  Relationship traversal is O(1) per hop in native graph storage.

================================================================
2. RECOMMENDATION ENGINES
================================================================

  Data: Users, Products, PURCHASED, VIEWED, REVIEWED, SIMILAR_TO.

  "Customers also bought" pattern:
  MATCH (:User { id: 'U001' })-[:PURCHASED]->(prod:Product)
        <-[:PURCHASED]-(:User)-[:PURCHASED]->(rec:Product)
  WHERE NOT (:User { id: 'U001' })-[:PURCHASED]->(rec)
  RETURN rec.name, COUNT(*) AS score
  ORDER BY score DESC LIMIT 10;

  Why graph?
  Collaborative filtering via relationship traversal is natural.
  In SQL: requires multiple self-joins on purchase history.

================================================================
3. FRAUD DETECTION
================================================================

  Data: Accounts, Devices, IPs, Transactions, Cards linked with
        relationships: USES, TRANSFERS_TO, SHARED_DEVICE, SAME_ADDRESS.

  Pattern: shared device or IP between multiple accounts is a fraud signal.

  MATCH (fraud:Account)-[:USES]->(device:Device)<-[:USES]-(suspect:Account)
  WHERE fraud.status = 'FRAUD' AND suspect <> fraud
  RETURN DISTINCT suspect.accountId, suspect.name;

  Ring fraud detection: A -> B -> C -> A (circular transactions)

  MATCH path = (a:Account)-[:TRANSFERRED_TO*3..5]->(a)
  RETURN path;

  Why graph?
  Circular and cross-entity patterns are expensive in SQL.
  In graph: pattern expressed directly, O(1) per hop traversal.

================================================================
4. ACCESS CONTROL AND PERMISSIONS
================================================================

  Data: Users, Groups, Roles, Permissions, Resources.
  Relationships: MEMBER_OF, HAS_ROLE, GRANTS, ASSIGNED_TO.

  "Does user U001 have permission to access Resource R99?"

  MATCH (:User { id: 'U001' })-[:MEMBER_OF*0..]->(group:Group)
        -[:HAS_ROLE]->(role:Role)
        -[:GRANTS]->(perm:Permission { resource: 'R99', action: 'READ' })
  RETURN COUNT(perm) > 0 AS hasAccess;

  Why graph?
  Role hierarchy is a graph problem.
  Recursive group membership is O(depth) in graph; recursive SQL needed in RDBMS.

================================================================
5. KNOWLEDGE GRAPH / SEMANTIC WEB
================================================================

  Data: Concepts, Entities, IS_A, PART_OF, RELATED_TO relationships.
  Used by: Google Knowledge Graph, Wikipedia, enterprise taxonomy.

  "Find all drugs that treat a symptom and share a mechanism with Drug X":
  MATCH (d:Drug { name: 'DrugX' })-[:MECHANISM]->(m:Mechanism)
        <-[:MECHANISM]-(other:Drug)-[:TREATS]->(symptom:Symptom)
  RETURN other.name, symptom.name;

================================================================
6. NETWORK TOPOLOGY AND IT OPERATIONS
================================================================

  Data: Servers, Applications, Databases, Networks, DEPENDS_ON,
        CONNECTS_TO, RUNS_ON relationships.

  Impact analysis: "If Server S5 goes down, what applications are affected?"

  MATCH (s:Server { name: 'S5' })<-[:DEPENDS_ON*1..5]-(app:Application)
  RETURN app.name, app.team, app.criticality;

================================================================
7. SUPPLY CHAIN / BILL OF MATERIALS
================================================================

  Data: Products, Components, CONTAINS, SUPPLIED_BY relationships.

  "What raw materials does Product P contain at any depth?"

  MATCH (:Product { id: 'P42' })-[:CONTAINS*]->(raw:RawMaterial)
  RETURN raw.name, raw.supplier;

  Recall query: "Which products contain Component C (possibly buried 5 levels deep)?"

  MATCH (p:Product)-[:CONTAINS*1..10]->(c:Component { id: 'C99' })
  RETURN DISTINCT p.name;

================================================================
WHEN NOT TO USE A GRAPH DATABASE
================================================================

  - Simple tabular data with no complex relationships
  - Primary queries are aggregations (SUM revenue by category) -- use RDBMS
  - Bulk data loading and batch analytics -- use column-store / data warehouse
  - High-write time-series data -- use Cassandra or InfluxDB

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a graph database best at?
  A: Queries that traverse relationships: social networks,
     fraud detection, recommendations, knowledge graphs,
     access control hierarchies, network topology.
     These require many JOINs in SQL but are simple pattern matches in graph.

  Q: Can you give a real-world example where a graph DB outperforms SQL?
  A: Fraud detection ring patterns: finding circular money transfers
     (A sends to B, B to C, C back to A) at any depth.
     In SQL: recursive CTEs needed, O(n^depth) performance.
     In Neo4j: MATCH path = (a:Account)-[:TRANSFERRED*3..5]->(a)
     -- O(edges) traversal with pointer chasing.
