================================================================
ANALYSIS PIPELINE
================================================================

  Text field value goes through analysis at index time AND query time:

  RAW TEXT --> Tokenizer --> Token Filters --> Indexed Tokens

  "The Quick Brown Fox"
     |
  Tokenizer (standard): ["The", "Quick", "Brown", "Fox"]
     |
  Lowercase filter:     ["the", "quick", "brown", "fox"]
     |
  Stop words filter:    ["quick", "brown", "fox"]
     |
  Stemmer (english):    ["quick", "brown", "fox"]
                             (foxes --> fox)

================================================================
BUILT-IN ANALYZERS
================================================================

  standard   --> Unicode tokenization, lowercase, removes punctuation
  english    --> lowercase + stop words + English stemmer
  whitespace --> splits only on whitespace, no lowercasing
  keyword    --> no tokenization (entire string as one token)
  simple     --> splits on non-alpha, lowercases
  stop       --> like simple + removes stop words

  Test an analyzer:
  POST /_analyze
  { "analyzer": "english", "text": "Running quickly through the woods" }

================================================================
CUSTOM ANALYZER
================================================================

  PUT /my_index
  {
    "settings": {
      "analysis": {
        "char_filter": {
          "html_strip_filter": { "type": "html_strip" }
        },
        "tokenizer": {
          "my_tokenizer": { "type": "standard" }
        },
        "filter": {
          "my_stop":    { "type": "stop",    "stopwords": "_english_" },
          "my_stemmer": { "type": "stemmer", "language": "english" },
          "my_synonym": {
            "type": "synonym",
            "synonyms": ["laptop, notebook => laptop", "tv, television => tv"]
          }
        },
        "analyzer": {
          "my_custom": {
            "char_filter": ["html_strip_filter"],
            "tokenizer":   "my_tokenizer",
            "filter":      ["lowercase", "my_stop", "my_synonym", "my_stemmer"]
          }
        }
      }
    },
    "mappings": {
      "properties": {
        "description": { "type": "text", "analyzer": "my_custom" }
      }
    }
  }

================================================================
RELEVANCE SCORING
================================================================

  TF-IDF (classic Lucene):
  - TF  = Term Frequency  -- how often term appears in the document
  - IDF = Inverse Document Frequency -- how rare the term is across all docs
  - Score = TF * IDF; rare terms in frequently matched docs score higher

  BM25 (default since ES 5):
  - Improvement over TF-IDF
  - Saturates TF (extra occurrences give diminishing returns)
  - Accounts for field length (shorter fields score higher for same term)
  - Parameters: k1 (term frequency saturation ~1.2), b (length normalization ~0.75)

  _score field in response shows computed relevance.

  Boosting fields in multi_match:
  "fields": ["title^3", "description^1", "tags^2"]

================================================================
PHRASE MATCHING
================================================================

  match_phrase: all terms must be in order AND adjacent

  { "match_phrase": { "description": "noise cancelling headphones" } }

  Slop: allows up to N positions between terms
  { "match_phrase": { "description": { "query": "noise headphones", "slop": 1 } } }

  -- slop 1 means one word can appear between "noise" and "headphones"

================================================================
AUTOCOMPLETE -- EDGE NGRAM TOKENIZER
================================================================

  Settings:
  "tokenizer": {
    "autocomplete_tokenizer": {
      "type": "edge_ngram",
      "min_gram": 1,
      "max_gram": 20,
      "token_chars": ["letter", "digit"]
    }
  }

  For input "Laptop":
  Edge ngrams: ["L", "La", "Lap", "Lapt", "Lapte", "Laptop"]

  At query time use "standard" analyzer (not edge_ngram):
  "fields": {
    "name": { "type": "text", "analyzer": "standard" },
    "name.autocomplete": {
      "type": "text",
      "analyzer": "autocomplete_analyzer",
      "search_analyzer": "standard"
    }
  }

================================================================
HIGHLIGHTING
================================================================

  Returns matched text with surrounding context, html-tagged:

  {
    "query": { "match": { "description": "wireless" } },
    "highlight": {
      "fields": {
        "description": {
          "fragment_size": 150,
          "number_of_fragments": 3,
          "pre_tags":  ["<em>"],
          "post_tags": ["</em>"]
        }
      }
    }
  }

  Response includes: "_source" + "highlight": { "description": ["...best <em>wireless</em> headphones..."] }

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between an analyzer, tokenizer, and token filter?
  A: Tokenizer splits text into tokens (e.g., by whitespace or punctuation).
     Token filters transform each token (lowercase, remove stop words, stem).
     An analyzer chains char_filter + tokenizer + token filters in sequence.

  Q: Why use BM25 instead of TF-IDF?
  A: BM25 handles term frequency saturation and field length normalization better.
     With TF-IDF, a term appearing 100x always scores higher; BM25 saturates
     so 100 occurrences is not much better than 10. Also BM25 penalizes long
     fields less harshly, resulting in more natural rankings.

  Q: How does edge ngram enable autocomplete?
  A: At index time, "Laptop" is tokenized into ["L","La","Lap","Lapt","Lapto","Laptop"].
     When the user types "Lap", the standard analyzer produces token "lap".
     Elasticsearch finds "lap" in the edge ngram index and returns the document.
     Use different analyzers for indexing (edge_ngram) vs querying (standard)
     to avoid matching "L" against "lap" query.
