  TIME SERIES DATABASES OVERVIEW
================================================================

================================================================
WHAT IS TIME SERIES DATA?
================================================================

  A sequence of data points indexed in time order.
  Each data point has: timestamp + one or more metric values.

  Examples:
  - CPU usage:    2024-01-15 10:00:00 | server=web01 | cpu=72.5
  - Stock price:  2024-01-15 10:00:01 | symbol=AAPL  | price=189.23
  - Temperature:  2024-01-15 10:00:05 | sensor=abc   | temp=23.4
  - HTTP request: 2024-01-15 10:00:05 | path=/api    | latency=45ms

  Characteristics:
  - Append-only (rarely update old values)
  - High ingestion rate (millions of points/sec)
  - Time-ordered reads (most recent or range queries)
  - Queries aggregate over time windows (avg last 5 min)
  - Old data can be downsampled or deleted

================================================================
WHY NOT JUST USE RDBMS?
================================================================

  RDBMS problem:
  - Writes to random index pages = slow for high-volume inserts
  - Old data grows without bound = table too large
  - Aggregations over billions of rows = slow
  - No built-in retention policies or downsampling
  - Schema not optimized for tags/labels filtering

  Time Series DB solution:
  - Columnar storage = adjacent timestamps stored together (fast scan)
  - Compressed storage: delta encoding for timestamps (save 80%+)
  - Built-in rollup/downsampling: keep 1s data 7 days, 1m data 90 days
  - Retention policies: auto-delete old data
  - Tag-based indexing: filter by server, region, service efficiently

================================================================
KEY CONCEPTS
================================================================

  Measurement / Metric  --> name of what is being measured (cpu_usage, requests)
  Tag                   --> metadata label, indexed, low cardinality (server="web01")
  Field                 --> actual value, not indexed, high cardinality (cpu=72.5)
  Timestamp             --> nanosecond precision usually
  Series                --> unique combination of measurement + tag set
  Retention Policy      --> how long data is kept
  Continuous Query      --> automatic downsampling on schedule

  Tag vs Field is critical:
  - Tags are indexed --> use for filtering/grouping
  - Fields are not indexed --> use for actual measurements
  - Don't put high-cardinality values in tags (user_id with millions of users)

================================================================
WHEN TO USE A TIME SERIES DATABASE
================================================================

  USE WHEN:
  - IoT sensor data (thousands of devices, high frequency writes)
  - Application performance monitoring (APM)
  - Infrastructure metrics (CPU, memory, network, disk)
  - Financial market data (tick data, OHLCV)
  - Business KPIs tracked over time (daily signups, revenue)
  - Log-based metrics

  AVOID WHEN:
  - Data is not primarily time-ordered
  - Need complex relational joins
  - Small volume of data (RDBMS works fine)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between a tag and a field in InfluxDB?
  A: Tags are string key-value pairs that are indexed -- use for filtering and grouping.
     Fields are actual numeric/string measurements that are NOT indexed.
     High-cardinality values (user IDs, UUIDs) must go in fields, never tags,
     or you get cardinality explosion that degrades performance.

  Q: How does a time series DB store data more efficiently than RDBMS?
  A: Columnar layout stores timestamps contiguously, enabling delta compression
     (store differences rather than full values). Metrics are similarly compressed
     using algorithms like Gorilla (Facebook's float compression).
     Combined: 10x-100x storage savings over row-based RDBMS.
