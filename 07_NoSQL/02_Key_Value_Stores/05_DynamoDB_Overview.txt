================================================================
  DYNAMODB OVERVIEW
================================================================

  Amazon DynamoDB is a fully managed NoSQL database service on AWS.
  Key-value + document hybrid model.
  Designed for extreme scale: millions of requests per second.
  Serverless: no cluster management, auto-scaling built-in.

================================================================
CORE CONCEPTS
================================================================

  Table         Collection of items (like MongoDB collection)
  Item          A single record (like a document or row)
  Attribute     A data element in an item (like a field)
  Primary Key   Uniquely identifies each item

================================================================
PRIMARY KEY TYPES
================================================================

  Partition Key (Hash Key) Only:
    Single attribute. DynamoDB uses a hash function to distribute
    items across partitions.
    Example: { "user_id": "U001" }

  Composite Key (Partition Key + Sort Key):
    Two attributes together uniquely identify an item.
    All items with the same partition key are stored together,
    sorted by the sort key.
    Example: { "user_id": "U001", "order_date": "2024-01-15" }
    --> Retrieve all orders for user U001 in a date range.

================================================================
DATA MODELING: SINGLE TABLE DESIGN
================================================================

  DynamoDB best practice: put multiple entity types in ONE table.
  Use the partition key + sort key to model different access patterns.

  PK            SK              Attributes
  ----------    ------------    -------------------------------------------
  USER#U001     PROFILE         name, email, created_at
  USER#U001     ORDER#ORD001    total, status, order_date
  USER#U001     ORDER#ORD002    total, status, order_date
  PRODUCT#P42   METADATA        name, price, category
  PRODUCT#P42   REVIEW#R001     rating, comment, user_id

  Overloaded keys = different entity types share the same table.
  GSI (Global Secondary Index) enables different access patterns.

================================================================
GLOBAL SECONDARY INDEX (GSI)
================================================================

  A GSI creates an alternate key structure for a different access pattern.

  Table primary key: user_id (PK)
  GSI:   email (PK)  --> enables lookup by email

  Table primary key: user_id (PK), order_date (SK)
  GSI:   status (PK), order_date (SK) --> get all orders by status

  A table can have up to 20 GSIs.

  Local Secondary Index (LSI):
  Same partition key, different sort key.
  Must be defined at table creation.

================================================================
READ/WRITE OPERATIONS
================================================================

  GetItem         Single item by exact primary key (O(1))
  PutItem         Create or overwrite an item
  UpdateItem      Update specific attributes of an item
  DeleteItem      Delete an item by primary key
  Query           Retrieve items with same partition key, range on sort key
  Scan            Read entire table (avoid in production -- expensive)
  BatchGetItem    Multiple GetItem in one request
  BatchWriteItem  Multiple PutItem/DeleteItem in one request
  TransactGet     ACID-like read of multiple items
  TransactWrite   ACID-like write of multiple items (up to 100)

================================================================
CONSISTENCY MODELS
================================================================

  Eventually Consistent Read (default):
  - Slightly stale data possible
  - Half the read capacity cost of strongly consistent
  - Usually fine for most reads

  Strongly Consistent Read:
  - Returns latest committed data
  - Uses full read capacity
  - Required when freshness is critical

================================================================
CAPACITY MODES
================================================================

  On-Demand:
  - Pay per request (no capacity planning)
  - Auto-scales instantly
  - More expensive at high, predictable load

  Provisioned:
  - Specify RCU (Read Capacity Units) and WCU (Write Capacity Units)
  - Can use Auto Scaling to adjust
  - Cheaper at steady, predictable load
  - ThrottlingException if you exceed provisioned capacity

================================================================
COMPARISON WITH MONGODB
================================================================

  Feature               DynamoDB                    MongoDB
  --------------------  --------------------------  --------------------------
  Hosting               AWS managed only            Self-hosted or Atlas
  Scaling               Auto-scales, serverless     Manual sharding or Atlas
  Query flexibility     Limited (key-based)         Rich (any field indexed)
  Schema                Flexible per item           Flexible per document
  ACID                  Transactions (up to 100)    Full ACID (4.0+)
  Pricing               Per request / provisioned   Atlas tiers or self-hosted
  Best for              AWS workloads, serverless   General-purpose documents

================================================================
SPRING BOOT DYNAMODB INTEGRATION
================================================================

  <!-- AWS SDK for DynamoDB Enhanced Client -->
  <dependency>
      <groupId>software.amazon.awssdk</groupId>
      <artifactId>dynamodb-enhanced</artifactId>
  </dependency>

  @DynamoDbBean
  public class Product {
      @DynamoDbPartitionKey
      private String id;
      @DynamoDbSortKey
      private String category;
      private String name;
      private BigDecimal price;
  }

  DynamoDbTable<Product> table = enhancedClient.table("products",
      TableSchema.fromBean(Product.class));

  table.putItem(product);
  Product found = table.getItem(Key.builder().partitionValue("P42").build());

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between a partition key and a sort key in DynamoDB?
  A: Partition key determines which physical partition stores the item (hash-based).
     Sort key orders items within the same partition and enables range queries.
     Together they form a composite primary key for modeling entity relationships.

  Q: What is Single Table Design in DynamoDB?
  A: Putting multiple entity types in one table, using overloaded
     partition key + sort key values to represent different entities.
     Avoids expensive cross-table queries; all access is by key.
     Requires upfront access pattern analysis.

  Q: When would you use DynamoDB over MongoDB?
  A: DynamoDB for AWS-native serverless workloads, extreme scale,
     and when access patterns are well-defined (key-based).
     MongoDB for flexible querying, rich query language, and multi-cloud.
