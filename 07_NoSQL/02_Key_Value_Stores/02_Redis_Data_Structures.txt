================================================================
  REDIS DATA STRUCTURES
================================================================

================================================================
STRING
================================================================

  Most basic type. Stores text, numbers, serialized JSON/binary.
  Max 512MB per value.

  SET name "Alice"
  GET name          --> "Alice"
  INCR counter      --> 1, 2, 3 ... (atomic)
  APPEND greeting " World"

  Use cases: caching, counters, session tokens, flags.

================================================================
HASH
================================================================

  Map of field --> value pairs inside one key.
  Like a struct or Java Map<String, String>.

  HSET user:1001 name "Alice" email "alice@ex.com" age "30"
  HGET user:1001 name          --> "Alice"
  HMGET user:1001 name email   --> ["Alice", "alice@ex.com"]
  HGETALL user:1001            --> {name:Alice, email:alice@ex.com, age:30}
  HDEL user:1001 age
  HEXISTS user:1001 email      --> 1
  HLEN user:1001               --> field count
  HINCRBY user:1001 score 10

  Use cases: user profiles, object attributes, counters per entity.
  More memory-efficient than separate keys per field.

================================================================
LIST
================================================================

  Ordered list of strings. Duplicates allowed.
  Implemented as a doubly linked list. O(1) at head/tail.

  LPUSH jobs task1 task2    -- push to left (head)
  RPUSH jobs task3          -- push to right (tail)
  LPOP jobs                 -- pop from left
  RPOP jobs                 -- pop from right
  LRANGE jobs 0 -1          -- all elements (0 to last)
  LLEN jobs                 -- length
  BLPOP jobs 30             -- blocking pop, wait up to 30s

  Use cases:
  - Message queue (LPUSH + BRPOP = simple FIFO queue)
  - Recent activity feed (LPUSH + LTRIM to cap size)
  - Stack (LPUSH + LPOP)

  LTRIM jobs 0 99           -- keep only first 100 items (cap list size)

================================================================
SET
================================================================

  Unordered collection of unique strings.

  SADD tags:product:42 "electronics" "computers" "sale"
  SMEMBERS tags:product:42          --> {"electronics","computers","sale"}
  SISMEMBER tags:product:42 "sale"  --> 1
  SCARD tags:product:42             --> 3 (count)
  SREM tags:product:42 "sale"
  SPOP tags:product:42              --> random element (remove)
  SRANDMEMBER tags:product:42 2     --> 2 random (no remove)

  Set operations:
  SUNION set1 set2          --> union of all members
  SINTER set1 set2          --> intersection
  SDIFF  set1 set2          --> difference (in set1 not set2)

  Use cases: tags, unique visitors per page, friend lists, permissions.

================================================================
SORTED SET (ZSET)
================================================================

  Like Set but each member has a floating-point score.
  Sorted by score. Members are unique; scores can repeat.

  ZADD leaderboard 1500 "alice" 2300 "bob" 1800 "carol"
  ZSCORE leaderboard "bob"              --> 2300
  ZRANK leaderboard "alice"             --> 0 (lowest score rank)
  ZREVRANK leaderboard "bob"            --> 0 (highest score rank)
  ZRANGE leaderboard 0 -1 WITHSCORES   --> all members with scores (asc)
  ZREVRANGE leaderboard 0 2             --> top 3 (desc)
  ZRANGEBYSCORE leaderboard 1000 2000   --> range by score
  ZINCRBY leaderboard 100 "alice"       --> increment score
  ZREM leaderboard "alice"

  Use cases:
  - Leaderboards (ZREVRANGE for top-N)
  - Rate limiting (sliding window: score=timestamp)
  - Priority queues (score=priority)
  - Expiring session tokens (score=expiry timestamp)
  - Delayed job queues

================================================================
BITMAP
================================================================

  Bit array operations on a string key.

  SETBIT user_active:2024-01-15 1001 1   -- user 1001 was active today
  GETBIT user_active:2024-01-15 1001     --> 1
  BITCOUNT user_active:2024-01-15        --> how many users active today
  BITOP AND result key1 key2             --> users active on both days

  Use cases: daily active users, feature flag per user at scale.

================================================================
HYPERLOGLOG
================================================================

  Probabilistic data structure for cardinality estimation.
  Uses ~12KB regardless of actual cardinality.
  Error rate: ~0.81%.

  PFADD unique_visitors "user1" "user2" "user3"
  PFCOUNT unique_visitors     --> approximate count
  PFMERGE merged key1 key2   --> merge two HLLs

  Use cases: approximate unique visitor counts, distinct events.

================================================================
GEO
================================================================

  Stores geographic coordinates as sorted set (internally).

  GEOADD locations 13.361389 38.115556 "Palermo"
  GEOADD locations 15.087269 37.502669 "Catania"
  GEODIST locations "Palermo" "Catania" km   --> 166.27
  GEORADIUS locations 15 37 200 km WITHCOORD WITHDIST

  Use cases: nearby stores, driver tracking, location-based features.

================================================================
STREAM
================================================================

  Append-only log data structure (like Kafka log, but in-memory).

  XADD events * action "purchase" user_id "1001" amount "99.99"
  XLEN events                         --> count of entries
  XRANGE events - +                   --> all events
  XREAD COUNT 10 STREAMS events 0     --> read from beginning
  XGROUP CREATE events mygroup $      --> consumer group

  Use cases: event sourcing, audit log, real-time analytics, IoT events.

SUMMARY TABLE
================================================================

  Type          Commands           Use Case
  -----------   ----------------   ---------------------------------
  String        GET/SET/INCR       Cache, counters, session tokens
  Hash          HGET/HSET          Object attributes, user profile

  Set           SADD/SMEMBERS      Tags, unique members, friend list

================================================================
INTERVIEW Q&A
================================================================

  Q: What data structure would you use for a leaderboard in Redis?
  A: Sorted Set (ZSET). ZADD stores user+score, ZREVRANGE retrieves
     top N users, ZINCRBY atomically increments a user's score.
     O(log N) insertion and retrieval.

  Q: How would you implement a simple message queue with Redis?
  A: LPUSH to enqueue messages, BRPOP to dequeue (blocking pop).
     BRPOP waits up to a timeout for a message -- efficient for workers.
     For durable, consumer-group messaging use Redis Streams.

  Q: What is a Redis HyperLogLog?
  A: A probabilistic data structure that estimates the cardinality
     (count of distinct elements) using ~12KB of memory.
     0.81% error rate. Use for approximate unique visitor counts.
