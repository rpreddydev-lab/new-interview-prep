================================================================
  KEY-VALUE STORES OVERVIEW
================================================================

  A key-value store is the simplest NoSQL model:
  Data is stored as a pair: KEY --> VALUE.

  Like a giant distributed HashMap / Dictionary.

================================================================
CORE CONCEPTS
================================================================

  Key     Unique identifier. Usually a string.
          Examples: "user:1001", "session:abc123", "product:42"

  Value   The associated data. Can be:
          - Simple string: "Alice"
          - Number: "42"
          - JSON blob: '{"name":"Alice","age":30}'
          - Binary data
          - Rich types (Redis): lists, sets, hashes, sorted sets, streams

================================================================
KEY DESIGN PATTERNS
================================================================

  Use structured keys with delimiters for clarity:

  Pattern                      Example
  ---------------------------  ----------------------------------
  entity:id                    "user:1001"
  entity:id:field              "user:1001:email"
  namespace:entity:id          "prod:session:abc123"
  composite lookup             "product:category:electronics"

================================================================
ADVANTAGES
================================================================

  1. Extremely fast reads and writes (O(1) per key lookup)
  2. Simple API: GET, SET, DEL
  3. Scales horizontally via consistent hashing
  4. Flexible values (any binary data)
  5. Great for caching, sessions, rate limiting

================================================================
LIMITATIONS
================================================================

  1. No rich query support (no WHERE, no range queries by default)
  2. Must know the exact key to retrieve data
  3. No relationships between keys
  4. No schema enforcement
  5. Not suitable for complex business data modeling

================================================================
POPULAR KEY-VALUE STORES
================================================================

  Redis       In-memory, rich data structures, pub/sub, Lua scripting,
              persistence options, cluster support.
              Use for caching, sessions, rate limiting, queues.

  Memcached   Simple in-memory cache. Multi-threaded. No persistence.
              Use for pure caching. No advanced data structures.

  DynamoDB    AWS managed KV+document store. Serverless scale.
              Use for AWS-native, globally distributed KV workloads.

  Riak        Distributed AP database. Conflict resolution built-in.

  etcd        Strongly consistent distributed KV. Used for cluster config.
              Powers Kubernetes leader election and config storage.

================================================================
WHEN TO USE KEY-VALUE STORES
================================================================

  Session storage     user_id --> session JSON (with TTL)
  Cache               db:query:hash --> result JSON
  Rate limiting       ip:endpoint --> request count + TTL
  Shopping cart       cart:user_id --> serialized cart
  Config              feature_flag:name --> boolean/json
  Lock/mutex          lock:resource_id --> acquired_by (with TTL)
  Counters            views:post_id --> integer (INCR)
  Pub/Sub             Redis channels for real-time messaging
  Leaderboard         Redis sorted set for ranked scores

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a key-value store?
  A: A NoSQL database that stores data as key-value pairs -- like a
     distributed HashMap. Extremely fast O(1) reads/writes by key.
     No query language; you must know the key to retrieve data.

  Q: When would you choose Redis over a relational database for sessions?
  A: Redis stores sessions in memory with TTL support.
     Retrieval is O(1) by session key vs a DB query.
     Scales horizontally. No complex SQL needed for session data.
