  NOSQL DATA MODELING OVERVIEW
================================================================

================================================================
KEY DIFFERENCE FROM RELATIONAL MODELING
================================================================

  Relational (normalize first):
  1. Model the data -- identify entities, normalize to 3NF
  2. Application queries follow the schema

  NoSQL (query first):
  1. Identify ALL access patterns your application needs
  2. Design the data model to serve those access patterns efficiently
  3. Denormalize, duplicate, and pre-aggregate to avoid expensive operations

  Rule: "NoSQL data modeling = optimizing for reads at the cost of writes"

================================================================
STEP 1 -- IDENTIFY ACCESS PATTERNS
================================================================

  Before writing any schema, list every query your app performs:

  Example: E-commerce order system access patterns:
  - Get order by order ID                    --> GET /orders/{id}
  - Get all orders for a user                --> GET /users/{userId}/orders
  - Get orders by status (PENDING/SHIPPED)   --> GET /orders?status=PENDING
  - Get orders in date range                 --> GET /orders?from=X&to=Y
  - Get order items for an order             --> GET /orders/{id}/items

  Each access pattern maps to:
  - A primary key structure (in DynamoDB/Cassandra)
  - An index (in MongoDB/Elasticsearch)
  - A collection/table design choice

================================================================
MODELING DECISIONS TREE
================================================================

  Is the data accessed together?
  YES --> Embed (document DB) or denormalize (wide column)
  NO  --> Reference (separate collection) or normalize

  Can one side grow unboundedly?
  YES --> Reference (avoid unbounded arrays / wide rows)
  NO  --> Embed

  Do you need transactions across both sides?
  YES --> Keep together or use RDBMS
  NO  --> Either approach works

  Are there multiple different access patterns?
  YES --> Duplicate data into multiple tables/indexes (Cassandra pattern)
         or use GSI/secondary index (DynamoDB, MongoDB)

================================================================
INTERVIEW Q&A
================================================================

  Q: How is NoSQL data modeling different from relational modeling?
  A: Relational modeling normalizes data to reduce redundancy, then writes
     queries to join tables. NoSQL starts with access patterns: you design
     the schema to serve each query directly with minimal joins (or none).
     This means accepting data duplication in exchange for read performance
     and horizontal scalability.

  Q: What is the first step in NoSQL data modeling?
  A: Enumerate all access patterns the application needs. Before writing
     any schema, document every read and write: what data is needed,
     in what order, filtered/sorted how. Each pattern drives key structure,
     index choices, and whether to embed or reference related data.
