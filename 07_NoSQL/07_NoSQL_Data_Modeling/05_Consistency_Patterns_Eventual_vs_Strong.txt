================================================================
  CONSISTENCY PATTERNS: EVENTUAL VS STRONG
================================================================

================================================================
THE CONSISTENCY SPECTRUM
================================================================

  STRONG          CAUSAL         SESSION       EVENTUAL
  (linearizable)  (happens-before)(read-own-writes)(no guarantee)
       |              |               |               |
  Most consistent                             Most available

================================================================
STRONG CONSISTENCY (LINEARIZABILITY)
================================================================

  Every read returns the result of the most recent completed write.
  Behaves as if there is only one copy of the data.

  How it feels: After you write, anyone who reads immediately sees your write.

  Cost:
  - Requires coordination between nodes (quorum or single primary writes)
  - Higher latency (wait for quorum acknowledgment)
  - Lower availability (cannot respond during network partition)

  Databases: MongoDB (w:majority + readConcern:majority), HBase, Zookeeper,
             etcd, Google Spanner

  Use when: financial transactions, inventory counts, seat reservations

================================================================
EVENTUAL CONSISTENCY
================================================================

  If no new updates are made, all replicas will eventually converge to the same value.
  Reads may return stale data.

  How it feels: You write, a friend reads immediately and may see old value.
  After some time (milliseconds to seconds), all replicas agree.

  Cost:
  - Must handle stale reads in application code
  - Conflict resolution for concurrent writes

  Databases: Cassandra (default), DynamoDB (default), CouchDB

  Use when: product catalog, social media feeds, analytics counts, user preferences

================================================================
CAUSAL CONSISTENCY
================================================================

  Operations that are causally related appear in order.
  Unrelated operations may appear in any order.

  Example: You post a comment, then reply to it.
  Causal consistency guarantees the comment is visible before the reply.
  Without it, a replica could show the reply before the comment.

  MongoDB: causal sessions with afterClusterTime provide causal consistency.
  Cassandra: PAXOS-based lightweight transactions (LWT) for conditional writes.

================================================================
SESSION CONSISTENCY (READ YOUR OWN WRITES)
================================================================

  Within a single session/connection, reads always reflect your own writes.
  Other users may still see stale data.

  Implementation:
  - Read from primary (MongoDB default)
  - Use sticky sessions (always route to same replica)
  - Read-your-writes via version tracking (read with min-version token)

  DynamoDB: consistent reads option per request.
  Cassandra: use LOCAL_QUORUM for read-your-own-writes in same DC.

================================================================
TUNABLE CONSISTENCY IN CASSANDRA
================================================================

  Cassandra lets you choose consistency level per operation:

  Level         | Description
  --------------|-----------------------------------------------------
  ONE           | Response from 1 replica (fastest, least consistent)
  TWO           | Response from 2 replicas
  THREE         | Response from 3 replicas
  QUORUM        | Response from majority: (RF/2)+1 replicas
  LOCAL_QUORUM  | Quorum within local datacenter
  EACH_QUORUM   | Quorum in each datacenter
  ALL           | Response from all replicas (slowest, most consistent)
  LOCAL_ONE     | 1 replica in local DC
  ANY           | Even hinted handoff counts (highest availability)
  SERIAL        | For lightweight transactions (paxos)

  For RF=3:
  W=QUORUM, R=QUORUM --> W+R=4 > 3 --> guaranteed to see latest write

================================================================
CONFLICT RESOLUTION
================================================================

  Problem: two nodes accept concurrent writes to the same key.
  Who wins?

  Last Write Wins (LWW):
  - Each write has a timestamp; higher timestamp wins
  - Cassandra uses this by default
  - Flaw: clocks can drift; writes can be silently lost

  Vector Clocks:
  - Track causality per-replica; detect concurrent updates
  - Application must resolve conflicts when concurrent writes detected
  - Riak used this approach

  CRDTs (Conflict-free Replicated Data Types):
  - Data structures that can merge without conflict
  - Counters: just sum all increments from all replicas
  - Sets: union always converges (grow-only set)
  - Redis CRDT (Redis Enterprise), Riak, DynamoDB counters
  - Add-only: no deletion problems

  Application-level resolution:
  - Shopping cart: union of all items from all replicas
  - Counter: sum all increments; track per-node
  - Document: present both versions to user (Wikipedia edit conflict)

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the difference between eventual and strong consistency?
  A: Strong consistency (linearizability) guarantees every read returns the
     most recent write, as if one copy exists. This requires coordination
     and reduces availability. Eventual consistency only guarantees that
     replicas will converge given no new writes -- reads may be stale.
     Choose strong for financial data; eventual for social feeds, catalogs.

  Q: How does Cassandra achieve "strong" consistency if it is eventually consistent?
  A: By using QUORUM for both reads and writes with RF=3: W=2, R=2.
     Since W+R=4 > RF=3, at least one node overlaps both the write set
     and read set, guaranteeing the read sees the latest write. This is
     quorum-based strong consistency, not full linearizability, but
     sufficient for most use cases.

  Q: What is a CRDT and why is it useful?
  A: Conflict-free Replicated Data Types are data structures that can be
     merged across replicas without conflicts, always converging to the
     same result. A counter CRDT tracks increments per node; the total
     is the sum of all node increments -- no conflicts regardless of
     replication order. Useful for counters, shopping carts, and any
     additive aggregation under eventual consistency.
