================================================================================
SYSTEM DESIGN INTERVIEW APPROACH - THE COMPLETE FRAMEWORK
================================================================================
Last Updated: April 2026
Purpose: A step-by-step framework for attacking any system design interview
         question with confidence, structure, and depth.
================================================================================

--------------------------------------------------------------------------------
1. WHAT IS BEING EVALUATED IN A SYSTEM DESIGN INTERVIEW
--------------------------------------------------------------------------------

System design interviews are open-ended by nature. There is no single correct
answer. What the interviewer evaluates:

  ✓ Can you scope and clarify requirements?
  ✓ Do you understand distributed systems fundamentals?
  ✓ Can you make and justify architectural decisions?
  ✓ Do you discuss trade-offs rather than stating facts?
  ✓ Can you estimate scale and identify bottlenecks?
  ✓ Do you design for failure (fault tolerance, replication)?
  ✓ Can you communicate complex systems clearly?
  ✓ Do you have production systems intuition?

LEVEL EXPECTATIONS:
  Junior (0-3 yr): Usually no system design; sometimes high-level only
  Mid-level (3-6 yr): 1 SD round; fundamentals + one deep-dive area expected
  Senior (6-10 yr): 1-2 SD rounds; full design expected; trade-off depth required
  Staff/Principal: 2 SD rounds; expected to challenge requirements, discuss
                   organizational and operational complexity

--------------------------------------------------------------------------------
2. THE 6-PHASE SYSTEM DESIGN FRAMEWORK
--------------------------------------------------------------------------------

  PHASE 1: CLARIFY REQUIREMENTS          (5-7 minutes)
  PHASE 2: DEFINE SCOPE + SCALE          (5-7 minutes)
  PHASE 3: HIGH-LEVEL ARCHITECTURE       (10-12 minutes)
  PHASE 4: DEEP DIVE ON KEY COMPONENTS   (20-25 minutes)
  PHASE 5: TRADE-OFFS + FAILURE MODES    (8-10 minutes)
  PHASE 6: WRAP-UP + QUESTIONS           (3-5 minutes)

  TOTAL: ~60 minutes

--------------------------------------------------------------------------------
PHASE 1: CLARIFY REQUIREMENTS (5-7 minutes)
--------------------------------------------------------------------------------

System design problems are intentionally vague. Start by clarifying.

FUNCTIONAL REQUIREMENTS:
  "What are the core features this system must support?"
  
  Example for "Design Twitter":
  - Users can create posts (tweets)
  - Users can follow other users
  - Users have a home feed (timeline)
  - Users can search for tweets/users
  - Users can like/retweet

  Scope to 2-3 CORE features for the interview:
  "For this interview, let me focus on tweet creation, following, and
   the home feed, since those are the core interactions. Should I include
   search as well, or focus on those three?"

NON-FUNCTIONAL REQUIREMENTS:
  - Consistency vs. Availability: "Is it okay if a user doesn't see a new
    tweet for a few seconds, or is strict consistency required?"
  - Read vs. Write ratio: "Is this read-heavy, write-heavy, or balanced?"
  - Durability: "Can we lose data, or must everything be durable?"
  - Latency: "What's the acceptable latency for loading a feed?"

  Twitter-like system answers:
  - High availability; some eventual consistency acceptable for feed
  - Extremely read-heavy (100:1 read/write ratio)
  - High durability (users care about their tweets)
  - Feed should load in <500ms

THE MAKE-YOUR-OWN-ASSUMPTIONS TECHNIQUE:
  If interviewer says "make assumptions", state them explicitly:
  "I'll assume this is a global system with users worldwide, that we
   need high availability over strict consistency, and that the read-to-write
   ratio is roughly 100:1. The feed needs to load under 500ms."

--------------------------------------------------------------------------------
PHASE 2: DEFINE SCOPE + SCALE (5-7 minutes)
--------------------------------------------------------------------------------

CAPACITY ESTIMATION (BACK-OF-ENVELOPE):
  This demonstrates you can reason about scale.

  KEY NUMBERS TO KNOW:
  - 1 day = 86,400 seconds (~100K seconds for rough math)
  - Average tweet = ~300 bytes (text + metadata)
  - Average image = ~500KB
  - 1 GB = 10^9 bytes, 1 TB = 10^12 bytes, 1 PB = 10^15 bytes

  EXAMPLE ESTIMATION (Twitter-like):
  "Let me estimate the scale:
  
  Users: 300 million monthly active users, 50 million daily active users (DAU)
  
  Writes:
  - If 1% of DAU tweet daily: 500K tweets/day
  - 500K / 100K seconds = ~5 tweets/second
  - Peak (10x): 50 tweets/second
  
  Reads:
  - If each DAU reads 200 tweets/day: 10 billion reads/day
  - 10B / 100K = 100K reads/second
  - Read:Write ratio = 100K / 5 = ~20,000:1 (extremely read-heavy)
  
  Storage:
  - 5 tweets/sec × 86,400 sec/day × 300 bytes = ~130 MB/day
  - 130 MB/day × 365 = ~47 GB/year (for text only)
  - If 10% of tweets have images: much larger; ~1 TB/year with images
  
  This tells me: I need to optimize for reads, use heavy caching,
  and separate media storage from metadata storage."

WHY THIS MATTERS:
  - Tells you which database tier to use
  - Determines caching strategy
  - Defines replication and partition strategy

--------------------------------------------------------------------------------
PHASE 3: HIGH-LEVEL ARCHITECTURE (10-12 minutes)
--------------------------------------------------------------------------------

Start with the classic 3-tier architecture and expand:

  USERS → CLIENT (Web/Mobile)
       → API GATEWAY / LOAD BALANCER
       → APPLICATION SERVICES (microservices or monolith)
       → DATABASES + CACHES + QUEUES
       → STORAGE (object store, CDN)

DRAW IT AS YOU SPEAK:
  Use the whiteboard/Excalidraw from the start. A picture is worth 1000 words.

CORE COMPONENTS FOR MOST SYSTEMS:

  1. CLIENTS: Web browser, iOS app, Android app
  
  2. DNS + CDN:
     - DNS resolves to nearest CDN/load balancer
     - CDN caches static content (images, JS, CSS) close to users
  
  3. API GATEWAY / LOAD BALANCER:
     - Entry point for all requests
     - Handles: authentication, rate limiting, SSL termination
     - Distributes traffic to backend services
     - Options: Nginx, AWS API Gateway, Kong
  
  4. APPLICATION SERVICES:
     - Stateless web servers (can scale horizontally)
     - Separated by domain (tweet service, user service, feed service)
     - Communicate via REST (synchronous) or message queue (async)
  
  5. DATABASES:
     - Primary (write) + Replicas (read): reduces read load on primary
     - Sharding: partition data across multiple DB nodes
     - SQL vs NoSQL decision based on data model and consistency needs
  
  6. CACHE:
     - Redis or Memcached for hot data
     - Cache feed, user profiles, follower lists
     - Cache aside pattern (most common)
  
  7. MESSAGE QUEUE:
     - Kafka, RabbitMQ, Amazon SQS
     - Decouple producers from consumers
     - Buffer spikes in write traffic
     - Fan-out to multiple consumers
  
  8. OBJECT STORAGE:
     - Amazon S3, Google Cloud Storage
     - For large blobs: images, videos, backups
     - NOT for structured queries

WHAT MAKES A GOOD HIGH-LEVEL ARCHITECTURE:
  - Clear separation of concerns
  - Horizontal scalability obvious
  - No single point of failure (SPOF)
  - Communication protocols specified

--------------------------------------------------------------------------------
PHASE 4: DEEP DIVE ON KEY COMPONENTS (20-25 minutes)
--------------------------------------------------------------------------------

The interviewer will guide you toward specific areas to deep dive.
Prepare to go deep on ANY of these:

DEEP DIVE 1: DATA MODEL / DATABASE CHOICE
  - Define tables/documents
  - Primary keys, indexes, foreign keys
  - SQL vs NoSQL decision with justification
  - Sharding strategy

DEEP DIVE 2: THE FEED ALGORITHM (if applicable)
  - Push model (fan-out on write): pre-populate followers' feeds at write time
    - Pro: fast reads
    - Con: expensive writes for users with millions of followers
  - Pull model (fan-out on read): build feed at read time
    - Pro: cheap writes
    - Con: expensive reads (must query all followed users)
  - Hybrid: push for regular users, pull for celebrities (>1M followers)

DEEP DIVE 3: CACHING STRATEGY
  - What to cache: hot/trending items, user profiles, follower lists
  - Cache eviction: LRU (most common), LFU, TTL-based
  - Consistency: cache-aside (lazy loading) vs write-through vs write-behind
  - Cache invalidation: on write, via TTL, or pub/sub notification
  - Cache miss storm: use request coalescing or mutex

DEEP DIVE 4: DATABASE SCALING
  - Read replicas: route reads to replicas, writes to primary
  - Vertical scaling (bigger machine) - limited
  - Horizontal sharding: distribute data by user ID, tweet ID, etc.
  - Consistent hashing: minimizes rehashing when nodes added/removed
  - Cross-shard queries: expensive; avoid in hot path

DEEP DIVE 5: UNIQUE ID GENERATION
  - Problem: Multiple servers can't use auto-increment (collisions)
  - Options:
    a) UUID v4: globally unique, no coordination, but 128-bit (large)
    b) Twitter Snowflake: 64-bit, timestamp + machine ID + sequence
    c) Database sequence (single point): simpler but bottleneck
    d) Redis atomic increment: fast but Redis becomes critical
  - Preferred: Twitter Snowflake-style for high-throughput systems

DEEP DIVE 6: RATE LIMITING
  - Protect against DDoS and API abuse
  - Algorithms:
    a) Fixed window counter: simple but allows burst at window boundary
    b) Sliding window log: accurate but memory-intensive
    c) Token bucket: allows controlled bursts; most common (Stripe, AWS)
    d) Leaky bucket: smooth output rate
  - Storage: Redis for distributed rate limiting (INCR + EXPIRE)

DEEP DIVE 7: SEARCH
  - Dedicated search infrastructure (Elasticsearch, Apache Solr)
  - Inverted index: term → list of document IDs
  - Indexing: async, via Kafka (don't index inline with write path)
  - Ranking: TF-IDF, BM25, engagement-based signals

--------------------------------------------------------------------------------
PHASE 5: TRADE-OFFS + FAILURE MODES (8-10 minutes)
--------------------------------------------------------------------------------

This phase separates senior from junior candidates. Senior engineers think
about what goes WRONG and how to handle it.

TRADE-OFFS TO DISCUSS:
  
  SQL vs NoSQL:
  - SQL: ACID, joins, complex queries, schema enforcement
  - NoSQL: horizontal scale, flexible schema, eventual consistency
  - Choice: depends on data model and consistency requirements
  
  Microservices vs Monolith:
  - Microservices: independent scaling, team autonomy, complex ops
  - Monolith: simpler development, fewer network calls, easier debugging
  - Choice: team size, traffic patterns, deployment requirements
  
  Push vs Pull for feeds:
  - See Deep Dive 2 above
  
  Synchronous vs Asynchronous:
  - Sync: simpler, immediate feedback, latency tied to dependency
  - Async: decoupled, scalable, adds complexity (message ordering, replay)

FAILURE MODES TO DISCUSS:
  
  Database goes down:
  - Primary-replica failover with automatic promotion
  - How long until replica is promoted? (RTO = Recovery Time Objective)
  - What data is lost? (RPO = Recovery Point Objective)
  
  Cache goes down:
  - All traffic hits database (thundering herd)
  - Mitigate: multiple cache replicas, circuit breaker, cache warming
  
  Service overload:
  - Rate limiting, circuit breakers, graceful degradation
  - "If the recommendation service is slow, show most recent tweets instead"
  
  Network partition:
  - CAP theorem: can't have consistency AND availability during partition
  - Choose: accept stale reads (AP) or reject requests (CP)
  
  Message queue lag:
  - Consumer group falls behind
  - Metrics: consumer lag
  - Mitigate: scale consumers, prioritize critical messages, DLQ (dead letter queue)

--------------------------------------------------------------------------------
PHASE 6: WRAP-UP + QUESTIONS (3-5 minutes)
--------------------------------------------------------------------------------

CLOSE YOUR DESIGN WITH A SUMMARY:
  "To summarize what I've designed:
   - [Client] sends requests to [API gateway] with rate limiting
   - [Service A] handles [core function], writing to [DB] and publishing to [queue]
   - [Service B] consumes the queue and updates the [cache/feed store]
   - Reads are served from [cache] with [DB] as fallback
   - [CDN] handles static assets
   
   The main trade-offs I made are [list 2-3].
   The weakest point is [known weakness] which could be addressed by [solution]
   given more time."

ASK A GOOD CLOSING QUESTION:
  "Is there any particular area you'd like me to go deeper on?"
  "Are there any aspects of this design that concern you?"
  "What would you change about this architecture?"

3. THE MUST-KNOW SYSTEM DESIGN PROBLEMS
--------------------------------------------------------------------------------

CATEGORY 1: SOCIAL / COMMUNICATION
  - Design Twitter / Instagram
  - Design WhatsApp / Messenger
  - Design Facebook News Feed
  - Design Notification System
  - Design Live Streaming (YouTube Live, Twitch)

CATEGORY 2: STORAGE / CDN
  - Design Google Drive / Dropbox
  - Design YouTube
  - Design TinyURL / URL Shortener
  - Design Image Hosting Service (Imgur)

CATEGORY 3: SEARCH / DISCOVERY
  - Design Google Search
  - Design Autocomplete / Typeahead
  - Design Yelp / Proximity Service
  - Design Google Maps

CATEGORY 4: TRANSACTION / MARKETPLACE
  - Design Uber / Lyft
  - Design Amazon / E-commerce
  - Design Booking.com / Airbnb
  - Design Ticketmaster

CATEGORY 5: DATA / ANALYTICS
  - Design a Web Crawler
  - Design a Rate Limiter
  - Design Distributed Cache (Redis-like)
  - Design a Metrics / Monitoring System
  - Design a Leaderboard

CATEGORY 6: INFRASTRUCTURE
  - Design a Load Balancer
  - Design a Distributed Message Queue (Kafka-like)
  - Design a Key-Value Store
  - Design Consistent Hashing

MINIMUM COVERAGE:
  Before any senior interview, study at least 10-12 problems (1 from each category).
