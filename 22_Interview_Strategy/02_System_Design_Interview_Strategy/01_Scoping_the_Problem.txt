================================================================================
SCOPING THE PROBLEM - REQUIREMENTS GATHERING IN SYSTEM DESIGN
================================================================================
Last Updated: April 2026
Purpose: Master the requirements gathering phase of system design interviews.
         This is the most impactful phase that most candidates rush through.
================================================================================

--------------------------------------------------------------------------------
1. WHY SCOPING IS THE MOST IMPORTANT PHASE
--------------------------------------------------------------------------------

The biggest system design failures happen here:
  - Designing a system for 100 users when 100 million are expected
  - Building strong consistency when eventual consistency is fine
  - Designing for writes when the system is 99% reads
  - Overengineering by including features not asked for

Strong scoping accomplishes three things:
  1. Shows you think like a product engineer, not just a code engineer
  2. Defines the problem clearly so your design is targeted
  3. Demonstrates senior-level communication and requirements thinking

THE GOLDEN RULE:
  Never draw a single box on the whiteboard before completing your scoping.
  Experienced engineers clarify requirements BEFORE designing.

--------------------------------------------------------------------------------
2. FUNCTIONAL REQUIREMENTS - WHAT DOES THE SYSTEM DO?
--------------------------------------------------------------------------------

START BY LISTING THE CORE FEATURES:
  "What are the must-have features for this system?"

HOW TO SCOPE FEATURES:
  For each feature, ask:
  - Is this a Day 1 feature (core MVP)?
  - Is this a future nice-to-have?
  - Should I handle this in the interview or state it as "out of scope"?

EXAMPLE: "Design a URL Shortener (like bit.ly)"

  Brainstormed features:
  1. Given a long URL, generate a short URL                    → MUST HAVE
  2. Short URL redirects to the original long URL              → MUST HAVE
  3. Custom short URL (e.g., bit.ly/my-brand)                 → OPTIONAL
  4. Analytics: how many times was this URL clicked?           → OPTIONAL
  5. URL expiration                                            → OPTIONAL
  6. User accounts + managing your URLs                        → OUT OF SCOPE
  7. Rate limiting (to prevent abuse)                          → MENTION ONLY

After brainstorming, state explicitly:
  "For this interview, I'll focus on the two core features: URL shortening
   and redirect. I'll mention analytics briefly but won't deep-dive.
   User accounts and management are out of scope. Does that work for you?"

FORMULA: State → Confirm → Proceed

WHY THIS HELPS YOU:
  - You control the scope; you won't be asked about features you said were OOS
  - You can go deep on fewer features rather than shallow on many
  - Finite scope allows you to finish the design

--------------------------------------------------------------------------------
3. NON-FUNCTIONAL REQUIREMENTS - HOW WELL DOES IT DO IT?
--------------------------------------------------------------------------------

These are the "-ilities" that define the quality attributes of your system.
This is where most junior candidates get weak.

NFR 1: SCALE
  Questions to ask/state:
  - "How many users does this need to support? MAU? DAU?"
  - "What are the read and write QPS (queries per second)?"
  - "Is traffic globally distributed or regional?"
  
  Impact on design:
  - Low scale (< 1M users): Single DB, single app server might be fine
  - Medium scale (1-100M users): Read replicas, caching, multiple app servers
  - High scale (100M+ users): Sharding, global distribution, multi-region

NFR 2: LATENCY
  Questions:
  - "What is the acceptable latency for reads?" (P50, P99)
  - "Is this user-facing (needs to be fast) or back-office?"
  
  Impact on design:
  - Strict latency (<100ms): Heavy caching, CDN, pre-computation
  - Relaxed latency (<2s): Can afford more reads from DB
  
  Common targets:
  - Web page load: <2 seconds (P99)
  - API read: <100ms (P99)
  - Feed load: <500ms (P99)
  - Real-time (chat): <100ms

NFR 3: AVAILABILITY
  Questions:
  - "What is the required uptime? 99.9%? 99.99%?"
  - "Can we tolerate brief downtime for maintenance?"
  
  Availability math:
  - 99.9%   = 8.7 hours downtime/year ("three nines")
  - 99.99%  = 52 minutes downtime/year ("four nines")
  - 99.999% = 5 minutes downtime/year ("five nines")
  
  Impact on design:
  - High availability requires: redundancy, failover, health checks,
    no single point of failure, multi-AZ deployment

NFR 4: CONSISTENCY
  Questions:
  - "Does the user need to see their own write immediately?"
  - "Is eventual consistency (data syncs within seconds) acceptable?"
  - "What happens if two users edit the same thing concurrently?"
  
  Consistency models (from weakest to strongest):
  - Eventual: "You'll see it eventually" (social feeds OK here)
  - Read-Your-Writes: "You always see your own writes immediately"
  - Monotonic Reads: "Once you've seen a value, you won't see an older one"
  - Strong: "Everyone sees the same data at the same time" (banking required)
  
  CAP theorem reminder:
  - Can't have both Consistency AND Availability during a network Partition
  - Most web systems choose AP (Availability + Partition tolerance)
  - Financial systems often choose CP (Consistency + Partition tolerance)

NFR 5: DURABILITY
  Questions:
  - "Can we lose any data in a failure scenario?"
  - "How long do we need to retain data?"
  
  Impact on design:
  - High durability: Multi-region replication, backups, WAL (write-ahead log)
  - Lower durability: Single region, single backup, cache-only for transient data

NFR 6: SECURITY
  Usually not deep-dived but should be mentioned:
  - Authentication: "Users authenticate via OAuth/JWT at the API gateway"
  - Authorization: "Users can only access their own data"
  - Encryption: "All data at rest and in transit is encrypted"
  - Rate limiting: "To prevent abuse and DDoS"

NFR 7: MAINTAINABILITY / OBSERVABILITY
  Senior signal:
  - "The system should be observable: metrics, logging, tracing"
  - "We'd want circuit breakers to prevent cascade failures"
  - "Each service should be independently deployable"

4. THE SCOPING CONVERSATION - ACTUAL DIALOGUE
--------------------------------------------------------------------------------

QUESTION: "Design Google Drive (file storage and sharing)"

HOW THE SCOPING CONVERSATION SHOULD GO:

YOU: "Before I start designing, let me clarify some requirements.
  
  For features - am I right to focus on: file upload, download, storage,
  and sharing? Should I include real-time collaboration (like Google Docs),
  or is that out of scope?"

INTERVIEWER: "Let's keep real-time collaboration out of scope. Focus on
  upload, download, and sharing."

YOU: "Got it. What about file versioning? Should I keep history of edits?"

INTERVIEWER: "Let's include basic versioning - keep the last 30 days."

YOU: "Understood. Now for scale - how many users? What's the data volume?"

INTERVIEWER: "Think at the scale of Dropbox - around 500 million users,
  but only 1 million are concurrently active at peak."

YOU: "And roughly how much data per user? And what file sizes are typical?"

INTERVIEWER: "Assume 10 GB per user on average. Files are mostly documents
  and photos - so under 100 MB each typically, but allow up to 5 GB."

YOU: "Perfect. And for consistency - is it okay if after upload, the file
  takes a second or two to show up on your other devices? Or strict sync?"

INTERVIEWER: "Eventual consistency is fine - a few seconds delay is acceptable."

YOU: "Great. So my requirements summary:
  Features: upload, download, sharing with permissions, versioning (30 days)
  Scale: 500M total users, 1M concurrent, ~10 GB/user, files up to 5 GB
  Consistency: eventual consistency, seconds-level sync across devices
  Availability: high - users expect it to work
  
  With that, let me start with capacity estimation..."

THIS DIALOGUE TAKES 5-7 MINUTES AND IS TIME WELL SPENT.

5. CAPACITY ESTIMATION AS PART OF SCOPING
--------------------------------------------------------------------------------

After functional + non-functional requirements, do quick estimation.

THE NUMBERS TO KNOW BY HEART:
  - 1 second = 1,000 ms = 1,000,000 μs
  - 1 day = 86,400 seconds (~100K for rough math)
  - 1 month = 30 days = 2.6 million seconds
  - 1 year = 365 days = 31.5 million seconds
  
  Powers of ten:
  - 1 KB = 10^3 bytes
  - 1 MB = 10^6 bytes
  - 1 GB = 10^9 bytes
  - 1 TB = 10^12 bytes

  Data sizes:
  - ASCII char = 1 byte
  - Unicode char = 2-4 bytes
  - Tweet = 280 chars ≈ 300 bytes with metadata
  - Photo (JPEG) = 1-5 MB
  - Video (1 min HD) = ~100 MB
  - User record = 1-2 KB

ESTIMATION EXAMPLE (Google Drive):
  
  Users: 500M total, 1M concurrent
  
  Upload rate:
  - If 10% of DAU (say 10M DAU) upload 1 file/day = 10M uploads/day
  - 10M / 86,400 = ~115 uploads/second
  - Peak (3x): ~350 uploads/second
  
  Average file size: assume 1 MB average (mix of docs and photos)
  
  Upload bandwidth:
  - 350 uploads/sec × 1 MB = 350 MB/s incoming bandwidth
  
  Storage:
  - 500M users × 10 GB = 5,000 PB = 5 EB total storage
  - Daily growth: 10M new files × 1 MB = 10 TB/day
  - Annual growth: 3.65 PB/year
  
  This tells me:
  - Need distributed storage (S3-like, not a single server)
  - Need chunked upload support (5 GB files can't be monolithic)
  - Need CDN for download acceleration
  - 350 MB/s upload bandwidth → need multiple upload servers

--------------------------------------------------------------------------------
6. THE SCOPE STATEMENT - HOW TO FORMALIZE IT
--------------------------------------------------------------------------------

After clarification, write or say a clear scope statement before designing:

TEMPLATE:
  "To summarize my design scope:
  
  FUNCTIONAL:
  - [Feature 1] - core
  - [Feature 2] - core
  - [Feature 3] - mentioned but not deep-dived
  - [Feature 4] - out of scope
  
  NON-FUNCTIONAL:
  - Scale: [X] users, [Y] QPS read, [Z] QPS write
  - Latency: [X ms] for reads
  - Availability: [X] nines
  - Consistency: [model]
  
  Estimated storage: [X] per year
  Estimated bandwidth: [X] MB/s
  
  With these requirements, let me start the architecture..."

This takes 60-90 seconds to state and shows exceptional clarity of thought.

--------------------------------------------------------------------------------
7. RED FLAGS IN SCOPING PHASE
--------------------------------------------------------------------------------

INTERVIEWERS WATCH FOR THESE ANTI-PATTERNS:
  
  ✗ Starting to design immediately without asking anything
     Signal: "This person starts coding before reading requirements"
  
  ✗ Asking too many hypothetical questions
     Signal: "This person can't make decisions under uncertainty"
  
  ✗ Designing for a scope that wasn't asked for
     Signal: "This person builds features that weren't requested"
  
  ✗ Vague requirements accepted without pushing back
     Signal: "This person doesn't understand what they need to design"
  
  ✗ No estimation at all
     Signal: "This person doesn't think about scale"
  
  ✓ Asking targeted, specific questions
  ✓ Making reasonable assumptions when needed
  ✓ Scoping down to a tractable set of features
  ✓ Estimating key numbers and using them in the design
