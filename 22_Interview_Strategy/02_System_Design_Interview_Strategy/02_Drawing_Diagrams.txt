================================================================================
DRAWING DIAGRAMS IN SYSTEM DESIGN INTERVIEWS
================================================================================
Last Updated: April 2026
Purpose: How to draw clear, professional system diagrams that communicate
         your architecture effectively in both virtual and in-person settings.
================================================================================

--------------------------------------------------------------------------------
1. WHY DIAGRAMS ARE ESSENTIAL IN SYSTEM DESIGN
--------------------------------------------------------------------------------

A system design without a diagram is like giving directions with no map.

Benefits of good diagrams:
  - Forces you to think about connections and data flow
  - Makes complex systems understandable at a glance
  - Gives the interviewer something concrete to react to and ask about
  - Shows you're used to communicating architecture (a real-world skill)
  - Prevents talking vaguely in circles

THE TRUTH: Many candidates talk abstractly ("I'd use microservices with
  some caching") but never draw anything. This is a missed opportunity.

RULE: Start drawing as SOON as you begin Phase 3 (high-level architecture).
  Don't wait until you have a complete picture in your head.

--------------------------------------------------------------------------------
2. TOOLS BY INTERVIEW FORMAT
--------------------------------------------------------------------------------

IN-PERSON WHITEBOARD:
  - Use the full whiteboard; don't crowd everything in one corner
  - Have multiple marker colors: black for boxes/arrows, blue for labels,
    red for highlighting bottlenecks or critical paths
  - Write large enough to read from 4-5 feet away
  - Leave space for annotations and additions
  - Number your components for easy reference during discussion

VIRTUAL - EXCALIDRAW (most common):
  - excalidraw.com - free, browser-based, collaborative
  - Supports shapes, arrows, text, freehand
  - Can be shared in real-time with interviewer
  - Use keyboard shortcuts: R (rectangle), A (arrow), T (text), V (select)

VIRTUAL - MIRO:
  - Richer tool; some companies pre-share a Miro board
  - Similar to Excalidraw but with more templates
  - Start with the blank template

VIRTUAL - GOOGLE SLIDES / POWERPOINT:
  - If no dedicated tool, use shapes in slides
  - Copy a previous blank slide to get a clean canvas quickly

VIRTUAL - ZOOM WHITEBOARD:
  - Built-in whiteboard in Zoom
  - Limited but functional for simple diagrams

TIPS FOR VIRTUAL:
  - Know your tool before the interview
  - Practice drawing a simple architecture before the day
  - Have a backup plan (can share screen with a text editor at minimum)
  - Don't spend >2 minutes figuring out the tool

--------------------------------------------------------------------------------
3. THE STANDARD DIAGRAM VOCABULARY
--------------------------------------------------------------------------------

Learn these symbols and use them consistently:

  ┌─────────────┐    Rectangle = Service or Component
  │  Service A  │
  └─────────────┘
  
  ┌─────────────┐    Cylinder = Database
  │     DB      │
  └─────────────┘
  
  ┌─────────────┐    Cloud/rounded rectangle = External service / Cloud
  │    S3/GCS   │
  └─────────────┘
  
  ─────→            Solid arrow = Synchronous call (REST, gRPC)
  - - →             Dashed arrow = Asynchronous call (event, queue message)
  ════→             Double arrow = Bidirectional communication
  
  ┌─────────────┐    Queue symbol
  │   Kafka     │═══
  └─────────────┘
  
  ├──── Multiple lines branching = Load balancer distributing traffic
  
  LABELS: Always label:
  - The service name
  - The arrow direction
  - The protocol (HTTP/REST, gRPC, AMQP)
  - Data volumes on arrows when relevant (for estimation review)

4. HOW TO DRAW A HIGH-LEVEL ARCHITECTURE DIAGRAM (STEP BY STEP)
--------------------------------------------------------------------------------

EXAMPLE: Designing a URL Shortener

STEP 1: Draw the entry points (left side)
  ┌────────┐    ┌────────┐
  │ Mobile │    │  Web   │
  └────────┘    └────────┘
       └──────────┘
            │
          [HTTP]
            ↓
  
STEP 2: Add the API gateway and load balancer
  ┌────────────────────┐
  │   Load Balancer    │
  │  (API Gateway)     │
  └────────────────────┘
            │
    ┌───────┼───────┐
    ↓       ↓       ↓
  (services below)

STEP 3: Draw your application services (can be grouped or separate)
  ┌────────────────┐   ┌────────────────┐
  │  URL Service   │   │  Redirect Svc  │
  │ (write/shorten)│   │ (read/redirect)│
  └────────────────┘   └────────────────┘

STEP 4: Add databases and caches
  ┌────────────────┐   ┌────────────────┐
  │  URL Postgres  │   │   Redis Cache  │
  │  (primary +    │   │ (hot short URLs│
  │   replicas)    │   │  cached here)  │
  └────────────────┘   └────────────────┘

STEP 5: Add supporting services
  - Counter/ID service for generating unique IDs
  - CDN if serving static content
  - Analytics service if tracking clicks

STEP 6: Draw data flows with arrows
  User → Load Balancer → URL Service → Write to DB + return short URL
  User → Load Balancer → Redirect Svc → Check Cache → Cache hit? → 302 redirect
                                                      Cache miss? → DB lookup → Cache + redirect

FINAL DIAGRAM (simplified):

  [Client] 
     │ HTTP
     ↓
  [Load Balancer] ──────────────────────────┐
     │                                       │
     ↓ (write: POST /shorten)                ↓ (read: GET /{code})
  [URL Service]                         [Redirect Service]
     │                                       │
     ↓ Write                         Check Cache First
  [PostgreSQL Primary]               [Redis Cache]
     │                                  (miss) │
     ├→ [Read Replica]                         ↓
     └→ [Read Replica]               [PostgreSQL Read Replica]
                                               │
  [ID Generator]                               ↓
  (Snowflake-style)                       HTTP 302 → Original URL

5. HOW TO DRAW A DATA FLOW DIAGRAM
--------------------------------------------------------------------------------

When explaining complex flows, add numbered arrows:

EXAMPLE: Feed Generation Flow (Twitter-like)

  1. User A tweets
     ↓ (1) Write tweet to DB
  [Tweet DB]
     ↓ (2) Publish event to Kafka topic "new_tweet"
  [Kafka]
     ↓ (3) Fan-out service reads event
  [Fan-out Worker]
     ↓ (4) Look up followers of User A
  [Follower DB / Cache]
     ↓ (5) For each follower, prepend tweet ID to their feed list in Redis
  [Feed Cache (Redis)]
     ↓ (6) User B loads feed → reads from Redis
  [User B Client]

NARRATING THE DATA FLOW:
  "When a user tweets - step 1 - we write the tweet to our primary DB.
   In step 2, we publish an event to Kafka. Step 3, a fan-out service
   is subscribed to this topic. In step 4, it looks up all followers.
   In step 5, it adds the tweet ID to each follower's feed in Redis.
   When User B loads their feed, step 6, we read from the Redis cache
   giving fast, pre-computed results."

--------------------------------------------------------------------------------
6. TIPS FOR CLEAR, PROFESSIONAL DIAGRAMS
--------------------------------------------------------------------------------

LAYOUT PRINCIPLES:
  - Left-to-right flow: request comes from left, response goes right
  - OR top-to-bottom: clients at top, databases at bottom
  - Keep related components near each other
  - Don't cross arrows if possible; route around instead

LABELING:
  - Every box needs a name
  - Every arrow needs a direction (arrowhead) and ideally a label
  - Use consistent naming: "User Service", not "UserService" in one place
    and "users-svc" in another

SCALE ANNOTATIONS:
  Add numbers to show scale impact:
  "→ 100K reads/sec → [Redis Cache] 99% hit rate → [DB] 1K reads/sec"

USE COLOR CODES (when available):
  - Blue: Core write path
  - Green: Core read path
  - Red/Orange: Potential bottlenecks or failure points
  - Grey: External dependencies

ITERATIVE REFINEMENT:
  - Start simple (just boxes and arrows)
  - Add detail as you discuss each component
  - Don't try to draw the perfect diagram upfront; refine as you talk

WHAT NOT TO DO:
  ✗ Giant diagram with 30 components that can't be explained
  ✗ Arrows without labels or direction
  ✗ Components with no clear purpose
  ✗ No data flow shown
  ✗ Presenting a completed diagram without narrating how you got there

--------------------------------------------------------------------------------
7. BUILDING YOUR DIAGRAM LIVE - THE PROGRESSIVE REVEAL
--------------------------------------------------------------------------------

Don't draw everything then explain. Draw AS YOU EXPLAIN.

TECHNIQUE: Announce before you draw each component

  "I'll start by placing the client here on the left..."
  [draw client box]
  
  "All requests will first go through an API Gateway for authentication
  and rate limiting..."
  [draw API Gateway box + arrow from client]
  
  "Behind the gateway, I'll have two main services: one for writes and
  one for reads, since read:write ratio is 100:1..."
  [draw two service boxes]
  
  "For storage, I'll use PostgreSQL with a primary for writes and
  read replicas for the high read volume..."
  [draw DB boxes]
  
  "And to cache the hot data - roughly 20% of content drives 80% of reads
  per the Pareto principle - I'll use Redis in front of the DB..."
  [draw Redis box + arrows]

THE EFFECT: The interviewer can follow your thinking in real time.
  They see WHY each component exists as you add it.
  This is much more impressive than presenting a pre-drawn diagram.

--------------------------------------------------------------------------------
8. QUICK REFERENCE - DIAGRAM CHECKLIST
--------------------------------------------------------------------------------

  HIGH-LEVEL ARCHITECTURE DIAGRAM SHOULD INCLUDE:
  [ ] Client(s) entry point
  [ ] Load balancer / API gateway
  [ ] Application service(s)
  [ ] Primary data store (DB)
  [ ] Cache layer (Redis)
  [ ] Message queue (if async operations)
  [ ] Object storage (if file/media handling)
  [ ] CDN (if serving static content at scale)
  [ ] Arrows with directions and labels
  [ ] Service names on all boxes

  DATA FLOW DIAGRAM SHOULD INCLUDE:
  [ ] Numbered steps for the happy path
  [ ] Read path clearly distinct from write path
  [ ] Cache hit vs cache miss paths
  [ ] Async steps marked differently

  DEEP DIVE COMPONENT DIAGRAM SHOULD INCLUDE:
  [ ] Internal structure of the component
  [ ] Sub-components and their interactions
  [ ] Database schema (key tables)
  [ ] API contract (key endpoints)
