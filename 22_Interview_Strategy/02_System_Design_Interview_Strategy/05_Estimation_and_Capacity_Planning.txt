--------------------------------------------------------------------------------
1. WHY ESTIMATION MATTERS IN SYSTEM DESIGN
--------------------------------------------------------------------------------

Estimation serves multiple purposes:
  1. Drives architecture decisions (caching needed? sharding needed?)
  2. Reveals bottlenecks before designing around them
  3. Shows you've thought about scale and cost
  4. Demonstrates production systems experience

THE WRONG APPROACH:
  "I'll just say millions of users and leave it at that."

THE RIGHT APPROACH:
  "Let's estimate: 10M DAU, each making 10 requests/day = 100M requests/day.
  100M / 86,400 seconds ≈ 1,200 QPS average. At 5x peak that's 6,000 QPS.
  A single web server handles ~5-10K RPS, so 1-2 app servers suffice here,
  but let's add headroom and use 3 with a load balancer."

The estimation revealed the answer to an architecture question.

2. FOUNDATIONAL NUMBERS TO MEMORIZE
--------------------------------------------------------------------------------

TIME UNITS:
  1 minute = 60 seconds
  1 hour = 3,600 seconds
  1 day = 86,400 seconds (~100,000 for rough math)
  1 week = 604,800 seconds (~600K)
  1 month = ~2,592,000 seconds (~2.5M)
  1 year = ~31,536,000 seconds (~31.5M)

POWERS OF 10 (STORAGE):
  1 KB = 10^3 bytes = 1,000 bytes
  1 MB = 10^6 bytes = 1,000,000 bytes
  1 GB = 10^9 bytes = 1,000,000,000 bytes
  1 TB = 10^12 bytes
  1 PB = 10^15 bytes
  1 EB = 10^18 bytes

BINARY EQUIVALENTS (for precision, but use powers of 10 for estimation):
  1 KiB = 1,024 bytes ≈ 10^3
  1 MiB = 1,048,576 bytes ≈ 10^6
  1 GiB = 1,073,741,824 bytes ≈ 10^9

TYPICAL DATA SIZES:
  ASCII character:        1 byte
  Unicode character:      2-4 bytes
  Short string (50 chars): 50-200 bytes
  Tweet/post (280 chars): 280 bytes text + ~200 bytes metadata = ~500 bytes
  User record:            1-2 KB
  Small image (thumbnail):10-50 KB
  Photo (JPEG, compressed):500 KB - 3 MB
  Large photo (raw):      5-20 MB
  Short video (1 min, 720p): 50-150 MB
  Long video (2 hr, 1080p): 3-10 GB
  App binary:             50-200 MB

LATENCY REFERENCE (approximate order of magnitude):
  L1 cache hit:           0.5 ns
  L2 cache hit:           5 ns
  RAM access:             100 ns
  SSD read (random):      100 µs (0.1 ms)
  HDD read (random):      10 ms
  Network (same datacenter): 0.5-1 ms (500 µs)
  Network (cross-region):  50-150 ms
  Network (cross-continent): 100-300 ms

THROUGHPUT BENCHMARKS:
  Single Redis instance:  100K-1M ops/sec
  PostgreSQL (single):    10K-100K QPS (simple reads, indexed)
  MySQL (single):         ~100K simple reads/sec
  Kafka:                  Millions of messages/sec per broker
  Web server (nginx):     50K-100K RPS (for static content)
  Web server (app):       1K-10K RPS (for typical application requests)
  CDN:                    Terabits/sec globally
  S3:                     Request rate depends on prefix design; use randomized prefixes

NETWORK:
  1 Gbps NIC:            125 MB/s
  10 Gbps NIC:           1.25 GB/s
  Typical server bandwidth: 1-10 Gbps

3. THE ESTIMATION FRAMEWORK
--------------------------------------------------------------------------------

STEP 1: ESTABLISH USER BASE
  - MAU (Monthly Active Users): Total registered and active users per month
  - DAU (Daily Active Users): Typically 10-30% of MAU for social apps
  - Concurrent Active Users: Typically 10% of DAU

STEP 2: ESTIMATE READ/WRITE QPS
  - Identify the key operations (write: create tweet; read: load feed)
  - Estimate frequency per user per day
  - Total = frequency/user/day × DAU / 86,400 = QPS average
  - Peak QPS = 3x-10x average

STEP 3: ESTIMATE STORAGE
  - Per-unit data size (one tweet, one user record, one photo)
  - Daily volume = units/day × data size
  - Annual volume = daily volume × 365
  - Retention multiplier if keeping historical data

STEP 4: ESTIMATE BANDWIDTH
  - Upload: data size per request × write QPS
  - Download: data size per response × read QPS
  - Often much larger than expected (images, videos)

--------------------------------------------------------------------------------
4. WORKED ESTIMATION EXAMPLES
--------------------------------------------------------------------------------

EXAMPLE A: DESIGN TWITTER (CLASSIC)

Users:
  - 300M MAU
  - 100M DAU (33% MAU, reasonable for Twitter)
  - 1M concurrent users

Write QPS (tweets):
  - Assume 1% of DAU tweets once/day: 1M tweets/day
  - 1M / 86,400 ≈ 12 tweets/second average
  - Peak (10x): 120 tweets/second

Read QPS (feed reads):
  - Each DAU loads feed 10 times/day: 100M × 10 = 1 billion feed requests/day
  - 1B / 86,400 ≈ 11,600 requests/second average
  - Peak (5x): ~60,000 read requests/second
  - Read:Write ratio = 60K / 120 = 500:1 → extremely read-heavy

Storage (tweets):
  - Tweet record: 280 chars text + metadata ≈ 500 bytes
  - 12 tweets/sec × 86,400 sec/day = 1,036,800 tweets/day ≈ 1M tweets/day
  - 1M tweets/day × 500 bytes = 500 MB/day text storage
  - 500 MB × 365 days = ~182 GB/year (text only; very manageable)
  - If 10% of tweets include media (average 1 MB): 100K tweets/day × 1 MB = 100 GB/day media
  - 100 GB/day × 365 = ~36 TB/year media storage

Bandwidth:
  - Write: 120 tweets/sec × 500 bytes = 60 KB/s (trivial)
  - Read: 60K requests/sec; if each response is ~50 tweets × 500 bytes = 25 KB:
    60K × 25 KB = 1.5 GB/s outbound bandwidth (significant!)

CONCLUSIONS:
  - Storage is fine for text; media needs dedicated object store (S3-like)
  - Read-heavy → heavy caching required
  - 60K read QPS → need multiple app servers + Redis cluster
  - 1.5 GB/s bandwidth → CDN is mandatory for media

EXAMPLE B: DESIGN A URL SHORTENER (TinyURL)

Users:
  - 100M DAU

Write QPS (create short URL):
  - Assume 0.1% of DAU create 1 URL/day: 100K new URLs/day
  - 100K / 86,400 ≈ 1.2 writes/second (very low write rate)

Read QPS (redirect):
  - Each URL gets hit 10 times/day: 100K × 10 = 1M redirects/day
  - 1M / 86,400 ≈ 12 redirects/second
  - Read:Write ratio = 12 / 1.2 = 10:1

URL Record Size:
  - short_code (7 chars): 7 bytes
  - original_url: average 200 bytes
  - created_at, user_id, expiry: ~50 bytes
  - Total: ~260 bytes per URL ≈ 300 bytes

Storage:
  - 100K URLs/day × 300 bytes = 30 MB/day
  - Over 10 years: 30 MB × 365 × 10 = ~110 GB total
  - Very manageable in a single PostgreSQL instance

Unique Short Code Space:
  - 7 characters, using base62 (a-z, A-Z, 0-9): 62^7 ≈ 3.5 trillion combinations
  - At 100K URLs/day: 3.5 trillion / 100K = 35 million days ≈ 95,000 years
  - No shortage of unique codes

CONCLUSIONS:
  - Very low write rate; simple single DB suffices
  - Read rate also low; minimal caching needed initially
  - The algorithmic challenge is unique ID generation, not scale
  - Main complexity: redirect latency optimization + analytics

EXAMPLE C: DESIGN A RIDE-SHARING APP (UBER/LYFT)

Users:
  - 10M DAU riders, 500K active drivers at peak
  - Peak: 1M concurrent riders, 200K active drivers

Location Updates (Write-heavy for drivers):
  - Active drivers send GPS update every 5 seconds
  - 200K drivers × (1 update / 5 sec) = 40K writes/second
  - Each update: driver_id (8 bytes) + lat/lng (16 bytes) + timestamp (8 bytes) = ~50 bytes
  - Bandwidth: 40K × 50 bytes = 2 MB/s (manageable)

Ride Requests (Write):
  - Assume 5 rides/user/day per active DAU: 1M concurrent × 5/day = 5M rides/day
  - 5M / 86,400 ≈ 58 ride requests/second

Location Query (Read):
  - For matching: need to query drivers near a location
  - This is a geospatial query → needs geospatial index
  - At 58 ride requests/sec, each needs to find nearby drivers → 58 geospatial queries/sec
  - With caching of driver locations in Redis with geospatial commands: very fast

Storage for Driver Locations:
  - Only need current location: 500K drivers × 50 bytes = 25 MB (fits in memory/Redis)
  - Historical location for a trip: ~100 GPS points × 50 bytes = 5 KB per trip
  - 5M rides/day × 5 KB = 25 GB/day of historical data

CONCLUSIONS:
  - Driver location updates are the write bottleneck: 40K writes/sec
  - Need Redis with geospatial commands (GEOADD, GEORADIUS)
  - Matching algorithm is the complex piece (not just proximity, but ETA)
  - Geospatial DB (PostGIS) or Redis Geo for current locations
  - Time-series DB or object store for historical trip data

5. CAPACITY PLANNING RULES OF THUMB
--------------------------------------------------------------------------------

DATABASE CAPACITY GUIDELINES:
  - Single PostgreSQL: handles up to ~10K-100K QPS (read-heavy with replicas)
  - Need sharding when: > 1TB data OR > 100K QPS OR query patterns don't fit
  - MongoDB: similar read performance; better for document-heavy workloads
  - Cassandra sweet spot: > 100K writes/sec, > 10 TB data

CACHE SIZING:
  - 80-20 rule: 20% of data is 80% of traffic → cache 20% of working set
  - Redis memory: 1-2x the size of the hot working set
  - Redis single instance: 100K-1M ops/sec for simple gets/sets
  - Redis Cluster: horizontally shards data across multiple nodes

WEB SERVER CAPACITY:
  - 1 web server: 1K-10K RPS for typical CRUD operations
  - Load balancer handles distribution automatically
  - Rule of thumb: Add a server for every ~5K expected RPS

MESSAGE QUEUE (KAFKA) CAPACITY:
  - 1 Kafka broker: handles millions of messages/sec
  - Partition count: determines parallelism; ~1 partition per consumer
  - Retention: configure per-topic based on replay needs

CDN CAPACITY:
  - Always use CDN for static assets (images, videos, JS, CSS)
  - CDN can serve terabits/sec globally
  - Reduces origin server bandwidth by 80-99% for media-heavy apps

6. ESTIMATION PITFALLS TO AVOID
--------------------------------------------------------------------------------

PITFALL 1: WRONG ORDER OF MAGNITUDE
  Off by 10x or 100x: 100K becomes 1M or 10K
  Fix: Double-check your powers of 10 explicitly

PITFALL 2: FORGETTING PEAK vs. AVERAGE
  Average QPS is fine for storage planning; use PEAK for server sizing
  Peak is typically 3x-10x average; use 5x as a safe default

PITFALL 3: STORAGE WITHOUT REPLICATION
  If you calculate 1 TB/year, you actually need 3 TB (3x replication)
  Always multiply by replication factor (3 for most systems)

PITFALL 4: IGNORING METADATA
  A 500-byte tweet has associated metadata: indexes, foreign keys,
  MVCC overhead in PostgreSQL (~20-30% overhead)
  Rule: multiply raw storage by 1.3x for overhead

PITFALL 5: NOT CONVERTING UNITS CONSISTENTLY
  1 million users × 10 MB/user = 10 million MB = 10,000 GB = 10 TB
  (Not 10 MB or 10 million GB)
  Write out unit cancellation explicitly if unsure

PITFALL 6: FORGETTING READ REPLICAS SCALE READS, NOT WRITES
  If you add 3 read replicas, reads scale by 4x (original + 3 replicas)
  But writes still only go to 1 primary → primary is the write bottleneck

7. THE ESTIMATION CHEAT SHEET
--------------------------------------------------------------------------------

USER SCALE RULES OF THUMB:
  < 1K users:         Single server, single DB, no caching
  1K - 100K users:    Web server + DB (primary/replica) + basic Redis
  100K - 10M users:   Multiple app servers, sharded DB, Redis cluster, CDN
  > 10M users:        Microservices, global distribution, multi-region

QPS RULES OF THUMB:
  < 1K QPS:           Single DB handles fine
  1K - 10K QPS:       Read replicas + Redis cache
  10K - 100K QPS:     DB sharding + Redis cluster
  > 100K QPS:         Specialized storage (Cassandra), CDN edge caching

STORAGE RULES OF THUMB:
  < 100 GB:           Single DB server
  100 GB - 10 TB:     DB with RAID or managed service (RDS)
  > 10 TB:            Sharded DB or distributed file system
  Media (images/video): Object storage (S3, GCS) always
