COMMON MISTAKES IN SYSTEM DESIGN INTERVIEWS
================================================================================
Last Updated: April 2026
Purpose: A comprehensive list of the most common system design interview
         mistakes and how to avoid or recover from each one.

--------------------------------------------------------------------------------
1. THE 15 MOST COMMON SYSTEM DESIGN INTERVIEW MISTAKES
--------------------------------------------------------------------------------

MISTAKE 1: JUMPING INTO DESIGN WITHOUT CLARIFYING REQUIREMENTS
-----------------------------------------------------------------
The Problem:
  Interviewer says "Design Uber". Candidate immediately starts drawing
  boxes: "So we have the user, the driver, the server..."
  
  After 20 minutes: "Wait, did you want me to design the real-time tracking
  system, the matching algorithm, or the payments?"
  
  Interviewer: "I was thinking the matching and real-time tracking."
  
  Candidate has wasted 15+ minutes designing the wrong thing.

Why It Happens:
  - Nervous; wants to appear decisive
  - Doesn't know that clarification is expected and valued
  - Mistakenly thinks clarity = knowing the answer immediately

How to Avoid:
  - ALWAYS spend the first 5-7 minutes on clarification (see 01_Scoping)
  - Ask: "Before I start designing, let me clarify the scope..."
  - Explicitly state: "I'll focus on [X] and [Y]. Is that the right scope?"

Recovery If You've Already Jumped In:
  "I realize I jumped ahead without clarifying scope. Let me take a step
  back - what are the two or three most important features you'd like me
  to focus on?"

---

MISTAKE 2: VAGUE HANDWAVY ARCHITECTURE
-----------------------------------------
The Problem:
  "I'd use a microservices architecture with some caching in front of
  the database, and maybe use Kafka for event streaming."
  
  No specific services named. No data flow explained. No trade-offs.

Why It Happens:
  - Candidate knows the vocabulary but not the substance
  - Trying to sound smart without committing to specifics

How to Avoid:
  - Name specific technologies and justify each
  - Describe which service calls which other service
  - Draw the data flow with arrows
  - Always say WHY: "I'm using Kafka here because..."

Good vs. Bad Examples:
  BAD: "I'd add some caching"
  GOOD: "In front of the database, I'd add Redis using cache-aside.
         Hot user profiles and session tokens fit this perfectly - they're
         read-heavy and tolerate a few minutes of staleness."

---

MISTAKE 3: OVER-ENGINEERING FROM THE START
--------------------------------------------
The Problem:
  For a system serving 10,000 users, candidate designs:
  - 12 microservices
  - 3 message queues
  - Global CDN
  - Multi-region failover
  - Kubernetes cluster with 50 pods
  
  This misunderstands that good engineering matches complexity to requirements.

Why It Happens:
  - Candidates associate complexity with impressiveness
  - Not thinking about the cost of complexity

How to Avoid:
  - Start simple: "For the initial scale of 10K users, a monolith on
    a well-resourced server works fine."
  - Add complexity: "As we scale to 10M users, we'd start adding..."
  - Always anchor to the requirements you established in scoping

QUOTE TO REMEMBER: "Premature optimization is the root of all evil." - Knuth
  This applies to system design too.

---

MISTAKE 4: DESIGNING WITHOUT ESTIMATING
-----------------------------------------
The Problem:
  Candidate never estimates. Proposes caching "for performance" without
  knowing whether you'd cache 100 KB or 100 TB. Proposes a single database
  without knowing if you need to handle 100 QPS or 1M QPS.

Why It Happens:
  - Estimation feels tedious
  - Candidate doesn't know the numbers to reason with

How to Avoid:
  - Always do back-of-envelope estimation in Phase 2
  - Anchor design decisions to numbers: "Given 100K QPS, a single Redis
    instance can handle this - Redis can do ~100K operations/second"
  - Show your math even if rough

---

MISTAKE 5: NO DISCUSSION OF FAILURE MODES
-------------------------------------------
The Problem:
  Design describes the happy path only. What if the database goes down?
  What if Kafka is overwhelmed? What if the cache has a miss storm?
  Candidate never mentions any of this.

Why It Happens:
  - Candidates think about "how things work" not "how things fail"
  - Less real-world production experience

How to Avoid:
  - Explicitly ask yourself: "What are the top 3 ways this system fails?"
  - Discuss each failure: "If Redis goes down, traffic falls back to the DB.
    We'd need read replicas to handle this load. We'd also add circuit breakers
    to prevent the DB from being overwhelmed during cache recovery."
  - Mention SPOFs (single points of failure) and how you've eliminated them

COMMON FAILURES TO MENTION:
  - Database primary goes down → failover to replica
  - Cache miss storm → gradual warmup, mutex to prevent thundering herd
  - Service overloaded → rate limiting, circuit breakers, auto-scaling
  - Network partition → graceful degradation
  - Message queue lag → scale consumers, dead letter queue for failures

---

MISTAKE 6: IGNORING THE DATA MODEL
-------------------------------------
The Problem:
  Candidate draws a box labeled "Database" but never defines what's inside.
  The interviewer asks "How would you store a tweet?" and the candidate says
  "Uh, like a document with fields."
  
  No schema. No index strategy. No sharding key.

Why It Happens:
  - Focus on architecture over data design
  - Not thinking about how queries will actually work

How to Avoid:
  - For any DB component, proactively say:
    "Let me sketch the key tables/documents..."
  - Define the core entities and relationships
  - Think about: What are the access patterns? What needs to be indexed?
  - For sharding: What's the sharding key? Why?

EXAMPLE (Tweet table):
  tweets: {id (Snowflake), user_id, content (280 chars), created_at,
           like_count, retweet_count, media_url}
  Indexes: user_id + created_at (for user timeline), created_at (for global feed)
  Shard key: tweet_id (for uniform distribution)

---

MISTAKE 7: CHOOSING TECHNOLOGY BEFORE UNDERSTANDING REQUIREMENTS
-----------------------------------------------------------------
The Problem:
  "I'll use Cassandra for storage" - said before knowing the query patterns,
  consistency requirements, or team expertise.

Why It Happens:
  - "Cassandra is what big tech uses for this type of problem"
  - Cargo-culting without understanding

How to Avoid:
  - Requirements first, technology second
  - "Given [requirement A], [requirement B], and [constraint C],
    Cassandra is the best fit because..."
  - Know the weaknesses of your chosen technology too

---

MISTAKE 8: TREATING THE INTERVIEW AS A MONOLOGUE
--------------------------------------------------
The Problem:
  Candidate talks for 45 minutes without asking the interviewer anything.
  Doesn't ask for feedback. Doesn't check if they're on the right track.
  
  Often: the interviewer had a specific area in mind to deep-dive, and
  the candidate spent all the time on a different area.

How to Avoid:
  - Check in at major transitions: "I've covered the high-level architecture.
    Which area would you like me to deep-dive into?"
  - Ask: "Am I going in the right direction?" after stating your approach
  - The interviewer is a collaborator; treat it as a whiteboard session, not a lecture

---

MISTAKE 9: AVOIDING TRADE-OFF DISCUSSION
------------------------------------------
The Problem:
  Every choice is stated with certainty. "I'd use PostgreSQL." No mention
  of why not MongoDB. No acknowledgment of what PostgreSQL gives up.

Why It Happens:
  - Candidates fear saying anything might be "wrong"
  - Not thinking about alternatives

How to Avoid:
  - For every major decision, mention the alternative:
    "I'm choosing [X] over [Y] because [reason]. The trade-off is [downside]."
  - See 03_Trade_offs_Discussion.txt for full guide

---

MISTAKE 10: FORGETTING ABOUT SECURITY
---------------------------------------
The Problem:
  Sophisticated distributed system designed. No mention of authentication,
  authorization, rate limiting, or data encryption.

How to Avoid:
  - Proactively mention: "At the API gateway layer, I'd add JWT authentication
    and rate limiting. All data would be encrypted at rest (AES-256) and in
    transit (TLS 1.3)."
  - For user data: mention access control (user can only access their own data)

---

MISTAKE 11: GETTING LOST IN ONE COMPONENT
-------------------------------------------
The Problem:
  Candidate spends 30 minutes designing the database schema perfectly but
  never discusses caching, load balancing, or failure modes. The design is
  incomplete and imbalanced.

How to Avoid:
  - Breadth first, then depth. Cover all major components briefly first.
  - Let the interviewer steer toward areas they want to deep-dive
  - Use time checks: "I want to make sure I cover caching and the API layer -
    let me briefly sketch those before going deeper on the DB."

---

MISTAKE 12: NOT KNOWING KEY NUMBERS
-------------------------------------
The Problem:
  "A single MySQL server can handle... um... a lot of queries?"
  
  You can't reason about scaling without ballpark numbers.

NUMBERS TO KNOW:
  - MySQL: ~100K simple reads/sec on beefy hardware
  - Redis: ~100K-1M ops/sec
  - Kafka: millions of messages/sec
  - PostgreSQL: ~100K queries/sec (read-heavy with replicas)
  - Network bandwidth: 1 Gbps = 125 MB/s
  - Read from SSD: 500 MB/s; from RAM: 10+ GB/s
  - Estimated web server RPS: 10-50K (varies by request complexity)

---

MISTAKE 13: USING "THE CLOUD" AS AN ANSWER
--------------------------------------------
The Problem:
  "We'd put everything in the cloud and scale automatically."
  
  "The cloud" is an infrastructure, not an architecture. Auto-scaling
  doesn't solve database hot spots or cache coherence problems.

How to Avoid:
  - Name specific services: "I'd use AWS S3 for object storage,
    ElastiCache (Redis) for caching, and RDS for the relational database"
  - Know what each cloud service does and what its limits are

---

MISTAKE 14: NO MENTION OF OBSERVABILITY / MONITORING
------------------------------------------------------
The Problem:
  A production system with no mention of how you'd know if it's failing.

Senior Signal: Always mention:
  - Metrics: "We'd instrument all services with Prometheus metrics - request
    rate, error rate, latency (RED metrics). Dashboard in Grafana."
  - Logging: "Structured JSON logs, aggregated in ELK stack or CloudWatch"
  - Tracing: "Distributed tracing with Jaeger to track requests across services"
  - Alerting: "PagerDuty alerts on P99 latency > 500ms or error rate > 1%"

---

MISTAKE 15: PANIC WHEN CHALLENGED
------------------------------------
The Problem:
  Interviewer says: "What happens if the cache goes down?"
  Candidate: (visibly flustered, defensive) "Well... I mean... it wouldn't
  go down because... um..."

Interviewer is NOT trying to break your design. They're probing depth.

How to Avoid:
  - Treat questions as collaborative exploration: "Good question - let me
    think through that failure scenario..."
  - Acknowledge the weakness: "You're right, this is a single point of failure.
    Here's how I'd address it..."
  - Never defend a flawed design dogmatically

--------------------------------------------------------------------------------
2. SELF-ASSESSMENT RUBRIC
--------------------------------------------------------------------------------

After each system design practice session, rate yourself on:

  [ ] Did I clarify requirements before designing? (1-5)
  [ ] Did I estimate scale? (1-5)
  [ ] Did I draw a clear diagram? (1-5)
  [ ] Did I discuss trade-offs? (1-5)
  [ ] Did I cover failure modes? (1-5)
  [ ] Did I define the data model? (1-5)
  [ ] Did I invite the interviewer to redirect? (1-5)
  [ ] Did I finish the design in time? (1-5)

Target: All scores 4+ before your interview.
