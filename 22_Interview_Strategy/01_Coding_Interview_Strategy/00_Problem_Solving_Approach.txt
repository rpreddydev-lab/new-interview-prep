================================================================================
PROBLEM SOLVING APPROACH - A REPEATABLE FRAMEWORK FOR CODING INTERVIEWS
================================================================================
Last Updated: April 2026
Purpose: A step-by-step, battle-tested approach to solving ANY coding problem
         in a live interview. Follow this every time - it becomes automatic.
================================================================================

--------------------------------------------------------------------------------
1. WHY YOU NEED A FRAMEWORK (NOT JUST KNOWLEDGE)
--------------------------------------------------------------------------------

In a live interview, your brain is under stress. Adrenaline narrows your
thinking. Without a framework, you risk:
  - Misunderstanding the problem
  - Jumping to code before thinking
  - Missing edge cases
  - Getting stuck with no recovery path
  - Running out of time

A framework is a checklist your brain runs automatically, even under stress.
After 30-50 practice problems using this framework, it will feel natural.

THE UNIVERSAL TRUTH:
  The best interviewers care about HOW you solve problems, not just whether
  you get the answer. A clean, communicated process with a slightly suboptimal
  solution often beats a perfect silent solution.

--------------------------------------------------------------------------------
2. THE 7-STEP PROBLEM SOLVING FRAMEWORK
--------------------------------------------------------------------------------

  STEP 1:  UNDERSTAND THE PROBLEM         (2-3 minutes)
  STEP 2:  CLARIFY AND EXPLORE EXAMPLES   (2-3 minutes)
  STEP 3:  IDENTIFY CONSTRAINTS           (1-2 minutes)
  STEP 4:  THINK OUT LOUD - APPROACH      (3-5 minutes)
  STEP 5:  CODE THE SOLUTION              (15-25 minutes)
  STEP 6:  TEST AND DEBUG                 (5-7 minutes)
  STEP 7:  ANALYZE COMPLEXITY             (2-3 minutes)
  
  TOTAL: ~30-45 minutes per problem (target for a Medium)

Let's go deep on each step.

--------------------------------------------------------------------------------
STEP 1: UNDERSTAND THE PROBLEM
--------------------------------------------------------------------------------

Before saying ANYTHING else, read the problem carefully. Read it TWICE.

Questions to answer in your head:
  - What is the INPUT? (type, size range, any guarantees?)
  - What is the OUTPUT? (single value, array, boolean, object?)
  - What is the core transformation being asked?
  - Is there anything ambiguous or potentially tricky in the wording?

Say: "Let me read through this carefully..."
Take 30-60 seconds of silence if needed. This is FINE.

COMMON BEGINNER MISTAKE:
  Starting to talk/code before fully understanding the problem.
  This leads to solving the wrong problem.

--------------------------------------------------------------------------------
STEP 2: CLARIFY AND EXPLORE WITH EXAMPLES
--------------------------------------------------------------------------------

Now interact with the interviewer. This step accomplishes two things:
  1. Confirms you understand the problem correctly
  2. Builds your intuition via concrete examples

DO:
  a) Restate the problem in your own words:
     "So if I understand correctly, I'm given an array of integers and
      I need to find the length of the longest subarray where..."
  
  b) Walk through the provided example:
     "With this example, input [2,3,1,1,4], the output is 2 because..."
  
  c) Create your own example:
     "Let me try another example: [1,2,3]. Here the answer would be..."
     Pick an example slightly different from the given one.

WHAT THIS ACHIEVES:
  - You catch misunderstandings BEFORE wasting time coding
  - You build a test case you can use in Step 6
  - The interviewer sees you're methodical and careful

IMPORTANT:
  Don't over-clarify. 2-3 specific questions is ideal. Asking 15 questions
  looks uncertain. Asking 0 looks careless.

--------------------------------------------------------------------------------
STEP 3: IDENTIFY CONSTRAINTS AND EDGE CASES
--------------------------------------------------------------------------------

Constraints define the algorithm. A solution that works for n=100 may be
completely wrong for n=10^6.

KEY QUESTIONS TO ASK:
  - "What is the size of the input? (e.g., n up to 10^5? 10^9?)"
  - "Can inputs be negative? Zero? Floating point?"
  - "Can the array be empty? Can strings be empty?"
  - "Can there be duplicates?"
  - "Can the output fit in a standard int? Or do I need long?"
  - "Is the array sorted?"
  - "Can I modify the input in place?"

CONSTRAINT → ALGORITHM IMPLICATIONS:
  n ≤ 10:         Any algorithm works (even O(n!))
  n ≤ 20:         O(2^n) backtracking works
  n ≤ 100:        O(n³) works
  n ≤ 10,000:     O(n²) works
  n ≤ 100,000:    O(n log n) required
  n ≤ 1,000,000:  O(n) or O(n log n) required
  n > 10^9:       O(log n) required (binary search territory)

EDGE CASES TO THINK ABOUT EVERY TIME:
  - Empty input ([], "", null, 0)
  - Single element
  - All same elements
  - All negative numbers
  - INT_MAX / INT_MIN boundary
  - Duplicate values
  - Sorted (ascending or descending)
  - Already-answer input (e.g., k > n)

--------------------------------------------------------------------------------
STEP 4: THINK OUT LOUD - STATE YOUR APPROACH
--------------------------------------------------------------------------------

This is the most important step for interviewer communication.

BEFORE writing a single line of code, say your approach in English.

STRUCTURE YOUR VERBAL APPROACH:
  a) Start with brute force:
     "The brute force approach would be to... which gives O(n²) time."
  
  b) Identify why it's suboptimal:
     "This is inefficient because we're recomputing..."
  
  c) State the optimization:
     "If I use a HashMap to store... I can reduce it to O(n)."
  
  d) Confirm with interviewer:
     "Does this approach make sense? Should I proceed?"

WHY THIS MATTERS:
  - Shows structured thinking even if your code has bugs
  - Gives the interviewer a chance to redirect you early (saves time)
  - If you verbalize the right approach but code it wrong, partial credit

WHAT NOT TO DO:
  - Don't say "I'm thinking..." for 5 minutes in silence
  - Don't jump to the optimal solution without mentioning brute force
  - Don't ask "Is this the right approach?" without explaining your approach first

PATTERN RECOGNITION DURING THIS STEP:
  Ask yourself:
  - "Do I need to look up elements repeatedly? → HashMap"
  - "Am I looking for a contiguous subarray? → Sliding Window"
  - "Is the array sorted and I need pairs? → Two Pointers"
  - "Is this about making choices at each step? → DP or Greedy"
  - "Do I need the K largest/smallest? → Heap"
  - "Is there a recursive structure? → DFS/BFS/Recursion"

--------------------------------------------------------------------------------
STEP 5: CODE THE SOLUTION
--------------------------------------------------------------------------------

Now - and ONLY now - start writing code.

CODING PRINCIPLES IN INTERVIEWS:

  PRINCIPLE 1: WRITE CLEAN, READABLE CODE
  - Use meaningful variable names (not i, j when 'left', 'right' is clearer)
  - Add brief comments at each logical block
  - Use whitespace; don't compress code for no reason
  - Interviewers read your code; make it easy

  PRINCIPLE 2: CODE TOP-DOWN
  - Write the main function skeleton first with comments as placeholders
  - Fill in the details
  - Example:
    // 1. Initialize result and data structures
    // 2. Iterate through input
    //    2a. Update state
    //    2b. Check condition and update result
    // 3. Return result

  PRINCIPLE 3: NARRATE AS YOU CODE
  - Don't go silent for more than 30 seconds
  - Say: "Here I'm initializing a HashMap to store the last seen index of
    each character..." - even if it's obvious
  - This shows reasoning and helps the interviewer follow along

  PRINCIPLE 4: DON'T BE AFRAID TO PAUSE AND THINK
  - "I need to think about this for a second..."
  - "Actually, let me reconsider this condition..."
  - Better to pause and think than charge ahead and write wrong code

  PRINCIPLE 5: MODULARIZE
  - If a sub-task is complex, extract it as a helper method
  - "I'll write a helper function isValid() that checks..."
  - Shows good engineering instincts; real code should be modular

  GOOD CODE STRUCTURE EXAMPLE (Java):
  ```
  public int maxSubarraySum(int[] nums, int k) {
      // Edge case check
      if (nums == null || nums.length < k) return -1;
      
      // Initialize window sum with first k elements
      int windowSum = 0;
      for (int i = 0; i < k; i++) {
          windowSum += nums[i];
      }
      
      int maxSum = windowSum;
      
      // Slide window: add next element, remove previous
      for (int i = k; i < nums.length; i++) {
          windowSum += nums[i] - nums[i - k];
          maxSum = Math.max(maxSum, windowSum);
      }
      
      return maxSum;
  }
  ```

--------------------------------------------------------------------------------
STEP 6: TEST AND DEBUG
--------------------------------------------------------------------------------

After writing the code, TEST it before declaring you're done.

TESTING SEQUENCE:
  a) Normal case: Use the example from Step 2
  b) Edge case 1: Empty input / single element
  c) Edge case 2: All same values
  d) Edge case 3: Boundary condition (first/last element answers)
  e) Off-by-one check: Trace through loop boundaries manually

HOW TO TEST VERBALLY:
  "Let me trace through this with input [2, 3, 1, 1, 4], k=2..."
  Walk through your code line by line with the input. Track variable values.
  Say: "At this point windowSum = 5, maxSum = 5..."

COMMON BUG PATTERNS TO WATCH:
  - Off-by-one errors (< vs <=, starting index)
  - Null pointer (forgot null check)
  - Integer overflow (sum of many integers - use long in Java)
  - Initializing result to wrong value (should be 0, INT_MIN, or nums[0])
  - Missing final return or wrong return value
  - Not handling empty input

IF YOU FIND A BUG:
  "Oh, I see an issue here - my loop should start at 1, not 0, because
  I'm accessing i-1 and don't want to go out of bounds. Let me fix that."
  
  Say it calmly. Fix it. Don't panic.

--------------------------------------------------------------------------------
STEP 7: ANALYZE COMPLEXITY
--------------------------------------------------------------------------------

Always state time and space complexity without being asked.
This shows engineering maturity.

FORMAT:
  "The time complexity is O(n) where n is the length of the input array.
   I iterate through the array once, and each HashMap operation is O(1)
   amortized. The space complexity is O(n) for the HashMap in the worst
   case where all characters are unique."

BE SPECIFIC ABOUT WHAT n, m, k REPRESENT.
  "O(n * m) where n is the number of rows and m is the number of columns"
  NOT just "O(n*m)"

COMMON COMPLEXITIES:
  O(1)       - Single lookup, math computation
  O(log n)   - Binary search, tree height traversal
  O(n)       - Single pass through array
  O(n log n) - Sort, divide and conquer, heap insertions
  O(n²)      - Nested loops
  O(2^n)     - Subset enumeration, backtracking
  O(n!)      - Permutation enumeration

FOLLOW-UP: "CAN YOU DO BETTER?"
  If you gave an O(n log n) solution, prepare for: "Can you do it in O(n)?"
  Think about:
  - What information is being recomputed that could be cached?
  - Can a hash map replace the sorting?
  - Can a sliding window replace the nested loop?
  Don't panic. Say: "Let me think about what's causing the extra log factor..."

--------------------------------------------------------------------------------
3. PATTERNS FOR QUICK RECOGNITION IN INTERVIEWS
--------------------------------------------------------------------------------

When you read a problem, these SIGNAL WORDS should trigger pattern recognition:

SIGNAL → PATTERN:

  "Subarray/Substring with condition"          → Sliding Window
  "Sorted array + two values"                  → Two Pointers
  "K-th largest/smallest"                      → Heap
  "All combinations/subsets/permutations"      → Backtracking
  "Shortest path / fewest steps"               → BFS
  "Tree traversal / path in tree"              → DFS
  "Previously seen / count occurrences"        → HashMap
  "Contiguous subarray sum"                    → Prefix Sum
  "Overlapping subproblems"                    → Dynamic Programming
  "Make the optimal choice at each step"       → Greedy
  "Sorted array + find element / boundary"     → Binary Search
  "Graph connectivity / components"            → Union-Find or DFS
  "Next greater / smaller element"             → Monotonic Stack
  "Word search / prefix matching"              → Trie

--------------------------------------------------------------------------------
4. HANDLING DIFFERENT PROBLEM FORMATS
--------------------------------------------------------------------------------

FOR PROBLEMS WITH MULTIPLE APPROACHES:
  Present the simplest correct approach first.
  Then discuss optimization.
  Never skip directly to complex optimal if you can't explain the path there.

FOR PROBLEMS YOU'VE SEEN BEFORE:
  Be honest: "I think I've seen a similar problem before, so I have a
  direction in mind. Let me walk through my reasoning to make sure I
  understand why this approach works..."
  
  DON'T: Silently write the optimal solution with no explanation.
  This backfires because you can't explain WHY it works.

FOR PROBLEMS THAT SEEM VERY HARD:
  Start simpler: "Let me think about a simplified version first...
  if the array only had 2 elements, the answer would be..."
  Reduce to base case. Build up.

FOR GRAPH/TREE PROBLEMS:
  Always draw the structure first on paper/whiteboard.
  Trace through an example manually before coding.
  Ask: directed or undirected? weighted? cyclic?

--------------------------------------------------------------------------------
5. PRACTICE DRILL - THE 45-MINUTE MOCK PROBLEM SESSION
--------------------------------------------------------------------------------

Do this for EVERY practice problem:

  0:00 - Start timer
  0:00-3:00 - Read problem twice. Understand input/output.
  3:00-6:00 - Ask clarifying questions (to yourself, out loud)
  6:00-9:00 - Identify constraints and edge cases (write them down)
  9:00-14:00 - State approach out loud. Brute force first, then optimize.
  14:00-34:00 - Code the solution (speak as you write)
  34:00-40:00 - Test with given example + 2 edge cases
  40:00-43:00 - State time and space complexity
  43:00-45:00 - Review: "Is there a cleaner way? What are the trade-offs?"

After session:
  - Compare with editorial / best solution
  - Identify: What pattern did you miss? What would you do differently?
  - Rate yourself: Process (1-5), Code quality (1-5), Communication (1-5)
