================================================================================
DRY RUN AND TESTING - HOW TO VERIFY YOUR SOLUTION LIKE A PRO
================================================================================
Last Updated: April 2026
Purpose: Master the technique of manually tracing through your code to find
         bugs before being asked, and impress interviewers with testing rigor.
================================================================================

--------------------------------------------------------------------------------
1. WHY DRY RUNNING IS A CRITICAL INTERVIEW SKILL
--------------------------------------------------------------------------------

After you finish writing your code, most candidates say "I think that's it."
Strong candidates say "Let me trace through this with an example to verify."

This distinction matters because:
  - It catches bugs BEFORE the interviewer points them out
  - It shows you don't trust code blindly (production mindset)
  - It demonstrates systematic thinking
  - It often shows the interviewer something they didn't catch
  - It buys you time to think if you're still figuring out the solution

THE RULE:
  Never declare your solution "done" without tracing through at least one
  example. Even if you're 100% confident, always do it.

--------------------------------------------------------------------------------
2. WHAT IS A DRY RUN?
--------------------------------------------------------------------------------

A dry run (also called a trace or desk check) is manually simulating your
code execution with a specific input, tracking the values of all relevant
variables at each step.

It answers the questions:
  - Does this code do what I THINK it does?
  - Are there off-by-one errors in loop boundaries?
  - Are there uninitialized or incorrectly initialized variables?
  - Does the final return statement produce the correct result?
  - Do edge cases break the logic?

--------------------------------------------------------------------------------
3. HOW TO DRY RUN EFFECTIVELY
--------------------------------------------------------------------------------

STEP 1: CHOOSE YOUR TEST INPUT
  - Start with the PROVIDED EXAMPLE in the problem
  - Then use a SELF-CREATED example (slightly different)
  - Then test EDGE CASES (empty, single element, negatives, etc.)

GOOD TEST INPUT PROPERTIES:
  - Small enough to trace completely (5-8 elements)
  - Contains variation (not all same value)
  - Covers the "interesting" case where the algorithm does something non-trivial
  - Different from the example given (to catch assumptions)

BAD TEST INPUT:
  - Too large (20+ elements; you'll get lost)
  - All same values (misses the interesting path through your logic)
  - Identical to the given example (might miss other behaviors)

STEP 2: SET UP YOUR TRACKING TABLE
  On your scratch paper or whiteboard, create a table:

  For a simple array traversal:
  ```
  i  | nums[i] | maxSoFar | currentSum | note
  ---+---------+----------+------------+------
  0  | 2       | 2        | 2          | init
  1  | -3      | 2        | -1         | currentSum < 0, reset
  2  | 4       | 4        | 4          | new max
  3  | 1       | 5        | 5          | accumulating
  ```

  For a HashMap problem:
  ```
  i  | char | map state        | result
  ---+------+------------------+--------
  0  | 'a'  | {a:0}            | 0
  1  | 'b'  | {a:0, b:1}       | 0
  2  | 'a'  | {a:0, b:1}       | 2 (i - map.get('a') = 2-0=2)
  ```

STEP 3: TRACE LINE BY LINE
  Go through your code line by line, updating the table with each step.
  Say it out loud:
  "At i=0, nums[0] is 2. Since currentSum (0) + 2 = 2 > 0, we keep it.
   maxSoFar = max(0, 2) = 2. Moving to i=1..."

STEP 4: VERIFY THE OUTPUT
  "At the end of the loop, maxSoFar = 5, and I return maxSoFar. The
   expected answer is 5. ✓"

STEP 5: RUN EDGE CASES
  "Now let me quickly check: what if the input is empty? My null check
   at line 3 returns 0 immediately. ✓"
  "What if all values are negative, say [-1, -2, -3]? With my initialization
   of maxSoFar = nums[0] = -1, and currentSum = -1... let me trace this..."

--------------------------------------------------------------------------------
4. VERBAL DRY RUN - WHAT TO SAY OUT LOUD
--------------------------------------------------------------------------------

In a live interview, your dry run should be VERBAL. Don't just trace silently.

NARRATION TEMPLATE:
  "Let me trace through this with input [2, -3, 4, 1].
   
   I initialize maxSoFar to nums[0] = 2, and currentSum to nums[0] = 2.
   
   At i=1, nums[1] = -3. currentSum = max(-3, 2 + (-3)) = max(-3, -1) = -1.
   Since -1 < 0, I reset currentSum to -3. maxSoFar stays at 2.
   
   Wait - actually, should currentSum be reset or should it be the current
   element? Let me re-check my Kadane's logic... yes, currentSum should be
   max(nums[i], currentSum + nums[i])... so at i=1, it's max(-3, -1) = -1.
   maxSoFar is still max(2, -1) = 2.
   
   At i=2, nums[2] = 4. currentSum = max(4, -1+4) = max(4, 3) = 4.
   maxSoFar = max(2, 4) = 4.
   
   At i=3, nums[3] = 1. currentSum = max(1, 4+1) = max(1, 5) = 5.
   maxSoFar = max(4, 5) = 5.
   
   Return maxSoFar = 5. ✓ That matches the expected output."

KEY ASPECTS OF GOOD VERBAL TRACE:
  - Say what variable you're updating and why
  - Call out when something interesting happens ("wait, should this reset?")
  - Explicitly state the final return value
  - Confirm it matches expectation

--------------------------------------------------------------------------------
5. WHAT TO DO WHEN YOU FIND A BUG DURING DRY RUN
--------------------------------------------------------------------------------

This is ACTUALLY a good situation. Finding your own bug > interviewer finding it.

WRONG REACTION:
  "Oh no... ugh... sorry... that's wrong..." (panicky, loses confidence)

RIGHT REACTION:
  "Ah, I see the issue here. At this step, my condition should be
   <= not <, because we need to include equal elements. Let me fix
   that on line 8."

STEPS:
  1. Say calmly: "I found an issue."
  2. Identify it precisely: "The condition on line X is wrong because..."
  3. Fix it confidently: "It should be [correct version] because [reason]."
  4. Continue the trace: "Let me re-trace from that point..."

PRINCIPLE: Finding and fixing your own bugs is a POSITIVE signal.
  It shows:
  - You have a debugging process
  - You don't blindly trust code
  - You can identify root cause, not just symptoms

--------------------------------------------------------------------------------
6. TESTING STRATEGY FOR DIFFERENT PROBLEM TYPES
--------------------------------------------------------------------------------

ARRAY PROBLEMS:
  Test cases to cover:
  1. Normal case (given example)
  2. Empty array → return 0 or -1
  3. Single element → check loop boundary
  4. All same elements → check deduplication/uniqueness logic
  5. Sorted input → check if algorithm handles sorted correctly
  6. All negatives → check initialization value

STRING PROBLEMS:
  Test cases to cover:
  1. Normal case
  2. Empty string → ""
  3. Single character
  4. All same characters "aaaaaa"
  5. Beginning/end of answer at boundary
  6. Palindrome or near-palindrome

LINKED LIST PROBLEMS:
  Test cases to cover:
  1. Normal multi-node list
  2. Single node
  3. Two nodes
  4. Operation on head node (requires returning new head)
  5. Operation on last node

TREE PROBLEMS:
  Test cases to cover:
  1. Normal balanced tree
  2. Null root
  3. Single node
  4. All left or all right (skewed)
  5. Answer is at root vs at leaf

GRAPH PROBLEMS:
  Test cases to cover:
  1. Connected graph
  2. Disconnected graph
  3. Single node, no edges
  4. Cycle (if relevant)
  5. Directed cycle (if relevant for topological sort)

DYNAMIC PROGRAMMING PROBLEMS:
  Test cases to cover:
  1. n = 0 or empty
  2. n = 1 (base case)
  3. n = 2 (first transition)
  4. Larger normal case (verify dp table logic)
  5. All same values

--------------------------------------------------------------------------------
7. COMMON BUGS FOUND DURING DRY RUN
--------------------------------------------------------------------------------

OFF-BY-ONE ERRORS (most common):
  BAD:  for (int i = 0; i < n; i++) { ... arr[i+1] }  // ArrayIndexOutOfBounds at i=n-1
  FIX:  for (int i = 0; i < n - 1; i++) { ... arr[i+1] }
  
  BAD:  return dp[n] where dp is size n (indices 0 to n-1)
  FIX:  return dp[n-1], or allocate dp of size n+1

WRONG INITIALIZATION:
  BAD:  int max = 0; (wrong if all values are negative)
  FIX:  int max = nums[0]; (correct initial value)
  
  BAD:  int sum = Integer.MAX_VALUE; (for min sum problem)
  FIX:  int sum = Integer.MAX_VALUE; or Integer.MIN_VALUE depending on what you need

MISSING RETURN STATEMENT:
  BAD:  Function falls through without returning in some branch
  FIX:  Ensure all code paths return a value

WRONG LOOP DIRECTION:
  BAD:  Iterating left to right when right to left is needed
  FIX:  Trace through manually; if the answer is wrong direction, flip

NOT RESTORING STATE IN BACKTRACKING:
  BAD:  list.add(item); recurse(); (missing: list.remove(list.size()-1))
  FIX:  Always have an undo step matching each action step

NULL POINTER EXCEPTIONS:
  BAD:  node.left.val (crashes if left is null)
  FIX:  node.left != null && node.left.val

USING WRONG INDEX:
  BAD:  dp[i] = dp[i-1] + dp[i-2]; (ArrayIndexOutOfBounds at i=1)
  FIX:  Start loop at i=2, with base cases dp[0] and dp[1] set

--------------------------------------------------------------------------------
8. THE 3-TEST MINIMUM RULE
--------------------------------------------------------------------------------

In every interview, run at MINIMUM 3 tests before declaring done:

  TEST 1: The provided example (or a straightforward normal case)
  TEST 2: An edge case (empty, single element, or all-same)
  TEST 3: A boundary case (answer at first element, negative values, k=n)

When you announce these tests to the interviewer:
  "I'll verify with three cases: the given example, an empty input,
   and a case where all values are negative."

This demonstrates a systematic testing approach and gives the interviewer
confidence that you think about correctness comprehensively.

--------------------------------------------------------------------------------
9. AFTER THE DRY RUN: COMPLEXITY CONFIRMATION
--------------------------------------------------------------------------------

After testing, before declaring done:

  "My solution has O(n) time complexity: I iterate through the array once,
   and all operations inside the loop are O(1). Space complexity is O(1)
   beyond the input, since I only use a few scalar variables.
   
   Is there anything you'd like me to optimize or any edge case you'd
   like me to handle differently?"

This closing sequence:
  - Cements your complexity analysis
  - Opens the door for the interviewer to push for optimization
  - Shows you're not done thinking even after the code works
