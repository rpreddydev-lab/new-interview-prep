1. ENVIRONMENT VARIABLE TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js has two categories of environment variables:

  Server-only (SECRET):
    - Accessible in: Server Components, Route Handlers, Server Actions, Middleware
    - NOT accessible in Client Components
    - Named without NEXT_PUBLIC_ prefix
    - Example: DATABASE_URL, STRIPE_SECRET_KEY, AUTH_SECRET

  Public (exposed to browser):
    - Accessible in: Client Components AND server-side code
    - Named with NEXT_PUBLIC_ prefix
    - Inlined at BUILD TIME into the JavaScript bundle
    - Example: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_POSTHOG_KEY

  // Usage:
  // Server Component:
  const dbUrl = process.env.DATABASE_URL;     // works
  const apiKey = process.env.STRIPE_SECRET_KEY; // works

  // Client Component:
  const publicUrl = process.env.NEXT_PUBLIC_API_URL; // works (inlined at build)
  const secret = process.env.DATABASE_URL;    // undefined (never exposed)

2. ENV FILE LOADING ORDER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js loads env files in this priority order (higher = overrides lower):

  1. process.env (OS-level, CI/CD variables)
  2. .env.$(NODE_ENV).local  (.env.production.local, .env.development.local)
  3. .env.local              (local overrides — NOT loaded in test environment)
  4. .env.$(NODE_ENV)        (.env.production, .env.development, .env.test)
  5. .env                    (base defaults)

  Environments: development (npm run dev), production (npm run build/start), test

  File purposes:
    .env                   → shared defaults, committed to git
    .env.local             → local overrides, NEVER commit to git
    .env.development       → dev defaults, can be committed
    .env.production        → production defaults (non-secrets), can be committed
    .env.development.local → local dev overrides, never commit
    .env.production.local  → local production testing, never commit

  // .gitignore (essential):
  .env*.local     # ignore all .local files

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. USING ENV VARIABLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // .env.local
  DATABASE_URL="postgresql://user:pass@localhost:5432/mydb"
  STRIPE_SECRET_KEY="sk_test_..."
  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY="pk_test_..."
  NEXT_PUBLIC_APP_URL="http://localhost:3000"

  // Server Component / Route Handler / Server Action:
  const stripeKey = process.env.STRIPE_SECRET_KEY!; // server-only
  const dbUrl = process.env.DATABASE_URL!;

  // Client Component (only NEXT_PUBLIC_):
  'use client';
  const publishableKey = process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY;
  // This value is replaced at build time with the actual string literal

  // process.env.NEXT_PUBLIC_KEY → replaced at build with "pk_test_..."
  // Changing it requires a rebuild!

4. TYPESCRIPT SAFETY WITH ENV VARIABLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // env.ts — validate and type env vars at startup
  import { z } from 'zod';

  const serverSchema = z.object({
    DATABASE_URL: z.string().url(),
    STRIPE_SECRET_KEY: z.string().startsWith('sk_'),
    AUTH_SECRET: z.string().min(32),
    NODE_ENV: z.enum(['development', 'test', 'production']),
  });

  const clientSchema = z.object({
    NEXT_PUBLIC_APP_URL: z.string().url(),
    NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY: z.string().startsWith('pk_'),
  });

  // Validate server env at startup:
  const _serverEnv = serverSchema.safeParse(process.env);
  if (!_serverEnv.success) {
    console.error('❌ Invalid server environment variables:', _serverEnv.error.format());
    throw new Error('Invalid server env vars');
  }
  export const env = _serverEnv.data;

  // Usage: import { env } from '@/lib/env';
  // env.DATABASE_URL — fully typed, validated at startup

  // Popular library: t3-env (or @t3-oss/env-nextjs)
  import { createEnv } from '@t3-oss/env-nextjs';

  export const env = createEnv({
    server: {
      DATABASE_URL: z.string().url(),
      AUTH_SECRET: z.string().min(1),
    },
    client: {
      NEXT_PUBLIC_APP_URL: z.string().url(),
    },
    runtimeEnv: {
      DATABASE_URL: process.env.DATABASE_URL,
      AUTH_SECRET: process.env.AUTH_SECRET,
      NEXT_PUBLIC_APP_URL: process.env.NEXT_PUBLIC_APP_URL,
    },
  });

5. ENV VARIABLES IN DIFFERENT CONTEXTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Context                  | Access to NEXT_PUBLIC_ | Access to SECRET
  ─────────────────────── | ────────────────────── | ──────────────────
  Server Component         | ✓                      | ✓
  Client Component         | ✓ (build-time replace)  | ✗ (undefined)
  Route Handler            | ✓                      | ✓
  Server Action            | ✓                      | ✓
  Middleware               | ✓                      | ✓ (Edge-safe only)
  next.config.ts           | ✓                      | ✓
  API Route (Pages Router) | ✓                      | ✓
  getServerSideProps       | ✓                      | ✓
  getStaticProps           | ✓                      | ✓

  // IMPORTANT: getStaticProps runs at build time.
  // If you use a secret in getStaticProps, make sure it's available at BUILD time
  // (CI/CD must have the var set when building)

6. RUNTIME vs BUILD-TIME ENV VARS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Build-time:
    - NEXT_PUBLIC_ variables are inlined into the JS bundle during `next build`
    - Changing them requires a REBUILD AND REDEPLOY
    - Cannot change at runtime without a new build

  Runtime:
    - Server-only (non-NEXT_PUBLIC_) variables are read at REQUEST time
    - Can be changed without rebuilding (just restart the server)
    - On Vercel: change env var in dashboard → redeploy (not just restart)

  // This is why API keys for third parties that change rarely use NEXT_PUBLIC_
  // but database URLs, secrets, and tokens that might rotate use server-only vars

7. COMMON MISTAKES AND GOTCHAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Mistake 1: Using server secrets in Client Components
    // BAD:
    'use client';
    const key = process.env.STRIPE_SECRET_KEY; // undefined → runtime error

  Mistake 2: Destructuring process.env
    // BAD: Next.js can't statically replace these
    const { DATABASE_URL } = process.env;  // may not work
    // GOOD:
    const dbUrl = process.env.DATABASE_URL; // static string replacement works

  Mistake 3: Dynamic key access
    // BAD: Next.js can't statically analyze this
    const key = `NEXT_PUBLIC_${name}`;
    process.env[key]; // won't work as expected for client vars

  Mistake 4: Committing .env.local
    // Always add to .gitignore:
    .env*.local

  Mistake 5: Forgetting vars in CI/CD
    // Build fails because DATABASE_URL is undefined
    // Must set all required server vars in CI environment / Vercel dashboard

8. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What's the difference between NEXT_PUBLIC_ and regular env vars?
A:  NEXT_PUBLIC_ variables are inlined into the JavaScript bundle at build time
    and are accessible in both server and client code. Regular env vars are
    server-only — they're read at request time and never sent to the browser.
    Use NEXT_PUBLIC_ for values the frontend needs (analytics IDs, public API URLs).
    Use regular vars for secrets (database URLs, API keys, auth secrets).

Q2: Can you access a non-NEXT_PUBLIC_ variable in a Client Component?
A:  No. In a Client Component, process.env.MY_SECRET evaluates to undefined.
    To pass server data to a Client Component: pass it as a prop from a
    Server Component, or expose it through a server-side API endpoint.

Q3: What is the loading order of .env files and which takes priority?
A:  Priority (highest first): OS env → .env.$(NODE_ENV).local → .env.local →
    .env.$(NODE_ENV) → .env. A .env.local file overrides .env defaults.
    .env.production.local overrides .env.production.

Q4: If you change a NEXT_PUBLIC_ variable, do you need to rebuild?
A:  Yes. NEXT_PUBLIC_ variables are inlined (replaced as string literals) at
    build time. They become part of the compiled JavaScript bundle. Changing
    the value requires a new build. Server-only variables are read at runtime
    and can be changed without a rebuild (just restart the server or redeploy).

Q5: How do you validate environment variables in a type-safe way?
A:  Use Zod schemas to validate process.env at startup (before the server
    handles any requests). If validation fails, throw an error immediately —
    better to crash at startup than get undefined at runtime. The @t3-oss/env-nextjs
    package provides a type-safe environment variable validator for Next.js projects.

Q6: How do you handle env vars for different environments (dev/staging/prod)?
A:  Use different .env files: .env for base defaults, .env.development and
    .env.production for environment-specific non-secrets, .env.local for local
    overrides (never committed). On Vercel, configure Production/Preview/Development
    env vars separately in the dashboard. Use preview-specific databases to
    prevent contaminating production data.

================================================================================
  SECURITY RULE: Never prefix secrets with NEXT_PUBLIC_.
  Secrets in client code are exposed to all users — they can view the
  JavaScript bundle and extract any NEXT_PUBLIC_ value.
================================================================================
