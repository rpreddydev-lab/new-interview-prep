1. VERCEL PLATFORM OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Vercel is the company behind Next.js and the recommended deployment platform.
It provides a first-class hosting experience with zero-configuration deployment.

Core Vercel infrastructure:
  - Edge Network (CDN): static assets, ISR, Edge Functions
  - Serverless Functions: API routes, SSR pages, Route Handlers
  - Edge Functions: Middleware, Edge Runtime routes
  - Build System: automatic Next.js build optimization
  - Analytics: Core Web Vitals, real user monitoring

Pricing tiers:
  - Hobby (Free): personal projects, preview deployments
  - Pro: teams, advanced analytics, concurrent builds
  - Enterprise: custom contracts, SLA, SSO

2. DEPLOYING TO VERCEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Option A — Git integration (recommended):
  1. Push to GitHub/GitLab/Bitbucket
  2. Import project on vercel.com/new
  3. Vercel auto-detects Next.js, sets build command: next build
  4. Every push to main → Production deployment
  5. Every PR → Preview deployment (unique URL)

Option B — Vercel CLI:
  npm i -g vercel
  vercel          # deploy to preview
  vercel --prod   # deploy to production

  # Vercel CLI also handles:
  vercel env pull .env.local  # pull env vars to local
  vercel logs                 # view deployment logs
  vercel dev                  # run locally with Vercel env

Option C — CI/CD with GitHub Actions:
  # .github/workflows/deploy.yml
  jobs:
    deploy:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-node@v4
          with: { node-version: 20 }
        - run: npm ci && npm run build
        - uses: amondnet/vercel-action@v25
          with:
            vercel-token: ${{ secrets.VERCEL_TOKEN }}
            vercel-org-id: ${{ secrets.ORG_ID }}
            vercel-project-id: ${{ secrets.PROJECT_ID }}

3. HOW VERCEL RUNS NEXT.JS UNDER THE HOOD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  next build output → .next/ folder:
    .next/static/        → static assets (JS, CSS, images) → served from CDN
    .next/server/        → server-side code → Serverless Functions
    Pre-rendered HTML    → SSG/ISR pages → served from Edge CDN

  Route type → Vercel infrastructure:
    Static pages (SSG)        → Edge CDN (global, instant)
    SSR pages (getSSP)        → Serverless Functions (per-region or global)
    ISR pages                 → Edge CDN + background revalidation
    API routes / Route handlers → Serverless Functions
    Middleware                → Edge Functions (runs at CDN edge, no cold start)
    Server Actions            → Serverless Functions (POST endpoints)

4. PREVIEW DEPLOYMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Every pull request gets a unique preview URL:
  https://my-app-git-feature-branch-myorg.vercel.app

Features:
  - Shares production environment variables (configurable)
  - Can override specific env vars per branch/preview
  - Automatic comments on PR with preview link
  - Shareable for stakeholder review
  - Isolated from production data (good practice: use test DB)

  // Configure preview env overrides in Vercel dashboard:
  // Environment Variables → Set environment → Preview
  // Set DATABASE_URL to preview database for PRs

5. VERCEL vs SELF-HOSTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Aspect                  | Vercel                   | Self-Host (Docker/Node)
  ──────────────────────  | ───────────────────────  | ──────────────────────
  Setup time              | Minutes                  | Hours/Days
  Edge CDN                | Global, built-in         | Manual CDN setup
  ISR support             | Full, automatic          | Requires custom setup
  Middleware               | Edge, zero config        | Via Node server
  Previews per PR          | Automatic                | Manual
  Scaling                 | Auto-scale               | Configure manually
  Cold starts             | Managed                  | Depends on infra
  Cost (high traffic)     | Expensive at scale       | Cheaper (own servers)
  Vendor lock-in          | Moderate                 | None
  Custom infrastructure   | Limited                  | Full control
  Multi-region deployment | Pro/Enterprise only      | Full control
  Node.js version control | Via package.json engines | Full control

  Self-hosting Next.js:
    // Dockerfile
    FROM node:20-alpine AS builder
    WORKDIR /app
    COPY package*.json ./
    RUN npm ci
    COPY . .
    RUN npm run build

    FROM node:20-alpine
    WORKDIR /app
    COPY --from=builder /app/.next/standalone ./
    COPY --from=builder /app/.next/static ./.next/static
    COPY --from=builder /app/public ./public
    EXPOSE 3000
    ENV PORT 3000
    CMD ["node", "server.js"]

    // next.config.ts for standalone output:
    module.exports = { output: 'standalone' };

6. ENVIRONMENT VARIABLES IN VERCEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Types of variables:
    - Production: main branch / prod deployments
    - Preview: PR deployments
    - Development: local dev (pulled via vercel env pull)

  Sensitive variables (marked as "sensitive"):
    - Encrypted, never shown in dashboard after saving
    - Used for DATABASE_URL, API_SECRET_KEY, etc.

  Team-level vs project-level env vars.
  System env vars set automatically by Vercel:
    VERCEL=1                    → always set on Vercel
    VERCEL_ENV                  → production|preview|development
    VERCEL_URL                  → deployment URL (preview deployments)
    VERCEL_GIT_COMMIT_SHA       → commit hash
    VERCEL_REGION               → region code (iad1, sfo1, etc.)

    "buildCommand": "npm run build",
    "outputDirectory": ".next",
    "installCommand": "npm ci",
    "framework": "nextjs",
    "regions": ["iad1"],          // deploy to specific regions
    "functions": {
      "app/api/heavy/route.ts": {
        "maxDuration": 60,        // max serverless function timeout (seconds)
        "memory": 1024            // memory in MB
      }
    },
    "headers": [
      {
        "source": "/api/(.*)",
        "headers": [
          { "key": "X-Frame-Options", "value": "DENY" }
        ]
      }
    ]
  }

8. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What are the different deployment environments in Vercel?
A:  Production (from main branch), Preview (from PRs and non-main branches),
    and Development (local). Each can have different environment variables.
    Preview deployments get a unique URL for stakeholder review, and they
    can use separate databases/services to avoid polluting production data.

Q2: How does Vercel handle SSR vs SSG routes differently?
A:  Static pages (SSG/ISR) are served from Vercel's Edge CDN globally —
    instant response from the nearest CDN node. SSR pages run as Serverless
    Functions, deployed to specific regions. Middleware runs as Edge Functions
    (V8 isolates at CDN edge) — no cold starts, sub-millisecond overhead.

Q3: What is the output: 'standalone' option in Next.js?
A:  It creates a self-contained build in .next/standalone/ that includes only
    the necessary files to run the server. No need for node_modules. Ideal for
    Docker deployments. Must separately copy public/ and .next/static/ to the
    output directory.

Q4: What are preview deployments and why are they valuable?
A:  Each PR automatically gets a unique deployment URL. Stakeholders can review
    UI changes before merging. QA teams can test against real server-rendered
    data. They prevent "it works on my machine" issues. They can connect to
    a staging database to test data changes safely.

Q5: What is VERCEL_URL and when is it useful?
A:  VERCEL_URL is an env var automatically set by Vercel to the deployment's
    URL (e.g., my-app-abc123.vercel.app). It's useful for setting absolute
    URLs in preview deployments (e.g., for OAuth redirect URLs, metadata
    canonical URLs, og:url). Not set in development — handle with fallback:
    const url = process.env.VERCEL_URL || 'http://localhost:3000';

Q6: What is Vercel Functions and how does serverless scaling work?
A:  Serverless Functions are on-demand compute that scales to zero when idle.
    Each request spawns (or reuses) a function instance. No server management.
    Limitation: 10-second default timeout (configurable to 60s on Pro). Cold
    starts can add latency on first request. Use Edge Runtime for lower latency,
    and connect to edge-compatible databases (Neon, PlanetScale, Upstash).
