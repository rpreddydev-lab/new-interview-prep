1. WHAT IS CLIENT-SIDE FETCHING IN NEXT.JS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Client-side fetching (CSR) means data is fetched in the browser AFTER the
component mounts, using useEffect + fetch/axios or a library like SWR/React
Query. The initial HTML from the server has no data; data loads after hydration.

In Next.js, CSR coexists with SSR/SSG/ISR. You choose per-component:
  - The page shell can be SSG/SSR (SEO-friendly)
  - Individual components can use CSR (user-specific data)

2. BASIC CSR PATTERN (useEffect + fetch)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  'use client'; // Required in App Router
  import { useState, useEffect } from 'react';

  interface User {
    id: string;
    name: string;
    email: string;
  }

  export default function UserProfile({ userId }: { userId: string }) {
    const [user, setUser] = useState<User | null>(null);
    const [loading, setLoading] = useState(true);
    const [error, setError] = useState<Error | null>(null);

    useEffect(() => {
      const controller = new AbortController();

      async function fetchUser() {
        try {
          setLoading(true);
          const res = await fetch(`/api/users/${userId}`, {
            signal: controller.signal,
          });

          if (!res.ok) throw new Error(`HTTP ${res.status}`);
          const data = await res.json();
          setUser(data);
        } catch (err) {
          if ((err as Error).name !== 'AbortError') {
            setError(err as Error);
          }
        } finally {
          setLoading(false);
        }
      }

      fetchUser();

      // Cleanup: abort fetch if component unmounts or userId changes
      return () => controller.abort();
    }, [userId]);

    if (loading) return <Skeleton />;
    if (error) return <ErrorMessage error={error} />;
    if (!user) return null;

    return (
      <div>
        <h1>{user.name}</h1>
        <p>{user.email}</p>
      </div>
    );
  }

3. PROBLEMS WITH useEffect DATA FETCHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WATERFALL REQUESTS
   Component A renders → useEffect runs → fetches A data → A renders children →
   Child B mounts → useEffect runs → fetches B data → B renders...
   Each level waits for the parent. Sequential, slow.

2. RACE CONDITIONS
   User types fast → multiple fetches in flight → the first response might
   arrive after the second → stale data overwrites fresh data.
   Fix: AbortController (as shown above) or track latest request ID.

3. NO CACHING BY DEFAULT
   Every component mount triggers a new fetch. Navigate back and forth →
   re-fetches every time. Use SWR or React Query to solve this.

4. LOADING STATE HELL
   Every component needs its own loading, error, and empty states.
   Boilerplate everywhere.

5. SSR HYDRATION MISMATCH
   Server renders with no data → client renders with data →
   if component renders differently, React might warn about mismatch.

4. WHEN TO USE CLIENT-SIDE FETCHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✓ User-specific data (cart, notifications, personalized recommendations)
  ✓ Frequently updating data (live scores, real-time prices)
  ✓ Data behind authentication (no SEO needed)
  ✓ User-triggered actions (search autocomplete, lazy-loaded tabs)
  ✓ Infinite scroll / pagination
  ✓ Third-party widget data (weather, social feeds)

  ✗ NOT for data that affects SEO (use SSR/SSG instead)
  ✗ NOT for initial page content users need to see immediately
  ✗ NOT when you can put the data in a Server Component (App Router)

5. HYBRID PATTERN: SSG SHELL + CSR DATA

Best of both worlds: static shell (SEO, fast FCP) + dynamic data (freshness).

  // pages/profile.tsx
  // SHELL is SSG (fast, SEO for public parts)
  export const getStaticProps = async () => ({
    props: { publicInfo: await getPublicInfo() },
  });

  export default function ProfilePage({ publicInfo }) {
    return (
      <div>
        {/* SSG content - visible immediately */}
        <h1>{publicInfo.title}</h1>

        {/* CSR content - loads after hydration */}
        <UserDashboard />   {/* fetches user-specific data client-side */}
      </div>
    );
  }

  // App Router equivalent:
  // app/profile/page.tsx (Server Component — public data)
  export default async function ProfilePage() {
    const publicInfo = await getPublicInfo();  // pre-rendered
    return (
      <div>
        <h1>{publicInfo.title}</h1>
        <UserDashboard />    {/* Client Component with useEffect */}
      </div>
    );
  }

6. AVOIDING HYDRATION MISMATCHES WITH CSR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // PROBLEM: renders differently on server vs client
  function NotificationBell() {
    const count = getNotificationCount(); // doesn't exist on server
    return <span>{count} notifications</span>;
  }

  // SOLUTION 1: useState + useEffect (CSR only)
  'use client';
  function NotificationBell() {
    const [count, setCount] = useState(0);
    const [mounted, setMounted] = useState(false);

    useEffect(() => {
      setMounted(true);
      setCount(getNotificationCount());
    }, []);

    if (!mounted) return <span>notifications</span>; // server-safe placeholder
    return <span>{count} notifications</span>;
  }

  // SOLUTION 2: dynamic import with ssr:false
  import dynamic from 'next/dynamic';
  const NotificationBell = dynamic(() => import('./NotificationBell'), {
    ssr: false,   // ONLY render on client; no server render at all
    loading: () => <span>...</span>,
  });

7. next/dynamic — CODE SPLITTING & LAZY LOADING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

next/dynamic is like React.lazy but with SSR control.

  import dynamic from 'next/dynamic';

  // Lazy load a heavy component (code-split, loads on demand)
  const HeavyChart = dynamic(() => import('./HeavyChart'), {
    loading: () => <ChartSkeleton />,
  });

  // Disable SSR for browser-only components
  const MapComponent = dynamic(() => import('./MapComponent'), {
    ssr: false,  // won't be rendered on server (avoids window/document errors)
  });

  // Named export
  const Editor = dynamic(() =>
    import('./rich-text-editor').then(mod => mod.RichTextEditor)
  );

  // With custom loading
  const Modal = dynamic(() => import('./Modal'), {
    loading: () => <div className="modal-skeleton" />,
  });

  Use cases for ssr: false:
    - Leaflet, Google Maps (uses window)
    - Browser-only plugins (canvas, WebGL)
    - Components that use localStorage, sessionStorage
    - Third-party scripts that aren't SSR-compatible

8. OPTIMISTIC UPDATES PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Update UI immediately before server confirms — better UX.

  'use client';
  function LikeButton({ postId, initialLikes }) {
    const [likes, setLikes] = useState(initialLikes);
    const [loading, setLoading] = useState(false);

    async function handleLike() {
      // Optimistically update
      setLikes(prev => prev + 1);
      setLoading(true);

      try {
        await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
      } catch {
        // Rollback on failure
        setLikes(prev => prev - 1);
      } finally {
        setLoading(false);
      }
    }

    return (
      <button onClick={handleLike} disabled={loading}>
        ♥ {likes}
      </button>
    );
  }

9. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: When would you use client-side fetching in a Next.js app?
A:  For user-specific data (notifications, cart), real-time data (live scores),
    or auth-gated content where SEO doesn't matter. In App Router, prefer Server
    Components for data that can be fetched server-side; use CSR only when the
    data is user-specific or must update without a page refresh.

Q2: What is a race condition in useEffect data fetching and how do you fix it?
A:  If a component fetches data on prop change and the user triggers multiple
    rapid changes, multiple fetches can be in flight. The first fetch might
    resolve after the second (slower network), overwriting fresh data with stale.
    Fix: use AbortController — cancel the previous fetch when a new one starts.
    SWR and React Query handle this automatically.

Q3: What does dynamic with ssr: false do?
A:  It prevents the component from being rendered on the server at all. The
    server sends a loading placeholder; the actual component loads only in
    the browser. Use for components that rely on browser APIs (window, document,
    canvas) that don't exist during SSR.

Q4: How do you prevent a hydration mismatch when data differs server vs client?
A:  (1) Don't render the data on the server at all (dynamic ssr: false, or
        useState with mounted check)
    (2) suppressHydrationWarning on elements that intentionally differ
    (3) Move browser-only code to useEffect
    (4) Use the 'use client' directive and useState/useEffect for client state

Q5: What is the difference between fetch in a Server Component vs useEffect?
A:  Server Component fetch: runs on the server, included in initial HTML,
    SEO-friendly, no client JS overhead, can access secrets, can be cached.
    useEffect fetch: runs in the browser after hydration, client JS is needed,
    shows loading state, no server access, not SEO-friendly.

================================================================================
  GUIDELINE: In App Router, start with Server Components.
  Only add 'use client' + CSR when you genuinely need browser APIs or
  real-time user-specific data that can't live on the server.
