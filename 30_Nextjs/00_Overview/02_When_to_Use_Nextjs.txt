  WHEN TO USE NEXT.JS — COMPLETE INTERVIEW PREPARATION GUIDE
================================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. DECISION FRAMEWORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ask these four questions to decide:

  1. Does SEO matter? (Search engine discoverability)
  2. Does performance matter? (Time to First Contentful Paint, LCP)
  3. Do you need a server-side backend?
  4. Is the content public or private/auth-gated?

  All "yes"  → Next.js is ideal
  All "no"   → Plain React SPA is fine
  Mixed      → Next.js (because it supports CSR too — no downside)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. USE NEXT.JS — STRONG CASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A) E-COMMERCE PLATFORMS
   Why Next.js?
   - Product pages need SEO (organic search traffic = revenue)
   - High traffic → performance critical (every 100ms matters)
   - Product inventory changes → ISR perfect (revalidate every 60s)
   - Cart/checkout → CSR or Server Actions
   - Flash sales → SSR for real-time pricing

   Rendering strategy:
   - /products (category pages)  → SSG + ISR
   - /products/[id]              → SSG (getStaticPaths) + ISR
   - /cart, /account             → CSR (client-side)
   - /checkout                   → SSR (real-time pricing/stock)

   Example: Shopify Hydrogen, Vercel Commerce template — all Next.js

B) CONTENT/BLOG/NEWS SITES
   Why Next.js?
   - Articles must rank on Google (SEO paramount)
   - Build thousands of pages from CMS at build time (SSG)
   - No database hit for every read (SSG served from CDN)
   - Breaking news → ISR (revalidate: 30 seconds)

   Rendering strategy:
   - Blog post pages    → SSG with ISR
   - Author pages       → SSG
   - Homepage (latest)  → SSR or ISR with short revalidation
   - Search page        → CSR or SSR

   Example: Next.js blog starters, Vercel documentation site

C) MARKETING / LANDING PAGES
   Why Next.js?
   - PageSpeed scores affect Google Ads Quality Score
   - Image optimization (WebP, AVIF) out-of-the-box
   - Font optimization (no layout shift)
   - Metadata API for Open Graph (social sharing)
   - SSG → instantaneous load from CDN

   Rendering strategy:
   - All pages → SSG (static HTML from build)

D) SAAS DASHBOARDS (HYBRID APPROACH)
   Why Next.js?
   - Public landing page needs SEO (SSG)
   - Auth-gated dashboard can be CSR
   - API routes serve as BFF (Backend for Frontend)
   - Single deployment, unified codebase

   Rendering strategy:
   - /              → SSG (landing)
   - /pricing       → SSG
   - /app/*         → CSR (auth-gated, SEO irrelevant)
   - /api/*         → API route handlers

E) FULL-STACK APPLICATIONS
   Why Next.js?
   - Replaces separate Express backend for moderate-complexity apps
   - API routes handle REST or tRPC
   - Server Actions handle form mutations
   - Database (Prisma, Drizzle) accessed directly in Server Components
   - One repo, one deployment, shared TypeScript types

F) MULTI-LANGUAGE / INTERNATIONAL SITES
   Why Next.js?
   - Built-in i18n routing (next.config.js locales config)
   - Per-locale static generation
   - locale detection and automatic redirection

G) REAL-TIME APPLICATIONS (WITH CAVEATS)
   Why Next.js?
   - WebSocket via API routes (or use a separate WS server)
   - Streaming responses (Server-Sent Events via App Router)
   - Real-time UI updates with Suspense + streaming

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. DON'T USE NEXT.JS — OR USE WITH CAUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A) PURE INTERNAL TOOLS (no SEO need)
   - Admin panels, internal BI dashboards, employee portals
   - Plain React SPA + Vite is simpler and faster to build
   - Next.js adds overhead with no benefit

B) EXISTING NON-NODE BACKEND
   - If you have a Rails, Django, or .NET backend, you don't need Next.js API
     routes; use plain React as the frontend instead
   - Unless you want SSR/SSG, which is still a valid reason to add Next.js

C) HEAVY REAL-TIME / WEBSOCKET APPS
   - Next.js is not designed to be a long-running WebSocket server
   - Use a dedicated real-time server (Socket.io, Ably, Pusher)
   - Next.js can still be the frontend, but WS needs a separate service

D) DESKTOP APPLICATIONS
   - For Electron/Tauri apps, plain React is typically preferred
   - SSR has no benefit for desktop

E) TINY STATIC SITES / MICRO-SITES
   - For a simple 1–3 page site, Astro or plain HTML might be more appropriate
   - Although Next.js output: 'export' mode handles this, it's overkill

6. PERFORMANCE TRADE-OFFS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SSG:
  Pros: Fastest possible (CDN, no compute), cheapest hosting
  Cons: Stale data until rebuild, can't serve user-specific content

ISR:
  Pros: SSG performance + ability to update content
  Cons: First request after expiry triggers re-generation (stale-while-revalidate
        pattern), slight complexity

SSR:
  Pros: Always fresh data, user-specific content, dynamic responses
  Cons: Slower than SSG (compute on every request), server costs, TTFB varies

CSR:
  Pros: Rich interactivity, no server needed, great for auth-gated pages
  Cons: Bad SEO, slow initial load (blank page + JS download)

Server Components (App Router):
  Pros: Zero client JS, direct DB access, great for static-ish data on server
  Cons: No hooks/state/browser APIs, mental model shift

7. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: When would you choose SSG over SSR?
A:  SSG when content doesn't change per-request and SEO matters (blog posts,
    documentation, marketing pages). SSR when data must be fresh on every
    request (user dashboards, search results, real-time pricing).

Q2: How do you handle a page that is mostly static but has one dynamic section?
A:  Two approaches:
    (1) SSG the page shell, use CSR (useEffect/SWR) for the dynamic section.
    (2) App Router: SSG the layout + Server Component, wrap dynamic part in
        <Suspense> with a dynamic Server Component (streaming).
    Partial Prerendering (PPR, Next.js 14+) automates this pattern.

Q3: Our blog has 100,000 posts. Can we use SSG?
A:  Yes, with getStaticPaths + fallback: 'blocking' or ISR. Build only
    popular/recent posts at build time, generate others on-demand (fallback).
    Set revalidate to update stale posts. In App Router, use
    generateStaticParams() + dynamicParams = true + revalidate.

Q4: When would you NOT recommend Next.js?
A:  (1) Purely internal tool behind auth — React SPA is simpler.
    (2) Existing mature non-Node backend (Rails/Django) where you just need
        a frontend — keep them separate.
    (3) Highly specialized real-time apps (games, collaborative editors) —
        the SSR overhead adds complexity without benefit.

Q5: A client says their product pages load in 4 seconds. They're using React
    (CRA). What would you recommend?
A:  Migrate to Next.js and use SSG/ISR for product pages.
    - Product pages are SEO-critical
    - SSG serves pre-built HTML from CDN → sub-second loads
    - next/image for product images (WebP, lazy load, no layout shift)
    - Add ISR for inventory/price updates (revalidate: 60)
    Expected improvement: 4s → ~0.3s TTFCP

  KEY TAKEAWAY: The decision is about rendering strategy, not just the
  framework. Use Next.js when you need SSR/SSG/ISR/RSC. The framework
  itself adds minimal overhead — it's the rendering strategy that matters.
