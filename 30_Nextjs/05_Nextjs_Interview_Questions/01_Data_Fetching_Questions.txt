SECTION 1: RENDERING STRATEGY FUNDAMENTALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the four data fetching/rendering strategies in Next.js?
A: 1. SSG (Static Site Generation): HTML pre-rendered at BUILD TIME. Fastest,
      served from CDN. No per-request data. getStaticProps (Pages) / async component
      with force-cache fetch (App).
   2. SSR (Server-Side Rendering): HTML rendered on EACH REQUEST. Always fresh,
      personalized data. getServerSideProps (Pages) / async component with
      cache:'no-store' fetch (App).
   3. ISR (Incremental Static Regeneration): Starts static, regenerates in the
      background after N seconds. Best of SSG and SSR. revalidate option.
   4. CSR (Client-Side Rendering): Data fetched in the browser after initial HTML.
      useEffect, SWR, React Query. For user-specific, real-time, interactive data.

Q: When would you choose each rendering strategy?
A: SSG: Marketing pages, documentation, blogs (rarely updated).
   SSR: User dashboards, search results, auth-protected pages, real-time prices.
   ISR: E-commerce products, news articles, frequently-but-not-constantly updated.
   CSR: User-specific settings, real-time feeds, infinite scroll, live charts.

Q: What is stale-while-revalidate and how does ISR implement it?
A: SWR is a cache strategy: serve the cached (possibly stale) response immediately,
   then revalidate in the background. The NEXT request gets the fresh data.
   ISR implements this: page is cached as static. When revalidate period expires,
   the NEXT request still gets the cached version while the server quietly
   regenerates a fresh version. The request AFTER that gets the new version.

SECTION 2: getServerSideProps AND getStaticProps (PAGES ROUTER)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What does getServerSideProps receive and what can it return?
A: Receives context: { params, query, req, res, cookies, locale, preview, previewData }.
   Returns one of:
   - { props: { ... } } — renders the page with these props
   - { redirect: { destination, permanent } } — redirect response
   - { notFound: true } — renders 404 page
   You can set cache headers via res.setHeader('Cache-Control', 'stale-while-revalidate=60').

Q: What is the difference between getStaticPaths fallback options?
A: false: only pre-generated paths work; others return 404 immediately.
   true: ungenerated paths show a fallback state (router.isFallback is true),
         then the page generates and becomes cached.
   'blocking': ungenerated paths wait for server generation (no fallback UI),
               then cached like SSG.
   App Router equivalent: dynamicParams = true (blocking behavior) / false (404).

Q: Can getServerSideProps and getStaticProps both be in the same file?
A: No. A page can only use one data fetching method. Using both would create
   conflicting rendering strategies. For a page that needs both static structure
   and server data, use SSR (getServerSideProps) or ISR (getStaticProps with revalidate).

Q: What is the difference between getStaticProps revalidate: 60 and cache-control max-age=60?
A: revalidate: 60 is ISR — Next.js regenerates the page on the server after 60s.
   The browser always gets fresh HTML from Next.js (no browser cache).
   Cache-Control max-age=60 is an HTTP cache — the browser/CDN caches the response
   for 60 seconds and won't even make a new request. They operate at different layers
   and can be combined.

SECTION 3: APP ROUTER DATA FETCHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you implement SSG, SSR, and ISR in the App Router?
A: SSG: fetch(url, { cache: 'force-cache' }) or export const dynamic = 'force-static'
   SSR: fetch(url, { cache: 'no-store' }) or export const dynamic = 'force-dynamic'
         or use cookies()/headers() which make the route dynamic automatically
   ISR: fetch(url, { next: { revalidate: 3600 } }) or export const revalidate = 3600

Q: What is the default fetch behavior in Next.js 15 vs 14?
A: Next.js 14: fetch() defaults to force-cache (static by default).
   Next.js 15: fetch() defaults to no-store (dynamic by default).
   In v15 you must explicitly opt into caching.

Q: How do you prevent duplicate database calls when multiple components need the same data?
A: Use React.cache() to memoize non-fetch calls:
   export const getUser = cache(async (id: string) => prisma.user.findUnique(...));
   Both layout.tsx and page.tsx can call getUser(id) — only one DB query happens.
   For fetch() calls, Next.js automatically deduplicates identical URL+options.

Q: What is the App Router equivalent of getStaticPaths?
A: generateStaticParams. It returns an array of param objects.
   The key differences: (1) no need for paths wrapper (flat array of params objects),
   (2) no fallback property (use dynamicParams export instead),
   (3) can call server-only code directly (no need for fetch API).

Q: How do on-demand revalidation (revalidatePath / revalidateTag) work?
A: revalidatePath('/posts') marks the cached output for /posts as stale.
   The next request triggers a fresh render.
   revalidateTag('posts') invalidates all fetch() calls tagged with 'posts'.
   Both can be called from Server Actions or Route Handlers.
   Call from a CMS webhook to purge specific content immediately after changes.

SECTION 4: CLIENT-SIDE FETCHING (SWR AND REACT QUERY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is SWR and when should you use it vs useEffect?
A: SWR (stale-while-revalidate) is a data fetching hook library by Vercel.
   Benefits over useEffect: automatic deduplication (same key = single fetch),
   focus revalidation (refetch when tab gains focus), retry on error, cache
   management, loading/error states. Use SWR for repeated data fetching patterns.
   Use useEffect only for one-time or side-effect-based fetching.

Q: What is the SWR key and why does it matter?
A: The key is SWR's cache identifier. Same key = same cached value (deduplication).
   Null or false key: disables fetching (conditional fetch).
   Array key: useSWR(['/api/user', userId], ...) — useful for params.
   Function key: automatically skips if throws (replaces conditional fetch).
   Changing the key triggers a new fetch.

Q: What is the difference between SWR's local mutate and global mutate?
A: Local mutate: from the useSWR hook's mutate function — only updates that
   specific cache key in the current component's context.
   Global mutate: import { mutate } from 'swr' — can update any cache key
   from anywhere. Use global mutate to update related data after a write operation.

Q: What is the difference between staleTime and gcTime in React Query?
A: staleTime: How long data is "fresh" — won't refetch during this period even
   on component remount. Default: 0ms (always stale, always refetch).
   gcTime (was cacheTime): How long unused/inactive data stays in memory before
   garbage collected. Default: 5 minutes.
   Rule of thumb: staleTime ≤ gcTime. Set staleTime: 60000 for data that doesn't
   change often to prevent unnecessary refetches.

Q: How do you pre-populate React Query with server-fetched data?
A: Use HydrationBoundary + dehydrate. In the Server Component:
   const queryClient = new QueryClient();
   await queryClient.prefetchQuery({ queryKey: ['posts'], queryFn: getPosts });
   return (
     <HydrationBoundary state={dehydrate(queryClient)}>
       <PostsList />
     </HydrationBoundary>
   );
   The client starts with pre-populated cache — no loading flash.

SECTION 5: ADVANCED DATA FETCHING PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you fetch data in parallel in Server Components?
A: Use Promise.all() to fire all requests simultaneously:
   const [user, posts, stats] = await Promise.all([
     getUser(id),
     getUserPosts(id),
     getUserStats(id),
   ]);
   Without Promise.all, fetches are sequential (waterfall) — much slower.

Q: What is a hydration mismatch and how do you fix it?
A: A hydration mismatch occurs when server-rendered HTML differs from what React
   produces on the client. Common causes: Date.now(), Math.random(), localStorage,
   window-based values. Fix: use useEffect to set client-only values after hydration,
   or use a mounted state flag: const [mounted, setMounted] = useState(false);
   useEffect(() => setMounted(true), []); — render fallback until mounted is true.

Q: When should you NOT use a Server Component for data fetching?
A: When data is: (1) user-specific and changes on interaction (cart counts, like states),
   (2) real-time or requires websockets, (3) dependent on client state (user's filters,
   form values), (4) needs optimistic updates (update UI before server confirms).
   For these, use SWR/React Query in Client Components.

Q: How do you handle loading and error states for streaming data?
A: Use Suspense boundaries (loading.tsx or manual <Suspense fallback={...}>)
   for per-component loading states. Use error.tsx for error boundaries at
   route level. Nest Suspense boundaries to stream independent components
   as they resolve without blocking each other.
