SECTION 1: REACT SERVER COMPONENTS (RSC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are React Server Components (RSC)?
A: RSC are React components that render ONLY on the server. Their code is never
   sent to the client JavaScript bundle. They can be async functions, access
   databases directly, read secrets, use the file system. In Next.js App Router,
   all components are RSC by default.

Q: What is the "RSC Payload"?
A: When React renders Server Components, it produces a JSON-like wire format called
   the RSC Payload instead of raw HTML. It encodes: the rendered output of server
   components, placeholders for Client Components (with their props), references to
   client-side JS modules to hydrate. On the first load it's used to produce HTML.
   On navigation, only the RSC payload is fetched — React merges it into the current UI.

Q: What are the rules for what RSC can and cannot do?
A: CAN: be async functions, await data, access DB/FS/secrets, import server-only
   packages, call other RSC or Client Components.
   CANNOT: useState, useReducer, useEffect, useContext, event handlers (onClick),
   browser APIs (window, document, localStorage), hooks that require client runtime.

Q: Can a Client Component import a Server Component?
A: No. Importing a Server Component into a Client Component would bundle all server
   code for the browser. The solution is the "children pattern": the Server Component
   is rendered by a Server parent and passed as children to the Client Component.
   The Client Component receives already-rendered RSC output as children — not
   the Server Component source code.

Q: What must be true about props passed from Server to Client Components?
A: Props must be serializable — able to be transmitted as JSON in the RSC payload.
   Primitive types (string, number, boolean), plain objects, arrays are fine.
   Functions, class instances, non-serializable objects are NOT. Dates must be
   serialized: date.toISOString(). The restriction exists because RSC output is
   serialized and sent over the network.

SECTION 2: CLIENT COMPONENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Does 'use client' mean the component only runs in the browser?
A: No — common misconception. 'use client' marks a "client boundary."
   The component still SSR-renders on the server for initial HTML, then
   hydrates in the browser to become interactive. 'use client' tells Next.js
   to include this component's code in the client JavaScript bundle.

Q: How does 'use client' propagate through imports?
A: When a file is marked 'use client', ALL files it imports become client code
   too. This means: if you import a server-only library in a Client Component,
   that library ships to the browser. Keep Client Components focused. Push 'use client'
   as far DOWN the component tree as possible to minimize client bundle size.

Q: What is the correct pattern for React Context providers in the App Router?
A: Create a Client Component provider file ('use client'). Wrap children in the
   root layout (Server Component). Since children is passed as RSC payload (not
   imported), Server Components can still be children of the provider:
   // layout.tsx (Server) → <ThemeProvider>{children}</ThemeProvider>
   // ThemeProvider ('use client') → manages theme state with useState

Q: How do you wrap a third-party library that uses hooks?
A: Create a wrapper file with 'use client' that imports and re-exports the library.
   This confines the client boundary to the wrapper, not your Server Component:
   // components/date-picker-wrapper.tsx
   'use client';
   export { DatePicker } from 'some-date-library';
   // Now import from the wrapper in Server Components

SECTION 3: STREAMING AND SUSPENSE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does streaming work in Next.js?
A: HTTP chunked transfer encoding sends HTML to the browser in pieces.
   Suspense boundaries delineate streaming points. The server sends the
   page shell + Suspense fallbacks immediately. As async data resolves,
   the actual content chunks are streamed and the browser swaps in the real content.
   Result: faster Time to First Byte — users see content progressively.

Q: What is the relationship between loading.tsx and Suspense?
A: loading.tsx is syntactic sugar for a Suspense boundary. Next.js automatically
   wraps page.tsx in <Suspense fallback={<Loading />}> when loading.tsx exists
   in the same directory. For finer control, use manual <Suspense> around
   individual slow components.

Q: What is Partial Pre-Rendering (PPR)?
A: Experimental Next.js 15 feature combining static and dynamic in one response.
   The static shell (outside Suspense boundaries) is pre-rendered at build time
   and served from CDN instantly. Dynamic parts (inside Suspense) stream in at
   request time. Best of both worlds: CDN-speed first paint + fresh dynamic data.

Q: What is React 19's use() hook and how is it used with Server Components?
A: use() reads Promises and Context in Client Components (unlike await which
   only works in Server Components or async functions). Pattern: Server Component
   creates a promise (without await) and passes it to a Client Component.
   The Client Component calls use(promise) to read it — this "suspends" the
   component until the promise resolves, triggering the nearest Suspense fallback.

SECTION 4: SERVER ACTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are Server Actions and what problem do they solve?
A: Server Actions are async server-only functions callable directly from the UI
   (form actions or event handlers). They eliminate the need to write explicit API
   routes for mutations. Also enable progressive enhancement — forms work without JS.

Q: How do you handle form validation errors in Server Actions?
A: Use useActionState (React 19) / useFormState (React 18). The Server Action
   receives prevState as first argument and returns an error state object.
   Use Zod.safeParse to validate and return field errors. The hook provides
   [state, formAction] — state contains the returned errors for display.

Q: How do you show loading state during a Server Action?
A: Two options: (1) useFormStatus from react-dom — in a child of the form,
   gives { pending } to disable submit buttons. (2) useTransition — wrap the
   call in startTransition(), get isPending boolean.

Q: Why must you re-throw redirect() errors in Server Actions?
A: redirect() from 'next/navigation' internally throws a NEXT_REDIRECT error.
   If you catch it in a try/catch block without re-throwing, the redirect is
   silently swallowed. Use isRedirectError() to detect and re-throw it:
   } catch (err) {
     if (isRedirectError(err)) throw err;
     return { message: 'Error' };
   }

Q: How do Server Actions compare to Route Handlers?
A: Server Actions: for mutations from your own UI, native form integration,
   progressive enhancement, end-to-end type safety, no URL needed.
   Route Handlers: for public APIs, webhooks, mobile clients, external services.
   Prefer Server Actions for internal mutations; Route Handlers for external API.

SECTION 5: ROUTE HANDLERS AND PAGES vs APP ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between Route Handlers (App Router) and API Routes (Pages Router)?
A: Route Handlers use Web Standard APIs (Request, Response, Headers) — works in
   any JS runtime. API Routes use Node.js NextApiRequest/NextApiResponse.
   Route Handlers: named exports per method (GET, POST, PUT), support Edge runtime,
   built-in caching config. API Routes: single default export with if/else method check.

Q: How do you read the raw request body in a Route Handler?
A: await request.text() returns the raw string. Use this for webhook signature
   verification (Stripe, GitHub, etc.) where re-serializing the body would change
   it and break signature checks. Never use request.json() for webhooks.

Q: What is the main architectural advantage of App Router over Pages Router?
A: React Server Components by default — components render on the server with
   zero client bundle impact, can access DB directly, use server secrets. Plus:
   nested file-based layouts, streaming/Suspense, Server Actions, parallel routes,
   intercepted routes — all unavailable in Pages Router.

Q: How do Pages Router and App Router coexist in the same project?
A: Both app/ and pages/ can exist simultaneously. Next.js routes requests to
   the appropriate router. app/ takes priority for conflicting paths. This enables
   incremental migration — move routes one by one from pages/ to app/.

Q: What is the migration path from getServerSideProps to App Router?
A: Replace getServerSideProps + page component with an async Server Component
   that awaits data directly in the component body. No more separate data
   function — the component IS the data fetcher. Pass the data to child
   components as props. Use notFound() instead of { notFound: true }.
   Use redirect() from 'next/navigation' instead of { redirect: {...} }.

================================================================================
  MENTAL MODEL SUMMARY:
  RSC = server-only, no JS bundle, async capable
  Client Component = 'use client', SSR+hydrate, browser APIs/hooks
  Server Actions = server functions callable from UI
  Route Handlers = public HTTP endpoints (for external consumers)
  Streaming = progressive HTML delivery via Suspense boundaries
