1. OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js supports two router architectures:
  Pages Router — introduced in Next.js v1, stable, widely used
  App Router   — introduced in Next.js 13, stable from Next.js 14

They can COEXIST in the same project during migration.
Both compile separately and can be used side-by-side.

2. COMPREHENSIVE COMPARISON TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Aspect                    | Pages Router             | App Router
  ─────────────────────────  | ───────────────────────  | ───────────────────────
  Root directory             | pages/                   | app/
  Component default          | Client Component         | Server Component
  Layout system              | _app.tsx + getLayout     | layout.tsx (nested)
  Custom HTML                | _document.tsx            | root layout.tsx
  Rendering in components    | No async components      | async Server Components
  Data fetching (page level) | getServerSideProps,      | fetch() inside component
                             | getStaticProps,          | or server library call
                             | getStaticPaths           |
  Data fetching (client)     | useEffect / SWR          | useSWR / useQuery
  Incremental static regen.  | revalidate in gSP        | export revalidate = N
  API endpoints              | pages/api/*.ts           | app/api/*/route.ts
  Middleware                 | middleware.ts (both)     | middleware.ts (both)
  Streaming                  | ✗ Not supported          | ✓ via Suspense
  Server Actions             | ✗                        | ✓
  React Server Components    | ✗                        | ✓ (default)
  Nested layouts             | Manual in _app.tsx       | ✓ Native file-based
  Loading states             | ✗ (manual)               | loading.tsx
  Error boundaries           | ✗ (manual)               | error.tsx
  Route groups               | ✗                        | (group) folders
  Parallel routes            | ✗                        | @slot convention
  Intercepted routes         | ✗                        | (.) (..) (...) 
  Metadata/SEO               | next/head                | generateMetadata()
  Font optimization          | next/font (both)         | next/font (both)
  Image optimization         | next/image (both)        | next/image (both)
  i18n routing               | Built-in (next.config)   | Manual or next-intl
  TypeScript support         | ✓                        | ✓ (better inference)
  Stability                  | Mature, battle-tested    | Stable from Next.js 14

  PAGES ROUTER:
    pages/
      index.tsx             → /
      about.tsx             → /about
      blog/
        index.tsx           → /blog
        [slug].tsx          → /blog/:slug

  APP ROUTER:
    app/
      page.tsx              → /
      about/
        page.tsx            → /about
      blog/
        page.tsx            → /blog
        [slug]/
          page.tsx          → /blog/:slug
        [...slug]/
          page.tsx          → /blog/* (catch-all)
      api/
        posts/
          route.ts          → /api/posts

4. DATA FETCHING COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  PAGES ROUTER — SSR:
    export default function ProductPage({ product }) {
      return <div>{product.name}</div>;
    }

    export async function getServerSideProps(context) {
      const product = await getProduct(context.params.id);
      if (!product) return { notFound: true };
      return { props: { product } };
    }

  APP ROUTER — SSR equivalent:
    export default async function ProductPage({ params }) {
      const { id } = await params;
      const product = await getProduct(id);
      if (!product) notFound();
      return <div>{product.name}</div>;
    }
    // async component IS the getServerSideProps — much simpler!

  ─────────────────────────────────────────────────────────────────────

  PAGES ROUTER — SSG:
    export async function getStaticProps({ params }) {
      const post = await getPost(params.slug);
      return { props: { post }, revalidate: 3600 };
    }

    export async function getStaticPaths() {
      const posts = await getPosts();
      return {
        paths: posts.map(p => ({ params: { slug: p.slug } })),
        fallback: 'blocking',
      };
    }

  APP ROUTER — SSG equivalent:
    export const revalidate = 3600;

    export async function generateStaticParams() {
      const posts = await getPosts();
      return posts.map(p => ({ slug: p.slug }));
    }

    export default async function PostPage({ params }) {
      const { slug } = await params;
      const post = await getPost(slug);
      return <PostContent post={post} />;
    }

5. LAYOUT COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  PAGES ROUTER — Single _app.tsx:
    // pages/_app.tsx
    function MyApp({ Component, pageProps }) {
      const getLayout = Component.getLayout ?? (page => page);
      return (
        <SessionProvider session={pageProps.session}>
          {getLayout(<Component {...pageProps} />)}
        </SessionProvider>
      );
    }

    // Per-page layout:
    BlogPage.getLayout = (page) => (
      <BlogLayout>{page}</BlogLayout>
    );

  APP ROUTER — Nested layouts:
    // app/layout.tsx (root)
    export default function RootLayout({ children }) {
      return (
        <html><body>
          <SessionProvider>
            <Navbar />
            {children}
          </SessionProvider>
        </body></html>
      );
    }

    // app/blog/layout.tsx (auto-applied to /blog/**)
    export default function BlogLayout({ children }) {
      return (
        <div>
          <BlogSidebar />
          <main>{children}</main>
        </div>
      );
    }

6. METADATA / SEO COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  PAGES ROUTER:
    import Head from 'next/head';
    export default function Page({ post }) {
      return (
        <>
          <Head>
            <title>{post.title}</title>
            <meta name="description" content={post.excerpt} />
            <meta property="og:title" content={post.title} />
          </Head>
          <article>{post.content}</article>
        </>
      );
    }

  APP ROUTER:
    export async function generateMetadata({ params }) {
      const { id } = await params;
      const post = await getPost(id);
      return {
        title: post.title,
        description: post.excerpt,
        openGraph: { title: post.title, description: post.excerpt },
      };
    }

    export default async function Page({ params }) {
      const { id } = await params;
      const post = await getPost(id);
      return <article>{post.content}</article>;
    }

7. COEXISTENCE (GRADUAL MIGRATION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Both routers can exist in the same project:

  my-app/
    app/                    ← App Router handles these routes
      dashboard/
        page.tsx
      layout.tsx
    pages/                  ← Pages Router handles these routes
      api/
        legacy-endpoint.ts
      old-page.tsx

Conflict resolution:
  - app/ routes take priority over pages/ for the SAME path
  - pages/_app.tsx, pages/_document.tsx still apply to Pages Router routes
  - Middleware works for both
  - Recommendation: migrate page by page, keep critical pages on Pages Router
    until App Router equivalents are tested and stable

8. MIGRATION STRATEGY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Recommended migration steps:
  1. Create app/ directory (coexistence enabled automatically)
  2. Migrate app-level setup:
     - pages/_app.tsx → app/layout.tsx
     - pages/_document.tsx → root layout <html>, <body>
     - Global CSS → app/layout.tsx imports
     - Context providers → Client Component providers in layout
  3. Migrate routes one by one (low-traffic pages first)
  4. Convert getStaticProps → async component + generateStaticParams
  5. Convert getServerSideProps → async component
  6. Convert getStaticPaths → generateStaticParams
  7. Migrate API routes to route.ts handlers (when ready)
  8. Server Actions for forms (can co-exist with API routes)
  9. Remove pages/ directory when all routes migrated

Things to watch for during migration:
  ✗ next/head → use generateMetadata or Metadata export
  ✗ useRouter from next/router → useRouter/usePathname/useSearchParams from next/navigation
  ✗ getServerSideProps props serialization → no longer needed
  ✗ _document.tsx Head → move to root layout
  ✗ Third-party providers needing 'use client' wrapper

9. WHEN TO USE EACH ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Use Pages Router if:
    - Existing project on Pages Router (migration risk not worth it)
    - Team is unfamiliar with RSC concepts
    - Heavy reliance on i18n built-in routing
    - Libraries not yet RSC-compatible
    - Stability is critical and RSC learning curve is a concern

  Use App Router if:
    - New project (always)
    - Need streaming / Suspense
    - Want Server Components for reduced JS bundle
    - Need Server Actions for form handling
    - Complex nested layouts
    - Want parallel routes or intercepted routes

10. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the main architectural difference between Pages and App Router?
A:  The App Router is React Server Components by default — components render on
    the server with zero JS bundle impact. Pages Router uses Client Components
    (classic React) by default. App Router has nested file-based layouts,
    Suspense/streaming, Server Actions, and async components. Pages Router uses
    getServerSideProps/getStaticProps lifecycle methods and _app.tsx for shared layout.

Q2: Can Pages Router and App Router coexist in the same project?
A:  Yes. Create an app/ directory alongside pages/. Next.js routes requests to
    the appropriate router based on directory. app/ routes take priority for
    conflicting paths. This enables incremental migration without a big-bang rewrite.

Q3: What replaces getServerSideProps in the App Router?
A:  Making the page component an async function and awaiting data directly in
    the component body. No props passing needed — the component fetches its
    own data. This is because the component runs on the server.

Q4: How does getStaticPaths translate to the App Router?
A:  getStaticPaths → generateStaticParams. Both return arrays of params to
    pre-render at build time. The fallback option in getStaticPaths maps to
    export const dynamicParams = true/false in App Router (default true = fallback:'blocking').

Q5: What replaces next/head in the App Router?
A:  The generateMetadata async function (for dynamic metadata) or a static
    metadata export. It's more powerful: supports full type-safety, OpenGraph,
    Twitter cards, robots, canonical URLs, and more — all with TypeScript support.

Q6: What happened to useRouter from next/router in the App Router?
A:  Different hooks serve different purposes now (all from 'next/navigation'):
    - useRouter()      → programmatic navigation (push, replace, back)
    - usePathname()    → current URL path
    - useSearchParams() → URL query parameters
    - useParams()      → dynamic route segments
    The old useRouter.query split into useParams + useSearchParams.

================================================================================
  KEY INSIGHT: App Router is the future. Pages Router is stable but not
  receiving new features. New projects should always use App Router.
  For existing projects, incrementally migrate route by route.
================================================================================
