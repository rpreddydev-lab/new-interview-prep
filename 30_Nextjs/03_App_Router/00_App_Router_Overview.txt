1. WHAT IS THE APP ROUTER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Introduced in Next.js 13 (May 2023) and stabilized in Next.js 13.4, the App
Router is a fundamentally new routing architecture that is built on top of
React Server Components (RSC). It exists alongside the Pages Router and both
can coexist in the same project.

The App Router represents the future of Next.js development. It makes full use
of the latest React features: Server Components, Suspense, Streaming, and Server
Actions.

Core directory: app/  (vs pages/ for the Pages Router)

2. CORE CONCEPTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

a) REACT SERVER COMPONENTS (RSC) — DEFAULT
   All components inside app/ are Server Components by default.
   They render on the server, zero JavaScript sent to client.
   Can be async (await data directly).
   No useState, useEffect, event handlers, or browser APIs.

b) CLIENT COMPONENTS — OPT-IN
   Add 'use client' directive at the top of the file.
   Same as traditional React components (hooks, events, browser APIs).
   Still benefit from SSR — rendered on server first, hydrated on client.

c) NESTED LAYOUTS
   Each route segment can have layout.tsx — persists across navigation.
   Layouts compose hierarchically.

d) STREAMING & SUSPENSE
   Pages stream progressively (initial HTML fast; dynamic parts stream in).
   loading.tsx automatically wraps page.tsx in <Suspense>.

e) SERVER ACTIONS
   Functions marked 'use server' that run on the server.
   Called directly from Client Components (no API endpoint needed).
   Handle form submissions, mutations.

f) ROUTE HANDLERS (API ROUTES)
   app/*/route.ts — Web standard Request/Response API.
   Named exports per HTTP method: GET, POST, PUT, DELETE.

4. HOW THE APP ROUTER RENDERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

First Request (SSR + Streaming):
  1. User requests /dashboard
  2. Server renders layout.tsx (Server Component) → HTML
  3. If loading.tsx exists, page.tsx is wrapped in Suspense
  4. Suspense boundary → server starts streaming response
  5. Loading skeleton HTML arrives at browser immediately
  6. In parallel: page.tsx async data fetching runs on server
  7. Once page data ready, HTML streams in to replace skeleton
  8. Client hydrates (React takes over with Client Components)
  9. Client-side React only hydrates Client Components

Subsequent Navigations (RSC Payload):
  1. User clicks Link to /about
  2. Next.js fetches RSC payload (JSON, not HTML) for /about
  3. No full page reload — React updates the DOM diff
  4. URL changes via browser History API
  5. Persistent layouts not re-mounted (only page.tsx changes)

5. ROUTE SEGMENT CONFIGURATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Export constants from page.tsx, layout.tsx, or route.ts to control behavior:

  // Rendering behavior
  export const dynamic = 'auto';          // default: infer from code
  export const dynamic = 'force-dynamic'; // always SSR (no caching)
  export const dynamic = 'force-static';  // always SSG (error if using headers/cookies)
  export const dynamic = 'error';         // error if dynamic code is detected

  // Caching / ISR
  export const revalidate = 0;            // no cache (SSR)
  export const revalidate = 60;           // ISR: revalidate every 60 seconds
  export const revalidate = false;        // cache forever (SSG)

  // Runtime
  export const runtime = 'nodejs';       // default
  export const runtime = 'edge';         // Edge Runtime (limited APIs)

  // Dynamic params handling
  export const dynamicParams = true;     // default: generate unknown params on demand
  export const dynamicParams = false;    // 404 for unknown params

  // Max segment duration (for Vercel Lambda timeout)
  export const maxDuration = 30;         // seconds

6. DATA FETCHING IN APP ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Fetch data directly in Server Components — no getServerSideProps needed
  export default async function ProductPage({ params }) {
    // Parallel fetching (no waterfall)
    const [product, reviews, related] = await Promise.all([
      getProduct(params.id),
      getReviews(params.id),
      getRelatedProducts(params.id),
    ]);

    return (
      <main>
        <ProductDetails product={product} />
        <Suspense fallback={<ReviewsSkeleton />}>
          <Reviews reviews={reviews} />  {/* Could also be async RSC */}
        </Suspense>
        <RelatedProducts products={related} />
      </main>
    );
  }

Caching behavior:
  // Cached (default) — SSG-like
  const data = await fetch('https://api.example.com/data');

  // ISR - revalidate every 60s
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 },
  });

  // No cache — SSR
  const data = await fetch('https://api.example.com/data', {
    cache: 'no-store',
  });

  // Cache with tags (for on-demand revalidation)
  const data = await fetch('https://api.example.com/products', {
    next: { tags: ['products'] },
  });

7. COEXISTENCE WITH PAGES ROUTER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - app/ and pages/ can coexist in the same project
  - URL conflicts: app/ takes priority over pages/ for the same path
  - Useful for incremental migration (migrate one route at a time)
  - Shared components between app/ and pages/ must be 'use client' or
    pure server logic (no RSC-only features)

Migration strategy:
  1. Start with pages/ router
  2. Add app/ directory to project
  3. Migrate routes one by one (start with simple static pages)
  4. Eventually remove pages/ when all routes migrated

8. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the App Router in Next.js and why was it introduced?
A:  The App Router (Next.js 13+) is a new routing architecture based on React
    Server Components. It was introduced to allow: (1) components that render
    entirely on the server with zero client JS, (2) streaming/Suspense for
    progressive rendering, (3) nested layouts with persistent state, (4) Server
    Actions for mutations, (5) async data fetching directly in components.

Q2: What is the biggest behavioral difference between App Router and Pages Router?
A:  In Pages Router, all components are client-side by default. In App Router,
    all components in app/ are Server Components by default (zero client JS).
    You opt into client behavior with 'use client'. This inverts the mental model
    — you add interactivity only where needed, minimizing JavaScript bundle size.

Q3: Can you use the App Router and Pages Router together?
A:  Yes. They can coexist in the same Next.js project. This enables incremental
    migration. app/ takes priority when both have the same route. Shared
    components need to be compatible with both (Client Components or plain
    server code).

Q4: What is route segment configuration and what can you control with it?
A:  Exporting constants like dynamic, revalidate, runtime from page/layout files
    controls rendering behavior: dynamic = 'force-dynamic' → SSR; revalidate = 60
    → ISR; runtime = 'edge' → Edge Runtime; dynamicParams = false → 404 for
    unknown params. These replace the functionality of getServerSideProps and
    getStaticProps config objects.

Q5: How does navigation work differently in App Router vs Pages Router?
A:  Pages Router: every navigation triggers a new request to the server
    (HTML returned). App Router: subsequent navigations fetch the RSC payload
    (compact JSON) for only the changed segments. Persistent layouts don't
    re-fetch or re-mount. The result is much faster client-side navigation.
