GENERICS BEST PRACTICES AND PITFALLS
======================================

BEST PRACTICE 1: PREFER GENERICS OVER OBJECT
----------------------------------------------
  ❌ BAD: Using Object — loses type safety, requires casts
    public class Pair {
        Object first, second;
        public Object getFirst() { return first; }
    }
    String s = (String) pair.getFirst(); // unchecked cast, can fail at runtime

  ✅ GOOD: Use generics
    public class Pair<A, B> {
        A first; B second;
        public A getFirst() { return first; }
    }
    String s = pair.getFirst(); // compile-time safety, no cast

BEST PRACTICE 2: USE BOUNDED WILDCARDS FOR FLEXIBILITY
--------------------------------------------------------
  ❌ TOO RESTRICTIVE: only accepts exact type
    public double sum(List<Number> list) { ... }
    // Cannot pass List<Integer> or List<Double>!

  ✅ FLEXIBLE: accepts Number and all subtypes
    public double sum(List<? extends Number> list) { ... }
    sum(List.of(1, 2, 3));    // ✅ List<Integer>
    sum(List.of(1.5, 2.5));   // ✅ List<Double>

BEST PRACTICE 3: FOLLOW PECS
------------------------------
  Producer (reading):  use ? extends T
  Consumer (writing):  use ? super T
  Both read and write: use exact type T

  // Right way (Collections.copy):
  public static <T> void copy(List<? super T> dest, List<? extends T> src) {
      for (T item : src) dest.add(item); // reads from producer, writes to consumer
  }

BEST PRACTICE 4: PREFER GENERIC METHODS OVER UNCHECKED CASTS
--------------------------------------------------------------
  ❌ BAD: unchecked cast
    @SuppressWarnings("unchecked")
    public Object[] toArray(List<?> list) {
        return ((List<Object>) list).toArray();
    }

  ✅ BETTER: generic method
    public <T> T[] toArray(List<T> list, T[] arr) {
        return list.toArray(arr);
    }

BEST PRACTICE 5: DON'T USE RAW TYPES
--------------------------------------
  ❌ BAD: raw types lose all type checking
    List list = new ArrayList();
    list.add("hello"); list.add(42);
    String s = (String) list.get(1); // runtime ClassCastException

  ✅ GOOD: parameterized type
    List<String> list = new ArrayList<>();
    list.add("hello");
    // list.add(42);  // compile error — caught early

BEST PRACTICE 6: MINIMIZE SCOPE OF UNCHECKED SUPPRESSIONS
-----------------------------------------------------------
  When @SuppressWarnings("unchecked") is necessary, apply it to the smallest possible scope:

  ❌ BAD: suppress entire method
    @SuppressWarnings("unchecked")
    public <T> T readConfig(String key) {
        Object val = config.get(key);
        return (T) val;
    }

  ✅ GOOD: suppress only the specific cast
    public <T> T readConfig(String key) {
        Object val = config.get(key);
        @SuppressWarnings("unchecked")
        T result = (T) val;
        return result;
    }

COMMON PITFALL 1: GENERIC ARRAY CREATION
------------------------------------------
  ❌ Cannot create generic arrays directly:
    T[] arr = new T[10]; // compile error: generic array creation

  ✅ Workarounds:
    // Option A: cast (with warning)
    @SuppressWarnings("unchecked")
    T[] arr = (T[]) new Object[10];

    // Option B: use List<T> instead (preferred)
    List<T> list = new ArrayList<>(10);

    // Option C: require Class<T> token from caller (type-safe)
    public <T> T[] create(Class<T> type, int size) {
        return (T[]) java.lang.reflect.Array.newInstance(type, size);
    }

COMMON PITFALL 2: OVERLOADING WITH ERASURE COLLISION
------------------------------------------------------
  ❌ Two methods that erase to the same signature:
    void process(List<String> strings) { }
    void process(List<Integer> integers) { } // ❌ compile error: same erasure!
    // Both erase to: void process(List list)

  ✅ Workaround: use different method names
    void processStrings(List<String> strings) { }
    void processIntegers(List<Integer> integers) { }

COMMON PITFALL 3: STATIC FIELD WITH TYPE PARAMETER
----------------------------------------------------
  ❌ WRONG: generic classes cannot have static type-parameterized fields
    class Box<T> {
        static T defaultValue; // ❌ compile error: cannot make static reference to T
    }
    // Box<String>.defaultValue and Box<Integer>.defaultValue would share the same field!

  ✅ OK: static fields with specific types, or static generic METHODS
    class Box<T> {
        static Object defaultValue; // OK (raw Object)
        static <T> Box<T> empty() { return new Box<>(null); } // method's own T
    }

COMMON PITFALL 4: INSTANCEOF WITH PARAMETERIZED TYPES
------------------------------------------------------
  ❌ WRONG:
    if (obj instanceof List<String>) { }  // compile error — type erased

  ✅ CORRECT:
    if (obj instanceof List<?>)  { }      // wildcard OK
    if (obj instanceof List)     { }      // raw type OK (but unchecked)

    // Java 16+ pattern matching:
    if (obj instanceof List<?> list) { System.out.println(list.size()); }

COMMON PITFALL 5: GENERIC EXCEPTION CREATION
---------------------------------------------
  ❌ Cannot catch or throw parameterized exceptions:
    try { ... } catch (SomeException<String> e) { } // ❌ compile error

  ❌ Cannot throw type parameter:
    <E extends Exception> void throwIt() throws E { throw new E(); } // ❌

  ✅ CAN have type parameter in exception class:
    class DataException<T> extends RuntimeException {
        private T offendingValue;
        public T getOffendingValue() { return offendingValue; }
    }

COMMON PITFALL 6: MUTABLE TYPE PARAMETER IN HASHMAP
----------------------------------------------------
  ❌ Using mutable object as HashMap key — hashCode changes after mutation:
    Map<Point, String> map = new HashMap<>();
    Point p = new Point(1, 2);
    map.put(p, "origin");
    p.x = 10;                    // mutation!
    map.get(p);                  // null — p now in wrong bucket!

  ✅ Use immutable keys (String, Integer, record types, enums)

COMMON PITFALL 7: HEAP POLLUTION FROM VARARGS
----------------------------------------------
  @SafeVarargs marks a method as not causing heap pollution from generic varargs.
  Without it, callers get an "unchecked" warning.

  // ❌ UNSAFE: leaks the vararg array — causes heap pollution
  @SafeVarargs
  public static <T> List<T> combine(List<T>... lists) {
      List<T> result = new ArrayList<>();
      for (List<T> list : lists) result.addAll(list); // safe: read only
      return result;
  }

  // Safe usage: only read from varargs array, never store reference to it
  combine(List.of(1, 2), List.of(3, 4)); // safe

TYPE INFERENCE IMPROVEMENTS TIMELINE
--------------------------------------
  Java 5:   Generics introduced, limited inference
  Java 7:   Diamond operator <> — infer from context
  Java 8:   Lambda target-type inference improved
  Java 10:  var (local variable type inference)
  Java 11+: var in lambda parameters: (var s) -> s.length()

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is heap pollution and how does it happen?
A: Heap pollution occurs when a variable of a parameterized type holds an object that
   doesn't match the parameterization. It happens through: raw types (assigning List to
   List<String>), unchecked casts, or vararg arrays of generic types. Result: a
   ClassCastException thrown at an unexpected location, far from the actual mistake.

Q: What does @SafeVarargs do?
A: Suppresses the "unchecked or unsafe" warning when calling a method with a generic
   varargs parameter. It's a promise by the developer that the vararg array is not
   stored or exposed in ways that could cause heap pollution. Only use it when you're
   certain the method is safe — typically when you only read from the vararg array.

Q: Why can't you create a generic array (new T[])?
A: Because of type erasure — at runtime T is just Object (or the bound type).
   Java arrays carry type information at runtime (for ArrayStoreException checks).
   Creating new T[] would create an Object[] that masquerades as T[], which is
   unsafe. The compiler blocks it to prevent heap pollution.

Q: What is the overloading erasure collision?
A: When two method overloads have the same type erasure — e.g., process(List<String>)
   and process(List<Integer>) — they both erase to process(List). The JVM cannot
   distinguish them. The compiler rejects this as a compile error.
