COMPARABLE vs COMPARATOR WITH GENERICS
========================================

RECAP: THE TWO ORDERING INTERFACES
------------------------------------
  Comparable<T>    — natural ordering, implemented BY the class
  Comparator<T>    — custom ordering, EXTERNAL to the class

  Both are generic interfaces. Understanding how generics interact with them
  is critical for writing correct sorting and ordered data structure code.

COMPARABLE WITH GENERIC TYPE BOUNDS
-------------------------------------
  // Standard self-comparable pattern:
  public class Student implements Comparable<Student> {
      private String name;
      private double gpa;

      @Override
      public int compareTo(Student other) {
          return Double.compare(other.gpa, this.gpa); // descending by GPA
      }
  }

  // Generic method that needs Comparable elements:
  public static <T extends Comparable<T>> T findMin(List<T> list) {
      return list.stream().min(Comparator.naturalOrder()).orElseThrow();
  }

  // More flexible form (recommended):
  public static <T extends Comparable<? super T>> T findMin(List<T> list) {
      T min = list.get(0);
      for (T item : list) {
          if (item.compareTo(min) < 0) min = item;
      }
      return min;
  }

WHY <T extends Comparable<? super T>>?
----------------------------------------
  The standard form <T extends Comparable<T>> requires T to compare with its OWN exact type.
  The flexible form <T extends Comparable<? super T>> allows T's compareTo to be defined
  on a SUPERTYPE of T.

  Example:
    class Animal implements Comparable<Animal> {
        int weight;
        @Override public int compareTo(Animal other) { return Integer.compare(this.weight, other.weight); }
    }
    class Dog extends Animal { } // Dog inherits compareTo(Animal) — can compare with any Animal

    List<Dog> dogs = Arrays.asList(new Dog(10), new Dog(5), new Dog(8));

    // ❌ With <T extends Comparable<T>>: T=Dog must implement Comparable<Dog> — Dog doesn't!
    // ✅ With <T extends Comparable<? super T>>: T=Dog needs Comparable<? super Dog>
    //    Dog's supertype Animal implements Comparable<Animal> → ? super Dog includes Animal → OK

  Collections.sort and TreeSet use <T extends Comparable<? super T>> — always prefer this.

COMPARATOR WITH GENERICS AND CHAINING
---------------------------------------
  Comparator<T> is parameterized with the type to compare.
  Java 8+ static/default methods use wildcards for maximum flexibility.

  // Comparator.comparing — the bound uses Function<? super T, ? extends U>
  public static <T, U extends Comparable<? super U>>
      Comparator<T> comparing(Function<? super T, ? extends U> keyExtractor)

  // Why ? super T? The function can work on T or any supertype of T
  // Why ? extends U? The function can return U or any subtype of U (still Comparable)

  Example:
    class Employee {
        String name;
        int salary;
        String department;
    }

    // Single-key comparator
    Comparator<Employee> byName = Comparator.comparing(Employee::getName);
    Comparator<Employee> bySalary = Comparator.comparingInt(Employee::getSalary);

    // Chained comparator — multiple sort keys
    Comparator<Employee> byDeptThenSalary = Comparator
        .comparing(Employee::getDepartment)
        .thenComparingInt(Employee::getSalary)
        .thenComparing(Employee::getName);

    // Reverse order
    Comparator<Employee> bySalaryDesc = Comparator
        .comparingInt(Employee::getSalary)
        .reversed();

    // Null-safe comparator
    Comparator<Employee> nullSafe = Comparator.nullsFirst(byName); // nulls come first

NATURAL ORDER vs REVERSE ORDER
--------------------------------
  Comparator.naturalOrder()    — orders using Comparable (ascending)
  Comparator.reverseOrder()    — reverses natural order (descending)
  comparator.reversed()        — reverses any existing comparator

  List<Integer> nums = Arrays.asList(3, 1, 4, 1, 5, 9);
  nums.sort(Comparator.naturalOrder());    // [1, 1, 3, 4, 5, 9]
  nums.sort(Comparator.reverseOrder());   // [9, 5, 4, 3, 1, 1]

  // With a stream:
  nums.stream()
      .sorted(Comparator.reverseOrder())
      .collect(Collectors.toList());

TREESET AND TREEMAP WITH COMPARATORS
--------------------------------------
  When using TreeSet/TreeMap with a Comparator, the comparator defines EQUALITY
  for the purpose of the set/map — not equals() and hashCode().
  This can lead to surprises if comparator.compare() ≠ equals()!

  Example:
    // Case-insensitive TreeSet
    TreeSet<String> set = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
    set.add("Apple");
    set.add("apple"); // NOT added — comparator says they're equal (compare == 0)
    System.out.println(set.size()); // 1

    // But: "Apple".equals("apple") = false!
    // TreeSet uses the comparator, not equals(), for uniqueness

  This inconsistency between compareTo and equals can cause bugs:
    TreeSet sees: "Apple" == "apple" (same element)
    HashSet sees: "Apple" != "apple" (different elements)

USING COMPARATOR IN PRIORITYQUEUE
-----------------------------------
  PriorityQueue<Employee> topEarners = new PriorityQueue<>(
      Comparator.comparingInt(Employee::getSalary).reversed()
  );
  employees.forEach(topEarners::offer);

  // Get top 5 highest-paid:
  for (int i = 0; i < 5; i++) {
      System.out.println(topEarners.poll().getName());
  }

WRITING A COMPLETE GENERIC SORTED CONTAINER
---------------------------------------------
  public class SortedContainer<T> {
      private final List<T> items = new ArrayList<>();
      private final Comparator<? super T> comparator;

      // Natural order — T must be Comparable
      public SortedContainer() {
          this.comparator = (Comparator<T>) Comparator.naturalOrder();
      }

      // Custom comparator
      public SortedContainer(Comparator<? super T> comparator) {
          this.comparator = comparator;
      }

      public void add(T item) {
          items.add(item);
          items.sort(comparator);
      }

      public T min() { return items.isEmpty() ? null : items.get(0); }
      public T max() { return items.isEmpty() ? null : items.get(items.size() - 1); }

      public List<T> toSortedList() { return Collections.unmodifiableList(items); }
  }

  // Usage:
  SortedContainer<String> sc = new SortedContainer<>();
  sc.add("banana"); sc.add("apple"); sc.add("cherry");
  System.out.println(sc.toSortedList()); // [apple, banana, cherry]

  SortedContainer<Employee> byPay = new SortedContainer<>(
      Comparator.comparingInt(Employee::getSalary)
  );

COMPARISON TABLE: Comparable vs Comparator WITH GENERICS
----------------------------------------------------------
  Aspect               | Comparable<T>              | Comparator<T>
  ---------------------|----------------------------|---------------------------------
  Interface package    | java.lang                  | java.util
  Generic bound        | <T> compareTo(T)           | <T> compare(T o1, T o2)
  Flexible bound       | implements Comparable<? super T> | Comparator<? super T>
  Usage in TreeSet     | No constructor arg needed  | Pass in constructor
  Multiple orderings   | ❌ One per class            | ✅ Unlimited
  Chaining             | N/A                        | .thenComparing(), .reversed()
  Null handling        | Must handle manually       | nullsFirst/nullsLast built-in
  Lambda support       | N/A (not functional iface) | ✅ (functional interface)

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Why is <T extends Comparable<? super T>> more flexible than <T extends Comparable<T>>?
A: The ? super T version allows T's compareTo method to be defined on a SUPERTYPE of T.
   This means: if Dog extends Animal, and Animal implements Comparable<Animal>,
   then Dog can be sorted using Animal's compareTo (inherited) without explicitly
   implementing Comparable<Dog>. Collections.sort uses this flexible form.

Q: What happens in a TreeSet if compareTo() says two objects are equal but equals() doesn't?
A: TreeSet uses the comparator/compareTo for ALL equality checks — not equals().
   If compareTo returns 0, TreeSet treats them as the same element and won't add the second.
   The set is "inconsistent with equals." This causes behavioral differences between
   TreeSet (treats them as same) and HashSet (treats them as different — uses equals()).

Q: How do you sort a list of objects by multiple criteria?
A: Use Comparator chaining with .thenComparing():
     Comparator<Employee> comp = Comparator
         .comparing(Employee::getDepartment)    // primary sort: department alphabetically
         .thenComparingInt(Employee::getSalary) // secondary: salary ascending
         .thenComparing(Employee::getName);     // tertiary: name alphabetically
     employees.sort(comp);

Q: Can Comparator handle null elements? How?
A: By default, most Comparators throw NullPointerException when null is encountered.
   Use Comparator.nullsFirst(comparator) or Comparator.nullsLast(comparator) to
   handle nulls gracefully — they treat null as less than / greater than all non-null values.
     Comparator<String> safe = Comparator.nullsFirst(Comparator.naturalOrder());
     // [null, "a", "b", "c"] — nulls sorted first
