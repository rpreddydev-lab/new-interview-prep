BOUNDED TYPE PARAMETERS
========================

WHAT ARE BOUNDED TYPE PARAMETERS?
-----------------------------------
  By default, a type parameter T accepts ANY reference type.
  Bounds restrict what types can be substituted for T.

  TWO KINDS:
  1. Upper-bounded:  <T extends SomeType>  — T must be SomeType or a subtype
  2. Lower-bounded:  <? super SomeType>    — wildcard only (not in class/method declarations)

UPPER BOUND: <T extends Type>
-------------------------------
  T must be Type or a subclass of Type (or implement the interface if Type is an interface).
  Inside the method/class, you can call any method declared in Type on a T variable.

  // Numeric computation — T must be a Number
  public static <T extends Number> double sum(List<T> list) {
      double total = 0;
      for (T item : list) {
          total += item.doubleValue();  // can call Number methods on T
      }
      return total;
  }

  sum(List.of(1, 2, 3));       // T = Integer (extends Number) ✅
  sum(List.of(1.5, 2.5));      // T = Double (extends Number)  ✅
  sum(List.of("a", "b"));      // ❌ compile error — String doesn't extend Number

  // Comparable bound — for sorting/min/max
  public static <T extends Comparable<T>> T max(T a, T b) {
      return a.compareTo(b) >= 0 ? a : b;
  }
  System.out.println(max(3, 7));        // 7
  System.out.println(max("apple", "mango")); // mango

MULTIPLE BOUNDS
----------------
  T can extend ONE class and implement MULTIPLE interfaces.
  Class must come first; interfaces after &.

  // T must extend Animal AND implement Comparable AND Serializable
  public static <T extends Animal & Comparable<T> & Serializable> T findLargest(List<T> animals) {
      return animals.stream().max(Comparator.naturalOrder()).orElseThrow();
  }

  // After erasure: T is replaced by the leftmost bound (Animal in this case)

WILDCARDS AND BOUNDS (PECS PRINCIPLE)
---------------------------------------
  WILDCARDS (?) are used in variable declarations and method parameters — NOT class definitions.
  There are THREE wildcard types:

  1. Unbounded wildcard:  List<?>
     - Accept a list of ANY type
     - Can only read as Object; cannot add (except null)
     - Use when type doesn't matter: print(List<?>)

  2. Upper-bounded wildcard:  List<? extends Number>
     - Accept List<Integer>, List<Double>, List<Number>
     - Can READ elements as Number
     - CANNOT ADD (don't know exact type — might be List<Integer>, can't add Double)
     - Use when you only PRODUCE (read) from the collection → "Producer Extends"

  3. Lower-bounded wildcard:  List<? super Integer>
     - Accept List<Integer>, List<Number>, List<Object>
     - Can ADD Integer (or subtypes) safely
     - Can only READ as Object (don't know what supertype it is)
     - Use when you only CONSUME (write to) the collection → "Consumer Super"

PECS: PRODUCER EXTENDS, CONSUMER SUPER
-----------------------------------------
  Collections.copy(dest, src):
    public static <T> void copy(List<? super T> dest, List<? extends T> src)
    //                          ^^^^^^^^^^^^^^^^       ^^^^^^^^^^^^^^^^
    //                          dest CONSUMES T         src PRODUCES T

  Rule:
    - If you READ FROM a collection → use extends (wildcard as producer)
    - If you WRITE TO a collection  → use super (wildcard as consumer)
    - If you BOTH read and write    → don't use wildcard (use exact type T)

  Example:
    // sum all numbers — reading only → extends
    public double sumList(List<? extends Number> list) {
        return list.stream().mapToDouble(Number::doubleValue).sum();
    }
    sumList(List.of(1, 2, 3));       // ✅ List<Integer>
    sumList(List.of(1.0, 2.5));      // ✅ List<Double>

    // Fill list with element — writing only → super
    public static <T> void fill(List<? super T> list, T val, int count) {
        for (int i = 0; i < count; i++) list.add(val);
    }
    List<Number> nums = new ArrayList<>();
    fill(nums, 42, 5);               // ✅ Integer is subtype of Number

WILDCARD CAPTURE
-----------------
  // Reading works fine:
  public void printList(List<?> list) {
      for (Object obj : list) System.out.println(obj);
  }

  // Adding fails — type unknown:
  public void addElement(List<?> list) {
      list.add("hello"); // ❌ compile error — cannot add to List<?>
      list.add(null);    // ✅ null is always valid
  }

  // Capture helper pattern — to work with wildcard:
  public <T> void swapHelper(List<T> list, int i, int j) {
      T temp = list.get(i);
      list.set(i, list.get(j));
      list.set(j, temp);
  }
  public void swap(List<?> list, int i, int j) {
      swapHelper(list, i, j); // wildcard captured as T
  }

GENERICS AND INHERITANCE: NOT COVARIANT
-----------------------------------------
  Arrays are COVARIANT: String[] is-a Object[]
    Object[] arr = new String[3]; // ✅ compiles
    arr[0] = 42;                  // ❌ ArrayStoreException at RUNTIME (type not checked at compile time)

  Generics are INVARIANT: List<String> is NOT a List<Object>
    List<Object> list = new ArrayList<String>(); // ❌ compile error
    // If this were allowed, you could add Integer to what's "really" a List<String>

  Wildcards restore flexibility:
    List<? extends Object> list = new ArrayList<String>(); // ✅
    // But you can only read (as Object), not add

SUMMARY TABLE
--------------
  Declaration           | What types accepted          | Can read?     | Can write?
  ----------------------|------------------------------|---------------|------------
  List<T>               | Exact type T only            | T             | T
  List<Object>          | Exact Object only            | Object        | Object
  List<?>               | Any type                     | Object        | ❌ No
  List<? extends T>     | T and subtypes of T          | T             | ❌ No
  List<? super T>       | T and supertypes of T        | Object only   | T (and subtypes)
  <T extends Bound>     | Bound and subtypes of Bound  | Bound         | T

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What does PECS mean?
A: PECS = "Producer Extends, Consumer Super."
   If a parameterized type is a PRODUCER (you read from it), use <? extends T>.
   If it is a CONSUMER (you write to it), use <? super T>.
   This comes from the Effective Java book and is used in the Java Collections API
   (e.g., Collections.copy — List<? super T> dest, List<? extends T> src).

Q: Why is List<String> not a subtype of List<Object>?
A: Generics are invariant. If List<String> were a subtype of List<Object>, you could write:
     List<Object> objects = new ArrayList<String>();
     objects.add(42); // would put an Integer into a List<String> — disaster
   Java prevents this at compile time to maintain type safety.
   Arrays don't have this protection (covariant), hence ArrayStoreException can occur at runtime.

Q: When would you use <T extends Comparable<T>> vs <T extends Comparable<? super T>>?
A: <T extends Comparable<T>>: T must compare with itself.
   <T extends Comparable<? super T>>: T must be comparable, and the comparison can be defined
   on any supertype of T. More flexible — allows a subclass to inherit compareTo from its parent.
   Example: TreeSet uses Comparable<? super T> so Dog (extends Animal) can use Animal.compareTo.
   Always prefer the more flexible <? super T> form in library/utility code.

Q: What is the difference between <T extends Number> and <? extends Number>?
A: <T extends Number>: T is a named type parameter. Can be referenced multiple times in the
   signature (e.g., T method(List<T> list) returns T). The caller/compiler resolves T.
   <? extends Number>: anonymous wildcard. Cannot reference the type by name. Used when
   you only need to express "some unknown subtype of Number" and don't need to name it.
