WILDCARDS AND TYPE ERASURE
===========================

WILDCARDS (?)
--------------
  A wildcard ? represents an UNKNOWN type in a generic type expression.
  Used in: variable types, method parameters, return types.
  NOT used in: class declarations, generic method type parameters.

  Three forms:
    List<?>              — unbounded wildcard: list of some unknown type
    List<? extends Foo>  — upper-bounded: list of Foo or any subtype
    List<? super Foo>    — lower-bounded: list of Foo or any supertype

UNBOUNDED WILDCARD: List<?>
-----------------------------
  Accept list of any type. Can only treat elements as Object.
  Cannot add (except null) because the type is unknown.

  public void printAll(List<?> list) {
      for (Object obj : list) {
          System.out.println(obj);
      }
  }

  printAll(List.of("a", "b"));  // ✅ List<String>
  printAll(List.of(1, 2, 3));   // ✅ List<Integer>
  printAll(List.of());          // ✅ empty list

  // Cannot add:
  public void addToList(List<?> list) {
      list.add("hello"); // ❌ compile error — type unknown, might be List<Integer>
      list.add(null);    // ✅ null is always safe
  }

  Use when: you only read elements, and the specific type doesn't matter.
  Common example: generic printing, size checking, clearing.

UPPER-BOUNDED WILDCARD: <? extends T>
---------------------------------------
  Accept a list parameterized with T or any subtype of T.
  Can READ elements as T.
  CANNOT ADD (except null) — the actual subtype is unknown.

  Why can't you add?
    List<? extends Number> nums;
    nums = new ArrayList<Integer>(); // OK — Integer extends Number
    nums.add(3.14);  // ❌ — nums might be List<Integer>, cannot add Double to it!
    // Compiler doesn't know the actual type — blocks writes to be safe

  public static double sumList(List<? extends Number> list) {
      double total = 0;
      for (Number n : list) {   // elements read as Number
          total += n.doubleValue();
      }
      return total;
  }

  sumList(List.of(1, 2, 3));     // ✅ List<Integer>
  sumList(List.of(1.5, 2.5));    // ✅ List<Double>
  sumList(List.of("a"));         // ❌ compile error — String doesn't extend Number

LOWER-BOUNDED WILDCARD: <? super T>
-------------------------------------
  Accept a list parameterized with T or any supertype of T.
  Can ADD elements of type T (or subtypes of T).
  Can only READ elements as Object.

  Why can you add?
    List<? super Integer> list;
    list = new ArrayList<Number>();  // Number is super of Integer
    list.add(42);    // ✅ — adding Integer is safe, regardless of whether list is
                     //       List<Integer>, List<Number>, or List<Object>
    Number n = list.get(0); // ❌ — list might be List<Object>, can only read as Object

  public static <T> void addMultiple(List<? super T> list, T value, int count) {
      for (int i = 0; i < count; i++) list.add(value);
  }

  List<Number> nums = new ArrayList<>();
  addMultiple(nums, 42, 5);   // T=Integer, List<Number> super Integer ✅
  // nums = [42, 42, 42, 42, 42]

TYPE ERASURE — DEEP DIVE
-------------------------
  Java generics are a COMPILE-TIME FEATURE ONLY.
  After compilation, all type parameters are removed (erased).
  The compiled bytecode looks like pre-generics code.

  What happens during erasure:
  1. Unbounded type parameters T → replaced with Object
  2. Bounded type parameters <T extends Foo> → replaced with Foo (the leftmost bound)
  3. Compiler inserts CASTS where needed at call sites

  Example:
    // Source code (generic):
    public class Box<T> {
        private T item;
        public T get() { return item; }
        public void set(T item) { this.item = item; }
    }

    // After erasure (what bytecode looks like):
    public class Box {
        private Object item;    // T → Object
        public Object get() { return item; }
        public void set(Object item) { this.item = item; }
    }

    // At call site — compiler inserts cast:
    Box<String> box = new Box<>();
    box.set("hello");
    String s = box.get();
    // becomes: String s = (String) box.get();  ← inserted by compiler

  Bounded erasure:
    // <T extends Number>
    public <T extends Number> T max(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }
    // After erasure:
    public Number max(Number a, Number b) {  // T → Number (leftmost bound)
        return a.compareTo(b) >= 0 ? a : b;
    }

CONSEQUENCES OF TYPE ERASURE
------------------------------
  1. Cannot use instanceof with parameterized types:
       if (obj instanceof List<String>)  // ❌ compile error — erased at runtime
       if (obj instanceof List<?>)       // ✅ with wildcard

  2. Cannot create arrays of generic types:
       T[] arr = new T[10];             // ❌ compile error
       T[] arr = (T[]) new Object[10];  // ✅ but unchecked cast warning

  3. Cannot instantiate type parameters:
       T instance = new T();            // ❌ compile error

  4. Cannot use in catch clause:
       catch (T e) { ... }              // ❌ compile error

  5. Cannot use in static context (without declaring on static method):
       static T staticField;            // ❌ compile error (no class-level T)

  6. Method overloading with same erasure:
       // void process(List<String> list) and void process(List<Integer> list)
       // BOTH erase to process(List list) → compile error: duplicate method

BRIDGE METHODS
---------------
  When a generic class is subclassed with a concrete type, the compiler generates
  BRIDGE METHODS to maintain polymorphism after erasure.

  class StringBox extends Box<String> {
      @Override
      public void set(String item) { ... }  // override
  }

  // After erasure, Box has set(Object). StringBox overrides set(String).
  // Compiler generates bridge method in StringBox:
  public void set(Object item) {  // bridge — called via Box reference
      set((String) item);         // delegates to actual override
  }

HEAP POLLUTION
---------------
  When a variable of parameterized type refers to an object of wrong parameterization.
  Can happen via unchecked casts or raw types.

  List<String> strings = new ArrayList<>();
  List rawList = strings;      // raw type assignment (no warning if raw)
  rawList.add(42);             // heap pollution — Integer in List<String>!
  String s = strings.get(0);  // ClassCastException at runtime

  @SafeVarargs — suppresses heap pollution warning for generic vararg methods.
  Used when you're sure the varargs array isn't exposed outside the method.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is type erasure and why does Java have it?
A: Type erasure removes generic type information at compile time — the bytecode
   has no type parameters. This was done to maintain backward compatibility:
   pre-Java 5 bytecode can call Java 5+ generic code seamlessly (both produce the same
   raw-type bytecode). The cost is losing type information at runtime.

Q: What is heap pollution in generics?
A: Heap pollution occurs when a variable of parameterized type T refers to an object
   that is not of type T. Most commonly caused by mixing raw types with generics or
   unsafe vararg arrays. Leads to ClassCastException at unexpected locations
   (the cast is inserted by the compiler far from the actual mistake).

Q: What is the difference between List<?> and List<Object>?
A: List<Object>: explicitly parameterized with Object. Only a List<Object> is assignable to it.
   You can add any Object to a List<Object>.
   List<?>: wildcard — can hold List of any type (List<String>, List<Integer>, etc.).
   You cannot add anything (except null) because the type is unknown.
   Key: List<String> can be assigned to List<?> but NOT to List<Object>.

Q: Can you create generic exceptions?
A: You can declare a generic class that extends Exception, but you cannot:
   - Throw or catch parameterized generic exceptions (type is erased at runtime)
   - catch (SomeException<String> e) — compile error
   The type parameter can be used within the class body but not in throw/catch.
