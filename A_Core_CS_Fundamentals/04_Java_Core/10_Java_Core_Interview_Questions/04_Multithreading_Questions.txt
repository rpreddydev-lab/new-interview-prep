MULTITHREADING QUESTIONS
=========================

Q1: What is the difference between Thread and Runnable? When to use each?
-------------------------------------------------------------------------
A:
  Thread: a class that represents a thread of execution. Subclass it to define behavior.
  Runnable: a functional interface (run()) that defines the task. Pass to a Thread.

  Prefer Runnable (or Callable) because:
  - Java only supports single inheritance; subclassing Thread prevents extending another class
  - Separates the task (Runnable) from the mechanism (Thread/Executor)
  - Executor framework (ThreadPoolExecutor, ExecutorService) accepts Runnable/Callable — you
    almost never create Thread directly in modern Java

  Thread t = new Thread(() -> System.out.println("task"));
  t.start();

  ExecutorService exec = Executors.newFixedThreadPool(4);
  exec.submit(() -> System.out.println("task"));  // preferred

  Callable: like Runnable but can return a result and throw checked exceptions.
  Future<Integer> future = exec.submit(() -> compute());

Q2: What is the difference between synchronized and volatile?
------------------------------------------------------------
A:
  synchronized:
  - Provides MUTUAL EXCLUSION (only one thread in the block at a time) AND visibility
  - Establishes happens-before for all shared state (not just one variable)
  - Can cause contention and blocking
  - Use for compound operations (check-then-act, read-modify-write)

  volatile:
  - Provides VISIBILITY ONLY — no mutual exclusion
  - A volatile write happens-before any subsequent volatile read of the same variable
  - Prevents CPU and compiler caching of the variable
  - Does NOT make compound operations atomic (volatile int i; i++ is NOT atomic)
  - Zero blocking — lower overhead than synchronized
  - Use for: simple flags (boolean stopped), published references (safe publication), DCL pattern

  volatile int counter;
  counter++  // NOT atomic: read, increment, write are three separate operations → data race

  AtomicInteger counter;
  counter.incrementAndGet()  // atomic CAS-based increment — correct

Q3: What is a deadlock and how do you prevent it?
-------------------------------------------------
A:
  Deadlock: two or more threads each hold a lock and are each waiting for a lock held by
  the other — circular wait, no thread can proceed.

  Four conditions for deadlock (Coffman conditions):
  1. Mutual exclusion: at least one resource held exclusively
  2. Hold and wait: a thread holds a lock while waiting for another
  3. No preemption: locks cannot be forcibly taken away
  4. Circular wait: a cycle of threads each waiting for the next

  Prevention strategies:
  a) Lock ordering: always acquire locks in the same global order across all threads
     (thread 1: lock A then B; thread 2: lock A then B — never B then A)
  b) tryLock with timeout (ReentrantLock.tryLock(timeout, unit)):
     if unable to acquire, release all held locks and retry
  c) Lock-free structures: use java.util.concurrent atomic classes (CAS-based — no locks)
  d) Minimize lock scope: hold locks for the shortest possible time
  e) Single-lock design: if feasible, use one lock to protect related state

  Detection: jstack -l <pid> → searches for and reports deadlock cycles.

Q4: What is the difference between wait/notify and Lock/Condition?
-----------------------------------------------------------------
A:
  wait()/notify()/notifyAll() (Object methods):
  - Must be called within a synchronized block on the same object (monitor)
  - notifyAll() wakes all waiting threads — they compete for the monitor
  - Cannot have multiple condition variables on one monitor
  - Spurious wakeups — must use while loop (not if) to re-check condition

  Lock/Condition (java.util.concurrent.locks):
  - Explicit Lock (ReentrantLock) separates locking from condition management
  - One Lock can have MULTIPLE Condition objects (condition variables) — fine-grained signaling
  - await() / signal() / signalAll() — analogous to wait/notify
  - await() also has timeout variants (awaitNanos, awaitUntil)
  - tryLock() — non-blocking acquire; avoids deadlocks
  - Lock is interruptible (lockInterruptibly())
  - Better diagnostic information (knows which thread holds the lock)

  Prefer Lock/Condition for: complex producer-consumer with multiple conditions,
  timed lock acquisition, fairness requirement (new ReentrantLock(true)).

Q5: What is ThreadLocal and when is it useful?
---------------------------------------------
A:
  ThreadLocal<T> provides a per-thread variable — each thread has its own independent copy.
  One thread's modifications are invisible to other threads.

  Key methods: set(T value), get(), remove()

  Thread t = new Thread(() -> {
      ThreadLocal<String> local = new ThreadLocal<>();
      local.set("thread-specific-data");
      System.out.println(local.get()); // "thread-specific-data" — not shared
  });

  Use cases:
  - Per-thread database connections / transactions (Spring's TransactionSynchronizationManager)
  - User/request context in web servers (MDC in logging — thread-per-request model)
  - DateFormat instances (not thread-safe — one per thread avoids synchronization)
  - Per-thread random number generators (ThreadLocalRandom)

  Critical: ALWAYS call threadLocal.remove() when done — especially in thread pool threads
  (threads are reused; stale values from a previous task persist and leak to the next task).
  Failure to remove causes MEMORY LEAKS and LOGIC BUGS.

Q6: What is the Executor framework, and what are the types of thread pools?
---------------------------------------------------------------------------
A:
  ExecutorService (java.util.concurrent):
  submit(Runnable/Callable) → returns Future
  shutdown() → graceful (completes in-progress tasks); shutdownNow() → attempt interrupt

  Executors factory methods (thread pools):
  newFixedThreadPool(n)    — fixed n threads; unbounded queue; good for known workload size
  newCachedThreadPool()    — unlimited threads, reuses idle threads; good for many short tasks
  newSingleThreadExecutor()— single thread, sequential task execution; good for ordering
  newScheduledThreadPool(n)— supports scheduleAtFixedRate / scheduleWithFixedDelay

  Java 21: Virtual Thread executor:
  Executors.newVirtualThreadPerTaskExecutor() — one virtual thread per task; scales to millions

  Custom pool (recommended for production):
  new ThreadPoolExecutor(corePoolSize, maxPoolSize, keepAliveTime, unit, new ArrayBlockingQueue<>(1000))
  — gives full control over queue size, rejection policy, thread lifecycle

  RejectedExecutionHandler (when queue is full + maxPoolSize reached):
  AbortPolicy (default) — throws RejectedExecutionException
  CallerRunsPolicy — executes task on the caller's thread (backpressure)
  DiscardPolicy — silently drop the task
  DiscardOldestPolicy — drop oldest queued task, then retry

Q7: What is a race condition? Give an example.
----------------------------------------------
A:
  A race condition occurs when the behavior of a program depends on the relative timing
  or interleaving of multiple threads — and at least one of the possible interleavings
  produces incorrect behavior.

  Classic example: unsynchronized counter
  int counter = 0;
  // Thread 1 and Thread 2 both execute counter++ concurrently
  // counter++ is: read counter → add 1 → write counter (3 non-atomic steps)
  // Possible interleaving:
  //   T1 reads counter=0
  //   T2 reads counter=0 (before T1 writes)
  //   T1 writes counter=1
  //   T2 writes counter=1  ← lost update! expected 2

  Fix: AtomicInteger.incrementAndGet() (CAS-based), or synchronized block, or volatile
  (not sufficient for i++ since it's not atomic).

  Check-then-act race:
  if (!map.containsKey(key)) { map.put(key, value); }  // NOT atomic → two threads can both pass the check
  Fix: map.putIfAbsent(key, value)  (ConcurrentHashMap provides this atomically)

Q8: How do CountDownLatch, CyclicBarrier, and Semaphore differ?
---------------------------------------------------------------
A:
  CountDownLatch:
  - One-shot counter. Threads await() until count reaches 0.
  - countDown() decrements; await() blocks until 0.
  - Cannot be reset. Used for "wait for N events before proceeding."
  - Example: main thread waits for 5 workers to finish initialization before proceeding.

  CyclicBarrier:
  - All-parties-must-arrive synchronizer. N threads call await() — all block until ALL N arrive.
  - Reusable (cyclic) — resets automatically after each use.
  - Optional barrier action (Runnable) runs once when all parties arrive.
  - Example: parallel computation phases — all threads complete phase 1, then all start phase 2.

  Semaphore:
  - Controls access to a pool of resources. acquire() takes a permit; release() returns it.
  - Blocks if no permits available.
  - Semaphore(1) ≈ mutex (but NOT reentrant); Semaphore(N) limits to N concurrent users.
  - Example: limit to at most 10 concurrent database connections.

  | Feature        | CountDownLatch | CyclicBarrier | Semaphore     |
  |----------------|----------------|---------------|---------------|
  | Reusable       | No             | Yes           | Yes           |
  | Typical use    | Wait for N events | N threads sync | Resource pool |
  | Direction      | Count down     | Count up to N | Permit pool   |
  | Barrier action | No             | Yes           | No            |
