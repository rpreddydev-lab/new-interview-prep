GENERICS AND EXCEPTIONS QUESTIONS
===================================

Q1: What is type erasure in Java generics?
------------------------------------------
A:
  Type erasure is the process by which the Java compiler removes generic type parameters
  from code during compilation. At runtime, generic types are replaced with their raw types
  (typically Object, or the upper bound if bounded wildcards are used).

  // Compile time:
  List<String> list = new ArrayList<String>();
  String s = list.get(0);

  // After erasure (runtime bytecode equivalent):
  List list = new ArrayList();
  String s = (String) list.get(0);   // compiler inserts the cast

  Why: Java generics were added in Java 5 for backward compatibility — the bytecode was
  designed to run on older JVMs that knew nothing about generics.

  Consequences:
  - Cannot create instances of type parameters: new T() — ILLEGAL
  - Cannot create arrays of generic types: new T[10] — ILLEGAL
  - instanceof check on parameterized types is illegal at runtime: list instanceof List<String> — ILLEGAL
  - Reflection shows raw type: list.getClass() → ArrayList.class (not ArrayList<String>.class)
  - Method overloading based solely on generic type parameters is disallowed (same erasure → same signature)

Q2: What is the difference between extends and super in wildcards?
-----------------------------------------------------------------
A:
  Wildcards allow flexibility when the exact type parameter is unknown.

  ? extends T (upper bounded wildcard — PRODUCES, read-only):
    A collection can hold any subtype of T.
    You can READ elements from it as T, but you CANNOT ADD to it (type-unsafe).
    Use when: reading from a collection; covariant behavior.
    List<? extends Number> nums;  // could be List<Integer> or List<Double>
    nums.get(0);  // returns Number — safe
    nums.add(3);  // COMPILE ERROR — could be List<Double>!

  ? super T (lower bounded wildcard — CONSUMES, write-friendly):
    A collection can hold T or any supertype of T.
    You can ADD elements of type T; reading gives Object.
    Use when: writing to a collection; contravariant behavior.
    List<? super Integer> ints;  // could be List<Integer>, List<Number>, List<Object>
    ints.add(5);   // safe — Integer is a subtype of all possible types
    Integer i = ints.get(0);  // COMPILE ERROR — could be Object

  Mnemonic — PECS: Producer Extends, Consumer Super.
  Read-only input parameters → ? extends T
  Write-only output parameters → ? super T

Q3: What is the difference between checked and unchecked exceptions?
---------------------------------------------------------------------
A:
  Checked exceptions (subclass of Exception but NOT RuntimeException):
  - Must be declared in method signature (throws clause) or caught
  - Compiler enforces handling: compile error if neither caught nor declared
  - Represent recoverable conditions the caller should handle
  - Examples: IOException, SQLException, ClassNotFoundException

  Unchecked exceptions (subclass of RuntimeException or Error):
  - Do NOT need to be declared or caught (compiler doesn't enforce)
  - Represent programming errors or unrecoverable conditions
  - RuntimeException examples: NullPointerException, IllegalArgumentException,
    IndexOutOfBoundsException, ConcurrentModificationException
  - Error examples: StackOverflowError, OutOfMemoryError, AssertionError

  Design debate:
  - Java's original intent: checked = recoverable, unchecked = programmer error
  - Modern view (Spring, Hibernate): checked exceptions are controversial; many frameworks
    wrap checked exceptions as unchecked (RuntimeException) for cleaner APIs
  - Effective Java (Bloch): use checked exceptions for conditions callers can reasonably
    recover from; use unchecked for programming errors.

Q4: What is the exception handling best practice for Java?
---------------------------------------------------------
A:
  1. Catch specific exceptions (not Exception or Throwable) — precise handling.
  2. Never swallow exceptions silently: catch (Exception e) {} — NEVER.
  3. Log at the boundary where you handle (not propagate) the exception.
  4. Use finally (or try-with-resources) to release resources — never rely on GC for I/O.
  5. Prefer try-with-resources for AutoCloseable resources:
     try (InputStream is = new FileInputStream(f)) { ... }
     — always closes the resource, even if exception thrown.
  6. Don't use exceptions for control flow (performance penalty, unclear intent).
  7. Include context in exception messages (file name, input value that caused the error).
  8. When rethrowing, preserve the original cause:
     throw new ServiceException("Failed to read config", originalException);
  9. Custom exceptions: extend RuntimeException for unchecked app exceptions;
     use checked only where the caller truly can recover.
  10. Multi-catch (Java 7+): catch (IOException | SQLException e) { ... } — avoid code duplication.

Q5: What happens in finally with return, throw, or System.exit()?
-----------------------------------------------------------------
A:
  finally ALWAYS executes when its try block exits normally, by exception, or by return —
  with two exceptions:
  1. System.exit() — terminates JVM; finally does NOT run.
  2. JVM crash / kill -9 — finally does NOT run.

  Interaction with return:
  try { return 1; } finally { return 2; }  // returns 2! finally overwrites the return value.
  → This is a design anti-pattern — never use return in finally.

  Interaction with throw:
  try { throw new RuntimeException("A"); }
  finally { throw new RuntimeException("B"); }  // B is thrown; A is LOST (suppressed silently)
  → Java 7 try-with-resources handles this correctly: suppressed exceptions are attached.
    try { ... } catch (Exception e) { e.getSuppressed(); }

  try-with-resources: if both the body throws exception A and close() throws exception B:
  A is the primary exception; B is added as a suppressed exception to A.
  This is the correct behavior — primary exception is not lost.

Q6: What is the difference between throw and throws?
----------------------------------------------------
A:
  throw (statement): used inside a method body to THROW an exception instance.
    throw new IllegalArgumentException("age must be positive");
    Execution immediately transfers to the nearest matching catch block.

  throws (clause): part of a method's signature; declares that the method MAY throw
    the listed checked exceptions (so callers must handle/declare them).
    public void readFile(String path) throws IOException { ... }

  A method can declare throws RuntimeException or throws Error (technically legal, but
  not required — the compiler doesn't enforce handling of unchecked exceptions).

Q7: What is a generic method and how does it differ from a generic class?
-------------------------------------------------------------------------
A:
  Generic class: the type parameter is declared at the class level and shared across
  all methods.
  class Box<T> { private T value; public T get() { return value; } }

  Generic method: the type parameter is declared at the method level (before the return type).
  Each invocation can have a different type argument, independent of the class type parameter.
  public <T extends Comparable<T>> T max(T a, T b) { return a.compareTo(b) > 0 ? a : b; }

  // Call:
  String s = max("alpha", "beta");   // T inferred as String
  int i    = max(3, 7);              // T inferred as Integer

  Generic methods are useful in utility/helper classes (Collections, Arrays) where the
  class itself isn't parameterized but individual operations are type-parameterized.

Q8: Can you catch and handle Error types? When should you?
----------------------------------------------------------
A:
  Error is the superclass for JVM-level failures: OutOfMemoryError, StackOverflowError,
  AssertionError, LinkageError, etc. It is NOT a subclass of Exception.

  Technically: yes, you can catch Error:
  try { ... } catch (Error e) { ... }

  Should you?
  - Generally NO. Errors represent unrecoverable JVM states. Attempting to recover from
    OOM or StackOverflow is usually futile and dangerous (heap may be corrupt, invariants broken).
  - Exceptions where catching Error is reasonable:
    * StackOverflowError: in certain recursive algorithms where recursion depth is bounded
      by input — catching it allows returning a result or fallback (use very carefully).
    * OutOfMemoryError: only at the very top-level to log and exit gracefully — not to retry.
    * AssertionError: in test frameworks or when assertions are used for invariant checking.
    * ThreadDeath: when overriding Thread.stop() behavior (rare, deprecated).

  Best practice: catch Throwable only at the absolute top level (e.g., server request handler)
  to log catastrophic failures before the application exits — never to recover silently.
