IMMUTABLE COLLECTIONS
======================

WHY IMMUTABILITY?
------------------
  Immutable collections cannot be modified after creation. Benefits:
  - Thread safety: safe to share across threads without synchronization
  - Defensive programming: prevent unintended modification of returned collections
  - Predictability: behavior is deterministic; no surprise side effects
  - Memory efficiency: can be safely shared/cached (same instance reused)

JAVA 9+ FACTORY METHODS (RECOMMENDED)
---------------------------------------
  Java 9 introduced convenient factory methods for unmodifiable collections.
  These are NOT backed by any mutable collection — they are truly immutable.
  Do NOT allow null elements/keys/values.
  Throw UnsupportedOperationException on any mutation attempt.

  List.of():
    List<String> list = List.of("apple", "banana", "cherry");  // up to 10 elements (varargs)
    list.add("date");       // throws UnsupportedOperationException
    list.set(0, "x");       // throws UnsupportedOperationException

  Set.of():
    Set<Integer> set = Set.of(1, 2, 3, 4, 5);
    set.add(6);             // throws UnsupportedOperationException
    // NOTE: Set.of() throws IllegalArgumentException for duplicate elements:
    // Set.of(1, 1); // ❌ throws at creation time

  Map.of():
    Map<String, Integer> map = Map.of("a", 1, "b", 2, "c", 3);  // up to 10 entries
    map.put("d", 4);        // throws UnsupportedOperationException

  Map.ofEntries() — for larger maps:
    Map<String, Integer> big = Map.ofEntries(
        Map.entry("key1", 1),
        Map.entry("key2", 2),
        Map.entry("key3", 3)
        // ... any number of entries
    );

  Map.copyOf(existingMap)  — immutable copy of another map
  List.copyOf(existingList) — immutable copy of another list
  Set.copyOf(existingSet)  — immutable copy of another set

ADDITIONAL PROPERTIES OF FACTORY METHOD COLLECTIONS
------------------------------------------------------
  - Iteration order: List.of() preserves order; Set.of() and Map.of() may NOT
    (their iteration order is intentionally NOT guaranteed — can change between runs)
  - Serializable
  - Value-based: equals() and hashCode() based on contents, not identity
  - Compact internal representation (smaller memory footprint than ArrayList/HashMap)

PRE-JAVA 9 APPROACHES
----------------------
  1. Collections.unmodifiableList/Set/Map (wrapper):
    List<String> mutable = new ArrayList<>(Arrays.asList("a", "b", "c"));
    List<String> immutable = Collections.unmodifiableList(mutable);
    immutable.add("d"); // throws UnsupportedOperationException

    ⚠️ PITFALL: the wrapper is just a VIEW. The original mutable list can still be changed!
    mutable.add("d");    // OK — and immutable.size() is now 4!
    // Solution: don't retain reference to original, or use defensive copy:
    List<String> safe = Collections.unmodifiableList(new ArrayList<>(mutable));

  2. Arrays.asList() — fixed size, but allows set():
    List<String> fixed = Arrays.asList("a", "b", "c");
    fixed.set(0, "x");  // ✅ allowed — mutation of existing element
    fixed.add("d");     // ❌ throws UnsupportedOperationException
    // Backed by array — changing original array changes the list

  3. Guava ImmutableList/ImmutableSet/ImmutableMap (third-party):
    ImmutableList<String> list = ImmutableList.of("a", "b", "c");
    ImmutableMap<String, Integer> map = ImmutableMap.of("k1", 1, "k2", 2);
    // Like List.of() but available pre-Java 9, with additional utilities

DEFENSIVE COPIES — BEST PRACTICE
----------------------------------
  When returning a collection from a class, return an immutable copy to prevent
  callers from modifying internal state:

  public class SchoolClass {
      private final List<String> students;

      public SchoolClass(List<String> students) {
          // Defensive copy on input
          this.students = new ArrayList<>(students);  // or List.copyOf(students)
      }

      // ❌ BAD — returns internal mutable list
      public List<String> getStudents() { return students; }

      // ✅ GOOD — returns immutable view
      public List<String> getStudents() { return Collections.unmodifiableList(students); }

      // ✅ BEST (Java 9+) — returns independent immutable copy
      public List<String> getStudents() { return List.copyOf(students); }
  }

COMPARISON TABLE
-----------------
  Method                                | Immutable? | Null OK? | Original mutable?
  --------------------------------------|------------|----------|------------------
  List.of(...)                          | ✅ True    | ❌ No    | N/A (no backing)
  List.copyOf(list)                     | ✅ True    | ❌ No    | N/A (deep copy)
  Collections.unmodifiableList(list)    | ⚠️ View only| ✅ Yes  | ⚠️ Yes — changes visible
  Arrays.asList(...)                    | ⚠️ Partial | ✅ Yes  | ✅ Can set()
  new ArrayList<>(list)                 | ❌ Mutable | ✅ Yes  | N/A (new copy)
  Guava ImmutableList.of(...)           | ✅ True    | ❌ No    | N/A (no backing)

RECORDS AND IMMUTABILITY (JAVA 16+)
-------------------------------------
  Records are great for pairing with immutable collections:

  public record Course(String name, List<String> topics) {
      public Course {
          topics = List.copyOf(topics); // defensive copy — compact constructor
      }
  }
  // Course.topics() is always unmodifiable

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What's the difference between List.of() and Collections.unmodifiableList()?
A: List.of() creates a truly immutable list — no backing mutable structure.
   Throws UnsupportedOperationException on mutation. Does not allow nulls.
   Iteration order is preserved but not guaranteed to match any particular implementation.

   Collections.unmodifiableList() returns a VIEW of the original list.
   The view is unmodifiable, but the underlying list can still be modified directly.
   Changes to the original list ARE visible through the view — it's not truly immutable.
   Allows null elements.

Q: Can you modify a List obtained from Arrays.asList()?
A: Partially. Arrays.asList() returns a fixed-size List backed by the original array.
   You can call set() to update elements. You CANNOT add() or remove() — those throw
   UnsupportedOperationException. Also: changes to the backing array are reflected in the list.

Q: Why do List.of() and Set.of() not allow null?
A: The designers made a deliberate choice: null in collections usually indicates a missing
   value, which leads to bugs. These immutable collections are meant for clear, defined
   values. If you need null, use Collections.unmodifiableList() or a mutable collection.

Q: Is List.of() serializable?
A: Yes. The factory-created immutable collections implement Serializable. They also
   implement a special serialization proxy to ensure deserialized instances remain immutable.
