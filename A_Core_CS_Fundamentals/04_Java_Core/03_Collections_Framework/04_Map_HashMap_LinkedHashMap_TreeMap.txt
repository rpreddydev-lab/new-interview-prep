MAP: HASHMAP vs LINKEDHASHMAP vs TREEMAP
==========================================

THE MAP INTERFACE
------------------
  java.util.Map<K,V> — NOT a Collection (doesn't extend Collection<E>)
  - Stores key-value pairs
  - Keys are unique; values may duplicate
  - Each key maps to exactly one value

  Core methods:
    put(K key, V value)      → adds or replaces entry, returns old value (or null)
    get(Object key)          → returns value or null if absent
    remove(Object key)       → removes entry, returns value
    containsKey(Object key)  → O(1) for HashMap
    containsValue(Object v)  → O(n) — must scan all values
    size(), isEmpty(), clear()
    keySet()   → Set<K>       — view of all keys
    values()   → Collection<V>— view of all values
    entrySet() → Set<Map.Entry<K,V>> — view of all pairs (most useful for iteration)

  Java 8+ additions:
    getOrDefault(key, defaultVal)
    putIfAbsent(key, value)
    computeIfAbsent(key, mappingFn)
    computeIfPresent(key, remappingFn)
    compute(key, remappingFn)
    merge(key, value, remappingFn)
    forEach((k, v) -> ...)
    replaceAll((k, v) -> newValue)

HASHMAP
--------
Internal Structure: Array of buckets + linked list (Java 7) or balanced tree (Java 8+)
  - Array size = capacity (default 16, always power of 2)
  - Load factor: 0.75 (resize when size > capacity × 0.75)
  - On resize: doubles capacity, rehashes all entries
  - Java 8: when a bucket has ≥ 8 entries AND array size ≥ 64, bucket converts to Red-Black tree
            (treeification). Reverts to linked list when size drops to ≤ 6.

Key Operations:
  put/get/remove/containsKey → O(1) average, O(log n) with treeified bucket, O(n) worst (all same hash)

Allows:
  - One null key (stored in bucket 0)
  - Multiple null values

Ordering: NONE — iteration order is not guaranteed

Example:
  Map<String, Integer> scores = new HashMap<>();
  scores.put("Alice", 90);
  scores.put("Bob", 85);
  scores.put("Charlie", 92);
  scores.put("Alice", 95);       // updates "Alice" → returns 90

  System.out.println(scores.get("Bob")); // 85
  System.out.println(scores.getOrDefault("Dave", 0)); // 0

  // Iterate entries (best practice)
  for (Map.Entry<String, Integer> entry : scores.entrySet()) {
      System.out.println(entry.getKey() + " → " + entry.getValue());
  }

  // Java 8 forEach
  scores.forEach((k, v) -> System.out.println(k + "=" + v));

  // computeIfAbsent — common for grouping
  Map<String, List<String>> groups = new HashMap<>();
  groups.computeIfAbsent("fruits", k -> new ArrayList<>()).add("apple");
  groups.computeIfAbsent("fruits", k -> new ArrayList<>()).add("banana");
  // groups = {fruits=[apple, banana]}

LINKEDHASHMAP
--------------
Internal Structure: HashMap + doubly-linked list through all entries
  - Maintains insertion order (default) OR access order (special constructor)
  - All HashMap operations at O(1) with slight overhead for list maintenance

Constructors:
  new LinkedHashMap<>()                           // insertion order
  new LinkedHashMap<>(capacity, loadFactor, true) // access-order (LRU basis)

Example — insertion order:
  Map<String, Integer> linked = new LinkedHashMap<>();
  linked.put("banana", 1);
  linked.put("apple", 2);
  linked.put("cherry", 3);
  System.out.println(linked.keySet()); // [banana, apple, cherry] — insertion order

Example — LRU Cache with access-order:
  Map<Integer, String> lru = new LinkedHashMap<>(16, 0.75f, true) {
      @Override
      protected boolean removeEldestEntry(Map.Entry<Integer, String> eldest) {
          return size() > 3; // keep at most 3 entries
      }
  };
  lru.put(1, "A"); lru.put(2, "B"); lru.put(3, "C");
  lru.get(1);       // accesses 1, moves it to end
  lru.put(4, "D");  // triggers removeEldestEntry — removes 2 (least recently used)
  System.out.println(lru.keySet()); // [3, 1, 4]

TREEMAP
--------
Internal Structure: Red-Black tree (self-balancing BST)
  - Keys are stored in sorted order (natural ordering or custom Comparator)
  - All operations O(log n)

Key Operations (beyond Map):
  firstKey() / lastKey()
  floorKey(K key)    → greatest key ≤ k
  ceilingKey(K key)  → smallest key ≥ k
  lowerKey(K key)    → greatest key < k
  higherKey(K key)   → smallest key > k
  headMap(K to)      → view of entries with keys < to
  tailMap(K from)    → view of entries with keys ≥ from
  subMap(K from, K to) → view in [from, to)

NULL: TreeMap does NOT allow null keys (can't compare null). Values can be null.

Example:
  TreeMap<String, Integer> tmap = new TreeMap<>();
  tmap.put("banana", 2);
  tmap.put("apple", 1);
  tmap.put("cherry", 3);

  System.out.println(tmap.firstKey());     // apple (alphabetically first)
  System.out.println(tmap.lastKey());      // cherry
  System.out.println(tmap.floorKey("b")); // banana
  System.out.println(tmap.headMap("cherry")); // {apple=1, banana=2}

  // Custom comparator — reverse order
  TreeMap<String, Integer> rev = new TreeMap<>(Comparator.reverseOrder());
  rev.put("a", 1); rev.put("b", 2); rev.put("c", 3);
  System.out.println(rev.keySet()); // [c, b, a]

HASHTABLE (LEGACY — AVOID)
----------------------------
  - Synchronized version of HashMap (all methods synchronized)
  - Does NOT allow null keys or null values
  - Replaced by: ConcurrentHashMap (for thread safety) or HashMap (single-threaded)
  - Properties class extends Hashtable — still used for .properties files

COMPARISON TABLE
-----------------
  Feature              | HashMap        | LinkedHashMap    | TreeMap
  ---------------------|----------------|------------------|------------------
  Internal structure   | Hash array     | Hash + linked    | Red-Black tree
  Ordering             | None           | Insertion/Access | Sorted (keys)
  get/put/remove       | O(1) avg       | O(1) avg         | O(log n)
  containsKey          | O(1)           | O(1)             | O(log n)
  Allows null key?     | ✅ One null    | ✅ One null      | ❌ No
  Range queries?       | ❌             | ❌               | ✅ headMap/tailMap
  Thread-safe          | ❌             | ❌               | ❌
  Best use             | General KV     | Ordered KV / LRU | Sorted KV / range

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What happens if you put a mutable object as a HashMap key, then mutate it?
A: The object's hashCode changes after mutation — it ends up in the wrong bucket.
   You can no longer find it with get(). The old bucket still holds it but it's effectively lost.
   Best practice: use immutable keys (String, Integer, enums).

Q: How does HashMap handle two keys with the same hashCode?
A: Hash collision → same bucket. Java uses chaining:
   - Java 7: stores as a linked list in the bucket
   - Java 8+: still a linked list for small sizes, converts to Red-Black tree if bucket size ≥ 8
   get() then uses equals() to find the exact key.

Q: What is the load factor in HashMap? What's the default?
A: Load factor = maximum occupancy ratio before resize. Default is 0.75.
   When (size / capacity) > 0.75, the map resizes (doubles capacity and rehashes all entries).
   Lower load factor = less collisions, more memory.
   Higher load factor = more collisions, less memory.

Q: Difference between HashMap and LinkedHashMap?
A: LinkedHashMap extends HashMap and maintains a doubly-linked list through all entries.
   Same O(1) performance. LinkedHashMap preserves insertion order (default) or access order
   (when constructed with accessOrder=true, used for LRU caches). HashMap has no ordering.

Q: When would you use TreeMap instead of HashMap?
A: When you need sorted keys, range queries (headMap/tailMap), or navigation operations
   (floor/ceiling/first/last). TreeMap is O(log n) vs HashMap's O(1) — choose HashMap
   unless sorting/range behavior is required.
