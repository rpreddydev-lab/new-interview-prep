JAVA COMPILATION AND EXECUTION MODEL
=====================================

STEP-BY-STEP FLOW
-----------------
  Step 1: Write source code
      HelloWorld.java

  Step 2: Compile with javac
      javac HelloWorld.java
      → Produces: HelloWorld.class (bytecode)
      → Bytecode is NOT machine code; it is intermediate code for the JVM.

  Step 3: Execute with java (JVM)
      java HelloWorld
      → JVM loads HelloWorld.class
      → Class Loader → Bytecode Verifier → Interpreter/JIT → Execution

DETAILED JVM EXECUTION PIPELINE
---------------------------------
  .class file
      │
      ▼
  Class Loader Subsystem
      ├── Bootstrap ClassLoader   (loads java.lang.*, rt.jar / java.base module)
      ├── Extension ClassLoader   (loads java/lib/ext, java.ext.dirs)
      └── Application ClassLoader (loads your classpath classes)
      │
      ▼
  Bytecode Verifier
      Checks: valid bytecode structure, no stack overflows, type safety,
              no illegal memory access. Security gate before execution.
      │
      ▼
  Execution Engine
      ├── Interpreter         — executes bytecode line-by-line (slow for repeated code)
      └── JIT Compiler        — compiles hot methods to native machine code
              ├── C1 Compiler — fast compilation, basic optimizations (startup)
              └── C2 Compiler — slow compilation, aggressive optimizations (peak perf)
      │
      ▼
  Native Machine Code → CPU executes

TIERED COMPILATION (Java 7+)
------------------------------
  Level 0: Interpreted
  Level 1: C1 — trivial methods (no profiling)
  Level 2: C1 — with light profiling
  Level 3: C1 — with full profiling
  Level 4: C2 — fully optimized native code

  JVM collects profiling data (branch prediction, method call frequency) and
  escalates "hot" code paths to C2 for maximum optimization.

CLASSPATH AND MODULES
----------------------
  Classpath (pre-Java 9):
    - A list of directories and JARs where JVM looks for .class files.
    - Set with: java -cp /path/to/classes:/path/to/app.jar MainClass
    - Or: export CLASSPATH=/path/to/classes

  Module System (Java 9+, Project Jigsaw):
    - Source is organized into named modules (module-info.java).
    - Modules declare: what they export (exports) and what they require (requires).
    - Benefits: strong encapsulation, reduced footprint, faster startup.
    - Example module-info.java:
        module com.example.myapp {
            requires java.sql;
            exports com.example.myapp.api;
        }

JAR FILES
----------
  JAR (Java ARchive) = ZIP file containing .class files + resources + META-INF/MANIFEST.MF
  Create:  jar cf app.jar com/example/*.class
  Run:     java -jar app.jar   (requires Main-Class in MANIFEST.MF)
  List:    jar tf app.jar

COMPILATION FLAGS (javac)
--------------------------
  -source  — specifies source compatibility version
  -target  — specifies target bytecode version
  -release — (Java 9+) preferred; sets source + target + boot classpath in one flag
             e.g., javac --release 17 MyApp.java

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is bytecode?
A: Bytecode is the compiled output of javac — an intermediate, platform-independent instruction
   set for the JVM (not native CPU instructions). It is stored in .class files. The JVM then
   interprets or JIT-compiles it to native machine code at runtime.

Q: What is the difference between an interpreter and JIT compiler in JVM?
A: The interpreter executes bytecode instructions one at a time — simple but slow for repeated
   code. The JIT compiler identifies "hot" (frequently executed) code paths and compiles them
   to native machine code, caching the result. Subsequent calls execute the native code directly,
   dramatically improving performance.

Q: What does javac do vs java?
A: javac is the Java compiler — converts .java source files to .class bytecode files.
   java is the JVM launcher — loads .class files and executes them through the JVM.

Q: What is the purpose of the bytecode verifier?
A: It ensures that loaded .class files are valid and safe before execution:
   - Bytecode has correct structure (no corrupted instructions)
   - No stack overflows/underflows
   - Type safety is maintained
   - No illegal access to private fields/methods
   This is a critical security layer, especially for code loaded over a network (applets era).

Q: What is AOT (Ahead-of-Time) compilation?
A: AOT compiles Java source/bytecode to native machine code BEFORE runtime, producing a native
   binary that starts instantly without JVM warmup. GraalVM Native Image does this.
   Trade-off: loses JIT's runtime profile-guided optimizations; startup faster, peak throughput
   may be lower. Ideal for serverless/cloud-native (Quarkus, Micronaut, Spring Native).
