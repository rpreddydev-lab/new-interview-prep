TRY-CATCH-FINALLY
===================

BASIC SYNTAX
-------------
  try {
      // code that might throw
  } catch (ExceptionType e) {
      // handle the exception
  } finally {
      // always executes — cleanup code
  }

  // Multiple catch blocks:
  try {
      String s = null;
      int result = Integer.parseInt(s);    // NumberFormatException or NPE
      int[] arr = new int[result];
      int x = arr[result + 1];             // ArrayIndexOutOfBoundsException
  } catch (NullPointerException e) {
      System.out.println("Null value: " + e.getMessage());
  } catch (NumberFormatException e) {
      System.out.println("Bad number format: " + e.getMessage());
  } catch (ArrayIndexOutOfBoundsException e) {
      System.out.println("Array out of bounds: " + e.getMessage());
  } finally {
      System.out.println("Always runs");
  }

EXECUTION ORDER RULES
-----------------------
  1. try block executes
  2. If an exception is thrown:
     a. Java searches catch blocks top-to-bottom for a matching type
     b. First matching catch executes
     c. Remaining catch blocks are skipped
     d. finally always runs after the matched catch
  3. If no exception is thrown:
     - All catch blocks are skipped
     - finally still runs
  4. If finally throws, it SUPPRESSES the original exception
  5. If return appears in try AND finally, the finally return WINS (overrides try return)

  Example — return in finally:
    public int test() {
        try {
            return 1;   // would return 1...
        } finally {
            return 2;   // ...but this wins — returns 2
        }
    }
    // test() returns 2 — ALWAYS. This is a known Java gotcha. Avoid return in finally!

  Example — exception in finally overrides original:
    public void bad() throws Exception {
        try {
            throw new IOException("original");
        } finally {
            throw new RuntimeException("finally exception"); // original IOException is LOST
        }
    }
    // Caller sees RuntimeException, not IOException. Original is silently discarded.

CATCH ORDERING: MOST SPECIFIC FIRST
--------------------------------------
  Always catch more specific exceptions BEFORE more general ones.
  Catching a parent class first makes child class catches unreachable (compile error).

  // ❌ Compile error — IOException is caught by Exception first:
  try {
      // ...
  } catch (Exception e) {    // too broad — catches everything
      // ...
  } catch (IOException e) {  // UNREACHABLE — compiler error
      // ...
  }

  // ✅ Correct order — specific first:
  try {
      // ...
  } catch (FileNotFoundException e) {   // most specific
      // ...
  } catch (IOException e) {             // broader
      // ...
  } catch (Exception e) {               // broadest
      // ...
  }

MULTI-CATCH (JAVA 7+)
-----------------------
  Catch multiple unrelated exception types in a single block using |:
    try {
        // code
    } catch (IOException | SQLException e) {   // multi-catch
        log.error("Operation failed", e);
        throw new ServiceException("Data access failed", e);
    }

  Rules:
  - The caught types MUST NOT be in the same inheritance hierarchy
    (e.g., catch (FileNotFoundException | IOException e) is a compile error)
  - The variable e is implicitly FINAL in a multi-catch — cannot be reassigned
  - Reduces boilerplate when the same handler applies to multiple exception types

FINALLY BLOCK
--------------
  finally always executes:
  - After try completes normally
  - After a catch block executes
  - When an exception is NOT caught (propagates up — finally still runs before propagation)
  - Even when a return statement is in the try or catch block

  finally does NOT execute when:
  - System.exit() is called (JVM shutdown)
  - The JVM crashes (power off, kill -9)
  - Infinite loop or deadlock in the try block (stuck, not exiting)
  - Thread.stop() is called on the thread (deprecated, dangerous API)

  Use finally for resource cleanup (pre-Java 7):
    Connection conn = null;
    try {
        conn = DriverManager.getConnection(url);
        // use connection
    } catch (SQLException e) {
        log.error("DB error", e);
    } finally {
        if (conn != null) {
            try { conn.close(); } catch (SQLException e) { log.warn("Close failed", e); }
        }
    }
    // Note: finally itself can throw — so inner try/catch is often needed

STACK UNWINDING
-----------------
  When an exception is thrown and not caught in the current method,
  Java "unwinds the stack" — pops the current frame and looks for a matching
  catch in the calling method, then its caller, and so on up the stack.
  If no catch is found at any level, the JVM's default uncaught exception
  handler prints the stack trace and terminates the thread.

  Thread t = new Thread(() -> {
      // uncaught exceptions in threads don't propagate to the main thread
      throw new RuntimeException("thread crash");
  });
  t.setUncaughtExceptionHandler((thread, ex) -> {
      System.err.println("Thread " + thread.getName() + " crashed: " + ex.getMessage());
  });
  t.start();

BEST PRACTICES
---------------
  ✅ Catch specific exceptions — not Exception or Throwable
  ✅ Log the original exception with full stack trace (use logging framework)
  ✅ Always preserve the cause: throw new MyException("msg", originalCause)
  ✅ Use try-with-resources instead of finally for resource cleanup (Java 7+)
  ✅ Never swallow exceptions silently: catch (Exception e) { } ← NEVER do this
  ❌ Don't use exceptions for control flow (expensive, unreadable)
  ❌ Don't return from finally — overwrites the try/catch return value
  ❌ Don't throw from finally — suppresses the original exception

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Does finally always execute?
A: Almost always. It executes even when an exception is not caught and propagates up,
   and even when a return statement is in the try block. The only cases where finally
   does NOT execute: System.exit() is called, the JVM crashes, or the thread is stuck
   in an infinite loop (never exits the try block).

Q: What happens if both try and finally throw an exception?
A: The exception thrown in finally SUPPRESSES the original exception from try.
   The caller only sees the finally exception; the original is lost. This is a notorious
   Java gotcha. Use try-with-resources (Java 7+) to avoid this — it properly handles
   suppressed exceptions via addSuppressed().

Q: What happens if return is in both try and finally?
A: The finally return wins. The return value from try is discarded. This is another
   reason to avoid return statements in finally blocks — it can silently mask the
   intended return value from try, making code hard to reason about.

Q: What is the order of catch block evaluation?
A: Top to bottom. The first catch whose declared type is assignable from the thrown
   exception's type is executed. If a broader catch appears before a narrower one,
   the narrower one becomes unreachable and the compiler reports an error.
