EXCEPTION BEST PRACTICES AND ANTI-PATTERNS
============================================

BEST PRACTICES
---------------

1. CATCH SPECIFIC EXCEPTIONS — NOT Exception OR Throwable
  ✅ catch (FileNotFoundException e) — handles exactly the condition you expect
  ❌ catch (Exception e) — catches NPE, IAE, ClassCastException — bugs disguised as handlers
  ❌ catch (Throwable e) — also catches OutOfMemoryError — almost never correct

  // ❌ Anti-pattern: hides bugs
  try {
      processOrder(order);
  } catch (Exception e) {
      log.error("Error", e);  // NPE bugs will be silently "handled" here
  }

  // ✅ Best practice: specific
  try {
      processOrder(order);
  } catch (OrderNotFoundException e) {
      return notFound(e.getOrderId());
  } catch (InsufficientStockException e) {
      return conflict(e.getMessage());
  }

2. ALWAYS LOG WITH FULL STACK TRACE
  ❌ log.error("Error: " + e.getMessage());   // loses stack trace — hard to debug
  ❌ log.error("Error occurred");              // no exception info at all
  ✅ log.error("Order processing failed", e); // SLF4J/Log4j will print full trace

3. PRESERVE THE CAUSE WHEN RE-THROWING
  ❌ throw new ServiceException("Failed");         // original cause lost
  ✅ throw new ServiceException("Failed", e);      // cause preserved — trace shows chain

4. USE MEANINGFUL EXCEPTION NAMES AND MESSAGES
  ❌ throw new RuntimeException("Error");
  ✅ throw new UserNotFoundException("User not found with email: " + email);
  ✅ throw new IllegalArgumentException("Page size must be between 1 and 100, got: " + size);

5. EXCEPTIONS ARE FOR EXCEPTIONAL CONDITIONS — NOT FLOW CONTROL
  ❌ Anti-pattern (expensive and semantically wrong):
    try {
        int value = Integer.parseInt(input); // throws if not a number
    } catch (NumberFormatException e) {
        value = 0; // using exception as an if statement
    }

  ✅ Best practice:
    if (input != null && input.matches("-?\\d+")) {
        int value = Integer.parseInt(input);
    } else {
        int value = 0;
    }

6. PREFER UNCHECKED FOR DOMAIN EXCEPTIONS IN MODERN CODE
  Checked exceptions force callers to handle or declare — this propagates upward
  and creates boilerplate. Modern Java (and frameworks) favor unchecked for domain
  exceptions. Use checked only when the CALLER genuinely has a meaningful recovery action.

7. DOCUMENT EXCEPTIONS IN JAVADOC
  /**
   * Finds user by ID.
   * @throws UserNotFoundException if no user exists with the given ID
   * @throws DataAccessException if the database is unavailable
   */
  public User findUser(long id) { ... }

ANTI-PATTERNS
--------------

ANTI-PATTERN 1: SWALLOWING EXCEPTIONS (THE WORST OFFENSE)
  try {
      riskyOperation();
  } catch (Exception e) {
      // do nothing ← completely silences the failure, hides bugs
  }

  // Minimal acceptable version if you truly intend to ignore:
  try {
      riskyOperation();
  } catch (Exception e) {
      log.warn("riskyOperation failed (non-critical), continuing", e);
  }

ANTI-PATTERN 2: CATCHING Exception IN APPLICATION CODE
  Makes it impossible to distinguish between expected conditions and programming errors.
  NullPointerException, ClassCastException — all caught — making bugs invisible.

ANTI-PATTERN 3: USING EXCEPTIONS FOR CONTROL FLOW
  Creating, throwing, and catching exceptions is expensive:
  - Exception construction captures a full stack trace (expensive operation)
  - JVM optimization (JIT escape analysis) can sometimes remove it — but don't rely on this
  Use if/else, Optional, or return codes for normal conditions.

ANTI-PATTERN 4: LOSING THE CAUSE
  catch (IOException e) {
      throw new ServiceException("Failed"); // ❌ e is swallowed — root cause lost
  }
  Always: throw new ServiceException("Failed", e);

ANTI-PATTERN 5: OVERUSING CHECKED EXCEPTIONS
  Checked exceptions crossing many architectural layers force every intermediate method
  to declare throws or catch-and-rethrow, polluting signatures throughout the codebase.
  Convert to unchecked at the appropriate layer boundary.

ANTI-PATTERN 6: CATCHING AND RE-THROWING THE SAME EXCEPTION WITHOUT ADDING VALUE
  catch (IOException e) {
      log.error("IO error", e);
      throw e;  // fine only if the log adds value; otherwise just let it propagate
  }
  // If you're just rethrowing unchanged, don't catch it — let it propagate naturally

ANTI-PATTERN 7: TOO BROAD throws DECLARATIONS
  public void processData() throws Exception { ... } // ← hides what actually can fail
  Be specific: throws IOException, SQLException

ANTI-PATTERN 8: FINALLY WITH RETURN OR THROW
  finally {
      return result;   // ❌ overrides try/catch return value
      // or
      throw new RuntimeException(); // ❌ suppresses original exception
  }

EXCEPTION PERFORMANCE CONSIDERATIONS
---------------------------------------
  Creating an exception is expensive because:
  - JVM fills in the full stack trace (StackTraceElement[]) at construction time
  - The deeper the call stack, the more expensive

  Options when performance matters (rare):
  1. Use a static SINGLETON exception (no per-instance stack trace):
       private static final MyException INSTANCE = new MyException();
       throw INSTANCE;  // no stack trace — only for internal "fast path" signals
  2. Override fillInStackTrace() to return 'this' (skips capture):
       @Override public Throwable fillInStackTrace() { return this; }
  3. In practice: exceptions should be truly EXCEPTIONAL — if they're on the hot path,
     you have a design problem. Use Optional, Result types, or return codes instead.

COMPARISON TABLE: GOOD vs BAD PRACTICES
-----------------------------------------
  Practice                          | Good ✅ or Bad ❌?
  ----------------------------------|----------------------------------
  catch (SpecificException e)       | ✅ Good
  catch (Exception e)               | ❌ Too broad
  log.error("msg", e)               | ✅ Preserves stack trace
  log.error(e.getMessage())         | ❌ Loses stack trace
  throw new Ex("msg", originalCause)| ✅ Preserves chain
  throw new Ex("msg")               | ❌ Loses chain
  catch (e) {} (empty catch)        | ❌ NEVER
  Use exception for if/else logic   | ❌ Anti-pattern
  Declare specific throws           | ✅ Good
  throws Exception in signature     | ❌ Too vague

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is exception swallowing and why is it dangerous?
A: Exception swallowing means catching an exception and doing nothing with it —
   empty catch block or catching and ignoring. It's dangerous because silent failures
   continue execution in a corrupted state, bugs become impossible to diagnose,
   and the system may produce wrong results with no indication of the root cause.
   At minimum, always log the exception if you decide not to rethrow it.

Q: Why shouldn't you use exceptions for flow control?
A: Two reasons: 1) Performance — constructing an exception captures a full stack trace,
   which is expensive, especially on deep call stacks. 2) Semantics — exceptions communicate
   "something went wrong." Using them for normal branching (like checking if a key exists)
   makes code harder to read and violates the principle of least surprise.

Q: What is the problem with a method declaring "throws Exception"?
A: It communicates nothing meaningful to the caller — every method in Java could potentially
   throw Exception. It forces callers to either catch Exception (too broad) or declare
   throws Exception themselves. Be specific: declare the exact exception types that can occur.

Q: Is it ever OK to catch and ignore an exception?
A: Very rarely. Cases where it might be acceptable:
   - A truly optional operation where failure has no consequence (e.g., trying to delete
     a temp file)
   - In a finally block trying to close a resource that's already closed
   Even then, log the exception at WARN/DEBUG level so that unexpected failures can be noticed.
