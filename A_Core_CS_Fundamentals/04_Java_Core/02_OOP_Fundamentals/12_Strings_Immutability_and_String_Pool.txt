STRINGS — IMMUTABILITY AND STRING POOL
========================================

STRING BASICS
-------------
  - String is a class in java.lang — NOT a primitive.
  - Represents a sequence of Unicode characters.
  - Stored internally as a char[] (pre-Java 9) or byte[] (Java 9+ with compact strings).
  - String literals are automatically interned in the String Pool.

STRING IMMUTABILITY
--------------------
Strings in Java are IMMUTABLE: once created, the character data cannot be changed.

  String s = "Hello";
  s.toUpperCase();  // does NOT change s
  s = s.toUpperCase();  // creates a new String object "HELLO"; s now points to it

WHY is String immutable?
  1. Security: Class names in ClassLoader, network hostnames — must not change.
  2. Thread Safety: Immutable objects are inherently thread-safe; no synchronization needed.
  3. String Pool efficiency: Pooling only works if strings can't be modified after sharing.
  4. HashMap key safety: hashCode is stable for the lifetime of the object.
  5. Caching: String caches its hashCode after first computation (lazy, cached).

How immutability is enforced:
  - String class is final (can't subclass to add mutation).
  - The internal char[]/byte[] field is private and final.
  - No mutating methods provided (replace, toUpperCase, etc. return new String).

STRING POOL (String Intern Pool / String Constant Pool)
--------------------------------------------------------
The JVM maintains a pool of String literals in the Heap (before Java 7: PermGen).

  String s1 = "Hello";   // stored in pool
  String s2 = "Hello";   // same pool reference returned — no new object
  s1 == s2               // TRUE — both point to same pool object

  String s3 = new String("Hello");  // FORCES a new object on heap, outside pool
  s1 == s3               // FALSE — s3 is a separate heap object
  s1.equals(s3)          // TRUE — same content

  String.intern():
    String s4 = s3.intern();  // returns the pool reference for "Hello"
    s1 == s4               // TRUE

MEMORY DIAGRAM:
  Heap: String Pool [ "Hello" ] ← s1, s2, s4 all reference this
  Heap: new String object ["Hello"] ← s3 references this (separate)

WHERE STRING POOL LIVES:
  Pre-Java 7:  PermGen (permanent generation) — fixed size, could cause OOM errors.
  Java 7+:     Heap — GC-managed, grows dynamically, less OOM risk.

== vs .equals() FOR STRINGS
-----------------------------
  ==         checks REFERENCE equality (same memory address)
  .equals()  checks VALUE equality (same character content)

  String a = "Java";
  String b = "Java";
  String c = new String("Java");

  a == b       // true  — both from pool, same reference
  a == c       // false — c is a new heap object
  a.equals(c)  // true  — same content

  ALWAYS use .equals() to compare String content.
  Use == only if you explicitly need reference identity.

COMMON PITFALL — null check:
  String s = null;
  s.equals("hello")  // NullPointerException!
  "hello".equals(s)  // false — safe: literal on left never null

  Or: Objects.equals(s, "hello")  // null-safe

STRING CONCATENATION AND PERFORMANCE
--------------------------------------
  + operator:
    String result = "Hello" + " " + "World";
    At compile time, string literal concatenation is optimized.
    At runtime with variables: compiled to StringBuilder.append().

  String s = "a";
  for (int i = 0; i < 10000; i++) {
      s = s + i;  // BAD: creates 10000 intermediate String objects on heap
  }
  // Compiler cannot optimize this loop — each iteration creates new String

  StringBuilder s = new StringBuilder("a");
  for (int i = 0; i < 10000; i++) {
      s.append(i);  // GOOD: single mutable buffer
  }
  String result = s.toString();

  Java 9+ String concatenation uses invokedynamic (StringConcatFactory) instead of
  StringBuilder for better JIT optimization, but manual StringBuilder is still best for loops.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Why is String immutable in Java?
A: 1. Security — used in ClassLoader, network code; mutation would be a vulnerability.
   2. Thread safety — can be shared across threads without synchronization.
   3. String Pool — pooling requires shared strings to never change.
   4. HashMap key safety — stable hashCode across the object's life.

Q: What is the String Pool?
A: A special area in the heap (Java 7+) where the JVM stores unique String literals.
   When you write a string literal, JVM checks the pool first; if found, returns the existing
   reference. This saves memory for commonly repeated strings.

Q: What is the difference between String s = "abc" and String s = new String("abc")?
A: "abc" — checks pool; if "abc" already there, returns same reference. No new object if pooled.
   new String("abc") — ALWAYS creates a new heap object, bypassing the pool.
   Result: two new String("abc") will have == false; two "abc" literals will have == true.

Q: Can you make String mutable?
A: No — String is final and its internal array is private/final. You can use StringBuilder
   (not thread-safe) or StringBuffer (thread-safe) for mutable character sequences.

Q: What does String.intern() do?
A: Adds the string to the pool (if not already there) and returns the canonical pool reference.
   After interning, == comparison works like .equals() for that string pair.
   Use case: deduplicating large numbers of equal strings in memory-constrained apps.
