INTERFACES vs ABSTRACT CLASSES — DEEP DIVE
===========================================

This file provides the complete nuanced comparison — essential for senior Java interviews.

QUICK SUMMARY
-------------
  Use interface when:    defining a CONTRACT / capability for unrelated classes
  Use abstract class when: sharing CODE / STATE among closely related classes

FULL FEATURE COMPARISON
------------------------
| Feature                         | Interface                         | Abstract Class                  |
|---------------------------------|-----------------------------------|---------------------------------|
| Keyword                         | interface                         | abstract class                  |
| Instantiation                   | No                                | No                              |
| Inheritance                     | implements (multiple allowed)     | extends (single only)           |
| Methods                         | abstract (default), default, static, private (Java 9+) | abstract + concrete |
| Fields                          | public static final ONLY          | Any visibility, any type        |
| Instance state                  | None                              | Yes (instance fields)           |
| Constructors                    | None                              | Yes (called via super())        |
| Access modifiers on methods     | public only (pre-Java 9)          | Any (public, protected, private)|
| Multiple inheritance            | Yes — multiple interfaces         | No — single class               |
| IS-A relationship               | Yes (type)                        | Yes (type + shared impl)        |
| Functional interface / lambda   | Yes (if 1 abstract method)        | No                              |
| Design intent                   | Capability / Contract / Role      | Shared Implementation / Template|

DEFAULT METHODS IN INTERFACES (Java 8+)
-----------------------------------------
Interfaces can now provide default implementations, blurring the line — but key differences remain:

  interface Validator<T> {
      boolean validate(T value);  // abstract — must implement

      default boolean validateAll(List<T> values) {  // default — optional override
          return values.stream().allMatch(this::validate);
      }
  }

  This allows adding behavior to interfaces WITHOUT breaking existing implementations.
  Critical for Java's backwards-compatible evolution (e.g., forEach added to Iterable).

DEFAULT METHOD CONFLICT RESOLUTION
-------------------------------------
  If two interfaces define the same default method, the implementing class MUST override:

  interface A { default void greet() { System.out.println("A"); } }
  interface B { default void greet() { System.out.println("B"); } }

  class C implements A, B {
      @Override
      public void greet() {
          A.super.greet();  // explicitly call A's or B's version
      }
  }

  Class wins over interface default:
    If a superclass has a concrete method with the same signature as an interface default method,
    the superclass method WINS — not the default method.

ABSTRACT CLASS: TEMPLATE METHOD PATTERN
-----------------------------------------
Perfect use of abstract class — define algorithm skeleton, let subclasses fill in steps:

  abstract class DataProcessor {
      // Template method — final so subclasses can't change the algorithm
      public final void process() {
          readData();
          processData();
          writeData();
          cleanup();
      }

      abstract void readData();    // subclass must implement
      abstract void processData(); // subclass must implement

      void writeData() { System.out.println("Writing data..."); }  // default impl
      void cleanup()   { System.out.println("Cleaning up..."); }   // default impl
  }

  class CSVProcessor extends DataProcessor {
      @Override void readData()    { System.out.println("Reading CSV"); }
      @Override void processData() { System.out.println("Processing CSV"); }
  }

CHOOSING BETWEEN INTERFACE AND ABSTRACT CLASS
----------------------------------------------

Scenario: Payment system

  interface Payable {          // INTERFACE — a contract/capability
      void pay(double amount);
      void refund(double amount);
  }

  abstract class BasePayment implements Payable {  // ABSTRACT CLASS — shared code
      protected String transactionId;
      protected double balance;

      protected void logTransaction(String type, double amount) {
          System.out.println(transactionId + ": " + type + " " + amount);
      }
      // pay() and refund() still abstract — subclasses implement
  }

  class CreditCardPayment extends BasePayment {
      @Override public void pay(double amount) { logTransaction("DEBIT", amount); }
      @Override public void refund(double amount) { logTransaction("CREDIT", amount); }
  }

INTERFACE WITH GENERICS AND TYPE BOUNDS
-----------------------------------------
  interface Repository<T, ID> {
      T findById(ID id);
      List<T> findAll();
      void save(T entity);
      void delete(ID id);
  }

  class UserRepository implements Repository<User, Long> {
      @Override public User findById(Long id) { ... }
      // ...
  }

MARKER INTERFACES
------------------
  Interfaces with NO methods — used as type tags:
    Serializable   — marks class as serializable
    Cloneable      — marks class as supporting clone()
    RandomAccess   — marks List as supporting O(1) random access (ArrayList)

  Annotations have largely replaced custom marker interfaces in modern Java.

FUNCTIONAL INTERFACES vs ABSTRACT CLASSES
-------------------------------------------
  Interface with single abstract method = functional interface → usable as lambda target:
    @FunctionalInterface interface Transformer<T> { T transform(T input); }
    Transformer<String> upper = s -> s.toUpperCase();

  Abstract class CANNOT be used as a lambda target, even if it has a single abstract method.

WHEN EACH IS A CODE SMELL
---------------------------
  Abstract class code smell: inheriting purely for code reuse (no true IS-A) → fragile base class
  Interface code smell: "fat interface" — too many unrelated methods in one interface → ISP violation
                        Adding fields to interface (they become public static final constants — avoid)

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Can an abstract class implement an interface without providing implementations?
A: Yes. An abstract class can implement an interface and leave some or all methods abstract.
   The first concrete subclass must then implement them.
   abstract class AbstractBase implements Runnable { }  // doesn't implement run()
   class Concrete extends AbstractBase { @Override public void run() { ... } }

Q: Can a class extend an abstract class and implement an interface simultaneously?
A: Yes — this is extremely common:
   class MyService extends AbstractService implements Comparable<MyService>, Serializable { }

Q: What was wrong with Java interfaces before Java 8?
A: Interfaces were "pure contracts" with no implementation. Adding a new method to an interface
   broke ALL existing implementations immediately. Java 8's default methods solved this by
   providing a default body — existing implementations don't need to change.

Q: Why can't an interface have instance fields?
A: Interfaces have no instance — they can't be instantiated and have no constructor to initialize
   instance state. All fields in an interface are implicitly public static final (constants).

Q: What is the key design principle for choosing interface vs abstract class?
A: Interfaces model TYPE (what you ARE: Flyable, Serializable, Comparable).
   Abstract classes model IMPLEMENTATION (what you DO: shared code, Template Method).
   When in doubt, prefer interfaces — they're more flexible (multiple inheritance, lambdas).
   Add abstract class as a convenience base implementation (e.g., AbstractList, AbstractMap).
