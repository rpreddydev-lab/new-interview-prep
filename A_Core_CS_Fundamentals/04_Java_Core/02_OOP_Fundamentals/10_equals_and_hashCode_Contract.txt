equals() AND hashCode() CONTRACT — DEEP DIVE
=============================================

WHY THIS MATTERS
----------------
The equals/hashCode contract is one of the most important (and most broken) contracts in Java.
Violating it causes SILENT BUGS in HashMap, HashSet, Hashtable, LinkedHashMap, and any code
that relies on object identity via hashing.

THE CONTRACT (from java.lang.Object Javadoc)
---------------------------------------------
1. equals() must be:
   a. Reflexive:   x.equals(x) == true
   b. Symmetric:   x.equals(y) == y.equals(x)
   c. Transitive:  x.equals(y) && y.equals(z) → x.equals(z) == true
   d. Consistent:  repeated calls return same result (no external state change)
   e. Null-safe:   x.equals(null) == false (never throws NPE)

2. hashCode() must be:
   a. Consistent:  same value on repeated calls if object unchanged
   b. Compatible:  if x.equals(y), then x.hashCode() == y.hashCode()
   c. Collisions OK: x.hashCode() == y.hashCode() does NOT require x.equals(y)

WHAT HAPPENS WHEN YOU ONLY OVERRIDE equals() (without hashCode)
----------------------------------------------------------------
  Person p1 = new Person("Alice", 30);
  Person p2 = new Person("Alice", 30);

  p1.equals(p2)  // true — you overrode equals correctly
  p1.hashCode() != p2.hashCode()  // different! default hashCode = memory address

  Set<Person> set = new HashSet<>();
  set.add(p1);
  set.contains(p2);   // FALSE! — looks in wrong bucket (wrong hashCode)

  Map<Person, String> map = new HashMap<>();
  map.put(p1, "Engineer");
  map.get(p2);   // NULL! — hashCode mismatch → bucket miss

CORRECT IMPLEMENTATION — MANUAL
---------------------------------
  @Override
  public boolean equals(Object o) {
      if (this == o) return true;           // identity shortcut
      if (!(o instanceof Person)) return false;  // type + null check
      Person other = (Person) o;
      return age == other.age
          && Objects.equals(name, other.name);  // null-safe String compare
  }

  @Override
  public int hashCode() {
      return Objects.hash(name, age);  // consistent with equals fields
  }

USING instanceof vs getClass() IN equals()
-------------------------------------------
  Approach 1: instanceof (recommended by Joshua Bloch / Effective Java)
    if (!(o instanceof Person)) return false;
    - Allows subclasses to be equal to parent.
    - Symmetric rule may be violated if subclass overrides equals differently.
    - Use when subclass doesn't add meaningful equality fields.

  Approach 2: getClass() (strict)
    if (o == null || getClass() != o.getClass()) return false;
    - Only same exact class can be equal.
    - Symmetric always holds.
    - Use when subclasses should not be considered equal to parent.

  Best practice: use instanceof with final class, or getClass() if inheritance is a concern.

RECORDS HANDLE THIS AUTOMATICALLY (Java 16+)
----------------------------------------------
  record Person(String name, int age) {}
  // JVM auto-generates:
  //   equals() — compares all record components
  //   hashCode() — from all components
  //   toString() — canonical representation

IMMUTABILITY + hashCode
------------------------
  If you store an object in a HashSet or as a HashMap key, you MUST NOT mutate the fields
  used in hashCode/equals while it's in the collection.

  Person p = new Person("Alice", 30);
  Set<Person> set = new HashSet<>();
  set.add(p);
  p.setName("Bob");  // mutable — dangerous!
  set.contains(p);   // FAILS — hash computed for "Bob", but p is in "Alice" bucket

  Best practice: use immutable objects as Map keys / Set elements.
  If mutable, use only fields that won't change as the key.

COMMON VIOLATIONS AND THEIR CONSEQUENCES
-----------------------------------------
  Violation                       | Consequence
  --------------------------------|------------------------------------------
  Override equals, not hashCode   | HashSet/HashMap broken (duplicates, misses)
  Non-symmetric equals            | a.contains(b) != b.contains(a) in collections
  Mutable key fields              | "Lost" entries in HashMap after mutation
  equals throws NPE for null      | NullPointerException when map contains null
  hashCode returns constant (0)   | Works correctly but O(n) performance (all in one bucket)

HASHCODE QUALITY
-----------------
  A good hashCode distributes objects uniformly across buckets to minimize collisions.
  Returning a constant (return 0) is technically legal (contract not violated) but
  makes every HashMap O(n) — all keys go to bucket 0.

  Objects.hash(f1, f2) uses 31 as multiplier (prime number reduces collision probability).

  IDE-generated hashCode (IntelliJ/Eclipse) is usually good enough.
  For critical performance paths, consider Guava's Hashing or custom XOR-based hashing.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What happens if two objects have the same hashCode but are not equal?
A: This is a hash COLLISION. It's perfectly legal — the contract doesn't prohibit it.
   In a HashMap, both objects will be placed in the same bucket, then equals() is used
   to distinguish them. Performance degrades but correctness is maintained.
   (In Java 8+, HashMap buckets convert to balanced BST at 8 entries to handle collisions.)

Q: What happens if two equal objects have different hashCodes?
A: CONTRACT VIOLATION. HashMap/HashSet behavior is UNDEFINED and broken. Objects will be
   placed in different buckets — contains/get will fail even for "equal" objects.

Q: How do you correctly implement hashCode for a class with multiple fields?
A: Use Objects.hash(field1, field2, field3) — it uses the same fields you use in equals.
   Or compute manually: int result = 31 * field1.hashCode() + field2.hashCode() + ...

Q: Can two different strings have the same hashCode?
A: Yes. String.hashCode() is a polynomial rolling hash — collisions exist (e.g.,
   "FB" and "Ea" have the same hashCode in Java's default implementation).
   HashMap handles this via equals() comparison in the bucket.
