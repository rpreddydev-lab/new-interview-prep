METHOD OVERLOADING vs METHOD OVERRIDING
========================================

OVERVIEW
--------
Both involve methods with the same name, but they are fundamentally different mechanisms:

  Overloading: same name, DIFFERENT signature — resolved at COMPILE TIME (static dispatch)
  Overriding:  same name, SAME signature — resolved at RUNTIME (dynamic dispatch)

METHOD OVERLOADING
------------------
Defining multiple methods in the SAME CLASS with the same name but different parameter lists.

  class Printer {
      void print(int n)    { System.out.println("int: " + n); }
      void print(double d) { System.out.println("double: " + d); }
      void print(String s) { System.out.println("String: " + s); }
      void print(int a, int b) { System.out.println("two ints: " + a + ", " + b); }
  }

Rules:
  ✅ Must differ in: number of parameters, type of parameters, or order of types.
  ❌ Return type alone does NOT constitute overloading (compile error).
  ❌ Throwing different exceptions alone doesn't count either.
  ✅ Access modifiers can be different.
  ✅ Can be in same class or subclass (inheritance-based overloading).

Resolved at compile time — compiler picks the best-matching method by argument types.

Widening in overloading (automatic type promotion):
  print(5)     → matches print(int)
  print(5L)    → matches print(long) if exists, else widens to print(double)
  print(5.0f)  → matches print(float), else widens to print(double)

Autoboxing and varargs priority:
  1. Exact match (no widening, no boxing)
  2. Widening primitive conversion
  3. Autoboxing
  4. Varargs

METHOD OVERRIDING
-----------------
Subclass provides its own implementation of a method inherited from the superclass.

  class Animal {
      public void makeSound() { System.out.println("..."); }
  }
  class Dog extends Animal {
      @Override
      public void makeSound() { System.out.println("Woof!"); }
  }
  class Cat extends Animal {
      @Override
      public void makeSound() { System.out.println("Meow!"); }
  }

  Animal a = new Dog();
  a.makeSound();  // "Woof!" — runtime type is Dog

Rules:
  ✅ Same method name.
  ✅ Same parameter list (exactly).
  ✅ Return type: same OR covariant (subtype).
  ✅ Access: same or more permissive (can't narrow).
  ✅ Checked exceptions: can throw fewer/narrower, not more/broader.
  ❌ Cannot override: final, static, or private methods.
  ✅ Use @Override — compiler verifies the contract.

COMPARISON TABLE
-----------------
| Feature              | Overloading                    | Overriding                         |
|----------------------|--------------------------------|------------------------------------|
| Where                | Same class (or subclass)       | Subclass redefines superclass method|
| Signature            | Must DIFFER                    | Must be IDENTICAL                  |
| Return type          | Can differ                     | Same or covariant                  |
| Resolution time      | Compile time (static)          | Runtime (dynamic dispatch)         |
| Polymorphism type    | Compile-time                   | Runtime                            |
| @Override            | Not used                       | Should always use                  |
| Access modifier      | Can be anything                | Can only widen, not narrow         |
| static methods       | Can be overloaded              | Cannot be overridden (hidden)      |
| private methods      | Can be overloaded              | Cannot be overridden               |
| Inheritance required | No                             | Yes                                |

TRICKY CASES
------------
1. Overloading with null:
     void process(String s) { ... }
     void process(Object o) { ... }
     process(null);  // calls process(String) — most specific type wins

2. Overloading and autoboxing:
     void display(Integer i) { ... }
     void display(int i) { ... }
     display(42);  // calls display(int) — exact primitive match before autoboxing

3. Overriding and covariant return type:
     class Animal { Animal clone() { return new Animal(); } }
     class Dog extends Animal {
         @Override Dog clone() { return new Dog(); }  // covariant — Dog IS-A Animal
     }

4. @Override on interface implementation:
     class MyList implements List<String> {
         @Override public int size() { return 0; }  // overriding interface method
     }

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between method overloading and overriding?
A: Overloading = same class, different parameter signatures, resolved at compile time.
   Overriding = subclass redefines inherited method, same signature, resolved at runtime via
   dynamic dispatch. Overloading is compile-time (static) polymorphism; overriding is runtime
   (dynamic) polymorphism.

Q: Can you overload a method by changing only the return type?
A: No. The compiler cannot distinguish methods by return type alone — ambiguity arises when
   the caller doesn't assign the result. Compile error.

Q: Can a static method be overridden?
A: No. Static methods are resolved at compile time by the reference type, not by the actual
   object type (no dynamic dispatch). Declaring a same-name static method in a subclass is
   METHOD HIDING, not overriding.

Q: What happens when you call an overloaded method with a null argument?
A: The compiler picks the most specific applicable type. If there's ambiguity (e.g., process(String)
   and process(Integer) — both are valid for null), a compile error "ambiguous method call" occurs.
   To resolve: cast the null: process((String) null).

Q: Does overriding change the method binding to late (dynamic) binding?
A: Yes. Instance method calls in Java use LATE binding (virtual dispatch) by default.
   The JVM looks up the actual runtime type and calls that class's implementation.
   Only static, private, and final methods use early (compile-time) binding.
