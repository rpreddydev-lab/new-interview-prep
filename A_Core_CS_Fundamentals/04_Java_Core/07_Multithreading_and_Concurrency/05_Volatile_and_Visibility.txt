VOLATILE AND VISIBILITY
=========================

THE VISIBILITY PROBLEM
------------------------
  In a multi-core system, each CPU core has its own cache (L1/L2/L3).
  When a thread writes to a variable, the new value may sit in the CPU's cache
  and not be immediately flushed to main memory.
  Other threads running on different cores may still see the OLD (stale) value.

  Example:
    public class StopExample {
        private boolean stopped = false;

        public void stop() { stopped = true; }

        public void run() {
            while (!stopped) {  // ← may NEVER see stopped = true!
                doWork();
            }
        }
    }

  Without visibility guarantees, the JIT compiler may also hoist `stopped` into
  a register and never re-read it from memory — the loop runs forever.

THE volatile KEYWORD
---------------------
  Declaring a field volatile guarantees:
  1. VISIBILITY: Every read of the field sees the most recently written value
     (reads go to main memory, writes flush to main memory immediately)
  2. ORDERING: Writes to volatile fields happen-before subsequent reads by other threads
     (prevents reordering of accesses around the volatile operation)

  volatile does NOT guarantee atomicity for compound operations (e.g., i++).

  // Fix the stop example:
  private volatile boolean stopped = false;
  // Now: all threads always see the latest value of stopped

HOW volatile WORKS INTERNALLY
--------------------------------
  - Writes: The JVM inserts a "store barrier" — writes to the volatile variable
    and all preceding writes are flushed to main memory before the store.
  - Reads: The JVM inserts a "load barrier" — the volatile variable is read from
    main memory, not from CPU cache. All subsequent reads see the current state.
  - Prevents instruction reordering across the volatile access point.

volatile vs synchronized VISIBILITY
--------------------------------------
  synchronized also provides visibility (changes made in a block become visible
  to any thread that subsequently synchronizes on the same lock).
  volatile is lighter — no lock, no mutual exclusion — just visibility and ordering.

WHEN TO USE volatile
---------------------
  ✅ Simple boolean flags for thread control (stop/started/initialized):
    private volatile boolean running = true;

  ✅ Lazy initialization flag (not double-checked locking — use that for objects):
    private volatile boolean initialized = false;

  ✅ Singleton double-checked locking (see below)

  ✅ Published object references — when one thread writes a reference and others read:
    private volatile Config config;  // ensure readers see non-null, fully constructed Config

  ❌ Compound operations like count++ (three steps: read, increment, write) — NOT atomic
  ❌ When you need mutual exclusion — use synchronized or ReentrantLock

VOLATILE AND DOUBLE-CHECKED LOCKING
--------------------------------------
  The classic (broken without volatile) singleton pattern:

  // ❌ BROKEN without volatile in Java 5+:
  public class Singleton {
      private static Singleton instance;
      public static Singleton getInstance() {
          if (instance == null) {            // check 1 — no sync
              synchronized (Singleton.class) {
                  if (instance == null) {    // check 2 — under sync
                      instance = new Singleton();  // can be partially published!
                  }
              }
          }
          return instance;
      }
  }
  // Problem: construction of Singleton is not atomic.
  // Step 1: allocate memory
  // Step 2: write reference to `instance` ← reordering can put this BEFORE step 3!
  // Step 3: initialize fields
  // Another thread sees non-null `instance` but a partially constructed object.

  // ✅ CORRECT with volatile:
  public class Singleton {
      private static volatile Singleton instance;  // volatile prevents reordering
      public static Singleton getInstance() {
          if (instance == null) {
              synchronized (Singleton.class) {
                  if (instance == null) {
                      instance = new Singleton();  // fully constructed before visible
                  }
              }
          }
          return instance;
      }
  }
  // volatile ensures: write to `instance` happens AFTER full construction.

  // ✅ Preferred alternative — initialization-on-demand holder (no volatile needed):
  public class Singleton {
      private Singleton() {}
      private static class Holder {
          static final Singleton INSTANCE = new Singleton();  // class loading is thread-safe
      }
      public static Singleton getInstance() { return Holder.INSTANCE; }
  }

VOLATILE vs synchronized vs Atomic
-------------------------------------
  Aspect               | volatile           | synchronized         | AtomicInteger etc.
  ---------------------|--------------------|-----------------------|---------------------
  Visibility           | ✅ Yes             | ✅ Yes               | ✅ Yes
  Atomicity            | ❌ No              | ✅ Yes (whole block)  | ✅ Yes (single op)
  Mutual exclusion     | ❌ No              | ✅ Yes               | ❌ No (CAS-based)
  Compound operations  | ❌ Not safe        | ✅ Safe              | ✅ incrementAndGet()
  Performance          | Very fast (no lock)| Slower (lock/unlock)  | Fast (CAS, no lock)
  Use case             | Flags, references  | Critical sections    | Counters, accumulators

MEMORY MODEL (BRIEF)
---------------------
  The Java Memory Model (JMM) defines rules for when writes by one thread are
  guaranteed to be visible to reads by another. The key principle is
  "happens-before" (see file 20 for full coverage):

  - A volatile write happens-before any subsequent volatile read of the same variable
  - An action in a thread happens-before any action in a thread that joins() it
  - All actions in a thread happen-before any other thread successfully returns from join()

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What problem does volatile solve?
A: Visibility. Without volatile, changes to a shared variable may remain in a CPU cache
   and not be seen by threads on other cores. The JIT compiler may also optimize away
   repeated reads of the variable. volatile forces every read to go to main memory and
   every write to be flushed immediately, ensuring all threads see up-to-date values.

Q: Does volatile provide atomicity?
A: Only for single read or write operations on variables that fit in 32 bits (or 64-bit
   volatile longs/doubles on 64-bit JVMs). It does NOT make compound operations atomic.
   For example, volatile int i; i++ is still three non-atomic operations (read, increment,
   write). Use AtomicInteger.incrementAndGet() or synchronized for compound operations.

Q: Why is volatile needed in double-checked locking?
A: Without volatile, the JIT or CPU can reorder the steps of object construction. A thread
   could write the object reference to the field BEFORE all fields of the object are
   initialized (steps can be reordered for performance). Another thread checking for
   non-null would then see a partially constructed object. volatile prevents this reordering
   by ensuring the write to the reference field happens only after full construction.

Q: What is the difference between volatile and synchronized?
A: synchronized provides both visibility AND mutual exclusion (only one thread in the
   block at a time). volatile provides only visibility (and ordering) — no mutual
   exclusion. volatile is suitable for flags and single reference publications where no
   compound operation is needed. synchronized is needed for any read-modify-write
   operations on shared state.
