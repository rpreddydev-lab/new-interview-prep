SYNCHRONIZATION: THE synchronized KEYWORD
==========================================

THE NEED FOR SYNCHRONIZATION
------------------------------
  Without synchronization, when two threads read and write shared data:
  1. Thread A reads balance = 100
  2. Thread B reads balance = 100
  3. Thread A writes balance = 100 + 50 = 150
  4. Thread B writes balance = 100 + 30 = 130  ← overwrites A's write — LOST UPDATE!

  Race condition: final balance should be 180, but it is 130.
  The compound operation (read-modify-write) is NOT atomic.

INTRINSIC LOCKS (MONITORS)
----------------------------
  Every Java object has an intrinsic lock (also called monitor lock or mutex).
  synchronized uses this lock to enforce mutual exclusion.
  - Only ONE thread can hold an object's intrinsic lock at a time.
  - Other threads attempting to enter a synchronized block on the same object BLOCK.
  - The lock is released when the synchronized block exits (normally or via exception).

SYNCHRONIZED INSTANCE METHOD
------------------------------
  Locks on `this` — the calling object's intrinsic lock:

  public class BankAccount {
      private int balance;

      public synchronized void deposit(int amount) {
          balance += amount;
      }

      public synchronized void withdraw(int amount) {
          if (balance >= amount) balance -= amount;
      }

      public synchronized int getBalance() {
          return balance;
      }
  }

  // Two threads calling deposit() on the SAME BankAccount instance will serialize.
  // Two threads calling deposit() on DIFFERENT BankAccount instances do NOT contend.

SYNCHRONIZED STATIC METHOD
----------------------------
  Locks on the CLASS object (Class<BankAccount>.class):

  public class Counter {
      private static int count = 0;

      public static synchronized void increment() {
          count++;  // protected by Counter.class lock
      }
  }

  All threads calling any static synchronized method of Counter contend on the same lock.

SYNCHRONIZED BLOCK (FINE-GRAINED)
------------------------------------
  Lock only the minimum code — reduce contention by shrinking the critical section:

  public class Cache {
      private final Map<String, Object> store = new HashMap<>();
      private final Object lock = new Object();  // dedicated lock object

      public Object get(String key) {
          synchronized (lock) {
              return store.get(key);
          }
      }

      public void put(String key, Object value) {
          synchronized (lock) {
              store.put(key, value);
          }
      }
  }

  // Using separate locks for reads and writes (manual separation):
  private final Object readLock = new Object();
  private final Object writeLock = new Object();
  // ← NOTE: This doesn't actually provide safe concurrent reads; use ReadWriteLock instead

REENTRANT LOCKING
------------------
  Intrinsic locks in Java are REENTRANT — a thread that already holds a lock
  can re-enter any synchronized block that uses the same lock without blocking itself.
  This prevents deadlock when synchronized methods call other synchronized methods.

  public synchronized void methodA() {
      methodB();  // safe — same thread already owns the lock
  }

  public synchronized void methodB() {
      // no deadlock even though methodA holds the lock
  }

WHAT synchronized GUARANTEES
------------------------------
  1. Mutual exclusion — only one thread executes the synchronized block at a time
  2. Visibility — changes made inside a synchronized block are visible to all
     threads that subsequently synchronize on the SAME lock
  3. Atomicity — compound actions within the block are protected from interleaving

  What synchronized does NOT guarantee:
  - It cannot prevent deadlock if multiple locks are used in inconsistent order
  - It cannot prevent Thread.stop() (deprecated)

LOCK SCOPE COMPARISON
-----------------------
  Scope                    | Lock Object         | Granularity
  -------------------------|---------------------|-----------------------------
  Synchronized instance    | this                | Per-instance
  method                   |                     |
  Synchronized static      | ClassName.class     | Per-class (global)
  method                   |                     |
  Synchronized block       | Explicit object     | Configurable — most flexible
  on field object          |                     |

COMMON PITFALL: SYNCHRONIZING ON WRONG OBJECT
-----------------------------------------------
  // ❌ Synchronizing on a local variable — useless! Each thread sees its own lock.
  public void bad() {
      Object lock = new Object(); // different object each call
      synchronized (lock) { /* no mutual exclusion */ }
  }

  // ❌ Synchronizing on a String literal — dangerous! String literals are pooled.
  // Multiple, unrelated components might synchronize on the same interned String.
  synchronized ("shared-key") { ... }  // Don't do this

  // ✅ Synchronize on a private final object field:
  private final Object lock = new Object();
  synchronized (lock) { ... }

  // ✅ Or synchronize on `this` (instance method):
  public synchronized void method() { ... }

SYNCHRONIZED vs LOCK OBJECTS (ReentrantLock)
----------------------------------------------
  Aspect                    | synchronized             | ReentrantLock
  --------------------------|--------------------------|------------------------------
  Syntax                    | Built-in keyword         | java.util.concurrent.locks
  Lock release              | Auto (block exit)        | Must call unlock() in finally
  Timeout attempt           | No                       | tryLock(timeout, unit)
  Interruptible wait        | No                       | lockInterruptibly()
  Fair scheduling           | No                       | new ReentrantLock(true)
  Multiple conditions       | One condition per monitor| Multiple Condition objects
  Readability               | Simple                   | More verbose but more control

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is a race condition and how does synchronized prevent it?
A: A race condition occurs when the outcome of a program depends on the timing of threads
   accessing shared data. synchronized prevents this by ensuring that only one thread
   can execute the protected code block at a time (mutual exclusion). It also ensures
   visibility — changes made in a synchronized block are flushed to main memory and
   visible to other threads that subsequently synchronize on the same lock.

Q: What is the difference between a synchronized instance method and a synchronized block?
A: A synchronized instance method locks on `this` (the entire object). A synchronized block
   lets you choose WHAT to lock on (any object reference) and which exact lines of code to
   protect. Synchronized blocks enable finer-grained locking — you only protect the minimum
   critical section — which reduces contention and improves throughput.

Q: What does it mean that Java locks are reentrant?
A: A thread that already holds an intrinsic lock can re-acquire it without blocking itself.
   This is called reentrancy. It allows synchronized methods to call other synchronized
   methods on the same object without deadlocking. Without reentrancy, methodA() calling
   synchronized methodB() on the same object (where A already holds the lock) would deadlock.

Q: Can two threads execute different synchronized methods on the same object simultaneously?
A: No. All synchronized instance methods of an object share the SAME intrinsic lock (this).
   If Thread A is in deposit() (synchronized), Thread B trying to enter withdraw() (also
   synchronized) on the same object will BLOCK until Thread A releases the lock.
