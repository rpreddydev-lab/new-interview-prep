ATOMIC VARIABLES AND CAS (COMPARE-AND-SWAP)
=============================================

THE PROBLEM WITH i++
---------------------
  int i = 0;
  i++;  // looks atomic — actually 3 CPU instructions:
        // LOAD  i into register
        // ADD   1
        // STORE result back to i

  If two threads execute i++ concurrently, both may read 0, both compute 1,
  and both write 1 — final value is 1 instead of 2. Race condition.

  synchronized fixes this but introduces lock overhead and potential contention.

COMPARE-AND-SWAP (CAS)
-----------------------
  CAS is a hardware instruction (CMPXCHG on x86) that atomically:
  1. Reads a memory location
  2. Compares it to an expected value
  3. If equal — writes a new value, returns success
  4. If not equal — does nothing, returns failure (the current value changed)

  This is the basis for lock-free programming — retrying until the CAS succeeds.

  Pseudo-code:
    boolean compareAndSwap(int* address, int expected, int newValue) {
        atomic {
            if (*address == expected) { *address = newValue; return true; }
            return false;
        }
    }

  Why better than a lock?
  - No thread is ever blocked (threads retry instead of sleeping)
  - Avoids context-switch overhead
  - No deadlock possible
  - Works best under low-to-medium contention

ATOMIC CLASSES IN java.util.concurrent.atomic
----------------------------------------------
  AtomicInteger     — int with atomic operations
  AtomicLong        — long with atomic operations
  AtomicBoolean     — boolean with atomic operations
  AtomicReference<V>— object reference with atomic operations
  AtomicIntegerArray— array of ints with per-element atomic operations
  AtomicLongArray   — array of longs with per-element atomic ops
  AtomicReferenceArray<E> — array of references with atomic ops

  Java 8+:
  LongAdder         — high-throughput counter (striped — see below)
  LongAccumulator   — generalized accumulator with custom binary operator
  DoubleAdder / DoubleAccumulator

KEY AtomicInteger METHODS
---------------------------
  Method                          | Description
  --------------------------------|---------------------------------------------
  get()                           | Read current value
  set(int)                        | Set value
  getAndSet(int)                  | Atomically set, return OLD value
  incrementAndGet()               | ++i (atomic)
  getAndIncrement()               | i++ (atomic)
  decrementAndGet()               | --i (atomic)
  addAndGet(int delta)            | += delta, return new value
  compareAndSet(expected, update) | CAS: if current==expected, set update, return true/false
  compareAndExchange(exp, update) | Like CAS but returns the WITNESS value (Java 9+)
  updateAndGet(IntUnaryOperator)  | Atomically apply function, return new value
  accumulateAndGet(int, IntBinaryOperator) — apply operator with given value

  AtomicInteger counter = new AtomicInteger(0);
  int prev = counter.getAndIncrement();  // thread-safe i++
  int curr = counter.incrementAndGet();  // thread-safe ++i
  boolean success = counter.compareAndSet(5, 10);  // if 5, set to 10

ATOMIC REFERENCE — COMPARE-AND-SWAP ON OBJECTS
-------------------------------------------------
  AtomicReference<Config> configRef = new AtomicReference<>(initialConfig);

  // Atomic update pattern (retry loop):
  Config current, updated;
  do {
      current = configRef.get();
      updated = new Config(current.getHost(), newPort);  // immutable objects ideal
  } while (!configRef.compareAndSet(current, updated));

  // Java 8+: updateAndGet with lambda
  configRef.updateAndGet(cfg -> cfg.withPort(newPort));

ABA PROBLEM
------------
  CAS has a subtle issue: if a value changes A→B→A, the CAS sees 'A' and thinks
  nothing changed, but the object was replaced (could have different identity/content).

  Solution: AtomicStampedReference — stores value + integer "stamp" (version number)
    AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
    int[] stampHolder = new int[1];
    String current = ref.get(stampHolder);  // gets value AND current stamp
    // compareAndSet checks BOTH value AND stamp:
    ref.compareAndSet("A", "B", stampHolder[0], stampHolder[0] + 1);

  AtomicMarkableReference — value + boolean mark (simpler than stamp)

LongAdder — HIGH-THROUGHPUT COUNTING
--------------------------------------
  Under high contention, many threads CAS-ing the same AtomicLong causes cache-line
  bouncing (each CAS causes the cache line to ping-pong between CPU caches).

  LongAdder solves this with STRIPING — maintains an array of separate counters,
  each on a different cache line. Threads increment different cells, reducing contention.
  sum() aggregates all cells. Accurate only eventually (not a consistent snapshot under writes).

  LongAdder counter = new LongAdder();
  counter.increment();         // thread-safe, near-zero contention
  counter.add(5);
  long total = counter.sum();  // snapshot (may not be perfectly consistent under concurrent adds)
  counter.reset();
  long sumAndReset = counter.sumThenReset();

  Use LongAdder over AtomicLong for high-frequency increment-only counters (metrics, stats).
  Use AtomicLong when you need compareAndSet or need a consistent snapshot.

WHEN TO USE WHICH
------------------
  Tool                   | Use when
  ---------------------- |--------------------------------------------------
  synchronized           | Multiple related state changes (compound updates)
  volatile               | Single flag or reference (visibility only)
  AtomicInteger/Long     | Single field, CAS-based update, medium contention
  AtomicReference        | Single object reference, CAS update pattern
  LongAdder              | High-frequency counters, throughput > consistency
  AtomicStampedReference | Need CAS without ABA problem

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is CAS (Compare-And-Swap) and how do Atomic classes use it?
A: CAS is a hardware-level atomic instruction that reads a value, compares it to an
   expected value, and writes a new value only if the comparison succeeds — all in one
   uninterruptible step. Atomic classes like AtomicInteger use CAS (via sun.misc.Unsafe
   or VarHandle in Java 9+) to implement lock-free thread-safe operations. Threads retry
   the CAS in a loop until it succeeds, avoiding lock overhead and context switches.

Q: What is the ABA problem and how is it solved?
A: The ABA problem occurs when a value changes A→B→A between a CAS read and attempt.
   The CAS sees 'A' and thinks the value hasn't changed, proceeding incorrectly.
   AtomicStampedReference solves this by pairing each value with an integer stamp
   (version number). Both value AND stamp must match for the CAS to succeed,
   so A→B→A changes are detectable through the changing stamp.

Q: When would you choose LongAdder over AtomicLong?
A: LongAdder is better for high-throughput counters under heavy contention because it
   uses striping — multiple counters on different cache lines, one per thread (roughly),
   aggregated by sum(). AtomicLong is better when you need compareAndSet, need a
   consistent point-in-time snapshot under concurrent modification, or when contention
   is low (single-threaded or rarely concurrent) where LongAdder's overhead is unnecessary.
