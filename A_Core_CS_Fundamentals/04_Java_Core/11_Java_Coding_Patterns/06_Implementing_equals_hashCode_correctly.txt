IMPLEMENTING equals() AND hashCode() CORRECTLY
================================================

PURPOSE
--------
  Correctly overriding equals() and hashCode() is foundational to using objects in:
  - HashMap/HashSet (object as key or element)
  - ArrayList.contains(), List.remove(Object)
  - Any algorithm relying on object equality
  - Assertions in unit tests (assertEquals)

  Violating the contracts causes silent bugs: objects that "equal" each other can't be
  found in a HashMap; HashSet accepts "duplicates" — bugs that are very hard to diagnose.

THE equals() CONTRACT
----------------------
  From Object Javadoc (must hold for all non-null x, y, z):
  1. Reflexive:  x.equals(x) == true
  2. Symmetric:  x.equals(y) iff y.equals(x)
  3. Transitive: if x.equals(y) && y.equals(z) → x.equals(z)
  4. Consistent: multiple calls return same result (no state change)
  5. Non-null:   x.equals(null) == false (NEVER throw NPE)

THE hashCode() CONTRACT
------------------------
  1. If x.equals(y) → x.hashCode() == y.hashCode() (REQUIRED)
  2. If !x.equals(y) → hashCodes MAY differ (not required, but desired for performance)
  3. Consistent: same object, same result during one JVM run

  Breaking rule 1: object can't be found in HashMap/HashSet after insertion.
  A "perfect" hashCode (rule 2 always violated) is fine but degrades HashMap to O(n).

SIMPLE VALUE OBJECT EXAMPLE
-----------------------------
  public final class Point {
      private final int x;
      private final int y;

      public Point(int x, int y) {
          this.x = x;
          this.y = y;
      }

      @Override
      public boolean equals(Object o) {
          // 1. Reference equality fast path
          if (this == o) return true;
          // 2. Null check + type check (pattern matching instanceof — Java 16+)
          if (!(o instanceof Point p)) return false;
          // 3. Field-by-field comparison
          return x == p.x && y == p.y;
      }

      @Override
      public int hashCode() {
          return Objects.hash(x, y);  // combines field hashes via 31-multiplier polynomial
      }
  }

COMPLEX OBJECT EXAMPLE
------------------------
  public final class Order {
      private final String orderId;      // String (nullable? — let's say non-null)
      private final Customer customer;   // Object reference
      private final BigDecimal total;    // BigDecimal — use compareTo for equality!
      private final LocalDate orderDate;
      private final List<String> items;  // Collection

      public Order(String orderId, Customer customer, BigDecimal total,
                   LocalDate orderDate, List<String> items) {
          this.orderId   = Objects.requireNonNull(orderId);
          this.customer  = Objects.requireNonNull(customer);
          this.total     = Objects.requireNonNull(total);
          this.orderDate = Objects.requireNonNull(orderDate);
          this.items     = List.copyOf(Objects.requireNonNull(items));
      }

      @Override
      public boolean equals(Object o) {
          if (this == o) return true;
          if (!(o instanceof Order other)) return false;
          return orderId.equals(other.orderId)
              && customer.equals(other.customer)
              && total.compareTo(other.total) == 0   // BigDecimal: use compareTo, not equals!
              && orderDate.equals(other.orderDate)    // (BigDecimal.equals considers scale)
              && items.equals(other.items);           // List.equals: element-by-element
      }

      @Override
      public int hashCode() {
          // BigDecimal: use stripTrailingZeros() + hashCode to be consistent with compareTo
          return Objects.hash(
              orderId,
              customer,
              total.stripTrailingZeros(),   // normalize before hashing
              orderDate,
              items
          );
      }
  }

  // BigDecimal pitfall:
  new BigDecimal("2.0").equals(new BigDecimal("2.00"))   // FALSE — different scale!
  new BigDecimal("2.0").compareTo(new BigDecimal("2.00")) // 0 — equal
  // Always use compareTo for BigDecimal numeric equality.
  // For hashCode, normalize with stripTrailingZeros() so 2.0 and 2.00 have the same hash.

HANDLING INHERITANCE
---------------------
  Equals across inheritance hierarchies is tricky. The Liskov Substitution Principle (LSP)
  conflicts with a correct symmetric equals when adding state in a subclass.

  class Point { int x, y; ... }
  class ColorPoint extends Point { Color color; ... }
  // ColorPoint.equals(Point): symmetric is IMPOSSIBLE if both compare color and x/y.

  Solutions:
  1. Use getClass() instead of instanceof — strict type check (breaks LSP but symmetric):
     if (o == null || getClass() != o.getClass()) return false;
     — Pro: symmetric. Con: violates Liskov (colorPoint.equals(point) is false even if x,y match)

  2. Composition over inheritance (Effective Java recommendation):
     class ColorPoint { private final Point point; private final Color color; }
     Avoids the problem entirely; equals only across the same class.

  3. If equals() is already correct in a superclass and the subclass adds NO new state,
     you can inherit equals(). Example: AbstractList.equals() compares element by element —
     ArrayList and LinkedList instances can be equal.

USING OBJECTS UTILITY CLASS
-----------------------------
  Objects.equals(a, b)     — null-safe equals; returns true if both null, false if one null
  Objects.hash(f1, f2, ...) — convenience for hashCode; uses Arrays.hashCode internally
  Objects.requireNonNull(x) — throws NullPointerException with message if null
  Objects.deepEquals(a, b)  — for arrays (delegates to Arrays.deepEquals)

  @Override
  public boolean equals(Object o) {
      if (!(o instanceof MyClass other)) return false;
      return Objects.equals(nullableField, other.nullableField)  // null-safe
          && primitiveField == other.primitiveField;
  }

  @Override
  public int hashCode() {
      return Objects.hash(nullableField, primitiveField);
  }

RECORD — AUTO-GENERATED equals/hashCode
-----------------------------------------
  Java 16+ records auto-generate equals(), hashCode(), and toString() from all components.

  record Point(int x, int y) {}
  // equals(): compares x and y for equality
  // hashCode(): based on x and y
  // toString(): "Point[x=3, y=4]"

  Components that are arrays: arrays use reference equality by default even in records!
  For array components, override equals() and hashCode() manually:
  record Matrix(int[][] data) {
      @Override public boolean equals(Object o) {
          if (!(o instanceof Matrix m)) return false;
          return Arrays.deepEquals(data, m.data);
      }
      @Override public int hashCode() { return Arrays.deepHashCode(data); }
  }

LOMBOK @EqualsAndHashCode
--------------------------
  @EqualsAndHashCode          — generates equals() and hashCode() from all fields
  @EqualsAndHashCode(of = {"id"})            — only use id field
  @EqualsAndHashCode(exclude = {"password"}) — exclude sensitive fields
  @EqualsAndHashCode(callSuper = true)       — include superclass fields

  @Data (includes @EqualsAndHashCode + @Getter + @Setter + @ToString + @RequiredArgsConstructor)

UNIT TESTING equals/hashCode
------------------------------
  // Using JUnit 5 + AssertJ:
  Point a = new Point(1, 2);
  Point b = new Point(1, 2);
  Point c = new Point(3, 4);

  assertThat(a).isEqualTo(b);               // reflexive + equals check
  assertThat(a).isNotEqualTo(c);
  assertThat(a.hashCode()).isEqualTo(b.hashCode());  // consistent hashCode
  assertThat(a).isEqualTo(a);               // reflexive

  // EqualsVerifier library (recommended for thorough contract testing):
  EqualsVerifier.forClass(Point.class).verify();
  // Automatically tests reflexivity, symmetry, transitivity, consistency, null handling,
  // and hashCode contract — catches subtle bugs.

INTERVIEW DISCUSSION POINTS
-----------------------------
  Q: What happens if you override equals() but not hashCode()?
  A: Objects that are equal (by equals()) may have different hashCodes. When used as
     HashMap keys or in a HashSet, the object is hashed to a bucket. The put() is in
     bucket X; when you try to get() the "equal" object, it's hashed to bucket Y →
     not found! Silent, hard-to-debug bug. Always override both together.

  Q: Why use instanceof instead of getClass() in equals()?
  A: instanceof is consistent with Liskov Substitution — a subclass instance that doesn't
     add new state IS equal to an instance of the superclass with the same state.
     AbstractList.equals() uses instanceof so ArrayList and LinkedList with the same
     elements are equal. getClass() is stricter — breaks polymorphic equality but is
     safer when subclasses add state.

  Q: How do you handle BigDecimal in equals/hashCode?
  A: Use compareTo() for equality (not equals()), because equals() on BigDecimal considers
     scale: new BigDecimal("2.0").equals(new BigDecimal("2.00")) → false. For hashCode,
     normalize with stripTrailingZeros() before calling hashCode() so numerically equal
     values produce the same hash.
