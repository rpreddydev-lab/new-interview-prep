GC ALGORITHMS: SERIAL, PARALLEL, G1, ZGC
==========================================

OVERVIEW
---------
  Java provides multiple garbage collector implementations, each making different
  trade-offs between throughput, latency, and footprint. Choosing the right GC
  depends on your application's requirements.

  Enable with JVM flags:
  -XX:+UseSerialGC       — Serial
  -XX:+UseParallelGC     — Parallel (Throughput) GC
  -XX:+UseG1GC           — G1 GC (default since Java 9)
  -XX:+UseZGC            — ZGC (Java 11+ experimental, Java 15+ production, Java 21 GA)
  -XX:+UseShenandoahGC   — Shenandoah (Red Hat, available in OpenJDK)

1. SERIAL GC
-------------
  Single-threaded GC — one thread does all GC work.
  Application must fully pause during both minor and major collections.

  Use case: single-CPU machines, small heaps, client-side or batch applications.

  Young gen: Stop-The-World copying collector
  Old gen:   Stop-The-World mark-sweep-compact

  Flags: -XX:+UseSerialGC

2. PARALLEL GC (THROUGHPUT COLLECTOR)
---------------------------------------
  Multi-threaded version of Serial GC — uses multiple threads for GC work.
  Still Stop-The-World for both young and old generation collections.
  Goal: maximize throughput (minimize % of time spent in GC).

  Use case: batch processing, scientific computation, non-latency-sensitive backends.

  Young gen: Parallel copying collector
  Old gen:   Parallel mark-sweep-compact

  Flags:
  -XX:+UseParallelGC
  -XX:ParallelGCThreads=N          — number of GC threads
  -XX:MaxGCPauseMillis=N           — soft pause time goal (may not always be met)
  -XX:GCTimeRatio=N                — target ratio (throughput): 1/(1+N) time in GC

3. G1 GC (GARBAGE-FIRST)
--------------------------
  DEFAULT since Java 9. Region-based, mostly concurrent, low-latency.

  Key concepts:
  - Heap is divided into equal-sized regions (1–32 MB each, ~2048 regions typically)
  - Regions are dynamically assigned as Eden, Survivor, Old, or Humongous (large objects)
  - G1 prioritizes collecting regions with the most garbage first (Garbage-First naming)
  - Concurrent marking runs alongside the application

  Phases:
  1. Initial Mark (STW, short): marks objects directly reachable from roots
  2. Root Region Scan (concurrent): scans survivor regions
  3. Concurrent Mark (concurrent): traces entire heap
  4. Remark (STW, short): finalizes live object marking
  5. Cleanup (STW + concurrent): identifies completely empty regions, sorts by garbage density
  6. Mixed GC: collects high-garbage Old regions + young gen (incremental)
  7. Full GC (fallback, STW): occurs if concurrent collection can't keep up

  Tuning:
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200      — pause goal (default 200ms — G1 tries to honor this)
  -XX:G1HeapRegionSize=N        — region size (1–32 MB)
  -XX:G1NewSizePercent=N        — min young gen % (default 5%)
  -XX:G1MaxNewSizePercent=N     — max young gen % (default 60%)
  -XX:G1MixedGCCountTarget=N    — number of mixed GC cycles (default 8)
  -XX:InitiatingHeapOccupancyPercent=N — start concurrent marking when heap N% full (default 45)

  Best for: most production applications, heap sizes 4 GB – 500 GB, response time matters.

4. ZGC (Z GARBAGE COLLECTOR)
------------------------------
  Ultra-low-latency GC. Concurrent, region-based.
  Goal: STW pauses under 1–10 ms regardless of heap size (10 MB to 16 TB).

  Key features:
  - Almost entirely concurrent — very short STW pauses (only for root scanning)
  - Uses colored pointers (load barriers) to track object state without STW scanning
  - Concurrent relocation: moves objects while app runs (requires load barriers to
    translate old references to new addresses on access)
  - Handles huge heaps (16 TB)

  Phases:
  1. Pause Mark Start (STW, ~1ms): mark roots
  2. Concurrent Mark: trace heap
  3. Pause Mark End (STW, ~1ms): finalize mark
  4. Concurrent Prepare for Relocation
  5. Pause Relocate Start (STW, ~1ms): relocate roots
  6. Concurrent Relocate: move objects

  Flags:
  -XX:+UseZGC
  -XX:MaxGCPauseMillis=10       — pause goal (soft target)
  -XX:ZCollectionInterval=N     — force GC every N seconds (for predictable latency)

  Best for: latency-sensitive apps (fintech, gaming, real-time), very large heaps.

5. SHENANDOAH GC
-----------------
  Similar goals to ZGC — sub-millisecond pauses, concurrent.
  Developed by Red Hat, available in OpenJDK.
  Uses Brooks pointers (forwarding pointer in object header) for concurrent evacuation.

  -XX:+UseShenandoahGC
  Best for: latency-sensitive apps similar to ZGC use cases.

GC COMPARISON TABLE
--------------------
  | GC            | Threads | Young STW | Old STW   | Pause Goal | Heap Size   | JDK Default |
  |---------------|---------|-----------|-----------|------------|-------------|-------------|
  | Serial        | 1       | Yes       | Yes       | N/A        | Small       | No          |
  | Parallel      | Many    | Yes       | Yes       | Throughput | Medium      | Java 8      |
  | G1            | Many    | Yes       | Concurrent| 200ms      | 4GB–500GB   | Java 9+     |

  | Shenandoah    | Many    | Minimal   | Concurrent| <10ms      | Any         | Opt-in      |

CHOOSING A GC
--------------
  Batch / high throughput (no latency requirement)  → Parallel GC
  Most production applications (balanced)           → G1 GC (default)
  Latency-sensitive (financial, gaming, real-time)  → ZGC or Shenandoah
  Very large heaps (> 100 GB)                       → ZGC
  Single CPU / small embedded                       → Serial GC

GC LOGGING (UNIFIED LOGGING — JAVA 9+)
----------------------------------------
  -Xlog:gc                          — GC events
  -Xlog:gc*                         — detailed GC logs
  -Xlog:gc,gc+heap=info:file=gc.log — write to file
  -Xlog:gc::time,uptime,pid         — add timestamps and PID

  // Pre-Java 9 flags (deprecated but still work):
  -verbose:gc
  -XX:+PrintGCDetails
  -XX:+PrintGCDateStamps

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is G1 GC and why is it the default since Java 9?
A: G1 (Garbage-First) is a region-based, concurrent GC that replaced Parallel GC as the
   default. It divides the heap into equal-sized regions (not fixed young/old areas) and
   prioritizes collecting regions with the most garbage, maximizing reclamation per pause.
   Most of the collection work is concurrent (runs alongside the application). Short STW
   pauses happen only for root marking and remarking. It targets a configurable pause goal
   (default 200ms) and works well for heaps from 4 GB to hundreds of GB, making it a
   good default for most production workloads balancing throughput and latency.

Q: What is ZGC and how does it achieve such low pauses?
A: ZGC uses colored pointers and load barriers to track object state concurrently.
   Almost all GC work (marking, relocation) happens while the application runs. Load
   barriers intercept every object reference load — if the reference points to an old
   address (pre-relocation), the barrier transparently updates it to the new address.
   This allows ZGC to compact memory concurrently without stopping the application.
   STW pauses are typically under 1–10 ms even on terabyte heaps. The trade-off is
   CPU overhead from load barriers and slightly higher memory footprint.

Q: What is the difference between a minor GC and a full GC in G1?
A: In G1, a minor/young GC collects Eden and Survivor regions (STW). A mixed GC collects
   young regions plus some Old regions with high garbage density — incremental old-gen
   collection. A Full GC (the fallback) is a STW mark-compact of the entire heap — happens
   when concurrent collection can't free memory fast enough (allocation starvation). G1 is
   tuned to avoid Full GC via the InitiatingHeapOccupancyPercent flag.

Q: How do you choose between G1 and ZGC for a production application?
A: Use G1 when: the application can tolerate 100–200ms GC pauses, heap is 4–100 GB,
   you want simpler tuning (just MaxGCPauseMillis). Use ZGC when: latency is critical
   (P99 must be < 10ms), heap is very large (hundreds of GB to TB), or you're running
   latency-sensitive workloads (trading, gaming, real-time analytics). ZGC has higher
   CPU overhead due to load barriers, and slightly higher memory footprint.
