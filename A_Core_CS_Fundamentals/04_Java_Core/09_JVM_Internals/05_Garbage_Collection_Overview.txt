GARBAGE COLLECTION OVERVIEW
=============================

WHAT IS GARBAGE COLLECTION?
-----------------------------
  Garbage Collection (GC) automatically identifies and reclaims heap memory occupied
  by objects that are no longer reachable from the application.

  An object is "reachable" if there is any chain of references from a GC root to it.

  GC Roots (always reachable):
  - Local variables and parameters in active stack frames
  - Static fields of loaded classes (in Metaspace)
  - JNI references (from native code)
  - Active threads

  Unreachable objects = garbage = eligible for collection.

GENERATIONAL HYPOTHESIS
------------------------
  Most objects die young — observed empirically across many Java programs.
  The JVM exploits this by dividing the heap into generations:

  Young Generation:
  - New objects allocated here (in Eden)
  - Minor GC: collects only Young Generation — frequent, fast (< 100ms)
  - Survivors promoted to Old Generation after N minor GCs

  Old Generation (Tenured):
  - Long-lived objects
  - Major GC / Full GC: collects Old (and sometimes Young) — infrequent, longer pause

GC PHASES
----------
  1. Mark:
     Traces all reachable objects starting from GC roots.
     Every live object is marked.

  2. Sweep:
     Reclaims memory of unmarked (unreachable) objects.
     Problem: leaves fragmented free space.

  3. Compact (optional):
     Moves live objects together to eliminate fragmentation.
     Expensive: must update all references.

  4. Copy:
     Alternative to compact — copies live objects to a new area, leaving old area empty.
     Eden → Survivor: copying GC for young generation.

STOP-THE-WORLD (STW) PAUSES
-----------------------------
  GC must pause application threads (Stop-The-World) to safely collect garbage.
  During a pause, no application code runs.
  Long pauses degrade response time and throughput.

  Modern GCs minimize STW by doing most work concurrently:
  - Concurrent marking: trace live objects while app runs
  - Incremental collection: collect in small chunks
  - Only short STW pauses for initial/final mark (roots need consistent state)

OBJECT LIFE CYCLE IN MEMORY
-----------------------------
  1. new Object() → allocated in Eden
  2. Minor GC: unreachable objects in Eden die; live objects copied to Survivor S0
  3. Next minor GC: live S0 objects copied to S1; age counter incremented
  4. After MaxTenuringThreshold (15 by default): promoted to Old Generation
  5. Old Generation full → Major/Full GC; unreachable old objects collected
  6. object.finalize() called before collection (deprecated Java 9, removed Java 18)

REFERENCE TYPES AND GC
------------------------
  Java provides four reference strengths (java.lang.ref package):

  Strong Reference (default):
  - Object obj = new Object();  // will never be GC'd while strongly referenced

  Soft Reference:
  - SoftReference<Cache> cache = new SoftReference<>(bigCache);
  - GC'd only when JVM is low on memory (before OOM)
  - Ideal for memory-sensitive caches

  Weak Reference:
  - WeakReference<T> ref = new WeakReference<>(obj);
  - GC'd at the next collection if no strong references exist
  - Used in WeakHashMap (cache that doesn't prevent GC)

  Phantom Reference:
  - PhantomReference<T> ref = new PhantomReference<>(obj, queue);
  - Object already finalized; used for cleanup actions (post-GC notification)
  - get() always returns null; used with ReferenceQueue

  // Practical WeakReference example:
  WeakHashMap<Key, Value> cache = new WeakHashMap<>();
  // Entries are automatically removed when keys are GC'd

GC METRICS THAT MATTER
------------------------
  Throughput: % of time application runs vs time spent in GC
    - High GC time → low throughput
    - Goal: maximize throughput

  Latency (pause time): duration of STW pauses
    - Goal: minimize worst-case pause (P99 latency)

  Footprint: total memory used by the JVM process
    - Smaller → better for containers/cloud

  Trade-offs: these three are in tension — optimizing one usually hurts others.

GC-RELATED JVMTI EVENTS AND MONITORING
----------------------------------------
  - jstat: command-line GC statistics
    jstat -gcutil <pid> 1s    // print GC stats every 1 second

  - JVM flags for GC logging (Java 9+ unified logging):
    -Xlog:gc=info              // basic GC info
    -Xlog:gc*=debug            // verbose GC detail
    -Xlog:gc,gc+heap=info      // heap + GC events

  - GC log contents:
    Heap before/after, pause duration, which collector ran, promoted bytes

COMMON JAVA GC-RELATED EXCEPTIONS
------------------------------------
  OutOfMemoryError: Java heap space       — heap exhausted (increase -Xmx or fix leak)
  OutOfMemoryError: GC overhead limit exceeded — GC spending >98% time with <2% freed
  OutOfMemoryError: Metaspace             — too many classes (increase -XX:MaxMetaspaceSize)
  OutOfMemoryError: Direct buffer memory  — off-heap buffer exhausted

COMMON INTERVIEW QUESTIONS
---------------------------
Q: How does garbage collection work in Java?
A: GC traces all reachable objects from GC roots (stack frames, static fields, JNI
   references) and marks them as live. Everything not marked is garbage. The collector
   reclaims garbage memory via sweep (free the space), copy (move live objects to a new
   area), or compact (slide live objects together). Java uses generational GC: new objects
   go to the Young Generation (Eden), where minor GC collects frequently and cheaply.
   Long-lived objects are promoted to the Old Generation, which is collected less often.

Q: What is a GC root?
A: GC roots are the starting points for reachability tracing. An object is live if it is
   reachable (directly or transitively) from a GC root. GC roots include: (1) local
   variables and parameters in all active stack frames; (2) static fields of loaded
   classes; (3) active threads; (4) JNI global references. Everything not reachable from
   these roots is garbage.

Q: What is a Stop-The-World pause and why is it necessary?
A: A Stop-The-World pause halts all application threads so the GC can safely examine
   the heap. During marking, if threads were running, references could change — the GC
   might mark an object as dead while a thread is about to use it, causing data corruption.
   STW ensures a consistent snapshot. Modern GCs (G1, ZGC, Shenandoah) minimize STW
   duration by doing most work concurrently, with only brief STW for initial and final
   mark phases.

Q: What is the difference between minor GC and major GC?
A: Minor GC collects only the Young Generation (Eden + Survivor). It is frequent (triggered
   when Eden fills) and typically fast (milliseconds) because it collects short-lived objects
   and works with a small area. Major GC (or Full GC) collects the Old Generation and
   sometimes the Young Generation. It is infrequent but much slower (seconds in the worst
   case) because the Old Generation is larger. Full GC pauses the application for longer,
   causing latency spikes.
