GC TUNING AND JVM FLAGS
=========================

TUNING PHILOSOPHY
------------------
  1. Measure first — use GC logs, jstat, JFR before tuning
  2. Define your goal: throughput, latency, or footprint?
  3. Tune one parameter at a time and measure the effect
  4. Don't over-tune — modern GCs (G1, ZGC) are self-tuning when given correct goals

  Three tuning goals (pick your priority):
  - Throughput: maximize work done per unit time → Parallel GC, minimize GC frequency
  - Latency: minimize worst-case pause → G1 (MaxGCPauseMillis) or ZGC
  - Footprint: minimize memory usage → smaller heap, Serial GC

HEAP SIZING FLAGS
------------------
  -Xms<size>       — minimum (initial) heap size   (e.g., -Xms512m)
  -Xmx<size>       — maximum heap size              (e.g., -Xmx4g)
  -Xmn<size>       — young generation size          (e.g., -Xmn1g)
  -XX:NewRatio=N   — ratio of old:young gen          (N=2 → old is 2x young, default)
  -XX:SurvivorRatio=N — ratio of eden:survivor       (N=8 → eden 8x each survivor, default)

  Best practice: set -Xms = -Xmx to avoid heap resizing at runtime (reduces GC overhead
  and OS memory fragmentation in containers).

  // Container sizing (Java 10+ with -XX:+UseContainerSupport, enabled by default):
  // JVM respects cgroup memory limits automatically
  -XX:MaxRAMPercentage=75.0   // use 75% of container RAM for heap
  -XX:InitialRAMPercentage=50.0

G1 GC TUNING FLAGS
-------------------
  -XX:+UseG1GC                    — enable G1 (default Java 9+)
  -XX:MaxGCPauseMillis=200        — soft pause time goal (default 200ms)
  -XX:G1HeapRegionSize=N          — region size in MB (1–32), default: heap/2048
  -XX:InitiatingHeapOccupancyPercent=45 — when to start concurrent marking (default 45%)
  -XX:G1NewSizePercent=5          — minimum young gen % (default 5%)
  -XX:G1MaxNewSizePercent=60      — maximum young gen % (default 60%)
  -XX:G1MixedGCCountTarget=8      — mixed GC cycles to spread old region collection (default 8)
  -XX:G1HeapWastePercent=5        — % of heap G1 won't bother collecting (default 5%)
  -XX:ConcGCThreads=N             — threads for concurrent marking
  -XX:ParallelGCThreads=N         — threads for STW phases

  Tuning for lower latency (trading throughput):
  -XX:MaxGCPauseMillis=100
  -XX:InitiatingHeapOccupancyPercent=35  // start marking earlier
  -XX:G1NewSizePercent=10                // keep young gen from growing too large

  Fixing "Full GC" in G1:
  Full GC = G1 ran out of memory before concurrent collection finished.
  Fix: increase heap, lower IHOP (start marking earlier), reduce allocation rate.

ZGC TUNING FLAGS
-----------------
  -XX:+UseZGC                     — enable ZGC
  -XX:MaxGCPauseMillis=10         — soft target (ZGC rarely exceeds 10ms regardless)
  -XX:ZCollectionInterval=N       — trigger GC every N seconds (for latency predictability)
  -XX:ZAllocationSpikeTolerance=N — safety factor for allocation spikes (default 2.0)
  -XX:ConcGCThreads=N             — concurrent GC thread count

PARALLEL GC TUNING
--------------------
  -XX:+UseParallelGC
  -XX:MaxGCPauseMillis=N          — pause goal
  -XX:GCTimeRatio=N               — throughput goal: (1/(1+N)) time in GC (default N=99 = 1% in GC)
  -XX:ParallelGCThreads=N         — GC thread count

GC LOGGING (JAVA 9+ UNIFIED LOGGING)
--------------------------------------
  -Xlog:gc                          — basic GC events
  -Xlog:gc*                         — detailed (all GC-related tags)
  -Xlog:gc,gc+heap=info:file=gc.log:time,uptime — log to file with timestamps
  -Xlog:gc+phases=debug             — G1 phase timing details

  // Reading a GC log:
  [0.123s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 12M->5M(256M) 8.123ms
  // Time=0.123s, GC#0, Young GC, heap 12M→5M, total 256M, pause 8.123ms

  // Full GC in G1 log (bad!):
  [10.456s][info][gc] GC(5) Pause Full (G1 Evacuation Failed) 512M->498M(512M) 3456.789ms
  // 3.4 second pause — heap too small or allocation too fast

JVM DIAGNOSTIC FLAGS
---------------------
  // Memory:
  -XX:+HeapDumpOnOutOfMemoryError  — dump heap when OOM
  -XX:HeapDumpPath=/tmp/heapdump.hprof
  -XX:+PrintGCDetails              — verbose GC (Java 8) / use -Xlog:gc* in Java 9+

  // Performance:
  -XX:+UseCompressedOops           — 4-byte refs for heaps ≤ 32 GB (default enabled)
  -XX:+UseStringDeduplication      — G1 only: deduplicate duplicate String contents (saves heap)
  -XX:+OptimizeStringConcat        — JIT optimizes StringBuilder chains (default)

  // JIT:
  -XX:+PrintCompilation            — log method compilations
  -XX:+TieredCompilation           — enable tiered (default)
  -server                          — use server JIT mode

  // Thread:
  -Xss<size>                       — stack size per thread (default 512k–1m)

GC MONITORING TOOLS
--------------------
  jstat — command-line GC statistics:
  jstat -gcutil <pid> 1000         // print GC stats every 1 second
  jstat -gc <pid> 1000             // detailed memory region sizes
  // Output columns: S0, S1, E (eden), O (old), M (metaspace), YGC, YGCT, FGC, FGCT, GCT

  jcmd — diagnostic commands:
  jcmd <pid> VM.gc                 // trigger GC
  jcmd <pid> GC.heap_info          // heap region summary
  jcmd <pid> GC.heap_dump /tmp/heap.hprof

  JFR (Java Flight Recorder):
  -XX:+FlightRecorder
  jcmd <pid> JFR.start duration=60s filename=recording.jfr
  // Analyze with JMC (Java Mission Control)

COMMON MEMORY PROBLEMS
------------------------
  Memory Leak: Objects remain referenced (in a cache, list, static map) longer than needed.
  Diagnosis: heap dump → analyze with Eclipse MAT or VisualVM.
  Signs: heap grows over time, increased GC frequency, eventual OOM.

  Humongous Allocations (G1): Objects > 50% of region size bypass young gen,
  go directly to old gen — can cause frequent full GC.
  Fix: increase G1HeapRegionSize or allocate smaller objects.

  GC Thrashing / Death Spiral: GC running constantly, recovering little memory.
  Signs: CPU 100%, throughput ~0%, OOM: GC overhead limit exceeded.
  Fix: increase heap, fix memory leak, or reduce object allocation rate.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: How do you identify and fix memory leaks in a Java application?
A: (1) Monitor heap growth over time with jstat or JFR — steady increase suggests a leak.
   (2) Capture heap dump: jcmd <pid> GC.heap_dump /tmp/heap.hprof. (3) Analyze with Eclipse
   MAT or VisualVM — look for dominator trees, accumulated objects, and unexpected retention.
   Common leak causes: static collections holding references (Map<K,V> never cleared),
   ThreadLocal not removed in thread pools, listeners not deregistered, long-lived caches
   without eviction. Fix: add eviction policies, use WeakReference/SoftReference, ensure
   ThreadLocal.remove() in finally blocks.

Q: What does -XX:+HeapDumpOnOutOfMemoryError do?
A: It tells the JVM to automatically write a heap dump to disk when an OutOfMemoryError
   occurs. Combined with -XX:HeapDumpPath=/path/to/dump.hprof, this captures the complete
   heap state at the moment of failure — invaluable for post-mortem analysis. Without this
   flag, you only get the OOM error message with no way to understand why.

Q: What is the difference between -Xms and -Xmx and why set them equal?
A: -Xms is the initial heap size (minimum). -Xmx is the maximum. When they differ,
   the JVM may start with a small heap and expand it as needed — each expansion is a
   system call that causes a brief pause. Setting them equal prevents dynamic resizing,
   eliminates resize-related pauses, and makes memory usage predictable. In production
   containers, matching them to the container memory limit (via MaxRAMPercentage) avoids
   OOM kills from OS/cgroup.

Q: What is GCTimeRatio and how does it relate to throughput?
A: GCTimeRatio=N means the JVM targets spending 1/(1+N) of total time in GC. The default
   N=99 means GC should take at most 1% of time (99% for application). Lower values allow
   more GC time. The GC adjusts heap size to meet this ratio — if GC is taking too much
   time, it grows the heap. This is a throughput tuning knob for Parallel GC.
