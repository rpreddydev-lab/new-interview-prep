================================================================
  COLLISION RESOLUTION TECHNIQUES
================================================================

----------------------------------------------------------------
WHAT IS A COLLISION?
----------------------------------------------------------------
A collision occurs when two different keys produce the same
hash index in a hash table.

  hash(key1) % m == hash(key2) % m   (different keys, same slot)

Collisions are INEVITABLE for any hash table where the number
of possible keys exceeds the number of buckets
(pigeonhole principle).

The goal of collision resolution is to handle multiple keys
mapping to the same slot while maintaining O(1) average
operations.

----------------------------------------------------------------
TWO MAIN STRATEGIES
----------------------------------------------------------------
  1. SEPARATE CHAINING (open hashing)
     Each bucket holds a list/tree of all keys that hash to it.

  2. OPEN ADDRESSING (closed hashing)
     All keys stored in the array itself.
     On collision, probe for the next available slot.
     Subtypes: Linear, Quadratic, Double Hashing

----------------------------------------------------------------
STRATEGY 1: SEPARATE CHAINING
----------------------------------------------------------------
Each bucket contains a linked list (or balanced BST) of all
entries that hash to that bucket.

  Visualization (table size = 4, load factor = 0.75):
    bucket[0] --> null
    bucket[1] --> ["bob", 25] -> ["dave", 31] -> null
    bucket[2] --> ["alice", 30] -> null
    bucket[3] --> null

  INSERT:
    Compute index = hash(key) % m
    Append (key, value) to the list at bucket[index]
    Time: O(1) average (O(n) worst if all keys in same bucket)

  SEARCH:
    Compute index, traverse list at bucket[index]
    Compare keys using equals()
    Time: O(1) average, O(n) worst

  DELETE:
    Find and remove from the list at bucket[index]
    Time: O(1) average

  Advantages:
    - Simple to implement
    - Never fills up (can always add more to chains)
    - Less sensitive to hash function quality
    - Load factor > 1 is possible (more keys than buckets)

  Disadvantages:
    - Extra memory for pointers (linked list overhead)
    - Poor cache performance (pointer chasing)
    - Long chains degrade to O(n)

  Java HashMap uses separate chaining:
    - Buckets are LinkedLists
    - Java 8+: converts to Red-Black Tree when chain > 8
    - Converts back to LinkedList when chain drops < 6

----------------------------------------------------------------
STRATEGY 2: OPEN ADDRESSING — LINEAR PROBING
----------------------------------------------------------------
All keys stored directly in the table array.
On collision, scan forward linearly to find next empty slot.

  probe sequence: i, i+1, i+2, i+3, ...

  INSERT key at index i:
    while table[i] != EMPTY:
      i = (i + 1) % m
    table[i] = (key, value)

  SEARCH key:
    start at i = hash(key) % m
    while table[i] != EMPTY:
      if table[i].key == key: FOUND
      i = (i + 1) % m
    return NOT FOUND

  DELETE key: (TRICKY)
    Cannot simply set to EMPTY -- this would break the search
    chain for other keys probed past this slot.
    Solution: mark deleted slots as DELETED (tombstone).
    Search skips over DELETED but treats EMPTY as stop.
    Insert can reuse DELETED slots.

  PRIMARY CLUSTERING:
    Linear probing creates "clusters" -- long contiguous runs
    of filled slots. New keys that hash into a cluster must
    probe through the entire cluster. This degrades performance
    significantly at high load factors.

  Performance:
    Excellent cache performance (sequential memory access)
    Degrades badly with high load factor (> 0.7)
    Average ops: O(1/(1-α)) where α = load factor

----------------------------------------------------------------
STRATEGY 2B: OPEN ADDRESSING — QUADRATIC PROBING
----------------------------------------------------------------
Probe sequence uses quadratic steps to reduce primary clustering.

  probe sequence: i, i+1², i+2², i+3², ...
  i.e.: i, i+1, i+4, i+9, i+16, ...

  INSERT:
    j = 0
    while table[(i + j²) % m] != EMPTY:
      j++
    store at (i + j²) % m

  SECONDARY CLUSTERING:
    Keys that hash to the same initial index follow the SAME
    probe sequence. This is "secondary clustering" -- less
    severe than primary but still a concern.

  Limitation:
    Does NOT guarantee finding an empty slot unless:
    table size is prime AND load factor <= 0.5

  Advantage over linear: fewer clusters, better distribution
  Disadvantage: doesn't guarantee full table coverage

----------------------------------------------------------------
STRATEGY 2C: OPEN ADDRESSING — DOUBLE HASHING
----------------------------------------------------------------
Use a second hash function to determine step size.
Eliminates both primary and secondary clustering.

  probe sequence: i, i+h2(key), i+2*h2(key), ...

  h1(key) = key % m                       (primary hash)
  h2(key) = prime - (key % prime)         (step size)

  INSERT:
    i = h1(key)
    step = h2(key)
    while table[i] != EMPTY:
      i = (i + step) % m
    table[i] = (key, value)

  Requirements:
    - h2(key) must never return 0
    - h2(key) and m must be coprime (use prime m)

  Advantages:
    - Best distribution among open addressing schemes
    - No clustering issues
    - Guaranteed to visit all slots if conditions met

  Disadvantages:
    - Two hash computations per probe
    - Still suffers at high load factors
    - More complex implementation

COMPARISON OF ALL COLLISION STRATEGIES
----------------------------------------------------------------
  Feature                Separate    Linear     Quadratic  Double
                         Chaining    Probing    Probing    Hashing
  ---------------------------------------------------------------
  Memory                 Extra ptrs  In-array   In-array   In-array
  Cache performance      Poor        Excellent  Good       Moderate
  Primary clustering     No          Yes        No         No
  Secondary clustering   No          No         Yes        No
  Load factor > 1        Yes         No         No         No
  Delete complexity      Easy        Tombstone  Tombstone  Tombstone
  Implementation         Simple      Simple     Moderate   Complex
  Used in Java           Yes (HashMap) No       No         No
  Used in Python         No          No         No         Yes
  Used in Go             No          Linear+    -          -
                                     quadratic

----------------------------------------------------------------
ROBIN HOOD HASHING (Modern Open Addressing)
----------------------------------------------------------------
A variant of linear probing that reduces variance by stealing
slots from "rich" elements (those close to their home bucket)
to give to "poor" elements (those far from home).

  Probe distance = current_index - home_index (distance from ideal)

  INSERT:
    During probing, if the current occupant has a LOWER probe
    distance than the new key, displace the occupant and
    continue inserting the displaced key.

  Effect:
    All elements end up roughly equidistant from their home.
    Reduces worst-case lookup time significantly.
    Used in: Rust's HashMap, many high-performance hash tables.

----------------------------------------------------------------
CUCKOO HASHING (Guaranteed O(1) Worst Case Lookup)
----------------------------------------------------------------
Uses TWO hash tables and TWO hash functions.
Each key can live in exactly one of two possible positions.

  INSERT key:
    Compute pos1 = h1(key) in table1
    If table1[pos1] is empty: done
    Else: displace existing key, try to place it in ITS other
          position. Repeat ("cuckoo eviction").
    If cycle detected (no progress): rehash everything.

  LOOKUP key:
    Check h1(key) in table1 AND h2(key) in table2
    Only 2 memory lookups -- guaranteed O(1) worst case

  INSERT: O(1) amortized (rehash occasionally)
  LOOKUP: O(1) worst case -- always exactly 2 comparisons
  DELETE: O(1) -- mark slot empty

  Trade-off: complex insertion, risk of rehash loops.
  Used in: high-performance network lookups (routers), caches.

----------------------------------------------------------------
TOMBSTONE DELETION IN OPEN ADDRESSING
----------------------------------------------------------------
Deleting in open addressing requires a tombstone marker,
not a simple EMPTY marker.

  Why tombstones are needed:
    Table: [A at 0] [B at 1] [C at 2] [EMPTY at 3]
    B and C both hashed to slot 0 and were placed via probing.
    If we delete B (slot 1) and set it to EMPTY,
    then searching for C starts at 0, checks 1 (EMPTY), stops.
    C is now "lost" even though it's at slot 2.

  With tombstone:
    Delete B -> set slot 1 to DELETED (tombstone)
    Search for C: checks 0 (not C), checks 1 (DELETED, skip),
    checks 2 (C found). Correct.

  Tombstone problems:
    Over time, tombstones accumulate and degrade performance.
    Solution: periodic rehashing to clean tombstones,
    or replace tombstone on first clean insert.

----------------------------------------------------------------
INTERVIEW QUESTIONS
----------------------------------------------------------------

Q: What is the difference between separate chaining and
   open addressing?
A: Separate chaining stores colliding keys in a list (or tree)
   at each bucket, outside the main array. Load factor can
   exceed 1. Good cache performance for the hash computation
   but poor for traversing the chain. Open addressing stores
   all keys in the array itself and probes for an empty slot
   on collision. Load factor must stay below 1. Linear probing
   has excellent cache performance but clusters. Both achieve
   O(1) average operations with a good load factor.

Q: Why does Java HashMap use separate chaining instead of
   open addressing?
A: Separate chaining handles load factors > 0.75 more gracefully
   and doesn't require tombstones for deletion. Java HashMap
   also stores key-value pairs (not just keys), and chaining
   simplifies the implementation. Additionally, Java 8's
   optimization (convert chain to Red-Black Tree at length 8)
   gives O(log n) worst-case bucket traversal. Open addressing
   with key-value pairs and tombstones would be more complex.

Q: What is primary clustering in linear probing and how
   is it mitigated?
A: Primary clustering is when consecutive filled slots form
   long runs. Any new key hashing into the cluster must probe
   through the entire cluster. This creates a snowball effect:
   larger clusters attract more keys. Quadratic probing
   eliminates primary clustering by using step sizes of 1, 4,
   9, 16... Double hashing eliminates it further by using a
   key-specific step size derived from a second hash function.

Q: Why can't you simply mark a deleted slot as EMPTY in
   open addressing?
A: In open addressing, keys are found by probing from their
   home index. If a key was displaced past a slot that's
   now marked EMPTY, the probe would stop at that EMPTY slot
   before reaching the displaced key. The tombstone marker
   (DELETED) tells the probe to continue past that slot.
   Without tombstones, deleting one key can make other keys
   unreachable.

Q: What is the load factor and what is the ideal value?
A: Load factor α = n / m (n = keys stored, m = table size).
   A higher load factor means more keys per bucket -> more
   collisions -> slower operations. Java HashMap resizes at
   α = 0.75 (default), which balances time and space.
   For open addressing, performance degrades sharply beyond
   α = 0.7. For separate chaining, α = 1.0 is often acceptable.
   In interviews, mentioning 0.75 as Java's threshold shows
   depth of knowledge.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------
  1. Know that Java uses SEPARATE CHAINING with LinkedList
     (and Red-Black Tree for long chains since Java 8)
  2. Tombstone deletion is a common follow-up question for
     open addressing -- always mention it
  3. Load factor 0.75 is Java HashMap's default -- worth
     stating in any HashMap internals question
  4. Double hashing has the best distribution of the open
     addressing schemes -- mention it when asked about
     alternatives to chaining
  5. Cuckoo hashing guarantees O(1) WORST CASE lookup --
     contrast this with all other methods which are O(1) average
  6. Robin Hood hashing is a modern improvement on linear probing
     -- mentioning it signals knowledge of current practices
