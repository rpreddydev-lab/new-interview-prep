COMPOSITION vs INHERITANCE
============================

INHERITANCE (IS-A)
------------------
A class extends another class — acquires all its state and behavior.
  class Dog extends Animal { ... }  // Dog IS-A Animal

COMPOSITION (HAS-A)
--------------------
A class contains a reference to another class — delegates behavior to it.
  class Car { private Engine engine; }  // Car HAS-A Engine

THE GOLDEN RULE
---------------
  "Favor composition over inheritance."
  — GoF Design Patterns, Joshua Bloch (Effective Java)

WHY PREFER COMPOSITION?
------------------------
  1. Flexibility: Composition allows behavior to be changed at runtime by swapping
     the held object. Inheritance is fixed at compile time.

  2. No tight coupling: Inheritance exposes parent internals to child class.
     The child is tightly coupled to the parent's implementation.

  3. Avoids fragile base class problem: When a parent class changes, all subclasses
     may break unexpectedly. Composition isolates changes.

  4. Multiple behaviors: Composition can combine multiple objects; Java only allows
     single class inheritance.

  5. Better testability: Composed objects can be mocked/stubbed; parent class methods
     harder to isolate in unit tests.

INHERITANCE PROBLEM EXAMPLE
-----------------------------
  class Stack<T> extends Vector<T> {   // Java's java.util.Stack — a DESIGN MISTAKE
      // Stack IS-A Vector? No! Stack should only expose push/pop/peek.
      // But now users can call Vector.add(index, element) — bypassing stack semantics.
  }
  // Fix: Stack should CONTAIN a Vector (or Deque), not extend it.

COMPOSITION EXAMPLE
--------------------
  // Bad: inheritance
  class LoggingList extends ArrayList<String> {
      @Override public boolean add(String s) {
          System.out.println("Adding: " + s);
          return super.add(s);
      }
  }
  // If ArrayList changes its addAll() implementation to call add() internally,
  // this breaks — fragile base class problem.

  // Good: composition (forwarding/wrapper)
  class LoggingList {
      private final List<String> list = new ArrayList<>();

      public boolean add(String s) {
          System.out.println("Adding: " + s);
          return list.add(s);
      }
      public int size() { return list.size(); }
      // Delegate only what you want to expose
  }

DELEGATION PATTERN
------------------
Composition often uses delegation: the outer class forwards method calls to the
inner (held) object.

  class Printer {
      void print(String s) { System.out.println(s); }
  }
  class Report {
      private Printer printer = new Printer();  // HAS-A

      void generate(String content) {
          // ... build report ...
          printer.print(content);  // delegate to Printer
      }
  }

WHEN IS INHERITANCE APPROPRIATE?
----------------------------------
  Use inheritance when:
    - There is a genuine IS-A relationship (not just code reuse).
    - You control both parent and child (same codebase).
    - The parent class was designed for inheritance (documented as such).
    - You need to override behavior for polymorphism.

  Don't use inheritance just to reuse code — use composition instead.

MIXIN VIA INTERFACES
---------------------
Java supports "mixin" behavior through interfaces with default methods.
This lets a class gain behavior without class inheritance:

  interface Auditable {
      default void audit(String action) {
          System.out.println("Audit: " + action + " on " + this.getClass().getSimpleName());
      }
  }
  class Order implements Auditable {
      void submit() {
          // ...
          audit("submit");  // gained behavior via interface — no inheritance tax
      }
  }

REAL-WORLD EXAMPLES
--------------------
  Composition:
    - java.util.HashMap is used inside java.util.HashSet (Set HAS-A HashMap).
    - java.io.BufferedReader wraps (composes) any Reader (Decorator pattern).
    - Spring services hold (compose) repositories — not extend them.

  Appropriate Inheritance:
    - Exception hierarchy: IOException extends Exception — genuine IS-A.
    - Spring's AbstractController — template method, designed for subclassing.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between composition and inheritance?
A: Inheritance is IS-A — a subclass extends a superclass and inherits its implementation.
   Composition is HAS-A — a class holds a reference to another and delegates to it.
   Composition is preferred for flexibility, looser coupling, and avoiding the fragile base
   class problem.

Q: Why is Java's Stack class considered a design mistake?
A: java.util.Stack extends Vector, so Stack IS-A Vector. But semantically a Stack should only
   expose push/pop/peek. Because Stack inherits Vector, callers can use all Vector methods
   (like add at arbitrary index) — violating stack semantics. It should have used composition.
   java.util.Deque (ArrayDeque) is the modern replacement.

Q: What is the fragile base class problem?
A: When a subclass overrides methods of a parent class, changes to the parent's internals
   can silently break the subclass. This is fragile coupling. Example: if a parent's addAll()
   calls add() internally, and a subclass overrides add() to count insertions, it will double-
   count when addAll() is called — even though the subclass never changed.

Q: Can you give an example where composition is better than inheritance?
A: A LoggingList that extends ArrayList is fragile (fragile base class). Instead, create a
   LoggingList that CONTAINS an ArrayList and delegates calls through it. This way, ArrayList
   implementation changes don't silently break LoggingList.
