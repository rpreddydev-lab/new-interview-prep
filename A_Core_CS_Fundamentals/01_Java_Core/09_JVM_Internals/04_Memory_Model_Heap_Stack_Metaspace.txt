JVM MEMORY MODEL: HEAP, STACK, METASPACE
==========================================

RUNTIME MEMORY REGIONS
------------------------
  The JVM divides memory into several regions, each with distinct purposes:

  +----------------------------------------------------------+
  |              JVM PROCESS MEMORY                          |
  |                                                          |
  |  +--------------------+  +--------------------------+   |
  |  |       HEAP         |  |       METASPACE          |   |
  |  |                    |  |  (native/off-heap)        |   |
  |  | Young Generation   |  |  Class metadata           |   |
  |  |   Eden             |  |  Method bytecode          |   |
  |  |   Survivor S0      |  |  Constant pool            |   |
  |  |   Survivor S1      |  |  Static field values      |   |
  |  |                    |  +--------------------------+   |
  |  | Old Generation     |                                  |
  |  | (Tenured)          |  +--------------------------+   |
  |  +--------------------+  |  JVM STACKS (per thread)  |   |
  |                          |  Stack Frame:              |   |
  |  +--------------------+  |    Local variables        |   |
  |  | Code Cache         |  |    Operand stack          |   |
  |  | (JIT compiled code)|  |    Frame data             |   |
  |  +--------------------+  +--------------------------+   |
  |                          |  PC Registers (per thread)|   |
  |                          |  Native Method Stacks     |   |
  +----------------------------------------------------------+

HEAP
-----
  Shared among all threads. Holds all object instances and arrays.
  Managed by the Garbage Collector.

  Young Generation:
  - Eden space: where new objects are initially allocated (fast bump-pointer allocation)
  - Survivor S0 and S1: objects that survive one or more minor GCs
  - Minor GC (young GC) collects this area — frequent, fast (milliseconds)
  - "Generational hypothesis": most objects die young

  Old Generation (Tenured):
  - Long-lived objects promoted from Young Generation (after surviving N minor GCs)
  - Major GC (Full GC) collects old gen — infrequent but longer pause
  - Promotion threshold: -XX:MaxTenuringThreshold (default 15)

  Sizing flags:
  -Xms<size>   — initial heap size (e.g., -Xms256m)
  -Xmx<size>   — maximum heap size (e.g., -Xmx2g)
  -Xmn<size>   — young generation size
  -XX:NewRatio=N — ratio of old:young (default N=2 → old is 2× young)

JVM STACK (PER THREAD)
-----------------------
  Each thread has its own stack. Created when the thread starts, destroyed when it ends.
  Stores method call frames — one frame per active method invocation.

  Stack Frame contents:
  - Local variables array: method parameters + locally declared variables
  - Operand stack: working area for bytecode instructions (push/pop)
  - Frame data: reference to constant pool, return address

  // Primitive values and object REFERENCES are on the stack;
  // the actual OBJECTS they refer to are on the heap.

  int x = 5;          // x (primitive) stored in local variables array on stack
  String s = "Hello"; // reference 's' on stack; the String object on heap

  Stack size: -Xss<size> (e.g., -Xss512k)
  Deep recursion → StackOverflowError

METASPACE (JAVA 8+ — REPLACES PERMGEN)
-----------------------------------------
  Stores class metadata: class name, field/method descriptors, bytecode of methods,
  runtime constant pool, static field values.

  Uses native (off-heap) memory — not the Java heap.
  Grows dynamically (no fixed size by default).

  Flags:
  -XX:MetaspaceSize=<size>      — initial trigger size for GC of metaspace
  -XX:MaxMetaspaceSize=<size>   — cap native memory usage

  PermGen (Java 7 and before):
  - Fixed-size heap region for class metadata
  - Common cause of OutOfMemoryError: PermGen space — especially in frameworks that
    generate many classes (JSPs, Hibernate, Spring proxies)
  - Eliminated in Java 8 — replaced by Metaspace

CODE CACHE
-----------
  Holds JIT-compiled native code.
  Off-heap, limited by -XX:ReservedCodeCacheSize (default ~240MB).
  CodeCacheIsFull warning → JIT disabled → performance degradation.
  Monitor with: -XX:+PrintCodeCache

OBJECT MEMORY LAYOUT
---------------------
  Every Java object in the heap has:
  - Object header:
    - Mark word (8 bytes): hashcode, GC age, lock state, GC mark bits
    - Klass pointer (4–8 bytes): reference to class metadata (compressed with -XX:+UseCompressedOops)
  - Instance fields: padded and aligned

  // Object overhead:
  // A minimal empty object uses 16 bytes (header on 64-bit JVM with compressed oops)
  // An int[] of length 0 uses 16 bytes (header + length field)

  // CompressedOops (-XX:+UseCompressedOops, enabled by default for heaps ≤ 32GB):
  // Reduces 8-byte object references to 4 bytes — saves ~30–40% heap

STACK TRACE AND MEMORY
------------------------
  class Foo {
      void a() { b(); }  // frame pushed
      void b() { c(); }  // frame pushed
      void c() { throw new RuntimeException(); } // stack: c, b, a
  }
  // When exception printed, stack trace shows: c -> b -> a (LIFO)

THREAD STACK VS HEAP — DECISION RULE
--------------------------------------
  Primitive value → local variable → on the stack
  Object created with new → on the heap (always)
  Reference to an object → on the stack if local, on the heap if a field
  Static field → in Metaspace (reference), referenced object on heap

DIRECT/OFF-HEAP MEMORY
------------------------
  Java programs can allocate memory outside the heap (off-heap) using:
  - ByteBuffer.allocateDirect(size) — used by NIO channels
  - sun.misc.Unsafe.allocateMemory() — used by frameworks (Netty, Cassandra)
  - Metaspace and Code Cache are also off-heap

  Off-heap: not GC'd automatically; must be explicitly freed.
  Controlled by: -XX:MaxDirectMemorySize

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between the JVM stack and the heap?
A: The stack is per-thread, stores method call frames (local variables, operand stack),
   and is automatically reclaimed when methods return. Primitives and object references
   live on the stack. The heap is shared among all threads and stores all object instances
   and arrays. GC manages heap reclamation. The stack is much faster (bump pointer) but
   limited in size (StackOverflowError); the heap is larger but GC-managed.

Q: What is the Young Generation and why is it divided into Eden and Survivor spaces?
A: The Young Generation is where new objects are allocated. The Generational Hypothesis
   (most objects die young) means minor GC is frequent but cheap. Eden is where new
   objects land — allocation is fast (bump pointer). During minor GC, live objects are
   copied from Eden to a Survivor space; objects that survive multiple GCs are promoted
   to Old Generation. Two survivor spaces (S0/S1) allow copying without fragmentation —
   only one is active at a time; the other is the destination.

Q: What replaced PermGen in Java 8 and why?
A: Metaspace replaced PermGen. PermGen was a fixed-size portion of the Java heap used for
   class metadata, frequently causing OutOfMemoryError: PermGen space — especially in
   web apps that deploy many JSPs, Spring beans, or Hibernate-generated proxies. Metaspace
   uses native (off-heap) memory and auto-expands, virtually eliminating PermGen OOM.
   You can still limit it with -XX:MaxMetaspaceSize to prevent unbounded native memory use.

Q: What is object header overhead in Java?
A: Every Java object has an object header of typically 12–16 bytes on a 64-bit JVM with
   compressed oops: an 8-byte mark word (hash, GC age, lock state) and a 4-byte compressed
   class pointer. Even an empty object (new Object()) consumes 16 bytes. This overhead
   matters for large arrays of small objects — prefer arrays of primitives or flat data
   layouts (records with primitive fields) over many small objects.
