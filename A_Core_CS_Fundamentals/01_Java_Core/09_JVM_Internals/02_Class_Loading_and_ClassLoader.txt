CLASS LOADING AND CLASSLOADERS
================================

CLASS LOADING PHASES
---------------------
  When the JVM first references a class, it goes through three phases:

  1. LOADING
  -----------
  The class loader locates and reads the .class file (binary bytecode).
  Creates a java.lang.Class object representing the class in the method area.
  Sources: filesystem, JAR, URL, generated in-memory, network.

  2. LINKING
  -----------
  a) Verification:
     Validates the bytecode against JVM spec constraints.
     Ensures no stack overflow in method bodies, correct type usage, no illegal jumps.
     Security gate — prevents malformed or malicious bytecode from executing.

  b) Preparation:
     Allocates memory for class-level (static) fields.
     Initializes them to default values (0, null, false) — NOT the declared values yet.

  c) Resolution:
     Replaces symbolic references (e.g., "com.example.Foo.bar") in the constant pool
     with direct memory references (pointers).
     May be eager (at load time) or lazy (at first use).

  3. INITIALIZATION
  ------------------
  Executes static initializer blocks and assigns declared values to static fields,
  in textual order from top to bottom.

  class Foo {
      static int X = 10;           // executed during initialization
      static { System.out.println("Foo initialized!"); }
  }

  Initialization is guaranteed to happen exactly once per class per JVM, and is
  thread-safe (synchronized by the JVM).

BUILT-IN CLASS LOADERS
-----------------------
  Bootstrap ClassLoader:
  - Written in C/C++ (not a Java class — ClassLoader.getParent() returns null for it)
  - Loads core Java classes: java.lang.*, java.util.*, etc.
  - Reads from $JAVA_HOME/lib (Java 8) or java.base module (Java 9+)

  Platform ClassLoader (Extension ClassLoader before Java 9):
  - Parent: Bootstrap
  - Loads JDK extension modules and platform classes
  - Java 9+: loads java.* and javax.* modules not in Bootstrap

  Application ClassLoader (System ClassLoader):
  - Parent: Platform
  - Loads classes from the application classpath (-cp, CLASSPATH env var)
  - Default loader for user-defined classes

  Custom ClassLoader:
  - Parent: Application (by default)
  - Extends java.lang.ClassLoader
  - Used by: application servers, OSGi, hot-reload, encryption/obfuscation

DELEGATION MODEL (PARENT-FIRST)
---------------------------------
  When asked to load a class, each ClassLoader:
  1. Delegates to parent first
  2. Only loads itself if parent returns null (class not found by parent)

  This ensures:
  - Core classes are always loaded by Bootstrap (tamper-proof)
  - No duplicate class loading by accident (two loaders → two different Class objects!)
  - Security: user cannot override java.lang.String

  // Class identity:
  // Two classes loaded by DIFFERENT ClassLoaders are considered different classes
  // even if same binary name — causes ClassCastException!

  // Check which ClassLoader loaded a class:
  System.out.println(String.class.getClassLoader());          // null = Bootstrap
  System.out.println(MyClass.class.getClassLoader());         // Application CL
  System.out.println(Thread.currentThread().getContextClassLoader()); // context CL

CUSTOM CLASS LOADER
--------------------
  public class CustomClassLoader extends ClassLoader {

      @Override
      protected Class<?> findClass(String name) throws ClassNotFoundException {
          byte[] bytecode = loadBytesFromSomewhere(name);
          if (bytecode == null) throw new ClassNotFoundException(name);
          return defineClass(name, bytecode, 0, bytecode.length);
      }

      private byte[] loadBytesFromSomewhere(String name) {
          // Load encrypted, remote, or dynamically generated bytecode
          String path = name.replace('.', '/') + ".class";
          try (InputStream is = getClass().getClassLoader().getResourceAsStream(path)) {
              return is != null ? is.readAllBytes() : null;
          } catch (IOException e) { return null; }
      }
  }

  // Use custom loader:
  ClassLoader cl = new CustomClassLoader();
  Class<?> cls = cl.loadClass("com.example.MyClass");
  Object obj = cls.getDeclaredConstructor().newInstance();

CLASS LOADER CONTEXT IN FRAMEWORKS
------------------------------------
  Application servers (Tomcat, JBoss) use hierarchical class loaders:
  - Different web apps get different ClassLoaders → isolation between deployments
  - Shared libraries loaded by a common parent loader
  - Hot redeploy: new ClassLoader for the new version; old one GC'd

  Thread Context ClassLoader (TCCL):
  - Set per-thread: Thread.currentThread().setContextClassLoader(cl)
  - JDBC drivers, JNDI, SPI use TCCL to find implementations
  - Service loaders (java.util.ServiceLoader) use context ClassLoader by default

  ServiceLoader:
  ServiceLoader<Plugin> loader = ServiceLoader.load(Plugin.class);
  for (Plugin p : loader) { p.execute(); }
  // Finds all classes in META-INF/services/com.example.Plugin
  // Uses context ClassLoader to locate the service files

CLASS UNLOADING
----------------
  A class can be unloaded (and its ClassLoader GC'd) only when:
  - The ClassLoader instance is no longer reachable
  - No instances of the class exist
  - No Class objects for the class are reachable

  Classes loaded by Bootstrap, Platform, and Application loaders are NEVER unloaded
  (those loaders are always reachable).
  Only custom ClassLoaders (e.g., per-webapp) can be unloaded — key to hot redeploy.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What are the three built-in class loaders and what does each load?
A: Bootstrap ClassLoader: loads core Java classes (java.lang.*, java.util.*) from the
   JDK itself. Platform ClassLoader (formerly Extension): loads JDK platform classes and
   modules beyond the core. Application ClassLoader: loads classes from the application's
   classpath. They form a delegation chain: Application → Platform → Bootstrap.

Q: Why does the ClassLoader delegation model use parent-first?
A: Parent-first delegation ensures that core Java classes (java.lang.String, etc.) are
   always loaded from the trusted JDK by the Bootstrap ClassLoader, not overridden by
   user code. It prevents multiple loading of the same class by different loaders in the
   hierarchy. It enforces a consistent, tamper-proof contract for standard API classes.

Q: What happens when two ClassLoaders load the same class?
A: They produce two distinct Class objects. Objects from one are not assignable to the
   other — you get a ClassCastException even though both are "the same class" by name.
   This is why application servers use isolated ClassLoaders per webapp: different webapps
   can have different versions of the same library without conflict.

Q: When would you write a custom ClassLoader?
A: When you need to: (1) load classes from a non-standard location (database, network,
   encrypted JAR); (2) instrument or transform bytecode at load time (e.g., AOP, coverage
   tools like JaCoCo); (3) implement hot-reload (create a new ClassLoader with updated
   classes, discard the old one); (4) provide class isolation between components (OSGi,
   application servers). You override findClass() and use defineClass() to turn raw
   bytecode into a Class object.
