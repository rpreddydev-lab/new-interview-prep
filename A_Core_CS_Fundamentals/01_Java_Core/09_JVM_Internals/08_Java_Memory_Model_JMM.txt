JAVA MEMORY MODEL (JMM)
========================
  (This is the JVM-level memory model — see also:
   07_Multithreading_and_Concurrency/20_Memory_Consistency_and_Happens_Before.txt
   for a detailed treatment of happens-before rules and concurrency implications.)

OVERVIEW
---------
  The Java Memory Model (JMM), defined in Chapter 17 of the Java Language Specification,
  specifies how threads interact through memory. It defines:
  - When writes made by one thread become visible to other threads
  - What orderings of operations threads can observe
  - The guarantees provided by synchronization constructs

  Without the JMM's guarantees, hardware and compiler optimizations (instruction reordering,
  caching) could cause programs to behave incorrectly in multithreaded contexts.

MEMORY VISIBILITY PROBLEM
--------------------------
  Modern CPUs have multi-level caches (L1, L2, L3) and write buffers.
  A thread's writes may be in CPU cache and not visible to other threads on other cores.

  Thread A:                    Thread B (on another core):
  x = 1;                       while (ready == false) {} // may spin forever
  ready = true;                System.out.println(x);    // may print 0!

  Without synchronization, Thread B may see a stale value of ready, or see ready=true
  but still see the old value of x — due to CPU caching and instruction reordering.

JMM KEY CONCEPTS
-----------------
  Main Memory vs Working Memory (conceptual model):
  - Each thread has a conceptual "working memory" (L1 cache, registers)
  - Main memory holds the authoritative state
  - Threads read from and write to working memory; synchronization flushes to main memory

  Actions:
  - Read/write of volatile fields
  - Lock (entering synchronized)
  - Unlock (exiting synchronized)
  - Thread start/join
  - Object creation (construction completes before constructor returns)

HAPPENS-BEFORE (HB) RELATIONSHIP
----------------------------------
  Action A happens-before Action B means:
  1. A's results are visible to B (memory visibility)
  2. A occurs before B in the program's observable execution order

  Key HB rules (summary — full detail in 20_Memory_Consistency_and_Happens_Before.txt):
  1. Program order: each action in a thread HB the next action in that thread
  2. Monitor lock: unlock of a monitor HB all subsequent locks of the same monitor
  3. Volatile write: write to volatile field HB all subsequent reads of that field
  4. Thread start: Thread.start() HB all actions in the new thread
  5. Thread termination: all actions in thread T HB Thread.join(T) returning
  6. Transitivity: if A HB B and B HB C, then A HB C

SAFE PUBLICATION
-----------------
  An object is "safely published" if its construction completes before other threads see it.
  Without safe publication, another thread might see a partially constructed object.

  Safe publication idioms:
  1. Initialize in static initializer (class loading is safe):
     static final SomeObject obj = new SomeObject();

  2. Store in a volatile field:
     volatile SomeObject obj = new SomeObject();

  3. Store in a final field:
     final SomeObject obj = new SomeObject();  // safe if 'this' doesn't escape

  4. Store after locking:
     synchronized(lock) { obj = new SomeObject(); }

  // Unsafe publication (may expose partially initialized object):
  SomeObject obj;   // non-volatile, non-final, non-synchronized
  // Thread A:
  obj = new SomeObject(); // reference stored before constructor may complete (CPU reorder)
  // Thread B:
  obj.use();  // may see uninitialized fields!

FINAL FIELDS AND SAFE CONSTRUCTION
------------------------------------
  final fields have a special JMM guarantee: once an object is safely published,
  all threads that access the object through any reference see the fully initialized
  final fields (written during construction).

  class ImmutablePoint {
      final int x;
      final int y;
      ImmutablePoint(int x, int y) { this.x = x; this.y = y; }
  }

  // Once the ImmutablePoint is safely published (e.g., in a volatile or final field),
  // all readers see x and y as initialized — no synchronization needed on reads.

  // Constructor escape (anti-pattern) — invalidates final field guarantee:
  class Bad {
      final int value;
      Bad(Registry r) {
          r.register(this);  // 'this' escapes before constructor completes!
          this.value = 42;   // may not be visible to threads seeing 'this' from registry
      }
  }

DATA RACE
----------
  A data race occurs when:
  - Two threads access the same variable concurrently
  - At least one access is a write
  - There is no happens-before relationship between them

  Data races produce undefined behavior — any outcome is possible.
  Eliminate data races with synchronized, volatile, or java.util.concurrent constructs.

JMM AND COMPILER/CPU OPTIMIZATIONS
-------------------------------------
  The JMM permits compilers and CPUs to reorder operations within a thread,
  as long as the result observed by THAT THREAD is the same (as-if-serial).
  However, other threads may observe a different order.

  Memory barriers are instructions that prevent reordering:
  - LoadLoad barrier: prevents reordering of two loads
  - StoreStore barrier: prevents reordering of two stores
  - LoadStore / StoreLoad barriers
  Volatile writes/reads and synchronized blocks insert appropriate barriers.

JMM AND IMMUTABLE OBJECTS
--------------------------
  Truly immutable objects (all fields final, no mutation after construction,
  no constructor escape) are inherently thread-safe — they can be shared freely
  without synchronization.

  Effectively immutable: fields are not final but never mutated after safe publication.
  These are also thread-safe IF safely published.

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the Java Memory Model?
A: The Java Memory Model (JMM) defines the rules for how threads interact through memory.
   It specifies when a write by one thread becomes visible to other threads, what
   orderings of operations are observable, and what guarantees are provided by
   synchronization constructs (volatile, synchronized, Thread.start/join). Without the
   JMM, hardware caching and compiler/CPU reordering would make concurrent programs
   unpredictable. The JMM uses the happens-before relationship to define visibility
   and ordering guarantees.

Q: What is a data race and how do you prevent it?
A: A data race occurs when two threads access a shared variable concurrently, at least
   one access is a write, and there is no happens-before relationship between them.
   Data races lead to undefined behavior — any value may be seen. Prevention: use
   synchronized to establish a monitor lock HB relationship, declare the field volatile
   for single variables (visibility without mutual exclusion), or use atomic classes
   (AtomicInteger etc.) for compound operations.

Q: Why are final fields important for thread safety?
A: Final fields in Java have a special JMM guarantee: once an object is safely published
   (made visible via a volatile write, synchronized release, or static initialization),
   any thread accessing it through any reference sees the fully initialized values of all
   final fields, even without synchronization. This makes immutable objects (all fields
   final, no mutation after construction) inherently thread-safe — no synchronization is
   needed to share them across threads.

Q: What is constructor escape and why is it dangerous?
A: Constructor escape occurs when the this reference leaks out of the constructor before
   construction completes — via passing this to another object, publishing it to a static
   field, or starting a thread inside the constructor. This invalidates the JMM's final
   field guarantee: other threads may access the object and see uninitialized final fields.
   It also creates threading hazards. Fix: never let this escape the constructor; if you need
   to register the object, use a factory method that completes construction first.
