JVM ARCHITECTURE
=================

OVERVIEW
---------
  The Java Virtual Machine (JVM) is an abstract computing machine that:
  1. Loads .class bytecode files
  2. Verifies the bytecode
  3. Interprets/compiles to native machine code
  4. Manages memory (heap, stack, metaspace)
  5. Provides garbage collection
  6. Enforces security and type safety

  "Write Once, Run Anywhere" — Java source compiles to platform-independent bytecode;
  the JVM translates to native code at runtime.

CLASS LOADER SUBSYSTEM
-----------------------
  Responsible for loading, linking, and initializing classes.

  1. Loading — reads .class files from filesystem, JARs, network
     - Bootstrap ClassLoader: built-in (C++), loads core java.* classes
     - Extension/Platform ClassLoader: loads java.ext.dirs / JDK modules (Java 9+)
     - Application ClassLoader: loads from classpath (user classes)

  2. Linking:
     a. Verification — validates bytecode against JVM spec (security)
     b. Preparation — allocates memory for static fields, sets defaults
     c. Resolution — resolves symbolic references to direct references (classes, methods, fields)

  3. Initialization — executes static initializers and static field assignments

  Delegation model (parent-first):
  Each classloader delegates to its parent before loading itself.
  Bootstrap → Platform → Application → Custom
  Ensures core classes (java.lang.String) can't be overridden by user code.

RUNTIME DATA AREAS
-------------------
  Method Area (Metaspace in Java 8+):
  - Stores class metadata: class structure, method bytecode, runtime constant pool, static variables
  - Shared across all threads
  - In Java 8+: off-heap (native memory) — no PermGen OOM (still possible but much rarer)

  Heap:
  - All object instances and arrays
  - Shared across all threads
  - Divided into Young Generation (Eden, Survivor S0/S1) + Old Generation
  - GC managed

  JVM Stack (per thread):
  - One frame per method call
  - Each frame contains: local variables array, operand stack, reference to runtime constant pool
  - Fixed size or dynamic; StackOverflowError on overflow

  PC Register (Program Counter, per thread):
  - Address of the currently executing JVM instruction

  Native Method Stack (per thread):
  - Used by native (C/C++) methods invoked via JNI

EXECUTION ENGINE
-----------------
  Interpreter:
  - Reads and executes bytecode instructions one at a time
  - Fast startup but slow execution (no optimization)

  JIT Compiler (Just-In-Time):
  - Monitors "hot" methods (frequently called)
  - Compiles bytecode to native machine code at runtime
  - Optimizations: inlining, dead code elimination, loop unrolling, escape analysis
  - Client (C1): fast compilation, fewer optimizations
  - Server (C2): aggressive optimization, slower compilation — used for long-running apps
  - Tiered Compilation (default since Java 8): starts with C1, promotes to C2 for hotspots

  GC (Garbage Collector):
  - Automatically reclaims memory of unreachable objects
  - Multiple algorithms available (Serial, Parallel, G1, ZGC, Shenandoah)

JVM STARTUP SEQUENCE
---------------------
  1. OS loads JVM executable
  2. JVM initializes subsystems (class loaders, GC, JIT)
  3. Bootstrap class loader loads core classes (java.lang.*, etc.)
  4. Main class located and loaded
  5. main(String[] args) invoked
  6. Application runs; JIT compiles hot methods
  7. On exit: finalizers (deprecated) → GC → JVM shutdown hooks → JVM exits

JVM IMPLEMENTATIONS
--------------------
  HotSpot (Oracle/OpenJDK) — reference implementation, most widely used
  GraalVM               — polyglot VM, supports native image compilation (ahead-of-time)
  OpenJ9 (IBM)          — optimized for cloud, lower footprint
  Android (ART)         — Android's JVM-compatible runtime (uses DEX bytecode)

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What are the main components of the JVM?
A: (1) Class Loader Subsystem — loads, links, and initializes classes. (2) Runtime Data Areas
   — Method Area (class metadata), Heap (objects), JVM Stack (method frames per thread),
   PC Register (current instruction per thread), Native Method Stack. (3) Execution Engine —
   Interpreter, JIT Compiler, and Garbage Collector. (4) Native Method Interface (JNI) —
   bridges Java and native code. These components work together to load bytecode, manage
   memory, execute programs, and reclaim unused objects.

Q: What is the difference between the JVM stack and the heap?
A: The JVM stack is per-thread and stores method call frames (local variables, operand stack).
   Primitive values and object references are on the stack; the actual objects they reference
   are on the heap. The heap is shared across all threads and holds all object instances and
   arrays. Stack memory is automatically reclaimed when a method returns (LIFO); heap memory
   is reclaimed by garbage collection.

Q: What replaced PermGen in Java 8?
A: Metaspace. PermGen was a fixed-size heap region for class metadata that frequently caused
   OutOfMemoryError: PermGen space when many classes were loaded. Metaspace uses native (off-heap)
   memory and grows dynamically, eliminating the fixed size constraint. By default it's unbounded
   (limited only by available native memory). You can cap it with -XX:MaxMetaspaceSize.

Q: What is the class loader delegation model?
A: The parent-first delegation model means each class loader asks its parent to load a class
   before trying itself: Application → Platform → Bootstrap. The Bootstrap ClassLoader has no
   parent. This ensures core Java classes (java.lang.String, etc.) are always loaded from the
   JDK rather than being overridden by user code, maintaining security and consistency.
