COLLECTIONS INTERNALS: HASHMAP DEEP DIVE
==========================================

OVERVIEW
---------
  HashMap<K,V> is the most commonly used Map in Java and a critical interview topic.
  Understanding its internals demonstrates strong Java knowledge.

  Key characteristics:
  - Not thread-safe
  - Allows one null key and multiple null values
  - No guaranteed iteration order
  - Default initial capacity: 16 (must be power of 2)
  - Default load factor: 0.75
  - Java 7: chaining with linked list
  - Java 8+: hybrid — linked list for small buckets, Red-Black tree for large buckets

INTERNAL DATA STRUCTURES
-------------------------
  // Simplified internal representation:
  transient Node<K,V>[] table;  // array of buckets (size = capacity)
  int size;                      // number of key-value mappings
  int modCount;                  // modification count (for fail-fast iterators)
  int threshold;                 // next resize trigger = capacity × loadFactor
  final float loadFactor;

  // Java 8 Node (linked list node)
  static class Node<K,V> implements Map.Entry<K,V> {
      final int hash;
      final K key;
      V value;
      Node<K,V> next;  // linked list chain
  }

  // Java 8 TreeNode (Red-Black tree node) — used when bucket is treeified
  static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> {
      TreeNode<K,V> parent, left, right, prev;
      boolean red;
  }

HASHING MECHANISM
------------------
  Step 1: Compute key.hashCode()
  Step 2: Spread the hash — HashMap applies a secondary hash (perturbation):
    static final int hash(Object key) {
        int h;
        return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    }
    // XOR high bits into low bits — reduces collisions for poor hashCode implementations

  Step 3: Find bucket index:
    index = (capacity - 1) & hash
    // Equivalent to hash % capacity, but faster (bitwise AND works because capacity is power of 2)

  Example:
    Key: "hello", hashCode() = 99162322
    hash = 99162322 ^ (99162322 >>> 16) = 99162322 ^ 1513 = 99163819
    With capacity 16: index = 15 & 99163819 = 11

PUT OPERATION (Step by Step)
------------------------------
  map.put(key, value):
  1. Compute hash = hash(key)
  2. Compute bucket index = (capacity-1) & hash
  3. If bucket is empty → create new Node, insert at bucket[index]
  4. If bucket has nodes:
     a. Check first node: if hash matches AND (key == existing || key.equals(existing)) → UPDATE value
     b. If bucket is a TreeNode → delegate to Red-Black tree insert
     c. Otherwise iterate linked list:
        - If found same key → update value
        - If end reached → append new Node
        - If linked list size reaches TREEIFY_THRESHOLD (8) → treeify (if capacity ≥ 64)
  5. If size > threshold → resize (double capacity, rehash all entries)

  // Pseudo-code:
  if (bucket[i] == null) {
      bucket[i] = new Node(hash, key, value, null);
  } else {
      // find or append
  }
  if (++size > threshold) resize();

GET OPERATION (Step by Step)
------------------------------
  map.get(key):
  1. Compute hash = hash(key)
  2. Compute bucket index = (capacity-1) & hash
  3. If bucket is null → return null
  4. Check first node: if hash matches AND key matches → return value
  5. If TreeNode → search Red-Black tree (O(log n))
  6. Otherwise traverse linked list (O(n) worst case)

TREEIFICATION (JAVA 8+)
------------------------
  When a single bucket's linked list reaches 8 entries:
    - AND the overall array capacity is ≥ 64
    - → Convert the linked list to a Red-Black tree (treeify)
    - Tree operations: O(log n) vs O(n) for linked list

  When does it un-treeify (back to linked list)?
    - When entries in a bucket fall to ≤ 6 (UNTREEIFY_THRESHOLD = 6)
    - During resize, bucket splits may fall below threshold

  Constants:
    TREEIFY_THRESHOLD = 8   // convert to tree
    UNTREEIFY_THRESHOLD = 6 // convert back to list
    MIN_TREEIFY_CAPACITY = 64 // tree only if overall capacity ≥ 64; else resize instead

RESIZE (REHASHING)
-------------------
  Trigger: size > threshold (= capacity × loadFactor)
  Process:
  1. Double the capacity: newCapacity = oldCapacity × 2
  2. Create new bucket array of newCapacity
  3. Rehash: for each existing Node, recompute index:
       newIndex = hash & (newCapacity - 1)
     Because capacity doubles, each bucket can split into two (same index or index + oldCapacity)
  4. Move all Nodes to new positions

  Rehashing is O(n) but happens infrequently (amortized O(1) per put).
  Java 8 optimization: entries either stay at same bucket index or move to index + oldCapacity
  (determined by one bit of the hash) — no full recompute needed.

LOAD FACTOR TRADEOFFS
----------------------
  Load Factor  | Collisions  | Memory    | When to use
  -------------|-------------|-----------|----------------------------
  0.25 (low)   | Very few    | Wasteful  | Performance-critical, lots of lookups
  0.75 (default)| Balanced   | Balanced  | General use
  0.95 (high)  | Many        | Efficient | Memory-constrained, accepts slower lookups

  Pre-sizing: If you know the number of entries, pre-size to avoid rehashing:
    int capacity = (int)(expectedSize / 0.75) + 1;
    Map<K,V> map = new HashMap<>(capacity);
    // Or: Guava Maps.newHashMapWithExpectedSize(expectedSize)

NULL KEY HANDLING
------------------
  HashMap allows one null key. It's always stored in bucket 0 (index 0).
    hash(null) = 0  (see hash() method — returns 0 for null)
    index = (capacity - 1) & 0 = 0

  Null values: unlimited — any value can be null.

WHY CAPACITY MUST BE POWER OF 2
---------------------------------
  index = hash & (capacity - 1)
  This works correctly ONLY when capacity is a power of 2:
    capacity = 16 → binary: 10000 → capacity-1 = 01111
    hash & 01111 = last 4 bits of hash = effectively hash % 16

  If capacity were not a power of 2, (capacity-1) would not be all-1s in binary,
  causing some buckets to never be used (uneven distribution).

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What happens when you put two keys with the same hashCode in a HashMap?
A: They map to the same bucket (hash collision). HashMap chains them:
   - Java 7: a linked list in the bucket (new entry prepended in Java 7, appended in Java 8)
   - Java 8+: linked list initially; converted to Red-Black tree if bucket size ≥ 8 and capacity ≥ 64
   get() then uses equals() to find the right key among all chained entries.

Q: What is the worst-case time complexity of HashMap.get()?
A: O(n) in Java 7 (all keys hash to same bucket → one long linked list).
   O(log n) in Java 8+ (treeification limits worst case for large buckets).

Q: Why does HashMap have default capacity 16 and load factor 0.75?
A: Capacity 16: small power-of-2 value — balances startup memory vs resize frequency.
   Load factor 0.75: empirical sweet spot between time (low collisions) and space (not too sparse).
   At 0.75, a well-distributed hash function results in most buckets having 0 or 1 entry.

Q: What happens if you don't override hashCode() for a class used as a HashMap key?
A: The default hashCode() (from Object) is based on memory address. Two logically equal objects
   with different memory addresses will hash to different buckets — get() will return null even
   after put() if a "new equal" object is used as the key. Always override both equals() AND hashCode().

Q: What is the purpose of the secondary hash (perturbation) in HashMap?
A: If hashCode() is poorly distributed (e.g., all values cluster in low bits), many keys would
   map to the same bucket. The secondary hash XORs high bits into low bits to spread hash values
   better across buckets, reducing collisions even with weak hashCode implementations.
