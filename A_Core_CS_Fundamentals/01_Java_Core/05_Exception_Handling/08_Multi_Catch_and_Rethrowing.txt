MULTI-CATCH AND RETHROWING EXCEPTIONS
=======================================

MULTI-CATCH (JAVA 7+)
-----------------------
  Catch multiple unrelated exception types in a SINGLE catch block using the pipe | operator:

  try {
      riskyOperation();
  } catch (IOException | SQLException e) {
      log.error("Data operation failed", e);
      throw new ServiceException("Data access error", e);
  }

  // Equivalent pre-Java 7 code (verbose):
  try {
      riskyOperation();
  } catch (IOException e) {
      log.error("IO failed", e);
      throw new ServiceException("Data access error", e);
  } catch (SQLException e) {
      log.error("SQL failed", e);
      throw new ServiceException("Data access error", e);
  }

MULTI-CATCH RULES
------------------
  Rule 1: The caught types MUST NOT share an inheritance relationship.
    catch (FileNotFoundException | IOException e)  // ❌ FileNotFoundException extends IOException
    catch (IOException | SQLException e)            // ✅ unrelated hierarchy

  Rule 2: The variable 'e' is IMPLICITLY FINAL — cannot be reassigned.
    catch (IOException | SQLException e) {
        e = new IOException("new");  // ❌ compile error — e is final
    }

  Rule 3: The inferred type of 'e' is the COMMON SUPERTYPE of all listed exception types.
    // If IOException and SQLException have no common parent except Exception,
    // 'e' is of type Exception in terms of what you can call on it.
    // But if you rethrow, Java 7+ does type-precise rethrowing (see below).

TYPE-PRECISE RETHROWING (JAVA 7+)
------------------------------------
  Before Java 7, if you caught Exception and rethrew 'e', the method had to declare
  throws Exception (the compiler inferred the broad type of e).

  Java 7+ improved type inference for rethrowing:
  If you catch Exception and rethrow 'e' unchanged, the compiler tracks the ACTUAL
  types that can be thrown into that catch block and uses those for the throws declaration.

  // Before Java 7:
  public void process() throws Exception {  // must declare throws Exception
      try {
          riskyA();  // throws IOException
          riskyB();  // throws SQLException
      } catch (Exception e) {
          cleanup();
          throw e;   // must declare throws Exception (too broad)
      }
  }

  // Java 7+ — compiler tracks actual thrown types:
  public void process() throws IOException, SQLException {  // precise!
      try {
          riskyA();  // throws IOException
          riskyB();  // throws SQLException
      } catch (Exception e) {
          cleanup();
          throw e;   // Java 7+ knows only IOException or SQLException can reach here
      }
  }

  This only works when:
  1. The rethrown variable (e) is not reassigned inside the catch block
  2. The variable is final or effectively final

RETHROWING — PATTERNS AND USE CASES
--------------------------------------
  Pattern 1: Rethrow unchanged (add side effect like logging):
    catch (Exception e) {
        log.error("Failed during processing", e);
        throw e;  // propagate as-is
    }

  Pattern 2: Wrap in new exception (exception translation):
    catch (SQLException e) {
        throw new DataAccessException("Failed to load user", e);
    }

  Pattern 3: Rethrow as unchecked (checked → unchecked conversion):
    catch (IOException e) {
        throw new UncheckedIOException(e);  // Java 8 class for this pattern
    }
    // Or generic wrapping:
    catch (Exception e) {
        throw new RuntimeException("Unexpected error", e);
    }

  Pattern 4: Conditional rethrow (handle some, propagate others):
    catch (Exception e) {
        if (isTransient(e)) {
            retry();
        } else {
            throw e;  // don't handle non-transient errors here
        }
    }

UncheckedIOException (JAVA 8)
--------------------------------
  Java 8 introduced java.io.UncheckedIOException — a RuntimeException that wraps IOException.
  Use it when you need to use I/O operations in streams or lambdas:

  // Without UncheckedIOException — verbose:
  lines.stream().map(line -> {
      try { return processLine(line); }
      catch (IOException e) { throw new RuntimeException(e); }
  }).collect(Collectors.toList());

  // With UncheckedIOException — clear intent:
  lines.stream().map(line -> {
      try { return processLine(line); }
      catch (IOException e) { throw new UncheckedIOException(e); }
  }).collect(Collectors.toList());

SNEAKY THROWS PATTERN (ADVANCED)
-----------------------------------
  Using generics to throw checked exceptions as unchecked without wrapping.
  Used by Lombok @SneakyThrows and some low-level frameworks:

  @SuppressWarnings("unchecked")
  public static <T extends Throwable> void sneakyThrow(Throwable e) throws T {
      throw (T) e;  // type erasure means this cast doesn't actually check at runtime
  }

  // Usage:
  try {
      riskyCheckedOperation();
  } catch (Exception e) {
      sneakyThrow(e);  // throws checked as if unchecked — no wrapping, no stack trace overhead
  }

  Use with CAUTION: callers don't know a checked exception can escape.
  Considered a hack by many — prefer explicit wrapping in most cases.

COMPLETE EXAMPLE: LAYERED EXCEPTION HANDLING WITH RETHROW
-----------------------------------------------------------
  public class OrderService {

      public OrderDTO placeOrder(OrderRequest request) {
          try {
              validateRequest(request);
              Order order = orderRepository.save(toOrder(request));
              notificationService.sendConfirmation(order);
              return toDTO(order);

          } catch (ValidationException e) {
              // domain exception — rethrow as-is (caller handles it)
              throw e;

          } catch (DataAccessException e) {
              // repository exception — translate to service exception
              throw new OrderServiceException("Failed to persist order", e);

          } catch (NotificationException e) {
              // non-critical — log but don't fail the order
              log.warn("Order saved but notification failed for order {}", request.getId(), e);
              return toDTO(orderRepository.findById(request.getId()).orElseThrow());

          } catch (Exception e) {
              // unexpected — wrap and propagate with full context
              throw new OrderServiceException("Unexpected error placing order: " + request.getId(), e);
          }
      }
  }

COMPARISON TABLE: RETHROWING APPROACHES
------------------------------------------
  Approach                          | Stack Trace | Original Cause | Compile Requirement
  ----------------------------------|-------------|----------------|---------------------
  throw e (unchanged)               | Original    | Same           | Declare/catch same type
  throw new Ex(msg, e)              | New + chain | Preserved      | Declare/catch new type
  throw new RuntimeException(e)     | New + chain | Preserved      | None (unchecked)
  throw new UncheckedIOException(e) | New + chain | Preserved      | None (unchecked)
  sneakyThrow(e)                    | Original    | Same           | None (bypasses compile check)

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is multi-catch? What are its restrictions?
A: Multi-catch (Java 7+) allows catching multiple exception types in one catch block:
   catch (IOException | SQLException e). Restrictions: 1) The types cannot have an
   inheritance relationship (compiler error if one extends the other). 2) The variable
   is implicitly final — cannot be reassigned. 3) The exception types must be unrelated
   (not in the same hierarchy).

Q: What changed about rethrowing in Java 7?
A: Java 7 introduced "more precise rethrow." Before Java 7, if you caught Exception and
   rethrew it, the compiler forced you to declare throws Exception (broad). Java 7 improved
   type inference: if the catch variable is effectively final and rethrown unchanged, the
   compiler tracks exactly which checked exception types can actually reach that catch block
   and allows you to declare only those specific types in the throws clause.

Q: What is UncheckedIOException?
A: java.io.UncheckedIOException is a RuntimeException subclass introduced in Java 8
   that wraps IOException. It exists specifically to make it easier to use I/O operations
   in lambdas and streams (which cannot throw checked exceptions). Instead of wrapping in
   RuntimeException (generic), you wrap in UncheckedIOException (intent is clear). You can
   also unwrap the original IOException by calling getCause().
