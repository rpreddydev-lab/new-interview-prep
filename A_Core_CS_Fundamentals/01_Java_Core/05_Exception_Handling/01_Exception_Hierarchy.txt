EXCEPTION HIERARCHY IN JAVA
==============================

OVERVIEW
---------
  Java uses a class hierarchy rooted at java.lang.Throwable to represent all
  error and exceptional conditions. Understanding this hierarchy determines:
  - What must be declared/caught (checked)
  - What the compiler ignores (unchecked)
  - What signals JVM-level catastrophe (Error)

THE FULL HIERARCHY
-------------------
  java.lang.Throwable
  ├── java.lang.Error                          ← JVM/system-level failures (unchecked)
  │   ├── OutOfMemoryError
  │   ├── StackOverflowError
  │   ├── VirtualMachineError
  │   ├── AssertionError
  │   ├── ThreadDeath
  │   └── LinkageError
  │       ├── NoClassDefFoundError
  │       └── ClassFormatError
  └── java.lang.Exception                      ← Application-level exceptions
      ├── java.lang.RuntimeException            ← Unchecked exceptions
      │   ├── NullPointerException
      │   ├── ArrayIndexOutOfBoundsException
      │   ├── ClassCastException
      │   ├── ArithmeticException
      │   ├── IllegalArgumentException
      │   │   └── NumberFormatException
      │   ├── IllegalStateException
      │   ├── UnsupportedOperationException
      │   ├── ConcurrentModificationException
      │   └── IndexOutOfBoundsException
      │       └── StringIndexOutOfBoundsException
      └── (All other Exception subclasses)     ← Checked exceptions
          ├── IOException
          │   ├── FileNotFoundException
          │   └── SocketException
          ├── SQLException
          ├── ClassNotFoundException
          ├── CloneNotSupportedException
          ├── InterruptedException
          ├── ParseException
          └── ReflectiveOperationException

KEY CLASSIFICATION RULES
--------------------------
  Checked Exception:
    - Subclass of Exception but NOT RuntimeException
    - Compiler ENFORCES handling: declare with throws OR catch it
    - Represent recoverable external conditions (I/O, DB, network)
    - Example: FileNotFoundException, SQLException, InterruptedException

  Unchecked Exception (Runtime):
    - Subclass of RuntimeException (or Error)
    - Compiler does NOT enforce handling
    - Represent programming bugs, not external conditions
    - Example: NullPointerException, ArrayIndexOutOfBoundsException

  Error:
    - Subclass of Error
    - Signals JVM-level failures the application CANNOT recover from
    - You should NEVER catch Errors (except in special framework code)
    - Example: OutOfMemoryError, StackOverflowError

COMMON EXCEPTIONS REFERENCE
------------------------------
  Exception                     | Type       | Typical Cause
  ------------------------------|------------|----------------------------------------------
  NullPointerException          | Unchecked  | Dereferencing null
  ArrayIndexOutOfBoundsException| Unchecked  | Access beyond array length
  ClassCastException            | Unchecked  | Invalid downcast without instanceof check
  NumberFormatException         | Unchecked  | Integer.parseInt("abc")
  IllegalArgumentException      | Unchecked  | Invalid method argument
  IllegalStateException         | Unchecked  | Object in wrong state for operation
  StackOverflowError            | Error      | Infinite / too-deep recursion
  OutOfMemoryError              | Error      | Heap exhausted
  FileNotFoundException         | Checked    | File does not exist at path
  IOException                   | Checked    | General I/O failure
  SQLException                  | Checked    | Database error
  InterruptedException          | Checked    | Thread interrupted during sleep/wait
  ClassNotFoundException        | Checked    | Class not found during reflection load

THROWABLE KEY METHODS
-----------------------
  Method                  | Description
  ------------------------|------------------------------------------
  getMessage()            | Short human-readable message
  getLocalizedMessage()   | Localized version (override for i18n)
  getCause()              | Returns wrapped/chained Throwable
  initCause(Throwable)    | Sets the cause (legacy API — prefer constructor)
  toString()              | Class name + message
  printStackTrace()       | Print to stderr (avoid in production — use logging)
  getStackTrace()         | Returns StackTraceElement[]
  addSuppressed(Throwable)| Used by try-with-resources for suppressed exceptions
  getSuppressed()         | Get suppressed exceptions array

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between Error and Exception?
A: Both extend Throwable. Exception represents application-level conditions that can
   potentially be caught and recovered from. Error represents JVM/system-level failures
   (OutOfMemoryError, StackOverflowError) that the application typically cannot recover from.
   Errors are unchecked and should almost never be caught in application code.

Q: What is the base class for all exceptions?
A: java.lang.Throwable. Both Error and Exception extend it.

Q: Can you catch multiple exceptions in a single catch block?
A: Yes — since Java 7, using multi-catch: catch (IOException | SQLException e).
   The exception variable is implicitly final in this form.

Q: Is NullPointerException checked or unchecked? Why?
A: Unchecked (RuntimeException subclass) because it represents a programmer error
   (not checking for null before dereferencing). Checked NPE would require try/catch
   everywhere an object is accessed, which is impractical.

Q: Can you catch Error in Java?
A: Yes, syntactically you can. But you almost never SHOULD. Errors indicate conditions
   the JVM itself cannot recover from. Catching OutOfMemoryError, for example, may run
   your catch block without enough memory to execute it reliably. Only specialized
   frameworks (e.g., test runners catching AssertionError) have legitimate reasons to catch Errors.
