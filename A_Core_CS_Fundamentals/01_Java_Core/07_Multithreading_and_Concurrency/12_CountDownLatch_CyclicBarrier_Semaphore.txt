COUNTDOWNLATCH, CYCLICBARRIER, AND SEMAPHORE
=============================================

OVERVIEW
---------
  java.util.concurrent provides high-level synchronizers that solve common
  coordination patterns without requiring manual wait/notify:
  - CountDownLatch  — one-time "await all N tasks/events" gate
  - CyclicBarrier   — reusable "all N threads meet here before continuing" barrier
  - Semaphore       — limit concurrent access to N threads (resource pool gate)

COUNTDOWNLATCH
---------------
  Initialized with a count N. Threads call countDown() to decrement. Other threads
  call await() to block until the count reaches zero. ONE-SHOT: cannot be reset.

  Use case: wait for N worker threads to complete before proceeding.

  int WORKERS = 5;
  CountDownLatch latch = new CountDownLatch(WORKERS);

  for (int i = 0; i < WORKERS; i++) {
      final int id = i;
      executor.submit(() -> {
          try {
              doWork(id);
          } finally {
              latch.countDown();  // always decrement, even on exception
          }
      });
  }

  latch.await();              // main thread waits until count = 0
  // OR:
  boolean done = latch.await(10, TimeUnit.SECONDS); // timed wait
  System.out.println("All workers done!");

  Other patterns:
  - Start gun: CountDownLatch(1) — all threads await(1), main calls countDown() to release all at once
  - Completion gate: await until N events have occurred (log initialization, service start, etc.)

CYCLICBARRIER
--------------
  All N parties call await() — ALL block until the last one arrives. Then all proceed.
  REUSABLE: resets automatically after all parties have passed — can be used for multiple rounds.

  Use case: split a large computation into phases; all worker threads must complete
  each phase before any proceeds to the next.

  int THREADS = 4;
  CyclicBarrier barrier = new CyclicBarrier(THREADS, () -> {
      System.out.println("All threads reached barrier — starting next phase!");
      // optional barrier action runs once when all parties arrive
  });

  for (int i = 0; i < THREADS; i++) {
      final int id = i;
      executor.submit(() -> {
          for (int phase = 0; phase < 3; phase++) {
              processPhase(phase, id);
              try {
                  barrier.await();   // wait for all threads before next phase
              } catch (InterruptedException | BrokenBarrierException e) {
                  Thread.currentThread().interrupt();
                  return;
              }
          }
      });
  }

  BrokenBarrierException: thrown when the barrier is broken because:
  - A thread waiting at the barrier is interrupted
  - barrier.reset() is called while threads are waiting
  - The barrier action throws an exception

COUNTDOWNLATCH vs CYCLICBARRIER
---------------------------------
  Aspect                | CountDownLatch               | CyclicBarrier
  ----------------------|------------------------------|------------------------------
  Reusable?             | ❌ No (one-shot)              | ✅ Yes (resets after each cycle)
  Participants          | Any thread can countDown()   | All N registered parties must arrive
  Direction             | N → 0 (countdown to release) | All meet at point simultaneously
  Who waits?            | Some threads await()          | All N parties await()
  Barrier action        | ❌ No                         | ✅ Optional Runnable on break
  Exception on break    | N/A                           | BrokenBarrierException
  Use case              | Wait for N events/tasks       | Phased multi-thread coordination

SEMAPHORE
----------
  Controls access to a limited resource pool. N permits available.
  Threads acquire() a permit (blocking if none available) and release() when done.
  Non-binary semaphore: acts like a counting gate (unlike mutex which is binary).

  // Connection pool with at most 5 concurrent connections:
  Semaphore permits = new Semaphore(5);

  public Connection getConnection() throws InterruptedException {
      permits.acquire();          // blocks if all 5 permits taken
      return pool.getConnection();
  }

  public void releaseConnection(Connection conn) {
      pool.returnConnection(conn);
      permits.release();          // return permit — wake a waiting thread
  }

  // Try without blocking:
  if (permits.tryAcquire()) {
      try { useResource(); }
      finally { permits.release(); }
  } else {
      System.out.println("Resource unavailable");
  }

  // Acquire multiple permits at once:
  permits.acquire(3);   // take 3 permits
  permits.release(3);   // return 3

  // Fair semaphore (FIFO ordering):
  Semaphore fairSem = new Semaphore(3, true);

BINARY SEMAPHORE as MUTEX
--------------------------
  Semaphore(1) acts like a non-reentrant mutex — only one thread at a time.
  Unlike synchronized, the RELEASING thread doesn't need to be the one that acquired.
  This enables "hand-off" patterns or releasing from a different thread.

  Semaphore mutex = new Semaphore(1);
  mutex.acquire();
  try { criticalSection(); }
  finally { mutex.release(); }

SEMAPHORE USE CASES
--------------------
  ✅ Connection pool / resource pool limiting
  ✅ Rate limiting (N requests per unit time)
  ✅ Bounded concurrent access (at most N threads processing at once)
  ✅ Producer signaling consumer (binary semaphore, starts at 0)
  ✅ Throttling parallel task execution

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the difference between CountDownLatch and CyclicBarrier?
A: CountDownLatch is one-shot: initialized with N, any thread can countDown(), and
   awaiting threads are released when count reaches zero. CyclicBarrier is reusable:
   all N registered parties must call await() — all block until the last arrives,
   then all proceed together (and the barrier resets for the next cycle). Use
   CountDownLatch for "wait until N events happen"; use CyclicBarrier for "all threads
   must finish phase X before any starts phase Y."

Q: What is a Semaphore and how does it differ from a mutex?
A: A Semaphore maintains N permits. Multiple threads can acquire permits up to the limit,
   blocking when all are taken. A mutex (binary semaphore, N=1) allows only one thread
   at a time. Unlike synchronized or ReentrantLock, a Semaphore can be RELEASED by a
   different thread than the one that acquired it — useful for producer-consumer signaling
   or cross-thread hand-off patterns.

Q: Can CyclicBarrier be reused after all parties arrive?
A: Yes — that's the key advantage over CountDownLatch. After all N parties have called
   await(), the barrier automatically resets and is ready for the next cycle. Threads can
   call await() again in the next iteration. The barrier can be broken (BrokenBarrierException
   thrown to all waiting threads) if a participant is interrupted or if reset() is called
   during waiting.
