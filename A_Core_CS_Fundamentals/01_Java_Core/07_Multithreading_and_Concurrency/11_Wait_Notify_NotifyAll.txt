WAIT, NOTIFY, AND NOTIFYALL
==============================

PURPOSE
--------
  Object.wait() / notify() / notifyAll() are the low-level Java mechanism for
  inter-thread communication — a thread can pause (wait) until another signals it.
  They are the foundation of the classic producer-consumer pattern (pre-Java 5).
  For new code, prefer Condition objects (ReentrantLock) or BlockingQueue.

THE MONITOR MODEL
------------------
  These methods operate on an object's MONITOR (intrinsic lock).
  A thread can only call wait(), notify(), or notifyAll() when it HOLDS the object's monitor.
  If called without owning the monitor, Java throws IllegalMonitorStateException.

  Acquire monitor → synchronized(obj) { ... }
  Inside the block: obj.wait() releases the monitor AND suspends the thread.
  When notified: thread reacquires the monitor before resuming.

THE METHODS
------------
  void wait()                 — release monitor, wait indefinitely until notified or interrupted
  void wait(long millis)      — release monitor, wait up to millis milliseconds
  void wait(long, int nanos)  — release monitor, wait with nanosecond precision
  void notify()               — wake ONE arbitrarily chosen waiting thread (which thread is JVM-specific)
  void notifyAll()            — wake ALL threads waiting on this monitor

  All three (wait/notify/notifyAll) must be called from within a synchronized block/method
  on the SAME object they are called on.

CORRECT USAGE PATTERN
-----------------------
  The canonical pattern for using wait() is ALWAYS inside a while loop, NOT an if:

  synchronized (sharedObj) {
      while (!condition) {         // ← WHILE, not IF
          sharedObj.wait();        // releases lock, suspends; reacquires before returning
      }
      // condition is now true — safe to proceed
  }

  Why while and not if?
  1. Spurious wakeups — JVM can wake a waiting thread without notify() being called (rare but real)
  2. Condition may have become false again between notify() and the thread reacquiring the lock
     (another thread may have consumed the item that made the condition true)
  3. notifyAll() wakes ALL waiters — only the one whose condition is actually true should proceed;
     the others must loop back and re-check

PRODUCER-CONSUMER WITH WAIT/NOTIFY
--------------------------------------
  public class BoundedBuffer {
      private final Queue<Integer> buffer = new LinkedList<>();
      private final int capacity;

      public BoundedBuffer(int capacity) { this.capacity = capacity; }

      public synchronized void produce(int item) throws InterruptedException {
          while (buffer.size() == capacity) {
              wait();                    // buffer full — wait for consumer
          }
          buffer.add(item);
          notifyAll();                   // wake waiting consumers (and other producers)
      }

      public synchronized int consume() throws InterruptedException {
          while (buffer.isEmpty()) {
              wait();                    // buffer empty — wait for producer
          }
          int item = buffer.poll();
          notifyAll();                   // wake waiting producers (buffer has space now)
          return item;
      }
  }

NOTIFY vs NOTIFYALL
---------------------
  notify():
    Wakes ONE arbitrary waiting thread. Which thread is JVM-implementation dependent.
    Use ONLY when:
    - All waiting threads are equivalent (same wait condition, same action when woken)
    - Exactly one thread can ever make progress at a time
    Otherwise, you risk missing a wakeup (wrong thread woken, condition not met for it).

  notifyAll():
    Wakes ALL waiting threads. Each one reacquires the lock in turn and re-checks condition.
    All threads that can't proceed go back to wait(). Safer and generally preferred.

    Trade-off: notifyAll() causes "thundering herd" — many threads wake and contend for
    the lock, but only one proceeds. For performance-critical code with many threads,
    use Condition.signal() with ReentrantLock (signals only threads waiting on that specific condition).

WAIT vs SLEEP REVISITED
-------------------------
  Aspect             | wait()                            | sleep()
  -------------------|-----------------------------------|---------------------------
  Releases lock?     | YES — releases the monitor        | NO — holds all locks
  Called on          | any Object (inside synchronized)  | Thread.sleep() (static)
  Woken by           | notify() / notifyAll() / timeout  | Timeout / interrupt
  Interrupted?       | Yes — throws InterruptedException | Yes — throws InterruptedException
  Re-acquires lock?  | Yes — before returning            | N/A

ILLEGALMONITORSTATEEXCEPTION
------------------------------
  Thrown when wait/notify/notifyAll is called WITHOUT holding the object's monitor:

  // ❌ IllegalMonitorStateException:
  Object obj = new Object();
  obj.wait();  // not inside synchronized(obj) block!

  // ✅ Correct:
  synchronized (obj) {
      obj.wait();
  }

MODERN ALTERNATIVE: Condition (ReentrantLock)
----------------------------------------------
  Condition offers multiple wait-sets per lock and interruptible await:

  ReentrantLock lock = new ReentrantLock();
  Condition notFull  = lock.newCondition();
  Condition notEmpty = lock.newCondition();

  // Producer:
  lock.lock();
  try {
      while (buffer.isFull()) notFull.await();
      buffer.add(item);
      notEmpty.signal();  // only wake consumers, not other producers
  } finally { lock.unlock(); }

  // Consumer:
  lock.lock();
  try {
      while (buffer.isEmpty()) notEmpty.await();
      T item = buffer.remove();
      notFull.signal();   // only wake producers
  } finally { lock.unlock(); }

  Use Condition over wait/notifyAll for fine-grained signaling (signal only the
  relevant waiting threads, not all of them).

COMMON INTERVIEW QUESTIONS
---------------------------
Q: Why must wait() be called inside a synchronized block?
A: wait() releases the monitor lock — if the thread doesn't hold it, there's nothing
   to release. The JVM enforces this: calling wait() without holding the monitor
   throws IllegalMonitorStateException. The monitor is reacquired automatically
   before wait() returns, maintaining the invariant that the thread has exclusive
   access to the protected state.

Q: Why must wait() be called in a while loop, not an if statement?
A: Two reasons: (1) spurious wakeups — the JVM can wake a waiting thread without
   notify() being called (allowed by the JMM); (2) with notifyAll(), multiple threads
   wake up but the condition may only be true for one of them — the others must re-check
   and go back to waiting. Using while ensures the condition is always re-verified before
   proceeding.

Q: What is the difference between notify() and notifyAll()?
A: notify() wakes one arbitrary thread from the wait set. notifyAll() wakes all waiting
   threads — they contend for the lock and re-check their condition. notifyAll() is safer
   when different threads wait on different conditions (with a single lock): notify()
   might wake the "wrong" thread (one whose condition is not yet true), causing missed
   wakeups. Use Condition.signal() (with ReentrantLock) for per-condition signaling without
   the thundering herd problem.
