DEADLOCK, LIVELOCK, AND STARVATION
====================================

DEADLOCK
---------
  Deadlock occurs when two or more threads are each waiting for a lock held by another,
  forming a circular dependency — none can proceed.

  Classic example — two threads, two locks, acquired in opposite order:

  Object lockA = new Object();
  Object lockB = new Object();

  Thread t1 = new Thread(() -> {
      synchronized (lockA) {                  // T1 acquires A
          Thread.sleep(100);                  // pause to let T2 acquire B
          synchronized (lockB) {              // T1 waits for B — BLOCKED
              System.out.println("T1 done");
          }
      }
  });

  Thread t2 = new Thread(() -> {
      synchronized (lockB) {                  // T2 acquires B
          synchronized (lockA) {              // T2 waits for A — BLOCKED
              System.out.println("T2 done");
          }
      }
  });
  // T1 holds A, waits for B. T2 holds B, waits for A. Neither proceeds. Deadlock!

FOUR CONDITIONS FOR DEADLOCK (Coffman Conditions)
---------------------------------------------------
  ALL four must be true for deadlock to occur:
  1. Mutual Exclusion  — resources cannot be shared (locks are exclusive)
  2. Hold and Wait     — a thread holds one lock while waiting for another
  3. No Preemption     — locks cannot be forcibly taken from threads
  4. Circular Wait     — T1 → T2 → T3 → T1 (circular chain of waiting)

  Breaking ANY one condition prevents deadlock.

DEADLOCK PREVENTION STRATEGIES
---------------------------------
  1. LOCK ORDERING (most practical):
     Always acquire locks in the same global order across all threads.
       synchronized (Math.min(id1,id2) == id1 ? lockA : lockB) {
           synchronized (Math.min(id1,id2) == id1 ? lockB : lockA) { ... }
       }

  2. TIMED LOCK ACQUISITION (with ReentrantLock):
     if (lock1.tryLock(500, MILLISECONDS)) {
         try {
             if (lock2.tryLock(500, MILLISECONDS)) {
                 try { /* do work */ }
                 finally { lock2.unlock(); }
             }
             // else: couldn't get lock2 — release lock1, retry
         } finally { lock1.unlock(); }
     }

  3. LOCK HIERARCHY — assign a numeric rank to each lock; only acquire higher-ranked
     locks after lower-ranked ones.

  4. USE ONE LOCK — combine related state under one lock to eliminate the need
     for holding multiple locks simultaneously.

DEADLOCK DETECTION
--------------------
  Generate a thread dump: kill -3 <pid>  or jstack <pid>
  JVM detects monitor deadlocks and prints: "Found one Java-level deadlock"
  JVM does NOT automatically resolve deadlock — it only reports it.

  VisualVM, JConsole, and Java Flight Recorder can also detect deadlocks.

LIVELOCK
---------
  Threads are ACTIVE (not blocked) but make no progress because they keep
  reacting to each other's state — like two people in a hallway both stepping
  the same way to let each other pass.

  Example:
  volatile boolean resource1Taken = false, resource2Taken = false;

  // Thread 1: take resource1, then try resource2
  while (true) {
      if (!resource1Taken) {
          resource1Taken = true;
          if (resource2Taken) {
              resource1Taken = false;  // release and retry — keeps looping
          } else {
              // use both resources, done
              break;
          }
      }
  }
  // Thread 2 does the symmetric opposite — both loop forever yielding to each other

  Solution: introduce randomized backoff — threads wait a random time before retrying,
  reducing the chance of permanently synchronized conflicts.

STARVATION
-----------
  A thread is perpetually denied CPU time or lock access because other (often
  higher-priority) threads always win the race.

  Causes:
  - Priority inversion: high-priority thread waits for a lock held by a low-priority thread
    that never gets scheduled
  - Unfair lock (default ReentrantLock) — a thread may be repeatedly bypassed
  - Long synchronized critical sections that monopolize a lock

  Solutions:
  - Fair locks: new ReentrantLock(true) — FIFO ordering guarantees no thread starves
  - Thread priority adjustment (platform-dependent, use cautiously)
  - Reduce lock hold time — keep critical sections short

PRIORITY INVERSION
-------------------
  High-priority thread H waits for a lock held by low-priority thread L.
  Medium-priority thread M preempts L (because L has lower priority).
  Result: M effectively blocks H, even though H has higher priority than M.

  Classic real-world case: Mars Pathfinder 1997 — priority inversion caused resets.
  Solution: Priority inheritance — temporarily raise L's priority to H's while L holds the lock.
  Java does not natively implement priority inheritance. Use careful design instead.

COMPARISON TABLE
-----------------
  Problem     | Threads state      | Making progress? | Cause
  ------------|---------------------|-------------------|------------------------------
  Deadlock    | BLOCKED             | No               | Circular lock dependency
  Livelock    | RUNNABLE (spinning) | No               | Reacting to each other's state
  Starvation  | RUNNABLE or WAITING | Yes (others)     | One thread perpetually bypassed

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What are the four conditions necessary for deadlock?
A: Mutual exclusion (locks are exclusive), hold-and-wait (thread holds one lock while
   waiting for another), no preemption (locks can't be forcibly taken), and circular wait
   (circular chain of threads each waiting for the next). Breaking any one condition
   prevents deadlock. The most practical prevention: consistent lock ordering (eliminates
   circular wait) or timed tryLock() (eliminates indefinite hold-and-wait).

Q: What is the difference between deadlock and livelock?
A: In deadlock, threads are BLOCKED — completely stuck, consuming no CPU. In livelock,
   threads are RUNNABLE — actively executing code — but making no actual progress because
   they keep reacting to each other and backing off simultaneously. Both result in no
   forward progress, but livelock is harder to detect because threads appear "busy."

Q: How do you detect a deadlock in a Java application?
A: Generate a thread dump using kill -3 <pid> or jstack <pid>. The JVM's deadlock
   detector identifies threads in circular lock dependency and prints a "Found one
   Java-level deadlock" report with the thread names and the locks involved.
   VisualVM and JConsole also provide deadlock detection UI. Note: the JVM detects
   intrinsic lock deadlocks; ReentrantLock deadlocks are also reported in modern JVMs.

Q: How do you prevent deadlock?
A: The most reliable strategy is consistent lock ordering — always acquire multiple locks
   in the same predefined order across all threads, eliminating circular wait. Other
   strategies: use tryLock() with timeout (acquire with a deadline, release and retry if
   not obtained), minimize the number of locks held simultaneously, and keep critical
   sections short. Using higher-level concurrency constructs (java.util.concurrent) also
   reduces the need to manage multiple locks manually.
