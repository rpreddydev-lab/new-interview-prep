MEMORY CONSISTENCY AND HAPPENS-BEFORE
========================================

THE JAVA MEMORY MODEL (JMM)
-----------------------------
  The Java Memory Model (JMM) defines:
  - When changes made by one thread are GUARANTEED to be visible to other threads
  - Which compiler and CPU instruction reorderings are allowed
  - What "synchronization" means in terms of memory ordering

  Without the JMM's guarantees, the JIT compiler and CPU can:
  - Reorder instructions (for optimization)
  - Cache values in registers or CPU caches (visibility problem)
  - Delay writes to main memory

  The JMM defines the "happens-before" relationship as the mechanism for reasoning
  about memory visibility in concurrent programs.

HAPPENS-BEFORE DEFINITION
---------------------------
  If action A "happens-before" action B, then:
  1. A is visible to B — all writes made by A and actions before A are visible to B
  2. A is ordered before B — A appears to have executed before B

  Happens-before is TRANSITIVE: if A hb B and B hb C, then A hb C.
  Happens-before does NOT mean A executes before B in wall-clock time.
  It means: IF B reads a variable, it will see A's writes.

HAPPENS-BEFORE RULES (JMM)
----------------------------
  1. PROGRAM ORDER RULE:
     Within a single thread, each action happens-before every subsequent action
     in program order. (Within one thread, code appears to execute sequentially.)

  2. MONITOR LOCK RULE (synchronized):
     An unlock of a monitor happens-before every subsequent lock of THAT SAME monitor.
     ← This is why synchronized provides visibility: all writes before unlock are
       visible to any thread after it acquires the same lock.

  3. VOLATILE VARIABLE RULE:
     A write to a volatile field happens-before every subsequent read of THAT SAME field.
     ← Every thread reading the volatile sees the latest write.

  4. THREAD START RULE:
     A call to thread.start() happens-before any action in the started thread.
     ← The started thread sees all writes made before start() was called.

  5. THREAD TERMINATION RULE:
     All actions in a thread happen-before another thread successfully returns from join()
     on that thread, or isAlive() returning false.
     ← After join() returns, you're guaranteed to see all the joined thread's writes.

  6. INTERRUPTION RULE:
     A call to thread.interrupt() happens-before the interrupted thread detects it
     (via isInterrupted(), interrupted(), or catching InterruptedException).

  7. FINALIZER RULE:
     The end of a constructor happens-before the start of the finalizer for that object.

  8. TRANSITIVITY:
     If A hb B and B hb C, then A hb C.

ILLUSTRATING HAPPENS-BEFORE
-----------------------------
  // Thread A:
  int x = 42;
  synchronized (lock) {           // ← releases lock (unlock action)
      ready = true;
  }

  // Thread B:
  synchronized (lock) {           // ← acquires same lock
      if (ready) {
          System.out.println(x);  // guaranteed to see x == 42!
      }
  }

  Why is x == 42 guaranteed?
  - x = 42 hb unlock(lock)         [program order rule]
  - unlock(lock) hb lock(lock) in B [monitor lock rule]
  - lock(lock) in B hb read(x)      [program order rule in B]
  - Therefore: x = 42 hb read(x)   [transitivity]

  Without synchronization, B might see x == 0 (default) due to caching/reordering.

SAFE PUBLICATION
-----------------
  "Publication" means making an object available to other threads (storing a reference
  they can see). "Safe publication" guarantees that the published object's fields are
  fully initialized and visible.

  Four safe publication idioms:
  1. Assign to a final field (final fields are safely published via the happens-before
     guarantee from constructors)
  2. Use a volatile field to publish the reference
  3. Assign to a field guarded by a lock, and all reads use the same lock
  4. Publish via a static initializer or enum constant (class loading is thread-safe)

  // ❌ UNSAFE: object may be partially constructed when another thread sees reference
  Object obj = new MyObject();          // reference written before fields initialized (possible reorder)
  sharedRef = obj;                       // another thread may read partially initialized obj

  // ✅ SAFE: volatile prevents reordering of constructor + reference write:
  volatile Object sharedRef;
  sharedRef = new MyObject();           // volatile write: construction hb write; write hb read

DATA RACE
----------
  A data race occurs when:
  1. Two threads access the same variable concurrently
  2. At least one access is a WRITE
  3. They are NOT ordered by a happens-before relationship

  A data race is UNDEFINED BEHAVIOR in the JMM — any result is permitted.
  Specifically: values can appear out of thin air, previous values can reappear,
  writes may never be seen.

  Fix: use synchronized, volatile, or atomic operations — any that establish happens-before.

HAPPENS-BEFORE AND COMMON IDIOMS
-----------------------------------
  Pattern                          | HB guarantee
  ---------------------------------|---------------------------------------------
  synchronized block               | unlock hb lock (same monitor)
  volatile field write/read        | write hb subsequent read (same field)
  thread.start()                   | All pre-start writes hb started thread's actions
  thread.join()                    | Thread's actions hb join() return
  Future.get() completion          | Task's actions hb get() caller actions
  CountDownLatch.await()           | countDown()s hb await() return
  Semaphore.release()              | release hb acquire()
  BlockingQueue put() / take()     | put() hb take() of same element
  AtomicInteger.set/compareAndSet  | Atomic writes hb subsequent reads

FINAL FIELDS AND SAFE CONSTRUCTION
--------------------------------------
  The JMM has a special guarantee for FINAL fields:
  Once a constructor completes, any thread that obtains a reference to the object
  is guaranteed to see the correct values of all final fields — WITHOUT synchronization.

  public class ImmutablePoint {
      final int x;
      final int y;
      ImmutablePoint(int x, int y) { this.x = x; this.y = y; }
  }

  // Publishing via a data race is still unsafe — but if safely published,
  // final fields are guaranteed correctly seen.

  ⚠️ DO NOT let `this` escape during construction:
  // ❌ Unsafe construction: another thread may see partially initialized object
  class Broken {
      final int x;
      Broken() { x = 5; register(this); } // 'this' escapes before constructor done
  }

COMMON INTERVIEW QUESTIONS
---------------------------
Q: What is the happens-before relationship in the Java Memory Model?
A: Happens-before (hb) is the JMM's formal guarantee that if action A happens-before
   action B, then all writes by A (and everything before A) are visible to B. It defines
   when memory visibility is guaranteed between threads. Key rules: synchronized unlock hb
   subsequent lock (same monitor); volatile write hb subsequent read (same field); thread
   start() hb started thread's actions; joined thread's actions hb join() return.

Q: What is a data race? How does it differ from a race condition?
A: A data race is when two threads access the same field concurrently without a
   happens-before relationship, with at least one being a write. The JMM gives no
   guarantees for data-racing programs — any result is permitted (including reading
   stale, partial, or "out of thin air" values). A race condition is broader — the
   program's LOGIC is incorrect depending on thread timing, even if there's no formal
   data race (e.g., two threads both passing an "if balance > 0" check and both withdrawing).

Q: Why does volatile prevent reordering in double-checked locking?
A: The JMM guarantees that a volatile write happens-before a subsequent volatile read.
   Without volatile, the JIT may reorder: (1) allocate memory, (2) write reference to field,
   (3) initialize fields — so another thread sees a non-null (step 2) but uninitialized
   object (step 3 not yet done). With volatile, write to the field (step 2) cannot be
   reordered before the object is fully initialized (step 3), because all writes before
   a volatile write hb the volatile write.

Q: What guarantees do final fields provide?
A: The JMM provides a "freeze" guarantee for final fields: after an object's constructor
   completes, any thread that reads a reference to that object is guaranteed to see the
   correct (fully initialized) values of all final fields — even without synchronization.
   This is why immutable objects (all fields final) can be safely published. Caveat:
   the `this` reference must not escape during construction (before the constructor returns).
