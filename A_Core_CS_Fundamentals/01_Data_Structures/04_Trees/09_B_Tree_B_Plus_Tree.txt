================================================================
  B-TREE AND B+ TREE
================================================================

----------------------------------------------------------------
WHAT IS A B-TREE?
----------------------------------------------------------------
A B-Tree is a self-balancing, multi-way search tree optimized
for storage systems with large block sizes (disks, SSDs).

  Unlike binary trees (2 children per node), a B-Tree of
  order m allows each node to have UP TO m children and
  m-1 keys.

  Properties of B-Tree of order m:
    - Root: 1 to m-1 keys, 2 to m children
    - Internal nodes: ceil(m/2) to m children
    - All leaves at the SAME level (perfectly height-balanced)
    - Keys in each node are sorted
    - For a node with k keys, there are k+1 children

  Visualization (order 3, max 2 keys per node):
            [30, 70]
           /    |    \
      [10,20] [40,60] [80,90]

  Height of B-Tree with n keys:
    h = O(log_m(n))  where m = order
    For m=1000 and n=1 billion: h = log_1000(10^9) = 3
    Only 3 disk reads to find any key in 1 billion records!

  This is why databases use B-Trees: tall binary trees
  require O(log2 n) = 30 disk reads for 1 billion records,
  while a B-Tree of order 1000 needs only 3.

----------------------------------------------------------------
B+ TREE vs B-TREE
----------------------------------------------------------------
  The B+ Tree is the variant actually used in databases.

  B-Tree:
    - Data (values) stored in ALL nodes (internal + leaf)
    - Sequential scan requires traversal through tree

  B+ Tree:
    - Data stored ONLY in leaf nodes
    - Internal nodes store only KEYS (routing information)
    - Leaf nodes linked together in a DOUBLY LINKED LIST

  B+ Tree visualization:

    Internal nodes: [30, 70]          (keys only, no data)
                   /    |    \
    Leaf nodes: [10,20] [30,40,60] [70,80,90]  (keys + data)
                  <---> <---------> <-------->  (linked list)

  B+ Tree advantages:
    1. Internal nodes can hold MORE keys (no data) -> shallower tree
    2. Range queries: traverse the linked leaf list sequentially
    3. Full table scan: traverse leaf linked list, no tree traversal
    4. Consistent O(log n) time for all operations

  B+ Tree is used in:
    MySQL InnoDB (clustered and secondary indexes)
    PostgreSQL (default index)
    Oracle, SQL Server
    Most file systems (ext4, NTFS, HFS+)

----------------------------------------------------------------
COMPLEXITY
----------------------------------------------------------------
  Operation       B-Tree          B+ Tree
  ---------------------------------------------------------------
  Search          O(log_m n)      O(log_m n)
  Insert          O(log_m n)      O(log_m n)
  Delete          O(log_m n)      O(log_m n)
  Range query     O(log_m n + k)  O(log_m n + k)  k=result size
  Full scan       O(n log_m n)    O(n) via leaf list
  Space           O(n)            O(n)

  m = order (branching factor)
  With m = 1000, log_m n is extremely small in practice.

----------------------------------------------------------------
INSERT AND SPLIT
----------------------------------------------------------------
  B-Tree Insert:
    1. Find the correct leaf for the new key.
    2. If leaf has room (< m-1 keys): insert directly.
    3. If leaf is full: SPLIT the node.
       - Move median key up to parent.
       - Create two new nodes with keys less than / greater than median.
    4. If parent overflows: split parent recursively.
    5. If root splits: create new root (tree grows in height).

  Key point: B-Trees grow UPWARD (splits propagate up to root).
  This is why all leaves stay at the same level.

  Example split (order 3, max 2 keys per node):
    Node [10, 20, 30] -> full, insert needs split:
    Median = 20 moves up to parent.
    Left: [10], Right: [30]

----------------------------------------------------------------
WHY DATABASES USE B+ TREES
----------------------------------------------------------------
  1. Disk I/O is the bottleneck:
     A disk page is typically 4KB or 16KB.
     A B+ Tree node fills exactly one page.
     Higher branching factor -> fewer pages to read.

  2. Clustered index (InnoDB primary key):
     Data rows stored IN the leaf nodes of the B+ Tree.
     Range scan reads contiguous disk pages.

  3. Secondary index:
     Leaf nodes store (indexed_key, primary_key) pairs.
     Lookup: find in secondary B+ Tree, then fetch from
     primary B+ Tree (index seek + table lookup).

  4. Fill factor / page utilization:
     Nodes typically 60-90% full to minimize splits.
     Better fill factor -> fewer nodes -> faster traversal.

  5. Why not Red-Black Tree or AVL?
     They're binary (height = log2 n = 30 for 1 billion rows).
     30 disk reads per lookup is unacceptably slow.
     B+ Tree with order 1000 needs 3 reads instead of 30.

----------------------------------------------------------------
INTERVIEW QUESTIONS
----------------------------------------------------------------

Q: What is the key difference between a B-Tree and a B+ Tree?
A: In a B-Tree, data (values) is stored in all nodes (internal
   and leaf). In a B+ Tree, data is stored ONLY in leaf nodes;
   internal nodes store only keys for routing. Additionally,
   B+ Tree leaf nodes are connected in a doubly linked list,
   enabling efficient range scans and full table scans in O(n)
   instead of O(n log n) tree traversal. B+ Trees are preferred
   in databases because smaller internal nodes means higher
   branching factor, resulting in a shorter tree.

Q: Why do databases use B+ Trees instead of hash indexes?
A: B+ Trees support both point queries AND range queries
   (BETWEEN, >, <, ORDER BY, LIKE 'prefix%') with O(log n)
   time. Hash indexes only support point equality queries in
   O(1) average but cannot handle ranges. B+ Trees maintain
   sorted order, so the database can use the index for ORDER BY
   without a separate sort step. Hash indexes are faster for
   pure equality lookups but unusable for range scans.

Q: What is a clustered vs non-clustered (secondary) index?
A: A clustered index stores the actual data rows in the leaf
   nodes of the B+ Tree (MySQL InnoDB primary key). There is
   only one clustered index per table. A non-clustered
   (secondary) index stores (indexed_column, primary_key) in
   leaf nodes. To retrieve the full row, the database does a
   second B+ Tree lookup on the primary key ("double lookup"
   or "bookmark lookup"). Covering indexes avoid this by
   including all needed columns in the secondary index.

Q: What happens when a B+ Tree node is full and you insert?
A: The node splits: the median key moves up to the parent,
   and the node is divided into two nodes each with half the
   keys. If the parent is also full, it splits too, propagating
   up. If the root splits, a new root is created with one key,
   and the tree height increases by 1. This "growth from the
   top" ensures all leaves remain at the same level.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------
  1. Know the key B-Tree vs B+ Tree difference: data storage
     location and the leaf linked list in B+ Tree
  2. The height formula O(log_m n) with large m is why
     databases are fast -- mention this in system design
  3. Clustered vs secondary index is a very common SQL
     interview topic -- tie it back to B+ Tree structure
  4. B-Trees grow upward (root splits when full) --
     unlike BSTs which grow downward
  5. Fill factor: database pages are kept partially full
     to reduce splits -- mention this for storage system design
  6. For Java interviews, you'll never implement a B-Tree;
     instead discuss when to use it (DB indexes, file systems)
