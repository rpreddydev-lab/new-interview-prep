================================================================
  CONTAINER WITH MOST WATER (LC 11)
  Deep Dive
================================================================

This problem is a canonical example of the greedy two-pointer
insight: not just "use two pointers" but WHY we move the
shorter bar and why that's provably correct.

----------------------------------------------------------------
PROBLEM STATEMENT
----------------------------------------------------------------

  Given n vertical lines where line i has height[i],
  find two lines that, together with the x-axis, form a
  container that holds the most water.

  Return the maximum amount of water the container can hold.

  Input:  height = [1, 8, 6, 2, 5, 4, 8, 3, 7]
  Output: 49

  Constraints: n >= 2, height[i] >= 0

----------------------------------------------------------------
FORMULA
----------------------------------------------------------------

  Water between line i and line j (i < j):
    area = min(height[i], height[j]) * (j - i)

  We want to MAXIMIZE this area over all pairs (i, j).

----------------------------------------------------------------
BRUTE FORCE (O(n^2))
----------------------------------------------------------------

  Check all pairs. Obviously too slow for n=10^5.

    int maxArea = 0;
    for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
            maxArea = Math.max(maxArea, Math.min(height[i], height[j]) * (j - i));
        }
    }

----------------------------------------------------------------
TWO POINTER APPROACH (O(n))
----------------------------------------------------------------

  Start with the widest possible container: l=0, r=n-1.
  This gives maximum width. Then narrow the container, but
  try to increase the height to compensate.

  Greedy rule:
    - Move the SHORTER bar inward.

  Why? Suppose height[l] < height[r].
    - Current area = height[l] * (r - l)
    - If we move r inward (r--): width decreases, and the height is
      still limited by height[l] (or something smaller). Area CANNOT increase.
    - If we move l inward (l++): width decreases, but height might
      increase. This is our ONLY chance to find a larger area.
    - Therefore, moving l (the shorter bar) is the ONLY rational move.

  This is a proof by contradiction -- moving the taller bar can
  never find a better result.

----------------------------------------------------------------
JAVA CODE
----------------------------------------------------------------

  public int maxArea(int[] height) {
      int l = 0, r = height.length - 1;
      int maxArea = 0;

      while (l < r) {
          int area = Math.min(height[l], height[r]) * (r - l);
          maxArea = Math.max(maxArea, area);

          if (height[l] < height[r]) {
              l++;
          } else {
              r--;  // if equal, move either (here we move r)
          }
      }
      return maxArea;
  }

  Time:  O(n)  -- each pointer moves at most n times total
  Space: O(1)

----------------------------------------------------------------
TRACE THROUGH THE EXAMPLE
----------------------------------------------------------------

  height = [1, 8, 6, 2, 5, 4, 8, 3, 7]
  Indices:  0  1  2  3  4  5  6  7  8

  l  r  h[l]  h[r]  width  area   max    move
  0  8   1     7      8     8      8      l++ (1 < 7)
  1  8   8     7      7     49     49     r-- (8 >= 7)
  1  7   8     3      6     18     49     r-- (8 >= 3)
  1  6   8     8      5     40     49     r-- (tie)
  1  5   8     4      4     16     49     r-- (8 >= 4)
  1  4   8     5      3     15     49     r-- (8 >= 5)
  1  3   8     2      2     4      49     r-- (8 >= 2)
  1  2   8     6      1     6      49     r-- (8 >= 6)
  l=1, r=1 --> stop

  Answer: 49

----------------------------------------------------------------
EDGE CASES
----------------------------------------------------------------

  1. All bars same height:
     height = [5, 5, 5]
     Area = 5 * 2 = 10. Correct.

  2. Monotone increasing:
     height = [1, 2, 3, 4, 5]
     Best pair is often not the outer pair. Two pointers handles.

  3. Two bars only:
     height = [1, 2]
     l=0, r=1: area = min(1,2)*1 = 1. Return 1.

  4. Zero height bar:
     height = [0, 10, 0]
     Area with index 0 or 2 = 0. Best = 0 (correct behavior).

----------------------------------------------------------------
COMMON MISTAKES
----------------------------------------------------------------

  1. Moving the TALLER bar instead of the shorter:
     This is the #1 mistake. The logic seems counterintuitive but
     moving the taller bar cannot improve the area (proof above).

  2. Using l <= r instead of l < r:
     When l == r we're looking at one bar (can't form a container).

  3. Computing area AFTER moving (should compute BEFORE):
     Compute area first with current l and r, THEN decide movement.

  4. Not handling ties: when height[l] == height[r], move either one.
     Moving r-- is the common convention.

----------------------------------------------------------------
FOLLOW-UP QUESTIONS
----------------------------------------------------------------

  Q: What if you could choose any number of lines (not just 2)?
     --> Always choose the tallest two adjacent bars. Different problem.

  Q: Can the answer include the endpoints?
     --> Yes. The two outermost bars are the first pair checked.

  Q: What if heights are in a circular array?
     --> Slightly harder. Usually need different approach.

  Q: Can you do better than O(n)?
     --> No. You need to inspect every element at least once.

----------------------------------------------------------------
PROOF OF CORRECTNESS
----------------------------------------------------------------

  Claim: The greedy choice (move the shorter bar) never misses
  the optimal pair.

  Proof sketch:
    Suppose optimal pair is (i*, j*) with i* < j*.
    Two pointers will consider (l, r) as some point where l <= i* and r >= j*.
    
    Case 1: l == i* and r == j*: we find the optimal pair. Done.
    
    Case 2: l < i* (l hasn't reached i*):
      At some point, l was at i* and r was >= j*. If height[i*] < height[r],
      we'd move l past i* only if the current pair (i*, r) was already recorded.
      The area(i*, r) >= area(i*, j*) because r >= j* doesn't hurt width AND
      the height is still bounded by height[i*]. So we've already recorded a
      value >= optimal. Similar logic for Case 3 (r > j*).
    
    QED (informal): moving the shorter bar never discards the optimal pair
    without having already recorded its area or a better area.

----------------------------------------------------------------
INTERVIEW Q&A
----------------------------------------------------------------

  Q: Why do we move the shorter bar?
  A: Because the area is controlled by the shorter bar. The wider pair
     we currently have is limited by the shorter side. Moving the taller
     bar can only decrease width while keeping the same limit. Moving
     the shorter bar is the only way to potentially find a greater height.

  Q: Is this greedy or two pointers?
  A: Both. It's a greedy two-pointer solution -- the greedy choice
     (which pointer to move) is what enables the O(n) complexity.

  Q: Can we prove this always finds the maximum?
  A: Yes. A formal proof by contradiction shows that any pair (i, j)
     that could beat the current answer will be visited by the algorithm
     before both pointers have moved past that pair.

  Q: What's the brute force time and why is O(n) achievable?
  A: Brute force is O(n^2) checking all pairs. Two pointers achieves
     O(n) by using the monotone structure -- after fixing one endpoint,
     we can eliminate entire ranges with the greedy rule.

----------------------------------------------------------------
INTERVIEW TIPS
----------------------------------------------------------------

  - Spend time JUSTIFYING the greedy rule -- interviewers WILL ask why.
  - Trace through 3-4 iterations on the whiteboard.
  - Mention the proof: "Moving the taller bar can never improve area
    because width decreases and the minimum height stays the same or
    decreases."
  - If asked follow-ups about circular arrays: "I'd need to think more
    carefully -- the greedy monotone argument may not hold."
