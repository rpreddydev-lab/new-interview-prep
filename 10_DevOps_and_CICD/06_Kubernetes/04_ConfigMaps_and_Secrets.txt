1. CONFIGMAPS — NON-SENSITIVE CONFIGURATION
================================================================================

What is a ConfigMap?
  Stores non-confidential key-value configuration data.
  Decouples configuration from container images.
  Can store: config files, env vars, command-line args.
  Max size: 1MB per ConfigMap.

Creating ConfigMaps:
  
  # Method 1: From literal values
  kubectl create configmap app-config \
    --from-literal=APP_ENV=production \
    --from-literal=APP_PORT=8080 \
    --from-literal=LOG_LEVEL=info
  
  # Method 2: From a file (key=filename, value=file contents)
  kubectl create configmap nginx-config \
    --from-file=nginx.conf
  
  # Method 3: From a file with custom key
  kubectl create configmap nginx-config \
    --from-file=myconfig=nginx.conf
  
  # Method 4: From a directory (each file becomes a key)
  kubectl create configmap app-configs \
    --from-file=./configs/
  
  # Method 5: From an env-file (KEY=value format)
  kubectl create configmap env-config \
    --from-env-file=.env
  
  # Method 6: YAML (declarative — use this for GitOps)
  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: app-config
    namespace: production
  data:
    # Simple key-value pairs (env vars)
    APP_ENV: "production"
    APP_PORT: "8080"
    LOG_LEVEL: "info"
    
    # Multi-line values (config files)
    application.yml: |
      server:
        port: 8080
      spring:
        datasource:
          url: jdbc:postgresql://postgres:5432/mydb
    
    nginx.conf: |
      server {
          listen 80;
          location / {
              proxy_pass http://backend:8080;
          }
      }
  binaryData:
    # base64 encoded binary data (optional)
    image.png: iVBORw0KGgoAAAA...

ConfigMap Commands:
  kubectl get configmap app-config
  kubectl describe configmap app-config
  kubectl get configmap app-config -o yaml
  kubectl edit configmap app-config
  kubectl delete configmap app-config

2. SECRETS — SENSITIVE CONFIGURATION
================================================================================

What is a Secret?
  Stores sensitive data: passwords, tokens, certificates, keys.
  Values are BASE64 ENCODED (NOT encrypted by default).
  
  IMPORTANT: Base64 ≠ encryption. It's encoding.
  echo "mypassword" | base64   →  bXlwYXNzd29yZAo=
  echo "bXlwYXNzd29yZAo=" | base64 -d  →  mypassword
  
  Secrets are "secret" because:
  1. API server requires specific permissions to read them (RBAC)
  2. Not shown in `kubectl describe` (shown as *** or [base64])
  3. Can be encrypted at rest (needs explicit configuration)
  4. Sent to nodes only when pods need them (not broadcast)

Secret Types:
  TYPE                            USE CASE
  ──────────────────────────────────────────────────────────────────
  Opaque (default)                Arbitrary key-value data
  kubernetes.io/service-account-token  ServiceAccount token (auto-created)
  kubernetes.io/dockerconfigjson  Docker registry credentials
  kubernetes.io/dockercfg         Legacy docker registry credentials
  kubernetes.io/basic-auth        Username/password (HTTP basic auth)
  kubernetes.io/ssh-auth          SSH private key
  kubernetes.io/tls               TLS certificate + private key
  bootstrap.kubernetes.io/token   Node bootstrap tokens

Creating Secrets:
  
  # Opaque secret (literal)
  kubectl create secret generic db-credentials \
    --from-literal=username=admin \
    --from-literal=password=SuperSecret123
  
  # Opaque secret (from file)
  kubectl create secret generic ssl-certs \
    --from-file=./tls.crt \
    --from-file=./tls.key
  
  # TLS secret (cert + key)
  kubectl create secret tls my-tls-secret \
    --cert=path/to/cert.crt \
    --key=path/to/cert.key
  
  # Docker registry secret
  kubectl create secret docker-registry regcred \
    --docker-server=myregistry.example.com \
    --docker-username=myuser \
    --docker-password=mypassword \
    --docker-email=myemail@example.com
  
  # YAML (values must be base64 encoded)
  apiVersion: v1
  kind: Secret
  metadata:
    name: db-credentials
    namespace: production
  type: Opaque
  data:
    username: YWRtaW4=          # base64 of "admin"
    password: U3VwZXJTZWNyZXQ=  # base64 of "SuperSecret"
  
  # YAML with stringData (K8s handles base64 encoding for you)
  apiVersion: v1
  kind: Secret
  metadata:
    name: db-credentials
  type: Opaque
  stringData:
    username: admin           # K8s encodes this to base64
    password: SuperSecret123  # K8s encodes this to base64

Viewing Secrets:
  kubectl get secrets
  kubectl describe secret db-credentials    # Shows keys but not values
  kubectl get secret db-credentials -o yaml # Shows base64-encoded values
  
  # Decode a secret value:
  kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d

3. USING CONFIGMAPS AND SECRETS IN PODS
================================================================================

Method 1: Environment Variables (individual keys):
  
  spec:
    containers:
    - name: app
      env:
      # From ConfigMap
      - name: LOG_LEVEL
        valueFrom:
          configMapKeyRef:
            name: app-config
            key: LOG_LEVEL
      # From Secret
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-credentials
            key: password
            optional: false   # Pod fails to start if secret missing

Method 2: envFrom (inject ALL keys at once):
  
  spec:
    containers:
    - name: app
      envFrom:
      # Load all keys from ConfigMap as env vars
      - configMapRef:
          name: app-config
      # Load all keys from Secret as env vars
      - secretRef:
          name: app-secrets
      # Optional prefix to avoid key collisions
      - configMapRef:
          name: feature-flags
          prefix: FEATURE_

Method 3: Volume Mount (files in the container):
  
  spec:
    containers:
    - name: app
      volumeMounts:
      - name: config
        mountPath: /app/config    # ConfigMap keys become files here
        readOnly: true
      - name: secrets
        mountPath: /app/secrets
        readOnly: true
      # Mount specific key to specific path
      - name: tls
        mountPath: /etc/ssl/certs/my-cert.crt
        subPath: tls.crt          # Mount only this key, not whole directory
    volumes:
    - name: config
      configMap:
        name: app-config
        # Optional: set file permissions
        defaultMode: 0644
        # Optional: mount only specific keys
        items:
        - key: nginx.conf
          path: nginx.conf        # Key name → file name in mountPath
    - name: secrets
      secret:
        secretName: db-credentials
        defaultMode: 0600         # Restrict permissions on secret files
    - name: tls
      secret:
        secretName: my-tls-secret

Volume Mount vs Env Vars:
  
  USE VOLUME MOUNT WHEN:
  - Configuration is multi-line (files, certs, configs)
  - Need dynamic updates (configmap changes → file updates without pod restart)
  - Secrets (better security: files more controllable than env vars)
  - Large configuration data
  
  USE ENV VARS WHEN:
  - Simple key-value pairs
  - Application reads from environment variables (12-factor apps)
  - Configuration is consumed at startup
  
  Note: Environment variables DON'T auto-update.
  Volume-mounted ConfigMaps DO auto-update (within ~1 minute).
  Your application must re-read the file to pick up changes.

4. ENCRYPTION AT REST
================================================================================

The Problem:
  By default, Secrets in etcd are base64 encoded — not encrypted.
  Anyone with etcd access can read all secrets.
  
  kubectl get secret db-credentials -o yaml  →  base64 encoded but readable
  etcdctl get /registry/secrets/default/db-credentials  →  plaintext in etcd!

Enabling Encryption at Rest:
  
  # 1. Generate a 32-byte encryption key:
  head -c 32 /dev/urandom | base64
  
  # 2. Create EncryptionConfiguration file:
  apiVersion: apiserver.config.k8s.io/v1
  kind: EncryptionConfiguration
  resources:
  - resources:
    - secrets
    - configmaps  # Optional: also encrypt configmaps
    providers:
    - aescbc:
        keys:
        - name: key1
          secret: <base64-encoded-32-byte-key>
    - identity: {}   # Fallback (unencrypted) for reading old secrets
  
  # 3. Update kube-apiserver to use the config:
  # Add flag: --encryption-provider-config=/etc/kubernetes/encryption.yaml
  
  # 4. Re-encrypt all existing secrets:
  kubectl get secrets --all-namespaces -o json | kubectl replace -f -
  
  Provider options (in order — first provider encrypts, all can decrypt):
  aescbc    AES-CBC with PKCS#7 padding (strong, local key)
  aesgcm    AES-GCM (strong, but keys must be rotated regularly)
  secretbox Faster than AES-CBC, also local key
  kms       Use external KMS provider (AWS KMS, GCP KMS, Azure Key Vault)
  identity  No-op (stored as-is — for reading unencrypted/migration)

KMS Provider (recommended for production):
  
  # AWS KMS example with KMS plugin:
  - kms:
      name: aws-kms-provider
      endpoint: unix:///var/run/kmsplugin/socket.sock
      cachesize: 1000
      timeout: 3s
  
  Benefits:
  - Keys stored outside the cluster (not in cluster state)
  - Key rotation handled by KMS
  - Audit log in KMS (who decrypted what)
  - No key material in etcd

5. SECRET MANAGEMENT BEST PRACTICES
================================================================================

DO:
  ✓ Use RBAC to restrict who can read secrets
  ✓ Enable encryption at rest (minimum AES, ideally KMS)
  ✓ Use short-lived, rotated credentials
  ✓ Mount secrets as files, not env vars (env vars leak in crash dumps/logs)
  ✓ Use external secret managers (Vault, AWS SSM, AWS Secrets Manager)
  ✓ Set defaultMode: 0600 on secret volumes
  ✓ Use separate namespaces to isolate secret access
  ✓ Audit secret access with audit logs

DON'T:
  ✗ Store secret YAML files in Git (they're just base64!)
  ✗ Print secrets in logs or error messages
  ✗ Use overly permissive RBAC (limit secrets get/list/watch)
  ✗ Commit .env files to Git
  ✗ Use env vars for secrets if possible (prefer volume mounts)
  ✗ Give service accounts access to secrets they don't need

The Git Problem with Secrets:
  Kubernetes Secret YAMLs contain base64 values.
  Committing them to Git is a security risk.
  
  Solutions:
  1. Sealed Secrets: Encrypt secrets with a public key before committing
  2. External Secrets Operator: Sync from AWS SSM/Secrets Manager/Vault
  3. SOPS (Mozilla): Encrypt YAML values with GPG/KMS
  4. Vault + vault-agent: Inject secrets at pod start time

RBAC for Secrets:
  
  # Give a role READ access to specific secrets only:
  apiVersion: rbac.authorization.k8s.io/v1
  kind: Role
  metadata:
    name: secret-reader
    namespace: production
  rules:
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["db-credentials", "api-keys"]  # Specific secrets only!
    verbs: ["get"]   # get only, NOT list or watch

6. EXTERNAL SECRETS OPERATOR
================================================================================

What is External Secrets Operator (ESO)?
  Kubernetes operator that syncs secrets from external secret stores into
  Kubernetes Secrets. The actual sensitive values stay in the external store.
  
  External stores supported:
  - AWS Secrets Manager
  - AWS Parameter Store (SSM)
  - HashiCorp Vault
  - Google Secret Manager
  - Azure Key Vault
  - 1Password, Doppler, CyberArk

Installation:
  helm repo add external-secrets https://charts.external-secrets.io
  helm install external-secrets external-secrets/external-secrets -n external-secrets --create-namespace

Configuration (AWS Secrets Manager example):
  
  # Step 1: SecretStore — connection config (per namespace)
  apiVersion: external-secrets.io/v1beta1
  kind: SecretStore
  metadata:
    name: aws-secrets-manager
    namespace: production
  spec:
    provider:
      aws:
        service: SecretsManager
        region: us-east-1
        auth:
          jwt:
            serviceAccountRef:
              name: external-secrets-sa   # ServiceAccount with IRSA/OIDC
  
  # Step 2: ExternalSecret — maps external secret to K8s Secret
  apiVersion: external-secrets.io/v1beta1
  kind: ExternalSecret
  metadata:
    name: db-credentials
    namespace: production
  spec:
    refreshInterval: 1h               # How often to sync
    secretStoreRef:
      name: aws-secrets-manager
      kind: SecretStore
    target:
      name: db-credentials            # Name of K8s Secret to create
      creationPolicy: Owner
    data:
    - secretKey: password             # Key in K8s Secret
      remoteRef:
        key: prod/db/credentials      # Path in AWS Secrets Manager
        property: password            # JSON key in the secret value
    - secretKey: username
      remoteRef:
        key: prod/db/credentials
        property: username
  
  # OR: extract all keys from JSON secret
  dataFrom:
  - extract:
      key: prod/db/credentials        # All keys in this JSON become K8s secret keys

ClusterSecretStore:
  Like SecretStore but cluster-scoped (all namespaces can use it).
  
  apiVersion: external-secrets.io/v1beta1
  kind: ClusterSecretStore
  metadata:
    name: global-aws-secrets
  spec:
    provider:
      aws:
        service: SecretsManager
        region: us-east-1

7. HASHICORP VAULT INTEGRATION
================================================================================

Vault Kubernetes Auth Method:
  Vault can authenticate pods using their ServiceAccount token.
  Pod presents its SA token → Vault verifies with K8s API → issues Vault token
  
  # Configure Vault Kubernetes auth:
  vault auth enable kubernetes
  vault write auth/kubernetes/config \
    kubernetes_host="https://kubernetes.default.svc" \
    kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
  
  # Create Vault policy:
  vault policy write my-app-policy - <<EOF
  path "secret/data/my-app/*" {
    capabilities = ["read"]
  }
  EOF
  
  # Create Vault role linking K8s SA to Vault policy:
  vault write auth/kubernetes/role/my-app \
    bound_service_account_names=my-app-sa \
    bound_service_account_namespaces=production \
    policies=my-app-policy \
    ttl=1h

Vault Agent Sidecar Injector:
  Annotation-based secret injection. Vault agent sidecar writes secrets
  to shared volume. No code changes needed in application.
  
  # Pod annotations:
  metadata:
    annotations:
      vault.hashicorp.com/agent-inject: "true"
      vault.hashicorp.com/role: "my-app"
      vault.hashicorp.com/agent-inject-secret-db.txt: "secret/data/my-app/db"
      vault.hashicorp.com/agent-inject-template-db.txt: |
        {{- with secret "secret/data/my-app/db" -}}
        DB_PASSWORD={{ .Data.data.password }}
        {{- end }}
  
  # Secret is written to: /vault/secrets/db.txt
  # Application reads from that file

8. SEALED SECRETS
================================================================================

What is Sealed Secrets?
  Kubernetes controller + CLI tool by Bitnami.
  Encrypts secrets with the controller's public key.
  Only the Sealed Secrets controller can decrypt.
  Safe to commit encrypted SealedSecret YAML to Git.

How It Works:
  1. Sealed Secrets controller generates RSA key pair on install
  2. kubeseal CLI encrypts Secret YAML using controller's public key
  3. Encrypted SealedSecret is safe to store in Git
  4. When applied to cluster, controller decrypts → creates regular Secret

Installation:
  helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
  helm install sealed-secrets sealed-secrets/sealed-secrets -n kube-system
  
  # Install kubeseal CLI:
  brew install kubeseal

Usage:
  # Create a regular Secret YAML (don't apply to cluster):
  kubectl create secret generic db-creds \
    --from-literal=password=SuperSecret \
    --dry-run=client -o yaml > secret.yaml
  
  # Seal it (fetch public cert from controller):
  kubeseal --format=yaml < secret.yaml > sealed-secret.yaml
  
  # sealed-secret.yaml is safe to commit to Git!
  cat sealed-secret.yaml:
  apiVersion: bitnami.com/v1alpha1
  kind: SealedSecret
  metadata:
    name: db-creds
    namespace: production
  spec:
    encryptedData:
      password: AgBy3i4OJSWK+PiTySYZZA9rO43cGDEq...  # RSA encrypted
  
  # Apply to cluster:
  kubectl apply -f sealed-secret.yaml
  # Controller creates regular Secret "db-creds" with decrypted values

Scope (important):
  namespace-wide (default): Sealed secret bound to specific namespace + name
  cluster-wide: Can be used in any namespace
  strict (most secure): Bound to specific namespace + name (can't rename/move)

9. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between ConfigMap and Secret?
A: Both store configuration data as key-value pairs, but:
   
   ConfigMap:
   - For non-sensitive data: URLs, ports, feature flags, config files
   - Stored in etcd in plaintext
   - Values are plain strings (no encoding)
   - Visible in kubectl describe configmap
   
   Secret:
   - For sensitive data: passwords, API keys, certificates, tokens
   - Stored in etcd as base64 (encoding, NOT encryption)
   - Requires explicit RBAC permissions to read
   - Values hidden in kubectl describe secret
   - Can be encrypted at rest with EncryptionConfiguration
   - Sent to nodes only when needed (not broadcast)
   
   Important: Base64 is NOT security. Anyone with kubectl access and get/list
   rights on secrets can decode them instantly. Real security comes from:
   1. RBAC (restrict who can access secrets)
   2. Encryption at rest (encrypt in etcd)
   3. External secret stores (Vault, AWS SSM)

Q2: How do you prevent secrets from being committed to Git?
A: Multiple approaches, defense in depth:
   
   1. .gitignore: Add secret files, .env files to .gitignore
      Pro: Simple. Con: Accidental commits still possible.
   
   2. Sealed Secrets: Encrypt with controller's public key using kubeseal.
      Encrypted YAML is safe in Git. Controller decrypts on apply.
      Pro: GitOps-friendly. Con: Key rotation complexity.
   
   3. External Secrets Operator: Secrets live in AWS Secrets Manager/Vault.
      ExternalSecret CRD in Git references (not contains) the secret.
      Pro: Centralized, rotation, audit logs. Con: External dependency.
   
   4. SOPS + GPG/KMS: Encrypt specific YAML values inline.
      Pro: Works with any YAML, existing workflows.
      Con: Key management overhead.
   
   5. git-secrets / pre-commit hooks: Scan commits for credentials.
      Pro: Catches accidents. Con: Not a substitute for proper practices.
   
   Recommendation: External Secrets Operator + strict RBAC + encrypted etcd.
   This provides defense in depth: secrets never leave the secret manager,
   encryption at rest in K8s, and access control via RBAC.

Q3: Explain how volume-mounted ConfigMaps are automatically updated.
A: When you mount a ConfigMap as a volume (not env vars), Kubernetes
   automatically updates the files when the ConfigMap changes:
   
   1. You update the ConfigMap: kubectl edit configmap app-config
   2. API server persists the change to etcd
   3. kubelet on the node is watching ConfigMaps referenced by its pods
   4. kubelet detects the change and updates the volume mount
      (uses atomic rename — replaces symlinks, not in-place edit)
   5. Within ~1 minute, new file content is available in the container
   6. Application needs to detect file changes and reload config
   
   Important caveats:
   - env vars DO NOT update automatically (pod must be restarted)
   - subPath mounts DO NOT update automatically
   - The update is eventually consistent (~1 minute delay default)
   
   Application patterns for hot reload:
   - Watch file for changes (inotify): signal.Notify, watchman, fsnotify
   - Periodic file re-read: check file mtime on a schedule
   - SIGHUP handler: send signal to reload config
   
   This feature is commonly used for:
   - Nginx config: nginx -s reload when config changes
   - Prometheus: YAML rules files auto-reload
   - Application feature flags: config file checked periodically

Q4: What are the risks of using Kubernetes Secrets in base64?
A: Base64 encoding provides ZERO security — it's trivially reversible.
   The risks:
   
   1. etcd access: Anyone who can read etcd directly (physical access,
      backup files, monitoring tools) gets all secrets in plaintext.
   
   2. Kubernetes API access: Any principal with secrets/get permission
      can read secrets: kubectl get secret -o yaml | base64 -d
   
   3. Backup files: etcd backups contain unencrypted secrets.
      A stolen backup file = all secrets compromised.
   
   4. Logging: If you accidentally log a secret value, it's plaintext.
   
   Mitigations:
   a) Encryption at rest: EncryptionConfiguration with aescbc or KMS
      → etcd content encrypted even if raw access obtained
   b) Strict RBAC: Service accounts only get secrets they need
      → limits blast radius if one SA is compromised
   c) External secret stores: Vault, AWS Secrets Manager
      → secrets never stored in etcd at all
   d) Audit logging: Log all secret access → detect unauthorized reads
   e) Short-lived, rotated credentials: Limit impact of a stolen secret

Q5: How does the External Secrets Operator work?
A: ESO bridges external secret management systems with Kubernetes:
   
   Architecture:
   1. ESO controller runs in cluster (installed via Helm)
   2. SecretStore: Configures connection to external store (AWS SM, Vault...)
   3. ExternalSecret: Declares which external secret to sync + target K8s Secret
   
   Sync flow:
   a) ESO controller watches ExternalSecret resources
   b) At the configured interval (e.g., 1h), ESO fetches the secret from
      the external store using the SecretStore credentials
   c) ESO creates/updates a regular Kubernetes Secret with the fetched values
   d) The Secret is tagged as owned by the ExternalSecret
   e) Pods can then mount the Secret normally
   
   Authentication to AWS (best practice):
   - Use IRSA (IAM Roles for Service Accounts) in EKS
   - ESO's ServiceAccount gets an IAM role via OIDC annotation
   - No AWS credentials stored in the cluster
   
   Benefits:
   - Source of truth stays in AWS Secrets Manager (centralized, audited)
   - Automatic rotation: ESO re-syncs on schedule → picks up rotated secrets
   - No secrets in Git (ExternalSecret YAML has no values, just references)
   - Works with existing secret management workflows

10. QUICK REFERENCE CHEAT SHEET
================================================================================

CONFIGMAP CREATION:
  kubectl create configmap <name> --from-literal=KEY=val
  kubectl create configmap <name> --from-file=config.yaml
  kubectl create configmap <name> --from-env-file=.env

SECRET CREATION:
  kubectl create secret generic <name> --from-literal=KEY=val
  kubectl create secret tls <name> --cert=cert.crt --key=cert.key
  kubectl create secret docker-registry <name> --docker-server=... ...
  # Encode manually: echo -n "value" | base64

CONSUME IN POD:
  env.valueFrom.configMapKeyRef     Single ConfigMap key → env var
  env.valueFrom.secretKeyRef        Single Secret key → env var
  envFrom.configMapRef              All ConfigMap keys → env vars
  envFrom.secretRef                 All Secret keys → env vars
  volumes + volumeMounts            Mount as files (supports hot reload)

SECRET SECURITY LAYERS:
  1. RBAC           Restrict who can read secrets
  2. Encryption     EncryptionConfiguration (aescbc/KMS) → encrypts in etcd
  3. External Store Vault/AWS SM (secrets never in etcd)
  4. Audit Logs     Track who accessed what

TOOLS FOR GITOPS-SAFE SECRETS:
  Sealed Secrets           kubeseal + controller, RSA encrypted in Git
  External Secrets Operator  Sync from AWS SM, Vault, GCP SM, etc.
  SOPS                     Encrypt YAML values with GPG/KMS
  Vault Agent Injector     Sidecar writes secrets to shared volume

EXTERNAL SECRETS OPERATOR:
  SecretStore         → Connection config to external secret store
  ClusterSecretStore  → Cluster-wide connection config
  ExternalSecret      → What to sync (external path → K8s secret key)

BASE64 HELPERS:
  echo -n "value" | base64          # Encode
  echo "dGVzdA==" | base64 -d      # Decode
  kubectl get secret x -o jsonpath='{.data.key}' | base64 -d
