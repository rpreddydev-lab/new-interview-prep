SECTION A: CI/CD CONCEPTS & PIPELINES
================================================================================

Q1: What is the difference between Continuous Integration, Continuous Delivery,
    and Continuous Deployment?

A: Three progressive stages of automation:
   
   Continuous Integration (CI):
   - Developers push code frequently (multiple times/day)
   - Every push triggers automated build + test
   - Goal: catch integration bugs early
   - Definition of done: code compiles, all tests pass
   
   Continuous Delivery (CD — Delivery):
   - Extends CI: after tests pass, artifact is deployable at any time
   - Deployment to production requires a HUMAN decision/approval
   - Goal: always be in a releasable state
   - Typical: automatic deploy to staging, manual approval for production
   
   Continuous Deployment (CD — Deployment):
   - Fully automated: every green main branch build deploys to production
   - No human approval in the pipeline
   - Requires: excellent test coverage, strong monitoring, fast rollback
   - Enables: multiple production deploys per day (Netflix, Google model)
   
   Most enterprise companies practice Continuous Delivery (not full Deployment)
   due to regulatory requirements, change management, or risk tolerance.

Q2: What should a CI pipeline contain, in what order?

A: A well-structured CI pipeline:
   
   Stage 1 — Code Quality (Fast, ~1 min):
   - Linting (ESLint, pylint, golangci-lint)
   - Code formatting check (prettier, black, gofmt)
   - Static type checking (mypy, tsc)
   
   Stage 2 — Security (Fast, ~2 min):
   - Secret scanning (TruffleHog, gitleaks)
   - SAST (Semgrep, CodeQL) — lightweight rules on PR
   - Dependency vulnerability scan (Snyk, safety, npm audit)
   
   Stage 3 — Build (~3 min):
   - Compile / build artifact
   - Docker image build (but don't push yet)
   
   Stage 4 — Test (~5-15 min):
   - Unit tests (all)
   - Integration tests
   - Code coverage check (fail if below threshold)
   
   Stage 5 — Publish (on main branch only):
   - Push Docker image to registry
   - Upload artifacts to S3/Nexus
   - Tag release
   
   Parallelization: Run stages 1+2 in parallel. Run unit/integration tests in parallel.
   
   Fail fast: Put cheapest/fastest checks first to minimize feedback time.

Q3: How do you handle database migrations in a CI/CD pipeline?

A: Database migrations are the hardest part of continuous deployment because
   they must be backward compatible.
   
   Key principles:
   1. Never break backward compatibility — old app code must work with new schema
   2. Separate deploys: migrate first, then deploy code
   3. Additive changes only in a single deploy:
      - Add new columns with defaults (don't require data immediately)
      - Never rename/drop columns in the same deploy as code that uses them
   
   Workflow (Expand-Contract / Blue-Green Migration):
   
   Step 1 - Expand:
   - Deploy migration: ADD new_column (nullable, with default)
   - Old code still runs (ignores new column)
   
   Step 2 - Deploy new code:
   - New code uses new_column, falls back to old_column
   - Both versions of code work
   
   Step 3 - Contract:
   - After all instances run new code
   - Deploy migration: DROP old_column
   
   Tools:
   - Liquibase, Flyway (migration versioning and rollback)
   - Run migration as K8s Job or Helm hook pre-upgrade
   
   # Flyway in pipeline:
   flyway -url=jdbc:postgresql://prod-db/myapp migrate
   
   # Kubernetes init container for migration:
   initContainers:
   - name: migrate
     image: myapp:$VERSION
     command: ["python", "manage.py", "migrate"]
     env:
     - name: DATABASE_URL
       valueFrom: { secretKeyRef: { name: db-creds, key: url } }

Q4: What is a monorepo CI/CD challenge and how do you solve it?

A: In a monorepo (multiple services in one repo), naive CI runs the ENTIRE
   pipeline for ALL services on every push — extremely slow.
   
   Problem: 200ms frontend change triggers 45-minute build+test for all 20 services.
   
   Solutions:
   
   1. Path-based filtering (GitHub Actions):
      on:
        push:
          paths:
            - 'services/user-service/**'
      jobs:
        build-user-service:
          if: contains(github.event.commits[*].modified[*], 'services/user-service/')
   
   2. Affected analysis (Nx, Turborepo, Bazel):
      - Track dependency graph between packages
      - Only build/test packages affected by changed files
      - Nx: nx affected --target=build
      - Turborepo: turbo run build --filter=...[origin/main]
   
   3. Separate pipelines per service directory:
      Use .gitlab-ci.yml changes: keyword or GitHub Actions paths filter
   
   4. Caching aggressive:
      - Cache node_modules, pip, Maven per service
      - Docker layer cache
      - Artifact cache for unchanged services

Q5: How do you prevent a bad deployment from impacting all users?

A: Use progressive delivery (serve new version to a subset of traffic):
   
   Canary deployment:
   - Deploy new version alongside old version
   - Route 5% of traffic to new version
   - Monitor error rates, latency, custom business metrics
   - If healthy: gradually increase to 25% → 50% → 100%
   - If degraded: route 100% back to old version (instant rollback)
   
   Feature flags:
   - Deploy code to 100% of servers, but enable feature for 5% of users
   - Can target: beta users, specific user IDs, specific regions
   - Tools: LaunchDarkly, Flagsmith, AWS AppConfig
   
   Blue/Green:
   - Two identical environments (blue = current, green = new)
   - Switch all traffic at once via load balancer
   - Instant rollback: switch back to blue
   - Downside: double infrastructure cost
   
   Automated analysis (Argo Rollouts, Spinnaker):
   - Define success metrics (error rate < 0.1%, p99 latency < 500ms)
   - Automated comparison between canary and baseline
   - Auto-promote if metrics pass, auto-rollback if they fail

SECTION B: DEPLOYMENT STRATEGIES
================================================================================

Q6: Compare rolling, blue/green, and canary deployments.

A: Quick comparison:
   
   Strategy     Downtime  Risk      Rollback    Cost     Use Case
   ─────────────────────────────────────────────────────────────────────
   Rolling      None      Medium    Slow         Normal   Standard deploys
   Blue/Green   None      Low       Instant      2x       Critical services
   Canary       None      Low       Instant      ~1.1x    High-traffic, new features
   Recreate     Yes       High      Slow         Normal   Non-critical, dev envs
   
   Rolling:
   - Gradually replace old pods with new pods
   - Always some old + some new running simultaneously
   - Rollback = rolling update in reverse (slow)
   - Kubernetes default strategy
   
   Blue/Green:
   - Two complete environments, switch load balancer
   - Zero-downtime instant cutover
   - Full environment cost (but can reuse blue after cutover)
   - Rollback: switch LB back to blue (< 1 minute)
   
   Canary:
   - Gradually shift traffic percentage
   - Real user traffic tests new version
   - Fine-grained control (5% → 10% → 25% → 100%)
   - Most sophisticated, requires traffic routing capability
   
   Kubernetes Canary with Argo Rollouts:
   apiVersion: argoproj.io/v1alpha1
   kind: Rollout
   spec:
     strategy:
       canary:
         steps:
         - setWeight: 5
         - pause: {duration: 10m}
         - setWeight: 25
         - pause: {duration: 10m}
         - setWeight: 100
         analysis:
           templates:
           - templateName: success-rate
           startingStep: 2

Q7: What is a rollback strategy and when do you use each type?

A: Rollback strategies (fastest to slowest):
   
   1. Traffic routing rollback (< 1 min):
      - Blue/Green: flip load balancer back to blue
      - Canary: route 100% back to stable
      - Feature flag: turn off flag (no redeploy needed)
      Best for: front-end issues, performance degradation
   
   2. Kubernetes rollout undo (2-5 min):
      kubectl rollout undo deployment/myapp
      Kubernetes re-applies previous ReplicaSet spec.
      Best for: app bugs caught quickly after deploy
   
   3. Helm rollback (2-5 min):
      helm rollback myapp 3
      Rolls back to release revision 3.
      Includes any Helm-managed ConfigMaps/Secrets.
   
   4. GitOps revert (5-15 min):
      git revert + PR + merge = triggers new pipeline deploy
      Best for: teams with strict audit requirements
   
   5. Database rollback (hard, avoid):
      Most dangerous — requires backward migration (undo)
      Prevention: use expand/contract pattern (no rollback needed)
   
   Automated rollback:
   - Argo Rollouts / Spinnaker: auto-rollback on metrics failure
   - Define: if HTTP 5xx rate > 1% in first 10 min → auto rollback
   
   Decision: Rollback vs Fix-Forward?
   - Rollback: data not corrupted, < 5 min to rollback, users affected now
   - Fix-forward: database migration already ran, rollback would corrupt data

SECTION C: GIT WORKFLOWS & BRANCHING
================================================================================

Q8: Compare GitFlow vs trunk-based development. When would you use each?

A: GitFlow:
   Branches: main, develop, feature/*, release/*, hotfix/*
   Process: Features merged to develop → release branch cut → tested → merged to main
   
   Pros:
   - Clear separation of release lifecycle
   - Easy to maintain multiple release versions in parallel
   - Good for: mobile apps (binary releases), libraries with semver, infrequent releases
   
   Cons:
   - Long-lived branches → merge conflicts
   - Slow feedback: features wait in develop branch
   - Not suitable for continuous deployment
   
   Trunk-Based Development:
   Branches: main only (+ short-lived feature branches < 2 days)
   Process: Direct commits to main (or PRs that are merged same day)
   
   Pros:
   - No long-lived branches → no merge conflict accumulation
   - Continuous integration is real (merges happen daily)
   - Enables continuous deployment
   - What Google, Meta, and Netflix use
   
   Cons:
   - Requires excellent test coverage
   - Requires feature flags (to hide incomplete features in production)
   - Team discipline needed (no "I'll finish this branch next week")
   
   When to use GitFlow:
   - Regulated industries with scheduled releases
   - Libraries maintaining multiple version branches (v1.x, v2.x)
   - Teams not ready for continuous deployment
   
   When to use Trunk-Based:
   - Web services deploying multiple times per day
   - Teams practicing true CI/CD
   - Microservices with independent deployments

Q9: What makes a good Pull Request review process from a CI/CD perspective?

A: Automated checks that must pass before human review:
   - Linting + formatting (no style debates in review)
   - All tests pass
   - Code coverage doesn't decrease
   - Secret scanning clean
   - Dependency vulnerability scan clean
   - SAST scan clean (or findings acknowledged)
   - Build succeeds
   
   Required human review policies:
   - At least 1 (or 2 for critical services) reviewer approval
   - Code owner review for specific directories
   - Dismiss stale approvals on new commits
   
   PR size best practices:
   - Small PRs (< 400 lines) — faster to review, easier to reason about
   - One concern per PR (not "refactor + add feature + fix bug")
   - Link to issue/ticket for context
   
   Branch protection rules (GitHub):
   - Require status checks to pass
   - Require approvals
   - Restrict who can push directly to main
   - Require signed commits (for compliance)

Q10: Compare Jenkins vs GitHub Actions vs GitLab CI. When would you choose each?

A: 
   Feature            Jenkins              GitHub Actions        GitLab CI
   ────────────────────────────────────────────────────────────────────────
   Hosting            Self-hosted          Cloud (GitHub)        Cloud or self-hosted
   Configuration      Jenkinsfile (Groovy) YAML                  YAML
   Plugin ecosystem   Huge (2000+)         Growing               Good
   Cost               Infrastructure only  Free minutes + paid   Included in GitLab
   K8s integration    Good                 Good                  Good
   Secrets management Jenkins creds plugin GitHub Secrets        GitLab Variables
   Self-hosted runner Jenkins agents       GitHub self-hosted    GitLab runner
   Learning curve     High                 Low-Medium            Low-Medium
   
   Choose Jenkins:
   - Legacy enterprise environments (already have Jenkins)
   - Need complex orchestration (parallel pipelines across many agents)
   - Compliance requires on-premises CI
   - Heavy customization via plugins
   
   Choose GitHub Actions:
   - Code is already on GitHub
   - Simple to start (marketplace actions for everything)
   - Open source projects (free for public repos)
   - Need OIDC to AWS/GCP/Azure (best native support)
   
   Choose GitLab CI:
   - Using GitLab for source control (integrated DevSecOps platform)
   - Need built-in container registry, security scanning, environments in one tool
   - Air-gapped/on-prem requirement (GitLab Self-Managed)

Q11: How does artifact management fit into a CI/CD pipeline?

A: Build artifacts need to be:
   1. Built ONCE — same binary deployed to staging AND production
   2. Versioned — traceable to exact commit
   3. Stored with retention policies
   4. Scanned before promotion
   
   Artifact types and storage:
   
   Docker images:     ECR (AWS), GCR (GCP), ACR (Azure), Harbor (self-hosted)
   Maven JARs:        Nexus Repository, Artifactory, GitHub Packages
   npm packages:      Artifactory, GitHub Packages, private npm registry
   Python wheels:     Artifactory, AWS CodeArtifact
   Terraform modules: Terraform Cloud, Git tags + module registry
   Helm charts:       ECR, OCI registry, ChartMuseum
   
   Promotion workflow:
   Build → Push to dev registry → Test → Promote digest to staging registry →
   Test → Promote same digest to prod registry
   
   Immutable tags:
   Never use :latest in production. Use:
   - Git SHA: myapp:a3f8bc2
   - Semantic version: myapp:1.4.2
   - Build ID: myapp:build-1234

Q12: Your CI pipeline takes 45 minutes to run. How do you optimize it?

A: Systematic approach:
   
   1. Measure first:
      - Which stages take the most time? (build, test, scan?)
      - Are there sequential steps that could be parallel?
   
   2. Parallelization:
      - Run lint/security/test in parallel, not sequentially
      - Split test suite into shards (matrix strategy)
      - GitHub Actions matrix: run tests on 4 workers, 25% each
   
   3. Caching:
      - Cache dependencies (npm, pip, Maven) between runs
      - Docker layer cache (only rebuild changed layers)
      - Build tool cache (Gradle build cache, Maven local repo)
   
   4. Test optimization:
      - Only run tests for affected modules (monorepo tools: Nx, Turborepo)
      - Run fast unit tests first, slow integration tests conditionally
      - Use test containers (Testcontainers) for faster DB setup
   
   5. Faster infrastructure:
      - Use larger runners for expensive steps
      - Use self-hosted runners on fast hardware (vs GitHub-hosted shared)
      - Dedicated build cache (faster than re-downloading)
   
   6. Remove unnecessary steps:
      - Skip SAST on tiny docs-only changes
      - Skip Docker build if only test files changed
   
   Target: < 10 minutes for a PR check, < 20 minutes for main branch deploy.

Q13: A production deployment failed halfway through. What do you do?

A: Incident response for a failed deployment:
   
   Immediate (first 5 minutes):
   1. Assess impact: Are users affected? How many? What functionality?
   2. Check pipeline status: did ALL pods fail or only some?
   3. Check logs: kubectl logs -l app=myapp --tail=100
   
   Decision: Rollback or Fix-Forward?
   
   Rollback (preferred if fast):
   - kubectl rollout undo deployment/myapp
   - Helm: helm rollback myapp
   - Monitor: kubectl rollout status deployment/myapp
   - Verify: check error rate in monitoring returns to baseline
   
   Fix-forward (if rollback is risky):
   - Database migration already applied → can't safely rollback
   - Fix the code → push to main → expedited pipeline → deploy
   
   Post-incident:
   - What monitoring alert caught this? Did it fire fast enough?
   - Was there a canary phase that could have caught this earlier?
   - How can the pipeline be improved to prevent this class of failure?
   
   Prevention:
   - Automated smoke tests after deploy (verify /health returns 200)
   - Automated rollback on error rate spike (Argo Rollouts analysis)
   - Staged rollout with auto-promotion criteria

Q14: How do you implement CI/CD for a service that requires environment-specific secrets?

A: Multiple environments (dev, staging, production) each need their own secrets.
   
   CI/CD platform approach (GitHub Actions Environments):
   - dev secrets: available to all branches
   - staging secrets: available after tests pass
   - production secrets: require manual approval + reviewer
   
   OIDC (no stored secrets):
   - Each environment has its own IAM role with limited permissions
   - production role: more restrictive, required manual approval to assume
   - GitHub Actions environment protection rules: require approval before deploying
   
   Vault approach (dynamic secrets per environment):
   - Vault namespaces: vault/dev, vault/staging, vault/prod
   - Pipeline assumes different Vault AppRole per environment
   - Prod AppRole is strictly controlled (audit logged, paged to security team)
   
   Key principle: Production secrets should be harder to access than staging.
   Not just different values — different access controls, different approval requirements.

QUICK REFERENCE CHEAT SHEET
================================================================================

CI/CD DEFINITIONS:
  CI:   Build + test on every commit
  CD:   Auto-deploy to staging, manual gate to prod (Continuous Delivery)
  CD:   Auto-deploy all the way to prod (Continuous Deployment)

DEPLOYMENT STRATEGIES:
  Rolling    Default K8s, gradual pod replacement
  Blue/Green  Two envs, LB switch, instant rollback
  Canary      Gradual traffic %, auto-rollback on metrics
  Recreate    Downtime, dev-only

ROLLBACK COMMANDS:
  kubectl rollout undo deployment/myapp
  helm rollback myapp [revision]
  ArgoCD: argo rollouts undo myapp

PIPELINE OPTIMIZATION:
  Parallelize: lint + security + build in parallel
  Cache:        deps, Docker layers, build artifacts
  Shard tests:  matrix strategy
  Path filter:  only run pipeline for changed services

KEY CI/CD TOOLS:
  Source Control:   GitHub, GitLab, Bitbucket
  CI/CD:            GitHub Actions, GitLab CI, Jenkins, CircleCI
  GitOps:           ArgoCD, FluxCD
  Deployment:       Argo Rollouts, Spinnaker
  Artifact Store:   ECR, Nexus, Artifactory, GitHub Packages
