1. WHY TEST INFRASTRUCTURE CODE
================================================================================

Infrastructure code is production code. Untested IaC causes:
  - Security misconfigurations (public S3 buckets, open security groups)
  - Compliance violations (unencrypted databases, missing audit logs)
  - Outages (bad config deployed to prod with no check)
  - Data loss (accidental resource deletion)
  - Secret leakage (credentials committed to Git)

Testing Pyramid for IaC:
  
  ┌──────────────────────────────────────────────────────────────┐
  │           Level 4: Compliance / Runtime                       │
  │           (AWS Config rules, Security Hub, CSPM tools)        │
  │           Slowest, most expensive but catches production drift │
  ├──────────────────────────────────────────────────────────────┤
  │           Level 3: Integration Tests                          │
  │           (Terratest — deploys REAL resources)                │
  │           Minutes to hours, cloud costs, very comprehensive   │
  ├──────────────────────────────────────────────────────────────┤
  │           Level 2: Plan-based / Unit Tests                    │
  │           (checkov vs plan JSON, OPA conftest)                │
  │           Seconds to minutes, free, high coverage             │
  ├──────────────────────────────────────────────────────────────┤
  │           Level 1: Static Analysis                            │
  │           (tflint, tfsec, terraform fmt, validate)            │
  │           Seconds, free, catches syntax + known bad patterns  │
  └──────────────────────────────────────────────────────────────┘

2. STATIC ANALYSIS
================================================================================

terraform fmt:
  Formats Terraform code to canonical style (2-space indent, aligned = signs).
  
  terraform fmt                   # Format current directory
  terraform fmt -recursive        # All subdirectories
  terraform fmt -check            # Exit non-zero if unformatted (CI use)
  terraform fmt -diff             # Show what would change

terraform validate:
  Validates syntax and configuration (does NOT contact cloud APIs).
  
  terraform init -backend=false   # Init without real backend
  terraform validate              # Check for errors
  
  Catches: undefined variables, invalid attribute names, wrong types.

tflint:
  A Terraform linter that catches:
  - Invalid instance types (typos like "t3.smal")
  - Deprecated resources
  - Missing required variables
  - Naming convention violations (via rules/plugins)
  
  # Install:
  curl -s https://raw.githubusercontent.com/terraform-linters/tflint/master/install_linux.sh | bash
  
  # Configure:
  # .tflint.hcl:
  config {
    call_module_type = "local"
  }
  
  plugin "aws" {
    enabled = true
    version = "0.27.0"
    source  = "github.com/terraform-linters/tflint-ruleset-aws"
  }
  
  rule "terraform_required_version" {
    enabled = true
  }
  
  rule "terraform_required_providers" {
    enabled = true
  }
  
  # Run:
  tflint --init
  tflint
  tflint --recursive   # All subdirectories

hadolint (Dockerfile linting):
  Lints Dockerfiles for best practices.
  
  hadolint Dockerfile
  hadolint --error DL3009 Dockerfile    # Error on specific rule
  hadolint --ignore DL3008 Dockerfile   # Ignore specific rule
  
  # Docker:
  docker run --rm -i hadolint/hadolint < Dockerfile

3. SECURITY SCANNING WITH TFSEC AND CHECKOV
================================================================================

tfsec:
  Security scanner specifically for Terraform.
  Catches: unencrypted storage, open security groups, public buckets, no logs, etc.
  
  # Install:
  brew install tfsec        # macOS
  
  # Run:
  tfsec .                              # Scan current directory
  tfsec environments/prod              # Scan specific path
  tfsec --minimum-severity HIGH        # Only HIGH and CRITICAL
  tfsec --exclude aws-s3-enable-bucket-logging  # Skip rule
  tfsec --out junit --format junit     # JUnit XML output (CI)
  tfsec --format sarif .               # SARIF (GitHub Security tab)
  
  # GitHub Actions:
  - name: Run tfsec
    uses: aquasecurity/tfsec-action@v1.0.0
    with:
      minimum_severity: HIGH
      soft_fail: false       # Fail pipeline on findings

checkov:
  Multi-framework security scanner: Terraform, CloudFormation, K8s, Dockerfile,
  Helm charts, GitHub Actions, ARM templates, Bicep.
  
  # Install:
  pip install checkov
  
  # Scan Terraform:
  checkov -d .                         # Scan directory
  checkov -f main.tf                   # Single file
  checkov -d . --check CKV_AWS_18      # Run specific check only
  checkov -d . --skip-check CKV_AWS_18,CKV_AWS_57  # Skip checks
  checkov -d . --compact               # Compact output
  checkov -d . --output json           # JSON output
  checkov -d . --output sarif          # SARIF
  
  # Scan Kubernetes:
  checkov -d k8s/ --framework kubernetes
  
  # Scan Dockerfile:
  checkov -f Dockerfile
  
  # Scan Terraform plan JSON:
  terraform plan -out=plan.tfplan
  terraform show -json plan.tfplan > plan.json
  checkov -f plan.json --file-type terraform_plan
  
  # GitHub Actions:
  - name: Checkov
    uses: bridgecrewio/checkov-action@v12
    with:
      directory: .
      framework: terraform
      output_format: sarif
      output_file_path: results.sarif
      skip_check: CKV_AWS_18    # Skip specific check

Common Checks:
  CKV_AWS_18    S3 bucket access logging
  CKV_AWS_19    S3 bucket encryption
  CKV_AWS_20    S3 bucket not public
  CKV_AWS_21    S3 versioning enabled
  CKV_AWS_25    Security group no unrestricted SSH (0.0.0.0/0:22)
  CKV_AWS_57    S3 bucket no public ACL
  CKV_AWS_86    RDS deletion protection
  CKV_AWS_157   RDS multi-AZ
  CKV_K8S_8     Liveness probe defined
  CKV_K8S_9     Readiness probe defined
  CKV_K8S_14    Image tag not "latest"
  CKV_K8S_30    readOnlyRootFilesystem

Custom checkov Checks:
  from checkov.common.models.enums import CheckResult
  from checkov.terraform.checks.resource.base_resource_check import BaseResourceCheck
  
  class S3BucketNoPublicACL(BaseResourceCheck):
      def __init__(self):
          super().__init__(
              name="S3 bucket should not have public ACL",
              id="CKV_CUSTOM_1",
              categories=[CheckCategories.GENERAL_SECURITY],
              supported_resources=["aws_s3_bucket"]
          )
      
      def scan_resource_conf(self, conf):
          acl = conf.get("acl", ["private"])[0]
          if acl in ["public-read", "public-read-write"]:
              return CheckResult.FAILED
          return CheckResult.PASSED

4. POLICY AS CODE — OPA/CONFTEST AND SENTINEL
================================================================================

Open Policy Agent (OPA) + Conftest:
  OPA evaluates JSON/YAML against Rego policies.
  Conftest is a test framework that uses OPA to test configuration files.
  
  # Install conftest:
  brew install conftest
  
  # Write a Rego policy:
  # policy/terraform.rego:
  package main
  
  # Deny public S3 buckets:
  deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_s3_bucket_acl"
    resource.change.after.acl == "public-read"
    msg := sprintf(
      "S3 bucket '%v' must not have public-read ACL",
      [resource.address]
    )
  }
  
  # Deny unrestricted SSH:
  deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_security_group_rule"
    resource.change.after.type == "ingress"
    resource.change.after.from_port <= 22
    resource.change.after.to_port >= 22
    cidr := resource.change.after.cidr_blocks[_]
    cidr == "0.0.0.0/0"
    msg := sprintf(
      "Security group rule '%v' allows unrestricted SSH",
      [resource.address]
    )
  }
  
  # Warn (not deny) — missing tags:
  warn[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_instance"
    not resource.change.after.tags.Owner
    msg := sprintf(
      "EC2 instance '%v' is missing Owner tag",
      [resource.address]
    )
  }
  
  # Run:
  terraform plan -out=tfplan
  terraform show -json tfplan > plan.json
  conftest test plan.json --policy policy/
  
  # In CI:
  - name: Conftest OPA policy check
    run: |
      terraform show -json plan.tfplan > plan.json
      conftest test plan.json --policy policy/ --no-color

Sentinel (HCP Terraform Enterprise):
  Policy as code integrated with HCP Terraform.
  Evaluated between plan and apply.
  
  Policy enforcement levels:
  - advisory:       Warn but allow apply to proceed
  - soft-mandatory: Can be overridden by admin
  - hard-mandatory: Cannot be overridden (blocks apply)
  
  # Example Sentinel policy:
  import "tfplan/v2" as tfplan
  import "strings"
  
  # All S3 buckets must have Owner tag:
  require_owner_tag = rule {
    all tfplan.resource_changes as _, change {
      change.type is "aws_s3_bucket" and change.mode is "managed" implies
        change.change.after.tags["Owner"] is not null
    }
  }
  
  # All instances must use approved AMIs:
  approved_amis = ["ami-0abcd1234", "ami-0efgh5678"]
  
  require_approved_ami = rule {
    all tfplan.resource_changes as _, change {
      change.type is "aws_instance" and change.mode is "managed" implies
        change.change.after.ami in approved_amis
    }
  }
  
  main = rule {
    require_owner_tag and require_approved_ami
  }

5. UNIT AND INTEGRATION TESTING WITH TERRATEST
================================================================================

Terratest:
  Go framework for testing IaC.
  Can deploy REAL resources, run assertions, destroy resources.
  Supports: Terraform, Packer, Docker, Kubernetes, AWS, GCP, Azure.
  
  # go.mod:
  module github.com/my-org/my-infra-tests
  
  go 1.21
  
  require (
    github.com/gruntwork-io/terratest v0.46.0
    github.com/stretchr/testify v1.8.4
  )
  
  // test/s3_module_test.go:
  package test
  
  import (
    "testing"
    "strings"
    
    "github.com/gruntwork-io/terratest/modules/aws"
    "github.com/gruntwork-io/terratest/modules/random"
    "github.com/gruntwork-io/terratest/modules/terraform"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
  )
  
  func TestS3Module(t *testing.T) {
    t.Parallel()    // Run parallel with other tests (faster)
    
    awsRegion := "us-east-1"
    bucketName := "test-bucket-" + strings.ToLower(random.UniqueId())
    
    terraformOptions := &terraform.Options{
      TerraformDir: "../modules/s3",
      Vars: map[string]interface{}{
        "bucket_name":      bucketName,
        "enable_versioning": true,
        "tags": map[string]string{
          "Environment": "test",
          "Owner":       "terratest",
        },
      },
      // Clean up if test panics:
      NoColor: true,
    }
    
    // Destroy at end of test (even if test fails):
    defer terraform.Destroy(t, terraformOptions)
    
    // Deploy:
    terraform.InitAndApply(t, terraformOptions)
    
    // Get outputs:
    bucketID := terraform.Output(t, terraformOptions, "bucket_id")
    bucketARN := terraform.Output(t, terraformOptions, "bucket_arn")
    
    // Assertion 1: Outputs are not empty:
    assert.Equal(t, bucketName, bucketID)
    assert.True(t, strings.HasPrefix(bucketARN, "arn:aws:s3:::"))
    
    // Assertion 2: Bucket actually exists in AWS:
    aws.AssertS3BucketExists(t, awsRegion, bucketName)
    
    // Assertion 3: Versioning is enabled:
    actualVersioning := aws.GetS3BucketVersioning(t, awsRegion, bucketName)
    assert.Equal(t, "Enabled", actualVersioning)
    
    // Assertion 4: Bucket encryption enabled:
    aws.AssertS3BucketVersioningExists(t, awsRegion, bucketName)
  }
  
  // Run tests:
  # go test -v -timeout 30m ./test/
  # INDIVIDUAL: go test -v -run TestS3Module -timeout 30m ./test/

Test Stages Pattern (for faster development):
  Use build tags to run specific stages:
  
  // test/vpc_test.go:
  //go:build integration
  
  package test
  
  // Run only integration tests:
  # go test -v -tags integration -timeout 60m ./test/

Kitchen-Terraform (Ruby alternative):
  Uses Test Kitchen + InSpec for verifying deployed infrastructure.
  Less common than Terratest but familiar to Chef users.

6. COMPLIANCE FRAMEWORKS AND DRIFT DETECTION
================================================================================

CIS Benchmarks:
  Center for Internet Security — prescriptive security configurations.
  CIS AWS Foundations Benchmark v1.4:
  - CloudTrail enabled in all regions
  - S3 bucket logging enabled
  - RDS encryption at rest
  - IAM password policy
  - VPC flow logs enabled
  
  Tools: checkov has CIS AWS mappings built-in.
  checkov -d . --check CIS_AWS  # Run only CIS checks

AWS Config Rules:
  AWS native — continuously evaluates resource configurations.
  
  Managed rules (examples):
  s3-bucket-public-read-prohibited     # No public S3 buckets
  restricted-ssh                       # No unrestricted SSH
  rds-storage-encrypted                # RDS must be encrypted
  cloudtrail-enabled                   # CloudTrail must be on
  iam-root-access-key-check            # Root should have no access keys
  
  Custom Config rules (Lambda function evaluates resource):
  Check that all EC2 instances have specific tags, etc.

Drift Detection:
  Drift = cluster/infrastructure state has diverged from desired state.
  
  Scheduled terraform plan:
  # Run terraform plan daily, alert if changes detected:
  # GitHub Actions scheduled workflow:
  on:
    schedule:
      - cron: '0 9 * * 1-5'  # Every weekday at 9am UTC
  
  jobs:
    drift-detection:
      steps:
      - uses: actions/checkout@v4
      - name: Terraform Plan (drift check)
        run: |
          terraform init
          terraform plan -detailed-exitcode -out=tfplan
        # Exit codes: 0=no changes, 1=error, 2=changes
        continue-on-error: true
      
      - name: Alert on drift
        if: steps.plan.outputs.exitcode == '2'
        run: |
          curl -X POST ${{ secrets.SLACK_WEBHOOK }} \
            -d '{"text": "⚠️ Terraform drift detected in prod!"}'

7. SECRET SCANNING
================================================================================

git-secrets:
  AWS-maintained tool to prevent committing AWS credentials.
  
  # Install and configure:
  git secrets --install
  git secrets --register-aws    # Register AWS credential patterns
  
  # Scan repo:
  git secrets --scan
  git secrets --scan-history    # Scan all commits

detect-secrets (Yelp):
  More comprehensive — detects various secret patterns.
  
  # Install:
  pip install detect-secrets
  
  # Create baseline (known false positives):
  detect-secrets scan > .secrets.baseline
  
  # Scan for new secrets:
  detect-secrets scan --baseline .secrets.baseline
  
  # Audit baseline:
  detect-secrets audit .secrets.baseline

truffleHog:
  Searches entire Git history for secrets using entropy and regex patterns.
  
  # Scan repo:
  trufflehog git file://path/to/repo
  trufflehog git https://github.com/my-org/my-repo
  
  # Scan only new commits in CI:
  trufflehog git file://. \
    --branch main \
    --since-commit ${{ github.event.before }}

gitleaks:
  Fast, popular secret scanner. SARIF output for GitHub.
  
  # Scan:
  gitleaks detect --source .
  gitleaks detect --source . --report-path gitleaks-report.json
  
  # GitHub Actions:
  - name: Gitleaks
    uses: gitleaks/gitleaks-action@v2
    env:
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Remediation When Secrets Are Found in Git:
  1. Revoke the secret immediately (rotate keys, invalidate tokens)
  2. Remove from Git history using git-filter-repo (not git filter-branch)
  3. Force push to all branches
  4. Notify any team members who may have pulled the compromised code
  
  Prevention: Pre-commit hooks (see section 8) stop commits before they happen.

  Framework for managing multi-language pre-commit hooks.
  Hooks run before each commit, blocking bad commits.
  
  # Install:
  pip install pre-commit
  
  # .pre-commit-config.yaml:
  repos:
  
  # Terraform specific:
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.83.5
    hooks:
    - id: terraform_fmt
    - id: terraform_validate
    - id: terraform_tflint

      - "--args=--init"
    - id: terraform_tfsec
      args:
      - "--args=--minimum-severity=HIGH"
    - id: terraform_checkov
      args:
      - "--args=--skip-check CKV_AWS_18"
    - id: terraform_docs          # Update README module docs automatically
  
  # Secret scanning:
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
    - id: detect-secrets
      args: ['--baseline', '.secrets.baseline']
  
  # General:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
    - id: trailing-whitespace
    - id: end-of-file-fixer
    - id: check-yaml
    - id: check-json
    - id: check-merge-conflict
    - id: detect-private-key    # Built-in key detection
  
  # Docker:
  - repo: https://github.com/hadolint/hadolint

9. SUPPLY CHAIN SECURITY
================================================================================

Provider Version Pinning:
  
  # REQUIRED: Pin provider versions
  terraform {
    required_version = ">= 1.5.0, < 2.0.0"
    
    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.20"    # Allow 5.20.x and 5.21+ but not 6.x
      }
      kubernetes = {
        source  = "hashicorp/kubernetes"
        version = "~> 2.23"
      }
    }
  }

.terraform.lock.hcl:
  Lock file generated by terraform init.
  Records exact provider versions and checksums.
  
  # Example:
  provider "registry.terraform.io/hashicorp/aws" {
    version     = "5.20.1"
    constraints = "~> 5.20"
    hashes = [
      "h1:abc123...",           # Hash of provider binary
      "zh:def456...",
    ]
  }
  
  ALWAYS commit to source control.
  terraform init -upgrade     # Update to newest allowed version
  terraform providers lock    # Update hashes for all platforms

Module Version Pinning:
  
  # ALWAYS pin module versions (never use HEAD/latest):
  module "vpc" {
    source  = "terraform-aws-modules/vpc/aws"
    version = "5.1.2"    # Exact version
    # or:
    version = "~> 5.1"   # 5.1.x patch updates allowed
  }
  
  # For Git-sourced modules:
  module "vpc" {
    source = "git::https://github.com/org/terraform-modules.git//vpc?ref=v1.2.0"
    # ref= should be a RELEASE TAG, not a branch
  }

Container Image Security (related):
  
  # In Terraform that manages container workloads:
  # Never use :latest tag in Terraform-managed ECS/EKS configs
  
  # Image scanning in pipeline:
  - name: Scan image with Trivy
    uses: aquasecurity/trivy-action@master
    with:
      image-ref: myapp:${{ github.sha }}
      format: sarif
      output: trivy-results.sarif
      severity: HIGH,CRITICAL

10. IAC SECURITY PIPELINE
================================================================================

Complete Pipeline:
  
  # .github/workflows/terraform-security.yaml:
  name: IaC Security Pipeline
  on:
    pull_request:
      paths:
      - '**.tf'
      - '**.tfvars'
      - 'Dockerfile*'
  
  jobs:
    security-scan:
      runs-on: ubuntu-latest
      permissions:
        contents: read
        security-events: write    # For SARIF upload
      
      steps:
      - uses: actions/checkout@v4
      
      # 1. Secret scanning:
      - name: Gitleaks secret scan
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      
      # 2. Terraform formatting:
      - name: Terraform fmt check
        run: |
          terraform fmt -check -recursive
      
      # 3. Terraform validate:
      - name: Terraform Init & Validate
        run: |
          terraform init -backend=false
          terraform validate
      
      # 4. tflint:
      - name: tflint
        run: |
          curl -s https://raw.githubusercontent.com/terraform-linters/tflint/master/install_linux.sh | bash
          tflint --init && tflint
      
      # 5. tfsec:
      - name: tfsec
        uses: aquasecurity/tfsec-action@v1.0.0
        with:
          minimum_severity: HIGH
          format: sarif
          sarif_file: tfsec.sarif
      
      - name: Upload tfsec results
        uses: github/codeql-action/upload-sarif@v2
        with:
          sarif_file: tfsec.sarif
      
      # 6. checkov:
      - name: Checkov
        uses: bridgecrewio/checkov-action@v12
        with:
          directory: .
          framework: terraform
          output_format: sarif
          output_file_path: checkov.sarif
          soft_fail: false
      
      - name: Upload checkov results
        uses: github/codeql-action/upload-sarif@v2
        with:
          sarif_file: checkov.sarif
      
      # 7. OPA Policy check (on terraform plan):
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/TerraformReadOnlyRole
          aws-region: us-east-1
      
      - name: Terraform Plan
        run: |
          terraform init
          terraform plan -out=tfplan
          terraform show -json tfplan > plan.json
      
      - name: OPA policy check
        run: |
          curl -sSL https://github.com/open-policy-agent/conftest/releases/download/v0.46.0/conftest_0.46.0_Linux_x86_64.tar.gz | tar xz
          ./conftest test plan.json --policy policy/

11. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What tools would you use to test Terraform code and what does each test for?
A: I use a layered approach matching different risk levels and costs:
   
   Layer 1 — Static analysis (seconds, free, always run):
   
   terraform fmt -check     Format verification (consistent style)
   terraform validate       Syntax and config validation (no API calls needed)
   tflint                   Linter: invalid resource configs, deprecated syntax,
                            missing required providers/versions, naming rules
   
   Layer 2 — Security scanning (seconds, free):
   
   tfsec                    Terraform-specific security: open SGs, public S3,
                            no encryption, missing access logging
   checkov                  Multi-tool: Terraform + K8s + Dockerfiles.
                            CIS benchmark checks, custom checks
   
   Layer 3 — Policy as code (seconds-minutes):
   
   conftest + OPA           Custom org policies applied to terraform plan JSON:
                            required tags, approved AMIs, allowed regions
   Sentinel (HCP)           Built-in to HCP Terraform — enforced before apply
   
   Layer 4 — Integration tests (minutes-hours, cloud costs):
   
   Terratest (Go)           Deploy real resources, assert on outputs and
                            AWS API responses, destroy after test
   
   In CI pipeline: Layers 1-3 run on every PR (fast, no cost).
   Layer 4 runs nightly or before major releases (too slow/expensive for every PR).

Q2: What is policy as code and how would you enforce it in a Terraform pipeline?
A: Policy as code defines infrastructure requirements as executable, versioned policies
   rather than human-readable documentation that gets ignored.
   
   Problem without it:
   "All S3 buckets must be encrypted" in a wiki → engineers forget → violation reaches prod
   
   With policy as code:
   - Rego policy scans every terraform plan
   - PR is blocked until policy passes
   - Policy lives in Git (version controlled, reviewed, audited)
   
   Implementation options:
   
   1. OPA + Conftest (open source):
      - Write Rego policies (deny/warn rules)
      - Generate plan JSON: terraform show -json plan.tfplan > plan.json
      - Run: conftest test plan.json --policy policy/
      - Integrates into GitHub Actions as a pipeline step
      
   2. Sentinel (HCP Terraform):
      - Policies defined in Sentinel language (similar to OPA)
      - Evaluated AUTOMATICALLY between plan and apply
      - Enforcement levels: advisory/soft-mandatory/hard-mandatory
      - No extra CI setup needed — built into HCP Terraform workflow
   
   3. checkov (simpler, no custom policies):
      - Runs built-in CIS/NIST checks without writing Rego
      - Custom checks possible in Python
   
   What to enforce: Required tags (Owner, CostCenter, Environment),
   no public resources, encryption at rest required, no unrestricted ingress,
   deletion protection on databases, specific regions only.

Q3: What is drift detection in IaC and how do you handle it?
A: Drift is when the actual state of infrastructure diverges from what's defined in code.
   
   Causes:
   - Manual changes (ClickOps — someone changed a security group in AWS console)
   - Partial failed applies (some resources updated, others not)
   - External systems modifying resources (auto-scaling tags, AWS auto-remediation)
   - Resources changed by other teams who bypassed IaC
   
   Detection methods:
   
   1. terraform plan (shows drift immediately):
      If plan shows changes when none are expected → drift detected
      
   2. Scheduled drift detection:
      Run terraform plan daily on a schedule.
      If exit code == 2 (changes exist) → alert to Slack/PagerDuty
      
   3. ArgoCD/FluxCD (Kubernetes):
      GitOps tools continuously detect drift.
      ArgoCD selfHeal automatically reverts manual kubectl changes.
      Dashboard shows "Out of Sync" when drift exists.
   
   4. AWS Config Rules:
      Continuously monitor AWS resources for compliance.
      Alert when resources violate rules (public bucket, unencrypted disk).
   
   Handling drift:
   - Auto-correct: terraform apply (reconcile with code)
   - Accept: Update code to match reality (terraform import the change)
   - Investigate: Was the manual change legitimate? If so, update code first.
   
   Prevention:
   - Restrict AWS console permissions (deny modification without IaC)
   - SCPs (Service Control Policies) preventing certain actions outside IaC
   - Enforce IaC process: all changes via PR

Q4: How do you prevent secrets from being committed to Git in an IaC workflow?
A: Multi-layer prevention:
   
   1. Pre-commit hooks (first line of defense):
      detect-secrets or gitleaks runs before every commit.
      Block the commit if secrets detected.
      Engineer must rotate secret (it's compromised) then try again.
      
      # .pre-commit-config.yaml:
      - repo: https://github.com/Yelp/detect-secrets
        rev: v1.4.0
        hooks:
        - id: detect-secrets
      
   2. CI pipeline scanning:
      gitleaks/truffleHog scans on every PR.
      Even if engineer bypassed pre-commit (--no-verify), CI catches it.
      gitleaks scans full git history, not just the diff.
      
   3. .gitignore and .terraformignore:
      Add *.tfvars, terraform.tfvars, *.auto.tfvars to .gitignore
      Use .tfvars.example with placeholder values instead
      
   4. Proper secret management:
      Store secrets in AWS Secrets Manager / HashiCorp Vault
      Reference by ARN/path in Terraform (not value)
      Use SOPS for encrypting files before commit
      Use Ansible Vault for Ansible secrets
      
   5. If a secret IS committed:
      Revoke IMMEDIATELY (API key, rotate password)
      Use git-filter-repo to remove from history
      Force push all branches
      Alert team (anyone who pulled has the secret locally)
      
   Never rely on "I'll delete it in the next commit" — git history is permanent
   unless explicitly purged, and malicious actors may have already extracted it.

Q5: What is Terratest and when would you use it vs. static analysis?
A: Terratest is a Go framework for testing infrastructure code against REAL cloud resources.
   
   How it works:
   1. Write Go test functions using terraform.Options struct
   2. Test calls terraform.InitAndApply() → deploys actual AWS/GCP/Azure resources
   3. Test runs assertions against outputs and direct AWS SDK calls
   4. defer terraform.Destroy() → cleans up resources
   
   Example test scenario:
   TestVPCModule:
   - Deploys a real VPC in us-east-1
   - Asserts vpc_id output is not empty
   - Uses AWS SDK to verify subnet count == 2
   - Verifies internet gateway attached
   - Defer destroy runs cleanup
   
   When to use Terratest:
   - Testing reusable modules before publishing to registry
   - Integration tests for complex modules (VPC + EKS + RDS)
   - Verifying cloud-specific behavior that static analysis cannot catch
     (e.g., security group rules actually block traffic)
   - Compliance validation in staging before prod
   
   When NOT to use (use static analysis instead):
   - Every PR (too slow/expensive — minutes to hours, real cloud costs)
   - Simple syntax validation (terraform validate is instant and free)
   - Known security misconfigs (checkov catches in seconds)
   - Format validation (terraform fmt is instant)
   
   Best practice: Static analysis + security scan on every PR (seconds, free).
   Terratest nightly or weekly against staging account (slower but thorough).
