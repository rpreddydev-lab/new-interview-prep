1. TERRAFORM OVERVIEW AND ARCHITECTURE
================================================================================

What is Terraform?
  Open-source Infrastructure as Code tool by HashiCorp.
  Declarative: you describe desired state in HCL.
  Multi-provider: AWS, GCP, Azure, Kubernetes, GitHub, Cloudflare, and 2000+ more.
  
  Current: Terraform (open source, BSL license after v1.5.6)
  Alternative: OpenTofu (truly open source fork of Terraform, CNCF incubating)
  Enterprise: HCP Terraform (formerly Terraform Cloud), Terraform Enterprise

Core Workflow:
  
  Write → Init → Plan → Apply → (repeat)
  
  terraform init     Download providers, set up backend
  terraform plan     Show what will change (no changes made)
  terraform apply    Apply the plan (make changes)
  terraform destroy  Destroy all managed resources

How Terraform Works Internally:
  
  1. Parse .tf files → Build resource dependency graph
  2. Compare graph against current state (state file)
  3. Determine diff (what needs create/update/delete)
  4. Plan: Show the diff
  5. Apply: Call provider APIs to make changes
  6. Update state file with new reality

Terraform File Types:
  *.tf          Configuration files (main.tf, variables.tf, outputs.tf)
  *.tfvars      Variable values (terraform.tfvars, prod.tfvars)
  *.tfstate     State files (usually remote, never commit to Git)
  .terraform/   Local directory with provider plugins, module cache
  .terraform.lock.hcl  Dependency lock file (commit to Git!)

Typical File Structure:
  
  infrastructure/
  ├── main.tf             # Main resources
  ├── variables.tf        # Variable declarations
  ├── outputs.tf          # Output declarations
  ├── providers.tf        # Provider configuration
  ├── versions.tf         # Required versions
  ├── locals.tf           # Local values
  ├── data.tf             # Data sources
  ├── terraform.tfvars    # Variable values (not for secrets!)
  ├── prod.tfvars         # Production overrides
  └── modules/            # Local modules
      └── vpc/

2. HCL SYNTAX AND CONFIGURATION BLOCKS
================================================================================

HCL (HashiCorp Configuration Language):
  Human-readable, JSON-compatible declarative language.
  
  # Single-line comment
  /* Multi-line
     comment */
  
  # String:
  name = "my-value"
  
  # Number:
  count = 3
  
  # Boolean:
  enabled = true
  
  # List:
  availability_zones = ["us-east-1a", "us-east-1b", "us-east-1c"]
  
  # Map:
  tags = {
    Environment = "production"
    Team        = "platform"
  }

Block Types:
  
  # terraform: Configuration for Terraform itself
  terraform {
    required_version = ">= 1.5.0"
    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.0"
      }
    }
    backend "s3" {
      bucket = "my-tfstate"
      key    = "prod/terraform.tfstate"
      region = "us-east-1"
    }
  }
  
  # provider: Cloud provider config
  provider "aws" {
    region = var.aws_region
    alias  = "us-west"     # Multiple provider instances
  }
  
  # resource: A cloud resource to manage
  resource "aws_instance" "web" {
    ami           = data.aws_ami.ubuntu.id
    instance_type = var.instance_type
  }
  
  # data: Read existing resources (not managed by this config)
  data "aws_ami" "ubuntu" {
    most_recent = true
    filter {
      name   = "name"
      values = ["ubuntu/images/hvm-ssd/ubuntu-22.04-amd64-*"]
    }
  }
  
  # variable: Input parameters
  variable "instance_type" {
    type        = string
    default     = "t3.micro"
    description = "EC2 instance type"
  }
  
  # output: Return values
  output "instance_ip" {
    value       = aws_instance.web.public_ip
    description = "Public IP of web server"
  }
  
  # locals: Computed values
  locals {
    common_tags = {
      ManagedBy   = "terraform"
      Environment = var.environment
    }
  }
  
  # module: Reusable module
  module "vpc" {
    source  = "terraform-aws-modules/vpc/aws"
    version = "5.0.0"
    
    name = "my-vpc"
    cidr = "10.0.0.0/16"
  }

3. PROVIDERS
================================================================================

Provider Configuration:
  
  terraform {
    required_providers {
      aws = {
        source  = "hashicorp/aws"    # Registry path
        version = "~> 5.0"           # Version constraint
      }
      kubernetes = {
        source  = "hashicorp/kubernetes"
        version = ">= 2.20.0"
      }
    }
  }
  
  provider "aws" {
    region  = "us-east-1"
    profile = "production"           # AWS CLI profile
    
    # Or with explicit credentials (not recommended, use env vars):
    # access_key = var.aws_access_key
    # secret_key = var.aws_secret_key
    
    default_tags {
      tags = {
        ManagedBy = "terraform"
      }
    }
  }

Provider Authentication (AWS):
  Priority order:
  1. Static credentials in provider block (NOT recommended)
  2. Environment variables: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
  3. AWS shared credentials file (~/.aws/credentials)
  4. Instance profile (when running on EC2)
  5. ECS task role, EKS pod role (IRSA)
  
  Best practice in CI/CD:
  Use GitHub Actions OIDC → assume IAM role → no static credentials stored.

Multiple Provider Aliases:
  
  # Primary AWS region:
  provider "aws" {
    region = "us-east-1"
  }
  
  # DR region:
  provider "aws" {
    alias  = "us-west"
    region = "us-west-2"
  }
  
  # Use alias in resource:
  resource "aws_s3_bucket" "dr" {
    provider = aws.us-west
    bucket   = "my-dr-bucket"
  }

Version Constraints:
  = 1.0.0     Exactly 1.0.0
  != 1.0.0    Not 1.0.0
  > 1.0.0     Greater than
  >= 1.0.0    Greater than or equal
  < 2.0.0     Less than
  ~> 1.5.0    "pessimistic": >= 1.5.0, < 1.6.0 (patch only)
  ~> 1.5      "pessimistic": >= 1.5, < 2.0 (minor only)
  
  Recommended: Use ~> to allow patch updates but pin major+minor.
  Lock file (.terraform.lock.hcl) pins exact versions: commit to Git.

4. RESOURCES
================================================================================

Resource Syntax:
  
  resource "<PROVIDER>_<TYPE>" "<NAME>" {
    # Arguments
  }
  
  # <PROVIDER>_<TYPE>.<NAME>  is the resource's address in Terraform

Resource Examples:
  
  # EC2 instance:
  resource "aws_instance" "web" {
    ami                    = "ami-0c55b159cbfafe1f0"
    instance_type          = "t3.medium"
    subnet_id              = aws_subnet.public.id       # Reference another resource
    vpc_security_group_ids = [aws_security_group.web.id]
    key_name               = "my-key-pair"
    
    user_data = <<-EOF
      #!/bin/bash
      apt-get update
      apt-get install -y nginx
    EOF
    
    tags = merge(local.common_tags, {
      Name = "web-server"
    })
  }
  
  # S3 bucket:
  resource "aws_s3_bucket" "data" {
    bucket = "my-company-data-${var.environment}"
    
    tags = local.common_tags
  }
  
  resource "aws_s3_bucket_versioning" "data" {
    bucket = aws_s3_bucket.data.id    # Dependency: waits for bucket
    versioning_configuration {
      status = "Enabled"
    }
  }
  
  resource "aws_s3_bucket_server_side_encryption_configuration" "data" {
    bucket = aws_s3_bucket.data.id
    rule {
      apply_server_side_encryption_by_default {
        sse_algorithm = "aws:kms"
      }
    }
  }

Resource Meta-Arguments:
  
  # count — create multiple resources:
  resource "aws_instance" "worker" {
    count         = 3
    instance_type = "t3.medium"
    ami           = data.aws_ami.ubuntu.id
    
    tags = {
      Name = "worker-${count.index}"    # worker-0, worker-1, worker-2
    }
  }
  
  # for_each — create resources from a map/set:
  variable "buckets" {
    default = {
      logs    = "STANDARD"
      backups = "GLACIER"
      media   = "STANDARD"
    }
  }
  
  resource "aws_s3_bucket" "each" {
    for_each = var.buckets
    bucket   = "my-company-${each.key}"    # key: logs, backups, media
    
    tags = {
      StorageClass = each.value             # value: STANDARD, GLACIER
    }
  }
  
  # depends_on — explicit dependency (usually auto-detected):
  resource "aws_instance" "app" {
    depends_on = [aws_db_instance.main]    # Explicitly wait for DB
  }
  
  # lifecycle — control resource behavior:
  resource "aws_instance" "web" {
    lifecycle {
      create_before_destroy = true    # Create new before destroying old
      prevent_destroy       = true    # Error if anyone tries to destroy
      ignore_changes        = [       # Don't track changes to these attributes
        user_data,
        tags["LastUpdated"],
      ]
    }
  }

References Between Resources:
  # Syntax: <resource_type>.<resource_name>.<attribute>
  
  resource "aws_security_group" "web" {
    name   = "web-sg"
    vpc_id = aws_vpc.main.id    # References vpc resource's id attribute
  }
  
  resource "aws_instance" "web" {
    vpc_security_group_ids = [aws_security_group.web.id]
    subnet_id              = aws_subnet.public.id
  }
  
  # Terraform builds a dependency graph from these references
  # and creates resources in the right order automatically

5. VARIABLES AND OUTPUTS
================================================================================

Variable Declaration (variables.tf):
  
  variable "environment" {
    type        = string                     # string, number, bool, list, map, any
    default     = "development"
    description = "Deployment environment"
    
    validation {
      condition     = contains(["development", "staging", "production"], var.environment)
      error_message = "Must be development, staging, or production."
    }
    
    sensitive = false    # Mark sensitive: true to hide from logs
  }
  
  variable "vpc_cidr" {
    type    = string
    default = "10.0.0.0/16"
  }
  
  variable "allowed_ports" {
    type    = list(number)
    default = [80, 443, 8080]
  }
  
  variable "instance_map" {
    type = map(string)
    default = {
      web    = "t3.medium"
      worker = "t3.large"
    }
  }
  
  variable "db_password" {
    type      = string
    sensitive = true    # Never logged or shown in plan output
    # No default: must be provided
  }

Providing Variable Values:
  1. terraform.tfvars (auto-loaded):
     environment = "production"
     vpc_cidr    = "10.1.0.0/16"
  
  2. Named .tfvars files:
     terraform apply -var-file="prod.tfvars"
  
  3. CLI flags:
     terraform apply -var="environment=production" -var="db_password=secret"
  
  4. Environment variables (TF_VAR_<name>):
     export TF_VAR_environment=production
     export TF_VAR_db_password=secret

Output Values (outputs.tf):
  
  output "vpc_id" {
    value       = aws_vpc.main.id
    description = "The ID of the VPC"
  }
  
  output "load_balancer_dns" {
    value       = aws_lb.main.dns_name
    description = "DNS name of the load balancer"
  }
  
  output "db_password" {
    value     = aws_db_instance.main.password
    sensitive = true    # Never shown in terminal output
  }
  
  # Output a map:
  output "instance_ips" {
    value = {
      for k, v in aws_instance.workers : k => v.public_ip
    }
  }

Accessing Outputs from Other Modules/States:
  # Remote state data source:
  data "terraform_remote_state" "vpc" {
    backend = "s3"
    config = {
      bucket = "my-tfstate"
      key    = "networking/terraform.tfstate"
      region = "us-east-1"
    }
  }
  
  # Use output from that state:
  resource "aws_instance" "app" {
    subnet_id = data.terraform_remote_state.vpc.outputs.private_subnet_ids[0]
  }

6. DATA SOURCES
================================================================================

Data sources READ existing resources (not managed by this Terraform code).
  
  # Look up the latest Ubuntu AMI:
  data "aws_ami" "ubuntu" {
    most_recent = true
    owners      = ["099720109477"]    # Canonical's AWS account
    
    filter {
      name   = "name"
      values = ["ubuntu/images/hvm-ssd/ubuntu-22.04-amd64-*"]
    }
    filter {
      name   = "virtualization-type"
      values = ["hvm"]
    }
  }
  
  # Use it:
  resource "aws_instance" "web" {
    ami = data.aws_ami.ubuntu.id
  }
  
  # Look up existing VPC:
  data "aws_vpc" "existing" {
    filter {
      name   = "tag:Name"
      values = ["production-vpc"]
    }
  }
  
  # Current AWS account:
  data "aws_caller_identity" "current" {}
  
  output "account_id" {
    value = data.aws_caller_identity.current.account_id
  }
  
  # AWS region:
  data "aws_region" "current" {}

7. LOCALS
================================================================================

Locals are computed values, used to avoid repeating expressions.
  
  locals {
    environment = var.environment
    region      = data.aws_region.current.name
    
    # Computed values:
    name_prefix = "${var.project}-${var.environment}"
    
    # Common tags for all resources:
    common_tags = {
      Environment = var.environment
      Project     = var.project
      ManagedBy   = "terraform"
      Region      = data.aws_region.current.name
    }
    
    # Conditional:
    instance_type = var.environment == "production" ? "t3.large" : "t3.micro"
    
    # List manipulation:
    enabled_azs = [for az in var.availability_zones : az if !contains(var.disabled_azs, az)]
  }
  
  # Use with:
  resource "aws_instance" "web" {
    tags = merge(local.common_tags, { Name = "${local.name_prefix}-web" })
  }

8. MODULES
================================================================================

Modules are reusable, composable Terraform configurations.
A module is just a directory with .tf files.

Using a Module:
  
  # Terraform Registry module:
  module "vpc" {
    source  = "terraform-aws-modules/vpc/aws"
    version = "5.1.0"
    
    name = "production-vpc"
    cidr = "10.0.0.0/16"
    
    azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
    private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
    public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]
    
    enable_nat_gateway = true
    single_nat_gateway = false  # HA: one per AZ
    
    tags = local.common_tags
  }
  
  # Local module:
  module "web_server" {
    source = "./modules/web-server"
    
    environment   = var.environment
    instance_type = local.instance_type
    vpc_id        = module.vpc.vpc_id
    subnet_ids    = module.vpc.private_subnets
  }

Accessing Module Outputs:
  # module.<MODULE_NAME>.<OUTPUT_NAME>
  subnet_id = module.vpc.private_subnets[0]
  vpc_id    = module.vpc.vpc_id

Writing a Module (modules/web-server/):
  
  # modules/web-server/variables.tf:
  variable "environment" { type = string }
  variable "instance_type" { type = string }
  variable "vpc_id" { type = string }
  variable "subnet_ids" { type = list(string) }
  
  # modules/web-server/main.tf:
  resource "aws_instance" "this" {
    ami           = data.aws_ami.ubuntu.id
    instance_type = var.instance_type
    subnet_id     = var.subnet_ids[0]
    # ...
  }
  
  # modules/web-server/outputs.tf:
  output "instance_id" {
    value = aws_instance.this.id
  }

  terraform state show aws_instance.web       # Show resource attributes

  terraform refresh    # Sync state with real cloud resources (deprecated: use plan -refresh-only)
  terraform plan -refresh-only   # Show drift without applying

10. TERRAFORM WORKFLOW COMMANDS
================================================================================

Daily Commands:
  
  # Initialize (run once per directory):
  terraform init
  terraform init -upgrade    # Upgrade providers to latest matching version
  terraform init -backend=false  # No backend (local testing)
  
  # Plan (what will change):
  terraform plan
  terraform plan -out=tfplan          # Save plan to file
  terraform plan -var-file=prod.tfvars
  terraform plan -destroy             # Plan a destroy operation
  terraform plan -target=aws_instance.web  # Plan only specific resource
  
  # Apply:
  terraform apply              # Prompts for confirmation
  terraform apply -auto-approve  # No prompt (CI/CD)
  terraform apply tfplan         # Apply saved plan file
  terraform apply -target=aws_instance.web
  
  # Destroy:
  terraform destroy
  terraform destroy -auto-approve
  terraform destroy -target=aws_instance.old
  
  # Format code:
  terraform fmt               # Format all .tf files in current directory
  terraform fmt -recursive    # Format all files in all subdirectories
  terraform fmt -check        # Check without modifying (CI check)
  
  # Validate:
  terraform validate    # Check syntax and internal consistency
  
  # Show:
  terraform show             # Show current state
  terraform show tfplan      # Show contents of saved plan
  
  # Output:
  terraform output                    # Show all outputs
  terraform output load_balancer_dns  # Specific output

11. WORKSPACES
================================================================================

Workspaces allow multiple states in the same directory.
  
  # Create and switch workspace:
  terraform workspace new production
  terraform workspace select staging
  terraform workspace list
  terraform workspace show    # Current workspace
  
  # Use workspace in code:
  locals {
    instance_type = {
      default    = "t3.micro"
      staging    = "t3.medium"
      production = "t3.large"
    }[terraform.workspace]
  }
  
  resource "aws_instance" "web" {
    instance_type = local.instance_type
    # ...
  }

Workspace vs Directory-per-environment:
  
  Workspaces:
  - Same code, different state
  - Simple setup
  - Limited: can't have different module configs per workspace
  - Good for: identical infrastructure in different accounts
  
  Directories (recommended for complex setups):
  infrastructure/
  ├── modules/
  ├── environments/
  │   ├── dev/
  │   │   ├── main.tf
  │   │   └── terraform.tfvars
  │   ├── staging/
  │   └── production/
  
  - Separate state per environment
  - Can customize per-environment
  - More files to maintain
  - Recommended for environments that differ significantly

12. ADVANCED FEATURES
================================================================================

Dynamic Blocks:
  
  # Generate multiple ingress rules from a list:
  variable "ingress_ports" {
    default = [80, 443, 8080]
  }
  
  resource "aws_security_group" "web" {
    name   = "web-sg"
    vpc_id = aws_vpc.main.id
    
    dynamic "ingress" {
      for_each = var.ingress_ports
      content {
        from_port   = ingress.value
        to_port     = ingress.value
        protocol    = "tcp"
        cidr_blocks = ["0.0.0.0/0"]
      }
    }
  }

For Expressions:
  
  # Transform a list:
  output "instance_ids" {
    value = [for i in aws_instance.workers : i.id]
  }
  
  # Filter + transform:
  output "public_ips" {
    value = [for i in aws_instance.workers : i.public_ip if i.public_ip != ""]
  }
  
  # Create a map from a list:
  locals {
    instance_map = {for i in aws_instance.workers : i.tags["Name"] => i.public_ip}
  }

Conditional Expressions:
  instance_type = var.env == "prod" ? "t3.large" : "t3.micro"
  
  count = var.create_resource ? 1 : 0    # Conditional resource creation

Functions:
  # String:
  lower("HELLO")           → "hello"
  upper("hello")           → "HELLO"
  format("%-10s", "hi")    → "hi        "
  replace(str, "/old/", "new")
  split(",", "a,b,c")      → ["a", "b", "c"]
  join("-", ["a", "b"])    → "a-b"
  
  # Collection:
  length(list)
  merge(map1, map2)
  concat(list1, list2)
  flatten(nested_list)
  toset(list)              → deduplicated set
  
  # Encoding:
  base64encode("text")
  jsonencode({key = "value"})
  yamlencode({key = "value"})
  
  # File:
  file("./scripts/init.sh")      # Read file contents
  filebase64("./cert.pem")       # Read file as base64
  templatefile("init.sh.tpl", {var = value})

Moved Blocks (Refactoring without destroy/recreate):
  
  # Renamed a resource? Use moved block to preserve state:
  moved {
    from = aws_instance.web
    to   = aws_instance.web_server
  }
  
  # Moved into a module:
  moved {
    from = aws_instance.web
    to   = module.web_server.aws_instance.this
  }

13. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: Explain the Terraform workflow. What happens when you run terraform apply?
A: The core Terraform workflow:
   
   1. terraform init:
      - Downloads providers (plugins) matching required_providers version constraints
      - Initializes backend (sets up S3 remote state connection)
      - Downloads modules
      - Creates .terraform/ directory and .terraform.lock.hcl
   
   2. terraform plan:
      - Reads all .tf files and builds a resource graph
      - Reads current state (remote state file)
      - Calls provider APIs to refresh actual resource state
      - Computes DIFF: what needs create/update/delete
      - Shows changes: + green (create), ~ yellow (update), - red (destroy)
      - Does NOT make any changes
   
   3. terraform apply:
      - Shows the plan again
      - Prompts for confirmation (or -auto-approve in CI)
      - Acquires state lock (DynamoDB for S3 backend)
      - Executes changes: creates, updates, deletes resources via provider APIs
      - After each successful change: updates state file
      - On completion: releases lock
   
   Key: Plan is deterministic and safe. Apply makes real changes.
   Always run plan in PR review, apply only after approval.

Q2: What is the difference between count and for_each? When would you use each?
A: Both create multiple resource instances, but differently:
   
   count:
   - Uses integers (0, 1, 2...)
   - Resources addressed as: aws_instance.web[0], aws_instance.web[1]
   - Problem: If you remove an item from the middle of a list,
     all subsequent resources are destroyed and recreated
     (indexes shift: item 2→1, item 3→2, etc.)
   
   for_each:
   - Uses maps or sets (string keys)
   - Resources addressed by key: aws_instance.web["frontend"], aws_instance.web["backend"]
   - Stable: Removing one item only destroys THAT item
     (others retain their keys, no unnecessary recreates)
   
   Use count when:
   - Creating N identical resources (N workers, N instances)
   - Simple "create or don't create": count = var.enabled ? 1 : 0
   
   Use for_each when:
   - Creating resources from a list/map of distinct items
   - Items might be added/removed (need stable addressing)
   - Resources are distinguishable (have meaningful names)
   
   Example of count problem:
   list = ["a", "b", "c"]  → web[0]="a", web[1]="b", web[2]="c"
   Remove "b":
   list = ["a", "c"]       → web[0]="a", web[1]="c"  ← web[1] changed!
   Terraform: destroy web[1]("b"), update web[1]("c"), destroy web[2]("c")
   → 3 operations to remove 1 item.
   
   for_each avoids this: each key is stable.

Q3: How does Terraform handle dependencies between resources?
A: Terraform builds a dependency graph automatically and handles ordering.
   
   Implicit dependencies:
   When you reference one resource in another, Terraform automatically
   infers the dependency:
   
   resource "aws_vpc" "main" { ... }
   resource "aws_subnet" "public" {
     vpc_id = aws_vpc.main.id    # Implicit dep: subnet created AFTER vpc
   }
   
   Terraform reads aws_vpc.main.id → knows subnet depends on vpc.
   Graph ensures VPC created first, subnet second.
   
   Parallel execution:
   Resources WITHOUT dependencies on each other are created in parallel.
   Terraform uses goroutines, limited by -parallelism flag (default: 10).
   
   Explicit dependencies (depends_on):
   For cases where dependency isn't evident from references:
   
   resource "aws_instance" "app" {
     depends_on = [aws_iam_role_policy.app_permissions]
     # Instance needs the IAM policy applied first,
     # but doesn't reference it in its config
   }
   
   Use depends_on sparingly — usually implicit is sufficient.
   Overuse breaks parallelism.

Q4: What are Terraform modules and why are they important?
A: A module is a reusable set of Terraform configurations packaged together.
   Any directory with .tf files is a module.
   
   Why modules:
   1. DRY (Don't Repeat Yourself): Define VPC config once, use in dev/staging/prod
   2. Abstraction: Hide complexity, expose simple interface (variables)
   3. Standardization: Enforce company standards (security defaults, tagging)
   4. Versioning: modules can be versioned; environments pin to versions
   
   Types:
   1. Root module: The .tf files you're running directly
   2. Local module: ./modules/vpc (relative path)
   3. Registry module: terraform-aws-modules/vpc/aws (Terraform Registry)
   4. Git module: git::https://github.com/example/modules.git//vpc
   
   Best practices:
   - Small, focused modules (vpc, eks-cluster, rds, not "everything")
   - Clear variable descriptions and validation
   - Document required/optional variables
   - Expose necessary outputs (IDs, ARNs for cross-module references)
   - Version pin registry modules (~> 5.0 not *)
   
   Terraform Registry modules:
   Community-maintained, battle-tested modules.
   terraform-aws-modules organization is most popular for AWS.
   Example: terraform-aws-modules/eks/aws for EKS cluster.

Q5: What happens if someone makes a manual change in the AWS console? How does Terraform detect it?
A: This is called "configuration drift" or "state drift."
   
   Detection:
   terraform plan (with refresh=true, which is default) calls cloud APIs
   to get actual current state, compares to state file, compares to code.
   
   If manual changes were made:
   - Plan shows changes to bring reality back to desired code state
   - Example: Someone added an inbound rule to a security group
     → plan shows: "~ aws_security_group.web: ingress to remove"
   
   Options when drift is detected:
   
   1. Apply (revert manual change, code wins):
      terraform apply
      Reverts the security group rule. Code is truth.
   
   2. Update code to match manual change (approved change):
      Add the rule to the .tf file.
      terraform plan → no changes.
   
   3. Refresh-only (update state to match reality, don't change anything):
      terraform apply -refresh-only
      Updates state file to include the manual change.
      WARNING: Now code and state are out of sync.
   
   Prevention:
   - Team policy: Never make manual changes. Always use Terraform.
   - IAM policies: Restrict production access to only Terraform's IAM role
   - Automated drift detection: Regular terraform plan in CI, alert on non-empty plan
   - Terraform Sentinel / OPA: Block manual changes via Service Control Policies
