1. WHAT IS INFRASTRUCTURE AS CODE
================================================================================

Definition:
  Infrastructure as Code (IaC) is the practice of managing and provisioning
  infrastructure (servers, networks, databases, cloud resources) through
  machine-readable configuration files, rather than manual processes or
  interactive configuration tools.
  
  "If your infrastructure can't be re-created from a Git commit, it's manual."

What IaC Manages:
  - Virtual machines and servers (EC2, VMs)
  - Networking (VPCs, subnets, security groups, load balancers)
  - Databases (RDS, DynamoDB tables, cloud SQL instances)
  - Kubernetes clusters (EKS, GKE, AKS)
  - DNS records
  - IAM roles and policies
  - Storage buckets (S3, GCS, Azure Blob)
  - Container registries
  - Message queues (SQS, SNS, Pub/Sub)
  - CDN configurations (CloudFront, CloudFlare)

Before IaC (Traditional "ClickOps"):
  
  Traditional approach:
  1. Log into AWS Console
  2. Click through wizard to create VPC, subnets, EC2 instances
  3. Write steps in a runbook (Word document)
  4. 6 months later: "What did we actually configure?"
  5. Another team member tries to recreate: slightly different
  6. Staging looks different from production
  7. "Works on my cloud, not yours"
  
  Problems:
  ✗ Not reproducible (manual steps = human error)
  ✗ Configuration drift (environments diverge over time)
  ✗ No version history (can't see what changed, when, by whom)
  ✗ Disaster recovery takes days (rebuild manually)
  ✗ Scaling requires manual work per resource

After IaC:
  ✓ Infrastructure defined in code (Git-tracked)
  ✓ Reproducible: same code = same infrastructure
  ✓ Version controlled: `git log` shows infrastructure history
  ✓ Code review: infrastructure changes go through PR process
  ✓ Automated: CI/CD applies infrastructure changes
  ✓ Testable: linting, validation, compliance checks
  ✓ Disaster recovery: `terraform apply` recreates everything

2. CORE IaC PRINCIPLES
================================================================================

1. Idempotency:
  Running the same IaC code multiple times produces the same result.
  If the desired state already exists → no changes.
  
  Idempotent: terraform apply (checks state, only makes needed changes)
  Not idempotent: running a shell script that creates resources
                  (would fail or duplicate on second run)

2. Version Control Everything:
  All IaC code lives in Git (or equivalent).
  Infrastructure changes are commits, PRs, reviewed like application code.
  
  "If it's not in Git, it doesn't exist."

3. Immutable Infrastructure:
  Don't modify running infrastructure. Replace it.
  Instead of: SSH into server and update config
  Do: Deploy new AMI/image, terminate old server
  
  Avoids configuration drift and "snowflake servers" (unique configs that
  can't be reproduced).

4. Declarative Configuration:
  Describe the DESIRED STATE, not the steps to get there.
  The tool figures out HOW to make reality match the desired state.
  
  Declarative: "I want 3 EC2 t3.medium instances with this security group"
  Imperative:  "Run: aws ec2 run-instances --type t3.medium (3 times)"

5. Self-documenting:
  The IaC files ARE the documentation of your infrastructure.
  No separate runbooks needed (they go stale).
  
  Good variable naming + comments + README = living documentation.

6. Separation of Environments:
  Different configurations for dev/staging/production.
  Achieved via Terraform workspaces, variable files, or directory structure.

3. IaC BENEFITS AND CHALLENGES
================================================================================

BENEFITS:
  
  Speed and Agility:
  ✓ Provision environments in minutes, not days/weeks
  ✓ Spin up complete dev environments on demand
  ✓ Tear down environments when not needed (cost savings)
  
  Consistency:
  ✓ Dev, staging, prod use identical infrastructure code
  ✓ No "it works in staging, not prod" due to infra differences
  ✓ Configuration drift eliminated
  
  Collaboration:
  ✓ Infrastructure changes reviewed via pull requests
  ✓ Team knowledge distributed (not one person knows the setup)
  ✓ Onboarding: new team member reads code to understand infra
  
  Risk Reduction:
  ✓ Changes planned before applied (terraform plan)
  ✓ Rollback possible (git revert + apply)
  ✓ Disaster recovery: full infrastructure recreatable from code
  
  Compliance and Auditing:
  ✓ Git history = audit trail for every infrastructure change
  ✓ Policy as code: enforce security standards automatically
  ✓ Compliance checks run in CI before applying

CHALLENGES:
  
  Learning Curve:
  ✗ Teams must learn Terraform/CloudFormation/Ansible
  ✗ HCL (Terraform), YAML (Ansible), JSON (CloudFormation) syntax
  ✗ Understanding cloud provider APIs through tool abstractions
  
  State Management:
  ✗ Terraform maintains state file — must be handled carefully
  ✗ State file can drift from reality (manual changes outside IaC)
  ✗ State locking needed for team environments
  
  Refactoring Difficulty:
  ✗ Renaming resources can cause destroy + recreate
  ✗ Moving resources between modules/states requires care
  
  Secrets Management:
  ✗ Credentials often needed in IaC (cloud API keys)
  ✗ Can't commit secrets to Git
  ✗ Secret injection via CI environment variables or Vault
  
  Testing Infrastructure Code:
  ✗ Hard to unit test (requires real cloud account usually)
  ✗ Infrastructure tests take minutes to run (slow feedback)
  ✗ Tools: Terratest, kitchen-terraform, checkov, tfsec

================================================================================

Major IaC Tools:
  
  ┌──────────────────┬────────────────┬───────────────┬──────────────────┐
  │ Tool             │ Type           │ Cloud         │ Language         │
  ├──────────────────┼────────────────┼───────────────┼──────────────────┤
  │ Terraform        │ Provisioning   │ Multi-cloud   │ HCL              │
  │ Pulumi           │ Provisioning   │ Multi-cloud   │ TypeScript/Python│
  │ AWS CloudFormation│ Provisioning  │ AWS only      │ YAML/JSON        │
  │ AWS CDK          │ Provisioning   │ AWS only      │ TypeScript/Python│
  │ Azure Bicep      │ Provisioning   │ Azure only    │ Bicep DSL        │
  │ Google Deployment│ Provisioning   │ GCP only      │ YAML/Python      │
  │ Ansible          │ Configuration  │ Multi-cloud   │ YAML             │
  │ Chef/Puppet      │ Configuration  │ Multi-cloud   │ Ruby/DSL         │
  │ SaltStack        │ Configuration  │ Multi-cloud   │ YAML/Python      │
  └──────────────────┴────────────────┴───────────────┴──────────────────┘

Terraform vs CloudFormation:
  
  ASPECT              TERRAFORM                   CLOUDFORMATION
  ───────────────────────────────────────────────────────────────────────
  Cloud support       Multi-cloud                 AWS only
  Language            HCL (HashiCorp Config Lang) YAML or JSON
  State               External state file         AWS manages state
  Plan before apply   Yes (terraform plan)        Change sets
  Provider community  Huge (2000+ providers)      AWS-only
  Drift detection     terraform plan              Drift detection built-in
  Import existing     terraform import            CloudFormation import
  Cost                Open source (Terraform),    Free
                      Terraform Cloud (paid)
  Managed offering    HCP Terraform / Terraform   CloudFormation Service
                      Enterprise
  Modules             Module registry             Nested stacks
  ───────────────────────────────────────────────────────────────────────
  
  Choose Terraform when: Multi-cloud, team already knows it, complex modules needed.
  Choose CloudFormation when: AWS-only, tight AWS service integration needed,
                              want AWS-managed state.

Terraform vs Ansible:
  
  ASPECT              TERRAFORM                   ANSIBLE
  ───────────────────────────────────────────────────────────────────────
  Primary use         Infrastructure provisioning Server configuration
  State               Stateful (tracks resources) Stateless
  Declarative/Imperative Declarative              Can be both
  Idempotent          Yes                         Mostly yes
  Agentless           Yes (provider APIs)         Yes (SSH)
  Best for            Cloud resources, VMs        OS config, software install
                      Networks, K8s clusters      Application deployment
  ───────────────────────────────────────────────────────────────────────
  
  Often used together:
  Terraform: Provision cloud infrastructure (EC2, VPC, RDS)
  Ansible: Configure the servers Terraform created (install nginx, deploy app)

Provisioning vs Configuration Management:
  
  Provisioning (Terraform, CloudFormation):
  - Create and manage cloud resources
  - Focus: What infrastructure exists
  
  Configuration Management (Ansible, Chef, Puppet):
  - Configure existing servers
  - Focus: What is installed/configured on servers
  
  Modern shift: Containers and Kubernetes have reduced the need for
  configuration management on servers (immutable images replace server config).

5. DECLARATIVE vs IMPERATIVE APPROACHES
================================================================================

Declarative (Terraform, CloudFormation, Kubernetes):
  You describe the DESIRED END STATE.
  The tool determines the steps to get there.
  
  # Terraform: "I want an S3 bucket with versioning enabled"
  resource "aws_s3_bucket" "my_bucket" {
    bucket = "my-company-data"
  }
  resource "aws_s3_bucket_versioning" "my_bucket" {
    bucket = aws_s3_bucket.my_bucket.id
    versioning_configuration {
      status = "Enabled"
    }
  }
  
  # Apply twice: Second run = no changes (idempotent)
  
  Benefits:
  ✓ Tool handles ordering, dependencies
  ✓ Idempotent by nature
  ✓ Easy to understand current desired state

Imperative (shell scripts, AWS CLI):
  You describe the STEPS to perform.
  
  #!/bin/bash
  aws s3api create-bucket --bucket my-company-data
  aws s3api put-bucket-versioning \
    --bucket my-company-data \
    --versioning-configuration Status=Enabled
  
  # Run twice: FAILS on second run (bucket already exists)
  
  Problems:
  ✗ Must handle idempotency yourself
  ✗ Must handle ordering and error cases
  ✗ Script describes HOW not WHAT

6. IaC IN THE CI/CD PIPELINE
================================================================================

IaC Pipeline Stages:
  
  Developer → Push → Git repo
                         ↓
                    Pull Request
                         ↓
                  ┌──────────────┐
                  │ CI Pipeline  │
                  │ - lint       │
                  │ - validate   │
                  │ - plan       │
                  │ - security   │
                  │   scan       │
                  └──────┬───────┘
                         ↓
                    PR Review
                  (shows plan output)
                         ↓
                    Merge to main
                         ↓
                  ┌──────────────┐
                  │ CD Pipeline  │
                  │ - apply      │
                  │   (staging)  │
                  │ - test       │
                  │ - apply      │
                  │   (prod)     │
                  └──────────────┘

GitHub Actions Terraform Pipeline:
  
  name: Terraform
  on:
    pull_request:
      paths: ['infrastructure/**']
    push:
      branches: [main]
      paths: ['infrastructure/**']
  
  jobs:
    terraform:
      runs-on: ubuntu-latest
      defaults:
        run:
          working-directory: infrastructure/
      steps:
      - uses: actions/checkout@v4
      
      - uses: hashicorp/setup-terraform@v2
        with:
          terraform_version: 1.6.0
      
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-actions-terraform
          aws-region: us-east-1
      
      - name: Terraform Init
        run: terraform init
      
      - name: Terraform Validate
        run: terraform validate
      
      - name: Terraform Lint
        run: |
          curl -s https://raw.githubusercontent.com/terraform-linters/tflint/master/install_linux.sh | bash
          tflint --init && tflint
      
      - name: Security Scan (tfsec)
        run: |
          curl -L https://github.com/aquasecurity/tfsec/releases/latest/download/tfsec-linux-amd64 -o tfsec
          chmod +x tfsec && ./tfsec .
      
      - name: Terraform Plan
        id: plan
        run: terraform plan -out=tfplan -input=false
      
      - name: Post Plan to PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v6
        # Post plan output as PR comment
      
      - name: Terraform Apply
        if: github.ref == 'refs/heads/main'
        run: terraform apply tfplan

GitOps for IaC:
  Same as application GitOps but for infrastructure.
  Tools: Atlantis (Terraform PR automation), Spacelift, env0, HCP Terraform.
  
  Atlantis workflow:
  1. PR → Atlantis auto-runs `terraform plan`
  2. Posts plan output as PR comment
  3. Reviewer approves: comment `atlantis apply`
  4. Atlantis runs `terraform apply`, commits plan file

7. STATE MANAGEMENT
================================================================================

What is IaC State?
  Terraform (and similar tools) maintain a STATE FILE that maps:
  Your code → Real cloud resources
  
  State file contains: resource IDs, attributes, metadata
  Without state: Can't update or destroy existing resources
  
  Default: terraform.tfstate (local file) — NOT for teams!

Remote State (required for teams):
  
  # terraform/backend.tf:
  terraform {
    backend "s3" {
      bucket         = "my-company-tfstate"
      key            = "production/terraform.tfstate"
      region         = "us-east-1"
      dynamodb_table = "terraform-locks"    # For state locking
      encrypt        = true                 # Encrypt at rest
    }
  }
  
  DynamoDB for state locking:
  - Prevents two people applying simultaneously (race condition)
  - Lock: Terraform writes a lock record to DynamoDB before apply
  - Unlock: Removes lock when done

State Files contain SENSITIVE data:
  - Resource IDs
  - Initial passwords (RDS master password)
  - Private IPs
  
  Always encrypt state backend. Never commit tfstate to Git.

State Commands:
  terraform state list                    # List all resources in state
  terraform state show aws_instance.web  # Show specific resource
  terraform state pull                   # Download remote state
  terraform state push                   # Upload state
  terraform import aws_s3_bucket.data my-bucket-name  # Import existing
  terraform state mv SOURCE DEST         # Move/rename in state
  terraform state rm aws_instance.old    # Remove from state (doesn't delete)

8. IaC SECURITY CONSIDERATIONS
================================================================================

Secrets in IaC:
  ✗ Never hardcode credentials in .tf files or YAML
  ✗ Never commit secrets to Git
  
  Approaches:
  1. Environment variables:
     export AWS_ACCESS_KEY_ID=...
     export TF_VAR_db_password=...
  
  2. Vault Provider:
     data "vault_generic_secret" "db_password" {
       path = "secret/production/db"
     }
  
  3. AWS Secrets Manager / Parameter Store:
     data "aws_secretsmanager_secret_version" "db" {
       secret_id = "prod/db/password"
     }
  
  4. OIDC/IRSA — No static credentials at all:
     CI pipeline assumes IAM role via OIDC (no keys stored)

Static Analysis Tools:
  tfsec:    Terraform security scanner (misconfigured S3, open security groups)
  checkov:  Multi-IaC scanner (Terraform, CloudFormation, K8s, Dockerfile)
  terrascan: Policy-as-code for IaC
  TFLint:   Terraform linter (catches errors before apply)
  
  # Run checkov:
  checkov -d infrastructure/ --framework terraform
  
  Common findings:
  - S3 bucket public access not blocked
  - Security groups open to 0.0.0.0/0 on port 22
  - RDS not encrypted
  - CloudTrail not enabled
  - MFA delete not enabled on S3

Policy as Code:
  OPA (Open Policy Agent): Define rules that infrastructure must follow.
  Conftest: Test IaC files against OPA policies.
  Sentinel: HashiCorp's policy framework (Terraform Enterprise).
  
  # Example OPA policy: Require tags on all resources:
  deny[msg] {
    resource := input.resource.aws_instance[_]
    not resource.config.tags.Environment
    msg := "All EC2 instances must have Environment tag"
  }

9. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Infrastructure as Code and why is it important?
A: Infrastructure as Code (IaC) is managing infrastructure through code files
   instead of manual processes. You write code to describe what infrastructure
   you want; the tool creates/modifies it to match.
   
   Why it matters:
   
   1. Reproducibility: Can recreate exact infrastructure in minutes.
      Disaster recovery: terraform apply brings everything back.
   
   2. Consistency: Dev, staging, production use identical code.
      Eliminates "but it works in staging" issues.
   
   3. Version control: Infrastructure changes are Git commits.
      git log shows WHO changed WHAT and WHEN.
      git revert can undo infrastructure changes.
   
   4. Code review: Infrastructure changes go through PR → review → merge.
      Catches mistakes before they reach production.
   
   5. Automation: IaC fits naturally into CI/CD.
      Push code → pipeline validates, plans, applies.
      No manual steps.
   
   6. Documentation: The code IS the documentation.
      No stale runbooks.
   
   Real example impact:
   Without IaC: Server corrupted → 3 days rebuilding manually from runbooks.
   With IaC: terraform apply → 10 minutes → identical environment back.

Q2: Explain the difference between Terraform and Ansible.
A: They solve different problems and are often used together:
   
   Terraform (Provisioning):
   - Creates/manages CLOUD RESOURCES (EC2, VPC, RDS, S3, IAM...)
   - Stateful: maintains a state file mapping code to real resources
   - Declarative: describe desired infrastructure, Terraform figures out steps
   - Idempotent: running plan+apply multiple times only makes needed changes
   - Best for: Initial infrastructure setup, cloud resource lifecycle
   
   Ansible (Configuration Management):
   - Configures existing SERVERS (installs packages, configures files, starts services)
   - Stateless: no state file, checks current server state each run
   - Agentless: connects via SSH, no agent needed on servers
   - Best for: Server hardening, application deployment, OS configuration
   
   Typical workflow together:
   1. Terraform creates EC2 instances (know the IP, write to inventory)
   2. Ansible connects to instances, installs nginx, configures app, deploys code
   
   Modern shift:
   With containers/Kubernetes, Ansible is less needed for server config.
   Instead: Docker builds the image (config baked in), Kubernetes runs it.
   Terraform + Kubernetes often replaces the Terraform + Ansible pattern.

Q3: What is Terraform state and why is remote state important?
A: Terraform state is a file that maps your Terraform code to real cloud resources.
   
   Without state, Terraform can't:
   - Know if a resource already exists (would try to create duplicate)
   - Know which real resource to update when code changes
   - Know which real resource to delete when you remove code
   
   State file contains: resource IDs (instance IDs, ARNs), attributes,
   dependencies between resources, metadata.
   
   Local state: terraform.tfstate file on your machine.
   Works alone, NOT for teams.
   
   Problems with local state in teams:
   - Two engineers apply simultaneously → state conflict, resource duplication
   - State file not shared → colleague's apply overwrites your resources
   - Lost laptop → lost state → can't manage existing resources
   
   Remote state solution:
   Store in S3 (or GCS, Azure Storage, Terraform Cloud).
   
   terraform {
     backend "s3" {
       bucket         = "company-tfstate"
       key            = "prod/terraform.tfstate"
       region         = "us-east-1"
       dynamodb_table = "terraform-locks"  # Critical: state locking
       encrypt        = true
     }
   }
   
   DynamoDB locking: Only one person can apply at a time.
   Before apply: Terraform writes lock to DynamoDB.
   If locked: Others see "Error acquiring state lock" and must wait.
   
   Security: State contains secrets (DB passwords, etc.). Always encrypt.
   Never commit tfstate to Git.

Q4: What is "configuration drift" and how does IaC prevent it?
A: Configuration drift is when actual infrastructure diverges from the desired
   state defined in code, typically because someone made manual changes.
   
   How drift happens:
   - Engineer SSHes into production server, manually changes nginx config
   - Someone clicks "Add inbound rule" in AWS Console Security Group
   - Quick fix applied directly in cloud console during incident
   
   Effects of drift:
   - Staging and production behave differently (inconsistency)
   - The next terraform apply might revert manual changes (surprise!)
   - No Git history for manual changes (lost audit trail)
   - "Why does this work here but not there?" — hard to debug
   
   How IaC prevents drift:
   1. All changes through code: Team policy "never touch console"
   2. Terraform plan in CI: detects drift (shows resources changed outside TF)
      "aws_security_group.web: 1 to change" when you didn't change code
   3. Drift detection: terraform plan → non-empty diff means drift exists
   4. Immutable infrastructure: servers replaced, not modified
      (deploy new AMI, terminate old) — can't drift if you can't SSH in
   5. Automated compliance: tfsec/checkov in CI catches manual changes
      if someone changes the code to allow them

Q5: How do you handle secrets in Infrastructure as Code?
A: Secrets in IaC is a common security challenge with multiple solutions:
   
   The problem:
   Terraform needs credentials (DB passwords, API keys) to create resources.
   But those secrets can't be in Git.
   
   Solutions:
   
   1. Environment variables (common, simple):
      export TF_VAR_db_password=$(vault read -field=password secret/db)
      Terraform reads TF_VAR_* variables.
      CI/CD injects these from vault or secret manager.
   
   2. Vault provider (recommended for enterprises):
      data "vault_generic_secret" "db" {
        path = "secret/production/database"
      }
      resource "aws_db_instance" "main" {
        password = data.vault_generic_secret.db.data["password"]
      }
      Vault generates dynamic credentials; Terraform reads them.
   
   3. AWS Secrets Manager / SSM Parameter Store:
      data "aws_ssm_parameter" "db_password" {
        name = "/production/db/password"
        with_decryption = true
      }
      Store secrets in AWS, reference from Terraform.
   
   4. OIDC (best: no static credentials):
      CI pipeline assumes IAM role via GitHub OIDC federation.
      No AWS_ACCESS_KEY_ID/SECRET stored anywhere.
      Terraform uses the assumed role credentials.
   
   5. State file security:
      Even if code has no secrets, state file often contains them
      (initial passwords generated by Terraform).
      Always encrypt the remote backend.
      Never store tfstate in Git.
