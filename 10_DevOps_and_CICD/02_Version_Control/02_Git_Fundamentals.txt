1. GIT DATA MODEL
================================================================================

Git stores data as a directed acyclic graph (DAG) of objects.
Unlike other VCS that store DIFFS, Git stores SNAPSHOTS.

Git Object Types:
  1. BLOB: Stores file contents (not the filename, just content)
  2. TREE: Stores a directory listing (filenames + blobs/subtrees + permissions)
  3. COMMIT: Points to a tree, parent commit(s), author, message
  4. TAG: Annotated tag with tagger info, points to a commit

Example Object Graph:
  commit abc123
    └── tree def456
          ├── blob aaa111  (README.md contents)
          ├── blob bbb222  (main.py contents)
          └── tree ccc333  (src/ directory)
                ├── blob ddd444  (src/utils.py)
                └── blob eee555  (src/config.py)

Key Insight:
  - Git NEVER modifies objects — they are immutable, content-addressed
  - The SHA-1 hash IS the content (if content changes, hash changes)
  - This is what makes Git's history tamper-evident

Content Addressable Storage:
  echo "Hello, World" | git hash-object --stdin
  → 8ab686eafeb1f44702738c8b0f24f2567c36da6d
  
  The same content ALWAYS produces the same hash.
  Different content ALWAYS produces different hashes (with negligible collision probability).

Three Trees of Git:
  1. HEAD: The last commit snapshot (what the commit points to)
  2. Index (Staging Area): The proposed next commit snapshot
  3. Working Directory: Current files on disk (sandbox for editing)

State Transitions:
  Untracked → [git add] → Staged → [git commit] → Committed
  Committed → [edit file] → Modified → [git add] → Staged

2. ESSENTIAL GIT COMMANDS
================================================================================

INITIALIZATION
--------------
git init                         # Initialize new local repo
git init --bare                  # Initialize bare repo (for servers, no working tree)
git clone <url>                  # Clone remote repo locally
git clone <url> <directory>      # Clone into specific directory
git clone --depth 1 <url>        # Shallow clone (only latest snapshot, no history)
git clone --branch <branch> <url> # Clone specific branch

CONFIGURATION
-------------
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "vim"         # Set default editor
git config --global merge.tool vimdiff        # Set merge tool
git config --list                             # Show all config
git config --global alias.st status          # Create alias: git st = git status
git config --global alias.lg "log --oneline --graph --all"

STAGING
-------
git add <file>                   # Stage specific file
git add .                        # Stage all changes in current directory
git add -A                       # Stage all changes (including deletions)
git add -p                       # Interactive staging (choose hunks)
git add -i                       # Interactive staging menu
git rm <file>                    # Remove file from tracking AND disk
git rm --cached <file>           # Remove file from tracking but keep on disk
git mv <old> <new>               # Rename/move tracked file

STATUS AND INSPECTION
---------------------
git status                       # Show status of working tree and staging area
git status -s                    # Short format: M = modified, A = added, ?? = untracked
git diff                         # Show unstaged changes
git diff --staged                # Show staged changes (what will be committed)
git diff HEAD                    # Show all uncommitted changes
git diff <branch1>..<branch2>    # Compare branches
git diff --stat                  # Summary of changes (files changed, insertions, deletions)

COMMITTING
----------
git commit -m "message"          # Commit staged changes with message
git commit -am "message"         # Stage all tracked files and commit
git commit --amend               # Modify last commit (message or staged content)
git commit --amend --no-edit     # Amend without changing message
git commit -S -m "message"       # Sign commit with GPG key

HISTORY
-------
git log                          # Show commit history
git log --oneline                # One line per commit
git log --oneline --graph --all  # ASCII graph of all branches
git log --author="Name"          # Filter by author
git log --since="2024-01-01"     # Filter by date
git log --grep="bug fix"         # Filter by commit message
git log -p                       # Show patch (diff) for each commit
git log --stat                   # Show file stats per commit
git log <file>                   # History of specific file
git show <commit>                # Show a specific commit
git show <commit>:<file>         # Show file content at a specific commit
git blame <file>                 # Show who changed each line and when
git shortlog -sn                 # Summary of commits by author

BRANCHING
---------
git branch                       # List local branches (* = current)
git branch -a                    # List all branches (local + remote)
git branch -r                    # List remote branches
git branch <name>                # Create new branch (doesn't switch)
git checkout <branch>            # Switch to branch (old style)
git switch <branch>              # Switch to branch (new style, Git 2.23+)
git checkout -b <name>           # Create and switch to new branch (old style)
git switch -c <name>             # Create and switch to new branch (new style)
git branch -d <name>             # Delete branch (safe, checks merge status)
git branch -D <name>             # Force delete branch
git branch -m <old> <new>        # Rename branch

MERGING
-------
git merge <branch>               # Merge branch into current branch
git merge --no-ff <branch>       # Always create merge commit (no fast-forward)
git merge --ff-only <branch>     # Only merge if fast-forward possible
git merge --squash <branch>      # Squash all commits into one before merging
git merge --abort                # Abort in-progress merge

REBASING
--------
git rebase <branch>              # Rebase current branch onto <branch>
git rebase -i HEAD~3             # Interactive rebase of last 3 commits
git rebase --continue            # Continue after resolving conflicts
git rebase --abort               # Abort rebase
git rebase --skip                # Skip current commit during rebase

Interactive Rebase Commands (in the editor):
  pick    # Use commit as-is
  reword  # Use commit, edit message
  edit    # Use commit, pause to amend
  squash  # Combine with previous commit
  fixup   # Like squash, discard this commit's message
  drop    # Remove commit entirely

STASHING
--------
git stash                        # Stash current changes
git stash push -m "description"  # Stash with description
git stash list                   # List all stashes
git stash pop                    # Apply most recent stash and remove it
git stash apply stash@{2}        # Apply specific stash without removing
git stash drop stash@{0}         # Delete specific stash
git stash clear                  # Delete all stashes
git stash show -p                # Show stash diff
git stash branch <name>          # Create branch from stash

TAGGING
-------
git tag                          # List all tags
git tag v1.0.0                   # Lightweight tag at current commit
git tag -a v1.0.0 -m "message"   # Annotated tag (recommended for releases)
git tag v1.0.0 <commit>          # Tag specific commit
git push origin v1.0.0           # Push specific tag
git push origin --tags           # Push all tags
git tag -d v1.0.0                # Delete local tag
git push origin :refs/tags/v1.0.0 # Delete remote tag

3. GIT CONFIGURATION
================================================================================

Config Levels (highest priority first):
  1. Local: .git/config (per-repo settings)
  2. Global: ~/.gitconfig (per-user settings)
  3. System: /etc/gitconfig (system-wide)

Useful Global Config:
  # Rebase instead of merge on pull
  git config --global pull.rebase true
  
  # Auto-stash before rebase
  git config --global rebase.autoStash true
  
  # Show branch in status
  git config --global status.showUntrackedFiles all
  
  # Push current branch by default
  git config --global push.default current
  
  # Colorful output
  git config --global color.ui auto
  
  # Set main as default branch name
  git config --global init.defaultBranch main

.gitignore (ignore patterns):
  # Directories
  node_modules/
  .venv/
  target/
  dist/
  build/
  
  # Files with specific extensions
  *.log
  *.class
  *.pyc
  *.jar
  
  # Specific files
  .env
  .env.local
  .DS_Store
  Thumbs.db
  
  # IDE files
  .idea/
  .vscode/
  *.iml

.gitattributes (file handling):
  *.sh text eol=lf              # Force Unix line endings for shell scripts
  *.bat text eol=crlf           # Force Windows line endings for batch files
  *.png binary                  # Treat as binary (no line-ending conversion)
  *.jpg binary
  *.pdf binary

4. WORKING WITH REMOTES
================================================================================

Remote Management:
  git remote                    # List remotes
  git remote -v                 # List remotes with URLs
  git remote add origin <url>   # Add remote named 'origin'
  git remote set-url origin <url> # Change remote URL
  git remote remove <name>      # Remove remote
  git remote rename old new     # Rename remote

Fetching and Pulling:
  git fetch origin              # Fetch all remote branches
  git fetch origin <branch>     # Fetch specific branch
  git fetch --prune             # Fetch and delete local refs to deleted remote branches
  git pull                      # Fetch + merge current branch
  git pull --rebase             # Fetch + rebase (cleaner history)
  git pull origin <branch>      # Pull specific branch

Pushing:
  git push origin <branch>      # Push branch to remote
  git push -u origin <branch>   # Push and set upstream tracking
  git push --force-with-lease   # Force push SAFELY (checks for new remote commits)
  git push --force              # Force push DANGEROUSLY (overwrites without checking)
  git push origin --delete <branch> # Delete remote branch
  git push origin :<branch>     # Delete remote branch (alternative syntax)

IMPORTANT: Force Push Rules:
  - NEVER force push to main/master/develop (shared protected branches)
  - Force push only on your own feature branches
  - Prefer --force-with-lease over --force
  - --force-with-lease fails if someone else pushed to the branch (safety)

Upstream Tracking:
  git branch -u origin/main     # Set upstream for current branch
  git branch -vv                # Show upstream tracking for each branch

5. UNDOING CHANGES
================================================================================

Scenario Matrix:

UNDO UNSTAGED CHANGES:
  git restore <file>            # Discard changes in working directory (Git 2.23+)
  git checkout -- <file>        # Same as above (old syntax)
  git clean -fd                 # Remove untracked files and directories

UNDO STAGED CHANGES (keep in working directory):
  git restore --staged <file>   # Unstage specific file
  git reset HEAD <file>         # Same as above (old syntax)
  git reset HEAD                # Unstage everything

UNDO LAST COMMIT (keep changes in staging):
  git reset --soft HEAD~1

UNDO LAST COMMIT (keep changes, unstage):
  git reset --mixed HEAD~1      # Default behavior of git reset HEAD~1

UNDO LAST COMMIT (discard changes completely):
  git reset --hard HEAD~1       # DANGER: Permanent data loss

AMEND LAST COMMIT:
  git commit --amend -m "new message"   # Change commit message
  git add <file> && git commit --amend  # Add changes to last commit

CREATE REVERTING COMMIT (safe for shared branches):
  git revert HEAD               # Creates new commit undoing last commit
  git revert abc123             # Revert specific commit
  git revert HEAD~3..HEAD       # Revert last 3 commits

RECOVER DELETED COMMITS (using reflog):
  git reflog                    # Show history of HEAD movements
  git checkout abc123           # Detach HEAD at old commit
  git branch recovery-branch    # Create branch to save it
  # Or: git reset --hard abc123 # Reset current branch to recovered commit

Git Reflog:
  - Git's "safety net" — records all movements of HEAD
  - Commits deleted with reset --hard are NOT immediately gone
  - Reflog retains them for 30-90 days (configurable)
  - git reflog show all HEAD movements with their hashes

6. GIT INTERNALS
================================================================================

Object Storage (.git/objects/):
  All Git objects stored in .git/objects/ as compressed files.
  File path: first 2 chars of SHA = directory, rest = filename.
  
  SHA abc1234... → .git/objects/ab/c1234...
  
  Object types: blob, tree, commit, tag

The .git Directory Structure:
  .git/
  ├── HEAD              # Current branch or commit reference
  ├── config            # Local repository config
  ├── index             # Staging area (binary)
  ├── objects/          # All git objects (blobs, trees, commits, tags)
  │   ├── info/
  │   └── pack/         # Packfiles (compressed object storage)
  ├── refs/
  │   ├── heads/        # Local branches (text files containing SHA)
  │   │   ├── main      # Contains commit SHA that main points to
  │   │   └── feature   # Contains commit SHA that feature points to
  │   ├── remotes/      # Remote tracking references
  │   │   └── origin/
  │   │       └── main
  │   └── tags/         # Tag references
  ├── logs/             # Reflog data
  ├── COMMIT_EDITMSG    # Last commit message
  ├── MERGE_HEAD        # During merge: the commit being merged
  ├── ORIG_HEAD         # Before merge/rebase: previous HEAD
  └── hooks/            # Pre/post-commit hooks (executable scripts)

Low-Level (Plumbing) Commands:
  git cat-file -t <sha>         # Show object type
  git cat-file -p <sha>         # Show object content
  git ls-tree HEAD              # List tree contents of HEAD
  git ls-files                  # List tracked files in index
  git hash-object <file>        # Compute SHA of file
  git write-tree                # Write index as tree object
  git commit-tree               # Create commit from tree

Fast-Forward vs True Merge:
  Fast-Forward: Target branch is directly ahead in the ancestor chain.
  Git just moves the branch pointer forward — no merge commit needed.
  
  Before: main → A → B
          feature →    B → C → D   (feature is ahead of main)
  
  After fast-forward merge:
          main → A → B → C → D   (main just moved to D)

  True Merge (3-way merge): Branches have diverged.
  Git finds the common ancestor, computes diffs, creates merge commit.
  
  Before: main → A → B → E
          feature →  B → C → D
  
  After merge: main → A → B → E → M (merge commit, M has parents E and D)
                                  D ←┘

7. ADVANCED GIT OPERATIONS
================================================================================

Cherry-Pick:
  Apply specific commit(s) from one branch onto another.
  
  git cherry-pick <commit-sha>      # Apply one commit
  git cherry-pick abc123..def456    # Apply range of commits
  git cherry-pick -n <commit>       # Stage but don't commit (--no-commit)
  
  Use case: Production hotfix → apply to both main and release branch.
  Anti-pattern: Cherry-picking too often (sign of bad branching strategy).

Bisect (Binary Search for Bugs):
  Find which commit introduced a bug using binary search.
  
  git bisect start
  git bisect bad                    # Current commit is bad
  git bisect good v1.2.0            # v1.2.0 was known good
  # Git checks out midpoint commit
  # Test whether bug exists, then:
  git bisect good                   # Or: git bisect bad
  # Repeat until Git identifies the exact commit
  git bisect reset                  # Return to original state
  
  # Automated bisect with test script:
  git bisect run ./run_tests.sh     # Run script to auto-determine good/bad

Worktree:
  Check out multiple branches simultaneously in different directories.
  
  git worktree add ../hotfix hotfix-branch  # Create worktree for hotfix
  git worktree list
  git worktree remove ../hotfix
  
  Use case: Need to work on a hotfix while mid-feature without stashing.

Submodules:
  Include another Git repo within your repo.
  
  git submodule add <url> <path>    # Add submodule
  git submodule init                # Initialize submodules
  git submodule update              # Check out submodules at pinned commit
  git submodule update --remote     # Update to latest remote commit
  git clone --recurse-submodules <url>  # Clone with all submodules
  
  Note: Submodules are complex and often cause confusion. Consider
  alternatives: package managers, Git subtree, or monorepo.

Sparse Checkout:
  Check out only specific subdirectories (useful for monorepos).
  
  git sparse-checkout init --cone
  git sparse-checkout set <directory>

Git Subtree (alternative to submodules):
  git subtree add --prefix=lib/logger https://github.com/logger v1.0.0 --squash
  git subtree pull --prefix=lib/logger https://github.com/logger main --squash

Stash Advanced:
  git stash push -u -m "desc" -- <file>   # Stash specific file(s)
  git stash push --keep-index              # Stash unstaged only
  git stash branch <branch>               # Create branch from stash and pop

8. GIT HOOKS
================================================================================

What Are Hooks:
  Scripts that Git executes before/after specific events.
  Stored in .git/hooks/ (not committed to repo by default).
  
  For team-wide hooks: Use frameworks like Husky (Node.js), pre-commit (Python),
  or symlink to a committed hooks directory.

Client-Side Hooks:
  pre-commit:       Runs before commit message editor. Use for linting/tests.
  prepare-commit-msg: Before commit message editor, after default message set.
  commit-msg:       Validate commit message format.
  post-commit:      After commit. Use for notifications.
  pre-push:         Before push to remote. Use for integration tests.
  post-checkout:    After git checkout. Use for setup scripts.
  post-merge:       After merge. Use for `npm install` after package.json changes.
  pre-rebase:       Before rebase. Use to prevent rebase of shared branches.

Server-Side Hooks:
  pre-receive:      Before accepting any push. Enforce policies.
  post-receive:     After push accepted. Trigger CI/CD pipelines.
  update:           Like pre-receive but for each branch being updated.

Example pre-commit Hook:
  #!/bin/bash
  # Run linting before commit
  npm run lint
  EXIT_CODE=$?
  if [ $EXIT_CODE -ne 0 ]; then
    echo "Linting failed. Fix errors before committing."
    exit 1
  fi
  
  # Check for secrets
  detect-secrets-hook --baseline .secrets.baseline
  EXIT_CODE=$?
  if [ $EXIT_CODE -ne 0 ]; then
    echo "Potential secrets detected. Remove them before committing."
    exit 1
  fi

Example commit-msg Hook (enforce Conventional Commits):
  #!/bin/bash
  MSG=$(cat $1)
  PATTERN="^(feat|fix|docs|style|refactor|test|chore|perf|ci)(\(.+\))?: .{1,72}"
  
  if ! echo "$MSG" | grep -qE "$PATTERN"; then
    echo "ERROR: Commit message doesn't follow Conventional Commits format"
    echo "Example: feat(auth): add OAuth2 login"
    exit 1
  fi

Husky (Node.js projects):
  npm install --save-dev husky
  npx husky install
  npx husky add .husky/pre-commit "npm test"
  npx husky add .husky/commit-msg "npx commitlint --edit $1"

pre-commit Framework (Python projects):
  # .pre-commit-config.yaml
  repos:
    - repo: https://github.com/pre-commit/pre-commit-hooks
      rev: v4.4.0
      hooks:
        - id: trailing-whitespace
        - id: end-of-file-fixer
        - id: check-yaml
        - id: detect-private-key
    - repo: https://github.com/psf/black
      rev: 23.3.0
      hooks:
        - id: black

9. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between `git reset` and `git revert`?
A: Both undo changes, but they work differently:
   
   git reset moves the branch pointer backward, optionally unstaging or
   discarding changes. It rewrites history. --soft keeps changes staged,
   --mixed keeps in working directory, --hard discards completely.
   Use reset only on commits that haven't been pushed (private history).
   
   git revert creates a new commit that reverses the changes of a specified
   commit. History is preserved. Safe for shared branches because it doesn't
   rewrite history.
   
   Rule: Reset for local/private branches. Revert for shared branches.

Q2: Explain Git stash and when you would use it.
A: git stash saves your current uncommitted changes (both staged and unstaged)
   to a stack and reverts your working directory to HEAD, letting you switch
   context cleanly.
   
   Use cases:
   - Need to urgently switch branches to fix a hotfix mid-feature work
   - Pull latest changes but have uncommitted local work that would conflict
   - Experiment with changes but need a clean state to run tests
   
   Example: Working on feature-123, PO asks to immediately check a bug.
   git stash → switch to main → fix bug → switch back → git stash pop.

Q3: What is the difference between `git pull` and `git pull --rebase`?
A: git pull does fetch + merge, creating a merge commit if histories have
   diverged. This creates a "noisy" history with merge commits.
   
   git pull --rebase does fetch + rebase, replaying your local commits on top
   of the fetched commits. This creates a linear history without merge commits.
   It's preferable for keeping clean commit history on feature branches.
   
   Many teams set `git config --global pull.rebase true` as default.

Q4: How does Git handle binary files, and what is Git LFS?
A: Git stores file contents as blobs. Binary files (images, videos, binaries)
   are stored fully with every change — no delta compression is possible.
   This causes repository size to balloon.
   
   Git LFS (Large File Storage) solves this by storing binary files in a
   separate LFS server while Git only stores a small "pointer" file.
   When you checkout, LFS downloads the actual file on demand.
   
   Setup: git lfs track "*.psd" then git add .gitattributes
   Common use: Game assets, design files, ML models, compiled binaries.

Q5: What is `git bisect` and how do you use it?
A: git bisect is a binary search tool for finding which commit introduced a bug.
   
   Steps:
   1. git bisect start
   2. git bisect bad (mark current commit as broken)
   3. git bisect good v1.2.0 (mark a known-good commit)
   4. Git checks out the midpoint. Test it.
   5. git bisect good or git bisect bad based on test result
   6. Repeat until Git pinpoints the exact commit
   7. git bisect reset to return to HEAD
   
   For large codebases, bisect can find the breaking commit in O(log n) steps.
   With a test script: git bisect run ./test.sh (fully automated).

Q6: Explain what a detached HEAD state is in Git.
A: Normally, HEAD points to a branch, which points to a commit. In detached
   HEAD state, HEAD points directly to a commit (not a branch).
   
   This happens when you: git checkout <commit-sha>, git checkout <tag>,
   or git checkout origin/main directly.
   
   Problem: Any commits made in detached HEAD state are on no branch. When
   you switch branches, those commits become unreachable and eventually GC'd.
   
   Solution: If you want to keep work done in detached HEAD state, create a
   branch: git checkout -b <new-branch-name> before switching away.

10. QUICK REFERENCE CHEAT SHEET
================================================================================

Git Data Model:
  blob (file contents) → tree (directory) → commit (snapshot)
  All objects: content-addressed SHA-1 hashes

Key Areas:
  Working Dir → [add] → Staging (Index) → [commit] → Local Repo → [push] → Remote

Essential Commands:
  git init / git clone                   # Start
  git add / git commit / git push        # Save changes
  git status / git log / git diff        # Inspect
  git branch / git checkout / git switch # Navigate
  git merge / git rebase                 # Integrate
  git fetch / git pull                   # Download
  git stash / git stash pop              # Temporarily save

Undo Commands:
  restore                # Discard working dir changes
  reset --soft           # Undo commit, keep staged
  reset --mixed          # Undo commit, unstage
  reset --hard           # Undo commit, discard (DANGER)
  revert                 # New commit undoing old (safe for shared)
  reflog                 # Recovery option after hard reset

Advanced:
  cherry-pick: Copy specific commits to current branch
  bisect: Binary search for bug-introducing commit
  rebase -i: Squash, reorder, edit, drop commits interactively

Hooks (in .git/hooks/):
  pre-commit: Run linting/tests before commit
  commit-msg: Validate message format
  pre-push: Run integration tests before push
  post-receive: Trigger CI/CD on server

Force Push:
  --force-with-lease: Safe (fails if remote has new commits)
  --force: Dangerous (overwrites anything)
  NEVER force push to shared branches (main/develop)
