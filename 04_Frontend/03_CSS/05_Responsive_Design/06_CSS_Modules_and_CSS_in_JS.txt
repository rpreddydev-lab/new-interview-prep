1. THE PROBLEM — CSS GLOBAL SCOPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CSS has global scope by design. Every class applies everywhere. In large
applications with many components, this causes:

  • Name collisions (.button in component A vs .button in component B)
  • Unintended style leakage (styles meant for one component affect others)
  • Fear to refactor (deleting a class might break something unknown)
  • Hard to determine which CSS belongs to which component
  • Dead CSS accumulates (can't safely remove old styles)

Solutions:
  1. Naming conventions (BEM, SMACSS) — manual discipline, still global
  2. CSS Modules — scoped by filename at build time
  3. CSS-in-JS (styled-components, Emotion) — scoped dynamically at runtime
  4. Shadow DOM / Web Components — browser-native scoping

2. CSS MODULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CSS Modules scope CSS class names locally by automatically transforming them
into unique identifiers at build time.

  File: Button.module.css
    .button { background: blue; color: white; padding: 8px 16px; }
    .primary { background: #007bff; }
    .danger  { background: #dc3545; }

  File: Button.jsx (React)
    import styles from './Button.module.css';

    function Button({ variant }) {
      return (
        <button className={`${styles.button} ${styles[variant]}`}>
          Click
        </button>
      );
    }

  What happens at build time:
    .button   → .Button_button__xR7Kp  (unique hash)
    .primary  → .Button_primary__2mNkL

  Benefits:
    ✅ Zero name collisions — classes are unique per file
    ✅ Dead code elimination — bundler knows which classes are used
    ✅ Type-safe class names (with TypeScript)
    ✅ Still plain CSS — no JS overhead, browser parses normal CSS
    ✅ Works with any framework (React, Vue, Svelte, Vite, webpack)

  Composing styles:
    .base { color: black; font-size: 1rem; }
    .heading { composes: base; font-size: 2rem; font-weight: bold; }
    /* composes applies multiple classes */

  Global escape hatch:
    :global(.active) { color: red; }  /* not scoped */
    :local(.title)   { color: blue; } /* explicitly local */

3. STYLED-COMPONENTS (CSS-in-JS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

styled-components lets you write CSS directly in JavaScript using template
literals. Styles are scoped to components automatically.

  import styled from 'styled-components';

  const Button = styled.button`
    background: ${props => props.primary ? '#007bff' : 'white'};
    color: ${props => props.primary ? 'white' : '#007bff'};
    padding: 8px 16px;
    border-radius: 4px;
    border: 2px solid #007bff;
    cursor: pointer;

    &:hover {
      opacity: 0.9;
      transform: scale(1.02);
    }
  `;

  // Usage
  <Button primary>Primary Button</Button>
  <Button>Secondary Button</Button>

  Extending styles:
    const DangerButton = styled(Button)`
      background: #dc3545;
      border-color: #dc3545;
    `;

  Theming:
    import { ThemeProvider } from 'styled-components';

    const theme = { primary: '#007bff', secondary: '#6c757d' };

    // Wrap app in ThemeProvider
    <ThemeProvider theme={theme}>
      <App />
    </ThemeProvider>

    // Use theme in styled component
    const Button = styled.button`
      background: ${props => props.theme.primary};
    `;

4. EMOTION (CSS-in-JS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Emotion is similar to styled-components but lighter and more flexible.
  Two approaches:

  1. css prop (requires Babel/TS config):
     import { css } from '@emotion/react';

     const style = css`
       color: red;
       font-size: 24px;
     `;
     <div css={style}>Hello</div>

  2. styled (same API as styled-components):
     import styled from '@emotion/styled';
     const Box = styled.div`color: red;`;

  MUI (Material UI) uses Emotion internally as its CSS engine.

5. CSS-IN-JS: TRADEOFFS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Advantages:
    ✅ Fully scoped — zero name collisions
    ✅ Dynamic styles based on props/state — no extra class toggling
    ✅ Co-location — styles live next to component logic
    ✅ Easy theming via ThemeProvider
    ✅ Dead styles eliminated automatically
    ✅ TypeScript support for props

  Disadvantages:
    ❌ Runtime cost — styles are generated/injected via JS at runtime
    ❌ Critical CSS — harder to extract for SSR without configuration
    ❌ Bundle size — adds KB to JavaScript bundle
    ❌ No CSS caching — styles reload with JS
    ❌ Server-side rendering requires extra setup
    ❌ Vendor lock-in (React-only or framework-specific)

6. ZERO-RUNTIME CSS-IN-JS (Modern)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Modern CSS-in-JS solutions extract CSS at BUILD TIME — zero runtime cost:

  Linaria — compile-time CSS extraction:
    import { css, styled } from '@linaria/react';

    const title = css`font-size: 2rem; color: blue;`;
    // Compiles to a static CSS file — no JS runtime

  vanilla-extract — type-safe CSS at build time:
    // styles.css.ts
    import { style } from '@vanilla-extract/css';

    export const button = style({
      background: 'blue',
      color: 'white',
      padding: '8px 16px',
    });

    // Component
    import { button } from './styles.css';
    <button className={button}>Click</button>

  Panda CSS — used by Chakra UI v3:
    import { css } from '../styled-system/css';
    const style = css({ color: 'blue', fontSize: '2xl' });

8. KEY INTERVIEW QUESTIONS — CSS MODULES AND CSS-IN-JS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What problem do CSS Modules solve?
A: CSS Modules solve the global scope problem in CSS. All class names are
   transformed into unique identifiers at build time, preventing name collisions
   between components. They maintain CSS syntax (no JS overhead) while ensuring
   isolation.

Q: How do CSS Modules work under the hood?
A: The build tool (webpack, Vite, etc.) transforms class names in .module.css
   files into unique hashed identifiers. The JS module exports an object mapping
   original names to hashed names. When you use `styles.button`, you get the
   unique class name that only applies to that component.

Q: What is the main downside of runtime CSS-in-JS like styled-components?
A: Runtime overhead — styles are generated as JavaScript strings and injected
   into a <style> tag at runtime. This blocks rendering, adds to bundle size,
   and makes SSR more complex. In React 18+, runtime CSS-in-JS also struggles
   with concurrent rendering. Zero-runtime alternatives (vanilla-extract,
   Linaria) extract CSS at build time.

Q: When would you choose CSS Modules over CSS-in-JS?
A: CSS Modules when: you want zero runtime overhead, simple SSR, and you prefer
   keeping CSS in separate files. CSS-in-JS when: you need truly dynamic styles
   based on component props/state, co-location is important to the team, or
   theming via ThemeProvider is needed.

Q: What is the difference between styled-components and vanilla-extract?
A: Both scope CSS to components, but styled-components generates styles at
   runtime in the browser (JS injection). vanilla-extract generates static CSS
   files at build time with no JavaScript runtime — same developer experience
   but with better performance characteristics.
