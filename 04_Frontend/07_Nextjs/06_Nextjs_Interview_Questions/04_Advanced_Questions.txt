━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does Next.js hydration work?
A: On first load: server renders the full HTML. Browser displays HTML immediately
   (First Contentful Paint). React "hydrates" — it traverses the DOM and attaches
   event listeners to existing HTML elements without re-creating them. After hydration,
   the page becomes fully interactive. Client Components attach event handlers,
   useState/useEffect start running. Server Components don't hydrate — their HTML
   stays static, no client JS for them.

Q: What is a hydration mismatch and how do you debug it?
A: A mismatch occurs when server-rendered HTML differs from React's client render.
   React throws a console warning and regenerates the affected subtree.
   Common causes: Date.now(), Math.random(), window.innerWidth, localStorage reads,
   browser-specific values. Debug: look for "Hydration failed" in console,
   compare server vs client rendered HTML.
   Fix: use useEffect for client-only values, or suppressHydrationWarning={true}
   on specific elements (not recommended broadly).

Q: What is the Next.js compiler and what does it use?
A: Next.js uses SWC (Speedy Web Compiler), a Rust-based JavaScript/TypeScript
   transformer that replaced Babel. SWC is 17x faster than Babel for transforms.
   Handles: TypeScript/TSX compilation, JSX transform, dead code elimination,
   minification, styled-components/emotion transforms. SWC-based Minifier replaces
   Terser (25% faster).

Q: What is Turbopack?
A: Turbopack is Next.js's Rust-based incremental bundler, replacing Webpack.
   Stable in Next.js 15 (for development). Much faster hot module replacement (HMR)
   and initial build times vs Webpack. Uses incremental computation (only re-computes
   what changed). Enable with: next dev --turbopack.
   Note: Production builds with Turbopack still use Webpack in some configurations.

Q: What is code splitting in Next.js and how does it work automatically?
A: Next.js automatically splits JavaScript into separate chunks per route.
   Visiting /about only loads the JS for that page, not the whole app.
   Additionally, dynamic imports (next/dynamic, React.lazy) create async chunks
   that load on demand. Server Components are never included in any client chunks.
   Result: smaller initial bundle, faster page loads.

SECTION 2: AUTHENTICATION PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the main approaches to authentication in Next.js App Router?
A: Three main patterns:
   1. Middleware auth: JWT checked at Edge Middleware, redirect before page renders.
      Fastest, but limited to Edge-compatible JWT verification (jose, not jsonwebtoken).
   2. Layout-level auth: Server Component layout calls auth(), redirects if unauthorized.
      More flexible (can use Prisma), but page starts rendering then redirects.
   3. Combined: Middleware checks JWT validity (fast), layout checks DB for full session.

Q: What are the popular authentication libraries for Next.js?
A: NextAuth.js / Auth.js v5: Full-featured, supports OAuth providers (Google, GitHub),
   credentials, database sessions. Most popular choice.
   Clerk: SaaS auth with prebuilt UI components, organizations, MFA.
   Lucia: Lightweight, highly customizable, not SaaS.
   Supabase: Auth + database + storage bundle.
   Custom JWT: For full control, use jose library for Edge-compatible JWT.

Q: How do you protect API routes in Next.js?
A: In App Router Route Handlers: call auth() or verify JWT at the start of the
   handler, return 401 if invalid. In Pages Router API Routes: use getServerSession()
   or verify the token from cookies/Authorization header.
   Always: (1) check authentication, (2) check authorization (does this user own
   this resource?), (3) validate input with Zod.

Q: What is the recommended pattern for session handling in Next.js?
A: Use HTTP-only cookies for session tokens (inaccessible to JavaScript — prevents XSS).
   Store session data in a database (scalable, can invalidate on logout).
   Alternative: JWT in HTTP-only cookie (stateless, no DB needed, but can't
   invalidate without token refresh mechanism).
   With NextAuth.js: choose database sessions (more secure) or JWT sessions (no DB needed).

SECTION 3: PERFORMANCE OPTIMIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How do you optimize a slow Next.js page?
A: Systematic approach:
   1. Measure first: use Lighthouse, Web Vitals, Next.js analytics
   2. Rendering strategy: is SSR needed or can it be ISR/SSG?
   3. Images: use next/image, correct sizes prop, priority on LCP
   4. Fonts: use next/font to eliminate FOIT/FOUT/CLS from fonts
   5. Bundle analysis: next build --analyze or @next/bundle-analyzer
   6. Code splitting: next/dynamic for heavy Client Components
   7. Parallel data fetching: Promise.all() in Server Components
   8. Server Components: move static sections server-side
   9. Caching: add cache tags, increase revalidate interval
   10. Database: add indexes, limit query fields, use connection pooling

Q: What is next/dynamic and when should you use it?
A: next/dynamic wraps React.lazy() with SSR support. Use for:
   (1) Browser-only libraries (maps, canvas, PDF viewers): { ssr: false }
   (2) Heavy components not needed on initial load (rich text editors, charts)
   (3) Components only shown on interaction (modals, tooltips with complex content)
   next/dynamic({ ssr: false }) fully removes the component from SSR output.

Q: What is the @next/bundle-analyzer and how do you use it?
A: A webpack plugin that generates visual treemaps of your bundle.
   Install: npm install @next/bundle-analyzer
   Configure in next.config.ts:
   const withBundleAnalyzer = require('@next/bundle-analyzer')({ enabled: process.env.ANALYZE === 'true' });
   Run: ANALYZE=true npm run build
   Opens browser with interactive bundle visualization — find large dependencies to lazy-load.

Q: What are Core Web Vitals and how does Next.js help with them?
A: LCP (Largest Contentful Paint): loading speed → next/image priority, ISR/SSG,
   preloading critical resources.
   INP (Interaction to Next Paint, replaced FID): interactivity → minimize client JS,
   use Server Components, lazy load heavy components.
   CLS (Cumulative Layout Shift): visual stability → next/image (reserves space),
   next/font (size-adjust prevents font CLS), explicit dimensions on media.

Q: What does output: 'standalone' do and when would you use it?
A: Creates a .next/standalone directory with everything needed to run the server —
   no node_modules installation required. Only includes files actually needed.
   Use for Docker deployments: COPY .next/standalone + .next/static + public.
   Results in smaller Docker images. Essential for containerized/Kubernetes deploys.

Q: How does ISR work in a self-hosted (non-Vercel) environment?
A: ISR relies on persistent caching. On Vercel it's handled automatically.
   Self-hosted: needs a persistent filesystem or distributed cache (Redis).
   Configure next.config.ts with custom cacheHandler pointing to Redis/filesystem.
   Without proper persistent storage, ISR cache is lost on container restart.

Q: What is the difference between Serverless Functions and Edge Functions on Vercel?
A: Serverless Functions: Node.js runtime, run in specific regions, cold starts
   possible, larger memory, full Node.js/npm ecosystem.
   Edge Functions: V8 isolates, run globally at CDN edge, no cold starts,
   ~128MB memory limit, Web API only (no Node.js built-ins, no Prisma).

Q: How do you handle database connections in serverless environments?
A: Serverless functions are short-lived — new function instances don't reuse DB
   connections. Solutions:
   (1) Prisma + connection pooling via PgBouncer or Prisma Accelerate
   (2) Serverless-first databases: Neon (PostgreSQL), PlanetScale (MySQL),
       Turso (SQLite at edge)
   (3) global._prisma pattern: cache Prisma client in global to reuse within
       warm function instances
   Never create a new connection on every request without pooling.

Q: How do you test Next.js components?
A: Unit/integration tests: Jest + React Testing Library. Test Client Components
   normally. Server Components: use react-server-dom-webpack/server to render,
   or mock and test page behavior with RTL.
   E2E tests: Playwright or Cypress — test full pages against a running Next.js server.
   API tests: Vitest or Jest for Route Handlers (use node-fetch or native fetch).

Q: How do you debug Server Component errors in production?
A: On Vercel: check Function Logs in the dashboard, filter by route.
   In server logs: error.digest is a hash — search logs with this hash.
   Locally: errors show in terminal. Use console.log in Server Components —
   they log to terminal, not the browser console.

Q: What is the error.digest property?
A: When an error occurs in production, Next.js creates a short hash (digest)
   of the error. This hash is shown in the browser error UI and passed to error.tsx.
   Match this hash in server logs to find the full error details (which are hidden
   from the browser for security in production).

Q: How would you debug a performance issue in a Next.js app?
A: 1. Check Vercel Analytics / Lighthouse for Core Web Vitals data
   2. Use React DevTools Profiler to find slow component renders
   3. Check network tab for large JS bundles → use bundle analyzer
   4. Check waterfall of network requests → look for serialized data fetching
   5. Add timing logs to Server Components to identify slow DB queries
   6. Use next build output to check page sizes (warn if over 130kB)
   7. Enable Vercel Speed Insights for real user data
