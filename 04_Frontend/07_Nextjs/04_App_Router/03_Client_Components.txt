1. WHAT ARE CLIENT COMPONENTS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Client Components are React components that:
  - Are marked with the 'use client' directive at the top of the file
  - Run in BOTH server (initial SSR) and client (hydration + updates)
  - Have access to hooks: useState, useEffect, useContext, etc.
  - Have access to browser APIs: window, document, navigator, localStorage
  - Can use event handlers: onClick, onChange, onSubmit, etc.

Important: 'use client' does NOT mean "only in browser".
The component still renders on the server for the initial HTML response.
The directive means "this component uses client-side runtime after hydration."

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. THE 'use client' DIRECTIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  'use client';  // MUST be the very first line, before imports

  import { useState, useEffect } from 'react';

  export function Counter() {
    const [count, setCount] = useState(0);
    return (
      <button onClick={() => setCount(c => c + 1)}>
        Count: {count}
      </button>
    );
  }

Rules for 'use client':
  - Must appear at the VERY TOP of the file (before any imports)
  - It's a string literal directive, not an import
  - Marks a "client boundary" — everything below this directive is client code
  - All modules IMPORTED by this file become client code too (propagation)
  - Can have multiple 'use client' files — each creates its own boundary

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. 'use client' PROPAGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When you mark a file 'use client', ALL its imports are bundled for the client:

  // components/nav.tsx
  'use client';
  import { NavLinks } from './nav-links';  // ← also bundled for client
  import { Logo } from './logo';           // ← also bundled for client
  import { someServerUtil } from '../lib/db'; // ← DANGEROUS: DB code goes to client!

  // Best practice: only import client-safe utilities in client components.
  // Use the 'server-only' package to guard server modules.

This means: minimize what you import in 'use client' files.
Push the 'use client' boundary as far DOWN the component tree as possible.

BAD — entire page is client:
  'use client';
  export default function ProductPage() {
    // 300 lines of server-renderable content + a tiny like button
  }

GOOD — only the button is client:
  // ProductPage.tsx — Server Component
  export default async function ProductPage({ params }) {
    const product = await getProduct(params.id);
    return (
      <div>
        <h1>{product.name}</h1>
        <p>{product.description}</p>
        <LikeButton productId={product.id} /> {/* only this is client */}
      </div>
    );
  }

  // LikeButton.tsx
  'use client';
  export function LikeButton({ productId }) {
    const [liked, setLiked] = useState(false);
    return <button onClick={() => setLiked(!liked)}>♥</button>;
  }

4. CLIENT COMPONENT CAPABILITIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Hooks available in Client Components:
  - useState, useReducer          — state management
  - useEffect, useLayoutEffect    — side effects / DOM manipulation
  - useContext                    — read React context
  - useRef                        — mutable refs / DOM refs
  - useMemo, useCallback          — memoization
  - useTransition, useDeferredValue — concurrent features
  - useFormStatus, useActionState  — form state (React 19)
  - Custom hooks (must be client-side compatible)

  // Comprehensive example
  'use client';
  import { useState, useEffect, useRef } from 'react';

  export function SearchBar({ onSearch }: { onSearch: (q: string) => void }) {
    const [query, setQuery] = useState('');
    const inputRef = useRef<HTMLInputElement>(null);

    useEffect(() => {
      inputRef.current?.focus(); // browser DOM access
    }, []);

    return (
      <input
        ref={inputRef}
        value={query}
        onChange={e => setQuery(e.target.value)}
        onKeyDown={e => e.key === 'Enter' && onSearch(query)}
        placeholder="Search..."
      />
    );
  }

5. SSR OF CLIENT COMPONENTS (VERY IMPORTANT INTERVIEW CONCEPT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Misconception: "Client Components only run in the browser."
Reality: Client Components run on the SERVER too (for the initial HTML).

Lifecycle:
  1. Server renders Client Component → produces initial HTML (SSR)
  2. HTML is sent to browser (fast First Contentful Paint)
  3. React hydrates: re-runs the component, attaches event listeners
  4. Now the component runs interactively in the browser

During server render of a Client Component:
  - useState initial value is used
  - useEffect does NOT run (only after hydration in browser)
  - Event handlers are attached as strings in HTML, activated on hydration

Hydration mismatch example:
  'use client';
  export function Clock() {
    // BAD: server renders one time, client renders different time → MISMATCH
    const [time, setTime] = useState(new Date().toLocaleTimeString());
    return <p>{time}</p>;
  }

  // FIX: Use useEffect to set time only after hydration
  export function Clock() {
    const [time, setTime] = useState('');  // empty during SSR
    useEffect(() => {
      setTime(new Date().toLocaleTimeString()); // only in browser
      const interval = setInterval(() => setTime(new Date().toLocaleTimeString()), 1000);
      return () => clearInterval(interval);
    }, []);
    return <p>{time || '--:--:--'}</p>;  // fallback for SSR
  }

6. CONTEXT PROVIDERS AS CLIENT COMPONENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is the canonical pattern for providing React context in the App Router:
Root Layout (Server) wraps a Client Component provider.

  // providers/theme-provider.tsx
  'use client';
  import { createContext, useContext, useState } from 'react';

  type Theme = 'light' | 'dark';
  const ThemeCtx = createContext<{ theme: Theme; toggle: () => void }>({
    theme: 'light',
    toggle: () => {},
  });

  export function ThemeProvider({ children }: { children: React.ReactNode }) {
    const [theme, setTheme] = useState<Theme>('light');
    return (
      <ThemeCtx.Provider value={{ theme, toggle: () => setTheme(t => t === 'light' ? 'dark' : 'light') }}>
        <div data-theme={theme}>{children}</div>
      </ThemeCtx.Provider>
    );
  }

  export const useTheme = () => useContext(ThemeCtx);

  // app/layout.tsx — ROOT LAYOUT IS A SERVER COMPONENT
  import { ThemeProvider } from '@/providers/theme-provider';

  export default function RootLayout({ children }) {
    return (
      <html>
        <body>
          <ThemeProvider>   {/* Client Component wraps server children */}
            {children}       {/* children can be Server Components */}
          </ThemeProvider>
        </body>
      </html>
    );
  }

7. THIRD-PARTY LIBRARIES COMPATIBILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Many npm packages are built for traditional React (not RSC-aware).
They use hooks, context, or browser APIs → they MUST be in Client Components.

Scenario: Using a date picker library that uses useState internally.

  // If you try this in a Server Component:
  import { DatePicker } from 'some-date-library';  // uses useState internally → ERROR

  // Fix: wrap in a Client Component
  // components/date-picker-wrapper.tsx
  'use client';
  import { DatePicker } from 'some-date-library';
  export { DatePicker };  // re-export as client component

  // Now import from your wrapper in server components:
  import { DatePicker } from '@/components/date-picker-wrapper'; // ✓

Some libraries have started adding 'use client' to their entry points.
Check the library's docs/changelog for RSC support status.

8. SERVER vs CLIENT COMPONENT COMPARISON TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Feature                         | Server Component | Client Component
  ─────────────────────────────── | ──────────────── | ────────────────
  Directive required               | None (default)   | 'use client'
  Runs on server (SSR)             | ✓ Always         | ✓ Initial render
  Runs in browser                  | ✗ Never          | ✓ After hydration
  async component                  | ✓                | ✗ (use useEffect)
  useState / useReducer            | ✗                | ✓
  useEffect / useLayoutEffect      | ✗                | ✓
  useContext                       | ✗*               | ✓
  Event handlers (onClick, etc.)   | ✗                | ✓
  Browser APIs (window, etc.)      | ✗                | ✓ (post-hydration)
  Direct DB / file system access   | ✓                | ✗
  Private env vars (no NEXT_PUBLIC_)| ✓               | ✗
  Import server-only packages      | ✓                | ✗
  Included in JS bundle            | ✗ (no runtime)   | ✓
  Can render Client Components     | ✓                | ✓
  Can render Server Components     | ✓                | Only via children prop

  *useContext: Server Components can't call useContext but can READ context
   values set by a Client Component parent using React.cache and passing as props.

9. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: Does 'use client' mean the component only runs in the browser?
A:  No — this is a common misconception. 'use client' marks a client boundary.
    The component still renders on the server for the initial HTML (SSR), then
    hydrates and becomes interactive in the browser. The directive tells Next.js
    to include this component's code in the JavaScript bundle sent to the client.

Q2: Why should you push the 'use client' boundary as far down as possible?
A:  'use client' propagates to all imports in that file. The more you put at
    the top of the tree, the more code gets bundled for the client, increasing
    JS size and reducing server-rendering benefits. Small, focused interactive
    components at the leaves of the tree maximize server rendering.

Q3: How do you use a React context in the App Router?
A:  Create a Client Component provider (with 'use client'). Wrap the root
    layout with this provider. Since children is passed as a prop (not imported),
    those children can still be Server Components. The layout.tsx remains a
    Server Component but ThemeProvider (Client) wraps children.

Q4: How do you use a third-party library that uses hooks in a Server Component?
A:  You can't use it directly. Create a wrapper file with 'use client' at the
    top that imports and re-exports the library component. Import from your
    wrapper instead of the library directly. This confines the client boundary
    to the wrapper, not your server component.

Q5: What is a hydration mismatch and how do you fix it?
A:  A hydration mismatch occurs when the HTML rendered on the server differs
    from what React renders on the client during hydration. Common causes:
    timestamps, random values, window dimensions, localStorage. Fix: use
    useEffect to set browser-specific values (skipped on server), or use a
    mounted state flag to render fallback content on both server and client.

Q6: Can you call a Client Component from a Server Component?
A:  Yes. Server Components can import and render Client Components. The Client
    Component will appear in the RSC payload as a reference with props, and
    React will hydrate it in the browser.
