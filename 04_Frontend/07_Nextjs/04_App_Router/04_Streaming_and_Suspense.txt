1. WHAT IS STREAMING IN NEXT.JS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Streaming allows Next.js to progressively send HTML to the browser in chunks
rather than waiting for ALL data to load before sending anything.

Without streaming (traditional SSR):
  Client ─── request ──► Server
  Server waits for ALL data (DB queries, APIs)
  Server ─── full HTML ──► Client (long wait, nothing visible)

With streaming:
  Client ─── request ──► Server
  Server immediately sends HTML shell (layout, nav, skeleton)
  Server streams Suspense boundary fallbacks first
  As each data source resolves, the actual content is streamed
  Client progressively updates the UI

Benefits:
  - Faster Time to First Byte (TTFB) — shell arrives immediately
  - Better Largest Contentful Paint (LCP) — critical content shows early
  - Better user experience — content appears progressively
  - Independent loading — slow components don't block fast ones

2. HOW STREAMING WORKS WITH HTTP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js uses HTTP chunked transfer encoding:
  - Server sends Transfer-Encoding: chunked header
  - Content is sent in pieces (chunks) as it becomes ready
  - Browser renders each chunk as it arrives
  - No need to wait for Content-Length (unknown at start)

React delineates streaming boundaries with <Suspense>.
For each Suspense boundary:
  1. Server immediately renders and sends the fallback component
  2. Server awaits the async data inside the Suspense
  3. When data resolves, server streams the actual content chunk
  4. React swaps the fallback for the real content in the browser

3. loading.tsx — AUTOMATIC ROUTE-LEVEL SUSPENSE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Next.js automatically wraps page.tsx in a Suspense boundary
when loading.tsx is present in the same directory.

  app/
    dashboard/
      loading.tsx    ← fallback shown while page.tsx loads
      page.tsx       ← async Server Component
      error.tsx      ← error boundary

  // dashboard/loading.tsx
  export default function DashboardLoading() {
    return (
      <div className="skeleton">
        <div className="skeleton-header" />
        <div className="skeleton-grid">
          {Array.from({ length: 6 }).map((_, i) => (
            <div key={i} className="skeleton-card" />
          ))}
        </div>
      </div>
    );
  }

  // dashboard/page.tsx (async Server Component)
  export default async function DashboardPage() {
    // This entire page is wrapped in Suspense via loading.tsx
    const data = await fetchDashboardData();
    return <DashboardUI data={data} />;
  }

  // Next.js renders this equivalent structure:
  // <Suspense fallback={<DashboardLoading />}>

4. MANUAL SUSPENSE BOUNDARIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For finer-grained streaming, wrap individual components in Suspense:

  // app/dashboard/page.tsx
  import { Suspense } from 'react';

  export default function DashboardPage() {
    return (
      <main>
        {/* Static content renders immediately */}
        <DashboardHeader />

        {/* Each section streams independently */}
        <Suspense fallback={<RevenueCardSkeleton />}>
          <RevenueCard />        {/* fetches revenue data */}
        </Suspense>

        <Suspense fallback={<LatestInvoicesSkeleton />}>
          <LatestInvoices />     {/* fetches invoices independently */}
        </Suspense>

        <Suspense fallback={<CustomerChartSkeleton />}>
          <CustomerChart />      {/* slow, but doesn't block others */}
        </Suspense>
      </main>
    );
  }

  // RevenueCard.tsx — async Server Component
  async function RevenueCard() {
    const revenue = await fetchRevenue(); // only this suspends
    return <Card value={revenue} />;
  }

  // Loading timeline:
  // t=0ms   → DashboardHeader + 3 skeleton fallbacks sent to browser
  // t=200ms → RevenueCard resolves → streamed to browser
  // t=500ms → LatestInvoices resolves → streamed to browser
  // t=2000ms → CustomerChart resolves → streamed to browser

5. NESTED SUSPENSE (GROUPING)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Group related components under one Suspense
  export default function Page() {
    return (
      <Suspense fallback={<SidebarSkeleton />}>
        {/* Both components stream together — wait for BOTH */}
        <SidebarProfile />
        <SidebarStats />
      </Suspense>
    );
  }

  // Independent loading with nested Suspense
  export default function Page() {
    return (
      <Suspense fallback={<PageSkeleton />}>
        <div>
          <Suspense fallback={<HeaderSkeleton />}>
            <Header />   {/* streams as soon as it's ready */}
          </Suspense>
          <Suspense fallback={<ContentSkeleton />}>
            <Content />  {/* streams independently */}
          </Suspense>
        </div>
      </Suspense>
    );
  }
  // Outer Suspense: shows PageSkeleton until BOTH Header AND Content are ready
  // Inner Suspense: streams each independently as they resolve

6. React's use() HOOK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React 19 introduced use() to read Promises and Context in Client Components:

  'use client';
  import { use } from 'react';

  // Pass a Promise from Server Component to Client Component
  // Server Component:
  export default function Page() {
    const postsPromise = getPosts(); // DON'T await — pass the promise
    return (
      <Suspense fallback={<Loading />}>
        <Posts postsPromise={postsPromise} />
      </Suspense>
    );
  }

  // Client Component using use():
  'use client';
  import { use } from 'react';

  function Posts({ postsPromise }: { postsPromise: Promise<Post[]> }) {
    const posts = use(postsPromise); // suspends until resolved
    return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
  }

  // use() vs async Server Component:
  // - async component: simpler, server-only
  // - use(): useful when you need to read a promise in a CLIENT component
  //   while keeping the Suspense boundary server-side

  // use() also works with React Context:
  const theme = use(ThemeContext); // alternative to useContext()

7. STREAMING WITH AI / LLM RESPONSES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Route Handler streaming (app/api/chat/route.ts)
  import { OpenAIStream, StreamingTextResponse } from 'ai'; // Vercel AI SDK
  import OpenAI from 'openai';

  const openai = new OpenAI();

  export async function POST(req: Request) {
    const { messages } = await req.json();
    const response = await openai.chat.completions.create({
      model: 'gpt-4',
      messages,
      stream: true,
    });
    const stream = OpenAIStream(response);
    return new StreamingTextResponse(stream);
  }

  // Client Component consuming the stream
  'use client';
  import { useChat } from 'ai/react'; // Vercel AI SDK

  export function ChatInterface() {
    const { messages, input, handleInputChange, handleSubmit } = useChat();
    return (
      <div>
        {messages.map(m => <div key={m.id}>{m.content}</div>)}
        <form onSubmit={handleSubmit}>
          <input value={input} onChange={handleInputChange} />
          <button type="submit">Send</button>
        </form>
      </div>
    );
  }

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // error.tsx alongside loading.tsx handles Suspense errors
  // app/dashboard/error.tsx
  'use client'; // MUST be a Client Component

  export default function Error({
    error,
    reset,
  }: {
    error: Error & { digest?: string };
    reset: () => void;
  }) {
    return (
      <div>
        <h2>Something went wrong!</h2>
        <p>{error.message}</p>
        <button onClick={() => reset()}>Try again</button>
      </div>
    );
  }

  // reset() re-renders the children of the error boundary
  // digest is a hash useful for looking up server-side logs

9. PARTIAL PRE-RENDERING (PPR) — NEXT.JS 15 EXPERIMENTAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PPR combines static and dynamic content on the same page:

  // next.config.ts
  module.exports = { experimental: { ppr: true } }

  // How it works:
  // At build time:
  //   - Next.js pre-renders the static "shell" (outside Suspense boundaries)
  //   - Dynamic parts (inside Suspense with dynamic data) are skipped
  // At runtime:
  //   - Static shell is served instantly from CDN (like SSG)
  //   - Dynamic parts stream in as they resolve (like streaming SSR)

  export default function ProductPage({ params }) {
    return (
      <div>
        <StaticHeader />     {/* pre-rendered at build time */}
        <ProductDetails />   {/* pre-rendered at build time */}
        <Suspense fallback={<ReviewsSkeleton />}>
          <Reviews />        {/* dynamic — fetched at request time */}
        </Suspense>
        <Suspense fallback={<InventorySkeleton />}>
          <Inventory />      {/* dynamic — real-time stock data */}
        </Suspense>
      </div>
    );
  }

10. COMMON INTERVIEW QUESTIONS & ANSWERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is streaming in Next.js and how does it improve performance?
A:  Streaming sends HTML to the browser progressively (in chunks) instead of
    waiting for all data. The server sends the page shell immediately, then
    streams content as data resolves. This improves TTFB and user experience
    because the user sees content immediately instead of a blank screen.
    It uses HTTP chunked transfer encoding under the hood.

Q2: What is the difference between loading.tsx and manual Suspense?
A:  loading.tsx automatically wraps the entire page.tsx in a single Suspense
    boundary — the whole page shows the loading skeleton until ALL data is ready.
    Manual Suspense boundaries around individual components provide finer control —
    each component can stream independently, so fast components appear while slow
    ones are still loading.

Q3: Does Suspense work only for data fetching?
A:  No. Suspense works for: async Server Components (data fetching), lazy-loaded
    Client Components (next/dynamic, React.lazy), and any component that
    "suspends" (throws a Promise). In React 19, the use() hook lets Client
    Components suspend on a Promise passed from a Server Component.

Q4: What is Partial Pre-Rendering (PPR)?
A:  PPR is an experimental Next.js 15 feature combining static and dynamic on
    the same page. The static shell (outside Suspense) is pre-rendered at build
    time and served from CDN instantly. Dynamic parts (inside Suspense boundaries)
    stream in at request time. Best of both worlds: CDN speed + fresh dynamic data.

Q5: Can you explain how loading.tsx relates to Suspense?
A:  loading.tsx is syntactic sugar for a Suspense boundary. When Next.js sees
    loading.tsx and page.tsx in the same folder, it wraps page.tsx in:
    <Suspense fallback={<Loading />}>
      <Page />
    </Suspense>
    This automatically enables streaming for that route.

Q6: What happens if an async Server Component inside a Suspense boundary throws?
A:  React's error boundary catches the error. In Next.js, error.tsx acts as
    the error boundary for the route segment. It MUST be a Client Component
    ('use client'). It receives the error object and a reset() function to
    retry rendering the failed component tree.

================================================================================
  KEY INSIGHT: Wrap slow components in Suspense to stream fast content first.
  Use loading.tsx for whole-page loading states, manual <Suspense> for
  component-level granularity. Each Suspense boundary is independent.
================================================================================
