================================================================================
  CSRF (Cross-Site Request Forgery) — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS CSRF?
────────────────────────────────────────────────────────────────────────────────

  Cross-Site Request Forgery (CSRF) tricks an authenticated user into
  unknowingly making requests to a target site where they're logged in.

  Core problem: Browsers automatically send cookies with every request to
  the matching domain — even requests triggered by another site.

  Attack flow:
    1. User is logged into bank.com (has valid session cookie)
    2. User visits malicious evil.com
    3. evil.com contains: <img src="https://bank.com/transfer?to=attacker&amount=5000">
    4. Browser makes GET request to bank.com (auto-includes session cookie)
    5. Bank processes transfer as authenticated request!

  Real-world impact:
    • Unauthorized money transfers
    • Email/password changes
    • Account deletion
    • Admin actions taken on the user's behalf

────────────────────────────────────────────────────────────────────────────────
2. CSRF ATTACK VECTORS
────────────────────────────────────────────────────────────────────────────────

  GET request via img src:
    <img src="https://bank.com/transfer?to=attacker&amount=1000">

  POST request via form auto-submit:
    <form action="https://bank.com/transfer" method="POST" id="f">
      <input name="to" value="attacker">
      <input name="amount" value="1000">
    </form>
    <script>document.getElementById('f').submit();</script>

  POST via fetch from evil.com:
    fetch('https://bank.com/transfer', {
      method: 'POST',
      credentials: 'include', // sends bank.com cookies
      body: 'to=attacker&amount=1000'
    });
    
    (Only works if bank.com has permissive CORS; typically blocked by CORS)

  JSON API attacks:
    Many modern APIs accept Content-Type: application/json.
    A simple HTML form can only send: application/x-www-form-urlencoded,
    multipart/form-data, or text/plain.
    
    If server requires JSON, form-based CSRF is blocked by content type.
    But if server accepts multiple content types, it can still be attacked.

────────────────────────────────────────────────────────────────────────────────
3. CSRF DEFENSES
────────────────────────────────────────────────────────────────────────────────

  3.1 SYNCHRONIZER TOKEN PATTERN (CSRF Tokens)
    Server generates a unique random token per session.
    Includes it in every HTML form (hidden field).
    On form submission, server validates the token.
    
    An attacker can't forge the request because they don't know the token.
    
    HTML form:
      <form method="POST" action="/transfer">
        <input type="hidden" name="_csrf" value="{{ csrfToken }}">
        <input name="to" value="">
        <input name="amount" value="">
        <button>Transfer</button>
      </form>
    
    For AJAX:
      // Send token in custom header (attacker can't set custom headers cross-origin)
      const csrfToken = document.querySelector('meta[name="csrf-token"]').content;
      fetch('/api/transfer', {
        method: 'POST',
        headers: {
          'X-CSRF-Token': csrfToken,
          'Content-Type': 'application/json'
        },
        body: JSON.stringify({ to: 'recipient', amount: 100 })
      });
    
    Meta tag pattern:
      <meta name="csrf-token" content="{{ csrfToken }}">

  3.2 SAMESITE COOKIE ATTRIBUTE (Best Modern Defense)
    Restricts when cookies are sent with cross-site requests.
    
    SameSite=Strict:
      Cookie only sent on same-site requests.
      Prevents ALL cross-site requests from including the cookie.
      Most secure but breaks external links to authenticated pages.
    
    SameSite=Lax (modern browser default):
      Cookie sent on same-site requests + top-level GET navigations.
      NOT sent on cross-site POST, XHR, or iframe requests.
      Blocks most CSRF attacks (forms POST, XHR) while allowing normal links.
    
    SameSite=None:
      Cookie sent with all requests — requires Secure flag.
      Needed for third-party embeds but eliminates CSRF protection.
    
    Set-Cookie: session=abc; SameSite=Strict; Secure; HttpOnly

  3.3 DOUBLE SUBMIT COOKIE PATTERN
    Server sets a CSRF token as a cookie.
    Client reads cookie and includes token in request header or body.
    Server compares header/body token with cookie token.
    
    Attacker can't read the cookie (same-origin policy) → can't duplicate it.
    
    Note: Vulnerable if attacker can inject cookie (subdomain compromise).

  3.4 ORIGIN / REFERER HEADER VALIDATION
    Check Origin or Referer header on state-changing requests.
    Accept only if it matches expected origin.
    
    Simple but can fail if headers are stripped by proxies or
    if browser doesn't send them. Not reliable as sole defense.
    
    // Server-side check
    if (req.headers.origin !== 'https://myapp.com') {
      return res.status(403).json({ error: 'CSRF check failed' });
    }

  3.5 CUSTOM REQUEST HEADERS
    Require a custom header (e.g., X-Requested-With: XMLHttpRequest).
    Cross-origin forms and direct browser requests cannot set custom headers
    (CORS preflight would block or the request wouldn't send them).
    
    Only works for AJAX requests, not form submissions.

  3.6 USER INTERACTION (Captcha, Re-authentication)
    For sensitive operations (password change, bank transfer):
    • Require password re-entry
    • Add CAPTCHA
    • 2FA confirmation
    Ensures the user is actively participating, not being tricked.

4. CSRF vs XSS
────────────────────────────────────────────────────────────────────────────────

  ┌─────────────────┬──────────────────────────────┬──────────────────────────────┐
  │ Feature         │ CSRF                         │ XSS                          │
  ├─────────────────┼──────────────────────────────┼──────────────────────────────┤
  │ Attack vector   │ Forged requests from          │ Injected script execution    │
  │                 │ another site                  │ on the victim's site         │
  │ Trust exploited │ Server trusts user's browser  │ User trusts the target site  │
  │ Cookie access   │ Doesn't need to read cookies  │ Can steal cookies            │
  │ Origin          │ Attacker's site               │ Victim's site (JS injected)  │
  │ Prevention      │ CSRF token, SameSite          │ Output encoding, CSP         │
  │ Impact          │ Unauthorized state changes    │ Full session hijack, data theft│
  └─────────────────┴──────────────────────────────┴──────────────────────────────┘

  Key insight: XSS can be used to bypass CSRF protections (read the CSRF token
  from the DOM and use it in a forged request). So XSS is often more dangerous.

────────────────────────────────────────────────────────────────────────────────
5. MODERN API CSRF CONSIDERATIONS
────────────────────────────────────────────────────────────────────────────────

  REST APIs with token-in-header (not cookies):
    If auth token is in Authorization header (localStorage → header):
    No CSRF risk — attackers can't set custom headers cross-origin.
    But vulnerable to XSS (token in localStorage is accessible to JS).
    
  REST APIs with cookie-based auth:
    CSRF risk exists. Protect with SameSite cookies + CSRF tokens.

  GraphQL APIs:
    Typically use POST with JSON body.
    Form-based CSRF is limited (can't POST JSON from a plain HTML form).
    But fetch with credentials:include from attacker site can work if CORS is open.
    Protect with SameSite + CORS restrictions.

  Preflight requests (CORS):
    For requests with custom headers or non-simple methods, browser sends
    a CORS preflight OPTIONS request. If server doesn't allow the origin,
    the actual request is blocked. But this only protects if CORS is properly configured.

────────────────────────────────────────────────────────────────────────────────
6. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is CSRF and how does it work?
A: CSRF tricks an authenticated user into unknowingly submitting a malicious
   request to a site where they're logged in. The attacker hosts a page with
   a form/image/script that sends a request to the target site. Since the
   browser automatically sends cookies for that domain, the request appears
   legitimate to the server.

Q: What is the most effective modern defense against CSRF?
A: SameSite=Strict/Lax cookie attribute. With SameSite=Lax (modern browser
   default), cookies are not sent with cross-site POST requests or
   cross-site AJAX requests. Combined with SameSite=Strict for sensitive
   operations, this blocks virtually all CSRF attacks without needing
   separate CSRF tokens.

Q: How does the CSRF token pattern work?
A: The server generates a random token, stores it in the session, and
   embeds it in HTML forms as a hidden field. When the form is submitted,
   the server validates that the token in the request matches the token
   in the session. An attacker on a different origin cannot read the
   token from the target site (same-origin policy), so they can't forge
   a valid request.

Q: Can XSS bypass CSRF protections?
A: Yes. If an attacker executes XSS on the target site, they can read
   the CSRF token from the DOM and use it in their forged request. This is
   why preventing XSS is also essential for CSRF protection — a CSRF token
   is only effective if attackers can't read it.

Q: How is CSRF different from XSS?
A: CSRF exploits the server's trust in the user's browser (forged requests
   include valid cookies). XSS exploits the user's trust in a website
   (attacker's script runs with the page's origin permissions). CSRF
   doesn't require stealing any data; XSS enables full session hijacking.

Q: Why doesn't CORS protection alone prevent CSRF?
A: Simple requests (GET, POST with standard content types like
   application/x-www-form-urlencoded) do NOT trigger CORS preflight
   and still include cookies. CORS prevents the attacker from READING
   the response cross-origin but doesn't block the state-changing
   request from being sent. SameSite cookies and CSRF tokens are needed.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • CSRF: forged requests exploit browser's auto-cookie behavior
  • Defenses: SameSite=Lax/Strict (best), CSRF tokens, Origin header check
  • SameSite=Lax (default): blocks cross-site POST/XHR but allows top-level GET nav
  • CSRF token: random value in form + server validates → attacker can't know it
  • XSS can bypass CSRF tokens → secure against XSS first
  • API with Authorization header (not cookie): no CSRF risk; but XSS risk
================================================================================
