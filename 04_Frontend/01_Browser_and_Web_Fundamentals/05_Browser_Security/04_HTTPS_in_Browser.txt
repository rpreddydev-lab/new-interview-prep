  HTTPS IN THE BROWSER — Complete Interview Reference

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS HTTPS?
────────────────────────────────────────────────────────────────────────────────

  HTTPS = HTTP over TLS (Transport Layer Security).
  TLS encrypts the HTTP communication between browser and server.

  Goals of TLS:
    • Confidentiality: Encrypted data — eavesdroppers cannot read it
    • Integrity: Data cannot be tampered with in transit (MAC/AEAD)
    • Authentication: Certificate verifies the server's identity

  HTTP vs HTTPS:
    HTTP: plaintext, visible to anyone on the network
    HTTPS: encrypted, only browser and server can read it

────────────────────────────────────────────────────────────────────────────────
2. TLS HANDSHAKE
────────────────────────────────────────────────────────────────────────────────

  TLS 1.3 Handshake (simplified, modern):

  1. ClientHello
     Browser → Server
     - TLS version supported
     - Cipher suites supported (e.g., AES-256-GCM-SHA384)
     - Client random (32 bytes)
     - Supported key exchange groups (Diffie-Hellman parameters)
     - Server Name Indication (SNI): which hostname is requested

  2. ServerHello
     Server → Browser
     - Selected cipher suite
     - Server random
     - Key share (Diffie-Hellman public value)
     - Session ID (for session resumption)

  3. Certificate + CertificateVerify
     Server → Browser
     - Server's TLS certificate (X.509) — contains:
       - Server's public key
       - Domain name (CN or SAN)
       - Issuer (Certificate Authority)
       - Validity period
       - Digital signature by the CA
     - CertificateVerify: server proves it holds the private key

  4. Browser Validates Certificate:
     - Is the signature from a trusted CA (in browser's root store)?
     - Is the domain in the certificate correct?
     - Is the certificate within validity period?
     - Is the certificate revoked? (CRL / OCSP)

  5. Key Derivation:
     Both sides compute the same session key using Diffie-Hellman key exchange.
     Shared secret never transmitted — both sides independently compute it.

  6. Finished:
     Both sides exchange Finished messages encrypted with session key.
     Handshake complete.

  TLS 1.3 improvements over 1.2:
    • 1-RTT handshake (was 2-RTT in TLS 1.2)
    • 0-RTT session resumption (data in first packet — slight replay risk)
    • Removed vulnerable cipher suites (RC4, DES, SHA-1 for MACs)
    • Forward Secrecy mandatory (ephemeral Diffie-Hellman)

────────────────────────────────────────────────────────────────────────────────
3. CERTIFICATES AND CERTIFICATE AUTHORITIES
────────────────────────────────────────────────────────────────────────────────

  X.509 Certificate contains:
    • Subject: the entity the cert is for (e.g., CN=example.com)
    • Subject Alternative Names (SAN): additional domains
    • Issuer: Certificate Authority (CA) that signed it
    • Validity: Not Before / Not After dates
    • Public Key
    • Signature: CA's digital signature over the above

  Certificate Chain (Chain of Trust):
    Root CA (self-signed, in browser/OS trust store)
      └── Intermediate CA (signed by Root)
            └── End-Entity Certificate (signed by Intermediate)
    
    Browser only ships Root CA public keys. Verifies chain up to root.

  Certificate Types:
    Domain Validated (DV):
      Verifies domain ownership only. Fast, cheap, automated.
      Let's Encrypt issues DV certs for free.
    
    Organization Validated (OV):
      Verifies domain + organization identity.
    
    Extended Validation (EV):
      Thorough validation of organization. Used to show company name in browser
      address bar (browsers largely removed this visual distinction).

  Certificate Revocation:
    CRL (Certificate Revocation List): download list of revoked certs (slow, large)
    OCSP (Online Certificate Status Protocol): query CA in real-time (slower)
    OCSP Stapling: server includes OCSP response in TLS handshake (fast)
    Chrome's CRLSets: Google pushes a subset of critical revocations to Chrome

  Certificate Transparency (CT):
    All public CAs must log certificates to public CT logs.
    Allows detection of misissued certificates.
    Browsers require CT compliance (Chrome, Safari).

────────────────────────────────────────────────────────────────────────────────
4. FORWARD SECRECY
────────────────────────────────────────────────────────────────────────────────

  Without forward secrecy:
    If attacker records encrypted traffic and later gets the server's private key,
    they can decrypt all recorded traffic.

  With forward secrecy (DHE, ECDHE):
    Each session uses a unique ephemeral Diffie-Hellman key pair.
    Session keys are never stored — discarded after session.
    Past sessions cannot be decrypted even with private key compromise.

  TLS 1.3 mandates forward secrecy for all cipher suites.

────────────────────────────────────────────────────────────────────────────────
5. HTTPS IN THE BROWSER
────────────────────────────────────────────────────────────────────────────────

  HSTS (HTTP Strict Transport Security):
    Server tells browser to only use HTTPS for future visits.
    
    Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
    
    max-age: seconds to remember (1 year = 31536000)
    includeSubDomains: all subdomains must use HTTPS
    preload: opt in to browser HSTS preload list
    
    HSTS Preload List:
      Browser vendors maintain a hardcoded list of HSTS domains.
      These domains ALWAYS use HTTPS even on first visit.
      Submit at: hstspreload.org

  Mixed Content:
    HTTPS page loading HTTP resources → mixed content warning/error.
    
    Passive mixed content (images, video): Deprecated — browser may block
    Active mixed content (scripts, CSS): Blocked — breaks security model
    
    Fix: upgrade all resources to HTTPS.
    Upgrade-Insecure-Requests CSP directive: browser upgrades HTTP to HTTPS.

  HTTPS Everywhere:
    Rule of thumb: serve EVERYTHING over HTTPS.
    Redirect HTTP → HTTPS at server level (301 permanent redirect).

  Browser indicators:
    🔒 Padlock: HTTPS with valid cert
    ⚠️  Warning: Expired cert, self-signed cert, or mixed content
    🔒 (no org name): DV cert
    "Not Secure": HTTP page (Chrome shows this prominently)

────────────────────────────────────────────────────────────────────────────────
6. PUBLIC KEY INFRASTRUCTURE (PKI)
────────────────────────────────────────────────────────────────────────────────

  Asymmetric Cryptography (public key / private key):
    • Public key: shared openly, embedded in certificate
    • Private key: kept secret by server
    • Data encrypted with public key → can only be decrypted with private key
    • Data signed with private key → can be verified with public key

  Symmetric Encryption:
    Same key for encryption and decryption.
    Much faster than asymmetric encryption.
    TLS uses asymmetric to establish session, then symmetric for data.
    (AES-256-GCM is common symmetric cipher)

  Diffie-Hellman Key Exchange:
    Allows two parties to establish a shared secret over an insecure channel.
    Neither party transmits the final secret — both compute it independently.
    ECDHE = Elliptic Curve Diffie-Hellman Ephemeral (fast, widely used)

7. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between HTTP and HTTPS?
A: HTTP sends data in plaintext — anyone on the network can read it.
   HTTPS uses TLS to encrypt communication, providing confidentiality
   (data is encrypted), integrity (data can't be tampered), and authentication
   (certificate proves server identity).

Q: How does the TLS handshake work?
A: (1) Client sends ClientHello with supported cipher suites and its key share.
   (2) Server responds with ServerHello, chosen cipher, its key share, and
   certificate. (3) Client validates the certificate (trusted CA, valid domain,
   not expired). (4) Both sides compute the same session key using ECDHE.
   (5) Finished messages confirm the handshake. All subsequent data is
   encrypted with the session key.

Q: What is a TLS certificate and what does it contain?
A: An X.509 certificate containing: the domain (Common Name/SAN), the server's
   public key, issuer (CA), validity period, and the CA's digital signature.
   The browser validates the signature chain up to a trusted root CA in its
   trust store.

Q: What is forward secrecy and why does it matter?
A: Forward secrecy (via ECDHE) means each TLS session uses a unique ephemeral
   key pair discarded after the session. If the server's long-term private key
   is later compromised, it cannot be used to decrypt past sessions.
   TLS 1.3 mandates forward secrecy for all cipher suites.

Q: What is HSTS?
A: HTTP Strict Transport Security is a response header that tells browsers to
   only connect to the site via HTTPS for a specified max-age period. This
   prevents SSL stripping attacks where a man-in-the-middle downgrades HTTPS
   to HTTP on the first request. The HSTS preload list hardcodes common sites
   to always use HTTPS even on the first visit.

Q: What is mixed content?
A: When an HTTPS page loads resources (scripts, images) over HTTP.
   Active mixed content (scripts/CSS) is blocked because it would undermine
   HTTPS security. Passive mixed content (images) may be warned or blocked
   depending on browser version. Fix by using HTTPS for all resources.

Q: What is OCSP stapling?
A: OCSP (Online Certificate Status Protocol) lets browsers check if a
   certificate is revoked. Normally, the browser queries the CA's OCSP server,
   adding latency. OCSP stapling means the server fetches the OCSP response
   and includes it in the TLS handshake, eliminating the extra round trip.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • HTTPS = HTTP over TLS: provides confidentiality, integrity, authentication
  • TLS handshake: ClientHello → ServerHello+Cert → Key derivation (ECDHE) → Finished
  • Certificate chain: end-entity cert → intermediate CA → root CA (trusted)
  • Forward secrecy (ECDHE): ephemeral keys; past traffic safe even if key compromised
  • HSTS: browser-enforced HTTPS for all future connections to a domain
  • TLS 1.3: 1-RTT, mandatory forward secrecy, removed weak ciphers
  • Mixed content: HTTP resources on HTTPS page → security risk; blocked
