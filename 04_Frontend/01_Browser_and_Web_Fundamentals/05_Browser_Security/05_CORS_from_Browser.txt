================================================================================
  CORS (Cross-Origin Resource Sharing) FROM THE BROWSER — Complete Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS CORS?
────────────────────────────────────────────────────────────────────────────────

  CORS is a browser mechanism that controls how web pages can request
  resources from a different origin than the page itself.

  Same-Origin Policy (SOP):
    The foundation: browsers block JS from reading responses from different origins.
    Origin = protocol + hostname + port
    
    https://example.com:443 vs:
    http://example.com         → different (protocol)
    https://sub.example.com    → different (hostname)
    https://example.com:8080   → different (port)

  CORS allows servers to opt-in to cross-origin requests by sending
  special HTTP headers. Without these headers, the browser blocks the response.

  Important: CORS is enforced by the BROWSER, not the server.
    • CORS does NOT prevent server from receiving the request
    • CORS only prevents JS from READING the response
    • Server-to-server requests are not subject to CORS

────────────────────────────────────────────────────────────────────────────────
2. SIMPLE REQUESTS vs PREFLIGHT REQUESTS
────────────────────────────────────────────────────────────────────────────────

  2.1 SIMPLE REQUESTS (no preflight)
    Conditions for a simple request (ALL must be true):
    • Method: GET, HEAD, or POST
    • Content-Type (if POST): one of:
        application/x-www-form-urlencoded
        multipart/form-data
        text/plain
    • No custom headers (beyond the CORS-safelisted headers)
    • No ReadableStream in request body
    
    Simple requests are sent directly; browser checks response headers.
    
    Browser sends:
      GET /api/data HTTP/1.1
      Origin: https://frontend.com
    
    Server must respond with:
      Access-Control-Allow-Origin: https://frontend.com

  2.2 PREFLIGHT REQUESTS
    Triggered for non-simple requests:
    • Methods: PUT, DELETE, PATCH, OPTIONS
    • Content-Type: application/json or other non-simple types
    • Custom headers (e.g., Authorization, X-Custom-Header)
    
    Browser sends an OPTIONS preflight FIRST:
      OPTIONS /api/data HTTP/1.1
      Origin: https://frontend.com
      Access-Control-Request-Method: PUT
      Access-Control-Request-Headers: Content-Type, Authorization
    
    Server must respond to preflight:
      Access-Control-Allow-Origin: https://frontend.com
      Access-Control-Allow-Methods: GET, POST, PUT, DELETE
      Access-Control-Allow-Headers: Content-Type, Authorization
      Access-Control-Max-Age: 86400   (cache preflight for 1 day)
    
    If server doesn't respond correctly → browser blocks the actual request.
    If server responds correctly → browser sends the actual request.

────────────────────────────────────────────────────────────────────────────────
3. CORS RESPONSE HEADERS
────────────────────────────────────────────────────────────────────────────────

  Access-Control-Allow-Origin:
    Specifies which origins can access the resource.
    
    Access-Control-Allow-Origin: *               (allow all — cannot use credentials)
    Access-Control-Allow-Origin: https://app.com (specific origin)
    
    Cannot use wildcard (*) when credentials (cookies, auth headers) are involved.
    Must specify exact origin when withCredentials=true.

  Access-Control-Allow-Methods:
    Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS

  Access-Control-Allow-Headers:
    Access-Control-Allow-Headers: Content-Type, Authorization, X-Custom-Header

  Access-Control-Allow-Credentials:
    Access-Control-Allow-Credentials: true
    Required for cookies/auth headers to be included in cross-origin requests.
    Must be true + origin must be specific (not *).

  Access-Control-Max-Age:
    How long the preflight response can be cached (in seconds).
    Access-Control-Max-Age: 86400 (1 day)

  Access-Control-Expose-Headers:
    By default, browsers only expose simple response headers to JS.
    To expose additional headers:
    Access-Control-Expose-Headers: X-Custom-Header, X-Total-Count

────────────────────────────────────────────────────────────────────────────────
4. CORS WITH CREDENTIALS
────────────────────────────────────────────────────────────────────────────────

  By default, fetch/XHR do NOT include cookies in cross-origin requests.
  
  To include cookies:
    // Client-side:
    fetch('https://api.example.com/data', {
      credentials: 'include'
    });
    
    // XHR:
    xhr.withCredentials = true;
  
  Server MUST respond with ALL THREE:
    Access-Control-Allow-Origin: https://app.example.com  (NOT *)
    Access-Control-Allow-Credentials: true
    
  If using wildcard: Access-Control-Allow-Origin: *
    Browser will NOT send cookies even if credentials: 'include' is set.

────────────────────────────────────────────────────────────────────────────────
5. COMMON CORS ERRORS
────────────────────────────────────────────────────────────────────────────────

  Error: "No 'Access-Control-Allow-Origin' header is present"
    Cause: Server didn't set CORS headers.
    Fix: Add CORS headers to server response.

  Error: "The 'Access-Control-Allow-Origin' header has value '*' which is 
         not allowed when 'Access-Control-Allow-Credentials' is set to 'true'"
    Fix: Use specific origin instead of wildcard.

  Error: "Response to preflight request doesn't pass access control check"
    Cause: Server's OPTIONS response doesn't include the required headers.
    Fix: Handle OPTIONS requests and return appropriate CORS headers.

  Error: "Request header 'Authorization' is not allowed by 
         Access-Control-Allow-Headers"
    Fix: Add Authorization to Access-Control-Allow-Headers.

6. SERVER-SIDE CORS CONFIGURATION
────────────────────────────────────────────────────────────────────────────────

  Express.js (Node.js):
    const cors = require('cors');
    
    // Allow specific origin
    app.use(cors({
      origin: 'https://frontend.com',
      methods: ['GET', 'POST', 'PUT', 'DELETE'],
      allowedHeaders: ['Content-Type', 'Authorization'],
      credentials: true,
      maxAge: 86400
    }));
    
    // Dynamic origin (multiple allowed origins):
    const allowedOrigins = ['https://app1.com', 'https://app2.com'];
    app.use(cors({
      origin: (origin, callback) => {
        if (!origin || allowedOrigins.includes(origin)) {
          callback(null, true);
        } else {
          callback(new Error('Not allowed by CORS'));
        }
      }
    }));

  Nginx:
    add_header Access-Control-Allow-Origin $http_origin always;
    add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
    if ($request_method = 'OPTIONS') {
      return 204;
    }

7. CORS SECURITY CONSIDERATIONS
────────────────────────────────────────────────────────────────────────────────

  Never use Access-Control-Allow-Origin: * for sensitive APIs:
    Allows any website to read your API responses.
    Use specific origins or authenticated endpoints.

  Reflect origin blindly — DANGEROUS:
    if (req.headers.origin) {
      res.setHeader('Access-Control-Allow-Origin', req.headers.origin); // BAD!
    }
    This allows ANY origin — same as wildcard. Use an allowlist.

  Null origin:
    Sandboxed iframes and local files send Origin: null.
    Never whitelist null: Access-Control-Allow-Origin: null
    Attackers can trigger null origin via sandboxed iframe.

  Subdomain trust:
    Domain allowlist: *.example.com means any subdomain can access.
    If any subdomain is compromised, all can access.

────────────────────────────────────────────────────────────────────────────────
8. CORS vs CSRF
────────────────────────────────────────────────────────────────────────────────

  Key distinction:
    CORS: Prevents cross-origin READING of responses in browser JS.
    CSRF: Prevents cross-origin WRITING (state-changing requests).

  CORS does NOT prevent CSRF:
    Simple form POST (no custom headers) doesn't trigger CORS preflight.
    The request IS made; only the response is blocked from JS reading.
    For state-changing actions: use CSRF tokens or SameSite cookies.

  CORS DOES prevent:
    JS on evil.com from reading responses from api.bank.com.
    Leaking sensitive data to attacker-controlled page JS.

9. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is CORS and why does it exist?
A: CORS is a browser mechanism that extends the Same-Origin Policy to allow
   controlled cross-origin requests. Without CORS (just SOP), JS cannot read
   responses from different origins. CORS lets servers explicitly opt-in to
   allow specific cross-origin requests via response headers. It exists to
   balance security (SOP) with the need for cross-origin API calls in modern apps.

Q: What is a preflight request?
A: A CORS preflight is an automatic OPTIONS request the browser sends before
   a non-simple cross-origin request (e.g., PUT with JSON body, custom headers).
   The browser asks: "Can I make this request?" The server responds with
   Access-Control-Allow-* headers. If approved, the actual request proceeds.

Q: What is the difference between * and a specific origin in CORS?
A: Access-Control-Allow-Origin: * allows any origin to read responses, but
   credentials (cookies) cannot be used with wildcard. Specifying an exact
   origin (https://app.com) restricts access and enables credentials with
   Access-Control-Allow-Credentials: true.

Q: Does CORS prevent CSRF attacks?
A: No. CORS controls what JS can READ from cross-origin responses. Simple
   cross-origin requests (GET, form POST) are SENT before CORS headers are
   checked — the server still processes them. CORS prevents response reading,
   not request sending. Use SameSite cookies and CSRF tokens to prevent CSRF.

Q: Why does a CORS error appear in the browser but not in Postman?
A: CORS is enforced by the BROWSER as part of the Same-Origin Policy. Postman
   and server-to-server requests don't enforce CORS — they can make any request.
   The browser blocks reading the response; the server still received and
   processed the request.

Q: What causes a "credentials with wildcard" CORS error?
A: When a cross-origin request includes credentials (cookies) via
   credentials: 'include', the server must respond with a specific origin (not *)
   and Access-Control-Allow-Credentials: true. Using wildcard (*) with credentials
   is disallowed because it would let any website access credentialed APIs.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • CORS extends Same-Origin Policy for controlled cross-origin access
  • CORS is browser-enforced; server still receives blocked requests
  • Simple requests: sent directly; server responds with ACAO header
  • Preflight: OPTIONS request for non-simple requests (custom headers, PUT/DELETE, JSON)
  • Credentials (cookies): requires specific origin (not *) + ACAC: true
  • Never blindly reflect Origin header; use an allowlist
  • CORS prevents response READING; SameSite+CSRF tokens prevent CSRF (writing)
