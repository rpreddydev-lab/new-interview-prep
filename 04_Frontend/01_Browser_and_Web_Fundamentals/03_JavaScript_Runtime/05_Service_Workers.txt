1. WHAT IS A SERVICE WORKER?
────────────────────────────────────────────────────────────────────────────────

  A Service Worker is a JavaScript file that:
    • Runs in its own thread (separate from the main JS thread)
    • Acts as a programmable network proxy between browser and server
    • Can intercept and handle network requests
    • Enables offline experiences, background sync, push notifications

  Key characteristics:
    ✓ Runs in a separate worker context (no DOM access)
    ✓ Asynchronous, event-driven
    ✓ HTTPS required (except localhost for development)
    ✓ Persistent: survives page close (registered with browser)
    ✓ Shared across all pages on the same origin
    ✓ Can cache requests/responses
    ✗ No access to DOM
    ✗ No synchronous APIs (XHR, localStorage)

  Service Worker acts as:
    Browser ←── SW ──→ Network (SW intercepts everything in between)

2. SERVICE WORKER LIFECYCLE
────────────────────────────────────────────────────────────────────────────────

  Registration:
    // main.js (page)
    if ('serviceWorker' in navigator) {
      navigator.serviceWorker.register('/sw.js', { scope: '/' })
        .then(registration => {
          console.log('SW registered:', registration.scope);
        })
        .catch(err => console.error('SW registration failed:', err));
    }

  Lifecycle Phases:

  1. DOWNLOAD:
    Browser downloads sw.js file.

  2. INSTALL:
    Triggered after download. Typically used to cache assets.
    If install fails (e.g., cache fails) → SW goes to "error" state.
    
    // sw.js
    const CACHE_NAME = 'v1';
    const ASSETS = ['/', '/style.css', '/app.js', '/offline.html'];
    
    self.addEventListener('install', event => {
      event.waitUntil(
        caches.open(CACHE_NAME)
          .then(cache => cache.addAll(ASSETS))
          .then(() => self.skipWaiting()) // activate immediately
      );
    });

  3. WAITING:
    New SW installed but can't activate yet because old SW is
    still controlling open pages. Waits for all old pages to close.
    Can be bypassed with self.skipWaiting() in install event.

  4. ACTIVATE:
    Old SW removed, new SW takes control. Typically clean up old caches.
    Does NOT automatically control existing open pages until they reload.
    Use clients.claim() to immediately take control of open pages.
    
    self.addEventListener('activate', event => {
      event.waitUntil(
        caches.keys().then(cacheNames => {
          return Promise.all(
            cacheNames
              .filter(name => name !== CACHE_NAME)
              .map(name => caches.delete(name)) // delete old caches
          );
        })
        .then(() => self.clients.claim()) // take control immediately
      );
    });

  5. ACTIVE (Idle):
    SW controls all in-scope pages. Listens for events.
    Browser may terminate idle SWs to free memory.

  6. TERMINATED:
    Browser may stop idle SWs. They're re-started when needed.
    Do NOT store state in SW global scope — use IndexedDB/Cache API.

  State Transitions:
    Installing → (success) → Installed/Waiting → Activated → Idle ↔ Handling events

3. FETCH EVENT (NETWORK INTERCEPTION)
────────────────────────────────────────────────────────────────────────────────

  The most important SW event — intercepts ALL network requests from controlled pages.

    self.addEventListener('fetch', event => {
      event.respondWith(
        caches.match(event.request)
          .then(cachedResponse => {
            // Return cached or fetch from network
            return cachedResponse || fetch(event.request);
          })
      );
    });

  event.request → the Request object
  event.respondWith(Promise<Response>) → resolve with a Response

4. CACHING STRATEGIES
────────────────────────────────────────────────────────────────────────────────

  4.1 CACHE ONLY
    Serve only from cache. Used for app shell assets.
    Fails if asset not in cache.
    
    self.addEventListener('fetch', event => {
      event.respondWith(caches.match(event.request));
    });

  4.2 NETWORK ONLY
    Always fetch from network. No caching.
    
    self.addEventListener('fetch', event => {
      event.respondWith(fetch(event.request));
    });

  4.3 CACHE FIRST (Cache-then-Network fallback)
    Check cache first. If miss, fetch network and cache response.
    Best for: static assets, offline fallback.
    Risk: stale data.
    
    self.addEventListener('fetch', event => {
      event.respondWith(
        caches.match(event.request).then(cached => {
          if (cached) return cached;
          return fetch(event.request).then(response => {
            const clone = response.clone();
            caches.open(CACHE_NAME).then(cache => cache.put(event.request, clone));
            return response;
          });
        })
      );
    });

  4.4 NETWORK FIRST (Network-then-Cache fallback)
    Try network first. If fails (offline), serve from cache.
    Best for: frequently updated content (API responses, news feeds).
    
    self.addEventListener('fetch', event => {
      event.respondWith(
        fetch(event.request)
          .then(response => {
            const clone = response.clone();
            caches.open(CACHE_NAME).then(cache => cache.put(event.request, clone));
            return response;
          })
          .catch(() => caches.match(event.request))
      );
    });

  4.5 STALE-WHILE-REVALIDATE
    Serve from cache immediately (fast). Simultaneously fetch new version.
    Update cache with new version for next request.
    Best for: balance between freshness and speed.
    
    self.addEventListener('fetch', event => {
      event.respondWith(
        caches.open(CACHE_NAME).then(cache => {
          return cache.match(event.request).then(cached => {
            const networkFetch = fetch(event.request).then(response => {
              cache.put(event.request, response.clone());
              return response;
            });
            return cached || networkFetch; // use cached if available, update in bg
          });
        })
      );
    });

  Choosing a strategy:
    ┌───────────────────────────────┬──────────────────────────────┐
    │ Resource Type                 │ Strategy                     │
    ├───────────────────────────────┼──────────────────────────────┤
    │ App shell (HTML, CSS, JS)     │ Cache First                  │
    │ Versioned static assets       │ Cache First (immutable)      │
    │ API data (dynamic)            │ Network First                │
    │ Non-critical content          │ Stale-While-Revalidate       │
    │ Always-fresh data             │ Network Only                 │
    │ Offline-only content          │ Cache Only                   │
    └───────────────────────────────┴──────────────────────────────┘

5. CACHE API
────────────────────────────────────────────────────────────────────────────────

  Storage API for Request/Response pairs.
  Used primarily by Service Workers.
  Also available in window context.

    caches.open('cache-name') → Promise<Cache>
    cache.put(request, response) → stores the pair
    cache.add(url) → fetches URL, stores in cache
    cache.addAll([url1, url2]) → fetches and stores multiple
    cache.match(request) → find matching response (or undefined)
    cache.keys() → all cached requests
    cache.delete(request) → remove entry
    caches.match(request) → search ALL named caches
    caches.keys() → list all cache names
    caches.delete('cache-name') → delete entire cache

6. PUSH NOTIFICATIONS
────────────────────────────────────────────────────────────────────────────────

  Architecture:
    1. Browser → Ask user permission
    2. Browser → Subscribe to Push Service (FCM, APNs, etc.)
    3. Browser gets a PushSubscription (endpoint + keys)
    4. Client sends PushSubscription to YOUR server
    5. Your server sends push message to Push Service with subscription
    6. Push Service → Browser → SW receives 'push' event
    7. SW displays notification

  Step 1: Request permission
    const permission = await Notification.requestPermission();
    if (permission === 'granted') { ... }

  Step 2-4: Subscribe
    const registration = await navigator.serviceWorker.ready;
    const subscription = await registration.pushManager.subscribe({
      userVisibleOnly: true,  // must show notification (no silent pushes)
      applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY)
    });
    await sendToServer(subscription.toJSON());

  Step 6-7: SW handles push event
    // sw.js
    self.addEventListener('push', event => {
      const data = event.data ? event.data.json() : {};
      event.waitUntil(
        self.registration.showNotification(data.title, {
          body: data.body,
          icon: '/icons/notification.png',
          badge: '/icons/badge.png',
          data: data.url, // for click handling
        })
      );
    });
    
    self.addEventListener('notificationclick', event => {
      event.notification.close();
      event.waitUntil(
        clients.openWindow(event.notification.data)
      );
    });

7. BACKGROUND SYNC
────────────────────────────────────────────────────────────────────────────────

  Defers actions until user has stable internet connectivity.
  Use case: sending messages, form submissions while offline.

    // Register sync from page:
    const registration = await navigator.serviceWorker.ready;
    await registration.sync.register('outbox-sync');

    // SW handles sync when online:
    self.addEventListener('sync', event => {
      if (event.tag === 'outbox-sync') {
        event.waitUntil(sendPendingMessages());
      }
    });
    
    async function sendPendingMessages() {
      const messages = await getFromIndexedDB('outbox');
      for (const msg of messages) {
        await fetch('/api/messages', { method: 'POST', body: JSON.stringify(msg) });
        await deleteFromIndexedDB('outbox', msg.id);
      }
    }

8. SW COMMUNICATION WITH PAGES
────────────────────────────────────────────────────────────────────────────────

  Page → SW (postMessage):
    navigator.serviceWorker.controller.postMessage({ type: 'CACHE_REFRESH' });

  SW → All Clients:
    self.addEventListener('message', async event => {
      const clients = await self.clients.matchAll();
      clients.forEach(client => client.postMessage({ type: 'UPDATE_AVAILABLE' }));
    });

  SW → Specific Client:
    event.source.postMessage({ reply: 'done' });

  MessageChannel (bidirectional):
    // page
    const mc = new MessageChannel();
    mc.port1.onmessage = (e) => console.log(e.data);
    navigator.serviceWorker.controller.postMessage('ping', [mc.port2]);
    // sw.js
    self.addEventListener('message', e => e.ports[0].postMessage('pong'));

9. PROGRESSIVE WEB APPS (PWA)
────────────────────────────────────────────────────────────────────────────────

  Service Workers are a key pillar of PWAs:
  
  PWA Requirements:
    ✓ Service Worker registered
    ✓ HTTPS
    ✓ Web App Manifest (manifest.json)
    ✓ Responsive design
    ✓ Works offline (cached app shell)

  Web App Manifest:
    {
      "name": "My App",
      "short_name": "App",
      "start_url": "/",
      "display": "standalone",
      "background_color": "#ffffff",
      "theme_color": "#000000",
      "icons": [
        { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
        { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
      ]
    }

  Workbox (Google):
    Library for SW caching strategies.
    Handles cache versioning, strategies, precaching, runtime caching.
    
    import { registerRoute } from 'workbox-routing';
    import { StaleWhileRevalidate } from 'workbox-strategies';
    
    registerRoute(
      ({ url }) => url.pathname.startsWith('/api/'),
      new StaleWhileRevalidate()
    );

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is a Service Worker?
A: A JS file running in a separate worker thread (no DOM access) that acts
   as a proxy between the browser and network. It can intercept fetch
   requests, serve from cache, enable offline support, receive push
   notifications, and run background sync. Requires HTTPS.

Q: What is the Service Worker lifecycle?
A: Register → Download → Install (cache assets) → Waiting (until old
   SW-controlled pages close) → Activate (cleanup old caches) → Active
   (controls pages, handles fetch/push/sync events). Self.skipWaiting()
   skips waiting; clients.claim() takes over existing pages immediately.

Q: What is the difference between Cache-First and Network-First strategies?
A: Cache-First: return cached version immediately, fall back to network
   if not cached. Best for static assets. Network-First: fetch from
   network first, fall back to cache if offline. Best for frequently
   updated API data. Stale-While-Revalidate: return cache immediately,
   update cache from network in background.

Q: How do you implement offline support with a Service Worker?
A: 1) During install, cache the app shell (HTML, CSS, JS, critical assets).
   2) In fetch handler, use Cache-First for static assets, Network-First
   for APIs. 3) In activate, clean up old caches. 4) Optionally add an
   offline fallback page for uncached navigation requests.

Q: What is the difference between Service Workers and Web Workers?
A: Web Workers: for CPU-intensive tasks (no network/cache control, no DOM,
   scoped to one page). Service Workers: persistent network proxy (handles
   fetch, push, sync, shared across all same-origin pages, background capable).

Q: What is Background Sync?
A: SW API that defers actions until a stable internet connection exists.
   Page registers a sync tag, SW handles the 'sync' event when online.
   Use case: sending queued form submissions/messages after being offline.

Q: How does Push Notification work with Service Workers?
A: 1) Request Notification permission. 2) Subscribe to push service via
   pushManager.subscribe (get endpoint + keys). 3) Send subscription to
   your server. 4) Server sends push via push service (FCM/APNs) using
   VAPID keys. 5) Browser wakes up SW → 'push' event → showNotification.

Q: Why do Service Workers require HTTPS?
A: Service Workers intercept ALL network requests — a compromised SW would
   be extremely dangerous (man-in-the-middle). HTTPS ensures the SW file
   itself can't be tampered with in transit. Localhost is exempt for
   development.

Q: What happens if you update your service worker file?
A: Browser downloads the new file. If it differs from the installed version,
   install event fires. New SW enters waiting state (old SW still controls
   open pages). When all old pages are closed, new SW activates. Or use
   skipWaiting() in install to force immediate activation.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • SW = background thread proxy for network requests; no DOM; HTTPS required
  • Lifecycle: Register → Install → Wait → Activate → Active
  • skipWaiting() skips waiting; clients.claim() takes over immediately
  • Caching strategies: Cache-First, Network-First, Stale-While-Revalidate
  • Push notifications: subscribe → send subscription to server → push service → SW push event
  • Background Sync: defer actions until online
  • PWA = SW + Manifest + HTTPS + responsive design
