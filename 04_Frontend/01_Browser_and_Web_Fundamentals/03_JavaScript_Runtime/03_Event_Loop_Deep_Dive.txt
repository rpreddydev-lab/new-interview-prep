1. WHAT IS THE EVENT LOOP?
────────────────────────────────────────────────────────────────────────────────

  The Event Loop is the mechanism that allows JavaScript to perform
  non-blocking operations despite being single-threaded.

  JavaScript is single-threaded:
    - One call stack, one thing at a time
    - Cannot do two things simultaneously
    - But browsers handle async operations (I/O, timers, HTTP) without blocking

  How it works:
    The Event Loop continuously checks if the call stack is empty,
    and if so, picks the next task from the queues and executes it.

  The complete picture:

    ┌─────────────────────────────────────────────────┐
    │          JAVASCRIPT RUNTIME (Browser)           │
    │                                                 │
    │  ┌─────────────────┐   ┌────────────────────┐  │
    │  │   Call Stack    │   │    Web APIs        │  │
    │  │                 │   │  (setTimeout,      │  │
    │  │  [main()]       │   │   fetch, DOM events│  │
    │  │  [callback()]   │   │   setInterval...)  │  │
    │  └────────┬────────┘   └──────────┬─────────┘  │
    │           │                       │             │
    │           │     ┌─────────────────┘             │
    │           │     ▼                               │
    │           │  ┌──────────────────────────────┐   │
    │           │  │  Microtask Queue             │   │
    │           │  │  (Promise callbacks,         │   │
    │           │  │   queueMicrotask, MutationOb.)│  │
    │           │  └──────────────────────────────┘   │
    │           │  ┌──────────────────────────────┐   │
    │           │  │  Macrotask Queue (Task Queue) │   │
    │           │  │  (setTimeout, setInterval,   │   │
    │           │  │   I/O callbacks, UI events)  │   │
    │           │  └──────────────────────────────┘   │
    │           │            │                        │
    │           └────────────┘                        │
    │              Event Loop                         │
    └─────────────────────────────────────────────────┘

2. EVENT LOOP ALGORITHM (STEP BY STEP)
────────────────────────────────────────────────────────────────────────────────

  The Event Loop runs the following cycle:

  1. Execute the current TASK (top of call stack)
     - Initial script execution is one task
     - Event callbacks are tasks
     - Timer callbacks are tasks

  2. When call stack is EMPTY:
     a. Drain the MICROTASK QUEUE:
        - Execute ALL microtasks (until queue is empty)
        - If a microtask adds more microtasks, process those too
        - NEVER leave microtask queue partially drained before next macrotask
     b. If rendering is needed (in browsers):
        - Run requestAnimationFrame callbacks
        - Render (style recalc, layout, paint, composite)
        - Run requestIdleCallback (if time remains)
     c. Pick ONE task from MACROTASK QUEUE
        - Execute it completely
     d. Go back to step 2a

  KEY RULE: All microtasks run before the next macrotask and before rendering.

────────────────────────────────────────────────────────────────────────────────
3. TASK (MACROTASK) QUEUE
────────────────────────────────────────────────────────────────────────────────

  Also called: "Task Queue", "Callback Queue", "Message Queue"

  Sources of macrotasks:
    • setTimeout(fn, delay)    — after delay (minimum delay, not guaranteed)
    • setInterval(fn, interval)— recurring
    • setImmediate(fn)         — Node.js only (like setTimeout 0, but after I/O)
    • I/O callbacks            — network response, file system
    • UI Events                — click, keydown, scroll, mousemove
    • postMessage              — cross-frame communication
    • MessageChannel           — structured communication
    • requestAnimationFrame*   — (technically special, before rendering)

  Important setTimeout behavior:
    setTimeout(fn, 0) does NOT run immediately
    Minimum clamp: HTML spec defines 4ms minimum for nested timers (>4 depth)
    Background tabs: timers clamped to ≥1000ms to save battery

  Each iteration of the Event Loop processes EXACTLY ONE macrotask.
  (Microtasks are exhausted between each macrotask)

────────────────────────────────────────────────────────────────────────────────
4. MICROTASK QUEUE
────────────────────────────────────────────────────────────────────────────────

  Sources of microtasks:
    • Promise.then() / catch() / finally()
    • async/await (await suspends, resumes as microtask)
    • queueMicrotask(fn)       — explicit microtask scheduling
    • MutationObserver callbacks
    • process.nextTick (Node.js — runs BEFORE other microtasks!)
    • Object.observe (deprecated)

  Microtask queue is FULLY DRAINED after every task:
    - After the current call stack is clear
    - After every resolved Promise chain step
    - Even if microtasks queue more microtasks!

  Danger of infinite microtask loop:
    function loop() {
      Promise.resolve().then(loop); // keeps adding microtasks
    }
    loop(); // FREEZES the browser! Microtask queue never empties.

5. COMPLETE EXECUTION EXAMPLE
────────────────────────────────────────────────────────────────────────────────

  Code:
    console.log('1');                          // A
    
    setTimeout(() => console.log('2'), 0);    // B
    
    Promise.resolve()
      .then(() => console.log('3'))            // C
      .then(() => console.log('4'));           // D
    
    console.log('5');                          // E

  Trace:
    Execute synchronous code (main task):
      A: console.log('1')   → prints "1"
      B: setTimeout(...)    → schedules in macrotask queue after 0ms
      C: Promise.resolve().then() → schedules C callback in microtask queue
      E: console.log('5')   → prints "5"
    
    Call stack empty → drain microtask queue:
      C: console.log('3')   → prints "3"  → .then() schedules D
      D: console.log('4')   → prints "4"  → microtask queue empty
    
    Pick next macrotask:
      B: console.log('2')   → prints "2"

  Output: 1, 5, 3, 4, 2

6. ADVANCED EXAMPLE: NESTING AND ORDERING
────────────────────────────────────────────────────────────────────────────────

  Code:
    console.log('start');
    
    setTimeout(() => {
      console.log('timeout 1');
      Promise.resolve().then(() => console.log('promise inside timeout'));
    }, 0);
    
    setTimeout(() => {
      console.log('timeout 2');
    }, 0);
    
    Promise.resolve()
      .then(() => console.log('promise 1'))
      .then(() => console.log('promise 2'));
    
    console.log('end');

  Output:
    start
    end
    promise 1
    promise 2
    timeout 1
    promise inside timeout   ← microtask runs BEFORE timeout 2!
    timeout 2

  Why "promise inside timeout" runs before "timeout 2":
    After "timeout 1" task runs, microtask queue is checked.
    The Promise from inside timeout 1 is in microtask queue.
    It runs BEFORE picking the next macrotask (timeout 2).

7. ASYNC/AWAIT AND THE EVENT LOOP
────────────────────────────────────────────────────────────────────────────────

  async/await is syntactic sugar over Promises + generators.
  
  What happens with await:
    async function fetchData() {
      console.log('before await');   // synchronous
      const data = await fetch('/api'); // suspends function
      console.log('after await');    // microtask (when Promise resolves)
    }
    fetchData();
    console.log('after call');

  Execution order:
    "before await"  → synchronous
    "after call"    → synchronous (fetchData suspended, returns Promise)
    (fetch resolves eventually...)
    "after await"   → microtask callback

  Each await point = one microtask boundary:
    async function f() {
      await 1; // schedules rest as microtask
      await 2; // another microtask boundary
      await 3; // another
    }

  Compared to manual Promise chaining:
    async function f() {
      const x = await p1;
      const y = await p2;
      return x + y;
    }
    // Equivalent to:
    function f() {
      return p1.then(x => p2.then(y => x + y));
    }

8. LONG TASKS AND BLOCKING THE EVENT LOOP
────────────────────────────────────────────────────────────────────────────────

  Problem:
    A long synchronous task blocks the event loop.
    No UI updates, no input handling, no network callbacks.
    User sees frozen/unresponsive page.

  Long Task definition:
    A task taking > 50ms is a "Long Task" (PerformanceObserver LongTask API)

  Example of blocking:
    function longTask() {
      const start = Date.now();
      while (Date.now() - start < 2000) {} // blocks for 2 seconds!
    }
    longTask();
    // No UI events, no repaints, no setTimeout callbacks for 2 seconds

  Measuring Long Tasks:
    const observer = new PerformanceObserver(list => {
      list.getEntries().forEach(entry => {
        console.log('Long Task:', entry.duration, 'ms');
      });
    });
    observer.observe({ type: 'longtask', buffered: true });

  Solutions to avoid blocking:

    1. Use Web Workers for CPU-intensive work:
       const worker = new Worker('compute.js');
       worker.postMessage(bigData);
       worker.onmessage = (e) => handleResult(e.data);
       // Main thread stays responsive

    2. Chunk work with setTimeout:
       function processChunk(data, index) {
         // process a batch
         processItems(data.slice(index, index + 100));
         if (index + 100 < data.length) {
           setTimeout(() => processChunk(data, index + 100), 0);
         }
       }

    3. Use requestIdleCallback:
       requestIdleCallback((deadline) => {
         while (deadline.timeRemaining() > 0 && tasks.length > 0) {
           tasks.shift()(); // process tasks while browser is idle
         }
         if (tasks.length > 0) requestIdleCallback(arguments.callee);
       });

    4. Use Scheduler API (scheduler.postTask):
       // Experimental — schedule tasks with priority
       scheduler.postTask(() => doWork(), { priority: 'background' });

9. RENDERING AND THE EVENT LOOP
────────────────────────────────────────────────────────────────────────────────

  Browser rendering is tied to the event loop:
    After each task + microtask drain, browser MAY render a new frame.
    Not every task triggers a render (browser renders at ~60fps = every 16ms)

  Order:
    [Task] → [Microtasks] → [rAF callbacks] → [Render] → [rIC callbacks]
    → [Next Task]

  requestAnimationFrame (rAF):
    - Callbacks run just before rendering (each frame)
    - Guaranteed to run before paint → see updated styles/layout
    - Use for: smooth animations, reading layout before paint

    let id = requestAnimationFrame(callback);
    cancelAnimationFrame(id);

  requestIdleCallback (rIC):
    - Callbacks run during browser idle time (after frame completes)
    - Receives deadline.timeRemaining() (ms until browser needs the main thread)
    - Use for: non-critical background work (analytics, prefetching)

    let id = requestIdleCallback(callback, { timeout: 2000 });
    cancelIdleCallback(id);

10. NODE.JS EVENT LOOP (COMPARISON)
────────────────────────────────────────────────────────────────────────────────

  Node.js event loop has phases (via libuv):
    timers     → setTimeout, setInterval callbacks
    pending    → some I/O callbacks deferred
    idle/prepare → internal
    poll       → retrieve new I/O events; blocking if nothing else
    check      → setImmediate callbacks
    close      → close event callbacks (socket.on('close'))

  Between EACH phase: process.nextTick + Promise microtasks run

  process.nextTick:
    - Runs BEFORE other microtasks (Promise.then)
    - Runs at end of current operation, before continuing to next phase
    - Higher priority than Promise microtasks

  Execution order in Node.js:
    synchronous → process.nextTick → Promise.then → setTimeout/setImmediate

  setImmediate vs setTimeout(0) in Node:
    - In I/O callback: setImmediate ALWAYS before setTimeout(0)
    - Outside I/O context: order non-deterministic (depends on system timing)

11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the Event Loop?
A: A mechanism that allows JS to perform async operations while being
   single-threaded. It monitors the call stack and task queues — when the
   stack is empty, it picks tasks from queues to execute. All microtasks
   are drained after each task (and before rendering).

Q: What is the difference between microtasks and macrotasks?
A: Macrotasks (tasks): setTimeout, setInterval, UI events, I/O — one per
   event loop iteration. Microtasks: Promise callbacks, queueMicrotask,
   MutationObserver — ALL microtasks drain after each task before the
   next macrotask. Microtasks have higher priority.

Q: What will be the output of this code?
   console.log('1');
   setTimeout(() => console.log('2'), 0);
   Promise.resolve().then(() => console.log('3'));
   console.log('4');
A: 1, 4, 3, 2
   "1" and "4" synchronous. Promise microtask ("3") runs before setTimeout
   macrotask ("2").

Q: Can you starve the event loop with Promises?
A: Yes. If microtasks continuously queue new microtasks (infinite Promise
   chains), the macrotask queue and rendering never get a chance to run.
   The browser will freeze. Example: Promise.resolve().then(function loop(){
   return Promise.resolve().then(loop); });

Q: Why does setTimeout(fn, 0) not execute immediately?
A: It schedules a macrotask — it must wait for: 1) current script to finish,
   2) all current microtasks to drain, 3) any rendering needed, THEN
   the timer callback is picked. Also, HTML spec has a minimum 4ms delay
   for nested/repeated timers.

Q: What is requestAnimationFrame and when should you use it?
A: rAF schedules a callback to run just before the next browser paint.
   Use for visual updates (animations, DOM reads before paint). It runs
   after microtasks but before actual rendering, synchronized with
   display refresh rate (~60fps). Better than setTimeout for animations.

Q: How do you prevent long tasks from blocking the UI?
A: 1) Move CPU work to Web Workers (separate thread).
   2) Chunk work with setTimeout(fn, 0) to yield to event loop periodically.
   3) Use requestIdleCallback for non-urgent work.
   4) Use scheduler.postTask with 'background' priority (experimental).

Q: What is the difference between async/await and .then()?
A: Functionally equivalent — async/await is syntactic sugar over Promises.
   Both resume as microtasks when the awaited Promise resolves. async/await
   is more readable for sequential async operations. Each await represents
   a microtask checkpoint (control can yield to other tasks/microtasks).

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Event loop: task → ALL microtasks → render → next task
  • Microtasks (Promise, queueMicrotask): run BEFORE next macrotask and render
  • Macrotasks (setTimeout, events): one per loop iteration
  • Long tasks (>50ms) block UI — use Web Workers or chunking to fix
  • rAF: before rendering (~60fps); rIC: during idle time
  • async/await = syntactic Promise sugar — each await = microtask boundary
  • Never create infinite microtask loops (starves rendering and macrotasks)
================================================================================
