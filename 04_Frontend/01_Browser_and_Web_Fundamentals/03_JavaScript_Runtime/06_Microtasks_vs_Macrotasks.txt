================================================================================
  MICROTASKS vs MACROTASKS — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. OVERVIEW
────────────────────────────────────────────────────────────────────────────────

  JavaScript is single-threaded, using an event loop to handle async operations.
  Async callbacks are queued in two distinct queues:

    MICROTASK QUEUE (a.k.a. "Job Queue"):
      • Higher priority
      • ALL microtasks are drained after each task completes
      • Before any rendering/next macrotask

    MACROTASK QUEUE (a.k.a. "Task Queue"):
      • Lower priority
      • ONE task per event loop turn
      • Browser may render between macrotasks

  Event Loop Algorithm (simplified):
    while (true) {
      task = macrotaskQueue.dequeue();
      task.execute();
      // Drain ALL microtasks
      while (microtaskQueue.length > 0) {
        microtask = microtaskQueue.dequeue();
        microtask.execute();
      }
      // Optional: re-render (if frame due)
    }

────────────────────────────────────────────────────────────────────────────────
2. MICROTASK SOURCES
────────────────────────────────────────────────────────────────────────────────

  • Promise.then() / Promise.catch() / Promise.finally()
  • queueMicrotask(fn)
  • MutationObserver callbacks
  • async/await (each await continuation is a microtask)
  • Node.js: process.nextTick (even higher priority — runs before other microtasks)

    Promise.resolve().then(() => console.log('microtask'));
    queueMicrotask(() => console.log('also microtask'));

  Important: microtasks can starve the event loop!
    function infiniteMicrotask() {
      Promise.resolve().then(infiniteMicrotask); // browser hangs!
    }

────────────────────────────────────────────────────────────────────────────────
3. MACROTASK SOURCES
────────────────────────────────────────────────────────────────────────────────

  • setTimeout(fn, delay)
  • setInterval(fn, delay)
  • setImmediate(fn) — Node.js only
  • I/O callbacks
  • UI rendering events
  • User interaction events (click, keydown, etc.)
  • MessageChannel / postMessage
  • <script> tag execution (initial script run is a macrotask)

    setTimeout(() => console.log('macrotask'), 0);

  Note: setTimeout(fn, 0) still fires AFTER all microtasks.

────────────────────────────────────────────────────────────────────────────────
4. EXECUTION ORDER EXAMPLE
────────────────────────────────────────────────────────────────────────────────

  Example 1 — Basic ordering:

    console.log('1');                           // sync
    
    setTimeout(() => console.log('2'), 0);      // macrotask
    
    Promise.resolve().then(() => console.log('3')); // microtask
    
    queueMicrotask(() => console.log('4'));     // microtask
    
    console.log('5');                           // sync
    
    Output: 1, 5, 3, 4, 2
    
    Explanation:
      - Sync code runs first: 1, 5
      - Then all microtasks: 3, 4
      - Then macrotask: 2

  Example 2 — Nested microtasks:

    Promise.resolve()
      .then(() => {
        console.log('A');
        Promise.resolve().then(() => console.log('B')); // queued during drain
      })
      .then(() => console.log('C'));
    
    Output: A, B, C
    
    Explanation:
      - First, Promise resolves → queue: [A]
      - Run A: A prints, queues B, queues C
      - Queue is now: [B, C]
      - Run B: prints B
      - Run C: prints C

  Example 3 — Mixed macrotasks and microtasks:

    console.log('start');
    
    setTimeout(() => {
      console.log('timeout 1');
      Promise.resolve().then(() => console.log('promise in timeout'));
    }, 0);
    
    setTimeout(() => console.log('timeout 2'), 0);
    
    Promise.resolve().then(() => console.log('promise 1'));
    
    console.log('end');
    
    Output: start, end, promise 1, timeout 1, promise in timeout, timeout 2
    
    Explanation:
      - Sync: start, end
      - Microtasks: promise 1
      - First macrotask: timeout 1 → immediately drains microtasks → promise in timeout
      - Second macrotask: timeout 2

5. async/await AND MICROTASKS
────────────────────────────────────────────────────────────────────────────────

  Every `await` suspends the async function and schedules the continuation
  as a microtask when the awaited Promise resolves.

    async function run() {
      console.log('async start');
      await Promise.resolve();
      console.log('after await'); // scheduled as microtask
      await Promise.resolve();
      console.log('after second await'); // another microtask
    }
    
    console.log('before');
    run();
    console.log('after call');
    
    Output: before, async start, after call, after await, after second await

  Equivalent without async/await:
    console.log('async start');
    Promise.resolve()
      .then(() => {
        console.log('after await');
        return Promise.resolve();
      })
      .then(() => {
        console.log('after second await');
      });

  Nuance with async functions returning non-Promises (ES2020 spec change):
    Previously, async functions wrapping non-Promise values added extra microtask ticks.
    Now, returning a non-thenable resolves immediately — same tick as then callbacks.

────────────────────────────────────────────────────────────────────────────────
6. RENDERING AND THE EVENT LOOP
────────────────────────────────────────────────────────────────────────────────

  Browsers aim for 60fps = 16.67ms per frame.
  Rendering happens between macrotasks (not between microtasks).

  Full event loop frame:
    [Macrotask] → [ALL Microtasks] → [rAF callbacks] → [Render] → [rIC callbacks]

  Implications:
    • DOM mutations in microtasks are batched and applied before render
    • requestAnimationFrame is called once per frame, before paint
    • requestIdleCallback called when browser has spare time

    // This does NOT cause multiple repaints:
    button.style.color = 'red';    // microtask from Promise chain
    button.style.color = 'blue';   // batched: only 'blue' renders
    button.style.color = 'green';

7. COMPARISON TABLE
────────────────────────────────────────────────────────────────────────────────

  ┌────────────────────┬──────────────────────────┬──────────────────────────────┐
  │ Feature            │ Microtask                │ Macrotask                    │
  ├────────────────────┼──────────────────────────┼──────────────────────────────┤
  │ Priority           │ Higher                   │ Lower                        │
  │ Execution          │ All queued, after task   │ One per event loop turn      │
  │ Examples           │ Promise, queueMicrotask  │ setTimeout, setInterval, I/O │
  │ Render between?    │ No (blocks render)       │ Yes (browser can render)     │
  │ Can starve loop?   │ Yes (if infinite chain)  │ No (one per turn)            │
  │ DOM reads in?      │ May get stale layout     │ Gets fresh layout            │
  └────────────────────┴──────────────────────────┴──────────────────────────────┘

8. NODE.JS SPECIFICS
────────────────────────────────────────────────────────────────────────────────

  Node.js adds extra queues to the event loop:
  
  process.nextTick queue:
    • Runs before any microtasks (Promise.then)
    • Even higher priority than Promise microtasks
    • Can starve the loop!
    
    process.nextTick(() => console.log('nextTick'));
    Promise.resolve().then(() => console.log('promise'));
    // Output: nextTick, promise

  setImmediate vs setTimeout(fn, 0) in Node.js:
    • Both are macrotasks
    • Inside I/O callbacks: setImmediate always fires first
    • Outside I/O callbacks: order is non-deterministic (depends on libuv)

  Node.js event loop phases:
    timers → pending callbacks → idle/prepare → poll → check (setImmediate) → close

9. TRICKY INTERVIEW SCENARIOS
────────────────────────────────────────────────────────────────────────────────

  Scenario 1: What is the output?
    setTimeout(() => console.log('A'), 0);
    Promise.resolve()
      .then(() => console.log('B'))
      .then(() => console.log('C'));
    console.log('D');
    
    Answer: D, B, C, A

  Scenario 2: What is the output?
    async function foo() {
      console.log('foo start');
      await null;
      console.log('foo end');
    }
    console.log('1');
    foo();
    console.log('2');
    
    Answer: 1, foo start, 2, foo end

  Scenario 3: Why does this spin indefinitely?
    function flood() {
      queueMicrotask(flood);
    }
    flood();
    
    Answer: Microtask queue is drained fully before moving to next macrotask.
    Adding infinite microtasks never lets the macrotask queue run — the browser
    appears frozen (no rendering, no events).

  Scenario 4: What logs?
    console.log('A');
    setTimeout(() => console.log('B'), 1000);
    setTimeout(() => console.log('C'), 0);
    Promise.resolve().then(() => {
      console.log('D');
      setTimeout(() => console.log('E'), 0);
    });
    console.log('F');
    
    Answer: A, F, D, C, E, B
    (C and E are both timeout 0, but E is queued AFTER D runs)

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between microtasks and macrotasks?
A: Microtasks (Promise.then, queueMicrotask, MutationObserver) run after each
   task, BEFORE the next macrotask and BEFORE any rendering. ALL queued
   microtasks run in one batch. Macrotasks (setTimeout, I/O, UI events) run
   one at a time, with microtask draining between them.

Q: What happens if a microtask schedules another microtask?
A: It gets added to the current microtask queue and is processed in the same
   drain cycle. This means infinite microtask chains starve the event loop,
   preventing rendering and macrotask execution.

Q: Why does Promise.then run before setTimeout even with setTimeout(fn, 0)?
A: The event loop drains the ENTIRE microtask queue after the current task
   finishes, before picking up any macrotask. setTimeout callbacks are
   macrotasks, so they always run after all pending microtasks.

Q: How does async/await interact with the microtask queue?
A: Each `await` suspends the function and schedules the rest as a microtask
   when the awaited Promise resolves. Essentially, code after `await` runs
   as a Promise.then callback.

Q: What is queueMicrotask?
A: A global function that schedules a callback as a microtask. It's similar
   to Promise.resolve().then(fn) but more explicit and direct. Use it when
   you need to schedule work after the current execution but before the next
   macrotask, without creating a Promise.

Q: Does rendering happen between microtasks?
A: No. The browser doesn't render between microtasks — the entire microtask
   queue is drained first. Rendering happens after the microtask queue is
   empty (when a new frame is due). This is why mutating the DOM in a chain
   of Promises results in only one repaint.

Q: Explain process.nextTick in Node.js vs Promise microtasks.
A: process.nextTick queue is processed before Promise microtasks (before the
   microtask queue). Both are higher priority than macrotasks. nextTick can
   starve the event loop if used recursively. The spec-compliant order is:
   nextTick queue → microtask queue → macrotask queue.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • Microtasks: ALL drained before next macrotask or render
  • Sources: Promise.then, queueMicrotask, MutationObserver, async/await
  • Macrotasks: ONE per loop turn; browser may render between them
  • Sources: setTimeout, setInterval, I/O callbacks, UI events
  • Infinite microtask chains starve the event loop
  • Rendering: [Macrotask] → [Microtasks] → [rAF] → [Render] → [rIC]
  • Node.js: process.nextTick > microtasks > macrotasks
================================================================================
