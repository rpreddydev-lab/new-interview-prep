  CRITICAL RENDERING PATH — Complete Interview Reference
================================================================================

────────────────────────────────────────────────────────────────────────────────
1. WHAT IS THE CRITICAL RENDERING PATH?
────────────────────────────────────────────────────────────────────────────────

  The Critical Rendering Path (CRP) is the sequence of steps the browser
  takes to convert HTML, CSS, and JavaScript into pixels on the screen
  for the FIRST paint.

  "Critical" = the minimum work required before the user sees ANYTHING

  Steps:
    1. Receive HTML bytes
    2. Parse HTML → DOM (incrementally)
    3. Parse CSS → CSSOM (blocking)
    4. Execute JavaScript (may block HTML parsing)
    5. DOM + CSSOM → Render Tree
    6. Layout (compute geometry)
    7. Paint (draw pixels)
    → FIRST PAINT (FP) / FIRST CONTENTFUL PAINT (FCP)

  Key metrics tied to CRP:
    • FP   — First Paint (any pixel drawn)
    • FCP  — First Contentful Paint (text, image, or non-white canvas)
    • LCP  — Largest Contentful Paint (largest visible element rendered)
    • TTI  — Time to Interactive (fully interactive)
    • TBT  — Total Blocking Time (sum of long tasks before TTI)

────────────────────────────────────────────────────────────────────────────────
2. RENDER-BLOCKING RESOURCES
────────────────────────────────────────────────────────────────────────────────

  Resources that BLOCK the browser from rendering:

  CSS (render-blocking by design):
    • Every <link rel="stylesheet"> in <head> blocks rendering
    • Browser must download AND parse all CSS before first paint
    • Reason: needs complete CSSOM to compute styles

  JavaScript (parser-blocking and potentially render-blocking):
    • Synchronous <script> tags BLOCK HTML parsing
    • Since CSS blocks script execution, and scripts block parsing:
      CSS → blocks script → blocks parsing → delays CRP

  Non-blocking JavaScript:
    <script defer>   → Downloads parallel, executes after parse
    <script async>   → Downloads parallel, executes when ready (unordered)
    <script type="module"> → Deferred by default

  Non-blocking CSS:
    <link rel="stylesheet" media="print">  → Only loads for print (not blocking screen render)
    <link rel="preload" as="style">        → Preload without render-blocking (then apply)

3. CRP OPTIMIZATION STRATEGIES
────────────────────────────────────────────────────────────────────────────────

  3.1 MINIMIZE CRITICAL RESOURCES
    Critical resource = resource required for first paint
    
    • Inline critical CSS (above-the-fold styles) in <style> tag
    • Load non-critical CSS asynchronously:
        <link rel="preload" as="style" href="non-critical.css" onload="this.rel='stylesheet'">
    • Defer non-critical JavaScript
    • Remove unused CSS/JS

  3.2 MINIMIZE CRITICAL PATH LENGTH
    Critical path length = number of round trips (network RTTs) required
    
    • Reduce number of blocking resources
    • Combine files (fewer requests)
    • Use HTTP/2 multiplexing (multiple requests in one connection)
    • Preload key resources

  3.3 MINIMIZE CRITICAL BYTES
    • Minify HTML, CSS, JS
    • Compress with gzip/Brotli
    • Remove unused code (tree shaking)
    • Optimize images

  3.4 INLINE CRITICAL CSS
    Identify styles needed for above-the-fold content.
    Put them in a <style> block in <head>.
    Load full stylesheet asynchronously.
    
    Tools: Critical (npm), PurgeCSS, Chrome Coverage tab

  3.5 PRELOAD IMPORTANT RESOURCES
    <link rel="preload" href="fonts/hero.woff2" as="font" crossorigin>
    <link rel="preload" href="hero-image.jpg" as="image">
    <link rel="preload" href="critical.js" as="script">
    
    Preload tells browser to fetch a resource early without blocking rendering.
    Use for: web fonts, hero images, late-discovered critical resources.

  3.6 PREFETCH (lower priority):
    <link rel="prefetch" href="next-page.html">
    Browser fetches in idle time for future navigations.
    Lower priority than preload.

  3.7 PRECONNECT:
    <link rel="preconnect" href="https://fonts.googleapis.com">
    Establishes TCP/TLS connection to third-party domain early.
    Saves 100-500ms when resources from that domain are later needed.

  3.8 DNS-PREFETCH:
    <link rel="dns-prefetch" href="//analytics.example.com">
    Performs DNS lookup early. Falls back gracefully on older browsers.

5. NETWORK WATERFALL AND CRP ANALYSIS
────────────────────────────────────────────────────────────────────────────────

  Typical unoptimized CRP waterfall:
    0ms    → HTML request starts
    200ms  → HTML received, parsing begins
    250ms  → CSS discovered, download starts (BLOCKS rendering)
    600ms  → CSS fully downloaded + parsed → CSSOM built
    650ms  → <script> discovered, download starts (BLOCKS parsing)
    1000ms → JS downloaded + executed
    1050ms → DOM construction complete
    1080ms → Render Tree + Layout + Paint
    → FCP at ~1080ms

  Optimized CRP waterfall:
    0ms    → HTML request + preload hints for CSS/fonts
    200ms  → HTML received, parsing begins
             CSS preloaded → arrives sooner
    250ms  → Critical CSS inlined → no blocking external CSS!
    260ms  → DOM construction + CSSOM from inline styles
    280ms  → First Paint
    500ms  → Deferred JS downloads in parallel
    700ms  → Deferred JS executes (after DOM ready)
    → FCP at ~280ms (4x faster)

6. BROWSER EVENTS AND CRP COMPLETION
────────────────────────────────────────────────────────────────────────────────

  DOMContentLoaded (DCL):
    - Fires when HTML parsing is COMPLETE and deferred scripts have executed
    - Does NOT wait for images, stylesheets, subframes
    - JS can safely query DOM at this point
    - In DevTools: blue vertical line in network/performance waterfall

    document.addEventListener('DOMContentLoaded', () => {
      // DOM ready, no images/CSS loaded yet
    });

  load (window.onload):
    - Fires when ALL resources are loaded (images, fonts, CSS, iframes)
    - Represents fully-loaded page
    - In DevTools: red vertical line

    window.addEventListener('load', () => {
      // Everything loaded
    });

  Relationship to blocking resources:
    DCL is delayed by: synchronous scripts, CSS that blocks scripts
    DCL is NOT delayed by: async scripts, images, fonts (normally)
    DCL IS delayed by defer scripts (they run just before DCL fires)

7. WEB PERFORMANCE METRICS (CORE WEB VITALS)
────────────────────────────────────────────────────────────────────────────────

  Core Web Vitals (Google ranking signal since 2021):

    LCP — Largest Contentful Paint
      Measures: Loading performance
      Target:   ≤ 2.5s (good), ≤ 4.0s (needs improvement), > 4.0s (poor)
      What:     Largest image or text block visible in viewport
      Common causes of poor LCP:
        - Slow server response times
        - Render-blocking CSS/JS
        - Slow image loading (large unoptimized images)
        - Client-side rendering delay

    FID — First Input Delay (being replaced by INP)
      Measures: Interactivity (responsiveness to first interaction)
      Target:   ≤ 100ms (good)
      What:     Time from first user input to browser response
      
    INP — Interaction to Next Paint (replaced FID in 2024)
      Measures: All interactions, not just first
      Target:   ≤ 200ms (good)
      
    CLS — Cumulative Layout Shift
      Measures: Visual stability (unexpected layout shifts)
      Target:   ≤ 0.1 (good)
      What:     Sum of unexpected layout shift scores during page lifetime
      Common causes:
        - Images without width/height attributes
        - Dynamic content insertion above existing content
        - Web fonts causing FOIT/FOUT
        - Animations that shift layout

  Other Important Metrics:
    TTFB — Time To First Byte (server responsiveness)
    FCP  — First Contentful Paint (user sees content)
    TTI  — Time To Interactive (can reliably respond to interactions)
    TBT  — Total Blocking Time (main thread blocked > 50ms tasks)
    SI   — Speed Index (how quickly content is visually populated)

8. FONT LOADING AND CRP
────────────────────────────────────────────────────────────────────────────────

  Web Fonts and CRP:
    Fonts are discovered late (after CSS is parsed, during styling)
    Fonts block text rendering by default

  FOIT (Flash of Invisible Text):
    - Browser hides text while font loads
    - Default in Chrome, Safari

  FOUT (Flash of Unstyled Text):
    - Browser shows fallback font, then swaps to web font
    - Default in Firefox

  font-display property:
    font-display: auto     → Browser default (usually FOIT)
    font-display: block    → FOIT (short block period)
    font-display: swap     → FOUT (instant fallback, swap when ready)
    font-display: fallback → Short block, then swap; no swap after 3s
    font-display: optional → Short block, swap only if font ready in time

  Recommended:
    font-display: swap for most text
    font-display: optional for non-critical decorative fonts

  Font Preloading:
    <link rel="preload" href="/fonts/roboto.woff2" as="font"
          type="font/woff2" crossorigin>
    Preloads font so it's ready when CSS needs it (reduces FOIT/FOUT)

9. IMAGE OPTIMIZATION AND CRP
────────────────────────────────────────────────────────────────────────────────

  Images don't block CRP (non-critical resources) but affect:
    - LCP (Largest Contentful Paint)
    - CLS (if no dimensions specified)
    - Overall page weight

  Best Practices:
    1. Always specify width and height:
       <img width="800" height="600" src="hero.jpg">
       Reserves space → prevents CLS

    2. Lazy loading:
       <img loading="lazy" src="below-fold.jpg">
       Defers loading until near viewport

    3. Modern formats:
       WebP: ~30% smaller than JPEG
       AVIF: ~50% smaller than JPEG
       <picture>
         <source srcset="image.avif" type="image/avif">
         <source srcset="image.webp" type="image/webp">
         <img src="image.jpg" alt="...">
       </picture>

    4. Responsive images:
       <img srcset="small.jpg 480w, medium.jpg 800w, large.jpg 1200w"
            sizes="(max-width: 600px) 480px, 800px" src="medium.jpg">

    5. Preload hero image:
       <link rel="preload" as="image" href="hero.jpg">

10. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: What is the Critical Rendering Path?
A: The sequence of steps the browser takes to convert HTML/CSS/JS into
   pixels for the first paint: receive HTML → parse DOM → parse CSS (CSSOM)
   → execute JS → build render tree → layout → paint. Optimizing CRP
   improves FCP and LCP scores.

Q: What are render-blocking resources?
A: Resources that prevent the browser from performing the first paint.
   CSS is always render-blocking (need complete CSSOM). Synchronous
   <script> blocks HTML parsing (which delays CRP). Optimize by:
   inlining critical CSS, using async/defer for scripts, preloading fonts.

Q: What is the difference between DOMContentLoaded and load event?
A: DOMContentLoaded fires when HTML is fully parsed and deferred scripts
   have run — DOM is ready, but images/CSS not necessarily loaded.
   load fires when ALL page resources (images, fonts, CSS, iframes) are
   fully loaded.

Q: What is preload and when should you use it?
A: <link rel="preload"> tells the browser to fetch a resource at high
   priority early in the CRP without blocking rendering or waiting for
   HTML parsing to discover it. Use for: web fonts, hero images, critical
   scripts not in <head>. Don't preload everything — it competes with
   critical resources.

Q: What is the difference between preload, prefetch, and preconnect?
A: preload: high-priority fetch for current page resource.
   prefetch: low-priority fetch for likely future navigation resource.
   preconnect: establish TCP/TLS connection to third-party domain early.
   dns-prefetch: DNS lookup only (cheaper, broader browser support).

Q: What are Core Web Vitals?
A: LCP (Largest Contentful Paint ≤ 2.5s — loading speed),
   INP (Interaction to Next Paint ≤ 200ms — responsiveness),
   CLS (Cumulative Layout Shift ≤ 0.1 — visual stability).
   Used by Google as ranking signals since 2021.

Q: How do you fix CLS (Cumulative Layout Shift)?
A: 1) Always specify width/height on images/videos.
   2) Reserve space for dynamic content (skeleton screens, min-height).
   3) Use font-display: swap with font-size-adjust for font swaps.
   4) Avoid inserting content above existing content (banner above text).
   5) Use transform animations instead of layout-shifting properties.

Q: How do you optimize LCP (Largest Contentful Paint)?
A: 1) Preload the hero image: <link rel="preload" as="image">.
   2) Use modern image formats (WebP/AVIF). 3) Optimize server TTFB.
   4) Eliminate render-blocking resources. 5) Lazy load below-fold images.
   6) Use a CDN for static assets. 7) Inline critical CSS.

Q: What is FOIT and how do you prevent it?
A: Flash of Invisible Text — browser hides text while a web font loads.
   Prevent with font-display: swap (shows fallback font immediately)
   and <link rel="preload"> to load fonts earlier.

================================================================================
  KEY TAKEAWAYS
================================================================================
  • CRP: HTML parse → CSSOM → JS execute → Render Tree → Layout → Paint
  • CSS = render-blocking; sync scripts = parser-blocking
  • Optimize: inline critical CSS, async/defer scripts, preload fonts/images
  • preload = current page (high priority); prefetch = future page (low priority)
  • Core Web Vitals: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1
  • DOMContentLoaded = DOM ready; load = all resources loaded
  • font-display: swap prevents FOIT
