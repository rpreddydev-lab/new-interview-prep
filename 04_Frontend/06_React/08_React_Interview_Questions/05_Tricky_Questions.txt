Q1: What does this component render?
  function App() {
    const [count, setCount] = useState(0);
    console.log('render', count);
    return <button onClick={() => setCount(0)}>Click</button>;
  }
  // First click: count is 0, setCount(0) is called
A: React bails out if new state === current state (Object.is comparison).
   setState(0) when state is already 0 = no re-render. The console.log
   runs once on mount, but NOT on button clicks because state doesn't change.

Q2: What is the output?
  function Counter() {
    const [count, setCount] = useState(0);
    function handleClick() {
      setCount(count + 1);
      setCount(count + 1);
      setCount(count + 1);
    }
    return <button onClick={handleClick}>{count}</button>;
  }
A: After click, count = 1 (NOT 3). All three calls use the same stale
   closure value (count = 0). All call setCount(1).
   Fix: setCount(c => c + 1) × 3 = count becomes 3.

Q3: What is the output?
  function App() {
    const [items, setItems] = useState([1, 2, 3]);
    function addItem() {
      items.push(4);          // direct mutation!
      setItems(items);        // same reference
    }
    return <button onClick={addItem}>{items.length}</button>;
  }
A: The displayed length NEVER updates. items.push(4) mutates the array in place.
   setItems receives the same array reference (Object.is = true) → React
   bails out (no re-render). Fix: setItems([...items, 4]).

Q4: What is the danger with this code?
  function Timer() {
    const [count, setCount] = useState(0);
    useEffect(() => {
      const id = setInterval(() => {
        setCount(count + 1);  // stale closure!
      }, 1000);
      return () => clearInterval(id);
    }, []);  // empty deps
    return <div>{count}</div>;
  }
A: count is captured at 0 and never updates (stale closure). The timer
   always sets count to 0 + 1 = 1. It never goes above 1.
   Fix: setCount(c => c + 1) — functional updater doesn't need the dep.
   OR add count to the dep array (interval recreates on every change).

Q5: What problem does this code have?
  useEffect(() => {
    fetchUser(userId).then(data => setUser(data));
  }, [userId]);
A: Race condition. If userId changes quickly (A → B), two requests are
   in flight. If B resolves before A, user state = B's data. Then A
   resolves and overwrites with A's stale data. Fix: use AbortController
   or track which request is the current one.
   
  Fixed:
  useEffect(() => {
    let cancelled = false;
    fetchUser(userId).then(data => { if (!cancelled) setUser(data); });
    return () => { cancelled = true; };
  }, [userId]);

Q6: Why does this cause a bug?
  function Parent() {
    const [count, setCount] = useState(0);
    function Child() {   // defined INSIDE Parent!
      return <div>Child</div>;
    }
    return (
      <div>
        <button onClick={() => setCount(c => c + 1)}>{count}</button>
        <Child />
      </div>
    );
  }
A: Child is recreated as a NEW function type on every render of Parent.
   React sees a different component type and unmounts/remounts Child on
   every render. Any state inside Child is lost. Fix: define Child OUTSIDE Parent.

Q7: What is "0" rendered as in JSX?
  function App() {
    const count = 0;
    return <div>{count && <p>Items: {count}</p>}</div>;
  }
A: Renders the number 0 to the screen! This is the famous && gotcha.
   0 is falsy, so count && <p>... evaluates to 0 (not false).
   React renders 0 as text "0". Fix: use a ternary:
   {count > 0 ? <p>Items: {count}</p> : null}
   OR convert to boolean: {!!count && <p>Items: {count}</p>}

Q8: What does this render?
  function App() {
    return (
      <div>
        {false}
        {null}
        {undefined}
        {0}       ← DIFFERENT from the others
        {NaN}     ← DIFFERENT from the others
      </div>
    );
  }
A: false, null, and undefined render NOTHING. But 0 renders "0" and
   NaN renders "NaN" as text. Only explicitly falsy primitives false/null/undefined
   are ignored by React's renderer. Numeric 0 is a valid renderable value.

Q9: What is the issue with using Math.random() as a key?
  items.map(item => <Item key={Math.random()} item={item} />)
A: Math.random() generates a new key on every render. React sees all items
   as new every time, causing full unmount/remount of every item — losing all
   local state, unnecessary DOM operations, and no animation transitions.
   Always use stable, unique identifiers (item.id) as keys.

TRICKY HOOKS QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q10: What is wrong with this code?
  function App({ userId }) {
    if (userId) {
      const [user, setUser] = useState(null);  // ❌ conditional hook!
    }
    ...
  }
A: Hooks must be called unconditionally and in the same order. A conditional
   hook call violates the Rules of Hooks. React will throw an error.
   Fix: always call the hook, use enabled/conditional logic inside the effect.

Q11: Why does useEffect run twice on mount in development?
A: React 18 StrictMode double-invokes effects to detect side effects in the
   render phase (mounts → unmounts → mounts again). This ONLY happens in
   development. It helps identify missing cleanup functions and non-idempotent
   effects. In production, effects run once.

Q12: What is the difference between useRef and a module-level variable?
A: A module-level variable is shared across ALL instances of a component.
   useRef creates a ref per component INSTANCE. If you have 3 Counters,
   each gets its own ref; they share a module-level variable.
   Use useRef for per-instance mutable values.

Q13: What happens when you call setState during render?
  function BadComponent() {
    const [count, setCount] = useState(0);
    setCount(1);  // during render!
    return <div>{count}</div>;
  }
A: React detects the state update during render and immediately re-renders
   the same component. If the condition doesn't prevent the setState from
   running again (e.g., setCount(1) always runs), this causes infinite loops.
   Only call setState during event handlers or useEffect, never unconditionally
   during render.

Q14: Will React.memo work here?
  function Parent() {
    const handleClick = () => console.log('click');  // new ref every render
    return <MemoChild onClick={handleClick} />;
  }
  const MemoChild = React.memo(({ onClick }) => <button onClick={onClick} />);
A: NO. handleClick is created inline, so it's a new function reference on
   every Parent render. MemoChild sees a changed prop and re-renders anyway.
   Fix: const handleClick = useCallback(() => console.log('click'), []);

Q15: Why might useMemo cause slower performance?
A: useMemo adds the overhead of: checking dependency equality + storing the
   memoized value. For CHEAP computations, this overhead exceeds the saved
   computation. useMemo also "captures" variables in a closure, adding memory
   pressure. Profile first, memoize only what's actually expensive.

Q16: Is this an infinite loop? Why or why not?
  const [data, setData] = useState(null);
  useEffect(() => {
    setData({ result: 42 });
  }, []);
A: NO — not infinite. The empty dependency array ensures the effect runs
   only once (on mount). setData updates state → re-render → effect does NOT
   run again because deps didn't change. If [data] were in the deps array, it
   WOULD be infinite: effect runs → setData → data changes → effect runs again.

Q17: What happens if two sibling components dispatch the same Redux action?
A: Both dispatches are processed sequentially by the reducer. The store state
   updates twice. All Redux subscribers (useSelector) check if their selected
   value changed and re-render if needed. There's no conflict — Redux is
   synchronous and processes one action at a time.
