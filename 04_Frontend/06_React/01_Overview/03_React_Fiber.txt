1. WHAT IS REACT FIBER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React Fiber is the complete internal rewrite of React's reconciliation engine,
introduced in React 16 (2017). It replaced the old "Stack Reconciler."

The name "Fiber" refers to the new data structure — a fiber is a unit of work
that represents a component in the tree.

Goals of Fiber:
  1. Enable incremental rendering — split rendering work into chunks
  2. Allow pausing and resuming work
  3. Enable prioritization of different types of updates
  4. Support Concurrent Mode (React 18)
  5. Better error handling (Error Boundaries)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. THE PROBLEM WITH THE OLD STACK RECONCILER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The old reconciler (React 15 and earlier) was synchronous and recursive:
  - It walked the component tree recursively using the call stack
  - Once started, it COULD NOT be interrupted
  - If a render took 200ms, the browser was BLOCKED for 200ms
  - No user input, no animations, nothing — completely janky

Problem example:
  A huge list of 10,000 items being sorted and re-rendered:
  - Old: Browser freezes for 300ms (dropped frames, jank)
  - New (Fiber): Work split into small chunks, browser can process input
    between chunks, UI stays responsive

Why recursion is the problem:
  - Call stack grows as you descend the tree
  - No way to pause mid-recursion and yield to the browser
  - JavaScript is single-threaded; long synchronous work blocks everything

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. WHAT IS A FIBER NODE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Fiber is a JavaScript object that represents a unit of work (one component).
It holds:

  {
    type,           // Component function or class, or DOM element string ('div')
    key,            // Key for reconciliation
    stateNode,      // Reference to real DOM node or class instance
    child,          // First child fiber
    sibling,        // Next sibling fiber
    return,         // Parent fiber (called 'return' because we return UP to it)
    pendingProps,   // Props for this render
    memoizedProps,  // Props from last committed render
    memoizedState,  // State after last committed render
    updateQueue,    // Queue of state updates
    effectTag,      // Type of side effect (PLACEMENT, UPDATE, DELETION)
    alternate,      // Pointer to the "other" fiber tree (current ↔ work-in-progress)
    lanes,          // Priority lanes
  }

The fiber tree mirrors the component tree. Instead of a recursive call stack,
React uses an explicit linked list of fiber objects.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. THE FIBER TREE STRUCTURE (LINKED LIST)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React maintains TWO fiber trees simultaneously:
  1. CURRENT TREE:   The tree that's currently rendered in the DOM
  2. WORK-IN-PROGRESS (WIP) TREE: The new tree being built during re-render

They are connected via the 'alternate' pointer.

  App ──────────────────────────────────────────────────────────────────
   │ child
   ▼
  Header ──── sibling ──► Main ──── sibling ──► Footer
   │ child                │ child
   ▼                      ▼
  NavBar                 Sidebar ──── sibling ──► Content

Traversal order (DFS with iterative approach):
  1. Visit node (beginWork)
  2. Go to child if it exists
  3. If no child, perform completions (completeWork)
  4. Go to sibling if it exists
  5. Return to parent (via 'return' pointer)
  6. Repeat

This is the "render phase" — building the WIP tree, computing diffs.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. TWO PHASES OF FIBER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PHASE 1 — RENDER PHASE (asynchronous, interruptible):
  - React traverses the component tree
  - Calls component functions / render methods
  - Builds the work-in-progress fiber tree
  - Computes diffs (reconciliation)
  - Marks fibers with effects (what needs to change in DOM)
  - Can be PAUSED, INTERRUPTED, ABORTED, RESUMED
  - No DOM mutations happen here
  - Must be pure (no observable side effects)
  - beginWork() and completeWork() happen here

PHASE 2 — COMMIT PHASE (synchronous, cannot be interrupted):
  - React walks the effect list
  - Applies all DOM mutations in one go
  - Runs getSnapshotBeforeUpdate() (class components)
  - Applies DOM changes
  - Runs useLayoutEffect (synchronously after DOM mutation, before paint)
  - Browser paints the screen
  - Runs useEffect (asynchronously after paint)
  - Cannot be paused — ensures DOM is consistent

6. PRIORITY SCHEDULING WITH LANES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Fiber introduced a priority system for rendering work. React 18 uses "Lanes"
(a bitmask-based priority system) replacing the older "expiration time" model.

Priority levels (high to low):
  1. SyncLane          — Synchronous (legacy mode or flushSync)
  2. InputContinuousLane — User input events (click, keypress, mousemove)
  3. DefaultLane       — Normal updates (setState from event handlers)
  4. TransitionLane    — useTransition / startTransition updates (low priority)
  5. IdleLane          — Lowest priority (idle callbacks)
  6. OffscreenLane     — Invisible/hidden content (Suspense, offscreen)

How scheduling works:
  1. Update triggers, assigned a lane/priority
  2. React schedules work via the Scheduler package
  3. High priority work can INTERRUPT low priority work
  4. React uses MessageChannel (or setTimeout fallback) to yield to the browser
     between chunks of work

  Example:
    User types (high priority) while a list is filtering (low priority):
    → React pauses the filter render
    → Processes the keypress immediately
    → Resumes the filter render
    → User never sees lag in the input field

7. DOUBLE BUFFERING (CURRENT vs WORK-IN-PROGRESS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React maintains two trees simultaneously:
  - CURRENT TREE: reflects what's currently on the screen
  - WORK-IN-PROGRESS (WIP) TREE: the tree being built for the next render

Each fiber in the current tree has an 'alternate' pointer to its WIP counterpart.

When WIP is fully built and ready to commit:
  - React flips the "current" pointer to point to the WIP tree
  - The old current tree becomes the new alternate (for reuse next time)

This is called "double buffering" (similar to GPU rendering):
  - The user always sees a fully consistent state (current tree)
  - No partial/half-rendered states are visible during the render phase

8. FIBER AND CONCURRENT FEATURES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Fiber laid the groundwork for Concurrent Mode (stable in React 18):

  useTransition:
    const [isPending, startTransition] = useTransition();
    startTransition(() => {
      setSearchQuery(value); // low-priority update
    });
    // React can interrupt this to process urgent updates

  useDeferredValue:
    const deferredQuery = useDeferredValue(query);
    // deferredQuery lags behind; React processes urgent updates first

  Suspense (for data fetching):
    React can "suspend" rendering of a component (throw a Promise)
    and show a fallback while waiting, resuming once data is ready.

  Offscreen Component (future):
    Pre-render hidden components without blocking the visible UI.

9. EFFECTS IN FIBER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

During the render phase, React marks fibers with effect tags:
  - PLACEMENT   → New node needs to be inserted into DOM
  - UPDATE      → Existing node needs attributes/text updated
  - DELETION    → Node needs to be removed from DOM
  - PASSIVE     → useEffect needs to run
  - LAYOUT      → useLayoutEffect needs to run

React builds an "effect list" — a linked list of fibers with effects.
During commit phase, React walks this list and applies all effects.

10. COMMON INTERVIEW QUESTIONS ON REACT FIBER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is React Fiber?
A: React Fiber is the rewritten reconciliation engine introduced in React 16.
   It replaced the synchronous stack reconciler with an asynchronous, interruptible
   architecture. A "fiber" is a JS object representing a unit of work (one component).
   Fiber enables incremental rendering, prioritization, and Concurrent Mode.

Q: Why was React Fiber introduced?
A: The old reconciler was synchronous and could not be interrupted. For large,
   complex UIs, this caused the browser to block (jank). Fiber allows rendering
   work to be split, paused, and prioritized, keeping the UI responsive.

Q: What are the two phases of React Fiber?
A: 1. Render phase (asynchronous, interruptible): builds WIP fiber tree, diffs.
   2. Commit phase (synchronous, uninterruptible): applies DOM changes, runs effects.

Q: What is the difference between the render phase and commit phase?
A: Render phase is pure (no side effects, can be interrupted). Commit phase
   applies real DOM mutations and runs effects (useLayoutEffect, useEffect).
   The commit phase cannot be paused because partial DOM updates would be visible.

Q: What is double buffering in React?
A: React maintains two fiber trees: current (what's on screen) and
   work-in-progress (the new render). When WIP is ready, React swaps them
   atomically. This ensures the user always sees a consistent UI.

Q: How does React prioritize updates?
A: Via a lane-based scheduling system. User interactions (click, keypress) get
   higher priority than transitions (data filtering, search) which get higher
   priority than idle work. Higher priority work can interrupt lower priority renders.

Q: What is the relationship between Fiber and Concurrent Mode?
A: Fiber is the infrastructure that ENABLES Concurrent Mode. Because the render
   phase uses an interruptible linked-list traversal (instead of a recursive call
   stack), React can pause renders to handle urgent work, then resume.

Q: What is a Fiber node's 'alternate' pointer?
A: Each fiber has an alternate pointer to its counterpart in the other tree
   (current ↔ WIP). After a commit, the WIP tree becomes the current tree,
   and its nodes reuse the old current nodes as their new alternates.

Q: Can render phase functions have side effects?
A: No. The render phase can be interrupted and re-run multiple times.
   Side effects in render phase (like fetch calls on each render) would
   execute multiple times unexpectedly. Effects must go in useEffect/useLayoutEffect.
