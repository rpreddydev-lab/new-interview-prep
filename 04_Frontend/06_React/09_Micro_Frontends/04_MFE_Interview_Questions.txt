Q: What are micro-frontends and why would you use them?
A: Micro-frontends apply microservices principles to frontend architecture.
   Instead of one large monolithic SPA, the UI is split into smaller, 
   independently deployable pieces, each owned by a separate team.
   You'd use them when: multiple large teams are working on the same frontend
   and blocking each other on releases; when domain boundaries in the UI are
   clear; when you need to incrementally migrate from a legacy frontend to a
   modern stack; or when different parts of the app have very different release
   cadences. The core benefit is independent deployability — Team A ships
   their feature without waiting for Team B to be ready.

Q: What are the different approaches to integrating micro-frontends?
A: Four main approaches:
   1. Build-time (npm packages): MFEs published as packages, shell installs
      them. Simple but requires shell rebuild to update — defeats independent
      deployment.
   2. Runtime via JavaScript: Shell dynamically loads MFE bundles at runtime
      using Module Federation or single-spa. True independent deployment.
   3. Runtime via iframes: Full isolation but poor UX, performance, and
      accessibility. Hard to share state. Used only when strict isolation
      is required (e.g., third-party widgets).
   4. Server-side composition: Server assembles HTML fragments from multiple
      MFE services. Good for SEO, complex infrastructure.

Q: How do micro-frontends communicate with each other?
A: Options, in order of preference (least to most coupling):
   1. URL / query string — persists across navigation, shareable
   2. Custom events (CustomEvent API) — loose coupling, no shared code needed
   3. Shared state via a utility module — reactive store all MFEs import
   4. Props from shell — shell passes data down to MFEs on mount
   5. Browser storage (localStorage/sessionStorage) — use sparingly, creates coupling
   Best practice: minimize cross-MFE communication; if two pieces of UI need
   to communicate constantly, they probably shouldn't be separate MFEs.

Q: How do you handle CSS conflicts between micro-frontends?
A: Several strategies:
   - CSS Modules: class names are hashed and scoped at build time
   - CSS-in-JS (emotion, styled-components): styles are scoped by default
   - Shadow DOM: complete CSS isolation but limits global styles/fonts
   - BEM + team prefix: .products__card vs .cart__card — naming convention
   - qiankun's CSS sandbox: automatically scopes CSS rules with unique attributes
   Most enterprise projects use CSS Modules or CSS-in-JS as they balance
   isolation and developer experience.

Q: What is the JS sandbox in qiankun and why is it important?
A: The JS sandbox prevents sub-applications from polluting the global window
   object. Without it, if Sub-App A sets window.config = {theme: 'dark'} and
   Sub-App B sets window.config = {theme: 'light'}, they overwrite each other.
   qiankun uses ES6 Proxy to intercept all window reads/writes per sub-app,
   giving each a virtual window. When the sub-app unmounts, its modifications
   to the virtual window are discarded. This enables multiple sub-apps to
   coexist on the same page with no global variable conflicts.

Q: How do you handle shared dependencies (like React) across micro-frontends?
A: Options:
   1. Module Federation's shared config: each MFE declares shared dependencies
      with singleton: true — only one copy of React loads across all MFEs.
   2. Import maps with externalization: shell provides React on the global scope,
      sub-apps mark React as external in their webpack config.
   3. Each MFE bundles its own React (simplest but doubles the bundle size and
      breaks React hooks across MFE boundaries — not recommended).
   The key constraint: React MUST be a singleton because it stores hook state
   in module-level variables. Two React instances on the same page cause
   "Invalid hook call" errors.

Q: How would you design authentication in a micro-frontend architecture?
A: Authentication is owned by the shell (host app). The shell:
   1. Handles login/logout flow
   2. Stores tokens (httpOnly cookies are ideal; localStorage for SPAs)
   3. Passes auth context down to each MFE as props on mount
   4. Can use a shared utility module (@myorg/auth) that all MFEs import
      for token retrieval and refresh logic
   MFEs should NEVER independently handle login — they receive auth context
   from the shell. For API calls, each MFE attaches the token to requests.
   Token refresh is centralized in the shell or the shared auth utility.

Q: How do you test micro-frontends?
A: Multi-level testing strategy:
   1. Unit/component tests: each MFE tested in isolation (Jest + RTL)
   2. Integration tests: each MFE tested with its API mocked (MSW)
   3. Contract tests (Pact.io): verify API contracts between shell and MFEs
      without running all services simultaneously
   4. End-to-end tests: run all MFEs together in a composed environment
      (Cypress or Playwright). These are expensive — keep minimal.
   5. Visual regression: catch CSS leakage or layout breaks across MFE boundaries

Q: How would you migrate a monolithic frontend to micro-frontends?
A: Strangler Fig pattern applied to frontend:
   1. Deploy a shell/proxy that routes some URLs to the new MFE, rest to monolith
   2. Start with the lowest-risk, most isolated section (e.g., a standalone page)
   3. Build new MFE independently, expose same UI surface
   4. Switch traffic to new MFE for that route
   5. Repeat for next section
   6. Eventually monolith handles nothing; decommission it
   Key: the shell is the seam. Users never see the transition — routing is transparent.

Q: What are the biggest downsides of micro-frontends?
A: 1. Operational overhead: more repos, CI pipelines, deployments, monitoring
   2. Consistent UX risk: divergent design if design system governance is weak
   3. Performance: more network requests for loading separate bundles,
      potential duplicate dependencies
   4. Cross-MFE debugging: tracing a user flow across 3 MFEs is harder
   5. Integration complexity: getting all MFEs running locally for E2E tests
      requires orchestration (docker-compose or similar)
   The rule: micro-frontends solve an organizational problem (team autonomy)
   at the cost of technical complexity. Don't use them to solve technical problems.

Q: When would you recommend NOT using micro-frontends?
A: When the team is small (< 4 developers), the overhead of multiple repos,
   CI pipelines, and integration complexity vastly outweighs any benefit.
   When domain boundaries in the UI are unclear or shifting — you'll constantly
   be refactoring what's in which MFE. When the application is early-stage —
   premature decomposition adds cost without benefit. When performance is
   critical and the extra network round-trips for loading MFEs are unacceptable.
   A well-structured monorepo with clear module boundaries often gives the same
   organizational benefits without the runtime complexity.

Q: single-spa vs Module Federation — which would you choose?
A: It depends on the team structure and technology choices:
   - If teams use different frameworks (React + Vue + Angular): single-spa
     or qiankun because Module Federation works best within the same framework.
   - If all teams use the same framework (all React): Module Federation is
     simpler, has better tooling, and native webpack 5 support.
   - For enterprise with strict isolation requirements (JS + CSS sandbox):
     qiankun (which wraps single-spa) provides this out of the box.
   - For pure runtime module sharing without a routing framework: Module
     Federation is the right choice.
   Many large teams use both: single-spa for orchestration + Module Federation
   for efficient shared dependency management.
