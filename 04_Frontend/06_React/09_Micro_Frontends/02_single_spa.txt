SINGLE-SPA — MICRO-FRONTEND ORCHESTRATION FRAMEWORK

1. WHAT IS SINGLE-SPA?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

single-spa is a JavaScript framework for orchestrating multiple SPAs (micro-
frontends) within a single browser window. It is framework-agnostic — you can
combine React, Vue, Angular, and Svelte apps on the same page.

GitHub: https://github.com/single-spa/single-spa
Maintained by: Canopy Tax, community

CORE CONCEPT:
  single-spa defines a lifecycle API that every micro-frontend must implement:
  - bootstrap: called once on first mount
  - mount: called when the MFE should render
  - unmount: called when the MFE should be removed from the DOM
  - update (optional): called when props change without unmount

  The root config (shell) registers each MFE with a route condition and
  single-spa calls these lifecycle functions at the right time.

2. APPLICATION TYPES IN SINGLE-SPA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

APPLICATION (most common):
  - Has a route — mounts/unmounts based on URL
  - Owns a section of the DOM

PARCEL:
  - Does NOT control its own routing
  - Mounted programmatically by another MFE or shell
  - Used for shared UI components (e.g., a date picker used by multiple MFEs)

UTILITY:
  - No DOM rendering at all
  - Provides shared logic / services (analytics, auth, API clients)

3. SETUP EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STEP 1 — Root Config (Shell):
  import { registerApplication, start } from 'single-spa';

  registerApplication({
    name: '@myorg/products',
    app: () => System.import('@myorg/products'), // SystemJS dynamic import
    activeWhen: '/products',                     // Route match condition
  });

  registerApplication({
    name: '@myorg/cart',
    app: () => System.import('@myorg/cart'),
    activeWhen: '/cart',
  });

  registerApplication({
    name: '@myorg/navbar',
    app: () => System.import('@myorg/navbar'),
    activeWhen: () => true,  // Always active (navbar is always shown)
  });

  start(); // Begin routing

STEP 2 — Micro-Frontend (React example):
  // src/root.component.jsx
  export default function Root() {
    return <h1>Products Page</h1>;
  }

  // src/products.js — single-spa lifecycle exports
  import React from 'react';
  import ReactDOM from 'react-dom';
  import singleSpaReact from 'single-spa-react';
  import Root from './root.component';

  const lifecycles = singleSpaReact({
    React,
    ReactDOM,
    rootComponent: Root,
    errorBoundary(err, info, props) {
      return <div>Products app failed to load</div>;
    },
  });

  export const { bootstrap, mount, unmount } = lifecycles;
  // single-spa calls these at the right time

4. IMPORT MAP — MODULE LOADING WITHOUT BUNDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

single-spa commonly uses Import Maps + SystemJS for runtime module loading:

  <!-- In index.html of the shell -->
  <script type="systemjs-importmap">
  {
    "imports": {
      "single-spa": "https://cdn.jsdelivr.net/npm/single-spa/esm/single-spa.min.js",
      "react": "https://cdn.jsdelivr.net/npm/react/umd/react.production.min.js",
      "react-dom": "https://cdn.jsdelivr.net/npm/react-dom/umd/react-dom.production.min.js",
      "@myorg/products": "https://products.example.com/myorg-products.js",
      "@myorg/cart": "https://cart.example.com/myorg-cart.js"
    }
  }
  </script>

HOW IT WORKS:
  - When URL matches /products, single-spa calls System.import('@myorg/products')
  - SystemJS fetches the URL in the import map
  - The bundle loads and its bootstrap/mount/unmount are called

UPDATING A MICRO-FRONTEND WITHOUT REDEPLOYMENT OF SHELL:
  - Deploy new products bundle to products.example.com
  - Update the import map to point to new URL (can be done via API or CI pipeline)
  - Users immediately get new version on next navigation — shell never rebuilt

5. COMMUNICATION BETWEEN MFEs IN single-spa
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CUSTOM EVENTS (recommended for loose coupling):
  // Emitter (Cart MFE):
  window.dispatchEvent(new CustomEvent('cart:item-added', {
    detail: { productId: 123, quantity: 1 }
  }));

  // Listener (Navbar MFE — updates cart count badge):
  window.addEventListener('cart:item-added', (event) => {
    updateCartCount(event.detail.quantity);
  });

SHARED UTILITY MODULE (single-spa utility):
  @myorg/store — a utility that exports a reactive store
  Both Products and Cart import from @myorg/store
  Because import maps point to the same URL, they share the same instance

PROPS FROM SHELL:
  registerApplication({
    name: '@myorg/products',
    app: () => System.import('@myorg/products'),
    activeWhen: '/products',
    customProps: {                           // Passed to lifecycle functions
      userId: getCurrentUserId(),
      authToken: getToken(),
    }
  });
  // In the MFE: mount(el, props) — props.userId, props.authToken available

6. single-spa vs MODULE FEDERATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Aspect                  single-spa              Module Federation
  ────────────────────────────────────────────────────────────────────
  Framework agnostic      ✅ Yes                  Partial (webpack only)
  Module loading          SystemJS / Import Maps  Webpack 5 native
  Routing control         single-spa owns it      Host app owns it
  Shared dependencies     Import maps             webpack shared config
  Mixed frameworks        ✅ React + Vue + Angular ❌ Best with same framework
  Setup complexity        Medium-High             Medium
  Maturity                High (since 2018)       Medium (since 2020)
  Best for                Large enterprise, polyglot  Same-framework teams

COMBINING BOTH:
  Many teams use single-spa for orchestration/routing + Module Federation
  for efficient module sharing. Not mutually exclusive.
