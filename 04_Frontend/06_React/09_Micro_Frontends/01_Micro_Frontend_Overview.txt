1. WHAT ARE MICRO-FRONTENDS?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Micro-frontends extend the microservices philosophy to the frontend. Instead
of one large monolithic frontend application, the UI is split into smaller,
independently developed, deployed, and owned pieces — each owned by a
separate team.

Coined by: ThoughtWorks Technology Radar (2016)
Popularized by: Cam Jackson's article on martinfowler.com (2019)

ANALOGY:
  Microservices split the backend into independently deployable services.
  Micro-frontends split the frontend into independently deployable UIs.

  Monolith App           Micro-Frontend App
  ─────────────          ──────────────────
  Single team            Multiple teams
  Single repo            Multiple repos (or monorepo)
  Single deploy          Independent deploys
  Single bundle          Multiple bundles
  One tech stack         Potentially mixed stacks

2. ARCHITECTURAL DECOMPOSITION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BY DOMAIN / FEATURE (most common — "vertical slice"):
  ┌──────────────────────────────────┐
  │           App Shell              │  ← Navigation, auth, layout
  ├────────────┬──────────┬──────────┤
  │  Products  │   Cart   │ Checkout │  ← Each owned by a team
  │  Team A    │  Team B  │  Team C  │
  └────────────┴──────────┴──────────┘

BY PAGE:
  /products/*  → Products MFE
  /cart/*      → Cart MFE
  /account/*   → Account MFE

BY UI SECTION (horizontal — less common):
  Header team, Footer team, Content team each own a horizontal slice.
  (Harder to manage, not recommended)

3. INTEGRATION APPROACHES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A) BUILD-TIME INTEGRATION (NPM Packages):
   - Micro-frontends published as npm packages
   - Shell installs and imports them
   - PROS: Simple, type-safe, tree-shakeable
   - CONS: Requires shell rebuild to update any micro-frontend — defeats independent deployment

B) RUNTIME INTEGRATION via <iframe>:
   - Each MFE runs in its own iframe
   - PROS: True isolation (CSS, JS, errors)
   - CONS: UX friction, performance overhead, hard to share state, poor SEO

C) RUNTIME INTEGRATION via JavaScript (Module Federation, single-spa):
   - Shell dynamically loads MFE JavaScript at runtime
   - PROS: True independent deployment, shared dependencies possible
   - CONS: Complexity, version conflicts, potential performance overhead
   - Tools: Webpack Module Federation, single-spa, qiankun

D) EDGE-SIDE INCLUDES (ESI) / SERVER-SIDE COMPOSITION:
   - Server composes HTML fragments from multiple micro-frontend services
   - PROS: Good SEO, fast initial load, no client-side complexity
   - CONS: Server infrastructure complexity, harder to do SPA-like transitions

4. CROSS-CUTTING CONCERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SHARED STATE:
  Micro-frontends should be as independent as possible — avoid sharing state.
  When necessary:
  - Custom events (CustomEvent API) for lightweight cross-MFE communication
  - URL / query string (persistent, shareable)
  - Browser storage (localStorage) — but beware coupling
  - Shared state via a shell-managed event bus
  - Backend (API) as the source of truth

ROUTING:
  Shell owns top-level routing (e.g., /products → load Products MFE)
  Each MFE manages its own sub-routing internally

AUTHENTICATION:
  Handled by the shell. MFEs receive tokens via:
  - Props/attributes from shell
  - Shared session (cookie or localStorage)
  - Custom events

SHARED DESIGN SYSTEM:
  Publish design system as npm package (not via Module Federation)
  All MFEs install same version.
  Problem: version drift — Team A on v2, Team B on v3.
  Solution: enforced via organizational policy + CI version checks.

CSS ISOLATION:
  - CSS Modules (scoped class names)
  - Shadow DOM (Web Components)
  - CSS-in-JS (emotion, styled-components — scoped by default)
  - BEM naming conventions + team prefixes

5. BENEFITS AND TRADE-OFFS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

BENEFITS:
  ✅ Independent deployment — teams ship without coordination
  ✅ Team autonomy — each team owns full stack for their domain
  ✅ Technology flexibility — teams can use different frameworks (carefully)
  ✅ Smaller codebases — easier to understand and test per team
  ✅ Fault isolation — one MFE crashing doesn't take down the whole app (with Error Boundaries)
  ✅ Incremental migration — migrate from legacy to modern stack page by page

TRADE-OFFS / COSTS:
  ❌ Operational complexity — more services, more deployments, more CI pipelines
  ❌ Consistency risk — divergent UX if design system governance is weak
  ❌ Performance overhead — more network requests, potential duplicate bundles
  ❌ Cross-team debugging — tracing bugs across MFE boundaries is harder
  ❌ Shared dependency versioning — React singletons, CSS conflicts
  ❌ Testing integration — end-to-end tests need all MFEs running

6. WHEN TO USE MICRO-FRONTENDS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE MFE WHEN:
  - Large organization: 4+ teams working on the same frontend
  - Domain boundaries are clear and stable
  - Teams are blocked by each other on releases
  - Incremental migration needed (legacy app alongside new)
  - Different parts of the app have very different release cadences

DO NOT USE MFE WHEN:
  - Small team (1–3 devs) — overhead outweighs benefits
  - Application is simple or early-stage
  - No clear domain boundaries
  - Team communication is already efficient
  - Performance requirements are extremely strict (MFE adds overhead)

7. TOOLS LANDSCAPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Tool                  Type              Best For
  ─────────────────────────────────────────────────────────────────
  Module Federation     Webpack plugin    Runtime JS integration, same framework
  single-spa            Framework         Multi-framework MFE orchestration
  qiankun               Framework         Enterprise, based on single-spa
  Luigi                 Framework         SAP's MFE framework
  Piral                 Framework         Plugin-based MFE apps
  Web Components        Browser native    Framework-agnostic component sharing
  ESI (Akamai/Varnish)  Server-side       HTML composition at CDN/proxy layer
