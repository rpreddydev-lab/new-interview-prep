1. OVERVIEW OF ALL OPTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  | Solution          | Category     | Bundle   | Boilerplate | Best For               |
  |-------------------|--------------|----------|-------------|------------------------|
  | useState          | Local        | 0        | None        | Component-level state  |
  | useReducer        | Local        | 0        | Low         | Complex local state    |
  | Context API       | Global       | 0        | Low         | Auth, theme, locale    |
  | Redux Toolkit     | Global       | ~15KB    | Medium      | Large apps, teams      |
  | Zustand           | Global       | ~1KB     | Very Low    | Small-medium apps      |
  | Jotai             | Atomic       | ~3KB     | Very Low    | Fine-grained atoms     |
  | Recoil            | Atomic       | ~20KB    | Low-Medium  | Complex derived state  |
  | TanStack Query    | Server State | ~12KB    | Low         | API data, caching      |
  | SWR               | Server State | ~4KB     | Very Low    | API data (simpler)     |
  | RTK Query         | Server State | (RTK)    | Low         | Redux + API data       |

2. CLIENT STATE vs SERVER STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  CLIENT STATE:                        SERVER STATE:
  - Lives in memory                    - Lives on a remote server
  - Synchronous                        - Asynchronous
  - You own it                         - You don't own it (can change externally)
  - Never stale                        - Can become stale
  - No deduplication needed            - Needs caching & deduplication
  - Examples: isModalOpen,             - Examples: user list from API,
    selectedTab, formInputs              product catalog, current user profile

  Mistake: Putting server state into Redux:
    dispatch(setUsers(await fetch('/users').then(r => r.json())));
    // You now have to manage: loading, error, caching, refetching manually

  Solution: TanStack Query / SWR handles server state automatically.
  Use Redux/Zustand only for client state.

3. DECISION FLOWCHART
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Is the state async data from an API?
  ├─ YES → Use TanStack Query (or SWR / RTK Query)
  └─ NO (client state) ↓

  Does only ONE component need it?
  ├─ YES → useState / useReducer
  └─ NO → shared state ↓

  Do only a FEW closely related components need it?
  ├─ YES → Lift state up + props (2-3 levels is fine)
  └─ NO → global state ↓

  Are updates INFREQUENT (auth, theme)?
  ├─ YES → React Context API
  └─ NO → ↓

  Do you need DevTools, middleware, large team?
  ├─ YES → Redux Toolkit
  └─ NO → Zustand (minimal, fast)

4. ZUSTAND vs CONTEXT API: DEEP COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Context API:
    const ctx = useContext(CartContext);
    // ALL consumers of CartContext re-render when ANY part of value changes
    // Even CartItemCount re-renders if only cartVisible toggle changed

  Zustand:
    const itemCount = useCartStore(state => state.items.length);
    // ONLY re-renders when items.length changes
    // Precise subscription = fewer unnecessary re-renders

  Performance difference:
    Context is fine for: theme, locale, user (low update frequency)
    Zustand is better for: cart, notifications, real-time data (high frequency)

5. REDUX vs ZUSTAND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Redux Toolkit:                       Zustand:
  ─────────────────────                ─────────────────────
  - Slice pattern (separate files)     - One store file, co-located state+actions
  - Provider required                  - No Provider (module-level singleton)
  - dispatch(action) pattern           - Direct function calls (store.increment())
  - Excellent DevTools + time-travel   - DevTools via middleware (less powerful)
  - RTK Query for data fetching        - Combine with React Query
  - Better for large teams with rules  - Better for quick iteration
  - More verbose but more structured   - Less boilerplate, less structure

  Both use selectors for performance.
  Both support middleware.
  Both have excellent TypeScript support.

6. TYPICAL MODERN STACK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  RECOMMENDED FOR MOST APPS:
    Server State:  TanStack Query
    Global State:  Zustand
    Auth/Theme:    Context API
    Local State:   useState / useReducer
    URL State:     React Router useSearchParams
    Form State:    React Hook Form

  FOR LARGE ENTERPRISE APPS:
    Server State:  RTK Query or TanStack Query
    Global State:  Redux Toolkit
    Auth/Theme:    Context API
    Local State:   useState / useReducer

7. COMMON INTERVIEW QUESTIONS

Q: How would you choose a state management solution for a new React project?
A: I'd first classify the state types. For async API data, I'd use TanStack
   Query. For simple component-level state, useState/useReducer. For global
   client state that's low-frequency (auth, theme), Context API. For high-
   frequency global state or complex state logic in a large team, Zustand or
   Redux Toolkit.

Q: Is Context API a replacement for Redux?
A: Not entirely. Context solves prop drilling but is not optimized for frequent
   state updates (all consumers re-render). Redux and Zustand have selector-
   based subscriptions that only re-render components when their specific slice
   of state changes. Use Context for low-frequency global values, Redux/Zustand
   for frequently-updated global state.

Q: Why shouldn't you store server/API data in Redux?
A: Server state needs caching, background refetching, deduplication, and
   expiration logic that you'd have to manually implement in Redux. TanStack
   Query provides all of this out-of-the-box. Mixing server state into Redux
   leads to overly complex state management with stale data issues.

Q: What is "atom-based" state management (Jotai/Recoil)?
A: Instead of one big store, state is split into small independent units called
   atoms. Components subscribe to individual atoms. When an atom changes, only
   components using that atom re-render (extremely fine-grained reactivity).
   Jotai is the more popular lightweight option.
