1. WHAT IS CONTEXT API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

React Context provides a way to pass data through the component tree without
having to pass props at every level (avoiding prop drilling).

  Three parts:
  1. React.createContext(defaultValue) — creates a Context object
  2. Context.Provider                  — provides the value to descendants
  3. useContext(Context)               — consumes the value in any descendant

  // 1. Create
  const ThemeContext = React.createContext('light'); // default value

  // 2. Provide
  function App() {
    const [theme, setTheme] = useState('light');
    return (
      <ThemeContext.Provider value={{ theme, setTheme }}>
        <Layout />
      </ThemeContext.Provider>
    );
  }

  // 3. Consume (anywhere in the tree, no matter how deep)
  function Button() {
    const { theme, setTheme } = useContext(ThemeContext);
    return (
      <button
        style={{ background: theme === 'dark' ? '#333' : '#fff' }}
        onClick={() => setTheme(t => t === 'dark' ? 'light' : 'dark')}
      >
        Toggle Theme
      </button>
    );
  }

2. COMPLETE AUTH CONTEXT EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // context/AuthContext.js
  import { createContext, useContext, useState, useCallback } from 'react';

  const AuthContext = createContext(null);

  export function AuthProvider({ children }) {
    const [user, setUser] = useState(null);
    const [loading, setLoading] = useState(false);

    const login = useCallback(async (credentials) => {
      setLoading(true);
      try {
        const response = await fetch('/api/login', {
          method: 'POST',
          body: JSON.stringify(credentials),
        });
        const userData = await response.json();
        setUser(userData);
      } finally {
        setLoading(false);
      }
    }, []);

    const logout = useCallback(() => {
      setUser(null);
    }, []);

    const value = useMemo(() => ({
      user,
      loading,
      login,
      logout,
      isAuthenticated: !!user,
    }), [user, loading, login, logout]);
    // useMemo prevents creating a new object on every render

    return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
  }

  // Custom hook — encapsulates useContext + error guard
  export function useAuth() {
    const context = useContext(AuthContext);
    if (!context) {
      throw new Error('useAuth must be used within an AuthProvider');
    }
    return context;
  }

  // Usage anywhere in tree:
  function ProfilePage() {
    const { user, logout } = useAuth();
    return (
      <div>
        <p>Welcome, {user.name}</p>
        <button onClick={logout}>Logout</button>
      </div>
    );
  }

3. CONTEXT RE-RENDERING BEHAVIOR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CRITICAL: When a Context Provider's value changes, ALL consumers re-render,
even if they only use part of the value that didn't change.

  // BAD: New object on every render → all consumers re-render every time
  function App() {
    const [user, setUser] = useState(null);
    const [theme, setTheme] = useState('light');

    return (
      <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
        {/* ThemeButton will re-render whenever user changes — unnecessary */}
        <ThemeButton />
        <UserProfile />
      </AppContext.Provider>
    );
  }

  Solution 1: Split contexts (recommended)
    <UserContext.Provider value={{ user, setUser }}>
      <ThemeContext.Provider value={{ theme, setTheme }}>
        {children}
      </ThemeContext.Provider>
    </UserContext.Provider>
    // Now ThemeButton only re-renders when theme changes

  Solution 2: Memoize the value
    const value = useMemo(() => ({ user, setUser }), [user]);
    <UserContext.Provider value={value}>

  Solution 3: Split state and dispatch (stable dispatch from useReducer)
    const UserStateContext = createContext(null);
    const UserDispatchContext = createContext(null);
    // dispatch never changes → components that only call dispatch never re-render

4. CONTEXT DEFAULT VALUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The default value in createContext(defaultValue) is ONLY used when a component
consumes the context WITHOUT a matching Provider above it.

  const ThemeContext = createContext('light'); // default: 'light'

  function App() {
    // No Provider wrapping — consumers will get 'light' from createContext
    return <Button />;
  }

  function Button() {
    const theme = useContext(ThemeContext); // 'light' (from default, not Provider)
    return <button className={theme}>Click</button>;
  }

  Common pattern: Use null as default + throw in custom hook
    const AuthContext = createContext(null);
    export function useAuth() {
      const ctx = useContext(AuthContext);
      if (!ctx) throw new Error('useAuth must be inside AuthProvider');
      return ctx;
    }

  // Clean way to compose multiple providers
  function AppProviders({ children }) {
    return (
      <AuthProvider>
        <ThemeProvider>
          <NotificationProvider>
            {children}
          </NotificationProvider>
        </ThemeProvider>
      </AuthProvider>
    );
  }

  function App() {
    return (
      <AppProviders>
        <Router>
          <Routes>...</Routes>
        </Router>
      </AppProviders>
    );
  }

6. WHEN TO USE CONTEXT vs REDUX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  | Criterion                   | Context API       | Redux / Zustand     |
  |-----------------------------|-------------------|---------------------|
  | Setup complexity            | Low               | Medium-High         |
  | Boilerplate                 | Minimal           | More                |
  | Performance (high updates)  | Poor (no selector)| Good (selectors)    |
  | Dev tools                   | Basic             | Excellent           |
  | Middleware (logging, thunk) | No                | Yes                 |
  | Time-travel debugging       | No                | Yes (Redux)         |
  | Best for                    | Auth, theme,locale| Complex app state   |
  | Learning curve              | Low               | Medium              |

  Use Context when:
  - State updates are infrequent (auth, theme)
  - The value is consumed by many but changes rarely
  - You want to avoid external dependencies

  Use Redux/Zustand when:
  - State updates are frequent
  - You need fine-grained subscriptions (only re-render when relevant slice changes)
  - You need time-travel debugging, middleware, or complex async flows

7. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is prop drilling and how does Context solve it?
A: Prop drilling is passing data through multiple intermediate components that
   don't need it, just to reach a deeply nested component. Context solves it
   by making the value available directly to any descendant without manual
   prop passing.

Q: What is the Context default value used for?
A: It's used ONLY when a component consumes the context but has no matching
   Provider anywhere above it. It's useful for testing components in isolation
   without wrapping them in a Provider.

Q: How do you prevent unnecessary re-renders with Context?
A: Split contexts by concern (so changes in one don't affect consumers of
   another). Memoize the provider value with useMemo. For very frequent
   updates, use Zustand or Redux with selectors instead of Context.

Q: Can you have multiple Providers for the same Context?
A: Yes. Each Provider creates its own value scope. The closest Provider
   above a consumer wins. This is useful for nested themes or user settings.

Q: What is the pattern of splitting state and dispatch contexts?
A: Create two separate contexts — one for state (changes on updates) and one
   for dispatch (stable reference from useReducer). Components that only need
   to trigger actions subscribe only to the dispatch context and never re-render
   due to state changes.
