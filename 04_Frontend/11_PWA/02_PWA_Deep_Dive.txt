SECTION 1 — PWA FUNDAMENTALS
================================================================================

Q1: What is a Progressive Web App and what are its core requirements?

A: A Progressive Web App (PWA) is a web application that uses modern web APIs
   to deliver app-like experiences: installability, offline capability, and
   push notifications — without requiring an app store.

   THREE CORE REQUIREMENTS:
   1. HTTPS: required for Service Workers and security (also localhost for dev)
   2. WEB APP MANIFEST: JSON file describing the app (name, icons, start URL)
   3. SERVICE WORKER: JavaScript background script for offline + notifications

   PWA CAPABILITIES (Progressive Enhancement):
   ✓ Works offline (or shows fallback) — Service Worker cache
   ✓ Installable — Add to Home Screen prompt, desktop install
   ✓ Push notifications — even when browser not open
   ✓ Background sync — queue actions offline, sync when back online
   ✓ Fast loading — cached assets, optimistic pre-caching
   ✓ Responsive — adapts to any device
   ✓ App-like UX — full-screen mode, splash screen

   PWA vs NATIVE APP vs WEB:
   ┌───────────────┬──────────┬───────────┬────────────┐
   │ Feature       │ Web      │ PWA       │ Native App │
   ├───────────────┼──────────┼───────────┼────────────┤
   │ Install       │ No       │ Yes       │ Yes        │
   │ Offline       │ No       │ Yes       │ Yes        │
   │ Push notif.   │ No       │ Yes       │ Yes        │
   │ App store     │ No       │ No        │ Yes        │
   │ Discoverability│ Easy    │ Easy      │ App store  │
   │ Updates       │ Instant  │ Instant   │ Manual/auto│
   │ Access level  │ Web APIs │ Web APIs  │ Full OS    │
   └───────────────┴──────────┴───────────┴────────────┘

SECTION 2 — SERVICE WORKERS
================================================================================

Q2: What is a Service Worker and how does its lifecycle work?

A: A Service Worker is a JavaScript file that runs in the BACKGROUND in a
   separate thread — separate from the main browser thread.

   CAPABILITIES:
   - Intercept network requests (act as a proxy)
   - Cache responses for offline use
   - Receive push notifications
   - Background sync

   RESTRICTIONS:
   - No DOM access (separate thread)
   - HTTPS only
   - Limited execution time (browser can terminate idle SWs)

   LIFECYCLE PHASES:
   1. REGISTRATION: app registers the SW file
      navigator.serviceWorker.register('/sw.js')
      → Browser downloads sw.js; parses it; starts installation

   2. INSTALLATION (install event): pre-cache essential assets
      self.addEventListener('install', event => {
          event.waitUntil(
              caches.open('v1').then(cache => cache.addAll([
                  '/', '/index.html', '/styles.css', '/app.js', '/logo.png'
              ]))
          );
          self.skipWaiting(); // immediately activate (skip waiting phase)
      });

   3. ACTIVATION (activate event): clean up old caches
      self.addEventListener('activate', event => {
          event.waitUntil(
              caches.keys().then(keys => Promise.all(
                  keys.filter(k => k !== 'v1').map(k => caches.delete(k))
              ))
          );
          self.clients.claim(); // take control of open pages immediately
      });

   4. FETCH INTERCEPTION (fetch event): serve from cache or network
      self.addEventListener('fetch', event => {
          event.respondWith(
              caches.match(event.request)
                  .then(cached => cached ?? fetch(event.request))
          );
      });

   5. IDLE / TERMINATED: browser terminates SW when not needed; revived on next event

Q3: What are the main Service Worker caching strategies?

A: CACHING STRATEGIES (by use case):

   1. CACHE FIRST (offline first):
      "Return from cache; fall back to network if not cached."
      Best for: static assets (CSS, JS, images, fonts) — rarely change
      const cached = await caches.match(request);
      return cached ?? fetch(request);

   2. NETWORK FIRST (freshness preferred):
      "Try network; fall back to cache if network fails."
      Best for: API responses, frequently changing content
      try {
          const response = await fetch(request);
          cache.put(request, response.clone());
          return response;
      } catch {
          return caches.match(request);
      }

   3. STALE WHILE REVALIDATE (best UX compromise):
      "Return cached immediately; update cache from network in background."
      Best for: content where showing slightly stale data is acceptable
      const cached = await caches.match(request);
      const networkPromise = fetch(request).then(res => {
          cache.put(request, res.clone());
          return res;
      });
      return cached ?? networkPromise; // return cache immediately if available

   4. CACHE ONLY:
      "Only serve from cache; never go to network."
      Best for: assets pre-cached at install time (app shell)

   5. NETWORK ONLY:
      "Always go to network; never cache."
      Best for: analytics, payment processing, non-idempotent requests

Q4: What goes in a Web App Manifest? Write a complete example.

A:
   <!-- In HTML <head>: -->
   <link rel="manifest" href="/manifest.json">

   manifest.json:
   {
     "name": "Telecom Customer Portal",
     "short_name": "TelPortal",
     "description": "Manage your telecom account, check usage and pay bills",
     "start_url": "/dashboard?source=pwa",
     "display": "standalone",       // fullscreen | standalone | minimal-ui | browser
     "orientation": "portrait",
     "background_color": "#ffffff",
     "theme_color": "#0070f3",
     "scope": "/",
     "lang": "en-GB",
     "icons": [
       { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
       { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
       {
         "src": "/icons/icon-512-maskable.png",
         "sizes": "512x512",
         "type": "image/png",
         "purpose": "maskable"
       }
     ],
     "shortcuts": [
       {
         "name": "Pay Bill",
         "short_name": "Pay",
         "description": "Go directly to bill payment",
         "url": "/billing/pay",
         "icons": [{ "src": "/icons/pay-shortcut.png", "sizes": "192x192" }]
       }
     ],
     "categories": ["utilities", "finance"],
     "screenshots": [
       {
         "src": "/screenshots/dashboard.png",
         "sizes": "1280x720",
         "type": "image/png",
         "form_factor": "wide"
       }
     ]
   }

   KEY PROPERTIES:
   - display: standalone → hides browser chrome (looks like native app)
   - theme_color: sets status bar/toolbar color on mobile
   - icons: must include 192×192 and 512×512 minimum
   - maskable purpose: allows OS to apply custom icon mask (rounded corners, etc.)
   - shortcuts: long-press icon → quick actions (Android 11+, Windows 11)
   - start_url: track installs via ?source=pwa query parameter

SECTION 4 — PUSH NOTIFICATIONS
================================================================================

Q5: How do PWA push notifications work?

A: PUSH NOTIFICATION FLOW:
   1. User grants notification permission:
      const permission = await Notification.requestPermission();
      if (permission !== 'granted') return;

   2. Subscribe to Push Service (browser-specific VAPID endpoint):
      const registration = await navigator.serviceWorker.ready;
      const subscription = await registration.pushManager.subscribe({
          userVisibleOnly: true,   // required; must always show notification
          applicationServerKey: urlB64ToUint8Array(VAPID_PUBLIC_KEY)
      });
      // Send subscription to your server
      await fetch('/api/push/subscribe', {
          method: 'POST',
          body: JSON.stringify(subscription)
      });

   3. Server sends push (using web-push library):
      // Node.js server (or Java with built-in WebPush library)
      webpush.sendNotification(subscription, JSON.stringify({
          title: 'Your invoice is ready',
          body: 'Your £45.99 invoice for November is available',
          icon: '/icons/icon-192.png',
          badge: '/icons/badge.png',
          data: { url: '/billing/invoice/2024-11' }
      }));

   4. Service Worker receives push event and shows notification:
      self.addEventListener('push', event => {
          const data = event.data?.json() ?? {};
          event.waitUntil(
              self.registration.showNotification(data.title, {
                  body: data.body,
                  icon: data.icon,
                  badge: data.badge,
                  data: data.data,
                  requireInteraction: false // auto-dismiss after ~5s
              })
          );
      });

   5. User clicks notification → Service Worker handles notificationclick:
      self.addEventListener('notificationclick', event => {
          event.notification.close();
          event.waitUntil(
              clients.openWindow(event.notification.data?.url ?? '/')
          );
      });

   VAPID (Voluntary Application Server Identity):
   - Public/private key pair identifying your server to the push service
   - Prevents unauthorized servers from sending notifications to your subscribers
   - Generate: npx web-push generate-vapid-keys

SECTION 5 — BACKGROUND SYNC AND INSTALLABILITY
================================================================================

Q6: What is Background Sync and when do you use it?

A: Background Sync lets a PWA defer actions until the user has a stable
   network connection — even if the user has left the app.

   USE CASE: User submits a payment while offline → action is queued →
   synced automatically when connectivity returns.

   IMPLEMENTATION:
   // In app: register a sync event
   async function submitPayment(paymentData) {
       if ('serviceWorker' in navigator && 'SyncManager' in window) {
           // Store payment in IndexedDB for the SW to process
           await storePaymentInIDB(paymentData);
           const reg = await navigator.serviceWorker.ready;
           await reg.sync.register('sync-payment');
       } else {
           // Fallback: direct submit
           await fetch('/api/pay', { method: 'POST', body: JSON.stringify(paymentData) });
       }
   }

   // In Service Worker: handle sync
   self.addEventListener('sync', event => {
       if (event.tag === 'sync-payment') {
           event.waitUntil(processPendingPayments());
       }
   });

   async function processPendingPayments() {
       const payments = await getPendingPaymentsFromIDB();
       for (const payment of payments) {
           await fetch('/api/pay', { method: 'POST', body: JSON.stringify(payment) });
           await removePaymentFromIDB(payment.id);
       }
   }

Q7: What triggers the "Add to Home Screen" (A2HS) prompt?

A: BROWSER INSTALLABILITY CRITERIA (Chrome/Edge):
   1. Site served over HTTPS
   2. Valid manifest.json with: name, icons (192+ and 512+), start_url, display
   3. Service Worker registered with a fetch event handler
   4. User has engaged with the page (heuristic — visited multiple times)

   CUSTOM INSTALL PROMPT:
   let deferredPrompt;
   window.addEventListener('beforeinstallprompt', event => {
       event.preventDefault(); // prevent automatic prompt
       deferredPrompt = event;  // save for later
       showInstallButton();     // show your custom "Install App" button
   });

   installButton.addEventListener('click', async () => {
       if (!deferredPrompt) return;
       deferredPrompt.prompt();
       const choice = await deferredPrompt.userChoice;
       if (choice.outcome === 'accepted') trackInstall();
       deferredPrompt = null;
   });

   TRACK INSTALLS:
   window.addEventListener('appinstalled', () => {
       analytics.track('pwa_installed');
   });

SECTION 6 — WORKBOX
================================================================================

Q8: What is Workbox and how does it simplify Service Worker development?

A: Workbox (by Google) is a library of modules that simplify common Service Worker
   patterns: routing, caching strategies, pre-caching, background sync.

   WITHOUT WORKBOX: manual fetch event handlers, cache management, version management
   WITH WORKBOX: declarative routing with strategy objects

   WORKBOX EXAMPLE (sw.js):
   import { registerRoute } from 'workbox-routing';
   import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
   import { precacheAndRoute } from 'workbox-precaching';
   import { BackgroundSyncPlugin } from 'workbox-background-sync';

   // Pre-cache build output (injected by build tool)
   precacheAndRoute(self.__WB_MANIFEST);

   // Cache-first for static assets
   registerRoute(
       ({ request }) => request.destination === 'image',
       new CacheFirst({ cacheName: 'images-cache', plugins: [
           new ExpirationPlugin({ maxEntries: 50, maxAgeSeconds: 30 * 24 * 60 * 60 })
       ]})
   );

   // Network-first for API calls with offline fallback
   registerRoute(
       ({ url }) => url.pathname.startsWith('/api/'),
       new NetworkFirst({ cacheName: 'api-cache', networkTimeoutSeconds: 3 })
   );

   // Stale-while-revalidate for pages
   registerRoute(
       ({ request }) => request.mode === 'navigate',
       new StaleWhileRevalidate({ cacheName: 'pages-cache' })
   );

   NEXT.JS PWA INTEGRATION:
   npm install next-pwa
   // next.config.js:
   const withPWA = require('next-pwa')({ dest: 'public', disable: process.env.NODE_ENV === 'development' });
   module.exports = withPWA({ ... your config ... });
   // Automatically generates sw.js and pre-caches all Next.js build output

QUICK REFERENCE CHEAT SHEET
================================================================================

PWA REQUIREMENTS: HTTPS + manifest.json + Service Worker
LIFECYCLE: register → install (cache shell) → activate (clean old) → fetch intercept

CACHING STRATEGIES:
  Cache First:           static assets (CSS, JS, images)
  Network First:         API responses, dynamic content
  Stale While Revalidate: pages, profiles (freshness + speed balance)
  Cache Only:            pre-cached app shell
  Network Only:          payments, analytics

MANIFEST ESSENTIALS:
  name, short_name, start_url, display: standalone
  icons: 192×192 + 512×512 + maskable 512×512
  theme_color, background_color, shortcuts

PUSH NOTIFICATIONS FLOW:
  requestPermission → subscribe (VAPID) → send to server
  Server: webpush.sendNotification(subscription, payload)
  SW: push event → showNotification → notificationclick → clients.openWindow

BACKGROUND SYNC:
  reg.sync.register('tag') → SW sync event → retry until success
  Use: form submissions, analytics, payments while offline

INSTALLABILITY:
  beforeinstallprompt → defer → show custom button → deferredPrompt.prompt()

WORKBOX: routing + strategy objects; Workbox precacheAndRoute for build output
