1. WHAT IS A MONOREPO?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A monorepo stores multiple projects/packages in a single repository.
Contrast with polyrepo (each project in its own repo).

MONOREPO STRUCTURE EXAMPLE:
  my-monorepo/
  ├── apps/
  │   ├── web/          ← Next.js frontend
  │   ├── api/          ← Node.js/Spring Boot backend
  │   └── mobile/       ← React Native
  ├── packages/
  │   ├── ui/           ← Shared component library
  │   ├── utils/        ← Shared utilities
  │   ├── types/        ← Shared TypeScript types
  │   └── config/       ← Shared ESLint/TS config
  ├── package.json      ← Root workspace config
  └── turbo.json        ← Turborepo pipeline config

BENEFITS:
  ✅ Atomic commits across projects (frontend + backend change together)
  ✅ Single source of truth for shared code (no versioning of shared packages)
  ✅ Easier cross-project refactoring
  ✅ Unified CI/CD pipeline
  ✅ Consistent tooling and dependency versions

CHALLENGES:
  ❌ Larger repository — slower clone, larger checkout
  ❌ Build performance — need smart caching to avoid rebuilding everything
  ❌ CI complexity — need to detect what changed and only build affected packages
  ❌ Governance — harder to restrict access to specific packages

USED BY:
  Google (entire codebase), Meta, Twitter, Microsoft, Airbnb, Vercel

2. PNPM WORKSPACES (Foundation Layer)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

pnpm workspaces (like npm/yarn workspaces) enable multiple packages in one repo
to share node_modules and cross-reference each other.

SETUP:
  # pnpm-workspace.yaml (root of repo)
  packages:
    - 'apps/*'
    - 'packages/*'

  # packages/ui/package.json
  {
    "name": "@myorg/ui",
    "version": "1.0.0"
  }

  # apps/web/package.json
  {
    "name": "web",
    "dependencies": {
      "@myorg/ui": "workspace:*"   ← Links to local package, not npm
    }
  }

INSTALLING WITH PNPM:
  pnpm install              # Install all workspace packages
  pnpm --filter web dev     # Run dev only in apps/web
  pnpm --filter @myorg/ui build   # Build only the UI package

WHY PNPM OVER NPM/YARN FOR MONOREPOS:
  - Content-addressable storage: each package version stored once on disk
  - Symlinks: packages linked, not copied — much faster and smaller disk usage
  - Strict: packages can only import what they declare in package.json
    (no phantom dependencies — a common npm workspace bug)
  - Faster install times in large repos

3. TURBOREPO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Created by: Jared Palmer (acquired by Vercel in 2021)
Language: Go (fast binary), JS config

WHAT IT DOES:
  Turborepo is a high-performance build system for monorepos. It adds:
  1. Task pipeline: define dependency order between tasks across packages
  2. Local caching: cache build outputs — if inputs haven't changed, skip the task
  3. Remote caching: share cache between developers and CI (via Vercel or self-hosted)
  4. Parallel execution: run tasks across packages in parallel

TURBO.JSON CONFIGURATION:
  {
    "$schema": "https://turbo.build/schema.json",
    "pipeline": {
      "build": {
        "dependsOn": ["^build"],   // ^ = run parent package's build first
        "outputs": [".next/**", "dist/**"]  // Cache these directories
      },
      "test": {
        "dependsOn": ["build"],
        "outputs": ["coverage/**"]
      },
      "lint": {
        "outputs": []              // No output to cache
      },
      "dev": {
        "cache": false,            // Never cache dev server
        "persistent": true         // Long-running task
      }
    }
  }

RUNNING TASKS:
  turbo run build          # Build all packages in correct order
  turbo run build --filter=web   # Build only web and its dependencies
  turbo run test --filter=...@myorg/ui  # Test packages that depend on @myorg/ui

HOW CACHING WORKS:
  Turbo hashes:
  - All source files in the package
  - Environment variables
  - turbo.json config
  If the hash matches a previous run → restore cached output, skip task.
  Result: if you only change apps/web, packages/ui doesn't rebuild.

REMOTE CACHING (team shared cache):
  turbo login                # Authenticate with Vercel
  turbo link                 # Link repo to Vercel remote cache

  Now all team members and CI share the same cache.
  CI run by Alice caches the build → Bob's CI skips the build entirely.

4. NX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Created by: Nrwl (now Nx, Inc.)
Language: TypeScript/Node

WHAT IT DOES (more opinionated than Turborepo):
  - Task pipeline with caching (like Turbo)
  - Code generation: nx generate @nx/react:component Button
  - Affected analysis: nx affected --target=test (only test what changed)
  - Dependency graph visualization: nx graph
  - Plugin ecosystem: @nx/react, @nx/next, @nx/node, @nx/java, etc.
  - Enforced module boundaries: ESLint rules preventing wrong cross-package imports

NX.JSON CONFIGURATION:
  {
    "tasksRunnerOptions": {
      "default": {
        "runner": "nx/tasks-runners/default",
        "options": {
          "cacheableOperations": ["build", "test", "lint"]
        }
      }
    },
    "targetDefaults": {
      "build": {
        "dependsOn": ["^build"]
      }
    }
  }

AFFECTED COMMANDS (key differentiator from Turbo):
  # Find and test only packages affected by changes on current branch:
  nx affected --target=test --base=main --head=HEAD

  # This uses the dependency graph to determine what actually changed:
  # If you changed packages/ui, Nx knows apps/web depends on it → test both
  # If you only changed apps/api, Nx skips apps/web tests

MODULE BOUNDARIES (enforce architecture):
  // .eslintrc.json
  {
    "rules": {
      "@nx/enforce-module-boundaries": ["error", {
        "allow": [],
        "depConstraints": [
          {
            "sourceTag": "scope:frontend",
            "onlyDependOnLibsWithTags": ["scope:frontend", "scope:shared"]
          },
          {
            "sourceTag": "scope:backend",
            "onlyDependOnLibsWithTags": ["scope:backend", "scope:shared"]
          }
        ]
      }]
    }
  }
  // Frontend code cannot import backend code — enforced at lint time

5. TURBOREPO vs NX — COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Aspect                Turborepo              Nx
  ──────────────────────────────────────────────────────────────────
  Philosophy            Minimal, fast          Feature-rich, opinionated
  Config complexity     Low (turbo.json)       Higher (nx.json + project.json)
  Code generation       ❌ No                  ✅ Yes (nx generate)
  Affected analysis     Via --filter           ✅ nx affected (smarter)
  Dep graph visual      Basic                  ✅ Interactive graph
  Module boundaries     ❌ No                  ✅ ESLint enforcement
  Plugin ecosystem      Minimal                Extensive (@nx/react, @nx/java)
  Learning curve        Low                    Medium-High
  Remote caching        Via Vercel             Via Nx Cloud
  Performance           Excellent (Go binary)  Excellent (Node + daemon)
  Best for              Simple monorepos,      Large enterprise teams,
                        Vercel-deployed apps   polyglot repos, strict arch

CHOOSE TURBOREPO IF:
  - You want minimal config and fast setup
  - Your repo is primarily Next.js/React and deployed on Vercel
  - You don't need code generation or architecture enforcement

CHOOSE NX IF:
  - Large team with strict architecture rules
  - Need code generation and scaffolding
  - Full-stack monorepo (React + Node + possibly Java via @nx/gradle)
  - Need smart affected analysis for very large repos

6. INTERVIEW QUESTIONS — MONOREPO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is a monorepo and what are its benefits over polyrepo?
A: A monorepo stores multiple projects in a single repository. Benefits:
   atomic commits across projects (frontend and backend change together in one PR),
   shared packages without versioning overhead, easier cross-project refactoring,
   and unified tooling. Polyrepo benefits: smaller repos, simpler access control,
   each team has full autonomy. For large orgs with tight coupling between
   frontend and backend, monorepos reduce coordination overhead significantly.

Q: What is the purpose of Turborepo's caching?
A: Turborepo hashes the inputs of each task (source files, env vars, config).
   If the hash matches a previous run, it restores the cached output and skips
   execution. This means: if only apps/web changed, packages/ui doesn't
   rebuild. With remote caching (Vercel), this cache is shared across the whole
   team and CI — so if Alice already built the UI package, Bob's CI pipeline
   retrieves the cache instead of rebuilding from scratch. In large repos,
   this can reduce CI times from 20 minutes to under 2 minutes.

Q: What does "affected" mean in Nx?
A: nx affected --target=test analyzes the dependency graph of the monorepo
   and runs tests only for packages that were changed OR depend on what changed.
   Example: if you modified packages/ui, Nx knows that apps/web depends on
   packages/ui, so it tests both. If you only changed apps/api, apps/web tests
   are skipped entirely. This is smarter than Turborepo's --filter because Nx
   builds a full dependency graph and traverses it, while Turbo requires more
   explicit filter expressions.

Q: How does pnpm differ from npm/yarn in a monorepo context?
A: pnpm uses a content-addressable store and symlinks. Each package version
   is stored once on disk globally, and workspaces symlink to it rather than
   copying. This makes install dramatically faster in large repos and saves
   gigabytes of disk space. pnpm is also strict: packages can only import
   modules they explicitly declare in package.json — preventing "phantom
   dependency" bugs where a package accidentally uses a transitive dependency
   that another package installed. npm workspaces hoist everything to root
   node_modules, which makes phantom dependencies common.
