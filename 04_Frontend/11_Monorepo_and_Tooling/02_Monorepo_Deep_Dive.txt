SECTION 1 — MONOREPO FUNDAMENTALS
================================================================================

Q1: What is a monorepo and why would you choose it over a polyrepo?

A: A monorepo (monolithic repository) stores multiple projects, packages, or
   services in a single version-controlled repository.

   MONOREPO vs POLYREPO COMPARISON:
   ┌────────────────────┬─────────────────────────┬─────────────────────────┐
   │ Aspect             │ Monorepo                │ Polyrepo                │
   ├────────────────────┼─────────────────────────┼─────────────────────────┤
   │ Code sharing       │ Direct import (no       │ Publish + install npm   │
   │                    │ publishing needed)      │ package per change      │
   │ Atomic changes     │ One commit for          │ Multiple PRs + version  │
   │                    │ cross-package refactor  │ bumps to coordinate     │
   │ Visibility         │ See all code in one     │ Context switching       │
   │                    │ place; easier discovery │ between repos           │
   │ CI complexity      │ Need smart tooling      │ Simple per-repo CI      │
   │                    │ (affected builds)       │                         │
   │ Dependency mgmt    │ Shared node_modules     │ Each repo manages deps  │
   │                    │ (deduplication)         │ independently           │
   │ Examples           │ Google, Meta, Microsoft │ Netflix, early Amazon   │
   │                    │ Nx Enterprise templates │                         │
   └────────────────────┴─────────────────────────┴─────────────────────────┘

   WHEN TO CHOOSE MONOREPO:
   ✓ Shared UI component library + multiple apps consuming it
   ✓ Full-stack apps where frontend and backend types should be shared
   ✓ Teams that frequently refactor across package boundaries
   ✓ You want atomic deployments across multiple services

   TYPICAL MONOREPO STRUCTURE:
   /
   ├── apps/
   │   ├── portal/          (Next.js customer portal)
   │   ├── admin/           (React admin panel)
   │   └── api/             (Express/NestJS backend)
   ├── packages/
   │   ├── ui/              (shared component library)
   │   ├── types/           (shared TypeScript types)
   │   ├── utils/           (shared utility functions)
   │   └── config/          (shared ESLint, TS configs)
   ├── package.json
   └── nx.json / turbo.json

SECTION 2 — TURBOREPO
================================================================================

Q2: How does Turborepo work and what problems does it solve?

A: Turborepo is a high-performance build system for JavaScript/TypeScript monorepos.

   KEY FEATURES:
   1. TASK PIPELINES: define build order (types must build before apps that use them)
   2. LOCAL CACHE: skip work when inputs haven't changed (hash-based)
   3. REMOTE CACHE: share cache across developers and CI machines (Vercel or self-hosted)
   4. PARALLEL EXECUTION: run independent tasks concurrently automatically

   turbo.json CONFIGURATION:
   {
     "pipeline": {
       "build": {
         "dependsOn": ["^build"],  // ^ = build all dependencies first
         "outputs": [".next/**", "dist/**"]
       },
       "test": {
         "dependsOn": ["build"],
         "outputs": []
       },
       "lint": {
         "outputs": []
       },
       "dev": {
         "cache": false,
         "persistent": true
       }
     }
   }

   HOW CACHING WORKS:
   - Input hash = hash of source files + env vars + task config
   - If hash matches cached result → skip execution, restore outputs
   - Cache hit rate of 80%+ is typical in active monorepos

   COMMANDS:
   turbo run build                  # Build all packages in dependency order
   turbo run build --filter=portal  # Build only portal and its deps
   turbo run build --affected       # Build only changed packages + dependents
   turbo run build --dry-run        # Show what would run without running it

   REMOTE CACHE SETUP:
   # .env or turbo.json
   TURBO_TOKEN=your-vercel-token
   TURBO_TEAM=your-team-name

   # Or self-hosted with Turborepo Remote Cache:
   turbo run build --api="https://your-cache.company.com"

Q3: How does Turborepo differ from Nx?

A:
   TURBOREPO:
   - Zero config focus: minimal setup, convention-over-configuration
   - Created by Vercel; tight integration with Next.js
   - Task runner only: no code generation, no project graph UI out of box
   - Best for: small-medium teams that want fast builds with minimal setup

   NX:
   - Feature-rich: built-in code generators, module boundaries, dependency graph UI
   - Plugin ecosystem: @nx/react, @nx/next, @nx/node, @nx/java (!)
   - Enforces architecture via module boundary rules (nx enforce-module-boundaries)
   - Nx Console VS Code extension for GUI-based generator usage
   - Best for: larger teams needing governance, generators, and architecture enforcement

   NX-SPECIFIC FEATURES:
   nx.json — define affected computation algorithms, nx cloud token
   project.json — per-project target definitions (replaces package.json scripts)
   nx graph — interactive dependency graph visualization in browser
   nx affected:build — only builds projects affected by current git changes
   nx generate @nx/react:component MyButton --project=ui — code generator

SECTION 3 — WORKSPACE PACKAGE MANAGERS
================================================================================

Q4: Compare Yarn Workspaces, PNPM Workspaces, and npm Workspaces.

A:
   YARN WORKSPACES (classic Yarn 1):
   package.json at root:
   {
     "private": true,
     "workspaces": ["apps/*", "packages/*"]
   }
   - Hoists shared dependencies to root node_modules
   - Symbolic links: packages/* appear in root node_modules/
   - yarn workspace portal add react  → adds react to portal's package.json

   PNPM WORKSPACES (recommended for large monorepos):
   pnpm-workspace.yaml:
   packages:
     - 'apps/*'
     - 'packages/*'
   - Uses content-addressable store: one copy per package version globally
   - Hard links: node_modules is fast; saves significant disk space
   - Strict by default: can't accidentally import undeclared deps (no hoisting)
   - pnpm add react --filter=portal

   NPM WORKSPACES (npm 7+):
   Same as Yarn but in package.json:
   { "workspaces": ["apps/*", "packages/*"] }
   - Less mature than Yarn/PNPM for large repos
   - Simpler for teams already on npm

   WHY PNPM IS PREFERRED FOR LARGE REPOS:
   ✓ 50-80% less disk space (content-addressable store)
   ✓ Strict dependency isolation (no phantom dependencies)
   ✓ Faster installs due to hard-linking
   ✓ pnpm dlx (like npx) without polluting global store

   CROSS-PACKAGE IMPORTS (workspace protocol):
   In portal/package.json:
   { "dependencies": { "@myorg/ui": "workspace:*" } }
   → Uses local packages/ version, not npm registry

SECTION 4 — CHANGESETS (VERSIONING & CHANGELOG)
================================================================================

Q5: What are Changesets and how do they solve versioning in monorepos?

A: Changesets is a tool for managing package versions and changelogs in
   JavaScript/TypeScript monorepos.

   PROBLEM WITHOUT CHANGESETS:
   - You have ui, utils, portal, admin packages
   - You add a feature to ui → which packages should bump version?
   - Who writes the changelog? In which package?
   - Manually tracking this across hundreds of PRs = chaos

   CHANGESETS WORKFLOW:
   1. Developer makes a change to packages/ui
   2. Runs: pnpm changeset
      → Prompted: "Which packages changed?" → select ui
      → "What kind of change?" → patch/minor/major
      → "Describe the change" → "Add Button loading state"
   3. A .changeset/abc123.md file is committed with the PR:
      ---
      "ui": minor
      ---
      Add Button loading state prop to support async actions

   4. When ready to release: pnpm changeset version
      → Reads all .changeset/ files
      → Bumps package versions (semver)
      → Updates CHANGELOG.md for each changed package
      → Deletes .changeset/ files

   5. pnpm changeset publish
      → Publishes changed packages to npm

   GITHUB ACTIONS INTEGRATION (automated):
   - Changesets Release Action creates a "Version Packages" PR automatically
   - When merged, automatically publishes to npm
   - Zero manual npm publish commands

   CHANGESET COMMANDS:
   pnpm changeset         # Create a new changeset
   pnpm changeset version # Apply changesets → bump versions
   pnpm changeset publish # Publish packages to npm
   pnpm changeset status  # Show pending changesets

SECTION 5 — MODULE BOUNDARIES AND ARCHITECTURE ENFORCEMENT
================================================================================

Q6: How do you enforce clean architecture in a monorepo?

A: NX MODULE BOUNDARY RULES:

   // nx.json or .eslintrc
   "@nx/enforce-module-boundaries": ["error", {
     "depConstraints": [
       // Apps can only import from packages (not other apps)
       { "sourceTag": "type:app", "onlyDependOnLibsWithTags": ["type:lib"] },
       // UI components cannot import from server-side packages
       { "sourceTag": "scope:ui", "notDependOnLibsWithTags": ["scope:server"] },
       // Shared utils can only import other utils
       { "sourceTag": "type:util", "onlyDependOnLibsWithTags": ["type:util"] }
     ]
   }]

   TAG STRATEGY (project.json per package):
   apps/portal/project.json:   { "tags": ["type:app", "scope:portal"] }
   packages/ui/project.json:   { "tags": ["type:lib", "scope:ui"] }
   packages/utils/project.json:{ "tags": ["type:util", "scope:shared"] }

   RESULT: ESLint fails if an app tries to import from another app,
   or if UI imports server-only code (API keys, DB connections, etc.)

QUICK REFERENCE CHEAT SHEET
================================================================================

TOOLING COMPARISON:
  Turborepo: zero-config task runner; best with Next.js/Vercel; remote cache
  Nx:        full-featured; generators; module boundaries; project graph; plugin ecosystem
  Lerna:     original monorepo tool; now uses Nx under the hood

WORKSPACE MANAGERS:
  Yarn 1 workspaces: simple, widely supported
  PNPM workspaces:   best for large repos; strict; disk-efficient; fast
  npm workspaces:    built-in with npm 7+; less mature

CHANGESETS:
  pnpm changeset        → create changeset (per PR)
  pnpm changeset version → bump versions + write changelogs
  pnpm changeset publish → publish to npm

TURBOREPO CACHE:
  Input hash = source files + env + config hash
  Cache hit → skip task; restore outputs from cache
  Remote cache: share across CI runs; 80%+ hit rate typical
  turbo run build --filter=portal  → only build portal + its deps

MODULE BOUNDARIES (Nx):
  Tags per project → depConstraints in ESLint → enforced at lint time
  Apps import from libs only | UI libs cannot import server libs
