================================================================
AUTH INTEGRATION INTERVIEW QUESTIONS
================================================================

Deep-dive Q&A covering JWT, OAuth2, session management, and
React authentication patterns.

================================================================
SECTION 1: JWT FUNDAMENTALS
================================================================

Q: What are the three parts of a JWT?
A: Header (Base64URL-encoded JSON with alg and typ), Payload
   (Base64URL-encoded JSON with claims: sub, iat, exp, roles, etc.),
   and Signature (HMACSHA256 or RSA-signed hash of header + payload).
   The signature allows the server to verify the token without a
   database lookup. JWTs are NOT encrypted — only signed (unless using JWE).

Q: Where should you store JWT access tokens in a React SPA?
A: In memory (module-level variable or React state). Never in
   localStorage (XSS can steal it) and not in regular cookies (CSRF risk).
   Refresh tokens should go in httpOnly, Secure, SameSite=Strict cookies
   (inaccessible to JavaScript, protected from XSS). This is the
   recommended secure architecture.

Q: What is the difference between access token and refresh token?
A: Access token: short-lived (15 min – 1 hour), sent with every API
   request in the Authorization header. Refresh token: long-lived
   (days/weeks), stored in httpOnly cookie, used only to get new
   access tokens. Separating them limits exposure: if an access token
   leaks, it expires quickly; the refresh token is protected from XSS.

Q: What is token refresh rotation?
A: Every time a refresh token is used, the server invalidates it and
   issues a new one. If an attacker steals and uses a refresh token,
   the legitimate user's next use will fail (server detects reuse),
   triggering a forced logout. This is a best practice for httpOnly
   refresh token cookies.

Q: How do you handle a JWT expiring while the user is actively using the app?
A: Two approaches: (1) Reactive — on any 401 response, trigger a
   token refresh before retrying the original request (interceptor
   pattern). (2) Proactive — use jwtDecode to get the exp claim,
   schedule a refresh ~60 seconds before expiry with setTimeout.
   Combine both for robustness.

SECTION 2: OAUTH2 AND OIDC
================================================================

Q: What is the OAuth2 Authorization Code flow with PKCE?
A: PKCE (Proof Key for Code Exchange) secures the Authorization Code
   flow for public clients (SPAs) that can't store secrets:
   1. Generate code_verifier (random 43-128 chars)
   2. Hash it: code_challenge = BASE64URL(SHA256(code_verifier))
   3. Redirect to /authorize with code_challenge
   4. User authenticates, server redirects back with code
   5. Exchange code + code_verifier for tokens (no client_secret needed)
   Prevents authorization code interception: even if code is stolen,
   the attacker doesn't have the code_verifier.

Q: What is the state parameter in OAuth2 and why is it important?
A: state is a random value included in the /authorize redirect and
   returned in the callback. You store it (localStorage/sessionStorage)
   and verify it matches on callback. It prevents CSRF attacks against
   the OAuth callback endpoint — without it, an attacker could trick
   the user into accepting a code for the attacker's account.

Q: What is the difference between OAuth2 and OIDC?
A: OAuth2 is an authorization framework — it grants access to resources.
   OIDC (OpenID Connect) is an identity layer on top of OAuth2 that
   adds authentication — it issues an id_token (JWT) containing user
   identity claims (name, email, sub). Use access_token for API calls,
   id_token to identify the user in the frontend.

Q: What is the difference between Keycloak and Auth0?
A: Keycloak is open-source and self-hosted (you manage infra, updates).
   Auth0 is a managed cloud service (SaaS, you pay per MAU). Keycloak
   is preferred in enterprises that need data sovereignty, private
   deployments, or custom storage. Auth0 is faster to set up, has
   extensive social login support, and handles scaling automatically.

Q: How does SSO (Single Sign-On) work with Keycloak?
A: All apps register as clients in the same Keycloak realm. When
   a user logs in to App A, Keycloak creates a session. When the
   same user visits App B, Keycloak redirects back with a token
   without prompting for credentials again (check-sso). Logout from
   one app triggers back-channel logout to all apps in the realm.

SECTION 3: REACT AUTH IMPLEMENTATION
================================================================

Q: How do you implement protected routes in React Router v6?
A: Create a ProtectedRoute component that reads auth state from context.
   If not authenticated, redirect to /login with location.state.from
   set to the current path. After login, redirect back to the intended
   route. Use <Outlet> for nested routes:
     <Route element={<ProtectedRoute />}>
       <Route path="/dashboard" element={<Dashboard />} />
     </Route>

Q: How do you implement role-based access control in React?
A: Add roles to the auth context (decoded from JWT). Create a RoleRoute
   component that checks allowedRoles against user.roles. For UI-level
   guards, create a <Can role="ADMIN"> component that renders children
   only if the user has the role. Always enforce RBAC on the server —
   client-side is UX only, not security.

Q: How do you persist authentication across page refreshes?
A: Don't store access tokens in localStorage. Instead: (1) store the
   access token in memory (reset on page refresh), (2) on app init,
   call /auth/refresh endpoint — if the httpOnly refresh cookie is
   valid, the server returns a new access token. This "silent refresh
   on mount" pattern restores auth state without exposing the refresh
   token to JavaScript.

Q: What happens to pending API requests when the token refresh happens?
A: Use the failedQueue pattern in the Axios 401 interceptor:
   - First 401: set isRefreshing = true, start refresh
   - Subsequent 401s: push {resolve, reject} pairs to failedQueue
   - On refresh success: call processQueue(null, newToken) → retry all queued requests
   - On refresh failure: call processQueue(error, null) → reject all → logout

Q: How do you clean up auth state on logout?
A: (1) Call /auth/logout on server to invalidate refresh token cookie
   and server-side session. (2) Clear access token from memory.
   (3) Call queryClient.clear() to remove all cached React Query data
   (which may contain sensitive user data). (4) Clear any user state
   in Zustand/Context. (5) Redirect to /login. Broadcast a custom
   'auth:logout' event so other tabs can log out simultaneously.

SECTION 4: CSRF AND SECURITY
================================================================

Q: What is a CSRF attack?
A: A Cross-Site Request Forgery attack tricks the user's browser into
   making a request to your API using the user's cookies (sent
   automatically). Example: attacker hosts a page with:
     <form action="https://bank.com/transfer" method="POST">
   When the logged-in user visits the attacker's page, the browser
   submits the form with the bank's cookies. CSRF only applies to
   cookie-based auth, not Bearer token auth (token must be explicitly
   set in headers by JavaScript).

Q: How does Spring Boot protect against CSRF?
A: Spring Security's default CSRF protection uses the Synchronizer
   Token Pattern. It sets a CSRF token in a cookie, and requires the
   same token in a request header (X-CSRF-TOKEN). For SPAs, use
   CookieCsrfTokenRepository.withHttpOnlyFalse() so JavaScript can
   read the cookie and set the header.
   Spring's default xsrf-token cookie name maps to Axios's built-in
   xsrfCookieName: 'XSRF-TOKEN' config.

Q: Does Bearer token auth need CSRF protection?
A: No. CSRF exploits the fact that cookies are sent automatically by
   the browser. Bearer tokens in Authorization headers must be
   explicitly set by JavaScript. An attacker's page can't read your
   token (same-origin policy) and can't set the Authorization header
   via a form submission. Therefore, JWT in header = no CSRF risk.

Q: What is the SameSite cookie attribute?
A: Controls when cookies are sent in cross-origin requests:
   Strict — never sent in cross-site requests (most secure, breaks SSO)
   Lax — sent only for top-level navigation GET requests (default)
   None — always sent (requires Secure=true)
   SameSite=Strict on refresh token cookies prevents CSRF against the
   refresh endpoint.

SECTION 5: ADVANCED SCENARIOS
================================================================

Q: How would you handle a user logging in from two tabs simultaneously?
A: Use the BroadcastChannel API or a localStorage event listener to
   communicate between tabs. When tab A refreshes the token, broadcast
   the new token to other tabs so they don't need to refresh again.
   For logout: broadcast 'auth:logout', all tabs clear state and
   redirect to /login.

Q: What is the risk of storing JWTs in localStorage?
A: Any JavaScript running on the page (including injected scripts from
   XSS attacks, third-party scripts, ads) can read localStorage.
   If your site has any XSS vulnerability, tokens in localStorage
   can be stolen. httpOnly cookies are inaccessible to any JavaScript.

Q: How would you implement "remember me" functionality securely?
A: Without "remember me": access token in memory (lost on tab close),
   refresh token in session cookie (expires on browser close).
   With "remember me": use a persistent httpOnly cookie (expires days later).
   Set Max-Age in Set-Cookie. Implement refresh token rotation and
   absolute expiry on the server to limit attack window.

Q: How do you test auth flows in a React app?
A: (1) Mock auth context in unit tests with a custom provider.
   (2) MSW (Mock Service Worker) intercepts requests including
   /auth/token, /auth/refresh. (3) Cypress for E2E — use cy.session()
   to preserve auth state across tests. (4) Test each route with
   different auth states (unauthenticated, authenticated, various roles).
