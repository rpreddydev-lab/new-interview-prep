REACT PERFORMANCE INTERVIEW QUESTIONS
================================================================

Covers: React rendering, memo, useMemo, useCallback, reconciliation,
        concurrent mode, virtualization, profiling, and patterns.

================================================================
RENDERING AND RE-RENDERS
================================================================

Q1: When does a React component re-render?
───────────────────────────────────────────
A: A component re-renders in these situations:
   
   1. STATE CHANGES: When setState / useState setter is called
      (even with same value — React 18 bails out after comparing, but
       older React may still re-render)
   
   2. PROPS CHANGE: When parent re-renders with different props values
   
   3. PARENT RE-RENDERS: When a parent component re-renders, ALL children
      re-render by default (even with same props) — this is the most
      common source of unnecessary re-renders
   
   4. CONTEXT CHANGES: When a context value changes, ALL consumers re-render
   
   5. HOOKS CHANGE: useReducer dispatch, useSyncExternalStore
   
   6. forceUpdate() (class components)
   
   EXCEPTION: React.memo prevents re-renders when props are shallowly equal.
   React.PureComponent does the same for class components.

──────────────────────────────────────────────────────────────

Q2: What is React reconciliation and how does the diffing algorithm work?
──────────────────────────────────────────────────────────────────────────
A: Reconciliation is React's process of updating the DOM efficiently when
   the component tree changes. Instead of re-rendering the entire DOM,
   React compares the new virtual DOM tree with the previous one (diffing).
   
   FIBER ARCHITECTURE:
   React 16+ uses Fiber — a reconciler that breaks work into units ("fibers")
   that can be interrupted, paused, prioritized, and resumed.
   This enables Concurrent Mode in React 18.
   
   DIFFING RULES (O(n) algorithm assumptions):
   1. ELEMENTS OF DIFFERENT TYPE → tear down entire subtree and rebuild
      <div>...</div> → <span>...</span> → destroys all children
   
   2. SAME TYPE ELEMENT → update attributes, recurse into children
      <div className="old"> → <div className="new"> → only className updated
   
   3. LIST ITEMS: Without key → O(n²) comparisons, poor performance
      With key → O(n) comparisons using key as identity marker
   
   KEYS MUST BE:
   - Stable: Same key = same component instance (DOM reused)
   - Unique within siblings
   - NOT array index (when order can change):
     Reordering with index keys → React "matches" wrong items → bugs + re-mounts

──────────────────────────────────────────────────────────────

Q3: Explain React.memo — what it does and when you should use it.
──────────────────────────────────────────────────────────────────
A: React.memo is a Higher Order Component that wraps a function component
   and skips re-rendering if the component's props haven't changed
   (shallow equality comparison).
   
   const MyComponent = React.memo(function MyComponent({ name, count }) {
     return <div>{name}: {count}</div>;
   });
   
   WHEN TO USE:
   - Component is "pure" (renders same output for same props)
   - Component re-renders frequently with SAME props
   - Component is expensive to render
   
   WHEN NOT TO USE:
   - Component always receives new props (memo overhead with no benefit)
   - Component renders rarely anyway
   - Component has local state/effects that change independently
   
   CUSTOM COMPARATOR (deep comparison when needed):
   const MyComponent = React.memo(
     function MyComponent({ items }) {
       return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
     },
     (prevProps, nextProps) => {
       // Return true = same props (skip re-render)
       // Return false = props changed (re-render)
       return prevProps.items.length === nextProps.items.length
         && prevProps.items.every((item, i) => item.id === nextProps.items[i].id);
     }
   );
   
   GOTCHA: React.memo is BROKEN if you pass new object/function refs each render:
   <Memoized onClick={() => handleClick(id)} />  // New function every render!
   → Needs useCallback on the parent side

──────────────────────────────────────────────────────────────

Q4: When should you use useMemo vs useCallback?
─────────────────────────────────────────────────
A: 
   useMemo: Memoizes a COMPUTED VALUE. Recalculates only when deps change.
   const sortedItems = useMemo(
     () => items.sort((a, b) => a.name.localeCompare(b.name)),
     [items]
   );
   // sortedItems is the same reference unless items changes
   
   useCallback: Memoizes a FUNCTION. Returns same function reference.
   const handleSubmit = useCallback((data) => {
     submitForm(id, data);
   }, [id]);
   // handleSubmit is the same reference unless id changes
   
   WHEN TO USE useMemo:
   - Expensive computations (sorting, filtering large arrays)
   - Creating objects/arrays passed to React.memo children (stable reference)
   - Values used in useEffect dependencies that would otherwise change every render
   
   WHEN TO USE useCallback:
   - Functions passed as props to React.memo children
   - Functions used in useEffect deps (avoiding infinite loops)
   - Event handlers passed to optimized child components
   
   WHEN NOT TO USE EITHER:
   - Simple values and functions that are cheap to create
   - Components that always re-render anyway (React.memo not applied)
   - The optimization cost > the optimization benefit
   
   RULE: Profile first, optimize second. Premature memoization adds
   code complexity. Only memoize when you have a measured performance problem.

──────────────────────────────────────────────────────────────

Q5: What is the problem with "passing a new object as a prop" to a memoized component?
───────────────────────────────────────────────────────────────────────────────────────
A: React.memo uses SHALLOW equality: it compares each prop with ===.
   Objects and functions are compared by REFERENCE, not by value.
   
   // Parent re-renders:
   function Parent() {
     // BUG: New object created on every render
     return <Child config={{ theme: 'dark', size: 'lg' }} />;
     // config's VALUE is the same, but the REFERENCE is new!
   }
   
   // React.memo sees: prevProps.config !== nextProps.config (different reference)
   // → Child re-renders even though values haven't changed!
   
   FIXES:
   
   1. Memoize the object in parent:
   function Parent() {
     const config = useMemo(() => ({ theme: 'dark', size: 'lg' }), []);
     return <Child config={config} />;
   }
   
   2. Move constant outside component:
   const CONFIG = { theme: 'dark', size: 'lg' }; // Created once
   function Parent() {
     return <Child config={CONFIG} />;
   }
   
   3. Spread primitive props (avoid object props entirely):
   function Parent() {
     return <Child theme="dark" size="lg" />; // Primitives compare by value
   }

CONTEXT AND STATE

Q6: How do you prevent context from causing unnecessary re-renders?
────────────────────────────────────────────────────────────────────
A: PROBLEM: Every context value change causes ALL consumers to re-render,
   even those that only use a portion of the context value.
   
   // ❌ Single context with frequently changing value:
   const AppContext = createContext();
   const [user, setUser] = useState(null);
   const [theme, setTheme] = useState('dark');
   
   // When user changes, EVERY consumer re-renders (including theme-only ones)
   <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
   
   SOLUTIONS:
   
   1. SPLIT CONTEXTS (best solution):
   const UserContext = createContext();
   const ThemeContext = createContext();
   
   // Only UserContext consumers re-render on user change
   // ThemeContext consumers only re-render on theme change
   
   2. MEMOIZE CONTEXT VALUE:
   const contextValue = useMemo(
     () => ({ user, theme }),
     [user, theme]
   );
   <AppContext.Provider value={contextValue}>
   // Prevents re-renders when Parent re-renders but user/theme unchanged
   
   3. USE ZUSTAND / JOTAI FOR FINE-GRAINED SUBSCRIPTIONS:
   // Zustand: components only re-render when selected slice changes
   const user = useStore(state => state.user);
   // Only re-renders when state.user changes (not entire store)
   
   4. SEPARATE STABLE AND UNSTABLE VALUES:
   <UserProvider>           // User data (changes on login/logout)
     <UserActionsProvider>  // Dispatch functions (STABLE — never change)
       <App />
     </UserActionsProvider>
   </UserProvider>
   // Components that only need dispatch functions use UserActionsContext
   // and NEVER re-render on user data changes

Q7: What is state colocation and how does it improve performance?
──────────────────────────────────────────────────────────────────
A: State colocation means placing state as close as possible to where it's
   used. Lifting state unnecessarily high causes excessive re-renders.
   
   // ❌ State lifted too high — entire app re-renders on input change
   function App() {
     const [searchQuery, setSearchQuery] = useState('');
     return (
       <div>
         <SearchBox query={searchQuery} onChange={setSearchQuery} />
         <HeavyDashboard />  // Re-renders every keypress!
       </div>
     );
   }
   
   // ✅ State colocated in SearchBox — only SearchBox re-renders
   function App() {
     return (
       <div>
         <SearchBox />  // Owns its own query state
         <HeavyDashboard />  // Never re-renders due to search!
       </div>
     );
   }
   
   function SearchBox() {
     const [query, setQuery] = useState('');  // Local, isolated
     return <input value={query} onChange={e => setQuery(e.target.value)} />;
   }
   
   COROLLARY - State Lifting: Only lift state when multiple components
   genuinely need to share it. Don't lift "just in case."

Q8: What is virtualization and when should you use it?
───────────────────────────────────────────────────────
A: Virtualization (windowing) renders only the visible portion of a list.
   Instead of 10,000 DOM nodes for 10,000 items, only ~20 nodes (visible)
   are rendered. Items are added/removed as user scrolls.
   
   WHEN TO USE:
   - Lists with > 100-200 items that are all visible
   - Tables with many rows
   - Feed-style interfaces (social media, chat)
   
   TOOLS:
   - @tanstack/react-virtual (most modern, headless)
   - react-window (lightweight, good for simple lists/grids)
   - react-virtuoso (dynamic heights, auto-scrolling to index)
   
   // @tanstack/react-virtual example:
   import { useVirtualizer } from '@tanstack/react-virtual';
   
   function VirtualList({ items }) {
     const parentRef = useRef(null);
     
     const virtualizer = useVirtualizer({
       count: items.length,
       getScrollElement: () => parentRef.current,
       estimateSize: () => 60, // estimated item height
     });
     
     return (
       <div ref={parentRef} style={{ height: '500px', overflow: 'auto' }}>
         <div style={{ height: `${virtualizer.getTotalSize()}px`, position: 'relative' }}>
           {virtualizer.getVirtualItems().map(virtualItem => (
             <div
               key={virtualItem.key}
               style={{
                 position: 'absolute',
                 top: 0,
                 transform: `translateY(${virtualItem.start}px)`,
                 height: `${virtualItem.size}px`,
               }}
             >
               {items[virtualItem.index].name}
             </div>
           ))}
         </div>
       </div>
     );
   }
   
   WHEN NOT TO USE:
   - Lists shorter than ~100 items (overhead > benefit)
   - When you need native scroll anchoring
   - SEO-critical content (non-rendered items aren't in DOM)

CONCURRENT FEATURES (REACT 18)
================================================================

Q9: How does React 18's Concurrent Mode work?
──────────────────────────────────────────────
A: React 18 Concurrent Mode allows React to work on multiple versions of
   the UI simultaneously and interrupt rendering to handle more urgent work.
   
   BEFORE (Synchronous React):
   - Once React starts rendering, it can't be interrupted
   - A 500ms render blocks user input for 500ms → bad INP
   
   WITH CONCURRENT MODE:
   - React splits rendering into small units of work
   - Between each unit, checks if higher-priority work exists
   - If user interaction detected → pauses current render → handles input
   - Then resumes rendering where it left off
   
   ENABLED BY:
   - ReactDOM.createRoot() (replaces ReactDOM.render() in React 18)
   
   KEY APIS:
   - useTransition(): Mark state updates as "non-urgent transitions"
   - useDeferredValue(): Defer a value update (debounce-like)
   - Suspense: Concurrent Suspense allows rendering incomplete trees
   - startTransition(): Wrap non-urgent updates without the isPending state
   
   The key insight: NOT all state updates are equal urgency.
   User input (typing, clicking) = HIGH priority
   UI response to data (filtering list) = LOW priority
   Concurrent Mode lets you express this distinction.

──────────────────────────────────────────────────────────────

Q10: Explain useDeferredValue and when you'd use it over useTransition.
────────────────────────────────────────────────────────────────────────
A: 
   useTransition: Wraps a STATE UPDATE to make it non-urgent
   useDeferredValue: Wraps a VALUE to create a deferred version
   
   // useTransition: you control the state setter
   const [isPending, startTransition] = useTransition();
   function handleSearch(query) {
     setUrgent(query);  // Urgent: update input immediately
     startTransition(() => {
       setDeferred(query);  // Non-urgent: update filtered list
     });
   }
   
   // useDeferredValue: you receive a prop/value you don't control
   function SearchResults({ query }) {
     // Deferred version lags behind during transitions
     const deferredQuery = useDeferredValue(query);
     const results = filterItems(deferredQuery);  // Uses deferred value
     
     const isStale = query !== deferredQuery;  // Show stale indicator
     return (
       <div style={{ opacity: isStale ? 0.5 : 1 }}>
         {results.map(r => <Item key={r.id} {...r} />)}
       </div>
     );
   }
   
   USE useDeferredValue when:
   - You receive a value as a prop and can't control the setter
   - You want to show stale content while new content renders
   - Third-party component handles the state
   
   USE useTransition when:
   - You own the state setter
   - You want the isPending state to show loading indicator

PROFILING

Q11: How do you use React Profiler to find performance bottlenecks?
────────────────────────────────────────────────────────────────────
A: React DevTools Profiler records renders and their causes.
   
   HOW TO USE:
   1. Install React DevTools extension
   2. Open DevTools > Profiler tab
   3. Click Record, interact with the app, stop recording
   
   WHAT IT SHOWS:
   - Flamechart: Each component as a bar, width = render time
     Wider bar = slower component
   - Ranked chart: Components sorted by render duration
   - "Why did this render?": Shows which prop/state/hook changed
   
   INTERPRETING RESULTS:
   - Find the tallest/widest bars → those are bottlenecks
   - Check "What caused this render?" → was it a state change?
     A prop change? A context change?
   - If "The parent component rendered" → memoize the child
   - If "Hook X changed" → check if the hook value is stable
   
   PROGRAMMATIC PROFILING:
   // Use React.Profiler component to measure specific subtrees:
   <Profiler id="ProductList" onRender={(id, phase, duration) => {
     if (duration > 16) { // 16ms = 60fps threshold
       console.warn(`${id} took ${duration}ms to ${phase}`);
     }
   }}>
     <ProductList />
   </Profiler>
   
   NOTE: Profile in PRODUCTION builds (development adds overhead).
   Add ?react_perf to URL or configure production profiling build.

Q12: What is the cause and fix for the "stale closure" problem?
────────────────────────────────────────────────────────────────
A: Stale closure: a function captures a variable from its closure at
   the time of creation, and reads an outdated value later.
   
   EXAMPLE:
   function Counter() {
     const [count, setCount] = useState(0);
     
     useEffect(() => {
       const timer = setInterval(() => {
         // BUG: count is always 0 (captured at effect creation)
         setCount(count + 1);  // Stale closure!
       }, 1000);
       return () => clearInterval(timer);
     }, []); // Empty deps → effect runs once → count captured as 0
   }
   
   FIXES:
   
   1. Functional update form (best for this case):
   setCount(prevCount => prevCount + 1); // Uses current value, not closure
   
   2. Add count to deps array (effect re-runs on each count change):
   useEffect(() => {
     const timer = setInterval(() => setCount(count + 1), 1000);
     return () => clearInterval(timer);
   }, [count]); // Restarts interval on each change (expensive)
   
   3. useRef to hold latest value:
   const countRef = useRef(count);
   useEffect(() => { countRef.current = count; }, [count]);
   // Use countRef.current in the interval (always up-to-date ref)

Q13: How do you avoid infinite loops with useEffect?
──────────────────────────────────────────────────────
A: Infinite loops happen when an effect creates or modifies something
   that's also in its dependency array.
   
   // ❌ INFINITE LOOP:
   useEffect(() => {
     setData(processData(data));  // Updates data → triggers effect again!
   }, [data]);
   
   // ❌ INFINITE LOOP (object comparison):
   const options = { sort: 'asc' };  // New object every render
   useEffect(() => {
     fetchData(options);
   }, [options]); // options !== options (different reference each render)
   
   FIXES:
   
   1. Remove the dependency if you only want to run once:
   useEffect(() => { fetchInitialData(); }, []); // Run once on mount
   
   2. Use functional update to avoid reading state in effect:
   useEffect(() => {
     setData(prev => processData(prev)); // Don't read data as dependency
   }, []); // Only run once
   
   3. Memoize objects used as dependencies:
   const options = useMemo(() => ({ sort: 'asc' }), []);
   useEffect(() => { fetchData(options); }, [options]); // Stable reference
   
   4. useEffectEvent (React 19 RFC) / use ref for non-reactive values:
   const latestHandler = useRef(handler);
   latestHandler.current = handler; // Update ref without triggering effect

Q14: What is the React Fiber architecture and how does it enable concurrent rendering?
───────────────────────────────────────────────────────────────────────────────────────
A: React Fiber (React 16+) is a complete rewrite of React's core algorithm.
   It's the reconciler — the system that decides what to update in the DOM.
   
   BEFORE FIBER (React 15 and earlier — Stack Reconciler):
   - Rendering was a single, synchronous, recursive call
   - Once started, couldn't be interrupted (blocking the main thread)
   - Long renders → janky animation, unresponsive input
   
   FIBER DATA STRUCTURE:
   Each React element has a corresponding Fiber node — a JavaScript object:
   {
     type: 'div',              // Element type
     return: fiberParent,      // Parent fiber
     child: fiberChild,        // First child fiber
     sibling: fiberSibling,    // Next sibling fiber
     alternate: workInProgress,// Previous render's fiber (double buffering)
     effectTag: UPDATE,        // What needs to happen (mount, update, delete)
     lanes: lanes,             // Priority lanes
   }
   
   HOW FIBER ENABLES CONCURRENCY:
   1. Work is split into units (one fiber = one unit)
   2. After each unit: check if there's higher priority work
   3. If yes: pause current work, save state in fiber tree, handle priority work
   4. If no: continue to next unit
   5. When all high-priority work done: resume where paused
   
   PRIORITY LANES (React 18):
   - Sync: Must happen synchronously (user interactions)
   - Input Continuous: Mouse move, scroll (continuous input)
   - Default: Normal setState calls
   - Transition: startTransition/useTransition (lower priority)
   - Idle: Lowest priority (browser idle time)
