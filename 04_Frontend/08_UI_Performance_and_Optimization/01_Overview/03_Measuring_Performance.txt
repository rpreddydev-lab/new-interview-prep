================================================================
MEASURING PERFORMANCE - TOOLS, METRICS & TECHNIQUES
================================================================

TWO CATEGORIES OF MEASUREMENT
──────────────────────────────
1. LAB DATA (Synthetic Monitoring)
   - Controlled, reproducible environment
   - Specific devices + network conditions simulated
   - Great for: debugging, CI/CD gating, regression detection
   - Tools: Lighthouse, WebPageTest, Chrome DevTools, SpeedCurve

2. FIELD DATA (Real User Monitoring - RUM)
   - Collected from actual users in the wild
   - Reflects real devices, real networks, real user behavior
   - Great for: understanding actual user experience
   - Tools: CrUX, Google Analytics, New Relic, Datadog, Sentry

WHY BOTH MATTER:
  - Lab: Your MacBook on fiber doesn't represent your users
  - Field: Aggregated real data shows true performance distribution
  - Lab catches regressions in CI; Field shows real-world impact

================================================================
CORE PERFORMANCE METRICS - DEEP DIVE
================================================================

1. LCP - LARGEST CONTENTFUL PAINT
   What: Time when the largest visible content element finishes rendering
   Elements tracked: <img>, <video> poster, <svg>, background-image, text blocks
   Good: ≤ 2.5s | Needs Work: 2.5–4s | Poor: > 4s
   Measures: Loading performance

2. INP - INTERACTION TO NEXT PAINT (replaced FID in March 2024)
   What: Worst-case interaction latency across the entire page lifetime
   Measured: From user input to next frame rendered after processing
   Good: ≤ 200ms | Needs Work: 200–500ms | Poor: > 500ms
   Measures: Responsiveness / Interactivity

3. CLS - CUMULATIVE LAYOUT SHIFT
   What: Measures unexpected layout shifts during the page lifecycle
   Score: Impact fraction × Distance fraction (per shift)
   Good: ≤ 0.1 | Needs Work: 0.1–0.25 | Poor: > 0.25
   Measures: Visual stability

4. FCP - FIRST CONTENTFUL PAINT
   What: Time when first text/image is painted
   Good: ≤ 1.8s | Needs Work: 1.8–3s | Poor: > 3s
   Measures: Initial visual feedback

5. TTFB - TIME TO FIRST BYTE
   What: Time from navigation start to first byte received
   Good: ≤ 800ms | Needs Work: 800ms–1.8s | Poor: > 1.8s
   Measures: Server responsiveness + network

6. TTI - TIME TO INTERACTIVE
   What: When the page is fully interactive (main thread quiet for 5s)
   Note: Being deprecated in favor of INP for real-world measurement
   Measures: When JS has loaded and executed enough to handle input

7. TBT - TOTAL BLOCKING TIME
   What: Sum of all long tasks (>50ms) between FCP and TTI
   Each task: (task duration - 50ms) = blocking portion
   Good: ≤ 200ms | Needs Work: 200–600ms | Poor: > 600ms
   Measures: Main thread contention

8. SPEED INDEX
   What: How quickly content visually fills in (visual progress)
   Measures: Perceived loading speed
   Calculated via video capture of page load

PERFORMANCE MEASUREMENT APIS (JavaScript)
================================================================

1. NAVIGATION TIMING API
─────────────────────────
const perfData = performance.getEntriesByType('navigation')[0];
console.log({
  DNS: perfData.domainLookupEnd - perfData.domainLookupStart,
  TCP: perfData.connectEnd - perfData.connectStart,
  TLS: perfData.requestStart - perfData.secureConnectionStart,
  TTFB: perfData.responseStart - perfData.requestStart,
  download: perfData.responseEnd - perfData.responseStart,
  DOMParsing: perfData.domInteractive - perfData.responseEnd,
  DOMComplete: perfData.domComplete - perfData.domInteractive,
  pageLoad: perfData.loadEventEnd - perfData.startTime,
});

2. PAINT TIMING API
────────────────────
const paintEntries = performance.getEntriesByType('paint');
// Returns: first-paint and first-contentful-paint

const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(`${entry.name}: ${entry.startTime}ms`);
  }
});
observer.observe({ entryTypes: ['paint'] });

3. LARGEST CONTENTFUL PAINT API
─────────────────────────────────
const observer = new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const lastEntry = entries[entries.length - 1]; // Most recent LCP
  console.log('LCP:', lastEntry.startTime);
});
observer.observe({ entryTypes: ['largest-contentful-paint'] });

4. LAYOUT SHIFT API (CLS)
──────────────────────────
let cumulativeScore = 0;
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) { // Ignore shifts caused by user input
      cumulativeScore += entry.value;
      console.log('CLS score:', cumulativeScore);
    }
  }
});
observer.observe({ entryTypes: ['layout-shift'] });

5. INTERACTION TO NEXT PAINT (INP) via Event Timing API
─────────────────────────────────────────────────────────
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // processingStart - startTime = input delay
    // processingEnd - processingStart = processing time
    // duration = full interaction duration
    if (entry.interactionId) {
      console.log(`INP candidate: ${entry.duration}ms`);
    }
  }
});
observer.observe({ entryTypes: ['event'], buffered: true });

6. RESOURCE TIMING API
───────────────────────
const resources = performance.getEntriesByType('resource');
resources.forEach(r => {
  console.log({
    name: r.name,
    size: r.transferSize,
    duration: r.duration,
    initiatorType: r.initiatorType, // 'script', 'link', 'img', etc.
  });
});

7. USER TIMING API (Custom Marks & Measures)
──────────────────────────────────────────────
// Mark a point in time
performance.mark('myFeature:start');

// Do your expensive operation
doHeavyWork();

// Mark end
performance.mark('myFeature:end');

// Measure the duration
performance.measure(
  'myFeature:duration',
  'myFeature:start',
  'myFeature:end'
);

const measure = performance.getEntriesByName('myFeature:duration')[0];
console.log(`myFeature took ${measure.duration}ms`);

8. WEB VITALS LIBRARY (Google's official library)
───────────────────────────────────────────────────
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

onLCP(({ name, value, rating }) => {
  console.log(name, value, rating); // rating: 'good' | 'needs-improvement' | 'poor'
  sendToAnalytics({ name, value, rating });
});

onCLS(metric => sendToAnalytics(metric));
onINP(metric => sendToAnalytics(metric));
onFCP(metric => sendToAnalytics(metric));
onTTFB(metric => sendToAnalytics(metric));

================================================================
UNDERSTANDING PERCENTILES IN PERFORMANCE
================================================================

WHY NOT USE AVERAGES:
  - An average hides the long tail of bad experiences
  - 1% of users with 10s load time drowns in an average
  - P50 (median), P75, P90, P95, P99 tell a better story

CORE WEB VITALS USE P75:
  - Google measures at the 75th percentile
  - "75% of page visits experience this or better"
  - Your 'Good' rating means 75% of visits have 'Good' scores

READING PERCENTILE DATA:
  - P50 = 1.2s LCP → Half of users load in 1.2s or less
  - P75 = 2.5s LCP → 75% load in 2.5s or less (the threshold)
  - P95 = 6s LCP → 5% of users wait 6s+ (long tail problem)

================================================================
RUM (Real User Monitoring) IMPLEMENTATION
================================================================

BASIC RUM SETUP:
────────────────
// Send all Core Web Vitals to analytics endpoint
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    delta: metric.delta, // Change since last report
    id: metric.id,       // Unique ID for this metric instance
    navigationType: metric.navigationType, // 'navigate' | 'reload' | 'back-forward'
    url: window.location.href,
    userAgent: navigator.userAgent,
    timestamp: Date.now(),
  });

  // Use sendBeacon to ensure delivery even when page is unloading
  navigator.sendBeacon('/analytics', body);
}

[onLCP, onINP, onCLS, onFCP, onTTFB].forEach(fn => fn(sendToAnalytics));

// Also report on page visibility change (ensures data is sent)
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    // Flush any buffered analytics
  }
});

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is the difference between lab and field data?
A: Lab data is collected in controlled conditions using tools like Lighthouse
   — same device, same network, every time. It's reproducible and great for
   debugging. Field data (RUM/CrUX) is collected from real users with real
   devices and connections. It represents actual user experience. Lab data
   can miss real-world variability; field data shows the true distribution.

Q: What is P75 and why does Google use it for Core Web Vitals?
A: P75 means the 75th percentile — 75% of page visits experience that value
   or better. Google uses P75 because it captures the experience of most
   users while still accounting for the long tail of bad experiences. Using
   averages would hide outliers; P99 would be too strict.

Q: What Performance APIs would you use to measure Core Web Vitals in code?
A: I'd use the web-vitals library from Google, which wraps the underlying
   PerformanceObserver APIs: largest-contentful-paint, layout-shift, and
   event entry types. For custom measurements, I'd use the User Timing API
   (performance.mark/measure). For resource analysis, the Resource Timing API.

Q: How do you measure performance in a React application?
A: I use React's built-in Profiler component/API to measure render times,
   the React DevTools Profiler for visual flame charts, and web-vitals for
   real user metrics. I also look at TBT and TTI which are proxies for
   JavaScript execution impact. For bundle analysis, webpack-bundle-analyzer.

Q: What is RUM and how do you implement it?
A: RUM (Real User Monitoring) collects performance metrics from actual users.
   I implement it with the web-vitals library, capturing LCP, INP, CLS, FCP,
   TTFB. I send data via navigator.sendBeacon() (which survives page unload)
   to an analytics endpoint, then aggregate by P75 to match CrUX methodology.
