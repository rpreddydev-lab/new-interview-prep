================================================================

WHAT IS WEB PERFORMANCE?
─────────────────────────
Web performance is the objective measurement and perceived user experience
of a website or application. It encompasses:
  - How fast content loads (loading performance)
  - How responsive it is to user input (interactivity)
  - How smooth the visual experience is (visual stability)
  - How efficiently resources are used (runtime performance)

Performance is NOT just about speed. It's about the PERCEPTION of speed.
A 3-second load that shows content progressively FEELS faster than a
2-second load that shows nothing until fully ready.

================================================================
THE PERFORMANCE SPECTRUM
================================================================

1. NETWORK PERFORMANCE
   - DNS lookup time
   - TCP connection time
   - TLS handshake
   - TTFB (Time to First Byte)
   - Download speed

2. LOADING PERFORMANCE
   - Resource size (HTML, CSS, JS, images)
   - Number of requests
   - Critical rendering path
   - Resource prioritization

3. PARSING & COMPILATION
   - JavaScript parse time
   - CSS parsing
   - HTML parsing

4. RENDERING PERFORMANCE
   - Layout / Reflow
   - Painting / Repaint
   - Compositing
   - Frame rate (target: 60fps = 16ms per frame)

5. RUNTIME PERFORMANCE
   - JavaScript execution
   - Memory usage
   - Event handling
   - Animations

================================================================
THE RAIL PERFORMANCE MODEL
================================================================

Google's RAIL model provides a user-centric performance framework:

R - RESPONSE (0–100ms)
  - Respond to user input within 100ms
  - Users perceive actions as instant if response < 100ms
  - For touch/keyboard input: complete within 50ms (leaves 50ms buffer for other tasks)

A - ANIMATION (0–16ms per frame)
  - Each frame must complete in 16ms (60fps = 16.6ms/frame)
  - Actually ~10ms budget due to browser overhead
  - Janky animations break immersion

I - IDLE (50ms chunks)
  - Use idle time to proactively complete deferred work
  - Break tasks into 50ms chunks to remain responsive
  - Defer non-critical operations using requestIdleCallback

L - LOAD (0–5000ms)
  - Deliver content and become interactive in 5 seconds on mid-tier devices
  - Repeat visits should load in < 2 seconds
  - Optimize the Critical Rendering Path

KEY PERFORMANCE METRICS
================================================================

FIELD METRICS (Real User Monitoring - RUM):
  - Collected from real users in the wild
  - Represents actual user experience across all devices/networks
  - Tools: Google Search Console, CrUX (Chrome User Experience Report)

LAB METRICS (Synthetic Monitoring):
  - Controlled, reproducible conditions
  - Useful for debugging and CI/CD
  - Tools: Lighthouse, WebPageTest, Chrome DevTools

CORE WEB VITALS (Google's official UX metrics):
  ┌─────────────────┬──────────────┬──────────────┬──────────────┐
  │ Metric          │ Good         │ Needs Work   │ Poor         │
  ├─────────────────┼──────────────┼──────────────┼──────────────┤
  │ LCP             │ ≤ 2.5s       │ 2.5s – 4s    │ > 4s         │
  │ INP             │ ≤ 200ms      │ 200ms – 500ms│ > 500ms      │
  │ CLS             │ ≤ 0.1        │ 0.1 – 0.25   │ > 0.25       │
  └─────────────────┴──────────────┴──────────────┴──────────────┘

OTHER IMPORTANT METRICS:
  - FCP (First Contentful Paint): When first text/image appears
  - TTFB (Time to First Byte): Server response speed
  - TTI (Time to Interactive): Fully interactive
  - TBT (Total Blocking Time): Sum of blocking time > 50ms tasks
  - Speed Index: How quickly content visually fills in

THE CRITICAL RENDERING PATH
================================================================

Browser steps to render a page:
1. Request HTML from server
2. Parse HTML → Build DOM
3. Encounter CSS → Fetch CSS → Build CSSOM
4. Encounter JS → Fetch → Execute (blocks parsing!)
5. Combine DOM + CSSOM → Render Tree
6. Layout: Calculate element positions and sizes
7. Paint: Fill in pixels
8. Composite: Layer compositing by GPU

BLOCKING RESOURCES:
  - CSS is RENDER-BLOCKING (must download & parse before rendering)
  - JS is PARSER-BLOCKING by default (use async/defer)

OPTIMIZATION GOALS:
  - Minimize critical resources
  - Minimize critical bytes
  - Minimize critical path length (round trips)

================================================================
PERFORMANCE OPTIMIZATION HIERARCHY
================================================================

1. ELIMINATE unnecessary work
   → Remove unused code, redundant requests, unnecessary re-renders

2. DEFER non-critical work
   → Lazy load, code split, requestIdleCallback

3. CACHE aggressively
   → Service workers, HTTP caching, memoization

4. COMPRESS & MINIMIZE
   → Gzip, Brotli, minification, image compression

5. PARALLELIZE where possible
   → HTTP/2 multiplexing, parallel resource loads, Web Workers

6. OPTIMIZE the critical path
   → Inline critical CSS, defer JS, preload key resources

PERFORMANCE TESTING ENVIRONMENTS
================================================================

TEST ON REAL DEVICES:
  - Desktop ≠ Mobile (CPU throttling 4x on mid-tier Android)
  - 4G network ≠ fiber connection
  - Use BrowserStack, LambdaTest, or physical devices

NETWORK CONDITIONS TO TEST:
  - Fast 3G: 1.6Mbps down / 750Kbps up / 150ms RTT
  - Slow 3G: 500Kbps down / 500Kbps up / 400ms RTT
  - Offline: Test service worker behavior

CPU THROTTLING:
  - Chrome DevTools: 4x or 6x slowdown
  - Simulates mid-tier Android performance

INTERVIEW QUICK REFERENCE
================================================================

Q: What is web performance?
A: Web performance is the speed at which web pages load and render, plus
   how responsive they feel. It includes loading time, interactivity, and
   visual stability. It's measured by metrics like Core Web Vitals.

Q: Why does web performance matter?
A: It directly impacts user experience, conversion rates, SEO rankings,
   and accessibility. Slower sites lose users and revenue.

Q: What is the RAIL model?
A: Response (100ms), Animation (16ms/frame), Idle (50ms chunks),
   Load (5s). A user-centric framework for thinking about performance.

Q: What's the difference between lab and field data?
A: Lab data (Lighthouse, DevTools) is collected in controlled conditions.
   Field data (CrUX, RUM) is from real users on real devices/networks.
   Both are needed — lab for debugging, field for real-world truth.

Q: What is the Critical Rendering Path?
A: The sequence of steps the browser takes to convert HTML, CSS, and JS
   into pixels: DOM → CSSOM → Render Tree → Layout → Paint → Composite.
   Optimizing it reduces time-to-first-render.
