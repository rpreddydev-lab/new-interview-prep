================================================================
DEBOUNCE AND THROTTLE
================================================================

WHAT PROBLEM DO THEY SOLVE?
─────────────────────────────
Some user events fire extremely rapidly:
  - keydown/keyup: every key press (potentially 5-10 per second)
  - scroll: fires 60-120 times per second (every frame!)
  - mousemove: fires 30-60 times per second
  - resize: fires continuously while resizing window
  
If we run expensive operations (API calls, DOM updates, calculations) on
every event, the browser gets overwhelmed → jank, dropped frames, high CPU.

Debounce and throttle control HOW OFTEN a function executes.

================================================================
DEBOUNCE
================================================================

CONCEPT: Wait for activity to STOP for X milliseconds before calling function.
If another event fires within the wait period, RESET the timer.

"Don't call until the user STOPS doing the thing."

VISUAL:
  Events:   ----E-E-E-E----E-E----EEE---------E---
  Debounced:                ↑F      ↑F               ↑F
  (wait=100ms)
  F fires 100ms after the LAST event in a burst.

USE CASES:
  - Search input: Don't search on every keypress; wait until user pauses
  - Window resize: Recalculate layout after user FINISHES resizing
  - Form validation: Validate after user pauses typing
  - Autocomplete: Fetch suggestions after user stops typing

IMPLEMENTATION:
  function debounce(fn, wait) {
    let timerId = null;
    
    return function(...args) {
      // If another call comes in, cancel the pending timer
      clearTimeout(timerId);
      
      // Schedule fn to run after 'wait' ms with no new calls
      timerId = setTimeout(() => {
        fn.apply(this, args);
        timerId = null;
      }, wait);
    };
  }
  
  // Usage:
  const handleSearch = debounce((query) => {
    fetchResults(query);  // Only called 300ms after last keypress
  }, 300);
  
  document.getElementById('search').addEventListener('input', (e) => {
    handleSearch(e.target.value);
  });

DEBOUNCE WITH LEADING EDGE (immediate + silence period):
  function debounce(fn, wait, { leading = false } = {}) {
    let timerId = null;
    
    return function(...args) {
      const isFirstCall = leading && !timerId;
      
      clearTimeout(timerId);
      timerId = setTimeout(() => { timerId = null; }, wait);
      
      if (isFirstCall) fn.apply(this, args);  // Call immediately on first
      else if (!leading) {
        clearTimeout(timerId);
        timerId = setTimeout(() => {
          fn.apply(this, args);
          timerId = null;
        }, wait);
      }
    };
  }
  
  // leading: true → call FIRST event immediately, then silence for wait ms
  // Use for button clicks: respond immediately, prevent double-submit

REACT DEBOUNCE HOOK:
  import { useRef, useCallback } from 'react';
  
  function useDebounce(fn, wait) {
    const timerRef = useRef(null);
    
    return useCallback((...args) => {
      clearTimeout(timerRef.current);
      timerRef.current = setTimeout(() => fn(...args), wait);
    }, [fn, wait]);
  }
  
  // Usage in component:
  function SearchBox() {
    const [query, setQuery] = useState('');
    const [results, setResults] = useState([]);
    
    const debouncedSearch = useDebounce(async (q) => {
      const data = await searchAPI(q);
      setResults(data);
    }, 300);
    
    return (
      <input
        value={query}
        onChange={e => {
          setQuery(e.target.value);     // Instant (controlled input)
          debouncedSearch(e.target.value); // Debounced API call
        }}
      />
    );
  }

  // ⚠️ useDebounce is tricky with closures — prefer useDeferredValue
  // or React Query's debounced input pattern for search:
  
  // BETTER React pattern (useDeferredValue):
  function SearchBox() {
    const [query, setQuery] = useState('');
    const deferredQuery = useDeferredValue(query);
    
    const { data } = useQuery({
      queryKey: ['search', deferredQuery],
      queryFn: () => searchAPI(deferredQuery),
    });
    
    return <input value={query} onChange={e => setQuery(e.target.value)} />;
  }

================================================================
THROTTLE
================================================================

CONCEPT: Allow function to run at MOST once per X milliseconds.
Regardless of how many events fire, the function executes at a steady rate.

"Call at most once every X ms, even if events keep firing."

VISUAL:
  Events:   ----EEEEEEEEEEEEEEEEEEEEEEEEEEEEEE----
  Throttled: ↑F        ↑F        ↑F        ↑F
  (wait=100ms)
  F fires immediately on first event, then once every 100ms max.

USE CASES:
  - Scroll events: Update parallax, sticky nav, progress bar
  - Mouse move: Drag operations, cursor tracking
  - Window resize: Adjust component sizes mid-resize
  - Game loop: Player input processing at fixed rate
  - API rate limiting: Max 1 request per second

IMPLEMENTATION:
  function throttle(fn, wait) {
    let lastCallTime = 0;
    let timerId = null;
    
    return function(...args) {
      const now = Date.now();
      const remaining = wait - (now - lastCallTime);
      
      if (remaining <= 0) {
        // Enough time has passed → call immediately
        clearTimeout(timerId);
        timerId = null;
        lastCallTime = now;
        fn.apply(this, args);
      } else if (!timerId) {
        // Schedule for when the wait period ends (trailing call)
        timerId = setTimeout(() => {
          lastCallTime = Date.now();
          timerId = null;
          fn.apply(this, args);
        }, remaining);
      }
    };
  }
  
  // Usage:
  const handleScroll = throttle(() => {
    updateProgress();  // Runs at most once per 16ms
  }, 16); // ~60fps
  
  window.addEventListener('scroll', handleScroll);

RAF-BASED THROTTLE (syncs with frame rate automatically):
  // Better for visual updates — syncs with browser rendering
  function rafThrottle(fn) {
    let rafId = null;
    
    return function(...args) {
      if (rafId) return; // Already scheduled for this frame
      
      rafId = requestAnimationFrame(() => {
        fn.apply(this, args);
        rafId = null; // Ready for next frame
      });
    };
  }
  
  // Usage:
  const onScroll = rafThrottle(() => {
    // Runs at most once per frame (16.67ms at 60fps, 8.33ms at 120fps)
    header.style.transform = `translateY(${-window.scrollY * 0.5}px)`;
  });
  
  window.addEventListener('scroll', onScroll, { passive: true });
  // { passive: true } tells browser this handler won't call preventDefault()
  // → Browser can start scrolling immediately (major performance win for scroll!)

================================================================
COMPARING DEBOUNCE AND THROTTLE
================================================================

Feature            | Debounce              | Throttle
───────────────────────────────────────────────────────────────
Behavior           | Wait for silence      | Rate limit
When fn executes   | After last event      | During steady events
Good for           | Final value needed    | Continuous feedback needed
Examples           | Search input, resize  | Scroll, mouse move, drag
Feels like         | "Wait until done"     | "Update periodically"

CHOOSING BETWEEN THEM:
  "Does the user need FEEDBACK DURING the action?"
  → YES (scroll, drag, resize preview): THROTTLE
  → NO (search, validation): DEBOUNCE

LODASH DEBOUNCE AND THROTTLE
================================================================

  import { debounce, throttle } from 'lodash-es';
  // OR: import debounce from 'lodash/debounce';
  
  // Lodash debounce — extra options:
  const search = debounce(fetchResults, 300, {
    leading: false,    // Don't call on first event (default)
    trailing: true,    // Call after wait (default)
    maxWait: 1000,     // Call at most every 1s even if still typing
  });
  
  // Lodash throttle — extra options:
  const update = throttle(updateUI, 100, {
    leading: true,     // Call on first event immediately (default)
    trailing: true,    // Call once more after events stop (default)
  });
  
  // CANCEL AND FLUSH:
  search.cancel();  // Cancel pending debounced call
  search.flush();   // Execute pending call immediately

================================================================
CLEANUP IN REACT (AVOID MEMORY LEAKS)
================================================================

  function SearchComponent() {
    // ❌ Creates new debounce function on every render!
    const handleSearch = debounce(fetchResults, 300);
    
    // ✅ Create once, stable across renders:
    const handleSearch = useRef(debounce(fetchResults, 300)).current;
    
    // ✅ OR: useCallback with useMemo for debounce:
    const handleSearch = useMemo(
      () => debounce(fetchResults, 300),
      [] // Create once
    );
    
    // Clean up pending timers on unmount:
    useEffect(() => {
      return () => handleSearch.cancel(); // Prevent state update after unmount
    }, [handleSearch]);
  }

================================================================
PASSIVE EVENT LISTENERS
================================================================

{passive: true} is a critical performance flag for scroll/touch events.

WITHOUT PASSIVE:
  - Browser must wait for JS to run before scrolling
  - JS might call event.preventDefault() (which blocks scrolling)
  - Result: 100–200ms scroll delay on touch devices!

WITH PASSIVE:
  - Browser starts scrolling immediately (on another thread)
  - JS runs concurrently
  - event.preventDefault() throws an error (scroll can't be blocked)

  // ✅ Always add passive: true for scroll/touch handlers that don't need preventDefault
  document.addEventListener('scroll', onScroll, { passive: true });
  document.addEventListener('touchmove', onMove, { passive: true });
  document.addEventListener('touchstart', onStart, { passive: true });
  
  // Calling preventDefault in a passive listener throws:
  // "Unable to preventDefault inside passive event listener invocation"

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is the difference between debounce and throttle?
A: Debounce waits for a "quiet period" — it resets a timer on each event
   and only calls the function when no events have fired for X milliseconds.
   Great for search inputs where you want the final value after the user
   pauses typing. Throttle limits the call rate — it ensures the function
   runs at most once every X milliseconds during continuous events.
   Great for scroll handlers where you want periodic updates, not silence.
   Rule of thumb: if you need feedback DURING an action (scroll), throttle;
   if you only need the final result (search query), debounce.

Q: What does passive: true do for event listeners and why does it matter?
A: Without passive, when a scroll or touch event fires, the browser must
   wait for your JavaScript handler to finish before it can start scrolling.
   This is because your handler might call event.preventDefault() to block
   scrolling. This wait adds 100-200ms of scroll latency on touch devices.
   With {passive: true}, you promise the browser your handler won't call
   preventDefault, so the browser starts scrolling immediately (on its
   compositor thread) while your JS runs concurrently. This eliminates the
   latency entirely. Always use passive for scroll, touchmove, and touchstart
   handlers that don't prevent default scrolling.

Q: How do you implement debounce in React without creating a new timer on each render?
A: The key is creating the debounced function once, not on every render.
   Use useRef to hold the debounced function across renders:
   const debouncedFn = useRef(debounce(handler, 300)).current;
   Or use useMemo(() => debounce(handler, 300), []).
   Always cancel the debounce on unmount with useEffect cleanup returning
   debouncedFn.cancel() to prevent calling setState after the component
   unmounts. For search patterns in React 18, useDeferredValue is often
   a better solution than manual debouncing.
