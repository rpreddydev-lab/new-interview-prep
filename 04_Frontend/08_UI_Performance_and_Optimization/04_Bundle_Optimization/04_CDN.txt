================================================================
CDN - CONTENT DELIVERY NETWORKS
================================================================

WHAT IS A CDN?
──────────────
A Content Delivery Network (CDN) is a globally distributed network of
servers ("edge nodes" or "Points of Presence" / PoPs) that cache and
serve your assets from locations geographically close to users.

WITHOUT CDN:
  User in Tokyo → Request → Your server in Virginia → Response
  Round-trip: 150ms+ just for network latency

WITH CDN:
  User in Tokyo → Request → CDN node in Tokyo → Response (cached)
  Round-trip: 5ms (cache hit, same city)

KEY BENEFITS:
  1. REDUCED LATENCY: Assets served from nearby servers
  2. REDUCED ORIGIN LOAD: 90%+ cache hit rate means few requests reach origin
  3. HIGHER AVAILABILITY: Multiple edge nodes; if one fails, others serve
  4. DDOS PROTECTION: CDN absorbs attack traffic before it hits origin
  5. AUTOMATIC COMPRESSION: Most CDNs handle Gzip/Brotli automatically
  6. HTTP/2 & HTTP/3: CDNs support latest protocols even if origin doesn't

================================================================
CDN ARCHITECTURE
================================================================

HOW CDN CACHING WORKS:

  1. First user in Tokyo requests /static/js/main.abc123.js
  2. Tokyo edge node: "Cache MISS — I don't have this"
  3. Edge node fetches from origin server (Virginia)
  4. Stores response in edge cache with TTL from Cache-Control header
  5. Returns response to user

  6. Second user in Tokyo requests same file
  7. Tokyo edge node: "Cache HIT — I have this!"
  8. Returns from edge cache: ~5ms, no origin request

CACHE HIERARCHY:
  User → Edge Node (PoP) → Regional Cache → Origin Server
  
  Some CDNs (Cloudflare, Akamai) have multiple cache tiers:
  - L1: Edge cache (closest to user, smaller)
  - L2: Regional parent cache (larger, shared by multiple edges)
  - L3: Origin shield (single "reverse proxy" in front of origin)

ORIGIN SHIELD:
  Most CDN providers offer an "origin shield" — a single intermediate
  cache server between edge nodes and your origin:
  
  Edge (Tokyo)  ──────→ Origin Shield (Virginia) → Origin
  Edge (London) ──────→            ↑
  Edge (Sydney) ──────→ (cache hits served here)
  
  Prevents cache misses from all 200+ edge nodes hitting your origin
  simultaneously. Instead, only origin shield talks to origin.

================================================================
CACHE-CONTROL HEADERS (CDN CONFIGURATION)
================================================================

FUNDAMENTAL DIRECTIVE COMBINATIONS:

1. STATIC ASSETS (JS, CSS with content hashes):
   Cache-Control: public, max-age=31536000, immutable
   
   - public: Can be cached by CDN (not just browser)
   - max-age=31536000: Cache for 1 year (in seconds)
   - immutable: Tell browser "this file will NEVER change;
     don't revalidate even on hard refresh"
   
   WHY 1 YEAR IS SAFE:
   With content hashing (main.abc123.js), when content changes,
   the filename changes (main.def456.js). So it's truly immutable.
   The old cached file can stay forever — it won't be requested
   anymore (HTML links to new filename).

2. HTML FILES:
   Cache-Control: no-cache
   # OR:
   Cache-Control: public, max-age=0, must-revalidate
   
   - Never cache HTML long-term (HTML references latest hashed assets)
   - no-cache doesn't mean "don't cache" — it means "always revalidate"
   - Browser stores it but checks with server (ETag/Last-Modified)
   - If server returns 304 Not Modified: use cache (no download needed)

3. API RESPONSES (dynamic data):
   Cache-Control: private, no-cache
   # OR for stale-while-revalidate:
   Cache-Control: public, max-age=60, stale-while-revalidate=300
   
   - private: Only browser can cache (not CDN)
   - stale-while-revalidate: Serve stale cache while fetching fresh

4. SERVICE WORKER / APP SHELL:
   Cache-Control: no-store  # Don't cache the service worker itself
   # Service workers MUST use no-store or very short max-age

ETAG:
  ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"
  
  Browser sends: If-None-Match: "33a64df..."
  If file unchanged: 304 Not Modified (no body, just headers)
  If file changed: 200 OK + new file + new ETag

LAST-MODIFIED:
  Last-Modified: Wed, 21 Oct 2024 07:28:00 GMT
  
  Browser sends: If-Modified-Since: Wed, 21 Oct 2024 07:28:00 GMT
  If not modified: 304 Not Modified
  If modified: 200 OK + new content

NGINX CACHE-CONTROL CONFIGURATION:
  # nginx.conf
  
  # HTML — always revalidate
  location ~* \.html$ {
    add_header Cache-Control "no-cache";
    add_header Vary "Accept-Encoding";
  }
  
  # Static assets with content hashes — cache forever
  location ~* \.(js|css|png|jpg|webp|avif|woff2|svg)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    add_header Vary "Accept-Encoding";
    expires max;
  }
  
  # API responses — no CDN caching
  location /api/ {
    add_header Cache-Control "private, no-cache";
    proxy_pass http://backend;
  }

================================================================
CDN PROVIDERS COMPARISON
================================================================

1. CLOUDFLARE
  - FREE tier: Full CDN, DDoS, SSL
  - Global: 300+ PoPs worldwide
  - Special features: Workers (edge computing), R2 (storage),
    Images (image optimization), Turnstile (CAPTCHA)
  - Best for: Most web apps, especially with edge computing needs
  - Tiered caching with Cache Reserve (persistent L2 cache)

2. AWS CLOUDFRONT
  - Pay per use (no free CDN tier)
  - Tight AWS integration (S3, EC2, API Gateway, Lambda@Edge)
  - Best for: Apps already on AWS
  - Lambda@Edge: Run Node.js at edge nodes (complex routing logic)
  - CloudFront Functions: Faster, cheaper but more limited

3. FASTLY
  - Enterprise-focused, highly configurable VCL (Varnish Config Language)
  - Real-time cache purging (critical for news sites, live data)
  - Best for: Sites needing instant cache invalidation, high customization
  - Used by GitHub, Twitter, The Guardian, Shopify

4. AKAMAI
  - Oldest, largest network (4,200+ PoPs)
  - Enterprise contracts only
  - Best for: Large enterprises, media streaming
  - EdgeScape: User location/device detection at edge

5. VERCEL EDGE NETWORK
  - Built into Vercel (no separate configuration)
  - Automatic caching for Next.js static files
  - ISR (Incremental Static Regeneration) works out of the box
  - Edge Functions: Serverless functions at edge (no cold starts)
  - Best for: Next.js applications

6. NETLIFY CDN
  - Built into Netlify
  - Automatic for all Netlify deployments
  - Edge Functions, Edge Handlers
  - Best for: Static sites, Jamstack

CDN FOR REACT/SPAs
================================================================

SERVING A REACT APP FROM CDN:
  React SPAs are just static files (HTML, JS, CSS, images).
  Perfect for CDN delivery.

// S3 + CloudFront setup (common pattern):
1. Build React app: npm run build
2. Upload to S3 bucket
3. CloudFront serves from S3 origin
4. CloudFront handles SSL, HTTP/2, global distribution

// Cache headers for SPA:
// index.html: no-cache (entry point must always be fresh)
// /static/js/*.js: max-age=31536000, immutable
// /static/css/*.css: max-age=31536000, immutable
// /static/media/*: max-age=31536000, immutable

NEXT.JS + VERCEL:
  // Vercel automatically:
  // 1. Serves static files with immutable caching from edge
  // 2. Caches ISR pages at edge nodes with smart revalidation
  // 3. Proxies dynamic routes to serverless functions
  // No CDN configuration needed!

NEXT.JS + CLOUDFLARE PAGES:
  // Build output
  npx next build && npx next export (static) 
  // Or use @cloudflare/next-on-pages adapter
  
  // Manual Cache-Control in Next.js:
  // next.config.js
  module.exports = {
    async headers() {
      return [
        {
          source: '/(.*)',
          headers: [{ key: 'Cache-Control', value: 'no-store' }] // HTML
        },
        {
          source: '/_next/static/(.*)',
          headers: [{
            key: 'Cache-Control',
            value: 'public, max-age=31536000, immutable' // Static assets
          }]
        }
      ]
    }
  }

CDN FOR npm PACKAGES (PUBLIC CDNs):
  // Use CDNs for commonly cached libraries
  // ESM.SH — Modern CDN for npm packages (HTTP/2, no bundling needed)
  <script type="module">
    import React from 'https://esm.sh/react@18';
  </script>
  
  // UNPKG — CDN for all npm packages
  <script src="https://unpkg.com/react@18/umd/react.production.min.js"></script>
  
  // jsDelivr — Open source CDN
  <script src="https://cdn.jsdelivr.net/npm/react@18/umd/react.production.min.js"></script>
  
  // CAUTION: Public CDNs have privacy implications and reliability risks
  // For production apps: bundle your own dependencies

CDN CACHE INVALIDATION
================================================================

"There are only two hard things in Computer Science: cache invalidation
and naming things." — Phil Karlton

STRATEGIES:

1. CONTENT-HASH FILENAMES (BEST PRACTICE):
   // Never need to invalidate — filename changes when content changes
   main.abc123.js → main.def456.js
   
   // webpack does this automatically with [contenthash]:
   output: { filename: '[name].[contenthash:8].js' }
   
   // Only index.html (with no-cache) needs fresh request

2. CDN CACHE PURGE (emergency use):
   // Cloudflare API purge:
   curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone}/purge_cache" \
     -H "Authorization: Bearer {token}" \
     -d '{"files": ["https://example.com/api/data.json"]}'
   
   // AWS CloudFront invalidation:
   aws cloudfront create-invalidation \
     --distribution-id {dist-id} \
     --paths "/api/data.json"
   
   // Note: CloudFront charges for invalidations beyond 1000/month

3. VERSIONED URLS:
   /api/v2/users      # Version in URL, never purge — add new version
   /static/v5/app.js  # Manual versioning

4. SHORT TTL + STALE-WHILE-REVALIDATE:
   Cache-Control: public, max-age=60, stale-while-revalidate=300
   
   // Serve stale cache for 5 minutes while fetching fresh content
   // User always gets fast response, background update happens

================================================================
INTERVIEW ANSWERS
================================================================

Q: How does a CDN improve performance?
A: CDNs improve performance in three main ways: (1) Geographic proximity —
   assets are served from the nearest edge node (e.g., Tokyo users get
   files from a Tokyo server instead of a US server), reducing latency by
   100-200ms; (2) Caching — subsequent requests are served from cache
   with no origin round-trip, just milliseconds; (3) Better protocols —
   CDNs support HTTP/2 and HTTP/3, Brotli compression, and have optimized
   network connections that beat typical origin servers.

Q: What Cache-Control headers should you set for static assets?
A: For JavaScript/CSS/images with content hashes in filenames:
   Cache-Control: public, max-age=31536000, immutable
   One year cache, immutable means browser never revalidates.
   This is safe because when file content changes, the hash changes,
   so the URL changes — the old cached file is simply never requested.
   For index.html: Cache-Control: no-cache, so browsers always check
   for the latest HTML which references the latest hashed asset URLs.

Q: How do you handle CDN cache invalidation?
A: My primary strategy is content-hash filenames (webpack [contenthash])
   — I never need to invalidate because changed files get new filenames.
   index.html is served with no-cache so it always reflects latest
   hashed URLs. For emergency invalidations (hotfixes), I use the CDN's
   purge API. For dynamic API responses that need freshness, I use
   stale-while-revalidate — users get cached data instantly while the
   CDN revalidates in the background.

Q: Should you use public CDNs (unpkg, jsDelivr) for libraries?
A: I avoid them in production. Reasons: (1) Shared CDNs had downtime in
   the past, causing cascading failures for thousands of sites;
   (2) Privacy concern — every user's browser connects to a third-party
   domain, leaking browsing behavior; (3) Browser cache is NOT shared
   between origins (since Chrome 86), so the "shared cache benefit" no
   longer exists; (4) You lose control over the exact version served.
   Better to bundle dependencies and serve from your own CDN.

Q: What's the difference between CDN edge functions and serverless functions?
A: Traditional serverless functions (AWS Lambda, Vercel Serverless) run
   in a single region and have cold start latency. CDN edge functions
   (Cloudflare Workers, Vercel Edge Functions) run at every CDN PoP
   globally — they're always warm and execute in the closest data center
   to the user (sub-millisecond execution time). Edge functions are
   limited to simpler use cases (routing, A/B testing, auth, headers)
   because they have smaller memory limits and no Node.js native modules.
   Use edge functions for latency-sensitive work (personalization, auth),
   use serverless for complex business logic.
