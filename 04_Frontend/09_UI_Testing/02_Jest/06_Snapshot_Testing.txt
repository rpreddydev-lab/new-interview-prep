1. WHAT IS SNAPSHOT TESTING?
================================================================================

Snapshot testing captures the output of a component (or any serializable value)
and saves it to a file. On subsequent test runs, the current output is compared
to the saved snapshot. If they differ, the test fails.

PURPOSE:
  - Detect unintended UI changes (regressions)
  - Serve as a visual documentation of rendered output
  - Catch unexpected changes in complex render trees

WHAT CAN BE SNAPSHOTTED:
  - React component render output (most common)
  - Strings
  - Objects
  - Arrays
  - JSON structures
  - Any serializable value

HOW SNAPSHOTS ARE STORED:
  - Stored in __snapshots__ directory next to the test file
  - Auto-generated filename: ComponentName.test.tsx.snap
  - Human-readable format
  - Should be COMMITTED to version control


================================================================================
2. HOW SNAPSHOTS WORK
================================================================================

FIRST RUN (snapshot created):
  1. Test calls toMatchSnapshot()
  2. Jest serializes the rendered output
  3. Jest checks if a snapshot file exists
  4. If NO snapshot: creates it and the test PASSES
  5. If YES snapshot: compares and PASSES if identical, FAILS if different

SUBSEQUENT RUNS:
  1. Jest renders the component
  2. Jest compares rendered output to saved snapshot
  3. PASS: Identical to saved snapshot
  4. FAIL: Different from saved snapshot (may be intentional or a regression)

SNAPSHOT FILE FORMAT:
  // Button.test.tsx.snap
  // Jest Snapshot v1, https://goo.gl/fbAQLP

  exports[`Button renders correctly 1`] = `
  <button
    class="btn btn-primary"
    type="button"
  >
    Click me
  </button>
  `;

THE SNAPSHOT WORKFLOW:
  1. Developer changes component UI
  2. CI fails on snapshot mismatch
  3. Developer reviews diff: "Is this change intentional?"
     - YES → Update snapshot: jest --updateSnapshot
     - NO  → Revert code change (found a regression!)

3. CREATING YOUR FIRST SNAPSHOT
================================================================================

BASIC REACT COMPONENT SNAPSHOT:
  import { render } from '@testing-library/react';

  describe('Button', () => {
    it('renders correctly', () => {
      const { asFragment } = render(
        <Button variant="primary" onClick={() => {}}>
          Click me
        </Button>
      );
      expect(asFragment()).toMatchSnapshot();
    });
  });

THE asFragment() METHOD:
  - Provided by RTL's render()
  - Returns a DocumentFragment of the rendered HTML
  - Serialized as HTML string in the snapshot
  - Preferred over container.firstChild for accuracy

ALTERNATIVE APPROACHES:
  // Using container.firstChild:
  const { container } = render(<Button>Click me</Button>);
  expect(container.firstChild).toMatchSnapshot();

  // Testing non-DOM values (objects, strings):
  const result = formatUser({ name: 'Alice', age: 30 });
  expect(result).toMatchSnapshot();

  const config = buildConfig({ env: 'test' });
  expect(config).toMatchSnapshot();

GENERATED SNAPSHOT FILE:
  // __snapshots__/Button.test.tsx.snap
  exports[`Button renders correctly 1`] = `
  <DocumentFragment>
    <button
      class="btn btn-primary"
      type="button"
    >
      Click me
    </button>
  </DocumentFragment>
  `;

4. INLINE SNAPSHOTS
================================================================================

Inline snapshots store the snapshot value directly in the test file,
not in a separate .snap file.

  it('renders correctly', () => {
    const { asFragment } = render(<Badge count={5} />);
    expect(asFragment()).toMatchInlineSnapshot();
  });

After the first run, Jest REWRITES the test file:
  it('renders correctly', () => {
    const { asFragment } = render(<Badge count={5} />);
    expect(asFragment()).toMatchInlineSnapshot(`
      <DocumentFragment>
        <span
          class="badge"
        >
          5
        </span>
      </DocumentFragment>
    `);
  });

ADVANTAGES OF INLINE SNAPSHOTS:
  ✅ Snapshot is visible directly in the test file
  ✅ No separate .snap files to manage
  ✅ Easier code review (see the expected output in context)
  ✅ Better for small, targeted snapshots

DISADVANTAGES:
  ❌ Makes test files longer
  ❌ Not great for large component trees

BEST PRACTICE: Use inline snapshots for small, focused components.
              Use file snapshots for larger component trees (sparingly).


================================================================================
5. UPDATING SNAPSHOTS
================================================================================

WHEN TO UPDATE:
  - You intentionally changed the component's output
  - A design update changed the rendered HTML
  - You updated class names, text content, structure

COMMANDS:
  npx jest --updateSnapshot
  npx jest -u                          # Shorthand
  npx jest -u Button.test.tsx          # Update specific file
  npx jest -u -t "renders correctly"  # Update specific test

INTERACTIVE UPDATE IN WATCH MODE:
  When running jest --watch, press:
    u → Update ALL failing snapshots
    i → Update snapshots interactively (one by one)

REVIEW BEFORE UPDATING:
  Always review the diff before blindly updating:

  ● Button > renders correctly
    Snapshot name: `Button renders correctly 1`
    - Snapshot  - 1
    + Received  + 1
      <button
    -   class="btn btn-primary"
    +   class="btn btn-primary btn-lg"
        type="button"
      >

  If you see "btn-lg" was added: Was this intentional? If yes, update.

DANGER: Never run --updateSnapshot blindly in CI or before review.
        It could hide real regressions.

6. WHEN TO USE SNAPSHOTS
================================================================================

GOOD USE CASES:
  ✅ Stable, simple components with predictable output
  ✅ Design system components (Button, Badge, Chip, Icon)
  ✅ Components you want to track structural changes over time
  ✅ Complex serialized output (config objects, API responses)
  ✅ Components with many formatting variations

  // Good snapshot candidates:
  <Badge count={5} />
  <Avatar src="..." name="Alice" size="lg" />
  <StatusPill status="active" />
  <Icon name="star" size={24} />

TARGETED SNAPSHOT (Better than full tree):
  // Instead of snapshotting the entire page, snapshot a small piece:
  it('renders the error state correctly', () => {
    const { getByRole } = render(<ErrorAlert message="Not found" />);
    expect(getByRole('alert')).toMatchSnapshot();
  });


================================================================================
7. WHEN NOT TO USE SNAPSHOTS
================================================================================

❌ COMPONENTS WITH DYNAMIC CONTENT
  // BAD: Date changes every test run
  const { asFragment } = render(<Footer year={new Date().getFullYear()} />);
  expect(asFragment()).toMatchSnapshot(); // Fails every year!

  // SOLUTION: Mock the date or don't snapshot dynamic values

❌ FREQUENTLY CHANGING COMPONENTS
  Snapshots for actively developed components become a maintenance burden.
  You'll be running --updateSnapshot constantly.

❌ LARGE COMPONENT TREES
  Snapshotting an entire page renders hundreds of lines of HTML.
  When it fails, the diff is unreadable.

  // BAD: Snapshots entire app
  const { asFragment } = render(<App />);
  expect(asFragment()).toMatchSnapshot();

  // GOOD: Snapshot a specific small component
  const { getByRole } = render(<NavigationBar />);
  expect(getByRole('navigation')).toMatchSnapshot();

❌ REPLACING REAL ASSERTIONS
  Snapshot tests don't tell you WHY something is correct.
  Use real assertions for behavior, snapshots for structure.

  // BAD: Testing a button click with snapshot
  await userEvent.click(button);
  expect(asFragment()).toMatchSnapshot(); // What does this verify?

  // GOOD: Test the actual outcome
  await userEvent.click(button);
  expect(screen.getByText('Submitted!')).toBeInTheDocument();


================================================================================
8. SNAPSHOT BEST PRACTICES
================================================================================

KEEP SNAPSHOTS SMALL:
  Snapshot only the relevant portion, not the entire page:
  expect(screen.getByRole('dialog')).toMatchSnapshot();  ← specific element
  NOT:
  expect(asFragment()).toMatchSnapshot();                  ← entire DOM

USE MEANINGFUL SNAPSHOT NAMES:
  it('renders expanded card', () => {
    render(<ProductCard expanded />);
    expect(screen.getByRole('article')).toMatchSnapshot('expanded card');
  });

COMMIT SNAPSHOT FILES:
  Snapshot .snap files MUST be committed to version control.
  They are part of the test suite, not generated artifacts.

  // .gitignore: DO NOT add *.snap here
  // Instead, make sure snapshot files are tracked:
  git add src/components/__snapshots__/

REVIEW SNAPSHOT UPDATES IN PR:
  When snapshot files change in a PR, reviewers should:
  1. Open the .snap file diff
  2. Verify each change is intentional
  3. Reject the PR if unexpected changes appear

PROPERTY MATCHERS FOR DYNAMIC CONTENT:
  When snapshot contains dynamic values (IDs, dates), use property matchers:

  it('renders user with dynamic id', () => {
    const { asFragment } = render(<UserCard user={{ id: '...', name: 'Alice' }} />);
    expect(asFragment()).toMatchSnapshot({
      // Replace dynamic values with matchers:
      'data-testid': expect.any(String),
    });
  });

  // Better: Structure your test data to be deterministic:
  const mockUser = { id: 'user-123', name: 'Alice', createdAt: '2024-01-01' };
  render(<UserCard user={mockUser} />);
  expect(asFragment()).toMatchSnapshot();

9. SNAPSHOT SERIALIZERS
================================================================================

Serializers control how values are converted to the snapshot string format.

BUILT-IN SERIALIZERS:
  - jest-snapshot serializes DOM nodes (used automatically)
  - jest-circus serializes simple JS values

CUSTOM SERIALIZERS:
  You can add serializers for specific formats:

  // jest.config.ts
  snapshotSerializers: [
    'enzyme-to-json/serializer',           // For Enzyme (legacy)
    '@emotion/jest/serializer',            // For Emotion CSS-in-JS
    'jest-serializer-html',                // For HTML strings
  ]

EMOTION / STYLED COMPONENTS:
  For CSS-in-JS, serializers include the generated class names + CSS rules:

  // With @emotion/jest:
  import { matchers } from '@emotion/jest';
  expect.extend(matchers);

  const { asFragment } = render(<StyledButton />);
  expect(asFragment()).toMatchSnapshot();
  // Snapshot includes actual CSS styles, not just class names

10. COMPONENT SNAPSHOT ALTERNATIVES
================================================================================

Snapshot testing has fallen somewhat out of favor in favor of:

BEHAVIORAL ASSERTIONS (RECOMMENDED):
  // Instead of snapshot:
  expect(asFragment()).toMatchSnapshot();

  // Use specific assertions:
  expect(screen.getByRole('button')).toHaveClass('btn-primary');
  expect(screen.getByRole('button')).toHaveTextContent('Click me');
  expect(screen.getByRole('button')).not.toBeDisabled();

VISUAL REGRESSION TESTING (for design systems):
  Tools like Chromatic, Percy, or BackstopJS take actual screenshots
  and compare them pixel-by-pixel. More accurate for visual testing.

STORYBOOK + CHROMATIC:
  Define component states in Storybook, then use Chromatic for
  visual regression testing. Better workflow than Jest snapshots for
  design systems.

WHEN TO STILL USE SNAPSHOTS:
  Snapshots are useful for:
  - Non-UI serialized data (config objects, API responses)
  - Small, stable utility component output
  - Quick regression detection in design systems

  The key is keeping them SMALL and STABLE.


================================================================================
INTERVIEW INSIGHT
================================================================================

Q: "What do you think about snapshot testing?"

A: "Snapshot tests are a useful tool but easily misused. I use them selectively
   for small, stable components like design system atoms (buttons, badges,
   icons) where I want to catch unintended structural changes. I avoid snapshot
   testing for large component trees, pages, or frequently-changing components
   because they become a maintenance burden — you end up updating them every
   time rather than catching real regressions.

   For behavior testing, I prefer explicit assertions with RTL matchers because
   they tell you exactly what broke and why. For visual testing at scale, I
   prefer visual regression tools like Chromatic, which test actual screenshots
   rather than HTML strings."
