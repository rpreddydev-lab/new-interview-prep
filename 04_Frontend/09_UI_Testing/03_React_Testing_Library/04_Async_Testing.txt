1. WHY ASYNC MATTERS IN RTL
================================================================================

Real React applications are full of asynchronous behavior:
  - Data fetching from APIs (fetch, axios)
  - Lazy-loaded components (React.lazy, Suspense)
  - Animations and CSS transitions
  - Debounced / throttled input handlers
  - Timers (setTimeout, setInterval)
  - State updates triggered after async operations

In testing, you must wait for async operations to complete before
asserting, otherwise you'll get false positives or false negatives.

DANGER ZONE — FALSE POSITIVE:
  ❌ Test passes even though component never updated:
  render(<AsyncComponent />);
  // ...async fetch is still pending
  expect(screen.queryByText(/loading/i)).not.toBeInTheDocument();
  // Test passes, but the component might render "Loading..." then fetch data
  // You never verified the actual loaded state!

CORRECT APPROACH:
  render(<AsyncComponent />);
  // Wait for the loaded state:
  expect(await screen.findByText('Data loaded')).toBeInTheDocument();

2. FINDBY* — ASYNC QUERIES
================================================================================

findBy* queries return a Promise that:
  - Resolves with the element when it appears
  - Rejects with an error if the element doesn't appear within the timeout

SYNTAX:
  await screen.findByRole('heading', { name: /results/i });
  await screen.findByText('Alice Johnson');
  await screen.findAllByRole('listitem');

OPTIONS:
  await screen.findByText('Loaded', {}, { timeout: 3000, interval: 100 });
  // {} = query options (exact, selector, etc.)
  // Third arg = waitFor options (timeout, interval)

COMPLETE EXAMPLE:
  it('loads and displays users', async () => {
    // Mock the API call
    global.fetch = jest.fn().mockResolvedValue({
      ok: true,
      json: async () => [
        { id: 1, name: 'Alice' },
        { id: 2, name: 'Bob' },
      ],
    });

    render(<UserList />);

    // Assert loading state is shown first:
    expect(screen.getByText(/loading/i)).toBeInTheDocument();

    // Wait for users to load:
    const alice = await screen.findByText('Alice');
    expect(alice).toBeInTheDocument();
    expect(screen.getByText('Bob')).toBeInTheDocument();

    // Assert loading state is gone:
    expect(screen.queryByText(/loading/i)).not.toBeInTheDocument();
  });

FINDALLBY* EXAMPLE:
  it('renders all search results', async () => {
    render(<SearchResults query="react" />);

    // Wait for all results to appear
    const results = await screen.findAllByRole('article');
    expect(results).toHaveLength(5);
  });

DEFAULT TIMEOUT: 1000ms (1 second)
  findBy* polls every 50ms until timeout is reached.

CUSTOM TIMEOUT:
  // Wait up to 5 seconds:
  await screen.findByText('Slow response', {}, { timeout: 5000 });

3. WAITFOR — WAITING FOR ASSERTIONS
================================================================================

waitFor(callback, options?) repeatedly runs a callback until it:
  - Passes without throwing (assertion succeeds)
  - OR times out (throws error)

import { waitFor } from '@testing-library/react';

BASIC USAGE:
  await waitFor(() => {
    expect(screen.getByText('Success')).toBeInTheDocument();
  });

MULTIPLE ASSERTIONS IN ONE WAITFOR:
  await waitFor(() => {
    expect(screen.getByRole('heading')).toHaveTextContent('Profile Updated');
    expect(screen.getByText('alice@example.com')).toBeInTheDocument();
    expect(screen.queryByRole('progressbar')).not.toBeInTheDocument();
  });

WAITFOR OPTIONS:
  await waitFor(
    () => expect(mockFn).toHaveBeenCalled(),
    {
      timeout: 2000,   // Max ms to wait (default: 1000)
      interval: 100,   // Polling interval (default: 50)
    }
  );

COMMON USE CASES:

  1. After a user action that triggers async state update:
  await user.click(screen.getByRole('button', { name: /save/i }));
  await waitFor(() => {
    expect(screen.getByRole('alert')).toHaveTextContent('Saved!');
  });

  2. After a mock function is called:
  await waitFor(() => {
    expect(onSave).toHaveBeenCalledWith({ name: 'Alice' });
  });

  3. After form validation:
  await user.click(screen.getByRole('button', { name: /submit/i }));
  await waitFor(() => {
    expect(screen.getAllByRole('alert')).toHaveLength(2); // 2 validation errors
  });

IMPORTANT: waitFor RE-RUNS THE ENTIRE CALLBACK
  Avoid side effects inside waitFor:
  ❌ await waitFor(() => {
    fireEvent.click(button); // Will fire click repeatedly until assertion passes!
    expect(something).toBeTruthy();
  });

  ✅ Perform actions OUTSIDE waitFor:
  await user.click(button);
  await waitFor(() => expect(something).toBeTruthy());

FINDBY* vs WAITFOR:
  findBy* is essentially waitFor + getBy* combined:
  // These are equivalent:
  await screen.findByText('Success');
  await waitFor(() => screen.getByText('Success'));

  // Prefer findBy* when querying for a single element.
  // Use waitFor when you have complex assertions (multiple expects, mock fn checks).

4. WAITFORELEMENTTOBEREMOVED
================================================================================

waitForElementToBeRemoved(callback, options?) waits for an element to be
removed from the DOM. Useful for testing loading states.

import { waitForElementToBeRemoved } from '@testing-library/react';

BASIC USAGE:
  render(<DataTable />);

  // Pass a callback that returns the element currently in the DOM:
  await waitForElementToBeRemoved(() => screen.queryByText(/loading/i));

  // After removal, verify the data is shown:
  expect(screen.getByRole('table')).toBeInTheDocument();

USING AN ELEMENT REFERENCE:
  const loading = screen.getByText(/loading/i);
  await waitForElementToBeRemoved(loading);
  // Note: pass the element itself, not a callback — RTL v13+

MULTIPLE ELEMENTS:
  await waitForElementToBeRemoved(screen.queryAllByRole('progressbar'));

COMPLETE PATTERN:
  it('shows loading then data', async () => {
    render(<ArticleList />);

    // Loading state is shown initially:
    expect(screen.getByRole('progressbar')).toBeInTheDocument();

    // Wait for loading to finish:
    await waitForElementToBeRemoved(() => screen.queryByRole('progressbar'));

    // Now data is visible:
    expect(screen.getByRole('list')).toBeInTheDocument();
    expect(screen.getAllByRole('listitem')).toHaveLength(5);
  });

WITH CUSTOM TIMEOUT:
  await waitForElementToBeRemoved(
    () => screen.queryByRole('progressbar'),
    { timeout: 3000 }
  );

WHEN IT THROWS:
  - If the element is NOT in the DOM when you call waitForElementToBeRemoved
  - If the element doesn't get removed within the timeout
  Both result in test failure with a clear error message.

5. ACT() AND WHEN RTL USES IT AUTOMATICALLY
================================================================================

act() is from React Testing and ensures all pending React updates
(state updates, effects, etc.) are processed before assertions.

WHY act() EXISTS:
  React batches state updates for performance.
  If you assert before React processes updates, you see stale state.
  act() flushes all pending updates.

RTL WRAPS EVERYTHING IN act() AUTOMATICALLY:
  render()            → wrapped in act()
  userEvent.click()   → wrapped in act()
  userEvent.type()    → wrapped in act()
  fireEvent.*()       → wrapped in act()
  waitFor()           → wrapped in act()

  This means: YOU ALMOST NEVER NEED TO CALL act() MANUALLY.

WHEN YOU MIGHT NEED act() MANUALLY:
  1. Wrapping a timer/delay:
  act(() => {
    jest.advanceTimersByTime(1000);
  });

  2. Manually triggering imperative updates (outside React's flow):
  act(() => {
    someSubjectObservable.next('new value');
  });

  3. Testing outside of RTL utilities (rare, low-level):
  act(() => {
    ReactDOM.render(<App />, container);
  });

THE "NOT WRAPPED IN ACT()" WARNING:
  Warning: An update to MyComponent inside a test was not wrapped in act(...)

  This usually means:
  - An async operation completed AFTER your test finished
  - You have a state update triggered by a timer or promise that you didn't wait for
  - You're missing an await on userEvent or waitFor

  FIXES:
  ✅ Await your async assertions:
  await waitFor(() => expect(mock).toHaveBeenCalled());

  ✅ Clean up pending operations:
  // If a component fetches on mount:
  render(<Component />);
  await waitForElementToBeRemoved(() => screen.queryByRole('progressbar'));

  ✅ Use fake timers and flush them:
  jest.useFakeTimers();
  render(<Debounced />);
  act(() => jest.runAllTimers());

ASYNC act():
  // When you need to await all async operations:
  await act(async () => {
    await user.click(fetchButton);
  });
  // RTL's async methods already do this — rarely needed

6. ASYNC PATTERNS IN PRACTICE
================================================================================

PATTERN 1: COMPONENT THAT FETCHES ON MOUNT
  // Component:
  function UserProfile({ userId }) {
    const [user, setUser] = useState(null);
    const [loading, setLoading] = useState(true);

    useEffect(() => {
      fetchUser(userId)
        .then(setUser)
        .finally(() => setLoading(false));
    }, [userId]);

    if (loading) return <div>Loading...</div>;
    return <h1>{user.name}</h1>;
  }

  // Test:
  it('renders user name after loading', async () => {
    const mockUser = { id: 1, name: 'Alice' };
    jest.spyOn(global, 'fetch').mockResolvedValue({
      ok: true, json: async () => mockUser,
    });

    render(<UserProfile userId={1} />);

    // Loading state is visible:
    expect(screen.getByText(/loading/i)).toBeInTheDocument();

    // Wait for name to appear:
    expect(await screen.findByText('Alice')).toBeInTheDocument();

    // Loading state is gone:
    expect(screen.queryByText(/loading/i)).not.toBeInTheDocument();
  });

PATTERN 2: BUTTON THAT TRIGGERS A FETCH
  it('submits order and shows confirmation', async () => {
    const user = userEvent.setup();
    jest.spyOn(api, 'placeOrder').mockResolvedValue({ orderId: 'ORD-123' });

    render(<OrderForm />);
    await user.click(screen.getByRole('button', { name: /place order/i }));

    // Button should be disabled while loading:
    expect(screen.getByRole('button', { name: /place order/i })).toBeDisabled();

    // Wait for confirmation:
    await waitFor(() => {
      expect(screen.getByText('Order confirmed: ORD-123')).toBeInTheDocument();
    });
  });

PATTERN 3: ERROR STATE
  it('shows error when fetch fails', async () => {
    jest.spyOn(global, 'fetch').mockRejectedValue(new Error('Network error'));
    render(<UserList />);
    const error = await screen.findByRole('alert');
    expect(error).toHaveTextContent(/failed to load/i);
  });

PATTERN 4: DEBOUNCED SEARCH
  it('debounces search input', async () => {
    const user = userEvent.setup({ delay: null }); // fast typing
    const mockSearch = jest.fn().mockResolvedValue([]);
    render(<SearchBox onSearch={mockSearch} debounceMs={300} />);

    await user.type(screen.getByRole('textbox'), 'react');

    // mockSearch should not have been called during typing (debounced):
    expect(mockSearch).not.toHaveBeenCalled();

    // Wait for debounce:
    await waitFor(() => expect(mockSearch).toHaveBeenCalledWith('react'), {
      timeout: 500,
    });
  });

PATTERN 5: POLLING / LIVE DATA
  it('updates data every 5 seconds', async () => {
    jest.useFakeTimers();
    const getCount = jest.fn()
      .mockResolvedValueOnce(1)
      .mockResolvedValueOnce(5);

    render(<LiveCounter getCount={getCount} pollInterval={5000} />);

    expect(await screen.findByText('1')).toBeInTheDocument();

    act(() => jest.advanceTimersByTime(5000));
    expect(await screen.findByText('5')).toBeInTheDocument();

    jest.useRealTimers();
  });

PATTERN 6: SUSPENSE BOUNDARIES
  it('shows fallback while lazy component loads', async () => {
    const LazyComponent = React.lazy(() =>
      import('./HeavyComponent').then(module => ({ default: module.HeavyComponent }))
    );

    render(
      <Suspense fallback={<div>Loading component...</div>}>
        <LazyComponent />
      </Suspense>
    );

    expect(screen.getByText('Loading component...')).toBeInTheDocument();
    expect(await screen.findByText('Heavy Component Loaded')).toBeInTheDocument();
  });

7. CONFIGURING TIMEOUTS
================================================================================

DEFAULT TIMEOUTS:
  findBy* / waitFor / waitForElementToBeRemoved → 1000ms (1 second)
  Polling interval → 50ms

GLOBAL CONFIGURATION:
  // In setupTests.ts:
  import { configure } from '@testing-library/react';

  configure({
    asyncUtilTimeout: 3000, // Default 1000ms → 3 seconds for slow CIs
  });

PER-CALL TIMEOUT:
  await screen.findByText('Data', {}, { timeout: 5000 });
  await waitFor(() => expect(fn).toHaveBeenCalled(), { timeout: 2000 });
  await waitForElementToBeRemoved(() => screen.queryByText('Loading'), { timeout: 3000 });

FOR SLOW CI ENVIRONMENTS:
  // jest.config.ts:
  export default {
    testTimeout: 15000, // Global Jest test timeout (default: 5000ms)
    // Combine with RTL's asyncUtilTimeout
  };

FAKE TIMERS WITH ASYNC RTL:
  // If using Jest fake timers with findBy* or waitFor:
  jest.useFakeTimers();

  // You must advance timers inside act() for RTL to process them:
  render(<Delayed />);
  act(() => jest.advanceTimersByTime(1000));
  expect(screen.getByText('Appeared after 1s')).toBeInTheDocument();

  jest.useRealTimers();

  // NOTE: userEvent.setup() has its own timer options:
  const user = userEvent.setup({ advanceTimers: jest.advanceTimersByTime });

8. COMMON ASYNC MISTAKES
================================================================================

MISTAKE 1: NOT AWAITING findBy*
  ❌ const el = screen.findByText('Loaded'); // Returns a Promise, not an element!
  ✅ const el = await screen.findByText('Loaded');

MISTAKE 2: USING getBy* FOR ASYNC CONTENT
  ❌ render(<AsyncComp />); expect(screen.getByText('Loaded')).toBe...; // Throws immediately
  ✅ const loaded = await screen.findByText('Loaded');

MISTAKE 3: MULTIPLE AWAITS IN WAITFOR
  ❌ This creates a new poll for each await, slowing tests:
  await waitFor(async () => {
    await somethingAsync();           // Anti-pattern
    expect(result).toBeTruthy();
  });

  ✅ Put async logic outside, sync assertions inside:
  await somethingAsync();
  await waitFor(() => expect(result).toBeTruthy());

MISTAKE 4: ASSERTING ABSENCE TOO EARLY
  ❌ render(<Form />);
  expect(screen.queryByText(/error/i)).not.toBeInTheDocument();
  // True initially, but doesn't test that error NEVER appears

  ✅ Submit and wait, THEN check absence:
  await user.click(screen.getByRole('button', { name: /submit/i }));
  await waitFor(() => {
    expect(screen.getByText('Success')).toBeInTheDocument();
  });
  expect(screen.queryByRole('alert')).not.toBeInTheDocument();

MISTAKE 5: NOT CLEANING UP ASYNC WORK
  ❌ Tests that don't wait for all async work leave "act() warning"
  render(<FetchOnMount />);
  // Test ends before fetch resolves → React still updates → Warning

  ✅ Wait for final state:
  render(<FetchOnMount />);
  await screen.findByText('Loaded'); // Ensures all async work is done

MISTAKE 6: WAITFOR INSIDE A LOOP
  ❌ Slow and misleading:
  for (const item of items) {
    await waitFor(() => expect(screen.getByText(item)).toBeVisible());
  }

  ✅ Wait for all at once:
  await waitFor(() => {
    items.forEach(item => expect(screen.getByText(item)).toBeVisible());
  });

QUICK REFERENCE:
  findByText()          → Element that will appear (async)
  findAllByRole()       → Multiple elements that will appear (async)
  waitFor(fn)           → Wait for assertion/callback to pass
  waitForElementToBeRemoved(el) → Wait for element to disappear
  act(() => timers...)  → Flush fake timers inside act()
