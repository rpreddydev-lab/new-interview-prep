1. WHAT IS UI TESTING?
================================================================================

UI Testing (User Interface Testing) is the practice of testing an application's
user interface to ensure it behaves correctly from a user's perspective.

It validates:
  - Correct rendering of components
  - Interaction behavior (clicks, inputs, form submissions)
  - Navigation between pages/views
  - Accessibility compliance
  - Visual consistency
  - Integration between components and data layers

UI Testing is NOT just about what the UI looks like — it's primarily about
what the UI DOES and how users interact with it.


================================================================================
2. WHY UI TESTING MATTERS
================================================================================

BUSINESS PERSPECTIVE:
  - Prevents regressions when shipping new features
  - Reduces QA bottlenecks before release
  - Increases confidence in deployments
  - Reduces bug-fixing costs (bugs caught earlier are cheaper to fix)
  - Protects user experience in production

DEVELOPER PERSPECTIVE:
  - Provides fast feedback during development
  - Acts as living documentation of component behavior
  - Encourages better component design (testable code = modular code)
  - Enables safe refactoring
  - Reduces fear of touching legacy code

COST OF BUGS AT DIFFERENT STAGES:
  Design  → $1
  Coding  → $10
  Testing → $100
  Production → $1,000+

Source: IBM System Science Institute study on cost of bugs.

3. TYPES OF UI TESTS
================================================================================

There are multiple distinct types of UI tests, each serving a different purpose:

┌─────────────────────────┬──────────────────────────────────────────────────┐
│ Test Type               │ Description                                      │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Unit Tests              │ Test a single component/function in isolation.   │
│                         │ Mock all dependencies.                           │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Integration Tests       │ Test how multiple units work together.           │
│                         │ May include API calls, context, routing.         │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ End-to-End (E2E) Tests  │ Simulate real user flows in a real browser.      │
│                         │ Uses tools like Cypress or Playwright.           │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Snapshot Tests          │ Capture component output and compare future      │
│                         │ renders against the saved snapshot.              │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Visual Regression Tests │ Compare screenshots pixel-by-pixel to detect    │
│                         │ unintended visual changes.                       │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Accessibility Tests     │ Validate compliance with WCAG standards.        │
│                         │ Tools: axe-core, jest-axe, Lighthouse.          │
├─────────────────────────┼──────────────────────────────────────────────────┤
│ Performance Tests       │ Measure load time, FPS, layout shifts.          │
│                         │ Tools: Lighthouse, WebPageTest, k6.             │
└─────────────────────────┴──────────────────────────────────────────────────┘

4. UI TESTING IN THE DEVELOPMENT LIFECYCLE
================================================================================

WHEN TO WRITE TESTS:
  - TDD (Test Driven Development): Write tests BEFORE writing code
  - BDD (Behavior Driven Development): Write tests in natural language first
  - TLD (Test Last Development): Write tests after implementation
  - Most teams use a pragmatic mix

RECOMMENDED APPROACH:
  1. Write unit tests for complex logic and utility functions
  2. Write integration tests for key user flows
  3. Write E2E tests for critical paths (login, checkout, onboarding)
  4. Add snapshot/visual tests for stable UI components

TEST-DRIVEN DEVELOPMENT (TDD) CYCLE:
  🔴 RED   → Write a failing test
  🟢 GREEN → Write minimum code to make the test pass
  🔵 BLUE  → Refactor code while keeping tests green

TDD BENEFITS:
  - Forces thinking about API/interface before implementation
  - Produces highly testable, modular code
  - Natural documentation of expected behavior
  - Higher confidence in refactoring

5. KEY CONCEPTS AND TERMINOLOGY
================================================================================

SUBJECT UNDER TEST (SUT):
  The component, function, or system being tested.

TEST DOUBLE:
  A generic term for any object used in place of a real dependency:
    - Mock:    A test double that tracks how it was called
    - Stub:    Returns fixed responses without tracking calls
    - Spy:     Wraps a real function but tracks invocations
    - Fake:    A working substitute (e.g., in-memory database)
    - Dummy:   Placeholder used when a parameter is required but not used

ASSERTIONS:
  Statements that verify expected behavior.
  Example: expect(element).toBeInTheDocument()

TEST RUNNER:
  The tool that discovers and executes tests.
  Examples: Jest, Vitest, Mocha.

TEST SUITE:
  A group of related tests, typically defined with describe() blocks.

FIXTURE:
  Pre-defined test data or setup used across multiple tests.

FLAKY TEST:
  A test that passes sometimes and fails other times — often due to
  timing issues, network calls, or global state leakage.

CODE COVERAGE:
  A metric that measures what percentage of your code is exercised by tests.
  Types: Statement, Branch, Function, Line coverage.

HAPPY PATH:
  The test scenario where everything works as expected (no errors).

SAD PATH / EDGE CASE:
  Test scenarios that cover error conditions, boundary values, or unusual inputs.

REGRESSION TEST:
  A test that ensures a previously fixed bug hasn't reappeared.

6. TESTING PRINCIPLES (F.I.R.S.T)
================================================================================

Good tests should follow the F.I.R.S.T principles:

F - FAST
  Tests should run quickly. Slow tests reduce the feedback loop and
  discourage frequent test execution.
  - Unit tests: < 1ms each
  - Integration tests: < 100ms each
  - E2E tests: < 30 seconds per flow

I - ISOLATED / INDEPENDENT
  Tests should not depend on each other. Running tests in any order
  should produce the same results.
  - Each test creates its own state
  - Use beforeEach/afterEach to reset state
  - Never rely on previous test outcomes

R - REPEATABLE
  Tests should produce the same result every time they run,
  regardless of environment, time, or network conditions.
  - Mock external APIs
  - Mock timers for date/time sensitive tests
  - Avoid hardcoded environment-specific data

S - SELF-VALIDATING
  Tests should have a clear pass/fail result.
  - Never require manual inspection of outputs
  - Each test must have at least one assertion
  - Use descriptive test names

T - TIMELY
  Tests should be written at the right time — ideally alongside or
  before the code they test.
  - Don't defer tests "until later"
  - Legacy untested code is the hardest to add tests to

7. COMMON TESTING MISTAKES
================================================================================

❌ TESTING IMPLEMENTATION DETAILS
  Don't test HOW something works, test WHAT it does.
  Bad:  expect(component.state.isOpen).toBe(true)
  Good: expect(screen.getByRole('dialog')).toBeVisible()

❌ OVER-MOCKING
  Mocking too many things makes tests fragile and disconnected from reality.
  Mock only what's truly external (network, timers, filesystem).

❌ TOO MANY SNAPSHOTS
  Snapshots that capture entire component trees become a maintenance burden.
  Use targeted assertions instead.

❌ TESTS WITHOUT ASSERTIONS
  Every test must assert something. A test that always passes is useless.

❌ NOT TESTING EDGE CASES
  Empty states, error states, loading states, null values — all must be tested.

❌ DUPLICATED TEST LOGIC
  Use helpers, factories, and utilities to DRY up test code.

❌ IGNORING FAILING TESTS
  Skipped or commented-out tests signal loss of trust in the test suite.

❌ TESTING EVERY LINE OF CODE
  Aim for meaningful coverage, not 100% at all costs. Test behavior, not LOC.

❌ NOT CLEANING UP AFTER TESTS
  Global state, DOM mutations, and mocks left dirty can cause test order issues.

8. TESTING MENTAL MODEL
================================================================================

Think of tests from the USER's perspective, not the code's perspective.

GUIDING QUESTIONS WHEN WRITING A TEST:
  1. What does the user see?
  2. What action does the user take?
  3. What does the user expect to happen?

ARRANGE - ACT - ASSERT (AAA PATTERN):

  // ARRANGE: Set up the component/state
  render(<LoginForm />);

  // ACT: Simulate user interaction
  await userEvent.type(screen.getByLabelText('Email'), 'user@example.com');
  await userEvent.click(screen.getByRole('button', { name: /login/i }));

  // ASSERT: Verify the expected outcome
  expect(screen.getByText('Welcome back!')).toBeInTheDocument();

THE TESTING TROPHY (Kent C. Dodds):
  ┌─────────────────┐
  │    E2E Tests    │  (Few — expensive but highest confidence)
  ├─────────────────┤
  │ Integration     │  (Most — best ROI)
  ├─────────────────┤
  │  Unit Tests     │  (Many — fast, targeted)
  ├─────────────────┤
  │  Static/Lint    │  (Always — catch typos, type errors)
  └─────────────────┘

KEY INSIGHT: Integration tests give you the BEST return on investment because
they test realistic user scenarios without the overhead of a full browser.
