1. WHY AUTOMATED ACCESSIBILITY TESTING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Automated a11y testing catches ~30–40% of accessibility issues early in the
development cycle — the rest require manual testing with screen readers.
Automated tools are valuable because they:
  - Catch regressions immediately in CI
  - Give developers instant feedback (no a11y expertise needed)
  - Scale across all components in the codebase

LIMITATIONS OF AUTOMATED TESTING:
  - Cannot verify meaningful alt text (only that alt attribute exists)
  - Cannot test keyboard interaction flows fully
  - Cannot judge color contrast in dynamic/generated colors reliably
  - Cannot detect cognitive accessibility issues
  → Always supplement with manual screen reader testing (NVDA/JAWS/VoiceOver)

2. AXE-CORE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

axe-core is the most widely used open-source a11y engine, built by Deque Systems.
It powers the Axe browser extension, Lighthouse, and jest-axe.

WHAT IT CHECKS:
  - Missing alt text on images
  - Insufficient color contrast (4.5:1 for normal text, 3:1 for large text)
  - Missing form labels
  - Missing landmark regions
  - Buttons/links without accessible names
  - Invalid ARIA attributes and roles
  - Missing document language
  - Heading order violations
  - Missing focus management

  npm install axe-core

USAGE IN BROWSER (vanilla):
  import axe from 'axe-core';

  axe.run(document, (err, results) => {
    if (err) throw err;
    console.log('Violations:', results.violations);
    // results.violations — array of failing rules
    // results.passes — array of passing rules
    // results.incomplete — needs manual review
  });

  // Promise API:
  const results = await axe.run(document.querySelector('#main'));

AXE RESULT STRUCTURE:
  {
    violations: [{
      id: 'color-contrast',
      impact: 'serious',           // 'critical' | 'serious' | 'moderate' | 'minor'
      description: 'Elements must meet minimum color contrast ratio thresholds',
      help: 'Ensure contrast ratio of at least 4.5:1',
      helpUrl: 'https://dequeuniversity.com/rules/axe/4.6/color-contrast',
      nodes: [{
        html: '<p style="color: #aaa;">Low contrast text</p>',
        target: ['p'],
        failureSummary: 'Fix any of the following: Element has insufficient color contrast...'
      }]
    }]
  }

3. JEST-AXE — UNIT TESTING A11Y WITH JEST + RTL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  npm install --save-dev jest-axe

SETUP (add to jest.config.js or setupFilesAfterFramework):
  import { configureAxe, toHaveNoViolations } from 'jest-axe';
  expect.extend(toHaveNoViolations);

BASIC TEST:
  import React from 'react';
  import { render } from '@testing-library/react';
  import { axe, toHaveNoViolations } from 'jest-axe';
  import ProductCard from './ProductCard';

  expect.extend(toHaveNoViolations);

  it('should have no a11y violations', async () => {
    const { container } = render(
      <ProductCard
        name="Blue Sneakers"
        price={89.99}
        imageUrl="/sneakers.jpg"
        imageAlt="Blue running sneakers"
      />
    );
    const results = await axe(container);
    expect(results).toHaveNoViolations();
  });

TESTING FORMS (most common a11y failure points):
  it('form inputs should have accessible labels', async () => {
    const { container } = render(
      <form>
        <label htmlFor="username">Username</label>
        <input id="username" type="text" />
        <button type="submit">Submit</button>
      </form>
    );
    const results = await axe(container);
    expect(results).toHaveNoViolations();
  });

CONFIGURING RULES:
  const results = await axe(container, {
    rules: {
      'color-contrast': { enabled: false },   // Disable specific rule
    }
  });

  // Or configure globally:
  const axe = configureAxe({
    rules: [
      { id: 'region', enabled: false },  // Skip landmark region requirement
    ]
  });

4. CYPRESS-AXE — E2E A11Y TESTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  npm install --save-dev cypress-axe axe-core

  // cypress/support/e2e.js
  import 'cypress-axe';

  // cypress/e2e/accessibility.cy.js
  describe('Accessibility', () => {
    it('Home page has no a11y violations', () => {
      cy.visit('/');
      cy.injectAxe();           // Inject axe-core into the page
      cy.checkA11y();           // Run axe on full page
    });

    it('Product page has no a11y violations', () => {
      cy.visit('/products/123');
      cy.injectAxe();
      cy.checkA11y('#product-detail', {  // Scope to specific element
        rules: { 'color-contrast': { enabled: false } },
      }, (violations) => {
        violations.forEach((v) => {
          cy.log(`${v.id}: ${v.description}`);
          v.nodes.forEach((node) => cy.log(node.html));
        });
      });
    });

    it('Modal dialog is accessible', () => {
      cy.visit('/');
      cy.findByRole('button', { name: /open modal/i }).click();
      cy.injectAxe();
      cy.checkA11y('[role="dialog"]');
    });
  });

5. PLAYWRIGHT A11Y TESTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  npm install --save-dev @axe-core/playwright

  import { test, expect } from '@playwright/test';
  import AxeBuilder from '@axe-core/playwright';

  test('home page accessibility', async ({ page }) => {
    await page.goto('/');

    const accessibilityScanResults = await new AxeBuilder({ page })
      .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])
      .analyze();

    expect(accessibilityScanResults.violations).toEqual([]);
  });

  test('focus trap in modal', async ({ page }) => {
    await page.goto('/');
    await page.getByRole('button', { name: 'Open Modal' }).click();
    await page.waitForSelector('[role="dialog"]');

    const results = await new AxeBuilder({ page })
      .include('[role="dialog"]')
      .analyze();

    expect(results.violations).toEqual([]);
  });

6. COMMON A11Y ISSUES AND FIXES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IMAGES WITHOUT ALT TEXT:
  // Bad:
  <img src="/product.jpg" />
  // Good:
  <img src="/product.jpg" alt="Blue running sneakers" />
  // Decorative (hidden from screen readers):
  <img src="/divider.svg" alt="" role="presentation" />

BUTTONS WITHOUT ACCESSIBLE NAME:
  // Bad (icon-only button):
  <button><SearchIcon /></button>
  // Good:
  <button aria-label="Search"><SearchIcon /></button>
  // Or:
  <button><SearchIcon aria-hidden="true" /> Search</button>

FORM WITHOUT LABELS:
  // Bad:
  <input type="email" placeholder="Email" />
  // Good (visible label):
  <label htmlFor="email">Email</label>
  <input id="email" type="email" />
  // Good (visually hidden label):
  <label htmlFor="email" className="sr-only">Email</label>
  <input id="email" type="email" placeholder="Email" />

INSUFFICIENT COLOR CONTRAST:
  // WCAG AA requires 4.5:1 for normal text, 3:1 for large text (18pt+)
  // Check: https://webaim.org/resources/contrastchecker/

KEYBOARD FOCUS NOT VISIBLE:
  // Never: outline: none without an alternative
  button:focus { outline: none; }           // ❌ Breaks keyboard navigation
  button:focus-visible { outline: 2px solid blue; } // ✅ Shown only for keyboard

Q: What percentage of accessibility issues can automated tools catch?
A: Automated tools like axe-core catch approximately 30–40% of accessibility
   issues — specifically structural and attribute issues (missing alt text,
   form label associations, ARIA misuse, color contrast). The remaining 60–70%
   require manual testing: meaningful alt text (axe can tell you it exists but
   not whether it describes the image meaningfully), keyboard interaction flows,
   screen reader announcement order, focus management in dynamic content, and
   cognitive accessibility. A mature a11y strategy uses automated testing as a
   baseline + manual testing with screen readers (NVDA, JAWS, VoiceOver).

Q: How do you integrate jest-axe into a React testing strategy?
A: Add jest-axe as a dev dependency and extend Jest's expect with
   toHaveNoViolations. Then add an axe test for each component in your test
   suite: render the component with RTL, pass the container to axe(), and
   assert expect(results).toHaveNoViolations(). This catches a11y regressions
   at the component level, integrated directly into the unit test suite — no
   separate CI job needed. For forms and interactive components, this is
   especially valuable since label associations, button names, and ARIA roles
   are common failure points caught early.

Q: What is the difference between focus and focus-visible?
A: :focus applies whenever an element has focus (mouse click OR keyboard tab).
   :focus-visible applies only when the focus is the result of keyboard navigation
   or another non-pointer interaction. This matters for UX: sighted mouse users
   typically don't need to see focus outlines when clicking a button (the click
   action is clear), but keyboard and screen reader users MUST see focus to know
   where they are. The correct pattern is: suppress the default outline with
   :focus { outline: none } and add a clear outline with :focus-visible
   { outline: 2px solid blue }. Never suppress :focus-visible without an alternative.
