1. WHAT IS VISUAL REGRESSION TESTING?
================================================================================

DEFINITION:
  Visual regression testing automatically detects unintended UI changes by
  comparing screenshots of the current UI against previously approved baselines.

WHY IT MATTERS:
  - CSS changes can visually break components without changing functionality
  - Unit/integration tests verify behavior, NOT appearance
  - A button could have correct text but wrong color, position, or font
  - Visual tests catch: broken layouts, font regressions, color changes,
    overlapping elements, z-index issues, animation glitches

WHAT VISUAL TESTS CATCH THAT FUNCTIONAL TESTS MISS:
  ✅ Wrong button color (passes .should('exist') but looks wrong)
  ✅ Misaligned form fields
  ✅ Overflow text or cut-off content
  ✅ Dark mode regressions
  ✅ Responsive layout breakage at certain viewport sizes
  ✅ Third-party component visual changes after npm update

LEVELS OF VISUAL TESTING:
  1. Component-level: Screenshot of a single component (Button, Card, Modal)
  2. Page-level: Screenshot of a full page (Dashboard, Login)
  3. User flow: Screenshots at key steps in a user journey

MENTAL MODEL:
  Think of it like git diff for pixels.
  Every visual test = "take a screenshot, compare to approved baseline,
  fail if pixels differ above threshold."

2. HOW SCREENSHOT COMPARISON WORKS
================================================================================

PROCESS:
  First run: Take baseline screenshots and store them.
  Subsequent runs: Take new screenshots, compare pixel-by-pixel to baseline.
  If difference > threshold: FAIL the test.

  Baseline           New Screenshot      Diff
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ ██ Submit ██ │   │ ██ Submit ██ │   │              │ ← 0 diff (pass)
  └──────────────┘   └──────────────┘   └──────────────┘

  Baseline           New Screenshot      Diff
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ ██ Submit ██ │   │ ▓▓ Submit ▓▓ │   │ ▓▓▓▓▓▓▓▓▓▓▓▓ │ ← diff (fail)
  └──────────────┘   └──────────────┘   └──────────────┘

THRESHOLD CONFIGURATION:
  Most tools let you configure tolerance:
  - maxDiffPixels: 100 (allow 100 pixels difference)
  - threshold: 0.1 (10% pixel difference tolerance per pixel)
  - maxDiffPixelRatio: 0.01 (1% of total pixels may differ)

UPDATING BASELINES:
  When you intentionally change the UI, you need to update the baseline.
  Command: npx playwright test --update-snapshots

3. PLAYWRIGHT BUILT-IN VISUAL TESTING (toHaveScreenshot)
================================================================================

INSTALLATION: No extra packages — built into @playwright/test

BASIC USAGE:
  import { test, expect } from '@playwright/test';

  test('login page looks correct', async ({ page }) => {
    await page.goto('/login');
    await expect(page).toHaveScreenshot('login-page.png');
  });

  test('button variants look correct', async ({ page }) => {
    await page.goto('/components/buttons');
    const primaryBtn = page.getByRole('button', { name: 'Primary' });
    await expect(primaryBtn).toHaveScreenshot('primary-button.png');
  });

FIRST RUN — GENERATING BASELINES:
  # Run tests — first run creates baseline screenshots
  npx playwright test --update-snapshots

  Baselines stored in: __screenshots__/login-page.png-1.png
  Or with custom dirs in playwright.config.ts

SNAPSHOT CONFIGURATION (playwright.config.ts):
  export default defineConfig({
    expect: {
      toHaveScreenshot: {
        maxDiffPixels: 100,          // Allow 100px difference
        threshold: 0.2,              // 20% color tolerance per pixel
        animations: 'disabled',      // Freeze CSS animations for screenshot
      },
    },
    snapshotDir: './snapshots',       // Where baselines are stored
    snapshotPathTemplate: '{snapshotDir}/{testFilePath}/{arg}{ext}',
  });

MASKING DYNAMIC CONTENT:
  Dynamic content (timestamps, avatars, ads) will always cause false failures.
  Use mask to exclude those elements:

  await expect(page).toHaveScreenshot('dashboard.png', {
    mask: [
      page.getByTestId('timestamp'),   // Hide timestamp
      page.getByTestId('avatar'),      // Hide user avatar
    ],
  });

FULL-PAGE SCREENSHOT:
  await expect(page).toHaveScreenshot('full-page.png', {
    fullPage: true,  // Capture beyond viewport
  });

CLIP TO A REGION:
  await expect(page).toHaveScreenshot('header.png', {
    clip: { x: 0, y: 0, width: 1280, height: 80 },
  });

UPDATING SNAPSHOTS:
  # Update all snapshots:
  npx playwright test --update-snapshots

  # Update specific test:
  npx playwright test login.spec.ts --update-snapshots

VIEWING DIFFS:
  npx playwright show-report
  The HTML report shows: baseline, actual, diff (highlighted in red)

CROSS-BROWSER SCREENSHOTS:
  Each browser/OS combination creates separate baseline files.
  Chrome baseline ≠ Firefox baseline ≠ WebKit baseline.
  CI machines and local machines may produce different screenshots.
  Solution: Run all visual tests in CI only, using Docker for consistency.

4. PERCY (BROWSERSTACK PERCY)
================================================================================

WHAT IT IS:
  Percy is a cloud-based visual testing service.
  Instead of local file comparison, Percy uploads screenshots to the cloud.
  Reviewers approve or reject visual changes in the Percy web UI.

HOW IT WORKS:
  1. Test runs and takes screenshots
  2. Screenshots are uploaded to Percy cloud
  3. Percy's AI compares to baseline
  4. PR shows a Percy status check: "X visual changes detected"
  5. Team member reviews changes in Percy UI and approves/rejects

INSTALLATION (Playwright integration):
  npm install --save-dev @percy/cli @percy/playwright

  import percySnapshot from '@percy/playwright';

  test('homepage visual test', async ({ page }) => {
    await page.goto('/');
    await percySnapshot(page, 'Homepage');  // Upload to Percy
  });

  CI:
  PERCY_TOKEN=xxx npx percy exec -- npx playwright test

WHY USE PERCY OVER PLAYWRIGHT'S BUILT-IN:
  ✅ Browser normalization (Percy renders consistently across browsers)
  ✅ Visual diff review UI with approval workflow
  ✅ Works with any browser (not affected by OS differences)
  ✅ Team collaboration on approvals
  ❌ Paid service (free tier available)
  ❌ Slower CI (screenshot upload time)

5. CHROMATIC (STORYBOOK INTEGRATION)
================================================================================

WHAT IT IS:
  Chromatic is a visual testing tool specifically designed for Storybook.
  Each Story becomes a visual test.
  Also provides: UI Review, UI Tests, and Storybook hosting.

HOW IT WORKS:
  1. You write a Story for each component state
  2. Chromatic captures a screenshot of every Story
  3. Each commit triggers a new Chromatic build
  4. Chromatic shows exactly which component stories changed
  5. Reviewers approve/reject visual changes in the Chromatic web UI

INSTALLATION:
  npm install --save-dev chromatic

  # CI command:
  npx chromatic --project-token=YOUR_TOKEN

WORKFLOW:
  // Button.stories.tsx
  export const Primary: Story = {
    args: { variant: 'primary', children: 'Click Me' },
  };
  export const Disabled: Story = {
    args: { variant: 'primary', disabled: true, children: 'Click Me' },
  };

  # Each story becomes a visual snapshot:
  # ✅ Button/Primary.png
  # ✅ Button/Disabled.png

  When you change Button.tsx, Chromatic detects:
  "Button/Primary changed" → Shows side-by-side diff → Requires approval

CHROMATIC VS PLAYWRIGHT toHaveScreenshot:
  Chromatic: Component-level, Storybook-driven, cloud service, team review workflow
  Playwright: Page/component-level, local baselines, free, developer-driven

6. APPLITOOLS EYES
================================================================================

WHAT IT IS:
  Enterprise visual AI testing service.
  Uses AI (Visual AI) to detect meaningful visual differences,
  ignoring irrelevant noise (font anti-aliasing, 1-pixel shifts).

INTEGRATION (Playwright):
  npm install @applitools/eyes-playwright

  import { Eyes, Target } from '@applitools/eyes-playwright';

  test('visual test', async ({ page }) => {
    const eyes = new Eyes();
    await eyes.open(page, 'My App', 'Homepage Test');
    await page.goto('/');
    await eyes.check('Homepage', Target.window().fully());
    await eyes.close();
  });

WHY APPLITOOLS:
  ✅ AI-based comparison (ignores non-meaningful pixel differences)
  ✅ Ultrafast Grid (run once, test across many browsers)
  ✅ Best for enterprise scale
  ❌ Most expensive option

7. HANDLING DYNAMIC CONTENT
================================================================================

PROBLEM: Dynamic content causes false failures.
  Common dynamic elements:
  - Timestamps ("Last updated 2 minutes ago")
  - User avatars / random profile photos
  - Ads and third-party widgets
  - Animated spinners, carousels
  - Random or generated IDs
  - Browser OS-level UI (scrollbars, fonts)

SOLUTIONS:

1. MASK THE ELEMENT (Playwright):
   await expect(page).toHaveScreenshot({
     mask: [page.getByTestId('timestamp')],
   });

2. REPLACE WITH PLACEHOLDER BEFORE SCREENSHOT:
   // In your app, add a CSS class for testing:
   // .visual-test img { visibility: hidden; }
   await page.addStyleTag({ content: '[data-visual-ignore] { visibility: hidden; }' });

3. FREEZE ANIMATIONS:
   // In playwright.config.ts:
   use: {
     launchOptions: {
       args: ['--force-prefers-reduced-motion'],
     },
   }
   // OR:
   await page.emulateMedia({ reducedMotion: 'reduce' });

4. USE CLIP/VIEWPORT:
   // Only screenshot the stable region:
   await expect(page).toHaveScreenshot({ clip: { x: 0, y: 0, width: 800, height: 400 } });

5. THRESHOLD TOLERANCE:
   await expect(page).toHaveScreenshot({
     maxDiffPixels: 500,  // Allow some variation for anti-aliasing
   });

6. WAIT FOR STABLE STATE:
   // Ensure loading is done before screenshot:
   await page.waitForLoadState('networkidle');
   await expect(page.getByTestId('spinner')).not.toBeVisible();
   await expect(page).toHaveScreenshot('dashboard.png');

7. MOCK DATES:
   // Playwright: Mock Date.now() for consistent timestamps
   await page.addInitScript(() => {
     Date.now = () => 1700000000000; // Fixed timestamp
   });

8. USE CONSISTENT FONTS (Docker):
   // Font rendering differs by OS — use consistent Docker image in CI
   // mcr.microsoft.com/playwright includes consistent font rendering

8. STORYBOOK + CHROMATIC WORKFLOW
================================================================================

FULL WORKFLOW:

  Step 1: Write Stories for every component state
  ─────────────────────────────────────────────────
  // Button.stories.tsx
  import type { Meta, StoryObj } from '@storybook/react';
  import { Button } from './Button';

  const meta: Meta<typeof Button> = {
    component: Button,
  };
  export default meta;
  type Story = StoryObj<typeof Button>;

  export const Primary: Story = { args: { variant: 'primary', children: 'Submit' } };
  export const Secondary: Story = { args: { variant: 'secondary', children: 'Cancel' } };
  export const Loading: Story = { args: { loading: true, children: 'Loading...' } };
  export const Disabled: Story = { args: { disabled: true, children: 'Disabled' } };
  export const Destructive: Story = { args: { variant: 'destructive', children: 'Delete' } };

  Step 2: Run Chromatic on every PR
  ─────────────────────────────────
  # .github/workflows/chromatic.yml
  - name: Run Chromatic
    uses: chromaui/action@v11
    with:
      projectToken: ${{ secrets.CHROMATIC_PROJECT_TOKEN }}
      buildScriptName: build-storybook

  Step 3: Review visual changes in Chromatic UI
  ──────────────────────────────────────────────
  - Chromatic comments on your PR: "5 stories changed"
  - Open Chromatic app to see before/after for each story
  - Team approves legitimate changes, rejects accidental regressions

  Step 4: Merge PR after approval
  ─────────────────────────────────
  - New baseline is set for approved changes
  - Next PR is compared to the new baseline

STORIES AS DOCUMENTATION:
  Storybook + Chromatic doubles as:
  - Visual test suite
  - Living style guide / design documentation
  - Component development environment

9. CI INTEGRATION FOR VISUAL TESTS
================================================================================

PLAYWRIGHT VISUAL TESTS IN CI (GitHub Actions):
  name: Visual Regression Tests
  on: [pull_request]

  jobs:
    visual-tests:
      runs-on: ubuntu-latest
      container:
        # Use official Playwright image for consistent screenshots:
        image: mcr.microsoft.com/playwright:v1.45.0-jammy

      steps:
        - uses: actions/checkout@v4

        - name: Install dependencies
          run: npm ci

        - name: Run visual tests
          run: npx playwright test visual/
          env:
            PLAYWRIGHT_HTML_REPORT: playwright-report

        - name: Upload Playwright Report
          if: failure()
          uses: actions/upload-artifact@v4
          with:
            name: playwright-report
            path: playwright-report/
            retention-days: 7

IMPORTANT: Using mcr.microsoft.com/playwright ensures:
  - Same font rendering as baseline
  - Consistent pixel-perfect screenshots
  - No OS-level variation

UPDATING BASELINES IN CI:
  # NEVER update snapshots in main CI — only from local dev or dedicated PR
  # Strategy: create a "update-snapshots" workflow triggered manually:

  name: Update Visual Snapshots
  on:
    workflow_dispatch:  # Manual trigger only
  jobs:
    update:
      runs-on: ubuntu-latest
      container:
        image: mcr.microsoft.com/playwright:v1.45.0-jammy
      steps:
        - uses: actions/checkout@v4
        - run: npm ci
        - run: npx playwright test --update-snapshots
        - uses: stefanzweifel/git-auto-commit-action@v5
          with:
            commit_message: "chore: update visual snapshots"

10. BEST PRACTICES
================================================================================

DO:
  ✅ Use Docker/container for consistent screenshot rendering
  ✅ Store baseline screenshots in version control (for Playwright)
  ✅ Mask dynamic content (timestamps, avatars, ads)
  ✅ Disable animations before capturing
  ✅ Capture component-level + page-level screenshots
  ✅ Set reasonable threshold (100-500 pixels) for anti-aliasing tolerance
  ✅ Wait for network idle before capturing
  ✅ Test multiple viewport sizes (mobile, tablet, desktop)
  ✅ Review visual diffs in PRs before merging

DON'T:
  ❌ Don't run visual tests on every minor PR if team has no review process
  ❌ Don't use local screenshots as CI baselines (OS font differences)
  ❌ Don't forget to update baselines after intentional UI changes
  ❌ Don't take screenshots of entire pages if only one component changed
  ❌ Don't let visual tests block CI without a review process

BASELINE MANAGEMENT TIPS:
  1. Tag baselines with semantic version of design system
  2. Update baselines as part of "design system upgrade" PRs
  3. Use branch protection to require visual review approval
  4. Store screenshot artifacts for 30 days in CI

WHEN TO USE VISUAL TESTING:
  High Value:
  - Design system components (Button, Input, Card, Modal)
  - Dashboard layouts
  - Critical user-facing pages (checkout, pricing)
  - Dark/light mode switch

  Low Value (skip visual testing):
  - Loading states (hard to capture at right moment)
  - Pages that change frequently (homepage, blog)
  - Data tables with dynamic data
