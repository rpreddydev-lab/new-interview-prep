2. ARCHITECTURE DIFFERENCES
================================================================================

CYPRESS:
  - Test code runs INSIDE the browser in an iframe alongside the app
  - Accesses the app's DOM directly (same JavaScript context)
  - Can inspect app's internal state (window, localStorage)
  - Uses a proxy server to intercept XHR/fetch
  - Limited: same-origin only (no cross-origin iFrames by default)

  Browser Process:
  ┌─────────────────────────────────────────┐
  │ Browser (Chrome/Firefox/Electron)       │
  │  ┌───────────────┐  ┌────────────────┐  │
  │  │ Test code     │  │ Your App       │  │
  │  │ (Cypress SDK) │  │ (under test)   │  │
  │  └───────────────┘  └────────────────┘  │
  └─────────────────────────────────────────┘

PLAYWRIGHT:
  - Test code runs in Node.js (OUTSIDE the browser)
  - Communicates with browser via CDP (Chrome DevTools Protocol) / WebSocket
  - Supports multiple browser types (Chromium, Firefox, WebKit)
  - Full cross-origin support (different tabs, iFrames on different domains)
  - Better isolation (test process crash doesn't crash browser)

  ┌────────────────────┐         ┌───────────────────────────────┐
  │ Node.js Process    │  CDP/WS │ Browser Process               │
  │ (test code)        │◄────────►│ (Chromium/Firefox/WebKit)    │
  └────────────────────┘         └───────────────────────────────┘

3. LANGUAGE AND API STYLE
================================================================================

CYPRESS — Command Queue Model:
  Tests are written SYNCHRONOUSLY but execute asynchronously.
  Each cy.* command is queued and Cypress runs them in order.

  // CYPRESS — no await needed, commands queue automatically:
  cy.visit('/login');
  cy.get('[data-testid="email"]').type('alice@example.com');
  cy.get('[data-testid="password"]').type('password123');
  cy.get('button[type="submit"]').click();
  cy.url().should('include', '/dashboard');

  PRO: Simpler for beginners, less async complexity
  CON: Can't use async/await easily, can cause confusion with returns

  // Cypress returns are chainable, not the actual value:
  const el = cy.get('.element'); // NOT the DOM element!
  // Use .then() to access the value:
  cy.get('.element').then(($el) => {
    const text = $el.text();
    expect(text).to.include('Hello');
  });

PLAYWRIGHT — Native async/await:
  Standard JavaScript/TypeScript async/await.
  All actions and assertions are Promises.

  // PLAYWRIGHT — explicit await:
  await page.goto('/login');
  await page.getByLabel('Email').fill('alice@example.com');
  await page.getByLabel('Password').fill('password123');
  await page.getByRole('button', { name: 'Sign In' }).click();
  await expect(page).toHaveURL('/dashboard');

  PRO: Standard, familiar, easy to use with loops/conditionals
  CON: Easy to forget await (TypeScript helps catch this)

  // Playwright returns actual values:
  const heading = await page.getByRole('heading').textContent();
  expect(heading).toBe('Dashboard'); // heading is a string

4. BROWSER SUPPORT
================================================================================

CYPRESS:
  ✅ Chrome (Chromium-based)
  ✅ Firefox
  ✅ Edge (Chromium-based)
  ✅ Electron (default, built-in)
  ❌ Safari — NOT supported
  ❌ Real iOS/Android — NOT supported

PLAYWRIGHT:
  ✅ Chromium (Chrome, Edge)
  ✅ Firefox
  ✅ WebKit (same engine as Safari on iOS/macOS)
  ✅ Mobile browser emulation (Pixel 5, iPhone 13, etc.)
  ❌ Real device testing (use Appium or BrowserStack instead)

IMPACT:
  If your users use Safari (common for iOS users): USE PLAYWRIGHT
  WebKit ≈ Safari, but it's not the exact same engine. Close enough for most tests.
  Real Safari on real Mac: use BrowserStack + Playwright for 100% accuracy.

5. LOCATORS AND SELECTORS
================================================================================

CYPRESS SELECTORS:
  cy.get('[data-testid="submit"]')       // Attribute selector
  cy.contains('Submit')                  // Text content
  cy.get('button').contains('Submit')    // Combined
  cy.get('[role="dialog"]')              // ARIA role attribute

  // Cypress doesn't have native "getByRole" like Playwright/RTL
  // Requires a third-party plugin for RTL-style queries:
  // @testing-library/cypress:
  cy.findByRole('button', { name: /submit/i }).click();

PLAYWRIGHT LOCATORS (more accessible-first):
  page.getByRole('button', { name: 'Submit' })  // ARIA role (native support)
  page.getByLabel('Email')                       // Label text
  page.getByText('Click here')                   // Text content
  page.getByTestId('submit-btn')                 // data-testid
  page.getByPlaceholder('Enter email')           // Placeholder

  PLAYWRIGHT LOCATORS ARE STRICT:
  If getByRole() matches multiple elements, it THROWS.
  This prevents accidentally clicking the wrong button.

  CYPRESS by default returns all matches:
  cy.get('button').click(); // Clicks first button, no error if multiple

VERDICT: Playwright's locator API is more RTL-aligned and catches ambiguity issues.

6. NETWORK INTERCEPTION
================================================================================

CYPRESS — cy.intercept():
  cy.intercept('GET', '/api/users', { fixture: 'users.json' }).as('getUsers');
  cy.wait('@getUsers');
  cy.get('[data-testid="user-list"]').should('be.visible');

  // Inspect request after wait:
  cy.wait('@getUsers').then(({ request, response }) => {
    expect(request.url).to.include('/api/users');
    expect(response.statusCode).to.equal(200);
  });

PLAYWRIGHT — page.route():
  await page.route('/api/users', async (route) => {
    await route.fulfill({ body: JSON.stringify(usersData) });
  });

  // Capture a request:
  const [request] = await Promise.all([
    page.waitForRequest('/api/users'),
    page.getByRole('button', { name: 'Load Users' }).click(),
  ]);

DIFFERENCES:
  - Cypress uses alias pattern (cy.intercept().as() + cy.wait('@alias'))
  - Playwright uses Promise.all() to capture requests/responses
  - Both support stubbing, modifying, and passing through requests
  - Playwright supports request modification (changing headers, body) more easily

7. DEBUGGING EXPERIENCE
================================================================================

CYPRESS — TIME TRAVEL DEBUGGING:
  The killer feature of Cypress.
  The Cypress Test Runner shows a snapshot of the DOM at EACH COMMAND.
  Click any step in the command log to see exactly what the DOM looked like.
  Hover over a command to pin the snapshot.

  Also:
  .pause()  → Pause test execution
  cy.debug() → Open Chrome DevTools at that point
  Screenshot on failure
  Video recording of entire test run

PLAYWRIGHT — TRACE VIEWER:
  After a test failure, Playwright saves a trace file.
  View with: npx playwright show-report
  The trace includes:
  - DOM snapshots before/after each action
  - Network requests
  - Console logs
  - Timestamps

  Also:
  --debug flag → Opens browser with step-through mode
  --ui flag → Interactive UI mode (similar to Cypress GUI)
  page.pause() → Pause execution
  PWDEBUG=1 → Extra debugging mode

  PLAYWRIGHT'S UI MODE (v1.32+):
  npx playwright test --ui
  Provides: test runner, DOM explorer, time-travel through steps.
  Brings Playwright close to the Cypress debugging experience.

VERDICT:
  Historically Cypress had a superior debugging experience.
  Since Playwright UI Mode (2023), the gap has closed significantly.

8. PARALLEL EXECUTION AND CI
================================================================================

CYPRESS:
  ❌ No built-in parallel execution across machines
  ✅ Requires Cypress Cloud (paid) for smart parallelization
  ✅ Can use GitHub Actions matrix manually for parallelization
  ✅ Multiple workers in the same machine (Cypress 12+): --auto-cancel-after-failures

PLAYWRIGHT:
  ✅ Built-in parallel execution (fullyParallel: true)
  ✅ Built-in sharding (--shard=1/4, --shard=2/4, etc.)
  ✅ Free parallelization with GitHub Actions matrix
  ✅ Workers per machine: workers: 4 in config

PERFORMANCE COMPARISON (approximate, varies by test suite):
  100 E2E tests, sequential:
  - Cypress: ~20 minutes
  - Playwright: ~20 minutes

  100 E2E tests, parallelized (4 workers):
  - Cypress (Cloud): ~6 minutes
  - Playwright (sharding): ~5 minutes (free)

VERDICT: Playwright has clear advantage — no paid service needed for parallelization.

9. COMMUNITY, ECOSYSTEM, AND PRICING
================================================================================

CYPRESS:
  Community: Large, well-established (since 2017)
  npm weekly downloads: ~5 million
  Plugins: @testing-library/cypress, cypress-axe, cypress-real-events, etc.
  Cypress Cloud: Paid dashboard with test analytics, parallelization, flakiness detection
  Free tier: Limited test recordings per month

PLAYWRIGHT:
  Community: Growing rapidly (since 2020 public release)
  npm weekly downloads: ~5 million (now comparable to Cypress)
  Maintained by Microsoft — strong long-term backing
  Free: All features are free, no paid cloud required
  Playwright Report: Free HTML report with trace viewer

LEARNING RESOURCES:
  Cypress: Comprehensive docs, Cypress Real World App (example app)
  Playwright: Excellent docs, codegen tool to record tests

INTEGRATIONS:
  Both integrate with: GitHub Actions, GitLab CI, Jenkins, CircleCI
  Both have VS Code extensions
  Playwright: Official VS Code extension with one-click test running

10. WHEN TO CHOOSE CYPRESS
================================================================================

CHOOSE CYPRESS WHEN:
  ✅ Your team is already using Cypress and has investment in it
  ✅ You don't need Safari support (your users are all Chrome/Firefox)
  ✅ Your app is a single-page app with no cross-origin requirements
  ✅ You want the classic time-travel debugging experience
  ✅ You value the @testing-library/cypress integration for accessible queries
  ✅ You're doing component testing alongside E2E (Cypress supports both)
  ✅ You want a mature ecosystem with many plugins
  ✅ Budget for Cypress Cloud for parallelization

TYPICAL CYPRESS USERS:
  - Frontend-focused teams in the React/Vue/Angular ecosystem
  - Teams that want an all-in-one solution (component + E2E)
  - Companies that value the visual debugging tools


================================================================================
11. WHEN TO CHOOSE PLAYWRIGHT
================================================================================

CHOOSE PLAYWRIGHT WHEN:
  ✅ You need cross-browser testing including Safari/WebKit
  ✅ You need multi-tab or cross-origin testing
  ✅ You want free, built-in parallel execution (no paid service)
  ✅ Your team is comfortable with async/await
  ✅ You need mobile browser emulation
  ✅ You need API testing alongside E2E (request context)
  ✅ You prefer accessible-first locators (getByRole, getByLabel)
  ✅ You're starting fresh (greenfield project)
  ✅ You need cross-language support (Python, Java, C# teams)
  ✅ Microsoft ecosystem (Azure, .NET) alignment

TYPICAL PLAYWRIGHT USERS:
  - Full-stack teams that need real cross-browser coverage
  - Teams starting fresh in 2024+
  - Enterprise teams that want no vendor lock-in (no Cypress Cloud needed)
  - Teams with multi-language backend (Python/Java tests too)

12. MIGRATION GUIDE (CYPRESS → PLAYWRIGHT)
================================================================================

CONCEPT MAPPING:
  cy.visit('/path')           → await page.goto('/path')
  cy.get('[data-testid]')     → page.getByTestId('id')
  cy.contains('text')         → page.getByText('text')
  .click()                    → await locator.click()
  .type('text')               → await locator.fill('text')
  .should('be.visible')       → await expect(locator).toBeVisible()
  .should('have.text', 'val') → await expect(locator).toHaveText('val')
  cy.url().should('include')  → await expect(page).toHaveURL(/path/)
  cy.wait('@alias')           → await page.waitForResponse('/api/...')
  cy.intercept(...)           → await page.route(...)
  beforeEach(() => {...})     → test.beforeEach(async ({ page }) => {...})
  cy.fixture('data')          → Built-in test.use({ ... }) or import JSON
  cy.task('taskName')         → Custom fixture or globalSetup
  cy.setCookie(...)           → await context.addCookies([...])

MIGRATION STEPS:
  1. Install Playwright: npm install @playwright/test && npx playwright install
  2. Copy test structure (describe → test.describe)
  3. Replace cy.* with page.* equivalents (above table)
  4. Add await everywhere
  5. Replace cy.intercept with page.route
  6. Move custom commands to fixtures or helper functions
  7. Update CI config to use Playwright GitHub Action
