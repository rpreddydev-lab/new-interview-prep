1. WHY KEYBOARD NAVIGATION MATTERS
================================================================================

Keyboard navigation is required by:
  - People with motor disabilities who cannot use a mouse
  - Screen reader users (screen readers use keyboard to browse)
  - Power users who prefer keyboard for speed
  - Sip-and-puff users, switch users (all ultimately keyboard-like)
  - Voice control users (Dragon NaturallySpeaking uses keyboard simulation)
  - Mobile users using external keyboards with tablets

WCAG Requirement 2.1.1 — Keyboard (Level A):
  "All functionality of the content is operable through a keyboard interface
   without requiring specific timings for individual keystrokes."

WCAG 2.1.2 — No Keyboard Trap (Level A):
  "If keyboard focus can be moved to a component using a keyboard interface,
   then focus can be moved away from that component using only a keyboard
   interface."

Default keyboard keys for web navigation:
  Tab             — Move focus forward
  Shift + Tab     — Move focus backward
  Enter           — Activate links, buttons (buttons also Space)
  Space           — Scroll page; activate buttons, checkboxes
  Arrow keys      — Navigate within composite widgets (menus, tabs, sliders)
  Escape          — Close dialogs, dismiss popups, cancel actions
  Home / End      — Go to first/last item in a widget
  Page Up/Down    — Scroll; navigate in large widgets

2. DEFAULT FOCUSABLE ELEMENTS
================================================================================

These elements are keyboard focusable by default (no tabindex needed):

  Element                       Notes
  ----------------------------  ------------------------------------------
  <a href="...">                Links with href are focusable; no href = not
  <button>                      All button types (submit, reset, button)
  <input> (all types)           Except type="hidden"
  <select>                      Dropdown
  <textarea>                    Multi-line text input
  <details> / <summary>         summary is the focus target
  <audio controls>              Control bar is focusable
  <video controls>              Control bar is focusable
  Elements with tabindex >= 0   Any element made focusable explicitly
  <iframe>                      The frame itself

NOT focusable by default:
  <div>, <span>, <p>, <h1>-<h6>, <img>, <table>, <section>, etc.
  (All structural/presentational elements)

Disabled form elements:
  HTML disabled attribute removes element from tab order.
  aria-disabled="true" keeps element in tab order but announces as disabled.
  Choose based on whether discovery is important.

================================================================================
3. THE TAB ORDER
================================================================================

The tab order is the sequence in which focusable elements receive focus
when the user presses Tab. It should:
  1. Follow the logical reading/visual order (left-to-right, top-to-bottom)
  2. Match the DOM order (best approach — don't fight the DOM)
  3. Never create confusion by jumping unexpectedly

Natural tab order = DOM order
  Browsers visit focusable elements in DOM order by default.
  Elements with tabindex > 0 are visited BEFORE all tabindex="0" elements
  (this is why tabindex > 0 is an antipattern).

Tab order can break when:
  - CSS changes visual order but not DOM order (flex-direction: row-reverse,
    order property, float, position: absolute without logical DOM sequence)
  - tabindex values > 0 are used
  - Elements are visually hidden but still in tab order
  - Focus is moved programmatically to unexpected places

Inspect tab order:
  Chrome DevTools → Elements panel → 
  "Accessibility" tab → "Tab order" visualization
  Or use Tab key manually.

4. TABINDEX ATTRIBUTE IN DEPTH
================================================================================

tabindex="0"    — Add element to natural tab order at its DOM position
tabindex="-1"   — Focusable via JavaScript (element.focus()) but not Tab key
tabindex="N>0"  — ANTI-PATTERN: Forces order, causes confusion; avoid

Details:
  tabindex="0"
    Useful for making non-interactive elements interactive (custom widgets).
    Should accompany role attribute.
    <div role="button" tabindex="0">Custom Button</div>

  tabindex="-1"
    Removes element from tab flow but allows programmatic focus.
    Used for:
      - Modal dialogs (focus programmatically on open/close)
      - Roving tabindex composite widgets
      - Skip link targets
      - Carousel items (only the active one is tabindex="0")
    
    Example:
    document.getElementById('modal').focus(); // tabindex="-1" allows this

  tabindex="1" and higher — AVOID
    Creates a parallel focus order that fights DOM order.
    Screen reader users and keyboard users experience jumping focus.
    Maintenance nightmare.
    
    ✗ <input tabindex="3">
    ✗ <button tabindex="1">
    ✓ Reorder the DOM instead

tabindex on non-interactive elements:
  When you add tabindex to a structural element, you should also:
    - Add an appropriate role
    - Add keyboard event handlers
    - Ensure visible focus indicator
    - Manage aria states
  
  Partial keyboard support is worse than none — if it looks interactive
  but doesn't respond to keyboard, users are confused.

5. VISIBLE FOCUS INDICATORS
================================================================================

WCAG 2.4.11 (AA, 2.2) — Focus Appearance:
  Focus indicator must have:
    - Area: Perimeter of the focused component, at least 2 CSS px
    - Contrast: 3:1 against adjacent colors
    - Not obscured by other content

The single most common accessibility bug in modern web development is
removing the focus outline with outline: none or outline: 0 without
providing a visible alternative.

✗ The wrong approach:
  * { outline: none; }  /* Destroys keyboard accessibility */
  :focus { outline: none; }

✓ The right approaches:

  /* Option 1: Style the outline */
  :focus-visible {
    outline: 3px solid #005fcc;
    outline-offset: 2px;
  }

  /* Option 2: Custom focus ring */
  :focus-visible {
    outline: none;
    box-shadow: 0 0 0 3px rgba(0, 95, 204, 0.6);
  }

  /* Option 3: Different styles for mouse vs keyboard */
  :focus:not(:focus-visible) {
    outline: none; /* Mouse focus: no ring */
  }
  :focus-visible {
    outline: 3px solid #005fcc; /* Keyboard focus: visible ring */
  }

:focus vs :focus-visible:
  :focus           — Fires on any focus (mouse click AND keyboard Tab)
  :focus-visible   — Fires only when browser determines focus should be
                     shown (keyboard navigation, not mouse click)
  
  Browsers use heuristics: keyboard Tab = show ring, mouse click = no ring
  (for most interactive elements). Forms fields show ring for both.

Focus indicator requirements:
  - Must be visible on ALL focusable elements
  - Must have sufficient contrast (3:1 against surroundings)
  - Must not be hidden behind other content
  - Must be at least a 2px outline (WCAG 2.2)

Testing focus styles:
  Tab through every interactive element on the page.
  Each one should have a clearly visible indicator.

6. SKIP LINKS
================================================================================

Skip links allow keyboard users to bypass repetitive navigation blocks
and jump directly to main content.

WCAG 2.4.1 — Bypass Blocks (Level A):
  "A mechanism is available to bypass blocks of content that are repeated
   on multiple Web pages."

Implementation:
  <!-- Place as the VERY FIRST element in <body> -->
  <a href="#main-content" class="skip-link">
    Skip to main content
  </a>
  
  <main id="main-content" tabindex="-1">
    <!-- main page content -->
  </main>

  CSS (shown only on focus):
  .skip-link {
    position: absolute;
    left: -9999px;
    top: auto;
    width: 1px;
    height: 1px;
    overflow: hidden;
    z-index: -999;
  }
  .skip-link:focus {
    position: fixed;
    top: 0;
    left: 0;
    width: auto;
    height: auto;
    overflow: auto;
    padding: 12px 24px;
    background: #000;
    color: #fff;
    font-size: 1rem;
    font-weight: bold;
    text-decoration: none;
    border-radius: 0 0 4px 0;
    z-index: 9999;
  }

Why tabindex="-1" on main:
  In some browsers, anchor links (#id) don't move browser focus, only
  scroll position. Adding tabindex="-1" makes the element programmatically
  focusable so the skip link actually moves focus to main content.

Multiple skip links (for complex pages):
  <a href="#main-content">Skip to main content</a>
  <a href="#search">Skip to search</a>
  <a href="#footer-nav">Skip to footer navigation</a>

In-page navigation (same page):
  Table of contents with anchor links serve as skip links within long pages.

7. FOCUS MANAGEMENT IN DYNAMIC UIS
================================================================================

Focus management is critical when content changes dynamically:

PRINCIPLE: When you open/show something, move focus INTO it.
           When you close/hide it, return focus to the trigger.

Opening a modal:
  1. Save reference to element that triggered the modal (document.activeElement)
  2. Set focus to first focusable element inside modal (or the modal itself)
  3. Trap focus within modal while open
  4. On close: return focus to the saved trigger

  function openModal(trigger) {
    const savedFocus = document.activeElement;
    const modal = document.getElementById('modal');
    modal.hidden = false;
    modal.setAttribute('aria-modal', 'true');
    // Move focus to first interactive element
    const firstFocusable = modal.querySelector(
      'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
    );
    if (firstFocusable) firstFocusable.focus();
    
    return () => {
      modal.hidden = true;
      savedFocus.focus(); // Return focus to trigger
    };
  }

Expanding content (accordion, dropdown):
  When expanding: move focus to the first item in the expanded content
  OR leave focus on the trigger (simpler, also acceptable)
  When collapsing: return focus to trigger if focus was inside the panel

Routing in SPAs:
  On route change, move focus to a logical location:
  Option 1: Focus the <h1> of the new page (tabindex="-1")
  Option 2: Focus a skip-navigation-like announcement region
  Option 3: Focus the <main> element
  
  // After navigation
  const h1 = document.querySelector('h1');
  if (h1) {
    h1.tabIndex = -1;
    h1.focus();
  }

Loading states:
  When content is loading, focus can remain on the trigger.
  When content loads, announce via live region.
  If focus element is removed from DOM, it falls back to <body>
  — always proactively manage focus before removing focussed elements.

Inline error messages:
  After form submission failure, move focus to:
  Option 1: Error summary at top of form (common pattern)
  Option 2: First field with an error
  
  // Focus error summary
  const summary = document.getElementById('error-summary');
  summary.removeAttribute('hidden');
  summary.tabIndex = -1;
  summary.focus();

8. FOCUS TRAPPING IN MODALS
================================================================================

A modal dialog must trap focus — Tab should cycle within the modal,
not escape to background content.

Focus trap implementation:
  function trapFocus(modalElement) {
    const focusable = modalElement.querySelectorAll(
      'a[href], button:not([disabled]), input:not([disabled]),' +
      'select:not([disabled]), textarea:not([disabled]),' +
      '[tabindex]:not([tabindex="-1"])'
    );
    const first = focusable[0];
    const last = focusable[focusable.length - 1];
    
    function handleKeydown(e) {
      if (e.key !== 'Tab') return;
      
      if (e.shiftKey) {
        // Shift+Tab: going backward
        if (document.activeElement === first) {
          e.preventDefault();
          last.focus();
        }
      } else {
        // Tab: going forward
        if (document.activeElement === last) {
          e.preventDefault();
          first.focus();
        }
      }
    }
    
    modalElement.addEventListener('keydown', handleKeydown);
    
    // Cleanup
    return () => modalElement.removeEventListener('keydown', handleKeydown);
  }

Also handle Escape key:
  document.addEventListener('keydown', (e) => {
    if (e.key === 'Escape' && modal.open) {
      closeModal();
    }
  });

Modern alternative: <dialog> element
  <dialog> provides native focus trapping and Escape handling.
  dialog.showModal()  — Opens modal, traps focus, ESC closes
  dialog.close()      — Closes, returns focus to trigger
  dialog.show()       — Opens non-modal (no focus trap)
  
  <dialog id="my-dialog">
    <h2>Are you sure?</h2>
    <button id="confirm">Confirm</button>
    <button id="cancel">Cancel</button>
  </dialog>
  
  <script>
    const dialog = document.getElementById('my-dialog');
    document.getElementById('open-btn').onclick = () => dialog.showModal();
    document.getElementById('cancel').onclick = () => dialog.close();
  </script>

9. KEYBOARD PATTERNS FOR CUSTOM WIDGETS
================================================================================

The ARIA Authoring Practices Guide (APG) defines expected keyboard patterns:

BUTTONS:
  Enter or Space   — Activate

LINKS:
  Enter            — Activate

CHECKBOXES:
  Space            — Toggle checked state

RADIO BUTTONS:
  Arrow keys       — Move between options in group (roving tabindex)
  Space            — Select focused option

SELECT / LISTBOX:
  Arrow keys       — Navigate options
  Enter or Space   — Select option
  Home / End       — First / last option
  Type character   — Jump to matching item

TABS:
  Arrow keys       — Switch between tabs
  Tab              — Move into the tab panel
  Home / End       — First / last tab

MENU / MENUBAR:
  Arrow keys       — Navigate items
  Enter / Space    — Activate item or open submenu
  Escape           — Close menu, return to trigger
  Home / End       — First / last item

TREE:
  Arrow Down/Up    — Next/previous item
  Arrow Right      — Expand or go to first child
  Arrow Left       — Collapse or go to parent
  Home / End       — First / last item
  Enter            — Select/activate item

SLIDER:
  Arrow keys       — Increment/decrement by step
  Home / End       — Min / max value
  Page Up/Down     — Large step

DIALOG:
  Escape           — Close dialog
  Tab / Shift+Tab  — Cycle through dialog focusable elements

10. ROVING TABINDEX PATTERN
================================================================================

For composite widgets (toolbars, tab lists, radio groups, menus), only ONE
element in the group should be in the tab order at a time. Arrow keys move
focus within the group.

This is the "roving tabindex" or "tab rover" pattern.

Why: If a toolbar has 10 buttons, you don't want 10 tab stops. Users Tab
into the toolbar (one stop), then use Arrow keys to navigate within it.

Implementation:
  <div role="toolbar" aria-label="Text formatting">
    <button tabindex="0" aria-pressed="false">Bold</button>
    <button tabindex="-1" aria-pressed="false">Italic</button>
    <button tabindex="-1" aria-pressed="false">Underline</button>
  </div>

  const toolbar = document.querySelector('[role="toolbar"]');
  const buttons = [...toolbar.querySelectorAll('button')];
  let currentIndex = 0;

  toolbar.addEventListener('keydown', (e) => {
    let newIndex;
    
    if (e.key === 'ArrowRight') {
      newIndex = (currentIndex + 1) % buttons.length;
    } else if (e.key === 'ArrowLeft') {
      newIndex = (currentIndex - 1 + buttons.length) % buttons.length;
    } else if (e.key === 'Home') {
      newIndex = 0;
    } else if (e.key === 'End') {
      newIndex = buttons.length - 1;
    } else {
      return;
    }
    
    e.preventDefault();
    buttons[currentIndex].tabIndex = -1; // Remove from tab order
    buttons[newIndex].tabIndex = 0;       // Add to tab order
    buttons[newIndex].focus();
    currentIndex = newIndex;
  });

  toolbar.addEventListener('focusin', (e) => {
    // When focus comes into the toolbar, always go to current item
    if (e.target === toolbar) {
      buttons[currentIndex].focus();
    }
  });

11. COMMON KEYBOARD NAVIGATION BUGS
================================================================================

BUG 1: Outline removed with no alternative
  Problem: *{outline:none} or :focus{outline:none}
  Fix: Style :focus-visible instead of removing it

BUG 2: Click-only event handlers (no keyboard equivalent)
  Problem: onclick on <div> without Enter/Space handling
  Fix: Use <button> or add keydown handler

BUG 3: Mouse-only hover interactions
  Problem: Dropdown menus that only trigger on :hover
  Fix: Also implement :focus-within or explicit JavaScript for keyboard

BUG 4: Focus trapped after closing modal
  Problem: Focus goes to <body> after modal closes
  Fix: Save the trigger reference and restore focus

BUG 5: Keyboard shortcuts conflicting with browser/OS shortcuts
  Problem: Using Ctrl+S, Ctrl+P, etc. for custom features
  Fix: Avoid common browser shortcuts, or only intercept in specific contexts

BUG 6: Tab order mismatch with visual layout
  Problem: CSS reorders visually (flex order, float) but DOM order differs
  Fix: Reorder DOM to match visual order

BUG 7: Focus jumps unpredictably on SPA navigation
  Problem: No focus management after route change
  Fix: Move focus to page title or main content after navigation

BUG 8: Keyboard inaccessible custom widgets
  Problem: Custom dropdown with only mouse support
  Fix: Implement full keyboard patterns per ARIA APG

BUG 9: tabindex > 0 values
  Problem: tabindex="1", tabindex="5", etc. causing confusing focus order
  Fix: Reorder DOM, use tabindex="0" and tabindex="-1" only

BUG 10: Missing keyboard activation for toggle buttons
  Problem: Toggle only activates on mouse click, not Space/Enter
  Fix: Native <button> handles this; for custom, add keydown handler

12. IMPORTANT INTERVIEW Q&A
================================================================================

Q1: Why is keyboard navigation important for accessibility?
A: Many users cannot use a mouse — motor disabilities, screen reader users,
   switch device users, voice control users all depend on keyboard. WCAG 2.1.1
   (Level A) requires all functionality to be keyboard accessible. Additionally,
   screen readers use the keyboard to navigate the page, so keyboard
   accessibility is a prerequisite for screen reader accessibility. Keyboard
   support also benefits power users who prefer keyboard for speed.

Q2: What are the three values of tabindex and when do you use each?
A: tabindex="0" adds the element to the natural tab order at its DOM position —
   use this to make non-interactive elements interactive (e.g., custom widgets).
   tabindex="-1" allows programmatic focus via JavaScript but removes from
   tab flow — use for modal dialog targets, skip link destinations, and
   non-active items in composite widgets (roving tabindex). tabindex="N > 0"
   creates a parallel focus order that fights DOM order — it's an antipattern
   that should be avoided; reorder the DOM instead.

Q3: What is the :focus-visible pseudo-class and when should you use it?
A: :focus-visible fires only when the browser determines the focus indicator
   should be visible — typically keyboard navigation but not mouse clicks.
   :focus fires for all focus methods including mouse. By styling :focus-
   visible instead of :focus, you can show visible focus rings for keyboard
   users without the visual distraction on mouse click. It's the modern best
   practice for focus styling. Never use outline:none on :focus without
   providing a :focus-visible alternative.

Q4: What is a skip link and why is it required?
A: A skip link is typically the first element in <body>, visually hidden but
   visible on focus, which allows keyboard users to jump directly to the main
   content — bypassing repeated navigation. WCAG 2.4.1 (Level A) requires a
   mechanism to bypass repeated content. Without it, keyboard users must
   Tab through every nav link on every page. The target element should have
   tabindex="-1" so the browser moves focus (not just scroll position) there.

Q5: How do you implement a focus trap for a modal dialog?
A: Find all focusable elements inside the modal. Listen for keydown. When Tab
   is pressed on the last focusable element, loop focus back to the first.
   When Shift+Tab is pressed on the first, loop to the last. Also handle
   Escape to close the modal and return focus to the element that opened it.
   Modern alternative: Use the native <dialog> element with showModal() which
   handles focus trapping and Escape key natively.

Q6: What is the roving tabindex pattern?
A: For composite widgets (menus, tab lists, toolbars, radio groups), only one
   element at a time should be in the tab order (tabindex="0"). All others have
   tabindex="-1". Arrow keys move focus between items, updating which element
   has tabindex="0". This gives the entire widget a single tab stop, reducing
   the number of Tab presses users need and matching expected keyboard patterns.
   It's recommended in the ARIA APG (Authoring Practices Guide).

Q7: What keyboard events should a custom button handle?
A: A custom button (e.g., div with role="button") must handle: Enter key for
   activation (keydown event), Space key for activation (keydown event,
   also prevent default scrolling with e.preventDefault()). Click must also
   work for mouse users. The element needs tabindex="0" for focusability.
   Best practice: just use a native <button> element which handles Enter,
   Space, and click automatically.

Q8: How do you manage focus after a navigation event in a SPA?
A: After a route change, move focus programmatically to a logical location so
   screen readers announce the new page content. Options: find the <h1> of
   the new page, add tabindex="-1", and call focus() on it; or focus the
   <main> element; or use a visually-hidden "page updated" announcement live
   region. Without focus management, screen readers don't know the page
   content has changed and users are left confused about where they are.

Q9: What is the difference between disabled and aria-disabled?
A: The HTML disabled attribute removes the element from the tab order and
   prevents interaction. aria-disabled="true" only communicates the disabled
   state to assistive technologies without removing keyboard focus. Use
   disabled when the element should truly be unreachable. Use aria-disabled
   when you want keyboard users to still discover the disabled element (e.g.,
   a button that's disabled due to permissions but users should know it
   exists). With aria-disabled, your JS must also prevent activation.

Q10: What is the minimum recommended size for keyboard/pointer targets?
A: WCAG 2.5.8 (AA, added in 2.2) requires a minimum target size of 24x24 CSS
   pixels (or adequate spacing to reach 24px effective target). WCAG 2.5.5
   (AAA) recommends 44x44 CSS pixels. Apple's HIG and Google's Material Design
   both recommend 44x44 dp minimum. Small targets cause problems for users with
   motor impairments, older users, and touch screen users. This applies to
   all interactive elements including icon buttons without visible labels.
