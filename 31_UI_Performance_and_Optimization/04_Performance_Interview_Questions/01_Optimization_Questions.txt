GENERAL OPTIMIZATION INTERVIEW QUESTIONS
================================================================

Covers: bundle size, loading strategies, network, rendering,
        architecture, infrastructure, and trade-off analysis.

================================================================
LOADING PERFORMANCE
================================================================

Q1: What is the Critical Rendering Path and how do you optimize it?
────────────────────────────────────────────────────────────────────
A: The Critical Rendering Path (CRP) is the sequence of steps the browser
   takes to convert HTML, CSS, and JS into pixels on screen:
   
   1. Parse HTML → construct DOM
   2. Parse CSS → construct CSSOM
   3. Combine DOM + CSSOM → Render Tree
   4. Layout (Reflow): Calculate geometry of each element
   5. Paint: Fill pixels
   6. Composite: Combine layers, display
   
   RENDER BLOCKING: CSS is render-blocking (can't render without CSSOM).
   JS is both render-blocking AND parser-blocking (HTML parser stops).
   
   OPTIMIZATIONS:
   - Inline critical CSS (above-the-fold styles): eliminates CSS blocking
   - Defer non-critical CSS: <link rel="stylesheet" media="print" onload="this.media='all'">
   - Add async/defer to scripts:
     async: download in parallel, execute when downloaded (parse-blocking!)
     defer: download in parallel, execute AFTER HTML parsed (preferred)
   - Minimize render-blocking CSS size: only ship what's needed
   - Use media queries: <link rel="stylesheet" media="(min-width: 768px)">
     Browser downloads but doesn't block for non-matching media

──────────────────────────────────────────────────────────────

Q2: What is the difference between async and defer script loading?
───────────────────────────────────────────────────────────────────
A: Both download scripts in parallel with HTML parsing (not blocking):
   
   <script async src="...">
   - Downloads in parallel with HTML parsing
   - Executes IMMEDIATELY when downloaded (pauses HTML parsing to execute!)
   - Order NOT guaranteed (first downloaded = first executed)
   - Use for: Independent scripts (analytics, ads) that don't depend on DOM
   
   <script defer src="...">
   - Downloads in parallel with HTML parsing
   - Executes AFTER HTML fully parsed, BEFORE DOMContentLoaded
   - Order GUARANTEED (executes in document order)
   - Use for: Most application scripts, scripts that need the DOM
   
   <script type="module">
   - Automatically deferred
   - Executed in strict mode
   - Has its own scope
   
   Rule of thumb: Use defer for your app scripts. Use async only for
   truly independent third-party scripts.

──────────────────────────────────────────────────────────────

Q3: How do you reduce the impact of third-party scripts on performance?
────────────────────────────────────────────────────────────────────────
A: Third-party scripts (chat widgets, ads, analytics) are a major source
   of performance issues because you can't control their size or execution.
   
   STRATEGIES:
   1. LAZY LOAD after interaction: Don't load until first user interaction
      document.addEventListener('click', loadChatWidget, { once: true });
   
   2. Use async/defer: Never load synchronously
   
   3. FACADE PATTERN: Show a lightweight placeholder, load real widget on click
      (e.g., YouTube lite-embed: shows thumbnail, loads player on click)
   
   4. PARTYTOWN: Move third-party scripts to Web Workers (zero main thread cost)
      No DOM access in workers, but for analytics/beacons it works well
   
   5. RESOURCE HINTS: Preconnect to third-party origins
      <link rel="preconnect" href="https://analytics.example.com">
      Eliminates DNS + TCP + TLS handshake time when script eventually loads
   
   6. NEXT.JS SCRIPT STRATEGY:
      strategy="afterInteractive" — loads after page is interactive
      strategy="lazyOnload" — loads during idle time
      strategy="worker" — uses Partytown to run in Web Worker

──────────────────────────────────────────────────────────────

Q4: What is prefetching and how does it differ from preloading?
────────────────────────────────────────────────────────────────
A: Both are resource hints that trigger early downloads, but priorities differ:
   
   PRELOAD (<link rel="preload" as="...">):
   - HIGH priority download for current page resources
   - Use for: LCP images, critical fonts, above-fold CSS
   - Browser MUST fetch this (not just a hint)
   - Browser warning if preloaded resource not used within 3s
   
   PREFETCH (<link rel="prefetch" href="...">):
   - LOW priority download for FUTURE navigation resources
   - Use for: Next page JS chunks, next page images
   - Browser fetches when idle (after current page loads)
   - Not guaranteed to be fetched on slow connections
   
   PRECONNECT (<link rel="preconnect" href="..."]):
   - Not a resource download — establishes TCP/TLS connection early
   - Use for: Third-party origins you'll fetch from
   - Eliminates ~150ms DNS + handshake for first request to that origin
   
   Example:
   <!-- LCP image: PRELOAD now (high priority, current page) -->
   <link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
   
   <!-- Next page: PREFETCH when idle (low priority, future navigation) -->
   <link rel="prefetch" href="/next-page/main.js">
   
   <!-- CDN we'll use: PRECONNECT now -->
   <link rel="preconnect" href="https://cdn.example.com">

================================================================
NETWORK OPTIMIZATION
================================================================

Q5: How does HTTP/2 improve performance over HTTP/1.1?
───────────────────────────────────────────────────────
A: HTTP/2 changes the fundamental transport mechanism:
   
   HTTP/1.1 limitations:
   - One request per TCP connection at a time (head-of-line blocking)
   - Browser opens 6 TCP connections per domain as workaround
   - Headers sent as plain text, uncompressed, every request
   - Domain sharding was needed to work around the 6-connection limit
   
   HTTP/2 improvements:
   - MULTIPLEXING: Multiple requests/responses on ONE TCP connection simultaneously
     → No need for domain sharding, no head-of-line blocking
   - HEADER COMPRESSION (HPACK): Reduces repeated header overhead
     Cookie headers (large!) only sent once, referenced later
   - SERVER PUSH: Server sends resources before client requests them
     (mostly deprecated/replaced by 103 Early Hints)
   - BINARY PROTOCOL: More efficient than HTTP/1.1's text protocol
   - STREAM PRIORITIZATION: Weight streams by importance
   
   HTTP/3 (QUIC): Same multiplexing as HTTP/2 but over UDP (not TCP)
   Eliminates TCP head-of-line blocking even further.

──────────────────────────────────────────────────────────────

Q6: What is connection pooling and how does it affect page load?
─────────────────────────────────────────────────────────────────
A: HTTP/1.1: Browser reuses TCP connections for multiple requests to the same
   host (keep-alive). Without keep-alive, every request pays DNS + TCP + TLS
   handshake cost (~300ms). With keep-alive, subsequent requests on the same
   connection have near-zero overhead.
   
   But still: only 1 request at a time per connection, 6 connections per domain.
   
   Optimization for HTTP/1.1 (largely obsolete with HTTP/2):
   - Domain sharding: distribute assets across cdn1.example.com, cdn2.example.com
     → More connections = more parallel downloads
     → BAD idea now: HTTP/2 benefits lost when sharding to multiple domains
   
   With HTTP/2: Single connection, all requests multiplexed.
   Recommendation: CONSOLIDATE resources to fewer domains for HTTP/2.
   Don't use domain sharding with HTTP/2.

──────────────────────────────────────────────────────────────

Q7: Explain how you'd reduce Time to First Byte (TTFB).
─────────────────────────────────────────────────────────
A: TTFB = DNS resolution + TCP connection + TLS handshake + server processing.
   
   TARGET: < 600ms for "good" TTFB.
   
   OPTIMIZATIONS:
   
   1. CDN: Move content geographically closer to users
      → Reduces DNS + TCP + TLS to nearest PoP
      → 100–200ms improvement globally
   
   2. SERVER CACHING: Cache rendered pages (Redis, in-memory, CDN)
      → Eliminates database queries and template rendering
      → TTFB goes from 500ms to < 50ms for cached pages
   
   3. DATABASE OPTIMIZATION:
      → Index frequently queried columns
      → Cache query results in Redis
      → Fix N+1 queries with DataLoader or eager loading
      → Read replicas for read-heavy workloads
   
   4. SERVER-SIDE EDGE COMPUTING:
      → Move processing to edge nodes near users
      → Vercel Edge Functions, Cloudflare Workers
      → Eliminates geographic latency
   
   5. STREAMING SSR:
      → Start sending HTML before entire page is rendered
      → React: renderToPipeableStream sends shell immediately
      → TTFB represents when first bytes arrive, streaming improves FCP
   
   6. CONNECTION SETUP: DNS prefetch + Preconnect for origins
      → <link rel="preconnect" href="https://api.example.com">

BUNDLE AND LOADING STRATEGY

Q8: What loading strategies would you apply to a large e-commerce site?
────────────────────────────────────────────────────────────────────────
A: I'd apply multiple strategies at different levels:
   
   ROUTE LEVEL: Split by route (automatic in Next.js)
   - Home page loads only home page JS
   - Product page loads product JS separately
   - Cart/Checkout lazy-loaded on route change
   
   COMPONENT LEVEL: Lazy load below-fold components
   - Reviews section (IntersectionObserver lazy load)
   - Recommendation carousel (lazy on scroll)
   - Size guide modal (lazy on click)
   
   VENDOR SPLITTING: Separate node_modules into vendor chunk
   - Changes less often → long-term caching
   - User pays download cost once, not on every deploy
   
   CRITICAL PATH: Inline critical CSS for above-fold content
   - Hero image with fetchpriority="high" and preload
   - Product title + Add to Cart button CSS inlined
   
   THIRD PARTIES: Defer to after interaction
   - Chat widget: load on first interaction
   - Analytics: async, after page load
   - Ads: load in requestIdleCallback
   
   ASSETS: WebP/AVIF images, AVIF for modern browsers with WebP fallback
   - <picture> with multiple <source> for format negotiation
   - srcset for responsive images

Q9: How do you measure and enforce performance budgets in a team?
──────────────────────────────────────────────────────────────────
A: 
   TOOLING:
   - size-limit or bundlesize in package.json for CI checks
   - Lighthouse CI (LHCI) with performance assertions on PRs
   - webpack performance hints (warning/error if chunks exceed limit)
   
   PROCESS:
   1. Set budgets based on current baseline + realistic goals
      e.g., total JS ≤ 200KB gzip, LCP ≤ 2.5s
   2. Add CI check that fails the PR if budget exceeded
   3. Bundle analysis diff shown in PR comments
   4. Team review required to merge if over budget (approved exception)
   5. Monthly review of budgets as app grows
   
   METRICS TO BUDGET:
   - Total JavaScript (gzipped)
   - Largest initial bundle chunk
   - LCP, CLS, TBT in Lighthouse
   - Third-party JS size
   
   CULTURE: Make performance visible — post Lighthouse scores on
   deploys to Slack/team channel. "If it's not measured, it won't improve."

Q10: What is resource prioritization in browsers and how do you control it?
─────────────────────────────────────────────────────────────────────────────
A: Browsers assign priorities to resources based on type and position:
   
   HTML: Highest
   CSS (render-blocking): Highest
   JS (render-blocking): High
   Fonts: High
   Images in viewport: Medium
   Images off-screen: Lowest
   
   OVERRIDE WITH fetchpriority:
   - fetchpriority="high": boost above default (LCP images)
   - fetchpriority="low": downgrade (non-critical images)
   - fetchpriority="auto": default behavior
   
   <img src="hero.webp" fetchpriority="high"> <!-- LCP image → High -->
   <img src="thumbnail.webp" fetchpriority="low"> <!-- Non-critical → Low -->
   <link rel="preload" as="font" fetchpriority="low"> <!-- Non-critical font -->
   <script fetchpriority="high" src="critical.js"> <!-- Boost script priority -->
   
   PRIORITY HINTS also work on fetch() API:
   fetch('/api/critical', { priority: 'high' });
   fetch('/api/analytics', { priority: 'low' });

RENDERING AND ARCHITECTURE
================================================================

Q11: Compare SSR, SSG, ISR, and CSR from a performance perspective.
─────────────────────────────────────────────────────────────────────
A: 
   CSR (Client-Side Rendering):
   - HTML is empty shell, JS renders content
   - Worst FCP/LCP: user waits for JS download, parse, execute
   - Best: After initial load, navigation is instant (SPA)
   - Use for: Dashboards, authenticated apps, frequent interactions
   
   SSR (Server-Side Rendering):
   - Server renders full HTML per request
   - Best FCP/LCP: Content in first HTML response
   - Worst: Every request hits server (TTFB depends on server)
   - Use for: Dynamic pages with user-specific content
   
   SSG (Static Site Generation):
   - HTML pre-built at build time
   - Best TTFB: Served directly from CDN
   - Best FCP/LCP: Content in first byte from edge
   - Limitation: Can't personalize, rebuilds needed for content updates
   - Use for: Marketing sites, blogs, documentation
   
   ISR (Incremental Static Regeneration — Next.js):
   - SSG with on-demand or time-based revalidation
   - Combines SSG speed with dynamic content
   - Pages served from CDN cache, regenerated in background
   - Use for: E-commerce product pages, news articles

Q12: What is code splitting and what's the right granularity?
──────────────────────────────────────────────────────────────
A: Code splitting divides your bundle into smaller chunks loaded on demand.
   
   LEVELS OF SPLITTING:
   - Route level: One chunk per route (always do this)
   - Component level: Lazy load heavy components (> 30KB) not visible initially
   - Vendor splitting: Separate stable third-party code for long caching
   
   GRANULARITY RULE OF THUMB:
   - Don't split too fine: < 10KB chunks add network overhead
     (each chunk is a separate HTTP request, TLS overhead, etc.)
   - Don't split too coarse: > 200KB initial bundle is too much
   - Sweet spot: 50-200KB chunks after compression
   
   WHAT TO LAZY LOAD:
   - Routes users haven't visited yet
   - Modals and dialogs (only when opened)
   - Below-fold sections (charts, tables, carousels)
   - Heavy editors (Monaco, Quill, CodeMirror)
   - Admin/settings panels
   
   WHAT NOT TO LAZY LOAD:
   - LCP image (should be eager!)
   - Above-fold critical content
   - Anything visible in first viewport

TOOLS AND DEBUGGING
================================================================

Q13: You notice a performance regression in production. How do you debug?
──────────────────────────────────────────────────────────────────────────
A: SYSTEMATIC APPROACH:
   
   1. QUANTIFY: Check RUM dashboards — which metric regressed? LCP/INP/CLS?
      On which pages? Which devices/connections? Since when?
   
   2. REPRODUCE: Use WebPageTest or Lighthouse CI with the affected device
      profile (slow 3G + mid-tier mobile = Moto G4 or similar)
   
   3. ISOLATE: Binary search on git history (git bisect) to find regressing commit.
      Or: Compare bundle-analyzer output before/after.
   
   4. DIAGNOSE: Chrome DevTools Performance tab — record, find bottleneck
      - New large package? (bundle-analyzer diff)
      - New render-blocking resource? (Network waterfall)
      - Layout shift introduced? (Performance > Experience lane)
      - New slow interaction? (Performance > INP marker)
   
   5. FIX + VERIFY: Apply fix, run Lighthouse CI, compare RUM 24h after deploy.
   
   TOOLSET:
   - RUM: Sentry Performance, Datadog, Vercel Speed Insights
   - CI: Lighthouse CI diff on PR
   - Bundle: webpack-bundle-analyzer, source-map-explorer
   - DevTools: Performance, Network, Coverage panels

Q14: How do you use Chrome DevTools Coverage panel?
─────────────────────────────────────────────────────
A: Coverage panel shows how much CSS and JS is actually used on a page.
   
   HOW TO ACCESS:
   DevTools > More Tools > Coverage (Cmd+Shift+P → "Show Coverage")
   
   HOW TO USE:
   1. Click the record button
   2. Navigate through your app (trigger features you want to measure)
   3. Stop recording
   4. Coverage shows % of JS/CSS used vs. total (red = unused)
   
   WHAT TO DO WITH RESULTS:
   - High unused CSS (> 60%): Consider Critical CSS extraction (critters)
     or CSS modules (only load CSS for rendered components)
   - High unused JS (> 40% on initial load): Code splitting opportunity
     Check WHICH functions are unused: third-party library loaded in full
     but only fraction used → tree shaking or lighter alternative
   
   IMPORTANT: Coverage is per-page-interaction. Run the user's
   most common flow, not "click everything" — focus on what 80% of
   users do in a session.

Q15: What is "paint flashing" and when would you enable it?
────────────────────────────────────────────────────────────
A: Paint flashing is a Chrome DevTools rendering diagnostic that highlights
   (in green) areas of the page that are being repainted.
   
   HOW TO ENABLE:
   DevTools > Rendering tab (three dots > More Tools > Rendering)
   Check "Paint flashing"
   
   WHAT TO LOOK FOR:
   - Small, localized green flashes = efficient (only changed area repaints)
   - Entire page flashing green on scroll = expensive full-page repaints
   - Expected: Only elements that actually changed should repaint
   
   CAUSES OF EXCESSIVE REPAINTING:
   - CSS changes that affect layout (trigger reflow → repaint)
   - Changing element opacity, background-color (repaint only, not reflow)
   - JavaScript animations using left/top instead of transform
   
   FIX:
   - Use CSS transform + opacity for animations (no repaint in compositor)
   - Use will-change: transform to promote element to its own layer
   - Avoid modifying styles on scroll events without requestAnimationFrame
