================================================================
IMAGE OPTIMIZATION
================================================================

WHY IMAGES MATTER FOR PERFORMANCE:
──────────────────────────────────────
Images are typically the LARGEST assets on a webpage.
  - Average webpage: 50-60% of total bytes are images
  - LCP element is an image 70% of the time
  - Unoptimized images → slow LCP → bad Core Web Vital score
  - Heavy images → long page load → high bounce rate

KEY DECISIONS FOR EACH IMAGE:
  1. Right FORMAT (WebP/AVIF vs JPEG/PNG)
  2. Right SIZE (responsive, not desktop-only)
  3. Right LOADING strategy (lazy vs eager, priority)
  4. Right DELIVERY (CDN, image CDN)
  5. Right QUALITY (visual quality vs file size balance)

================================================================
IMAGE FORMATS COMPARISON
================================================================

FORMAT    | USE CASE                     | COMPRESSION | TRANSPARENCY | ANIMATION
──────────┼──────────────────────────────┼─────────────┼──────────────┼──────────
JPEG      | Photos, complex images       | Lossy       | ❌           | ❌
PNG       | Logos, icons, transparency   | Lossless    | ✅           | ❌
WebP      | Everything (modern fallback) | Both        | ✅           | ✅
AVIF      | Best compression available   | Both        | ✅           | ✅
GIF       | Simple animations (legacy)   | LZW         | 1-bit        | ✅
SVG       | Icons, illustrations         | XML text    | ✅           | ✅

SIZE COMPARISON (same image, similar quality):
  JPEG:  100KB (baseline)
  WebP:  ~70KB  (30% smaller than JPEG)
  AVIF:  ~50KB  (50% smaller than JPEG, 20-30% smaller than WebP)

AVIF SUPPORT: Chrome 85+, Firefox 93+, Safari 16+ (~94% of users as of 2024)
WebP SUPPORT: All modern browsers (~97% of users)
JPEG/PNG:     Universal fallback

RESPONSIVE IMAGES WITH srcset AND sizes
================================================================

PROBLEM: Serving a 1500px image to a mobile device that displays 375px
is wasteful — the browser downloads 16x more data than needed.

SOLUTION — srcset attribute:

  <!-- srcset: provide multiple resolutions -->
  <!-- sizes: tell browser how wide the image WILL BE displayed -->
  
  <img
    src="hero-800.jpg"               <!-- Fallback for old browsers -->
    srcset="
      hero-400.jpg 400w,
      hero-800.jpg 800w,
      hero-1200.jpg 1200w,
      hero-2400.jpg 2400w
    "
    sizes="
      (max-width: 600px) 100vw,      <!-- Mobile: full viewport width -->
      (max-width: 1200px) 80vw,      <!-- Tablet: 80% viewport -->
      1200px                          <!-- Desktop: capped at 1200px -->
    "
    alt="Hero image"
    loading="eager"
    fetchpriority="high"             <!-- LCP image: high priority! -->
  />

  HOW THE BROWSER CHOOSES:
    Browser has: devicePixelRatio=2, viewport=375px
    Effective display size: 375 * 2 = 750px
    Browser picks: hero-800.jpg (closest size ≥ 750)
    → Desktop gets the large image, mobile gets the right-sized image

THE <picture> ELEMENT — format negotiation:

  <picture>
    <!-- AVIF first (best compression, limited support) -->
    <source
      type="image/avif"
      srcset="hero-400.avif 400w, hero-800.avif 800w, hero-1200.avif 1200w"
      sizes="(max-width: 600px) 100vw, 800px"
    />
    
    <!-- WebP fallback -->
    <source
      type="image/webp"
      srcset="hero-400.webp 400w, hero-800.webp 800w, hero-1200.webp 1200w"
      sizes="(max-width: 600px) 100vw, 800px"
    />
    
    <!-- JPEG ultimate fallback -->
    <img
      src="hero-800.jpg"
      alt="Hero image"
      width="800" height="600"     <!-- Always set width/height to prevent CLS! -->
    />
  </picture>

LAZY LOADING
================================================================

NATIVE LAZY LOADING (no JavaScript required!):

  <!-- ✅ Lazy load below-fold images (browser default: eager) -->
  <img src="below-fold.jpg" loading="lazy" alt="..." />
  
  <!-- ✅ Eagerly load above-fold/LCP images -->
  <img src="hero.jpg" loading="eager" fetchpriority="high" alt="..." />
  
  <!-- NEVER lazy load images that are immediately visible! -->
  <!-- ❌ BAD: Lazy loading the LCP image delays it significantly -->
  <img src="hero.jpg" loading="lazy" alt="..." />

  BROWSER HEURISTICS:
  - Browser loads lazy images when they're within ~1500px of viewport
  - Not consistent across browsers (Chrome is more aggressive about pre-loading)
  - For iframes: <iframe loading="lazy" src="..."> also works!

INTERSECTION OBSERVER APPROACH (custom lazy loading):

  // For more control than native loading="lazy"
  function LazyImage({ src, alt, ...props }) {
    const [isVisible, setIsVisible] = useState(false);
    const imgRef = useRef(null);
    
    useEffect(() => {
      const observer = new IntersectionObserver(
        ([entry]) => {
          if (entry.isIntersecting) {
            setIsVisible(true);
            observer.disconnect();
          }
        },
        { rootMargin: '200px' } // Start loading 200px before visible
      );
      
      if (imgRef.current) observer.observe(imgRef.current);
      return () => observer.disconnect();
    }, []);
    
    return (
      <img
        ref={imgRef}
        src={isVisible ? src : undefined}
        data-src={src}              // Placeholder until visible
        alt={alt}
        {...props}
      />
    );
  }

NEXT.JS IMAGE COMPONENT
================================================================

next/image handles ALL optimization automatically:
  - Resizes images on the server to the right dimensions
  - Converts to WebP/AVIF automatically
  - Implements lazy loading (loading="lazy" by default)
  - Prevents CLS (requires width + height or fill)
  - Serves via CDN with immutable caching headers
  - Generates blur placeholder automatically

  import Image from 'next/image';
  
  // ─── Above-fold/LCP image (eager + high priority): ───
  <Image
    src="/hero.jpg"
    alt="Hero"
    width={1200}
    height={600}
    priority              // = fetchpriority="high" + loading="eager"
    quality={85}          // Default: 75. Range: 1-100
    placeholder="blur"    // Optional: shows blurry placeholder
  />
  
  // ─── Below-fold image (lazy loaded by default): ───
  <Image
    src="/product.jpg"
    alt="Product"
    width={400}
    height={400}
    // loading="lazy" is the default — no need to specify
  />
  
  // ─── Fill mode (when dimensions unknown — e.g., full-bleed): ───
  <div style={{ position: 'relative', height: '100vh' }}>
    <Image
      src="/background.jpg"
      alt="Background"
      fill
      style={{ objectFit: 'cover' }}
      sizes="100vw"       // Tell Next.js how wide image will be
    />
  </div>
  
  // ─── Remote images (need allowlist in next.config.js): ───
  // next.config.js:
  // images: {
  //   remotePatterns: [
  //     { protocol: 'https', hostname: 'images.example.com' }
  //   ]
  // }
  
  // ─── Custom loader (e.g., Cloudinary): ───
  const cloudinaryLoader = ({ src, width, quality }) => {
    return `https://res.cloudinary.com/demo/image/upload/w_${width},q_${quality || 75}/${src}`;
  };
  
  <Image
    loader={cloudinaryLoader}
    src="my-image.jpg"
    width={800}
    height={600}
    alt="..."
  />

ASPECT RATIO AND CLS PREVENTION
================================================================

ALWAYS set width and height on images to prevent CLS:

  ❌ BAD (causes layout shift when image loads):
  <img src="image.jpg" alt="..." />
  
  ✅ GOOD (browser reserves space before image loads):
  <img src="image.jpg" width="800" height="600" alt="..." />
  
  ✅ ALSO GOOD (modern CSS approach):
  <img
    src="image.jpg"
    width="800"
    height="600"
    style={{ width: '100%', height: 'auto' }} /* Responsive scaling */
    alt="..."
  />
  
  CSS aspect-ratio property:
  .image-container {
    aspect-ratio: 16 / 9;   /* Reserves correct space even without dimensions */
    overflow: hidden;
  }
  
  INTRINSIC SIZE TRICK: Even if you override width/height in CSS,
  setting them in HTML tells the browser the ASPECT RATIO, so it can
  pre-reserve the right amount of space.

BLUR PLACEHOLDER PATTERN
================================================================

Show a blurry low-quality version while the full image loads:

  // 1. Generate blur hash or base64 placeholder at build time
  // 2. Display placeholder immediately (no network request needed)
  // 3. Fade in full image when loaded
  
  function ProgressiveImage({ src, placeholderSrc, alt, ...props }) {
    const [loaded, setLoaded] = useState(false);
    
    return (
      <div style={{ position: 'relative', overflow: 'hidden' }}>
        {/* Placeholder: always visible, blurred */}
        <img
          src={placeholderSrc}  // Tiny (20px) base64 encoded version
          alt=""
          aria-hidden="true"
          style={{
            position: 'absolute',
            inset: 0,
            width: '100%',
            height: '100%',
            objectFit: 'cover',
            filter: 'blur(20px)',
            transform: 'scale(1.1)', // Prevent blur edge artifacts
            transition: 'opacity 0.3s',
            opacity: loaded ? 0 : 1,
          }}
        />
        
        {/* Full image */}
        <img
          src={src}
          alt={alt}
          onLoad={() => setLoaded(true)}
          style={{
            width: '100%',
            height: 'auto',
            opacity: loaded ? 1 : 0,
            transition: 'opacity 0.3s',
          }}
          {...props}
        />
      </div>
    );
  }
  
  // Next.js does this built-in with placeholder="blur"!

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is the difference between srcset and sizes attributes?
A: srcset lists the available image URLs and their intrinsic widths
   (e.g., "img-400.jpg 400w, img-800.jpg 800w"). The browser uses this as
   a MENU of options. sizes tells the browser HOW WIDE the image will actually
   be displayed at different viewport widths — a HINT for selection
   (e.g., "(max-width: 600px) 100vw, 800px"). Without sizes, the browser
   assumes the image is 100vw. With both attributes, the browser multiplies
   the display width by devicePixelRatio and picks the closest srcset entry.
   This is critical for high-DPI (Retina) screens — a 400px display slot on
   a 2x screen needs an 800px image.

Q: How does Next.js Image component prevent CLS?
A: Next.js Image requires either explicit width+height props OR the fill prop
   with a positioned parent. With width+height, it sets both HTML attributes
   AND the aspect-ratio CSS property, causing the browser to reserve exactly
   the right space before the image loads — preventing layout shift. With fill,
   it positions the image absolutely inside its container, so the container
   (whose height you control) defines the space. It also generates a blurry
   inline placeholder (with placeholder="blur") that occupies the space
   immediately, providing both CLS prevention and perceived performance.

Q: When should you use loading="eager" vs loading="lazy"?
A: Use loading="eager" (or omit loading — it's the default) for images that
   are visible in the initial viewport: hero images, above-fold content, the
   likely LCP element. Combine with fetchpriority="high" for the LCP image.
   Use loading="lazy" for everything else — product images in a grid, blog
   thumbnails, footer images, anything below the fold. A common mistake is
   lazy loading ALL images with a blanket CSS class or plugin, which then
   lazy-loads the LCP image and significantly hurts LCP score. Audit lazy
   loading with DevTools: check if your LCP image has loading="lazy" set
   (visible in the Performance panel as a "discovered late" resource).

Q: Why is AVIF not just universally used instead of WebP?
A: AVIF offers better compression (~50% smaller than JPEG, 20-30% vs WebP)
   but has trade-offs: (1) Encoding is significantly SLOWER — generating AVIF
   thumbnails at scale requires more compute; (2) Browser support, while now
   ~94%, still has gaps; (3) Decoding can be slower on lower-end devices, which
   could hurt LCP on mobile. Best practice: serve AVIF to browsers that support
   it (via Accept header negotiation or <picture> with type="image/avif"),
   WebP as a fallback, and JPEG as the final fallback. Image CDNs like
   Cloudinary (f_auto) or Vercel handle this negotiation automatically.
