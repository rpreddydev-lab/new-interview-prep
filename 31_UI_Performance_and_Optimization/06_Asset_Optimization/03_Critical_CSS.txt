================================================================
CRITICAL CSS
================================================================

THE PROBLEM: RENDER-BLOCKING CSS
──────────────────────────────────────
The browser CANNOT render ANY content until ALL CSS is downloaded,
parsed, and processed (CSS is render-blocking by design).

RENDERING PIPELINE:
  HTML → DOM Tree
  CSS  → CSSOM Tree     ← BLOCKED until ALL CSS downloaded
  DOM + CSSOM → Render Tree → Layout → Paint

  If your styles.css is 80KB and takes 300ms to load,
  the page shows NOTHING for 300ms — blank white screen.
  This directly hurts FCP (First Contentful Paint).

THE SOLUTION: Split CSS into:
  1. CRITICAL CSS: Styles needed to render above-the-fold content
     → Inline directly in <head> (zero network round trip!)
  2. NON-CRITICAL CSS: Everything else
     → Defer loading (doesn't block rendering)

================================================================
WHAT IS "CRITICAL" CSS?
================================================================

Critical CSS includes styles needed to render:
  - Visible text, headings, body fonts
  - Above-the-fold images and backgrounds
  - Navigation/header layout
  - Any content visible WITHOUT scrolling

NON-CRITICAL CSS includes:
  - Below-fold styles (anything requiring scroll)
  - Hover states (can't be "above fold" visually)
  - Modal/dialog styles (not initially visible)
  - Print styles
  - Specific page sections not in initial view

TYPICAL SIZES:
  Critical CSS: 5-20KB (inline in <style> tag)
  Full CSS: 50-500KB (loaded normally or deferred)

================================================================
INLINING CRITICAL CSS
================================================================

  <!-- CRITICAL CSS: Inlined, renders above-fold immediately -->
  <head>
    <meta charset="UTF-8">
    <style>
      /* Critical: only above-fold styles */
      *, *::before, *::after { box-sizing: border-box; }
      body { margin: 0; font-family: system-ui, sans-serif; }
      .header { display: flex; align-items: center; height: 60px; background: #fff; }
      .hero { min-height: 70vh; display: flex; flex-direction: column; }
      .hero h1 { font-size: clamp(2rem, 5vw, 4rem); }
      .hero p { font-size: 1.2rem; color: #555; }
      /* ... only what's visible above fold ... */
    </style>
    
    <!-- NON-CRITICAL CSS: Deferred (doesn't block rendering) -->
    <link rel="stylesheet" href="/full-styles.css"
          media="print" onload="this.media='all'" />
    <!-- ↑ Trick: media="print" → browser loads at low priority (non-blocking)
         onload swaps to media="all" → applies normally after load -->
    
    <!-- Fallback for no-JS: -->
    <noscript>
      <link rel="stylesheet" href="/full-styles.css" />
    </noscript>
  </head>

THE media="print" TRICK EXPLAINED:
  1. Browser sees media="print" → "this is for print only"
  2. Downloads it at LOW priority (non-blocking for screen rendering)
  3. onload fires when downloaded → media changes to "all"
  4. CSS now applies to screen — no layout shift because page is
     already rendered with inline critical CSS

EXTRACTION TOOLS
================================================================

MANUAL APPROACH (for small projects):
  - Use DevTools Coverage panel (Ctrl+Shift+P → Show Coverage)
  - Filter to CSS files
  - Red sections = unused CSS on current page
  - Manual: copy only green (used) rules for above-fold content

CRITICAL NPM PACKAGE (most popular):
  npm install --save-dev critical
  
  // critical.js build script
  const critical = require('critical');
  
  critical.generate({
    base: 'dist/',
    src: 'index.html',
    target: 'index.html',     // Overwrite with inlined critical CSS
    width: 1300,
    height: 900,              // Viewport for "above fold" definition
    inline: true,             // Inline CSS into <head>
    extract: true,            // Remove inlined rules from stylesheet
    // Multiple dimensions (responsive critical CSS):
    dimensions: [
      { width: 375, height: 667 },   // Mobile
      { width: 768, height: 1024 },  // Tablet
      { width: 1300, height: 900 },  // Desktop
    ],
  });

CRITTERS (webpack/Next.js):
  // webpack.config.js
  const Critters = require('critters-webpack-plugin');
  
  module.exports = {
    plugins: [
      new Critters({
        // Inline critical CSS, lazy-load the rest
        preload: 'swap',        // font-display: swap for deferred CSS
        pruneSource: true,      // Remove inlined rules from stylesheet
      })
    ]
  };
  
  // Next.js: Critters is BUILT IN since Next.js 10!
  // next.config.js:
  module.exports = {
    experimental: {
      optimizeCss: true,  // Enable Critters in Next.js
    }
  };

VITE PLUGIN:
  // vite.config.js
  import { defineConfig } from 'vite';
  import critters from 'vite-plugin-critters';
  
  export default defineConfig({
    plugins: [critters()],
  });

================================================================
CSS MODULES — AUTOMATIC CRITICAL CSS IN REACT
================================================================

With CSS Modules or CSS-in-JS, components only load their styles when
the component is rendered — naturally "critical" CSS!

  // CSS Modules: Next.js, Create React App, Vite
  import styles from './Button.module.css';
  
  function Button({ children }) {
    return <button className={styles.button}>{children}</button>;
  }
  
  // Button.module.css is bundled with the component chunk
  // Only loads when Button is rendered (or in the JS bundle)
  
  // RESULT: Code splitting at the component level = CSS split too!
  //   Initial bundle: only styles for components in initial render
  //   Lazy-loaded component chunks: include their own styles

CSS-IN-JS CRITICAL CSS (Styled Components, Emotion):
  // Server-side rendering collects all styles used during render
  // and inlines them in the <head> — automatic critical CSS!
  
  // styled-components SSR (Next.js):
  // pages/_document.js
  import Document, { Head, Html, Main, NextScript } from 'next/document';
  import { ServerStyleSheet } from 'styled-components';
  
  export default class MyDocument extends Document {
    static async getInitialProps(ctx) {
      const sheet = new ServerStyleSheet();
      const originalRenderPage = ctx.renderPage;
      
      ctx.renderPage = () =>
        originalRenderPage({
          enhanceApp: (App) => (props) =>
            sheet.collectStyles(<App {...props} />),
        });
      
      const initialProps = await Document.getInitialProps(ctx);
      return {
        ...initialProps,
        styles: [
          ...React.Children.toArray(initialProps.styles),
          sheet.getStyleElement(),  // ← Inlines all used styles!
        ]
      };
    }
  }
  
  // NOTE: Vanilla Extract, Linaria, Panda CSS are "zero-runtime CSS-in-JS"
  // They extract to CSS at build time (no runtime cost, no hydration issues)
  // and work naturally with critical CSS extraction.

================================================================
PURGECSS — REMOVING UNUSED CSS
================================================================

For CSS frameworks (Tailwind, Bootstrap), most utility classes are unused.
PurgeCSS scans HTML/JS and removes unused CSS classes.

  // postcss.config.js
  module.exports = {
    plugins: {
      tailwindcss: {},
      autoprefixer: {},
      // PurgeCSS (Tailwind has this built-in in production!)
      ...(process.env.NODE_ENV === 'production' ? {
        '@fullhuman/postcss-purgecss': {
          content: [
            './src/**/*.{js,jsx,ts,tsx}',  // Scan all component files
            './public/index.html',
          ],
          defaultExtractor: content =>
            content.match(/[\w-/:]+(?<!:)/g) || [],
          // Safelist patterns that are dynamically added:
          safelist: {
            patterns: [/^text-/, /^bg-/],  // Keep all text-* and bg-* classes
          }
        }
      } : {})
    }
  };
  
  // Tailwind CSS v3: JIT (Just-In-Time) mode does this automatically!
  // Only generates CSS for classes actually found in your templates.
  // Before: Tailwind = 3MB of CSS. After Tailwind JIT: ~10-50KB!
  
  // tailwind.config.js (tell Tailwind where to scan):
  module.exports = {
    content: ['./src/**/*.{js,jsx,ts,tsx}'],
    // No purge config needed — JIT handles it automatically
  };

================================================================
CONTENT-VISIBILITY — CSS SKIP RENDERING
================================================================

CSS content-visibility: auto is like "virtual scrolling for the DOM":
The browser SKIPS rendering off-screen content entirely!

  /* Heavy page with many sections */
  .section {
    content-visibility: auto;
    
    /* Required: hint the browser about expected size to avoid layout shift */
    contain-intrinsic-size: 0 500px; /* width 0 (auto), height ~500px */
  }
  
  /* Results in Chrome tests: up to 7x faster initial rendering!
     - Browser renders sections lazily as they scroll into view
     - Off-screen sections: skipped in Layout + Paint steps
     - Re-rendered on scroll (fast, GPU-assisted) */
  
  /* WARNING: Don't use on sections with animations, sticky elements,
     or elements that need to respond to scroll events when off-screen */

================================================================
RENDER-BLOCKING VS PARSER-BLOCKING CSS/JS
================================================================

CSS: ALWAYS render-blocking (no workaround except media queries)
  <link rel="stylesheet" href="all.css" />  ← Blocks rendering
  <link rel="stylesheet" href="print.css" media="print" />  ← Non-blocking!
  <link rel="stylesheet" href="mobile.css" media="(max-width: 768px)" />
    ← Non-blocking on desktop! But blocks on mobile.

JS: Parser-blocking by default (inline scripts block HTML parsing)
  <script src="app.js"></script>          ← Parser-blocking
  <script src="app.js" defer></script>    ← Non-blocking, runs after HTML
  <script src="app.js" async></script>    ← Non-blocking, runs when ready
  
  // RULE: Always use defer for scripts that don't need to run
  // before HTML is parsed. Use async only for fully independent scripts
  // (analytics) that don't depend on other scripts or DOM being ready.

================================================================
PERFORMANCE IMPACT: BEFORE vs AFTER CRITICAL CSS
================================================================

BEFORE (typical setup):
  HTML loads → CSS download starts (300ms) → CSS parsed → JS runs → Paint
  FCP: 800ms  LCP: 1500ms

AFTER (critical CSS + deferred full CSS):
  HTML loads → Critical CSS already inline → IMMEDIATE paint of above-fold
  Full CSS loads in background (300ms) → Applies silently
  FCP: 200ms  LCP: 800ms
  
  Improvement: FCP 4x faster, LCP 2x faster

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is critical CSS and why does it improve FCP?
A: Critical CSS is the minimum CSS required to render the above-the-fold
   content (what's visible without scrolling). Normally, browsers can't render
   ANY content until all CSS is downloaded and processed (CSS is render-blocking).
   By inlining critical CSS directly in the <head> as a <style> tag, there's
   zero network round trip — the browser has everything it needs to paint the
   first screen immediately after parsing the HTML. The full stylesheet is then
   deferred and loads non-blocking (via the media="print" + onload trick or
   rel="preload"). FCP improvements of 300-800ms are common, directly improving
   both LCP and user perception.

Q: How does the media="print" trick work for loading CSS asynchronously?
A: Setting media="print" on a <link rel="stylesheet"> tells the browser the
   stylesheet is only for printing — so it downloads it at low priority and,
   importantly, doesn't block rendering. The onload attribute then fires when
   the download completes and changes media to "all", making the styles apply
   to the screen. The CSS applies silently (no visible switch) because the page
   was already rendered with inline critical CSS. This is a neat trick because
   rel="preload" for stylesheets would download the CSS but NOT apply it. The
   media switch is the standard technique for loading non-critical CSS without
   blocking rendering. A <noscript> fallback should always accompany it.

Q: How does Tailwind CSS JIT mode relate to critical CSS?
A: Tailwind JIT (Just-In-Time) doesn't generate critical CSS in the traditional
   sense, but it solves the unused CSS problem at build time. Traditional Tailwind
   generated a 3MB+ CSS file with every possible utility class. JIT scans your
   template files and generates ONLY the classes actually used — typically 10-50KB.
   This solves the file size problem but not the render-blocking problem. For
   render-blocking, you still need critical CSS extraction (Critters) or CSS
   Modules. JIT's small output means critical CSS extraction becomes simpler
   since you're starting with a smaller file, and the "non-critical" portion
   after extraction is also small.

Q: What's the difference between content-visibility and lazy loading?
A: Lazy loading (loading="lazy" or Intersection Observer) defers LOADING
   resources (images, iframes) until they're near the viewport. content-visibility:
   auto defers RENDERING work (Layout, Paint, Compositing) for DOM elements that
   are off-screen — the DOM elements ARE in the document and loaded, but the
   browser skips the expensive rendering steps for them. This can dramatically
   reduce initial render time for long pages (7x improvement has been documented).
   The key requirement is providing contain-intrinsic-size as a size hint so the
   browser can correctly compute scrollbar size and scroll position without
   actually rendering all content. Both techniques can and should be combined.
