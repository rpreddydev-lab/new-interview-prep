================================================================
BUNDLE ANALYSIS - UNDERSTANDING AND REDUCING BUNDLE SIZE
================================================================

WHAT IS BUNDLE ANALYSIS?
─────────────────────────
Bundle analysis is the process of examining the contents of your compiled
JavaScript bundles to understand:
  - What dependencies are in the bundle
  - How large each dependency is
  - What code is duplicated across chunks
  - What opportunities exist for reduction

A bundle is what a bundler (webpack, Vite, Rollup, esbuild) produces by
taking your source files and all their imports and compiling them into
files that browsers can execute.

WHY ANALYZE YOUR BUNDLE?
  - JavaScript is the most expensive resource type per byte
  - Large bundles → longer download, parse, compile times
  - "You can't optimize what you can't measure"
  - Easy wins: single npm package might account for 40% of your bundle

================================================================
BUNDLE SIZE CONCEPTS
================================================================

THREE SIZES TO UNDERSTAND:
  1. STAT SIZE: The original file size before processing
  2. PARSED SIZE: After webpack parsing (JS with module scaffolding)
  3. GZIPPED SIZE: After gzip compression (what's actually sent over wire)

  ALWAYS optimize for GZIPPED size (that's what users download).
  Gzip typically reduces JS by 60-70%.
  
  Example:
  lodash stat size: 1.42MB
  lodash parsed: 1.38MB
  lodash gzipped: 70KB → users only download 70KB!
  
  But: users must still PARSE and COMPILE the full 1.38MB!
  Parse/compile happens on the uncompressed size.

WHAT MAKES BUNDLES LARGE:
  - Large third-party libraries (moment.js, lodash, chart.js)
  - Importing entire libraries when only a subset is needed
  - Duplicate code (same library in multiple chunks)
  - Development-only code in production bundle
  - Unused features (polyfills for supported browsers)
  - CSS-in-JS generating large CSS objects
  - Large JSON data files bundled with JS

================================================================
BUNDLE ANALYSIS TOOLS
================================================================

1. WEBPACK BUNDLE ANALYZER
────────────────────────────
# Install
npm install --save-dev webpack-bundle-analyzer

# webpack.config.js
const BundleAnalyzerPlugin = require('webpack-bundle-analyzer').BundleAnalyzerPlugin;

module.exports = {
  plugins: [
    new BundleAnalyzerPlugin({
      analyzerMode: 'static',    // 'server' | 'static' | 'json'
      reportFilename: 'bundle-report.html',
      openAnalyzer: true,
      generateStatsFile: true,
      statsFilename: 'stats.json',
    })
  ]
};

# Run: npm run build → opens interactive treemap in browser
# OR: ANALYZE=true npm run build (with env var check in config)

# Next.js
npm install --save-dev @next/bundle-analyzer

// next.config.js
const withBundleAnalyzer = require('@next/bundle-analyzer')({
  enabled: process.env.ANALYZE === 'true',
});
module.exports = withBundleAnalyzer({ /* next config */ });

# Run: ANALYZE=true npm run build

2. SOURCE MAP EXPLORER
───────────────────────
# Install
npm install --save-dev source-map-explorer

# Run (requires source maps to be generated)
npx source-map-explorer 'build/static/js/*.js'
npx source-map-explorer 'dist/**/*.js'

# Benefits over bundle-analyzer:
# - Shows exact bytes from source code (not webpack module overhead)
# - Works without webpack (works with any bundler)
# - CLI output + visual treemap

3. BUNDLEPHOBIA.COM (pre-bundle analysis)
──────────────────────────────────────────
- Check npm package size BEFORE installing
- Shows: minified size, gzipped size, download time estimates
- Shows: composition (what other packages it bundles)
- Shows: alternatives and their sizes
- Great for evaluating dependencies during code review

Example: Should we use moment.js or day.js?
  moment.js: 285KB minified, 72KB gzip
  day.js: 2.6KB minified, 1KB gzip  ← 72x smaller!

4. VITE BUNDLE VISUALIZER
──────────────────────────
# rollup-plugin-visualizer (works with Vite and Rollup)
npm install --save-dev rollup-plugin-visualizer

// vite.config.js
import { visualizer } from 'rollup-plugin-visualizer';

export default {
  plugins: [
    visualizer({
      filename: './dist/stats.html',
      open: true,
      gzipSize: true,
      brotliSize: true,
    })
  ]
};

5. SIZE-LIMIT
──────────────
# Install
npm install --save-dev size-limit @size-limit/file @size-limit/webpack

// package.json
{
  "size-limit": [
    { "path": "dist/index.js", "limit": "20 kB" },
    { "path": "dist/vendor.js", "limit": "150 kB" }

# Shows: size (gzip), loading time estimate, comparison to limit

───────────────
# CI-focused bundle size tracking

{
  "bundlewatch": {
    "files": [
      { "path": "dist/js/main.*.js", "maxSize": "200kB" },
      { "path": "dist/css/main.*.css", "maxSize": "50kB" }
    ]
  }
}
# Integrates with GitHub to show bundle size diff on PRs

================================================================
READING BUNDLE ANALYSIS RESULTS
================================================================

WHAT TO LOOK FOR:
  1. OVERSIZED SINGLE DEPENDENCIES
     → A single npm package taking > 100KB gzipped = investigate
     → Often: moment.js, lodash, chart.js, monaco-editor, PDF.js
  
  2. DUPLICATE MODULES
     → Same module appearing in multiple chunks = wasted bytes
     → Often caused by: multiple versions of same package, missing
       shared chunks config, incorrect dependency ranges
  
  3. UNUSED IMPORTS
     → Library imported in full but only small part used
     → Example: import _ from 'lodash' when only _.debounce needed
  
  4. DEVELOPMENT CODE IN PRODUCTION
     → Test utilities, debug helpers, source maps in production
     → React DevTools bundle in production build
  
  5. LARGE INLINE DATA
     → JSON data embedded in JS (locales, mock data, SVG icons)
     → Better to serve as separate files or use dynamic import

INTERPRETING THE TREEMAP:
  - Larger box = more bytes
  - Color = chunk (main, vendor, specific features)
  - Hover = exact size
  - Click = zoom into module structure

================================================================
COMMON BUNDLE BLOAT CULPRITS AND SOLUTIONS
================================================================

1. MOMENT.JS (285KB → Use day.js or date-fns)
──────────────────────────────────────────────
  // ❌ moment.js — huge locales included
  import moment from 'moment';
  
  // ✅ day.js — 2.6KB, same API
  import dayjs from 'dayjs';
  
  // ✅ date-fns — tree-shakeable, only import what you need
  import { format, parseISO, differenceInDays } from 'date-fns';
  // Only the used functions are bundled

2. LODASH (71KB gzip → use specific imports or lodash-es)
──────────────────────────────────────────────────────────
  // ❌ Full lodash (entire library)
  import _ from 'lodash';
  _.debounce(fn, 300);
  
  // ✅ Direct import (only debounce bundled)
  import debounce from 'lodash/debounce';
  
  // ✅ lodash-es (ES modules, tree-shakeable)
  import { debounce, throttle } from 'lodash-es';
  
  // ✅ Even better: use native alternatives
  // debounce → implement yourself (5 lines) or use @xobotyi/scrollbar-width
  // isArray → Array.isArray (native)
  // isEmpty → item.length === 0 or Object.keys(item).length === 0

3. CHART.JS / RECHARTS (large → lazy load)
────────────────────────────────────────────
  // ❌ Always loaded
  import { LineChart } from 'recharts';
  
  // ✅ Lazy loaded (only when chart is visible)
  const LineChart = lazy(() =>
    import('recharts').then(m => ({ default: m.LineChart }))
  );

4. ICON LIBRARIES (loading entire set)
────────────────────────────────────────
  // ❌ Load ALL icons (1000+ icons, 1MB+)
  import { MdHome, MdSettings } from 'react-icons/md';
  // This imports from react-icons/md which is a large file
  
  // ✅ Deep imports (only the imported icons)
  import MdHome from 'react-icons/md/MdHome';
  import MdSettings from 'react-icons/md/MdSettings';
  
  // ✅ Tree-shakeable alternatives: @iconify/react, phosphor-react
  // ✅ Or use inline SVGs for your 10 most-used icons

5. CSS-IN-JS RUNTIME OVERHEAD
───────────────────────────────
  // ❌ styled-components / Emotion at runtime: adds ~12-25KB + runtime cost
  import styled from 'styled-components';
  const Button = styled.button`color: blue;`;
  
  // ✅ Linaria / Vanilla Extract: compile-time CSS extraction (zero runtime)
  import { styled } from '@linaria/react';
  const Button = styled.button`color: blue;`; // Extracted to CSS at build time
  
  // ✅ Or just use CSS Modules (zero runtime, native browser CSS)
  import styles from './Button.module.css';
  <button className={styles.button}>...</button>

6. POLYFILLS FOR SUPPORTED BROWSERS
─────────────────────────────────────
  // ❌ Polyfilling for IE11 in 2024 (IE11 is dead)
  // @babel/preset-env with targets: "> 0.25%, not dead"
  
  // ✅ Modern targets — ship much less polyfill code
  // .browserslistrc or package.json:
  // "browserslist": "> 0.5%, last 2 versions, not dead"
  // Removes IE11 support → removes many KB of polyfills

================================================================
BUNDLE ANALYSIS WORKFLOW
================================================================

STEP 1: MEASURE CURRENT STATE
  npm run build
  npx source-map-explorer 'build/**/*.js'
  # OR: ANALYZE=true npm run build (bundle-analyzer)

STEP 2: IDENTIFY TOP OFFENDERS
  - List top 10 largest modules by gzipped size
  - Check for duplicates
  - Look for unexpected inclusions

STEP 3: INVESTIGATE EACH OFFENDER
  # Find who is importing a module
  npx webpack-deps-tree --dependency "moment" 
  # Shows all files that import moment.js
  
  # Or use dependency-cruiser for import chain visualization

STEP 4: APPLY OPTIMIZATIONS
  - Replace large libs with smaller alternatives
  - Convert full imports to specific imports
  - Lazy-load rarely used code
  - Enable tree shaking (see Tree Shaking file)

STEP 5: MEASURE IMPROVEMENT
  - Re-run bundle analysis
  - Compare gzipped sizes
  - Run Lighthouse to see performance improvement

// GitHub Actions workflow
name: Bundle Size Check
on: [pull_request]

jobs:
  bundle-size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run build
      - name: Check bundle size
        run: npx size-limit
      - name: Upload bundle analysis
        uses: actions/upload-artifact@v4
        with:
          name: bundle-analysis
          path: dist/stats.html

// Optional: Use bundlewatch for PR comments showing size diff
// Or: Use relative-ci for automatic bundle size tracking

================================================================
INTERVIEW ANSWERS
================================================================

Q: How do you analyze and reduce JavaScript bundle size?
A: I start with webpack-bundle-analyzer or source-map-explorer to visualize
   what's in the bundle. I look for: oversized dependencies (moment.js,
   lodash imported in full), duplicate modules across chunks, and code that
   should be lazy-loaded. Common fixes: replace moment.js with day.js (72x
   smaller), use lodash/debounce instead of full lodash, lazy load heavy
   components (charts, editors), and enable proper tree shaking with ES
   module imports.

Q: What's the difference between stat, parsed, and gzipped bundle size?
A: Stat size is the raw source size. Parsed size is after webpack processes it
   (includes module scaffolding). Gzipped is what users actually download
   over the network. I always optimize for gzipped size since that's the
   transfer cost. However, parse/compile time is proportional to parsed size,
   not gzipped — so even a small gzipped size can mean significant parse cost.

Q: How do you find what's causing bundle size regression in a PR?
A: I use Bundlewatch or size-limit in CI to catch regressions automatically —
   if the PR exceeds the budget, it fails. For investigation, I run bundle
   analysis before and after, looking at the diff. I also use tools like
   webpack-deps-tree to trace which file is importing a large module.
   Git bisect can help find the exact commit that introduced the regression.

Q: What are the biggest bundle size quick wins you've seen?
A: (1) Replacing moment.js with day.js — saved 70KB gzipped in a project;
   (2) Switching from full lodash import to specific function imports —
   saved 50KB; (3) Lazy-loading chart library (Recharts) — removed 45KB
   from initial bundle; (4) Switching icon library imports from barrel exports
   to direct file imports — saved 200KB by removing unused icons;
   (5) Removing IE11 polyfills — saved 30-40KB.

Q: How do you identify duplicate modules in a bundle?
A: webpack-bundle-analyzer shows duplicate modules across chunks as the
   same module name appearing in multiple chunks. This often happens with
   multiple versions of the same library (e.g., two packages each requiring
   different versions of lodash). webpack's SplitChunksPlugin with
   optimization.splitChunks.chunks: 'all' deduplicates shared modules into
   a single vendor chunk. I also check package-lock.json for version conflicts
   with: npm ls <package-name>.
