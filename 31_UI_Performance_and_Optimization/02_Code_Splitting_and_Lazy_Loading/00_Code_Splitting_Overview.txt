================================================================
CODE SPLITTING - OVERVIEW AND FUNDAMENTALS
================================================================

WHAT IS CODE SPLITTING?
────────────────────────
Code splitting is the practice of splitting your JavaScript bundle into
multiple smaller chunks that can be loaded on demand, rather than loading
all JavaScript upfront.

Instead of:
  main.bundle.js (2MB) → loaded at start → user waits 8 seconds

With code splitting:
  initial.bundle.js (200KB) → loaded at start → user sees content in 1s
  route-about.chunk.js (50KB) → loaded when user navigates to /about
  route-dashboard.chunk.js (300KB) → loaded when user navigates to /dashboard
  chart-library.chunk.js (400KB) → loaded when user opens chart view

THE CORE PRINCIPLE:
  "Only load what the user needs RIGHT NOW.
   Load everything else WHEN THEY NEED IT."

================================================================
WHY CODE SPLITTING MATTERS
================================================================

THE PROBLEM WITH LARGE BUNDLES:
  - JavaScript is the MOST expensive resource per byte
  - 1MB JS != 1MB Image in terms of cost:
    → Image: download + decode
    → JS: download + parse + compile + execute (4 steps!)
  
  - On a mid-tier Android, 1MB JS:
    → Takes ~3-4 seconds to parse and compile alone
    → This BLOCKS the main thread, delaying interactivity
  
  - Wasted resources:
    → 70% of code in a typical SPA is never executed on any given page
    → Users pay download + parse cost for code they never use

IMPACT ON PERFORMANCE METRICS:
  - Reduces initial bundle size → faster FCP, LCP
  - Reduces JavaScript parse/compile time → better TTI, TBT, INP
  - Reduces main thread blocking → less input delay
  - Enables parallel loading (multiple small chunks vs one big chunk)

================================================================
TYPES OF CODE SPLITTING
================================================================

1. ENTRY POINT SPLITTING (Manual)
───────────────────────────────────
Create separate entry points in webpack config:

// webpack.config.js
module.exports = {
  entry: {
    main: './src/index.js',
    admin: './src/admin.js',
  },
  output: {
    filename: '[name].bundle.js',
  },
};

Use case: Multi-page apps with completely separate code paths.
Downside: Manual maintenance; shared code may be duplicated unless
          using SplitChunksPlugin.

2. DYNAMIC IMPORT SPLITTING (Automatic + On-demand)
─────────────────────────────────────────────────────
The modern, preferred approach using dynamic import():

// Load module only when needed
button.addEventListener('click', async () => {
  const { default: HeavyChart } = await import('./HeavyChart');
  renderChart(HeavyChart);
});

Webpack/Vite automatically creates a separate chunk for anything
behind a dynamic import(). The chunk is loaded on demand.

3. ROUTE-BASED SPLITTING (Most common in React)
────────────────────────────────────────────────
Load route components only when the user navigates to that route:

// React Router with code splitting
const Home = React.lazy(() => import('./pages/Home'));
const About = React.lazy(() => import('./pages/About'));
const Dashboard = React.lazy(() => import('./pages/Dashboard'));

// Only the current route's code is loaded
function App() {
  return (
    <Suspense fallback={<LoadingSpinner />}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
        <Route path="/dashboard" element={<Dashboard />} />
      </Routes>
    </Suspense>
  );
}

4. COMPONENT-LEVEL SPLITTING
──────────────────────────────
Lazy load heavy components (modals, charts, editors):

const RichTextEditor = React.lazy(() => import('./RichTextEditor'));
const DataGrid = React.lazy(() => import('./DataGrid'));

function Page() {
  const [showEditor, setShowEditor] = useState(false);
  
  return (
    <>
      <button onClick={() => setShowEditor(true)}>Open Editor</button>
      {showEditor && (
        <Suspense fallback={<div>Loading editor...</div>}>
          <RichTextEditor />
        </Suspense>
      )}
    </>
  );
}

5. VENDOR SPLITTING (Split vendor code)
────────────────────────────────────────
Separate vendor (node_modules) code from app code:

// webpack.config.js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
        // Split large vendor libs separately
        react: {
          test: /[\\/]node_modules[\\/](react|react-dom)[\\/]/,
          name: 'react',
          chunks: 'all',
          priority: 10,
        },
      },
    },
  },
};

Benefit: Vendor code rarely changes → long-lived browser cache.
         App code changes frequently → only app chunk invalidated.

================================================================
WEBPACK AUTOMATIC CODE SPLITTING
================================================================

webpack automatically handles:
  1. Dynamic imports → separate chunks
  2. SplitChunksPlugin → deduplication of shared modules
  3. Magic comments → control chunk names and loading

MAGIC COMMENTS:
────────────────
// Webpackchunkname: name the chunk
const Chart = await import(/* webpackChunkName: "chart" */ './Chart');
// Creates: chart.chunk.js

// Webpack prefetch: load in browser idle time (low priority)
const AdminPanel = await import(
  /* webpackPrefetch: true */
  './AdminPanel'
);
// Browser downloads in idle time, available for future navigation

// Webpack preload: load in parallel with parent chunk (high priority)
const LoginModal = await import(
  /* webpackPreload: true */
  './LoginModal'
);
// Use carefully — abusing preload wastes bandwidth

================================================================
VITE / ROLLUP CODE SPLITTING
================================================================

Vite handles code splitting automatically:
  - Dynamic imports → automatic chunks
  - manualChunks for custom chunking

// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          // Bundle specific vendors together
          'vendor-react': ['react', 'react-dom'],
          'vendor-charts': ['recharts', 'd3'],
          'vendor-ui': ['@mui/material', '@emotion/react'],
        },
      },
    },
  },
});

================================================================
ANALYZING CODE SPLITTING EFFECTIVENESS
================================================================

TOOLS:
  1. webpack-bundle-analyzer
     npm install --save-dev webpack-bundle-analyzer
     ANALYZE=true npm run build
     → Visual treemap of all chunks

  2. source-map-explorer
     npx source-map-explorer 'build/static/js/*.js'
     → Shows what's in each chunk

  3. @next/bundle-analyzer (for Next.js)
     ANALYZE=true next build

  4. Vite bundle analyzer plugin
     npm install --save-dev rollup-plugin-visualizer

WHAT TO LOOK FOR:
  - Large dependencies in the initial bundle → candidate for splitting
  - Duplicate code across chunks → needs deduplication
  - Unused imports → tree shaking opportunity
  - Large route chunks → split further or optimize imports

================================================================
CODE SPLITTING BEST PRACTICES
================================================================

✅ DO:
  - Split at route boundaries (highest ROI, natural division)
  - Split large libraries only used on specific pages (Chart.js, Monaco Editor)
  - Split heavy UI components (modal, data grid, rich text editor)
  - Add meaningful loading states (Suspense fallback)
  - Name chunks with webpackChunkName for debuggability
  - Prefetch likely-next routes during idle time
  - Test what the user experiences during loading (network throttling)

❌ DON'T:
  - Over-split into tiny chunks (network overhead per request)
  - Split code that's used on every page (no benefit, extra requests)
  - Forget fallback UI (Suspense without fallback = crash on error)
  - Lazy-load above-the-fold content (delays initial render)
  - Use static imports after you've set up lazy loading (defeats purpose)

RULE OF THUMB:
  A chunk under 30KB is probably too small (network request overhead outweighs benefit).
  A chunk over 244KB (webpack warning threshold) should be investigated for splitting.

================================================================
INTERVIEW ANSWERS
================================================================

Q: What is code splitting and why is it important?
A: Code splitting divides a JavaScript bundle into multiple smaller chunks
   loaded on demand. It's important because JS is the most expensive resource
   per byte — it must be downloaded, parsed, compiled, and executed. A 2MB
   bundle can block the main thread for 3-4 seconds on mobile. Code splitting
   reduces the initial payload, improving FCP, LCP, TTI, and TBT. Users only
   download code for what they're actively using.

Q: What are the different types of code splitting?
A: (1) Entry point splitting — multiple webpack entry points for multi-page
   apps; (2) Dynamic import splitting — use import() for on-demand loading;
   (3) Route-based splitting — React.lazy() per route (most common in SPAs);
   (4) Component-level splitting — lazy load heavy components like modals,
   charts, or editors; (5) Vendor splitting — separate node_modules from
   app code to leverage long-lived browser caching.

Q: How does webpack decide what to put in each chunk?
A: By default, webpack puts everything in one bundle. Code splitting is
   triggered by: (1) Multiple entry points; (2) Dynamic import() statements
   — each creates a separate chunk; (3) SplitChunksPlugin configuration
   which automatically extracts shared modules into common chunks to avoid
   duplication. Magic comments like webpackChunkName let you control chunk names.

Q: What's the difference between webpackPrefetch and webpackPreload?
A: webpackPreload loads in parallel with the parent chunk (high priority,
   like a preload link) — use for resources needed by the current page.
   webpackPrefetch loads in browser idle time after the current page loads
   (low priority, like a prefetch link) — use for resources needed on likely
   next navigation. Misusing preload wastes bandwidth; prefetch is safe for
   speculative loading.

Q: When should you NOT code split?
A: Don't split code that's used on every page (React core, routing, global
   styles) — it's always needed so splitting just adds extra requests. Don't
   create chunks smaller than ~30KB (network overhead exceeds benefit). Don't
   lazy-load above-the-fold content — it delays initial render. The decision
   should be driven by bundle analysis showing which code is actually only
   used on specific routes/interactions.
