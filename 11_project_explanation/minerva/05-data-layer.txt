Q: "Why PostgreSQL for config and not MongoDB?"

"Dashboard config has strong relational structure — a dashboard HAS many filters, charts, grids, map layers. Foreign keys enforce referential integrity (can't have an orphaned chart). ACID transactions mean we can save a dashboard + all its components atomically. MongoDB's flexible schema would be a liability here — we WANT strict structure for config data. JSONB columns give us flexibility where we need it (like layoutjson and columnsjson)."

BigQuery Cost Model

Pricing: $5 per TB scanned (on-demand pricing)

Example costs per query type:
- Chart query (filtered by region + date range):  ~2 GB scanned  = $0.01
- Grid query (paginated, 50 rows):                ~3 GB scanned  = $0.015
- Report query (full export, 500K rows):           ~50 GB scanned = $0.25
- Unfiltered full table scan:                      ~200 GB scanned = $1.00

Monthly estimate for ~200 users: $500-$800 (with caching reducing 60% of queries)

Production Guards for BigQuery

@Service
public class BigQueryExecutor {

    private static final long MAXBYTESBILLED = 50L  1024  1024 * 1024; // 50 GB per query
    private static final long REPORTMAXBYTES = 100L  1024  1024 * 1024; // 100 GB for reports
    private static final int TIMEOUTMS = 60000; // 60 seconds

    public QueryResult execute(String sql, Map params, boolean isReport) {
        QueryJobConfiguration config = QueryJobConfiguration.newBuilder(sql)
            .setUseLegacySql(false)
            .setMaximumBytesBilled(isReport ? REPORTMAXBYTES : MAXBYTESBILLED)
            .setJobTimeoutMs(TIMEOUT_MS)
            .setPriority(QueryJobConfiguration.Priority.INTERACTIVE)
            .build();

        // Bind parameters (prevents SQL injection)
        for (Map.Entry entry : params.entrySet()) {
            config = config.toBuilder()
                .addNamedParameter(entry.getKey(), toQueryParameter(entry.getValue()))
                .build();
        }

        TableResult result = bigQuery.query(config);
        return mapResult(result);
    }
}

Q: "Why BigQuery if your services are on AWS?"

"The Verizon Data Engineering team standardized on GCP for their data platform — they run Airflow and Dataflow pipelines that land curated data in BigQuery. We consume that data. Cross-cloud latency (AWS → GCP) adds ~20-50ms per query, but since we cache aggressively in Redis (60% cache hit rate), most users never feel it. The alternative was replicating 50M+ rows daily from BigQuery to an AWS data warehouse, which would cost more and add ETL complexity."

3. Kinetica — GPU-Accelerated WMS Tiles
---------------------------------------

Role
- WMS (Web Map Service) tile rendering ONLY
- No general queries, no GeoJSON, no API calls from services
- GPU-accelerated server-side rendering of heatmaps, point maps, contour maps
- Managed by Verizon infrastructure team

How It Works

Map Service  ──GET /wms?LAYERS=coverage_heatmap──►  Kinetica
             ◄──PNG tile (256x256 pixels)──────────

Kinetica renders the tile server-side using GPU → returns a pre-rendered PNG image → browser just displays the image. No data transfer, no GeoJSON parsing, no client-side rendering.

What's in Kinetica

| Table/View | Source | Purpose |
|-----------|--------|---------|
| coveragedatageo | Materialized view from BigQuery data | RF coverage heatmaps with RSRP/RSRQ |
| towerlocationsgeo | Materialized view | Tower location point maps |
| trafficdensitygeo | Materialized view | Traffic density contour maps |

Q: "Why Kinetica and not PostGIS or Mapbox?"

"Scale and rendering speed. We're plotting millions of data points (every cell site measurement) on a map. PostGIS could store and query geospatial data, but rendering millions of points server-side is CPU-intensive. Kinetica uses GPUs for server-side rendering — a heatmap of 5 million points renders in ~200ms as a PNG tile. Mapbox was considered but Verizon had data sovereignty concerns about sending network coverage data to a SaaS provider."

Caching Strategy

@Service
public class QueryCacheService {

    private final RedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    public Optional getCached(String tenantId, String dashboardId,
                                            String componentId, Map filters) {
        String cacheKey = buildCacheKey(tenantId, dashboardId, componentId, filters);
        String cached = redisTemplate.opsForValue().get(cacheKey);

        if (cached != null) {
            return Optional.of(objectMapper.readValue(cached, QueryResult.class));
        }
        return Optional.empty();
    }

    public void cache(String tenantId, String dashboardId, String componentId,
                      Map filters, QueryResult result, int ttlMinutes) {
        String cacheKey = buildCacheKey(tenantId, dashboardId, componentId, filters);
        redisTemplate.opsForValue().set(
            cacheKey,
            objectMapper.writeValueAsString(result),
            Duration.ofMinutes(ttlMinutes)
        );
    }

    // Cache key includes ALL filter values — different filters = different cache entry
    private String buildCacheKey(String tenantId, String dashboardId,
                                  String componentId, Map filters) {
        String filterHash = DigestUtils.sha256Hex(
            new TreeMap<>(filters).toString() // sorted for deterministic hash
        );
        return String.format("query:%s:%s:%s:%s", tenantId, dashboardId, componentId, filterHash);
    }

    // Bulk invalidation after data refresh
    public void invalidateByTable(String tableName) {
        // Scan for keys referencing dashboards that use this table
        // Uses Redis SCAN (not KEYS) to avoid blocking
        Set keys = scanKeys("query:*");
        // Filter to keys for dashboards using the refreshed table
        // Then delete in batches
        redisTemplate.delete(matchingKeys);
    }
}

Redis Cluster Setup

Redis Cluster (3 masters + 3 replicas)
├── Shard 0: config: keys + filter-opts:
├── Shard 1: query:* keys (highest volume)
├── Shard 2: jwt:, rate:, idem:, alert-dedup:, ws pub/sub

Q: "Why not Caffeine (local cache) instead of Redis?"

"Two reasons: (1) We have multiple pods per service — Caffeine is local to each pod, so cache invalidation would require coordinating across pods. Redis gives us a shared cache that all pods read from. (2) Redis also serves as our WebSocket pub/sub transport and rate limiting store. Using one system for all three reduces operational complexity."

Error Handling: Retry + DLT

@Configuration
public class KafkaConsumerConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate kafkaTemplate) {
        // Retry 3 times with exponential backoff: 1s, 2s, 4s
        BackOff backOff = new ExponentialBackOff(1000L, 2.0);
        ((ExponentialBackOff) backOff).setMaxElapsedTime(7000L); // 1s + 2s + 4s = 7s max

        // After 3 retries, send to Dead Letter Topic
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
            kafkaTemplate,
            (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition())
        );

        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);

        // Don't retry for these (non-transient errors)
        handler.addNotRetryableExceptions(
            JsonParseException.class,
            IllegalArgumentException.class
        );

        return handler;
    }
}

Idempotent Consumers

@KafkaListener(topics = "report-events", groupId = "notification-service")
public void handleReportEvent(ConsumerRecord record) {
    ReportEvent event = objectMapper.readValue(record.value(), ReportEvent.class);

    // Idempotency check — prevent duplicate processing on Kafka redelivery
    String idempotencyKey = "idem:report:" + event.getJobId();
    Boolean isNew = redisTemplate.opsForValue().setIfAbsent(
        idempotencyKey, "processed", Duration.ofHours(1)
    );

    if (Boolean.FALSE.equals(isNew)) {
        log.info("Duplicate event for report {}, skipping", event.getJobId());
        return; // already processed
    }

    // Process the event
    notifyUser(event.getUserId(), event.getStatus(), event.getDownloadUrl());
}

Q: "How do you handle Kafka consumer failures?"

"Three-layer strategy: (1) Retry — 3 attempts with exponential backoff (1s, 2s, 4s) for transient errors like network blips. (2) DLT — after 3 retries, the message goes to a Dead Letter Topic (e.g., report-events.DLT). PLATFORM_ADMINs can view DLT messages in the Admin Service UI and retry/discard them. (3) Idempotency — every consumer checks a Redis setIfAbsent key before processing, so Kafka redeliveries don't cause duplicate side effects."

Q: "Why Kafka and not RabbitMQ or SQS?"

"Three reasons: (1) The DE team already publishes data-refresh-events to Kafka — it's the existing event backbone. (2) Kafka's built-in consumer groups give us fan-out — one dashboard-events message is consumed by both Notification Service AND Query Execution Service independently. (3) Kafka retains messages for 7 days, so if a consumer goes down, it catches up when it recovers. SQS would need separate queues for each consumer. RabbitMQ could work but doesn't have the native DLT pattern we rely on."

Key interview points:
- We don't own the ETL pipeline — the DE team does
- We consume curated, clean data — no raw data processing
- Our contract with DE: "publish a Kafka event when you're done loading"
- If DE pipeline fails, our dashboards show yesterday's data (stale but not broken)

Q&A Bank (Data Layer)
---------------------

Q: "What happens if BigQuery goes down?"
"Our circuit breaker (Resilience4j) detects failures and trips OPEN after 5 consecutive errors. During outage: (1) config loads still work (PostgreSQL), (2) cached query results are served with a 'stale data' badge, (3) new queries get a 503 with retryAfter. When BigQuery recovers, the breaker goes HALF-OPEN, tests with one query, then CLOSED."

Q: "How do you manage Redis memory?"
"Three approaches: (1) TTL on every key — no key lives forever. (2) maxmemory-policy: allkeys-lru — if Redis approaches memory limit, least recently used keys are evicted first (query cache is the least critical). (3) Monitoring — CloudWatch alerts on Redis memory usage > 80%."

Q: "What if the DE team's ETL fails and data isn't refreshed?"
"Graceful degradation. No data-refresh-events message means no cache invalidation, so users continue seeing yesterday's cached data. We have a monitoring dashboard that tracks the last refresh timestamp per table. If it's > 6 hours stale, we alert the DE team. Our dashboards show a 'Data as of: March 14, 2025' timestamp so users know what they're looking at."

Q: "How do you prevent expensive BigQuery queries?"
"Four layers: (1) SQL validation on config save — dry-run shows estimated scan size, warns if > 10 GB. (2) maximumBytesBilled cap on every query (50 GB normal, 100 GB reports). (3) Rate limiting — 30 queries/min per user. (4) queryexecutionlog table tracks every query's bytes scanned and cost estimate. The Admin cost dashboard makes it easy to identify expensive dashboards and optimize them."
