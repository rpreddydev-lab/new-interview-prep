CATEGORY 1: CREATIONAL PATTERNS
================================================================

  ┌─────────────────────────────────────────────────────────┐
  │  BUILDER PATTERN                                        │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Constructs a complex object step by step. Separates construction
  from representation. Each step returns the builder (fluent API).

  Where in Minerva:
  Used in TWO places —

  (A) DTOs and domain objects with Lombok @Builder:
  Every DTO — DashboardConfigDto, ChartDto, FilterDto, ReportDto —
  uses @Builder. A full dashboard config has nested lists of filters,
  charts, grids, map layers, and reports. Without Builder, the
  constructor would have 15+ parameters.

      DashboardConfigDto config = DashboardConfigDto.builder()
          .id(dashboard.getId())
          .name(dashboard.getName())
          .department(dashboard.getDepartment())
          .layout(dashboard.getLayoutJson())
          .filters(filters.stream().map(FilterDto::from).toList())
          .charts(charts.stream().map(ChartDto::from).toList())
          .grids(grids.stream().map(GridDto::from).toList())
          .mapLayers(mapLayers.stream().map(MapLayerDto::from).toList())
          .build();

  (B) Elasticsearch NativeQuery construction:
  Building bool queries with must/should/filter clauses, pagination,
  sorting, and highlighting — NativeQuery.builder() chains all of
  these without needing a single giant constructor call.

      Query query = NativeQuery.builder()
          .withQuery(q -> q.bool(b -> b
              .must(m -> m.match(mt -> mt.field("name").query(keyword)))
              .filter(f -> f.term(t -> t.field("category").value(cat)))
              .filter(f -> f.range(r -> r.field("price").lte(maxPrice)))))
          .withPageable(PageRequest.of(page, 10))
          .withSort(Sort.by(Sort.Direction.DESC, "_score"))
          .build();

  Why Builder over a constructor?
  "Readability and safety. A dashboard config has 8+ fields, some
  optional. A 15-parameter constructor is impossible to read and easy
  to pass parameters in the wrong order. Builder makes each field
  named and explicit, and @Builder in Lombok generates it for free."

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  FACTORY / FACTORY METHOD PATTERN                       │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Defines an interface for creating objects, but lets subclasses or
  implementations decide which class to instantiate. Decouples the
  caller from concrete types.

  Where in Minerva:
  Report format factory — the Report Service generates reports in
  CSV, Excel (XLSX), or PDF format. Each format has different
  generation logic. A ReportGeneratorFactory decides which generator
  to return based on the format string stored in the DB config.

      public interface ReportGenerator {
          File generate(QueryResult data, ReportConfig config);
      }

      @Component
      public class CsvReportGenerator implements ReportGenerator { ... }

      @Component
      public class ExcelReportGenerator implements ReportGenerator { ... }

      @Component
      public class PdfReportGenerator implements ReportGenerator { ... }

      @Component
      public class ReportGeneratorFactory {
          private final Map<String, ReportGenerator> generators;

          public ReportGeneratorFactory(List<ReportGenerator> allGenerators) {
              // Spring injects all implementations; we map by format name
              this.generators = allGenerators.stream()
                  .collect(Collectors.toMap(
                      g -> g.getClass().getAnnotation(ReportFormat.class).value(),
                      g -> g
                  ));
          }

          public ReportGenerator getGenerator(String format) {
              return Optional.ofNullable(generators.get(format.toUpperCase()))
                  .orElseThrow(() -> new UnsupportedFormatException(format));
          }
      }

      // Usage in SAGA Step 2:
      ReportGenerator generator = factory.getGenerator(config.getFormat()); // "CSV", "EXCEL", "PDF"
      File file = generator.generate(queryResult, config);

  Why Factory?
  "Adding a new format (e.g., Parquet) means implementing one new
  class and annotating it. Zero changes to the calling code in the
  SAGA. This is the Open/Closed principle in action — open for
  extension, closed for modification."

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  SINGLETON PATTERN (Spring managed)                     │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Ensures a class has only one instance for the application's lifetime.

  Where in Minerva:
  Spring beans are singletons by default. Key examples:
  - BigQueryConfig @Bean → single BigQuery client shared across all
    Query Execution Service threads (thread-safe, expensive to create)
  - RedisConfig @Bean → single RedisTemplate (connection pool)
  - KafkaProducerConfig @Bean → single KafkaTemplate (thread-safe)

  We do NOT use hand-written singleton code (enum or double-checked
  locking). Spring manages it — Spring's IoC container IS the
  singleton registry.

  "In practice, I rely on Spring's bean scope rather than implementing
  Singleton myself. If someone asks me to implement it manually, I'd
  use the enum-based singleton (Effective Java recommendation) since
  it's thread-safe and serialization-safe out of the box."

CATEGORY 2: STRUCTURAL PATTERNS
================================================================

  ┌─────────────────────────────────────────────────────────┐
  │  PROXY PATTERN                                          │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Provides a surrogate or placeholder for another object to control
  access to it. The proxy and the real object share the same interface.

  Where in Minerva — THREE instances:

  (A) Map Service as a WMS Proxy:
  The Map Service sits between React/Leaflet and Kinetica's WMS engine.
  React sends a WMS tile request (LAYERS, BBOX, WIDTH, HEIGHT).
  The proxy:
    1. Validates the JWT (tenant + role check)
    2. Looks up map layer config from Dashboard Service
    3. Appends CQL_FILTER server-side (tenant isolation — never trusted from browser)
    4. Forwards to Kinetica WMS endpoint
    5. Returns the PNG tile to the browser

  The browser has no idea Kinetica exists. It thinks the Map Service
  IS the WMS server. That's the proxy.

      // Map Service acts as WMS proxy
      @GetMapping("/api/map/wms")
      public ResponseEntity<byte[]> proxyWmsTile(
              @RequestParam Map<String, String> wmsParams,
              @AuthenticationPrincipal Jwt jwt) {

          // 1. Validate
          String tenantId = jwt.getClaimAsString("tenant_id");

          // 2. Build CQL_FILTER server-side
          String cqlFilter = "tenant_id='" + tenantId + "' AND "
              + buildFilterFromParams(wmsParams);

          // 3. Forward to Kinetica (the real object)
          byte[] tile = kineticaClient.fetchTile(wmsParams, cqlFilter);

          return ResponseEntity.ok()
              .contentType(MediaType.IMAGE_PNG)
              .body(tile);
      }

  Why Proxy here?
  "Security. We can never trust a filter value that arrives from the
  browser. Server-side CQL_FILTER construction means a user cannot
  manipulate it to see another tenant's geospatial data. The proxy
  also hides Kinetica credentials entirely."

  (B) Spring AOP as a Proxy:
  @Cacheable, @Transactional, @PreAuthorize all work through Spring's
  AOP proxy. When you call dashboardService.getFullConfig(), you're
  calling the proxy, which intercepts the call to apply caching,
  transaction management, and security checks before delegating to
  the real implementation.

  (C) Redis Cache as a Proxy for BigQuery:
  The Query Execution Service checks Redis before going to BigQuery.
  Redis acts as a proxy / caching layer — same interface (you ask for
  query results), but the proxy (Redis) handles it if it has the data,
  only delegating to the real backend (BigQuery) on a cache miss.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  FACADE PATTERN                                         │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Provides a simplified interface to a complex subsystem of classes.
  Hides the complexity behind a single entry point.

  Where in Minerva:
  The DashboardService is a Facade over the complex config loading
  subsystem. A single call to getFullConfig() hides:
  - 5 separate repository queries (dashboard, filters, charts, grids, map layers)
  - Cache check and cache populate logic
  - DTO mapping from 5 different entity types
  - Tenant isolation enforcement

  The caller (DashboardController) doesn't know any of this:

      // Controller — simple facade call
      DashboardConfigDto config = dashboardService.getFullConfig(id, tenantId);

      // Behind the facade — complex subsystem
      public DashboardConfigDto getFullConfig(String id, String tenantId) {
          Optional<DashboardConfigDto> cached = cacheService.getConfig(id);
          if (cached.isPresent()) return cached.get();

          Dashboard dashboard = dashboardRepo.findByIdAndTenantId(id, tenantId)...;
          List<DashboardFilter> filters = filterRepo.findByDashboardId(id);
          List<DashboardChart> charts = chartRepo.findByDashboardId(id);
          List<DashboardGrid> grids = gridRepo.findByDashboardId(id);
          List<DashboardMapLayer> mapLayers = mapLayerRepo.findByDashboardId(id);

          DashboardConfigDto config = DashboardConfigDto.builder()...build();
          cacheService.putConfig(id, config);
          return config;
      }

  Similarly, the QueryExecutionService is a Facade over:
  rate limiting check → cache lookup → SQL parameterization →
  BigQuery execution → result caching → audit log write.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  DECORATOR PATTERN                                      │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Attaches additional responsibilities to an object dynamically,
  wrapping it with new behavior without changing the original class.

  Where in Minerva:
  Spring Security's filter chain IS a decorator chain. Each filter
  wraps the next:
  TenantContextFilter → JwtBlacklistFilter → JwtAuthenticationFilter
  → SecurityContextFilter → ... → actual Controller

  We added our own custom decorators to the chain:

  (A) TenantContextFilter — wraps the request to populate a
      ThreadLocal with the tenant_id extracted from the JWT.
      Every downstream component can call TenantContext.get()
      without passing tenant_id as a method parameter.

  (B) JwtBlacklistFilter — wraps the request to check if the
      JWT's jti claim is in the Redis blacklist (logged-out tokens).
      If blacklisted, returns 401 before hitting any controller.

  These filters "decorate" every incoming HTTP request with extra
  behavior (tenant context, blacklist check) without modifying any
  controller code.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  ADAPTER PATTERN                                        │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Converts the interface of a class into another interface that clients
  expect. Lets incompatible interfaces work together.

  Where in Minerva:
  The BigQuery result set has its own FieldValueList API. Our system
  works with generic List<Map<String, Object>> for all query results
  (so Report Service, Cache, and REST response don't need to know about
  BigQuery's type system).

  A BigQueryResultAdapter converts between the two:

      public class BigQueryResultAdapter {
          public static List<Map<String, Object>> adapt(TableResult result) {
              List<Map<String, Object>> rows = new ArrayList<>();
              for (FieldValueList row : result.iterateAll()) {
                  Map<String, Object> map = new LinkedHashMap<>();
                  Schema schema = result.getSchema();
                  for (int i = 0; i < schema.getFields().size(); i++) {
                      String fieldName = schema.getFields().get(i).getName();
                      FieldValue value = row.get(i);
                      map.put(fieldName, value.isNull() ? null : value.getValue());
                  }
                  rows.add(map);
              }
              return rows;
          }
      }

  The rest of the system never imports BigQuery's FieldValueList —
  it always works with List<Map<String, Object>>.

CATEGORY 3: BEHAVIORAL PATTERNS
================================================================

  ┌─────────────────────────────────────────────────────────┐
  │  STRATEGY PATTERN ← Most important one to nail          │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Defines a family of algorithms, encapsulates each one, and makes
  them interchangeable. The strategy can change at runtime without
  the client knowing which algorithm is being used.

  Where in Minerva — TWO strong examples:

  (A) Filter type rendering strategy:
  Dashboard filters can be DROPDOWN, MULTI_SELECT, DATE_RANGE, or TEXT.
  Each type has different validation logic and different option-loading
  behavior. A FilterStrategy interface defines the contract:

      public interface FilterStrategy {
          List<FilterOption> loadOptions(DashboardFilter filter, String tenantId);
          Object validateValue(Object value, DashboardFilter filter);
      }

      @Component("DROPDOWN")
      public class DropdownFilterStrategy implements FilterStrategy {
          public List<FilterOption> loadOptions(...) {
              // Execute optionsSql against PostgreSQL
          }
      }

      @Component("DATE_RANGE")
      public class DateRangeFilterStrategy implements FilterStrategy {
          public List<FilterOption> loadOptions(...) {
              return List.of(); // No options — date picker, no SQL
          }
          public Object validateValue(Object value, ...) {
              // Validate date format, start <= end
          }
      }

      // Injected by Spring — strategy selected at runtime
      Map<String, FilterStrategy> strategies; // bean name = filter type
      FilterStrategy strategy = strategies.get(filter.getFilterType());
      List<FilterOption> options = strategy.loadOptions(filter, tenantId);

  (B) SQL Parameterization strategy per filter type:
  When building a BigQuery query, ${region} is substituted differently
  by type — a DROPDOWN filter becomes a single quoted string, a
  MULTI_SELECT becomes an UNNEST() expression, a DATE_RANGE becomes
  a BETWEEN clause. Each has its own SqlBindStrategy:

      public interface SqlBindStrategy {
          String bind(String placeholder, Object value);
      }

      // MULTI_SELECT: "5G-NR", "4G-LTE" → UNNEST(['5G-NR', '4G-LTE'])
      @Component("MULTI_SELECT")
      public class MultiSelectBindStrategy implements SqlBindStrategy {
          public String bind(String placeholder, Object value) {
              List<String> values = (List<String>) value;
              String quoted = values.stream()
                  .map(v -> "'" + v + "'")
                  .collect(Collectors.joining(", "));
              return "UNNEST([" + quoted + "])";
          }
      }

  Why Strategy here?
  "Adding a new filter type (say, NUMERIC_RANGE) means implementing
  two interfaces — FilterStrategy and SqlBindStrategy. Zero changes to
  the Query Execution Service's core execution loop."

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  OBSERVER PATTERN                                       │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Defines a one-to-many dependency between objects. When one object
  (Subject) changes state, all its dependents (Observers) are notified
  automatically.

  Where in Minerva — TWO instances:

  (A) Spring Application Events (@TransactionalEventListener):
  When a dashboard is saved, we publish a DashboardSavedEvent.
  Multiple observers react independently:

      // Publisher (Subject)
      @Transactional
      public DashboardConfigDto updateDashboard(...) {
          Dashboard saved = dashboardRepo.save(dashboard);
          eventPublisher.publishEvent(new DashboardSavedEvent(saved));
          return DashboardConfigDto.from(saved);
      }

      // Observer 1: Invalidate Redis cache
      @TransactionalEventListener(phase = AFTER_COMMIT)
      public void onDashboardSaved(DashboardSavedEvent event) {
          cacheService.evict(event.getDashboard().getId());
      }

      // Observer 2: Publish Kafka event (notify active viewers)
      @TransactionalEventListener(phase = AFTER_COMMIT)
      public void publishKafkaEvent(DashboardSavedEvent event) {
          kafkaTemplate.send("dashboard-events", event.toDashboardUpdatedDto());
      }

      // Observer 3: Write audit log
      @TransactionalEventListener(phase = AFTER_COMMIT)
      public void auditDashboardChange(DashboardSavedEvent event) {
          auditProducer.publishAuditEvent(AuditEvent.of(event));
      }

  Key: AFTER_COMMIT means observers only fire if the DB transaction
  committed successfully. No risk of cache invalidation on a rollback.

  (B) Kafka + WebSocket (cross-service Observer):
  Kafka is the distributed Observer pattern across services:
  - DE team publishes "data refresh complete" → Subject
  - Notification Service is the Observer → WebSocket push to browsers
  - Query Execution Service is the Observer → cache invalidation + warm-up

  Multiple observers react to the same event independently.
  They don't know each other exist.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  TEMPLATE METHOD PATTERN                                │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Defines the skeleton of an algorithm in a base class, deferring
  some steps to subclasses. Subclasses can redefine certain steps
  without changing the overall algorithm structure.

  Where in Minerva:
  The SAGA pattern orchestration in the Report Service. Every report
  type (ad-hoc, scheduled, alert-triggered) follows the same 4-step
  skeleton but with slight variation in notification target:

      public abstract class ReportSaga {

          // Template method — the fixed algorithm skeleton
          public final String execute(ReportConfig config, String tenantId) {
              String reportId = initReport(config, tenantId);
              try {
                  QueryResult data = step1_query(config);        // FIXED
                  File file = step2_generate(data, config);      // FIXED
                  String url = step3_upload(file, reportId);     // FIXED
                  step4_notify(reportId, url, tenantId);         // VARIES
                  markComplete(reportId, url);
              } catch (Exception e) {
                  compensate(reportId, e);                       // FIXED
              }
              return reportId;
          }

          // Subclasses define who to notify
          protected abstract void step4_notify(String reportId, String url, String tenantId);
      }

      public class UserReportSaga extends ReportSaga {
          protected void step4_notify(String reportId, String url, String tenantId) {
              kafkaTemplate.send("report-events", new ReportReadyEvent(reportId, url));
              // → Notification Service → WebSocket push to requesting user
          }
      }

      public class ScheduledReportSaga extends ReportSaga {
          protected void step4_notify(String reportId, String url, String tenantId) {
              // Email to the schedule's recipient list
              emailService.sendReportEmail(schedule.getRecipients(), url);
          }
      }

  Why Template Method?
  "The query → generate → upload steps are identical for all report
  types. Only the notification step differs. Template Method prevents
  copy-paste of the orchestration logic across three classes, and
  ensures compensating actions always run on failure regardless of
  the subtype."

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  CHAIN OF RESPONSIBILITY PATTERN                        │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Passes a request along a chain of handlers. Each handler decides
  whether to process the request or pass it to the next handler.

  Where in Minerva:
  (A) Spring Security FilterChain:
  Every HTTP request passes through:
  CorsFilter → JwtBlacklistFilter → TenantContextFilter
  → JwtAuthenticationFilter → SecurityContextFilter → Controller

  Each filter either handles the request (e.g., returns 401 on
  blacklisted token) or calls chain.doFilter() to pass it forward.

  (B) SQL Validation pipeline (Dashboard Service):
  When a CONFIGURATOR saves a chart SQL, the validation runs as a
  chain — each validator either rejects or passes to the next:

      SELECT-only check → Placeholder validation → BigQuery dry-run → Scan estimate warning

  Each step can short-circuit the chain (return rejected) without
  the next steps running.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  SAGA PATTERN (Distributed Transactions)                │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Not a GoF pattern but a distributed systems pattern. Manages a
  long-running process as a sequence of steps, each with a
  compensating action if it fails. Used when you can't use a
  single ACID transaction across services.

  Where in Minerva:
  Report generation — 4 steps, each with a compensating action:

  Step 1: Query BigQuery (500K row cap, 60s timeout)
    → Fail: Mark FAILED, notify user "Query timed out"

  Step 2: Generate CSV/Excel/PDF from result set
    → Fail: Delete temp file, mark FAILED, notify user

  Step 3: Upload to S3 (signed URL, 24h TTL)
    → Fail: Delete S3 object (if partial), mark FAILED, notify user

  Step 4: Publish report-ready event to Kafka → WebSocket push
    → Fail: S3 object stays (user can retry download), mark FAILED,
            log for DLT inspection

  Why SAGA over synchronous?
  "Reports take 30–120 seconds — synchronous HTTP would timeout at
  30 seconds. SAGA lets us decouple each step, observe status
  independently (user polls /api/reports/{id}/status), and ensure
  cleanup happens on failure. Before SAGA, we had a 30% failure rate
  with orphaned S3 objects. After: <1% failure rate with no orphans."

CATEGORY 4: CONCURRENCY & RESILIENCE PATTERNS
================================================================

  ┌─────────────────────────────────────────────────────────┐
  │  CIRCUIT BREAKER PATTERN                                │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Monitors calls to an external service. If failures exceed a
  threshold, the circuit "opens" — further calls fail fast instead
  of waiting for timeouts. After a cooldown, the circuit goes to
  half-open to test if the service recovered.

  Where in Minerva:
  Resilience4j CircuitBreaker on all BigQuery calls in the
  Query Execution Service.

      resilience4j:
        circuitbreaker:
          instances:
            bigquery:
              failure-rate-threshold: 50        # open if 50% of last 10 calls fail
              minimum-number-of-calls: 5        # don't open on first failure
              sliding-window-size: 10
              wait-duration-in-open-state: 30s  # wait 30s before half-open
              permitted-number-of-calls-in-half-open-state: 1

      @CircuitBreaker(name = "bigquery", fallbackMethod = "queryFallback")
      public QueryResult executeQuery(String sql, Map<String, Object> params) {
          return bigQueryClient.execute(sql, params);
      }

      // Fallback: return cached result or empty
      public QueryResult queryFallback(String sql, Map<String, Object> params, Exception e) {
          return cacheService.getStaleResult(cacheKey(sql, params))
              .orElse(QueryResult.empty("BigQuery temporarily unavailable"));
      }

  Why this matters:
  "BigQuery has occasional latency spikes. Without circuit breaking,
  a BigQuery slowdown causes all Query Execution Service threads to
  block waiting for responses — cascading failure across the platform.
  With circuit breaking, after 5 failures in the window, calls fail
  immediately and return stale cached data. Users see a warning banner
  instead of a spinning chart."

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  IDEMPOTENCY PATTERN (Messaging)                        │
  └─────────────────────────────────────────────────────────┘

  What it is:
  Ensures that executing the same operation multiple times produces
  the same result as executing it once. Critical for Kafka consumers
  where messages can be retried.

  Where in Minerva:
  Report Service — Kafka messages can be delivered more than once
  (at-least-once delivery). Without idempotency, a single "generate
  report" event could trigger 3 reports.

      // Before processing: check if we've already handled this event
      public void handleReportRequest(ReportRequestEvent event) {
          String idempotencyKey = "report:request:" + event.getRequestId();

          // setIfAbsent = only set if key doesn't exist
          Boolean isNew = redisTemplate.opsForValue()
              .setIfAbsent(idempotencyKey, "processing", Duration.ofHours(1));

          if (Boolean.FALSE.equals(isNew)) {
              log.warn("Duplicate report request ignored: {}", event.getRequestId());
              return; // Already processing or processed
          }

          // New request — proceed with SAGA
          reportSaga.execute(event.getReportConfig(), event.getTenantId());
      }

CATEGORY 5: SPRING-SPECIFIC PATTERNS (Mention These Too)
================================================================

  ┌─────────────────────────────────────────────────────────┐
  │  DEPENDENCY INJECTION (IoC)                             │
  └─────────────────────────────────────────────────────────┘

  All Minerva services use constructor injection (not field injection).
  Benefits: testable without Spring context, immutable dependencies,
  makes missing dependencies fail at startup not at runtime.

      @Service
      @RequiredArgsConstructor  // Lombok generates constructor
      public class QueryExecutionService {
          private final BigQueryClient bigQueryClient;   // injected
          private final RedisTemplate<String, String> redisTemplate;
          private final DashboardServiceClient dashboardClient;
          private final QueryExecutionLogRepository logRepo;
      }

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  REPOSITORY PATTERN                                     │
  └─────────────────────────────────────────────────────────┘

  All DB access goes through Spring Data JPA Repository interfaces.
  Service layer never writes SQL directly — it calls repository
  methods. This decouples business logic from data access technology.

  Even BigQuery results are adapted into a common QueryResult object
  via the BigQueryResultAdapter, keeping the service layer agnostic
  to which data store it's reading from.

  ─────────────────────────────────────────────────────────

  ┌─────────────────────────────────────────────────────────┐
  │  THREAD-LOCAL PATTERN                                   │
  └─────────────────────────────────────────────────────────┘

  TenantContext is a ThreadLocal holder. The TenantContextFilter
  populates it from the JWT at the start of each request. Every
  downstream component calls TenantContext.get() instead of passing
  tenant_id through every method signature.

      public class TenantContext {
          private static final ThreadLocal<String> TENANT =
              new ThreadLocal<>();

          public static void set(String tenantId) { TENANT.set(tenantId); }
          public static String get() { return TENANT.get(); }
          public static void clear() { TENANT.remove(); } // called in finally block
      }

  Risk: must call clear() in a finally block in the filter, otherwise
  the ThreadLocal leaks across requests in a thread pool.

  Creational — Builder, Factory, Singleton, Prototype, Abstract Factory.
  Structural — Proxy, Facade, Decorator, Adapter, Composite, Bridge.
  Behavioral — Strategy, Observer, Template Method, Chain of Responsibility,
  Command, Iterator, State, Mediator.
  Beyond GoF, distributed systems patterns like SAGA, Circuit Breaker,
  Outbox, and Event Sourcing are equally important in modern microservices.
  Should I walk through the ones I've used in Minerva?"

  FLOW 2 — "Which pattern did you find most useful in your project?"
  ──────────────────────────────────────────────────────────────────
  "Strategy was the most impactful. Minerva's config-driven model means
  the system has to handle unknown filter types at runtime. Using Strategy,
  each filter type — DROPDOWN, MULTI_SELECT, DATE_RANGE, TEXT — has its
  own implementation of FilterStrategy. Adding a new filter type is just
  one new class, zero changes to the execution engine. Without Strategy,
  I'd have a massive if-else chain that would grow with every new type."

  FLOW 3 — "Explain a real problem and how a pattern solved it"
  ─────────────────────────────────────────────────────────────
  Use the SAGA story:
  "Report generation was originally synchronous. HTTP request came in,
  we ran BigQuery, generated the file, uploaded to S3, and returned the
  URL — all in one HTTP call. Large reports took 60-90 seconds and HTTP
  clients timed out at 30 seconds. We had a 30% failure rate.
  I redesigned it using the SAGA pattern. Each step is now atomic with
  its own compensating action — if S3 upload fails, we delete the partial
  file and mark the report FAILED. The client polls /api/reports/{id}/status
  and gets a download URL when COMPLETED. Failure rate dropped to <1%."

  FLOW 4 — "Singleton vs. Prototype Spring bean?"
  ─────────────────────────────────────────────────
  "Singleton (default) — one instance shared across the application.
  Good for stateless beans: services, repositories, Kafka templates.
  Prototype — new instance per injection. Good for stateful objects.
  In Minerva, all our beans are singletons. If we needed per-request
  state, we'd use @Scope('request') or just keep state in the request
  object — never in a singleton field."
