01 — MINERVA: PROJECT OVERVIEW
==============================

What to use this for: Your opening in ANY interview — "Tell me about your most recent project."

60-Second Pitch
---------------

"I built Minerva, a configuration-driven analytics platform for Verizon's network engineering organization. Instead of coding dashboards, our analysts and engineering leads define dashboards entirely through database configuration — filters, charts, grids, map layers, reports — all stored as rows in PostgreSQL. React reads that config and renders dynamically. Zero deployments to add a new dashboard.
The platform runs 7 services (6 internal microservices on Spring Boot 3 / Java 17 + ForgeRock SSO), deployed to AWS EKS via ArgoCD GitOps. Analytics data lives in GCP BigQuery (loaded daily by our Data Engineering team), geospatial tiles are rendered by Kinetica's WMS engine, and all configuration lives in PostgreSQL. We use Kafka for event-driven flows — daily data refresh, async report generation with the SAGA pattern, and real-time notifications via WebSocket.
Security is handled by Verizon's ForgeRock SSO (OAuth2 + PKCE + OIDC) with 5 RBAC roles mapped to real Verizon job functions — from RF Engineers who analyze coverage data to VPs who get read-only executive dashboards.
The platform serves ~200 users across multiple departments, processes 50M+ BigQuery rows daily, and delivers sub-second dashboard loads through aggressive Redis caching and smart cache warm-up after the daily data refresh."

The 7 Services at a Glance
--------------------------

| # | Service | Owns | Key Tech |
|---|---------|------|----------|
| 1 | ForgeRock SSO (external) | Authentication, JWT issuance | OAuth2 + PKCE + OIDC, RS256, JWKS |
| 2 | Dashboard Service | All config CRUD — dashboards, filters, charts, grids, map layers | PostgreSQL, SQL validation (SELECT-only parse + dry-run) |
| 3 | Query Execution Service | Run configured SQL against BigQuery, return results | BigQuery Java SDK, Redis cache, rate limiting, audit log |
| 4 | Report Service | Async report generation, scheduled reports | SAGA pattern, Quartz scheduler, S3, 500K row cap |
| 5 | Map Service | WMS tile proxy to Kinetica | Server-side CQL_FILTER construction, no browser trust |
| 6 | Notification Service | Real-time push + Kafka consumer | WebSocket (STOMP), ChannelInterceptor auth, Redis pub/sub |
| 7 | Admin Service | Tenant/user management, audit, DLT viewer, cost dashboard | Kafka audit consumer, queryexecutionlog |

The 5 RBAC Roles (Mapped to Verizon Job Functions)
--------------------------------------------------

| Role | Who (Verizon Titles) | Can Do | Cannot Do |
|------|---------------------|--------|-----------|
| PLATFORM_ADMIN | Minerva ops team (us) | Everything + tenant management, DLT viewer, cost dashboard | — |
| TENANT_ADMIN | IT Ops Manager | User provisioning, role assignment within their tenant | Cross-tenant access, DLT viewer |
| CONFIGURATOR | Analytics Lead, Senior Network Engineer, Team Lead | Create/edit dashboards, configure filters/charts/grids/reports/alerts | Tenant management, DLT viewer |
| ANALYST | RF Engineer, Traffic Engineer, NOC Analyst, Performance Engineer | View dashboards, apply filters, export data, run ad-hoc reports | Create/edit dashboard config |
| VIEWER | SVP, VP, Senior Director, Director | View dashboards only (read-only, no export) | Export, filter editing, config changes |

Why "Configuration-Driven" Matters
----------------------------------

The core insight: In traditional analytics platforms, every new dashboard requires developer time — writing API endpoints, database queries, frontend components. In Minerva, a CONFIGURATOR opens the admin UI, fills in a form (SQL query, chart type, filter bindings), hits save, and the dashboard is live. Zero code, zero deployment.

How it works:
1. PostgreSQL stores everything — dashboards, dashboardfilters, dashboardcharts, dashboardgrids, dashboardmaplayers, dashboardreports, reportschedules, alertconfigs
2. React reads config at load time — fetches the config payload, dynamically renders the right components
3. Query Execution Service runs the configured SQL — parameterized, validated, rate-limited, cached
4. Dashboard Service validates on save — SELECT-only SQL parse, BigQuery dry-run, scan estimate warning

Interview angle: "We turned dashboard creation from a 2-week dev cycle into a 30-minute configuration task. Our Analytics Leads could self-serve without any engineering involvement."
