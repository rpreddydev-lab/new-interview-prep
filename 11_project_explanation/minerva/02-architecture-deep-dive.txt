What to use this for: "Walk me through the architecture" / "Why did you make that design decision?" / "How does service X work?"

Why Configuration-Driven? (The Core Design Decision)
----------------------------------------------------

Q: Why not just build dashboards the traditional way?

"Verizon's network engineering org has 5+ departments — RF, Traffic, NOC, Performance, Executive — each needing different views of the same underlying data. In a traditional approach, every new dashboard means a Jira ticket, a sprint, a deployment. We had a backlog of 20+ dashboard requests.
So we inverted the model: the database IS the application. Every visual element — filter dropdowns, chart configs, grid columns, map layers, report definitions — is a row in PostgreSQL. React reads that config and renders dynamically. A CONFIGURATOR (our Analytics Leads) can create a complete dashboard in 30 minutes without any engineering involvement.
This reduced our dashboard delivery time from 2 weeks to 30 minutes and eliminated the deployment bottleneck entirely."

Trade-offs I'd discuss in an interview:
- ✅ Speed: 30 min vs 2 weeks for new dashboards
- ✅ Self-service: Non-developers can create dashboards
- ✅ Zero-deployment: No CI/CD needed for new content
- ⚠️ Complexity: SQL validation layer is non-trivial (SELECT-only parse + dry-run)
- ⚠️ Testing: Config changes aren't code-reviewed (we compensate with dry-run validation + audit logging)
- ⚠️ Flexibility: Truly custom visualizations still need dev work

Service 1: ForgeRock SSO (External IdP)
---------------------------------------

Owner: Verizon Enterprise IAM team (not us)  
Our Role: Integrate as a relying party

What ForgeRock Provides
- OAuth2 Authorization Server + OIDC Provider
- PKCE flow (public SPA client — no client_secret in browser)
- RS256-signed JWTs with custom claims: tenant_id, roles[], department
- JWKS endpoint for public key distribution
- Token revocation endpoint

How We Integrate
React SPA
  │
  ├── 1. Redirect to ForgeRock /authorize (with PKCE code_challenge)
  │
  ├── 2. User authenticates (ForgeRock login page)
  │
  ├── 3. Redirect back with authorization_code
  │
  ├── 4. POST /token (code + codeverifier) → accesstoken + refreshtoken + idtoken
  │
  └── 5. All API calls: Authorization: Bearer 

JWT Structure (What ForgeRock Returns)
{
  "sub": "john.smith@verizon.com",
  "iss": "https://sso.verizon.com/openam/oauth2",
  "aud": "minerva-spa",
  "exp": 1712700000,
  "iat": 1712696400,
  "tenant_id": "vz-network-eng",

Our Spring Security Integration
- All 6 internal services validate JWTs locally — no call back to ForgeRock per request
- JWKS public keys cached at startup, refreshed every 5 minutes
- JWT validation: signature (RS256), expiration, issuer, audience
- Roles extracted from roles[] claim → Spring GrantedAuthority
- Tenant extracted from tenant_id claim → TenantContext ThreadLocal

SQL Validation (On Config Save) — Production Guard

When a CONFIGURATOR saves a chart/grid/report SQL:

1. Parse — Verify it's a SELECT statement (no INSERT/UPDATE/DELETE/DROP). Uses a lightweight SQL parser.
2. Parameterize — Verify all ${filter_name} placeholders match defined filters
3. BigQuery Dry-Run — JobConfigurationQuery.setDryRun(true) → validates syntax, checks column existence, returns estimated bytes scanned
4. Scan Estimate Warning — If estimated scan > 10 GB, return a warning (not a block) to the CONFIGURATOR
5. Save — Store validated SQL in PostgreSQL

// SQL validation on save
public SqlValidationResult validateSql(String sql, String tenantId) {
    // Step 1: SELECT-only check
    if (!sqlParser.isSelectOnly(sql)) {
        return SqlValidationResult.rejected("Only SELECT statements allowed");
    }

    // Step 2: BigQuery dry-run
    QueryJobConfiguration dryRunConfig = QueryJobConfiguration.newBuilder(sql)
        .setDryRun(true)
        .setUseQueryCache(false)
        .build();

    Job dryRunJob = bigQuery.create(JobInfo.of(dryRunConfig));
    long estimatedBytes = dryRunJob.getStatistics().getQuery().getTotalBytesProcessed();

    // Step 3: Scan estimate warning
    if (estimatedBytes > 10L  1024  1024 * 1024) { // 10 GB
        return SqlValidationResult.warning(
            "Query will scan ~" + (estimatedBytes / 1073741_824) + " GB. Consider adding partition filters."
        );
    }

    return SqlValidationResult.valid(estimatedBytes);
}

Service 3: Query Execution Service
----------------------------------

Owner: Our team  
Purpose: Execute configured SQL against BigQuery, cache results, enforce limits

Why a Separate Service?
- Single responsibility: Dashboard Service owns config, Query Execution owns data retrieval
- Cost control: Centralized BigQuery quota management, rate limiting, audit logging
- Caching: Results cached in Redis — same query + same filters = cache hit
- Isolation: If BigQuery has issues, Dashboard Service (config) still works

Key APIs
POST   /api/query/execute                     → execute SQL with filter params
POST   /api/query/execute-batch               → execute multiple queries (chart + grid in parallel)
GET    /api/query/filters/{filterId}/options   → run optionsSql against PostgreSQL
GET    /api/query/cache/stats                  → cache hit/miss rates (PLATFORM_ADMIN)
POST   /api/query/cache/invalidate             → manual cache invalidation (PLATFORM_ADMIN)

Query Execution Flow (with Production Guards)

Request: { dashboardId, chartId, filters: { region: "northeast", technology: ["5G-NR"] } }
    │
    ├── 1. Rate Limit Check (30 req/min per user via Redis sliding window)
    │
    ├── 2. Lookup chart config from Dashboard Service (inter-service call with JWT forwarding)
    │
    ├── 3. Build Cache Key: SHA256(tenantId + dashboardId + chartId + sortedFilterValues)
    │
    ├── 4. Redis Cache Check → HIT? Return cached result
    │
    ├── 5. MISS → Parameter Binding (replace ${region} with parameterized value)
    │
    ├── 6. Execute against BigQuery:
    │       - maximumBytesBilled: 50 GB (safety cap)
    │       - timeoutMs: 60,000 (60 seconds)
    │       - priority: INTERACTIVE
    │
    ├── 7. Cache Result in Redis (TTL from config, default 10 min)
    │
    ├── 8. Write Audit Log → queryexecutionlog table
    │       (user, dashboard, query hash, bytes scanned, duration, cost estimate)
    │
    └── 9. Return result to caller

Filter Options (Against PostgreSQL, NOT BigQuery)

Filter dropdowns (e.g., "Select Region") query dimension tables in PostgreSQL, not BigQuery:

// Executes optionsSql against read-only PG connection
// PG user is scoped to dim_* tables only (schema-level security)
public List getFilterOptions(String filterId, String tenantId) {
    DashboardFilter filter = dashboardService.getFilter(filterId);
    String sql = filter.getOptionsSql(); // e.g., "SELECT regionid, regionname FROM dimregions WHERE tenantid = :tenantId"

    return readOnlyJdbcTemplate.query(sql,
        Map.of("tenantId", tenantId),
        (rs, i) -> new FilterOption(rs.getString(1), rs.getString(2))
    );
}

Why PostgreSQL for filters? Dimension tables are small (~1K rows), rarely change, and querying BigQuery for a dropdown would be wasteful and slow.

Cache Warm-Up (After Daily Data Refresh)

When the DE team publishes a data-refresh-events Kafka message:
1. Notification Service consumes the event
2. Publishes cache-events → Query Execution Service
3. Query Execution Service:
   - Invalidates all cached results for the refreshed table
   - Re-executes queries for recently-viewed dashboards (last 7 days) with default filters only
   - Batched execution (5 concurrent queries max) to avoid BigQuery quota spike

Service 4: Report Service
-------------------------

Owner: Our team  
Purpose: Async report generation with SAGA pattern, scheduled reports via Quartz

Why SAGA?

Reports can take 30–120 seconds (large BigQuery queries → CSV/Excel generation → S3 upload). Synchronous request-response would timeout. The SAGA pattern orchestrates the multi-step process with compensating actions on failure.

SAGA Flow (Report Generation)

Step 1: QUERY          Step 2: GENERATE         Step 3: UPLOAD          Step 4: NOTIFY
┌─────────────┐       ┌─────────────────┐      ┌──────────────┐       ┌──────────────┐
│ Execute SQL │──OK──►│ Generate CSV/   │─OK──►│ Upload to S3 │──OK──►│ Kafka event  │
│ against     │       │ Excel from      │      │ with signed  │       │ → Notification│
│ BigQuery    │       │ result set      │      │ URL (24h TTL)│       │   Service    │
│             │       │                 │      │              │       │ → WebSocket  │
│ 500K row    │       │                 │      │              │       │   push       │
│ cap enforced│       │                 │      │              │       │              │
└──────┬──────┘       └────────┬────────┘      └──────┬───────┘       └──────────────┘
       │ FAIL                  │ FAIL                  │ FAIL
       ▼                       ▼                       ▼
  Mark FAILED            Delete temp file        Delete S3 object
  Notify user            Mark FAILED             Mark FAILED
                         Notify user             Notify user

Report Status Lifecycle
QUEUED → RUNNING → QUERY_COMPLETE → GENERATING → UPLOADING → COMPLETED
                                                              │
                                             Any step fails → FAILED (with error detail)

Key APIs
POST   /api/reports/generate                  → start async report (returns reportId)
GET    /api/reports/{id}/status               → poll status + download URL when COMPLETED
GET    /api/reports                            → list user's reports (paginated)
GET    /api/reports/{id}/download              → redirect to S3 signed URL
DELETE /api/reports/{id}                       → cancel if QUEUED/RUNNING, delete if COMPLETED

Scheduled Reports (Quartz)

// Quartz job triggered by cron expression stored in report_schedules table
@DisallowConcurrentExecution
public class ScheduledReportJob implements Job {

    @Override
    public void execute(JobExecutionContext context) {
        String scheduleId = context.getJobDetail().getJobDataMap().getString("scheduleId");
        ReportSchedule schedule = reportScheduleRepository.findById(scheduleId);

        // Generate report using same SAGA flow
        String reportId = reportService.generateReport(
            schedule.getReportConfig(),
            schedule.getTenantId(),
            "SYSTEM" // system-triggered, not user-triggered
        );

        // Email notification to recipients
        notificationService.sendReportEmail(
            schedule.getRecipients(),
            reportId,
            schedule.getTimezone() // UTC stored, converted for display
        );
    }
}

Production Guards
- 500K row cap: LIMIT 500001 — if 500,001 rows return, reject with "Report too large, add filters"
- 60-second BigQuery timeout: Prevents runaway queries
- maximumBytesBilled: 100GB: Cost ceiling per report query
- Idempotency: Redis setIfAbsent(reportId, ..., TTL 1h) prevents duplicate generation from Kafka retries
- Cleanup: S3 objects auto-expire after 7 days (S3 lifecycle policy)

Service 5: Map Service
----------------------

Owner: Our team  
Purpose: WMS tile proxy between React/Leaflet and Kinetica

Why a Proxy? Why Not Call Kinetica Directly?

1. Security: CQL_FILTER is constructed server-side from the user's role/tenant/filters — never trusted from the browser
2. Tenant isolation: Server appends AND tenantid = '...' to every CQLFILTER
3. Credential hiding: Kinetica connection details never exposed to frontend
4. Caching headers: We control Cache-Control per layer type

WebSocket Architecture (Multi-Pod)

Browser 1 ──── Pod A (Notification Service)
                    │
Browser 2 ──── Pod B (Notification Service)    ← Redis Pub/Sub bridges pods
                    │
Browser 3 ──── Pod A (Notification Service)

- STOMP over WebSocket with SockJS fallback
- Redis Pub/Sub for cross-pod message delivery (user on Pod A, event consumed on Pod B)
- ChannelInterceptor validates JWT + tenant + role on every SUBSCRIBE

Subscribe Auth (Production Guard)

@Override
public Message preSend(Message message, MessageChannel channel) {
    StompHeaderAccessor accessor = StompHeaderAccessor.wrap(message);

    if (StompCommand.SUBSCRIBE.equals(accessor.getCommand())) {
        String destination = accessor.getDestination();
        // e.g., /topic/tenant/vz-network-eng/dashboard/dash-rf-coverage

        String token = accessor.getFirstNativeHeader("Authorization");
        Claims claims = jwtValidator.validate(token);

        String tenantId = claims.get("tenant_id", String.class);
        List roles = claims.get("roles", List.class);

        // Verify tenant matches subscription channel
        if (!destination.contains("/tenant/" + tenantId)) {
            throw new AccessDeniedException("Cross-tenant subscription denied");
        }

        // Verify role has access to this dashboard
        String dashboardId = extractDashboardId(destination);
        if (!accessService.canView(dashboardId, tenantId, roles)) {
            throw new AccessDeniedException("Insufficient role for this dashboard");
        }
    }
    return message;
}

Cost Dashboard (From queryexecutionlog)

-- Top 10 most expensive dashboards this month
SELECT d.name, d.department,
       COUNT(*) as query_count,
       SUM(qel.bytesscanned) as totalbytes,
       SUM(qel.estimatedcostusd) as total_cost
FROM queryexecutionlog qel
JOIN dashboards d ON qel.dashboard_id = d.id
WHERE qel.executedat >= DATETRUNC('month', CURRENT_DATE)
GROUP BY d.name, d.department
ORDER BY total_cost DESC
LIMIT 10;

Design Decision Matrix (Interview-Ready)
----------------------------------------

| Decision | Why | Alternatives Considered |
|----------|-----|------------------------|
| Config-driven (no-code) | 30-min dashboard delivery vs 2-week dev cycle; 5 departments need different views | Traditional coded dashboards, BI tools (Looker/Tableau) |
| PostgreSQL for config | Relational integrity for dashboard→filter→chart relationships; ACID for config changes | MongoDB (flexible schema but no FK constraints), BigQuery (overkill for config) |
| BigQuery for analytics | Verizon DE team already loads data there; serverless, scales to PB, cost-per-query model | Snowflake (similar but Verizon standardized on GCP for data), Redshift (AWS but cross-cloud latency) |
| Kinetica for maps | GPU-accelerated WMS server-side tile rendering; no GeoJSON transfer to browser | PostGIS (CPU-based, slower for large datasets), Mapbox (SaaS, data sovereignty concerns) |
| Separate Query Execution Service | Centralized BigQuery cost control, rate limiting, caching; isolation from config service | Queries in Dashboard Service (simpler but no isolation, harder to rate-limit) |
| SAGA for reports | Reports take 30–120s; synchronous would timeout; need compensating actions on failure | Simple async with polling (no compensation), queued jobs (no orchestration visibility) |
| Quartz for scheduling | Spring-native, persistent job store in PostgreSQL, cluster-safe, cron expressions | Spring @Scheduled (no persistence, no cluster awareness), external scheduler (over-engineering) |
| Redis for caching | Sub-ms reads; dual-purpose: query result cache + WebSocket pub/sub + JWT blacklist | Caffeine (local only, no cross-pod), Memcached (no pub/sub) |
| Kafka for events | DE team already publishes data-refresh events; we needed guaranteed delivery + DLT | RabbitMQ (simpler but no built-in DLT pattern), SQS (AWS-only, no topic fan-out) |
| ForgeRock (not custom auth) | Verizon enterprise standard; SSO across all internal tools; we don't own identity | Keycloak (self-hosted, more work), Auth0 (SaaS, doesn't meet Verizon enterprise policy) |
| ArgoCD GitOps | Declarative deployments; git as source of truth; automatic drift detection | Helm install via CI (imperative, no drift detection), Spinnaker (heavier, more complex) |

Scaling Strategy
----------------

Horizontal Scaling (HPA)

| Service | Scale Trigger | Min/Max Pods | Why |
|---------|--------------|-------------|-----|
| Dashboard Service | CPU > 70% | 2 / 6 | Config reads are lightweight |
| Query Execution Service | CPU > 60% OR queue depth | 3 / 10 | BigQuery calls are the bottleneck |
| Report Service | Queue depth | 2 / 8 | Reports are batch-heavy |
| Map Service | CPU > 70% | 2 / 6 | WMS proxying is I/O-bound |
| Notification Service | WebSocket connections | 2 / 6 | Connection count matters more than CPU |
| Admin Service | CPU > 70% | 2 / 4 | Low traffic, admin-only |

What Scales and What Doesn't

- BigQuery: Auto-scales (serverless) — but we cap cost with maximumBytesBilled
- PostgreSQL: Single primary + read replica — config reads go to replica, writes to primary
- Redis: Cluster mode with 3 shards — cache + pub/sub + JWT blacklist
- Kafka: 3 brokers, partition-per-consumer for parallel consumption
- Kinetica: Managed by Verizon infra team — we just call the WMS endpoint
