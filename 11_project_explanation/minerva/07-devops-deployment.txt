Dockerfile (Multi-Stage)

STAGE 1: BUILD
==============
FROM eclipse-temurin:17-jdk-alpine AS builder
ARG JAR_FILE
WORKDIR /app
COPY ${JAR_FILE} app.jar
RUN java -Djarmode=layertools -jar app.jar extract

STAGE 2: RUNTIME
================
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app

SECURITY: NON-ROOT USER
=======================
RUN addgroup -S minerva && adduser -S minerva -G minerva
USER minerva

COPY LAYERS IN ORDER OF CHANGE FREQUENCY (LEAST TO MOST)
========================================================
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD wget -qO- http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", \
    "-XX:MaxRAMPercentage=75.0", \
    "-XX:+UseG1GC", \
    "-Djava.security.egd=file:/dev/urandom", \
    "org.springframework.boot.loader.launch.JarLauncher"]

Key points:
- Multi-stage build: Build layer has JDK, runtime layer has JRE only (smaller image ~200MB vs ~400MB)
- Layered extraction: Spring Boot layers ordered by change frequency → Docker cache optimization
- Non-root user: minerva user, not root
- MaxRAMPercentage=75%: Container-aware memory — uses 75% of the container's memory limit

ArgoCD GitOps
-------------

How It Works

Developer pushes code
        │
        ▼
GitLab CI builds + tests + pushes Docker image to ECR
        │
        ▼
GitLab CI updates image tag in k8s-manifests repo
        │
        ▼
ArgoCD watches k8s-manifests repo (polling every 3 min)
        │
        ▼
ArgoCD detects drift between repo and cluster
        │
        ▼
ArgoCD syncs: applies Helm chart with new image tag to EKS
        │
        ▼
EKS performs rolling update (zero downtime)

ArgoCD Application Definition

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: dashboard-service
  namespace: argocd
spec:
  project: minerva
  source:
    repoURL: https://gitlab.verizon.com/minerva/k8s-manifests.git
    targetRevision: main
    path: production/dashboard-service
    helm:
      valueFiles:
        - values.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: minerva
  syncPolicy:
    automated:
      prune: true      # Remove resources no longer in git
      selfHeal: true    # Revert manual changes to match git
    syncOptions:
      - CreateNamespace=true

Q: "Why ArgoCD and not just helm install from CI?"

"Three reasons: (1) Git as source of truth — every deployment is a git commit, fully auditable. (2) Drift detection — if someone manually changes a K8s resource, ArgoCD detects the drift and reverts it. (3) Separation of concerns — CI builds and pushes images, ArgoCD handles deployment. No kubectl credentials in CI pipelines."

  labels:

HPA (Horizontal Pod Autoscaler)

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ .Values.name }}-hpa
  namespace: minerva
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ .Values.name }}
  minReplicas: {{ .Values.replicas.min }}
  maxReplicas: {{ .Values.replicas.max }}
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.scaling.cpuThreshold }}
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # Wait 60s before scaling up
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300   # Wait 5 min before scaling down
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120

IRSA (IAM Roles for Service Accounts)

Each service gets its own K8s ServiceAccount linked to an AWS IAM role via IRSA — no shared credentials, no access keys in pods.

// Structured JSON logging with MDC for tracing
@Slf4j
@RestController
public class QueryController {

    @PostMapping("/api/query/execute")
    public ResponseEntity execute(@RequestBody QueryRequest request,
                                                @AuthenticationPrincipal Jwt jwt) {
        MDC.put("tenantId", jwt.getClaimAsString("tenant_id"));
        MDC.put("userId", jwt.getSubject());
        MDC.put("dashboardId", request.getDashboardId());
        MDC.put("traceId", UUID.randomUUID().toString());

        try {
            log.info("Executing query for chart={}", request.getChartId());
            QueryResult result = queryService.execute(request);
            log.info("Query completed: cacheHit={}, durationMs={}, bytesScanned={}",
                result.isCacheHit(), result.getDurationMs(), result.getBytesScanned());
            return ResponseEntity.ok(result);
        } finally {
            MDC.clear();
        }
    }
}

Q&A Bank (DevOps)
-----------------

Q: "How do you handle zero-downtime deployments?"
"Rolling updates with maxUnavailable: 0 and maxSurge: 1. A new pod starts, passes readiness probe (health check on /actuator/health/readiness), then an old pod is terminated. Users never see downtime. For database migrations, we use backward-compatible Flyway migrations — add new columns before removing old ones, never rename in-place."

Q: "How do you manage secrets?"
"Kubernetes Secrets for database passwords and API keys, referenced as environment variables in pod specs. In production, secrets are managed through AWS Secrets Manager with External Secrets Operator syncing them to K8s Secrets. No secrets in git, no secrets in Docker images."

Q: "What's your rollback strategy?"
"Since ArgoCD uses git as source of truth, rollback = git revert on the k8s-manifests repo. ArgoCD detects the change and syncs the previous image tag. Takes about 2-3 minutes. We also keep the last 10 image tags in ECR for quick rollbacks."

Q: "How do you handle cross-cloud networking (AWS EKS → GCP BigQuery)?"
"We use GCP service account keys stored as K8s Secrets for BigQuery authentication. The traffic goes over the public internet (HTTPS/TLS). The added latency (~20-50ms per request vs ~5ms for same-cloud) is mitigated by aggressive Redis caching. Long-term, we're evaluating GCP Workload Identity Federation to eliminate the service account key."
