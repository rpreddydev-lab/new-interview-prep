Dockerfile (Multi-Stage)

STAGE 1: BUILD
==============
FROM eclipse-temurin:17-jdk-alpine AS builder
ARG JAR_FILE
WORKDIR /app
COPY ${JAR_FILE} app.jar
RUN java -Djarmode=layertools -jar app.jar extract

STAGE 2: RUNTIME
================
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app

SECURITY: NON-ROOT USER
=======================
RUN addgroup -S minerva && adduser -S minerva -G minerva
USER minerva

COPY LAYERS IN ORDER OF CHANGE FREQUENCY (LEAST TO MOST)
========================================================
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD wget -qO- http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", \
    "-XX:MaxRAMPercentage=75.0", \
    "-XX:+UseG1GC", \
    "-Djava.security.egd=file:/dev/urandom", \
    "org.springframework.boot.loader.launch.JarLauncher"]

Key points:
- Multi-stage build: Build layer has JDK, runtime layer has JRE only (smaller image ~200MB vs ~400MB)
- Layered extraction: Spring Boot layers ordered by change frequency → Docker cache optimization
- Non-root user: minerva user, not root
- MaxRAMPercentage=75%: Container-aware memory — uses 75% of the container's memory limit

ArgoCD GitOps
-------------

How It Works

Developer pushes code
        │
        ▼
GitLab CI builds + tests + pushes Docker image to ECR
        │
        ▼
GitLab CI updates image tag in k8s-manifests repo
        │
        ▼
ArgoCD watches k8s-manifests repo (polling every 3 min)
        │
        ▼
ArgoCD detects drift between repo and cluster
        │
        ▼
ArgoCD syncs: applies Helm chart with new image tag to EKS
        │
        ▼
EKS performs rolling update (zero downtime)

ArgoCD Application Definition

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: dashboard-service
  namespace: argocd
spec:
  project: minerva
  source:
    repoURL: https://gitlab.verizon.com/minerva/k8s-manifests.git
    targetRevision: main
    path: production/dashboard-service
    helm:
      valueFiles:
        - values.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: minerva
  syncPolicy:
    automated:
      prune: true      # Remove resources no longer in git
      selfHeal: true    # Revert manual changes to match git
    syncOptions:
      - CreateNamespace=true

Q: "Why ArgoCD and not just helm install from CI?"

"Three reasons: (1) Git as source of truth — every deployment is a git commit, fully auditable. (2) Drift detection — if someone manually changes a K8s resource, ArgoCD detects the drift and reverts it. (3) Separation of concerns — CI builds and pushes images, ArgoCD handles deployment. No kubectl credentials in CI pipelines."

Q&A Bank (DevOps)
-----------------

Q: "How do you handle zero-downtime deployments?"
"Rolling updates with maxUnavailable: 0 and maxSurge: 1. A new pod starts, passes readiness probe (health check on /actuator/health/readiness), then an old pod is terminated. Users never see downtime. For database migrations, we use backward-compatible Flyway migrations — add new columns before removing old ones, never rename in-place."

Q: "How do you manage secrets?"
"Kubernetes Secrets for database passwords and API keys, referenced as environment variables in pod specs. In production, secrets are managed through AWS Secrets Manager with External Secrets Operator syncing them to K8s Secrets. No secrets in git, no secrets in Docker images."

Q: "What's your rollback strategy?"
"Since ArgoCD uses git as source of truth, rollback = git revert on the k8s-manifests repo. ArgoCD detects the change and syncs the previous image tag. Takes about 2-3 minutes. We also keep the last 10 image tags in ECR for quick rollbacks."

Q: "How do you handle cross-cloud networking (AWS EKS → GCP BigQuery)?"
"We use GCP service account keys stored as K8s Secrets for BigQuery authentication. The traffic goes over the public internet (HTTPS/TLS). The added latency (~20-50ms per request vs ~5ms for same-cloud) is mitigated by aggressive Redis caching. Long-term, we're evaluating GCP Workload Identity Federation to eliminate the service account key."

Custom Metrics Implementation

@Component
@RequiredArgsConstructor
public class BigQueryMetrics {

    private final MeterRegistry meterRegistry;

    public void recordQuery(String dashboardId, boolean cacheHit, long durationMs, long bytesScanned) {
        Timer.builder("bigquery.query.duration")
            .tag("dashboard_id", dashboardId)
            .tag("cache_hit", String.valueOf(cacheHit))
            .register(meterRegistry)
            .record(durationMs, TimeUnit.MILLISECONDS);

        if (!cacheHit) {
            meterRegistry.counter("bigquery.bytes.scanned",
                "dashboard_id", dashboardId)
                .increment(bytesScanned);
        }
    }

    public void recordError(String errorType) {
        meterRegistry.counter("bigquery.query.errors",
            "error_type", errorType)
            .increment();
    }
}

Sample Log Query (CloudWatch Logs Insights)

-- Find all queries for a specific user in the last hour
fields @timestamp, @message
| filter tenantId = "vz-network-eng" and userId = "john.smith@verizon.com"
| sort @timestamp desc
| limit 50

-- Find slow BigQuery queries (> 3 seconds)
fields @timestamp, dashboardId, userId, durationMs, bytesScanned
| filter message like /Query completed/ and durationMs > 3000
| sort durationMs desc

-- Trace a request across services by traceId
fields @timestamp, service, @message
| filter traceId = "abc-123-def"
| sort @timestamp asc

SLIs and SLOs

| SLI (What We Measure) | SLO (Target) | How We Measure | Alert Threshold |
|----------------------|-------------|----------------|------------------|
| Dashboard load latency (p95) | < 2 seconds | Prometheus histogram: bigquery_query_duration_seconds | P1: > 5s for 5 min |
| Dashboard availability | 99.5% uptime | Synthetic probe hitting /api/dashboards every 60s | P1: 3 consecutive failures |
| Report generation success rate | > 99% | report_saga_step_status counter | P2: < 95% over 1 hour |
| Cache hit ratio | > 50% | redis_cache_hit_ratio gauge | P3: < 30% for 30 min |
| BigQuery error rate | < 1% | bigquery_query_errors_total / total queries | P2: > 5% for 10 min |
| WebSocket delivery rate | > 99% | websocket notifications sent vs acknowledged | P3: < 95% for 15 min |
| API error rate (5xx) | < 0.5% | http_server_requests_seconds_count with status=5xx | P2: > 2% for 5 min |
| Kafka consumer lag | < 1000 messages | kafka_consumer_lag gauge per topic | P2: > 5000 for 10 min |

Alert Severity and Routing

| Severity | Criteria | Notification | Response Time |
|----------|----------|-------------|----------------|
| P1 — Critical | Data unavailable, auth down, all dashboards failing | PagerDuty (phone call) + Slack #minerva-incidents | 15 min |
| P2 — Degraded | Elevated error rate, slow queries, Kafka lag, partial feature outage | PagerDuty (push notification) + Slack | 1 hour |
| P3 — Warning | Cache hit ratio drop, single dashboard issue, cosmetic errors | Slack #minerva-alerts | Next business day |
| P4 — Info | Cost threshold approaching, scheduled maintenance | Email digest | Weekly review |

Grafana Alert Rule Example

// Alert: BigQuery circuit breaker opened
alert: BigQueryCircuitBreakerOpen
expr: resilience4j_circuitbreaker_state{name="bigquery"} == 1  // 1 = OPEN
for: 1m
labels:
  severity: P1
  team: minerva
annotations:
  summary: "BigQuery circuit breaker OPEN on {{ $labels.instance }}"
  description: "BigQuery calls are failing. Circuit breaker opened. Dashboard queries will return stale cached data or 503."
  runbook: "https://wiki.verizon.com/minerva/runbooks/bigquery-circuit-breaker"

Incident Response Runbook (Abbreviated)

1. DETECT: Grafana alert fires → PagerDuty pages on-call engineer
2. ACKNOWLEDGE: Engineer acknowledges in PagerDuty (SLA: 15 min for P1)
3. ASSESS: Check Grafana Service Health dashboard → identify affected service
4. MITIGATE:
   - BigQuery down → Circuit breaker auto-opens, stale cache serves data
   - Redis down → Graceful degradation, queries go direct to DB/BigQuery
   - Kafka lag → Check consumer health, restart consumer group if stuck
   - Pod crash loop → Check logs, rollback to previous image via ArgoCD
5. COMMUNICATE: Post in Slack #minerva-incidents with status + ETA
6. RESOLVE: Fix root cause, verify via Grafana, close PagerDuty incident
7. POST-MORTEM: Blameless review within 48 hours, action items in Jira

Q&A Bank (Observability)
------------------------

Q: "What metrics do you track?"
"We track four categories: (1) Business metrics — dashboard views, report generations, active users by role. (2) Performance metrics — BigQuery query duration (p50/p95/p99), cache hit ratio, API latency. (3) Cost metrics — BigQuery bytes scanned per dashboard, estimated daily cost. (4) Reliability metrics — error rates, circuit breaker state, Kafka consumer lag, SAGA step success rates. All exposed via Micrometer → Prometheus → Grafana."

Q: "How do you debug a slow dashboard?"
"Start with the traceId from the user's request. Search CloudWatch Logs to trace the request across services. Check if it was a cache miss (bigquery.query.duration with cache_hit=false). Look at bytesScanned — if it's high, the configured SQL may need partition filters. Check the BigQuery Cost dashboard in Grafana for that specific dashboard_id. If it's a pattern, talk to the CONFIGURATOR about query optimization."

Q: "What would you improve about your observability?"
"Three things: (1) Adopt OpenTelemetry for automatic distributed tracing — our current MDC-based traceId doesn't propagate through Kafka events automatically. (2) Add synthetic monitoring — automated browser tests that exercise full dashboard load flows. (3) Add SLO burn rate alerts instead of threshold alerts — 'we're burning through our error budget 10x faster than sustainable' is more actionable than 'error rate > 2%'."
