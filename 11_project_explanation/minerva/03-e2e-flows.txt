03 — END-TO-END FLOWS
=====================

What to use this for: "Walk me through what happens when…" questions. Each flow is production-grade with security, caching, and error handling baked in.

Flow 1: Login (ForgeRock SSO + PKCE)
------------------------------------

Trigger: User opens Minerva in their browser

Browser                        React SPA                    ForgeRock SSO                 Any Backend Service
   │                              │                              │                              │
   ├── Navigate to minerva.vz ──►│                              │                              │
   │                              │                              │                              │
   │                  No token in localStorage                   │                              │
   │                              │                              │                              │
   │                              ├── Generate PKCE:             │                              │
   │                              │   code_verifier (random)     │                              │
   │                              │   code_challenge = SHA256(v) │                              │
   │                              │                              │                              │
   │◄── Redirect ────────────────┤                              │                              │
   │    302 → ForgeRock /authorize?                              │                              │
   │    response_type=code                                       │                              │
   │    client_id=minerva-spa                                    │                              │
   │    redirect_uri=https://minerva.vz/callback                 │                              │
   │    scope=openid profile email                               │                              │
   │    code_challenge=...                                       │                              │
   │    codechallengemethod=S256                               │                              │
   │                              │                              │                              │
   ├── ForgeRock login page ─────────────────────────────────────►                              │
   │   User enters Verizon SSO credentials                       │                              │
   │                              │                              │                              │
   │◄── Redirect back ──────────────────────────────────────────┤                              │
   │    302 → minerva.vz/callback?code=AUTH_CODE                 │                              │
   │                              │                              │                              │
   │                              ├── POST /token ──────────────►│                              │
   │                              │   granttype=authorizationcode                             │
   │                              │   code=AUTH_CODE              │                              │
   │                              │   code_verifier=...          │                              │
   │                              │   redirect_uri=...           │                              │
   │                              │                              │                              │
   │                              │◄── 200 ─────────────────────┤                              │
   │                              │   {                          │                              │
   │                              │     access_token: "eyJ...",  │                              │
   │                              │     refresh_token: "eyJ...", │                              │
   │                              │     id_token: "eyJ...",      │                              │
   │                              │     expires_in: 3600         │                              │
   │                              │   }                          │                              │
   │                              │                              │                              │
   │                              ├── Store tokens in memory     │                              │
   │                              │   (access_token, refresh)    │                              │

   │                              │                              │                              │

   │    Show sidebar based on roles                              │                              │

Key interview points:
- PKCE because SPA is a public client — no client_secret
- Tokens in memory, NOT localStorage (XSS protection)
- id_token decoded client-side for user display name, role-based UI rendering
- access_token sent as Authorization: Bearer to all backend calls

Flow 2: Silent Token Refresh
----------------------------

Trigger: access_token expires (every 60 minutes), intercepted by Axios interceptor

React SPA (Axios Interceptor)              ForgeRock SSO
   │                                            │
   ├── API call returns 401 ──────►             │
   │                                            │
   ├── Check: refresh_token exists?             │
   │   YES                                      │
   │                                            │
   ├── POST /token ────────────────────────────►│
   │   granttype=refreshtoken                  │
   │   refresh_token=eyJ...                      │
   │   client_id=minerva-spa                     │
   │                                            │
   │◄── 200 ───────────────────────────────────┤
   │   { access_token: "new...", ... }          │
   │                                            │
   ├── Update tokens in memory                  │
   ├── Retry original failed request            │
   │   with new access_token                    │
   │                                            │
   │   If refresh also fails (403):             │
   │   → Clear all tokens                       │
   │   → Redirect to ForgeRock /authorize       │
   │     (full re-login)                        │

Key interview points:
- Queue concurrent 401s — only one refresh request at a time
- If refresh fails → full re-login (refresh token may be revoked by ForgeRock admin)
- No "remember me" — Verizon security policy requires re-auth after refresh token expiry (8 hours)

   │  │                     │                        │             │           │             │  │
   │  │  STEP 4: NOTIFY     │                        │             │           │             │  │
   │  │                     ├── Publish ─────────────────────────────────────►│             │  │
   │  │                     │   report-events: {jobId, status:COMPLETED,     │             │  │
   │  │                     │                   downloadUrl, userId}          │             │  │
   │  │                     │                        │             │           │             │  │
   │  │                     │                        │             │     ┌─────┤             │  │
   │  │                     │                        │             │     │  Consume          │  │
   │  │                     │                        │             │     └────►│             │  │
   │  │                     │                        │             │           │             │  │
   │  │                     │                        │             │           ├── WebSocket │  │
   │  │                     │                        │             │           │   push to   │  │
   │  │                     │                        │             │           │   user      │  │
   │  └─────────────────────────────────────────────────────────────────────────────────────┘  │
   │                        │                        │             │           │                │
   │◄── WebSocket: "Report ready! [Download]" ─────────────────────────────────────────────────┤
   │                        │                        │             │           │                │
   ├── GET /api/reports/    │                        │             │           │                │
   │   rpt-123/download ───►│                        │             │           │                │
   │                        │                        │             │           │                │
   │◄── 302 → S3 signed URL┤                        │             │           │                │

SAGA Compensation (on failure at any step):
- Step 1 fails (BigQuery timeout) → Mark FAILED, notify user "Query too complex"
- Step 2 fails (OOM generating file) → Delete temp file, mark FAILED, notify user
- Step 3 fails (S3 unavailable) → Delete temp file (no S3 object exists yet), mark FAILED, retry up to 3x
- Step 4 fails (Kafka down) → Report is COMPLETED (S3 object exists) but notification delayed (eventual consistency)

Key interview points:
- 500K row cap prevents massive exports that crash the pod
- Idempotent: Redis setIfAbsent(jobId) prevents duplicate report generation from Kafka retries
- S3 lifecycle policy auto-deletes reports after 7 days
- VIEWER role cannot trigger reports (no export permission)

- Quartz uses PostgreSQL as persistent job store — survives pod restarts

- Time zones: cron stored in UTC, display converted to user's timezone in the UI
- Quartz clustered mode: only one pod picks up each job (via DB row lock)

- We DON'T warm all dashboards × all filter combos — only recently-viewed with defaults
- Batched at 5 concurrent to avoid BigQuery quota spike
- Notification to active users → they see "Data updated, click to refresh" banner
- Cache warm-up is fire-and-forget — if it fails, next user request will just be a cache miss

Flow 12: Filter Change → Re-Query
---------------------------------

Trigger: User changes a filter dropdown on an active dashboard

React SPA                                    Query Execution Service
   │                                                │
   ├── User selects "Southeast" in Region filter    │
   │                                                │
   ├── 300ms debounce (FE) ─────────────────────── waits
   │   (prevents rapid-fire on multi-select)        │
   │                                                │
   ├── POST /api/query/execute-batch ──────────────►│
   │   {                                            │
   │     dashboardId: "dash-rf",                    │
   │     filters: { region: "southeast", ... },     │
   │     queries: [                                 │
   │       { chartId: "c1" },                       │
   │       { chartId: "c2" },                       │
   │       { gridId: "g1" }                         │
   │     ]                                          │
   │   }                                            │
   │                                                │
   │                               ┌────────────────┤
   │                               │ Execute all queries in parallel │
   │                               │ (each checks cache independently) │
   │                               │ Rate limit: per-user, per-batch │
   │                               └────────────────┤
   │                                                │
   │◄── 200 ───────────────────────────────────────┤
   │   {                                            │
   │     results: {                                 │
   │       c1: { data: [...], cached: false },      │
   │       c2: { data: [...], cached: true },       │
   │       g1: { data: [...], cached: false }       │
   │     }                                          │
   │   }                                            │
   │                                                │
   ├── Re-render only changed components            │
   │   (React memoization for unchanged data)       │

Key interview points:
- 300ms debounce on frontend — prevents 10 requests when selecting multi-select options
- Batch API — one HTTP call for all charts/grids affected by the filter change
- Parallel execution server-side — queries run concurrently against BigQuery
- Partial cache hits — some queries may be cached (unchanged by this filter), others not
- Map tiles also refresh (Leaflet re-requests with new BBOX, Map Service constructs new CQL_FILTER)

Flow 15: Circuit Breaker (BigQuery Degradation)
-----------------------------------------------

Trigger: BigQuery starts returning errors or timing out

React SPA                   Query Execution Service                    BigQuery
   │                                │                                     │
   ├── POST /api/query/execute ────►│                                     │
   │                                │                                     │
   │                    ┌───────────┤                                     │
   │                    │ Circuit breaker state: CLOSED (normal)          │
   │                    │                                                 │
   │                    │ Execute query ─────────────────────────────────►│
   │                    │                                                 │
   │                    │◄── 500 / Timeout ──────────────────────────────┤
   │                    │                                                 │
   │                    │ Failure count: 1 → 2 → 3 → 4 → 5              │
   │                    │ (threshold: 5 failures in 60 seconds)          │
   │                    │                                                 │
   │                    │ Circuit breaker → OPEN                          │
   │                    └───────────┤                                     │
   │                                │                                     │
   │◄── 503 Service Unavailable ───┤                                     │
   │   {                            │                                     │
   │     error: "Analytics service  │                                     │
   │       temporarily unavailable",│                                     │
   │     retryAfter: 30,           │                                     │
   │     cached: true/false        │                                     │
   │   }                            │                                     │
   │                                │                                     │
   │   React shows:                 │                                     │
   │   - Cached data if available   │                                     │
   │     (with "stale data" badge)  │                                     │
   │   - "Service recovering"       │                                     │
   │     message if no cache        │                                     │
   │                                │                                     │
   │   ──── 30 seconds later ────   │                                     │
   │                                │                                     │
   │                    ┌───────────┤                                     │
   │                    │ Circuit breaker → HALF-OPEN                     │
   │                    │ Allow 1 test request                            │
   │                    │                                                 │
   │                    │ Execute test query ────────────────────────────►│
   │                    │                                                 │
   │                    │◄── 200 OK ─────────────────────────────────────┤
   │                    │                                                 │
   │                    │ Circuit breaker → CLOSED (recovered)           │
   │                    └───────────┤                                     │
   │                                │                                     │
   │   Next request works normally  │                                     │

Key interview points:
- Resilience4j circuit breaker with configurable thresholds
- OPEN state: fast-fail (no BigQuery calls) → returns 503 with retryAfter
- HALF-OPEN: allows one test request to check if BigQuery recovered
- Stale cache serving: If cached data exists, return it with a "stale" flag → React shows data with a warning badge instead of an error screen
- Config reads (Dashboard Service) are unaffected — they don't depend on BigQuery
- Separate circuit breaker per operation: chart queries, report queries, filter options each have their own breaker
