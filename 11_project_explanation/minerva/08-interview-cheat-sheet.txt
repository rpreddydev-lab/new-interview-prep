08 — INTERVIEW CHEAT SHEET
==========================

What to use this for: Quick reference before/during interviews. Pitches, one-liners, STAR stories, rapid-fire answers.

60-Second Pitch (Memorize This)
-------------------------------

"I built Minerva, a configuration-driven analytics platform for Verizon's network engineering organization — about 200 users across RF, Traffic, NOC, Performance, and Executive teams.
The core innovation: instead of coding dashboards, our Analytics Leads define everything through database configuration — filters, charts, grids, map layers, reports — all stored as rows in PostgreSQL. React renders dynamically from that config. Zero deployment for new dashboards — 30 minutes from concept to live.
It's 7 microservices on Spring Boot 3 / Java 17, deployed to AWS EKS via ArgoCD GitOps. Analytics data lives in GCP BigQuery (50M+ rows, loaded daily by the DE team), geospatial tiles rendered by Kinetica's GPU-powered WMS engine, and Kafka handles event-driven flows — daily data refresh, async report generation with SAGA pattern, and real-time WebSocket notifications.
Security is Verizon's ForgeRock SSO with 5 RBAC roles mapped to real job functions — RF Engineers get coverage analysis dashboards, VPs get read-only executive views."

Story 3: Data Refresh & Cache Strategy (Distributed Systems)

S: Daily data refresh at 2 AM ET meant all cached data was stale by morning. First users of the day experienced slow loads (cache miss → BigQuery query → 2-5 seconds per chart).

T: Ensure first-thing-in-the-morning dashboard loads are as fast as cached loads.

A: Designed an event-driven cache warm-up pipeline: (1) DE team publishes data-refresh-events to Kafka when ETL completes. (2) Notification Service consumes the event, pushes WebSocket notification to active users, and publishes cache-events. (3) Query Execution Service consumes cache-events, invalidates stale results, then proactively re-executes queries for recently-viewed dashboards (last 7 days) with default filters only. Limited to 5 concurrent queries to avoid BigQuery quota spike.

R: Morning dashboard loads went from 2-5 seconds to < 1 second for the top 20 most-used dashboards. Users see a "Data updated" banner if they were on the dashboard during refresh.

Story 4: Report Generation Reliability (SAGA Pattern)

S: Report generation was originally synchronous — HTTP request triggered BigQuery query + file generation + S3 upload. Large reports (500K rows) caused HTTP timeouts and left partial files in S3.

T: Make report generation reliable for large datasets with proper error handling and cleanup.

A: Redesigned as a SAGA pattern with 4 steps: (1) Query BigQuery (with 500K row cap + 60s timeout), (2) Generate CSV/Excel (streaming to temp file), (3) Upload to S3 (with signed URL, 24h TTL), (4) Notify user via Kafka → WebSocket. Each step has a compensating action on failure (e.g., delete S3 object if notification fails). Added Redis idempotency keys to prevent duplicate reports from Kafka retries. Built scheduled reports with Quartz for recurring needs (e.g., "Weekly SLA Report every Monday 7 AM").

R: Report generation went from ~30% failure rate to < 1%. S3 cleanup eliminated orphaned files. Scheduled reports reduced ad-hoc report requests by 40%.

Story 5: Security Incident Response (Leadership)

S: During a security audit, we discovered that WebSocket subscriptions weren't validating tenant isolation — any authenticated user could subscribe to any dashboard's notification channel, potentially seeing alert events for dashboards they shouldn't access.

T: Fix the vulnerability immediately and ensure it couldn't happen again.

A: Implemented a STOMP ChannelInterceptor that validates JWT claims on every SUBSCRIBE frame — checks that tenant_id matches the channel path and that the user's role has access to the specific dashboard. Added integration tests specifically for cross-tenant WebSocket scenarios. Conducted a security review across all services for similar gaps. Established a security checklist for all new features.

R: Vulnerability patched within 24 hours of discovery. Zero data exposure confirmed through audit log analysis. Security checklist prevented 3 similar issues in subsequent features.

Story 6: Mentoring Junior Developers (Leadership)

S: Two junior developers joined the team and struggled with the config-driven architecture — they kept trying to write traditional coded dashboards instead of thinking in configuration.

T: Get them productive and aligned with the architecture within their first sprint.

A: Paired with each developer for the first week. Created an internal "Architecture Walkthrough" doc (similar to what these files contain). Assigned them a simple feature: "Add a new filter type (DATE_RANGE)" — which required touching Dashboard Service (config schema), Query Execution Service (parameter binding), and React (filter component). This single feature taught them the full config-driven flow. Established PR review guidelines focused on architectural compliance.

R: Both developers were independently shipping features by sprint 3 (6 weeks). One of them later proposed the cascading filter feature (depends_on field) — proving they'd internalized the config-driven model.

Rapid-Fire Q&A
--------------

Architecture

Q: "Why microservices and not a monolith?"
"Independent scaling — Query Execution Service needs 10 pods during peak hours while Admin Service needs 2. Independent deployment — we deploy Dashboard Service weekly but Report Service only when needed. Independent failure — BigQuery outage doesn't take down config loads."

Q: "What's the most complex part of the system?"
"The SQL validation layer in Dashboard Service. Parsing SQL to ensure it's SELECT-only, validating parameter placeholders match defined filters, running a BigQuery dry-run, and estimating scan cost — all before allowing a CONFIGURATOR to save config. It's the trust boundary between self-service and system safety."

Q: "How do you handle cross-cutting concerns?"
"Spring Security filter chain handles auth/authz uniformly. TenantContext ThreadLocal propagates tenant isolation. Resilience4j circuit breakers wrap all external calls. Micrometer + Prometheus for metrics. MDC for structured logging with traceId propagation."

Data

Q: "What's the most expensive BigQuery query?"
"Full coverage_data scan without partition filters — ~200 GB, costs $1. That's why we validate SQL on save with scan estimates and enforce maximumBytesBilled at runtime."

Q: "How do you handle data consistency between PostgreSQL and Redis cache?"
"Cache-aside pattern with TTL. Write to PostgreSQL, then invalidate Redis cache. TTL provides eventual consistency even if invalidation fails. For config changes, we also publish dashboard-events to Kafka, which triggers cache invalidation across all service instances."

Q: "What if Redis goes down?"
"All operations degrade gracefully — cache misses go directly to PostgreSQL/BigQuery. Rate limiting falls back to a local in-memory counter. WebSocket pub/sub for cross-pod delivery stops, but same-pod connections still work. JWT blacklist checks fail open (accept the token), but JWT expiry still provides a 60-minute upper bound."

Security

Q: "How long does it take to revoke a user's access?"
"Immediate via Redis JWT blacklist. When ForgeRock revokes a token, we add the JWT ID to Redis. All 6 services check the blacklist on every request (~0.5ms overhead). The Redis key auto-expires when the JWT would have expired anyway."

Q: "What's your biggest security concern?"
"SQL injection through the configuration layer. A CONFIGURATOR writes SQL that runs against BigQuery. We mitigate with SELECT-only parsing, parameterized query execution (never string concatenation), and BigQuery's own column/table validation via dry-run."

Behavioral

Q: "Tell me about a time you disagreed with a teammate."
"A senior developer wanted to use MongoDB for config storage because 'dashboard config is flexible and document-like.' I advocated for PostgreSQL because dashboard→filter→chart relationships need referential integrity — you can't have an orphaned chart pointing to a deleted dashboard. We ran a proof-of-concept with both. MongoDB was faster to prototype but we hit data integrity issues within a week. We went with PostgreSQL + JSONB columns for the flexible parts (layout, column config). The teammate agreed once he saw the FK constraint catching a real bug."

Q: "Tell me about a time you had to make a tradeoff."
"Cross-cloud latency. Our services are on AWS EKS but data is in GCP BigQuery. The 'right' architecture would be same-cloud, but the DE team had already invested heavily in GCP data pipelines. Migrating would take months and risk their SLAs. Instead, we accepted the ~30ms latency penalty and invested in aggressive Redis caching. Result: 60% cache hit rate means most users never feel the cross-cloud hop. The cost savings from not migrating the data pipeline far outweighed the minimal latency impact."

Q: "How do you handle production incidents?"
"We follow a structured incident response: (1) Detect via Grafana alerts (PagerDuty integration), (2) Acknowledge and assess severity (P1 = data unavailable, P2 = degraded, P3 = cosmetic), (3) Mitigate first (e.g., circuit breaker auto-opens for BigQuery issues), (4) Root cause analysis using structured logs + audit trail + queryexecutionlog, (5) Post-mortem with blameless review, action items tracked in Jira. Our circuit breaker and stale cache serving handle most P2 incidents automatically."

Story 7: Production Outage — BigQuery Quota Exhaustion (Incident Response)

S: On a Monday morning, all dashboard charts started returning 503 errors. Grafana fired a P1 alert — the BigQuery circuit breaker had opened across all Query Execution Service pods simultaneously. ~200 users were impacted.

T: Restore dashboard functionality immediately, identify root cause, and prevent recurrence.

A: (1) Mitigate first (5 min): Confirmed circuit breaker was open via Actuator endpoint. Checked BigQuery console — our project had exhausted the daily query quota (concurrent query limit hit). A scheduled report cron job had misfired over the weekend, triggering ~500 queued reports simultaneously at 8 AM Monday. Immediately killed the Quartz batch via Admin Service DLT viewer and manually reset the circuit breaker.
(2) Restore (10 min): Circuit breaker transitioned to half-open, let one request through — BigQuery responded normally. Within 2 minutes all pods recovered. Users saw cached data (stale but functional) for charts that had recent cache entries, while fresh queries resumed.
(3) Root cause: A CONFIGURATOR had created a scheduled report with a cron expression that ran every minute instead of every Monday ("* * * * 1" vs "0 8 * * 1"). The Quartz misfire policy was set to FIRE_AND_PROCEED, so 2,880 missed executions (48 hours × 60/hr) all fired at once on Monday startup.
(4) Prevent: Added cron expression validation in Dashboard Service — minimum interval of 1 hour for scheduled reports. Added a Quartz misfire policy override to IGNORE_MISFIRES for reports. Added a concurrent report execution cap (max 5 simultaneous report jobs per tenant). Added a Grafana alert on BigQuery concurrent query count approaching 80% of quota.

R: Total outage was 15 minutes. Zero data loss. Post-mortem led to 4 preventive measures. The cron validation caught 2 similar misconfigurations in the following month. Added the incident to our runbook with step-by-step recovery playbook.

Key interview points:
- Circuit breaker (Resilience4j) contained the blast radius — BigQuery failure didn't crash the services
- Stale cache serving meant some users saw data during the outage (graceful degradation)
- Blameless post-mortem — the CONFIGURATOR wasn't at fault; our system should have validated the cron expression
- Defense in depth: validation + misfire policy + concurrency cap + monitoring alert

Story 8: Redis Cluster Failure — Graceful Degradation Under Dependency Loss

S: During a routine Redis cluster upgrade in our staging environment (which shared infrastructure with production in our early months), a misconfigured rolling restart caused all Redis pods to be unavailable simultaneously for ~8 minutes. This cascaded into production because the Lettuce connection pool exhausted its retry budget and started failing fast. Grafana fired alerts simultaneously for: cache miss rate → 100%, JWT blacklist check failures, WebSocket cross-pod pub/sub broken, and rate limiter returning errors.

T: Restore the system to a functional state immediately, assess what data was exposed or corrupted, and document the failure modes we hadn't properly designed for.

A: (1) Immediate mitigation (2 min): Confirmed Redis was the root cause via Grafana. Rolled back the Redis cluster restart — Redis came back online within 3 minutes. Lettuce connection pools auto-recovered within 30 seconds of Redis availability.
(2) Impact assessment: Cache misses → all API calls fell through to PostgreSQL/BigQuery directly. Slower (2-5s vs <1s), but functionally correct. JWT blacklist failures → we had coded these to fail open (accept the token) to avoid a hard Redis dependency blocking all traffic. That decision proved correct — no users were locked out. Rate limiting fell back to the in-memory counter per pod (not cross-pod), so technically rate limits were enforced per-pod instead of globally for 8 minutes. WebSocket cross-pod delivery stopped, but connections stayed alive — users connected to the same pod still got notifications.
(3) Root cause: The Redis rolling restart config was missing the cluster-require-full-coverage: no flag. With full coverage required (the default), Redis refuses reads/writes when any slot is missing. Our staging/production cluster boundary was also incorrectly configured — a mistake I caught and fixed immediately after this incident by splitting the infrastructure properly.
(4) Fixes shipped: (a) Set cluster-require-full-coverage: no on all Redis clusters so partial availability degrades gracefully instead of failing completely. (b) Added Resilience4j circuit breaker specifically around Redis operations — not just BigQuery. This ensures cache operations fail fast and fall through to the data store rather than blocking. (c) Added a Grafana alert on Redis connection pool saturation at 70% so we catch pressure before it becomes an outage. (d) Documented the fail-open vs fail-closed decision for each Redis use case in the runbook — JWT blacklist is fail-open (availability wins), rate limiting is per-pod fallback (acceptable degradation), WebSocket pub/sub is fail-silent (local pod delivery only).

R: Incident lasted 8 minutes, no data loss, no security exposure. The fail-open JWT blacklist decision, which I had debated at design time, turned out to be the right call — it kept users working during the outage. Post-incident, we properly separated staging and production Redis clusters (they should never have shared infrastructure), and the circuit breaker around Redis has prevented 2 subsequent smaller Redis hiccups from impacting users at all.

Key interview points:
- Fail-open vs. fail-closed is a deliberate security vs. availability tradeoff — not laziness
- Every external dependency needs a circuit breaker, not just the ones you're most worried about
- Shared staging/production infrastructure is a hidden risk that looks fine until it isn't
- Graceful degradation means designing every failure path, not just the happy path

"What Would You Do Differently?" (Pre-Built Answers)
----------------------------------------------------

Q: "If you could start Minerva over, what would you change?"

1. Same-Cloud Architecture
"I'd push harder to keep compute and data in the same cloud. Our AWS EKS → GCP BigQuery cross-cloud hop adds 20-50ms latency per query. We compensate with aggressive Redis caching (60% hit rate), but same-cloud would give us sub-5ms data access and eliminate the GCP service account key management overhead. The DE team's investment in GCP pipelines was the reason we didn't migrate, but in hindsight, the long-term operational cost of cross-cloud exceeds the one-time migration effort."

2. Contract Testing Between Services
"I'd add Pact contract tests between React ↔ Backend and between microservices. Right now, we catch integration issues in staging, but contract tests would shift that left to PR time. We had 2-3 incidents where a Dashboard Service API response shape change broke the React SPA because the frontend team didn't know about the change until staging deployment."

3. Event Sourcing for Configuration Changes
"Config changes are currently CRUD operations with audit logging after the fact. If I started over, I'd use event sourcing for the configuration layer — every config change as an immutable event. This would give us built-in audit trail, config versioning (rollback to any point in time), and the ability to replay config state. The current system has audit logs but can't reconstruct 'what did this dashboard look like 3 weeks ago?'"

4. OpenTelemetry from Day One
"We added observability incrementally — Micrometer metrics, then MDC logging, then manual traceId propagation. If I started fresh, I'd adopt OpenTelemetry from day one for unified traces, metrics, and logs with automatic context propagation. Our current traceId is manually set in MDC and doesn't propagate through Kafka events, which makes debugging async flows harder than it should be."

5. Feature Flags for Configuration
"Dashboard configurations go live the moment a CONFIGURATOR saves them. I'd add a feature flag layer — save config as 'draft', preview in staging mode, then promote to 'live'. We compensate with SQL dry-run validation, but there's no way to preview a dashboard before it's visible to all users with access."

Technology Defense (Why We Chose X)
-----------------------------------

| "Why not X?" | Our Answer |
|-------------|-----------|
| Why not Tableau/Looker? | Config-driven means we own the experience — custom RBAC, Verizon SSO integration, embedded in the workflow. BI tools are generic. Plus, Kinetica WMS integration wouldn't work with off-the-shelf BI tools. |
| Why not GraphQL? | Our queries are config-driven SQL, not flexible client queries. REST fits — one endpoint per operation, well-defined payloads. GraphQL's flexibility would bypass our SQL validation layer. |
| Why not gRPC for service-to-service? | Most inter-service calls are Kafka (async). The few REST calls are simple CRUD. gRPC's benefits (streaming, binary protocol) don't justify the complexity for our use case. |
| Why not AWS-native (SQS, DynamoDB)? | Kafka was already in place (DE team). PostgreSQL gives us relational integrity that DynamoDB can't. We do use AWS-native for what makes sense: EKS, ECR, S3, CloudWatch. |
| Why not Next.js/SSR? | Our React SPA talks to 7 backend services via REST. Server-side rendering would add a Node.js layer between React and Spring Boot with no benefit — our data isn't SEO-relevant, and the dashboard is an authenticated internal tool. |
