1. WHAT IS KAFKA CONNECT?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka Connect is a scalable, fault-tolerant framework for streaming data BETWEEN
Kafka and external systems (databases, object stores, search engines, etc.)
without writing custom producer/consumer code.

  External System → [Source Connector] → Kafka Topic
  Kafka Topic     → [Sink Connector]   → External System

Key traits:
  - No-code / low-code: configure connectors with JSON, no Java needed for most cases
  - Library of pre-built connectors (Confluent Hub: 200+ connectors)
  - Scalable: runs as a cluster (distributed mode)
  - Fault-tolerant: connector tasks are redistributed on failure
  - REST API: manage connectors dynamically (create, pause, resume, delete)

2. SOURCE CONNECTORS vs SINK CONNECTORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SOURCE CONNECTOR:
  - Pulls data from an external system and writes to Kafka topics
  - Examples:
      JDBC Source: polls a relational database and streams row changes
      Debezium: reads MySQL/Postgres/MongoDB CDC (change data capture) via binlog
      S3 Source: reads files from S3 into Kafka
      HTTP Source: polls an HTTP endpoint
  
SINK CONNECTOR:
  - Reads from Kafka topics and writes to an external system
  - Examples:
      JDBC Sink: writes records to a relational database
      Elasticsearch Sink: indexes records in Elasticsearch
      S3 Sink: archives records to S3 (partitioned by date/hour)
      BigQuery Sink: streams into Google BigQuery
      HTTP Sink: calls REST API with record payloads

3. CONNECT ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌─────────────────────────────────────────────────────────────┐
  │                  Kafka Connect Cluster                      │
  │  ┌────────────┐  ┌────────────┐  ┌────────────┐            │
  │  │  Worker 1  │  │  Worker 2  │  │  Worker 3  │            │
  │  │  task 0    │  │  task 1    │  │  task 2    │            │
  │  └────────────┘  └────────────┘  └────────────┘            │
  │         │               │               │                  │
  │  ┌──────────────────────────────────────────────────────┐  │
  │  │            Internal Kafka Topics                     │  │
  │  │  connect-configs    (connector/task configurations)  │  │
  │  │  connect-offsets    (source connector positions)     │  │
  │  │  connect-status     (connector/task status)          │  │
  │  └──────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────┘

Components:
  - WORKER: JVM process that runs connector tasks. Handles REST API, config storage.
  - CONNECTOR: Logical definition (what to connect to, how to configure it)
  - TASK: Actual unit of work (a connector spawns N tasks for parallelism)
  - CONVERTER: Serializes/deserializes data (JSON, Avro, Protobuf, String)
  - TRANSFORM (SMT): Single Message Transform — applies lightweight transformations inline

Deployment modes:
  - STANDALONE: single worker, no fault tolerance; for development/testing
  - DISTRIBUTED: multiple workers, fault-tolerant; for production

Internal topics (created automatically):
  connect-configs    → stores connector configs (compacted)
  connect-offsets    → stores source connector positions (compacted)
  connect-status     → stores connector/task status (compacted)

4. CONNECTOR CONFIGURATION (JDBC EXAMPLE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Creating a connector via REST API:

  POST /connectors
  {
    "name": "orders-jdbc-source",
    "config": {
      "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
      "connection.url": "jdbc:postgresql://db:5432/mydb",
      "connection.user": "kafka_user",
      "connection.password": "secret",
      "mode": "timestamp+incrementing",
      "timestamp.column.name": "updated_at",
      "incrementing.column.name": "id",
      "table.whitelist": "orders",
      "topic.prefix": "db.",
      "poll.interval.ms": "1000",
      "tasks.max": "3"
    }
  }

  # This creates topic: db.orders

Sink example (S3):
  {
    "name": "orders-s3-sink",
    "config": {
      "connector.class": "io.confluent.connect.s3.S3SinkConnector",
      "tasks.max": "4",
      "topics": "orders",
      "s3.region": "us-east-1",
      "s3.bucket.name": "my-kafka-archive",
      "s3.part.size": "67108864",
      "flush.size": "1000",
      "storage.class": "io.confluent.connect.s3.storage.S3Storage",
      "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
      "partitioner.class": "io.confluent.connect.storage.partitioner.TimeBasedPartitioner",
      "path.format": "'year'=YYYY/'month'=MM/'day'=dd/'hour'=HH"
    }
  }

Managing connectors via CLI:
  # List connectors
  curl -s http://localhost:8083/connectors | jq
  
  # Check connector status
  curl -s http://localhost:8083/connectors/orders-jdbc-source/status | jq
  
  # Restart a failed task
  curl -X POST http://localhost:8083/connectors/orders-jdbc-source/tasks/0/restart
  
  # Pause/resume
  curl -X PUT http://localhost:8083/connectors/orders-jdbc-source/pause
  curl -X PUT http://localhost:8083/connectors/orders-jdbc-source/resume
  
  # Delete
  curl -X DELETE http://localhost:8083/connectors/orders-jdbc-source

5. SINGLE MESSAGE TRANSFORMS (SMT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SMTs apply lightweight, stateless transformations to each message as it flows
through a connector — no need to write a separate Kafka Streams job.

Common built-in SMTs:
  ReplaceField       → rename or drop fields
  MaskField          → mask sensitive fields with null (PII handling)
  InsertField        → add a field (e.g., add topic name, timestamp)
  ExtractField       → extract a single field as the new key/value
  SetSchemaMetadata  → override schema name/version
  TimestampConverter → convert timestamp format
  Filter             → drop records matching a predicate (or keep only matching)
  ValueToKey         → copy a value field to become the key
  Flatten            → flatten nested structs into top-level fields
  Cast               → type cast a field

Example: rename column + add timestamp
  "transforms": "rename,addTs",
  "transforms.rename.type": "org.apache.kafka.connect.transforms.ReplaceField$Value",
  "transforms.rename.renames": "user_id:userId,created_at:createdAt",
  "transforms.addTs.type": "org.apache.kafka.connect.transforms.InsertField$Value",
  "transforms.addTs.timestamp.field": "ingestTimestamp"

Limitations:
  - SMTs are STATELESS (no joins, no aggregations)
  - For complex transformations → use Kafka Streams downstream
  - SMTs execute inside the connector worker (impacts connector throughput)

6. DEBEZIUM — CDC WITH KAFKA CONNECT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Debezium is the most popular Kafka Connect source connector for Change Data Capture.
It reads the database's WAL (Write-Ahead Log) / binlog for real-time change events.

Supported databases: MySQL, PostgreSQL, MongoDB, Oracle, SQL Server, DB2

How it works (MySQL example):
  1. Debezium connects to MySQL as a replica client
  2. Reads the binlog (binary log of all changes)
  3. Emits one Kafka record per INSERT/UPDATE/DELETE
  4. Record contains: before (null for INSERT), after (null for DELETE), op (c/u/d/r)

Debezium MySQL config:
  {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "mysql",
    "database.port": "3306",
    "database.user": "debezium",
    "database.password": "dbz",
    "database.server.id": "1",
    "topic.prefix": "mydb",
    "database.include.list": "inventory",
    "schema.history.internal.kafka.topic": "mydb.schema-changes.inventory"
  }

  # Topics created: mydb.inventory.orders, mydb.inventory.customers, ...

Debezium record format:
  {
    "before": {"id": 1, "status": "PLACED"},     // null for INSERT
    "after":  {"id": 1, "status": "SHIPPED"},    // null for DELETE
    "op": "u",   // c=insert, u=update, d=delete, r=snapshot-read
    "ts_ms": 1704067200000,
    "source": {"db": "inventory", "table": "orders", ...}
  }

7. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is Kafka Connect and how does it differ from writing a custom Kafka producer?
A: Kafka Connect is a managed framework for integrating Kafka with external systems.
   It provides pre-built connectors, automatic offset management, fault tolerance
   (failed tasks are reassigned to other workers), REST API management, and SMTs for
   inline transformations — all without writing code. A custom producer gives you full
   control but requires you to build and maintain reliability, offset management, and
   scaling yourself. Connect is preferred for standard integrations (databases,
   object stores); custom code for unique or complex logic.

Q: What is the role of internal Kafka Connect topics?
A: Connect uses three internal topics: connect-configs (stores connector/task
   configurations — compacted, durable), connect-offsets (stores source connector
   positions/offsets so they survive worker restarts — compacted), and
   connect-status (stores connector/task states like RUNNING, FAILED, PAUSED).
   These topics make the Connect cluster stateless — any worker can take over any
   task by reading the shared state from Kafka itself.

Q: What is a Single Message Transform (SMT) in Kafka Connect?
A: SMTs are lightweight, stateless per-record transformations applied inline within
   a connector — before the record is written to Kafka (source) or after reading
   from Kafka (sink). Examples: renaming fields, masking PII, adding timestamps,
   extracting a field as the record key. They're configured as a JSON chain on the
   connector. SMTs cannot be stateful (no joins or aggregations) — use Kafka Streams
   for complex transformations.

Q: How does Debezium achieve Change Data Capture (CDC)?
A: Debezium connects to a database as a replication client and reads the database's
   write-ahead log (WAL / binlog). Every INSERT, UPDATE, and DELETE generates a Kafka
   record containing the before and after state of the row, plus operation type (c/u/d).
   Because it reads the log (not polling queries), it captures every change with
   sub-second latency and zero impact on the production database. It also performs
   an initial snapshot of existing data on startup.

Q: What happens when a Kafka Connect worker fails?
A: In distributed mode, the Connect cluster detects the failure via heartbeats.
   The remaining workers rebalance: tasks from the failed worker are redistributed
   among the healthy workers. Source connector positions are stored in connect-offsets
   (in Kafka), so the new worker picks up exactly where the failed worker left off.
   No data is lost. This is analogous to a Kafka consumer group rebalance.
