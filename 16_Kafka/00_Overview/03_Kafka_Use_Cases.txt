1. REAL-TIME EVENT STREAMING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Kafka ingests, stores, and delivers streams of events in real time.
  Events can be user actions, sensor readings, transactions, or any occurrence.

Examples:
  - LinkedIn: Tracking page views, clicks, job applications, searches (~7T/day)
  - Netflix: Tracking playback position, buffering events, user behavior
  - Uber: Real-time tracking of ride states (requested, picked-up, completed)
  - Twitter: Timeline events, tweet engagements, trending topic updates

Architecture:
  App (producer) → Kafka Topic → Real-time Processing (Flink/Kafka Streams) → DB/Dashboard

Why Kafka fits:
  - Millisecond-level end-to-end latency
  - Handles millions of events/sec from thousands of clients
  - Durable (survives crashes), replayable (replay historical events)

2. MICROSERVICES EVENT-DRIVEN COMMUNICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Microservices communicate asynchronously via Kafka events instead of
  synchronous REST/gRPC calls. This reduces coupling and improves resilience.

Examples:
  - Order Service publishes "order.placed" → Inventory Service, Payment Service,
    Notification Service, Analytics Service all consume independently
  - Payment Service publishes "payment.processed" → Order Service updates status

Benefits:
  - Services don't need to know each other (loose coupling)
  - Services can be deployed, scaled, failed independently
  - New consumers can be added without changing producers
  - Event history preserved for debugging and replay

Saga Pattern with Kafka:
  - Choreography-based sagas use Kafka events to coordinate distributed transactions
  - Each service publishes success/failure events
  - Other services react and either continue or compensate

3. LOG AGGREGATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Collect logs from many servers/services into a central Kafka topic, then route
  to Elasticsearch, Splunk, S3, or any monitoring system.

Architecture:
  App Server 1 → Filebeat/Logstash → Kafka (topic: app-logs)
  App Server 2 →                                    ↓
  App Server 3 →                      Consumer A → Elasticsearch
                                      Consumer B → S3 (archival)
                                      Consumer C → Alerts Engine

Benefits over direct shipping (e.g., Filebeat → Elasticsearch):
  - Buffer against Elasticsearch downtime (replay from Kafka)
  - Multiple consumers: logs go to both Elastic AND S3 simultaneously
  - Decoupled: change sinks without touching app code

Example companies: LinkedIn replaced Scribe/Flume with Kafka for log aggregation

4. CHANGE DATA CAPTURE (CDC)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  CDC captures every INSERT, UPDATE, DELETE from a database's transaction log
  and publishes them as Kafka events. This enables real-time data synchronization.

Tool: Debezium (the de facto CDC solution for Kafka)
  - Reads from: MySQL binlog, PostgreSQL WAL, Oracle LogMiner, MongoDB oplog
  - Publishes to: Kafka topics (one topic per table)
  - Supports: exact schema evolution, transaction boundaries

Use cases:
  a) Database migration: Sync data from legacy DB to new DB in real time
  b) Cache invalidation: Automatically invalidate Redis when DB record changes
  c) Search index updates: Publish DB changes to Elasticsearch via Kafka
  d) Microservice data sync: Each service has its own DB, CDC keeps them consistent
  e) Audit trail: Complete history of all database changes in Kafka

Architecture:
  PostgreSQL → Debezium (Kafka Connect Source) → Kafka topic (orders-cdc)
                                                 → Consumer 1: Elasticsearch
                                                 → Consumer 2: Redis
                                                 → Consumer 3: Audit DB

Why Kafka + CDC is powerful:
  - No changes to application code (reads the DB log directly)
  - Exactly-once semantics possible
  - Historical replay to rebuild any downstream system

5. REAL-TIME ANALYTICS & DASHBOARDS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Stream raw events into Kafka, process them in real time to compute metrics,
  and serve fresh dashboards.

Examples:
  - E-commerce: Real-time revenue dashboard, orders per second, conversion rates
  - Gaming: Live player counts, in-game event frequency, leaderboards
  - Financial: Real-time P&L, trade execution statistics, risk metrics

Architecture:
  User clicks → Kafka → Flink/Kafka Streams → Aggregated metrics → Druid/Cassandra → Dashboard

Kafka Streams example:
  Raw clickstream topic → KStream.groupByKey().count() → "page-views-per-minute" topic

6. FRAUD DETECTION & RISK SCORING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Ingest financial transactions in real time, apply ML models and rule engines
  to detect fraudulent patterns within milliseconds.

Architecture:
  Transaction → Kafka → Stream Processor (enrichment, risk scoring) → Decision topic
                                                                     → Block/Allow action

Examples:
  - Credit card transaction: validate in <100ms against fraud patterns
  - PayPal: Uses Kafka to stream 200M+ events/day through risk scoring
  - Banking: AML (Anti-Money Laundering) patterns across windowed transactions

Why Kafka matters here:
  - Sub-10ms latency from transaction to decision
  - Stateful stream processing (count recent transactions per card/IP)
  - Audit log of all decisions (replay to retrain ML models)

7. EVENT SOURCING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Instead of storing only current state in a DB, store EVERY state change as an
  immutable event. The current state is derived by replaying all events.

How Kafka enables event sourcing:
  - Kafka's immutable, replayable log is a natural event store
  - compacted topics store the latest value per key (event sourcing + snapshotting)
  - Consumers rebuild state from scratch by replaying from offset 0

Benefits:
  - Full audit trail of every state transition
  - Rebuild any read model by replaying events
  - Time-travel: reconstruct state at any point in time
  - Debugging: reproduce bugs by replaying the exact event sequence

Example — Order Service:
  Events: OrderCreated, OrderPaid, OrderShipped, OrderDelivered, OrderCancelled
  State: replaying these events gives you current order status

8. DATA PIPELINE / ETL (EXTRACT, TRANSFORM, LOAD)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Description:
  Kafka as the backbone for streaming ETL: data flows continuously from sources
  to destinations, with transformations applied in-flight.

Traditional ETL (batch):
  Source DB → Extract (nightly job) → Transform → Load to DW → Available next day

Kafka-based streaming ETL:
  Source DB → Debezium (CDC) → Kafka → Kafka Streams (transform) → Kafka Connect Sink → DW
  Available in seconds/minutes instead of the next day

Use cases:
  - Real-time data warehousing (Snowflake, BigQuery, Redshift streaming ingest)
  - Cross-datacenter replication (MirrorMaker 2)
  - Data lakehouse ingestion (Kafka → S3 → Delta Lake / Iceberg)

Description:
  IoT devices (sensors, vehicles, industrial machines) produce millions of readings
  per second. Kafka is the ideal ingestion layer.

Examples:
  - Tesla: Vehicle telemetry (speed, battery, location) → Kafka → analytics
  - Smart factory: 10,000 sensors × 100 readings/sec = 1M readings/sec → Kafka

  IoT Devices → MQTT Broker → Kafka Connect (MQTT source) → Kafka
                                                           → Stream processing
                                                           → Time-series DB (InfluxDB)
                                                           → Alerting

12. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What are the main use cases for Kafka?
A: (1) Real-time event streaming, (2) microservices communication, (3) log
   aggregation, (4) Change Data Capture (CDC), (5) real-time analytics,
   (6) fraud detection, (7) event sourcing, (8) streaming ETL/data pipelines,
   (9) IoT telemetry ingestion, (10) activity tracking.

Q: How is Kafka used for microservices?
A: Services publish events to Kafka topics; other services consume those events
   asynchronously and independently. This decouples services — the order service
   doesn't need to call the payment service directly. It publishes an "order.placed"
   event, and payment, inventory, and notification services all react to it.

Q: What is CDC and how does Kafka help?
A: CDC captures database changes (INSERT/UPDATE/DELETE) from the transaction log
   without touching application code. Tools like Debezium publish these changes
   as Kafka events. Downstream consumers (Elasticsearch, cache, other DBs) can
   react to these changes in real time.

Q: How would you design a real-time fraud detection system using Kafka?
A: Transactions flow into a Kafka topic. A stream processor (Kafka Streams/Flink)
   enriches each transaction with user profile data, computes risk features
   (velocity, location, amount patterns) using a tumbling window, applies an ML
   model or rule set, and publishes the decision to a "fraud-decisions" topic.
   A downstream service blocks/flags the transaction if the score exceeds a threshold.
   The audit trail is preserved in Kafka for model retraining.
