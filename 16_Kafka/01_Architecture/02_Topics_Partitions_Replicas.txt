1. TOPICS IN DEPTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A topic is the fundamental unit of organization in Kafka.

Characteristics:
  - Named logical channel (e.g., "user-signups", "order-events")
  - Append-only: producers always write to the end
  - Split into 1+ partitions for parallelism
  - Replicated across brokers for durability
  - Configurable retention (time-based or size-based)
  - NOT deleted when consumed (unlike traditional queues)

Topic creation:
  kafka-topics.sh --create \
    --bootstrap-server localhost:9092 \
    --topic user-events \
    --partitions 12 \
    --replication-factor 3 \
    --config retention.ms=86400000 \
    --config min.insync.replicas=2

Listing topics:
  kafka-topics.sh --list --bootstrap-server localhost:9092

Describing a topic:
  kafka-topics.sh --describe --topic user-events --bootstrap-server localhost:9092
  Output:
    Topic: user-events  Partitions: 12  ReplicationFactor: 3  Configs: ...
    Topic: user-events  Partition: 0  Leader: 2  Replicas: 2,1,3  Isr: 2,1,3
    Topic: user-events  Partition: 1  Leader: 3  Replicas: 3,2,1  Isr: 3,2,1
    ...

Auto-create topics:
  - auto.create.topics.enable=true (broker config, default true)
  - Dangerous in production: typos create unwanted topics
  - Best practice: set to FALSE and manage topics explicitly

2. PARTITIONS IN DEPTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A partition is the basic unit of parallelism, ordering, and replication.

Key properties:
  1. ORDERED: Messages within a partition are strictly ordered by offset
  2. IMMUTABLE: Records cannot be updated or deleted (compaction is background)
  3. APPEND-ONLY: New records are always appended at the end
  4. BOUNDED CONCURRENCY: ONE consumer per partition per group at a time
  5. DISTRIBUTED: Different partitions live on different brokers

Partition assignment (how messages go to partitions):

  Case 1: Key is provided (most important case)
    partition = murmur2(key.getBytes()) % numPartitions
    → Guarantees: all messages with the same key go to the same partition
    → Use for: order events by orderId, user events by userId
    → PROBLEM: If numPartitions changes, key routing breaks for existing keys
               This is why you cannot decrease partitions.

  Case 2: No key (Kafka 2.3 and earlier)
    → Round-robin across partitions
    → Each message goes to the next partition in sequence

  Case 3: No key (Kafka 2.4+ sticky partitioning)
    → Messages accumulate into a batch for one partition
    → Once batch is full or linger.ms expires, switch to next partition
    → Better batching efficiency than pure round-robin

  Case 4: Custom Partitioner
    → Implement org.apache.kafka.clients.producer.Partitioner interface
    → Useful for special routing logic (e.g., route VIP customers to dedicated partitions)

Partition count decision:
  Formula: max(P_consumer, P_producer) where:
    P_consumer = target_consumer_throughput / throughput_per_consumer
    P_producer = target_producer_throughput / throughput_per_producer

  Rule of thumb:
    - Start with 2-3x the number of consumer instances you expect to run
    - For most applications: 6, 12, or 24 partitions
    - High-throughput: 48, 96, or more
    - Single-partition (global ordering): only when ordering is more important than scale

Increasing partitions (after creation):
  kafka-topics.sh --alter --topic orders --partitions 12 --bootstrap-server localhost:9092
  
  WARNING: This is IRREVERSIBLE. And messages with keys that were going to
  partition X will now route to a different partition → ordering broken for those keys.
  Existing data in old partitions is NOT redistributed.

3. REPLICAS IN DEPTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A replica is a copy of a partition stored on a broker.

Replication factor:
  - Number of copies of each partition (including the leader)
  - replication-factor=3: 1 leader + 2 followers
  - Can tolerate (RF - 1) broker failures before data loss is possible
  - Can tolerate (RF - min.insync.replicas) broker failures before writes stop

Leader replica:
  - ONE leader per partition at any time
  - ALL producer writes go to the leader
  - ALL consumer reads go to the leader (by default)
    Exception: Kafka 2.4+ supports follower reads for rack-aware consumers

Follower replica:
  - Passively replicates from the leader
  - Sends FetchRequests just like a consumer (but it's internal)
  - If follower LEO lags behind leader HW by more than replica.lag.time.max.ms → removed from ISR

ISR (In-Sync Replicas):
  - The set of replicas currently caught up with the leader
  - For acks=all: producer waits for ALL ISR replicas to acknowledge
  - min.insync.replicas: minimum ISR size required for producer writes
  - If ISR < min.insync.replicas: broker throws NotEnoughReplicasException

ISR dynamics:
  ISR shrinks when:
    - Follower is slow (GC pause, slow disk, network issue)
    - Follower is restarting
    - Under-replicated partition situation (UnderReplicatedPartitions metric)

  ISR grows when:
    - Follower catches up (fetches all records up to HW)

Preferred replica:
  - The FIRST replica in the Replicas list (the "preferred leader")
  - Kafka tries to keep this as the leader (auto.leader.rebalance.enable=true)
  - Re-balancing runs every leader.imbalance.check.interval.seconds (300s default)

4. REPLICATION FACTOR RECOMMENDATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Environment          RF    min.insync.replicas   Trade-offs
──────────────────────────────────────────────────────────────────────────────
Development           1    1                     No durability, max throughput
Staging               2    1                     1 failure tolerated, some durability
Production            3    2                     Tolerates 1 failure, good durability
Critical (banking)    3    3                     No data loss but writes fail if any
                                                  broker is down (very conservative)

The golden rule: RF=3, min.insync.replicas=2 is the production standard.

Understanding the trade-off:
  - RF=3, min.ISR=1: Very fast (only leader needs to ack), can lose data if leader
                      fails between write and replication
  - RF=3, min.ISR=2: Balanced. Write blocks if 2 replicas are down. Data safe
                      if 1 broker fails.
  - RF=3, min.ISR=3: Writes block if any broker is down. Maximum safety.
                      Effectively synchronous writes.

5. LOG COMPACTION VS DELETE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

cleanup.policy=delete (default):
  - Old segments are deleted when:
    - retention.ms is exceeded (default 7 days)
    - retention.bytes is exceeded (default: -1, no size limit)
  - Use for: transient events (logs, metrics, user activity)

cleanup.policy=compact:
  - Kafka keeps ONLY the latest record for each key
  - Old records for the same key are deleted during compaction
  - NULL value (tombstone) = delete the key from the compacted log
  - The "tail" of the log (recent segment) is NOT compacted yet
  - Compaction runs in background via cleaner threads (log.cleaner.threads)
  - Use for: latest state per entity (CDC, config store, user profiles)

cleanup.policy=compact,delete:
  - BOTH: compact old records AND delete segments older than retention.ms
  - Use for: CDC with a retention period

Compaction guarantees:
  - The log retains AT LEAST the last record for each key
  - Compaction is NOT guaranteed to happen immediately
  - min.cleanable.dirty.ratio: fraction of log that must be dirty before cleaning

Compaction internals:
  - Log has a "clean" portion (compacted) and "dirty" portion (recent, not yet compacted)
  - Cleaner thread reads the dirty portion, builds an offset map (key → latest offset)
  - Creates a new clean segment with only the latest records per key
  - Replaces the old dirty segments with the new clean segment

7. PARTITION LEADERSHIP AND CONSUMER READS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Reads from leader (default behavior):
  - All consumer reads go to the partition leader
  - In multi-AZ setup: consumer in us-east-1b reads from leader in us-east-1a
  - This causes cross-AZ network traffic (costs money and adds latency)

Reads from follower (Kafka 2.4+):
  - "Fetch from closest replica" (rack-aware read)
  - Consumer configured with: client.rack=us-east-1b
  - Broker's replica configured with: broker.rack=us-east-1b
  - Kafka routes consumer to the closest replica in the same rack/AZ
  - Reduces cross-AZ data transfer costs significantly
  - CAVEAT: Consumer reads only data up to the remote HW
            (may be slightly behind leader HW)

8. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: How does Kafka guarantee ordering?
A: Ordering is guaranteed WITHIN a single partition. By using the same message
   key, all related messages (e.g., all events for userId=123) are routed to
   the same partition via hash(key) % numPartitions. This ensures sequential
   processing. Ordering is NOT guaranteed across partitions.

Q: What happens if you change the number of partitions in a topic?
A: Partitions can only be increased, never decreased. Increasing partitions
   breaks key-based ordering — messages for a key that previously went to
   partition 2 may now go to partition 5. Existing data is NOT redistributed.
   Applications relying on key ordering must be aware of this.

Q: What is the difference between the leader and follower replicas?
A: The leader handles all reads and writes for a partition. Followers passively
   replicate from the leader. The ISR list tracks which followers are caught up.
   If the leader fails, a new leader is elected from the ISR. Followers help
   achieve fault tolerance without serving production traffic (by default).

Q: What is a tombstone in Kafka log compaction?
A: A tombstone is a record with a non-null key but a NULL value. When compaction
   runs, it removes all records for that key, effectively deleting the key from
   the compacted log. After delete.retention.ms, the tombstone itself is also
   deleted. This is the mechanism for deleting data from compacted topics.

Q: What is the replication factor vs min.insync.replicas?
A: Replication factor is the total number of copies of each partition.
   min.insync.replicas is the minimum number of those copies that must
   acknowledge a write (when acks=all) for the write to succeed. 
   RF=3, min.ISR=2: you have 3 copies, need 2 to ack — tolerates 1 broker failure.
   If only 1 broker is up, writes fail (protecting against data loss).

Q: How does rack-aware replica assignment help?
A: By setting broker.rack on each broker (e.g., us-east-1a, us-east-1b, us-east-1c),
   Kafka distributes replicas across availability zones. This means even if an
   entire AZ goes down, the remaining replicas in other AZs can continue serving
   data without data loss (assuming RF >= 3 and replicas in >= 2 AZs).
