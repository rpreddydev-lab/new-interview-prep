1. WHY KAFKA NEEDED EXTERNAL METADATA MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Kafka needs to store and manage:
  - Cluster membership (which brokers are alive)
  - Topic and partition configuration
  - Partition leader assignments
  - ISR (In-Sync Replica) lists
  - Consumer group coordinator assignments
  - Access control lists (ACLs)
  - Quotas

In the early design, ZooKeeper was used as an external distributed coordination
service to store this metadata.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. APACHE ZOOKEEPER (Legacy Mode)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What is ZooKeeper?
  - Apache ZooKeeper is a distributed coordination service
  - Provides: leader election, distributed locks, config management, name service
  - Uses a tree-like znodes structure
  - Raft-like Zab (ZooKeeper Atomic Broadcast) consensus protocol internally
  - Typically deployed as a 3 or 5 node ensemble

How Kafka used ZooKeeper:
  1. Broker registration: Each broker creates an ephemeral znode
     /brokers/ids/<broker.id> → when broker dies, ephemeral node is deleted
  2. Controller election: First broker to write /controller znode becomes controller
  3. Topic metadata: /brokers/topics/<topic>/partitions/<n>/state
  4. ISR updates: Written to ZooKeeper on every ISR change
  5. Consumer group offsets (pre-0.9): /consumers/<group>/offsets/<topic>/<partition>

ZooKeeper architecture:
  - 3-node ensemble: can tolerate 1 node failure
  - 5-node ensemble: can tolerate 2 node failures
  - Must have an ODD number of nodes for quorum
  - Leader elected via Zab consensus
  - All writes go to the leader → followers sync

3. PROBLEMS WITH THE ZOOKEEPER ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. SEPARATE SYSTEM TO OPERATE
   - ZooKeeper requires its own hardware, monitoring, tuning, security
   - Separate JVM with its own heap/GC issues
   - Teams need expertise in BOTH Kafka and ZooKeeper
   - Two systems to scale, upgrade, and maintain

2. METADATA SCALABILITY LIMIT
   - Each ISR change for every partition is written to ZooKeeper
   - ZooKeeper has a hard limit on data size (znodes limited to 1 MB by default)
   - A large Kafka cluster with 200,000+ partitions is near ZooKeeper's limits
   - Controller startup: must read ALL metadata from ZooKeeper → slow at scale
     (controller restart with 200K partitions: can take minutes)

3. CONTROLLER BOTTLENECK
   - When controller restarts, it must read all metadata from ZooKeeper AND
     propagate it to all brokers one-by-one
   - Until this is done, no partition leadership changes can happen
   - With 1 million partitions: controller restart could take HOURS

4. SPLIT-BRAIN RISK
   - If ZooKeeper and Kafka have inconsistent views, data inconsistency is possible
   - Metadata is "eventual" — ZooKeeper events may lag actual broker state

5. SECURITY COMPLEXITY
   - Two separate systems to configure TLS/SASL for
   - ZooKeeper authorization is separate from Kafka authorization

Timeline of ZooKeeper deprecation:
  - 2019: KIP-500 proposed ZooKeeper removal
  - 2021: KRaft preview in Kafka 2.8
  - 2022: KRaft production-ready in Kafka 3.3
  - 2024: ZooKeeper mode deprecated in Kafka 3.7
  - Planned removal: Kafka 4.0

4. KRAFT (KAFKA RAFT METADATA MODE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KRaft = Kafka + Raft consensus. Introduced via KIP-500.

How KRaft works:
  - Metadata stored in a special internal topic: __cluster_metadata
  - A quorum of "controller" brokers run the Raft consensus protocol
  - One controller is the ACTIVE CONTROLLER (leader)
  - Remaining controllers are STANDBY CONTROLLERS (followers)
  - Regular "broker" nodes store topic data, do NOT participate in metadata quorum

The Raft protocol ensures:
  - All controllers have the same metadata log
  - Active controller handles all metadata writes
  - On failover, a standby is elected as the new active controller
  - Failover time: < 1 second (vs 30-60s in ZooKeeper mode)

Key differences in KRaft:
  - Metadata is an EVENT LOG (like a Kafka topic), not a tree of znodes
  - Brokers learn of metadata changes by "replaying" the metadata log
  - No need for ZooKeeper ensemble — completely self-contained

KRaft configuration (server.properties):
  # Role: can be "broker", "controller", or "broker,controller" (combined mode)
  process.roles=broker,controller
  node.id=1
  
  # Controller quorum (all controllers listed)
  controller.quorum.voters=1@kafka1:9093,2@kafka2:9093,3@kafka3:9093
  
  # Dedicated listener for inter-controller communication
  controller.listener.names=CONTROLLER
  listeners=PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093

  # Cluster ID (must be generated and same on all nodes)
  # Generate with: kafka-storage.sh random-uuid
  # Format storage: kafka-storage.sh format -t <cluster-id> -c server.properties

KRaft deployment modes:
  1. COMBINED MODE: Controller and Broker roles on the SAME JVM
     - Simpler to deploy (fewer nodes needed)
     - Good for: small clusters, development, cost-sensitive environments
     - Typical: 3 nodes, all combined

  2. DEDICATED MODE: Controller nodes are SEPARATE from broker nodes
     - Controllers: 3 or 5 dedicated nodes (no topic data stored)
     - Brokers: N nodes (no metadata quorum participation)
     - Good for: large production clusters, better isolation
     - Typical: 3 controller nodes + 5-20 broker nodes

6. RAFT CONSENSUS — HOW IT WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Raft is a consensus algorithm designed to be more understandable than Paxos.

Core concepts in the context of KRaft:
  - Leader: The active controller; handles all metadata write requests
  - Followers: Standby controllers; replicate the leader's log
  - Term: A logical clock; incremented on each election
  - Log: Ordered sequence of metadata records (like a Kafka topic)
  - Commit: A log entry is committed when a majority of controllers have it

Leader election:
  1. If a follower doesn't hear from the leader within the election timeout,
     it becomes a CANDIDATE and requests votes from others
  2. If a candidate gets votes from a majority (e.g., 2 of 3), it becomes leader
  3. New leader starts serving metadata writes from its current term

Log replication:
  1. Client sends metadata write to the active controller
  2. Leader appends to its local log
  3. Leader sends AppendEntries to all followers
  4. Once a majority (quorum) acknowledge, the entry is COMMITTED
  5. Leader notifies all controllers of the new commit index
  6. Brokers replicate committed metadata to their local caches

KRaft in Kafka specifics:
  - Kafka adapted Raft to store metadata records (not binary Raft messages)
  - Uses the same binary format as Kafka record batches for efficiency
  - __cluster_metadata topic stores the metadata event log

7. MIGRATING FROM ZOOKEEPER TO KRAFT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Migration steps (Kafka 3.x rolling migration):
  1. Upgrade all brokers to Kafka 3.x (ZK mode)
  2. Deploy KRaft controllers alongside ZooKeeper
  3. Run in "migration mode" — controllers observe ZooKeeper
  4. Perform metadata migration: controllers read from ZK → write to KRaft log
  5. Broker by broker: update to KRaft mode, reconnect to KRaft controllers
  6. Decommission ZooKeeper

New clusters (Kafka 3.3+):
  - Start directly in KRaft mode
  - No ZooKeeper needed at all

8. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is ZooKeeper's role in Kafka?
A: ZooKeeper stored Kafka's cluster metadata (broker membership, topic configs,
   partition leaders, ISR lists) and managed controller election via ephemeral
   znodes. Kafka brokers wrote state to ZooKeeper and the controller received
   watch notifications when state changed. Consumer offsets were also stored in
   ZooKeeper before Kafka 0.9.

Q: What are the limitations of the ZooKeeper-based architecture?
A: (1) External dependency adds operational complexity. (2) Scales to ~200K
   partitions before ZooKeeper becomes a bottleneck. (3) Controller restart
   is slow at scale (must re-read all metadata from ZK). (4) Split-brain risks.
   (5) Security is complex (separate auth for ZK and Kafka).

Q: What is KRaft and why was it introduced?
A: KRaft is Kafka's built-in Raft consensus protocol for metadata management,
   replacing ZooKeeper. Benefits: no external dependencies, supports millions
   of partitions, controller failover in < 1 second (vs 30-60s), simpler
   operations, and faster cluster recovery.

Q: What is the difference between combined and dedicated KRaft mode?
A: Combined mode: controller and broker roles on the same node (simpler, fewer
   nodes). Dedicated mode: controllers are on separate nodes from brokers (better
   isolation, for large production clusters). Dedicated is recommended for
   high-scale environments.

Q: How does Raft consensus work in KRaft?
A: One controller is elected as the active leader. All metadata writes go to
   the leader. The leader appends to its log and replicates to follower controllers.
   An entry is committed when a majority (quorum) of controllers acknowledge it.
   If the leader fails, a new leader is elected from the followers. The metadata
   is stored as a topic-like event log in __cluster_metadata.
