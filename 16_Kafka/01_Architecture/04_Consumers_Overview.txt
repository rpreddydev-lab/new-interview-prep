1. WHAT IS A KAFKA CONSUMER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A Kafka consumer is a client that reads (subscribes to) records from Kafka topics.

Key characteristics:
  - PULL-based: consumers request data from brokers (not pushed)
  - Tracks its own position using offsets
  - Belongs to a consumer group for load balancing
  - Can seek to any offset (replay historical data)
  - Reads only up to the HIGH-WATERMARK (only committed, replicated data)

Why pull (not push)?
  - Consumers can control their own pace — prevents overwhelming slow consumers
  - Consumers can batch-read many records in one fetch
  - Simple back-pressure: if consumer is slow, it just polls less frequently
  - Consumers can replay at any time by changing offset

2. CONSUMER POLL LOOP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The core consumer pattern:

  Properties props = new Properties();
  props.put("bootstrap.servers", "localhost:9092");
  props.put("group.id", "order-processor");
  props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
  props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
  props.put("auto.offset.reset", "earliest");
  props.put("enable.auto.commit", "false");

  KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
  consumer.subscribe(Arrays.asList("orders", "payments"));

  try {
    while (true) {
      ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
      
      for (ConsumerRecord<String, String> record : records) {
        System.out.printf("Topic=%s Partition=%d Offset=%d Key=%s Value=%s%n",
          record.topic(), record.partition(), record.offset(), record.key(), record.value());
        // process record
      }
      
      consumer.commitSync(); // commit offsets after processing
    }
  } finally {
    consumer.close(); // triggers rebalance so partitions are reassigned
  }

poll() semantics:
  - Sends a FetchRequest to the broker if needed
  - Returns up to max.poll.records records
  - If no records available: waits up to the given Duration (long-poll)
  - poll() also sends heartbeats and triggers rebalances
  - Must call poll() at least every max.poll.interval.ms (5 minutes default)
    OR the broker assumes the consumer is dead and triggers a rebalance

3. CONSUMER CONFIGURATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Core:
  bootstrap.servers             = "broker1:9092,broker2:9092"
  group.id                      = "my-consumer-group"
  key.deserializer              = StringDeserializer
  value.deserializer            = StringDeserializer
  client.id                     = "my-consumer-1"  (for monitoring)

Offset behavior:
  auto.offset.reset             = latest    (start from new messages only)
                                = earliest  (start from beginning)
                                = none      (throw exception if no committed offset)
  enable.auto.commit            = false     (highly recommended: manage offsets manually)
  auto.commit.interval.ms       = 5000      (if enable.auto.commit=true)

Fetch tuning:
  fetch.min.bytes               = 1         (min bytes broker must have before responding)
  fetch.max.bytes               = 52428800  (50 MB max per fetch response)
  fetch.max.wait.ms             = 500       (max wait if min.bytes not satisfied)
  max.poll.records              = 500       (max records returned per poll())
  max.partition.fetch.bytes     = 1048576   (1 MB max per partition per fetch)

Health:
  session.timeout.ms            = 45000     (heartbeat failure detection)
  heartbeat.interval.ms         = 3000      (must be < session.timeout.ms / 3)
  max.poll.interval.ms          = 300000    (5 min max between poll() calls)

4. CONSUMER SUBSCRIPTION MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Mode 1: Subscribe to topics (automatic partition assignment)
  consumer.subscribe(Arrays.asList("orders", "payments"));
  → Kafka assigns partitions automatically based on group membership
  → Triggers rebalance when consumers join/leave group
  → Most common mode

Mode 2: Assign specific partitions (manual assignment)
  TopicPartition tp0 = new TopicPartition("orders", 0);
  TopicPartition tp1 = new TopicPartition("orders", 1);
  consumer.assign(Arrays.asList(tp0, tp1));
  → No group coordination, no rebalancing
  → Useful for: exact replay, testing, custom load balancing
  → Consumer doesn't join a group (no group.id coordination)

Mode 3: Subscribe with pattern (regex)
  consumer.subscribe(Pattern.compile("order-.*"));
  → Matches: order-events, order-history, order-notifications
  → New topics matching pattern are automatically added
  → Useful for multi-tenant scenarios

5. CONSUMER GROUP MEMBERSHIP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

How consumer groups work:
  - All consumers with the same group.id form a consumer group
  - Kafka distributes partitions evenly across active consumers
  - Each partition is assigned to exactly ONE consumer in the group
  - Multiple groups read the same topic independently (fan-out)

What triggers a rebalance?
  - New consumer joins the group
  - Existing consumer leaves (graceful: consumer.close())
  - Consumer is presumed dead (heartbeat failure or max.poll.interval exceeded)
  - New partitions added to a subscribed topic

Rebalance protocol:
  1. Group Coordinator detects membership change
  2. Sends JoinGroup request to all consumers → suspends fetching
  3. One consumer is elected as "Group Leader"
  4. Group leader runs the partition assignment algorithm
  5. Group leader sends partition assignments to Group Coordinator
  6. Group Coordinator sends individual assignments to each consumer (SyncGroup)
  7. Consumers resume fetching from their new partitions

Rebalance strategies:
  RangeAssignor (default):
    - Assigns contiguous ranges of partitions per topic
    - Can be uneven if #partitions not divisible by #consumers
  
  RoundRobinAssignor:
    - Distributes partitions round-robin across consumers
    - More even distribution

  StickyAssignor (Kafka 0.11+):
    - Tries to keep existing assignments unchanged during rebalance
    - Minimizes partition movement → less disruption
    - RECOMMENDED for production

  CooperativeStickyAssignor (Kafka 2.4+):
    - Incremental rebalancing: only reassigns partitions that changed
    - Consumers don't need to stop ALL processing during rebalance
    - "Cooperative" = consumers give up partitions first, then receive new ones
    - BEST CHOICE: partition.assignment.strategy=CooperativeStickyAssignor

6. OFFSET MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Offset = the position of the consumer in the partition.

Committing offsets:
  1. Auto-commit (enable.auto.commit=true):
     - Background thread commits every auto.commit.interval.ms
     - Risk: if consumer crashes AFTER poll() but BEFORE processing, offset is
             already committed → records are SKIPPED (at-most-once)
     - NOT recommended for critical applications

  2. Manual sync commit:
     consumer.commitSync();
     - Blocks until committed by group coordinator
     - Safe but slow (synchronous)

  3. Manual async commit:
     consumer.commitAsync();
     - Non-blocking, fires and forgets
     - Doesn't retry on failure (risk of duplicate if retry is needed)
     - Use with async + fallback to commitSync in finally block

  4. Manual per-partition commit (most fine-grained):
     Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
     offsets.put(tp, new OffsetAndMetadata(record.offset() + 1));
     consumer.commitSync(offsets);
     - Precise control
     - Useful when processing partitions in parallel within a consumer

Important: You commit the NEXT offset to read (current + 1), NOT the current:
  commitSync({tp: OffsetAndMetadata(lastProcessedOffset + 1)})

7. CONSUMER ISOLATION: READ_COMMITTED vs READ_UNCOMMITTED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

isolation.level = read_uncommitted (default):
  - Consumer reads ALL records including those in an OPEN transaction
  - Can read records that are later ABORTED
  - Higher throughput

isolation.level = read_committed:
  - Consumer reads ONLY records in COMMITTED transactions
  - Records from aborted transactions are filtered out
  - Also reads non-transactional records normally
  - Required for exactly-once consumption

  records-consumed-rate    → messages per second being consumed

  commit-latency-avg       → average offset commit latency
  rebalance-latency-max    → max duration of a rebalance (high = problem)
  join-time-avg            → avg time to join a group during rebalance

9. KEY INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why does Kafka use a pull model instead of push?
A: Pull allows consumers to control their own pace. They can batch-read many
   records at once, handle back-pressure naturally (just poll less), and replay
   from any offset. Push would require the broker to track each consumer's
   capacity, which is complex to manage at scale.

Q: What happens when a Kafka consumer is slower than the producer?
A: Consumer lag grows. The consumer falls behind the log-end offset. This is
   normal and Kafka handles it — messages are retained until retention.ms.
   If lag grows continuously, the consumer needs to be scaled (add instances
   or optimize processing). Alert on records-lag-max growing unboundedly.

Q: What is a consumer group rebalance and when does it happen?
A: A rebalance is when Kafka redistributes partition assignments among consumers
   in a group. It's triggered by a consumer joining or leaving (or crashing),
   or new partitions being added. During (eager) rebalance, ALL consumers stop
   reading until the new assignment is complete. CooperativeStickyAssignor
   minimizes disruption by doing incremental rebalancing.

Q: What is the difference between auto.offset.reset=earliest and =latest?
A: earliest: When there's no committed offset for a partition (new consumer
   group or partition), start reading from offset 0 (the beginning).
   latest: Start reading from the end of the log (only new messages after
   the consumer starts). latest is the default.

Q: How do you ensure at-least-once delivery in Kafka consumers?
A: Disable auto.commit (enable.auto.commit=false). Process records fully, then
   commit offsets with commitSync() AFTER processing. If the consumer crashes
   after processing but before committing, it will reprocess some records
   (duplicates possible). Handle idempotency at the application layer.
