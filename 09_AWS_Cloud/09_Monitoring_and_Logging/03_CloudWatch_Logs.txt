================================================================
AWS MONITORING — CLOUDWATCH LOGS
Complete Interview Preparation Guide
================================================================

1. CLOUDWATCH LOGS OVERVIEW
================================================================

  CloudWatch Logs stores, monitors, and accesses log files from:
    - EC2 instances (via CloudWatch Agent)
    - Lambda functions (automatically)
    - ECS/EKS containers
    - API Gateway access logs
    - VPC Flow Logs
    - CloudTrail
    - Route 53 DNS query logs
    - Custom applications

================================================================
2. LOG GROUPS AND LOG STREAMS
================================================================

  LOG GROUP:
    - Container for log streams
    - Retention policy set at group level (1 day to never expire)
    - Per-group encryption (KMS)
    - Default Lambda log group: /aws/lambda/function-name
    - Default API Gateway log group: API-Gateway-Execution-Logs_apiId/stage
  
  LOG STREAM:
    - Sequence of log events from a single source
    - Lambda: one stream per function instance (execution environment)
    - EC2: one stream per instance
    - Events within a stream are ordered by time

  CLI:
  # Create log group
  aws logs create-log-group \
    --log-group-name /myapp/prod/app-service
  
  # Set retention (7 days)
  aws logs put-retention-policy \
    --log-group-name /myapp/prod/app-service \
    --retention-in-days 7
  
  # List log groups
  aws logs describe-log-groups --log-group-name-prefix /aws/lambda
  
  # Tail logs (CloudWatch Logs Insights is better for queries)
  aws logs tail /aws/lambda/my-function --follow

3. METRIC FILTERS
================================================================

  Extract metrics from log data by matching patterns.
  
  Pattern syntax:
    [ip, user, ..., status=5*, ...]   # field-based
    { $.level = "ERROR" }             # JSON filter
    "ERROR"                           # simple string match
    "NullPointerException"            # detect specific exceptions
  
  CREATE METRIC FILTER:
  aws logs put-metric-filter \
    --log-group-name /myapp/prod/app-service \
    --filter-name "ErrorCount" \
    --filter-pattern "ERROR" \
    --metric-transformations '[{
      "metricName": "AppErrors",
      "metricNamespace": "MyApp",
      "metricValue": "1",
      "defaultValue": 0
    }]'
  
  Then create a CloudWatch Alarm on the AppErrors metric!
  
  COMMON PATTERNS:
    "ERROR"                           → count error log lines
    "Exception"                       → Java exceptions
    "[status=5*, ...]"                → HTTP 5xx errors
    { $.statusCode = 500 }            → JSON structured logs
    "Task timed out"                  → Lambda timeouts

4. CLOUDWATCH LOGS INSIGHTS
================================================================

  Serverless SQL-like query engine for CloudWatch Logs.
  No infrastructure needed — queries across log groups.
  
  QUERY SYNTAX:
  
  Basic structure:
    fields @timestamp, @message
    | filter @message like /ERROR/
    | sort @timestamp desc
    | limit 20
  
  Common query patterns:
  
  -- Lambda cold starts
  filter @type = "REPORT"
  | stats avg(@initDuration), max(@initDuration), count(@initDuration) by bin(5m)
  
  -- Top 10 slowest Lambda invocations
  filter @type = "REPORT"
  | stats max(@duration) as maxDuration by @requestId
  | sort maxDuration desc
  | limit 10
  
  -- Error rate over time
  filter @message like /ERROR/
  | stats count(*) as errorCount by bin(5m)
  | sort @timestamp
  
  -- API Gateway 5xx responses
  filter status >= 500
  | stats count(*) by status, httpMethod, resourcePath
  | sort count(*) desc
  
  -- Lambda memory utilization from REPORT line
  filter @type = "REPORT"
  | parse @message "Max Memory Used: * MB" as memUsed
  | parse @message "Memory Size: * MB" as memSize
  | stats max(memUsed / memSize * 100) as maxMemPct by functionVersion
  
  RUN QUERY VIA CLI:
  aws logs start-query \
    --log-group-name /aws/lambda/my-function \
    --start-time $(date -d '1 hour ago' +%s) \
    --end-time $(date +%s) \
    --query-string 'fields @timestamp, @message | filter @message like /ERROR/ | limit 20'
  
  # Get results
  aws logs get-query-results --query-id <queryId>

5. LOG SUBSCRIPTIONS
================================================================

  Stream logs in real time to processing services:
  
  SUBSCRIPTION FILTER:
    - Match a pattern in incoming log events
    - Forward matched events to: Lambda, Kinesis, Kinesis Firehose
  
  USE CASES:
    - Real-time error alerting via Lambda
    - Stream logs to OpenSearch for full-text search
    - Stream logs to S3 (via Firehose) for long-term archival
    - Cross-account log aggregation
  
  CREATE SUBSCRIPTION FILTER:
  aws logs put-subscription-filter \
    --log-group-name /myapp/prod/app-service \
    --filter-name "ForwardErrors" \
    --filter-pattern "ERROR" \
    --destination-arn arn:aws:kinesis:us-east-1:123456789012:stream/log-stream
  
  CROSS-ACCOUNT LOG AGGREGATION:
    Log Archive Account: create Kinesis Data Stream
    Source accounts: put subscription filters pointing to Log Archive account's Kinesis
    (Requires cross-account Kinesis resource policy)

================================================================
6. LOG EXPORT TO S3
================================================================

  For long-term retention and cost-effective storage:
  
  # Create export task
  aws logs create-export-task \
    --log-group-name /myapp/prod/app-service \
    --from 1705276800000 \
    --to 1705363200000 \
    --destination my-log-archive-bucket \
    --destination-prefix logs/myapp/prod
  
  Note: Export tasks are NOT real-time — use subscription filter with Firehose 
  for near-real-time delivery to S3.

7. STRUCTURED LOGGING BEST PRACTICES
================================================================

  Use JSON structured logs for easy querying in Logs Insights:
  
  // Java structured logging with SLF4J + Logback
  import org.slf4j.Logger;
  import org.slf4j.LoggerFactory;
  
  // Bad (unstructured):
  logger.error("Order failed for orderId=" + orderId + " reason=" + reason);
  
  // Good (structured JSON):
  logger.error("Order processing failed",
      kv("orderId", orderId),
      kv("customerId", customerId),
      kv("errorReason", reason),
      kv("requestId", requestId));
  
  // Results in:
  // {"level":"ERROR","message":"Order processing failed",
  //  "orderId":"123","customerId":"456","errorReason":"PAYMENT_DECLINED",
  //  "requestId":"abc-def"}
  
  // CloudWatch Logs Insights query:
  // filter level = "ERROR" | stats count(*) by errorReason
  
  For Lambda, use AWS Lambda Powertools:
  import software.amazon.lambda.powertools.logging.Logger;
  @Logger
  public class Handler implements RequestHandler<...> {
      public Object handleRequest(Input input, Context ctx) {
          Logger.info("Processing", Map.of("orderId", input.getOrderId()));
      }
  }

8. INTERVIEW QUESTIONS
================================================================

Q: How would you find all Lambda functions with error rates above 1% in the last hour?
A: Use CloudWatch Logs Insights across Lambda log groups:
   
   fields @timestamp, @requestId, @message
   | filter @type = "REPORT"  
   | stats count(*) as invocations by bin(1h)
   
   Then cross-correlate with error filter:
   filter @message like /ERROR/ or @message like /Task timed out/
   | stats count(*) as errors by bin(1h)
   
   For a proper error rate dashboard: create CloudWatch metric filters on each 
   Lambda's log group for ERROR pattern, then compute error rate = Errors / Invocations 
   using CloudWatch math expressions. Use metric math: m1/m2*100 where m1=Errors 
   metric and m2=Invocations metric from Lambda namespace.
   
   Alternatively, use CloudWatch Lambda Insights (enhanced monitoring) which provides 
   out-of-the-box error rate, cold start metrics.

Q: What is the difference between CloudWatch Logs metric filters and Logs Insights?
A: Metric filters extract real-time metrics from log streams continuously — they count 
   matching log lines and publish to a CloudWatch metric that you can alarm on. They 
   are always-on and look forward (from the time you create them).
   
   Logs Insights is an ad-hoc query engine — you write SQL-like queries to analyze 
   historical log data. It's for investigation, not for alerting. It queries across 
   multiple log groups, supports complex aggregations (stats, parse, pattern), and 
   shows results interactively. It costs per GB of data scanned.
   
   Use metric filters + alarms for proactive alerting. Use Logs Insights for reactive 
   investigation and ad-hoc analysis.

Q: How do you centralize logs from multiple AWS accounts into one account?
A: Use CloudWatch Logs subscription filters with Kinesis Data Streams or Kinesis Firehose:
   1. In the central Log Archive account, create a Kinesis Data Stream or Firehose.
   2. Create a Kinesis resource policy allowing the source accounts to put records.
   3. In each source account, create a CloudWatch Logs subscription filter pointing 
      to the central Kinesis stream's ARN. Use PutSubscriptionFilter API with 
      cross-account destination.
   4. The Kinesis Firehose in the Log Archive account delivers all logs to a central S3 
      bucket, organized by account ID prefix.
   Alternative: Use CloudWatch cross-account observability (newer feature) which allows 
   viewing log groups from linked accounts directly in the monitoring account's console.
