================================================================
AWS MESSAGING — SNS (SIMPLE NOTIFICATION SERVICE)
Complete Interview Preparation Guide
================================================================

1. SNS OVERVIEW
================================================================

  SNS is a fully managed pub/sub messaging service.
  One message published to an SNS Topic is pushed to ALL subscribers.
  
  Key characteristics:
    - Push-based (subscribers receive messages proactively)
    - Fan-out: one publish reaches many subscribers simultaneously
    - Subscribers: SQS, Lambda, HTTP/S webhooks, Email, SMS, mobile push
    - Fully managed, scales automatically
    - Up to 12.5 million subscriptions per topic
    - Up to 100,000 topics per account (soft limit)

================================================================
2. SNS ARCHITECTURE
================================================================

  PUBLISHER → [SNS Topic] → [Subscriber 1: SQS Queue]
                           → [Subscriber 2: Lambda]
                           → [Subscriber 3: HTTPS Endpoint]
                           → [Subscriber 4: Email]
                           → [Subscriber 5: SMS]

  Publishers:
    - Application code (SDK)
    - AWS services: CloudWatch Alarms, S3 Events, RDS Events, CodeBuild, etc.

================================================================
3. SNS + SQS FAN-OUT PATTERN (CRITICAL)
================================================================

  Problem: You need to process an event in multiple different systems.
  Solution: Publish to SNS → SNS delivers to multiple SQS queues.

  [Order Placed Event]
        ↓
  [SNS: order-events topic]
        ↓ Fan-out
  ┌─────────────────────────────────────────────────────────┐
  │  [SQS: email-queue]     → [Lambda: send confirmation email]│
  │  [SQS: inventory-queue] → [ECS: decrement inventory]      │
  │  [SQS: analytics-queue] → [Lambda: record to data warehouse]│
  └─────────────────────────────────────────────────────────┘

  Benefits:
    - Each subscriber processes independently
    - Failed inventory processing doesn't affect email sending
    - Each SQS queue has its own DLQ
    - Services can be scaled independently

  SQS queue must allow SNS to publish (queue policy):
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Service": "sns.amazonaws.com" },
      "Action": "sqs:SendMessage",
      "Resource": "arn:aws:sqs:us-east-1:123456789012:inventory-queue",
      "Condition": {
        "ArnEquals": { "aws:SourceArn": "arn:aws:sns:us-east-1:123456789012:order-events" }
      }
    }]
  }

================================================================
4. SNS TOPIC TYPES
================================================================

  STANDARD TOPIC:
    - Unlimited throughput
    - At-least-once delivery
    - Best-effort ordering
    - All subscriber types supported

  FIFO TOPIC:
    - Strictly ordered delivery
    - Exactly-once delivery
    - Only SQS FIFO queues and Lambda can subscribe
    - Throughput: same limits as SQS FIFO (300/sec or 3000/sec batched)
    - Use for: ordered event-driven workflows where duplicates cause problems

================================================================
5. SNS MESSAGE FILTERING
================================================================

  Subscribers can filter messages based on message attributes.
  Only messages matching the filter policy are delivered to that subscriber.
  
  Example: Order topic with message attributes { "status": "placed" / "shipped" / "delivered" }
    - Email subscriber: filter only "status": "placed" → send order confirmation
    - Logistics subscriber: filter "status": "shipped" → notify logistics

  Filter policy (set on subscription):
  {
    "status": ["placed", "shipped"],  // Only receive placed or shipped orders
    "amount": [{"numeric": [">=", 100]}]  // Only orders >= $100
  }

  CLI:
  aws sns set-subscription-attributes \
    --subscription-arn arn:aws:sns:us-east-1:123456789012:OrderEvents:abc123 \
    --attribute-name FilterPolicy \
    --attribute-value '{"status":["placed"]}'

================================================================
6. SNS MESSAGE DELIVERY TYPES
================================================================

  SQS:         Messages stored in queue until consumed (most reliable)
  Lambda:      Direct invocation (synchronous from SNS perspective)
  HTTP/HTTPS:  POST to your webhook endpoint; retry with backoff on failure
  Email:       Plain text or JSON; requires subscription confirmation
  SMS:         Plain text to phone number; charges apply
  Mobile Push: APNs (iOS), FCM (Android), ADM, Baidu via platform applications

  DELIVERY RETRY POLICY (for HTTP/HTTPS):
    - Immediate retries: 3 attempts
    - Pre-backoff: 2 attempts with 1-second delays
    - Backoff: up to 10 attempts with exponential backoff
    - Post-backoff: up to 100,000 attempts (configurable)

================================================================
7. SNS SECURITY
================================================================

  ENCRYPTION:
    - In-transit: HTTPS (TLS) by default
    - At-rest: SSE-SNS or SSE-KMS

  ACCESS CONTROL:
    - IAM policies: who can publish to or subscribe to the topic
    - Topic Policy (resource-based): allows cross-account or service publishing

  # Allow cross-account publishing
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::ACCOUNT_B:root" },
      "Action": "sns:Publish",
      "Resource": "arn:aws:sns:us-east-1:123456789012:my-topic"
    }]
  }

8. JAVA SDK v2 — SNS OPERATIONS
================================================================

  import software.amazon.awssdk.services.sns.SnsClient;
  import software.amazon.awssdk.services.sns.model.*;
  
  private static final SnsClient snsClient = SnsClient.create();
  
  // PUBLISH MESSAGE
  snsClient.publish(PublishRequest.builder()
      .topicArn("arn:aws:sns:us-east-1:123456789012:order-events")
      .message("{\"orderId\":\"123\",\"amount\":99.99,\"status\":\"placed\"}")
      .subject("New Order Placed")
      .messageAttributes(Map.of(
          "status", MessageAttributeValue.builder()
              .dataType("String")
              .stringValue("placed")
              .build(),
          "amount", MessageAttributeValue.builder()
              .dataType("Number")
              .stringValue("99.99")
              .build()
      ))
      .build()
  );
  
  // SUBSCRIBE SQS TO TOPIC
  snsClient.subscribe(SubscribeRequest.builder()
      .topicArn("arn:aws:sns:us-east-1:123456789012:order-events")
      .protocol("sqs")
      .endpoint("arn:aws:sqs:us-east-1:123456789012:inventory-queue")
      .attributes(Map.of(
          "FilterPolicy", "{\"status\":[\"placed\"]}",
          "RawMessageDelivery", "true"  // Send message body as-is, not wrapped in JSON envelope
      ))
      .build()
  );
  
  // CREATE TOPIC
  snsClient.createTopic(CreateTopicRequest.builder()
      .name("order-events")
      .attributes(Map.of(
          "KmsMasterKeyId", "alias/aws/sns",     // SSE-SQS encryption
          "FifoTopic", "false"
      ))
      .build()
  );

9. INTERVIEW QUESTIONS
================================================================

Q: What is the SNS fan-out pattern and why is it useful?
A: Fan-out means publishing a single message to an SNS topic that then delivers
   it to multiple subscribers simultaneously. The pattern: Publish once → SNS
   → SQS-A + SQS-B + Lambda + HTTP endpoint all receive it in parallel. Useful because:
   multiple services need to react to the same event (order placed → email, inventory,
   analytics), each service is decoupled (doesn't know about others), failures in one
   subscriber don't affect others, and each queue has independent scaling and DLQ.

Q: What is SNS message filtering and how does it work?
A: Message filtering lets each subscriber specify a filter policy. SNS only delivers
   messages matching the policy to that subscriber. The filter is based on message
   attributes (metadata sent with the message). Example: a topic for all order events,
   but the email service only subscribes with a filter for status=placed (not shipped/
   delivered), while the logistics service filters for status=shipped. This avoids
   delivering irrelevant messages and reduces processing costs.

Q: What is the difference between SNS Standard Topic and FIFO Topic?
A: Standard Topics offer unlimited throughput, best-effort ordering, and at-least-once
   delivery. FIFO Topics guarantee strict ordering and exactly-once delivery within a
   message group, but are limited to 300-3,000 msg/sec and only support SQS FIFO queue
   and Lambda subscribers. Use FIFO Topics when order matters AND duplicates would cause
   problems — e.g., a workflow where a user's actions must be processed in the exact
   sequence they occurred.

Q: What is Raw Message Delivery in SNS subscriptions to SQS?
A: By default, SNS wraps the message in a JSON envelope with metadata fields (Type,
   TopicArn, Timestamp, UnsubscribeURL, Message, etc.) before sending to SQS. With Raw
   Message Delivery enabled, the SQS message body contains ONLY your original message
   body — no SNS wrapper. Use Raw Message Delivery when: your consumer code expects
   the raw message format without parsing SNS envelope, or you're using the SNS→SQS
   pattern and consumers don't need SNS metadata.
