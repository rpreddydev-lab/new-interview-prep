1. KINESIS OVERVIEW
================================================================

  Amazon Kinesis is a suite of services for real-time data streaming:
  
  ┌─────────────────────────┬────────────────────────────────────────────────────┐
  │ Service                 │ Purpose                                            │
  ├─────────────────────────┼────────────────────────────────────────────────────┤
  │ Kinesis Data Streams    │ Real-time streaming data ingestion/processing       │
  │ Kinesis Data Firehose   │ Fully managed delivery to S3/Redshift/OpenSearch    │
  │ Kinesis Data Analytics  │ SQL/Apache Flink processing on streams              │
  │ Kinesis Video Streams   │ Video streaming (separate product, rare in exams)   │
  └─────────────────────────┴────────────────────────────────────────────────────┘

2. KINESIS DATA STREAMS — ARCHITECTURE
================================================================

  ┌──────────────────────────────────────────────────────────────────┐
  │  KINESIS DATA STREAM                                             │
  │                                                                  │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
  │  │ Shard 1  │  │ Shard 2  │  │ Shard 3  │  │ Shard N  │        │
  │  │1MB/s in  │  │1MB/s in  │  │1MB/s in  │  │1MB/s in  │        │
  │  │2MB/s out │  │2MB/s out │  │2MB/s out │  │2MB/s out │        │
  │  └─────┬────┘  └─────┬────┘  └─────┬────┘  └─────┬────┘        │
  │        └─────────────┴─────────────┴──────────────┘             │
  │                            │                                     │
  │                    ┌───────┴───────┐                             │
  │               Consumer 1     Consumer 2                          │
  └──────────────────────────────────────────────────────────────────┘

  SHARD:
    - Base unit of capacity
    - 1 MB/s or 1,000 records/s write
    - 2 MB/s read (shared across all consumers on that shard)
    - Each record has: Partition Key → Shard, Sequence Number, Data (up to 1 MB)

  PARTITION KEY:
    - Determines which shard the record goes to (MD5 hash of key)
    - Same partition key → same shard → ordering guaranteed within a shard
    - Hot shard problem: if all records use the same partition key

  SEQUENCE NUMBER:
    - Unique ID assigned to each record within a shard
    - Monotonically increasing within a shard

================================================================
3. SHARD CAPACITY MATH
================================================================

  Total Stream Capacity = Number of Shards × Shard Capacity
  
  Example: 10 shards = 10 MB/s ingest, 20 MB/s read
  
  WRITE throttling occurs when:
    - Exceed 1 MB/s per shard — ProvisionedThroughputExceededException
    - Exceed 1,000 records/s per shard
  
  READ throughput:
    - Standard consumers share 2 MB/s per shard across all consumers
    - If 5 consumers on 1 shard → each gets ~400 KB/s
    - Enhanced Fan-Out: each consumer gets dedicated 2 MB/s per shard (push model)

================================================================
4. DATA RETENTION
================================================================

  - Default: 24 hours
  - Extended: up to 7 days (small cost)
  - Long-term: up to 365 days
  
  Unlike SQS, records are NOT deleted after consumption.
  Consumers track their position using SHARD ITERATOR.

================================================================
5. CONSUMER TYPES
================================================================

  ┌──────────────────────────────┬──────────────────────────────────┐
  │ Standard (Classic)           │ Enhanced Fan-Out (EFO)           │
  ├──────────────────────────────┼──────────────────────────────────┤
  │ Pull model (GetRecords API)  │ Push model (SubscribeToShard API)│
  │ 2 MB/s shared per shard      │ 2 MB/s DEDICATED per consumer    │
  │ Up to 5 reads/s per shard    │ ~70ms propagation delay          │
  │ Higher latency (~200ms)      │ Register consumer with stream    │
  │ Free (no extra charge)       │ Extra cost per shard-hour        │
  │ Good for few consumers       │ Good for multiple consumers      │
  └──────────────────────────────┴──────────────────────────────────┘
  
  Lambda integration:
    - Lambda uses Enhanced Fan-Out internally for low-latency trigger
    - Parallelization Factor: 1–10 concurrent batches per shard

6. RESHARDING — SCALING THE STREAM
================================================================

  SHARD SPLIT:
    - Divide one shard into two (increase capacity)
    - Provide the shard ID and the new hash key range split point
    - Hot shard: split the hot shard specifically
  
  SHARD MERGE:
    - Combine two ADJACENT shards into one (decrease capacity/cost)
    - Both shards must be adjacent in the hash key range
  
  CLI:
  # List shards
  aws kinesis list-shards --stream-name my-stream
  
  # Split a shard
  aws kinesis split-shard \
    --stream-name my-stream \
    --shard-to-split shardId-000000000000 \
    --new-starting-hash-key 170141183460469231731687303715884105728
  
  # Merge adjacent shards
  aws kinesis merge-shards \
    --stream-name my-stream \
    --shard-to-merge shardId-000000000000 \
    --adjacent-shard-to-merge shardId-000000000001

7. KINESIS DATA FIREHOSE
================================================================

  Fully managed delivery pipeline — no shards to manage.
  
  DESTINATIONS:
    - Amazon S3 (most common)
    - Amazon Redshift (via S3 staging)
    - Amazon OpenSearch Service (Elasticsearch)
    - HTTP endpoint (custom)
    - Splunk, Datadog, New Relic (partner destinations)
  
  KEY FEATURES:
    - Automatic scaling
    - Built-in data transformation (via Lambda)
    - Compression (GZIP, Snappy, ZIP)
    - Encryption (SSE-KMS)
    - Data format conversion (JSON → Parquet/ORC using Glue schema)
    - Buffering (by size or time before writing to destination)
  
  BUFFERING:
    - Size buffer: 1 MB – 128 MB (deliver when buffer is full)
    - Interval buffer: 60 s – 900 s (deliver on interval)
    - Whichever condition is reached first triggers delivery
  
  FIREHOSE ARCHITECTURE:
  
  Producers → Firehose Delivery Stream → [Lambda Transform] → Destination
  
  S3 PREFIX PATTERN:
    - Default: s3://my-bucket/2024/01/15/
    - Custom: s3://my-bucket/events/year=!{timestamp:yyyy}/month=!{timestamp:MM}/
  
  CLI:
  aws firehose create-delivery-stream \
    --delivery-stream-name my-stream \
    --s3-destination-configuration '{
      "RoleARN": "arn:aws:iam::123456789012:role/firehose-role",
      "BucketARN": "arn:aws:s3:::my-data-lake",
      "Prefix": "events/",
      "BufferingHints": {"SizeInMBs": 5, "IntervalInSeconds": 300},
      "CompressionFormat": "GZIP"
    }'

8. KINESIS DATA STREAMS vs FIREHOSE
================================================================

  ┌─────────────────────┬─────────────────────┬──────────────────────────┐
  │ Feature             │ Data Streams        │ Firehose                 │
  ├─────────────────────┼─────────────────────┼──────────────────────────┤
  │ Management          │ You manage shards   │ Fully managed            │
  │ Latency             │ Real-time (~200ms)  │ Near real-time (60s min) │
  │ Consumers           │ Multiple custom     │ One destination          │
  │ Data retention      │ 1 – 365 days        │ No retention (delivery)  │
  │ Replay              │ Yes                 │ No                       │
  │ Lambda transform    │ Requires Lambda     │ Built-in                 │
  │ Destinations        │ Any (you code)      │ S3/Redshift/OpenSearch   │
  │ Cost model          │ Per shard-hour      │ Per GB ingested          │
  │ Record size         │ Up to 1 MB          │ Up to 1 MB               │
  └─────────────────────┴─────────────────────┴──────────────────────────┘

9. JAVA SDK v2 — KINESIS PRODUCER
================================================================

  import software.amazon.awssdk.services.kinesis.KinesisClient;
  import software.amazon.awssdk.services.kinesis.model.*;
  import software.amazon.awssdk.core.SdkBytes;
  
  private static final KinesisClient kinesisClient = KinesisClient.create();
  
  // PUT A SINGLE RECORD
  public void putRecord(String streamName, String orderId, String data) {
      PutRecordResponse response = kinesisClient.putRecord(
          PutRecordRequest.builder()
              .streamName(streamName)
              .partitionKey(orderId)            // determines shard
              .data(SdkBytes.fromUtf8String(data))
              .build()
      );
      System.out.println("Shard: " + response.shardId());
      System.out.println("Sequence: " + response.sequenceNumber());
  }
  
  // PUT MULTIPLE RECORDS (batch, up to 500 records or 5 MB)
  public void putRecords(String streamName, List<Order> orders) {
      List<PutRecordsRequestEntry> entries = orders.stream()
          .map(order -> PutRecordsRequestEntry.builder()
              .partitionKey(order.getId())
              .data(SdkBytes.fromUtf8String(order.toJson()))
              .build())
          .collect(Collectors.toList());
  
      PutRecordsResponse response = kinesisClient.putRecords(
          PutRecordsRequest.builder()
              .streamName(streamName)
              .records(entries)
              .build()
      );
  
      if (response.failedRecordCount() > 0) {
          // handle partial failures — retry failed records
          System.err.println("Failed records: " + response.failedRecordCount());
      }
  }
  
  // GET RECORDS (Standard Consumer)
  public void consumeRecords(String streamName, String shardId) {
      // Get starting shard iterator
      GetShardIteratorResponse iterResponse = kinesisClient.getShardIterator(
          GetShardIteratorRequest.builder()
              .streamName(streamName)
              .shardId(shardId)
              .shardIteratorType(ShardIteratorType.TRIM_HORIZON) // from oldest record
              .build()
      );
  
      String shardIterator = iterResponse.shardIterator();
  
      while (shardIterator != null) {
          GetRecordsResponse records = kinesisClient.getRecords(
              GetRecordsRequest.builder()
                  .shardIterator(shardIterator)
                  .limit(100)
                  .build()
          );
  
          for (Record record : records.records()) {
              String data = record.data().asUtf8String();
              System.out.println("Record: " + data);
          }
  
          shardIterator = records.nextShardIterator();
          // Add delay to avoid exceeding 5 reads/s per shard limit
          Thread.sleep(200);
      }
  }

10. LAMBDA + KINESIS DATA STREAMS
================================================================

  Lambda is triggered per batch of records from a shard.
  
  import com.amazonaws.services.lambda.runtime.events.KinesisEvent;
  
  public class KinesisLambdaHandler
      implements RequestHandler<KinesisEvent, Void> {
  
    @Override
    public Void handleRequest(KinesisEvent event, Context context) {
        for (KinesisEvent.KinesisEventRecord record : event.getRecords()) {
            String data = record.getKinesis().getData().toString();
            // process record
        }
        return null;
    }
  }
  
  Lambda event source mapping config:
  aws lambda create-event-source-mapping \
    --function-name process-stream \
    --event-source-arn arn:aws:kinesis:us-east-1:123456789012:stream/my-stream \
    --starting-position TRIM_HORIZON \
    --batch-size 100 \
    --parallelization-factor 2 \
    --bisect-batch-on-function-error true \
    --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:..."}}'

12. INTERVIEW QUESTIONS
================================================================

Q: What is a Kinesis shard? How do you determine how many shards you need?
A: A shard is the base throughput unit — 1 MB/s or 1,000 records/s ingest, 2 MB/s read.
   To determine shard count:
     - Incoming throughput: shards = ceil(MB/s ÷ 1)
     - Outgoing throughput: shards = ceil(MB/s ÷ 2) if using standard consumers
   Example: 5 MB/s ingest, 3 consumers each reading 5 MB/s:
     - Ingest: 5 shards
     - Read with standard: 15 MB/s needed ÷ 2 MB/s = 8 shards, OR use Enhanced Fan-Out
       so each consumer gets dedicated 2 MB/s per shard regardless of other consumers.
   You also need to consider record count limits (1,000 records/s per shard).

Q: How does ordering work in Kinesis? Compare to SQS FIFO.
A: Kinesis guarantees ordering within a shard. Records with the same partition key always
   go to the same shard, ensuring ordered processing for that key. Example: all events for
   customer-123 use partition key "customer-123" → same shard → ordered processing.
   
   SQS FIFO also guarantees ordering but within a Message Group ID, and is limited to
   3,000 msg/s (with batching) and 300 msg/s (without batching). Kinesis can handle much
   higher throughput. Use Kinesis when you need high-throughput ordered streaming; use
   SQS FIFO for lower-volume strictly-ordered task queuing.

Q: What is the difference between Kinesis Data Streams and Kinesis Firehose?
A: Data Streams is a real-time data stream where you write custom consumers, retain data
   for up to 365 days, and can have multiple independent consumers replay data. Firehose
   is a managed delivery pipeline to specific AWS destinations (S3, Redshift, OpenSearch);
   it has no replay, buffers for 60+ seconds, and manages scaling automatically. Use Data
   Streams when you need real-time processing, multiple consumers, or replay. Use Firehose
   when you just want to land data in S3 or Redshift with minimal operational overhead.

Q: What is Enhanced Fan-Out and when should you use it?
A: Enhanced Fan-Out (EFO) gives each registered consumer its own dedicated 2 MB/s
   throughput per shard, using a push-based (SubscribeToShard) model instead of polling.
   Without EFO, all standard consumers share the 2 MB/s per shard.
   Use EFO when: multiple consumers are competing and getting throttled, you need
   ~70ms latency instead of ~200ms, or you're building multiple independent analytics
   pipelines on the same stream. Extra cost: per shard-hour per consumer.
