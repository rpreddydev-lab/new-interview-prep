================================================================
AWS INTERVIEW QUESTIONS — NETWORKING AND VPC
================================================================

Q1: What is a VPC? What is the difference between public and private subnets?

A: VPC (Virtual Private Cloud): Your own private, logically isolated network within AWS.
   You control: IP address range (CIDR block), subnets, route tables, gateways, and security.
   All resources you launch go into a VPC.

   Public Subnet:
   - Has a route in its route table to an Internet Gateway (IGW).
   - Resources assigned a public IP can send and receive traffic to/from the internet.
   - Place here: ALB, NAT Gateway, Bastion hosts, anything that must be internet-facing.

   Private Subnet:
   - NO route to an IGW. Resources cannot be directly reached from the internet.
   - Can reach the internet OUTBOUND only via a NAT Gateway (in the public subnet).
   - Place here: EC2 app servers, ECS tasks, RDS instances, ElastiCache, internal APIs.

   Isolated Subnet (common best practice):
   - No route to IGW and NO route to NAT Gateway — completely air-gapped.
   - Place here: Databases, data stores that should never initiate outbound internet calls.

   Standard HA design:
   - 2+ Availability Zones (AZs) for HA.
   - Each AZ: 1 public subnet, 1 private subnet (optionally 1 isolated subnet).
   - ALB spans public subnets across AZs.
   - App tier in private subnets, Auto Scaling Group across AZs.
   - RDS Multi-AZ in isolated subnets.

Q2: What is a NAT Gateway and why do private subnet resources need it?

A: Private subnet resources have no public IP and no route to the internet.
   They cannot receive incoming connections from the internet.
   But they often need OUTBOUND internet access (downloading packages, calling external APIs,
   reaching AWS services not accessible via VPC Endpoints).

   NAT Gateway:
   - Sits in the PUBLIC subnet with an Elastic IP (static public IP).
   - Private subnet route table: 0.0.0.0/0 → NAT Gateway.
   - NAT Gateway forwards outbound requests to the IGW, receives responses, routes back.
   - The internet sees only the NAT Gateway's Elastic IP (source IP is hidden).
   - AWS-managed: automatically scales, HA within a single AZ.
   - Cost: ~$0.045/hour (~$32/month) + $0.045/GB data processed.

   For HA: deploy one NAT Gateway per AZ, private subnets in each AZ route to their local NAT.
   (A single NAT Gateway is a single point of failure for multiple AZs.)

   NAT Gateway vs. NAT Instance:
   - NAT Gateway: managed, scales automatically, no maintenance, HA within AZ.
   - NAT Instance: EC2 you manage. Cheaper for low traffic, but you handle HA, patching, scaling.
   - Best practice: Use NAT Gateway. Use NAT Instance only for extreme cost optimization.

   Cost optimization tip:
   - S3 and DynamoDB access through NAT Gateway is expensive for high-volume traffic.
   - Use VPC Gateway Endpoints for S3/DynamoDB (free, keeps traffic off NAT).

Q3: What is a VPC Endpoint? Difference between Gateway and Interface Endpoints?

A: VPC Endpoint: Connect to AWS services from your VPC without traffic leaving the AWS network.
   No internet gateway, no NAT gateway, no public IP required.
   Benefits: Better security (private traffic), lower latency, reduced data transfer costs.

   Gateway Endpoint:
   - FREE.
   - Supported ONLY for: S3 and DynamoDB.
   - Implemented as a route table entry (add to private/isolated subnet route tables).
   - Traffic from your VPC to S3/DynamoDB goes through AWS's private backbone, not the internet.
   - Always use this for S3 and DynamoDB in every VPC. Zero cost, immediate benefit.

   Interface Endpoint (AWS PrivateLink):
   - Creates an ENI (Elastic Network Interface) with a PRIVATE IP in your subnet.
   - Supported for: most AWS services (SQS, SNS, Secrets Manager, SSM, KMS, ECR, CloudWatch, etc.)
     and third-party SaaS services (via PrivateLink marketplace).
   - Cost: $0.01/hour per AZ per endpoint + $0.01/GB data processed (~$7.30/month per endpoint/AZ).
   - DNS: the service's public DNS hostname automatically resolves to the private IP in your VPC
     (enabled by "Private DNS" — check the box when creating the endpoint).
   - No code changes needed in your application.

   Best practice:
   - ALWAYS create Gateway Endpoints for S3 and DynamoDB in every VPC. Free.
   - Create Interface Endpoints for: Secrets Manager (so Lambda/ECS in private subnets
     can retrieve secrets without NAT), SSM (EC2 instances without internet access),
     ECR (pull container images without NAT Gateway).

Q4: What is VPC Peering? When would you use Transit Gateway instead?

A: VPC Peering:
   - Private connection between two VPCs (same or different account/region).
   - Traffic stays on AWS private network (no internet).
   - NON-TRANSITIVE: if VPC A peers with VPC B, and B peers with VPC C,
     A cannot reach C through B. You need a direct A-C peering.
   - No bandwidth limit, no gateway bottleneck.
   - Use for: simple 1:1 or small number of VPC connections.
   - Cost: data transfer charges (no peering setup cost).

   Transit Gateway (TGW):
   - Hub-and-spoke model. All VPCs attach to the TGW. TGW routes between them.
   - TRANSITIVE routing: VPC A can reach VPC C through the TGW.
   - Scales to thousands of VPCs and on-premises connections.
   - Centralized route management (one route table to manage).
   - Also connects to VPN and Direct Connect.
   - Cost: TGW attachment fee (~$0.05/hr per attachment) + data processing ($0.02/GB).

   When to use which:
   - 1-5 VPCs: VPC Peering (simpler, cheaper).
   - Many VPCs (6+) or need transitive routing: Transit Gateway.
   - Connecting on-premises to many VPCs: Transit Gateway + Direct Connect/VPN.

Q5: What is Route 53? How does DNS failover work?

A: Route 53: AWS's managed DNS service and domain registrar.

   Core record types:
   - A: hostname → IPv4 address
   - AAAA: hostname → IPv6 address
   - CNAME: hostname → another hostname (cannot be used for zone apex/root domain)
   - Alias: AWS-specific. Like CNAME but can be used for zone apex.
     Resolves directly to AWS resources (ALB, CloudFront, S3 website, etc.).
     Free queries for Alias records pointing to AWS services.
   - MX: mail server
   - TXT: verification, SPF

   Routing Policies:
   - Simple: one record, returns the value (no health checks).
   - Weighted: split traffic by percentage (e.g., 90% to v1, 10% to v2 for blue/green).
   - Latency: route to the region with the lowest latency for the user.
   - Failover: Active/passive. Primary record with health check; if unhealthy, route to secondary.
   - Geolocation: route based on user's geographic location.
   - Geoproximity: route based on location with optional bias toward/away from a region.
   - Multivalue Answer: return up to 8 healthy records; client-side DNS load balancing.
   - IP-Based: route based on client's IP prefix (CIDR).

   DNS Failover:
   - Attach health checks to Route 53 records.
   - Health checks: HTTP/HTTPS endpoint check, TCP check, or CloudWatch alarm.
   - If primary endpoint fails health check, Route 53 stops returning that IP.
   - TTL determines how quickly clients see the change (keep TTL low during planned changes).

Q6: What is CloudFront and how does it work with S3?

A: CloudFront: AWS Content Delivery Network (CDN) with 400+ edge locations worldwide.
   Caches content at edge locations close to users → lower latency, less origin load.

   How it works:
   1. User requests content.
   2. DNS resolves to nearest CloudFront edge location.
   3. If edge has cached content (cache hit): returns immediately.
   4. If no cache (cache miss): forwards to origin (S3, ALB, EC2, custom HTTP server).
   5. Caches response at edge for subsequent requests (TTL-based).

   S3 + CloudFront (static website pattern):
   - S3 bucket stores objects (HTML, CSS, JS, images).
   - CloudFront distribution configured with S3 as origin.
   - S3 bucket can be PRIVATE (no public access) — CloudFront uses Origin Access Control (OAC)
     to access S3 on behalf of users.
   - Custom domain + SSL certificate (ACM certificate in us-east-1).
   - Benefits: global performance, DDoS protection (Shield Standard included), HTTPS enforcement.

   Security features:
   - WAF (Web Application Firewall): attach to CloudFront for SQL injection, XSS, rate limiting.
   - Signed URLs / Signed Cookies: time-limited access to private content (paid video, premium downloads).
   - Geo-restriction: block or allow access from specific countries.
   - Field-level encryption: encrypt specific POST fields at the edge (credit card numbers).

   Cache invalidation:
   - CloudFront caches based on URL + headers/query strings (per cache policy).
   - To force edge refresh: create a cache invalidation (/* or specific paths). Cost: $0.005/path.
   - Better practice: use versioned file names (app-v2.js) to avoid invalidation costs.
