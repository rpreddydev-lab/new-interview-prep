================================================================
AWS INTERVIEW QUESTIONS — IAM AND SECURITY
================================================================

Q1: What is the difference between an IAM Role and an IAM User?

A: IAM User is a permanent identity with long-term credentials (access key + secret).
   Represents a person or service that always authenticates with the same credentials.
   Supports MFA, console password, and programmatic access keys.

   IAM Role is a temporary identity with NO permanent credentials.
   It is assumed by trusted entities (EC2, Lambda, another AWS account, federated users)
   and issues short-lived credentials via STS (15 minutes to 12 hours).

   Key differences:
   - Users: long-term credentials stored on disk / in environment variables — security risk.
   - Roles: no credentials stored anywhere; the SDK fetches them automatically from instance
     metadata (169.254.169.254) or the Lambda execution environment.

   Best practice: Use Roles for ALL application and service access.
   Never embed access keys in code, config files, or EC2/Lambda environment variables.
   Assign IAM Roles to EC2 instances, ECS tasks, Lambda functions — the SDK handles
   credential fetching and rotation automatically.

   Interview answer template:
   "IAM Users are for human identities and legacy service accounts that can't assume roles.
   For all application workloads — EC2, Lambda, ECS, EKS — I use IAM Roles. The SDK
   automatically fetches temporary credentials from the instance metadata service, so I
   never store long-term credentials anywhere."

Q2: What is the principle of least privilege and how do you enforce it in AWS?

A: Least privilege = grant only the minimum permissions needed to do the job. Nothing more.

   How to enforce it in AWS:

   1. Start with zero. Add only what is explicitly needed.
   2. Use resource-level permissions, not wildcards:
      BAD:  "Resource": "*"
      GOOD: "Resource": "arn:aws:s3:::my-bucket/*"

   3. Use IAM Access Analyzer:
      - Generates least-privilege policies from CloudTrail activity logs.
      - Identifies external access to resources (S3 buckets, KMS keys, etc.).

   4. Use Permission Boundaries:
      - Set the maximum permissions a role or user can ever have.
      - Even if an inline policy grants s3:*, a permission boundary can cap it.

   5. Use Service Control Policies (SCPs) in AWS Organizations:
      - Org-wide guardrails. Even admins cannot bypass SCPs.
      - Example: deny ec2:* in regions you don't use.

   6. Review IAM Access Advisor:
      - Shows which services a role/user has actually accessed in the last 90 days.
      - Remove permissions for services never used.

   7. Use IAM Credential Report:
      - Lists all users, when their credentials were last used, MFA status.
      - Helps identify stale access keys and accounts without MFA.

Q3: What are the IAM Policy types? Managed vs. Inline?

A: AWS Managed Policies:
   - Created and maintained by AWS (e.g., AmazonS3ReadOnlyAccess, AWSLambdaBasicExecutionRole).
   - Cannot be modified by you.
   - AWS updates them as services evolve.
   - Easy to attach to multiple identities.
   - Acceptable for standard permissions.

   Customer Managed Policies:
   - Created and owned by you.
   - Reusable: attach to multiple users, groups, or roles.
   - Version-controlled: IAM keeps up to 5 versions, you can roll back.
   - Best practice for any custom permission logic.

   Inline Policies:
   - Embedded directly into a single User, Group, or Role.
   - Not reusable. Deleted when the identity is deleted (strict 1:1 relationship).
   - Hard to audit across the account.
   - Only use when a policy MUST be strictly tied to one identity and deleted with it.

   Best practice: Customer Managed Policies for everything custom.
   Avoid inline policies except for specific strict-binding requirements.

Q4: How does STS AssumeRole work? Walk me through the flow.

A: STS (Security Token Service) issues temporary credentials.
   AssumeRole is the most common STS operation.

   Flow:
   1. Principal (EC2 instance, Lambda, another AWS account's user) calls:
      sts:AssumeRole with the target Role ARN.

   2. IAM checks the Role's Trust Policy:
      - Is this principal listed as a trusted entity?
      - Does the principal have sts:AssumeRole permission in their own policy?

   3. If both checks pass, STS returns:
      - AccessKeyId (temporary)
      - SecretAccessKey (temporary)
      - SessionToken (must be included in all API calls)
      - Expiration (15 min to 12 hours)

   4. The caller uses these credentials to make API calls with the role's permissions.

   Common use cases:
   - Cross-account access: Role in Account B trusts Account A's EC2 role.
     Account A's EC2 calls AssumeRole on Account B's role → gets temporary access.
   - Service access: EC2 instance role assumed automatically by the SDK.
   - SAML federation: Corporate IdP (Okta, ADFS) authenticates user,
     STS exchanges SAML assertion for AWS credentials (AssumeRoleWithSAML).
   - OIDC/Cognito: web/mobile app tokens exchanged for AWS credentials (AssumeRoleWithWebIdentity).

Q5: What is KMS? When do you use Customer Managed Keys (CMKs) vs. AWS Managed Keys?

A: KMS (Key Management Service): managed service for creating and controlling encryption keys.
   Used by almost all AWS services for at-rest encryption (S3, RDS, EBS, DynamoDB, Secrets Manager).

   AWS Managed Keys:
   - Created automatically by AWS services (key aliases like aws/s3, aws/rds).
   - Free to use.
   - You CANNOT control the key policy, rotation schedule, or cross-account sharing.
   - Automatic annual rotation (for symmetric keys).
   - Acceptable when you just need encryption and have no specific key control requirements.

   Customer Managed Keys (CMKs):
   - You create and control the key.
   - Define exactly who can use and administer the key (key policy + IAM).
   - Enable automatic annual rotation (optional, you control the schedule).
   - Disable or schedule deletion to make encrypted data permanently inaccessible.
   - Share with other AWS accounts for cross-account encryption.
   - Use key grants for temporary, delegated access.
   - All usage logged in CloudTrail (who encrypted/decrypted what, when).
   - Cost: $1/month per CMK + $0.03 per 10,000 API calls.

   Use CMKs when:
   - Compliance requires audit trails of key usage.
   - You need to restrict which accounts/services can decrypt.
   - You need the ability to disable/delete the key (data becomes permanently unreadable).
   - Multi-region replication of keys for Disaster Recovery.

Q6: What is the difference between Security Groups and NACLs?

A: Security Groups (SG):
   - STATEFUL: if inbound traffic is allowed, the response is automatically allowed.
   - Applied at the INSTANCE/ENI level.
   - ALLOW rules only — cannot create deny rules.
   - Can reference other Security Groups (e.g., allow all traffic from ALB SG to App SG).
   - ALL rules are evaluated; most permissive wins.

   NACLs (Network Access Control Lists):
   - STATELESS: must explicitly allow both inbound AND outbound for each traffic flow.
   - Applied at the SUBNET level (affects ALL instances in the subnet).
   - ALLOW and DENY rules.
   - Rules processed in NUMBER ORDER (lowest rule number first); first match wins.
   - Use to block known bad IP ranges at the network level.

   When to use each:
   - Security Groups: always — fine-grained control at the instance level.
   - NACLs: sparingly — for subnet-level blocking of specific IP ranges (e.g., DDoS mitigation).

   Best practice:
   - Restrict SGs so only ALB SG can reach App SG, only App SG can reach DB SG.
   - Use NACLs to block known malicious IP ranges as an additional layer.
   - Default NACL allows all traffic. Custom NACLs deny all by default.
