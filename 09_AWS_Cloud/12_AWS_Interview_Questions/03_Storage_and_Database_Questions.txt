================================================================
AWS INTERVIEW QUESTIONS — STORAGE AND DATABASES
================================================================

Q1: What are the S3 storage classes and when do you use each?

A: S3 Standard:
   - Frequent access. 99.99% availability. Replicated across 3+ AZs.
   - No retrieval fee. No minimum storage duration.
   - Use: Active application data, images/videos served to users, ML datasets.

   S3 Standard-IA (Infrequent Access):
   - Same durability/AZ replication as Standard. 99.9% availability.
   - Lower storage cost ($0.0125/GB vs. $0.023/GB), but retrieval fee ($0.01/GB).
   - Minimum 30-day storage charge.
   - Use: Backups, DR files accessed monthly or quarterly.

   S3 One Zone-IA:
   - Same as Standard-IA but stored in a SINGLE AZ only.
   - Cheaper still, but data lost if that AZ is destroyed.
   - Minimum 30-day storage charge.
   - Use: Reproducible data (thumbnails, transcoded video) that can be regenerated.

   S3 Glacier Instant Retrieval:
   - Archive storage. Millisecond retrieval (same as Standard-IA but cheaper).
   - Minimum 90-day storage charge.
   - Use: Medical images, news archives, compliance data accessed quarterly or less.

   S3 Glacier Flexible Retrieval:
   - Archive. Retrieval time: Expedited (1-5 min), Standard (3-5 hrs), Bulk (5-12 hrs).
   - Minimum 90-day storage charge.
   - Use: Backups and archives where occasional retrieval with flexible SLA is acceptable.

   S3 Glacier Deep Archive:
   - Cheapest storage in AWS (~$0.00099/GB/month).
   - Retrieval time: Standard (12 hrs), Bulk (48 hrs).
   - Minimum 180-day storage charge.
   - Use: Long-term compliance archives (7-10 year retention), rarely or never retrieved.

   S3 Intelligent-Tiering:
   - Automatically moves objects between tiers based on access patterns.
   - Small monitoring fee per object ($0.0025/1,000 objects).
   - No retrieval fees. No minimum storage charge for frequent/infrequent access tiers.
   - Use: Unknown or unpredictable access patterns.

Q2: When would you choose DynamoDB over RDS?

A: Choose DynamoDB when:
   - Need single-digit millisecond latency at ANY scale (millions of req/sec).
   - Access patterns are known and fixed at design time (schema driven by access, not normalization).
   - Data fits a key-value or document model with no complex JOINs.
   - Need global distribution (DynamoDB Global Tables: multi-region active-active).
   - Want serverless pricing (pay-per-request, scales to zero at no cost).
   - Schema varies per item (flexible attributes).
   - Need event streaming (DynamoDB Streams → Lambda).

   Choose RDS when:
   - Need complex SQL: JOINs, aggregations, window functions, GROUP BY, subqueries.
   - Strong ACID transactions across multiple tables/rows.
   - Team is SQL-proficient; business reports require ad-hoc queries.
   - Normalized relational data model is the right fit.
   - Need stored procedures, complex triggers, full SQL feature set.
   - Migrating an existing RDBMS application.

   Critical DynamoDB interview insight:
   "Design starts with access patterns, not data model."
   Before touching DynamoDB, answer: "What queries will this application run?"
   That determines table structure, partition key, sort key, and GSIs.
   Getting this wrong is the #1 DynamoDB mistake — you cannot easily change it later.

Q3: What is a DynamoDB partition key and sort key? How do you choose a good partition key?

A: Partition Key (PK):
   - DynamoDB hashes the PK to determine which physical partition stores the item.
   - All items with the same PK live in the same partition.
   - Queries can only retrieve items from ONE partition at a time.
   - A "hot partition" occurs when too many requests target the same PK value.

   Sort Key (SK) — optional:
   - Secondary dimension within a partition. Items sorted by SK within the partition.
   - Enables range queries: get all items where PK = "USER#123" AND SK begins_with "ORDER#"
   - Composite key (PK + SK) allows multiple items per PK.

   Choosing a good Partition Key:
   BAD characteristics:
   - Low cardinality: few distinct values → hot partitions.
     Example: status ("ACTIVE" / "INACTIVE") — 2 values, all reads hit 2 partitions.
   - Skewed access: some values get 99% of traffic → hot partition throttling.

   GOOD characteristics:
   - High cardinality: millions of distinct values.
   - Uniform access distribution: no single value is accessed far more than others.
   - Examples: userId, orderId, productId, sessionId.

   Single Table Design pattern:
   Store multiple entity types in one table using generic PK/SK:
     PK = "USER#123",  SK = "PROFILE"      → user profile item
     PK = "USER#123",  SK = "ORDER#456"    → order for that user
     PK = "USER#123",  SK = "ORDER#789"    → another order
     PK = "ORDER#456", SK = "ITEM#001"     → order line item

   This allows:
   - Get user profile: query PK = "USER#123", SK = "PROFILE"
   - Get user + all orders: query PK = "USER#123" (returns all SK values)
   - Get specific order: query PK = "ORDER#456"
   All of these are single-table operations — no JOINs, ultra-fast.

Q4: What is the difference between RDS Multi-AZ and Read Replicas?

A: RDS Multi-AZ (High Availability):
   - AWS maintains a STANDBY replica in a different AZ using SYNCHRONOUS replication.
   - The standby is NOT accessible for reads or writes — it only exists for failover.
   - If the primary fails (hardware, AZ outage), DNS automatically failovers in 60-120 seconds.
   - Application reconnects to same endpoint; no code change needed.
   - Same storage cost roughly doubles the instance cost.
   - Purpose: AVAILABILITY and DURABILITY. No read performance benefit.

   RDS Read Replicas (Read Scalability):
   - One or more readable replica instances using ASYNCHRONOUS replication.
   - Replicas ARE accessible for SELECT queries — route reporting/analytics there.
   - Can be in the same AZ, different AZ (HA), or different region (cross-region DR).
   - Replication lag: usually milliseconds, but can increase under heavy write load.
   - Can be promoted to a standalone RDS instance (for DR, migration, or testing).
   - Purpose: READ SCALING. Offload SELECT queries from the primary.

   Combining both:
   For production: use Multi-AZ for HA + Read Replicas for read scaling.
   Both are independent — Multi-AZ standby is not a Read Replica.

   Aurora note:
   Aurora handles both natively and more efficiently:
   - Up to 15 Read Replicas, all readable, failover in under 30 seconds.
   - Storage is automatically replicated 6 ways across 3 AZs — no manual Multi-AZ config needed.
   - Aurora Global Database: cross-region reads with <1 second replication lag.

Q5: What is ElastiCache? Redis vs. Memcached on AWS?

A: ElastiCache: AWS-managed in-memory caching. Reduces database load and improves latency.
   Typical use: cache database query results, session storage, leaderboards, rate limiting.

   ElastiCache for Redis:
   - Rich data structures: strings, lists, sets, sorted sets, hashes, streams, bitmaps.
   - Persistence: RDB snapshots (point-in-time) and AOF log (append-only, replay on restart).
   - Pub/Sub messaging.
   - Sorted sets for leaderboards (O(log N) rank operations).
   - Cluster mode: horizontal sharding across multiple nodes for data that exceeds one node.
   - Replication + Multi-AZ: automatic failover to replica if primary fails.
   - Lua scripting for atomic compound operations.
   Use for: Session storage, leaderboards, rate limiting, pub/sub, distributed locks,
            queues, any use case needing data persistence or complex types.

   ElastiCache for Memcached:
   - Simple key-value only (no rich data structures).
   - No persistence (data lost on restart).
   - Multi-threaded: can use multiple CPU cores efficiently.
   - Simpler horizontal scaling (built-in sharding, consistent hashing).
   - No replication. No automatic failover.
   Use for: Pure, simple caching when you don't need any Redis features.

   Decision:
   Default: Redis. It does everything Memcached does, plus persistence, replication,
   rich data structures, pub/sub, and sorted sets.
   Only choose Memcached if: need extreme multi-threaded cache performance
   and explicitly don't need Redis features.

Q6: What is the difference between S3 and EBS and EFS?

A: S3 (Simple Storage Service):
   - Object storage. Not a file system. Access via HTTP API (GET, PUT, DELETE).
   - Cannot be "mounted" as a drive in the traditional sense.
   - Massive scale: virtually unlimited storage, objects up to 5 TB each.
   - Global namespace within a region. Public/private access controls.
   - Use for: Static files, images, videos, backups, data lake, ML training data,
              CloudFront origin, Lambda deployment packages.

   EBS (Elastic Block Store):
   - Block storage. Mounted to ONE EC2 instance at a time (like a virtual hard drive).
   - Low latency: microseconds to milliseconds for I/O.
   - Types: gp3 (general purpose SSD, default), io2 (provisioned IOPS for high performance),
            st1 (throughput HDD), sc1 (cold HDD).
   - Tied to one AZ. To move to another AZ: create snapshot → restore in new AZ.
   - Persists independently of the EC2 instance (survives instance termination if not deleted).
   - Use for: OS volumes, database storage (RDS uses EBS), any need for a mounted drive.

   EFS (Elastic File System):
   - Managed NFS (Network File System). Can be mounted on MANY EC2 instances simultaneously.
   - Elastic: grows and shrinks automatically. No capacity planning.
   - Multi-AZ: data replicated across multiple AZs automatically.
   - Higher latency than EBS. More expensive than EBS.
   - Performance modes: General Purpose (low latency) and Max I/O (high throughput).
   - Use for: Shared file storage across multiple instances (content management, home dirs,
              code repos shared by fleet of web servers, shared configuration).

   Summary:
   S3:  Object store. HTTP API. Unlimited scale. Web-accessible.
   EBS: Block device. One instance. Low latency. Single AZ.
   EFS: Network file system. Many instances. Multi-AZ. Shared access.
