1. THE CLASSIC TESTING PYRAMID
================================================================================

Introduced by Mike Cohn, the Testing Pyramid defines three layers:

               /\
              /  \
             / E2E\          ← Few, slow, expensive, high confidence
            /──────\
           /Integrat\        ← Some, moderate speed, good confidence
          /──────────\
         / Unit Tests \      ← Many, fast, cheap, low confidence per test
        /──────────────\

PYRAMID PRINCIPLES:
  1. Write more unit tests than integration tests
  2. Write more integration tests than E2E tests
  3. Move testing "left" (earlier in the process)
  4. Faster feedback = more tests of that type

RATIO GUIDELINE (Classic):
  Unit:        70%
  Integration: 20%
  E2E:         10%

2. THE TESTING TROPHY (MODERN ALTERNATIVE)
================================================================================

Proposed by Kent C. Dodds, the Testing Trophy challenges the pyramid
for front-end applications:

            ┌──────────────┐
            │   E2E Tests  │   (Top, fewest)
            ├──────────────┤
            │  Integration │   (WIDEST - most tests here)
            │    Tests     │
            ├──────────────┤
            │  Unit Tests  │   (Fewer than integration)
            ├──────────────┤
            │ Static Tests │   (TypeScript, ESLint - always on)
            └──────────────┘

WHY THE TROPHY FOR FRONT-END:
  - UI components are inherently about user interaction, not isolated logic
  - Integration tests in React Testing Library test components with their
    real internal logic, hooks, and DOM output
  - This gives better confidence than pure unit tests with heavy mocking
  - Unit tests are still valuable for utilities, reducers, pure functions

KEY INSIGHT FROM KENT C. DODDS:
  "The more your tests resemble the way your software is used,
   the more confidence they can give you."

3. EACH LAYER EXPLAINED
================================================================================

────────────────────────────────────────────────────────────────────────────────
STATIC ANALYSIS (Base Layer)
────────────────────────────────────────────────────────────────────────────────
Tools: TypeScript, ESLint, Prettier, Husky (pre-commit hooks)

What it catches:
  - Typos in variable/function names
  - Type mismatches
  - Undefined variables
  - Unreachable code
  - Formatting inconsistencies

Cost: Near zero — runs during development in the editor
Speed: Instant (IDE) or seconds (CI)

Example:
  // TypeScript catches this at compile time:
  function greet(name: string) { ... }
  greet(42); // Error: Argument of type 'number' is not assignable to 'string'

────────────────────────────────────────────────────────────────────────────────
UNIT TESTS
────────────────────────────────────────────────────────────────────────────────
Test a single unit (function, class, component) in complete isolation.
All dependencies are mocked.

BEST FOR:
  - Pure functions (math utils, formatters, validators)
  - Business logic (reducers, state machines)
  - Utility helpers
  - Complex algorithms

NOT IDEAL FOR:
  - Components with heavy dependency on context/routing
  - Highly integrated UI flows

CHARACTERISTICS:
  ✅ Very fast (milliseconds per test)
  ✅ Easy to pinpoint failures
  ✅ Great for TDD
  ❌ High mocking overhead
  ❌ Low confidence that the whole system works together

EXAMPLE:
  // Testing a pure utility function
  describe('formatCurrency', () => {
    it('formats positive numbers correctly', () => {
      expect(formatCurrency(1234.5)).toBe('$1,234.50');
    });
    it('handles zero', () => {
      expect(formatCurrency(0)).toBe('$0.00');
    });
    it('handles negative numbers', () => {
      expect(formatCurrency(-50)).toBe('-$50.00');
    });
  });

────────────────────────────────────────────────────────────────────────────────
INTEGRATION TESTS
────────────────────────────────────────────────────────────────────────────────
Test multiple units working together. For UI, this typically means rendering
a component with its real dependencies (hooks, context, child components)
while mocking only network calls.

BEST FOR:
  - React components with state, hooks, and children
  - Form submissions with validation
  - Components that interact with context or Redux
  - Feature workflows spanning multiple components

CHARACTERISTICS:
  ✅ High confidence in real behavior
  ✅ Tests user-visible behavior
  ✅ Catches integration bugs that unit tests miss
  ✅ Moderate speed (10-100ms per test)
  ❌ Slower than unit tests
  ❌ Harder to pinpoint exactly which unit caused a failure

EXAMPLE:
  // Testing a login form with real validation logic
  it('shows error message for invalid email', async () => {
    render(<LoginForm onSubmit={mockSubmit} />);

    await userEvent.type(screen.getByLabelText(/email/i), 'notanemail');
    await userEvent.click(screen.getByRole('button', { name: /submit/i }));

    expect(screen.getByText(/invalid email/i)).toBeInTheDocument();
    expect(mockSubmit).not.toHaveBeenCalled();
  });

────────────────────────────────────────────────────────────────────────────────
END-TO-END (E2E) TESTS
────────────────────────────────────────────────────────────────────────────────
Simulate real user workflows in a real browser with a real server.
No mocking — tests the entire system as deployed.

BEST FOR:
  - Critical business flows (login, checkout, signup)
  - Cross-page navigation
  - Authentication and authorization flows
  - Third-party integrations (payment, OAuth)
  - Regression testing before major releases

CHARACTERISTICS:
  ✅ Highest confidence — tests the real application
  ✅ Catches issues that no other test type can
  ❌ Slowest (seconds to minutes per test)
  ❌ Most expensive to maintain
  ❌ Flaky due to network, timing, browser issues
  ❌ Hard to debug when they fail

EXAMPLE (Playwright):
  test('user can log in and see dashboard', async ({ page }) => {
    await page.goto('/login');
    await page.fill('[name="email"]', 'user@example.com');
    await page.fill('[name="password"]', 'password123');
    await page.click('button[type="submit"]');
    await expect(page).toHaveURL('/dashboard');
    await expect(page.getByText('Welcome, User')).toBeVisible();
  });

4. RATIO GUIDELINES
================================================================================

┌───────────────┬──────────┬────────────────────────────────────────────────┐
│ Test Type     │ Quantity │ Notes                                          │
├───────────────┼──────────┼────────────────────────────────────────────────┤
│ Static        │ Always   │ TypeScript + ESLint on every project           │
│ Unit          │ Many     │ Focus on pure logic, utilities, reducers       │
│ Integration   │ Most     │ Test components as users experience them       │
│ E2E           │ Few      │ Critical paths only: login, checkout, signup   │
└───────────────┴──────────┴────────────────────────────────────────────────┘

A typical mature React app might have:
  - 1 ESLint/TypeScript config
  - 200+ unit tests for utilities
  - 100+ integration tests for components/features
  - 20–50 E2E tests for critical flows

5. COST VS. CONFIDENCE TRADE-OFF
================================================================================

                    HIGH CONFIDENCE
                          ↑
          E2E ────────────┤
                          │
    Integration ──────────┤
                          │
         Unit ────────────┤
                          │
       Static ────────────┤
                          ↓
                    LOW CONFIDENCE

              LOW COST ←──────────────→ HIGH COST
              FAST     ←──────────────→ SLOW

The goal is to maximize CONFIDENCE while minimizing COST.
This is why integration tests have the best ROI for UI work.

DECISION MATRIX:
  ┌────────────────────────────────┬─────────────┬───────────────────────┐
  │ Scenario                       │ Test Type   │ Reason                │
  ├────────────────────────────────┼─────────────┼───────────────────────┤
  │ A utility that formats dates   │ Unit        │ Pure logic            │
  │ A Redux reducer                │ Unit        │ Pure function         │
  │ A form component               │ Integration │ User interaction      │
  │ A data fetching hook           │ Integration │ Hook + API mock       │
  │ Complete checkout flow         │ E2E         │ Full user journey     │
  │ Undefined variable             │ Static      │ TypeScript catches it │
  └────────────────────────────────┴─────────────┴───────────────────────┘

6. ANTI-PATTERNS: THE ICE CREAM CONE
================================================================================

The Ice Cream Cone is what happens when a team does the OPPOSITE of the pyramid:

             /──────────────────\
            / Lots of E2E Tests  \     ← Slow, flaky, expensive
           /────────────────────\
          /  Some Integration    \
         /──────────────────────\
        /  Few or No Unit Tests  \     ← No fast feedback
       /────────────────────────\

THIS HAPPENS WHEN:
  - The team relies on QA to manually test
  - Tests are added as an afterthought
  - The team only trusts "real browser" tests
  - There's no culture of TDD

CONSEQUENCES:
  - CI pipeline takes 45+ minutes
  - Flaky tests cause random build failures
  - Fear of making changes
  - Bugs are found late (expensive)
  - Developer frustration

7. CHOOSING THE RIGHT TEST TYPE
================================================================================

FLOWCHART FOR DECIDING WHAT TEST TO WRITE:

START: What are you testing?
  │
  ├─→ A pure function or utility?
  │   └─→ UNIT TEST
  │
  ├─→ A React component?
  │   ├─→ Does it only render static content?
  │   │   └─→ SNAPSHOT TEST (small, targeted)
  │   └─→ Does it interact, fetch data, use state?
  │       └─→ INTEGRATION TEST with RTL
  │
  ├─→ A multi-page user workflow?
  │   └─→ E2E TEST with Cypress/Playwright
  │
  └─→ Visual design/CSS pixel perfect?
      └─→ VISUAL REGRESSION TEST (Percy, Chromatic)

8. REAL-WORLD APPLICATION
================================================================================

EXAMPLE: E-COMMERCE PRODUCT PAGE

What to unit test:
  - formatPrice(price, currency) utility
  - calculateDiscount(originalPrice, discountPercent) utility
  - addToCartReducer(state, action) Redux reducer
  - useProductRating custom hook

What to integration test:
  - <ProductCard /> component renders correctly with props
  - Add to cart button updates cart count
  - Image carousel navigation works
  - Out-of-stock shows disabled button
  - Form validation on quantity input

What to E2E test:
  - User can search, find a product, add to cart, and checkout
  - User can log in and see saved cart
  - Payment flow completes successfully

What to visual test:
  - Product card design looks correct across viewports
  - Cart overlay renders correctly on mobile

INTERVIEW INSIGHT:
  Interviewers often ask: "How do you decide what kind of test to write?"
  Answer: "I follow the testing trophy model. I write the most tests at the
  integration level because they test real user behavior with the best
  cost/confidence ratio. I write unit tests for complex pure logic, and
  E2E tests for critical business-critical workflows only."
