1. CORE CONCEPTS (BEGINNER)
================================================================================

Q: What is Jest and what problems does it solve?
A: Jest is a JavaScript testing framework developed by Meta.
   It provides an all-in-one solution: test runner + assertion library + mocking
   system + code coverage. Before Jest, teams needed to combine separate tools
   (Mocha + Chai + Sinon + Istanbul). Jest runs tests in isolation using Node.js
   with a jsdom environment to simulate a browser DOM.

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between describe(), test(), and it()?
A: - describe(): Groups related tests into a test suite. Can be nested.
   - test() and it(): Identical — register a single test case.
     it() is an alias for test(). it() reads more like English:
     "it should redirect when unauthenticated"

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between toBe() and toEqual()?
A: - toBe(): Uses Object.is() (strict reference equality). For primitives,
     checks exact value. For objects, must be THE SAME reference.
   - toEqual(): Deep equality — recursively checks all properties.

   expect(1).toBe(1);        // ✅ primitive
   expect([1]).toBe([1]);    // ❌ different array references
   expect([1]).toEqual([1]); // ✅ deep equality

─────────────────────────────────────────────────────────────────────────────

Q: What do beforeEach, afterEach, beforeAll, and afterAll do?
A: - beforeEach: Runs before every test in the describe block → setup
   - afterEach: Runs after every test → cleanup
   - beforeAll: Runs ONCE before all tests in the block → expensive setup (DB connect)
   - afterAll: Runs ONCE after all tests → teardown (close connections)

   Key: beforeEach/afterEach are preferred because they ensure test isolation.
   beforeAll can cause tests to share state and create flakiness.

─────────────────────────────────────────────────────────────────────────────

Q: What does test.skip and test.only do?
A: - test.skip(): Marks a test as skipped — won't run, shown as pending.
   - test.only(): Runs ONLY this test (and other .only tests in the file).
     DANGER: Easy to accidentally commit test.only and block the full suite.
   - describe.only(): Only runs tests in this describe block.

2. MOCKING AND SPIES (INTERMEDIATE)
================================================================================

Q: What is the difference between jest.fn(), jest.spyOn(), and jest.mock()?
A:
  jest.fn()      — Creates a standalone mock function (not tied to any module).
                   Used when you need a callback or injectable dependency.

  jest.spyOn()   — Wraps an existing function to spy on calls. The original
                   implementation runs by default (unless you mock it).
                   Used on class instances or imported module methods.

  jest.mock()    — Replaces an entire module with a mocked version at the
                   module system level. Hoisted to the top of the file by Babel.

  // jest.fn():
  const callback = jest.fn().mockReturnValue(42);
  doSomething(callback);
  expect(callback).toHaveBeenCalledTimes(1);

  // jest.spyOn():
  const spy = jest.spyOn(Math, 'random').mockReturnValue(0.5);
  expect(Math.random()).toBe(0.5);
  spy.mockRestore();

  // jest.mock():
  jest.mock('./api');
  import { fetchUser } from './api'; // auto-mocked

─────────────────────────────────────────────────────────────────────────────

Q: Why must jest.mock() be called at the top of the file and not inside a test?
A: Jest hoists jest.mock() calls to the TOP of the file before any imports,
   using Babel transforms. This means:
   1. You can mock before the module is imported (even though import is hoisted).
   2. If you call jest.mock() inside a test or beforeEach, it may not work
      correctly because imports have already been evaluated.

   // This works:
   jest.mock('./api');
   import { fetchUser } from './api';

   // This may NOT work (depends on module system):
   import { fetchUser } from './api';
   test('...', () => { jest.mock('./api'); }); // Too late!

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between mockReturnValue, mockResolvedValue, and mockReturnValueOnce?
A:
  mockReturnValue(val)       — Always returns val synchronously.
  mockResolvedValue(val)     — Always returns Promise.resolve(val).
  mockRejectedValue(err)     — Always returns Promise.reject(err).
  mockReturnValueOnce(val)   — Returns val only for the NEXT call, then falls
                               through to next once or default.

  const mock = jest.fn()
    .mockReturnValueOnce('first')
    .mockReturnValueOnce('second')
    .mockReturnValue('default');

  mock(); // 'first'
  mock(); // 'second'
  mock(); // 'default'
  mock(); // 'default'

─────────────────────────────────────────────────────────────────────────────

Q: How do you reset, restore, and clear mocks? What's the difference?
A:
  mockFn.mockClear()    — Resets call count and recorded calls/instances.
                          Does NOT restore implementation.
  mockFn.mockReset()    — Clears + removes mock implementation/return values.
                          The mock becomes a no-op.
  mockFn.mockRestore()  — Only works for jest.spyOn(). Restores original
                          implementation and removes the spy.

  In jest.config.ts:
  clearMocks: true      — Auto-clear between tests
  resetMocks: true      — Auto-reset between tests
  restoreMocks: true    — Auto-restore spies between tests

─────────────────────────────────────────────────────────────────────────────

Q: How do you test that a function threw an error?
A:
  // ✅ Correct — wrap in a function:
  expect(() => throwingFn()).toThrow('error message');
  expect(() => throwingFn()).toThrow(TypeError);

  // ❌ Wrong — Jest can't catch the error:
  expect(throwingFn()).toThrow();

  // For async functions:
  await expect(asyncFn()).rejects.toThrow('error message');

3. ASYNC TESTING (INTERMEDIATE)
================================================================================

Q: What are the 3 ways to test async code in Jest?
A:
  1. Return the Promise:
     test('async', () => {
       return fetchData().then(data => expect(data).toBe('OK'));
     });

  2. async/await:
     test('async', async () => {
       const data = await fetchData();
       expect(data).toBe('OK');
     });

  3. done callback (legacy, avoid):
     test('async', (done) => {
       fetchData((data) => {
         expect(data).toBe('OK');
         done();
       });
     });

  Best practice: Use async/await — most readable.

─────────────────────────────────────────────────────────────────────────────

Q: What happens if you forget await in an async test?
A: The test passes immediately (vacuously) even if the async operation would
   fail. The assertion runs but the Promise is not awaited, so Jest moves on
   before the assertion resolves.

   test('bug: forgot await', async () => {
     expect(failingPromise()).resolves.toBe('right'); // ❌ no await
     // Test passes! The Promise is never awaited.
   });

   Always use: await expect(promise).resolves.toBe(...)

─────────────────────────────────────────────────────────────────────────────

Q: How do fake timers work and when would you use them?
A: Fake timers replace setTimeout, setInterval, Date, etc. with Jest-controlled
   implementations. Time only advances when you explicitly tell it to.

   jest.useFakeTimers();
   const callback = jest.fn();
   setTimeout(callback, 1000);
   expect(callback).not.toHaveBeenCalled();
   jest.advanceTimersByTime(1000);
   expect(callback).toHaveBeenCalledTimes(1);

   When to use: Debounce functions, polling, retry logic, anything that
   would make tests take seconds to run with real timers.

   Always restore: jest.useRealTimers() in afterEach.

4. CONFIGURATION AND COVERAGE (INTERMEDIATE)
================================================================================

Q: What is jest.config.ts and what are the most important options?
A:
  testEnvironment: 'jsdom'    // Browser-like env (default for React projects)
  testEnvironment: 'node'     // Node.js env (for APIs, utils)
  transform                   // Transform files (TypeScript, JSX via babel-jest)
  moduleNameMapper            // Alias resolution (match tsconfig paths)
  setupFilesAfterFramework    // Run after test framework loads (import jest-dom)
  collectCoverage: true       // Collect coverage on every run
  coverageThreshold           // Fail if coverage drops below threshold

─────────────────────────────────────────────────────────────────────────────

Q: What are the 4 types of code coverage? Which is most important?
A:
  Statement Coverage: % of executable statements run.
  Branch Coverage:    % of branches (if/else, ternary) exercised.
  Function Coverage:  % of functions called.
  Line Coverage:      % of lines executed.

  Most important: BRANCH coverage.
  Example: A function with an if/else has 100% statement coverage if you
  call it once, but only 50% branch coverage if you only tested one path.
  Untested branches = untested logic = potential bugs.

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between Istanbul and V8 coverage?
A:
  Istanbul (babel-jest): Code is instrumented at the AST level via Babel
    transforms. Works with TypeScript transpilation.
  V8: Uses Node.js's built-in V8 engine code coverage. No instrumentation
    needed. Generally more accurate but requires TypeScript source maps.
    Faster because no instrumentation overhead.

  provider: 'v8'  → Use V8 (recommended for modern setups)
  provider: 'babel' → Use Istanbul (traditional, broader compatibility)

─────────────────────────────────────────────────────────────────────────────

Q: What is a snapshot test and when should you use it?
A: Snapshot tests serialize a component's rendered output to a .snap file.
   On subsequent runs, the output is compared to the snapshot. If different,
   the test fails until you update the snapshot.

   test('Button renders', () => {
     const { asFragment } = render(<Button>Click</Button>);
     expect(asFragment()).toMatchSnapshot();
   });

   When to use:
   ✅ Serialized non-HTML output (GraphQL schema, CSS-in-JS output, config objects)
   ❌ Complex React component trees — creates brittle tests that break on minor changes

   Better alternative: Use toHaveTextContent, toBeVisible, etc. from @testing-library/jest-dom.

5. ADVANCED AND GOTCHAS (SENIOR)
================================================================================

Q: Why does jest.mock() hoisting cause issues when using factory functions with imports?
A: jest.mock() is hoisted before imports, but variables in the factory
   function are NOT hoisted. You can't reference an imported variable in the
   factory if the import hasn't loaded yet.

   // ❌ FAILS — 'mockFn' is declared after the mock factory:
   const mockFn = jest.fn();
   jest.mock('./module', () => ({ getData: mockFn }));

   // ✅ WORKS — use jest.fn() inside the factory directly:
   jest.mock('./module', () => ({
     getData: jest.fn(),
   }));

   // OR use the "mock" prefix to bypass hoisting issue:
   const mockGetData = jest.fn();  // prefix 'mock' is special
   jest.mock('./module', () => ({ getData: mockGetData }));

─────────────────────────────────────────────────────────────────────────────

Q: How do you test a module that has a default export vs named export?
A:
  // Named export mock:
  jest.mock('./utils', () => ({
    formatDate: jest.fn(() => '2024-01-01'),
  }));

  // Default export mock:
  jest.mock('./api', () => ({
    __esModule: true,             // Required for ES modules with default export
    default: jest.fn(() => 'data'),
  }));

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between jest.isolateModules() and jest.resetModules()?
A:
  jest.resetModules(): Clears the module registry so the next require() or
    import() loads a fresh version of the module.

  jest.isolateModules(fn): Runs fn with a fresh module registry, then restores
    the original. Useful for testing module initialization side effects.

  Use case: Testing modules that have side effects on load (e.g., logging,
  singleton initialization that reads process.env).

─────────────────────────────────────────────────────────────────────────────

Q: How do you test private methods or internal implementation details?
A: You generally should NOT test private methods — only test public interfaces.
   Testing internals creates brittle tests that break on refactoring.

   If you feel you need to test a private method, ask:
   1. Is the behavior tested indirectly through public methods? (Best)
   2. Should this private method be extracted to its own module? (Common fix)
   3. Am I testing implementation instead of behavior? (Usually yes → rethink)

   In JavaScript/TypeScript, "private" doesn't truly exist at runtime,
   so you CAN access private members. But you SHOULDN'T.

─────────────────────────────────────────────────────────────────────────────

Q: What is the module registry and how does Jest's test isolation work?
A: Jest runs each test FILE in a separate Node.js process (or VM context).
   This means:
   - Module singletons are fresh per file (no cross-file state leakage)
   - Changes to process.env in one file don't affect another
   - jest.mock() affects only the current file

   Within a file, tests SHARE the module registry unless you call
   jest.resetModules() or jest.isolateModules().

6. QUICK-FIRE ANSWERS
================================================================================

Q: What does .not do?
A: Inverts the matcher. expect(value).not.toBeNull()

Q: What is expect.assertions(n)?
A: Fails the test unless exactly n assertions were called. Useful in async
   tests to ensure you don't accidentally skip assertions.

Q: How do you test console.error was called?
A: jest.spyOn(console, 'error').mockImplementation(() => {});
   Then: expect(console.error).toHaveBeenCalledWith(...)

Q: What is the difference between test timeout and jest.setTimeout()?
A: Default timeout is 5 seconds per test. jest.setTimeout(10000) changes it
   globally in the file. Or pass as 3rd arg: test('...', async () => {}, 10000)

Q: What is a module factory in jest.mock()?
A: The optional 2nd argument to jest.mock() — a function that returns the
   mocked module: jest.mock('./mod', () => ({ fn: jest.fn() }))

Q: How do you check a mock was called with specific arguments?
A: expect(mockFn).toHaveBeenCalledWith('arg1', expect.objectContaining({ id: 1 }))

Q: What does mockImplementation() do vs mockReturnValue()?
A: mockReturnValue: always returns the specified value.
   mockImplementation: calls a function to compute the return value.
   Use mockImplementation when the return value needs to be computed or
   when the mock should have side effects.

Q: How do you skip a test in CI but run it locally?
A: test.skip() or: if (process.env.CI) { test.skip(...) } else { test(...) }
   Or use test.skipIf (Jest 29.4+): test.skipIf(process.env.CI)(...)
