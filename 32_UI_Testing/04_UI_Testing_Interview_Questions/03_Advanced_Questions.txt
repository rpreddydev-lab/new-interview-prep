1. TESTING ARCHITECTURE AND DESIGN
================================================================================

Q: What is the Testing Trophy vs the Testing Pyramid? Which is better?
A:
  TESTING PYRAMID (Mike Cohn):
  - Base: Unit tests (most, cheapest)
  - Middle: Integration/Service tests
  - Top: E2E/UI tests (fewest, most expensive)
  - "Write mostly unit tests"

  TESTING TROPHY (Kent C. Dodds, RTL author):
  - Bottom: Static (TypeScript, ESLint)
  - Base: Unit tests (some)
  - Middle: Integration tests (MOST — biggest layer)
  - Top: E2E (few)

  Key difference: The Trophy elevates INTEGRATION tests as most valuable.
  Reasoning: Integration tests (components with MSW) test more of the user
  experience per test than pure unit tests, with less flakiness than E2E.
  Unit tests of implementation details give false confidence.

  "Write tests. Not too many. Mostly integration." — Kent C. Dodds

─────────────────────────────────────────────────────────────────────────────

Q: How do you decide WHAT to test? What's your decision framework?
A: Ask these questions in order:

  1. What is the RISK if this breaks?
     High-risk: payment processing, auth, data submission → test everything
     Low-risk: text formatting utility → brief unit test

  2. What is the USER IMPACT if this breaks?
     User-facing → integration/E2E
     Internal utility → unit test

  3. How COMPLEX is the logic?
     Complex branching → needs thorough unit tests
     Simple render → basic render test is enough

  4. Does this integrate MANY PARTS together?
     Yes → integration test
     No → unit test

  5. Is this a CRITICAL USER JOURNEY?
     Yes → E2E test
     No → don't add E2E overhead

─────────────────────────────────────────────────────────────────────────────

Q: What is "testing implementation details" and why is it an anti-pattern?
A: Testing implementation details means testing HOW the code works internally,
   not WHAT the user experiences.

   EXAMPLES OF IMPLEMENTATION DETAIL TESTING:
   - Asserting component state: expect(wrapper.state('count')).toBe(1)
   - Testing that a specific function was called internally
   - Testing class method directly instead of user interaction
   - Testing prop names match component internals

   WHY IT'S BAD:
   - Tests break when you refactor (even if behavior stays the same)
   - False positives (test passes but UI is broken)
   - False negatives (test fails but user experience is fine)

   EXAMPLE:
   // ❌ Implementation detail:
   wrapper.instance().handleSubmit(); // internal method, not user action
   expect(wrapper.state('submitted')).toBe(true);

   // ✅ User behavior:
   await user.click(screen.getByRole('button', { name: 'Submit' }));
   expect(screen.getByText('Form submitted!')).toBeInTheDocument();

─────────────────────────────────────────────────────────────────────────────

Q: What should you NOT mock in tests?
A: Avoid mocking:
   1. The module under test (testing the mock, not the code)
   2. Language primitives (Array.prototype.map, Math.abs, etc.)
   3. Your own internal business logic (use it directly)
   4. Interfaces you don't own at the wrong level (mock at API boundary, not transport)

   DO mock:
   1. External services (network calls, third-party APIs)
   2. Non-deterministic results (Date.now(), Math.random())
   3. Browser APIs unavailable in jsdom (matchMedia, IntersectionObserver)
   4. Slow operations (filesystem, heavy computations)

2. MOCKING DEEP DIVES
================================================================================

Q: How does MSW actually work under the hood?
A:
  IN THE BROWSER (E2E/Storybook):
  MSW registers a real Service Worker (SW) at the browser level.
  The SW intercepts all fetch()/XHR requests before they hit the network.
  MSW's handlers match the request and return a mocked Response.
  The original app code never knows the network was intercepted.

  IN NODE.JS (Jest):
  MSW uses node-interceptors to monkey-patch Node.js's http/https modules.
  When your code calls fetch() (undici/node-fetch) or axios,
  the interceptor catches the request before it leaves Node.js.
  The handler returns the mocked response.

  KEY INSIGHT: MSW intercepts at the HIGHEST level possible (SW / Node HTTP stack),
  so ALL networking code (fetch, axios, ky, got) is intercepted identically.

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between manual mocking and automatic mocking in Jest?
A:
  AUTOMATIC MOCKING: jest.mock('./module')
  Jest auto-generates a mock by analyzing the module's exports:
  - Functions become jest.fn() (no implementation)
  - Objects keep their structure but methods become jest.fn()
  - Classes get constructor and methods mocked

  MANUAL MOCKING: Create __mocks__/module.ts file
  You write the mock implementation yourself.
  Jest automatically uses __mocks__ version if it exists for:
  - node_modules: Always requires jest.mock('moduleName') in the test
  - Local modules: Auto-used if automock: true, else requires jest.mock()

  FACTORY FUNCTION MOCK: jest.mock('./module', () => ({ ... }))
  Inline manual mock. Good for one-off mocks.
  Better than auto-mock because you control what the mock returns.

─────────────────────────────────────────────────────────────────────────────

Q: How do you mock a module that has both a default export and named exports?
A:
  // Original module:
  export default class ApiClient { ... }
  export const BASE_URL = 'https://api.example.com';
  export function formatResponse(data) { ... }

  // Mock:
  jest.mock('./api-client', () => ({
    __esModule: true,    // REQUIRED for ESM default exports
    default: jest.fn().mockImplementation(() => ({
      get: jest.fn().mockResolvedValue({ data: [] }),
    })),
    BASE_URL: 'http://mock-api',
    formatResponse: jest.fn((data) => data),
  }));

  // Access the mock default class:
  import ApiClient from './api-client';
  const mockClient = ApiClient as jest.MockedClass<typeof ApiClient>;

3. PERFORMANCE AND SCALABILITY
================================================================================

Q: How do you manage a large test suite that takes too long to run?
A:
  1. PARALLELIZATION:
     Jest: --maxWorkers=50% (use half CPU cores)
     Playwright: workers: os.cpus().length / 2
     Cypress: Cypress Cloud parallel or GitHub Actions matrix

  2. TEST PARTITIONING:
     Run only affected tests on PR (test impact analysis)
     Tools: jest --changedSince, nx affected, turbo pipeline

  3. TEST CLASSIFICATION:
     Unit/Integration: Fast, run on every commit
     E2E smoke: Run on PR (5-10 critical tests)
     E2E full: Run nightly or on main branch merge

  4. CACHING:
     Cache node_modules between CI runs
     Cache Playwright browser binaries (60-100MB)
     Cache Jest's transformation cache

  5. ELIMINATE WASTE:
     Remove duplicate tests (same thing tested at 3 levels)
     Remove tests of trivial code (getters, simple mappings)
     Optimize slow individual tests (fake timers, API mocking)

─────────────────────────────────────────────────────────────────────────────

Q: What is test isolation and why does it matter at scale?
A: Test isolation means each test can run independently in any order without
   being affected by or affecting other tests.

   VIOLATIONS OF ISOLATION:
   - Shared module-level state: let store = createStore() (once for all tests)
   - Tests relying on order: Test 3 assumes Test 2 logged in
   - Missing cleanup: setTimeout fires after test ends → "not in act()" warning
   - Shared DB state: E2E test creates user, next test breaks because user exists

   SOLUTIONS:
   - Unit/Integration: beforeEach cleanup, clearMocks: true, restoreMocks: true
   - E2E: Each test seeds its own data, deletes after; or use transactions/rollback

4. ACCESSIBILITY TESTING
================================================================================

Q: How do you test for accessibility in unit/integration tests?
A:
  1. RTL naturally encourages accessible queries (getByRole, getByLabel)
     If you can't find an element by role/label, it may not be accessible.

  2. jest-axe for automated a11y auditing:
     import { axe, toHaveNoViolations } from 'jest-axe';
     expect.extend(toHaveNoViolations);

     test('no a11y violations', async () => {
       const { container } = render(<LoginForm />);
       const results = await axe(container);
       expect(results).toHaveNoViolations();
     });

  3. Test keyboard navigation:
     await user.tab();
     expect(screen.getByRole('button', { name: 'Submit' })).toHaveFocus();

  4. Test ARIA attributes:
     expect(screen.getByRole('dialog')).toHaveAttribute('aria-modal', 'true');
     expect(errorMsg).toHaveAttribute('role', 'alert');

─────────────────────────────────────────────────────────────────────────────

Q: How do you test that focus management is correct in a modal?
A: A proper modal should:
   1. Move focus INTO the modal when opened
   2. Trap focus (Tab stays within modal)
   3. Return focus to the trigger when closed

   const user = userEvent.setup();
   const openBtn = screen.getByRole('button', { name: 'Open Modal' });

   await user.click(openBtn);

   // 1. Focus moved to modal heading or close button:
   expect(screen.getByRole('heading', { name: 'Modal Title' })).toHaveFocus();

   // 2. Tab stays in modal:
   await user.tab();
   expect(screen.getByRole('button', { name: 'Close' })).toHaveFocus();
   await user.tab();
   // Should wrap back, not escape to page behind modal

   // 3. Focus returns after close:
   await user.click(screen.getByRole('button', { name: 'Close' }));
   expect(openBtn).toHaveFocus();

Q: How would you test a component that uses WebSocket?
A:
  Option 1: Mock the WebSocket constructor:
  const MockWebSocket = jest.fn().mockImplementation(() => ({
    send: jest.fn(),
    close: jest.fn(),
    addEventListener: jest.fn(),
    readyState: WebSocket.OPEN,
  }));
  global.WebSocket = MockWebSocket;

  Option 2: Use MSW for WebSocket mocking (MSW 2.x supports WS):
  import { ws } from 'msw';
  const chat = ws.link('ws://localhost:3000/chat');

  server.use(
    chat.addEventListener('connection', ({ client }) => {
      client.send(JSON.stringify({ type: 'message', text: 'Hello' }));
    })
  );

  Option 3: Wrap WebSocket in a service class and mock the class.

─────────────────────────────────────────────────────────────────────────────

Q: How do you test file upload?
A:
  // RTL with userEvent:
  const file = new File(['content'], 'test.pdf', { type: 'application/pdf' });
  const input = screen.getByLabelText('Upload PDF');
  await user.upload(input, file);
  expect(screen.getByText('test.pdf')).toBeInTheDocument();

  // Playwright:
  await page.getByLabel('Upload PDF').setInputFiles({
    name: 'test.pdf',
    mimeType: 'application/pdf',
    buffer: Buffer.from('file contents'),
  });
  await expect(page.getByText('test.pdf')).toBeVisible();

─────────────────────────────────────────────────────────────────────────────

Q: How do you test browser APIs that jsdom doesn't support?
A: jsdom doesn't support: matchMedia, IntersectionObserver, ResizeObserver,
   window.scrollTo, navigator.clipboard, etc.

   Strategies:
   1. Mock at global level in setupFilesAfterFramework:
      Object.defineProperty(window, 'matchMedia', {
        writable: true,
        value: jest.fn().mockImplementation(query => ({
          matches: false,
          media: query,
          addEventListener: jest.fn(),
        })),
      });

   2. For IntersectionObserver:
      global.IntersectionObserver = jest.fn().mockImplementation((callback) => ({
        observe: jest.fn(),
        unobserve: jest.fn(),
        disconnect: jest.fn(),
      }));

   3. Mock the hook/service that uses the API instead of the API itself.

─────────────────────────────────────────────────────────────────────────────

Q: How would you test a component that uses React Suspense and lazy loading?
A:
  import { Suspense } from 'react';
  const LazyComponent = React.lazy(() => import('./LazyComponent'));

  // Wrap in Suspense with fallback:
  render(
    <Suspense fallback={<div>Loading...</div>}>
      <LazyComponent />
    </Suspense>
  );

  // Wait for lazy component to load:
  expect(screen.getByText('Loading...')).toBeInTheDocument();
  await screen.findByText('Lazy content loaded');

  // If lazy import hangs: mock the lazy import:
  jest.mock('./LazyComponent', () => ({
    default: () => <div>Mocked lazy content</div>,
  }));

6. SENIOR-LEVEL GOTCHAS
================================================================================

Q: What is the "false confidence" problem in testing?
A: A test suite with high coverage can still give false confidence if:
   1. Tests test WHAT, not WHY (assertion-free tests)
   2. Tests mock too aggressively (the mock always passes)
   3. Tests only test happy paths
   4. E2E tests only test one browser
   5. Tests pass because the wrong assertion was used

   Examples:
   - test('renders', () => { render(<Comp />); }) — No assertions, always passes!
   - Snapshot test that gets updated without review
   - mockResolvedValue(anything) without testing the failure path

─────────────────────────────────────────────────────────────────────────────

Q: How does tree shaking affect test coverage reporting?
A: Bundlers tree-shake unused code for production. But Jest runs the raw source.
   So coverage might show 100% of source code is covered, but some branches
   only exist for non-production builds. This creates misleading coverage.

   Solution: Run coverage on the SAME code that ships to production.
   V8 coverage provider is more accurate because it uses the same engine
   as production Node.js environments.

─────────────────────────────────────────────────────────────────────────────

Q: How do you test React error boundaries?
A:
  // Suppress expected console.error output:
  const consoleError = jest.spyOn(console, 'error').mockImplementation(() => {});

  const ThrowingComponent = () => { throw new Error('Test error'); };

  render(
    <ErrorBoundary fallback={<p>Something went wrong</p>}>
      <ThrowingComponent />
    </ErrorBoundary>
  );

  expect(screen.getByText('Something went wrong')).toBeInTheDocument();
  expect(consoleError).toHaveBeenCalled(); // React logs errors even with boundary

  consoleError.mockRestore();

─────────────────────────────────────────────────────────────────────────────

Q: How do you prevent test pollution when a module has singleton state?
A: Use jest.resetModules() + re-importing between tests:

  let store;
  beforeEach(() => {
    jest.resetModules();
    store = require('./store').default;  // fresh singleton each test
  });

  Or use jest.isolateModules():
  test('test with fresh module', () => {
    jest.isolateModules(() => {
      const freshModule = require('./singleton');
      expect(freshModule.getState()).toBe('initial');
    });
  });

  This is common when testing: config loaders, stores, loggers, caches.
