1. LEGACY CODE AND RETROFITTING TESTS
================================================================================

Q: How would you add testing to an existing codebase with zero tests?
A: You can't add tests everywhere overnight. Prioritize strategically:

   STEP 1 — Establish the foundation:
   - Set up testing infrastructure (Jest, RTL, MSW, Playwright)
   - Add a pre-commit hook (lint + unit tests)
   - Set coverage baseline: coverage = 0%. Document it.

   STEP 2 — "Boy Scout Rule" (the ongoing strategy):
   Any code you TOUCH gets tested. Never leave touched code worse than you found it.
   - Fixing a bug? Write a failing test that reproduces it, then fix.
   - Adding a feature? Write tests for the new feature.
   - Refactoring? Ensure tests exist before refactoring.

   STEP 3 — Test critical paths first:
   - Identify the 5-10 most business-critical user flows
   - Write E2E tests for those (even before unit tests) — highest ROI
   - Focus on things that break often or cost most when broken

   STEP 4 — Track and improve over time:
   - Set coverage thresholds that START LOW (e.g., 30%) and ratchet up each sprint
   - Use a coverage dashboard (Codecov, SonarQube)
   - Never let coverage drop below the current baseline

─────────────────────────────────────────────────────────────────────────────

Q: You inherit a codebase where all tests are tightly coupled to implementation.
   How do you improve this without rewriting everything?
A:
   1. DON'T rewrite all tests at once — continue improving incrementally
   2. When a test breaks for the wrong reason (refactor, not behavior change):
      - Replace the broken test with a behavior-focused one
      - Don't fix the coupled test — replace it
   3. Add RTL-style tests alongside Enzyme tests for new features
   4. Track the ratio of implementation-detail tests vs behavior tests
   5. Document the principle: "Query by role, not by CSS" in the team wiki
   6. Code review: start requiring reviewers to flag implementation-detail tests

─────────────────────────────────────────────────────────────────────────────

Q: How do you avoid breaking ALL tests when the UI is redesigned?
A:
   1. Use SEMANTIC selectors (getByRole, getByLabelText, data-testid)
      not CSS classes or visual structure
   2. Separate concerns: test BEHAVIOR (what form does), not STRUCTURE (how it's laid out)
   3. Avoid brittle assertions: don't assert exact text if it changes often
   4. Keep E2E tests focused on FLOWS (user journey), not pixel-perfect layout
   5. Visual regression tests handle visual changes explicitly — they fail
      intentionally when visuals change, requiring deliberate review/approval

2. WHAT AND HOW MUCH TO TEST
================================================================================

Q: How do you decide whether to write a unit test, integration test, or E2E test?
A: Use this decision tree:

   Does it involve a critical user journey across multiple pages?
   → YES → E2E test

   Does it involve multiple components, real DOM, and API interaction?
   → YES → Integration test (RTL + MSW)

   Does it involve complex business logic with many branches?
   → YES → Unit test (fast, isolated)

   Is it a trivial utility function with no branches?
   → Probably not worth testing, or just one happy-path test

   SHORTCUTS:
   - Auth flows, checkout, sign-up → E2E
   - Form validation, data display, user interactions → Integration (RTL)
   - Pure functions, algorithms, state reducers → Unit
   - CSS, markup structure → Visual regression (Chromatic/Percy)

─────────────────────────────────────────────────────────────────────────────

Q: What is a good test coverage target and how do you enforce it?
A: There is NO universally correct coverage number.

   Context matters:
   - Banking/healthcare app: 90%+ branch coverage is reasonable
   - Internal admin tool: 70% may be fine
   - E2E for payment flow: 100% of critical paths

   PRACTICAL APPROACH:
   - Set thresholds in jest.config.ts:
     coverageThreshold: { global: { branches: 70, functions: 80, lines: 80 } }
   - Track over time, not a point-in-time metric
   - 100% coverage is possible while having useless tests (no assertions)
   - 70% coverage with meaningful tests >> 95% with assertion-free tests

   WHAT TO TELL THE INTERVIEWER:
   "Coverage is a signal, not a target. I aim for high coverage in critical
   paths and business logic, and I use coverage reports to find untested
   branches — not to hit a number."

─────────────────────────────────────────────────────────────────────────────

Q: Should you test every edge case?
A: Test edge cases proportional to RISK:

   HIGH RISK: Off-by-one in pagination? Authentication redirect logic?
   Error message display for 403 vs 404? → Test all edge cases.

   LOW RISK: Text formatting utilities? → Happy path + 1-2 edge cases.

   RED FLAGS (always test):
   - Any if/else around security (auth, permissions)
   - Any async code with error handling
   - Any user input processing
   - Any money/date/number calculations

3. TEAM AND PROCESS QUESTIONS
================================================================================

Q: How do you get a team to actually write tests?
A:
  1. LEAD BY EXAMPLE: Write tests in your PRs. Reviewers copy patterns.
  2. REMOVE FRICTION: Setup jest, RTL, MSW, code snippets — make writing tests easy
  3. PAIR ON THE FIRST TESTS: Sit with team members, write tests together
  4. TDD FOR NEW FEATURES: Write failing test first — team sees tests fail then pass
  5. CELEBRATE WINS: When a test catches a real bug in CI → "Tests saved us!"
  6. MAKE FAILING TESTS VISIBLE: Block merges if tests fail (CI enforcement)
  7. DON'T MANDATE 100% COVERAGE overnight — start low, ratchet up

─────────────────────────────────────────────────────────────────────────────

Q: What is TDD and when is it appropriate?
A: Test-Driven Development: Write FAILING test → Write minimal code to pass → Refactor

   Red → Green → Refactor cycle.

   GOOD FIT FOR TDD:
   - Well-understood business logic (validation rules, algorithms)
   - Bug fixes (write failing test that reproduces the bug)
   - API design (tests clarify what the interface should look like)
   - Pure functions

   POOR FIT FOR TDD:
   - Exploratory UI work (design/UX not yet determined)
   - Prototyping / spike work (throw away code)
   - Complex async code where test setup is harder than implementation

   INTERVIEW ANSWER: "I practice TDD when writing business logic and bug fixes.
   For UI work, I often write tests after the initial design is stable."

─────────────────────────────────────────────────────────────────────────────

Q: How do you handle disagreements in PR review about test quality?
A:
  1. Refer to agreed-upon principles (link to testing guide in docs)
  2. Ask "what scenario is this testing?" — if they can't answer, the test needs work
  3. Distinguish opinion from principle:
     - Opinion: "I would have written it differently"
     - Principle: "This tests implementation, not behavior — here's why that matters"
  4. For contentious cases, propose a team RFC to set policy
  5. Be respectful: Focus on the code, not the author

4. SCENARIO-BASED "HOW WOULD YOU TEST X?" QUESTIONS
================================================================================

Q: How would you test a checkout / payment flow?
A:
   UNIT LEVEL:
   - Test price calculation functions (discount, tax, totals)
   - Test cart reducer (add/remove/update quantity)
   - Test form validation (card number, expiry, CVV)

   INTEGRATION LEVEL:
   - Render CheckoutForm, fill fields, submit
   - Mock Stripe/payment API with MSW
   - Assert: success message on 200, error message on 402

   E2E LEVEL (CRITICAL):
   - Full user journey: add to cart → checkout → payment form → order confirmation
   - Use Stripe test cards (not real card numbers)
   - Test failure: expired card shows error
   - Test retry: user corrects card and resubmits
   - Only 2-3 E2E tests covering the critical paths

─────────────────────────────────────────────────────────────────────────────

Q: How would you test a search/filter feature?
A:
   UNIT:
   - Filter function: given items + criteria, returns correct subset
   - Sort function: ascending, descending, by different fields
   - Debounce logic (with fake timers)

   INTEGRATION:
   - Render SearchPage, type in search box (debounced)
   - MSW intercepts GET /api/items?q=keyboard
   - Assert: results show filtered items
   - Assert: loading state while searching
   - Assert: empty state when no results
   - Assert: error state on network failure

   E2E:
   - Smoke test: search for a known item, see it in results (1 test)

─────────────────────────────────────────────────────────────────────────────

Q: How would you test real-time features like chat or live notifications?
A:
   UNIT:
   - Test message formatting functions
   - Test notification store (add/dismiss actions)

   INTEGRATION:
   - Mock WebSocket with jest.fn() implementation
   - OR use MSW v2's ws() handler for WebSocket interception
   - Simulate incoming messages → assert UI updates
   - Simulate connection drop → assert reconnection UI

   E2E:
   - Use two browser contexts (Playwright):
     const context1 = await browser.newContext();
     const context2 = await browser.newContext();
     const page1 = await context1.newPage();
     const page2 = await context2.newPage();
     // Login as user1, user2
     // User1 sends message → assert user2 sees it

─────────────────────────────────────────────────────────────────────────────

Q: How would you test a drag-and-drop kanban board?
A:
   UNIT:
   - Column state management (move task between columns)
   - Position calculation (reorder within column)

   INTEGRATION:
   - @testing-library/user-event: user.pointer events for drag simulation
   - Or mock the drag-and-drop library's callbacks directly:
     const { onDragEnd } = screen.getByTestId('droppable').props; // Enzyme-style
     // Better: trigger the drop via the library's test utilities

   E2E (Playwright):
   await page.getByText('Task: Fix bug').dragTo(page.getByTestId('done-column'));
   await expect(page.getByTestId('done-column')).toContainText('Fix bug');

─────────────────────────────────────────────────────────────────────────────

Q: How would you test authentication and protected routes?
A:
   UNIT:
   - Auth helper: isTokenExpired(), parseJWT(), getAuthHeader()

   INTEGRATION:
   - Render ProtectedRoute with and without auth context
   - Without auth: renders <Navigate to="/login" /> or redirect
   - With auth: renders the protected component
   - Token expiry: use fake timers, advance past expiry, assert redirect

   E2E:
   - Test login flow: valid credentials → dashboard
   - Test failed login: wrong password → error message
   - Test direct navigation to protected URL → redirect to login
   - Test logout: click logout → redirect to home, back button doesn't restore session
   - Bypass UI for auth in other tests: use storageState or API login

5. SYSTEM DESIGN LEVEL QUESTIONS
================================================================================

Q: How would you design a test strategy for a micro-frontend architecture?
A:
   Micro-frontends are independently deployed UI modules. Testing strategy:

   1. UNIT + INTEGRATION PER MFE:
      Each micro-frontend has its own Jest/RTL test suite.
      Tests run independently in each repo's CI pipeline.

   2. CONTRACT TESTING:
      The "shell" app imports MFEs. Test the contract (props/events API).
      Any breaking change to a MFE's interface → contract test fails.
      Tool: Pact.js for consumer-driven contract testing.

   3. SHARED COMPONENT LIBRARY:
      If there's a shared design system, test it with Storybook + Chromatic.
      Visual regression catches inconsistencies across MFEs.

   4. E2E INTEGRATION:
      A separate E2E suite runs against the full composed application.
      Tests critical user journeys that span multiple MFEs.
      Use Playwright for its ability to handle cross-origin iFrames.

─────────────────────────────────────────────────────────────────────────────

Q: How would you test a Next.js application with SSR/SSG?
A:
   1. UNIT TESTS:
      - Test utility functions, data transformation, business logic
      - Test custom hooks (renderHook)

   2. COMPONENT TESTS (RTL):
      - Render client components normally
      - For server components: export just the async data fetching logic,
        mock it, test the client rendering separately

   3. API ROUTE TESTS:
      - Test Next.js API routes (route handlers) with Jest
      - Import the handler, create mock request/response objects, call directly

   4. E2E TESTS (Playwright):
      - Build the app: npm run build
      - Run with production server: npm run start
      - Test SSR: assert page title/meta tags from server-rendered HTML
      - Test SSG: assert static pages load instantly (no loading spinner)
      - Test middleware: authentication redirects, locale handling

─────────────────────────────────────────────────────────────────────────────

Q: How would you handle test data management at scale?
A:
   PRINCIPLES:
   1. Tests own their data — each test creates and cleans up its own data
   2. Data factories — generate test data programmatically (faker.js)
   3. Seeding API — REST endpoint for test data creation (test environments only)
   4. Database rollback — each E2E test runs in a transaction that rolls back

   PATTERNS:
   // Factory pattern:
   function createUser(overrides = {}) {
     return {
       id: uuid(),
       name: faker.person.fullName(),
       email: faker.internet.email(),
       ...overrides,
     };
   }

   // Usage in tests:
   const user = createUser({ email: 'alice@test.com' });

   ANTI-PATTERNS TO AVOID:
   ❌ Hardcoded test data IDs ("user-id-123")
   ❌ Tests that assume data created by other tests
   ❌ Shared fixtures that all tests modify

6. BEHAVIORAL / CULTURE FIT QUESTIONS
================================================================================

Q: Tell me about a time a test caught a bug before it reached production.
A: (Template for your own story)
   Situation: We were adding pagination to the user list. The API returned
   page-based results. The developer assumed pageSize was always 10.
   A unit test for the pagination selector tested edge case: 0 results.
   It caught that an empty page returned undefined instead of an empty array,
   which would crash the component.
   Result: Fixed before PR merge. The crash would have affected 2% of users
   who had no results on a certain filter combination.

─────────────────────────────────────────────────────────────────────────────

Q: What's your opinion on 100% code coverage?
A: "100% coverage is an aspirational metric, not a goal in itself.
    I've seen codebases with 95% coverage and critical untested paths
    because the tests had no meaningful assertions.
    
    I aim for high branch coverage on business-critical code (auth, payments,
    data processing), and I use coverage reports as a DISCOVERY tool —
    to find branches I forgot to test — not as a success metric.
    
    The real question is: 'If this breaks, will a test catch it?'
    Good tests answer yes. Coverage doesn't guarantee that."

─────────────────────────────────────────────────────────────────────────────

Q: How do you handle time pressure when testing gets skipped?
A: "Testing debt compounds like financial debt — skipped tests today = bugs
    tomorrow + harder refactoring later.
    
    My approach:
    1. Estimate test writing time AS PART OF the feature estimate.
       '3 days of dev' means '3 days of dev + tests'.
    2. Negotiate what test LEVEL — maybe no E2E for a minor feature,
       but at least integration tests.
    3. If testing is truly skipped due to deadline, create a ticket for
       'test debt' immediately — it's a known risk, not forgotten.
    4. Never use coverage as proof of quality to stakeholders without
       context. Be honest about what's tested and what isn't."
