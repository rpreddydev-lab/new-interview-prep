1. E2E FUNDAMENTALS (BEGINNER)
================================================================================

Q: What is end-to-end testing and how does it differ from unit/integration testing?
A:
  Unit Testing:    Tests a single function/module in isolation. No real DOM,
                   no real HTTP, everything mocked. Fast, cheap.

  Integration:     Tests multiple units together. May use real DOM with jsdom.
                   Mocked APIs (MSW). Moderate speed.

  E2E Testing:     Tests the full user journey through the REAL browser,
                   hitting (or stubbing) real network requests, exercising
                   real UI rendering. Slow, expensive, but highest confidence.

  Example:
  Unit: "the formatPrice function returns '$10.00' for input 1000"
  Integration: "the CartItem component shows formatted price"
  E2E: "user adds item to cart, sees $10.00 in checkout, clicks Buy, sees order confirmation"

─────────────────────────────────────────────────────────────────────────────

Q: What are the trade-offs of E2E tests? When are they most valuable?
A:
  PROS:
  + Highest confidence — tests real user flows
  + Catches integration bugs that unit tests miss (API contract mismatch, routing)
  + Tests accessibility interactions in real browser
  + Catches issues in third-party integrations

  CONS:
  - Slow (10-30x slower than unit tests)
  - Flaky (network, timing, browser rendering)
  - Expensive (browser setup, parallelization costs)
  - Hard to debug when they fail

  MOST VALUABLE FOR:
  - Critical business flows (checkout, login, sign-up, payment)
  - Flows spanning multiple pages
  - Flows that require real browser APIs (clipboard, file upload, webcam)
  - Regression detection for known bugs

─────────────────────────────────────────────────────────────────────────────

Q: How many E2E tests should a typical application have?
A: Follow the testing pyramid: E2E tests should be the SMALLEST layer.
   A rough guideline:
   - Small app: 5-15 E2E tests (happy paths only)
   - Medium app: 15-50 E2E tests
   - Large app: 50-200 E2E tests

   Focus E2E tests on CRITICAL USER JOURNEYS, not comprehensive coverage.
   A test suite with 500 E2E tests is a maintenance nightmare — prefer
   expanding integration test coverage instead.

2. CYPRESS QUESTIONS (INTERMEDIATE)
================================================================================

Q: What is Cypress's architecture? How does it execute tests?
A: Cypress runs INSIDE the browser. The test code and the app under test run
   in the same browser context (same process). Cypress injects a JavaScript
   proxy alongside your app.

   This means:
   + Direct access to the DOM (same window object)
   + Can stub network at the browser level
   + Time-travel debugging (DOM snapshots per command)
   - Limited to same-origin (one domain per test, by default)
   - Can't open multiple browser tabs natively

─────────────────────────────────────────────────────────────────────────────

Q: What is Cypress's command queue and how does async work?
A: Cypress commands are SYNCHRONOUS to write but ASYNCHRONOUS to execute.
   cy.get(), cy.click(), etc. don't execute immediately — they are queued
   and executed in order with built-in auto-waiting.

   cy.get('.button').click();  // Not immediately — added to queue

   This means:
   ❌ DON'T use async/await with Cypress commands
   ❌ DON'T assign cy.get() to a variable expecting the DOM element
   ✅ Use .then() to access yielded values
   ✅ Use .as() to alias values for later use

   const $el = cy.get('.btn'); // NOT the button! It's a Cypress chainable.
   cy.get('.btn').then(($el) => { /* $el is now the jQuery element */ });

─────────────────────────────────────────────────────────────────────────────

Q: What is cy.intercept() and how do you use it?
A: cy.intercept() intercepts network requests and allows you to:
   - Stub a response (return a fake response)
   - Spy on a request (wait for it to happen)
   - Modify the response before it reaches the app

   // Stub:
   cy.intercept('GET', '/api/users', { fixture: 'users.json' }).as('getUsers');

   // Spy and wait:
   cy.intercept('POST', '/api/login').as('loginRequest');
   cy.get('[data-testid="submit"]').click();
   cy.wait('@loginRequest').then(({ request, response }) => {
     expect(request.body.email).to.equal('alice@example.com');
     expect(response.statusCode).to.equal(200);
   });

─────────────────────────────────────────────────────────────────────────────

Q: What are Cypress custom commands and when should you use them?
A: Custom commands extend cy.* with reusable actions:

   // cypress/support/commands.ts
   Cypress.Commands.add('login', (email, password) => {
     cy.request('POST', '/api/auth/login', { email, password })
       .then(({ body }) => {
         window.localStorage.setItem('token', body.token);
       });
   });

   // Usage:
   cy.login('alice@example.com', 'password123');

   When to use:
   ✅ Authentication shortcuts (bypass UI for login)
   ✅ Repeated multi-step interactions (fill a complex form)
   ✅ Common assertions used across many tests

   Anti-pattern: Don't create commands for every tiny action.
   If something is only used once, keep it inline.

─────────────────────────────────────────────────────────────────────────────

Q: What is the difference between cy.get() and cy.find()?
A: cy.get() queries the ENTIRE document from the root.
   cy.find() queries within the previously yielded element (scoped).

   cy.get('[data-testid="dialog"]').find('button[type="submit"]');
   // Equivalent to: within(dialog).getByRole('button', { name: 'Submit' })

3. PLAYWRIGHT QUESTIONS (INTERMEDIATE)
================================================================================

Q: How does Playwright differ architecturally from Cypress?
A: Playwright runs tests in Node.js (OUT of browser process).
   It communicates with browsers via CDP (Chrome DevTools Protocol).

   Benefits:
   + Real cross-browser support (Chromium, Firefox, WebKit/Safari)
   + Multi-tab, multi-context, cross-origin support
   + Test process crash won't crash the browser
   + Native async/await (no command queue confusion)
   + Built-in parallelization (no paid service needed)

─────────────────────────────────────────────────────────────────────────────

Q: What are Playwright Locators and why are they better than direct selectors?
A: Locators are lazy, re-queryable references to elements. They:
   - Are evaluated at the time of each action (not when defined)
   - Automatically retry (built-in waiting)
   - Are STRICT by default (throw if multiple matches)
   - Work with the most recent DOM state

   const btn = page.getByRole('button', { name: 'Submit' });
   // 'btn' doesn't query the DOM yet
   await btn.click();  // NOW it finds and clicks the button

   vs. querySelector:
   const el = await page.$('button');  // evaluated immediately, may be stale

─────────────────────────────────────────────────────────────────────────────

Q: What is a Playwright Fixture and what is the Page Object Model?
A: FIXTURES: A mechanism to set up and share state across tests.
   Built-in: page, browser, context.
   Custom: extend test with your own:

   const test = base.extend({
     loggedInPage: async ({ page }, use) => {
       await page.goto('/login');
       await page.fill('#email', 'alice@example.com');
       await page.click('button[type="submit"]');
       await use(page); // provide the logged-in page to the test
     },
   });

   test('dashboard shows welcome message', async ({ loggedInPage }) => {
     await expect(loggedInPage.getByText('Welcome, Alice')).toBeVisible();
   });

   PAGE OBJECT MODEL (POM): Pattern to encapsulate page interactions in classes:

   class LoginPage {
     constructor(private page: Page) {}
     async login(email: string, password: string) {
       await this.page.getByLabel('Email').fill(email);
       await this.page.getByLabel('Password').fill(password);
       await this.page.getByRole('button', { name: 'Sign In' }).click();
     }
   }

   WHY POM: If the login form changes, you update ONE class, not 50 tests.

─────────────────────────────────────────────────────────────────────────────

Q: How do you handle authentication in Playwright tests efficiently?
A: Logging in via the UI for every test is slow. Use storageState:

   // global-setup.ts — runs once before all tests:
   async function globalSetup() {
     const browser = await chromium.launch();
     const page = await browser.newPage();
     await page.goto('/login');
     await page.fill('#email', 'alice@test.com');
     await page.click('[type="submit"]');
     await page.context().storageState({ path: 'auth.json' });
     await browser.close();
   }

   // playwright.config.ts:
   use: { storageState: 'auth.json' }  // reuse auth for every test

   // auth.json contains: cookies, localStorage, sessionStorage
   // Tests start already authenticated — saves 3-5 seconds per test

─────────────────────────────────────────────────────────────────────────────

Q: What is Playwright sharding and how does it enable parallelization?
A: Sharding splits the test suite across multiple CI machines.

   # Run tests on 3 machines in parallel:
   # Machine 1:
   npx playwright test --shard=1/3

   # Machine 2:
   npx playwright test --shard=2/3

   # Machine 3:
   npx playwright test --shard=3/3

   # After all 3 complete, merge HTML reports:
   npx playwright merge-reports --reporter html ./blobs

   In GitHub Actions matrix:
   strategy:
     matrix:
       shard: [1, 2, 3]
   run: npx playwright test --shard=${{ matrix.shard }}/3

   No paid service required! Just standard CI parallelism.

4. SELECTORS AND LOCATORS (INTERMEDIATE)
================================================================================

Q: What is the best selector strategy for E2E tests?
A: PRIORITY ORDER:
   1. Accessible attributes (role, label): Most stable, tests accessibility
   2. data-testid: Stable, test-specific, immune to text/style changes
   3. Text content: OK for user-visible text, brittle if copy changes
   4. CSS classes: Brittle, classes change during styling refactors
   5. XPath: Most brittle, avoid unless necessary

   data-testid convention:
   data-testid="submit-button" — kebab-case, purpose-specific
   data-testid="user-list-item" — not "test-1" or "div-2"

─────────────────────────────────────────────────────────────────────────────

Q: Why should you avoid CSS class selectors in E2E tests?
A: CSS classes:
   - Are used for STYLING — they change when designers redesign
   - May be auto-generated (CSS Modules, Tailwind JIT classes)
   - Don't reflect the user's perspective
   - Example: .btn-primary-v2 → .cta-button (class rename = test failure)

   Use accessible attributes instead — they reflect what users see and
   what assistive technologies interact with.

5. NETWORK INTERCEPTION (INTERMEDIATE)
================================================================================

Q: Should E2E tests hit real APIs or mock them?
A: Depends on the test strategy:

  REAL API (pure E2E):
  + Most realistic
  + Tests full stack integration
  - Slow (DB queries, network latency)
  - Requires seeded data
  - Tests can interfere with each other (state in shared DB)

  STUBBED/MOCKED NETWORK:
  + Fast and deterministic
  + Can test edge cases (network errors, 500s, timeouts)
  + Tests in isolation
  - May miss API contract mismatches

  RECOMMENDED HYBRID:
  - Stub 90% of calls for speed
  - Have a small suite of "smoke tests" hitting real API for confidence

─────────────────────────────────────────────────────────────────────────────

Q: How do you test error states in E2E tests?
A:
  // Cypress:
  cy.intercept('POST', '/api/checkout', { statusCode: 500 }).as('checkout');
  cy.get('[data-testid="buy-button"]').click();
  cy.wait('@checkout');
  cy.get('[role="alert"]').should('contain', 'Something went wrong');

  // Playwright:
  await page.route('/api/checkout', (route) =>
    route.fulfill({ status: 500, body: JSON.stringify({ error: 'Server error' }) })
  );
  await page.getByRole('button', { name: 'Buy' }).click();
  await expect(page.getByRole('alert')).toContainText('Something went wrong');

6. CI/CD AND PERFORMANCE (SENIOR)
================================================================================

Q: How do you integrate E2E tests into a CI/CD pipeline?
A: Best practice staging strategy:
   Stage 1 (fast, ~2 min): Lint + unit tests + type check
   Stage 2 (~5 min): Build application
   Stage 3 (parallel, ~10 min): E2E tests against built app

   Key considerations:
   - Start the dev server before tests (start-server-and-test or Playwright webServer)
   - Use parallelization to stay under 15 minutes total
   - Upload test artifacts (reports, traces) on failure
   - Run E2E on every PR, not just main branch

─────────────────────────────────────────────────────────────────────────────

Q: How do you reduce E2E test suite execution time?
A:
  1. Parallelization: Run tests across multiple workers/machines
  2. Auth shortcuts: storageState or API login instead of UI login
  3. API data setup: Create test data via API, not UI
  4. Smart selection: Only run affected tests on PRs (test impact analysis)
  5. Headless mode: Always run headless in CI (no browser UI overhead)
  6. Skip non-critical browsers: Run Chrome only on PR, full cross-browser on main
  7. Limit retries in CI: Don't retry flaky tests 3x — it masks real problems

7. FLAKY TESTS (SENIOR)
================================================================================

Q: What makes E2E tests flaky and how do you prevent it?
A: COMMON CAUSES:
   1. Race conditions (element not ready, animation still running)
   2. Time-dependent data (timestamps, "3 minutes ago" text)
   3. Shared test state (one test leaves dirty DB state for the next)
   4. Network variability (slow CI vs fast dev machine)
   5. Explicit sleeps (cy.wait(2000) is never the right answer)
   6. Brittle selectors (class names that change often)

   PREVENTION:
   1. Use smart waits: cy.wait('@alias'), expect(locator).toBeVisible()
   2. Isolate tests: Each test seeds own data, cleans up after
   3. Use deterministic data: Mock time/dates in tests
   4. Use data-testid for stability
   5. Test retry (last resort): retries: { runMode: 2 } — masks problems

─────────────────────────────────────────────────────────────────────────────

Q: How do you handle a test that's flaky in CI but passes locally?
A:
  1. Check CI vs local differences:
     - Different OS (font rendering, file paths)
     - Different screen size / resolution
     - Different network speed
     - Different parallelism (resource contention)

  2. Add more specific waits:
     await expect(page.getByRole('heading')).toBeVisible(); // not just goto()

  3. Use Playwright's --repeat-each flag to reproduce locally:
     npx playwright test --repeat-each=20 (run 20 times to catch rare failure)

  4. Check for animation/transition timing issues:
     Add reducedMotion: 'reduce' to emulateMedia

  5. Check for shared state: Is another test affecting this one?
     Add test isolation (clean DB state before each test)

  6. Quarantine strategy: Mark as skip while you investigate,
     track flaky tests in a GitHub issue, fix within 1 sprint.

8. QUICK-FIRE ANSWERS
================================================================================

Q: When does Cypress throw an error vs Playwright?
A: Cypress throws "element not found" after default 4000ms timeout.
   Playwright throws "element not found" after default 30000ms timeout.
   Both auto-retry until timeout.

Q: What is the Page Object Model?
A: A design pattern where each page/component has a class that encapsulates
   selectors and interactions. Tests use page objects, not raw selectors.
   Benefit: One class to update when UI changes, not 20 tests.

Q: Why are cy.wait(1000) and page.waitForTimeout(1000) bad practices?
A: They add arbitrary fixed delays. If the app is slow, 1000ms might not be
   enough. If the app is fast, 1000ms wastes time. Use conditional waits:
   cy.wait('@apiAlias') or await expect(locator).toBeVisible()

Q: What is Cypress Cloud?
A: Cypress's paid SaaS product. Provides: parallel test execution, test
   analytics, flakiness detection, test replay (video). Alternative to
   Playwright's free built-in sharding.

Q: What is the webServer config in Playwright?
A: Tells Playwright to start and wait for your dev server before tests:
   webServer: { command: 'npm run dev', url: 'http://localhost:3000' }
   No need for start-server-and-test package.

Q: How do you take a screenshot when a test fails in Playwright?
A: It's automatic. Configure in playwright.config.ts:
   screenshot: 'only-on-failure'  or  screenshot: 'on'
   Screenshots saved in test-results/ and shown in HTML report.

Q: What does test.fixme() do in Playwright?
A: Marks a test as fixme — skipped but tracked. Like test.skip() but
   communicates "this is a known broken test that needs fixing soon."
