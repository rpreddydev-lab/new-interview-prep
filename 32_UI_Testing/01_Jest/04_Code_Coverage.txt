1. WHAT IS CODE COVERAGE?
================================================================================

Code coverage is a metric that measures what percentage of your source code
is executed during your test suite.

It answers: "Which parts of my code are exercised by tests?"

WHAT IT IS:
  - A quantitative measure of test completeness
  - A tool for finding UNTESTED code paths
  - A quality gate in CI pipelines

WHAT IT IS NOT:
  - A measure of test quality
  - A guarantee that code is bug-free
  - The goal itself (coverage is a means, not an end)

FAMOUS QUOTE:
  "100% coverage with bad assertions is meaningless.
   80% coverage with meaningful assertions is valuable."

EXAMPLE: False sense of security
  function divide(a, b) {
    return a / b;
  }

  // This test achieves 100% line coverage:
  it('divides numbers', () => {
    expect(divide(4, 2)).toBe(2); // PASSES — but never tests division by zero!
  });

2. COVERAGE TYPES EXPLAINED
================================================================================

Jest (via Istanbul) provides 4 types of coverage metrics:

────────────────────────────────────────────────────────────────────────────────
STATEMENT COVERAGE
────────────────────────────────────────────────────────────────────────────────
  Was each statement (line of code) executed?

  function processUser(user) {
    const name = user.name;       // Statement 1
    if (!name) {
      return null;                // Statement 2
    }
    return name.toUpperCase();    // Statement 3
  }

  // Test only: processUser({ name: 'Alice' })
  // Coverage:  Statements 1 and 3 executed = 2/3 = 66.6%
  //            Statement 2 was NOT covered

────────────────────────────────────────────────────────────────────────────────
BRANCH COVERAGE
────────────────────────────────────────────────────────────────────────────────
  Was each branch of a conditional executed?
  (if/else, ternary, switch, &&, ||, ??)

  function getDiscount(user) {
    if (user.isPremium) {         // Branch: true + false
      return 0.2;
    } else {
      return 0.1;
    }
  }

  // Test only: getDiscount({ isPremium: true })
  // Branch coverage: 1/2 = 50% (else branch never taken)

  // More subtle: Short-circuit evaluation
  const name = user && user.name; // 2 branches: user truthy, user falsy

  // Ternary also counts:
  const label = count > 1 ? 'items' : 'item'; // 2 branches

────────────────────────────────────────────────────────────────────────────────
FUNCTION COVERAGE
────────────────────────────────────────────────────────────────────────────────
  Was each function called at least once?

  function add(a, b) { return a + b; }       // Called in tests → covered
  function subtract(a, b) { return a - b; }  // NOT called → uncovered

  // Function coverage: 1/2 = 50%

────────────────────────────────────────────────────────────────────────────────
LINE COVERAGE
────────────────────────────────────────────────────────────────────────────────
  Was each physical line of code executed?
  Similar to statement coverage but counts lines, not statements.

  // Multiple statements on one line:
  const x = 1; const y = 2; // One line, two statements

  // Statement coverage: 2/2 = 100%
  // Line coverage: 1/1 = 100%
  // They can differ for complex code.

WHICH MATTERS MOST?
  Branch coverage is typically the most important metric.
  Untested branches = untested error conditions = bugs.

3. RUNNING COVERAGE REPORTS
================================================================================

CLI COMMANDS:
  npx jest --coverage
  npx jest --coverage --coverageReporters=text
  npx jest --coverage --watchAll=false  # CI mode, don't watch
  npx jest --coverage --coverageDirectory=./reports/coverage

OUTPUT FORMATS:
  text       → Terminal table (default)
  text-summary → Brief terminal summary
  lcov       → Standard format, used by CI services
  html       → Visual browser report in coverage/ directory
  json       → Machine-readable output
  clover     → XML format (Java tools)
  cobertura  → XML format (Azure DevOps)

VIEWING HTML REPORT:
  npx jest --coverage && open coverage/lcov-report/index.html
  # On macOS/Linux: open
  # On Windows: start coverage\lcov-report\index.html

THE HTML REPORT SHOWS:
  - File-by-file breakdown
  - Line-by-line highlighting: green (covered), red (uncovered), yellow (partial)
  - Clickable files for drill-down
  - Summary statistics per directory

5. COVERAGE CONFIGURATION IN JEST
================================================================================

// jest.config.ts
const config = {
  // Don't auto-collect coverage — only with --coverage flag
  collectCoverage: false,

  // WHICH files to include in coverage (even if not tested)
  collectCoverageFrom: [
    'src/**/*.{ts,tsx}',           // Include all source files
    '!src/**/*.d.ts',              // Exclude TypeScript declaration files
    '!src/**/*.test.{ts,tsx}',     // Exclude test files themselves
    '!src/**/*.spec.{ts,tsx}',     // Exclude spec files
    '!src/**/*.stories.{ts,tsx}',  // Exclude Storybook stories
    '!src/**/index.ts',            // Exclude barrel exports
    '!src/main.tsx',               // Exclude entry point
    '!src/setupTests.ts',          // Exclude test setup
    '!src/vite-env.d.ts',          // Exclude Vite types
  ],

  // Output directory for coverage reports
  coverageDirectory: 'coverage',

  // Output formats
  coverageReporters: ['text', 'text-summary', 'lcov', 'html'],

  // Provider: 'babel' (default) or 'v8'
  coverageProvider: 'babel',
};

IMPORTANT: collectCoverageFrom includes files even if they have ZERO tests.
Without this, coverage is only calculated for files that are imported by tests.
This is a critical distinction — without it, untested files don't appear!

6. SETTING COVERAGE THRESHOLDS
================================================================================

Thresholds enforce minimum coverage levels and FAIL the CI build if not met.

GLOBAL THRESHOLDS:
  coverageThreshold: {
    global: {
      branches: 80,    // 80% of branches must be covered
      functions: 80,   // 80% of functions must be covered
      lines: 80,       // 80% of lines must be covered
      statements: 80,  // 80% of statements must be covered
    }
  }

PER-FILE THRESHOLDS:
  coverageThreshold: {
    global: { branches: 70, lines: 70 },
    // High-stakes files require higher coverage:
    './src/utils/payment.ts': { branches: 100, lines: 100, functions: 100 },
    './src/utils/': { branches: 90, lines: 90 },
    // Wildcard patterns (globs):
    './src/components/**/*.tsx': { lines: 85 },
  }

THRESHOLD FAILURE OUTPUT:
  Jest: "Global coverage threshold for branches (80%) not met: 75%"
  Jest: "Coverage threshold for ./src/utils/payment.ts branches (100%) not met: 92%"

TYPICAL THRESHOLDS BY CONTEXT:
  New project (greenfield):  90%+ with strict TDD
  Established project:       80% global
  Legacy/retrofitted tests:  60-70% (growing over time)
  Critical business logic:   95-100% for specific modules

STARTING FROM ZERO:
  If adding coverage to a project with no tests, start with current coverage
  levels and increment gradually (+2% per sprint):

  // Start: document what you have
  coverageThreshold: {
    global: { lines: 45 }  // Current actual level
  }
  // Next sprint: raise to 47, then 49, etc.

7. EXCLUDING CODE FROM COVERAGE
================================================================================

METHOD 1: collectCoverageFrom exclude patterns (BEST — in jest.config.ts)
  collectCoverageFrom: [
    'src/**/*.{ts,tsx}',
    '!src/**/*.stories.tsx',  // Exclude Storybook stories
    '!src/mocks/**',          // Exclude mock files
  ]

METHOD 2: Inline comments (for specific lines/blocks)
  Coverage ignore directives (Istanbul syntax):

  /* istanbul ignore next */
  /* istanbul ignore if */
  /* istanbul ignore else */
  /* istanbul ignore file */  (entire file)

  EXAMPLES:
    // Ignore a whole function:
    /* istanbul ignore next */
    function debugOnlyFunction() {
      console.log('debug info');
    }

    // Ignore an if branch:
    if (process.env.NODE_ENV !== 'production') {
      /* istanbul ignore next */
      debugTools.init();
    }

    // Ignore an else branch:
    if (condition) {
      doSomething();
    } else /* istanbul ignore next */ {
      handleEdgeCase(); // very hard to test in unit tests
    }

    // Ignore an entire file:
    /* istanbul ignore file */
    // Use at the top of the file

METHOD 3: V8 coverage comments (when using coverageProvider: 'v8')
  /* c8 ignore next */
  /* c8 ignore start */
  /* c8 ignore stop */

COMMON LEGITIMATE EXCLUSIONS:
  - Type definitions (*.d.ts)
  - Config files (jest.config.ts, babel.config.js)
  - Entry points (main.tsx, index.ts)
  - Storybook stories
  - Code only relevant in specific environments (dev-only features)
  - Fallback error handlers for "impossible" states

8. COVERAGE PROVIDERS: ISTANBUL vs V8
================================================================================

ISTANBUL (BABEL) — default:
  - Instruments code by inserting tracking calls during transformation
  - Works with Babel and ts-jest
  - More accurate for complex code patterns
  - Slower (adds instrumentation overhead)
  - Uses /* istanbul ignore */ comments

  // jest.config.ts (default):
  coverageProvider: 'babel',  // 'babel' is the default

V8 — modern alternative:
  - Uses Node.js V8 engine's built-in coverage reporting
  - No code instrumentation needed
  - Faster (no overhead during execution)
  - Less accurate for some patterns (ternaries, destructuring)
  - Uses /* c8 ignore */ comments

  // jest.config.ts:
  coverageProvider: 'v8',

RECOMMENDATION:
  - Use babel (Istanbul) for maximum accuracy and compatibility
  - Use v8 for large projects where test speed is critical
  - Vitest uses v8 by default and it works well

9. INTEGRATING WITH CI SERVICES
================================================================================

CODECOV (most popular):
  - Tracks coverage over time
  - Shows coverage diff on PRs ("this PR increased coverage by 2%")
  - Free for open source

  // GitHub Actions:
  - name: Run Tests with Coverage
    run: npx jest --coverage --ci

  - name: Upload coverage to Codecov
    uses: codecov/codecov-action@v3
    with:
      token: ${{ secrets.CODECOV_TOKEN }}
      files: ./coverage/lcov.info
      fail_ci_if_error: true

COVERALLS:
  - Similar to Codecov
  - Good integration with GitHub/GitLab

  - name: Upload coverage to Coveralls
    uses: coverallsapp/github-action@v2
    with:
      file: ./coverage/lcov.info

GITHUB ACTIONS: ARTIFACT UPLOAD
  - name: Archive coverage report
    uses: actions/upload-artifact@v3
    with:
      name: coverage-report
      path: coverage/lcov-report/

SONARQUBE (Enterprise):
  For large enterprise projects with detailed quality metrics.
  Configure in sonar-project.properties:
    sonar.javascript.lcov.reportPaths=coverage/lcov.info

10. COVERAGE BEST PRACTICES
================================================================================

DO:
  ✅ Set realistic thresholds based on current coverage, then improve
  ✅ Exclude generated and boilerplate code from coverage
  ✅ Focus on BRANCH coverage — it reveals untested conditions
  ✅ Use HTML report to visually find gaps
  ✅ Track coverage trends in CI over time
  ✅ Require coverage thresholds in CI — fail builds that drop below

DON'T:
  ❌ Chase 100% coverage blindly
  ❌ Write tests just to hit coverage numbers (test-washing)
  ❌ Trust coverage as a proxy for test quality
  ❌ Include test files, mocks, and stories in coverage metrics
  ❌ Ignore the "Uncovered Lines" column — those are your testing gaps

GOOD CANDIDATES FOR HIGH COVERAGE:
  - Business logic (validators, calculators, formatters) → 90-100%
  - Authentication/authorization code → 90-100%
  - Data transformation utilities → 90-100%
  - Error handling paths → 90-100%

ACCEPTABLE LOWER COVERAGE:
  - UI components with many conditional render states → 70-80%
  - Configuration files → Not worth testing
  - Generated code (GraphQL types, proto stubs) → Exclude entirely

INTERVIEW INSIGHT:
  "What's your approach to code coverage?"
  Answer: "Coverage is a tool, not a goal. I use it to find untested code
  paths, especially branches — those represent unhandled conditions that
  often lead to bugs. I set CI thresholds at ~80% globally and higher for
  critical business logic. I never write tests purely to hit numbers —
  every test should validate real behavior."
