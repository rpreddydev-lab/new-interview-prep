1. WHAT IS END-TO-END TESTING
================================================================================

End-to-End (E2E) testing verifies the entire application flow from the user's
perspective — exactly as a real user would interact with it.

An E2E test:
  - Opens a real browser (or headless browser)
  - Navigates to your app's URL
  - Interacts with the UI (click, type, select, upload)
  - Asserts on what the user sees (text, URLs, screenshots)
  - Optionally, checks network requests or database state

E2E tests are HIGH CONFIDENCE because they test the full stack:
  Browser → React App → API Client → HTTP → Backend → Database → Response → UI

EXAMPLE (Cypress syntax):
  it('user can log in and see their dashboard', () => {
    cy.visit('/login');
    cy.get('[data-testid="email"]').type('alice@example.com');
    cy.get('[data-testid="password"]').type('password123');
    cy.get('button[type="submit"]').click();
    cy.url().should('include', '/dashboard');
    cy.contains('Welcome, Alice').should('be.visible');
  });

EXAMPLE (Playwright syntax):
  test('user can log in and see their dashboard', async ({ page }) => {
    await page.goto('/login');
    await page.getByLabel('Email').fill('alice@example.com');
    await page.getByLabel('Password').fill('password123');
    await page.getByRole('button', { name: /sign in/i }).click();
    await expect(page).toHaveURL('/dashboard');
    await expect(page.getByText('Welcome, Alice')).toBeVisible();
  });

2. WHERE E2E FITS IN THE TESTING STRATEGY
================================================================================

TESTING PYRAMID:
         ┌─────────────┐
         │    E2E      │  ← Few, slow, expensive but high confidence
         ├─────────────┤
         │ Integration │  ← Some, medium speed and cost
         ├─────────────┤
         │    Unit     │  ← Many, fast, cheap, low confidence per test
         └─────────────┘

TESTING TROPHY (Kent C. Dodds):
         ┌─────────────┐
         │    E2E      │  ← Few critical flows
         ├─────────────┤
         │ Integration │  ← Most tests here (best ROI)
         ├─────────────┤
         │    Unit     │  ← Pure functions, complex logic
         ├─────────────┤
         │   Static    │  ← TypeScript, ESLint
         └─────────────┘

E2E ROLE IN A HEALTHY TESTING SUITE:
  - 5-10% of your total tests should be E2E
  - Focus on CRITICAL USER JOURNEYS (login, checkout, signup)
  - Don't duplicate what integration tests already cover
  - E2E tests are the final safety net

KEY PRINCIPLE: "Write as few E2E tests as you can get away with,
                while still having confidence in your critical paths."

3. WHAT E2E TESTS SHOULD COVER
================================================================================

IDEAL E2E TEST CANDIDATES (Critical User Journeys):

  1. Authentication:
     - User sign-up (email + verification)
     - Login and session persistence
     - Logout
     - Password reset flow

  2. Core Business Flows:
     - E-commerce: Add to cart → Checkout → Order confirmation
     - SaaS: Create account → Set up project → Invite team member
     - Banking: Transfer money → Verify in history
     - Social: Create post → See it in feed

  3. Navigation:
     - Main navigation links work
     - Deep links / direct URL access
     - 404 page for unknown routes

  4. Forms with Complex Validation:
     - Multi-step wizards
     - File uploads
     - Payment forms (Stripe, etc.)

  5. Real-time Features:
     - WebSocket-based live updates
     - Notifications

WHAT E2E TESTS SHOULD NOT COVER:
  ❌ Every UI variation (leave to unit tests)
  ❌ Error states that are hard to reproduce in a real browser
  ❌ Every form validation rule (leave to unit/integration tests)
  ❌ Responsive breakpoints (leave to visual regression tests)
  ❌ Accessibility details (leave to axe audits in unit tests)

4. E2E VS UNIT VS INTEGRATION TESTS
================================================================================

  ┌────────────────────┬──────────────┬───────────────┬───────────────┐
  │ Attribute          │ Unit         │ Integration   │ E2E           │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Speed              │ Very Fast    │ Fast          │ Slow          │
  │                    │ (<1ms)       │ (~100ms)      │ (1-30s)       │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Confidence         │ Low per test │ Medium        │ High          │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Scope              │ One function │ Component+API │ Full app      │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Real Browser       │ No (jsdom)   │ No (jsdom)    │ Yes           │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Real API           │ No (mock)    │ No (MSW)      │ Yes/Staging   │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Failure Clarity    │ Very clear   │ Clear         │ Sometimes     │
  │                    │              │               │ unclear       │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Maintenance        │ Low          │ Medium        │ High          │
  ├────────────────────┼──────────────┼───────────────┼───────────────┤
  │ Flakiness risk     │ Very low     │ Low           │ Medium/High   │
  └────────────────────┴──────────────┴───────────────┴───────────────┘

E2E tests are slow because:
  - Browser startup overhead (~500ms-2s)
  - Real network calls or local server startup
  - Waiting for animations, transitions
  - Database operations

5. KEY CONCEPTS IN E2E TESTING
================================================================================

TEST ENVIRONMENT:
  - A running version of your app (localhost or staging)
  - A test database (seeded with known data)
  - Or: tests interact with a staging environment

SELECTOR STRATEGIES (in order of preference):
  1. data-testid  → Most reliable, won't change with content
  2. Role + name  → Cypress/Playwright support accessible queries
  3. Text content → Fragile if copy changes
  4. CSS selectors → Very fragile, tied to implementation

PLAYWRIGHT LOCATOR PRIORITY (mirrors RTL):
  page.getByRole('button', { name: /submit/i })   // Best
  page.getByLabel('Email Address')
  page.getByText('Click here')
  page.getByTestId('submit-btn')                   // Fallback

ASSERTIONS (should be on what the user SEES):
  - URL has changed to expected route
  - Text is visible on the page
  - Element exists / doesn't exist
  - Form shows validation errors
  - Toast notification appears
  - Data updated after action

FLAKY TESTS:
  Tests that intermittently pass/fail due to timing, race conditions,
  or external dependencies. The biggest challenge in E2E testing.

  Prevention:
  - Use smart waits (waitForSelector, findBy) not sleep/setTimeout
  - Isolate tests (clean state before each test)
  - Use stable selectors (data-testid, roles)
  - Retry failed tests once (CI only)

HEADLESS vs HEADED MODE:
  Headless: Browser runs without UI (faster, for CI)
  Headed: Browser UI visible (for debugging, demo)

  Cypress: Cypress GUI (headed) vs npx cypress run (headless)
  Playwright: --headed flag for headed mode

6. HOW E2E TOOLS WORK
================================================================================

CYPRESS ARCHITECTURE:
  Runs test code in the same JavaScript process as the browser.
  Uses a proxy to intercept network requests.
  Has a time-travel debugger (snapshots of DOM at each step).
  Chrome/Edge/Firefox support. No Safari.

  Test Code → Cypress Commands → Browser (Electron/Chrome/Firefox)
  Cypress runs INSIDE the browser alongside your app.

PLAYWRIGHT ARCHITECTURE:
  Runs test code in Node.js, controls the browser via WebSocket (CDP/CDP2).
  Out-of-process — tests run in Node, browser runs separately.
  Chrome, Firefox, Safari (WebKit) support. True cross-browser.

  Test Code (Node.js) → WebSocket → Browser Process (Chromium/Firefox/WebKit)

7. THE E2E TESTING WORKFLOW
================================================================================

TYPICAL E2E TEST LIFECYCLE:

  1. Before the test suite:
     - Start your dev/test server (or point to staging)
     - Seed the test database (if using a real DB)
     - Set up authentication tokens / cookies

  2. Before each test:
     - Navigate to a known URL (or clear state)
     - Set up cookies, localStorage for pre-auth (if needed)
     - Reset database to known state (if using DB)

  3. During the test:
     - Perform user actions
     - Assert on visible results

  4. After each test:
     - Clean up (logout, delete created data)

  5. After the test suite:
     - Stop the test server
     - Generate reports

SEEDING DATA FOR TESTS:
  Cypress: cy.task() to run Node.js code (seed DB)
  Playwright: fixtures, global setup hooks, API calls to seed

  // Playwright global setup:
  async function globalSetup() {
    const response = await fetch('http://localhost:3000/api/seed', {
      method: 'POST',
    });
    await response.json();
  }

AUTHENTICATION SHORTCUTS:
  Don't fill in login form on every test! Pre-authenticate:

  // Playwright — save auth state:
  // (in setup script)
  await page.goto('/login');
  await page.fill('[name="email"]', 'alice@example.com');
  await page.fill('[name="password"]', 'password123');
  await page.click('[type="submit"]');
  await page.context().storageState({ path: 'auth.json' });

  // Reuse in tests:
  // playwright.config.ts:
  use: { storageState: 'auth.json' }

  // Cypress — set cookies/localStorage directly:
  cy.setCookie('session', 'abc123');
  cy.window().then(win => win.localStorage.setItem('token', 'abc123'));

8. TRADE-OFFS AND WHEN TO SKIP E2E
================================================================================

WHEN E2E IS WORTH IT:
  ✅ Critical user journeys (checkout, signup, payment)
  ✅ Smoke tests to verify deployment is working
  ✅ Flows that span many components and pages
  ✅ Features where regression would cause significant user/business impact

WHEN TO SKIP E2E AND USE INTEGRATION TESTS:
  ❌ Testing individual form validation rules
  ❌ Testing all UI states of a single component
  ❌ Testing API error handling in isolation
  ❌ Testing UI text content or styles

REAL COSTS OF E2E TESTS:
  - Slower CI pipeline (each E2E test = 5-30 seconds)
  - Flakiness creates noise in CI → engineers start ignoring failures
  - Harder to debug failures (network? Database? React? CSS?)
  - Requires a running server + often a real/seeded database
  - High maintenance when UI changes

RECOMMENDED E2E COUNT PER APP SIZE:
  Small app:   5-15 E2E tests (critical flows only)
  Medium app:  15-50 E2E tests (all major user journeys)
  Large app:   50-200 E2E tests (major journeys + regression suite)

9. E2E TESTING MENTAL MODEL
================================================================================

THINK LIKE A USER:
  Don't test "what does this component render"
  Test "what can a user DO with this app and what do they see"

  User Mental Model:
  "As a new user, I can sign up with my email, verify it, then see my dashboard."
  "As a shopper, I can search for a product, add it to cart, and complete payment."
  "As an admin, I can create a user, assign them a role, and they can log in."

LOCATORS: Pick based on stability
  Most stable → data-testid
  Most user-friendly → getByRole + accessible name
  Avoid → CSS selectors tied to styling classes

WAITS: Always use smart waits
  ✅ await page.waitForURL('/dashboard')
  ✅ await page.getByText('Order confirmed').waitFor()
  ✅ cy.url().should('include', '/dashboard')
  ❌ cy.wait(3000) // Hard-coded sleep — flaky and slow

ASSERTIONS: On user-visible outcomes
  ✅ User sees "Order placed successfully"
  ✅ URL changes to /confirmation
  ❌ Redux state has { orderId: '123' } — that's implementation detail
