================================================================
  REVOKE
================================================================

  REVOKE removes previously granted privileges.

================================================================
SYNTAX
================================================================

  REVOKE [ GRANT OPTION FOR ] privilege [, ...]
  ON object_type object_name
  FROM { user | role | PUBLIC }
  [ CASCADE | RESTRICT ];

  CASCADE: also revoke from anyone who received the privilege
           via WITH GRANT OPTION from this user.
  RESTRICT (default): fail if anyone else received the privilege
           through this user's GRANT OPTION.

================================================================
EXAMPLES
================================================================

  Revoke single privilege:
  REVOKE SELECT ON orders FROM alice;

  Revoke multiple:
  REVOKE INSERT, UPDATE, DELETE ON orders FROM temp_worker;

  Revoke from role:
  REVOKE analyst_role FROM alice;
  -- alice loses all privileges that came from analyst_role

  Revoke with cascade (remove downstream grants too):
  REVOKE SELECT ON orders FROM alice CASCADE;
  -- If alice used WITH GRANT OPTION to grant bob, bob loses it too

  Revoke only the grant option (keep the privilege itself):
  REVOKE GRANT OPTION FOR SELECT ON orders FROM alice;
  -- alice can still SELECT, but can no longer grant it to others

  Revoke from PUBLIC:
  REVOKE SELECT ON lookup_codes FROM PUBLIC;

================================================================
REVOKE IN DIFFERENT DATABASES
================================================================

  MySQL:
  REVOKE SELECT ON mydb.orders FROM 'alice'@'localhost';
  REVOKE ALL PRIVILEGES ON mydb.* FROM 'old_user'@'%';
  FLUSH PRIVILEGES;

  SQL Server:
  REVOKE SELECT ON dbo.orders FROM alice;

================================================================
GRANT vs REVOKE vs DENY
================================================================

  Most databases: REVOKE removes a GRANT; if no other source of
  privilege exists, the user loses access.

  SQL Server adds DENY:
  DENY SELECT ON dbo.salary TO alice;
  -- alice is blocked EVEN IF she has SELECT through a role
  -- DENY wins over GRANT -- explicit block, not just removal

  Standard SQL / PostgreSQL has no DENY. Access is additive.

================================================================
AUDIT: CHECKING CURRENT PRIVILEGES
================================================================

  PostgreSQL:
  SELECT grantee, privilege_type, table_name
  FROM information_schema.role_table_grants
  WHERE table_schema = 'public';

  \dp orders          -- in psql: show privileges on table
  \du alice           -- show user's roles

  MySQL:
  SHOW GRANTS FOR 'alice'@'localhost';

================================================================
INTERVIEW Q&A
================================================================

  Q: What is CASCADE in REVOKE?
  A: Removes the privilege from the specified user AND from all
     users who received it via that user's WITH GRANT OPTION.
     Without CASCADE, REVOKE fails if downstream grants exist.

  Q: Difference between REVOKE and DENY?
  A: REVOKE removes a specific grant. If user has another source
     of the privilege (via a role), they still have access.
     DENY (SQL Server only) explicitly blocks access, overriding
     any GRANTs from roles or other sources.

  Q: How do you find what privileges a user has?
  A: PostgreSQL: information_schema.role_table_grants or \dp.
     MySQL: SHOW GRANTS FOR 'user'@'host'.
