================================================================
  TRANSACTION LIFECYCLE
================================================================

================================================================
STATES
================================================================

  ACTIVE          After BEGIN; transaction is in progress
  PARTIALLY       After last DML; waiting for COMMIT to be flushed
  COMMITTED
  COMMITTED       COMMIT acknowledged; data permanent
  FAILED          Error occurred; must ROLLBACK
  ABORTED         After ROLLBACK; state restored to pre-BEGIN

  State transitions:
  START --> ACTIVE --> PARTIALLY COMMITTED --> COMMITTED (success path)
  START --> ACTIVE --> FAILED --> ABORTED  --> (restart possible)

================================================================
POSTGRESQL TRANSACTION STATES
================================================================

  PostgreSQL adds: if a DML statement fails inside a transaction,
  the transaction enters an error state.
  You MUST ROLLBACK before issuing any further SQL.

  BEGIN;
    INSERT INTO orders ...;         -- success
    INSERT INTO orders (id, ...) VALUES (SAME_ID, ...);  -- PK violation
    -- transaction is now in ERROR state
    SELECT * FROM orders;           -- ERROR: current transaction is aborted
  ROLLBACK;                         -- must roll back before any new work

  This surprises many developers who expect to continue after an error.

================================================================
IMPLICIT BEGIN IN PostgreSQL
================================================================

  If you run a DML statement without BEGIN, PostgreSQL wraps it
  in an implicit single-statement transaction:
  INSERT INTO orders ...;  -- equivalent to: BEGIN; INSERT...; COMMIT;

  For explicit multi-statement transactions, always use BEGIN.

================================================================
TRANSACTION IN SPRING / JPA
================================================================

  @Transactional lifecycle (Spring AOP proxy):
  1. Method invoked through Spring proxy
  2. Proxy obtains connection from HikariCP pool
  3. Proxy calls connection.setAutoCommit(false)
  4. Target method executes (multiple JDBC calls, JPA flushes)
  5a. Method returns normally --> proxy calls connection.commit()
  5b. RuntimeException thrown --> proxy calls connection.rollback()
  6. Connection returned to pool (autoCommit restored to true)

  JPA flush modes within transaction:
  FlushModeType.AUTO:    flush before query or at commit
  FlushModeType.COMMIT:  flush only at commit

================================================================
TWO-PHASE COMMIT (DISTRIBUTED)
================================================================

  For transactions spanning multiple databases/services:

  Phase 1 (Prepare):
  Coordinator asks all participants: "Can you commit?"
  Each participant writes to its WAL and responds "yes" or "no."

  Phase 2 (Commit / Rollback):
  If all say "yes": coordinator sends COMMIT to all.
  If any say "no": coordinator sends ROLLBACK to all.

  PREPARE TRANSACTION 'txid_1234';   -- PostgreSQL two-phase
  COMMIT PREPARED 'txid_1234';
  ROLLBACK PREPARED 'txid_1234';

================================================================
INTERVIEW Q&A
================================================================

  Q: What happens to a transaction when a Java application crashes
     after sending a COMMIT?
  A: If COMMIT was already written to the WAL and acknowledged,
     data is durable. If the crash happened before acknowledgment,
     the transaction is treated as aborted on recovery.

  Q: Why does PostgreSQL require ROLLBACK after a statement error?
  A: PostgreSQL puts the transaction in "aborted" state after any error.
     Further statements return "current transaction is aborted."
     You must ROLLBACK and start a new transaction.

  Q: What is the PREPARE TRANSACTION command for?
  A: Two-phase commit. PREPARE writes the transaction as "prepared"
     to disk. It can then be COMMITTED or ROLLED BACK by the coordinator,
     even after a server restart (persistent prepared state).
