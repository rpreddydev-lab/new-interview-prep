================================================================
  DEADLOCKS AND LOCKING
================================================================

================================================================
LOCKS
================================================================

  Databases use locks to prevent conflicting concurrent access.

  Lock Types:
  Row-level lock       Lock specific rows (most granular)
  Table-level lock     Lock entire table (less granular, blocks more)
  Page-level lock      Lock a storage page (MySQL MyISAM)
  Advisory lock        Application-defined lock (PostgreSQL pg_advisory_lock)

  Lock Modes (PostgreSQL):
  FOR UPDATE           Exclusive row lock; blocks other updates and locks
  FOR SHARE            Shared row lock; allows reads but blocks updates
  FOR NO KEY UPDATE    Less restrictive than FOR UPDATE
  FOR KEY SHARE        Allows FK checks but blocks FOR UPDATE

  Table-level modes (from least to most restrictive):
  ACCESS SHARE         (SELECT) -- allows all concurrent operations
  ROW SHARE            (SELECT FOR UPDATE/SHARE)
  ROW EXCLUSIVE        (INSERT/UPDATE/DELETE)
  SHARE UPDATE EXCLUSIVE (VACUUM, ANALYZE)
  SHARE                (CREATE INDEX)
  SHARE ROW EXCLUSIVE  (triggers, some foreign key)
  EXCLUSIVE            (rare)
  ACCESS EXCLUSIVE     (ALTER TABLE, DROP) -- blocks everything

================================================================
SELECT FOR UPDATE
================================================================

  Locks selected rows for the duration of the transaction.
  Prevents other transactions from modifying these rows.

  BEGIN;
    SELECT * FROM inventory WHERE product_id = 5 FOR UPDATE;
    -- Nobody else can UPDATE this row until this transaction ends
    UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 5;
  COMMIT;

  Use when: read-then-update pattern requires atomic check + update.

  SKIP LOCKED: skip rows already locked (queue processing):
  SELECT * FROM jobs WHERE status = 'PENDING' LIMIT 1 FOR UPDATE SKIP LOCKED;

  NOWAIT: fail immediately if lock can't be acquired:
  SELECT * FROM jobs WHERE id = 42 FOR UPDATE NOWAIT;

================================================================
DEADLOCK
================================================================

  Transaction A holds Lock 1, waits for Lock 2.
  Transaction B holds Lock 2, waits for Lock 1.
  Neither can proceed. This is a deadlock.

  Example:
  Tx A: BEGIN; UPDATE accounts SET balance=balance-100 WHERE id=1; (holds lock on row 1)
  Tx B: BEGIN; UPDATE accounts SET balance=balance-100 WHERE id=2; (holds lock on row 2)
  Tx A: UPDATE accounts SET balance=balance+100 WHERE id=2;         (waits for Tx B)
  Tx B: UPDATE accounts SET balance=balance+100 WHERE id=1;         (waits for Tx A)
  --> DEADLOCK

================================================================
DEADLOCK DETECTION AND RESOLUTION
================================================================

  Databases detect deadlock cycles and automatically ROLLBACK
  one of the transactions (usually the one that did less work).

  PostgreSQL error:
  ERROR: deadlock detected
  DETAIL: Process 12345 waits for ShareLock on transaction 67890;
          blocked by process 67890.
  HINT: See server log for query details.

  Application must catch DeadlockLoserDataAccessException (Spring)
  and retry the transaction.

================================================================
PREVENTING DEADLOCKS
================================================================

  1. Access tables/rows in consistent order:
     Always lock rows in order of ID (low to high):
     SELECT ... WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
     Never: lock row 2 then row 1 in one path, row 1 then row 2 in another.

  2. Keep transactions short:
     Long-running transactions hold locks longer, increasing deadlock chance.

  3. Use lower isolation levels when possible:
     READ COMMITTED uses shorter-lived locks in some databases.

  4. Use SKIP LOCKED for queue processing to avoid competing for same rows.

================================================================
LOCK MONITORING
================================================================

  PostgreSQL:
  SELECT pid, mode, granted, relation::regclass, query
  FROM pg_locks
  JOIN pg_stat_activity USING (pid)
  WHERE NOT granted;   -- show waiting queries

  Find blocking queries:
  SELECT blocking.pid, blocking.query, waiting.pid, waiting.query
  FROM pg_stat_activity blocking
  JOIN pg_stat_activity waiting
      ON waiting.wait_event = 'relation'
  WHERE NOT waiting.state = 'idle';

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a deadlock?
  A: Two or more transactions each hold a lock that the other needs.
     Both wait forever. The DB detects the cycle and automatically
     rolls back one transaction.

  Q: How do you prevent deadlocks in SQL?
  A: 1. Always access rows/tables in the same order across transactions.
     2. Keep transactions short.
     3. Use SKIP LOCKED for queue-style processing.
     4. Avoid holding locks during user interaction (open transaction).

  Q: What is SELECT FOR UPDATE?
  A: Acquires an exclusive row lock on selected rows for the duration
     of the transaction. Prevents other transactions from updating
     those rows until the lock is released (COMMIT/ROLLBACK).
