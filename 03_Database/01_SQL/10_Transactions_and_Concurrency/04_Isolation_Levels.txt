================================================================
  ISOLATION LEVELS
================================================================

  Isolation levels trade consistency guarantees for concurrency.
  Higher isolation = more protection, less concurrency.

================================================================
CONCURRENCY PHENOMENA
================================================================

  Dirty Read          Reading uncommitted data from another transaction.
                      Data may be rolled back --> read "phantom" data.

  Non-Repeatable Read Same row read twice in same tx returns different values.
                      Another tx committed an UPDATE between your reads.

  Phantom Read        Same query run twice returns different SET of rows.
                      Another tx committed INSERT or DELETE affecting result.

  Lost Update         Two txs read same value, both update based on it.
                      One update is silently overwritten.

================================================================
ISOLATION LEVELS COMPARISON
================================================================

  Level              Dirty Read  Non-Repeatable  Phantom Read  Lost Update
  ----------------   ----------  --------------  ------------  -----------
  READ UNCOMMITTED   Possible    Possible        Possible      Possible
  READ COMMITTED     Prevented   Possible        Possible      Possible
  REPEATABLE READ    Prevented   Prevented       Possible*     Prevented
  SERIALIZABLE       Prevented   Prevented       Prevented     Prevented

  * PostgreSQL REPEATABLE READ prevents phantoms too (MVCC snapshot).
  * MySQL REPEATABLE READ still has some phantom scenarios.

================================================================
READ UNCOMMITTED
================================================================

  Can read uncommitted (dirty) changes from other transactions.
  Fastest, least consistent.
  Almost never used in practice.
  MySQL supports it. PostgreSQL treats it as READ COMMITTED.

================================================================
READ COMMITTED (default for PostgreSQL, Oracle, SQL Server)
================================================================

  Each statement in the transaction gets a fresh snapshot.
  You always read the latest committed data.

  Problem: Non-repeatable reads.
  SELECT balance FROM accounts WHERE id = 1;  --> 1000
  -- another transaction commits: UPDATE balance = 500
  SELECT balance FROM accounts WHERE id = 1;  --> 500  (different!)

  SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

================================================================
REPEATABLE READ (default for MySQL InnoDB)
================================================================

  Transaction gets a snapshot at its START time.
  Same row read twice within the transaction returns the same value,
  even if other transactions committed changes.

  Problem: Phantom reads (other txs INSERT new rows).
  PostgreSQL: MVCC snapshot also prevents phantoms.
  MySQL: some scenarios still possible.

  SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

================================================================
SERIALIZABLE
================================================================

  Transactions appear to execute one at a time, serially.
  No concurrency anomalies possible.
  PostgreSQL uses Serializable Snapshot Isolation (SSI) -- optimistic.
  MySQL uses traditional locking for SERIALIZABLE -- pessimistic.

  Higher correctness, lower throughput. Use for financial or
  critical-correctness scenarios.

  SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

================================================================
SPRING / JPA ISOLATION LEVEL
================================================================

  @Transactional(isolation = Isolation.READ_COMMITTED)
  @Transactional(isolation = Isolation.REPEATABLE_READ)
  @Transactional(isolation = Isolation.SERIALIZABLE)
  @Transactional(isolation = Isolation.DEFAULT)  -- use DB default

================================================================
CHOOSING AN ISOLATION LEVEL
================================================================

  Scenario                              Recommended Level
  ------------------------------------  -----------------------
  Reporting (reads only)                READ COMMITTED
  Inventory with concurrent updates     REPEATABLE READ
  Financial transfers, exact balances   SERIALIZABLE
  Default for most web apps             READ COMMITTED

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a dirty read?
  A: Reading data that another transaction has modified but not yet
     committed. If that transaction rolls back, you read "phantom" data
     that never actually existed.

  Q: What is the difference between Repeatable Read and Serializable?
  A: Repeatable Read prevents dirty reads and non-repeatable reads.
     It still allows phantom reads (new rows from another tx appearing).
     Serializable prevents all anomalies -- transactions appear serial.

  Q: What isolation level does PostgreSQL default to?
  A: READ COMMITTED.

  Q: What is a phantom read?
  A: Running the same SELECT twice in one transaction returns different
     rows because another transaction committed an INSERT or DELETE
     that affects the result set of the query.
