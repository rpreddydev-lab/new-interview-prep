================================================================
  DDL — DATA DEFINITION LANGUAGE OVERVIEW
================================================================

  DDL defines and modifies the STRUCTURE of database objects.
  Unlike DML (INSERT/UPDATE/DELETE), DDL changes the schema, not data.

  Commands:  CREATE, ALTER, DROP, TRUNCATE, RENAME

  Key property in most RDBMS:
  DDL statements auto-commit — they cannot be rolled back.
  (PostgreSQL is an exception — DDL is transactional there.)

================================================================
DDL COMMANDS AT A GLANCE
================================================================

  Command    Purpose                              Can Rollback?
  ---------  -----------------------------------  ---------------------------------
  CREATE     Create a new object (table, index)   PostgreSQL: yes; Others: no
  ALTER      Modify an existing object            PostgreSQL: yes; Others: no
  DROP       Delete an object and its data        PostgreSQL: yes; Others: no
  TRUNCATE   Delete all rows from a table         PostgreSQL: yes; Others: no
  RENAME     Rename an object                     PostgreSQL: yes; Others: no

================================================================
OBJECTS YOU CAN CREATE WITH DDL
================================================================

  TABLE         — relational data structure
  INDEX         — performance structure for fast lookups
  VIEW          — named saved query
  SEQUENCE      — auto-increment number generator
  SCHEMA        — namespace for tables and objects
  DATABASE      — top-level container
  STORED PROC   — reusable procedural SQL code
  FUNCTION      — returns a value; can be used in queries
  TRIGGER       — automatic code on INSERT/UPDATE/DELETE
  TYPE          — custom data type (PostgreSQL ENUM, composite type)
  MATERIALIZED VIEW — view with physical data snapshot

================================================================
DDL IN PRODUCTION — MIGRATION TOOLS
================================================================

  Direct DDL in production is risky. Tools manage schema changes:

  Flyway (Java):     V1__create_orders.sql, V2__add_status.sql
  Liquibase (Java):  XML/YAML/SQL changeset format
  Rails Migrations:  Ruby DSL
  Alembic:           Python/SQLAlchemy

  These tools:
  - Version schema changes (tracked in a changelog table)
  - Apply changes in order across environments (dev/test/prod)
  - Allow rollback to previous versions

  Spring Boot + Flyway:
  Place SQL files in src/main/resources/db/migration/
  Spring auto-runs migrations on startup.

================================================================
DDL BEST PRACTICES
================================================================

  1. Always use IF EXISTS / IF NOT EXISTS to prevent errors in scripts.
  2. Add constraints in CREATE (fail early, data integrity from day 1).
  3. Index foreign keys — join performance depends on it.
  4. Use VARCHAR with reasonable length limits.
  5. Prefer TIMESTAMP WITH TIME ZONE (or TIMESTAMPTZ in PostgreSQL).
  6. Use descriptive names: idx_orders_customer_id, not just idx1.
  7. Test DDL on dev/staging before production.
  8. Use migration tools for version control of schema changes.
