================================================================
  CORRELATED SUBQUERIES
================================================================

  A correlated subquery references a column from the outer query.
  It is RE-EVALUATED for each row of the outer query.
  This makes it potentially slow but very expressive.

================================================================
SYNTAX
================================================================

  SELECT col1
  FROM table_a a
  WHERE expression operator (
      SELECT aggregate(col)
      FROM table_b b
      WHERE b.fk = a.pk    -- <-- references outer query alias a
  );

================================================================
EXAMPLE: EMPLOYEES EARNING MORE THAN DEPT AVERAGE
================================================================

  SELECT name, salary, department_id
  FROM employees e
  WHERE salary > (
      SELECT AVG(salary)
      FROM employees
      WHERE department_id = e.department_id   -- references outer e
  );

  For each row in the outer query (each employee e),
  the subquery computes AVG salary for THAT employee's department.

================================================================
EXAMPLE: LATEST ORDER PER CUSTOMER
================================================================

  SELECT *
  FROM orders o
  WHERE created_at = (
      SELECT MAX(created_at)
      FROM orders
      WHERE customer_id = o.customer_id   -- correlated
  );

  Returns one row per customer: their most recent order.

================================================================
EXAMPLE: DELETE DUPLICATES (KEEP LOWEST ID)
================================================================

  DELETE FROM customers
  WHERE id NOT IN (
      SELECT MIN(id)
      FROM customers c2
      WHERE c2.email = customers.email   -- correlated
  );

================================================================
CORRELATED vs NON-CORRELATED
================================================================

  Non-correlated: inner query runs ONCE, result reused for all outer rows.
  Correlated:     inner query runs ONCE PER OUTER ROW.

  Non-correlated (runs once):
  SELECT * FROM products
  WHERE price > (SELECT AVG(price) FROM products);

  Correlated (runs per row):
  SELECT * FROM products p1
  WHERE price > (SELECT AVG(price) FROM products WHERE category = p1.category);

================================================================
PERFORMANCE CONSIDERATIONS
================================================================

  Correlated subqueries on large tables can be very slow:
  - O(n) subquery executions for n outer rows
  - Each execution may do a full scan

  Often rewritable as JOINs for better performance:

  Correlated:
  SELECT e.name, e.salary
  FROM employees e
  WHERE e.salary > (
      SELECT AVG(salary) FROM employees WHERE department_id = e.department_id
  );

  Equivalent JOIN (usually faster):
  SELECT e.name, e.salary
  FROM employees e
  INNER JOIN (
      SELECT department_id, AVG(salary) AS avg_sal
      FROM employees
      GROUP BY department_id
  ) da ON e.department_id = da.department_id
  WHERE e.salary > da.avg_sal;

  Or with window functions (most efficient):
  SELECT name, salary
  FROM (
      SELECT name, salary,
             AVG(salary) OVER (PARTITION BY department_id) AS dept_avg
      FROM employees
  ) sub
  WHERE salary > dept_avg;

================================================================
INTERVIEW Q&A
================================================================

  Q: What makes a subquery correlated?
  A: It references a column from the outer query. The database must
     re-execute the inner query for each row processed by the outer query.

  Q: What is the performance impact of a correlated subquery?
  A: Can be O(n) inner query executions. For large tables, this is slow.
     Often replaceable with a JOIN or window function for better performance.

  Q: How would you rewrite a correlated subquery for performance?
  A: If it computes aggregates per group, use a JOIN with a derived table
     that pre-computes the aggregates. Or use window functions (OVER PARTITION BY).

  Q: When is a correlated subquery acceptable?
  A: When table is small, or when EXISTS is used (short-circuits on first match).
     Complex update/delete operations where rewriting as JOIN is awkward.
