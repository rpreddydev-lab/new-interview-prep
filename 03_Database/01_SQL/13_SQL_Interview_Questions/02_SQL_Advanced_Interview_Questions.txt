Q1. What are window functions? How are they different from GROUP BY?
---------------------------------------------------------------------
Window functions perform calculations across a set of rows RELATED to the current row,
WITHOUT collapsing the rows like GROUP BY does.

GROUP BY: Returns ONE row per group.
Window:   Returns ONE row per original row, with the aggregated value alongside it.

Syntax:
  function_name() OVER (
    PARTITION BY column   -- optional: split into groups
    ORDER BY column       -- optional: define row order within partition
    ROWS/RANGE BETWEEN ... -- optional: define frame
  )

Examples:
  -- Running total
  SELECT name, salary, SUM(salary) OVER (PARTITION BY dept ORDER BY hire_date) AS running_total
  FROM employees;

  -- Rank within department
  SELECT name, dept, salary, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
  FROM employees;

  -- Previous row value
  SELECT name, salary, LAG(salary, 1) OVER (ORDER BY hire_date) AS prev_salary
  FROM employees;

Q2. What is the difference between RANK(), DENSE_RANK(), and ROW_NUMBER()?
---------------------------------------------------------------------------
Given salaries: 90k, 85k, 85k, 80k

ROW_NUMBER():   1, 2, 3, 4       -- Unique sequential numbers, no gaps, no ties
RANK():         1, 2, 2, 4       -- Tied rows get same rank; next rank skips (gap)
DENSE_RANK():   1, 2, 2, 3       -- Tied rows get same rank; NO gap in next rank

Use DENSE_RANK when you need "top N distinct salaries" or "no gaps in ranking".
Use ROW_NUMBER when you need exactly one row per rank (e.g., latest record per group).

Q3. What is a CTE (Common Table Expression)? When would you use it over a subquery?
-------------------------------------------------------------------------------------
A CTE is a named temporary result set defined at the start of a query using WITH.

WITH dept_avg AS (
  SELECT dept, AVG(salary) AS avg_sal FROM employees GROUP BY dept
)
SELECT e.name, e.salary, d.avg_sal
FROM employees e
JOIN dept_avg d ON e.dept = d.dept
WHERE e.salary > d.avg_sal;

Advantages over subqueries:
  - More readable, especially for complex queries
  - Can be referenced MULTIPLE TIMES in the same query (subquery repeats execution)
  - Supports RECURSION (recursive CTEs)

Recursive CTE (traversing hierarchy):
  WITH RECURSIVE org_tree AS (
    SELECT id, name, manager_id FROM employees WHERE manager_id IS NULL  -- anchor
    UNION ALL
    SELECT e.id, e.name, e.manager_id
    FROM employees e
    JOIN org_tree o ON e.manager_id = o.id                               -- recursive
  )
  SELECT * FROM org_tree;

Q4. Explain different isolation levels and what anomalies each prevents.
-------------------------------------------------------------------------
| Isolation Level    | Dirty Read | Non-Repeatable Read | Phantom Read |
|--------------------|------------|---------------------|--------------|
| READ UNCOMMITTED   | Possible   | Possible            | Possible     |
| READ COMMITTED     | Prevented  | Possible            | Possible     |
| REPEATABLE READ    | Prevented  | Prevented           | Possible     |
| SERIALIZABLE       | Prevented  | Prevented           | Prevented    |

Anomaly Definitions:
  Dirty Read:           Reading uncommitted data from another transaction
  Non-Repeatable Read:  Same row read twice gives different values (another TX committed)
  Phantom Read:         New rows appear in same query range (another TX inserted + committed)

Real-world defaults:
  PostgreSQL: READ COMMITTED (default)
  MySQL InnoDB: REPEATABLE READ (default, also prevents phantoms via gap locks)
  Oracle: READ COMMITTED (default)

In Spring: @Transactional(isolation = Isolation.SERIALIZABLE)

Q5. What is a deadlock? How do you detect and prevent it?
----------------------------------------------------------
A deadlock occurs when two or more transactions are waiting for each other to release locks.

TX1: Locks row A, waits for row B
TX2: Locks row B, waits for row A → Deadlock!

Detection: Databases automatically detect deadlocks via wait-for graphs and kill one TX.

Prevention strategies:
  1. Always access tables/rows in the same ORDER across transactions
  2. Keep transactions SHORT — acquire locks as late as possible, release early
  3. Use lower isolation levels where appropriate
  4. Use SELECT ... FOR UPDATE NOWAIT or SKIP LOCKED (PostgreSQL/Oracle) to avoid waiting
  5. Use optimistic locking to reduce lock contention

In Java/Spring: Handle DeadlockLoserDataAccessException with retry logic.

Q6. What is the difference between EXISTS and IN?
-------------------------------------------------
IN: Evaluates subquery result into a list, then checks membership.
    SELECT * FROM orders WHERE customer_id IN (SELECT id FROM customers WHERE country='US');
    - Bad performance with large subquery result sets
    - NULL in subquery list → unexpected behavior (IN NULL = UNKNOWN, not FALSE)

EXISTS: Checks if subquery returns at least one row. Short-circuits on first match.
    SELECT * FROM orders o WHERE EXISTS (SELECT 1 FROM customers c WHERE c.id = o.customer_id AND c.country='US');
    - Generally faster for large subqueries
    - Handles NULLs safely
    - Use when checking existence only

Rule of thumb:
  - EXISTS is usually faster when subquery result is large
  - IN is fine for small, fixed lists
  - NOT EXISTS is preferred over NOT IN (NULL-safety)

Q7. How do you find duplicate rows? How do you delete them while keeping one?
------------------------------------------------------------------------------
Find duplicates:
  SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

Delete duplicates, keep the one with the lowest ID:
  DELETE FROM users
  WHERE id NOT IN (
    SELECT MIN(id) FROM users GROUP BY email
  );

Alternative using CTE (PostgreSQL):
  WITH dupes AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM users
  )
  DELETE FROM users WHERE id IN (SELECT id FROM dupes WHERE rn > 1);

Q8. What is the N+1 query problem in SQL context?
-------------------------------------------------
N+1 occurs when you load N parent records and then execute 1 query per parent to get children.

Result: 1 query for parents + N queries for children = N+1 total queries.

Example (ORM scenario):
  List<Department> depts = deptRepo.findAll();   // 1 query
  for (Department d : depts) {
    d.getEmployees().size();  // 1 query per dept → N queries!
  }

SQL-level fix: Use a JOIN to fetch everything in ONE query:
  SELECT d.*, e.* FROM departments d LEFT JOIN employees e ON e.dept_id = d.id;

ORM fix (JPA): Use JOIN FETCH or @EntityGraph.

Q9. How would you get the Nth highest salary?
---------------------------------------------
-- Using DENSE_RANK (handles ties correctly):
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = N;

-- Using LIMIT/OFFSET (simpler but ignores ties):
SELECT DISTINCT salary FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET N-1;

-- Using correlated subquery:
SELECT salary FROM employees e1
WHERE N-1 = (SELECT COUNT(DISTINCT salary) FROM employees e2 WHERE e2.salary > e1.salary);

Q10. Explain partitioning in databases. When would you use it?
---------------------------------------------------------------
Table partitioning splits a large table into smaller pieces (partitions) while
appearing as a single table to the application.

Types:
  Range Partitioning: By value ranges (e.g., date ranges — one partition per year)
  List Partitioning:  By specific values (e.g., country = 'US', 'UK', 'IN')
  Hash Partitioning:  By hash of a column — evenly distributes data
  Composite:          Combination (e.g., range + hash)

Benefits:
  - Query performance: Queries on partition key prune irrelevant partitions
  - Maintenance: Drop old data quickly (DROP PARTITION vs DELETE)
  - Parallel processing: Each partition can be processed independently

When to use: Tables with 100M+ rows, time-series data, archival needs.

PostgreSQL example:
  CREATE TABLE orders (id BIGINT, order_date DATE, amount DECIMAL)
  PARTITION BY RANGE (order_date);

  CREATE TABLE orders_2024 PARTITION OF orders FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

Q11. What is EXPLAIN / EXPLAIN ANALYZE? How do you interpret it?
-----------------------------------------------------------------
EXPLAIN shows the QUERY PLAN the database will use without executing the query.
EXPLAIN ANALYZE actually runs the query and shows actual vs estimated costs.

Key things to look for:
  Seq Scan:    Full table scan — index may be missing or not used
  Index Scan:  Uses an index — efficient
  Index Only Scan: Only reads index, doesn't touch table — most efficient
  Hash Join / Nested Loop / Merge Join: Join strategies
  Rows:        Estimated vs actual row count (large differences = stale statistics)
  Cost:        Relative cost (startup cost..total cost) — not milliseconds
  Actual Time: In EXPLAIN ANALYZE — real execution time in ms

Bad sign: Large difference between "estimated" and "actual" rows → run ANALYZE to update stats.

Q12. What are materialized views? When to use them vs regular views?
---------------------------------------------------------------------
Materialized View: Stores the query RESULT physically on disk.

vs Regular View:
  Regular View:        Virtual — query re-executed each time view is accessed
  Materialized View:   Physical — data stored, fast reads, requires explicit REFRESH

When to use Materialized Views:
  - Complex aggregation queries (dashboards, reports) run frequently
  - Underlying data doesn't change too often
  - Read performance is critical

Refresh strategies:
  REFRESH MATERIALIZED VIEW view_name;            -- Full refresh (locks)
  REFRESH MATERIALIZED VIEW CONCURRENTLY view_name; -- PostgreSQL: no lock, requires unique index

Trade-off: Staleness vs performance. Balance refresh frequency with data freshness requirements.

Q13. What is the difference between CHAR, VARCHAR, and TEXT?
------------------------------------------------------------
CHAR(n):    Fixed-length. Always uses n bytes. Padded with spaces. Good for codes (e.g., 'US', 'UK').
VARCHAR(n): Variable-length. Max n characters. Efficient for variable data.
TEXT:       No length limit. Stored out-of-line if large. No index on full column (use partial).

For Java developers:
  - Map Java String to VARCHAR or TEXT
  - CHAR rarely needed in modern apps
  - Use VARCHAR with a sensible limit for indexed columns

Q14. How do you handle pagination in SQL?
-----------------------------------------
OFFSET-based pagination (simple but has problems):
  SELECT * FROM products ORDER BY id LIMIT 20 OFFSET 200;

  Problems:
  - Slow on large offsets (DB scans and discards 200 rows)
  - Inconsistency: if rows are inserted/deleted between pages, rows can be missed or duplicated

Keyset (Cursor-based) pagination (recommended for large datasets):
  -- Page 1:
  SELECT * FROM products ORDER BY id LIMIT 20;

  -- Next page: use last ID from previous page
  SELECT * FROM products WHERE id > :lastId ORDER BY id LIMIT 20;

  Advantages: O(log n) via index, consistent regardless of concurrent changes.
  Limitation: Can't jump to arbitrary page numbers.

For Java: Spring Data's Slice<T> works well for cursor-based patterns.
          Page<T> uses OFFSET — fine for small datasets.

Q15. Write a query to find employees who earn more than the average salary in their department.
-----------------------------------------------------------------------------------------------
-- Using correlated subquery:
SELECT e.name, e.dept, e.salary
FROM employees e
WHERE e.salary > (
  SELECT AVG(salary) FROM employees WHERE dept = e.dept
);

-- Using window function (more efficient, single scan):
SELECT name, dept, salary
FROM (
  SELECT name, dept, salary,
         AVG(salary) OVER (PARTITION BY dept) AS dept_avg
  FROM employees
) t
WHERE salary > dept_avg;
