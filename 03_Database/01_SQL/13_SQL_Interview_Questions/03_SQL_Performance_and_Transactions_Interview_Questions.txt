SQL PERFORMANCE & TRANSACTIONS — INTERVIEW QUESTIONS & ANSWERS
(For Java Developers with 7+ Years Experience)
===========================================================================================================

Q1. What is a covering index? How does it eliminate table lookups?
------------------------------------------------------------------
A covering index is one that contains ALL columns required by a query —
the query engine never needs to visit the actual table rows.

Example:
  Query: SELECT name, email FROM users WHERE dept = 'Engineering';
  
  Normal index on dept: DB uses index to find row IDs, then fetches name + email from table.
  Covering index on (dept, name, email): DB satisfies query entirely from index — no table lookup.

  CREATE INDEX idx_covering ON users (dept, name, email);

In EXPLAIN: Shows "Index Only Scan" — the most efficient scan type.

Java/JPA note: Often needs careful tuning with @Index annotations + custom queries.

Q2. When does MySQL / PostgreSQL NOT use an index?
---------------------------------------------------
The query optimizer skips an index when:

  1. Function applied to indexed column:
       WHERE LOWER(email) = 'ray@test.com'  -- use functional index or store lowercase
  
  2. Type mismatch:
       WHERE user_id = '123'  -- user_id is INT, '123' is VARCHAR → implicit cast, no index
  
  3. LIKE with leading wildcard:
       WHERE name LIKE '%ray%'  -- can't use B-Tree index (use full-text index instead)
       WHERE name LIKE 'ray%'   -- CAN use index
  
  4. Low cardinality: Boolean columns, status flags (few distinct values)
  
  5. Small table: Full scan cheaper than index lookup
  
  6. OR conditions on different columns (unless separate indexes exist + index merge)
  
  7. Negation: WHERE status != 'ACTIVE' — optimizer may prefer full scan

Q3. Explain B-Tree index internals. Why are they the default?
-------------------------------------------------------------
B-Tree (Balanced Tree) is the default index type in PostgreSQL, MySQL, SQL Server, Oracle.

Structure:
  - Root node → Branch nodes → Leaf nodes (actual data pointers)
  - Always balanced (same depth from root to all leaves)
  - Leaf nodes are doubly linked (enables range scans)

Why B-Tree:
  - Supports: =, <, >, <=, >=, BETWEEN, ORDER BY, IN (list)
  - O(log n) lookup time
  - Range scans are efficient (follow linked leaf nodes)
  - Works well for high cardinality columns

When to use Hash index instead:
  - Only equality comparisons (= operator)
  - Slightly faster for exact matches (O(1))
  - Doesn't support range queries or ordering

Q4. What is a dirty read, phantom read, and non-repeatable read? Give concrete examples.
----------------------------------------------------------------------------------------
DIRTY READ: Reading uncommitted data from another transaction.
  TX1: UPDATE salary SET amount = 90000 WHERE id = 1; (not committed)
  TX2: SELECT amount FROM salary WHERE id = 1; → reads 90000 (dirty!)
  TX1: ROLLBACK; → TX2 read data that never existed officially

NON-REPEATABLE READ: Same row returns different data when read twice in same transaction.
  TX1: SELECT salary FROM employees WHERE id = 1; → 80000
  TX2: UPDATE employees SET salary = 90000 WHERE id = 1; COMMIT;
  TX1: SELECT salary FROM employees WHERE id = 1; → 90000 (changed!)

PHANTOM READ: New rows appear in same query range between two reads.
  TX1: SELECT COUNT(*) FROM orders WHERE date = '2024-01-01'; → 100
  TX2: INSERT INTO orders (date) VALUES ('2024-01-01'); COMMIT;
  TX1: SELECT COUNT(*) FROM orders WHERE date = '2024-01-01'; → 101 (phantom!)

Fix: Use SERIALIZABLE isolation, or gap locks (MySQL InnoDB REPEATABLE READ uses gap locks
to prevent phantoms even at that level).

Q5. What is MVCC (Multi-Version Concurrency Control)?
------------------------------------------------------
MVCC allows concurrent reads and writes without traditional read locks,
by maintaining MULTIPLE VERSIONS of data rows.

How it works (PostgreSQL):
  - Every row has xmin (transaction that created it) and xmax (transaction that deleted/updated it)
  - Each transaction sees a SNAPSHOT of data as of its start time
  - Writers create new versions; readers see old versions
  - Old versions are cleaned up by VACUUM

Benefits:
  - Readers don't block writers
  - Writers don't block readers
  - High concurrency without sacrificing consistency

Trade-off:
  - Storage overhead (multiple versions)
  - VACUUM process needed (PostgreSQL) to reclaim dead tuples
  - Long-running transactions prevent VACUUM from cleaning up → table bloat

MySQL InnoDB also uses MVCC via the undo log.

Q6. How do you handle long-running transactions in production?
--------------------------------------------------------------
Problems with long transactions:
  - Hold locks for extended periods → blocking other operations
  - Prevent VACUUM (PostgreSQL) → table bloat
  - Risk of deadlocks

Strategies:
  1. Keep transactions as SHORT as possible
  2. Do NOT perform external I/O (HTTP calls, file reads) inside a transaction
  3. Use READ ONLY transactions where possible (no locks needed in MVCC databases)
  4. Use batching: process in chunks instead of one massive transaction
  5. Monitor: pg_stat_activity (PostgreSQL), SHOW PROCESSLIST (MySQL)
  6. Set statement_timeout (PostgreSQL) or wait_timeout (MySQL)
  7. Use optimistic locking to avoid holding locks during business processing

Java/Spring:
  - Never put @Transactional on top of a method that does external HTTP calls
  - Use @Transactional(timeout = 30) to set a timeout
  - Prefer @Transactional(readOnly = true) for read operations

Q7. Explain SAVEPOINT. When is it useful?
------------------------------------------
SAVEPOINT creates a rollback point WITHIN a transaction.
You can roll back to a savepoint without rolling back the entire transaction.

  BEGIN;
  INSERT INTO orders (id, amount) VALUES (1, 100);
  SAVEPOINT sp1;
  INSERT INTO order_items (order_id, product) VALUES (1, 'Widget');
  -- Something goes wrong with items
  ROLLBACK TO SAVEPOINT sp1;  -- Undo items but keep order
  INSERT INTO order_items (order_id, product) VALUES (1, 'Gadget');
  COMMIT;

Use cases:
  - Processing batch records: skip failed records without losing all work
  - Nested transaction-like semantics in a single DB transaction

In Spring/JPA:
  Nested transactions using Propagation.NESTED create a savepoint internally.
  If inner method fails → rolls back to savepoint, outer transaction can continue.

Q8. What is connection pooling and why is it important?
--------------------------------------------------------
Database connection creation is expensive (TCP handshake, authentication, session setup).
Connection pooling maintains a POOL of reusable connections.

Without pooling: New connection per request → ~50-100ms overhead per request.
With pooling:    Connections reused → sub-millisecond checkout.

HikariCP (default in Spring Boot):
  Key properties:
    maximumPoolSize:     Max connections in pool (default 10). Size based on workload.
    minimumIdle:         Minimum idle connections kept alive.
    connectionTimeout:   How long to wait for a connection (default 30s).
    idleTimeout:         How long idle connections stay in pool (default 10 min).
    maxLifetime:         Max lifetime of a connection (default 30 min — prevents stale connections).

Optimal pool size formula (for CPU-bound workloads):
  pool_size = (number of CPU cores * 2) + effective_spindle_count

  e.g., 8-core machine → ~17 connections max. Bigger isn't always better!

Q9. What are the ACID properties and how does your database enforce them?
-------------------------------------------------------------------------
ACID = Atomicity, Consistency, Isolation, Durability

ATOMICITY: All operations in a transaction succeed or ALL fail.
  Enforced by: Undo log (MySQL), WAL/rollback segments (PostgreSQL, Oracle).

CONSISTENCY: DB moves from one valid state to another. Constraints always satisfied.
  Enforced by: Constraints (PK, FK, CHECK, UNIQUE), triggers, application logic.

ISOLATION: Concurrent transactions don't interfere with each other.
  Enforced by: Locking (pessimistic), MVCC (optimistic), isolation level settings.

DURABILITY: Committed data persists even through crashes.
  Enforced by: WAL (Write-Ahead Log) — changes written to log before being applied to data files.
              fsync ensures log is flushed to disk.

Q10. What is a SQL injection attack? How do you prevent it in Java?
--------------------------------------------------------------------
SQL Injection: Attacker injects malicious SQL through user input.
  Vulnerable code:
    String query = "SELECT * FROM users WHERE name = '" + userInput + "'";
    // Input: ' OR '1'='1 → returns all users!
    // Input: '; DROP TABLE users;-- → destroys table!

Prevention in Java:

  1. PreparedStatement (JDBC):
       PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
       ps.setString(1, userInput);  // Input treated as data, not SQL

  2. JPA/JPQL with parameters:
       @Query("SELECT u FROM User u WHERE u.name = :name")
       List<User> findByName(@Param("name") String name);

  3. Named parameters (never string concatenation in JPQL)

  4. Input validation: Whitelist allowed characters, validate lengths

  5. Stored procedures (inputs are parameterized)

  6. Least privilege: DB user should only have SELECT/INSERT/UPDATE on needed tables

Never use string concatenation to build SQL queries!

Q11. How would you design a database schema for a multi-tenant SaaS application?
----------------------------------------------------------------------------------
Three patterns:

Pattern 1: Shared Database, Shared Schema (single tenant_id column)
  - Add tenant_id to every table
  - All tenants share same tables
  PRO: Cost-efficient, easy to add tenants
  CON: Data isolation risk, complex queries, one bad query affects all tenants

Pattern 2: Shared Database, Separate Schemas
  - One schema per tenant (schema per tenant with same table structure)
  - Connect to right schema based on tenant context
  PRO: Better isolation, easy to backup per tenant
  CON: Schema migrations needed for all schemas, more complex connection management

Pattern 3: Separate Databases per Tenant
  - Each tenant has their own database
  PRO: Complete isolation, independent scaling and backup
  CON: Expensive, connection pool management complex (1000 tenants = 1000 DBs)

Spring Boot: Use AbstractRoutingDataSource to dynamically select datasource by tenant context.

Recommended for most cases: Pattern 1 (shared schema) with proper row-level security
and careful query filtering. Add database-level RLS for additional security.

Q12. What is database replication? Explain primary-replica setup.
------------------------------------------------------------------
Replication: Process of copying data from one database (primary/master) to
             one or more replicas (secondaries/slaves).

Types:
  Synchronous: Primary waits for replica to confirm write before committing.
               Ensures zero data loss but higher write latency.

  Asynchronous: Primary commits immediately, replica catches up later.
                Lower write latency but risk of data loss on primary failure.

Primary-Replica (Master-Slave) architecture:
  - All WRITES go to primary
  - All READS can be distributed to replicas
  - Replicas serve as hot standbys for failover

Replication Lag: Time for replica to catch up to primary.
  Problem: Reads from replica may see stale data.
  Solution: Read-your-writes consistency — after a write, route to primary for a short time.

In Spring Boot:
  Use AbstractRoutingDataSource with a TransactionSynchronizationManager
  to route read-only transactions to replica.
