================================================================
  CLUSTERED VS NON-CLUSTERED INDEX
================================================================

================================================================
CLUSTERED INDEX
================================================================

  The data rows are PHYSICALLY STORED in the order of the index.
  There can be only ONE clustered index per table (it IS the table).

  SQL Server: Primary Key automatically creates a clustered index.
  MySQL InnoDB: Primary Key IS the clustered index (IOT = Index Organized Table).
  PostgreSQL: No traditional clustered index. CLUSTER command reorders
              heap data once, but does not maintain order on new inserts.

================================================================
MYSQL INNODB CLUSTERED INDEX (PRIMARY KEY)
================================================================

  InnoDB stores rows in a B-tree indexed by the PK.
  PK lookup: single B-tree traversal --> reach data directly.

  Row: [PK | other columns] stored together in leaf nodes.

  Implications:
  - PK lookups are fastest (no second hop)
  - PK should be a narrow, monotonically increasing integer/UUID
    (large random UUIDs cause page splits, fragmentation)
  - Secondary indexes include PK value, not row pointer
    Secondary index lookup = two B-tree lookups (secondary + clustered)

================================================================
NON-CLUSTERED INDEX (SECONDARY INDEX)
================================================================

  A separate data structure that stores index key + pointer to the actual row.
  Multiple non-clustered indexes per table allowed.

  B-tree stores: [indexed_col_value | row_pointer (heap TID)]
  Lookup: find in index --> follow pointer to heap --> read row.
  Extra hop = "heap fetch" or "bookmark lookup."

================================================================
POSTGRESQL HEAP TABLE + SECONDARY INDEX
================================================================

  PostgreSQL uses a heap (unordered) table with secondary indexes.
  All indexes are "secondary" in PostgreSQL terminology.
  Each index entry = (key_value, CTID) where CTID is (page, offset).

  CLUSTER command:
  CLUSTER employees USING idx_employees_dept;
  -- Rewrites table in index order. Not maintained; degrades over time.

================================================================
COMPARISON TABLE
================================================================

  Feature              Clustered (MySQL PK)   Non-Clustered (Secondary)
  ------------------   --------------------   -------------------------
  Row storage          In index leaves        Separate heap
  Lookup hops          1 (data in leaf)       2 (index + heap fetch)
  # per table          1                      Many
  Insert cost          Ordered insert (fast   Additional structure
                       for sequential IDs,    to maintain
                       slow for random UUIDs)
  Best use             PK range queries       Equality/range on other cols
  Coverage             Can be covering        Can be covering (see next file)

================================================================
HEAP FETCH AND INDEX-ONLY SCAN
================================================================

  Heap fetch: secondary index lookup + follow pointer to heap.
  Expensive when many rows returned (random I/O).

  Index-only scan: if ALL needed columns are IN the index,
  database skips heap fetch entirely.
  PostgreSQL requires Visibility Map bit set to allow index-only scan.

  SELECT id, status FROM orders WHERE customer_id = 42;
  -- If index is on (customer_id, status, id):
  -- ALL columns (customer_id, status, id) are in the index
  -- Index-only scan: no heap fetch needed

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a clustered index?
  A: An index that defines the physical storage order of rows.
     Only one per table. In MySQL InnoDB, the PK is the clustered index.
     In SQL Server, PK creates clustered index by default.

  Q: Why should InnoDB primary keys be sequential integers?
  A: InnoDB PK is the clustered index. Sequential inserts (1,2,3...)
     append to the rightmost leaf, no page splits.
     Random UUIDs insert at random positions, causing page splits,
     fragmentation, and slower performance.

  Q: What is the extra "hop" in non-clustered index lookup?
  A: The index stores the indexed key + a pointer to the actual row.
     Finding the index entry is step 1; following the pointer to the
     heap to retrieve all columns is step 2. Covering indexes avoid step 2.
