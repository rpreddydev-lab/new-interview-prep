================================================================
  QUERY OPTIMIZATION TIPS
================================================================

================================================================
1. SELECT ONLY NEEDED COLUMNS (AVOID SELECT *)
================================================================

  Bad:  SELECT * FROM orders;
  Good: SELECT id, status, total FROM orders;

  Why: less data transferred, enables index-only scans,
  prevents surprises when table schema changes.

================================================================
2. INDEX THE RIGHT COLUMNS
================================================================

  Always index:
  - Primary key (automatic)
  - Foreign key columns (for JOIN performance and cascading deletes)
  - Columns in WHERE, ORDER BY, JOIN ON conditions
  - Composite index columns ordered by: equality first, range second

  Avoid indexing:
  - Low-cardinality columns with uniform distribution (e.g., boolean active=true 80% of rows)
  - Rarely queried columns
  - Tables with heavy writes and light reads

================================================================
3. AVOID FUNCTIONS ON INDEXED COLUMNS IN WHERE
================================================================

  Bad:  WHERE YEAR(created_at) = 2024     -- function disables index
  Good: WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

  Bad:  WHERE LOWER(email) = 'alice@example.com'
  Good: CREATE INDEX ON users(LOWER(email)); then WHERE LOWER(email) = ...

================================================================
4. USE SARGABLE PREDICATES
================================================================

  SARG = Search ARGument. A predicate that can use an index.
  Non-sargable examples:
  WHERE SUBSTR(code, 1, 3) = 'ABC'    --> scan
  WHERE age + 1 = 25                  --> scan
  WHERE NOT status = 'PENDING'        --> often scan (use positive form)

  Sargable:
  WHERE code LIKE 'ABC%'              --> index on code
  WHERE age = 24                      --> index on age
  WHERE status IN ('CONFIRMED', 'SHIPPED')  --> index on status

================================================================
5. FILTER EARLY WITH WHERE
================================================================

  Filter before joining to reduce row count fed into join:
  SELECT c.name, o.total
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  WHERE o.total > 500;   -- applied after join

  Better (optimizer usually handles this, but explicit is clearer):
  SELECT c.name, o.total
  FROM customers c
  JOIN (SELECT customer_id, total FROM orders WHERE total > 500) o
      ON o.customer_id = c.id;

================================================================
6. LIMIT RESULTS WHEN ONLY PARTIAL DATA NEEDED
================================================================

  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
  -- No need to sort all rows; optimizer may stop early

================================================================
7. AVOID CORRELATED SUBQUERIES ON LARGE TABLES
================================================================

  Replace with JOIN or window function (see Correlated Subqueries file).

================================================================
8. USE CTEs FOR CLARITY BUT UNDERSTAND MATERIALIZATION
================================================================

  In PostgreSQL < 12: CTEs are always materialized (optimized separately).
  In PostgreSQL 12+: CTEs are inlined by default (can be optimized together).

  Force materialization when CTE is expensive and reused:
  WITH MATERIALIZED ranked AS (...)

================================================================
9. UPDATE/DELETE IN BATCHES
================================================================

  Deleting 10M rows in one statement can block other transactions
  and fill up WAL / undo logs.

  DO $$
  LOOP
      DELETE FROM archive_logs WHERE created_at < NOW() - INTERVAL '1 year'
      LIMIT 1000;
      EXIT WHEN NOT FOUND;
      PERFORM pg_sleep(0.05);  -- short pause between batches
  END LOOP;
  $$;

================================================================
10. STATISTICS AND ANALYZE
================================================================

  Planner decisions depend on statistics about table data distribution.
  After large data changes, run:
  ANALYZE orders;           -- update statistics
  VACUUM ANALYZE orders;    -- reclaim space + update statistics

  Auto-analyze handles this automatically but may lag behind
  during bulk loads.

================================================================
11. CONNECTION POOLING (APPLICATION LEVEL)
================================================================

  Opening a new DB connection is expensive (5-20ms + memory).
  Use connection pool: HikariCP (Spring Boot default), PgBouncer.
  Ideal pool size ≈ (num_cores * 2 + effective_spindle_count).

================================================================
INTERVIEW Q&A
================================================================

  Q: What are the most common SQL performance mistakes?
  A: 1. SELECT * instead of specific columns
     2. Missing indexes on FK / WHERE / ORDER BY columns
     3. Functions applied to indexed columns in WHERE (non-sargable)
     4. Correlated subqueries on large tables (use JOIN/window fn)
     5. Missing LIMIT on queries returning millions of rows
     6. Stale statistics (run ANALYZE after bulk loads)

  Q: What is a sargable predicate?
  A: A condition that can use an index (Search ARGument able).
     Equality (=), range (<, >, BETWEEN), prefix LIKE ('abc%') are sargable.
     Functions on columns (YEAR(date), LOWER(col)), negation (NOT IN large set),
     and LIKE '%suffix' are not sargable.
