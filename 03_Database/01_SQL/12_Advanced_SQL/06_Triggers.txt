================================================================
  TRIGGERS
================================================================

  A trigger is a function automatically called when a specified
  event (INSERT, UPDATE, DELETE) occurs on a table.

================================================================
TRIGGER TYPES
================================================================

  Timing        BEFORE -- fires before the DML completes; can modify NEW
                AFTER  -- fires after DML; cannot change NEW; typical for audit
                INSTEAD OF -- fires instead of DML on a view

  Level         ROW-LEVEL   -- once per affected row (FOR EACH ROW)
                STMT-LEVEL  -- once per DML statement (FOR EACH STATEMENT)

================================================================
POSTGRESQL TRIGGER STRUCTURE
================================================================

  Step 1: Create the trigger function (returns TRIGGER type)
  Step 2: Create the trigger that calls the function

  -- Step 1: trigger function
  CREATE OR REPLACE FUNCTION log_order_changes()
  RETURNS TRIGGER
  LANGUAGE plpgsql
  AS $$
  BEGIN
      IF TG_OP = 'INSERT' THEN
          INSERT INTO audit_log (table_name, operation, new_data, changed_at)
          VALUES ('orders', 'INSERT', row_to_json(NEW), NOW());

      ELSIF TG_OP = 'UPDATE' THEN
          INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_at)
          VALUES ('orders', 'UPDATE', row_to_json(OLD), row_to_json(NEW), NOW());

      ELSIF TG_OP = 'DELETE' THEN
          INSERT INTO audit_log (table_name, operation, old_data, changed_at)
          VALUES ('orders', 'DELETE', row_to_json(OLD), NOW());
      END IF;
      RETURN NEW;
  END;
  $$;

  -- Step 2: attach the trigger
  CREATE TRIGGER orders_audit_trigger
  AFTER INSERT OR UPDATE OR DELETE ON orders
  FOR EACH ROW
  EXECUTE FUNCTION log_order_changes();

================================================================
SPECIAL VARIABLES IN TRIGGER FUNCTION
================================================================

  NEW        -- the new row (INSERT or UPDATE); NULL for DELETE
  OLD        -- the old row (DELETE or UPDATE); NULL for INSERT
  TG_OP      -- 'INSERT', 'UPDATE', 'DELETE', or 'TRUNCATE'
  TG_TABLE_NAME -- name of the table that fired the trigger

================================================================
BEFORE TRIGGER -- MODIFY DATA
================================================================

  BEFORE triggers can modify NEW to change what gets inserted/updated.

  CREATE OR REPLACE FUNCTION normalize_email()
  RETURNS TRIGGER
  LANGUAGE plpgsql
  AS $$
  BEGIN
      NEW.email := LOWER(TRIM(NEW.email));
      RETURN NEW;  -- must RETURN NEW (or NULL to cancel)
  END;
  $$;

  CREATE TRIGGER normalize_email_trigger
  BEFORE INSERT OR UPDATE ON customers
  FOR EACH ROW
  EXECUTE FUNCTION normalize_email();

  -- RETURN NULL cancels the DML (the row is not inserted/updated)

================================================================
INSTEAD OF TRIGGER (ON VIEWS)
================================================================

  Allow INSERT/UPDATE/DELETE on non-updatable views.

  CREATE TRIGGER order_view_insert
  INSTEAD OF INSERT ON order_summary_view
  FOR EACH ROW
  EXECUTE FUNCTION handle_order_view_insert();

================================================================
CONDITIONAL TRIGGER (WHEN CLAUSE)
================================================================

  CREATE TRIGGER price_change_trigger
  AFTER UPDATE OF price ON products
  FOR EACH ROW
  WHEN (OLD.price <> NEW.price)
  EXECUTE FUNCTION log_price_change();

  -- Only fires when price actually changes

================================================================
DROPPING TRIGGERS
================================================================

  DROP TRIGGER orders_audit_trigger ON orders;
  DROP TRIGGER IF EXISTS orders_audit_trigger ON orders;

================================================================
TRIGGER CAUTIONS
================================================================

  1. Hidden side effects: triggers fire implicitly; hard to trace
  2. Performance: each row-level trigger adds overhead; watch on bulk inserts
  3. Ordering: triggers fire in alphabetical name order by default (PostgreSQL)
  4. Cascading: triggers can call functions that cause more triggers
  5. Debugging difficulty: not visible in application code
  6. Prefer application-layer auditing (Hibernate Envers, Spring AOP)
     for better testability and visibility

================================================================
INTERVIEW Q&A
================================================================

  Q: What is a trigger and when would you use one?
  A: A trigger is an automatic function that runs on INSERT/UPDATE/DELETE.
     Use cases: audit logging, enforcing complex business rules that
     CHECK constraints can't handle, keeping derived/denormalized data in sync.

  Q: What is the difference between BEFORE and AFTER triggers?
  A: BEFORE: fires before DML completes, can modify NEW or cancel DML (RETURN NULL).
     AFTER: fires after DML, used for audit logging or propagating changes.

  Q: What is the difference between row-level and statement-level triggers?
  A: Row-level (FOR EACH ROW): fires once per affected row. Has access to OLD/NEW.
     Statement-level (FOR EACH STATEMENT): fires once per DML statement.
     Has no OLD/NEW row access. Useful for logging bulk operations.

  Q: What are the risks of using triggers?
  A: Hidden behavior (not visible in application code), performance overhead,
     potential for cascading trigger chains, hard to test and debug.
     Often better to implement business logic in the application layer.
