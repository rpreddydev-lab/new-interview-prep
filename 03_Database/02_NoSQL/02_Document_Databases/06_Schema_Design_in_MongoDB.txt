================================================================
  SCHEMA DESIGN IN MONGODB
================================================================

================================================================
DESIGN PHILOSOPHY
================================================================

  In SQL: Design for the data model (normalize).
  In MongoDB: Design for the access pattern (how you query).

  Key question: "How will my application access this data?"

================================================================
EMBEDDING vs REFERENCING
================================================================

  Embedding (Denormalized -- nested document):
  Store related data inside the parent document.

  {
      "_id": "ORD001",
      "customer": {
          "name": "Alice",
          "email": "alice@example.com"
      },
      "items": [
          { "product_id": "P1", "name": "Laptop", "price": 999.99, "qty": 1 },
          { "product_id": "P2", "name": "Mouse",  "price": 29.99,  "qty": 2 }
      ],
      "total": 1059.97
  }

  When to embed:
  - Data is always accessed together (order with its items)
  - Child is owned by parent (order items belong to one order)
  - Array is small and bounded
  - Prefer single-document atomicity

  Referencing (Normalized -- FK-like):
  Store only the ID; look up in another collection.

  {
      "_id": "ORD001",
      "customer_id": "C001",
      "item_ids": ["ITEM001", "ITEM002"]
  }

  When to reference:
  - Data is accessed independently (product catalog)
  - Array could grow unbounded (user's post history)
  - Data is shared across many parents (product referenced by many orders)
  - Document size would exceed 16MB BSON limit

================================================================
16MB DOCUMENT SIZE LIMIT
================================================================

  MongoDB documents are limited to 16MB (BSON limit).
  If an embedded array could grow large (e.g., user activity logs),
  use referencing or a separate time-bucketed collection.

================================================================
ANTI-PATTERNS
================================================================

  1. Massive Arrays (unbounded growth):
     { user_id: "U1", posts: [ ...100,000 posts ] }
     PROBLEM: document grows forever, slow updates.
     FIX: store posts in a separate collection with user_id FK.

  2. Unnecessary Normalization:
     Splitting tightly coupled data (order + items) into two collections
     and doing $lookup every time.
     FIX: embed items inside the order document.

  3. Bloated Documents:
     Storing large blobs or logs inside documents.
     FIX: Use GridFS for files > 16MB; separate collections for logs.

  4. Overusing $lookup:
     Frequent joins in MongoDB are expensive (not storage-optimized).
     FIX: Denormalize frequently-joined data.

================================================================
SCHEMA DESIGN PATTERNS
================================================================

  Pattern               Description
  --------------------  -----------------------------------------------
  Embedded              Embed related data (order + items)
  Referenced (FK)       Store IDs, lookup in separate collection
  Bucket                Group time-series events into hourly buckets
  Outlier               Handle occasional huge documents separately
  Computed              Pre-compute expensive aggregations, store result
  Polymorphic           Same collection, different document shapes
  Attribute             Flexible key-value pairs via array of {k,v} docs
  Schema Versioning     Add schemaVersion field; handle in app logic

================================================================
POLYMORPHIC PATTERN
================================================================

  All shapes of a resource in one collection:

  // Vehicle collection -- different types
  { type: "car",   make: "Toyota", doors: 4, fuel: "gasoline" }
  { type: "bike",  make: "Trek",   gears: 21 }
  { type: "truck", make: "Ford",   payload_tons: 3 }

  Good for: polymorphic catalog items, product variants.

================================================================
BUCKET PATTERN (TIME SERIES)
================================================================

  Instead of one document per sensor reading (millions of docs):
  Group readings into hourly buckets:

  {
      sensor_id: "TEMP-01",
      date: ISODate("2024-01-15T10:00:00Z"),
      readings: [
          { time: "10:00:01", value: 72.3 },
          { time: "10:00:02", value: 72.5 },
          ...  // up to ~200 readings per bucket
      ],
      count: 200,
      min: 71.8,
      max: 73.1,
      avg: 72.4
  }

  Benefits: fewer documents, pre-aggregated stats, better index efficiency.

================================================================
INTERVIEW Q&A
================================================================

  Q: How do you decide whether to embed or reference in MongoDB?
  A: Embed when data is always accessed together, owned by the parent,
     and the array is bounded in size. Reference when data is shared,
     independently accessed, or could grow without bound.

  Q: What is the 16MB BSON limit and when does it matter?
  A: MongoDB documents cannot exceed 16MB.
     For unbounded arrays (social feed, activity log), use separate collections
     with referencing to avoid hitting this limit.

  Q: What is the Bucket pattern?
  A: Group time-series data into time-based buckets (hourly/daily) per document.
     Reduces document count, enables pre-aggregated metrics per bucket,
     and improves query and index performance for time-range queries.
