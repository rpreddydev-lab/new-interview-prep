================================================================
  DENORMALIZATION IN NOSQL
================================================================

================================================================
WHAT IS DENORMALIZATION?
================================================================

  Denormalization = intentionally duplicating data to optimize read performance.
  The opposite of 3NF/normalization (which eliminates all duplication).

  In NoSQL this is not a flaw -- it is the primary design tool.

  RDBMS approach:
  users table + orders table + products table
  --> JOIN at query time --> flexible but slow at scale

  NoSQL approach:
  orders document contains user name, user email, product name, product price
  --> single document read --> fast but data is duplicated

================================================================
WHY DENORMALIZE?
================================================================

  1. Avoid JOINs (no JOINs in most NoSQL databases)
  2. Optimize for specific access patterns
  3. Reduce round trips (everything in one document/row)
  4. Enable horizontal sharding (JOIN across shards is expensive)
  5. Pre-compute aggregations (store total in parent document)

================================================================
DENORMALIZATION PATTERNS
================================================================

  -- 1. SNAPSHOT PATTERN (copy at write time)
  Store a snapshot of the value at the moment of transaction.

  Order stores price at time of purchase:
  { "productId": "P1", "name": "Laptop", "price": 999.99, "qty": 1 }

  Even if product.price changes, the order is historically accurate.

  -- 2. DUPLICATE FOR READ PATTERNS
  Same data stored in multiple documents to serve different queries.

  Cassandra: create a separate table per access pattern:
  CREATE TABLE orders_by_user    (user_id UUID, order_id UUID, ..., PRIMARY KEY(user_id, order_id));
  CREATE TABLE orders_by_status  (status TEXT, order_id UUID, ..., PRIMARY KEY(status, order_id));

  Both tables hold the same order data -- duplication is intentional.

  -- 3. PRE-AGGREGATION (computed fields)
  Instead of summing at query time, maintain running totals:

  User document:
  {
    "_id": "U100",
    "name": "Alice",
    "totalOrders": 42,         <-- maintained via $inc on every order insert
    "totalSpent": 4253.50      <-- maintained via $inc on every order insert
  }

  Query: "show user profile with order stats" = single document read.

  -- 4. MATERIALIZED AGGREGATION
  Store aggregated results as a document (like a materialized view):

  {
    "_id": "stats:category:electronics:2026-03",
    "category": "electronics",
    "month": "2026-03",
    "totalRevenue": 125430.00,
    "orderCount": 312,
    "avgOrderValue": 402.00
  }

  Updated via background job or Kafka consumer on every order event.

================================================================
KEEPING DENORMALIZED DATA CONSISTENT
================================================================

  Challenge: when source data changes, all copies must be updated.

  Strategy 1 -- Acceptable Staleness:
  For snapshot data (order price), staleness is by design.
  No sync needed.

  Strategy 2 -- Eventual Consistency via Events:
  When product name changes, emit "product.updated" event.
  Consumer updates embedded copies in recent orders.
  Old orders may be stale; query layer falls back to product collection.

  Strategy 3 -- Synchronous Dual Write (application layer):
  On order insert: write order document AND update user's totalOrders in same txn.
  Multi-document transactions available in MongoDB 4.0+ and Cassandra LWT.

  Strategy 4 -- Background Jobs:
  Periodic batch job re-computes aggregates and refreshes denormalized fields.
  Acceptable for analytics; not for real-time.

================================================================
WHEN NOT TO DENORMALIZE
================================================================

  - Frequently changing data (real-time pricing, live inventory) that is
    embedded in thousands of documents becomes costly to keep fresh.
  - When write throughput is more important than read performance.
  - When data integrity / auditing requires single source of truth.
  - When schema is highly dynamic and duplication is unpredictable.

================================================================
INTERVIEW Q&A
================================================================

  Q: How do you handle data consistency when you denormalize in NoSQL?
  A: Depends on tolerance for staleness. Snapshot fields (e.g., order price)
     are intentionally immutable. For mutable duplicated fields, use events:
     emit a change event, consumers asynchronously update all copies.
     Accept eventual consistency. For critical aggregates (account balance),
     avoid denormalization or use transactions to update atomically.

  Q: What is a pre-aggregation pattern?
  A: Instead of computing aggregates (COUNT, SUM) at query time, you maintain
     running totals in a parent document. Every write that changes a count
     atomically increments the stored aggregate (using $inc in MongoDB or
     counter columns in Cassandra). Reads get the result instantly without
     scanning millions of rows.
