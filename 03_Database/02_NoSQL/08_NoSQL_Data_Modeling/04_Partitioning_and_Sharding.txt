================================================================
  PARTITIONING AND SHARDING IN NOSQL
================================================================

================================================================
WHY PARTITION?
================================================================

  A single machine has limits: disk, RAM, CPU, network bandwidth.
  Partitioning (sharding) splits data across multiple machines.

  Vertical scaling  --> bigger machine (has a ceiling, expensive)
  Horizontal scaling--> more machines (partition data across them)

  Sharding = splitting a dataset into partitions (shards) where
  each shard holds a subset of the data and lives on a node.

================================================================
PARTITION STRATEGIES
================================================================

  -- 1. RANGE PARTITIONING
  Keys are divided into consecutive ranges, each range on one shard.

  orders 1-1000000  --> shard 1
  orders 1000001-2000000 --> shard 2

  Pros: range queries efficient (all data for month on same shard)
  Cons: hot spots if all writes are to latest range (monotonic IDs/timestamps)

  -- 2. HASH PARTITIONING
  Apply hash function to partition key --> shard = hash(key) % numShards

  MongoDB: shard key is hashed before routing
  Cassandra: Murmur3 hash of partition key

  Pros: even distribution of writes
  Cons: range queries require scatter-gather (broadcast to all shards)

  -- 3. CONSISTENT HASHING
  Nodes placed on a ring at token positions.
  key hash falls on ring --> goes to first node clockwise.
  Adding/removing nodes only moves a fraction of keys (vs re-hashing all).

  Used by: Cassandra (token ring), DynamoDB, Riak

  Ring visualization:
  Node A: tokens 0-25
  Node B: tokens 26-50
  Node C: tokens 51-75
  Node D: tokens 76-99

  Remove Node B --> its tokens absorbed by Node C.
  Only Node B's data moves; A, C, D unaffected.

  -- 4. DIRECTORY PARTITIONING
  A lookup table maps keys to shards.
  Flexible but the directory becomes a bottleneck / SPOF.

================================================================
CHOOSING A PARTITION KEY
================================================================

  Good partition key:
  - High cardinality (many distinct values)
  - Even access distribution (no hot partitions)
  - Access pattern aligned (queries on same partition)

  Bad partition key:
  - Low cardinality: "status" (PENDING/SHIPPED) -- only 2-3 shards used
  - Monotonic: auto-increment ID or timestamp -- all writes to last shard
  - userId alone when one user has 90% of traffic (celebrity problem)

  Solutions for hot partition:
  - Compound key: (userId, datePrefix) -- spreads across time buckets
  - Write sharding: append random suffix to key (user:123:shard0..9)
    then read from all 10 shards and aggregate

================================================================
HOW SHARDING WORKS IN MAJOR DATABASES
================================================================

  MongoDB:
  - Enable sharding on collection: sh.shardCollection("db.orders", {userId: "hashed"})
  - mongos router directs queries to appropriate shard(s)
  - Config servers track which shard holds which range
  - Chunk migration: MongoDB auto-balances chunks across shards

  Cassandra:
  - Partitioner: Murmur3Partitioner (default, consistent hash)
  - Each node owns token ranges; virtual nodes (vnodes) = 256 tokens per node
  - Adding a node: takes ~1/n of each existing node's tokens
  - No "shard router" needed -- any node acts as coordinator

  Redis Cluster:
  - 16384 hash slots; each node owns a range of slots
  - CLUSTER KEYSLOT key --> returns slot number
  - Cross-slot operations not allowed (keys in same slot via {hashtag})

================================================================
SECONDARY INDEXES ON SHARDED DATA
================================================================

  Local secondary index: index on each shard (Cassandra LSI, DynamoDB LSI)
  - Fast but only useful if partition key is known

  Global secondary index: index spans all shards (DynamoDB GSI, MongoDB index)
  - Can query without partition key
  - Extra write overhead (index maintained separately)
  - Eventual consistency in DynamoDB GSI by default

================================================================
INTERVIEW Q&A
================================================================

  Q: What is the celebrity (hot partition) problem in sharding?
  A: When one partition key receives disproportionate traffic.
     E.g., a popular user generates 80% of reads. The shard holding
     that user becomes a bottleneck. Solutions: write sharding
     (append random suffix, read all and merge), composite key
     (distribute data further), or caching to absorb read traffic.

  Q: What is consistent hashing and why is it used?
  A: Consistent hashing places nodes and keys on a circular hash ring.
     A key maps to the first node clockwise from its hash position.
     When a node is added or removed, only that node's neighbors are
     affected -- not the entire dataset. This minimizes data movement
     during cluster changes, making it ideal for elastic scaling in
     distributed systems (Cassandra, DynamoDB).

  Q: How does MongoDB shard a collection?
  A: You choose a shard key and run sh.shardCollection(). MongoDB splits
     data into chunks based on shard key ranges and distributes chunks
     across shards. The mongos router uses chunk metadata from config
     servers to route queries. The balancer automatically migrates
     chunks to maintain even distribution.
