================================================================
  EMBEDDING VS REFERENCING IN NOSQL
================================================================

================================================================
EMBEDDING (DENORMALIZATION)
================================================================

  Store related data inside the same document / row.
  No JOIN needed -- all data retrieved in one read.

  MongoDB example: Order with embedded line items

  {
    "_id": "ORD001",
    "userId": "U100",
    "status": "SHIPPED",
    "createdAt": "2026-03-01T10:00:00Z",
    "items": [
      { "productId": "P1", "name": "Laptop", "qty": 1, "price": 999.99 },
      { "productId": "P2", "name": "Mouse",  "qty": 2, "price": 29.99 }
    ],
    "shippingAddress": {
      "street": "123 Main St",
      "city": "New York",
      "zip": "10001"
    }
  }

  Pros:
  - Single read to get entire order
  - Atomic write (entire document in one operation)
  - Fast -- no round trips
  - Simple application code

  Cons:
  - Document can grow large (MongoDB 16MB limit)
  - If item data changes (price), embedded copies are stale
  - Cannot query/update embedded arrays independently at scale
  - Duplication if same product embedded in thousands of orders

================================================================
REFERENCING (NORMALIZATION)
================================================================

  Store only the ID of related document; fetch separately.

  MongoDB example: Order references Product

  Order document:
  {
    "_id": "ORD001",
    "userId": "U100",
    "items": [
      { "productId": "P1", "qty": 1 },
      { "productId": "P2", "qty": 2 }
    ]
  }

  Product document (separate collection):
  {
    "_id": "P1",
    "name": "Laptop",
    "price": 999.99,
    "category": "electronics"
  }

  Pros:
  - No data duplication -- update product once, all orders see change
  - Product can be accessed/updated independently
  - No document size concerns
  - Natural fit for shared / independently accessed entities

  Cons:
  - Multiple reads required (N+1 problem)
  - $lookup in MongoDB (costly vs native JOIN)
  - More complex application code

================================================================
DECISION GUIDE
================================================================

  Embed when:
  - Data is always read together (order + its items)
  - Ownership relationship (order owns its items)
  - Array is bounded in size (max ~100 items)
  - Need atomic writes over both pieces
  - Child rarely queried independently

  Reference when:
  - Data is shared (product in many orders)
  - Child is independently accessed/updated
  - Array could grow unboundedly (user's all-time activity feed)
  - Parent document would exceed 16MB (MongoDB) or practical size
  - Child has its own lifecycle

================================================================
HYBRID PATTERN
================================================================

  Copy only the fields you need at read time, reference for full data:

  {
    "_id": "ORD001",
    "items": [
      {
        "productId": "P1",
        "name": "Laptop",       <-- snapshot at purchase time
        "price": 999.99,        <-- snapshot (prices change)
        "qty": 1
      }
    ]
  }

  This is correct for e-commerce: the order stores the price AT THE TIME
  of purchase. Even if the product price changes later, the order is correct.

================================================================
EXTENDED REFERENCE PATTERN
================================================================

  Embed only the fields you commonly need, reference for the rest:

  Order:
  {
    "_id": "ORD001",
    "customer": {
      "userId": "U100",
      "name": "Alice Smith",    <-- embedded for display
      "email": "alice@ex.com"   <-- embedded for notifications
    }
    -- Full user document is in users collection
  }

  Avoids $lookup for common display fields while keeping full user data separate.

================================================================
INTERVIEW Q&A
================================================================

  Q: When would you embed vs reference in MongoDB?
  A: Embed when: data is always accessed together, has an ownership
     relationship, the array is bounded, and you need atomic writes.
     Reference when: data is shared across documents, can grow unboundedly,
     or needs to be independently updated. In practice, use hybrid: embed
     a snapshot of needed fields at write time (e.g., product name/price
     in an order) while keeping the canonical product in its own collection.

  Q: What is the N+1 problem in NoSQL?
  A: When you load a list of N documents and then make one extra query per
     document to load related data (N+1 total queries). To avoid it:
     embed frequently needed fields, use $lookup in one query, or use
     batch-fetching (load all referenced IDs in one findMany call).
