================================================================
  INFLUXDB BASICS
================================================================

================================================================
CORE CONCEPTS
================================================================

  InfluxDB 2.x data model:
  Organization --> Bucket --> Measurement --> Series

  Bucket         = database + retention policy combined
  Measurement    = logical name for data (like a table name): "cpu"
  Tag Set        = indexed metadata: {host="web01", region="us-east"}
  Field Set      = actual values: {cpu_usage=72.5, memory=4096}
  Timestamp      = nanosecond precision by default

  Line Protocol (wire format for writing):
  measurement,tag_key=tag_val field_key=field_val timestamp

  Example writes:
  cpu,host=web01,region=us-east cpu_usage=72.5,memory=4096 1700000000000000000
  http_requests,service=api,method=GET count=150,latency=45.2 1700000000000000000

================================================================
LINE PROTOCOL SYNTAX
================================================================

  Structure:
  <measurement>[,<tag_key>=<tag_value>...] <field_key>=<field_value>[,...] [<timestamp>]

  Rules:
  - Tags: comma-separated key=value, before fields, strings (no quotes needed)
  - Fields: space after tags, comma-separated, can be float/int (i suffix)/string (quotes)/bool
  - Timestamp: optional, defaults to server time, nanoseconds since epoch

  Examples:
  temperature,location=room1,building=A celsius=23.4,humidity=55.2 1700000000
  stock,symbol=AAPL price=189.23,volume=1500000i 1700000000000000000
  events,type=login user="alice",success=true 1700000000000000000

================================================================
FLUX QUERY LANGUAGE (InfluxDB 2.x)
================================================================

  Functional pipeline syntax (similar to UNIX pipes):

  -- Average CPU per host in last hour:
  from(bucket: "monitoring")
    |> range(start: -1h)
    |> filter(fn: (r) => r._measurement == "cpu")
    |> filter(fn: (r) => r._field == "cpu_usage")
    |> group(columns: ["host"])
    |> mean()

  -- Top 5 hosts by average CPU (last 30 min):
  from(bucket: "monitoring")
    |> range(start: -30m)
    |> filter(fn: (r) => r._measurement == "cpu" and r._field == "cpu_usage")
    |> group(columns: ["host"])
    |> mean()
    |> sort(columns: ["_value"], desc: true)
    |> limit(n: 5)

  -- Downsampling: 1-minute windows from 1-second data:
  from(bucket: "monitoring")
    |> range(start: -24h)
    |> filter(fn: (r) => r._measurement == "cpu")
    |> aggregateWindow(every: 1m, fn: mean, createEmpty: false)

  -- Join two measurements:
  cpu = from(bucket: "metrics") |> range(start: -1h) |> filter(fn: (r) => r._measurement == "cpu")
  mem = from(bucket: "metrics") |> range(start: -1h) |> filter(fn: (r) => r._measurement == "memory")
  join(tables: {cpu: cpu, mem: mem}, on: ["_time", "host"])

================================================================
RETENTION POLICIES
================================================================

  InfluxDB 2.x -- set on bucket creation:
  POST /api/v2/buckets
  {
    "name": "monitoring",
    "retentionRules": [{ "type": "expire", "everySeconds": 604800 }]
  }
  -- retains 7 days, auto-deletes older data

  Downsampling via Tasks (Flux):
  option task = { name: "downsample_cpu", every: 1h }
  from(bucket: "monitoring")
    |> range(start: -2h)
    |> filter(fn: (r) => r._measurement == "cpu")
    |> aggregateWindow(every: 5m, fn: mean)
    |> to(bucket: "monitoring_5m")

================================================================
SPRING BOOT INTEGRATION
================================================================

  Dependency: influxdb-client-java

  @Bean
  public InfluxDBClient influxDBClient() {
      return InfluxDBClientFactory.create(
          "http://localhost:8086",
          "my-token".toCharArray(),
          "my-org",
          "my-bucket"
      );
  }

  Write example:
  WriteApiBlocking writeApi = client.getWriteApiBlocking();
  Point point = Point.measurement("cpu")
      .addTag("host", "web01")
      .addField("cpu_usage", 72.5)
      .time(Instant.now(), WritePrecision.NS);
  writeApi.writePoint(point);

  Query example:
  QueryApi queryApi = client.getQueryApi();
  String flux = "from(bucket:\"monitoring\") |> range(start: -1h) |> filter(fn: (r) => r._measurement == \"cpu\")";
  List<FluxTable> tables = queryApi.query(flux);
  for (FluxTable table : tables) {
      for (FluxRecord record : table.getRecords()) {
          System.out.println(record.getTime() + " " + record.getValue());
      }
  }

================================================================
INTERVIEW Q&A
================================================================

  Q: What is cardinality explosion in InfluxDB?
  A: Each unique combination of tags creates a new series.
     If you store a UUID or user_id in a tag with 1 million users,
     you get 1 million series. InfluxDB maintains an in-memory index
     for all series, so this can exhaust memory and crash the DB.
     Solution: put high-cardinality values in fields, not tags.

  Q: What is the Flux query language and how is it different from SQL?
  A: Flux is a functional, pipeline-based query language.
     Data flows through transformation steps (|>) rather than
     declarative SELECT/FROM/WHERE. It is optimized for time-series
     operations like aggregateWindow, fill, derivative, and moving averages.
     InfluxDB 1.x used InfluxQL (SQL-like); 2.x uses Flux.
