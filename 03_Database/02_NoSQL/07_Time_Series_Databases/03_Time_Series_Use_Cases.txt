  TIME SERIES DATABASE USE CASES
================================================================

================================================================
INFRASTRUCTURE MONITORING
================================================================

  Collect CPU, memory, disk, network from every server every 10 seconds.
  Millions of data points per minute across a fleet.

  Tools: Prometheus + Grafana (most common), InfluxDB + Telegraf

  Prometheus scrapes /metrics endpoints:
  - Each service exposes HTTP endpoint with metric values
  - Prometheus pulls on interval, stores locally
  - PromQL for querying, Grafana for dashboards
  - Alertmanager for threshold-based alerts

  PromQL example:
  -- CPU usage > 80% in last 5 min:
  100 - (avg by(instance)(irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

  -- Alert: pod restarts > 5 in last hour:
  increase(kube_pod_container_status_restarts_total[1h]) > 5

================================================================
IoT SENSOR DATA
================================================================

  Thousands of sensors sending temperature, pressure, humidity every minute.
  Need:
  - Fast ingest (many concurrent writers)
  - Long retention with downsampling (keep 1s for 1 day, 1m for 30 days, 1h for 2 years)
  - Anomaly detection queries

  InfluxDB example pipeline:
  Sensor --> MQTT --> Telegraf --> InfluxDB --> Grafana

  Downsampling task (Flux):
  option task = { name: "downsample_temp", every: 1h }
  from(bucket: "sensors_raw")
    |> range(start: -2h)
    |> filter(fn: (r) => r._measurement == "temperature")
    |> aggregateWindow(every: 1m, fn: mean)
    |> to(bucket: "sensors_1m")

FINANCIAL TICK DATA
================================================================

  Stock price, bid/ask, volume every millisecond.
  Need millisecond/nanosecond precision and fast range queries.

  TimescaleDB (Postgres extension) is popular here:
  - Full SQL compatibility
  - Hypertables auto-partition by time
  - Continuous aggregates (auto-materialized rolling views)
  - Compression policies

  CREATE TABLE stock_ticks (
    time        TIMESTAMPTZ NOT NULL,
    symbol      TEXT NOT NULL,
    price       NUMERIC(12,4),
    volume      BIGINT
  );
  SELECT create_hypertable('stock_ticks', 'time');

  Continuous aggregate (1-minute OHLCV):
  CREATE MATERIALIZED VIEW stock_ohlcv_1m
  WITH (timescaledb.continuous) AS
  SELECT time_bucket('1 minute', time) AS bucket,
         symbol,
         first(price, time)  AS open,
         max(price)          AS high,
         min(price)          AS low,
         last(price, time)   AS close,
         sum(volume)         AS volume
  FROM stock_ticks
  GROUP BY bucket, symbol;

================================================================
APPLICATION PERFORMANCE MONITORING (APM)
================================================================

  Track: request latency, error rate, throughput per service/endpoint.
  "RED Method": Rate, Errors, Duration for every microservice.

  Metrics emitted via Micrometer (Spring Boot):
  - http.server.requests timer (count, sum, max)
  - jvm.memory.used gauge
  - hikaricp.connections.active gauge

  Prometheus scrapes /actuator/prometheus and stores in TSDB.
  Alert if p99 latency > 500ms or error rate > 1%.

================================================================
REAL-WORLD ARCHITECTURE
================================================================

  [Services] --> [Micrometer/Telegraf/StatsD]
                        |
                  [Kafka / MQTT]           (optional buffer for high throughput)
                        |
              [InfluxDB / Prometheus]      (storage + query)
                        |
                [Grafana / Kibana]         (visualization)
                        |
              [AlertManager / PagerDuty]   (alerting)

================================================================
DOWNSAMPLING STRATEGY TABLE
================================================================

  Time Range     | Resolution | Retention
  ---------------|------------|----------
  Last 24 hours  | 1 second   | raw data
  Last 30 days   | 1 minute   | aggregated
  Last 1 year    | 5 minutes  | aggregated
  Older          | 1 hour     | aggregated or deleted

================================================================
INTERVIEW Q&A
================================================================

  Q: How do you handle data retention for time-series data?
  A: Use a tiered downsampling strategy. Keep raw high-resolution data for
     the most recent period (1-7 days), downsample to 1-minute averages
     for 30 days, then hourly for longer. Retention policies auto-delete
     expired tiers. This dramatically reduces storage while keeping
     long-term trends accessible.

  Q: What is the RED method?
  A: Rate (requests per second), Errors (error rate), Duration (latency).
     Apply to every microservice. If rate drops, errors spike, or p99
     latency exceeds SLA, alert immediately. Pair with USE method for
     infrastructure (Utilization, Saturation, Errors).

  Q: Why use Prometheus over InfluxDB?
  A: Prometheus uses a pull model (scrapes endpoints) which is easier to
     configure for dynamic Kubernetes environments (service discovery).
     InfluxDB uses a push model, better for IoT/edge where targets cannot
     be scraped. Prometheus has stronger alerting (AlertManager) and is
     the de-facto standard for Kubernetes observability.
