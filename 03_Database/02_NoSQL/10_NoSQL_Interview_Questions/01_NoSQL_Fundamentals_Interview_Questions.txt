NoSQL FUNDAMENTALS — INTERVIEW QUESTIONS & ANSWERS
(For Java Developers with 7+ Years Experience)
===========================================================================================================

Q1. What is NoSQL? Why would you choose NoSQL over a relational database?
-------------------------------------------------------------------------
NoSQL ("Not Only SQL") databases store and retrieve data in non-tabular formats.
They are designed for specific access patterns, horizontal scalability, and flexibility.

Types of NoSQL:
  Document:    MongoDB, Couchbase (JSON-like documents)
  Key-Value:   Redis, DynamoDB (simple key → value)
  Column-Family: Cassandra, HBase (column-oriented storage)
  Graph:       Neo4j, Amazon Neptune (nodes and edges)
  Search:      Elasticsearch, Solr (inverted indexes, full-text)
  Time-Series: InfluxDB, TimescaleDB (time-stamped data)

Choose NoSQL when:
  ✅ Schema is dynamic or varies frequently
  ✅ Need horizontal scalability across commodity hardware
  ✅ Very high read/write throughput (millions of ops/sec)
  ✅ Denormalized, hierarchical data fits naturally
  ✅ Specific access patterns can be optimized (e.g., key lookups, time-series)

Choose SQL when:
  ✅ Complex relationships and joins are needed
  ✅ Strong ACID guarantees required
  ✅ Data is structured and schema is stable
  ✅ Reporting, analytics, ad-hoc querying

Q2. Explain the CAP Theorem.
-----------------------------
CAP Theorem states that a distributed database can only guarantee 2 of 3 properties:

  C — Consistency:  Every read receives the most recent write or an error.
  A — Availability: Every request receives a response (may not be latest data).
  P — Partition Tolerance: System continues operating despite network partitions.

Network partitions are UNAVOIDABLE in distributed systems → P must always be chosen.
Therefore the real choice is: CP vs AP.

CP (Consistency + Partition Tolerance): 
  Sacrifices availability during partitions.
  Examples: HBase, Zookeeper, MongoDB (with strong read preference)
  Use when: Banking, financial systems — data accuracy is critical.

AP (Availability + Partition Tolerance):
  Sacrifices consistency during partitions (eventual consistency).
  Examples: Cassandra, CouchDB, DynamoDB
  Use when: Social media feeds, shopping carts — availability matters more.

Important nuance: CAP is binary — real systems operate on a SPECTRUM.
Modern databases tune consistency and availability via configuration
(e.g., Cassandra consistency levels: ONE, QUORUM, ALL).

Q3. What is eventual consistency? How do you handle it in application design?
------------------------------------------------------------------------------
Eventual Consistency: Given no new updates, all replicas will EVENTUALLY converge
to the same value. Reads may return stale data in the short term.

Example: You post a tweet (written to one node). Your follower may not see it for
a fraction of a second while other nodes replicate.

Handling it in application design:
  1. Read-your-writes: After a write, route subsequent reads to the same replica
                       or wait for propagation (e.g., DynamoDB strongly consistent reads)
  
  2. Monotonic reads: Ensure a client always sees data at least as new as their last read
  
  3. Version vectors / timestamps: Track causality of updates
  
  4. Optimistic UI updates: Show updated state in UI immediately, reconcile later
  
  5. Idempotent operations: Design for retries — same write can be applied multiple times
                             without changing result (use unique IDs for deduplication)
  
  6. CRDT (Conflict-free Replicated Data Types): Data structures that merge without conflicts
     (counters, sets) — used in Cassandra, Redis Cluster

Q4. What is the difference between BASE and ACID?
--------------------------------------------------
ACID (Relational databases):
  Atomicity:   All or nothing per transaction
  Consistency: DB always in valid state
  Isolation:   Concurrent transactions don't interfere
  Durability:  Committed data survives crashes

BASE (Many NoSQL databases):
  Basically Available:  System is available most of the time (AP in CAP)
  Soft State:           State may change over time (due to eventual consistency)
  Eventually Consistent: System will converge to consistency given no new input

ACID: Sacrifices scalability for correctness.
BASE: Sacrifices immediate consistency for availability and scalability.

Example:
  Bank transfer → ACID required (money must be exactly right)
  Social media likes counter → BASE is fine (approximate count is acceptable)

Q5. What is MongoDB? Explain its key concepts.
----------------------------------------------
MongoDB is a document-oriented NoSQL database storing data as BSON (Binary JSON) documents.

Key Concepts:
  Database:    Logical container (similar to schema in RDBMS)
  Collection:  Group of documents (similar to table in RDBMS)
  Document:    A JSON-like record (similar to a row) — can be nested
  Field:       Key-value pair within a document (similar to column)
  _id:         Unique identifier (ObjectId by default)

Key Features:
  - Flexible schema: Documents in same collection can have different fields
  - Embedded documents: Nest related data within a document (avoids joins)
  - Powerful aggregation pipeline: $match, $group, $project, $lookup (JOIN equivalent)
  - Horizontal scaling via sharding
  - Replica sets for high availability

When to use MongoDB:
  - Product catalogs (varying attributes per product)
  - Content management systems
  - User profiles with varying data
  - Event logging

Q6. Explain embedding vs referencing in MongoDB schema design.
--------------------------------------------------------------
EMBEDDING: Store related data INSIDE the parent document.
  {
    "_id": "order123",
    "customer": "Ray",
    "items": [
      {"product": "Widget", "qty": 2, "price": 10.00},
      {"product": "Gadget", "qty": 1, "price": 25.00}
    ]
  }

  PRO: Single document read (no join) — very fast
  PRO: Atomic updates on the document
  CON: Document grows unboundedly (MongoDB 16MB limit per document)
  CON: Can't query embedded docs independently

REFERENCING: Store foreign key (like RDBMS), use $lookup to join.
  // orders collection
  { "_id": "order123", "customerId": "cust456", "items": ["item1", "item2"] }
  
  // items collection
  { "_id": "item1", "product": "Widget", "qty": 2 }

  PRO: Avoids document bloat
  PRO: Items queryable independently
  CON: Two queries or $lookup needed (less performant than embedding)

RULE OF THUMB:
  - Embed if data is accessed together, has bounded size, 1:few relationship
  - Reference if data is accessed independently, 1:many (many = thousands), or data is shared

Q7. What is Redis? What are its primary data structures?
---------------------------------------------------------
Redis is an in-memory data structure store, used as cache, database, and message broker.

Data Structures:
  String:   SET key "value"  GET key   -- Simplest, most common. TTL support.
  List:     LPUSH, RPUSH, LPOP, RPOP -- Ordered list, use as queue/stack
  Set:      SADD, SMEMBERS, SISMEMBER -- Unordered unique elements. Union/Intersection.
  Sorted Set: ZADD, ZRANGE, ZRANK -- Elements with scores. Leaderboards, priority queues.
  Hash:     HSET, HGET, HMGET -- Field-value pairs. Ideal for objects.
  Bitmap:   SETBIT, GETBIT -- Compact boolean flags. Track daily active users.
  HyperLogLog: PFADD, PFCOUNT -- Approximate cardinality counting (unique visitors)
  Stream:   XADD, XREAD -- Append-only log of messages. Like Kafka-lite.

Common Patterns:
  Caching:      Cache expensive DB queries. SET key value EX 3600
  Session:      Store HTTP sessions with TTL
  Rate Limiting: INCR + EXPIRE for sliding window counters
  Distributed Lock: SET key uuid NX EX 30 (atomically set if not exists)
  Pub/Sub:      Real-time messaging between services

Q8. What is Redis caching? Explain cache-aside, write-through, and write-behind patterns.
------------------------------------------------------------------------------------------
CACHE-ASIDE (Lazy Loading) — most common:
  1. App checks cache → miss
  2. App queries DB
  3. App writes result to cache
  4. Next request → cache hit

  PRO: Cache only contains requested data
  CON: First request is always slow (cache miss)
  CON: Stale data if DB updated directly

WRITE-THROUGH:
  1. App writes to cache
  2. Cache synchronously writes to DB
  3. Reads always from cache

  PRO: Cache always up-to-date with DB
  CON: Write latency (two writes on every update)
  CON: Caches data that may never be read again

WRITE-BEHIND (Write-Back):
  1. App writes to cache
  2. Cache ASYNCHRONOUSLY flushes to DB later

  PRO: Very fast writes (async)
  CON: Risk of data loss if cache fails before flushing
  CON: Complex conflict resolution

WRITE-AROUND:
  1. App writes DIRECTLY to DB (bypasses cache)
  2. Cache populated on next read

  PRO: Cache not polluted with write-heavy data
  CON: Higher cache miss rate initially

In Spring: Spring Cache abstraction (@Cacheable, @CachePut, @CacheEvict) supports all patterns.

Q9. Explain Apache Cassandra's architecture. What makes it suitable for high writes?
-------------------------------------------------------------------------------------
Cassandra is a wide-column distributed database designed for massive write throughput.

Key Architecture:
  Ring Architecture: All nodes are equal — NO master/slave. Data distributed across the ring.
  Partitioning:      Partition key determines which node stores the data (consistent hashing).
  Replication:       Data replicated to N nodes (replication factor). Configurable per keyspace.
  Gossip Protocol:   Nodes communicate cluster state without a central coordinator.

Write path (why writes are so fast):
  1. Write to Commit Log (sequential disk write — very fast)
  2. Write to MemTable (in-memory)
  3. Periodically flushed to SSTables (immutable files on disk)
  4. Compaction merges SSTables periodically

  No in-place updates → appends only → sequential I/O → very high write throughput.

Consistency Levels (tunable per query):
  ONE:     Fastest, weakest. Write/read from 1 node.
  QUORUM:  Read/write from majority (N/2 + 1). Strong consistency when used together.
  ALL:     All replicas must respond. Strongest but slowest.

Cassandra trade-offs:
  ✅ Extremely high write throughput (millions/sec)
  ✅ Linear scalability — add nodes, add capacity
  ❌ No joins, no transactions across rows
  ❌ Data model must match query patterns exactly
  ❌ Eventual consistency by default

Q10. What is Elasticsearch? How does it handle full-text search?
----------------------------------------------------------------
Elasticsearch is a distributed search and analytics engine built on Apache Lucene.

Core Concepts:
  Index:      Collection of documents (like a table)
  Document:   JSON object being stored (like a row)
  Field:      Key-value pair within a document
  Shard:      Partition of an index across nodes (horizontal scaling)
  Replica:    Copy of a shard (fault tolerance + read scalability)

Full-Text Search:
  Inverted Index: Maps terms → documents containing that term.
    Text "Java developer interview" → {Java: [doc1, doc5], developer: [doc1, doc3], ...}
  
  Analysis pipeline:
    1. Character Filter:   Remove HTML, special chars
    2. Tokenizer:          Split text into tokens ("Java developer" → ["Java", "developer"])
    3. Token Filter:       Lowercase, remove stopwords, stemming (running→run)

  Query types:
    match:       Full-text search with analysis applied
    term:        Exact match (for keyword fields, not analyzed)
    match_phrase: Exact phrase in order
    bool:        Combine queries (must, should, must_not, filter)
    range:       Range queries on numbers/dates

Use cases: Product search, log analysis (ELK stack), autocomplete, recommendation engines.

Java integration: Spring Data Elasticsearch, Elasticsearch Java client.

Q11. How does DynamoDB differ from other NoSQL databases?
---------------------------------------------------------
DynamoDB is AWS's fully managed, serverless NoSQL database.

Key Concepts:
  Table:         Top-level container
  Item:          A record (row equivalent)
  Attribute:     Field (column equivalent)
  Partition Key: Required. Determines which partition stores the item. Must be unique alone.
  Sort Key:      Optional. Combined with partition key = composite key. Enables range queries.

Capacity Modes:
  Provisioned: Specify read/write capacity units (RCU/WCU). Predictable cost.
  On-Demand:   Auto-scales. Pay per request. Best for unpredictable traffic.

Global Secondary Index (GSI): New partition key + sort key. Can query by different attributes.
Local Secondary Index (LSI):  Same partition key, different sort key. Must be created at table creation.

DynamoDB Streams: Change data capture — triggers Lambda on insert/update/delete.

Java integration:
  - AWS SDK v2 DynamoDB Enhanced Client
  - Spring Data DynamoDB (community)
  - DynamoDBMapper (v1 SDK)

Key difference from Cassandra: DynamoDB is fully managed (no cluster to run), serverless,
AWS-native with IAM auth. Cassandra is open-source, self-managed (or DataStax).

Q12. What is sharding? Explain consistent hashing.
--------------------------------------------------
Sharding: Horizontally partitioning data across multiple database nodes.
          Each node (shard) holds a SUBSET of total data.

Why: Single node can't handle all data or traffic → split across shards.

Consistent Hashing:
  Problem with naive hashing (key % N_nodes): Adding/removing nodes reshuffles most keys.
  
  Solution: Place nodes on a virtual ring. Hash key → position on ring → 
            walk clockwise to find responsible node.
  
  Adding a node: Only keys between new node and its predecessor move. ~1/N keys moved.
  Removing a node: Only that node's keys move to successor. ~1/N keys moved.
  
  Virtual nodes (vnodes): Each physical node handles multiple virtual positions on the ring.
                          Distributes load more evenly.

Shard key design (critical for MongoDB, Cassandra):
  Good shard key: High cardinality, evenly distributed access pattern.
  Bad shard key: User's country (uneven — US has way more data than Liechtenstein = hotspot).
                 Monotonically increasing ID (all writes go to last shard = hotspot).
