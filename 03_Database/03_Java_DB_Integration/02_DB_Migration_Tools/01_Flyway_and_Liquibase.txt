DATABASE MIGRATION TOOLS — FLYWAY & LIQUIBASE
===========================================================================================================

WHY DATABASE MIGRATION TOOLS?
------------------------------
In production, you can NEVER manually run SQL scripts and hope everyone's DB is in sync.
You need:
  - Version-controlled database changes (tracked in Git alongside code)
  - Reproducible schema evolution across environments (dev, QA, staging, prod)
  - Audit trail of all schema changes
  - Team collaboration (no conflicting schema changes)
  - Automated schema migration during app deployment / startup

Two primary tools in the Java ecosystem:
  FLYWAY:    Simple, SQL-first, convention-based. Better for SQL-heavy teams.
  LIQUIBASE: XML/YAML/JSON/SQL changesets. Better for database-agnostic, complex workflows.

===========================================================================================================
FLYWAY
===========================================================================================================

CONCEPT
--------
Flyway tracks schema changes using versioned SQL migration files.
It maintains a "flyway_schema_history" table in your DB to track which scripts have been applied.

Migration naming convention:
  V{version}__{description}.sql     — Versioned (applied once, in order)
  R__{description}.sql              — Repeatable (re-applied when checksum changes)
  U{version}__{description}.sql     — Undo (rollback — requires Flyway Teams)

Examples:
  src/main/resources/db/migration/
    V1__Create_users_table.sql
    V2__Add_email_to_users.sql
    V3__Create_orders_table.sql
    V4__Add_index_on_order_date.sql
    R__Create_reporting_view.sql

V1__Create_users_table.sql:
  CREATE TABLE users (
    id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    username VARCHAR(50) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT NOW()
  );

V2__Add_email_to_users.sql:
  ALTER TABLE users ADD COLUMN email VARCHAR(255) NOT NULL;
  ALTER TABLE users ADD CONSTRAINT uq_email UNIQUE (email);

---

SPRING BOOT INTEGRATION
------------------------
Maven dependency:
  <dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
  </dependency>
  <!-- For PostgreSQL: -->
  <dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
  </dependency>

Spring Boot auto-configures Flyway. It runs automatically on app startup BEFORE any beans.

application.yml:
  spring:
    flyway:
      enabled: true
      locations: classpath:db/migration   # Default location
      baseline-on-migrate: true           # Safe to run on existing DB with data
      baseline-version: 0                 # Starting version for baseline
      validate-on-migrate: true           # Validate applied migrations match classpath
      out-of-order: false                 # Prevent out-of-order migrations
      clean-disabled: true                # SAFETY: disables flyway:clean in production!
      table: flyway_schema_history        # History table name

---

HOW FLYWAY WORKS
-----------------
On startup:
  1. Connects to DB
  2. Checks if flyway_schema_history table exists (creates if not)
  3. Reads all migration files from configured locations
  4. Compares applied versions (from table) with available scripts
  5. Runs unapplied scripts IN ORDER
  6. Records each applied migration with version, checksum, timestamp, success/failure

Checksum Validation:
  If a previously applied migration file is modified → Flyway throws an error.
  This prevents accidental modification of already-applied migrations.
  NEVER modify a versioned migration file after it's been applied anywhere.
  Instead: Create a NEW versioned migration to make the additional change.

---

FLYWAY COMMANDS
----------------
flyway:migrate    — Apply pending migrations (default on Spring Boot startup)
flyway:info       — Show status of all migrations (applied, pending, failed)
flyway:validate   — Validate applied migrations match files (no changes)
flyway:repair     — Remove failed migrations from history table
flyway:clean      — DROP ALL objects in the schema (NEVER in production!)
flyway:baseline   — Mark existing schema as baseline (for existing databases)

Maven plugin:
  mvn flyway:info
  mvn flyway:migrate
  mvn flyway:validate

---

FLYWAY BEST PRACTICES
---------------------
1. NEVER modify a migration file after it's been run in any environment.
   Change history is sacred — create a new migration instead.

2. Test migrations locally before merging.
   Run flyway:validate in CI pipeline.

3. Use baseline-on-migrate: true for existing databases.
   Marks current state as V0 baseline, applies only new migrations.

4. Set clean-disabled: true in all non-local environments.
   flyway:clean drops everything — catastrophic in production.

5. Keep migrations small and focused.
   Each migration does ONE thing (add column, create table, add index).
   Easier to review, debug, and rollback manually if needed.

6. For data migrations, separate data from schema:
   V5__Add_full_name_column.sql   -- schema change
   V6__Backfill_full_name.sql     -- data migration (UPDATE)
   V7__Drop_first_last_name.sql   -- cleanup (after verification)

===========================================================================================================
LIQUIBASE
===========================================================================================================

CONCEPT
--------
Liquibase uses CHANGESETS (not versioned files) to track DB changes.
Each changeset has an id + author + file = unique identifier.
Tracked in DATABASECHANGELOG table.

Change log formats supported: XML, YAML, JSON, SQL.

db/changelog/db.changelog-master.yaml:
  databaseChangeLog:
    - include:
        file: db/changelog/001-create-users-table.yaml
    - include:
        file: db/changelog/002-add-email-to-users.yaml

db/changelog/001-create-users-table.yaml:
  databaseChangeLog:
    - changeSet:
        id: 001
        author: ray
        changes:
          - createTable:
              tableName: users
              columns:
                - column:
                    name: id
                    type: BIGINT
                    autoIncrement: true
                    constraints:
                      primaryKey: true
                - column:
                    name: username
                    type: VARCHAR(50)
                    constraints:
                      nullable: false
                      unique: true
                - column:
                    name: created_at
                    type: TIMESTAMP
                    defaultValueComputed: NOW()

db/changelog/002-add-email-to-users.yaml:
  databaseChangeLog:
    - changeSet:
        id: 002
        author: ray
        changes:
          - addColumn:
              tableName: users
              columns:
                - column:
                    name: email
                    type: VARCHAR(255)
                    constraints:
                      nullable: false
                      unique: true

---

SPRING BOOT INTEGRATION WITH LIQUIBASE
---------------------------------------
Maven:
  <dependency>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-core</artifactId>
  </dependency>

application.yml:
  spring:
    liquibase:
      change-log: classpath:db/changelog/db.changelog-master.yaml
      enabled: true
      drop-first: false  # NEVER true in production
      contexts: prod     # Run only changesets tagged with context 'prod'
      labels: ""         # Filter by label

Liquibase also auto-runs on startup in Spring Boot.

---

LIQUIBASE ROLLBACK
-------------------
Liquibase supports automatic rollback (defined inline with changeSet).

  - changeSet:
      id: 003
      author: ray
      changes:
        - addColumn:
            tableName: users
            columns:
              - column:
                  name: phone
                  type: VARCHAR(20)
      rollback:
        - dropColumn:
            tableName: users
            columnName: phone

Rollback commands:
  liquibase rollbackCount 1         -- Rollback last 1 changeset
  liquibase rollbackToDate <date>   -- Rollback to a specific date
  liquibase rollbackTag v1.0        -- Rollback to a tagged state

---

FLYWAY vs LIQUIBASE — COMPARISON
---------------------------------
| Feature              | Flyway                  | Liquibase                  |
|----------------------|-------------------------|----------------------------|
| Primary format       | SQL files               | XML/YAML/JSON/SQL          |
| Learning curve       | Very simple             | Moderate                   |
| Rollback             | Paid (Teams)            | Free (built-in)            |
| DB abstraction       | Less (SQL dialects)     | More (generates SQL per DB)|
| Spring Boot support  | Native auto-config      | Native auto-config         |
| Community            | Large                   | Large                      |
| Checksum validation  | Yes                     | Yes                        |
| Conditional logic    | Limited                 | Good (preconditions)       |
| Best for             | SQL teams, simplicity   | Multi-DB, complex workflows|

RECOMMENDATION for Java/Spring Boot:
  - FLYWAY: When your team is SQL-comfortable and wants simplicity.
  - LIQUIBASE: When you need database portability (Oracle + PostgreSQL + MySQL),
               or need native rollback support, or complex conditional migrations.

INTERVIEW QUESTIONS ON DB MIGRATIONS
--------------------------------------
Q: How do you handle a failed migration in Flyway in production?
A: A failed migration leaves an entry in flyway_schema_history with success=false.
   Flyway won't run further migrations until this is resolved.
   Steps:
   1. Fix the SQL script (or manually apply partial fix in DB)
   2. Run flyway:repair to remove the failed entry from history table
   3. Re-run flyway:migrate
   Never manually edit the history table without using repair.

Q: Can you run a Flyway migration without restarting the app?
A: Yes — invoke Flyway.migrate() programmatically via the Flyway bean,
   or use Spring Boot Actuator's /flyway endpoint (if enabled).

Q: What is baseline-on-migrate in Flyway?
A: When you adopt Flyway on an existing database, it already has schema/data.
   baseline-on-migrate creates a baseline entry in the history table for the
   current database state (as version 0 or specified baseline-version),
   so only NEW migration files after the baseline are applied.

Q: How do you prevent different developers' migrations from conflicting?
A: Use a migration versioning strategy:
   - Use timestamps instead of sequential numbers: V20240409120000__description.sql
   - Use PR review process to assign migration numbers sequentially
   - CI pipeline runs flyway:validate on every PR to catch conflicts early

Q: What happens if two instances of the app start simultaneously?
A: Flyway uses a distributed lock (via the DB) to ensure only one instance runs migrations.
   The second instance waits until the first completes. This is thread-safe and cluster-safe.
