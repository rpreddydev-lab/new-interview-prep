DATABASE SECURITY IN JAVA APPLICATIONS
===========================================================================================================

WHY DATABASE SECURITY?
------------------------
Databases contain the most sensitive data in an application — user credentials, PII,
financial records, health data. A single security failure can be catastrophic.

Senior Java developer interviews frequently test:
  - SQL Injection prevention
  - Least privilege DB access
  - Secure credential management
  - Encryption at rest and in transit

===========================================================================================================
1. SQL INJECTION — THE #1 DATABASE SECURITY THREAT
===========================================================================================================

What it is:
  Attacker injects malicious SQL through user input that gets executed by the database.

Vulnerable code (NEVER do this):
  // Concatenating user input into SQL
  String query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'";
  Statement stmt = conn.createStatement();
  ResultSet rs = stmt.executeQuery(query);
  
  // Attacker input: username = ' OR '1'='1'--
  // Generated SQL: SELECT * FROM users WHERE username = '' OR '1'='1'--' AND password = ''
  // Result: Returns ALL users! Authentication bypassed.
  
  // Attacker input: username = '; DROP TABLE users;--
  // Generated SQL: SELECT ... WHERE username = ''; DROP TABLE users;--
  // Result: Table destroyed!

---

FIX 1: PreparedStatement (JDBC)
--------------------------------
  // Parameterized query — input treated as DATA, not SQL
  String query = "SELECT * FROM users WHERE username = ? AND password_hash = ?";
  PreparedStatement ps = conn.prepareStatement(query);
  ps.setString(1, username);
  ps.setString(2, hashedPassword);
  ResultSet rs = ps.executeQuery();
  
  // Attacker input: username = ' OR '1'='1'--
  // DB treats this as literal string, not SQL syntax. No injection possible.

---

FIX 2: JPA / JPQL Named Parameters
------------------------------------
  // SAFE: parameterized
  @Query("SELECT u FROM User u WHERE u.username = :username")
  Optional<User> findByUsername(@Param("username") String username);
  
  // SAFE: Spring Data derived query
  Optional<User> findByUsernameAndActive(String username, boolean active);
  
  // DANGEROUS: String concatenation in JPQL
  @Query("SELECT u FROM User u WHERE u.username = '" + username + "'")  // WRONG!

---

FIX 3: Stored Procedures
-------------------------
  // Stored procedures use parameterized calls
  CallableStatement cs = conn.prepareCall("{CALL get_user(?)}");
  cs.setString(1, username);
  ResultSet rs = cs.executeQuery();

---

FIX 4: Input Validation and Whitelisting
-----------------------------------------
  // Validate that input matches expected pattern
  if (!username.matches("^[a-zA-Z0-9_]{3,50}$")) {
    throw new IllegalArgumentException("Invalid username format");
  }
  
  // For dynamic ORDER BY (parameterized doesn't work for column names):
  // Use an allowlist instead:
  Set<String> ALLOWED_SORT_COLUMNS = Set.of("name", "created_at", "salary");
  if (!ALLOWED_SORT_COLUMNS.contains(sortColumn)) {
    throw new IllegalArgumentException("Invalid sort column: " + sortColumn);
  }
  String sql = "SELECT * FROM employees ORDER BY " + sortColumn;  // Safe now

---

FIX 5: ORM Frameworks
-----------------------
  JPA, Hibernate, Spring Data: All use parameterized queries by default.
  They prevent SQL injection when used correctly (no string concatenation in queries).

2. LEAST PRIVILEGE — DATABASE USER PERMISSIONS
===========================================================================================================

Principle of Least Privilege: Application DB user should only have the permissions it NEEDS.

Bad practice: Application connects as root / admin user.
  - Full control if application is compromised
  - Can DROP tables, access all schemas

Good practice:
  -- Create dedicated application user
  CREATE USER app_user WITH PASSWORD 'secret';
  
  -- Grant ONLY necessary permissions
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
  GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_user;
  
  -- Do NOT grant:
  -- DROP, TRUNCATE, CREATE, ALTER, REFERENCES (unless needed)
  -- Permissions on other schemas
  -- Superuser privileges

For microservices: Each service gets its OWN DB user with access to only its tables.

Read replicas: Use a separate read-only user for read replicas.
  CREATE USER readonly_user WITH PASSWORD 'secret';
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_user;

3. SECURE CREDENTIAL MANAGEMENT
===========================================================================================================

NEVER hardcode database credentials in:
  - Source code
  - application.properties checked into Git
  - Docker images

Correct approaches:

1. Environment Variables:
   spring.datasource.url=${DB_URL}
   spring.datasource.username=${DB_USER}
   spring.datasource.password=${DB_PASSWORD}
   
   In K8s: Use Kubernetes Secrets mounted as environment variables.

2. Spring Cloud Config Server:
   Externalized config with encryption support.
   Credentials stored in encrypted form in config repository.

3. Vault (HashiCorp):
   spring.cloud.vault.uri=https://vault.company.com
   spring.cloud.vault.token=${VAULT_TOKEN}
   
   Vault dynamically generates DB credentials with short TTL.
   No long-lived passwords — credentials rotate automatically.

4. AWS Secrets Manager / Azure Key Vault / GCP Secret Manager:
   Application fetches credentials from managed secret store at runtime.
   IAM-based access control — no static passwords.
   
   Spring Cloud AWS + Secrets Manager:
   spring.config.import=aws-secretsmanager:/myapp/db-credentials

5. Kubernetes Secrets:
   Store as K8s Secret, mount as env variable or volume.
   Base64 encoded (NOT encrypted at rest by default!).
   Use with external-secrets-operator for proper secret management.

4. ENCRYPTION IN TRANSIT
===========================================================================================================

All communication between application and database MUST be encrypted (TLS/SSL).

PostgreSQL:
  spring.datasource.url=jdbc:postgresql://host:5432/db?ssl=true&sslmode=require
  
  Or verify server certificate:
  ?ssl=true&sslmode=verify-full&sslrootcert=/path/to/ca.crt

MySQL:
  spring.datasource.url=jdbc:mysql://host:3306/db?useSSL=true&requireSSL=true&verifyServerCertificate=true

HikariCP:
  config.addDataSourceProperty("ssl", "true");
  config.addDataSourceProperty("sslmode", "require");

Cloud managed DBs (RDS, Cloud SQL, Azure DB):
  TLS is typically enabled by default. Always verify SSL is required, not just allowed.

5. ENCRYPTION AT REST
===========================================================================================================

Database-level encryption:
  PostgreSQL: pgcrypto extension for column-level encryption.
  MySQL: InnoDB tablespace encryption (encrypt entire tables).
  Cloud: AWS RDS KMS encryption, Azure TDE, GCP CMEK.

Application-level encryption (column-level):
  Sensitive fields encrypted BEFORE storing in DB.
  
  Using Jasypt with JPA:
    @Column(name = "ssn")
    @Convert(converter = AttributeEncryptor.class)
    private String ssn;
    
    @Converter
    public class AttributeEncryptor implements AttributeConverter<String, String> {
      private final TextEncryptor encryptor;
      
      @Override
      public String convertToDatabaseColumn(String plainText) {
        return encryptor.encrypt(plainText);
      }
      
      @Override
      public String convertToEntityAttribute(String cipherText) {
        return encryptor.decrypt(cipherText);
      }
    }
  
  Encrypted fields CANNOT be efficiently queried — use for store-only sensitive data.
  Alternative: Store hash for lookup + encrypted value for display.

6. ROW-LEVEL SECURITY (RLS)
===========================================================================================================

Row-Level Security: Database enforces access control at the ROW level.
Even if a bug in the application skips a WHERE clause — DB denies access.

PostgreSQL RLS:
  -- Enable RLS on table
  ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;
  
  -- Policy: Users can only see their own accounts
  CREATE POLICY user_isolation ON accounts
    USING (user_id = current_setting('app.current_user_id')::BIGINT);
  
  -- In application: Set the current user context before querying
  entityManager.createNativeQuery("SET LOCAL app.current_user_id = " + userId).executeUpdate();
  // Now all queries on 'accounts' automatically filter by this user_id

Use case: Multi-tenant applications where each tenant should only see their data.
          Financial applications where users should only see their own records.

7. SQL AUDIT LOGGING
===========================================================================================================

Track who accessed/modified what data, and when.

Approaches:

1. Application-level audit (Spring Data Auditing):
   @EnableJpaAuditing
   
   @Entity
   public class Order {
     @CreatedBy String createdBy;
     @LastModifiedBy String modifiedBy;
     @CreatedDate LocalDateTime createdAt;
     @LastModifiedDate LocalDateTime updatedAt;
   }
   
   @Component
   public class AuditorAwareImpl implements AuditorAware<String> {
     @Override
     public Optional<String> getCurrentAuditor() {
       return Optional.ofNullable(SecurityContextHolder.getContext())
           .map(ctx -> ctx.getAuthentication())
           .map(auth -> auth.getName());
     }
   }

2. Database triggers for audit tables:
   -- Create audit table
   CREATE TABLE employees_audit (
     audit_id BIGSERIAL PRIMARY KEY,
     employee_id BIGINT,
     action VARCHAR(10),  -- INSERT, UPDATE, DELETE
     changed_by VARCHAR(100),
     changed_at TIMESTAMP DEFAULT NOW(),
     old_data JSONB,
     new_data JSONB
   );
   
   -- Trigger to capture changes
   CREATE TRIGGER employees_audit_trigger
   AFTER INSERT OR UPDATE OR DELETE ON employees
   FOR EACH ROW EXECUTE FUNCTION log_employee_changes();

3. Change Data Capture (CDC) with Debezium:
   Captures all DB changes via WAL/binlog → streams to Kafka → audit consumer writes to audit DB.
   Most scalable and decoupled approach.

8. PREVENTING MASS ASSIGNMENT AND OVER-FETCHING
===========================================================================================================

Mass Assignment Attack:
  If entity has admin=false field and client sends admin=true in request body
  and you blindly save the entity → admin privilege escalation!

  Fix in Spring:
    // NEVER map request body directly to entity
    // Use DTOs and explicitly map fields
    @PutMapping("/users/{id}")
    public UserDto updateUser(@PathVariable Long id, @RequestBody UserUpdateDto dto) {
      User user = userRepo.findById(id).orElseThrow();
      user.setName(dto.getName());      // Only allowed fields
      user.setEmail(dto.getEmail());    // No admin, no role, no internal fields
      return UserDto.from(userRepo.save(user));
    }

Over-fetching (returning sensitive data in API):
  // WRONG: Returns entity with password hash, internal flags
  @GetMapping("/users/{id}")
  public User getUser(@PathVariable Long id) { return userRepo.findById(id).get(); }
  
  // CORRECT: Use projection/DTO
  @GetMapping("/users/{id}")
  public UserPublicDto getUser(@PathVariable Long id) {
    return userRepo.findPublicById(id);  // Only name, email, avatar — no password!
  }

9. INTERVIEW Q&A
===========================================================================================================

Q: What is SQL injection and how do you prevent it in a Spring Boot application?
A: SQL injection occurs when user input is concatenated into SQL strings, allowing
   attackers to inject malicious SQL. Prevention:
   1. Use PreparedStatement with parameterized queries (JDBC)
   2. Use JPA/JPQL with named parameters (never string concatenation in queries)
   3. Use Spring Data derived query methods or @Query with :param syntax
   4. Validate and whitelist input for dynamic parts (ORDER BY column names)
   5. Use ORM frameworks consistently — they parameterize by default

Q: What is the principle of least privilege for database users?
A: The application database user should have ONLY the permissions required for its function.
   No DROP, no ALTER, no access to other schemas. Read-only users for read replicas.
   Each microservice has its own user with access only to its tables.

Q: How do you store database credentials securely in a Spring Boot application?
A: Never hardcode in source code or properties files committed to Git.
   Use environment variables, Spring Cloud Config Server, HashiCorp Vault,
   AWS Secrets Manager, or Kubernetes Secrets. The best approach for cloud-native
   apps is a managed secrets service (Vault / AWS SM) with short-lived credentials.

Q: What is row-level security and when would you use it?
A: RLS is a database-enforced policy that restricts which rows a user can see/modify.
   Even if application code has a bug and misses a WHERE clause, the DB enforces isolation.
   Use for multi-tenant apps, financial data isolation, healthcare systems (HIPAA compliance).
