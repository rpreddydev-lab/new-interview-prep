================================================================
GRAPHQL SCHEMA DEFINITION LANGUAGE (SDL)
================================================================

1. WHAT IS SDL?
---------------
The Schema Definition Language (SDL) is the human-readable syntax for
defining a GraphQL schema. It is language-agnostic — the same SDL works
regardless of whether you implement your server in Java, JavaScript, Python,
or any other language.

SDL files typically use the .graphql or .graphqls extension.

2. BASIC BUILDING BLOCKS
-------------------------

  2.1 TYPE DEFINITIONS
  --------------------
  ```graphql
  type TypeName {
    fieldName: FieldType
    fieldWithArgs(arg: ArgType): ReturnType
  }
  ```

  2.2 NON-NULL AND LIST MODIFIERS
  --------------------------------
  String      → nullable scalar
  String!     → non-null scalar
  [String]    → nullable list of nullable strings
  [String!]   → nullable list of non-null strings
  [String!]!  → non-null list of non-null strings
  [String]!   → non-null list of nullable strings

  Read right-to-left: the outermost ! means the list itself won't be null;
  the inner ! means each element won't be null.

  2.3 DESCRIPTIONS (DOCSTRINGS)
  ------------------------------
  ```graphql
  """
  A registered user of the application.
  """
  type User {
    "The user's unique identifier"
    id: ID!

    "The user's display name"
    name: String!

    "ISO-8601 timestamp of account creation"
    createdAt: String!
  }
  ```

3. SCALAR TYPES
---------------
Built-in scalars:
  Int      → 32-bit signed integer
  Float    → Double-precision floating-point
  String   → UTF-8 character sequence
  Boolean  → true / false
  ID       → Unique identifier (serialized as String, treated as opaque)

Custom scalars (require server-side implementation):
  ```graphql
  scalar Date
  scalar DateTime
  scalar JSON
  scalar Upload       # For file uploads (multipart spec)
  scalar BigDecimal
  scalar UUID
  ```
  Custom scalars need a coercion implementation (serialize, parseValue,
  parseLiteral) on the server.

4. OBJECT TYPES
----------------
The most common type. A named set of fields.

  ```graphql
  type Product {
    id: ID!
    name: String!
    price: Float!
    category: Category!
    tags: [String!]!
    createdAt: DateTime!
    updatedAt: DateTime
  }
  ```

5. QUERY, MUTATION, SUBSCRIPTION TYPES
---------------------------------------
These are special root object types — entry points into the graph.

  ```graphql
  type Query {
    # Single item lookup
    product(id: ID!): Product

    # List with filtering/pagination
    products(
      filter: ProductFilter
      first: Int
      after: String
    ): ProductConnection!

    # Current authenticated user
    me: User
  }

  type Mutation {
    createProduct(input: CreateProductInput!): ProductPayload!
    updateProduct(id: ID!, input: UpdateProductInput!): ProductPayload!
    deleteProduct(id: ID!): DeletePayload!
  }

  type Subscription {
    productPriceChanged(id: ID!): Product!
    newOrderPlaced: Order!
  }
  ```

6. ENUM TYPES
--------------
  ```graphql
  enum OrderStatus {
    PENDING
    CONFIRMED
    SHIPPED
    DELIVERED
    CANCELLED
  }

  enum Role {
    ADMIN
    USER
    MODERATOR
    GUEST
  }
  ```
  Enums are serialized as strings but validated strictly against declared values.

7. INTERFACE TYPES
-------------------
An Interface defines a contract. Any type that implements an interface must
include all of the interface's fields.

  ```graphql
  interface Node {
    id: ID!
  }

  interface Timestamps {
    createdAt: DateTime!
    updatedAt: DateTime
  }

  type User implements Node & Timestamps {
    id: ID!
    name: String!
    email: String!
    createdAt: DateTime!
    updatedAt: DateTime
  }

  type Post implements Node & Timestamps {
    id: ID!
    title: String!
    body: String!
    createdAt: DateTime!
    updatedAt: DateTime
  }
  ```

  Querying an interface field requires inline fragments to access type-specific fields:
  ```graphql
  query {
    nodes(ids: ["1", "2"]) {
      id                         # from Node interface
      ... on User { name email } # type-specific
      ... on Post { title }      # type-specific
    }
  }
  ```

8. UNION TYPES
---------------
A Union represents one of several concrete types. Unlike Interface, union
members don't need to share any fields.

  ```graphql
  union SearchResult = User | Product | Article

  type Query {
    search(query: String!): [SearchResult!]!
  }
  ```

  Querying a union:
  ```graphql
  query {
    search(query: "alice") {
      ... on User    { name email }
      ... on Product { name price }
      ... on Article { title publishedAt }
    }
  }
  ```

  INTERFACE vs UNION:
  - Use Interface when types share common fields
  - Use Union when types are unrelated but can appear in the same position

9. INPUT TYPES
--------------
Input types are used ONLY as argument types (not return types). They allow
complex, structured arguments.

  ```graphql
  input CreateProductInput {
    name: String!
    price: Float!
    categoryId: ID!
    tags: [String!]
    description: String
  }

  input ProductFilter {
    minPrice: Float
    maxPrice: Float
    categoryId: ID
    inStock: Boolean
  }

  type Mutation {
    createProduct(input: CreateProductInput!): Product!
  }
  ```

  WHY SEPARATE INPUT TYPES?
  - Object types can have arguments on their fields — input types cannot
  - This prevents circular references in input arguments
  - Creates a clear separation between read types and write types

10. DIRECTIVES IN SDL
----------------------
  Built-in type-system directives:
  ```graphql
  type User {
    oldField: String @deprecated(reason: "Use 'newField' instead")
    newField: String!
  }
  ```

  Declaring custom directives:
  ```graphql
  directive @auth(requires: Role = USER) on FIELD_DEFINITION
  directive @upper on FIELD_DEFINITION
  directive @length(max: Int!) on ARGUMENT_DEFINITION | INPUT_FIELD_DEFINITION
  directive @rateLimit(max: Int!, window: String!) on FIELD_DEFINITION
  ```

  Directive locations:
  QUERY, MUTATION, SUBSCRIPTION, FIELD, FRAGMENT_DEFINITION,
  FRAGMENT_SPREAD, INLINE_FRAGMENT, VARIABLE_DEFINITION
  (above are "executable" directive locations)

  SCHEMA, SCALAR, OBJECT, FIELD_DEFINITION, ARGUMENT_DEFINITION,
  INTERFACE, UNION, ENUM, ENUM_VALUE, INPUT_OBJECT, INPUT_FIELD_DEFINITION
  (above are "type system" directive locations)

11. PAGINATION PATTERNS IN SDL
--------------------------------
  Cursor-based (Relay Connection Spec — RECOMMENDED):
  ```graphql
  type PageInfo {
    hasNextPage: Boolean!
    hasPreviousPage: Boolean!
    startCursor: String
    endCursor: String
  }

  type UserEdge {
    cursor: String!
    node: User!
  }

  type UserConnection {
    edges: [UserEdge!]!
    pageInfo: PageInfo!
    totalCount: Int!
  }

  type Query {
    users(first: Int, after: String, last: Int, before: String): UserConnection!
  }
  ```

  Offset-based (simpler, but problematic with inserts/deletes):
  ```graphql
  type Query {
    users(page: Int! = 1, pageSize: Int! = 20): UserPage!
  }

  type UserPage {
    items: [User!]!
    total: Int!
    page: Int!
    pageSize: Int!
    totalPages: Int!
  }
  ```

12. PAYLOAD PATTERN (MUTATION RESPONSES)
-----------------------------------------
Best practice: mutations return a "payload" type instead of directly
returning the entity. This allows returning errors alongside the data.

  ```graphql
  type CreateUserPayload {
    user: User            # null if error
    userErrors: [UserError!]!
  }

  type UserError {
    field: [String!]      # which field(s) the error relates to
    message: String!
    code: UserErrorCode!
  }

  enum UserErrorCode {
    EMAIL_TAKEN
    INVALID_EMAIL
    NAME_TOO_LONG
  }

  type Mutation {
    createUser(input: CreateUserInput!): CreateUserPayload!
  }
  ```

  Shopify pioneered this pattern. It allows partial success and structured
  field-level validation errors without relying on the top-level "errors" array.

13. SCHEMA-FIRST vs CODE-FIRST
--------------------------------
  Schema-First:
    - Write .graphql SDL files first
    - Generate code from schema (or hand-write resolvers)
    - Used by: Apollo Server, Spring for GraphQL
    - Pros: clear contract, easier collaboration, tool support
    - Cons: keeping schema and code in sync is manual

  Code-First:
    - Write code with annotations; framework generates schema
    - Used by: TypeGraphQL, Nexus (JS), graphene-django (Python)
    - Java: nothing standard (Spring for GraphQL is schema-first)
    - Pros: single source of truth in code, type-safe
    - Cons: generated SDL can be messy, less explicit contract

14. INTERVIEW QUESTIONS & ANSWERS
-----------------------------------

Q: What is the difference between Interface and Union in GraphQL?
A: An Interface defines common fields that implementing types must have. A Union
   is a set of possible concrete types with no required shared fields. Use
   Interface when types share a structure (like `Node { id: ID! }`), use Union
   when types are unrelated but can appear in the same field (like `SearchResult
   = User | Product | Post`).

Q: Can an Input type have fields of Object type?
A: No. Input type fields must be scalar types, enum types, or other input types.
   Object types cannot be used as input field types. This is by design — it
   prevents circular input types and separates the read and write models.

Q: What is non-null in GraphQL and when should you use it?
A: The `!` suffix marks a field or argument as non-null. Use it when:
   - A field will ALWAYS have a value (id, name of required things)
   - An argument is required for the query to make sense
   Be conservative: it's a breaking change to ADD non-null (removes null as a
   valid value), but easy to make a non-null field nullable later.

Q: What is the Relay Connection Specification?
A: A standardized pagination pattern: a Connection type has `edges` (array of
   Edge types each containing `cursor` and `node`) and `pageInfo`
   (hasNextPage, hasPreviousPage, startCursor, endCursor). Enables stable
   cursor-based pagination. Most GraphQL clients (especially Relay) expect this.

Q: How do you handle breaking schema changes?
A: (1) Never remove or rename fields without deprecation first.
   (2) Mark old fields @deprecated and add new fields alongside.
   (3) Monitor actual query usage to determine when deprecated fields are safe
       to remove (use Apollo Studio or similar analytics).
   (4) For input argument changes, add new arguments with defaults rather than
       changing existing ones.
