REDIS STREAMS — DEEP DIVE FOR INTERVIEWS
================================================================================

1. OVERVIEW
────────────
Redis Streams (added in Redis 5.0) is an append-only log data structure,
similar conceptually to Apache Kafka. Key features:
  - Each entry has a unique auto-generated ID (timestamp-based)
  - Entries are immutable after addition
  - Consumer Groups: multiple consumers share work from the same stream
  - Acknowledgment: messages tracked until explicitly ACKed
  - Replay: consumers can read from any position
  - Persistence: survives restarts (with AOF/RDB)

Streams are the most complex and powerful Redis data type.


2. STREAM ENTRY IDs
────────────────────
Every stream entry has an ID in the format: <millisecondsTime>-<sequenceNumber>

  Auto-generated:  XADD stream:orders * field1 value1
    → Redis generates ID like "1709000000000-0"
    millisecondsTime = current Unix timestamp in milliseconds
    sequenceNumber   = monotonically increasing within the same millisecond

  Manual:  XADD stream:orders 1709000000000-1 field1 value1
    → Useful for migration or deterministic IDs

  Partial:  XADD stream:orders 1709000000000-* field1 value1
    → Use given timestamp, auto-generate sequence

  ID ordering is guaranteed: newer IDs are always > older IDs.
  IDs are lexicographically and numerically ordered.


3. CORE COMMANDS
─────────────────

  Add:
    XADD key [NOMKSTREAM] [MAXLEN [~] count | MINID [~] id] * field value [...]
      *        → auto-generate ID
      MAXLEN   → trim to at most N entries (MAXLEN 1000 = exact, MAXLEN ~ 1000 = approx)
      MINID    → trim entries with ID < given ID
      ~        → approximate trimming (faster, allows a few extra entries)
      NOMKSTREAM → don't create stream if it doesn't exist

    Examples:
      XADD orders * orderId 42 amount 99.99 status pending
      XADD orders MAXLEN ~ 100000 * orderId 43 amount 59.99

  Read (no consumer group):
    XREAD [COUNT n] [BLOCK ms] STREAMS key [key…] id [id…]
      id = 0  → read from beginning
      id = $  → read only NEW entries (from now on)
      BLOCK 0 → block forever until new data
      BLOCK 5000 → block for 5 seconds

    XRANGE key start end [COUNT n]    → range query (inclusive)
      - means -inf, + means +inf
      XRANGE orders - +               → all entries
      XRANGE orders 1709000000000-0 + → from specific ID onwards

    XREVRANGE key end start [COUNT n] → reverse range

  Inspect:
    XLEN key                          → number of entries. O(1).
    XINFO STREAM key [FULL [COUNT n]] → stream metadata and sample entries
    XINFO GROUPS key                  → consumer group info
    XINFO CONSUMERS key groupname     → consumers in a group

  Delete / Trim:
    XDEL key id [id …]               → delete specific entries by ID
    XTRIM key MAXLEN [~] count        → trim to length
    XTRIM key MINID [~] id            → remove entries before ID

  Consumer Groups:
    XGROUP CREATE key groupname id [MKSTREAM] [ENTRIESREAD n]
      id = 0  → read from beginning
      id = $  → read only new entries
      id = >  → (in XREADGROUP) fetch undelivered messages

    XREADGROUP GROUP groupname consumer [COUNT n] [BLOCK ms] [NOACK]
               STREAMS key [key…] > [> …]
      >        → fetch new (never delivered to this group) messages

    XACK key groupname id [id …]     → acknowledge processed messages

    XCLAIM key groupname consumer min-idle-time id [id …] [IDLE ms] [TIME ms]
               [RETRYCOUNT n] [FORCE] [JUSTID]
      → reassign pending messages to a different consumer
      → used for dead-letter / retry logic

    XAUTOCLAIM key groupname consumer min-idle-time start [COUNT n] [JUSTID]
      → auto-reassign messages idle > min-idle-time (Redis 6.2+)
      → simpler than XCLAIM for common retry patterns

    XPENDING key groupname [[IDLE ms] start end count [consumer]]
      → inspect pending (delivered but not ACKed) messages

    XGROUP DELCONSUMER key groupname consumer
    XGROUP DESTROY key groupname
    XGROUP SETID key groupname id    → rewind/advance read position


4. CONSUMER GROUPS IN DEPTH
─────────────────────────────
  Without consumer groups: all readers see all messages (broadcast).
  With consumer groups: messages are distributed among consumers (competing).

  State tracked per consumer group:
    - Last delivered ID: which messages have been fetched by this group
    - PEL (Pending Entries List): messages delivered but not yet ACKed
      per consumer

  Flow:
    1. XREADGROUP ... > → consumer fetches NEW messages
       → message added to consumer's PEL (pending)
    2. Consumer processes message
    3. XACK → message removed from PEL
       → permanently acknowledged; no longer redeliverable

    If consumer crashes (no XACK):
    4. XPENDING → see what's stuck in PEL
    5. XAUTOCLAIM → reassign to another consumer after timeout
    6. Other consumer processes and ACKs

  Multiple groups on same stream:
    - Each group maintains its own position
    - Group A and Group B both see ALL messages independently
    - Within Group A: messages distributed among its consumers
    - Use case: stream:orders → Group "inventory" + Group "email" + Group "analytics"
      Each group processes all orders independently but distributes within group.

  Multiple consumers in same group:
    - Each consumer gets a DIFFERENT subset of messages
    - Work is distributed (load balancing)
    - Use case: 5 worker instances all in "workers" group


5. XREAD vs XREADGROUP — KEY DIFFERENCE
─────────────────────────────────────────
  XREAD STREAMS stream 0:
    - Independent reader, no group tracking
    - Multiple readers each see ALL messages
    - No acknowledgment, no PEL
    - Good for: replaying all events, multiple independent processors
    - Like Kafka consumer without consumer group (each reads all partitions)

  XREADGROUP GROUP mygroup consumer1 STREAMS stream >:
    - Coordinated reading within a group
    - Each message delivered to exactly ONE consumer in the group
    - Messages tracked in PEL until ACKed
    - Good for: distributed work queue, load-balanced processing


6. PENDING ENTRIES LIST (PEL) AND RETRY
──────────────────────────────────────────
  XPENDING stream mygroup - + 10
  → Shows up to 10 pending messages (delivered but not ACKed):
  1) 1709000000000-0  consumer1  15000 (idle ms)  3 (delivery count)
  2) 1709000000001-0  consumer2  8000             1

  Delivery count > 1 means message has been redelivered (consumer crashed).
  High delivery count → message may be "poison pill" → send to dead-letter.

  Auto-claim and retry:
  XAUTOCLAIM stream mygroup recovery-consumer 60000 0-0 COUNT 10
  → Reassign messages idle > 60 seconds to "recovery-consumer"
  → Starting from ID 0-0 (beginning of PEL)

  Dead-letter pattern:
  if delivery_count > MAX_RETRIES:
      XADD dead-letter * original_id <id> error "max retries exceeded"
      XACK stream mygroup <id>


7. STREAM vs KAFKA COMPARISON
───────────────────────────────
  Feature                  │ Redis Streams                 │ Kafka
  ─────────────────────────┼───────────────────────────────┼───────────────────────
  Storage                  │ In-memory + optional persist  │ Disk-based (durable)
  Latency                  │ Sub-millisecond               │ 1-10ms typical
  Throughput               │ 100K+ msgs/sec per shard      │ Millions/sec clustered
  Retention                │ Bounded (MAXLEN / MINID trim) │ Configurable, unlimited
  Consumer groups          │ Yes (manual ACK)              │ Yes (offset commit)
  Message replay           │ Yes (XRANGE from ID)          │ Yes (seek to offset)
  Ordering                 │ Within single stream          │ Per partition
  Partitioning             │ Multiple streams manually     │ Built-in partitions
  Exactly-once             │ Not natively (at-least-once)  │ Yes (with config)
  Ecosystem                │ Limited                       │ Rich (Kafka Connect, etc.)
  Setup complexity         │ Simple (part of Redis)        │ Complex (brokers, ZK/KRaft)
  Best for                 │ Low-medium volume, simple MQ  │ High-volume event streaming


8. STREAM TRIMMING STRATEGIES
────────────────────────────────
  MAXLEN (count-based):
    XADD stream MAXLEN ~ 100000 * ...
    → Keep approximately the last 100,000 entries
    → ~ = approximately (uses radix tree structure; may keep slightly more)
    → Without ~: exact trimming (slower, must check each node)

  MINID (time-based):
    # Keep only entries from last 24 hours
    cutoff = current_ms - 86400000
    XTRIM stream MINID ~ <cutoff>

  Recommended: MAXLEN ~ for simple retention, MINID ~ for time-based retention.
  Always use ~ for production (10-20x faster trimming).


9. XINFO — MONITORING STREAMS
────────────────────────────────
  XINFO STREAM orders FULL COUNT 5
  → Stream metadata:
    length: 42389
    first-entry: ...
    last-entry: ...
    radix-tree-keys: 12
    radix-tree-nodes: 25
    groups: 3
    entries-added: 50000
    recorded-first-entry-id: ...

  XINFO GROUPS orders
  → Per group: name, consumers, pending count, last-delivered-id

  XINFO CONSUMERS orders mygroup
  → Per consumer: name, pending count, idle time, inactive time


10. REAL-WORLD PATTERNS
────────────────────────

10a. Order Processing Pipeline:
  # Producer
  XADD stream:orders * orderId 42 userId 99 amount 99.99 status PENDING

  # Consumer Group: inventory service
  XGROUP CREATE stream:orders inventory $ MKSTREAM
  loop:
    messages = XREADGROUP GROUP inventory worker1 COUNT 10 BLOCK 0
               STREAMS stream:orders >
    for each message:
        update_inventory(message)
        XACK stream:orders inventory message.id

  # Consumer Group: email service
  XGROUP CREATE stream:orders emails $
  loop:
    messages = XREADGROUP GROUP emails worker1 COUNT 10 BLOCK 0
               STREAMS stream:orders >
    for each message:
        send_confirmation_email(message)
        XACK stream:orders emails message.id

10b. Event Sourcing:
  XADD events:user:42 * event_type LOGIN ip 192.168.1.1
  XADD events:user:42 * event_type PURCHASE item 1001 amount 50.00
  XADD events:user:42 * event_type LOGOUT

  # Replay all user events
  XRANGE events:user:42 - +
  → Rebuild user state by replaying events

10c. Fan-Out with Multiple Groups:
  XADD stream:notifications * userId 42 type ORDER_SHIPPED
  # Each downstream service (push, email, SMS) has its own consumer group
  # All services independently process the same notification event


11. INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────
  Q: What is a Redis Stream and how is it different from a List?
  A: A Stream is an append-only log with unique time-based IDs, consumer groups,
     acknowledgment semantics, and message replay. A List is a simple linked list
     where LPOP removes messages without any tracking. Streams support multiple
     consumer groups that independently track their position; a List has no such
     concept. Use Streams when you need durable, acknowledged, replayable messages.

  Q: What is a Consumer Group in Redis Streams?
  A: A consumer group is a named group of consumers that share a single stream.
     The group tracks a "last delivered ID" so each new message is delivered to
     exactly ONE consumer in the group (load balancing). Messages are tracked in
     a PEL (Pending Entries List) until explicitly ACKed with XACK. If a consumer
     crashes, the message stays in PEL and can be reclaimed by another consumer.

  Q: What happens if a consumer in a group crashes before ACKing?
  A: The message remains in the consumer's PEL. Use XPENDING to inspect it,
     then XAUTOCLAIM to reassign it to another consumer after a timeout.
     This prevents message loss while still allowing at-least-once delivery.

  Q: How does Redis Streams compare to Kafka?
  A: Redis Streams: sub-ms latency, simpler setup, memory-based (bounded
     retention), good for moderate workloads. Kafka: disk-based, unlimited
     retention, built-in partitioning, exactly-once semantics, better for
     high-volume long-term event streaming. Use Redis Streams for internal
     service communication at moderate scale; use Kafka for big data pipelines.

  Q: What is the difference between XREAD and XREADGROUP?
  A: XREAD is a simple read without group tracking — multiple callers each see
     all messages independently (no coordination). XREADGROUP reads within a
     consumer group — each message is delivered to exactly one consumer, tracked
     in PEL until ACKed. XREADGROUP is for distributed work queues.
