KAFKA VS APACHE PULSAR VS AMAZON KINESIS
==========================================

=== OVERVIEW COMPARISON TABLE ===

Feature               | Kafka              | Apache Pulsar       | Amazon Kinesis
----------------------|--------------------|---------------------|------------------
Model                 | Log-based          | Log-based           | Log-based (shards)
Storage               | Broker-local disk  | BookKeeper (tiered) | AWS managed
Multi-tenancy         | Manual (namespaces)| Native              | AWS account based
Geo-replication       | MirrorMaker 2      | Native built-in     | Kinesis Global Tables
Replay               | Yes (offset)        | Yes (cursor)        | Yes (24h default, 7 days max)
Message ordering      | Per partition      | Per partition       | Per shard
Message retention     | Configurable       | Configurable        | 24h (extendable)
Throughput            | Very high          | Very high           | High (limited by shard)
Schema registry       | Confluent (external)| Built-in            | No (use Glue)
Dead letter           | Manual             | Built-in            | No (manual)
Exactly-once          | Yes (transactions) | Yes (transactions)  | No (at-least-once)
Protocol              | Custom (Kafka protocol) | Custom + Kafka compat | HTTP/AWS SDK
Cloud-native          | Requires management| Requires management | Fully managed
Cost model            | Infrastructure     | Infrastructure      | Per shard-hour + PUT

=== APACHE KAFKA ===

Architecture:
  - Brokers store data locally on disk (coupled storage and compute)
  - Topics → partitions → leader/follower replication
  - Zookeeper (old) or KRaft (new, no Zookeeper) for metadata

Strengths:
  + Industry standard — massive ecosystem
  + Extremely high throughput (millions of messages/sec per broker)
  + Kafka Streams, ksqlDB for stream processing
  + Exactly-once semantics with transactions
  + Mature, battle-tested (LinkedIn, Netflix, Uber)
  + Rich connectors (Kafka Connect, 200+ connectors)

Weaknesses:
  - Storage and compute coupled → scaling means adding brokers (expensive)
  - No native multi-tenancy (quotas, namespaces must be managed)
  - MirrorMaker 2 for geo-replication (not seamless)
  - Partition count cannot be reduced (only increased)
  - Operational complexity (especially at scale)
  - No built-in delayed/scheduled messages

Best for:
  - High-throughput event streaming
  - Stream processing with Kafka Streams
  - Existing Kafka ecosystem investment
  - On-premises or self-managed cloud deployments

=== APACHE PULSAR ===

Architecture (key difference from Kafka):
  Separates compute (brokers) from storage (Apache BookKeeper).
  Brokers are stateless → easy to scale compute independently.
  BookKeeper stores data → scale storage independently.

  Topics → partitions → broker (stateless) → BookKeeper ledgers

Unique features:
  1. Tiered storage: offload old data to S3/GCS automatically
  2. Native geo-replication: built in, not add-on
  3. Native multi-tenancy: tenant/namespace/topic hierarchy
  4. Unified messaging: both queue and stream semantics on same topic
  5. Built-in schema registry
  6. Delayed message delivery (deliver after X seconds)
  7. Dead letter topics built-in
  8. Pulsar Functions: lightweight stream processing (like Kafka Streams)

Strengths:
  + Storage-compute separation → independent scaling
  + Native multi-tenancy (SaaS use cases)
  + Built-in geo-replication
  + Tiered storage (cost-effective long retention)
  + Kafka compatibility (Kafka clients can connect)
  + Rich subscription types: Exclusive, Failover, Shared, Key_Shared

Weaknesses:
  - Smaller ecosystem than Kafka
  - More complex architecture (brokers + BookKeeper + ZooKeeper)
  - Less mature tooling than Kafka
  - Smaller community and fewer battle-tested stories

Best for:
  - Multi-tenant SaaS platforms
  - Long message retention with tiered storage
  - Global geo-distributed messaging
  - When Kafka ecosystem limitations are constraints

=== AMAZON KINESIS DATA STREAMS ===

Architecture:
  Shards are the unit of capacity.
  Each shard: 1 MB/s ingestion, 2 MB/s consumption.
  Scale: add more shards (manual or auto-scaling).

Unique features:
  - Fully managed by AWS (no infrastructure to manage)
  - Native AWS integrations: Lambda, Firehose, S3, DynamoDB, Glue
  - Kinesis Data Firehose: delivery to S3, Redshift, Elasticsearch
  - Kinesis Data Analytics (Flink): SQL/Flink on streams
  - Enhanced fan-out: each consumer gets 2 MB/s dedicated throughput

Strengths:
  + Zero operational overhead (fully managed)
  + Native AWS ecosystem integration
  + Auto-scaling with on-demand mode
  + Pay-per-use pricing
  + Kinesis Client Library (KCL) handles consumer group complexity
  + 7-day max retention (extended retention available)

Weaknesses:
  - 1 MB/s per shard → must plan shard capacity (can be restrictive)
  - 24-hour default retention (7-day max) → not for long-term replay
  - No exactly-once delivery (at-least-once)
  - Higher cost at high throughput vs self-managed Kafka
  - AWS vendor lock-in
  - Limited stream processing (Flink/KDA required for complex processing)
  - Shard-based pricing can be hard to predict

Best for:
  - AWS-first teams wanting zero ops
  - Event ingestion for serverless/Lambda architectures
  - Medium-scale event streaming
  - Teams without Kafka expertise

=== WHEN TO CHOOSE WHAT ===

Choose Kafka when:
  - Need highest throughput and lowest latency
  - Team has Kafka expertise
  - Want rich stream processing (Kafka Streams, ksqlDB)
  - Not locked into a cloud provider
  - Using Confluent Cloud for managed Kafka

Choose Pulsar when:
  - Building multi-tenant SaaS
  - Need native geo-replication
  - Want storage-compute independence
  - Long retention with tiered storage to S3

Choose Kinesis when:
  - All-in on AWS
  - Want zero Kafka/Pulsar operational knowledge
  - Building Lambda-based event-driven architecture
  - Moderate scale (not LinkedIn-level)

=== PRICING COMPARISON (HIGH LEVEL) ===

Kafka (self-managed):
  - Pay for EC2 instances + EBS storage
  - r6i.2xlarge × 3 brokers ≈ $1,500-2,000/month

Kafka (Confluent Cloud):
  - ~$0.11 per CKU-hour (Confluent Kafka Unit)
  - Typically higher than self-managed but no ops cost

Kinesis:
  - $0.015 per shard-hour + $0.014 per million PUT records
  - 10 shards = $108/month base + PUT costs

Pulsar (self-managed on cloud):
  Similar to Kafka infrastructure cost.
  StreamNative Cloud (managed Pulsar) for SaaS option.
