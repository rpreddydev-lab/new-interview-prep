================================================================
TDD — TEST DRIVEN DEVELOPMENT: Complete Interview Preparation Guide
================================================================

1. WHAT IS TDD?
================================================================
Test-Driven Development (TDD) is a software development methodology where:
  - You write a FAILING TEST before writing any production code
  - You write the MINIMUM code to make the test pass
  - You REFACTOR while keeping tests green

TDD was formalized by Kent Beck as part of Extreme Programming (XP).
His book "Test-Driven Development: By Example" (2003) is the definitive resource.

TDD is NOT just "write tests first" — it's a design discipline.
The process of writing tests first FORCES better design.

================================================================
2. THE RED → GREEN → REFACTOR CYCLE
================================================================

Every TDD iteration follows this exact cycle:

  ┌─────────────────────────────────────────────┐
  │  RED: Write a failing test                   │
  │  The test describes desired behavior that    │
  │  doesn't exist yet. Test MUST fail first.    │
  └──────────────────────┬──────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────────────┐
  │  GREEN: Write MINIMUM code to pass          │
  │  Don't over-engineer. Write just enough.    │
  │  "Make it work." Ugly code is OK here.      │
  └──────────────────────┬──────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────────────┐
  │  REFACTOR: Improve the code                 │
  │  Remove duplication, improve naming,        │
  │  simplify. Tests must stay GREEN.           │
  └──────────────────────┬──────────────────────┘
                         │
                         ▼
                   Repeat with next test

Key insight: Each cycle is SMALL — minutes, not hours.
If a cycle takes more than 15 minutes, the step is too big.

3. TDD EXAMPLE — STEP BY STEP (Java)
================================================================

Requirement: Build a FizzBuzz service that returns:
  - "Fizz" for multiples of 3
  - "Buzz" for multiples of 5
  - "FizzBuzz" for multiples of both
  - The number as string otherwise

─────────────────────────────────────────────────────────
ITERATION 1: Basic number
─────────────────────────────────────────────────────────

RED — Write failing test:
  @Test
  void shouldReturnNumberAsString() {
      FizzBuzzService service = new FizzBuzzService();
      assertEquals("1", service.evaluate(1));
  }
  
  // Run → FAILS: FizzBuzzService doesn't exist

GREEN — Write minimum code:
  public class FizzBuzzService {
      public String evaluate(int n) {
          return String.valueOf(n);
      }
  }
  // Run → PASSES

REFACTOR — Nothing to refactor yet.

─────────────────────────────────────────────────────────
ITERATION 2: Fizz
─────────────────────────────────────────────────────────

RED:
  @Test
  void shouldReturnFizzForMultiplesOfThree() {
      assertEquals("Fizz", service.evaluate(3));
      assertEquals("Fizz", service.evaluate(9));
  }
  // Run → FAILS

GREEN:
  public String evaluate(int n) {
      if (n % 3 == 0) return "Fizz";
      return String.valueOf(n);
  }
  // Run → PASSES

─────────────────────────────────────────────────────────
ITERATION 3: Buzz
─────────────────────────────────────────────────────────

RED:
  @Test
  void shouldReturnBuzzForMultiplesOfFive() {
      assertEquals("Buzz", service.evaluate(5));
      assertEquals("Buzz", service.evaluate(10));
  }
  // Run → FAILS

GREEN:
  public String evaluate(int n) {
      if (n % 3 == 0) return "Fizz";
      if (n % 5 == 0) return "Buzz";
      return String.valueOf(n);
  }

─────────────────────────────────────────────────────────
ITERATION 4: FizzBuzz
─────────────────────────────────────────────────────────

RED:
  @Test
  void shouldReturnFizzBuzzForMultiplesOfBoth() {
      assertEquals("FizzBuzz", service.evaluate(15));
      assertEquals("FizzBuzz", service.evaluate(30));
  }
  // Run → FAILS (returns "Fizz" because 15%3==0 first)

GREEN:
  public String evaluate(int n) {
      if (n % 3 == 0 && n % 5 == 0) return "FizzBuzz";
      if (n % 3 == 0) return "Fizz";
      if (n % 5 == 0) return "Buzz";
      return String.valueOf(n);
  }

REFACTOR — Eliminate duplication:
  public String evaluate(int n) {
      StringBuilder result = new StringBuilder();
      if (n % 3 == 0) result.append("Fizz");
      if (n % 5 == 0) result.append("Buzz");
      return result.length() > 0 ? result.toString() : String.valueOf(n);
  }
  // Run all tests → ALL PASS

4. WHY TDD IMPROVES DESIGN
================================================================

TDD naturally enforces good design principles:

  SINGLE RESPONSIBILITY PRINCIPLE
    Hard-to-test code usually does too much.
    TDD forces you to write small, focused, testable units.

  DEPENDENCY INVERSION
    If your class creates its own dependencies (new Service()),
    it's untestable. TDD forces you to inject dependencies.
    
    Bad (untestable): 
      class OrderService {
          private EmailService emailService = new EmailService(); // hard-coded
      }
    
    Good (TDD-friendly):
      class OrderService {
          private final EmailService emailService;
          
          OrderService(EmailService emailService) {  // injectable
              this.emailService = emailService;
          }
      }

  INTERFACE SEGREGATION
    When you mock dependencies in tests, you realize if an interface
    is too large or has unrelated methods.

  SEPARATION OF CONCERNS
    Testing I/O and business logic separately forces you to keep them apart.

  API USABILITY
    Writing tests first makes you experience the API as a consumer.
    Awkward APIs become obvious before you build the implementation.
    "If it's hard to test, it's hard to use."

5. TDD TYPES (SCHOOLS OF TDD)
================================================================

DETROIT SCHOOL (Classic TDD) — Kent Beck
  - Test the behavior of the system
  - Use real collaborators when possible
  - Mocks only for external dependencies (DB, network, time)
  - Let design emerge from tests
  
  Focus: Making it work, then making it clean

LONDON SCHOOL (Mockist TDD)
  - Mock ALL collaborators
  - Specify interactions between objects
  - Test one object at a time
  - Design is driven by specifying roles/responsibilities
  
  Focus: How objects communicate

HYBRID (most common in practice)
  - Mock external infrastructure (DB, HTTP clients, email)
  - Use real collaborators within the same service layer
  - Balance between isolation and realism

6. TDD BEST PRACTICES
================================================================

ARRANGE-ACT-ASSERT (AAA) / GIVEN-WHEN-THEN
  Every test method should follow this structure:
  
  @Test
  void shouldApplyDiscountForPremiumMember() {
      // GIVEN (Arrange)
      Member member = new Member(MemberTier.PREMIUM);
      Cart cart = new Cart(List.of(new Item("Book", 100.0)));
      DiscountService service = new DiscountService();
      
      // WHEN (Act)
      double finalPrice = service.calculateTotal(member, cart);
      
      // THEN (Assert)
      assertEquals(90.0, finalPrice, 0.001);
  }

ONE ASSERTION PER TEST (generally)
  Tests with multiple unrelated assertions are harder to diagnose.
  When the test fails, you can't tell WHICH assertion failed.
  Exception: multiple assertions about the SAME object are fine.

DESCRIPTIVE TEST NAMES
  Test method name should describe: subject + scenario + expected outcome
  
  // Bad:
  void test1()
  void testCalculate()
  
  // Good:
  void calculateTotal_withPremiumMember_appliesTenPercentDiscount()
  void shouldReturnNotFoundWhenOrderDoesNotExist()
  
  With @DisplayName:
  @DisplayName("Calculate total: premium member gets 10% discount")

NEVER SKIP THE RED STEP
  Always run the test BEFORE writing the code and see it FAIL.
  If it passes immediately, either:
    - The behavior already existed, or
    - Your test is wrong (testing nothing)

SMALL STEPS
  Each TDD iteration should be a tiny increment.
  Resist the urge to implement everything at once.

7. TDD WORKFLOW IN A TEAM
================================================================

Daily TDD workflow:
  Morning: Pull latest code, run all tests (should pass)
  During work: Red → Green → Refactor (many small cycles)
  Before push: Run full test suite
  CI/CD: Automated tests run on every commit

Pair programming + TDD ("Ping-Pong"):
  Developer A writes a failing test
  Developer B writes code to pass it
  Developer B writes the next failing test
  Developer A writes code to pass it
  Repeat — encourages shared ownership

TDD in Sprint:
  Story cards have acceptance criteria
  Write acceptance tests (BDD) from criteria before coding
  Implement until all tests pass
  Story is "done" when tests are green + code is clean

8. TDD BENEFITS (INTERVIEW TALKING POINTS)
================================================================

  1. HIGH TEST COVERAGE BY DEFAULT
     Tests are written before code, so you can't forget to test.
     Coverage is a natural byproduct, not an afterthought.
  
  2. FASTER DEBUGGING
     When a test fails, the failure is small and recent.
     You know exactly WHAT changed and WHERE to look.
  
  3. CONFIDENT REFACTORING
     Green test suite = safety net.
     Change code, run tests, see immediately if anything broke.
  
  4. BETTER DESIGN
     TDD forces loosely coupled, dependency-injected code.
     Hard-to-test code is a design smell caught early.
  
  5. LIVING DOCUMENTATION
     Tests describe expected behavior in executable form.
     More reliable than comments (code can lie, tests fail).
  
  6. REDUCED DEBUGGING TIME
     Studies (Nagappan et al., Microsoft Research) show TDD
     reduces defect density by 40-90% at 15-35% overhead initially.
     Over time, less time debugging = net time savings.

9. TDD CHALLENGES AND MISCONCEPTIONS
================================================================

COMMON MISCONCEPTIONS:

  ❌ "TDD means 100% test coverage"
  ✅ TDD naturally produces high coverage, but the goal is good design
     and confidence, not a coverage percentage.

  ❌ "TDD slows you down"
  ✅ Initially yes, but you spend less time debugging later.
     Roy Osherove says: "Tests are time machines — they let you
     find bugs before users do."

  ❌ "TDD means unit tests only"
  ✅ TDD can be applied at any level: unit, integration, acceptance.
     ATDD (Acceptance TDD) drives development from acceptance criteria.

  ❌ "You can't do TDD with databases/UI"
  ✅ You can! Use embedded DBs, WireMock, or write acceptance tests
     against the real stack in a controlled environment.

GENUINE CHALLENGES:

  - Hard to retrofit TDD into legacy codebases (start with new features)
  - Requires team discipline and culture change
  - Learning curve: writing good tests is a skill
  - Over-mocking can make tests meaningless
  - Tests can encode wrong behavior if requirements are misunderstood

10. ATDD — ACCEPTANCE TEST DRIVEN DEVELOPMENT
================================================================

An extension of TDD where the "first test" is an ACCEPTANCE TEST
derived from the business requirements.

Workflow:
  1. Business, QA, and Developer discuss a user story
  2. They agree on acceptance criteria in Given-When-Then form
  3. QA/Dev write automated acceptance tests from criteria
  4. Tests drive implementation
  5. Story is DONE when acceptance tests pass

ATDD bridges the gap between:
  - Business requirements and technical implementation
  - Developers and business stakeholders

Related: BDD (see 04_BDD_Behavior_Driven_Development.txt)

11. COMMON INTERVIEW QUESTIONS ON TDD
================================================================

Q: What is TDD and how does it work?
A: TDD is a development methodology where you write a failing test first,
   write minimum code to pass it, then refactor. Red → Green → Refactor.
   The goal is both high quality and better design through rapid iteration.

Q: What are the benefits of TDD?
A: High test coverage naturally, confident refactoring, better design
   (forces decoupling), faster debugging (failures are small and recent),
   tests serve as living documentation.

Q: What is the difference between TDD and testing?
A: Testing verifies existing code works. TDD is a DEVELOPMENT technique
   where tests drive the design and implementation. TDD happens BEFORE coding.

Q: Have you used TDD in a real project? What challenges did you face?
A: [Personalize, but mention]: Initial slowdown, resistance from team members
   used to "code first" approach, difficulty testing legacy code, over-mocking
   trap where tests verify mock behavior instead of real behavior.

Q: Can you explain the Red-Green-Refactor cycle?
A: Red: Write a failing test that describes desired behavior.
   Green: Write the simplest code that makes the test pass.
   Refactor: Improve code quality without changing behavior.
   Each cycle is tiny — minutes, not hours.

Q: What is ATDD?
A: Acceptance Test-Driven Development. Tests are written from business
   acceptance criteria before implementation. Bridges business requirements
   and technical code. Often uses BDD-style scenarios (Cucumber/Gherkin).

Q: When would you NOT use TDD?
A: Exploratory/research code where requirements are unknown.
   Very simple CRUD with no business logic.
   Legacy code without proper DI setup (need to refactor first).
   Tight deadlines (though the long-term cost is usually higher without TDD).

Q: How does TDD improve design?
A: Forces dependency injection (can't mock if you new() dependencies).
   Forces single responsibility (untestable = doing too much).
   Forces you to experience the API as a consumer before building it.
   "If it's hard to test, it's a design smell."
