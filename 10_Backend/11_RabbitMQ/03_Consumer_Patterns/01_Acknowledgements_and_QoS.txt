CONSUMER PATTERNS AND ACKNOWLEDGEMENTS
=======================================

=== MESSAGE ACKNOWLEDGEMENT MODES ===

1. AUTO ACKNOWLEDGEMENT (autoAck=true)
   - Message is acknowledged as soon as it is delivered to the consumer
   - Fastest — no round-trip for ack
   - Risk: message lost if consumer crashes before processing
   - Use: fire-and-forget, non-critical tasks

2. MANUAL ACKNOWLEDGEMENT (autoAck=false)
   - Consumer explicitly acknowledges (basicAck) or rejects (basicNack/basicReject)
   - Message stays unacknowledged until ack is sent
   - Unacked messages are redelivered if consumer connection drops
   - Use: all reliable processing scenarios

Manual Ack Commands:
  channel.basicAck(deliveryTag, multiple)
    - deliveryTag: unique ID of the delivery
    - multiple=true: ack all messages up to this tag

  channel.basicNack(deliveryTag, multiple, requeue)
    - requeue=true: message goes back to front of queue (risk of infinite loop!)
    - requeue=false: message is discarded or sent to dead-letter exchange

  channel.basicReject(deliveryTag, requeue)
    - Like basicNack but for single message only

=== PREFETCH / QoS ===

Problem: Slow consumer gets overwhelmed if broker pushes all messages at once.

Solution: channel.basicQos(prefetchCount)
- prefetchCount=1: consumer receives next message only after acking current one
- prefetchCount=10: up to 10 unacked messages at a time
- prefetchCount=0: unlimited (default, can overwhelm consumer)

Best Practice:
- Set prefetchCount to a small number (1–10) for balanced load distribution
- Prevents fast consumers from hoarding all messages while slow ones are idle
- Use per-consumer (channel-level) QoS for fairness

=== CONSUMER PATTERNS ===

1. COMPETING CONSUMERS (Task Queue)
   - Multiple consumers on same queue
   - Messages distributed round-robin (or based on prefetch)
   - Use: parallel task processing, scaling workers

2. PUBLISH/SUBSCRIBE
   - Fanout exchange + multiple queues (one per subscriber)
   - Each subscriber gets a copy of every message
   - Use: event notifications, broadcasting

3. ROUTING (selective consumption)
   - Topic/direct exchange with different routing keys
   - Each consumer queue bound with specific pattern
   - Use: log-level routing, region-based routing

4. RPC (Request/Reply)
   - Producer sends message with reply_to property (temporary queue name)
   - Consumer processes and publishes response to reply_to queue
   - correlation_id used to match request to response
   - Use: synchronous-style communication over async transport

   RPC Flow:
   Client → request queue (with replyTo="amq.rabbitmq.reply-to", correlationId)
   Server → processes → publishes to replyTo queue
   Client → consumes from replyTo queue, matches correlationId

5. PRIORITY QUEUE
   - Queue declared with x-max-priority argument (e.g., 10)
   - Messages published with priority (0–max)
   - Higher priority messages consumed first
   - Use: urgent task processing

=== CONSUMER CANCELLATION ===

- Consumers can be cancelled: channel.basicCancel(consumerTag)
- Broker sends ConsumerCancellation notification if queue is deleted
- Implement handleCancelOk() to gracefully handle cancellation

=== FLOW CONTROL ===

- RabbitMQ uses TCP back-pressure if a consumer is slow
- If queue grows too large, broker applies credit-based flow control
- Producers may be blocked if memory/disk watermark is reached
- Monitor via management UI or via blocked-connection notifications

=== DEAD LETTER EXCHANGE (DLX) ===

Messages are dead-lettered when:
- basicNack/basicReject with requeue=false
- Message TTL expires
- Queue is full (max-length reached with overflow=reject-publish)

Set via queue argument:
  x-dead-letter-exchange: "dlx-exchange"
  x-dead-letter-routing-key: "dead" (optional)

Dead-lettered messages get headers added:
  x-death: array with reason, count, time, queue name

Use case: inspect failed messages, retry with backoff, alerting
