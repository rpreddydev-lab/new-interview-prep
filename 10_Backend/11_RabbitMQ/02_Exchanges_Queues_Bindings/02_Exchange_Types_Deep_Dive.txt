DIRECT, FANOUT, TOPIC, HEADERS EXCHANGES — DEEP DIVE
======================================================

=== DIRECT EXCHANGE — DEEP DIVE ===

Scenario: Order processing system
- Exchange: "order-exchange" (direct)
- Queue 1: "order-new"      bound with key "new"
- Queue 2: "order-shipped"  bound with key "shipped"
- Queue 3: "order-cancelled" bound with key "cancelled"

Producer publishes with routingKey="new" → only "order-new" queue receives it

Multiple bindings with same key = load balancing:
- Two consumers on same queue = round-robin delivery
- Two queues with same routing key = both queues receive the message

=== FANOUT EXCHANGE — DEEP DIVE ===

Scenario: User registration event broadcast
- Exchange: "user-events" (fanout)
- Bound queues: "email-service-queue", "analytics-queue", "welcome-bonus-queue"

All queues receive a copy when any message is published — routing key ignored.
Each service processes independently.

Fan-out = horizontal scaling + loose coupling

=== TOPIC EXCHANGE — DEEP DIVE ===

Routing key format: dot-separated words (e.g., "region.service.event")

Wildcard rules:
- * matches exactly ONE word
- # matches ZERO or MORE words

Examples:
  Binding key         | Matches                     | Does NOT match
  "us.*.*"            | "us.orders.created"         | "eu.orders.created"
  "*.orders.*"        | "us.orders.created"         | "us.orders.v2.created"
  "us.#"              | "us.anything.at.all"        | "eu.anything"
  "#.created"         | "us.orders.created"         | "us.orders.updated"
  "#"                 | everything                  | -

Use case: Multi-region event routing
- us.orders.created → us-order-processor
- *.orders.*        → global-audit-queue
- #.failed          → alerting-queue

=== HEADERS EXCHANGE — DEEP DIVE ===

Instead of routing key, matches on message headers (key-value pairs):

Example:
  Queue binding args: {"format": "pdf", "type": "report", "x-match": "all"}
  Message headers:    {"format": "pdf", "type": "report"}  → MATCH
  Message headers:    {"format": "pdf", "type": "summary"} → NO MATCH (all required)

x-match: "any" → at least one header must match
x-match: "all" → all specified headers must match

Less commonly used — topic exchange handles most routing needs.

=== CHOOSING THE RIGHT EXCHANGE ===

Need                                       → Exchange Type
-------------------------------------------+--------------
Route to specific worker/service           → Direct
Broadcast to all subscribers               → Fanout
Pattern-based routing (regions, levels)    → Topic
Route based on message content/metadata   → Headers
Simple point-to-point (default exchange)  → Direct (default)

=== EXCHANGE TO EXCHANGE ROUTING ===

RabbitMQ supports binding an exchange to another exchange:
Exchange A → binding → Exchange B → Queue

Useful for:
- Hierarchical routing
- Adding a fanout stage before topic routing
- Modular routing without changing producers

=== DEFAULT EXCHANGE ===

- Name: "" (empty string)
- Type: direct
- Cannot be deleted or modified
- Every queue is automatically bound to it with the queue name as routing key

Usage: channel.basicPublish("", "myQueueName", null, message.getBytes())
This publishes directly to "myQueueName" queue — convenient for simple cases.
