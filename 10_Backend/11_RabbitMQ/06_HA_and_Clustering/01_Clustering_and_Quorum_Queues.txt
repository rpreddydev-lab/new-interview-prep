RABBITMQ HIGH AVAILABILITY AND CLUSTERING
==========================================

=== CLUSTERING ===

RabbitMQ Cluster:
- Multiple nodes share metadata (exchanges, queues, policies, users)
- Queues by default exist on ONE node (the declaring node)
- Classic mirrored queues: deprecated in 3.x — use Quorum Queues instead

Quorum Queues (Recommended):
- Replicated across majority of nodes using Raft
- Tolerates (N-1)/2 node failures
- Recommended for 3 or 5 node clusters
- Must be declared as: x-queue-type: quorum

Forming a cluster:
  Node 1: rabbitmq-server start
  Node 2: rabbitmqctl stop_app
          rabbitmqctl join_cluster rabbit@node1
          rabbitmqctl start_app

=== LOAD BALANCING ===

- Use HAProxy or a load balancer in front of RabbitMQ nodes
- Clients connect to LB → distributed across nodes
- Queue data lives on specific node — LB routes internally

=== SHOVEL AND FEDERATION ===

Federation:
- Links brokers in different data centers
- Messages are forwarded from upstream to downstream
- Good for WAN replication with high latency tolerance

Shovel:
- Continuously moves/copies messages from source to destination queue
- Within same broker or across brokers
- Useful for queue draining, migration, bridging

=== POLICIES ===

Policies apply settings to queues/exchanges matching a pattern:
- Applied dynamically without queue re-declaration
- Override queue/exchange arguments

Example policy (via CLI):
  rabbitmqctl set_policy ha-all "^ha\." '{"ha-mode":"all"}' \
    --apply-to queues

Common policy parameters:
  ha-mode, ha-sync-mode, message-ttl, max-length, dead-letter-exchange

=== FLOW CONTROL AND ALARMS ===

Memory alarm: triggered when broker uses > memory-high-watermark (default 40%)
Disk alarm:   triggered when free disk < disk-free-limit

When alarm triggered:
- All producer connections are blocked
- Consumers continue working (drain queues)
- Resume after resource freed

Monitor alarms:
  rabbitmqctl status | grep alarm
  Management UI: Overview tab shows blocked connections

=== RABBITMQ INTERVIEW QUESTIONS ===

Q: What happens to messages if RabbitMQ node restarts?
A: Transient messages (delivery_mode=1) are lost. Persistent messages (delivery_mode=2)
   in durable queues survive. Quorum queues provide best durability across restarts.

Q: What is the difference between exclusive and auto-delete queues?
A: Exclusive: only one connection can use it; deleted when connection closes.
   Auto-delete: deleted when last consumer unsubscribes.

Q: How do you prevent message loss in RabbitMQ?
A: 1) Use durable queues, 2) Publish persistent messages (delivery_mode=2),
   3) Use publisher confirms, 4) Use manual acks on consumers,
   5) Use Quorum queues for replication.

Q: What is publisher confirm?
A: Asynchronous ack from broker to producer that message was received and
   persisted. Enabled via channel.confirmSelect(). Prevents data loss on
   producer side. RabbitTemplate can be configured with publisherConfirmType.

Q: How do you scale RabbitMQ consumers?
A: Increase consumer count on same queue (competing consumers).
   Use prefetchCount to ensure fair dispatch. Scale instances horizontally.

Q: What is a vHost?
A: Virtual host — logical isolation within one broker. Separate namespaces
   for exchanges, queues, users, permissions. Default is "/".

Q: How does RabbitMQ differ from Kafka for event sourcing?
A: RabbitMQ deletes messages after consumption — no replay capability.
   Kafka retains messages for configurable period — supports replay,
   event sourcing, multiple consumer groups reading independently.
   Use Kafka for event sourcing; use RabbitMQ for task queues.

Q: What are Quorum Queues and why prefer them over classic mirrored?
A: Quorum queues use Raft consensus for replication — better data safety,
   predictable failover. Classic mirrored queues had split-brain issues
   and are deprecated in RabbitMQ 3.x.
