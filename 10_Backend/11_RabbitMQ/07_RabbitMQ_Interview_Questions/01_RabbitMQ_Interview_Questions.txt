RABBITMQ INTERVIEW QUESTIONS
==============================

=== CORE CONCEPTS ===

Q: What is RabbitMQ and what problem does it solve?
A: RabbitMQ is an open-source message broker implementing AMQP. It decouples
   producers from consumers, allowing asynchronous communication. Producers
   don't need to know who consumes their messages, and consumers can process
   at their own pace.

Q: Explain the AMQP model: producer, exchange, queue, consumer.
A: Producer sends messages to an exchange. Exchange routes messages to queues
   based on bindings and routing keys. Queues buffer messages. Consumers
   read and process messages from queues.

Q: What are the 4 exchange types?
A: Direct (exact routing key match), Fanout (broadcast to all bound queues),
   Topic (wildcard pattern matching: * = one word, # = zero or more words),
   Headers (route based on message headers, not routing key).

Q: What is a binding?
A: A rule that connects an exchange to a queue, optionally with a routing key.
   When a message arrives at the exchange, bindings determine which queues
   receive the message.

=== DELIVERY AND RELIABILITY ===

Q: What is the difference between auto-ack and manual-ack?
A: Auto-ack: message acknowledged as soon as delivered (risk of loss if consumer
   crashes). Manual-ack: consumer explicitly sends basicAck after successful
   processing — guarantees at-least-once delivery.

Q: What happens when basicNack with requeue=true?
A: Message is returned to the front of the queue and immediately redelivered.
   Risk: infinite loop if processing always fails (poison message). Prefer
   requeue=false + DLX for proper retry/dead-letter handling.

Q: What is a Dead Letter Exchange (DLX)?
A: An exchange that receives messages that are rejected, expired, or dropped
   due to queue overflow. Configured via x-dead-letter-exchange argument.
   Used for error handling, retry with backoff, poison message isolation.

Q: How do you implement retry with exponential backoff in RabbitMQ?
A: Use a chain of dead-letter queues with increasing TTL:
   main-queue → DLX → wait-30s-queue (TTL=30s) → DLX → main-queue
   After N retries (check x-death count), dead-letter to permanent DLQ.

Q: What is prefetchCount and why is it important?
A: Prefetch (QoS) limits how many unacknowledged messages a consumer can hold.
   prefetchCount=1 ensures fair dispatch — consumer gets next message only after
   acking the current one. Prevents fast consumers from hoarding work.

Q: What is a publisher confirm?
A: Asynchronous acknowledgement from the broker to the producer that a message
   was durably received. Ensures no data loss on producer side. Enabled via
   channel.confirmSelect(). Spring RabbitTemplate supports it natively.

=== ADVANCED TOPICS ===

Q: What are Quorum Queues?
A: Quorum queues are replicated queues using Raft consensus across multiple nodes.
   They tolerate (N-1)/2 node failures in a cluster. Preferred over deprecated
   classic mirrored queues for durability. Declared with x-queue-type: quorum.

Q: How does RabbitMQ handle high availability?
A: Use a cluster with Quorum queues. All nodes share metadata; queue data is
   replicated. Use a load balancer in front. In case of node failure, Raft
   elects a new leader for quorum queues automatically.

Q: What is a vHost in RabbitMQ?
A: Virtual host provides logical isolation within one broker — separate
   namespaces for exchanges, queues, users, and permissions. Used for
   multi-tenancy or environment separation.

Q: How do you implement RPC with RabbitMQ?
A: Producer publishes to RPC queue with reply_to="amq.rabbitmq.reply-to" and
   correlationId=UUID. Server processes and publishes response to reply_to queue
   with same correlationId. Client correlates response to request.
   Spring: RabbitTemplate.convertSendAndReceive() handles this automatically.

Q: What is the difference between RabbitMQ Streams and classic queues?
A: Streams (RabbitMQ 3.9+) are append-only logs with persistent retention,
   allowing multiple consumers to replay. Like Kafka topics within RabbitMQ.
   Classic queues delete messages after consumption.

Q: When would you NOT use RabbitMQ?
A: When you need message replay (use Kafka). When you need extremely high
   throughput — millions/sec (use Kafka). When you need long-term event
   storage for event sourcing (use Kafka or EventStore).

Q: How does Spring AMQP simplify RabbitMQ usage?
A: RabbitTemplate for sending, @RabbitListener for consuming, RabbitAdmin for
   auto-declaring infrastructure, Jackson2JsonMessageConverter for serialization,
   RetryTemplate for retry logic — all configured declaratively.

Q: What is a Shovel in RabbitMQ?
A: A plugin that continuously moves messages from a source queue/exchange to a
   destination, within the same broker or across brokers. Used for migration,
   bridging environments, or draining queues.
