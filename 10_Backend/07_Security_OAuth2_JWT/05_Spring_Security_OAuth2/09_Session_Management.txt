======================================================
SPRING SECURITY — SESSION MANAGEMENT
======================================================

1. STATELESS vs STATEFUL SESSIONS
──────────────────────────────────
Stateful (Session-based):
  - Server stores session in memory or Redis
  - Client holds a JSESSIONID cookie
  - Pros: easy invalidation, full control
  - Cons: sticky sessions needed or shared store, scales poorly

Stateless (Token-based / JWT):
  - No server-side session; JWT in Authorization header or cookie
  - Pros: horizontally scalable, no shared state
  - Cons: token revocation is complex

Spring Boot config for stateless REST APIs:
  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
      http.sessionManagement(sm -> sm
              .sessionCreationPolicy(SessionCreationPolicy.STATELESS));
      return http.build();
  }

SessionCreationPolicy options:
  - STATELESS    → never create or use HTTP session
  - ALWAYS       → always create session
  - IF_REQUIRED  → create only when needed (default)
  - NEVER        → never create but will use existing if present


2. SPRING SESSION (DISTRIBUTED SESSION STORE)
─────────────────────────────────────────────
Used when stateful sessions are required but app is clustered.

Dependency:
  spring-session-data-redis

Config:
  @EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800)

application.yml:
  spring:
    session:
      store-type: redis
      redis:
        flush-mode: on-save
        namespace: spring:session

How it works:
  - JSESSIONID is backed by Redis
  - Any node can serve the session
  - Session is automatically serialized/deserialized

Key beans:
  - RedisIndexedSessionRepository
  - SessionRepositoryFilter (intercepts all requests)


3. SESSION FIXATION PROTECTION
───────────────────────────────
Attack: attacker sets a known session ID before login; after login, same ID is used.

Spring Security protection (default: changeSessionId):
  http.sessionManagement(sm -> sm
      .sessionFixation().changeSessionId()); // default in Servlet containers
  // alternatives: newSession(), migrateSession(), none()

changeSessionId → only changes the session ID, preserves attributes
newSession      → creates a new session, loses attributes


4. CONCURRENT SESSION CONTROL
──────────────────────────────
Limit the number of sessions per user:
  http.sessionManagement(sm -> sm
      .maximumSessions(1)
      .maxSessionsPreventsLogin(false) // false = new login kicks out old session
      .sessionRegistry(sessionRegistry()));

  @Bean
  public SessionRegistry sessionRegistry() {
      return new SessionRegistryImpl();
  }

maxSessionsPreventsLogin(true) → new login is rejected if limit reached


5. REMEMBER-ME (PERSISTENT SESSIONS)
──────────────────────────────────────
Two strategies:
  a) Simple hash-based token (default): stores username+expiry+hash in cookie
  b) Persistent token: stores token in DB (more secure, can be invalidated)

  http.rememberMe(rm -> rm
      .tokenRepository(persistentTokenRepository())
      .tokenValiditySeconds(86400 * 7));

  @Bean
  public PersistentTokenRepository persistentTokenRepository() {
      JdbcTokenRepositoryImpl repo = new JdbcTokenRepositoryImpl();
      repo.setDataSource(dataSource);
      return repo;
  }


6. SESSION EXPIRY AND TIMEOUT
──────────────────────────────
application.yml:
  server:
    servlet:
      session:
        timeout: 30m   # session timeout

Handle expired sessions:
  http.sessionManagement(sm -> sm
      .invalidSessionUrl("/session-expired"));

Or with concurrent session control:
  .expiredUrl("/session-expired");


7. INTERVIEW QUESTIONS
──────────────────────
Q: How does Spring Security handle sessions in a microservices architecture?
A: Typically STATELESS — each request carries a JWT or opaque token validated
   by the resource server. No server-side session is created.

Q: What is the difference between SessionCreationPolicy.STATELESS and NEVER?
A: STATELESS never creates or uses a session (truly stateless).
   NEVER won't create a session but WILL use one if it already exists.

Q: How do you invalidate all sessions for a user (e.g., password change)?
A: With Spring Session + Redis: iterate sessionRegistry or use
   SessionRepository.deleteById(). With JWT: maintain a token blacklist or
   rotate signing keys (short-lived tokens + refresh token revocation).

Q: What is session fixation and how does Spring Security prevent it?
A: Attacker plants a known session ID before user logs in.
   Spring Security by default calls changeSessionId() after authentication
   to generate a new session ID, preventing the attack.
