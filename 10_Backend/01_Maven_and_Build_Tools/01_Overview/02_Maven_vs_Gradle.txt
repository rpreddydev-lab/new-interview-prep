================================================================================
  MAVEN vs GRADLE — DETAILED COMPARISON
================================================================================

PHILOSOPHY
──────────
  Maven   → Declarative, convention-over-configuration. You declare WHAT you
             want; Maven provides the HOW via its lifecycle and plugins.
             Strict rules, less flexibility, more predictability.

  Gradle  → Declarative + imperative hybrid. You can follow conventions BUT
             also write custom Groovy/Kotlin code for anything not covered.
             More power, more rope to hang yourself with.

─────────────────────────────────────────────────────────────────────────────────
CONFIGURATION FORMAT
─────────────────────────────────────────────────────────────────────────────────

  Maven — pom.xml (XML)
  ─────────────────────
  <?xml version="1.0" encoding="UTF-8"?>
  <project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <version>3.2.0</version>
      </dependency>
    </dependencies>
  </project>

  Gradle — build.gradle (Groovy DSL)
  ────────────────────────────────────
  plugins {
      id 'java'
      id 'org.springframework.boot' version '3.2.0'
  }

  dependencies {
      implementation 'org.springframework.boot:spring-boot-starter-web'
  }

  Gradle — build.gradle.kts (Kotlin DSL) — preferred for type safety
  ────────────────────────────────────────────────────────────────────
  plugins {
      java
      id("org.springframework.boot") version "3.2.0"
  }

  dependencies {
      implementation("org.springframework.boot:spring-boot-starter-web")
  }

─────────────────────────────────────────────────────────────────────────────────
PERFORMANCE
─────────────────────────────────────────────────────────────────────────────────

  Feature               Maven             Gradle
  ──────────────────── ──────────────── ──────────────────────────────
  Incremental builds    Limited           Full (only re-runs changed tasks)
  Build cache           No                Yes (local + remote cache)
  Parallel execution    Limited           First-class support
  Daemon                No                Yes (keeps JVM warm between builds)
  Configuration cache   No                Yes (Gradle 7.4+)
  Typical large project 5–15 min          1–3 min (with cache hit: seconds)

  Real-world example: A large Android project with 200+ modules builds in
  ~2 min with Gradle (cache hit) vs would take 15+ min if done with Maven.

─────────────────────────────────────────────────────────────────────────────────
DEPENDENCY MANAGEMENT
─────────────────────────────────────────────────────────────────────────────────

  Maven:
  • Uses <dependencyManagement> section for version control
  • BOM (Bill of Materials) via <scope>import</scope>
  • Conflict resolution: "nearest wins" — shortest path in dependency tree
  • Well-understood, deterministic behavior

  Gradle:
  • Uses resolutionStrategy for conflict resolution
  • Supports platforms() which are the Gradle equivalent of BOMs
  • Default conflict resolution: highest version wins
  • More flexible but can lead to surprising version selections

  Example — BOM in Maven:
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>3.2.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  Example — Platform in Gradle:
  implementation(platform("org.springframework.boot:spring-boot-dependencies:3.2.0"))

─────────────────────────────────────────────────────────────────────────────────
MULTI-MODULE PROJECTS
─────────────────────────────────────────────────────────────────────────────────

  Maven:
  • Parent POM aggregates child modules via <modules> element
  • Each child inherits from parent via <parent> block
  • Reactor build: Maven builds modules in the correct order automatically
  • Command: mvn -pl module-a,module-b -am install

  <!-- parent pom.xml -->
  <modules>
    <module>service-api</module>
    <module>service-impl</module>
    <module>service-web</module>
  </modules>

  Gradle:
  • settings.gradle (or settings.gradle.kts) declares included subprojects
  • Compound builds supported via includeBuild()
  • Fine-grained task dependencies between modules

  // settings.gradle
  include ':service-api', ':service-impl', ':service-web'

LIFECYCLE COMPARISON
─────────────────────────────────────────────────────────────────────────────────

  Maven (fixed lifecycle phases)          Gradle (task graph, no fixed order)
  ─────────────────────────────────────── ──────────────────────────────────────
  validate                                compileJava
  compile                                 processResources
  test                                    classes
  package                                 compileTestJava
  verify                                  test
  install                                 jar
  deploy                                  build (depends on all above)

  Maven: phases are always sequential and ordered
  Gradle: tasks declare explicit dependencies, forming a DAG (Directed Acyclic Graph)

─────────────────────────────────────────────────────────────────────────────────
WHEN TO CHOOSE WHICH
─────────────────────────────────────────────────────────────────────────────────

  Choose MAVEN when:
  ✔ Working in an enterprise Java shop with existing Maven infrastructure
  ✔ Team is more comfortable with XML / less programming
  ✔ Need maximum predictability and auditability
  ✔ Using a corporate Nexus/Artifactory that's Maven-centric
  ✔ Building Spring Boot apps via Spring Initializr defaults
  ✔ Regulatory compliance requires reproducible, auditable builds

  Choose GRADLE when:
  ✔ Build performance is critical (large monorepo, many modules)
  ✔ Building Android apps (Google mandates Gradle)
  ✔ Complex custom build logic needed
  ✔ Teams want type-safe build scripts (Kotlin DSL)
  ✔ Need incremental compilation and build caching
  ✔ Using Kotlin-first frameworks (Kotlin, KMP)

SIDE-BY-SIDE COMMAND COMPARISON
─────────────────────────────────────────────────────────────────────────────────

  Task                    Maven command               Gradle command
  ─────────────────────── ─────────────────────────── ────────────────────────
  Clean build output      mvn clean                   gradle clean
  Compile                 mvn compile                 gradle compileJava
  Run tests               mvn test                    gradle test
  Package artifact        mvn package                 gradle jar (or assemble)
  Skip tests              mvn package -DskipTests     gradle build -x test
  Install locally         mvn install                 gradle publishToMavenLocal
  Dependency tree         mvn dependency:tree         gradle dependencies
  Show effective config   mvn help:effective-pom      gradle properties
  Run specific module     mvn -pl module -am install  gradle :module:build

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the main philosophical difference between Maven and Gradle?
A: Maven is purely declarative (you describe the project, Maven decides how to
   build it using a fixed lifecycle). Gradle is hybrid — it supports convention-
   based builds but also allows imperative, task-based build logic via
   Groovy/Kotlin code.

Q: Why is Gradle faster than Maven?
A: Gradle provides: (1) incremental builds — only tasks with changed inputs/
   outputs re-run, (2) a build cache — task outputs are cached locally and
   remotely so the same work is never done twice, (3) a persistent daemon
   keeping the JVM warm, (4) parallel task execution, and (5) configuration
   cache (Gradle 7.4+). Maven rebuilds everything by default each time.

Q: Can Maven and Gradle use the same repositories?
A: Yes. Both can use Maven Central, and both can talk to corporate artifact
   repositories like Nexus or Artifactory. Gradle resolves Maven POM files
   natively, so artifacts published from Maven are fully consumable in Gradle.

Q: What is the Gradle wrapper (gradlew) and why use it?
A: The Gradle Wrapper (gradle/wrapper/gradle-wrapper.properties + gradlew script)
   pins the Gradle version to the project. Anyone cloning the repo builds with
   exactly the right Gradle version without installing Gradle globally. Same
   concept as Maven Wrapper (mvnw).

Q: How does conflict resolution differ between Maven and Gradle?
A: Maven uses "nearest wins" — the version closest to the project root in the
   dependency tree wins. Gradle uses "highest version wins" by default, but this
   can be overridden with resolutionStrategy. Gradle's approach avoids accidental
   downgrades but can surface incompatibilities.
