================================================================================
  DEPENDENCY CONFLICTS — DETECTION, RESOLUTION STRATEGIES
================================================================================

WHAT IS A DEPENDENCY CONFLICT?
────────────────────────────────
A conflict occurs when two or more dependencies transitively require
different versions of the same artifact.

Example:
  Your project depends on:
    A → depends on guava:30.0
    B → depends on guava:32.0

  Both A and B need guava, but at different versions.
  Only ONE version can be on the classpath at runtime.

─────────────────────────────────────────────────────────────────────────────────
MAVEN CONFLICT RESOLUTION — "NEAREST WINS"
─────────────────────────────────────────────────────────────────────────────────

  Maven picks the version CLOSEST to the root of the dependency tree (fewest hops).

  Example dependency tree:
  ─────────────────────────
  your-app
  ├── A (direct dep, depth 1) → guava:30.0     ← depth 2 from root
  └── B (direct dep, depth 1) → guava:32.0     ← depth 2 from root

  When both are at the same depth, Maven picks whichever appears FIRST in pom.xml.
  → guava:30.0 wins (A declared before B in pom.xml)

  To override — declare the desired version as a direct dependency (depth 1 = nearest):
  ─────────────────────────────────────────────────────────────────────────────────────
  <dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
    <version>32.0-jre</version>   <!-- depth 1; beats all transitives -->
  </dependency>

  OR use <dependencyManagement> (does not add to classpath, just pins version):
  ─────────────────────────────────────────────────────────────────────────────
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.google.guava</groupId>
        <artifactId>guava</artifactId>
        <version>32.0-jre</version>
      </dependency>
    </dependencies>
  </dependencyManagement>

  With <dependencyManagement>: version is enforced for all instances in the tree,
  including transitives. This is the preferred approach.

─────────────────────────────────────────────────────────────────────────────────
GRADLE CONFLICT RESOLUTION — "HIGHEST WINS"
─────────────────────────────────────────────────────────────────────────────────

  Gradle picks the HIGHEST version of any requested version in the graph.
  This is generally safer than Maven's nearest-wins approach.

  A → guava:30.0
  B → guava:32.0
  → Gradle selects guava:32.0 automatically ✅

  When to override:
  • Security: a newer version has a vulnerability
  • Compatibility: higher version breaks the consumer

  Force a specific version in Gradle:
  ─────────────────────────────────────
  // Option 1: strictly — hard requirement (fails if incompatible)
  dependencies {
      implementation("com.google.guava:guava") {
          version { strictly("31.1-jre") }
      }
  }

  // Option 2: force on resolutionStrategy (global)
  configurations.all {
      resolutionStrategy {
          force("com.google.guava:guava:31.1-jre")
      }
  }

  // Option 3: dependencySubstitution (replace one with another)
  configurations.all {
      resolutionStrategy.dependencySubstitution {
          substitute(module("com.google.guava:guava:30.0"))
              .using(module("com.google.guava:guava:32.0-jre"))
      }
  }

─────────────────────────────────────────────────────────────────────────────────
DETECTING CONFLICTS
─────────────────────────────────────────────────────────────────────────────────

  Maven — detect version convergence issues:
  ───────────────────────────────────────────
  # Shows all versions including omitted (conflicting) ones
  mvn dependency:tree -Dverbose

  # dependencyConvergence enforcer rule — fails build if convergence issues
  <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <executions>
      <execution>
        <goals><goal>enforce</goal></goals>
        <configuration>
          <rules>
            <dependencyConvergence/>
          </rules>
        </configuration>
      </execution>
    </executions>
  </plugin>

  # See why a specific version was chosen
  mvn dependency:tree -Dincludes=com.google.guava:guava -Dverbose

  Gradle — detect and investigate conflicts:
  ───────────────────────────────────────────
  # See why a version was selected (shows selection reason + path)
  ./gradlew dependencyInsight \
      --dependency guava \
      --configuration runtimeClasspath

  # Fail build on any version conflict (strict mode)
  configurations.all {
      resolutionStrategy { failOnVersionConflict() }
  }

  # Fail on dynamic versions in production
  configurations.all {
      resolutionStrategy { failOnDynamicVersions() }
  }

─────────────────────────────────────────────────────────────────────────────────
COMMON REAL-WORLD CONFLICTS
─────────────────────────────────────────────────────────────────────────────────

  Conflict Scenario                    Resolution
  ──────────────────────────────────── ──────────────────────────────────────────
  Multiple logging implementations     Exclude all but one; use SLF4J bridges
  (logback + log4j + commons-logging)  mvn dependency:tree to find sources

  Spring version mismatch              Use spring-boot-dependencies BOM;
  (spring-core:5.x vs 6.x)            never declare Spring versions manually

  Jackson version mismatch             Use jackson-bom or Spring Boot's BOM;
  (core:2.14 vs annotations:2.16)      never mix Jackson module versions

  Servlet API mismatch                 Use compileOnly/provided scope for servlet API;
  (javax.servlet vs jakarta.servlet)   choose one namespace (Java EE vs Jakarta EE)

  Guava version conflict               Pin in <dependencyManagement> or BOM import;
                                       often safe to use the highest version

  SLF4J conflict (1.7 vs 2.0)         All SLF4J modules must be same version;
                                       pin all in <dependencyManagement>

─────────────────────────────────────────────────────────────────────────────────
LOGGING FRAMEWORK CONFLICT — CLASSIC EXAMPLE
─────────────────────────────────────────────────────────────────────────────────

  Problem: commons-logging, log4j:log4j, and logback all on classpath.
           Multiple SLF4J bindings cause runtime error.

  Solution with Maven:
  ─────────────────────
  <!-- 1. Exclude legacy logging from every dependency that brings it in -->
  <dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <exclusions>
      <exclusion>
        <groupId>commons-logging</groupId>
        <artifactId>commons-logging</artifactId>
      </exclusion>
    </exclusions>
  </dependency>

  <!-- 2. Replace with SLF4J bridge -->
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>jcl-over-slf4j</artifactId>
    <version>2.0.9</version>
  </dependency>

  <!-- 3. Use one SLF4J binding -->
  <dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.4.14</version>
  </dependency>

  Spring Boot handles this automatically via spring-boot-starter-logging.

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between Maven's and Gradle's default conflict resolution?
A: Maven uses "nearest-wins" — the version declared closest to the project root
   in the dependency tree wins. Gradle uses "highest-wins" — the highest version
   requested anywhere in the dependency graph wins. Gradle's approach is generally
   safer (you get the newest compatible version). Maven's can silently downgrade
   a dependency if a direct dependency declares an older version.

Q: How do you force a specific version of a transitive dependency in Maven?
A: Two approaches: (1) Declare the dependency directly (at depth 1) — Maven's
   nearest-wins picks it over any transitive. (2) Use <dependencyManagement> to
   pin the version across the entire project without adding it to the classpath.
   <dependencyManagement> is preferred because it's explicit about intent and
   applies to all modules in a multi-module project.

Q: What is the dependencyConvergence Maven Enforcer rule?
A: It's a rule in the maven-enforcer-plugin that fails the build if any dependency
   is resolved at different versions across different paths in the dependency tree.
   For example, if path A requires guava:30 and path B requires guava:32, Maven
   silently picks one, but with dependencyConvergence the build fails until you
   explicitly pin the version. Forces intentional version management.

Q: How do you investigate why a specific version of a dependency was selected?
A: Maven: mvn dependency:tree -Dverbose -Dincludes=group:artifact — shows all
   versions including omitted ones and which was selected.
   Gradle: ./gradlew dependencyInsight --dependency <name> --configuration <config>
   — shows the full selection reason including which rule forced the version.
