  GRADLE TASKS — DEFINITION, TYPES, DEPENDENCIES, AND LIFECYCLE

WHAT IS A GRADLE TASK?
───────────────────────
A task is the fundamental unit of work in Gradle. Everything Gradle does is
a task: compiling Java, running tests, creating JARs, publishing artifacts.

Tasks have:
  • Actions        — code that runs (doFirst / doLast blocks)
  • Inputs         — files, directories, properties the task reads
  • Outputs        — files, directories the task produces
  • Dependencies   — other tasks that must run first
  • Type           — built-in task type (Copy, Exec, Jar, Test, etc.)

─────────────────────────────────────────────────────────────────────────────────
LISTING TASKS
─────────────────────────────────────────────────────────────────────────────────

  ./gradlew tasks                    # main tasks grouped by category
  ./gradlew tasks --all              # every task including internal ones
  ./gradlew help --task test         # details about a specific task
  ./gradlew :module:tasks            # tasks for a specific subproject

BUILT-IN LIFECYCLE TASKS (Java Plugin)
─────────────────────────────────────────────────────────────────────────────────

  Task              Depends On                  Description
  ───────────────── ─────────────────────────── ──────────────────────────────
  assemble          jar (and others)             Build outputs without running tests
  build             assemble + check             Full build
  check             test                         Run all verification tasks
  clean             —                            Delete build/ directory
  compileJava       —                            Compile main Java sources
  processResources  —                            Copy main resources to build/
  classes           compileJava + processResources  Compile + resources
  compileTestJava   classes                      Compile test sources
  processTestResources —                         Copy test resources
  testClasses       compileTestJava + processTestResources
  test              testClasses                  Run unit tests
  jar               classes                      Create the JAR file
  javadoc           classes                      Generate Javadoc
  publishToMavenLocal jar                        Install to ~/.m2 (like mvn install)

─────────────────────────────────────────────────────────────────────────────────
DEFINING CUSTOM TASKS
─────────────────────────────────────────────────────────────────────────────────

  Style 1 — tasks.register (PREFERRED — lazy evaluation):
  ─────────────────────────────────────────────────────────
  tasks.register("greet") {
      description = "Prints a greeting"
      group = "custom"
      doLast {
          println("Hello, Gradle!")
      }
  }

  Style 2 — tasks.register with typed task:
  ──────────────────────────────────────────
  tasks.register<Copy>("copyDocs") {
      description = "Copy documentation to build dir"
      group = "documentation"
      from("src/docs")
      into(layout.buildDirectory.dir("docs"))
      include("**/*.md", "**/*.html")
  }

  Style 3 — tasks.create (EAGER — avoid for performance):
  ─────────────────────────────────────────────────────────
  // Triggers configuration for ALL tasks, even ones not being run.
  // Use tasks.register instead.
  tasks.create("eagerTask") {
      doLast { println("Eager") }
  }

  Style 4 — Reusable task class:
  ──────────────────────────────
  abstract class GenerateReport : DefaultTask() {
      @get:InputFile
      abstract val inputFile: RegularFileProperty

      @get:OutputFile
      abstract val outputFile: RegularFileProperty

      @TaskAction
      fun generate() {
          val input = inputFile.asFile.get().readText()
          outputFile.asFile.get().writeText("Report: $input")
      }
  }

  tasks.register<GenerateReport>("generateReport") {
      inputFile.set(layout.projectDirectory.file("data.json"))
      outputFile.set(layout.buildDirectory.file("report.txt"))
  }

─────────────────────────────────────────────────────────────────────────────────
TASK ACTIONS — doFirst AND doLast
─────────────────────────────────────────────────────────────────────────────────

  tasks.test {
      doFirst {
          println("Starting tests in environment: ${System.getenv("ENV") ?: "local"}")
      }
      doLast {
          println("Tests completed.")
      }
  }

  Multiple doFirst/doLast blocks are allowed — they are queued in order.
  doFirst blocks run before the task's main action.
  doLast blocks run after the task's main action.

─────────────────────────────────────────────────────────────────────────────────
TASK DEPENDENCIES
─────────────────────────────────────────────────────────────────────────────────

  Method 1 — dependsOn:
  ──────────────────────
  tasks.register("deployApp") {
      dependsOn("build", "runMigrations")
      doLast { println("Deploying...") }
  }

  Method 2 — mustRunAfter (does NOT create a dependency, just ordering):
  ────────────────────────────────────────────────────────────────────────
  tasks.test {
      mustRunAfter(tasks.named("integrationTest"))
  }
  // If both are requested, test runs after integrationTest
  // But running just 'test' alone does NOT trigger integrationTest

  Method 3 — finalizedBy:
  ────────────────────────
  tasks.test {
      finalizedBy(tasks.jacocoTestReport)
  }
  // jacocoTestReport always runs after test, even if test fails

  Method 4 — shouldRunAfter (weak ordering, can be violated):
  ─────────────────────────────────────────────────────────────
  tasks.build {
      shouldRunAfter(tasks.clean)
  }

  Dependency via task output:
  ────────────────────────────
  val generateSources = tasks.register<JavaExec>("generateSources") {
      mainClass.set("com.example.CodeGen")
      classpath = configurations.runtimeClasspath.get()
      outputs.dir(layout.buildDirectory.dir("generated-sources"))
  }

  tasks.compileJava {
      dependsOn(generateSources)
      source(generateSources.map { it.outputs.files })
  }

─────────────────────────────────────────────────────────────────────────────────
COMMON TASK TYPES
─────────────────────────────────────────────────────────────────────────────────

  Task Type     Description               Example
  ───────────── ─────────────────────────────────────────────────────────────
  Copy          Copy files                tasks.register<Copy>("copyConfig") { from("src/config"); into("build/config") }
  Delete        Remove files/dirs         tasks.register<Delete>("cleanLogs") { delete("logs/") }
  Exec          Run external command      tasks.register<Exec>("dockerBuild") { commandLine("docker", "build", ".") }
  JavaExec      Run a Java main class     tasks.register<JavaExec>("run") { mainClass.set("com.App"); classpath = ... }
  Jar           Create a JAR file         tasks.jar { manifest { attributes("Main-Class" to "com.App") } }
  Test          Run tests                 tasks.test { useJUnitPlatform() }
  Zip/Tar       Create archives           tasks.register<Zip>("dist") { from("build/libs"); archiveFileName.set("app.zip") }
  WriteProperties Write a .properties file  tasks.register<WriteProperties>("writeVersion") { ... }

INPUTS AND OUTPUTS — INCREMENTAL BUILDS
─────────────────────────────────────────────────────────────────────────────────

  Gradle skips tasks whose inputs and outputs haven't changed ("UP-TO-DATE").
  Declaring inputs/outputs correctly is critical for build correctness.

  Annotations for custom task classes:
  @Input          — A property value (String, Int, etc.) that affects the output
  @InputFile      — A single input file
  @InputFiles     — Multiple input files
  @InputDirectory — An input directory
  @OutputFile     — A single output file
  @OutputDirectory — An output directory
  @Internal       — Not an input or output (just internal state); won't affect UP-TO-DATE

  Example:
  abstract class ProcessTemplate : DefaultTask() {
      @get:Input
      abstract val templateName: Property<String>

      @get:InputDirectory
      abstract val templateDir: DirectoryProperty

      @get:OutputDirectory
      abstract val outputDir: DirectoryProperty

      @TaskAction
      fun process() {
          val name = templateName.get()
          // ... process template
      }
  }

  Without proper inputs/outputs:
  • Missing @Input: Gradle won't rerun when that value changes (stale output)
  • Missing @OutputFile: Gradle can't verify output exists (always reruns)

─────────────────────────────────────────────────────────────────────────────────
TASK CONFIGURATION AVOIDANCE
─────────────────────────────────────────────────────────────────────────────────

  PROBLEM: In large builds, eagerly configuring ALL tasks at configuration time
           even when only a few tasks run wastes time.

  SOLUTION: tasks.register() (lazy) vs tasks.create() (eager)

  // LAZY — task is only configured when it will actually run (preferred)
  tasks.register<Test>("slowTest") {
      description = "Slow integration tests"
      useJUnitPlatform()
  }

  // Configuring an existing task lazily:
  tasks.named<Test>("test") {       // tasks.test { ... } also works but is eager
      useJUnitPlatform()
      maxHeapSize = "512m"
      jvmArgs("-XX:+UseG1GC")
  }

  // The tasks.test {} shorthand works because the java plugin eagerly registers 'test'
  // For your own tasks, prefer tasks.named("myTask") { ... }

─────────────────────────────────────────────────────────────────────────────────
RUNNING TASKS
─────────────────────────────────────────────────────────────────────────────────

  ./gradlew build                    # Run task and all dependencies
  ./gradlew clean build              # Run clean then build
  ./gradlew test --tests "*.UserServiceTest"   # Run specific test class
  ./gradlew test --tests "*UserServiceTest.testCreate"  # Specific test method
  ./gradlew :module:build            # Run task in specific subproject
  ./gradlew build -x test            # Exclude the test task
  ./gradlew build --continue         # Don't stop on first failure
  ./gradlew --dry-run build          # Show what would run (no execution)
  ./gradlew build --info             # Info-level logging (shows UP-TO-DATE decisions)
  ./gradlew build --scan             # Generate Build Scan report (web dashboard)
  ./gradlew dependencies             # Print dependency tree

─────────────────────────────────────────────────────────────────────────────────
INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between tasks.register and tasks.create in Gradle?
A: tasks.register() is lazy — the task is only configured when it is actually
   needed (i.e., when it or a dependent task is being run). tasks.create() is
   eager — it configures the task immediately during the configuration phase,
   even if it will never run. For large multi-project builds, register() can
   significantly improve configuration time.

Q: What are task inputs and outputs and why do they matter?
A: Inputs are the files, directories, and property values a task consumes.
   Outputs are what it produces. Gradle uses these to determine if a task is
   UP-TO-DATE (skip it) or needs to run. If you declare them incorrectly, you
   can get stale output (skipped when it should run) or always-run tasks
   (runs when it could be skipped). With remote build cache, properly declared
   inputs/outputs also enable cache hits across machines.

Q: What is the difference between dependsOn, mustRunAfter, and finalizedBy?
A: dependsOn("x") — the current task won't run unless x has already run.
   mustRunAfter("x") — if both tasks are in the task graph, this task runs
     after x, but does NOT add x to the graph.
   finalizedBy(x) — x always runs after the current task, even on failure.
   Use case: tasks.test { finalizedBy(jacocoTestReport) } ensures coverage
   report is generated even when tests fail.

Q: What does "UP-TO-DATE" mean in Gradle?
A: Gradle skipped the task because its declared inputs and outputs haven't
   changed since the last run. This is Gradle's incremental build feature.
   Related: "FROM-CACHE" means the output was pulled from the build cache
   (local or remote). "SKIPPED" means the task has an onlyIf condition that
   evaluated to false.
