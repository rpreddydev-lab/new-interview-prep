  MAVEN REPOSITORIES AND MIRRORS
================================================================================

WHAT IS A MAVEN REPOSITORY?
─────────────────────────────
A Maven repository is a directory (local filesystem or remote server) that stores
Maven artifacts (JARs, WARs, POMs) in a specific directory structure:

  <groupId-as-path>/<artifactId>/<version>/<artifactId>-<version>.<ext>

  Example: org.springframework:spring-core:6.1.2 is stored as:
  .../org/springframework/spring-core/6.1.2/spring-core-6.1.2.jar
  .../org/springframework/spring-core/6.1.2/spring-core-6.1.2.pom
  .../org/springframework/spring-core/6.1.2/spring-core-6.1.2-sources.jar
  .../org/springframework/spring-core/6.1.2/spring-core-6.1.2-javadoc.jar
  .../org/springframework/spring-core/6.1.2/spring-core-6.1.2.jar.sha1  ← checksum

─────────────────────────────────────────────────────────────────────────────────
TYPES OF REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

  1. LOCAL REPOSITORY
  ────────────────────
  Location: ~/.m2/repository/
  • Maven's local cache — checked FIRST before any remote repo
  • Populated by:
    - "mvn install" (installs your project's artifacts locally)
    - Downloading from remote repos during builds
  • Deleting it is safe — Maven re-downloads everything on next build
  • Can override location in settings.xml: <localRepository>/path/to/repo</localRepository>

  2. CENTRAL REPOSITORY (Maven Central)
  ──────────────────────────────────────
  URL: https://repo.maven.apache.org/maven2/
  Also: https://search.maven.org/ (UI for searching)
  • The largest public Java artifact repository (~10 million artifacts)
  • Read-only for the public; uploading requires Sonatype OSS account
  • Defined in the Super POM — always available by default
  • Artifacts are indexed by search.maven.org

  3. PRIVATE/CORPORATE REPOSITORIES
  ────────────────────────────────────
  Tools: Nexus Repository (Sonatype), Artifactory (JFrog), GitHub Packages,
         GitLab Package Registry, AWS CodeArtifact, Azure Artifacts
  • Store proprietary artifacts not suitable for Maven Central
  • Act as proxy/cache for Maven Central (air-gapped environments)
  • Provide access control, vulnerability scanning, audit trails
  • Typical structure:
    - Hosted repo: stores your own artifacts
    - Proxy repo: caches artifacts from Maven Central or other repos
    - Group repo: aggregates multiple repos into one URL

─────────────────────────────────────────────────────────────────────────────────
DECLARING REPOSITORIES IN POM.XML
─────────────────────────────────────────────────────────────────────────────────

  <repositories>
    <repository>
      <id>company-nexus</id>             <!-- Unique ID — matches credentials in settings.xml -->
      <name>Company Nexus</name>
      <url>https://nexus.company.com/repository/maven-public/</url>
      <releases>
        <enabled>true</enabled>
        <updatePolicy>never</updatePolicy>   <!-- never | daily | always | interval:30 -->
        <checksumPolicy>warn</checksumPolicy> <!-- fail | warn | ignore -->
      </releases>
      <snapshots>
        <enabled>true</enabled>
        <updatePolicy>always</updatePolicy>   <!-- Always check for new snapshots -->
      </snapshots>
    </repository>
  </repositories>

  <!-- For plugin repositories: -->
  <pluginRepositories>
    <pluginRepository>
      <id>company-nexus-plugins</id>
      <url>https://nexus.company.com/repository/maven-public/</url>
      <releases><enabled>true</enabled></releases>
      <snapshots><enabled>false</enabled></snapshots>
    </pluginRepository>
  </pluginRepositories>

  KEY: The repository <id> must match the <server><id> in settings.xml for
  authentication to work.

─────────────────────────────────────────────────────────────────────────────────
REPOSITORY RESOLUTION ORDER
─────────────────────────────────────────────────────────────────────────────────

  Maven searches in this order:
  1. Local repository (~/.m2/repository)
  2. Repositories defined in the POM (in order declared)
  3. Repositories defined in settings.xml
  4. Maven Central (defined in Super POM)

  If multiple repositories are configured, Maven checks them in order and uses
  the first one that contains the requested artifact.

─────────────────────────────────────────────────────────────────────────────────
SNAPSHOT vs RELEASE REPOSITORIES
─────────────────────────────────────────────────────────────────────────────────

  Repositories are typically configured to handle either releases or snapshots
  (or both). Best practice: keep them SEPARATE.

  Release repository:
  • Stores immutable release versions (1.0.0, 2.1.3)
  • Artifacts once deployed CANNOT be redeployed (enforced by repo managers)
  • <snapshots><enabled>false</enabled></snapshots>

  Snapshot repository:
  • Stores mutable SNAPSHOT versions (1.0.0-SNAPSHOT)
  • The same SNAPSHOT version CAN be redeployed
  • Maven downloads newer snapshots based on updatePolicy
  • <releases><enabled>false</enabled></releases>

  <distributionManagement>
    <repository>
      <id>nexus-releases</id>
      <url>https://nexus.company.com/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
      <id>nexus-snapshots</id>
      <url>https://nexus.company.com/repository/maven-snapshots/</url>
    </snapshotRepository>
  </distributionManagement>

─────────────────────────────────────────────────────────────────────────────────
MIRRORS — REDIRECTING REPOSITORY REQUESTS
─────────────────────────────────────────────────────────────────────────────────

  A mirror is a redirect — instead of hitting the original repository URL,
  Maven sends requests to the mirror URL. Mirrors are configured in settings.xml
  (not pom.xml) because they're infrastructure/environment-specific.

  settings.xml:
  <mirrors>
    <mirror>
      <id>central-mirror</id>
      <name>Corporate Nexus Mirror</name>
      <url>https://nexus.company.com/repository/maven-public/</url>
      <mirrorOf>central</mirrorOf>         <!-- Mirror only Maven Central -->
    </mirror>
  </mirrors>

  Common mirrorOf values:
  ─────────────────────────────────────────────────────────────────────────────
  central             Only mirror Maven Central
  *                   Mirror ALL repositories (forces everything through Nexus)
  *,!company-repo     Mirror everything EXCEPT company-repo
  repo1,repo2         Mirror specific named repos

  The <mirrorOf>*</mirrorOf> pattern is the most common corporate setup:
  it forces ALL artifact resolution through your corporate Nexus/Artifactory,
  which then proxies to Maven Central. This provides:
  ✔ Air-gapped support (Nexus caches; devs don't need internet access)
  ✔ Central vulnerability scanning
  ✔ Bandwidth savings (cached downloads)
  ✔ Audit trail of all artifact downloads

─────────────────────────────────────────────────────────────────────────────────
PROXY SETTINGS
─────────────────────────────────────────────────────────────────────────────────

  settings.xml:
  <proxies>
    <proxy>
      <id>corporate-proxy</id>
      <active>true</active>
      <protocol>https</protocol>
      <host>proxy.company.com</host>
      <port>8080</port>
      <username>proxyUser</username>         <!-- optional -->
      <password>proxyPassword</password>     <!-- optional -->
      <nonProxyHosts>localhost|*.company.com</nonProxyHosts>
    </proxy>
  </proxies>

AUTHENTICATION — SERVER CREDENTIALS
─────────────────────────────────────────────────────────────────────────────────

  Credentials for deploying to or downloading from private repos go in settings.xml,
  NOT in pom.xml (never commit passwords to source control!).

  settings.xml:
  <servers>
    <server>
      <id>nexus-releases</id>         <!-- Must match the <repository><id> in pom.xml -->
      <username>deploy-user</username>
      <password>secret-password</password>
    </server>
    <server>
      <id>nexus-snapshots</id>
      <username>deploy-user</username>
      <password>secret-password</password>
    </server>
  </servers>

  Better: Use encrypted passwords (mvn -emp) or CI/CD secrets:

  # Encrypt master password:
  mvn --encrypt-master-password mysecret
  → {jSMOWnoPFgsHVpMvz5VrIt5kRbzGpI8u+9EF1iFQyJQ=}

  # Add to ~/.m2/settings-security.xml:
  <settingsSecurity>
    <master>{jSMOWnoPFgsHVpMvz5VrIt5kRbzGpI8u+9EF1iFQyJQ=}</master>
  </settingsSecurity>

  # Encrypt the actual password:
  mvn --encrypt-password mypassword
  → {COQLCE6DU6GtcS5P=}

  # Use encrypted password in settings.xml:
  <password>{COQLCE6DU6GtcS5P=}</password>

FORCING UPDATES / OFFLINE MODE
─────────────────────────────────────────────────────────────────────────────────

  # Force Maven to check remote repos for updated snapshots:
  mvn clean install -U   (--update-snapshots)

  # Build completely offline (fail if not in local cache):
  mvn clean install -o   (--offline)

  # Delete corrupted local repo entries and re-download:
  find ~/.m2/repository -name "*.lastUpdated" -delete
  mvn clean install

INTERVIEW QUICK-HITS
─────────────────────────────────────────────────────────────────────────────────

Q: What is the difference between a Maven repository and a mirror?
A: A repository is a storage location for Maven artifacts. A mirror is a redirect
   configured in settings.xml that intercepts requests to one repository and sends
   them to another URL instead. Mirrors don't change what you declare in pom.xml;
   they change WHERE Maven actually goes to fetch artifacts at the network level.

Q: Why would you configure <mirrorOf>*</mirrorOf> in settings.xml?
A: To route ALL artifact resolution through a corporate proxy repository (Nexus/
   Artifactory). This provides: caching (faster builds, less bandwidth), security
   scanning, air-gapped support, and audit trails. All requests are intercepted
   before reaching the internet.

Q: Where should repository credentials go?
A: In ~/.m2/settings.xml under <servers>, NEVER in pom.xml. The <server><id>
   must match the <repository><id> in pom.xml. In CI/CD, inject credentials via
   environment variables or vault secrets, not hardcoded in settings.xml.

Q: What does the -U flag do in Maven?
A: --update-snapshots forces Maven to check remote repositories for updated
   SNAPSHOT versions, even if a newer version was already downloaded recently.
   Without -U, Maven uses the cached snapshot based on the updatePolicy.

Q: Why separate release and snapshot repositories?
A: Release repositories are immutable — artifacts can't be overwritten after
   deployment. Snapshot repositories allow redeployment of the same version.
   Separating them gives different access policies, retention policies, and
   makes it clear what's production-ready vs in-development.
