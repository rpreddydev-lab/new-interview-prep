  1. JPQL vs SQL vs HQL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  JPQL  = JPA Query Language  — operates on ENTITIES and their fields
  HQL   = Hibernate Query Language — Hibernate superset of JPQL
  SQL   = Standard SQL — operates on TABLES and COLUMNS

  Key differences:
  - JPQL uses entity class names (case-sensitive): FROM Product
  - JPQL uses entity field names: p.name, p.price
  - JPQL is DB-agnostic (Hibernate translates to dialect SQL)
  - Native SQL uses table/column names and is DB-specific

  2. JPQL SYNTAX ESSENTIALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SELECT clause:
  SELECT p FROM Product p
  SELECT p.name, p.price FROM Product p         -- scalar results
  SELECT new com.example.dto.ProductDto(p.name, p.price) FROM Product p
  SELECT DISTINCT p.category FROM Product p

WHERE clause:
  WHERE p.price > :minPrice
  WHERE p.name LIKE :pattern                    -- % wildcard
  WHERE p.category IN :categories               -- IN list
  WHERE p.createdAt BETWEEN :from AND :to
  WHERE p.tags IS EMPTY                         -- collection empty
  WHERE :tag MEMBER OF p.tags                   -- element in collection

JOIN:
  SELECT o FROM Order o JOIN o.items i WHERE i.product.id = :pid
  SELECT o FROM Order o LEFT JOIN FETCH o.items WHERE o.id = :id
  SELECT o FROM Order o JOIN FETCH o.customer

ORDER BY:
  SELECT p FROM Product p ORDER BY p.price DESC, p.name ASC

GROUP BY / HAVING:
  SELECT p.category, COUNT(p), AVG(p.price)
  FROM Product p
  GROUP BY p.category
  HAVING AVG(p.price) > 100

Aggregate functions: COUNT, SUM, AVG, MIN, MAX
Scalar functions:    UPPER, LOWER, LENGTH, SUBSTRING, TRIM, CONCAT
                     ABS, SQRT, MOD, SIZE (collection size)

  3. BINDING PARAMETERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Named parameters (preferred — readable, order-independent):
  @Query("SELECT p FROM Product p WHERE p.category = :cat AND p.price < :max")
  List<Product> findCheapByCategory(@Param("cat") Category cat,
                                    @Param("max") BigDecimal max);

Positional parameters (JPA standard ?1, ?2, ...):
  @Query("SELECT p FROM Product p WHERE p.category = ?1 AND p.price < ?2")
  List<Product> findCheapByCategory(Category cat, BigDecimal max);

  ⚠️  Positional params are fragile (order matters); prefer named.

  4. JOIN FETCH — SOLVING LAZY LOADING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Without FETCH — Order loaded, items will lazy-load (N+1 risk)
@Query("SELECT o FROM Order o WHERE o.customer.id = :custId")
List<Order> findByCustomer(@Param("custId") Long custId);

// With FETCH — items loaded in same query (single JOIN)
@Query("SELECT DISTINCT o FROM Order o " +
       "JOIN FETCH o.items i " +
       "JOIN FETCH o.customer " +
       "WHERE o.customer.id = :custId")
List<Order> findByCustomerWithItems(@Param("custId") Long custId);

⚠️  JOIN FETCH with pagination is problematic:
  - Hibernate applies LIMIT in memory (HibernateJpaDialect warning)
  - Solution: use @EntityGraph or two queries
    (1) paginated IDs query, (2) fetch full entities by ID list

  5. @EntityGraph — CONTROLLING FETCH PLAN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Defined on entity:
  @Entity
  @NamedEntityGraph(name = "Order.withItems",
                    attributeNodes = @NamedAttributeNode("items"))
  public class Order { ... }

Used in repository:
  @EntityGraph("Order.withItems")
  List<Order> findByStatus(OrderStatus status);

Ad-hoc entity graph in repository:
  @EntityGraph(attributePaths = {"items", "items.product", "customer"})
  Optional<Order> findWithDetailsById(Long id);

  → No entity-side annotation needed for attributePaths form

  6. NATIVE QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Simple native query returning entities:
  @Query(value = "SELECT * FROM products WHERE sku = :sku",
         nativeQuery = true)
  Optional<Product> findBySku(@Param("sku") String sku);

Native query with custom result mapping (SqlResultSetMapping):
  @Query(value = """
      SELECT p.id, p.name, COUNT(oi.id) AS order_count
      FROM products p
      LEFT JOIN order_items oi ON oi.product_id = p.id
      GROUP BY p.id, p.name
      ORDER BY order_count DESC
      LIMIT :limit
      """,
      nativeQuery = true)
  List<Object[]> findTopSelling(@Param("limit") int limit);

  // Destructure:
  // Object[] row → row[0]=id, row[1]=name, row[2]=count

Native query with projection interface:
  public interface TopProduct {
      Long getId();
      String getName();
      Long getOrderCount();
  }

  @Query(value = """
      SELECT p.id, p.name, COUNT(oi.id) AS order_count
      FROM products p LEFT JOIN order_items oi ON oi.product_id = p.id
      GROUP BY p.id ORDER BY order_count DESC LIMIT :limit
      """,
      nativeQuery = true)
  List<TopProduct> findTopSelling(@Param("limit") int limit);
  // Column aliases MUST match projection getter names (camelCase → snake_case auto-mapped)

  7. SUBQUERIES IN JPQL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

-- Products cheaper than average price in their category
SELECT p FROM Product p
WHERE p.price < (
    SELECT AVG(p2.price) FROM Product p2
    WHERE p2.category = p.category
)

-- Customers who placed at least one order over $1000
SELECT c FROM Customer c
WHERE EXISTS (
    SELECT o FROM Order o
    WHERE o.customer = c AND o.total > 1000
)

-- Products that have never been ordered
SELECT p FROM Product p
WHERE p NOT IN (
    SELECT DISTINCT oi.product FROM OrderItem oi
)

  8. JPQL UPDATE AND DELETE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  @Modifying
  @Transactional
  @Query("UPDATE Product p SET p.active = false WHERE p.stock = 0")
  int deactivateOutOfStock();

  @Modifying
  @Transactional
  @Query("DELETE FROM Product p WHERE p.category = :cat AND p.active = false")
  int deleteInactiveByCategory(@Param("cat") Category cat);

  Note: Bulk UPDATE/DELETE bypass entity lifecycle callbacks and
  don't update first-level cache. Use @Modifying(clearAutomatically = true)
  or evict affected entities manually.

  9. SORTING AND PAGINATION WITH @Query
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Add Pageable param — Spring appends ORDER BY / LIMIT automatically
@Query("SELECT p FROM Product p WHERE p.category = :cat")
Page<Product> findByCategory(@Param("cat") Category cat, Pageable pageable);

// Provide a separate count query for native pagination
@Query(value = "SELECT * FROM products WHERE category = :cat",
       countQuery = "SELECT count(*) FROM products WHERE category = :cat",
       nativeQuery = true)
Page<Product> findByCategoryNative(@Param("cat") String cat, Pageable pageable);

Q: What is the difference between JPQL and SQL?
A: JPQL operates on entity class names and field names; it is
   DB-agnostic and Hibernate translates it to the target dialect.
   SQL operates on table and column names and is DB-specific.
   Use JPQL for portability; native SQL when you need DB-specific
   features (window functions, CTEs, JSON operators, etc.).

Q: When should you use native queries over JPQL?
A: When you need DB-specific features (recursive CTEs, window functions,
   EXPLAIN, RETURNING, JSON operators), when JPQL does not support
   the operation, or when a hand-crafted SQL outperforms the JPQL-
   generated one significantly.

Q: What is JOIN FETCH and when is it needed?
A: JOIN FETCH eagerly loads an association in the same query,
   preventing LazyInitializationException outside a transaction and
   avoiding N+1 selects. It is needed when you know you'll always
   access the association in the same request.

Q: Why does JOIN FETCH with Pageable produce a warning?
A: Hibernate cannot apply SQL LIMIT with a collection JOIN FETCH
   (would produce wrong results), so it fetches all rows and
   applies pagination in memory. Fix: use @EntityGraph or a
   separate two-query approach (page IDs, then fetch by IDs).

Q: What does @Modifying(clearAutomatically = true) do?
A: After the bulk UPDATE/DELETE, it clears the persistence context
   (first-level cache) so subsequent finds load fresh data from
   the DB rather than returning stale cached entities.

Q: What is @EntityGraph and how does it differ from JOIN FETCH?
A: Both achieve the same end — eager load associations. @EntityGraph
   is declarative and re-usable (defined on entity or repository),
   while JOIN FETCH is embedded in the JPQL string. EntityGraph is
   preferred for its composability and avoiding duplicate query strings.

Q: How do you use projection interfaces with native queries?
A: The projection interface getter names must match the column aliases
   in the SELECT clause (Spring Data maps snake_case columns to
   camelCase getters automatically, or use exact alias match).
