======================================================
PROBLEM DETAILS (RFC 7807) — SPRING 6 / SPRING BOOT 3
======================================================

1. WHAT IS RFC 7807?
─────────────────────
RFC 7807 "Problem Details for HTTP APIs" is a standard format for HTTP error responses.

Problem:
  Every API returns errors differently:
    {"error": "Not found"}         ← no structure
    {"code": 404, "msg": "..."}    ← custom
    {"errors": [{"field": "..."}]} ← validation errors

RFC 7807 defines a standard JSON (or XML) structure:
  {
    "type":     "https://api.example.com/errors/not-found",  // URI identifying error type
    "title":    "Resource Not Found",                         // short human-readable title
    "status":   404,                                          // HTTP status code
    "detail":   "Order with ID 123 was not found",           // detailed description
    "instance": "/api/v1/orders/123"                          // specific instance URI
  }

Media type: application/problem+json


2. SPRING 6 NATIVE SUPPORT — ProblemDetail
────────────────────────────────────────────
Spring Framework 6 (Spring Boot 3.x) introduced native RFC 7807 support
via the ProblemDetail class — no extra library needed.

ProblemDetail class:
  ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
  problem.setType(URI.create("https://api.example.com/errors/order-not-found"));
  problem.setTitle("Order Not Found");
  problem.setDetail("Order with ID 123 was not found");
  problem.setInstance(URI.create("/api/v1/orders/123"));
  // Add custom properties:
  problem.setProperty("orderId", 123);
  problem.setProperty("timestamp", Instant.now());

Enable RFC 7807 responses from Spring MVC:
  application.yml:
    spring:
      mvc:
        problemdetails:
          enabled: true    # Spring Boot 3.0+: enables RFC 7807 for all default exceptions


3. @ExceptionHandler WITH ProblemDetail
──────────────────────────────────────────
  @RestControllerAdvice
  public class GlobalExceptionHandler {

      // Spring Framework 6 style:
      @ExceptionHandler(OrderNotFoundException.class)
      public ProblemDetail handleOrderNotFound(OrderNotFoundException ex,
                                               HttpServletRequest request) {
          ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
          problem.setType(URI.create("https://api.example.com/errors/order-not-found"));
          problem.setTitle("Order Not Found");
          problem.setDetail(ex.getMessage());
          problem.setInstance(URI.create(request.getRequestURI()));
          problem.setProperty("orderId", ex.getOrderId());
          problem.setProperty("timestamp", Instant.now());
          return problem;
      }

      @ExceptionHandler(MethodArgumentNotValidException.class)
      public ProblemDetail handleValidationError(MethodArgumentNotValidException ex) {
          ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
          problem.setTitle("Validation Failed");
          problem.setDetail("One or more fields failed validation");

          List<Map<String, String>> fieldErrors = ex.getBindingResult()
              .getFieldErrors().stream()
              .map(fe -> Map.of(
                  "field", fe.getField(),
                  "message", Objects.requireNonNullElse(fe.getDefaultMessage(), "Invalid value")
              ))
              .collect(Collectors.toList());
          problem.setProperty("fieldErrors", fieldErrors);
          return problem;
      }

      @ExceptionHandler(AccessDeniedException.class)
      public ProblemDetail handleAccessDenied(AccessDeniedException ex) {
          ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.FORBIDDEN);
          problem.setTitle("Access Denied");
          problem.setDetail(ex.getMessage());
          return problem;
      }
  }


4. ResponseEntityExceptionHandler (Spring MVC Default Errors)
──────────────────────────────────────────────────────────────
Spring MVC internally uses ResponseEntityExceptionHandler to handle:
  - MethodArgumentNotValidException
  - HttpMessageNotReadableException
  - HttpRequestMethodNotSupportedException
  - etc.

With spring.mvc.problemdetails.enabled=true:
  All these return ProblemDetail responses automatically.

Extend to customize:
  @RestControllerAdvice
  public class CustomExceptionHandler extends ResponseEntityExceptionHandler {

      @Override
      protected ResponseEntity<Object> handleMethodArgumentNotValid(
              MethodArgumentNotValidException ex, HttpHeaders headers,
              HttpStatusCode status, WebRequest request) {

          ProblemDetail problem = ex.getBody();  // Spring 6 auto-creates ProblemDetail
          problem.setTitle("Validation Failed");
          problem.setProperty("violations", buildViolationMap(ex.getBindingResult()));
          return ResponseEntity.badRequest().body(problem);
      }
  }


5. ErrorResponse INTERFACE
────────────────────────────
Spring 6 introduced ErrorResponse interface for exceptions that carry HTTP error info:

  public class OrderNotFoundException extends RuntimeException
          implements ErrorResponse {

      private final Long orderId;

      public OrderNotFoundException(Long orderId) {
          super("Order not found: " + orderId);
          this.orderId = orderId;
      }

      @Override
      public HttpStatusCode getStatusCode() {
          return HttpStatus.NOT_FOUND;
      }

      @Override
      public ProblemDetail getBody() {
          ProblemDetail detail = ProblemDetail.forStatus(getStatusCode());
          detail.setTitle("Order Not Found");
          detail.setDetail(getMessage());
          detail.setProperty("orderId", orderId);
          return detail;
      }
  }

When thrown, Spring MVC automatically converts to ProblemDetail response.
No @ExceptionHandler needed for self-describing exceptions.


6. WEBFLUX SUPPORT
───────────────────
ProblemDetail works with WebFlux too:

  @RestControllerAdvice
  public class ReactiveExceptionHandler {

      @ExceptionHandler(OrderNotFoundException.class)
      public ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex,
                                                          ServerWebExchange exchange) {
          ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
          problem.setDetail(ex.getMessage());
          problem.setInstance(URI.create(exchange.getRequest().getPath().value()));
          return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
      }
  }

Enable for WebFlux:
  spring.webflux.problemdetails.enabled=true  # Spring Boot 3.x


7. CUSTOM PROBLEM TYPES (BEST PRACTICES)
──────────────────────────────────────────
Define problem type URIs as constants:
  public class ProblemTypes {
      private static final String BASE = "https://api.example.com/problems/";
      public static final URI ORDER_NOT_FOUND    = URI.create(BASE + "order-not-found");
      public static final URI PAYMENT_FAILED     = URI.create(BASE + "payment-failed");
      public static final URI VALIDATION_ERROR   = URI.create(BASE + "validation-error");
      public static final URI RATE_LIMIT_EXCEEDED= URI.create(BASE + "rate-limit-exceeded");
  }

Type URI should point to documentation (even if the page doesn't exist yet).
It's an identifier, not necessarily a live URL.

Standard type URIs for generic errors:
  "about:blank"  → generic error with no specific type (RFC 7807 default)

9. INTERVIEW QUESTIONS
──────────────────────
Q: What is RFC 7807 and why should APIs use it?
A: RFC 7807 defines a standard JSON structure for HTTP API error responses.
   Using it means clients (and developers) know what to expect in error responses:
   type (URI identifier), title (human description), status (HTTP code), detail,
   and instance (specific request URI). It promotes interoperability and
   removes the need to document custom error schemas.

Q: How does Spring Boot 3 support RFC 7807 natively?
A: Set spring.mvc.problemdetails.enabled=true. Spring MVC then returns
   ProblemDetail objects for all its built-in exception handlers
   (MethodArgumentNotValidException, HttpRequestMethodNotSupportedException, etc.).
   Use ProblemDetail class in @ExceptionHandler methods for custom errors.

Q: What is the ErrorResponse interface in Spring 6?
A: An interface that exceptions can implement to be self-describing.
   Exceptions provide their own HttpStatusCode and ProblemDetail body.
   Spring MVC automatically converts them to RFC 7807 responses without
   needing an @ExceptionHandler in a @ControllerAdvice.

Q: What is the difference between ProblemDetail.type and ProblemDetail.instance?
A: type is a URI identifying the category/type of problem (same for all occurrences).
   instance is a URI identifying the specific occurrence of the problem
   (usually the request URI). type stays stable; instance varies per request.

Q: What should the "type" URI point to?
A: Ideally, a documentation page explaining the error type and how to resolve it.
   It must be a URI (can be "about:blank" for generic errors).
   It's an identifier — the URI doesn't need to be a live, resolvable URL,
   but it should be stable and unique to the error category.
