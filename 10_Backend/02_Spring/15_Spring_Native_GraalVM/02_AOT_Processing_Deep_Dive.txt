======================================================
AOT (AHEAD-OF-TIME) COMPILATION — SPRING BOOT 3 DEEP DIVE
======================================================

1. WHAT IS AOT PROCESSING?
────────────────────────────
AOT (Ahead-of-Time) processing: Spring analyzes the application at build time
and generates optimized code/configuration instead of doing it at runtime.

Traditional Spring Boot (JIT — Just-In-Time):
  - Application starts → Spring scans classpath, processes annotations
  - Bean definitions created dynamically via reflection
  - Proxy classes generated at runtime (CGLIB, JDK)
  - Expensive, slow startup, reflection-heavy

AOT Processing (Spring Boot 3.0+):
  - At BUILD TIME: Spring processes all annotations, conditions, configurations
  - Generates: Java source files, bytecode, resource hints
  - At RUNTIME: no more annotation scanning, no runtime reflection
  - Result: faster startup, lower memory, GraalVM Native Image support

AOT is required for GraalVM Native Image (no dynamic reflection at runtime).
AOT is optional for JVM (JIT) but provides startup improvements.


2. ENABLING AOT PROCESSING
────────────────────────────
Maven:
  ./mvnw spring-boot:process-aot        # generate AOT sources
  ./mvnw spring-boot:build-image        # uses AOT automatically when building images

  The spring-boot-maven-plugin runs AOT processing before compilation:
  <plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
  </plugin>

Gradle:
  ./gradlew processAot                  # generate AOT sources
  ./gradlew bootBuildImage              # uses AOT

Generated files location:
  target/spring-aot/main/sources/       # generated Java source code
  target/spring-aot/main/resources/     # generated resource hints


3. WHAT AOT GENERATES
───────────────────────
a) BeanDefinitionRegistrar classes:
   Instead of scanning @Component at runtime, AOT generates explicit
   BeanDefinitionRegistrar that registers all beans programmatically.

b) BeanFactoryInitializer:
   Executes at startup to register beans without reflection.

c) ApplicationContextInitializer:
   AOT-generated initializer that sets up the context faster.

d) Resource hints (for Native Image):
   META-INF/native-image/ folder with:
     - reflect-config.json   → classes needing reflection
     - resource-config.json  → resources to include in native image
     - proxy-config.json     → proxy classes
     - serialization-config.json → serializable types

AOT Generated code example:
  // Instead of: Spring discovers @Service OrderService at runtime
  // AOT generates:
  public class OrderServiceBeanDefinitions implements BeanDefinitionRegistrar {
      @Override
      public void register(BeanDefinitionRegistry registry) {
          RootBeanDefinition bd = new RootBeanDefinition(OrderService.class);
          bd.setInstanceSupplier(OrderService::new);
          registry.registerBeanDefinition("orderService", bd);
      }
  }


4. REFLECTION HINTS
────────────────────
GraalVM native image closes the open world — no dynamic reflection by default.
Spring AOT generates reflection hints for everything that needs reflection.

Manual hints (when AOT can't detect automatically):
  @ImportRuntimeHints(MyRuntimeHints.class)
  @Configuration
  public class MyConfig { ... }

  class MyRuntimeHints implements RuntimeHintsRegistrar {
      @Override
      public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
          // Register class for reflection
          hints.reflection()
              .registerType(MyDomainClass.class,
                  MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                  MemberCategory.INVOKE_PUBLIC_METHODS);

          // Register resource pattern
          hints.resources().registerPattern("data/*.json");

          // Register proxy
          hints.proxies().registerJdkProxy(MyInterface.class);

          // Register serialization
          hints.serialization().registerType(MySerializable.class);
      }
  }

Common scenarios needing manual hints:
  - Custom deserializers or serializers
  - Reflection-based code (e.g., reading annotations at runtime)
  - Dynamic class loading
  - JAXB, Jackson with dynamically discovered types
  - Some third-party libraries


5. @RegisterReflectionForBinding
──────────────────────────────────
Convenient annotation for registering types for Jackson/serialization:

  @RegisterReflectionForBinding(OrderDto.class)
  @RestController
  public class OrderController { ... }

Or on configuration:
  @Configuration
  @RegisterReflectionForBinding({OrderDto.class, PaymentDto.class})
  public class DtoConfig { ... }


6. GRAALVM NATIVE IMAGE COMPILATION
──────────────────────────────────────
Native image: compile Spring Boot app into a native executable (no JVM needed).
  - Startup: milliseconds (vs seconds for JVM)
  - Memory: much lower (no JVM overhead)
  - Performance: good for I/O-bound apps; JIT may outperform for CPU-heavy

Requirements:
  - GraalVM 22.3+ or Oracle GraalVM 21+
  - Spring Boot 3.0+
  - AOT processing (mandatory for native)

Build native image:
  # With GraalVM installed:
  ./mvnw -Pnative native:compile

  # With Buildpacks (no GraalVM needed locally):
  ./mvnw -Pnative spring-boot:build-image

pom.xml (Spring Boot 3.x native support):
  <profiles>
    <profile>
      <id>native</id>
      <build>
        <plugins>
          <plugin>
            <groupId>org.graalvm.buildtools</groupId>
            <artifactId>native-maven-plugin</artifactId>
            <executions>
              <execution>
                <goals><goal>compile-no-fork</goal></goals>
                <phase>package</phase>
              </execution>
            </executions>
          </plugin>
        </plugins>
      </build>
    </profile>
  </profiles>

Native image build time: 2–10 minutes (significant investment).


7. TESTING NATIVE IMAGES
──────────────────────────
Test with JVM AOT mode (fast feedback loop without full native compilation):
  @SpringBootTest
  @EnabledIfSystemProperty(named = "spring.aot.enabled", matches = "true")
  class NativeCompatibilityTest { ... }

  # Run with AOT enabled (no native compilation):
  ./mvnw test -Dspring.aot.enabled=true

Test native image:
  # Build then run tests against native binary:
  ./mvnw -Pnative native:test

  # Or with Testcontainers:
  @SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
  @TestPropertySource(properties = "spring.aot.enabled=true")
  class NativeIntegrationTest { ... }


8. CLASS DATA SHARING (CDS) — JVM STARTUP BOOST
─────────────────────────────────────────────────
CDS shares class metadata across JVM instances (Spring Boot 3.3+):

  # Step 1: Run with class extraction
  ./mvnw spring-boot:extract-classes-aot

  # Step 2: Create CDS archive
  java -Xshare:dump -XX:SharedArchiveFile=app.jsa -cp app.jar ...

  # Step 3: Run with CDS
  java -Xshare:on -XX:SharedArchiveFile=app.jsa -jar app.jar

Result: 20–30% faster startup on JVM (not as fast as native but much simpler).

Spring Boot 3.3+ Maven/Gradle support:
  ./mvnw spring-boot:build-image   # CDS included automatically


9. CRaC (COORDINATED RESTORE AT CHECKPOINT)
─────────────────────────────────────────────
JVM feature (Java 21+): take a checkpoint of running JVM state, restore instantly.
  - Checkpoint: capture JVM heap, threads, connections after warmup
  - Restore: start from checkpoint → millisecond startup with warmed JVM

Spring Boot 3.2+ supports CRaC:
  spring.context.checkpoint=onRefresh   # take checkpoint after context refresh

  # Run with checkpoint:
  java -XX:CRaCCheckpointTo=/checkpoint -jar app.jar

  # Restore:
  java -XX:CRaCRestoreFrom=/checkpoint

Use case: AWS Lambda SnapStart, Kubernetes rolling restarts.


10. COMPARISON: JVM vs AOT/JVM vs NATIVE IMAGE
────────────────────────────────────────────────
Mode              | Startup | Memory | Throughput | Build Time | Flexibility
─────────────────────────────────────────────────────────────────────────────────────
JVM (standard)    | 3–10s   | High   | Highest    | Fast       | Full dynamic
JVM + AOT         | 1–3s    | Medium | High       | Medium     | Full dynamic
JVM + CDS         | 1–2s    | Medium | High       | Medium     | Full dynamic
GraalVM Native    | <0.1s   | Low    | Good (no JIT)| 5–10 min | Closed world
JVM + CRaC        | <0.5s   | High*  | Highest    | Medium     | Full dynamic

*CRaC restores full JVM state including heap


11. INTERVIEW QUESTIONS
────────────────────────
Q: What is AOT processing in Spring Boot 3 and why is it needed for GraalVM?
A: AOT processing analyzes Spring apps at build time and generates explicit
   bean registrations, proxy classes, and reflection hints. GraalVM Native Image
   requires this because native images are closed-world — no dynamic reflection
   or classpath scanning at runtime. AOT generates all necessary metadata upfront.

Q: What are reflection hints and when do you need to write them manually?
A: Reflection hints tell GraalVM which classes, methods, and constructors need
   runtime reflection support. Spring AOT auto-detects most hints, but manual
   hints are needed for: dynamic class loading, custom Jackson serializers,
   JAXB, or third-party libraries that use reflection but aren't Spring-aware.
   Use RuntimeHintsRegistrar + @ImportRuntimeHints.

Q: What are the trade-offs of GraalVM Native Image vs JVM?
A: Native Image: near-instant startup (<100ms), much lower memory, no JVM overhead.
   Downsides: long build time (5–10 min), no JIT optimization (steady-state may be
   slower for CPU-heavy code), closed-world restrictions (dynamic features limited),
   harder debugging.
   JVM: slower startup but higher peak throughput with JIT.
   Choose native for: serverless, CLI tools, fast pod restarts.
   Choose JVM for: long-running services, CPU-intensive workloads.

Q: What is the difference between AOT processing and CDS (Class Data Sharing)?
A: AOT generates code to avoid runtime annotation scanning/reflection.
   CDS shares pre-loaded class metadata between JVM instances — no code
   generation, just shared memory-mapped class data. CDS is JVM-only (no native).
   Both reduce startup time but through different mechanisms.
   AOT is required for native; CDS is JVM only (easier to adopt).

Q: How do you test that your Spring Boot application is native-image compatible?
A: Run tests with -Dspring.aot.enabled=true to run in AOT mode on JVM (fast).
   Use native:test Maven goal for actual native compilation testing.
   Use @EnabledIfSystemProperty to tag native-specific tests.
   Watch for: reflection usage, dynamic proxies, resource loading patterns.
