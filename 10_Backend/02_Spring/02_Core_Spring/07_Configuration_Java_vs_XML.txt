================================================================
  SPRING CONFIGURATION: JAVA vs XML — IN DEPTH
================================================================

================================================================
THREE CONFIGURATION STYLES
================================================================

  1. XML Configuration     (Spring 1.x, legacy)
  2. Annotation-based      (Spring 2.5+, @Component etc.)
  3. Java Configuration    (Spring 3.0+, @Configuration + @Bean)

  Modern Spring Boot applications use Java Config + Annotations.
  XML is still encountered in legacy enterprise codebases.

================================================================
XML CONFIGURATION — LEGACY STYLE
================================================================

  <?xml version="1.0" encoding="UTF-8"?>
  <beans xmlns="http://www.springframework.org/schema/beans"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xmlns:context="http://www.springframework.org/schema/context"
         xsi:schemaLocation="...">

    <!-- Property placeholder -->
    <context:property-placeholder location="classpath:db.properties"/>

    <!-- Bean definition -->
    <bean id="dataSource" class="com.zaxxer.hikari.HikariDataSource">
        <property name="jdbcUrl"   value="${db.url}"/>
        <property name="username"  value="${db.username}"/>
        <property name="password"  value="${db.password}"/>
    </bean>

    <!-- Constructor injection -->
    <bean id="userRepository" class="com.example.repo.UserRepositoryImpl">
        <constructor-arg ref="dataSource"/>
    </bean>

    <!-- Setter injection -->
    <bean id="emailService" class="com.example.service.EmailService">
        <property name="smtpHost" value="smtp.example.com"/>
        <property name="port"     value="587"/>
    </bean>

    <!-- Enable annotation-based DI alongside XML -->
    <context:annotation-config/>

    <!-- Enable component scanning -->
    <context:component-scan base-package="com.example"/>

  </beans>

  Loading XML:
    ApplicationContext ctx =
        new ClassPathXmlApplicationContext("applicationContext.xml");

================================================================
JAVA CONFIGURATION — MODERN STYLE
================================================================

  @Configuration
  @PropertySource("classpath:db.properties")
  @ComponentScan("com.example")
  public class AppConfig {

      @Value("${db.url}")      private String dbUrl;
      @Value("${db.username}") private String dbUser;
      @Value("${db.password}") private String dbPassword;

      @Bean
      public DataSource dataSource() {
          HikariDataSource ds = new HikariDataSource();
          ds.setJdbcUrl(dbUrl);
          ds.setUsername(dbUser);
          ds.setPassword(dbPassword);
          return ds;
      }

      @Bean
      public JdbcTemplate jdbcTemplate(DataSource dataSource) {
          return new JdbcTemplate(dataSource);
      }

      @Bean
      public UserRepository userRepository(JdbcTemplate jdbcTemplate) {
          return new JdbcUserRepository(jdbcTemplate);
      }
  }

  Loading Java Config:
    ApplicationContext ctx =
        new AnnotationConfigApplicationContext(AppConfig.class);

================================================================
MODULAR JAVA CONFIGURATION — BEST PRACTICE
================================================================

  Split @Configuration classes by concern:

  @Configuration
  public class DatabaseConfig {
      @Bean public DataSource dataSource() { ... }
      @Bean public JdbcTemplate jdbcTemplate(DataSource ds) { ... }
  }

  @Configuration
  public class SecurityConfig {
      @Bean public PasswordEncoder passwordEncoder() {
          return new BCryptPasswordEncoder();
      }
  }

  @Configuration
  @Import({DatabaseConfig.class, SecurityConfig.class})
  public class AppConfig { }

  // Or in Spring Boot — just have them all in the same package,
  // @SpringBootApplication will scan them all.

================================================================
@Bean METHOD PARAMETERS — DEPENDENCY INJECTION
================================================================

  @Bean methods can accept other beans as parameters.
  Spring injects them automatically (same rules as @Autowired).

  @Configuration
  public class ServiceConfig {

      // Parameter injection — cleaner than calling dataSource() directly
      @Bean
      public UserService userService(UserRepository userRepository,
                                     PasswordEncoder encoder,
                                     MailSender mailSender) {
          return new UserService(userRepository, encoder, mailSender);
      }
  }

================================================================
@Bean ATTRIBUTES
================================================================

  Attribute       | Default      | Purpose
  ----------------|--------------|------------------------------------
  name / value    | method name  | Override bean name(s)
  initMethod      | ""           | Method to call after init
  destroyMethod   | "(inferred)" | Method to call on shutdown
  autowireCandidate| true        | Whether eligible for autowiring

  @Bean(name = "primaryDataSource",
        initMethod = "init",
        destroyMethod = "close")
  public DataSource dataSource() { ... }

  destroyMethod = "(inferred)": Spring auto-detects close() or
                                shutdown() methods (like Closeable).
  destroyMethod = "":           Disable auto-detection.

================================================================
@ConfigurationProperties — BINDING STRUCTURED CONFIG
================================================================

  # application.properties
  app.datasource.url=jdbc:postgresql://localhost/mydb
  app.datasource.username=admin
  app.datasource.max-pool-size=10

  @ConfigurationProperties(prefix = "app.datasource")
  @Component  // or @Bean method return type
  public class DataSourceProperties {
      private String url;
      private String username;
      private int maxPoolSize = 5;  // default
      // getters + setters required
  }

  @Configuration
  public class DataSourceConfig {

      @Bean
      public DataSource dataSource(DataSourceProperties props) {
          HikariDataSource ds = new HikariDataSource();
          ds.setJdbcUrl(props.getUrl());
          ds.setUsername(props.getUsername());
          ds.setMaximumPoolSize(props.getMaxPoolSize());
          return ds;
      }
  }

  Benefits:
    ✓ Type-safe (validated at startup)
    ✓ IDE auto-completion with spring-configuration-processor
    ✓ Supports nested objects and lists
    ✓ Relaxed binding: max-pool-size ≡ maxPoolSize ≡ MAX_POOL_SIZE

================================================================
XML vs JAVA CONFIG — COMPARISON
================================================================

  Aspect               | XML                        | Java Config
  ---------------------|----------------------------|---------------------
  Type safety          | None (string class names)  | Full compile-time
  Refactoring support  | Manual                     | IDE rename works
  Visibility           | External file              | Code-level, in IDE
  Conditional logic    | Limited (SpEL)             | Full Java (if/for)
  Third-party beans    | Verbose but possible       | Clean @Bean method
  Testing override     | Requires separate XML      | @TestConfiguration
  Readability          | Verbose                    | Concise
  Legacy compatibility | ✓ Common in old code       | Modern standard

================================================================
MIXING XML AND JAVA CONFIG
================================================================

  Import XML from Java:
    @Configuration
    @ImportResource("classpath:legacy-beans.xml")
    public class AppConfig { }

  Import Java from XML:
    <context:component-scan base-package="com.example.config"/>

  // This lets you migrate gradually from XML to Java Config.

================================================================
INTERVIEW QUESTIONS — CONFIGURATION
================================================================

  Q: What is the difference between @Configuration and @Component?
  A: @Configuration marks a class as a source of @Bean definitions.
     It's CGLIB-proxied so @Bean method calls return singletons.
     @Component is a generic stereotype; @Bean methods in it run
     without proxying (lite mode — each call creates a new instance).

  Q: How do you import configuration from another @Configuration class?
  A: Use @Import(OtherConfig.class) or place it in the same scan path.

  Q: What is @ConfigurationProperties and its advantage over @Value?
  A: @ConfigurationProperties binds a whole group of properties to a
     typed POJO with validation support. @Value injects individual
     properties but doesn't support structured binding or validation.

  Q: How can you override beans from XML using Java Config?
  A: Use @ImportResource to include the XML, then define a @Bean with
     the same name — Java Config beans take precedence.

  Q: What does @PropertySource do?
  A: Registers a properties file as a PropertySource in the Environment,
     making its values available via @Value and Environment.getProperty().
