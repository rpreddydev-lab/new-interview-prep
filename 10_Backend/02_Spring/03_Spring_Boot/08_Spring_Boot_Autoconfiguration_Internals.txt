================================================================
  SPRING BOOT AUTO-CONFIGURATION INTERNALS — DEEP DIVE
================================================================

================================================================
THE FULL FLOW — STEP BY STEP
================================================================

  When you call SpringApplication.run(MyApp.class, args):

  1. @SpringBootApplication
       └─► @EnableAutoConfiguration
             └─► @Import(AutoConfigurationImportSelector.class)

  2. AutoConfigurationImportSelector.selectImports() is called
     by the Spring container during configuration loading.

  3. It calls getCandidateConfigurations() which reads:
       Spring Boot 3.x:
         META-INF/spring/
           org.springframework.boot.autoconfigure.AutoConfiguration.imports
       Spring Boot 2.x:
         META-INF/spring.factories
           key: org.springframework.boot.autoconfigure.EnableAutoConfiguration

  4. Returns a list of ~140+ auto-configuration class names.

  5. Each class is processed as a @Configuration candidate.
     @Conditional* annotations gate whether it applies.

  6. Passing beans are registered into the ApplicationContext.

================================================================
AutoConfigurationImportSelector — KEY METHODS
================================================================

  selectImports(AnnotationMetadata)
    └─► getAutoConfigurationEntry(metadata)
          ├─► getCandidateConfigurations()       -- reads .imports file
          ├─► removeDuplicates()
          ├─► getExclusions(metadata, attributes) -- @SpringBootApplication.exclude
          ├─► checkExcludedClasses(candidates, exclusions)
          ├─► filter(candidates, autoConfigurationMetadata)
          │     (applies @Conditional filters quickly without loading class)
          └─► fireAutoConfigurationImportEvents()

================================================================
CONDITIONAL EVALUATION PHASES
================================================================

  Two phases for efficiency:

  Phase 1 — PRE-FILTER (without loading class):
    Uses spring-autoconfigure-metadata.properties (generated at build time)
    Checks ConditionalOnClass conditions BEFORE loading the config class
    → avoids ClassNotFoundException and speeds up startup

  Phase 2 — FULL EVALUATION (class loaded):
    Full @Conditional* evaluation on the loaded class
    @ConditionalOnMissingBean requires full context scan

  The metadata file (spring-autoconfigure-metadata.properties):
    org.springframework.boot.autoconfigure.web.servlet
      .WebMvcAutoConfiguration.ConditionalOnClass=\
        javax.servlet.Servlet,\
        org.springframework.web.servlet.DispatcherServlet

================================================================
spring-autoconfigure-metadata.properties
================================================================

  This file is generated by the spring-boot-autoconfigure-processor
  at build time. It encodes @Conditional conditions in a simple
  properties file for fast pre-filtering.

  Generated at: META-INF/spring-autoconfigure-metadata.properties

  Example entries:
    DataSourceAutoConfiguration.ConditionalOnClass=\
      javax.sql.DataSource,...
    DataSourceAutoConfiguration.AutoConfigureBefore=\
      SqlInitializationAutoConfiguration

  This lets Spring Boot pre-filter auto-configs without loading
  each class, dramatically improving startup performance.

================================================================
HOW @ConditionalOnMissingBean WORKS INTERNALLY
================================================================

  OnMissingBeanCondition implements SpringBootCondition:

  1. Parses the @ConditionalOnMissingBean annotation for:
     - type (class)
     - name (bean name)
     - annotation
     - ignored types

  2. Searches the BeanDefinitionRegistry:
     - Already registered beans (from previous @Configuration classes)
     - Parent contexts

  3. Returns ConditionOutcome:
     - MATCH if no matching bean found
     - NO_MATCH if a matching bean already exists

  ORDER MATTERS: @ConditionalOnMissingBean depends on the order
  beans are registered. Use @AutoConfigureAfter to ensure user
  beans are registered before the auto-config's conditional check.

================================================================
WRITING AUTO-CONFIGURATION — DETAILED WALKTHROUGH
================================================================

  Step 1: Create the properties class
  ─────────────────────────────────────
  @ConfigurationProperties(prefix = "notification.email")
  public class EmailNotificationProperties {
      private String smtpHost = "localhost";
      private int smtpPort = 25;
      private boolean ssl = false;
      private String from = "noreply@example.com";
      // getters + setters
  }

  Step 2: Create the auto-configuration class
  ─────────────────────────────────────────────
  @AutoConfiguration
  @ConditionalOnClass(JavaMailSender.class)
  @EnableConfigurationProperties(EmailNotificationProperties.class)
  @ConditionalOnProperty(prefix = "notification.email", name = "enabled",
                         havingValue = "true", matchIfMissing = true)
  public class EmailNotificationAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean(JavaMailSender.class)
      public JavaMailSender javaMailSender(EmailNotificationProperties props) {
          JavaMailSenderImpl sender = new JavaMailSenderImpl();
          sender.setHost(props.getSmtpHost());
          sender.setPort(props.getSmtpPort());

          Properties javaMailProps = sender.getJavaMailProperties();
          javaMailProps.setProperty("mail.smtp.ssl.enable",
              String.valueOf(props.isSsl()));
          return sender;
      }

      @Bean
      @ConditionalOnMissingBean
      public EmailNotificationService emailNotificationService(
              JavaMailSender mailSender,
              EmailNotificationProperties props) {
          return new EmailNotificationService(mailSender, props.getFrom());
      }
  }

  Step 3: Register it
  ─────────────────────
  // Create file:
  // src/main/resources/META-INF/spring/
  //   org.springframework.boot.autoconfigure.AutoConfiguration.imports

  com.example.notification.EmailNotificationAutoConfiguration

  Step 4: (Optional) Add configuration metadata for IDE support
  ──────────────────────────────────────────────────────────────
  // src/main/resources/META-INF/
  //   additional-spring-configuration-metadata.json
  {
    "properties": [
      {
        "name": "notification.email.smtp-host",
        "type": "java.lang.String",
        "description": "SMTP server hostname",
        "defaultValue": "localhost"
      }
    ]
  }

  Or use spring-boot-configuration-processor in build to auto-generate.

================================================================
DEFERRED IMPORT — WHY AUTO-CONFIG LOADS LAST
================================================================

  AutoConfigurationImportSelector implements DeferredImportSelector.
  DeferredImportSelectors are processed AFTER all regular @Configuration
  classes (from @Import) have been processed.

  This ensures:
    • User's @Bean definitions are registered first
    • Auto-config's @ConditionalOnMissingBean can see them
    • User beans always take precedence over auto-config beans

================================================================
@AutoConfigureOrder — CONTROLLING ORDER
================================================================

  Spring processes auto-configurations in this order:
  1. Sorted by @AutoConfigureOrder (default = 0)
  2. Topological sort respecting @AutoConfigureAfter / @AutoConfigureBefore
  3. Natural order within the .imports file otherwise

  @AutoConfiguration(after = DataSourceAutoConfiguration.class)
  public class MyRepoAutoConfiguration { }

  Important: @AutoConfigureAfter does NOT guarantee the other config
  has run — only that if it runs, it runs before this one.

================================================================
CONDITIONAL ON ABSENCE PATTERN — THE OVERRIDE MECHANISM
================================================================

  // Auto-config default:
  @Bean
  @ConditionalOnMissingBean
  public PasswordEncoder passwordEncoder() {
      return new BCryptPasswordEncoder(10);
  }

  // User override — simply declare a bean:
  @Bean
  public PasswordEncoder myCustomEncoder() {
      return new Argon2PasswordEncoder(...);
  }
  // auto-config's @ConditionalOnMissingBean sees this and skips

  This is why Spring Boot says: "opinionated but easy to customize."

================================================================
INTERVIEW QUESTIONS — AUTO-CONFIGURATION INTERNALS
================================================================

  Q: How does Spring Boot decide which auto-configurations to apply?
  A: AutoConfigurationImportSelector reads class names from
     META-INF/spring/...AutoConfiguration.imports. Each class's
     @Conditional* annotations are evaluated, and only passing
     classes register their @Bean methods.

  Q: What is DeferredImportSelector and why does auto-config use it?
  A: It's an ImportSelector that processes imports AFTER all regular
     @Configuration classes. This ensures user beans are registered
     first, so @ConditionalOnMissingBean can see them.

  Q: What is spring-autoconfigure-metadata.properties?
  A: A compile-time-generated file containing @Conditional conditions
     for each auto-configuration class. Spring Boot reads this to
     pre-filter candidates before loading their classes, significantly
     speeding up startup.

  Q: Why is @AutoConfigureAfter important?
  A: It ensures that if configuration A needs beans from configuration B,
     B is processed first. This is critical for @ConditionalOnBean
     dependencies between auto-configurations.

  Q: How do you provide IDE auto-completion for custom starter properties?
  A: Add spring-boot-configuration-processor as an annotation processor
     in the build. It generates META-INF/spring-configuration-metadata.json
     which IDEs use for property completion and documentation.
