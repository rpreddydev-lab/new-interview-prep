======================================================
CUSTOM SPRING BOOT STARTERS & AUTO-CONFIGURATION
======================================================

1. WHY BUILD CUSTOM STARTERS?
──────────────────────────────
Custom starters package reusable infrastructure concerns for teams:
  - Audit logging for all services
  - Common security configuration
  - Observability (metrics, tracing) setup
  - Database multi-tenancy
  - Rate limiting

Benefits:
  - Zero-config for consumers (just add the dependency)
  - Centralized configuration enforcement
  - Consistent setup across microservices
  - Version-controlled via artifact repository


2. STARTER PROJECT STRUCTURE
──────────────────────────────
Convention: two modules (but one is acceptable for small starters):

  audit-spring-boot-starter/          ← uber starter (just brings dependencies)
    pom.xml
      └── depends on: audit-spring-boot-autoconfigure

  audit-spring-boot-autoconfigure/    ← actual logic
    src/main/java/
      com/mycompany/audit/
        AuditAutoConfiguration.java
        AuditService.java
        AuditProperties.java
    src/main/resources/
      META-INF/
        spring/
          org.springframework.boot.autoconfigure.AutoConfiguration.imports  ← Spring Boot 3.x

Naming convention:
  Official Spring starters: spring-boot-starter-*
  Third-party starters:     *-spring-boot-starter  (e.g., audit-spring-boot-starter)


3. STEP-BY-STEP IMPLEMENTATION
────────────────────────────────

STEP 1: Properties class (type-safe configuration):
  @ConfigurationProperties(prefix = "mycompany.audit")
  @Validated
  public class AuditProperties {
      private boolean enabled = true;
      private String logLevel = "INFO";
      private List<String> excludedPaths = new ArrayList<>();

      // getters + setters
  }

STEP 2: Main service:
  public class AuditService {
      private final AuditProperties properties;

      public AuditService(AuditProperties properties) {
          this.properties = properties;
      }

      public void audit(String action, String userId) {
          if (properties.isEnabled()) {
              log.info("AUDIT | action={} | user={}", action, userId);
          }
      }
  }

STEP 3: Auto-configuration class:
  @AutoConfiguration
  @EnableConfigurationProperties(AuditProperties.class)
  @ConditionalOnClass(AuditService.class)
  @ConditionalOnProperty(prefix = "mycompany.audit", name = "enabled",
                         havingValue = "true", matchIfMissing = true)
  public class AuditAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean   // allows consumer to override
      public AuditService auditService(AuditProperties properties) {
          return new AuditService(properties);
      }

      @Bean
      @ConditionalOnMissingBean
      @ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
      public AuditFilter auditFilter(AuditService auditService) {
          return new AuditFilter(auditService);
      }
  }

STEP 4: Register auto-configuration (Spring Boot 3.x):
  File: src/main/resources/META-INF/spring/
        org.springframework.boot.autoconfigure.AutoConfiguration.imports

  Content:
    com.mycompany.audit.AuditAutoConfiguration

  (Spring Boot 2.x used META-INF/spring.factories — still supported in 3.x)


4. CONDITIONAL ANNOTATIONS
────────────────────────────
@ConditionalOnClass(SomeClass.class)
  → Only auto-configure if SomeClass is on the classpath
  → Use to make starter optional (if dependency present → configure it)

@ConditionalOnMissingClass("some.Class")
  → Configure only if class NOT present

@ConditionalOnBean(SomeBean.class)
  → Configure only if another bean is already registered

@ConditionalOnMissingBean
  → Configure bean only if the consumer hasn't defined one themselves
  → ESSENTIAL in auto-configuration: always use this to allow overrides

@ConditionalOnProperty(prefix = "myapp", name = "enabled",
                       havingValue = "true", matchIfMissing = true)
  → Configure based on property value
  → matchIfMissing=true: configure even if property is absent (opt-out)
  → matchIfMissing=false: only configure if property explicitly set (opt-in)

@ConditionalOnWebApplication(type = Type.SERVLET)
  → Only in servlet-based web applications

@ConditionalOnWebApplication(type = Type.REACTIVE)
  → Only in reactive (WebFlux) applications

@ConditionalOnExpression("${feature.x.enabled:true} && ${db.available:true}")
  → SpEL expression condition


5. CONFIGURATION METADATA (IDE SUPPORT)
──────────────────────────────────────────
Add this to get IDE autocomplete for your custom properties:

  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
  </dependency>

Generates: META-INF/spring-configuration-metadata.json at build time.
IDE shows: property descriptions, default values, type info in application.yml.

Add descriptions via JavaDoc on @ConfigurationProperties fields:
  /**
   * Whether audit logging is enabled.
   */
  private boolean enabled = true;


6. AUTO-CONFIGURATION ORDER
──────────────────────────────
Control when your auto-configuration runs relative to others:
  @AutoConfiguration(after = DataSourceAutoConfiguration.class)
  public class MyDataAwareAutoConfiguration { ... }

  @AutoConfiguration(before = SecurityAutoConfiguration.class)
  public class MySecurityPreconfiguration { ... }

  @AutoConfigureAfter(DataSourceAutoConfiguration.class)  // older annotation style
  @AutoConfigureBefore(SecurityAutoConfiguration.class)   // older annotation style

Spring Boot 3.x: use @AutoConfiguration(after=, before=) directly.


7. TESTING YOUR AUTO-CONFIGURATION
────────────────────────────────────
  class AuditAutoConfigurationTest {

      private final ApplicationContextRunner contextRunner =
          new ApplicationContextRunner()
              .withConfiguration(AutoConfigurations.of(AuditAutoConfiguration.class));

      @Test
      void auditServiceIsAutoConfiguredByDefault() {
          contextRunner.run(context -> {
              assertThat(context).hasSingleBean(AuditService.class);
          });
      }

      @Test
      void auditServiceNotConfiguredWhenDisabled() {
          contextRunner
              .withPropertyValues("mycompany.audit.enabled=false")
              .run(context -> {
                  assertThat(context).doesNotHaveBean(AuditService.class);
              });
      }

      @Test
      void userDefinedAuditServiceTakesPrecedence() {
          contextRunner
              .withUserConfiguration(CustomAuditConfig.class)
              .run(context -> {
                  assertThat(context).hasSingleBean(AuditService.class);
                  assertThat(context.getBean(AuditService.class))
                      .isInstanceOf(CustomAuditService.class);
              });
      }
  }

ApplicationContextRunner is the standard test utility for auto-configuration.


8. COMMON PATTERNS IN AUTO-CONFIGURATION
──────────────────────────────────────────

Pattern: Feature toggle via property
  @ConditionalOnProperty(prefix = "myapp.feature-x", name = "enabled",
                         matchIfMissing = false)  // opt-in
  @Bean
  public FeatureXService featureXService() { ... }

Pattern: Provide default, allow override
  @Bean
  @ConditionalOnMissingBean
  public MetricsService defaultMetricsService() {
      return new DefaultMetricsService();
  }

Pattern: Conditional on multiple beans
  @Bean
  @ConditionalOnBean({DataSource.class, JpaTransactionManager.class})
  public AuditEntityListener auditEntityListener() { ... }

Pattern: Conditional on profile (use sparingly in starters)
  @Profile("!test")
  @Bean
  public SecurityEnforcer securityEnforcer() { ... }


9. INTERVIEW QUESTIONS
──────────────────────
Q: What is a Spring Boot custom starter and when would you build one?
A: A starter is a reusable, auto-configured library. Build one when you have
   cross-cutting infrastructure concerns (audit logging, security, metrics)
   that multiple services need to share consistently without manual setup.

Q: What is the difference between @AutoConfiguration and @Configuration?
A: @AutoConfiguration is a specialized @Configuration used in auto-configuration
   classes. It supports after/before ordering, is detected via
   AutoConfiguration.imports, and Spring Boot treats it specially during
   the auto-configuration processing phase.

Q: What does @ConditionalOnMissingBean do and why is it essential?
A: It registers a bean only if no bean of that type is already defined.
   This is essential in auto-configuration to allow consumers to override
   default beans. Without it, your starter's beans would conflict with
   consumer-defined beans.

Q: How does Spring Boot discover auto-configuration classes?
A: Spring Boot 3.x reads META-INF/spring/org.springframework.boot.autoconfigure
   .AutoConfiguration.imports file. Each line is a fully qualified class name.
   Spring Boot 2.x used META-INF/spring.factories (still supported in 3.x).

Q: How do you test an auto-configuration class?
A: Use ApplicationContextRunner (or ReactiveWebApplicationContextRunner for
   WebFlux). It creates a lightweight ApplicationContext for testing without
   starting a full Spring Boot application. Use .withPropertyValues() to
   test conditional behavior and .withUserConfiguration() to test overrides.
