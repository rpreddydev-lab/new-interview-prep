N+1 PROBLEM (Most-Asked Performance Question)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1: What is the N+1 problem?
A: Loading N parent entities triggers N additional SELECT queries to load
   a LAZY association. One SELECT for the list + one per entity = N+1 total.
   Example: loading 100 orders then accessing order.getCustomer() = 101 queries.

Q2: How do you detect the N+1 problem?
A: Enable SQL logging (spring.jpa.show-sql=true). Look for repeated similar
   SELECTs in a loop. Use Hibernate Statistics (logStatisticsEnabled=true)
   to see query counts. Datasource-proxy / p6spy count queries per request.

Q3: What are all the ways to fix N+1?
A: (1) JOIN FETCH: SELECT o FROM Order o JOIN FETCH o.customer.
   (2) @EntityGraph on repository method.
   (3) @BatchSize(size=N) on association: replaces N selects with N/batch IN-clause selects.
   (4) @Fetch(FetchMode.SUBSELECT): one extra subquery fetches all associations.
   (5) DTO projection: SELECT new OrderDto(o.id, c.name) — no association loading.

Q4: When should you use JOIN FETCH vs @BatchSize?
A: JOIN FETCH: use when you always need the association; load them together.
   @BatchSize: use when you access associations conditionally, or when multiple
   associations would cause MultipleBagFetchException. @BatchSize is also
   less impactful on pagination.

Q5: Can JOIN FETCH cause its own problems?
A: Yes: (1) Cartesian product — multiple JOIN FETCHes multiply result rows.
   (2) Pagination + JOIN FETCH on collections = in-memory pagination (Hibernate
   warning: "HHH90003004"). Hibernate fetches ALL rows, then paginates in memory.
   Fix: use @BatchSize or separate queries when paginating over entities with collections.

FETCH STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q6: What is the default fetch type for each JPA annotation?
A: @OneToMany → LAZY (collection, never EAGER)
   @ManyToMany → LAZY
   @ManyToOne → EAGER (single entity — change to LAZY always)
   @OneToOne  → EAGER (single entity — change to LAZY always)

Q7: What problem does EAGER fetching cause?
A: (1) All associations loaded on every query — even when not needed.
   (2) findAll() with EAGER @ManyToOne = N+1 or Cartesian product.
   (3) MultipleBagFetchException when multiple EAGER collections.
   Rule: always use LAZY; control loading per-query with JOIN FETCH / @EntityGraph.

Q8: What is @EntityGraph?
A: Declarative way to specify which associations to fetch eagerly for a specific
   query. Defined inline (@EntityGraph(attributePaths={"orders"})) or named
   (@NamedEntityGraph). Use on Spring Data repository methods without changing
   the entity default fetch type.

Q9: What is EntityGraphType.FETCH vs LOAD?
A: FETCH: only the specified attributes are eagerly loaded; all others use LAZY.
   LOAD: specified attributes are eagerly loaded; others use their default fetch type.
   FETCH is the safer choice — explicit control over what loads.

Q10: How can you solve MultipleBagFetchException?
A: Cannot JOIN FETCH two LAZY Bags simultaneously. Solutions:
   (1) Change List to Set on the associations (no ORDER guarantee).
   (2) Use @BatchSize on each collection — Hibernate uses IN-clause batching.
   (3) Split into two separate queries and merge in Java.
   (4) Use two @EntityGraphs via separate repository methods.

PROJECTIONS AND DTOs
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q11: Why are DTO projections faster than loading entities?
A: DTOs skip: (1) entity lifecycle management; (2) 1LC storage;
   (3) dirty checking snapshot creation; (4) proxy creation for associations.
   Also: load only needed columns (SELECT id, name vs SELECT *).

Q12: What are interface projections in Spring Data?
A: Return type is an interface with getter methods matching entity fields.
   Spring Data generates a proxy. Only declared fields are included in SELECT.
   Supports SpEL computed values: @Value("#{target.firstName + ' ' + target.lastName}").

Q13: What is a DTO/record projection?
A: A class or record in the JPQL constructor expression:
   SELECT new com.example.UserDto(u.id, u.email) FROM User u.
   Or a Java record matching field order in the query. Fully type-safe.

Q14: When should you use @Transactional(readOnly=true)?
A: For read-only service methods. Benefits:
   (1) Hibernate skips dirty checking (no snapshot comparison on flush).
   (2) Spring can route to read replica if using AbstractRoutingDataSource.
   (3) Some DBs optimize FOR READ ONLY (PostgreSQL defers XID assignment).

Q15: What is @Immutable in Hibernate?
A: Entity is never dirty-checked and Hibernate skips generating UPDATE SQL for it.
   Any change attempt is silently ignored. Perfect for reference data / history tables.
   Also applies to collections: @Immutable collection — no insert/remove/update.

PAGINATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q16: What is the JOIN FETCH + Pageable trap?
A: Using Pageable with a query that JOIN FETCHes a collection causes Hibernate
   to load ALL matching rows in memory, then paginate in Java. Large datasets
   cause OOM and slow performance. Hibernate logs warning HHH90003004.
   Fix: use @BatchSize, or paginate the parent entity query without JOIN FETCH,
   then use @BatchSize to load associations in separate batched queries.

Q17: What is the difference between Page and Slice?
A: Page: runs TWO queries (data + COUNT(*) for totalElements). Good for UI pagination.
   Slice: runs ONE query (data + 1 extra row to check hasNext()). No total count.
   Use Slice for infinite scroll or cursor-based pagination.

Q18: What is keyset/cursor pagination? When is it better than OFFSET?
A: Keyset: WHERE id > :lastId LIMIT N. Performance O(log N) using index.
   OFFSET: SKIP N rows — DB must scan and discard rows. Performance O(N).
   Keyset is dramatically faster on large datasets; drawback is no random-page access.

Q19: What is Spring Data 3.1 Scroll API?
A: Window<T> with ScrollPosition. Supports both OFFSET and KEYSET cursor scrolling.
   Repository method returns Window<T>, next call passes position from previous result.
   Provides a framework-level abstraction over cursor-based pagination.

BATCH PROCESSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q20: How do you batch insert 100,000 rows efficiently?
A: 1. spring.jpa.properties.hibernate.jdbc.batch_size=50
   2. hibernate.order_inserts=true / hibernate.order_updates=true
   3. Use @GeneratedValue(strategy=SEQUENCE) — IDENTITY disables batching.
   4. Loop with flush+clear every 50 rows to prevent 1LC memory growth.
   5. For maximum throughput: use StatelessSession (no 1LC, no dirty check).

Q21: Why does IDENTITY generation strategy disable JDBC batching?
A: IDENTITY requires the DB to return the generated ID immediately after each INSERT.
   Hibernate must know the entity's ID to store it in 1LC. This forces one INSERT at a time.
   SEQUENCE pre-allocates ID ranges (allocationSize=50 means 50 IDs from one DB call),
   allowing Hibernate to batch multiple INSERTs before flushing.

Q22: What is the flush+clear pattern?
A: In a batch loop:
   if (i % batchSize == 0) { em.flush(); em.clear(); }
   flush() sends accumulated SQL to DB. clear() removes all entities from 1LC.
   Without clear(), 1LC grows unbounded holding all entities, causing OOM or slowdown.

Q23: What is @Modifying bulk update and when do you use it?
A: Spring Data @Modifying + @Query("UPDATE User u SET u.status=:s WHERE...")
   executes a single UPDATE affecting many rows. Bypasses dirty checking and 1LC.
   Always add clearAutomatically=true to evict stale 1LC state:
   @Modifying(clearAutomatically=true, flushAutomatically=true).

CACHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q24: When should you use second-level cache?
A: Use 2LC for entities that are: read often, rarely written, shared across users.
   Examples: countries, currencies, product categories, configuration.
   Don't use for entities with frequent writes — cache invalidation overhead
   and cache miss patterns will hurt rather than help.

Q25: How does 2LC interact with Spring @Cacheable?
A: Hibernate 2LC caches entity state. Spring @Cacheable caches method return values.
   They operate at different layers. Use Hibernate 2LC for entity caching.
   Use Spring @Cacheable for service-level or query result caching (e.g., cache a
   full page of results from a complex join).

CONNECTION POOLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q26: What is HikariCP and why is it the default in Spring Boot?
A: HikariCP is a high-performance JDBC connection pool. Default since Spring Boot 2.
   Known for low latency, minimal overhead, reliable behavior under load.
   Benchmarks consistently rank it fastest among JDBC pools.

Q27: How do you size a HikariCP pool?
A: Formula: pool_size = (core_count × 2) + effective_spindles.
   For a 4-core server with SSD: 4×2+1 = 9. Counterintuitively, larger pools
   are often slower — excessive threads compete for CPU. Start small and measure.

Q28: What is connection pool exhaustion?
A: All connections in the pool are in use; new requests wait until
   connectionTimeout (default 30s). Causes: long transactions holding connections,
   thread leaks, pool too small for load. Detect with leakDetectionThreshold.
   Fix: reduce transaction time, increase pool size modestly, add metrics.

Q29: What HikariCP property detects connection leaks?
A: spring.datasource.hikari.leak-detection-threshold=2000 (ms).
   If a connection is held longer than threshold, Hikari logs a warning
   with the stack trace of where it was acquired. Set to ~2× expected max
   transaction duration.

DIAGNOSTICS AND MONITORING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q30: How do you log actual SQL with bind parameters?
A: logging.level.org.hibernate.SQL=DEBUG
   logging.level.org.hibernate.orm.jdbc.bind=TRACE   (Hibernate 6)
   For production use datasource-proxy (captures at DataSource level,
   logs parameters, counts queries, measures duration).

Q31: What is Hibernate Statistics?
A: Enable with spring.jpa.properties.hibernate.generate_statistics=true.
   Reports: entity loads, collection loads, queries executed, L2C hit/miss,
   transaction counts. Access via SessionFactory.getStatistics(). Export to Micrometer.

Q32: How do you measure slow queries in JPA?
A: (1) DB slow query log (postgres log_min_duration_statement).
   (2) datasource-proxy with threshold: log queries > 500ms.
   (3) Spring Boot Actuator + Micrometer: spring.datasource.hikari.metrics-registry.
   (4) APM tools (Datadog, New Relic, Jaeger tracing + DB spans).

OPEN-IN-VIEW ANTI-PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q33: What is open-in-view and why is it bad?
A: OpenEntityManagerInViewFilter (enabled by default in Spring Boot) keeps the
   EntityManager open through the entire HTTP request including view rendering.
   Problems: (1) DB connection held for entire request duration; (2) lazy loading
   silently fires in controller/view layer (hidden N+1); (3) misleads developers.
   Fix: spring.jpa.open-in-view=false and load everything you need in the service layer.

SCENARIO QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q34: You have a REST API that returns a list of orders with customer names.
     It runs 101 queries for 100 orders. How do you fix it?
A: Classic N+1 on Customer association. Options:
   (1) Add JOIN FETCH: @Query("SELECT o FROM Order o JOIN FETCH o.customer")
   (2) Add @EntityGraph(attributePaths="customer") on the repository method.
   (3) Return DTO: SELECT new OrderSummaryDto(o.id, c.name) FROM Order o JOIN o.customer c.
   Best: use DTO projection — no entity lifecycle overhead, lean SELECT.

Q35: Your paginated endpoint with 20-items-per-page is slow at page 500.
     Why and how do you fix it?
A: OFFSET pagination requires the DB to scan and skip 500×20=10,000 rows.
   O(N) scan. Fix: keyset pagination. Store the last seen id, next page:
   WHERE id > :lastId ORDER BY id LIMIT 20. O(log N) index lookup.

Q36: An endpoint needs to export 500,000 records to CSV. How?
A: (1) Stream results: use Slice/ScrollableResults or JpaCursorItemReader.
   (2) Use StatelessSession to avoid 1LC memory buildup.
   (3) Flush+clear every N rows.
   (4) Use DTO projection — don't load full entities.
   (5) Write CSV in chunks; stream HTTP response if via REST.

Q37: findAll() in a service method is slow. Walk me through debugging.
A: Step 1: Enable SQL logging → count queries. N+1?
   Step 2: Check EXPLAIN ANALYZE on the generated SQL → missing index?
   Step 3: Check if projections can replace full entity load.
   Step 4: Is EAGER fetch type loading unwanted associations?
   Step 5: Add pagination — should rarely call findAll() without limit.

Q38: Two @ManyToMany associations cause MultipleBagFetchException. Fix?
A: Option A: Change both List<X> to Set<X> — allows multiple JOIN FETCH but
   loses ordering and can create Cartesian product.
   Option B: @BatchSize(size=20) on both collections — no Cartesian, IN-clause batching.
   Option C: Two separate repository queries merged in service layer.

Q39: After running a bulk UPDATE via @Modifying, a subsequent findById
     returns stale data. Why?
A: Bulk UPDATE bypasses Hibernate 1LC. Entity in 1LC still has old values.
   Fix: @Modifying(clearAutomatically=true) to evict entire 1LC after update.
   Or call em.clear() manually, or em.refresh(entity) for a specific entity.

Q40: What is @DynamicUpdate and when is it worth adding?
A: @DynamicUpdate generates UPDATE SQL with only changed columns instead of all.
   Worth it when: (1) table is wide (50+ columns); (2) frequent partial updates;
   (3) row-level locking contention — narrower WHERE conditions help.
   Not worth it: small tables or when all columns typically change anyway.

Q41: You need both read replicas and a primary DB. How do you route JPA queries?
A: Implement AbstractRoutingDataSource — map transaction readOnly=true to read replica.
   ReadWriteRoutingDataSource extends AbstractRoutingDataSource, overrides
   determineCurrentLookupKey() to return "read" if current tx is readOnly, else "write".
   @Transactional(readOnly=true) service methods auto-route to replica.

Q42: What causes high CPU with Hibernate even with few DB queries?
A: Likely dirty checking: loading many entities per request → Hibernate compares
   N × M fields on every flush. Fix: (1) DTO projections; (2) @Immutable for
   read-only queries; (3) @Transactional(readOnly=true) skips dirty check;
   (4) reduce entity load size with pagination.

Q43: How do you benchmark the impact of your JPA change?
A: (1) Baseline: measure queries-per-request and latency before change.
   (2) Enable Hibernate Statistics, capture query count, entity load count.
   (3) Load test with wrk/k6/Gatling to get p99 latency.
   (4) Compare DB CPU and slow query log after change.
   (5) Use Testcontainers + datasource-proxy in unit tests to assert query counts.

Q44: What is the difference between fetching via JOIN FETCH and
     @BatchSize in terms of SQL generated?
A: JOIN FETCH: SELECT o.*, c.* FROM orders o JOIN customers c ON o.customer_id=c.id.
   ONE query, returns all data but multiplies rows for collections.
   @BatchSize: SELECT * FROM customers WHERE id IN (1,2,3,...,N).
   Multiple queries (one per batch), but no row multiplication.
   JOIN FETCH is faster for single association; @BatchSize better for
   multiple associations or pagination scenarios.

Q45: What is the recommended general approach to ORM performance?
A: 1. Make all fetch types LAZY by default.
   2. Use DTO projections for read-only endpoints (most endpoints are reads).
   3. Detect N+1 early: enable SQL logging in tests; use datasource-proxy.
   4. Never call findAll() without Pageable.
   5. Use JOIN FETCH or @EntityGraph only for associations always needed.
   6. Use @BatchSize for conditional/collection access.
   7. Separate read and write models (CQRS) for complex domains.
   8. Profile before optimizing — don't add complexity prematurely.
