SCHEMA MIGRATION INTERVIEW QUESTIONS
=====================================

=== FLYWAY VS LIQUIBASE — COMPARISON QUESTIONS ===

Q1: What is the difference between Flyway and Liquibase?
A:  Both are database migration tools that version-control schema changes.

    Flyway:
    - Uses SQL migration scripts (or Java-based migrations)
    - Migration files: V1__create_users.sql, V2__add_email_index.sql
    - Simple, SQL-first, easy to understand
    - Convention: V{version}__{description}.sql
    - Less flexible but lower learning curve

    Liquibase:
    - Uses changesets in XML, YAML, JSON, or SQL
    - Database-agnostic (generates DB-specific SQL)
    - Supports rollback out-of-the-box (Flyway community: no rollback)
    - More complex but more powerful
    - Tracks changes with checksum of each changeset

    When to use Flyway:
    - Team is SQL-centric, likes raw SQL control
    - Simpler projects, fewer environments
    - Spring Boot (first-class auto-configuration)

    When to use Liquibase:
    - Multi-database support (same changeset for Oracle, PostgreSQL, MySQL)
    - Need rollback capability
    - Complex enterprise environments

Q2: What does Flyway's flyway_schema_history table contain?
A:  Flyway creates a tracking table (default: flyway_schema_history) with:
    - installed_rank: sequence number of execution
    - version: migration version (V1, V2, etc.)
    - description: script description
    - type: SQL, JAVA, etc.
    - script: filename of migration
    - checksum: hash of script content (detects tampering)
    - installed_by: DB user
    - installed_on: timestamp
    - execution_time: ms
    - success: boolean

    Flyway compares applied migrations against filesystem at startup.
    If checksums don't match → startup FAILS (prevents running altered scripts).

Q3: What happens if you modify an already-applied Flyway migration?
A:  Flyway detects the checksum mismatch and throws FlywayValidationException.
    Application WILL NOT start — preventing schema inconsistency.

    Solutions:
    - NEVER modify applied migrations
    - Create a new migration (V5__fix_previous_issue.sql) instead
    - In dev: flyway.cleanOnValidationError=true (destroys data — dev only!)
    - For emergencies: flyway repair command (clears failed migrations from history)

Q4: What are Flyway repeatable migrations?
A:  Versioned migrations: V1, V2, V3 — run exactly once.
    Repeatable migrations: R__create_views.sql — run whenever file changes.

    Prefix: R instead of V.
    Use for: views, stored procedures, functions — things that can be recreated.
    File: R__update_reporting_views.sql

    Flyway runs repeatable migrations after all versioned migrations.
    If checksum changes → runs again.

=== FLYWAY IN SPRING BOOT ===

Q5: How does Flyway integrate with Spring Boot?
A:  spring-boot-starter-data-jpa or spring-boot-starter-flyway includes Flyway.
    Spring Boot auto-configures Flyway and runs migrations at startup (before app).

    application.yml:
      spring:
        flyway:
          enabled: true
          locations: classpath:db/migration
          baseline-on-migrate: true   # for existing DB with no history
          out-of-order: false         # disallow V3 after V4 was applied
          validate-on-migrate: true   # checksum validation (default)
          table: flyway_schema_history  # default tracking table name

    Files in: src/main/resources/db/migration/
    Format: V{version}__{description}.sql
    Example: V1__create_user_table.sql

Q6: What is baseline-on-migrate?
A:  For existing databases that have schema but no Flyway history:
    baseline-on-migrate=true → Flyway marks the current state as baseline (V1)
    and only runs migrations V2 and above.
    Without it: Flyway would try to run V1 on an existing table → fails.

=== LIQUIBASE SPECIFIC ===

Q7: What is a changeset in Liquibase?
A:  A changeset is an atomic unit of schema change in Liquibase.

    changelog.xml:
      <changeSet id="1" author="john">
          <createTable tableName="users">
              <column name="id" type="bigint" autoIncrement="true">
                  <constraints primaryKey="true"/>
              </column>
              <column name="email" type="varchar(255)">
                  <constraints nullable="false" unique="true"/>
              </column>
          </createTable>
      </changeSet>

    Each changeset has a unique id+author combination.
    Liquibase tracks applied changesets in DATABASECHANGELOG table.
    checksum: stored and verified to detect modification.

Q8: How does Liquibase rollback work?
A:  Liquibase supports rollback to a previous state:

    Automatic rollback: for simple operations (createTable → dropTable)
    Manual rollback: specify <rollback> tag in changeset:
      <changeSet id="3" author="john">
          <addColumn tableName="users">
              <column name="phone" type="varchar(20)"/>
          </addColumn>
          <rollback>
              <dropColumn tableName="users" columnName="phone"/>
          </rollback>
      </changeSet>

    Run rollback:
      liquibase rollback --tag=v1.0        // rollback to tag
      liquibase rollbackCount 2            // rollback last 2 changesets
      liquibase rollbackToDate 2024-01-01  // rollback to date

Q9: How do you handle migrations in a multi-tenant application?
A:  Approach 1: Schema-per-tenant
    Each tenant has its own schema. Flyway/Liquibase run per-schema.
    Flyway: configure target schema dynamically for each tenant migration.

    Approach 2: Shared schema with tenant_id column
    Single migration applies to all. Tenant isolation via SQL WHERE tenant_id=?

    Approach 3: Database-per-tenant
    Each tenant has their own database. Run migrations per database.

=== BEST PRACTICES ===

Q10: What are migration best practices for CI/CD?
A:  1. Never modify applied migrations — create new ones
    2. Keep migrations backward compatible (blue-green deployments)
        - Add columns as nullable initially
        - Remove columns in separate migration after old code is gone
    3. Test migrations in staging before production
    4. Use transaction-aware migrations (wrap DDL in transactions where supported)
    5. Separate DDL (schema) from DML (data) migrations for clarity
    6. Name clearly: V15__add_index_on_orders_created_at.sql
    7. For large tables: add indexes CONCURRENTLY (PostgreSQL), avoid lock
    8. Test rollback strategy before running in production
    9. Use CI validation: run migrations against clean DB in pipeline

Q11: What is a zero-downtime deployment migration strategy?
A:  Expand-Contract pattern (3-phase migration):

    Phase 1 — Expand:
      Add new column as nullable (old code doesn't know about it, still works)
      Both old and new code can run simultaneously.

    Phase 2 — Migrate:
      Deploy new code that writes to both old and new column.
      Run data migration: backfill new column from old column.

    Phase 3 — Contract:
      Once all data backfilled and old code removed:
      Drop old column, add NOT NULL constraint to new column.

    This allows schema and code changes without downtime.
