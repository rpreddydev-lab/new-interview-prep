ORM vs Raw SQL — Deep Comparison
================================================================

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. CORE PHILOSOPHY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Raw SQL (JDBC):
  - You write every SELECT, INSERT, UPDATE, DELETE
  - Full control of every byte sent to DB
  - Boilerplate: open connection → prepare statement → bind params
    → execute → map ResultSet → close resources

ORM (JPA/Hibernate):
  - You write Java code; ORM generates SQL
  - Entities are first-class citizens
  - Automatic dirty checking, caching, lazy loading
  - Trade-off: less control, more magic

2. CODE COMPARISON
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCENARIO: Find all orders for a user with id = 42

── Raw JDBC ──────────────────────────────────────────────────
String sql = "SELECT * FROM orders WHERE user_id = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setLong(1, 42L);
    ResultSet rs = ps.executeQuery();
    List<Order> orders = new ArrayList<>();
    while (rs.next()) {
        Order o = new Order();
        o.setId(rs.getLong("id"));
        o.setTotal(rs.getBigDecimal("total"));
        o.setStatus(rs.getString("status"));
        orders.add(o);
    }
    return orders;
}

── Spring JDBC (JdbcTemplate) ────────────────────────────────
List<Order> orders = jdbcTemplate.query(
    "SELECT * FROM orders WHERE user_id = ?",
    new BeanPropertyRowMapper<>(Order.class),
    42L
);

── JPA / Spring Data JPA ─────────────────────────────────────
List<Order> orders = orderRepository.findByUserId(42L);
// ORM generates: SELECT o FROM Order o WHERE o.user.id = :id

── MyBatis (SQL Mapper — middle ground) ─────────────────────
@Select("SELECT * FROM orders WHERE user_id = #{userId}")
List<Order> findByUserId(@Param("userId") Long userId);

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Criterion              | Raw JDBC / SQL       | ORM (JPA/Hibernate)
───────────────────────|──────────────────────|────────────────────────────
Boilerplate            | Very high            | Very low
Developer productivity | Low (CRUD = verbose) | High
SQL control            | Full (100%)          | Partial (JPQL, native)
Query optimization     | Manual, precise      | Can be suboptimal
Complex queries        | Easy to write        | Tricky with JPQL
Bulk updates           | Very efficient       | Slow (loads entities)
Learning curve         | Low (know SQL)       | Higher (ORM concepts)
Portability            | DB-specific SQL      | DB-agnostic JPQL
Object graph           | Manual mapping       | Automatic
Cache support          | None (manual)        | 1st + 2nd level cache
Lazy loading           | Manual               | Built-in
Schema migration       | Manual               | Flyway/Liquibase/DDL-auto
Debugging SQL          | You write it         | Use show-sql=true
Performance (bulk)     | ★★★★★               | ★★☆☆☆
Performance (CRUD)     | ★★★☆☆               | ★★★★☆
Maintenance            | Hard (string SQL)    | Easy (refactor-safe)

4. WHEN TO USE EACH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

USE ORM WHEN:
  ✓ Domain-driven apps with complex object graphs
  ✓ CRUD-heavy applications
  ✓ Team prefers Java-first development
  ✓ You need caching, lazy loading, optimistic locking
  ✓ Portability across databases matters

USE RAW SQL / JDBC WHEN:
  ✓ Batch inserts/updates of millions of rows
  ✓ Complex analytical queries (window functions, CTEs)
  ✓ Reporting / BI queries
  ✓ Performance is critical, every millisecond counts
  ✓ DB-specific features (PostgreSQL JSONB, MySQL full-text, etc.)
  ✓ ETL pipelines

BEST PRACTICE — Hybrid Approach:
  Use ORM (Spring Data JPA) for standard CRUD.
  Drop down to @Query with native SQL or JdbcTemplate for
  complex/reporting queries.

  Example:
  @Repository
  public interface ReportRepository extends JpaRepository<Order, Long> {

      // JPQL for simple queries
      @Query("SELECT o FROM Order o WHERE o.status = :status")
      List<Order> findByStatus(@Param("status") String status);

      // Native SQL for complex reporting
      @Query(value = """
          SELECT u.email, SUM(o.total) as revenue
          FROM orders o
          JOIN users u ON u.id = o.user_id
          WHERE o.created_at >= :since
          GROUP BY u.email
          ORDER BY revenue DESC
          LIMIT 10
          """, nativeQuery = true)
      List<Object[]> topCustomerRevenue(@Param("since") LocalDate since);
  }

5. SQL INJECTION — BOTH NEED PARAMETERIZED QUERIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DANGEROUS (JDBC):
  String sql = "SELECT * FROM users WHERE email = '" + email + "'";
  // Attacker: email = "' OR '1'='1" → dumps all users!

SAFE (JDBC PreparedStatement):
  PreparedStatement ps = conn.prepareStatement(
      "SELECT * FROM users WHERE email = ?"
  );
  ps.setString(1, email);

SAFE (JPA — always parameterized):
  @Query("SELECT u FROM User u WHERE u.email = :email")
  User findByEmail(@Param("email") String email);
  // Parameters are always bound safely

DANGEROUS (JPA with string concat in native query):
  @Query(value = "SELECT * FROM users WHERE email = '" + email + "'",
         nativeQuery = true)  // DON'T DO THIS

Q: What are the downsides of using ORM?
A: N+1 problem, hidden SQL complexity, harder to optimize bulk ops,
   overhead of loading full objects when you only need 2 columns,
   lazy loading issues outside transaction (LazyInitializationException).

Q: When would you prefer JDBC over Hibernate?
A: Bulk INSERT/UPDATE of millions of records (Hibernate loads each entity);
   complex reporting queries with aggregates; DB-specific SQL features;
   when every microsecond of latency matters.

Q: What is MyBatis and how does it differ from Hibernate?
A: MyBatis is a SQL Mapper framework. You write SQL explicitly in XML or
   annotations, but MyBatis handles result mapping. It's a middle ground:
   more control than Hibernate, less boilerplate than raw JDBC.
   Hibernate generates SQL; MyBatis executes your SQL.

Q: Can you mix JPA and native queries in the same app?
A: Yes. Use @Query(nativeQuery = true) in Spring Data JPA, or
   entityManager.createNativeQuery() for complex cases.
