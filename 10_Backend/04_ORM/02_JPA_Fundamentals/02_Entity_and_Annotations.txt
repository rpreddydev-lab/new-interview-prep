1. WHAT MAKES A VALID JPA ENTITY?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Requirements for a JPA Entity class:
  ✓ Annotated with @Entity
  ✓ Has a no-argument constructor (public or protected)
  ✓ Has an @Id field (primary key)
  ✓ Must NOT be final (Hibernate creates proxies via subclassing)
  ✓ Must NOT have final fields or methods (proxy limitation)
  ✓ Must be a top-level class (not inner/anonymous)

@Entity
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    // Required: no-arg constructor
    protected Product() {}

    public Product(String name) { this.name = name; }
}

2. @Entity AND @Table
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Entity
  - Marks a class as a JPA entity
  - Attribute: name = entity name used in JPQL (default: class simple name)

@Table
  - Customizes the table mapping
  - Attributes:
      name        → table name (default: entity name in lowercase)
      schema      → DB schema name
      catalog     → DB catalog name
      uniqueConstraints → define multi-column unique constraints
      indexes     → define DB indexes (DDL hint)

@Entity(name = "UserAccount")    // JPQL uses "UserAccount"
@Table(
    name = "user_accounts",
    schema = "app",
    uniqueConstraints = {
        @UniqueConstraint(name = "uq_email", columnNames = {"email"}),
        @UniqueConstraint(name = "uq_phone", columnNames = {"country_code", "phone"})
    },
    indexes = {
        @Index(name = "idx_user_created", columnList = "created_at DESC")
    }
)
public class User { ... }

3. @COLUMN — COLUMN CUSTOMIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Column Attributes:
  name          → column name (default: field name)
  nullable      → NOT NULL constraint (default: true)
  unique        → unique constraint (default: false)
  length        → VARCHAR length for String (default: 255)
  precision     → total digits for decimal
  scale         → decimal places for decimal
  insertable    → include in INSERT (default: true)
  updatable     → include in UPDATE (default: true)
  columnDefinition → raw SQL column DDL

Examples:

@Column(name = "email", nullable = false, unique = true, length = 100)
private String email;

@Column(name = "price", precision = 10, scale = 2, nullable = false)
private BigDecimal price;

@Column(name = "description", columnDefinition = "TEXT")
private String description;

@Column(name = "created_at", insertable = true, updatable = false)
private LocalDateTime createdAt;

@Column(name = "profile_picture", columnDefinition = "LONGBLOB")
@Lob
private byte[] profilePicture;

4. FIELD ACCESS vs PROPERTY ACCESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JPA supports two access strategies:

FIELD ACCESS (Recommended):
  Put @Id on the FIELD → Hibernate accesses fields directly via reflection

  @Entity
  public class User {
      @Id                       // <-- @Id on field = field access
      private Long id;
      @Column(name = "first_name")
      private String firstName;
  }

PROPERTY ACCESS:
  Put @Id on the GETTER → Hibernate calls getters/setters

  @Entity
  public class User {
      private Long id;
      private String firstName;

      @Id                       // <-- @Id on getter = property access
      public Long getId() { return id; }
  }

Best Practice:
  Always use field access (annotations on fields, not getters).
  Consistent, less surprising behavior with proxies/lazy loading.

  // Mix (override specific fields only):
  @Entity
  @Access(AccessType.FIELD)   // default: field access
  public class User {
      @Id private Long id;

      private String fullName;

      @Access(AccessType.PROPERTY)    // this field uses property access
      @Column(name = "full_name_upper")
      public String getFullNameUpper() {
          return fullName != null ? fullName.toUpperCase() : null;
      }
  }

5. SPECIAL FIELD ANNOTATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

@Transient
  - Field NOT mapped to any column (skipped by ORM entirely)
  - Also use Java `transient` keyword for the same effect

  @Transient
  private String computedFullName;  // calculated, not stored

@Basic
  - Default for all persistent fields (rarely needed explicitly)
  - fetch = FetchType.LAZY → lazily load a column (rare use case for LOBs)
  - optional = false → like nullable = false

  @Basic(fetch = FetchType.LAZY)
  @Lob
  private byte[] largeContent;   // loaded on demand

@Lob
  - Maps large objects: CLOB (text) or BLOB (binary)
  - On String/char[]: maps to CLOB
  - On byte[]/Byte[]/Serializable: maps to BLOB

  @Lob
  @Column(name = "resume_text")
  private String resumeText;   // CLOB

  @Lob
  @Column(name = "avatar")
  private byte[] avatar;       // BLOB

@Temporal (Legacy — for java.util.Date)
  @Temporal(TemporalType.DATE)       → maps to SQL DATE
  @Temporal(TemporalType.TIME)       → maps to SQL TIME
  @Temporal(TemporalType.TIMESTAMP)  → maps to SQL TIMESTAMP

  // Modern Java 8+ — no @Temporal needed:
  private LocalDate birthDate;          // DATE
  private LocalTime meetingTime;        // TIME
  private LocalDateTime createdAt;      // TIMESTAMP
  private ZonedDateTime eventTime;      // TIMESTAMP WITH TIMEZONE (DB-specific)

@Enumerated
  @Enumerated(EnumType.ORDINAL)  → stores 0, 1, 2 (brittle!)
  @Enumerated(EnumType.STRING)   → stores "ACTIVE", "INACTIVE" (recommended)

  @Enumerated(EnumType.STRING)
  @Column(name = "status", length = 20)
  private UserStatus status;

6. @MAPPEDSUPERCLASS — SHARED FIELDS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Use @MappedSuperclass to share common fields across entities
without creating a separate table for the superclass.

@MappedSuperclass
public abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @Version
    private Long version;

    // getters/setters
}

@Entity
@Table(name = "users")
public class User extends BaseEntity {
    private String email;
    // inherits id, createdAt, updatedAt, version
}

@Entity
@Table(name = "products")
public class Product extends BaseEntity {
    private String name;
    // inherits id, createdAt, updatedAt, version
}

IMPORTANT: @MappedSuperclass is NOT itself an entity.
You cannot query it: "FROM BaseEntity" → error.
Use @Inheritance strategies for polymorphic queries.

7. EQUALS AND HASHCODE — CRITICAL FOR JPA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Problem: When entity is transient (id = null), then persisted (id set),
  its hash code changes → breaks Set/HashMap behavior.

Strategy 1: Use DB id (simple but problematic for new entities in sets)
  @Override
  public boolean equals(Object o) {
      if (this == o) return true;
      if (!(o instanceof User)) return false;
      User user = (User) o;
      return id != null && id.equals(user.id);
  }
  @Override
  public int hashCode() {
      return getClass().hashCode();  // stable, entity-class based
  }

Strategy 2: Use natural/business key (email, username, UUID)
  @NaturalId  // Hibernate annotation
  @Column(nullable = false, unique = true)
  private String email;

  @Override
  public boolean equals(Object o) {
      if (this == o) return true;
      if (!(o instanceof User)) return false;
      return Objects.equals(email, ((User) o).email);
  }
  @Override
  public int hashCode() {
      return Objects.hash(email);
  }

Strategy 3: Use UUID as ID (simplest for equals/hashCode)
  @Id
  @GeneratedValue
  @Column(columnDefinition = "uuid", updatable = false)
  private UUID id = UUID.randomUUID();  // set before persist

  @Override
  public boolean equals(Object o) {
      if (this == o) return true;
      if (!(o instanceof User)) return false;
      return Objects.equals(id, ((User) o).id);
  }
  @Override
  public int hashCode() { return Objects.hash(id); }

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Why must a JPA entity have a no-arg constructor?
A: JPA (and Hibernate in particular) creates entity instances via reflection
   when loading data from the DB. It needs a no-arg constructor to instantiate
   the object before setting field values.

Q: Why can't JPA entity classes be final?
A: Hibernate creates CGLIB proxy subclasses for lazy loading. If the class
   is final, it cannot be subclassed, breaking lazy loading for @OneToOne
   and @ManyToOne relationships.

Q: What is the difference between @Transient and Java's transient keyword?
A: @Transient (JPA annotation) excludes a field from ORM mapping.
   Java's transient keyword excludes a field from Java serialization.
   Both can be used together, but @Transient is the one ORM cares about.

Q: Why is EnumType.ORDINAL dangerous?
A: If you reorder the enum values or add one in the middle, all existing
   DB records become incorrect (stored 0/1/2 no longer match enum positions).
   Always use EnumType.STRING.

Q: How do you implement equals/hashCode for JPA entities?
A: Best practice: base equals on the primary key (or natural key).
   Use a stable hashCode (class-based or natural key based).
   Never base hashCode on mutable fields or DB-generated ID if entity
   can be in a Set before being persisted (id would be null).
