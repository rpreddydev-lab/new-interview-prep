1. ENTITYMANAGER — THE CORE API
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EntityManager (EM) is the primary JPA API for:
  - Persisting, reading, updating, removing entities
  - Running JPQL / native queries
  - Managing transactions (in non-Spring environments)
  - Controlling persistence context lifecycle

Key characteristics:
  - NOT thread-safe (never inject as a singleton field directly)
  - Spring injects a thread-local proxy → safe to @Autowired in beans
  - Scoped to a unit of work (usually one transaction)

2. ENTITYMANAGER API — ALL KEY METHODS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// Injecting in Spring (thread-safe via proxy)
@Repository
public class UserRepository {

    @PersistenceContext
    private EntityManager em;

    // ─── PERSIST ───────────────────────────────────────────
    // Makes a TRANSIENT entity MANAGED (tracks it, INSERT on commit)
    public void save(User user) {
        em.persist(user);         // user.id is populated after flush
    }

    // ─── FIND ──────────────────────────────────────────────
    // Returns managed entity (hits 1st-level cache first)
    // Returns null if not found
    public User findById(Long id) {
        return em.find(User.class, id);
    }

    // ─── GETREFERENCE ─────────────────────────────────────
    // Returns a proxy (no DB hit); use for foreign key assignment only
    // Throws EntityNotFoundException on first field access if not found
    public void addOrderToUser(Long userId, Order order) {
        User userProxy = em.getReference(User.class, userId);
        order.setUser(userProxy);   // no SELECT needed!
        em.persist(order);
    }

    // ─── MERGE ────────────────────────────────────────────
    // Re-attaches a DETACHED entity; returns a NEW managed instance
    // Does NOT modify the passed object! Use the returned value.
    public User update(User detachedUser) {
        return em.merge(detachedUser);  // returned entity is managed
    }

    // ─── REMOVE ───────────────────────────────────────────
    // Schedules DELETE; entity must be MANAGED first
    public void delete(Long id) {
        User user = em.find(User.class, id);
        if (user != null) {
            em.remove(user);   // DELETE on commit
        }
    }

    // ─── REFRESH ──────────────────────────────────────────
    // Reloads entity from DB, discarding pending changes
    public void refresh(User user) {
        em.refresh(user);
    }

    // ─── DETACH ───────────────────────────────────────────
    // Stops tracking the entity (removes from persistence context)
    public void detach(User user) {
        em.detach(user);
    }

    // ─── CONTAINS ─────────────────────────────────────────
    // Check if entity is currently managed
    public boolean isManaged(User user) {
        return em.contains(user);
    }

    // ─── FLUSH ────────────────────────────────────────────
    // Synchronize persistence context to DB NOW (within transaction)
    // Called automatically on commit; call manually when needed before query
    public void flush() {
        em.flush();
    }

    // ─── CLEAR ────────────────────────────────────────────
    // Detach ALL entities from persistence context
    // Useful for batch processing to free memory
    public void clear() {
        em.clear();
    }

    // ─── QUERIES ──────────────────────────────────────────
    public List<User> findByEmail(String email) {
        return em.createQuery(
            "SELECT u FROM User u WHERE u.email = :email", User.class)
            .setParameter("email", email)
            .getResultList();
    }

    public Optional<User> findSingleByEmail(String email) {
        try {
            User u = em.createQuery(
                "SELECT u FROM User u WHERE u.email = :email", User.class)
                .setParameter("email", email)
                .getSingleResult();
            return Optional.of(u);
        } catch (NoResultException e) {
            return Optional.empty();
        }
    }
}

3. PERSISTENCE CONTEXT — THE FIRST-LEVEL CACHE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Persistence Context is an in-memory map:
  Map<EntityKey(Class + ID) → Entity Instance>

All managed entities live here. Within one transaction:
  - Same entity loaded twice → same Java object (identity guarantee)
  - Changed fields → tracked for dirty checking
  - On flush → Hibernate compares snapshots → generates UPDATEs

Example — Identity Guarantee:
  User u1 = em.find(User.class, 1L);   // SELECT issued
  User u2 = em.find(User.class, 1L);   // NO SELECT — returned from cache
  assert u1 == u2;   // TRUE — same object reference

Example — Dirty Checking:
  @Transactional
  public void changeEmail(Long id, String newEmail) {
      User user = em.find(User.class, id);
      user.setEmail(newEmail);   // no em.save() needed!
      // On @Transactional commit: Hibernate detects change → issues UPDATE
  }

4. PERSISTENCE CONTEXT SCOPE TYPES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TRANSACTION-SCOPED (Default in Spring):
  - Persistence context created when transaction begins
  - Closed (and all entities detached) when transaction commits/rollbacks
  - Most common and recommended

  @PersistenceContext   // default: TRANSACTION scope
  private EntityManager em;

  @PersistenceContext(type = PersistenceContextType.TRANSACTION)
  private EntityManager em;

EXTENDED (Stateful beans only — avoid in Spring):
  - Persistence context lives beyond the transaction
  - Entity remains managed across multiple transactions
  - Only for @Stateful EJBs or specialized use cases
  - Can cause memory leaks and stale data in Spring apps

  @PersistenceContext(type = PersistenceContextType.EXTENDED)
  private EntityManager em;  // Avoid unless you know what you're doing

5. PERSIST vs MERGE vs SAVE (Spring Data)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Method          | Entity State | Behavior
────────────────|──────────────|──────────────────────────────────────
persist(entity) | Transient    | Makes entity managed; throws if already managed
merge(entity)   | Detached     | Copies state into managed entity; returns managed copy
merge(entity)   | Transient    | Works like persist (inserts)
repo.save(entity)| Any         | Spring Data: calls persist if new, merge if existing

Spring Data JPA's save() logic:
  if (entity.getId() == null) {
      em.persist(entity);
      return entity;
  } else {
      return em.merge(entity);
  }

  // For Persistable<T> entities (custom isNew() logic):
  public class User implements Persistable<Long> {
      @Transient private boolean isNew = true;
      @Override public boolean isNew() { return isNew; }
      @PostPersist @PostLoad void markNotNew() { isNew = false; }
  }

6. FLUSH MODES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FlushModeType.AUTO (Default):
  - Flushes before executing a JPQL/Criteria query that may be affected
    by pending changes
  - Flushes on transaction commit

FlushModeType.COMMIT:
  - Only flushes on transaction commit (NOT before queries)
  - Risky: queries may see stale state if context has pending changes
  - Useful for read-heavy scenarios to avoid unnecessary flushes

// Set globally:
em.setFlushMode(FlushModeType.COMMIT);

// Set per query:
em.createQuery("SELECT u FROM User u")
  .setFlushMode(FlushModeType.COMMIT)
  .getResultList();

Hibernate-specific flush modes:
  ALWAYS   → flush before every query
  MANUAL   → only when em.flush() is called explicitly

7. ENTITYMANAGERFACTORY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EntityManagerFactory (EMF):
  - Application-scoped (one per persistence unit, one per DataSource)
  - Thread-safe, expensive to create (scans entities, builds metamodel)
  - Created at startup, closed at shutdown
  - Spring Boot auto-creates it; inject with @PersistenceUnit

  @PersistenceUnit
  private EntityManagerFactory emf;

  // Manually creating EntityManager (rarely needed):
  EntityManager em = emf.createEntityManager();
  try {
      em.getTransaction().begin();
      em.persist(new User("alice@example.com"));
      em.getTransaction().commit();
  } catch (Exception e) {
      em.getTransaction().rollback();
  } finally {
      em.close();  // MUST close to release resources
  }

8. INTERVIEW QUICK HITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between persist() and merge()?
A: persist() makes a NEW (transient) entity managed. It throws if
   the entity is already managed. merge() is used for DETACHED entities;
   it copies the detached state into a managed entity and returns the
   managed copy. The original passed-in object remains detached.

Q: What is the difference between find() and getReference()?
A: find() immediately hits the DB (or 1st-level cache) and returns the
   full entity or null. getReference() returns a proxy object without
   hitting the DB; the DB is only queried when you first access a field.
   Use getReference() for FK assignments to avoid unnecessary SELECTs.

Q: Is EntityManager thread-safe?
A: No. But Spring injects a thread-local proxy. Each thread gets its own
   underlying EntityManager for the current transaction.

Q: What happens if you call em.persist() outside a transaction?
A: In Spring (with transaction-scoped EM), it throws a
   TransactionRequiredException. Always use @Transactional.

Q: What is dirty checking?
A: When an entity is loaded into the persistence context, Hibernate
   stores a snapshot of its state. On flush/commit, it compares current
   state to the snapshot and auto-generates UPDATE SQL for changed fields.
   You never need to call em.update() or em.save() for managed entities.

Q: What is the difference between flush() and commit()?
A: flush() synchronizes the persistence context to the DB within the
   current transaction (SQL is sent, but not committed; still rollback-able).
   commit() commits the transaction permanently to the DB (also triggers flush).
