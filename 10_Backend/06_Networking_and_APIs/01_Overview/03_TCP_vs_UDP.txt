================================================================================
TCP vs UDP — IN DEPTH
================================================================================

OVERVIEW
---------
TCP (Transmission Control Protocol) and UDP (User Datagram Protocol) are the
two primary transport-layer protocols in the Internet protocol suite.
They sit at Layer 4 of the OSI model and define how data is sent between hosts.

================================================================================
1. TCP — TRANSMISSION CONTROL PROTOCOL
================================================================================

CHARACTERISTICS:
  - Connection-oriented (requires handshake before data transfer)
  - Reliable: guarantees delivery, ordering, and error checking
  - Flow control: prevents sender overwhelming receiver (sliding window)
  - Congestion control: prevents sender overwhelming network (slow start, AIMD)
  - Byte-stream abstraction (not message boundaries)

TCP 3-WAY HANDSHAKE (Connection Establishment):
  ┌─────────┐                        ┌─────────┐
  │ Client  │                        │ Server  │
  └────┬────┘                        └────┬────┘
       │  SYN (seq=x)                     │
       │─────────────────────────────────>│
       │                                  │
       │  SYN-ACK (seq=y, ack=x+1)        │
       │<─────────────────────────────────│
       │                                  │
       │  ACK (ack=y+1)                   │
       │─────────────────────────────────>│
       │                                  │
       │  [Connection Established]        │
       │                                  │

  SYN     = Synchronize sequence numbers (client proposes its seq number x)
  SYN-ACK = Server acknowledges and sends its own seq number y
  ACK     = Client acknowledges server's seq number

TCP 4-WAY HANDSHAKE (Connection Termination — TIME_WAIT):
  ┌─────────┐                        ┌─────────┐
  │ Client  │                        │ Server  │
  └────┬────┘                        └────┬────┘
       │  FIN                             │
       │─────────────────────────────────>│
       │                                  │
       │  ACK                             │
       │<─────────────────────────────────│
       │                                  │
       │  FIN                             │
       │<─────────────────────────────────│
       │                                  │
       │  ACK                             │
       │─────────────────────────────────>│
       │ [TIME_WAIT 2MSL]                 │

  TIME_WAIT: Client waits 2×MSL (Maximum Segment Lifetime ~60s) before releasing
  the port. Ensures the final ACK is received; prevents old duplicates.

TCP FEATURES:
  a) SEQUENCE NUMBERS
     - Each byte of data has a sequence number
     - Receiver reorders out-of-order segments

  b) ACKNOWLEDGEMENTS (ACKs)
     - Receiver ACKs highest in-order byte received
     - Cumulative ACKs (or Selective ACKs — SACK)
     - Retransmission on timeout or triple duplicate ACK (Fast Retransmit)

  c) FLOW CONTROL — SLIDING WINDOW
     - Receiver advertises its receive window (rwnd)
     - Sender cannot have more unACKed bytes than rwnd
     - Prevents fast sender from overwhelming slow receiver

  d) CONGESTION CONTROL
     - Slow Start: Begin with small congestion window (cwnd), double each RTT
     - Congestion Avoidance: Linear increase after ssthresh
     - Fast Retransmit: On 3 duplicate ACKs, retransmit immediately
     - Fast Recovery: Halve ssthresh, enter congestion avoidance

  e) NAGLE'S ALGORITHM
     - Buffers small segments until ACK received or buffer full
     - Reduces chattiness; can increase latency for interactive apps
     - Disable with TCP_NODELAY socket option

  f) KEEP-ALIVE
     - Sends periodic probes to detect dead connections
     - Configured via SO_KEEPALIVE, tcp_keepalive_time

TCP HEADER FIELDS (key ones):
  Source Port    (16 bits)
  Dest Port      (16 bits)
  Sequence Num   (32 bits)
  Ack Num        (32 bits)
  Data Offset    (4 bits) — header length
  Flags          (9 bits) — SYN, ACK, FIN, RST, PSH, URG
  Window Size    (16 bits) — flow control
  Checksum       (16 bits)
  Urgent Pointer (16 bits)

================================================================================
2. UDP — USER DATAGRAM PROTOCOL
================================================================================

CHARACTERISTICS:
  - Connectionless (no handshake)
  - Unreliable: no guarantee of delivery, ordering, or deduplication
  - No flow control, no congestion control
  - Preserves message boundaries (each send = one datagram)
  - Very low overhead (8-byte header vs ~20-byte TCP header)

UDP HEADER:
  Source Port  (16 bits)
  Dest Port    (16 bits)
  Length       (16 bits)
  Checksum     (16 bits)

WHEN TO USE UDP:
  - Real-time audio/video (WebRTC, VoIP, video calls)
  - Online gaming (position updates; old data is useless)
  - DNS queries (short, single request-response)
  - DHCP (bootstrap protocol)
  - Multicast/broadcast
  - Metrics/telemetry (loss acceptable)
  - QUIC (HTTP/3) — implements reliability on top of UDP

================================================================================
3. TCP vs UDP COMPARISON
================================================================================

FEATURE              TCP                         UDP
-------------------  --------------------------  ---------------------------
Connection           Connection-oriented          Connectionless
Reliability          Guaranteed delivery          Best effort, may drop
Ordering             In-order delivery            No ordering guarantee
Error Checking       Yes + retransmission         Checksum only, no retransmit
Flow Control         Yes (sliding window)         No
Congestion Control   Yes (slow start, AIMD)       No
Overhead             Higher (~20B header + RTT)   Lower (8B header)
Latency              Higher (ACK round trips)     Lower
Throughput           Lower in lossy networks      Higher (no retransmit wait)
Message Boundaries   Stream (no boundaries)       Preserved (each send = 1 pkt)
Use Cases            HTTP, SSH, FTP, SMTP          DNS, video, VoIP, gaming, QUIC
Multiplexing         No (application-level)       Application-level or QUIC

4. TCP STATES (Important for Troubleshooting)
================================================================================

State           Description
--------------  -----------------------------------------------------------
CLOSED          No connection
LISTEN          Server waiting for incoming connections
SYN_SENT        Client sent SYN, waiting for SYN-ACK
SYN_RECEIVED    Server received SYN, sent SYN-ACK, waiting for ACK
ESTABLISHED     Connection established, data transfer in progress
FIN_WAIT_1      Sent FIN, waiting for ACK
FIN_WAIT_2      Received ACK of FIN, waiting for FIN from other side
CLOSE_WAIT      Received FIN, sent ACK, waiting for app to close
LAST_ACK        Sent FIN (in CLOSE_WAIT), waiting for final ACK
TIME_WAIT       Waiting 2×MSL before releasing port
CLOSING         Both sides sent FIN simultaneously

netstat -an | grep ESTABLISHED   → see established connections
netstat -an | grep TIME_WAIT     → TIME_WAIT connections (normal but can exhaust ports)
ss -s                            → socket statistics summary

5. COMMON TCP ISSUES AND TUNING
================================================================================

TIME_WAIT EXHAUSTION
  Problem: High-traffic servers run out of ephemeral ports (typically 16K-64K)
  Solution:
    - Enable tcp_tw_reuse (reuse TIME_WAIT sockets for new connections)
    - Increase ephemeral port range: net.ipv4.ip_local_port_range = 1024 65535
    - Use connection pooling to reduce new connection rate

HALF-OPEN CONNECTIONS (SYN Flood Attack)
  Problem: Attacker sends many SYN packets; fills server's half-open queue
  Solution: SYN cookies (cryptographic SYN-ACK without state)
    net.ipv4.tcp_syncookies = 1

BUFFER SIZES
  net.core.rmem_max / wmem_max = max socket receive/send buffer
  net.ipv4.tcp_rmem / tcp_wmem = min/default/max per-socket buffers
  Larger buffers → better throughput on high-latency connections (BDP)

NAGLE + DELAYED ACK INTERACTION
  Nagle delays sending small segments; delayed ACK delays ACK 40ms
  Combined effect: 40ms latency on small messages
  Solution: TCP_NODELAY + TCP_QUICKACK for latency-sensitive apps

6. QUIC (HTTP/3) — UDP WITH RELIABILITY
================================================================================

QUIC solves TCP limitations by building reliability at the application level
on top of UDP:

  - Independent streams: packet loss on stream A doesn't block stream B
  - 0-RTT / 1-RTT connection establishment (vs TCP 1-3 RTTs)
  - Connection ID-based: connections survive IP address changes (mobile handoff)
  - Built-in TLS 1.3 (no separate handshake)
  - Better on lossy networks (mobile, Wi-Fi)

QUIC vs TCP+TLS:
  TCP+TLS: 1 RTT TCP handshake + 1 RTT TLS handshake = 2 RTT before first byte
  QUIC:    1 RTT for combined QUIC+TLS (or 0 RTT for resumed sessions)

7. INTERVIEW QUESTIONS — TCP vs UDP
================================================================================

Q1: Why is TCP reliable but UDP is not?
    TCP uses sequence numbers to detect missing segments, acknowledgements to
    confirm receipt, and retransmission timers. If a segment is lost, TCP
    retransmits it. UDP sends datagrams with no tracking; lost packets are gone.

Q2: Why would you choose UDP over TCP?
    When low latency matters more than reliability: VoIP, gaming, live video.
    When losing an old packet is better than receiving it late. When the
    application implements its own reliability (QUIC, game engines). For DNS
    (single request-response; timeout and retry is fine).

Q3: What is the TCP 3-way handshake and why does it matter?
    SYN → SYN-ACK → ACK establishes initial sequence numbers for both sides.
    This costs 1 RTT before any data is sent. At scale, this overhead motivated
    QUIC's 0-RTT/1-RTT approach and connection pooling strategies.

Q4: What is head-of-line blocking?
    In TCP, segments must be delivered in order. If one segment is lost, all
    subsequent segments wait in a buffer (even if received) until the lost one
    is retransmitted and received. HTTP/2 multiplexes over one TCP connection,
    so a single lost packet blocks all HTTP/2 streams. QUIC on UDP has
    independent streams so only the affected stream is delayed.

Q5: What is TIME_WAIT and why does it exist?
    After closing a TCP connection, the initiating side waits for 2×MSL (~120s).
    This ensures (a) the final ACK arrives before the connection truly closes,
    (b) old delayed segments from the connection don't interfere with a new
    connection reusing the same port tuple.

Q6: How does TCP handle congestion?
    Slow Start: cwnd starts small, doubles each RTT until ssthresh.
    Congestion Avoidance: linear increase after ssthresh.
    On packet loss (timeout): ssthresh = cwnd/2, restart slow start.
    On triple duplicate ACK: Fast Retransmit + Fast Recovery (halve, continue).

Q7: What is a SYN flood attack and how is it mitigated?
    Attacker sends many SYNs, never completing handshake. Server fills its
    half-open connection queue and stops accepting legitimate connections.
    Mitigation: SYN cookies (server encodes state in SYN-ACK sequence number,
    no per-connection state until handshake completes).
