================================================================================
HTTP AND NETWORKING INTERVIEW QUESTIONS — COMPREHENSIVE Q&A
================================================================================

This file covers HTTP protocol, TCP/UDP, DNS, OSI model, TLS, HTTP/2, HTTP/3,
and general networking questions at senior/staff engineer interview level.

================================================================================
SECTION 1: HTTP PROTOCOL
================================================================================

Q: What happens when you type "https://www.example.com" in a browser?
A: Complete sequence:
   
   1. URL PARSING: Browser extracts scheme (https), host (www.example.com), path (/)
   
   2. DNS RESOLUTION:
      - Check browser DNS cache
      - Check OS DNS cache (/etc/hosts, OS cache)
      - Check router cache
      - Query recursive resolver (ISP's or 8.8.8.8)
      - Resolver queries root nameserver → TLD nameserver (.com) → authoritative
        nameserver for example.com → returns A/AAAA record with IP
      - Result cached per TTL
   
   3. TCP CONNECTION:
      - Three-way handshake: SYN → SYN-ACK → ACK
      - If HTTPS: TLS handshake follows (see TLS section)
   
   4. TLS HANDSHAKE (for HTTPS):
      - ClientHello (supported ciphers, TLS version, random)
      - ServerHello (chosen cipher, TLS version, random)
      - Server sends Certificate
      - Key exchange (ECDHE): client+server derive shared secret
      - Finished messages both ways — encrypted channel established
      (TLS 1.3 does this in 1 RTT)
   
   5. HTTP REQUEST:
      GET / HTTP/2
      Host: www.example.com
      Accept: text/html
   
   6. SERVER PROCESSING: DNS → load balancer → CDN/web server → backend
   
   7. HTTP RESPONSE: 200 OK with HTML body
   
   8. BROWSER RENDERING: Parse HTML, fetch CSS/JS/images (parallel with HTTP/2),
      DOM/CSSOM → layout → paint

Q: What is the difference between HTTP/1.1, HTTP/2, and HTTP/3?
A: HTTP/1.1 (1997):
   - Text-based protocol
   - One request per TCP connection at a time (pipelining rarely works)
   - Head-of-line (HOL) blocking: slow response blocks subsequent ones
   - Workarounds: domain sharding (multiple connections), inlining, bundling
   
   HTTP/2 (2015):
   - Binary framing (frames with stream IDs)
   - Multiplexing: multiple requests/responses in parallel on ONE TCP connection
   - Header compression (HPACK: static + dynamic table, Huffman encoding)
   - Server push (deprecated in 2022)
   - Still uses TCP: if one TCP packet is lost, all streams stall (TCP HOL blocking)
   
   HTTP/3 (2022, RFC 9114):
   - Uses QUIC transport (UDP-based) instead of TCP
   - Stream-level packet loss recovery: only the affected stream pauses
   - TLS 1.3 built into QUIC (0-RTT or 1-RTT connection)
   - Connection migration: can switch from WiFi to cellular without reconnection
   - ~15% faster page loads than HTTP/2 in typical conditions
   - Uses QPACK (HPACK adapted for QUIC's out-of-order delivery)

Q: What is HTTP Keep-Alive and connection reuse?
A: HTTP/1.0 closed TCP connection after each request (expensive).
   HTTP/1.1 introduced persistent connections (keep-alive) by default:
   Connection: keep-alive (client) / Connection: keep-alive (server)
   
   After a response, the TCP connection stays open for subsequent requests.
   Connection: close signals last response on this connection.
   
   Server controls max idle time and max requests per connection:
   Keep-Alive: timeout=5, max=1000
   
   HTTP/2 takes this further: one connection per host, all requests multiplexed.
   Connection management is handled at the stream level, not connection level.
   
   Application impact: Use connection pooling (HikariCP for DB, Reactor Netty
   connection pool for HTTP) to reuse connections efficiently.

Q: What is the difference between cookies and sessions?
A: Session: server-side storage of user state, keyed by session ID.
   Session ID stored in a cookie (JSESSIONID in Java EE/Spring).
   
   Cookies: small key-value pairs stored in the browser, sent with every
   request to the matching domain.
   
   Types:
   - Session cookies: expire when browser closes (no Max-Age/Expires)
   - Persistent cookies: have Max-Age or Expires date
   - Secure: only sent over HTTPS
   - HttpOnly: not accessible by JavaScript (prevents XSS theft)
   - SameSite: Strict/Lax/None — controls cross-site sending (prevents CSRF)
   
   JWT vs Cookies:
   - JWT in Authorization header: stateless, works cross-domain, but can't
     be invalidated before expiry
   - Session cookie: server stores state (can invalidate), but requires sticky
     sessions or shared session store (Redis) for scaling

Q: What are HTTP cache headers and how do they work?
A: Cache-Control (most important):
   max-age=3600       — browser/CDN can cache for 3600 seconds
   no-cache           — always revalidate with server (but can serve cached on 304)
   no-store           — never cache (sensitive data)
   public             — CDN can cache
   private            — only browser can cache (user-specific data)
   must-revalidate    — after max-age, revalidate before using stale
   s-maxage=86400     — shared cache (CDN) TTL; overrides max-age for CDNs
   stale-while-revalidate=60 — serve stale, revalidate in background
   
   Conditional requests:
   ETag: "abc123"                — response with entity tag (content hash)
   If-None-Match: "abc123"      — request: "only respond if ETag changed"
   Last-Modified: Tue, 15 Jan   — response with modification date
   If-Modified-Since: [date]    — request: "only respond if modified"
   
   Server returns:
   304 Not Modified — content unchanged; browser uses cached copy (no body)
   200 OK           — content changed; new body returned

SECTION 2: TCP AND UDP
================================================================================

Q: What is the TCP three-way handshake?
A: TCP establishes a reliable, ordered, connection-oriented channel:
   
   1. SYN: Client → Server
      "I want to connect; my sequence number starts at X"
      TCP header: SYN flag, Seq=X
   
   2. SYN-ACK: Server → Client
      "OK, I accept; my sequence number starts at Y, I acknowledge X"
      TCP header: SYN+ACK flags, Seq=Y, Ack=X+1
   
   3. ACK: Client → Server
      "Acknowledged; connection established"
      TCP header: ACK flag, Seq=X+1, Ack=Y+1
   
   After this: data can flow. Connection state: ESTABLISHED on both sides.
   
   Connection teardown is four-way: FIN → ACK, FIN → ACK
   (or three-way if piggybacked: FIN → FIN+ACK → ACK)
   
   TIME_WAIT state: after closing, client waits 2×MSL (2 minutes default)
   before releasing port — ensures all packets in flight are consumed.

Q: What is the difference between TCP and UDP?
A: TCP (Transmission Control Protocol):
   - Connection-oriented (handshake required)
   - Reliable: acknowledgments, retransmission of lost packets
   - Ordered: packets delivered in sequence
   - Flow control: receiver advertises window size
   - Congestion control: slows down when network is congested
   - Higher overhead (~20-byte header + 3 RTT to establish)
   - Use when: data integrity matters (HTTP, databases, file transfer)
   
   UDP (User Datagram Protocol):
   - Connectionless (fire and forget)
   - Unreliable: no acks, no retransmission
   - Unordered: packets may arrive out of order
   - No flow or congestion control
   - Low overhead (~8-byte header, no connection setup)
   - Use when: speed/latency matters more than reliability
     (DNS queries, video streaming, gaming, VoIP, QUIC/HTTP/3)
   
   QUIC (HTTP/3) uses UDP but implements reliability and ordering per-stream
   at the QUIC layer, getting best of both worlds.

Q: What is TCP head-of-line blocking and how does HTTP/3 solve it?
A: TCP delivers bytes in order. If one packet is lost, all subsequent packets
   must wait in the receive buffer until the lost packet is retransmitted —
   even if they belong to completely different HTTP/2 streams.
   
   Example: Three HTTP/2 streams (images A, B, C) multiplexed on one TCP.
   If a packet for stream A is lost, streams B and C also stall even though
   their data arrived successfully. This is TCP HOL blocking.
   
   HTTP/3 solution: QUIC creates independent, reliable streams over UDP.
   Packet loss only blocks the specific QUIC stream it belongs to. Streams
   B and C continue flowing while stream A's packet is retransmitted.
   
   This is especially beneficial for mobile networks with higher packet loss
   rates, and for fetching many independent resources (images on a webpage).

SECTION 3: DNS
================================================================================

Q: How does DNS resolution work?
A: DNS is a hierarchical, distributed system translating names to IPs.
   
   Query for "api.example.com":
   1. Browser cache (stored for DNS query's TTL)
   2. OS cache + /etc/hosts
   3. Local recursive resolver (ISP or configured: 8.8.8.8, 1.1.1.1)
   4. If resolver cache miss:
      a. Query root server (13 root server clusters): "who handles .com?"
      b. Root → TLD server (.com): "who handles example.com?"
      c. TLD → authoritative nameserver for example.com
      d. Authoritative → returns A record: "api.example.com = 1.2.3.4, TTL=300"
   5. Resolver caches result for TTL; returns to client
   
   DNS record types:
   A     — maps hostname to IPv4
   AAAA  — maps hostname to IPv6
   CNAME — alias to another hostname (can't use at apex/root domain)
   MX    — mail server for domain
   TXT   — arbitrary text (SPF, DKIM, domain verification)
   NS    — authoritative nameservers for zone
   SOA   — start of authority (zone metadata)
   SRV   — service locator (port, protocol, priority)
   PTR   — reverse DNS (IP → hostname)

Q: What is the difference between DNS A record and CNAME?
A: A record directly maps a hostname to an IPv4 address.
   api.example.com → 1.2.3.4
   Only one lookup.
   
   CNAME creates an alias pointing to another hostname.
   api.example.com → loadbalancer.elb.amazonaws.com → 1.2.3.4
   Requires additional lookup to resolve the alias.
   
   Restrictions:
   - CNAME cannot coexist with other records at same name
   - CNAME not allowed at zone apex (example.com itself) — use ALIAS/ANAME
     record (proprietary, supported by Route 53, Cloudflare) or flatten CNAME
   - A record at apex: example.com → IP directly
   
   Use CNAME for: CDN/cloud hostnames that change IPs frequently
   Use A record for: stable IPs (own servers)

SECTION 4: TLS AND SECURITY
================================================================================

Q: How does TLS prevent man-in-the-middle attacks?
A: TLS uses certificates issued by trusted Certificate Authorities (CAs).
   
   During handshake:
   1. Server sends certificate (public key + domain name + CA signature)
   2. Client verifies certificate:
      a. Is the CA signature valid? (trust chain to root CA in browser/OS store)
      b. Does the hostname match? (CN or SAN field)
      c. Is the certificate not expired? (validity dates)
      d. Is it revoked? (OCSP/CRL check)
   3. If all pass: client uses server's public key for key exchange
   
   MITM attack attempt:
   - Attacker intercepts and presents their own certificate
   - Attacker's certificate for "example.com" won't be signed by a trusted CA
   - Browser shows certificate error; connection rejected
   
   Edge case MITM (corporate proxy):
   - Corporate IT installs their CA root in employee machines
   - Their proxy can then issue certs for any domain
   - Employee traffic is decrypted and re-encrypted — legitimate MITM
   - This is why "certificate pinning" exists (app pins expected cert/public key)

Q: What is Perfect Forward Secrecy (PFS)?
A: PFS means compromising the server's long-term private key cannot decrypt
   past recorded sessions.
   
   Without PFS (RSA key exchange):
   - Client encrypts session key with server's RSA public key
   - If attacker records encrypted traffic now and later steals private key,
     they can decrypt all historical sessions
   
   With PFS (ECDHE key exchange):
   - Client and server each generate ephemeral (temporary) key pairs per session
   - Derive shared session key via Elliptic Curve Diffie-Hellman
   - Ephemeral keys are discarded after the session
   - Even with the long-term private key, past sessions cannot be decrypted
   
   TLS 1.3 requires PFS (only ECDHE key exchange; no RSA key exchange).
   TLS 1.2 supports both; configure to require ECDHE cipher suites.
   Spring/Nginx: configure ssl_ciphers to only include ECDHE suites.

SECTION 5: LOAD BALANCING AND HIGH AVAILABILITY
================================================================================

Q: What is the difference between L4 and L7 load balancing?
A: L4 (Transport Layer) Load Balancer:
   - Routes based on IP and TCP/UDP port
   - Doesn't inspect HTTP content
   - Very fast, low overhead (hardware or kernel-level)
   - No SSL termination
   - No content-based routing
   - Examples: AWS NLB, HAProxy TCP mode, Linux LVS
   
   L7 (Application Layer) Load Balancer:
   - Reads HTTP headers, URLs, cookies
   - Can route based on path (/api/ vs /static/), header, cookie
   - SSL termination
   - Content-based decisions: sticky sessions (by session cookie)
   - Can modify requests/responses
   - Slower (full HTTP parsing) but much more flexible
   - Examples: Nginx, AWS ALB, HAProxy HTTP mode, Envoy
   
   Use L4 when: ultra-low latency, non-HTTP protocols (TCP apps), no need for
   content routing.
   Use L7 when: HTTPS termination, routing multiple services on one IP,
   canary deployments, WAF integration.

Q: What are the common load balancing algorithms?
A: Round Robin: requests distributed equally, in order.
   Weighted Round Robin: servers with more capacity get more requests.
   Least Connections: route to server with fewest active connections.
   Least Response Time: route to server with lowest latency + fewest connections.
   IP Hash: consistent hash of client IP → same client always hits same server
            (useful for sticky sessions without cookies).
   Random: random selection; works well with health checks.
   
   Best practice: least connections for HTTP APIs (handles slow endpoints better
   than round robin); round robin for stateless homogeneous services.

SECTION 6: NETWORKING PRACTICAL QUESTIONS
================================================================================

Q: What is a CDN and how does it work?
A: A Content Delivery Network is a globally distributed network of edge servers
   that cache and serve content from locations close to end users.
   
   How it works:
   1. User requests cdn.example.com
   2. DNS returns IP of nearest edge node (anycast or GeoDNS)
   3. Edge node checks cache: HIT → serve immediately; MISS → fetch from origin
   4. Response served from edge, cached for future requests
   
   Benefits: reduced latency (data is geographically close), reduced origin load,
   DDoS absorption (distributed attack surface), global availability.
   
   Cache invalidation strategies:
   - TTL-based (max-age): content expires and is re-fetched
   - Manual purge via CDN API (Cloudflare, CloudFront)
   - Cache busting: change URL when content changes (/app.v2.js)
   
   Dynamic content: CDN can still accelerate dynamic requests via optimized
   routes to origin (Cloudflare Argo, CloudFront origin shield).

Q: What is NAT (Network Address Translation)?
A: NAT allows multiple devices on a private network to share one public IP.
   A router/NAT device rewrites source IP and port in outgoing packets,
   maintains a translation table, and reverses the translation for responses.
   
   Private → Public:
   192.168.1.5:12345 → 203.0.113.1:50001 (outgoing)
   203.0.113.1:50001 → 192.168.1.5:12345 (incoming response)
   
   Problems for servers: servers behind NAT aren't directly reachable from
   internet (no inbound connection possible unless port forwarding is configured).
   Solution: port forwarding (router forwards port 80 to internal IP:80).
   
   Impact on IPv6: IPv6 has enough addresses that NAT isn't needed; every
   device can have a unique public IP.
