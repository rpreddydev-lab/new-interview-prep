======================================================
API VERSIONING STRATEGIES IN SPRING BOOT
======================================================

1. WHY API VERSIONING?
───────────────────────
APIs must evolve without breaking existing clients.
Versioning allows:
  - Introduce breaking changes safely
  - Support multiple client versions simultaneously
  - Deprecate old versions gracefully

Breaking changes include:
  - Removing or renaming fields in response
  - Changing field types
  - Changing request structure
  - Changing business rules/behavior


2. VERSIONING STRATEGIES
─────────────────────────

A) URI PATH VERSIONING (most common)
  URL: /api/v1/users, /api/v2/users

  @RestController
  @RequestMapping("/api/v1/users")
  public class UserControllerV1 { ... }

  @RestController
  @RequestMapping("/api/v2/users")
  public class UserControllerV2 { ... }

  Pros:
    - Easy to understand, discoverable, bookmarkable
    - Works with API gateways, caching, logs
  Cons:
    - URI should identify a resource, not a version (REST purist argument)
    - Leads to controller duplication

  Best for: public APIs, external clients, REST APIs

B) QUERY PARAMETER VERSIONING
  URL: /api/users?version=1, /api/users?version=2

  @GetMapping("/api/users")
  public ResponseEntity<?> getUsers(@RequestParam(defaultValue = "1") int version) {
      return version == 2 ? ResponseEntity.ok(serviceV2.getUsers())
                          : ResponseEntity.ok(serviceV1.getUsers());
  }

  Pros: No URL change, simple to implement
  Cons: Less visible in logs, not cacheable (query params bust cache), messy at scale

  Best for: internal APIs, minor versions

C) HEADER VERSIONING (Accept header / Custom header)

  Custom header:
    Request: GET /api/users, Header: X-API-Version: 2

    @GetMapping(value = "/api/users", headers = "X-API-Version=1")
    public ResponseEntity<UserV1Dto> getUsersV1() { ... }

    @GetMapping(value = "/api/users", headers = "X-API-Version=2")
    public ResponseEntity<UserV2Dto> getUsersV2() { ... }

  Accept header (Media Type / Content Negotiation):
    Request: Accept: application/vnd.myapp.v2+json

    @GetMapping(value = "/api/users",
                produces = "application/vnd.myapp.v1+json")
    public ResponseEntity<UserV1Dto> getUsersV1() { ... }

    @GetMapping(value = "/api/users",
                produces = "application/vnd.myapp.v2+json")
    public ResponseEntity<UserV2Dto> getUsersV2() { ... }

  Pros:
    - Clean URIs
    - Semantically correct (Accept header for content negotiation)
  Cons:
    - Not visible in URL, hard to test in browser
    - Custom headers not standard; vendor MIME types are complex
    - Harder to cache (Vary: Accept header needed)

  Best for: internal microservice-to-microservice APIs


3. SPRING BOOT IMPLEMENTATION PATTERNS
──────────────────────────────────────

Pattern 1: Separate Controllers (cleanest for major versions)
  @RestController
  @RequestMapping("/api/v1")
  public class OrderControllerV1 {
      @GetMapping("/orders/{id}")
      public OrderDtoV1 getOrder(@PathVariable Long id) { ... }
  }

  @RestController
  @RequestMapping("/api/v2")
  public class OrderControllerV2 {
      @GetMapping("/orders/{id}")
      public OrderDtoV2 getOrder(@PathVariable Long id) { ... }  // new fields
  }

Pattern 2: Shared Controller + Service Strategy
  @GetMapping("/api/{version}/orders/{id}")
  public ResponseEntity<?> getOrder(@PathVariable String version,
                                    @PathVariable Long id) {
      return switch (version) {
          case "v1" -> ResponseEntity.ok(orderService.getOrderV1(id));
          case "v2" -> ResponseEntity.ok(orderService.getOrderV2(id));
          default   -> ResponseEntity.badRequest().build();
      };
  }

Pattern 3: RequestMappingHandlerMapping (programmatic versioning)
  Implement custom RequestMappingHandlerMapping that extracts version
  from header and maps to annotated controllers.

Pattern 4: API Gateway routing (infrastructure-level)
  AWS API Gateway, Kong, Spring Cloud Gateway routes by path/header
  to different service versions or deployments:
    /api/v1/* → service-v1
    /api/v2/* → service-v2
  No code changes needed in services.


4. DTO EVOLUTION STRATEGIES
────────────────────────────
Instead of creating entirely new controllers, evolve DTOs:

  // Add optional fields (non-breaking):
  public class UserDto {
      private String name;
      private String email;
      private String phoneNumber;  // new in v2, null for v1 responses
  }

  // Use @JsonView for different versions:
  public class UserDto {
      @JsonView(Views.V1.class)
      private String name;

      @JsonView({Views.V1.class, Views.V2.class})
      private String email;

      @JsonView(Views.V2.class)
      private String phoneNumber;   // only in V2
  }

  @GetMapping(value = "/api/v1/users/{id}")
  @JsonView(Views.V1.class)
  public UserDto getUserV1(@PathVariable Long id) { ... }

  @GetMapping(value = "/api/v2/users/{id}")
  @JsonView(Views.V2.class)
  public UserDto getUserV2(@PathVariable Long id) { ... }


5. DEPRECATION STRATEGY
─────────────────────────
Mark old versions with deprecation:
  - Add Deprecation + Sunset headers:
    Deprecation: Sat, 01 Jan 2026 00:00:00 GMT
    Sunset: Sat, 01 Jul 2026 00:00:00 GMT
    Link: <https://api.myapp.com/v2/users>; rel="successor-version"

  Filter to add deprecation headers:
    @Component
    public class DeprecationHeaderFilter extends OncePerRequestFilter {
        @Override
        protected void doFilterInternal(...) {
            chain.doFilter(request, response);
            if (request.getRequestURI().startsWith("/api/v1/")) {
                response.addHeader("Deprecation", "true");
                response.addHeader("Sunset", "Sat, 01 Jul 2026 00:00:00 GMT");
            }
        }
    }

  Log usage of deprecated endpoints for migration tracking.


6. COMPARISON TABLE
────────────────────
Strategy        | Clarity | Cacheability | RESTful | Tooling Support | Recommended For
────────────────────────────────────────────────────────────────────────────────────────
URI Path        | High    | High         | Medium  | Excellent       | Public APIs
Query Param     | Medium  | Low          | Low     | Good            | Internal/minor
Custom Header   | Low     | Medium       | Medium  | Good            | Internal/microservices
Accept Header   | Low     | Medium       | High    | Moderate        | REST purist APIs


7. OPENAPI / SPRINGDOC VERSIONING
──────────────────────────────────
Expose separate OpenAPI docs per version:
  springdoc:
    group-configs:
      - group: v1
        paths-to-match: /api/v1/**
      - group: v2
        paths-to-match: /api/v2/**

  Swagger UI shows dropdown: "v1", "v2"


8. INTERVIEW QUESTIONS
──────────────────────
Q: What are the main API versioning strategies and their trade-offs?
A: URI path (most common, highly visible, good caching), query parameter
   (simple but pollutes URI, poor caching), custom header (clean URIs but
   not visible in logs/browser), Accept header (most RESTful via content
   negotiation but complex). URI path is the industry standard for public APIs.

Q: What is a non-breaking vs breaking API change?
A: Non-breaking: adding optional fields, adding new endpoints, new optional
   query params, loosening validation. Breaking: removing fields, renaming
   fields, changing field types, changing required fields to required+different
   format, changing HTTP status codes.

Q: How do you communicate API deprecation to clients?
A: Use Deprecation and Sunset HTTP headers per RFC 8594.
   Deprecation: date when it was deprecated.
   Sunset: date after which it will be removed.
   Include a Link header pointing to the successor version.
   Log and monitor usage of deprecated endpoints.

Q: How would you version a REST API in a microservices architecture?
A: At the API Gateway level (Spring Cloud Gateway or AWS API Gateway):
   route by path or header to different service versions or canary deployments.
   This decouples versioning from service code. Internally, services
   themselves can be versioned by deploying new instances.
