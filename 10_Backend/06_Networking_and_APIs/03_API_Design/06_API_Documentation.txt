API DOCUMENTATION — IN DEPTH
================================================================================

WHAT IS API DOCUMENTATION?
----------------------------
API documentation is the complete reference material that developers need to
understand, integrate with, and use your API effectively. Good documentation
is the #1 factor in API adoption and developer experience (DX).

Types of API documentation:
  1. Reference docs  : Endpoint-level spec (OpenAPI)
  2. Guides & tutorials: Getting started, authentication walkthrough
  3. Concepts        : Domain model explanations, terminology
  4. Changelogs      : Version history, migration guides, deprecation notices
  5. Code samples    : Real-world examples in multiple languages

================================================================================
1. PRINCIPLES OF EXCELLENT API DOCUMENTATION
================================================================================

1. ACCURACY
   - Docs must match actual behavior — stale docs are worse than no docs
   - Use code-first or design-first to keep spec and code in sync
   - Automated tests should validate spec examples (contract testing)

2. COMPLETENESS
   - Every endpoint, parameter, status code, and error documented
   - All authentication flows explained
   - Rate limits, quotas, and throttling behavior documented
   - Webhook payload shapes documented

3. CLARITY
   - Plain language; avoid internal jargon
   - Describe what an endpoint DOES, not just its technical shape
   - Explain WHY fields exist and what they mean in the domain
   - Document edge cases and gotchas

4. EXAMPLES
   - Real, working request/response examples for every endpoint
   - Multiple examples showing success and failure cases
   - Code snippets in popular languages (curl, Java, Python, JS)

5. NAVIGABILITY
   - Logical grouping by domain (users, orders, payments)
   - Search functionality
   - Consistent structure across all endpoints
   - Interactive try-it-out capability (Swagger UI)

================================================================================
2. DOCUMENTATION ELEMENTS
================================================================================

ENDPOINT DOCUMENTATION (each endpoint needs):
  ✓ HTTP method + path
  ✓ One-line summary
  ✓ Detailed description (what, when, gotchas)
  ✓ Authentication requirement
  ✓ All path/query/header parameters (name, type, required, description, example)
  ✓ Request body schema (all fields, types, constraints, examples)
  ✓ All possible response codes with descriptions
  ✓ Response body schemas
  ✓ Working curl example
  ✓ Code samples in at least 2-3 languages

FIELD DOCUMENTATION:
  Each field in a request/response object needs:
    - Data type
    - Required vs optional
    - Constraints (min/max, pattern, enum values)
    - Business meaning (not just technical name)
    - Example value
    - Nullability (can it ever be null?)
    - Deprecation status

AUTHENTICATION DOCUMENTATION:
  - Which auth mechanism is used (OAuth2, API key, JWT)
  - Step-by-step flow diagrams for OAuth2
  - How to obtain credentials / tokens
  - Token expiry and refresh process
  - Scopes/permissions mapping

RATE LIMITING DOCUMENTATION:
  - Rate limit tiers (free vs paid plans)
  - Which endpoints have limits
  - Response headers that communicate current usage:
      X-RateLimit-Limit: 1000
      X-RateLimit-Remaining: 456
      X-RateLimit-Reset: 1714500000
  - 429 response body and when to retry

ERROR DOCUMENTATION:
  - Error code taxonomy (VALIDATION_FAILED, RESOURCE_NOT_FOUND etc.)
  - Explanation of each error code
  - Remediation steps for common errors
  - Retry guidance (which errors are retriable)

3. API CHANGELOG AND DEPRECATION
================================================================================

CHANGELOG FORMAT (keep-a-changelog.com style):
  ## [2.0.0] - 2026-01-15
  ### Breaking Changes
  - `POST /users` response no longer includes `password` field
  - `role` field changed from string to enum (USER|ADMIN|MODERATOR)
  
  ### Added
  - `GET /users/{id}/permissions` endpoint
  - `X-Request-Id` header in all responses
  
  ### Changed
  - `GET /users` now returns `data` envelope instead of flat array
  - Default page size changed from 10 to 20
  
  ### Deprecated
  - `GET /users/{id}/profile` deprecated; use `GET /users/{id}` instead
  
  ### Removed
  - `DELETE /users/bulk` (deprecated since 1.5.0)

DEPRECATION HEADERS (RFC 8594):
  HTTP/1.1 200 OK
  Deprecation: Sun, 01 Jan 2027 00:00:00 GMT
  Sunset: Sun, 01 Jun 2027 00:00:00 GMT
  Link: <https://api.example.com/v2/users>; rel="successor-version"

  Deprecation  : When this endpoint was deprecated
  Sunset       : When it will be removed (unavailable)
  Link rel=successor-version: Where to migrate to

BREAKING CHANGE POLICY:
  - Never make breaking changes without a version bump
  - Announce deprecation at least 6 months before sunset
  - Maintain deprecated endpoints for deprecation window
  - Send email/webhook notifications to active API consumers

4. DOCUMENTATION TOOLS AND PLATFORMS
================================================================================

OPEN SOURCE / SELF-HOSTED:
  Swagger UI    : Interactive HTML page from OpenAPI spec; easy setup
  Redoc         : Beautiful three-panel layout; read-only; highly customizable
  Docusaurus    : Static site generator; great for guides + reference
  MkDocs        : Markdown-based; Material theme popular for API docs

COMMERCIAL:
  Stoplight     : Full API design + documentation platform
  ReadMe.io     : Developer hub with analytics, API explorer
  Postman       : API documentation + testing; auto-generated from collections
  Apiary        : API Blueprint format; acquired by Oracle

SPRING BOOT TOOLING:
  SpringDoc OpenAPI (springdoc-openapi-starter-webmvc-ui):
    - Generates OpenAPI 3.0 spec from Spring annotations
    - Embeds Swagger UI at /swagger-ui.html
    - YAML/JSON at /v3/api-docs

5. WRITING GOOD API DESCRIPTIONS (EXAMPLE)
================================================================================

BAD EXAMPLE:
  summary: "Updates user"
  description: "PUT /users/{id} updates the user."

GOOD EXAMPLE:
  summary: "Replace a user's profile"
  description: |
    Replaces all mutable fields of a user identified by `userId`.
    
    This is a full replacement (PUT semantics) — all required fields must be
    supplied. Fields omitted from the request will be reset to defaults or
    cleared. Use PATCH /users/{id} for partial updates.
    
    **Authorization:** Requires `USER_WRITE` scope or admin role.
    
    **Idempotency:** Calling this endpoint multiple times with the same body
    produces the same result (idempotent).
    
    **Audit:** All changes are logged to the audit trail.

BAD FIELD DESCRIPTION:
  email:
    description: "The email."

GOOD FIELD DESCRIPTION:
  email:
    description: |
      The user's primary email address. Must be unique within the system.
      Used for login, password reset, and notification delivery.
      Cannot be changed via this endpoint — use POST /users/{id}/email-change
      to initiate a verified email change flow.
    format: email
    example: "alice@example.com"

6. CONTRACT TESTING — KEEPING DOCS IN SYNC
================================================================================

PROBLEM: Docs and code drift over time.

SOLUTIONS:

1. CONSUMER-DRIVEN CONTRACT TESTING (Pact):
   - Consumer writes contracts (expected interactions)
   - Provider verified against those contracts in CI
   - Guarantees compatibility between spec and implementation

2. SPEC CONFORMANCE TESTING:
   - Dredd: HTTP API testing against OpenAPI spec
   - Prism: Mock server from spec; also validates real responses against spec
   
   dredd openapi.yaml http://localhost:8080

3. SPRING RESTDOCS:
   - Generate documentation snippets from test code
   - Docs fail to build if code doesn't match — docs always accurate
   
   @Test
   void shouldGetUser() throws Exception {
       mockMvc.perform(get("/users/1"))
           .andExpect(status().isOk())
           .andDo(document("get-user",
               pathParameters(
                   parameterWithName("id").description("User ID")
               ),
               responseFields(
                   fieldWithPath("id").description("User identifier"),
                   fieldWithPath("email").description("User email"),
                   fieldWithPath("role").description("User role")
               )
           ));
   }
   // Fails to compile if fields in response don't match documented fields

4. GENERATE SPEC FROM TESTS:
   Use Spring RestDocs + restdocs-api-spec to generate OpenAPI spec from tests.
   Spec becomes a byproduct of passing tests.

7. DEVELOPER EXPERIENCE (DX) BEST PRACTICES
================================================================================

QUICK START GUIDE:
  1. Show the simplest possible working example in <5 minutes
  2. Copy-pasteable curl commands
  3. Sandbox/test environment with pre-populated data
  4. Example API keys or OAuth2 client for testing

ERROR MESSAGES AS DOCUMENTATION:
  - Error responses should point to documentation:
    {
      "error": "INVALID_EMAIL_FORMAT",
      "message": "Email address must be in standard format",
      "documentationUrl": "https://docs.api.example.com/errors/INVALID_EMAIL_FORMAT"
    }

SDKs AND CLIENT LIBRARIES:
  - Auto-generate from OpenAPI spec using openapi-generator
  - Reduces integration friction for common languages
  - Maintain and version SDK alongside API

CHANGELOGS IN DEVELOPER PORTAL:
  - Email digest on breaking changes
  - RSS/Atom feed for changelog
  - Differentiate breaking vs non-breaking changes

SANDBOX ENVIRONMENT:
  - Dedicated environment that resets daily
  - Pre-seeded test data
  - No real money/data consequences

9. INTERVIEW QUESTIONS — API DOCUMENTATION
================================================================================

Q1: Why does API documentation matter beyond just listing endpoints?
    Documentation is the primary interface between API producers and consumers.
    Poor documentation increases support burden, slows developer onboarding, and
    leads to incorrect API usage. Good documentation includes intent, constraints,
    error handling, rate limits, migration guides, and examples — not just schemas.
    It also enables tooling like code generation, contract testing, and mocking.

Q2: How do you ensure documentation stays in sync with the code?
    Three main approaches:
    1. Code-first: annotations generate spec, so code changes update spec automatically
    2. Contract testing (Dredd, Pact, Prism) that fail the build when code drifts from spec
    3. Spring RestDocs: snippets generated from tests; docs won't build if tests fail
    Best practice: treat spec as code; commit it to VCS; validate it in CI.

Q3: What should API error responses include from a documentation perspective?
    Error code (machine-readable), human-readable message, request ID for debugging,
    timestamp, field-level details for validation errors, a link to documentation for
    that error code, and optionally a traceId. They should NOT include stack traces,
    internal class names, or SQL errors in production.

Q4: What is the Sunset header and why is it important?
    The Sunset header (RFC 8594) communicates the exact date-time when a deprecated
    resource will be removed. It gives API consumers programmatic notice of upcoming
    breaking changes. Monitoring tools can alert teams when consuming a sunsetted
    endpoint. Deprecation header shows when it was deprecated; Sunset shows removal.

Q5: What is the difference between Swagger UI and Redoc?
    Both render OpenAPI specs as HTML documentation.
    Swagger UI: interactive, has "Try it out" feature for executing requests,
    three-column layout, maintained by SmartBear.
    Redoc: read-only but beautifully formatted, three-panel responsive layout,
    better for public-facing documentation, more customizable branding,
    open source. Neither is better — Redoc for public docs, Swagger UI for
    developer internal testing.
