================================================================================
HTTP STATUS CODES — IN DEPTH
================================================================================

OVERVIEW
---------
HTTP status codes are 3-digit numbers indicating the result of an HTTP request.
They are grouped into 5 classes by the first digit.

CLASSES:
  1xx — Informational   (request received, continuing process)
  2xx — Success         (request successfully received, understood, accepted)
  3xx — Redirection     (further action needed to complete request)
  4xx — Client Error    (request contains bad syntax or cannot be fulfilled)
  5xx — Server Error    (server failed to fulfill valid request)

================================================================================
1. 2xx SUCCESS CODES
================================================================================

200 OK
  The most common success code.
  GET: resource returned in body
  PUT/PATCH: resource updated, updated resource in body
  POST: action completed (or use 201 for created resources)
  DELETE: resource deleted (or use 204 if no body)

201 Created
  Resource was successfully created.
  Always include Location header pointing to new resource.
  Used for: POST /users (creates user), PUT /users/42 (creates new)
  
  Example:
  POST /users → 201 Created
  Location: /users/99
  { "id": 99, "name": "Alice" }

202 Accepted
  Request accepted for processing but processing not yet complete.
  Used for: asynchronous operations, queued tasks, batch processing.
  Should return a way to check status (polling URL or callback).
  
  Example:
  POST /reports/generate → 202 Accepted
  { "jobId": "job-123", "statusUrl": "/jobs/job-123", "estimatedTime": "30s" }

204 No Content
  Request succeeded but there's no content to return.
  Used for: DELETE, PATCH/PUT when no body returned
  Body MUST be empty (by spec).
  
  DELETE /users/42 → 204 No Content

206 Partial Content
  Response to a Range request (byte serving).
  Content-Range header indicates which part was returned.
  
  GET /video.mp4 Range: bytes=0-1023 → 206 Partial Content
  Content-Range: bytes 0-1023/10240000

================================================================================
2. 3xx REDIRECTION CODES
================================================================================

301 Moved Permanently
  Resource permanently moved to new URI.
  Browser caches this redirect (updates bookmarks).
  Method may change to GET on redirect (browser behavior).
  SEO: Google transfers link juice to new URL.
  Use: Permanent URL restructuring.

302 Found (Previously "Moved Temporarily")
  Temporary redirect. Do NOT cache.
  Method may change to GET on redirect.
  
  Common for: post-login redirect, temporary URL changes.

303 See Other
  After a POST/PUT/DELETE, redirect client to GET a different resource.
  Method ALWAYS changes to GET.
  Use: POST /checkout → 303 → GET /orders/123
  Prevents form re-submission on browser back/refresh (PRG pattern).

304 Not Modified
  Conditional GET: resource hasn't changed since If-None-Match / If-Modified-Since.
  Client should use its cached copy.
  Body must be empty.
  Doesn't count as "success" but is not an error.

307 Temporary Redirect
  Temporary redirect. Do NOT cache.
  Method MUST NOT change.
  
  If POST /api/v1/users → 307 → POST /api/v2/users  (method preserved)

308 Permanent Redirect
  Permanent redirect. Cache this.
  Method MUST NOT change.
  
  Use over 301 when you want to preserve POST method.

PRG PATTERN (Post-Redirect-Get):
  1. User submits form → POST /orders
  2. Server processes → 303 See Other → Location: /orders/123
  3. Browser follows redirect → GET /orders/123
  4. User sees order confirmation page
  
  Benefit: Refreshing page doesn't resubmit form (no duplicate orders)

3. 4xx CLIENT ERROR CODES
================================================================================

400 Bad Request
  Client sent a malformed or invalid request.
  Use for: Missing required fields, wrong data types, syntax errors, 
           general validation failures.
  
  POST /users { "email": "not-an-email" }
  → 400 Bad Request
  { "error": "VALIDATION_ERROR", "message": "Invalid email format", 
    "field": "email" }

401 Unauthorized (Really: Unauthenticated)
  Authentication is required but missing or invalid.
  The name is a misnomer — it really means "unauthenticated."
  Must include WWW-Authenticate header with auth scheme.
  
  GET /api/protected
  (no Authorization header)
  → 401 Unauthorized
  WWW-Authenticate: Bearer realm="api"
  
  Triggers: No token, expired token, invalid token, bad credentials.

403 Forbidden
  Client is authenticated but not authorized for this resource/action.
  Server knows WHO you are but you don't have PERMISSION.
  
  DELETE /users/1 (as a regular user trying to delete admin)
  → 403 Forbidden
  { "error": "INSUFFICIENT_PERMISSIONS", "message": "Cannot delete admin users" }

401 vs 403:
  401: "Who are you? Please log in." (authentication failure)
  403: "I know who you are. You can't do this." (authorization failure)

404 Not Found
  Resource doesn't exist at the given URI.
  Use for: Requested resource doesn't exist.
  Also: Sometimes returned instead of 403 to avoid revealing existence of resources.
  
  GET /users/99999 (doesn't exist) → 404 Not Found

405 Method Not Allowed
  HTTP method not supported for this URI.
  Must include Allow header listing supported methods.
  
  DELETE /users (deleting entire collection disallowed)
  → 405 Method Not Allowed
  Allow: GET, POST, HEAD, OPTIONS

406 Not Acceptable
  Server can't produce a response matching client's Accept headers.
  Client requested Accept: application/xml but server only supports JSON.
  → 406 Not Acceptable

408 Request Timeout
  Server timed out waiting for the request.
  Client should consider retrying.

409 Conflict
  Request conflicts with current resource state.
  Use for: Duplicate creation, concurrent modification conflicts, state machine violations.
  
  POST /users { "email": "existing@example.com" }
  → 409 Conflict
  { "error": "EMAIL_ALREADY_EXISTS", "message": "User with this email already exists" }
  
  PUT /orders/42 { "status": "cancelled" } (order already shipped)
  → 409 Conflict
  { "error": "INVALID_STATE_TRANSITION", "message": "Cannot cancel a shipped order" }
  
  ETag mismatch on conditional PUT:
  → 412 Precondition Failed (see below) or 409

410 Gone
  Resource permanently removed from server.
  Different from 404: 410 means we KNOW it existed and was intentionally removed.
  Can be cached by browsers/proxies (like 301 permanent redirect).
  
  Use: Deleted resources that will never come back.
       Deprecated API versions.

412 Precondition Failed
  A precondition header (If-Match, If-None-Match, If-Modified-Since) evaluated to false.
  Use: Optimistic locking / conditional updates.
  
  PUT /users/42
  If-Match: "etag-v1"
  → 412 Precondition Failed (resource was modified by someone else)

413 Content Too Large (formerly Payload Too Large)
  Request body exceeds server's size limit.
  
  POST /upload (file too large) → 413 Content Too Large

414 URI Too Long
  Request URI too long for server to process.

415 Unsupported Media Type
  Server doesn't support the Content-Type of the request.
  
  POST /api/users
  Content-Type: application/xml  (server only accepts JSON)
  → 415 Unsupported Media Type

422 Unprocessable Entity
  Request is syntactically correct but semantically invalid.
  Use: Business rule violations, logical validation errors.
  
  POST /orders { "quantity": -5 }
  → 422 Unprocessable Entity
  { "error": "INVALID_QUANTITY", "message": "Quantity must be positive" }
  
  400 vs 422 DISTINCTION:
  400: Can't parse the request (malformed JSON, wrong structure)
  422: Parsed successfully but data violates business rules
  
  Many APIs use 400 for both (acceptable); 422 is more precise.

429 Too Many Requests
  Rate limit exceeded. Client should slow down.
  Should include Retry-After header.
  
  → 429 Too Many Requests
  Retry-After: 60
  X-RateLimit-Limit: 100
  X-RateLimit-Remaining: 0
  X-RateLimit-Reset: 1718000000

451 Unavailable For Legal Reasons
  Resource removed due to legal demands.
  Name from Fahrenheit 451 (censorship reference).
  Use: DMCA takedowns, court orders, regional content restrictions.

4. 5xx SERVER ERROR CODES
================================================================================

500 Internal Server Error
  Catch-all for unexpected server errors.
  Use: Unhandled exceptions, bugs, unexpected failures.
  Do NOT expose stack traces or internal details in response.
  Log details server-side with correlation ID.
  
  → 500 Internal Server Error
  { "error": "INTERNAL_ERROR", "requestId": "req-abc123", 
    "message": "An unexpected error occurred" }

501 Not Implemented
  Server does not support the functionality required to fulfill the request.
  Correct code for unimplemented HTTP methods (if not planning to implement).

502 Bad Gateway
  Server (acting as proxy/gateway) received invalid response from upstream.
  Use: Upstream service returned garbage, crashed mid-response.
  Common in: Nginx/ALB in front of app server that crashed.

503 Service Unavailable
  Server temporarily unavailable (overloaded, maintenance).
  Include Retry-After header to hint when to retry.
  
  → 503 Service Unavailable
  Retry-After: 30
  { "error": "SERVICE_UNAVAILABLE", "message": "Maintenance in progress" }

504 Gateway Timeout
  Upstream server didn't respond in time.
  Use: App server took too long to respond; database timeout.
  Different from 408 (client didn't send request in time).

6. BEST PRACTICES FOR STATUS CODES
================================================================================

1. NEVER return 200 with an error body:
   ❌ 200 OK { "success": false, "error": "Not found" }
   ✅ 404 Not Found { "error": "USER_NOT_FOUND" }

2. Be specific but don't over-engineer:
   Most APIs need: 200, 201, 204, 400, 401, 403, 404, 409, 422, 429, 500
   Use other codes when clearly applicable.

3. Include error details in body:
   {
     "error": "VALIDATION_FAILED",
     "message": "Human-readable description",
     "requestId": "uuid-for-tracing",
     "timestamp": "2026-04-08T10:00:00Z",
     "details": [
       { "field": "email", "message": "Invalid email format" }
     ]
   }

4. Security: Don't reveal sensitive info in 4xx/5xx responses.
   Don't say "User with this email doesn't exist" (reveals account enumeration).
   Say "Invalid credentials" for both wrong email and wrong password.

5. Log with correlation IDs:
   Return X-Request-Id or requestId in error responses.
   Makes debugging production issues easier.

7. INTERVIEW QUESTIONS — HTTP STATUS CODES
================================================================================

Q1: What is the difference between 401 and 403?
    401 Unauthorized (actually "unauthenticated"): The client has not provided
    valid credentials or no credentials at all. "Who are you? Please log in."
    Server must include WWW-Authenticate header.
    403 Forbidden: The client is authenticated, but not authorized to perform
    this action on this resource. "I know who you are. You can't do this."

Q2: When would you return 422 vs 400?
    400: Request is malformed — can't parse the JSON, missing required structure.
    422: Request is syntactically valid but semantically wrong — fails business
    rules (negative quantity, invalid date range, illegal state transition).
    Many APIs use 400 for both (acceptable). 422 is more semantically precise.

Q3: What is the PRG pattern and what problem does it solve?
    Post-Redirect-Get. After a POST (form submission), redirect to a GET with
    303 See Other. This prevents duplicate form submissions when user refreshes
    or uses back/forward buttons. Browser refresh replays GET, not POST.

Q4: What's the difference between 404 and 410?
    404: Resource not found — may have never existed, we don't know.
    410: Resource permanently gone — we know it existed and was deleted.
    410 can be cached by clients/proxies (resource won't come back).
    Use 410 for deleted resources you want clients to stop requesting.

Q5: When should you use 202 Accepted?
    When processing happens asynchronously — request is received and queued but
    result isn't ready yet. Return a jobId and statusUrl so client can poll.
    Examples: Video encoding, report generation, bulk imports, email sending.

Q6: What status code for duplicate resource creation?
    409 Conflict — the resource already exists and the request conflicts with
    current state. Include specific error code (EMAIL_ALREADY_EXISTS) and
    message to help the client understand what to fix.

Q7: What status code for rate limiting?
    429 Too Many Requests with Retry-After header. Also include
    X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers
    to inform client of their quota and when it resets.
