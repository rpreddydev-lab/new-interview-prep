OBSERVABILITY INTERVIEW QUESTIONS
===================================

=== FUNDAMENTALS ===

Q: What are the three pillars of observability?
A: Metrics (aggregated numerical measurements — rates, counts, latencies),
   Logs (timestamped event records), and Traces (end-to-end request paths
   across distributed services). Together they enable understanding of system
   behavior from external outputs.

Q: What is the difference between monitoring and observability?
A: Monitoring tracks predefined metrics for known failure modes — reactive.
   Observability enables answering arbitrary questions about system state —
   proactive. You need both: monitoring for known problems, observability
   for unknown ones.

Q: What is a distributed trace?
A: A trace represents the full journey of a request across all services.
   It consists of spans — individual units of work. Each span has a spanId,
   parentSpanId, operation name, start time, and duration. Spans from different
   services are correlated by the shared trace ID.

Q: What is the difference between a liveness probe and a readiness probe?
A: Liveness: is the app still alive? Kubernetes restarts pod if fails.
   Readiness: is the app ready to receive traffic? Kubernetes removes from
   load balancer if fails. A startup crash → liveness fails → restart.
   A warm-up period → readiness fails → no traffic until ready.

=== MICROMETER AND METRICS ===

Q: What is Micrometer and why use it?
A: Micrometer is a vendor-neutral metrics facade for JVM applications — like
   SLF4J for metrics. Write metric code once, switch backends (Prometheus,
   Datadog, CloudWatch) without changing application code.

Q: What metric types does Micrometer support?
A: Counter (monotonic increment), Gauge (current value up/down), Timer (latency
   + count + throughput), DistributionSummary (non-time measurements like bytes),
   LongTaskTimer (ongoing task duration).

Q: Why should tags have low cardinality?
A: Each unique tag value combination creates a new metric series. High-cardinality
   tags (userId, orderId) create millions of series → overwhelm Prometheus,
   increase storage, degrade query performance. Use low-cardinality tags:
   status, region, method, endpoint pattern (not exact URL with path variables).

Q: How do you measure P99 latency with Micrometer?
A: Use Timer with publishPercentileHistogram() enabled. Prometheus scrapes
   the histogram buckets. PromQL: histogram_quantile(0.99, rate(timer_bucket[5m]))

=== TRACING ===

Q: What is OpenTelemetry?
A: CNCF standard for telemetry — unified SDK for metrics, logs, and traces.
   Vendor-neutral — works with Jaeger, Zipkin, Datadog, AWS X-Ray.
   Replacing Spring Cloud Sleuth in Spring Boot 3.x.

Q: How is trace context propagated between services?
A: Via HTTP headers. W3C TraceContext standard uses "traceparent" header
   (00-{traceId}-{spanId}-{flags}). B3 format (Zipkin legacy) uses separate
   X-B3-TraceId, X-B3-SpanId headers. Spring Boot 3 uses W3C by default.

Q: What is sampling in tracing and why is it important?
A: Recording every single request creates massive overhead and cost. Sampling
   decides what percentage of requests to trace. Production: 1-10% probabilistic
   sampling, but always sample errors and slow requests (tail-based sampling).

Q: How do you correlate logs with traces?
A: Inject trace ID and span ID into MDC. Include MDC fields in log pattern.
   Spring Boot 3 with Micrometer Tracing does this automatically.
   Result: given a trace ID, find all log lines across all services.

=== LOGGING ===

Q: Why use SLF4J instead of directly using Logback or Log4j2?
A: SLF4J is a facade — decouples application code from logging implementation.
   You can switch from Logback to Log4j2 by changing one dependency, not
   rewriting all logging calls. Same as JDBC abstraction for databases.

Q: What is structured logging and why is it important?
A: Structured logging outputs logs as JSON with named fields instead of
   plain text. This enables log aggregation tools (Elasticsearch, Splunk,
   CloudWatch Logs Insights) to index, search, and filter by specific fields
   like orderId, traceId, customerId — impossible with plain text.

Q: What is MDC and how do you use it?
A: Mapped Diagnostic Context — thread-local key-value store for logging context.
   MDC.put("orderId", id) → all subsequent log statements in that thread
   include orderId in the log output. Essential for correlating related log
   lines. Clean up with MDC.remove() or MDC.clear() after request processing.

Q: What log level should you use in production?
A: Root level: WARN or INFO. Application packages: INFO.
   DEBUG in production only for specific packages when troubleshooting.
   Never TRACE in production — too verbose, performance impact.

=== ELK ===

Q: What is the role of each component in the ELK stack?
A: Elasticsearch: distributed search engine — stores and indexes logs.
   Logstash: log pipeline — ingests, parses, transforms, routes log data.
   Kibana: visualization UI — dashboards, search, alerts over Elasticsearch.
   Filebeat: lightweight agent — tails log files and ships to Logstash/ES.

Q: How would you debug a production issue using observability tools?
A: 1) Check Grafana dashboards — which metric is anomalous? Error rate spike?
   2) Set alert time as filter in Kibana — search for ERROR logs in that window.
   3) Find a trace ID from an error log.
   4) Open Jaeger/Zipkin — find that trace — see which service/span is slow.
   5) Use trace ID in Kibana to see all related log lines across all services.
   6) Find root cause — upstream service timeout? DB slow query? OOM?
