1. OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  JavaScript is single-threaded — only one thing executes at a time.
  The Event Loop is the mechanism that lets JS perform non-blocking I/O
  by offloading operations to the host environment (browser/Node), then
  scheduling callbacks when results are ready.

  ┌─────────────────────────────────────────────┐
  │           JavaScript Runtime                │
  │                                             │
  │  ┌────────────┐      ┌──────────────────┐  │
  │  │ Call Stack │      │   Heap (Memory)  │  │
  │  │            │      │  (objects, fns)  │  │
  │  └────────────┘      └──────────────────┘  │
  │                                             │
  │  Host Environment (Browser / Node.js)       │
  │  ┌───────────────────────────────────────┐  │
  │  │  Web APIs / C++ APIs                  │  │
  │  │  (setTimeout, fetch, DOM events, fs)  │  │
  │  └───────────────────────────────────────┘  │
  │                                             │
  │  ┌──────────────┐  ┌──────────────────────┐ │
  │  │  Microtask   │  │  Macrotask / Callback │ │
  │  │    Queue     │  │       Queue           │ │
  │  │  (Promises,  │  │  (setTimeout,setInt-  │ │
  │  │  queueMicro) │  │  erval, I/O, UI)      │ │
  │  └──────────────┘  └──────────────────────┘ │
  │                                             │
  │  ┌──────────────────────────────────────┐   │
  │  │           Event Loop                 │   │
  │  └──────────────────────────────────────┘   │
  └─────────────────────────────────────────────┘

2. COMPONENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  CALL STACK
  - LIFO (Last In, First Out) data structure
  - Tracks currently executing function contexts
  - Synchronous code runs here
  - Stack overflow: too many nested calls

  HEAP
  - Unstructured memory region
  - Stores objects, closures, functions

  WEB APIS (Browser) / C++ APIs (Node.js)
  - Handles async work OUTSIDE the JS engine:
    - setTimeout / setInterval
    - fetch / XMLHttpRequest
    - DOM event listeners
    - File system I/O (Node)
  - When work completes, pushes callback to queue

  CALLBACK QUEUE (Macrotask Queue)
  - Callbacks from Web APIs waiting to run
  - FIFO (First In, First Out)

  MICROTASK QUEUE
  - Higher priority than callback queue
  - Filled by: Promise.then/catch/finally, queueMicrotask(), MutationObserver
  - Drained COMPLETELY before any macrotask runs

  EVENT LOOP ALGORITHM (simplified):
  1. Execute all synchronous code (drain call stack)
  2. Drain ALL microtasks (process every microtask queued, including new ones)
  3. Execute ONE macrotask from callback queue
  4. Drain ALL microtasks again
  5. Render (browser) if needed
  6. Go to step 3

3. EXECUTION ORDER EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  console.log("A");                          // 1) sync

  setTimeout(() => console.log("B"), 0);    // macrotask queue

  Promise.resolve()
    .then(() => console.log("C"));           // microtask queue

  console.log("D");                          // 2) sync

  // Output: A, D, C, B

  // Explanation:
  // "A" → call stack (sync)
  // setTimeout queued → Web API, 0ms, moves to macrotask queue
  // Promise.resolve().then → callback to microtask queue
  // "D" → call stack (sync)
  // Stack empty → drain microtasks: "C"
  // Microtasks empty → run one macrotask: "B"

  // More complex example:
  console.log("1");                          // sync

  setTimeout(() => {
    console.log("2");                        // macrotask
    Promise.resolve().then(() => console.log("3"));  // microtask
  }, 0);

  Promise.resolve().then(() => {
    console.log("4");                        // microtask
    setTimeout(() => console.log("5"), 0);  // schedules macrotask
  });

  console.log("6");                          // sync

  // Output: 1, 6, 4, 2, 3, 5

4. NODE.JS EVENT LOOP PHASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Node.js uses libuv which has more specific phases:

  ┌──────────────────────────────────────────────────┐
  │   timers         — executes setTimeout/setInterval│
  │                    callbacks whose delay expired  │
  ├──────────────────────────────────────────────────┤
  │   pending I/O    — I/O callbacks deferred to      │
  │                    next loop                      │
  ├──────────────────────────────────────────────────┤
  │   idle, prepare  — internal use                   │
  ├──────────────────────────────────────────────────┤
  │   poll           — retrieve new I/O events;       │
  │                    execute I/O-related callbacks  │
  ├──────────────────────────────────────────────────┤
  │   check          — setImmediate() callbacks       │
  ├──────────────────────────────────────────────────┤
  │   close callbacks— socket.on("close", ...) etc.  │
  └──────────────────────────────────────────────────┘

  Between EACH phase: microtasks (Promises) and process.nextTick drain.
  process.nextTick fires before other microtasks.

  setTimeout vs setImmediate:
  - setTimeout(fn, 0) fires in "timers" phase
  - setImmediate(fn) fires in "check" phase (after I/O)
  - Inside I/O callback: setImmediate always runs before setTimeout

5. BLOCKING THE EVENT LOOP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Any synchronous operation that takes too long BLOCKS the event loop.
  No callbacks, events, or timers can fire during this time.

  // BAD — blocks the event loop:
  function processLargeArray(arr) {
    arr.forEach(item => heavyComputation(item));  // all synchronous
  }

  // BETTER — yield control between chunks:
  function processInChunks(arr, chunkSize = 100) {
    let i = 0;
    function processChunk() {
      const end = Math.min(i + chunkSize, arr.length);
      for (; i < end; i++) heavyComputation(arr[i]);
      if (i < arr.length) setTimeout(processChunk, 0);  // yield
    }
    processChunk();
  }

  // BEST for CPU-heavy work: Web Workers / worker_threads (Node)

6. requestAnimationFrame
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  requestAnimationFrame(fn) fires before the browser's next repaint.
  It sits between macrotasks and rendering in the browser event loop.

  // Use for smooth animations:
  function animate() {
    updateState();
    render();
    requestAnimationFrame(animate);  // schedule next frame
  }
  requestAnimationFrame(animate);

7. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the Event Loop?
A: It's the mechanism that allows JavaScript (single-threaded) to handle
   asynchronous operations. When the call stack is empty, the event loop
   checks the microtask queue (drains it fully), then picks one task from
   the macrotask queue, and repeats.

Q: What is the difference between the call stack and the task queue?
A: The call stack executes synchronous code in LIFO order. The task queue
   holds async callbacks waiting to be pushed to the call stack. Callbacks
   only run when the call stack is completely empty.

Q: Why does setTimeout(() => ..., 0) not run immediately?
A: Even with 0ms delay, setTimeout goes through the Web API, then to the
   macrotask queue. It only runs after the current synchronous code AND all
   microtasks have completed.

Q: What is the output?
   setTimeout(() => console.log("A"), 0);
   Promise.resolve().then(() => console.log("B"));
   console.log("C");
A: C, B, A — sync first, then microtask (Promise), then macrotask (setTimeout).

Q: How does blocking the event loop harm performance?
A: Long synchronous operations prevent callbacks, timers, UI events, and
   I/O from being processed. In a browser this causes UI freezes. In Node.js
   it blocks ALL incoming requests.

Q: How is Node.js event loop different from the browser's?
A: Node uses libuv with explicit phases (timers, I/O poll, check, etc.).
   It also has setImmediate() and process.nextTick(). process.nextTick()
   runs before all microtasks — it has the highest priority.
