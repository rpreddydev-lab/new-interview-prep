1. WHAT IS A JS ENGINE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A JavaScript Engine is a program that:
  1. Parses JavaScript source code
  2. Converts it to machine code
  3. Executes it

2. V8 ENGINE — DEEP DIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V8 Pipeline:
  Source Code
       │
       ▼
  [Scanner/Lexer] → Token stream
       │
       ▼
  [Parser] → AST (Abstract Syntax Tree)
       │
       ▼
  [Ignition Interpreter] → Bytecode
       │  (profile-guided)
       ▼
  [TurboFan JIT Compiler] → Optimized Machine Code
       │  (deoptimize if assumption wrong)
       ▼
  [Execution]

IGNITION (Interpreter):
  - Converts AST to compact bytecode
  - Faster startup (bytecode is smaller than machine code)
  - Collects runtime type/feedback data (type profiling)
  - Runs all code initially

TURBOFAN (JIT Compiler):
  - Compiles HOT functions (frequently called) to optimized machine code
  - Uses speculative optimization: assumes types remain the same
  - If assumption violated → DEOPTIMIZATION → falls back to Ignition

MAGLEV (newer, 2023+):
  - Mid-tier JIT between Ignition and TurboFan
  - Faster to compile than TurboFan, better than Ignition
  - Reduces deoptimization overhead

3. JIT COMPILATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

JIT = Just-In-Time Compilation
  - Code compiled at RUNTIME (not ahead-of-time like C++)
  - Combines benefits of interpretation (fast startup) + compilation (fast exec)

Speculative Optimization Example:
  function add(a, b) { return a + b; }
  add(1, 2);       // TurboFan assumes a, b are always numbers
  add(3, 4);       // Generates optimized machine code for number addition
  add("x", "y");   // Type assumption violated → DEOPTIMIZATION

Performance Tips (related to JIT):
  - Keep function signatures consistent (same types every call)
  - Avoid changing object shapes after creation (hidden classes)
  - Don't mix object property access patterns

4. HIDDEN CLASSES (V8 Internal Optimization)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V8 assigns a "hidden class" (C0, C1, C2...) to each object based on its
shape (property names and order). This allows V8 to optimize property access
like a compiled language.

  // GOOD: consistent object shape → single hidden class
  function Point(x, y) {
    this.x = x;
    this.y = y;
  }
  const p1 = new Point(1, 2);
  const p2 = new Point(3, 4);
  // Both share the same hidden class → optimized property access

  // BAD: adding properties dynamically changes hidden class
  const obj = {};
  obj.x = 1;   // hidden class C0 → C1
  obj.y = 2;   // C1 → C2

  // BAD: same properties, different order → different hidden classes
  const a = { x: 1, y: 2 };
  const b = { y: 2, x: 1 };  // different hidden class from a!

  // BAD: delete property
  delete obj.x;  // creates new hidden class, disables optimization

Best Practice: initialize all properties in the constructor in the same order.

5. INLINE CACHES (ICs)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V8 uses Inline Caches to speed up repeated property access:
  - Monomorphic IC: always same hidden class → fastest path
  - Polymorphic IC: 2-4 different hidden classes → slightly slower
  - Megamorphic IC: 5+ different classes → slow, no caching

  // Monomorphic (fast):
  function getX(obj) { return obj.x; }
  getX({ x: 1 });  getX({ x: 2 });  // always same shape

  // Megamorphic (slow):
  getX({ x: 1, a: 1 });
  getX({ x: 2, b: 2 });
  getX({ x: 3, c: 3 }); // different shapes every time

6. MEMORY MANAGEMENT IN V8
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

V8 Heap Structure:
  ┌────────────────────────────────────────────┐
  │                  V8 Heap                  │
  │  ┌──────────────┐   ┌───────────────────┐ │
  │  │  New Space   │   │    Old Space      │ │
  │  │  (Nursery)   │   │  (Tenured Objects)│ │
  │  │  Small, fast │   │  Large, slower GC │ │
  │  │  Scavenger GC│   │  Major GC (M&S)   │ │
  │  └──────────────┘   └───────────────────┘ │
  │  ┌──────────┐  ┌─────────┐  ┌──────────┐ │
  │  │ Code Sp. │  │Map Sp.  │  │ Large Ob.│ │
  │  │(compiled)│  │(hid cls)│  │  Space   │ │
  │  └──────────┘  └─────────┘  └──────────┘ │
  └────────────────────────────────────────────┘

  New Space (Young Generation):
    - Newly allocated objects land here
    - Scavenger GC (minor GC) runs frequently
    - Survivors promoted to Old Space after 2 GC cycles

  Old Space (Old Generation):
    - Long-lived objects
    - Mark-and-Sweep + Mark-Compact GC (major GC, slower)
    - Uses incremental marking to avoid long pauses

7. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is V8 and what makes it fast?
A: V8 is Google's JS engine (C++). Fast because: JIT compilation via Ignition
   (interpreter) + TurboFan (optimizing compiler), hidden classes for fast
   property access, inline caches, and generational GC.

Q: What is JIT compilation?
A: Just-In-Time: code is compiled at runtime, not before. The engine first
   interprets code, profiles which functions are "hot" (called often), and
   compiles those to native machine code for future calls.

Q: What is deoptimization?
A: When TurboFan's speculative assumptions (e.g., "this will always be a
   number") are violated at runtime, V8 "deoptimizes" back to Ignition
   interpreted bytecode for that function and re-profiles.

Q: How do hidden classes help performance?
A: V8 assigns hidden classes to objects based on their structure/shape.
   Objects with identical shapes share a hidden class, enabling V8 to do
   offset-based property lookup (like C structs) rather than dictionary lookup.

Q: What is the difference between bytecode and machine code?
A: Bytecode is an intermediate representation (platform-independent)
   executed by the interpreter. Machine code is CPU-specific native
   instructions executed directly by hardware — much faster.

Q: How do Web Workers differ from the main JS thread?
A: Web Workers run in separate OS threads with their own V8 instance and
   memory. They communicate via postMessage (structured clone). They cannot
   access the DOM. They enable true parallelism in browsers.
