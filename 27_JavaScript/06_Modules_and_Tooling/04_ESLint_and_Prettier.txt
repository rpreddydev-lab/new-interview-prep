1. ESLint — LINTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ESLint is a static analysis tool that finds BUGS and STYLE issues.
  It applies rules to your code and reports problems.

  // .eslintrc.json (legacy config):
  {
    "env": {
      "browser": true,
      "es2022": true,
      "node": true
    },
    "extends": [
      "eslint:recommended",
      "plugin:react/recommended",
      "plugin:@typescript-eslint/recommended"
    ],
    "parser": "@typescript-eslint/parser",
    "parserOptions": { "ecmaVersion": "latest", "sourceType": "module" },
    "plugins": ["react", "@typescript-eslint"],
    "rules": {
      "no-unused-vars": "warn",
      "no-console": ["warn", { "allow": ["error"] }],
      "eqeqeq": ["error", "always"],        // enforce ===
      "no-var": "error",                    // disallow var
      "prefer-const": "warn",
      "no-eval": "error",
      "no-implicit-globals": "error"
    },
    "ignorePatterns": ["dist/", "node_modules/"]
  }

  // ESLint flat config (eslint.config.js — ESLint 9+):
  import js from "@eslint/js";
  import globals from "globals";
  export default [
    js.configs.recommended,
    { languageOptions: { globals: globals.browser } },
    { rules: { "no-unused-vars": "warn" } }
  ];

  // Rule severity:
  "off" or 0   — disable rule
  "warn" or 1  — warning (non-breaking)
  "error" or 2 — error (breaks build/CI)

2. PRETTIER — FORMATTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Prettier is an OPINIONATED code formatter. It reformats code
  automatically, enforcing a consistent style regardless of what was written.

  // .prettierrc:
  {
    "semi": true,
    "singleQuote": false,
    "printWidth": 80,
    "tabWidth": 2,
    "useTabs": false,
    "trailingComma": "es5",   // "none" | "es5" | "all"
    "bracketSpacing": true,   // { foo: bar } vs {foo: bar}
    "arrowParens": "always",  // (x) => vs x =>
    "endOfLine": "lf"
  }

  // .prettierignore:
  node_modules/
  dist/
  build/
  *.min.js

  Commands:
  npx prettier --check .      # check without changing
  npx prettier --write .      # format all files
  npx prettier --write src/   # format specific directory

3. ESLint vs PRETTIER — KEY DIFFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌────────────────────────────┬────────────────────────────────────────────┐
  │ ESLint                     │ Prettier                                   │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ Finds BUGS & logic issues  │ Formats CODE STYLE only                    │
  │ no-unused-vars, eqeqeq     │ indentation, quotes, trailing commas       │
  │ Highly configurable rules  │ Opinionated, few options                   │
  │ Can auto-fix many issues   │ Always reformats to consistent style       │
  │ Used together with Prettier│ Used together with ESLint                  │
  └────────────────────────────┴────────────────────────────────────────────┘

  They complement each other:
  - ESLint catches logical errors, code quality issues
  - Prettier handles all formatting (indentation, line length, quotes)

4. USING THEM TOGETHER (AVOIDING CONFLICTS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ESLint's formatting rules conflict with Prettier.
  Fix: disable ESLint formatting rules, let Prettier handle them.

  // Install:
  npm install -D eslint-config-prettier  // disables ESLint formatting rules
  npm install -D eslint-plugin-prettier  // (optional) runs Prettier as ESLint rule

  // .eslintrc.json — add "prettier" LAST in extends:
  {
    "extends": [
      "eslint:recommended",
      "plugin:react/recommended",
      "prettier"            // MUST be last — disables conflicting rules
    ]
  }

  // Or with plugin (Prettier violations show as ESLint errors):
  {
    "plugins": ["prettier"],
    "rules": { "prettier/prettier": "error" }
  }

5. DISABLING RULES INLINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  // Disable for whole file:
  /* eslint-disable */

  // Disable specific rule for whole file:
  /* eslint-disable no-console */

  // Disable for next line:
  // eslint-disable-next-line no-unused-vars
  const x = 1;

  // Disable for a block:
  /* eslint-disable no-eval */
  eval("something");
  /* eslint-enable no-eval */

  // Prettier — ignore block:
  // prettier-ignore
  const matrix = [
    1, 0, 0,
    0, 1, 0,
    0, 0, 1
  ];

6. HUSKY AND lint-staged (PRE-COMMIT HOOKS)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Run ESLint + Prettier automatically before every commit:

  npm install -D husky lint-staged
  npx husky init

  // .husky/pre-commit:
  npx lint-staged

  // package.json:
  {
    "lint-staged": {
      "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"],
      "*.{css,json,md}": ["prettier --write"]
    }
  }

  // Benefit: only lints/formats staged files — fast even in large projects.

7. COMMON INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: What is the difference between ESLint and Prettier?
A: ESLint is a linter — it finds bugs, enforces code quality rules (no-unused-vars,
   eqeqeq). Prettier is a formatter — it rewrites code style (indentation, quotes,
   line width) without changing logic. They are complementary, not alternatives.

Q: How do you prevent ESLint and Prettier from conflicting?
A: Add eslint-config-prettier to the LAST position in ESLint's extends array.
   It disables all ESLint rules that would conflict with Prettier's formatting.

Q: What does "opinionated" mean in the context of Prettier?
A: Prettier offers very few configuration options intentionally. It enforces
   one consistent style, removing style debates from code reviews. You use
   its output or you don't use Prettier — no middle ground.

Q: What is lint-staged used for?
A: It runs linters/formatters only on files staged for a commit, making
   pre-commit hooks fast by avoiding processing the entire codebase.

Q: How do ESLint rules work?
A: Each rule is identified by a name (e.g. no-unused-vars). Severity can be
   "off", "warn", or "error". Rules can accept options (arrays). Rules are
   enforced by ESLint's AST traversal — each rule registers visitors for
   specific AST node types.
