1. CLARIFYING THE TERMINOLOGY CONFUSION
================================================================================

The Confusion:
  "CD" stands for BOTH Continuous Delivery AND Continuous Deployment.
  
  In interview contexts, most people mean Continuous Delivery when they say CD.
  
  The pipeline is often called "CI/CD" which means CI + Continuous Delivery.
  Full Continuous Deployment is a more advanced and less common practice.

The Hierarchy:
  
  CONTINUOUS INTEGRATION
  ──────────────────────
  Commit → Build → Test → ✓ Artifact Ready
  (Code is always tested and integrated)
  │
  ▼
  CONTINUOUS DELIVERY
  ───────────────────
  CI + Staging Validation → [MANUAL GATE] → Production Deploy
  (Software is always in a deployable state)
  │
  ▼ (optional next step)
  CONTINUOUS DEPLOYMENT
  ─────────────────────
  CI + Staging Validation → AUTO Deploy to Production
  (Every passing change goes to production automatically)

Mental Model:
  - CD is a CAPABILITY, not a process step
  - Having CD means you CAN deploy safely at any time
  - Continuous Deployment means you DO deploy automatically every time
  - Every team doing Continuous Deployment practices Continuous Delivery
  - NOT every team doing Continuous Delivery practices Continuous Deployment

2. CONTINUOUS DELIVERY: DEEP DIVE
================================================================================

Definition:
  Continuous Delivery is a software engineering approach in which teams produce
  software in short cycles, ensuring that software can be reliably released at
  any time. The goal is to build, test, and release software with greater speed
  and frequency.
  
  Key word: CAN be released. Not WILL be automatically released.

The Deployment Button:
  In CD, there is a "deploy to production" button (literal or metaphorical).
  Pressing it should be:
  - Safe (all automated tests have passed)
  - Fast (minutes, not days)
  - Reliable (same process every time)
  - Boring (not a special ceremony)
  
  The button should be available to any authorized person:
  - A developer who merged a hot fix
  - A product manager who wants to release a feature
  - An operations engineer responding to a customer issue

CD Pipeline (Delivery):

  [Code Push] → [CI: Build + Test] → [Artifact Published]
       ↓                                     ↓
  [Staging Deploy]                    [Staging Tests]
       ↓                                     ↓
  [UAT / Review]  ←───────────────── [Staging Validated]
       ↓
  [MANUAL APPROVAL] ← Product/QA/Change Manager clicks approve
       ↓
  [Production Deploy] → [Smoke Tests] → [Monitor]

Why Keep the Manual Gate?
  
  1. REGULATORY COMPLIANCE:
     SOX (Sarbanes-Oxley): Requires documented approvals for financial systems
     FDA 21 CFR Part 11: Electronic records and signatures for medical software
     PCI-DSS: Change control requirements for payment processing
     HIPAA: Audit trails for healthcare software
     ISO 27001: Change management process controls
  
  2. BUSINESS COORDINATION:
     Marketing campaigns timed with feature launches
     Support team needs to be prepared for new features
     Documentation must be updated before release
     Coordinating with partners/integrations
  
  3. RISK MANAGEMENT:
     High-stakes changes (pricing algorithms, security features)
     Large user-facing UI changes
     Breaking API changes affecting external consumers
  
  4. NOT ENOUGH TEST CONFIDENCE:
     Team is still building automated test coverage
     Some paths only catchable with human judgment
     New team building CD maturity gradually

CD in Regulated Industries:
  
  CHANGE ADVISORY BOARD (CAB):
    Traditional IT organizations use a CAB to review and approve changes.
    High-ceremony, scheduled meetings (often weekly).
    Can be a bottleneck: Emergency patch must wait for Friday's CAB meeting.
    
  MODERN APPROACH (Continuous Compliance):
    Policy as Code: Automated checks replacing manual CAB reviews
    Risk-based approval: Low-risk changes auto-approved; high-risk get review
    ITSM integration: ServiceNow tickets auto-created and closed by pipeline
    Audit trail: Pipeline logs serve as evidence for compliance audits
    
    Example: Atlassian Jira + ServiceNow ITSM integrated with CI/CD:
    - Low-risk changes: Pipeline creates and auto-closes ServiceNow ticket
    - High-risk changes: Pipeline creates ticket and requires human approval
    - Audit: Every deployment has corresponding change record

DELIVERING WITHOUT DEPLOYING (Dark Launches):
  Deploy code to production but feature is hidden behind a flag.
  Users don't see it yet. Technical deployment is done.
  "Release" (turning on the flag) is separate from deployment.
  
  Benefits:
  - Test new code on real production infrastructure
  - Warm up caches, validate performance
  - Let product team decide exactly when to launch
  - Decouple tech team's work from business calendar

3. CONTINUOUS DEPLOYMENT: DEEP DIVE
================================================================================

Definition:
  Continuous Deployment is an extension of Continuous Delivery where every
  change that passes all automated stages of the production pipeline is
  automatically released to customers.
  
  There is NO human gate before production.
  
  "Every green build goes to production."

The Continuous Deployment Pipeline:

  [Code Merge to Main]
       ↓
  [CI: Build + Test] → ✗ Failed: Stop, notify developer
       ↓ ✓
  [Artifact: Docker Image pushed to registry]
       ↓
  [Deploy to Staging]
       ↓
  [Integration/E2E Tests] → ✗ Failed: Stop, notify developer
       ↓ ✓
  [Performance Tests] → ✗ Failed: Stop, notify developer
       ↓ ✓
  [Deploy to Production] ← AUTOMATIC, no human click needed
       ↓
  [Synthetic/Smoke Tests] → ✗ Failed: AUTO-ROLLBACK triggered
       ↓ ✓
  [Progressive rollout: 1% → 10% → 100% over 30min]
       ↓
  [Monitor: error rate, latency, business metrics]
       → Exceeds thresholds: AUTO-ROLLBACK
       → Within thresholds: Deployment successful

Prerequisites for Continuous Deployment:
  
  MUST HAVE:
  ✓ Comprehensive test suite (unit, integration, E2E, contract)
    - High confidence: > 90% code coverage + critical path coverage
    - Fast tests: < 15 minutes for CI stage
    - Reliable tests: < 1% flakiness rate
  
  ✓ Feature flags system
    - Incomplete features can be in trunk, hidden by flags
    - Instant rollback: disable flag = instant revert without deploy
    - Gradual rollout: enable for 1% → 10% → 100% of users
  
  ✓ Production monitoring with automatic alerting
    - Error rate monitoring with thresholds
    - Performance (latency, throughput) monitoring
    - Business metrics (sign-ups, transactions, conversion) monitoring
    - PagerDuty/OpsGenie integration for immediate notification
  
  ✓ Automated rollback capability
    - Deploy old version automatically if thresholds exceeded
    - Argo Rollouts or Flagger for Kubernetes-based automated promotion/rollback
  
  ✓ Mature on-call culture
    - Engineers who wrote code are on-call for it
    - Runbooks for common incidents
    - Mean Time to Recovery (MTTR) is short (minutes, not hours)
  
  ✓ Trunk-based development
    - No long-lived branches (merging multiple times per day)
    - Feature flags for work in progress
    - Small, atomic commits

  NICE TO HAVE:
  ○ Chaos engineering practice
  ○ Progressive delivery tools (Argo Rollouts, Flagger)
  ○ Service mesh for fine-grained traffic control
  ○ Automated performance regression detection

Continuous Deployment at Scale:
  
  How companies like Amazon, Netflix, Facebook do it:
  
  AMAZON:
    - Deploys to production every 11.6 seconds (peak)
    - Each service team deploys independently
    - Microservices: Each service has its own pipeline
    - Automated canary analysis (ACA): Deploy to 1 host, analyze, expand
  
  NETFLIX:
    - 700+ microservices, each deployed independently
    - Spinnaker (open-sourced by Netflix) for automated CD
    - Chaos Monkey: Intentionally kills production instances
    - "If your service can't survive Chaos Monkey, you can't deploy"
  
  FACEBOOK:
    - Gatekeeper system: Feature flags for gradual rollouts
    - Ship it: Tool for managing who sees what version
    - Dark launches: New code deployed to production, not activated

Risk Management in Continuous Deployment:
  
  "More frequent smaller deployments are SAFER than infrequent big ones"
  
  The paradox: Teams that deploy 50 times/day have fewer major incidents than
  teams that deploy once/month.
  
  Reason: Small changes are:
  - Easier to review (< 100 lines vs 10,000 lines)
  - Easier to test (isolated change)
  - Easier to roll back (only 1 thing changed)
  - Easier to debug ("the change was this one commit")

Testing Philosophy for Continuous Deployment:
  
  TEST PYRAMID:
  
       /\
      /E2E\        ← Few. Critical paths only. < 50 tests.
     /──────\
    / INTEGR \     ← Some. Service-to-service interactions.
   /──────────\
  /  UNIT TESTS \  ← Many. Fast. Isolated. 1000s of tests.
  ──────────────────

  CONTRACT TESTING (Consumer-Driven):
    Service A and Service B test their interface independently.
    Pact framework: Consumer writes expected contract.
    Provider validates it can satisfy contracts.
    Enables independent deployment of services.
  
  SYNTHETIC MONITORING:
    Automated tests that run continuously in production.
    Test real user journeys (login, checkout, search) every few minutes.
    Alert immediately when production behavior degrades.
    Different from E2E tests (which run in CI against staging).

4. COMPARISON: DELIVERY VS DEPLOYMENT
================================================================================

ATTRIBUTE                 CONTINUOUS DELIVERY          CONTINUOUS DEPLOYMENT
─────────────────────────────────────────────────────────────────────────────
Definition               Always deployable             Always deployed
Human gate to prod        YES                          NO
Release decision          Business/product team        Engineering automation
Deployment frequency      When business decides        Every successful build
Risk profile              Lower (human review)         Higher (automated)
Team maturity needed       Medium                       High
Test coverage needed       High                         Very high
Feature flags needed       Recommended                  Required
Monitoring needed          Good                         Excellent
Rollback strategy          Manual or auto               Must be automated
Regulatory compliance      Easier                       Harder (audit trails)
Good for                   Regulated, enterprise        SaaS, startups, web
Examples                   Most enterprises             Netflix, Etsy, GitHub

5. APPROVAL GATES AND GOVERNANCE
================================================================================

Types of Gates in CD Pipelines:

  AUTOMATED GATES (no human needed):
  - All unit tests pass
  - Code coverage ≥ minimum threshold
  - Security scan shows no critical/high vulnerabilities
  - Performance tests show no regression
  - Contract tests pass
  - Container image scan passes
  
  SEMI-AUTOMATED GATES:
  - Quality Gate in SonarQube (automated check, but human-configured rules)
  - Policy-as-Code (OPA, Conftest) checks pass
  - DORA metrics still within acceptable range
  
  MANUAL GATES (human approval):
  - Product owner approves feature for release
  - QA engineer signs off on exploratory testing
  - Change Advisory Board (CAB) approval
  - Security team sign-off for sensitive changes
  - Legal/compliance review for regulatory features

GitHub Actions — Environment Protection Rules:
  Environments can require reviewers before deployment:
  
  # .github/workflows/deploy.yml
  jobs:
    deploy-to-production:
      environment:
        name: production
        url: https://myapp.example.com
      # Configured in GitHub Settings → Environments:
      # - Required reviewers: [alice, bob, security-team]
      # - Wait timer: 10 minutes (allows cancellation)
      # - Allowed branches: main only
      runs-on: ubuntu-latest
      steps:
        - name: Deploy
          run: ./scripts/deploy.sh production

GitLab CI — Protected Environments:
  # .gitlab-ci.yml
  deploy-production:
    stage: deploy
    environment:
      name: production
    when: manual  # Requires human click
    rules:
      - if: $CI_COMMIT_BRANCH == "main"
  
  # In GitLab UI: Environment → Settings → Required approvals (Premium)

Change Management Integration (ServiceNow):
  Pipeline integrates with ITSM for audit trails:
  
  # Simplified ServiceNow integration in pipeline
  create_change_request:
    script:
      - |
        # Create change request via ServiceNow API
        CR_NUMBER=$(curl -s -X POST \
          "https://company.service-now.com/api/now/table/change_request" \
          -H "Authorization: Bearer $SNOW_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{
            "short_description": "Deploy v'$VERSION' to production",
            "risk": "low",
            "type": "standard"
          }' | jq -r '.result.number')
        
        echo "CR_NUMBER=$CR_NUMBER" >> $GITHUB_ENV
  
  close_change_request:
    if: always()
    needs: [deploy-production]
    script:
      - |
        # Close change request after deployment
        STATUS=${{ needs.deploy-production.result == 'success' && 'successful' || 'unsuccessful' }}
        curl -s -X PATCH \
          "https://company.service-now.com/api/now/table/change_request/$CR_NUMBER" \
          -H "Authorization: Bearer $SNOW_TOKEN" \
          -d '{"close_code": "'$STATUS'"}'

6. CHANGE MANAGEMENT IN CD
================================================================================

Traditional Change Management vs DevOps Change Management:

  TRADITIONAL (ITIL):
  - Scheduled Change Advisory Board (CAB) meetings (weekly)
  - RFC (Request for Change) document prepared in advance
  - Peer review in CAB meeting
  - Approved → Implementation window
  - Post-implementation review
  - Total time: Days to weeks
  
  DEVOPS CHANGE MANAGEMENT:
  - Change record auto-created by pipeline
  - Risk assessed programmatically (coverage, test results, blast radius)
  - Standard/low-risk changes: Auto-approved
  - High-risk changes: Async review (no waiting for CAB meeting)
  - Audit trail: Pipeline logs
  - Total time: Minutes to hours

Risk-Based Approvals:

  LOW RISK (auto-approve):
    - Bug fixes
    - Performance improvements (no functionality change)
    - Internal code refactoring (no API change)
    - Configuration updates to non-critical systems
    - Dependency version patches
  
  MEDIUM RISK (async approval):
    - New features for internal users
    - API additions (backward compatible)
    - Database additions (no schema removal)
    - Changes to secondary systems
  
  HIGH RISK (synchronous CAB or security review):
    - Breaking API changes
    - Security and authentication changes
    - Database schema removals
    - Payment processing changes
    - Features affecting all users simultaneously
    - Infrastructure architectural changes

Deployment Windows:
  TRADITIONAL: Deploy only during "maintenance windows" (usually 2-4am Sunday)
  
  DEVOPS APPROACH: Deploy any time using:
  - Blue-Green deployment (zero downtime)
  - Canary releases (limit blast radius)
  - Automatic rollback (fast recovery)
  - Comprehensive monitoring (know immediately if something breaks)
  
  The maintenance window model persists in:
  - Organizations with high customer SLAs during business hours
  - Batch processing systems that need downtime windows
  - Hardware maintenance requiring actual downtime

The Two-Person Rule:
  For sensitive operations, require two people:
  - One to approve/review
  - One to execute
  
  Applies to: Production deployments in financial systems, healthcare,
  critical infrastructure.
  
  Implementation: Required reviewers on GitHub Environments, GitLab protected
  environments with multiple approval requirements.

7. INDUSTRY EXAMPLES
================================================================================

NETFLIX — Full Continuous Deployment:
  Context: 700+ microservices, 100M+ users globally
  
  How they do it:
  - Spinnaker: In-house CD platform, later open-sourced
  - Automated Canary Analysis (ACA): Statistical comparison of canary vs baseline
  - Each service team owns their pipeline, deployment, operations
  - Chaos Monkey, Simian Army: Proactive resilience testing
  - "You build it, you run it, you fix it" culture
  
  Result: Thousands of deployments per day, high availability (>99.99%)
  
  Key insight: "Continuous deployment forces you to build resilient systems"

AMAZON:
  Context: Multiple services (aws.amazon.com, retail, AWS services)
  
  How they do it:
  - "Two-Pizza Teams": Each service owned by small team
  - Each team has their own deployment pipeline
  - Apollo deployment system: Manages rollout across regions
  - IPIPE (internal): Automated canary deployment per availability zone
  
  Quote (Werner Vogels, CTO):
  "Failure is not a question of if, it's a question of when.
  Build systems that survive failures."

ETSY — Pioneered Continuous Deployment:
  Context: E-commerce, one of the first to publicly discuss CD
  
  How they do it:
  - Deployinator: Internal tool allowing any engineer to deploy
  - Feature flags: Every feature wrapped in a flag
  - Deploy 25-50 times per day
  - "IRC deployments": Engineers announce deployment in chat
  
  Key insight: "Deployment should be so easy that a new engineer can do it
  on their first day without breaking anything."

TYPICAL ENTERPRISE (Banks, Healthcare):
  Context: Regulated, risk-averse
  
  How they do it:
  - Continuous Delivery with CAB approval gate
  - ITIL-aligned change management
  - Monthly or quarterly release trains
  - Automated testing but manual production sign-off
  - Compliance evidence: Pipeline logs stored as audit artifacts
  
  Goal: Getting to weekly releases is a major achievement.
  
  Obstacle: Cultural resistance, legacy systems, compliance requirements
  
  Success story: ING Bank moved from quarterly releases to bi-weekly sprints
  with automated testing while maintaining regulatory compliance.

8. CHOOSING THE RIGHT APPROACH
================================================================================

Decision Framework:

  START HERE: Do you have regulatory/compliance requirements?
  ├─ YES → What is the compliance requirement?
  │        ├─ Requires documented human approval → Continuous DELIVERY only
  │        └─ Can use automated compliance controls? → Can do either
  └─ NO → Continue to next question
  
  How mature is your automated test suite?
  ├─ Low coverage, many flaky tests → Start with Continuous DELIVERY
  │  (build test confidence first)
  └─ High coverage, reliable tests → Continue
  
  Do you have feature flags?
  ├─ NO → Implement feature flags first
  └─ YES → Continue
  
  Do you have production monitoring with auto-alerting?
  ├─ NO → Build monitoring first
  └─ YES → Continue
  
  Do you have automated rollback capability?
  ├─ NO → Implement auto-rollback first
  └─ YES → Ready for Continuous DEPLOYMENT

Signals You're Ready for Continuous Deployment:
  ✓ 90%+ automated test coverage on critical paths
  ✓ Pipeline runs in < 15 minutes
  ✓ Pipeline success rate > 98%
  ✓ Feature flags for all incomplete features
  ✓ Monitoring in place, MTTD (mean time to detect) < 5 minutes
  ✓ MTTR < 1 hour for production incidents
  ✓ Team practices trunk-based development
  ✓ Rollback automated and tested
  ✓ Culture: "We own what we build and deploy"

Signals You're NOT Ready for Continuous Deployment:
  ✗ Manual testing still required to validate changes
  ✗ Pipeline takes > 30 minutes
  ✗ Flaky tests causing unreliable pipelines
  ✗ No feature flags
  ✗ Monitoring is reactive (know about problems from user complaints)
  ✗ Deployments are complex, multi-step manual processes
  ✗ Multiple long-lived branches

9. THE PATH FROM CI TO CD TO CONTINUOUS DEPLOYMENT
================================================================================

The Journey (no shortcuts):

  LEVEL 0: NO CI
  ──────────────
  Developers manually test and deploy
  Release every 6-12 months
  Deployment is a major event
  
  LEVEL 1: CI IMPLEMENTED
  ────────────────────────
  Automated build and unit tests on every commit
  Faster feedback on broken code
  Still deploying manually (scripts or click-ops)
  
  LEVEL 2: CONTINUOUS DELIVERY — STAGING
  ───────────────────────────────────────
  Automated deployment to staging
  Integration tests in staging
  Production deployment still manual
  Goal: Weekly or bi-weekly releases
  
  LEVEL 3: CONTINUOUS DELIVERY — PRODUCTION
  ──────────────────────────────────────────
  Automated deployment to production
  Manual approval gate before production
  Deployment is routine, not scary
  Goal: Daily or on-demand releases
  
  LEVEL 4: CONTINUOUS DEPLOYMENT
  ───────────────────────────────
  No manual gate
  Every passing build goes to production
  Feature flags, monitoring, auto-rollback in place
  Goal: Multiple deployments per day
  
  LEVEL 5: PROGRESSIVE DELIVERY
  ──────────────────────────────
  Continuous Deployment + automated canary analysis
  Metrics-based auto-promotion (Flagger, Argo Rollouts)
  A/B testing built into deployment pipeline
  Goal: Continuous innovation with built-in risk controls

Common Anti-Patterns to Avoid on This Journey:

  1. "Big Bang" CD Adoption:
     Don't try to implement everything at once.
     Start with CI, then staging automation, then production.
  
  2. Skipping Test Maturity:
     Teams that rush to automate production deployment without solid tests
     experience high failure rates and lose trust in CD.
  
  3. Neglecting Rollback:
     CD without rollback is high-risk. Implement rollback early.
  
  4. Keeping Long-Lived Branches:
     CD is impossible if your "release" branch is weeks behind main.
     Adopt trunk-based development gradually.
  
  5. Not Instrumenting Deployments:
     If you don't measure deployment frequency and failure rate, you can't
     improve them. Add metrics from day one.

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between Continuous Delivery and Continuous Deployment?
A: Both are built on Continuous Integration. 
   
   Continuous Delivery means software is always in a deployable state. After
   tests pass and staging validation succeeds, a human approves the final step
   of deploying to production. The VALUE is that deployment becomes routine and
   risk-free, but the decision remains with the business.
   
   Continuous Deployment goes one step further — the human approval gate is
   removed. Every change that passes all automated tests goes directly to
   production, automatically.
   
   Analogy: CD means your car is always fueled and ready to drive. You still
   decide when and where to go. Continuous Deployment means the car drives
   itself to the destination whenever ready.

Q2: When would you choose Continuous Delivery over Continuous Deployment?
A: Several situations favor Continuous Delivery with a manual gate:
   - Regulatory compliance requiring documented human approval (SOX, FDA, HIPAA)
   - Business coordination needs (marketing campaigns, support team readiness)
   - Low test confidence (still building automated test coverage)
   - High-risk changes (pricing changes, security modifications)
   - Customer-facing breaking changes requiring communication
   
   The choice isn't permanent — most teams start with Continuous Delivery and
   work toward Continuous Deployment as their test suite, monitoring, and
   culture matures.

Q3: How does Continuous Deployment affect your approach to testing?
A: Continuous Deployment fundamentally changes testing requirements:
   
   1. Test coverage must be comprehensive — you can't deploy without confidence
      in your tests, so coverage requirements increase significantly
   
   2. Tests must be reliable — flaky tests break the automated pipeline, so
      you invest heavily in test reliability
   
   3. Testing shifts earlier (shift-left) — issues caught post-deployment are
      more expensive than pre-deployment
   
   4. Contract testing becomes essential — in microservices, services must be
      able to deploy independently, requiring consumer-driven contract testing
   
   5. Synthetic monitoring becomes a form of continuous testing — tests running
      in production 24/7 to validate real behavior
   
   6. The test strategy must cover not just code correctness but production
      readiness (performance, security, configuration)

Q4: How do you handle feature releases that span multiple deploys with Continuous Deployment?
A: This is solved with feature flags (also called feature toggles):
   
   When building a large feature that takes multiple weeks:
   1. Write code with feature wrapped in a flag: if (featureEnabled("new-ui"))
   2. Deploy code to production with flag disabled (dark launch)
   3. Continue merging incomplete work to main — flag hides it from users
   4. When complete: enable flag for internal testers, then 1%, then 100%
   5. After full rollout: remove the flag and the old code path
   
   This decouples deployment (technical) from release (business). Developers
   deploy whenever they want; product team releases when ready.
   
   Tools: LaunchDarkly, Unleash, AWS AppConfig, Flagsmith.

Q5: How do you maintain audit trails with Continuous Deployment for compliance?
A: This is about replacing manual processes with automated equivalents:
   
   - Every deployment creates a timestamped record: who triggered it (git
     author + pipeline), what changed (commit SHA, diff), test results,
     deployment time, deployment outcome
   - Change records auto-created in ITSM (ServiceNow, Jira)
   - Pipeline logs stored as immutable artifacts
   - Git history is an immutable record of every change
   - For extra-sensitive operations: require two-person approval in the
     pipeline even for automated deployments (approver + executor are different)
   
   Key message: "Continuous Deployment can actually provide BETTER audit trails
   than manual processes, because everything is automated and logged consistently."

11. QUICK REFERENCE CHEAT SHEET
================================================================================

CONTINUOUS DELIVERY:
  - Every build is potentially shippable
  - Manual gate before production
  - Business decides when to release
  - Works with regulated industries
  - Requires: CI, staging, automated tests

CONTINUOUS DEPLOYMENT:
  - Every passing build goes to production automatically
  - No manual gate
  - Requires: Feature flags, monitoring, auto-rollback, high test confidence
  - Used by: Netflix, Amazon, GitHub, Etsy

CI → CD → Continuous Deployment Journey:
  No CI → CI → CD to Staging → CD + Manual Gate → Full Continuous Deployment

Prerequisites for Continuous Deployment (short list):
  1. Comprehensive automated tests (> 90% critical path coverage)
  2. Feature flags
  3. Production monitoring + alerting (MTTD < 5 min)
  4. Automated rollback
  5. Trunk-based development
  6. Culture of ownership ("you build it, you run it")

Gates in CD:
  Automated gates: test coverage, security scan, performance regression
  Manual gates: product owner approval, compliance sign-off, CAB
  Semi-automated: SonarQube quality gates, policy-as-code

Industry Examples:
  Netflix: Full CD — thousands/day, Spinnaker, chaos engineering
  Amazon: Full CD — every 11 seconds, per-service pipelines
  Enterprise bank: Continuous Delivery — automated testing, manual prod approval

Key Quote:
  "If it hurts, do it more often."
  — Jez Humble, Continuous Delivery (2010)
