1. DEPENDENCY SCANNING (SCA) OVERVIEW
================================================================================

Software Composition Analysis (SCA) identifies vulnerabilities in third-party
dependencies (open source libraries).

Why It Matters:
  Modern software is 80-90% open source code.
  Log4Shell (CVE-2021-44228): Critical RCE in Log4j, used by thousands of apps.
  Apps needed to find and patch ALL usage within hours. SCA tools made this possible.

What SCA Scans:
  - Language dependencies: requirements.txt, package.json, pom.xml, go.mod
  - Transitive dependencies: not just what you import, but what your deps import
  - License compliance: GPL licenses in proprietary software = legal risk

CVE Databases:
  NVD     National Vulnerability Database (NIST)
  OSS Index (Sonatype)
  GitHub Advisory Database
  Snyk Vulnerability Database

Key Findings:
  CVE-ID:      Common Vulnerabilities and Exposures identifier
  CVSS Score:  0.0-10.0 severity score (Critical ≥ 9.0)
  Affected:    Which versions are vulnerable
  Fixed:       Version that patches the vulnerability
  PoC:         Is a proof-of-concept exploit available?

Remediation Priority:
  Critical + PoC exploit available → Fix immediately
  Critical, no PoC → Fix within days
  High → Fix within weeks
  Medium/Low → Fix in regular maintenance cycle

2. SNYK
================================================================================

What is Snyk?
  Commercial SCA + SAST + Container + IaC scanning platform.
  Developer-first focus (IDE plugin, fast, low friction).
  Free tier available.
  
  Integrations: GitHub, GitLab, Bitbucket, Jenkins, CLI, IDE plugins.

Snyk CLI:
  # Install:
  npm install -g snyk
  # or
  brew install snyk
  
  # Authenticate:
  snyk auth
  
  # Test dependencies (Python):
  snyk test --file=requirements.txt
  
  # Test with exit code (for CI):
  snyk test --severity-threshold=high --file=requirements.txt
  # Exits non-zero if HIGH or CRITICAL found
  
  # Test Node.js:
  snyk test --file=package.json
  
  # Test Java (Maven):
  snyk test --file=pom.xml
  
  # Container scan:
  snyk container test myapp:latest
  
  # IaC scan:
  snyk iac test --severity-threshold=high terraform/
  
  # Monitor (send results to Snyk dashboard, track over time):
  snyk monitor --project-name=payment-service

Snyk in GitHub Actions:
  name: Snyk Security Scan
  
  on:
    push:
      branches: [main]
    pull_request:
  
  jobs:
    snyk:
      runs-on: ubuntu-latest
      steps:
      - uses: actions/checkout@v4
      
      - name: Run Snyk SCA (dependencies)
        uses: snyk/actions/python@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          command: test
          args: --severity-threshold=high --sarif-file-output=snyk-oss.sarif
        continue-on-error: true   # Don't fail CI, let SARIF upload handle it
      
      - name: Run Snyk Container Scan
        uses: snyk/actions/docker@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          image: myapp:latest
          args: --severity-threshold=high --sarif-file-output=snyk-container.sarif
        continue-on-error: true
      
      - name: Upload Snyk results to GitHub Security
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: snyk-oss.sarif

Snyk Fix:
  # Automatically open PRs to fix vulnerabilities:
  snyk fix     # Interactive fix suggestions
  snyk fix --dry-run  # Preview changes
  
  # Generate SBOM (Software Bill of Materials):
  snyk sbom --format=cyclonedx1.4+json > sbom.json

3. OWASP DEPENDENCY-CHECK
================================================================================

What is OWASP Dependency-Check?
  Open-source SCA tool.
  Checks project dependencies against NVD CVE database.
  No registration required. Good for offline/air-gapped environments.

CLI Usage:
  # Download and run:
  wget https://github.com/jeremylong/DependencyCheck/releases/download/v9.0.0/dependency-check-9.0.0-release.zip
  unzip dependency-check-9.0.0-release.zip
  
  # Scan project:
  ./dependency-check/bin/dependency-check.sh \
    --project "payment-service" \
    --scan /path/to/project \
    --format HTML \
    --format JSON \
    --out reports/ \
    --failOnCVSS 7.0 \    # Fail if CVSS >= 7.0 found
    --nvdApiKey <api-key>  # NVD API key for faster updates

Maven Integration:
  <!-- pom.xml: -->
  <plugin>
    <groupId>org.owasp</groupId>
    <artifactId>dependency-check-maven</artifactId>
    <version>9.0.0</version>
    <configuration>
      <failBuildOnCVSS>7</failBuildOnCVSS>
      <formats>
        <format>HTML</format>
        <format>JSON</format>
      </formats>
    </configuration>
    <executions>
      <execution>
        <goals><goal>check</goal></goals>
      </execution>
    </executions>
  </plugin>
  
  # Run:
  mvn dependency-check:check

4. GITHUB DEPENDABOT
================================================================================

What is Dependabot?
  GitHub's built-in automated dependency update and vulnerability alerting.
  Free for all GitHub repos (public and private).

Two Features:
  Dependabot Alerts:    Notify when a dependency has a known CVE.
  Dependabot Updates:   Automatically open PRs to update dependencies.

Configuration:
  # .github/dependabot.yml:
  version: 2
  updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "weekly"    # daily | weekly | monthly
    open-pull-requests-limit: 5
    ignore:
    - dependency-name: "boto3"
      versions: ["1.x"]    # Don't auto-update major versions
    labels:
    - "security"
    - "dependencies"
    reviewers:
    - "security-team"
  
  - package-ecosystem: "docker"
    directory: "/"
    schedule:
      interval: "weekly"
  
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"

Dependabot Security Updates:
  When a CVE is found in a dependency, Dependabot:
  1. Creates a security advisory alert
  2. Automatically opens a PR with the fix (if a fixed version exists)
  3. Labels it with "security"
  
  Enable in GitHub Settings → Security → Dependabot:
  - Dependabot alerts: ON
  - Dependabot security updates: ON (auto-PRs for fixes)
  - Dependabot version updates: ON (weekly PRs for all deps)

5. SECRETS IN PIPELINES
================================================================================

The Secrets Problem in CI/CD:
  CI/CD pipelines need credentials to:
  - Push Docker images to registries
  - Deploy to AWS/GCP/Azure
  - Access databases, APIs
  - Sign artifacts
  
  These credentials must be available in the pipeline but NEVER exposed.

Bad Patterns (DO NOT DO):
  ❌ Hardcode in Dockerfile: ENV DB_PASSWORD=mypassword
  ❌ Hardcode in source code: api_key = "sk-abc123..."
  ❌ Store in plain text .env file committed to Git
  ❌ Print to CI logs (some tools auto-print env vars)
  ❌ Use long-lived static credentials (rotate risk)

Good Patterns:

Pattern 1: CI Platform Native Secrets
  GitHub Actions: Settings → Secrets and Variables → Actions secrets
  Accessed as: ${{ secrets.MY_SECRET }}
  GitLab CI: Settings → CI/CD → Variables (Masked + Protected)
  Accessed as: $MY_SECRET
  
  Benefits: Simple, integrated, secrets masked in logs.
  Limitations: Can't rotate centrally, hard to audit across repos.

Pattern 2: OIDC (Best for Cloud Credentials — No Long-Lived Keys)
  GitHub Actions → AWS using OIDC:
  
  # No stored AWS keys! GitHub gets short-lived token via OIDC.
  - name: Configure AWS credentials
    uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789:role/github-actions-role
      aws-region: us-east-1
  # GitHub Actions gets a 1-hour credential. No keys to rotate or leak.
  
  # AWS IAM Identity Provider must trust GitHub's OIDC:
  # Provider URL: https://token.actions.githubusercontent.com
  # Audience: sts.amazonaws.com
  
  # IAM Role trust policy:
  {
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:ref:refs/heads/main"
      }
    }
  }

Pattern 3: HashiCorp Vault (See Section 6)

Pattern 4: Cloud Secrets Managers
  AWS Secrets Manager, GCP Secret Manager, Azure Key Vault.
  Applications and pipelines retrieve secrets at runtime.
  Centralized rotation (change in one place, all consumers get updated value).

If a Secret is Leaked:
  1. ROTATE IMMEDIATELY (before investigation):
     aws iam delete-access-key --access-key-id AKIAIOSFODNN7EXAMPLE
     aws iam create-access-key  (new key)
  
  2. Audit: Was the key used maliciously?
     aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,...
  
  3. Remove from Git history:
     git filter-repo --path-glob '*.env' --invert-paths
     git push --force-with-lease origin main  (requires unprotecting branch)
     
     Or use BFG Repo Cleaner:
     java -jar bfg.jar --delete-files .env
     git reflog expire --expire=now --all && git gc --prune=now --aggressive
     git push --force

6. HASHICORP VAULT
================================================================================

What is HashiCorp Vault?
  Enterprise-grade secrets management.
  Centralized: one place to manage all secrets.
  Dynamic secrets: Generate on demand, auto-expire.
  Audit log: Every secret access recorded.

Vault Secrets Engines:
  KV v2:        Static key-value secrets (API keys, passwords). Versioned.
  AWS:          Dynamic IAM credentials generated on demand (auto-expire in 1 hour).
  Database:     Dynamic DB credentials generated per request.
  PKI:          Issue TLS certificates on demand.
  SSH:          Signed SSH certificates for server access.

KV v2 (Static Secrets):
  # Enable KV v2:
  vault secrets enable -path=secret kv-v2
  
  # Write secret:
  vault kv put secret/payment-service/prod \
    db_password="s3cur3p@ss" \
    stripe_key="sk_live_abc123"
  
  # Read secret:
  vault kv get secret/payment-service/prod
  vault kv get -field=db_password secret/payment-service/prod
  
  # Read with version:
  vault kv get -version=2 secret/payment-service/prod

Dynamic Database Credentials:
  # Configure DB secrets engine:
  vault secrets enable database
  vault write database/config/my-postgres \
    plugin_name=postgresql-database-plugin \
    connection_url="postgresql://{{username}}:{{password}}@postgres:5432/mydb" \
    allowed_roles="app-role" \
    username="vault" \
    password="vaultpassword"
  
  # Define role with TTL:
  vault write database/roles/app-role \
    db_name=my-postgres \
    creation_statements="CREATE ROLE '{{name}}' WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO '{{name}}';" \
    default_ttl="1h" \
    max_ttl="24h"
  
  # App requests credentials (valid for 1 hour, then auto-expire):
  vault read database/creds/app-role
  # Returns: username=v-app-role-xyz123, password=<generated>

Vault in Kubernetes:
  # Vault Agent Sidecar (auto-inject secrets as files):
  # Annotate pod to inject Vault secrets:
  annotations:
    vault.hashicorp.com/agent-inject: "true"
    vault.hashicorp.com/role: "payment-service"
    vault.hashicorp.com/agent-inject-secret-db: "secret/data/payment-service/prod"
    vault.hashicorp.com/agent-inject-template-db: |
      {{- with secret "secret/data/payment-service/prod" -}}
      export DB_PASSWORD="{{ .Data.data.db_password }}"
      export STRIPE_KEY="{{ .Data.data.stripe_key }}"
      {{- end }}
  
  # Secret written to /vault/secrets/db — container sources it at startup.

7. EXTERNAL SECRETS OPERATOR
================================================================================

What is External Secrets Operator (ESO)?
  Kubernetes operator that syncs secrets from external managers INTO K8s Secrets.
  App accesses native K8s Secret as usual.
  Source of truth: AWS Secrets Manager / Vault / GCP SM / Azure Key Vault.

Architecture:
  AWS Secrets Manager → [ESO] → K8s Secret → Pod env var / volume mount

ESO Setup:
  helm repo add external-secrets https://charts.external-secrets.io
  helm install external-secrets \
    external-secrets/external-secrets \
    --namespace external-secrets \
    --create-namespace

SecretStore (connects to AWS Secrets Manager):
  apiVersion: external-secrets.io/v1beta1
  kind: ClusterSecretStore
  metadata:
    name: aws-secrets-manager
  spec:
    provider:
      aws:
        service: SecretsManager
        region: us-east-1
        auth:
          jwt:
            serviceAccountRef:
              name: external-secrets-sa
              namespace: external-secrets

ExternalSecret (defines what to sync):
  apiVersion: external-secrets.io/v1beta1
  kind: ExternalSecret
  metadata:
    name: payment-service-secrets
    namespace: payment
  spec:
    refreshInterval: 1h    # Re-sync every hour (catches rotations)
    secretStoreRef:
      name: aws-secrets-manager
      kind: ClusterSecretStore
    target:
      name: payment-service-secrets    # K8s Secret name created
      creationPolicy: Owner
    data:
    - secretKey: DB_PASSWORD           # Key in K8s Secret
      remoteRef:
        key: payment-service/prod      # AWS Secrets Manager path
        property: db_password          # Field within the secret JSON
    - secretKey: STRIPE_API_KEY
      remoteRef:
        key: payment-service/prod
        property: stripe_key

8. CONTAINER IMAGE SCANNING
================================================================================

Why Scan Container Images?
  Images contain OS packages, language runtimes, dependencies.
  All can have CVEs. Running a vulnerable image = running vulnerable software.
  
  What's scanned:
  - OS packages (apt, yum, apk installed packages)
  - Language packages (pip, npm, maven, gem)
  - Application files (JAR manifests, package.json)
  - Configuration (exposed ports, running as root, etc.)

When to Scan:
  After build (pre-push): Block push of vulnerable images.
  Registry-side: AWS ECR, Docker Hub scan on push automatically.
  Pre-deploy: Scan image again at deployment time (CVE may have been discovered since build).
  Running containers: Continuously scan running pods (Snyk/Aqua).

Key Tools:
  Trivy (Aqua Security):     Open source, comprehensive, fast. Most popular.
  Grype (Anchore):           Open source, similar to Trivy.
  Snyk Container:            Commercial, integrates with Snyk platform.
  Clair (CoreOS/Red Hat):    Open source, used by Quay.io.
  AWS ECR Scanning:          Built-in with ECR (powered by Clair → Inspector).

9. TRIVY
================================================================================

What is Trivy?
  Open-source vulnerability scanner by Aqua Security.
  Scans: container images, filesystems, git repos, IaC, SBOM.
  Extremely fast and easy to use.
  The de-facto standard for container scanning.

Installation:
  brew install trivy
  # or
  wget https://github.com/aquasecurity/trivy/releases/download/v0.49.1/trivy_0.49.1_Linux-64bit.deb
  dpkg -i trivy_0.49.1_Linux-64bit.deb

Basic Usage:
  # Scan Docker image:
  trivy image nginx:latest
  
  # Scan image, only show HIGH and CRITICAL:
  trivy image --severity HIGH,CRITICAL nginx:latest
  
  # Exit non-zero if vulnerabilities found (for CI):
  trivy image --exit-code 1 --severity CRITICAL nginx:latest
  
  # Exit non-zero on HIGH or CRITICAL:
  trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest
  
  # Only exit non-zero if fixed version available (don't fail on unfixable):
  trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed myapp:latest
  
  # Output as JSON:
  trivy image --format json --output trivy-results.json myapp:latest
  
  # Output as SARIF (GitHub Security):
  trivy image --format sarif --output trivy-results.sarif myapp:latest
  
  # Scan filesystem (local project):
  trivy fs --severity HIGH,CRITICAL .
  
  # Scan IaC (Terraform/K8s):
  trivy config terraform/
  trivy config k8s/

Trivy in GitHub Actions:
  name: Container Security Scan - Trivy
  
  on:
    push:
      branches: [main]
  
  jobs:
    trivy:
      runs-on: ubuntu-latest
      steps:
      - uses: actions/checkout@v4
      
      - name: Build Docker image
        run: docker build -t myapp:${{ github.sha }} .
      
      - name: Scan with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: 'myapp:${{ github.sha }}'
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          ignore-unfixed: true
          exit-code: '1'   # Fail build on findings
      
      - name: Upload Trivy SARIF to GitHub Security
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: 'trivy-results.sarif'

Trivy .trivyignore (suppress known false positives):
  # .trivyignore:
  CVE-2022-12345    # Known false positive: not exploitable in our context
  CVE-2023-67890    # Accepted risk: fix not available, mitigated by network policy
  
  # Note: Add justification comments for auditability.

Container Security Best Practices (Trivy helps verify):
  
  1. Use minimal base images:
     ❌ FROM ubuntu:22.04   (500+ packages, large attack surface)
     ✅ FROM python:3.11-slim  (minimal, fewer packages)
     ✅ FROM gcr.io/distroless/python3  (no shell, no package manager — hardest to exploit)
  
  2. Don't run as root:
     FROM python:3.11-slim
     RUN groupadd --gid 1001 app && useradd --uid 1001 --gid app app
     USER app
  
  3. Keep base images updated:
     Regular rebuilds pick up patched base images.
     Dependabot can update Dockerfile FROM versions.
  
  4. Multi-stage builds (only ship what's needed):
     FROM golang:1.21 AS builder
     COPY . .
     RUN go build -o app
     
     FROM gcr.io/distroless/base-debian11
     COPY --from=builder /app /app
     CMD ["/app"]
     # Result: No Go toolchain in final image, much smaller, fewer vulns

SBOM (Software Bill of Materials):
  Manifest of all components in an image.
  Required by some regulations (US Executive Order 14028, EU Cyber Resilience Act).
  
  # Generate SBOM with Trivy:
  trivy image --format cyclonedx --output sbom.json myapp:latest
  trivy image --format spdx-json --output sbom.spdx.json myapp:latest

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: How do you manage secrets in a Kubernetes environment?
A: Multiple layers: prevention, secure storage, access control.
   
   What NOT to do:
   Don't use K8s Secrets directly for sensitive data.
   K8s Secrets are just base64-encoded (not encrypted by default).
   Base64 is NOT encryption — echo "dXNlcm5hbWU=" | base64 -d → "username".
   
   Recommended approaches (in order of preference):
   
   Option 1: External Secrets Operator (recommended):
   Store secrets in AWS Secrets Manager / HashiCorp Vault.
   ESO syncs them into K8s Secrets automatically.
   Source of truth stays in the secrets manager.
   Rotation: Change in AWS SM → ESO re-syncs within 1h → no app restart needed.
   
   Option 2: Sealed Secrets:
   Encrypt secrets with a cluster-public-key.
   Store encrypted SealedSecret in Git (safe to commit).
   Only the cluster can decrypt with its private key.
   Good for GitOps (everything in Git, including encrypted secrets).
   
   Option 3: HashiCorp Vault Agent Sidecar:
   Vault Agent runs as a sidecar, injects secrets as files/env vars.
   Applications never talk to Vault directly.
   Dynamic secrets (DB credentials) expire automatically.
   
   Also important:
   - Enable K8s Secret encryption at rest (etcd encryption)
   - RBAC: Only the app's ServiceAccount can read its secrets
   - Audit: Log all secret access (Vault audit log, CloudTrail for AWS SM)

Q2: Walk me through a container image security strategy from build to runtime.
A: Defense in depth across the full image lifecycle:
   
   Build time:
   - Use minimal base images (slim, distroless, alpine)
   - Multi-stage builds: builder stage vs final runtime stage
   - Don't install debugging tools in production images
   - Run Trivy in CI: fails build on HIGH/CRITICAL vulnerabilities
   - Sign images with cosign (image signing/verification)
   
   Push to registry:
   - AWS ECR / Docker Hub / GCR — scan on push (automatic in ECR)
   - Image remains in registry, continuously re-scanned as new CVEs emerge
   
   Pre-deploy:
   - Trivy scan in CD pipeline (re-scan at deployment time — new CVEs may have appeared)
   - Kyverno/OPA policy: Only allow images from trusted registries
     Example: Block images from Docker Hub, only allow ECR
   - Kyverno: Require all images to have passed security scan (image attestation)
   
   Runtime:
   - Falco: Detect anomalous behavior (shells spawned, unexpected writes)
   - Kubernetes security contexts: runAsNonRoot, readOnlyRootFilesystem, drop capabilities
   - Network policies: Only allow expected ingress/egress traffic
   - Continuous scanning: AWS Inspector, Snyk/Aqua re-scan running pods

Q3: What is the difference between Snyk and Trivy?
A: Both are security scanning tools with different strengths:
   
   Trivy:
   - Open source, free, very fast
   - Best for: Container image scanning (OS packages + language packages)
   - Also: IaC scanning (Terraform, K8s YAML), filesystem, git repos
   - Simpler: single binary, no registration needed
   - Output: SARIF, JSON, table
   - Limitations: Free = community support, fewer integrations than commercial Snyk
   
   Snyk:
   - Commercial platform (free tier available)
   - Best for: SCA (dependencies in code), developer workflow integration
   - Also: Container, IaC, SAST
   - Developer-friendly: IDE plugins, PR checks, fix suggestions, fix PRs
   - Deeper SCA: Better at transitive dependencies, more languages
   - Fix guidance: "Upgrade X from 1.0 to 1.2 to fix CVE-2023-XXXX"
   - Dashboard: Track vulnerabilities over time, org-level visibility
   
   Use both in practice:
   - Trivy: Fast container scan in CI (seconds, no API key needed)
   - Snyk: SCA in PR checks, developer feedback, org vulnerability tracking

Q4: How do you prevent secrets from being committed to Git?
A: Multi-layer prevention:
   
   1. Pre-commit hooks (developer side):
      Install detect-secrets or gitleaks as a pre-commit hook.
      Scans staged files for patterns (AWS keys, SSH keys, passwords, tokens).
      Blocks the commit if a secret is detected.
      
      # .pre-commit-config.yaml:
      repos:
      - repo: https://github.com/Yelp/detect-secrets
        rev: v1.4.0
        hooks:
        - id: detect-secrets
          args: ['--baseline', '.secrets.baseline']
      
      # Or gitleaks:
      - repo: https://github.com/gitleaks/gitleaks
        rev: v8.18.0
        hooks:
        - id: gitleaks
   
   2. CI scanning (repo-side):
      GitHub Secret Scanning: Built-in, free for public repos, free with GHAS.
      Scans all commits and PRs for known secret patterns.
      Alert types: Key-based (AWS, Stripe, GitHub tokens) + custom patterns.
      
      TruffleHog in CI:
      # Scan current PR for new secrets:
      trufflehog git --since-commit ${{ github.event.pull_request.base.sha }} \
        --only-verified \
        file:///repo
   
   3. Branch protection rules:
      Require secret scanning checks to pass before merging.
      Block pushing if GitHub Secret Scanning alert is open.
   
   4. Developer education:
      Use .env files locally (never committed — in .gitignore)
      Use environment variables or secrets managers in CI
      NEVER use real credentials in tests — use mocks/stubs

Q5: What is SBOM and why is it becoming increasingly important?
A: SBOM stands for Software Bill of Materials — a formal inventory of all components
   in a software artifact (application, container image).
   
   Analogous to a food nutrition label: lists all ingredients and their versions.
   
   Contents:
   - All direct and transitive dependencies with versions
   - License information for each component
   - Known vulnerabilities (linked CVEs)
   - Component provenance (where it came from)
   
   Why it matters:
   
   1. Supply chain security (biggest driver):
      After Log4Shell, SolarWinds, and XZ Utils attacks, organizations need to
      answer "Are we using component X?" within hours.
      Without SBOM: manual inventory of 50 repos × 100 dependencies each.
      With SBOM: query your SBOM registry in seconds.
   
   2. Regulatory requirements:
      US Executive Order 14028 (2021): Federal software vendors must provide SBOM.
      EU Cyber Resilience Act: Requires SBOM for products sold in EU.
      FDA: Medical device software requires SBOM.
   
   3. License compliance:
      Open source licenses have obligations (GPL copyleft, attribution requirements).
      SBOM enables automated license compliance scanning.
   
   Formats:
   CycloneDX: OWASP project, JSON/XML
   SPDX:      Linux Foundation standard, JSON/YAML/RDF
   SWID:      ISO standard, XML
   
   Generation tools:

SECRETS IN CI/CD (BEST TO WORST):
  OIDC (no keys!)       → GitHub Actions → AWS/GCP/Azure via OIDC
  Vault dynamic creds   → On-demand, short-lived, auto-expire
  Cloud secrets manager → AWS SM / GCP SM / Azure KV
  CI native secrets     → GitHub Actions secrets, GitLab variables
  ❌ Long-lived keys     → Rotate, rotation risk
  ❌ Hardcoded in code   → Never

  ClusterSecretStore → defines connection to AWS SM / Vault
  ExternalSecret     → defines what to sync into K8s Secret
  Pod                → reads from K8s Secret (env var or volume mount)
