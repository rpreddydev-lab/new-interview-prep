1. WHAT IS GITHUB ACTIONS?
================================================================================

GitHub Actions is a CI/CD and automation platform integrated directly into
GitHub. It allows automating workflows in response to GitHub events.

Launched: August 2019 (public)

Key Characteristics:
  - YAML-based pipeline configuration
  - Native GitHub integration (PRs, issues, releases, deployments)
  - GitHub-hosted runners (Linux, macOS, Windows) — no infrastructure required
  - Self-hosted runners (your own VMs or containers)
  - 15,000+ pre-built actions in GitHub Marketplace
  - Free for public repos, paid per-minute for private repos

Pricing (for private repos):
  GitHub-hosted Linux: $0.008/minute
  GitHub-hosted Windows: $0.016/minute
  GitHub-hosted macOS: $0.08/minute
  
  Free tier: 2,000 minutes/month (Free plan), 3,000 (Pro), 50,000 (Team)
  Self-hosted runners: Always free (you pay for your own compute)

GitHub Actions is NOT just CI/CD — it's a general automation platform:
  - Auto-label PRs, triage issues
  - Auto-merge dependency updates (Dependabot)
  - Publish packages to npm, Maven, PyPI
  - Deploy to any cloud or Kubernetes
  - Generate and publish documentation
  - Send notifications

2. CORE CONCEPTS
================================================================================

WORKFLOW:
  An automated process defined in a YAML file.
  Stored in: .github/workflows/*.yml
  A repository can have multiple workflows.
  Each workflow is independent.

EVENT (TRIGGER):
  What causes a workflow to run.
  Examples: push, pull_request, schedule, workflow_dispatch (manual), release

JOB:
  A group of steps that run on the same runner (machine).
  Jobs run in parallel by default.
  Use 'needs:' to create sequential dependencies.

STEP:
  An individual task within a job.
  Either:
  1. An Action (uses: owner/action@version)
  2. A shell command (run: npm test)
  Steps within a job run sequentially.

ACTION:
  A reusable unit of automation.
  Can be a Docker container action, JavaScript action, or composite action.
  From Marketplace, your own repo, or inline.

RUNNER:
  The server where jobs execute.
  GitHub-hosted: ubuntu-latest, windows-latest, macos-latest
  Self-hosted: Your own infrastructure, labeled for targeting.

ARTIFACT:
  Files generated in a workflow and saved for later use or download.
  
CONTEXT:
  Objects providing workflow information: github, env, vars, secrets, 
  runner, job, steps, strategy, matrix, needs, inputs.

3. WORKFLOW YAML ANATOMY
================================================================================

Full structure of a workflow file:

  name: Workflow Name          # Optional display name (shown in GitHub UI)
  
  run-name: "Deploy ${{ github.ref_name }}"  # Dynamic run name (optional)
  
  on: { ... }                  # Triggers (required)
  
  permissions: { ... }         # Token permissions (security best practice)
  
  env:                         # Global environment variables
    GLOBAL_VAR: value
  
  defaults:                    # Default run configuration
    run:
      shell: bash
      working-directory: ./backend
  
  concurrency:                 # Prevent concurrent runs
    group: ${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true
  
  jobs:
    job-id:                    # Unique job identifier
      name: Human readable name
      runs-on: ubuntu-latest
      needs: [other-job]       # Dependencies
      if: condition            # Conditional execution
      timeout-minutes: 30
      continue-on-error: false
      
      permissions: { ... }     # Job-level token permissions
      
      environment:             # Deployment environment
        name: production
        url: https://example.com
      
      concurrency:             # Job-level concurrency
        group: deploy-prod
      
      strategy:                # Matrix configuration
        matrix: { ... }
        fail-fast: true
        max-parallel: 4
      
      env:                     # Job-level environment variables
        JOB_VAR: value
      
      services:                # Docker services (like docker-compose)
        postgres: { ... }
      
      outputs:                 # Pass data to dependent jobs
        my-output: ${{ steps.step-id.outputs.result }}
      
      steps:
        - name: Step name
          id: step-id          # Reference this step's outputs
          uses: action@version # OR
          run: command         # Can't use both
          with: { ... }        # Action inputs
          env: { ... }         # Step-level env vars
          if: condition        # Conditional step
          continue-on-error: false
          timeout-minutes: 5
          working-directory: ./subdir

4. TRIGGERS (EVENTS)
================================================================================

PUSH TRIGGER:
  on:
    push:
      branches: [ main, develop, 'release/**' ]
      branches-ignore: [ 'dependabot/**' ]
      paths:
        - 'src/**'
        - 'pom.xml'
      paths-ignore:
        - '**.md'
        - 'docs/**'
      tags:
        - 'v*'

PULL REQUEST TRIGGER:
  on:
    pull_request:
      branches: [ main ]
      types:
        - opened          # New PR
        - synchronize     # New commit pushed to PR
        - reopened        # Closed PR reopened
        - ready_for_review # Draft → Ready
      paths: [ 'src/**' ]

SCHEDULE TRIGGER (CRON):
  on:
    schedule:
      - cron: '0 2 * * *'    # 2 AM UTC every day
      - cron: '0 9 * * 1-5'  # 9 AM UTC every weekday
  
  Note: Cron runs are in UTC. Scheduled workflows only run on default branch.

MANUAL TRIGGER (workflow_dispatch):
  on:
    workflow_dispatch:
      inputs:
        environment:
          description: 'Deployment target'
          required: true
          type: choice
          options: [ staging, production ]
        version:
          description: 'Version to deploy'
          required: true
          type: string
        dry-run:
          description: 'Dry run only'
          required: false
          type: boolean
          default: false
  
  # Access inputs: ${{ inputs.environment }}

RELEASE TRIGGER:
  on:
    release:
      types: [ published, created ]
      # Fires when a release is published in GitHub

WORKFLOW_CALL (Reusable workflows):
  on:
    workflow_call:
      inputs:
        java-version:
          required: true
          type: string
      secrets:
        registry-token:
          required: true
      outputs:
        image-tag:
          value: ${{ jobs.build.outputs.tag }}

REPOSITORY_DISPATCH (API trigger):
  on:
    repository_dispatch:
      types: [ deploy-staging ]
  
  # Trigger via API:
  # curl -X POST \
  #   -H "Authorization: token $TOKEN" \
  #   https://api.github.com/repos/OWNER/REPO/dispatches \
  #   -d '{"event_type": "deploy-staging", "client_payload": {"env": "staging"}}'

MULTIPLE TRIGGERS:
  on:
    push:
      branches: [ main ]
    pull_request:
      branches: [ main ]
    schedule:
      - cron: '0 2 * * *'
    workflow_dispatch:

5. JOBS AND STEPS
================================================================================

Job Dependencies:

  jobs:
    test:
      runs-on: ubuntu-latest
      steps: [ ... ]
    
    lint:
      runs-on: ubuntu-latest
      steps: [ ... ]
    
    build:
      needs: [ test, lint ]   # Runs after BOTH test and lint pass
      runs-on: ubuntu-latest
      steps: [ ... ]
    
    deploy:
      needs: build            # Runs after build passes
      runs-on: ubuntu-latest
      steps: [ ... ]

Job Outputs (pass data between jobs):
  
  jobs:
    build:
      runs-on: ubuntu-latest
      outputs:
        version: ${{ steps.get-version.outputs.version }}
        image-tag: ${{ steps.tag.outputs.tag }}
      
      steps:
        - name: Get version
          id: get-version
          run: |
            VERSION=$(cat version.txt)
            echo "version=$VERSION" >> $GITHUB_OUTPUT
        
        - name: Generate tag
          id: tag
          run: |
            TAG="${{ github.sha }}-$(date +%Y%m%d)"
            echo "tag=$TAG" >> $GITHUB_OUTPUT
    
    deploy:
      needs: build
      runs-on: ubuntu-latest
      steps:
        - name: Deploy version
          run: |
            echo "Deploying ${{ needs.build.outputs.version }}"
            echo "Image tag: ${{ needs.build.outputs.image-tag }}"

Conditional Jobs:
  
  deploy-staging:
    needs: test
    if: github.ref == 'refs/heads/main'
    
  deploy-production:
    needs: deploy-staging
    if: startsWith(github.ref, 'refs/tags/v')

Common if Conditions:
  github.ref == 'refs/heads/main'           # Main branch
  startsWith(github.ref, 'refs/tags/')      # Any tag
  github.event_name == 'push'               # Push event
  github.event_name == 'pull_request'       # PR event
  github.actor == 'dependabot[bot]'         # Dependabot PR
  contains(github.event.pull_request.labels.*.name, 'deploy')  # Label

Step Types:

  # Type 1: Run a shell command
  - name: Run tests
    run: |
      npm install
      npm test
    shell: bash
    working-directory: ./frontend
  
  # Type 2: Use a marketplace action
  - name: Checkout code
    uses: actions/checkout@v4
    with:
      fetch-depth: 0
  
  # Type 3: Use an action from same repo
  - uses: ./.github/actions/my-custom-action
    with:
      input: value
  
  # Type 4: Use a Docker container action
  - uses: docker://alpine:3.18
    with:
      entrypoint: /bin/sh
      args: -c "echo hello"

Setting Environment Variables Dynamically:

  - name: Set variables
    run: |
      # Set env var for subsequent steps in this job
      echo "IMAGE_TAG=${GITHUB_SHA::8}" >> $GITHUB_ENV
      
      # Set output for other jobs
      echo "tag=${GITHUB_SHA::8}" >> $GITHUB_OUTPUT
      
      # Add to PATH for subsequent steps
      echo "/custom/bin" >> $GITHUB_PATH

Services (Docker containers for tests):

  jobs:
    test:
      services:
        postgres:
          image: postgres:15
          env:
            POSTGRES_USER: test
            POSTGRES_PASSWORD: test
            POSTGRES_DB: testdb
          ports:
            - 5432:5432
          options: >-
            --health-cmd pg_isready
            --health-interval 10s
            --health-timeout 5s
            --health-retries 5
        
        redis:
          image: redis:7
          ports:
            - 6379:6379
          options: >-
            --health-cmd "redis-cli ping"
            --health-interval 10s
            --health-retries 5
      
      steps:
        - run: |
            # Access DB at localhost:5432
            psql -h localhost -U test -d testdb -c "SELECT 1"

  # Release
  softprops/action-gh-release@v1        # Create GitHub releases

Version Pinning (Security Best Practice):
  
  # BAD: Latest tag can change (supply chain risk)
  uses: actions/checkout@latest
  
  # BETTER: Semantic version tag
  uses: actions/checkout@v4
  
  # BEST: Pin to exact commit SHA (immutable)
  uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2

Creating Custom Actions:

  TYPE 1: JavaScript Action (runs on runner directly)
  File: action.yml
    name: 'My Action'
    description: 'Does something useful'
    inputs:
      input-value:
        description: 'Input description'
        required: true
        default: 'default'
    outputs:
      result:
        description: 'Result of action'
    runs:
      using: 'node20'
      main: 'index.js'
  
  TYPE 2: Docker Container Action (consistent environment)
  File: action.yml
    name: 'My Docker Action'
    runs:
      using: 'docker'
      image: 'Dockerfile'
      args:
        - ${{ inputs.input-value }}
  
  TYPE 3: Composite Action (multiple steps, shell commands)
  File: .github/actions/setup-env/action.yml
    name: 'Setup Environment'
    description: 'Installs tools needed for CI'
    runs:
      using: composite
      steps:
        - name: Install dependencies
          run: npm ci
          shell: bash
        - uses: actions/cache@v4
          with:
            path: ~/.cache
            key: deps-${{ hashFiles('package-lock.json') }}

7. SECRETS AND VARIABLES
================================================================================

Secrets (sensitive, masked in logs):
  
  Scopes:
  - Organization secrets: Available to all repos in org
  - Repository secrets: Available to all workflows in repo
  - Environment secrets: Available only when using that environment
  
  Configure: Settings → Secrets and variables → Actions
  
  Access in workflow:
    env:
      API_KEY: ${{ secrets.API_KEY }}
      DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
    
    # Or directly in step
    - run: curl -H "Authorization: ${{ secrets.API_TOKEN }}" https://api.example.com
  
  GITHUB_TOKEN (auto-provided):
    Always available. Scoped to the repo. Expires when workflow ends.
    Used for: Publishing packages, creating PRs, commenting on issues.
    
    permissions:              # Set permissions for GITHUB_TOKEN
      contents: read          # Default
      pull-requests: write    # To comment on PRs
      packages: write         # To push to GHCR
      id-token: write         # For OIDC

Variables (non-sensitive, visible in logs):
  
  Configure: Settings → Secrets and variables → Actions → Variables tab
  
  Use for: JAVA_VERSION, REGISTRY, APP_NAME, SLACK_CHANNEL
  
  Access: ${{ vars.JAVA_VERSION }}

Environment Variables:
  
  # Set in workflow YAML (not secret)
  env:
    IMAGE_NAME: my-application
    REGISTRY: ghcr.io
  
  # Set dynamically during workflow
  run: echo "VERSION=2.3.1" >> $GITHUB_ENV

OIDC Authentication (cloud credentials without stored secrets):
  
  # Setup: Create IAM role/service principal trusting GitHub
  # Then in workflow:
  
  permissions:
    id-token: write
    contents: read
  
  - name: Auth with AWS
    uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
      aws-region: us-east-1
  
  # No AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY needed!

8. ENVIRONMENTS AND DEPLOYMENTS
================================================================================

What are GitHub Environments?
  Named deployment targets with protection rules and secrets.
  Examples: development, staging, production
  
  Features:
  - Required reviewers (manual approval)
  - Wait timer (delay before deployment)
  - Deployment branches (only main can deploy to production)
  - Environment-specific secrets and variables
  - Deployment history and logs

Configuring an Environment:
  Settings → Environments → New environment
  - Name: production
  - Required reviewers: [senior-engineer, team-lead]
  - Wait timer: 5 minutes
  - Deployment branches: Selected branches → main only

Using Environments in Workflow:
  
  jobs:
    deploy-staging:
      environment:
        name: staging
        url: https://staging.example.com
      runs-on: ubuntu-latest
      steps:
        - run: echo "Deploying to staging"
          env:
            DB_URL: ${{ secrets.STAGING_DB_URL }}  # Staging-specific secret
    
    deploy-production:
      needs: deploy-staging
      environment:
        name: production           # Triggers approval requirement
        url: https://example.com
      runs-on: ubuntu-latest
      steps:
        - run: echo "Deploying to production"
          env:
            DB_URL: ${{ secrets.PROD_DB_URL }}     # Production-specific secret

Deployment Status Tracking:
  When you use 'environment:' in a job, GitHub tracks deployments:
  - Repository → Deployments shows history
  - Each environment shows current version and status
  - Link to the deployment URL

9. MATRIX BUILDS
================================================================================

Run jobs with multiple variable combinations in parallel:

  jobs:
    test:
      strategy:
        matrix:
          java-version: [17, 21]
          os: [ubuntu-latest, windows-latest]
        fail-fast: false       # Don't cancel all if one fails
        max-parallel: 4        # Max concurrent jobs
      
      runs-on: ${{ matrix.os }}
      
      steps:
        - uses: actions/setup-java@v4
          with:
            java-version: ${{ matrix.java-version }}
            distribution: temurin
        
        - run: mvn test

Result: 4 parallel jobs (2 Java versions × 2 OS)

Matrix Includes and Excludes:
  
  strategy:
    matrix:
      os: [ubuntu-latest, macos-latest, windows-latest]
      node: [18, 20, 22]
      exclude:
        - os: macos-latest
          node: 18    # Don't test Node 18 on macOS
      include:
        - os: ubuntu-latest
          node: 22
          experimental: true   # Add extra variable to specific combo

Matrix with Dynamic Values:
  
  # Generate matrix from script
  jobs:
    generate-matrix:
      runs-on: ubuntu-latest
      outputs:
        services: ${{ steps.find-services.outputs.services }}
      steps:
        - id: find-services
          run: |
            # Find all services with changed files
            SERVICES=$(find . -name 'Dockerfile' -exec dirname {} \; | jq -R . | jq -sc .)
            echo "services=$SERVICES" >> $GITHUB_OUTPUT
    
    build-services:
      needs: generate-matrix
      strategy:
        matrix:
          service: ${{ fromJson(needs.generate-matrix.outputs.services) }}
      steps:
        - name: Build ${{ matrix.service }}
          run: docker build ${{ matrix.service }}

10. REUSABLE WORKFLOWS
================================================================================

Define a workflow once, call it from multiple other workflows.

Reusable Workflow Definition (.github/workflows/build-and-push.yml):
  
  on:
    workflow_call:
      inputs:
        image-name:
          required: true
          type: string
        java-version:
          required: false
          type: string
          default: '21'
        push-image:
          required: false
          type: boolean
          default: true
      secrets:
        registry-token:
          required: true
      outputs:
        image-tag:
          description: "The published image tag"
          value: ${{ jobs.build.outputs.tag }}
  
  jobs:
    build:
      runs-on: ubuntu-latest
      outputs:
        tag: ${{ steps.meta.outputs.tags }}
      steps:
        - uses: actions/checkout@v4
        
        - uses: actions/setup-java@v4
          with:
            java-version: ${{ inputs.java-version }}
            distribution: temurin
            cache: maven
        
        - run: mvn package -DskipTests
        
        - uses: docker/metadata-action@v5
          id: meta
          with:
            images: ghcr.io/org/${{ inputs.image-name }}
            tags: |
              type=sha,prefix={{branch}}-
              type=semver,pattern={{version}}
        
        - uses: docker/build-push-action@v5
          with:
            push: ${{ inputs.push-image }}
            tags: ${{ steps.meta.outputs.tags }}

Calling a Reusable Workflow (service-a.yml):
  
  jobs:
    build:
      uses: ./.github/workflows/build-and-push.yml
      with:
        image-name: service-a
        java-version: '21'
        push-image: ${{ github.ref == 'refs/heads/main' }}
      secrets:
        registry-token: ${{ secrets.GITHUB_TOKEN }}
    
    deploy:
      needs: build
      runs-on: ubuntu-latest
      steps:
        - run: echo "Image tag is ${{ needs.build.outputs.image-tag }}"

Calling External Reusable Workflow:
  
  uses: org/shared-workflows/.github/workflows/build.yml@v1.2.0
  with:
    node-version: '20'
  secrets: inherit    # Pass all secrets from caller to callee

11. SECURITY IN GITHUB ACTIONS
================================================================================

1. PIN ACTION VERSIONS (supply chain security):
   # Vulnerable:
   uses: actions/checkout@latest        # Can change
   uses: actions/checkout@v4            # Better (tag can be moved)
   
   # Best:
   uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683

2. PRINCIPLE OF LEAST PRIVILEGE:
   # Default: Read-only for GITHUB_TOKEN
   permissions:
     contents: read        # Read repo only
     pull-requests: write  # Only if needed to comment
   
   # Never grant: permissions: write-all (unless absolutely necessary)

3. SECRETS PROTECTION:
   - Never echo secrets: echo ${{ secrets.TOKEN }} → masked but still risky
   - Use environment secrets for deployment secrets
   - Rotate secrets regularly
   - Use OIDC instead of long-lived credentials

4. PREVENT SCRIPT INJECTION:
   # VULNERABLE: Attacker can inject code via PR title
   - run: echo "PR title: ${{ github.event.pull_request.title }}"
   
   # SAFE: Use environment variable
   - name: Safe
     env:
       PR_TITLE: ${{ github.event.pull_request.title }}
     run: echo "PR title: $PR_TITLE"

5. FORK PR SAFETY:
   PRs from forks run with limited permissions and NO access to secrets by default.
   Workflow from fork: restricted token, no secrets.
   
   pull_request_target trigger: Has secrets access but runs attacker's code!
   Use pull_request_target only for specific safe use cases (labeling, comments).
   Never checkout and run untrusted code with pull_request_target.

6. CODEQL ANALYSIS (automated security scanning):
   jobs:
     analyze:
       runs-on: ubuntu-latest
       permissions:
         security-events: write
       
       strategy:
         matrix:
           language: [ java, javascript ]
       
       steps:
         - uses: github/codeql-action/init@v3
           with:
             languages: ${{ matrix.language }}
         
         - uses: github/codeql-action/autobuild@v3
         
         - uses: github/codeql-action/analyze@v3

7. DEPENDENCY REVIEW:
   - uses: actions/dependency-review-action@v4
   with:
     fail-on-severity: high    # Fail PR if high CVE in new dependencies

12. GITHUB ACTIONS RUNNERS
================================================================================

GitHub-Hosted Runners:
  
  Labels:
    ubuntu-latest     → ubuntu-24.04
    ubuntu-22.04      → specific Ubuntu version
    windows-latest    → Windows Server 2022
    macos-latest      → macOS 14
    macos-14          → specific macOS version
  
  Specs (Ubuntu/Windows):
  - 2-core CPU, 7 GB RAM, 14 GB SSD
  
  Specs (macOS):
  - 3-core CPU, 14 GB RAM, 14 GB SSD
  
  Larger GitHub-hosted runners (paid):
  - 4, 8, 16, 32, 64-core options
  - GPU runners available
  - Required for: Heavy compilation, large test suites

Self-Hosted Runners:
  
  Why use:
  - Cost savings at scale
  - Compliance (run in your own VPC)
  - Custom hardware (GPU, ARM, specific OS)
  - Faster network to your resources (registry, database)
  - Cached dependencies (persistent between runs)
  
  Setup:
  1. Settings → Actions → Runners → New self-hosted runner
  2. Download and configure runner agent
  3. Register with token
  
  At scale: Use auto-scaling solutions:
  - actions-runner-controller (ARC): Kubernetes-based, scales pods on demand
  - AWS CodeBuild (GitHub-integrated)
  - Philips Labs GitHub runners (EC2 auto-scaling)
  
  Security for self-hosted runners:
  - Don't use for public repos (fork PRs can run arbitrary code on runner)
  - Network isolation: Runners shouldn't have unnecessary access
  - Ephemeral runners: Each job gets a fresh runner (no persistence between jobs)
  - Use runner groups to restrict which repos can use which runners

13. PRACTICAL EXAMPLES
================================================================================

Example 1: Node.js Full CI Pipeline

  name: Node.js CI
  
  on:
    push:
      branches: [ main ]
    pull_request:
      branches: [ main ]
  
  jobs:
    quality:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        
        - uses: actions/setup-node@v4
          with:
            node-version: '20.x'
            cache: 'npm'
        
        - run: npm ci
        - run: npm run lint
        - run: npm run type-check
        - run: npm test -- --coverage
        
        - name: Upload coverage
          uses: codecov/codecov-action@v4
          with:
            token: ${{ secrets.CODECOV_TOKEN }}
    
    build-docker:
      needs: quality
      if: github.ref == 'refs/heads/main'
      runs-on: ubuntu-latest
      
      permissions:
        contents: read
        packages: write
      
      steps:
        - uses: actions/checkout@v4
        
        - uses: docker/login-action@v3
          with:
            registry: ghcr.io
            username: ${{ github.actor }}
            password: ${{ secrets.GITHUB_TOKEN }}
        
        - uses: docker/metadata-action@v5
          id: meta
          with:
            images: ghcr.io/${{ github.repository }}
            tags: |
              type=sha
              type=semver,pattern={{version}}
              type=edge,branch=main
        
        - uses: docker/setup-buildx-action@v3
        
        - uses: docker/build-push-action@v5
          with:
            push: true
            tags: ${{ steps.meta.outputs.tags }}
            labels: ${{ steps.meta.outputs.labels }}
            cache-from: type=gha
            cache-to: type=gha,mode=max

Example 3: Release Workflow

  name: Release
  
  on:
    push:
      tags:
        - 'v[0-9]+.[0-9]+.[0-9]+'
  
  jobs:
    release:
      runs-on: ubuntu-latest
      permissions:
        contents: write
        packages: write
      
      steps:
        - uses: actions/checkout@v4
        
        - uses: actions/setup-java@v4
          with:
            java-version: '21'
            distribution: temurin
            cache: maven
        
        - name: Extract version from tag
          run: echo "VERSION=${GITHUB_REF_NAME#v}" >> $GITHUB_ENV
        
        - name: Build release artifact
          run: mvn package -DskipTests -Dversion=$VERSION
        
        - name: Build and push Docker image
          uses: docker/build-push-action@v5
          with:
            push: true
            tags: |
              ghcr.io/${{ github.repository }}:${{ env.VERSION }}
              ghcr.io/${{ github.repository }}:latest
        
        - name: Create GitHub Release
          uses: softprops/action-gh-release@v2
          with:
            files: target/*.jar
            generate_release_notes: true

15. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is GitHub Actions and how does it differ from Jenkins?
A: GitHub Actions is a CI/CD platform natively integrated into GitHub. Unlike
   Jenkins (a standalone server you manage), GitHub Actions provides cloud-hosted
   runners — you just write YAML workflow files and GitHub runs them.
   
   Key differences:
   - No infrastructure to manage with GitHub Actions
   - Native GitHub events (PRs, issues, releases trigger workflows natively)
   - 15,000+ marketplace actions vs Jenkins 1,800 plugins
   - GitHub Actions is YAML vs Jenkins' Groovy DSL
   - Jenkins is more powerful for complex custom workflows and air-gapped setups
   
   I prefer GitHub Actions for cloud-native projects for its simplicity and
   zero infrastructure overhead. Jenkins makes sense for on-premises, highly
   customized, or already-existing Jenkins setups.

Q2: What is a composite action and when would you create one?
A: A composite action bundles multiple steps into a reusable action that can
   be called with 'uses:' from any workflow in any repository.
   
   I'd create one when: Multiple workflows repeat the same sequence of steps.
   For example, a "setup-dev-environment" composite action that installs specific
   tool versions, configures authentication, and sets environment variables.
   
   Unlike reusable workflows (which are entire workflows), a composite action
   is just a collection of steps usable within any job.

Q3: How do you pass data between jobs in GitHub Actions?
A: Two mechanisms:
   1. JOB OUTPUTS: A job writes to $GITHUB_OUTPUT file, declares the outputs in
      the 'outputs:' section, and dependent jobs access via
      ${{ needs.job-name.outputs.output-name }}
   
   2. ARTIFACTS: One job uploads with actions/upload-artifact@v4, the next
      downloads with actions/download-artifact@v4. Better for larger files
      (build outputs, test reports).
   
   Job outputs are limited to strings; use artifacts for files.

Q4: Explain GitHub Actions security best practices.
A: Top practices:
   1. PIN ACTION VERSIONS to commit SHAs (supply chain protection):
      uses: actions/checkout@11bd71901bbe... not @latest
   
   2. LEAST PRIVILEGE for GITHUB_TOKEN:
      Set 'permissions:' explicitly; default to read-only.
   
   3. OIDC for cloud credentials:
      No stored AWS/GCP keys. OIDC gives short-lived tokens.
   
   4. PREVENT INJECTION: Never interpolate GitHub event data directly in run:
      steps. Use environment variables as intermediary.
   
   5. FORK PR SAFETY: Use pull_request trigger (not pull_request_target) for
      untrusted fork PRs. They get no secrets by default.
   
   6. ENVIRONMENT PROTECTION RULES: Require approvals before production deploys.

Q5: What is the difference between 'needs' and 'if' in GitHub Actions?
A: 'needs' creates dependency ordering — job B runs after job A completes.
   Without 'needs', jobs run in parallel.
   
   'if' adds a conditional — the job/step only runs when the expression is true.
   
   They work together:
     deploy:
       needs: build          # Run after build
       if: github.ref == 'refs/heads/main'   # Only on main
   
   Even with needs, a job with 'if: false' is skipped, not failed.
   Important: By default, if job A fails, dependent job B is also skipped.
   To run B even when A fails: if: always() or if: failure()
