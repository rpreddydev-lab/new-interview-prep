1. DOCKER COMPOSE OVERVIEW
================================================================================

What is Docker Compose:
  Docker Compose is a tool for defining and running multi-container Docker
  applications using a declarative YAML configuration.
  
  Single command to:
  - Build images
  - Create networks
  - Create volumes
  - Start all services
  - Handle service dependencies

Install:
  Docker Desktop includes Docker Compose v2.
  
  # Verify
  docker compose version          # Docker Compose v2 (built-in plugin)
  docker-compose version          # Legacy v1 (standalone binary — deprecated)
  
  # In scripts, prefer the v2 syntax:
  docker compose ...              # v2 (preferred)
  docker-compose ...              # v1 (legacy, deprecated)

Core Use Cases:
  1. LOCAL DEVELOPMENT: App + database + cache + queue all running locally
  2. INTEGRATION TESTING: Spin up dependent services in CI pipeline
  3. DEMO/PROTOTYPE: Share reproducible multi-service setups
  4. SIMPLE STAGING: Run in production for simple deployments (not recommended
     at scale — use Kubernetes instead)

2. DOCKER-COMPOSE.YML STRUCTURE
================================================================================

Top-level Keys:
  
  version: "3.9"       # Compose file format version
  
  services:            # Container definitions
    service-name:
      ...
  
  networks:            # Network definitions
    network-name:
      ...
  
  volumes:             # Volume definitions
    volume-name:
      ...
  
  configs:             # Configs (Docker Swarm)
    config-name:
      ...
  
  secrets:             # Secrets (Docker Swarm)
    secret-name:
      ...

Version History:
  Version 3.x: Current. Compatible with Docker Swarm.
  Version 2.x: Local compose only. Some features not in v3.
  Version 3.9: Most commonly used in practice.
  
  Note: Version key is technically optional in Compose v2 — Compose v2 ignores
  it. But it's still recommended for documentation and tool compatibility.

3. SERVICES CONFIGURATION
================================================================================

Service Options Reference:
  
  services:
    myservice:
      
      # --- IMAGE ---
      image: nginx:1.25-alpine             # Use pre-built image
      
      # --- BUILD ---
      build:
        context: ./myapp                   # Build context directory
        dockerfile: Dockerfile.prod        # Custom Dockerfile name
        args:
          APP_ENV: production              # Build arguments
          APP_VERSION: "1.2.3"
        target: production                 # Multi-stage build target
        cache_from:
          - myregistry/myapp:cache
        labels:
          com.example.version: "1.2.3"
      
      # --- CONTAINER CONFIGURATION ---
      container_name: my-app-container    # Explicit container name
      hostname: myapp                     # Container hostname
      
      # --- COMMAND ---
      command: python app.py              # Override CMD
      entrypoint: /bin/sh                 # Override ENTRYPOINT
      
      # --- PORTS ---
      ports:
        - "8080:80"                       # HOST:CONTAINER
        - "127.0.0.1:8081:80"            # Bind to specific host IP
        - "8082-8085:80-83"              # Port range
      expose:
        - "80"                            # Only expose to other services (no host)
      
      # --- ENVIRONMENT ---
      environment:
        NODE_ENV: production
        DB_HOST: db                       # Service name = DNS name
        DB_PASSWORD: ${DB_PASSWORD}       # Variable substitution from .env
      env_file:
        - .env
        - .env.production
      
      # --- VOLUMES ---
      volumes:
        - myvolume:/data                  # Named volume
        - ./config:/app/config            # Bind mount (relative to compose file)
        - /host/absolute:/app/absolute    # Bind mount (absolute path)
        - type: volume                    # Long-form syntax
          source: myvolume
          target: /data
          read_only: true
      
      # --- NETWORKING ---
      networks:
        - frontend
        - backend
      
      # --- DEPENDENCIES ---
      depends_on:
        db:
          condition: service_healthy      # Wait for healthcheck
        redis:
          condition: service_started      # Just wait for start (not healthy)
      
      # --- RESOURCE LIMITS ---
      deploy:
        resources:
          limits:
            cpus: '0.50'
            memory: 512M
          reservations:
            cpus: '0.25'
            memory: 128M
        replicas: 3                       # Scale instances
        restart_policy:
          condition: on-failure
          max_attempts: 3
      
      # --- RESTART POLICY (non-Swarm) ---
      restart: unless-stopped            # no | always | on-failure | unless-stopped
      
      # --- HEALTH CHECK ---
      healthcheck:
        test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
        interval: 30s
        timeout: 10s
        retries: 3
        start_period: 40s
      
      # --- LABELS ---
      labels:
        com.example.description: "My App"
        traefik.enable: "true"
      
      # --- PROFILES ---
      profiles:
        - production
        - debug
      
      # --- EXTRA HOSTS ---
      extra_hosts:
        - "host.docker.internal:host-gateway"  # Access host from container
      
      # --- SECURITY ---
      user: "1001:1001"                  # Run as specific user
      read_only: true                    # Read-only filesystem
      tmpfs:
        - /tmp
        - /run
      cap_drop:
        - ALL
      cap_add:
        - NET_BIND_SERVICE
      security_opt:
        - no-new-privileges:true
      
      # --- DNS ---
      dns:
        - 8.8.8.8
        - 8.8.4.4
      
      # --- LOGGING ---
      logging:
        driver: "json-file"
        options:
          max-size: "10m"
          max-file: "3"

4. NETWORKING IN COMPOSE
================================================================================

Default Network Behavior:
  Docker Compose creates a default network for your application.
  All services are connected to this default network.
  Services can reach each other by SERVICE NAME (DNS resolution).
  
  # If you have:
  services:
    web:
      image: myapp
    db:
      image: postgres:15
  
  # The web service can connect to the database at: db:5432
  # Compose auto-creates a network: <project-name>_default

Custom Networks:
  
  networks:
    frontend:
      driver: bridge
    backend:
      driver: bridge
      internal: true               # No external internet access
    monitoring:
      name: my-monitoring          # Override generated network name
      external: true               # Use pre-existing network (don't create)
      driver: overlay              # For Docker Swarm multi-host
      driver_opts:
        encrypted: "true"
      ipam:
        driver: default
        config:
          - subnet: 172.20.0.0/16
            gateway: 172.20.0.1

Network Isolation Pattern:
  
  # Frontend services can reach backend, but backend can't reach frontend
  # Monitoring can reach everything
  
  services:
    nginx:
      networks:
        - frontend
    
    api:
      networks:
        - frontend
        - backend
    
    db:
      networks:
        - backend
    
    prometheus:
      networks:
        - frontend
        - backend
  
  networks:
    frontend:
    backend:

Network Aliases:
  services:
    db:
      networks:
        backend:
          aliases:
            - database             # Services can also use "database" as hostname
            - postgres

5. VOLUMES IN COMPOSE
================================================================================

Volume Types:

  NAMED VOLUMES (persistent, Docker-managed):
    volumes:
      postgres_data:                 # Declared at top level
    
    services:
      db:
        volumes:
          - postgres_data:/var/lib/postgresql/data
    
    # Data persists even after docker compose down
    # docker compose down -v  → removes volumes too
  
  BIND MOUNTS (local filesystem):
    services:
      web:
        volumes:
          - ./src:/app/src           # Relative to compose file directory
          - ./config.yaml:/app/config.yaml:ro  # Read-only
  
  ANONYMOUS VOLUMES:
    services:
      app:
        volumes:
          - /app/data                # No name = anonymous, less portable

Volume Configuration (top-level):
  
  volumes:
    postgres_data:
      driver: local                  # Default
    
    shared_config:
      driver: local
      driver_opts:
        type: none
        device: /host/path
        o: bind
    
    nfs_data:
      driver: local
      driver_opts:
        type: nfs
        o: "addr=10.0.0.1,ro,nfsvers=4"
        device: ":/path/to/data"
    
    existing_volume:
      external: true                 # Use pre-existing volume, don't create

6. ENVIRONMENT VARIABLES AND SECRETS
================================================================================

Environment Variables in Compose:

  1. Inline values:
     services:
       app:
         environment:
           NODE_ENV: production
           PORT: "3000"
  
  2. From host environment (no value = use host):
     environment:
       - NODE_ENV                     # Inherits from host shell
  
  3. Variable substitution from .env file:
     environment:
       DB_PASSWORD: ${DB_PASSWORD}    # From .env file or host env
       REDIS_URL: ${REDIS_URL:-redis://localhost:6379}  # With default
  
  4. env_file:
     env_file:
       - .env
       - .env.${ENV:-development}    # Dynamic env file name

.env File:
  The .env file in the same directory as docker-compose.yml is automatically
  loaded for VARIABLE SUBSTITUTION in compose file (not inside containers!).
  
  .env:
  DB_PASSWORD=supersecret
  DB_PORT=5432
  APP_VERSION=1.2.3
  
  docker-compose.yml:
  services:
    db:
      image: postgres:${POSTGRES_VERSION:-15}
      environment:
        POSTGRES_PASSWORD: ${DB_PASSWORD}
  
  # DB_PASSWORD from .env is passed to container's env
  # To see what Compose resolves: docker compose config

Secrets (Docker Swarm mode):
  
  secrets:
    db_password:
      file: ./secrets/db_password.txt     # Read from file
    api_key:
      external: true                      # Pre-existing secret in Swarm
  
  services:
    app:
      secrets:
        - db_password
        - api_key
  
  # Secrets are mounted at /run/secrets/<secret_name> inside container
  # App reads: open("/run/secrets/db_password").read()
  
  # Note: Secrets in Compose (outside Swarm mode) just bind-mount the file.
  # True secrets management requires Docker Swarm or Kubernetes.

7. HEALTH CHECKS AND DEPENDENCIES
================================================================================

Healthcheck Definition:
  
  services:
    db:
      image: postgres:15
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
        interval: 10s            # How often to check
        timeout: 5s              # How long to wait for result
        retries: 5               # How many consecutive failures = unhealthy
        start_period: 30s        # Grace period before first check

Healthcheck Test Forms:
  
  test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
  # Uses exec form — no shell wrapping
  
  test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
  # Uses shell — can use || and && operators
  
  test: ["NONE"]
  # Disables inherited healthcheck

depends_on Conditions:
  
  services:
    app:
      depends_on:
        db:
          condition: service_healthy   # Wait for healthcheck to pass
          restart: true               # Restart app if db restarts
        redis:
          condition: service_started  # Just wait for container to start
        migrations:
          condition: service_completed_successfully  # Wait for one-off task to finish
    
    db:
      image: postgres:15
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U postgres"]
        interval: 5s
        retries: 10
    
    redis:
      image: redis:7
    
    migrations:
      image: myapp:latest
      command: ["python", "manage.py", "migrate"]
      depends_on:
        db:
          condition: service_healthy

One-off Tasks (Init Containers pattern):
  
  services:
    db-init:
      image: postgres:15
      command: ["psql", "-h", "db", "-U", "user", "-c", "CREATE DATABASE myapp;"]
      depends_on:
        db:
          condition: service_healthy
      restart: "no"              # Run once and exit
    
    app:
      depends_on:
        db-init:
          condition: service_completed_successfully

8. OVERRIDE FILES AND PROFILES
================================================================================

Override Files:
  Compose automatically merges files:
  docker-compose.yml  → base configuration
  docker-compose.override.yml → automatically loaded overrides (for local dev)
  
  # Explicit merging:
  docker compose -f docker-compose.yml -f docker-compose.staging.yml up
  
  Override semantics:
  - Simple values: Override (later file wins)
  - Lists (ports, volumes, environment): APPEND (not replace)
  - Maps (services, networks): Deep merge

Typical File Structure:
  
  docker-compose.yml:          # Base (production-like settings)
  version: "3.9"
  services:
    web:
      image: myregistry/myapp:${IMAGE_TAG:-latest}
      environment:
        LOG_LEVEL: info
      restart: unless-stopped
  
  docker-compose.override.yml:  # Local dev (auto-loaded)
  version: "3.9"
  services:
    web:
      build: .                   # Build locally instead of pulling
      volumes:
        - .:/app                 # Mount source for live reload
      environment:
        LOG_LEVEL: debug         # Override log level for dev
      ports:
        - "3000:3000"
  
  docker-compose.prod.yml:       # Production overrides
  version: "3.9"
  services:
    web:
      deploy:
        replicas: 3
        resources:
          limits:
            memory: 512M

Using Override Files in Commands:
  
  # Development (auto-loads docker-compose.override.yml):
  docker compose up
  
  # Production:
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
  
  # Staging:
  docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d
  
  # CI testing (no override file):
  docker compose -f docker-compose.yml up -d

Profiles:
  Profiles allow conditional service activation.
  
  services:
    app:
      image: myapp
      # No profile = always started
    
    db:
      image: postgres:15
      profiles:
        - full
    
    redis:
      image: redis:7
      profiles:
        - full
        - cache-only
    
    mailcatcher:
      image: mailhog/mailhog
      profiles:
        - dev
  
  # Activate profiles:
  docker compose --profile full up       # Start app + db + redis
  docker compose --profile dev up        # Start app + mailcatcher
  
  # Environment variable:
  COMPOSE_PROFILES=full docker compose up

9. DOCKER COMPOSE CLI COMMANDS
================================================================================

Starting and Stopping:
  docker compose up                      # Start everything (foreground)
  docker compose up -d                   # Start everything (detached/background)
  docker compose up --build              # Rebuild images before starting
  docker compose up --force-recreate    # Recreate containers even if config unchanged
  docker compose up --no-deps web       # Start only web (skip dependencies)
  docker compose up web db              # Start specific services only
  docker compose up --scale web=3       # Scale web to 3 instances
  docker compose down                    # Stop and remove containers and networks
  docker compose down -v                 # Also remove volumes
  docker compose down --rmi all         # Also remove images
  docker compose stop                    # Stop without removing
  docker compose start                   # Start stopped services
  docker compose restart                 # Restart services
  docker compose pause web              # Pause specific service
  docker compose unpause web            # Unpause

Status and Inspection:
  docker compose ps                      # Status of all services
  docker compose ps web                  # Status of specific service
  docker compose images                  # Images used by services
  docker compose port web 80             # Find published port

Logs:
  docker compose logs                    # All service logs
  docker compose logs -f                 # Follow all logs
  docker compose logs -f web            # Follow logs for web service
  docker compose logs --tail=50 web     # Last 50 lines
  docker compose logs --since=1h web    # Logs from last hour

Executing Commands:
  docker compose exec web bash          # Interactive shell in running container
  docker compose exec web python manage.py createsuperuser
  docker compose run --rm web python manage.py migrate  # Run one-off command
  docker compose run --rm -e ENV=test web pytest        # One-off with env var

Build:
  docker compose build                   # Build all services
  docker compose build web              # Build specific service
  docker compose build --no-cache web   # Build without cache
  docker compose pull                    # Pull all images

Project Management:
  docker compose config                  # Print resolved configuration
  docker compose config --quiet         # Validate config (exit 1 on error)
  docker compose top                     # Running processes in containers
  docker compose events                  # Stream container events
  
  # Project name:
  docker compose -p myproject up
  COMPOSE_PROJECT_NAME=myproject docker compose up

10. COMPOSE VS KUBERNETES
================================================================================

When to Use Docker Compose:
  ✓ Local development
  ✓ Integration testing in CI
  ✓ Small, simple applications with few requirements
  ✓ Quick demos and prototyping
  ✓ Single-host deployments
  ✓ When team doesn't need K8s expertise

When to Use Kubernetes:
  ✓ Production-grade deployments
  ✓ Multi-host / multi-zone deployments
  ✓ Auto-scaling (HPA, VPA)
  ✓ Self-healing, automatic restarts
  ✓ Rolling updates and rollbacks
  ✓ Fine-grained RBAC and security policies
  ✓ Complex service mesh networking
  ✓ Stateful workloads with PersistentVolumes

Comparison Table:
  
  Feature                  Docker Compose    Kubernetes
  ─────────────────────────────────────────────────────────
  Multi-container apps     ✓                 ✓
  Single host              ✓                 Limited
  Multi-host               ✗                 ✓
  Auto-scaling             ✗                 ✓ (HPA/VPA)
  Self-healing             Limited           ✓
  Load balancing           Basic             Advanced
  Rolling updates          ✗                 ✓
  Declarative config       ✓                 ✓
  Setup complexity         Low               High
  Resource overhead        Low               Higher
  Production-ready         Simple use cases  Enterprise scale
  RBAC                     ✗                 ✓
  Secrets management       Basic             Advanced
  Service discovery        DNS               DNS + more
  Config management        env/files         ConfigMaps/Secrets
  Health checks            ✓                 ✓
  Persistent storage       Basic             Advanced (StorageClasses)

Bridge: Kompose
  Tool to convert docker-compose.yml to Kubernetes manifests:
  
  kompose convert                        # Convert to K8s YAML files
  kompose up                             # Deploy to K8s
  
  # Annotations in compose file for K8s customization:
  services:
    web:
      labels:
        kompose.service.type: nodeport
        kompose.image-pull-policy: Always

11. REAL-WORLD COMPOSE EXAMPLES
================================================================================

Full-Stack Web App (Django + PostgreSQL + Redis + Celery + Nginx):
  
  version: "3.9"
  
  x-common-env: &common-env
    DATABASE_URL: postgresql://user:${DB_PASSWORD}@db:5432/myapp
    REDIS_URL: redis://redis:6379/0
    SECRET_KEY: ${SECRET_KEY}
  
  services:
    nginx:
      image: nginx:1.25-alpine
      ports:
        - "80:80"
        - "443:443"
      volumes:
        - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
        - static_files:/staticfiles:ro
      depends_on:
        - web
      networks:
        - frontend
    
    web:
      build:
        context: .
        target: production
      command: gunicorn myapp.wsgi:application --bind 0.0.0.0:8000 --workers 2
      environment:
        <<: *common-env
        DEBUG: "0"
      volumes:
        - static_files:/app/staticfiles
      expose:
        - "8000"
      depends_on:
        db:
          condition: service_healthy
        redis:
          condition: service_started
      networks:
        - frontend
        - backend
      restart: unless-stopped
    
    celery:
      build:
        context: .
        target: production
      command: celery -A myapp worker --loglevel=info
      environment:
        <<: *common-env
      depends_on:
        db:
          condition: service_healthy
        redis:
          condition: service_started
      networks:
        - backend
      restart: unless-stopped
    
    db:
      image: postgres:15-alpine
      environment:
        POSTGRES_DB: myapp
        POSTGRES_USER: user
        POSTGRES_PASSWORD: ${DB_PASSWORD}
      volumes:
        - postgres_data:/var/lib/postgresql/data
        - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U user -d myapp"]
        interval: 10s
        timeout: 5s
        retries: 5
      networks:
        - backend
    
    redis:
      image: redis:7-alpine
      command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
      volumes:
        - redis_data:/data
      networks:
        - backend
  
  volumes:
    postgres_data:
    redis_data:
    static_files:
  
  networks:
    frontend:
    backend:
      internal: true

12. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is Docker Compose and how is it different from running individual
    docker run commands?
A: Docker Compose is a tool for defining multi-container applications in a
   single docker-compose.yml file. Instead of running many complex docker run
   commands (each with volumes, ports, networks, environment variables), you
   define everything once in YAML and manage the entire application with a
   single docker compose up.
   
   Key advantages:
   - Single source of truth for all service configuration
   - Services share a named project network automatically (DNS by service name)
   - Easy to reference volumes across services
   - Version control the whole application stack
   - Repeatable: anyone can run the same stack with one command
   - Override files for environment-specific customization
   
   Example: A web app with PostgreSQL, Redis, and Nginx would require 4
   carefully crafted docker run commands with multiple flags, network creation,
   volume creation. With Compose, docker compose up handles everything.

Q2: How do service dependencies work in Docker Compose?
A: depends_on controls service startup order, with different condition types:
   
   service_started: Waits for the container to be running (default behavior
   before v2). Just means the container process started, not that it's ready.
   
   service_healthy: Waits for the service's healthcheck to return "healthy".
   This is the correct way to wait for databases to be truly ready.
   
   service_completed_successfully: Waits for a container to finish and exit 0.
   Used for one-off initialization tasks (like DB migrations).
   
   Example:
   services:
     app:
       depends_on:
         db:
           condition: service_healthy  # DB must pass healthcheck
   db:
     healthcheck:
       test: ["CMD-SHELL", "pg_isready -U postgres"]
   
   IMPORTANT: depends_on only controls startup ORDER within Compose.
   In production, apps must handle connection retries regardless, because:
   - A container being "running" doesn't mean the service is ready
   - Services can restart independently
   - Networks can be temporarily unavailable

Q3: What is the purpose of Compose override files?
A: Override files let you layer configuration for different environments without
   duplicating the base configuration.
   
   Structure:
   docker-compose.yml: Base configuration (common to all environments)
   docker-compose.override.yml: Automatically loaded for local development
   docker-compose.prod.yml: Production-specific settings
   docker-compose.ci.yml: CI-specific settings
   
   Compose deeply merges these files. Simple values are overridden, but lists
   (volumes, ports, environment) are appended.
   
   Development override might:
   - Use build: . instead of pre-built image (build locally)
   - Mount source code as volume for live reload
   - Enable debug mode
   - Expose extra debug ports
   
   Production override might:
   - Set deploy.replicas: 3
   - Add resource limits
   - Use different logging configuration
   - Disable development tools

Q4: How do you handle secrets in Docker Compose?
A: Docker Compose has different levels of secret management:
   
   1. .env file (most common for development):
      - Store secrets in .env (add to .gitignore!)
      - Reference with ${SECRET_NAME} in compose file
      - Limitation: values visible in process environment, docker inspect
   
   2. Docker Secrets (production with Docker Swarm):
      - Store as Swarm secrets (encrypted at rest and in transit)
      - Mounted at /run/secrets/<name> inside container
      - Not visible in environment variables or docker inspect
      - Syntax: secrets: [db_password] in service config
   
   3. Environment variables at runtime:
      - Pass with docker compose run -e SECRET=value
      - Or export in shell before running docker compose up
   
   4. External secret managers:
      - HashiCorp Vault, AWS Secrets Manager
      - App reads secrets via API at startup, not from environment
   
   Best practice:
   - NEVER commit .env files with real secrets
   - Use .env.example with placeholder values in version control
   - Use Docker Secrets for Swarm, Kubernetes Secrets for K8s

Q5: When would you use Docker Compose in production vs Kubernetes?
A: This is a nuanced question that depends on requirements:
   
   Use Docker Compose for simple production deployments when:
   - Single-host deployment is acceptable
   - Traffic is low, no need for auto-scaling
   - Team is small, limited DevOps expertise
   - Application has few services, simple requirements
   - You need simplicity over features
   
   Use Kubernetes when:
   - Multi-host, high-availability requirements
   - Auto-scaling needed (CPU, memory, custom metrics)
   - Complex rolling updates and rollbacks
   - Multiple teams sharing infrastructure
   - Fine-grained RBAC and security policies required
   - Enterprise-scale operations
   
   Key limitations of Compose in production:
   - No auto-scaling
   - No automatic pod rescheduling if host fails
   - No built-in load balancing across hosts
   - No sophisticated health management
   - No rolling updates
   
   Many organizations use Compose for development and Kubernetes for production.
   The Kompose tool can convert Compose files to Kubernetes manifests.

COMPOSE FILE STRUCTURE:
  version: "3.9"
  services:         # Container definitions
  networks:         # Network definitions
  volumes:          # Volume definitions

COMMON SERVICE OPTIONS:
  image: name:tag           # Pre-built image
  build: ./path             # Build from Dockerfile
  ports: ["host:cont"]      # Port mapping
  environment: [KEY=val]    # Environment variables
  env_file: [.env]          # Load from file
  volumes: [named:/path]    # Volume mounts
  networks: [netname]       # Networks to join
  depends_on: [service]     # Start after these services
  restart: unless-stopped   # Restart policy
  healthcheck: ...          # Health check

DEPENDS_ON CONDITIONS:
  service_started            # Container started (not necessarily ready)
  service_healthy            # Healthcheck passed ← Use for databases
  service_completed_successfully  # One-off task completed

CLI COMMANDS:
  docker compose up -d       # Start all services (detached)
  docker compose up --build  # Rebuild and start
  docker compose down        # Stop and remove containers+networks
  docker compose down -v     # Also remove volumes
  docker compose ps          # Service status
  docker compose logs -f     # Follow logs
  docker compose exec svc sh # Shell into service
  docker compose run --rm svc cmd  # One-off command
  docker compose build       # Build images
  docker compose pull        # Pull images
  docker compose config      # Validate and show resolved config

OVERRIDE FILES:
  docker-compose.yml         # Base
  docker-compose.override.yml # Auto-loaded (dev defaults)
  docker compose -f base.yml -f override.yml up  # Explicit merge

VARIABLE SUBSTITUTION:
  ${VAR}                     # Required variable
  ${VAR:-default}            # With default if unset
  ${VAR:?error message}      # Required — fail with message if unset

YAML ANCHORS (DRY):
  x-common: &common          # Define anchor
    networks: [mynet]
  services:
    web:
      <<: *common            # Merge anchor

NETWORKING:
  Default: All services in one project network, DNS by service name
  Custom: Define networks, assign services to control isolation
  Access by service name: db:5432, redis:6379, etc.

COMPOSE vs KUBERNETES:
  Compose: Local dev, CI testing, simple/single-host production
  Kubernetes: Auto-scaling, multi-host, rolling updates, enterprise scale
