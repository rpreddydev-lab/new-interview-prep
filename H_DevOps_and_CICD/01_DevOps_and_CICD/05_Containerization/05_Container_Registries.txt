1. CONTAINER REGISTRY OVERVIEW
================================================================================

What is a Container Registry:
  A container registry is a service for storing, distributing, and managing
  container images. It is to containers what npm is to Node.js or PyPI is to
  Python.
  
  Registry → Repository → Images (Tags)
  
  registry.example.com/team/app:v1.2.3
  ─────────────────────────────────────
  registry.example.com  = Registry (server)
  team/app              = Repository (image name)
  v1.2.3                = Tag (specific version)

Registry Types:
  
  PUBLIC:     Docker Hub, Quay.io, GitHub Container Registry
              Anyone can pull; push requires account
  
  PRIVATE:    AWS ECR, Google Artifact Registry, Azure ACR, Harbor
              Authentication required for push AND pull
  
  HYBRID:     Docker Hub (public repos + private repos)

Key Operations:
  
  1. PUSH: Upload an image to the registry
     docker push registry.example.com/team/app:v1.2.3
  
  2. PULL: Download an image from the registry
     docker pull registry.example.com/team/app:v1.2.3
  
  3. TAG: Add a name to an image
     docker tag myapp:latest registry.example.com/team/app:v1.2.3

Registry in CI/CD Pipeline:
  
  Developer    CI Pipeline              Registry       Production
  ─────────    ──────────────────────   ────────────   ──────────────
  git push →   docker build             push image →   docker pull
               run tests           →    registry       deploy
               docker push →→→→→→→→→→→→→→→              kubectl apply

2. DOCKER HUB
================================================================================

Overview:
  The default, largest public registry. docker pull ubuntu automatically pulls
  from Docker Hub.
  
  URL: hub.docker.com
  Default registry: docker.io (implied when no registry specified)

Image Types on Docker Hub:
  
  OFFICIAL IMAGES: ubuntu, nginx, postgres, python, redis
    - Maintained by Docker and community
    - Vetted security standards
    - Identified by no namespace: FROM ubuntu:22.04
  
  VERIFIED PUBLISHERS: mysql/mysql-server, bitnami/nginx
    - Commercial/enterprise software vendors
    - Verified identity
  
  COMMUNITY IMAGES: username/imagename
    - Anyone can push

Authentication:
  docker login                                  # Interactive login
  docker login -u username -p password          # Non-interactive (INSECURE)
  docker login -u username --password-stdin     # Pipe password (secure)
  echo $DOCKER_TOKEN | docker login --username $USER --password-stdin
  
  Credentials stored in: ~/.docker/config.json
  For CI/CD: Use access tokens (not passwords)

Rate Limits (Free Tier):
  - Unauthenticated: 100 pulls/6 hours per IP
  - Authenticated free: 200 pulls/6 hours per account
  - Docker Pro/Team: Unlimited
  
  Solution for CI/CD: Authenticate with Docker Hub credentials.
  Solution for on-prem: Use Docker Hub mirror or pull-through cache.

Automating Builds:
  Docker Hub can automatically build images from GitHub/Bitbucket on push.
  (Deprecated automated builds replaced by GitHub Actions integration)

3. AWS ELASTIC CONTAINER REGISTRY (ECR)
================================================================================

Overview:
  AWS-native, fully managed container registry.
  Integrated with IAM for authentication — no separate user management.
  Two types:
  - ECR Private: Authenticated access
  - ECR Public (Gallery): Public images at public.ecr.aws

Setup:
  # Create repository (via AWS CLI)
  aws ecr create-repository \
      --repository-name my-app \
      --region us-east-1 \
      --image-scanning-configuration scanOnPush=true \
      --encryption-configuration encryptionType=AES256
  
  # Result: 123456789.dkr.ecr.us-east-1.amazonaws.com/my-app

Authentication:
  ECR uses time-limited tokens (12 hours). Must re-authenticate.
  
  # Get login token and authenticate Docker
  aws ecr get-login-password --region us-east-1 \
      | docker login --username AWS --password-stdin \
        123456789.dkr.ecr.us-east-1.amazonaws.com
  
  # Helper tool: amazon-ecr-credential-helper (auto-refreshes tokens)
  # ~/.docker/config.json:
  # {"credHelpers": {"123456789.dkr.ecr.us-east-1.amazonaws.com": "ecr-login"}}

ECR in GitHub Actions:
  
  jobs:
    build:
      runs-on: ubuntu-latest
      permissions:
        id-token: write   # Required for OIDC auth
        contents: read
      
      steps:
        - uses: actions/checkout@v4
        
        - name: Configure AWS credentials (OIDC - no long-lived secrets!)
          uses: aws-actions/configure-aws-credentials@v4
          with:
            role-to-assume: arn:aws:iam::123456789:role/GitHubActionsRole
            aws-region: us-east-1
        
        - name: Login to Amazon ECR
          id: login-ecr
          uses: aws-actions/amazon-ecr-login@v2
        
        - name: Build, tag, and push image to Amazon ECR
          env:
            ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
            ECR_REPOSITORY: my-app
            IMAGE_TAG: ${{ github.sha }}
          run: |
            docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
            docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG

ECR IAM Permissions:
  
  # Minimal push permissions (CI role):
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": [
          "ecr:GetAuthorizationToken"
        ],
        "Resource": "*"
      },
      {
        "Effect": "Allow",
        "Action": [
          "ecr:BatchCheckLayerAvailability",
          "ecr:PutImage",
          "ecr:InitiateLayerUpload",
          "ecr:UploadLayerPart",
          "ecr:CompleteLayerUpload"
        ],
        "Resource": "arn:aws:ecr:us-east-1:123456789:repository/my-app"
      }
    ]
  }
  
  # Production pull permissions (ECS Task Role / EKS Node Role):
  Action: ecr:GetAuthorizationToken, ecr:BatchGetImage, ecr:GetDownloadUrlForLayer

ECR Features:
  - Image scanning on push (Clair-based, or Amazon Inspector)
  - Image lifecycle policies for automated cleanup
  - Cross-region replication
  - Encryption at rest (KMS or AES256)
  - VPC endpoints for private access
  - Tag immutability (prevent re-tagging existing images)

4. GOOGLE ARTIFACT REGISTRY / GCR
================================================================================

Overview:
  Google Artifact Registry (GAR): Current, recommended service
  Google Container Registry (GCR): Legacy (gcr.io) — being deprecated
  
  GAR supports: Docker, Maven, npm, Python, APT, Yum, etc.

Authentication:
  # Configure Docker credential helper
  gcloud auth configure-docker us-central1-docker.pkg.dev
  
  # Push image
  docker tag myapp:latest us-central1-docker.pkg.dev/PROJECT_ID/REPO/myapp:v1

In CI/CD (GitHub Actions with Workload Identity):
  
  - name: Authenticate to Google Cloud

    run: |
      docker build -t us-central1-docker.pkg.dev/my-project/my-repo/myapp:${{ github.sha }} .
      docker push us-central1-docker.pkg.dev/my-project/my-repo/myapp:${{ github.sha }}

5. GITHUB CONTAINER REGISTRY (GHCR)
================================================================================

Overview:
  Registry at ghcr.io, integrated with GitHub.
  Images associated with GitHub users or organizations.
  
  Free for public images. Storage cost for private.

Authentication:
  # Personal Access Token (PAT) with read:packages, write:packages scopes:
  echo $GITHUB_TOKEN | docker login ghcr.io --username $GITHUB_ACTOR --password-stdin
  
  # In GitHub Actions (uses GITHUB_TOKEN automatically):
  - name: Log in to GitHub Container Registry
    uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}  # Auto-provided by GitHub

Image Naming:
  ghcr.io/OWNER/IMAGE:TAG
  ghcr.io/myorg/myapp:v1.2.3
  ghcr.io/myusername/myapp:latest

Linking Image to Repository:
  # Label in Dockerfile links image to GitHub repo:
  LABEL org.opencontainers.image.source="https://github.com/owner/repo"
  
  # Image then appears in GitHub repo's "Packages" section

================================================================================

  # Assign AcrPull or AcrPush role to managed identity

Push/Pull:
  docker tag myapp:v1 myregistry.azurecr.io/myapp:v1

7. SELF-HOSTED: HARBOR
================================================================================

Overview:
  Open-source, CNCF-graduated container registry.
  Enterprise features: RBAC, vulnerability scanning, content trust, replication.
  Can be deployed on-premises or on any cloud.

Architecture Components:
  - Portal: Web UI
  - Core: API server
  - Job Service: Background async jobs
  - Registry: Distribution layer (Docker Registry v2)
  - Trivy: Vulnerability scanner (built-in)
  - Notary: Content trust / image signing
  - Database: PostgreSQL
  - Redis: Session and cache
  - MinIO/Object Storage: Image blob storage

Key Features:
  RBAC:
    Projects → Roles → Users
    Project Admin, Developer, Guest, Maintainer, Limited Guest
  
  VULNERABILITY SCANNING:
    Built-in Trivy scanner.
    Scan on push, scan on schedule.
    Block pull of vulnerable images (policy-based).
  
  REPLICATION:
    Replicate images between Harbor instances or to/from cloud registries.
    Push-based or pull-based replication.
  
  WEBHOOK:
    Trigger external systems on push, scan completion, etc.

Authentication:
  docker login harbor.example.com
  docker tag myapp:v1 harbor.example.com/myproject/myapp:v1
  docker push harbor.example.com/myproject/myapp:v1

Install with Helm:
  helm repo add harbor https://helm.goharbor.io
  helm install harbor harbor/harbor \
    --namespace harbor \
    --create-namespace \
    --set expose.type=ingress \
    --set expose.ingress.hosts.core=harbor.example.com \
    --set externalURL=https://harbor.example.com \
    --set harborAdminPassword=admin123

8. IMAGE TAGGING STRATEGIES
================================================================================

Why Tagging Matters:
  Tags are mutable by default — you can push a new image with the same tag.
  "latest" means "the last image pushed with this tag", NOT "the latest version".
  Bad tagging leads to: not knowing what's deployed, can't roll back reliably.

Tagging Strategies:

  1. SEMANTIC VERSIONING (SemVer):
     myapp:1.2.3
     myapp:1.2     # Tracks latest 1.2.x (mutable)
     myapp:1       # Tracks latest 1.x.x (mutable)
     
     Pros: Human-readable, follows software versioning standards
     Cons: Manual version bumping, can be tedious
  
  2. GIT SHA (RECOMMENDED for CI/CD):
     myapp:sha-abc1234                    # Short SHA
     myapp:git-abc1234                    # Common prefix
     myapp:abc1234ef56789abc1234ef56789abc1234ef  # Full SHA
     
     Pros: 1:1 mapping to code commit, automatic, perfect traceability
     Cons: Not human-readable without looking up commit
  
  3. GIT BRANCH + SHA:
     myapp:main-abc1234
     myapp:feature-auth-def5678
     
     Pros: Understand what branch, which commit
     Cons: Branch names can be long/ugly
  
  4. BUILD NUMBER (Jenkins, etc.):
     myapp:build-123
     myapp:ci-456
     
     Pros: Sequential, simple to understand order
     Cons: Coupled to CI system, can be confusing across CI runs
  
  5. TIMESTAMP:
     myapp:20240115-143022
     myapp:2024.01.15
     
     Pros: Know when it was built
     Cons: Doesn't tell you what code is in the image
  
  6. COMBINATION (BEST PRACTICE):
     myapp:v1.2.3-abc1234       # SemVer + Git SHA
     myapp:main-20240115-abc1234 # Branch + date + SHA

The "latest" Anti-Pattern:
  
  PROBLEM with "latest" in production:
  - Non-deterministic: docker pull myapp:latest today vs tomorrow = different image
  - Can't roll back: what was "latest" before your breaking change?
  - No audit trail: can't tell what's deployed by reading the tag
  
  WHEN "latest" is OK:
  - Local development and quick testing
  - Base images in Dockerfile (but even here, pin versions)
  - Never in production Kubernetes manifests!
  
  RULE: Never use "latest" in production. Always use a specific, immutable tag.

Tag Immutability:
  Many registries support tag immutability — prevents overwriting an existing tag.
  
  ECR: Enable during repo creation or update
  docker build --build-arg ... → push with NEW tag each time
  Harbor: Repository → Immutable tag rules
  
  With immutability: if myapp:v1.2.3 exists, pushing again FAILS.
  Ensures "pin to version" is actually safe.

Docker Hub Metadata Action (GitHub Actions):
  
  # docker/metadata-action generates tags automatically
  - name: Extract Docker metadata
    id: meta
    uses: docker/metadata-action@v5
    with:
      images: myregistry/myapp
      tags: |
        type=sha                                    # sha-abc1234
        type=semver,pattern={{version}}             # v1.2.3
        type=semver,pattern={{major}}.{{minor}}     # v1.2
        type=ref,event=branch                       # main
        type=ref,event=pr                           # pr-42
        type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

9. IMAGE SIGNING AND TRUST
================================================================================

Why Sign Images:
  Verify that an image comes from a trusted source and hasn't been tampered
  with between build and deployment.
  
  Attack vector without signing:
  - Man-in-the-middle attack swaps image in transit
  - Registry compromise replaces image
  - Confused deputy: deploy from wrong repo
  
  With signing: Kubernetes admission controller rejects unsigned images.

Cosign (Sigstore):
  Modern, widely adopted image signing tool.
  
  # Install cosign
  brew install cosign
  
  # Generate key pair
  cosign generate-key-pair
  # Creates: cosign.key (private) and cosign.pub (public)
  
  # Sign an image (after pushing)
  cosign sign --key cosign.key registry.example.com/myapp:v1.2.3
  
  # Verify signature
  cosign verify --key cosign.pub registry.example.com/myapp:v1.2.3
  
  # Sign with GitHub OIDC (keyless — no private key management):
  cosign sign registry.example.com/myapp:v1.2.3
  # Uses OIDC identity; signature recorded in Rekor transparency log
  
  # In GitHub Actions:
  - name: Sign image
    run: |
      cosign sign \
        --yes \
        ${{ steps.login-ecr.outputs.registry }}/myapp:${{ github.sha }}
    env:
      COSIGN_EXPERIMENTAL: "true"  # Keyless signing

Sigstore Rekor:
  Transparency log for supply chain security.
  Every signature is recorded immutably.
  Can audit who signed what and when.

Docker Content Trust (Notary):
  Older signing mechanism based on Notary.
  
  # Enable:
  export DOCKER_CONTENT_TRUST=1
  docker push myimage:v1     # Auto-signs on push
  docker pull myimage:v1     # Verifies signature on pull

Admission Controllers for Signature Enforcement:
  
  # Cosign + Kyverno policy in Kubernetes:
  apiVersion: kyverno.io/v1
  kind: ClusterPolicy
  metadata:
    name: verify-image-signatures
  spec:
    validationFailureAction: enforce
    rules:
    - name: check-image-signature
      match:
        resources:
          kinds: [Pod]
      verifyImages:
      - imageReferences: ["registry.example.com/myapp:*"]
        attestors:
        - count: 1
          entries:
          - keys:
              publicKeys: |-
                -----BEGIN PUBLIC KEY-----
                ... (cosign.pub content) ...
                -----END PUBLIC KEY-----

SBOM (Software Bill of Materials):
  List of all components and dependencies in a container image.
  
  # Generate SBOM with Syft
  syft myapp:v1.2.3 -o spdx-json > sbom.json
  
  # Attach SBOM to image with Cosign
  cosign attach sbom --sbom sbom.json myapp:v1.2.3
  
  # Verify and retrieve SBOM
  cosign verify-attestation --type spdx myapp:v1.2.3

10. REGISTRY ACCESS CONTROL AND AUTHENTICATION
================================================================================

Authentication Methods:

  1. USERNAME + PASSWORD / TOKEN:
     Most registries. Tokens preferred over passwords (scoped, revocable).
     docker login -u user --password-stdin
  
  2. CLOUD IAM (ECR, GCR, ACR):
     Authenticate with cloud credentials (AWS, GCP, Azure).
     No separate user management — reuse existing IAM.
     Best for cloud-native workflows.
  
  3. OIDC / WORKLOAD IDENTITY (GitHub Actions, etc.):
     No long-lived secrets. CI runner gets short-lived token via OIDC.
     Proves identity via the OIDC flow.
     Best practice for modern CI/CD.
  
  4. SERVICE ACCOUNTS / ROBOT ACCOUNTS:
     Non-human accounts for CI/CD systems.
     Docker Hub: Access Tokens
     Harbor: Robot accounts
     ECR: IAM Roles for service accounts

Kubernetes Image Pull Secrets:
  
  # Create secret from docker config:
  kubectl create secret docker-registry regcred \
    --docker-server=myregistry.example.com \
    --docker-username=user \
    --docker-password=password \
    --docker-email=user@example.com
  
  # Reference in Pod spec:
  spec:
    imagePullSecrets:
    - name: regcred
    containers:
    - image: myregistry.example.com/myapp:v1
  
  # Or attach to ServiceAccount (applies to all Pods using that SA):
  kubectl patch serviceaccount default \
    -p '{"imagePullSecrets": [{"name": "regcred"}]}'
  
  # For ECR: Use Amazon ECR credential helper or IAM node role

Authorization Levels:
  Registry → Namespaces/Projects → Repositories
  
  Common roles:
  - Admin: Full access including delete
  - Developer/Writer: Push images
  - Reader/Puller: Pull images only
  - Scanner: Trigger vulnerability scans

11. IMAGE RETENTION POLICIES
================================================================================

Why Retention Policies:
  Images accumulate over time. Without cleanup:
  - Storage costs grow unbounded
  - Old, vulnerable images remain accessible
  - Registry becomes slow with thousands of images
  
  Best practice: Keep N most recent versions, keep tagged release versions,
  delete untagged/intermediate images.

ECR Lifecycle Policy:
  
  {
    "rules": [
      {
        "rulePriority": 1,
        "description": "Keep last 10 images",
        "selection": {
          "tagStatus": "tagged",
          "tagPrefixList": ["v"],
          "countType": "imageCountMoreThan",
          "countNumber": 10
        },
        "action": {
          "type": "expire"
        }
      },
      {
        "rulePriority": 2,
        "description": "Delete untagged images older than 1 day",
        "selection": {
          "tagStatus": "untagged",
          "countType": "sinceImagePushed",
          "countUnit": "days",
          "countNumber": 1
        },
        "action": {
          "type": "expire"
        }
      }
    ]
  }
  
  # Apply policy:
  aws ecr put-lifecycle-policy \
    --repository-name my-app \
    --lifecycle-policy-text file://policy.json

Harbor Garbage Collection:
  
  # Harbor > Administration > Garbage Collection
  # Schedule: Daily/Weekly or manual trigger
  
  # Also tag retention rules:
  # Keep last 10 tags matching "v*"
  # Delete tags older than 90 days

Docker Hub:
  # Free accounts: Limited to 1 private repo
  # Pro/Team: Set retention policies in Hub UI

General Retention Strategy:
  
  KEEP:
  - All semantically versioned release tags (v1.2.3)
  - Last N (e.g., 10) builds from main branch
  - Tags from the last 30 days
  
  DELETE:
  - Untagged (dangling) images
  - PR/branch images older than N days
  - SHA tags older than N weeks (keep the corresponding versioned tag)

12. REGISTRY MIRRORS AND PROXIES
================================================================================

Why Use Registry Mirrors:
  - PERFORMANCE: Pull from geographically close mirror
  - RATE LIMITS: Avoid Docker Hub rate limits in CI
  - AIR-GAPPED: No internet access, use internal mirror
  - CACHING: Save bandwidth with pull-through cache
  - CONTROL: Review and approve images before use

Types:

  PULL-THROUGH CACHE:
    Acts as transparent proxy. First pull fetches from upstream, caches locally.
    Subsequent pulls served from cache.
    
    Ideal for: Avoiding Docker Hub rate limits in CI pipelines.
  
  MIRROR:
    Pre-populated copy of upstream registry.
    Must explicitly sync (not transparent).
  
  PROXY:
    Routes requests to multiple upstreams based on rules.
    Harbor supports acting as proxy cache for Docker Hub, ECR, etc.

Configure Docker Daemon to Use Mirror:
  
  # /etc/docker/daemon.json
  {
    "registry-mirrors": [
      "https://my-mirror.example.com",
      "https://mirror.gcr.io"          # Google's Docker Hub mirror
    ]
  }
  
  # Restart Docker:
  sudo systemctl restart docker

Harbor as Pull-Through Cache:
  # In Harbor: Admin > Registries > New Endpoint
  # Add Docker Hub, ECR, GCR as upstream
  # Create project with "Proxy cache" enabled
  # Team uses: harbor.example.com/dockerhub-proxy/library/ubuntu:22.04
  # Harbor transparently fetches from Docker Hub, caches

ECR Pull-Through Cache:
  # AWS ECR can mirror Docker Hub, Quay.io, GCR
  # One-time setup in ECR console
  # Then pull as: 123456789.dkr.ecr.us-east-1.amazonaws.com/docker-hub/library/ubuntu

13. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is a container registry and how does it fit into a CI/CD pipeline?
A: A container registry is a service for storing and distributing container
   images — similar to what npm registry is for JavaScript packages or PyPI
   for Python.
   
   In a CI/CD pipeline:
   1. CI system checks out code on a commit/PR
   2. docker build creates an image (with a unique tag — usually git SHA)
   3. Run tests against the image or in separate container
   4. docker push uploads the image to the registry
   5. Deployment system (K8s) pulls the image and deploys it
   
   This creates an immutable artifact: the exact same image that passed CI
   is what gets deployed to production. There's no risk of "build differently
   on the production server."
   
   Choice of registry depends on cloud provider (ECR for AWS, GCR for Google,
   ACR for Azure) and requirements (public vs private, scanning, RBAC).

Q2: Why should you avoid using "latest" as a production image tag?
A: The "latest" tag is mutable — it points to whatever image was last pushed
   with that tag. This creates several problems in production:
   
   1. NON-DETERMINISTIC DEPLOYMENTS: Rolling out to a new server weeks later
      may deploy a different image than what you tested.
   
   2. CAN'T ROLL BACK: If latest points to a broken release, you can't roll
      back to a previous "latest" — there's no way to reference it.
   
   3. NO AUDIT TRAIL: You can't tell from a deployment manifest what code
      is actually running.
   
   4. CACHE CONFUSION: Docker may cache "latest" and serve a stale image
      even when a newer version exists.
   
   Best practice:
   - Use git SHA tags: myapp:sha-abc1234 (automatic, unique, traceable)
   - Or SemVer: myapp:v1.2.3 (human-readable, meaningful)
   - Enable tag immutability on the registry to enforce this
   - Reserve "latest" for local development only

Q3: How does authentication work for private registries in Kubernetes?
A: Kubernetes needs credentials to pull images from private registries.
   
   Approach 1: imagePullSecrets (universal):
   - Create a Kubernetes Secret of type docker-registry:
     kubectl create secret docker-registry regcred \
       --docker-server=myregistry.com --docker-username=user --docker-password=pass
   - Reference in Pod spec: spec.imagePullSecrets: [{name: regcred}]
   - Or attach to ServiceAccount to apply to all Pods in namespace
   
   Approach 2: Node-level credentials (cloud-managed clusters):
   - EKS: Attach IAM role with AcrPull permission to node group
     - Nodes authenticate to ECR automatically via instance metadata
   - GKE: Default service account has pull access to GCR in same project
   - AKS: Assign AcrPull role to AKS managed identity for ACR
   
   Approach 3: Cloud IAM + IRSA/Workload Identity (pod-level for EKS/GKE):
   - Each pod gets its own IAM identity
   - Least privilege: only specific pods can pull specific repos
   - No secrets to manage
   
   Best practice for cloud workloads: Use cloud-native IAM (option 2/3) rather
   than managing credentials as Kubernetes secrets.

Q4: What is image signing and why is it important?
A: Image signing cryptographically ensures that an image:
   1. Comes from a trusted source (not tampered with)
   2. Hasn't been modified between build and deployment (integrity)
   
   Without signing, an attacker who compromises the registry or network could
   swap images. A malicious image could be deployed undetected.
   
   The modern standard is Cosign (Sigstore):
   - Build image and push to registry
   - Sign: cosign sign --key cosign.key registry.example.com/myapp:v1
   - Signature stored as an OCI artifact alongside the image
   - Verify: cosign verify --key cosign.pub registry.example.com/myapp:v1
   
   In Kubernetes, admission controllers (Kyverno, OPA/Gatekeeper) can enforce
   that only signed images from trusted keys can run.
   
   Keyless signing with OIDC: CI/CD gets an OIDC identity token from GitHub
   Actions; cosign uses that to sign without a private key. Signatures are
   recorded in Rekor (public transparency log).

Q5: How do you manage image retention and avoid storage cost explosion?
A: Without policies, registries grow indefinitely. Key strategies:
   
   1. LIFECYCLE POLICIES (automated):
      - ECR: Put lifecycle policy JSON to delete old images by count or age
      - Harbor: Tag retention rules + scheduled garbage collection
      - GCR: Use Container Registry retention policies
   
   2. TAGGING STRATEGY:
      - PR/branch images: Delete after 7-30 days (short-lived)
      - Main branch images: Keep last 20 by count
      - Release tags (v1.2.3): Keep indefinitely
   
   3. CLEAN UNTAGGED IMAGES:
      - When rebuilding with same tag, old image becomes "dangling" (untagged)
      - Delete untagged images older than 1 day
   
   4. SEPARATE REPOS:
      - dev/: Short retention
      - staging/: Medium retention
      - prod/: Long retention (or never delete)
   
   Example ECR policy:
   - Rule 1: Keep last 10 images with "v" prefix (releases)
   - Rule 2: Keep last 5 images with any tag (dev builds)
   - Rule 3: Delete untagged images older than 1 day
