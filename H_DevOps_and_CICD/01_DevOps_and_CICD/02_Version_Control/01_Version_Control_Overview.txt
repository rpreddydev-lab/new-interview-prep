1. WHAT IS VERSION CONTROL?
================================================================================

Version Control System (VCS):
  A system that records changes to files over time, enabling you to:
  - Track the history of every change
  - Revert files or entire projects to previous states
  - Compare changes over time
  - See who modified what and when
  - Collaborate with multiple people simultaneously
  - Recover from mistakes

Also called:
  - Source Control
  - Revision Control
  - Source Code Management (SCM)

Why It's Critical:
  Without version control:
  - "final_version_v3_REALLY_FINAL_use_this.py" file naming chaos
  - No record of why a change was made
  - Can't collaborate without overwriting each other's work
  - No ability to safely experiment
  - Can't audit who made a breaking change

2. TYPES OF VERSION CONTROL SYSTEMS
================================================================================

A. LOCAL VERSION CONTROL
   ----------------------
   Files stored on a single developer's machine.
   Example: RCS (Revision Control System)
   
   Problems:
   - No collaboration capability
   - Single point of failure (if machine dies, history lost)
   - No backup

B. CENTRALIZED VERSION CONTROL (CVCS)
   -------------------------------------
   Single central server holds the repository.
   Developers checkout from and commit to the central server.
   
   Examples: Subversion (SVN), Perforce (Helix Core), CVS
   
   Advantages:
   - Central admin can see all activity
   - Simple model for small teams
   
   Problems:
   - Single point of failure (server goes down = no one can work)
   - Network required to commit or view history
   - Slow operations (everything goes through server)
   - Branching is expensive/painful in SVN
   - Trunk-based development forced (branching too hard)

C. DISTRIBUTED VERSION CONTROL (DVCS)
   -------------------------------------
   Every developer has a full copy of the repository (history and all).
   Operations are local and fast. Sync with remote when needed.
   
   Examples: Git, Mercurial (Hg), Bazaar
   
   Advantages:
   - Full repository available offline
   - Fast local operations
   - Multiple backups (every clone is a backup)
   - Flexible branching and merging
   - Multiple workflows possible (centralized, peer-to-peer, hierarchical)
   - Best for open source collaboration

   Git specific:
   - Linus Torvalds created Git in 2005 for Linux kernel development
   - Replaced BitKeeper after licensing dispute
   - Designed for speed, distributed workflows, and data integrity

CVCS vs DVCS:
  Feature                | CVCS (SVN)         | DVCS (Git)
  -----------------------|--------------------|-----------------------------------
  Repository copy        | Server only        | Full copy on each client
  Network required       | For all operations | Only for push/pull
  Speed                  | Slow (network)     | Fast (local)
  Branching              | Expensive          | Cheap (just a pointer)
  History                | Server only        | Fully local
  Single point of failure| Yes                | No (every clone = backup)
  Learning curve         | Lower              | Higher

3. WHY VERSION CONTROL IS ESSENTIAL FOR DEVOPS
================================================================================

"Everything as Code" Foundation:
  DevOps requires that infrastructure, configuration, pipelines, and policies
  be stored in version control. Without VCS, none of the following are possible:

CI/CD Pipelines:
  - Every pipeline is triggered by a commit/push to a VCS
  - Pipeline configuration (Jenkinsfile, .github/workflows) lives in Git
  - Artifact versions traced back to git commits (git SHA → build artifact)

Infrastructure as Code:
  - Terraform, Helm charts, Kubernetes manifests → stored in Git
  - Changes to infrastructure go through PR review
  - Audit trail: who approved the infrastructure change

Configuration Management:
  - Ansible playbooks, Chef recipes, Puppet manifests → in Git
  - Configuration changes tracked and reviewed

GitOps:
  - Git is the source of truth for the desired state of infrastructure
  - ArgoCD/FluxCD watches Git and syncs cluster state to match
  - The VCS IS the operational interface

Security and Compliance:
  - Immutable audit log of every change
  - Who changed what, when, and why (commit messages)
  - PR reviews provide separation of duties
  - Branch protection enforces code review requirements

4. CORE CONCEPTS
================================================================================

Repository (Repo):
  The database that stores all files and their history.
  Local repo: On your machine.
  Remote repo: On a server (GitHub, GitLab, Bitbucket).

Working Tree / Working Directory:
  The files you're actively working with on disk.
  These are the "checked out" versions of files.

Staging Area (Index):
  Git's unique concept — a preparation area for commits.
  You "stage" changes before committing them.
  Allows you to commit only specific changes from a working directory.

Commit:
  A snapshot of the staged files at a point in time.
  Includes: message, author, timestamp, parent commit hash.
  Content-addressable: each commit has a SHA-1 hash (40 hex chars).
  Example: a3f8d92b1c0f4e5d7a9b2c3e4f5a6b7c8d9e0f1

Branch:
  A lightweight, movable pointer to a commit.
  Creating a branch is just writing a 41-byte file.
  "Branching is cheap in Git" — no copying of files.

HEAD:
  A special pointer that indicates which branch/commit you're currently on.
  HEAD → main → abc123 (commit hash)
  "Detached HEAD" state: HEAD points directly to a commit, not a branch.

Remote:
  A reference to another repository (usually on a server).
  `origin` is the conventional name for the primary remote.

Merge vs Rebase:
  Merge:
    - Combines two branches by creating a merge commit
    - Preserves the complete history (shows branching and merging)
    - Safer (non-destructive)
    - Creates "merge commits" that can clutter history
    
  Rebase:
    - Moves commits from one branch onto the tip of another
    - Creates a linear, cleaner history
    - Rewrites commit history (changes commit SHAs)
    - Never rebase commits that have been pushed to a shared remote
    - "Golden Rule of Rebasing"

Clone vs Fork:
  Clone: Copy a repository to your local machine.
  Fork: Copy a repository to your account on GitHub/GitLab (for contributing
        to projects where you don't have push access).

Pull vs Fetch:
  Fetch: Download remote changes but don't integrate (safe).
  Pull: Fetch + merge (or rebase). Integrates remote changes immediately.

Tags:
  Permanent pointers to specific commits (unlike branches, tags don't move).
  Used for releases: v1.0.0, v2.1.3.
  
  Lightweight tag: Just a pointer to a commit.
  Annotated tag: Full object with tagger name, date, message, GPG signature.

5. GIT vs OTHER VCS
================================================================================

Git vs SVN (Subversion):

Feature                 | Git                    | SVN
------------------------|------------------------|---------------------------
Model                   | Distributed            | Centralized
Branching               | O(1), instant          | Copy operation, slow
Offline work            | Full history offline   | Need server connection
History                 | Graph (DAG)            | Linear (revision numbers)
Staging area            | Yes (index)            | No
Data model              | Snapshots              | Differences (patches)
Rename tracking         | Content-based          | Explicit rename command
Large file support      | Needs Git LFS          | Better natively
Learning curve          | Steeper                | Gentler
Enterprise adoption     | Dominant               | Legacy systems

Git vs Perforce (p4 / Helix Core):
  - Perforce still used in gaming (large binary assets: textures, 3D models)
  - Git LFS handles this now (Large File Storage)
  - Perforce has better locking for binary files (prevent merge conflicts)
  - Git is overwhelmingly dominant for text/code

Git vs Mercurial (Hg):
  - Very similar concepts (both DVCS)
  - Git "won" the market (GitHub, ecosystem)
  - Mercurial: simpler, more consistent command syntax
  - Facebook used Mercurial at scale (then built "Eden" VCS)

6. HOSTING PLATFORMS
================================================================================

GitHub:
  - Largest code hosting platform (100M+ developers, 300M+ repositories)
  - Features: GitHub Actions (CI/CD), GitHub Packages, GitHub Pages,
    GitHub Copilot, Dependabot, Code Scanning, Secret Scanning
  - Acquisition: Microsoft acquired GitHub in 2018 for $7.5B
  - GitHub.com (public/private) + GitHub Enterprise (self-hosted)

GitLab:
  - Complete DevOps platform (not just VCS)
  - Features: Built-in CI/CD, Container Registry, Package Registry,
    Security Scanning, Issue Tracking, Wiki, Monitoring
  - GitLab.com (SaaS) + GitLab Self-Managed
  - Open source (Community Edition)
  - "One platform for the entire DevOps lifecycle"

Bitbucket:
  - Atlassian product (integrates with Jira, Confluence)
  - Features: Bitbucket Pipelines (CI/CD), Code Insights, Branch Permissions
  - Bitbucket Cloud + Bitbucket Data Center (self-hosted)
  - Free for small teams (up to 5 users on free tier)

Azure DevOps (Azure Repos):
  - Microsoft's platform, integrates with Azure services
  - Supports both Git and TFVC (Team Foundation Version Control)
  - Features: Azure Pipelines (CI/CD), Azure Boards, Azure Artifacts
  - Common in Microsoft-stack enterprise environments

Choosing a Platform:
  - Startups / Open Source: GitHub (ecosystem, community)
  - Enterprise (complete platform): GitLab
  - Microsoft/Azure shops: Azure DevOps
  - Jira/Atlassian shops: Bitbucket

7. BEST PRACTICES
================================================================================

Commit Best Practices:
  1. Commit early, commit often (small, atomic commits)
  2. Every commit should be a single logical change
  3. Write meaningful commit messages
  4. Never commit broken code (it blocks others)
  5. Don't commit generated files, build artifacts, or secrets

Commit Message Format (Conventional Commits):
  Format: <type>(<scope>): <description>
  
  Types:
    feat:     New feature
    fix:      Bug fix
    docs:     Documentation changes
    style:    Formatting, no code change
    refactor: Code refactoring
    test:     Adding or modifying tests
    chore:    Build process, dependencies, tooling
    perf:     Performance improvements
    ci:       CI/CD changes
  
  Examples:
    feat(auth): add OAuth2 Google login
    fix(payment): correct rounding error in cart totals
    docs(api): update authentication endpoint documentation
    chore(deps): upgrade spring-boot to 3.2.1
    
  Benefits: Auto-generate changelogs, semantic versioning automation

.gitignore:
  - Tells Git which files to ignore (never track)
  - Common patterns:
    node_modules/     # Dependencies
    .env              # Secrets/environment variables
    *.log             # Log files
    target/           # Build outputs (Maven)
    dist/             # Build outputs (npm)
    .DS_Store         # macOS metadata
    *.class           # Java bytecode
  - Generate with: gitignore.io or GitHub's templates

Branch Naming Conventions:
  feature/<ticket-id>-brief-description    (feature/JIRA-123-add-user-auth)
  fix/<ticket-id>-brief-description        (fix/JIRA-456-fix-login-timeout)
  hotfix/<description>                     (hotfix/critical-payment-bug)
  release/<version>                        (release/v2.1.0)
  chore/<description>                      (chore/update-dependencies)

Repository Structure Best Practices:
  - README.md: Project description, setup instructions, how to contribute
  - CONTRIBUTING.md: Contribution guidelines
  - .github/ or .gitlab/: CI/CD configs, PR templates, issue templates
  - docs/: Architecture docs, ADRs
  - src/ or app/: Source code
  - tests/: Test files
  - infrastructure/ or terraform/: IaC files
  - Makefile: Common development commands

Security Best Practices:
  - NEVER commit secrets, API keys, passwords
  - Use pre-commit hooks with detect-secrets or git-secrets
  - Enable secret scanning on GitHub/GitLab
  - Sign commits with GPG keys (especially for production deployments)
  - Require signed commits on protected branches
  - Rotate any secrets accidentally committed immediately (assume compromised)

8. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is the difference between Git and GitHub?
A: Git is a distributed version control system — the tool you install and run
   locally to track file changes. GitHub is a web-based hosting platform for
   Git repositories, with additional features like pull requests, code review,
   issue tracking, and GitHub Actions for CI/CD. GitHub is to Git what Gmail
   is to email — a service built on top of the underlying protocol.
   
   Other hosts: GitLab, Bitbucket, Azure Repos.

Q2: What is the difference between `git merge` and `git rebase`?
A: Both integrate changes from one branch into another, but differently.
   
   Merge creates a new "merge commit" joining two branch histories. The history
   shows exactly what happened (when branches were created, when merged). Safe
   for shared/public branches.
   
   Rebase moves commits onto the tip of the target branch, creating a linear
   history as if the branches were never forked. It rewrites commit SHAs.
   Cleaner history, but "The Golden Rule": never rebase commits already pushed
   to a shared remote because it rewrites history that others have pulled.
   
   Common pattern: Rebase feature branch on main before merging for clean history.

Q3: What is the difference between `git fetch` and `git pull`?
A: Git fetch downloads remote changes to your local repository without
   integrating them into your working branch. Safe — doesn't touch your files.
   
   Git pull does fetch + merge (or rebase) in one command. It immediately
   integrates remote changes into your current branch.
   
   Best practice: Use fetch to review changes before integrating, especially
   on shared branches. Use pull when you're confident merging is safe.

Q4: Explain the Git staging area (index).
A: The staging area (also called the "index") is a preparation area between
   your working directory and the repository. When you `git add` a file, it
   goes to the staging area. When you `git commit`, only staged changes are
   committed.
   
   This allows you to make many changes but commit them selectively. Example:
   You fix a bug AND add a new feature. You can stage only the bug fix files
   and commit them separately from the feature changes.
   
   `git add -p` (interactive staging) lets you stage specific HUNKS within a
   file, not just entire files.

Q5: What happens when you run `git commit`?
A: Git creates a commit object containing:
   - A tree object representing the state of the staging area (snapshot of files)
   - Parent commit(s) reference(s) (SHA hash)
   - Author and committer information (name, email, timestamp)
   - The commit message
   
   Git computes a SHA-1 hash of the entire commit content. This hash uniquely
   identifies the commit and is content-addressable (if anything changes, the
   hash changes). The branch pointer advances to point to the new commit.

Q6: How would you undo the last commit in Git?
A: Several options depending on the situation:
   
   `git reset --soft HEAD~1`: Undoes the commit but keeps changes staged.
   Good for: committed too early, want to amend the commit message.
   
   `git reset --mixed HEAD~1` (default): Undoes commit, unstages changes,
   but keeps changes in working directory.
   Good for: need to reorganize or add more changes before committing.
   
   `git reset --hard HEAD~1`: Undoes commit AND discards all changes.
   Dangerous: data loss possible. Good for: completely undo a bad commit.
   
   `git revert HEAD`: Creates a NEW commit that undoes the previous commit.
   Safe for shared branches because it doesn't rewrite history.
   
   Rule: Use reset for local/private branches. Use revert for shared branches.

9. QUICK REFERENCE CHEAT SHEET
================================================================================

VCS Types: Local → Centralized (SVN) → Distributed (Git)
Git advantage: Full local copy, offline work, fast branching

Key Git Areas:
  Working Directory → [git add] → Staging Area → [git commit] → Local Repo
  Local Repo → [git push] → Remote Repo
  Remote Repo → [git pull/fetch] → Local Repo

Core Concepts:
  Repo: Database of files + history
  Commit: Snapshot with SHA-1 hash
  Branch: Pointer to a commit (cheap!)
  HEAD: Current position pointer
  Remote: Reference to another repository (origin)

merge vs rebase:
  merge: Preserves history, creates merge commit (safe for shared branches)
  rebase: Linear history, rewrites SHAs (never on shared branches)

fetch vs pull:
  fetch: Download only (safe)
  pull: Download + integrate (merges or rebases)

Undo operations:
  reset --soft: Undo commit, keep staged
  reset --mixed: Undo commit, unstage (keep files)
  reset --hard: Undo commit, discard changes (dangerous)
  revert: New commit that undoes previous (safe for shared)

Conventional Commits: feat / fix / docs / style / refactor / test / chore / ci

Platforms: GitHub (ecosystem) | GitLab (DevOps platform) | Bitbucket (Atlassian) | Azure Repos (Microsoft)
