1. INCIDENT MANAGEMENT OVERVIEW
================================================================================

What is Incident Management?
  The process for detecting, responding to, resolving, and learning from
  unplanned service disruptions.
  
  Good incident management:
  - Minimizes customer impact (reduces MTTR)
  - Enables organized response under pressure
  - Captures learnings to prevent recurrence
  - Builds institutional knowledge

Key Metrics:
  MTTD    Mean Time to Detect       Time from incident start to detection
  MTTR    Mean Time to Resolve      Time from detection to resolution
  MTTF    Mean Time to Failure      How long until next failure
  MTBF    Mean Time Between Failure MTTF for repairable systems
  
  Goal: Reduce MTTD (better alerting) and MTTR (better runbooks, automation).

SRE vs Traditional Operations:
  
  ┌───────────────────────────┬────────────────────────────────────┐
  │ Traditional Ops           │ SRE                                │
  ├───────────────────────────┼────────────────────────────────────┤
  │ React to failures         │ Engineer for reliability proactively│
  │ Manual operations (toil)  │ Automate toil away                 │
  │ 100% uptime goal          │ Error budget: accept some downtime  │
  │ Ops and Dev are separate  │ SREs are engineers who do ops      │
  │ Post-mortem = blame        │ Post-mortem = blameless learning   │
  └───────────────────────────┴────────────────────────────────────┘

2. INCIDENT SEVERITY AND CLASSIFICATION
================================================================================

Standard Severity Levels:
  
  ┌──────┬─────────────────────────────────────────────┬───────────────────┐
  │ SEV  │ Impact                                       │ Response SLA      │
  ├──────┼─────────────────────────────────────────────┼───────────────────┤
  │  P0  │ Complete outage. All users affected.         │ Page NOW. 5 min   │
  │      │ Revenue-impacting. Core services down.       │ response.         │
  ├──────┼─────────────────────────────────────────────┼───────────────────┤
  │  P1  │ Major degradation. Large % of users          │ Page within 15    │
  │      │ affected. Performance severely degraded.     │ minutes. Activate │
  │      │ Critical feature broken.                     │ war room.         │
  ├──────┼─────────────────────────────────────────────┼───────────────────┤
  │  P2  │ Partial outage. Subset of users affected.    │ On-call responds  │
  │      │ Workaround exists. Non-critical features.    │ in 1 hour.        │
  ├──────┼─────────────────────────────────────────────┼───────────────────┤
  │  P3  │ Minor issue. Low user impact. Not urgent.    │ Ticket created.   │
  │      │ Cosmetic issues, non-critical bugs.          │ Next sprint.      │
  └──────┴─────────────────────────────────────────────┴───────────────────┘

Severity Assessment Questions:
  - How many users are affected? (all / many / some / few)
  - Is revenue/data at risk?
  - Does a workaround exist?
  - Is the issue growing or stable?
  - What is the business impact (during business hours vs 3am Sunday)?

Upgrading Severity:
  Start at lower severity, upgrade if:
  - Issue isn't resolved in expected timeframe
  - More users become affected
  - Data integrity concern identified
  - Multiple services start failing (cascade)

3. INCIDENT RESPONSE LIFECYCLE
================================================================================

Phase 1: DETECT
  
  Alert fired (Prometheus/Datadog/PagerDuty)
  OR
  Customer reports issue (support ticket, Twitter/social, internal Slack)
  OR
  Automated health check fails (synthetic monitoring)
  
  Goal: Minimize MTTD.
  Techniques: Good alerting on SLO burn rate, synthetic monitoring globally,
              anomaly detection, real-time customer reporting channels.

Phase 2: TRIAGE
  
  On-call engineer wakes up, evaluates:
  1. Confirm the incident is real (not flapping alert)
  2. Determine scope: which services, how many users
  3. Assign severity level (P0/P1/P2/P3)
  4. Declare incident and open incident channel (#incident-YYYY-MM-DD-short-desc)
  
  Triage SLAs:
  P0: Immediately declare, page additional responders
  P1: Triage within 15 minutes
  P2: Triage within 1 hour

Phase 3: RESPONSE
  
  Roles:
  Incident Commander (IC):  Overall coordination. Delegates work. Manages comms.
                             Does NOT do technical investigation (keeps overview).
  Scribe/Chronicler:        Takes notes in real time (timeline, decisions, actions).
  Technical Lead(s):        Debug and fix the problem.
  Communications Lead:      Updates stakeholders, status page. Shields tech from noise.
  
  Activities:
  - Investigate: Dashboards → Logs → Traces → Source of truth
  - Hypothesize: Form theories about root cause
  - Test: Small changes to confirm hypothesis
  - Fix: Apply the fix (rollback, config change, scale, hotfix)
  - Verify: Confirm metrics return to normal

Mitigation vs Fix:
  Mitigation:   Stops the bleeding. Reduces user impact immediately.
                Rollback a deployment. Disable a feature flag.
                Route traffic away from a bad server. Scale up.
  
  Fix:          Addresses root cause. May take longer.
                Fix the bug, add the index, increase connection pool.
  
  Prioritize mitigation first, then root cause analysis.

Phase 4: RESOLVE
  
  - Metrics return to baseline (green dashboards)
  - Confirm with user reports / support queue decreasing
  - Close the incident channel
  - Set reminder for post-mortem (within 24-72 hours while fresh)
  - Update status page: "Resolved - all systems operational"

Phase 5: POST-MORTEM
  See Section 7.

4. ON-CALL PRACTICES
================================================================================

On-Call Goals:
  - Ensure fast response to P0/P1 alerts 24/7
  - Distribute burden fairly across team
  - Prevent on-call burnout
  - Continuously improve alert quality

On-Call Rotations:
  Primary:    First responder. Responsible for all pages during their shift.
  Secondary:  Backup. Escalate to if primary doesn't acknowledge in X minutes.
  Manager:    Final escalation for organizational decisions.
  
  Weekly rotations are most common. Follow-the-sun for global teams.
  
  Handoff: Primary calls/Slacks incoming primary with:
  - Active incidents
  - Recent deployments
  - Known fragile services
  - Anything unusual from the week

On-Call Hygiene:
  Keep alert volume low — < 2 pages per day max during on-call.
  If you're getting 10 pages/night, fix alerts before fixing systems.
  
  Track per-on-call metrics:
  - Number of pages per shift
  - Pages outside business hours (nights/weekends)
  - Alert action rate (pages that required action vs noise)
  
  Team on-call review: Monthly meeting to review:
  - Top paging alerts
  - Recurring incidents
  - Runbook quality
  - Opportunities to reduce toil

Compensation/Culture:
  On-call should be recognized (financial compensation or time-off in lieu).
  Reasonable on-call frequency: no more than once every 3-4 weeks per person.
  If on-call is overwhelming, that's a staffing/architecture/alert quality problem.

5. PAGERDUTY AND OPSGENIE
================================================================================

PagerDuty Core Concepts:
  Service:          Maps to a team's responsibility (payment-service).
  Escalation Policy: Who to page and when (primary → secondary → manager).
  Schedule:         On-call rotation schedule (who is on-call when).
  Integration:      Connect Prometheus/Datadog/etc. to PagerDuty.

PagerDuty Setup Flow:
  1. Create Service (e.g., "Payment Service")
  2. Create Schedule (on-call rotation — weekly by default)
  3. Create Escalation Policy:
     Level 1: Page primary on-call (acknowledge within 5 minutes)
     Level 2: Page secondary (if primary doesn't ack in 5 min)
     Level 3: Page on-call manager (if secondary doesn't ack in 10 min)
  4. Assign Escalation Policy to Service
  5. Add Integrations (Alertmanager → PagerDuty):
     Use PagerDuty Events API v2

Alertmanager → PagerDuty Integration:
  # alertmanager.yml:
  receivers:
  - name: 'pagerduty-critical'
    pagerduty_configs:
    - routing_key: '<PAGERDUTY_INTEGRATION_KEY>'
      severity: '{{ if eq .CommonLabels.severity "critical" }}critical{{ else }}warning{{ end }}'
      description: '{{ .CommonAnnotations.summary }}'
      details:
        firing: '{{ .Alerts.Firing | len }}'
        runbook: '{{ .CommonAnnotations.runbook_url }}'
        environment: '{{ .CommonLabels.environment }}'
      client: 'Prometheus Alertmanager'
      client_url: 'https://alertmanager.mydomain.com'
  
  route:
    receiver: 'pagerduty-critical'
    routes:
    - match:
        severity: critical
      receiver: 'pagerduty-critical'
    - match:
        severity: warning
      receiver: 'slack-warnings'

OpsGenie Setup:
  Teams:         Groups of users.
  Schedules:     On-call rotations per team.
  Escalations:   Auto-escalation chains.
  Integrations:  Prometheus, Grafana, Datadog connectors.
  
  OpsGenie API integration with Alertmanager:
  receivers:
  - name: 'opsgenie-critical'
    opsgenie_configs:
    - api_key: '<OPSGENIE_API_KEY>'
      message: '{{ .CommonAnnotations.summary }}'
      description: '{{ .CommonAnnotations.description }}'
      priority: 'P{{ if eq .CommonLabels.severity "critical" }}1{{ else }}2{{ end }}'
      tags: 'env:{{ .CommonLabels.environment }},service:{{ .CommonLabels.service }}'

6. INCIDENT COMMUNICATION
================================================================================

Incident Slack Channel Naming:
  #incident-2024-01-15-payment-outage
  
  Channel uses:
  - Real-time investigation communication
  - Link to dashboards, runbooks, PRs
  - Actions taken and decisions made
  - Timeline documented by scribe
  - Do NOT use for stakeholder communication (too noisy)

Status Page (Statuspage.io / Atlassian):
  External-facing page customers check during outages.
  
  Components: Map your services to status components.
    Payment Processing: [Operational | Degraded Performance | Partial Outage | Major Outage]
    User Authentication: [...]
    Checkout: [...]
  
  Update cadence during incident:
  - P0: Update every 15-30 minutes
  - P1: Update every 30-60 minutes
  
  Template:
  "We are investigating reports of [symptom]. Impact: [who/what is affected].
  We will provide an update in [X] minutes."

Stakeholder Communication:
  Who to notify: Engineering leadership, product managers, customer support, legal (if data).
  
  Format: Brief, factual, non-technical.
  "We are experiencing elevated error rates on the payment service.
  Approximately 20% of payment attempts are failing.
  Our on-call team is actively investigating.
  Next update in 30 minutes or sooner if resolved."
  
  Not: technical details, speculation about root cause (until confirmed).

Customer-Facing Communication:
  Use status page for public incidents.
  Support team uses templated responses.
  Never understate severity — loss of trust worse than the outage itself.

War Room:
  For P0/P1: Create Zoom/Meet call with all responders.
  Benefits: Faster than Slack back-and-forth. Real-time alignment.
  Scribe stays on call, takes notes → feeds into post-mortem later.

7. POST-MORTEM / BLAMELESS POST-INCIDENT REVIEW
================================================================================

What is a Blameless Post-Mortem?
  A written review of an incident focused on SYSTEMS, PROCESSES, and TOOLS —
  not individual blame.
  
  Principle: People made reasonable decisions given the information they had.
  Systems and processes should prevent individuals from making catastrophic errors.
  
  Why blameless?
  - Blame discourages honesty → people hide information → you can't learn
  - Root cause is almost always systemic (bad process, poor tooling, unclear runbook)
  - Blame doesn't prevent recurrence; system improvements do

Post-Mortem Structure:
  
  ┌──────────────────────────────────────────────────────────────────┐
  │ Incident Post-Mortem: Payment Service Outage — 2024-01-15        │
  ├──────────────────────────────────────────────────────────────────┤
  │ Severity: P0 | Duration: 47 minutes | Users Affected: ~15,000    │
  │ On-Call: Jane Doe | Incident Commander: John Smith               │
  ├──────────────────────────────────────────────────────────────────┤
  │ SUMMARY                                                          │
  │ A database migration introduced a missing index on the orders    │
  │ table, causing checkout queries to do full table scans.          │
  │ Payment service timed out, affecting 15,000 users for 47 minutes.│
  ├──────────────────────────────────────────────────────────────────┤
  │ TIMELINE (all times UTC)                                         │
  │ 10:15 — Migration deployed to production                         │
  │ 10:17 — Checkout latency begins increasing (not yet alerted)     │
  │ 10:23 — Alert fires: p99 latency > 5s                           │
  │ 10:28 — On-call engineer acknowledges, begins investigation      │
  │ 10:35 — Identifies DB slow query via APM                         │
  │ 10:39 — Confirms missing index via EXPLAIN ANALYZE               │
  │ 10:45 — Begins adding index (CONCURRENTLY to avoid table lock)   │
  │ 11:02 — Index built, latency normalizes                          │
  │ 11:05 — Incident resolved                                        │
  ├──────────────────────────────────────────────────────────────────┤
  │ ROOT CAUSE                                                        │
  │ Migration script added new query but did not add required index.  │
  │ Query reviewed in code review but index requirement was not       │
  │ obvious without query execution plan analysis.                    │
  ├──────────────────────────────────────────────────────────────────┤
  │ CONTRIBUTING FACTORS                                             │
  │ - No automated slow query detection in migration CI pipeline     │
  │ - Staging database has 1,000 rows; production has 50M rows        │
  │   → slow queries not detected in staging                         │
  │ - Alert threshold was too high (p99 > 5s) — should alert at 1s  │
  ├──────────────────────────────────────────────────────────────────┤
  │ WHAT WENT WELL                                                   │
  │ - APM flamegraph enabled rapid root cause identification         │
  │ - On-call runbook covered DB issues, had EXPLAIN ANALYZE commands│
  │ - Adding index CONCURRENTLY prevented additional table lock       │
  ├──────────────────────────────────────────────────────────────────┤
  │ ACTION ITEMS                                                     │
  │ Owner        | Action                                  | Due     │
  │ Jane Doe     | Add slow query check to migration CI    | 2024-01-22│
  │ John Smith   | Lower latency alert threshold to 1s     | 2024-01-17│
  │ DevOps Team  | Populate staging with production-size   | 2024-02-01│
  │              | anonymized data (or query plan testing) |          │
  └──────────────────────────────────────────────────────────────────┘

5 Whys Analysis:
  A technique to drill down to root cause.
  
  Why did payment service fail? → DB queries timed out
  Why did DB queries time out? → Full table scan on 50M row table
  Why was there a full table scan? → Missing index
  Why was the index missing? → Migration script didn't add it
  Why didn't we catch it? → Staging DB too small to show slow queries
  
  Root cause: No production-representative staging environment for DB queries.
  Fix: Anonymized data copy, or CI pipeline EXPLAIN ANALYZE testing.

Post-Mortem Meeting:
  Who: On-call responders, engineering leadership, product manager.
  When: 24-72 hours after incident (while details are fresh).
  Duration: 60-90 minutes max.
  
  Agenda:
  1. Walkthrough timeline (no interrupting/blaming — just facts)
  2. Identify contributing factors
  3. Confirm action items, assign owners, set due dates
  4. Open forum: what would have helped? what was confusing?

8. ERROR BUDGETS AND RELIABILITY ENGINEERING
================================================================================

Error Budget Concept:
  SLO: 99.9% availability = 0.1% error budget per 30 days = 43.2 min downtime.
  
  Error budget is the ALLOWED downtime.
  It's a negotiated agreement between SRE and product teams.

Error Budget Policy:
  If error budget is HEALTHY (> 50% remaining):
  - Ship features at normal pace
  - Deploy frequently
  - Take reliability risks to learn
  
  If error budget is BURNING FAST (< 25% remaining):
  - Slow down deployments
  - Focus on reliability improvements
  - No risky changes until budget recovers
  
  If error budget is EXHAUSTED (0% remaining):
  - Freeze feature deployments
  - All engineering focused on reliability
  - Must do root cause analysis and preventive work

Why Error Budgets Work:
  Aligns incentives: Product wants features, SRE wants reliability.
  Error budget = shared resource both sides want to protect.
  
  "Can we deploy this risky change today?"
  "We have 35% error budget remaining. If it causes an incident, we'll exhaust
  the budget. Let's canary deploy it instead."

SRE Toil Reduction:
  Toil = Manual, repetitive, operational work that doesn't provide lasting value.
  
  Examples of toil:
  - Manually restarting services when they OOM
  - Manually updating Kubernetes manifests with new image tags
  - Manually rotating secrets on a schedule
  - Manually provisioning new environments by clicking in consoles
  
  SRE goal: Spend < 50% of time on toil. Rest on engineering/automation.
  
  Automate toil: Kubernetes HPA, GitOps pipelines, External Secrets Operator.

9. RUNBOOK DESIGN
================================================================================

What is a Runbook?
  Step-by-step instructions for responding to a specific alert or incident.
  
  Goal: An engineer who has never seen this system before can follow the runbook
        and resolve the incident (or escalate correctly).

Good Runbook Structure:
  
  # Alert: HighErrorRatePaymentService
  
  ## Overview
  This alert fires when the payment service error rate exceeds 5% for 5 minutes.
  Typical causes: DB connectivity, external payment gateway issues, deployment bugs.
  
  ## Impact
  Users cannot complete checkout. ~$X revenue impact per minute at 100% error rate.
  
  ## Triage (5 minutes)
  1. Check service dashboard: https://grafana.mydomain.com/d/payment-service
  2. Check which endpoint is failing:
     ```
     kubectl logs -n payment -l app=payment-service --tail=50 | grep ERROR
     ```
  3. Determine error type: DB timeout? Gateway timeout? 500 from code?
  
  ## Remediation
  ### If DB connectivity issue:
  1. Check DB pod status: `kubectl get pods -n database`
  2. Check DB max connections: <SQL to run>
  3. If connection pool exhausted: restart payment service pods
     `kubectl rollout restart deployment/payment-service -n payment`
  4. If DB pod not running: escalate to DB team
  
  ### If recent deployment:
  1. Check last deployment: `kubectl rollout history deployment/payment-service`
  2. If deployment was within 1 hour, rollback:
     `kubectl rollout undo deployment/payment-service -n payment`
  3. Confirm rollback successful: `kubectl rollout status deployment/payment-service`
  
  ### If payment gateway issue:
  1. Check gateway status page: https://status.stripe.com
  2. If gateway outage: No action needed (automatic recovery when gateway recovers)
  3. If gateway timeout: Check circuit breaker status, may need to adjust timeout config
  
  ## Escalation
  - DB issues: Page database team (#oncall-database)
  - Payment gateway issues: Notify product team, update status page
  - Unknown cause after 15 minutes: Escalate to P0, page engineering manager

Runbook Best Practices:
  ✅ Link directly from alert annotation (runbook_url)
  ✅ Copy-pasteable commands (no manual variable substitution where possible)
  ✅ Clear escalation paths
  ✅ Update after every incident involving this service
  ✅ Include "expected normal state" for comparison
  ✅ Test runbooks in chaos engineering exercises

Runbook Automation:
  Many runbooks steps can be automated with "runbooks-as-code":
  - Auto-restart on OOM kill (K8s liveness probe)
  - Auto-scale on high CPU (HPA)
  - Auto-rollback on error rate spike (Flagger canary analysis)
  - Automated response with tools like Ansible Tower, Rundeck

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: Walk me through how you would handle a P0 incident.
A: First, when the alert fires and I acknowledge it:
   
   1. Declare the incident immediately:
      - Create #incident channel: #incident-2024-01-15-payment-down
      - Post initial message: "P0 declared — payment service errors spiking. Investigating."
      - Page Incident Commander if I can't handle it alone
      - Update status page: "We are investigating a payment processing issue"
   
   2. Triage and understand scope (first 5-10 minutes):
      - Check service dashboard: how many users affected, what's the error rate?
      - Was there a recent deployment? (first question — deployments cause most incidents)
      - Is it isolated to one region/availability zone or global?
      - What type of error: 500s? Timeouts? DB errors?
   
   3. Mitigation first, root cause second:
      - If recent deployment → rollback immediately (don't wait to confirm cause)
      - If resource exhaustion → scale up
      - If specific AZ is bad → shift traffic to healthy AZs
      - Goal: Stop user impact, then understand why
   
   4. Continuous communication:
      - Update incident channel with every finding and action
      - Scribe captures timeline
      - Comms lead updates status page every 15-30 min
   
   5. After resolution:
      - "All systems green, monitoring closely for 30 minutes"
      - Schedule post-mortem within 24 hours
   
   Key principle: Time to mitigate > time to perfect diagnosis.
   A rollback that takes 2 minutes beats a 30-minute investigation.

Q2: What makes a good post-mortem?
A: A good post-mortem drives systemic improvement while maintaining psychological safety.
   
   Characteristics of a GOOD post-mortem:
   
   Blameless: Focus on systems, processes, tools — not individuals.
   "The engineer didn't add the index" → "Our migration CI doesn't verify index requirements"
   This shift changes a blame moment into an actionable system improvement.
   
   Accurate timeline: Exact timestamps, not approximate. "Around 10:30" is less useful
   than "10:23 — alert fired, 10:28 — ack, 10:35 — root cause identified."
   
   Root cause depth (5 Whys): Don't stop at the proximate cause.
   "Missing index" is the proximate cause.
   "No production-representative staging" is the root cause.
   Fix the root cause, not just the symptom.
   
   Concrete action items: Every action item has an owner and a due date.
   "Team will improve testing" → not actionable.
   "Jane will add EXPLAIN ANALYZE check to migration CI — due 2024-01-22" → actionable.
   
   What Went Well section: Balance — it's not just about failures.
   Celebrating good decisions under pressure reinforces good behavior.
   
   Follow-through: Track action items in sprint planning. Post-mortem is useless
   if action items sit in a doc forever. Review completion at next on-call meeting.
   
   Bad post-mortem signs:
   - Ends with "engineer was more careful" → no systemic learning
   - Action items with no owner or "TBD" dates → won't get done
   - Only management attendees write it → missing ground truth from responders

Q3: How do you reduce on-call burden?
A: On-call burden comes from two main sources: alert noise and incident frequency.
   
   Reduce alert noise:
   - Audit all alerts: Every alert that fires should require human action.
     If it auto-resolves without action → delete or convert to ticket.
   - Alert on symptoms, not causes: "High error rate" (affects users) not "CPU > 80%"
     (might not matter). CPU high without user impact = noisy alert.
   - Alert on SLO burn rate, not individual thresholds.
   - Increase alert thresholds + duration requirements: p99 > 1s FOR 5 MINUTES.
     Not: p99 > 1s for 30 seconds (too flappy).
   - Review alert history monthly: What was the top-paging alert? Is it actionable?
   
   Reduce incident frequency (proactive reliability):
   - Invest in testing: More tests → fewer production bugs.
   - Canary deployments: Catch bad deploys before they hit 100% of users.
   - Chaos engineering: Find failure modes before they find you in production.
   - Capacity planning: Don't let services run at 90% capacity (no headroom).
   - Dependency health: Monitor external dependencies (if Stripe is down, alert teams).
   
   Improve MTTR (faster resolution when incidents do happen):
   - Keep runbooks current and copy-pasteable.
   - Automate common remediations (auto-restart, auto-scale).
   - Practice incident response (gamedays, fire drills).
   - Post-mortem action items: address root causes, not just symptoms.

Q4: What is an error budget and how does it affect engineering decisions?
A: An error budget is the allowed downtime derived from your SLO.
   
   Example:
   SLO: 99.9% availability → 0.1% errors allowed
   Monthly error budget: 43.2 minutes of downtime
   
   Error budget as a management tool:
   
   It creates a shared language between SRE and product teams.
   Product team wants to ship features fast (which introduces risk).
   SRE team wants stability (which means slower releases).
   
   Error budget resolves this tension:
   - If budget is healthy → ship features, take risks
   - If budget is low → slow down, invest in reliability
   
   Real conversation:
   "We want to do a big production migration this week."
   "We've already burned 80% of this month's error budget.
    If this migration causes even a small incident, we'll exhaust the budget.
    Can we delay until next month, or use a safer migration strategy?"
   
   Error budget policy formalization:
   Write it down: "If error budget < 50%, deployment freeze until budget recovers
   or SLO is revised." This removes subjectivity from the decision.
   
   Also drives SLO calibration:
   If budget is never burned → SLO might be too lenient (tighten it).
   If budget burns every month → SLO might be too tight, or reliability needs investment.

Q5: How do you set up alerting that avoids both false positives and missed incidents?
A: The two failure modes are:
   Alert fatigue: Too many false positive pages → on-call ignores alerts → real incidents missed.
   Missed incidents: Thresholds too conservative → real outages don't page.
   
   Key principles:
   
   1. Alert on SYMPTOMS, not causes:
      Page when users are impacted.
      Error rate > 5% → users can't checkout → PAGE
      CPU > 85% → might be fine if there's no user impact → TICKET
   
   2. Alert on SLO burn rate (multi-window, multi-burn-rate):
      Google SRE Workbook approach:
      Alert: burn_rate > 14.4 over past 1 hour AND over past 5 minutes
      → This means budget burning fast enough to exhaust in 5 days.
      High specificity (few false positives), good sensitivity (catches real incidents).
   
   3. Set appropriate duration: FOR 5 MINUTES, not for 30 seconds.
      Brief spikes that auto-recover shouldn't wake people up.
   
   4. Test your alerts:
      - Run regular "gameday" exercises (inject faults, verify alerts fire)
      - Check that resolved alerts actually fire when things break
      - Alert on "alert manager is healthy" (dead man's switch)
   
   5. Categorize alerts:
      Page (wake on-call now): User-impacting, high error rate, p99 > threshold
      Ticket (fix during business hours): Elevated warning, disk growing, cert expiring in 14 days
      Inform (dashboard only): Deployment happened, traffic spike
   
   6. Monthly alert review:
      Top 5 paging alerts → are they actionable? → tune or remove.
      Track "noise rate" (pages that required no action).

11. QUICK REFERENCE CHEAT SHEET
================================================================================

INCIDENT SEVERITY:
  P0   Complete outage, all users. Page NOW.
  P1   Major degradation, large % users. Page within 15 min.
  P2   Partial outage, workaround exists. Respond within 1 hour.
  P3   Minor issue. Create ticket, next sprint.

INCIDENT LIFECYCLE:
