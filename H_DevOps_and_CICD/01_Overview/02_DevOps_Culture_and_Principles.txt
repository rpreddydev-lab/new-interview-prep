1. THE THREE WAYS OF DEVOPS
================================================================================

Introduced by Gene Kim in "The Phoenix Project" and "The DevOps Handbook",
the Three Ways are the foundational principles underlying DevOps practices.

-------------------------------------------------------
THE FIRST WAY: FLOW (Systems Thinking)
-------------------------------------------------------
Focus: Left-to-right flow of work from Development → Operations → Customer

Principles:
  - Optimize for GLOBAL performance, not local optimization
  - Never pass known defects downstream
  - Never allow local optimization to degrade global flow
  - Increase flow by understanding the system as a whole

Practices:
  - Continuous Build, Integration, Test, Deployment
  - Limit Work in Progress (WIP)
  - Small batch sizes (deploy small, frequent changes)
  - Eliminate waste (unnecessary hand-offs, waiting, rework)

Analogy: A manufacturing assembly line. If one station optimizes at the expense
of the whole, the entire line suffers. Cars waiting in inventory = code waiting
to be deployed.

Example Anti-Pattern: Dev team has 95% test coverage, but the deployment to
Ops takes 3 weeks due to manual change approval boards. Flow is broken.

Example Practice: Feature branches merged daily, automated pipeline deploys to
staging in 15 minutes. Small batches flow through quickly.

-------------------------------------------------------
THE SECOND WAY: FEEDBACK (Amplifying Feedback Loops)
-------------------------------------------------------
Focus: Right-to-left feedback from Operations → Development to prevent problems
       from recurring

Principles:
  - Create fast and constant feedback at all stages
  - See problems as they occur
  - Swarm and solve problems to build new knowledge
  - Keep feedback loops short (don't wait for weekly reports)

Practices:
  - Automated tests providing immediate feedback on commits
  - Production monitoring feeding back to developers
  - Stopping the pipeline when quality gates fail
  - Telemetry (metrics, logs, traces) visible to all teams
  - Peer reviews and pair programming

Example Anti-Pattern: Production goes down, but the developer who wrote the
code doesn't know for 3 days because alerts only go to the Ops team.

Example Practice: When a deployment fails, Slack alerts include the commit
author, a link to the failing test, and a suggested rollback command. The dev
who broke it fixes it within minutes.

-------------------------------------------------------
THE THIRD WAY: CONTINUAL LEARNING AND EXPERIMENTATION
-------------------------------------------------------
Focus: Creating a culture of continual learning, experimentation, and risk-taking

Principles:
  - Create a high-trust culture where experimentation is encouraged
  - Allocate time for improvement of daily work
  - Use blameless post-mortems to learn from failures
  - Amplify learning by sharing knowledge broadly

Practices:
  - Blameless post-mortems after incidents
  - Game Days / Chaos Engineering (intentional failure injection)
  - Innovation days / hackathons (Google's 20% time concept)
  - Internal tech talks and documentation sharing
  - "If it hurts, do it more often" — deploy more often to improve deployment

Example Anti-Pattern: After a production outage, the responsible engineer is
blamed and reprimanded. Others hide problems to avoid punishment.

Example Practice: After every major incident, a blameless postmortem is held.
The root cause is documented publicly, action items assigned, and findings
shared with all engineering teams to prevent recurrence.

2. THE FIVE IDEALS (THE UNICORN PROJECT — GENE KIM)
================================================================================

Gene Kim's follow-up to the Phoenix Project introduced the Five Ideals:

1. LOCALITY AND SIMPLICITY
   - Teams should be able to make changes locally without requiring dependencies
     on other teams
   - Systems should be simple enough to reason about
   - Long dependency chains and tightly-coupled architectures violate this

2. FOCUS, FLOW, AND JOY
   - Developers should have uninterrupted time to do deep work
   - Flow state: being "in the zone" where work is easy and joyful
   - Eliminate interruptions, context-switching, meetings that block work
   - Related: "Maker's Schedule" (Paul Graham) vs "Manager's Schedule"

3. IMPROVEMENT OF DAILY WORK
   - Improve processes and systems continuously
   - Reduce toil (repetitive manual work)
   - Budget time for paying down technical debt
   - "It is not enough to just do your work; you must also improve how you work"

4. PSYCHOLOGICAL SAFETY
   - People must feel safe to speak up, report problems, experiment
   - Google's Project Aristotle found this as the #1 factor in team performance
   - Without safety: problems are hidden, mistakes recur, innovation dies

5. CUSTOMER FOCUS
   - Every team member understands how their work serves the customer
   - Avoid "vanity metrics" — focus on customer outcomes
   - Engineers directly interacting with customer feedback/telemetry

3. CALMS FRAMEWORK
================================================================================

CALMS is a framework for assessing DevOps culture and practices:

C — CULTURE
  - Collaborative environment between Dev and Ops
  - Shared ownership and responsibility
  - Trust, psychological safety
  - Willingness to change

A — AUTOMATION
  - Automate everything repetitive
  - CI/CD pipelines
  - Infrastructure provisioning
  - Testing, security scanning
  - "Automate the boring stuff"

L — LEAN
  - Eliminate waste (inventory, waiting, defects, over-processing)
  - Small batch sizes
  - Limit WIP
  - Value stream mapping to identify bottlenecks

M — MEASUREMENT
  - If you can't measure it, you can't improve it
  - DORA metrics (Deployment Frequency, Lead Time, CFR, MTTR)
  - Application metrics (latency, error rate, throughput)
  - Business metrics (conversion, revenue impact)

S — SHARING
  - Knowledge sharing across teams
  - Open source internally (InnerSource)
  - Blameless postmortems published
  - Runbooks and documentation maintained
  - "If knowledge stays in one person's head, it's a single point of failure"

4. PSYCHOLOGICAL SAFETY & BLAMELESS CULTURE
================================================================================

Psychological Safety (Dr. Amy Edmondson, Google Project Aristotle):
  - Definition: The belief that you won't be punished for speaking up
  - #1 predictor of high-performing teams at Google
  - Without it: Problems are hidden, risk-taking stops, innovation dies

Blameless Post-Mortems:
  - Originated at Google SRE (Site Reliability Engineering)
  - Premise: When incidents occur, the system failed — not the person
  - "Engineers don't come to work intending to cause outages"

Blameless Postmortem Structure:
  1. Timeline of events (factual, no blame)
  2. What went well
  3. What went wrong (systemic, not personal)
  4. Root Cause Analysis (5 Whys technique)
  5. Action Items (with owners and deadlines)
  6. Lessons Learned

The 5 Whys Technique:
  Problem: Production database is down
  Why 1: The disk is full
  Why 2: Log files were not rotated
  Why 3: Log rotation was not configured
  Why 4: The runbook doesn't include log rotation setup
  Why 5: There is no process to review/update runbooks
  Root Cause: No systematic process for maintaining operational runbooks

  Action Item: Create quarterly runbook review process

Just Culture (Sidney Dekker):
  - Distinguish between human error (inevitable) and reckless behavior (rare)
  - Punishing errors removes psychological safety and hides future problems
  - Build guardrails to prevent errors, don't punish the error itself

5. DEVOPS PRINCIPLES DEEP DIVE
================================================================================

A. EVERYTHING AS CODE
   - Infrastructure as Code (IaC)
   - Configuration as Code
   - Pipeline as Code
   - Policy as Code
   - Security as Code
   
   Why: Code can be version-controlled, reviewed, tested, automated, and
   audited. Documentation as Code (Docs-as-Code) keeps docs in sync with
   the codebase.

B. IMMUTABLE INFRASTRUCTURE
   - Never modify servers in place — replace them
   - Build a new image, deploy it, destroy the old one
   - Benefits: No configuration drift, reproducible deployments
   - Tools: Docker, Packer, AMIs, Terraform
   
   Configuration Drift: When servers that were once identical diverge over
   time due to manual changes. "Snowflake servers" — unique, fragile,
   irreplaceable.

C. IDEMPOTENCY
   - Running the same operation multiple times produces the same result
   - Critical for IaC and configuration management
   - Example: Running `terraform apply` twice doesn't create duplicate resources

D. FAIL FAST
   - Surface failures as early as possible in the pipeline
   - A failing unit test should stop the pipeline immediately
   - Don't let bad code reach production — catch it at unit test, not load test
   - "Fast feedback enables fast correction"

E. SINGLE SOURCE OF TRUTH
   - Git repository is the authoritative source for all configuration
   - No manual changes that aren't reflected in version control
   - GitOps: Git as the source of truth for cluster desired state

F. MINIMIZING WORK IN PROGRESS (WIP)
   - Limiting WIP reduces lead time and exposes bottlenecks
   - Kanban principle: "Stop starting, start finishing"
   - Large PRs sitting in review = WIP piling up
   - Benefit: Smaller batches = easier to review, test, and roll back

G. CONTINUOUS IMPROVEMENT (KAIZEN)
   - From Lean/Toyota Production System
   - Small, incremental improvements continuously
   - "Improve daily work, not just do daily work"
   - Retrospectives, hackathons, innovation days

6. TEAM TOPOLOGIES
================================================================================

From the book "Team Topologies" by Matthew Skelton and Manuel Pais:

Four Fundamental Team Types:

1. STREAM-ALIGNED TEAM
   - Aligned to a flow of work (product, service, user journey)
   - Full ownership from code to production
   - Example: "Payments Team" — owns the entire payment service
   - This is the "squad" model (Spotify model)

2. ENABLING TEAM
   - Helps stream-aligned teams overcome obstacles
   - Provides expertise that stream-aligned teams need
   - Example: "Platform Team" helps teams adopt Kubernetes
   - Temporary — transfers knowledge then steps back

3. COMPLICATED SUBSYSTEM TEAM
   - Owns a complex subsystem requiring deep specialist knowledge
   - Example: Real-time video encoding engine, ML inference platform
   - Reduces cognitive load on stream-aligned teams

4. PLATFORM TEAM
   - Provides internal platform as a product
   - Makes stream-aligned teams self-sufficient
   - Example: Internal Kubernetes platform, CI/CD toolchain, Developer Portal
   - Golden rule: Treat the internal platform like a product (with UX, docs)

Three Interaction Modes:
  1. Collaboration — work closely together (temporary, high bandwidth)
  2. X-as-a-Service — consume or provide something with minimal interaction
  3. Facilitating — one team helps another adopt new practices

Conway's Law:
  "Organizations which design systems are constrained to produce designs which
  are copies of the communication structures of those organizations."
  
  Reverse Conway Maneuver: Design your team structure to match the desired
  software architecture, not the other way around.

7. TOIL AND AUTOMATION
================================================================================

Toil (SRE concept, from Google):
  - Manual, repetitive, automatable, tactical work
  - Scales linearly with service growth
  - Provides no enduring value
  - Examples: Manual deployments, password resets, capacity provisioning

Why Toil is Harmful:
  - Prevents engineers from doing valuable work
  - Burns out high performers
  - Hides systemic problems (manual fixes mask root causes)
  - Technical debt accumulates

Google SRE Rule:
  No more than 50% of SRE time should be spent on toil.
  If toil exceeds 50%, the team must escalate and address systemic issues.

Automation Ladder (from most manual to most automated):
  1. Manual (run commands by hand)
  2. Documented runbooks (instructions in a wiki)
  3. Scripts (automate individual steps)
  4. Self-service (teams trigger automation themselves)
  5. Fully automated (system triggers itself based on conditions)

Toil vs Engineering Work:
  Toil                              | Engineering Work
  ----------------------------------|--------------------------------
  Manual scaling of servers         | Auto-scaling based on metrics
  Manually rotating credentials     | Automated secret rotation
  Copy-pasting deploy commands      | CI/CD pipeline
  Checking logs manually for errors | Alerting rules in Prometheus
  Writing the same report weekly    | Automated dashboard/report

8. COMMON ANTI-PATTERNS
================================================================================

A. "DEVOPS TEAM" (The Ops Team Renamed)
   - Creating a separate "DevOps Team" that owns all pipelines, tooling, and
     deployments is an anti-pattern
   - It recreates the silo — now "Dev vs DevOps" instead of "Dev vs Ops"
   - Correct approach: DevOps is embedded in all teams, or there's a Platform
     Team that supports all teams

B. SHADOW IT
   - Teams creating their own tools outside of sanctioned platforms
   - Leads to inconsistency, security gaps, duplicated effort
   - Solution: Make the official platform easy enough that Shadow IT isn't
     attractive ("pave the road, don't build a wall")

C. MANUAL CHANGE APPROVAL BOARDS (CABs)
   - Weekly meetings approving every change
   - Bottleneck that kills deployment velocity
   - Solution: Automate controls. If you can't automate approval, automate
     detection and rollback

D. BROKEN WINDOWS THEORY
   - Ignoring small problems (flaky tests, ignored alerts) leads to larger ones
   - "If we let one flaky test slide, we'll let ten slide"
   - Fix alerts that fire: either fix the underlying problem or remove the alert

E. SNOWFLAKE SERVERS
   - Manually configured servers that are irreplaceable
   - "The database server? Don't touch it — only Bob knows how it works"
   - Solution: Immutable infrastructure, IaC, documentation

F. LONG-LIVED FEATURE BRANCHES
   - Branches open for weeks/months
   - Massive merge conflicts, integration hell
   - Solution: Trunk-based development, feature flags

G. ENVIRONMENT PARITY GAPS
   - "Works on my machine" / "Works in staging but not prod"
   - Different OS, library versions, configurations between environments
   - Solution: Containers, IaC, environment parity practices

9. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What are the Three Ways of DevOps?
A: The Three Ways are foundational principles from Gene Kim's "DevOps Handbook":
   1. Flow (First Way): Optimize work flowing left-to-right from Dev to Ops to
      customer. Use small batches, automate, and eliminate waste.
   2. Feedback (Second Way): Create fast feedback loops flowing right-to-left.
      Catch problems at the source, not downstream.
   3. Continual Learning (Third Way): Foster a culture of experimentation,
      blameless learning from failures, and improvement of daily work.

Q2: What is the CALMS framework?
A: CALMS stands for Culture, Automation, Lean, Measurement, and Sharing. It's
   a framework for assessing DevOps maturity. Culture is the foundation —
   without a collaborative, trust-based culture, tools and automation won't
   succeed. Automation removes toil. Lean eliminates waste. Measurement
   provides data-driven improvement. Sharing distributes knowledge.

Q3: What is psychological safety and why does it matter in DevOps?
A: Psychological safety is the belief that you won't be punished for speaking
   up, making mistakes, or raising concerns. Google's Project Aristotle found
   it was the #1 factor in team performance. In DevOps, it enables blameless
   postmortems (teams openly discuss failures), experimentation (trying new
   approaches without fear), and rapid detection of problems (people report
   issues early rather than hiding them).

Q4: What is toil and how does Google SRE handle it?
A: Toil is manual, repetitive, automatable work that scales with service growth
   and provides no enduring value. Google SRE mandates that no engineer should
   spend more than 50% of their time on toil. If toil exceeds this, the team
   escalates to get engineering time allocated to automate it. The goal is to
   continuously reduce toil so engineers can focus on valuable engineering work.

Q5: What is Conway's Law and how does it relate to DevOps?
A: Conway's Law states that organizations produce systems that mirror their
   communication structures. If you have separate Dev and Ops teams that don't
   communicate, you'll produce software that is hard to deploy. The "Reverse
   Conway Maneuver" means designing your team structure to match the desired
   architecture — forming cross-functional teams that own microservices end-to-
   end, enabling independent deployment and DevOps practices.

Q6: What is an "immutable infrastructure" and why is it important?
A: Immutable infrastructure means never modifying a running server — instead,
   you build a new server image (AMI, Docker image), deploy it, and destroy
   the old one. This eliminates configuration drift (where servers diverge from
   their intended state), makes deployments reproducible, and simplifies
   rollbacks (just redeploy the previous image). It's enabled by containerization
   and IaC tools like Terraform.

Q7: Describe a blameless postmortem process.
A: A blameless postmortem is a structured review after an incident, focused on
   improving systems rather than assigning blame. The process:
   1. Build a factual timeline with data
   2. Identify what went well
   3. Identify what went wrong (systemic failures: tooling, monitoring gaps,
      process issues — not "Bob made a mistake")
   4. Run 5 Whys root cause analysis
   5. Create concrete action items with owners and deadlines
   6. Publish the postmortem broadly so others can learn
   The philosophy: errors are human and inevitable; the system should prevent
   them from causing outages.

10. QUICK REFERENCE CHEAT SHEET
================================================================================

The Three Ways:
  1. Flow → optimize left-to-right flow (small batches, automation)
  2. Feedback → amplify right-to-left feedback (fast alerts, test results)
  3. Learning → blameless culture, experiments, continual improvement

CALMS:
  Culture, Automation, Lean, Measurement, Sharing

Key Concepts:
  - Toil: manual, repetitive, automatable work (should be <50% of time)
  - Blameless Postmortem: fix systems, not people; 5 Whys root cause analysis
  - Psychological Safety: safe to speak up, experiment, admit mistakes
  - Immutable Infrastructure: replace, don't modify; eliminates config drift
  - Idempotency: same operation, same result every time
  - Conway's Law: team structure → software structure

Team Topologies:
  1. Stream-aligned (owns a product end-to-end)
  2. Enabling (helps others overcome obstacles)
  3. Complicated Subsystem (expert-knowledge systems)
  4. Platform (internal platform as a product)

Anti-patterns to avoid:
  - "DevOps Team" silo
  - Manual Change Approval Boards
  - Long-lived feature branches
  - Snowflake servers
  - Environment parity gaps
