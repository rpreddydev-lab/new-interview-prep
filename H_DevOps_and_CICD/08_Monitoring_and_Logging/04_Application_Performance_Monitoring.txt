1. APM OVERVIEW
================================================================================

What is APM (Application Performance Monitoring)?
  Code-level performance visibility for applications in production.
  
  APM answers:
  - Which endpoint is slow (and exactly which code line is slow)?
  - What database query is taking 3 seconds?
  - Are we experiencing N+1 query problems?
  - How is performance impacting users right now?
  - What's the throughput/error rate per API endpoint?

Infrastructure Monitoring vs APM:
  
  ┌─────────────────────────────┬────────────────────────────────────┐
  │ Infrastructure Monitoring   │ APM                                │
  ├─────────────────────────────┼────────────────────────────────────┤
  │ CPU, memory, disk, network  │ Request latency by endpoint        │
  │ Node-level metrics          │ Error rate by service/operation    │
  │ Host health                 │ Database query time                │
  │ Prometheus, CloudWatch      │ Downstream service call latency    │
  │ "Is the server OK?"         │ "Is the APPLICATION performing?"   │
  └─────────────────────────────┴────────────────────────────────────┘

Key APM Capabilities:
  Transaction tracing:     Record each incoming request end-to-end
  Distributed tracing:     Follow a request across microservices
  Code profiling:          Identify slow functions/methods
  Database monitoring:     Capture and analyze SQL/NoSQL queries
  Error tracking:          Group, count, and surface exceptions
  Dependency mapping:      Auto-discover service dependencies
  Apdex score:             User satisfaction metric (0.0-1.0)

Apdex Score:
  Application Performance Index — standardized satisfaction metric.
  
  Apdex T (threshold) = target response time (e.g., 0.5 seconds)
  
  Satisfied:   response_time <= T
  Tolerating:  T < response_time <= 4T
  Frustrated:  response_time > 4T
  
  Apdex = (Satisfied + Tolerating/2) / Total Requests
  
  Score 1.0 = perfect; Score 0.0 = all users frustrated.

2. DATADOG APM
================================================================================

How it Works:
  Datadog Agent runs on each host (or as sidecar).
  Application sends traces via ddtrace library (or auto-instrumentation).
  Traces enriched with host/container/K8s metadata.

Instrumentation (Python example):
  # Install:
  pip install ddtrace
  
  # Auto-instrumentation (zero code change):
  DD_SERVICE="payment-service" \
  DD_ENV="production" \
  DD_VERSION="1.2.3" \
  DD_AGENT_HOST="datadog-agent" \
  ddtrace-run python app.py
  
  # Manual span creation:
  from ddtrace import tracer
  
  @tracer.wrap(service="payment-service", resource="process_payment")
  def process_payment(order_id: str) -> dict:
      with tracer.trace("payment.validate") as span:
          span.set_tag("order_id", order_id)
          validate_order(order_id)
      
      with tracer.trace("payment.charge") as span:
          result = charge_card(order_id)
          span.set_tag("amount", result["amount"])
          return result

Datadog APM + Kubernetes:
  # values.yaml for Datadog Helm chart:
  datadog:
    apiKey: "<YOUR_API_KEY>"
    apm:
      enabled: true
      portEnabled: true
    logs:
      enabled: true
      containerCollectAll: true
    processAgent:
      enabled: true
    
    # Admission controller (auto-inject APM library):
    admissionController:
      enabled: true
      mutateUnlabelled: false
  
  # In your application Deployment:
  metadata:
    labels:
      tags.datadoghq.com/env: "production"
      tags.datadoghq.com/service: "payment-service"
      tags.datadoghq.com/version: "1.2.3"
    annotations:
      admission.datadoghq.com/java-lib.version: "latest"  # Auto-inject Java agent

Unified Service Tagging:
  env, service, version tags must be applied consistently everywhere:
  - Kubernetes labels/annotations
  - Application environment variables
  - Datadog Agent configuration
  
  This allows correlation: trace ↔ log ↔ metric all by env+service+version.

Datadog APM Features:
  Service Map:            Auto-discovered dependency graph
  Flame Graphs:           Visualize time spent in each code span
  SQL Analysis:           Top queries, slow queries, query plan
  Error Tracking:         Group similar errors, first/last seen, count
  Continuous Profiler:    Low-overhead code profiling in production
  Watchdog:              ML-based anomaly detection

3. NEW RELIC APM
================================================================================

How it Works:
  New Relic agent added to application (Java agent JAR, Python package, etc.).
  Reports to New Relic OTEL-based backend.
  Query with NRQL (New Relic Query Language — SQL-like).

Instrumentation (Java):
  # Add -javaagent to JVM args:
  JAVA_OPTS="-javaagent:/opt/newrelic/newrelic.jar"
  
  # newrelic.yml:
  common: &default_settings
    license_key: '<YOUR_LICENSE_KEY>'
    app_name: payment-service
    distributed_tracing:
      enabled: true
    logs_in_context:
      enabled: true    # Correlate logs with traces

NRQL Queries:
  -- Average response time by service:
  SELECT average(duration) FROM Transaction
  WHERE appName = 'payment-service'
  FACET name SINCE 1 hour ago
  
  -- Error rate:
  SELECT percentage(count(*), WHERE error IS true) FROM Transaction
  WHERE appName = 'payment-service' SINCE 30 minutes ago
  
  -- Throughput (requests per minute):
  SELECT rate(count(*), 1 minute) FROM Transaction
  WHERE appName = 'payment-service' TIMESERIES

New Relic Features:
  APM Summary:     Service health at a glance
  Transactions:    Individual transaction breakdown
  Databases:       Query analysis, slow query tracing
  External Services: Calls to downstream APIs, DB, cache
  Browser:         RUM built-in
  Alerts:          NRQL-based alerting conditions

4. DYNATRACE
================================================================================

Key Differentiator: OneAgent — single agent auto-discovers everything.
  Install OneAgent → it auto-instruments all processes on the host.
  No code changes needed for mainstream languages/frameworks.

Davis AI:
  Dynatrace AI engine that performs root cause analysis automatically.
  "Deployment of payment-service v1.2.3 caused 40% error rate increase."
  Detects anomalies, correlates events, surfaces root cause.

Dynatrace Architecture:
  OneAgent (host/pod) → ActiveGate (gateway, optional) → Dynatrace SaaS
  
  PurePath Technology:
  End-to-end distributed traces captured automatically.
  Captures EVERY request (no sampling by default).

Kubernetes Integration:
  Dynatrace Operator deployment:
  kubectl apply -f https://github.com/Dynatrace/dynatrace-operator/releases/...
  
  # DynaKube custom resource:
  apiVersion: dynatrace.com/v1beta1
  kind: DynaKube
  metadata:
    name: dynakube
    namespace: dynatrace
  spec:
    apiUrl: https://<tenant>.live.dynatrace.com/api
    oneAgent:
      cloudNativeFullStack:
        tolerations:
        - effect: NoSchedule
          key: node-role.kubernetes.io/master

5. OPENTELEMETRY AS VENDOR-NEUTRAL APM
================================================================================

Why OpenTelemetry (OTel)?
  Avoid vendor lock-in.
  One instrumentation → send to Jaeger, Zipkin, Datadog, Honeycomb, etc.
  
  OTel provides:
  - SDK (instrument your code)
  - Auto-instrumentation (framework-level, zero code change)
  - Collector (receive, process, export telemetry)
  - OTLP protocol (standard transport format)

OTel SDK (Python):
  from opentelemetry import trace
  from opentelemetry.sdk.trace import TracerProvider
  from opentelemetry.sdk.trace.export import BatchSpanProcessor
  from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
  
  # Initialize tracer:
  provider = TracerProvider(
      resource=Resource.create({
          "service.name": "payment-service",
          "service.version": "1.2.3",
          "deployment.environment": "production",
      })
  )
  
  # Export to OTel Collector:
  exporter = OTLPSpanExporter(endpoint="http://otel-collector:4317")
  provider.add_span_processor(BatchSpanProcessor(exporter))
  trace.set_tracer_provider(provider)
  
  tracer = trace.get_tracer("payment-service")
  
  def process_payment(order_id: str):
      with tracer.start_as_current_span("process_payment") as span:
          span.set_attribute("order.id", order_id)
          
          with tracer.start_as_current_span("validate_order") as child:
              validate_order(order_id)
          
          with tracer.start_as_current_span("charge_card") as child:
              result = charge_card(order_id)
              child.set_attribute("payment.amount", result["amount"])
          
          return result

OTel Auto-Instrumentation (Python):
  pip install opentelemetry-distro
  opentelemetry-bootstrap -a install   # Install instrumentation libs
  
  OTEL_SERVICE_NAME=payment-service \
  OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317 \
  opentelemetry-instrument python app.py   # Auto-instruments Flask, requests, SQLAlchemy, etc.

OTel Collector (Kubernetes):
  # otel-collector-config.yaml:
  receivers:
    otlp:
      protocols:
        grpc:
          endpoint: 0.0.0.0:4317
        http:
          endpoint: 0.0.0.0:4318
  
  processors:
    batch:
      send_batch_size: 1000
      timeout: 10s
    memory_limiter:
      check_interval: 1s
      limit_mib: 512
  
  exporters:
    # Send to Jaeger for traces:
    jaeger:
      endpoint: jaeger-collector:14250
      tls:
        insecure: true
    
    # Send to Prometheus for metrics:
    prometheus:
      endpoint: "0.0.0.0:8889"
    
    # Send to Loki for logs:
    loki:
      endpoint: http://loki:3100/loki/api/v1/push
    
    # Send to multiple destinations:
    datadog:
      api:
        key: ${DATADOG_API_KEY}
  
  service:
    pipelines:
      traces:
        receivers: [otlp]
        processors: [memory_limiter, batch]
        exporters: [jaeger, datadog]
      metrics:
        receivers: [otlp]
        processors: [memory_limiter, batch]
        exporters: [prometheus]
      logs:
        receivers: [otlp]
        processors: [batch]
        exporters: [loki]

6. PROFILING AND CODE-LEVEL DIAGNOSTICS
================================================================================

What is Profiling?
  Continuous or on-demand measurement of CPU, memory, I/O at function level.
  Answer: "Which function is consuming the most CPU in production?"

Continuous Profiling:
  Low-overhead profiling that runs always in production.
  
  Tools:
  - Datadog Continuous Profiler
  - Pyroscope (open source, supports Go/Python/Java/Ruby)
  - Parca (open source, Go)
  - Google Cloud Profiler
  
  What it shows:
  - Flame graphs: CPU time breakdown by function call stack
  - Memory allocation hotspots
  - Lock contention in concurrent code

Pyroscope (Open Source):
  # Instrument Python:
  import pyroscope
  
  pyroscope.configure(
    application_name="payment-service",
    server_address="http://pyroscope:4040",
    tags={"env": "production", "version": "1.2.3"}
  )
  
  # Run Go application (no code change):
  pyroscope exec -server-address=http://pyroscope:4040 ./my-go-app

Common Performance Issues Found with APM:
  N+1 Query:    Load 100 users → 100 separate DB queries for each user's orders
                Fix: Use JOINs, eager loading, or caching
  
  Slow queries: Missing index on high-cardinality column
                Fix: Add database index, optimize query
  
  External call latency: Payment service calls external API synchronously
                         Fix: Cache, async, circuit breaker, timeout
  
  Memory leak:  Memory allocation grows without bound
                Fix: Find unclosed connection, unbounded cache

7. SYNTHETIC MONITORING
================================================================================

What is Synthetic Monitoring?
  Simulated user interactions from external locations.
  Tests your service from the OUTSIDE (not relying on internal metrics).
  
  Unlike RUM (real users): Synthetic runs continuously, even with no users.
  
  Use cases:
  - Detect outages before users do (1-minute interval checks globally)
  - Test critical user journeys (checkout flow, login)
  - Measure performance from different geographic regions
  - Verify third-party dependencies (payment gateway availability)

Types of Synthetic Tests:
  
  API Tests (HTTP checks):
  - Check HTTP status code, response time, response body
  - Simple, low-cost, good for uptime
  
  Browser Tests (scripted UI flows):
  - Selenium/Playwright-based scripted interactions
  - Simulate user: login → add to cart → checkout → confirm
  - Capture screenshots on failure
  - More complex, higher cost, catches UI regressions

Datadog Synthetics Example:
  # API test (using Terraform for IaC):
  resource "datadog_synthetics_test" "checkout_api" {
    type    = "api"
    subtype = "http"
    name    = "Checkout API - POST /api/checkout"
    status  = "live"
    
    request_definition {
      method = "POST"
      url    = "https://api.myapp.com/checkout"
      body   = jsonencode({ order_id = "test-123" })
    }
    
    request_headers = {
      "Content-Type"  = "application/json"
      "Authorization" = "Bearer {{checkout_api_key}}"
    }
    
    assertion {
      type     = "statusCode"
      operator = "is"
      target   = "200"
    }
    
    assertion {
      type     = "responseTime"
      operator = "lessThan"
      target   = 2000  # 2 seconds
    }
    
    assertion {
      type        = "body"
      operator    = "contains"
      target      = "order_id"
    }
    
    locations = [
      "aws:us-east-1",
      "aws:eu-west-1",
      "aws:ap-southeast-1"
    ]
    
    options_list {
      tick_every           = 60   # Every 60 seconds
      min_location_failed  = 1    # Alert if 1+ location fails
    }
  }

AWS CloudWatch Synthetics:
  # Canary (Lambda-based synthetic):
  resource "aws_synthetics_canary" "checkout_health" {
    name                 = "checkout-health"
    artifact_s3_location = "s3://my-canary-artifacts/"
    execution_role_arn   = aws_iam_role.canary.arn
    handler              = "canary.handler"
    runtime_version      = "syn-python-selenium-1.3"
    
    schedule {
      expression = "rate(5 minutes)"
    }
    
    run_config {
      timeout_in_seconds = 60
    }
  }

Multi-Step API Test (Datadog):
  Test sequence:
  1. POST /auth/login → extract JWT token
  2. POST /cart/add → add item using token
  3. GET /cart → verify item is in cart
  4. POST /checkout → place order
  5. GET /orders/{id} → verify order created

8. REAL USER MONITORING (RUM)
================================================================================

What is RUM?
  Monitoring based on actual user sessions in the browser/mobile app.
  Captures real user performance, not simulated.

What RUM Measures:
  Core Web Vitals (Google's performance metrics):
  
  LCP — Largest Contentful Paint:
    Time for largest content to load.
    Good: < 2.5s
    
  FID — First Input Delay (replaced by INP in 2024):
    Time from first user input to browser response.
    Good: < 100ms
    
  CLS — Cumulative Layout Shift:
    Visual stability — do elements shift unexpectedly?
    Good: < 0.1
  
  Other RUM metrics:
  - Page load time (by country, browser, device)
  - Time to First Byte (TTFB) — server response time
  - JavaScript error rate
  - Resource timing (CSS, JS, image load times)
  - User sessions and replays

RUM Tools:
  Datadog RUM:   Full session replay, Core Web Vitals, error tracking
  New Relic Browser: Similar, integrates with APM
  Dynatrace:     Session replay, user journey analysis
  Sentry:        Error tracking + performance (smaller budget option)
  Google Analytics: Basic Core Web Vitals (free)

Sentry (Error Tracking + Performance):
  # Install Sentry SDK:
  pip install sentry-sdk[flask]
  
  import sentry_sdk
  from sentry_sdk.integrations.flask import FlaskIntegration
  
  sentry_sdk.init(
    dsn="https://your-dsn@sentry.io/project-id",
    environment="production",
    release="payment-service@1.2.3",
    integrations=[FlaskIntegration()],
    traces_sample_rate=0.1,       # Sample 10% of transactions
    profiles_sample_rate=0.1,     # Sample 10% for profiling
    send_default_pii=False,       # Don't send personal data
  )

9. SLO-BASED MONITORING
================================================================================

Connecting APM to SLOs:
  Define SLOs at the service level:
  
  SLO 1: Availability
    SLI: percentage of HTTP requests returning 2xx or 3xx
    SLO: 99.9% over 30 days
  
  SLO 2: Latency
    SLI: percentage of requests completing in < 500ms
    SLO: 99% of requests within 500ms over 30 days
  
  Error budget = 0.1% × 30 days × 24 hours × 60 min = 43.2 minutes/month

Datadog SLOs (via Terraform):
  resource "datadog_service_level_objective" "availability" {
    name        = "Payment API Availability"
    type        = "metric"
    description = "99.9% of payment requests succeed"
    
    query {
      numerator   = "sum:trace.servlet.request.hits{service:payment-service,!http.status_code:5*}.as_count()"
      denominator = "sum:trace.servlet.request.hits{service:payment-service}.as_count()"
    }
    
    thresholds {
      timeframe       = "30d"
      target          = 99.9
      warning         = 99.95
    }
  }

Alerting on Error Budget Burn Rate:
  Instead of alert "error rate > threshold", alert on how fast you're burning error budget.
  
  Burn rate 1 = consuming error budget at normal speed (OK)
  Burn rate 14.4 = burning budget 14.4x faster → 5% of budget gone in 1 hour
  
  Multi-window alert (Google SRE book recommendation):
  - Alert: burn rate > 14.4 AND measured over 1h AND confirmed over 5min
  → Pages immediately for critical burns.

10. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: What is APM and why is it important in a microservices architecture?
A: APM (Application Performance Monitoring) provides code-level performance 
   visibility for applications in production.
   
   It goes beyond infrastructure monitoring (CPU, memory) to answer:
   - Which API endpoint is slow?
   - What database query is causing latency?
   - Which downstream service call is failing?
   - Where in the code is time being spent?
   
   In a monolith, you can attach a debugger or add logs. In microservices with
   50+ services, a single user request flows through multiple services. Without APM:
   - You see high latency but can't tell which service is responsible
   - Errors are hard to trace across service boundaries
   - You can't identify N+1 queries in individual services
   
   APM solves this through distributed tracing (correlate spans across services),
   error tracking (group exceptions, first seen, frequency), and database monitoring
   (capture actual SQL queries with execution time).
   
   When to choose commercial APM (Datadog/Dynatrace/New Relic) vs open source
   (OTel + Jaeger/Grafana Tempo):
   Commercial: Less ops overhead, better out-of-box dashboards, AI anomaly detection.
   Open source: Cost control at large scale, no vendor lock-in, full data ownership.

Q2: How does OpenTelemetry help with observability?
A: OpenTelemetry is a vendor-neutral observability framework that standardizes:
   - How applications are instrumented (SDK)
   - How telemetry is collected and processed (Collector)
   - How telemetry is transmitted (OTLP protocol)
   
   Without OTel, every vendor has their own agent:
   - Switching from Jaeger to Datadog requires re-instrumenting every service.
   - Each vendor's agent has different APIs, overhead, capabilities.
   
   With OTel:
   - Instrument once using OTel SDK
   - OTel Collector receives all telemetry (traces, metrics, logs)
   - Configure collectors to export to any backend(s)
   - Change backends without touching application code
   
   OTel also enables:
   - Auto-instrumentation: framework-level tracing with zero code changes
     (Flask, Django, FastAPI, SQLAlchemy, requests, boto3 all auto-traced)
   - Semantic conventions: standardized attribute names (http.method, db.system)
     means dashboards work across services consistently
   - Context propagation: W3C traceparent header automatically injected into
     HTTP calls, gRPC, Kafka messages

Q3: What is synthetic monitoring and how does it differ from Real User Monitoring (RUM)?
A: Synthetic Monitoring simulates user interactions from external locations using
   scripts. It runs proactively on a schedule (e.g., every 60 seconds).
   
   RUM captures performance from ACTUAL users in real time.
   
   Key differences:
   
   Synthetic: Consistent, repeatable — same test script every time.
   Catches outages even when no users are online (middle of night).
   Can test specific user flows that might be infrequent.
   Low data volume, predictable cost.
   
   RUM: Real user data — shows actual geographic distribution, device types.
   Captures edge cases (slow mobile in rural India, old browser in IE11).
   Requires traffic — no data when no users.
   High data volume at scale.
   
   In practice, use BOTH:
   - Synthetic for alerting on outages and testing critical flows continuously
   - RUM for understanding real user experience and performance by segment
   
   Common approach:
   - Synthetic: 30-second API health checks from 5 regions + 5-minute browser test
   - RUM: Core Web Vitals by country/device, JS error rate
   - Alert: Synthetic test failure (outage) → page immediately
   - Investigate: RUM data to understand user impact

Q4: How do you approach identifying a performance regression after a deployment?
A: Systematic approach using APM data:
   
   1. Detect with deployment markers + metrics:
      - Mark deployments in APM tool (Datadog deployment tracking or annotation in Grafana)
      - Compare error rate and latency BEFORE and AFTER deployment
      - Alert condition: p99 latency increases >20% post-deploy
   
   2. Narrow down in APM service map:
      - Check which services had latency increase (the change may impact downstream)
      - Often a database service slows down, causing all callers to slow
   
   3. Analyze traces from affected period:
      - Open a slow trace from after the deployment
      - Compare trace flame graph to baseline (before deployment)
      - Identify which span suddenly became slower
   
   4. Drill into the specific span:
      - DB span slow? → Check slow query logs, EXPLAIN ANALYZE the query
        (a new query path might miss an index, or a new query is doing full scans)
      - External service slow? → Check if the downstream service had issues
      - In-process span slow? → Check if new code added expensive operation in hot path
   
   5. Fix and verify:
      - Make the fix (add index, rewrite query, optimize code)
      - Re-deploy, confirm metrics return to baseline
      - Post-incident review: add monitoring so this is caught faster next time
   
   Prevention:
   - Load test in staging with production-like data before deploying
   - Set up automated performance comparisons in CI/CD (benchmark tests)
   - Canary deployments: route 5% of traffic to new version, compare metrics

Q5: What are Core Web Vitals and why do they matter for operations teams?
A: Core Web Vitals are Google's standardized metrics for web performance:
   
   LCP — Largest Contentful Paint:
   Time to render the largest content element (image, text block).
   Good: < 2.5s. Affects Google SEO ranking.
   Common causes of slow LCP: slow server, large images, render-blocking JS
   
   INP — Interaction to Next Paint (replaced FID in 2024):
   Responsiveness of page to user interactions (clicks, taps, keystrokes).
   Good: < 200ms. Long JavaScript tasks blocking main thread.
   
   CLS — Cumulative Layout Shift:
   How much the page layout shifts unexpectedly (images without dimensions,
   ads loading late, dynamic content injected above existing content).
   Good: < 0.1
   
   Why operations teams care:
   - SEO: Google uses Core Web Vitals in page ranking → bad performance = less traffic
   - Revenue correlation: Every 100ms of latency = 1% fewer conversions (Amazon data)
   - SLO: Define SLOs on Core Web Vitals, alert when they degrade
   
   Operationalizing Core Web Vitals:
   1. Measure with RUM tool (Datadog RUM, Sentry, Google Search Console)
   2. Segment by page type, geography, device (mobile usually worse)
   3. Track trends — did a deployment worsen CLS? (added dynamic banner?)
   4. Optimize: image sizing, lazy loading, CDN, HTTP/2, preload hints

11. QUICK REFERENCE CHEAT SHEET
================================================================================

APM TOOLS:
  Datadog APM     Unified service tagging, flamegraphs, Watchdog AI
  New Relic       Auto-instrumentation, NRQL queries
  Dynatrace       OneAgent auto-discovery, Davis AI root cause
  OpenTelemetry   Vendor-neutral SDK+Collector+OTLP (use with Jaeger/Tempo)

OTEL SETUP:
  Install SDK     → Instrument code (or use auto-instrumentation)
  OTel Collector  → Receive, process, export telemetry
  OTLP            → Standard transport (gRPC port 4317, HTTP port 4318)

SYNTHETIC MONITORING:
  API tests       HTTP checks (status code, response time, body content)
  Browser tests   Scripted UI flow (login → add to cart → checkout)
  RUM             Real user performance (LCP, CLS, INP, JS errors)

CORE WEB VITALS:
  LCP   Largest Contentful Paint  < 2.5s  (page load)
  INP   Interaction to Next Paint < 200ms (interactivity)
  CLS   Cumulative Layout Shift   < 0.1   (visual stability)

APM COMMON ISSUES:
  N+1 query      100 objects → 100 DB queries instead of 1 JOIN
  Slow query     Missing index on frequently-queried column
  Memory leak    Memory grows without bound (unclosed connection/cache)
  Blocking call  Synchronous external API call in request hot path

PERFORMANCE DEBUGGING STEPS:
  1. Detect with deployment markers + metrics comparison
  2. Narrow to service via service map
  3. Open traces from affected period
  4. Compare flame graph before/after deployment
  5. Drill into slow span (DB/external/in-process)
  6. Fix + verify + post-mortem
